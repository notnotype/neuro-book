# 0.9.0：Application State catalog v3 与 Agent Session v2

## 影响

本版本把应用数据库、Agent 图片附件和 Agent Session 统一纳入启动前迁移。Session metadata 升级为 schema v2，只用可选的 `currentProjectRoot` 记录 Current Project；旧 `workspaceRoot`、`workspaceKey` 和 `projectPath` 不再被运行时读取。

旧 Session 的消息、分支和可证明的工具状态会保留。指向已删除 Project 的 Session 仍可查看，但执行时返回 `current_project_missing`；只有无法从旧 header 确定 Project 归属的 Session 才会标记为需要检查，并在执行时返回 `migration_review_required`。历史工具参数无法安全改写时会保留原文和 warning，不会误把整个 Session 标成待恢复。

早期 Session v2 迁移曾把 3 份可以确定 Project 的 Session 错误标成待恢复，并把迁移执行时间写成最后活动时间。第四个自动步骤会从原迁移 backup 和 manifest 重建这些前缀，保留迁移后的 append-only 新记录，并恢复真实最后活动时间；它按 manifest 扫描，不硬编码 Session ID。

## 自动步骤

Release 声明为 `policy: automatic`，按以下顺序执行：

1. `app-sqlite`：checkpoint App SQLite，逐字节备份后应用缺失 schema migration。
2. `agent-attachment-v1`：把旧图片内容迁为 Attachment 引用。
3. `agent-session-v2`：离线转换 Session JSONL，并发布 complete v2 sentinel。
4. `agent-session-v2-review-repair`：修复早期 Session v2 的错误 review、历史路径投影和迁移时间污染。

NeuroBook Manager 管理的 Source、Product、Container 和 Windows Portable 会在 install、update 或 start 时自动完成。迁移成功后重复启动无副作用。

顶层 catalog 中只有 `applied` 表示对应不可变合同已经完成。`skipped` 表示上次检查时没有工作，后续 `plan` 仍会重新检查；因此已经写成 complete v3、但早期跳过 review repair 的 State Root 也会自动发现待修复 Session，并用新的 v3 runId 执行 repair。无需手工删除或改写 sentinel。

## 非 Manager 启动

直接运行源码或 Product 时不会自动修改数据。启动提示迁移未完成后，在相同 State Root 和目标版本代码下执行：

```bash
bun run migrate:application-state -- --plan
bun run migrate:application-state -- --apply
```

`--plan` 不创建数据库、目录、backup、journal 或 sentinel。保存返回的 `runId`；若 apply 中断，用同一个 runId 执行 `--resume` 或 `--rollback`，不要重新发起另一个 apply。

## 备份位置

Product runner 的迁移资料位于 Workspace Root：

- 总 sentinel：`.nbook/agent/migrations/application-state.json`
- 总 journal：`.nbook/agent/migrations/application-state/<runId>/journal.json`
- App SQLite：`.nbook/agent/migrations/app-sqlite/<stepRunId>/`
- Attachment：`.nbook/agent/migrations/attachment-v1/<stepRunId>/`
- Session v2：`.nbook/agent/migrations/session-v2/<stepRunId>/`
- Session v2 review repair：`.nbook/agent/migrations/session-v2-review-repair/<stepRunId>/`

Session 与 Attachment 目录保存 manifest、journal、报告和实际变化文件的 backup。Manager 还会在 Installation Root `.deploy/backups/<operationId>/` 保存整个安装/更新事务使用的外层备份，其中 App SQLite 位于 `database/app.sqlite`。

## 回滚

Product runner 的 `--rollback --run-id <runId>` 按 `agent-session-v2-review-repair → agent-session-v2 → agent-attachment-v1 → app-sqlite` 反序恢复，并逐字节还原进入该 run 前的 Application State sentinel。Manager 的安装/更新/start 失败恢复会先终止本次候选，再调用该回滚，然后恢复外层数据库快照和旧 Product。

若 rollback 报告 checksum、journal 或 backup 损坏，迁移会 fail closed。此时不要启动新旧 Product 或手工拼接 Session；先复制完整 State Root 和 `.deploy`，保留报错与 runId，再人工审计。

Manager 只有在确认本次候选进程或容器已经终止后才会开始回滚。若候选终止失败，状态回滚不会继续；若 Product rollback 失败，Manager 会保留 Operation Journal、staging runner 和 backup，供下一次 start/update 继续恢复。不要手工删除 `.deploy/staging`、`.deploy/backups` 或 Journal 指向的 Source Dev worktree。

## 已知限制

- `migrationReview` 只表示 `current_project_unresolved`，不会阻断整个实例升级；对应 Session 在 Project Picker 重绑 Project 或明确改为 Workspace Root Session 前不可执行。
- complete v1/v2 sentinel 会创建新的 v3 run；incomplete 旧 run 必须先按提示 resume 或 rollback，不能直接发起新 apply。
- complete v3 仍会复查曾 skipped 的动态步骤；发现 repair 工作时返回新的 `planned`，没有工作时才返回 `already_current`。
- 本版本没有已知的 release-level `manual_required` 数据形状。若规划阶段返回该状态，必须按 JSON 中的 `guide` 处理，不能继续 apply。
