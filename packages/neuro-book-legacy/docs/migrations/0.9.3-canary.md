# 0.9.3-canary 迁移指南（限量 canary，已发布）

> 对应公开 tag：`v0.9.3-canary.20260807.175842Z.771ac42b`。GitHub Release：[NeuroBook v0.9.3-canary](https://github.com/notnotype/neuro-book/releases/tag/v0.9.3-canary.20260807.175842Z.771ac42b)。

## 发布版本

- NeuroBook：`v0.9.3-canary.20260807.175842Z.771ac42b`
- Manager：`manager-v0.1.0-canary.52`
- 这是限量 canary，不是 stable 发布；签名安装器、updater 和最终 Desktop 框架仍不在发布承诺内。

## 迁移策略

- **Application State：`policy: none`。** 本版本没有新的数据库 schema 迁移；现有 Manager 的 Application State plan/apply 流程保持不变。
- Agent Job 历史从旧的 `<Workspace Root>/.nbook/agent/jobs.jsonl` 迁移到每个 Job 一个文件：`<Workspace Root>/.nbook/agent/jobs/<jobId>.json`。
- 新 Job 文件保存任务终态、完整结果、kind 详情、Session/usage 摘要和结果回流身份。它属于 Workspace 数据，应随正常备份保留。

## 升级前

1. 停止 NeuroBook 和正在运行的 Source Dev/Product/Portable。
2. 备份完整 State Root，以及每个重要 Project Workspace 的 `.nbook/` 和 `project.yaml`。不要只备份 SQLite；Session、Job、附件和配置也属于恢复所需的数据。
3. Source Dev 使用新的 hoisted linker 重新安装依赖：

   ```bash
   bun install --frozen-lockfile --linker hoisted
   ```

4. 直接运行源码或 Product 时先执行只读检查：

   ```bash
   bun run migrate:application-state -- --plan
   ```

   只有报告确实列出待应用步骤时，才执行 `--apply`。本版本本身没有新增 schema 步骤。

## Job 和 Workflow 行为变化

- 进程重启后，已完成、已失败、已取消的 Job 仍会出现在任务中心，并可读取已保存的完整结果。
- 旧 `jobs.jsonl` 中仍处于 `running` 或 `waiting` 的遗留 Job 会转为 `interrupted`；旧登记表没有完整结果时，不会伪造一个“已完成”结果。
- 旧 `jobs.jsonl` 中的 terminal 行不能恢复为完整 terminal result；原文件保留供人工审计，之后不再追加。
- 重启不会续跑旧 Workflow。Workflow 图、逐步 journal、完整时间线和 pending ask 仍是当前进程内观察数据；运行细节不可用时，界面会保留 Job 的真实终态并提示“运行细节不可用，最终结果已保存”。
- “清除已结束”会删除对应 durable Job 文件；结果仍处于 `pending` 回流的 Job 不允许被清除。系统不设置猜测性的自动 TTL。

## Source Dev 缓存

- 未显式设置 `NEURO_BOOK_CACHE_ROOT` 时，Source Dev 使用 `<checkout>/.agent/cache`。
- 显式设置的 Cache Root 不会被覆盖。Product/Portable 仍使用其自身的 State/Cache Root 合同。
- 旧 checkout 根目录下的 `cache/image-variants/` 不会自动迁移或删除。确认服务已经停止、且没有自定义 `NEURO_BOOK_CACHE_ROOT` 后，可以人工删除这份可重建缓存：

  ```powershell
  Remove-Item -LiteralPath '<checkout>\cache\image-variants' -Recurse -Force
  ```

  只删除明确的 `cache/image-variants` 目录，不要把 `cache`、State Root 或 Project Workspace 当作整体删除目标。

## Profile 模型覆盖

- Profile 的显式模型覆盖仍优先于全局默认模型。
- 如果某个显式覆盖的 Provider 不可用，升级后应恢复该 Profile 的继承设置，或选择确认可用的模型；本版本不提供静默自动换模型。
- retrieval、researcher 的默认模型真实 smoke 已取得，summarizer 只完成有限运行状态复核；这不等于 Composer/Workflow 的完整人工验收。限量 canary 不把未取得的真实证据写成全流程通过。

## 回滚

如果升级后需要回滚，停止服务后恢复升级前完整 State Root 和 Project Workspace 备份，再启动旧 Product。不要手工编辑 migration journal、Session JSONL、Job JSON 或 SQLite sequence。
