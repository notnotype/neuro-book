# 文件资源管理器第二版：快速打开与删除恢复

**状态：draft（2026-09-26）。** 开发者同意以“文件快速打开 + 删除恢复”为第二版核心方向并起草本文；具体行为、恢复保证与交付范围尚未批准。本文不是当前行为规范，也不授权实施、迁移或真实数据验证。首版范围及 F1–F9 以 [workspace.files](../../../../docs/specs/workspace/files.md) 与 [workbench.files-explorer](../../../../docs/specs/workbench/files-explorer.md) 为准；[第一版提案](files-explorer.md)只解释理由，不在这里重订合同。

## 问题

首版解决同一项目内基础浏览、编辑与文件操作，但用户仍需沿树定位文件；删除后也没有可依赖的文件恢复入口。文件定位与误删恢复是两个独立问题：前者需要复用已有工作台输入体验，后者必须由实际持有文件和 Project 的宿主承担，不能靠面板状态或浏览器本地能力假装实现。

## 目标与非目标

- **核心方向（待审行为）**：在当前有效项目内按文件名、相对路径及已取得的内容标题查找并打开真实文件，提供最近文件入口；对受支持的删除提供可核对的回收与恢复，清楚区分永久删除。
- **不变边界**：首版的普通/内容节点双模式、多选和基础文件操作、F1–F9 不因本提案而推迟或重定义。文件打开继续使用文档/编辑器的唯一正文、dirty、条件保存及 Project 代次合同。
- **非目标**：不默认实现全文搜索或全局替换、所有文件操作撤销、编辑器撤销跨文件恢复、Git、跨 Project 搜索/恢复、远程文件系统提供者、领域模板、静默迁移或无条件恢复保证。浏览器系统回收站不是远端 Project 文件的回收站。
- **后续候选（不是第二版承诺）**：全文搜索应另定索引/内容权限与更新语义，不顺带全局替换；内容节点整理应将 frontmatter 标题编辑与路径改名分开，给出引用影响诊断，而非恢复领域模板；导入导出须分别审定浏览器上传/下载和桌面宿主的文件访问、授权及失败恢复。根据首版真实反馈至多优先选一项另行评审，不默认打包。

## 当前行为与证据

- [workbench.quick-open](../../../../docs/specs/workbench/quick-open.md) 已为 `implemented`，当前只有命令模式（`Ctrl/Cmd+Shift+P`）与当前文档行号模式；**文件快速打开和 `Ctrl/Cmd+P` 尚非现有合同**。现有命令 MRU 是宿主实例内的命令 id 排序，不是最近文件记录。第二版宜扩展同一快速输入浮层、焦点交接与命令分发，而非另造平行面板；具体前缀/键位仍待审。
- [workbench.files-explorer](../../../../docs/specs/workbench/files-explorer.md) 与 [workspace.files](../../../../docs/specs/workspace/files.md) 均为 `planned` 的首版合同：前者管呈现和发起，后者管绑定下文件事实与操作；两者明确不承诺回收站或文件操作撤销。既有 History 保留规则不等同删除回收站，也不能证明用户可以恢复任意删除。
- [第一版提案](files-explorer.md) 记录首版取舍及 F1–F9；例如内容模式目录打开真实 `index.md`、F9 对 dirty 删除默认取消、批量结果逐项核对。本提案尚无第二版产品测量或运行验收证据，不把草案写成已实现功能。

## 方案、用户旅程与取舍

### 在同一浮层快速打开文件

建议通过工作台既有 QuickInput/命令体系增加文件入口（`Ctrl/Cmd+P` 仅是**拟议键位**），不改变已有命令和行号入口。有效 Project 的文件列表/树元信息作为候选来源：文件名、相对路径、已取得的内容标题可匹配；**不为查找读取全项目正文**。空查询建议以当前绑定下最近成功打开的文件为先，并提供可浏览候选；具体记录寿命、上限和排序规则待审，不挪用命令 MRU。重名文件展示可辨识的相对路径；内容模式的目录标题与普通模式的 `index.md` 指向同一真实文档时只给一个打开候选，候选身份以真实资源而非标签去重。选中候选后沿现有文档打开链路进入正确编辑组；可从候选或已打开文档 **reveal in tree**，展开真实祖先并定位相应行，在两种模式下映射到合法可见入口；揭示只是定位，不是改写磁盘、切换模式或重新打开正文。

项目未就绪、树读取不完整、候选已删除/改名、访问失效或 Project 换代时，不把旧列表视为当前项目的有效结果；提交前核对绑定和目标，失败给出原因并可在有效绑定下重新查询，不打开旧正文冒充成功。快速连续选择仍遵守后发打开意图，旧异步结果不抢焦点。文件源和正文的成本按首版链路测量；不把全项目预读、全文索引或另一份文档缓存当作快速打开前提。

### 文件所在宿主管理删除恢复

建议 Project/Files 所在宿主在受授权根内承担可恢复删除的文件事实、回收项及恢复操作；浏览器 UI 只发意图和呈现结果，远端项目仍由远端宿主处理。普通删除应明确进入受管理回收路径或返回拒绝/未知，不得因回收不可用静默降级为永久删除。**永久删除是独立动作，需独立且明确的确认**，不得借用普通删除的确认。现有 History 是已有文件历史能力，不能代替回收条目；回收站处理已删除资源，编辑器 Ctrl+Z 只撤销正文编辑，任意复制/移动/重命名/删除的文件操作撤销不在此承诺内。

删除前按首版 dirty/冲突保护结算用户输入；成功后树、打开文档绑定与最近文件入口不能继续把已回收目标当作可写文件。恢复先检查原位置、Project 绑定、权限和冲突：原路径已被占用时不覆盖，向用户提供不覆盖的可审选择（例如保留回收项并取消，或明确选择另一合法位置；后者是否开放待审）。批量删除/恢复、目录含子项、磁盘满、权限失败、进程崩溃或网络断开可能导致部分完成或结果未知；必须能按真实源、回收项和目标核对已完成/残留/未执行，重新读取事实后才允许针对明确失败项操作，不用旧树快照冒充回滚，也不盲目重复有副作用的请求。回收服务在接纳前不可用则拒绝操作并保留源；操作已开始后发生故障，按实际结果核对，不假报源完整保留，更不转为永久删除。恢复后的正文打开与引用诊断遵守既有文档及文件保护；不声称外部 Markdown 引用会自动修复。

### 未采用项

- **第二套搜索面板或仅树名称筛选**：前者复制浮层与键位，后者不能从任意工作区焦点直达文件；同一 QuickInput 扩展文件来源更合适，但不得破坏已实现命令/行号语义。
- **浏览器/操作系统本机回收站**：浏览器不拥有远端服务器的原始文件或项目授权，桌面与浏览器行为会失真。
- **以 History 或 Ctrl+Z 冒充删除恢复 / 自动回滚整个批次**：历史基线、正文输入与文件资源的语义和故障边界不同；失败后覆盖其它窗口的新文件风险更高。
- **恢复时自动覆盖、删除失败自动永久删除**：均可能将可恢复误操作升级为不可逆数据损失。

## 数据、接口、安全、迁移、发布与回滚影响

| 边界 | 第二版待审影响 |
|---|---|
| 数据与归属 | 查询只消费有效 Project 的文件元信息与允许显示的标题；最近文件只记真实资源定位，不复制正文。回收项与原路径、操作结果由文件所在宿主/Project owner 管理；存储布局、保留时长、容量/清理策略、空间不足政策和跨版本兼容尚待决定，不在此预设预算或迁移方法。 |
| 接口 | 工作台快速输入需文件候选和打开/定位接缝；Files/宿主 API 需可恢复删除、列出/核对、恢复及独立永久删除的受控行为和逐项结果。具体端点、DTO、事务/状态机与事件协议在行为批准后设计；不以服务注册自动暴露网络接口。 |
| 权限与保护 | 查询、删除、回收列表、恢复及永久删除在宿主逐次验证有效 Project 绑定、根内范围、授权与链接/控制文件保护；UI 隐藏或确认不代替服务端校验，结果不泄漏根外路径或无权披露内容。不同窗口与外部修改的冲突不能由当前窗口代签放弃。 |
| 迁移、发布与回滚 | 首版尚为 `planned`，第二版不修改首版数据格式或既有 History，不能假定旧删除可追溯。发布前审定旧/新版本对回收项的可见性与恢复兼容、功能不可用时的拒绝行为及回滚后的数据保全；无法安全读取回收项时须阻止不可逆清理，不以“关闭 UI”充当数据回滚方案。 |

## 对 Spec 的预期改动与草案验收例

**仅在具体行为被批准后**，将文件候选、入口/键位、最近文件、去重、失效和 reveal-in-tree 的输入/输出/状态/失败补入现有 [`workbench.quick-open`](../../../../docs/specs/workbench/quick-open.md)（同一 capability 当前正文）；[`workbench.files-explorer`](../../../../docs/specs/workbench/files-explorer.md) 补树定位和删除/恢复入口与反馈，[`workspace.files`](../../../../docs/specs/workspace/files.md) 补授权文件操作和结果边界。若审定的删除恢复可以独立验收且有独立数据 owner，届时决定是否单列恢复 capability；**本轮不新建第二版 Spec 或 Task**，也不改写 quick-open 的 `implemented` 现状。

以下均是未来隔离项目的**草案验收例，未运行**：

1. 两个目录各有同名文件，内容模式目录 `index.md` 又由普通模式可见：查文件名/路径/已取得标题，两个同名项可辨，`index.md` 的两个入口只打开同一文档；最近文件可再次打开，揭示定位到当前模式的真实可见行。不扫描全项目正文；命令与 `:行号` 继续工作。
2. 快速打开浮层打开后删除目标或切换 Project，旧候选不可提交到新绑定；旧异步读取不改变新的编辑器正文或焦点。未开项目与读取故障分别说明，而非显示假空目录。
3. 在隔离项目删除干净文件后从受管回收项恢复，核对原路径与字节；已有同名新文件时恢复拒绝覆盖并保留回收项。目录、多选的部分失败能逐项核对，磁盘满、断线或崩溃后的未知结果不自动永久删除或盲目重试。
4. dirty 文件删除默认不执行；确认的永久删除使用独立动作和明确确认；浏览器连接远端宿主时不展示“已进本机回收站”之类虚假保证。恢复项经过旧版本/回滚后的可读性门禁在发布策略获批后单独验证。

## 需要首版反馈的假设与待审点

- 首版真实树规模、路径/标题歧义、打开耗时和用户在两种模式下的定位习惯是否支持现有元信息查询？缺失标题时如何降级；文件入口的查询前缀、默认键位、最近文件的保留范围/时长和同分排序是否合意？
- 首版批量删除、dirty、同名目标和外部改动的真实错误分布是什么？回收内容保存多久、谁可清理、容量耗尽如何拒绝、目录与部分结果如何核对、跨版本/回滚怎样确保不丢回收项？是否应开放另选位置恢复？
- 浏览器远端与桌面宿主是否都能提供等价受管恢复，何时必须明确标记能力不可用？恢复是否需要单独的能力与验收 owner？
- 首版反馈是否值得从全文搜索、内容节点整理、导入导出中**至多选一项**进一步起草；没有证据时不因本文标题把候选并入第二版。
