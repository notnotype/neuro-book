Profile 系统架构

一个 Profile 怎样从一段 TSX 变成模型收到的请求：谁注册、谁取数、谁渲染、哪些消息写进会话日志。行为合同以 harness.profile 与 harness.runtime 为准，本页只做讲解。

一张图：从 TSX 到模型请求

设计原理

  1. Profile 是数据，不是程序。<Prompt> 返回普通的对象树 {type, props, children}，TSX 只是写法。所以它能校验（props schema、父子规则）、能预览，诊断能带路径（例如 Prompt>Appending>Reminder[0]）。提示词函数是纯函数：只读 ctx，不做 I/O。
  2. 外部数据走“数据源 + 节点”，不在提示词函数里 await。节点只声明“我要某个数据源”，取数由准备阶段统一做：并发、按 schema 校验、失败变成诊断、能取消。时机分两种：invocation 一次调用取一次；model-call 每次请求模型前刷新。系统提示词因此能随时更新，而已写进日志的种子不会被刷新改写。
  3. 准备与渲染两段式。准备产出冻结的结果，四个渲染函数都是纯函数。运行时可以在不同时刻、以不同输入渲染同一份准备结果：调用开始时渲染种子与追加消息并写日志，每次请求前渲染系统提示词与请求消息。预览用的是同一套函数，所以与真跑同形。
  4. 三类消息按“写不写进日志”分区。<History> 的子节点是种子；<Appending> 的内容每次调用开始写入；直接放在 <Prompt> 下的消息只进本次请求。历史本身不由 Profile 产生，是运行时从日志回放的；<History last={2}> 只是在请求里裁剪它。种子、提醒、摘要回放后都带 attribution: "agent"，“轮”只按用户真正发出的消息数。
  5. 主机是注册表，没有全局状态。节点类型、数据源、字段都注册到某个主机；运行时创建时登记自己的四个字段，插件注册自己的节点与数据源。harness/ 命名空间下拼错的字段是错误，别的命名空间未知字段只警告。
  6. 工具只以名字出现在 Profile 里。tools: ["read", "edit"] 是请求；工具实体在运行时的工具来源里。每次受理时取两者的交集作为可见工具，请求了没装的给 unknown-tool 警告。同一个 Profile 装到不同宿主，可见工具可以不同。
  7. 失败是诊断，不是异常。校验不在第一条错误停下，全部收集。准备或刷新失败时诊断随结果返回，运行时把它们放进 invalid-profile 的说明与预览的 diagnostics，界面能一次列全。

ctx 里有什么

type PromptContext = {
    session: {id: string; title?: string; createdAt: string};   // 来自会话日志
    turn: number;                                                // 本次是第几轮用户发言，从 1 起
    now: Date;                                                   // 运行时的时钟
    fields: Readonly<Record<string, JsonValue>>;                 // 校验过的字段值（含 tools、model 等一等属性）
};

title 是可选的：创建会话时没给就没有，Profile 里写 {ctx.session.title ?? "未命名"}。需要更多外部数据时不要往 ctx 里加，注册一个数据源。
