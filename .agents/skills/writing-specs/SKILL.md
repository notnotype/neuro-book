# 写 Spec

Spec 是现在（`implemented`）或下一次实现（`planned`）必须成立的行为，是唯一的当前合同。规则以 [`docs/specs/README.md`](../../../docs/specs/README.md) 为准：成熟度与待晋升、[写什么、不写什么与两条判据](../../../docs/specs/README.md#spec-写什么不写什么)、[编号](../../../docs/specs/README.md#编号)、[实现合同与证据](../../../docs/specs/README.md#实现合同与证据)、frontmatter、注册表与完成条件。本 skill 讲怎么写。

## 流程

1. **定位能力**：查注册表与相邻 Spec，找到就原地改。一个可独立验收的能力一份 Spec；在已实现的能力上加几条行为时，按 README 用条目级“（planned）”。一次需求包含几个能各自交付、各自验收的能力时，先列能力地图交开发者确认，再逐个写：

   | 能力 | 职责 | 依赖 |
   |---|---|---|
   | `storage.persistence` | 插件记录的读写与订阅 | `runtime.services`、`runtime.projects` |

   依赖只能单向；两个能力互相需要，说明它们是一个能力。
2. **核实依据**：`planned` 要有 `accepted` 的提案或开发者明确批准；`implemented` 要读实现、调用方与测试。
3. **先列假设**：动笔前把会改变行为的假设列给开发者确认，不默默替开发者选。模糊的要求先改写成可判定的判据再问（“打开要快”改写成“冷启动打开项目在 2 秒内可编辑”）。
4. **写合同**：按下文模板。条目、失败码与场景编号，只在末尾追加。修订已有合同的记法或语义时，在 `docs/` 中搜索旧写法的全部出现（示例、其它 Spec 的引用）一并修改，否则同一概念在不同 Spec 里出现两种合同。
5. **自查**：逐句过 README 的两条判据；用到的共用词与[运行时术语表](../../../docs/specs/runtime/glossary.md)一致，术语与失败码不与相邻 Spec 冲突；运行 `bun run docs:check`。
6. **实现之后**：补实现合同与证据；晋升 `implemented` 由开发者批准。

## 写交互合同

交互合同最常漏：它不在任何一个函数里，只有调用方撞上才知道。写“状态与转换”时逐项问：

- 调用方拿到的东西从什么时候起可用、到什么时候作废，作废后访问会怎样；
- 哪件事要等另一件事先发生（例如“工厂返回之后才签发”“同步段里就开始”），在此之前调用会怎样；
- 断线、重连、重启、换代之后，已有的句柄、订阅与在途请求各怎样结束或重建；
- 并发的两次操作谁赢，另一次得到什么。

把答案列成“时序与寿命”清单，每条写成调用方可以依赖、测试可以判定的一句话。跨两个能力的交互写在提供方的 Spec，使用方链接过去。

## 模板

```markdown
---
schema: nbook.spec/v1
kind: behavior
status: planned
capability: <稳定的点分标识>
owners:
  - <负责行为与数据边界的模块或插件>
---

# <能力名称>

## 目标与非目标
<一段话说清给谁什么能力>；“不承诺”逐条列出，已知限制也写在这里。

## 术语与参与者
只定义本 Spec 新引入或含义不同的词；通用的词链接术语表或定义它的 Spec。

## 输入与前置条件
触发方式、数据形状、规则（表格）、公开接口的类型签名、在哪些位置可用。

## 输出与可观察行为
编号条目，每条一个可判定的行为。

## 状态与转换
状态表；并发语义；“时序与寿命”列出交互合同。

## 副作用与数据
落点、格式版本与兼容、寿命与清理。

## 失败与恢复
失败码表：码、含义、调用方怎么办。

## 边界与兼容
公开接口是哪些、版本怎样变、信任边界。

## 验收与 Smoke
只写跨多条规则的组合场景与特殊环境（多进程、多窗口、重启、真实浏览器）；单条规则由“输出”条目本身验收。最后一行写 Smoke 入口。

## 证据
- 批准依据：<提案、ADR 或开发者决定的链接>
```

- 九个二级标题固定，不适用的写一行“无”。
- `implemented` 在“验收与 Smoke”与“证据”之间加“实现合同”，证据另加三行固定标签，写法见 README 的“实现合同与证据”。从实现合同里删下来、维护者仍需要的内部细节，写进对应源码的模块头注释。
