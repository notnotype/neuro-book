# 写 Spec

Spec 是现在（`implemented`）或下一次实现（`planned`）必须成立的行为，是唯一的当前合同。frontmatter、成熟度、注册表与 `docs:check` 机检的规则以 [`docs/specs/README.md`](../../../docs/specs/README.md) 为准；本 skill 讲怎么写。

## 流程

1. **定位能力**：查注册表与相邻 Spec，找到就原地改。一个可独立验收的能力一份 Spec。一次需求包含几个能各自交付、各自验收的能力时，先列能力地图交开发者确认，再逐个写：

   | 能力 | 职责 | 依赖 |
   |---|---|---|
   | `storage.persistence` | 插件记录的读写与订阅 | `runtime.services`、`runtime.projects` |

   依赖只能单向；两个能力互相需要，说明它们是一个能力。
2. **核实依据**：`planned` 要有 `accepted` 的提案或开发者明确批准；`implemented` 要读实现、调用方与测试。
3. **先列假设**：动笔前把会改变行为的假设列给开发者确认，不默默替开发者选。模糊的要求先改写成可判定的判据再问（“打开要快”改写成“冷启动打开项目在 2 秒内可编辑”）。
4. **写合同**：按下文“模板”与“写什么、不写什么”。
5. **自查**：逐句过两条判据；与相邻 Spec 的术语、失败码不冲突；`bun run docs:check`。
6. **实现之后**：补实现合同与证据；晋升 `implemented` 由开发者批准。

## 写什么、不写什么

**必须写：**

- 对外可观察的行为：输入、输出、状态与转换、失败码与恢复。
- **交互合同**：调用方能依赖的先后与寿命——什么时候可用、什么时候作废、谁先谁后、断线或重启后会怎样、哪些事要等对方先发生。写在“状态与转换”。跨两个能力的交互写在**提供方**的 Spec，使用方链接过去。
- 对外的格式与兼容：别的进程、版本或用户会读写的东西（线上协议、持久化文件的位置与格式版本、目录布局），只写兼容所需的部分。
- 编号的条目与验收场景。

**不写：**

- 实现做法（数据结构、算法、事务写法、内部缓存键、内部诊断原因名、文件布局）：写进代码与注释。
- 取舍理由与备选：写进提案或 ADR，需要时链接。
- 历程（“随 tNN 实现”、某日改写、审查结论）：留在 Task 与 git。
- 证据叙述：证据只留下文的固定几行。

**两条判据**（逐句检查）：

1. 换一种实现、行为不变，这句话要不要改？要改，它就不属于 Spec。
2. 这句话能写成测试或审查判据吗？不能，就删掉或改写到能。

## 编号

“输出与可观察行为”的条目、失败码表与验收场景都编号，编号稳定：只在末尾追加，删除时保留空号并写“（已删除）”。测试名引用编号（`Spec storage.persistence 输出 4`、`场景 7`），所以插入中间会让测试名失效。

## 模板

```markdown
---
schema: nbook.spec/v1
kind: behavior
status: planned
capability: <稳定的点分标识>
owners:
  - <负责行为与数据边界的模块或插件>
---

# <能力名称>

## 目标与非目标
<一段话说清给谁什么能力>；“不承诺”逐条列出，已知限制也写在这里。

## 术语与参与者
只定义本 Spec 新引入或含义不同的词；通用的词链接术语表或定义它的 Spec。

## 输入与前置条件
触发方式、数据形状、规则（表格）、公开接口的类型签名、在哪些位置可用。

## 输出与可观察行为
编号条目，每条一个可判定的行为。

## 状态与转换
状态表；并发语义；“时序与寿命”列出交互合同。

## 副作用与数据
落点、格式版本与兼容、寿命与清理。

## 失败与恢复
失败码表：码、含义、调用方怎么办。

## 边界与兼容
公开接口是哪些、版本怎样变、信任边界。

## 验收与 Smoke
只写跨多条规则的组合场景与特殊环境（多进程、多窗口、重启、真实浏览器）；单条规则由“输出”条目本身验收。最后一行写 Smoke 入口。

## 证据
- 批准依据：<提案、ADR 或开发者决定的链接>
```

- 九个二级标题固定（`docs:check` 按它们提取）；不适用的写一行“无”。
- `implemented` 的 Spec 在“验收与 Smoke”与“证据”之间加“实现合同”：公开入口（包入口与公开符号，不列内部文件）、owner 与依赖方向、不超过五条维护者必须知道且有测试锁定的内部不变量。
- `implemented` 的证据另有三行固定标签，各链接仓库里存在的文件：`实现入口：`（源码）、`合同测试：`（测试文件）、`Smoke：`（可执行脚本或测试；确实没有时写“不适用——<理由>”）。

## 给已实现的 Spec 加新行为

整块新能力另起一份 Spec。在已有能力上加几条行为时，新条目末尾标“（planned）”，实现并验证后去掉标记；不在条目里写 Task 编号。
