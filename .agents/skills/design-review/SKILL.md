# 界面设计评审

界面的版式、入口、信息层级这类要开发者拍板的事，先出静态稿、逐轮评审，定了再写 Spec 与计划。编码规范、组件复用与 UI 检查见 [ui-development](../ui-development/SKILL.md)，本技能只管从“要设计”到“设计定了”这一段。

## 流程

1. **现状与参照**：先用 `nbdev find <词>` 查已有产物（含其它 Work 的评审板），再用 `nbdev shot` 截现状；有旧应用或旧稿时先调研。现状截图与参照清单写进本 Task 评审板的“现状与参照”一节，用 nbdev 发布。沿用旧设计的机制时说明它防什么、现在还要不要，交开发者决定。
2. **注意力排序**：先和开发者确认首先看什么、默认收起什么、什么时候整块收起，再出视觉候选；版式未定时的视觉迭代会被反复推翻。
3. **静态稿**：搭稿前先加载用户级 Skill `frontend-design` 与本仓库的 [ui-development](../ui-development/SKILL.md)，按前者先定这一页的视觉方向（只在一处用力，其余照器械写法保持安静）再动手（w00050 t08 第 1 轮只读了设计语言、没加载它们，开发者答“样式有点丑”，整轮重做）；再读 nb-ui 的 [`design-language.md`](../../../packages/nb-ui/docs/design-language.md)（至少“四、排版”与“五、颜色角色”两节）：静态稿定下的版式、密度与用词会被照着实施，不合设计语言的画法（例如每屏一句灰色说明、一种颜色表示几种意思）要在出稿前改掉，不留给审查。同时读 [`ui-development-spec.md`](../../../packages/nb-ui/docs/ui-development-spec.md) 第 3 节第 4 到 6 条（状态变化不推动周围内容、同一列表的行等高、同种零件同列）：只在某个状态才出现的东西（待办提示、错误、空态、加载、最后一页不满的列表），逐个问一句“它不出现时，这块位置是什么”，答案是“后面的内容整体上移”就改画法（放进原来就留着的格子，或换成单独的一步）；这样的状态在评审板上把两种并排给出，只画一种状态时位移看不出来（w00037 t09 第 2 轮在账号页顶上加了一条“还没有邮箱”的横幅，只画了没有邮箱的那一种，开发者指出它让表单整体下移）。搭稿的同时请 omp 的 `@designer`（Gemini）当方案、文案与交互顾问看现状截图（见 [ui-development](../ui-development/SKILL.md) 的第 8 条），它的意见由主会话取舍、写进评审板的推荐。然后在 Lab 里用真实 nb-ui 组件与主题 token 搭草稿场景（放在 Lab 的草稿区，见下文），不改产品源码。背景可以用真实页面的截图。一轮只问一两个问题，同一个问题的候选并排。界面背后是一套新的数据模型时，静态稿之后可以再做一轮数据驱动的原型（见下文“数据驱动的原型”）。
4. **评审板**：每轮的图与说明放进评审板（见下文），待定的问题写成提问，主 Agent 逐张看过、写好推荐，用 `nbdev artifact publish` 发布，再请开发者看。
5. **记录决定**：用 `nbdev answers` 读开发者的答复，把决定按编号写进 Task README（文字），再用 `nbdev answers ack … --through <cursor> --include <Task README>` 与 README 一起提交；计划写进 `plan.md`。评审板只是讨论材料。
6. **定稿之后**：把行为写进 Spec，再按计划实施。

## 草稿放在哪里

- **草稿目录**：Lab 的草稿区 `packages/neuro-book/src/plugins/lab/web/drafts/<workId 短号>-<taskId 短号>/`（例如 `w00039-t42/`），一个 Task 一个目录：草稿组件与同名 `.md`、样本数据、场景的包装组件，以及导出这个目录场景登记的 `fixtures.ts`（用 `../../fixtures/define` 的 `defineLabFixture`）。放进来就出现在 Lab 组件树的 `drafts` 一组里，不改总登记表；草稿可以引别的插件的 `web/` 与 `shared/`，不引别的插件的素材（图片用 Lab 的样本图）。规则见 [`ui/component-lab`](../../../docs/specs/ui/component-lab.md) 的“草稿区”（开发者 2026-11-25 定，w00022 t24）。
- **草稿入库**：每轮在草稿 worktree（例如 `.worktree/<Work 短名>-<Task>-drafts`，分支 `<Task>/drafts`）里搭；跑过 `bun run typecheck`、`fixtures/index.dom.test.ts` 与 `src/architecture.test.ts` 后合进 master，再发评审板（草稿引了别的插件的素材，只有后者报：w00056 t06 第 5 轮引了星璃的头像与贴纸，前两项都过了，合进 master 以后包内依赖方向一直是红的，到第 6 轮才发现；开发者许可用产品里的图时，复制一份放进草稿目录），所以任何开着的开发服务都能打开评审板里的 Lab 链接。草稿和编码不在同一个 worktree：开发服务热重载会把编码中途的错误带进草稿截图。上一轮的场景留着，新一轮的场景 id 加轮次前缀（`r2-…`）或另起组件，评审板的旧链接不失效。
- **草稿的寿命**：草稿照样参加类型检查与 Lab 场景的挂载检查（版面检查不量它们）。产品组件改了让旧草稿编不过或挂不上时，在同一个提交里修好或删掉它（评审板上的截图还在）。
- **评审板**：Task 的产物，放主工作区的 `.agents/works/<workId>/tasks/<taskId>/artifacts/review/`，入库，任何会话都能读到。`index.html` 是唯一入口，每轮的图放 `r1/`、`r2/`…；`versions/`（发布记录）与 `answers/`（开发者的答复与确认）只由 nbdev 写。图片按 [本地与入库](../../works/README.md#本地与入库) 的体积上限转成 WebP，原图与完整截图集留在本地 `.local/agent/works/<workId>/tasks/<taskId>/shots/`。
- **不入库**：完整截图集。

## 评审板怎么写

照模板 [`review-board.html`](../../../packages/dev-panel/docs/examples/review-board.html) 写（t23，规则来自开发者的 visualize 经验）：

- **一节一问**：节标题就是要问的事，写成问句；标题下第一行加粗写推荐与一句理由；候选并排、等宽、用同一个例子画；这道题的材料都放在这一节里。在面板里打开时，nbdev 在每道题的元素末尾放答题控件，开发者看完材料就地作答；不要自己写答题控件。
- **一轮只问要定的事**：“直接修、不用答”的列成一张表，不提问；已定的收到页面最后。题多时拆成几轮（t22 第 1 轮 13 题，开发者说找不到题对应的材料）。
- **不写补丁文字**：引导句、图注、复述标题的说明行、页头小字都不要；想补一句解释，说明图没讲清，回去改图。
- 每节写：要开发者定什么、各候选（图或 HTML）、主 Agent 的推荐与理由；开发者的决定写进 Task README，页面上已定的只留一行结论。
- 结构、贡献关系、对照表、流程这类能用 HTML 直接表达的，写成 HTML，不截图；“长什么样”用真实组件的截图。
- 每个候选与“直接修”的图旁附 Lab 链接（`<开发服务地址>/lab?c=<组件>&s=<场景>`，链接所在的元素加 `data-nbdev-skip`），交评审板时回复里也给一条：开发者要在 Lab 里自己点状态、换宽度（2026-11-25）。地址写当时开着的开发服务；草稿已在 master 上，那个服务停了，换任何一个开着的开发服务的地址也能打开。
- 标注稿（例如“哪里能贡献”）用界面里不会出现的固定标注色画虚线框加编号，旁边一栏逐条解释；能贡献与不能贡献用两种颜色区分。

## 提问、发布与答复

- **先分清问在哪里**：要看图、要把几个候选并排比较的问题，写进评审板；几乎是纯文字、几句话就讲得清的问题（例如确认提纲、确认写正文时自定的几条、二选一的范围），直接在会话里问，不发评审板。会话里得到的决定照样按编号写进 Task README（开发者 2026-10-15 定）。

- **待定的问题写成提问**：在包住这一节的元素上加 `data-nbdev-question="<题号>"` 与 `data-nbdev-type`，候选上加 `data-nbdev-option="<值>"`，推荐写 `data-nbdev-recommend`；写法见 [提问标记](../../../packages/dev-panel/docs/file-formats.md#提问标记)、[例子页](../../../packages/dev-panel/docs/examples/questions.html) 与上面的模板。标题里的“待定”“已定”徽标、候选里的“打开”按钮加 `data-nbdev-skip`，不进题目与选项名。标题后直接跟兄弟元素的扁平板，先给每道题包一层 `section`。题目缺省是选答（开发者 2026-11-05）：开发者可以只答一部分，也可以自己关掉评审；只有不定就做不下去的才加 `data-nbdev-required` 标成必答。
- **发布**：每轮写好后运行 `nbdev artifact publish <workId> <taskId> review --kind design`（第一次要 `--kind`），它解析提问、检查图片体积、写发布记录并与页面文件一起提交。输出逐题列出解析到的题，核对一遍。题意变了就换题号；被后一轮取代的问题换题号或从页面删掉，输出会列出被取代的题（已答的题删掉不算取代）。
- **读答复**：`nbdev answers <workId> <taskId> review --json`，记下输出里的 `cursor`；要挂着等，加 `--wait`，用会话自己的后台机制运行（Claude Code 用 Bash 的 `run_in_background`，不用 Monitor：Monitor 最长 30 分钟就结束它挂的命令；`--wait` 缺省等 6 小时）；`artifact publish` 与 `ask` 的输出末尾就给出这条命令（`--json` 时在 `data.waitCommand`），发完就挂上。退出码 4（超时、被打断，或被宿主结束）时按原参数重挂；退出码 0 是有了答复，先处理答复并 `answers ack --through <cursor>`，或带 `--since <cursor>` 重挂，否则按原参数重挂会立刻返回。开发者在会话里口头定的，用 `nbdev answers record … --set <题号>=<值>` 代录。
- **确认**：决定写进 Task README 之后运行 `nbdev answers ack <workId> <taskId> review --through <cursor> --include <Task README 的路径>`，确认与 README 同一个提交。`cursor` 取读答复时输出里的那个：只确认读过的答复；读完之后开发者又交的会给 `newer_answers_unacked`，读了它们再确认一次。
- 页面上的“待定”“已定”徽标只给人看，哪道题待答、已答、被取代以发布记录与答复为准。
- **过渡条款**：nbdev 不可用、或还没获授权在真实仓库使用时，按旧做法：直接写产物目录，路径限定提交（`git commit -- <路径>`），答复与决定照旧写进 Task README。

## 谁来搭草稿

- 草稿由主会话自己写：搭稿要用到对问题、已定决定和评审板的了解，交给空白上下文的子代理要整段重讲，还要等它重读代码。
- 开发者要求派子代理时才派。每轮派一个新的，说明里给上一轮的草稿文件路径、评审板与已定的决定，不续用已交回的子代理。
- 任务说明写明：worktree 与输出目录、已定与待定的事、每个场景的内容与取值、文件名、不提交（主会话核过以后合入）、开发服务记 PID 并在结束时停掉。
- 要它报告：每张图的路径、Lab 地址与场景 id、和要求不一致的地方、搭稿时发现的会影响真实实现的问题（缺字段、组件做不到、合同说不通）。这些问题由主 Agent 核实后进计划或另建 Task。

## 数据驱动的原型

界面背后是一套还没实现的数据模型（新的领域对象、计算规则）时，静态稿只能让开发者看到界面，看不到数据长什么样。可以把草稿改成由数据驱动的原型，同样放在草稿区：

- **类型与引擎**：草稿目录里放一份类型（要存的对象）和一组纯函数（写入、计算、校验），不碰界面，界面只是它的视图。
- **样本按真实的写入搭**：样本数据不写死，由一串真实会发生的写入一步步搭出来；界面顶上放一条步骤条，点哪一步就退回到哪一步。
- **看得到原始数据**：留一栏“数据”，选中什么就显示它存下来的原样与算出来的值（来历、改前改后）。
- **能操作的只做主路径**：几个关键动作真的产生写入，其余按钮可以是摆设。

依据：w00039 t16 第 2、3 轮把已接受提案的内核做成这样的原型，搭的过程中找出十来处提案没写到或照字面画出来别扭的地方（初值与“第 1 章开头”混用、修订存整份对象太占地方、冲突不必另设对象等），开发者看着原始数据又提出“精确与语义两档”。

交给开发者试玩之前，先把主要点击路径跑一遍：给要点的按钮加 `data-*` 属性，用 `nbdev shot -- -c <组件> -s <场景> --click <选择器> …` 依次点击，看报告里有没有 `pageerror` 与 Vue 警告；各块界面包一层出错兜底，一块出错不让外壳的更新跟着坏掉。依据：t16 有两个报错是开发者试玩时才发现的（退回早一步后，标签页还去读已经不存在的修订；一类改动被回执当成另一类）。
