# 实施计划

计划回答“为什么做、具体改哪里、按什么顺序、怎么证明做对了”。它让开发者在动代码前确认方向，也让实施者不用再发明设计。

## 何时写

- 写：新功能；改变已有行为或结构；跨两三个以上文件；存在多个可行做法；需求要先读代码才清楚。
- 不写：单点修复、措辞修改，或开发者已给出具体改法的小改动。

## 流程

1. **理解**：读请求与相关代码。主动找可复用的现有函数、工具与模式，不另写已有的实现。只把会改变结果、范围或不可逆后果的问题交给开发者。范围不明或涉及多个区域时，宿主支持的话可派只读探索子代理，给每个子代理一个明确的搜索范围。要重做旧应用或应用里已有的交互时，逐项列出参照的可观察行为（例如拖动的起拖门槛、拖影、落点、取消），计划里每一项写明做还是不做。重做参照软件已有的能力时，除了读实现，也通读它的设置项，逐项判断要不要、缺不缺。在依赖库之上加重试、超时或缓存这类机制前，先用本机假端点实测它内层已经做了什么、能不能关，并按接口分别测，不只看类型说明。
2. **设计**：先做技术选型：方案里的通用问题（命令行解析、交互提示、校验、日期时间、文件监听等）先查仓库已有的依赖和该领域稳定成熟的第三方库，能用库就用；手写只在库确实不合适时，并写明理由。再形成推荐方案。定共用代码放在哪个包时，候选里加上“只放共用部分的新小包”，并给出每个候选的数字：新公开的导出与包、使用者多装的包、要不要另写已知缺陷的说明。含技术选型或架构取舍时，按 [reviewing](../reviewing/SKILL.md#审查方式) 的“独立设计”请一个只拿到目标的子代理另出一版，对照后取舍。
3. **复核**：回读计划依赖的关键文件，核对方案与开发者原意一致；方案依赖现有机制的顺序、时序或寿命保证时，读该机制的 Spec 或实现确认它确实提供，不按名字推断；方案依赖外部服务的限制（网关上限、配额、限流）时，动手前用与真实请求同形状的请求复测几次；只凭一两次探测得出的结论，不作为计划的依据；方案让同一种格式暂时由两套解析器或两份实现各读各的（先接上一边、另一边以后再换）时，先拿两边的真实实现跑一张差异表：哪些输入一边收一边拒，哪些两边都收却读成不同的东西；据此估代价、再向开发者推荐先后，不按“只是边角”估（w00039 t39：推荐“先接富文本编辑器、内核后换”时只凭印象说两边差在少数写法，设计审查用真实内核跑出 `1<2`、`<br>`、正文里的花括号被拒收，四个空格开头的段落两边读成不同的块，要补的东西是原计划的两到三倍，开发者改选了源文字编辑）；多进程按版本发布数据（“只创建一次”的版本文件）时，版本号不能随回收马上空出来，否则读到旧版本的写入者晚到会重用它、覆盖别人的写入，计划里要有用真实子进程并发写的测试；要把草稿或原型代码（例如草稿 worktree 里的界面）搬进正式代码时，先核对它依赖什么（原型自己的引擎、注入的状态、同步调用），依赖要换掉的按重写估工作量，并按正式代码的规范（组件契约、Lab 场景、测试）计入；计划里有两条交互会落在同一个按键或同一个时刻时（例如“打 `---` 新建后把焦点给新属性名”与“紧接着按退格还原”），写明每条交互做完后焦点在哪、接着的按键归谁，e2e 按这条先后走一遍：焦点换了，第二条交互的前提就变了，到写 e2e 时才发现要改 Spec（w00025 t10）；把启动或装配代码搬进一个带收口的共用函数时，逐步写明每一步落在收口的 `try` 之内还是之外、在开始受理请求之前还是之后：`try` 外的失败不经收口（端口与认领留着），受理之后的失败已经被外部看到（w00043 t02 实现审查的两条重要发现都出在这里）；新加的读取会被频繁调用、每次的输入都不同时（预览、联想这类），沿它的调用路径查一遍按输入留结果的缓存与读取层的保留策略，以及结果比输入大多少：这些缓存是给稳定的输入设计的，换成一串只用一次的输入会被撑满（w00039 t40：预览差点把内核的解析缓存与窗口的读取层填成上万份整篇；渲染结果是源文字的十几到四十倍，按源文字长度定的上限形同虚设）；剩余问题在定稿前问清。
4. **写计划**：按下面的结构写 `plan.md`。
5. **交开发者确认**：回复中给出要点与需要确认的项。确认前不改产品代码、不提交实现。

## plan.md 的结构

1. **Context**：为什么做——要解决的问题、由什么引起（开发者要求、审查结论、上一个 Task 的结果）、期望结果；依据的 Spec、Proposal、ADR 链接；开发者已确认的决定；工作方式与约束。
2. **技术选型**：每个通用问题一行：选用什么（仓库已有的依赖优先）、为什么、否决了什么（各一句）。用库替换已有实现时（例如手写的解析器换成库），把旧实现接受的写法与对应行为逐条列出，第一个切片先写成对照测试再换，换完逐条核对；对不上的要么改回旧行为，要么写进 Spec 并告诉开发者。没有通用问题时写“无”。
3. **关键设计**：按模块或目录分节，节标题写路径。每节写：要改或新增的文件；新增接口的签名或形状；要复用的现有函数与工具（带路径）；要守住的不变量与理由。
4. **Spec 与文档改动**：文件 → 改什么。
5. **切片**：顺序、每片对应哪几节关键设计、提交边界、自跑验证命令。
6. **验收映射**：Spec 编号（输出条目、失败码、验收场景，例如 `storage.persistence 输出 4`）→ 由哪个测试、smoke 或 e2e 覆盖。只写编号，不复述 Spec 内容；计划要求的行为 Spec 里还没有时，先写进 Spec 再映射。
7. **验证**：端到端怎么验证（运行哪些命令，真实浏览器或真实进程怎样观察），以及明确留下的未验证边界。e2e 分两段写：合入前跑一次的清单（超过 8 个文件要写明要消除什么不确定性），与实施中改动后只重跑什么。清单不是每轮都跑的，规则见[验证门禁](../../../docs/testing/README.md#验证门禁)。
8. **测试分工**（大型任务把 e2e 交子代理写时）：谁写什么、分几段派、各段对应哪几片；e2e 要用的 `data-*` 属性与可观察状态逐条列出，主会话照它实现、子代理照它写用例。
9. **不做与风险**。把风险交给某条测试兜底时，写明它要用的真实对象（例如调用真实的内置工具，不是测试自造的替身），实施时核对这条测试确实覆盖到。

## 写法

- 只写推荐方案，不罗列备选（技术选型里对否决的库各写一句除外）；被否决但有长期价值的备选写进 Proposal。
- 短到能快速扫完，细到能直接照着实施。
- 同一模式在多个文件重复时，只描述一次并列出几个代表路径，不逐个枚举文件或行号。
- 表格单元格只放短语与引用；设计写在“关键设计”的正文里。
- 不写时间估计。
- 有性能预算的热路径，后续切片或审查修正改到它时（序列化、冻结、哈希、遍历），当片重跑它的测量脚本，不只在初测那片跑一次。测量脚本造的数据要走到方案涉及的路径：先核对它有没有这些形状（例如计划、多条子线、靠后的切口），否则量出来的“不变差”没有证明力。
- 方案要靠人列举“某个计算读了什么”时（依赖摘要、缓存失效），先看能不能减少它读的东西，再决定怎么列。审查连续在同一处找到漏项时停止打补丁，追那个读取本身（w00039 t34：依赖摘要在按计划模式的值上连漏三轮，改成不读它，比前面的补丁加起来消掉的都多）。
- 有性能预算的写入路径，在第一个能端到端发布的切片就量完整路径（校验、算出的派生结果、落盘、重新打开），不只量计算核心：只量核心时，按数据量平方增长的部分要到接进应用才被发现。
- 给已有接口加上限、校验或改缺省值时，先搜仓库里的调用方，改掉按旧行为传值的地方。
- “验证”里列的每个 e2e 文件（含只在某一片才跑的，例如开销计数），开工前先在起点上跑一遍记作基线。中途挂了才回起点对照，要多花几轮分辨是不是原有失败（w00026 t37：基线漏了 `workbench-drag-cost`，第 4 片挂了一条，回头才查出分支起点上就 3 次挂 2 次）。
- 把散落各处的判断收成一个出口（关卡）时，关于某个对象的规则（这个人、这个马甲、这个条目）写进出口的名字与分类判断里，不加在各段、各处的入口上：入口上的判断会漏掉经名字、值、分类绕过去的路径（w00039 t35 的简报保密，三轮实现审查都漏在“身份不给写手的人”这条只加在入口的规则上）。
- 计划需要改已 `accepted` 的提案时，只追加决策记录，正文要变的内容写进 Spec。要改已接受的 ADR 时不动它的正文，另写一份新 ADR 部分取代它（[`docs/adr/README.md`](../../../docs/adr/README.md)）；交给子代理的说明同样照此写。

## 与 Task 的关系

- `plan.md` 放在 Task 目录；Task README 只链接它并记录当前进展。
- 实施中计划失效（发现新事实、开发者改了方向）时，先改 `plan.md` 再继续，不让代码与计划分叉。
- Task 完成后计划保留作历程，不再更新；当前状态以 Task README 为准。
- 计划里的内部设计在完成后仍需要知道的，写进代码注释或模块头，不回写 Spec（文档分工见 [`docs/specs/README.md`](../../../docs/specs/README.md#文档分工与寿命)）。
