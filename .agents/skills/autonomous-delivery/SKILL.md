# 自主推进

开发者在场时不用本 Skill：计划先给开发者看、确认后再审查与实施（见 [implementation-planning](../implementation-planning/SKILL.md)）。开发者显式指定本 Skill 后，把逐步确认换成事后追认：照推荐做，记下本该由开发者决定的点，到停止条件或终点时一次汇报。

## 循环

每个 Task 走一遍，Task 之间不停：

1. **写计划**：按 [implementation-planning](../implementation-planning/SKILL.md) 写 `plan.md`，跳过它的“交开发者确认”。计划、Task README 与 Work README 的登记行一起提交。
2. **计划审查**：按 [reviewing](../reviewing/SKILL.md) 做设计审查，审查者是一个强模型子代理，阻塞等它的结论，见下文“审查分工”。
3. **处理审查**：按 reviewing 的“处理结果”逐条核实。成立的直接改进计划；“接受取舍”与本该开发者决定的写进待确认清单。修订后的计划与审查证据一起提交。
4. **实施**：按计划的切片逐片实现、自跑验证、单独提交。计划失效时先改 `plan.md` 再继续。
5. **实现审查**：Task 的切片都提交后，对本 Task 的提交范围启动一次 omp 实现审查，不等它，直接进入下一个 Task；审查报告回来后在主会话有空时处理，处理方式同第 3 步，修正单独提交。收口验证（含全量 e2e）在启动审查前跑完，Task README 写完成状态、证据与“实现审查待处理”。
6. **下一步**：按 Work 的推进顺序（Work README、整体实施路径与已接受提案的切片表）确定下一个 Task，编号按 Work 最大值连续分配，回到第 1 步。

每次提交后 push 当前 Work 分支作为备份，见下文“Git”。

## 审查分工

开发者 2026-10-10 定：omp 审查慢，只在提交 Task 时做一次，且不阻塞；计划与设计的审查改由快的子代理做、可以阻塞。

- **计划与设计审查**：一个强模型子代理（Claude Code 用 Agent 工具、`model: fable`；没有子代理的宿主仍用一个 omp 会话）。说明里给出计划路径、依据的 Spec 与代码位置，要它核对计划里的事实与现有代码是否相符，再看对照参考实现（例如 VS Code、旧应用）、架构与授权的对抗面、真实使用场景与可测性，并补充遗漏的细节与更有用的功能。主会话等结论、处理后再实施。
- **实现审查**：一个 omp 会话，用默认模型（不写 `--model`），每个 Task 一次。说明要求先读本 Task 的完整 diff，再做系统性审查：正确性与不变量、设计缺陷、测试与验收映射、代码质量与 Spec 一致。审查者用一个 detached 审查 worktree（固定在被审提交）、一个仓库外的会话目录与报告文件；审查完删除审查 worktree。同一时间只跑一个 omp 审查。
- omp 会话因上游断开或额度用完中途退出时，用原会话续跑；被时间上限截停时，续跑只要报告。

## 并行

- 线性推进的切片由主会话自己实现：主会话已有上下文，子代理从空白上下文启动要重读代码。
- 出现彼此独立、文件不重叠的切片（例如另一个 Task 的服务端部分）时，主会话继续做当前切片，把独立的切片派给编码子代理（`model: opus`），各用独立的 worktree 与分支，说明写清目标、允许改的文件、验证命令与禁止项；主会话审查它的 diff、自己跑验证后合入。
- 全量 e2e 只在 Task 收口时跑；切片内跑受影响的 e2e 文件。

## 待确认清单

清单在 Work 目录的 `pending-confirmations.md`，Work README 链接它。下面几类照推荐做，并各记一行：

- 产品取舍：界面行为、默认值、文案、外观；
- 偏离已接受的提案或 ADR：按规则只追加决策记录，标“待开发者追认”；
- 新增依赖；
- 审查意见“成立，但接受取舍”；
- 推进顺序之内的调整：拆分、合并 Task，把未开工的已建 Task 并入当前 Task。

每行写日期、Task、类别、做了什么决定、理由、要改回时的代价、链接。开发者追认或改判后，在该行写结果；改判需要的改动另建 Task 或并入下一个 Task。

## 停下等开发者

遇到下面的情况，写好 Task README 的当前状态后停下汇报，不绕过：

- 除 push 当前 Work 分支以外的远端写入：PR、合并、Issue 与 Project、其它分支、force push；
- 真实模型调用；删除用户数据、改写已 push 的历史等不可逆动作；
- 改变产品方向、范围或推进顺序：跳过或调换切片、放弃已接受的功能；
- 同一对象审查满三轮仍有实质问题（reviewing 的轮数上限）；
- 所有模型提供方的额度用完，或环境故障无法验证。

## Git

- 只在 Work 的 worktree 里改动；按路径暂存，不用 `git add -A`、不用裸 `git stash`；提交信息用 Conventional Commit。
- 每次提交后 `git push origin <Work 分支>`，只 push 这个分支，不 force。push 失败时记下原因继续，不改写历史去迁就远端。
- 首次 push 或积压多个提交时，先扫一遍待 push 范围里的密钥（`git diff origin/<Work 分支>..HEAD`），有发现就停下。

## 上下文

推进可能跨越多次上下文压缩。决定一出现就写进 `plan.md`、Task README 或待确认清单，不只留在对话里；压缩后先读当前 Task 的 README 与 `plan.md`、`git log` 与待确认清单，再继续。

性能测量与其它耗时的基准不要和 omp 审查同时跑，审查会话占用的 CPU 会让结果偏慢。

## 汇报

到终点或停下时，用中文、结论先行汇报：完成了哪些 Task 与提交、各轮审查的条数与处理、待确认清单里新增的条目（逐条列出决定与改回代价）、停下的原因与下一步。
