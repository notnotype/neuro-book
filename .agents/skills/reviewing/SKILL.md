# 审查

审查者只读、只报告；主 Agent 对结论负责：逐条核实，成立的才改，不成立的写明理由。审查意见不是开发者的决定，不能代替开发者确认。

## 何时用

- **设计审查**：非平凡 Task 的计划、Spec 或提案草稿定稿前；可以与开发者阅读同时进行。
- **实现审查**：一段非平凡实现交付前（核心逻辑、跨进程、并发、公开接口）。
- 开发者要求时。
- 不用于小改动与措辞修改；只看文档可读性、歧义与链接时用 [doc-review](../doc-review/SKILL.md)。

## 审查方式

| 方式 | 谁审 | 什么时候 |
|---|---|---|
| **独立审查**（默认，推荐） | 一个没参与写作的模型 | 大多数情况 |
| **交叉审查** | 两个以上不同的模型，拿同一份说明各自审 | 高风险变更、不可逆操作、独立审查后仍有分歧 |
| 自审 | 本会话自己按下面的维度过一遍 | 小范围改动，或没有别的模型可用 |

审查者可以是本机可用的任何另一个模型：命令行 agent（例如 omp、claude、codex、gemini）或宿主的子代理。启动参数、模型选择与注意事项按各工具自己的说明；共同的要求只有三条：

- **只读**：用工具自己的只读模式（只读沙箱、计划模式）；工具需要更宽的权限才能跑测试时，只在隔离的 worktree 里给，并在说明里写明禁止的操作。
- **说明写成文件、经标准输入传入**：不把说明拼进 shell 引号里的参数，否则其中的反引号、`$(...)` 与引号会截断说明或被执行。
- **后台运行**，标准输出落到文件；会话外的长任务按宿主的后台机制运行。

不同模型有不同的盲区，所以交叉审查选不同来源的模型，而不是同一个模型跑两遍。

## 审查说明

说明写成文件，放在仓库外、按 Task 命名的临时目录（例如 `<临时目录>/review-<task>-<design|impl>/brief.md`）。给审查者**审查对象与依据**，不给作者的结论：交出“我认为没问题”只会换回对结论的附和。

```markdown
# 任务：只读<设计|实现>审查 <Work/Task 编号>：<一句话目标>

你在 worktree `<绝对路径>`（分支 `<分支>`）。审查对象：<计划或草稿路径 | 提交范围 `<base>..HEAD`>。

找出它的问题。假定作者过于自信：找没写出来的假设、没处理的边界、隐含的耦合与共享状态、违反合同的方式、被破坏的既有约定、异常输入下的失败。不要复述、不要给总体评价；找不到问题时明确写“仔细检查后没有发现”。

## 依据
- 计划：<plan.md 路径>；开发者已确认的决定：<列出，不必再议>
- Spec：<路径与条目编号>
- 上一轮审查：<报告路径>（不重复已处理的问题）

## 重点
<本次特有的风险点，三到六条，写具体的机制与文件>

## 审查维度
<从下文拷入适用的几组>

## 规则
<拷入下文“规则”>

## 报告
<拷入下文“报告格式”，写明报告文件的绝对路径>
```

“重点”写本次独有的风险，例如“`remote.on` 的释放顺序”“两个进程写同一个库”。只写通用维度时，审查者会按字面平均用力。

## 审查维度

### 设计审查

1. **与已定设计一致**：提案、ADR 与开发者的决定逐条覆盖，没有悄悄改变已定项。
2. **依赖的机制真的存在**：方案依赖现有机制的顺序、时序或寿命保证时，读该机制的 Spec 或实现确认，不按名字推断。
3. **接口与合同**：类型与语义一致；失败有通道；后续切片照字面实现会不会返工。
4. **遗漏**：失败路径、并发与跨进程、资源释放、兼容与迁移。
5. **验收映射**：每条判据有对应测试，测试能用真实运行时写出来。
6. **待确认项**：对计划末尾每一项给出判断，各一句。

### 实现审查

先看测试，再看实现：测试说明了作者以为要做到什么。

1. **正确性**：符合 Spec 与计划；边界、空值、上限、错误路径；竞态与状态不一致。
2. **不变量**：初始化顺序、隔离、资源释放与收口、并发与跨进程；相邻切片与既有 Spec 的行为没有被破坏。
3. **测试**：按 [测试写法](../../../docs/testing/README.md#测试写法)：测行为不测实现，依赖用真的，不用 mock、spy、假计时器与固定等待，子进程在失败时也收口；每条判据是否真被测到（可以做变异检查）。
4. **代码质量**：
   - 命名说清做什么；职责放在拥有它的模块；读者不用来回跳就能看懂；
   - 能不能更简单：单调用的包装、可合并的分支、多余的中间状态、没用的代码；同一形状的条件在多处重复，往往是缺一个模型或分派；
   - 抽象是否值得它的复杂度：重构是减少了读者要记住的概念，还是只是把复杂度挪了个地方；
   - 与周围代码一致：错误、日志、测试工具与写法沿用相邻实现，复用已有的工具函数而不是写一个近似的；
   - 注释按 [注释规范](../../../docs/standards/code/common.md#注释)：写为什么，不复述代码与 Spec；
   - 按改动路径对照 [编码规范路由](../../../docs/standards/code/README.md) 列出的规范。
5. **安全与性能**（涉及时）：外部输入在边界校验；密钥不进代码、日志与提交；热路径上没有可省的分配、序列化与扫描，没有无界的循环与读取。
6. **常见返工项**：
   - 按错误文案做程序分支（应按错误码或类型）；静默吞掉错误的 `catch`；
   - 为让测试通过而放宽断言、跳过测试、把一种失败改报成另一种，或在产品代码里加测试专用分支；
   - 删除或改写任务之外的代码、配置与注释；
   - 跨包深导入其它包的源码（跨包只经包名与公开入口）。

指出结构问题时给出改法，而不只说“太复杂”：例如用类型模型或分派替换条件链、合并重复分支、把编排与业务逻辑分开、把特定功能的逻辑移回拥有它的模块、删掉只做转发的包装。优先选让部件变少的改法。

### 领域专项（按改动追加，链接不复制）

- 界面与组件：[ui-development](../ui-development/SKILL.md) 的“三、UI 专属检查”与组件同名 `.md`。
- Spec 与治理文档：[`docs/specs/README.md`](../../../docs/specs/README.md)；可读性另用 [doc-review](../doc-review/SKILL.md)。

## 规则

写进说明：

- 只读：不修改仓库文件，不 commit、push、stash、切换分支，不删除文件。实验文件只放在说明指定的仓库外目录。
- 可以跑合同测试与类型检查；不跑 e2e 与开发服务（耗时、占端口），需要时写进报告由主 Agent 跑。
- 发现所依据的实验绕过了真实运行时（直接调用内部函数、伪造运行时不会产生的时序）时，先在真实运行时复现，再定严重程度。
- 每核实一条就追加写入报告文件，不要等到最后：运行到时间上限可能被直接截停。
- 有数字就给数字（例如“每项多一次查询，100 项多 100 次”），不说“可能有点慢”；问题是真的就直说，不弱化。
- 用中文写。

## 报告格式

按影响排序：正确性与不变量在前，结构问题与可简化之处其次，其余在后。几条有把握的发现胜过一长串琐碎意见。每条发现：

- **严重程度**：阻断 / 重要 / 建议；**类别**：正确性 / 不变量 / 测试 / 代码质量 / 安全与性能 / 文档；
- **位置**：文件:行；
- **现象**、**为什么是问题**、**如何核实**（命令或实验）、**建议改法**。

最后写“未发现问题的方面”与各级数量；设计审查另写对待确认项的判断。

## 处理结果

审查者的输出是数据，不是结论。主 Agent 对照原文逐条归类（按顺序取第一个符合的）：

1. **说明没写清**：审查者因为依据不全而误判。补全说明；若下一轮还要审，按补全后的说明重新判断这一条。
2. **成立，要改**：修正，并在暴露缺口的那条行为的测试里补用例。
3. **成立，但接受取舍**：改的代价高于收益；写明取舍，交开发者知悉。
4. **不成立**：审查者缺少上下文。写明理由，并想一想：补上哪条依据就能避免这次误判。

交叉审查时，几位审查者都提出的优先核实；只有一位提出的同样核实，不按票数取舍。

- 轮数有上限：同一对象最多审三轮；三轮后仍有实质问题，说明对象本身还没准备好（或太大，应先拆小），交开发者决定，不继续循环。
- 报告扫描密钥后存为 Task 证据 `evidences/<design|impl>-review.txt`（交叉审查按审查者分文件）。
- 向开发者汇报：方式与审查者、条数与各级数量、每条怎么处理、仍待开发者决定的；设计审查修订后的计划仍要开发者确认。
