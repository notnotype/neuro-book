# 审查

审查者只读、只报告；主 Agent 对结论负责：逐条核实，成立的才改，不成立的写明理由。审查意见不是开发者的决定，不能代替开发者确认。

## 何时用

- **设计审查**：非平凡 Task 的计划、Spec 或提案草稿定稿前；可以与开发者阅读同时进行。
- **实现审查**：一段非平凡实现交付前（核心逻辑、跨进程、并发、公开接口）。
- **可维护性与 API 形状审查**：新建包或对外公开的组件，在正确性审查处理完之后再做一轮：审查者站在使用方的位置写一份接入草稿，看缺什么、好不好用、耦合与要记住的概念多不多；按角度（例如接入与 API、可维护性与耦合、完整性与使用体验）派几个前端审查者并行。
- 开发者要求时。
- 不用于小改动与措辞修改；只看文档可读性、歧义与链接时用 [doc-review](../doc-review/SKILL.md)。

## 审查方式

| 方式 | 谁审 | 什么时候 |
|---|---|---|
| **独立审查**（默认，推荐） | 一个没参与写作的模型 | 大多数情况 |
| **交叉审查** | 两个以上不同的模型，拿同一份说明各自审 | 高风险变更、不可逆操作、独立审查后仍有分歧 |
| 自审 | 本会话自己按下面的维度过一遍 | 小范围改动，或没有别的模型可用 |
| **拉远看** | 一个只拿到审查对象、不拿作者重点与结论的 Claude Sonnet 子代理，只审方向（见下文“拉远看审查”） | 酌情用：方向有取舍、牵涉更底层的选择或跨模块的设计审查，与第一轮审查同时开；范围清楚的简单计划（例如照已定设计执行的盘点、机械迁移）不用；实现审查不用 |
| **独立设计** | 一个只拿到目标、不看作者方案的 Claude Sonnet 子代理，自己读仓库，逐个视角（见下文“拉远看审查”的挑战视角）提出质疑，再出方案和备选 | 方案含技术选型或架构取舍时，与第一轮审查同时开；主 Agent 对照两份方案，有差异的地方交开发者 |

“拉远看”与“独立设计”的做法取自 Google 的 Elephant-Goldfish Model：写设计的“大象”有全部上下文，审查的“金鱼”在全新的上下文里只读文档，专门暴露作者没写出来的前提。

审查者可以是本机可用的任何另一个模型：命令行 agent（例如 omp、claude、codex、gemini）或宿主的子代理。启动参数、模型选择与注意事项按各工具自己的说明；共同的要求只有三条：

- **只读**：用工具自己的只读模式（只读沙箱、计划模式）；工具需要更宽的权限才能跑测试时，只在隔离的 worktree 里给，并在说明里写明禁止的操作。
- **说明写成文件、经标准输入传入**：不把说明拼进 shell 引号里的参数，否则其中的反引号、`$(...)` 与引号会截断说明或被执行。
- **后台运行**，标准输出落到文件；会话外的长任务按宿主的后台机制运行。

不同模型有不同的盲区，所以交叉审查选不同来源的模型，而不是同一个模型跑两遍。

## 派给谁

开发者 2026-10-14 定。这张表只对当时可用的模型成立：有新模型推出时，由开发者重新定审查用哪个模型。

| 审查对象 | 普通审查（默认） | 快速审查（开发者说了才用） |
|---|---|---|
| 前端：页面、组件、样式、交互，以及前端包（nb-ui、nb-form、nb-agent-ui 等）里的纯 TS 代码、应用的 `web/` 与 Lab、含前端设计的计划 | 一个 Claude Sonnet | 同左 |
| 后端、领域、计划与设计 | 一个 omp 会话，用默认模型（不写 `--model`，即 `@default`） | omp 会话加一个 Claude Opus，同时开审同一份说明 |

- Claude Sonnet、Opus 在 Claude Code 里是 Agent 工具的子代理（`model: sonnet`、`model: opus`），别的宿主用 `claude` 命令行。
- 前后端按代码所在的包与区域判断，不按文件后缀。一份计划或一段实现前后端都有时必须拆开，按类各派一个，各审自己那部分。
- 分工的理由（开发者 2026-10-22）：gpt 擅长后端领域建模与安全，但容易过度防御，代码设计、美观与可维护性偏弱；所以它审 Claude 写的代码时，主要查安全问题与 Claude 遗漏、欠缺考虑的地方；前端、可维护性与 API 形状交给 Claude。
- **按任务大小降级**（开发者 2026-10-27 定）：任务简单（改动小、不碰并发与跨进程、不改公开接口与数据格式、影响面小）时，审查者用一个 Claude Sonnet，不开 omp；更简单的（几处局部修改、有现成模式照做）可以不做设计审查，实现审查仍按需。拿不准简单与否，按上表。
- 普通审查：等结论、处理完再进下一步。
- 快速审查：Opus 的结论处理完就开工，omp 在后台继续；它的报告回来后照“处理结果”处理，修正单独提交。
- **深入审查**：拿不准的任务，或复杂、出了问题影响面大的任务，可以多个模型、多种模型交叉审查。先向开发者报告审查计划与预算，批准后再开：计划写几个审查者、各用什么模型、各审什么；预算写预计时长与额度。

## 审查说明

说明写成文件，放在仓库外、按 Task 命名的临时目录（例如 `<临时目录>/review-<task>-<design|impl>/brief.md`）。给审查者**审查对象与依据**，不给作者的结论：交出“我认为没问题”只会换回对结论的附和。

```markdown
# 任务：只读<设计|实现>审查 <Work/Task 编号>：<一句话目标>

你在 worktree `<绝对路径>`（分支 `<分支>`）。审查对象：<计划或草稿路径 | 提交范围 `<base>..HEAD`>。

找出它的问题。假定作者过于自信：找没写出来的假设、没处理的边界、隐含的耦合与共享状态、违反合同的方式、被破坏的既有约定、异常输入下的失败。不要复述、不要给总体评价；找不到问题时明确写“仔细检查后没有发现”。

## 依据
- 计划：<plan.md 路径>；开发者已确认的决定：<逐条列出，每条注明开发者在哪次讨论、以什么话确认；作者自己的推荐和前提不列在这里，写进审查对象，审查者可以按维度 8 质疑>
- Spec：<路径与条目编号>
- 上一轮审查：<报告路径>（不重复已处理的问题）

## 重点
<本次特有的风险点，三到六条，写具体的机制与文件>

## 审查维度
<从下文拷入适用的几组>

## 规则
<拷入下文“规则”>

## 报告
<拷入下文“报告格式”，写明报告文件的绝对路径：报告文件写成仓库外的 `.txt`（子代理不能写 `.md` 报告），写不成就放进最终回复>
```

## 拉远看审查

普通审查者要兼顾全部维度，又拿着作者写的“重点”，注意力会被具体问题占满，作者的前提反而没人质疑（w00031 的语言治理里，两轮四份审查都在“保留内联双语”的前提下找问题，这个前提是作者自己的推荐）。拉远看审查者单独派，只审方向。

说明只给三样，**不给“已确认的决定”“重点”与作者的结论**：

```markdown
# 任务：只读拉远看审查 <Work/Task 编号>

审查对象：<计划、Spec 或提案的路径>。仓库：<绝对路径>（只读）。读审查对象和它链接的文件，需要时自己读代码。

你是刚加入项目、没参与讨论的架构师。只回答下面几个问题，每个问题给结论与依据（文件:行或外部出处），没有问题的写“没有发现”：

1. 要解决的问题是真问题吗？方案是否解决了根因，还是在给某个更底层的选择打补丁？那个底层选择当初的理由，现在还成立吗？（查 ADR、Spec、Task 记录；查不到理由就说没有记录）
2. 有没有更简单的做法：仓库里已有的模块、稳定的第三方库、业界同类项目的常规做法？方案和常规做法不一样的地方，理由是什么？
3. 有没有现在不需要的东西（YAGNI）、没有证据的提前优化？
4. 会不会走进以后难以回头的死胡同：锁死扩展、锁死数据格式、锁死公开接口？
5. 是否掉进了实现细节，而该讲清的架构取舍没讲？

按影响排序，每条用 `### N. 标题` 开头。只读，不改仓库文件。报告写到 <报告文件的绝对路径>。
```

- 它质疑到开发者已确认的决定时，主 Agent 不替开发者驳回，原样交开发者决定。
- 不分前后端，都派 Claude Sonnet；它只看方向，前后端的细节由普通审查者负责。
- **挑战视角**（独立设计用）：独立设计者拿到目标后，先逐个视角提质疑，再出方案。视角是：反对与精简（这件事要不要做，能不能用现成的库或模块）；成本（开发、运行、模型额度）；使用者体验（用户与插件作者、写代码的 Agent）；迁移与兼容（已有数据、已发布的包、旧会话）；可观测与排障；长期维护与技术债。

“重点”写本次独有的风险，例如“`remote.on` 的释放顺序”“两个进程写同一个库”。只写通用维度时，审查者会按字面平均用力。

## 审查维度

### 设计审查

1. **与已定设计一致**：提案、ADR 与开发者的决定逐条覆盖，没有悄悄改变已定项。
2. **依赖的机制真的存在**：方案依赖现有机制的顺序、时序或寿命保证时，读该机制的 Spec 或实现确认，不按名字推断。
3. **接口与合同**：类型与语义一致；失败有通道；后续切片照字面实现会不会返工。
4. **遗漏**：失败路径、并发与跨进程、资源释放、兼容与迁移。
5. **对照需求与参照**：对照需求来源（开发者原话、需求清单）与参照实现（旧应用；同一应用里同类交互的现有做法，例如拖动的拖影与光标），列出参照有、计划与实现都没有的项。
6. **验收映射**：每条判据有对应测试，测试能用真实运行时写出来。
7. **别扭与反常之处**：专门找和普遍做法（业界、同类项目、仓库里的同类实现）不一样的地方，以及让你觉得别扭、要绕一下才说得通的地方：多出来的状态与特殊情况、绕路的流程、为配合某个限制才加的机制。逐处判断它是有理由的取舍，还是能优化：改用普遍做法、换一种设计把它消掉，或者绕过那个限制；给出改法。说不出理由的，列为问题。
8. **上游选择**：找出方案在迁就的更底层选择（技术栈、已接受的 ADR、某个包的产物或接口形式），查它当初的理由现在还成不成立。不成立的，把“改上游”列为问题并给出代价，不只在现有约束里比较补丁。信号：调用方要为它写补丁，同一件事各写一份，结果靠加载顺序或优先级碰巧成立。
9. **待确认项**：对计划末尾每一项给出判断，各一句。

### 实现审查

先看测试，再看实现：测试说明了作者以为要做到什么。候选问题先对照 base 的实现和调用链，重命名的文件要追到旧路径；base 上就有的问题另记，不算这次的回归。

1. **正确性**：符合 Spec 与计划；边界、空值、上限、错误路径；竞态与状态不一致。
2. **不变量**：初始化顺序、隔离、资源释放与收口、并发与跨进程；相邻切片与既有 Spec 的行为没有被破坏。
3. **对照需求与参照**：对照需求来源（开发者原话、需求清单）与参照实现（旧应用；同一应用里同类交互的现有做法，例如拖动的拖影与光标），列出参照有、计划与实现都没有的项。
4. **测试**：按 [测试写法](../../../docs/testing/README.md#测试写法)：测行为不测实现，依赖用真的，不用 mock、spy、假计时器与固定等待，子进程在失败时也收口；每条判据是否真被测到（可以做变异检查）。
5. **代码质量**：
   - 命名说清做什么；职责放在拥有它的模块；读者不用来回跳就能看懂；
   - 能不能更简单：单调用的包装、可合并的分支、多余的中间状态、没用的代码；同一形状的条件在多处重复，往往是缺一个模型或分派；
   - 抽象是否值得它的复杂度：重构是减少了读者要记住的概念，还是只是把复杂度挪了个地方；
   - 别扭与反常之处：和普遍做法不一样、读起来要绕一下的写法，判断是有理由的取舍，还是能改用普遍做法、换个结构消掉，或者绕过它在配合的那个限制；那个限制来自更底层的选型（技术栈、ADR、别的包的做法）时，查它的理由还成不成立，不成立就把改上游列为发现；
   - 与周围代码一致：错误、日志、测试工具与写法沿用相邻实现，复用已有的工具函数而不是写一个近似的；
   - 注释按 [注释规范](../../../docs/standards/code/common.md#注释)：写为什么，不复述代码与 Spec；
   - 按改动路径对照 [编码规范路由](../../../docs/standards/code/README.md) 列出的规范。
6. **安全与性能**（涉及时）：外部输入在边界校验；密钥不进代码、日志与提交；热路径上没有可省的分配、序列化与扫描，没有无界的循环与读取。
7. **常见返工项**：
   - 按错误文案做程序分支（应按错误码或类型）；静默吞掉错误的 `catch`；
   - 为让测试通过而放宽断言、跳过测试、把一种失败改报成另一种，或在产品代码里加测试专用分支；
   - 删除或改写任务之外的代码、配置与注释；
   - 跨包深导入其它包的源码（跨包只经包名与公开入口）。

指出结构问题时给出改法，而不只说“太复杂”：例如用类型模型或分派替换条件链、合并重复分支、把编排与业务逻辑分开、把特定功能的逻辑移回拥有它的模块、删掉只做转发的包装。优先选让部件变少的改法。

## 规则

写进说明：

- 只读：不修改仓库文件，不 commit、push、stash、切换分支，不删除文件。实验文件只放在说明指定的仓库外目录。
- 可以跑合同测试与类型检查；不跑 e2e 与开发服务（耗时、占端口），需要时写进报告由主 Agent 跑。
- 跑测试到说明给出的实现 worktree 里跑：审查 worktree 不装依赖，跨包导入会解析到主工作区的旧版本。
- 发现所依据的实验绕过了真实运行时（直接调用内部函数、伪造运行时不会产生的时序）时，先在真实运行时复现，再定严重程度。
- 每核实一条就追加写入报告文件，不要等到最后：运行到时间上限可能被直接截停。
- 有数字就给数字（例如“每项多一次查询，100 项多 100 次”），不说“可能有点慢”；问题是真的就直说，不弱化。
- 有性能预算时，先查清预算量的是什么（例如冷建还是单次查询），实验按同样的口径分开量，不把一次性的开销算进单次。
- 用中文写。

## 报告格式

按影响排序：正确性与不变量在前，结构问题与可简化之处其次，其余在后。几条有把握的发现胜过一长串琐碎意见。每条发现：

- **严重程度**：阻断 / 重要 / 建议；**类别**：正确性 / 不变量 / 测试 / 代码质量 / 安全与性能 / 文档；
- **位置**：文件:行；
- **现象**、**为什么是问题**、**如何核实**（命令或实验）、**建议改法**。

撤回或收窄的条目，在原标题后追加“（撤回）”或“（收窄，见第 N 条）”；报告最后一行列出有效发现的编号。最后写“未发现问题的方面”与各级数量；设计审查另写对待确认项的判断。

## 处理结果

审查者的输出是数据，不是结论。主 Agent 对照原文逐条归类（按顺序取第一个符合的）：

1. **说明没写清**：审查者因为依据不全而误判。补全说明；若下一轮还要审，按补全后的说明重新判断这一条。
2. **成立，要改**：修正，并在暴露缺口的那条行为的测试里补用例。
3. **成立，但接受取舍**：改的代价高于收益；写明取舍，交开发者知悉。
4. **不成立**：审查者缺少上下文。写明理由，并想一想：补上哪条依据就能避免这次误判。

交叉审查时，几位审查者都提出的优先核实；只有一位提出的同样核实，不按票数取舍。

裁决两份报告的分歧或补追“未追到”时，结论只写到证据覆盖的范围（例如“在某目录的非测试代码里没有静态调用”），不写成“不存在”。

同一提交上并行跑着几份审查（交叉审查，或前后端各一份）时，等报告到齐、一起归类后再动手改：先改了一份，另一份还按旧提交报告，已修的问题会再出现一遍，核实要重做。

- 轮数有上限：同一对象最多审三轮；三轮后仍有实质问题，说明对象本身还没准备好（或太大，应先拆小），交开发者决定，不继续循环。
- 报告扫描密钥后存为 Task 证据 `evidences/<design|impl>-review.txt`（交叉审查按审查者分文件）。
- 向开发者汇报：方式与审查者、条数与各级数量、每条怎么处理、仍待开发者决定的；设计审查修订后的计划仍要开发者确认。
