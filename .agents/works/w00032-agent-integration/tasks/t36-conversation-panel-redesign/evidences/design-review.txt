## 1. `head` 加在 `ViewImplementation` 上就等于经 SDK 导出了，与决定 6 冲突

- **严重程度**：重要；**类别**：不变量 / 文档
- **位置**：计划“关键设计 / 工作台：视图的标题区”第 1 条、“不做与风险”最后一条；`packages/neuro-book/src/sdk/workbench.ts:24`、`packages/neuro-book/plugin-sdk/pack.test.ts:376`
- **现象**：计划把 `head?(): Promise<Component>` 直接加到 `contracts.ts` 的 `ViewImplementation`，把 `headShown` 加到 `ViewContext`。而 `src/sdk/workbench.ts:24` 是 `export type {ItemImplementation, ViewContext, ViewImplementation} from "nbook/plugins/workbench/web/contracts"`，`pack.test.ts:376` 把这两个名字列为 `@notnotype/nb-plugin-sdk/workbench` 的公开导出。
- **为什么是问题**：决定 6 是“插件 SDK 不导出，等第二个用户出现再导出”。照计划写，第三方插件立刻就能在类型上写 `head` 并读 `context.headShown`，工作台也会照样渲染它（`registry.ts` 不区分内置与第三方），等于没有门。计划的风险一节还写着“插件 SDK 会导出它”与“先只给内置插件用”两句并列，说明作者没注意到导出是自动发生的。
- **如何核实**：`grep -n "ViewImplementation\|ViewContext" packages/neuro-book/src/sdk/workbench.ts`。
- **建议改法**：二选一并写进计划：（a）在 `contracts.ts` 另立内部类型，例如 `BuiltinViewImplementation extends ViewImplementation {head?…}` 与 `ViewHeadContext extends ViewContext {headShown}`，SDK 只导出原来的两个；`registry.ts` 读 `head` 时还要按 `manifestFormat.isBuiltinId(descriptor.plugin)` 判，第三方交了也不用，否则“只给内置”只是类型上的约定。（b）接受导出，那就改决定 6，并让 `pack.test.ts` 的导出清单与 SDK 文档跟着改。
## 2. 开场指令发 `composer.draftChanged` 不会把文字放进输入框

- **严重程度**：阻断；**类别**：正确性
- **位置**：计划“nb-agent-ui：第一屏”第 4 条（“点了发 `composer.draftChanged` 填进输入框”）；`packages/neuro-book/src/plugins/agent/web/session-host.ts:359-367`、`:1310-1313`；`packages/nb-agent-ui/src/types.ts:413-417`；`packages/nb-agent-ui/src/vue/composer/AgentConversationComposer.vue:124-128`、`:192`
- **现象**：输入框是“宿主给版本号”的受控方式：`AgentConversationComposer` 只在 `composer.draft.version` 变化时把 `draft.text` 写进编辑器（124–128 行）。宿主处理 `composer.draftChanged` 时只做 `draftText = action.text; noteDraft(action.text)`（1310–1313 行），不动 `draft` 也不加版本；只有 `setDraft`/`setDraftSilently` 才加版本。`draftChanged` 的语义是“编辑器报告用户打了什么”，方向是视图到宿主。
- **为什么是问题**：照字面实现，点了指令宿主记下了文字，输入框却还是空的；用户一按发送，发出去的是 `draftText`（宿主那份）而不是看到的内容，看到与发出的不一致。验收映射里的 e2e“没选会话时点一条指令，输入框里是它”会直接失败，到第 6 片才暴露，返工要回到第 2、3 片改动作合同。
- **如何核实**：读上面几处；或在 `session-host.test.ts` 里 `act({type: "composer.draftChanged", text: "x"})` 后看 `ctx.value.composer.draft.version` 不变。
- **建议改法**：新增一个动作，例如 `composer.fill`（或 `starter.pick`，带 `text`），宿主用 `setDraft(text)` 处理（加版本、有会话时存草稿）；在 `types.ts` 的 `AgentViewAction` 与 `agent-conversation-view.md` 的动作表里登记。同时写清两件计划没定的事：已有草稿时是替换还是询问（旧应用是直接填入、覆盖）；填入后光标放在末尾。DOM 测试要断言编辑器里的文字，而不是断言发出了某个动作。
## 3. `meta.model` 只有一个码，宿主推不出“哪个角色、哪个模型、哪家服务商”；“没有服务商”没有对应的码

- **严重程度**：重要；**类别**：正确性 / 接口与合同
- **位置**：计划“模型不可用的提示卡”的宿主一条；`packages/nb-harness/src/kernel/api/host.ts:155`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:114`、`:209-213`；`packages/nb-models/src/core/choice.ts:17-26`；`packages/nb-models/src/core/core.ts:128-156`；`packages/nb-models/src/config/shapes.ts:77`
- **现象**：
  1. 快照里的 `model` 失败时是 `{ok: false; code}`，不带角色 id、模型引用或服务商。
  2. 一次请求用哪个角色由 `chooseModel` 定：会话设置 `core.model`（可能是模型引用，也可能是 `role:<id>`）> Profile 设置里的 `model` > Profile 设置里的 `role` > 声明的 `role` > 主力档（`agent.ts:209-213` 读的是 `agentSettings.settings.profileSettings`，用户可改）。浏览器的宿主只有 `deps.roles()`（每个角色的状态）、`deps.models()`（只含有凭据的可用模型，`plugin.ts:110`）、`deps.profiles()`（声明的 `role`）。
  3. `no-model` 只在模型服务不在时产生（`agent.ts:114` 的 `NO_MODELS`），不是“没有服务商”。一个服务商都没有时，内置角色的 `model` 是 null（`shapes.ts:77`），码是 `role-unbound`。
- **为什么是问题**：
  - 计划写“按 `meta.model` 的码，加上模型服务的角色与服务商快照，组出三种卡”。照字面实现，宿主只能自己在浏览器里再写一遍 `chooseModel` 的顺序，还要另读 Profile 设置。这是同一件事写两份，后端改了选择顺序，卡片就会指错角色，“去绑定”把用户带到不相干的角色上。
  - 会话直接选了某个模型（不是角色）时根本没有角色。`no-credentials` 卡的“说明写哪个角色绑定的哪个模型”在这种情况下没法写。
  - “没有服务商”那张卡照字面永远不会出现：没有服务商时码是 `role-unbound`，用户看到的是“‘主力’角色还没绑定模型 / 去绑定”，点进角色页又没有模型可绑。
- **如何核实**：读上面几处；`grep -rn '"no-model"' packages/neuro-book/src packages/nb-models/src`，只有 `agent.ts:114` 一处产生。
- **建议改法**：
  - 让失败结果带上选中了什么。在 nb-models 的端口解析失败时附 `choice`（`{role}` 或 `{reference}`，`no-credentials` 时再带 `provider`），经 `ModelResolution` 的失败分支进快照的 `model`。harness 的类型（`host.ts:155`、`ModelResolutionCode` 所在的 `model.ts`）要跟着加可选字段，对应改 `models/service.md` 与 `agent/sessions.md` 的快照形状。宿主只做查表，不再推导。
  - 判定顺序写进计划和 Spec：服务商快照为空时，不管码是什么都出“添加服务商”；其次按码分 `role-unbound`、`no-credentials`；`unknown-model` 与 `no-model` 走原写法。
  - 这一改跨 nb-harness、nb-models、agent 后端三处，第 4 片的范围与验证要相应扩大，不能只写 `session-host.test.ts`。
## 4. 子代理浮层的行数据，现有的 `tree` 与 `jobs` 给不齐；孙代理的停止会静默失败

- **严重程度**：重要；**类别**：正确性 / 接口与合同
- **位置**：计划“子代理管理”的 `subagents-panel.ts` 与 `SubagentsEntry.vue` 两条；`packages/neuro-book/src/plugins/agent/shared/subagents.ts:19-69`；`packages/neuro-book/src/plugins/agent/backend/subagents/tree.ts:22-23`、`:114-122`；`packages/neuro-book/src/plugins/agent/backend/remote.ts:216-220`；`packages/neuro-book/src/plugins/agent/web/session-host.ts:329-337`；`packages/nb-harness/src/kernel/api/storage.ts:13-17`
- **现象**（逐项对照计划给每一行要的字段）：
  1. **任务（prompt 首行）**：`TreeItem` 没有 prompt，只有 `callId`/`invocation`。agent 任务的 `JobItem.summary` 是子会话标题（`subagents/tools.ts:313`、`:397`、`:412`），也不是 prompt。prompt 只在派它的那次工具调用的参数里：子代理的在当前会话的 transcript 里，孙代理的在子会话的 transcript 里，而当前宿主没有加载子会话。
  2. **最近一步或结果**：`step`、`tools` 只给最近开始的至多 16 个在跑后代，其余会被删掉（`tree.ts:117-121`）。结果文字不在 `tree` 里，卡片是从父会话 transcript 里的工具结果按 `runId` 建索引取的（conversation.md 输出 33）。孙代理的结果在子会话里，取不到。`runs[].reason` 只有 `finished|completed|error|interrupted|aborted`，没有出错原因；定稿图 `r6/head-open.webp` 里出错行写的是“模型服务不可用”，这句话没有来源。
  3. **状态**：计划列了 5 种（运行中、等你处理、完成、出错、已停止）。`TreeState` 还有 `question`（等派它的 Agent 答），收口原因还有 `interrupted`，计划都没有对应。卡片（输出 33）写的是“在问：…”“已中断”，同一个子代理在卡片和浮层里会写成两种状态。
  4. **停止**：`jobs` 只有本会话启动的任务（`session-host.ts` 的 `Current.jobs` 注释）。孙代理的运行是子会话的任务，当前宿主拿不到它的 `jobId`。就算拿到了，`killJob` 也只认 `owner === sessionId`（`remote.ts:218`），`store.kill` 遇到 `job-unknown` 又不报（`session-host.ts:333`），结果是点了停止什么都不发生。用户直接在子会话里发消息引起的运行不是父会话的任务，同样没有 `jobId`。
  5. **定稿图里有、计划没写的**：浮层标题行的汇总（“5 个 · 2 个在跑 · 1 个等你处理”）、每行的“工具次数 · 用时”（要 `now` 每秒走）、底部的提示（“点一行进入子会话；运行中的悬停可停止。”）。
- **为什么是问题**：第 5 片照计划写纯函数时，会发现一半字段没有来源。到时候只能临时加后端字段，或者孙代理的行留空、停止按钮没反应，都偏离已定的决定 11（“全部子代理与孙代理……运行中的悬停可停止”）。
- **如何核实**：读 `TreeItem`、`JobItem` 的字段；`grep -n "owner !== sessionId" packages/neuro-book/src/plugins/agent/backend/remote.ts`。
- **建议改法**：开工前在计划里加一节“行数据从哪来”，逐字段写来源与取不到时的写法：
  - 后端给 `TreeItem` 加 `task`（派发参数里 prompt 的首行，截断）与 `outcome`（最近一次收口的第一句或出错原因），在 `tree.ts` 里随整份推送；动态字段被截掉的行写“运行中”，不写次数。
  - 停止改用按子会话停：新的远程指令 `stopRun({sessionId: 子会话, runId})`，按“祖先是当前会话”校验，或者让 `killJob` 认“owner 是当前会话的后代”；`store.kill` 遇到 `job-unknown` 要给提示，不能吞掉。
  - 状态与卡片共用一张表（输出 33 的那套），把 `question`、`interrupted` 列进去。
  - 汇总、次数与用时、底部提示照定稿写进计划。
  - 这些都是后端合同（`agent/subagents.md` 输出 21、`jobs.md`）的改动，要列进“Spec 与文档改动”和第 5 片的范围。
## 5. 把手当 `Popover` 的触发器时，Reka 会改写把手的 id、叠加点击；点标题同时“激活或展开面板”和“开会话列表”

- **严重程度**：重要；**类别**：正确性 / 不变量
- **位置**：计划“工作台：视图的标题区”第 1 条（“点击由视图监听”）、“nb-agent-ui：新的顶栏”（中列把手里放标题与下拉）；`WorkbenchPanelHead.vue:84-93`；`node_modules/reka-ui/dist/Popover/PopoverTrigger.js:26-54`、`node_modules/reka-ui/dist/Primitive/Slot.js:15-19`；`docs/specs/ui/workbench-layout.md` 输出 20（“点标题激活它，面板收成标题行时展开”）
- **现象**：
  1. 现在的会话下拉是 `<Popover>` 加一个触发按钮（`AgentConversationView.vue:388-396`）。新的顶栏要让把手本身当触发器，否则就是按钮里套按钮。`PopoverTrigger` 用 `as-child` 时，会把 `id`（`reka-popover-trigger-*`）、`type`、`aria-haspopup="dialog"`、`aria-expanded`、`aria-controls`、`onClick` 合进子节点。把手是组件，这些落成 fallthrough attrs，覆盖它根元素上的同名属性。于是工作台给的 `id`（`panelTabDomId`）被换掉，而 `WorkbenchSurface.vue:319` 的 `aria-labelledby`、按 id 找标签的测试都指着原来那个 id。
  2. 把手自己的 `@click="emit('activate')"`（84–93 行）还在，Reka 的 `onOpenToggle` 叠在上面。面板收成标题行时点标题，按输出 20 要展开面板，现在会同时弹出会话列表；面板展开、头的位置跟着变，列表的锚点也跟着跳。
  3. 读屏上，把手的角色变成“按钮，有弹出对话框”，可访问描述还是“按空格拿起并拖动”。空格拿起、回车开列表，这两个键位计划没有写，Spec 也没写。
- **为什么是问题**：计划说“拖动、键盘拿起、右键菜单都还挂在工作台给的把手上，所以一个视图交不交 `head`，拖动行为完全相同”。这个不变量能不能成立，取决于视图怎样把把手接到浮层上，计划没有定，照最自然的写法会破坏 id 与点击语义。
- **如何核实**：读 Reka 的 `Slot.js`：`mergeProps(attrs, child.props)` 之后 `cloneVNode`。把手是组件节点，`child.props` 里没有 `id`，Reka 的 `id` 落成 fallthrough attr；Vue 合并根节点时 fallthrough 胜出（`class`、`style`、`on*` 除外）。可以在 nb-ui 的 DOM 测试里把一个带固定 `id` 的组件放进 `Popover` 的 `trigger` 插槽，看渲染出来的 `id`。
- **建议改法**：
  - 把手合同写死：根元素的 `id`、`data-panel-tab`、`aria-description`、`contextmenu` 由工作台定，不接受 fallthrough，`inheritAttrs: false`，只透传 `aria-expanded`、`aria-haspopup` 两项。把手发一个 `press` 事件，由工作台先处理收起（收起时只展开、不往下传），再交给视图。
  - 视图用受控的浮层（`sessionsOpen` 加 `AnchoredPopover` 或 `Popover` 不带 `trigger`，锚到把手元素），不用 `as-child` 的触发器。焦点与 Escape 要自己处理，这一点计划要写。
  - Spec 输出 20 写清：有标题区时点标题，在收起状态下只展开，在展开状态下开会话列表；回车开列表，空格拿起。
## 6. 标题区组件出错、加载失败或交付撤回时，计划没有退路，面板会连拖动源一起丢掉

- **严重程度**：重要；**类别**：不变量 / 正确性
- **位置**：计划“工作台：视图的标题区”的 `WorkbenchShell.vue` 一条（“加载与 `load()` 同时进行，没加载完时照旧写标题”）与“不变量”一条；`WorkbenchViewFrame.vue:46`（内容的 `onErrorCaptured`）；`views/registry.ts:157-167`（`load` 的作废判定）；`views/view-instances.ts:93-106`（交付撤回时卸组件）
- **现象**：
  - 内容组件有 `WorkbenchViewFrame` 兜着：渲染出错只坏这一个视图，可以重试。标题区组件画在 `WorkbenchPanelHead` 里，工作台那棵树上没有错误边界。它渲染时抛错，Vue 会把它渲染成空注释，把手也就没了：这块面板没有拖动源、没有右键菜单，内容 `region` 的名字也指空。
  - 视图如果有条件地不渲染把手（例如 `v-if` 写错、加载中先画别的），结果一样。
  - `head()` 的 Promise reject、贡献方插件停止或撤回交付（`view-instances.ts:97-101` 卸内容组件）时标题区怎么办，计划没写。照“与 `load()` 同时进行”实现，很容易漏掉作废判定（`registry.ts` 的 `#current`），插件停了，面板头还挂着它的组件。
- **为什么是问题**：计划的不变量是“一个视图交不交 `head`，拖动行为完全相同”，可工作台没有任何机制保证这一点，全靠视图写对。决定 6 说先只给内置插件用，正是因为这个接口还新，出错的代价落在工作台的结构操作上（拖不动、移不走）。
- **如何核实**：读 `WorkbenchViewFrame.vue` 的错误边界，对照 `WorkbenchPanelHead.vue` 没有对应的东西。
- **建议改法**：
  - `WorkbenchPanelHead` 画标题区时包一层错误边界：出错、加载失败、交付不在、视图实例不是 `ready` 时，都退回原来的 `<h2><button>`，并写一条诊断。`headShown` 跟着退回的结果走（为假），内容里照样画头。
  - `head()` 的结果按 `load()` 同样的句柄与代际作废。
  - 把手由工作台渲染在标题区组件外层，视图组件只填插槽内容（作用域插槽，或工作台把视图组件包进把手里，而不是把手交给视图），这样视图漏画也不会丢拖动源。代价是视图不能把别的按钮放在把手两侧的同一个网格里，但可以把左、右两列做成另外两个插槽。
  - 切片 1 的 DOM 测试加两种情况：标题区组件抛错，Promise reject。两种都应该看到原来的标题按钮，拖动描述还在。
## 7. “标题按整个头的宽度居中”在现有面板头结构里做不到

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“nb-agent-ui：新的顶栏”第 2 条、“工作台”的 `WorkbenchPanelHead.vue` 一条；`WorkbenchPanelHead.vue:79-133`、`:137-155`
- **现象**：面板头是 flex：`__band`（`flex: 1 1 auto`）、视图动作、框架按钮各占一段。计划把 `<component :is="head">` 画在标题带里，替代 `<h2>`，所以标题区的三列网格只占标题带那一段，右边还有 2 到 3 个 26px 的框架按钮（`headReserved` 的估算），浮动窗是 1 个。标题会在标题带里居中，比整个头的中线偏左大约 26 到 39px，偏多少还随框架按钮的个数变（能不能收起取决于父分支方向）。内容里画的那份头没有框架按钮，两处的居中位置也就不一样。
- **为什么是问题**：开发者在决定 7、8 里明确说居中好看，`r3/p-center*.webp` 定的是对称居中。偏移会随面板位置变，截图验收时容易被当成实现错误返工。
- **如何核实**：按 `headReserved` 算：树里的分节有最大化、浮动、可能还有收起，即 2 到 3 个按钮。
- **建议改法**：二选一写进计划：（a）有标题区时，`WorkbenchPanelHead` 不再自己排框架按钮，把它们作为一个插槽或属性交给标题区组件，放进右列，由那一列的网格对称留位；（b）标题区网格的左右两列用相同的 `minmax`，宽度取左右两侧较大的那个（CSS 的 `grid-template-columns: 1fr auto 1fr`，框架按钮也画在网格里）。不管选哪种，框架按钮都要和 `trailing` 一起放在标题区网格的右列。
## 8. `focus` 怎样送到页面没有定：窗口已开、要先确认放弃改动、页面还没加载、同一个 `focus` 再点一次，这几种情况都没处理

- **严重程度**：重要；**类别**：正确性 / 接口与合同
- **位置**：计划“模型不可用的提示卡”中设置窗口一条（“`focus?: string`，原样交给那一页，由页面解释”）；`packages/neuro-book/src/plugins/settings/web/settings-window.ts:666-713`（`perform`、`requestLeave`、`openWindow`）、`:202-221`、`:651`、`:757`（`fileLocation`/`takeFileLocation`）；`packages/neuro-book/src/plugins/settings/web/contracts.ts:27`；`packages/neuro-book/src/sdk/settings-browser.ts:10`
- **现象**：
  - `openWindow` 在窗口已开、分区没变时不导航（`moves` 为假），只加 `focusRequest`（窗口自己的聚焦）。页面已挂着，计划没说它怎样得知“又来了一个 `focus`”。如果做成一个 ref，用户连点两次“去绑定”，值不变，第二次就没反应。
  - 窗口开着、当前页有未保存的改动时，`requestLeave` 先弹确认框，`leaving` 存的是 `SettingsLeaveTarget`。`{kind: "open"}` 里没有 `focus`，用户确认之后 `focus` 已经丢了；用户取消时 `focus` 也不该留下。
  - 页面是懒加载的，角色页、服务商页的数据也要异步取。挂载时角色列表可能还是空的，“滚到这个角色、聚焦它的选择框”要等数据到了才能做。
  - 仓库里已经有一样形状的东西：`fileLocation` 加 `takeFileLocation`，“只属于紧接着的那一次打开”，在 `perform` 里先清掉（669 行），由视图读完文件后取走。计划没有沿用它，另起了一个“原样交给页面”的说法。
  - 要把 `focus` 交给页面，只能加在 `SettingsPageContext` 上，而这个类型经 `src/sdk/settings-browser.ts:10` 公开导出。计划没提它会成为第三方设置页的公开接口。
- **为什么是问题**：验收映射里只有“角色没绑定时点‘去绑定’，设置窗口开在角色页、焦点在那个角色上”这一条 e2e，覆盖的是窗口原本关着的情况。上面四种都会失败，而且失败时没有任何提示（计划规定认不出的 `focus` 忽略）。
- **如何核实**：读 `openWindow` 与 `perform`；`SettingsLeaveTarget` 的 `open` 分支只有 `section`、`layer`。
- **建议改法**：
  - 照 `fileLocation` 做：`SettingsLeaveTarget` 的 `open` 加 `focus`；`perform` 时存进 `pendingFocus = {section, focus, seq}`；页面经上下文的 `takeFocus(): string | null` 在数据就绪后取走，取走即清空。窗口已开、分区相同时也写一次新的 `seq`，页面 `watch` 这个序号。
  - 在计划里写明 `SettingsPageContext` 加的是公开字段，同步 `settings/settings-window.md` 输出 15 与 SDK 文档；不想公开就做成只给内置页的内部上下文。
  - 测试补三种：窗口已开在同一页、已开在别的页且有未保存改动（确认、取消各一次）、页面数据晚到。
## 9. 第一屏的“最近对话”和“查看全部（N）”没有写数据从哪来；直接用 `session-list` 会带上过滤、子会话，而且列表没人刷新

- **严重程度**：重要；**类别**：正确性
- **位置**：计划“nb-agent-ui：第一屏”第 1、3 条（`welcome.recent`、`total`）；`packages/neuro-book/src/plugins/agent/web/session-list.ts:44-68`、`:76-118`；`SessionPanelHost.vue:30-37`；旧应用 `AgentChatEmptyState.vue` 的 `displayRecentSessions`

## 10. 提示卡的适用范围与叠放没定：没选会话时不出卡；`ready` 时的能力提示、归档、打开失败怎么画没写；浮在输入框上沿会压住排队消息、停靠区和最后一条消息

- **严重程度**：重要；**类别**：正确性 / 与已定设计一致
- **位置**：计划“模型不可用的提示卡”nb-agent-ui 一条；`session-host.ts:1575-1583`；`AgentConversationComposer.vue:358-372`、`:181-188`；`docs/specs/agent/conversation.md` 输出 37（“在排队消息与可用性提示的上面”）与“失败与恢复”表；t29 决定 9（“要与应用里别处的警告写法统一”）
- **现象**：
  1. **没选会话时不出卡**：`target === null` 时 `meta` 是 undefined、`model` 是 null，`availability` 落到 `ready`。新用户第一次打开、一个服务商都没有时，第一屏上没有任何提示，要发出第一句、建好会话之后才出现卡片。可第一屏正是最需要这张卡的地方（`r4/notice-no-provider.webp` 就是这个场景）。
  2. **其它状态**：现在那一行字画的是所有 `availability.message !== ""` 的情况，包括 `ready` 时的模型能力提示（输出 32，不拦发送）、`archived` 加“恢复”、`load-error` 加“重试”。计划只说“输入框不再画上方那行字，改画 `AgentNoticeCard`”，又说“别的码保留现在的写法”，没说这几种是变成卡片还是保留行。能力提示如果也变成一张常驻、关不掉、压住消息的卡片，就太重了。
  3. **叠放**：Spec 输出 37 定的顺序是停靠区在排队消息与可用性提示之上，都在输入框里排版。浮层卡片压在输入框上沿，会盖住排队消息（`AgentQueuedMessages` 在同一个 footer 里）、停靠区和消息流最后几行。计划只写了消息区顶端的渐隐，没写底部要给卡片留出多少距离、自动贴底时把卡片高度算进去。

- **为什么是问题**：第 1 点让主场景失效；第 2、3 点照字面实现会和现有 Spec 打架，Lab 截图阶段才会发现。
- **如何核实**：读 `ctx` 的 `availability` 计算与 composer 的模板。
- **建议改法**：
  - 没选会话时，宿主按“新会话会用的 Profile”求一次可用性（与第 3 条的判定共用，只读服务商快照与角色状态），出同样的卡。
  - 列一张表：`profile-unavailable` 出卡；`ready` 加能力提示保留现在的一行（或做成可关的轻提示）；`archived`、`load-error` 保留一行。写进 `ui/agent-conversation-view.md` 的输入框小节。
  - 卡片放进停靠区的位置（输出 37 的“可用性提示”那一层），不另做浮层；或者在 Spec 里改写输出 37 的顺序，并规定消息流底部的留白等于卡片高度，贴底时也算进去。
  - 占位的优先级写清：不可用的原因 > 中断后继续 > 运行中 > 普通；`message` 为空时用普通占位。

## 12. `headShown` 的切换时机：启动时头会先画在内容里再跳到面板头；`ViewContext` 由实例层建，拿不到算它要的条件

- **严重程度**：建议；**类别**：正确性 / 代码质量
- **位置**：计划“工作台”的 `ViewContext` 一条与 `WorkbenchShell.vue` 一条；`views/view-instances.ts:55-59`、`:61-77`；`state/layout-present.ts:132-134`
- **现象**：
  1. `head()` 与 `load()` 是两个 Promise，计划让它们同时进行，“没加载完时照旧写标题”。内容先到、头后到时，`headShown` 先为假，`ConversationHost` 在内容顶上画一份头；等头到了再变真，内容里那份消失，整块内容上移一行（约 32px）。反过来头先到时，面板头先画出会话标题，内容还在加载，也说得过去。前一种是肉眼可见的跳动。
  2. `contextFor` 只接收 `visible` 与 `location` 两个来源，`headShown` 要的“这块面板只写标题”和“`head` 已加载”都在外壳里（`titleOnlyPanelIds`、外壳侧的头组件表），实例层要多收一个回调。计划只列了 `contracts.ts`、`WorkbenchPanelHead.vue`、`WorkbenchShell.vue`，没列 `view-instances.ts` 与 `WorkbenchSurface.vue`（第 13 条）。
  3. 标签数变化（例如命令把另一个视图开进同一块）时 `headShown` 翻转：会话下拉因为 `sessionsOpen` 在宿主上会在新位置重开；子代理浮层的开合在 `SubagentsEntry` 自己身上，会丢，焦点也丢。计划只考虑了 `sessionsOpen`。
- **为什么是问题**：第 1 点是每次启动都会看到的闪动；第 2 点会让第 1 片的文件清单偏小；第 3 点是焦点管理的缺口，键盘用户会被丢回文档根。
- **如何核实**：读 `view-instances.ts` 的 `load` 与 `contextFor`。
- **建议改法**：有 `head` 的视图，实例的 `ready` 等两个 Promise 都 settle（`head()` 失败按第 6 条退回）再置，`headShown` 从一开始就是最终值；`contextFor` 增加 `headShown: (viewId) => boolean` 选项，并把 `view-instances.ts` 列进第 1 片；子代理浮层的开合也放到宿主上；翻转时如果焦点在旧的头里，把它移到新位置对应的元素上（按 `data-` 标记找）。

## 15. 返回取“`path` 的倒数第二项”是错的：`path` 不含本会话，父会话是最后一项

- **严重程度**：重要；**类别**：正确性
- **位置**：计划“nb-agent-ui：新的顶栏”第 2 条第 1 小点；`packages/nb-agent-ui/src/types.ts:176-180`；`session-host.ts` 中 `ctx` 的 `path`（`[...target.ancestors].reverse()`）
- **现象**：`AgentSessionView.path` 的合同是“子会话的祖先，从根会话到父会话”，不含本会话。宿主也是把“从父会话起”的 `ancestors` 反过来交出去的。所以直接的父会话是 `path.at(-1)`。取倒数第二项时：子代理（`path` 只有根一项）取到 undefined，返回按钮没有反应；孙代理会跳过父会话，直接回到根。
- **为什么是问题**：返回是子会话头部唯一的导航（面包屑按决定删掉了），这里取错，子会话就回不去了。计划的 DOM 测试“返回到父会话”如果照计划的说法写断言，会把错误固定下来。
- **如何核实**：读 `types.ts:176-180` 的注释。
- **建议改法**：写成 `path.at(-1)`。`path` 为空或缺失时不画返回，左列画新建。父会话读不到（`title === null`）时照样可以返回，选不到时按切换会话失败的现有写法提示。DOM 测试用三层（根、子、孙）的 `path`，断言孙会话点返回发的是子会话的 id。
## 16. “出错未看”的基线与归属没写清：宿主按位置有两个，“本窗口”的记录会变成两份；什么算“旧的出错”没有判据

- **严重程度**：建议；**类别**：正确性
- **位置**：计划“子代理管理”的“出错未看”三条；决定 3；`plugin.ts:273-296`（`hosts` 按 `"view" | "page"` 各建一个宿主）
- **现象**：
  1. 计划说“会话宿主在本窗口里记一份”，可宿主是按位置建的，右栏一个、编辑区页面一个。在页面里打开浮层看过了，右栏那份不知道，红点还亮。
  2. “刷新后旧的出错不再亮”要有一条基线：第一次拿到某个会话的 `tree` 时，已有的出错都算看过。可宿主同一时刻只订阅当前会话。用户在会话 B 时，会话 A 的子代理出了错；切回 A 时这是第一次拿到 A 的 `tree`，这条出错按基线算“旧的”，不亮。而决定 3 的说法是“窗口打开期间新出错、还没看过的才亮”。
  3. “出错”的判定计划写的是 `runs` 里的 `reason`，取值有 `finished|completed|error|interrupted|aborted`（`nb-harness/src/kernel/log/index-file.ts:59`、`events.ts:108`），计划没说只认 `error`，还是 `interrupted` 也算。
- **为什么是问题**：第 1 点是两个位置都在用时会看到的不一致；第 2 点和决定 3 的字面意思不符，测试按哪种写都可能被认为写错。
- **如何核实**：读 `hostAt` 与 `subagentData` 的订阅范围。
- **建议改法**：已看过的 `runId` 集合放在插件作用域（窗口级），两个宿主共用。基线改为“窗口启动时刻”：`IndexedRun.endedAt` 早于插件激活时刻的出错算旧的，之后结束的都算新的，与当时订阅的是哪个会话无关。出错只认 `reason === "error"`，写进 `agent/conversation.md` 的新输出与纯函数测试。

## 20. `starters` 写成 schema 上限会让整个 Profile 被拒：多写一条或多一个键，Profile 就从目录里消失

- **严重程度**：建议；**类别**：不变量 / 接口与合同
- **位置**：计划“Profile 的开场指令”第 1 条（“至多 3 条”）；`packages/neuro-book/src/plugins/agent/shared/points.ts:63-93`；`docs/specs/runtime/plugins.md` 输出 15、验收 16（`invalid-declaration` 拒绝整条贡献）；`packages/neuro-book/src/sdk/agent.ts:15`（`AgentProfileDeclaration` 公开导出）
- **现象**：Profile 声明按 `ProfileDeclarationSchema` 校验，根对象是 `additionalProperties: false`。按现有写法，`starters` 会写成 `Type.Array(Type.Object({...}, {additionalProperties: false}), {maxItems: 3})`。第三方插件写了 4 条，或者给某条多加一个键（例如模仿旧应用写 `iconColorClass`），这条 Profile 贡献就整条以 `invalid-declaration` 被拒，连会话都开不了，而起因只是一段装饰性的文字。计划没说“至多 3 条”是靠 schema 拒绝，还是由界面截断。

- **如何核实**：读 `points.ts` 的 schema 与 `plugins.md` 输出 15。

## 未发现问题的方面

- **指针拖动认源**：`layout-drag.ts` 的 `fromElement` 用 `closest("[data-panel-tab]")`。把手里面放图标、标题、箭头这些不可交互的元素，指针拖动照样成立。浮动窗里只有一个标签时，按把手拖的是整个窗，这一点也不变。
- **拖完不触发点击**：拖动结束时吞掉同一手势末尾的 click，是在根上用捕获阶段做的（`nb-layout/src/vue/drag-session.ts:303`）。标题区在根里面，拖完不会误开会话列表。
- **键盘拿起**：`keyboard.sourceAt` 要求焦点在 `[data-panel-tab]` 本身，把手仍是那个按钮就成立。拿起用的那一下空格，keydown 与 keyup 都被拦下（`drag-session.ts:133-136`），不会顺带开浮层。
- **Alt 加方向键**：只写标题的头现在本来就没有这个键（它在 `TabStrip` 里），加不加标题区都一样，不变量成立。
- **右键菜单**：只要把手的 `contextmenu` 由工作台绑定（第 5 条的改法），就不受影响。
- **翻译端口**：`TEXT_PORT_KEY` 在应用根上提供（`web/mount.ts:32`），面板头与内容两棵树都拿得到，nb-agent-ui 的组件在面板头里照常翻译。只有子代理数据、`toolActionKey`、注册表拿不到（第 11 条）。
- **新会话会用的 Profile**：没有会话时发送走 `create()`，缺省是 `MAIN_PROFILE`；`profileKey()` 在没有会话时也交回它。计划说“取 `create()` 的缺省”，与实际一致。顶栏的新建另走 `pickProfile`，建好后已经有会话，按决定 5 取会话的 Profile，两条路不冲突。
- **e2e 夹具的可行性**：`agent-subagents.e2e.ts` 用本机假端点按会话分派脚本，已经能一条回复派两个子代理（验收 1）。`models.e2e.ts` 已经能造出角色没绑定的状态（`data-role-unbound`）。计划列的几条 e2e 都能在现有夹具上用真实运行时写出来，“入口个数”的判据要先按第 19 条定清。
- **Profile 声明的兼容**：给 `additionalProperties: false` 的声明加一个可选字段，已有的声明照样通过，不需要迁移。风险只在写错新字段时（第 20 条）。
- **已有用户布局**：标题区不改布局文档的形状，`titleOnlyPanels` 仍按已提交的文档算，不需要迁移布局记录。
