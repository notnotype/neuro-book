## 1. 第一屏刷新的 watch 在每次对话上下文变化时都重取最近对话

- 严重程度：重要；类别：正确性（性能）
- 位置：`packages/neuro-book/src/plugins/agent/web/ConversationHost.vue`，注释“第一屏出现时（切到没有消息的会话、新建、没选会话）重取最近对话”那段 `watch`（约 78 行）
- 现象：`watch(() => [session?.id ?? null, messages.length === 0] as const, ([, empty]) => { if (empty) void props.recent.refresh(); }, {immediate: true})`。getter 每次返回新数组，Vue 用 `hasChanged` 比较引用，所以只要 getter 依赖的东西触发，回调就跑，不看两个元素有没有变。getter 读的是整个 `props.host.ctx.value`，而宿主的 ctx 在每次 `bump()`（revision 加一）后都换新对象。
- 为什么是问题：Spec conversation 输出 41 写“第一屏出现时重新取一次”，计划与 Task README 也写“第一屏出现时才刷新”。实现成了“第一屏显示期间，ctx 每变一次就发一次 `agent.list` 远程调用”。第一屏上会触发 ctx 变化的有：点开场指令（`composer.fill` 会 `bump`）、模型快照变、连接状态变、`notice` 变、子代理树变（后台有运行中的会话时很频繁）。每次都是一次完整的会话索引读取，而且 `refresh` 的 `latest` 令牌会让较早返回的结果作废，列表还可能闪动。
- 如何核实：在 `packages/neuro-book` 下跑 `bun -e`：用 `ref` 做 revision、`computed` 返回新对象、`watch(() => [ctx.value.session?.id ?? null, ctx.value.messages.length === 0] as const, cb, {immediate: true})`，连续改 5 次 revision，回调执行 6 次（1 次 immediate 加 5 次无关变化）。这是 Vue 行为的实验，没有经过 `ConversationHost`，但这个 getter 与 ctx 的形状同实际代码一致。
- 建议改法：让监视的源是值，不是新数组：`watch([() => host.ctx.value.session?.id ?? null, () => host.ctx.value.messages.length === 0], ...)`（数组源逐项比较），或把两项拼成一个字符串 key。同时补一个 DOM 测试：第一屏显示时 bump 一次无关状态，断言 `refresh` 次数不变。

## 2. 第一屏的开场指令按“没有响应式依赖”的 `profileKey()` 取，切到或新建非主创 Profile 的会话后可能一直是主创的指令

- 严重程度：重要；类别：正确性
- 位置：`packages/neuro-book/src/plugins/agent/web/plugin.ts` 的 `welcomeOf`（约 388 到 392 行）与 `draftProfileOf`；`session-host.ts` 的 `profileKey()`（约 1302 行）
- 现象：`welcomeOf(host)` 在 `AgentConversationPosition` 的渲染函数里调用，用 `host.profileKey()` 选 Profile。`profileKey()` 读的是 `current?.transcript.meta()?.profile`：`current` 是普通 `let`，`transcript.meta()` 来自 `createKernelTranscript`（nb-agent-ui，非响应式）。`open()` 先 `current = target; sessionId.value = id`（此时 `meta()` 为 null，`profileKey()` 回落 `MAIN_PROFILE`），快照到了才 `applySnapshot` 填上 meta。渲染函数只读 `host.sessionId`、`profiles`、`recentSessions.sessions` 这几个 ref，没有读 ctx，所以快照到了以后这个渲染函数不会因 meta 变化而重跑。
- 为什么是问题：Spec conversation 输出 41 与 Task 决定 5：“有会话没消息时显示这个会话 Profile 的指令”。新建一个非主创 Profile 的空会话（`pickProfile` 选了别的 Profile）或打开一个空的非主创会话，第一屏写的是主创的指令，除非碰巧有别的响应式依赖触发重渲染。现在能“碰巧”修好的是 `ConversationHost` 为第一屏调的 `recent.refresh()`：列表返回后 `entries` 换新值，`sessions` computed 变，渲染函数重跑；它与快照是两个并发的 RPC，谁先回不确定，所以结果取决于时序。
- 如何核实：从代码推断，未跑。可写一个 `plugin` 级 DOM 测试：宿主新建选了带 `starters` 的非主创 Profile 的会话，快照在 `recent.refresh()` 之后才返回，断言第一屏的指令是该 Profile 的。也可以直接看 `welcomeOf` 的依赖：没有一条经过 `host.ctx`。
- 建议改法：把 Profile 的取法并进 ctx（例如 `ctx.session.profileKey` 或 `welcome` 由 `host.ctx` 的 computed 产出），让 `welcome` 与 `draftProfile` 成为 ctx 的一部分或 `host` 上的 computed（依赖 `revision`），不要在渲染函数里读非响应式状态。更少的部件：`SessionHost.profileKey()` 内部先 `void revision.value` 再读，这样任何读它的 computed 或渲染函数都跟着快照更新。

## 3. 子代理浮层开着时，取不到的收口结果会随每次树更新重发请求，调用失败的诊断也同样刷屏

- 严重程度：重要；类别：正确性（性能）
- 位置：`packages/neuro-book/src/plugins/agent/web/components/SubagentsEntry.vue` 的 `watch([open, rows], ...)`（约 41 行）与 `subagents-panel.ts` 的 `createRunResults.load`
- 现象：浮层开着时，`rows` 每次重算（后代在跑时 `tools`、`step`、`now` 相关字段很频繁）都对每个已收口的行调 `results.load`。`load` 只防“正在取”和“已取到”；`runResult` 交回 `null`（`remote.runResult` 失败或没有结果）时不记，`finally` 里又清了 `loading`，下一次 `rows` 变化就再取一次；`fetch()` 抛错时还每次 `report("run-result-failed", ...)`。
- 为什么是问题：Spec 输出 43：“结果在浮层打开时才取，同一次运行只取一次；取到之前、取不到时只写状态”。实现注释写“取不到的不记，下次打开浮层再取”，实际是“浮层开着期间每次行变化都再取”。一个持续失败的行（例如后端读不到那次运行）加一个在跑的兄弟行，就是每秒级的失败请求与诊断。
- 如何核实：`createRunResults` 的现有测试只证明“取完后再调 `load` 会再取”（用 `waitUntil` 里重复调 `load`），没有证明“同一次打开最多取一次”。在 `SubagentsEntry.dom.test.ts` 里让假 `runResult` 恒返回 null，浮层开着时推进两次 `tree` 更新，断言调用次数；按现在的实现是每次更新加一次。
- 建议改法：把“这次打开已经试过”记在 `watch` 一侧（打开时清一个 `tried` 集合，试过的不再 `load`），或让 `createRunResults` 把失败也记成“本次浮层内已试”，`open` 变 false 时清。更少的部件：只在 `open` 由 false 变 true 时取一次（`watch(open)`），开着期间新出现的已收口行单独由一个“看见新 id 才取”的集合处理。

## 4. 子代理浮层为所有已收口的行取运行结果，其中停止、中断的从不显示

- 严重程度：建议；类别：代码质量（性能）
- 位置：`SubagentsEntry.vue` 的 `watch([open, rows], ...)`；`detail()` 只在 `done`、`failed` 用结果
- 现象：`for (const row of list) { if (row.ended !== null) results.load(...) }`，`aborted`、`interrupted` 的行也有 `ended`，会被取，但 `detail()` 对它们返回空串。
- 为什么是问题：后代很多时每次打开浮层白发若干次远程调用，还把永不显示的结果放进缓存。
- 建议改法：只对 `row.state === "done" || row.state === "failed"` 取。

## 6. 提示卡的按钮不带 `layer`：设置窗口上次停在“本作品”标签时，落在“只在用户设置里”的说明页，`focus` 也丢了

- 严重程度：重要；类别：正确性
- 位置：`packages/neuro-book/src/plugins/agent/web/plugin.ts` 的 `openSettings`（约 340 行，`commands.execute(OPEN_SETTINGS_COMMAND, target)`）与 `model-notice.ts` 的各个 `target`（只有 `section`、`focus`）；`settings/web/settings-window.ts` 的 `perform` 的 `open` 分支与 `shownPage`

## 8. “出错未看”拿浏览器时钟与服务端的 `endedAt` 比较

- 严重程度：建议；类别：不变量
- 位置：`packages/neuro-book/src/plugins/agent/web/subagents-panel.ts` 的 `createSeenErrors`（`unseen` 里 `row.ended.endedAt > seenUntil(row.id)`）；`plugin.ts` 的 `createSeenErrors(clock.now())` 与 `markSession(id, clock.now())`
- 现象：基线、切会话的时刻来自浏览器的 `clock.now()`，被比较的 `ended.endedAt` 来自服务端日志。注释写“两者在同一台机器上”，没有任何代码保证；NeuroBook 的服务端与浏览器分开时（开发者自己远程用就是），时钟差几秒到几分钟都有。
- 为什么是问题：浏览器时钟比服务端快 Δ 时，激活后 Δ 以内出的错被当成已看过，红点不亮；慢 Δ 时，激活前 Δ 以内收口的旧错一开始就亮，又因为 `markSession` 用的也是浏览器时刻，切到那个会话也盖不住，只能打开浮层才灭。计划原本写“按 `会话:运行` 记”，实现改成时刻是为“少存一份集合”，代价是引入了跨时钟比较。
- 如何核实：纯函数层可以直接验：`createSeenErrors(1000)`，`endedAt` 取 1000 加一个偏移，看 `unseen` 的结果随偏移翻转；现有测试里的 `ACTIVATED ± n` 隐含了两个时钟相同。
- 建议改法：改回按运行 id 记：记“已看过的出错运行 id”集合（`markRows` 加 `row.ended.runId`，`markSession` 需要时记那个会话当前最后一次出错的 runId），基线用“插件第一次读到某个后代时它已有的出错”处理（第一次见到某个会话行时若已是出错就记为看过）。这样没有时钟比较。若坚持时刻，至少把基线与切会话的时刻改取服务端给的时间（例如 `tree` 帧里的服务端时间戳），并在注释里写明依据。

## 9. 子代理行的停止按钮只在悬停与键盘聚焦时出现，触屏上够不到

- 严重程度：建议；类别：UI

## 11. 换代时旧的 `ViewHead` 的 `slots` 不清空，仍指着已拆掉的元素

- 严重程度：建议；类别：不变量
- 位置：`packages/neuro-book/src/plugins/workbench/web/views/view-instances.ts` 的 `dropContext` / `setContext`；`views/view-head.ts`
- 现象：`dropContext` 只从表里删掉控制，不对旧控制 `setSlots(null)`；视图手里的旧 `ViewHead.slots` 保留最后一次的元素，直到组件卸载。`ViewHead` 的注释写“旧的那份不再收到位置与按下，视图手里的旧引用自然作废”，“作废”其实只是“不再更新”，不是“变 null”。
- 为什么是问题：现在安全，是因为 `WorkbenchViewFrame` 的 `ErrorBoundary :key="generation"` 在换代的同一轮就卸载旧组件。但这个安全来自外层的 key，不是来自标题区本身的合同；以后任何长寿命的订阅者（视图外的 `watch`、`onTitlePress` 之外的异步任务）拿着旧 `slots` 往里 `Teleport`，会往已不在文档里的元素里写。这正是计划风险里的“位置是元素但已不在文档里”。
- 建议改法：`dropContext` 与换代处理里先 `heads.get(viewId)?.setSlots(null)`（一行），旧 `ViewHead` 随即变成“没有位置”，与合同的文字一致；`view-head.ts` 注释改为“旧的那份的位置被清成 null”。

## 13. 子会话的头在祖先读到之前（或读失败时）画“新建”，不是返回

- 严重程度：建议；类别：正确性
- 位置：`packages/nb-agent-ui/src/vue/head/AgentConversationHead.vue`（`parent` 与左列的 `v-if / v-else-if`）；`session-host.ts` 的 `open()`（`ancestors: []` 起步，`remote.ancestors` 与快照并行取）、会话上下文里 `path` 只在祖先非空时给
- 现象：打开子会话时 `target.ancestors` 先是 `[]`，ctx 里没有 `path`，`parent === null`，左列画“新建”按钮；祖先一到才换成返回。`remote.ancestors` 失败时（只写 `conversation-ancestors-failed` 诊断）一直是“新建”。
- 为什么是问题：Spec 输出 35：子会话的头左边是返回。短暂画成“新建”时点下去会在子会话里新建一个顶层会话；读不到祖先时没有任何返回路径（旧的面包屑同样依赖 `path`，但旧版没有把“新建”放在同一位置）。
- 建议改法：祖先还没读到时（`target.ancestors` 未取到）左列不画任何按钮；读失败时按“未知祖先”画一个返回到会话列表或不画，不要画新建。需要宿主在 `path` 之外给一个“还没读到”的标记（例如 `path` 为 `undefined` 与 `[]` 区分：顶层会话给 `[]`，没读到不给）。

## 15. `nbook.settings.open` 只给 `focus`、不给 `section` 时，等着的值可能落到不显示的页面上

- 严重程度：建议；类别：正确性
- 位置：`packages/neuro-book/src/plugins/settings/web/settings-window.ts` 的 `perform` 的 `open` 分支（`section: target.section ?? section.value`）与 `openWindow` 里“不离开这一页”的分支
- 现象：窗口开着、正在搜索（`query !== ""`，显示搜索结果，当前分区的页面没挂）时，`openWindow({focus: "x"})`（没给 `section`）会把 `focus` 记在 `section.value` 那一页上；那一页此刻没显示，直到用户从搜索结果点进它才取到，而且是一个与这次命令无关的时刻。命令描述写“`focus` 交给那一页，由页面解释”，没写必须带 `section`。
- 建议改法：命令参数加约束：给了 `focus` 必须给 `section`（`invalid-args`），免得“当前分区”的含义随窗口状态漂移；现有调用方都带 `section`。

## 17. `SubagentsEntry` 的浮层状态在“没有后代”时随组件一起丢，重新出现后会自动重开

- 严重程度：建议；类别：正确性

- 现象：`open` 是组件自己的 model，不随 `v-if` 卸载 `Popover` 而重置。浮层开着时若 `rows` 变成 0（切到没有后代的会话时 `store.data` 先换，浮层的关闭靠 `select` 里的 `open.value = false`；从别处切会话或会话被删则没有人关），`Popover` 被拆掉但 `open` 仍为 true；之后 `rows` 再不为空（切回有后代的会话），浮层自己弹开。

- 建议改法：`watch(() => rows.value.length, (n) => { if (n === 0) open.value = false; })`。

## 18. 标题按整行居中的做法让两侧各预留“较宽一侧”的宽度，默认 400px 的右栏里标题只剩几个字

- 严重程度：建议；类别：UI
- 位置：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchPanelHead.vue`：`sideWidth`（两列取较大值）与 `.workbench-panel-head--view` 的 `grid-template-columns: minmax(var(--view-head-side), 1fr) minmax(0, auto) minmax(var(--view-head-side), 1fr)`
- 现象：右列（子代理入口、更多、框架按钮）比左列（一个 24px 的按钮）宽得多，左列被撑到同样的宽度，只为让标题居中。按代码估算（按钮 24px、间距 4px、右栏默认宽 `SHELL_AUXILIARYBAR_DEFAULT_WIDTH = 400`）：有子代理入口时右列约 124px，标题按钮可用宽约 `400 − 16 − 2×124 − 8 = 128px`，扣掉按钮自身的图标、箭头与内边距约 62px，标题文字只剩约 66px（四五个汉字）；右栏上再有一个框架按钮（分节的收起）或固定的顶栏动作时更少。没有量，是从样式与默认尺寸算的。
- 为什么是问题：标题写的是会话名，窄到只剩几个字时用户分辨不出是哪个会话；两侧留白里左边那一侧是空的。Spec 与计划写的是“标题按整行居中，两侧放不下时标题让位”，没有要求在窄栏里也牺牲标题到这个程度。
- 如何核实：`bun run dev` 之外不便跑；Lab 的“标题区”场景（`WorkbenchSurfaceFixture`，场景名 `view-head`）里把右栏的宽度拉到 400 与 390，量标题按钮的 `getBoundingClientRect().width`，再给对话视图的真实头加上子代理入口看。作者可在 `lab-workbench-surface.e2e.ts` 里加一条宽度断言（例如标题按钮至少 120px）。
- 建议改法：居中只在放得下时保证：标题列放不下一个最小宽度（例如 120px）时，改成 `auto minmax(0, 1fr) auto`，标题靠左占满剩余宽度；放得下时才用对称的三列。用容器查询（`@container`）判断即可，不需要再多一个测量。
