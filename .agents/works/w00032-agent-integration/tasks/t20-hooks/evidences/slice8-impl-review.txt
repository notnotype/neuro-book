### 1. 阻断 / 正确性：不合作的压缩方法或 restore 能永久卡住中止和关闭

### 3. 重要 / 正确性：结果校验会抛异常或接纳非数值 token，绕过“结果不合格换下一个”

### 12. 建议 / 安全与性能：每次请求边界为估算重新遍历并分配整条路径

- **位置**：`packages/nb-harness/src/kernel/compaction/compact.ts:44`、`:47`；`dispatch/core.ts:142`；`run/loop.ts:191`。
- **现象**：通常最近的 assistant 就在叶子附近，但 estimateContext 先用 pathTo 从叶子追到根、建立完整数组并 reverse，然后才从末尾找基数。每个普通模型请求边界都做，甚至 Profile 的 compaction 为 false 时仍先估算才进 compact 判 disabled。
- **为什么是问题**：路径越长，单次固定边界成本与临时分配越大；已压缩掉的历史仍在日志路径里，所以压缩不能缩短这项开销。这是可省的扫描，不以整次请求超预算作为成立前提。
- **如何核实**：worktree 根运行 `NODE_ENV=production bun /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00032-agent-integration/tasks/t20-hooks/reports/slice8-impl-review/lab/performance.ts`。先经真实 openSession + send 验证 **20,000** 条合成事件、**1,818** 轮、每答 **1,500** 字的路径，再在同一日志上拆测：estimateContext **1,000 次平均 1.587 ms/次**；当前 path **14,630** 节点，仅返回数组的引用空间就至少 **117,040 bytes/次**（未含数组扩容），1,000 次至少分配 **117 MB**。compactionCuts 单次 **21.108 ms**。真实入口 open **160.099 ms**，首个请求 **100.093 ms**，之后 11 次 **33.707–51.850 ms**；这些整次数字没有做父提交同负载对照，**不据此声称本片造成预算回归**。
- **建议改法**：从叶子沿 parent 逆走，累计新增 conv，碰到最近 assistant/compaction 即停，直接返回基数加累计；不构造全路径数组。compaction 为 false 或窗口未知且无手动请求时，先跳过估算。多步切点的 tokensKept 也用一次后缀累加，避免每步 slice/reduce 的二次方计算。
