**建议改法**：为 `abort` 设计与非队列中止兼容的幂等记录：在单写者里为本次中止建立受理/结果凭据，或按 `commandId` 保存第一次结果并让重试只返回它；保留“触发信号不等队列”的即时性，但不得让同一指令的重试重新解释当前运行状态。
### 重要｜只读合同：未知 Profile 的会话仍能用 `resolve` 改变对话

**位置**：`packages/nb-harness/src/kernel/session/session.ts:199-206`、`packages/nb-harness/src/kernel/run/interaction.ts:101-161`

**现象**：`openSession()` 找不到会话头的 Profile 时把 `state.readOnly` 设为 `unknown-profile`；但 `buildApi()` 对 `resolve` 只套 `closedGuard`，`resolveCommand()` 没有 `readOnly` 检查。未知 Profile 会话里已有待处理异步提问时，用户仍可写 `interactionResolved` 和 `commandAccepted`。

**为什么是问题**：`session.md` 输出 169 明确规定未知 Profile 会话“能查询，不受理会改变对话的指令”。`resolve` 会结算路径上的互动并可能把回答写入输入缓冲区，正是改变对话的指令；当前实现让只读快照与可写行为矛盾，也让未知 Profile 下无法安全归约的扩展状态被继续推进。

**如何核实**：

```text
bun run /home/notnotype/CodeRepository/neuro-book/.local/agent/works/w00032-agent-integration/tasks/t20-hooks/reports/deep-review-omp/lab/readonly-resolve.ts
```

真实 `openSession`、内存存储和合成待处理提问输出：`before {code: "unknown-profile"}`，`resolve {ok: true, seq: 5}`，日志新增 `interactionResolved` 与 `commandAccepted`，`after` 仍显示未知 Profile。

**建议改法**：把 `resolve` 视为改变对话的指令，在 `resolveCommand` 或统一的写指令门禁中拒绝 `readOnly !== null`；若产品确实要允许回答未知 Profile 的异步问题，应单独定义只写内核事件的恢复命令并更新 Spec，不要让普通 `resolve` 绕过只读合同。
