### 1. 写入批仍没有可判定的提交状态
严重程度：阻断；类别：正确性 / 不变量 / 持久化。
位置：计划第 2 节“写入批”、第 3.2 节“打开顺序／写失败”、第 3.6 节“commandAccepted”；第 2 片。

现象：第二版把合同写成“**一批一次 `write` 后 `fsync`**”，失败后句柄进入 `log-broken`，重开时“截到最后一个完整批的末尾”。但仍只有 `batch: {id, n, of}`，没有提交标记、批次状态或重开时按 `batch.id` 判定提交的规则。

为什么是问题：`fsync` 在完整字节已经写入但同步失败时，调用方仍得到失败；重开按“行和 `of` 完整”会把这批当成事实，无法区分“已提交但响应丢失”和“未提交”。反过来，恢复后重试的 mount／反应输出没有 `commandId` 幂等屏障，不能像命令那样去重。于是相同日志状态在故障重试与重开后可能产生重复事实，或者一次失败的写入在重开后被错误接受；“写入、归约、推帧”顺序只解决了内存状态，没解决落盘提交语义。

如何核实：给第 2 片的文件句柄端口注入“完整写出批字节后 `fsync` 抛错”，关闭并重开；对比重开是否接受该批，再重发同一个非命令来源的批。当前计划没有一个可判定的预期结果，也没有对应的提交标记或 batch-id 幂等验收。

建议改法：优先把批写成可验证的提交协议：临时批文件写完并同步后原子落位，或日志写入提交标记并在重开时只接受有标记的批；`append` 的不确定失败统一标记句柄损坏，重开按批 id 恢复且不重复派发。若坚持“完整行即提交”，必须明确 `fsync` 失败后的语义并为所有可重试写入口提供批 id 幂等，不要只靠 `commandAccepted`。
### 2. `ModelRequest` 仍没有冻结 OMP 所需的 canonical 内容合同
严重程度：阻断；类别：接口 / 正确性 / OMP 兼容。
位置：计划第 3.1 节“请求与回复、工具”、第 3.9 节“OMP 适配器”、第 2 片的适配器；对应提案第五稿待定项 11。

现象：第二版把文字改成“请求带完整工具声明”“内容块含思考签名与图片”，但没有给出这些字段的实际类型。依据的 v5 原型仍是 `Block {text, origin, kind?: "text" | "thinking" | "image"}`、`ModelRequest.tools: ToolInfo[]`；`image` 没有媒体 URI、mime、数据或 provider 载荷，思考块没有 `redacted`／provider 元数据，`ModelRequest` 也没有 `tool_choice`、附件或适配器选项的边界。计划只说第 1 片“改成定稿类型”，没有差异表中可实现的字段和丢失信息时的失败合同。

为什么是问题：第 2 片必须同时实现 `streamSimple` 的请求转换、事件流终态、图片／思考签名保存、工具 schema 传输与重放；照当前文字实现，适配器只能自定一种图片表示和工具选择语义，或把 OMP 的信息丢掉。第 5 片才接工具拦截与第 10 片才做真实使用方时再改这些公共类型，会返工日志事件、哈希、预览和请求校验，不能把 O6 仅当成“把 `ToolInfo` 换成 `ToolDeclaration`”解决。

如何核实：对照 v5 `api.ts` 的 `Block`、`ModelRequest` 与 `ModelResponse` 定义，再逐项列 OMP `streamSimple` 的 image／thinking／toolcall／error／终态字段；当前计划没有一项能映射到 image payload、tool choice、partial/error 或 provider metadata 的字段，也没有对应的编译或事件合同测试。

建议改法：在第 1 片冻结独立的 canonical `ContentBlock`、工具声明、tool choice、provider 选项与响应终态；明确 blob／图片引用、思考签名和 partial/error 的编码，以及不支持时 fail-closed 的错误码。适配器只做 canonical 与 OMP 的一次转换，第 2 片用目标 18.14.0 的公开类型和事件流写逐字段合同测试，再允许后续切片使用。
### 3. `SessionEnv` 不能完成重开时的 Profile 装配，也没有工具实例生命周期
严重程度：阻断；类别：接口 / 恢复 / 资源释放。
位置：计划第 3.2 节会话头、第 3.3 节 Profile 哈希、第 3.10 节 `SessionEnv` 与会话入口；第 2、9 片。

现象：计划的 `openSession(env, id)` 只拿会话 id，`SessionEnv` 列出 `store`、`models`、`tools`、`resources`、`sessions`、`clock`、`approve`、`plugin`，没有 Profile 注册表或 `resolveProfile(profileKey)`。会话头只有 `profile` 标识；计划也没有说明 host 如何把该标识解析成当前 Profile、装配扩展并计算当前 hash。与此同时，`tools: () => {declarations, implementation(id)}` 写成“每个边界取一次”，而 t04 已定工具实现由 `create(会话上下文)` 每会话创建一次、可带 `dispose`；计划的接口没有 `create`、句柄保存或释放返回值，`closeSession` 却声称会“释放工具句柄”。

为什么是问题：第 2 片的“重开接着聊”和第 3.3 的 Profile hash 比对在没有 Profile 解析入口时无法落地；实现者只能把 Profile 偷塞进闭包、从宿主全局取，或改动 `openSession` 公开签名。按边界重新取 implementation 还会丢失 t04 要求的会话级闭包状态，插件撤回与关闭时也没有可调用的资源释放合同，直接导致 t04 的声明快照、`plugin-unavailable` 和 `dispose` 语义返工。

如何核实：只按计划签名构造一个新进程的 `SessionEnv`，读取 header.profile 后无法得到 Profile 对象；再按 t04 README 的 `create(会话上下文)`／`dispose` 对照第 3.10 的 `tools` 与 `closeSession` 类型，二者没有连接点。第 2 片验收要求重开，当前接口没有可执行的装配路径。

建议改法：给 `SessionEnv` 一个显式的 Profile 解析／装配入口（并规定快照中的 key、版本与缺失错误），或把解析后的 Profile 作为带合同的 `openSession` 参数；把工具改成每会话 `create` 返回声明与句柄、在会话 close/revoke 时统一 dispose，边界只刷新声明快照，不重复创建实现。不要用 `tools()` 闭包和宿主隐式全局补接口。
### 4. t20 的“全部放行”缺省实现与 t06 已确认的默认审批相反
严重程度：重要；类别：安全 / 跨 Task 合同。
位置：计划第 3.1 节审批钩子、第 3.6 节审批、第 5 片；t06 README“改判”第 52–56 行。

现象：计划写“t20 交付‘全部放行’的缺省实现”，并要求测试规则拒绝、规则放行、`ask` 和会话批准记忆；t06 的最新决定却是“默认不放行写入，写入要审批”，且规则命中拒绝／放行／询问后才跳过模式，yolo 也不能绕过拒绝。计划把 t06 的规则表留在本 Task 之外，却没有说明这个“缺省实现”只属于测试宿主，还是会成为 `SessionEnv.approve` 缺省行为。

为什么是问题：照字面完成 t20 后，未注入审批实现的生产会话会让写入工具直接执行，违反 t06 的安全默认；只在 t06 后替换回调又会改变第 5 片已经冻结的审批链签名和测试语义。更严重的是 `approve` 的 `info` 只有 effect、核心设置和批准记忆，计划没有一个承载“按工具／参数的规则先于模式”的接口，后续 t06 只能在钩子外再包一层，容易绕过“改参后对 effective call 判定”的不变量。

如何核实：对照计划第 3.6 节“审批是全部拦截之后的调用、之后不再改参数”和 t06 的规则顺序；用未提供 `approve` 的 `SessionEnv` 调一个写工具，计划没有规定应得到 `ask`、`deny` 还是 `allow`，而三者的生产结果不同。

建议改法：把“全部放行”限定为 `createTestSession` 的显式测试策略，不作为产品缺省；产品 `approve` 必须是必填的判定端口，或安全缺省为按 t06 规则／模式处理。第 1 片先冻结 `effectiveCall`、规则评估结果和 `approve` 的输入／输出，t06 只提供策略数据，不再在 t20 之后改链形状。
### 5. 工具声明删掉 `name`，回归 t04 已定的显式服务商名称覆盖
严重程度：重要；类别：接口 / 跨 Task 合同。

现象：计划以 master `ToolDeclaration` 为底的字段清单里省略 `name`，并明确“`name` 字段去掉，交给服务商的名字由适配器按 t04 换算”；但 t04 已定内部 id 与日志／审批使用 id，服务商名默认由 `.` 换 `__`，同时允许显式覆盖服务商名称，且覆盖值也要按服务商规范校验。计划只保留自动换算，没给覆盖字段或等价形状。

建议改法：保留 canonical 声明中的 provider-facing `name`（或命名为 `providerName`，缺省才按 t04 换算）；日志、`ToolCall`、Profile 与审批继续只用 id，适配器只在缺省时生成并校验 wire name。
### 6. 输入拦截移到受理时后，拒绝与缓冲区事实没有合同
严重程度：重要；类别：正确性 / 指令幂等 / 跨 Task 合同。
位置：计划第 1 节决定 6、第 3.5 节队列、第 3.6 节指令与拦截链、第 3.7 节等用户；第 5、6、7 片。

现象：计划要求输入链在“指令受理时”运行，`inputQueued`、`inputEdited` 保存拦截后的文字；但事件清单只列这两个事件，没有受理时拒绝的事件字段、命令失败码或 `inputQueued` 的 rejected 形状。与此同时，计划仍保留“被拒绝的写 `inputConsumed{rejected: ...}`”的旧规则，并写“内核的 `send` 在 waiting 时照常入队”。提案第五稿仍把输入拦截描述为“取走时”，第 2、3 节的正文和位置表也没有全部改成受理时。

为什么是问题：受理时被拒绝的输入到底是返回失败且不写、写一条不可取走的 `inputQueued`、还是写入后再在取走时拒绝，三种结果分别影响 `commandAccepted`、缓冲区、重放和 UI；当前没有唯一答案。特别是 t07 要求审批等待时输入框文字转成拒绝附言、提问时转成回答，而计划的普通 `send` 仍可入队，绕过界面转换就会违反等待状态合同。异步拦截若在受理前挂起，`abort` 的“立即受理”也没有定义与它的竞态。

如何核实：构造三个场景：受理时 input 拦截返回 reject、等待 approval 时直接调用 `send`、拦截运行中调用 `abort`。按计划无法确定日志应有的事件、返回的 `seq`／错误码和后续是否还能 `start`；再对照 t07 决定 4 与提案第 3 节的取走规则即可复现合同冲突。

建议改法：先冻结受理时输入的结果类型：成功写入已改写文本，拒绝写带 `commandId`／拒绝码的 session 事实并明确命令结果，且 `edit` 沿用同一规则；等待状态下由内核而非 UI 把 `send` 分派为 `resolve` 或明确拒绝普通 send。同步修正提案第 2、3、9 节和 `commandErrors`，并规定 input chain 的取消、超时与 commandAccepted 批边界。
### 7. 动态 `yield` 没有进入会话创建、工具快照与幂等合同
严重程度：重要；类别：接口 / 不变量 / t14 对接。
位置：计划第 3.6 节收尾工具、第 3.10 节会话入口、第 5 片；t14 README 决定 2、20、25、33。

现象：计划说 `yield` 按“Profile 声明或 `agent_spawn` 的 `outputSchema`”动态生成收尾工具，但 `createSession(env, {profile, initial, header})`、会话头和 `SessionEnv` 都没有 `outputSchema`／结果模式字段；`tools()` 也只返回声明与 implementation，没有说明生成工具的 id、工具 schema 如何冻结进快照、何时写 `toolsAnnounced`，或 Profile 已声明结果 schema 时如何禁止父调用覆盖。t14 明确 `agent_spawn` 可传 `outputSchema`，且结果模式属于子会话 Profile，父 Agent 只能在 Profile 未声明时提供。

为什么是问题：照字面实现，子会话拿不到一次 `agent_spawn` 调用的 schema，无法为下一次模型请求生成正确的 `yield` 参数；临时把 schema 塞进 Profile 设置会改变 Profile hash 与工具声明，改动路径、恢复和 `toolsAnnounced` 语义。若把它作为每次请求临时工具，又会破坏 t04 的会话声明快照和模型看到的工具集，重发相同父工具调用还可能生成不同的收尾 schema。

如何核实：从 t14 的 `agent_spawn(... outputSchema?)` 调用追到计划的 `createSession` 签名；没有任何参数能携带它。再按第 3.6 节边界顺序检查，计划没有生成／记录动态工具的步骤。

建议改法：把结果模式放进带版本的会话创建／调用方元数据，并规定优先级：Profile 声明的 schema 锁定，只有未声明时才接受 `outputSchema`。生成的 `yield` 声明、schema hash 和工具版本随会话头或首个 `toolsAnnounced` 固定，恢复时按快照校验；命令幂等重放必须复用同一 schema。
### 8. 压缩公共接口没有落实 t11 的统一结果与失败回退
严重程度：重要；类别：接口 / 正确性 / 跨 Task 合同。
位置：计划第 3.8 节方法接口与公共流程、第 5 片和第 8 片；t11 README 决定 2、4、8。

现象：计划只给出 `CompactionJob{method, request, require, signal, model}`，并说 t20 带一个经 `ctx.model` 得摘要的测试方法；没有在定稿类型或计划中给出 `CompactionResult` 的统一形状、方法失败如何换下一个、`replacement`／`details`／`omitted`／放回批怎样由方法交回。t11 已定压缩方法为 `shake → inplace` 或 `shake → summary` 两套顺序，结果统一含 `method`、`firstKeptEntryId`、`replacement`、`tokensBefore`、`tokensAfter`、`details`，不合格按失败换下一个；提案第五稿还加了 `omitted`、`restoreBatch`。

为什么是问题：切点、`core.compaction` 和恢复内容都由内核写，但当前 Job 没有承载恢复批与 token 结果，失败也没有可判定的“换方法”信号。第 8 片即使能测一次摘要成功，也无法保证 t11 的方法顺序、溢出与手动压缩、失败 fallback 和公共恢复流程；等 t11 实现再补会改第 1 片 API、日志事件和第 8 片测试，不是“方法实现留给 t11”这么简单。

如何核实：把一个失败的 `inplace` 和可成功的 `summary` 注入计划第 8 片流程，当前 `CompactionJob` 没有 fallback／结果协议可让测试判定第二个方法应被调用；再对照 t11 决定 8，计划的 `CompactionResult` 字段不完整且没有验收项。

建议改法：第 1 片冻结 `CompactionResult` 与失败分类，内核持有按 Profile 配置的两套方法序列；第 8 片先测失败换下一个、统一结果、`restoreBatch` 与压缩同批，中止不写事件；t11 后续只实现具体 `shake`／`inplace`／`summary`，不再改内核边界。
### 9. Profile 哈希只被计算，没有成为回放与提交的版本屏障
严重程度：重要；类别：正确性 / 回放 / 缓存。
位置：计划第 3.3 节 Profile 哈希、第 3.4 节 `commit` 缓存、第 3.10 节 `openSession`；第 3、4、9、11 片。

现象：计划定义 `hash(id, version, 代码包哈希或包版本, 扩展 id／版本, 工具声明)`，打开时“不同比就写 `profileChanged{reason: "code-updated"}`”，同时规定 `commit` 结果按节点缓存、重开或回退用同一纯函数重算。但 `profileChanged` 的字段没有旧／新 hash，提交缓存没有 `profileHash` 绑定，扩展实现／reducer 的版本也只写 id 与 version；打开顺序还是先归约，再装配比对并恢复。

为什么是问题：Profile 代码、模板、工具 schema 或 reducer 变化时，重开会先用新实现归约旧日志；之后只写一条没有哈希值的原因事件，无法证明使用过哪一版。缓存若按节点复用，可能把旧 Profile 的消息交给新 Profile；若全部重算，又会改变过去已提交轮的模型历史，违反提案第五稿“提交绑定 Profile 内容哈希”与 t04 的配置变化审计。插件自身代码变化而只改实现不改显式 version 时，当前清单同样没有 per-extension implementation version 可比对。

如何核实：构造同 id／版本、不同 `commit` 或 reducer 实现的两个 Profile，写一轮后重开；按计划没有持久化 hash 可供比较，也没有规定旧提交用旧 `commit`、缓存失效范围或拒绝／迁移。读取计划第 3.4 节即可看到缓存键没有 Profile 版本字段。

建议改法：把规范化 manifest、每个扩展实现版本和工具声明 hash 写入 `profileChanged`，并让每个提交节点／缓存键带 `profileHash`；打开先确定当前 Profile 与版本，再按“同 hash 重放、不同 hash 迁移或拒绝”的合同处理，明确是否只影响后续请求。不要用一个无字段的 `code-updated` 诊断替代版本屏障。
### 10. 异步提问在中止、停服与重开之间没有一致的结算规则
严重程度：重要；类别：正确性 / 恢复 / 交互状态。
位置：计划第 3.6 节中止与恢复、第 3.7 节等用户、第 3.10 节 `closeSession` 与进程收尾；第 7、9 片；关联 t07、t14。

现象：计划明确“异步提问不随运行中止结算，只在分支被回退或工具卸载时结算”，但恢复又写“等回答的提问 `interrupted`”，停服走同一条收口；`closeSession` 只说中止当前运行、等收口、关闭日志，没有说如何结算仍挂起的异步 `interactionRequested`。t14 又规定异步提问的回答经 `resolve`，可在运行结束后作为新输入进入缓冲区。

为什么是问题：同一条未回答的异步问题，在普通 `abort` 后可以继续存在，在优雅停服后是否被结算、进程崩溃重开后是否还能 `resolve`，按当前文字有三种互相冲突的结果。若重开把它标为 `interrupted`，父 Agent 可能收到一次中断结果后又能提交同一个 `resolve`；若保留它，计划的“等待中的事项一律收口”又不成立；若只结算同步 waiting，界面无法区分两类待处理事项。

如何核实：建立 `async: true` 的问题，让运行自然结束后调用 `closeSession`，再从同一日志 `openSession` 并尝试 `resolve`；计划没有规定应得到 `already-answered`、`unknown-interaction` 还是成功，也没有唯一的 `interactionResolved` 事件。

建议改法：在恢复矩阵中单列同步 waiting 与异步 pending：分别定义 `abort`、优雅 close、崩溃重开、rewind、插件卸载的结算事件和 `resolve` 结果；若开发者决定停服一律 interrupted，就让 close 走同一收口批并禁止后续回答，否则明确异步问题跨重启保留且不属于“等待中的运行”。
### 11. 第 6 片仍把第 7 片才提供的 `resolve`／waiting 当成已交付能力
严重程度：重要；类别：切片顺序 / 测试 / 交付。
位置：计划第 5 节第 5–8 片的内容与出口条件、第 3.6–3.7 节；尤其第 6、7 片。

现象：第 5 片先接审批钩子，且验收要求 `ask`；第 6 片标题写“全部指令”、列出 `resolve` 与恢复，并要求把 spike 场景搬成测试；但 `RunStatus.waiting`、`interactionRequested`／`interactionResolved`、同批多事项、并发应答、`resolve` 的发出者和结算全部属于第 7 片。第 7 片的出口又要求重启中断与 `interrupted-before-approval`，即它需要第 6 片已经有恢复骨架；计划没有定义第 6 片的占位合同或允许提前实现的边界。

为什么是问题：按“每片单独提交、只做本片”照字面实现，第 6 片只能伪造 pending／resolve 或先实现第 7 片，随后第 7 片会重写命令返回值、队列和恢复状态；第 5 片的 `ask` 也没有真实的事件通道。这样切片看似已把第一轮依赖前移，实际仍把同一状态机拆在两个相互依赖的提交里，测试会出现临时 harness 或重复实现。

如何核实：按表格顺序检查第 6 片出口中 `resolve`、恢复与审批测试所需的类型和状态，逐一对照第 7 片“3.7 全部”的内容；它们在第 6 片之前都没有拥有者。读取 v5 `host.ts` 也可见 `RunStatus` 原型还没有 waiting 变体。

建议改法：把最小 interaction 状态、`resolve` 指令及恢复结算前置到第 6 片，或把第 6 片收窄为 command 记录／缓冲区／中止，明确不实现 `ask` 与 `resolve`，将第 7 片独立扩展该已冻结接口；不要让第 5、6 片写临时等待通道。
### 12. 大块内容的 blob 引用没有覆盖写入、校验与 fork
严重程度：重要；类别：持久化 / 兼容 / 性能。
位置：计划第 2 节“大块内容”、第 3.2 节会话目录与 `LogStore.fork`、第 3.4 节状态归约；第 2、6、8 片。

现象：计划规定超过 16 KB 的字符串写进会话目录 `blobs/<sha256>`，事件只记 `{$blob, size}`，打开时全量读回；但没有定义字符串到 blob 引用的递归编码边界、写 blob 与写事件批的先后／同步关系、哈希校验失败码，也没有规定 `fork` 复制当前路径时如何携带这些 session-local blob。`fork` 只写成“复制当前路径、头记来源”。

为什么是问题：如果日志批先落盘、blob 后落盘，进程崩溃会留下可解析但缺 blob 的日志；如果 blob 先落盘，批失败会留下未被引用的文件，重试和清理也没有合同。fork 后新目录中的 `session.jsonl` 仍引用旧会话相对路径，除非复制全部被引用 blob 或把 blob 存到共享内容寻址根；两种策略会影响重放、删会话和哈希。对任意扩展 `details`、工具 raw、思考／图片块是否递归替换也未定，第一版的“全量读回”不能替代缺失引用的错误语义。

如何核实：构造一个包含大于 16 KB 工具结果的会话，在写 blob 后、写日志前和写日志后、blob 未完成时分别中断，再执行 `open` 与 `fork`；计划没有可判定的恢复结果，且没有一个验收断言新会话的 blob 可验证读取。

建议改法：冻结内部 `BlobRef` 编码与所有可溢出字段的递归规则；批提交前写并同步所有 blob，日志批提交后再更新索引，重开校验 hash／size，缺失或不匹配报结构化 `log-corrupt`。`fork` 明确复制当前路径引用的 blob，或把 blob 根提升为共享不可变存储并写入引用范围；清理只删无引用 blob，不能让 fork 后的日志依赖旧会话目录。
### 13. 第 10 片“验收门”没有定义失败后的门禁动作
严重程度：建议；类别：验收 / 计划可执行性。
位置：计划第 1 节决定 8、第 5 节第 10 片与收口、第 6 节验收映射。

现象：第 10 片只列五个 nb-story 场景，并写“发现的缺口先回写 Spec 与本计划再修”；没有规定缺口发现后哪些前置切片必须重跑、验收门是否阻止第 11 片性能与最终收口、修复后五个场景是否必须重新通过，也没有把决定 8 列出的 `complete()`、`runResult`、错误归类、密钥遮盖、进程收尾、相邻 user 合并等语义映射到这道门或明确由第 2／9 片覆盖。

为什么是问题：照字面实现，验收测试可以发现缺口、修改计划后继续做性能与收口，最后只保留一次失败前的结果；或者修复第 2–9 片后不重跑已经依赖旧行为的门禁。这样“门”只是一次示例测试，不是对 nb-story 合同的阻断验收，问题会在迁移 Task 才暴露并返工。

如何核实：按第 10 片清单逐项对照第 1 节决定 8、现行合同输出 10–21 和第 6 节映射；再模拟其中一个场景发现 `complete()` 缺口，计划没有停止条件、回溯切片或重跑矩阵。

建议改法：把第 10 片写成明确 gate：逐项列合同编号与测试，任一失败即停止第 11 片和 Task 收口；修复后重跑受影响切片的合同测试与五个 acceptance 场景，全部通过才进入性能片。若只保留五个 smoke，就把名称改成“nb-story smoke”而不是验收门。
