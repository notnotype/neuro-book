### 2. `/plan 文字` 在等切换结果期间换了会话：文字落进别的会话的草稿（已在真实运行时复现）
严重程度：建议（偏重要）　类别：正确性、竞态
位置：web/session-host.ts:1668-1676（`planCommand`）
现象：`planCommand` 在 `await setMode("plan")` 之后无条件 `setDraft("/plan " + text)`，没有核对当前会话还是发起时那一个。`setMode` 对有会话的情形要等一次 `changeSettings` RPC；这期间用户切到别的会话，失败的结果会把文字写进新会话的草稿。对比同文件的 `compactCommand`（1585-1600）、`renameCommand`、`forkCommand`：被拒后放回文字之前都先判 `current !== target`。
复现（真实内核、真实 changeSettings，副本里临时加的用例，已不在被审 worktree）：目录项引用了模式扩展、真实 Profile 没有（得 `unknown-extension`）；`act(command.run plan "先想清楚再写")` 后立刻 `open(另一个会话)`，等稳定后另一个会话的 `composer.draft.text` 是 `"/plan 先想清楚再写"`，notice 为空（提示被 `open` 清了，用户不知道发生了什么）。
附带：用户在等待期间继续在输入框里打的字也会被这次 `setDraft` 整个覆盖。成功路径同理：`await setMode` 之后 `submit(text, "prompt")` 取的是 `current`，切走后文字会以普通模式发到新会话，而模式切在旧会话上。这条成功路径是原有行为，这次没有改坏，但这次新增了失败路径，是同一个洞。
为什么是问题：用户的话进了另一个会话（草稿或消息），且无提示。窗口只有一次 RPC 的时间，所以不算阻断。
建议改法：`planCommand` 取 `const target = current`；`setMode` 之后若 `current !== target` 直接 return（模式已切在 target 上，文字不在新会话里处理）；失败放回文字时只在 `current === target` 且 `draftText` 仍是发起时的内容时才 `setDraft`，否则不动用户已改的输入（与 `compactCommand` 一致）。

### 3. `/mode 名字不对` 在没有模式的会话里报“没有这个模式，可选：normal、discuss、plan”，先于“没有 Agent 模式”
严重程度：建议　类别：正确性（提示的顺序）
位置：web/session-host.ts:1679-1690（`modeCommand`）
现象：`modeCommand` 先在固定的 `MODE_OPTIONS` 里找名字，找不到就写 `conversation.mode.unknown`（列出三个可选项）并把 `/mode 名` 塞回草稿；`setMode` 里的 `modesAvailable` 判断在后面。所以在没有模式的会话里输入 `/mode foo`，用户读到的是“可选 normal、discuss、plan”，一个根本不存在的选项表；只有名字写对时才看到“这个会话没有 Agent 模式”。`/mode`（无参）与名字写对的那条走到判据，提示是对的。
为什么是问题：与 Spec 输出 12“没有模式的会话里 `/plan`、`/mode` 都提示‘这个会话没有 Agent 模式，切换不了’”不一致，且误导。
如何核实：从代码读出；没有用例（新用例的 `/mode` 只用了合法名字 `discuss`）。
建议改法：`modeCommand` 开头先判 `modesAvailable(current)`，没有就提示并返回；`setMode` 里的判据保留给控件与 `/plan`。顺手把 `modesAvailable` 抽成 `setMode` 与 `modeCommand` 共用的一处，现在控件（2109 行）、`modesAvailable`、`createSession` 各写一遍“按哪个目录项判”。

### 4. 成功的 `/plan`、`/mode`（无文字）不清输入框，输入框里留着 `/plan`（从代码推断，原有行为）
严重程度：建议　类别：正确性（与相邻命令不一致；非这次引入）
位置：web/session-host.ts:1668-1690（`planCommand`、`modeCommand`）对照 1584-1600（`compactCommand` 先 `setDraft("")`）
现象：输入框发 `command.run` 时不清自己的文字（AgentConversationComposer.vue:314 只 emit；“发送后不清空：宿主受理后给出新版本的空草稿”）。`compact`、`new`、`fork`、`rename` 受理后都自己 `setDraft("")`；`plan`、`mode` 成功后没有，只有带文字走 `submit` 时才被清。副本里用真实宿主确认：`composer.draftChanged "/plan"` + `command.run plan` 之后 `composer.draft.version` 仍是 0（宿主没给新版本的草稿，输入框本地文字不会被换掉）。Lab 夹具的 `runCommand` 用 `acceptSubmission` 清掉了草稿，说明视图一侧的合同是“受理后清空”。
与这次的关系：这次新增的失败路径 `setDraft("/plan 文字")` 是“切不成，文字留着”，与上面这条一起看，用户无法从输入框区分“切成了”和“没切成”（只有模式控件与 notice 不同）。`/plan 文字` 失败时 `setDraft` 本身几乎是空操作（输入框里本来就还是这句话），只在用户等待期间改过输入时才有可见效果，而那种情形它是覆盖用户新输入（见第 2 条）。
没有在真实 DOM 里验证：只验证了宿主侧不产生新草稿版本；组件是否另有清空没有读到。
建议改法：成功受理（`/plan`、`/mode` 切成了，或已在目标模式）时 `setDraft("")`；失败时不要 `setDraft`，让文字原样留着（改动更少，也消掉第 2 条的覆盖）。若开发者认为这是有意（命令留在输入框方便再改），则在 Spec 输出 12 写一句。

### 7. 小项：重复的判据写法、`createSession` 里的会话漂移、英文文案
严重程度：建议　类别：代码质量
位置：web/session-host.ts:1263、2109、1644；locales/en-US.json:258
- 控件（2109）、`modesAvailable`（1644）、`createSession`（1263）各写一遍“按哪个目录项判”，控件一处在“会话头还没读到”时按主创判、`modesAvailable` 同样情形按 `undefined` 判（都得 true，目前结果相同，改动其一就会分叉）。控件直接用 `modesAvailable(target ?? null)` 即可，判据只剩一处。
- `createSession` 里 `await openHere(...)` 之后调 `setMode(mode)`，`setMode` 用的是此刻的 `current`，不是刚建好的会话；等待期间用户切走时，草稿模式会提交到别的会话（原有行为）。这次在 `setMode` 前面加了 `modesAvailable(current)`，同一情形下还会在别的会话上冒出“这个会话没有 Agent 模式”的提示。可在 `createSession` 里判 `current?.id === created.value.sessionId` 再提交。
- en-US “This session has no agent modes, so it cannot switch”：同文件别处写 “Agent session”“Agent activity”，大小写不一致；中文“这个会话没有 Agent 模式，切换不了”能懂，不解释内部处理，符合“界面不写说明”的规则。`extensionsMissing` 两句直接显示扩展 id（与 `toolsMissing` 显示工具 id 一致），可以接受；若要更友好，说明里加一句“检查 Profile 里引用的 id 有没有写错”（插件作者拼错 id 时“装上提供它的插件”指错了方向）。
