# w00032 t30 界面部分设计审查（前端视角）

审查对象：plan.md “nb-agent-ui 核心 / 渲染层 / 应用前端”与切片 4、5、验收映射；Spec `agent/request-trace.md` 输出 12 到 25 与入口。事实逐条对照了 master 上的代码。

### 1. “查看这次请求”的 appliesTo 没有数据可看：MessageView 无请求序号，且拦截链直接给出的回复有序号却没有记录
- 严重程度：重要；类别：正确性
- 位置：plan.md “应用前端”最后一条（`appliesTo` 看这条回复在日志里有没有 `request`；“回复的条目 id 经会话日志换成请求序号”）；Spec 入口表、输出 25 末句；`packages/nb-agent-ui/src/registry.ts:166-172`（`appliesTo(message: MessageView)`）；`packages/nb-agent-ui/src/types.ts:95-117`（`AssistantMessageView` 没有 `request`）；`packages/nb-agent-ui/src/kernel-transcript.ts:286-299`（`assistantFrom` 不拷贝 `data.request`）
- 现象：
  1. `appliesTo` 是同步纯函数，只收到 `MessageView`；视图里没有会话日志，宿主 `session-host.ts` 的 `run()` 也不在渲染时介入。计划里“经会话日志换成请求序号”没有可走的通路。`assistant` 事件的 `data.request` 在适配器里被丢掉了（`assistantFrom` 只取 content、toolCalls、usage、model）。
  2. 即使把 `request` 带进视图，“有 `request` 就显示”也是错的：拦截链不调 `next` 直接交回回复时，`assistant` 事件照样带 `request`（`callModel` 末行 `lastRequest ?? core.reserveRequest()`），但没有 `modelStarted`，也没有记录（Spec 输出 1 末句）。核实：`packages/nb-harness/src/kernel/run/tools.test.ts:441-444`（`blocked` 的 `assistant.request` 是 `started[1].request + 1`，且 `not.toContain("modelStarted")`）。这种回复上会出现按钮，点了得到“这次请求的记录已经清掉了”，是谎话。关记录期间发出的请求、升级前的旧会话同理：有序号、没有记录，文案“已经清掉”不对。
  3. 动作条只挂在用户消息与每轮的 `outcomeMessage` 上（`AgentConversationTurn.vue:163-211`），一轮里中间几次请求没有入口，这是可以接受的，但计划与 Spec 都没写，“回复”指的是 `outcomeMessage` 应写明。
  4. `toAction(message, target)` 拿不到会话 id（`MessageView` 没有），payload 只能带 `request`，会话 id 要宿主在 `run()` 里补（`current.id`）。
- 如何核实：`grep -n "request" packages/nb-agent-ui/src/types.ts` 看不到 `AssistantMessageView.request`；`sed -n 286,299p kernel-transcript.ts`；读 `tools.test.ts:430-445`。
- 建议改法：给 `AssistantMessageView` 加 `request?: number`（核心类型，随 npm 公开，计划“nb-agent-ui 核心”要列出）。`kernel-transcript.ts` 里已有 `purposes` 表（`modelStarted` 处 `purposes.set`），只在 `purposes.has(request)` 时才填，这样拦截链直给的回复自然没有；`liveMessage`（`id: live-<request>`）也带上，进行中的请求也能点。`appliesTo: (m) => m.kind === "assistant" && m.request !== undefined`。Spec 输出 25 与 `request-not-found` 的文案改成“没有这次请求的记录”，不说“已经清掉”。验收加一条：拦截链直给的回复没有该按钮。

### 2. 顶栏动作：Spec 与注册表里没有“钉住”的来源，计划“没有钉住的进溢出菜单”无从判定；panel 目标、角标、`when` 同样没人渲染
- 严重程度：重要；类别：不变量
- 位置：plan.md “nb-agent-ui 渲染层”末条；`docs/specs/ui/agent-conversation-view.md:174,220`（“常驻顶栏的动作不超过两个，其余收进溢出菜单”“是否允许常驻顶栏”）；`packages/nb-agent-ui/src/registry.ts:178-187`（`pinnable: boolean`，注释“常驻的最多两个”）；`AgentConversationView.vue:86-94,114-125`（`overflowItems` 与 `onOverflowSelect` 写死 context、tree、toggle-view-mode 三个 id）；`packages/nb-agent-ui/src/vue/AgentConversationView.md:111`（写明 `panels`、`headerActions` 都还没实现）
- 现象：
  1. `pinnable` 只是“允许”，没有任何字段、用户设置或规则说明哪些真的常驻。全仓库没有一处登记过顶栏动作（`grep -rn headerActions packages/*/src` 只有注册表与它的测试），渲染代码一行都没有。计划说“没有钉住的进溢出菜单”，但“钉住”在 Spec 里没有定义，实现者只能猜。
  2. 回答“要不要连带做钉住”：不要做用户钉住。用最小规则：`pinnable` 为真的按 `order` 取前两个常驻，其余与 `pinnable` 为假的进溢出菜单；本动作登记 `pinnable: false`。这条规则要写进 Spec“顶栏”一节并补验收，不然两个插件各登记两个 `pinnable: true` 时谁常驻是未定义的。
  3. 只补 `target.kind === "action"` 这一支，`{kind: "panel", panelId}`、`badge`、`when` 仍是登记了不生效，同一个注册表类型里一半能用一半静默无效，正是 `EntryRendererEntry` 注释里警告过的“登记了却以为已经生效”。要么一起实现，要么在类型上收窄/加运行时拒绝。
  4. 溢出菜单现在用写死的 id 分派，登记动作的 id 可能与 `context`、`tree`、`toggle-view-mode` 撞名；“溢出菜单固定包含原始视图”的位置（最后一项）也要写。登记项的 `label` 是 `Text`，要经翻译端口取。
  5. ui Spec 现有的验收只有第 14 条（重复 id 构造失败），没有“顶栏动作怎么显示、点了发什么”的验收；计划“Spec 与文档改动”只提了 `AgentConversationView.md`，没有改 Spec，行为合同缺位。
  6. 计划没写这条动作与回复动作登记在哪：`plugin.ts:403` 每个对话位置各 `createAgentViewRegistry([...builtinContributions, subagentContribution(...)])`，需要在这里再加一个 `AgentViewContribution`（含 `when: ctx.session !== null`，没有会话时不显示）。
- 如何核实：`grep -rn "headerActions\|pinnable" packages/nb-agent-ui/src packages/neuro-book/src`；读 `AgentConversationView.vue:86-125,370-381`。
- 建议改法：Spec“顶栏”补一段规则（上面第 2 点）加一条验收；实现 action 与 panel 两支，或把 panel 支从类型里拿掉并写进非目标；溢出项 id 加来源前缀（`header:<id>`）；登记位置写进计划。

### 3. `open-requests` 的“先开页、再交筛选”时序只在页面宿主是插件级单例时成立；计划没写宿主的归属与寿命
- 严重程度：重要；类别：正确性
- 位置：plan.md “应用前端”第 1、2 条；Spec 输出 12、25；`packages/neuro-book/src/plugins/agent/web/plugin.ts:455-461,486-509`（`hostAt(position)` 是插件作用域里按位置缓存的单例，`FOCUS_SESSION_COMMAND` 先 `reveal()` 再 `host.open()`）；`packages/neuro-book/src/plugins/editor/web/pages.ts:56-62`（页面组件由 `load()` 异步取得，挂载在命令之后）
- 现象：`FOCUS_SESSION` 能“先开后交”，是因为 `SessionHost` 不依赖组件是否挂载。计划把 `requests-page.ts` 写成“订阅 `changed`、调远程、持有筛选与选中”的页面宿主，却没说它在哪建。若在页面组件的 `load()`/`setup()` 里建：命令执行 `nbook.editor.open-page` 返回时组件很可能还没挂载（异步组件），此刻没有宿主可交；页面已开着时又会遇到“旧宿主还活着”。
  另有四个没写的情况：
  1. 页面开着时，无参数的 `open-requests`（命令面板）是保留现有筛选，还是重置为“全部”？Spec 输出 12 写“换成入口要的筛选与选中”，无参数时入口没有要求，行为未定。
  2. `request` 指定的那一次不在已加载的第一页（旧、或被当前筛选/搜索排除）时，选中与详情不能依赖列表，必须能直接 `read(id)`；输出 25 的“列表照常显示”隐含这点，但计划的 `read` 只在“选择”动作里出现。
  3. 页面关掉再用命令开：宿主若是单例，会带着上一次的筛选与搜索词复活，要明确是否清空。
  4. 多窗口：每个窗口一个浏览器入口、一个页面宿主，各自订阅；这一点没问题，但清空操作后别的窗口的列表要靠 `changed` 事件刷新，计划的事件只写了“新增与结算”，没有“清空/过期清理”事件。
- 如何核实：读 `plugin.ts:479-509` 对照 `hostAt` 的写法；`pages.ts` 的 `EditorPageImplementation.load()` 只返回组件。
- 建议改法：把 requests 页面的状态仓（筛选、选中、查询词、已加载页）建在插件作用域，与 `hostAt` 同一种做法，组件挂载时读它、卸载时只释放订阅；命令里先写仓、再 `open-page`（写在前面对“未挂载”和“已挂载”两种情形都对）；Spec 输出 12 补一句：无参数时沿用现有筛选，页面新开时从全部开始；`changed` 事件加“记录被清掉”的种类。

### 4. 全文查找的命中数在服务端 `search` 与客户端 `findMatches` 各算一遍，评审板自己已经对不上；原始请求体页的命中还要依赖懒加载
- 严重程度：重要；类别：正确性
- 位置：plan.md “关键设计”记录器 `search(query, filters)`（逐条扫、命中片段与处数）与“nb-agent-ui 核心”`findMatches(detail, query)`（各页命中数、逐处位置）；Spec 输出 16、19、验收 4；评审板 `artifacts/review/r1/search.webp`
- 现象：
  1. 同一个“有几处命中”由两处实现：列表第二行的“另外还有几处”来自 nb-harness 里的记录器，详情查找条的“第几处/共几处/各页命中数”来自 nb-agent-ui 核心。两边对“正文”的定义必须逐字一致（工具调用参数是 JSON 序列化还是展开字段、工具声明哪些字段、不分大小写用 `toLowerCase` 还是别的、重叠匹配、`İ` 这类小写后长度变化的字符让偏移错位），而它们在两个包里，nb-agent-ui 不能依赖 nb-harness，没有共享函数。这是 AGENTS 里“同一件事各写一份”的信号。
  2. 评审板已经出现不一致：搜“年龄”时列表 #10 写“+1”（另外 1 处，共 2 处），打开后详情查找条写“2 / 5”，各页“消息 4、工具 0、原始请求体 1”（共 5）。验收 4 只要求“详情查找条的总数与各页命中数一致”（详情内部自洽），没要求与列表一致，所以这个矛盾过得了验收。
  3. Spec 输出 16 的查找范围不含原始请求体（正文、系统提示词、工具声明、工具调用参数、错误文字），输出 19 却写“各页的命中数”，评审板的查找条也有“原始请求体 1”。原始请求体是 `load-payload` 懒加载的（计划动作表），客户端在没加载时无从计数，加载前后命中总数会变，“共几处”跳动；响应页、和上一次比较页的命中数怎么算也没写。
- 如何核实：看 `search.webp`；`grep -n "findMatches\|search(" plan.md`。
- 建议改法：命中的权威只留一处。推荐服务端：`read(id, {query})` 一并返回逐处位置（页、消息序号、偏移、片段），列表的“处数”与详情的“共几处”同源；客户端 `findMatches` 只负责把位置高亮。原始请求体页不计命中（与输出 16 一致，查找条里不列这一页），或明确写“只在已加载后计、总数不含”。验收 4 加一句“与列表第二行的处数一致”。

### 5. `AgentRequestTrace` 的 props 与 action 清单缺好几项，照字面做不出定稿的样子；形状也和同包的 `AgentSessionPanel` 不一致
- 严重程度：重要；类别：代码质量
- 位置：plan.md “nb-agent-ui 渲染层”第 1 条（action 清单 `select`、`query`、`load-payload`、`clear`、`open-session`、`open-settings`、`copy`）与“核心”的视图类型；对照 `packages/nb-agent-ui/src/vue/AgentSessionPanel.vue:12-56`、`docs/specs/ui/agent-conversation-view.md` 的受控约定
- 现象：定稿的界面里有下面这些东西，计划的 props 与 action 里都没有对应项：
  1. **加载更多**：`list` 带分页游标，但没有 `load-more` 动作，也没写每页多少条、触底自动加载还是按钮。
  2. **重试**：Spec 失败表要求 `trace-unavailable` 时“页面整块写原因与重试”，没有 `retry` 动作。
  3. **换比较对象**：Spec 输出 20 与评审板 `compare.webp` 有“和 #3（上一次）比”的下拉，可换成同一会话的任意一次。组件需要：同会话的请求候选（不受当前筛选影响，筛选成“失败”时前一次可能不在列表里）、所选对象的详情、对应的 action。计划里 `compareRequests(a, b)` 的 b 从哪来、`outline(detail, previous?)` 的 `previous` 谁取，没写。“新一次、旧一次”也没说是列表里的相邻项，还是同会话的前后序号（排序按 token 时两者完全不同）。
  4. **筛选下拉的候选值**：会话（带标题与条数）、模型有哪些，必须由后端给（`list` 只“带合计”）。计划没有这项数据，也没有对应的类型字段。
  5. **“进行中，已等 4.1 秒”**：要有 `now`。同包的会话面板用 `now` prop 加宿主定时更新；若组件自己 `setInterval` 就要在 `.md` 声明 `env:timer`，Lab 场景也无法确定性验证。计划没选。
  6. **状态**：列表加载中、列表出错、详情加载中、详情 `request-not-found`、原始请求体加载中/失败、“没有选中”（宽屏右栏空着写什么；旧应用的“打开时自动选中最新一条”在参照清单第 16 项标了“做”，Spec 没写）。`AgentSessionPanel` 有 `loading`、`error`，这里一个都没有。
  7. **形状**：同包的做法是领域操作走 `action`（`AgentViewAction` 联合，`type: "session.select"` 点分写法），纯界面状态走 `update:*`（`update:query`、`update:scope`）。计划把 `query`（含筛选、排序、查找词）也塞进 `action`，名字是裸词。`AgentViewAction` 是个被 `session-host.run()` 逐个 `case` 的联合，请求页的动作混进去会污染它；应单独声明 `RequestTraceAction` 联合并写进核心类型，筛选/排序/查找词用 `update:*` 或 `update:query` 一个事件。
- 建议改法：在计划里把 `AgentRequestTraceProps` 与 `RequestTraceAction` 写成类型清单（上面 7 条逐一落位），再动手。至少补：`facets`、`now`、`loading/error`、`detail` 的状态联合、`compare`（候选与对象）、`more`、`retry` 动作。

### 6. 查找输入每次变化都是一次服务端全量逐条扫：没有去抖、取消、过期响应丢弃，也没处理输入法组字；键盘操作整体未设计
- 严重程度：重要；类别：正确性
- 位置：plan.md “渲染层”第 1 条（`query` 是 action）与“验证/不做与风险”（逐条扫）；Spec 输出 16、17、22；`packages/neuro-book/src/plugins/editor/web/key-event.ts:1-12`（仓库已有的键位匹配约定，组字中不匹配）
- 现象：
  1. 查找框每敲一个字发一次 `search`（服务端逐条扫 1 万条、目标 1 秒内）。快速输入时前一次还没回，后一次已发出，晚到的旧响应会盖掉新结果。计划没有去抖时长、没有取消（远程调用能否中止也没写）、没有“只认最后一次”的版本号。
  2. 中文用户用输入法组字时，拼音阶段的 `input` 事件会触发查询；仓库的键位代码专门处理了 `isComposing`，这里没提。
  3. `#N` 的跳转语法与 Markdown 里的字面 `#`：搜“#伏笔”不受影响（非数字），但搜“#12”这种文字不可能；至少在查找框的占位里写明，并在输入 `#12` 时同时给出“跳到 #12”和“查找字面 #12”。
  4. 键盘：Spec 只提了详情的“新一次、旧一次”。没有写：列表是 `listbox`/`grid` 还是一排按钮，上下键移动、回车打开；“新一次/旧一次”的键位（不能是裸方向键，那是列表的）；查找条的上一处/下一处（常见为回车、Shift+回车）与 Esc 关闭；`Ctrl/⌘+F` 要不要接管。编辑区里的页面本身不应吞掉浏览器的 `Ctrl+F`，若接管须只在页面获得焦点时、并在查找框已有焦点时不再接管；这条的 `.md` 还要声明 `env:global`（全局监听）或把监听限定在组件根元素上，两种写法的标签不同。
- 建议改法：查找词在组件里是本地输入态，去抖 250 到 300 毫秒、组字结束后才提交；宿主按“请求序号”丢弃过期响应；`search` 能被中止就中止。键盘约定写进 `AgentRequestList.md` / `AgentRequestFindBar.md`，监听限定在组件根元素上；Lab 的 e2e 验一次“上下键、回车、Esc”。

### 7. “新请求进顶部、选中与滚动不变”只对“按时间排序、无筛选、无查找、在第一页”成立；Spec 输出 14 与 15 互相冲突，推送后筛选由谁再算没写
- 严重程度：重要；类别：正确性
- 位置：Spec 输出 14、15、16；plan.md 记录器 `onChange(listener)`（推新增与结算的摘要行）、应用后端远程服务 `changed` 事件、应用前端页面宿主；README 决定 7
- 现象：
  1. 输出 15 允许按总时长、输入 token、费用排序且“不按时间排时不分组”；输出 14 同时要求新请求出现在列表顶部。按费用排序时新请求不该在顶部；进行中的请求没有时长与费用，结算后排序键变了，“原地更新，不换位置”与排序结果矛盾（要么列表不再有序，要么要动）。
  2. `changed` 推来一行摘要后，客户端要判断它是否满足当前的会话、用途、状态、模型、时间、查找词六种条件。若在客户端重算，就是把筛选与查找逻辑再实现一遍（查找需要全文，根本做不到）；若收到事件就重新 `list`，就丢了已加载的多页与滚动位置，违背输出 14。计划没有选。
  3. 列表头的“条数、输入合计、缓存命中、费用合计”随新请求变化，要写是否实时更新。
  4. 在列表中间（已滚下去）时新行插到顶部：Chrome 有 scroll anchoring，但页面里有吸顶的组头、行高固定的虚拟/分页列表、动态组头计数，anchoring 常在这些条件下失效；“滚动位置不变”需要组件自己补偿，或在已滚离顶部时改成顶部一条“有 N 条新请求”的提示。
  5. 选中的那条被后来改变的筛选排除，或在“重发过”等状态筛选下结算后不再满足条件，详情继续显示还是清掉，没写。
- 建议改法：写成一条规则：只有“按时间排序、无查找词”时才实时插入，且客户端只在“筛选条件能由摘要行直接判断”（会话、用途、状态、模型、时间都能）时自己判断是否插入、合计增量更新；其余情况（非时间排序、有查找词）不插入，顶部显示“有 N 条新请求，点此刷新”。结算只改行内内容，不重排。选中项被排除时详情保留并在列表头标出“当前选中不在筛选结果里”。把这些写进 Spec 输出 14 与验收。

### 8. 规模：`read(id)` 把整份请求全文展开后一次传回，方向键连按会连续取；“列表首屏 300 毫秒”没有口径；分页大小与加载更多未定
- 严重程度：重要；类别：安全与性能
- 位置：plan.md 记录器 `read(id)`（引用展开成内容）、“验证”（列表首屏 300 毫秒内）、核心 `outline`、渲染层 `AgentRequestJson`；Spec 输出 17、18、21、22
- 现象：
  1. `read(id)` 返回“引用展开成内容”的整个请求，计划只在显示层面做“长的先露前几行、看全文”，传输与解析层面没有分层。实测量级（`/tmp/review-w00032-t30-design/frontend/scratch/payload-lines.ts`，合成 60 条消息、8 条各约 6 万字符的工具结果）：pretty JSON 约 498 KB。按单条几万 token 的真实工具结果，一份请求 0.5 到 1 MB、一个会话里每条请求都这么大。详情打开一次需要 `read` 加（比较页）上一次的 `read` 加（原始请求体页）`payload`，约 1 到 3 MB 进浏览器并解析；“新一次、旧一次”连按几次就是连续几次这样的读，没有取消、没有预取策略、没有“上一次”的缓存（同一份被比较的数据反复取）。
  2. 同一份实验显示 pretty JSON 只有 254 行、最长一行 54,907 字符：因为字符串里的换行被转义，JSON 视图的“行号”对长文本没用，最长一行要折行或横向滚动；Spec 输出 21“带行号”需要写清超长行的显示（折行并显示行号只在逻辑行首）。
  3. 大纲一条消息一行，几百条消息的请求一次性画几百行、每行带 token 条，没有问题；但“点一行在原地展开全文”的单条几万 token 的工具结果若逐行带行号（评审板的工具结果展开有行号），一条就是几千个 DOM 行，应限制为展开时才渲染、“看全文”后分块渲染。
  4. 列表：计划只写“分页游标”，没写页大小。一个会话几百次请求、14 天全部会话上千条，每条两行 + 组头；按页 100 到 200 条分页加载，不需要虚拟滚动；但必须定页大小与触发方式（见发现 5 第 1 条）。
  5. “列表首屏 300 毫秒内”：没有说是服务端 `list` 耗时、含网络的往返，还是含懒加载 `nb-agent-ui` 的 Vue 块（`plugin.ts` 里 `loadVue` 动态导入）与新页面块的冷启动。口径不同，数字差一个数量级，证据里要写明（建议：服务端 `list` 的 p95，加“数据到达到首行渲染”的前端耗时，冷启动单列）。
- 建议改法：`read` 返回大纲（每条消息的角色、预览、token、内容哈希），单条全文用 `readMessage(id, index)` 按需取（点开、看全文时），请求体与系统提示词也按页取；前端对 `read` 做取消与同会话的小缓存（LRU 几条）；方向键用去抖或只在停下后取。`AgentRequestJson` 的“行号”按逻辑行，超长行折行并给“只显示前 N 字，展开”；这些写进计划的“关键设计”与性能验证。

### 15. “和上一次比较”：`compareRequests` 只定义了前缀相同的情形，中间插入或压缩改写历史时逐行差异会整段错位

- 位置：plan.md 核心 `compareRequests(a, b)`、`outline` 的“相同前缀的长度（逐条比内容哈希）”；Spec 输出 18、20；评审板 `r1/compare.webp`；`packages/nb-ui/src/components/display/DiffView.md`（按字比有 150ms、按行比有 300ms 的主线程预算，超了整段标记）
