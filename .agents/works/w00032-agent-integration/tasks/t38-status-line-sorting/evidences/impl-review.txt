### F1 【重要】【正确性】状态栏项右边换到左边（挂载中改设置）后，新槽不再被量宽
位置：packages/nb-agent-ui/src/vue/composer/AgentStatusBar.vue bindSlot（约 137-149 行）与模板里左右两个 v-for（各自 :ref="(element) => bindSlot(item.id, element)"，同一个 id）
现象：同一个 id 从右块换到左块时，Vue 先补丁左块（新元素挂上，bindSlot(id, 新元素) 把 slots 里的旧元素换成新元素并 observe），再补丁右块（旧元素卸载，bindSlot(id, null)）。后一次调用读到的 previous 已经是新元素，于是 unobserve(新元素)、slots.delete(id)。从左换到右顺序相反，没事。
为什么是问题：设置页或右键菜单改了边之后，会话视图里那一项不再被 ResizeObserver 观察，widths 里是旧值，之后内容变宽（令牌数 999 到 1.2k、费用位数、模型名换了）收起判断一直用旧宽度，放不下也不收（或相反）。t38 之前项不换边，这条路径是新增的；AgentStatusBar.dom.test.ts 的“项换到左边”用例是一开始就带 side 挂载，没有覆盖“挂载后换边”。
如何核实：我在 /tmp/claude-1000/review-t38-impl/exp/side.test.ts 里用记录 observe/unobserve 的假 ResizeObserver 挂 AgentStatusBar，setProps({statusLine: {side: {usage: "left"}}})：换边后新槽在 .acv-status__left 里，observed.has(槽) 为 false（换回右边后为 true）。运行：在 packages/nb-agent-ui 下 ../../node_modules/.bin/vitest run --config /tmp/claude-1000/review-t38-impl/exp/vitest.exp.config.ts --silent=false
建议改法：bindSlot 卸载分支只在 slots.get(id) === 该次卸载的元素时才删，但函数 ref 的 null 调用拿不到旧元素；改成用 :ref 的 key 带边（`${side}:${id}`）分开登记，或用一个 ref 函数闭包记住自己绑过的元素（const el 变量，卸载时按它 unobserve、仅当 slots.get(id) === el 才 delete）。并补一条挂载后换边的 dom 测试。

### F7 【建议】【正确性】useSortable 的读屏播报：放回原位也报“已取消”；“已放到…”在写入结果出来之前就播了
位置：packages/nb-layout/src/vue/useSortable.ts onEnd（约 247-250 行）与 commit（announcement 先于 onMove 写）
现象：1) onEnd 对一切非 committed 结束播“已取消，X回到原处”，包括 no-action（松手时回到原位，实际是放下、不是取消；键盘在原位按回车也是）。2) commit 里先播“已把X放到某区第几位”再调 onMove，onMove 的 Promise 之后失败回原样时没有任何后续播报，读屏用户听到“已放到”而界面回了原样（失败原因在宿主的通知里，但那条通知不一定被读到）。
为什么是问题：Spec 输出 8 说“放下、取消各播报一句”；放回原位是放下。第二条是文案先于结果。
如何核实：SortableList.dom.test.ts 的“回到原位不调 @move”那条先按 Esc，再空格加回车放回原位，断言里没有看 role=status 的文字；加一句断言即可看到“已取消”。
建议改法：onEnd 里 no-action 播“已放下，X仍在某区第几位”（或不播）；Promise 失败时 settle 里补一句“没有保存，X回到原处”之类（文案进 nb-layout 的 locales）。属于窄场景，也可以记为已知限制。

### F8 【建议】【代码质量】commit 里把宿主的 Promise 失败再抛一次，产生第二个 unhandled rejection
位置：packages/nb-layout/src/vue/useSortable.ts 约 232-236 行（void result.then(settle, (error) => {settle(); throw error;})）
现象：result.then(a, b) 产生一个新 Promise，b 里 throw 让它 reject，而且没人接。宿主若已经处理了自己返回的 result（例如 .catch 报告），这里仍多一个全局 unhandledrejection（浏览器控制台“Uncaught (in promise)”，Vitest 里会让整个运行失败）。注释说“失败的 Promise 照样往外抛，宿主自己报告原因”，但外抛的不是宿主那一个。StatusLinePage 的包装用 `.then(reportIfFailed)` 让 Promise 恒 resolve，现在碰不到；别的使用方（SortableList 通用组件）会碰到。
如何核实：任何 onMove 返回 Promise.reject(new Error("x")) 并自己 catch 过的使用方；window.onunhandledrejection 会收到一次。
建议改法：用 result.then(settle, settle) 只负责收口（宿主的 Promise 由宿主处理，本来就是它的）；或用 finally 且不改变结果：`void Promise.resolve(result).finally(settle).catch(() => undefined)` 并在 Spec 写明“失败不报，由宿主处理”。
F8 更正（追加）：上面的“建议改法”不成立：只要对 result 挂了任何回调，原 Promise 就算已处理，`then(settle, settle)` 会让宿主没处理的失败被静默吞掉（违反“不静默吞错”）。外抛一次是这种写法下没法两全的取舍，F8 降为【建议】：只在 SortableList.md 与 Spec 失败一节写明“失败的 Promise 会在这里再抛一次，宿主要在自己返回的 Promise 里收口（像 StatusLinePage 那样让它恒 resolve）”，不改代码。

### F13 【建议】【nb-ui】Checkbox 的 mt-[calc((1lh-18px)/2)] 在行高小于 18px 时变成负外边距；插槽内容自带行高时对不齐
