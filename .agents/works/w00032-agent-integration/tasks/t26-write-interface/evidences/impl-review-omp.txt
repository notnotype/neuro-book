### 重要｜正确性｜packages/neuro-book/src/backend/staged-commit.ts:95-100,156-164
现象：目标已存在时提交无条件走 rename(options.staged, file)，没有检查目标 Stats.nlink；因此目标有硬链接时只替换当前目录项，其他硬链接仍指向旧 inode。计划与验收明确要求 nlink > 1 时锁内拷贝/就地写并保留硬链接关系。
为什么是问题：同一文件的另一个硬链接会继续看到旧内容，写入接口对一个逻辑文件产生分裂版本，违反“硬链接仍在/提交内容一致”的文件合同；这不是外部并发窗口，而是每次硬链接目标覆盖的确定行为。

### 重要｜正确性｜packages/neuro-book/src/backend/staged-commit.ts:141-151,167-191
现象：新建目标的初始 link(staged, file) 遇到 EXDEV 时进入 placeCopy；placeCopy 把 staged 拷到目标目录临时文件后仍无条件 link(temporary, file)。目标文件系统不支持硬链接时，这第二次 link 返回 EPERM/ENOTSUP/EOPNOTSUPP，流程直接失败，没有走已有的 exclusiveCopy/open(wx) 回退。
为什么是问题：提案与计划要求跨盘提交走目标目录临时文件再原子放到位，并同时覆盖不支持硬链接的文件系统；当前组合（暂存盘与目标盘不同、目标盘又禁用硬链接）会让本来可提交的新建写入稳定得到 io-failed，且暂存文件留下。该分支不是理论上的初始 link 失败：EXDEV 已经把流程带到这里。
如何核实：真实文件系统上让 staged 位于 /dev/shm、目标位于不支持 hardlink 的挂载点，调用 commitStaged 的 absent 路径；或在测试中让第一次 link 返回 EXDEV、目标目录的 link 返回 EOPNOTSUPP，观察 placeCopy 未调用 exclusiveCopy。现有 staged-commit.test.ts 只覆盖跨盘覆盖已有文件（how=over），没有跨盘新建，也没有 hardlink 不支持的组合。
建议改法：placeCopy 的 how=new 在 link(temporary,file) 遇到不支持硬链接的错误时改用目标目录的排他拷贝并 fsync；补跨盘新建与目标盘禁用硬链接的真实测试，并确认 temporary、staged 的收尾。
### 重要｜不变量/安全与性能｜packages/neuro-book/src/plugins/files/backend/workspace-files.ts:163-170,179-194；packages/neuro-book/src/plugins/files/backend/projects-scheme.ts:438-450

为什么是问题：计划与资源 Spec 要求租约从 stage 持有到 commit 或 discard，保证目标项目代次与暂存目录在同一次操作内有效。当前项目可以在生成器写入数秒期间停止、换代或登记路径变更；服务端仍会直接写旧 record.path，既可能留下旧项目目录的残留，也可能在 commit 时重新租到另一代/另一目录而找不到刚写的 stage。它还绕过项目实例的 checkProjectDirectory/身份核对，在项目未运行时就直接向登记路径下建控制目录。

### 重要｜正确性/接口合同｜packages/neuro-book/src/plugins/files/shared/contracts.ts:220,270-272；packages/neuro-book/src/plugins/files/web/client.ts:67-73
