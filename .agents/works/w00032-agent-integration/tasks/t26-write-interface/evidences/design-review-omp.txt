### 阻断｜正确性｜计划“拥有根的一侧”第 24、26 行；`backend/locked-replace.ts:57-60,68-72,163-193`、`backend/rooted.ts:263-275`
**现象：** `adopt` 必须把已写完的 stage 文件交给 `replaceLocked`，但现有替换算法在文件身份变化时会删除临时文件再重做（第 180-185 行），重做机会最多 3 次；catch 失败也会删除临时文件（第 189-192 行）。这些都是原有临时副本的正确收尾，不适用于可消费的 stage token。`adopt` 改名成功后 stage 源路径也已消失。计划仅写“身份变了从新字节重做”，没有规定改动通用清理逻辑还是 adopt 专用保留/重建，也未规定失败后 token 是否仍可提交或 discard。
**为什么是问题：** 若照原有 cleanup 复用，第一次发现目标身份变化就删掉唯一暂存内容，第二次 `replaceOnce` 无法打开 stage 文件，符合期望基线的提交也会以 I/O 错误结束；若为支持 retry 而全局改变 cleanup，则配置层与普通保存的失败清理行为会变化。项目根还需要把不存在目标交给 `decide(null)`，而 `RootedRoot.replace` 当前先 `resolve(path)` 并要求目标已是普通文件（`rooted.ts:263-266`），虽然下层 `replaceLocked` 支持 `current === null`，项目根入口仍需新增不存在目标的解析与锁路径才能兑现 `expect: "absent"`。
**如何核实：** 逐步跟踪 `replaceLocked` 的最多 3 次循环、`replaceOnce` 的 `modified` 清理和 catch 清理；对照 `RootedRoot.replace` 的目标预解析，以及计划第 27 行的 `absent` 期望。
**建议改法：** 把“可消费 stage”建模为独立替换输入，明确暂存源的所有权与状态转换：冲突/身份变化/锁丢失/I/O 错误后源保留可 discard（除非已原子消费）；提交时目标不存在可安全排他创建并在锁内核对；配置层保留原有临时文件清理。用真实文件系统覆盖身份变化一次后重做成功、三次不稳定后 stage 仍可 discard、目标不存在的 absent 提交。

### 重要｜正确性｜计划“服务端：写入接口”第 46 行；`docs/specs/workspace/resources.md` 122 行、`runtime/plugin-channel.md` 90-94 行
**现象：** 计划把“目标当前 baseline 哈希等于 stage 哈希”当成提交成功证明。远程写请求一旦交给链路就可能 `unknown-outcome`，包括没有到达提供方、没有执行的时序；若调用前目标已经恰好等于 stage 内容，或请求用 `expect: "absent"` 但目标原本就存在同内容，当前哈希仍相同，计划会把未提交/冲突误报为成功。相同内容也可能由另一外部写者在未知期间写入。
**为什么是问题：** 内容相等只能证明当前末态相等，不能证明本次操作被执行，也不能证明它满足了本次 `expect` 条件；调用者会把未执行的副作用当作成功，并可能推进自己的状态。远程合同明确 ACK 不证明副作用，未 ACK 也不证明没执行。

**建议改法：** 不把字节相等表述成“已提交”的确定证明。采用可核对的提交身份（例如稳定 operation id 与拥有根侧持久/可恢复的提交回执），或将该分支保留为结果不确定并交 `unknown-outcome`；同步修订 planned Spec 和验收，明确能证明什么、何时允许报告成功。

### 阻断｜并发与原子性｜计划“拥有根的一侧”第 24 行；`backend/rooted.ts:263-275`、`backend/changes.ts:237-245`
**现象：** 硬链接数大于 1 时改为锁内原位写，但现有写入锁按解析后的相对路径 hash 命名（`rooted.ts:267-274`），而两个硬链接名的路径不同、inode 相同，因此不会拿到同一把锁。计划只按目标路径锁沿用现有规则，没有说明 hard-link 目标改按 inode 锁或串行化所有链接名。两个并发 writer 可各自通过基线检查后同时 truncate/write 同一 inode。
**为什么是问题：** 会交错写出损坏/混合字节，且两个提交都可能报告成功；这是为保留 hard link 而新引入的就地写路径特有竞态，不是开发者已决定的锁范围取舍可以覆盖的：该决定保留按目标路径写锁，但硬链接别名不是同一目标路径。内容写入也不再原子，监视器可看到半文件。
**如何核实：** `rooted.ts:267-274` 的锁名取 `resolved.realPath`，`resolve` 对硬链接保持各自词法目录项路径；`replaceLocked` 的锁覆盖单次写；为 `a`、`b` 建硬链接并从两个路径同时使用相同基线提交不同大块内容即可观察锁互不相同且写入可交错。
**建议改法：** 针对硬链接分支使用基于 inode 身份的跨进程锁，并确保目标锁身份在锁内重新核对；另需承认此分支不是原子替换，定义监视如何等锁释放/避免半写事件，或选择拒绝无法同时满足链接保留与原子性的情况。并发硬链接别名必须成为验收用例。
### 阻断｜结果结算与资源释放｜计划“服务端：写入接口”第 46 行；`backend/projects-scheme.ts:55-71`、`runtime/plugin-channel.md` 输出 90-94
**现象：** `unknown-outcome` 可由调用取消、超时、断链造成，项目实例在 ACK 后仍可能继续提交。计划随后还要发起一次 `read` 比较目标基线，但没规定它使用什么 signal；若沿用同一调用 signal，取消/超时后它已 aborted，核对直接失败。也没有说明 unknown 后是否调用 `discard(token)`：立即删 token 文件会与仍执行的 commit 竞争；不删则只剩 1 小时清理，可能泄漏到下次启动或误删仍在写的 token。
**为什么是问题：** 结果未知必须同时处理“再次查询可用性”与“暂存仍可能被提供方消费”两种状态。复用已中止 signal 会使计划承诺的核对在常见取消时序完全不可执行；主动 discard 又可能删除仍在进行的原子替换输入。项目进程退出或调用方 facade 释放也不能等同于远端操作已停。
**如何核实：** `runtime/plugin-channel.md` 输出 90-94 明确写请求发出后取消/超时都为 `unknown-outcome` 且不自动重放；`projects-scheme.ts:66-71` 将 request.signal 传到远程调用并只在其返回后释放租约；按计划用同一 signal 做 post-error read 将在 abort 下被拒。
**建议改法：** 明确 commit 的状态机与 token 所有权：提交帧发出前取消可 discard；帧发出后未知必须保留 token，不能由调用方直接 discard；核对使用有单独预算、不会被原请求取消的信号，并在提供方仍不可达时返回 unknown。增加拥有根侧可判断 commit 是否仍在执行的状态/租约，或明确 token 只能在 owner 确认结算后删除、否则进入可安全回收的状态。

### 重要｜兼容与文件系统｜计划“拥有根的一侧”第 26 行；`backend/entry-ops.ts:68-82,121-128`
**现象：** 暂存位置靠比较 `st_dev` 判定是否与目标同盘，否则才落到目标目录。`dev` 不同足以表明设备不同，但相同不保证同一可改名挂载点：bind mount/子挂载可以报告相同设备号，而跨挂载点 rename 仍返回 `EXDEV`。现有文件操作明确处理 `EXDEV` 为 `cross-device`/`unsupported`，说明仅按名字或同一个 device id 推断改名一定可用并不成立。
**为什么是问题：** 这类目标会被判为 staging 与目标同盘，随后 adopt 的 rename 返回跨设备错误；若 `replaceOnce` 将错误收成普通 `io-failed` 并清理 stage，数据写入失败且用户无法重试。用户指定的“跨盘回退判定（dev 比较）”正是未覆盖的边界。
**如何核实：** 核实 `prepare` 的比较是 `stat.dev`；对照 `entry-ops.ts` 已将系统 `EXDEV` 单独识别。Linux 可在同一文件系统 bind mount 的源/目标之间尝试 rename，`stat.dev` 相同而 rename 报 `EXDEV`。
**建议改法：** 把 `dev` 仅作快速预判，不作改名成功保证；若 adopt/rename 实际返回 `EXDEV`，在 stage 未消费前迁移/重写到目标目录的 fallback 文件并重试，或在提交前用不会覆盖数据的能力检测确认同一 rename 域。验收增加 same-dev mountpoint 跨挂载用例。

### 重要｜行为兼容｜计划“拥有根的一侧”第 26 行；`backend/entry-ops.ts:42-49`、`locked-replace.ts:163-171`
**现象：** stage 文件固定以 `0o600` 创建。覆盖已有目标时计划恢复原权限位，但 `expect: "absent"` 创建新文件时没有指定最终模式；若直接 rename adopt，最终文件保持 `0o600`。现有普通空文件新建由 `open(path, "wx")` 使用进程 umask（通常 `0644`），原子替换新文件则使用 `0644` 后应用 umask。

### 阻断｜一致性与锁内顺序｜计划“拥有根的一侧”第 27 行、“记账槽”第 55 行；`backend/rooted.ts:263-275`、`backend/locked-replace.ts:53-76`
**现象：** 计划要求回声登记、事件与 ledger 记账都在提交文件锁里完成；但 `RootedRoot.replace()` 直接调用 `replaceLocked()`，后者在返回结果前已于 `finally` 释放锁，接口也没有成功后回调。计划还把 ledger 放在事件之后（第 27、55 行），而 Spec `workspace/resources.md:119` 明确顺序是替换、记账槽、登记回声/发事件、放锁。

### 阻断｜并发与条件写｜计划“拥有根的一侧”第 27 行；`backend/entry-ops.ts:42-58`、`backend/rooted.ts:263-275`
**现象：** `expect: "absent"` 的 stage commit 是目标文件新建，但文件操作 `create` 按开发者决定只取根操作锁，而暂存提交按目标文件写锁；两把锁互不排斥。现有 `entry-ops.createFile` 用 `open("wx")` 排他，而计划的 adopt 是 `rename` 替换，未规定 absent 路径用系统排他 rename/no-replace。

**如何核实：** 对照计划末尾锁决定与 `rooted.ts:267-274` 的路径锁、`commit.ts` 文件操作使用的根操作锁；对照 `entry-ops.ts:42-58` 排他新建与 `replaceOnce` 的普通 `rename`（`locked-replace.ts:183-188`）。用真实 barrier 在 absent 最后身份检查后执行 `createFile`，再让 adopt rename 继续即可复现覆盖。
**建议改法：** absent commit 必须有系统级 no-replace 提交原语，不能依赖两个不相交的互斥锁；若平台无原子 no-replace 替换，定义目标存在即冲突且保留 stage，或给这个精确路径的创建协议增加共享锁，而不是让写入覆盖先前的 `create`。验收并发 stage-absent 与 create/createContent，断言恰有一方成功且清单/字节一致。

### 阻断｜内存与大文件｜计划“拥有根的一侧”第 24、27 行、“技术选型”第 17 行；`backend/locked-replace.ts:143-160`、`backend/files-service.ts:164-179`
**现象：** stage 的新内容可以流式任意大小，但 adopt 提交仍沿用现有 `replaceLocked` 的 `readFile(target)`，把目标旧版本完整读进内存，再由 `decide` 对 `current.bytes` 调 `hashOf`。计划只把写入中间内容与回声做成流式，并将超 32 MB 的 Ledger `bytes` 设为 null；没有限制或流式处理提交前的基线计算。将 100 GB 文件替换为小文件，当前逻辑仍会先分配/读入约 100 GB。
**为什么是问题：** “流式写任意大小”只解决新版本一侧，旧版仍导致 O(目标文件大小) 的内存峰值与 I/O；大文件实际会 OOM 或长时间占住文件锁。Ledger 记录字段设 null 不能解决 `replaceLocked` 的旧内容副本。

**建议改法：** 为 adopt 增加独立提交决策：锁内用打开的文件句柄分块计算基线哈希；只在 `record` 上限内收集旧内容，超过 32 MB 不保存 bytes，避免完整缓存；改名前再按现有身份/锁规则核对。若保持现有 full-read，需明确 `stage` 可接受的最大目标大小，不能同时承诺任意大文件流式写。

### 阻断｜安全与文件系统边界｜计划“拥有根的一侧”第 29-30 行；`backend/rooted.ts:109-119,288-309`、`server/projects/identity.ts:226-242`
**现象：** 计划把 staging 放到 `root.real/.nbook/staging/`，并在打开根时扫描、删除超龄文件，但没有定义这条内部路径如何安全建目录及拒绝符号链接。`RootedRoot` 仅在用户资源路径 API 层保护 `.nbook`；直接 join 该控制目录绕开了解析器。项目身份现有合同还允许 `.nbook/project.json` 本身是符号链接，所以不能假设 `.nbook` 及其子目录一定是可信普通目录。

**建议改法：** staging 管理器初始化前逐层 `lstat` 并验证 `.nbook`、`staging` 是根内真实目录，不跟随符号链接；清理只枚举并 unlink 自己登记的普通文件，核对文件身份/前缀与目录身份。失败时整项报告 `protected-path`/`io-failed`，绝不进入链接目标。

### 重要（收窄，见第 12 条）｜超时与锁寿命｜计划“记账槽”第 55 行；`backend/locked-replace.ts:64-75`
**现象：** 计划只写 `record(entry, signal)`、“2 秒为限”，没有规定超时后 callback 必须停止、不得迟到提交，还是 Files 必须继续持锁等待它完成。现有 `record()` 是任意贡献者 Promise，传 `AbortSignal` 本身不强制 Promise settle。
**为什么是问题：** 若实现用 `await record()`，一个忽略 signal 的记账者会让保存锁无界等待；若 2 秒 race 后放锁，迟到的 `record()` 仍能写入 History，可能打乱与后续同路径提交的记账顺序。提案要求 History 可选、记账失败不阻断落盘，计划又要求锁内调用；必须定义超时确切语义。
**如何核实：** `replaceLocked()` 只有在调用方工作结束后才从 `finally` 释放锁；检查插件贡献接收者契约，未要求普通回调在 signal 时必须结束。可用忽略 signal 的 Promise 测试计划所说 2 秒后保存是否结束、晚到写是否仍发生。
**建议改法：** 将 2 秒预算语义写清：要么规定 ledger writer 在超时后保证不提交并结束其 Promise（并测试撤回/超时），要么 Files 超时后脱离等待并用 operation id/幂等接收与顺序约束隔离迟到写。不能仅以 AbortSignal 宣称硬截止。

### 重要｜正确性｜计划“拥有根的一侧”第 24 行、“服务端”第 27 行；`backend/entry-ops.ts:42-49`、`backend/locked-replace.ts:163-188`
**现象：** `expect: "absent"` 与现有“创建文件”并发时，创建取操作锁，stage commit 取目标写入锁；两者不互斥。计划要求 absent 是条件创建，但 `adopt` 替换目前走普通 `rename`，没有 no-replace 原语或与 `createFile` 共用的提交锁。目标在 `decide` 的 absent 检查后被 `createFile(open "wx")` 占用，后续普通 rename 会以 stage 文件替换它。
**为什么是问题：** 这会把提交检查和副作用分开，违反 `expect: "absent"`“仅当目标不存在才创建”，也可覆盖一个已成功的显式 create；若路径位于内容树，create 与 adopt 还可能分别造成清单状态与正文不一致。现有 Files 对普通操作锁的取舍并未免除每个提交原语本身必须原子满足条件。
**如何核实：** `entry-ops.ts:42-49` 用 `open("wx")` 排他创建；`locked-replace.ts:183-188` 以 stat 检查后调用普通 `rename`；计划把文件操作锁与文件写锁分开。Linux barrier 可在身份复核后、rename 前执行一次 create，验证其文件被覆盖。
**建议改法：** absent 写入采用系统级排他提交/创建原语并保留 stage；若要复用文件操作，明确其交叉锁方案并在提交前重新核实目录身份。为 `create` 与 staged absent 的真实并发加验收，断言最多一个成功且目标字节不被覆盖。

### 重要｜访问控制与合同边界｜计划“项目合同”第 36 行；`shared/contracts.ts:242-251`、计划第 43-46 行
**现象：** `projectFilesContract` 的 `CALLERS` 明确含 `browser`，合同 caller 是整份服务级别限制。计划新增 `stage/commit/discard` 同一项目合同，并只规定“带 `as` 时只接受服务端 `nbook.files`”；`as?` 可省略，因此 browser 可直接调用新阶段方法，和本 Task 服务端写入接口、避免浏览器直用新写入方案的范围不一致。stage 远程返回还包含绝对 `path`。
**为什么是问题：** 远程方法是公开合同入口，不是只能经服务端 façade 到达。照计划，浏览器能直接创建任意目标的 stage token 并取得 staging 绝对路径，也能在后续提交时绕过 Agent 的 `classify`/会话绑定授权；现有 `sourceFor` 只验证请求里确实带了 `as` 的情形，未带则把 browser 当普通用户放行。
**如何核实：** `contracts.ts:242-251` 证明 project/user 文件合同允许 browser；计划第 36 行把 `as` 设为 optional 且仅拒绝“别的调用方带了 as”；`server-files.ts` 只在服务入口做 Agent 权限判断，远程项目入口 `plugin.ts` 的 `implementation(backend, consumer)` 直接按远程身份生成方法。
**建议改法：** 在项目服务端 implementation 明确将 stage、commit、discard 限定为 server 位置的 `nbook.files`（并验证该调用方的 `as`/来源字段）；不以可选来源字段代替 caller 身份校验。若用户浏览器保存继续走旧接口，就不要向 browser 提供这几个方法；也不要把服务端临时绝对路径作为远程输出交给 browser。

### 重要｜取消与资源收口｜计划“服务端：写入接口”第 46 行、“Agent”第 59 行；`shared/resources.ts:18-21,23-32`、`backend/mounted.ts:159-163`
**现象：** `call(ctx)` 需把工具调用绑定到一次操作分组，但计划未说明这个门面如何传播 `ctx.signal`。现有 `ResourceCallOptions` 只在每个方法的可选参数里接受 signal；现有挂载方案只在文件操作开始前查 signal，开始后的操作不被取消。内核 `ToolContext.signal` 在调用 abort 时触发，而 Agent wrapper 在撤回宽限期后可先对工具调用返回，底层实现仍可能继续。
**为什么是问题：** 若工具用 `const at = resources.call(ctx); await at.stage(...)` 而未手动对每个方法传 signal，取消不会触发 stage 的 discard；若 `call(ctx)` 仅绑 group/source 而不绑 signal，就没有任何地方把取消合同落实到 scoped facade。门面被 revoke 后延迟写入会继续产生文件副作用并落在原 group/entry 上。
**如何核实：** `ToolContext.signal` 是每调用的字段；`AgentToolServices.resources` 按会话创建一次，`ResourceCallOptions.signal` 目前由方法调用者逐项传入；计划 `call(ctx)` 新增每调用门面但没列 signal 注入规则；对照 `mounted.ts:159-163` 开始后的动作不因 signal 中途停止。
**建议改法：** 定义 `call(ctx)` 返回的 scoped 门面把 `ctx.signal` 作为默认 signal 注入所有读写与文件操作，显式调用参数不得静默覆盖取消信号；stage 的 sink 与 token 生命周期在 abort/门面释放时立即封闭，迟到 write 必须确定失败且不能再 commit。验收在真实工具执行期间 abort，确认目标不变、token 收口、无迟到事件。
### 重要｜远程失败语义｜计划“服务端：写入接口”第 46 行；`runtime/plugin-channel.md` 输出 90-94、`backend/projects-scheme.ts:55-71`
**现象：** `stage` 自己就是项目合同上的远程写请求：它创建暂存文件与 token 并返回 token/path。帧一旦发出后若断线或 timeout，即使项目端已创建文件，调用方也会得到 `unknown-outcome` 且拿不到返回 token；计划只描述 commit 的 unknown-outcome 比较，没有为 stage 的未知结果提供提交身份、查找方式或可定向 discard 的句柄。
**为什么是问题：** 该暂存文件既不能由调用者提交，也不能按 token 主动删除，只能等 1 小时清理；若 staging token 同时持有项目租约，租约也会在响应未知时失去 owner。按当前 RPC 合同无法把写请求断线解释为 stage 未执行。
**如何核实：** `runtime/plugin-channel.md` 输出 90-94 将已发出的写请求断线/timeout/cancel 全部结算为 `unknown-outcome`；计划 `stage` 的远程分支在第 46 行、项目合同 stage 输出 `{token,path}` 在第 36 行。用 barrier 让项目端创建 stage 后、返回帧到达前断开即可验证调用方无 token。
**建议改法：** 给 stage 设计调用前由服务端生成的稳定 operation/token id，使重试/查询能幂等找回同一 staging 资源；或者把 stage 与数据写入/commit 合并为有明确定义的单一事务协议。未知时不能自动重试创建，也不能依赖定时清理作为正常收口。

### 重要｜接口与可观察行为｜计划“项目合同”第 39 行、“服务端”第 49 行；`resources.md` 操作分组第 37、73、125 行
**现象：** Spec 与已接受提案的 group 有必需 `title` 与可选 `note`；SDK 合同接口明确 `group(info: {title; note?}, …)`。计划事件只写 `{id,title}`，LedgerEntry 的 group 未列 shape，`group(info,run)` 只把“组号与标题”带给 scoped 门面；`call(ctx, {title})` 也没有 `note`。
**为什么是问题：** `note` 会在从用户/API 到事件与 History 的路径上丢失；后续 t13 需要标题与说明做分组展示时，必须再改事件合同、记账合同及已升到版本 7 的项目/用户合同。
**如何核实：** 查 `workspace/resources.md` 术语 37 行、API 73 行和输出 125 行的可选 note，提案接口 `WorkspaceFiles.group` 也含 note；对照计划 39、49、55、59 行的 group 形状。
**建议改法：** 明确 group metadata 为 `{id, title, note?}` 并在 scoped facade、事件 schema、LedgerEntry 与 Agent `call(ctx, {title?, note?})` 间保持同一字段；若刻意不在事件传播 note，写明仅存在 group 元数据/记账项中的哪个边界及原因。

### 重要｜Agent 权限兼容｜计划“Agent”第 59 行；`agent/resources.md` 输出 2、4、5，`packages/neuro-book/src/plugins/agent/resources.test.ts:148-202`
**现象：** 计划说每个 `SessionResources` 方法都在改写后“按第 4 条判权限”。第 4 条限制的是 Agent 写入不可写位置；`classify()` 返回的 `write: "denied"` 不代表读权限也拒绝。当前已有合法行为包括读其它会话的 `session.jsonl`、读 `docs://` 与读虚拟根，同时禁止写入这些位置。
**为什么是问题：** 若照“每个方法都判权限”的字面实现，把 `classify().write === "denied"` 当作方法总门禁，既有合法读取会被拒，违反 Agent 输出 4、5 与当前合同测试；若每个操作分开判断，计划应写明只有写方法检查 `write` 分类，读取沿 Files 的读授权。
**如何核实：** 对照 `resources.test.ts:155-163,184-202` 当前允许读而拒绝写的场景及 Agent Spec 输出 4、5；计划第 59 行要求每个方法均按权限判断。
**建议改法：** 在计划明确“按 operation 判权限”：读/列出/路径解析按方案的 read 授权，只有 write/create/文件操作按 `classify.write` 决定拒绝或审批；保留读其它会话日志、docs 和虚拟根的验收。
