### 1. 跟随模板时，已确定的请求地址仍会被 pi-ai 改写
- 严重程度：阻断；类别：安全与性能。
- 位置：取舍 3、B.1、B.4、切片 B4；`pi-ai/src/providers/openai-shared.ts:270–295`；`docs/specs/models/service.md:29,68`。
- 现象：B.3 按模板／地区的有效地址列模型，但 B.4 仅当用户写了覆盖才退出专用分支。跟随 Moonshot 模板时，`resolveOpenAIRequestSetup` 仍以实时 `$env.MOONSHOT_BASE_URL` 覆盖非空 `model.baseUrl`；Sakana 同样读 `SAKANA_BASE_URL`／`FUGU_BASE_URL`，xAI 还有按凭据改地址的分支。用户选地区而不写 `baseUrl` 也落在这条路径。即使模板表跟着读启动环境，也管不到调用时再读的进程环境。
- 为什么是问题：首轮第 24 条只消掉了显式覆盖一侧。发现、协议检测、缓存身份与实际推理可指向不同部署；带凭据的推理不会因为这是“跟随”而变得安全。B4 的实收测试若只用已覆写实例，会漏掉整类场景。
- 如何核实：沿 `openai-shared.ts:271–295,365–382` 看最终地址和认证头的构造。用两个本机夹具和虚构密钥，在没有 `baseUrl`／`api` 覆盖时配置模板地区及环境地址，分别核对发现、检测和 `ompCall` 的实收端点；再核对启动后环境变化。
- 建议改法：先为每次解析确定允许的线地址，模板／地区与显式覆盖一视同仁。优先让上游接受锁定地址（不必移除几十处 provider 分支）；若暂不改上游，在最内层发出带凭据请求前对照按协议制定的允许地址，不一致则拒绝。不要让目录或运行时环境自行确定另一个目的地。

### 2. 公共重定向包装会让探测和网页工具改变出网合同
- 严重程度：阻断；类别：正确性。
- 位置：B.3、B.6、C.1、C.2；`docs/specs/web/tools.md:69–70,120,144`；`pi-ai/src/providers/openai-completions.ts` 的流式请求。
- 现象：C.1 总是把下游 `redirect` 设为 `manual`、再自行跟随最多 5 跳，未保留调用方禁止跟随的意图。列表明确传 `manual`；探测承诺每种协议恰好 1 次 HTTP；网页工具要求 3xx 原样按 `failed` 结算。这三条路径 C.2 都接同一包装。仅给 `fetch` 传 `manual` 但不阻止外层跟随，夹具回一个 307 就会让一次探测变成两次 POST。对于普通对话，307/308 按标准会保留 POST 正文；只去掉凭据头仍会把对话、工具结果等正文带到另一个源。若换成 GET，又破坏 307/308 的语义。
- 为什么是问题：挂接代理不应改变调用方的请求预算、3xx 含义或正文的授权目的地。只验跨源第二跳不带头不足以守住这些行为。
- 如何核实：经真实 B.6、web-tools 远程检测／Agent 工具和模型 SSE 分别打两个本机夹具。首跳回 302、307，断言探测与网页工具只访问首端点；另验正常对话允许的同源重定向仍可先收 SSE 首帧、再取消，跨源不发模型正文。当前为合同与代码路径核对，未运行未实现的包装。
- 建议改法：出口传输遵守 `Request` 与 `init` 的有效 `redirect`（`manual` 交回、`error` 拒绝）。带模型正文或凭据的请求默认拒绝跨源重定向；仅明确允许的安全请求逐跳重算线路。对同源跟随定下 301/302/303 的方法与头变更、307/308 正文能否重放、丢弃中间响应的正文及整次取消。

### 3. `{provider, api}` 无法隔离同模板、换部署或被路由的历史回复
- 严重程度：阻断；类别：不变量。
- 位置：取舍 3、B.4、切片 B4；`pi-ai/src/providers/transform-messages.ts:522–528,921–948,1059–1085`；`packages/nb-harness/src/kernel/model/omp.ts:183–201,375–377`。
- 现象：首轮第 7 条处置要求原生来源至少记线上 model id，第二稿只存 `{provider, api}`。两家同模板同模型，或同一家从网关 A 改到网关 B 后仍用相同的 `nbook-compatible`／协议，这两个字段完全一样。公开引用能区分同时存在的两家，却不能区分同一实例改址；按旧日志拆名也无法知道地址是否变过。Anthropic 在同 provider 的最近一条历史上会保留签名；路由场景的 `upstreamModel`／实际作答 id 也不等于公开引用的模型 id。
- 为什么是问题：不是字段可选就能兼容。按第二稿字段无法实现“改地址后不还原旧签名”的验收；跨部署复用的签名会被拒绝，并可能把部署绑定的续写元数据带到别处。把 `ModelResponse.model` 改成固定配置引用还会抹掉当前所报的实际作答模型。
- 如何核实：把上述 A/B 两次解析代入 `isSameModelTurn` 与最近签名的分支；沿 `kernel/run/loop.ts:379–388` 看回复是逐字段持久化。用真实 harness 跑签名＋工具多轮，改变地址但不改变公开引用、provider 或协议，再重开旧日志验保守回放。
- 建议改法：分开公开请求引用、实际作答 id 和适配器的续写来源。持久化原生 provider、api、原生模型 id 与不含凭据的实例／部署身份；沿 assistant 事件、折叠历史、`Message`、`toContext` 全链保留。只有能证明同部署才还原专用元数据；不给旧日志凭当前地址补历史身份。

### 4. stencil 的公开取目录接口不交回成功或失败，也不能随插件停止而中止传输

- **严重程度：重要；类别：正确性、不变量。**
- **位置：**技术选型，B.3 `catalog.ts`、`coordinator.ts`、停止，B1/B3；`node_modules/@oh-my-pi/pi-catalog/src/provider-models/openai-compat.ts:167–272`。
- **现象：**计划把 `.json` 中的 ETag、最后一次成功及取消单独交给本地协调器，但选用的 `fetchWellKnownModels(fetch, signal)` 只返回 payload。上游的私有会话按 fetch 函数记 ETag/在途请求；已有 payload 时，503、解析失败乃至订阅者 abort 都会兑现为上一份 payload。调用者的信号只中止等待，真正的 HTTP 请求和解压仍属上游的内部截止时间；重启也不能把本地 ETag 和 payload 交回该接口。
- **为什么是问题：**只按返回值接入会重现首轮 omp 第 23 条的“失败报新鲜”；收到的同一份 payload 无法区分成功的 304、断网和取消。代次护栏能拒绝提交，不能让在途传输按计划停掉。重启后的条件请求也没有计划宣称的磁盘状态所有权。
- **如何核实：**对照 `fetchWellKnownModels` 的 catch、`waitForCatalogRequest` 的 race 与 `fetchCatalogPayload` 读写的 session；影响的是 B.3 的在线目录，不是已改为自有适配器的各家列表。
- **建议改法：**沿用映射函数，不复用此取数函数；本地拥有传输、大小上限、ETag 和 `200/304/failed/cancelled`，或让上游先提供交回这组信息及可取消传输的公开合同。重启后 304、503 保留旧时间、停止时流被关闭分别验收。

### 5. stencil 按裸模型 id 覆盖部署元数据，会填进别家的协议、推理档和价格

- **严重程度：重要；类别：正确性。**
- **位置：**取舍 2，B.2 `api` 注释，B.3 `catalog.ts`，B.4 物化；`pi-catalog/src/provider-models/openai-compat.ts:286–305,2697–2711,7149–7179`。
- **现象：**第二稿按 id 查“在线优先，打包兜底”；但 `mapModelsDevToModels` 的输出带发布者、协议、窗口、阶梯、成本，且没有价时补 `0`。同一个 id 可由多个部署提供，连模型名相同都不意味着服务的窗口、思考协议和价格相同。上游对努力档先按 `provider\0id`，仅所有发布方一致才给按 id 的兜底；Fireworks 单价也明确不能取裸 id 的引用。
- **为什么是问题：**在线更新可以不动本实例配置就把同名模型认成别的协议，或把“价格未知”变“免费”。前者会把可用模型变成发错请求的模型；后者破坏现行用量的 `cost: null` 合同。目录先列成员、后补证据的做法不解决证据用错部署。
- **如何核实：**读映射结果的 `provider/api/cost/contextWindow`，与 `target.ts:157–187` 的 `priceKnown` 对照。验收用两个目录发布方同 id、不同协议/窗口/价格，一行缺价另一行明确为零；身份未知的自定义部署不能任选其一。
- **建议改法：**区分模型族描述与部署事实。协议、地址、窗口、价格和线上的档位只由实例或同部署证据决定；裸 id 仅补有明确一致性规则的提示元数据。映射保留“缺价格”；不把另一个发布方的协议当模板默认。

### 6. 列表缓存身份漏掉有效请求头，换账号后仍可沿用旧账号的成员

- **严重程度：重要；类别：正确性、安全与性能。**
- **位置：**B.3 `listing.ts`、`cache.ts`、`coordinator.ts`；`packages/nb-harness/src/models/target.ts:114–151`；`docs/specs/models/service.md:68,103`。
- **现象：**B.3 用 `requestAuth` 发列表，它会解析服务商任意 `headers`（包括 `env:` 和用户自定的认证头）；但缓存键只列地址、列表协议、认证方式与凭据摘要，未要求纳入最终的有效请求头。当前 `keyOf` 只取 API Key，头由另一条路径解析。地址、API Key 和认证模式不变，改租户/组织头就能得到另一套成员，而旧请求也不因身份变化被取消。截断无密钥 SHA-256 还不能使低熵凭据“不可逆”，会留下可离线比对的指纹。
- **为什么是问题：**首轮 omp 第 6 条修了地址与 Key 的一部分，没隔开同地址、同 Key、不同账号或不同授权范围的列表；重启后也会误信旧成员。两状态根按路径隔离文件，不需要全局锁；也不应共享鉴权指纹。
- **如何核实：**对照 `requestAuth` 两项输出。用假端点对同一个 Key 按自定义组织头交回不同成员，变化前留一个迟到响应；重启后同时检查当前成员与 `retired` 都不跨身份。
- **建议改法：**以规范化后的有效列表请求为身份，包含敏感头的值与缺值状态，不落头原文；需跨重启比对时用状态根独立、受保护的 HMAC 密钥。代次提交校验复用同一个身份，并定义身份失效时哪些诊断/成员可保留。

### 7. “成功空表权威”没有配套的完整分页与落盘提交判据

- **严重程度：重要；类别：不变量、安全与性能。**
- **位置：**B.3 `listing.ts`、`cache.ts`、`coordinator.ts`，B3 验证；`pi-catalog/src/discovery/gemini.ts:98–144`。
- **现象：**计划只说“分页读完”，却没有定义重复游标、下一页失败、包体超限、合法空表与解析失败如何区分。上游 Gemini 循环到重复 token 或 `maxPages` 会 `break` 后返回已读的行；不能拿这类结束算完整。JSON 的提交也只写“串行队列”，没规定崩溃时保留上一份完整缓存；同实例重新添加还可能重用旧名字对应的文件。
- **为什么是问题：**把读到的前缀当完整，后续页上的成员就被移进 `retired`，时间被标成成功；重启后还把这个错误当权威。没结束的游标链还会让自动更新一直出网。直接覆写 JSON 时，即使同一状态根只允许一个服务端，也挡不住半写。按名称分配 id 的新实例不该读到已经删除的上一实例快照。
- **如何核实：**本机端点第一页成功，第二页 503/坏 JSON/重复游标；核对时间、成员、`retired` 与重启结果。再测写入过程中断、删除后同名重建、不同状态根同实例 id；保证旧代次的网络结果不会复写。
- **建议改法：**只有协议声明到末页且每页均有效才发布完整集合；页数、读字节与总截止用作失败预算，不截断成功成员。暂存同目录再原子替换，提交时校验代次，单状态根单写者即可；删实例时撤销发布与缓存，避免同名重建复用上一代。

### 8. `retired` 没有“上一次物化”的可靠来源，也没有保留期

- **严重程度：重要；类别：正确性、不变量。**
- **位置：**B.2“来历决定解析”、B.3 `cache.ts`、B.4 物化，B2/B3 验收。
- **现象：**成员行合同只有 `{id,name?,kind,evidence}`；模型还要与可变的在线目录、打包目录和用户覆盖合成。B.3 在列表成功少了一行时才把它搬到 `retired`，没有规定在哪一次成功时保存什么才能恢复上一次的窗口、协议和兼容字段。静态模板、v1 首次启动无前一份成员缓存；凭据轮换又会丢弃前身份的成员与 `retired`。也没有删掉不再启用、未被任何角色引用的 `retired` 的条件。
- **为什么是问题：**目录补充信息先消失、列表后少了一行时，届时重算已拿不到当时可用的模型；把所有历史列表行永久留着则使缓存随外部目录滚动增长。“来源仍在哪个账号中存在”也不能和“本部署上次用的参数”共用一个失效时机。
- **如何核实：**让一条已绑定的来源模型只从在线目录取得窗口和协议；先换在线目录，再让列表删除该条，随后重启。再分别做 v1 首启、同端点换凭据、换端点和用户移出，观察哪些还能解析以及 `retired` 何时释放。
- **建议改法：**定义不含凭据的最后可用物化快照及写入时机，分开成员的鉴权身份与历史结果的部署身份，不跨部署沿用。指定 v1/静态来源的种子、无历史时的错误，以及按有效启用/绑定/排除清理与存储上限。

### 9. 中性身份不能兑现四种协议的免认证约定

- **严重程度：重要；类别：正确性。**
- **位置：**B.1 `addable`、B.3 列表认证、B.4 中性身份、B.6 免认证探测；`packages/nb-harness/src/models/target.ts:117–137`，`pi-ai/src/providers/google.ts:22–44`。
- **现象：**现有 `requestAuth` 对 `none` 交给 pi-ai 的是内部哨兵 `N/A`。OpenAI 公共请求构造会滤掉它，Gemini 协议不识别：要求 `options.apiKey` 非空且无条件写 `x-goog-api-key`。改为 `nbook-compatible` 也不会走到别的鉴权分支。Anthropic 对哨兵的最终过滤还取决于官方端点和专用分支；不能假定四个协议共用同一语义。
- **为什么是问题：**本地 Gemini 兼容端点可在列表与自建探测中收到无认证请求，但实际对话收到额外的 `x-goog-api-key: N/A`；按有无认证头选择鉴权分支的网关可以拒绝这次对话。把哨兵当真正的库密钥或写进列表头也不符合无凭据合同。
- **如何核实：**`timeout 15s bun /tmp/review-w00032-t43-design-r2/lab/contracts.ts` 以 `buildModel` + `streamSimple` 向本机端点发请求，Gemini 线上实收 `x-goog-api-key: N/A`，流正常结算；未使用真实服务商。并对照 `openai-shared.ts:379–382` 与 `anthropic.ts:4008–4045`。
- **建议改法：**让列表、探测、推理共用按线协议的认证合同；在受控的最后一跳剥离内部哨兵和不应出现的认证头，或明确拒绝不支持的 `none × 协议` 组合。验收断言实收头，而非只看请求达到了服务端。

### 10. v1 归一只处理旧 `api`，仍会把旧运行时忽略的字段激活

- **严重程度：重要；类别：正确性。**
- **位置：**B.2 v1 读法，B.4 物化；`packages/nb-models/src/config/shapes.ts:21–48`、`packages/nb-harness/src/models/target.ts:82–101,157–187`。
- **现象：**v1 schema 允许目录模型写 `contextWindow`、`maxOutput`、`vision`、`reasoning`、`efforts`，但 v1 的运行时目录分支对这些字段全取打包值，只有 `name`、`price` 和另行处理的头、压缩参与；甚至现有快照会显示运行时没采用的值。第二稿把条目改为 `origin: "source"`，只约定丢弃旧 `api`，又用元数据加覆盖 `buildModel`，没有规定不能把上述旧字段当 v2 覆盖；在线目录先于打包还会在首写前改掉同一条 v1 的有效值。
- **为什么是问题：**不编辑设置也会把手写但从未生效的旧窗口、视觉或推理档变成运行参数，改变截断、压缩或图片请求，违反 B2 的“v1 读进来行为不变”。用原值做 `expect` 不会解决值的解释变了。
- **如何核实：**在真实设置场地放一个 v1 目录条目，令手写 `contextWindow`、`vision` 等与打包值不同；记旧版口径的 `ModelInfo` 与实收请求，比较只读后及首写再重启的结果。
- **建议改法：**按 v1 解析而非快照列两个旧形状到 v2 的逐字段映射；规定 v1 未迁移、首写及固定成员各取哪份元数据，并保持 v1 id（角色、日志与凭据都用它）。

### 11. 解冻会删除用户原本显式停用的目录模型条目

- **严重程度：重要；类别：正确性。**
- **位置：**B.2 v1 读法、“关掉自动加入”；验收映射第 245 行；`packages/nb-models/src/core/core.ts:285–296`。
- **现象：**B.2 假定只有 `id` 与 `enabled` 的来源条目都是冻结临时补的。v1 原本就支持只保存 `{id, enabled: false}`（停用，不是移出）；归一后只有 `{id, origin: "source", enabled: false}`。v2 用户在关闭跟随后停用一条来源模型也可能得到完全相同的记录。开关重新打开时按字段形状删除，不能分辨临时材料化与用户的决定。
- **为什么是问题：**往返后可能重新启用此前停用的模型，重新出现在选择器或批量检测，亦违反“已有条目原样不动”的验收目标。`excluded` 表示移出并解绑，不是停用，不能把停用迁到那里代替。
- **如何核实：**把 v1 只含 `id/enabled:false` 的活动目录行读进真实设置；再比较跟随开启及“关→开”后启用位。另测关闭期间手动改过 `enabled` 的条目。
- **建议改法：**将冻结的成员 id 与用户显式启用位/字段覆盖分开保存；解冻只清冻结成员，不删除任何覆盖，历史停用仍可恢复而不改变角色绑定。

### 12. `canDisable` 公式会把“降到最低档”标成“关闭”

- **严重程度：重要；类别：正确性。**
- **位置：**A.1–A.2；`pi-catalog/src/compat/resolve.ts:301–318,1174–1231`；`pi-ai/src/providers/openai-shared.ts:1044–1078,4197–4212`。
- **现象：**`!requiresEffort || suppressWhenOff` 只决定 pi-ai 是否先夹到必选档，不说明线上能关闭。打包 `openai/gpt-5.4` 未标 `requiresEffort`，兼容策略却是 `lowest-effort`；“关闭”实际发 `reasoning.effort:"low"`。反向例：Gemma 4 只有 `high` 一档，仍能发 `MINIMAL` 抑制；“单档固定”和“支持关闭”不是同一维度。未验证梯级也不是通用兜底：该构建只在规则显式 `thinking-unverified` 时生成；无能力证据的中性模型可能没有梯级，`reasoning:true` 的通用回退又可能不标 `unverified`。
- **如何核实：**`timeout 8s bun /tmp/review-w00032-t43-design-r2/lab/responses-off.ts` 的本机端点收到 `/v1/responses`、`reasoning.effort:"low"`（随后夹具按设计回 400，只验证发包）。`lab/contracts.ts` 实收 Gemma 4 的 `thinkingLevel:"MINIMAL"`；`lab/inventory.ts` 打印锁定目录与中性构建的实际字段。
- **建议改法：**把可调档、自动/未证实、有证据的关闭、仅降档区分开；从协议的禁用策略与模型资料导出，未验证试档由本地显式选择且默认不发送。验收加 `requiresEffort` 为空但协议只会降档，以及一档却确能关闭的反例。

- **为什么是问题：**用户会把最低推理档当作无推理；界面与审批/探测的成本、时延判断会据此出错。

### 13. 请求档位没有贯通独立的会话快照；摘要压缩又有两份优先级

- **严重程度：重要；类别：接口、正确性。**
- **位置：**A.2、A.3、A.8、A1/A5、验收映射第 241 行；`kernel/session/session.ts:367–370`、`kernel/session/preview.ts:109–128`、`kernel/run/model-call.ts:159–166`、`kit/compaction/{inplace,summary}.ts`。
- **现象：**A.3 加的是模型服务快照；选择器用的 `SessionSnapshot.model` 成功分支只传 `id/contextWindow/efforts`，没有实际解析的角色、继承档或支持关闭的结果。两个角色可以绑定同一个 id 而有不同默认档，Profile 还可能直接指定模型，因此浏览器不能从模型 id 与角色清单反推出这次解析。预览实际在 `kernel/session/preview.ts` 构造，改 `view/request.ts` 不能给它补解析参数。另：A.2 定义会话档优先，验收却写摘要用压缩角色的档；`ModelCaller` 当前还允许 `ModelDraft.effort`，就地草稿已带原对话请求的档。
- **为什么是问题：**照切片改，选择器“跟随 X”可与实发请求不一致；只在 `ModelCaller` 统一覆写，又会覆盖就地压缩和显式草稿的档，或让对话用了 `off` 的会话测试不到压缩角色。
- **如何核实：**两个角色绑同模型但档位不同，再用直接模型的 Profile；比较真实会话快照、预览、实收请求。另用会话 `low`、压缩角色 `high`、显式草稿档各不同，覆盖就地/摘要和 `complete()`。
- **建议改法：**在服务端按一次解析产出选择来源与有效档，经会话快照同步；把 `turn`、就地、摘要、审批、显式草稿的优先级写成表，并将 `preview.ts` 及会话合同列进切片。摘要以会话档还是压缩角色优先，计划和验收只能有一份答案。

### 14. 探测通过不能代表 Agent 的实际流式协议可用

- **严重程度：重要；类别：正确性。**
- **位置：**B.5 `check`、B.6、B5 验证；`pi-ai/src/providers/google.ts:35–44`、`openai-completions.ts:2222–2241`、`openai-responses.ts:1638–1647`；`research/magpie.md:114–128`。
- **现象：**第二稿另写一套不带推理的短请求，B.6 字面用 Gemini `generateContent`，而推理走 `streamGenerateContent?alt=sse`；代理可只实现前者，或 HTTP 200 后在 SSE 里报错。`max_tokens` 也不是通用字段：Responses 用 `max_output_tokens`，一些 Chat 端点只认 `max_completion_tokens`，Gemini 用 `generationConfig.maxOutputTokens`。只写“省略推理参数”不能阻止 Gemini 服务端默认开推理，某些模型也不允许关闭。
- **为什么是问题：**把 JSON 端点可达当 `check` 通过会误报；也会把参数、模型、鉴权或强制推理约束误认成“协议不支持”。一次请求与不落盘已避开原重试路径，但不能替代成功合同。
- **如何核实：**本机夹具只给 `generateContent` 200、对 SSE 返回 404 或首事件错误；另让 Chat 端点拒绝 `max_tokens` 但接收 `max_completion_tokens`。对比探测结果与实发推理，不调用真实模型。
- **建议改法：**让 `check` 走同一套目标、认证和最小线协议（同路径、流式与首个有效事件），只替换传输为单次、有限读取、不落盘。`detectApi` 若只测基础协议，区分“可达/可生成/不支持无推理检测”，不宣称验证了 Agent；验收加误报反例和出网总次数。

### 15. `detectApi` 没有可传的新凭据，也没有能校验库内换密钥的采纳凭证

- **严重程度：重要；类别：正确性、安全与性能。**
- **位置：**B.5 `detectApi({provider, baseUrl?, model?, signal})`，B.6 采纳与异源凭据；`nb-runtime/src/remote/contract.ts:185–187,284–287`、`json-codec.ts:45–63`；`nb-harness/src/models/target.ts:130–137`。
- **现象：**待测速地址与当前有效地址不同且新地址要求认证时，合同没有一次性凭据或其引用输入；禁止带旧凭据又要求先填密钥，若先用现有 `setKey`，它写到仍指向旧地址的实例，能被后台列表或对话读取。即使探测同源，随后在另一窗口换了库存 Key，设置文件的 `expect` 仍可相等，过期结果可采纳。签名里若将 `signal` 放进输入对象，RPC 不接受非普通对象；链路已有第二参数的取消信号。
- **为什么是问题：**原子写协议和地址解决了首轮的一半；没有安全可达的“先测新地址，再应用”路径，且协议采纳并不绑定实际受测的凭据与路由。
- **如何核实：**A、B 两个本机端点使用不同假 Key；保持 A 现用，先测 B 再采纳，检查 A 没收到 B 的 Key。另在探测返回和点采纳之间从第二窗口换库存 Key；校验设置不变时采纳仍被拒。用真实 RPC 的 `method(input,{signal})` 断开在途请求。
- **建议改法：**定义仅本次使用的新认证输入/安全草稿，或异源必须先显式保存新地址再测并删掉矛盾承诺；保存/校验受测地址、协议、模型及有效鉴权代次等，不回传密钥；`signal` 放 RPC 调用选项。

### 16. 批量检测仍允许重复扣费，且没有单批与全局的出网预算

- **严重程度：重要；类别：安全与性能。**
- **位置：**B.5 `checkAll({provider, ids})`，B.6，B5 验收；`packages/nb-models/src/contract/settings-spec.ts:83–84`，`docs/specs/runtime/plugin-channel.md:85–94`。
- **现象：**确认时发送 id 修掉了“名单变大”，每实例并发 4 也挡住同一实例的两个窗口，但计划没要求唯一 id、批次总截止/位数或服务端总限额。8 个实例各有 4 条可同时出网；若批次逐项用 15 秒、600 项全到截止，单批占用可达 37.5 分钟。沿用 `effect:"read"` 时，RPC 断开/超时后合同承诺可重试；下游接收后取消不能撤销已经计费的请求。
- **为什么是问题：**“每协议一次”限制单项，不限制重复 id、重试或多实例造成的实际账单。长队列取消若只给 RPC 的 `cancelled`，调用方分不清已发与未发，不能安全全量重试。
- **如何核实：**同一批重复 id、不同实例同时发、RPC 取消/断开后重试三个场景，用本机端点数实收。量总预算、实际未开始项与已开始但结算未知项；不跑长达 37.5 分钟的试验。
- **建议改法：**名单去重并校验受测版本，定义单批数目/截止、全局与实例并发预算，超预算拆批而不偷偷扩大确认范围。把可计费的检测标成不能盲重试的操作，或给稳定操作 id 与逐项结算，让取消或断线能读回结果。

### 17. 混合协议模板没有一个可同时供列表、探测和推理的“有效地址”

- **严重程度：重要；类别：正确性。**
- **位置：**B.1 模板默认、B.2 `api/baseUrl`、B.3 列表、B.4 物化；`pi-catalog/src/provider-models/openai-compat.ts:3271–3283,3321–3367,3393–3410`。
- **现象：**模板记录给一个默认地址，列表按实例的有效协议与地址发，推理协议又可逐模型跟目录。以当前已打包的 OpenCode Zen 为例：列表为 `https://opencode.ai/zen/v1/models`；Anthropic 基址是 `/zen`，Chat 和 Responses 是 `/zen/v1`，一个 Gemini 目录条目是 `/inference/google/v1beta`。上游还为列表传 `x-opencode-session`、按不同模型钉路由，不能只用“有效推理协议”决定列表协议。自身是 `fetch` 也不是对话准入：同一个模板还列 `typesafe` 等非对话协议。
- **为什么是问题：**按第一条模型或模板默认地址统一物化会破坏现有逐模型请求；反过来按选中的 Anthropic 或 Gemini 模型走那个协议做发现，会请求错列表。静态模板也没有写清 `refreshModels` 的 `not-supported` 回法。
- **如何核实：**`lab/inventory.ts` 读锁定目录并打印 `opencode-zen`、`commandcode`、`openrouter` 的实际 `(api,baseUrl)` 组合；对照目录工厂的 `discoveryBaseUrl` 与逐模型 `resolveApi`。验收一份混合模板同时测试各路推理和独立列表，再测显式协议覆盖。
- **建议改法：**模板分别声明已支持的对话路由、独立列表路由/必需头及静态回法；显式协议/地址覆盖后按清楚的通用规则重新绑定两者。不能在三种适配器兑现的就声明静态，手动刷新回 `not-supported`，不猜路径。

### 18. 只改 `package.json` 不会抬高实际发布和启动时的 Bun 门槛

- **严重程度：重要；类别：正确性、验证。**
- **位置：**技术选型、C.1、第 C1/C4 片；`packages/neuro-book/src/shared/product.ts:29–30`、`src/cli/run.ts:170–175`、`scripts/pack-app.ts:278–288`、`desktop/src/bun/index.ts:665`；`pi-catalog/package.json:99–101`。
- **现象：**C.1 只写抬 `packages/neuro-book/package.json` 的 `engines.bun` 至 `>=1.4.3`。发布包的 manifest、随包说明与 `nbook` 启动检查读取另一个 `BUN_ENGINE`（当前 `>=1.3.14`）；桌面走 Electrobun 的 `process.execPath` 启动 `server/main.js`，绕过 CLI 检查。锁定的 `pi-catalog` 还声明 `>=1.4.4`。这些不是 `bun 1.4.4` 开发机过代理用例能覆盖的。
- **为什么是问题：**旧 Bun 可以通过发布门禁却没有已验证的按次强制直连语义；在“直连”与隐私边界上不能以运行时碰巧支持为依据。桌面随包的版本也不会因修改 manifest 自动变化。

- **建议改法：**门槛以实际依赖和传输要求的较高者为准，改共享常量和 manifest；托管入口或桌面打包须同样把关，不满足则升级随包 Bun 或拒发该产物。

### 19. 仅用 Gemini 的生成方法判对话会收进图像模型，列表还丢了可用的窗口证据

- **严重程度：重要；类别：正确性。**
- **位置：**B.3 `listing.ts`、B.4，决定 2；`pi-ai/src/images/google-generative-ai.ts:65–88`；`pi-catalog/src/compat/rules/providers/google.kdl:25–29`、`src/discovery/gemini.ts:183–206`；`kernel/compaction/compact.ts:60`。
- **现象：**Gemini 的图像传输也调用 `:generateContent`，打包目录明确把 `gemini-3.1-flash-lite-image` 列为 `image`。`supportedGenerationMethods` 只能证明端点提供方法，不证明它输出对话文本。另一个方向，B.3 的成员行只给 id、名称、分类与证据，B.4 物化只列在线/打包元数据与实例覆盖；Gemini 列表现有 `inputTokenLimit/outputTokenLimit`，OpenRouter 有 `context_length`。不定义如何保留，新的确认为对话但不在目录的模型缺窗口，物化为 0 后内核的自动压缩触发点是无穷大。

### 20. `proxy-unsupported` 没有穿过模型和网页工具的错误合同

- **严重程度：重要；类别：接口、正确性。**
- **位置：**C.1–C.2，B.3 列表失败；`packages/nb-harness/src/kernel/model/{omp.ts:356–383,classify.ts:14–29}`；`packages/neuro-book/src/plugins/web-tools/backend/providers/http.ts:145–155`。
- **现象：**计划承诺发现系统代理是 SOCKS/PAC 时“请求失败并给 `proxy-unsupported`”。`fetchFor` 只能抛出一个错误，现有 `ompCall` 将流错误变成通用 provider 错误，现有网页工具直接把未取消的 fetch 异常归到 `unreachable`；B.3 的列表失败分类也没有该码。只把全局 `fetch` 替换掉不会把失败原因传给调用方。
- **为什么是问题：**用户收不到“改用 HTTP 端口”的处置，可能把配置错误当服务商离线；模型上层也无法基于机器码阻止不必要的重试。系统读取失败与无配置既然有区别，也必须在这些入口可观察，不只是网络页摘要里有区别。
- **如何核实：**`timeout 8s bun /tmp/review-w00032-t43-design-r2/lab/proxy-error.ts` 在独立进程用会抛 `code:"proxy-unsupported"` 的传输替身走现有 `ompCall` 与真实 pi-ai；传输调用一次，结果只有 `{kind:"provider",message:"lab transport refused the proxy"}`，未联网。网页工具的归类由代码确认。实施验收应喂 SOCKS/PAC 系统样本，经实际入口分别请求模型、列表、探测、网页工具，断言没有实际连接且结果带各自合同约定的原因。
- **建议改法：**出口在边界交出类型化失败，并在每个调用栈显式映射。若 pi-ai 擦除错误码，在本地请求包装中记录有类型的选路失败、在适配器最终结算时优先交出，或在入适配器前做可复核的预检；不按错误文字补猜。

### 21. “测试代理”可能只测到直连，却把出口 IP 当作代理已生效

- **严重程度：重要；类别：正确性。**
- **位置：**C.1 `describe()/test()`、C.2 远程合同，决定 16；首轮处置接受 `NO_PROXY` 仍可绕过显式代理。
- **现象：**`describe()` 没有目标参数，只返回一项 `origin/source`；同一份系统配置可以让 HTTP 走 A、HTTPS 走 B、旁路主机直连。`test()` 没写测试目标、结果的线路证据或旁路时的结算。已知 Bun 即使设置显式代理也会因 `NO_PROXY` 绕过；此时回来的 IP 和耗时都正常，但并未测试代理。不能把本机/私网必走直连的地址用于证明代理通，也不能只比较出口 IP 判定是否走代理。
- **为什么是问题：**用户会用这条结果确认是否经代理出网。网络页作为应用数据读取配置的摘要，不能替代对实际请求的判定。测试目标还决定会向哪方交出来源 IP。
- **如何核实：**向本机两个端点分别布置直连与代理夹具，明确选一个理论可代理的目标，再让这个目标匹配 `NO_PROXY`；检查代理侧实收从 1 变 0、页面后端结果不说代理正常。另测超时、非预期内容及设置变更后的重新测试。无需请求公网 IP 服务。
- **建议改法：**摘要返回按目标生效的规则，或注明代表的目标；定义固定、对用户可见的探测服务与小型响应上限。测试交回明确“走代理／已旁路／未验证线路”及依据，不加未经确认的公网直连对照；如不能证明实际走了代理，就只验可达与耗时。

### 22. 只分页管理列表，启用清单和冻结设置仍会超过 1 MiB 合同

- **严重程度：重要；类别：接口、安全与性能。**
- **位置：**B.2、B.5、B7 验收；`packages/nb-models/src/contract/settings-spec.ts:87–88`；`packages/neuro-book/src/plugins/settings/shared/contracts.ts:96–99,118–119`；`docs/specs/runtime/plugin-channel.md:117`。
- **现象：**图标不进设置、`providerModels` 分页，解决了首轮的两个直接增长点；但启用清单仍全量交给选择器。默认全启用时清单和所有对话来源同阶。`lab/inventory.ts` 合成 8 家每家 600 行，只取 B.5 规定的 id、名称、组、能力、窗口、单价，数组已是 1,375,381 字节，超过 1,048,576 字节，尚未计 RPC 外壳；这是合成上界反例，不是线上断开实测。冻结和排除还会把来源 id 写回整份 `settings.json`，设置编辑器 `writeText` 不经过模型分页，入站硬上限仍在。
- **为什么是问题：**量了才决定是否改，不能兑现“全量启用不设阈值”。`offset` 也不能跨刷新稳定翻页；在两页之间插入成员，下一页可重复或跳过 id。
- **如何核实：**真实 WebSocket 测 `snapshot/changed/重连`、大批冻结或排除后的设置全文读写；测跨来源代次翻页与单条异常长的 id/名称，按 UTF-8 线字节而非行数断言。不把合成行的字节数当实际出站结果。
- **建议改法：**先定单帧字节预算、带代次的分页/变更提示和超限回法，启用清单同样受约束而不是截掉已启用模型。设置全文走现有大对象传输模式或给出独立可恢复的超限合同；用最大有效输入验收，不只量 8 个固定目录。

### 23. 内容寻址图标缺少上传到绑定之间的事务与回收规则

- **严重程度：重要；类别：不变量。**
- **位置：**B.5 `setIcon`、B.7，决定 20；`docs/specs/settings/configuration.md:197–198`；`packages/neuro-book/src/plugins/bots/backend/avatar.ts:30–68`、`plugins/stickers/backend/routes.ts:96–172`。
- **现象：**`POST` 写文件，另一次 `setIcon` 才写引用。上传后取消、断线或设置 CAS 失败，不会触发“删服务商或换图标”的回收。两家传相同图片或复制服务商会共用同一个摘要；窗口甲删最后一条已提交引用时，窗口乙可能持有同一摘要的待绑定上传。只按已提交引用删除会让乙保存成功却得到 404。头像参照只涵盖 GET，并没有处理这两步的事务、上传并发和限流。
- **为什么是问题：**单文件 256 KB 的上限不限制暂存文件总量；通过快照、手编设置或部分成功还会产生持久的悬空引用。决定 20 写的是内联 ≤48 KB，换成文件是合理的候选，但回收与备份行为不同，应把实际取舍写回决定。
- **如何核实：**两窗口上传同一内容，在其中一家换图或删除时让另一家绑定；另测上传后取消、写入冲突、断线与重启，读取引用及目录。分别断言 GET 404 的只是真正不存在的资源、可达文件不删、未绑定文件按期收口。
- **建议改法：**优先一个带版本的上传并绑定操作：有界收包，写完并原子发布内容文件，再 CAS 设置；切勿先提交引用。若保留两步，定义有期限的暂存令牌及总预算，回收以当前可达性与在途绑定为准，允许宽限期，覆盖取消/冲突/重启；把引用和图标文件一起纳入状态根备份说明。

### 24. 在计数与记录之下跟随重定向，会少记实际 HTTP 尝试

- **严重程度：重要；类别：不变量。**
- **位置：**B.4 `OmpTarget.fetch`、C.1–C.2；`packages/nb-harness/src/kernel/model/omp.ts:294–300,366–373`、`wire.ts:42–58`；`docs/specs/harness/models.md` 输出 10、20，`docs/specs/agent/request-trace.md` 输出 1。
- **现象：**把 `fetchFor()` 接成 `observedFetch` 的下层时，适配器按上层调用计数，一次调用内 302/307 再接 SSE 仍只计 1 次。记录器只看得到首个 URL、请求头/体和最后一个状态码，也看不到跳转后真正送出的头。这在限制为同源跳转后仍然成立，和第 2 条中“本来拒绝跟随的调用方”是两条不同路径。
- **为什么是问题：**请求记录会把首地址和末响应拼成一条从未发生的 HTTP 交换；多次尝试还会被算成 `Usage.complete: true`，与现行合同不一致。现行 Bun 自动重定向也没有逐跳观察能力；新包装自己控制跳转后，不该继续把这个盲点当成功。
- **如何核实：**同源夹具首跳回 307，第二跳发 SSE，按服务端实收对照记录里的尝试数、状态、URL 与 `complete`。若策略禁止跳转，应只看到首个实际 3xx 与一次尝试。
- **建议改法：**模型请求不跟随，或让观察与计数落在逐跳发送处；每跳按同一遮盖规则记录，明确代理握手不算模型 HTTP 尝试，补请求记录与用量合同的实收用例。

### 25. 已解析的旧端点可以在真正发送时读到新端点的密钥

- **严重程度：重要；类别：不变量、安全与性能。**
- **位置：**B.3 配置代次、B.4 地址锁定，B4 验收；`packages/nb-harness/src/models/target.ts:82–107,130–137`；`packages/nb-models/src/core/core.ts:68–97`；`kernel/run/model-call.ts:120–135`。
- **现象：**列表结果有代次护栏，但推理持有的 `buildResolution` 闭包冻结了旧模型、旧地址；真正调用时又从同一个实例 id 现读库存 Key。当前调用链在解析和发包之间可等待压缩、拦截、日志与附件。其间把实例从 A 改到 B 并写入 B 的 Key，旧解析仍可向 A 发送 B 的 Key。清解析缓存只影响下一次 `resolve()`，不会撤回已交出的闭包。这是既有时序，模板实例都可换端点后影响面更大。
- **为什么是问题：**最后一跳“地址与此次解析相同”仍会通过，但该密钥已经不属于此次解析的地址；与第 1 条的 pi-ai 改址无关。密钥清除后不应发包的现行保证也不能靠永久捕获密钥来换取。
- **如何核实：**实际 harness 在模型拦截器处暂停已解析的请求，用第二窗口变更地址与测试密钥后放行；观察两个本机端点均未收到错配凭据。另验只换同部署密钥、清除密钥与已发流的结算。
- **建议改法：**把允许的部署与鉴权范围绑到解析快照，发包前再校验双方仍相容；异部署则拒绝旧解析并要求重新解析，不在已构造的上下文中偷偷改投。与列表复用代次定义，区分同部署换密钥和跨部署换密钥。

### 26. OpenRouter 的公开发现不能沿用推理端口的缺密钥判据

- **严重程度：重要；类别：正确性。**
- **位置：**B.1 模板能力、B.3 `listing.ts`；`packages/nb-harness/src/models/{catalog.ts:74–85,target.ts:117–137}`、`pi-catalog/src/compat/rules/providers/openrouter.kdl:3–6`，Task 调研第 49 行、决定 2–3。
- **现象：**OpenRouter `/api/v1/models` 支持无密钥；上游将 `allow-unauthenticated` 放在 discovery 规则，现有 `providerAccess("openrouter")` 对推理仍返回 `key`（本轮 Bun 只读探针）。B.3 直接沿用实例的 `requestAuth` 并列出 `no-credentials`，没区分“发现可匿名、推理要求密钥”。如果把整个模板设成 `auth:"none"` 来补，又会让推理走错认证路径。
- **为什么是问题：**刚添加 OpenRouter 即自动拉取是 Task 明列的起点；未填 Key 就停下来，会保留第一稿被指出的不可发现体验。反过来，不能把捕获到的匿名成员当成有权限推理的证据。
- **如何核实：**本机只读 `providerAccess("openrouter")` 返回 `key`；源码的 discovery 声明为可匿名。用假端点模拟：添加但不填 Key，应实收无认证 GET；已能显示来源成员，角色仍为 `no-credentials`。再填 Key 并验证新身份；显式改到要求认证的兼容部署时不继承官方匿名特例。
- **建议改法：**模板分别声明列表与推理认证，明确哪些部署／路由可匿名，把匿名与已认证的列表身份隔开；不给本地传输哨兵出网。用添加及填密钥的真实 RPC 验收两阶段。

### 27. 模板合成放在 nb-harness，会反向依赖不发布的 nb-models

- **严重程度：重要；类别：不变量、包边界。**
- **位置：**B.1、切片 B1；`packages/nb-harness/package.json:1–17,47–58`、`packages/nb-models/package.json:1–5,21–24`；ADR 0045 决策 2、4。
- **现象：**我方模板表放 `nb-models/src/config/templates.ts`，合成函数 `listTemplates()` 却放在 `nb-harness/src/models/templates.ts`、描述为直接合并这份表。现有依赖只有 `nb-models → nb-harness`。若按这两个落点直接引用，要么反向引私有包、形成依赖环，要么在打包前偷读别包源码；当前计划没有声明注入边界。
- **为什么是问题：**`nb-harness` 是独立发出的源码包，`nb-models` 是不发布的工作区包。开发机能解析，不表示 npm 消费者能解析；切片 B1 也不能隐含修改 ADR 确立的依赖方向。
- **如何核实：**对照两包 manifest 的 `private/dependencies/exports` 及 ADR。实现后验证 nb-harness 对外入口不依赖应用或 nb-models；在产物边界验证模板读取，而非只在拥有完整工作区的样例验证。
- **建议改法：**nb-harness 只交出 OMP 的基础目录与协议能力；我方表和合成函数放同一上层，通过公开入口取上游数据。若表由应用决定，传数据给模型核心，不让基础库读模型服务或 UI 资产。

### 28. A 已改变严格 RPC 合同，版本切换却排到 B

- **严重程度：重要；类别：接口、兼容。**
- **位置：**A.3、A2/A7、B.5；`packages/nb-models/src/contract/{settings-spec.ts:60,87–91,shapes.ts:66–76}`；`docs/specs/runtime/plugin-channel.md:49–55`。
- **现象：**A 单独合入，已把 `setRole` 的必填 `model` 变成字段补丁，并给快照及 `changed` 增字段；现有旧快照 schema 是 `additionalProperties:false`。A 客户端只写档发给未更新服务时过不了输入校验；旧客户端接 A 的扩展快照过不了输出校验。B 写了升到 v2，A 没定义自己的版本转换。设置文件可读 v1 与 RPC 兼容是两件事。
- **为什么是问题：**不同时升级的提供方和调用方仍宣称同一个协议版本，失败变成无效输入或输出，而不是明确的 `version-changed`。单跑同版本服务和浏览器的回归不会暴露这个切片边界。
- **如何核实：**用 A 前后的合同定义，经真实链路向两边分别发档位补丁、取快照并订阅；断言同版本可用，不同版本得到定义好的刷新/拒绝结果，已存设置不被改写。
- **建议改法：**把 A 的 RPC 切换放进 A2，同步迁完 `nbook.models/settings` 的调用方并更新 Spec；B 的破坏性改动另升版本。若坚持只升一次，重排独立交付边界，或在 A 保持真正向后兼容的合同，不能只把字段写成可选。

### 29. 图标上传只验魔数，不能保证是可显示的静态小图

- **严重程度：重要；类别：接口、资源边界。**
- **位置：**技术选型、B.7、切片 B5；`packages/neuro-book/src/shared/image-type.ts:13–26`；首轮前端第 17 条处置。
- **现象：**第二稿只写 256 KB 输入与 `sniffStillImageType`，没有落实原处置的 64 像素成品。该函数只按魔数排除 GIF。本轮临时样本中，213 字节、两帧的 APNG 返回 `image/png`，只取开头 8 字节也返回 `image/png`。这是对拟复用函数的实测，不是未实现的上传路由实测。
- **为什么是问题：**只做这项校验就能保存坏图或动图；文件字节上限也不是浏览器的解码像素上限。图标在每个选择器反复使用，不能依赖上传页面预处理来守服务端合同。
- **如何核实：**在 `lab/` 用 `bun -e` 调实际 `sniffStillImageType`，已得到 `213 true image/png image/png`（`true` 表示有 APNG `acTL` 块）。实现后经真 POST 对截断 PNG、动图和小文件大尺寸分别断言结果及 GET 成品。
- **建议改法：**确定静态成品合同；保留魔数判定作为入口预筛，另有界地校验格式、尺寸与动画，拒收不符合的输入或规范化为静态小图。把输入流大小、成品尺寸与输出字节分开验收。

### 30. 等插件停止才取消目录刷新，已经晚于 HTTP/RPC 排空

- **严重程度：重要；类别：时序、验收缺口。**
- **位置：**B.3 停止、B.5 `refreshModels`／`refreshCatalog`、切片 B3；`docs/specs/runtime/server-host.md:77–85`；`packages/nb-host/src/server/host.ts:128–143`、`packages/neuro-book/src/plugins/models/backend/plugin.ts:36–41`。
- **现象：**B.3 写的是在插件停止时取消在途刷新、再等收尾。宿主先封接纳并等两路排空，各限 20 秒，之后才关闭模型入口并释放核心。若“重新拉取”RPC 等实际网络完成，目录端点收了请求但不发完响应时，RPC 会拖到排空超时才轮到这项取消。B.3 没有给列表全程截止；如果 RPC 只启动任务就返回，计划也未定义如何交回最终失败。它与后台自动刷新不能共用同一个没有区分的停止规则。
- **为什么是问题：**按既定宿主时序，正常退出可能被记成关闭未完成。反过来若在封接纳时把写入队列一起清掉，又违反已接纳写入应结算的合同。
- **如何核实：**真实宿主里让假列表端点进入“响应体一直不结束”，通过 RPC 手工刷新，同时放入一个已接纳的设置写，再发停止。核对调用结算、端点是否收到了取消、是否触发 20 秒门限，以及关闭缓存前是否还有提交。
- **建议改法：**写清手工刷新是等结果还是返回任务；前者给请求体读取与全部分页共用的截止并接入停止信号，后者用事件结算。停止时先封新的网络任务并撤销可取消的刷新，保留已接纳的持久写入结算；将停机夹具列入 B3，而不只验代次丢弃。

### 31. 角色设置从 A 就不能安全降级，发布说明却没排进这一段

- **严重程度：重要；类别：兼容、发布。**
- **位置：**A.2–A.3、Spec 与文档表、A2/A7 与 B2/B7、决定 23；`packages/nb-models/src/config/shapes.ts:50–61,77`；`docs/specs/settings/configuration.md` 输出 4；`docs/standards/releasing.md:14–18`。
- **现象：**A 单独合入、写出任一角色的 `effort` 或 `icon` 时，A 之前的设置 schema 已会丢弃整个角色键。用当前锁定的 TypeBox 对有绑定的五角色数据实测：原值 `true`，只给 `main` 添 `effort:"low"` 或 `icon:"bolt"` 都为 `false`；读取该键的默认 `main.model` 为 `null`。不是到 B 的服务商迁移才出现降级破坏。计划把降级归到 v2 迁移，没有列决定 23 要求的应用发布说明，也没给 A 写入的独立边界。
- **为什么是问题：**用户在 A 改过一档，退回旧版时主力绑定和其他角色同时消失；旧程序再写此键还可能覆盖新值。只读取未改写的旧设置、写过 A 的角色设置、写过 B 的服务商设置，是三个不同的恢复情形。
- **如何核实：**已用现行 `RolesSchema` 验证形状；实施时让 A 写一次档、B 写一次服务商，再分别用 A 前与 B 前的真实设置读取，检查各自丢弃哪些键；不要求加降级保护。
- **建议改法：**A 和 B 分别在写出新数据的切片同步更新兼容节与应用 `CHANGELOG.md` 的「数据与升级」；描述触发字段、最早不能退回的版本及未写入时无迁移，不把两段都归成“升级后一定丢”。

### 32. 原值 CAS 会把 schema 拒绝的键当成“不存在”，首写仍能覆盖坏条目

- **严重程度：重要；类别：数据兼容、不变量。**
- **位置：**B.2 的“单个坏条目……不当成空数组写回”、切片 B2；`plugins/settings/shared/layer-text.ts:41–65`、`instance.ts:213–219`、`layers.ts:38–42`；`plugins/settings/backend/layer-owner.ts:198–218`；`plugins/models/backend/settings-store.ts:24–33`（均在 `packages/neuro-book/src/`）。
- **现象：**语法正确但有一条服务商不合 schema 时，整层仍为 `ok`，设置服务丢弃该键并列为 `problems`，`inspect(...).user` 只看到无值。核心以空数组作首写基底，`expect.present:false` 比的是已经过滤的 `parsed.values`，即使磁盘上仍有整个键也会通过。用现有解析、比较与文本编辑三函数的本轮探针得到 `status:ok`、`invalid-value`、`absentExpectPasses:true`，替换结果为 `{"nbook.models/providers":[]}`；没有真的写设置文件。
- **为什么是问题：**“比较归一前原值”保护的是合法 v1 数据，不保护被 schema 丢弃的原值；添加服务商的正常首写即可覆盖含坏项的整组有效配置。只测坏 JSON 会误判安全，坏 JSON 走的是不同的 `layer-invalid` 分支。
- **如何核实：**真实设置场地写两条服务商（一好一坏，JSON 合法），分别在启动前和 RPC 提交前破坏一条，再从应用添加实例；断言拒绝写入且原文逐字节不变，修好后可写。对照真正没有键时能创建。
- **建议改法：**区分缺键和键存在但被拒；在落盘锁内核对原文存在性与校验结果，模型场地拒绝对此坏键的首写或重试，引导用户修设置。允许用户在全文编辑器显式修复，不给业务写默默清理旧数据的权力。

### 33. B 开始后台联网，但控制自动更新的设置要到 C 才登记

- **严重程度：重要；类别：切片依赖、用户控制。**
- **位置：**B.3 `coordinator.ts`、B.5 `refreshCatalog`、C.2 `catalogAutoUpdate`，切片 B3/C2，决定 3、24；`docs/specs/settings/configuration.md` 输出 1、4、11；`packages/neuro-book/src/plugins/settings/shared/layers.ts:139,149`。
- **现象：**B 已承诺根据开关决定启动后台刷新，并单独合入；开关的声明、缺省值和拥有者却只在 C.2。B 独立运行时，不登记就不能通过设置服务写；用户手改同名键也不进入有效值。反过来，B 依赖 C 才提供的 `networkKey` 则无法在 B 独立装配。差的不只是页面入口。
- **为什么是问题：**B 安装后会开始新的后台出网，而用户没有生效的关闭途径；关过再重启保留偏好、关闭仍允许显式刷新都无法在 B 验收。当前 B3 验收只写按身份更新，未覆盖开关所有权。
- **如何核实：**仅装 A+B，预置用户层关闭自动更新、缓存过期，启动后向本机假目录断言 0 次自动出网；手动更新仍收到一次；再启用并重启。C 合入后同一个键仍有效，不要求用户重设。
- **建议改法：**由模型服务的描述在 B 声明并消费唯一的开关键，B 验收实际设置的读写；C 的网络页只展示同一项，出网服务按 C 的边界替换。若产品要连同开关一起延后后台更新，就显式重划 B 的可交付范围。

### 34. 批量检测的失败明细能在一条响应里超过 1 MiB

- **严重程度：重要；类别：接口、资源边界。**
- **位置：**B.5 `checkAll({provider, ids})`、B.6 原文截断、B5/B7；`packages/nb-models/src/contract/{settings-spec.ts:83–84,shapes.ts:108–112}`；`docs/specs/models/service.md` 输出 11；`docs/specs/runtime/plugin-channel.md:117`。
- **现象：**现有 `checkAll` 一次交回所有项，每条失败可带约 8 KB 原文。第二稿只改输入名单与并发，没有替换结果传输。按现有结果形状合成 ASCII 原文并量 UTF-8：128 条已达 1,058,835 字节；600 条为 4,963,691 字节，均不含 RPC 外壳。一家 600 个模型用错密钥或碰上统一网关错误即可让多数项同样失败；这不是线上断链实测。
- **为什么是问题：**即使按第 16 条限制并发，和第 22 条把目录分页，都不能交付已发生的检测结果。用户最需要诊断时可能只看到掉线，再做一遍又产生出网。
- **如何核实：**真实 `checkAll` 经 WebSocket 检测超过 128 个模型，假端点回长错误；断言链路不掉、所有项都能结算、失败原文仍遮盖。补 Unicode 与 JSON 转义使字节超出字符数的输入。
- **建议改法：**在批量接口中记录有界摘要，详情按项读取，或按字节分页交付结果；按编码后的字节给一条消息留出外壳预算，不把并发限制当帧大小限制，也不把失败原文砍短到不可诊断。

### 35. 只查目录无法自动加入采用本地别名的对话模型

- **严重程度：重要；类别：正确性、决策落地。**
- **位置：**B.1 本机模板、B.3 `listing.ts`、B.8 `unknown` 不自动加入，决定 2；`packages/neuro-book/src/plugins/models/models.test.ts:24–41,295–307`。
- **现象：**OpenAI 兼容列表允许只给 `id`。现有本机夹具的 `/models` 正是这种形状，`qwen3:8b` 可走实际 Chat 流；本轮用锁定的 `listCatalog()` 查这个 id，匹配为 `[]`。vLLM 等还可把对话模型暴露为本地任意别名，在线目录也不能靠公开名称识别。这类列表按照 B.3 只能标 `unknown`，因此可能添加成功却没有一个启用模型。
- **为什么是问题：**与 Gemini 图像被误启用的第 19 条相反，这里丢掉真实可用的会话模型。“加入全部对话模型”与“不自动启用未知项”没有共同的分类证据时不能同时承诺；把所有 `/models` 行默认作对话则会重引首轮问题。
- **如何核实：**扩展现有本机端点：同一列表只给一个可流式对话的私有别名和一个 embedding 别名；不预注入目录，查看添加时的来源分类、可启用状态，最后走一轮对话确认结果不是用假目录推出来的。
- **建议改法：**先利用该部署可靠提供的类型／能力字段；只有 id 又没有可信证据时，明确哪些能由用户补证并启用，把“全部”限定为能判定的对话模型。若要主动探测补证，要另定授权、限额和结果合同，不能为分类偷偷跑整表生成。

### 36. “跟随系统、没有代理规则”不能把空决定交给 pi-ai 或 Bun

- **严重程度：重要；类别：接口、选路。**
- **位置：**C.1 按次选路与 C1 验收；`pi-ai/src/utils/transport-fetch.ts:25–42`、`utils/proxy.ts:134–175`。
- **现象：**C.1 明写 `direct` 时设 `proxy:false`，但没有定义 `system` 找完启动环境和 OS 都没有规则时，是否仍重写已有 `init.proxy`。上游在调用注入的 fetch 前可能写入 `PI_PROXY_<PROVIDER>`／`PI_PROXY`；`withProxyInit` 用真值判断已有 `proxy`，连上游传入的 `false` 也能被替换。本轮用真实 `transportFetch` 搭捕获函数，设置虚构 `PI_PROXY` 后，无 `proxy` 与预设 `false` 两种输入都收到同一个代理 URL；没有连接目标。
- **为什么是问题：**如果空决定只是原样调用 Bun，会跟随 pi-ai 暗中附加的代理或 Bun 进程环境，模型和不经 pi-ai 的列表／网页工具线路不同。只测显式 `direct` 不能证明默认 `system` 为空或旁路时没有继承。
- **如何核实：**系统读法返回“未设置”、启动代理环境为空，但子进程设虚构 `PI_PROXY`；在真实 `ompCall` 的末端验证，并由本机目标和代理分别数连接。再验某目标命中旁路、另一个有明确系统规则，不将捕获 `init` 的探针当线路实测。
- **建议改法：**出口选择给出互斥的直连／代理／错误三种结果；空规则与旁路也产生明确直连，并在最终 Bun 入口统一覆盖 `init.proxy`。Bun 的 `NO_PROXY` 对显式代理仍然生效这条已接受限制不变。

### 37. 逐段合入会让当前 Spec 与实现脱节，收口也没验文档证据

- **严重程度：建议；类别：实施计划、文档。**
- **位置：**计划第 15 行、Spec 与文档表、切片 A7/B7/C4、验收映射第 237 行；`docs/specs/README.md:323–346`。
- **现象：**计划把 Spec 放主工作区改、实现放三段各自分支；现有 `models.service` 等是 `implemented`，不能在代码未合入时就把将来的形状和行为改成现行合同。反过来，实现先合入也会留一段错误的合同。表只把新 `network/egress.md` 标为 `planned`，未安排在 C 验收后写入实现入口／合同测试／Smoke 和同步索引；各段收口未列 `docs:check`。
- **为什么是问题：**三个可独立发布的段应各自带准确的当前行为；计划里“改完 Spec 后按编号补全”不能证明 A 读档位、B 读旧设置、C 按代理选路分别对应的是哪一版合同和证据。
- **如何核实：**在每段合入候选上从公开 Spec 条目反查相同提交中的实现、合同测试与 Smoke；执行 `bun run docs:check --since <本段基点>`，机检通过后仍人工核对条目未描述后续段。
- **建议改法：**批准依据与未实现部分可以先登记；每段的当前行为、验收编号与证据跟代码同一变更合入，Task 记录仍可独立归档。C 完成后按证据与审批规则决定是否晋升，不在起稿时宣称实现已验。

### 38. 真实模型 smoke 的范围、进入路径和授权没有落到验证门禁

- **严重程度：建议；类别：验收、授权。**
- **位置：**B5、A/B 收口与“验证”；`docs/testing/README.md:124–130,196–208`；`packages/neuro-book/src/plugins/models/models.llm.test.ts:34–51`。
- **现象：**B5 与段 B 收口都列 `test:llm`，未说明哪一次是同一份证据、在哪个包目录或按什么范围运行，也没标付费授权。现有 `models.llm.test.ts` 直接 `resolve()` 后手工构造不带档的请求并 `call()`，不会经过 A 改的会话档位计算；原样跑通不能作为该链路的 smoke。仓库根只有 `test:affected`，不是 `test:llm`。
- **为什么是问题：**照计划可重复付费；选错误验证入口时，默认角色档没发出去也能通过。没有密钥时的 skip 也不能算链路通过。
- **如何核实：**对照 smoke 的入口和 A1/B5 新增真实路径；用本机端点先核会话触发到线上档位，再由获准的真实模型调用验对应路径。不在本轮调用真实服务。
- **建议改法：**每段区分必跑的本机合同与经授权才跑的真实 smoke，写 `bun run test:affected --tier llm --since <本段基点>` 的实际选中范围或指定包／文件，避免 B5 与收口重复跑。选用由会话入口触发的用例验证 A；没有授权或凭据写“未验证”。各段同时列出受影响类型表面的 `--typecheck` 门禁。
