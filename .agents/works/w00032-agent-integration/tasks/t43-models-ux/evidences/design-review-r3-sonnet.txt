# t43 段 B 前端设计审查（Claude Sonnet）

审查对象：plan-snapshot.md 的段 B（B.5 快照与网页数据模块、B.7、B.8）与切片 B6、B7、验收映射、验证。依据：README 决定 1 至 25、静态稿评审板（r1、r2）、已合入的段 A 实现、现行 Spec 与上两轮处理。读过的代码：models 插件 web 全部组件与 models-store、agent 插件 web 的 plugin.ts、session-host.ts、profile-view.ts、nb-agent-ui 的 ComposerIcon、nb-ui 的 SearchSelect、nb-runtime 的 JSON 编解码、e2e/models.e2e.ts。

### 1. “选用数据”的归属没定：消费者分在两个插件，计划写成“网页数据模块里一份、共用”
严重程度：重要
类别：接口与合同、遗漏
位置：计划 B.5“快照”一段；packages/neuro-book/src/plugins/models/web/plugin.ts:36-49；packages/neuro-book/src/plugins/agent/web/plugin.ts:291-340
现象：models-store 属于 nbook.models 的浏览器入口，激活事件只有两个设置页（activationEvents 为 settingsPageEvent），窗口第一次显示设置页才激活。选择器、agent 标签、Profile 页的消费者在 nbook.agent 的浏览器入口（onStartup），它现在有自己的一份订阅与快照（ensureModels、takeModels、modelsSnapshot），不经 models-store。计划说选择器、角色页、Profile 页、agent 标签、models-store 共用一份，没说这份放哪、谁建、怎么跨插件拿。
为什么是问题：跨插件只能经 shared/contracts（ADR 0025 的服务键或合同）。有状态的订阅、缓存和分页读取不能放进 contracts 的纯形状文件。可行做法至少三种：A 在 nbook.models/shared 放一个纯 TS 工厂，两个插件各自实例化（两份缓存，各读一遍全量）；B 让 models 浏览器入口改为 onStartup 并提供浏览器端服务键给 agent（设置页的懒激活没了，每个窗口启动就多一个入口）；C 只在 agent 里保留一份，设置页的角色页反过来依赖 agent（方向不对）。三种对“同一窗口同时开着对话与设置”时的重复读取、对启动顺序、对测试替身的影响不同，B6 开工前必须选一种，否则“21 处逐处迁移”没有统一的目标接口。
如何核实：读上述两处入口声明与 ensureModels；grep createModelsStore 只在 models 插件内。
建议改法：选 A 且写清：工厂是纯 TS（不引 Vue 以外的东西），输入是远程合同客户端，输出是 `rows`、`revision`、`ready` 三个响应式量；两个插件各建一份。理由是 models 入口保持懒激活、不新增服务键；代价是同窗口两份全量读取，用第 3 条的“只读可用的”切片收敛。写进计划 B.5。

### 2. `providerModels` 的“偏移分页”与“系列分组、默认收起、搜索展开命中组”对不上
严重程度：重要
类别：接口与合同、别扭与反常
位置：计划 B.5 的 `providerModels(provider, {query?, offset, limit})`、B.8“模型区”、切片 B6 的性能预算
现象：静态稿（r2 provider-detail）每组一个收起的组头带个数（anthropic 42、google 38 ……），展开才见行。偏移分页返回的是按某种顺序切开的行：一页的边界会落在组中间，组头的总数、一个组是否整体收起、“有搜索时展开命中组”需要的“哪些组有命中”，都得知道整个服务商的分组汇总，而分页只给一页。计划没说 `providerModels` 的返回里有没有 `total`、分组汇总，行的排序键是什么，`query` 命中的是名字还是 id 还是别名。
为什么是问题：实现的人只有两条出路，都不在计划里：一是把一个服务商的所有页读完再在客户端分组（那 `query` 与分页对详情页没意义，且要处理读到一半数据换了版本），二是给服务端加“按组取页”（合同要改）。另外 B6 的预算“600 个模型打开详情首屏 < 300 ms、搜索一次 < 100 ms（happy-dom）”假定搜索是本地过滤，与“`query` 交给服务端”矛盾；若搜索走 RPC，还要处理输入防抖与迟到的旧结果（models-store 里没有这类机制）。
如何核实：对照 r2/provider-detail.webp 与 B.5、B.8 的文字；读 ProviderDetail.vue:163-170（现在按 group 在客户端分组）。
建议改法：简单做法：一个服务商的模型最多约 600 行、约 200 KB（SnapshotModel 每行约 350 字节估算），用一个页大小 200 的分页读完整家（3 次调用），详情页客户端分组与搜索，`providerModels` 删掉 `query`，只保留分页与 `revision`，响应里带 `total`。分页只是为了每次响应不超 1 MiB。管理页同理。这样“系列收起、搜索展开”的逻辑与现在的 ProviderDetail 一致，预算也成立。

### 3. 选用数据的一致性：分页读取的版本、闪烁与整体重读
严重程度：重要
类别：遗漏（并发、失败路径）
位置：计划 B.5“网页数据模块……按版本失效”；agent/web/plugin.ts:145-170、300-306；agent/web/session-host.ts:1924、2012、2052-2054
现象：快照事件到达（带 modelsRevision）与选用数据读全之间有一段时间，计划没写这段时间界面显示什么。现有代码在这段时间会出的事：(1) roleOptions 里 `labels.get(role.model) ?? role.model`，角色卡片会闪出原始的“服务商/模型 id”；(2) session-host 2012 行：当前会话选的模型不在 models 列表里时补一项“unavailable”，列表暂空就会闪“模型不可用”；(3) session-host 2052 行 `watch(() => deps.models(), …, {flush: "sync"})` 对每次换数组都 `refreshModel`（一次 RPC）：选用数据分几页到、每页都换数组就会连发；(4) 分页读取中间版本又变了：偏移分页的第二页可能属于新版本，计划没说每页响应带它读到的版本、不一致时丢弃重读。
整体重读：`modelsRevision` 看起来是单个值。启动时 8 家服务商都过了 24 小时就会各自后台更新，各自提交一次（每次“清解析缓存并发 changed”），每次都使全部窗口把 8 × 600 = 4800 行（约 1.7 MB JSON）重读一遍，且在途读取要作废重来。
为什么是问题：闪烁与连发是用户看得见的；重读是 8 次更新的放大。
如何核实：读上述行。
建议改法：(a) 选用数据在新版本到齐之前继续交出旧版本，到齐后一次换（一次换引用，只触发一次 refreshModel）；(b) 每页响应带版本，与快照版本不同就整体重读，并限制重试次数；(c) 版本按服务商分（`modelsRevision` 放进每个服务商），只重读变了的那家；(d) 快照事件对同一服务商 N 毫秒内合并。把 (a)(b)(c) 写进计划的失败与并发段。

### 4. `enabledModels` 要带“被 Profile 引用的未启用模型”，服务端不知道 Profile 设置
严重程度：重要
类别：接口与合同
位置：计划 B.5 `enabledModels({offset, limit})`；profile-view.ts:141、155-161、184-188
现象：Profile 的模型选择存在 nbook.agent 的设置键 `profileSettings`（agent/shared/settings.ts:119）；packages/nb-models 与 plugins/models 里搜不到对它的引用（grep profileSettings 在这两处无命中）。nbook.agent 依赖 nbook.models，反过来不行。计划却让 `enabledModels` 带上“被角色或 Profile 引用的未启用模型”。角色的引用服务端有，Profile 的没有。
为什么是问题：Profile 页的 findModel 要对已绑定但没启用的模型给出“模型已不可用”与能力缺口（modelNeedsText 需要 vision、contextWindow、reasoning 等），拿不到这行时只能把它当“不存在”，文案会错（“没有这个模型”与“没启用”不同）。分页读全也不是“按引用查”的好形状。
如何核实：grep 上述两处；读 profile-view.ts 的 findModel 与 usable。
建议改法：给合同加 `modelsByReference({references: string[]})`（一次最多 50 个，返回同 `enabledModels` 的行加 `enabled` 标记），由调用方交引用列表：Profile 页传 Profile 设置里的引用，角色引用服务端已知可直接并入 `enabledModels`。选用数据的 `findModel` 先查已读的行，查不到再按引用补取并缓存。同时在合同里把“可用”的判定（有凭据、启用、状态 ok）放进行里（`usable: boolean`），免得三个消费者各写一遍。

### 5. B 的图标会破坏段 A 的选择器取图：实例 id 不再等于模板 id，ComposerIcon 也没有“上传文件”这一种
严重程度：重要
类别：遗漏、接口与合同
位置：agent/web/plugin.ts:141-144、187、604-607；nb-agent-ui/src/types.ts:394-397；计划 B.2 `icon`、B.7、B.8“服务商详情”；Spec 改动表（只有 A 改 agent-conversation-view.md）
现象：A 的 providerIconRef 用 `key: provider.id` 取图（图标表键 = 目录服务商 id）。B 起实例 id “由名称生成、同模板可多份”（“openrouter-2”、“公司中转”），图标按实例的 `icon`（builtin 键、file 名、initial）决定。ComposerIcon 只有 key、initial、class 三种，没有“URL（上传文件）”。计划只写了设置页怎么画，没写选择器与角色卡片的图标怎么跟着改。
为什么是问题：不改的话：第二个 OpenRouter 实例、改名的实例、任何上传了图标的实例，在选择器里都退回首字母，且与设置页不一致；用户刚在设置页挑好的图标在最常用的位置（Composer）不出现。
如何核实：读上述行；grep ComposerIcon 的使用点。
建议改法：(1) ComposerIcon 加 `{kind: "url"; src: string; fallback?: string}`，Vue 层照 image 类渲染；(2) agent 插件的 providerIconRef 改为读快照里的 `icon`：builtin 走 key（键用图标表键，不是实例 id），file 走 `/api/nbook.models/icons/<name>` 的 URL，initial 走首字母；(3) 把这条列进 B6 的迁移清单与 Spec 改动表（ui/agent-conversation-view.md 在 B 也要改），验收加“同模板两实例各自的图标不同、上传图标在选择器里出现”的 dom 用例。

### 6. `setIcon` 的 `png: bytes` 过不了 JSON 传输；画布缩图在 happy-dom 里测不了；上传失败路径没写
严重程度：重要
类别：接口与合同、遗漏
位置：计划 B.5 `setIcon`、技术选型“上传图标”、B.8“图标弹出”；nb-runtime/src/remote/json-codec.ts:34-60
现象：远程帧是严格 JSON 编码，非普通对象（含 Uint8Array）会抛 FrameEncodingError（“不是普通对象”）。计划的合同写 `png: bytes`。Lab 的 fake-remote 目前用 structuredClone 做载荷校验（models-store.ts 注释里写了），不走这个编码，测试会过、真运行失败。另外：客户端“用画布缩成 128 像素 PNG”依赖 createImageBitmap 与 canvas.toBlob，happy-dom 里没有；计划没写这段怎么测、失败怎么显示。
为什么是问题：实现者第一次接真实后端才发现；上传失败（不是图片、解码失败、含透明度的巨图、SVG、缩完仍超 64 KB、动图）没有任何界面状态。
如何核实：读 json-codec.ts 的 strictReplacer；grep happy-dom 对 createImageBitmap 无实现。
建议改法：合同写成 `png: base64 字符串`（≤ 64 KB 的 PNG 编码后约 87 KB，远低于 1 MiB），服务端解码后再按 PNG 头校验；缩图封装成 `shrinkToPng(file, {decode, encode})`，注入解码与编码两个函数，dom 测试用假的，e2e（Chromium）里用真图验一条；弹出面板内一行错误位（role="alert"）写失败原因，并列出五种（不是图片、读取失败、SVG 不收、缩后仍过大、写入被拒）；上传中禁用面板并显示进行中。B6 验收加上述两条。

### 7. 服务商只有一种了，但编辑模型对话框、“手动添加”、详情里的协议下拉仍按 `kind: catalog|custom` 分支，B.8 没写这些
严重程度：重要
类别：遗漏、对照参照
位置：ModelEditDialog.vue:16、34、170-192；ProviderDetail.vue:224-226、257；ProvidersPage.vue:199、237、441；ProviderRail.vue:156；计划 B.8、决定 1
现象：现有组件用 `provider.kind` 做五件事：目录服务商的模型能力与单价在编辑对话框里只读（edit.catalogFixed）；“手动添加”按钮只在自定义服务商出现；协议下拉只在自定义服务商出现；“管理模型”按 kind 走 catalogModels 或 discover；添加模型时按 kind 决定是否带字段。决定 1 说所有服务商一种、名称协议地址图标都能改。B.8 对这些一字未提。

### 8. “模型区”与“管理模型”各列什么、“停用”与“移出”是不是两回事，计划没分清；`setModels` 的去向没写
严重程度：重要
类别：遗漏、别扭与反常
位置：计划 B.2（`excluded`、`frozen`）、B.5（合同表）、B.8“模型区”“管理模型”；Spec settings-pages.md 输出 6、7、10；静态稿 r2 的模型区
现象：现状：详情列“已加入列表”的模型，“管理模型”对话框列目录全部候选，加入、移出，“完成”一次写 `setModels`。v2 里添加就加入全部来源模型，模型区（静态稿）因此就是全部 587 个，每行一个开关；“管理模型”再列“来源的全部模型”，两个列表内容几乎一样。B.2 又有 `excluded`（用户移出的来源模型）与 `enabled: false` 两种“不用”。计划没说：(1) 模型区显示 excluded 的行吗；(2) 开关关掉是 `enabled:false` 还是 `excluded`；(3) “管理模型”存在的理由是什么（unknown 一组一键启用？找回被移出的？）；(4) `setModels` 在合同 v3 里是否保留，B.5 的方法表里没有它，也没有 `removeModel`/`upsertModel` 对来源模型的语义；(5) 角色用着的模型被“移出”时行内确认（Spec 输出 7）要对哪一种操作触发。
为什么是问题：用户会看到两个功能重叠的入口，开发者实现时要自己发明状态机；e2e（models.e2e.ts:129-145）现在整条依赖“管理模型里加入 → 完成”的流程，需要知道新流程才能迁。
如何核实：对照 B.2 与 B.8，读 settings-pages.md 输出 6、7、10 与 ProvidersPage.vue:201-260。
建议改法：只保留一个概念：来源模型默认全部在列表里，开关就是 `enabled`；“移出”只有一处，在“管理模型”，语义是 `excluded`，被移出的在“管理模型”里以“已移出”一组出现、可找回；`unknown` 一组与“需补字段”一组也在管理模型里。写明 `setModels` 的新语义（add 是取消 excluded 或手加，remove 是 excluded 或删手加），并在 B.5 的方法表里列出。模型区不显示 excluded 的行。

### 9. “有未保存修改时检测按钮停用”与现有“失焦或回车即写”的输入模型冲突，检测的状态机没写
严重程度：重要
类别：遗漏（并发、焦点）、对照参照
位置：计划 B.6 末句、B.8“检测协议”；ProviderDetail.vue:60-103（draftField）、194-205（commitUrl）、ProvidersPage.vue 页面“改了就写，没有保存按钮”
现象：页面没有“保存”概念：地址与密钥在 focusout 或回车时才写。B.6 要求“有未保存修改时检测按钮停用并说明”。输入框里有草稿、尚未失焦的这段就是“未保存”。用户在地址框里改完直接点“检测协议”：鼠标按下先触发 focusout，commitUrl 发起 updateProvider（异步），随后按钮因“有未保存修改”变停用，点击被吞（或在 mousedown 与 click 之间被禁用而丢失）；或者按钮没来得及停用，检测按旧地址发出。密钥框同理（未失焦的草稿，原文还没写入）。
还有没写的状态：(1) 没有密钥（需要密钥的服务商）时四种协议都会 401，结果全是红，用户以为协议都不支持；(2) 检测进行中又改地址或协议；(3) 结果与配置版本不符时（别的窗口改了、自己保存了）：整块置灰并禁用“用这个”，还是直接清掉；(4) 检测被取消（切服务商、离开页面）；(5) 检测中又删了这家服务商（unknown-provider）；(6) 四行结果的版面在 390 宽（路径、毫秒、动作三列）会溢出，静态稿的失败行还有“复制”按钮，计划没写。
如何核实：读 ProviderDetail.vue 的 draftField/commitUrl；按键序（mousedown 的 focusout 先于 click）推演。
建议改法：检测按钮的点击处理里先 `await` 提交当前草稿（commitUrl/commitKey 返回 Promise，写成功后再发检测），草稿非法（地址无效）时不检测并把焦点放回地址框；按钮的停用只由“正在检测”“没有密钥且需要密钥（写“先填密钥”）”决定，不由“未保存”决定。结果带版本，版本变了就整块置灰并写“配置已改，请重新检测”，只留“重新检测”。把六条写成状态表放进组件 .md，对应 dom 用例。

### 10. 其余交互状态机缺口：重新拉取、复制、就地改名、检测全部的“未知”
严重程度：重要（合并为一条，逐项列）
类别：遗漏
位置：计划 B.5 的 `checkAll`、`duplicateProvider`、`updateProvider({name})`、`refreshModels`；models-store.ts:171-205；ModelRow.vue、AllModelsView.vue
现象与建议：
