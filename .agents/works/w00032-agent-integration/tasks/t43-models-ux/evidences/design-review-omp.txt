### 1. 回环中继没有鉴权，客户端还可以指定任意上游
- 严重程度：阻断；类别：安全与性能。
- 位置：固定计划第 37、42、186 行；`docs/specs/runtime/server-host.md:71–72`。
- 现象：`127.0.0.1` 只限制监听接口，不识别调用进程。按计划，任何能连接本机 TCP 端口的进程均能声明 `direct` 或提交自己的上游代理 URL；不需要经设置层、模型服务或宿主准入。随机端口不是凭据。结论不依赖浏览器能否发 CONNECT。
- 为什么是问题：实际多出一个不受“仅模型服务使用”约束的通用转发口；出口规则在中继入口可被替换，未授权连接也会消耗连接与解析资源。现有服务端接受某些本机调用的约定不能替这个新增端口做校验。
- 如何核实：对照第 42 行的监听与协议合同，无鉴权服务端无法从合法的目标和出口头区分同机调用者。实现后用实际 Bun 客户端和另一独立本机连接验证：没有有效内部凭据、出口未知或有重名标记的请求在拨号前拒绝；仅授权请求到达测试上游。
- 建议改法：保留决定 18 的中继，但用每进程高熵凭据和中继持有的不可伪造线路标识；不接受客户端给的代理 URL。认证与路由只放代理请求头，绝不进源站/日志；拒绝协议歧义、递归线路，规定连接与握手上限。约束写进中继合同，不靠 UI 隐藏端口。

### 2. Bun 对本机目标绕过显式代理，和“仍经中继”冲突（撤回）
- 严重程度：阻断；类别：正确性。
- 位置：固定计划第 33、37、165 行；决定 18。
- 现象：在本机 Bun `1.4.4` 中，给 `https://127.0.0.1:<实验端点>` 的 `fetch` 显式传 `proxy`，URL 和 `{url, headers}` 两种写法都收到源站 `200` 和完整 SSE，而实验代理收到了 **0 次 CONNECT**。对 `http://127.0.0.1:1/` 同样传显式代理时得到直接连接的 `ECONNREFUSED`，代理没收到绝对 URI 请求。
- 为什么是问题：计划说本机地址仍经中继执行直连，并以“显式代理总生效”为基础；常见本机 Ollama/vLLM 路径上这一前提不成立。也不能把指向本机服务的成功当成代理通路已被验证。
- 如何核实：`lab/relay-transport.ts` 的回环变体（同目录的 `relay-loopback.ts` 保留首次探针）；只起本机 HTTPS 源与代理，分别记录源站响应和代理的 `connect`/HTTP 请求数。
- 建议改法：先定清楚强制经过中继的范围。允许安全直拨的地址要显式走不读取环境代理的直连传输；需要统一通过中继的地址则不能依赖 Bun 对其注入 `proxy`。测试必须断言经过哪条线路，不能只断言得到回复。

撤回理由：首轮测试继承了含 `127.0.0.1` 的 `NO_PROXY` / `no_proxy`；在仅清除实验子进程代理环境的对照中，相同本机地址和客户端成功经显式代理。不能归因为 Bun 对本机地址无条件直拨。

### 3. `NO_PROXY` 能绕过显式中继；路由标记发给谁取决于 Bun 的选项
- 严重程度：阻断；类别：正确性。
- 位置：固定计划第 29–43、148、165、186 行；决定 5、18。
- 现象：Bun `1.4.4` 在子进程清除 `NO_PROXY` / `no_proxy` 时把 HTTPS 回环实验请求送进显式代理；只设 `NO_PROXY=127.0.0.1 no_proxy=127.0.0.1` 时同一请求成功，但代理收到零次 CONNECT。另一方面，对一个实际经代理的 HTTPS 请求，普通 `init.headers` 里的出口头到了源站、CONNECT 没收到；用 `proxy: {url, headers}` 才只到 CONNECT。HTTP 绝对 URI 请求在中继收到该头，须剥离后转发。
- 为什么是问题：线路规则由应用计算却可被保留给子进程的环境再次改写；若按“在请求头带上”直接实现，HTTPS 中继拿不到标记，源站却拿到了。仅证明客户端收到了完整 SSE 不能覆盖这两个条件。
- 如何核实：`lab/relay-loopback.ts` 在仅改变实验子进程两种 `NO_PROXY` 条件下对照；`bun relay-transport.ts` 用本机 TLS 源站和模拟域名，打印代理与源站各自看到的头。
- 建议改法：明确 `NO_PROXY` 只在哪个模式参与选路，选定后由不再读进程代理环境的传输兑现；保留决定 18 的中继与子进程环境。使用代理专用头，分别验 CONNECT 和绝对 URI 的鉴权、线路与源站不收内部头。应用级代理不能让 pi-ai 注入的 `init.proxy` 改写已选出口。

### 4. 关掉自动加入会覆盖用户编辑和手加模型的必填字段
- 严重程度：阻断；类别：正确性。
- 位置：固定计划第 59–68、94、162 行；`docs/specs/models/service.md` 输出 5、6、17；`packages/nb-models/src/core/core.ts:285–296`。
- 现象：设某来源模型已有自定义名称、请求头、压缩阈值，另有手加的 `{id:"local-special", enabled:true, contextWindow:32768}`。按“有效列表全部写进 `models`（只写 id 与 enabled）”，两者的字段都丢失。前者请求行为变了；后者从不在来源里，失去必填窗口后不能再解析。再次开启时，冻结生成的 id 也不能被一律当成手加覆盖。
- 为什么是问题：这是把跟随状态切换变成用户设置的破坏性改写；CAS 只能防覆盖别人刚写的设置，不能让重算得到的错误写法变对。跟随开关仅应冻结成员集合，不应更改模型本身。
- 如何核实：对照 `ModelConfig` 和现有 `stored()` 的字段保留规则，将上述两种模型代入第 94 行。验收中读取磁盘和实际 `resolve`/请求，不能只断言新模型没长出来。
- 建议改法：在同一个带 `expect` 的补丁里保存冻结的来源 id 集合，或者仅给尚无条目的来源 id 补最小条目，完整保留已有覆盖和手加记录；明确再次打开、排除项、漂移的判定及加载中的切换。CAS 重试必须基于最新设置重新合并，不复用冲突前的列表。

### 5. Gemini 的发现地址忽略覆盖，密钥会交给默认端点
- 严重程度：阻断。类别：安全与性能。
- 位置：固定计划第 57–59、85–86、95 行。`pi-catalog@18.14.0` 的 `src/provider-models/descriptors.ts:125`、`google.ts:79–89`、`src/discovery/gemini.ts:79–105,147–160`。
- 现象：Gemini 实例填了私有网关地址及该网关的 key。按第 85 行直接接描述器，`googleModelManagerOptions` 即使收到 `baseUrl` 也只向 `fetchGeminiModels` 转交 key 和 fetch。发现会把 key 放入请求 URL 发往 `generativelanguage.googleapis.com`，推理却按第 86 行走覆盖后的地址。加服务商、填 key、改地址都可触发这次发现。
- 为什么是问题：用户修改了目标地址，发现仍向另一个源提交该实例的凭据，还可能把官方返回的模型用在私有网关上。
- 如何核实：沿描述器调用到 `buildModelsUrl` 和 `normalizeBaseUrl`，核对地址的默认值和 key 的去向。集成验收用两个捕获请求的夹具与虚构 key，断言覆盖态只访问已配置的端点，并核对恢复模板后所用地址。
- 建议改法：模板提供元数据与发现适配器。先按实例选定发现的协议、目标与认证，再调用确认尊重这些值的发现函数。Gemini 覆盖态显式传 `fetchGeminiModels({baseUrl, …})`。其他描述器逐个核对，无法保证目标的一律不发带凭据的发现请求。

### 6. 同一个实例改地址、协议或密钥后仍会读旧目录
- 严重程度：阻断。类别：不变量。
- 位置：固定计划第 77–86、93–97、187 行。`pi-catalog@18.14.0` 的 `src/model-manager.ts:248–305,413–445`、`src/provider-models/cache-provider-id.ts:97–154`。
- 现象：实例 `test-gateway` 已有端点 A 的缓存，改到 B 时沿用同一 `cacheProviderId`，刷新失败或重启离线仍能读到 A 的模型。A 在途时改到 B，按“同一服务商合并在途”还可能把 B 的刷新合到 A。即使发布前丢弃 A 的结果，ModelManager 已在返回前写了 SQLite。删后同名重建也能命中旧行。Kimi Code 等已有按凭据和端点分区的 OMP 工厂，覆盖成裸实例 id 会取消这层隔离。
- 为什么是问题：同步解析可能把旧目录的能力、价格、线协议标识甚至地址带进新请求。串行发布无法保护已经提交的 SQLite，也无法区分同 id 的两次配置。
- 如何核实：用同一状态根和两个可控列表端点，卡住 A，改地址或换 key 后让 B 先完成，再放 A。核对刷新结果、`changed`、同步解析和重启离线读取。另验删除重建及 B 失败时的回退范围。
- 建议改法：区分模板 id、实例 id 与来源身份。用实例加规范化端点、协议、实际认证范围组成缓存命名空间，敏感值只用不可直接还原的身份。按来源身份合并在途，按配置代次发布，旧代次退出时先取消再收口。失败保留的上一份也必须属于同一来源。

### 7. 第二个模板实例的历史会被当成别家的模型回复
- 严重程度：阻断。类别：正确性。
- 位置：固定计划第 86–89、161、164 行。`packages/nb-harness/src/kernel/model/omp.ts:183–201,245–246`，`pi-ai@18.14.0` 的 `src/providers/transform-messages.ts:522–528,911–944,1059–1112`，`docs/specs/harness/models.md` 输出 7。
- 现象：从 Anthropic 模板加第二家。新日志记录 `anthropic-2/<模型>`，适配器接着用 `Model.provider = anthropic` 发请求。`toContext` 从日志模型名拆 provider，与 `Model.provider` 不等就给历史消息 `api: unknown`。同一个实例自己刚生成的回复，在接工具结果的下一次请求里也不再被 OMP 当成原协议的自己，签名和思考块会走跨模型的清理分支。反过来，同一实例改协议后用现在的协议还原旧回复，也不能推出旧签名适用。
- 为什么是问题：公开引用和原生续写的身份已经不同。只改 `ompModelInfo`、`ompCall` 的对外名字，不能守住多轮签名与元数据合同。首次调用的验收看不到这条回归。
- 如何核实：两家同模板绑同一模型。用第 2 家跑带已签名思考块和工具调用的本机流，第 2 个请求核对原签名。再换实例、协议或端点，确认不会把只适用于旧部署的签名当成本次原生签名。
- 建议改法：适配器同时保存公开模型引用和可验证的原生来源（实例、协议、线上的 model id 及必要的部署身份）。只在来源相容时还原同源续写身份，历史无来源字段时明确兼容规则。保留模板身份供 OMP 选择兼容分支。

### 8. Cursor 默认的 HTTP/2 请求不走注入的 fetch
- 严重程度：阻断。类别：正确性。
- 位置见固定计划第 37、85–89、148、165 行，决定 5、18。`pi-catalog@18.14.0` 的 `src/provider-models/descriptors.ts:114` 和 `pi-ai@18.14.0` 的 `src/providers/cursor.ts:1055,1319–1335`。
- 现象是 Cursor 有目录描述器，能进入模板解析路径。它默认走 HTTP/2，调用 `getProxyForUrl` 读取 OMP 的环境代理规则，再走 `http2.connect`。设置应用或服务商出口、传入 `OmpTarget.fetch` 都不会改变这条连接的出口。Codex WebSocket 也有独立出口，但本任务的登录范围可以排除它。锁定版本的 Bedrock 推理已改用 `options.fetch`，不能按现有适配器注释判为 SDK 直连。
- 因果是 `SimpleStreamOptions.fetch` 只接管使用它的协议。支持模板与否不能只由目录工厂判断。
- 核实方法是在锁定版本下检查 Cursor 的 `transportMode` 分派、`getProxyForUrl` 与 `transportFetch`。验收应在本机可数连接的夹具中断言所选线路，对支持的每个非 fetch 分支也断言。
- 建议在协议适配器处明确传输能力。要支持 Cursor 就给其实际 HTTP/2 连接接入同一出口决策，或验证可用的 fetch 路径。范围确实要排除的协议须让服务端公开可判定的不可用原因，不能静默使用环境或直拨。

### 9. v1 的 `api` 原样迁入 v2 会改变已在用的协议，归一化值不能当写入期望
- 严重程度：阻断；类别：正确性。
- 位置：固定计划第 57、68、146、161、189 行；`packages/nb-models/src/config/shapes.ts:38–48`、`packages/nb-harness/src/models/target.ts:82–84,157–170`、`packages/nb-models/src/core/core.ts:242–263`、`packages/neuro-book/src/plugins/models/backend/settings-store.ts:24–32`；`settings/configuration.md` 输出 4、25。
- 现象：v1 schema 接受目录服务商带 `api`，但 `catalogModel` 只覆盖地址等字段，不读它。v1 OpenRouter 即使存 `api: "openai-completions"`，仍用目录的 `openrouter`；按计划原样归一为 v2 则立即强制改协议。另一个独立的写入边界：如果在 `editable()` 返回时先归一，`mutate` 会拿带 `template` 的值与磁盘上带 `kind` 的值比较，三次重读也只会得到 `conflict`。
- 为什么是问题：第 2 片声称行为不变。兼容要保留原配置的有效行为，也要能从旧文件成功做第一次按 id 补丁，不能只测旧文件能读。
- 如何核实：同一真实设置层放两种 v1 服务商，目录实例带旧 `api` 和地址覆盖。对照升级前后实际请求协议；在首写前插入一次外部编辑，断言重读后两处变更都在，旧条目不会因整键校验被丢弃。
- 建议改法：以 v1 运行时语义迁移，旧目录 `api` 不变成有效覆盖；保留原数组、id 与引用。设置层 schema 对数组的每个元素兼容新旧形状；从原始已校验的本层值计算 `expect`，只把归一后的副本给补丁，并在冲突后重新归一、重算。另验单个坏条目的整键回退，不把坏键当空数组覆盖。

### 10. 模型来源消失时，覆盖记录和手加模型没有可区分的身份
- 严重程度：阻断；类别：正确性。
- 位置：固定计划第 62–68、94–96、162–164 行；`docs/specs/models/service.md` 输出 9、15，`packages/nb-models/src/core/core.ts:129–151,166–185,391–438`。
- 现象：来源曾有 `m`，用户给它改了名字并绑定角色；同一家另有用户手加的 `n`。来源成功删除 `m` 后，两种记录在 `models` 中都变成“来源没有的条目”。第 94 行将前者和后者都当手加，第 96 行却要求前者保留引用、标 `missing`。若手加的模型后来也被来源列出再移除，按当下是否在来源判断同样会反转含义。
- 为什么是问题：来源漂移、用户明确移出和手加模型的解析规则不同。前者应保留绑定并报不可用，明确移出按现行输出 15 要解绑，手加模型仍应可用。不能拿有无 `contextWindow` 猜来源：覆盖也能写窗口。
- 如何核实：同一实例分别手加、覆盖、绑定三个模型；让端点成功移除其中两个，另一个由用户移出；核对快照、引用解析与角色，重启离线后再核对。
- 建议改法：持久区分手加、源模型覆盖与冻结成员，迁移时用 v1 的 `kind` 决定初始类别。统一一个模型判定给同步 `resolve`、快照、角色状态和检测。给用户移出与来源消失分别规定转换，避免靠当前列表推断来历。

### 11. `off` 和“通用档”都可能与适配器实际发出的档位不同
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 88、100、105–107、166 行；`pi-ai@18.14.0` 的 `src/stream.ts:1173–1178,1706–1743,1786,1833–1859`，`pi-catalog@18.14.0` 的 `src/model-thinking.ts:17–39,164–183`、`src/compat/resolve.ts:1024–1028,1200–1219`。
- 现象：`off → disableReasoning` 传到 OMP 后，`requiresEffort` 且无 `suppressWhenOff` 的端点会把关闭或省略改成默认线路档或最低档，并移除关闭标记。计划验收却要求 `off` 一定不推理。反方向也有缺口：`getSupportedEfforts()` 为空可能是明确不接受档位（Responses 的 `supportsReasoningEffort:false`），并非缺元数据。给它造通用档，选项还是会被适配器省略。OMP 已给部分无证据的模型造了 `unverified` 梯，不能见非空就叫 `declared`。
- 为什么是问题：用户选了档却未兑现；审批仍须压过角色档（现有代码带固定工具调用，DeepSeek 已有推理未关闭即 400 的记录）。`check` 的极小请求也不能据此保证无推理费用。
- 如何核实：在协议夹具捕获实际请求体和线上 `model`，覆盖可关闭、强制推理、明确无档、未验证梯四类；审批绑定有默认档及回落两条路径均验强制工具与关闭行为。
- 建议改法：把“默认省略”“明确关闭”“服务商要求推理”“可试的未验证档”分开，展示与发包用同一份有效能力和映射；不可关不承诺关。审批的禁用优先，不兼容强制工具时按现合同转人工。验收断言线请求，不只断言草稿布尔字段。

### 12. 摘要压缩的实际请求不经过计划列出的算档位置
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 101、105–107、149、166 行；`packages/nb-harness/src/kernel/compaction/compact.ts:178–193`、`kit/compaction/summary.ts:80–102`、`kernel/run/model-call.ts:159–167`、`kernel/session/complete.ts:27–49`；`packages/nb-models/src/core/core.ts:129–151`。
- 现象：会话跟随 `main` 的 `high`，`compaction` 绑同一个模型却设 `low`。在 `compact.ts` 给压缩前请求算出 `high`，只够就地压缩；摘要方法会另建草稿，`ModelCaller` 按 `compaction` 解析后只补模型与用途，发不出 `low`。若为加角色档直接改 `resolveReference` 缓存里的 `info`，两个角色及直指这个模型也会互相串档。
- 为什么是问题：预算、预览、压缩前的请求和真实发出的请求不是同一条链；同模型的角色默认值是一次解析的属性，不是模型目录属性。
- 如何核实：按上面的双绑例分别捕获对话、预览、就地压缩、摘要压缩、`complete()` 的请求。再直指模型、改绑角色、重开已存 `effort:null` 的会话；子会话不传 `effort` 应按子 Profile 选择，显式传才覆盖（`agent/subagents.md` 参数表）。已有就地压缩测试不覆盖摘要的角色默认。
- 建议改法：角色解析在共享模型结果之外带默认档；在每条实际请求构造处用同一次解析确定档位。摘要在 `ModelCaller` 选定专用模型后算档；就地压缩保留本轮对话的目标与档；明确专用摘要如何处理会话显式档。`complete()` 仍单独接入；审批草稿带关闭时不套档。Spec 写到 `harness/runtime.md` 对应输出。

### 13. 仅按 `modelKind() === "chat"` 会误收非对话模型，也补不回被上游筛掉的对话模型
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 20–21、85、94、162 行；决定 2；`pi-catalog@18.14.0` 的 `src/discovery/openai-compatible.ts:194–232`、`src/types.ts:122–124`、`src/provider-models/openai-compat.ts:3585–3637`。
- 现象：通用发现的默认 mapper 不接收行里的 `kind`，没有分类的物化行又默认是 chat。OpenRouter 路径恰好相反：在物化前要求 `supported_parameters` 包含 `tools`，无工具能力但输出文本的模型不会到达外层筛选器。
- 为什么是问题：假端点只返回 3 个对话 id 的验收掩盖了两边的误判；自动加入随后会令误收模型进入启用列表、检测与选择。通用发现中的未知模型还可能无窗口和价格依据，不能把默认零价格当确认免费。
- 如何核实：`bun lab/catalog-contract.ts` 使用本机 `/models` 和临时 SQLite：Chat、Embedding、Image 三行经通用发现都成为 `chat`、窗口 `null`；OpenRouter 的两条文本输出中只返回带 `tools` 的一条。同一实验也证实第 6 条：新地址离线时读旧地址行且 `stale:false`，新地址 503 时仍读旧行而 `stale:true`。
- 建议改法：在发现适配器中保留明确分类证据，未知独立处理，不按 id 猜。区分“列在来源里”“可作为 Agent 模型”“可自动启用”；若保留 OpenRouter 的工具筛选，要明确它与“全部对话模型”的产品口径。用有/无工具、非对话、未知及缺窗口的混合列表验收。

### 14. 协议检测成功后只保存 `api`，不一定能复用测通的请求
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 57–59、86、98–100、167 行；决定 7、13；Magpie `internal/provider/detect.go:39–66,82–124,318–342`；`packages/nb-harness/src/models/target.ts:113–137`。
- 现象：在现有实例上填未保存的 `baseUrl`，探测以它为准，点“用这个”却只写 `api`，下次推理仍走原地址。即使覆盖地址已保存，也要统一 `/v1`、`/v1beta`、`/messages` 等路径的规范化。空白服务商尚无启用模型时只有 `no-model`；Magpie 会用表单中的模型、已有目录，必要时先做一次列表 GET。这里 `model?` 没定义能否用一个尚未加入的 id，因此可能要求用户先手动选一个协议才能测协议。
- 为什么是问题：探测得出的可用性只属于实际试过的地址、协议、模型和认证。模型不在、401、空响应、服务商业务拒绝与协议不存在不是同一个结论。
- 如何核实：以 A 为已存地址，B 为待应用地址；四种夹具各验真实路径和认证头，对 B 测通再点采纳，下一次用相同模型发往 B。另测空列表、显式尚未加入的模型、200 非协议响应、401、404、429、超时与取消。
- 建议改法：返回受测的规范化地址与 model id、机器可判定的结果（含未探测）；采纳时将协议与地址一次 CAS 写入，拒绝套用已被改过的输入。至少明确空目录时可填模型 id，或先用同一认证与出口做有界发现。临时改到异源地址时，不默认转交已存凭据。

### 15. 复制与删除跨两个存储，失败后不能只回普通失败
- 严重程度：重要；类别：不变量。
- 位置：固定计划第 53、70、93–98、161 行，决定 20；`docs/specs/models/service.md` 输出 1、2、6、13、15；`packages/nb-models/src/core/core.ts:305–318,391–400,472–495`；`packages/nb-harness/src/models/credentials.ts:41–52`。
- 现象：复制先写配置再写 key，第二步失败时副本已经存在，重试普通 `duplicateProvider` 又生成一个 id。若先写 key，设置 CAS 失败会留下孤儿行。现有删除先删设置后清 key，也已经有失败窗口；按名字重新分配刚删掉的 id 时，`requestAuth` 会把残存的 key 用在新实例上，甚至新端点上。复制一个 `apiKeyEnv` 实例时，复制变量引用与复制库内被遮盖的旧 key 不是一回事。
- 为什么是问题：串行队列不跨文件和凭据库提供事务。副本的有效认证、失败返回和 id 分配必须对应同一次操作，不能靠调用方重试猜测是否已生效。
- 如何核实：真实设置与隔离凭据库中分别制造配置冲突、key 写失败、删后清 key 失败；随后重试或用相同名称新建。核对返回、快照、两个存储与本机端点实收头，无凭据值出现在响应、事件或诊断。
- 建议改法：保留决定 20 时只复制有效的凭据方式（env 只复制引用，免认证不复制库存值）。明确持久副本已存在时的 `partially-applied` 结果（副本 id、实际 `KeyStatus`）及补救，不重新复制配置；新建不得接手遗留凭据。若不接受双存储部分成功，改为显式复制凭据的独立操作，并提交开发者决定。

### 16. 四个极小逻辑请求不是最多四次出网，也不保证无推理和不落盘
- 严重程度：重要；类别：安全与性能。
- 位置：固定计划第 99–100、133、149、167、174 行；`docs/specs/models/service.md` 输出 11、16；`docs/specs/harness/models.md:20–22`；`pi-ai@18.14.0` 的 `src/utils/openai-http.ts:26–33,100–120`、`src/providers/anthropic.ts:1106,2452,3549`、`src/utils/http-inspector.ts:82–112`。
- 现象：通过常规 `ompCall` 发探测，`maxHttpAttempts:1` 只限制 Chat Completions；Responses 一个 503 可触发 6 次 HTTP 尝试。Anthropic 也有内部重试与 400 请求体文件路径，常规适配器删不到内部恢复成功的文件。“不写配置”不等于没有文件写入。`maxTokens:16` 不限制请求次数或输入计费；四种协议若均可用，四个模型调用都可能计费并触发限流。
- 如何核实：隔离环境运行 `bun lab/effort-attempts.ts`：本机 Responses 夹具回 503、`Retry-After: 0`，`maxHttpAttempts:1` 下实收 6 个 POST。打包目录的强制推理模型重定向到同一本机端点后，带关闭标记仍发 `reasoning.effort:"low"`，补证第 11 条。未测真实计费。落盘验收须另以非 `bun test` 的隔离子进程观察实际文件。
- 建议改法：检测用专门的一次请求模式，复用认证、协议序列化、代理和错误遮盖，不复用会重发或落盘的普通流恢复；优先让上游支持统一传输预算，不能支持时才使用专门的最小探测适配。15 秒是整次检测期限，取消传播到四条。契约列最大实际请求数、付费与未知结算，验收按服务端实收次数断言。

### 17. “检测全部”确认的对象和服务端实际出网的对象没有绑定
- 严重程度：重要；类别：安全与性能。
- 位置：决定 2；固定计划第 94、98–100、162、167 行；`packages/nb-models/src/contract/settings-spec.ts:83–84`、`packages/nb-models/src/core/core.ts:325–336,519–536`；`docs/specs/models/settings-pages.md` 输出 8。
- 现象：`checkAll` 现在只收服务商 id，进方法才取所有启用项。确认 3 个后、发送前后台刷新到 587 个，按有效列表替换旧配置列表就会检测 587 个。并发 4 没限制总数；若每项都等 30 秒，587 项这一批是 147 波、约 73.5 分钟。现在的 worker 在整体取消后仍逐个从队列取余下条目；两窗口的批次各自可开 4 个 worker。
- 为什么是问题：启用数从手选几条扩大到自动全量，继续沿用原合同会使带费用确认及并发上限无法按服务商兑现；取消也没有定义未开始项的结果。
- 如何核实：确认后先放行一次刷新，再发调用；两客户端同时跑批次并取消之一，用本机端点数实际实收和峰值，另验缺凭据与被排除模型不出网。上述时间是上界场景的计算，未做长跑。
- 建议改法：确认携带已确认的 id 集或快照代次，服务端拒绝名单变化或只跑确认且仍可解析的项。按同一服务商共享并发预算、取消后不再认领待发项；大批次分段交回，保留逐项结算，不把未检测记作模型失败。合同明确这类可计费操作中断后不能无条件重试。

### 18. 选定的系统代理库不读 Linux 桌面，Windows 路径含原生模块
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 22、43、145、175–176 行，决定 5、13、16；`os-proxy-config@1.1.2/src/index.ts`、`windows-system-proxy@1.0.1/src/index.ts`；`packages/neuro-book/scripts/pack-app.ts:66,134`、`desktop-payload.ts:209–215`；ADR 0036 决定 1。
- 现象：Linux 落在环境变量分支，没读 GNOME 或 KDE。启动环境没有代理、桌面设了代理时，“跟随系统”查不到；与 Magpie 读 `gsettings`／`kioslaverc` 不同。Windows 则经动态导入进入 `registry-js`（依赖范围 `^1.15.1`）；符合范围的 `1.16.1` 的 `lib/registry.ts` 在 Windows 加载 `build/Release/registry.node`。现有服务端构建只外置 `@oh-my-pi/*`，Linux 仓库内启动成功不能证明 Windows 发布产物带对了模块。第 43 行已有原生依赖退路，现在应按退路评审，不应继续视为三平台已覆盖。
- 如何核实：源码已核对，未构建 Windows 产物。用不含 `*_PROXY` 的启动环境，平台读法分别喂 Linux 桌面、macOS、Windows 的代理及旁路配置；另在目标 Windows 的真实安装产物上启动并读系统代理，不能用仓库 `node_modules` 补齐。
- 建议改法：用有期限的系统适配器，Linux 补桌面手动代理，Windows 选用系统命令免引入第二份原生模块发布链；若保留原生依赖，就把外置、安装闭包与目标平台验证列进切片。PAC／自动发现、执行超时和读不到配置要与“未设置代理”区分。

### 19. “跟随系统”把面向目标的代理规则压成一个地址
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 37、41–44、165 行，决定 5、13、16、18；`pi-ai@18.14.0/src/utils/proxy.ts:24–119`；`os-proxy-config@1.1.2/src/index.ts`；Magpie `internal/netproxy/netproxy.go:527–561,670–742`。
- 现象：系统及环境代理不一定对所有目标共用一个 URL。只取优先级最高的 `HTTPS_PROXY` 会把它用到本应走 `HTTP_PROXY` 的 HTTP 端点；丢掉 OS `noProxy` 会使企业域名或局域网主机名走上游。`isLocalOrMetadataHost` 只看主机字符串，不会解析指向私网的域名，也不识别 IPv4 映射 IPv6。macOS 库会返回 `socks://`，而计划只定义 `socks5://`、`socks5h://`；`socks` 的目标字段传主机名时会交给上游解析，若两种 URL 都原样传主机名，得到的都是远端 DNS。另有带用户信息的环境代理：设置表单拒收不能防 `systemProxy()` 回显原文。
- 如何核实：用本机分别收 HTTP、HTTPS、SOCKS 的实际连接，配置不同的环境代理和系统旁路，区分 SOCKS 握手里的 IP 与域名；检查测试结果、诊断和 `systemProxy()` 无凭据。源码已证实输入形状和主机分类，未做桌面系统实测。
- 建议改法：系统来源返回可按目标协议、主机判定的规则，公开结果只给脱敏摘要；明确系统旁路优先级、系统读失败或代理失联是否回退直连，不把失败当“没有”。精确定义本机例外与 SOCKS 两种解析语义（或只承诺一种），在每次实际选路落实；不要靠 Bun 再读 `NO_PROXY` 偶然实现。

### 20. 自动跟随重定向会复用上一个目标的出口
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 37、42–44、165 行；决定 5、18；`lab/relay-transport.ts` 的重定向对照。
- 现象：`fetchFor` 在调用开始按 URL 算一次出口，Bun 跟随重定向时不重新进入这个包装。Bun 1.4.4 的本机 TLS 对照中，两个不同目标各有一次 CONNECT，但两次都收到首跳设置的 `route-follow`。跨目标后仍会用同一个出口；例如局域网首跳重定向到外部服务会继续直连，外部首跳重定向到本机则可能把本机地址交给上游。两个目标都经中继不是选路正确的证据。
- 为什么是问题：本机与系统旁路规则是对实际连接目的地的承诺，不只对用户最初填写的 URL 生效；中继看不到 HTTPS 隧道里产生的重定向，也不能补算。
- 建议改法：明确哪些请求可跟重定向；同一出口和认证范围之外拒绝，或由出站层逐跳重新匹配出口并限制次数、跨源凭据与自定义头。现有实验已证明 Bun 复用首跳代理头；验收再让两个目标按产品规则期望不同出口，断言各线路实收及头未转给第二目的地。

### 21. 停机只说断开中继，没有收口发现、排空和流取消的顺序
- 严重程度：重要；类别：不变量。
- 位置：固定计划第 42、77–81、95、148、186 行；`packages/nb-host/src/server/start.ts:370–387`、`host.ts:128–143`、`packages/neuro-book/src/plugins/models/backend/plugin.ts:36–40`；`docs/specs/runtime/server-host.md:77–85`。
- 现象：停止扩展与两路排空并行等，HTTP／RPC 的 20 秒上限不限制 `extension.stopping()` 自身，插件关闭又在这之后。如果先关中继，已接纳的检测或对话会中途断；若只在插件释放时断连接，没有地方阻止后台发现再排任务。`ModelManager` 无关闭入口，stencil 等待者取消不取消共享传输，且 SQLite 可以在 Promise 返回前写入（第 6 条）。同步 `sources.close()` 加“完成后进串行队列”不能保证停机后不再入队或开库。
- 为什么是问题：JSON 请求成功或 SSE 正常读完不验证取消、半关闭、背压或启动失败回滚；若只关监听器，未完成的 CONNECT、拨号或单向 pipe 仍可能持有资源。
- 如何核实：以宿主实际停止入口触发，夹具同时停在未完成代理握手、已收到首个 SSE 帧、共享 stencil、尚未开始的刷新；分别取消和停机，验已接纳请求结算、新请求拒绝、刷新不再发布、双边套接字和缓存句柄都在期限内释放。
- 建议改法：规定停止接纳、已有 RPC 排空与后台任务取消的顺序；网络等待不占设置写队列。贯穿请求／任务／宿主信号，结束时先使当前代次不可提交，再限时等传输与排队工作收口，最后关闭句柄。流式转发保留半关闭与背压，不将源站全部读入才返回。

### 22. 目录工厂的 `{apiKey, baseUrl, fetch}` 不是实例的实际认证
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 59、77、85、89、95、98 行；`docs/specs/models/service.md` 输出 1、3、4、12；`packages/nb-models/src/core/core.ts:497–516`、`packages/nb-harness/src/models/target.ts:117–137`；`pi-catalog@18.14.0/src/provider-models/descriptor-types.ts:6–13`、`src/discovery/openai-compatible.ts:151–176`。
- 现象：当前发现先解析 `env:` 请求头、检查缺失变量，免认证时明确不传 `apiKey`。照计划调用 OMP 工厂，公共配置没有 `headers` 和认证方式。有只接受自定义 `X-Api-Key` 的网关时，对话能通、发现会 401；若把免认证的内部占位 `N/A` 直接传给通用发现器，它会发 `Authorization: Bearer N/A`。原 `discover` 区分没凭据、404、401／403、连不上和响应坏；`ModelManager` 把子来源失败收成 `null`，其公共结果没有计划许诺的 `SourceError`。
- 如何核实：读工厂配置与通用发现器的请求头构造；验收用一个只验环境变量头的本机端点，比较发现与推理实收认证，再覆盖缺变量（0 请求）、免认证、401、404、503、合法空表；stencil 必须不收实例凭据。
- 建议改法：先解析一次实例的有效认证，再由协议适配器显式生成发现和探测的线请求；不把 `auth:none` 占位交给会自行添凭据的发现器。记录每路的结构化结果后才交给目录合并，回退名单与本次请求的失败各自报告；避免用给所有 URL 加头的 fetch 包装，防止凭据串到其他来源。

### 23. OMP 的缓存更新时间不等于目录成功时间，权威空表重启后也可能复活模型
- 严重程度：重要；类别：不变量。
- 位置：固定计划第 78、95–96、163、187 行，决定 3、13、16；`pi-catalog@18.14.0/src/model-manager.ts:375–384,425–498`、`model-cache.ts:609–625,805–839`。
- 现象：OMP 一次远端失败后用当前时刻重写回退缓存，以实现 5 分钟退避。转交 `updatedAt` 后会把失败当成新的成功时间。另一个独立结果：端点成功给权威空表时当次确实移除了静态名单，但空动态表不是持久权威，下一次离线加载可重新返回打包模型；`followSource` 会把它们重新加入。
- 如何核实：`bun lab/catalog-restart.ts` 的本机夹具：成功 `updatedAt:1000000`，503 结果仍是 `1000000`，重新建管理器离线成 `1010000`，网络请求为 0；权威空表返回 `[]`、`stale:false`，新管理器离线变为 `["bundled"]`、`stale:true`。没有重启产品宿主或打线上端点。
- 建议改法：区分最近尝试、最近成功和缓存退避，不以 OMP 的缓存 `updatedAt` 代替产品的成功时间。规定成功空表是否算持久的成员记录；若算，单独记录同一来源的持久权威成员（含空集），失败和离线不能用打包模板擅自恢复，除非明确标为回退而不是现役成员。

### 24. 推理运行时也会改写用户已保存的地址，凭据随实际请求过去
- 严重程度：阻断；类别：安全与性能。
- 位置：固定计划第 35、57–59、85–89、99 行，决定 1、13；`pi-ai@18.14.0/src/providers/openai-shared.ts:244–290,365–381`；`pi-catalog@18.14.0/src/provider-models/openai-compat.ts:850–854,5037–5048`。
- 现象：第 86–87 行保留 `Model.provider = "moonshot"` 并用 `buildModel` 设实例地址。Moonshot 的工厂发现尊重 `config.baseUrl`；推理却在 `resolveOpenAIRequestSetup` 里以进程的 `MOONSHOT_BASE_URL` 再盖一次，即使 `model.baseUrl` 非空。因而发现、探测或界面可指向实例网关，真实请求与 Bearer 密钥去了另一个地址。与第 5 条不同，这里发错的是推理，问题不在目录工厂。
- 如何核实：`bun lab/template-route.ts` 调实际 `ompCall`，两个本机端点、虚构 key、同一 `baseUrl`。中性 provider 仅击中 `instance-config`，`moonshot` 仅击中 `moonshot-env`；两者实收 `/v1/chat/completions` 和虚构 Bearer。未用真实端点或凭据。
- 建议改法：明定实例地址覆盖的最终优先级，让上游区分宿主锁定地址与可被环境改写的模板缺省；逐个核对会根据环境或凭据变更请求地址的专用分支。锁定的是线上的目的地而非配置字段；同一实例的发现、检测与推理须按同一地址合同验收。不能兑现的覆盖按明确错误拒绝，不把密钥转给另一个源。

### 25. 切到通用协议后，实例 id 仍可能触发原本要退出的专用分支
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 53、57、70、86–87、161 行，决定 1；`packages/nb-models/src/config/rules.ts:27–39`；`pi-ai@18.14.0/src/providers/openai-shared.ts:255–290`。
- 现象：计划在协议覆盖或空白模板时把 `Model.provider` 换成实例 id，以退出模板的 OMP 专用处理。但第一个 Moonshot 实例的 id 可正是 `moonshot`；自定义实例也可能用目录里未被占用的名字。按其规则切到通用协议后，这个值没有变，照样触发基于 `model.provider` 的分支。同模板第二家 `moonshot-2` 的兼容行为反而不同。OpenRouter 对同名 provider 加特定头，是另一处直接的分支。
- 如何核实：第 24 条的本机实收对照表明，仅更换 provider 字符串就能改变实际目的地。验收再由公共配置创建同模板两实例和同名空白模板，指定相同通用协议和地址，比较实际请求；还原跟随时才恢复专用行为。
- 建议改法：将实例引用留给宿主；明确跟随模板时才选原生 OMP 身份、协议覆盖时选不会撞任何已知 provider 的中性身份。保留用户字段，不无条件带入旧协议的 `compat`、`requestModelId` 或动态头；需要重建的字段按本次协议决定。

### 26. 协议覆盖和角色档缺少清除语义，改档还可能覆盖另一个窗口的角色绑定
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 57–58、65、98、101 行，决定 1、6、13、15；`packages/nb-models/src/contract/settings-spec.ts:41–60`、`src/core/core.ts:380–388,434–445`；`docs/specs/models/service.md` 输出 6。
- 现象：v2 以字段缺失表示跟随模板协议／模型档，但计划只说写入方法加字段。现合同里 `baseUrl:null` 才是删除，省略是“不改”，`api` 没有清除值。保存过通用协议后，按这条路径无法回到模板的专用协议或混合协议。`setRole` 目前强制携带 `model`：窗口 A 已将角色由 X 换成 Y，窗口 B 用旧快照只改档，却不得不再提交 X；服务端在最新层做 CAS 仍会成功把角色改回 X。反过来，仅重绑也不应清掉明确配置的档位。
- 如何核实：一个目录实例从跟随改到通用协议，再恢复，断言线协议；两个 RPC 客户端交错改同一角色的模型和档。另验“跟随模型”会删除已存的 `effort` 而不改绑定。
- 建议改法：在版本 2 合同按字段打补丁，区分省略不改、`null` 清覆盖、具体值写入；角色只改档不传 `model`。保留第一次绑定 `fast` 的播种规则，只在模型字段真的由未绑定变为绑定时触发。

### 27. 刷新只挂在几个 RPC 上，直接改设置不会加载新来源
- 严重程度：重要；类别：不变量。
- 位置：固定计划第 77–81、93–98、163 行，决定 3；`packages/nb-models/src/core/core.ts:83–97,129–144`、`packages/neuro-book/src/plugins/models/backend/settings-store.ts:17–18,36–45`；`docs/specs/models/service.md` 输出 6、7 及“状态与转换”。
- 现象：计划列了入口激活、`addProvider`、`setKey`、改地址／协议的 `updateProvider` 和手动刷新。直接写设置文件创建或改服务商不经过这些 RPC；`onChange` 现有逻辑仅清快照和解析缓存。按计划的同步 `sources.models(id)` 读不到从别处新增实例的缓存，也不会拉它；直接改头、认证，或 `clearKey` 后同样没有来源切换触发点。已使用的模型可先变 `unknown-model`，或继续拿到旧认证范围的目录（第 6 条）。
- 如何核实：在真实设置场地用第二窗口写配置文本，不调用模型的编辑方法；验新配置的离线命中、冷缓存后台更新、删后不继续刷新、关自动更新时不出网。看第一份 `changed` 与同步 `resolve` 是否用了同一代次，而不是只看最后一份列表。
- 建议改法：由模型核心对有效设置和凭据变化统一协调来源，RPC 只声明需要强制更新的意图。首份快照前恢复本地数据或提供明确加载状态；定义自动开关更改的行为，网络传输不占写队列，提交时一次清解析缓存并发变更。手动 `online` 不得被一条只读缓存的在途任务吞掉。

### 28. OpenRouter 的对话列表拉取失败，其他列表成功会把结果标成新鲜
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 85、95–96、163 行，决定 2、3；`pi-catalog@18.14.0/src/provider-models/openai-compat.ts:3585–3596,3807–3825`、`model-manager.ts:353–370,411–424`。
- 现象：描述器并发拉 6 类列表，只有 6 路全失败才回 `null`。对话 `/models` 回 503，其他 5 路只回成功空表，工厂也把本次交成成功；ModelManager 可丢掉旧缓存、改为打包对话名单，并标 `stale:false`。对话侧旧在线模型从有效列表和解析里消失，与“失败保留上一份并标 stale”相反。即使修复第 6 条的缓存命名空间，同一来源也会发生。
- 如何核实：`bun lab/openrouter-partial.ts` 使用本机 6 路端点与临时 SQLite，隔离打包种子。健康时得到 `fixture/chat`；仅对话路由改为 503、其余 200 后，对话结果变为 `[]`、`source:"provider"`、`stale:false`。
- 建议改法：以对话子来源结果作为对话成员的新鲜度和替换依据，不把图片、排序等成功算给它；可用只查询对话的公开适配器，或由上游交回分来源状态。验收把这一组与真正的成功空对话表分开。

### 29. 量一个 OpenRouter 快照漏掉累计体积，也漏掉会被硬上限拒绝的设置写入
- 严重程度：重要；类别：安全与性能。
- 位置：固定计划第 56、94、98、162、188 行；`packages/nb-models/src/contract/settings-spec.ts:87–88`；`packages/neuro-book/src/plugins/settings/shared/contracts.ts:96–99,118–130`；`packages/nb-host/src/server/rpc-listener.ts:79–90`、`rpc-listener.test.ts:80–90`；`docs/specs/runtime/plugin-channel.md:117`。
- 现象：模型服务每次 `changed` 当前推整份快照，不是一家。用锁定目录的对话行做合成快照，OpenRouter 为 587 行、173,114 B；NanoGPT、Kilo、OpenRouter、Vercel AI Gateway、AIMLAPI、ZenMux、Venice、NVIDIA 共 3,790 行、1,081,145 B，已超过 1 MiB 的合同值，未计上传图标与用户覆盖。更直接的入站路径是设置文件编辑器：23 个合法范围内、各 46,000 字节的 data URL 仅字符串就 1,058,000 B，`writeText` 还要带完整文本与 RPC 外壳，不能经 1 MiB 入站限制保存；按家读取模型不能修复这条路径。
- 如何核实：合成目录大小不是产品出站实测；现有硬限制测试是客户端发超长帧。实现验收应经真实 WebSocket 衡量多实例的 `snapshot`、连续 `changed`、重连首帧，以及带图标和冻结成员的设置文件读写；都量 UTF-8 线字节，不用字符数。
- 建议改法：第 3 片先定总预算与超限行为，按服务商拆页或发有代次的变更提示，不等单商超过才拆。图标容量按设置 RPC 总预算算；如不限制累计图标，就采用独立资源存储与有界上传，或者调整整份设置读写的传输合同。前端少渲染行不减少这些负载。

### 30. 模板可添加、可推理、可发现是三种能力，计划只按是否有发现工厂分支
- 严重程度：重要；类别：正确性。
- 位置：固定计划第 54、57、69、85–87、97、184 行，反馈 3，决定 1、13、20；`packages/nb-harness/src/models/catalog.ts:74–85`、`packages/nb-models/src/core/core.ts:367–376`；`pi-catalog@18.14.0/src/provider-models/descriptors.ts:1–9,191–205`、`src/compat/rules/providers/azure.kdl:3–5`。
- 现象：Azure 有 API Key 配置与 `azure-openai-responses` 模型，但没有描述器工厂，不能因缺工厂就调用四种通用列表发现之一。反过来 Cursor 的认证分类是 `login`，却有描述器；如计划只把它归到默认收起的组，服务端仍可能接受添加。第 8 条是实际支持 Cursor 或漏掉服务端准入时的后果，不是要求本任务做 OAuth。保留模板作元数据参照没问题，但只按模板找工厂也不能兑现“由 Gemini 模板建成 GPT 兼容实例”后的 OpenAI 发现。
- 如何核实：以锁定依赖列出受支持模板的鉴权、实际协议、可用列表方法；经服务端合同测试 Azure 无专用发现时不会猜地址、登录专用模板不启动后台刷新，以及原生 Gemini 实例切为通用 OpenAI 后的实收列表路径。
- 建议改法：用模板提供初始值与能力参照，按实例有效协议、地址和认证选择发现适配；服务端对登录及不支持的组合给明确失败码。只有静态目录的仍能用静态模型，重新拉取要能明确区分已更新、未实现与失败。若产品要求每家都能实际发现，先列必须补的适配器再切片。
