### 1. 只比 URL 的源，会放行改到同一主机另一部署路径的请求
- 严重程度：阻断；类别：安全、与 ADR 的保证不一致。
- 位置：取舍 3、B.4、切片 B4；ADR 0057 决策 4；`pi-ai/src/providers/openai-shared.ts:270–295`。
- 现象：第三稿新增的 fetch 钩子确实能看到 Moonshot 改写后的 URL，但 `.origin` 只有协议、主机和端口，不含路径。环境变量只改路径时，设置没变、部署哈希没变、两项检查全过。
- 为什么是问题：反向代理可以用路径隔离两个不同的部署或租户；密钥、对话和工具结果会送到非配置的部署。这不是第二轮已处理的跨源改址。同一条规则还会把该回复的日志归在未实际作答的部署下。
- 如何核实：在隔离目录运行 `bun --no-env-file egress.ts`（Bun 1.4.4、pi-ai 18.14.0，本机 HTTP、虚构凭据）；配置 `/saved/v1`，环境改为同源 `/other-tenant/v1`，钩子确认同源，服务端实收 `/other-tenant/v1/chat/completions`，请求正常结束。
- 建议改法：匹配规范化后的协议级线请求地址（含路径、协议允许的查询参数），不是字符串前缀或裸 origin；不可解释的改写在发送前拒绝，保留 `endpoint-mismatch`，验收断言两个端点实收均为零。ADR 已定「请求的源必须等于实例有效地址的源」；这里建议保留该条件并加严，以兑现同条的防改址目标。

### 2. 写前看到“键不存在”，锁内仍会把刚写入的坏值覆盖
- 严重程度：重要；类别：数据丢失、CAS。
- 位置：B.2「写前核对」、B2 验收；`settings-store.ts:24–33`、`settings/shared/instance.ts:250–265`、`settings/backend/layer-owner.ts:189–217`。
- 现象：模型适配层预检时没有问题，得到 `expect: {present:false}`；用户在实际写入前保存了一个 schema 不接受的 providers 值。设置拥有者锁内从 `parsed.values` 看到这个键不存在，忽略记着该键的 `parsed.problems`，CAS 通过并覆盖用户原文。
- 为什么是问题：第三稿修的是预检时坏键已经可见的情况，不是第二轮第 32 条的重复；从预检到带锁写入的窗口仍违反“真没有键才创建”。重读、重试只能处理被判为冲突的写，此处直接成功。
- 如何核实：`bun --no-env-file --tsconfig-override packages/neuro-book/tsconfig.json …/settings-race.ts`，用真实 `createLayerOwner`、providers 声明、文件解析和替换：快照 `checkedProblems:[]`，外部文件确实已有该键，结果 `writeOk:true`，磁盘变成 `{"nbook.models/providers":[]}`。
- 建议改法：让设置拥有者在锁内比较目标键的实际状态，把缺省、存在但无效、存在且有效分开；或提供受支持的文本修订 CAS。若键变坏返回不可写、保留原文；有效值冲突才重读归一。验收让外部写发生在预检之后、加锁比较之前，并断言原文逐字节保留。

### 3. 同名删建或换了签发凭据，历史签名仍会被认成同部署
- 严重程度：重要；类别：会话兼容、隔离。
- 位置：取舍 3、B.2、B.4、B4 验收映射；`nb-models/src/config/rules.ts:31–40`；`pi-ai/src/providers/transform-messages.ts:943–979`。
- 现象：实例 id 是可重用的名称 slug，B3 已安排验“删除后同名重建”。用同一名称、地址、协议和模型重建时，旧 `assistant` 事件与新目标的四元组完全相同。原地换成另一账号的同地址密钥也不会改变四元组；pi-ai 给签名型 Anthropic 端点另做 `credentialId` 比较，两侧都有 id 才生效，而 nb-harness 当前传的是字符串 `apiKey`，不传凭据身份。
- 为什么是问题：删实例时清缓存/密钥不会清该实例生成的会话历史。新实例可重新接上旧的签名、加密推理、工具续写元数据；新凭据也未必能让端点验证旧签名。第二轮已修不同实例 id 或不同地址，这里是四项都相等的例子，不质疑旧日志按旧规则。
- 如何核实：对照 slug 生成、ADR 0057 决策 4 的哈希输入、OMP 的 `foreignCredential` 和 nb-harness 的 `ompCall` 入参；为代码推导，未调用真实签名服务。
- 建议改法：新增持久、不可复用的实例世代标识供新日志回放（展示 id 可保持）；签名型协议另比较不含原文的凭据身份，无法证明时降级成无专用元数据的历史。ADR 原文「`deployment` 是实例 id 加有效地址与协议的哈希，不含凭据」；凭据身份单列，不把密钥放入部署哈希或日志。B4 验同名同址删建、同址换凭据，并经过会话关闭重开而非手造 `Message`。

### 4. v1 目录实例只要覆盖了地址，冷启动就接不回原来可用的模型
- 严重程度：重要；类别：升级回归、物化。
- 位置：B.2「v1 的读法」「来历决定解析」、B.3 `catalog.ts`、B2/B4 验收；现行 `models/service.md` 输入及输出 8；`nb-harness/src/models/target.ts:158–174`。
- 现象：合法 v1 目录服务商可以填中转地址，模型行只存 `{id, enabled:true}`；旧 `catalogModel` 用打包模型，仅覆盖地址。新读法把它归为 `origin:"source"`、保留地址覆盖；冷启动没有新缓存，而 B.2/B.3 只给跟随模板的实例回落到打包元数据。即使新端点回 OpenAI 形状的列表，它通常也只有 id，不给窗口。
- 为什么是问题：不改一字的设置升级后会从可调用变为 `source-unavailable` 或“需补字段”，绑定的角色也断；对不上验收“v1 设置读进来行为不变”。与第二轮修复的“旧字段被激活”不同，这是本来生效的打包元数据被切断。
- 如何核实：按现行类型、`target.ts` 与第三稿的读取顺序代入 `anthropic` + 显式中转地址 + 已启用的打包 Claude id、无 B 缓存；OpenAI 的官方 `/models` 文档只保证 id/归属等基础字段。
- 建议改法：迁移时按 v1 行为给这批已选模型播种无凭据的已知元数据（窗口、上限、模态等），和后续跟随/发现分开；不复用旧的专用认证、路由或签名。若不能兼容这种实例，明确哪类升级会停用、怎样恢复，并改对应验收，不能留一句“行为不变”。测试在无缓存、列表失败或只报 id 的情况下绑定原角色发一次本机请求。

### 5. `addable` 拦不住已保存的非 fetch 传输，迁移会绕过闸门或断老会话
- 严重程度：重要；类别：升级、出站边界。
- 位置：B.1 `addable`、B.2 v1 读法、B.4 `OmpTarget.fetch`、B1/B4 验收；`nb-models/src/core/core.ts:136–150,376–395`；`pi-ai/src/providers/cursor.ts:1327–1331`。
- 现象：第三稿只说 Cursor、Bedrock、登录类模板不能新加；v1 目录实例却全部映射到原模板，未定义这些既有实例能否解析发送。现行 `addProvider` 对目录条目不检查 `access`；现行 schema 和手改设置也能导入，解析只检查行、目录和凭据。Cursor 的 HTTP/2 分支直接 `http2.connect`，没有从 `OmpTarget.fetch` 通过。
- 为什么是问题：若为保持 v1 行为继续放行，这些请求绕过 B.4 承诺的地址核对和重定向设置（C 的出口也管不到）；若实现顺手在解析挡掉，又会无提示停用已有配置。“禁止新加”不能同时回答这两种情况。
- 如何核实：`bun --no-env-file catalog-contract.ts`：已装目录 Cursor 有 123 行 `cursor-agent`，Bedrock 有 219 行 `bedrock-converse-stream`，Codex 有 9 行 `openai-codex-responses`；对照输入 schema、服务解析和 Cursor 传输源码。未给这些服务商发请求。
- 建议改法：按实际传输逐模型做服务端准入（包括 v1、手改文件、复制、打开缓存），不按模板能加就认所有模型可发送。无可接管传输的已存配置原样保留并明确不可发送的码和迁移办法，或先提供等效闸门；B4 增加 v1 非 fetch 行“不创建出站连接”的验收。

### 6. 一份凭据绑定的缓存不能兼做“消失模型继续可用”的历史
- 严重程度：重要；类别：缓存身份、用户数据连续性。
- 位置：B.2「关掉自动加入」「来历决定解析」、B.3 `cache.ts`，验收映射“来源消失时被引用的仍可调用”。
- 现象：同一部署下，账号 A 的列表含模型 X，用户绑定角色或冻结了 X；设置只存模型 id 和覆盖。换账号 B 使 HMAC 变，第三稿规定不读 A 的缓存；B 的首次成功列表不列 X（也可能是完整空表）。没有旧成员可转为 `missing`，X 若不在打包目录，只能报 `source-unavailable`。模型仍能不能调用可以由端点决定，但本地连物化都做不到。
- 为什么是问题：第二轮已删 `retired` 并以成员行物化字段代替；第三稿只给同一个成员文件一个列表身份，旧行仍在换凭据时整份失效。保留旧账号的整个列表也不对，会把旧账号的未选模型带到新账号。这两个需求需要不同的有效边界，不能靠冻结标记解决。
- 如何核实：按计划的读顺序走“新发现、未打包的 X → 绑定或冻结 → 地址协议不变只换 Key → 新列表 `[]` → 重新解析”；当前 B3 测试只要求“不读旧缓存”，消失测试没组合这两个条件。
- 建议改法：二选一并写入 Spec：同部署下单独保留已选行所需的无凭据物化数据，不让它充当新账号的来源成员；或明说换目录鉴权是断代，停止旧行解析并让用户能重新补字段。不要恢复无限保留的 `retired`；验收分别考察保留已选与不沿用未选、改部署后一律失效。

### 7. 改地址与换密钥没有安全的交接点，自动发现会使用中间状态
- 严重程度：重要；类别：凭据边界、设置时序。
- 位置：B.3 `coordinator.ts`、B.5 `updateProvider`/`setKey`、B.6 保存后再测；现行 `models/service.md` 输出 1、13。
- 现象：把已有带密钥的实例从部署 A 改到需另一把密钥的 B，地址与库中的密钥分别保存。先存地址，按有效配置变化刷新的列表会向 B 带上 A 的密钥；先存密钥，填完即拉的请求则向 A 带上 B 的密钥。现行 `requestAuth` 按实例 id 读密钥，不绑定地址，且 `headers` 也能配置认证。发送前核对部署身份只拦过期的解析：这里每次新解析都读取了刚提交的一半。
- 为什么是问题：自动发现替用户执行了原本可以在改完两项后才手工执行的外联；B.6 又要求先保存再检测。换地区、覆盖地址和复制一份再改址都有相同路径。
- 如何核实：对照 `target.ts:114–138` 与 `core.ts:399–409,491–507`，把计划规定的“填完密钥立即拉”与“设置变化统一协调”代入；这是新旧机制组合的时序推导，不是对真实服务商发请求。
- 建议改法：新部署不得自动接手旧部署的有效认证（含认证请求头）；在服务端把地址与凭据继续使用、置空或更换的选择一起结算，完成前不允许任何入口出站。保留“只测已保存配置”不变。用两个回环端点和不同虚构密钥验证两种编辑顺序间都没有错误收件方。

### 8. `openrouter` 的实际协议会变，回复里的 `api` 却不变
- 严重程度：重要；类别：协议选择、会话回放。
- 位置：取舍 3、B.1 `routes`、B.4 `origin`、B.6 “与对话同一路径”；`pi-ai/src/stream.ts:924–948,2007–2035`。
- 现象：模板跟随若沿用打包目录的 `api: "openrouter"`，pi-ai 受 `PI_OPENROUTER_RESPONSES` 控制在 Responses 和 Chat Completions 之间切换。出站闸门只比源，地址根和配置哈希都不变；两种回复的原生 `api` 也都仍为 `openrouter`。按见到的回包字段填写 `origin`，两个不同线协议仍相等；检测结果不能按该字段选“和对话一样”的路由。
- 为什么是问题：两种协议的签名与工具续写字段不通用。选择器写的是四种公开协议，不承诺另一个可被进程环境翻转的第五种。第二轮解决了把列表路径当推理路径；这个反例不改变列表请求。
- 如何核实：`bun --no-env-file probe-observation.ts` 用原生 `streamSimple` 与回环服务：环境 `1` 实收 `/api/v1/responses`，`0` 实收 `/api/v1/chat/completions`，两边都交回 `api:"openrouter"`。
- 建议改法：B1 明定 OpenRouter 经过实测的线协议，物化时用显式 `openai-responses` 或 `openai-completions`，可保留 `provider:"openrouter"` 的受控兼容策略；或把上游实际路由决议变为同一处可调用的纯能力，探测、闸门及 `origin.api` 都吃它。不要从回包的 `api` 反推。B4 用切环境变量的两次调用验证协议不漂移或签名不跨协议恢复。

### 9. 旧日志的同服务商判断会被中性身份改变，新增字段也没有列清回放链
- 严重程度：重要；类别：向后兼容、验收。
- 位置：B.4 `OmpTarget.name`/`ModelResponse.origin`、B4；`kernel/model/omp.ts:183–204,371–385`，`kernel/run/loop.ts:380–389`，`kernel/api/events.ts:166–176`，`kernel/view/format.ts:134–144`。
- 现象：同一个 v1 自定义实例、相同端点和协议，旧日志的 `assistant.model` 是 `<实例 id>/<模型 id>`。当前 `toContext` 用第一段和 `Model.provider` 比；升级后后者固定为 `nbook-compatible`，照抄旧规则会把原本同服务商的回复改成 `api:"unknown"`。新日志也不是在 `ModelResponse` 加字段就能回放：事件写入与历史投影都是逐字段构造，`RequestBlock.origin` 另有既有含义。
- 为什么是问题：不改地址也会丢旧回复的原生推理/工具续写信息；没有覆盖重开路径的适配器测试能过而日志仍没写 `origin`。同样，`ompModelInfo` 仍从原生 provider 拼 id，仅改 `ompCall` 的模型名不会令 `ModelRequest.model`、会话快照等统一为公开引用。
- 如何核实：沿现行调用路径和会话字段逐项对照，将同一自定义实例的旧日志输入代入 v2 身份规则；`kernel/run/loop.ts:310` 使用 `resolution.info.id` 作为请求模型。
- 建议改法：明确无 `origin` 时用旧的实例 id 映射进行旧规则判断，不能拿新的中性 id 直接对比，也不补历史地址。新事件用独立的可选回复来源字段贯通日志、重开投影、`Message`、`toContext`；不匹配时主动不还原专用字段，避免把隔离完全交给 pi-ai。公开引用、实际作答模型、签发/回放身份分开赋值。验收加同部署 v1 日志重开与新的多轮重开。

### 10. 上传合同的裸字节过不了 RPC，过了头检查也不一定能显示
- 严重程度：重要；类别：接口、输入校验。
- 位置：技术选型「上传图标」、B.5 `setIcon`、B.7、B5 验收；`docs/specs/runtime/plugin-channel.md`「编码」；`nb-runtime/src/remote/json-codec.ts:27–52`。
- 现象：`png: bytes` 若按 `Uint8Array`/`Buffer` 实现，现行 RPC 帧会在发出前拒绝；计划没规定 JSON 线格式。第三稿的 IHDR 尺寸和 `acTL` 检查也不能保证 PNG 可解码：一个只到 IHDR 的 33 字节文件有合法魔数、尺寸 1×1、无动画，但没有像素数据。
- 为什么是问题：客户端画布产生合法 PNG，只证明正常入口，不替代服务端合同。真 RPC 会拒收正常上载，或按字面头检查成功绑定一张坏图。第二轮已经加尺寸与动画检查；这里的反例通过这两项。
- 如何核实：`bun --no-env-file icon-wire.ts` 调现行 `encodeJsonValue` 实得 `FrameEncodingError: 字段 png 不是普通对象（Uint8Array），JSON 不能如实表示`；那份截断 PNG 用 `Bun.Image` 实得 `Error: Image: decode failed`。
- 建议改法：同一次 `setIcon` 仍完成上传绑定，明确用有界 base64 字符串、校验解码后的 ≤64 KB；尺寸与动画预检后有界解码或规范化，再发布成品。B5 走真 RPC 验 64 KB 边界、损坏图不改配置，以及共用摘要的第二次绑定遇 CAS 失败时原图仍可读。

### 11. 768 KiB 是磁盘文本预算，不是设置全文的 RPC 预算
- 严重程度：重要；类别：线协议、验收。
- 位置：B.2 冻结、B.5 模型分页、B7；`settings/shared/contracts.ts:96–99`、`docs/specs/settings/configuration.md` 输出 24、`nb-host/src/shared/socket.ts:15`。
- 现象：设置文件被包进 `{text, revision, ...}` 再做 JSON 编码，原文里的反斜杠、双引号和控制字符会再次转义。冻结按原始 UTF-8 长度卡 768 KiB 时仍可生成超过 1 MiB 的 `readText` 响应和 `writeText` 入参；`snapshot` 移除模型行没有改变 `nbook.settings` 这条合同。排除、模型设置、服务商/角色元数据等写法也没有这个冻结专用上限。
- 为什么是问题：模型功能可以制造一个自己还能读、但设置文件编辑器不能再经 RPC 读写的文件。常规 8×600 的短字段数据不能证明可达输入的上限，也不能证明单行长名称不会单独撑满模型分页。
- 如何核实：`bun --no-env-file wire-limits.ts` 以合法字符串字段构造文件：磁盘 620,161 B（<786,432），仅 `JSON.stringify({text})` 已 1,240,200 B（>1,048,576），尚未加 RPC 帧。
- 建议改法：按完整线帧 UTF-8 字节做拒绝/分段，而不是以磁盘字节推断；把设置文件的通用大文本传输作为上游选项（仓库 Files 已按转义后字节验收）。若保留当前合同，至少所有新增业务写按同一有效预算核对并避免制造超限文件；B7 加转义密集与单行超限反例。

### 12. 首个合法 SSE 事件可能只是握手，不能当作一次生成通过
- 严重程度：重要；类别：探测语义、验收。
- 位置：B.6「第一个有效事件」、B5 验收；`pi-ai/src/providers/openai-responses.ts:993–1019`、`openai-completions.ts:1052`。
- 现象：Responses 可以先发完全合法的 `response.created` 再发 `response.failed`；Anthropic 的 `message_start`、空 Chat Completions 角色帧也不说明能生成内容。用库的 `start` 更早：部分适配器收到 HTTP 响应就发出。第三稿没给四种“有效”的负例或判定字段。
- 为什么是问题：把首个可解码帧认作成功，会在端点已明确返回额度、模型、权限等生成错误时让用户采纳该协议。另写探测请求避免了 OMP 重试，但不会自动修正此判定。
- 如何核实：`bun --no-env-file probe-observation.ts` 的本机 Responses 流按顺序发 `response.created`、`response.failed`；真实 pi-ai 最终报 `server_error`，这次逻辑请求实收两次 HTTP，证明既不能照搬 `start`，也不能用原流入口承诺单次。
- 建议改法：定义逐协议的首个生成证据；心跳、角色、created/start、空候选不算通过，证据之前的错误优先，EOF/超字节失败；证据到达即 cancel 读取器并中止 fetch，不能再触发第二次。若只承诺握手，状态单列“已打开协议流”，不能与 `check` 通过等同。B5 加“先合法头再错误”、长开流验证取消实收、3xx 不跟随三个反例。

### 13. 分页没有把读到的模型行绑到同一个修订
- 严重程度：重要；类别：后端读合同、并发。
- 位置：B.5 `providerModels`、`enabledModels` 与 `modelsRevision`；B7。
- 现象：两个分页方法的输入只有 `offset/limit`（管理页另有 `query`），没有期望修订号；也没规定页的修订、顺序和下一页。读取 `[a,b]` 后来源刷新成 `[x,a,b,c]`，offset=2 得 `[b,c]`，这样读全重复 b、漏 x。`changed` 有修订号，但事件与不同请求的结果不是一个事务；断线还能错过通知。
- 为什么是问题：仅分页解决字节数，不能兑现“启用清单读全”或让管理页的成员和计数一致。时间窗由 B.3 的正常后台刷新、Role/Profile 改动或用户排除即可触发，不需要网络失败。
- 如何核实：把上述成员序列代入计划的 `offset` 合同；B7 只有单份大清单的逐页大小检查，未跨修订读取。是合同反例，不是尚未实现的 RPC 实测。
- 建议改法：页输出带 `{revision, rows, nextOffset}` 和稳定排序；后续请求带首个页的修订，已换代明确失效、重读首个页，不让两代拼起来。修订覆盖实际出现在该列表的数据。每页仍限完整帧字节。B7 加首、次页之间发布新来源和变更角色引用的夹具。

### 14. 推理协议已变，列表 HMAC 一样，仍会读到旧模式物化的能力
- 严重程度：重要；类别：缓存身份、能力边界。
- 位置：B.2 来源读取优先级、B.3 `cache.ts`、`catalog.ts`、`coordinator.ts`、B.4 物化；前轮处置第 5、6、8 条。
- 现象：一个跟随模板的 Chat Completions 实例和改成 Responses 之后，可以打同一个 OpenAI 形状的 `GET /models`：地址、列表协议、认证与请求头全同，列表 HMAC 不变。原成员行已经融入在线/打包窗口、价格等；B.2 优先从成员行读，B.3 又规定只有跟随模板时才能用这些值。同一个问题出现在旧列表飞行中、只更改物化规则的配置时。
- 为什么是问题：列表身份回答“这次得到哪些 id”，不回答“这些 id 用哪些推理能力”；HMAC 正确也挡不住改协议后沿用旧价格、推理档和窗口。不是第二轮所修的“有效请求头没进 HMAC”。
- 如何核实：比较 `listing.protocol:"openai"` 与 B.2 的两个推理协议，按 B.3 的五项规范化输入计算，相同；沿 B.2「缓存里的成员行 → …」无法区分列表原生数据和模板补值。
- 建议改法：列表行保留原生字段及证据；模板补值在当前部署/物化策略下另算，必须持久化的历史成员再标它的物化身份。签名的 HMAC 不负责这层。验收仅切协议而不变 GET，旧目录字段不得出现在新解析，列表仍可复用。

### 15. 探测结果虽说带版本，采纳 RPC 没有提交这个版本的合同
- 严重程度：重要；类别：CAS、远程合同。
- 位置：B.5 `updateProvider`、B.6 采纳、B5 验收；现行 `nb-models/src/contract/settings-spec.ts:40–51`、`models/service.md` 输出 6、13。
- 现象：第三稿已经要求“用这个”核对检测时的地址、协议和凭据，但 B.5 只为 `updateProvider` 列出新 patch 字段；当前输入 schema 不收其它字段，`detectApi` 与普通编辑之间没有一个要携带检测版本的写入入口。现行设置 `expect` 也只比较配置键的原值，凭据库改行不会使这个 CAS 冲突。地址相同、改了认证请求头、路由或目标模型也会让探测失效。
- 为什么是问题：光在 `detectApi` 输出带版本、或在页面清结果，不能阻止已经发出的采纳与另一个写入交错。第二轮第 15 条的“只用已保存配置”和“库凭据代次要核对”保留；这里是 B.5 还没有给该判定提供输入与结算边界。
- 如何核实：对照 B.5 的方法一览和现有严格 schema；依次让检测成功、另一次 `setKey` 仅改库、发 `updateProvider` 修改协议，现行 patch 与 settings CAS 不带前次检测的任何证据。为合同走查。
- 建议改法：给采纳单独方法或严格的 `expectDetection` 入参，绑定检测时实际端点、协议、模型及有效认证版本；在模型写队列里核对库版本，同时依赖设置所有者的锁内 CAS，冲突不重基成无条件写。验收分别改库密钥、请求头和有效地址，并通过远程方法验证拒绝版本而不是只测页面。

### 16. 自动拉取能把坏配置造成的缺省值误认成用户删除实例
- 严重程度：重要；类别：缓存寿命、设置服务边界。
- 位置：B.2「写前核对」、B.3 `cache.ts`/`coordinator.ts`；`settings/backend/layer-owner.ts:137–157`、`settings/shared/instance.ts:101–128`、`models/backend/settings-store.ts:21–43`。
- 现象：外部编辑保存了一份能解析、但 providers 中一行不合 schema 的文件，设置拥有者会从 `values` 丢掉整个键并记 `problems`，有效 `providers` 回到 `[]`。B.2 只保护写前不覆写，B.3 按有效设置变更做协调并“删实例时删文件”。若将有效集合差直接当删除，缓存被删；外部修好原配置也找不回之前冻结或绑定且已从列表消失的动态成员。
- 为什么是问题：缓存现在兼任历史物化，已不是纯性能缓存。用户未作删除；配置暂不可用不应触发不可逆清理。与第 2 条锁内覆写是不同副作用。
- 如何核实：真实设置竞态夹具的坏 providers 值被按缺省处理；沿计划用有效列表 `有实例 → [] → 有实例` 模拟协调器，预计会走删除分支，计划未定义这一过渡。纯 JSON 语法错误保留上一份有效层，是另一条路径。
- 建议改法：把“经写入确认的删除/从有效原文确认的外部删除”与不合 schema、不可用、尚未就绪分开；后几种不提交新出站任务也不回收。缓存文件含版本、类型和边界校验，坏缓存作为不可用（不是成功空表），回收失败不让重建合同接手旧成员。验收先破坏一个合法文件内的条目再修回，断言仍有原缓存。

### 17. 强制直连在 B 首次生效，最低 Bun 版本却到 C 才改
- 严重程度：重要；类别：运行时兼容、切片。
- 位置：技术选型「代理」、B.1/B1 `fetchFor`、B.4；`packages/neuro-book/src/shared/product.ts:29–30`、`cli/run.ts:173–174`。
- 现象：B1 给模型服务直连入口，选型要求最内层显式 `proxy: false`；B 合入时 CLI 与发布包仍接受 `>=1.3.14`。Bun 到 [1.4.3](https://bun.com/blog/bun-v1.4.3#better-proxy-environment-support-in-fetch) 才公布单次忽略环境代理的开关；B 的门槛随 C 验收就晚了一段。
- 为什么是问题：在 B 自己声明支持的版本区间内，不能承诺请求不再继承代理环境。反过来，在支持新开关的机器确实强制直连，会中断原来靠环境代理可达、而在 B 又尚不能配置代理的用户。不是第二轮发现的“只改 package.json”：包含完整门槛的切片排在能力的首次使用之后。
- 如何核实：对照 B1、技术选型与现行 CLI 门槛；`bun --no-env-file fetch-contract.ts` 在 1.4.4 上给 `HTTP_PROXY` 指向本机夹具，`proxy:false` 一次命中目标，代理收零次。未用旧 Bun 实测；已装两个 OMP 包均另声明 `>=1.4.4`，核定应用下限时应一并对齐依赖。
- 建议改法：如果 B 必须强制直连，把生效下限、CLI/服务入口与发布产物检查移到 B1，并在发布说明注明这一段代理中断。若不能接受该中断，B 接上出站核对和禁止重定向，但出口暂保留现状，到 C 有配置入口时再切换；不要把继承环境的实现称为强制直连。保留决定 21「直连用 `proxy: false`（Bun 1.4.3 起；审查查出、主 Agent 复测）」。

### 18. v1 的“保留但不生效”没有能穿过首次 v2 写盘的表示
- 严重程度：重要；类别：迁移、配置语义。
- 位置：B.2 `models` 形状和「v1 的读法」、B2 验收；`nb-models/src/config/shapes.ts:25–40`、`nb-harness/src/models/target.ts:158–174`。
- 现象：合法 v1 目录行可以写 `vision:true` 或 `contextWindow:4096`，旧解析仍取打包的模态和窗口。第三稿说保留这些字段但不生效，而 v2 同名字段代表显式覆盖，`origin:"source"` 与 `frozen` 都不记录单个字段如何取得。读 v1 时知道该忽略什么，但在只改服务商显示名后若该实例按 v2 形状写回，冷启动就不能现算出哪些值以前是无效的。
- 为什么是问题：按原名原值回写等于悄悄激活；丢掉又不满足“原样保留”。它和第二轮第 10 条的区别在于：只在 v1 归一器里屏蔽旧字段，首次读进来的验收能过，写出 v2 再读仍会错。
- 如何核实：对照 schema 与 `catalogModel`，取一个 v1 目录条目，在同一份原文准备一个旧运行时忽略的字段；走“只改服务商名称 → 写出 v2 → 重启解析”的计划时序。此为持久化形状推导，B2 目前没有明确要求这个往返。
- 建议改法：明确转换边界：选择不写出旧无效字段并记录清理取舍，或给旧无效字段单独保留位置，只有明确编辑该字段才进入覆盖。设置写入的 CAS 仍用原文对应的值。验收比较三时点实际解析的窗口、模态等，不只比较设置结构。

### 19. 列表的 15 秒网络截止不约束排队提交，不能据此保证宿主排空
- 严重程度：重要；类别：停止、并发。
- 位置：B.3 `listing.ts`、`coordinator.ts` 与停止，B3 验收；`nb-host/src/server/start.ts:329–343`、`nb-runtime/src/remote/router.ts:227–245`、`nb-models/src/core/core.ts:250–254`。
- 现象：第三稿限定读体与全部分页的总时长，但列表结束后还要排入模型写队列，等持久化及发布。现行队列不能取消尚未开始的工作；设刷新在 14.9 秒收到末页，前方两个设置写各再占 3 秒，完成在 20 秒之后。即使不排队，B.3 也没有把在线目录的传输、解压和落盘纳入手工刷新的同一预算。
- 为什么是问题：宿主先排空 RPC（20 秒），随后才触发插件停止；路由端 `drain` 到截止只返回 `deadline`，不取消执行中的业务。停机夹具只让响应体挂起，能测传输取消，却不能测这段尾部，也不能保证已回超时的刷新后来不改成员。不是第二轮第 30 条所述“整个分页没有截止”，是新增截止没有覆盖结算。
- 如何核实：按现行 promise 尾队列、设置锁约 3 秒退避及 `await router.drain` 作时序推导；`bun --no-env-file fetch-contract.ts` 另证 Bun 1.4.4 的 signal 能中止已开流并让对端收到取消，未实测未实现的刷新队列。
- 建议改法：从 RPC 接纳起共用绝对截止，覆盖排队、读体、解压、暂存与提交资格；超时后未取得提交资格的工作有界撤掉，已过提交点的不谎报“没有变化”。或者手工调用只接纳任务、用状态事件说明成败，停止时按 B.3 规则收口；设置写仍照原合同结算。B3 在刷新即将到期时堵住写队列，并走真实宿主停止。

### 20. 删实例成功后、删缓存前崩溃，同名重建会继承上一个实例的清单
- 严重程度：重要；类别：持久化、删除与重建。
- 位置：B.2 实例 id、B.3 `cache.ts` 与 `coordinator.ts`、B3「删除后同名重建」；`nb-models/src/config/rules.ts:31–39`。
- 现象：设置和缓存不是一个原子提交。实例 `local` 的设置已写成删除，缓存 `local.json` 尚未删除就崩溃；重启只有“未配置这个实例”，没有一次旧实例删除事件。用户同名重建同址的免认证服务商时，id、有效列表请求及状态根 HMAC 密钥都相同，孤立文件的校验能通过。完整空表也会被继承。
- 为什么是问题：同目录原子替换解决的是一份缓存文件的半写，不覆盖设置与缓存之间的崩溃窗口；内存代次也跨不过重启。正常退出后同名重建的 B3 用例可以通过，仍排不掉这个反例。第 3 条是签名历史，这一条是来源成员被复用。
- 如何核实：对第三稿的两个落盘点作故障时序推导；拟做夹具只在隔离状态根留下“设置删除已提交、旧缓存文件还在”的状态，重开后先断开列表端点再重建，断言不读旧成员也不把旧空表当权威。
- 建议改法：读缓存必须匹配现存配置的不可复用实例世代（可与第 3 条共用），不把 `unlink` 是否成功当作防串用条件；删除文件只是回收。有效设置确认未引用才清孤立文件；坏设置或层未就绪按第 16 条处理。

### 21. 本机未知模型默认启用，但只有 id 的模型仍不能解析
- 严重程度：重要；类别：决定落地、模型能力。
- 位置：B.2「来历决定解析」、B.3 `listing.ts` 与 `unknown`、B3 验收；`nb-harness/src/models/target.ts:176–187`，`kernel/compaction/compact.ts:54–62`。
- 现象：决定 25「本机与空白模板里类型不明的模型默认启用」。现有本机夹具 `/models` 给 `qwen3:8b` 和 `gemma3:12b` 的 id，没有窗口；空白模板明确不借打包元数据。B.3 可以把这两行标 `unknown` 又设 `enabled`，但不能据此给出可用窗口。若把“需补字段，不启用”只施加给已判为 `chat` 的行，反而是证据更少的 `unknown` 能穿过。
- 为什么是问题：保留现行正整数窗口要求，会出现“已启用但不能选用”的默认状态；若用 0 绕过，内核没有固定触发点时不按阈值压缩。第二轮修的是未知项一律不启用，这里是启用与可解析的合同仍相撞。
- 如何核实：`plugins/models/models.test.ts:23–42,295–307` 的列表正是 id-only；该用例对话通过靠另存了窗口，不证明自动启用后的行能发。用同一端点新增空白模板，不预填窗口，验收同时断言成员、启用状态、可调用性与补字段后的恢复。
- 建议改法：区分“自动加入成员”“用户要求启用”“可解析”。先取本机端点明确提供的窗口；字段不全时可进列表并保留启用意图，不计入可用清单。若决定 25 的“启用”专指立即可调用，则须重定“先补窗口”的例外或另定明确的本机未知窗口策略，不默填猜测值。

### 22. `enabledModels` 承诺包含 Profile 引用，核心却拿不到这些引用及变更
- 严重程度：重要；类别：包边界、读合同。
- 位置：B.5 `enabledModels`/`modelsRevision`、B5/B7；`nb-models/src/core/core.ts:76–104,358–373`、`plugins/agent/backend/agent.ts:221–225`，ADR 0045 决策 2。
- 现象：共享模型核心只订阅模型设置与凭据；`port(profileDefaults)` 是 Agent 调它时传入的单个 Profile 回调，不是可枚举、可订阅的来源。直接指定模型的引用存在 `nbook.agent/profileSettings`。只改 Profile 指向一个仍存在但停用的模型时，不会触发当前 models 核心的任何失效。
- 为什么是问题：分页可以永远漏掉应随页返回的停用行，或引用变了但仍用同一个修订；与第 13 条的多页一致性不同，这里单页也缺输入。让 `nbook.models` 后端同步解析 Agent 服务还会和 Agent 启动时依赖 `modelsKey` 的方向冲突。
- 如何核实：逐项对照 `createModelsCore` 的输入/订阅和 `plugins/agent/backend/plugin.ts:81–91` 的依赖。构造“没有角色绑定的停用行，只被一个 Profile 指定，之后改绑或删除”的单页反例；现有 B7 体积数据不覆盖。
- 建议改法：若整表合同要保留这一项，由应用装配传入可枚举、可订阅的直接模型引用快照，不反向激活 Agent，也不把 NeuroBook 的 Profile 类型引入 nb-models。Profile 改动与行的纳入/移出共用修订；或将这类读取留给引用拥有者并显式改合同。B5 走真 RPC 验只改 Profile 时返回的修订与行集一起变。

### 23. `source-unavailable` 只写在物化规则里，现有会话失败合同不收
- 严重程度：重要；类别：兼容、错误合同。
- 位置：B.2、B.4、B.5、验收映射；`nb-harness/src/kernel/api/model.ts:189–193`、`kernel/api/codes.ts:12–22`、`plugins/agent/shared/remote.ts:151–167`、`nb-models/src/contract/shapes.ts:78`。
- 现象：磁盘中仍有模型引用、但缓存与打包目录均不能物化时，B.2 要报 `source-unavailable`。现行内核 `ModelResolutionCode` 与会话指令的远程错误枚举不含它；角色状态的严格 schema 也不含它。只升 `nbook.models/settings` 版本不改变 `nbook.agent` 的会话合同。
- 为什么是问题：只在构建层返回新码，下游仍会把它折成 `unknown-model`，或在严格合同边界拒绝该失败值。用户无法区分“模型配置不存在”与“需恢复其来源或补字段”；B.4 的适配器夹具不经过会话命令及失败状态的序列化。
- 如何核实：沿现行 `resolveReference`、`resolveRole` 到 `remote.ts` 的 `commandErrorsOf`，对照 `harness/models.md` 输出 16 的原样返回约定。这个缺口不用访问任何模型即可验：保留绑定、隔离状态根无快照，走真实 Agent RPC 发消息、拉快照和预览。
- 建议改法：决定新码是来源内部诊断，还是端口可见的处理分支。若要原样交出，更新内核失败码、会话合同/兼容版本和角色状态，覆盖命令受理、预览及后台解析；若只内部区分，明确映射为旧码并在模型服务的状态给恢复原因。不要靠只在实现里加一个字符串。

### 24. 采纳协议会换原生身份，同一地址和密钥不代表同一套认证头
- 严重程度：重要；类别：探测、认证、上游选择。
- 位置：取舍 3、B.1 模板对话路由、B.4 中性身份、B.6「与对话同一路径与认证」；`pi-ai/src/providers/anthropic-headers.ts:245–275`、`anthropic.ts:4010–4050`。
- 现象：同属 Anthropic Messages 的两次请求，在相同基址、协议、模型和密钥下可以走不同认证。跟随 OpenCode Zen 时 pi-ai 特判 `X-Api-Key`；显式覆盖协议后改用 `nbook-compatible`，通用非官方地址默认发 Bearer。`requestAuth` 只给密钥和配置头，不会作这层决议。如果探测按当前模板发，采纳后的请求未必能过；若按四种协议各写固定认证头，检测当前模型也可能失败而对话正常。
- 为什么是问题：检测应验证被采纳后的请求，而不只是能用另一种认证 ping 通同一路径。CAS 版本正确也挡不住这种必然的采纳前后差异。
- 如何核实：`bun --no-env-file anthropic-auth-contract.ts` 用现行 pi-ai 18.14.0 对回环 SSE 各发一次。两次都是 `/gateway/v1/messages`、`anthropic-version:2023-06-01`，中性身份只有 Bearer，`opencode-zen` 只有 `x-api-key`；均正常结束，未用真实密钥。
- 建议改法：从已保存配置算出候选采纳后的线请求，明确提交哪些地址/协议字段；单项 `check` 则使用当前已解析的模型。与其把各家特判抄进探测，不妨让上游导出无 I/O 的请求决议（含认证、线上模型 id 与上限字段），探测只发送一次、不进入恢复循环。ADR 0057 的「不改上游：让 pi-ai 不按 provider 分支要改几十处」不要求删 provider 分支，窄接口可复用它们；若不改上游，B5 加同一网关不同身份的实收头及采纳后再对话的验收。

### 25. 选定的 stencil 映射输出分不清未知价与免费，也不交出自报档位
- 严重程度：重要；类别：上游接口、元数据正确性。
- 位置：技术选型「模型元数据」、B.3 `catalog.ts`、B.4；`pi-catalog/src/provider-models/openai-compat.ts:279–283,430–454,7098–7181`；`nb-harness/src/models/catalog.ts:129–134`。
- 现象：改用正确的 `(provider,id)` 索引后，`mapModelsDevToModels` 仍把缺 `cost` 与显式的零价都映射为四个 0，通用映射也不读 `reasoning_options.effort.values`。OMP 在通用映射之外另查原文补档，并在 Fireworks 单价映射处显式保留“发布过价格”的证据。现行 `catalogPrice` 把四个 0 都当未知。
- 为什么是问题：B.3 要缺价保持 `null`，现行设置页又区分未知/免费；只吃已映射行不能同时做到。把目录的 `reasoning: true` 当成已知档位同样不成立。第二轮改掉了跨 provider 借元数据，但没有恢复这些字段的证据。
- 如何核实：`bun --no-env-file catalog-contract.ts` 末行：缺价和明确四项零价的两行输出都为 `{input:0,output:0,cacheRead:0,cacheWrite:0}`。档位结论来自上述源码，不是远端请求结果。
- 建议改法：B1 明定公开映射入口及返回边界。按当前部署在原文提取价目是否存在与自报档位，或请上游扩充纯映射接口让证据随行；不能靠数值全零倒推。对一行缺价、一行明确免费及一行有非通用档位验收模型详情与同一模型的实际请求能力。

### 26. 批量检测被取消后，单个 RPC 回包送不出逐项“未知”
- 严重程度：重要；类别：取消、远程合同。
- 位置：B.5 `checkAll`、B5 验收；`nb-runtime/src/remote/peer.ts:125–135,178–184,216–218`；`docs/specs/runtime/plugin-channel.md` 输出 4。
- 现象：B.5 承诺“取消后不再领新项，已发出未结算的标‘未知’”。远端调用的 `AbortSignal` 一触发，调用方立即发 cancel、以 `cancelled`（读）或 `unknown-outcome`（写）结算并移除待收表项。提供方随后算出的逐条结果，即使发回同一条 RPC，也无人接收。断线后亦无法仅由该回包找回已结算项。
- 为什么是问题：名单去重、并发和总预算是第二轮已经加的保证；这个反例不增加任何请求数，却使新加的逐项取消语义不可兑现。把全批每行都标未知也混淆从未出站和已经计费的请求。
- 如何核实：对照 `#interrupt`、`pending.settle`、`case "result"`；验收用真 RPC、一条已返回成功、一条正等端点、其余仍排队，触发调用方取消，确认不能靠迟到回包恢复这些区别。
- 建议改法：如需逐项结算，显式取消批次而不取消结果通道，或用批次 id 加有界的结果查询/推送，注明断线与清理语义；若不引入独立批次状态，只承诺取消后停止领新项，整批结果未确认，不承诺逐项定位。任何一种都不盲重试已发出的检测。

### 27. 在线目录能补已有行，但没有规则让静态模板出现新模型
- 严重程度：重要；类别：来源归属、需求验收。
- 位置：取舍 1、B.1 `listing:"static"`、B.2 的解析顺序、B.3 `catalog.ts`、B3 验收；README 决定 2、3。
- 现象：B.1 允许模板没有列表适配器，B.3 把 stencil 定义成按 `(provider,id)` 查的元数据，B.2 的无缓存兜底又只查打包目录。对于一个跟随模板的 `static` 实例，stencil 即使返回该 provider 的新 id，只要它不在包内且没有设置行，按计划没有一步会让它成为成员。另一方面，泛化成每次合并全部打包/在线 id，又会让成功的完整空表复活。
- 为什么是问题：两种来源承担不同的承诺；不能用“在线更新成功”替代“新模型进入可解析的集合”。这是模板没有可用列表时的成员来源缺口，不是第二轮已修的混合协议地址。
- 如何核实：用固定夹具提供一条同 provider、仅 stencil 有的新模型；同一模板分别声明 `static` 与已成功返回空表的列表，比较新 id 是否出现、是否可解析。现行 B3 的空表用例没有覆盖无缓存时的成员初始化与两种权威来源的区别。
- 建议改法：B1 给各模板定成员权威。列表型有已验证全集时只用它决定在供成员；无可用快照时明确离线种子。静态型明确是“仅打包”还是“由同部署打包和在线目录决定成员”，后者须通过同一套对话/路由准入。B3 对照这两类验收；只保留元数据作用的模板不要承诺在线新增成员。

### 28. stencil 不能只限下载字节；展开和条件命中还需要验收边界
- 严重程度：重要；类别：资源上限、缓存完整性。
- 位置：技术选型「模型元数据」、B.3 `catalog.ts`、B1/B3；`pi-catalog/src/provider-models/openai-compat.ts:245–271`。
- 现象：第三稿已有大小上限与独立的 `304` 分支，但没有说限制压缩体、解压后正文还是两者，也没有规定 `304` 找不到对应可用快照时的结果。Bun 的整块 `zstdDecompress` 先分配解压结果，之后量长度已经晚了；单独保留 ETag 也不能让损坏或丢失的正文成为成功快照。
- 为什么是问题：目录默认后台更新，压缩体达标仍可在 JSON 校验前耗尽内存；重启后用残存 ETag 收到 304，若更新最近成功时间，会延长无可用目录的时间。这是在第二轮已经决定自行取数之后，对本地解压及重启缓存的附加判据。
- 如何核实：`stencil-cap.ts` 对公开目录无凭据实收 200、235,288 B 压缩体，流式解出 3,576,649 B，使用原 ETag 再请求得 304；`catalog-contract.ts` 合成样本 90 B 展开为 1,048,607 B。前者不证明未来响应的上限；未运行 B 的缓存实现。
- 建议改法：对传输字节与流式解压输出分别设上限并共用截止；只在正文验证成功后提交正文与 ETag。304 只复用匹配、可重读的快照，否则无条件重取（同一总预算）或按失败结算，不刷新成功时间。B3 加压缩体达标但展开超限、首启/缓存损坏时的 304 两个反例。

### 29. B 的远程合同提前接受不会生效的代理配置
- 严重程度：建议；类别：范围、跨段合同。
- 位置：B.1/B1 `networkKey.fetchFor`、B.2 配置形状、B.5 `updateProvider` 和快照。
- 现象：B.1 只提供直连，B.2 把 `proxy` 标为“段 C”，B.5 却已把 `proxy` 列进可写补丁和快照。逐字实施 B.5，调用方有理由相信写成 `custom` 后请求会改走代理，实际出口仍是 B1 的直连。
- 为什么是问题：这是 B 就会暴露的持久化合同，不是 C 的代理实现问题。提前接受无效设置会让用户误判实际出口，也在验收路由之前固化字段与清除语义。与第 17 条不同：即使 Bun 版本正确，设置仍不起作用。
- 如何核实：对照 B1 与 B.5 的阶段描述；以调用方成功写入自定义代理、再发一条本机假端点请求作为验收反例，不需要 C 的实现。
- 建议改法：`proxy` 的实例设置、RPC 写入和对外状态一起排到实际选路生效的阶段；B 只交付自身可兑现的出站行为。段 B 的来源、检测、复制和图标仍按原验收，在 B 内分开推进，不把已定交付移出 B。

## 待确认项的判断

- README 决定 5 的「Bun 的 fetch 能否走 socks5 待验证」已由决定 21「SOCKS5 地址拒收，提示改用代理软件的 HTTP 端口」结案；不把 SOCKS5 实测当成段 B 的门禁。README 的轻投影截图待办归段 A，不在本轮结论内。
- 不做 OAuth、抓站点图标、Magpie 的额外功能、降级保护或出口重定向，不妨碍段 B；既有不支持传输须明确拦在发送前（第 5 条），决定 23 的降级后果按首次写出新字段记录，不说成只要升级就丢设置。
- 自有列表适配器可继续用公开接口、失败保留上一次；需要先区分列表权威与元数据补全，并明确未知字段不能作为成功空表（第 14、16、27、28 条）。
- 中性身份会改变线上认证，不只是丢掉服务商优化；保留已定的身份分界时须验证采纳后的线请求（第 24 条）。旧会话按旧规则读取不等于用新的中性 provider 做旧比较（第 9 条）。
- 3xx 不跟随有可用的运行时机制；“改为最终地址”要等部署及凭据一起结算（第 7 条），被拒绝的请求与正常配置请求应分别验收（第 1 条）。
- Cloudflare「测试代理」是段 C 的外联，本轮不判。图标仅作厂商标识是已记录的商标取舍；本轮只核对上传、绑定与服务端读取，不将包的 MIT 许可当作商标授权。
- 数百行保留为容量验收，不把 600 行变成服务商成员上限；B 的后端需按编码字节和一致修订结算（第 11、13 条）。B6 的界面耗时与虚拟列表不在本轮范围。
- 范围：按决定 24「每段单独合入」，不必增加一次合入。B 内先走通一条 v1 迁移、枚举、绑定、发送、重开的链，再扩模板矩阵；图标、复制及批量检测可独立验收。代理配置合同不必提前登记（第 29 条）。这不删改段 B 的既定验收。

## 未发现问题的方面

- 同一个 NeuroBook 服务端认领档案下，仔细检查后没有发现需要为来源缓存再做一套跨进程认领。现行宿主按状态根认领、规范化路径别名，不会因活进程暂时无响应而接管；不依赖这个保证来覆盖崩溃后遗留文件（第 20 条）。依据是 `claimStateRoot` 与 `runtime/server-host.md` 的合同，未复跑全套测试。
- 对“能否在最低层禁止跟随、读体等待能否中止”仔细检查后没有发现 Bun 1.4.4 缺少所需能力。回环 `fetch-contract.ts` 实收两个初始 307 请求、零次后续跳转；`manual` 返回 307，`error` 返回 `TypeError`，挂起正文因超时关闭且服务端收到取消。未据此认定插件排空通过。
- 对选用的 OMP 公开入口及 stencil 基本传输，仔细检查后没有发现版本 18.14.0 缺少入口：根导出有 `getBundledModels`，`@oh-my-pi/pi-catalog/provider-models` 导出映射函数和 41 个描述项，`@oh-my-pi/pi-catalog/build` 导出 `buildModel`；本机 `node:zlib` 的流式 zstd 能解实际目录，原 ETag 条件请求实收 304。返回字段和缓存有效性的缺口另见第 25、27、28 条。
- 对明确的完整空表，仔细检查后没有发现必须拒绝空表本身的理由：空表是结构有效、分页已结束的成功响应，不等于缺字段、无数据、部分页或坏缓存。核对了 Anthropic 的 `has_more`/`last_id` 与 Gemini 的 `nextPageToken`；OpenAI 公开 Models List 不保证窗口等额外字段。匿名 OpenRouter 只证实此次单个响应有 477 行，不能由此断言无分页或每个账号的名单相同。
- 对“检测不用原有的推理流入口”仔细检查后没有发现需要保留它的重试机制；原入口的首帧与多次 HTTP 恰好是第 12 条的反例。探测也不能经 `transportFetch` 的调试落盘路径。只验证了现行依赖、回环夹具和匿名目录；未调用真实模型、未跑产品构建、类型检查、e2e 或段 B 的实现测试。
