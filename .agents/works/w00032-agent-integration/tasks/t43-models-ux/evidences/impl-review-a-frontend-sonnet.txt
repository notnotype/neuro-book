F2
严重程度：重要
类别：正确性 / 竞态（200 ms 写入合并与外部回写）
位置：packages/nb-agent-ui/src/vue/composer/AgentRoleModelPicker.vue 的 onEffort 与 releaseTimer（约 l.139-153）
现象：settleTimer 触发 emit 之后挂一个 1500 ms 的 releaseTimer 把 pending 清空；onEffort 重入时只 clearTimeout(settleTimer)，不清 releaseTimer，宿主回写（watch 把 pending 置 null）时也不清它。结果是上一次选择留下的 releaseTimer 会在“下一次选择还没写出去”的时候把新的 pending 清掉，控件在宿主回写之前跳回旧档。
为什么是问题：不需要宿主慢或失败，正常使用就会碰到：先选一档（宿主几十毫秒内回写），1.3 到 1.5 秒后再选一档，上一次的 releaseTimer 在 t=1500+ms 触发，新的 settleTimer（再过 200 ms）还没发，于是 pending=null、控件显示回旧档，直到新的 emit 与宿主回写完成才跳到新档。即用户点“高”，控件先亮“高”，然后闪回旧档约 200 ms 加一次往返，再亮“高”。这正是 pending 机制要消除的“跟手”问题。
如何核实：在真实组件上用假时钟复现（实验文件 /tmp/review-t43a-impl/exp/race.dom.test.ts，用 vitest 在 nb-agent-ui 包里跑，挂载真 AgentRoleModelPicker，点真实的 radio 按钮；没有绕过运行时）。时间线：t0 点“中”；t200 emit medium；t1450 点“高”；t1650 emit high；t1700 上次的 releaseTimer 触发。radio 选中态（低/中/高）依次为：t1450+点击 后 fft（高亮在高）、t1690 fft、t1720 tff（回到“低”，即旧值），此时 emit 已经含 high、宿主未回写。
建议改法：onEffort 开头与 pending 被 watch 清空时一并 clearTimeout(releaseTimer)；或者干脆把 release 改成“以最后一次 emit 的时刻为准”，只保留一个定时器句柄。补一条测试：第二次选择发生在第一次 release 窗口内，断言控件一直停在第二次选的档上。

F3
严重程度：建议（真实存在，窗口小）
类别：正确性 / 竞态
位置：AgentRoleModelPicker.vue 的“用默认”按钮（template 里 data-model-picker-reset，@click="emit('reset-thinking')"）与 onEffort
现象：用户刚选了一档（pending 有值、200 ms 合并窗口内），马上点“用主力的默认”：reset-thinking 立即发出，之后窗口到点时 settleTimer 仍会发 select-thinking(刚选的档)，宿主按顺序处理，最后状态是“钉在刚选的档”，与用户最后一个动作（回到跟随）相反。
如何核实：同一实验文件 race.dom.test.ts 第一条：点“高”，nextTick，点 data-model-picker-reset，advanceTimers(300)。picker.emitted() 得到 reset-thinking 一次、select-thinking [["high"]] 一次（顺序为先 reset 后 select）。组件级真实交互，没有伪造时序。
为什么是问题：“跟随”按钮的效果被后到的写入盖掉，用户会看到界面上的“跟随”提示消失、又变回明确档。同类的还有“在 200 ms 内切角色”：select-model 立即发，thinking 写入晚于它发出，档位被钉到新角色上（对旧模型的档位），宿主要靠夹取自救。
建议改法：reset 的点击里先清 settleTimer 与 pending（取消还没发的写入）；选角色/选模型发 select-model 之前也同样冲刷或取消 pending。至少在 .md 里写明语义：窗口内的后续动作是否取消待写档位。
