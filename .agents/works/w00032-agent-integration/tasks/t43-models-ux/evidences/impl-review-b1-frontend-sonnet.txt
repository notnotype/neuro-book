### 1. 快照里服务商版本没变时，选用数据仍整份换 rows 与 lookup 并通知 3 次，agent 插件因此多发会话快照请求
- 严重程度：重要　类别：不变量　位置：packages/neuro-book/src/plugins/models/shared/selection.ts:112-135（refresh 与 refreshLookup）；packages/neuro-book/src/plugins/agent/web/plugin.ts:327-333（takeModels）、plugin.ts:318-326（rebuild）；packages/neuro-book/src/plugins/agent/web/session-host.ts:2053（`watch(() => deps.models(), …, {flush:"sync"})`）
- 现象：refresh 在 stale 为空时仍无条件执行 `rows.value = combined`（flatMap 产生新数组）、`notify()`；随后 refreshLookup 无条件 `lookup.value = new Map(...)` 再 `notify()`。agent 插件的 takeModels 又在 attach 之后同步 `rebuild()`，`want()` 在 attach 之前也会同步走一遍 refreshLookup。结果是任何快照事件（改角色名、改某家的非模型字段以外的一切、重连后的 resync）都让 `models.value` 被赋新数组多次。
- 实验（/tmp/review-t43b1-impl/exp-frontend/exp1.ts，用真实 selection.ts 与计数用的假远端）：两家服务商、一个被引用的模型，第二份快照只改角色、两家 `modelsRevision` 不变：服务端请求 0 次（这部分对），但 `rows` 引用换了、`lookup` 引用换了，订阅回调被调 3 次（want 1 次 + rows 1 次 + lookup 1 次）。
- 为什么是问题：计划 B6a 写明“到齐后一次换引用（只触发一次 refreshModel）”，Spec 的选用数据一节也以此为卖点。session-host 对 `deps.models()` 用 sync 的 watch，每次赋值都是一次 `remote.snapshot({sessionId})` 的 RPC（整份会话快照）。agent 插件里 takeModels 的同步 rebuild（旧 rows + 新快照）加上读完后的 rows 通知与 lookup 通知，一份快照最多触发 3 到 4 次 refreshModel，而且其中第一次拿旧 rows 配新快照，交出的是新旧混合的中间状态。selection.test.ts 只断言了“版本变了的那家换 rows 一次”，没有“版本没变时不换引用”的用例，所以抓不到。
- 如何核实：`cd /tmp/review-t43b1-impl/exp-frontend && bun exp1.ts`，输出第二行 `notifies 3 … rows ref changed true lookup ref changed true`。
- 建议改法：refresh 里 stale 为空且 present 集合没变时不换 rows、不通知；rows 与 lookup 的新值先按内容比较（逐项引用相同则保留原数组）；lookup 的通知并入 rows 的同一次（refresh 先等 refreshLookup 的结果再一次 notify），或者让 plugin 的 rebuild 只在 rows 或 lookup 真的换了引用时改 `models.value`。takeModels 里的同步 rebuild 去掉（rows 未换时不用重算 models，只有 groups 与 roles 需要立即换）。补一条“版本没变的快照不换引用、不通知”的测试，并给 plugin 层加“一份快照触发 models 变化的次数”的断言。

### 2. 选用数据 lookup：连续两次 want 时，先完成的那次把还没取到的引用报成 null（“模型不存在”）
- 严重程度：重要　类别：正确性　位置：packages/neuro-book/src/plugins/models/shared/selection.ts:133（`lookup.value = new Map(wanted.map(... looked.get(reference)?.row ?? null))`）
- 现象：refreshLookup 结束时用“当前的 wanted”重建整张 lookup，没取到的键（`looked` 里没有）一律写成 null，而 null 的合同含义是“没有这个模型（服务商或模型不在、被移出）”。`mine !== generation` 只挡新快照，挡不住 `want()` 的并发：want 不增加 generation。
- 实验（exp2.ts 第二段）：快照就绪后 want(["a/x"])，10ms 后 want(["a/x","a/y"])，远端每次 60ms。订阅收到的两次 lookup 依次是 `[x:有值, y:null]`、`[x:有值, y:有值]`。即 y 先被当成“已不存在”再变成有值。
- 为什么是问题：Profile 页打开时 `watch([snapshot, settingEdits])` 立即 want 一次，用户在页内改一个 Profile 的模型、或快照事件在途时，角色页与 Profile 页都会短暂把绑定的模型显示成“模型已不存在/用不了”（profile-view 里 `found === null` 走 `profiles.model.modelGone`，问题条是 role="alert" 一类的告警位），之后又消失，用户看到闪烁的误报。agent 标签的 `modelLabel` 也会短暂退成原始引用字符串。
- 建议改法：lookup 只写已经取到的键，未取到的键不进 Map（调用方区分“没取到”与“确认不存在”：Map 里没有键 = 还在读）；或者每次 refreshLookup 带自己的 wanted 序号，结束时序号不是最新的就丢弃；`looked` 里没有的键不能写 null。补一条“want 并发”的测试（可以复用 selection.test.ts 的真实服务端夹具，在 modelsByReference 前加延迟）。

### 3. 选用数据：新快照到来就丢弃整轮已读完的结果，快照间隔短于读取耗时时永远不到齐
- 严重程度：建议　类别：不变量　位置：packages/neuro-book/src/plugins/models/shared/selection.ts:104-107（`if (disposed || mine !== generation) return;`）
- 现象：每份快照 `generation += 1`，在途那轮 refresh 读完之后整体丢弃，已经读完的各家结果也不写进 `cached`；新一轮又从 stale 集合（缓存没动，仍是全部）重读。在途的旧请求也没有取消，只是结果作废。
- 实验（exp2.ts 第一段）：读一家要 100ms，每 40ms 来一份版本不同的快照，连发 10 份：`ready` 一直为 false，发出 10 次请求；安静下来之后才到 true。
- 为什么是问题：设置页里连续改几项（例如数密钥时每输入一次 setKey 不会，但改名、拖动开关、批量 setModels 会连发快照），选择器的模型列表与 agent 标签在这期间一直停在旧数据（或第一次打开时一直是空的，`ready` 为假则 `models` 不更新）。真实后端快照频率不高，所以只列建议；作者在注释里写“这一轮读到的结果作废”是有意的，但代价没有写。
- 建议改法：读完的一家按它读到的版本写进 `cached`（key 是 provider.id，值带 revision），不管 generation；generation 只决定最后要不要换 `rows`。这样新一轮 stale 只剩没读完的。

### 4. models-store.loadRows：三轮 revision-changed 用完后 `loading` 停在 true，页面一直写“正在读取模型”
- 严重程度：建议　类别：正确性　位置：packages/neuro-book/src/plugins/models/web/models-store.ts:191-229（loadRows 的 for round<3 循环）
- 现象：每轮开始都 `rowCache.set(key, {…loading: true, failure: null})`；读到 `revision-changed` 时 `continue`；第三轮也 revision-changed 之后循环结束，函数无声返回，缓存条目仍是 `loading: true、failure: null`、`revision` 是旧值。选用数据那边（selection.ts）用尽重试会 `onFailure("revision-changed")`，这里没有对应处理。
- 为什么是问题：ProviderDetail 在 `rows.length === 0 && rowsLoading` 时一直显示“正在读取”，没有重试按钮（重试按钮只在 failure 非空时出现）；除非又来一份该家的快照才会重新读。服务商在三次分页读取期间连续变化的概率很低，所以是建议级。
- 如何核实：从代码推断；构造 fake remote 让 providerModels 连续回 revision-changed 三次即可复现（现有 models-store.test.ts 没有“用尽重试”的用例）。
- 建议改法：循环结束后写 `failure: {code: "revision-changed", detail: …}` 并 `loading: false`，让详情页出现重试按钮；补测试。

### 5. “复制一份”密钥没复制成功时，用户只看到泛用的“只完成了一半”，写好的专用文案没有被用

### 6. Profile 页：按引用取行还没回来时，没取到的引用被当成“模型已不存在”，选一个模型就闪一条告警
- 严重程度：重要　类别：正确性　位置：packages/neuro-book/src/plugins/agent/web/profile-view.ts:174（`findModel = reference => selection.lookup.get(reference) ?? null`）、:190-195（problem）、:158 与 plugin.ts roleOptions 的 `lookup.get(role.model)?.name ?? role.model`；packages/neuro-book/src/plugins/agent/web/profile-page.ts:163-168
- 现象：`lookup` 里没有这个键（还没取、正在取）与值为 null（服务端确认没有这个模型）在 `?? null` 之后分不开。Profile 页用户在下拉里改选一个模型：setting.model 变成新引用，profile-page 的 watch 才去 `want`，在 modelsByReference 回来之前 `lookup.get(新引用)` 是 undefined，直接走 `profiles.model.modelGone` 的告警文案（hint 带 `warning: true`，图标变警示），回来之后消失。第一次打开页面时每个直接指名模型的 Profile 也会闪一次。角色名同理：agent 标签的 `modelLabel` 在取到之前显示原始引用字符串。
- 为什么是问题：Spec/计划里 lookup 的合同是“没有这个模型的值为 null”，调用方把“还没取到”也当成“不存在”，等于把一个加载态当成了业务错误；且告警位 `warning` 会触发图标。profile-view.test.ts 的夹具一次性给齐了 lookup，所以没有“未取到”的用例。
- 建议改法：lookup 用 `Map<string, ModelRow | null>`，未取到的键不在 Map 里（同第 2 条），调用方用 `lookup.has(reference)` 区分“读取中”（不显示问题、名字先用引用的模型部分）与 null（确认不存在）；补 profile-view 测试：lookup 缺键时 `warning` 为假。

### 7. 全部模型页：200 行的预算在不搜索时也跨服务商共用，展开第二家得到空表；没有加载中、失败与无命中的状态
- 严重程度：重要　类别：正确性/界面　位置：packages/neuro-book/src/plugins/models/web/components/AllModelsView.vue:48-58（sections）、:63 `<table v-if="section.open">`；AllModelsView.md 第 7 行
- 现象：`budget` 从 200 起，每个展开的节减去自己画的行数，没有区分搜索与否。展开一家 600 个启用模型的服务商（OpenRouter）画 200 行、预算归 0；再展开第二家（比如 DeepSeek），`matched.slice(0, 0)` 得到 0 行，只有表头加页脚一句“还有 N 条，缩小搜索词”，而且没有搜索框内容可缩——这第二家与 OpenRouter 的另外 400 行在不搜索时根本看不到。AllModelsView.md 写的是“搜索时…一共至多画 200 行”，实现不一致。
- 另外：节展开后行还没读到（`rows[provider.id]` 无键）、读失败（页面只传 rows，不传 failure）时是一张只有表头的空表，没有“加载中”也没有重试；搜索词无命中时 sections 为空，什么也不显示（ProviderDetail 有“没有匹配的模型”，这里没有）。ProvidersPage 传给它的 `rows` 是模板里内联 `Object.fromEntries(...)`，每次父组件渲染都是新对象，sections 随之整体重算。
- 如何核实：代码推断，预算语句无条件作用于所有展开的节；ProvidersPage.dom.test.ts 的“全部模型”用例只展开 moonshot 一家、1 个模型，抓不到。
- 建议改法：预算只在搜索时共用；不搜索时每节单独封顶（或不封顶并虚拟化），页脚文案区分“搜索”与“展开”；传入每家 `{rows, loading, failure}`，节内写加载中与失败重试；无命中时写“没有匹配的模型”；rows 用 computed 构造而不是模板里内联。补测试：先展开一家大服务商再展开另一家，第二家的行数 > 0。

### 8. 编辑模型：“恢复来源值”只给了 2 个字段按钮，点了不显示来源值，且整条新增行为没有 dom 测试

### 11. ProviderDetail：系列“默认展开或收起”的阈值按模型总数判断，跨过 30 时用户的展开收起选择整体取反
- 严重程度：建议　类别：正确性　位置：packages/neuro-book/src/plugins/models/web/components/ProviderDetail.vue:166-172（`AUTO_OPEN_LIMIT`、`isOpen`）
- 现象：`isOpen(group) = (rows.length <= 30) !== toggled.has(group)`。`toggled` 记的是“用户点过的组”，语义是“与默认相反”，而默认由行数决定。服务商从 30 个变成 31 个（管理模型里加一个、别处加了、`followSource` 自动加入）时默认翻转：用户合上的组（在 toggled 里）一下全部展开，其余全部收起。

### 12. 上传图标的文件输入是覆在按钮上的透明 input，键盘用户有两个停靠点且看不见焦点

### 14. 标题区名称编辑按 Esc：焦点回铅笔的那一步抛 TypeError，焦点丢到 body；.md 与测试名都说有 Esc 回退但没有被测
- 严重程度：重要　类别：正确性/测试　位置：packages/neuro-book/src/plugins/models/web/components/ProviderHeader.vue:47（`const editButton = ref<HTMLElement | null>(null)`）、:79（`editButton.value?.focus()`）、:176（`<IconButton ref="editButton" …>`）；ProviderHeader.md“名称”一条；ProvidersPage.dom.test.ts:“改名：回车提交；重名……；空名与 Esc 回退”
- 现象：`ref="editButton"` 绑在组件 `IconButton` 上，拿到的是组件实例，不是元素；nb-ui 的 IconButton 没有 `defineExpose`（controls/IconButton.vue），所以 `.focus` 不是函数。`cancel()` 是 async：先 `editing = false`，`await nextTick()` 之后调用 `editButton.value?.focus()` 抛 `TypeError: editButton.value?.focus is not a function`，成为 unhandled rejection。结果：输入框已关掉，但焦点没有回到铅笔（落在 body），键盘用户丢了位置；还多一条未处理的拒绝（宿主的诊断端口会记一次错误）。类型声明 `HTMLElement | null` 也与实际不符，所以 vue-tsc 没报。
- 如何核实（实验，未改仓库）：/tmp/review-t43b1-impl/exp-frontend/more.exp.dom.test.ts 的“header Esc”用例，用 `bunx vitest run --config /tmp/review-t43b1-impl/exp-frontend/vitest.exp.config.ts more --silent=false`：输出 `ESC: editing still? false focus: null emitted: undefined`，并带 `Unhandled Rejection TypeError: editButton.value?.focus is not a function ❯ cancel ProviderHeader.vue:79`。
- 测试：用例标题写“空名与 Esc 回退”，正文只测了空名（输入“   ”回车）；Esc 从未被触发。ProviderHeader.dom.test.ts 也只测了重名。这是“标题声称的判据没被测到”。
- 建议改法：给铅笔换成元素引用（IconButton 的 attrs 落在根元素上，可以用 `data-provider-rename` 选择器查，或让 IconButton 暴露 `focus()`）；补 Esc 用例：断言输入框关闭、`rename` 未发出、`document.activeElement` 是铅笔；顺带测 blur 提交与重名行内提示在失焦时的行为。

### 17. 数据模块无条件挂选用数据：只开“服务商”页、没人用角色下拉时也读全部服务商的启用模型，之后每次改某家的任何配置又整家重读两次
- 严重程度：建议　类别：不变量（规模）　位置：packages/neuro-book/src/plugins/models/web/models-store.ts:131（`apply` 里的 `selection.attach(next)`）；packages/neuro-book/src/plugins/models/web/components/RolesPage.vue（唯一消费者）
- 现象：store 是两页共用的，`start()` 订阅快照后第一份快照就 `attach`，选用数据（`usable: false`，全部启用的模型）立即对每家发 `enabledModels`；只有角色页读 `store.selection.rows`。实验（/tmp/review-t43b1-impl/exp-frontend/store.exp.dom.test.ts，Lab 假远端的 6 家服务商，没挂任何页面）：`store.start()` 之后 `enabledModels` 被调 6 次；随后只改一家的名称，又调 1 次。8 家 × 600 个模型的最大输入就是 24 页 JSON，而服务商页自己的 `providerModels` 读（详情、管理模型、全部模型）还要再读一遍同样的行。服务端的 `modelsRevision` 是整份服务商配置的哈希（nb-models/core/core.ts:114：`revisionOf(provider, key)`），所以改名、换图标、加请求头都会让这家 600 个模型的两份读取（选用数据与详情）各重来一遍。

### 19. 选用数据：首次读取里有一家失败，整个选择器的模型列表一直不出；重试时 agent 插件会再建一份选用数据且旧的不释放
- 严重程度：建议　类别：正确性　位置：packages/neuro-book/src/plugins/models/shared/selection.ts:108-118（`ready` 只在“这一轮每一家都成功”时置真）；packages/neuro-book/src/plugins/agent/web/plugin.ts:322-325（`rebuild` 以 `data.ready.value` 为门）、:339-348（`ensureModels` 失败后 `modelsStarted = false`，下一个对话位置再进来会再 `createSelectionData`）
