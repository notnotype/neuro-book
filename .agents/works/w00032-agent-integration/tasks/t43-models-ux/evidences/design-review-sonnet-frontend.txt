# t43 计划前端部分设计审查（Sonnet 5.5，只读）

### 1. 图标表放在 plugins/models/web/logos.ts，agent 插件的选择器拿不到它
- 严重程度：重要；类别：不变量；位置：计划“packages/neuro-book/src/plugins/models/web/”的 logos.ts，与“agent/web/plugin.ts 与 session-host.ts：构造选择器的视图时带上图标”
- 现象：选择器的 `ComposerModelView.icon/groupIcon`、`ComposerRoleView.modelIcon` 由 `agent/web/plugin.ts` 的 `modelOptions(snapshot)`、`roleOptions(snapshot)` 构造（packages/neuro-book/src/plugins/agent/web/plugin.ts:131-160）。计划却把 `iconOf(provider)` 放在 `models/web/logos.ts`。
- 为什么是问题：`src/architecture.test.ts:121-126` 机检“跨插件的运行时导入只能指向对方的 shared/contracts.ts”，agent/web 运行时导入 models/web/logos.ts 会直接让该测试失败；而 shared 侧又不能引前端（同文件 :124 “共用代码引用了一侧的实现”），把 SVG 表塞进 `models/shared/contracts.ts` 会让后端 tsc 与服务端 bundle 带上 994 个图标的导入表。计划没有处理这个矛盾。另外 `iconOf` 要同步给出 `ComposerIcon`（视图是 computed 里同步构造的，session-host.ts:1905-1925 一带），而表是“动态导入成一个块”，异步到达后谁触发 computed 重算、到达前画什么，计划没写。
- 如何核实：读 architecture.test.ts 的 violationsOf；grep agent/web 现有对 models 的引用，只有 `nbook/plugins/models/shared/contracts`（plugin.ts:22）。
- 建议改法：把图标表放到跨插件允许的共享前端位置，例如 `src/ui/provider-icons/`（`src/ui/` 下已有 file-icons、brand，web 侧都能引，且没有被后端 tsc 包含）；表本身导出一个 `shallowRef` 式的“已加载”状态，加载完成前一律回退首字母方块，加载完才换（视图里的图标字段读这个 ref，自然触发重算）。同时写明后端 tsc（agent/web/plugin.ts 在 tsconfig.json 的 include 里）看不到 `*.svg?raw` 的模块声明，需要给 `?raw` 补一份 ambient 声明或把导入限制在 tsconfig.web.json 范围内的文件。
- 补正（对第 1 条末句）：tsconfig.json 的 include 只有 `src/plugins/*/plugin.ts`、backend、shared，不含 `src/plugins/*/web`，所以“agent/web/plugin.ts 在 tsconfig.json 的 include 里”不准确；是否被后端 tsc 间接拉到取决于 `plugins/agent/plugin.ts` 是否导入 web 入口（plugin.ts:150 的注释自述“这个文件也由不带 DOM 类型的 tsc 检查”）。`?raw` 声明一点降为“实现时留意”，不影响第 1 条的结论。

### 2. “--elevation-popover 取 --elevation-menu 的值”在 tokens.css 里是循环引用，在 nbook 暗色里会丢掉浮层的亮边
- 严重程度：重要；类别：正确性；位置：计划“packages/nb-ui/”第一条（themes/nbook/vars.css 亮暗两处与 src/tokens.css）
- 现象与依据：
  - packages/nb-ui/src/tokens.css:73-75：`--elevation-popover` 是写死的四层投影，`--elevation-menu: var(--elevation-popover)`。“取现在 menu 的值”在这个文件里只能写成 `--elevation-popover: var(--elevation-menu)`，两条互相引用，计算值为 guaranteed-invalid，`box-shadow` 整条作废（没装主题的消费方浮层、Tooltip 全部没有投影）；要么得另写一个字面量，计划没说是什么。
  - themes/nbook/vars.css:304-307 的 `--elevation-menu` 只有一份，注释写“明暗共用”（:298-303）；暗色块在 :443-447 单独给了加重的 popover（20%/35%/28% 和一圈 1px `--text-main` 10% 的亮边）。同一文件 :430 一带的注释写明理由：暗色里“压暗的边等于没有边”“环境投影加重”“层级撑不住”；tokens.css:59-64 记着“8% 的黑压在暗色底上等于没有影子……真回归”。把暗色 popover 换成菜单档，就把这两条一起退掉：菜单的外圈是 0.5px 的 `--shadow-color` 16%，在暗色底上不可见，投影 10%/24% 也比现在的暗色值轻。
  - 定稿依据只有亮色：评审板 r1/shadow-menu.webp、shadow-popover.webp 都是亮色截图，没有暗色对比；决定 10 的“整档调轻”是在只看过亮色的情况下做的。
- 影响面（这一档的消费者，grep `nb-ui-popover-surface`、`nb-ui-tooltip-surface`、`--elevation-popover`）：nb-ui 的 Popover、AnchoredPopover、Tooltip、DateInput；nb-agent-ui 的 AgentNoticeCard、AgentWizardFrame、AgentWizard 与 AgentDock 的收起条；markdown 插件的 MarkdownToolbar（bottom）、MarkdownCommentMargin 的批注卡片，以及经 AnchoredPopover 的 MarkdownSelectionMenu、ImageCard、StickerCard、CommentCard、TextPrompt、CommentLayer 与两个选择器。Dialog、AlertDialog、Drawer 用 `--elevation-dialog`，DropdownMenu、Select、ContextMenu、QuickPick、SuggestionMenu、ColorSwatches 已经是菜单档，不受影响。其中 AgentWizardFrame、AgentNoticeCard、AgentDock、批注卡片是常驻在页面里的“卡片”，不是弹出后一闪而过的气泡，它们靠这一档投影才和底色分开；t86 评审已经记过菜单档“在暖白的侧栏上几乎看不出浮起”（vars.css:301-303）。计划写“约 20 处一起变”但没有列出、没有逐个看过。
- 如何核实：在 Lab 里用暗色主题打开 AgentWizardFrame、AgentNoticeCard、批注卡片与选择器，改变量前后各截一张（亮、暗各一）；或直接对比两档在 `--bg-main` 上的对比度。
- 建议改法：(1) 把 nbook 的改动限定为亮色块，暗色块保持原值或另给一档“暗色菜单”；(2) tokens.css 写出字面量（或明说不改 tokens.css，只改 nbook 主题）；(3) 先把上面列的常驻卡片排除出“气泡档”：给它们换 `--elevation-raised` 或保留原值，只把弹出的气泡降档，而不是整档改；(4) 计划里写明需要亮暗各一份对照截图才能验收，而不是只说“亮色”。若开发者就是要全部变轻，把“暗色可能看不出浮起”作为已知代价写进决定 10。

### 3. 网络页不能经 SettingsRow 写 nbook.models 声明的“自动更新模型目录”（写入授权 denied）
- 严重程度：重要；类别：正确性；位置：计划“plugins/network/”的 web 一条（“自动更新模型目录”是 `nbook.models` 的设置项，`section` 指向 `nbook.network`）
- 现象：网络页是 `nbook.network` 贡献的 page 分区，页面里的 `SettingsRow` 经页面所属插件的配置服务写设置（SettingsRow.md：`settings` 属性“页面传自己插件的”）。而 docs/specs/settings/configuration.md 输出 11：“`update` 只写调用方插件自己声明的项……调用方是声明者（否则 `denied`）”；settings-window.md:244、264 也写“page 分区经自己插件的配置服务写自己声明的项”“别的插件的页面只能写自己声明的项”。`section` 指向别的插件的分区只在 list 分区里成立（settings-window.md:166 的“指向 page 分区的项不在列表里画，由页面负责”），页面要画就得写它，写它就是 `denied`。
- 为什么是问题：r3 稿里“自动更新模型目录”开关是页面里的一行，计划的做法会让这个开关点了写不进去（失败通知“设置没有保存”），而且 SettingsRow 的“已修改圆点、恢复默认”也走同一条写路径，一并失效。
- 如何核实：读 configuration.md 输出 11、19 与 settings-window.md:166、244、264；对照 `SettingsRow.vue` 的 `run()` 经 `props.settings.update(...)`。
- 建议改法：把设置项声明在 `nbook.network`（例如 `nbook.network/catalogAutoUpdate`），`nbook.models` 的服务端只读它（读别的插件声明的项没有限制，写才有）；或者整行不用 SettingsRow、改成经 `nbook.models` 远程合同写。前一种更省：开关、恢复默认与“已修改”都沿用现成的行。计划里还要写明 `nbook.models` 对 `nbook.network` 设置的读取方向，避免出现 models 依赖 network 的静态环（architecture.test.ts 只许跨插件运行时导入 shared/contracts.ts，读设置键本身只要引键声明，需要核对 `settingsKey` 的用法）。

### 4. 代理地址“不收用户名密码”与开发者确认的第 3 轮稿、与系统代理的常见写法冲突
- 严重程度：重要；类别：正确性；位置：计划“shared/settings.ts”（`url` 只收 http、https、socks5、socks5h，不收用户名密码）；README 决定 20；决定 16
- 现象：开发者在 review v3 确认的“网络”页（artifacts/review/r3/network-custom.webp）里，“代理地址”行的说明文字写的是“http、https 或 socks5，可以带用户名和密码”，决定 16 以“按第 3 轮稿做”确认。计划又在决定 20 里自己定“代理地址不带用户名密码”（作者定、开发者没有异议），实现了就和已确认的稿面直接矛盾：说明写“可以带”，输入带了却被拒。
- 为什么是问题：(a) 稿面与实现对不上，是开发者确认过的文案；(b) 带认证的 HTTP/SOCKS5 代理（公司网关、付费线路）很常见，拒收等于这类用户只能用“跟随系统”、再靠环境变量，而计划又要把环境变量里的地址原样读进来（见第 5 条），行为不一致；(c) 计划自己的理由只有一句“设置文件里不放凭据，信任边界同 models/service.md”，但 models/service.md 的凭据是放在凭据库里、设置里只有 `apiKeyEnv`，说明凭据可以有存放处，没有论证过“代理凭据也必须这样”。
- 如何核实：看 r3/network-custom.webp 的“代理地址”说明；读 plan 与 README 决定 20。
- 建议改法：二选一并写进决定：A) 代理凭据另存：设置里只放不带凭据的地址，用户名密码存凭据库（同服务商密钥），页面多一行“代理密码”（secret 项 `secret: true`，configuration.md 输出 20 已有机制），中继按上游 URL 拼接；B) 第一版不收凭据，那就必须同时改 r3 稿里这行说明（去掉“可以带用户名和密码”）、并在输入框里校验到 `user:pass@` 就报明确的出错文字（不是静默丢弃）。无论 A 或 B，都要把这条从“主 Agent 定”改成向开发者确认的决定，因为它改了已确认稿面的文案与能力。

### 5. “现在用的是 <系统代理地址>”可能把环境变量里的代理密码显示给用户并写进日志、快照
- 严重程度：重要；类别：安全与性能；位置：计划“backend/proxy.ts：describeSystemProxy”与远程合同 `systemProxy()`；web 页面“跟随系统时行下信息色写出现在用的代理与来源”
- 现象：`describeSystemProxy(env)` 读 `HTTPS_PROXY` 等，返回 `{url, source}`，页面把 `url` 原样写在行下（r3 稿：“现在用的是 http://127.0.0.1:7890（来自环境变量 HTTPS_PROXY）”）。环境变量里的代理地址常带 `http://user:pass@host:port`；`os-proxy-config` 读到的系统设置同样可能带。
- 为什么是问题：密码会出现在 DOM、远程合同返回值、本机服务端日志与诊断、截图里；这和“设置文件里不放凭据”的立场自相矛盾。检测面板（“测试代理”）失败时返回的“失败的类别与原文”（计划写“原文”）里也可能带出代理 URL（连接错误文本常含它）。
- 如何核实：`HTTPS_PROXY=http://u:p@127.0.0.1:1 bun -e` 里 fetch 一次，看错误文本是否含 `u:p@`（Bun 的 ProxyConnectionRefused 一类文案在不同版本会不会带 URL，要实测）。
- 建议改法：契约里只给 `{origin: "http://127.0.0.1:7890", hasCredentials: boolean, source}`，`url` 不出后端；错误原文经 `models/service.md` 已有的遮盖函数处理并加一条“把代理 URL 的 userinfo 遮成 ***”的用例；web 页的“现在用的”也写 `origin`，带凭据时在句尾加“（带认证）”。这条要进验收映射的 `network` 插件测试。

### 6. 滑块换成分段按钮后，“停下才发一次”的约束没了；方向键一按就把“跟随”改成“明确选择”并逐次写设置
- 严重程度：重要；类别：不变量；位置：计划“AgentRoleModelPicker.vue”（思考档 raised 分段、跟随时 `tentative`）；packages/nb-agent-ui/src/vue/composer/AgentRoleModelPicker.vue:78-97
- 现象：现有选择器给滑块加了 200ms 的“停下才发”（`THINKING_SETTLE_MS`），注释写着原因：“一格一次写设置，多次写入的先后没有保证，停下时可能落在中间那一档”。计划换成 SegmentedControl，没提这条约束。SegmentedControl 的方向键行为是“选中随焦点走”：packages/nb-ui/src/components/controls/SegmentedControl.vue:127-142 在 `handleKeydown` 里对目标项直接 `selectOption`，每按一次发一次 `update:modelValue`；选择器的 `select-thinking` 又直接映射成 `thinking.set` → `changeSettings({effort})`（session-host.ts:1717-1719）。键盘用户在“关闭、低、中、高、极高”上连按 4 次方向键，就是 4 次并发写，落点可能不是最后一次。
- 同一处还有语义问题：跟随状态下 `tentative` 那一档只是“显示默认”，键盘用户用方向键“看一眼邻档”就已经把会话钉成明确选择（`core.effort` 从 null 变成具体值），要再点“用 X 的默认”才能退回。点击已画细框的那一档同理：SegmentedControl 的 `selectOption` 不去重（:112-117），要选择器自己决定“点的就是默认值那一档”时发不发；老代码是 `level !== props.thinking` 才发，在新语义下 `thinking` 为 null，不会被挡，但若实现者把 `modelValue` 绑成显示用的“有效档位”再沿用旧的去重，就发不出去，用户没法把默认值钉成明确值。计划没写这几条。
- 如何核实：读上面两处；在 dom 测试里对 SegmentedControl 连发 ArrowRight 数次，数 `update:modelValue` 次数。
- 建议改法：选择器内给分段按钮包一层与旧滑块同样的合并（键盘连按只发最后一个，或把 SegmentedControl 的方向键改成“只移焦点、回车或空格确认”的一个 `selectOnFocus?: boolean` 开关——后者影响所有调用方，不建议）；跟随态下去掉 tentative 档与方向键的联动：方向键移动焦点不提交，点击或回车才提交；把“点中默认那一档也发”写进验收（dom 测试：跟随态点 tentative 档，期望发出一次 `select-thinking`）。

### 7. 思考档的四种状态只给了名字，没有定义画法与读屏；跟随态“有效档位”该取夹取后的值没说
- 严重程度：建议；类别：正确性；位置：计划“推理档的数据流”“AgentRoleModelPicker.vue”
- 现象：
  - `EffortLevels` 有 `declared`（一档时“画成固定”）、`generic`、`none` 三种加跟随/明确两种；计划只说“按 effortLevels 画四种状态”。r1 稿 effort-states.webp 里 none 是整条灰掉加一句“这个模型不支持思考”，generic 是“?”图标，只有一档是单个固定按钮加“只有这一档”。这些文字与图标的来源（`ComposerView` 没有对应字段）、读屏文字（整组 `aria-disabled` 的 radiogroup 没有“为什么停用”；SegmentedControl 根会透传 `aria-describedby`，所以可行，但计划没写）、“?”的悬停说明都没有定义；nb-agent-ui 的文案要走 `useAgentText` 的目录，两种语言都要补键。
  - `thinkingFollow.level` 是 role 的原始档位还是夹取后的？角色上设了“极高”、模型只有 low/high 时，原始值不在 `levels` 里，分段按钮没有哪一档能画 tentative；内核的夹取在 omp.ts，选择器看不到。计划统一了 `EffortLevels` 的函数，但没有统一“夹取后显示的有效档位”（QaPage 里已经有一份自己的 `clampThinking`，nb-story/src/web/pages/QaPage.vue:269）。
  - r3 稿 picker-raised-models.webp 里在模型库页直接选了模型（触发器只写“DeepSeek V4 · 高”，没有角色），行尾仍写“主力的默认”；按计划 `thinkingFollow.source` 在直接选模型时应是 `"model"`，文案该是“模型的默认”，稿与计划不一致，实现时会被当成回归。
  - 直接选模型且模型没有默认档（“不发”）时，`level` 为 null：哪一档有细框、行尾写什么，计划没写。

### 8. ComposerIcon 用 v-html：能用，但应收窄成 “mask 与 image”，而且 per-model 带图标的字段设计没定义
- 严重程度：建议；类别：代码质量；位置：计划“类型（types.ts）”：`ComposerIcon = {kind: "svg"; svg: string} | …`、`ComposerModelView.icon?`、`groupIcon?`、`ComposerRoleView.modelIcon?`
- 现象：
  - 边界：nb-agent-ui 与应用无关，宿主把 SVG 原文塞进视图、组件 `v-html` 写进 DOM，等于让包信任任意宿主给的标记。本仓库已有先例（neuro-book/src/ui/file-icons/FileIcon.vue:14-15 的 `v-html`，但那是应用自己的组件、表来自生成脚本）；nb-agent-ui 里目前没有 `v-html`，规范里也没有这类约定。真正的 `<svg>` 里可以带 `<script>`、事件属性；计划只写了“同名 .md 写明调用方约束”，没有机检。另外 Vue 的 `v-html` 不会去重 `id`，彩色版图标里的渐变 `id="lobe-icons-…"`（research/magpie.md 已指出这是 lobehub 导出物的特征）在同一页面出现多次时，如果第一份所在的子树被 `display:none`（折叠的分组、关着的 Tab），后面的同 id 引用就画不出渐变。
  - 更窄的做法：Magpie 的做法就是“单色版用 CSS mask（随主题着色），彩色版用 `<img>`”（research/magpie.md 第 1.1 节末）。`ComposerIcon` 改成 `{kind: "mask"; src}`（单色，用 `mask-image:url(...)` 加 `background:currentColor`）与 `{kind: "image"; src}`（彩色与上传图），`src` 是 data URL 或打包后的资源 URL，组件不再解析标记，也没有 id 冲突。上传的图本来就走 `image`，所以同一套代码路径。代价：mask 要求 SVG 是单色图形；lobehub 的单色版满足。
  - 字段设计：视图里同一服务商下的几百个模型各带一份 `icon`（计划同时有 `icon?` 与 `groupIcon?`）：`icon` 是什么的图标没写——服务商图标重复 587 次、还是“系列”图标？若是前者就是多余的（按组取 `groupIcon` 即可），若把 SVG 原文按模型各存一份，587 个视图对象虽然引用同一个字符串，但 Lab 场景、序列化到测试快照、`v-html` 的 587 次解析都变大；若是后者，计划没有定义“系列图标”的来源（模板表只有服务商一级）。
- 如何核实：grep nb-agent-ui 的 `v-html`（无）；看 FileIcon.vue 与 magpie.md 第 1.1 节；在 happy-dom 里渲染 600 行带 2 KB SVG 的列表量一次。
- 建议改法：采用 mask/image 两种；删掉模型级 `icon`，保留 `groupIcon` 与角色的 `icon/modelIcon`；若坚持 `svg`，就在类型注释与 .md 里写明“只收宿主打包的静态资产”并在组件里加一道最小的白名单检查（以 `<svg` 开头、不含 `<script`、`on*=`）。

### 15. SegmentedControl 加 `variant` 与 `tentative`：外观变体可以，`tentative` 的名字与细框语义要重想；指示块的过渡没定

- 如何核实：grep `thinkingLevels`（8 个文件）、`applyComposerAction`；读 context.ts:46。
- 建议改法：新字段全部可选；`effortLevels` 缺省时从 `thinkingLevels` 推出（`declared`，少于一档为 `none`），旧宿主不改；`thinkingFollow` 缺省表示“没有跟随概念”（不画“用 X 的默认”）；`thinking.reset` 只有带 `thinkingFollow` 的宿主才会收到，在 .md 与类型注释里写明；`applyComposerAction` 处理 `thinking.reset` 时清 `thinking`、保持 `thinkingFollow` 原样（默认档由宿主在下一轮视图里给），补一条用例。

### 17. 图标：data URL 存进设置的做法可行，但缺上限的口径、复用点、图标选择范围与角色图标类名的生成
- 严重程度：建议；类别：代码质量；位置：计划“icon?: {kind: "image"; data: string} …≤48 KB”“logos.ts”“上传图标的缩放”“RoleConfig.icon（lucide 类名）”“RolesPage：自建角色可挑图标”
- 现象：
  1. “≤48 KB”是原始字节还是 data URL 字符串没写：base64 后膨胀约 33%，48 KB 的图是 64 KB 的 JSON 字符串。设置里放上限为字符串的 schema（`maxLength`）与浏览器端缩放（目标边长、输出格式：PNG 与 WebP 的取舍）必须用同一个口径，否则“上传成功但写入被 `invalid-value` 拒绝”。计划只写了“浏览器 `createImageBitmap` 加 `OffscreenCanvas`”，没有边长、没有“缩完仍超上限时怎么办”（报错文字？降质量重试？）。
  2. 复用：“按魔数判类型”仓库里已有现成实现 `nbook/shared/image-type.ts` 的 `sniffStillImageType`（PNG、JPEG、WebP，不含 GIF、SVG，正好是计划要的三种）；封面、主题素材、bots 头像（plugins/bots/backend/avatar.ts）、表情包都已经这样做，计划里没有引用，容易再写一份。
  3. 先例与代价：bots 头像、表情包都是“文件加路由”而不是写进设置；独立设计（evidences/independent-design-opus.md:388-393）也是这样做的，计划以“少一条路由”为由换成 data URL。代价没写全：用户层设置文件（`settings.json`，用户也会在“设置文件”视图里读写它）里会出现一行 64 KB 的 base64；每次任何设置写入（含无关的主题）都要重写整文件、重新解析一次；设置文件视图在 Monaco/CodeMirror 里显示一行 64 KB 会卡；快照每次推送带上所有服务商的图标（10 家自定义图标就是 640 KB 每次 `changed`）。可行，不阻断，但至少要把“服务商列表快照只带图标引用，data 只在详情里按需取”写进设计，否则“快照随全部加入变大”的预算（计划已提）会被图标吃掉一部分。
  4. 内置图标的选择范围：弹出的“内置”是只列 logos.ts 里模板用到的几十到一百个，还是 994 个全部？前者没有搜索也够用，后者要搜索与按需加载分页；计划没写，`logos.ts` “按需动态导入成一个块”只对前者成立。
  5. `RoleConfig.icon` 存“lucide 类名”：UnoCSS/Tailwind 的图标是按源码里的字面量类名生成的（packages/nb-ui/src/tailwind.css:31-70 的说明，动态拼的类名需要 `@source inline`）。`i-lucide-${name}` 拼出来的名字在产物里没有样式，选择器与角色页显示为空白。BUILTIN_ROLE_ICONS 与“自建角色可挑的图标”必须是一张写字面量类名的表（`{feather: "i-lucide-feather", …}`），schema 的 `icon` 收表里的键而不是任意字符串，表放在 nb-agent-ui 之外的宿主里并被 Tailwind 扫到。nb-models 是与应用无关的包，不应持有 `i-lucide-` 前缀的类名。
  6. 商标：research/magpie.md 第 1.1 节明确写了“MIT 只覆盖 lobehub 的图形文件，品牌标志的商标归各厂商……NeuroBook 若打包同一批图标要自己判断商标风险”，计划的技术选型表只写了“MIT”，没有记录这一判断（开发者是否知情）。
- 建议改法：1) 写明“≤48 KB 指 data URL 字符串长度”，缩放目标边长（如 128px）与超限处理；2) 引用 `sniffStillImageType`；3) 列表快照里 `icon.data` 换成内容哈希、详情按需取，或直接改回文件加路由（有 bots 头像的先例，代码可抄）；4) 定内置图标选择范围；5) 角色图标用键加字面量表；6) 把商标判断作为一条需要开发者确认的风险写进计划。
- 补正（第 2 条）：AgentWizardFrame 的“停靠”形态已经单独压成一层 0 1px 2px 的轻阴影（e2e/agent-subagents.e2e.ts:125-131 断言 `/ 0px 1px 2px 0px$/`，design-language.md 的“停靠的面不用浮层的阴影档”），所以它不依赖气泡档，应从受影响名单里去掉，只剩它浮动形态的那一支。其余名单项（AgentNoticeCard、批注卡片、AnchoredPopover 系、Popover、Tooltip、DateInput、MarkdownToolbar bottom）我没有逐个核对它们是否也有各自的覆盖，建议在计划里逐个核对后再写“约 20 处”。markdown-comments.e2e.ts:743-760 只断言“当前卡片的 shadow 不是 none”，改档不会让它失败。
- 补正（第 17 条第 3 点）：“设置文件视图里一行 64 KB 会卡”是推测，我没有实测那个视图用的编辑器；该项只当风险列出。

### 18. 协议下拉“每家都有”：没有回到“跟随来源”的选项；检测结果的失效与取消没定
- 严重程度：建议；类别：正确性；位置：计划“ProviderConfig.api?”“ProviderDetail：协议下拉每家都有，旁边‘检测协议’，结果就地列出”“models-store.ts：detectApi……寿命归数据模块”
- 现象：
  - `api` 不写表示“每个模型用来源给的协议”（OpenRouter 的专用协议、12 家混合协议的模板），写了表示“所有模型改用这个通用协议”。下拉里只有四种协议时，一旦选过（或点过检测结果里的“用这个”）就回不去“跟随来源”；“恢复模板地址”只恢复地址。对混合协议的模板，误点“用这个”会让一部分本来能用的模型改成不兼容的协议，且从界面上不可逆。未覆盖时下拉显示什么（空？“按模型”？）也没写。
  - 检测发的是 4 条真实请求、每条最长 15 秒；`detectApi` 是一次调用返回全部，没有取消（对照 settings-pages.md 输出 8 的检测可取消、输出 10 的“对话框关闭后迟到的发现结果丢弃”）。结果按服务商记在数据模块里，但改了地址、协议、密钥或请求头之后，之前的结果就不再对应当前设置，计划没有写“这些改动清掉结果”。现有 `models-store.ts:apply` 只在模型消失时清检测结果，不看地址变化。
  - 同一模型 id 在不同协议下的结果可能被“用这个”误导：检测挑的是“第一个启用的模型”（或含 claude/gemini 的），挑中的模型不一定能代表整个服务商（来源里有 587 个模型，第一个可能是图片模型之外的某个冷门模型）。结果行里没有写“用的是哪个模型”，用户无法判断。
- 建议改法：下拉加第一项“按模型（跟随来源）”，仅在 `api` 未写时选中；选“用这个”前若服务商有混合协议则弹出确认写明影响；`detectApi` 接 `AbortSignal`，页面卸载与改地址时取消；结果带 `{checkedAt, baseUrl, model}`，地址、密钥、协议任一变化就清；结果行写出所用的模型名。

### 19. 验收映射：旧用例的变化、关键交互与可访问性没有对应的断言

### 20. 模型库与添加对话框的键盘与读屏：几百项的列表仍是“每行一个 Tab 停靠点”，折叠组与搜索的联动没写
- 严重程度：建议；类别：测试；位置：计划“模型库按服务商分组带图标与个数，超过 30 个的组默认收起，搜索时只渲染命中的”“AddProviderDialog：分组、组内多列、登录组默认收起”
- 现象：
  - 现有模型库每个模型是一个 `<button>`（AgentRoleModelPicker.vue:279-292），没有方向键导航，Tab 逐个走。分组头加图标与个数后，每个展开的组最多 30 行，几组展开就是上百个 Tab 停靠点；搜索框之后键盘用户只能 Tab 一路下去。计划只写了“只渲染命中项”，没有写：(a) 组头是 `button` 加 `aria-expanded`、可访问名称带个数（“OpenRouter，587 个模型，已折叠”）；(b) 搜索有词时折叠组是否自动展开命中的组（不展开就搜了也看不到命中项，若展开则搜索词清掉后是否恢复）；(c) 搜索框里按 ↓ 进入结果、↑ 回到搜索框；(d) 命中为空时的读屏提示（现有 `noMatch` 是普通段落，没有 `role="status"`）。
  - 添加对话框同理：登录组“默认收起”的组头、搜索时是否展开、多列时 Tab 顺序按行还是按列（DOM 顺序按组内顺序，视觉上多列网格从左到右，一般一致，但 390 宽退成单列时仍一致即可）。“已添加”不停用之后，行的可访问名称要写“OpenRouter，已添加 1 个”，否则读屏用户听不出点它会再建一个。
- 建议改法：在 `.md` 与 dom 测试里把 (a)-(d) 逐条写出；选择器的模型库加上下方向键的 roving 焦点（现有 nb-ui `utils/roving` 就是给这种场景写的）；添加对话框每行的名称带“已添加 N 个”。

## 对“不做与风险”各项的判断
- 不做：OAuth 登录、Magpie 的粘贴 curl 与余额探测与导入、抓站点图标：合理，与前端无冲突；代理只管模型服务：合理，但第 5 条的凭据遮盖要在这个范围内先做对。
- 风险“中继是新的长驻网络组件”：属后端审查范围，前端只关心它的状态不要经 `systemProxy()` 泄露凭据（第 5 条）。
- 风险“OMP 来源合并规则随升级变化”：与前端无关；前端受影响的是来源失败时的 stale 显示，计划没写画法（第 19 条第 7 点）。
- 风险“几百个模型的界面”：低估。计划只覆盖选择器与管理模型，漏了服务商详情、全部模型页、检测全部与当前模型所在组的展开（第 11 条），且“量一次”没有预算。
- 风险“旧配置的读法”：属后端；前端注意旧的 `kind` 字段不会再从快照里出现，ProviderDetail 里的 `provider.kind === 'custom'` 等判断（ProviderDetail.vue:125、226、257）要全部换成基于模板的判断，计划的 ProviderDetail 一条没有提到这几处。
