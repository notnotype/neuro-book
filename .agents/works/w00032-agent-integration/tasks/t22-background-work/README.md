# 后台任务与协作：shell 后台、Agent 后台调用、Monitor、活动面板

## 目标与范围

把 shell 后台命令与 Agent 后台调用当作同一类后台工作统一管理：执行时限、转后台、通知、Monitor、停止与寿命，以及全局的活动面板（对应 omp 的 Agent Hub）

来源：t12 讨论（2026-10-28）；开发者指出 Agent 后台调用与 shell 后台命令逻辑类似，可以统一管理。2026-11-19 重开（开发者：接下来做 t22，也为 [t24](../t24-workflow-integration/README.md) 做准备）。

合同：[`agent/jobs.md`](../../../../../docs/specs/agent/jobs.md)（`implemented`）；本 Task 要做的正是它“不承诺”里的几项，定了再改 Spec。

## 参照（2026-11-19 核实）

- omp 18.14.1（源码 `pi-coding-agent/src/session/async-job-delivery.ts`、`agent-session.ts`、`async/auto-background.ts`）：后台任务结束时把结果（12,000 字以内直接给，长的给预览与地址）作为一条消息送回启动它的会话；会话空闲时这条消息开新的一轮。几个同时结束的合成一条。不送的：已被 `wait` 等着或已取过的；用户打断运行之后，直到有一轮自己正常结束前不自动唤起；换了会话（`/new`）之后送达的丢掉。`bash` 与 eval 单元前台跑过 60 秒自动转后台（`DEFAULT_AUTO_BACKGROUND_THRESHOLD_MS`）。子代理的运行要等它自己的后台任务都送达才算结束。
- Claude Code（本会话自己的工具，2026-10-28 与本次）：`run_in_background` 的命令结束时宿主唤起 Agent；Monitor 把长期运行脚本的每一行输出当事件推给 Agent。
- 其余事实见[外部参照](../../../../../docs/research/agent-runtime-references.md)“shell 工具、执行时限与后台任务”一节。

nb-harness 内核里现成的（[`harness/runtime.md`](../../../../../docs/specs/harness/runtime.md) 输出 3、28、103–107）：宿主身份的 `enqueue` 在运行中是一条插话、下一个边界进这一轮；空闲时宿主的 `enqueue` 留着、不开运行，用户下一句话放行它、先于新话进去；宿主的 `send` 在空闲时开一次运行（`runStarted.by` 是宿主）。结束通知用这些就够，不用给内核加机制。

## 决定

开发者 2026-11-19：下面 6 条都按推荐。

1. **结束通知**：后台任务结束时，启动它的会话怎样知道。推荐：把结果直接送进那个会话，算取过（之后 `wait` 不再交回它）；会话在跑时下一个边界作为插话进这一轮，空闲时以宿主身份开一次运行让 Agent 接着做。不自动唤起：上一次运行是用户停的（结果留着，随用户下一句话进去）；正被 `wait` 或前台调用等着的不另送；同时结束的合成一条。备选：只送进会话、从不唤起；维持现状。代价：自动唤起会在用户不在时调模型，费用上限缺省关（`maxCost` 为 0）。
2. **自动转后台**：推荐 `shell` 前台跑过 60 秒自动转后台，交回任务 id 与输出文件，结束时按第 1 条送达；设置可调，0 为关；`timeout` 短于门槛时照 `timeout`。依赖第 1 条至少送进会话。子代理不自动转（前台等待已有超时返回）；eval 单元不转（内核一次只跑一个单元，转后台后下一个单元要排队，另议）。
3. **Monitor 与 stdin**：推荐不做，记进后续：写作场景里没有要盯着输出流的长驻进程。
4. **活动视图**：推荐不另起面板，Agent 的后台任务（转后台的命令、后台子代理）与在跑或在等你处理的后台会话（`startTask` 起的、不进会话列表的）也进工作台的“后台任务”清单，每项能停止、能跳到它的对话；命令与子代理结束不弹通知（第 1 条已让对话接着走），后台会话等你处理时弹。以后 Workflow 的运行也进这份清单。备选：单独的 Agent 活动视图（像 omp 的 Agent Hub）；不做，只看对话里的卡片。
5. **任务种类开放（为 t24）**：推荐任务中心对别的服务端插件开放登记（种类、摘要、怎样停、结束时交回什么），`shell` 与子代理也改走这个接口；t24 里“Agent 启动一次 Workflow”就是一种任务，`wait`、`kill`、`jobs`、结束通知、卡片与清单都现成。Workflow 自己的事（提问交给谁、结果转换）仍归 t24。备选：接口等 t24 再开。
6. **其余照旧**：任务表不持久化，重启后在跑的按“已中断”收口，不补送通知；上限不变。

留给计划的细节：子代理会话自己的后台任务结束时怎样（omp 是等它们送达后子代理的运行才算结束）；几个任务同时结束的合并窗口；通知文字的形状与截断（沿用 `wait` 的结果文字）。

## 方向调整（2026-11-19）

开发者看过第 2 稿后提出（原话大意）：缓冲区里的话各有发送时机——system-reminder 这类提示下一次请求就发出去、排在插话前面，插话下一次请求，排队下一次运行；Agent 异步调工具取结果有两种，`wait` 自己等，或工具把结果放进内核的缓冲区（本质是别的插件给会话发消息，例如 eval 内核重置时发一条提示）；更新、带进度的计算、Agent 的运行、cron、HTTP 服务、端口转发都是后台任务，可以都归 `nbook.tasks` 管，要按类型、按会话等分类。另要求看 [w00043 t14](../../../w00043-neurobot/tasks/t14-input-buffer-states/README.md)（它也改了内核缓冲区）。

开发者同意（“其他都同意”）：

7. 先写提案“统一后台任务”：形态（一次性、服务、定时）、归属（应用、项目、会话）、来源、存盘与重启、界面分组、Agent 的接法（取件记录与 `wait`、`kill`、`jobs`、结果送达）、内核缓冲区的提示模式与唤起；定了之后 t22 改成它的第一批实现（内核的提示与唤起、一次性任务带归属、Agent 的后台任务搬进 `nbook.tasks`、结果送达、`shell` 自动转后台、eval 的重置提示），服务与定时另开 Task。
8. 缓冲区加“提示”模式：下一次模型请求取走、排在插话前面，空闲时等到下一次运行的第一次请求；不因停止变成留着、不用放行；唤起是发提示时另带的选项。
9. eval：空闲回收、内核意外退出时当场发提示；换 Profile、切分支、换目录、服务重启这类调用时才发现的，仍写在那次 eval 的结果里。

14. 唤起的门挂在会话上（开发者“同意”）：停止被受理、守卫停下、进程中断时会话记一个“等你”标记，写进会话日志、不随回退与切分支变；有标记时后台结果只进缓冲区、不唤起；用户自己发话或点继续时清掉，等着的结果随这句话一起送。

17. 计划第 3 稿的四处取舍（开发者 2026-11-23，“其他的都同意”）：提醒不另过拦截，对服务商的遮盖统一在请求拦截做（开发者：脱敏不是在请求发给服务商时做吗）；子会话也送、不唤起；送达未确认用发提醒的指令 id 在下次打开时重发；eval 提醒同一会话一个 `key`。审查按 2026-11-23 的新分工：本 Task 碰单写者与“只交一次”，计划用快速审查（Opus 先审，omp `@review` 在后台）。
