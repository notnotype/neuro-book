# w00032 t22 设计审查：计划第 1 稿（22ae48c62）

### 1. 停止已受理、尚未收口时，后台结果会重开用户刚停的会话

- **严重程度**：阻断；**类别**：正确性；**位置**：计划“`backend/jobs/delivery.ts`”第 4 步。
- **现象与影响**：`lastChat` 是随叶子走的日志投影，收到 `runEnded` 才出现 `stoppedBy`。用户 `abort` 同步受理后，运行已经不取输入，但 `lastChat` 仍没收口；即使宿主在发话前读到了「在跑」，输入拦截等待期间也能发生停止。此时 `send` 成功交回 `later`，收口批把停止范围外新到的宿主输入放行并开新运行。这直接违反决定 1，不是把 `send` 改成先读一次 `snapshot` 能修的。只压缩时也走 `later`：上一轮对话若是用户停的，不能用「有运行」判解除抑制。
- **核实**：`bun /tmp/review-t22-design/probe-delivery-stop.ts` 走真实内核的 `send`、输入拦截与用户 `abort`，得到 `placement: "later"`、`stoppedBy.kind: "user"`、下一次 `runStarted.by.kind: "host"`、模型端口收到 2 次请求。对照 `run/commands.ts:150–179`、`run/settle.ts:103–149`、`state/kernel-state.ts:67–79` 与 runtime 输出 30、104。
- **建议**：在内核单写者受理位置做原子的「有运行则插话、否则有条件唤起」判定，用已受理的用户停止与最后一轮对话判定；不许唤起时只留着。保留普通 `send` 的语义。决定用户发新话、恢复暂停与切分支各如何解除抑制，并测输入拦截期间停、停止期间到达与只压缩三条路径。

### 2. 送达与 `wait` 没有共享的取件权，结果可以送两次

- **严重程度**：阻断；**类别**：不变量；**位置**：计划 `center.ts`、`delivery.ts` 第 1、2、5 步。
- **现象与影响**：送达挑中终态后要 `await driver.result()`（真实命令要读 `status.json` 与输出文件），再等打开会话与写入。在此期间，同会话的 `wait([id])` 可以把它取走并交回；送达仍握着旧对象并写入。同样，提问在等待写入期间可能已被回答，甚至已经换了一题。`watched` 只制约「先开始等」的一边；每会话只跑一条送达也不约束 `wait`、前台续用或应答。把标记提前又会在拒绝、打开失败、写失败时丢结果；读结果结束后复查一次也挡不住输入拦截期间开始的 `wait`。
- **核实**：按 `center.ts:229–255,267–275`、`jobs/tools.ts:84–96,109–115`、`shell-background.ts:170–179` 和计划的顺序即可走出交错。内核的 `commandAccepted` 与入队同批，但 `writeAndReact` 先落盘再等反应，不能把 Promise 没交回都当作没写过（`run/commands.ts:66–79`、`dispatch/reactions.ts:43–49`）。整个进程崩溃后任务表本来就丢，不需要为此另做持久化；已写的缓冲项不等于要从任务表补送。
- **建议**：任务中心同步仲裁消费权，冻结被领的终态或提问 id，明确 `wait` 遇到领取中的行为；只在明确未提交时退还，按稳定 `commandId` 重试或查询受理。回退到 `enqueue` 只用于确定未写的失败；失败后留给 `wait`，不要让「复扫仍可送」立即无限重试。用真实工具等待挡住结果读取或输入拦截，同时从另一次调用点名 `wait`，断言只交回一次。

### 3. 改写子代理任务的 `runId` 会破坏续用、卡片与中止的身份约束

- **严重程度**：阻断；**类别**：不变量；**位置**：计划“子代理等自己的后台工作”，拟只给 `subagents.md` 加输出 26。
- **现象与影响**：父会话已写入的工具结果仍指向 R1；把活任务改成 R2 后，卡片仍优先按 R1 找历史终态，会在任务正在等或 R2 正在跑时显示完成，随后自动取件移出任务也无法校正。驱动结果现在闭包捕获 R1，改单个字段不会改它。子会话在空档能被用户或父 Agent 先发话，结果可能进入那次运行；`forRun` 此时按 R2 可查不到旧任务，`agent_send` 会再占名额或拒绝，甚至先建第二个跟踪者。把 R2 一律算 `ownRun` 会让父会话中止牵连用户开的运行；当前 `abort` 停的是此刻的运行，不校验预期 `runId`，空档调用则什么都不停。
- **核实**：对照 `subagents.md` 输出 6、10、11、16、21，`jobs.md` 输出 9 与状态表，`conversation.md` 输出 33；走读 `jobs/center.ts:147–154`、`subagents/children.ts:45–59,109–121`、`subagents/tools.ts:266–274,290–311,403–426,539–542`、`subagent-card.ts:122–137`。现行合同明确一个任务对应一次运行，不能只追加输出 26。
- **建议**：保留一任务一运行，后台结果若开续跑则明确怎样关联新运行与原任务，别改历史身份；若产品要父任务跨多次运行，另定义稳定任务 id、当前运行、受理与归属、卡片的持久终态。中止只对核实归属的指定运行生效；保留用户运行不连带及续用名额合同。

### 4. 子代理等错了信号：没有待送任务，不代表结果已进入运行

- **严重程度**：重要；**类别**：不变量；**位置**：计划 `children.ts` 与 `delivery.ts` 第 4–6 步。
- **现象与影响**：`send` 成功并不保证开了运行或结果已被取走。暂停且宿主无权恢复时成功值是 `held`；收口窗口是 `later`，再解析模型失败也会留着；原运行被停或出错时，已受理的输入也可以没进模型。计划在写进缓冲区时就移出任务，却让父任务按“在跑／排着／送达中”判断：失败后重试不休则占住父任务名额；不重试或落成 `held` 则可能宣称子代理已处理完，实际用的是旧结果。不能靠一次 `onChanged` 或下一次 `runStarted` 补齐两者之间的空档。
- **核实**：`run/commands.ts:155–182`、`run/settle.ts:99–149`、runtime 输出 36、103–106 与现有 `buffer.test.ts` 的真实内核用例；omp 18.14.1 `session/agent-session.ts:3463–3476` 明确计入已移出送达队列、尚未注入模型的结果，`task/executor.ts:2625–2648` 区分等结果、重新交最终结果与模型错误退出。
- **建议**：由同一处状态跟踪 `inputId` 及其去向，只有确实能唤起、正被处理的工作才延长父任务；留着待用户、打不开、模型或预算失败要有明确退出和报告。若维持跨运行等待，明确 `kill` 先封住该任务的后续唤起，再停归属明确的工作；不要让无时限命令耗尽名额后只能靠用户猜测。用真实运行验证有输入已受理但未取走、模型无法唤起，以及 `kill` 撞在换轮空档。

### 5. 接手失败后的前台时限会被底层报成中止，不是超时

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `shell.ts`，第 68 行；验收映射第 154 行。
- **现象与影响**：省略 `timeout` 且可自动转后台时，计划不传原生 `timeoutMs`。若到上限不能接手，套件计时到 300 秒只能去取消命令；如果仍按原生结果映射，工具变成 `cancelled`、`timedOut: false`，违反 `builtin-tools.md` 输出 22。不必为自动转后台取消默认期限：决定 2 只规定何时交回，不规定省略 `timeout` 后要变成无限期。若保留这条作者选择，还须定义门槛等于或大于 300 秒、前台时限与移交同时到达、取消已经获胜后不得继续接手。
- **核实**：`bun /tmp/review-t22-design/probe-brush.ts` 用当前安装的真实 `executeShell`：带 `TimeoutError` 原因的 `AbortController.abort()` 得 `{cancelled:true,timedOut:false}`；原生 `timeoutMs` 到期得 `{cancelled:false,timedOut:true}`。`kit/tools/shell.ts:135–159` 直接按原生字段定码。omp 18.14.1 的 `tools/bash.ts:938–949` 将原期限交给同一个进程，`async/auto-background.ts:16–20,38–73` 限制前台等待并清理定时器，而不是转后台时取消期限。
- **建议**：优先保留原默认期限，明确自动转后台与显式 `async: true` 的区别。若要省略即无限期，前台期限、父调用取消和接手要用同一个仲裁点记录胜因；恢复期限映射（含 `details` 与保留输出），用注入时钟配真实进程验收。

### 6. `adopt` 没有定义一次性移交；仅拷贝输出字节也会丢状态

- **严重程度**：重要；**类别**：不变量；**位置**：计划 `ShellBackground`、`RunningCommand`、`openCommandOutput`。
- **现象与影响**：`adopt` 是 Promise，且要定位目录、占名额、建文件。期间进程仍可输出、退出，父调用也可中止。先登记再拷贝会让 `jobs`、工作台取消与关停看到半接手的命令；异步复制后再改出口会漏掉复制期间的块；全同步则一次可读写 64 MiB，挡住服务端处理取消和其他会话。另一个反例不依赖竞态：移交前已超过 64 MiB、移交后不再输出，重放恰好 64 MiB 不会设置 `truncated`，也不能重建超过上限后的行数、最后一行或写入错误。已有暂存文件出错时，“拷贝全文”根本不可兑现。
- **核实**：`kit/tools/output-capture.ts:30–73,83–105` 保存的是有界字节、独立的总字节数和错误；`shell-background.ts:88–145` 按每块累计行数并在结束时写 `status.json`。现有 `jobs.start` 立即发布（`center.ts:130–135`），不是提交前的私有阶段。
- **建议**：只起一个进程，先准备后台输出目标，再同步决定所有权、取消连接和任务可见性；失败清理占位与文件、原调用继续，不重跑命令。优先让一个输出记录持有字节、统计和故障，移交该记录或接续一个有顺序的汇，别公开 `copyOutput`／`redirect` 两步协议。验收覆盖准备期间退出/中止、写失败、移交前超 64 MiB 后无新输出、跨界未换行与状态文件一致。

### 7. 登记句柄会越过插件代次；关停后仍可能启动任务或调用已停的驱动

- **严重程度**：重要；**类别**：不变量；**位置**：计划 `AgentService.jobs`、`JobSlot`、`JobControl`（第 80–100 行）。
- **现象与影响**：内核只作废门面的顶层方法及属性访问。先取出的 `jobs` 对象、已拿到的 slot/control 不随它失效；计划只收口「在跑」的任务，而 `starting` 也占全局名额。停止前占位、停止后 `start`，或丢下没释放的 slot，分别会复活任务和卡住名额。已经结束、但尚未交付的任务也可能在入口释放后首次调用 `result()`；已经开始的读取/停止不因门面作废而结束。把状态改为 `interrupted` 而不撤掉驱动，解决不了这两条路径。
- **核实**：`bun --no-install /tmp/review-t22-design/probe-facade.ts` 走真实 `nb-runtime` 插件装配、停止与释放：`onStop` 内顶层方法仍可用，停止后缓存的顶层方法抛 `ServiceRevokedError`，缓存的 `jobs.begin` 仍进入实现。对照 `services/per-consumer.ts:52–86`、`composition.ts:599–623`、`jobs/center.ts:119–140,174–184`、`runtime/services.md` 输出 12 与 `runtime/plugins.md` 输出 13。
- **建议**：按消费者代次跟踪所有占位、任务和在途驱动调用；入口停止前由登记方取消实际工作，释放时封闭该代次并同步撤掉未启动占位、终结在跑的，之后的句柄调用不能再改变任务。完成时冻结有界结果数据或由 Agent 持有的地址，而不是停完后再向旧驱动取。把 `beginJob` 放顶层还可沿用现成的作废规则；slot 的二次启动、释放后启动、停止中启动仍要自己保证。补两代激活与迟到回调的真实装配测试。

### 8. 后台会话的内置提问进不了计划的提醒路径

- **严重程度**：重要；**类别**：正确性；**位置**：计划工作台镜像第 105 行、Spec 改动第 126、130 行与验收第 152 行。
- **现象与影响**：`background: true` 会话调用内置 `ask`/`ask-form`（包括 `async`）直接得 `ask-unavailable`，不会写入提问事项；模式切换工具同样拒绝。审批是另一条路径，可以进入等用户。只改镜像，验收里“后台会话的提问”若用产品内置工具就过不了；若用自定义工具调用 `ctx.ask` 可以证明镜像，但不能证明用户会在内置工具的场景看到所承诺的通知。
- **核实**：`builtin-tools.md` 输出 25、28；`kit/tools/ask.ts:103–122`、`backend/permissions/modes.ts:81–83`；`builtin-tools.test.ts:532–541` 是经产品运行时断言后台会话不进等待的既有用例，审批走 `kernel/run/tools.ts:405–417`，不经过 `askTool` 的 `background` 判定。
- **建议**：明确产品要哪些事项。若内置提问也要通知且可答，同片改输出 25、28 与门禁，并明确只等待同步事项还是也提醒跨轮的异步问题；若维持现有提问合同，把验收明确改成真实 `startTask` 的审批与自定义工具的同步事项，不要把内置提问写成已支持。还应验证从通知打开并处理后同一条提醒确实撤回。

### 9. 只给清单加字段，不等于 v1 可以继续互通

- **严重程度**：重要；**类别**：正确性；**位置**：计划清单第 112 行（远程合同版本不变）。
- **现象与影响**：当前 `TaskItemSchema` 拒绝额外字段，`list` 和 `changed` 复用它；旧调用方看到带 `notify`、`open` 或 `attention` 的一项就无法按 v1 接收整份清单。把新字段设为可选只解决新调用方读旧数据，不能解决反向。整应用版本门若保证混合版本不可能接通，可以不提供滚动兼容；但那是发布前提，不是 schema 兼容。
- **核实**：`plugins/tasks/shared/contracts.ts:70–106`、`runtime/plugin-channel.md` 的版本与输出校验规则；对照 `runtime/projects.md` 输出 18 提升版本、让旧页面得到 `version-changed` 的既有做法。没有浏览器跨版本试验。
- **建议**：把字段和合同版本一起改，或写清可以依赖哪一道整应用版本门、哪些调用方一定同版。增加旧调用方可解释地拒绝及同版 `list`、`changed` 恢复的合同用例；不要靠旧端吞掉校验错误。

### 10. 计划给内置任务留了第二条登记路径，和决定 5 相反

### 12. 后台提问的送达文字不足以调用 `agent_answer`

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `delivery.ts` 第 2 步、验收映射第 149–150 行。
- **现象与影响**：计划只承诺题干、提问 id 和一句“用 agent_answer 回答”。`agent_answer` 的 `id` 要的是子会话 id，不是任务 id；`ref: jobs:<id>` 亦只有任务 id，默认模型渲染不交出这个 `ref`。现有 `wait` 的文字也短，但 `details.jobs` 有子会话 id，子代理直接交回的文字亦带地址。异步派出多个同 Profile 的子代理时，自动送达不能让模型单凭这条消息应答。结构化回答还需要题干之外的必要格式；计划的“一律不用 wait”也不区分待答与已经结束。
- **核实**：`subagents/tools.ts:94–109,609–629`、`jobs/tools.ts:64–76,91–96`、`subagents/children.ts:69–84` 与 `subagents.md` 输出 11。`JobQuestion` 只有 `{id, text}`，不是完整的 `interactionRequested`。
- **建议**：每条可由父 Agent 应答的通知写明 `sessionId`、`questionId`、题干与必要的 `answer` 形状，明确审批、模式请求和交给用户的提问不走这里；终态与待答分开措辞。用两个子代理的真实问答验收：父模型收到送达后无须先查 `jobs`，能用给出的 id 应答正确的事项，已换题的通知不替代新题。

### 11. 批量送达直接拼 `wait` 全文，能把会话快照撑到不可用

- **严重程度**：重要；**类别**：安全与性能；**位置**：计划 `delivery.ts` 第 2、3 步、`AgentJobs` 第 85–96 行、对话行第 116 行。
- **现象与影响**：一条命令的结果可带约 40 KiB 的头尾窗口。同一会话允许保留 32 个未取的终态，7 个饱满窗口就超过单事件 256 KiB，13 个就超过 `snapshot` 的 512 KiB；用户停止时这条合并输入会一直在缓冲区，`eventChunk` 能取大日志事件却救不了 `snapshot`。外部任务的 `result()` 是任意长字符串，无需有很多任务；`label`、`summary`、`progress` 又可进入整份 `jobsChanged` 及清单，有各自的体积和文字校验契约。默认模型渲染把 `input`/`steer` 当用户消息，并不把 `by` 的宿主来源变成模型可读的身份或单独的数据边界。
- **核实**：`shell-window.ts:6–12`、`shell-background.ts:170–188`、`jobs/center.ts:18–20`、`backend/frames.ts:13–17`、`backend/remote.ts:154–158,202,226` 和 `kernel/view/format.ts:35–44,85–92,119–130`。omp 18.14.1 `session/async-job-delivery.ts` 单项过 12,000 字符时改用有界预览与地址，并转义输出数据，不把它误作宿主标记。
- **建议**：给每项、每批及留着的结果设预算（按 UTF-8 字节并给 JSON 转义留余量），正文过长存到可读地址，预览保留 id、类型、状态、退出码和来源；模型与 UI 共用结构化元数据，不解析输出正文来识别宿主指令。补多任务同刻完成、引号与多字节字符、长外部结果、用户停止后重开快照的用例。

### 13. B 不唤醒任务等待器，却经插话路径把 `wait([A])` 打断

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `wait` 改动、`delivery.ts` 第 4 步、待确认 3。
- **现象与影响**：只让 `JobCenter.waitNext` 按名单筛选不够。正在等 A 时，B 的结果可能作为就绪 `steer` 入队，现有 `watchSteer` 会把它当用户插话，使 `wait([A])` 提前返回。若只过滤 B，结果要等这一整批工具结束才进模型；“不返回”与“立刻看到 B”不能同时保证。计划还用了单个 `watched`，但 `wait` 是 `shared` 工具：两个等待可重叠，一个返回不能提前解除另一个的阻挡。
- **核实**：临时 `probe-wait.ts` 经真实 `JobCenter`、`jobTools` 和内核批调度，B 仅结束时不返，送 B 的宿主 `steer` 后返回“用户插话了”，A 仍为 `running`。同批一个无参等待和一个点名等待在同一任务结束时都交回了终态（`parallelWaitResults: 2`）。按第 2 条复刻“先读结果再送达”时，点名 `wait` 先取走，已在途送达仍成功另开运行（`sameResultViaWaitAndDelivery: true, driverReads: 2, deliveryPlacement: taken`）。等待超时和用户停止均不停止任务，之后仍可取到终态。
- **建议**：定义“用户插话”与后台结果可否打断等待，两处 `watchSteer`（初查与订阅）按可信来源执行同一规则；B 可先入缓冲、在 A 完成/超时后再给模型。观察按调用登记并成对退还，取件按第 2 条另设排他领取。验收交错两个等待一先超时/取消、另一个仍在等；最后一个退还时终态和未答题均可再送。

### 14. `jobs.close()` 只拒绝预占，已经进内核的送达仍可在停止后开运行

- **严重程度**：重要；**类别**：不变量；**位置**：计划“送达”第 6 步、切片 2 的装配。
- **现象与影响**：停止先关任务表与会话表的入口，等后台命令结算及 Profile 停止，之后才真正关闭会话。送达若已取得会话引用、阻在输入拦截，关门不撤销那次调用；拦截回来后仍会写 `runStarted`、向模型发请求。只在扫描前或 `await` 前看停止标志守不住这个窗口；反过来，停止若等待整个送达队列而拦截未退，也会卡住关停。
- **核实**：`backend/agent.ts:442–456`、`kit/sessions/table.ts:213–216,244–285`、`kernel/run/commands.ts:63–79`。`probe-wait.ts shutdown` 在真实内核的输入拦截里关 `SessionTable` 门：新读被拒，放开拦截后旧 `send` 成功开运行，并实发一次模型请求。
- **建议**：送达管理器的停止与会话受理之间要有栅栏：关门时先取消/封住所有未提交送达，内核在判定写入和唤起的位置检查停止状态，并收口已提交的输入；仅对未提交的请求可退还领取。验收令外部驱动读结果、输入拦截、后台命令写状态各挂起一次，不允许关门后再开新运行，也不死等已关的会话。

### 15. 外部登记只盖任务种类，没绑定任务所属会话与真实工具调用

- **严重程度**：重要；**类别**：不变量；**位置**：计划“任务种类开放”的 `AgentJobs.begin`、验收映射第 151 行。
- **现象与影响**：`owner`、`invocation` 都是字符串，服务门面只能知道插件身份，不能从这两个参数知道调用正在执行、由该插件提供、属于同一会话。写错会话或重用上一轮的 id 仍可占全局名额、出现在别人的清单、把结果送给别的会话甚至唤起它；会话不存在时拖到送达阶段才失败。这不要求防住恶意的本机插件，要求的是入口能兑现“调用工具的会话、这次调用”的合同，且不会把 bot 等服务层的归属误当成工具归属。
- **核实**：`kernel/api/tool.ts:106–114` 明确区分 `callId` 与跨回复唯一的 `invocation`；`agent/shared/resources.ts:54–58` 的工具服务没有登记能力；`backend/agent.ts:480–501` 的门面只有 `ConsumerIdentity`；`jobs/center.ts:118–127,215–225` 原样用 `owner` 作任务归属。没有新增 API，未把源码推演当作产品复现。
- **建议**：对工具开放由执行器按真实 `ToolContext` 绑定的登记口，在调用结算时撤销登记权（已启动的任务继续按所属插件代次收口）；对 t24 若还需服务层发起，另明确它的会话与来源身份，不伪造工具 `invocation`。验收交叉使用两个会话、两个插件及旧调用的凭据，同时规定无效 `kind`、空标签、坏 id 的失败码与名额不变。

### 16. 外部任务单独中断，镜像项却没有结束路径

- **严重程度**：重要；**类别**：正确性；**位置**：计划第 100、104 行，`AgentJobs` 停止、`mirror.ts` 终态映射。
- **现象与影响**：登记插件单独停用时，Agent 里的任务按 `interrupted` 收口；工作台项却是 `nbook.agent` 调 `tasks.start` 建的，发起方没有停。`TaskHandle` 没有 `interrupt`，计划只映射成功、失败、取消；“由 `nbook.tasks` 随 `nbook.agent` 停止转成”要等后者也停止，甚至应用关停时窗口看不到这次转换。这期间镜像一直显示运行、取消按钮找不到真实工作，宿主还把它报为关停会中断的工作。
- **核实**：`background-tasks.md` 输出 3、5 与时序条款；`tasks/shared/contracts.ts:37–54`、`tasks/backend/core.ts:244–258` 按登记它的 `ConsumerIdentity` 释放。已跑既有用例“发起方入口单独停止……”，证明停的是实际持 `TaskHandle` 的发起方；测试没有假装外部 Agent 任务登记已经实现。
- **建议**：让镜像拥有显式的 `interrupted` 终态操作，或提供受管的发起方归属能力，二选一并写进 Spec；不可报成普通失败来补齐。验收保持 Agent 和窗口都在线，只停一个插件代次；其任务与镜像都为已中断、另外代次/插件的任务继续，且不误触发取消回调和结束弹窗。

### 17. 直接镜像会重复报告在跑的工作；不合规的标题可打断任务结算

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `mirror.ts`、切片 5。
- **现象与影响**：Agent 和 `nbook.tasks` 都向宿主报告在跑的工作，报告项只有发起方和文字，没有底层工作 id；计划新增镜像但不改报告来源，关停确认会把同一项再报一次。镜像拟把原摘要/标题塞进本地化文字的参数：对这种结构，任务服务不是按 200 码元截断，而是超过 1,024 字节就同步抛错。如果从 `JobCenter.onChanged` 同步调用 `tasks.start`，这个异常会打断后续等待者通知；在 `shell` 的 `jobs.start` 处甚至可能让已执行的命令被报告为“命令没有执行”。
- **核实**：`probe-mirror.ts` 在实际 `startTask(background: true)` 等审批时，用真正的任务服务登记一项代表该会话的镜像，宿主同时列 `nbook.agent`、`nbook.tasks`；用 1,308 字节文字引用登记，`tasks.start` 同步抛 `invalid task title`。异常传播是源码推演：`tasks/backend/core.ts:86–95,215–221`，`jobs/center.ts:130–135,323–333`，`shell-background.ts:49–54,118–155`，`backend/running-work.ts:60–75` 与 `server/running-work.ts:77–92`。
- **建议**：工作台镜像不另算关停工作；保留原 Agent 报告语义（前台不进任务视图，仍要报告）。在镜像边界按编码后的文字预算截参数，校验/推送失败记录诊断、不得打断真实任务的状态转换。验收一个会话和一个命令各在宿主只增加一项；超长、多字节标题时等待和收口照常。

### 18. 点上一轮的“取消”可以停掉用户刚开的下一轮

- **严重程度**：阻断；**类别**：正确性；**位置**：计划 `mirror.ts` 第 105 行（每次运行一项，以用户身份中止这次运行）；也适用于第 42 行的子代理 `kill`。
- **现象与影响**：镜像项以一次运行区分，`abort` 却只按会话定位，且不进单写者队列。若点击来自上一份清单，或取消处理读完快照后该轮收口、另一轮已开，实际停的是新运行；`cancelRequested` 也不能说明原运行被停了。旧行还可能保留“正在取消”，而新行收到用户中止。
- **核实**：`kernel/run/commands.ts:316–331`、`run/control.ts:109–118`、`tasks/backend/core.ts:266–275`。`probe-mirror-cancel.ts` 经实际 `startTask(background: true)`、任务服务、JSON 链路与本机模型端点：取消回调已读到 R1，R1 正常完成，用户开 R2，回调再调用 `abort`，实测 R2 为 `aborted`、`stoppedBy: user`。探针只复刻取消转接，不把镜像当已实现。
- **建议**：若行的语义是“这次运行”，内核在 `recordStop` 的同步受理点核对期望 `runId`，旧运行已结束时不碰新运行，镜像按旧运行真实结果收口。只改成“按会话取消”会改变用户动作含义，且仍不能供子代理的按运行中止复用。验收旧快照点取消、已结束到新一轮之间、两个窗口重复取消。

### 19. 宿主送达会解除“等用户发新话”的循环保护

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `delivery.ts` 第 4 步、“不做与风险”第 167 行。
- **现象与影响**：`tool-call-loop` 以 `error` 收口，不是用户 `aborted`。按计划，下一条后台结果会用宿主 `send` 开新轮；循环保护只看新轮有没有输入，不看发出者，于是清掉停止状态。用户不发话也可继续调模型，绕过现有保护。费用上限是在模型请求前另行拦截，不能代替这道检查。
- **核实**：`agent/run-guards.md` 输出 8、10 与“关键不变量”；`kit/guards/loop-guard.ts:54–70,85–91`。`probe-wake-guard.ts` 经真实内核与 `loopGuard` 得到 `firstRun: tool-call-loop`、`startAfterLoop: tool-call-loop`、`hostDeliveryAfterLoop: completed`，后一次额外发了 1 次模型请求。探针只按计划使用宿主输入，未实现自动送达。
- **建议**：明定后台结果不能代替用户解除保护；对这类停止留着结果，只有实际用户发新话或依 Spec 关闭保护才能继续。若产品有意让任务结果解除保护，需改 `run-guards.md` 并写清适用的结果与重试上限。补循环保护和费用拦截两种验收，分别断言结果去向及模型请求数。

### 20. 活动汇总不能当“每次后台对话运行”的清单真相源

- **严重程度**：重要；**类别**：不变量；**位置**：计划 `mirror.ts` 第 105 行，`sessions.md` 输出 12 的验收。
- **现象与影响**：`activityWithBackground` 是关停汇总：前台、后台与只压缩的会话都可能在里面，只有 `id` 和 `running/waiting`，没有运行 id、运行种类、会话后台标志或待处理事项 id。`onActivityChanged` 只在忙闲／等待布尔值变化时回调，回答第一项、仍有第二项时可以没有变化。只补订阅日志也不够：打开前的帧不补、接续暂停运行写 `runResumed` 而不是 `runStarted`，断裂日志还能先到 `broken` 而没有 `runEnded`。按这些回调一见忙就建、一见回答就清，可能给前台或只压缩建错行、漏建接续行，或在还有用户审批时撤掉提醒。
- **核实**：源码与合同推演：`kit/sessions/table.ts:154–187,314–335,365–381`；`kernel/api/events.ts:123–134,222–223`；`kernel/run/commands.ts:115–121,175–182`；`kernel/run/control.ts:162–178,228–238`；runtime 输出 36、39–43。`probe-mirror.ts` 已证实后台会话能等真实审批，未运行计划中的镜像投影。
- **建议**：镜像以已受理的会话头、实际 `(sessionId, runId)` 与有序生命周期为输入；初始从同一快照拿身份与当前叶子，和后续帧按水位合并；终态、异常断开与 resumed 的同一 id 分别定义。待办按当前叶子上的事项集合算，只认该用户应处理的事项，决定异步问题留在空闲分支时是否还要显示；不能以一条回答清整个任务。验收前台、内部标题、纯压缩都不建行，两个待批事项分次答，接续旧运行与日志损坏各收口一次。

### 21. `attention` 只有文字，合并推送后认不出换了一批待办

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `nbook.tasks` 第 111–112 行、验收映射输出 20。
- **现象与影响**：同一运行先问 A，用户答了；250 毫秒内又问 B。两份清单都只是 `attention: "等你处理"`，窗口看不到中间的 `null`，按“从无到有”不会为 B 发通知。A 若已关闭或点过“打开”，此时没有 B 的提醒；两项同时待批时，也不能答一项就撤整条。反过来，重连时盲目把当前有值当成新待办，又会重发已经看过的 A。继续只用结束通知的基线则会吞掉断线时新出现、现在仍需要操作的 B。
- **核实**：`tasks/backend/remote.ts:25–31,44–63`、`shared/push-throttle.ts:19–28,36–50`、`tasks/web/store.ts:93–113,140–155`。`probe-attention-coalescing.ts` 经真实任务服务、注入时钟与 JSON 链路，借现有 `message` 模拟同形状文字字段；服务端中途读到 `null`，窗口两次推送看到的都是“等你处理”。这是快照合并的已证实行为，不是新提醒的产品复现。
- **建议**：给待办一个稳定标识或当前待办集合版本，按未解决的状态对账，不把 `null` 边沿当事件。定义首次连接、重连、可见状态、用户关闭或点“打开”后的本窗口记忆；新待办和已处理待办的撤回不受 `notify: false`（仅用于结束）影响。验收两个窗口、断线前有 A／断线后是 B／断线期间重新清空三种状态，以及 A 清掉、B 到达在同一合并窗口内。

### 22. “打开”在书架上可返回成功却不显示对话，还会移除唯一提醒

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `mirror.ts` 的 `nbook.agent.focus-session`，`nbook.tasks` 输出 19、20。
- **现象与影响**：书架页照样订阅清单、挂通知，却不加载工作台布局；`focus-session` 默认走 `nbook.view.open`，后者在布局未就绪时得 `unavailable`。`reveal()` 不读该结果，仍切换后台的会话宿主，`focus-session` 报成功；没有可见的对话去处理审批。通知动作调用后立即从队列与中心移除，即使打开失败。清单里还可能有已停插件的命令或参数已不合 schema 的动作。如果给既有成功/失败通知也加“打开”，还会与失败通知必有的“重试”（可重试时）、成功通知的限时相撞：现有通知只能有一个动作，带动作默认常驻。
- **核实**：`workbench/home-page.ts` 对应实现 `web/home-page.ts:85–113,141–147`、`workbench/web/plugin.ts:282–299`、`agent/web/plugin.ts:317–321,666–671,695–700`、`workbench/web/commands/view-commands.ts:30–38,152–160`。实跑 `view-commands.test.ts` 的“布局没打开时不可用”：1 通过，13 个断言；完整书架点击是源码推演，未跑浏览器。命令解析、参数与可用性失败见 `commands/shared/registry.ts:308–325`；通知移除与时长见 `workbench/notifications.md` 输出 3、4、13 与 `background-tasks.md` 输出 14。
- **建议**：先定义“打开”是本窗口可到达的导航，不只执行任意命令；给 `command` 与对象参数设验证和编码预算，在本窗口复查命令及作用域，并呈现不可用/失败。保证书架或布局未就绪时能去正确的工作台，或不要给点不动的动作；失败不能把唯一提醒吞掉。保留失败的“重试”和成功的限时，明确何时用“打开”。验收从书架、未加载布局、普通工作台点击，以及命令停用或参数失效；断言真的看到目标会话及待办，不只断言命令被调。

### 23. 停止后留着的结果，回退分支后能被下一条宿主送达放行

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `delivery.ts` 第 4 步，“用户下一句话放行它”。
- **现象与影响**：无运行时宿主 `enqueue` 写的是 `cause: {queued: "idle"}`，没有 `heldBy: user`；缓冲区跨叶子共享，最后一次对话的停止原因却随叶子变化。用户停止后先来的结果被留着，用户只回退到另一个叶子、未发新话；之后另一个结果根据新叶子走宿主 `send`，会把第一条一并放行，甚至让它开第一轮。手工恢复时两条结果跟谁走，以及回退本身是否算解除用户停止，计划没有定义。
- **核实**：`run/commands.ts:175–182,197–211`、`run/permissions.ts:11–25`、`state/kernel-state.ts:147–178` 与 runtime 输出 103、105。`probe-held-host.ts` 用真实内核做用户停止、宿主留置、回退和下一次宿主送达，观察到 `afterUserStop: held`、`oldResultTakenByHostAfterRewind: true`，路径先见第一件结果再见第二件，没有用户新话。
- **建议**：把“会话此刻可自动唤起”与“这条已留置的结果由谁才能放行”分开定；若回退不等于恢复，保留用户放行的事实，不能只依赖每次读当前叶子。验收停后连续来两件、只回退、用户明确继续、用户下一句分别怎样放行，断言第一条实际被谁、在哪条路径取走；若允许只回退就重启，明确写进合同。

**第 9 条补证。** `probe-list-v1.ts` 经真实 `nb-runtime` JSON 链路模拟提供方仍为 v1、只加一个可选的 `notify`：`{"sameContractVersion":1,"oldList":"provider-error","oldChangedDelivered":0,"newList":true}`。验证的是远程合同两端，不是不同构建的浏览器握手；整应用版本门仍须单独说明。

### 24. 前台续用会被镜像误认成后台任务

- **严重程度**：重要；**类别**：不变量；**位置**：计划 `mirror.ts` 第 104 行、验收映射第 152 行。
- **现象与影响**：前台 `agent_spawn` 在发布任务前已 `attach`，但前台 `agent_send` 或 `agent_answer` 新登记任务时，`adopt` 先经 `children.start` 发布 `running`，调用者随后才 `attach`。在现有同步 `onChanged` 上按 `running && waiters === 0` 建镜像，会给始终在前台的任务建行；计划又规定之后变成前台不撤，于是这条可取消的错行会一直留到结束。
- **核实**：源码顺序：`subagents/tools.ts:290–303,325–329,419–425,539–544`、`subagents/children.ts:45–59`、`jobs/center.ts:130–135,200–213,323–330`；未运行计划中的镜像。
- **建议**：首次发布任务时就带上真实的前台归属，只有明确从前台转为后台或直接在后台启动才建行。验收覆盖前台派发、前台续用启动新运行、以及前台超时后转后台，分别断言不建、仍不建、只建一次。

### 25. 自动取走子代理结果后，历史卡片失去持久终态和结果正文

- **严重程度**：重要；**类别**：正确性；**位置**：计划 `delivery.ts` 第 2、5 步、对话界面第 116 行、`conversation.md` 输出 33、51。
- **现象与影响**：即使保持一个任务对应一个运行，后台派发的调用结果仍是 `running`；原卡片从后来的 `wait` 等工具结果读取 `details.runId/state/line` 和正文。自动送达只写宿主输入文字、再移出任务，旧卡片只能回退到 `tree.runs`，此时只有结束原因，没有结果首句和正文；同一个子会话再收口 20 次后，原运行还会被挤出索引，父子都空闲时旧卡片变成“状态未知”。新送达行能展开正文，不等于旧卡片的可见合同仍成立。
- **核实**：源码与合同推演：`agent/web/subagent-card.ts:91–102,129–157`、`nb-agent-ui/src/kernel-transcript.ts:499–507`、`agent/backend/subagents/tree.ts:125–145`、`nb-harness/src/kernel/log/index-file.ts:6,60`；`conversation.md` 输出 33、`subagents.md` 输出 21。不是第 3 条的跨运行身份问题，未跑浏览器。
- **建议**：保留自动送达的结构化任务 id、运行 id、终态和结果预览，供原卡片与送达行共同读取；或明确用原卡片的运行 id 按需读持久日志。不要从展示正文反推身份。验收自动送达后不再调用 `wait`、重开父对话且原运行已移出 `tree.runs`，断言原卡片仍显示该运行的终态并可核对结果。

### 26. `ShellBackground` 的破坏性变更没有公开迁移边界

- **严重程度**：建议；**类别**：正确性；**位置**：计划 `ShellBackground` 第 46–65 行、切片 3、“不做与风险”第 169 行。
- **现象与影响**：旧宿主交的是函数，按新方案执行 `start`、`threshold` 或 `adopt` 时，该函数不能满足新接口。计划已识别这是破坏性变更，但“仓内现有宿主只有 NeuroBook”不能证明不存在包外调用方；仓内的测试也不能判定旧公开用法仍能升级，或新宿主能从包的公开入口得到移交类型。
- **核实**：`packages/nb-harness/package.json:3,17–40` 当前为 `0.1.2` 且公开 `./kit/tools`，`kit/tools/index.ts:29,35–55` 转出类型并由 `builtinTools` 消费，`kit/tools/shell.ts:112–116,131–133` 是可调用函数；ADR 0029 决定这些包按源码发布，允许其它宿主单独使用，并采用 `workspace:^`。未查询包外实际调用量。
- **建议**：先按第 5、6 条确定最小的接手协议；保留旧显式 `async` 的起动合同、单独加可选接手能力，或明确采用不兼容的包版本并给宿主迁移说明。用一份只从 `@notnotype/nb-harness/kit/tools` 导入的宿主夹具检查公开形状，不用仓内深导入或提前发布证明兼容。

### 27. 新旧验收对闲置后的 `wait` 给出相反预期

- **严重程度**：重要；**类别**：测试；**位置**：计划第 124、149–150、156、161 行与 `jobs.md` 输出 6、验收 4。
- **现象与影响**：现有验收 4 要求子代理在父会话闲置超过 30 秒后完成，之后 `wait` 仍能取到；计划规定向这个空闲会话自动送达并视同取过，只补新验收会留下互斥判据。既有脚本里紧接派发调用 `wait`，但任务可在等待登记前完成；这不是“`wait` 已经在等”的受控用例。现有子代理 Smoke 最后的“收到结果了”是端点脚本的回复，仅出现这句话也不能证明结果从 `wait` 取得或只交付一次。
- **核实**：`agent/jobs.md:50–53,99–108`，计划第 23、34–35、124、149–150 行；`packages/neuro-book/src/plugins/agent/subagents.test.ts:227–245,508–526`、`packages/neuro-book/e2e/agent-subagents.e2e.ts:176–190`；这是合同及夹具走查，未重跑这些用例。
- **建议**：替换旧验收 4：先用注入时钟跨过关闭句柄的空闲期限，再让任务完成，验证重开同一会话、结果进入实际模型请求、之后 `wait` 不再交回；另用可观察的等待登记屏障覆盖 `wait` 先到。把明确没写入的送达失败留给 `wait` 验收，分别断言来源、结果内容和次数，不依靠固定时序或预写的模型回复。

## 未发现问题的方面

- 仔细检查后没有发现既有 `wait` 的目标筛选与等待寿命有问题：只等 A 时 B 本身的终态不结束等待，等待超时或被用户中止也不停止目标，结果仍可取；不包括新送达产生的插话或重叠取件，见第 2、13 条。
- 仔细检查后没有发现显式 `async: true` 命令必须依附父运行的理由：既有真实命令用例确认父运行停止后任务仍在，正常停用 Agent 时后台命令写 `interrupted`；这不证明自动接手的边界或异常退出时一样能写状态。
- 仔细检查后没有发现自动接手需要重新执行命令或重新审批：按现有内核合同，参数、只读与审批在执行前判定，接手应只改变已启动命令的所有权；现有真实 shell 用例还确认保存全文失败不会再执行一次，未验证计划中的移交。
- 仔细检查后没有发现清单现有取消信号与最终结果分离有问题：远程 `cancel` 只发请求，任务按发起方真正结束的状态收口；发起方停用按实际持有者中断。需要补的是 Agent 镜像对任务和运行的绑定，见第 16–18 条。
- 仔细检查后没有发现切换窗口中的会话就应丢弃送达的理由：NeuroBook 按会话 id 区分结果归属，omp 的 `/new` 代次屏障值得用于阻止已关闭宿主的旧送达，但不应把切视图当作关闭原会话。

证据边界：固定基线 `22ae48c62`，Bun `1.4.4` 的三批定向合同测试分别为 8、7、1 项通过，均为 0 失败；探针所模拟的计划接线不算新增功能验收。未跑全量测试、类型检查、e2e、开发服务或真实模型。

## 对计划“不做与风险”的逐项判断

- **Monitor**：接受不做，任务结束送达和清单进度不承诺逐行输出订阅。
- **后台命令的 stdin**：接受不做，依赖交互输入的命令不因转到后台就能继续，仍需明确的超时或停止途径。
- **eval 单元自动转后台**：接受不做，嵌套调用的 `shell` 也不得借自动接手越过外层调用寿命。
- **任务表持久化**：接受不做，区分任务表与已经写下的会话输入、命令输出和终态文件，非正常退出时不把缺失的 `status.json` 报成已确认中断。
- **重启后补送通知**：接受不补送，不从日志或状态文件重新登记已清空的任务，已受理的缓冲输入仍按现有恢复规则处理。
- **子代理前台等待自动转后台**：接受不做，保留已有的前台超时与主动让出，不把子代理等待自己后台工作的策略偷换成新的前台转后台门槛。
- **用户不在时调用模型及费用**：这是已接受的代价，但 `maxCost=0` 不等于用户停止或循环保护可以被跳过，配置了费用上限时还要验收不发请求且结果仍可找回。
- **送达与用户输入的先后**：接受按内核受理与放行规则确定顺序，不承诺键入时刻排序，但不得改变结果归属、放行权限或取件次数。
- **父任务久挂**：若采用跨运行等待，只写可 `kill` 或可取消不足以收口，必须规定长期命令、已留着但不可唤起的结果、换轮空档及实际停止范围，见第 3、4、18 条。
- **`ShellBackground` 换形状**：不以仓内使用范围替代公开迁移承诺，先确定接手协议和默认期限，再决定兼容的扩展或明确的不兼容版本，见第 5、6、26 条。
