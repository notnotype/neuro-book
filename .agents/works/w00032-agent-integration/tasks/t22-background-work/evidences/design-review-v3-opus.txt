# t22 计划第 3 稿设计审查（Claude Opus）

## 1. 提醒受理后、取走前，`wait` 看不到它：子代理的同步提问会让父会话的 `wait` 空等到超时（最长 30 分钟）

- 严重程度：阻断；类别：正确性（死等）
- 位置：计划“`backend/jobs/center.ts`”的同步领取与结算（`delivered` 对提问记 `questionDelivered`；`wait` 不把 `claimed`、`unconfirmed` 当候选）；“提醒不是插话：`wait` 与前台等子代理的 `watchSteer` 不因它提前返回”；`center.ts:240-241`（`ready()` 跳过 `questionDelivered === question.id`）；内核取提醒只在对话请求的边界（runtime.md 输出 113）。
- 现象：父会话的模型正在生成一条回复（里面要调 `wait`），这期间子代理停在同步提问上。此时 `watched` 为 0，送达领取它、发出带唤起的提醒；会话在跑，不唤起，提醒只是待发。受理即 `delivered`，记下 `questionDelivered`。随后这条回复里的 `wait()` 开始执行：提问已记为交过，`ready()` 不再交回它；提醒要等下一个边界才取走，而下一个边界要等 `wait` 这个工具结算之后才到。子代理在等父 Agent 回答，父 Agent 的 `wait` 在等子代理，只能靠超时（缺省 1800 秒）、别的任务结束或用户插话解开。结果也一样：任务 A 在模型生成期间结束、提醒受理但还没取走，同一条回复里的 `wait()` 把 A 排除在外，于是去等 B（可能等很久），或者只有 A 时得 `no-jobs`，文字是“你启动的任务都已结束并取过结果”，可模型其实还没见过 A 的结果。
- 为什么是问题：计划把“受理”当成“模型已经看到”，但待发的提醒在工具执行期间不可能被取走。`wait` 的契约（jobs.md 输出 3：有已结束没取过的立即交回）对模型来说不再成立。在跑的会话里，任务在模型生成期间结束是常见时序，不是边角情况。
- 如何核实：读 `center.ts:229-275`（`wait` 的候选与 `ready()`）、runtime.md 输出 113（只在边界取）；`wait` 的并发是 `shared`，调用期间没有边界。
- 建议改法：不要把“受理”记成交过，只在提醒被取走时才算。`wait` 碰到这次领取发出、还在待发的提醒时，先 `removeNotice` 撤回：撤回成功就由 `wait` 交回（提醒没进过请求）；得 `notice-taken`，就说明它已经在上下文里，交回“已送进对话”。这样“已经（或可能已经）送进对话”这种含糊的说法也去掉了。见第 12 条：这个规则还能让 `watched` 整个去掉。

## 2. 指令 id 取“这批任务 id 的哈希”：同一件任务的第二次送达（第二个提问，或提问之后的结果）一定得 `command-id-conflict`

- 严重程度：阻断；类别：接口与合同（照字面实现必出）
- 位置：计划“`backend/jobs/delivery.ts`”第 3 步 `notice({commandId: "jobs:" + 这批任务 id 的哈希, …})`；“子代理有话问父 Agent”（“送达把它当一件送”）；`nb-harness/src/kernel/run/commands.ts:62-63,111-123`（`accept` 先按 `commandId` 查受理记录，参数哈希不同得 `command-id-conflict`）；`dispatch/core.ts:236-239`（受理记录从日志重建，不过期）。
- 现象：子代理任务 J 问了 Q1，送达发一条提醒，指令 id 是 `jobs:H([J])`；之后 J 又问 Q2（或者答完之后 J 结束、要送结果），这一批还是只有 J，指令 id 还是 `jobs:H([J])`，正文不同，内核交回 `command-id-conflict`，什么都不写。计划的结算只分了“成功”“确定没写”“结果未知”三类，冲突码不在前两类；按“抛错、未知”处理，就成了“送达未确认”，下次打开用同一个 id 重发，还是冲突，这件任务就永远停在“送达未确认”：自动送不出去，点名 `wait` 又被告知“可能已经送进对话”。凡是问过一次的子代理，结果都送不回来。
- 为什么是问题：会话的受理记录从日志重建、不过期（`core.commands`），指令 id 在会话里必须终身唯一；任务 id 不能代表“这一次送达”。
- 如何核实：读 `accept` 与 `replay`；在内核合同测试里用同一个 `commandId`、不同的 `text` 发两次 `notice`，第二次得 `command-id-conflict`。
- 建议改法：每次领取生成一个新 id（例如 `jobs:<领取序号或 UUID>`），记在领取记录上，重发时照用；提问的送达把提问 id 带进去。`command-id-conflict` 单列一类，按程序错误写诊断，交还给 `wait`，不进“送达未确认”。

## 3. “送达未确认”的重发要求参数逐字节相同，计划没有写把第一次的正文存下来；按驱动重读会重建出不同的文字

- 严重程度：重要；类别：依赖的机制（重放的前提）
- 位置：计划“一次送达”第 4 步（“会话下次被打开时用同一个指令 id 重发一次：内核按指令 id 交回第一次的结果”）；`commands.ts:111-123`（`argsHash` 是去掉 `commandId` 之后整个参数的哈希，包括 `text`、`key`、`wake`）；`subagents/children.ts:109-130`（`#result` 每次都现读 `asyncQuestionsOf(view)` 与 `view.runResult({runId})`）。
- 现象：受理过的那次重发能命中重放，前提是 `text` 与第一次完全相同。子代理的段落每次都现读：子会话里异步提问的增减、同一 `runId` 回退之后接着跑、读失败落到“子会话读不了（…）”的那句（错误消息会变），都会让第二次的文字和第一次不同；命令的段落如果第一次读 `status.json` 失败、第二次成功，也不同。参数不同就得 `command-id-conflict`（见第 2 条），而不是“受理过的照原样交回”，这正是“结果未知”最要靠重放兜底的时候。
- 为什么是问题：“绝不交两次”完全靠重放；重放的前提计划没写成不变量，测试只要写“同一个指令 id 重发”，用的却是新拼的文字，测试也测不出（测试里两次读的结果正好相同）。
- 如何核实：读 `argsHashOf` 与 `ChildRuns.#result`；在真实内核上用同一 `commandId`、正文差一个字重发，得 `command-id-conflict`。
- 建议改法：在“送达未确认”的记录里冻结整份参数（`text`、`key`、`wake` 与指令 id，至多 30 KiB，进程内存里放得下），重发时原样使用，不再调驱动；计划与 `jobs.md` 写成不变量，验收里断言重发的参数与第一次逐字节相同。

## 4. `watched` 归零时不会触发领取：`wait` 返回之后，期间已结束的任务永远等不到自动送达

- 严重程度：重要；类别：正确性（送不出去）
- 位置：计划“`watched`”（“每次 `wait` 开始时加一、返回时减一”）与“`JobDelivery` 跟着 `center.onChanged(owner)`”；`center.ts:243-249,323-330`（`wait` 交回时只对交回的那一件发 `#ownerChanged`，超时、插话、中止都不发任何变化）。
- 现象：送达只在 `onChanged(owner)` 时领取。`wait()` 看着 A、B：A 结束时 `watched(A)` 为 1，领取跳过它；`wait` 接着交回 A，或者在 A 结束的同一刻以超时、插话收口——B 若在这期间结束，`end(B)` 发的那次变化同样因 `watched(B)` 为 1 被跳过。`wait` 返回、`watched` 减到 0，没有新的变化事件，B 就留在“已结束、没取过、没人领”的状态，直到这个会话的任务表下次有别的变化。而 `wait` 交回的“其余任务”里还写着 B“完成”，模型按 `shell` 与 `wait` 的新说明（“结束时结果会自动送来”）不会去取它。
- 为什么是问题：违反“任务结束后结果会送回会话”的承诺；第二轮审查第 19 条最后一句（“任务在等时限或插话已经选定后、观察者释放前结束，只在任务结算时检查又会漏调度”）原样没有处理。
- 如何核实：读 `wait` 的 `finally` 与 `deliver`；按计划的接口推一遍上面的时序即可，不依赖实现细节。
- 建议改法：`watched` 减到 0 时，如果这件任务能被领取，就发一次 `onChanged(owner)`；验收补“`wait` 超时的同一刻另一件结束”“`wait` 交回 A 时 B 已经结束”两条。更简单的做法见第 12 条：去掉 `watched`。

## 5. 两个并发的 `wait` 现在就会交回同一件任务两次，计划的“同步领取”只挡住了送达，没有挡住 `wait` 与 `wait` 之间

- 严重程度：重要；类别：不变量（只交一次）
- 位置：计划“同步领取”只写了 `claim(owner)` 给送达用；`center.ts:242-249,256-268`（`check` 在通知时选中任务，`deliver` 在之后的微任务里执行，不复查 `fetched`）。
- 现象：同一条回复里两个 `wait()`（`wait` 的并发是 `shared`）都在等 A。A 结束时两个监听都 `resolve({ready: A})`，随后两个 `deliver(A)` 都执行，都交回 A 的结果。探针（`/tmp/review-t22-design/opus/probe-two-waits.ts`，直接用 `JobCenter`，两个 `wait` 加一次 `end`，时序与两个并发的工具调用相同）输出 `ready ready job-id1… job-id1…`。
- 为什么是问题：提案第四节第 3 小节第 3 条要求“一件任务的结果只有一个出口——`wait`、前台调用或一条提示——在任务中心里同步领取”，`wait` 也是要领取的出口；第二轮审查第 19 条点过这个问题，计划的“`watched`”只防送达，不防两个 `wait`。验收映射里“读结果期间点名 `wait` 同一个只交回一次”测的是另一种时序。
- 如何核实：`bun /tmp/review-t22-design/opus/probe-two-waits.ts`（在 `packages/neuro-book` 下运行）。探针绕过了内核，结论只依赖 `JobCenter` 的同步语义；严重程度按“base 上就有、计划声称要修的不变量没覆盖”定。
- 建议改法：`wait` 交回走同一个领取：`deliver` 在同一个同步段里检查并标“已被 `wait` 取”，没抢到的 `wait` 重新挑（还有别的候选就接着等）。验收加“两个并发的 `wait` 等同一件，只有一个交回结果”。

## 6. “确定没写就只留给 `wait`、不再自动送”把暂时的失败变成永久的静默：模型已被告知“不用 `wait`”

- 严重程度：重要；类别：失败路径
- 位置：计划“结算”（`returned` 标 `deliveryFailed`，之后只留给 `wait`）与第 4 步的分类（会话打不开、只读、`notice-budget`、`session-closed`）；自动转后台交回的文字“结束时结果会自动送来，不用 wait 轮询”，`shell`、`wait` 的说明“改成结果会自动送来”；`commands.ts:431-453`（每会话待发至多 64 条、编码后合计至多 128 KiB）；`agent/sessions.md` 输出 24 的打开码含 `session-busy`、`storage-failed`。
- 现象：
  - `notice-budget` 在两种常见情形下会出现：根会话的门关着（用户停过之后离开），提醒只进缓冲区、不唤起，会一直积着；子会话的提醒从不唤起，子代理的运行结束之后它自己起的后台命令再结束，提醒也一直积着。每条至多 30 KiB，大约四五件大结果就到 128 KiB。之后每件都得 `notice-budget`，按计划永久转给 `wait`。用户回来说一句话，模型看到前几件的结果，对其余几件一无所知：没有任何提醒告诉它还有结果要 `wait` 去取，它又被明确告知不用轮询。
  - `session-busy`、`storage-failed`、`open-failed` 这类打开失败多是暂时的，同样被当成永久。
  - 一次领取里“放不下的下一条再送”，下一条若得 `notice-budget`，就有一部分结果送了、另一部分永久留给 `wait`，模型同样不知道。
- 为什么是问题：`notice-budget` 在 runtime.md 的失败表里写的是“自己留着内容（例如交给 `wait`），或撤回过时的”，前提是调用方知道要去 `wait`；这里调用方是模型，它不知道。第二轮审查第 20 条也问过保留与淘汰（`deliveryFailed` 的任务照样会被每会话 32 件的 `#trim` 丢掉）。
- 如何核实：读 `noticeCommand` 的上限判断与 `center.ts:336-342` 的 `#trim`；按计划写一个门关着、5 件 12 KiB 结果先后结束的场景推一遍即可。
- 建议改法：`notice-budget` 与暂时的打开失败不算“确定送不了”，任务回到“可领取”，在这个会话下一次 `noticeTaken`（预算腾出来了）或下一次打开时再领取；只有只读、会话已删这类永久的情况才转给 `wait`。同时保证“至少告诉模型一次”：放不下全文时发一条很短的提醒（“还有 N 件后台任务的结果没放下：job-a、job-b，用 wait 取”），它几乎总能放下。

## 7. 每段“留开头 12 KiB 并写全文地址”与现有的结果文字对不上：命令丢掉结尾（出错的地方），12–50 KiB 的子代理报告没有全文地址

- 严重程度：重要；类别：接口与合同
- 位置：计划“一次送达”第 2 步；`builtin/shell-background.ts:170-188`（`commandResult` 是状态行、输出的开头加结尾各 20 KiB，最后一行才是“全文：<地址>”与“读写输出时出错”）；`subagents/result.ts:160-186`（`clip` 只在超过 50 KiB 或 2,000 行时才存 `artifacts/`，交回开头 20 KiB、省略标记、结尾 20 KiB）；`children.ts:58`（`report()` 交回的已经是 `clip` 过的文字，地址嵌在中间的省略标记里，调用方拿不到）。
- 现象：
  - 命令：在 `commandResult` 上留前 12 KiB，留下的是状态行和输出开头，丢掉的是输出结尾（报错、测试汇总一般在结尾）与“读写输出时出错”那行。比 `wait` 交回的少，模型又被告知不用 `wait`（任务送达之后也从表里移出，`wait` 取不回来了）。
  - 子代理：报告在 12–50 KiB 之间时 `clip` 不存全文，计划说的“存进 `artifacts/` 的全文”并不存在；超过 50 KiB 时 `clip` 存过一次，但地址在第 20 KiB 附近的省略标记里，留前 12 KiB 正好把它切掉，送达要么解析文字取地址，要么再存一份。
  - 子代理的结论一般在最后一条回复里，`run.text` 整段就是它，留开头没问题；结构化结果的 JSON 被从中间切开也没有标记。
- 为什么是问题：第二轮审查第 26 条（“只截现有 `wait` 文本会连它原来放在末尾的地址都一起截掉”“13,000 字符的短行不建产物”）在计划里没有落实，计划列它为输入。
- 如何核实：读上面三处；拿一个 20 KiB 的子代理回复与一个以错误结尾的 1 MiB 命令输出，按计划的规则手算送达正文。
- 建议改法：驱动交出“有界的送达段落”而不是让送达去截 `wait` 的文字：`JobDriver` 加 `notice(limit)`（或 `result()` 交回 `{head, body, reference}`），状态行与全文地址是不可截的部分，正文由驱动按自己的语义截（命令取开头加结尾，子代理取开头，超出的由驱动存全文、交回地址）。插件登记的任务在 `end` 时已经给了至多 12 KiB 的文字，同一个接口自然成立。

## 8. 提案第 3 小节第 8 条“结果在收口时定下，`wait` 与提示用同一份”没有落实：子代理的段落在读的那一刻才去取最近一次收口

- 严重程度：重要；类别：与已定设计一致
- 位置：计划只为第 8 条做了 `abort{runId}`（“`kill` 带 `runId`”）；`children.ts:109-125`（`#result` 现读 `view.runResult({runId})` 与 `asyncQuestionsOf`）；第二轮审查第 18 条（同一 `runId` 回退之后接着跑，再收口一次）。
- 现象：子代理任务 J 以“出错”收口，`JobOutcome` 记 `failed`；送达在读结果之前（读文件、排队、上一条提醒还在送），用户在子会话里回退并接着跑同一个 `runId`，这次正常完成。送达读到的是新的 `runResult`，拼出来的是“状态：出错”加上新分支的成功正文。现在加了自动送达，“结束到读取”之间多了一段排队与组包的时间，窗口比 `wait` 还宽。
- 为什么是问题：这是提案明文接受的规则（第 8 条后半句），计划的“开发者已定的取舍”里没有改它；第二轮审查第 18 条把它归给 t22，计划没有提。
- 如何核实：对照提案第 3 小节第 8 条、计划“`abort` 的 `runId`”一节与 `children.ts:#follow`、`#result`。
- 建议改法：`#follow` 在 `waitRun(runId)` 返回时就拿到那次的 `RunResult`（`waitRun` 交回的就是它），存在任务上（或直接拼好有界的段落，见第 7 条），`wait` 与送达都用它，不再现读。子会话的异步提问照旧现读，但要写明它属于“当前状态”，不在冻结的结果里。

## 9. 用户取消了待发的结果或提问提醒，计划没有处理：结果从此谁都拿不到，提问让子代理一直等

- 严重程度：重要；类别：遗漏（失败路径）
- 位置：计划的结算只有 `delivered`、`returned`、`unconfirmed`；runtime.md 输出 112（“用户能取消任何一条”，`noticeRemoved{reason: "cancelled"}`）；第二轮审查第 20 条（“写入缓冲区、进入路径、被用户取消是三个不同的结局”），计划列为输入。
- 现象：
  - 结果提醒：受理即 `delivered`，任务移出任务表。门关着时用户在排队区把“提醒 · 后台任务”取消，模型从没见过这件结果，`wait` 得 `job-unknown`，只剩输出文件或子会话日志。
  - 提问提醒：用户取消之后，`questionDelivered` 仍等于这个提问，`wait` 不再交回它；父 Agent 永远不知道有这个提问，子代理停在提问上，直到用户自己去子会话里答。
- 为什么是问题：用户取消一条提醒的本意多半是“别打扰我”，不是“把这件任务丢掉”；即便接受“取消就是丢弃”，也要写成合同，`jobs.md` 不能再说“结果已经送进对话”。
- 如何核实：读 runtime.md 输出 112 的 `removeNotice` 与计划“结算”一节，两者没有交集。
- 建议改法：送达订阅本会话的 `noticeRemoved`：自己发的提醒被用户取消（`reason: "cancelled"`）时，提问回到“没交过”（清 `questionDelivered`，`wait` 能再交回）；结果二选一写进 Spec——回到 `deliveryFailed`、只留给 `wait`（推荐：任务还在表里，卡片照样能看），或者明确算丢弃。这条与第 1 条的“受理不等于交过”是同一个改法：把交过的时刻推迟到 `noticeTaken`。

## 10. 被 `kill`、`killJob` 停掉的任务也会作为结果送达并唤起根会话：用户在界面上停掉一件任务，空闲的 Agent 被叫起来调一次模型

- 严重程度：重要；类别：正确性（意外的模型调用）
- 位置：计划“同步领取”的条件（已结束、没取过、没有前台、没有 `wait`），不区分怎样结束；“根会话带唤起”；jobs.md 输出 4、11；`center.ts:220-227`。
- 现象：
  - 用户经远程 `killJob` 停一个后台子代理或命令，此时根会话空闲、门开着。任务以 `aborted` 收口，送达领取它，发带唤起的提醒，开一次运行，模型读到“任务 X 已停止”，很可能再把它启动一次。用户的意思是停，不是让 Agent 接着做。
  - Agent 自己 `kill` 时，`kill` 已经交回“已停止”，送达再发一条同样内容的提醒，是一次重复（不唤起，因为会话在跑，但多占一次请求与预算）。
- 为什么是问题：门只在“用户停止整次运行”时关，用户停一件任务不关门；计划的“风险”里只考虑了“用户不在时调模型”的费用，没有考虑“用户刚刚停了它”。
- 如何核实：读 `JobCenter.kill`、`ChildRuns.start` 里的驱动 `kill`，与计划的领取条件对照。
- 建议改法：`kill`（Agent 自己）交回“已停止”时把任务视同取过（同前台以中止交回的做法，`settleEarly`）；`killJob`（用户）停掉的照样送达、写明“用户停了它”，但不带唤起，随下一次请求带上。写进 `jobs.md` 的送达规则与验收。

## 11. 自动转后台在移交时同步拷贝至多 64 MiB，违反已接受的提案第 3 小节第 9 条“交接时不同步拷贝大文件”

- 严重程度：重要；类别：与已定设计一致
- 位置：计划“`shell` 自动转后台”（“`OutputCapture` 加 `copyTo(fd)`：……溢出后同步拷暂存文件（至多 64 MiB）”）与“风险”（“会让服务端在这一刻停顿（估计几十毫秒）”）；提案第四节第 3 小节第 9 条（“命令只起一次，从一开始就是一份连续的输出记录，交接时不同步拷贝大文件”）；第二轮审查第 29 条；`kit/tools/output-capture.ts:30-73`（暂存文件在 `os.tmpdir()` 下，溢出时先写入当时的全部内存，之后逐块追加，所以它就是从头开始的完整记录）。
- 现象：计划沿用第 2 稿的设计，把提案明文排除的做法写成了“风险”，没有列进“开发者已定的取舍”。64 MiB 同步拷贝在本机 SSD 上是几十毫秒，在慢盘、跨文件系统（`/tmp` 与状态根不在同一个文件系统）或磁盘忙时是秒级，整个服务端（所有会话的内核、远程推送）这段时间都停着；“几十毫秒”只是估计，“未验证边界”里也只在本机测一次。
- 为什么是问题：已接受的规则被悄悄改了；而提案给出的方向（一份连续的记录）在现有代码上并不难做。
- 如何核实：对照提案第 9 条与计划原文；`OutputCapture.#spoolWrite` 的写法说明暂存文件已经是完整记录。
- 建议改法：让暂存文件本身成为后台任务的输出记录，移交时不拷贝：`ShellAutoBackground` 在命令开始时给出暂存位置（会话工作区下的一个临时目录，与 `jobs/<任务 id>/` 在同一个文件系统），移交时同步 `rename` 成 `jobs/<任务 id>/output.log` 并接着用同一个 fd 追加；没溢出时只写内存里那至多 50 KiB。拷贝不可避免时（宿主给不出同一文件系统的位置）才退回现在的做法，并写进 Spec。若坚持现在的做法，应作为第 5 处取舍交开发者定，而不是写成风险。

## 12. 领取的状态太多：`waiters`、`watched`、`fetched`、`claimed`、`unconfirmed`、`deliveryFailed`、`questionDelivered` 七个字段管一件事；改成“谁取走了它”一个字段，`watched` 可以去掉

- 严重程度：建议；类别：可简化
- 位置：计划“`backend/jobs/center.ts`”的同步领取、结算与 `watched`；`center.ts:55-63`。
- 现象：计划在现有的 `waiters`、`fetched`、`questionDelivered` 上又加了 `delivery: "claimed"`、`unconfirmed`（带指令 id）、`deliveryFailed` 与 `watched`。第 1、4、5、9 条的问题都出在这些字段之间的组合上：`watched` 归零不触发领取，`wait` 与 `wait` 之间没有领取，受理与取走被混成“交过”。
- 为什么能更简单：`watched` 的用处是“`wait` 正看着的，送达别抢”。若按第 1 条的规则让 `wait` 能撤回自己会话里还在待发的结果提醒，送达抢先也无害：`wait` 在跑时会话一定在跑，提醒不会唤起，`wait` 交回之前撤回它就行（工具执行期间没有边界，撤回不会遇到 `notice-taken`）。于是不需要 `watched`，也不需要“点名等已领取的得‘可能已送’”这条特殊路径。
- 建议改法：任务上只留一个“出口”字段：`null`（没人取）、`wait`、`foreground`（即 `waiters > 0`）、`{notice: {commandId, args, noticeId?, state: "sending" | "pending" | "unconfirmed"}}`、`failed`（只留给 `wait`）；`wait`、前台、送达都在同一个同步段里检查并写它。`wait` 遇到 `sending` 等这次发送结算，遇到 `pending` 就撤回再交回，遇到 `unconfirmed` 才说“可能已经送进对话”。提问另用同样形状的一个字段，按提问 id 记。

## 13. eval 的“意外退出”现在不是当场知道的；发提醒与“新内核起来时撤回”之间没有定序，旧一代的提醒可能在新内核起来之后才受理

- 严重程度：重要；类别：依赖的机制
- 位置：计划“eval：`backend/eval/tool.ts`”（“空闲”“被回收”“意外退出（两次调用之间发现）”当场发；“每一代内核只发一次；新内核起来、能用之后……还没取走的撤回”）；`eval/tool.ts:216-218`（两次调用之间的退出只在下一次调用开头发现）、`tool.ts:376-380`（空闲计时到点时内核已死才记“意外退出”，最长晚 30 分钟）；`eval/kernels.ts:89-97`（`Kernel.exited` 带 `intentional`，现在没人在单元之外监听它）；第二轮审查第 28 条。
- 现象：
  - 现有代码里，两次调用之间内核被杀，要么下一次 eval 开头发现（这是“调用时才发现”，按决定 9 只写在结果里），要么 30 分钟后空闲计时到点发现。计划写的“两次调用之间发现”照字面实现就是这两处之一，都不是“当场”。要当场，得在 `SessionKernel` 上监听 `kernel.exited`（`intentional` 为假、当时没有在执行的单元）；这时空闲计时到点又会以“意外退出”走一次 `#reset`，要防同一代发两次。
  - `notify` 要经会话表开会话、进单写者队列，是异步的。旧内核 K1 退休、提醒还在路上时，下一次 eval 起了 K2、执行 `withdraw()`，这时没有可撤的；随后 K1 的提醒才受理，K2 已经能用了，提醒却说“之前的变量没了”。`key: "eval-kernel"` 只管替换，不管先后。
- 为什么是问题：提案第 10 条要求“新内核已经能用之后不再排进去”；第二轮审查第 28 条正是这个时序，计划没有给出定序。
- 如何核实：读 `SessionKernel.#execute`、`#scheduleIdle`、`Kernel` 构造里的 `exited`。
- 建议改法：`SessionKernel` 记“这一代的提醒”：`{generation, sending: Promise | null, noticeId | null}`。`withdraw()` 先等 `sending` 结算再撤；`notify` 受理回来时若已经有了新一代，立即撤回自己。意外退出用 `kernel.exited.then(exit => !exit.intentional && 不在单元里 && 这一代还没发过)` 触发；`#reset` 与空闲计时按同一个 `generation` 判重。验收加“K1 的提醒写入被卡住时 K2 起来”“空闲期间杀掉内核进程，当场有提醒、到点不再发第二条”。

## 14. eval 的空闲回收提醒会重开已关闭的会话、写进日志，并把它顶到会话列表最前面

- 严重程度：建议；类别：遗漏（可观察的副作用）
- 位置：计划“eval”（`notify` 由 `evalTool` 用会话表实现）；`kit/sessions/table.ts:329-361`（视图上的任何调用都会按需打开会话）；`kernel/log/index-file.ts:41`（每条事件都把 `lastActivityAt` 推到这一刻）与 `jsonl-store.ts:341`（列表按 `lastActivityAt` 倒序）；`eval/kernels.ts:296-305`（全服务端至多 8 个内核，第 9 个起来时回收最久没用的）。
- 现象：用户最后一次 eval 之后 30 分钟，或者在别的会话里起了第 9 个内核，这个会话被从磁盘重新打开（装配 Profile 与扩展），写下 `noticeQueued` 与 `commandAccepted`，30 秒后再关；会话列表里它的“最近活动”变成此刻，排到最前面，用户没有碰过它。另外，路径上从没跑过 eval 的情况（例如回退到第一次 eval 之前之后才回收）也会发“之前的变量没了”，而结果第一行那句有 `ranOnPath` 判断，提醒没有。
- 为什么是问题：会话列表的顺序是用户看得到的行为；为一条不唤起、多半等很久才被取走的提醒去开会话、改排序，代价与收益不对等。
- 如何核实：读 `advanceIndex` 与 `SessionTable.#acquire`。
- 建议改法：二选一写进 Spec：会话没开着时不发（下次 eval 的结果第一行照样会写，开发者要的“说两遍”在会话开着时成立），或者接受并写明排序会变。无论哪种，发之前按 `ranOnPath` 的同一条件判断。

## 15. 子代理卡片改读整份 `runResult`，超过一页就得 `result-too-large`，卡片没有终态

- 严重程度：重要；类别：接口与合同
- 位置：计划“前端”（“按自己的子会话 id 与 `runId` 经远程读那次运行的 `runResult` 取终态与首句”）；`backend/remote.ts:154-158`（`runResult` 不分页，编码后超过一页明确失败 `result-too-large`）；第二轮审查第 25 条，计划列为输入。
- 现象：子代理最后一条回复很长（长篇写作场景里一章就是几十 KiB，结构化结果也可能很大），超过一页时远程交回 `result-too-large`。送达之后任务已从表里移出，`wait` 的 `details` 也没有，卡片既拿不到终态也拿不到首句，计划没有写这种情况怎么显示。
- 为什么是问题：卡片只要终态与一句话，却去取整份正文；失败通道没有定义，照字面实现会把失败当成“还没收口”。
- 如何核实：读 `remote.ts` 的 `whole` 与 `agent/sessions.test.ts` 里覆盖 `result-too-large` 的用例（第二轮审查第 25 条已核实）。
- 建议改法：给远程加一个有界的查询（例如 `runOutcome({sessionId, runId})`，交回 `{reason, line, error?}`，大小固定有界），卡片只读它；读失败时显示明确的“读不到结果”，不显示成在跑。或者在送达时把终态与首句写进父会话这条提醒对应的展示数据里（但提醒的 `details` 目前没有这个字段，要改内核，不推荐）。

## 16. “送达未确认”的重发只写了理想路径：重发再次未知、重发时打不开、送达自己触发的打开，都没有定义；`onOpened` 也可以不加

- 严重程度：建议；类别：遗漏（失败路径）与可简化
- 位置：计划“`kit/sessions/table.ts`”（`onOpened`）与“一次送达”第 4 步（“下次被打开时……重发一次”）；`commands.ts:60-74`（坏句柄上 `accept` 先查受理记录、再因 `core.broken` 交回 `log-broken`）；`table.ts:409-418,440-450`（`broken` 也算空闲，没有引用时 30 秒后关闭）；`table.ts:329-361`（视图上的调用会按需打开会话）；host-kit.md 的“不承诺”（句柄表的行为写在 `agent/sessions.md`，不在 host-kit.md）。
- 现象：
  - 重发也得 `log-broken`（重开后又写坏）或抛错：计划只说“重发一次”，之后是再等下一次打开、还是放弃，没写。
  - 重发时打不开（`log-corrupt`、`open-failed`）：第一次的“会话打不开”被算作“确定没写”，但重发时打不开并不能说明第一次没写进去，不能照第一次的分类退回给 `wait`。
  - 送达自己发别的提醒时会把已关闭的会话打开，`onOpened` 在送达的串行队列里回调，重发若直接在回调里执行就会重入。
  - 用户一直不回来时会话就不会再开，任务一直停在“未确认”；风险里写了，但其实不必等用户：句柄因损坏、空闲关闭之后，送达自己再调一次视图就会重开它。
  - `onOpened` 写进 host-kit.md 与该 Spec 的“不承诺”冲突，应写进 `agent/sessions.md`。
- 如何核实：读上面几处。
- 建议改法：不加 `onOpened`：送达在句柄关闭之后（会话表已有 `closed(sessionId)` 回调，可改成可订阅）把这件任务的重发排进它的串行队列；重发得到受理或明确的校验失败就结算，再次未知就保持“未确认”、等下一次关闭，打不开也保持“未确认”。把这几条写进 `jobs.md` 的失败表。

## 17. 自动转后台的 `prepare` 要建 `jobs/<任务 id>/`，但任务 id 在之后同步的 `take` 里才登记

- 严重程度：建议；类别：接口与合同（照字面实现会返工）
- 位置：计划 `ShellAutoBackground.prepare`（“建好输出位置”）与 `BackgroundTarget.take`（“同步：登记任务……失败时抛错（到上限……）”）；`builtin/shell-background.ts:47-61`（目录名就是任务 id）；`backend/remote.ts:207,216`（`jobTail`、`jobStatuses` 按任务 id 拼目录读）；`center.ts:118-125`（任务 id 由 `reserve` 生成）。
- 现象：输出目录必须叫 `jobs/<任务 id>/`，远程才读得到；`prepare` 建目录时还没有任务 id。照字面实现只能二选一：`prepare` 里先 `reserve`（占名额、出现 `starting` 的任务，“到上限”就成了 `prepare` 交回 null，而不是 `take` 抛错；`discard` 还要 `release`），或者 `take` 里登记之后再 `rename` 目录。计划的接口注释两种都不是。
- 建议改法：写明 `prepare` 先 `reserve` 再建目录，`discard` 负责 `release`；`take` 只做 `start` 与换出口，不会因上限失败。配合第 11 条，`prepare` 正好也是把暂存记录放进这个目录的时机。

## 18. 工具登记的任务：撤回时只“按 `interrupted` 收口”，不停插件的工作；没注册 `onKill` 时 `kill` 什么都不做却报“已停止”

- 严重程度：建议；类别：与已定设计一致、失败路径
- 位置：计划“工具里登记任务”（“插件的 `agent.tools` 贡献撤回时：封住这一代……它登记的在跑任务按 `interrupted` 收口”，`onKill(handler)`）；提案第 3 小节第 7 条（“撤回时封住这一代、退还没开始的名额、停掉在跑的”）；第二轮审查第 23 条（“封任务句柄不代表外部工作已中断”）；`backend/tools.ts:260-320`（撤回等进行中的调用至多 5 秒）；`center.ts:220-227`（`kill` 调完驱动就交回 `killed`）。
- 现象：
  - 撤回时计划只改任务表里的状态，没有调插件的 `onKill`；插件的 Workflow 运行可能还在跑、还在写文件，模型与用户看到的却是“已中断”。
  - 插件没调 `onKill` 就开始了任务，`kill`、`killJob` 照样交回“已停止”，任务继续 `running`。
- 建议改法：撤回时先封住这一代，再对它的每件在跑任务调 `onKill(false)`，给一个上限（同撤回的 5 秒），到时还没 `end` 就按 `interrupted` 收口，并写诊断说明插件没有确认停下。`begin` 要求在同一次调用里给出停止的办法（把 `onKill` 改成 `begin` 的必填参数），免得出现停不了的任务；或者没有处理函数时 `kill` 交回“这个任务不能停”。

## 19. `abort{runId}` 得 `aborted: false` 时，`kill` 仍交回“已停止”

- 严重程度：建议；类别：接口与合同
- 位置：计划“`abort` 的 `runId`”；`center.ts:220-227`（`kill` 调完 `driver.kill` 就交回 `killed`）；`children.ts:49-53`（驱动的 `kill` 只在 `!aborted.ok` 时写诊断，不看 `value.aborted`）。
- 现象：带上 `runId` 之后，“那次运行已经收口、任务的终态还没报回”这段时间里 `kill` 会得 `{aborted: false}`，这正是加 `runId` 要防的情形。驱动不看 `aborted`，任务中心交回“已停止”，随后 `#follow` 以 `completed` 收口，模型被告知停了的任务其实完成了，结果再作为提醒送来（或者按第 10 条的改法被当成取过而丢掉）。
- 建议改法：`JobDriver.kill` 交回是否真的停了；`aborted: false` 时任务中心等这件任务报回终态，交回“已经结束”，不视同取过。`jobs.md` 输出 4 的“已经结束的交回‘已经结束’”照这个时序写清。验收里“旧任务的 `kill` 不停新一轮”之外，再断言它交回“已经结束”。

## 20. 提问提醒的撤回与还在路上的发送没有定序：提问刚被答完，旧提醒才受理并唤起父会话

- 严重程度：建议；类别：并发
- 位置：计划“子代理有话问父 Agent”（“提醒取走之前提问被答了……`removeNotice` 撤回”）；第二轮审查第 22 条；`children.ts:69-77`（提问的清除来自子会话的帧，异步到达）。
- 现象：送达领取了提问 Q、正在读结果或等单写者受理；这时用户在子会话里答了 Q，`#follow` 看到 `interactionResolved`，送达要撤回，可提醒还没受理、没有 `noticeId`，撤回落空；随后提醒受理，根会话空闲、门开着，于是为一个已经答完的提问开一次运行，模型调 `agent_answer` 得错误。与第 13 条 eval 的时序是同一类问题。
- 建议改法：撤回与发送走同一条串行队列：撤回请求先等这件提问的发送结算，拿到 `noticeId` 再撤；发送结算时若提问已不在（`job.question?.id !== Q`）就立即撤回自己。验收加“提问提醒受理被卡住时用户答了提问：父会话不被唤起，日志里提醒是 `withdrawn`”。

## 21. 验收映射缺几条关键时序，现有几条照写也测不出上面的问题

- 严重程度：建议；类别：验收映射
- 位置：计划“验收映射”。
- 现象与建议：
  - “送达未确认”只写了“模拟写日志失败”一种。第二轮审查第 4 条要两处注入：整批写完之后报错（实际已受理，重发要交回原结果、不再写）与写出不完整的批（实际没受理，重发要写下）。两处的断言不同，只测一处测不出第 3 条（重发参数必须相同）。
  - 没有“提醒待发期间同一条回复里的 `wait`”这条（第 1 条），也没有“`wait` 超时的同一刻另一件结束”（第 4 条）、“两个并发的 `wait`”（第 5 条）、“问过一次的子代理的结果送达”（第 2 条）、“门关着时 5 件大结果先后结束”（第 6 条）。这几条都能用真实内核加注入时钟写出来。
  - eval 的映射只有空闲回收与“执行中崩溃不另发”，第 3 片的验证里写了“杀掉内核进程”，映射里却没有“空闲期间内核被杀，当场有提醒、到点不再发第二条”。
  - “几件同时结束合成一条”：计划没有合并窗口，只有同一个同步段里结束的、或前一条还在送时积下的才会合并，测试要按这个语义写，否则会靠时序碰巧通过。

## 未发现问题的方面

- `abort{runId}` 的内核语义：与现有 `abortCommand` 的“权限判定、读范围、触发信号在同一个同步步骤里”相容，`runId` 的比较放在 `recordStop` 之前同一步即可；不动缓冲区、不关门与输出 117 的关门条件不冲突（`aborted: false` 不进收口批）。
- 提醒的发出者与 `key`：内核按 `source.plugin` 判同一发出者（`permissions.ts:12-16`），后台任务与 eval 都是 `nbook.agent`，但 `eval-kernel` 与 `question:<jobId>` 不会撞，替换与撤回不会串到对方；`label` 不同只影响来源行。
- 取舍 1（提醒不另过拦截）：提醒在请求里是一段文字，`intercept.model` 拦得到；与 runtime.md 输出 118“`noticeQueued.text` 是内容字段、日志与帧经出站过滤”一致。
- 前台续用的“先 `attach` 再发布”：`subagents/tools.ts` 现在已经在任务可见之前 `attach`（第 329、424-425 行），领取只取已结束的任务，`start` 与 `attach` 之间没有让任务结束的异步点。
- 停止时 `delivery.close()` 作为第一步：与决定 14（已发出的那次按日志结算）一致。
- “在跑的工作只报一项”：子代理任务在跑时子会话一定在 `activityWithBackground` 里（在跑或在等），按根归并已经覆盖它。
