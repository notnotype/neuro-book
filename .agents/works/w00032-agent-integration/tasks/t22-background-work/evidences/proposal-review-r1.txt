# 「统一后台任务」提案只读设计审查（w00032 t22）

### 1. 停止保护绑在叶子上，回退后另一条提示能重开刚停的会话

- **严重程度**：阻断；**类别**：正确性。**位置**：提案第四节第 1 小节的「提示一直是就绪的」「唤起」（第 58、62 行）。
- **现象与影响**：R1 正常结束；用户停止 R2，任务 A 结束、提示留在会话里；用户只回退到 R1 的结束点，不发新话；任务 B 完成。照提案，B 读到当前叶子的 `completed` 便唤起，第一次请求把 A、B 一起带走。回退到尚无运行的节点也一样。单写者消除了读状态与停止受理的竞态，没消除唤起资格与提示不同作用域的问题。上一稿第 23 条靠用户才可放行的留置状态挡住旧结果；本稿取消放行后，旧提示重新能被宿主唤起带走，和「随用户下一句话进去」冲突。
- **核实**：合同与源码走读：`harness/runtime.md` 输出 35–36（回退不改缓冲区），`kernel/state/kernel-state.ts:27–33`（`lastChat` 随叶子）；再按提案第 58、62 行逐步推演。新版提示尚未实现。
- **建议**：将禁止自动唤起的事实记在会话级，不由回退、换分支或纯压缩解除；与当前叶子可开新运行的检查同时满足才允许自动唤起。明确哪些用户动作重开这道门。用真实内核验收「停止→到件→只回退或切分支→再到件」不发模型请求，用户下一次对话请求才取走两条。

### 2. `inputConsumed` 证明移出缓冲区，不证明进入下一次模型请求

- **严重程度**：阻断；**类别**：不变量。**位置**：提案第四节第 1、6 小节（第 53、59、106 行）。
- **现象与影响**：照稿与取插话同批先写 `inputConsumed` 和路径 `notice`，后面仍可能无模型、压缩切掉放在最后一步后的提示、Profile 算请求失败或隐藏 `notice`、费用守卫不调模型。尤其是压缩切掉当前轮的旧步骤时，提示已离开缓冲区，却连第一次对话请求都没经过；后台结果按第四节第 3 小节已算取过，`wait` 也拿不回。反过来，压缩如果没切这条，它的摘要请求能先读到正文。单写者同项和原子批只能保证两条日志一起写，不能保证服务商已收到正文。
- **核实**：源码及合同：`kernel/run/loop.ts:245–292` 的取输入→解析→压缩→渲染→调用顺序；`kernel/state/history.ts:82–86,102–119` 的位置章与切步规则；`kernel/view/format.ts:55–89` 的 `render` 可隐藏事件；`harness/runtime.md` 输出 22，拦截可以不调用模型端口。
- **建议**：明确承诺的是「进入一次对话请求」还是「消费到某次逻辑尝试」，不要把受理、消费、发出混称送达。让真正进入对话请求的提示走内核保证的渲染位置，明确自动压缩只估算还是可读正文；对发请求前失败保留待发或给可查的失败去向。`preview` 用相同选取与排序做只读投影，不消费。用真实内核验收阈值切步、模型不可用、Profile 隐藏、守卫拦截和重试，查记录及模型端口实际收到的块。

### 3. 结果在最后一次回复时到达，按到达窗口不同结果会一直等或立即唤起

- **严重程度**：重要；**类别**：正确性。**位置**：提案第四节第 1 小节「唤起」、第 3 小节「结果的两条路」。
- **现象与影响**：任务结束时模型的最后一条回复还在流式返回，`takesInput` 为真，提示就「照常等下一次请求」。这条回复没有工具调用，缓冲区也没有插话或排队，这一轮正常收口，不会再请求；提案只让在「不再取输入时」受理的提示参与收口唤起。相同一笔完成记录晚到一个队列项反而能唤起。`takesInput` 不是「肯定还有下一次请求」；空闲后没有新事件替它重判，结果按提案已领取。
- **核实**：`harness/runtime.md` 输出 7、28、104 与 `kernel/run/loop.ts:393–425` 只为 `steer` 继续请求、只为 `followup` 开下一轮；对照提案第 62 行的两个分支。单纯无 `wake` 的提示继续等，不是问题。
- **建议**：将 `wake` 保留为尚未消费提示的待判资格，不只存到当时活跃运行的 `deferred` 列表；每个正常收口批看剩余的带 `wake` 提示，至多开一次，已取消、已取走、停止、重装配与关闭都给明确去向。不要让提示本身像 `steer` 一样延长旧轮。真实内核以模型响应屏障控制同一结果在最终回复前后受理，验证两边的收口结果一致且只开一轮。

### 4. 提示只限正文，静置的缓冲区仍能撑破 512 KiB 快照

- **严重程度**：重要；**类别**：安全与性能。**位置**：提案第四节第 1、3 小节（第 57–63、83 行）。
- **现象与影响**：第 2 稿给合并包明确过段数和总量预算。本稿改成每条提示单独排队、可永久留在会话里，只限单条正文，`key` 又是可选。按文中的 16 KiB 示例，32 条满长 ASCII 正文加 JSON 外壳就超过 512 KiB；短但需要 JSON 转义的正文或已有用户附件会更早撞上。同一插件连发不同 key，或几个插件各发一批即可；Agent 的并发上限不限制已经结束并入队的结果。窗口重连时拿不到快照，偏偏不能从排队区取消这些提示；`eventChunk` 只能救日志事件。
- **核实**：`agent/sessions.md` 输出 9、22；`backend/frames.ts:13–24` 的编码口径；`kernel/session/session.ts:340–357` 快照复制整份缓冲区；按提案的示例预算计算，非新实现的压测。
- **建议**：定会话级待发总量（含来源和编码开销），给已有用户输入保留预算；溢出提供可恢复的受理失败或把多段结果合成有界摘要加地址，不悄悄清掉已受理的提示。验收停止后堆积、混合来源及转义字符，重开仍能读快照、取消，并能追到未获交付的结果。

### 5. 子代理运行按方案会在同一份清单和关停确认各出现两次

- **严重程度**：重要；**类别**：不变量。**位置**：提案第四节第 3、5 小节（第 82、85、100 行）。
- **现象与影响**：父会话 P 后台派子会话 C 的 R。第 82 行登记 `{kind: nbook.agent.subagent, owner: P}`，第 85 行同一 R 再登记 `{kind: nbook.agent.run, owner: C}`；第 71、97 行又把二者归到同一个根组。不是两件会各自继续的工作：两行的停止都指向 C/R；工作台数两件，现行 `runningWork` 实现也逐行报两件。删除 `nbook.agent` 的 reporter 只能删除跨插件重复，不能删除这一次双登记。父 Agent 中途附着到用户开的子会话运行时也得决定哪一行是原件，不能再建一份。
- **核实**：`agent/subagents.md` 输出 10、16（续用、归属及停止范围），`agent/jobs.md` 输出 1、4、9；`tasks/backend/plugin.ts:42–45` 按每个 `running` 行报工作；对照提案三项登记规则。
- **建议**：按实际工作去重。子代理任务与运行行共享精确的执行目标 `(childSessionId, runId)`，父会话的取件引用它而不再登记第二件；或把父任务明确当关联，只投影一次停止和计数。分开定义「运行结束时移出的行」与父卡片的结果寿命。验收后台派发、前台派发、插入用户开的运行三种情况各只有一件实际可停工作，父方取件与用户定向停止都有效。

### 6. 自动转后台越过了 `eval` 的嵌套调用寿命

- **严重程度**：重要；**类别**：不变量。**位置**：提案第四节第 3 小节「`shell` 自动转后台」（第 87 行）。
- **现象与影响**：提案排除了子代理会话与 eval 单元本身，却没有排除普通会话里的 `eval` 调 `tool.shell({command, timeout: 120})`，它仍是一条前台 `shell`。按通用 60 秒门槛接手后，代码误把「已转后台」当作命令成功返回，单元收口、超时或被中止后命令还可能继续。现有合同拒绝代码里的 `async` 就是为了禁止这种寿命脱离；给参数缺省值之外再开一条脱离路径没有改变这个约束。
- **核实**：`agent/builtin-tools.md` 输出 29（`async-in-code` 与原因），`agent/eval.md` 输出 5、14、19，`harness/runtime.md` 输出 90、100；对照提案只排除「子代理会话里不转」。这是新方案边界缺失，不是当前版本已逃逸。
- **建议**：自动移交只在真正的顶层 `shell` 启用，明确按内核的 `ToolContext.within` 判，不按会话或工具名猜。真实 eval 内核＋子进程＋注入时钟测 60 秒门槛前后：嵌套命令仍受外层寿命约束，不建后台行；同样的顶层调用只移交一次并保留原截止时刻。

### 7. 经 Agent 登记的外部任务，拿不到真实的清单来源和插件代次

- **严重程度**：重要；**类别**：不变量。**位置**：提案第四节第 2、3 小节（第 71–72、82–84 行）。
- **现象与影响**：外部 Workflow 工具在 Agent 里执行，工具入口盖得出会话和 `invocation`；但如果它经 Agent 调用 `tasksKey.start`，`nbook.tasks` 看见的调用方是 `nbook.agent`。按稿盖章就得不到 Workflow 的 `kind`，只停 Workflow 也不释放 Agent 的门面。反过来让 Workflow 直接传会话和 `invocation` 给自己的 `tasksKey`，又丢了本次实际调用的绑定。按这两条路接，无法同时兑现来源、调用归属、按发起插件中断。
- **核实**：`runtime/services.md` 输出 11–13（身份由内核签发，没有本地代调用方取门面）；`tasks/backend/plugin.ts:46–48` 和 `core.ts:242–258`（只按实际门面身份释放）；`agent/backend/tools.ts:223–257,278–290`（执行调用与创建工具处在不同寿命，且贡献句柄有代次）。这是从合同推出的集成缺口；上一稿第 7、15 条处理了 Agent 登记权，本稿还新增了清单的来源盖章与代次合同。
- **建议**：分别绑定登记插件代次和实际工具调用，不让调用方自报其一。用同一次登记的受限凭据把两份身份合在一条记录上；定义撤回时先封住登记、发起方实际工作收口、再清回调和转终态的次序。用真实插件装配验收：A 的工具在两个会话登记，停 A 不停 Agent 或 B；来源、归属各正确，A 的旧句柄不能新增、改行或在停代后被调用。

### 8. 清除工作台的已结束项不能顺带清掉尚未领取的 Agent 结果

- **严重程度**：重要；**类别**：正确性。**位置**：提案第四节第 3、5 小节（第 82–84、99 行）。
- **现象与影响**：命令 A 已结束，结果读取或会话写入还没完成。这时窗口点「清除已结束」，或其它插件结束第 51 件任务。如果 Agent 的取件记录只保留题述的布尔状态，其结果、驱动或终态随着唯一清单行没了；提示明确没写进去时，`wait(A)` 也无从接手。若反过来为了保留 A 禁止从清单清除，又改变工作台的现有合同。工作台留 50 行和 Agent 未取件上限不是同一个寿命。
- **核实**：`workbench/background-tasks.md` 输出 7、8、14；`tasks/backend/core.ts:138–146,294–307` 的移出不分调用者；`agent/jobs.md` 输出 3、6、10（未取件按每会话 32 个、全局 1,024 个；命令的文件可在行移出后读取）。提案与 Task 决定 6 没把工作台移出定义为放弃领取。
- **建议**：50 件只限制工作台的已结束投影；同一份真实终态和结果引用，在尚有 `wait`、送达领取者或未取件保留期时不丢；不要做另一张镜像状态表。Spec 分别列出列表、远程 `jobs`、`wait` 与 `jobTail` 的可见寿命。用真实远程合同卡住交付、跨窗口清除或淘汰行，再验证明确未送达的结果仍可取且只取一次。

### 9. 不改日志版本就回滚，旧内核会把提示作为一轮普通输入执行

- **严重程度**：重要；**类别**：正确性。**位置**：提案第五节（第 111、114–115 行）。
- **现象与影响**：提案断言旧内核读到新模式会报 `log-corrupt`。但 `inputQueued` 和 `notice` 本来就是已知事件，旧读者不查 `inputQueued.data.mode` 的取值；空闲时开运行按首条 `ready` 取，不按模式筛。若继续写格式 1，带一条待发提示的会话回滚后可能正常打开，下一句用户输入触发的第一轮先执行这条提示。它进入 `user` 角色的 `input`，不是新合同里的非授权提醒。
- **核实**：在固定提交的临时副本运行 `bun --no-install /tmp/review-t22-proposal/probe-log-and-run.ts`。用真实 JSONL 存储追加提案规定的格式 1 `inputQueued(mode: "notice", state: "ready")`，通过现版公开会话接口打开、发话并检查实际模型端口：`opened:true`、`readMode:"notice"`、`oldReaderInput:"提示哨兵"`、`oldReaderRole:"user"`、`modelRequests:2`。已复现的是旧读者对拟议日志形状的行为，不是新功能。`kernel/api/events.ts:164` 的 `notice` 名也已存在，不可依赖未知事件名拒读。
- **建议**：写入第一批新语义前使用旧内核能识别的前向不兼容边界（例如新的日志格式门槛；旧读者报 `needs-migration`），并保留新读者打开既有日志的路径；仅升级 TS 联合或给新事件数据加校验拦不住已发布的旧读者。验收用旧程序从磁盘重开新日志，断言在写入或模型请求前拒绝；另验证旧的 `notice.code` 记录照常读。

### 10. `runId` 不能区分回退后重跑的两次执行，旧取消仍能停错

- **严重程度**：重要；**类别**：正确性。**位置**：提案第四节第 3 小节、第六节（第 85、119、122 行）。
- **现象与影响**：按 `abort{runId}`，能拦住上一稿第 18 条所说的不同 `runId`；同一 `runId` 的重跑拦不住。用户打开旧的任务卡片；另一窗口完成 R、回退到 R 中间并使 R 接着跑；第一个窗口的旧取消仍匹配 R。按 `runId` 懒读旧卡片结果，也会换成重跑后另一条分支的结果，而不是原任务结算时的结果。
- **核实**：同一条临时命令走真实 `say → rewind → start → waitRun → log/runResult`，得 `sameRunId:true`、`sameIdEndings:2`、`resultOfOldId:"第二次收口"`。`harness/runtime.md` 输出 36、`kernel/run/commands.ts:222–227` 和 `kernel/run/results.ts:21–40` 是现有合同。取消停错是对提案只比较 `runId` 的推演，未实现、未执行该取消。
- **建议**：清单与取件引用区分逻辑 `runId`、本次启动/恢复的执行代次、结算时的 `runEnded` 标识。停的条件用激活代次，在受理停止的同步段核验；原卡片按结算标识读或保留原结果引用，不改变现有 `runResult(runId)` 的“最近一份结果”合同。验收卡住第二次执行，对第一次执行发迟到的取消，再检查第二次未停、旧卡片结果仍是第一次。

### 11. 只登记对话运行，会从关停确认漏掉手动压缩

- **严重程度**：重要；**类别**：正确性。**位置**：提案第四节第 3、5 小节（第 85、100 行）。
- **现象与影响**：用户启动手动压缩，压缩模型还在跑。这是 `runStarted{kind: "compact"}`，不是提案入清单的对话运行。移除 Agent 的报告方之后，最后一个窗口关闭前问「什么会中断」时就没有它。另一个漏报入口是未装或未解析到 `tasksKey`：现在 Agent 照常可运行，删除报告方不能保证工作已经移交。
- **核实**：`harness/runtime.md` 输出 52、53；`agent/backend/running-work.ts:39–75` 通过 `activityWithBackground()` 报忙的非内部会话，不限定 `chat`；`agent/backend/plugin.ts:80–91` 把 `tasksKey` 声明为可选；`runtime/server-host.md` 的“在跑的工作”按实际会被中断的工作收集。结论为现行合同与拟议登记范围的差集。
- **建议**：由 `nbook.tasks` 的一份数据报告所有会被中断的用户工作（纯压缩能保留自己的种类；视图是否显示另定），显式排除内部拟标题运行。明确 `tasksKey` 对 Agent 是否从可选变为必需；任一支持的装配不能静默漏报。验收停在真实手动压缩的模型端口，从宿主询问工作应见一项，结算后不再报。

### 12. 清单 v2 若仍只推整份，一个大 `open` 参数就能卡住别的任务的取消

- **严重程度**：重要；**类别**：安全与性能。**位置**：提案第四节第 2、5 小节（第 78、97–100、137 行）。
- **现象与影响**：`open` 的命令参数、种类与归属都是新字段，却没有逐项编码预算；`nbook.tasks` 又按决定不限制同时在跑的件数。维持 v1 的整表传输，一个含 512 KiB 字面参数的任务加上 JSON 外壳就够跨上限；即使逐项限长，多任务仍有同一界限。服务端跳过更新、重连也取不到，窗口会看不见其它新任务或仍对着已结束的旧行。
- **核实**：`workbench/background-tasks.md` 输出 8、9 与“失败与恢复”；`tasks/backend/remote.ts:24–36,44–55` 在 JSON UTF-8 超过 `LIST_MAX_BYTES`（512 KiB）时返回 `too-large` / 跳过推送。是 v1 的可观察契约与 v2 未限输入的容量推演，不是已实现的 v2 测试。
- **建议**：给行摘要与跳转参数独立编码上限，只放定位所需 id；v2 的同步边界用可分页的快照和带版本的失效/更新，而不是超过预算便停更整表。保留进行中的任务不设数量上限。验收大参数拒绝不留半行，正常登记超一页后两个窗口仍可看到、取消和重连对账。

### 13. 同步领取之外，还缺少写入结果未知时的结算规则

- **严重程度**：重要；**类别**：不变量。**位置**：提案第四节第 3 小节（第 82–84 行）、第五节第 114 行。
- **现象与影响**：送达先排他领取，再读输出、开会话、写日志。写入或同步失败时可能已有完整的受理批，也可能没有；`send` 还可能在受理已经写下、等待反应时没交回成功。凭失败退回领取，平行 `wait` 就能在已写提示之外再交一遍；凭领取就删，不曾受理的结果会丢。前台续用也可能接上同一子运行，不能只让 `wait` 与送达互斥。上一稿第 2、13 条的处理有稳定 `commandId`、未知结果不退还及按等待次数登记，本稿只保留了同步领取这一半。

- **建议** Agent 的命令和子代理在登记时明确 `notify: false`，外部任务是否弹按其合同定。首批规定结束即移出的行不支持结束通知，登记时处理冲突，保留现有插件任务的默认通知及多窗口撤回规则。验收两个窗口里 Agent 结果已送达且无结束弹窗，同期普通插件任务完成仍正常通知。

### 25. 自动送达后，历史子代理卡片仍缺少持久的终态和正文来源

- **严重程度** 重要。**类别** 正确性。位置在提案第四节第 1、3 小节和第六节（第 59、83、126 行）。
- `agent_spawn` 先交回 `running`，自动送达只写 `notice{by, text}`，领取记录随后可清。现有卡片从调用结果或后续 `wait` 等工具结果取终态和正文。没有这些结果时只看子会话最近 20 次收口，拿不到正文，旧运行退出索引后还会退到“状态未知”。提示被用户取消或父会话回退时，路径上的提示也无法当作旧卡片唯一的数据来源。
- **核实** `agent/conversation.md` 输出 33，`agent/subagents.md` 输出 21，`agent/web/subagent-card.ts:91–102,123–157`，`nb-agent-ui/src/kernel-transcript.ts:641–644`，`kernel/log/index-file.ts:6,56–60`。上一稿第 25 条已有读取持久结果的处理，本稿第 126 行只保留了目标。卡片退化是按已实现的取数顺序推演，本轮未跑浏览器。
- **建议** 卡片持久保存可定位该次结算的引用，沿用子会话日志读取终态与正文；引用按第 10 条定位实际收口，避免同一 `runId` 接着跑后读到新结果。可在送达时提供有界的结构化摘要以加快展示，无需解析提示正文。验收不调 `wait`、移除已结束行、原运行退出 20 条索引后重开父对话，仍能打开原结果。

### 26. 同时结束的任务缺少合并点，可能各自触发一次模型请求

- **严重程度** 重要。**类别** 正确性。位置在提案第四节第 1、3 小节（第 62、83 行）。
- Task 决定 1 要求同时结束的结果合成一条。草稿只描述每件结束后各自送一条。如果同批完成的 A、B 各自异步读文件，A 先排进空闲会话并启动模型，B 即使与 A 同时结算，也可能晚于 A 的请求组装。B 若在 A 的正常收口后才受理，还会再唤起一次。第 3 条的收口重判只能防止 B 遗漏，不能兑现合并。多发的请求会增加费用，默认未设费用上限。
- **核实** Task README 决定 1 与“留给计划的细节”，`agent/run-guards.md` 的 `maxCost` 默认值。omp 18.14.1 在 `session/async-job-delivery.ts:113–168` 把一批有效结果合成一条，`session/yield-queue.ts:125–174,179–199` 在请求边界或空闲刷新时合并。NeuroBook 的交错按提案推演，未运行新送达。
- **建议** 由 Agent 对同一会话设有界的合并窗口，按任务分别核对领取权，按条数与字节把可送的结果一次提交。等待窗口内到来的 `wait` 仍可领取未提交的项，单项读取失败不阻塞其它结果。用注入时钟和读结果的屏障让两项在同一窗口完成、格式化先后不同，核对实际只唤起一次，两个结果各出现一次。

### 27. 展示文字校验失败会阻止共享任务记录收口

- **严重程度** 重要，**类别** 不变量。位置在提案第四节第 2、3 小节（第 72、78、82–84 行）。
- 若用现有 `TaskHandle.fail` 承担合并后的终态转换，带长参数的本地化失败原因超过 1 KiB 时，方法只记诊断、返回，任务仍是 `running`。真实命令或 Workflow 此时可能已经失败。以前这一校验错误影响清单，合并后如果取件与名额也从该终态读，就会继续等待、占着名额，关停确认也会多报一件。上一稿第 17 条处理了登记标题，这里卡在结算时。
- **核实** `workbench/background-tasks.md` 输入的文字值校验，`tasks/backend/core.ts:87–95,156–161,187–204`，`agent/backend/jobs/center.ts:173–184`。现有文字拒绝行为由源码确定，合并后对取件的影响是推演。
- **建议** 在受管工作接入清单时校验元数据，结算时独立接受真实结局。失败说明不合格时交回固定的有界文案并记录诊断，给模型的结果与产物仍按 Agent 的预算处理。用真实服务验收插件传入超预算的本地化失败原因后，运行行收口、名额归还、结果仍有明确去向。

### 28. 按项目过滤后，打开清单可能把未显示的失败标成已看过

- **严重程度** 重要。**类别** 正确性。位置在提案第四节第 5 小节和第八节第 4 条（第 97、137 行）。
- 项目 A 的窗口在前台打开默认清单。项目 B 的任务失败，只能切到全部项目才看到。如果在现有 store 之后增加视图过滤，B 仍会在 `accept` 里被标为看过，状态栏提前失去失败指示。若改为把过滤后的列表传给 `accept`，切换项目又会被当成任务移除，撤掉仍有效的失败通知和重试动作。
- **核实** `workbench/background-tasks.md` 输出 12–14。`tasks/web/store.ts:93–113,123–129`用同一份列表判断条目是否仍存在、推进通知基线并标为看过。两种接法的后果是对既有代码和新过滤规则的推演。
- **建议** 以全局清单维护任务存在性和首次连接、重连的基线。视图标为看过时只用本窗口当前筛选能显示的已结束项。状态栏跨项目统计与通知范围分别按合同定义，切换筛选不产生任务终态或移除。验收两个项目窗口分别开着任务视图，令 B 的任务失败，核对 A 切到全部项目之前的未读状态，并核对切回时不会撤掉 B 的有效通知。
