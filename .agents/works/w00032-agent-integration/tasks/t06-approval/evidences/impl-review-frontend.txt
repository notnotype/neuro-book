### 规则写入是“读—合并—写回”，没有 `expect`，也没有乐观更新，并发时后写的盖掉先写的
- 严重程度：重要
- 类别：正确性（并发）
- 位置：`packages/neuro-book/src/plugins/agent/web/plugin.ts:275`；`packages/neuro-book/src/plugins/agent/web/components/PermissionRulesPage.vue:58-71`；`packages/neuro-book/src/plugins/agent/web/permission-page.ts:41-60`
- 现象：
  1. 一批审批里选了两条不同命令的“以后都允许”（例如 `git diff *` 与 `touch *`）后提交，`AgentWizard.submitApprovals` 同一个 tick 里连发两个 `input.submit`，宿主两次进入 `resolveInput` 的 `allow-always` 分支，两次 `rememberRules` 都在 `await` 之前同步执行 `appendRules(settings.get(...), rules)`，读到的是同一份旧列表。两次 `settings.update` 各自写“旧列表加自己那一条”，后到的覆盖先到的，有一条规则丢失，但界面对两条都按“已批准”走，用户以为都存了。
  2. 设置页同理：`remove`、`move`、`save` 都用当前 `props.rules` 算出整份新列表再 `emit("change")`。`settings.update` 只在写入成功后才 `apply` 快照（`plugins/settings/shared/instance.ts:259-266`，没有乐观更新），所以两次点击落在一次写入往返之内（上移连点两次、删除连点）时，第二次用的是旧列表，把第一次的结果盖掉。
  3. 设置窗口开着时，别处（对话里的“以后都允许”、外部编辑设置文件）追加的规则，会被页面下一次写整份列表时盖掉。
- 为什么是问题：权限规则丢一条或复活一条已删的拒绝规则，都是安全相关的静默错误。配置服务本来为“读、合并、写回”提供了 `update(..., {expect: {value}})`（`packages/neuro-book/src/shared/settings.ts:419-425`，configuration.md 输出 25），这里一处也没用；`session-host.test.ts` 的 `rememberRules` 是桩，测不到。
- 如何核实：读上面三处；`instance.ts` 的 `update` 里 `apply(layer, result.snapshot)` 在 `await link.write` 之后。复现 1：脚本两条 shell 审批在同一批里，各选“以后都允许”，提交后看 `settings.json` 里 `nbook.agent/permissionRules` 只有一条（未验证，从代码推断）。
- 建议改法：`rememberRules` 与页面的 `write` 都带 `expect: {value: 读到的那份}`，得 `conflict` 时重读再合并重试一次；`rememberRules` 同时在宿主里串行化（一个 promise 链），这样一批里的多条依次追加。页面可在写入未完成时停用增删移动按钮，或维护本地待写队列。补一条测试：两次 `rememberRules` 并发都落盘。

### 表单换算会改变关键词规则的意思，且来回测试没有覆盖关键词
- 严重程度：重要
- 类别：正确性、测试
- 位置：`packages/neuro-book/src/plugins/agent/web/permission-rules.ts:33`（`join("、")`）、`:53-56`（`split(/[,，、\s]+/u)`）；`permission-rules.test.ts:19-26`
- 现象：`arg`+`keywords` 的 `value` 是字符串数组，每个元素是整段子串（`backend/permissions/rules.ts:90` 用 `includes`）。手写规则 `value: ["blood splatter", "a,b"]` 在表单里显示成 `blood splatter、a,b`，只要用户打开编辑、改了别的字段（比如理由）点保存，就会被按空白与逗号拆成 `["blood","splatter","a","b"]`，匹配范围变宽（放行规则变宽就是放行得更多）。另外 `value` 为单个字符串时走 JSON 分支，没问题；`value` 里混了非字符串元素时 `join` 会把它们转成文字，同样丢类型。
- 为什么是问题：“手写在设置文件里的规则照样显示、照样能改”（permissions.md 输出 22）的前提是表单来回不变，这里违反了；`permission-rules.test.ts` 的 `rules` 里没有任何 `arg` 规则，来回测试漏掉了这一类，而 Lab 场景里恰好有 `keywords: ["血腥", "暴力"]` 这种条件。
- 如何核实：`formToRule(ruleToForm({tool:"x", action:"allow", when:{type:"arg", path:"prompt", op:"keywords", value:["blood splatter"]}}))`，得到 `value: ["blood","splatter"]`。
- 建议改法：关键词里含空白、逗号、顿号，或元素不是字符串时，`ruleToForm` 走 `json`（与“认不出的条件走 JSON”一致）；或者把分隔符限定为 `、` 与换行并在界面写明。测试补一条关键词来回与一条含空格的关键词。

### JSON 条件只校验语法，不校验形状；写错 `type` 的拒绝规则会拦掉这个工具的全部调用
- 严重程度：建议
- 类别：边界
- 位置：`packages/neuro-book/src/plugins/agent/web/permission-rules.ts:58-63`；`PermissionRulesPage.vue:128-130`（`problem` 只给输入框标红）
- 现象：`JSON.parse` 成功就接受，`123`、`null`、`[]`、`{"type":"comand"}` 都会写进设置。按 permissions.md 的“偏向收紧”，未知匹配器的拒绝与询问规则命中，等于“这个工具所有调用都被拒绝或询问”，且设置页只显示“自定义条件”，用户看不出写错了。另外 `problem` 只让对应输入框 `invalid`，没有文字说明为什么，JSON 解析错误与“必填为空”无法区分，读屏也读不到；用户改字后红框不会自己清除。
- 如何核实：读 `formToRule` 的 `json` 分支；`evaluate` 对未知 `type` 返回 `"unknown"`（`rules.ts:131-133`）。
- 建议改法：`when` 必须是非数组对象；至少在保存前对顶层 `type`/`all`/`any`/`not` 做一次已知性检查并警告（可以保存，但要说明“写错了会拦住整个工具”）；`problem` 对应一行错误文字，字段改动时清除。

### “这本书的规则”加载失败时整段不显示，用户以为这本书没有规则
- 严重程度：建议
- 类别：边界、错误显示

### 还没有会话时选的模式（`draftMode`）会漏到之后建的任何会话里

- 类别：正确性（状态收口）

### Shift+Tab：作曲框总是绑着监听，但切不了模式时仍然吞键，焦点出不来

- 类别：可访问性、实现耦合
- 位置：`packages/nb-agent-ui/src/vue/composer/AgentConversationComposer.vue:414`（`@shift-tab="cycleMode"` 无条件）、`:241-250`；`packages/nb-markdown/src/prompt/PromptEditor.vue:423-424`、`:452-456`
- 现象：`PromptEditor` 现在“没人监听就不吞”，但作曲框永远传了 `@shift-tab`。`cycleMode` 在 `modeDisabled`、`modes.length < 2`（非主创会话 `modes` 为空）或可用状态不是 ready 时直接返回，而 `handleKeyDown` 已经 `return true`（preventDefault），键盘用户在这些会话里无法用 Shift+Tab 从输入框往回走。补全菜单开着时同理：吞掉且什么也不做（这是 spec 要求的，但焦点也出不来）。另外 `shiftTabListened` 在 setup 里读 `getCurrentInstance().vnode.props.onShiftTab` 取一次值，父组件之后条件性绑定监听则不会更新，且依赖 Vue 的内部结构。

### “以后都允许”没有说清要永久放行什么，说明只在悬停提示里
- 严重程度：建议
- 类别：界面、安全告知
- 位置：`packages/nb-agent-ui/src/vue/wizard/AgentApprovalWizard.vue:115-116`；`packages/nb-agent-ui/src/locales/zh-CN.ts`（`allowAlways`、`allowAlwaysHint`）
- 现象：本会话按钮写明规则（`本会话都批准 git diff *`），而永久放行的按钮只写“以后都允许”，写进哪里、所有作品都生效、记的是哪条规则只在 `title` 里（键盘、触屏、读屏用户都看不到）。对没有 `remember` 的工具（`write`、`edit` 等），记的是整个工具：一次点击永久放行这个工具在所有作品里的所有调用，而按钮上看不出来。批量时 `choose()` 只联动 `allow-session`，不联动 `allow-always`，同一条规则的其余项还要逐个点。

### 已有更靠前的询问规则时，“以后都允许”追加的放行规则永远不生效，界面却当成功
- 严重程度：建议
- 类别：边界
- 位置：`packages/neuro-book/src/plugins/agent/web/permission-rules.ts:104-108`（`appendRules`）；`session-host.ts:986-998`
- 现象：规则从上到下第一条命中算数。审批请求恰好是因为一条用户层 `ask` 规则（或项目层规则）才出现时，末尾追加的 `allow` 排在它后面，下次仍然会问。写入成功，界面没有任何提示，用户以为已经记住了。`same` 比较用 `JSON.stringify([tool, when, action])`，键顺序不同的手写规则（`{pattern, type}` 与 `{type, pattern}`）判为不同，会重复追加；`tool` 简写（`shell`）与全名（`nbook.agent.shell`）也判不同。
- 如何核实：用 `appendRules([{tool:"nbook.agent.shell", action:"ask"}], [{tool:"nbook.agent.shell", when:{...}, action:"allow"}])`，结果 `allow` 在 `ask` 之后。
- 建议改法：追加前检查是否已有排在前面、同工具且条件覆盖它的 `ask`（`when` 相同或没有）；有时提示“你有一条更靠前的询问规则，它会继续生效”；比较时对 `when` 做键序无关的规范化。开发者已定“写到末尾”，这条只补提示，不改位置。

### `approvalReason` 把用户规则的理由与内部暗号放在同一个字符串通道里，会误判

  2. `AgentModeSwitchWizard`：附言非空时“批准”禁用、审批模式只在与当前不同时才随答案交回、`hasPlan` 两种标题，都没有 DOM 测试；只有 `session-host.test.ts` 直接发 `input.submit` 绕过了向导，以及 e2e 里点一次默认“批准并开始”。
  3. `AgentApprovalWizard`：`remember === false` 时两个按钮都不显示、有 `label` 时按钮文字、`allow-always` 的 `pick` 都没有组件测试；`wizard.test.ts` 的新用例只测 `choose`，没有 `allow-always` 不联动的判据。
  4. `PermissionRulesPage`：增删改、上移下移、`writable=false` 停用、`projectRules="invalid"`、只读命令失焦才写，只有 Lab 场景与一个 e2e 删除用例；`permission-rules.test.ts` 的“来回”没有关键词（见上）。
  5. e2e 的“模式”用例 `toHaveClass(/is-muted/u)` 断言的是实现用的类名，不是用户看到的结果（变淡）。
- 建议改法：补 `AgentModeSwitchWizard.dom.test.ts`、`AgentApprovalWizard` 的按钮可见性用例、`PermissionRulesPage` 的 DOM 用例；`.text()` 断言恢复。

### 设置页的编辑状态假设列表不变；保存时先关对话框，写失败后表单已丢
- 严重程度：建议
- 类别：边界
- 位置：`PermissionRulesPage.vue:42-69`（`editing` 记的是下标）、`:76-84`（只读命令失焦才写）
- 现象：
  1. `editing` 是下标：编辑对话框打开期间列表被别处改过（另一个窗口、对话里的“以后都允许”只追加到末尾不影响，但删除或排序会），`save` 的 `next[editing.value] = result.rule` 改到别的规则上；列表变短时写到越界下标，得到带空洞的数组（JSON 序列化成 `null`），写入会被 schema 拒绝。
  2. `save()` 成功校验后立刻 `editing.value = null` 关闭对话框，写入失败只在设置窗口弹通知，用户刚填的整张表单没有了。
  3. 只读命令框“失去焦点才写”：用户在框里改了字，直接用 Esc 或快捷键关闭设置窗口、切别的页，Chrome 对被移除的聚焦元素并不保证先发 `blur`（从代码推断，未验证），改动丢失，且没有未保存标记（`SettingsPageContext.dirty` 没用）。
- 建议改法：用规则内容（或写入时的完整快照）而不是下标定位；保存成功后再关对话框；页面卸载时（`onBeforeUnmount`）补一次 `commitCommands`，或在输入时设 `context.dirty(true)`。

### 窄屏与英文界面：折图标的断点固定在 420px，没有按文字长度；Lab 场景有重复与缺口
- 严重程度：建议
- 类别：界面、维护性
- 位置：`AgentConversationComposer.vue:845-849`；`packages/neuro-book/src/plugins/lab/web/fixtures/index.ts`（`PermissionRulesPage` 场景）、`agent-scene/PermissionRulesFixture.vue`
- 现象：
  1. 非单行版式下左边 `+`、模式、审批、登记按钮（`flex: none`）与右边模型版（最宽 18em）并排，只有 ≤420px 才隐藏文字。英文界面（`Allow writes`、`Ask each time`、`Discuss`）下文字更长，421 到约 480px 之间左边的 chip 不可收缩、`.acv-composer__tools` 也没有 `overflow`，可能压到右边（未验证，需要 en-US、窄容器的 Lab 截图）。
  2. 同一份 5 条规则的数组在 `fixtures/index.ts` 的五个场景里整段重复，改一处要改五处；`PermissionRulesFixture.vue` 只透传 `rules` 等几项，忽略了 `modeWriteAction`、`readOnlyCommands`，所以“其它”区的 `ask` 状态、已有只读命令这类状态没有场景可看，页面的 `modeWriteAction`、`readOnlyCommands` 事件在 Lab 里也不更新。
  3. 没有“批量里选了以后都允许”的向导场景、没有英文窄屏的作曲框场景。
- 建议改法：规则数组提成常量；夹具把这两项也接成 `ref`；补英文窄屏场景（`english` 后缀），顺手核实 1。
