# t06 设计审查（omp）

### 1. 项目询问规则会遮住用户拒绝规则

- **严重程度**：重要；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:65-66`
- **现象**：项目规则先拼接、用户规则随后拼接，第一条命中即结束；项目规则虽禁 `allow`，仍可放 `ask`。同一工具/参数上项目 `ask` 命中后，后面的用户 `deny` 永远不会生效，用户在审批卡片批准即可执行。
- **为什么是问题**：这把用户显式拒绝降成可被作品配置绕开的询问，和“用户拒绝应高于项目授权/询问”的常见配置所有权不变量冲突；“项目不允许放行”并未保护用户的拒绝。恶意或误配的作品规则可把封禁改成审批。
- **如何核实**：按计划逐条求值两条规则：项目 `{tool: "x", action: "ask"}`、用户 `{tool: "x", action: "deny"}`；第 1 条命中即 `ask`，不检查用户规则。参照 Codex 调研第 4.8 节是 deny 优先于 ask，Claude Code 也是按 deny/ask/allow 分级。
- **建议改法**：跨来源先算拒绝的硬优先级（至少用户 deny 覆盖项目 ask）；或者把项目规则限制为纯追加 ask/deny 但将用户 deny 放到项目规则之前。保留同一来源内的明确首条命中语义，并为来源间冲突定义确定优先级。


### 2. `yolo` 会绕过“模型进入 plan 必须用户批准”

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:34,63-66,98`
- **现象**：计划要求模型通过 `switch_mode` 进入 `plan` 必须经用户批准，但此调用没有被定义为审批流水线外的特殊操作，也没有声明不可覆盖的内建规则。现有通用审批模式约定是 `yolo` 放行工具声明的询问；`approveByMode` 对 `yolo` 直接返回 allow。因而按普通工具实现 `switch_mode` 时，yolo 会使“批准向导”不出现，plan 直接切换。
- **为什么是问题**：违反开发者 2026-11-06 已定的“模型进 plan 要用户批准”。把 `switch_mode` 标成普通 `ask`、或依赖用户规则里有一条 ask 都不够：已定 yolo 语义会放行前者，后者可被规则删除或被优先级遮住。
- **如何核实**：按计划将 `switch_mode{mode:"plan"}` 作为普通工具，经现有 `approveByMode` 输入 `mode:"yolo"`；结果是 `{verdict:"allow", by:"mode:yolo"}`，不会生成 `interactionRequested`。当前尚无 `switch_mode` 实现，因此这是由既有审批合同推导的计划冲突，不是声称已运行新功能。
- **建议改法**：把进入 `plan` 定义成不可被审批模式、普通规则和“全部放行”覆盖的专用确认操作，或明确另一种符合开发者决定的硬性合同；不要用可配置的普通 `ask` 规则代替。

### 3. 同一回复里的工具会沿用切换前模式判定，可能在新模式下执行写入

- **严重程度**：阻断；**类别**：不变量
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:98,111`；`packages/nb-harness/src/kernel/run/tools.ts:271-280,310-315`
- **现象**：内核按既有输出 79，在任何工具执行前先判完同一条回复的所有调用。判定结果随后只因工具/参数或核心 `readOnly`、`approvalMode` 变化而重算；计划模式是另一维，当前判定快照不包含它。若同一回复先调用 `switch_mode{mode:"discuss"}`、再调用写工具，后者会按切换前的 `normal` 判定；即使切换工具先执行，写工具仍可复用旧的 allow。反向从 discuss/plan 切到 normal，同批调用也会按旧模式拒绝或再询问。
- **为什么是问题**：新模式声称“立刻生效”，但一个模型回复可把切换和受模式约束的副作用绑定在一起，违反模式闸门。额外的 UI 模式切换若发生在审批已通过、工具尚未开始时，也没有计划中定义的模式代次校验。
- **如何核实**：内核 `approvalPhase()` 先按 `runnable` 顺序完整填充 `judged`，之后才进入 `runCall()`；`stillHolds` 不比较扩展模式。Spec 输出 79 同样明确同回复所有调用先过审批再执行。新功能还未实现，计划的运行时验收应以真实内核一次返回“切模式 + 写入”两个调用，分别覆盖切入与切出、两种工具顺序，并检查 `toolStarted`/文件内容。
- **建议改法**：把模式状态纳入内核每次执行前的判定快照，并在切换边界使同批剩余调用重新判定；更简单的合同是切模式调用终止当前回复的工具批，模式确认后续轮再执行其余工作。明确运行中的已批准调用不能被追溯取消。


### 4. 审批记忆事件变形缺少旧日志回放策略

- **严重程度**：重要；**类别**：不变量
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:85,104`；`docs/specs/harness/session.md:174-175`；`packages/nb-harness/src/kernel/api/events.ts:95-96`
- **现象**：计划把已有 `approvalRemembered{tool, scope:"tool", by}` 改成带具体规则的事件，但没有说明旧日志怎样归约。会话日志按格式 1 回放；Spec 要求事件字段只加不改，改变已有字段语义必须升格式并迁移。当前内核打开时直接用 `reduceSessionKernel` 重放，旧事件仍会到达新 reducer。
- **为什么是问题**：升级后已有会话的记忆要么丢失、要么被错误解释；旧事件代表“整个工具已批准”，不能无声解释成新的窄命令规则。该设置跨重启生效，回放偏差会改变用户已经作出的权限选择。
- **如何核实**：取现有日志中的 `approvalRemembered` 数据 `{tool:"lab.write", scope:"tool", by:{kind:"user"}}`，按格式 1 重开；计划未给新 reducer 对缺少规则字段的处理。`session.ts` 的 `forkSession` 只复制 path 事件、最后 `profileChanged` 与 `settingsChanged`，不复制 `approvalRemembered`；新规则“本会话”是否随 fork 继承也未约定。
- **建议改法**：明确旧事件保持旧的整工具语义，或新增事件名/版本并给出受支持的历史迁移；同时明确并测试 fork 不继承会话级批准记忆（更符合“本会话”范围），避免实现者把它误塞进 path。

### 5. 自动审批模式的判定步骤与失败语义没有写入流水线

- **严重程度**：重要；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:34,104,109-110`；`.agents/works/w00032-agent-integration/tasks/t06-approval/README.md:54-56`
- **现象**：Task 已定 `auto` 为交审批模型，内核 `ApprovalCtx` 已提供 `model`；计划在“没命中”时只写“按审批模式”，却没有说 `auto` 怎样调用审批模型、模型结果如何解析、拒绝/格式错误/超时/中止怎样结算。现有 `approveByMode` 将除 `yolo`、`allow-writes` 外的调用都返回 `ask`，没有实现自动评审。
- **为什么是问题**：照计划替换 `approveByMode` 很容易让 `auto` 退化成人工询问，或把模型调用失败当作放行；二者都违背 t06 的既定审批模式合同。审批模型请求还会进入日志、用量与中断恢复，不能只定义一个布尔结果。
- **如何核实**：逐行对照 README 决定 1 与 2026-10-30 改判、内核 `ApprovalCtx.model` 和当前 `approveByMode`。计划验收列了 `yolo` 与模式闸门组合，没有 `auto` 的批准、拒绝、无效输出与失败场景。
- **建议改法**：在规则未命中分支定义完整的四模式决策表；具体规定 `auto` 的审批请求格式、可解析的判定类型，以及模型失败一律拒绝还是转人工询问，并将其纳入真实内核合同场景。

### 6. 模式状态、fork 继承与即时提醒没有可落地的内核接口

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:89-99,104,111`；`packages/nb-harness/src/kernel/api/model.ts:140-149`；`packages/nb-harness/src/kernel/helpers/reminder.ts:1-7,21-39`；`packages/nb-harness/src/kernel/session/session.ts:552-595`
- **现象**：计划称模式是“会话级设置”，但没有指定写入 `CoreSettings`、某个扩展的 `settingsChanged`，还是新的事件/状态接口。当前核心设置只有 `approvalMode` 与 `readOnly`；审批钩子只能从 `ApprovalInfo` 取得这两项，或用 `ApprovalCtx.read` 读当前装配中已有扩展的导出。`reminder()` 只在 `turnStarted` 触发，不能单独保证模型调用 `switch_mode` 后同一轮下一次请求前立即收到完整提醒；用户在运行中从菜单切换也没有定义提醒如何进入该轮。`fork` 的现有行为只带路径、Profile 与 settingsChanged。
- **为什么是问题**：照计划实现时，UI、模式闸门、提醒与重启恢复可能各自读写不同状态；若把模式记在 path 扩展片，回退会切回模式，违反决定 7；若另建 session 事件，fork 当前不会继承它；若仅用 `Reminder` helper，模式切换后同轮模型请求前不会触发。计划声称即时生效与会话级持久化，却没有界定这些结果。
- **如何核实**：检查 `CoreSettings`、`ApprovalInfo`、`reminder()` 的实际触发点和 `forkSession` 的复制集合；没有一个现存 `mode` 字段或通用宿主 API 能同时完成用户命令更新、审批读取与对话提醒。
- **建议改法**：指定模式状态的唯一 owner 和持久事件，明确回退、重启、fork 的继承语义及前端快照投影；定义 mode-change 提醒的写入时点与载体，覆盖工具切换、审批批准后和用户运行中切换。若模式用 `settingsChanged` 表达，要把它纳入 fork 的设置复制与会话状态恢复合同。

### 7. `subjects(args)` 的声明位置与未激活工具行为未定义

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:40-49,63-65,104`；`docs/specs/agent/contributions.md:39,42,59`；`packages/neuro-book/src/plugins/agent/backend/tools.ts:113-124`
- **现象**：计划让工具声明 `subjects(args)`，但 Agent 工具贡献声明当前是可序列化字段，参数相关的 `effect(args)` 放在实现里；未激活提供方时只用静态声明的 effect，第一次执行才激活。计划没有定义 subject 提取器属于声明还是实现，也没定义提供方未激活、禁用或提取器抛错时，按参数的 deny 规则怎样保持有效。
- **为什么是问题**：若把提取器放在实现，预审批时可能没有它；按参数的 `deny` 规则就会变成“无 subject/不匹配”，随后在 `yolo` 下放行。若为了取 subjects 提前激活插件，则改变了现有“声明可读、工具首次执行才激活”的生命周期，并把插件激活副作用放到了审批前。
- **如何核实**：当前 `AgentToolDeclaration` 是 TypeBox 序列化声明；`AgentTools.#declaration` 只在 provider 已发布时调用实现的动态 `effect`，否则回到静态值。计划的 `subjects` 无生命周期和错误策略，不能据此保证 MCP/第三方工具的参数拒绝规则。
- **建议改法**：把 rule-critical 的 subject 提取逻辑定义为可在工具未激活时读取、可校验的声明合同；若提取失败或声明不可用，deny 规则不得被当作未命中。若需提前激活，明确其失败结算与资源收口，并调整现有懒激活合同。

### 8. 贡献的 Matcher 异常或停用会让拒绝规则失效

- **严重程度**：重要；**类别**：安全与性能
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:54-65`
- **现象**：计划允许插件通过 `agent.permissionMatchers` 扩展 Matcher，且写明未知类型“规则不生效并写诊断”。没有规定插件被禁用、未知 matcher 类型、实现抛错或返回非法值时，正在引用它的 `deny` 规则怎样处理。
- **为什么是问题**：如果上述情况按“规则不生效”跳过，规则列表继续到 `yolo` 或 `allow`，禁用一个插件即可让依赖该 matcher 的拒绝规则放行。给拒绝规则提供的扩展点不能通过异常或加载状态改变其语义。
- **如何核实**：构造 `action:"deny"` 且 matcher 类型由一个插件贡献的规则；让 matcher 不可用或抛错。按计划现有“未知类型不生效”会跳过这条规则，后续模式照常执行。
- **建议改法**：定义按 action 分级的失败语义：拒绝条件无法求值时至少拒绝当前调用；allow 条件无法求值可安全地视为未命中；ask 条件无法求值则必须进入询问或拒绝。错误需诊断且不能由后续放行规则覆盖。


### 9. 闸门按工具 effect 无法兑现临时目录豁免与 plan 文件写入

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:32-36,49,79-80,91-95`
- **现象**：模式闸门依据这次调用“算写”决定，且计划明确 shell 只有全部子命令只读、没有写重定向时才是 `effect: read`，其它调用算 `exec`。但已定合同明确 `discuss`/`plan` 下写临时目录与会话目录不算写；`discuss` 要放行这类写入，`plan` 还必须能写 `session://plan.md`。仅凭 effect 的 `read|write|exec` 无法区分 project 写与 session/tmp 写，也无法区分 discuss 可写的 scratch 与 plan 专属文件。
- **为什么是问题**：照流水线实现时，`echo x > session://scratch.md` 和 `write({path:"session://plan.md"})` 都被闸门拒绝；若为满足计划文件而放开所有 `session://` 写，discuss 又会有权写 plan.md，违反讨论模式边界。`yolo`、allow 规则均按计划不能越过闸门，不能补救这个模型缺口。
- **如何核实**：将上面两种资源地址交给计划中的 `write`/shell 判定：`write` 固定声明 effect 为 `write`，重定向命令因为有写重定向是 `exec`；门闸没有地址类别字段或 mode-specific path predicate。现有文件服务将 `session://` 展开成 `sessions://<id>/home/...`，计划也将 `tmp://` 展开到独立的 temps 方案。
- **建议改法**：闸门必须基于归一化后的资源目标与操作类别，而非单一工具 effect；写规则至少区分项目内容、会话 home、临时目录与计划文件，并写出 discuss/plan 各自的路径矩阵。shell 重定向与文件工具共用同一资源分类，不允许对整类 `session://` 做宽泛豁免。


### 10. 只读清单允许常见会改当前工作目录的 shell 命令

- **严重程度**：重要；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:73-80`
- **现象**：计划称“全部只读”才将 shell effect 设为 `read`，但没有定义只读清单判定的全部隐含状态效果。比如 `cd /tmp && cd -` 会切换当前 shell 工作目录并可能让之后命令在作品目录执行；`git status` 在仓库缺少 `.git/index`、锁文件或刷新索引时会写 `.git`；`git log` 的分页器、外部 diff/credential helper 等可启动有副作用程序。列表只举 `git log`、`find`、`sed` 等命令与选项，未定义工作目录/环境/配置副作用、子程序调用与当前仓库元数据写入如何影响“只读”。
- **为什么是问题**：开发者要求 discuss 只能执行只读 shell；只读命令清单是模式闸门的唯一依据。清单把普通的查询命令名当作纯读会让 `discuss` 下工具被视为读而直接越过闸门；“规则不是安全边界”不改变模式合同必须正确分类常见行为。
- **如何核实**：在隔离的真实 Git 仓库与真实 shell 下分别执行 `git status`（移除 `.git/index` 后）和含 `cd -` 的复合命令，观察索引文件及最终 cwd；比较计划当前清单没有对这些状态副作用作判定的分支。代码尚未实现，本审查没有在工作区执行写实验。
- **建议改法**：将只读清单定为“所有可观察副作用都只读”，明列 cwd/环境/仓库索引与外部 helper 等状态；将不确定或能执行子程序的形式归为非只读。把这类真实运行场景列入白名单验收，而不是只测命令名表。
### 11. 作品权限规则的热读取与现有作品规则文件语义冲突

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:63,66`；`docs/specs/agent/builtin-profiles.md:43,52-53`
- **现象**：计划按项目、用户、会话拼接规则，但没有定义项目规则的独立机器格式、文件路径或缓存失效时机。现有作品规则入口是 `project://AGENTS.md`：它是任意自然语言提示，只在建会话与压缩后加载，fork 复制旧内容；并非每次工具调用都读取的规则表。
- **为什么是问题**：若复用 `AGENTS.md`，审批器无法可靠解析其非结构化内容，且刚改的拒绝规则会在审批时立即生效、模型上下文却仍含旧指令；fork 后两者更会分叉。若另建规则文件，计划漏了文件名、schema、改动监听和读取失败语义，后续切片无法照字面实现。
- **如何核实**：对照计划的来源顺序与现有 builtin-profiles Spec 输出 4、5；后者规定 `AGENTS.md` 内容入 opening，建会话/压缩读取，不是审批规则解析器。
- **建议改法**：明确这是独立的结构化权限规则文件及其 TypeBox schema；写清新建/改写/删除如何使下一次审批读到新版本、读取失败如何 fail closed，以及它与提示用 `AGENTS.md` 各自的用途。若意图共用 `AGENTS.md`，须先定义可无歧义解析的子格式与双层生效时序。
### 12. 用户询问规则会使“本会话都批准”永远不生效

- **严重程度**：重要；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:66,83-85`
- **现象**：全局按项目、用户、会话拼接，首条命中；“本会话都批准”写入会话规则。若用户已有 `action:"ask"` 规则，同工具每次先命中用户 ask，永远到不了后面的 session allow。项目 ask 也会遮住 session allow。
- **为什么是问题**：对用户主动选择的“本会话都批准”按钮而言，它应停止本会话重复询问；计划既将 session 规则放到用户规则后以免覆盖用户 deny，又没有让它覆盖 ask 的优先级模型，选择在常见配置下是空操作。
- **如何核实**：创建用户规则 `{tool:"nbook.agent.write", action:"ask"}`，再按计划追加相同工具的 session allow；下一次从上到下仍先命中 ask。此时重复操作会再次弹向导。
- **建议改法**：将拒绝作为跨层硬优先级，其他动作再按层级和顺序选择；至少定义 session allow 可覆盖项目/用户 ask、不能覆盖任一 deny。验收覆盖用户 ask + 本会话批准、用户 deny + 本会话批准两例。
### 13. `modeWriteAction:"ask"` 后的规则放行会穿过模式闸门

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:29-36,95`
- **现象**：流程先把讨论/计划模式下写调用的闸门结果改为询问（配置为 `ask` 时），随后第 5 步又规定规则结果 `allow` 或 `ask`“照办”。同一写调用命中 allow 规则时，后一步仍会执行 allow；这与开发者决定“discuss、plan 下全部放行与放行规则都过不了模式闸门”相反。`modeWriteAction:"ask"` 与普通规则/yolo 产生的 ask 也没有区分来源。
- **为什么是问题**：用户开启“闸门改弹审批”后，放行规则仍能免审写入；这把闸门变成可被规则绕过。若把闸门 ask 当普通 approval-mode ask，`yolo` 还可能将它自动放行；若特殊处理，则需有独立判定来源，计划没有定义。
- **如何核实**：照步骤 3、4、5 顺序代入 discuss + `modeWriteAction:"ask"` + 命中 `action:"allow"` 的写命令：步骤 4 得 ask，步骤 5 的 allow “照办”使执行。代入 yolo 时也没有标记该 ask 是模式强制还是普通规则询问。
- **建议改法**：为决策结果使用来源区分的联合类型（规则、模式闸门、审批模式）；模式闸门的 ask 必须压过 allow，并且不得由 yolo 自动放行。先实现并列出规则 deny/ask/allow × mode deny/ask × yolo 的决策表，再据表编码流水线。
### 14. `path` Matcher 没定义地址归一化与 `access` 来源

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:43-60`
- **现象**：Subject 的 path 只带 `address:string`，Matcher 以 glob 和可选 access 匹配；没有说明它匹配调用参数里的原文、Agent 展开的全局地址，还是解析符号链接后的真实路径。绝对路径、相对路径、`session://` 与等价 `sessions://<id>/home/` 的匹配结果也未定义；大小写、Unicode 规范化与 Windows 路径大小写同样空缺。
- **为什么是问题**：同一目标可以用单数地址、全局地址或 shell 地址替换写入；若按字符串匹配，给全局路径配置的 deny 可以被单数地址绕过。若按真实路径匹配，计划目前的 `subjects(args)` 没有资源解析能力合同，也无法说明链接目标变更时稳定性。
- **如何核实**：对照资源 Spec 的地址等价规则及 `sessionResources.expand()`：`session://x` 展开为 `sessions://<当前会话>/home/x`，而文件服务另行跟随链接定位目标。计划的 `Subject.path.address` 与 `Matcher.path.glob` 没说明在哪个阶段取值。
- **建议改法**：规定唯一匹配层：解析合法资源地址后匹配规范全局地址，写入授权再按文件服务真实目标复核；定义大小写/Unicode 语义及无效/相对路径如何处理。重定向与文件工具必须走相同归一化器。
### 15. 命令 Matcher 的 pattern 未定义对应单条 argv 的匹配方式

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:54-60,77-80`
- **现象**：Rule 的命令 pattern 示例是 `"git push *"`，但 shell 方案先把复合文本拆成 `SimpleCommand{argv}`，剥包装、剥环境变量前缀、解析 `bash -c`，并将绝对路径基名化。计划没有说明 pattern 是匹配 argv 数组前缀、单条命令的序列化文本，还是重组后字符串；未定义引号、空格、通配符、参数中 `*` 与空参数的边界。
- **为什么是问题**：同一规则在拆分前匹配整串、拆分后匹配每条命令、或匹配 argv token 时结论不同；实现者会自行挑语义，导致 `git push *` 可能放过 `git -c … push`，也可能因空格/引号而误拒。审批记忆也复用此前缀规则形状，含糊会影响权限范围。
- **如何核实**：将示例 `git push *` 分别应用于 `git push origin main`、`git push`、`git -c x=y push origin main`、`git 'push' origin main`；计划没有能唯一决定这些结果的语法定义。调研中的 Codex 明确按 argv 前缀，Claude/omp 明确按 shell 命令文本/分段，参照并非可互换。
- **建议改法**：为 `command.pattern` 选择并写明一种结构化语义（建议 argv token 前缀加 glob token），明确拆分后每段独立匹配及包装归一化边界；给带引号、空参数、选项前置、绝对路径的合同样例。
### 16. “未声明 effect 默认 exec”与既有工具声明合同冲突

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/README.md:45`；`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:40-49`
- **现象**：Task 决定写“工具没声明按执行”，但既有 `ToolDeclaration.effect` 是必填字段，Agent `agent.tools` 声明 schema 也强制必填。Plan 又说工具可省略 `subjects`，却未区分 effect 缺失与 subjects 缺失；MCP/第三方是否进入同一声明入口也未定。
- **为什么是问题**：实施者可能把“未声明 effect”当作可配置兼容值并放宽公开类型/schema，或只在某类工具上默认 exec，产生两个判定合同。若外部工具确实没有 effect，计划没有说明拒绝、诊断、执行默认等级和规则匹配优先顺序；dynamic effect 失败则现有桥接回退到提供方固定声明，声明不保守时仍会低估风险。
- **如何核实**：`ToolDeclaration.effect` 是非可选字段；`AgentToolDeclarationSchema` 的 `effect` 必填；第三方声明可序列化 effect，激活后实现可给动态 effect，动态函数抛错时 AgentTools 回退固定值。Task README 的默认 exec 决定未说明如何覆盖这些合同。
- **建议改法**：保留必填 `effect` 合同，或作为明确的公开 schema 变更同时覆盖插件、MCP 与内核工具声明；缺失/计算失败的行为按最严 `exec`，不得回退到更宽松等级。区分“不提供 subjects”与“effect 不存在”。
### 17. 方言解析失败时仍允许文本规则放行，无法实现“看不懂不放行”

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:73-80`
- **现象**：对于解析不出的命令，计划只规定 allow 规则“不生效”，但 ask/deny 仍按原文本匹配；没有命中时回到模式判定。若用户处于 `yolo`，或命令 effect 被错误算成 read，这条不透明命令仍可放行。开发者原话明确要求适配新工具时“解析不了就不放行”。
- **为什么是问题**：纯文本的 `deny`/`ask` 匹配不能证明不透明 shell 内容安全；在完全访问模式下它会落回放行。把它描述为“allow 规则不生效”弱于需求要求的不可放行兜底。
- **如何核实**：使用 `eval "$cmd"` 或命令名含变量展开、方言 parse 返回 `{opaque:true}`；无文本 deny/ask 命中且审批模式 yolo 时，计划没有拒绝分支，最后按 yolo 放行。`xargs`、`find -exec`、`eval` 已被列为 opaque 类型。
- **建议改法**：opaque 必须成为流水线中的独立强制结果：deny，或按用户明确可配置的安全策略进入人工审批但不能被 yolo/allow 绕过；区别“ask 是需要用户决定”与“规则 ask”。对解析器异常与方言未知采取同一保守结果。
### 18. 固定包装只剥一层会漏掉嵌套包装中的副作用

- **严重程度**：重要；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:77-79`
- **现象**：计划要求“剥一组固定包装”，但未定义重复剥离直到稳定、选项解析或递归语义。常见命令 `timeout 5s env X=1 nice rm file` 或 `command timeout 5 rm file` 只剥一层时仍以 `env`/`command`/`timeout` 为基名，危险命令规则不命中；空的包装选项也会改变实际 argv。
- **为什么是问题**：shell 的只读分类与 deny 规则都依赖剥包装后命令；若解析到中间层而不是最终执行体，`discuss` 可能把带写操作的包装链当成只读，显式拒绝也会失效。
- **如何核实**：计划列出的包装包括 `timeout`、`nice`、`nohup`、`command` 等，但未定义一个命令含多个包装时的循环剥离与参数边界；按只剥一次的解释，上述命令无法匹配 `rm`。
- **建议改法**：定义包装 AST/argv 归一化为有界递归过程，只有在能精确识别包装语法与其命令位置时继续剥；未知选项或参数形式返回 opaque，并依第 17 条保守处理。
### 19. discuss 下只读 shell 仍可经临时文件读写作品内容

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:77-80,91-95`
- **现象**：计划把 `write` 重定向目标交 path Matcher，且 `/dev/null` 除外；但未定义 shell 写入再读回的临时文件流水线如何判定。常见 `git show HEAD:file > /tmp/copy; cp /tmp/copy project://chapter.md` 的第一个命令可能被白名单认成读（写临时文件不算项目内容写），第二个 `cp` 的重定向目标不是语法重定向，subject 只能覆盖 `cp` 命令文本，工具 effect 为 exec；若清单把 `cp` 或相关形式放入只读 allow，项目写入可逃过按目标路径的闸门。
- **为什么是问题**：讨论模式的目标是禁止修改项目，不只是拦截直接 `>` 到项目地址。临时目录许可与 shell 自由组合时，直接写目标扫描不足以覆盖从 scratch 到 project 的常见两步操作。
- **如何核实**：将命令拆成计划要求的两条 SimpleCommand：第一条写 `/tmp`，第二条以 `cp` 为 argv、目标 `project://...` 经地址替换成绝对路径。计划的 `SimpleCommand` 只有 `redirects`，不包含 `cp` 的文件操作目标；rule subject 也只提供 command/path 声明，没定义此命令如何提取输入输出路径。
- **建议改法**：模式闸门必须拦所有不能证明目标副作用只限 scratch/session 的写命令；`cp`/`mv` 等按参数声明来源与目标 path subjects；无法可靠提取时不能当只读，也不能用工具名 allow 覆盖项目内容写入。
### 20. “消息注入不影响缓存”不能推出完整提醒的实现不破坏前缀缓存

- **严重程度**：建议；**类别**：安全与性能
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:97`
- **现象**：计划由“消息而非 system prompt”直接推断“缓存不受影响”，却要求切换时完整提醒、之后每轮短提醒、normal 退出提醒，未定义这些消息是一次性对话事件还是每轮动态槽，也未定义插入位置。现有 `reminder()` 会在 `turnStarted` 写进当前轮消息；缓存能否复用取决于消息在已有前缀之后的位置与稳定性，而不只看它是否位于 system 字段。
- **为什么是问题**：如果完整提醒每轮重写或放在已缓存历史之前，消息缓存会失效；每轮短提醒内容随模式/状态变化也会改变前缀。计划引用 Claude Code 的做法，但调研只说明其消息注入与缓存-safe 文档，不证明 NeuroBook 当前 `computeRequest` 的任意消息布局都保持缓存。
- **如何核实**：当前请求缓存按提交轮的 block keys 与消息前缀工作；`computeRequest` 依据 Profile 模板决定 history/turn/slot 顺序。计划没有指定提醒事件、消息位置或稳定键，无法由“非 system”推出缓存不变。
- **建议改法**：将缓存主张改为可观察合同：定义完整提醒只在模式变化时追加一次、短提醒的实际插入位置与内容稳定规则；验收连续同模式多轮时稳定前缀保持，切换时只从提醒的插入点之后失效。若无法保证，就删去“缓存不受影响”的承诺。
### 21. 可贡献 command dialect 没有约束 parser 与只读分类器的一致性

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:70-80,104`
- **现象**：`agent.commandDialects` 允许插件提供 `parse()` 与 `readOnly()`，但没有定义其输入/输出验证、错误处理、版本/优先级或与 `subjects`、规则 Matcher 的对应关系。插件可返回 readOnly=true 同时把写命令解析为空/遗漏子命令，规则系统没有契约保证解析树覆盖所有会执行的命令。
- **为什么是问题**：新增方言（例如 SSH 的 PowerShell）是可信代码，但该贡献点直接控制模式闸门与规则拒绝的判定。若解析器漏掉 `$(...)` 子命令、重定向或嵌套语句，deny 规则可能看不到实际副作用；仅靠贡献者约定无法维持“拒绝规则不能失效”。
- **如何核实**：计划定义 dialect 接口为 `parse(text)` 与 `readOnly(SimpleCommand)`，没有要求解析结果保留未解析子树或完整覆盖证明，也没有规定 parser/readOnly 抛错、异步、非法结果与 unknown dialect 的 fail-closed 行为。
- **建议改法**：将每个执行节点与 opaque 残余保存在解析结果；仅当解析完整且所有节点都通过副作用分类才算只读。贡献校验需拒绝非法/抛错结果，拒绝规则无法求值时优先拒绝；Dialect 有明确版本与诊断 owner。
### 22. Matcher 贡献点无法在插件撤回后保证拒绝规则继续权威

- **严重程度**：重要；**类别**：不变量
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:65,104`
- **现象**：规则允许 `agent.permissionMatchers` 增加匹配类型，但没有说一个 matcher 插件撤回/禁用时，已加载的规则保留编译结果、重新求值，还是变成未知类型。Agent 插件当前可因提供方撤回而重装扩展；工具声明在未激活时仍可见，matcher 没有对应生命周期安排。
- **为什么是问题**：被用户明确写成 deny 的规则不能因插件生命周期变化自动消失。若实时列表不再含 matcher，计划“未知类型规则不生效”会让调用落到 allow/yolo；若保留闭包则可能继续调用已撤回插件代码，违反资源释放合同。
- **如何核实**：按计划的扩展贡献点模型撤回提供 matcher 的插件，再评估带该 type 的 deny 规则；当前没有定义快照、版本或撤回时的策略，两个可实现行为都违背其中一项既有合同。
- **建议改法**：在装载规则时校验并编译 matcher 到版本化、纯数据的执行器；撤回后对引用它的 deny 规则 fail closed 并诊断，不能静默删规则。设置界面需指出失效规则，恢复插件后再启用。
### 23. 模式闸门会拦截它自身的退出调用

- **严重程度**：阻断；**类别**：正确性
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:32,95,98-99`
- **现象**：`switch_mode` 改变会话状态，应视为写/状态变更；但流水线规定 discuss/plan 下每个写调用先被模式闸门拒绝并提示切换模式。模型在 plan 下调用 `switch_mode{mode:"normal"}` 时，闸门会先拒绝该请求，永远到不了“显示计划全文、批准并开始/继续改”的退出向导；discuss 下请求进入 plan 也同样自我阻断。
- **为什么是问题**：计划把模型申请模式切换作为唯一模式专用工具流程，却没有定义闸门豁免，导致计划的主路径不可达。靠用户菜单直接切 normal 不等价：模型无法提交计划，批准退出行为不发生。

### 24. 批准计划后不清上下文且“开始”没有实现阶段提示

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:93,97-99`
- **现象**：plan 文件写入 `session://plan.md`，退出向导可“批准并开始”，但明确不清上下文，计划没有说批准结果怎样把全文交给 normal 模式下一次模型请求，也没有说明此前计划提醒如何撤销、计划文件是否保留或模式如何改变。现有压缩 restore 只把 `session://plan.md` 作为文件放回；它不会自动成为实现任务消息。
- **为什么是问题**：用户批准的是待执行计划，但若只把模式从 plan 切到 normal，下一轮模型只看到原对话上下文与文件地址，可能继续规划、未读计划或执行了用户刚改的内容。Claude Code/omp 调研的批准都把计划正文或稳定引用明确注入实现阶段；本计划没有对应接口。
- **如何核实**：对照计划的退出选项与 compaction Spec 输出 8；后者仅在压缩后放回计划文件，不提供批准事件或实现阶段消息。Plan 未列任何新事件、输入缓冲区操作或模式提醒承载批准正文。
- **建议改法**：批准时在切回 normal 的同一写入批写入一条带计划快照/哈希的明确实现指令或批准提醒，并定义之后修改计划文件是否影响已批准版本；“继续改”必须保持 plan 且不产生实现指令。
### 25. 把匹配细节和拒绝理由交给模型会泄露策略并诱导探测

- **严重程度**：建议；**类别**：安全与性能
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:54,63-65,79,97`
- **现象**：计划允许 Rule `reason` 写进拒绝文字，让模型知道“怎样改”，且规则既可匹配 `image-gen` prompt 关键词、也可匹配主机/命令参数。没有区分面向用户的诊断与发送给模型的反馈，也没有对命中词、内部路径/主机名或拒绝规则内容做脱敏策略。
- **为什么是问题**：模型可通过反复改写提示词/命令探测哪些关键词触发 deny，策略信息会进入持久对话历史并在后续请求复用；若 reason 含内部主机、路径或组织规则，会直接暴露给模型上下文。规则作者无法控制其文本对模型的披露范围。
- **如何核实**：计划明确 `reason` 写进给模型的拒绝文字，且匹配器支持关键词、path 与 host subject；没有审计/隐藏字段或用户可见与模型可见两种文案。
- **建议改法**：把拒绝理由分为模型安全提示与本地用户诊断；默认仅给模型不泄漏条件的通用提示，详细原因只显示用户端。若产品决定让模型得知具体规则，明确该数据进入日志/压缩上下文及其安全边界。
### 26. 验收映射留空，核心不变量缺少可执行场景

- **严重程度**：重要；**类别**：测试
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:114-120`
- **现象**：计划把“验收映射”留作 Spec 写完后补；当前仅列少量样例，未覆盖首条优先级的来源组合、modeWriteAction 与规则 ask/allow/yolo 交互、approve-session 规则范围、分支/fork/重启状态、并行工具切换模式与拒绝规则、matcher/dialect 撤回或抛错。
- **为什么是问题**：这些是本次设计最容易照字面产生错误的合同，且只靠一条端到端真实模型 smoke 无法稳定触发指定工具顺序/边界；若等 Spec 之后才映射，Spec 很可能照实现补写，遗漏会被固化。
- **如何核实**：把已列判据与计划第 29-100 行逐项对应；验证段只覆盖 image-gen、复合命令、项目 allow、会话规则、各档工具、yolo+plan、未知方言与模型冒烟，无法定位上述失败场景的测试判据。真实运行时合同测试可以脚本化模型端点指定多个工具调用，不需 e2e。
- **建议改法**：Spec 前先列黑盒决策矩阵，至少覆盖流水线组合、会话记忆边界、模式变更时序与 fail-closed 贡献失败；每项映射到内核+真实文件/本机端点的合同测试。UI 向导外观另映射组件测试，不以真实模型随机行为验权限核心。
### 27. 新贡献点缺少应用注册与公开 SDK 接入切片

- **严重程度**：重要；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:65,70,102-112`
- **现象**：计划定义 `agent.permissionMatchers`、`agent.commandDialects` 并说 `agent.contributions` 加两个贡献点，但实施切片没有写更新应用的贡献点表、插件描述或 SDK 公开入口。当前 Agent 插件只登记四个贡献点，`@notnotype/nb-plugin-sdk/agent` 也只导出既有四组工具/扩展/Profile 助手。
- **为什么是问题**：仅更新 Spec 与 matcher 注册表不会使第三方插件贡献进入运行时；跨插件实现必须经 SDK 公开子路径，不能依赖深导入应用源码。实现者照切片完成后，内置规则能跑但第三方扩展无法贡献，与明确的可扩展需求不符。
- **如何核实**：检查 `agentBackendPlugin.contributionPoints`/`receives` 与 `src/sdk/agent.ts` 导出；当前清单只有 extensions/tools/profiles/compactionMethods。计划切片 1–5 没有 SDK 类型、助手、构建入口或 surface 测试更新项。
- **建议改法**：在切片中明确新贡献点的公开声明 schema、助手函数、服务端注册/接收、SDK 导出与 SDK surface/打包合同测试；不把贡献点只实现成 Agent 内部 matcher 表。
### 28. 审批等待期间模式改变不会使已批准调用重新判定

- **严重程度**：阻断；**类别**：并发与状态
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:32-36,98`；`packages/nb-harness/src/kernel/run/tools.ts:264-280,310-315`
- **现象**：同一回复先完成审批判定并创建 waiting 事项，用户等待期间可以从另一个窗口或菜单切换模式；恢复后内核对已批准项的 `stillHolds` 只比较 `readOnly/approvalMode`，不比较新 Agent 模式。若先在 normal 允许写，等待另一个工具审批时用户切到 discuss，之前放行的写调用仍会执行。
- **为什么是问题**：计划称模式是会话级、切换立刻生效且模式闸门决定是否写；但等待期间已经通过闸门的调用跨越模式状态变化。工具可能在用户显式进入“只讨论”之后落盘，违反模式不变量。
- **如何核实**：按内核真实流程构造同一回复两个工具：第一个写调用初次判 allow，第二个 ask 使运行 waiting；等待时执行模式变更，再批准第二项。当前内核的二次校验不看扩展模式。计划没有为模式代次或 in-flight approved calls 定义语义。
- **建议改法**：将模式代次/模式值纳入 judgment 快照，在写入 `toolStarted` 前若变化则重判；或者规定运行中模式切换排队到当前回复所有工具结算之后，并在 UI 显示待生效。验收须用真实等待交互覆盖该顺序。
### 29. `modeWriteAction` 可配置但没有配置 owner、范围与生效时点

- **严重程度**：建议；**类别**：接口与合同
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:95,104,112`
- **现象**：计划只给出 `modeWriteAction: "deny" | "ask"`，没有说明它是用户全局、Profile 初值、还是会话设置；没有列入设置 schema/事件/界面位置，也未说明运行中修改何时生效。现有 Profile 设置、会话 `CoreSettings` 与全局 Agent 设置是不同的 owner 和生命周期。
- **为什么是问题**：同一个字段可能被实现为各会话共享配置，也可能作为会话快照持久化；改动会影响已打开会话、回退与 fork 的行为。未定义生效边界会导致宿主 UI 展示值与内核闸门使用值不一致。
- **如何核实**：计划只在模式段落提出字段，在 Spec 改动清单、切片与验收映射中没有设置 owner、持久化位置或运行中变更场景；当前 `agentSettings` 和 `CoreSettings` 都没有该字段。
- **建议改法**：明确配置 owner、默认值、用户入口、是否允许作品级覆盖，以及会话内修改/运行中的生效时点；选择现有设置合同或新增正式事件，不保留无来源的实现变量。
### 30. 项目规则可询问或拒绝却未定义作品信任门槛

- **严重程度**：建议；**类别**：安全与性能
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:63,66`
- **现象**：项目目录规则只禁止 allow，但允许作品自行声明 ask 与 deny；没有定义项目路径是信任作品身份、是否要用户确认该规则文件，或作品规则是否可限制宿主级工具/MCP/主机 subjects。
- **为什么是问题**：作品文件可由外部来源、同步或版本控制更新。deny 可能把用户工具永久封死，ask 可增加审批频次；若 matcher scope 可指向主机或第三方工具，作品作者还可影响非作品资源。将拒绝视为安全有利不等于项目内容应无条件控制全局会话行为。
- **如何核实**：计划规定工具通配覆盖第三方与 MCP，subject 也可扩展 host；项目规则只限制 action allow，没有限制可匹配的工具/subject 命名空间或信任确认。
- **建议改法**：为项目规则定义作用域，只能约束会话中访问当前作品内容的工具/路径；全局用户 deny 始终权威。说明不可信/未确认作品的项目 ask/deny 是否加载，并以真实作品切换测试核对旧项目规则不会污染另一作品会话。
### 31. 退出 plan 向导展示当前文件而非生成计划时的版本

- **严重程度**：建议；**类别**：并发与状态
- **位置**：`.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md:93,99`
- **现象**：向导退出 plan 时“显示计划全文”，来源是可由 Agent 写入、shell 修改或外部编辑的 `session://plan.md`；没有规定文件读取与批准之间如何固定版本、检查冲突或防止内容变化。审批确认后的实际执行仍可读取变更后的文件。
- **为什么是问题**：用户可能看到并批准版本 A，但在确认前并发工具已写成 B，或确认后模型读到 B 执行；批准记录与实际执行计划不再一致。规则声明“计划写 session 文件”并没有冻结文件或建立审批快照。
- **如何核实**：按计划向导读取全文后，模型仍可通过工具调用改写同一地址；内核 `ToolContext.read`/资源写入未与向导审批建立文件基线。计划没有文件哈希或批准版本字段。
- **建议改法**：打开退出向导时读取正文与内容哈希；批准提交时核对哈希仍一致，不一致则重新展示；将批准的正文/哈希固定进批准事件与下一轮实现提醒，执行阶段不得静默换用新文件。
