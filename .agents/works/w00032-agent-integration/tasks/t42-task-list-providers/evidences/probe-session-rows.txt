结论（按它核对 sessions.md 输出 30、jobs.md 输出 20 的 planned 句子，没有不符的）：

1. 收口时排着的话（followup）：运行中排进去的话被同一次运行接着消费（inputConsumed 带同一个 runId），不另开运行；会话行的 runId 不变。
2. 新的一次运行之前总有一帧 idle 状态：按状态帧记 runId 时，换运行一定经过空闲，开始时刻在第一次看到新 runId 时取。
3. 用户停止并保留排队（abort keepQueue）：runEnded reason=aborted、inputHeld heldBy=user；之后 activityWithBackground() 为空、activity() 给 held。放行后开新运行（新 runId），held 消失。所以“有留着的话等你放行”的行要会话表另交 held，它没有在跑的运行。
4. 前台子代理（同步派发）等你批准：父会话 status=running（表里算在跑，不算等你）；子会话 status=waiting、pending=[approval]、questions=caller，表里算等你（activity 里 waiting）；任务 state=running、foreground=true，target 的 runId 与子会话此刻的运行相同。子会话不是后台会话。
5. 后台子代理等你批准：父会话已空闲；子会话 waiting（approval）；任务 running、foreground=false。根会话空闲时没有组头行，块里只有任务行。
6. 后台子代理向父 Agent 提问：父会话这时可能还在跑、也可能已空闲（两次运行各见一种，看提问与父会话收口谁先）；任务 state=question；子会话 status=waiting、pending=[question]，但 questions=caller，表里算在跑（activity 里 running）。
7. 只送了短回执（预算满）与永久送不到：从代码核对（delivery.ts #send）：两条路都先 jobs.announce 再 jobs.receiptSettled，后者发 onChanged；出口变成 announced，任务留在表里只等 wait。清单按出口不列它，变化有通知。
8. 合并提醒被 wait 撤回一件时（delivery.ts #returnOthers），其余几件的出口经 unclaim 从“提醒已受理”退回“还没领”，unclaim 不发变化；它们重送遇到暂时失败时再 unclaim，也不发。清单要另有一个变化信号覆盖 claim、unclaim、announce、attach：不能让它们发 onChanged，送达订着 onChanged、每次都重排一轮，暂时失败时会绕过退避连续重送。
