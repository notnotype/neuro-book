# w00032 t42 计划第 1 稿与 planned Spec 设计审查

### 1. 清单只裁结束行，合法的全在跑快照仍发不出去

- **严重程度**：阻断；**类别**：正确性。
- **位置**：`plan.md:73,87–90`；`docs/specs/workbench/background-tasks.md:146,174–179`；`docs/proposals/unified-background-tasks.md:76`。
- **现象**：一家交出 200 行，全部 `running`；每行标题 200 个常用汉字、进展 500 个、种类名 200 个。每行这三段共 2,700 字节，连其余小字段仍低于 4 KiB；整份光文字就有 540,000 字节，超过 524,288 字节，还没算 `groups` 和 `background`。可裁的结束行是 0。多家时，一家只要有足够在跑的行，也能让其它家的更新和停止入口不可达。
- **为什么是问题**：实现无法同时遵守已批准的 512 KiB、只从结束最早的行裁起和成功交出整份快照。只显示“另有 N 件”也没有找回被隐藏的可操作行的路径；提案第四节第 2 小节第 4 条要求按筛选分页，决定 4 只延后形态与种类筛选。第一轮第 12 条、第二轮第 12 条未闭合。
- **如何核实**：对照三处合同，按普通汉字 UTF-8 3 字节算 `200 × (200 + 500 + 200) × 3`。实现验收用真实远程订阅送全在跑的快照，验证两窗口仍能到达被截部分并操作正确的行。这里是合同反例，不是 v2 运行结果。
- **建议改法**：保持三个上限与“另有 N 件”，补上同一范围内续取的入口；先保证报文（含组头和汇总）有界，再按顺序取页，计数用裁剪前数据。定义只有在跑行时如何续取，不把办不到的裁剪写成总能成功。

### 2. 复用 `kill` 会把明确没有受理的停止报成已受理

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:89,110,138,140`；`docs/specs/agent/jobs.md:57,64,66`；`packages/neuro-book/src/plugins/agent/backend/subagents/children.ts:51–58`；`packages/neuro-book/src/plugins/agent/backend/jobs/center.ts:345–353`。
- **现象**：子代理驱动收到 `abort` 的 `{ok: false}`（例如命令返回 `log-broken`）只记诊断，随后返回 `undefined`；`JobCenter.kill` 把它和成功一样交成 `killed`。计划只把 `already-ended` 转 `rejected`、抛错转 `unknown`，这一路不会抛；`job-unknown`（在途期间回执被领取、移出）也没有明确映射。
- **为什么是问题**：用户收到“已受理”，但驱动只知道停止指令失败；窗口更新不能把已经给错的答复改回来。第二轮第 15 条指出的旧反馈缺口没有被新三态填上。
- **如何核实**：从 `ChildRuns.start` 的驱动沿 `JobCenter.kill` 追返回值；查 `harness/runtime.md` 输出 33：受理批写失败通过结果交回，不抛错。验收不能仅用人为返回三态的测试提供方：真实子会话的 `abort` 失败也须到达清单并交回对应结果；目标移出须另测。
- **建议改法**：从真实停止驱动起保留受理、明确拒绝、无法确认三种结果，按失败码映射（并区分目标消失）；清单只是转发。明确写请求发出后链路的 `unknown-outcome` 也显示未知，不自动重试，不凭结果改行的真实状态。

### 3. 状态帧加 `runId` 不足以同步产出正确的组头和待办状态

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:41,105–112,155`；`docs/specs/agent/sessions.md:94`；`packages/nb-harness/src/kernel/api/host.ts:123–147,317–322`；`packages/nb-harness/src/kit/sessions/table.ts:188–199,402–422`；`packages/neuro-book/src/plugins/agent/backend/running-work.ts:16–44`、`agent/backend/agent.ts:208–219,289–319,460–468`。
- **现象**：状态帧已有 `runId`，但等待项只有 `{id, callId, kind}`，没有工具名，状态也不带运行开始时刻。会话表把等待集合压成布尔，只在 `idle/waiting` 翻转时通知：两项审批撤一项、另一个工具仍在等时，视图不会更新。`SessionTitles` 可同步查，但只在启动扫描、fork 登记和收到 `titleChanged` 时写，没有独立变更通知；启动后新建会话的初始标题不能靠扫过的索引取得。
- **为什么是问题**：只照计划缓存 `runId`、监听两个变化源，不开会话、不读日志的 `rows()` 无法知道等的是哪个工具，也无法知道开始时刻、何时刷新标题。手动压缩、等用户答题与模式切换也会落入“正在回复”，没有写出此刻在做什么。第一轮第 19 条只处理了活动来源，没处理连续变化。
- **如何核实**：对照 `RunStatus`、`Frame` 与 `#watch` 的通知条件、Agent 三个标题写入点；`SessionApi.snapshot/path` 均是异步，不能从 `rows()` 补读。验收真实并行审批中撤掉展示的第一项、仍在等另一项，再核对标题和开始时刻。
- **建议改法**：在会话表与 Agent 现有观测点同步维护最小投影：实际执行 id 与时刻、从日志按 `callId` 关联的工具名、用户待办类型；首读要有完整初值，改变投影字段即失效，关闭或 `broken` 要清。复用标题缓存，加初值和变更订阅；只投影展示需要的数据，不把审批原文放进不经过出站过滤的状态帧。

### 4. 门面释放不等于停止门禁；在途 `stop` 的结算没有合同

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md:43–46,74–79,102,110`；`docs/specs/workbench/background-tasks.md:87,174–180,204–212`；`docs/specs/runtime/services.md:62–65`、`docs/specs/runtime/plugins.md:68,197–202`；`packages/neuro-book/src/plugins/agent/backend/plugin.ts:197–200`、`agent/backend/agent.ts:477–489`；`packages/nb-runtime/src/services/composition.ts:565–569,603–619`。
- **现象**：已解析的可选 `tasksKey` 借用保护的是释放顺序，不是 Agent 停止信号的顺序。Agent 在入口 signal 到达时就关会话表、停回执、开始中断任务；计划到门面 release 才撤回提供方，期间 `nbook.tasks` 可以仍存有可派发的旧行。已进入 `stop` 的请求会跨 `await`；计划里的 `jobs.kill` 和 `SessionApi.abort` 没接提供方 signal，`abort()` 信号本身也不能取消已受理的用户停止。哪时返回 `target-gone`、拒绝或未知，何时丢回调，都未规定。
- **为什么是问题**：停的是 Agent 自身还是整个服务、操作是否已经受理，会改变命令结果和中止身份。单靠最终释放，窗口可能在 Agent 收口时才派发；反过来把已派发的一律报“目标不在”，又把可能已停的结果伪装成确定没做。
- **如何核实**：对照运行时的借用与门面释放代码，沿 Agent 的 signal 监听到同步 `table.closeGate()`；再查 `harness/runtime.md` 输出 30 的同步受理点。验收用真实入口把操作挡在受理前及受理后，分别停止 Agent、停止清单，并重登同名行。
- **建议改法**：Agent signal 到达时同步封住该登记，再收口 Agent 工作；门面 release 保留为幂等兜底。清单自己的门禁也在其停止信号上关闭。把客户请求取消、登记撤回、后端受理分开：受理前退出不产生副作用；受理后保留已知结论，不可确认则未知，不重派给新一代。明确在途回调由哪一侧取消、等待或丢弃。

### 5. 同步投影仍可在撤回后回填；订阅建立、退订抛错未隔离

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md:40–46,74–81,90`；`docs/specs/workbench/background-tasks.md:174–177,239–241`；`packages/neuro-book/src/shared/push-throttle.ts:19–50`、`tasks/backend/remote.ts:44–62`（位于 `plugins/`）；`packages/nb-runtime/src/services/per-consumer.ts:52–75`。
- **现象**：`rows()` 是同进程回调：外部异步停用不能插入其同步执行，但它可以同步调用已有的撤回闭包，仍返回旧行；退订也能同步调用旧 `notify`、重登或抛错。计划只捕获 `rows()` 抛错，没规定首订阅失败时回滚、退订抛错后仍清表，以及回调回来时旧代是否还可提交。即使 `rows()` 不重入，`PushThrottle` 对同步 `compute` 也走 `await`；撤掉一家不会关闭整份订阅，已算好的旧载荷仍能在之后推送。
- **为什么是问题**：依赖同步和门面代理不会自动作废提供方外泄的 `notify` 或已算完的载荷。旧代能回填、残留登记挡住新的 `provide`，清理异常还会跑出这一家的隔离边界。第二轮第 13 条的首读与撤回反例仍适用。
- **如何核实**：查 `PushThrottle.#flush` 的 `await`、`close` 的粒度及门面守卫只包方法；真实测试插件可自撤回并返回当前旧行，或在 `unsubscribe` 内调旧 `notify` 再抛错，无需伪造并发。
- **建议改法**：先建立一条精确代次的登记及脏标记，定义首读与 `subscribe` 的接合和失败回滚；撤回先作废登记与 `notify`，清理用 `finally`，退订异常只影响该家。提交共享投影及推送前各校验水位，不提交或重放撤回前的快照。

### 6. 注册代次和日志 `runId` 都挡不住同代旧点击停错执行

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md:50–51,74,110–112`；`docs/specs/workbench/background-tasks.md:91–93,177,228`；`docs/specs/agent/sessions.md:94`；`docs/specs/harness/runtime.md:99,223`；`packages/nb-harness/src/kernel/run/commands.ts:137–143,375–390`、`kernel/run/control.ts:168–193`。
- **现象**：同一个 `provide` 内，id 只要求当前唯一；A 消失后 B 用同 id，发出的 `p:<插件>:<代次>:<行 id>` 完全相同，迟到的点击能派给 B。会话即使用 `sessionId + runId` 做 id 也有同样问题：窗口 A 留着 R 的旧行，窗口 B 让 R 收口、回退到 R 中途、接着跑；新的 `RunControl.launch` 复用 R 的 `runId`。`abort` 只比 `runId`，旧点击能停新的执行、把新排的用户话留住并关唤起门。
- **为什么是问题**：输出 30 承诺“出这一行时那次运行”已收口则拒绝，不能停下一次实际执行。卡片历史查询读同 `runId` 最近一次收口的已知限制，不等于写操作也可以指向最近一次。第二轮第 11 条建议的同代 id 边界及第 18 条的实际执行身份没锁定。
- **如何核实**：第一轮第 10 条已有真实会话 `rewind → start` 的旧证据（`sameRunId:true`、`sameIdEndings:2`）；本次对照 `abortCommand` 的同步谓词推导旧键不被挡，未运行实验。验收让第二次执行停在可控模型端口，经两窗口发第一次的停止，确认第二次照跑、队列和唤起门不变。
- **建议改法**：展示 id 与操作目标分开；同一登记内的行 id 禁止重用，或操作带行代次。会话的键绑定一次实际执行（如启动/接续的受理序号），在内核受理 `abort` 的同一个同步段校验，不能只在视图或 `await` 之前比一次。

### 7. 子代理覆盖按子会话找，既会藏掉独立运行，也会藏掉用户待办

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:105–110,155`；`docs/specs/agent/jobs.md:47–55,66`；`docs/specs/agent/sessions.md:94`；`docs/specs/workbench/background-tasks.md:184–185`；`packages/neuro-book/src/plugins/agent/backend/jobs/center.ts:84–92,196–203`、`agent/backend/subagents/children.ts:25–32,91–106`、`agent/backend/subagents/tools.ts:253–282,477–488`。
- **现象**：J 跟 C 的运行 R1，计划却按 C 是在跑任务的 `target` 就隐藏 C。收口可以批内开 R2，任务终态须等 `waitRun`/后续查询回到 `jobs.end`；J 仍在表为活跃时，就会遮 R2，而旧 J 的“停止”只会停 R1 或说已结束。`later` 的后台续用本来可能没有任务。另一个反例：后台 J 覆盖了 C，C 卡在用户审批上，但 `Job.question` 只代表等父 Agent；如果根已空闲，组头没有 `head`，计划只会画普通组头与一条普通运行行。
- **为什么是问题**：隐藏的是惟一可停/可见待办的行。根的用户停止只连带正在前台等且由它启动的后代（`subagents.md` 输出 16），它不能替代独立或后台行的入口；根已空闲时不设组头停止本身合理，但下级入口必须可靠。第一轮第 5 条、第二轮第 17 条要求的是同一次实际执行、确实有可操作代表行才去重。
- **如何核实**：对照 `waitRun` 收口后可已换代（`harness/runtime.md` 输出 13）、任务跟踪、`later` 路径和提问过滤。验收前台等待与转后台、R1/R2 接力、没有 `head` 的审批子会话各只有一个正确可操作代表，并显示待办。
- **建议改法**：先按 `waiters` 明定哪些任务行真的出列，再用 `(子会话, 执行代次)` 匹配覆盖；过滤/裁剪不能留下既无代表行、也无可续取入口的活动。把实际用户待办投到代表行，组的警示/排序从组内待办汇总，不取 `Job.question` 或仅取 `head`；不把组头“停止”改成停整组。

### 8. “提醒已受理”与“结果已有去处”不能只读一个出口枚举

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:104–110,154`；`docs/proposals/unified-background-tasks.md:85–87`；`docs/specs/agent/jobs.md:52,59–62,66`；`packages/neuro-book/src/plugins/agent/backend/jobs/center.ts:41–54,257–264,379–401`、`packages/neuro-book/src/plugins/agent/backend/jobs/delivery.ts:98–108,263–294,310–315`。
- **现象**：`announced` 同时表示“短提醒已受理，正文还要 `wait`”和“永久投递失败，一条提醒都没发成”，按是否“已经有一条提醒”无法区分。另一条路：结果 A、B 共用一条已受理的提醒，都退出清单；`wait(A)` 撤了整条，B 的出口退回。`unclaim` 不向清单发 `onChanged`；若 B 重送遇到暂时失败，显示缓存还可留在“B 已送达”，直到无关变化或后来重送才修正。
- **为什么是问题**：尚可取的结果可能过早隐没，或回到未确认状态却不给用户看见。用提醒正文、快照里有没有该提醒、或 `questionExit` 推断结果交付，有同样的误判；提问受理不等于任务结果受理。`taken` 是前台/`wait` 领取，不能和提醒已取走一律处理成再次送达。
- **如何核实**：沿 `#send` 的 `pending`、`unconfirmed`、`announce` 和合并提醒的撤回分支查 `jobs.onChanged`。验收用真实会话填满提醒预算、触发短回执；制造受理结果未知并按原 id 核实；对合并提醒 `wait` 一件后让另一件暂时发不出，核对两窗口行与取件仍一致。
- **建议改法**：由 Agent 公开同一份受管任务的可见性投影，明确 `sending`、`unconfirmed`、短回执、永久失败均不等同完整结果已受理；真实领取或完整提醒受理后退出。对撤回导致的回退在修改出口时同步失效投影（或按同一幂等交付水位结算），不因读行、切范围或清除工作台已结束项改变领取权。

### 9. `focus-session` 回传失败还不够：缺少可核验的落点和完成条件

- **严重程度**：重要；**类别**：合同冲突。
- **位置**：`plan.md:111,119,132,157`；`docs/proposals/unified-background-tasks.md:78`；`docs/specs/agent/conversation.md:146–150`、`sessions.md:14,92`；`packages/neuro-book/src/plugins/agent/web/plugin.ts:379–406,861–866,890–902`、`agent/web/session-host.ts:1171–1224`、`workbench/web/commands/view-commands.ts:89–94,131–135,152–159`。
- **现象**：现有 `ownedTree` 只给布尔值，主对话与它的子会话都交给 `hostAt("view").open`，没调归属插件；连 `header`/`ancestors` 读不出来也可能回落普通路由。提案要求主对话走归属插件，而输出 53 只要求揭示消息视图，没钉住如何走其处理器。现有 `nbook.view.open` 成功只说明布局记录已改；`Host.open` 在订阅、快照、路径失败或被新打开取代时仍可正常 resolve。
- **为什么是问题**：给 `focus-session` 补一个 `try/catch` 或回传布局命令结果仍会假成功，而且可能把 bot 主对话放到通用或不可见的位置。跨项目的会话是服务端全局对象，不等于可以更换窗口的项目绑定；失败理由也不能靠当前宿主里恰好显示的会话推断。第一轮第 17 条、第二轮第 14 条未完全关闭。
- **如何核实**：沿命令到 `ownedTree`、`host.open` 与工作台布局返回值；`shared/projects.ts:164–174` 定窗口一生的项目身份。验收从任务行核对实际目标：普通及跨项目会话、归属主对话和它的子会话；撤回处理器、布局未就绪、订阅失败和两次打开交错时检查结构化失败或被取代，无假成功。
- **建议改法**：在 Agent 一处决定路由：归属主对话经当前有效的 owner 处理器落到消息视图，子会话保持就地进入；普通跨项目会话明确在当前窗口显示原会话，不改绑定，若不可落点就失败。让揭示与会话宿主都返回本次请求的结果：目标路由已显示/可显示、该会话初始数据已应用才成功；失败或被取代沿原调用返回，任务视图只负责提示。

### 10. 历史卡片的终态查询限了返回字节，没限读取成本，也没接上全文

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`plan.md:123–125,141,156`；`docs/proposals/unified-background-tasks.md:94`；`docs/specs/agent/sessions.md:95`、`conversation.md:101`；`packages/nb-harness/src/kernel/run/results.ts:21–39,42–75`、`kernel/log/jsonl-store.ts:249–285`；`packages/neuro-book/src/plugins/agent/web/subagent-card.ts:123–157`、`agent/web/components/SubagentCard.vue:98–102`、`agent/web/subagents-panel.ts:131–149`。
- **现象**：若沿 `runResult` 做“取完再截”，热会话对每个历史卡片都倒扫日志、建运行路径并拼完整回复；冷会话还会拿写锁、读整份日志和 blob。1 KiB 上限只管返回值。现有卡片在 `tree.runs` 命中时甚至直接回终态、没有首句；展开全文按钮只有 `model.result` 存在才启用。另一个问题是卡片重开时，`jobs` 一时没这项也可能只是还没加载或断线，并不证明回执已送；永久缓存 miss 或失败会把活跃行/恢复后的终态卡死。
- **为什么是问题**：一次打开父对话就可能让多张历史卡片反复读无关长日志；终态有时退成当前子会话的状态，或显示了首句却再也打不开原来的全文。收口查询不应让 `session-busy`、`log-corrupt`、取消读等变成确定的 `run-not-found`。
- **如何核实**：对照满量查询和 JSONL 打开路径；真正的用例要在回执完成、旧运行推出 `tree` 的最近项、进程重开后打开父对话，并验证热/冷两条查询不加载不相关 blob；另验收会话忙/损坏、有明确失败理由、卡片展开后仍能读全文。
- **建议改法**：提供按 `runId` 查最后一个已提交收口的有界摘要读，区分冷读与打开活动会话；用日志事实和可重建索引，避免复用完整结果再截。1 KiB 按 UTF-8 定义，沿该收口分支取末次回复；按卡片需要合并并限制查询，失败不作永久终态。摘要与用户主动展开的全文分开，全文不可取时明确原因并保留去子会话的入口；保留已定的同 `runId` 取最近一次的限制。

### 11. 停止带代次，打开却只拿命令字符串；前缀也不证明归属

- **严重程度**：重要；**类别**：合同冲突。
- **位置**：`plan.md:35–38,65–75,89,111,119`；`docs/specs/workbench/background-tasks.md:104,175,177,181,240`；`docs/specs/workbench/commands.md:59–66`；`packages/neuro-book/src/plugins/commands/shared/registry.ts:125–145,217–230,308–325`。
- **现象**：`stop({key})` 查登记代次，`open` 则直接执行旧载荷上的命令和参数。同一提供方撤回、重新登记并复用目标 id，旧行的“打开”可以被后来注册的同名命令接收。仅查 `<插件>.` 前缀也不能证明是该插件的命令：内置命令的 `nbook.<domain>.<action>` 只核对域词表，实际贡献方在命令元数据的 `source`。会话组头的 `owner.open` 还是第二条进入路，`TaskInput.owner` 也复用该形状。
- **为什么是问题**：输出 21 对旧行的“操作”承诺 `target-gone`，输出 19、25 又要求打开拥有者的目标。命令表的存在/可用性检查不会验证这个旧行。第一轮第 17 条的同名导航反例不因 `focus-session` 变诚实而消失。
- **如何核实**：对照命令声明的内置校验分支、登记的 `source` 和窗口执行的解析入口；验收在 250 毫秒合并内撤回再登记后点旧行和旧组头，并用一个合法内置域名但贡献方不匹配的导航做反例。
- **建议改法**：行与组头的导航共用一条验证路径，窗口核对实际命令贡献及导航可用性，不以字符串前缀当拥有者。明确哪些导航对象可跨登记安全引用（例如不复用的会话 id），其余以代次绑定导航引用并在真正落点校验；或在合同中明确把稳定导航与带代次的写操作区分。不让 `start.owner.open` 绕过相同规则。

### 12. “全部项目”丢了当前项目身份，同一订阅无法给两窗口正确排序

- **严重程度**：重要；**类别**：合同冲突。
- **位置**：`plan.md:88,94–98,116–118,151`；`docs/specs/workbench/background-tasks.md:116–117,178–184`；`packages/neuro-book/src/shared/projects.ts:164–174`、`plugins/tasks/web/plugin.ts:73–90`、`plugins/workbench/web/plugin.ts:154–162`（均位于 `packages/neuro-book/src/`）。
- **现象**：A、B 两个项目窗口切到全部，都发送 `{scope: "all"}`；计划让服务端给出已经排好顺序的 `groups`，但 A 要 A 在前、B 要 B 在前。`groupRows(..., currentProjectTitle?)` 未交代实参从哪里来，标题相同也不能辨别两个项目。当前 Tasks 浏览器入口没有 `windowProjectKey`；无绑定窗口的 `project` 是 `null`，不能用 `{project: ""}` 悄悄引入第三种范围。
- **为什么是问题**：排序也属于范围合同。“把 A 放在前”的信息不能从全部范围或显示名恢复；随意选首个项目会在一个窗口错，伪造项目或碰巧无同名只能让单窗口验收通过。
- **如何核实**：查现有 Workbench 读取的窗口绑定和类型；按同一份 A/B 数据代入两窗口的同样 `"all"` 参数，比较输出 26 要求。验收两个项目标题相同的实际窗口各切全部、还原当前；书架页仍只订阅结束通知的 `own`，不凭空造项目或面板。
- **建议改法**：当前项目使用稳定 id 与范围分开传（或在窗口按 `windowProjectKey` 原地排项目组，服务端只做与窗口无关的排序）。如果需要服务端按绑定分组，明确可信身份来源；缺省当前项目的选择与切换态用同一按窗口的值，供 `toggled` 公开键和订阅复用。

### 13. `own` 才是通知真相源，却把 v1 的超限停更和新归属一起带进来

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:33–38,81,87–89,116,121,150–152`；`docs/specs/workbench/background-tasks.md:76–80,114–119,146–147,165–171,179,190,227–233`；`packages/neuro-book/src/plugins/tasks/backend/remote.ts:24–37,44–62`、`tasks/web/store.ts:93–118`、`tasks/tasks.test.ts:385–397`（后两处也位于 `plugins/`）。
- **现象**：计划让 `own` 带全部自有任务和新的 `owner`，沿用 v1；v1 超限时不发事件、读得 `too-large`，本来就允许在跑任务超过这个体积。`owner` 的新大小约束写在提供方行上，没钉住 `start` 后到底如何限制持久到内存的归属形状，也没说明 v2 的 `too-large` 归哪个方法。即使 `rows` 解决了分页，仍可能看见某件任务结束或已移除，却始终不见与之对应的 `own` 更新。
- **为什么是问题**：`own` 丢的是存在性和通知基线，不只是几个标题；窗口会保留已经无效的重试通知、漏掉连接期间的结束通知，书架连替代可见投影都没有。不能拿 `rows` 的页当 `own`，否则翻页又会误撤通知。v1 的停更已有明确取舍；v2 若继续承受，须说明扩大到哪些输入和怎么恢复，不能把 `rows` 的 512 KiB 处理当作已经覆盖。
- **如何核实**：用现有 400 件长进展的自有任务用例对照 v1 不推的明确判据；新用例令其中一件结束或被重试移出，过载前后分别断开、重连，检查书架和项目窗口的通知、详情与基线。再验证新归属按实际编码拒绝或归一，而不是先保存后切断全局流。
- **建议改法**：给 `own` 独立的有界全局同步方式（可分段初始快照、带水位的变化，不把分页作删除），或按已定 v1 限制明确它单独的超限状态与重新建基线的恢复合同。给 `start.owner` 明确的写入前大小、归属和复制规则；预算与失败归属分别写进 Spec、方法 schema 与用例。

### 14. 范围重订缺少世代检查，两个流不能靠到达顺序认定“看过”

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:87–90,116–120,151–152`；`docs/specs/workbench/background-tasks.md:147,165–171,186,190`；`docs/specs/runtime/plugin-channel.md:97`；`packages/neuro-book/src/plugins/tasks/web/store.ts:93–128,140–155`、`tasks/web/components/TasksView.vue:17–32`（位于 `plugins/`）。
- **现象**：切当前 → 全部 → 当前时，第一份当前范围的订阅建立或读请求可以尚未交回。只按当前范围比较，或只释放已交回的订阅，都会让第一代的迟到结果覆盖第三代。另一个交错：`own` 已看到 A 失败，`rows` 仍显示 A 在跑；如果仅用可见 id 与 `own` 取交集，A 在画出终态之前就算看过。收起的组、没列出的行、前后台切换也不是同一种“可见”。
- **为什么是问题**：远程只保证同一订阅内有序，不保证两个流或首读与重订之间排序。新设计若沿用每次 `accept` 全量覆盖及 `viewVisible` 时全标，会把旧项目行重新显示、让失败图标过早消失。反过来让 `rows` 管通知，又把范围变化当作删除。
- **如何核实**：对照现有 `start` 的先订后取及 `onResync` 清基线；验收延后首订阅和首读，三次范围切换后送回最早的一份；再分别让 `own`、`rows` 先到，折起有失败项的组、让窗口失焦，核对本窗口何时算看过以及原通知未撤回。
- **建议改法**：每次范围变更、停止及重建都有世代；迟到订阅立即释放，旧 RPC/事件不可提交。同一流的快照与事件靠水位或有序接合，不靠到达先后；全局存在性、通知与首取/重连基线只由 `own` 更新，平时仅把实际显示的当前代自有终态算看过（沿用有效可见且在前台）。

### 15. `isLive` 不是“可以出行”：占位能早于命令与子会话露出

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:104–109,120,154`；`docs/specs/agent/jobs.md:48–55,66`；`packages/neuro-book/src/plugins/agent/backend/jobs/center.ts:14–20,168–190,340–353,477–484`。
- **现象**：`isLive` 包括 `starting`；`JobCenter.reserve` 立即占位，晚一点 `start` 才填驱动、目标。照计划据 `isLive` 出行，另一窗口首读或其它变化触发读时会看到检查中的任务；点停止得 `job-unknown`。派发失败走 `release`，只删占位、不通知，若已被读进共享快照还会留下幽灵行。计划也未定 `question` 映射到什么：它是等父 Agent，不是用户，但仍算在跑的后台工作。
- **为什么是问题**：工作台不能比 Agent 任务中心更早发布尚未开始的工作，也不能把等父 Agent 的运行挪到用户待办、从后台计数里排除。现有 `JobCenter.list` 已排除占位；共用 `isLive` 是并发名额合同，不是展示合同。
- **如何核实**：按真实子代理派发路径把创建阶段挡在占位与发布之间（例如卡住会话打开所需的端口），这时让另一窗口订阅；分别放行、拒绝及后续进入 `question`，核对只发布可操作的已开始任务，且不把等父 Agent 当用户待办。
- **建议改法**：Agent 先选已发布、不是前台等待的后台任务，再用穷尽映射生成行。`question` 的后台任务仍按运行计数、说明写“等父 Agent”；等用户使用第 7 条的实际待办投影。不要让视图或 `nbook.tasks` 猜任务中心的中间态。

### 16. 第三类 Agent 行的种类编码无合法映射

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:56–57,73–80,104–105,154`；`docs/specs/workbench/background-tasks.md:93–94,175`；`docs/specs/agent/jobs.md:65–66`；`docs/adr/0056-background-work-providers-and-session-notices.md:37`；`packages/neuro-book/src/plugins/agent/backend/jobs/tool-jobs.ts:38–55,60–84`。
- **现象**：工具任务的 `Job.kind` 已经是 `<贡献工具的插件>.<名字>`，而提供方 `kind` 只收不带点、至多 40 字符的本地种类。直接转发会丢行；只取末段会让不同插件的同名种类合并。标题用 `label` 能显示，但不解决种类身份，也不能拿它代替真正归属。
- **为什么是问题**：第三类已在首批范围，不能只靠命令和子代理两种行通过验收。清单提供方永远是 `nbook.agent`，工具插件的调用代次由 Agent 负责；错把来源改成工具插件会破坏撤回与停止责任（第一轮第 7 条）。
- **如何核实**：对照 `reserve` 的盖章和 planned schema；验收两家真实工具插件登记相同的本地种类但不同标签，停其中一家，检查两条行的身份、标签、停止、回执与另一家不受影响。
- **建议改法**：明确两种身份：清单的登记与 `stop` 仍归 `nbook.agent`，工具任务在它的本地种类编码里有合法、不会撞成内置种类的映射；若工作台需要区分两个工具来源，用单独的受限种类标识，不改原 `Job.kind`、`jobId` 或既有返回。

### 17. 根组元数据由任一行自报，多家交出同一组头时会改变停止对象

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md:33–38,58–65,79–81,94–98`；`docs/specs/workbench/background-tasks.md:76–80,96–104,174–175,178,184–185`；`docs/specs/runtime/services.md:61–65`、`docs/specs/runtime/plugins.md:57`。
- **现象**：两个登记可以合法交出同一 `{kind: "session", session}`、各自 `head: true`，或在根无活动时交出不一样的 `owner.title/open`；`start.owner` 也能指向这个组。合同只去重同一家里的行 id，没有给组的元数据定拥有者。取第一个 `head` 会让登记、排序或裁剪顺序决定组头停哪件；按提供方加前缀拆组又会把一个根画成两组。
- **为什么是问题**：按根分组授予组头“停根运行”的语义，不是把任一有效 `stop` 提升成组操作；同一个插件的不同服务端入口也可单独激活，不能以插件名推断同一登记。根空闲时组头应只有可靠的打开，不应由最后剩下的任意行决定。
- **如何核实**：用两个真实测试入口交同一个根及不同的标题、导航、`head`；交换登记顺序、撤下其中一方及让若干结束行受裁，比较组键、组头目标和其余行是否稳定。
- **建议改法**：把归属引用与组的权威元数据分开；由该实体的拥有方给一份组头与导航，其它行只引用根。若首批只允许 Agent 提供会话组头，写入合同并验证，其它冲突行不能劫持组头。去重按签发的消费身份和登记代次，保留一根一组。

### 18. 250 毫秒的展示缓存不能决定此刻还可不可停

- **严重程度**：重要；**类别**：正确性。
- **位置**：`plan.md:43–48,74,79–81,89–90,117`；`docs/specs/workbench/background-tasks.md:176–180,228–229`；`packages/nb-runtime/src/remote/node.ts:839–864`。
- **现象**：提供方把同一行改成 `stoppable: false`（或删掉）并 `notify`；下一次刷新前，核心还持有旧的合格行。若按这份缓存派发，提供方收到它已撤销的操作；只在发下一份快照时重查太晚。这里不需要行 id 复用或入口换代，稳定的 id 也有此交错。另有两个窗口同时点同一行，窗口按钮的“正在停止”只挡本窗口，计划没说持久停止信号如何合并或何时拒绝第二次。
- **为什么是问题**：`stop` 的 `target-gone`、`not-stoppable` 是操作时的失败，不是窗口最近看过的能力；通道的 ACK 只表示进入方法。`accepted` 也只表示受理，不能据此把行当已停止，或把任意 `provider-error` 当成确定拒绝。
- **如何核实**：让真实测试提供方通知变更但不推进合并时钟，两个窗口发旧的操作；验收删行、同 id 失去可停能力、两窗口重复停止，以及 `rejected` 带可翻译有界原因、写链路中断的结果未知。
- **建议改法**：将展示缓存与实时派发的门禁分开。已声明能力及行代次要在真正的执行边界核验；若权威检查在提供方，就给它传回 `target-gone`、`not-stoppable` 的类型通道，并规定同目标重复停止的幂等或拒绝规则。拒绝原因必填且有编码预算；不能用不合格原因使实际结果变成远程 `provider-error`。

### 19. v2 切片切断现有客户端的方法；`runOutcome` 另一条兼容边界未定

- **严重程度**：重要；**类别**：不变量。
- **位置**：`plan.md:85–90,116,123–125,138–150`；`docs/specs/workbench/background-tasks.md:110–126,179,227,257`；`docs/specs/agent/sessions.md:37–44,93–95,136–137`；`packages/neuro-book/src/plugins/tasks/web/store.ts:115–118,140–155`、`tasks/tasks.test.ts:55,356,390`（位于 `plugins/`）；`packages/neuro-book/src/plugins/agent/shared/remote.ts:269,384`；`packages/nb-runtime/src/remote/node.ts:805–817,893–905`。
- **现象**：第 1 片写 v2 `shared`、`backend` 并要求 typecheck，迁移浏览器在第 2 片；`TasksStore` 与现有合同夹具仍从同一份 `tasksContract` 调 `list`、`events.changed`。删除旧方法会在类型层失败，改号却保留旧浏览器线上调用也不会兼容。另一方面 `runOutcome` 加在 `nbook.agent/sessions` 当前的 v2 上，若保持版本 2，新窗口连没有新方法的服务端是 `invalid-input`，不是 `run-not-found`；若升号，旧窗口的整个 Agent 合同都会拒绝。计划没说明选哪种、何时可做第 4 片的调用。
- **为什么是问题**：两条切换是不同的合同：Tasks 已定整份升 v2；Agent 只新增历史只读入口，不应凭一次 RPC 失败让已打开的对话、任务输出文件读法或历史卡片损坏。`version-changed` 由内核保证检查顺序，不证明任何具体插件入口真的加载了 v2。
- **如何核实**：核对 `tasksContract` 的引用与 `remote/node.ts` 版本/方法检查顺序；验收用冻结 v1 客户端对新 Tasks 同时请求和订阅，两者得 `version-changed`；旧 Agent 方法、`jobId`、`jobTail` 仍照常，单独覆盖新卡片连旧 Agent 服务端的行为。
- **建议改法**：Tasks 在升号片一起迁移生产调用方与合同夹具，后片再专做分组呈现；不保留隐式旧路。对 Agent 明确采用兼容的新增读（不可用时回退已有终态，不误判不存在），或另立版本明确窗口刷新边界；将真相源中已过时的 Agent v1 版本声明和 Tasks v1 实现合同同步收口。

### 20. 复用每订阅一个节流器，空闲窗也可能成倍重做全量工作

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：`plan.md:72–73,79,87–94,116,168`；`docs/specs/workbench/background-tasks.md:147,175–176,179`；`packages/neuro-book/src/plugins/tasks/backend/remote.ts:24–29,44–62`、`packages/neuro-book/src/shared/push-throttle.ts:19–50`。
- **现象**：“每 250 毫秒一次”既写在提供方聚合，又写每个远程订阅；没有定义哪一层给共同读/投影作水位。若仍像 v1 在每订阅的 `compute` 里读、分组、编码，10 个持续更新的窗口每家可被读 40 次/秒，新的 `own`、`rows` 还有互不相关的更新；即便共享投影，按任意 `rows(scope)` 请求绕过限制仍能触发全量工作。同步只表示不会等 Promise，不保证一家执行慢或返回 20 万行时不会阻塞其他家。
- **为什么是问题**：只截发出去的第 201 项之后，不能证明没有处理/复制大量剩余项，也不能知道上限是按原始数组还是按合法项计。“当前项目”先按全局前 200 截，能把当前项目抹光；按可见前 200 算 `background` 又会错计。这是第一轮第 12 条与第二轮第 12、13 条的共同边界。
- **如何核实**：看现有 `PushThrottle` 把计算放到订阅实例；在真实场地让多窗口互相错开订阅与读，验证一轮变化只向脏的提供方取一次、总计数/截断与窗口数无关、坏家不停止好家的更新。
- **建议改法**：保留每订阅的传输节流，移出提供方读取：每批只更新一次受版本约束的公共投影。按范围从该投影取页、能合并的相同范围共用一次编码；明确原始候选、合法项、筛选和 200 行上限的顺序，以及 `more` 对哪一批负责。同步插件同进程跑不提供 CPU 隔离，合同明确限制投影工作量与诊断速率，不承诺靠 `try/catch` 隔离卡住。

### 21. 框架/宿主的现有验收没接入切片；核心通过不能证明组合行为通过

- **严重程度**：建议；**类别**：测试。
- **位置**：`plan.md:136–163`；`docs/specs/workbench/background-tasks.md:145,160–172,173,244–253`；`packages/neuro-book/src/plugins/tasks/tasks.test.ts:371–385`、`tasks/testing/world.ts:47–61,79–87`、`agent/running-work.test.ts:70–127`、`tasks/web/plugin.ts:55–69,90–111`（后三处在 `plugins/` 下）。
- **现象**：输出 17 的用例只证实 `nbook.tasks` 自有记录；现有 Tasks 的世界只装一个模拟发起方、窗口均不绑定项目。当前验收表没在两家真服务同时启用时核对宿主上报没有重复，也没验证清除命令只由自有结束项启用、提供方行与 Agent 可取结果不受清除污染，或提供方独占的清单能从状态栏发现。`background.count = 0` 与“清单空”是两件事，沿用 `store.items.length` 或改成 `count > 0` 都不能直接保留输出 12。
- **为什么是问题**：分开测同一条假任务的组、按钮和计数不能覆盖服务装配、旧行为与新行为的交集。停用 Agent 或不用可选 `tasksKey` 时，Agent 的关停确认仍应照常；装上两者后，关停不能改为把提供方行再报一遍。
- **如何核实**：对照测试场地装配和状态栏 `nonEmpty`、`hasFinished` 的真实绑定。用受管启动和同步关停收集验证，不直接调用新增内部汇总函数模拟宿主；窗口验收查看条目和命令可用性，不仅断言仓库有数据。
- **建议改法**：输出 17 晋升继续用自有任务用例，再把“有/无可选依赖、手动压缩、后台根、只剩后代、两边各报且不重”的组合加到实际入口；验收清除、撤通知、取件互不改变。在输出 26–28 明确 `nonEmpty` 的依据及无后台计数时的保留图标，测试仅有提供方/前台行、无自有任务以及 `more > 0` 的窗口。

### 22. 分组多一列，没有验收保住现行窄屏和无障碍合同

- **严重程度**：建议；**类别**：测试。
- **位置**：`plan.md:117–120,151–152,161–162`；`docs/specs/workbench/views.md:128`、`workbench/background-tasks.md:148–155,172,184–189`；`packages/neuro-book/src/plugins/tasks/web/components/TasksView.md:12–25`、`TasksHover.md:7–11`；`docs/standards/code/components.md:16–26,49–62`。
- **现象**：旧视图不足 600px 会把一件事改成两行，同名按钮由 `aria-describedby` 指向自己的标题；悬停保留进展和不定进度。计划只说“列同现在，多一列”，而 `background` 在 3.3 只列标题与进度，漏了输出 23 的进展。新分组、缩进、种类、两个新按钮与折叠会消耗窄屏空间，DOM 用例断言有按钮、两个默认窗口能点并不能证明实际可操作。
- **为什么是问题**：遵守已定外观还要保持旧版可用：窄屏看得见停止/打开、键盘知道当前组与按下状态、缩进后的进展可读；缺字段时悬停多件工作失去原来的进展。不是要求新画方案或增加筛选。
- **如何核实**：比较现有组件的列、窄屏两行及 `aria-describedby`，核对评审板的窄稿标注为 648 宽，而规范包含 390px。实现方在真实工作台使用中文和英文、长标题和组头，分别测 390px 与桌面、折叠后的键盘路径和悬停第 20/21 件。
- **建议改法**：同步 `TasksView`、`TasksHover` 的同名文档及真实界面判据；沿用工作台标题动作 `toggled`（公开键驱动 `aria-pressed`），组开关有可识别名称与展开状态，仍按窗口记；`background` 保留 `message`，超 20 显示总数差，不把裁剪后条数当总数。
