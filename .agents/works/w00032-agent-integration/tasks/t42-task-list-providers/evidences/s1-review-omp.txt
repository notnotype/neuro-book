# w00032 t42 第 1 片实现审查

审查范围：`bf4abac78^..d592d0d52`，位置均指被审提交；产品合同以主工作区 Spec 为准。

### 1. 一个越界时间让所有提供方的 `rows` 读与推送一起失败

- **严重程度**：阻断；**类别**：正确性／隔离。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:238–239`，`backend/groups.ts:40,62–79,135–138`，`backend/remote.ts:51,67`（后两文件同属 `tasks/`）。
- **现象**：入口只查时刻是有限数，`Number.MAX_SAFE_INTEGER` 合格，但超出 JS `Date` 可表示的 ±8,640,000,000,000,000 ms，转 ISO 时抛 `RangeError: Invalid Date`。所有行在按窗口范围过滤前就被转换，所以即使坏行不在当前范围也会堵住该窗口。
- **为什么是问题**：Spec 输出 19、20、边界与兼容要求坏行丢弃且只影响本家；实际整个 `rows` 得 `provider-error`，已有 `rowsChanged` 停在旧快照，好家的变化也看不到。
- **如何核实**：用 `tasksWorld` 的真实登记门面与 JSON 远程链路，先登记一条时刻为 `1` 的好行，收到首推；再由另一家登记时刻为 `Number.MAX_SAFE_INTEGER` 的行，推进 250 ms。实测读从成功变成 `provider-error`，推送总数仍为 1，诊断是 `tasks.push-failed: … Invalid Date`，不是 `tasks.provider-row-invalid`。
- **建议改法**：在逐行接收处验证 `startedAt` 与非空 `endedAt` 可以无异常转为 ISO，失败按坏行处理；用两家通过真实订阅的用例同时核对坏行被丢、好家还能推和停。

### 2. `stop` 在撤回之后仍会调用已退订的提供方

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:135–167,178–190`。
- **现象**：查行与建立 `flight` 在当前同步段完成，但真正的 `provider.stop` 挂在 `Promise.resolve().then(...)` 上，不检查登记是否仍有效。撤回既能先结算 `unknown`、abort 和退订，也挡不住这个排队中的首次调用。
- **为什么是问题**：Spec 输出 21 要求撤回先封派发、再收口；`signal` 已 abort 不是“未调用”。提供方可能已释放底层资源，或者只在受理后才观察 signal，因而仍停掉实际工作。
- **如何核实**：经 `tasksWorld` 发真实 `stop`，让脏提供方的 `rows()` 用 `queueMicrotask(revoke)` 安排撤回并返回原行。实测顺序是“撤回 → 退订 → 调用 `stop(id, signal)`（`aborted: true`）”，窗口得 `unknown`，后续读无此行。没直接调用登记表的内部方法。
- **建议改法**：在确认代次有效并登记 `flight` 后同步进入提供方回调，用 `try` 处理同步抛错；若必须延后，在调用前重新核对登记与 `flight`，已撤回的不调用。测试既断言返回值，也断言退订后的提供方没有收到首次调用。

### 5. 撤回后 `rowsChanged` 仍能先推出新一份旧代的行

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:178–195`，`backend/remote.ts:38–50,82–86`（同属 `tasks/`）；`packages/neuro-book/src/shared/push-throttle.ts:36–50`。
- **现象**：快照已算好，`PushThrottle` 即使面对同步 `compute` 也要经过 `await`。期间撤回只排下一次刷新，不使已经计算的载荷作废，`sink.next` 会发送其中的旧代。
- **为什么是问题**：Spec 输出 21 的“丢掉它的行、推送一次”不等于允许撤回后发布一份它的新状态；窗口会先看见一行服务端已拒绝操作的工作，再等一轮合并才消失。同一个空档也存在于用同一合并器的 `ownChanged.background`（从代码推断）。
- **如何核实**：通过 `tasksWorld` 订阅真实 `rowsChanged`。先显示 `original`，再让普通的同步 `rows()` 返回标题改为 `obsolete` 的行，同时用微任务调用撤回。实测退订完成、主动读已为空；订阅随后收到 `["obsolete"]`，下一个 250 ms 才收到 `[]`。
- **建议改法**：计算结果携带撤回水位，发出前检查；失效后跳过该载荷，并保证新一轮能发。或者让同步计算与进入 `sink.next` 同段执行，同时明确原合并器对异步投影的行为。

### 4. 合法的 50 件自有失败任务就能让 `rows` 超过 512 KiB

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/groups.ts:42–59,94–110,117–131`，`backend/remote.ts:67,83–86`（后者同属 `tasks/`）。
- **现象**：自己的行把标题、进展等同时编码进 `ListedRow` 和 `own: task`；会话壳再复制会话 id 与标题。裁剪不能删自己的失败行，且没有检查最终编码后的载荷。当前预算没有保证这批必留行能同时发出。
- **为什么是问题**：Spec 输出 23 同时要求 512 KiB 和自己的失败一直列。`own` 远未超限时，`rows` 已能返回超限载荷；不是 v1 `own` 超限停更的已知取舍，也不需要几家提供方同时交满。
- **如何核实**：通过 `start` 登记 50 件任务，各用独立会话 id，标题和归属标题各 200 个 NUL 码元，失败原因 500 个（JSON 每个编码为 6 字节）；令全部失败。实验另放 256 个短的在跑任务，后者全部修剪。真实 RPC 收到的 `rows` 剩 50 行、`692901` 字节；同期 `own` 有 306 件、`419848` 字节。未触发远程传输的 1 MiB 硬限，不把超 512 KiB 写成断线。
- **建议改法**：改行 DTO，让自己的任务只传一份展示字段，`source.id` 和额外可做操作就够；给必留的 50 行及所在组证明最坏字节数，按最终结构执行预算。若仍装不下，须明确调整数据或合同，不能悄悄删失败任务。

### 3. 提供方返回值的异常越过隔离边界，`stop` 还能产生未处理的拒绝

- **严重程度**：阻断；**类别**：隔离／资源寿命。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:164–167,199–218,231–274,277–286`；`packages/nb-host/src/server/host.ts:89–95,120–125`。
- **现象**：`#read` 的 `try` 只包 `rows()` 和 `Array.isArray`，逐行读字段、校验和复制在外面。`stop` 的第二参数只接前一段拒绝，不接成功回调中的 `#outcome` 异常，产生未处理的拒绝。结果晚到时也先跑校验或记失败诊断，再发现 `flight` 已结算；并非丢弃。
- **为什么是问题**：一家返回一个访问字段时抛错的对象就能打断 `rows` 或别家的 `stop`（它会读脏快照）；停止结果校验失败不仅让请求等到超时，产品宿主还把 `unhandledRejection` 当作 fatal 请求关停。后者按宿主代码判定，未启动产品宿主验证关停。
- **如何核实**：经真实 JSON 远程链路分别交 `title` getter 抛错的行和 `reason` getter 抛错的 `{kind:"rejected"}`。前者令读和停止好行都得 `provider-error`、无提供方行诊断；后者实测触发 `unhandledRejection`、到 10,000 ms 才得 `unknown`。超时后再交缺 `reason` 的结果仍新增一条 `provider-stop-invalid`。
- **建议改法**：把字段访问、归一化和复制纳入提供方边界；逐行失败安全地记录有限元数据。由单一 `flight` 拥有结算、取消与异常处理，在读结果或记诊断前检查是否已结算。

### 6. `TaskItem.owner` 变为必填后，两个现有浏览器消费者没有迁移

- **严重程度**：阻断；**类别**：兼容性。
- **位置**：`packages/neuro-book/src/plugins/tasks/shared/contracts.ts:138–154`；`packages/neuro-book/src/plugins/lab/web/fixtures/tasks-scene/TasksFixture.vue:30–38`；`packages/neuro-book/src/plugins/tasks/web/components/TasksView.dom.test.ts:30–32`。
- **现象**：Lab 的 6 条 `TaskItem` 样例及组件用例的 `task()` 都没有给 `owner`。两个 Vue 类型检查均失败：`tsconfig.web.json` 有 6 条 `TS2741`，`tsconfig.browser-test.json` 另有 1 条 `TS2719`（`owner` 可为 `undefined`）。
- **为什么是问题**：应用的 `typecheck` 是后端、前端、浏览器测试三道。`bunx tsc --noEmit` 的通过不覆盖 `.vue` 或该 DOM 用例；不需要改第 2 片的视图也能完整迁移这个类型。
- **如何核实**：在 `packages/neuro-book` 分别运行 `bunx --no-install vue-tsc --noEmit -p tsconfig.web.json` 与 `bunx --no-install vue-tsc --noEmit -p tsconfig.browser-test.json`；本轮两项退出码均为 2。
- **建议改法**：在两个 fixture 的默认字段里加 `owner: {kind: "app"}`，保持远程 DTO 必填，不用断言或可选字段掩盖漏迁移。

### 7. `subscribe` 抛错后，已交出去的 `notify` 还会唤醒清单

- **严重程度**：重要；**类别**：资源寿命。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:94–106,178–195`。
- **现象**：失败分支只从 Map 删除表项，没有置 `sealed`；提供方可能先把 `notify` 接进自己的事件源、再抛错。后来这段闭包仍能调全局 `changed()`。成功返回的退订值也没有检查是否可调用（从代码推断）。
- **为什么是问题**：登记失败不该留下对活跃列表的反向调用通路；去重只能挡重复帧，挡不住每个窗口重算和再次记超量诊断。
- **如何核实**：经真实门面让 `subscribe` 保存回调后抛错；登记确实抛 `TypeError`。在 `ownChanged` 已稳定的情况下，清单准备 400 件长进展自有任务，使每次重算有 `tasks.list-too-large` 作为可观察信号。单独调失败登记留下的回调并推进时钟，诊断从 1 条变 2 条。
- **建议改法**：登记提交成功前只记脏，不对外通知；失败原子封住该表项的回调，只清本代；让 `notify` 同时核对当前表项身份。验证退订是函数，注明提供方要自行回滚在抛错前装上的监听（清单拿不到退订函数）。

### 8. 按每组预留 2 KiB 会把仅约 170 KiB 的列表裁成空

- **严重程度**：重要；**类别**：正确性／容量。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/groups.ts:19–21,94–110,139–141`。
- **现象**：每组先收 2,048 字节，删掉组内最后一行也不退回组壳预算。256 个非空组的预留就等于 524,288 字节；循环会一路删光所有可删的行，不看各组实际占用。
- **为什么是问题**：Spec 输出 23 只有编码后超限才修剪，且被裁行在视图里没有入口。这里不是偏保守多裁几行，而是越过一个常量门槛便从 3 个组变成空列表；并且 2 KiB 不是可靠上界，光会话 id 和标题就可各用 200 个编码后 6 字节的码元。
- **如何核实**：经 `tasksWorld` 启动 255 件短标题任务，各一个不同项目，`all: true` 真 RPC 收到 3 组、`more:252`、2,088 字节；再加同形第 256 件，收到 0 组、`more:256`、52 字节。按样本每个完整组不到 700 字节，256 组原可不到 175 KiB。
- **建议改法**：先建立真实的分组与开销，按最终 JSON 字节数计量；按优先级裁行时回收变空的组壳、正确计入改变的组头。最后断言实际载荷有界，不用固定余量代替合同。

### 9. 单家 100 行截断吃掉了 `more`，也让范围外在跑件数失真

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:211–228`，`backend/groups.ts:135–141,165–170`（同属 `tasks/`）。
- **现象**：单家先截到 100 行，只把留下的行交给分组。`more` 只数第二次（整份预算）截掉的行；`elsewhere`、`background.count` 同样只能数第一阶段留下的。
- **为什么是问题**：输出 23、26 定义 `more` 为范围内因上限没列出的件数，不限于 512 KiB；`elsewhere` 和状态栏的件数也不是“抽中的 100 行有几件”。现在可以把仍在跑的其他项目报成 0。
- **如何核实**：一家给 99 条在跑应用行、项目 A/B 各一条在跑行（A 排在 B 前）、A 一条结束行，均合法。真实 RPC：当前 A 得 `more:0, elsewhere:0`；全部得 `more:0`，实际只列 100；`own.background.count:100`。按合同口径当前 A 有 1 件没列、范围外 1 件在跑，全部少列 2 件，在跑共 101 件。
- **建议改法**：保留单家超额行的最小计数信息（按归属、在跑、前台与否聚合），在按范围计数时加回；给 100 行上限补跨项目、`waiting` 和纯在跑超额的测试，明确同优先级的取舍。

### 10. 会话组头取到了正确的行，却可能把“打开”指向另一家

- **严重程度**：重要；**类别**：正确性／归属。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/groups.ts:117–130`。
- **现象**：有 `head` 时，标题取 `head.owner`，但 `head.row.open` 为空就回退到最早登记的任意提供方行的 `owner.open`，甚至跳过 `head.owner.open`。
- **为什么是问题**：输出 26 只在没有组头行时才从最早登记的提供方取组头的打开。现在组里的停止、标题和打开可来自两个插件、两个不同目标；第 2 片即使正确按命令来源验证，也无法从这份混合元数据恢复真正的意图。
- **如何核实**：真实 RPC：先登记一条归属会话 `r` 的普通行，它的 `owner.open` 指向早登记插件的 `open {session:"other"}`；再由另一家给 `r` 的 `head`，其中 `owner.open` 指向自己的 `open {session:"r"}`，不填行级 `open`。实测组标题与 `head.source` 属于后者，`group.open` 却是前者的 `other`。
- **建议改法**：选定组头后只从该行和它自己的归属取 `open`，没有才是无操作；只在无 `head` 时从按登记顺序选中的提供方取后备标题与导航。

### 11. 修剪后才判定组头冲突，会把“普通行”提升为组头

- **严重程度**：重要；**类别**：正确性／组头来源。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/groups.ts:98–103,117–122,135–151`。
- **现象**：修剪按每行原始 `head` 标志给优先级，留完才挑同会话的实际组头。晚登记的冲突行被当成高优先级组头；真正的组头较早开始、被裁掉后，晚登记的行升成组头，连冲突诊断也不记。
- **为什么是问题**：输出 26 要求最早登记者为组头、其它作为普通行并诊断。有没有超总预算不应改变同一个根会话的组头停止目标；若真正组头被裁，冲突行也不能代它受理。
- **如何核实**：两家各交 80 个长的在跑会话组头，其中 `same` 由两家都交，早登记方时刻为 `0`，晚登记方为 `10000`，其它 158 条时刻居中。真实 `rows` 余 106 组、`more:54`，`same` 组头来自晚登记方，`provider-head-conflict` 为 0 条。
- **建议改法**：在修剪前定正选组头与冲突普通行，按这个角色裁并记冲突；正选已被裁时保留明确的无组头状态，不重新选竞争者。

### 12. 2 KiB 卡的是内部表项，不是提供方输入或发给窗口的行

- **严重程度**：重要；**类别**：正确性／容量。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:253–274`，`backend/groups.ts:62–79`（同属 `tasks/`）。
- **现象**：内部 `AcceptedRow` 既带组元数据，又重复带原始 id、插件和登记代次。实际 `ListedRow` 去掉部分内部字段，却加 `source`、`own:null`，两个数字时刻换成 ISO 字符串。两种布局不能互为上界。
- **为什么是问题**：Spec 输入与计划 3.1 把 2 KiB 写成行的编码预算。当前实现既拒绝符合输入预算且可装进窗口一行的内容，也能把超过 2 KiB 的单行发出去；内部字段调整会无意改掉插件的准入边界。
- **如何核实**：真实远程测试：`id:"0"`、120 汉字标题、420 汉字进展、120 ASCII 字符种类名、应用归属、`startedAt:0`，实际提供方 id 为 `test.tasks-owner-old`，输入 1,889 字节，被丢弃。另一条完成行（`id:"z39"`、200 汉字标题、200 汉字种类名、174 汉字进展、`startedAt:0, endedAt:1`）输入 1,887 字节、被接收，窗口的 `ListedRow` 为 2,067 字节。
- **建议改法**：明确预算所指形状，在相应的规范化边界按实际编码计量；输入规则与输出预算分别约束，测试实测收到的 JSON 字节，而不是拿私有结构替代合同。

### 13. 门面释放先跑提供方退订，破坏自己任务的中断语义

- **严重程度**：重要；**类别**：不变量／既有行为。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/core.ts:159–160,193–198,251–266`，`backend/providers.ts:178–190`（同属 `tasks/`）。
- **现象**：同一入口既 `start()` 又 `provide()` 时，门面释放先调用提供方的 abort 监听和退订，之后才去找自己在跑的任务和清 `retry`。门面代理已经作废，但之前交出去的任务句柄还有效。退订中的 `handle.succeed()` 会把运行中的任务先改成成功。
- **为什么是问题**：输出 5 和实现合同要求门面释放时先清重试资格，再收口在跑任务，已释放发起方的句柄不应再改变状态。这里该任务不会被中断或 abort，还会符合输出 14 的成功通知条件（通知未跑浏览器验证）。
- **如何核实**：真实测试插件同时登记，退订回调调 `handle.succeed("retiring")` 后抛错；停止发起方入口。`own` 实测返回 `succeeded`，句柄 `signal.aborted === false`，而提供方确实退订一次、记诊断一次并移出。
- **建议改法**：门面释放时先同时封住该登记的派发和自己任务的更新资格，清这家的重试、落定中断状态，再执行可能重入的 abort 和退订回调；回调结束后合成一次变化。

### 14. `rows()` 里同步 `notify`，两个订阅会在同一轮各读一遍

- **严重程度**：重要；**类别**：不变量／共享快照。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:98–101,122–132`，`backend/core.ts:269–279`，`backend/remote.ts:76–86`（后两文件同属 `tasks/`）。
- **现象**：读前清 `dirty`，读中再 `notify` 会立刻把它置回。第一个订阅自身的合并器把这次变化留到下一轮，但同一轮接着运行的第二个订阅（也可以是 `ownChanged`）会立即读掉新 `dirty`。
- **为什么是问题**：计划 3.2 规定读中来的 `notify` 留到下一轮，输出 20 要求同批共用已读快照。实际连着的窗口在同一个合并时点看到不同投影；“下一轮”取决于有几个订阅。
- **如何核实**：两个真实窗口订范围相同的 `rowsChanged`。通常每次变化提供方总共只读一次；让提供方某次 `rows()` 先拍 `three`，再同步改为 `four` 并 `notify`。实测两次 `rows()` 都发生在手动时钟的 750 ms，窗口 A 得 `three`、B 得 `four`；到 1000 ms 才对齐。
- **建议改法**：由登记表统一拥有提交的批次和失效水位；读期间的变化排下一批，不交给另一个订阅当场消费。订阅分开节流传输，不分开推进共享投影。

第 12 条证据补正：`id:"0"` 的行按窗口结构计算为 2,058 字节，应当丢弃，不能用作误拒样本。误拒用 `id:"a".repeat(200)`、120 汉字标题、340 汉字进展、80 ASCII 字符种类名的行：输入 1,808 字节，按窗口结构为 1,977 字节，仍记 `over 2048 bytes`、没有出现在 `rows`。2,067 字节已发出的反例不变。Spec 输入明确以「按发给窗口的样子」为准，并未另定原始输入字节数门槛；建议只按实际窗口行计量。

第 9 条诊断补证：同一场地另交 101 条短的合法在跑行，`rows` 只列 100 条，但服务端 `tasks.provider-rows-capped` 为 0 条。输出 19 要求持续超额只记一次，不是完全不记；计数修复应同时记录本代进入超额的变化。

### 15. 同一不合格行每次读都重复记诊断

- **严重程度**：重要；**类别**：诊断／资源边界。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:211–218`。
- **现象**：逐行校验每次见到相同错误都调用 `report`，没有按登记、行 id 与原因去重。
- **为什么是问题**：输出 19 要求同一行同一原因只记一次。提供方经常更新其它行时，一个未修复的问题就会反复占用诊断空间，淹没同时发生的不同失败。
- **如何核实**：一家登记 `{id:"INVALID-KIND", kind:"Work"}`，真实 `rows` 读后有 1 条 `provider-row-invalid`。保持该行不变，`notify` 后再读，有 2 条相同 id、相同原因 `bad kind` 的诊断。
- **建议改法**：为每家在快照中去重稳定的诊断键，随登记寿命释放，且避免不合格的长 id 本身进入诊断；测同一原因不重记、另一个原因仍可查。

### 16. 提供方的可选布尔字段类型错误时，坏行仍进清单

- **严重程度**：重要；**类别**：正确性／输入校验。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/providers.ts:232–252,266–270`。
- **现象**：`head`、`foreground`、`stoppable` 没有类型校验，只用 `=== true`。例如传入字符串 `"yes"` 与省略该字段效果相同。
- **为什么是问题**：输出 19 要求字段不合格的行丢掉并记诊断。类型错误被吞掉后，本应丢弃的行可出现在视图里；`foreground` 的错误还会把它算入状态栏而不提示提供方。
- **如何核实**：经真实门面交一条 `foreground`、`stoppable` 都是字符串 `"yes"` 的行。`rows` 列出了它，两个字段均为 `false`，服务端没有给该 id 记 `provider-row-invalid`。
- **建议改法**：在逐行入口区分缺省、合法布尔值和类型错误；只对缺省应用默认值，不改合法的 `false`。

### 18. “关闭时交回未知”用例不看远程结果；修剪用例只覆盖优先级第一段

- **严重程度**：建议；**类别**：测试判据。
- **位置**：`packages/neuro-book/src/plugins/tasks/providers.test.ts:312–339,387–399`。
- **现象**：关闭用例 `void client.stop(...)`，只核对服务关闭、signal 和退订。修剪用例的超额不足以删完提供方结束行，根本没走到“自己结束但不是失败”“在跑普通行”“组头”三个阶段。
- **为什么是问题**：断言没有保护标题写的合同。关于关闭时的 `unknown`，即使请求一直未结算，用例也照样结束；修剪顺序的前三个分支之后全错也不会红。
- **如何核实**：只在临时副本变异：去掉撤回时的 `flight.settle({kind:"unknown"})`，单跑 `服务停止` 仍为 1 pass、0 fail、3 条断言；去掉修剪顺序的后 3 个桶，单跑 `整份超过上限` 仍为 1 pass、0 fail、8 条断言。
- **建议改法**：关闭用例保留那次 RPC 的 Promise，并断言收到 `ok / unknown`；用分段预算的输入跨过每一级，断言同时消失的行和仍在的行。保留现有场地与 RPC，不读内部登记表。

### 17. 两路推送的去重用例没有证明提供方的通知进了推送链

- **严重程度**：重要；**类别**：测试判据。
- **位置**：`packages/neuro-book/src/plugins/tasks/providers.test.ts:343–382`。
- **现象**：`ownChanged` 用例靠 `w.tasks.start` 唤醒首推，之后只断言改前台行不推，没断言提供方更新后台行会推；`rowsChanged` 用例的首推与后续自有任务变化同样不依赖提供方通知，提供方的更新仅断言不重推。
- **为什么是问题**：两条用例会把「有通知但载荷不变」和「没有通知」判成同一种通过结果。输出 20、23 的主要链路仍可能断掉而绿灯。
- **如何核实**：只在系统临时目录的代码副本里，将 `ProviderRegistry` 的 `changed` 换成空函数。原测试的 `background 数` 和 `rowsChanged 按订阅的范围推` 分别仍为 1 pass、0 fail、各 2 条断言。未改工作区文件。
- **建议改法**：两路先走一次仅由提供方触发、确实要推的变化，并断言远程收到新载荷；再以同一条链路的可观察动作收口，断言内容未变不多推。后台行只改标题、进展或进度，也应触发 `ownChanged`。

### 19. `own` 超限期间，每个窗口的每次读和推送都重复记诊断

- **严重程度**：重要；**类别**：远程合同／诊断。
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/remote.ts:26–32,63–66,76–80`，`packages/neuro-book/src/plugins/tasks/tasks.test.ts:384–397`。
- **现象**：`bounded()` 每次遇到超限都写 `tasks.list-too-large`，各订阅与直接读共享逻辑，但不共用“已经超限”的状态。迁移后的旧用例还用 `>= 2` 条诊断判定推送跳过，实际在保护重复记诊断。
- **为什么是问题**：Spec「失败与恢复」要求 v2 每次进入超限只记一次，持续超限时各窗口和各次推送不重复记。这不是改变 `too-large` 或保留上一份的行为，而是避免一次持续超限随窗口数和刷新频率淹没诊断。
- **如何核实**：两个真实 `ownChanged` 订阅先各收到空清单，登记 400 件各带 500 汉字进展的任务。第一次读、第二窗口读、两次合并推送及第三次读后，诊断依次为 1、2、5 条；直接读均为 `too-large`，两个窗口仍只持有首份。减到 280 件后，两边均恢复收到更新。
- **建议改法**：在两路 `own` 入口共享的预算状态中只在进入超限时记一次；恢复可发后清标记。测试用最后一次正常载荷与恢复后的新载荷判定跳过，不用重复日志当推送完成信号。

## 未发现问题的方面

- 用基线提交的真实 v1 合同调用 `list` 和订阅 `changed`，分别得到 `version-changed`；不需要额外的 v1 兼容端点。迁移后的仓库仍从 `own.tasks` 建立基线，既有重连、通知与“看过”用例通过。
- 正常登记下，重复登记同步拒绝；已成功撤回的门面退订一次，显式撤回再登记后旧键不派发给新代。生产清单的插件 id 不允许冒号；行 id `session:r:run` 的实际 RPC 能查到整段 id。先改成不可停、再移走，同一键依次得到 `not-stoppable`、`row-gone`。
- 正常收到 `stop` 的提供方可返回已受理、带原因的拒绝或未知；10,000 ms 等待及显式撤回时的在途结算通过既有合同用例。另用真实 `hub.stop()` 探针核对，挂起调用得到 `ok / unknown`，提供方信号已 abort；不以未等返回值的关闭用例作为这项结论的证据。
- 未触发修剪时，按范围过滤与会话／项目／应用的顺序通过；当前项目置前，等待会话置前，非等待会话用组头开始时刻排序，不因同会话另起后台工作而前跳。合法归属登记、不给归属时归应用、拒绝自有归属带 `open` 的合同用例通过。
- 常规同步 `notify` 下，两路订阅共用一次提供方读取。探针中仅改前台行只推 `rowsChanged`；仅改后台行进展和进度时两路均推，`own.tasks` 不变；重复内容从版本 3 到 4 不多推。`own` 超限仍保持上一份，恢复预算后两个订阅都能恢复收件；诊断次数的问题见第 19 条。
