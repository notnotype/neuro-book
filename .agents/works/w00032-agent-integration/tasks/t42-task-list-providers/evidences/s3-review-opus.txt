## F1 留着的话的行在会话空闲关闭（30 秒）后消失，再次打开时开始时刻跳成打开的时刻

- **严重程度**：重要；**类别**：正确性 / 文档
- **位置**：`packages/nb-harness/src/kit/sessions/table.ts:214-229`（`activityWithBackground` 只看 `state === "open"` 的表项）、`table.ts:483-491`（`#maybeIdle` 不看 `held`）；`packages/neuro-book/src/plugins/agent/backend/task-rows.ts:115`
- **现象**：从清单停一个根会话（`abort({keepQueue: true})`）后，它变成“有留着的话等你放行”的组头；但会话此时空闲、没有引用（清单本身不打开会话，用户多半没在对话里开着它），`IDLE_CLOSE_MS = 30_000` 后句柄表关掉它，`activityWithBackground()` 不再列它，这一行与块的“等你处理”一起消失。之后任何读这个会话的调用把它重新打开，行又出现，`startedAt` 变成重新打开的时刻。
- **为什么是问题**：sessions.md 输出 30 写“这一行随之变成‘有留着的话等你放行’”，没有“30 秒后消失”的例外；从清单停下恰恰是最常见的“会话没开在对话里”的场景，用户回到清单时提示已经没了，留着的话只能靠自己记得。`activity()` 的文档注释里有“空闲关闭之后不再列出，已知限制”，但那是前台活动条目的旧限制，新的清单行继承了它而 Spec 30 与计划 8 的已知限制都没写。
- **如何核实**：真实会话表加手动时钟（`/tmp/t42-s3-review/probe/held-idle.test.ts`，在 `packages/nb-harness` 下 `bun test` 它）：停下后 `[{"id":"s-1","state":"held","startedAt":0}]`；`clock.advance(IDLE_CLOSE_MS)` 后 `[]`，日志里那条仍是 `held`；再 `snapshot()` 一次又成 `[{"id":"s-1","state":"held","startedAt":30000}]`。`task-rows.test.ts` 的“根会话在跑时一行组头……”用的是手动时钟、不推进，测不到。
- **建议改法**：二选一交开发者：（a）句柄表在 `held` 时不起空闲计时（`#maybeIdle` 加 `!entry.held`，`#refreshHeld` 变成不 held 时再 `#maybeIdle`）——部件不变、行为与 Spec 一致，代价是留着话的会话一直开着，数量受用户操作约束；（b）写进 sessions.md 输出 30 与计划 8 的已知限制。倾向（a）。

## F3 留着的话的行 id `session:<会话>:held` 在同一代里会复用，违反 background-tasks.md 输出 19

- **严重程度**：建议；**类别**：正确性（合同）
- **位置**：`packages/neuro-book/src/plugins/agent/backend/task-rows.ts:95`
- **现象**：同一会话第一次停下留话得 `session:S:held`；用户放行（开新运行，行换成 `session:S:<run2>`，held 行消失），再从清单停一次又留话，又得 `session:S:held`。同一次登记里一个已经消失的行 id 再次出现。
- **为什么是问题**：输出 19 明写“提供方在同一代里不复用已经消失的行 id：键只带代次与行 id，复用会让旧窗口迟到的操作落到新的那一行上”（计划 7a 的 omp 6）。眼下 held 行不可停、打开的是同一个会话，所以迟到操作的实际后果小；但这是合同的字面违反，以后给 held 行加操作（例如“放行”）时就会落错。
- **如何核实**：读代码即可；行 id 只由会话 id 与常量 `held` 组成。
- **建议改法**：把看到留着的话的时刻带进 id：`session:${id}:held-${startedAt}`（`heldAt` 在每次 false→true 时重取，天然区分两次）；`stop` 里按前缀 `held-` 判。不想改 id 就在输出 19 写明 held 行的例外与理由。

## F4 后台命令最后一行含大量控制字符时整行超过 2 KiB 被清单丢掉，命令从清单与状态栏件数里消失

- **严重程度**：建议；**类别**：正确性 / 安全与性能
- **位置**：`packages/neuro-book/src/plugins/agent/backend/task-rows.ts:72`（`job.lastLine`、`job.outcome?.line` 原样作进展）；上限在 `tasks/backend/providers.ts:326`（按 JSON 编码后的字节量）
- **现象**：`shell-background.ts` 的 `lastLine` 只按 UTF-8 原始字节截到 768（`capLine`），清单再截到 500 个码元，但 2 KiB 量的是 JSON 编码后的字节：C0 控制字符（ESC、NUL 等）编码成 `\u001b`，一个字符 6 字节。`QUESTION_MAX` 只管了提问，命令的输出行没管。
- **为什么是问题**：行超过 2 KiB 时清单整行丢掉、只记一次 `provider-row-invalid`，这件后台命令在清单与状态栏“后台任务”件数里都不见了，用户停不了它（模型的 `kill` 仍可以）。
- **如何核实**：`node /tmp/t42-s3-review/size.mjs`（按 `listedRowOf` 的形状组一行、按与清单相同的两步截短）：空标题空进展的外壳 369 字节；最后一行是 400 个汉字 → 1223 字节；npm 式的 `\x1b[1G\x1b[0K⠙` 转圈 → 1622 字节；二进制样的 `\x00\x01\x02\x7f` 重复 → 2827 字节（超出，整行丢）。常见的彩色输出在线内，真正超出的是 `cat` 二进制、带大量控制序列的 TUI 输出这类。
- **建议改法**：在 `jobRow` 里给进展去掉控制字符（`/[\u0000-\u0008\u000b-\u001f\u007f]/gu` 换空、顺手去掉 ANSI 序列），或者按编码后字节截短进展；提问那里同样处理即可去掉 `QUESTION_MAX` 只防一处的不对称。

## F5 有归属的树里的子代理任务行可停，以用户身份停会把子会话排着的话变成用户留着的——正是决定 7 不给 bot 会话“停止”的理由

## F6 驱动的 `kill` 抛错时 `stopByUser` 不复位，只有交回 `StopFailed` 才复位

- **严重程度**：建议；**类别**：正确性
- **位置**：`packages/neuro-book/src/plugins/agent/backend/jobs/center.ts:374-383`
- **现象**：新加的复位只在 `typeof stopped === "object"` 分支里；驱动 `kill` reject 时 `await` 直接抛出，`job.stopByUser = true` 留着。会 reject 的驱动是现成的：插件登记的任务 `tool-jobs.ts:63-64` 直接 `await input.stop(byUser === true)`，插件的 `stop` 抛错就 reject；子代理驱动在会话表停止中 `table.view(child).abort` 经 `#gate` 抛 `SessionTableStopping`。
- **为什么是问题**：注释写的不变量是“没停下：之后别的原因收口时不算用户停的”。抛错同样是没停下；之后它因为模型 `kill` 或自己结束成 `aborted` 时，`end` 会盖上 `byUser: true`，回执不唤起父会话（jobs.md 输出 11 只给真正被用户停的）。清单这边由 `providers.ts` 把 reject 记成“未知”，远程 `killJob` 则把异常抛给 RPC 层。
- **如何核实**：`jobs.test.ts` 的新用例把驱动改成 `kill: async () => { throw new Error("x"); }`、`await expect(jobs.kill(null, job.id)).rejects…`，之后 `jobs.end(job, "aborted", …)`，`job.outcome?.byUser` 为 `true`（预期 undefined）。
- **建议改法**：`let stopped; try { stopped = await job.driver?.kill(…); } catch (error) { if (owner === null && isLive(job.state)) delete job.stopByUser; throw error; }`，或者把抛错也归成 `{kind: "stop-failed", code: "stop-threw"}` 交回（远程 `killJob` 随之得 `stop-failed` 而不是内部错误，更贴 jobs.md 输出 4）。倾向后者，部件不增加。

## F10 可简化：`focus-session` 另写了一遍读会话头；`jobStop` 的 `not-allowed` 分支经清单到不了

- **严重程度**：建议；**类别**：代码质量
- **位置**：`packages/neuro-book/src/plugins/agent/web/plugin.ts:899-905` 与 `plugin.ts:385-393`（`sessionOwners.ownerOf`）；`backend/task-rows.ts:164`
- **现象与改法**：

## 未发现问题的方面

- **会话表的运行与开始时刻**：非空闲的四种状态（`running`、`waiting`、`aborting`）都带 `runId`，`broken` 归空闲，所以非空闲时 `run` 不会是 null，`?? "run"` 与 `stoppable` 的 `runId !== undefined` 只是兜底；`run` 只在 id 变时换对象，`aborting → running` 同一 `runId` 不换行、不多发。`pending` 只在等用户时有，审批优先，符合计划 7b。
- **`onActivityChanged` 漏发**：运行、等你、事项种类、压缩、留着的话五样变化都发；换运行必经空闲（探针 2），按 id 比也不依赖它。多发只有 F8 的白推，`tree.ts` 自己去重，不会出错。
- **任务中心的清单信号**：逐个核对改变 `listed()` 或行字段的写入点：`start`/`question`/`progress`/`end`/`detach`/`receiptTaken`/`#restore`/`wait` 的取走经 `#changed` 或 `#ownerChanged`（后者现在也发清单信号）；`claim`/`unclaim`/`announce`/`attach`/`settleEarly` 单发清单信号；`delivery.ts` 把 `exit.state` 改成 `pending`/`unconfirmed` 后都紧跟 `receiptSettled`。`#trim` 只删出口是“提醒已受理”的任务，它们本来就不列，不发信号没有可见影响；`reserve`/`release` 只碰 `starting`，也不列。送达只订 `onChanged`，`claim`/`unclaim` 不发它，不会绕过退避重送。
- **同步读与重入**：清单核心的 `notify` 只标脏，读行在 `PushThrottle` 的定时回调里，不在 `claim`/`unclaim` 的同步段里读，不会读到半截状态或重入；`unclaim`/`announce` 在循环里逐件发，即使被读，中间态也都是合法的出口。
- **标题缓存与订阅先后**：`titles.follow(table)` 在建表时先订 `onLog`，提供方后订；而且读行是异步合并的，先后本身也不影响结果。
- **行 id 的解析**：`lastIndexOf(":")` 对会话 id 里有 `:` 的情况正确，运行 id 是 12 位十六进制、不含 `:`；行 id 远低于 200 字符。
- **停止**：`stop` 的 `signal` 没有用上不违反输出 24——清单到点或撤回时自己以“未知”结算并丢弃之后的结果，合同没有要求提供方响应它；会话行的停止经核心先按最新快照查键，换了运行的旧键得 `row-gone`，到不了提供方，极少数竞态下到达时 `runId` 不符得 `aborted: false` → 被拒，不停下一次运行。
- **登记与撤回的先后**：`stop` 第一步 `revokeRows()`，之后核心封住派发、在途的停止以“未知”交回、退订；`runtime.stop()` 期间会话表与任务中心的变化调到的 `notify` 已被封住，不再读行或转来停止；`nbook.tasks` 先停时 `core.close()` 撤回，Agent 的撤回函数成空操作。
- **focus-session 的失败交回**：`reveal` 的失败一路交回到 `open`、`new-session`、`focus-session` 三个命令；编辑区页面的 `elsewhere` 改成等结果并在失败时提示，没有形成 `focus-session` 与页面宿主之间的递归（有归属时走 `hostAt("view")`，那个宿主没有 `elsewhere`）。正常路径上先读的会话头写进归属表，`ownerOf` 不再读第二次。
- 合同测试与类型检查：`packages/neuro-book` 下 `bun test src/plugins/agent/task-rows.test.ts src/plugins/agent/jobs.test.ts` 40 过 0 失败；`packages/nb-harness` 下 `bun test src/kit/sessions` 18 过；`packages/neuro-book` 下 `bunx tsc --noEmit` 退出码 0。
