# 内核缓冲区的提示与会话级唤起门

## 目标与范围

按已接受的[提案“统一后台任务”](../../../../../docs/proposals/unified-background-tasks.md)第四节第 1 小节与 [ADR 0056](../../../../../docs/adr/0056-background-work-providers-and-session-notices.md) 改 nb-harness 内核：

- 缓冲区的提示：在取插话的同一处取走、同一次请求里排在插话与新话前面（可以调整现有边界的先后）；不进输入的就绪与留着；会话级、一直待发；渲染成带来源行的 `<system-reminder>`；不算授权、不解除守卫；单条与会话合计的上限、与输入共用快照预算；`key` 替换、发出者撤回、用户取消；预览只读显示。
- 唤起：受理时与每个收口批里判；收口时只开一次后继运行，推迟的用户的话优先、提示随它带上；唤起的提示在第一次请求前全被撤回时不发空请求。
- 门挂在会话上：停止受理、非正常结束时关，用户自己的发话、继续、放行真正开起运行时开；回退、换分支、压缩不开；旧日志的初值。
- 提示与插话同等对待；“取走后那次请求没发出去就放回缓冲区”简单就一起做，复杂就接受限制（开发者 2026-11-19）。

合同：改 [`harness/runtime.md`](../../../../../docs/specs/harness/runtime.md)、[`harness/session.md`](../../../../../docs/specs/harness/session.md)（先写 planned）。

依赖：无。t22 的结果送达与 eval 的提示依赖本 Task。

## 探针（2026-11-19）

用真实内核跑了 5 条（[探针](evidences/probe-external-facts-and-wake.test.ts.txt)、[输出](evidences/probe-outputs.txt)）。先读代码确认了两件事：边界的先后是“写运行中到达的外部事实 → 工具集 → 取插话 → 解析模型 → 压缩 → 组请求”（`run/loop.ts`）；内核写对话事件时按状态盖位置章，一轮还没有回复时是“附带内容”（请求里排在这一轮的新话前面），有回复后是“最后一步之后”，空闲时是“等下一轮”（并进下一轮的附带内容）（`dispatch/core.ts`、`view/format.ts`）。所以提示与插话在同一处、先于插话写下，就自然排在新话与插话前面——第二轮审查的第 1 条阻断不必动开运行的那一批。

| 探针 | 结果 |
|---|---|
| E1 空闲时扩展写的外部事实（`mount` 里的 `emit`，对话事件） | 盖“等下一轮”，下一次请求里与新话同一条用户消息、排在新话前面 |
| E2 运行中写外部事实，同时用户插话 | 下一次请求里事实在插话前面（边界第 1 步早于第 3 步） |
| E3 空闲时写外部事实后回退到它之前再发 | 新分支的请求里没有它（写在当时的叶子上） |
| E4 用户停止已受理、收口前宿主 `send` | 收口后放行并开一次宿主的运行，多一次模型请求：现在没有门 |
| E5 只压缩的运行里宿主与用户都发话 | 收口批只开一个后继运行、记成用户的，两句都带上（宿主的先） |

另：运行中到达的外部事实进内存的收件箱，只在边界第 1 步写出（`dispatch/mount.ts`、`run/loop.ts`）；在最后一条回复期间到达的要等到下一次运行的第一个边界，进程这期间停了就丢。

**新发现**：扩展的“外部事实”已经是“插件告诉会话一件事”的通道，发送时机正好是开发者定的“下一次请求带上、排在插话前面”。用它做提示（B），比在缓冲区里新加一种（A，提案与 ADR 0056 的写法）少很多内核改动；两条路摆给开发者选，见“当前状态”。

## 开发者的缓冲区分级（2026-11-19）

开发者看过 A、B 两条路后先要求把缓冲区理一遍，按行为分成提醒级、steer 级、followup 级（原话要点）：

1. 用户发一条消息，可以表达成“往 steer 队列加一条、再开 ReAct 循环”，或“一条带用户消息的 ReAct 任务请求（不进 steer 队列）”。
2. steer 队列缺省等到下一次请求前把队列里的消息一起插进会话（可以选择合并成一条用户消息）。
3. followup 队列等到下次空闲时自动发起一次 ReAct。
4. 提醒消息（例如 bun 内核重置）也算一种 steer，但排在 steer 前面；怎么排 Profile 应该可以指定。

在此之上由主 Agent 整理 ReAct 中途取消与恢复；并讲清现在的 Profile 机制（能控制用户消息、哪些写回），给出新缓冲区下 Profile 怎样扩展。

## 决定（2026-11-19，开发者“全部同意”）

1. 用户发话保留“一条带用户消息的 ReAct 请求”：空闲时开一轮、这句话是这一轮的输入；在跑时排进队列（缺省 steer 级，选排队就是 followup 级）；开一轮时待发的提醒随第一次请求带上、排在这句话前面。
2. followup 一条一轮还是合成一轮由 Profile 选，缺省一条一轮。
3. 提醒是缓冲区的一级（选 A，不用扩展的外部事实）；外部事实留给扩展写随路径的事实。
4. Profile 加 `queue` 声明：级别之间的顺序（缺省提醒在 steer 前）与 followup 的批量；steer 合成一段用辅助函数（`turn`、`commit` 里用）。取走的时机、留着与放行、门留在内核。
5. 中途取消与恢复按会话里的表：停止、清空、出错、进程中断时提醒级不动，steer 与 followup 级留着（停止时只有用户能放行、出错时谁排的谁放行、守卫停下的除外），门关；回退到运行中途时运行暂停、门不变；恢复走用户发话（按恢复方式放行、留着的先跑）、点继续（先接着跑被打断的那一轮）、宿主或插件只放行自己排的、提醒级唤起只在门开且空闲时；收口时推迟的话优先开运行。

6. `followups: "all"` 暂缓，等第一个需要它的 Profile 再做；`queue` 这次只有 `order`。设计审查后的四处细化（插话改在压缩之后取、旧日志门按关、只压缩不改门、两轮之间接着跑会带上提醒）开发者知悉（2026-11-19，“没问题”）。
