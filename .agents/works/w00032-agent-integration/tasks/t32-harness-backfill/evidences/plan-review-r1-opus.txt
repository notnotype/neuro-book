依据：上面两处文件:行。

### 2. `modelChoice` 的签名与注释漏了“按用途定角色”这两步，照字面实现会改变模型选择（严重程度：高）
位置：计划“`packages/nb-harness/src/models/rules.ts`（设计问题 7）”的代码块与“理由”段
问题：现在的选择顺序是 `packages/neuro-book/src/plugins/models/backend/core.ts:340-347`：先 `query.role`，再 `purpose === "compaction"` → 角色 `compaction`，再 `purpose === "approval"` → 角色 `fast`，然后才是会话选择、Profile 的 `model`、Profile 的 `role ?? "main"`。计划给 `modelChoice` 写的注释只有三步“指定的角色、会话选的、Profile 缺省的模型或角色”，`MODEL_ROLES` 只列 `main`、`fast`、`compaction` 三个 id，没有表达“用途 approval 用 fast 角色”。照字面实现，`approval` 用途会落到会话选的模型，`auto` 的审批模型从快模型变成对话模型，行为变化且没有测试点名（计划的验收映射只说 `models.service` 输出 8、9 由搬来的测试覆盖）。另外计划“理由”里“审批模型按用途 approval、取不到时退回会话模型”是 kit 侧 `auto-review.ts:131-133`（`role-unbound` 时带 `sessionModel: true` 重试）的行为，与端口的选择顺序是两回事，写在一起容易让人以为退回会话模型由 `modelChoice` 负责。
依据：`core.ts:340-347`；`auto-review.ts:131-133`；`nb-harness/src/kernel/api/model.ts:163-170` 的 `ModelQuery`（`purpose`、`role` 分开）。
建议：`modelChoice` 的注释与返回值把五步写全（指定角色 → 用途对应的角色 → 会话选择 → Profile 模型 → Profile 角色或 `main`），用途到角色的表作为常量导出（例如 `PURPOSE_ROLES = {compaction: "compaction", approval: "fast"}`），在 `rules.test.ts` 里逐步各一条用例；变异检查里“选择顺序”那一项明确包括用途这两步。

### 3. `models/rules.ts` 要的 `ModelQuery` 类型从哪里导入，计划没定；现有边界测试只放行会拖进 OMP 的那个入口（严重程度：中）
位置：计划“`models/rules.ts`（设计问题 7）”末段“`rules.ts` 只引 `typebox`……`boundary.test.ts` 的允许表加 `typebox`”
问题：`modelChoice(query: ModelQuery, …)` 需要内核的 `ModelQuery`（`nb-harness/src/kernel/api/model.ts:163`）。`src/models/boundary.test.ts:10` 的 `ALLOWED` 只放行 `../kernel/index.js`，不放行 `../kernel/contracts.js`；而 `kernel/index.ts` 值导出 `ompCall`、`ompModelInfo`（`./model/omp.js`，引 OMP 与 `Bun.Image`）、`createJsonlStore` 等。实施者照现有测试写 `import type {ModelQuery} from "../kernel/index.js"`：运行期会被擦掉，但 `vue-tsc -p tsconfig.web.json`（`types: ["vite/client"]`，没有 bun 类型）会顺着这条类型导入检查整个内核，`Bun.*`、`node:` 的类型可能报错；有人顺手写成值导入，OMP 就进浏览器包。计划说的“单独核对 `rules.ts` 不引 `node:` 与 OMP”只看 `rules.ts` 自己的说明符，拦不住经 `kernel/index.js` 的传递依赖。
依据：`boundary.test.ts:10`；`kernel/index.ts` 的导出列表；`packages/neuro-book/tsconfig.web.json` 的 `types`。
建议：明确 `rules.ts` 只 `import type` 自 `../kernel/contracts.js`（它注明“不拖内核实现”），边界测试对 `rules.ts` 单列允许表：`typebox`、`../kernel/contracts.js` 且必须是 `import type`；或者 `modelChoice` 的参数改成结构类型 `Pick<ModelQuery, …>` 的本地等价物，彻底不引内核。

### 4. `kit/compaction` 要用 `models/rules.ts` 的角色常量，但 kit 的分层表和导入规则都不允许（严重程度：低）

### 5. 句柄表换成 `clock.wait` 后，“取消”在到点之后不再生效，复查回调要自己识别过期的计时（严重程度：中）
位置：计划“`kit/guards/`、`src/kit/sessions/`”第 2 条（“只比现在晚一个微任务”“then(复查并关闭, 忽略中止)”）；“不做与风险”的“SessionTable 换时钟”
问题：现在 `sessions.ts:276-281` 用 `RuntimeClock.schedule`，取消函数同步摘掉计时，回调里 `entry.cancelIdle = null` 清的一定是自己。换成 `clock.wait(...).then(cb)` 后，到点时 `kernelClock`（`agent.ts:76-95`）在 `schedule` 回调里先 `resolve()`、摘掉 abort 监听，`cb` 排在微任务里；这之间如果同一个同步段里有人调了 `cancelIdle()`（`controller.abort()`）再经 `#release` → `#maybeIdle` 登记了新计时，旧的 `cb` 仍会跑：把新的 `entry.cancelIdle` 清成 null，且按当时的 `refs === 0 && idle` 直接关掉会话，新的 30 秒计时作废。nb-runtime 的 `ManualClock.advance`（`nb-runtime/src/lifecycle/testing/manual-clock.ts:24-31`）正是在一个同步段里按先后执行全部到点回调，并注明“前一个回调可能已取消它”，现有实现依赖取消同步生效；`agent.test.ts:336` 就有 `advance(IDLE_CLOSE_MS * 2)` 这种一次跨过多个计时的写法。生产上的真实时钟每个计时一个宏任务，窗口很小，但“只晚一个微任务”的结论只在“到点与取消不在同一同步段”时成立，计划没写这个前提。
依据：上述文件:行。停止顺序本身（`stop` → `closeGate` → `#close` → `cancelIdle`）不受影响：`abort` 让 `wait` reject、被忽略，`#close` 照旧。
建议：回调开头先查 `controller.signal.aborted` 与 `entry.cancelIdle === 本次的取消函数`，不是就直接返回；`sessions/table.test.ts` 加一条：同一次 `advance` 里先到点、后取消再重登记，断言会话没被提前关。或者 kit 的句柄表直接收一个 `schedule(cb, ms) => cancel` 形状的计时口（与 `RuntimeClock` 同形），不经 `Clock.wait`，保留同步取消的语义。

### 6. 判定者只在 `auto` 的第 6 步可换；其余转问一律交给用户，NeuroBot 要“bot 判定工具调用”只能复制整个钩子（严重程度：高，涉及开发者决定 2）
位置：计划“`kit/approval/`”的 `Reviewer`、`createApprovalHook` 与“怎么接”一段
问题：开发者定的是“判定接口不能写死判定者”，层面是“工具调用这一层”。计划的 `review` 只在 `decide` 交回 `review`（`approvalMode === "auto"` 且不是本地写）时调用；规则的 `ask`、模式闸门的 `ask`、地址分类为 `ask` 的写（`user://`，`hook.ts` 里 `classifiedAsk`）、项目规则读坏后的 `ask`、`auto` 下审批模型转人工，全部作为 `{verdict: "ask"}` 交回内核问用户，判定者仍被写死为用户。`auto` 下本地写（`isLocalWrite`）又绕过判定者直接放行。计划给的出路是“用导出的 `decide` 与 `createApprovalHook` 之外的组合自建钩子”，但把调用整理成判定对象的部分（`hook.ts` 的 `buildViews`、`redirectTarget`、`classify` 闸门分类、`isLocalWrite`、`rememberFor`，约 150 行）计划没说导出，自建就要复制，以后两份分叉。NeuroBot 提案第七节还要“任务运行不等审批，清单外直接拒绝”，同样需要在“要转问用户”这一点换成别的处理。
依据：`packages/neuro-book/src/plugins/agent/backend/permissions/hook.ts:43-95`（`decide` 之后只有 `review` 一个分叉）、`judge.ts:27-46`；`docs/proposals/neurobot.md` 第 157-161 行。
建议：把“谁来回答需要询问的调用”做成钩子的一个选项，例如 `escalate?: (request: ReviewRequest & {source: "rule" | "gate" | "address" | "rules-invalid" | "reviewer"; reason?: string}, ctx) => Promise<ApprovalVerdict>`，缺省原样交回 `ask`（NeuroBook 不传，行为不变）；或者导出一个纯的 `evaluate(call, info, ctx) → {decision, request, remember}`，`createApprovalHook` 建在它上面，宿主可以只换最后一步。两种都不改内核，也不改 NeuroBook 的行为；计划至少要写明选哪种，免得 NeuroBot 落地时回头改 kit 的公开接口。

### 7. `localFiles` 被定位成 NeuroBot 的实现，但缺 NeuroBot 提案明写要的写锁与改动记录，`forCall` 把调用身份丢了（严重程度：中）
位置：计划“`kit/files/`”的 `files/local.ts` 段；“需要开发者确认”第 4 条
问题：计划说 `localFiles` “也是 NeuroBot‘直接读写 bot 的电脑’的实现”，`write` 是“按基线核对后写临时文件再改名”，`forCall` “不分组”。NeuroBot 提案第五节对记忆目录的要求是“目录一把写锁，写暂存文件后改名；每次改动记一条（时刻、会话、工具调用、来源）”。按计划的写法：(a) 没有锁，核对基线与改名之间另一个会话（主对话与任务会话共用一台电脑，提案第七节）的写入会被静默覆盖，`expect` 失去意义；(b) `forCall(call)` 交回的 `FileCalls` 不带 `callId`、会话，`localFiles` 的选项里也没有记录改动的回调，NeuroBot 想记“哪个会话哪个调用写的”只能另包一层、自己再实现一遍 `forCall`；(c) `classify?` 可选但没写缺省值，缺省若是 `allowed`，`allow-writes` 下 bot 可以改自己的规则与设置文件（NeuroBook 靠 `user://` 分类为 `ask` 防这一点，`permissions.md` 输出 7）。这些不补，NeuroBot 实际用时要改 `localFiles` 的选项形状，即改 kit 的公开接口。
依据：`docs/proposals/neurobot.md` 第 131 行（写锁、改动记录）、第 155-156 行（共享一台电脑、文件访问由 NeuroBot 实现）；计划原文。
建议：二选一写清。其一，`localFiles` 只定位为 kit 测试的真实依赖与参考实现，确认项第 4 条改成“NeuroBot 自己实现 `SessionFiles`，可以包 `localFiles`”；其二，现在就给它进程内按根的写锁（基线核对与改名在锁内）、`onWrite({address, session, callId, title})` 回调，`classify` 缺省为 `denied` 或必须传。无论哪种，确认项第 4 条的“NeuroBot 也直接用它”要与提案“文件访问由 NeuroBot 实现”对齐。
