## F1 没有在跑的任务时，状态栏“后台任务”条目悬停出一个 16rem 宽的空提示框，`tooltip()` 的文字永远显示不出来

- 严重程度：重要；类别：正确性
- 位置：`packages/neuro-book/src/plugins/tasks/web/plugin.ts:111-115`（`tooltip` 与 `hover`），`src/plugins/tasks/web/components/TasksHover.vue:19-28`、`.tasks-hover { width: 16rem }`，`src/plugins/workbench/web/components/WorkbenchItemStrip.vue:117-145`（`tooltipOf` 在有 hover 时返回 undefined，`<Tooltip>` 包着按钮）
- 现象：任务条目的 `hover` 是写死的对象，条目一出现（清单不空）就一直有。只剩结束的任务（淡色任务图标，或危险色失败图标）时，`WorkbenchItemStrip` 仍走 `Tooltip` 分支：原生 `title` 被去掉，悬停 300ms 后弹出的提示框里是 `TasksHover`，而它 `v-for` 的 `store.running.value` 是空，只剩一个 `width: 16rem` 的空 span，也就是一个空白的深色胶囊。`tooltip: () => tasksText(unseenFailure ? "status.failed" : "status.idle")` 写了却没有任何路径会显示（`WorkbenchItemHover` 的 `fallback` 只在加载中、加载失败时才露出一下）。
- 为什么是问题：这正是“只有一个图标”的状态，也是条目最需要提示文字说明图标含义的时候（失败图标、淡色图标）；现在悬停得到一个空框，键盘聚焦同样（Tooltip 聚焦即显示）。`TasksHover.md` 自己写“没有在跑的任务时……条目这时没有悬停内容可看，只剩图标”，与实现不符：实现不是“没有悬停内容”，而是画出空框。测试与 e2e 都没有覆盖“没有在跑的任务时悬停”（`TasksView.dom.test.ts:146-153` 只测有在跑的）。
- 如何核实：看代码即可；真实运行时复现：`TasksFixture` 里让清单只剩结束的任务，悬停条目 300ms，检查 `[data-tasks-hover]` 的子节点为 0、而 `.nb-ui-tooltip-surface` 存在。
- 建议改法：最少的改法是 `TasksHover` 在没有在跑的任务时渲染条目的提示文字（`status.failed`/`status.idle`，同 `plugin.ts` 里 `tooltip()` 的两个键），宽度也只在有行时才定为 16rem；或把 `ItemImplementation.hover` 改成可返回 `null` 的函数 `hover?(): ItemHover | null`，没有可列的内容时退回 `tooltip()`（后者让外壳按状态选，更符合“有它时取代 tooltip()”的合同语义）。无论哪种，补一条“只剩结束的任务时悬停显示图标的含义”的测试。

## F2 通知中心里的详情没有按 8000 码元截断：中心里点“详情”看到并复制到完整原文，也不注明已截断

- 严重程度：重要；类别：正确性（合同）
- 位置：`packages/neuro-book/src/plugins/workbench/web/notifications.ts:138-148`（`notify` 里 `detail = hasNotificationDetail(input.detail) ? input.detail : undefined`，`detailTruncated` 只取发出方给的）、`:178-179`（`update` 里 `patchEntry(id, {detail: patch.detail, detailTruncated: patch.detailTruncated === true})`）；对照 `packages/nb-ui/src/composables/useNotification.ts:45-69`（`boundDetail` 只在 nb-ui 队列里截）
- 现象：截断与“已截断”标志的 OR 只发生在 nb-ui 队列的 `detailFields` 里。中心条目 `CenterEntry` 是自己另存的一份，存的是 `input.detail` 原文。所以发出方交一段 20000 码元、没带 `detailTruncated` 的详情时：右下角弹出的那条“详情”是 8000 码元加“原文过长，已截断”，而通知中心里同一条的“详情”（`WorkbenchNotificationsView.vue:63-72` 取 `entry.detail`）是 20000 码元、`truncated` 为假、没有注明，“复制原文”把全部 20000 码元交给剪贴板。“通知”视图开着时发出的通知不进队列，这时只有中心这一份，永远不截。
- 为什么是问题：notifications.md 输入段与失败表要求“载体最多留 8000 个 UTF-16 码元，超出的截掉并注明已截断”；同一条通知两个入口行为不一致；中心至多 100 条，每条的详情无界，内存也没有上限（诊断原文含堆栈时很大）。任务通知的 detail 已在服务端截过，所以任务这条路径看不到，但通知服务对所有发出方开放。
- 如何核实：`notifications.dom.test.ts` 里加一例：`notify({message: "m", detail: "x".repeat(9000)})`，读 `center.entries.value[0].detail.length`（预期现在是 9000，应为 8000）与 `detailTruncated`（应为 true）；再在 `center.setVisible(true)` 之后发一条，同样检查。
- 建议改法：把 `detailFields`（含 `boundDetail`）从 nb-ui 的 `notifications` 子路径导出，`notify` 与 `update` 的中心那份与队列共用它，不在两处各写一份规则；或者反过来中心的详情取队列条目归一后的结果（但视图开着时没有队列条目，所以前者更直接）。补测试：中心的详情长度、`detailTruncated`、`update` 同样。

## F4 状态栏任务条目只有图标时，读屏拿不到“有没看过的失败”；视图与通知中心每行的“取消 / 重试 / 详情 / 移除”没有行上下文

- 严重程度：重要；类别：正确性（可访问性）
- 位置：`packages/neuro-book/src/plugins/tasks/web/plugin.ts:97-116`、`src/plugins/workbench/web/components/WorkbenchItemStrip.vue:30-34,117-135`；`TasksView.vue:100-105`、`WorkbenchNotificationsView.vue:95-98`
- 现象一：任务条目没有在跑的任务时 `text()` 为空串，条目的读屏名称（`nameOf`）只剩声明的标题“后台任务”；图标是 `aria-hidden`；失败与否只在 `tooltip()` 里（`status.failed`/`status.idle`），而有 `hover` 的条目又把 `title` 去掉（`tooltipOf` 在有 hover 时返回 `undefined`）。所以读屏用户只会听到“后台任务，按钮”，听不出有没看过的失败（危险色图标是唯一信号，颜色加图标形状，对读屏等于没有）。`WorkbenchItemStrip.dom.test.ts` 的图标用例用的是 `title: "后台任务：1 个没有成功"` 这种把状态写进标题的假条目，真实的任务条目并不这样给。

## F5 在两次推送之间“开始又失败”、且没有详情的任务，不发失败通知（输出 14 的“上一份里没有它”情形漏了）

- 严重程度：重要；类别：正确性
- 位置：`packages/neuro-book/src/plugins/tasks/web/store.ts:61-76`（`announce`）与 `:78-98`（`accept`）
- 现象：`accept` 在循环里调 `void announce(item)`，此时 `items.value` 还是旧清单（`items.value = next` 在第 96 行，循环之后）。`announce` 对失败的任务先 `const detail = item.hasDetail ? await store.detail(item.id) : null`，`hasDetail` 为假时没有 `await`，整个函数同步往下走到第 68 行 `if (!items.value.some((entry) => entry.id === item.id)) return;`：旧清单里没有这件任务（正是“上一份里没有它”的情形：任务在一次合并推送的间隔内开始并失败），于是直接 return，通知不发，`announced` 里也没有它。带详情的因为有 `await`，检查时 `items.value` 已是新清单，所以能发；成功的不经这个检查，也能发。只有“新出现 + 失败 + 没有详情”这一格漏掉。
- 为什么是问题：输出 14 明说“上一份清单里它在跑，或上一份里没有它”都发；“重试后马上失败”“登记即失败”（例如装依赖时 registry 立刻连不上）正是最常见的快速失败，用户既没看到通知，条目又因为 `unseenFailure` 也许是真，只剩图标变红。`store.test.ts` 的失败用例都是先 `settled` 等到“在跑”再 `fail`，没有覆盖这一格。
- 如何核实：我在 `/tmp/review-t34-impl/scratch-frontend/fast-fail.test.ts` 里用真实的 `createTasksStore` 加一个只捕获推送回调的远程替身，依次推：新出现且失败、无详情的一件（`sent: 0`）；新出现且成功的一件（累计 1）；新出现、失败、带详情的一件（累计 2）。`cd /tmp/review-t34-impl/scratch-frontend && bun test ./fast-fail.test.ts`。（替身只替了传输，`accept` 与 `announce` 是真实代码；真实服务端上的复现是：`start` 后在同一个 250ms 窗口内 `fail`，不带 `detail`。）
- 建议改法：“任务已离开清单”的检查改成基于这次要接受的清单：`announce(item, present)`，或者让 `accept` 先 `items.value = next` 再发通知，使两条路径（有无 await）看到同一份清单；更简单的是让这个检查只用在 `await` 之后（`if (item.hasDetail) { const detail = await …; if (!items.value.some(...)) return; }`）。补用例：不先经过“在跑”，直接推一份已失败（无详情）的清单，断言发出一条；以及取详情的这会儿任务被移出时不发。

## F6 `store.start` 在订阅等待期间被 abort 时，退订监听挂得太晚，订阅泄漏

- 严重程度：建议；类别：不变量（资源释放）
- 位置：`packages/neuro-book/src/plugins/tasks/web/store.ts:125-136`
- 现象：`signal.addEventListener("abort", …, {once: true})` 在 `await remote.events.changed.subscribe(...)` 之后才登记。入口在订阅完成之前停止（启动即激活，页面刚打开就切换或应用关停）时，`abort` 事件已经派发过，监听器永远不会触发，订阅不释放；`refresh()` 也照样跑、`accept` 照样发通知。
- 如何核实：测试里先 `stop.abort()` 再 `await store.start(stop.signal)`，用替身记录 `release` 次数（预期 1，现在 0）。若远程运行时在入口停止时本来就会回收这个入口的全部订阅，则此条降为“多余的防御缺失”，请主 Agent 先看 `context.remote` 的停止语义。
- 建议改法：订阅后先判 `signal.aborted` 立即 `release()` 并返回；监听器仍保留给之后的 abort。

## F9 悬停提示组件的小问题与代码重复

- 严重程度：建议；类别：代码质量
- 位置与建议：
  1. `WorkbenchItemStrip.vue:114` `<component :is="hoverOf(entry) === null ? Bare : Tooltip">`：条目按钮的可用性（`disabledReason`）变化时，外层组件在 `Bare` 与 `Tooltip` 之间切换，按钮被卸载重建（焦点丢失，正在进行的悬停丢失）。任务条目的命令永远可用，现在碰不到；有命令会变不可用的条目一用就会碰到。直接用 `<Tooltip :disabled="hoverOf(entry) === null">` 包着所有条目（nb-ui 的 `Tooltip.disabled` 就是为此设计的：禁用时不开、已开的关上），可以删掉 `Bare`。
  2. `items/registry.ts:150-162`：悬停组件的 `load` 失败后 `loading` 的拒绝结果被永久缓存，一次网络抖动导致的分块加载失败，直到刷新页面条目都只有文字退回、没有重试。若要保持“只记一条诊断”，可以失败后清掉 `loading` 允许下次悬停重试，诊断仍由 `reported` 去重。
