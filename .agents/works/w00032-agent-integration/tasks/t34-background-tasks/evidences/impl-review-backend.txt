## 1. 结构化文字按引用存进清单：发起方之后改动这个对象就绕过校验，整份清单的 `list` 与全部推送一起失败，用户还移不掉这件在跑的任务

- **严重程度**：重要；**类别**：正确性 / 不变量
- **位置**：`packages/neuro-book/src/plugins/tasks/backend/core.ts:91-99`（`normalizeText` 对文字引用与语言映射 `return {ok: true, text: value}`，存的是调用方传进来的那个对象）；用到它的 `startFor`（:209-221）、`report`（:175-177）、`succeed`/`fail`/`cancelled`。
- **现象**：校验只在登记与更新的那一刻做，之后清单里放的仍是发起方手里的同一个对象。发起方复用这个对象（例如留着一个 `{kind: "text", ns, key, params}` 下次改 `params.count` 再 `report`），在改和下一次 `report` 之间，或者改成不合格的值时，清单内容变了却没有经过 `normalizeText`，也没有 `changed()`。
- **为什么是问题**：文件头写明的不变量是“进了清单的每一项都要过远程合同的 schema……一件不合格就会让全部窗口收不到推送”，计划审查第 9 条正是为此加的入口校验。按引用存放让这个不变量只在登记那一刻成立。实测后果是全局的：`list` 得 `provider-error`（“返回值不符合合同：/0/message/params/count …”），推送被远程节点按 `payload-invalid` 丢掉（`nb-runtime/src/remote/node.ts:930-938`），所有窗口都收不到任何后续变化；`nbook.tasks` 自己不记任何 `tasks.*` 诊断；这件任务在跑，`remove` 得 `running`，用户无法自救，直到发起方结束它。即使改成合格的值，窗口也要等下一次无关的变化才看到。
- **如何核实**：`/tmp/review-t34-impl/scratch-backend/probe.test.ts` 的 E1：`start({title: "t", message: msg})` 后订阅，`msg.params.count = true` 再 `report({progress: 10})`，推进时钟 5 个间隔：推送数停在 1，`client.list({})` 得 `{"ok":false,"code":"provider-error",...}`。运行：在 `packages/neuro-book` 下 `bun test /tmp/review-t34-impl/scratch-backend/probe.test.ts`。
- **建议改法**：`normalizeText` 已经为量大小做了 `JSON.stringify(value)`，直接存 `JSON.parse(json)` 的副本（或 `structuredClone`），一行改动；字面字符串不受影响。这样清单里的值归清单所有，入口校验即终身有效。补一条测试：登记后改动传入的对象，`list` 仍是登记时的值。

## 2. 只校验了文字字段：`detail` 不是字符串时 `fail` 抛错而不是“不起作用、记诊断”；`retry` 不是函数时照样登记成可重试

- **严重程度**：建议；**类别**：正确性
- **位置**：`core.ts:106-111`（`normalizeDetail` 直接 `value.trim()`）、`core.ts:190-197`（`fail`）、`core.ts:170-173`（`report` 直接读 `patch.message`）、`core.ts:213-219`（`retry: input.retry` 不查类型）、`core.ts:135`（`retryable` 只看 `!== undefined`）。
- **现象**：实测（probe.test.ts E2）：`fail({message: "x", detail: 42})` 抛 `TypeError: value.trim is not a function`；`report(undefined)` 抛 `TypeError: ... evaluating 'patch.message'`；`start({title: "t2", retry: true})` 不抛，`fail` 后 `retryable: true`，窗口会显示“重试”，点了只得到一条 `retry-failed` 诊断、旧行被删。
- **为什么是问题**：Spec“输入与前置条件”写的是“句柄的方法这一次调用不起作用，记诊断”，输出 3 与“时序与寿命”写“调用不起作用、不抛错”；`start` 的输入不合格要同步抛 `TypeError`，`retry` 也是输入的一部分。TS 类型挡住了第一方调用方，影响有限；但 `test.tasks-probe` 就是把 HTTP 正文原样 `as` 进 `fail`（`test-plugins.ts` 的 `case "fail"`），e2e 写错正文时这里会抛进 Hono 而不是按合同忽略。
- **如何核实**：`bun test /tmp/review-t34-impl/scratch-backend/probe.test.ts`（在 `packages/neuro-book` 下），看 E2 的三行输出。
- **建议改法**：`startFor` 里 `input.retry !== undefined && typeof input.retry !== "function"` 时抛 `TypeError`；`fail` 里 `failure.detail !== undefined && typeof failure.detail !== "string"` 时走 `textFor` 同样的“记诊断、这次不起作用”；`report`/`fail` 的参数本身不是对象时同样处理。不必为此加测试以外的机制。

## 5. `TaskRecord.released` 是多余的状态：`release()` 已把发起方在跑的任务转为结束、清掉 `retry`，`live()` 只看状态就够

- **严重程度**：建议；**类别**：代码质量
- **位置**：`core.ts:63-64`（字段）、`:157`（`live` 里的 `!record.released`）、`:216`（初值）、`:240-243`（`release` 里的读写）。
- **现象**：`release(consumer)` 对发起方名下的记录只做两件有效的事：在跑的 `finish(..., "interrupted")`，全部的 `retry = undefined`。之后 `live(record)` 因 `state !== "running"` 已经为假，`retry` 因 `record.retry === undefined` 已经不可用；`released` 不再改变任何可观察结果。它在 `release` 循环里的唯一作用是让第二次 `release` 同一调用方时跳过，而第二次本来也是空操作（只会多一次 `changed()`，运行时每个门面只释放一次，这种调用不会发生）。
- **为什么是问题**：多一个要和 `state`、`retry` 保持一致的布尔，读者要推演“released 为真但 state 仍是 running”能不能出现（不能）。字段注释“发起方释放后为 true：句柄作废”也让人以为句柄作废靠它，实际靠的是状态转换。
- **如何核实**：删掉这个字段与 `live` 里的条件、`release` 里的 `|| record.released` 与赋值，`touched` 改为“有在跑的被中断或有 `retry` 被清掉”；`bun test src/plugins/tasks/tasks.test.ts` 应仍 16 过（未实际跑，推断）。
- **建议改法**：如上删除，`release` 写成：遍历时 `if (record.owner !== consumer) continue; if (record.retry !== undefined) { record.retry = undefined; touched = true; } if (record.state === "running") interrupted.push(record);`，中断非空时同样 `touched = true`。

> 第 5 条补充（核实）：在副本里按“建议改法”删掉 `released` 后实际跑过，16 过 0 败；副本已还原。

## 6. 零碎：量大小的写法、超限诊断的频率、远程方法的样板、计划偏差、测试探针

- **严重程度**：建议；**类别**：代码质量 / 安全与性能 / 文档
- **位置与现象**：
  1. `remote.ts:65,72` 与 `core.ts:88,97` 各建一个 `TextEncoder`，用 `utf8.encode(JSON.stringify(x)).length` 量字节，每次都分配整份缓冲。Agent 的同类检查用的是 `plugins/agent/backend/frames.ts` 的 `byteLength`（`Buffer.byteLength`，不分配）。服务端代码可直接用 `Buffer.byteLength(JSON.stringify(x))`。量级：结束的至多 50 件、每件按上限约 4.5 KB，每个订阅每 250 毫秒一次，开销小，改它只为与相邻实现一致。
  2. 清单超限时，`bounded()` 每次被调用都记一条 `tasks.list-too-large`：每个订阅每 250 毫秒一条，再加每次 `list`。只在在跑的件数极多时发生；与 Agent 的 `tree-too-large` 同一做法，可接受，但若想收敛，只在“未超限 → 超限”翻转时记一次即可。

  5. 场地 `testing/world.ts:49` 的发起方插件 id 是 `test.tasks-probe`，与 `server/testing/test-plugins.ts` 的 HTTP 探针同名、定义不同；两者不同时装载，不出错，但查诊断或日志时同名不同物。场地的改名为 `test.tasks-owner` 即可。
  6. `test-plugins.ts` 的 `POST /:task/:method` 用 `c.req.json(...).catch(() => ({}))` 吞掉所有解析错误：正文写坏的 e2e 会静默地当成空参数（例如 `fail` 的 `message` 变成 `undefined`，走“文字不合格、这次不起作用”），失败原因要绕一圈才查得到。改成正文为空时用 `{}`、非空但解析失败时回 400。

## 未发现问题的方面

- **按调用方的登记与释放**：门面工厂与释放回调收到同一个冻结的 `ConsumerIdentity`（核对 `nb-runtime/src/services/composition.ts:585-618`：先 `facade.revoke("released")` 再同步调用 `provision.release(facadeTarget, consumer)`，两者之间没有可插入的调用）。释放后旧门面的 `start` 抛 `ServiceRevokedError`；旧句柄靠状态转换失效；换代后新代次是另一个身份对象，与旧记录互不影响。核心全部同步，`release` 与在途的 `report`/`succeed`/`fail` 不会交错：之后到达的调用一律不起作用。`release` 之后 `retry` 回调不会再被调用（`retry` 字段已清，`not-retryable`）。
- **重试的顶替时序**：`drop` 与 `changed()` 在调用回调之前，回调同步 `start` 时两次 `changed()` 落在同一个合并窗口，推送里不会同时出现新旧两行；回调异步登记时会有一份两行都没有的推送，Spec“时序与寿命”只对同步 `start` 作承诺，符合。抛错与 Promise 失败都记 `tasks.retry-failed`、返回成功、旧行已移出；对在跑、成功、已中断、发起方已停止的任务都得 `not-retryable`，对已移出的得 `unknown-task`，与失败码表一致（状态表那一行的文字除外，见第 3 条）。
- **截断**：标题 200、进展与原因 500、详情 8000 都按 UTF-16 码元截，`truncate` 在第 `max-1` 位是高代理时退一位，实测不切开代理对（E3）；详情先 `trim` 再截、`truncated` 标记正确；文字引用缺 `ns` 与超过 1 KiB 的判定正确；`params` 里的 `NaN`、`Infinity` 被 `TextSchema` 拒绝（实测 `Value.Check` 为假），不会经 JSON 变成 `null` 再坏掉整份清单。
- **推送**：订阅时立即排一次推送（延迟 0）；`PushThrottle` 保证两次推送之间至少 250 毫秒；订阅结束（含提供方停止，`ended` 联了 `found.stopSignal`）时取消计时器并退订；超过 512 KiB 时跳过推送、`list` 得 `too-large`。按上限算，结束的 50 件每件至多约 4.5 KB（含 JSON 转义），到不了 512 KiB，Spec 的说法成立。
- **`PushThrottle` 搬家**：只改了文件位置、引用路径与头注释，逻辑逐字未变；`bunx tsc --noEmit` 无错误；`src/plugins/agent/subagents.test.ts` 27 过 0 败。
- **上限与清理**：第 51 件结束时 `shift` 掉最早结束的；被丢的记录随后的 `detail`、`retry`、`remove` 得 `unknown-task`，核心同步，不存在“读到一半被丢”。除在跑的（Spec 不设上限）外没有无界增长：订阅监听随订阅退订，门面不在核心里留映射，结束的记录至多 50 件、发起方释放后不再持有它的 `retry` 闭包。
- **登记**：`manifest.ts`、`server/plugins.ts`、内置名单与名字、命令域词表、`server.test.ts` 的期望都已同步；`test.tasks-probe` 只出现在 `TEST_PLUGIN_IDS`，由测试入口 `server/testing/fixture-entry.ts` 按请求装载，不进产品装配。
