### 1. 预览把审批事件撑过 256 KiB 内联上限，占位里没有 id 和请求，向导画不出来，运行一直等
**严重程度**：重要
**类别**：接口与不变量（两个上限互相矛盾）
**位置**：/home/notnotype/CodeRepository/neuro-book/.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md:68,74-75（`applyEvent(item)`、`pending()`）；/home/notnotype/CodeRepository/neuro-book/docs/specs/harness/runtime.md:142（输出 76“单份上限 256 KiB”）；/home/notnotype/CodeRepository/neuro-book/.worktree/w00032-t17-conversation-ui/packages/neuro-book/src/plugins/agent/backend/frames.ts:14,26-29；同 worktree packages/nb-harness/src/kernel/run/tools.ts:265
**现象**：单份预览上限是 256 KiB，而远程层对整条事件的内联上限也是 256 KiB。`interactionRequested` 同时带 `args`（`write` 的 `content`、`edit-replace` 的 `old_string`/`new_string`）、`preview.before`、`preview.after`，三者相加后，文件约 128 KiB（约 4.3 万个汉字）起就变成 `{kind:"oversized", seq, type, bytes}`。占位里没有事项 id、`callId`、请求内容。计划的 `pending()` 定义为“`interactionRequested` 减去 `interactionResolved`”，`applyEvent` 是同步纯函数、“认不出的跳过”，整份计划与 `conversation.md` 没有出现 `eventChunk`，也没说占位之后的帧怎样保序。
**为什么是问题**：照字面实现，大文件的审批得不到向导：`pending()` 为空，运行在 `waiting`，用户看不到批准按钮。这正是“预览”这个新功能自己制造的路径，不是罕见旧数据；设定集、全书大纲这类文件在写作产品里能到这个大小。计划风险表只提了“预览进日志，每次多存一份”，没发现它撞内联上限。另外预览进日志后，首屏 `path` 每条历史审批都要重传一次全文（改一章 30 KiB 的文件 100 次，约多传 6 MB；磁盘上 blob 按内容去重，传输不去重），而审批结算之后这些预览再也不显示。
**如何核实**：`bun /tmp/review-t17-design/opus/remote.ts`，经 `agentWorld`、真实远程 `send`、真实工具 `ctx.ask`，请求里放前后各 7 万字的文字（每份约 210 KiB，低于单份上限）：帧与 `path` 里都得到 `oversized:interactionRequested:420302`，同一时刻 `status:waiting` 只有 `{id, callId, kind}`。
**建议改法**：二选一，都比现在简单。（甲）预览不进日志：`interactionRequested` 只带 `args`，预览由只读查询按事项 id 现算（报告 design-backend 第 1 条已建议的方向），同时解决这里、日志膨胀和懒加载三件事。（乙）若保留进日志：预览只存改动块与上下文，不存全文，整条事件预算压到内联上限以内，超了给 `too-large`；单份上限改成“整条事件不超过 200 KiB”。无论选哪个，都要给占位定接法：`session-host` 遇到 `oversized` 先经 `eventChunk` 拼回再按 seq 顺序交给 `applyEvent`，后续帧排队；`kernel-transcript` 不接触远程。向导的存在以 `status.waiting.pending` 为准，请求内容拿不到时降级显示“内容过大”，审批按钮仍在。加一条大文件审批的验收。

### 2. “第 1 / 3 个”算不出来：写入工具都是 exclusive，待处理事项永远只有一条；拒绝第一个之后后面的照问
**严重程度**：重要
**类别**：依赖的机制不存在（已定设计与内核调度不符）
**位置**：/home/notnotype/CodeRepository/neuro-book/docs/specs/agent/conversation.md:65（输出 11）、“状态与转换”表；/home/notnotype/CodeRepository/neuro-book/.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md:75,81,88；/home/notnotype/CodeRepository/neuro-book/docs/specs/agent/builtin-tools.md:38-43（`write`、`edit`、`shell` 都是 exclusive）；/home/notnotype/CodeRepository/neuro-book/.worktree/w00032-t17-conversation-ui/packages/nb-harness/src/kernel/run/tools.ts:340-345（只有连续的 shared 并发）、run/interaction.ts:43-46
**现象**：计划的数据来源是 `pending()` = 请求减结算。一条回复里三个 `edit` 时，exclusive 工具逐个执行，第二个的审批要等第一个结算并执行完才写下。所以 `pending` 始终是 1 条，向导只能显示“第 1 / 1 个”三次。两次审批之间状态回到 `running/tools`，按 Spec 的状态表向导离开（“全部答完”）、输入框回来，下一个审批再把它盖住；“收起”状态也无处保留。另外用户拒绝第一个并写附言“停，别改了”之后，第二、第三个照常来问，已批准的那个工具卡片一直转到整条回复做完（F4）。
**为什么是问题**：开发者定的是“几个审批逐个处理，向导标第 1 / 3 个”（README 注意力排序第 3 条）。这个行为没有数据来源；Lab 用静态夹具能画出来，所以到 e2e 才会发现。输入框在两次审批之间短暂可用，用户此时打字或回车会变成一次插话。拒绝加附言是审批向导的主要纠错手段，附言却要等后面的审批全部处理完才到模型手里，体验上是“我说了停，它还在问”。
**如何核实**：`bun /tmp/review-t17-design/opus/approvals.ts`（真实内核、`createTestSession`、真实 `resolve`）：一条回复三个 exclusive 写工具，三次都打印 `pending 1`；帧序列 `waiting(1) -> interactionResolved -> running/tools -> interactionRequested -> waiting(1) -> ...`；三次之间 `toolResults so far` 是 0、0、3；第一个的结果 `denied/user-denied` 带附言，后两个 `ok`。
**建议改法**：分母按 `assistant.toolCalls` 算：这条回复里还没有 `toolResult` 的调用数是上界，序号是其中已结算的数加一；Spec 写明分母可能减少（后面的调用不一定要审批）。若不想要会变的分母，就把 Spec 改成“这条回复还有 N 个调用”。向导状态表加“同一条回复的工具段内不离开”：`status.running.phase === "tools"` 且这条回复还有未开始的调用时保持向导外框与收起状态，输入框不回来。拒绝的后续行为交开发者定：要么维持现状并在向导里写明“后面的还会问”，要么内核加“这条回复里一旦用户拒绝，其余未开始的调用记 `denied`、码 `aborted-by-denial`”（改 `run/tools.ts` 的段循环，几行）。验收 2 加一条三个调用的回复；`testing/endpoint.ts` 目前一条回复只能脚本一个工具调用，要扩（见第 11 条）。

### 5. `toolResult.status` 的五个值对不上 `ToolCallStatus`，映射没写，`unknown` 和拒绝会显示错
**严重程度**：重要
**类别**：接口与合同
**位置**：/home/notnotype/CodeRepository/neuro-book/.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md:76；/home/notnotype/CodeRepository/neuro-book/.worktree/w00032-t17-conversation-ui/packages/nb-agent-ui/src/types.ts:43；同 worktree packages/nb-agent-ui/src/tool-status.ts:8-16、packages/nb-harness/src/kernel/api/tool.ts:47-50、packages/nb-harness/src/kernel/run/tools.ts:204-215、packages/nb-agent-ui/src/conversation-turns.ts:386-390
**现象**：内核是 `ok | error | denied | blocked | unknown`，视图是 `streaming | running | success | error | invalid`。计划只写“`toolStarted`、`toolResult` 挂到调用上”。F15 第 4 点早就指出要视图新增状态，计划把 F15 一并判为不做，而 `ui/agent-conversation-view.md` 的改动清单里也没有工具状态。还有两个没有对应的中间态：调用在等审批（有 `interactionRequested`、没有 `toolStarted`）与等回答（`ask` 的 `toolStarted` 已写）。
**为什么是问题**：最省事的实现是“不是 ok 就 error”，于是：用户自己拒绝的调用显示成红色失败，思维链把它算进失败；`unknown` 显示成普通失败，而内核专门区分它，就是因为这时副作用不确定（tools.ts:204-205 的注释：`denied` 不必提示用户核对副作用，言下之意 `unknown` 要）。服务端重启后用户看到的正是这种调用（验收 5 的场景），写文件可能已经落盘，用户不知道要去核对。`code` 为 `invalid-arguments` 才对应 `invalid`，也要写进映射。
**如何核实**：对照两边类型；`/tmp/review-t17-design/opus/approvals.ts` 真实产生 `denied/user-denied`；recover.ts:25-30 产生 `unknown/interrupted` 与 `denied/interrupted-before-approval`。
**建议改法**：Spec 写明映射表，视图 `ToolCallStatus` 加 `denied`、`unknown`（`toolCallPhase` 同步处理）：`ok → success`；`error` 且 `code: invalid-arguments → invalid`，其余 `error → error`；`denied`、`blocked → denied`，副文字按 `code` 与 `by` 区分“你拒绝了”“规则拒绝”“只读模式”“还没开始就停了”；`unknown → unknown`，文字写明“不确定有没有执行完，请核对”。等审批、等回答的调用状态按 `status.waiting.pending` 的 `callId` 标成 `running` 加“等你处理”，不让它和普通执行中无法区分。`result.text` 给模型看的英文（`The user denied the call…`）不直接显示。

### 6. 转录映射其余部分的缺口：提醒文字、认不出的事件、增量用途、压缩之后、中断判定
**严重程度**：重要
**类别**：接口与合同；遗漏
**位置**：/home/notnotype/CodeRepository/neuro-book/.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md:72,76-77；/home/notnotype/CodeRepository/neuro-book/.worktree/w00032-t17-conversation-ui/packages/nb-harness/src/kernel/api/events.ts:124-133,246-258；同 worktree packages/nb-harness/src/kernel/run/commands.ts:143-145、packages/nb-harness/src/kernel/api/host.ts（`DeltaFrame.purpose`）
**现象**：逐项：

**为什么是问题**：这些都是实现时一定要做决定的点，没写就会各写各的；`text` 直接显示会把内部标签露给作者。
**如何核实**：`opus/remote.ts` 的帧时序列出了实际事件类型；其余读 events.ts 与 commands.ts。压缩中断的 `nothing-to-continue` 是读代码得出，未跑（第一版没有压缩方法）。
**建议改法**：计划或 Spec 里给一张完整事件表，每种事件三选一：产出视图内容、改状态、明确忽略；只有真正不认识的类型（且不是 `ext` 声明的）才记 `problems()`。提醒条目按 `code`、`by` 查文案，`tools-changed`、`restored` 第一版不进消息流，`result-requested`、`continued{by:"core"}` 显示一行小字。`applyFrame` 只画 `purpose === "turn"`。压缩写一句定论：界面照旧显示全部历史，只加一条分隔（`source: "compaction"`，`text` 取 `replacement ?? ""`），占用在下一次回复前取 `tokensAfter`。`interrupted()` 只看 `kind: "chat"` 的运行，或者 `start` 得 `nothing-to-continue` 时把输入框退回普通状态。

### 14. 乐观用户消息没有对账键：`input` 帧先于 `send` 的响应到达
**严重程度**：建议
**类别**：并发；遗漏
**位置**：/home/notnotype/CodeRepository/neuro-book/.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md:98；/home/notnotype/CodeRepository/neuro-book/.worktree/w00032-t17-conversation-ui/packages/nb-agent-ui/src/types.ts:60-70（`delivery`）；同 worktree packages/nb-harness/src/kernel/api/host.ts（`send` 的 `value: {inputId, runId}`）、packages/nb-harness/src/kernel/run/input.ts
**现象**：计划只写“乐观显示用户消息”。真实时序是 `log:inputQueued | log:runStarted | log:inputConsumed | log:turnStarted | log:input | log:commandAccepted | <<send-response>>`：`input` 帧到的时候 `inputId` 还不知道，乐观消息与真实消息会并存到响应回来；输入链拦截还可能改写 `text`，不能按文字比。运行中 `enqueue` 走 `buffer`，是另一条路径。断线时写指令得 `unknown-outcome`，`delivery: "unknown"` 之后的重发（同一个 `commandId`）也没写。
**为什么是问题**：每次发送都闪一下两条相同的消息，或者实现者按文字去重，遇到拦截改写就留下一条幽灵消息。
**如何核实**：`opus/remote.ts` 的 `timeline` 输出（真实远程链路）。
**建议改法**：同一批的 `commandAccepted` 带 `commandId` 与 `value.inputId`，但它排在 `input` 之后。宿主把日志帧按批缓一拍不划算，更简单的做法：适配器遇到 `input` 时，若有乐观消息就直接替换最早的一条（发送入口串行，窗口内只有一条在飞）；别的窗口发的同样会替换，所以再用 `commandAccepted.commandId` 核对，对不上就把乐观消息放回。失败与 `unknown-outcome` 的显示写进 Spec 输出 6。
