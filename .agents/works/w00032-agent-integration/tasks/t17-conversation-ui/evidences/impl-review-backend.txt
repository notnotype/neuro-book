### 1. 用户省略结构化回答即可绕过 ask 的全部校验

- **严重程度：重要；类别：正确性。**
- **位置：** `/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/neuro-book/src/plugins/agent/backend/builtin/ask.ts:116-120`。
- **现象：** 前台用户经 `session.resolve` 提交 `decision: "answer", answer: {text: "plain text only"}`，不带 `data`，`ask-form` 直接返回 `status: "ok"`。请求有一道必填 `age: integer` 的表单时也如此；题数、选项和表单一项都没有校验。代码注释只为父会话纯文字回答开例外，分支实际没有区分回答者或 `questions: "caller"`。
- **为什么是问题：** `builtin-tools.md` 输出 23 和计划的回答合同要求不合规回答得 `ask-invalid-answer`；这条分支使最需要防守的“其它调用方”反而能彻底绕过防守。结构化多选的 `selected: ["A", "A"]` 也被接受并原样作为 `A；A` 交给模型，没有唯一性校验。`ask.ts` 在 base 不存在，这是新增行为的问题。
- **如何核实：** 从审查 worktree 执行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-t17-review-lab/backend-probes.ts answer`。实验经真实插件运行时、JSON 远程链路场地、本机 OpenAI 兼容端点调用内置工具；不是直接调校验函数。三次回答结果依次为：空结构化答案 `ask-invalid-answer`；省略 data 的纯文字 `ok`；重复选项 `ok`。
- **建议改法：** 用户回答统一要求 `data.answers`，始终走题数、选项、唯一性和表单校验；若保留父会话纯文字入口，须把内核已认证的回答者信息传给工具，再按该身份明确开放例外，而不是按 `data` 缺失推断。已有回答校验用例补齐这两种绕过方式。

### 2. 拦截器只改工具 id 时，写工具沿用读工具的审批结论

### 3. hashline 跨调用粘贴寄存器时，审批预览静默变成空列表

- **严重程度：重要；类别：正确性。**
- **位置：** `/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/neuro-book/src/plugins/agent/backend/builtin/edit.ts:181-202`；`/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/neuro-book/src/plugins/agent/backend/builtin/preview.ts:39-46`。
- **现象：** 先执行 `CUT 2.=2 @saved` 把 `beta` 存进会话寄存器；下一次对另一个已读文件调用 `PUT >1 @saved`，远程 `approvalPreview` 成功返回 `{files: []}`。批准后目标实际从 `one\ntwo\n` 改成 `one\nbeta\ntwo\n`。
- **为什么是问题：** 副本只复制了文本快照和 seenLines，没有复制 `EditStore` 的 clipboard registers。原生 `EditStore` 的公开声明明确还保存寄存器与 no-op guard；空的新 store 不等价于实际执行状态。试算失败时目标列表又依赖不完整的 `editInspect(...).paths`，导致连 `failed` 都没返回。内置 edit 的合法操作被展示为“没有专门预览”，用户失去文件清单与明确的预览失败原因，违反输出 26 的逐文件结果合同。这条预览路径为本次新增，base 的真实 edit 本来就保留会话寄存器。
- **如何核实：** 审查 worktree 运行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-t17-review-lab/backend-probes.ts register`。走真实插件、内置 read/edit、远程 approvalPreview 和批准执行；输出 `cut.status: ok`、`preview.files: []`，随后磁盘目标出现 `beta`，实验没有直接改会话 store。
- **建议改法：** 在原生引擎提供完整只读 clone/preview 能力后复用完整状态；当前至少要可靠枚举 hashline 头里的全部目标，对不能复现的寄存器操作逐文件返回 `failed`，不能成功返回空列表。不要在真实 store 上试算再回滚，它会动行锚与寄存器。

### 5. 工具超过中止宽限期后仍推成功帧，覆盖已经结算的 unknown

- **严重程度：重要；类别：不变量。**
- **位置：** `/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/nb-harness/src/kernel/run/tools.ts:356,393-405`。
- **现象：** 工具不响应 AbortSignal，2,000 ms 宽限期到后日志已写 `toolResult{status:"unknown",code:"aborted"}` 与 `runEnded{aborted}`；之后工具才返回成功，新增的 `core.emit({type:"tool",callId,status:"ok"})` 仍然发给订阅者。真实帧顺序是 unknown、runEnded、ok，而不是“迟到结果只诊断”。
- **为什么是问题：** 输出 25 要求宽限期后的结果丢弃；输出 76 明确批末 toolResult 才是权威。外层确实不再写日志，却挡不住 runCall 内直接 emit 的新帧。对应 transcript 的完成帧覆盖表按 callId 叠加显示，迟到 ok 会把已落盘 unknown 显示成成功；刷新又回 unknown。这个 emit 是本次新增，base 没有这条迟到状态通道。
- **如何核实：** 审查 worktree 执行 `bun /tmp/claude-t17-review-lab/late-tool-frame.ts`。实际调用会话 send、等 execute 开始、abort、推进注入时钟 2,000 ms，得到 `afterGrace` 两帧：unknown 与 runEnded；释放真实工具 Promise 后 `afterLate` 追加第三帧 `{type:"tool",status:"ok"}`。不直接调用 runTools、不伪造帧。显示影响由现有消费者代码推断；未运行浏览器。
- **建议改法：** 工具完成帧经运行所有者的有效期检查输出，宽限期结束后与日志写入一样拒绝；在段内确定该调用结果仍有效时再推帧，而不是在已经脱离运行的 runCall 内无条件 emit。现有中止测试同时断言不再推迟到完成帧。

### 6. 256 KiB 限额在整份编辑之后才检查，预览会先分配巨量结果

- **严重程度：重要；类别：安全与性能。**
- **位置：** `/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/neuro-book/src/plugins/agent/backend/builtin/preview.ts:39-43`；`/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/neuro-book/src/plugins/agent/backend/builtin/edit.ts:104-109,146-150`。
- **现象：** 一个 1,048,576 字节的文件（已经是预览上限的 4 倍），把每个 `a` 替换成 64 个 `b`，查询预览先经原生引擎生成 67,108,864 字节结果，再返回 `too-large`。实测仅这次预览耗时 1,525 ms，进程峰值 RSS 从 337,460 KiB 升到 688,160 KiB，增加 350,700 KiB；用户尚未批准执行。
- **为什么是问题：** 明知输入文件超过 256 KiB，仍做全文读取、试算和大字符串复制，最后才在 `fileEntry` 判大。`replace_all` 的输出膨胀比例受参数控制，输入 32 MiB 的资源允许读入，输出没有预览预算，自动加载 diff 就能在批准之前消耗数百 MiB 乃至耗尽进程内存。base 没有这条自动预览入口；实际写工具被批准后执行的既有成本不算本次问题。大文件的通道分段解决不了服务端分配。
- **如何核实：** 审查 worktree 执行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-t17-review-lab/large-preview.ts 1048576 64`。真实插件、内置 edit-replace 等审批、真实远程 approvalPreview；输出 `{kind:"too-large",bytes:67108864}` 及以上 RSS/耗时。实验只拒绝审批，没有执行编辑。
- **建议改法：** 在跑引擎前，经会话权限的只读定位/stat 判断原文件字节数，超过预算立即返回 too-large；对小文件变成大结果也要在引擎内限制预览输出和计算预算，不等完整字符串造完再判断。需要原生引擎提供受限 preview，不能只在 JS writer 末端检查。

### 7. 审批缓存不因核心设置变化失效，未启动的写调用绕过新只读设置

- **严重程度：重要；类别：正确性。**
- **位置：** `/home/notnotype/CodeRepository/neuro-book/.worktree/review-w00032-t17/packages/nb-harness/src/kernel/run/tools.ts:238-243,262-267,302-307`。
- **现象：** 模型一条回复先后调用两个 exclusive 写工具；第一个已经开始但尚未结束时，`changeSettings({core:{readOnly:true}})` 成功。释放第一个后，第二个尚未启动的写调用仍使用审批阶段的 allowed 并执行，快照此时为 `readOnly: true`。同一实验在 base 上第二个得 `denied/read-only`，只执行第一个。
- **为什么是问题：** 缓存只比较参数，既不重新检查内核只读门，也不校验判定时的 approvalMode 等设置。原本在实际执行入口受控的未启动调用，现在被整批提前判定成永久放行。输出 31 的返回仍是 `next-boundary`，但 base 对工具入口读取的是已写入的当前设置；本次没有记录把只读门也冻结到整条回复结束的已接受决定。该变化削弱了输出 18 的只读限制，不属于“同批审批先问完”本身必须付出的代价。
- **如何核实：** 审查 worktree 执行 `bun /tmp/claude-t17-review-lab/approval-settings.ts`：`writes ["first","second"]`，两条结果均 ok；执行 `bun /tmp/claude-t17-review-lab/approval-settings-base.ts`：`writes ["first"]`，第二条为 `denied/read-only`。均经真实会话 send、工具执行门、changeSettings 和 waitRun，不直接调用审批函数；只用可控工具 Promise 确定用户改设置的时刻。
- **建议改法：** terminal 必须重新检查当前核心只读门；审批缓存记录决策相关设置的版本，版本改变时按新设置重新判定，保留用户对同一调用的明确拒绝。为“排在慢调用后面尚未启动的写调用”补只读与审批模式中途收紧用例。

将实验的回答入口改为真实 `client.resolve({sessionId,...})` 后，用同一命令再次运行：三次远程调用全部受理；内置工具结果仍依次是 `ask-invalid-answer`、`ok`、`ok`。已确认不是同进程宿主特权路径才有的绕过。
