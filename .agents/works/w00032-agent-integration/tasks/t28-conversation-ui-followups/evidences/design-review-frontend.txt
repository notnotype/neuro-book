# t28 计划前端设计审查报告

被审：`.agents/works/w00032-agent-integration/tasks/t28-conversation-ui-followups/plan.md`（worktree `.worktree/t28-design-review`，提交 a8b28133d）。范围：`packages/nb-agent-ui`、`plugins/agent/web`、`plugins/models/web`。未跑测试与类型检查，下列结论均来自读代码，核实方式在各条里写明。

### 1. 计划说“视图已有”的编辑态、面板宿主与入口其实都不存在
- 严重程度：阻断
- 类别：依赖的机制不存在 / 范围低估
- 位置：plan.md:36（“视图已有消息操作与 `branch.switch`、`tree.activate`、`message.editSubmit`……”）、plan.md:30、plan.md:43；`packages/nb-agent-ui/src/vue/AgentConversationView.vue:273-286`（顶栏只有标题、新建、一个只含“切换原始视图”的 ⋯ 菜单）；`packages/nb-agent-ui/src/vue/composer/AgentContextMeter.vue:27-37`
- 现象：
  1. `ctx.editing` 没有任何 `.vue` 读它（`grep -rn "editing\|editSubmit\|editCancel" packages/nb-agent-ui/src/vue --include='*.vue'` 无结果，仅 `types.ts`、`context.ts` 和一个测试夹具出现）。`message.editSubmit`、`message.editCancel` 没有任何组件发出；内置“编辑”操作只发 `message.editStart`（`builtin-message-actions.ts:25`）。Spec 的“消息就地变为编辑器，原文仍在加载时只读”（`ui/agent-conversation-view.md:272`）没有实现。
  2. 注册表的 `panels`、`headerActions`、`trayItems` 只在 `registry.ts` 里有数据结构和合并规则，视图里没有任何地方渲染它们（`grep -rn "headerActions\|trayItems" packages/nb-agent-ui/src` 只命中 `registry.ts` 与 `registry.test.ts`）。也就没有“弹窗”宿主、没有 `presentation: "popover" | "dialog"` 的实现，没有任何 action 表示“打开面板”。
  3. 上下文圆环（`AgentContextMeter`）是 `role="img"` 的 Tooltip，不能点；状态栏的缓存与费用同样不能点。
- 为什么是问题：批 2、批 3 都写成“接宿主数据”，工作量被当成宿主侧的映射；实际要新写：就地编辑器（含历史消息原文分段加载的只读态）、面板/弹窗宿主、打开状态（Spec 第 33、361 行规定面板与弹窗开关是视图自持的纯界面状态）、顶栏菜单项、圆环与缓存的点击与键盘语义。切片表里“先出静态稿”一栏批 3 只写“分支树”，批 2 写“检查器”，漏了编辑态；而 Spec 第 272 行要求编辑态支持 `@` 引用与插图，等于再接一遍批 4、批 5 的触发菜单和附件。
- 如何核实：上面的 grep；读 `AgentConversationView.vue` 模板（顶栏到 `acv-body`）与 `AgentConversationTurn.vue` 全文，没有编辑态分支。
- 建议改法：把批 3 拆成“视图侧：就地编辑态、面板宿主与入口（含静态稿）”和“宿主侧：映射”；在计划里写明面板宿主的归属（视图持有打开状态，打开时发出哪个 action，例如打开检查器即发 `context.refresh`），并为这个新机制在 `ui/agent-conversation-view.md` 补合同，再让批 2、批 3 依赖它。若不想动视图合同，替代做法是由宿主（`ConversationHost.vue`）持有弹窗，但那样 `ctx.panels` 的约定也要一并改写，两条路必须选一条写进计划。

### 2. 模型状态刷新只修了“模型库变化”这一条路径，设置变化与整份快照覆盖都没处理
- 严重程度：重要
- 类别：遗漏 / 并发
- 位置：plan.md:19；`packages/nb-agent-ui/src/kernel-transcript.ts:424-426`（`settingsChanged`）、`:551-580`（`applySnapshot`）；`packages/neuro-book/src/plugins/agent/web/session-host.ts:89`、`:197-203`、`:581-586`
- 现象：
  1. `meta.model`（解析后的模型、`efforts`、`contextWindow`、`ok/code`）只在 `applySnapshot` 里写。`settingsChanged` 事件只合并 `meta.settings`。所以用户用选择器切模型或切思考档以后，`availability`、`thinkingLevels`、`contextLimit` 都还是旧模型的，直到重开会话。这和开发者反馈第 1 条是同一个 bug，只是触发点换成了 `model.set`；计划的宿主测试只写了“未绑定 → 绑定后可发送”。
  2. 计划写“重读 snapshot，只更新 `meta.model`”，但 `KernelTranscript` 没有这种窄接口，现有 `refresh()`（session-host.ts:197）会调 `applySnapshot` 再 `loadPath`，同时覆盖 `usage`、`queue`、`status`、`title` 等整份基线。快照是异步取回的：取的过程中收到的状态帧、`inputQueued`，会被稍早的快照倒退覆盖（`open()` 为此专门有 `staleUntil` 与 `head` 丢帧逻辑，`refresh()` 没有）。
  3. 宿主没有订阅 models 变化的入口：`plugin.ts:141-163` 的 `models` 是插件级 `shallowRef`，`SessionHostDeps.models` 只是个读取函数（session-host.ts:89），两个宿主（右栏视图、编辑区页面）各自需要一个“模型库变了”的回调才能触发重读，计划没写这个依赖。
  4. 选角色后面板保持打开（plan.md:20），而思考档列表来自旧的 `meta.model.efforts`：用户刚选完角色，看到的是上一个模型的档位；若新模型不支持当前 `settings.effort`（例如 `xhigh`），触发器仍显示这个值（`composer.thinking = settings.effort`，session-host.ts:689），单选组里没有任何项被勾选。
- 为什么是问题：用户可观察的症状（“还显示要先绑定”“上下文窗口、思考档不对”）在换一条路径后依旧出现，而且计划的验收只覆盖一条。
- 如何核实：读上面几处；在宿主测试里 `changeSettings({model})` 后检查 `ctx.composer.thinkingLevels` 与 `ctx.usage.contextLimit` 是否变化（预期不变）。
- 建议改法：给 `KernelTranscript` 加只替换 `meta.model` 的方法（例如 `applyModel(model)`），宿主在两种时机调用：models 变化回调，以及收到 `settingsChanged` 且 patch 含 `model` 或 `effort` 的帧之后；用代数标记丢弃过期结果。`SessionHostDeps` 加 `onModelsChanged(listener)`。验收加一条“选角色后思考档与上下文窗口随之变化”，并规定新模型不支持当前档位时的显示（回落到第一个支持的档，或显示“默认”）。

### 3. 角色未绑定或没有凭据时选择器整个被禁用，用户在选择器里改不了
- 严重程度：重要
- 类别：与目标矛盾 / 失败路径
- 位置：`packages/nb-agent-ui/src/vue/composer/AgentConversationComposer.vue:49-51`、`:436-446`（`runtimeDisabled`、`:disabled="runtimeDisabled"`）；session-host.ts:659-660；plan.md:20-21
- 现象：`readonly = availability.status !== "ready" || !canSend`，`runtimeDisabled = readonly || !canChangeRuntime`，选择器的 `disabled` 取后者。会话的解析模型失败（`role-unbound`、`no-model`、`no-credentials`、`unknown-model`）时 `availability` 是 `profile-unavailable`，选择器被禁用，横幅只给“打开设置”。新选择器加了“选角色”，最需要它的正是这个状态（Profile 默认角色没绑、用户想改选另一个角色或具体模型）。
- 为什么是问题：计划把选择器当成这类问题的出口，实际上进不去；用户只能去设置页绑定，再等刷新（见第 2 条）。
- 如何核实：读上面几行；Lab 里把 `availability.status` 设为 `profile-unavailable` 看选择器。
- 建议改法：选择器的禁用条件只看 `canChangeRuntime` 与归档、读失败，不看模型解析失败；`profile-unavailable` 下仍允许 `model.set`、`thinking.set`。输入框正文仍只读。在计划里写明各 `availability` 状态下选择器是否可用（表格）。

### 4. 草稿直接写 `localStorage` 违反存储规范；按会话切换还有读写竞态
- 严重程度：重要
- 类别：违反既有约定 / 并发
- 位置：plan.md:12、plan.md:50；`docs/standards/code/frontend.md:64`、`docs/specs/storage/boundaries.md:59`；session-host.ts:139-158、`:527-529`、`:302-313`（`open` 不重置 `draft`）、`:738-742`
- 现象：
  1. 规范写明“禁止新增组件内裸 `localStorage` / `sessionStorage` 读写”，宿主的持久化走适配层。同一个插件已经有先例：`plugin.ts:83-85` 的 `agent.recent-session` 用 `defineRecord({scope, locality: "local", keyed: true})`，经 `storageKey` 服务读写。计划写“存 `localStorage`，不引库”，既绕过 Storage 的归属与作用域（作品范围/用户层、客户端身份），也让 t17 第 8 条“另一个窗口看不到草稿”靠不住：同源窗口共享 `localStorage`，另一窗口刷新或打开同一会话就看到了。
  2. `composer.draftChanged` 每次按键都发（`AgentConversationComposer.vue:onChange`），现在宿主只改内存变量。持久化要防抖，计划没说；切会话时旧会话的待写草稿要先落盘。
  3. 草稿是宿主的单个变量，不分会话：`open()` 不重置它（`closeCurrent` 也不碰 `draft`），所以今天 A 会话里没发的字切到 B 会话还在输入框里。按会话存要在 `open()` 里异步读 B 的草稿再 `setDraft`；用户在这段异步读取期间已经打字时，晚到的读取结果会用新版本号把他刚写的字替换掉（编辑器遇到版本号变化就替换内容）。没有会话（`current === null`）时的输入没有键可存，随后 `submit` 才 `create()`。
  4. 编辑区页面与右栏是两个宿主（`hostAt("view"|"page")`），同一会话可能同时在两处打开，各自的 `draftText` 互不知道，最后写入者赢。
  5. “10 条、30 天”需要一个索引记录做淘汰；`keyed` 记录是按键独立读写的，没有“数条数”的机制，计划没说放哪。
- 为什么是问题：规范违反会在 `governance:check` 或审查里被拦；竞态会丢用户的字，属于数据丢失。
- 如何核实：读 `storage/boundaries.md:59` 与 `plugin.ts:83-85`；在宿主测试里 `open(A)`、设草稿、`open(B)`，看 `ctx.composer.draft`（现状会保留 A 的字）。
- 建议改法：用 `nbook.storage` 的记录（一个“草稿索引”记录放最近 10 个会话的文本与时间，整体读改写，淘汰在写入时做）；写入防抖 + 切会话、`dispose`、`borrow` 归零时同步冲刷；`open()` 先清空草稿、读到之后仅当版本未被用户输入推进时才替换（用打开代数与“读取期间是否 `draftChanged`”判定）；无会话时的草稿用固定键 `new`，创建会话后迁移或清掉；两个位置共享同一个草稿索引时，约定以“最近打开的位置”为准并写进 Spec。

### 5. 分支树“从完整日志算”：超大事件拿不到 id 与父节点，nb-ui 的 `Tree` 画不了旧版的行
- 严重程度：重要
- 类别：依赖的机制不够 / 合同
- 位置：plan.md:43、plan.md:12（“树形展开用 nb-ui 现有的折叠与键盘导航做法”）；`packages/neuro-book/src/plugins/agent/shared/remote.ts:106`（`LogItem`）、`backend/frames.ts:28`；`packages/nb-ui/src/components/navigation/Tree.md`；旧应用 `agent/session-tree.ts`、`dialogs/session-tree/AgentSessionTreeDialog.vue:566-603`
- 现象：
  1. 日志条目放不进一条消息时变成 `{kind: "oversized", seq, type, bytes}`，不含 `id` 与 `parent`。树要靠每个节点的 `id/parent` 连起来。工具结果、长回复正好是最容易超限的事件，丢了它们的父子关系，子树会断成孤儿或接错位置；补救只能经 `eventChunk` 把整条大事件读回来，只为拿一个父 id，对长会话是几十 MB 的读取。计划的“风险”一节只说分页多，没说这一点。
  2. 旧弹窗是一个扁平的 `treeRows` 列表，每行有导引线格、分支点折叠（`+N` 隐藏计数）、五列网格（图标、类型、摘要、时间、状态）。nb-ui 的 `Tree` 的节点只有 `title`、`iconClass`、`children`，没有插槽（`TreeSlots = Record<never, never>`），不支持行内多列、搜索过滤、不渲染导引线；会话日志绝大多数是线性链，递归 `children` 嵌套深度等于事件数，几千层的缩进与递归渲染不可用。“用 nb-ui 现有的折叠与键盘导航做法”指向不明。
  3. 树数据从哪来、什么形状没定：`AgentSessionTree.vue` 在 `nb-agent-ui`（纯受控、ctx 必须能 JSON 化），所以要么宿主把整棵树放进 `ctx.panels.tree`，要么把“日志事件 → 树行”的构建函数放在 nb-agent-ui 核心里由宿主喂事件。计划没有选，也没有给 `ctx.panels` 里树的字段。
  4. 日志读完后新事件还在追加（对话在跑时可以开树），计划只写了“读完前显示进度”，没有写读完后的增量更新或手动刷新。
- 为什么是问题：树在长会话里不正确或过慢，且实现者需要自己发明数据形状。
- 如何核实：`remote.ts:106` 与 `frames.ts:28` 的类型；`Tree.md` 的 `TreeSlots`；旧弹窗模板。
- 建议改法：给后端加一个只返回树骨架（`id, parent, type, seq, 摘要前 N 字`）的查询（与后端审查的结论对接），不要让浏览器读全部事件体；树行用自己的扁平列表（`role="tree"` 的 roving tabindex + 窗口化），构建函数放 nb-agent-ui 核心并单测；计划里写明 `ctx.panels.tree` 的字段、增量更新规则（以 `seq` 追加）。

### 6. `ctx.branches` 与“重试/编辑重发”需要“视图消息 id → 内核节点”的映射，转录器里没有；`siblings` 要按轮逐个取
- 严重程度：重要
- 类别：接口与合同 / 依赖的机制不存在
- 位置：plan.md:36-41；`packages/nb-agent-ui/src/kernel-transcript.ts:285-345`（`input`、`assistant`、`modelStarted` 的处理）、`:15`（`runtime.md` 输出 36、37）；`packages/nb-harness/src/kernel/run/tree.ts:15-98`
- 现象：
  1. `siblings(node)` 以“同一个父节点的 path 事件”为单位。重试/swipe 产生的兄弟节点是 `modelStarted`（`runtime.md` 输出 36：“接着跑之后的模型请求（`modelStarted`）与原来那次是兄弟节点”），而视图的分支切换器挂在 `turn.user.id` 与 `turn.outcomeMessage.id` 上（`AgentConversationTurn.vue:150-157`、`:183-189`），后者是 `assistant` 事件的 id，它的父节点是 `modelStarted`，对 `assistant` 调 `siblings` 只会返回它自己。`KernelTranscript` 对 `modelStarted` 只记下 `purposes`，不保留节点 id、父子关系；`rewindTargets` 的 `turnId` 与视图“轮”（`splitIntoTurnGroups` 按用户消息切）也没有对应关系。
  2. “重试：`rewindTargets` 找这轮的目标后 rewind 再 start”没有说选哪个 `kind`：用户的话之后的第一个 `after-step`，还是 `before-turn`（后者会回到用户输入之前）；一个视图轮里可含多个内核 turn 和多个 `after-step`；助手消息上的“重试”和用户消息上的“重试”（`builtin-message-actions.ts:29-36` 两种都有）是否同一个目标。
  3. 切换器要给每个有分支的消息填 `ctx.branches`，用 `siblings` 就是每轮至少一次远程调用（用户侧加助手侧可达两次），打开长会话和每次 `leafChanged` 后都要重算。
- 为什么是问题：不先建立映射，批 3 实现时只能从事件里重新猜，换一种事件顺序（压缩、steer、被中断的运行）就会选错回退点，属于破坏历史的操作。
- 如何核实：读 `kernel-transcript.ts` 上述区间（没有任何 `parent`/节点 id 字段）；读 `tree.ts` 的 `rewindTargets` 与 `siblingsOf`。
- 建议改法：让转录器为每条用户/助手消息记下它的内核节点 id、所在 `modelStarted` 的 id 和 `rewindTargets` 要的 `turnId`（作为 `KernelTranscript` 的新只读查询）；计划写一张表：消息种类 × 操作 → 回退目标 `kind`。分支信息用第 5 条的树骨架一次算出，不要按消息调 `siblings`。

### 7. 编辑与分支切换的禁用条件，计划说“视图已有”，实际没有
- 严重程度：重要
- 类别：遗漏 / 与现有实现不符
- 位置：plan.md:42；`packages/nb-agent-ui/src/vue/builtin-message-actions.ts:19-27`；`packages/nb-agent-ui/src/vue/stream/AgentConversationTurn.vue:150-157`、`:183-189`、`stream/AgentMessageActions.vue:29-40`；session-host.ts:673
- 现象：
  1. “编辑”操作的 `when` 只看 `canMutateHistory`，不看 `run.status === "idle"`（重试与分支都看了）；运行中能点开编辑，提交才被内核拒成 `running`。
  2. 分支切换的 ‹ › 按钮有 `props.disabled` 入参，但 `AgentConversationTurn` 两处都没传，所以运行中永远可点。计划说“按钮按 `run.status` 禁用”，需要改视图。
  3. `canMutateHistory` 在宿主里目前是不设（常量 false）。计划说“把它打开”，没说条件。归档会话、`meta.readOnly` 不为 null 的会话（`KernelMeta.readOnly`）、子会话都不该能改历史；等待审批/回答（`run.status === "waiting"`）时同样不该改。
- 为什么是问题：用户在运行中点“编辑”，写了长文，提交时失败；失败后 `message.editSubmit` 没有定义失败通道（见第 1 条，宿主没有放回文字的位置）。
- 如何核实：读上述三处；Lab 里把 `run.status` 设为 `running` 检查编辑按钮。
- 建议改法：`canMutateHistory` 在宿主里算成 `run.status === "idle" && !archived && readOnly === null`，同时视图里编辑、分支切换统一按 `ctx.interaction.canMutateHistory` 隐藏或禁用（不是各自再判一遍 `run.status`）；编辑重发失败时保留编辑态并显示原因（`ctx.editing` 需要加一个错误字段，或复用 `composer.notice`）。

### 8. `@` 菜单依赖的“编辑区现有文件查找”不存在，且 `resolveTriggerMenu` 是同步纯函数
- 严重程度：重要
- 类别：依赖的机制不存在 / 合同
- 位置：plan.md:48；`docs/specs/workbench/quick-open.md` 的“非目标”（“文件/实体快速打开（`Ctrl/Cmd+P`）……本批不交付”）；`packages/neuro-book/src/plugins/files/shared/contracts.ts:214-234`（只有 `list`、`read`、`identify`……，没有搜索）；`packages/nb-agent-ui/src/types.ts` 的 `resolveTriggerMenu`

### 9. 附件：无会话时无处上传；文字写法与 `input.attachments` 二选一没定；读取路由缺失
- 严重程度：重要
- 类别：遗漏 / 合同
- 位置：plan.md:54-56；`docs/specs/ui/prompt-editor.md:44-50`（附件目标写在文字里）、`docs/specs/ui/agent-conversation-view.md:348`（“附件都写在文字里，不另带”）；`packages/nb-agent-ui/src/kernel-transcript.ts:285-291`；`packages/nb-agent-ui/src/vue/stream/AgentUserContent.md`；session-host.ts:419-436（`submit` 在无会话时先 `create()`）
- 现象：
  1. 附件存进会话工作区 `session://attachments/`，需要会话。选中“未选择会话”的空状态时，用户粘贴图片，`composer.attachmentAdded` 到宿主，`current === null`，没有可上传的目的地；现在 `submit` 是发送时才建会话。计划没有规定：先建会话，还是在无会话时 `canRegisterAttachments` 为 false。
  2. 视图合同是“附件写在文字里”（`![image #N](session://attachments/…)`），转录器却同时把 `input.attachments` 转成附件块（`kernel-transcript.ts:287-289`）。宿主发送时是只发 `{text}`（让内核从文字里解析），还是另带 `attachments`，计划没写；两样都发会在气泡里显示两次（文字里的小块和附件块）；只发文字则计划里“内核读 `uri` 转图片块”读的是哪个字段要对上。`recall`（上方向键）从日志取文字时也会因此或带或不带附件标签。
  3. `resolveAttachmentUrl(locator, variant)` 是同步函数，要返回一个 URL，缩略图与原图要有读取路由；计划只列了上传路由。16 MB 的原图直接当缩略图 `<img>` 会拖慢长对话，没有缩略图规则。URL 要带会话与作品范围，且 `<img>` 请求不能带自定义头，鉴权方式要核对 `http` 插件的做法。
  4. 数量与大小限制（8 张、16 MB）：编辑器没有数量或大小的属性，只能在宿主收到 `attachmentAdded` 后把状态设为 `failed` 并给出原因；“最多 8 张”是按会话、按这一条输入，还是按草稿，没定。
  5. 内容哈希相同不重复写：同名但内容被改过的 `session://attachments/<hash>` 不会冲突，可以；但文字写法要求“名称在会话内唯一，不含空白与括号”，以哈希为名则 `[file #N · 文件名]` 里的原文件名不可恢复，只能放在小块的标签里，需确认编辑器的文字写法能带文件名（有，`[file #N · 文件名](目标)`）。
- 如何核实：读 `prompt-editor.md` 附件小节、`kernel-transcript.ts:287`、`session-host.ts:419-436`。
- 建议改法：计划里加三句定论：无会话时附件入口关闭（`canRegisterAttachments: current !== null`）或先建会话；发送只发文字，转录器不再从 `input.attachments` 生成附件块（旧数据保留）；增加 `GET` 读取路由并规定缩略图的做法（服务端缩放，或浏览器只加载原图但 `loading="lazy"` 并限制尺寸）。

### 10. 缓存命中率的口径不含写入量，且不报缓存的服务商会一直显示 0%
- 严重程度：重要
- 类别：合同 / 失败路径
- 位置：session-host.ts:704；`AgentStatusBar.vue:72`；plan.md:26、plan.md:30
- 现象：
  1. 宿主算 `cacheRead / (input + cacheRead)`。`input` 只含没命中缓存的部分（`CompactionView` 注释），`cacheWrite` 是另一类未命中（本次新写入缓存的输入），不在分母里：首次请求大量写入、第二次读取时，分母偏小、命中率偏高。上下文占用的口径用的是 `input + cacheRead + cacheWrite`（Spec 第 111 行），两个口径不一致。计划还要在检查器里再显示“最近一次请求的命中率”，宿主需要第二份同样的公式。
  2. 不报告缓存用量的服务商或中转（`cacheRead` 恒为 0）：`input > 0` 时命中率是 0%，而不是“未知”。计划把它从悬停提升为状态栏的常驻项，这些模型上会永远显示 0%，被用户当成“缓存坏了”。`cacheHitRate: null` 只在两者都是 0 时才出现。
- 为什么是问题：用户据此判断成本和提示词是否稳定，错误的数字比没有更糟。
- 如何核实：读 session-host.ts:704；构造 `{input: 50, cacheRead: 10000, cacheWrite: 500}`，现公式 99.5%，含写入是 94.8%。
- 建议改法：公式移到 nb-agent-ui 核心的一个纯函数（累计与最近一次共用，附测试），分母含 `cacheWrite`；`cacheRead` 与 `cacheWrite` 累计都为 0 时给 `null`（“服务商未报告”），状态栏不显示该项。把口径写进 `ui/agent-conversation-view.md` 的 `usage` 一行。
