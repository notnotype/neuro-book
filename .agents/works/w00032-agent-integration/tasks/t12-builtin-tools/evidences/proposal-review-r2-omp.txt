### 1. 阻断；类别：不变量、跨进程架构；位置：提案“待定项 1”第 229–232 行、“影响”第 212–218 行；`docs/specs/runtime/projects.md:19–25,65–86,172–179`；`packages/neuro-book/src/plugins/files/backend/plugin.ts:148–219`

- **现象：** 提案把同一本书的两个服务端处理为“先打开者持有 `history.sqlite` 写锁，后打开者只读、不记账”，但没有定义后打开者的文件写入如何交给第一个项目实例。现有拓扑允许两个不同状态根的服务端同时打开同一目录，且每个服务端都会启动自己的项目子进程；`nbook.files` 的 `project` 入口和 `ChangeHub` 也各自在各自子进程中创建。后打开者仍然能通过自己的项目文件服务执行写入，写入发生在它的进程里，而账本主只能在另一个进程里观察到它。

- **为什么是问题：** 这不是“少一个操作者字段”的降级，而是双实例时文件、事件、账本三者不再有单一拥有者：第二服务端的 Agent/用户写入会被第一服务端的监视当成外部，第二服务端自己的浏览器订阅又会把同一写入按自己的回声/来源处理，可能产生重复外部条目、错误来源和不同步时间线。若禁止第二实例写，提案必须定义项目文件服务的只读门禁；若允许写，必须有跨实例的提交转发或明确的账本主代理协议。仅靠 SQLite 写锁不能完成这件事，因为写锁只保护数据库，不把写入和事件路由到持有者。

- **如何核实：** 代码核对 `runtime.projects`：不同状态根不阻止双开，且每个项目代次都是独立子进程；代码核对 `files/backend/plugin.ts`：每个项目入口调用 `openBackend`，创建自己的 `ChangeHub`、操作锁和写入实现。按真实拓扑启动两个服务端/项目实例，令实例 B 经 `projectFilesContract` 写文件，再让实例 A 的监视与 History 主进行对账，即可观察 B 的来源无法通过当前内存回声表跨进程传递；本轮未启动服务，结论来自现有合同和实现。

- **建议改法：** 把“账本主”提升为“文件根主”：主进程之外的项目写入统一 RPC 转发到主实例执行，并由主实例回发事件；或在项目根层明确第二服务端只能读、其写入口返回结构化 `history-owner`/`read-only`，包括浏览器保存、文件树操作和 Agent 代表写入。主实例崩溃、锁过期、重新选主、旧主恢复和事件订阅切换必须写成状态机并验收；不能把后打开者简单标成“只读账本”而让文件写继续存在。
### 2. 重要；类别：正确性、进程生命周期；位置：提案“文件监视与外部改动”第 111–118 行、“影响”第 212–216 行；`docs/specs/workspace/resources.md:93`；`docs/specs/runtime/projects.md:15,25,37–39,65–86,140–145`；`packages/neuro-book/src/plugins/files/backend/projects-scheme.ts:55–72`

- **现象：** 提案把项目根的监视与外部改动记账交给项目子进程，并承诺 Agent `shell` 执行期间观察到的改动归给该会话；但 Agent 先取得 `readPath` 再在服务端直接运行 shell，`projects://` 的实现只在单次调用的 `withProject` 内取得并释放项目租约。返回本机路径后，shell 运行期间没有继续持有项目租约。若没有浏览器或其它租约，项目会进入 5 分钟宽限期并停止；停止后监视器不再观察，长 shell 的后半段、宽限期后的写入及项目重启窗口都不在这个项目实例的监视寿命内。

- **为什么是问题：** “shell 期间归属推断”是产品承诺，不是普通刷新优化。当前接口把“路径可读”与“项目实例存活/监视”分成了两个短时操作，调用方拿到路径后再执行任意时长命令，无法证明命令期间存在观察者。结果可能是 shell 已成功改盘但无事件、无 History 条目，或项目被停止后下一次打开才把整段变化作为外部补记，时间和会话归属都丢失。项目子进程崩溃又不会自动重启，提案没有说明 shell 对已失效观察者是继续执行、失败还是降低为外部。

- **如何核实：** `projects-scheme.ts` 的 `withProject` 注释和实现显示租约围绕单次远程调用取得与释放；`runtime.projects` 明确 `projects://` 每次调用取得与释放、宽限期缺省 5 分钟、子进程崩溃不自动重启。用真实项目实例先经 `projects://` 取路径，释放租约后等待项目进入 `idle-grace`/停止，再让 shell 直接改路径，验证项目 `ChangeHub` 已关闭且没有监视对账；本轮未启动开发服务，未把静态核对冒充运行结果。

- **建议改法：** 把“执行 shell”建模为一个持有精确项目代次租约的长操作：由 shell 工具在命令开始前取得并持有项目 lease，命令结束、取消、超时或入口释放时再释放；同时把会话 id 与该 lease/监视订阅绑定。若 shell 必须允许不打开项目，则明确取消“期间归属”承诺，改为只在项目实例存活时推断、否则标 external/deferred，并给调用方可观察的降级结果。项目停止、崩溃、服务端重启和命令取消要分别定义收口，不能依靠一次 `readPath` 的短租约。
### 3. 重要；类别：职责边界、插件依赖方向；位置：提案“职责划分”第 76–83 行、“一次写入”第 90–100 行、“影响”第 212–218 行；`docs/proposals/project-file-foundation.md:36–50,141–149,185–195`；`docs/specs/runtime/plugins.md:60–75,122–128`；`docs/specs/runtime/services.md:31–33,42–45,123–130`

- **现象：** 提案一方面保留“History 是可选插件、没装或出错文件读写照常”，另一方面要求 nbook.files 在每次提交的根锁内调用 History 的记账回调并等待/处理结果。History 又要依赖 Files 的变更事件、恢复写回与服务入口。于是文件提交的关键路径实际依赖一个可撤回、可失败、寿命独立的投影插件；如果用服务依赖表达会形成 Files↔History 的依赖环，如果用贡献/回调绕开服务依赖，则 Files 无法从现有插件合同得到“回调已接上、仍存活、何时撤回”的稳定保证。

- **为什么是问题：** 这改变了 accepted 提案明确的所有权：Files 底座只发事件，History 作为独立观察者；同时把“可选”降成了关键路径上的动态可选回调。History 停止、入口切 Project、账本连接关闭或回调抛错时，文件提交仍必须继续，但锁内代码要处理半初始化、撤回、超时和迟到回调，且不能把 History 的失败误报为文件失败。更严重的是，事务内调用 History 只解决“当前进程此刻看到的记录”，不能让文件服务拥有 History 的持久数据、恢复/收件箱语义；职责变成两边共同维护一个提交协议，边界反而比旧观察型模型更模糊。

- **如何核实：** 对照 accepted 提案第 4 节：History 原本订阅 Files 事件、失败或关闭不影响文件功能；对照运行时合同：服务必需依赖会形成失败闭包，贡献协作本身不构成依赖，入口关闭时贡献会撤回。再按提案时序枚举“Files 已激活、History 尚未激活/正在停止/回调已取出后被关闭”的提交，现有运行时没有一个现成状态能同时满足锁内等待、可选失败隔离和回调寿命。

- **建议改法：** 先在提案中选定唯一的依赖形状，不要同时宣称“投影插件独立”和“Files 每次提交同步调用插件”。更干净的形状是：Files 拥有一个窄的、可选的 `HistorySink`/提交通知槽，槽的接口和寿命由 Files 定义；History 以贡献方式接入，撤回后 Files 立即回到“只写盘、记诊断、可对账”，不让 Files 依赖 History 的查询或恢复实现。若要求故障后仍保留准确的改前/改后数据，则把提交事件或暂存内容引用放进 Files 自己拥有的短期 durable outbox，再由 History 投影；否则明确接受账本故障时只补 external、丢操作者与该次快照。同步回调、贡献撤回、超时和失败结果写成状态机并补合同，不以“软依赖”四字代替。
### 4. 重要；类别：端到端正确性、职责边界；位置：提案“影响”第 212–218 行、“对 Spec 的预期改动”第 220–227 行（未定义恢复写回路径）；`packages/nb-history/src/workspace-history.ts:231–291`；`packages/nb-history/README.md:46–53,68–74`；`docs/specs/workspace/files.md:56–64,131–147`

- **现象：** 用户故事要求从时间线恢复/收件箱还原一个文件，但提案只定义了通用 `commit`、`write` 与 `History` 的账本回调，没有定义 History 恢复如何调用它们。现有 `nb-history.revert`、`revertAtRevision`、`restore` 在自己的 History 写锁里直接 `writeDisk(path, body)`，然后才追加 `file.revert`/`file.restore`；它们不经过 nbook.files 的项目操作锁、基线期望、`ChangeHub` 回声登记或来源事件。

- **为什么是问题：** 恢复不是查询，而是一次用户可见写入。按现状它会与 Agent/编辑器的文件提交使用两套锁，可能覆盖并发的新版本；文件服务订阅方只收到裸监视事件（或在监视关闭时完全不知道），来源无法标为用户还原，文件树/编辑器不会获得提案承诺的精确事件；History 自己又同时写入一条历史记录，若再由监视补记会重复或形成错误链。于是“恢复”这个核心产品目标在 B+ 下没有闭合的端到端路径。

- **如何核实：** 直接读取 `WorkspaceHistory.revert`、`revertAtRevision`、`restore`：三者在 History 锁内读盘并调用 `writeDisk`，没有 `nbook.files`/`ChangeHub` 参数。对照 Files Spec 的提交不变量：所有保存要在同一受保护提交中核对基线、替换并确认新基线；本轮未启动完整插件，未把源码核对写成运行通过。

- **建议改法：** 禁止 History 的 `revert`/`restore` 直接落盘。让 History 只在自己的读锁/事务中生成 `{bytes, sourceEntryId, expectedRevision, expectedCurrentHash}` 的恢复计划，再调用 Files 拥有的 `restore`/`commit` 操作；Files 在根操作锁内重新核对当前版本、原子替换、登记来源为 `user`（收件箱还原）或显式 `restore` 操作者、发出精确事件，随后由 History 在同一提交协议中登记该恢复事件。必须定义账本提交失败、History 与 Files 顺序、删除找回时父目录/目标类型、revision 过期和 `unknown-outcome` 的结算；否则不要把“History 提供恢复”列为已覆盖目标。
### 5. 重要；类别：产品目标、数据与性能；位置：提案“问题”第 24–27 行、“一次写入”第 84–106 行、“nb-history 要补的”第 119–128 行、“影响”第 210–218 行；`packages/nb-history/README.md:96–126`；`packages/neuro-book/src/plugins/files/backend/entry-ops.ts:121–148`

- **现象：** B+ 让服务端可以流式暂存并原子提交任意大小的文件，示例是 8 MB PNG；但账本仍只对“快照上限内”的二进制存全量，超过上限只存 hash/size。提案没有给出首版上限、磁盘预算、超过上限的用户可见语义，也没有为大文件恢复另设内容存储。于是“写入成功”和“历史可恢复/可 diff”被同一个接口伪装成同一能力，实际是按大小突然分叉。

- **为什么是问题：** 图生文的大图能落盘，但随后被删除、被 Agent 覆盖或在时间线中还原时，History 只有 hash，核心恢复故事必然失败；收件箱只能显示“已更改”，用户无法审查内容。另一方面一次提交至少要同时容纳暂存文件、目标旧/新版本、SQLite 快照/WAL，8 MB 甚至 100 MB 文件会在项目目录和状态根产生多个副本；同步盘、磁盘满与备份体积会在“写成功后记账”阶段才暴露。没有明确阈值与失败/降级合同，插件作者无法判断何时可安全承诺可恢复。

- **如何核实：** `nb-history` README 明确当前超过默认 2 MiB 或二进制只记 hash，`snapshotBody` 对无 body 的版本不可恢复；提案只说“上限内存全量、超过只记哈希”，没有改写这一语义或给出数值。现有 Files 复制/原子替换也会在暂存与目标间保留额外副本。可用真实 8 MB PNG 走提交后删除、调用 `deletedFiles`/`restore`，应得到“快照 body 不可用”；本轮未安装依赖，未将该场景报告为已执行。

- **建议改法：** 把“大文件可写”与“大文件可恢复”拆成两个明确能力：第一阶段先承诺原子落盘、hash/size 记账和不可恢复提示，图生文插件不得宣称可从 History 还原；或为可恢复对象指定独立内容寻址/外部 blob 存储、上限、保留与垃圾回收。提交前预检空间（至少暂存、目标、SQLite/WAL 的预算）并定义 `snapshot-deferred`/`disk-full` 的可观察结果；用 8 MB、32 MB、超过阈值和磁盘不足的真实场景验收，别把“流式写入成功”当作“历史目标完成”。
### 6. 重要；类别：可靠性、安全与性能；位置：提案“文件监视与外部改动”第 111–118 行、“nb-history 要补的”第 121–128 行、“待定项 2”第 229–234 行；`research/file-history.md:55–63`；`packages/neuro-book/src/plugins/files/backend/changes.ts:5–18,36–41`；`docs/specs/runtime/projects.md:90–91`

- **现象：** 提案把账本正确性押在每本书常驻的递归 `fs.watch`、启动对账和一次基线扫描上，但没有定义事件丢失后的自动重扫周期、重扫粒度、扫描期间的写入序列化或“基线未完成时如何合并新事件”。现有监视器只在有订阅时启动，溢出时通知订阅者 `resync`；没有订阅就没有消费方，也没有周期对账。调研已记录 Bun 在 Windows 递归子目录、macOS 嵌套监视和删除目录后存在已知缺陷。

- **为什么是问题：** 文件监视在这里不再只是 UI 刷新，而是外部编辑器、`git checkout`、shell 归属和离线变更的唯一发现机制。一次事件丢失或项目子进程在宽限期/崩溃期间错过事件，就会永久漏账，直到某次写入碰巧触发对账；这与“记录谁改了什么”的核心承诺冲突。10,000 个文件、数百 MB 书的首次基线也不是一个可忽略的启动副作用：若后台扫描与用户写入并发，账面可能在基线前后混入两种时间点；若串行，项目打开后的可用性和临时写入都会被拖延。现有项目合同还把首扫峰值/耗时作为需要重测的资源预算，提案没有继承这个门禁。

- **如何核实：** 现有 `changes.ts` 的订阅寿命、`MAX_BATCH_PATHS` 溢出和 `resync` 行为可直接核对；调研报告列出 Bun 的 Windows/macOS 缺陷和“任何方案都需定期全量对账”的结论；项目 Spec 给出 3000 文件首扫约 1.2 秒、峰值约 97 MB 的基线。用 10,000 文件、事件队列溢出、扫描中外部改动和项目子进程崩溃重启的真实平台实验，比较账本条目和最终磁盘状态；本轮未运行平台实验。

- **建议改法：** 把观察器降级为低延迟提示，把账本正确性建立在可恢复的对账机制上：启动先确定根身份和扫描快照边界，扫描期间把写入/外部事件按序排队；事件溢出、监视器异常、项目重启和定时周期都触发可观测的增量/全量对账。明确 10,000 文件/数百 MB 的打开、内存、扫描并发与用户写入预算；Windows/macOS 在发布门禁前完成真实监视器验收，若 `fs.watch` 不满足则现在就选适配器或声明外部记账不可用，而不是把关键正确性留到“平台验收时再验证”。
### 7. 重要；类别：兼容、持久化与长期运维；位置：提案“影响”第 210–218 行、“决策记录”第 236–244 行；`packages/nb-history/README.md:17–23,105–126`；`packages/nb-history/src/db.ts:60–74`；`docs/specs/runtime/projects.md:172–179`

- **现象：** 提案把 `.nbook/history.sqlite` 定义为随书移动的作品数据，但没有定义数据库在打开状态下的备份/同步协议、WAL/SHM 伴随文件、跨机器同时打开的合并/冲突处理、只读降级或损坏恢复；“两个服务端”只讨论同机/跨状态根的 SQLite 写争用。nb-history 当前使用 WAL、libsql，并明确单进程单写者；提案又计划切换 `bun:sqlite`、增加压缩、stat 缓存、操作者字段和快照语义。

- **为什么是问题：** 普通同步盘会把项目正文和账本视为多个独立文件：机器 A 记下正文版本与账本，机器 B 也记下另一版本；同步冲突可能只合并/覆盖其中一方，正文最终状态与账本末态脱节，History 反而会把同步后的结果再记成 external。数据库正在 WAL 模式打开时，复制主库而遗漏 `-wal`/`-shm` 可能得到旧账本或损坏账本；项目移动到另一目录/机器后，版本升级或驱动差异还会决定能否打开。产品目标要求历史随书可用，但当前设计只保证“路径随书移动”，没有保证“账本与作品共同可恢复”。

- **如何核实：** `db.ts` 明确启用 WAL；README 明确库是独立 SQLite、单进程单写者，并保留无 delta、无版本迁移的限制；提案把数据库放进项目控制目录却没有在数据/迁移章节列同步与备份合同。可用两个临时目录模拟同步：复制打开中的 `history.sqlite` 及不复制 `-wal`，再打开并对照正文末态；本轮未做破坏性数据库实验。

- **建议改法：** 先决定 `history.sqlite` 是本地缓存还是作品格式：若是作品格式，写入原子快照/备份导出合同，关闭或 checkpoint 后才允许备份，检测同步冲突并以“历史不可用、正文照常”降级；若是缓存，移动/导出不携带它，并在新机器按基线重建。无论哪种，加入 schema/user_version、驱动/格式版本、旧/新版本打开策略、WAL sidecar 处理和损坏修复路径；多设备并发编辑不要暗示 SQLite 文件能合并，明确只支持单设备或定义冲突导入。
### 8. 建议；类别：接口与长期扩展；位置：提案“接口形态（草案）”第 130–180 行、“一次写入”第 84–97 行；`docs/specs/runtime/plugin-channel.md:18–24,134–142`；`packages/neuro-book/src/plugins/files/shared/contracts.ts:196–251`

- **现象：** 提案把流式暂存表达成服务端返回 `Staged extends AsyncDisposable`，由调用方多次 `write(chunk)` 后 `commit()`；但项目文件的真实拥有者在项目子进程，服务端调用它走 JSON 远程服务。现有远程合同不提供上行流、二进制帧或跨实例对象引用，项目文件合同也只有整份文本与简单路径/结果方法。实现者只能额外约定“服务端和项目子进程共享同一台机器、暂存绝对路径可互见、远程门面跨多次调用仍绑定同一代次”的隐含协议。

- **为什么是问题：** 在当前本机拓扑中可以用共享文件系统绕开 RPC 载荷，但这不是 `WorkspaceFiles` 接口本身表达的合同：暂存路径的 owner、租约寿命、来源授权、提交前项目代次失效和服务端/项目进程不在同一主机时都没有类型或失败码。未来把项目子进程移到远程主机、多设备写入或浏览器直接写时，这个接口不能复用，只能再造上传会话/对象存储，且临时文件清理和 unknown-outcome 语义会重新设计。它还使“任意大小不经 RPC”成立的前提从提案正文退到了部署拓扑。

- **如何核实：** 远程 Spec 明确没有流和二进制传输；当前 `projectFilesContract` 的 methods 全是 JSON 可序列化整份输入，版本 6 也没有 staging/commit 句柄。静态检查接口示例与远程能力即可确认没有现成的异步 disposable 跨进程对象；本轮未伪造远程流运行。

- **建议改法：** 第一版明确命名为“同机项目子进程共享文件系统协议”，把 `stage` 拆成可序列化的 `stagePath/commit({stagingPath,...})`，在合同中写清路径仅服务端内部、项目代次/租约绑定、提交后自动清理和跨盘回退；不要让作者误以为它是通用流接口。若要保留未来远程能力，在接口层引入可替换的 `ContentSource`/上传会话 seam（本机路径与远程分块上传各一个 adapter），但不要在首版实现两套状态；先把主路径的部署前提和拒绝码写死。
### 推荐的交付顺序

- **第一阶段：只交付能解锁 t12 的文件能力，不接 History。** 先在 `nbook.files` 内统一根拥有者的 `readPath/list`、暂存文件、提交时基线核对、同目录原子替换、`createParents`、`update` 与已有文件操作；服务端 `projects://` 只传可序列化的暂存路径和提交参数，项目子进程仍是项目根的唯一落盘者。固定排除 `.nbook/`，先保留现有变更事件与诊断。用真实服务端/项目子进程验收 Agent 的 `read`（文本、图片、分页）、`write`、`edit`、`grep`、`glob`、前台 `shell`，包括 Agent 与编辑器并发得到 `conflict`、shell 写入不阻塞、项目子进程停止时得到可区分失败。此阶段不承诺时间线、收件箱、shell 归属或离线外部改动已记账。

- **第二阶段：先解决根所有权与观察可靠性，再接账本。** 在接入 `nb-history` 前定稿双服务端策略（单根主、只读副本或跨实例提交转发）、项目租约与 shell 长操作绑定、常驻监视/启动扫描/事件溢出/周期对账的状态机、固定排除规则、相对真实路径键和 schema 迁移。先用 10,000 文件、数百 MB、事件溢出、项目崩溃/重启、Windows/macOS 真实平台验收；否则 History 只会把观察缺口永久化。

- **第三阶段：接入 History 作为可撤回投影，但不让它拥有文件落盘。** 由 Files 提供窄的可选 sink 或提交事件，明确 History 未装、正在停、失败、超时均不阻断正文；把 `revert/restore` 改成“History 生成计划，Files 提交并发事件，History 记录结果”。再做 Agent 三文件按会话/条目归组、收件箱接受/还原、未见变更、外部安静期和保留策略。

- **第四阶段：数据体积与交付运维。** 定稿二进制/大文件恢复上限、zstd、WAL/备份/同步盘、损坏修复、旧库版本策略、移动到另一机器、硬链接/跨盘/Windows busy 和 macOS/Windows watcher fallback；再考虑 delta、自动接受、浏览器直写、远程项目和多设备。

- **首版必须锁死的概念：** 根 owner、提交期望/冲突、暂存清理、操作锁与文件锁的关系、来源与 unknown-outcome、排除规则、相对路径键、History 失败降级、恢复写回路径、数据库版本。

- **可以推迟且不锁死后续选择的概念：** 跨版本 delta、复杂 zstd 等级调优、同操作者合并、全量二进制恢复、精确外部改名关联、用户自定义排除规则、远程上传适配器。`安静期`不能在第一阶段阻塞 t12，但在第二阶段接账本前必须定义，否则外部慢写会生成假版本。

- **更简单的整体形状：** 第一版把 Files 定义成“唯一落盘提交者 + 变更事件源”，History 只消费结构化提交/观察事件，不在锁内同步调用可选插件；先接受账本异步、可能丢操作者但不丢正文。若产品第一版必须有收件箱，则让 Files 自己持有短期提交记录/暂存引用，History 后续投影；不要让 Files 与 History 互相持有对方的关键锁。代价是 History 故障恢复期间时间线延迟、恢复动作需要等投影可用；换来的收益是没有锁内插件 RPC、没有可选插件依赖环、文件写入路径可先交付。
### 待定项判断

- **1. 同一本书两个服务端同时打开：必须在实施前定稿。** 当前“先打开者写账本、后打开者只读账本”不足以保证后者不写文件；应先决定根 owner/写转发/只读门禁，并覆盖主实例崩溃与重新选主。

- **4. 原子替换代价：平台验收前必须定稿。** 硬链接、最终符号链接、跨盘暂存、Windows 目标占用、macOS/Windows 监视与权限/ACL/扩展属性的保留不能留给发布后；不能把不支持路径静默降级成会破坏正文的就地写。
