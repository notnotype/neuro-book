# t12 设计审查第二轮的处理

审查者：omp 默认模型，报告 [design-review-r2-omp.txt](design-review-r2-omp.txt)，17 个标题，审查者自己撤回 6 个，最终有效 11 条（全部“重要”）。审查对象为提交 `eef621d69` 上的第三稿。这轮依赖装好了，审查者用真实的 Agent 与 Files 入口、`pi-natives` 和项目子进程做了二十多个实验，脚本不进仓库，数字写在报告里。主会话复核了类型声明、`resources.ts`、`format.ts` 并重跑了正则实验；第 1、2、8 条的做法另参照了 omp 的 `grep.ts`、`glob.ts` 与 `OutputSink`。

编号用报告“最终裁定与有效索引”的编号。

| # | 问题 | 归类 | 处理 |
|---|---|---|---|
| 1 | `grep` 的 `onMatch` 搜完才回调；`onMatches` 不等异步核对；`glob` 没有流式入口 | 成立，要改 | `grep` 用 `onMatches`，回调只入队，异步消费者逐文件核对，够了配额再停，结束后等队列；`glob` 用 `maxResults` 候选上限后过滤；信号分类不看原生错误 |
| 2 | 搜索不进根下面的目录链接，与计划第三稿“搜索跟随链接”不一致 | 成立，接受取舍（待开发者确认） | 决定 13 说的是读。`grep` 没有跟随选项，自己枚举链接多根搜索要处理去重与防环；ripgrep 与 omp 缺省都不跟随。计划改成搜索根可以是链接，根下面不进，说明里写明 |
| 3 | hashline、replace 都不新建文件，计划的新建分支不可达 | 成立，要改 | 删新建分支与验收，目标不存在报 `not-found` 并提示用 `write` |
| 4 | 原始写入接口不认单数 `session://` | 成立，要改 | `SessionArtifacts` 按会话构造，自己拼全局地址 |
| 5 | 调用 id 不跨请求唯一，固定文件名撞 `expect: "absent"` | 成立，要改 | 文件名由 `save` 生成（`<label>-<uuid>.log`），不用调用 id |
| 6 | `shell` 地址的结束规则吞掉 `;`、`\|`、`>` | 成立，要改 | 引号外到空白或操作符结束，处理反斜杠，补无空格写法的验收 |
| 7 | `edit` 原样交回的文字保留单数地址 | 成立，要改 | 进引擎前把输入规范成全局地址，不改引擎的文字 |
| 8 | 暂存准备失败时写入函数不执行，`shell` 跟着不执行 | 成立，要改（换了审查者建议的做法） | 输出超出窗口才写本地临时文件，同步追加；命令结束后再 `save`。命令不再套在 `stage` 里，一并解决内存里 64 MiB 待写队列的问题，内存只留尾部，部件更少。omp 的 `OutputSink` 同样同步落本地文件 |
| 9 | 压缩省略后仍附图，估算与请求不一致 | 成立，要改 | 省略时只发占位不附图，补验收 |
| 10 | 部分失败的逐文件结果只在 `details`，模型看不到 | 成立，要改 | 部分失败时在引擎文字后追加逐文件摘要 |
| 11 | 原生 `grep` 对不合法的模式不报错，`invalid-pattern` 做不到 | 成立，改合同（待开发者确认） | 删 `invalid-pattern`，说明里写明按字面搜。没有同语法的校验入口；用 JavaScript 正则预检会误拒原生支持的写法 |

报告里不计入发现、已顺手落实的：

- 文档缺口：`harness/models.md`、`harness/session.md` 的图片条目随切片 1 改；`api/model.ts` 注释与 `omp.test.ts` 同改。
- `rawHash`：没有图片的结果算法不变；改写未脱敏时另记 `rawImages`。
- 4 MiB 是 `recordSnapshotFile` 的上限，不是引擎的上限；`read` 的说明改为不能用行锚改，可用 replace、`write`、`shell`。
- `grep`、`glob` 都 `hidden: true`（`glob` 的缺省是 false，照 omp 改），都按 `.gitignore` 过滤。
- 部分失败后引擎已登记写成的文件，删去“让快照失效”。
- `glob` 到期限原生不交回部分结果，改报 `timeout`。

审查者撤回、核实后同意撤回的：项目 `readPath` 的租约（关闭项目不影响磁盘路径，实测）、共享 `EditStore`（属于待实现，方案可行）、图片没有贯通（计划已列）、逐文件授权的性能（实测 1000 个文件串行 579 ms，p99 1.8 ms）、960 KiB 的回归用例（保留，不是产品上限）、`shell` 回调不能 await（实验证明有界做法可行；本次改用第 8 条的做法）。
