# 设计审查：文件访问与改动记账（docs/proposals/file-access-and-history.md @ e574e7b00）

审查者：Claude Opus（深入审查之一，只读）。依据：提案、t12 README 与 research/file-history.md、workspace/resources.md、workspace/files.md、agent/resources.md、runtime/plugin-channel.md、runtime/projects.md、nbook.files 后端代码、locked-replace.ts、nb-history 源码。以下发现按核实顺序追加，末尾按影响汇总。

### 1. 记录先于改名，但没有“准备/提交”两段：改名失败、进程崩溃、RPC 结果未知都会在账本里留下磁盘上从未出现过的版本

- 严重程度：阻断
- 类别：写入协议 / 失败路径 / 与 nb-history 合同冲突
- 位置：提案“写入的顺序”第 4、5 步与其后一段；`packages/nb-history/README.md` “数据模型”（`operation_log` append-only，删除只允许 `prune` 与 `purgePaths`）；`packages/nb-history/src/workspace-history.ts:829-844`（`implicitReconcile`）
- 现象：第 4 步把“改后内容”作为一条完成的记录交给账本并等确认，第 5 步才改名，“失败时撤回这条记录”。三种情况提案没有处理：
  1. 改名失败（Windows 上目标被别的进程打开时 `rename` 报 `EPERM`/`EBUSY` 并不罕见；`ENOSPC`、权限变化）：要撤回，但 nb-history 的日志是 append-only，没有撤回入口；`purgePaths` 是按路径整段清除，不能删一条。撤回本身若走 RPC（服务端写项目文件时），还可能再得到 `unknown-outcome`。
  2. 账本确认之后、改名之前写入方进程崩溃（服务端被杀、项目子进程正常而服务端崩）：账面末态是一个从没落盘的版本，磁盘没变，文件监视不会报任何事件，账本一直错着。下一次经接口写这个文件时，`registerWrite` 的写前对账（`implicitReconcile`：把调用方给的改前哈希与账面末态比）发现不一致，会补一条 `external` 条目，把“幽灵版本 → 磁盘真实版本”记成外部改动。时间线变成“Agent 写了 X，随后外部改回原样”，Agent 那条还会进收件箱（收件箱由 agent/system 条目触发），用户要审一段从未存在的改动。
  3. 服务端经 `{project}` 交记录得到 `unknown-outcome`（`runtime/plugin-channel.md` 第 90–94 行：写请求从帧交给链路起被中断，结果一律未知）：服务端不知道记没记上。改名就可能出现“磁盘有、账本无”（之后被当作外部改动，归属丢失），不改名就可能出现第 2 种的幽灵版本；提案对这两种选择都没写。
- 为什么是问题：账本的承诺是“谁改了什么”，上面三种都让它与磁盘不一致，而且第 2、3 种没有任何事件会触发修复；错误归因直接进入审查收件箱与会话未见变更（t13 依赖它）。
- 如何核实：读 nb-history 写入面，确认没有撤回或删除单条的方法（`workspace-history.ts:97-235`）；在测试里先 `registerWrite(agent, p, before, after)` 而不改盘，再 `registerWrite(user, p, before, after2)`，看到多出一条 `external` 的 `after → before` 条目。
- 建议改法：二选一并写进提案。
  - 甲（推荐，最简单）：照 nb-history 自己的 R10“写盘在先、记账紧随”，在锁内先改名、后记账；崩溃或 `unknown-outcome` 只会造成“账面落后于磁盘”，由写前对账或监视对账补一条 `external`（真相不错，只丢归属）。为了让监视事件不被误记为外部，见第 2 条的改法（对账在文件锁内读盘，或账本记着“进行中的写入”）。
  - 乙：两段式。第 4 步记“待定”条目（带写入号、改前与改后哈希），改名成功后再“落定”；“待定”条目不进时间线、收件箱与未见变更；重启、对账或下一次写入时，用磁盘哈希判定待定条目的去向（等于改后哈希即落定，等于改前哈希即丢弃）。这要求 nb-history 增加待定状态与按写入号落定、丢弃的入口，并写明它们不违反 append-only。

### 2. 监视对账在文件锁外读盘，与“记录先到、改名后到”交错时会记下假的外部改动

- 严重程度：阻断
- 类别：回声与外部改动 / 并发
- 位置：提案“写入的顺序”末段（“记录在改名之前送达，文件监视随后看到的变化与账面末态一致，按回声吸收”）与“外部改动”；`packages/neuro-book/src/plugins/files/backend/changes.ts:158-200, 218-246`（批合并 75 ms、`flush` 里逐路径 `lstat`/`readFile`，不取文件锁）；`packages/nb-history/src/workspace-history.ts:300-314`（`reconcile(path, current)` 由宿主读好内容后传入）
- 现象：提案只考虑了“记录先到、监视后到”这一种先后。但监视一批的处理是：攒 75 ms → 逐个路径读盘 → 交账本。读盘与交账本之间、以及读盘本身，都不在文件锁里。同一文件连续两次经接口写（Agent 连续 `edit` 同一文件很常见）时：第一次写的监视事件正在处理，读到的是第一次的内容 C1；第二次写此时走到第 4 步，账面末态已是 C2，但磁盘仍是 C1；监视把 C1 交给 `reconcile`，末态 C2 ≠ C1，记一条外部 “C2 → C1”；第二次写改名后，监视又看到 C2，末态 C1 ≠ C2，再记一条外部 “C1 → C2”。外部编辑器在附近写同一文件时也一样。
- 为什么是问题：“回声吸收”只在“磁盘已经追上账面”时成立；提案的顺序恰好制造了“账面领先磁盘”的窗口（RPC 往返加改名，p99 约 2.4 ms，负载下更长），而监视的读盘与对账都没有和这个窗口互斥。产生的假外部条目会打断收件箱的分组基准、触发会话未见变更。
- 如何核实：在测试里对同一路径连续两次经接口写，第二次在第 4 步与第 5 步之间暂停（注入钩子），同时让监视的一批处理第一次写的事件；看账本是否出现两条 `external`。
- 建议改法：对账与写入要么互斥、要么让账本知道“进行中的写入”。可选：
  - 对账在同一把文件锁里读盘并交账本（锁是按真实路径的 `proper-lockfile` 目录，监视处理每条路径多一次取锁，可以只对“账面与读到的内容不一致”的路径再取锁复核一次，避免常态开销）；
  - 或第 1 条的乙方案：账本里有“待定”条目时，读到的内容等于待定条目的改前或改后哈希都按回声吸收；
  - 或第 1 条的甲方案（先改名后记账）加“对账前在锁内复核”。
  无论哪种，提案要写出“监视读到的内容与交账本之间不变”靠什么保证，并加一条验收：连续两次经接口写同一文件，账本只有两条经接口的条目、没有外部条目。

### 3. 浏览器对 `project://` 的保存与文件操作由项目子进程执行，不是“服务端替它写”；改成服务端本机写之后，一个项目同时有两个进程的写入方，变更事件的来源与回声也随之失效

- 严重程度：阻断
- 类别：跨进程与归属 / 与既有合同的冲突
- 位置：提案“职责划分”表的 nbook.files 一行、“接口形态”末段（“浏览器保存仍调现有的 RPC 方法，服务端用 `writeText(地址, 正文, {baseline})` 替它写，操作者记为用户”）、“影响”的“浏览器的 RPC 合同不变”；`packages/neuro-book/src/plugins/files/backend/plugin.ts:209-221`（项目入口在项目子进程里提供 `projectFilesContract`）；`plugins/files/web/client.ts:25`（浏览器经 `project` 目标直连项目实例）；`backend/projects-scheme.ts:202-208`（现在服务端写项目文件是把整次写入转给项目实例执行）；`backend/changes.ts:284-290`（`saved` 只在本进程的 ChangeHub 里登记回声并以真实来源发事件）
- 现象：
  1. 浏览器写 `project://` 根本不经服务端，提案说的“服务端替它写”在 `project://` 上不成立。要么项目子进程里也有一份写入接口（账本在同进程，直接调用），要么改浏览器的路由，提案都没写。
  2. 提案让服务端在本机写项目文件、只把记录经 RPC 交给项目子进程。现在项目文件的写入方因此从一个进程（项目子进程，ChangeHub 与写入同进程）变成两个（服务端与项目子进程）。项目子进程的 ChangeHub 不知道服务端的写入：它的回声登记（`expected`）是进程内的 Map，临时文件过滤只认本实例的随机标记（`changes.ts:90` 的 `temporaryPattern`），所以服务端写的文件在网页上表现为来源 `external` 的修改，服务端的临时文件名也会作为 `changed`/`deleted` 推给文件树。
  3. 这直接违反 `workspace/resources.md` 验收 2（“写作者、Agent 会话、系统分别写入同一 Project，订阅方收到的变更事件带正确来源”）与验收 10（“代表会话写……订阅方看到来源为该会话”），以及 `agent/resources.md` 验收 2（“项目实例里记下的来源为该会话”）。提案的“对 Spec 的预期改动”没有列这几条。
- 为什么是问题：t13 的“每轮改动文件”、网页里区分“Agent 改了正在编辑的文档”与“外部改了”都靠事件来源；改成本机写后来源全部降为外部，而提案声称“网页的文件资源管理器与编辑器照旧实时收到变更事件”。
- 如何核实：读上面几处代码；在现有 `projects-scheme.test.ts` 的思路上，让服务端直接 `replaceLocked` 项目里的文件，订阅项目的变更，看到来源为 `external`、并收到临时文件路径。
- 建议改法：提案要写明项目子进程收到记录时还要做的事：登记回声（按改后哈希）、以记录里的操作者为来源发出精确事件；所有进程用同一个临时文件命名规则（例如固定前缀加任意标记），ChangeHub 与账本都按规则过滤而不是按本实例标记。更简单的替代见第 12 条：服务端对 `project://` 的写仍转给项目子进程执行（只是把载荷换成“临时文件路径 + 哈希”），写入、记账、回声与事件都留在拥有根的那一个进程里。

### 4. 第 4 步要把“改后内容”整份经 RPC 交给项目子进程：提案否掉备选一的理由（跨进程 1 MiB）在自己的方案里原样出现

- 严重程度：重要
- 类别：写入协议 / 备选取舍自相矛盾
- 位置：提案“写入的顺序”第 4 步（记录含“改后内容”）、“账本放在哪个进程”（“服务端写项目文件时，第 4 步经 RPC 交给项目子进程的账本”）、“问题”第 2 条与“备选与取舍”第一行（“`projects://` 跨进程受 1 MiB 消息上限，大文件与 20 MB 图片要分块搬”）；`packages/neuro-book/src/shared/rpc-socket.ts:16`、`server/rpc/listener.ts:76`（1 MiB 上限只设在 WebSocket 监听上）；`server/projects/ipc.ts:1-6`（IPC 用 Bun 的 JSON 序列化，代码里没有大小上限）
- 现象：用法举例里图生文插件流式存一张 8 MB 的 PNG；按第 4 步，这 8 MB 要作为记录的一部分经 `{project}` 交给项目子进程。两种读法都有问题：
  - 若以为 IPC 也有 1 MiB 上限（提案“问题”第 2 条的说法），那第 4 步对任何超过约 960 KiB 的文件都发不出去，方案不成立；
  - 实际上 IPC 链路代码里没有这个上限（只有 WebSocket 有），但远程服务的帧是 JSON 文本，字节要先转 base64（膨胀 4/3），整帧在两端都要完整驻留内存，并且占住这条唯一的 IPC 通道（同一项目的浏览器事件、统计、其它调用排在它后面）。同时这说明提案“问题”第 2 条与备选一的放弃理由不准确：跨进程的上限是 Files 合同自己定的正文预算（`TEXT_BUDGET_BYTES`，为浏览器链路设计），不是 IPC 的硬限制。
- 为什么是问题：大文件与二进制恰是提案要解决的场景；把它们塞进锁内同步 RPC，既放大锁的持有时间，又与“记录不挪到锁外，实测 RPC 毫秒以内”的依据（实测是空载荷，t12 README 第 16 条自己也写了“记录带上改动内容后载荷会变大，实施时再测一次”）不符。
- 如何核实：读上述三处代码；按提案的形状在 `{project}` 上发一个带 8 MB base64 字段的调用，测往返与同一项目上其它调用的延迟。
- 建议改法：记录不带内容，只带“临时文件的路径 + 改后哈希 + 大小”（以及改前哈希）；账本所在进程在同一台机器上自己读临时文件、核对哈希后入库（临时文件此时还在锁内、尚未改名，不会被换掉）。改前内容同理：账本已经有末态快照，不需要写入方再传。顺带修正“问题”第 2 条与备选一的放弃理由，写成“Files 合同的正文预算为浏览器链路设计；给服务端补字节接口要另定合同，且仍是整份经 JSON 帧搬运”。

### 5. 锁内“算改动”（第 3 步）是多余的，而且会把大文本的行 diff 放进只等约 3.3 秒的跨进程锁里

- 严重程度：重要
- 类别：写入协议 / 与 nb-history 的设计不符
- 位置：提案“写入的顺序”第 3 步、“备选与取舍”最后一行（“在锁里算出改动更准”）；`packages/nb-history/src/db.ts`（`operation_log` 没有存改动的列，只有前后哈希）、`workspace-history.ts:369-414`（`textDiff` 在查询时按两个快照现算）；`packages/neuro-book/src/backend/locked-replace.ts:25-28`（锁 10 秒不刷新视为残留；等锁退避 20 ms 起、1.5 倍、上限 600 ms、重试 12 次，合计约 3.3 秒）
- 现象：nb-history 的模型是“每个版本存全文快照，diff 在看的时候现算”，记录里没有“改动”这一项；提案第 4 步要交的“改动”账本无处可放，要么新加列（与“diff 现算”重复存一份），要么白算。另一方面，npm `diff` 的 `diffLines` 是 Myers 算法，代价随改动量 D 增长（O(ND)），大文本大改动（Agent 整份重写一章、导入覆盖）可以到秒级（jsdiff 为此提供 `timeout`、`maxEditLength` 选项；本次未实测，worktree 没装依赖）。算 diff 时别的写入方等锁只等约 3.3 秒，超时报的是 `io-failed`“写入锁一直被别的进程占着”，浏览器保存因此失败；同步计算若阻塞事件循环超过 10 秒，`proper-lockfile` 的刷新计时器停摆，锁会被别的进程当作残留接管，本次写入在改名前核对时失败。
- 为什么是问题：备选最后一行“在锁里算出改动更准”的“准”来自“在锁里拿到确切的前后字节”，与在哪里算 diff 无关；只要账本拿到确切的改前哈希与改后字节，diff 在任何时候算结果都一样。
- 如何核实：读 `db.ts` 的表结构与 `textDiff`；用 jsdiff 对一份 2 MB、改动一半的中文文本跑 `diffLines` 计时（建议主会话补测）。
- 建议改法：删掉第 3 步，锁内只做“读改前哈希（或复用账面末态）→ 写临时文件并算改后哈希 → 交记录 → 改名”；行 diff 留给查询时（nb-history 现状）或锁外的后台任务（例如为收件箱预算摘要），并给 diff 设 `timeout`。备选最后一行的理由改为“在锁里拿到确切的前后字节”。

### 6. “外部改动由文件监视发现”依赖的常开监视与启动对账都不存在：监视只在有订阅时开，挂载方案没有监视，“保留定期全量对账”保留的是没有的东西

- 严重程度：重要
- 类别：依赖的机制是否存在 / 遗漏
- 位置：提案“目标”第 3 条、“外部改动”、“文件监视”（“保留定期全量对账兜底”）；`packages/neuro-book/src/plugins/files/backend/changes.ts:5`（“监视按订阅持有：第一个订阅建立时开一个递归 `fs.watch`，最后一个释放时关掉”）与 `:273-281`；`docs/specs/workspace/resources.md` “副作用与数据”（“文件监视由文件服务按订阅持有，订阅释放后停止”）与“挂载方案”（“这次不支持监视与订阅”）；`files/backend/*.ts` 里没有任何定期对账（`grep setInterval|定期|全量` 无结果），失同步时只给订阅方推 `resync`，由订阅方自己重列
- 现象：
  1. `user://` 只有网页开着文件树时才有监视；项目的监视靠浏览器窗口或作品统计的订阅维持。没有窗口、只有 Agent 在后台跑 shell 时，`user://` 上 shell 的改动没人看见，账本要到下一次经接口写这个文件时才由写前对账补一条外部（时间戳与归属都已失真）；从未再经接口写的文件永远不记。
  2. NeuroBook 没运行时用户用外部编辑器或 `git checkout` 改了书，下次打开项目时没有任何东西去比对“账面末态 vs 磁盘”。提案只说了运行中的监视与“定期全量对账”，没有“打开时对账”，也没定“定期”是多久、谁来跑、扫描时持不持锁。
  3. 账本第一次在一个已有的项目上建立时，全部现有文件怎样入账（全记为外部新建、带全文快照？二进制也存全量？）没写；3000 个文件、几十 MB 的书第一次打开会有一次全量读与入库，阻塞还是后台、期间的写入怎么排，都没写。
- 为什么是问题：目标第 3 条是提案的核心承诺之一；按现有机制，它只在“有网页开着、且进程一直在跑”时成立。改成常开监视又会改变 Spec 的“按订阅持有”与资源占用（每个打开的项目与 `user://` 常驻递归 inotify，`max_user_watches` 有上限）。
- 如何核实：读 `changes.ts` 的 `subscribe`/`stopWatcher`；在测试里不订阅，直接外部改 `user://` 下的文件，确认没有任何回调。
- 建议改法：提案补“监视与对账的寿命”一节：账本所在进程为记账的根常开监视（与给浏览器的订阅解耦，订阅只是分发）；打开根时做一次全量对账（stat 缓存命中的不读内容）；失同步（溢出、根事件）时除了推 `resync` 还要触发一次全量对账；定期对账的间隔与是否持锁写明。首次建账的做法（基线条目的操作者、是否进收件箱、大文件与二进制是否存全量）写明。同时把 `workspace/resources.md` 的“文件监视由文件服务按订阅持有”列入“对 Spec 的预期改动”。

### 7. “读一律 `locate` 后本机读”丢掉了挂载方案的读授权、列出过滤与虚拟根，与 `agent/resources.md` 输出 4、5 和 `workspace/resources.md` 的挂载方案合同冲突

- 严重程度：重要
- 类别：与既有合同的冲突 / 遗漏
- 位置：提案“职责划分”后一段（“读不经接口：服务端使用方用 `locate` 取真实路径后在本机读”）、“接口形态”（`WorkspaceFiles` 只有 `locate` 与写方法，没有 `list`、`read`）、“对 Spec 的预期改动”的 `agent/resources.md` 一条（只写“读经 `realPath`”）；`docs/specs/agent/resources.md` 输出 4（“会话目录里 `session.jsonl` 与 `home/` 之外的文件为 `protected-path`，列出时也不出现”）、输出 5（虚拟根的列出与读）；`docs/specs/workspace/resources.md` “挂载方案”（授权两次、列出的子项逐项按读授权）；`packages/neuro-book/src/plugins/agent/backend/schemes.ts:95`（`skills://` 只声明 `read`、`list`，没有 `realPath`）与 `:104-106`（`sessionRule` 对 `path === ""` 的读放行）
- 现象：
  1. `locate("sessions://<id>")`：挂载点本身按 `sessionRule` 的读规则放行，交回会话目录的真实路径；调用方 `readdir` 后看到的是会话目录里的全部内容，`session.jsonl` 与 `home/` 之外本应 `protected-path`、“列出时也不出现”的文件都露出来。`authorize` 是 Files 在每个请求里调用的，读不经 Files 后就没人调用了。
  2. 虚拟根（`sessions://`、`projects://`、`profiles://` 等）没有真实路径（`unsupported-capability`），而接口里没有 `list`/`read`：Agent 无法再列出“有哪些会话、哪些书”。
  3. `skills://` 没有 `realPath` 能力：读只剩 `locate` 一条路时它完全不可读。
  4. 浏览器访问已注册方案（planned）、以后的虚拟提供者（`plot://` 一类，数据在数据库里，`workspace/resources.md` 能力矩阵“读：返回实体的文本呈现”）都没有真实路径，提案把“读”整体移出 Files 后它们无处安放。
- 为什么是问题：非目标写的是“不防恶意插件”，但这里丢的不是安全边界，而是 `nbook.agent` 自己声明给模型的可见范围与已实现、已验收的合同（`agent/resources.md` 已 `implemented`，`resources.test.ts`“各方案对 Agent 的权限”覆盖）。
- 如何核实：读 `schemes.ts` 的 `sessionRule`；在 `resources.test.ts` 的场景下对 `sessions://<id>` 取真实路径后 `readdir`，比较与经 Files `list` 的结果。
- 建议改法：保留 Files 的 `list` 与按需的 `read`（文本）给挂载方案与虚拟根，`locate` 只作“需要真实路径的工具”（shell、读图片、大文件分页）的入口；`locate` 对目录的结果要么不给（只给文件），要么写明“目录里的过滤由调用方按方案的授权自己做”，并让 Agent 的 `read`/`grep`/`glob` 工具复用同一授权函数。把 `agent/resources.md` 输出 4、5 与 `workspace/resources.md` 挂载方案的“列出的子项逐项按读授权”列入“对 Spec 的预期改动”，写明保留还是放宽。

### 8. 写入协议只描述了“替换已有文件的内容”；新建、删除、改名、移动、复制、转换与清单写入各有自己的落盘方式，记账顺序与锁都没定，“锁保证同一文件的记录按写入顺序到达”在内容写与文件操作之间不成立

- 严重程度：重要
- 类别：写入协议 / 遗漏 / 与 `folder-kinds.md` 的操作锁
- 位置：提案“写入的顺序”（只有“写临时文件 → 改名替换”一种）、“接口形态”的 `create`/`remove`/`rename`；“职责划分”（“现有的 RPC 读、条件保存与文件操作，内部改用下面的写入接口”）。代码：`backend/rooted.ts:263-266`（`replace` 先 `resolve`，目标不存在为 `not-found`：现有替换原语不能新建）；`backend/operations.ts:229-238`、`execute.ts:58`（新建用排他 `open`）；`backend/entry-ops.ts`（改名、移动用 `renameNoReplace`，删除递归 `unlink`，复制先临时名再排他改名）；`backend/manifests.ts:80-111`（清单经 `replace` 写）；`backend/commit.ts:51-64, 92-133, 171-188`（文件操作只在内容树或目录时取整根的操作锁，普通文件夹不取；任何操作都不取按文件的写入锁）；`docs/specs/workspace/folder-kinds.md` 第 73–75 行（经文件服务的操作同步清单、操作锁）
- 现象：
  1. 新建、删除、排他改名都不是“临时文件 + 改名替换”，第 1–6 步套不上；提案没写它们在什么时候、带什么内容交账本。nb-history 的 `registerRename` 从磁盘的目标路径读内容（`workspace-history.ts:215-235`），只能在改名之后调用，与“记录先于落盘”的顺序相反。
  2. 删除要可找回，`registerDelete` 必须拿到删除前的字节（`workspace-history.ts:203-213`）；删一个有 2000 个文件的目录，要在操作锁里读出全部文件并逐个交账本（服务端写项目时还要经 RPC），提案没提。目录改名、移动对账本是“子树里每个文件改名”，同样没提（nb-history 的改名是按文件的）。
  3. 内容写只取按真实路径的文件锁，普通文件夹里的改名、删除什么锁都不取，内容树里的取整根操作锁——两类锁互不排斥。同一文件上“经接口写”与“改名”并发时：写入在第 4 步记下 `edit a.md`，改名随即把 `a.md` 挪走并记 `rename a→b`（`registerRename` 的写前对账发现磁盘与账面不一致，再插一条外部），写入在改名前的身份核对里发现文件不在、重做后失败，又要撤回第一条。提案“锁保证同一文件的记录按写入顺序到达，账本不用排序”只对“同一文件的内容写之间”成立。
  4. 接口的 `create`/`remove`/`rename` 若用于内容树，要同时维护清单并取整根操作锁（`folder-kinds.md` 输出“操作锁”）；提案没说接口方法算不算“经文件服务的操作”。若算，服务端进程要复制一份清单维护与操作锁逻辑；若不算，服务端经接口在内容树里新建的文件只能按“未列入”显示，与浏览器新建的表现不一致。浏览器还有接口里没有的 `copy`、`convert`、`createContent`、`reorder`、`display`、`include`、`drop` 与带位置的移动，“内部改用写入接口”对它们无从谈起。
- 为什么是问题：文件树里的每一种操作都会进账本；只定了一种写入的顺序，其余的实现者只能各自发明，正是第 1、2 条那类不一致最容易出现的地方。
- 如何核实：读上面列出的落盘路径；在测试里对普通文件夹里的 `a.md` 并发“经接口写”与“改名”，观察账本条目。
- 建议改法：提案按落盘方式列一张表（替换、排他新建、排他改名、递归删除、复制、清单写入），逐行写：取哪把锁、何时交账本、交什么（删除交改前内容或快照引用，目录操作展开成逐文件条目还是一条目录条目）、失败与撤回。并定一条锁的规则：凡要记账的操作，对涉及的每个文件路径取同一把文件锁（或者让文件操作在取整根操作锁之外，再对单文件源与目标取文件锁），否则把“账本不用排序”删掉、改为账本按“改前哈希”链接条目并能容忍乱序。另写明接口方法在内容树里是否维护清单。

### 9. `openWrite` 从打开到 commit 一直持有跨进程文件锁：等锁方只等约 3.3 秒，忘了 commit/abort 的写入方会把这个文件永久锁住，现有原语也不支持流式

- 严重程度：重要
- 类别：写入协议 / 资源释放 / 依赖的机制是否存在
- 位置：提案“接口形态”`openWrite` 的注释（“commit 之前一直持有这个文件的锁”）与 `FileWriter`；`packages/neuro-book/src/backend/locked-replace.ts:25-28`（等锁约 3.3 秒、10 秒残留）、`:95`（`proper-lockfile` 持锁期间按定时器刷新锁目录，进程活着锁就一直有效）、`:150, 168`（`replaceOnce` 把当前文件整份读进内存、把 `decision.write` 整份写出）；`docs/specs/workspace/files.md` “读取与保存”的“提交”
- 现象：
  1. 图生文、导入导出的流式写可能持续几十秒（边生成边写）。这期间浏览器对同一文件的保存、Agent 的 `edit` 等锁约 3.3 秒后失败，得到的码是 `io-failed`（“写入锁一直被别的进程占着”），不是 `busy`，调用方无从区分“稍后重试”与“读写失败”。
  2. 调用方忘了 `commit`/`abort`、抛异常跳过了收尾、或调用方入口停止：锁由本进程的刷新计时器一直续着，别的进程永远等不到；同进程的门面释放也没有说要中止在途的 writer（`server-files.ts:112-114` 现在只中止在途调用的 signal）。临时文件同样留在用户的书目录里（进程崩溃时更是如此），提案没有启动时清理残留临时文件的规则。
  3. 服务端写项目文件时，流式写的整个过程还要持有项目租约（第 4 步要调用项目子进程）；现在 `projects://` 的租约按每次调用取得与释放（`projects-scheme.ts:171-187`），`openWrite` 跨多次 `write` 调用，租约怎么持有没写。
  4. `replaceLocked` 只支持整份字节，`openWrite` 需要新的原语（锁内打开临时文件、流式写、commit 时做身份核对与改名），这部分代码要新写而不是“内部改用”。
- 为什么是问题：锁泄漏的后果是“某个章节再也存不上”，只能重启服务端恢复；而提案的“目标”第 1 条把大文件流式写列为主要场景。
- 如何核实：读 `locked-replace.ts` 与 `proper-lockfile` 的 `update` 缺省（`stale / 2`）；写一个持锁不放的测试，另一进程保存同一文件，看到约 3.3 秒后 `io-failed`。
- 建议改法：流式写的数据先写到临时文件、不持锁（临时文件名带实例标记，监视与账本都忽略），`commit` 时才取锁，在锁内做“读改前哈希、核对基线、交账本、改名”，锁的持有时间与整份写相同。若一定要从 `openWrite` 起就持锁（防止别人在生成期间改），要写明：writer 绑定调用方门面与 `signal`，门面释放、`signal` 触发、空闲超时都自动 `abort`；等锁失败报 `busy`；启动时按命名规则清理残留临时文件。

### 10. 两个服务端同开一个项目时，“SQLite 事务兜底”不够：nb-history 在事务外读账面末态，再开写事务追加

- 严重程度：重要
- 类别：跨进程与归属 / nb-history 的补强
- 位置：提案“账本放在哪个进程”（“两个服务端同时打开同一个项目的少见情形，靠 SQLite 事务（`BEGIN IMMEDIATE` 加等锁超时）兜底”）、“nb-history 要补的”第 5 条；`packages/nb-history/src/workspace-history.ts:161-176`（`registerWrite`：先 `implicitReconcile` 在写连接上读末态，再 `appendEntries` 开写事务）、`:829-844`、`:870-906`；`src/db.ts:62-67`（没有设 `busy_timeout`）；`docs/specs/runtime/projects.md` 第 21、175 行（不加目录锁，项目级数据靠数据本身的机制）
- 现象：nb-history 的“读末态 → 决定是否补外部条目、算 beforeHash → 追加”是两步：读在事务外（`nameEndState(this.client, path)`），追加在随后开的写事务里。进程内靠 Promise 队列串行，所以单进程没问题；两个项目子进程（各属一个服务端）同写一个库时，A 读到末态 H0，B 追加了 H1，A 再以 H0 为基准追加，链断开、或两边各补一条重复的外部条目。两个进程的监视都会看到同一次外部改动，各自 `reconcile`，同样依赖“读末态与追加在同一个事务里”才能只记一次。`prune`、`purgePaths`、接受位点与游标的读改写也一样。把每次写包成 `BEGIN IMMEDIATE` 只解决“写不撕裂”，不解决“读到的末态已过期”。
- 为什么是问题：`runtime/projects.md` 明确允许这种情形，并要求“优先用数据本身的机制”；提案说事务兜底，但列出的补强（第 5 条“写入进事务”）没写读也要进同一个事务，实现者按字面会只包写。
- 如何核实：读上述代码；起两个 `WorkspaceHistory` 打开同一个库，交错调用 `registerWrite` 与 `reconcile`，看链是否断开或出现重复外部条目（libsql 不设 `busy_timeout` 时第二个写事务直接 `SQLITE_BUSY`）。
- 建议改法：把“nb-history 要补的”第 5 条写成：所有写入口在一个 `BEGIN IMMEDIATE` 事务里完成“读末态、写前对账、写快照、追加条目、改位点”，设 `busy_timeout`，`SQLITE_BUSY` 有明确的失败码与重试；`prune` 同样整体在一个事务里；去掉 NOTES 里“单进程单写者”的前提后补一条双进程的合同测试。另：两个项目子进程都在算同一份 stat 缓存（第 3 条），缓存若放进库里也要按同样的事务规则更新。`user://` 不受此影响：同一状态根只跑一个服务端（`runtime/server-host.md` 场景 18），不同状态根的 `user://` 是不同目录。

### 11. 账本成了每一次保存的硬前置：账本不可用（库损坏、磁盘满、等锁超时、项目子进程停止中）时保存怎么办没写

- 严重程度：重要
- 类别：失败路径 / 可用性
- 位置：提案“写入的顺序”第 4 步（“交给这个根的账本，等它确认”）、“影响”的“迁移与回滚”（“回滚即停用账本，文件本身不受影响”）；`docs/specs/runtime/projects.md` 第 75、77 行（停止序列按依赖逆序关闭插件；崩溃即 `terminated`、全部租约失效、不自动重启）
- 现象：按提案，记录确认是改名的前提。于是 `history.sqlite` 损坏或被同步盘锁住、磁盘写满（快照写不进但正文那几 KB 本来写得进）、两个服务端争库超时、项目子进程正在停止（账本已关、文件服务还在）或刚崩溃时，浏览器保存、Agent 写入都会失败。提案只在“回滚”里说可以停用账本，没有运行时的降级：账本失败时是拒绝写入（用户的章节存不上），还是照写并留待对账补一条外部（丢归属不丢正文）；失败码是什么（现有码表里没有对应项，`io-failed` 会被调用方当作可重试的读写失败）。
- 为什么是问题：账本是“记录谁改了什么”的辅助数据，正文是用户的作品；没有写明优先级时，实现者照“等它确认”的字面会让历史库的故障阻断保存，这是比丢一条归属严重得多的失败。停止序列里账本与文件服务谁先关也影响在途写入。
- 如何核实：把测试里的 `history.sqlite` 换成只读或损坏文件，按提案的顺序经接口保存，看结果。
- 建议改法：写明“账本失败不阻断写入”：账本不可用时照常落盘，结果里带一个可观察的标记（例如 `recorded: false`），账本恢复后由对账补外部条目，并记诊断；或者明确选择“拒绝写入”并给出专门的失败码与用户提示。同时写明项目实例停止序列中账本晚于文件服务关闭（或文件服务停止前排空在途写入）。

### 12. 没考虑的更简单做法：读放开、写仍由拥有根的进程提交，服务端只交“临时文件 + 基线”

- 严重程度：重要
- 类别：备选与取舍
- 位置：提案“备选与取舍”、“账本放在哪个进程”
- 现象：提案在“全部经文件服务”与“各进程本机读写、锁内经 RPC 交账本”之间二选一。中间还有一种：读一律 `locate` 后本机读（提案已定，解决分页、字节、shell 的需求）；写由调用方先在目标目录写好临时文件（流式、任意大小、不持锁），再调用拥有根的进程的“提交”方法，参数只有临时文件路径、目标地址、基线与操作者；拥有根的进程（项目的是项目子进程，`user://` 的是服务端）在自己的文件锁里核对基线、读临时文件算哈希、改名、记账、登记回声、以真实来源发事件。
- 为什么更好：
  - 消息体只有几百字节，1 MiB 与 JSON 帧的问题（第 4 条）不存在；
  - 写入、账本、回声、事件都在一个进程里，第 3 条的来源丢失、临时文件外泄不出现，第 1 条变成同进程内的顺序问题（可以照 nb-history 的 R10 先改名后记账，或在同一个进程里做准备/落定）；
  - `unknown-outcome` 有了确定的核对办法：调用方比较目标的当前哈希与自己临时文件的哈希，即可知道是否提交；临时文件仍在就是没提交；
  - 文件操作（第 8 条）本来就在拥有根的进程里执行，清单与操作锁不必复制到服务端；
  - 浏览器的保存路径不变（项目子进程本来就在执行它），“浏览器 RPC 合同不变”自然成立。
  代价：服务端写项目文件仍是一跳 RPC（实测 p99 约 2.4 ms，和提案第 4 步的那一跳相同），项目没在运行时要先打开（现状已如此）；跨设备时临时文件必须与目标同目录（由 `locate` 给出目标位置即可）。
- 如何核实：对照提案“账本放在哪个进程”第一句“由拥有这个根的进程独占写”——该句说的是账本；把同一原则用到“落盘”上就是这个做法。
- 建议改法：把它作为备选写进“备选与取舍”，与现方案比较（锁的持有方、失败恢复、回声、文件操作、浏览器路径），由开发者定。若仍选现方案，至少要逐条回应第 1、3、4、8 条。

### 13. 账本记哪些文件没有规则：项目里的 `.git`、编辑器交换文件、别的实例的临时文件都会进账本，提案还把“读用户的 `.gitignore`”当作 git 方案的缺点

- 严重程度：重要
- 类别：遗漏 / 外部改动
- 位置：提案“外部改动”“影响”的“数据”、“备选与取舍”第二行（“读用户的 `.gitignore`”列为隐藏 git 的缺点）、决策记录第 3 条（只排除了 Agent 会话目录与临时目录）；`packages/neuro-book/src/plugins/files/backend/changes.ts:141-142`（监视只过滤项目根下的 `.nbook` 与本实例标记的临时文件）
- 现象：现在的监视只为“刷新网页”服务，多报几条无害；接上账本后每条外部变化都变成一条带全文快照的条目。用户在书目录里 `git init`（写作者常用 git 备份）时，每次 `git commit`/`git gc` 会改动 `.git/objects` 下大量文件，全部以外部新建、修改记进 `history.sqlite`，并且按提案第 1 条“二进制与大文件存全量”存下（git 对象是压缩后的二进制）；Vim 的 `.swp`、Emacs 的 `.#文件`、`~` 备份、`.DS_Store`、`Thumbs.db`、导出目录、别的 NeuroBook 实例（第二个服务端）的临时文件同理。提案没有任何排除规则，也没写排除规则改了之后已有条目怎么办（nb-history 有 `purgePaths`，见 NOTES 第 15 条）。
- 为什么是问题：库体积与对账开销会被与写作无关的文件主导，时间线与“外部改动”里充满噪声；`.git` 是最可能出现在书目录里的大目录。
- 如何核实：在测试项目里 `git init` 并提交几次，统计监视报来的路径（`changes.ts` 的 `pending`）中 `.git/` 下的数量。
- 建议改法：定一份账本的路径规则（缺省排除 `.git/`、`.hg/`、`.svn/`、常见编辑器交换与备份文件、系统元数据文件、所有实例的临时文件命名模式），写明是否读取 `.gitignore`（只读不写，与“隐藏 git 读用户的 `.gitignore`”不是一回事）以及用户能否自行配置；规则变化时用 `purgePaths` 清掉已有条目。同时把“账本只记普通文件，符号链接、FIFO 等不记；经链接写入记在真实路径上”写明。

### 14. stat 缓存只比修改时间、大小与 inode，漏了 ctime：保留时间戳的原地改写会被判为未变，与现有回声设计特意避开的情形相同

- 严重程度：重要
- 类别：外部改动 / 对照参照（git）
- 位置：提案“外部改动”（“对账前先比文件的修改时间、大小与 inode（照 git 的 index 缓存），不变就不读内容”）、“nb-history 要补的”第 3 条；`packages/neuro-book/src/plugins/files/backend/changes.ts:9-11`（“保存登记内容 hash（不靠修改时间与大小：保留时间戳的外部修改会被它吞掉）”）与 `:244`（目录项回声另比 ctime）；`docs/specs/workspace/files.md` 实现合同（字节路由的 ETag 取 inode、ctime、mtime 与大小，“同样大小、改回修改时间的改写也换 ETag”）
- 现象：git 的 index 记 ctime、mtime、dev、ino、uid、gid、size，缺省也比 ctime（`core.trustctime`）。提案只取三项。`cp -p`、`rsync -t`、`touch -r`、部分同步盘与备份还原都会原地改写内容并恢复修改时间；大小不变时（例如改一个错别字、同字数替换）缓存判为未变，外部改动永远不进账本，之后经接口写这个文件时写前对账才补一条外部，时间与归属都错。仓库里另外两处（回声、ETag）都已经因为这个原因加了 ctime 或改比内容。
- 为什么是问题：漏记外部改动会让“恢复”拿不到那个版本；而提案称“照 git”，实际比 git 弱。
- 如何核实：写文件、记 stat，`cp -p` 一份同大小不同内容的文件覆盖原文件（或写后 `utimes` 恢复修改时间），比较三项与 ctime。
- 建议改法：stat 缓存加 ctime（Windows 上无可靠 ctime 时退回比内容，或比 `birthtime` 加 `mtime` 并写明限制）；另外，文件监视报来的路径已经说明“有变化”，对这些路径直接读内容比哈希，stat 缓存只用于启动对账与定期全量对账。racy 判定按 git 的做法记“缓存写入时间”，修改时间不早于它的条目一律比内容。

### 17. “nb-history 要补的”只列了五项，接入时必然要改的还有：大文件入参、快照格式标记、库的版本与迁移、操作者与用户身份、路径键

- 严重程度：重要
- 类别：nb-history 的补强
- 位置：提案“nb-history 要补的”；`packages/nb-history/src/workspace-history.ts:161-176`（`registerWrite(actor, path, before: Uint8Array | null, after: Uint8Array)`）、`:857-864`（`putSnapshot` 只按“超限或含 NUL”决定 body 是否为空）、`NOTES.md` 第 4 条（“`byte_size ≤ maxSnapshotBytes` 却无 body ⇒ 只可能是二进制”的推断）、`src/db.ts:13-52`（`CREATE TABLE IF NOT EXISTS`，没有版本号）、`src/hash.ts:9-11`（整文件查 NUL）、`README.md` “语义要点”（actor 四类，`user(userId)`）与“已知限制”第 4 条（收件箱阻止稀疏、需要自动接受）；仓库里依赖 nb-history 的只有旧应用（`packages/neuro-book-legacy/package.json`）
- 现象（每项都是接入时绕不过去的）：
  1. **大文件入参**：`registerWrite` 要求前后两份字节都在内存里；提案要“二进制与大文件存全量”、流式写，入口要改成接受文件路径或流加哈希，否则 20 MB 图片的改前、改后各在内存里一份，经 RPC 时还要再编码。
  2. **快照格式**：加 zstd 与“二进制也存 body”之后，`file_snapshot` 需要显式的编码与种类列（压缩与否、文本或二进制、为何没有 body）；NOTES 第 4 条靠“有没有 body”推断二进制的做法随之失效，`textDiff` 的二进制判定要改。
  3. **库的版本与迁移**：`history.sqlite` 放在书里、“随书移动”，会被新旧不同版本的 NeuroBook 打开；现在没有 `user_version` 或版本表，加列（操作者种类、会话条目 id、压缩标记、stat 缓存）只能靠 `IF NOT EXISTS`。提案“迁移与回滚”说“没有旧格式要迁”只对今天成立，要定版本号与“遇到更新的库怎么办”（只读、拒绝打开或降级）。
  4. **操作者**：nb-history 的 `user` 带 `userId`，`system` 带 `source`；新应用没有用户身份（浏览器写入的来源是 `{kind: "user", plugin}`），收件箱与接受位点按 `userId` 分组。提案加 `plugin` 一类，却没说与现有 `system` 的关系、`userId` 填什么、`plugin` 条目是否触发收件箱（现在 agent/system 触发）。
  5. **判二进制**：提案要照 git 看前 8000 字节，nb-history 看整个文件，两者会给同一文件不同结论；接口第 3 步与账本各判一次时要统一到一处。
  6. **路径键**：nb-history 记录调用方给的字符串、由 `resolvePath` 落盘；经符号链接写入时 Files 替换的是链接目标（`rooted.ts` `replace`），监视报来的也是真实路径。要写明账本按“相对根的真实路径”记，否则同一文件经别名写入会成为两条时间线。
  7. **自动接受**：README 已知限制第 4 条要求宿主提供“N 天未审自动接受”，否则库只增不减；Agent 写入接上之后收件箱条目会成倍增加，提案的保留策略只说“保留策略”四个字。
  8. **驱动更换**：`libsql` 换 `bun:sqlite` 不只是换连接，`transaction("read"|"write")`、`lastInsertRowid`、blob 返回类型都要改，旧应用仍依赖这个包（要么旧应用跟着改，要么新应用用分叉，提案没说）。
- 为什么是问题：提案把 nb-history 描述为“已经实现了账本的大半”，补强清单决定了实施工作量与计划切片；漏掉的这几项每一项都会改表结构或公开方法。
- 如何核实：读上面列出的代码位置。
- 建议改法：把以上八项并入“nb-history 要补的”，并写明 nb-history 是原地改（旧应用随之受影响）还是新应用另起一版。

### 18. 第 4 步插在“改名前的身份核对”与改名之间还是之前，提案没定；两种放法各有代价

- 严重程度：建议
- 类别：写入协议 / 与现有锁原语的配合
- 位置：提案“写入的顺序”第 4、5 步；`packages/neuro-book/src/backend/locked-replace.ts:64-76`（`replaceOnce` 最多重做 3 次，`decide` 每次重做都会再调用）、`:178-187`（改名前先核对仍持锁、再核对文件身份没变，然后紧接着改名）；`docs/specs/workspace/files.md` “提交”（“外部编辑器不走锁：改名前的身份核对只缩小窗口，核对与改名之间被外部写入的那一次仍会被覆盖”）
- 现象：
  - 放在身份核对之后、改名之前：核对与改名之间原本只隔一次系统调用，现在隔一次跨进程 RPC（空载荷 p99 约 2.4 ms，带内容见第 4 条）。窗口内外部编辑器的写入会被覆盖，而且覆盖后磁盘等于账面末态，监视把那次外部写入的事件当回声吸收——这次外部改动在账本里不留痕迹，与“外部改动由文件监视发现”的目标相反。
  - 放在身份核对之前：核对发现文件变了（`modified`）就要重做，每次重做都留下一条要撤回的记录（第 1 条的撤回问题被放大）；核对失去锁（锁被当作残留接管）时同样。
- 为什么是问题：实现者只能二选一，提案没给依据；`files.md` 的已知窗口会被放大，Spec 的这句要随之更新。
- 如何核实：读 `replaceOnce`。
- 建议改法：采用第 1 条甲方案（先改名后记账）时问题消失：记账前磁盘已是新内容，窗口内的外部写入会让记账时的写前对账或随后的监视看到不一致而补外部条目。若坚持先记账，写明放在身份核对之前，并配合“待定/落定”两段，使重做只产生被丢弃的待定条目。
- 更正（上一条“建议改法”的措辞）：先改名后记账时，窗口回到现状的“一次系统调用”宽度，并不是消失；窗口内被覆盖的外部写入仍不留痕迹，这是 `files.md` 已接受的限制，提案应照抄这条限制并说明账本同样记不到它。

### 19. 回声判定变成两套：ChangeHub 的进程内登记（60 秒寿命、失同步时清空）与账本的“与账面末态一致”，两者结论可能不同

- 严重程度：建议
- 类别：回声与外部改动 / 别扭之处
- 位置：提案“文件监视”（“保留现有的递归 `fs.watch`……与批合并、回声过滤”）与“外部改动”（账本按账面末态吸收回声）；`packages/neuro-book/src/plugins/files/backend/changes.ts:40-41`（`EXPECT_TTL_MS = 60_000`）、`:121-130, 175-177`（关监视或失同步重建时 `expected.clear()`）、`:237-246`（按登记的哈希读文件比对）
- 现象：同一次写入，网页事件的来源由 ChangeHub 的登记决定，账本条目由账面末态决定。登记过期、因溢出被清空、或写入发生在别的进程（第 3 条）时，ChangeHub 把它当外部发给网页，账本却当回声吸收（或反过来：账本因第 2 条的竞态记了外部，网页却收到真实来源）。同一个文件的同一次变化，网页与时间线给出不同的归属；两套机制还各读一次文件内容算哈希。
- 为什么是问题：用户在编辑器里看到“外部修改”的提示，打开时间线却是“Agent 写入”，难以解释；两套逻辑也要各自维护。
- 如何核实：读上述代码；在测试里写入后触发一次溢出（`changes.test.ts` 已有失同步用例），再看网页事件与账本条目。
- 建议改法：对记账的根，以账本为回声的唯一依据：监视一批先交账本对账，账本返回“回声 / 外部 / 经接口（带操作者）”，ChangeHub 按这个结果给网页发事件；不记账的根（会话目录、临时目录）保留现有的进程内登记。提案写明这一点，并把 `workspace/resources.md` 的回声规则（“回声按真实路径的预期状态判定”）列入改动。

### 20. 备选表最后两行的放弃理由只针对“锁外”的变体，锁内的同名做法没有比较

- 严重程度：建议
- 类别：备选与取舍
- 位置：提案“备选与取舍”的“写盘之后异步报账”“写入方只报‘操作者 + 改后哈希’，由账本读文件算改动”两行
- 现象：
  - “写盘之后异步报账”的放弃理由是“记录与写入的顺序要靠哈希链加序号排序”。这只对“锁外、异步”成立；“锁内、先改名后同步记账”（nb-history 自己的 R10 顺序）保留了锁带来的按文件有序，又不会留下幽灵版本（第 1 条），表里没有这一行。
  - “只报改后哈希，由账本读文件”的放弃理由是“账本读文件时内容可能又变了”。若账本在写入方仍持锁时读临时文件（第 4 条的改法），内容不会变，且省掉经 RPC 搬内容；表里同样没有这一变体。
- 为什么是问题：被比较掉的是两个容易反驳的版本，开发者看到的取舍不完整；而这两个锁内变体正好能解决第 1、4 条。
- 如何核实：对照表格原文与 `nb-history/src/workspace-history.ts:57-66` 的崩溃一致性说明。
- 建议改法：表里补“锁内先改名后记账”“锁内由账本读临时文件”两行，写各自的代价，再说明为什么选现方案（或改选）。

### 21. Agent 经 `shell` 改书一律记为外部，而外部条目不进审查收件箱：Agent 最常用的改文件方式绕过了审查

- 严重程度：重要
- 类别：外部改动 / 与既有合同的冲突 / 目标是否达成
- 位置：提案“影响”的“安全”（“shell 与外部工具的写入照旧记为外部”）、“接口形态”末段；`docs/specs/workspace/resources.md` “写入来源”（“bash 等绕过文件服务的写入由文件监视发现，来源记为外部，能按会话工作目录确定会话时记为该会话”）；`packages/nb-history/README.md` “语义要点”的收件箱（“某文件在接受位点之后存在 agent / system 条目时出现……用户 / 外部条目本身不触发收件箱”）、`NOTES.md` 第 9 条
- 现象：t12 第一批工具里有 `shell`，code agent 习惯用 `sed -i`、脚本、`mv` 批量改文件。按提案，这些改动在账本里是“外部”，不进收件箱、不算“这一轮改动的文件”（t13），会话未见变更里也不会标为该会话自己的改动。现有 Spec 已经写了“能按会话工作目录确定会话时记为该会话”，提案把它退成了“照旧记为外部”，没有列为对 Spec 的改动，也没有说明对审查收件箱这一目标的影响。
- 为什么是问题：提案“问题”第 3 条把“审查收件箱、每轮改动文件”列为要解决的需求；Agent 经 `shell` 的改动是它最需要覆盖的那部分。非目标“不防恶意”说的是故意绕开，这里是 Agent 的正常用法。
- 如何核实：对照 nb-history 收件箱的触发规则与提案对 shell 的处理。
- 建议改法：`nbook.agent` 执行一条 `shell` 命令期间登记一个“归属窗口”（会话、命令开始与结束时刻、工作目录），账本在窗口内对账得到的外部改动记为该会话（标明“经 shell，推断”），窗口结束后再做一次对账收口；并发的外部编辑仍可能被误归，写明这一限制。若决定不做，在“非目标”里明说“Agent 经 shell 的改动不进收件箱”，并请开发者确认，同时改 `workspace/resources.md` 的那句。

### 22. `locate` “不建任何东西”与挂载方案“取真实路径时建好挂载点”冲突；本机读也失去了 Files 读取时的身份核对

- 严重程度：建议
- 类别：与既有合同的冲突
- 位置：提案“接口形态”`locate` 的注释（“不存在时给出将来的位置（exists: false），不建任何东西”）；`docs/specs/agent/resources.md` 输出 6（“第一次写、新建或取真实路径时建好（Profile 的笔记目录、会话的临时目录、会话的 `home/`）”）、`workspace/resources.md` 挂载方案第三条；`packages/neuro-book/src/plugins/files/backend/mounted.ts:31-33`（`MATERIALIZES` 含 `realPath`）；`backend/rooted.ts:239-261`（Files 读取时打开句柄后核对 dev 与 inode，解析与打开之间被换掉就报错）
- 现象：`shell` 的工作目录是会话的 `home/`（`workspace/resources.md` 的 shell 一条），现在靠“取真实路径”把它建出来；`locate` 改成不建之后，新会话第一次跑 `shell` 时工作目录不存在。另外，Files 的读在打开句柄后核对身份，挡住“解析与打开之间目录项被换成链接”的竞态；调用方拿路径自己读时没有这层核对。后者在 t12 第 13 条（跟随用户的链接）之后多半可以接受，但要写明。
- 为什么是问题：前者是已实现合同（`mounted.ts`）的行为变化，后者是 `workspace/resources.md` “已知限制”的扩大，提案都没列。
- 如何核实：读 `mounted.ts` 的 `MATERIALIZES` 与 `rooted.ts` 的 `read`。
- 建议改法：`locate` 保留“挂载点按声明按需建目录”的行为（只建挂载点与声明的子目录，不建调用方路径里的中间目录），或另给一个 `ensure` 选项；在 Spec 的已知限制里写明“经 `locate` 的本机读不做打开后的身份核对”。
- 更正（上一条“现象”）：`shell` 的工作目录在没有主项目时才是会话的 `home/`，有主项目时是项目目录（`workspace/resources.md` 的 shell 一条）；受影响的是没有主项目的新会话。

## 未发现问题的方面

- `user://` 的账本放在服务端：同一状态根同一时间只跑一个服务端（`runtime/server-host.md` 场景 18），不同状态根的 `user://` 是不同目录，单写者前提对它成立。
- 外部对账用的“上一版”在保留策略稀疏化之后仍在：每个文件的最新一条永不删除（`prune.ts` 保护规则 c），快照 GC 同时统计 `before_hash` 与 `after_hash` 的引用（`prune.ts:139-143`），留下的条目两侧快照都在；例外只有超过 2 MiB 或二进制（现状只记哈希），提案第 1 条补强已覆盖。
- 放弃“隐藏 git 仓库”的理由（依赖系统 git、读用户的 `.gitignore`、每次记账一次进程、要另建一套 SQLite 并保持两套账本一致）与调研记录一致，站得住。
- 与 ADR 0027 的关系：非目标“记账只对守约的写入方成立”与 ADR 0027 后果第一条一致，没有发现冲突。
- 锁内 RPC 的延迟数字与 t12 README 第 16 条的实测一致（空载荷）；带内容后的问题见第 4 条。
