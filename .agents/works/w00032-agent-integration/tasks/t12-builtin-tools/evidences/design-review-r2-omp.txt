### 重要｜正确性｜grep/glob 的 onMatch 不是流式入口

- **严重程度**：重要；**类别**：正确性、安全与性能。
- **位置**：计划 28、113–114 行；`node_modules/@oh-my-pi/pi-natives/native/index.d.ts:2191–2202,2289–2299`。
- **现象**：计划依赖第二参数 `onMatch` 边搜边授权、取得 `limit + 1` 条后取消。该回调在搜索结束后才交付；真实流式 grep 是选项里的 `onMatches`。glob 的第二参数同样不能据此提前截断搜索。
- **为什么是问题**：按计划实现会先把所有匹配搜完、存入原生结果，再执行授权。首条回调取消也挡不住剩余交付；30 秒/5 秒期限不是可见结果限额，超大目录仍先做全量工作。授权是异步 `readPath`，而 `onMatches` 类型和 glob 回调都是返回 `void`，也不能未经核实地假定回调等待这些 Promise 并提供背压。
- **如何核实**：`bun --no-install --no-env-file /tmp/review-t12-design-r2/lab/native.ts`；1500 个各含一处匹配的文件，grep 的 `onMatch` 第一次即 abort，仍收到 **1500** 次回调，最后抛 `AbortError`；glob 同样收到 **1500** 次。改为 grep 选项 `onMatches`，首次批次中止只交付 **8** 条（批次大小不固定）。实验调用真实公开原生入口。
- **建议改法**：grep 明确改用 `onMatches`，定义可等待异步授权的有界队列/分批扫描，先验证原生是否等待异步回调；glob 不再承诺不存在的流式停止能力，可按资源授权裁剪遍历根后用 `maxResults: limit + 1`，或选真正支持可中止分批遍历的入口。验收必须证明达到可见配额后没有继续遍历全部候选，而不只断言最终返回长度。

### 重要｜不变量｜搜索不跟随用户目录链接，与已定读语义不一致

- **严重程度**：重要；**类别**：不变量、正确性。
- **位置**：计划 20、28、112 行；Task README 决定 13。
- **现象**：计划明确用户自己建的链接“读、搜索跟随链接”，却给 glob 固定 `followLinks: false`；原生 grep 默认也不递归进入后代目录链接。
- **为什么是问题**：用户把外部资料目录链接进书后，`read project://资料/某文件` 可读，`grep` 和 `glob` 从书根搜索却看不到里面的文件，会错误报告没有匹配。这不是链接替换竞态或 shell 的安全豁免。
- **如何核实**：同一 `native.ts` 实验：`links/alias` 链接到包含 `visible.txt` 的真实目录。以 `links/` 为根 grep 得 **0** 条、`filesSearched: 0`；glob `followLinks:false` 只交回链接项 `alias`，没有子文件；把显式搜索根换为 `links/alias` 则 grep 返回 **1** 条。授权 `readPath` 在结果出现后执行，不能补回根本没被搜索的文件。
- **建议改法**：glob 开启跟随并保留逐结果授权；grep 使用支持后代链接的遍历方式，或先按资源视图枚举可读根，再对每个真实目录执行原生搜索并去重、防环。补“从书根搜用户目录链接内文件”的验收，而不只测搜索根本身是链接。

### 重要｜正确性｜两种 edit 均不会进入计划的新建写回分支

- **严重程度**：重要；**类别**：正确性、测试。
- **位置**：计划 103–105、157 行。
- **现象**：第 2 步记目标不存在、第 5 步期望用 `absent + createParents` 新建；验收也要求 edit 新建文件。但所选 hashline 和 replace 模式在 writer 之前就拒绝不存在的文件。
- **为什么是问题**：即使新增“最近祖先定位”辅助并成功把 URL 换成不存在的真实位置，也无法让引擎交出 `create` 写请求。新底座支持新建不代表这两个模式支持新建；照计划的验收无法通过。
- **如何核实**：同一 `native.ts`，真实 EditSession，URL resolver 直接给出尚不存在的 `new/nested.txt`；hashline `PUT <1` 返回 `file_not_found`，原文 `Use the write tool to create new files.`，writer **0** 次。replace 的 `old_string:""` 返回 `old_string must not be empty.`，writer **0** 次。已有文件 replace、虚设 cwd/homeDir、宿主 writer 不落盘均正常，不是 URL/cwd 接线失败。
- **建议改法**：最少部件方案是把新建统一交给已有 `write` 工具，删掉 edit 的不存在目标预读/新建分支与对应验收，并在工具合同明确 edit 只改现有文件；若坚持 edit 新建，要明确新增语法/引擎能力，而不能只改 writer。
### 阻断｜正确性｜项目 readPath 的租约在工具真正读取前已经释放

- **严重程度**：阻断；**类别**：正确性、不变量。
- **位置**：计划 37、68、113 行；`packages/neuro-book/src/plugins/files/backend/workspace-files.ts:122–127`；`packages/neuro-book/src/plugins/files/backend/projects-scheme.ts:97–110`。
- **现象**：计划让工具先 `resources.readPath(project://...)`，再在本机分页读、搜索或交给 edit。当前 `readPath` 对 `projects://` 经 `projects.call` 调项目的 `realPath(follow:true)`；`projects.call` 在回调完成后立刻 `lease.release()`。返回的只是字符串路径，没有携带租约或保持项目实例的句柄。
- **为什么是问题**：项目可在定位返回后进入宽限关闭、代次被替换或停止，工具随后打开的路径就可能失效、指向旧代目录，甚至读到项目已不再由当前资源视图承诺的对象。计划把“定位后路径还有效多久”当作读路径事实，但底座没有这个寿命保证；逐文件 `readPath` 核对也只保护核对那一刻。
- **如何核实**：静态跟随真实调用链可见：`workspace-files.ts` 第 125 行调用 `projects.call`，而 `projects-scheme.ts` 第 105–110 行在 `finally` 无条件释放租约；`ReadPath` 类型只有 `path/kind`，没有 `release`。没有用伪造项目代替真实运行时。
- **建议改法**：不要把跨进程项目路径裸交给长时间工具。为 `readPath` 增加持有期明确的 read lease（工具调用结束或取消时释放），或在工具实际读取期间由 Files 提供带租约的读/搜索入口；至少 edit 的读基线、read 的分页、grep/glob 的整次扫描要在同一个项目租约内完成。验收覆盖定位后停止项目、换代和取消收口。
### 阻断｜正确性｜SessionArtifacts 计划使用了文件服务不认识的单数地址

- **严重程度**：阻断；**类别**：正确性、接口与合同。
- **位置**：计划 72–83 行；`packages/neuro-book/src/plugins/agent/backend/resources.ts:24–39,68–78`；`packages/neuro-book/src/plugins/files/backend/workspace-files.ts:102–127`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:95–125`。
- **现象**：计划的 `SessionArtifacts.save` 写入 `session://artifacts/<name>`，实现又说调用 `nbook.agent` 自己的 `WorkspaceFiles` 门面且“不带 as”。单数地址的改写只发生在 `sessionResources(...).expand/bind`；AgentRuntime 直接把 `options.files` 传给资源视图，宿主门面并不自动改写。`WorkspaceFiles.begin()` 只做 `parseAddress`，随后按方案注册表查找 `session`。
- **为什么是问题**：`session` 不是 `nbook.files` 注册的全局方案，当前 Agent 只注册 `sessions`，所以这条写路径会返回 `unknown-scheme`，根本不会创建 `artifacts/`。把“不带 as”理解成“自动拥有单数地址改写”混淆了 `WorkspaceFiles` 与 `SessionResources` 两层；宿主绕过 Agent 分类的决定不能同时绕过地址解析。
- **如何核实**：`resources.ts:24–39` 是唯一的单数地址改写实现；`schemes.ts:43` 的全局方案为 `sessions/profiles/temps/docs/skills`，没有 `session`；`workspace-files.ts:102–127` 直接按解析后的 scheme 查 registry。现有资源测试也只断言 `resources.expand("session://...")` 后得到 `sessions://...`，没有证明原始 WorkspaceFiles 能接受单数地址。
- **建议改法**：`SessionArtifacts` 的实现持有会话上下文，写入全局地址 `sessions://<sessionId>/home/artifacts/<name>`；或把“宿主身份写 artifact”做成拥有 `expand` 的 Agent 专用接口。接口文档明确单数地址只属于会话资源视图，不能传给原始 `WorkspaceFiles`。补宿主写入口真实成功测试。
### 重要｜不变量｜共享 EditStore 没有接入点，跨工具的 hashline 快照会断掉

- **严重程度**：重要；**类别**：接口、不变量、生命周期。
- **位置**：计划 50、66–69、88、96 行；`packages/neuro-book/src/plugins/agent/shared/resources.ts:44–46`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:101–125`；`packages/neuro-book/src/plugins/agent/backend/tools.ts:88–95,215–227`。
- **现象**：计划要求同一会话的 `read`、`write`、两种 `edit` 共用一份 `EditStore`，并按会话引用计数到所有工具 `dispose` 后清理。但现有 `AgentToolServices` 只有 `resources`；`AgentTools` 为每个会话每个工具分别调用 `services(context, toolId)` 并各自建实现，当前没有会话级 store、引用计数或释放回调。
- **为什么是问题**：若按现有自然接法在每个 builtin 工具工厂里 `new EditStore()`，read 产生的 hashline 头不会被 edit 看到；若用模块级 `Map<sessionId, EditStore>`，还必须处理工具集重算、绑定切换、Profile 换代、会话 fork/close 和提供方撤回，否则会泄露快照或在旧代 dispose 时删掉新代仍在用的 store。计划只写结论，没有定义所有权与时序，后续实现会在工具之间返工。
- **如何核实**：真实类型表明 `AgentToolServices` 当前无该字段；`agent.ts:103` 每次按 context/toolId 构造只有 `{resources}`；`AgentTools.create` 每个工具返回独立 `ToolWrapper`。这是当前装配路径，不是按名字推断。
- **建议改法**：把会话级 `EditStore` 放进 AgentRuntime/SessionTable 持有的 session resource bundle，由 `services(context, toolId)` 交出同一引用，并给会话关闭的明确释放点；工具 `dispose` 不直接拥有或删除它。验收必须真实走“read 输出头 → 另一个 edit 工具应用”，再测工具离开工具集后会话关闭与重开。
### 重要｜安全与性能｜shell 的原生输出回调不能 await，计划的有界边写边存没有实现路径

- **严重程度**：重要；**类别**：安全与性能、资源释放。
- **位置**：计划 69、114、127 行；`node_modules/@oh-my-pi/pi-natives/native/index.d.ts:2014–2018,3352–3370`。
- **现象**：`executeShell` 的 `onChunk` 签名是 `(error, chunk) => void`，不是 Promise 回调；计划却要每个 chunk 立即写 `SessionArtifacts` 的异步 `StagedSink.write`，同时内存只留最后 50 KB/2000 行。引擎没有在该 API 上暴露可暂停输出或异步背压参数。
- **为什么是问题**：直接在回调里启动异步写会积累未完成的 Promise/队列，磁盘慢或跨进程提交慢时内存随输出增长，重新引入第一轮已经修掉的无界累计；同步丢 chunk 则全文 artifact 不完整；等待写完又无法阻塞原生回调。取消、写失败与命令退出之间还会有并发收口竞态。计划的 64 MiB 上限只限制最终文件，不能限制写入前的队列。
- **如何核实**：类型核对已确认回调返回 `void`；同一实验 `/tmp/review-t12-design-r2/lab/native.ts` 的真实 `executeShell` 在 50 ms 超时前交付了 `yes
part
error: interrupted
`，没有任何异步 drain 合同。没有用同步假实现替代原生 API。
- **建议改法**：先定一个可证明有界的输出管道：优先使用能暂停/背压的原生入口；若没有，落到受控本地临时文件并让宿主异步提交，明确磁盘写失败时是停止命令还是返回“全文未保存”。回调错误参数必须进入结果，超时、取消、异常与 artifact finalize 只允许一次。验收用持续高速输出加慢写入，断言进程内存和最终全文边界。
### 重要｜正确性｜图片没有贯通工具结果到模型消息、过滤和现有图片合同

- **严重程度**：重要；**类别**：正确性、不变量、兼容。
- **位置**：计划 42–48、134、154 行；`packages/nb-harness/src/kernel/api/tool.ts:52–60`；`api/events.ts:168–181`；`view/format.ts:101–103`；`helpers/content.ts:72–77,107–109`；`api/model.ts:30–37`；`model/omp.ts:64–77,89–91,159–176`。
- **现象**：计划说给 `ToolResult`/`toolResult` 加 `images`，组请求时在工具文字后附图片，并把现有 `ContentBlock.image.blob` 改为 `data`。当前工具结果格式化只生成一个 text block；出站 `blocks()` 只处理含 `text` 的块；现有 `ContentBlock.image` 是会话 `blobs/` 的 SHA-256 引用；OMP 适配器对 image block 明确抛 `unsupported-content`，助手消息和回复图片也明确不收。
- **为什么是问题**：只改类型和结果事件不能使图片进入模型。`format.tool()` 仍会丢掉图片，出站过滤可能把图片原样穿透或因无 image 分支无法按“改写”规则处理，重开/压缩/预览仍按旧 blob 形状或 JSON 估算；改名还会破坏既有日志图片形状与 OMP 测试合同。计划没有列出这些实际消费点、迁移格式、旧会话兼容和“图片被 omitted 后不再附图”的流程。
- **如何核实**：逐段阅读以上真实实现；当前 `omp.test.ts` 第 187–191 行用 `image.blob` 验证不发请求，`omp.ts` 第 90、175 行验证适配器拒绝图片。无用户代码使用方不等于无内核消费点，现有测试和适配器就是消费方。
- **建议改法**：先选兼容的数据模型：保留日志 `blob` 引用，工具结果图片在格式化时从会话 blob 解析成模型块，或定义明确的 `data` 迁移/解码边界，不要直接替换公共 `ContentBlock` 字段。切片清单必须覆盖 `format.tool`、`blocks`/出站过滤、`preview` 的对齐与 token、compaction、JSONL codec、重开/fork、OMP 的 `ToolMessage` 图片映射和非 vision 降级；每个消费点有真实会话验收。
### 重要｜不变量｜artifacts 用调用 id 加 expect absent 会在重试或重复 id 时丢全文

- **严重程度**：重要；**类别**：正确性、失败恢复。
- **位置**：计划 69、78–83、127、159–160 行；`packages/nb-harness/src/kernel/api/tool.ts:36–44`；`packages/nb-harness/src/kernel/run/tools.ts:276–280`。
- **现象**：计划把全文名固定为 `<调用 id>-<工具>.log`，再用 `stage(..., {expect: "absent"})`。`ToolContext.callId` 是模型服务商给的调用 id，合同只保证同一条回复里的调用不重复；没有跨请求、重试、fork 或服务商的全局唯一保证。计划重点也要求处理“调用 id 重复、重试、一次调用多份”，但方案没有命名去重或冲突策略。
- **为什么是问题**：同一会话下一次模型请求再次产生 `call_1`，或者一个工具调用保存第二份 artifact，就会得到 `conflict`。当前 plan 又规定保存失败不影响工具结果，于是模型拿到一个声称有全文地址的结果或“全文没能保存”，而正常命令输出已经无法分页恢复。fork 还会把历史里的旧链接带进新会话，重名冲突更难诊断。
- **如何核实**：工具调用 id 的类型与注释只写“同一条回复里不重复”；`run/tools.ts` 将它原样传给 `ToolContext`，没有跨请求去重。原生/测试代码也使用不同请求重复 `call_1`，不能把 provider 示例当作全局唯一合同。
- **建议改法**：保存入口内部生成不可碰撞的单段文件名（例如 UUID），把会话、调用 id、工具名作为结果元数据而非唯一键；或由一次调用分配序号并在冲突时重试新名。`save` 交回的地址只能是实际提交成功的地址；多份全文、重试、fork 后读回都要有验收。
### 重要｜安全与性能｜项目搜索的逐文件授权把跨进程成本放进热路径且没有预算

- **严重程度**：重要；**类别**：安全与性能、接口。
- **位置**：计划 109–115 行；`packages/neuro-book/src/plugins/files/backend/workspace-files.ts:122–127`；`packages/neuro-book/src/plugins/files/backend/projects-scheme.ts:97–110`；Task README “文件访问的架构讨论”第 83 行。
- **现象**：计划规定每个文件第一次出现都把相对结果拼回全局地址，再调用一次 `readPath` 核对；对 `project://`，这就是一次 `projects.call`、一次项目租约 acquire/release 和一次跨进程 `realPath`。结果缓存只在一次搜索内按文件生效。
- **为什么是问题**：1000 个候选文件就至少 **1000 次**项目路由调用；README 已测空载 RPC p99 **1.9–2.4 ms**，仅串行授权就约 **1.9–2.4 秒**，还没算项目租约、搜索和异步队列。隐藏/受保护候选文件可以在可见结果前消耗这笔预算，30 秒期限可能返回“不完整”而不是可见结果。计划没有规定并发度、总授权预算、项目租约持有或路由失败如何区分。
- **如何核实**：真实代码中 `readPath(projects://...)` 第 125 行调用 `projects.call`，第 107 行释放租约；计划算法明确每文件第一次 `readPath`。数字取 Task README 的本机真实子进程测量，不把它当成本机直接文件读取。
- **建议改法**：让搜索在一次持有的项目租约/真实根上下文内枚举并授权，或给 Files 增加“按目录返回已授权可读子树”的批量合同；若保留逐文件核对，定义有界并发、路由调用上限和 `incomplete` 原因，验收 100、1000 个候选文件与隐藏文件占前的情况。
### 建议｜测试｜验收映射仍保留已废弃的 960 KiB 上限

- **严重程度**：建议；**类别**：测试、文档。
- **位置**：计划 154–159 行，尤其 `read` 的“超过 960 KiB 与 32 MB 的文件能分页读”和 `shell` 的“超过 1 MiB 的输出完整落盘”。
- **现象**：第三稿已明确 `readPath` 在本机分页，普通 `resources.read` 只给 edit 取 32 MB 以内字节；写入接口正文的约 960 KiB RPC 上限不再约束 read 工具或宿主 artifact。验收映射仍把“超过 960 KiB”作为 read 核心边界，shell 只测超过 1 MiB，而 artifact 合同上限是 64 MiB。

### 重要｜正确性｜shell 地址结束条件会吞掉管道、分号和重定向

- **建议改法**：保持原生英文错误段原样，在 text 追加宿主生成的逐文件摘要（全局地址、已提交/失败/结果未知、稳定 code）；details 保存同一份结构化状态。明确保留原文只约束错误段，不禁止说明副作用。验收从下一次模型请求里的 tool 消息断言 A 已提交、B 失败都可见，不能只检查 details。

### 重要｜正确性｜grep 不会按计划为非法正则交 invalid-pattern

- **严重程度**：重要；**类别**：正确性、接口与合同。
- **位置**：计划 70、111、158 行；`node_modules/@oh-my-pi/pi-natives/native/index.d.ts:2228–2299,3300–3346`。
- **现象**：本稿定义 grep 的 pattern 是正则、非法时为 `invalid-pattern`，又把正则执行完整交给 pi-natives，没有验证/错误映射步骤。当前公开 native grep 对非法模式会退回能匹配的字面/其它引擎语义，根本不抛一个可映射的非法正则错误。
- **为什么是问题**：模型写错 `[`、`(` 或未闭合字符类时，会得到“没有匹配”或字面匹配，而不是能修正输入的失败。验收里的“非法正则”照自然接法过不了；照 omp 参照按错误文案正则捕获也救不了本版本根本不报错的输入，而且违反本稿不按英文文字分支的规则。
- **如何核实**：`bun --no-install --no-env-file /tmp/review-t12-design-r2/lab/search-errors.ts`：在 **1500** 个普通文件上 `pattern: "["` 成功交 0 匹配、`filesSearched:1500`；`regex.ts` 在包含单独 `[`、`(`、反斜杠的文件上，同样三个非法模式分别成功命中对应字面行；`[a-` 返回成功 0 匹配。`search("",{pattern})` 也没有 error，不能拿它预编译查错。缺文件和非法 glob 都是 `GenericFailure`，不能据其 code 区分非法正则。
- **建议改法**：明确 grep 的正则语言并在搜索前用同一语法的编译入口校验；优先让 pi-natives 提供结构化 compile/validate 结果。若接受原生的容错字面搜索，就改合同和验收，取消 `invalid-pattern` 承诺并向模型说明回退；不要用 JavaScript RegExp 预检去误拒 Rust/PCRE 能支持的模式（实验中的 `(?i)` 与 lookahead 都能搜）。
