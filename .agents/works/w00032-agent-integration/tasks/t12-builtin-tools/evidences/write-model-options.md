# 三个写入与记账方案（供比较）

## 背景

NeuroBook 是本地优先的长篇写作工作区（Bun 1.4、TypeScript；仓库 `/home/notnotype/CodeRepository/neuro-book`，只读参照）。一本书是用户磁盘上的一个目录（项目目录）。进程：

- **服务端进程**：Agent（AI 写作助手）在这里运行，它的工具要读写书里的文件；以后的插件（例如图生文插件存图片）也在这里。
- **项目子进程**：每本打开的书一个。现在由它执行浏览器编辑器的保存与文件树的文件操作，也由它监视项目目录（`node:fs.watch` 递归监视、批合并、回声过滤，见 `packages/neuro-book/src/plugins/files/backend/changes.ts`），把变更事件推给浏览器的文件树与编辑器（要实时）。
- 服务端与项目子进程之间是本机 IPC，实测一次空载荷往返 p50 约 0.3 ms、p99 约 2 ms；一条 RPC 消息上限 1 MiB、不传二进制。

外部工具（Agent 的 `shell` 里的 `sed -i`、`>>`、`cp`，用户用的别的编辑器，`git checkout`）会直接改书里的文件，管不了。

要做的“记账”：记下谁（用户经网页、某个 Agent 会话、某个插件、外部）改了哪个文件、改成什么，支撑时间线、diff（文本按行；二进制只记“已更改”加前后哈希与大小）、恢复旧版本、误删找回、审查收件箱（用户看 Agent 改了什么、接受或还原）。账本用现有的 `packages/nb-history`（SQLite：事件日志 + 按内容寻址的快照；有 `performWrite`、`registerWrite`、`registerObservedWrite`、`reconcile` 等，见它的 `README.md`），项目的账本放项目的 `.nbook/history.sqlite`，由项目子进程独占写。

已定的约束：

- 不再让一个服务“劫持”所有文件访问（做不到，外部工具会直接写）；
- 读：服务端的使用方拿到文件的本机绝对路径后自己读（分页、字节、原生搜索都行），读不记账；
- 账本是软依赖：账本出故障时文件读写照常，只是丢了操作者并写诊断（已接受的设计里承诺过“History 失败时文件功能照常”）；
- Agent 用 `shell` 改的文件：命令执行期间这个会话的根里观察到的外部改动，记为该会话并标“推断（shell）”；
- 写文件时要在锁里得到确定的改动（开发者在意“算出来的改动和真实发生的一致”）；
- 开发者担心磁盘读写负担，也希望设计简单、不按场景分好几种写法。

## 方案 A：写入方自己写盘，先改名、后记账

以服务端的 Agent 改 `project://第三章.md` 为例：

1. 写入方（服务端）取这个文件的跨进程锁（现有 `packages/neuro-book/src/backend/locked-replace.ts`）；
2. 读出改前值，写同目录的临时文件，算出改动（按行 diff）；
3. 改名替换目标文件（原子替换）；
4. 把记录（操作者、路径、前后哈希、改动，不带整份内容）经 RPC 交给项目子进程的账本，等确认；账本要存快照时自己读磁盘上的文件（锁还在写入方手里，读到的一定是这一版）；
5. 放锁；
6. 项目子进程的文件监视看到变化：这个文件的锁还被持着时先不判定，等锁放了再判；对上记录就当回声吸收，对不上记为外部。

意外：第 3 步失败则什么都没变；第 3、4 步之间写入方崩溃，锁过期后监视按外部记；账本故障则写入照样完成、记一条诊断。

## 方案 B：写入方只写临时文件，由拥有根的进程提交

1. 写入方用定位拿到目标位置，在同目录写临时文件（可以流式、任意大小、不持锁）；
2. 写入方调一次“提交”（参数只有临时文件路径、目标地址、基线、操作者，几百字节），项目文件经 RPC 交给项目子进程，`user://` 等在服务端本进程内；
3. 拥有根的进程在自己的锁里：核对基线 → 读改前值 → 算改动 → 改名替换 → 记账 → 登记回声并以真实来源发事件。

写盘、账本、监视都在一个进程里；浏览器的保存路径不变；结果不确定时写入方比对目标的当前哈希即可知是否提交。

## 方案 C：照 git，账本存“当前值”，记账就是一次提交（开发者提出）

1. 账本为每个文件存“当前值”（上一次记账时的内容快照，相当于 `.git` 的对象）；
2. **所有改动走同一条记账路径**：文件监视看到某个文件变了，账本读出它现在的内容，与存着的当前值比，算出改动、记一条、把新内容存为当前值——这就是一次提交；经接口写的与外部改的一视同仁；
3. 经接口写的，写之前先“认领”：告诉账本“我是 Agent 会话 s1，要把这个文件写成哈希 H”（几十字节，项目文件经一次 RPC）；账本提交时新内容的哈希对上认领就记为 s1，对不上记为外部；认领只是意图，不是版本，写失败或写的人崩溃都不留假版本，到期作废；
4. 写入方不在锁里读改前值、算改动，也不把内容交给账本；改动一律由账本在提交时算；
5. 写入方怎么写文件不限定（整份写、就地改、追加），开发者倾向不按场景分写法；就地写在写到一半时可能被监视或别的读者读到半截内容，这是 C 要回答的问题之一；
6. 连续保存可以合并成一个版本（例如同一文件 30 秒内的连续保存只记一个），快照用 zstd 压缩、内容相同不重复存、大文件不存快照、按保留策略稀疏化。

## 要比较的维度

正确性（改动与归属是否与真实发生的一致：并发写、写到一半被读、崩溃、账本故障、外部改动）；磁盘读写负担（每次保存的读写字节、快照）；实时性（浏览器文件树与编辑器多快看到变化、来源是否正确）；跨进程（服务端写项目文件、浏览器保存、两个服务端打开同一本书）；简单程度（写入方要做的事、要维护的状态、要写的代码）；与现有代码的契合（`changes.ts`、`rooted.ts`、`locked-replace.ts`、nb-history）。
