# 写入与记账方案评估（侧重：简单与负担）

评估者 r3。环境：Linux 7.2.11，btrfs，NVMe，8 核，Bun 1.4.4；`nb-history` 用仓库里的真实代码（libsql）。语料：仓库 docs 里的中文文档，以及 `.local/novels` 下一部真实中文小说（只读）。实验脚本与输出都在 `/tmp/review-write-models/r3/`。

## 结论

**推荐 B，并从 C 借三样东西：外部改动仍由监视事后观察入账、暂存目录放进 `.nbook/staging/`、快照可选 zstd。** 一句话理由：B 是三案里唯一让“写盘、记账、回声、事件”在同一个进程、同一把锁里完成的，写入方只剩“写暂存文件 + 一次几百字节的提交”这一种写法，不需要 A 的跨进程锁与回声判定时序，也不需要 C 的认领、合并、静默检测等一批新状态；磁盘字节与耗时三案几乎相同（见下表），所以负担不是选择依据，简单程度与正确性才是。

具体机制（改良后的 B）：

1. 写入方（服务端的 Agent 工具、插件）统一调一个函数 `files.write(target, source, {baseline, actor})`：它向拥有根的进程要一个暂存路径（放在 `<根>/.nbook/staging/<uuid>`，同文件系统，控制目录本来就被监视忽略，所以 `changes.ts` 里为临时文件做的“随机标记正则”在这条路径上用不到）、把内容写进去（可流式、任意大小）、再提交。小文本、图片同一条路径，不分场景。
2. 提交 RPC 的参数只有暂存路径、目标地址、基线哈希、操作者，约 200 字节，一次往返 p50 约 0.3 ms。
3. 拥有根的进程用现有的 `replaceLocked` 取锁、核对基线、读改前值、改名替换、`registerWrite(actor, path, before, after)` 记账、`changes.saved()` 登记回声并立即以真实来源发事件。基线不符返回“已过期”，调用方（编辑类工具）重读后重试，次数上限沿用 `replaceLocked` 现有的 3 次。
4. 浏览器保存、文件树操作本来就在这个进程里，走同一个内部函数，不变。
5. 外部改动（`shell` 里的 `sed -i`、别的编辑器、`git checkout`）：监视判为外部后，对文本文件读一次内容，交给 `reconcile` 或 `registerObservedWrite`。这就是 C 里“账本存当前值、监视看到变了就提交”的那一半，且 nb-history 已经有（`implicitReconcile` 对账末态）；它只用于确实看不到的写入，不负责接口写入。`shell` 的归属推断在这里按“命令期间、该会话的根里观察到的外部改动”处理。

## 逐项比较

### 1. 磁盘读写负担（实测，E3、E2、E4、E5）

真实 `WorkspaceHistory`（libsql，WAL），连续保存同一章的相邻版本，每次包含：持锁读改前值、写临时文件并 fsync、改名、记账、回声核对一次读。“实际落盘”取 `/proc/self/io` 的 `write_bytes`，每次平均：

| 章节大小 | 方案 | 读 KB | 写 KB（syscall） | 实际落盘 KB | 每次耗时 ms |
|---|---|---|---|---|---|
| 15 KB | 仅写盘（基线，无账本） | 15 | 15 | 101 | 0.9 |
| 15 KB | A（写入方交 before+after，账本自己再读盘） | 86 | 40 | 137 | 9.2 |
| 15 KB | B（账本在同进程，持有字节） | 71 | 40 | 188 | 3.7 |
| 15 KB | C（监视读一次，`reconcile` 补条目） | 71 | 40 | 195 | 3.1 |
| 154 KB | 仅写盘 | 150 | 150 | 235 | 1.0 |
| 154 KB | A | 486 | 175 | 325 | 3.4 |
| 154 KB | B | 335 | 175 | 332 | 3.8 |
| 154 KB | C | 335 | 175 | 326 | 3.0 |

读法：

- 账本的固定开销约每次保存多落盘 100 KB（SQLite 页放大加 WAL 与检查点），与章节大小关系不大；绝对耗时 3 到 4 ms，A 在小章节上那次 9 ms 我推断是首次预热（A 是每组里第一个跑的，未单独验证），不能当作稳定差异（应由读者复测，见 E3 命令）。
- 三案的字节差别在一个 N（章节大小）以内：A 比 B 多一次“账本读盘取快照”，约多 1N 读；B 与 C 在这里几乎相同，因为我的 C 模拟里 `reconcile` 与 B 的 `registerWrite` 做的事相近。**C 的真实额外成本不在单次保存，在下面两项。**
- 单次保存本身对人类写作节奏（每几秒一次）微不足道；对 Agent 一次写几百个文件，约 3 ms 一个，也只有秒级。

C 的额外成本（这是 C 才有的）：

- 失同步或外部批量改动（`git checkout`、`changes.ts` 的 `MAX_BATCH_PATHS`=1000 溢出推 `resync`、重启补账）后，账本要逐个核对“当前值”，只能读内容算哈希。实验 E4（450 个文件、333 MB 的书，热缓存）：只 `stat` 2 ms；全部读加哈希 755 ms；只读文本（18 MB）33 ms。冷缓存会更慢（要从盘读 333 MB）。要避免就得规定“大文件/二进制只比大小与修改时间”，又多一套规则。B 同样有这个批量场景（外部批量改动），但只对文本做 `reconcile`、二进制只记哈希；C 把它当成“所有写入的常态路径”，A 与 B 里它只是兜底。
- 就地追加写的大文件（下载、导出、插件流式生成）：E5 用 100 MB 文件追加写约 10 s，监视每批 75 ms 读全文核对，共 59 批，累计读加哈希 2893 MB，占 CPU 约 63%，并产生 59 个“版本”。C 若不加“静默期”（文件大小与时间稳定后再提交）就会这样；加了静默期，就是 C 多出来的一块状态。A、B 的接口写入是整份改名替换，监视看到的永远是完整文件；外部的就地追加在 B 里也会遇到同样问题，但只发生在“外部工具写大文件”，并且用 `size > maxSnapshotBytes`（nb-history 默认 2 MB）就能直接跳过读内容，只记一条“已更改”。

快照体积（E2，真实中文小说，zstd3）：30 KB 压成约 61%，100 KB 约 54%，300 KB 约 50%，整本 730 KB 约 48%；文档类文本（汉字占比 35%）约 47%。**只能省一半，不是数量级**。100 个相邻小改版本（每版 40 KB）：全文存 4.12 MB，zstd3 存 2.07 MB，每次保存 1.5 ms 对 3.2 ms。所以：

- zstd 值得做（解压 0.2 到 1.6 ms，压缩 1 到 5 ms），但属于账本内部的存储细节，与 A/B/C 选择无关；C 把它和“合并 30 秒内的连续保存”捆在一起，合并是不必要的，也不该是前提：100 版 4 MB 的量级，用 nb-history 现有的 `prune` 稀疏化即可。合并还会带来 C 独有的副作用：Agent 与用户在 30 秒内交替改同一个文件，归属会被抹成一条。
- `nb-history` 的 `putSnapshot` 对 `before` 也会绑定整份内容再靠 `ON CONFLICT DO NOTHING` 去重：`registerWrite(before, after)` 每次多一次 N 字节的哈希与绑定。实测影响小于 1 ms（15 KB：只传 after 的 `registerObservedWrite` 2.84 ms 对 `registerWrite(before, after)` 3.69 ms；154 KB：3.44 对 3.82 ms），不必为此改接口。

### 2. 实时性（E1）

- Bun 递归 `fs.watch` 从写入完成到回调收到事件：改名替换 90 KB p50 0.03 ms、p99 0.76 ms；就地写 p50 0.02 ms、p99 1.96 ms。事件本身不是瓶颈，瓶颈是 `changes.ts` 的 `BATCH_DELAY_MS = 75`。
- B：经提交的写入由 `saved()` 立即发事件，延迟 = 一次 RPC（约 0.3 ms）加落盘，来源是真实的，与浏览器保存现有路径完全一致。
- A：服务端写完后记账 RPC 才到拥有监视的进程，事件可以在这次 RPC 里发，但回声要等锁放掉，监视那边还得查“这个文件的锁是否还被持着”，延迟相同量级，多一份时序。
- C：事件来自监视，至少 75 ms 批延迟，再加读文件与账本提交；而事件上的“来源”要等账本匹配认领之后才知道，所以经接口写入的实时性比 B 差 75 ms 以上，且来源有出错可能（下一节）。对写作场景 75 ms 可以接受，但“Agent 改一行，编辑器立刻刷新并标明是谁”这个体验 B 更直接。

### 3. 正确性（侧重与负担相关的部分）

- 写到一半被读：E1 实测，就地写 6 MB 文件，写入方在块间让出事件循环时，80 个监视回调里有 75 个读到的是半截内容（含 0 字节的截断态）。A、B 都是改名替换，监视与读者永远只看到完整文件。C 允许“就地写”，就把这个问题变成必须回答的：监视读到半截，会记一个假版本，随后第二个事件再记真版本；认领按最终哈希匹配时，半截版本会被记成“外部”。要缓解就得有静默期。这与“开发者倾向不按场景分写法”相冲突：C 看似放开写法，其实把约束从写入方转给了账本，而且账本侧才是代码最复杂的地方。
- 连续写与归属：`changes.ts` 里 `pending` 是 `Set<string>`，一批 75 ms 内同一路径只判一次。C 在 75 ms 内连续两次写同一文件（Agent 连改两行，或 Agent 与用户的保存挨着），账本只看到最终内容，第一个认领无处匹配，最终的 diff 全记在最后一个认领的操作者名下。B 的提交在锁里串行，每次一条记录，before/after 是精确的。
- 崩溃：A 在改名后、记账前崩溃，监视判“外部”，Agent 的写入被误记成外部（A 文本里已承认）。B 在拥有根的进程里“改名后立刻记账”，两步之间崩溃的窗口还在，但只丢操作者，且下一次任何写入的 `implicitReconcile` 会补 `external` 条目，链仍精确；B 比 A 多一个好处：不存在“写入方持锁时去 RPC 等一个可能已卡死的子进程、锁 10 秒过期被别人接管”这类跨进程持锁（`locked-replace.ts` 的 `LOCK_STALE_MS`=10 s）。
- 账本故障：B 与 A 一样，`registerWrite` 失败写诊断，写盘已完成不回滚；C 在“账本即检测器”的结构里故障意味着丢失全部归属，但文件功能也照常。
- 两个服务端同开一本书：三案都靠 `replaceLocked` 的跨进程锁保证文件不互相覆盖，但账本都碰到同一个问题（见最后一节）。

### 4. 简单程度与契合现有代码

写入方要做的事（插件作者视角）：

| | A | B | C |
|---|---|---|---|
| 要调用 | 取锁、读改前、写临时、算 diff、改名、记账 RPC、放锁（可封装成一个函数，但函数在服务端，要有根的路径解析与符号链接安全检查的第二份实现） | `write(target, source, baseline)` 一个函数；内部为“要暂存路径、写入、提交”三步 | 认领 RPC + 任意方式写；还要自己保证写完整（否则会被读到半截） |
| 写入方的状态 | 持锁期间的 RPC、崩溃窗口 | 无，暂存文件崩溃后残留由拥有根的进程启动时清扫 | 认领的到期 |
| 写法数量 | 浏览器在子进程一条、Agent 在服务端一条（两条写路径） | 一条 | 一条（任意写）+ 一条（监视提交） |

要维护的状态与新增代码：

- A：回声“等锁放掉再判”（`changes.ts` 要为每个事件多查一次锁目录是否存在，并为“锁过期、写入方崩溃”写兜底）；服务端要有一份能读写项目根的 Rooted 逻辑。`changes.ts` 现有的 `expect`/`saved` 机制保留。
- B：几乎全部复用。`replaceLocked` 现在由 `decide` 返回要写的字节、自己写临时文件；B 需要它支持“采用外部暂存文件”：把 `decide` 的结果改为可选 `{adopt: 暂存路径}`，在持锁、核对身份之后做改名；约 20 到 40 行。`rooted.ts` 的 `replace` 已有锁路径与权限位处理，`changes.saved` 已有登记回声与立即发事件。新增代码主要是：提交 RPC、暂存目录的创建与启动清扫、基线检查、账本调用。
- C：新增状态最多：认领表（带到期）、静默期（防半截与大文件抖动）、合并窗口、“当前值”的存取、失同步后的全量核对、大文件策略。`changes.ts` 的“回声登记”整块（`expect`、hash/entry/absent 三种登记、60 秒到期）本来是为“自己写的不要当外部”设计的，C 里这件事变成“认领匹配”，但又不能删掉（目录操作的回声仍要它），于是两套匹配机制并存。nb-history 的 `registerWrite` 路径在 C 里基本不用，改用 `reconcile`；它的 `implicitReconcile` 已经是 C 的核心，所以 C 并没有省下账本侧代码。

与 nb-history：它的“宿主集成义务”是“把全部写入路径接到 `perform*`/`register*`（带 actor），把 watcher 事件喂给 `reconcile`”。这正是 B 的结构（接口写 `registerWrite`，外部写 `reconcile`），不需要改库。

### 5. 数字汇总

| 维度 | A | B | C |
|---|---|---|---|
| 单次保存耗时（15 到 154 KB） | 3 到 9 ms | 3.7 到 3.8 ms | 3.0 ms（加静默期则 +75 ms 起） |
| 单次保存落盘（含 SQLite 放大） | 约 137 到 325 KB | 约 188 到 332 KB | 约 195 到 326 KB |

环境同上。命令都在 `/tmp/review-write-models/r3/` 下执行，用 Bun，不安装依赖；E3 通过绝对路径导入仓库 `packages/nb-history/src/index.ts`（只读）。

| 实验 | 命令 | 内容 | 结果 |
|---|---|---|---|
| E1 | `bun e1-watch-latency.ts` | Bun 递归 `fs.watch` 事件延迟；就地写时回调读到半截的比例 | 事件 p50 0.02–0.03 ms、p99 0.8–2 ms；6 MB 就地慢写 80 回调中 75 个读到半截 |
| E2 | `bun e2-compress.ts` | 仓库中文文档：zstd 各级别、gzip；100 版库体积 | 30 KB 文档 zstd3 46.6%；100 版 4.12 MB 对 2.07 MB |
| E2b | `bun e2b-novel.ts` | 真实小说的压缩比 | zstd3：30 KB 61%、100 KB 54%、300 KB 50%、730 KB 48%；zstd19 约 40 到 53% |
| E3 | `bun e3-save-cost.ts` | 真实 nb-history，A/B/C/A'/仅写盘 的读写字节与耗时，15 KB 与 154 KB 两档 | 见上表 |
| E4 | `bun e4-scan.ts` | 450 文件 333 MB 书的全量核对成本 | stat 2.2 ms；读加哈希 755 ms；仅文本 33 ms |
| E5 | `bun e5-growing.ts` | C 模式下监视每批读全文，核对一个被追加 100 MB 的文件 | 59 批、2893 MB、63% CPU、59 个“版本” |

说明与限制：

- E3 的 A、B、C 是我用 nb-history 现有接口按方案文字拼出的近似（A：`registerWrite` 加一次盘读；B：`registerWrite` 持有字节；C：`reconcile`），没有写出三个方案的完整实现，也没有跨进程 RPC（那一项用方案文字里的 0.3 ms 数字）。所以 E3 能说明“字节与耗时量级相同”，不能说明各方案的正确性。
- E3 的章节大小标称 30 KB 与 300 KB，实际按字符切片，成品是 15 KB 与 154 KB。
- 耗时是单机热缓存数字，磁盘为 NVMe + btrfs；机械盘或网络盘上 fsync 与 SQLite 页写会明显更慢，需要重测。
- E4 是热缓存；E1 的“事件延迟”是同进程写、同进程收，跨进程写入的 inotify 延迟没有单独测，量级预期相同（内核同一条路径）。
- 小说压缩比用单部作品（约 73 万字节）做样本。

## 三个方案都没解决的问题

1. **同一本书两个服务端、两个项目子进程，各自写 `.nbook/history.sqlite`**：nb-history 的限制 1 写明“单进程单写者、多进程同时打开不支持”，它的写互斥和 `implicitReconcile` 的账面末态都是进程内的。文件写由 `replaceLocked` 的跨进程锁保护，账本没有。需要决定：禁止同一本书被两个服务端同时写账本（只读打开、或用锁文件选出一个账本主）、或把账本锁也做成 SQLite 层面的跨进程事务。
2. **改名、移动、删除目录的记账**：`registerRename` 是单文件；移动含 500 个文件的目录，是 500 条记录还是一条“目录移动”记录，没人定。`changes.ts` 的 `moved` 回声登记有 `MAX_BATCH_PATHS` 溢出后推 `resync` 的退化路径，账本对应的退化也要定。
3. **范围外的路径**：`.git/`、`node_modules`、编辑器交换文件、`.nbook/` 本身。nb-history 说“哪些文件值得记录由宿主调用侧决定”，三案都没有写这份过滤规则，而它决定外部批量改动时的读量（E4）。
4. **首次接入已有的书**：账本里没有任何末态，第一次保存触发 `implicitReconcile` 会补一条 `create`/`external`；要让“恢复到最初版本”可用，需要一次性对所有文本文件拍基线，读整本文本（18 MB 约 33 ms 热缓存，冷缓存更久）。谁做、何时做，没人定。
5. **外部写入的归属是推断**：`shell` 期间根里观察到的改动记为该会话，若用户同时在别的编辑器改另一处，会被误记；并发的两个 Agent 会话各自的 `shell` 也会互相被误记。三案同样，B 只能保证接口写入的归属是精确的。
6. **外部就地写的半截内容**：外部编辑器、`cp`、下载在监视看到时可能没写完，无论哪个方案，监视侧入账都需要静默期或大小上限，否则会产生假版本（E1、E5）。
7. **账本无增量压缩**：nb-history 是全文快照，zstd 只能省一半；中长篇每天几十次保存、一年后体积需要靠 `prune` 稀疏化加“未审收件箱不清理”之间的取舍（nb-history 限制 4），这与方案无关，但是账本增长的主因。
8. **用户在审查收件箱里“还原”要写文件**：还原本身也是写入，必须走同一条提交路径（B 里自然成立，A 里要服务端也参与，C 里要认领）。三案没讲还原与进行中的 Agent 写入的冲突如何提示。
