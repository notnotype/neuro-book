# 写入与记账三方案评估（r1）

## 结论

推荐 **方案 B（拥有根的进程提交）**，并在它上面补两样取自 C 的东西，作为改良组合：

- 经接口的写入：写入方写同目录临时文件（流式、不持锁），一次几百字节的“提交”交给拥有根的进程；拥有根的进程在文件锁里核对基线、读改前值、改名、记账、以真实来源发事件。
- 其余一切改动（shell、外部编辑器、git checkout、账本故障期间的写入、启动时发现的离线改动）走观察路径：监视报来、用账本存的“上一版”加 stat 缓存对账、记为外部。这条路径就是 C 的账本语义（nb-history 的 `reconcile` / `registerObservedWrite` 已有）。C 的 30 秒同操作者合并、zstd 快照、启动扫描也要，但只作账本内部策略，不作为写入的记账路径。

一句话理由：只有 B 在锁里拿到“真实的改前字节”并让写盘、记账、发事件在同一个进程里按序完成，所以并发写、外部改动夹在中间、崩溃这三种时序下改动和归属都与真实发生的一致；A 缺改前快照且要在跨进程锁里挂一次 RPC，C 在写入合并与半截读上无法保证一致，而且让“Agent 写了什么”依赖文件监视是否完整。

另有一个附带发现：`docs/proposals/file-access-and-history.md`（draft）里“记录在改名之前送达，失败时撤回”与账本 append-only 冲突，B 的顺序（改名成功后在同一进程里记账）不需要撤回。

## 逐维度比较

评级只用“好 / 可 / 差”，依据见下面每项的机制分析。

| 维度 | A 写入方自写、先改名后记账 | B 写临时文件、拥有根的进程提交 | C 账本存当前值、统一由监视提交 |
|---|---|---|---|
| 正确性：并发写 | 好（同一把锁串行，记录按锁序到达） | 好（同上，且锁只在提交时持有） | 差（75 ms 或合并窗口内两次写只剩一个版本，归属给最后一个） |
| 正确性：写到一半被读 | 好（改名原子） | 好（同上） | 差（就地写；监视与其他读者都可能读到半截；流式写必现） |
| 正确性：改前值真实 | 可（写入方锁内读到，但账本拿不到字节；账面缺这一版时丢快照） | 好（拥有根的进程手里有改前字节与改后文件） | 差（改前值是账面旧值，外部改动夹在中间会被吞进写入者的 diff） |
| 正确性：崩溃 | 可（改名到记账之间崩溃，锁到期后按外部记，内容对、归属丢） | 好（窗口只剩同进程内一次 SQLite 提交，recover 同 A） | 可（认领作废不留假版本；但就地写崩溃会留下 0 字节或半截文件） |
| 正确性：账本故障 | 好（但 RPC 超时后迟到的记录会造成重复条目，需幂等键） | 好（同进程，try/catch 一处） | 可（写入照常，补不回归属，靠启动扫描自愈） |
| 正确性：外部改动 | 同 | 同 | 同（三者都靠观察路径；C 的“统一”只是把写入也塞进这条路径） |
| 磁盘读写 | 读约 2N 到 3N，写 N 加快照 | 读约 2N，写 N 加快照；大二进制由写入方给哈希，可零读 | 读 N 加解压旧值；但每次事件都要整读整哈希，大文件与增长中的日志反复读 |
| 实时性 | 好（记录到达后立即发带来源的事件，约 3 到 5 ms） | 好（同） | 可（监视批合并 75 ms 起，再加读与哈希；大文件再加 40 ms 每 20 MB） |
| 跨进程：服务端写项目文件 | 差（跨进程锁里挂一次 RPC；账本慢则锁被占） | 好（一次 RPC，不持跨进程锁等别人） | 可（认领一次 RPC，之后全靠监视） |
| 跨进程：浏览器保存 | 不变 | 不变，且与服务端写入走同一段提交代码 | 也要改成认领加监视 |
| 跨进程：两个服务端同一本书 | 好（同一把文件锁排序） | 好（同） | 差（两边监视各自提交，需要库里的幂等提交与库里的认领表） |
| 简单程度：写入方 | 中（锁、读、写、记账 RPC、放锁、重试） | 低（写临时文件加一次提交） | 最低（认领加随便怎么写） |
| 简单程度：拥有者与状态 | 中（锁内等待规则、监视要看锁目录） | 低（复用现有保存路径） | 高（认领表与 TTL、流式写的开始与结束、静默判定、合并窗口、全量基线） |
| 与现有代码契合 | 可（要改 `changes.ts` 去看锁目录；服务端要会算锁路径） | 好（`files-service.write` 已有 `temporaryPath` 参数，`changes.saved` 已是“真实来源立即发事件”，`replaceLocked` 只需多一种“收养临时文件”） | 差（要替换 `changes.ts` 的整套回声登记，`matches()` 的读文件加哈希变成主路径） |

### 关键机制与时序

**1. 并发写与归属（C 的硬伤）。**
t0 文件为 v0；t0+10 ms 用户经网页保存 v1；t0+40 ms Agent 会话 s1 写 v2；监视在 t0+75 ms 批合并后读到 v2。C 在这里只看到一个新哈希 v2，对上 s1 的认领，记为“s1：v0 到 v2”。用户的 v1 不存在于账本，收件箱“还原 Agent 的修改”会还原到 v0，把用户的修改一起抹掉。A、B 在各自的锁里各读一次真实的改前字节，得到两条记录（用户 v0 到 v1，s1 v1 到 v2）。

更常见的夹法是外部改动：`sed -i` 在 t0 把文件改成 v_ext，监视批还没触发，t0+10 ms Agent 写 v2。C 的账面当前值还是 v0，结果同上，外部修改被算进 Agent 头上。B 在锁里读到磁盘上的 v_ext，账本发现它不是账面末态，先补一条外部（v0 到 v_ext，快照用 B 手里的字节），再记 s1（v_ext 到 v2）。A 的写入方也读到了 v_ext，但账本在改名之后才被通知，拿不到 v_ext 的字节：它只能记 before 哈希，快照缺失，diff 无法展示。要补，A 就得改成“先 prepare 再改名再 commit”两段，即变成 B。

**2. 写到一半被读（C 的第二个硬伤）。**
就地写不是原子的：先截断再写。实验 3 与 2 的数字见后。读者包括监视的批处理、Agent 的 `read`、浏览器的 HTML 预览字节路由、作品统计订阅者，没有一个知道写入方在写。C 里半截内容会被监视当成一个新版本提交，记为外部（与认领不符）；随后完整内容到达，对上认领，记为 s1，但它的“改前值”是那份半截的外部版本，于是收件箱里 Agent 的 diff 只剩尾巴，另有一条不存在的外部修改。A、B 用同目录临时文件加改名，读者看到的只有旧的完整版本或新的完整版本。C 要修这个，就得给认领加“开始/结束”两段，或等文件静默，前者回到锁，后者对慢速流式写仍无保证。

**3. 崩溃。**
A：改名后、记账 RPC 返回前崩溃，锁目录不再刷新，监视要等锁到期（`LOCK_STALE_MS` 10 s）才敢判定，然后记为外部，内容对、归属丢，窗口约一次 RPC 往返加账本提交（几毫秒）。B：改名和记账在同一进程，同一个窗口只剩一次 SQLite 提交，进程死则两者一起死，同样按外部补。C：认领不留假版本是对的，但就地写在 `O_TRUNC` 之后崩溃会留下 0 字节文件，磁盘上旧版本已没了，只有账本里的“当前值”能恢复，这对作品文件是不可接受的失败方式。

**4. 账本故障。**
三者都能让文件读写照常。A 的特殊问题：记账 RPC 超时放弃后，项目子进程里的账本可能其实已经提交，迟到的记录或写入方的重试会产生重复条目，需要以 (路径, 前哈希, 后哈希) 作幂等键；监视同时会在锁放掉后看到变化，如果这时账面还没记录就先记一条外部，随后到达的 s1 记录因“与账面末态一致”被 `registerObservedWrite` 吸收为回声，归属永久丢失。B 里账本与提交者同进程，没有这类分歧。

**5. 实时性。**
实验 7 显示 Bun 的递归 `fs.watch` 在写入完成后约 0 到 3 ms 就回调，75 ms 是 `changes.ts` 的 `BATCH_DELAY_MS`。A、B 在记账成功后直接以真实来源发事件（照 `changes.saved`），浏览器约 3 到 5 ms 看到；C 的事件要等监视批、读文件、对账，约 75 ms 加读哈希时间（20 MB 约 40 ms）。人眼上 75 ms 可接受，所以实时性不是决定因素，但来源正确性在 C 里依赖认领先于批到达。

**6. 磁盘读写（N 为文件大小，文本快照 zstd 约 0.6N）。**
- 字节量：三种写法写盘的字节都是 N（临时文件与就地写一样），区别是 `tmp+fsync+rename` 多 1 到 2 ms 延迟，不多写字节。开发者担心的读写负担，不是在这三条之间区分。
- A：写入方读旧 N，写临时 N，账本读改名后的文件取快照 N，监视回声核对再读 N（可改用 inode 身份核对避免）；SQLite 写 0.6N 加 WAL。
- B：拥有者读旧 N、读临时文件 N（取快照），回声用 inode 身份登记（`changes.ts` 已有 `entry` 类登记），不再读。大二进制不存快照时，写入方边写边算哈希随提交带上，拥有者连临时文件都不用读。
- C：监视读新 N、哈希、解压旧值算 diff。大二进制与增长中的日志：每个监视批都要整读整哈希，因为就地写时别人没有哈希可信；stat 缓存只能挡“没变”，挡不了“在变”。
- 30 KB 文本级别三者都不到 1 ms 量级，差异只有在大文件上才有意义（实验 5）。

**7. 跨进程。**
- 服务端写项目文件：A 把跨进程文件锁（proper-lockfile，10 s 不刷新即残留）的持有时间与另一个进程（项目子进程）的响应时间绑在一起；项目子进程忙于哈希大文件或 SQLite 等锁时，写入方的锁一直占着，浏览器同一文件的保存等 3 秒后 `locked` 失败。B 里写入方不持锁，锁只在拥有者里持有几毫秒。
- 两个服务端同一本书（每个服务端各有一个项目子进程，共享同一份 `history.sqlite`）：A、B 靠同一把文件锁排序，且“账面末态等于文件哈希”这一条判定放在共享的 SQLite 里，两边监视对对方的写入天然当回声吸收。C 的认领若放内存，另一个服务端的监视先看到变化，就记为外部；放库里则每次保存多一次 SQLite 写事务，两边监视同时提交还需要幂等事务。

**8. 简单程度。**
C 对写入方最省事，但把复杂度全推到“拥有者的启发式”上：认领 TTL、开始与结束、静默判定、合并窗口按操作者拆分、全量基线。这些没有一个能用确定的不变量证明正确，只能靠实验调参数。B 对写入方多一个“临时文件 + 提交”，但拥有者那一段几乎就是现有的保存路径。A 的额外状态是“监视看锁目录再决定是否判定”，这是两个进程之间的隐式协议。

## 实验与数字

环境：Linux 7.2.11，Bun 1.4.4，8 核，/tmp 为 btrfs（NVMe），空闲内存很紧（约 1.7 GB 可用），所以大文件只到 100 MB；各数字为单机几次到几十次重复，不是基准测试。脚本与原始输出都在 `/tmp/review-write-models/r1/exp/` 和 `/tmp/review-write-models/r1/results-*.txt`。运行方式均为 `cd /tmp/review-write-models/r1 && bun exp/<脚本>.ts <参数>`。

**实验 1：同进程写会阻塞事件循环（作废的第一版）。** `exp/watch1.ts`。写入方与监视在同一进程时，同步写期间回调被推迟到写完，数字不能说明监视行为；改成独立写入进程（实验 2）。

**实验 2：递归 `fs.watch` 在就地写与临时文件加改名时的事件数与批后读到的内容。** `exp/watch2.ts`、`exp/writer.ts`。每组 10 次，监视按现有 `changes.ts` 的 75 ms 批合并后读文件并核对哈希；`.tmp` 名的事件已按 `temporaryPattern` 滤掉。输出见 `results-watch2.txt`。

| 写法 | 每次写的事件数 | 每次写的批数 | 半截读次数（10 次合计） | 至少一次读到非完整内容的次数 |
|---|---|---|---|---|
| 就地一次写，30 KB | 1.1 | 1 | 0 | 0 / 10 |
| 就地一次写，1 MB | 1 | 1 | 0 | 0 / 10 |
| 就地一次写，20 MB | 2 | 1 | 0 | 0 / 10 |
| 就地分块写，20 MB，不停顿 | 4 | 1 | 0 | 0 / 10 |
| 就地分块写，20 MB，每 1 MB 停 20 ms（模拟流式生成、慢速下载） | 20.2 | 5 | 39 | 10 / 10（第一批从未完整） |
| 临时文件加改名，20 MB，不停顿 | 1 | 1 | 0 | 0 / 10 |
| 临时文件加改名，20 MB，每 1 MB 停 20 ms | 1 | 1 | 0 | 0 / 10 |

结论：就地一次写完的文本（Agent 常见的 `writeText`）在 75 ms 批之后读，半截的概率在这 40 次里为 0；流式、慢写、大文件，半截读是必现的，并且每个中间批都会让 C 记一条错误的外部版本。临时文件加改名在所有情形下都是一个事件、一批、完整。（临时文件自身的事件会很多，20 MB 一次产生约 15 个 `change`，但被 `temporaryPattern` 在 `onRaw` 就丢掉了，成本可忽略。）

**实验 3：就地写时“半截可见窗口”。** `exp/torn.ts`（紧循环整读，`results-torn.txt`）与 `exp/torn2.ts`（紧循环 `stat`，`results-torn2.txt`）。另一个进程写；读者在紧循环里。采样粒度约几十微秒，窗口可能被漏掉，所以只能当作“存在”的证据，不是概率。

- 30 KB 一次写：窗口 0.04 ms，1 次中间观测；1 MB：0.18 ms，19 次中间观测，4 个不同大小。
- 64 MB 加 36 MB 两块写（100 MB 文件）：窗口 16.6 ms，大小为 0 的观测 64 次，中间观测 3123 次、397 个不同大小。20 MB 一次大 write（`chunks` 且块大于文件）：窗口 4.6 ms，大小为 0 的观测 90 次，中间观测 458 次。
- 临时文件加改名：任何采样都只见旧或新，没有 0 字节或中间大小。
- 紧循环整读（`torn.ts`）：30 KB 与 1 MB 各抓到 1 次半截读；20 MB、100 MB 的单次大写没抓到（读本身慢于窗口），临时文件加改名 0 次。

**实验 4：SQLite 存快照的开销。** `exp/sqlite-zstd.ts`，`bun:sqlite`（不是 nb-history 现用的 libsql，数字是下限参考），源文本为本机 `.local` 里的中文小说 UTF-8 切片。输出 `results-sqlite.txt`。

- zstd level 3 压缩比：3 KB 为 0.69，30 KB 为 0.63，120 KB 为 0.60，1 MB 为 0.54（中文文本压缩率不高）。耗时：30 KB 压缩 0.4 ms、解压 0.07 ms；120 KB 压缩 1.2 ms；1 MB 压缩 25 ms、解压 3.1 ms；sha256 1 MB 为 2.5 ms。level 9 在 30 KB 上只比 level 3 小约 10%，耗时 2.8 倍，不值。
- 连续 100 次每次改一个字节的 30 KB 保存，每次一个事务（快照加日志）：WAL 加 `synchronous=NORMAL`，原文 p50 0.27 ms，zstd p50 0.82 ms；`FULL`，原文 p50 1.05 ms，zstd 1.38 ms。库体积：原文 3.11 MB，zstd 2.09 MB。只压缩单版本把 100 版省了三分之一，没有改变“版本数乘文件大小”的量级。
- 相邻版本差异的粗估（`exp/delta-est.ts`）：30 KB 文件改约 600 字节加插入 300 字节，单独压缩 19042 字节，以前一版作字典的增量约 618 字节（约 3%）。120 KB 的那一行为负数（窗口效应），不可信，不引用。这说明真正省空间的是版本合并加增量存储，不是单版本压缩。

**实验 5：一次保存的耗时。** `exp/write-cost.ts`，`results-writecost.txt`，p50 ms。

| 写法 | 30 KB | 1 MB | 20 MB |
|---|---|---|---|
| 就地写，不 fsync | 0.02 | 0.10 | 12.9 |
| 临时文件加改名，不 fsync | 0.12 | 0.86（p95 12） | 9.9（p95 397） |
| 临时文件加 fsync 加改名（现有 `replaceLocked` 的写法） | 1.54 | 1.94 | 11.95 |
| 取 proper-lockfile 锁加读旧值加哈希加上一行加放锁 | 1.61 | 4.2 | 48 |
| 仅读加 sha256（监视核对、C 的提交读） | 0.05 | 1.7 | 40 |

读法：就地写快 1.5 ms，但没有耐久性与原子性；btrfs 上“不 fsync 的临时文件加改名”在大文件上会出现几百毫秒的尖峰（改名覆盖触发数据刷盘），所以不 fsync 并不更省。写入的字节数两种写法相同。锁本身约 0.3 到 0.5 ms，不是代价。

**实验 6：C 的“每个文件一份当前值”的首次基线与稳态。** `exp/baseline-scan.ts`，`results-baseline.txt`。2000 个 30 KB 文本，共 60 MB：读、哈希、zstd、入库共 1.41 s（0.71 ms 每文件），库里 37.3 MB。稳态用 stat 缓存（大小、mtime、inode）核对 2000 个文件 10 ms，对照无缓存整读哈希 129 ms（暖缓存）。所以基线不贵，但大二进制要有大小上限。

**实验 7：Bun 递归 `fs.watch` 的回调延迟。** `exp/event-latency.ts`，`results-latency.txt`。另一个进程完成改名或就地写后，回调到达的时间减去写入进程打印的时间：改名 p50 0 ms、p99 2 ms；就地写 p50 0 ms、p99 3 ms（各 100 次）。因此监视看到事件的 75 ms 全是 `BATCH_DELAY_MS`。记账 RPC 往返 p50 0.3 ms、p99 2 ms（来自任务书的实测）远小于 75 ms，所以 A 在多数情况下赶得上批判定，但它只是“多数”，不是保证，这是 A 为什么还需要“锁没放不判定”的原因。

## 改良组合 B 的具体形态

1. 写入方：向 `locate` 要目标的真实路径，写同目录临时文件，名字符合项目实例的 `temporaryPattern`（现有 `hub.temporaryPath`，由拥有根的进程发，免得监视把它当用户文件），边写边算 sha256 与大小，`fsync` 后调一次 `commit({tmp, target, baseline?, hash, size, actor})`。临时文件不持锁。
2. 提交（拥有根的进程，复用 `rooted.replace` / `replaceLocked`）：取文件锁，条件写核对基线，读改前字节（有 stat 缓存且账面末态吻合时可以只 `stat`，不读），核对临时文件指纹（大小、inode、mtime，或让拥有者读一遍），`chmod` 对齐原权限，`stillHeld` 通过则 `rename`，随后 `history.registerWrite(actor, path, beforeBytes, afterBytes)`（账面末态与 beforeHash 不一致时 nb-history 自动补外部条目），再 `changes.saved` 以真实来源发事件、按 inode 身份登记回声。账本失败只记诊断，不影响返回。
3. 外部与未登记的改动：监视批合并后，用账面“当前值”加 stat 缓存对账，按 `registerObservedWrite` 记为外部；`shell` 的归属按“命令执行期间该会话根里观察到的改动”推断；改动时刻取 mtime 而不是提交时刻。
4. 账本策略（取自 C）：同文件同操作者 30 秒内的连续保存合并为一个版本，不同操作者永不合并；快照 zstd level 3；大文件与二进制只记哈希与大小；启动时按 stat 缓存扫描补记离线改动。
5. 不做的：不就地写、不做认领、不让监视成为经接口写入的记账依据。

## 三个方案都没解决的问题

1. **从未记过账的文件被外部第一次改动时没有改前值。** 账面没有它的快照，diff 只能显示“新建”，误删也无法找回。只有启动时对全部文本文件做一次基线才能补上（实验 6：60 MB 约 1.4 s、37 MB 库），要决定基线的大小与类型上限、是后台做还是首次读到时做。
2. **临时文件加改名改变了文件身份。** inode、创建时间改变，硬链接断开，扩展属性与 ACL 丢失（现有代码只保留权限位），外部工具按 inode 跟踪文件、云同步盘把它看成删除加新建；也要为大文件预留两倍空间。Windows 上目标被其他程序打开时改名覆盖会失败（EBUSY / EPERM），本机无法验证。
3. **Windows 与 macOS 的监视可靠性**。外部改动与 `shell` 归属全靠它，proposal 已承认 Bun 在这两个平台有缺陷；C 另外把经接口写入的归属也押在上面。
4. **`shell` 推断归属会误判。** 命令执行期间用户在别的编辑器保存、或两个会话的 shell 同时运行，都会把别人的改动记成这个会话“推断（shell）”；监视批合并也使命令结束与最后一个事件的先后不确定。
5. **读与写之间的冲突处理。** Agent 先读后写，读与写之间被外部改动时，基线冲突后怎样告诉模型、是否自动重读，三个方案都留给上层。
6. **历史体积的量级。** 实验 4：zstd 单版本只省约三分之一；真正省空间要相邻版本增量存储（粗估约 3%）加合并与稀疏化，A、B、C 都没有定；30 秒合并与收件箱 diff 基准、`revertedEntryIds` 的相互作用也没验证。
7. **账本多进程。** nb-history README 明确“多进程同时打开同一库不支持”，两个服务端同一本书（各有项目子进程）时靠 SQLite 事务兜底；它的进程内写互斥与“写前对账”并不跨进程，两边交错时可能补出多余的外部条目。
8. **孤儿临时文件。** 写入方（服务端）或拥有者在提交前崩溃会在用户目录留下 `.xxx.tmp`；需要按项目实例标记与年龄清扫。现有保存路径已有此问题，B 把它扩大到服务端写入方。
9. **外部改名** 被记为删除加新建，时间线按内容相似度接起来这件事没有设计。
