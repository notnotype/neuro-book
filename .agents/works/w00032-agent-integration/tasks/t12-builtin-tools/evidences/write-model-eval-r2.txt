# 三个写入与记账方案的失败与并发评估（r2）

## 结论

推荐方案 B 作为接口写入的主路径，并吸收 C 里“观察者兜底外部改动”的部分，组合成下面这个改良方案，称为 B+：

- 接口写入（Agent 工具、插件、浏览器保存）统一走 B：写入方只写临时文件，拥有根的进程在自己的锁里完成“核对基线、读改前值、算改动、改名、记账”。
- 外部改动由项目子进程的常驻监视加启动扫描兜底。判定一律对照账本末态的哈希（`registerObservedWrite` / `reconcile`），不依赖认领，也不依赖内存里的回声表。
- 不采用 C 的“认领”模型：它是三个方案里失败与并发行为最差的。

一句话理由：只有 B 让“读改前值”和“落盘改名”发生在同一个进程的同一把锁里，所以崩溃、并发写、外部改动夹在中间时，改动与归属能与真实发生的一致；C 靠事后观察，会丢版本、把半截内容记成版本、把覆盖写当成正常提交。

下面的 B+ 的具体修改（第 5 节）在 B 的基础上补了 5 处，缺任何一处，B 在个别场景也会出错。

## 1. 比较前的三个事实（来自代码与实验）

1. 现有 `replaceLocked`（`locked-replace.ts`）已经是“持锁、读当前字节、`decide`、写临时文件、核对锁与文件身份、改名”。B 的提交几乎就是把它放进项目子进程；A 是让服务端也调用它。
2. `nb-history` 声明单进程单写者（README 已知限制 1）。`registerObservedWrite` / `reconcile` / 写入口内建的 `implicitReconcile` 都靠“账面末态哈希对磁盘”来补账，这是下面所有方案共用的兜底。
3. `changes.ts` 的监视只在有订阅时才开（第一个订阅开、最后一个释放时关），回声登记是内存表，临时文件名带“本实例随机标记”，别的进程写的临时文件会被当成外部新建文件报出来。

## 2. 场景比较

记号：A = 写入方（服务端）自己写盘、先改名后记账；B = 写入方只写临时文件，拥有根的进程提交；C = 账本存“当前值”，监视驱动提交，写前认领。

### S1 写到一半崩溃（写临时文件或就地写时进程死亡）

| | 时序 | 结果 |
|---|---|---|
| A | 服务端写临时文件时被杀，持锁 | 目标文件没变，账本没变；残留 `.tmp` 与一把锁。别的写入方（例如浏览器保存）要等锁过期：实验 E4 里持锁进程被 SIGKILL 后，另一写入方前两次尝试各等约 3.3 s 失败，8.2 s 才成功 |
| B | 服务端写临时文件时被杀，不持锁 | 目标文件没变，账本没变；残留 `.tmp`，没有锁，别的写入方不受影响。启动时清扫临时文件即可 |
| C | 写入方在写（就地写或临时文件）时被杀 | 就地写：目标文件已被截断或写了一半，监视会把半截内容提交成一个版本（E2 场景 1：账本出现一条 12000B 的 external 版本，随后才是 24001B 的完整版本）；临时文件写法：同 B。认领到期作废，不留假版本，这一点 C 做得对 |

结论：B 最稳。A 的代价是持锁者崩溃会拖住同文件的所有写入方约 10 s。C 允许就地写，让“半截版本”成为正常现象。

### S2 改名之后、记账之前崩溃

| | 时序 | 结果 |
|---|---|---|
| A | 服务端改名后崩溃（或 RPC 悬挂中被杀） | 文件已变、账本没记；锁 10 s 后过期，监视按外部记。归属丢成“外部”，内容在监视观察时能存下 |
| B | 项目子进程在改名后、记账前崩溃 | 同 A 的账本结果；但锁属于子进程，子进程重启后可立刻清锁或等过期；启动扫描会补记 external。归属丢失 |
| C | 认领已发、写入已完成，监视或账本崩溃 | 重启后扫描发现文件与存着的“当前值”不同，认领在内存里就丢了，记外部；认领若落盘则能找回，但要多一层持久化 |

结论：三者都会在这个窗口丢归属，不会丢内容，也不会出现假版本；窗口都是“改名到记账”之间的微秒到毫秒。差别只在能否更快自愈：B 的提交在一个进程内，窗口最小；A 要跨一次 RPC，窗口多一个 IPC 往返（p99 约 2 ms）。

### S3 两个写入方同时写同一文件（Agent 会话与浏览器保存，或两个会话）

| | 时序 | 结果 |
|---|---|---|
| A | s1、s2 同时取同一把文件锁（浏览器保存在项目子进程里也用同一把锁，`rooted.replace`） | 串行：后到的在锁里读到先到的结果，`decide` 重算；每次写入都各记一条，改前改后链正确。风险：持锁时间含一次 RPC，账本慢则其他保存等锁，约 3 s 后失败（E4 第一部分：持锁者存活时另一写入方 3.3 s 后失败） |
| B | 两个写入方各写临时文件，各发“提交（基线 H0）” | 提交在子进程锁内按序执行：第二个提交的基线已不是 H0，返回冲突，写入方重读重做。每次成功写入各记一条。写入方需要能处理“冲突”，但这正是想要的 |
| C | 无锁，认领 H1、H2，各自改名 | 版本丢失且无人知晓：E2 场景 3（两次写入隔 40 ms，小于 75 ms 批合并）账本只记了 s2，s1 的版本没有记录，s1 以为写成功了；场景 4（隔 200 ms）两版都记；场景 5（s2 基于旧版覆盖 s1，无锁无基线）账本照常记 s1 与 s2，覆盖没有被发现 |

结论：C 在这里明显最差，且是“静默”的。A、B 都靠锁串行，B 还多了“基线核对”，等价于现有 `replaceLocked` 里的重做。

### S4 外部工具与接口写入交错（`sed -i`、用户编辑器、`git checkout`）

把外部写记为 X，Agent 写记为 Y，改名前文件是 V0。

| | 时序 | 结果 |
|---|---|---|
| A | X 在写入方读改前值之前发生 | 若记账只带哈希，账本要么用 `registerObservedWrite`（改前取账面末态 V0）：把用户在 X 里的改动全算在 Agent 名下（E5 的 A1：diff 里“用户在 vim 里加的第三行”与“Agent 加的第四行”同属 s1，快照里也没有 X）；要么写入方把改前全文也交给账本（`registerWrite`，E5 的 A2：正确记成 external V0→X、agent X→Y），但改前全文要走 RPC，受 1 MiB 单条上限限制，更大的文件就退化为 A1 |
| A | X 在改名之后、账本读快照之前发生（锁约束不了外部工具） | 账本“自己读磁盘”读到的是 X，不是写入方写的 Y，快照与记录的后哈希对不上；账本必须核对读到的字节哈希等于记录的后哈希，否则只记哈希行没有快照 |
| B | X 在提交内读改前值之前 | 提交进程在锁里读到 X，账本拿到的就是读到的字节，走 A2 的正确路径，`registerWrite(before=X)` 补一条 external；进程内传参不受 RPC 上限限制 |
| B | X 在读改前值之后、改名之前 | 与现有 `replaceLocked` 一样：改名前核对文件身份，变了就重做；核对到改名之间仍有一个很小的窗口，X 会被覆盖且账本不知道（见第 4 节） |
| C | X 在 75 ms 批合并窗口内、Agent 写 Y 之前 | 监视只在到点时读当前内容：看到的就是 Y，哈希对上认领，整段 V0→Y 都记给 s1（与 A1 同样的误归属）；X 的版本没有被观察，没有快照 |
| C | X 与 Y 间隔大于批合并窗口 | 两次都被观察，归属正确：X 记外部，Y 记 s1 |

结论：A 与 C 都有“误归属给 Agent、丢外部版本”的窗口，A 能靠把改前全文交给账本补救但有大小上限，C 的窗口由批合并时长决定。B 在进程内同时拿到改前字节与改名权，是唯一能在整份内容规模上都做对的。

### S5 写到一半被读（监视、别的读者、浏览器）

| | 结果 |
|---|---|
| A、B | 写入方只用“临时文件加改名”，读者永远只看到完整的旧版或新版（E2 场景 2：并发读者只见 2 个版本，旧版与完整新版）。临时文件本身会被监视看到，见 S9 |
| C | 写入方怎么写不限定。就地写时，读者与监视会读到半截内容（E2 场景 1：读者看到 3 个版本，其中 12000B 的是半截；账本提交了一条半截 external 版本，随后再提交完整版本记给 s1）。若采用“同文件 30 秒内连续保存合并成一个版本”，半截的 external 与完整的 s1 要不要合并、合并后算谁，没有定义 |

结论：C 若要避免半截版本，必须规定接口写入也走临时文件加改名，这样就不再“不限定写法”，而且仍管不了外部工具的就地写。

### S6 账本故障（SQLITE_BUSY、磁盘满、库损坏、账本进程卡住）

约束是“账本是软依赖：文件读写照常，只丢操作者并写诊断”。

| | 结果 |
|---|---|
| A | 改名已完成，账本失败只写诊断；锁在 RPC 等待期间一直被持有，RPC 悬挂会把同文件其他写入方挡住（超过约 3 s 失败），所以服务端必须给账本 RPC 设短超时。事后恢复靠 `implicitReconcile`：下一次写入或监视观察时补一条 external，历史不断链，归属丢失 |
| B | 提交在同一进程内：账本抛错即捕获，改名已完成，不持锁等 RPC；最稳。但账本故障也是“项目子进程自己的故障”，写入依旧经由它，见 S7 |
| C | 账本是提交的唯一入口：账本故障时监视看到变化也无法提交，直到账本恢复；认领丢了，恢复后的变化一律记 external。与“账本故障时文件功能照常”的承诺相容（文件照写），但中间版本全部合并成恢复后的一条 |

### S7 项目子进程重启

| | 时序 | 结果 |
|---|---|---|
| A | 服务端写入时子进程不在：账本 RPC 失败 | 文件写成，记一条诊断；子进程回来后监视与启动扫描按 external 补记，归属丢失。写入本身不受影响（A 的优点：对子进程无硬依赖） |
| B | 项目文件的提交要经子进程：子进程不在 | 提交失败，写入方得到“可重试”错误；写入不再对子进程无依赖，需要把“子进程重启中”当作可重试而不是失败。浏览器保存本来就有同样的依赖；`user://` 等在服务端本进程内的不受影响 |
| C | 认领在内存里：认领发出后子进程重启 | 认领丢失，写入完成后回来的监视记 external。若认领落盘（写入时多一次磁盘写），可修复，代价是认领需要清理与到期逻辑 |

重启间隙里外部改动的一致处理（三方案相同）：子进程启动时必须做一次全量对账（账本里每个活文件对磁盘；按大小与修改时间过滤，只读有变化的）。现有监视没有这一步，且只在有订阅时才开（`changes.ts` 的 `subscribe`），没有浏览器标签打开时，C 的“监视驱动记账”根本没有观察者，B、A 没有监视也不会错（接口写入已同步记账），只有外部改动延迟入账。所以 C 对“监视常驻”的依赖最强。

### S8 两个服务端打开同一本书（各有自己的项目子进程，共享同一个项目目录）

文件锁放在项目的控制目录里，两个服务端共享；账本 `.nbook/history.sqlite` 也共享。这一场景暴露了三方案共同的问题，也暴露了差别：

- 实验 E1：两个进程同时对同一个 history.sqlite 记同一文件的版本，真实的 `WorkspaceHistory`。紧凑循环下一个进程 0 成功 60 失败，另一个进程成功 58 到 60 个，全部是 `SQLITE_BUSY`；加 0 到 30 ms 随机间隔仍然是一个进程 1 成功 59 失败。出现过 1 次链断裂（改前哈希与上一条的改后哈希对不上）和 1 条多余的 external 条目。两个进程顺序而不并发时全部成功（60 加 60）。裸 libsql 对照（E1c）：`PRAGMA busy_timeout` 没有改善（超时 0 时失败 33 与 20，设为 5000 时失败 23 与 40），推断原因是 `transaction("write")` 另开了连接，PRAGMA 没有带过去。
- A 与 B：文件的写入串行由共享锁保证，没问题；账本写入会失败，记一条诊断，之后由 `implicitReconcile` 补 external，归属丢失。另一台服务端的监视会看到这次改名；若它不遵守“锁被持着时不判定”，可能抢在账本记录之前把它记成 external（再加上账本内 `registerWrite` 随后补记，出现“external 把 Y 记成 external，再记一条 Agent X→Y”的怪序列）。解法是监视按路径检查共享锁文件，锁在就先不判定，且判定用账本末态哈希，不用本进程内存里的回声表（见第 5 节）。
- C：认领在服务端 1 的子进程内存里，服务端 2 的监视先看到文件变化就没有认领，记 external；两个监视各自“读当前值、比较、写入”，读与写不在同一事务里，E1 已见链断裂；没有任何一把锁约束认领与监视。C 在这个场景下归属必然不稳定。

### S9 临时文件与监视的交互（A、B 共有，C 在写入方用临时文件时同样有）

`changes.ts` 的临时文件识别用“本实例随机标记”，只认本进程生成的名字。A 与 B 的临时文件由服务端生成，项目子进程的监视认不得，会把它当作外部新建的文件推给文件树（用户会看到闪一下的 `.第三章.md.xxxx.tmp`），回声过滤再把它的 `rename` 记成外部。需要二选一：临时文件放进控制目录（例如 `.nbook/tmp/`，现有规则已忽略控制目录，且与项目同一文件系统时改名仍是原子的，跨设备时退回同目录加固定前缀并登记）；或者让所有进程共用固定命名规则。注意：仓库的做法是不按点文件名或后缀忽略，防止吞掉用户真实文件，所以只能选前者或“固定前缀加随机串”这种用户不会用的名字。

### S10 持锁者卡住或崩溃（E4 实测）

仓库真实的 `holdLock`，持锁者是另一个进程：

- 持锁者存活但不放锁（相当于 A 里账本 RPC 悬挂）：另一写入方 3.3 s 后失败，`写入锁一直被别的进程占着`。
- 持锁者被 SIGKILL：另一写入方第 1 次（3.4 s）、第 2 次（6.7 s）失败，第 3 次（8.2 s）成功；锁的残留判定是 10 s 无刷新。

对 B 的意义：只有项目子进程（轻载、专用）持锁；对 A 的意义：服务端是 Agent 运行的进程，事件循环忙（大 diff、长工具调用）时更容易刷新不及时，且崩溃或被杀的概率更高，一次就能让浏览器保存失败数秒。C 不用锁，没有这个问题，但也没有串行。

## 3. 汇总表

“好”表示改动与归属与真实发生的一致，“弱”表示有明确且不罕见的窗口，“差”表示静默丢失或误记。

| 场景 | A | B | C |
|---|---|---|---|
| S1 写一半崩溃 | 好，但锁残留约 10 s | 好 | 就地写则差（半截版本） |
| S2 改名后记账前崩溃 | 弱（丢归属） | 弱（丢归属，窗口最小） | 弱（认领丢） |
| S3 并发写同一文件 | 好 | 好（有基线冲突） | 差（静默丢版本、覆盖无感） |
| S4 外部与接口交错 | 弱（改前全文有大小上限） | 好（仅剩改名前的微小窗口） | 弱（批合并窗口内误归属） |
| S5 写一半被读 | 好 | 好 | 差（除非强制临时文件） |
| S6 账本故障 | 好，需 RPC 短超时 | 好 | 弱（中间版本合并） |
| S7 子进程重启 | 好（无硬依赖） | 弱（写入依赖子进程，需可重试） | 弱（认领丢，监视依赖订阅） |
| S8 两个服务端 | 弱（账本 BUSY） | 弱（账本 BUSY） | 差 |
| S9 临时文件被监视看到 | 要补命名规则 | 要补命名规则 | 同 |
| S10 持锁者崩溃 | 弱（服务端持锁） | 好 | 无锁，不适用 |

## 4. 实验

环境：Linux，Bun 1.4.4，8 核；脚本都在 `/tmp/review-write-models/r2/`，从该目录运行；引用仓库源码只读，用绝对路径导入，没有安装依赖，也没有改仓库。

| 编号 | 命令 | 结果 |
|---|---|---|
| E1 | `bun e1-two-ledgers.ts`，另加环境变量 `JITTER_MS=0` 或 `30` | 见 S8：两进程并发写同一个 history.sqlite，一方几乎全部 `SQLITE_BUSY`（最好的一次 60 失败，随机间隔时 59 失败），出现过链断裂 1 次、多余 external 1 条 |
| E1b | `bun e1b-single-and-sequential.ts` | 对照：A 写 60、B 写 60，不并发，120 次全部成功。说明失败来自并发而不是脚本 |
| E1c | `bun e1c-busy-timeout.ts` | 裸 libsql 两进程并发写：`busy_timeout` 0 与 5000 都有 20 到 40% 失败，PRAGMA 没有起作用 |
| E2 | `bun e2-inplace-and-coalesce.ts` | 用真实 `fs.watch` 加 75 ms 批合并，模拟方案 C 的“看到变化后读当前内容、按哈希对认领”。场景 1：就地分块写，账本提交了一条 12000B 的半截 external 版本；场景 2：临时文件加改名，只见完整版本；场景 3：40 ms 内先后两版，只记了后一版；场景 4：间隔 200 ms，两版都记；场景 5：覆盖写，没有任何冲突提示 |
| E4 | `bun e4-lock-crash.ts` | 见 S10：持锁者存活，另一写入方 3.3 s 失败；SIGKILL 之后 8.2 s 才能写成 |
| E5 | `bun e5-external-before-write.ts` | 真实 nb-history：外部在 Agent 写入前改了文件。只带哈希、用 `registerObservedWrite`：agent 一条，diff 把外部的一行记成 agent 加的；带改前全文、用 `registerWrite`：external 一条加 agent 一条，diff 只含 Agent 的一行 |

E2 是对 C 模型的模拟，不是 C 的真实实现，它验证的是“监视批合并加按哈希对认领”这一机制的后果，细节（例如批合并时长、是否合并）可以由 C 的实现调整，但“只能看到被观察到的状态”这一性质不会变。E1 的“链断裂”由时间线里相邻两条的哈希是否衔接判定。

## 5. 推荐方案 B+ 的具体修改

在 B 上加下面 5 项：

1. **提交内读改前、记账带改前字节**：提交进程在锁里已经读了改前值，记账用 `registerWrite(before, after)`（进程内传字节），这样先到的外部改动会被正确补成 external 条目，Agent 的 diff 只含它自己的改动（E5 的 A2）。账本故障时只记诊断，改名照常。
2. **提交带基线**：基线不符返回冲突，由写入方重读重做，与现有 `replaceLocked` 的“身份变了就重做”一致；改名前保留身份核对。
3. **监视判定对照账本，且遵守共享锁**：监视在文件锁被持着时不判定；判定时用 `registerObservedWrite` / `reconcile`（账面末态哈希相同即吸收），内存回声表只用来省去读文件。这样两个服务端、子进程重启后也不会把别人的写入记成外部或记两遍。
4. **监视常驻加启动对账**：项目子进程打开项目后监视就不依赖订阅，启动时扫描账本里的活文件对磁盘，补上宕机与重启期间的外部改动。
5. **临时文件放控制目录**：写入方的临时文件放 `.nbook/tmp/`（跨设备时退回同目录加固定前缀并告知子进程），消除 S9。服务端启动清扫残留。

同时对 C 的取舍：C 的“所有改动走同一条记账路径”这一点保留在第 3 项（外部与接口写入的兜底路径相同，都经账本末态比较），但不要让接口写入依赖认领。

不推荐的组合：A 加“服务端持锁并等账本 RPC”。它让服务端进程成为“持锁并依赖另一个进程”的一方，是 S1、S6、S10 里风险最高的结构。

## 6. 三个方案都没解决的问题

1. **外部工具与改名之间的微小窗口**：`replaceLocked` 注释已承认，改名前核对身份到改名之间，外部写入会被覆盖，账本不知道。三个方案都无法消除，只能缩小。
2. **两个服务端同时记账**：`nb-history` 声明单写者，E1 实测并发写大量 `SQLITE_BUSY` 并出现链断裂。需要指定“账本拥有者”（例如项目级所有权锁，第二个子进程转发记账或只读打开），或者让 nb-history 在写事务内读末态并带重试。这需要改 nb-history，不属于三个方案的任何一个。
3. **归属推断的天然上限**：Agent 用 `shell` 改的文件、改名与记账之间崩溃，归属只能是“推断”或“外部”；三个方案相同。
4. **改前全文很大的文件**：二进制与超限文件不存快照，因而无法“恢复旧版本”，只能记哈希与大小；B+ 的第 1 项对大文件也只能记哈希。
5. **批合并窗口内的多次外部改动**：同一文件被外部工具在 75 ms 内连改多次，监视只能看到最后一版；中间版本无法找回。
6. **项目子进程宕机时的写入策略**：B+ 让接口写入依赖子进程，需要决定“重启期间 Agent 写入等待还是失败”；若要求不依赖，就必须保留一条服务端直写的备用路径，等于重新引入 A，需要开发者决定。
7. **对账时机与成本**：启动全量对账、大目录下的成本以及与“稀疏化保留策略”的相互作用，三个方案都没有测过。
