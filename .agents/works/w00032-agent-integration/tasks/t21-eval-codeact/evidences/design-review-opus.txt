# t21 计划设计审查（Claude Opus，从整体看）

审查对象：`/tmp/claude-1000/review-t21-design/plan.md`；仓库 master `1fb32049f`，只读。

## 1. 嵌套调用的事件一半复用、一半新造：现有消费者只看到开头，归约改状态的合同对嵌套调用悄悄失效

- **严重程度**：重要；**类别**：接口形状 / 长期代价
- **位置**：关键设计“nb-harness 内核：工具里调工具”的“流水线”“不进模型上下文”“中止与收尾”
- **现象**：嵌套调用的开始复用 `toolStarted`（加 `within`），结束却写新的 ctrl 事件 `nestedToolResult`。现有读 `toolStarted` 的代码不认 `within`：`nb-agent-ui/src/kernel-transcript.ts:382` 按 `callId` 找回复里的调用（`<父>~<n>` 找不到，静默丢掉）；`plugins/agent/backend/subagents/tree.ts:64` 把每条 `toolStarted` 计入子代理的“已调工具数”和“当前一步”；`kit/compaction/restore.ts` 的 `recentFiles` 把 `toolStarted` 按 `callId` 记下、只认 `toolResult` 配对，所以 eval 里读过、改过的文件压缩后不放回。另一面，`api/tool.ts` 的 `ToolContext.read` 注释写明“工具要改状态，把新值放进结果的 `details`，由扩展从 `toolResult` 归约”：嵌套调用的结果是 `nestedToolResult`，没有扩展归约它，经 eval 调这类工具时状态变化直接丢；嵌套调用的 `ctx.read` 读的又是父回复所在叶子的状态（输出 23），同一单元里前一次嵌套调用的效果它也看不到。
- **为什么是问题**：同一件事（一次工具调用）的两半落在两种可见性上，每个现有和以后的消费者都得各自想明白“开头看得见、结尾看不见”怎么处理；漏想的地方不报错，只是数字不对或状态丢失（信号正是“调用方要为它写补丁，同一件事各写一份”）。计划只为 `loop-guard` 写了一条规则，别的消费者没列。
- **建议改法**：两半用同一种可见性，二选一，写进 Spec：
  - 推荐 A（默认不可见、按需订阅）：开头也用新事件 `nestedToolStarted`，与 `nestedToolResult` 成对；现有消费者零改动、行为不变。另在 Spec 写明：嵌套调用的结果不进扩展归约，靠归约改状态的工具在代码里调时状态不变；需要的扩展显式在 `reduce` 里订 `nestedToolResult`。工具声明可加 `codeCallable: false`（缺省 true）让这类工具从代码里调直接得 `invoke-not-allowed`，不让它半生效。
  - B（默认可见、在一处过滤）：两半都是普通 `toolStarted`/`toolResult` 加 `within`，组请求与压缩的投影跳过带 `within` 的；归约与“最近文件”自然覆盖嵌套调用，`loop-guard`、子代理计数各自按 `within` 过滤。
  - A 的部件更少、对已发布的事件消费者无破坏，B 更贴近决定 3 的“照常”；不管选哪个，`toolStarted{within}` 配 `nestedToolResult` 的混合形状都不要留。

## 2. 全局对象是“一个工具加 `{method, args}`”：审批记忆、规则、预览与校验都只能按整个对象，等 w00033/w00034 有了使用方再改就是破坏性改动

- **严重程度**：重要；**类别**：接口形状
- **位置**：关键设计“全局对象（`agent.tools` 的声明）”
- **现象**：`browser.goto(url)`、`browser.submit(...)`、`nbook.snapshot()` 都变成同一个工具 id 的 `invoke(id, {method, args})`。
  - 档位：`ToolDeclaration.effect` 可以是按参数求值的函数，所以按方法分档本身做得到（这一点计划没写出来，应写进 SDK 文档）。
  - 但“本会话都批准”：[`agent/permissions.md`](docs/specs/agent/permissions.md) 输出 18 写“别的工具记整个工具”。用户对 `browser.goto` 点一次“本会话都批准”或“以后都允许”，`browser.submit`（w00034 要单独确认的“对外操作：发布、提交表单”）就一起放行了；除非每个全局对象的插件自己在审批钩子里造 `remember` 规则，而钩子是 nbook.agent 的，插件改不了。
  - 用户规则按工具与参数模式写，`{method, args: [...]}` 里位置参数没有名字，规则和审批预览都只能显示 `args: ["e12", {...}]`。
  - 内核按声明 schema 做的参数校验（输出 18 的 `invalid-arguments`）失效，每个插件在 `method` 分派里手写校验；文档 `global.docs` 手写 Markdown，与 w00033 已定的“写成一份由类型定义生成的文档”、调研第 6 节“各家共同的做法：接口声明从真实的工具定义生成，不手写”相反，迟早与实现漂移。
- **为什么是问题**：决定 5 只定了“只有 `对象.方法(...参数)` 一种写法”，没定它背后映射到一个工具。现在没有任何使用方，改形状零成本；w00033、w00034 落地后，换成按方法拆就要改每个插件、SDK 示例和已写下的用户规则。
- **建议改法**（不改模型看到的写法）：一个方法一个 `exposure: "code"` 工具，各有自己的 `parameters`、`effect`、`description`；声明多一个 `global: {object: "browser", method: "goto"}`。对象级的一行摘要放在一个对象级声明里（最小的形状：同插件里一个工具的 `global` 带 `summary`，或者一个只有 `{name, summary}` 的小贡献点，二者取一）。内核 Proxy 把 `browser.goto(x)` 映射为 `invoke("<插件>.browser.goto", x)`，约定单个对象参数，同 `tool.*`。`docs://eval/<object>` 由成员工具的 schema 生成 TypeScript 声明（同 Codex code mode 的 `declare const tools`），可选再拼插件写的说明文字。这样审批记忆、规则、预览、校验、文档全部按方法、全部复用现有机制，插件也不用写分派。

## 3. `tool.<名>` 的返回类型按“这一次有没有 `details`、图片”变化，`details` 由此变成模型代码依赖的公开接口

- **严重程度**：重要；**类别**：接口形状 / 长期代价
- **位置**：关键设计“nbook.agent：eval 工具与内核”的“内核”一条（`tool` 是 Proxy……）
- **现象**：成功且只有文字时交回字符串，有 `details` 或图片时交回 `{text, details?, images?}`。同一个工具在不同调用间返回类型会变（`read` 读文本文件是字符串、读图片是对象；`edit` 部分文件失败时带 `details.files`），模型写的 `(await tool.read(...)).split("\n")` 时好时坏。`ToolResult.details` 的注释是“给程序看、不进请求”，各工具的 `details` 形状从来不是对模型的合同；交给代码之后，工具作者给某个工具加一个 `details` 字段，就把所有调用它的模型代码的返回类型从字符串改成了对象，没有任何地方提示。
- **为什么是问题**：模型无从得知某个工具什么时候返回什么类型，文档也写不出来；以后要按 schema 生成 `tool.*` 的 TypeScript 声明（第 2 条、以及 t19 的按需加载）时没有可写的返回类型。下一批的 `judge`、`completion` 和以后的 Python 内核都要沿用这条约定，越晚改越贵。
- **建议改法**：返回类型由声明决定、每次都一样：
  - 工具声明可选 `returns?: <JSON Schema>`（同 MCP 的 `outputSchema`）。有它时代码拿到的就是 `details`（照 schema 校验，不合格算工具出错）；没有时一律交回文字字符串。
  - 图片不改变返回类型：嵌套调用带图时，图片默认并进本单元的图片（同 `display`），或者另给 `tool.<名>.full(args)` 交回完整 `{text, details, images}`，二者取一。
  - 全局对象的方法（第 2 条）同样按 `returns` 交回结构化值，这正是句柄（w00034 的标签页 id）需要的出口。

## 4. 没写 eval 的“本会话都批准”“以后都允许”记什么：按现行规则会记整个工具，等于一次点击放开任意代码

- **严重程度**：重要；**类别**：长期代价
- **位置**：关键设计“审批预览”；“Spec 与文档改动”的 `agent/permissions.md` 一条（只写“eval 是执行档”）
- **现象**：[`agent/permissions.md`](docs/specs/agent/permissions.md) 输出 18：`shell` 按命令前缀记，解释器、shell 这类太宽的前缀不能记（`remember: false`）；“别的工具记整个工具”。eval 不是 `shell`，计划没给它 `remember`，于是落到“记整个工具”：在 `ask`、`allow-writes` 模式下对一段代码点“本会话都批准”，之后本会话所有代码不问；点“以后都允许”（输出 23）则写进用户规则，以后所有会话的所有代码不问。eval 没有沙箱（计划“不做与风险”第 2 条），这与 `shell` 不许记 `node *`、`python *` 的理由完全相同。
- **为什么是问题**：决定 3 要求“整段代码按执行档审批”，现行规则下一次点击就把它退化成 `yolo` 对代码的放行，而且是用户难以意识到的永久规则。
- **建议改法**：审批钩子对 eval 一律给 `remember: false`（界面上就没有这两个选项），写进 `agent/permissions.md` 输出 18 与 `agent/eval.md`；要少问的用户用审批模式（`auto`、`yolo`）。全局对象若按第 2 条拆成按方法的工具，它们照常按工具记，不受影响。

## 5. “等用户应答的时间不计”要求 eval 知道嵌套调用在等人，`invoke` 的签名给不出这个信号；下一批派子代理还会再撞一次

- **严重程度**：重要；**类别**：接口形状
- **位置**：关键设计“时限”；`ToolContext.invoke?(tool, args): Promise<ToolResult>`
- **现象**：嵌套调用的审批（`interactionRequested`）在内核里发生，eval 只握着一个没 settle 的 Promise，分不清它是在执行、在等审批，还是在等 `ask`。要实现“等用户应答不计”，要么给 `invoke` 加回调或事件，要么 eval 去订会话日志找 `interactionRequested{within}`，后者把 eval 绑在日志格式上。下一批的派子代理、`wait` 这类委派调用会跑几分钟，omp 的做法是等委派工具时暂停单元计时（调研“工具桥”第 4 条 `bridge-timeout.ts`）；按计划现在的规则，它们会被 30 秒时限杀掉，到时要再改 `invoke` 的签名。
- **为什么是问题**：`invoke` 是内核的公开接口（插件 SDK 可见），第一版定下只返回 Promise，第二批就要加参数或换形状。另外嵌套调用不计入 `loop-guard`，单元时限是 `for (;;) await tool.read(...)` 这类失控循环唯一的上限；时限暂停规则一旦放宽，这个上限也就没了。
- **建议改法**：用一条更简单的规则，同时不让失控循环无界：
  - 单元时限只计“没有嵌套调用在途”的时间：有任一 `invoke` 在途就暂停（等审批、等提问、等子代理、慢工具都覆盖，`invoke` 签名不用变，下一批不返工）。
  - 另加每个单元的嵌套调用上限（例如 2,000 次，超过的 `invoke` 得 `error`、码 `invoke-limit`），并写进 Spec 作为 `loop-guard` 不计嵌套调用的替代上限。
  - 若坚持只暂停等用户的时间，就在第一版把 `invoke` 定成 `invoke(tool, args, {onWaiting?(waiting: boolean)})`，别等第二批再改。

## 6. 嵌套结果全文进会话日志：计划自己的头号用例（批量读章）每跑一次就把读过的正文重写一遍日志

- **严重程度**：重要；**类别**：长期代价
- **位置**：关键设计“流水线”（`nestedToolResult{..., text, images?, details?}`）；Context 第 1 段
- **现象**：每个嵌套调用写一条 `toolStarted` 和一条带全文的 `nestedToolResult`。日志的外置规则是单个字符串超过 16,384 字节才写成按 SHA-256 去重的 `$blob`（[`harness/session.md`](docs/specs/harness/session.md)“大块内容”）。一章 3,000 汉字约 9 KB UTF-8，低于阈值，内联、不去重（字数是推断的典型值，未取本仓库样本）。一次读 300 章做统计，日志多约 2.7 MB 的 path 事件和 600 个写入批；同样的统计改一行重跑，再加 2.7 MB。这些内容模型看不到（不进请求）、内核恢复不了（决定 2），只供界面子行与审计。界面的 transcript 与 `treeNodes` 都按 path 读，会话越用越重。
- **为什么是问题**：批量读是 Context 里写的第一用途，不是边角；体积按“单元数 × 读的量”线性涨，且没有压缩会回收它（压缩只换模型看到的内容）。
- **建议改法**（部件不增加）：`nestedToolResult` 的 `text` 一律外置成 `$blob`（不看阈值），同一章读多少次只存一份，界面点开子行时照现有的 blob 读法取全文；图片同理。再进一步可只对 `effect: "read"` 的嵌套结果这样做，写入类保持现状以便审计。若外置不可行，就只记前 2 KB 加 `textHash` 与 `size`，界面子行显示截断，Spec 写明。

## 7. `exposure` 定在工具声明上：MCP 的“工具多时经代码按需加载”是按绑定、按数量的选择，声明级字段装不下；不带 `global` 的 `code` 工具也没有任何发现途径

- **严重程度**：重要；**类别**：接口形状 / 遗漏的候选
- **位置**：关键设计“`ToolDeclaration.exposure`”；“全局对象”第 3 条（eval 的说明只列全局对象）
- **现象**：
  - w00036 决定 5、6：MCP 工具 id 为 `mcp.<服务>.<工具>`，按服务绑到 Profile；工具多时经 CodeAct 按需加载。同一个 MCP 工具在工具少的 Profile 里应直接给模型、在工具多的 Profile 里只走代码，这是 Profile 绑定或会话层面的选择，不是工具作者在声明里能定的。声明级 `exposure` 迫使 MCP 插件在登记时二选一，或登记两份声明。
  - 计划里模型认识 `code` 工具的唯一途径是全局对象的一行摘要加 `docs://eval/<name>`；`exposure: "code"` 而不带 `global` 的工具，模型既不在工具清单里看到，也没有列表或搜索能找到它（对照调研第 6 节：Codex 的 `tools.tool_search`、Cloudflare 的 `search()`、Anthropic 的文件树）。
  - 计划没写 `code` 工具是否进 `toolsAnnounced` 与给模型的 `notice{tools-changed}`（输出 16）：照现行规则会把模型调不到的工具名告诉模型。
- **为什么是问题**：t19 的需求是计划要服务的三个来源之一，计划没说它怎样落在这套接口上；先把可见性做成声明字段，以后挪到绑定上要兼容两处来源。
- **建议改法**：
  - 第一版把“只在代码里可见”收窄为“属于全局对象的成员”（声明带 `global` 即只进代码，不另设 `exposure` 字段），部件少一个；没有 `global` 的工具照旧按绑定进清单，在代码里同样能 `tool.<名>` 调。
  - 留给 w00036：在 Profile 绑定上加“经代码”这一档（例如 `tools.code: string[]`，或绑定项 `{tool, via: "code"}`），与 `required`/`optional` 并列；配一个由 schema 生成的 `docs://eval/tools` 列表（TypeScript 声明，同第 2 条的生成器）。现在只需在 Spec 里写明可见性由绑定决定这一方向，不必实现。
  - Spec 写明 `code`-only 工具不进 `notice{tools-changed}` 的文字（仍可进 `toolsAnnounced` 以便回退比对）。

## 8. `ToolContext.invoke` 发给每一个模型直接调用的工具：一个只为 eval 的能力变成所有插件工具的 SDK 面

- **严重程度**：建议；**类别**：接口形状
- **位置**：关键设计“`ToolContext.invoke?`”（“只给模型直接发起的调用”）
- **现象**：按计划，任何插件工具（包括声明为 `read` 的）在执行时都拿得到 `invoke`，能以本会话身份调工具集里的任何工具。审批照常，所以按模式不越权；但嵌套调用不计 `loop-guard`、日志与界面多出一层“某某工具里的调用”，插件作者也会把它当成正式能力来用（例如一个 `read` 档的工具内部去调 `write`），这些用法以后都要兼容。
- **为什么是问题**：内核新概念只有一个真实使用方，却以最宽的形式公开；以后想收窄（例如只许 eval、只许执行档）就是破坏性改动。
- **建议改法**：声明加 `invokes?: true`（缺省没有），只有声明了的工具的上下文里有 `invoke`；第一版只有 `nbook.agent.eval` 声明它。下一批的 `judge`、派子代理若也需要，各自声明即可。部件只多一个布尔，换来公开面收窄与审批界面上“谁会在里面调工具”可预知。

## 9. 全局对象重名时“后登记的不进这个会话”：结果取决于插件加载顺序

- **严重程度**：建议；**类别**：接口形状
- **位置**：关键设计“全局对象”第 2 条
- **现象**：两个插件都登记 `browser` 时，谁可用取决于登记先后，换一次安装或升级顺序，模型拿到的 `browser` 就换成另一个插件的，审批档位与文档跟着变。
- **为什么是问题**：结果靠加载顺序碰巧成立；用户看到的是“昨天能用的接口今天变了”，诊断里才有线索。
- **建议改法**：重名的双方都不进会话、诊断写明两个来源；或在登记时按插件 id 排序取确定的一方并诊断另一方。前者更简单，也逼插件作者改名。与内置名冲突时只拒绝插件一方（计划已是如此）。

## 10. 只有空闲回收，没有内核总数上限；下一批派子代理会把“每会话一个进程”乘上去

- **严重程度**：建议；**类别**：遗漏的候选 / 长期代价
- **位置**：关键设计“内核宿主”“空闲回收”；“不做与风险”第 3 条
- **现象**：本机实测 Bun 1.4.4 一个只挂着 IPC 的空子进程 VmRSS 约 34 MB（`/tmp/claude-1000/review-t21-design/lab-opus/parent.ts`），载入 acorn、跑过几次单元后更高。omp 的子代理各有自己的内核（调研“进程与执行”第 1 条）；下一批 `agent`/`workpool` 一波 10 个用 eval 的子代理就是 10 个进程，30 分钟内都不回收。开发者机器 15 GB，已有 e2e 因内存超时的记录。
- **为什么是问题**：上限只靠“空闲 30 分钟”间接兜，进程数随并发会话线性涨，没有天花板。
- **建议改法**：内核宿主加全进程的上限（例如 8 个），超出时回收最久没用的内核。回收走已有的重置路径与提示（决定 2 已接受“重置后下一次结果写明”），只多一个计数与 LRU，部件几乎不增加。上限与读数写进 Spec 的边界。

## 11. 切片 2 到 4 合入后、切片 5 之前，嵌套调用在界面上不可见，询问也看不出来自代码

- **严重程度**：建议；**类别**：范围
- **位置**：“切片”
- **现象**：现行 `kernel-transcript.ts` 对 `callId` 为 `<父>~<n>` 的 `toolStarted` 找不到对应调用、静默忽略，不认识的 `nestedToolResult` 也不显示；嵌套调用的 `interactionRequested` 会照常弹审批，但没有“eval 里的调用”字样（那是切片 5 的事）。按仓库“验证完直接合入 master”的流程，切片 3 合入后，用户在 `ask` 模式下用 eval 会看到一串来历不明的 `write` 询问。
- **为什么是问题**：每片“能独立验证”，但合入后的产品状态不自洽；评审板定稿可能要几天。
- **建议改法**：二选一写进计划：切片 5 之前 eval 不进任何内置 Profile（决定 5 的“可选工具”在切片 5 时再登记）；或切片 2 顺带让 transcript 把带 `within` 的询问加一行纯文字来源（不等评审板），子行等切片 5。前者零代码。

## 汇总

按影响排序：

1. 第 2 条（重要，接口形状）全局对象映射成一个 `{method, args}` 工具：审批记忆与规则只能按整个对象，校验与生成文档丢失；现在零使用方，改成“一个方法一个工具、`global: {object, method}`”零成本，w00033/w00034 之后就是破坏性改动。
2. 第 1 条（重要）嵌套调用开头复用 `toolStarted`、结尾新造 `nestedToolResult`：现有三处消费者（transcript、子代理计数、压缩放回）只看到一半，“靠 `toolResult` 归约改状态”的合同对嵌套调用悄悄失效；两半统一可见性。
3. 第 3 条（重要）`tool.<名>` 返回类型按每次结果变化，`details` 被动成为模型代码的公开接口；改成按声明 `returns` 固定。
4. 第 4 条（重要）eval 没规定 `remember`，按现行规则一次“本会话都批准”或“以后都允许”放开任意代码；给 `remember: false`。
5. 第 5 条（重要）“等用户应答不计时”需要 `invoke` 给不出的信号，下一批派子代理还要再改签名；改为“有嵌套调用在途就暂停”加每单元调用数上限。
6. 第 6 条（重要）嵌套结果全文进日志，批量读 300 章约 2.7 MB/次且不去重；嵌套结果一律外置成 blob。
7. 第 7 条（重要）`exposure` 放在声明上装不下 MCP 按绑定、按数量的选择，`code` 工具也无从发现；第一版只让 `global` 成员只进代码，方向写成“可见性由绑定决定”。
8. 第 8 条（建议）`invoke` 改为声明 `invokes: true` 才有。
9. 第 9 条（建议）全局对象重名按加载顺序取舍，改为双方都拒绝。
10. 第 10 条（建议）内核进程加总数上限与 LRU 回收，复用重置路径。
11. 第 11 条（建议）切片 5 之前 eval 不进内置 Profile，避免合入后出现来历不明的询问。

仔细检查后没有发现问题的方面：

- 问题框定本身：决定 3 要求嵌套调用照常审批、过拦截链、记日志，而审批钩子、拦截链、`approvalRemembered` 等 ctrl 事件都只在内核里，eval 在插件侧无法不经内核做到；“omp 式只审批整段”与“只记在 eval 结果里”都达不到决定 3，所以内核通道是必要的。问题在事件与接口的形状（第 1、3、5、8 条），不在要不要内核通道。
- 内核进程模型：子进程加 SIGKILL 是同步死循环唯一可停的做法，否决 Worker 与 `node:vm` 的理由有调研证据；Codex code mode、Cloudflare Code Mode 的隔离环境是无状态或另有运行时，与决定 2 的常驻变量不相容，不是被漏掉的更简单候选。
- 重置判定：由扩展从 `toolResult.details` 归约“路径上最后一个单元”，与回退、分叉、swipe 的路径语义一致，是在不给工具开放路径读取前提下最小的做法。
- 下一批的 Python 内核：协议消息（`run`、`log`、`display`、`call`、`done`）与语言无关；唯一绑定 JS 的是手写的 `global.docs`，第 2 条的“由 schema 生成声明”同时解决。

各级数量：阻断 0，重要 7，建议 4，共 11 条。
