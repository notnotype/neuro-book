## 1. 子会话里的 `switch_mode` 提问交给父 Agent：父 Agent 能用 `agent_answer` 把子会话切出 `plan` 并把审批模式改成 `yolo`；答不了时子会话又卡住

- **严重程度**：重要；**类别**：不变量 / 安全；第一轮第 1 条没处理完的一半
- **位置**：`docs/specs/agent/subagents.md:82`（输出 11）、`subagents.md:89`（输出 15）、`subagents.md:41`（`answer` 参数没定类型）；`docs/specs/agent/modes.md:58`（输出 8“任何审批模式下都要用户答”）；`plan.md:126`（“后代的 `mode-switch` 不进停靠区”）；代码 `packages/neuro-book/src/plugins/agent/backend/permissions/modes.ts:92-103`、`packages/nb-harness/src/kernel/run/interaction.ts:96-99`
- **现象**：`switch_mode` 不走审批，而是用 `call.ask` 发一个 `kind: "question"` 的同步提问，回答的 `data` 是 `{approved, approvalMode?}`，批准后一次 `changeSettings` 同时改模式与审批模式（modes.ts:92-103）。内核的 `allowed()` 对提问只看会话头：`questions: "caller"` 时父会话也能答（interaction.ts:98）。子会话缺省 `questions: "caller"`，于是子会话里的 `switch_mode` 提问是“交给调用方的同步提问”：父会话的前台等待以 `question` 返回，父 Agent 用 `agent_answer` 应答。
- **为什么是问题**：
  1. `agent_answer` 的 `answer` 若能带结构化数据（nb-form 表单提问需要它，Spec 没定），父 Agent 答 `{approved: true, approvalMode: "yolo"}` 就把子会话切到 `normal`、审批模式改成 `yolo`：父 Agent 自己在 `plan` 里也能这样干。这同时违反 README 第 8 条（审批一律交给用户）、subagents“不承诺”第 2 条与 modes 输出 8。
  2. `answer` 若只收文字，`isAnswer` 不过，子会话的 `switch_mode` 总是 `ask-invalid-answer`；而按 plan.md:126 后代的 `mode-switch` 又不进父会话的停靠区，用户只有打开子会话才看得到、答得了，前台等待则一直停在 `question`。
  3. 白名单允许“自己派自己”（前端处理第 21 条），用户把主创加进主创的白名单，子会话就是带 `switch_mode` 的主创；adhoc 没有这个工具，所以缺省路径碰不到，但白名单是用户可改的。
- **如何核实**：读 modes.ts:75-104 与 interaction.ts:96-99；脚本化模型：父会话 `plan`，派一个带 `switch_mode` 的 Profile，子会话第一条回复调 `switch_mode{mode: "normal"}`，父会话 `agent_spawn` 以 `question` 返回，事项是 `mode-switch`。
- **建议改法**：Spec 写明模式切换的提问只交给用户：(a) 内核层面最干净——`interactionRequested` 加一个“只收用户”的标记（或 `switch_mode` 改用审批事项，审批本来就只收用户），`allowed()` 照它判；(b) 只在插件层面做：`agent_answer` 对 `mode-switch` 事项得 `not-allowed`，等待把 `mode-switch` 当成“等用户”而不是 `question`，并让它进停靠区（推翻 plan.md:126 那一句）。同时在 subagents 输入表里定 `answer` 的形状（`{text, data?}` 还是只有文字）。

## 2. 模式闸门仍可经续用绕过：`plan` 里的父会话对 `normal` 时派出的子会话 `agent_send`，子会话照写作品

- **严重程度**：重要；**类别**：不变量；第一轮第 1 条没处理完的另一半
- **位置**：`docs/specs/agent/subagents.md:62`（输出 3“之后两边各改各的”）、`subagents.md:81-83`（输出 10–12，续用没有模式检查）、`subagents.md:141`（`mode-unsupported` 只列 spawn）；`docs/specs/agent/modes.md:68`（输出 14 的理由“没有闸门的子会话会绕过父会话的模式”）
- **现象**：`mode-unsupported` 只在派发时查，子会话的模式只在建好时复制一次。用户常见的用法：`normal` 下让主创派一个 adhoc（模式 `normal`），然后把主创切到 `plan` 讨论；这时模型 `agent_send{id, message: "把第三章改成……"}`，子会话在 `normal` 下照写。`agent_send`、`agent_answer` 等级是 `read`、不经审批，等于第一轮第 1 条描述的绕过换了一个入口：modes 输出 14 写的理由同样适用。没装模式扩展的子 Profile（`normal` 时允许派）续用时也一样。
- **为什么是问题**：第一轮的修法只堵了派发，没堵续用；adhoc 是缺省可派的，这条路径就在缺省配置里。
- **如何核实**：对照输出 3、10–12 与 modes 输出 14；脚本化模型：`normal` 下 `agent_spawn{async}` 一个 adhoc 并让它空闲，`changeSettings` 把父会话切到 `plan`，父会话 `agent_send` 让子会话调 `write`，子会话的 `write` 得 `ok`。
- **建议改法**：二选一写进 subagents 与 modes 输出 14：(a) 让子会话开新运行或插话的 `agent_send`、`agent_answer` 先把子会话的模式“收紧到不宽于父会话”（父会话非 `normal` 时，子会话是 `normal` 就先 `changeSettings` 成父会话的模式，没装模式扩展的得 `mode-unsupported`）；(b) 规定父会话非 `normal` 时续用一律得 `mode-unsupported`。(a) 更顺：用户切回 `normal` 后子会话不会自动放宽，要写明。

## 3. 内核第 4 处只保证进入 Agent 插件的包装 `ToolWrapper.execute`，到不了子代理工具自己的 `execute`：“同步段按调用顺序”靠的是时序，不是合同

- **严重程度**：重要；**类别**：正确性 / 接口；第一轮第 6 条的修法没落到实处
- **位置**：`plan.md:31`（内核第 4 处）、`plan.md:52`（预占在 `execute` 同步段）、`plan.md:63`（“内核第 4 条保证同步段按调用顺序进入”）；`docs/specs/harness/runtime.md:153`（输出 86）；`docs/specs/agent/subagents.md:76`（输出 8）、`docs/specs/agent/jobs.md:49`、`jobs.md:74`；代码 `packages/neuro-book/src/plugins/agent/backend/tools.ts:181-217`、`238-252`
- **现象**：子代理工具经 `agent.tools` 贡献（subagents.md:35），内核拿到的实现是 `AgentTools.create` 交回的 `ToolWrapper`（tools.ts:99-105）。内核调用的 `execute` 是包装的：它先 `await this.#ensure()`（里面 `await registry.current(id)`，提供方没激活时 `await activate(...)` 是真的 I/O），再在 `#run` 里 `await built.implementation`（工厂 `create` 返回 Promise 时要等它），最后才调真正的 `implementation.execute`（tools.ts:181-217、238-252）。内核第 4 处让第 i+1 个调用在第 i 个“进入 `execute`”之后进入，进入的是包装；包装之后两个调用各自经过的 await 次数取决于：这个会话里这个工具是否第一次用（要建 `Built`）、工厂是不是异步、提供方是否已激活。`agent_answer` 后跟 `agent_send`（两个不同的工具 id、两个包装）或 `agent_spawn{async}` 后跟 `jobs`，后一个的包装已建好而前一个第一次用时，后一个先到达真正的 `execute`，先挂 promise 链或先读任务表。
- **为什么是问题**：plan.md:63 把“对同一子会话按调用顺序”与 jobs.md:74“排在后面的 `jobs` 列得出前面以 `async` 登记的任务”建立在一条到不了插件实现的保证上。现在多数时候顺序碰巧对：第 i+1 个在进入前还要写一次 `toolStarted`（JSONL 存储里每次 `append` 都 `fsync`，jsonl-store.ts:276），给了第 i 个几毫秒的领先；内存存储下这段领先只剩几个微任务，测试与产品的时序不同。名额不会被越过（预占是一步同步的检查加登记），但“同一回复第 9 个被拒”的是哪一个、`jobs` 看不看得到、两次 `agent_send` 的先后都不是合同。
- **如何核实**：读 tools.ts:181-217 与 238-252；实验思路：同一回复 `[agent_spawn{async}, jobs]`，让 `nbook.agent.spawn` 的提供方在这个会话第一次用、工厂 `create` 返回一个晚一个宏任务才完成的 Promise，`jobs` 先读任务表，看不到前者（从代码推断，未跑）。
- **建议改法**：让顺序保证落到插件实现上，二选一：(a) 包装加同步快路径：`#published` 里有句柄且 `#built` 已就绪（`implementation` 已完成，记一个同步可读的值）时，同步调用真正的 `execute`，不经过任何 await；第一次用的工具在 `AgentTools` 层按会话排队，保证同一段里的调用按到达包装的先后进入实现。runtime 输出 86 的测试同时覆盖“经过 Agent 插件包装”这一层。(b) 不依赖进入顺序：内核在 `ToolContext` 里给出调用在这条回复里的位置（例如 `reply: {id, index}`，`id` 用 `assistant` 事件 id），子代理工具按位置自己排队。(b) 还顺带解决第 4 条的调用 id 不唯一问题。

## 4. 改成随机 id 之后，`tree`、卡片与重启找回都改按（父会话、`callId`）认子会话，而第 51 条的理由正是 `callId` 跨回复会重复；`fork` 子会话又制造出同 `callId` 的第二个子会话

- **严重程度**：重要；**类别**：接口 / 正确性；第一轮第 4、13、14 条处理后引入
- **位置**：`docs/specs/agent/subagents.md:104`（输出 21 每项带 `callId`）、`subagents.md:109`（输出 23，fork 照抄 `caller`）、`subagents.md:110`（输出 24，按调用 id 找回）、`subagents.md:164`（验收 7）；`docs/specs/agent/resources.md:74`（输出 13）；`plan.md:125`（卡片“`agent_spawn` 按（父会话、`callId`）”找自己）；README 第 51 条
- **现象**：
  1. 第 51 条的理由原文：“服务商在不同回复里给出重复的调用 id 时反而会把新任务发进旧子会话”。调用 id 的合同只是“同一条回复里不重复”（`packages/nb-harness/src/kernel/api/tool.ts:37`）。同样的前提下，同一个父会话里两次 `agent_spawn` 的子会话头都可能是 `caller.callId: "call_0"`：`tree` 两项 `callId` 相同，卡片按（父会话、`callId`）找到两个，重启后 `sessions://` 根里两个子会话标着同一个调用 id。
  2. 输出 23 定了 fork 子会话得到的新会话仍是同一父会话的子会话、会话头照抄 `caller`（含 `callId`），所以用户 fork 一次子会话，`tree` 里就有两项同 `callId`，卡片同样认不出哪个是自己的。
- **为什么是问题**：卡片在运行中（没有工具结果之前）只能靠这把键找子会话；找错会把别的子会话的进度画到这张卡上。重启找回的唯一线索也是它。第 51 条拿掉了确定性 id，却把同一个不唯一的键搬到了界面与恢复上。
- **如何核实**：读 tool.ts:37 与 runtime.md 输出 37；脚本化模型让两条回复各带一个 id 为 `call-1` 的 `agent_spawn`（第一轮第 4 条的复现方法），`tree` 交回两项 `callId` 相同。
- **建议改法**：给调用一个内核保证唯一的身份。`toolStarted` 已经有 `invocation: core.newId()`（`packages/nb-harness/src/kernel/run/tools.ts:332`），把它放进 `ToolContext`（内核小改，写进 runtime 与 extensions），会话头的 `caller` 加 `invocation`（或用 `assistant` 事件 id 加 `callId`）；`tree`、卡片、`sessions://` 根都按它认。fork 出来的子会话：`caller` 照抄但 `tree` 标出 `origin`（来源会话），卡片只认没有 `origin` 的那一个，或在输出 23 里写明卡片跟随哪一个。

## 5. “一个任务就是一次运行”要知道 `runId`，但插话进在跑的运行时 `send` 交回 `runId: null`，`resolve` 不交回 `runId`：任务关联与 `waitRun` 都缺内核机制

- **严重程度**：重要；**类别**：正确性 / 接口；第一轮第 2、17 条处理后引入
- **位置**：`plan.md:62`（“记下 `runId` 填进任务”）、`plan.md:64`（等待用 `waitRun(runId)`）、`plan.md:66`（续用）；`docs/specs/agent/subagents.md:81-83`（输出 10–12）、`docs/specs/agent/jobs.md:70`；代码 `packages/nb-harness/src/kernel/api/host.ts:29`、`:35`，`packages/nb-harness/src/kernel/run/commands.ts:107`，`packages/nb-harness/src/kernel/run/interaction.ts:129-156`
- **现象**：
  1. `send` 在子会话不空闲时交回 `{inputId, runId: null}`（commands.ts:107）。输出 10 的“插话、`queue: true` 都关联到这次运行的任务”与“用户开的运行登记一个任务”都要知道“这次运行”的 `runId`，内核不给，插件只能事后查快照的状态：这之间运行可能已结束（`queue: true` 的 followup 让同一运行再开一轮，loop.ts:380-382，还好；但被中止时缓冲区被清空，见第 11 条），查到的就不是放话时那次运行。
  2. `resolve` 的值是 `{}`（host.ts:35）。应答异步提问在子会话空闲时由内核决定开新运行（或让暂停的运行接着跑），`runId` 只在受理批的 `runStarted` 里（interaction.ts:137-146）；没有模型可用时（`startProblem` 非空）回答只入队、不开运行，`resolve` 照样成功。插件拿不到 `runId`，也分不清这次应答到底开没开运行，输出 11、12 的“开新一轮时登记新任务”“先查上限再动子会话”都无从判断。
  3. 子会话被用户回退到运行中途时，`send`、`start`、`resolve` 都让暂停的旧运行接着跑（commands.ts:109-110、136，interaction.ts:140-141），交回的是旧 `runId`；“空闲时开新一轮就是新任务”与内核的“同一个 `runId`”对不上。
- **为什么是问题**：任务与运行一一对应是第一轮第 2 条修法的核心；照计划实现，只有“空闲时 `send`”这一条路径能拿到可靠的 `runId`，其余路径要靠事后查快照猜，猜错了任务的结束、`question` 与 `waitRun` 全对不上。
- **如何核实**：读上面几处；脚本化模型：子会话在跑时父会话 `agent_send{message}`，`send` 的值里 `runId` 是 null。
- **建议改法**：内核加第五处小改：`send`、`enqueue` 在有运行（或暂停的运行）时交回它的 `runId`；`resolve` 在开了（或续了）运行时交回 `runId`，没开时不给。写进 runtime.md 与 host.ts 的 `CommandMap`。Spec 输出 10、11 改成按交回的 `runId` 判定“同一运行还是新运行”，并写明暂停的运行接着跑算哪种（建议算原任务已移出时登记新任务、沿用旧 `runId`）。

## 6. `wait` 对停在 `question` 的任务每次都立即返回，而 `wait` 又被豁免重复检测：模型不答提问只想等别的任务时会空转

- **严重程度**：重要；**类别**：正确性；第一轮第 3 条处理后引入
- **位置**：`docs/specs/agent/jobs.md:50`（输出 3“有已经结束、还没取过的，或状态是 `question` 的，立即交回它”）；`docs/specs/agent/run-guards.md:68`（输出 14，`wait` 与上一条相同时不算重复、也不清计数）；`plan.md:55`
- **现象**：“已结束未取过”交回一次就标为取过，下次不再立即返回；`question` 没有对应的“取过”，任务一直停在 `question`（同步提问没有时限，子会话一直等）。父 Agent 派了 A、B 两个后台子代理，A 提问，父 Agent 决定先等 B 结束再答 A：每次不带 `jobs` 的 `wait` 都立即交回 A 的 `question`，一次请求接一次请求地空转，直到费用上限；重复检测因为 `wait` 被豁免而不会停它。带 `jobs: [B]` 能避开，但这要模型自己想到。
- **为什么是问题**：第一轮第 3 条要的是“`wait` 开始前就已在等的提问不漏掉”，修成了“每次都立即交回”；与输出 14 的豁免叠在一起，正好是 run-guards 想防的无效循环。
- **如何核实**：对照 jobs.md 输出 3 与 run-guards 输出 14；脚本化模型：两个后台子代理，一个停在 `question`，父会话连续三次 `wait`（不带 `jobs`），三次都立即以 `question` 返回。
- **建议改法**：按提问事项记“已交回过”：同一个事项 id 的 `question` 只在第一次 `wait`（或前台返回）时算立即返回的理由，之后的 `wait` 只把它列在“其余任务的状态”里、继续等别的条件；或者 run-guards 输出 14 的豁免只在 `wait` 交回的结果与上一次不同时成立。

## 7. 费用的树累计：“索引汇总 + 反应加增量”两个来源会重复或漏记；fork 子会话把复制来的用量再算一遍；口径漏了 `modelFailed`

- **严重程度**：重要；**类别**：正确性；第一轮第 5 条处理后引入
- **位置**：`plan.md:29`（索引 `spend` “随 `assistant`、`modelEnded` 累加”）、`plan.md:92`（cost-guard：按根会话的内存表，启动与打开会话时从索引汇总，之后各会话的反应加增量）；`docs/specs/agent/run-guards.md:67`（输出 13）；`docs/specs/harness/session.md:137`（输出 22）；`docs/specs/harness/runtime.md:136`（输出 70）；`docs/specs/agent/subagents.md:109`（输出 23）
- **现象**：
  1. **两个来源。** 内核每次 `append` 后写索引（`packages/nb-harness/src/kernel/log/jsonl-store.ts:279-280`），反应在写入批之后才派发。计划在“启动与打开会话时”从索引重新汇总，又在反应里加增量。若汇总是“替换”：会话 Y 的 `assistant` 已写进索引、Y 的反应还没跑时另一个会话打开触发汇总，汇总已含这笔，随后 Y 的反应再加一次，重复；汇总读的是一组文件（`LogStore.list` 逐个读 `index.json`，jsonl-store.ts:288-300），读的过程中 Y 写了一笔并加了增量，汇总完成后替换掉，又漏一笔。若汇总是“累加”：打开一次会话就把整棵树重复加一次。计划两种都没写。
  2. **fork。** runtime 输出 70：fork 把复制来的路径上的用量算进新会话。输出 23 又规定 fork 子会话得到的新会话仍在同一棵树里。用户 fork 一个花了 $3 的子会话，树累计凭空多 $3，可能直接触发上限。
  3. **口径。** runtime 输出 70 按 `assistant`、`modelEnded`、`modelFailed` 三种事件累计（`modelFailed` 也带 `usage`，例如流到一半失败）；plan.md:29 与 92 只写了前两种，现有 cost-guard 对三种都反应（`packages/neuro-book/src/plugins/agent/backend/guards/cost-guard.ts:41-44`）。session 输出 22 写“同快照口径”，计划与它不一致。
- **为什么是问题**：上限是要真拦请求的（验收 10），累计数偏大会误停整棵树、偏小会放过；这类误差只在并发与打开会话交错时出现，测试很难稳定复现。

## 12. 中止“不等子会话收口”留下的窗口：紧接着的 `agent_send` 放进正在中止的子会话，话会被中止清掉；父会话中止还会连带用户自己在子会话里开的运行

- **严重程度**：建议；**类别**：正确性；第一轮第 7、17 条处理后引入
- **位置**：`docs/specs/agent/subagents.md:93`（输出 16：立即以 `aborted` 返回、不等子会话收口）、`subagents.md:81`（输出 10：插进在跑的运行，“用户在子会话里自己开的运行，这时登记一个归调用方的任务”）；`plan.md:65`；代码 `packages/nb-harness/src/kernel/run/commands.ts:166-172`
- **现象**：
  1. 内核的 `abort` 先等运行收口，再把此刻缓冲区里的全部输入写成 `inputRemoved{reason: "aborted"}`（不带 `keepQueue` 时，commands.ts:167-169）。子会话收口要经过它自己的工具宽限期 2 秒、模型端口 2 秒，有孙会话时再叠一层。父会话被中止后用户马上让它接着做，或父 Agent 先 `kill` 再 `agent_send`（如果 `kill` 也不等收口），这段时间里 `agent_send` 看到子会话“在跑”，按插话放进缓冲区（`runId: null`），随后被这次中止清掉；`agent_send` 关联的是正在中止的那次运行，交回 `aborted`，模型以为子代理又被停了一次，话其实丢了。
  2. 用户在子会话里自己开了一次运行，父 Agent `agent_send` 插话进去（登记了归父会话的任务、前台等它）；用户随后中止父会话，按输出 16 这次“正在前台等的子代理运行”跟着中止，被停的是用户自己开的运行。
- **为什么是问题**：两种情况用户都看不出原因：话丢了、自己的运行被别处停了。
- **如何核实**：读 commands.ts:157-182；对照输出 10、16。
- **建议改法**：插件对子会话发 `abort` 时带 `keepQueue: true`，或 `agent_send`、`agent_answer` 遇到子会话处于 `aborting` 时先等它收口再放话（等待有上限，例如 10 秒，超了得一个可重试的码）；输出 16 的连带只对父会话自己启动的运行（任务由派发或空闲时的续用登记），插话附着到用户开的运行时不连带，写进 Spec。

## 13. 内核第 4 处对审批重判与异常路径的影响没写：重新询问被串成一个接一个；第 i 个以异常离开时后面的调用可能永远等着

- **严重程度**：建议；**类别**：正确性 / 文档
- **位置**：`docs/specs/harness/runtime.md:153`（输出 86）；`plan.md:31`、`plan.md:186`；代码 `packages/nb-harness/src/kernel/run/tools.ts:283-287`、`316-332`、`402-412`

## 16. 结束而没取过的任务要留到 `wait`，但只按会话限 32 个，没有全局上限，结果全文常驻内存

- **为什么是问题**：第一轮第 8 条的修法去掉了唯一的回收点，换来的上限只管单个会话。
- **如何核实**：对照 jobs.md 输出 6 与 plan.md:54。
- **建议改法**：任务记录只存身份与终态（`sessionId`、`runId`、`reason`、`shell` 的退出码与行数），结果在 `wait` 交回时再读（子代理用 `waitRun(runId)` 从日志取，`shell` 读 `status.json` 与输出文件）；另加一个全局上限（例如 1,024 条），满了丢最早结束的。

## 17. 关系表的启动扫描是异步的：扫完之前的深度检查、`tree` 与费用表都按“没有父子”算，扫描期间新建的子会话可能被扫描结果覆盖

- **严重程度**：建议；**类别**：正确性
- **位置**：`plan.md:61`（“启动时扫一次索引，之后由派发与 `fork` 增量更新”）、`plan.md:92`（费用表“启动……时从索引的 `spend` 汇总”）；代码 `packages/nb-harness/src/kernel/log/jsonl-store.ts:288-300`
- **现象**：`LogStore.list` 逐个读每个会话目录的 `index.json`，会话多时要一段时间。计划没写扫描与服务开门的先后：若插件先开门、后台扫描，扫完之前深度为 3 的子会话被当作根（深度 0），能再派出第 4、5 层；费用表为空，上限不生效；`sessions://` 根找不到子会话。若扫描结果在完成时整体替换内存表，扫描期间派发或 fork 增量登记的关系会丢（`list` 读到它的 `index.json` 与否取决于读到那个目录的先后）。
- **为什么是问题**：深度与费用上限是防失控的兜底，恰在进程刚重启、用户让 Agent“接着干”时失效。
- **如何核实**：读 jsonl-store.ts:288-300；对照 plan.md:61、92。
- **建议改法**：计划写明：扫描在 `nbook.agent` 启动时完成、之后才开门（或子代理工具与 `tree` 在扫描完成前等它）；扫描结果与扫描期间的增量登记合并（按会话 id 取并集，增量优先），不整体替换。
