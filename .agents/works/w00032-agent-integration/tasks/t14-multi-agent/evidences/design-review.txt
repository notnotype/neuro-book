### 1. 子代理审批继承规则与“审批一律交给用户”互相冲突
**严重程度**：阻断；**类别**：正确性

**位置**：`.agents/works/w00032-agent-integration/tasks/t14-multi-agent/README.md` 决定 8、确定的工具后的规则；`t06-approval/README.md` 决定 1、8。

**现象**：t14 同时规定“审批一律交给用户，父 Agent 不审批”，又规定“子会话继承父会话当时的审批模式与 Agent 模式”。t06 已定的审批模式包含“每次都问、放行写入、交审批模型、全部放行”，而且 Profile 和会话都能设置审批模式。

**为什么是问题**：父会话若处于“全部放行”或“交审批模型”，子会话的审批就不会交给用户；若强制冒泡给用户，又没有说明继承的审批模式如何被覆盖。照字面实现会出现同一工具在父会话与子会话两套判定链上得到不同结果，尤其无法确定 `yolo` 下子代理是否仍弹用户审批。

**如何核实**：逐条对照 t14 第 8 条及“子会话继承”规则与 t06 决定 1、8；t20 提案第 9 节还明确审批在工具拦截链最里层判定，未定义子会话的特殊覆盖层。

**建议改法**：明确唯一规则：父会话只继承 Agent/只读模式，还是同时继承审批模式；若子代理审批必须用户应答，就把它定义成 t06 判定链之后的“用户冒泡”而非新的审批模式，并规定自动放行、审批模型、拒绝规则在子会话中的优先级和日志记录。
### 2. t20 的新交互通道没有落到 v5 的公开类型合同
**严重程度**：阻断；**类别**：接口

**位置**：`docs/proposals/agent-harness-event-model.md` 第 11 节和待定项 14；`.agents/works/w00032-agent-integration/tasks/t20-hooks/spike/v5/api.ts` 的 `KernelEvents`；`v5/host.ts` 的 `RunStatus`。

**现象**：提案已经要求 `interactionRequested`、`interactionResolved`、`resolve`，并把运行状态扩为 `waiting`；但 v5 类型仍声明旧的 `asked`、`answered`、`approvalRequested`、`approvalResolved` 四个事件。`RunStatus` 只有 `idle`、`running`、`aborting`，没有 `waiting`，`SessionMirror.AttentionItem` 也没有待处理交互项。

**为什么是问题**：t14 明确要求子会话和父会话都能看到待处理审批/提问，且重启后继续等待。照现有 v5 合同实现，事件名称、状态枚举和界面镜像都无法表达这个状态；实现者要么改 v5（牵动 t20 已认可的接口），要么在 Agent 插件另造一套事件，违反“子代理工具对照 v5 会话接口”的决定。

**如何核实**：读取提案第 11 节的交互事件与 `resolve` 规则，再读取 `api.ts:89-119`、`host.ts:87-121`、`host.ts:355-373`；前者是四个旧占位事件，后者没有 `waiting` 或 pending interaction 字段。

**建议改法**：在 t20 的正式接口中一次性定义交互项的 id、callId、kind、request、允许的应答者、状态和失败码，并同步更新 `KernelEvents`、`RunStatus`、快照、帧、镜像和恢复合同；t14 只引用这套类型，不再把“完整形状在实施计划里定”留成跨 Task 的隐藏接口。
### 3. 异步提问的 `replyTo` 没有闭环语义，重复回答和回退都会失控
**严重程度**：阻断；**类别**：正确性

**位置**：t14 决定 17、18 与确定的 `agent_answer`；`docs/proposals/agent-harness-event-model.md` 第 11 节；`v5/api.ts` 的 `UserInput`、`inputQueued`、`input` 与 `steer`。

**现象**：提案规定异步 `ask` 的回答是普通输入并带 `replyTo`，但 `UserInput` 仍只有 `text`、`payload`、`attachments`，所有输入事件也没有 `replyTo`。更重要的是，普通输入路径没有说明是否同时写 `interactionResolved`：若不写，原问题永久保持待处理；若写，需定义回答者、重复回答的原子竞争和失败码。

**为什么是问题**：t20 的 `resolve` 合同要求 `unknown-interaction`、`already-answered`、`not-allowed`，而 `replyTo` 走的是 `send`/输入缓冲区，天然支持编辑、删除、steer、followup 和重放。回答在同一问题上重复投递、问题所在路径被回退、进程重启后重放回答时，可能被当成多条普通用户消息，或一条回答已执行但问题仍可再次回答。问题被交给父 Agent 时还没有定义这条输入怎样跨子会话送达。

**如何核实**：对照提案第 11 节第 493 行与 t14 第 17、18 条，再读 `api.ts:26-30`、`92-105`；类型和事件中没有 `replyTo`，也没有由 `replyTo` 归约为 resolved 的规则。

**建议改法**：把异步回答建模成带问题 id 的专用输入合同（仍可作为普通输入显示，但必须由内核原子校验并写 `interactionResolved`），明确问题的会话、所有权、当前叶子、允许回答者、重复回答结果和回退后的结算；父 Agent 的代答必须通过同一条受鉴权的解析入口。
### 4. 非异步提问返回后没有“答完并取得最终结果”的生命周期
**严重程度**：阻断；**类别**：接口

**位置**：t14 确定的 `agent_spawn`、`agent_send`、`agent_answer`；“不带 `async`”的返回规则。

**现象**：`agent_spawn`/`agent_send` 遇到“提问交给调用方”就返回问题；`agent_answer` 只写子会话的 `resolve`，没有返回最终结果，也没有说明子会话恢复后是否仍是原工具调用的等待方。此时该子会话既不是 `async` 创建的任务，也不是用户插话转后台时才产生的任务 id。

**为什么是问题**：父 Agent 答完后无法按确定的接口拿到子代理的最终 `yield`/最后回复：调用 `wait` 需要任务 id，但问题返回路径没有任务 id；再次调用 `agent_send` 可能是启动一轮新消息，也可能被实现成继续原调用。强制结构化模式还没有说明答完后何时重新执行“缺少 `yield` 的催一次”规则。照字面实现必然需要新增隐藏的 `resume`/任务转换语义，破坏第 13 条“不要 `agent_continue`”的决定。

**如何核实**：只按 t14 表格和返回规则推演：`agent_answer` 的返回类型未列，`wait` 的输入只有任务 id，非异步提问分支没有任务 id 产生时机；t20 的 `resolve` 只描述会话恢复为运行，没有 Agent 工具结果回流合同。

**建议改法**：定义一次明确的状态转换：问题返回时即生成稳定的子运行/任务 id，`agent_answer` 返回“已受理”并允许父用 `wait` 取得最终结果；或者规定 `agent_answer` 阻塞到本次子运行结束。写明强制 `yield` 的催促次数、最终终止原因、重复 answer 和子会话被杀/出错时的返回码。
### 5. “用户插话即返回任务”违反 t07 的批次取走时序
**严重程度**：重要；**类别**：正确性

**位置**：t14 `agent_spawn`/`agent_send` 的不带 `async` 返回条件；t07 决定 1；t20 第 1、3 节的输入缓冲区与边界顺序。

**现象**：t14 说父会话收到用户插话时，正在等待的子会话转进任务中心并立即把任务 id 返回；t07 已定用户插话在当前工具批次之后、下一次模型请求时才送达，t20 又规定输入先进入缓冲区，运行边界才取走。

**为什么是问题**：如果父 Agent 在同一回复里并发派出多个子代理，用户消息到达时它只能先进入父会话缓冲区，不能在“当前工具批次之后送达”。实现者无法判断应当在消息入缓冲区时打断 `agent_spawn`、在整批工具结果写完后打断，还是等父会话下一次边界；三种选择会分别破坏 t07 的批次原子性、t20 的取走规则或 t14 的即时返回。返回任务 id 后，父 Agent 是否能在同一批次继续调用 `agent_send`/`wait` 也没有定义。

**如何核实**：按 t20 的顺序构造“父回复包含两个 shared `agent_spawn`，工具执行中用户提交输入”的时序；t07 只允许输入在批次结束后送达，而 t14 没有定义一个不改变父会话状态的旁路通知。

**建议改法**：把“用户插话”拆成已入队与已送达两个状态：工具调用只在当前批次完整结算后观察入队标记，并规定哪些正在等待的工具返回任务 id；或者取消非异步调用因用户输入提前返回的特殊分支，统一由 `async`/任务中心处理。
### 6. 用户与父 Agent 同时回答同一交互时没有可信的仲裁合同
**严重程度**：重要；**类别**：不变量

**位置**：t14 决定 8、9、17 与规则；t20 第 11 节的 `resolve`；t07 决定 4。

**现象**：同一个待处理区同时允许用户直接答、父 Agent 用 `agent_answer` 答，审批只允许用户但审批项又出现在父会话界面。提案只写 `resolve` 带 `by`，没有定义 `by` 如何由宿主身份签发，也没有规定两个来源同时提交时谁先占用交互。

**为什么是问题**：不能让调用方在参数里自报“用户”或“父会话”；否则父 Agent 可伪造用户审批，或者任意会话用一个问题 id 答题。若用户在父界面输入文字而父 Agent 也调用 `agent_answer`，t07 的“等审批输入等于拒绝、等提问输入作为回答”与父会话自己的输入缓冲区会同时竞争，最终可能出现两条回答、一次拒绝和一次通过，或父模型收到错误的工具结果。

**如何核实**：t20 的 `resolve` 失败码只有文字级的 `not-allowed` 方向，没有调用方凭证、交互所有者、原子 compare-and-set 或获胜者事件；t14 的 `agent_answer` 参数只有 `id`、`question`、`answer`，没有来源字段。

**建议改法**：由服务端从已认证的会话/用户连接注入 `by`，调用方不能传；给每个交互绑定 owner、允许答题者和单调版本，所有回答走同一个原子解析命令，竞争失败稳定返回 `already-answered`，并规定父会话输入框在等待子问题时的路由。
### 7. 待处理审批/提问在插件撤回、中止和父回退时没有结算路径
**严重程度**：重要；**类别**：遗漏

**位置**：t14 确定的工具后的规则；t04 决定 6；t07 决定 2、6、7；t20 第 11、14 节。

**现象**：t04 已定“等审批或等回答的调用，其工具被卸载时按 `tool-unavailable` 结算”，t10 又规定插件停用时执行中的调用由内核结算；但 t14/t20 只规定交互写日志并等待，未定义撤回时由谁写 `interactionResolved`、`toolResult` 和父工具结果。父会话回退时也没有说明独立子会话是否中止、其结果是否还能回流。

**为什么是问题**：一个待处理事项可以同时占住子会话的 `waiting`、父 Agent 的同步工具调用和任务中心的任务。若插件撤回只结算工具而不结算交互，父同步调用永久挂起；若父回退后仍允许子会话完成，结果会回流到已经不存在的父工具调用；若自动拒绝，又必须区分用户拒绝、插件不可用和中止，不能伪装成普通回答。

**如何核实**：对照 t04 决定 6 的 `tool-unavailable` 与 t20 第 11 节“全部处理完才回到运行”、第 14 节插件撤回语义；后者没有交互 pending 项的取消事件，也没有父子边回退/失效规则。

**建议改法**：为 interaction 增加系统结算原因（`tool-unavailable`、`aborted`、`owner-rewound`、`session-closed` 等）和一次性状态转换；规定父工具调用、子会话运行、任务中心任务三者的收口顺序，并明确回退只影响父日志还是连带取消子运行。
### 8. `shared` 并发没有进入工具声明，且没有同资源冲突语义
**严重程度**：阻断；**类别**：不变量

**位置**：t14 决定 6、17；t04 工具声明字段；t20 第 9 节第 436 行；`t20-hooks/spike/v5/api.ts` 的 `ToolInfo`。

**现象**：t14/t20 规定连续 `shared` 调用并发、`exclusive` 单独执行，但 v5 `ToolInfo` 只有 `name` 与 `effect`，没有并发字段或其可用值。更没有规定 `shared` 是否只允许读：`effect` 允许 `write` 和 `exec`，所以两个 shared 写调用、一个写一个读、两个子代理同时编辑同一文件都合法。

**为什么是问题**：结果按调用顺序写入不等于副作用按调用顺序发生。一个并发写可能覆盖另一个，读可能看到任意中间状态；bash 还绕过文件服务与 nb-history。若以 `shared` 表示“工具本身线程安全”，它无法吸收不同调用的资源冲突；若只依赖文件服务的条件保存，shell 和跨会话写入仍没有同一基线、锁或结果未知策略。

**如何核实**：读 `api.ts:42-53` 可见 `ToolInfo` 无 concurrency；读 t04 决定 7 可见工具声明确实包含“并发”字段，但未给出合同；读 t08 资源文件失败合同和 t12 shell 决定可见资源冲突与 shell 绕过仍是不同路径。

**建议改法**：先把 `concurrency: "shared" | "exclusive"` 写进工具声明并规定默认值、同批限制和审批等待行为；安全选项是 `shared` 只允许无副作用工具。若允许写，必须声明资源键/锁或统一使用文件服务的条件写入，并把冲突、部分完成和未知结果按 t08/t07 的失败码回流。
### 9. Agent 工具没有沿用 t20 的 `commandId` 幂等合同
**严重程度**：阻断；**类别**：接口

**位置**：t14“确定的工具”表；t20 第 3 节与 `v5/host.ts` 的 `SessionCommands`。

**现象**：t20 要求每个远程写指令带 `commandId`，链路断开后可用同一 id 重发并得到第一次结果；`agent_spawn`、`agent_send`、`agent_answer`、`wait`、`kill`、`jobs` 的参数和返回没有 command id、重放标记或幂等合同。

**为什么是问题**：远程服务在“子会话已经创建但父工具没收到返回”时重试 `agent_spawn` 会创建两个子会话；`agent_send` 可能重复插话或排两条 followup；`agent_answer` 可能与用户回答竞争。用户要求的“同一子会话被两个父工具调用或用户同时操作”也无法靠 t20 的单会话写者解决，因为重复的 Agent 工具命令在进入子会话前就已产生多个副作用。

**如何核实**：读取 `host.ts:78-80` 的统一 `commandId` 入口，再逐项对照 t14 工具参数表；只有 `id`、`question`、`job` 等业务标识，没有一次调用的幂等键或 `replayed` 返回字段。

**建议改法**：把每个会改变会话/任务中心状态的 Agent 工具调用包装成宿主指令，使用调用方生成的 `commandId` 和按工具分类的失败码；返回创建的 child/job id、是否重放及最终状态。对 `wait`/`jobs` 的查询可定义幂等读，但 `kill` 仍需稳定的已完成/已不存在结果。
### 10. 任务中心只有“等到一个”定义，没有结果、终止原因和超时合同
**严重程度**：重要；**类别**：接口

**位置**：t14 任务中心的 `wait`、`kill`、`jobs` 表；t22 已定部分；确定的 `agent_spawn` 返回规则。

**现象**：`wait` 只说返回最先结束的一个，`jobs` 只列 id、种类、状态、开始时间和一行摘要；没有定义结束项的结构化结果、`completed/error/aborted/interrupted/timeout` 终止原因、子会话问题、强制 `yield` 失败详情、结果全文地址或“结果已消费”后的寿命。`kill` 也没有成功、已结束、未知和无权限的失败码。

**为什么是问题**：异步子代理完成后，父 Agent 可能只得到一行摘要，无法取得 Profile schema 要求的结构化结果；超长结果虽说全文进 `session://artifacts/`，却没有明确是子会话还是父会话的路径，且工具结果被截断后如何引用未定义。父 Agent 无法区分“子代理正常交回 error 结果”和“任务中心杀死/进程崩溃”，也无法决定是否重试。

**如何核实**：逐项对照 t14 的三个工具参数/行为表和 `agent_spawn` 的结果段；t22 只把通知、寿命、上限、活动面板留待重开，没有补任务结果合同；调研中 Gemini 明确带终止原因，omp 明确有结构化 `yield` 与全文地址，t14 没有同等字段。

**建议改法**：定义统一 `JobResult`（任务类型、job/session/run id、状态、终止原因、结构化/文本结果、截断与 artifact URI、details、可否重试），规定 `wait` 返回一次还是可重复读取，以及 `jobs` 是否只给摘要；所有失败按代码返回，不用一行自然语言承担状态机。
### 11. Workflow 调用 Agent 没有提问与后台的对接合同
**严重程度**：阻断；**类别**：接口

**位置**：t14 决定 22；t10 决定 7 的 `agent.startTask`；t14 决定 9、10、19。

**现象**：t14 规定 Workflow 经 `agent.startTask` 调 Agent，且这类会话的调用方是 Workflow；但 t10 的公开方法只有 `profile`、`initial`、`input`、`project?`、`background?`，返回 `session id` 与 `TurnResult`，没有 `questions`、交互回调、`agent_answer` 或 `replyTo` 处理。t14 又规定提问缺省交给调用方，即这里应交给 Workflow；同时 t14 要求可后台工具统一使用 `async`，t10 仍使用 `background?`。

**为什么是问题**：Workflow 不是拥有 Agent 工具的模型会话，无法按 t14 的 `agent_answer` 回答子问题，也不知道同步 `startTask` 在提问时应返回什么。若把问题交给用户，会改变“缺省交给调用方”；若让 Workflow 自动回答，必须给它回答协议和失败/中止处理。后台参数若保留两套，Workflow 和 Agent 的任务中心会出现两个任务生命周期。

**如何核实**：逐条读取 t10 决定 7 与 t14 决定 9、10、19、22；两份合同的参数名和调用方模型不一致，t22 也只取代草稿中的 `background: true`，没有更新 t10 的已定远程接口。

**建议改法**：为 `AgentPort.startTask` 定义调用方能力（同步结果、交互回调/用户转交、取消、进度和后台 job id），明确 Workflow 负责回答还是只能把问题冒泡给用户；统一 `async`/`background` 的一个命名和任务中心映射，并规定 `TurnResult` 与 Agent `yield` 的转换。
### 12. `sessions://` 的整目录映射把“可见性”退化成了知道 id 即可读
**严重程度**：阻断；**类别**：安全与隐私

**位置**：t14 决定 7、12 与资源地址表；t08 方案表及“另定的两条”。

**现象**：t14 把 `sessions://<id>/` 改成整个真实会话目录，包含 `session.jsonl` 和 `home/`，并说 Agent 可直接读原始日志；根目录只在列表上优先展示父、子、兄弟，其余会话分页。t08 原方案同时规定“自己的读写、别人的只读”，且明确日志在 `home/` 外，Agent 不能直接读写，别的会话对话记录要等 t14 另定。

**为什么是问题**：目录映射和根列表是两层机制；只要 Agent 获得任意会话 id，就能绕过“有关会话/最近使用”的列表范围读整本会话日志、附件、工具大结果和 Profile 私有内容，跨书泄露也没有租约、用户/项目边界或敏感字段过滤。t23 的访问规则还搁置，t14 却把最宽的访问能力先写成默认地址合同，后续收窄会牵动资源提供者、提示词和所有审计。

**如何核实**：读取 t08 方案表第 55-59 行、第 110-113 行与 t14 第 12 条、第 119 行；前者只给别人的只读且禁止直接读日志，后者把同一真实目录全部暴露。当前资源 Spec 还要求不向 Agent 暴露状态根、数据库和凭据。

**建议改法**：先定义会话访问策略再定 URI：至少校验调用方与会话的父子关系、同一书/项目租约和用户授权，日志与 `home` 分开声明能力；无授权时返回明确 `not-allowed`，而不是依赖 id 不可猜。若 t14 坚持原始日志直读，应把它作为 t23 的受限能力并写脱敏、审计和跨重启合同。
### 13. bash 工作目录改成 `project://` 后，既有计划模式与环境变量示例失效
**严重程度**：重要；**类别**：正确性

**位置**：t14 决定 15；t08 方案表、用例与后续修改；t12 shell 决定。

**现象**：t14 把有项目会话的 shell 当前目录改为 `project://`，但 t08 的规则仍把 `session://` 定义为 bash 工作目录，示例仍要求计划写 `session://plan.md`、中间文件写 `tmp://`；t12 只说会替换命令中的地址并提供 `$NBOOK_PROJECT`、`$NBOOK_SESSION`，没有规定相对路径如何映射或是否禁止把会话路径当 cwd。

**为什么是问题**：模型照既有示例运行 `cat > plan.md`、`python script.py` 或相对路径 `rg`，现在会读写作品目录而非会话 home。计划模式原本明确写 `session://plan.md` 不算作品写、无需审批；改成相对路径后变成项目写，需按 t06 审批。没有项目时又回退到 `session://`，同一条命令在两种会话上下文中有不同副作用，形成隐含的项目存在分支。

**如何核实**：对照 t08 第 57、94、97 行与后续修改第 118 行，再读 t12 第 47-48 行；后续修改只写了新 cwd，没有同步修改地址替换、计划示例、只读判断和 `$NBOOK_SESSION` 的优先级。

**建议改法**：明确 shell 的 cwd 是资源地址还是绝对路径、相对路径的唯一根、`$NBOOK_PROJECT`/`$NBOOK_SESSION` 的定义及白名单命令能否跨根；更新所有示例。若保留 `project://` cwd，计划/临时脚本必须显式使用 `$NBOOK_SESSION`/`tmp://`，并在只读/审批判定中按解析后的真实目标判断。
### 14. 子会话、后台任务与父会话的中止/重启边界没有统一
**严重程度**：重要；**类别**：遗漏

**位置**：t14 决定 4、10、14、19 及末尾规则；t07 决定 2、7；t22 已知情况与 t20 第 2 节恢复。

**现象**：t14 说父会话中止时其子会话运行一起中止，`kill` 只杀任务不删子会话；但没有说明用户插话后转入任务中心的子任务是否仍受父中止影响，也没有区分直接子会话与孙会话。t22 草稿又说服务端重启、Agent 插件停用时后台任务结束并记“已中断”，而 t20 规定日志恢复、缓冲区保留、未完成工具结算为 unknown。

**为什么是问题**：同一运行在父会话、子会话和任务中心有三个生命周期。父 abort、子 job kill、插件停用、服务端崩溃的先后不同，会产生“任务已被杀但子日志仍可继续”“父已恢复但后台 job id 丢失”“孙代理继续消耗模型额度”等状态。重启后若只按日志恢复，任务中心的非持久状态无法把结果或 pending interaction 重新绑定回父工具调用。

**如何核实**：按“父 spawn async → child spawn grandchild → 用户向父插话转后台 → 父 abort → 服务端重启”的顺序对照 t14、t20 `recover()` 和 t22 寿命草稿；没有唯一的所有权树、取消传播、任务持久化或结果未知规则。

**建议改法**：定义 job/session/run 三层的状态机和父子边：detach 是否解除取消继承、abort 是否递归、`kill` 的边界、重启后哪些任务恢复/终止；为每次运行持久化稳定 job/run id，恢复时要么可观察地结算为 interrupted/unknown，要么明确不可恢复且通知父会话。
### 15. 只有深度上限，没有宽度、额度和并发上限
**严重程度**：重要；**类别**：性能与资源

**位置**：t14 决定 3、21；t22 已知情况；调研报告第 2.7 节。

**现象**：t14 允许“有派生工具就能再派”，缺省最多 3 层，且上限可在 Agent 设置中改；没有每个父会话的子代理数、全局活动任务数、模型请求数、token/费用、超时或队列长度上限。

**为什么是问题**：深度 3 不限制宽度：根 Agent 可以在一个回复中派任意多个子代理，每个子代理再派任意多个孙代理，任务中心和模型额度会按宽度指数增长；`shared` 并发还会把这些调用同时启动。可调的“安全上限”若能调高或设为无限，就不再是安全上限。调研中的 Claude Code、Codex、DeepSeek Harness 分别有 20、6、8 的并发上限，t14 没有替代机制。

**如何核实**：读取 t14 第 3、21 条与 `agent_spawn` 参数表，没有 count/budget/timeout；读取调研第 2.7 节，参照实现明确记录了并发上限。

**建议改法**：定义硬性的全局活动任务上限和每会话/每 Profile 的子代理上限，再分别定义模型请求、运行时长和费用/token预算；设置只能在硬上限内调整。超过上限返回稳定的 `concurrency-limit`/`budget-exceeded`，并规定排队或拒绝，不让深度检查承担宽度控制。
### 16. Agent 工具缺少按错误类型分流的失败码
**严重程度**：重要；**类别**：接口

**位置**：t14“确定的工具”表及各工具参数；t12 shell 的失败约定；t20 指令失败码合同。

**现象**：t14 只单独写出 `profile-not-allowed`、`depth-limit` 两个失败码，没有为 Profile 不存在/不可用、`initial` 校验失败、模型或推理档不存在、凭据缺失、子会话创建失败、未知/非自有子会话、已结束运行、问题不存在/已回答、任务不存在/无权操作等定义封闭码表和返回形状。

**为什么是问题**：调用方只能按自然语言区分“参数错、权限错、资源暂时不可用、子会话已结束和结果未知”，会把不可重试的错误重试，或把已创建成功但响应丢失的 `agent_spawn` 当成失败再次派生。t04/t20 已定程序按 code 分支、不解析错误文案；t14 若不补这层，就无法落地该不变量。

**如何核实**：读取 t14 三张工具表和 `agent_spawn` 的返回段，未见 `errors`/`code` 合同；对照 t20 `commandErrors` 的逐命令封闭列表与 t12 第 48 行要求工具结果在 `details` 给 `code`。

**建议改法**：为每个 Agent/任务工具定义 TypeBox 参数、成功值、封闭失败码及可重试性；至少区分 `profile-not-found`、`initial-invalid`、`model-unavailable`、`not-owner`、`child-closed`、`question-unknown`、`question-answered`、`job-unknown`、`job-not-allowed`、`result-unknown` 和资源/存储错误。
### 17. `sessions://` 的只读属性没有覆盖 shell 的真实路径能力
**严重程度**：重要；**类别**：不变量

**位置**：t14 决定 12、15；t08 方案表与后续修改；t12 shell 决定。

**现象**：t14 把别的会话目录标为只读、日志标为只读，但 t08 又规定真实目录“工具与 bash 都能用”，t12 规定 shell 会把可解析资源替换为绝对路径并暴露 `$NBOOK_SESSION`。没有说明 shell 对 `sessions://<id>/` 的读写能力如何继承资源提供者的只读声明。

**为什么是问题**：资源工具可以拒绝写入，不代表已启动的 shell 进程会拒绝 `cp`、重定向、`rm` 或通过脚本打开该绝对路径；t12 已明确第一版 shell 绕过地址读写规则和 nb-history。这样“日志只读”可能只对 `read` 工具成立，且只读/plan 模式的审批白名单也无法按目标地址识别越界写。

**如何核实**：对照 t08 第 43-44、55-59、73 行与 t12 第 44、48 行；一个方案同时被声明为 bash 可用的真实目录和只读目录，但没有 bash 能力矩阵、路径沙箱或失败码。

**建议改法**：为 bash 规定能力边界：只读资源不得作为可写真实路径导出，或由 shell 执行器按解析后的每个路径强制检查 scheme/capability；重定向、脚本打开和子进程继承都必须适用同一规则。若第一版接受绕过，t14 不应把“只读”写成资源合同，而应明确这是未提供的安全保证。
### 18. 子代理结果没有不可信来源标记或安全扫描边界
**严重程度**：建议；**类别**：安全与接口

**位置**：t14 结果三种交回方式、`yield` 与 Agent 工具结果；调研报告第 2.2、2.4 节。

**现象**：子代理最后回复或 `yield` 参数会直接作为父 Agent 的工具结果，设计没有规定结果是“子代理声称的内容”还是已验证事实，也没有来源标记、危险指令/提示注入扫描、结构化 schema 失败后的隔离方式。子代理可以读项目文件、读其它会话资源或执行 shell，结果天然包含不可信外部文本。

**为什么是问题**：父 Agent 会把工具结果当作下一轮上下文；未标记的子代理输出可以伪装成用户指令、审批结论或已经完成的文件操作，且结果扫描若直接改文案会破坏 Profile schema 和原始审计。调研列出的参照中，结构化 `yield`、结果预览/全文地址和终止原因分别承担了可验证边界，t14 只定义了交回形状，没有信任等级。

**如何核实**：读取 t14 第 2、20 条与确定的 `yield` 表，再对照调研第 2.2、2.4 节；工具结果合同没有 `source`、`termination`、`validated` 或安全处理字段。

**建议改法**：至少把子代理结果包成带 `childSessionId`、run/job id、终止原因、schema 校验状态和“非用户指令”来源的结构化值；扫描或拒绝策略放在父 Agent 工具结果边界，不静默修改原文，完整原文继续通过受控 artifact 地址获取。
