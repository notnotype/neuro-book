## 新问题

### 1. 将有状态的 Agent 与任务中心操作声明为 `shared`，同一子会话的操作顺序变成未定义
**严重程度**：阻断；**类别**：正确性 / 不变量

**位置**：`.agents/works/w00032-agent-integration/tasks/t14-multi-agent/README.md` 第 24 条并发字段与工具表；`docs/proposals/agent-harness-event-model.md` 第 9 节第 436 行。

**现象**：修订把 `agent_spawn`、`agent_send`、`agent_answer`、`wait`、`jobs` 都标成 `shared`，因此同一回复中的连续调用会并发执行；但这些调用都改变或观察任务中心、子会话输入缓冲区和 pending interaction。t20 只规定结果按调用顺序写入，未规定并发调用的副作用顺序或快照。

**为什么是问题**：同一回复同时对一个子会话调用两次 `agent_send`，两条 steer/followup 的入队顺序不再由 t07 的“按入队顺序”确定；`agent_answer` 与 `agent_send` 并发时，子会话可能先收到继续消息再解析问题，或相反；`agent_spawn` 与无 `jobs` 的 `wait` 并发时，`wait` 是否包含本批次刚创建的任务也未定义。子会话日志的单写者只能排序已经进入子会话的事件，不能排序任务中心里尚未派发的操作。

**建议改法**：Agent/任务中心工具默认改为 `exclusive`，或为每个目标子会话和任务中心建立独立的串行队列；明确同一回复中的调用顺序、任务快照时点和跨目标并发规则。只有纯查询或不触碰同一目标的操作才允许 `shared`。
### 2. `exclusive` 只覆盖同一回复，不能解决跨子会话和 shell 的文件竞态
**严重程度**：重要；**类别**：不变量 / 接口

**位置**：t14 第 24 条并发字段与只读边界；t20 第 9 节第 436 行；t08/t12 的文件与 shell 约定。

**现象**：修订说“几个子代理同时写同一文件……交给文件服务的条件写入”，同时把内置写文件工具和 `shell` 标为 `exclusive`。但 t20 的 `shared`/`exclusive` 只描述同一个回复里的连续工具调用；两个独立子会话的 `exclusive` 工具仍可同时运行，shell 又明确可以绕过文件服务。

**为什么是问题**：两个子会话各调用一次 `edit` 时，二者不在同一回复，`exclusive` 不提供全局锁，只能依靠各自的条件基线；两个子会话用 shell 重定向同一文件时，既没有条件保存也没有 nb-history 来源。于是“交给文件服务”只覆盖部分调用路径，冲突、覆盖、部分完成和结果未知仍取决于工具实现，不能成为多 Agent 的统一合同。

**建议改法**：把 `concurrency` 明确为回复内调度属性，不把它当资源锁；跨会话写入统一要求 Files 的条件保存/资源锁，shell 要么导出受控写入口，要么明确其写冲突和结果未知合同。文档应按“同回复并发”和“跨会话并发”分别给验收场景。
### 3. 并发上限没有覆盖前台任务，且“每会话”与“全局”统计对象不一致
**严重程度**：重要；**类别**：正确性 / 性能与资源

**位置**：t14 第 23、24 条及确定的工具第 121 行。

**现象**：修订把每会话上限写成“同时在跑的子代理最多 8 个”，全局上限写成“同时在跑的后台任务最多 16 个”；但又规定每次前台子会话运行一开始就是任务、所有返回都带任务 id（t14:100-123）。没有说明同步 `agent_spawn`/`agent_send` 创建的前台任务是否计入全局 16，也没有说明同一回复中并发派生前台任务采用哪个上限。

**为什么是问题**：如果全局 16 只统计后台任务，模型可以用不带 `async` 的 shared `agent_spawn` 绕过全局上限；如果前台任务也统计，当前“后台任务”定义和错误返回时机不成立。并发检查若在任务登记后才做，还会留下已创建子会话但调用返回 `concurrency-limit` 的半成功状态。

**建议改法**：统一统计对象为所有活动的 child run/job，明确前台等待任务和后台任务的计数、父子任务是否重复计数、检查发生在建会话前还是登记任务前；超限必须原子拒绝且不留下子会话，或返回明确的已创建但未启动状态。
### 4. “每次子会话运行都是任务”引入了前台任务的留存与重启孤儿
**严重程度**：重要；**类别**：不变量 / 遗漏

**位置**：t14 第 24 条与确定的工具第 121-131 行；t07 决定 7；t22 任务中心范围。

**现象**：修订把前台同步运行也登记进任务中心，并规定每次返回都带任务 id；但 `jobs` 只列“自己启动的任务”，`wait` 只取最先有结果的任务，未定义前台任务完成后的删除/保留、结果消费、父会话关闭和进程重启后的 task record。

**为什么是问题**：一个父 Agent 连续完成 1,000 次同步 `agent_send` 就会产生 1,000 个任务记录；若为让返回的 task id 可查询而永久保留，任务中心无界增长，若完成即删除，返回的 id 不能再用于恢复或审计。进程重启后 t14 只说“在跑的任务记已中断”，没有说明已完成但未消费的前台结果是否仍可由父取回，容易留下父工具结果未知。

**建议改法**：区分 `run` 与可持久化 `job`：只有后台/需要跨工具等待的运行进入任务中心，前台调用使用一次性结果；若坚持所有运行都登记，定义结果保留 TTL/确认删除、重启恢复记录和父会话关闭时的收口，并给 `jobs` 分页与稳定状态。
### 5. t08 修订留下互相冲突的资源合同，实施者无法确定 `sessions://` 的真实根
**严重程度**：重要；**类别**：文档 / 接口

**位置**：`.agents/works/w00032-agent-integration/tasks/t08-resources-home/README.md` 第 41-59、110-119 行；t14 第 141 行。

**现象**：t08 的主表仍写 `sessions://<会话 id>/…` 映射到 `home/`、`session://` 等于当前会话的整个 `sessions://` 条目，并写“日志在 `home/` 外，Agent 不能直接读写”；同一文件后续修改又写 `sessions://<id>/` 映射整个会话目录、日志可读，且任何会话都能读任何会话目录。

**为什么是问题**：这不是已注明的单纯历史说明：资源表、状态根布局、用例“导演看写手的产物”和后续修改都在同一份当前 Task 中，实施者按不同段落会分别把 `session://session.jsonl` 当不存在、把 `sessions://id/home` 当根，或拒绝 t14 明确要求的原始日志读取。资源解析、bash 地址替换和只读能力会因此产生两套实现。

**建议改法**：在 t08 主表和布局图中直接替换旧合同，只保留一个映射：`sessions://<id>/` 是会话目录，`session://` 是当前会话 `home/`；补上日志、home、附件、artifacts 的能力矩阵。后续修改保留为决策记录即可，不要让已废弃文本继续看起来像现行表。
### 6. 嵌套子代理的任务所有权与 `jobs` 可见范围没有定义
**严重程度**：重要；**类别**：接口 / 不变量

**位置**：t14 第 23 条的逐层中止规则；确定的工具第 129-131 行；父子关系规则第 143 行。

**现象**：子代理可以继续派孙代理，且每次运行都进入任务中心；但 `jobs` 定义为“列出自己启动的任务”，`wait` 缺省也只等自己启动的全部任务。没有说明根父会话能否看到、等待或杀死孙代理任务，也没有定义孙代理任务在父会话的每会话 8 个上限和全局 16 个上限中归属哪一层。

**为什么是问题**：深度最多 5 层时，孙代理可以继续运行但根父的 `jobs` 看不到；父只能杀子会话当前运行，不能直接杀孙任务，或者实现者被迫违反“自己启动”的权限规则向上转发。发生孙代理提问、结果未知或父会话中止时，任务中心无法确定通知和取消对象。

**建议改法**：定义任务所有权树：祖先是否拥有后代的只读查询、等待和 kill 权限；明确每个任务只计入创建它的会话、整棵子树还是全局一次；父中止、`kill`、重启和结果通知都按这棵树传播，并给 `jobs` 增加作用域参数或明确只显示直接任务。
### 7. 异步提问不进入 `waiting`，但用户直接输入的路由没有定义
**严重程度**：重要；**类别**：正确性 / 接口

**位置**：t14 第 18、23、24 条；t20 第 11 节；t07 决定 4。

**现象**：异步 `ask` 的工具立即返回、运行继续（t14:81），回答改为 `resolve` 并把回答放入缓冲区（t14:94；t20:493）；同时 t20 仍写“用户任何时候都能直接应答”（t20:492）。但 t07 的输入框规则只定义“等提问时，输入文字作为自由输入回答”（t07:41），异步提问此时并不处于 `waiting`。

**为什么是问题**：用户在异步问题显示期间输入“选 A”时，系统无法按现有合同判断这是普通 `steer`/`followup`，还是对异步问题调用 `resolve`。按普通输入处理会留下一个未回答的交互；按回答处理又可能把用户原本给父会话的插话误消费为子代理答案。父 Agent 的 `agent_answer` 有明确问题 id，用户输入没有。

**建议改法**：给异步问题提供明确的用户回答动作/问题 id；或者规定“有可见异步问题时裸输入优先回答哪一项”，并定义多个问题、普通插话、重复回答和问题已回退时的 UI 与内核路由。不要同时保留“运行继续”和“输入框等同回答”的无条件语义。
