# w00032 t08 只读设计审查

审查对象：`/tmp/review-t08-design/wt/.agents/works/w00032-agent-integration/tasks/t08-resources-home/plan.md`，固定基线 `aa190052f`。以下静态结论均由计划、Spec 与现有调用链交叉核实；没有把尚未实现的方案当作已复现的产品缺陷。

### 1. 挂载级 access 无法表达会话内的权限，复用 Backend 也不保护只读子树

- **严重程度**：阻断；**类别**：不变量。
- **位置**：plan.md“方案注册”第 33–36 行、“Agent 的方案”第 59、65 行；`packages/neuro-book/src/plugins/files/backend/rooted.ts:133`、`packages/neuro-book/src/plugins/files/backend/entry-ops.ts:108`、`:213`。
- **现象**：`mount(name, caller)` 只返回整挂载点一个 `access: "read" | "write"`，`visible(relativePath)` 只区分可见与不可见。但同一个 `sessions://<id>` 必须同时满足：`session.jsonl` 对所有人只读、自己的 `home/` 可写、自己的 `home/attachments` 与 `home/artifacts` 对 Agent 只读而宿主可写。这不是挂载级二值权限能表达的。把日志设不可见会破坏“任何会话能读日志”；把自己的挂载点设可写又会放行日志。
- **为什么是问题**：现成 RootedRoot 只对 `.nbook` 有硬编码保护，没有这套按调用者、操作与路径检查的机制。即使在顶层方法检查 `home/attachments/...`，`delete(home)` 会在 `entry-ops.ts:213` 递归处理全部后代，`rename(home, ...)`/移动祖先也影响只读子树；`home` 里的链接指回会话根或日志时，`resolve` 允许根内链接，词法前缀检查不能保护日志。只在注册表入口多加几个 if 不能兑现已定不变量。
- **如何核实**：静态逐读 plan.md 第 33–36、59–65 行，对照 `rooted.ts` 第 133–207 行的真实路径解析，以及 `entry-ops.ts` 第 104–113、161–261 行的递归操作；后者只收已解析的源/目标，不收权限策略。这里报告接口表达能力缺口，未用绕过运行时的内部函数实验认定已实现漏洞。
- **建议改法**：实施前定义按 `(caller, operation, lexicalPath, resolvedPath)` 判断的路径授权策略，并规定目录级操作涉及受保护后代时的拒绝/逐项行为；读取、列出、identify、realPath、保存、移动双端、递归复制/删除和事件过滤共用该策略。挂载缓存只缓存磁盘 Backend，不能缓存某调用者的可写结论。补真实合同用例：日志可读不可写、自己的普通 home 可写、两个只读子树与其祖先/链接别名不能被 Agent 改动，宿主仍可写。

### 2. temps 启动扫描会删除另一个状态根仍在使用的会话临时数据

- **严重程度**：阻断；**类别**：不变量。
- **位置**：plan.md“Agent 的方案”第 61、67 行；Task README“方案”第 64 行；`docs/specs/runtime/projects.md:21`。
- **现象**：所有状态根共用 `<tmp>/nbook/sessions/<id>/`，但扫描以本状态根的会话目录判断“已不存在或已归档”。状态根 A 启动时，状态根 B 的活会话 id 在 A 中不存在，正好满足计划的删除条件。`nbook-<uid>` 只区分系统用户，不区分同一用户的两个状态根。
- **为什么是问题**：Task 已定“只清本状态根的会话”，现有拓扑也明确允许不同状态根的服务端同时运行。UUID 唯一性不能防止误删：这里不是撞 id，而是 B 的每一个 id 在 A 中都不存在。归档一个同 id 的独立副本也会删到另一实例的数据；启动时若扫 `nbook*` 还会涉及其它用户的容器。删除不跟随符号链接与所有权隔离是两件事，前者不能解决此问题。
- **如何核实**：对照 plan.md 第 61、67 行的全局目录与扫描谓词、Task README 第 64 行“只清本状态根的会话”，以及 `runtime/projects.md` 第 21 行的多状态根保证。按该谓词枚举即可得出 B 的活会话全被判为“不存在”；未执行破坏性删除实验。
- **建议改法**：为每个会话临时目录写明所属状态根的稳定标记；扫描只处理本状态根拥有且经过 lstat/uid 核验的真实目录，未知归属与其它用户目录保留并诊断。若改成状态根分区目录，保持已批准的 `temps://<id>` 外部地址不变。验收必须有两个同时存在的状态根：A 扫描/归档后 B 的活会话字节不变，并覆盖遗留无标记目录与符号链接。

### 3. 放宽 parseResource 后 rawUrlOf 会把其它方案悄悄改投当前项目

- **严重程度**：阻断；**类别**：正确性。
- **位置**：plan.md“地址规则”“前端”第 27、80–81 行；`packages/neuro-book/src/plugins/files/shared/contracts.ts:364`；`packages/neuro-book/src/plugins/files/backend/raw-route.ts:211`。
- **现象**：计划允许任意合法方案通过 `parseResource`，却没有列出 `rawUrlOf` 的切换。它只显式判断 `user`，剩下所有解析成功的地址都拼成窗口绑定项目的 URL。例如绑定 A 时，`docs://agent/a.png` 会被映射成 A 的 `project://agent/a.png`，`sessions://s/home/x.png` 会被映射成 A 的 `project://s/home/x.png`，未知方案同样如此。
- **为什么是问题**：旧解析器承担了“只有 project/user 能进入这里”的隐含前置条件，移走该判断以后默认分支变成跨根 fallback。raw-route 只看已经拼出的项目 id、代次与路径，无法恢复原始方案并拒绝，会交出错误文件，破坏资源地址与目标一致性。Spec 明定非这两个方案的 `rawUrl` 应为 null（`workspace/files.md:70`）。
- **如何核实**：静态顺读 `contracts.ts` 第 364–369 行与 `raw-route.ts` 第 211–220 行；后者确实按 URL 的项目根读取，不会再判方案。计划只列客户端分派、类型与面包屑，没有 raw URL 的白名单调整。
- **建议改法**：`rawUrlOf` 显式分支 `project`、`user`，其它方案返回 null；若本次要支持新方案的二进制读取，另外明确可授权的字节路由合同、挂载与项目代次寿命，不复用 project 默认分支。增加绑定/未绑定窗口下的新方案与未注册方案用例，断言不会读到同名的项目文件。

### 4. 挂载回收没有在途借用与独立作用域，64 个上限与订阅固定相互冲突

- **严重程度**：阻断；**类别**：不变量。
- **位置**：plan.md“方案注册”第 33–35 行、“不做与风险”第 129 行；`packages/neuro-book/src/plugins/files/backend/plugin.ts:47`、`:122`；`packages/nb-runtime/src/lifecycle/scope.ts:530`、`:790`。
- **现象**：回收条件只写“无订阅且 5 分钟没有请求”，超过 64 就关闭最久未用者；没有给进行中的 read/write/batch、打开中的 mount 或释放中的 Backend 占用。第 65 个挂载到来时，最老的一个可能正执行复制/等待锁，或者全部 64 个都被订阅占着。计划既要求订阅占住挂载点，又没有定义无可回收项时怎样响应。
- **为什么是问题**：现有 `openBackend` 把 ChangeHub 与 `tracked` 写入全部挂在整个插件的 `context.scope` 上，不是每个 Backend 的作用域。手动 `changes.close()` 不会等 `tracked` 的真实 termination，之后保存/复制仍能落盘而事件被 `closed` 吞掉；若关闭它的 scope，关掉的是整个 Files 入口。反复关闭再打开还会在入口作用域中积累已关闭的 ChangeHub 登记。内核只在关闭正确的作用域时保证等在途再释放，不会理解 LRU 表里的使用状态。
- **如何核实**：静态核对 `plugin.ts` 第 47–54、122–138 行（同一个 `context.scope`）与 `changes.ts` 第 284–308、312–315 行（关闭后保存/事件直接返回），对照 `scope.ts` 第 530–540、790–811 行的实际等候门禁。此为计划缺少状态与所有权合同，未伪造时序宣称已复现。
- **建议改法**：每个挂载点一个独立 child scope，并定义 `opening/open/closing`、请求借用数、订阅数和唯一打开 Promise；整段请求实际结束前持借用，回收只选借用数与订阅数均为 0 的项，closing 后新请求等它收口再开。明确 64 指活跃 Backend 还是空闲缓存；若是硬上限，全部被占时返回已有 `busy` 或有界等待，不能驱逐活跃项。入口/贡献撤回时先拒新借用、结束订阅、等在途实际结算再关监视并删登记。覆盖慢操作中的第 65 次打开、同时首次打开、订阅建立中撤回、长调用超过 5 分钟与停止的真实合同场景。

### 5. 新方案能在编辑器打开，但“全部保存”与两份持久化记录仍只接受 project/user

- **严重程度**：重要；**类别**：正确性。
- **位置**：plan.md“前端”第 80–81 行、“切片”第 100 行；`packages/neuro-book/src/plugins/editor/web/area.ts:902`、`web/session-record.ts:20`、`web/recent-record.ts:14`。
- **现象**：计划把编辑器变化限于 Scheme 类型和根标签，遗漏三个真实的双方案边界。`saveAll()` 只保存 `["project://", "user://"]`；`editor.session` 标签地址与 `editor.recent` 地址数组的 schema 都是 `^(?:project|user)://...`。打开 `profiles://.../notes.md` 后，全部保存会跳过它并报告成功；记录中只要混入 1 个新方案地址，整个快照/最近列表的保存就不合 schema。
- **为什么是问题**：打开命令的 `address` 只是 string，`area.open` 会创建标签并调用 `opened`，放宽解析以后这些路径确实可达。Storage 的记录整体校验与保存队列不会按地址过滤，一份不合法的快照会挡住后续持久化；刷新丢失新标签与之后的布局变化。计划的 user/project 浏览器 smoke 捕捉不到这些后果。
- **如何核实**：静态追踪 `editor/web/commands.ts:55` → `area.ts:728–753`、`:902–905`，以及 `session-record.ts:59–65`、`recent-record.ts:29–32` 两条保存路径；对照各自 schema 和 `shared/store/persisted.ts:372–405` 的失败后暂停队列。只读检索设置定义没有找到其它把通用文件地址存为 setting 的生产字段；Explorer 展开记录是分 root 的相对路径，不需要泛化成任意方案。
- **建议改法**：明确编辑器支持哪些已注册方案，持久化使用与解析器一致的通用地址语法，保留未注册/已撤回方案的失败呈现而不是判整份记录损坏；全部保存从实际打开的可保存文档枚举。把 session/recent schema、记录恢复、area.saveAll 与 Lab 的双根类型收窄一并列入第 2 片；用 1 份 project 文件加 1 份 profiles 文件验证保存、刷新恢复和最近列表。

### 6. 继续按整个方案监视，既会打开所有项目/会话，又让不支持 watch 的可读文档永远等不到正文

- **严重程度**：重要；**类别**：正确性。
- **位置**：plan.md“服务端的通用合同”“前端”第 42、80 行；`packages/neuro-book/src/plugins/editor/web/documents/store.ts:217`、`:283`、`packages/neuro-book/src/plugins/files/web/client.ts:144`。
- **现象**：新服务端过滤器虽有 `{scheme, mount?}`，浏览器公开方法仍是 `watch(scheme, listener)`，编辑器按方案开监视“逻辑不变”。打开 1 份 `sessions://s/home/a.md` 就订阅整个 sessions；打开 1 份 `projects://b/a.md` 就订阅整个 projects。计划没有定义无 mount 的订阅到底覆盖哪些条目、新挂载点如何加入、项目根变化如何跟进。另一方面，注册表允许只声明 read/list 的方案，编辑器却先等 watch 的 ready，watch 不支持/建立失败只走 ended，ready Promise 从不完成，`files.read` 根本不会发出。
- **为什么是问题**：若无 mount 表示全覆盖，200 条会话列表已经超过 64 个挂载上限，projects 的全方案订阅会为所有登记项目起子进程并永久占租约；若只覆盖已打开 Backend，又会在没有订阅的间隙漏外部变化，违背 ready 之后的监视合同。若回答不支持，明明能 read 的文档停在 loading；未注册方案从解析失败移到分派也落进同一个等待问题。现有 store 里的每个方案订阅直到整个编辑器 dispose 才释放，关闭最后一个文档也不释放它，不能靠“关标签后回收挂载”解决。
- **如何核实**：静态追踪 `FilesService.watch`（`shared/contracts.ts:357`）、`web/client.ts:144–159`、`documents/store.ts:217–252`（仅 ready resolve）、`:283–291`（先等 ready 后读）、`:697–707`；对照计划第 31–35、49、80 行。验收映射只有服务端 read/list 能力测试，没有编辑器打开不支持 watch 的方案用例。
- **建议改法**：让消费方按实际资源的挂载点/路径订阅并按最后一个文档引用释放，规定根虚拟目录的订阅不隐式全量打开项目；明确 subscribe 的 ready、ended 与能力不支持的握手语义。文档能查询能力并在无 watch 时显式按非实时方式读，未知方案直接显示失败，不留下未完成的 ready。测试同方案两个挂载点的独立收口、65 个挂载点、只读无 watch 提供方及未知方案打开路径。

### 7. “同方案”不再等于“同一文件根”，批量与 cancel 缺少可分派的合同

- **严重程度**：重要；**类别**：正确性。
- **位置**：plan.md“方案注册”“服务端的通用合同”第 32–44 行；`packages/neuro-book/src/plugins/files/shared/contracts.ts:182`、`:191`、`:195`；`packages/neuro-book/src/plugins/files/web/client.ts:38`、`:291`。
- **现象**：计划说方法与现有一套相同、`sameScheme` 批量检查不变，但 `sessions://a/...` 与 `sessions://b/...`、`projects://a/...` 与 `projects://b/...` 现在是同方案下不同根。现有 batch 是一个 RootedRoot 上的操作；identify 输入是 paths 数组、reorder 输入是 directory、move/copy 各有 source/target，不能只把 `{path}` 改成 `{address}` 完成迁移。尤其 `cancel` 只有 `{operation}`，现客户端虽在闭包里记了方案，却发请求时没有带方案；所有非 project 合并成一个 server 合同后，注册表无法据此选择提供方/挂载点。
- **为什么是问题**：按第一个地址选 Backend 会把其余挂载点路径错投；按挂载拆批又必须保持逐项下标、父子去重、部分完成、停止后未执行项和取消的所属调用方。Files 现行合同只承诺同根搬运，不承诺跨根复制/移动。当前 active 操作表在 `implementation` 的按调用方门面内；若重构成共享 SchemeProvider，不能只以 operation id 全局存放，否则一个调用者能取消另一个调用者同 id 的操作。
- **如何核实**：静态核对 `web/client.ts:38–51`、`:291–303`，`shared/contracts.ts:182–195` 的完整方法输入，以及 `backend/plugin.ts:66–82`、`:107–110` 的 active 表与 `backend/batch.ts:53–125` 的单根预处理。计划没有列出新的多地址/无地址方法合同。
- **建议改法**：本次明确只允许同一规范化挂载根的批量搬运，跨挂载在任何副作用前拒绝；若允许多挂载 delete/identify，单独定义逐项对齐和停止规则。给 cancel 明确的 scheme/mount 或注册表级 `(consumer activation, operation)` 查找，保持原调用方隔离，并列全每个方法的地址字段。验收至少包括同方案跨会话/跨项目搬运、混合挂载批量、取消成功与另一个调用方取消被拒。

### 8. 首次 Profile/temp 访问没有存在的根可打开，“第一次写时创建”没有落到可执行流程

- **严重程度**：重要；**类别**：正确性。
- **位置**：plan.md“方案注册”“Agent 的方案”第 33、60–61、66 行；`packages/neuro-book/src/plugins/files/backend/plugin.ts:122`；`backend/rooted.ts:108`；`backend/files-service.ts:140`。
- **现象**：Profile 挂载目录“第一次写时创建”，temps 只给了路径；而 mountedScheme 一收到请求就复用 `openBackend`，它对不存在的根把 `root-gone` 抛成 Error。只读列出全新 Profile 得不到可区分的空 home/not-found，而会成为 provider-error；第一次 create 若也先打开 Backend，会在创建根之前失败。`realPath(tmp://)` 用来启动 shell/grep 时同样拿不到目录。
- **为什么是问题**：现有 Files create 是在已存在父目录下排他新建，write 只保存已有文件，都不补父目录。t10 没有建立 `<状态根>/agent/profiles/<key>` 和 temp 根的其它路径。建会话只加 home 不能让这两个根出现，按计划照字面拼装不能完成“写 Profile 笔记”“脚本写 tmp”“SDK 之外仅 project 不可用”的用例。已有 t10 会话和内核 fork 的 home 也不会经过新的外层 createSession 补建路径。
- **如何核实**：静态核对 `openBackend` 第 124–125 行、`openRoot` 第 108–119 行；`workspace/files.md:61,104` 明定不补父目录；`agent/backend/agent.ts:116–118,176–187` 只建 sessions 根，`nb-harness/kernel/session/session.ts:503–539` 的 fork 直接调 store.create，不经过 Agent 外层 createSession。
- **建议改法**：把 mount 的存在性与初始化时机列成合同：未物化的 Profile 根读/列出怎样返回、首次允许写入由谁创建、tmp 首次 realPath 是否物化，缺失资源不能用激活期抛错报成 provider-error。所有建会话路径（普通、startTask、fork）与已有会话首次打开要统一确保 home 可用；保留“只读浏览不创建用户文件”的既有约定或明确记录例外。用完全空的隔离状态根覆盖上述首次访问与老会话打开。

### 9. agentSession 只核对插件身份，未定义会话值与“当前 Profile”的权威校验

- **严重程度**：重要；**类别**：不变量。
- **位置**：plan.md“服务端的通用合同”“Agent 地址层”第 43、55、60、72–76 行；`packages/nb-harness/src/kernel/session/session.ts:102`、`:258`；`kernel/log/index-file.ts:20`。
- **现象**：`agentSession: string` 只写了“来自服务端 nbook.agent 就接受”。没有说会话 id 的格式、存在性、失败码、允许代表哪一个真实会话，也没有定义 profiles 权限如何取得该会话此刻使用的 Profile。SchemeCaller 只有 consumer/source，内核身份不含会话与 Profile；它们不能从插件 id 推出来。

### 10. projects 的内层调用与订阅不会自动继承外层寿命，结束事件也不会替它释放租约

- **严重程度**：重要；**类别**：不变量。

- **如何核实**：静态核对 `runtime/plugin-channel.md` 输出 7 的订阅归属、`shared/contracts.ts:216–224` 的业务 ended，`backend/changes.ts:167–173` 的根消失分支，以及 `shared/projects.ts:142–147` 的无 signal acquire。计划的 projects 用例只列成功读写、宽限期、来源透传，未映射建立中取消、root-gone、内层 onEnd 与租约 revoked。

### 15. expand 后再规范化未规定别名根界限与失败通道，classify 也没有保证使用同一地址

- **严重程度**：重要；**类别**：不变量。

### 16. 新方案的权限没有进入编辑器 writable/保存协作，打开只读挂载仍会显示可编辑

- **严重程度**：重要；**类别**：正确性。
- **位置**：plan.md“方案注册”“前端”第 31–36、78–81 行；`packages/neuro-book/src/plugins/editor/web/documents/store.ts:399–402`；`docs/specs/workbench/editor.md:89,165,170`。
- **现象**：计划只改 Scheme 类型与面包屑，未规定 `read` 返回能力/权限元数据，也未改变文档 `writable` 的计算。当前它只看 `ready`、订阅未结束与文本类型；因此 `docs://`、别的会话 home、profiles 的只读路径读成功后仍给编辑控件 `readonly=false`。用户输入会先进入本地正文，随后保存才被服务端拒绝；“保存全部”还会把它列为可保存文档。
- **为什么是问题**：资源 Spec 要求显示只读的资源仍由服务端拒绝，编辑器 Spec 要求只读文档的视图不接受输入，且 `save-all`/资源管理器结算依赖 writable 状态。只在 write 方法返回 `permission-denied` 是后置失败，无法满足用户可观察的只读行为，也会在关闭时制造不必要的保存询问。VS Code 参照同样把只读能力作为每个 FileStat/Provider 的公开元数据；计划声明的能力矩阵没有对应输出。
- **如何核实**：静态追踪 `documents/store.ts:401` → `EditorGroup.vue:339` 的 readonly 绑定，核对 editor Spec 输出 20、18 与 Files Spec 的“显示为只读仍服务端拒绝”；对照 `FilesService.read` 当前只返回 `{text, baseline}`，计划未列 `readonly`/capability 元数据迁移。没有把未实现路径当成运行时已复现。
- **建议改法**：在地址打开/读取结果或独立 stat 合同中返回该调用方的可写能力与文档级只读状态，并让文档模型以它计算 writable；读成功但不支持 write 时控件从一开始只读。区分“当前调用方不可写”与“文档被外部删除/订阅结束”，保留服务端二次拒绝。验收 docs、他人 sessions/home、attachments/artifacts、profiles 与可写自己的 session/profile 混合打开，断言输入、保存全部、关闭询问和资源管理器操作均符合合同。

## 第 16 条的范围更正

第 16 条只适用于实际对当前调用方只读的资源：`docs://`、`sessions://<id>/session.jsonl`、只读第三方方案，以及按 Agent 身份访问的他人 home/只读子树。plan.md 第 55 行已允许浏览器用户写可写的会话与 Profile home，因此原条目中“别的会话 home、profiles 的只读路径”不代表它们对浏览器一律只读；这部分例子收窄，不能作为禁止浏览器写他人 home 的依据。有效问题仍是缺少把方案/路径的实际权限交给文档模型的合同；收窄后的验收分别使用浏览器与 Agent 的真实身份，不能混用两者权限。

## 未发现问题的方面

这些结论限于本次静态检查，不表示新设计已通过运行时验收。

- **已批准方向**：按文件服务注册 Agent 方案、`temps://` 名称、每调用取得项目租约、按服务端插件 id 接受代会话请求、sessions 根 200 条、5 分钟/64 个挂载上限、两个新失败码、旧窗口刷新均作为本次约束；发现针对落实机制，没有建议撤销这些方向。
- **内核身份与委托本身**：宿主签发完整 ConsumerIdentity，路由覆盖实例位置；委托保留原 consumer、代理只放在 via，提供方按原 consumer.location/plugin 识别 `nbook.agent`/`nbook.files` 即能拒绝浏览器或其它服务端插件自报 agentSession/as。远端收到的 consumer 不能再交给 remote.on 代理到第三个实例（plugin-channel 输出 10）；projects 应以 Files 自己身份发起内层调用，来源只经受控 as 传，不能为了来源改用远端委托。
- **Project 根与递归分派**：项目合同只处理一个已绑定目录内的相对路径，现有 projectEntry 没有回调方案注册表；projects 去掉挂载段后调用它，不必再经过 projects 注册表，也没有固有的 scheme→scheme 递归。项目子进程对 server 合同的新调用则仍是一个完整的新 RPC，不能把它假定成内部本地调用。
- **现有项目管理器状态机**：普通 acquire 已处理 creating 共用创建、idle-grace 取消宽限期、stopping 等上一代退出后再建、停止接纳后拒绝，并在等待回来后重验 admission；不需要在 Files 中复制这些状态。返回后持有 lease 足以阻止正常宽限期关闭，释放幂等；实际调用/订阅结束与代次失效仍需第 10 条的接线。
- **短名与 id**：登记表 resolve 先匹配 id 再匹配短名，manager.acquire 用 id 队列复核登记。计划可沿用它，不需要另造一份名称解析器；地址正规形与别名显示仍需第 15 条补齐，不能声称两种引用已经同步统一。
- **Agent 生命周期接缝**：内核已有按当前装配创建 ToolSessionContext、changeProfile 后 refreshContext 重建 Resources 并退休旧工具的机制；替换 sessionResources 可以保留这条既有路径，不必把 resource 对象绑死在最初的 header Profile。真正的 Profile load 经 opening 的 sessionCreated/compaction 反应执行，初始化会话尚未登记时的读取已计入第 8、9 条。
- **原语复用范围**：RootedRoot 已有词法/真实路径包含、根身份与 .nbook 保护；文件操作有条件保存、跨进程锁、逐项取消与部分结果。复用这些能力有真实代码依据；它们不能自动推出会话子树授权、挂载缓存所有权或逐跳 RPC 失败透传。`changes.ts` 实际用 `node:fs.watch`，不是 plan 第 19 行所称 chokidar，验收应沿真实监视器设计。
- **Explorer 双根与持久化**：文件树继续只有 project/user 与已定范围一致；其展开记录存双根下的相对路径，不必跟通用 Scheme 一起扩成任意方案。生产设置检索未发现其它必须随本次变更泛化的通用资源地址字段；已定位的 Storage 地址缺口在编辑器 session/recent（第 5 条）。
- **参照范围**：核对了 [VS Code FileSystemProvider 的公开定义](https://raw.githubusercontent.com/microsoft/vscode/main/src/vscode-dts/vscode.d.ts)：注册返回可撤销句柄、同方案唯一、watch 按 URI 可释放、逐文件权限和方案只读元数据；本次相关缺口已落在第 1、4、6、16 条。没有把 VS Code 的二进制/远程文件系统等完整能力直接变成 t08 的额外目标。
