## 1. `$` 菜单的“同名要写 id”漏算无效的同名 Skill，插入的标签被服务端判为 ambiguous
- 严重程度：重要　类别：正确性
- 位置：packages/neuro-book/src/plugins/agent/web/skills.ts:91-97（usable 过滤后才数同名）、:105 `duplicated`；对照 shared/skills.ts:70-82 `matchSkillToken`、skills.md 输出 7
- 现象：`sameName` 只在 `usable`（白名单里且不是无效）里数。`matchSkillToken` 里 `permitted = named.filter(allowed)` 不排除无效的，同名且都在白名单的不止一个就是 `ambiguous`，认到之后才判 `invalid`。所以“用户的 `review` 是无效的（无 SKILL.md 之类），内置也有 `review`，两个都在白名单（声明 "all" 时无效的也在）”时，菜单里只剩内置那个，`duplicated=false`，插入 `$review`，服务端认标签得 `ambiguous`，Skill 正文没有带上，界面上也没有任何提示（输出 12 只给模型一条 system-reminder，输出 28 界面不提示）。
- 为什么是问题：这正是任务说明重点 1 要求的“插入文字与后端认标签对得上”。无效的 Skill 名字取自目录名（backend/skills/catalog.ts:189 `name: folder`），用户放了一个没 SKILL.md 的 `review` 文件夹再用内置 `review` 是现实场景。菜单测试里 ENTRIES 恰好有 user.outline 无效但没有与它同名的有效 Skill，所以没覆盖。
- 如何核实（已做）：scratch 实验 /tmp/review-w00032-t15-impl/frontend-scratch/dup.test.ts，用 `bun test` 在 /tmp 下跑：entries=[user.review(invalid), builtin.review(ready)]，allowed 全选，输出 `skillMenu` 为 `[["review","$review"]]`，同一份数据 `matchSkillToken("review", …)` 为 `{"ok":false,"reason":"ambiguous"}`。
- 建议改法：`sameName` 对 `input.entries` 里“在白名单里”的条目计数（不排除无效的），与 `matchSkillToken` 的 `permitted` 同口径；补一例“同名一个无效一个可用”，断言插入 `${builtin.review}` 且 `promptSkillTokens` 读回 id。更稳的是让 `skillMenu` 直接对每个要列的条目调 `matchSkillToken(插入的名字, …)`，认不回自己就改写 id，口径就不会再分叉。

## 4. 取计划失败后点“重试”不重新取计划：没有 bun.lock 的 Skill 永远装不上，且取计划失败没有诊断
- 严重程度：建议　类别：正确性
- 位置：packages/neuro-book/src/plugins/agent/web/skill-init.ts:51-53（`ask` 失败分支）、:55-69（`confirm`）
- 现象：`skillInitPlan` 失败（传输错误、`skill-not-found`、`not-initializable`）时状态是 `phase: "failed"`、`plan: null`、`failure.code: "unavailable"`；对话框页脚给出“关闭 / 重试”。“重试”调 `confirm()`，它直接 `initSkill({id})`，`plan === null` 所以不带 `resolve: true`。没有锁的 Skill 后端得 `lock-missing`（backend/skills/install.ts:164），`confirm` 把它当意外码 `report` 一条再改成 `unavailable`，对话框回到同一个失败状态，用户点多少次都一样。有锁的 Skill 则会不经确认（依赖列表与“要联网”从没显示过）直接联网安装，与 Spec 输出 27“先问”相悖。另外 `ask` 的失败分支没有调 `report`，取计划失败在诊断里没有痕迹（对照 `confirm` 里对意外码是会 `report` 的）。
- 为什么是问题：窄边角（取计划本来就很少失败），但“重试”按钮是对话框主动给出的，行为与它的字面意思不符；诊断缺一条会让这类失败查不出来。
- 如何核实：从代码推断：`createSkillInit(fakeRemote, report)` 让 `skillInitPlan` 返回 `{ok:false, code:"unavailable"}`，`ask` 之后 `confirm`，观察 `initSkill` 收到的入参没有 `resolve`。skills.test.ts 的窗口流程只走了成功取计划的路径。
- 建议改法：`confirm` 在 `plan === null` 时改为重新 `ask`（同一个 id 与 name，状态回到 loading）；`ask` 失败分支补一条 `report("skill init plan <id>: <code>")`。这样“重试”总是先回到确认状态，不会绕过确认。补一例：计划失败 → 重试 → 取到计划 → 处于 confirm。

## 10. `$` 菜单只在目录与最近用过变化时换函数，不盯 profiles；启动时两路并行取数，菜单可能先显示“没有可用的 Skill”

## 12. 失败路径上用户没有反馈：目录取不到时 `$` 菜单一直转“加载中”，打开文件夹的其它失败码只进诊断
- 严重程度：建议　类别：正确性
- 位置：packages/neuro-book/src/plugins/agent/web/skills.ts:36-40（`load` 失败只 `report`，`entries` 保持 null）；web/skills-page.ts:43-52（`openFolder` 对 `no-desktop`、`open-failed` 之外的码只 `report`）
- 现象：（a）`remote.skills({})` 失败（例如 `unavailable`）时 `entries` 一直是 null，`skillMenu` 对 null 返回 `{loading: true, items: []}`，菜单永远显示“正在查找”，Skill 页永远显示“正在读取 Skill”转圈；只有下一次 `skillsChanged` 或重连的 `onResync` 才会重取。（b）`openFolder` 遇到 `unavailable`、`denied` 之类运行时失败码，点了按钮什么都不发生。
- 为什么是问题：用户无从判断是慢还是坏了。属于窄边角（本地应用里远程调用很少失败），按“窄场景选简单改法”不建议加机制。
- 如何核实：从代码推断。
- 建议改法：`skillMenu` 加一个最简单的第三态不值得；只需 `load` 失败且 `entries` 还是 null 时才 `entries.value = []`（已有目录时失败不覆盖）并保留诊断，这样菜单落到“没有可用的 Skill”而不是一直转圈（代价是把“取不到”显示成“没有”，诊断里有 `skills: <code>`）。`openFolder` 的兜底分支用 `no-desktop` 同一条通知（“打不开 Skill 文件夹”，不带路径）即可。

## 13. Skill 页从不显示上次安装失败的输出：`install-failed` 的 `detail` 被丢掉
- 严重程度：建议　类别：正确性

## 16. 白名单为空的 Profile 下，正文里写 `$5` 之类再按回车，“打开 Profile 设置”那一项会吃掉这段文字并打开设置窗口，消息没发出去
- 严重程度：重要　类别：正确性
- 位置：packages/neuro-book/src/plugins/agent/web/skills.ts:93-95（白名单为空时返回只含 OPEN_PROFILE_SETTINGS_ITEM 的菜单，不看 `query`，`insertText: ""`、`continues: true`）；机理在 packages/nb-markdown/src/prompt/PromptEditor.vue:511-520（`handleMenuKey`：有高亮项时回车确认它）与 :415-425（`confirmItem` 用 `insertText` 替换触发范围）
- 现象：用户 Profile 默认不声明 `skills`，白名单为空，是常态。这时 `$` 前面是空白的任何输入（“他花了 $50”“路径 $HOME”）都会打开菜单，菜单里永远只有那一项且自动高亮（`keepActive` 选第一个可用项）。此时回车是“确认这一项”而不是“发送”：触发范围（`$50`）被替换成空串，设置窗口被打开，消息没有发出。查询词匹配不到任何 Skill 时（白名单非空）菜单没有项，回车照常发送，所以只有白名单为空的这条分支有问题。
- 为什么是问题：小说写作里的 `$` 不罕见（价格、货币、变量名、shell 命令讨论），而且这是静默地删掉用户刚写的字并放弃发送。Spec 输出 26 要求“白名单为空时写一句说明，并带去 Profile 设置的入口”，没有要求它吞掉文字；入口可以做得不抢回车。
- 如何核实（已做，真实 PromptEditor 组件）：在 /tmp/review-w00032-t15-impl/frontend-scratch/nbm（nb-markdown 包的副本，不动 worktree）里 `bunx vitest run src/prompt/Scratch.dom.test.ts`：`resolveMenu` 对 `$` 返回与 `skillMenu` 白名单为空时逐字相同的那一项；输入 `价格是 $5` 后派发 Enter，输出 `menu-open [[{"trigger":"$"}]]`、option 数 1；Enter 后 `change` 依次为 `["价格是 $5","价格是 "]`，`submit` 为 undefined，`menu-select` 为 `[{"trigger":"$","id":"open-settings"}]`。
- 建议改法（选最简单的）：把“去 Profile 设置”做成不被回车选中的提示：`PromptMenuItem` 已有 `disabled`，但 `disabled` 项点不了；更直接的是白名单为空时 `skillMenu` 返回 `{items: [], emptyText: "这个 Profile 还没有可用的 Skill。到设置里加"}`，不放可确认的项，入口用 `emptyText` 里的文字加设置窗口自己的入口承担（回车照常发送）。若开发者一定要可点的入口，让该项 `disabled: false` 但不是默认高亮（需要 PromptEditor 支持“无默认高亮”，是更大的改动，不建议）。
