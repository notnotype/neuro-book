# 建立组件 Lab 与第一批入驻组件

## 目标

在主应用里建成 Component Lab 原型，让三个真实组件入驻，并补上产物门禁使 Lab 从第一天起就不进发布包。要验证的是一条链：**组件文档能不能驱动一个确定性的检视环境**。三个组件按难度递增选取，覆盖组件规范里三种不同的可验证程度。

## 顺序调整

t04 记录的顺序是「t04 → 清退 preview → Lab 原型 → 种子组件 → 补写 Lab 界面合同 → 主题切换」。开发者已把清退 preview 顺延为 [t06](../t06-preview-retirement/README.md)，Lab 提到本 Task。新顺序：

本 Task → 回头补写 Lab 界面合同 → 主题切换 → 清退 preview → 渐进迁移剩余组件。

t04 的浏览器人工走查在本 Task 开工时仍未完成。两者不互相阻塞，但 t04 的完成门禁不因本 Task 开工而视为通过。

## 已核实的现状

以下四条是本 Task 的设计前提，来自开工前的代码阅读，除标注外未运行验证。

**一、nb-ui 已有一套 Lab，本 Task 不复用也不合并。**`packages/nb-ui/playground/app/component-lab/` 约 2500 行，覆盖 48 个组件，含场景、变量编辑器、事件日志、三视口与 URL 状态。它跑在 nb-ui 自己的 playground 里，解析不到主应用的别名、i18n 与自动导入，看不见主应用的组件。开发者已拍板：它只服务 nb-ui 的纯组件，NeuroBook 的 Lab 自建且要更重。另有一条技术理由——它的组件清单是手写的 1102 行登记表，与本仓库 Lab 规范「索引是扫描组件声明得到的派生产物、不保留第二份清单」直接冲突，照搬即违规。

**二、主应用当前没有任何按环境排除页面的机制。**构建配置里找不到针对 preview 页面的过滤，也没有 `pages:extend` 之类的钩子。也就是说 14 个 preview 页面是随产品一起发布的，而 Lab 规范要求的产物门禁属于全新工程，不是抄现成做法。（从代码读出，未跑构建验证。）

**三、开发者点名的「左侧文件面板」进不了 Lab，能进的是它里面的文件树。**

| 组件 | 行数 | 直接操作 store | 浏览器存储 | 其它通道 | 能否进 Lab |
|---|---|---|---|---|---|
| `WorkspaceFileTree.vue` | 265 | 无 | 无 | 向自己的子节点 provide 上下文 | 能 |
| `MarkdownStudioWorkbench.vue` | 237 | 无 | 无 | 无 | 能 |
| `JsonViewer.vue` | 420 | 无 | 无 | 剪贴板（只写） | 能 |
| `WorkspaceFilePanel.vue` | 721 | 建、删、改名、移动文件，加载文件树 | `localStorage` 存展开路径 | 剪贴板（只写） | **不能** |

`WorkspaceFilePanel` 命中 Lab 规范「含 `io:` 或 `state:shared-write` 的组件只能在正式界面验证，Lab 不挂载」。它写 `localStorage` 这条另外命中组件规范禁止规则档位 B「出现任何 `persist:` 标签」。本 Task 只如实记录，不修实现。

树、拖拽、展开、选中这些看得见的行为全在 `WorkspaceFileTree` 里，`WorkspaceFilePanel` 是它外面那层负责真删文件的壳。Lab 的边界恰好落在这两者之间，这一对正是验证组件规范的线画得对不对的好样本。

**四、编辑器工作台的 controller 可以用真的，不必伪造。**`useMarkdownStudioController` 只要 `markdown` 与 `viewMode` 两个 ref，内部不碰 store、不发请求。Monaco 与 TipTap 都是本地打包的动态导入，不走 CDN。所以工作台的 fixture 就是一段 Markdown 字符串加一份标签页列表，不需要造假 controller，也不违反「fixture 不得要求网络」。这消除了本 Task 开工前最大的一处不确定。

## Lab 要做到什么

前三条是 Lab 规范的硬性要求，后四条由开发者选定。

1. **预置状态快照。**规范要求含「直接读 store」标签的组件需要预置状态快照后才能验证。nb-ui 的组件没有 store，它那套完全没有这层；NeuroBook 的 Lab 必须有。第一批三个组件都不读 store，因此本 Task 只需把这条通路建出来并有一个可用样例，不追求覆盖所有 store。
2. **挂不上的组件也要在清单里，并说明原因。**规范验收第 4 条。`WorkspaceFilePanel` 是本 Task 的验证样本：可查询、可看到理由，但不挂载任何 fixture，也不给替代结论。
3. **手机 `390×844` 与平板 `768×1024` 两种固定容器**，加一种随窗口的桌面容器。切换容器不改变 fixture 语义。
4. **组件文档与实物并排显示。**把组件旁边那份 `.md` 渲染在实物边上。文档说「不支持什么」「注意什么」，实物就在旁边，对不上当场能发现。这是 nb-ui 那套没有的概念，也是验证「先文档后实现」是否成立的唯一手段。
5. **事件日志。**组件往外发了什么事件、带了什么数据，实时列出。文件树往外发 6 个事件，编辑器工作台发 19 个，这两个组件自己不改任何东西、只负责往外报，不看事件就只能看到一个没反应的界面。
6. **假数据可以在 Lab 里现场改。**不止开关和下拉，要能直接编辑那份数据本身——把文件树从 5 个文件改成 300 个、改成五层嵌套、改成空目录，不必预先写死场景。
7. **主题与配色切换。**主应用自己有一套主题，后面的主题切换那一片要全推倒重做；Lab 里先能切，那一片就有了现成的验证场地。

界面形态（导航怎么排、检视面板长什么样、场景怎么组织）**本 Task 不预先规定**。Lab 规范明写这些等原型建成后按真实形态补写，提前写只能是猜测。第一版由 Tasker 定形，开发者看过原型后再补写合同。

## 索引与 fixture

**索引是派生的。**扫描 `app/components/**/*.md` 的 frontmatter 能力标签得到组件清单，并据标签推导每个组件能不能挂、需不需要状态快照。仓库里不留第二份手写组件清单。

需要说明的是这条链目前只覆盖到「有哪些组件、能不能挂」。**场景本身不来自组件文档**——文档里没有场景这个概念——场景由 fixture 提供，按组件名与索引对上。这个划分是本 Task 对规范的执行方式，形态稳定后写进 Lab 合同。

**fixture 集中放在开发专用目录**（t04 已定，随「不目录化」一起），按整目录排除，不散落进组件目录。

## 允许改动

- 新增 `packages/neuro-book/app/component-lab/`：Lab 外壳、索引扫描与全部 fixture。整个目录只在源码开发环境存在。
- 新增 Lab 入口路由，位置与形式由实现确定；只在源码开发环境注册。
- `packages/neuro-book/nuxt.config.ts`：加入排除规则，使非开发环境下 Lab 目录与路由不进构建图。**排除必须发生在构建图与路由生成阶段**，不接受运行时守卫或环境变量隐藏一个实际已打包的 Lab。
- 新增三份组件文档：`WorkspaceFileTree.md`、`MarkdownStudioWorkbench.md`、`WorkspaceFilePanel.md`。前两份是入驻组件的说明书；第三份存在的意义是让 Lab 的「挂不上并说明原因」这条路径有真实样本，同时把它的档位 B 违规如实登记。
- 三个入驻组件的实现**默认不改**。写文档时发现实现与应有行为不符，按组件规范记入「已知偏差」，不在本 Task 顺手修。

## 批次顺序

每一批都是一个可以停下的边界，中途叫停不留半成品。

1. **骨架 + 索引扫描 + 产物门禁 + JsonViewer 入驻。**最小闭环：能选组件、能看场景、能切三种容器、文档并排显示，且构建产物里没有它。JsonViewer 已有文档，用它验证整条链。
2. **文件树入驻 + 事件日志 + 现场改假数据。**文件树 6 个事件、数据是一棵可以任意变形的树，正是这两件能力的用武之地。
3. **编辑器工作台入驻。**最重的一个，验证 Lab 扛不扛得住 TipTap 与 Monaco 这类重编辑器。
4. **主题与配色切换 + `WorkspaceFilePanel` 的「挂不上」路径。**

## 开发者参与

- **Lab 的界面形态没有合同，第一版由 Agent 定。**这是 Lab 规范里明写的安排，不是省略。原型出来后由开发者定形，再回头补写 Spec。看着不对就说，此时改的代价最小。
- 三份新组件文档写完后由开发者过目，与 t04 的安排一致：写起来别扭就改组件规范，不将就着往下写。
- 浏览器人工走查只有开发者能做。
- `WorkspaceFilePanel` 写 `localStorage` 这条档位 B 违规改不改、怎么改，由开发者决定。本 Task 只记录。

## 验证

1. `bun run --cwd packages/neuro-book typecheck`。
2. 与改动表面相关的聚焦测试。
3. **产物门禁**：跑一次产品构建，检查路由、模块图、产物文本与清单中不存在 Lab 模块、fixture、开发绝对路径或识别标记，访问 Lab 路径得到正常的不存在结果。顺带确认组件旁的 `.md` 文件没有被打进产物。
4. 开发入口下 Lab 可打开，三个组件均可挂载、可切场景、可切三种容器；桌面按不低于 1440px、手机按 `390×844` 记录实际视口值。
5. `WorkspaceFilePanel` 在清单中可见、不可挂载、显示不可挂载的原因，且不给出任何 fixture 替代结论。
6. 同一场景重复打开或重置后，初始输入与可观察状态一致。
7. 确认无新增 console error 或 warning。

## 完成门禁

- 三个组件在 Lab 中可挂载、可交互；`WorkspaceFilePanel` 可见不可挂并说明原因。
- 组件索引来自扫描组件文档，仓库中没有第二份手写组件清单。
- 产物中不含 Lab、fixture 或开发路径，且该结论来自实际构建输出而非静态阅读。
- 三份新组件文档符合组件规范，frontmatter 能力标签与实现一致。
- fixture 不要求凭据、网络、真实 Project/Session、Provider/Model 或浏览器持久化状态。
- 未运行或未授权的项目标注为未验证，不以静态阅读代替执行结果。
