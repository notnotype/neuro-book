1. [重要][正确性] 外框开启时 #app 是 position:fixed，它自成层叠上下文，把通知与离线横幅压到模态遮罩与命令面板之下
位置：packages/neuro-book/src/web/styles.css:146（html[data-desktop-frame] #app）；受影响方：packages/nb-ui/src/components/feedback/NotificationStack.vue:137-138（z-index 9050，不经 Portal，渲染在工作台页面根里）、styles.css:110 的 .nb-offline-banner（z-index 2147483000）。
现象：position:fixed 总是建立层叠上下文，#app 之内所有 z-index 都只在它里面比。登记表与 ui-development-spec 2.1 约定“通知高于所有模态层，模态开着时出的通知也看得见”，离线横幅“刻意压住对话框与命令面板”；外框开启后这两条都不成立，body 下的模态遮罩（9000 起）、命令面板（9200）整块压在它们上面。普通浏览器里 #app 不定位，行为不变，所以 e2e 的“不带标记”对照看不出来。
核实：探针页 #app{position:fixed;inset:36px 0 0 0;overflow:auto} 里放 z-index 9050 的固定块，body 下放 z-index 9000 的全屏遮罩，elementFromPoint 命中遮罩；把 #app 改成 position:static 后命中通知。测试没有覆盖：desktop-frame.e2e.ts 没有“模态开着时出通知”或“离线横幅盖在对话框上”的断言。
改法：#app 不用 fixed。外框开启时视口不滚动，html 是 overflow:hidden，所以 position:absolute; inset:var(--nb-window-frame-offset) 0 0 0（包含块是初始包含块，大小就是视口）同样得到固定盒子，z-index 为 auto 时不建立层叠上下文，内部 fixed 子孙的包含块也仍是视口。补一条 e2e：外框开启 + 打开对话框 + 发一条通知，断言通知在遮罩之上（elementFromPoint）；离线横幅同理。

2. [重要][正确性] 窗口按钮被鼠标点击后拿走焦点：编辑器失焦，之后按空格或回车会再次触发按钮
位置：packages/neuro-book/src/web/DesktopFrame.vue:31-35（三个 button，tabindex="-1"，没有 mousedown 处理）；packages/neuro-book/src/web/host/close-ui.ts 的按键放行 `[data-desktop-frame-root]`。
现象：tabindex="-1" 只是不进 Tab 顺序，鼠标点击照样把焦点移到按钮上。用户在编辑器里打字、点“最大化”，焦点离开编辑器落在按钮上，接着打的字没地方去；按空格或回车就再次触发刚点过的按钮（最大化又还原，或者再点一次“最小化”后恢复时按空格又最小化）。系统标题栏按钮不拿页面焦点，计划与 DesktopFrame.md 都说“同系统按钮”，这一点没做到。
核实：探针页 contenteditable 聚焦后点一个 tabindex=-1 的按钮，document.activeElement 变成按钮（Chrome 156）。DOM 测试与 e2e 都没有断言点击前后焦点不变。
改法：按钮写 @mousedown.prevent（阻止焦点转移，click 照常触发）；加断言“编辑器聚焦时点最大化，activeElement 不变”。这样焦点不会落在外框里，close-ui.ts 的 installCloseKeyGuard 里为 `[data-desktop-frame-root]` 开的放行也可以去掉（它只为焦点在按钮上的按键存在），少一处与关闭层的耦合。

3. [重要][正确性/文档] 关闭询问期间“窗口照样能拖动”不成立：关闭层的遮罩自己是全屏 no-drag
位置：docs/specs/runtime/browser-host.md 输出 10（“窗口外框例外，窗口照样能最小化、最大化与拖动”）；packages/neuro-book/src/web/CloseLayer.md（新增那一行“询问期间窗口照样能最小化、拖动”）；packages/neuro-book/src/web/host/close-ui.ts 文件头同样的话；styles.css:152 的浮层规则。
现象：关闭层是两个 nb-ui Dialog，遮罩与内容 Portal 到 body 下，晚于 [data-desktop-frame-root] 出现在文档里，全屏 fixed inset-0。外框开启时它们被 `body > :not(#app, [data-desktop-frame-root])` 标成 no-drag。拖动区域按树序合并、后写的 no-drag 扣掉先写的 drag（计划依据 frame-probe-r1 第 7 条：DOM 在后的 no-drag 浮层压在拖动条上，命中 HTCLIENT），所以询问期间后备标题栏与工作台标题栏都拖不动，双击最大化也没有。能用的只有三个按钮。输出 12 自己写了“模态开着时整个窗口因此不能拖动”，与输出 10 互相矛盾。
核实：从代码推断。Windows 证据 windows-frame-r1.txt 没有测询问期间（只在第 8 条测了无询问的关闭），Task README 的“Windows 验收全过”比计划“验证”一节列的项目少：没有“开着的对话框是 HTCLIENT”“有未保存修改的关闭询问与询问期间最小化”“命令面板盖住标题栏”。desktop-shell 场景 15 若列了“关闭询问期间能最小化”，也没有证据。
改法：二选一。（a）把输出 10、CloseLayer.md、close-ui.ts 的话改成“能最小化、最大化与关闭，拖动不可用”，与输出 12 一致；（b）真要拖动，就让关闭层的遮罩在顶部 36px 不盖外框区域或写 drag，并在 Windows 上实测。无论哪种，补上 Windows 一轮询问期间的实测再写“全过”。

（补充第 3 条：desktop-shell 验收场景 15 确实写了“点关闭……询问期间还能最小化”，windows-frame-r1.txt 没有这一项的证据，README 的“Windows 验收全过”应改为“除询问期间与开着的对话框、命令面板的命中测试外全过”，或补测。）

6. [建议][测试] e2e 的“可交互部分都是 no-drag”断言抄了实现的选择器，是自证
位置：e2e/desktop-frame.e2e.ts 的 INTERACTIVE 常量与 WorkbenchTitleBar.vue 新增的非 scoped 块里的 :is(...) 列表。
现象：两处列表几乎逐项相同（button、a[href]、input、[role=menuitem]、[tabindex]:not(-1)、[data-workbench-item]），实现漏了某一类（例如以后加了 role=menuitemcheckbox、summary、label、contenteditable、带 title 悬停提示的 span）时，测试用同一份列表仍然通过。“有点击或悬停行为的一切”这条合同没有被独立地验证。另外只量了计算值，没有真正点进去过的位置（Windows 证据也只扫了左端标志与几个已知元素）。
改法：测试里独立枚举：标题栏子树里 getComputedStyle(el).cursor 为 pointer 的、能 focus 的（el.tabIndex >= 0 或 button/a/input）、带 title 属性的、有 hover 样式的元素，要求都是 no-drag；或者反过来，枚举标题栏上所有 drag 的叶子元素，要求它们没有 title、cursor 不是 pointer、不可聚焦。

7. [建议][正确性] window 的 blur 在焦点移进 iframe 时也会触发，按钮字形会在窗口其实在前台时变淡
位置：packages/neuro-book/src/web/host/desktop-frame.ts:104-107（onBlur 直接 update({focused: false})）；产品里有 iframe：packages/neuro-book/src/plugins/html-preview/web/components/HtmlPreview.vue、nb-markdown 的 html-embed。
现象：用户点进 HTML 预览的 iframe，父页面 window 收到 blur，但 document.hasFocus() 仍为 true。外框把它当成“窗口失去前台”，窗口按钮变成次要文字色，直到焦点回到父页面。
核实：探针页里父窗口聚焦按钮后点 iframe 里的按钮，日志是 “blur hasFocus=true”（Chrome 156）。
改法：onBlur 里写 update({focused: document.hasFocus()})；DOM 测试补一条“blur 时 hasFocus 仍为 true 不变淡”。
