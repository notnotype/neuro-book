# w00046 t01 拉远看审查（Sonnet）：desktop-distribution 提案

### 1. 发布流水线的前提与现有发布脚本对不上：npm trusted publishing、标签与版本号、发布范围（4.8 第 1、3 段）
结论：流水线这一段按“只有两个包、`npm` 直接发”写，而仓库现在的发布链不是这样，照写会在第一次打标签时失败。依据：
- `scripts/release/publish.ts:178-212`：门禁先跑 `npm whoami`（CI 里没有登录态会直接 GateFailure），真正发布走 `bun publish`。npm 的 trusted publishing（GitHub OIDC）要求 npm CLI 11.5.1 以上自己去换令牌（https://docs.npmjs.com/trusted-publishers/ 、https://github.blog/changelog/2025-07-31-npm-trusted-publishing-with-oidc-is-generally-available/），我没搜到 Bun 官方支持 `bun publish` 走 OIDC，只有第三方做法（https://github.com/victor-software-house/bun-release ，用 OIDC 换短期令牌再交给 `BUN_CONFIG_TOKEN`）。提案写“`release:publish` 已能跳过 registry 上已有的版本”，没写它要改发布命令或加换令牌这一步。
- `docs/standards/repository-workflow.md:89-93`：发布清单是 11 个包（9 个源码包加应用与 SDK），源码包版本各自独立，只有应用与 SDK 共用产品版本。提案 4.8 第 1 段写“标签版本与各包 package.json 的版本一致”，对 9 个源码包不成立；第 2 段 ubuntu 只“打 npm 的两个包”，而现行 `release:smoke` 与 `release:publish` 处理的是 11 个。必须先定：标签只代表产品版本（应用、SDK、桌面包），源码包按“版本没发过才发”的现行规则带着发，还是拆成两条线。
- trusted publisher 要逐个包在 npmjs 网站上配置，并且包得已存在才能配（npm/cli#8544，见 bun-release 的说明）；11 个包都要配，这个一次性成本与顺序提案没提。
- `docs/standards/repository-workflow.md:83` 写“发布渠道是 npm；GitHub Releases 只留旧应用 0.10.x 的历史版本”。提案第六节说要改这一节，但没提 Release 页面上新旧两类产物并存（0.10.x 旧应用与 v2 桌面包）时下载页与更新源怎么避免混淆；更新源 `release.baseUrl` 指向“最新 Release”，旧版本号的 Release 会被 GitHub 的“最新”判定影响。
建议：4.8 补一句“发布命令改动”的取舍（改 `publish.ts` 在 CI 里用 `npm publish` 发同一份 tarball，保留 `bun publish` 给本机；或 OIDC 换令牌），并把标签与版本的对应关系写成合同。

### 2. 自动更新加“不签名”的组合：更新通道成了单点信任，且官方文档本身建议签名（4.6、五安全）
结论：提案把它写成“已知代价”，但没有比较更便宜的缓解。依据：Electrobun 自己的文档写明 `update-v2.json` 里的摘要只核对载荷与清单一致，不是清单的签名，“需要真实性时请用平台的代码签名”（research/electrobun-src/docs/src/content/docs/electrobun/guides/updates.mdx:70-76）。也就是谁能改 GitHub Release（账号被盗、令牌泄露、CI 被投毒）谁就能给所有已装用户推可执行文件；比首次下载安装包的风险大，因为首次下载用户至少还看到 SmartScreen 警告，更新是静默换上的。另外 `updateAvailable` 的判定是 `manifest.hash !== info.hash`（package/src/sdks/main/core/Updater.ts:1863），不看版本号高低，所以更新源也能把用户“更新”到旧的有漏洞版本。
有更小的做法可选：第一版更新只提示并打开下载页（与便携版一致，4.5 已为便携版这样做），把“静默换上”推迟到能验签名时；或应用里钉死一个公钥，下载后自己验分离签名（minisign 或 ed25519，不需要买证书）再交给更新器，签名私钥只放在 GitHub 的环境密钥里。提案没有评估这两条路，也没有说“不买证书”的决定是否覆盖了“更新也不验签”。
另：回滚一段的“更新器会不会接受版本号更低的最新版还没查”可以直接回答：按上面的判定，只要哈希不同就会更新，所以把旧版标为最新会被已装用户装上（需在 Windows 上实测确认）。这既回答了回滚，也印证了上一段的降级风险。

### 3. 桌面壳的取舍理由偏单薄，ADR 0033 决定 6 列出的另外两种选项没有出现在方案里（4.1、4.2）
结论：ADR 0033 决定 6（docs/adr/0033-app-delivered-as-built-npm-package.md:27）要求“在 Electrobun、Tauri、Electron 里实测后选”，并列了两个维度：运行时（用户的 Bun 或捆绑 Bun 的目录包）、界面（浏览器、浏览器安装的独立窗口或原生窗口）。本稿的 4.1 表只有“npm 包”和“桌面包”两行；4.2 记的是开发者 2026-11-13 的指定（Electrobun 为主、Electron 为候选），理由是“主进程就是 Bun”“包小”“自带安装与更新”。Tauri 完全没有出现；Electron 的对照数字来自旧应用 2026-08 的另一个产品体积（提案第三节，t01 README 里的 legacy t143/t145），不是同一条件下实测。
我没查到更早的记录把“只实测 Electrobun”作为取舍写下来：t01 README 只说“开发者决定直接用 Electrobun”。因此：
- 如果这是开发者的产品决定，提案应当明说“跳过了 ADR 0033 要求的三选一实测”，并给出一句现在仍成立的理由，由开发者确认 ADR 决定 6 的要求被他的决定取代（必要时在 ADR 里记一笔）。
- “主进程本身就是 Bun”的理由对本方案其实没有用上：壳只做窗口、拉子进程、标准输入停止、更新（4.3），服务端是独立的 Bun 进程，换成别的壳也一样。真正差别在体积、安装与更新器、以及 Hutch 的成熟度。提案把“Bun 同一运行时”当主理由，容易让后面的人以为壳与服务端有耦合。
- 没被评估的更简单做法：目录包加启动器，用系统 Edge 的 `--app=http://127.0.0.1:端口` 开独立窗口（Windows 11 自带 WebView2/Edge，4.1 表里本来就写“便携版共用同一套产物”）。它没有安装程序、更新器和 Hutch 依赖，便携版天然成立；缺点是没有开始菜单集成与自动更新、窗口行为不由我们控制。是否值得作为“第一版”或兜底，应该在提案里有一段比较，哪怕结论是“不选，因为……”。
- 便携包（4.5）本身就是“目录包”。既然目录包已经要做，应当说明桌面版相对“目录包加浏览器窗口”多出来的价值到底是安装、更新和窗口行为里的哪几项。

### 4. Bun 版本被壳的版本钉死，与服务端共用状态根时存在运行时版本不一致（4.2、4.4）
结论：提案把“Bun 版本由 Electrobun 版本决定（2.0.6 对应 Bun 1.4.4）”当优点写，其实是一处升级耦合。依据：Electrobun 的配置校验拒绝 `build.bunVersion`（electrobun-src/package/src/config/validate.ts:28-41；docs 的 migrating-to-v2.mdx:178 写“具体的 Electrobun 版本提供它自带的运行时版本”）。后果：
- pi-natives 要求 `bun >= 1.4.4`（t01 README 提到），现在刚好等于下限；以后 pi-natives 或服务端依赖要求新的 Bun 时，只能等 Electrobun 升级，或换壳。提案没写这个约束，也没写升级顺序。
- 桌面版与 `nbook`（用户自己的 Bun，ADR 0033 决定 1）共用 `%LOCALAPPDATA%\NeuroBook`（4.4），而插件、SQLite 文件、项目子进程可能在两个 Bun 版本之间切换。提案没有说明状态根里有没有“被哪个版本写过”的标记、新旧版本互相打开时的行为（ADR 0033 后果一节只处理了“nbook start 遇到版本不同的实例时报错”）。4.3 的第 1 条却相反：壳发现有实例就直接打开它的地址，没有版本核对。那个实例可能是用户 Bun 起的老版本 `nbook`，壳的“自动更新到新版本”与它的页面和 `project.js` 版本因此可能不一致。建议在 4.3 写明版本不同时的处理（报错、提示，或只接管自己版本相同的实例）。

### 5. 外部工具向导是现在不需要、且与桌面发行无关的范围（4.7、七、六）
结论：它是本提案里最不必要的一块。依据：t01 README 记录 v2 产品代码自身不调用 git 或 python，Agent 的命令工具跑在 pi-natives 内嵌 shell 里，40 多个命令自带，中文和管道在 Windows 上实测都正常；只有 Agent 里用户或模型自己执行 `git`、`python` 才需要外部程序。没有证据说明用户会卡在这里（没有失败样例，没有用户反馈，这些是推断）。而方案规格是完整的：每个工具的登记、两种来源（PortableGit、uv 管理 Python、winget 调起）、下载地址与哈希随发行固定、可选国内镜像，并新建 Spec `runtime/external-tools`。几处具体问题：
- 它与桌面壳没有技术依赖：npm 版用户（含 Linux、macOS）同样会遇到“找不到 git”。把它塞进桌面发行提案，会让桌面发行的验收与它绑在一起。建议拆成独立提案或只留一句“后续”，4.7 缩成两三行（t05 已经是独立 Task）。
- “下载地址与 SHA-256 随发行版固定”意味着每次发布要更新工具版本表，PortableGit 与 uv 的升级节奏成了发布流程的一部分；“可选国内镜像”是没有证据的提前优化。
- 随 NeuroBook 安装的工具放进数据目录，“NeuroBook 负责升级与卸载”，这是一个包管理器的责任面；运行时可能被 Agent 命令用到的 PATH 注入、与系统已有 git 冲突的优先级都没有讨论。
- 第一版可以只做“检测并提示用户去哪里装”（零下载、零哈希、零卸载责任），观察用户是否真的需要自动装。

### 6. 状态根的位置与标识符等一次性选择没有写进提案，但以后难改（4.4、4.5、4.6）
结论：下面几个值一旦发到用户手里就很难更改，提案没有列为决定：
- Electrobun 的 `identifier` 与 channel：决定 `%LOCALAPPDATA%\<identifier>\stable`（4.4 表）、WebView2 数据目录、更新器自己的位置；改它等于所有已装用户要重装。提案没有给出取值，也没说它与状态根目录名 `NeuroBook` 的关系。
- 更新源：`release.baseUrl` 指向 GitHub Releases（4.6）会写进已装应用；仓库改名、迁移、改成私有、GitHub 在本地区访问不稳（环境说明里提到国内访问国际资源慢）都会让已装用户收不到更新。更新器如何容错（比如多个镜像）没有设计。
- 窗口加载的页面来源是 `http://127.0.0.1:端口`；缺省端口 4217 被占用时服务端会顺延 100（docs/specs/runtime/server-host.md:40）。WebView2 的 localStorage、IndexedDB 按来源分区，所以端口一变，页面里按来源保存的前端状态就“丢了”。提案没提端口选择：桌面壳是否固定一个端口，与 `nbook` 同时跑时谁让谁。
- Hutch 的“应用名 + identifier + 渠道”决定的卸载项与数据位置，换壳（比如以后换成 Electron）时需要迁移安装与更新通道。提案说“接口：服务端合同不变，壳只是又一个调用方”，这对服务端成立，但对已装用户的安装与更新通道不成立；这是换壳的真实代价，值得在 4.2 写成一条。

### 7. 便携版的“便携”并不完整，且第一版接受的缺口应写进用户可见的合同（4.4、4.5、决策记录第二条）
结论：便携版的状态根随程序，但 WebView2 的数据仍写在 `%LOCALAPPDATA%\<identifier>\stable`（4.4 表第二行，决策记录已接受）。这意味着：在 U 盘上用，会在别人电脑上留下浏览器缓存与 Cookie；同一个便携目录在两台机器上使用，前端本地存储不会跟着走；便携版与安装版若 identifier 相同还会共用 WebView2 数据，页面状态互相串。提案已接受该缺口，但“适合 U 盘”（二、目标）与它冲突；建议目标处改成“解压即用，状态根随程序走，浏览器缓存仍在本机”，别让用户以为可以不留痕迹。另外便携版靠“程序目录里的标记文件”识别，没说标记文件被误放进安装版目录时怎么办（安装版会突然换状态根，作品登记像丢了）；应说明标记文件只由 CI 打包写入、安装包里不会出现。

### 8. 第三节与 4.8 掉进实现与测量细节，架构取舍反而没写（五、整体结构）
结论：第三节大量是实测数字与命令级细节（runner 上 112 秒、82 秒、4.7 秒、206 毫秒、setup 在无桌面会话里不退出），这些属于 t01 的证据，提案里只需要“能做到”的结论加证据链接；4.8 里 Hutch 0.29.0 与 `HTTPS_PROXY` 的细节、冒烟用 `launcher.exe` 的做法也是实现层。同时，读者要靠自己推断的取舍没有讲：
- 为什么桌面包与 npm 包版本号绑定（4.1“版本号相同”）：绑定意味着桌面版小修也要走 npm 发布与 11 个包的清单；反过来 npm 的修复也强制发桌面包。是否接受？
- 壳崩溃时服务端“不留孤儿但没走有序停止”（第三节）与“数据安全靠 SQLite 与原子写入”的结论只在 t01 README 里，提案没有把它列为风险，实际是用户会遇到的（壳被杀、系统注销、更新时强制结束）；至少应在“数据与安全”一节里说明崩溃时 Agent 会话、进行中的工作流的状态如何恢复，这是产品数据（AGENTS.md 说它们是可审查的产品数据）。
- 关最后一个窗口即停服务（4.3）：Agent 在后台跑长任务时关窗会中断它。ADR 0033 决定 5 把“后台运行”划给别的提案，但提案没有说明关窗时有任务在跑怎么办（提示、延迟停止、或照停）。
- 第六节的 Spec 改动清单只写了名字与要点，没有写 `runtime/desktop-shell` 与已有的 `runtime/cli`、`runtime/server-host`（实例认领、`--stop-stdin` 合同）的边界；4.3“壳只是又一个调用方”应当落到“哪些现有合同变成对外合同”的清单上（`--stop-stdin`、`Listening on` 输出行被壳按文本读取）。壳读文本行来取得监听地址是一个隐含接口，按 AGENTS.md 不应按文案做分支，值得在提案里定成合同（例如读实例认领的应答而不是标准输出）。
