### 1. 状态根单实例不能保护同一安装目录的更新（第一轮 4 未解决）
- **严重程度**：重要；**类别**：不变量、并发。
- **位置**：修订稿 4.3:84、4.4:116、4.6:130；Electrobun Updater.ts:631-632、742-745、2368-2393；extractor/main.zig:7456-7486。
- **现象**：桌面锁按状态根派生，环境变量允许同一份安装使用不同状态根。用同一安装目录分别以状态根 A、B 启动，可合法得到两个壳和两个自有服务端。A 关末窗、停完自己的服务端便调用 applyUpdate，此时 B 及其项目仍使用待替换目录。修订稿只解决了同一状态根的双壳，没有解决第一轮指出的“同一安装目录的所有使用者”。
- **为什么是问题**：更新目标与暂存区按 identifier/channel 的安装目录定位，不按 NeuroBook 状态根隔离。助手只等待发起者的 launcher PID，再重命名整个 app；不等待 B。Windows 下会遭遇文件占用导致替换失败；若重命名成功，B 仍运行旧代码而随后读取/启动的资源已被移动或替换。把“非自有服务端用自己的文件”当普遍保证也不成立：随包应用本身保留 nbook.js，或者另一个状态根的壳，均可从同一载荷启动。
- **如何核实**：上述源码确认两个不同的隔离键和只等待单个 parent_pid；4.4 明确允许 NBOOK_STATE_ROOT 覆盖。此为源码与配置组合反例，未运行 Windows 双实例更新。
- **建议改法**：区分“按状态根协调窗口”与“按实际安装目录协调换文件”。更新前取得安装级排他许可，确认该载荷的所有壳和后端已退出；不能协调的使用者存在时推迟应用更新，不停止不属于自己的服务端。加入同安装目录、两个状态根的真实更新验收。

### 2. 关闭前握手没有页面失联的结束路径
- **严重程度**：重要；**类别**：正确性、失败恢复。
- **位置**：修订稿 4.3:97-99、第六节:168-170；Electrobun proc/native.ts:2709-2719，docs apis/browser-view.mdx:232-239、browser/electroview-class.mdx:94-97。
- **现象**：修订后只有“页面同意后才真正关窗”，没有规定页面加载失败、RPC 尚未建立、页面 JS 卡死或询问一直不回答时怎么办。后端停止的截止只在最后一窗已经关闭之后开始，覆盖不了前面的握手。启动失败页和失联页面同样可能没有可回答的产品运行实例。
- **为什么是问题**：Electrobun 确实支持同步否决 will-close，但不会等待异步返回；必须先否决，再等页面回信。executeJavascript 没有返回值且不保证执行，typed RPC 的超时也只是报错，不替产品决定是否允许关闭。照“只收到同意才关”实现，页面故障会使关闭和更新退出永远停在壳运行中，用户只能强杀；若实现者擅自超时放行，又把正常关闭变成无提示丢稿。此为新握手缺少失败合同，不重复第一轮“完全没有询问”的问题。
- **如何核实**：上述第三方源码确认同步否决和异步通道的边界；editor.md:166、179、264 规定保存失败保留修改、结算输入和取消语义。未运行 Windows 卡死页面。
- **建议改法**：定义请求代次、单窗口至多一个待决询问、超时/通道断开与迟到回答的处理；无产品页的启动/错误窗口直接由壳判定，已进入编辑的页面无应答时由原生对话框提供“继续等待 / 取消 / 强制关闭并丢失未保存内容”，不得自动当作保存成功。正常退出与更新退出共用这条路径，验 RPC 未就绪、卡死和保存失败。

### 3. 调用 Updater 换上更新会立即重开应用，不是退出后等待下次打开
- **严重程度**：重要；**类别**：正确性、接口。
- **位置**：修订稿 4.6:128-130；Electrobun Updater.ts:2348-2440；extractor/main.zig:7299-7325、7533-7555。
- **现象**：新时序要求最后一窗关闭、后端停完后调用更新器换文件，并承诺“退出时换上，下次打开就是新版本”。Electrobun 2.0.6 的 applyUpdate 没有“只应用、不重启”选项；助手完成替换和系统集成后无条件 launchAppliedUpdate，再生成本次结果。
- **为什么是问题**：用户关最后一个窗口，本应结束的桌面应用会被更新助手重新打开，并重新启动服务端。提案没有批准退出即重启，也没有设计如何让新进程只完成更新而不再开窗。简单把 applyUpdate 放到停止完成后，解决了第一轮的停服先后，却兑现不了修订稿选定的用户行为；改为不调用它，普通退出又不会自动激活暂存包。
- **如何核实**：上面两段源码直接串起 applyUpdate → 助手 → launchAppliedUpdate；后者在 Windows 以 launcher 路径创建新进程，参数里没有延迟启动或禁止重启。属于固定 2.0.6 的实现核实，未运行 Windows 真更新。
- **建议改法**：在提案中选定可执行做法：扩展助手支持只应用不 launch，或新进程识别持久化的“退出应用更新”意图、确认更新结果后不开窗口立即退出。若改成“退出会重启”，那是用户可见决定变更，应明确提出而非隐含接受。验关末窗后程序是否保持退出。

### 4. 已有桌面壳的转交分支绕过了新加的版本门禁（第一轮 1 未解决）
- **严重程度**：重要；**类别**：不变量、兼容。
- **位置**：修订稿 4.3:84-93；runtime/cli.md:64-65、74-87。
- **现象**：4.3 先取桌面锁，失败就把“开一个窗口”交给原壳、自己退出；只有拿到锁的壳才核对服务端版本。旧版本 A 的壳还在运行时，从新装的 B 或另一个目录的 B 打开同一状态根，B 在第一步就退出，实际开窗的仍是 A；新增连接判定表根本没有执行。
- **为什么是问题**：修订声称与 nbook start 相同，但 CLI 在复用前把本命令版本与实例 version 比较，不同则 version-mismatch。桌面转交协议没有调用者的产品版本、接收壳的版本及拒绝结果，无法区分“同版第二次启动”与“用户已经打开新版”。这就是第一轮“用户以为启动新版，实际仍用旧服务端”的另一条现成路径，不是要求再次质疑共用状态根。
- **如何核实**：对照提案两段的明确先后和“拿到锁之后”限制；现有 cli/start.ts:79-93 在打开前核对 PRODUCT_VERSION。未虚构双版本 Windows 实测。
- **建议改法**：桌面 hello/转交应答带协议版本、壳产品版本及生命周期；发送者先核对版本，不同版明确提示先退出原壳，不发送开窗。开窗只允许请求当前壳自行生成的本机页面，不接收任意 URL；获得成功应答后发送者才退出，异常/停止中有截止和恢复规则。补旧壳 A 加新启动 B 的验收。

### 5. 多窗口同时关闭会漏掉最后一窗的任务确认
- **严重程度**：重要；**类别**：并发、不变量。
- **位置**：修订稿 4.3:97-99、第六节:168；runtime/browser-host.md:91、96，runtime/projects.md:90。
- **现象**：新流程按每个窗口发起异步关闭前询问，并在“这是最后一个窗口”时提示任务会中断，但没定义跨窗口关闭的串行或提交阶段重判。仅剩 A、B 两窗时，先后快速点关闭：A 的询问未结束，B 也进入询问；两者看到的窗口数都是 2，都不提示任务。两次保存/许可随后完成，两个窗口都关闭，壳按末窗规则停止服务端。
- **为什么是问题**：任务是服务端/项目的状态，不随一个窗口关闭而结束；全局停止才中断它。把“是否最后一窗”在异步询问开始时各算一次，不能保证真正提交最后一次关闭时已有用户授权。4.3 的三态只保护后端已经开始停止之后，不保护两个正在询问的窗口。开发者已要求最后一窗有任务时由用户决定，不能被快速连续关闭绕过。
- **如何核实**：按修订流程即可排出两次许可重叠的合法时序；browser-host 上述条目和 projects 的全局停止说明确认任务与窗口不是同一个寿命。没有声称做过 Windows 并发关窗实验。
- **建议改法**：由壳串行提交窗口关闭，或维护待决关闭集合，在真正关闭最后一扇仍存活的窗口前重新判定任务并取得一次全局许可；取消保留必要窗口。转交开窗与这一提交同一把协调，不在停止中向将退出的壳盲目添窗。验两窗关闭握手重叠、其中一窗取消和询问期间转交开窗。

### 6. 同版本摘要不符一律失败，意外取消了九个源码包的独立发布语义
- **严重程度**：重要；**类别**：发布、兼容。
- **位置**：修订稿 4.8:140、146、151；ADR 0029:27、40；scripts/release/publish.ts:190-199、publish.test.ts:53-62。
- **现象**：4.8 一面承诺九个源码包保留各自版本、没发过才发，一面把“npm 上已有同版本而摘要不同时失败”无条件套在全部 11 个 tarball。一个被应用 bundle 的源码包改了但本次不发它，只提升产品版本，本来是受支持的发布；第 2 步仍会重打那个源码包，第 3 步便因它与 registry 的旧字节不同而终止产品发行。
- **为什么是问题**：现有发布器有意区分两类差异：待发包运行时依赖它就阻断；应用把它打进 bundle、不在 npm 依赖图里时只提醒。本轮为保证“同一发行重跑不能换字节”加的规则，误把“本次没有要发布的独立包”也当成必须与历史相同，实际上迫使底层源码包随每次产品改动提版、发布，违背修订刚保留的 ADR 0029。不是要求容忍同一产品版本的不同载荷。
- **如何核实**：在指定 worktree 直接调用真实 blockingStalePackages：pending=[@notnotype/neuro-book]、stale=[@notnotype/nb-harness] 且应用无该运行时依赖，输出 blocked=[]；退出 0。现有永久测试也明确覆盖这项语义。未访问 registry、未发布。
- **建议改法**：先冻结本次实际待发集合与其摘要。对本次发行身份已发出的应用/SDK及待发集合重跑坚持完全相同；对原已发布、这次只参与 bundle 的源码包保留原有依赖闭包判断。若真正想取消独立发布，应单独修改决定，不能靠重跑门禁暗改。

### 7. “不回拨”只处理 GitHub 最新项，较旧发行的 npm 续发没有路径（第一轮 13 未解决）
- **严重程度**：重要；**类别**：发布、失败恢复。
- **位置**：修订稿 4.8:148-151；npm CLI v11.5.1 lib/commands/publish.js:110-112、152-162。
- **现象**：旧标签 A 在构建后、发布应用/SDK前失败；较新标签 B 先完成发布；重跑 A 时按约定复用原产物、补发未发布版本，并只在 GitHub 那一步不设最新。但方案选定的 npm publish <tarball> 没有为这个较旧版本指定 dist-tag；npm 11.5.1 发现 registry 已有更高稳定版，会直接拒绝隐式 latest，A 到不了补 GitHub Release 的步骤。
- **为什么是问题**：串行只防同时写，不保证按版本排队，也不阻止新版本完成后重跑旧失败任务。现有“缺哪个补哪个”与“不高于最新就不设最新”只对 GitHub 的分支作了处理，未给 npm 相同的分支。不能为恢复而简单补 --tag latest，那会显式允许把 npm latest 拉回旧版；九个独立版本包还必须逐包比较，不能只比较产品标签。
- **如何核实**：已读取 npm/cli 固定 v11.5.1 源码 https://raw.githubusercontent.com/npm/cli/v11.5.1/lib/commands/publish.js ：160-161 行直接抛 Cannot implicitly apply the "latest" tag。GitHub 官方并发文档也明确等待顺序不是分发/版本顺序。未执行真实发布。
- **建议改法**：在同一个发布排他区内，逐包读取当前 registry 版本和 dist-tag；旧版未发项明确使用不推进 latest 的历史标签发布，再补齐该发行的 Release。查询失败则停，不盲发。保留已发同版的摘要核对；验 A 未发完、B 成功、A 续发且两个 latest 均不倒退。

### 8. 端口变化的损失边界写反了：主题语言会恢复，布局与标签却会换一份
- **严重程度**：建议；**类别**：文档、兼容。
- **位置**：修订稿 4.3:95；第一轮处理结果 Sonnet 6；settings/configuration.md:29-31、234，ui/workbench-layout.md:250-254，storage/persistence.md:30-32。
- **现象**：新增文字把客户端身份、主题、语言都说成存在按来源隔离的浏览器存储里，端口顺延后三者消失、前端设置回默认。实际主题和语言的权威值在状态根 settings.json（主题可由项目层覆盖）；localStorage 只缓存首帧外观和启动语言，插件就绪后会取回原设置。真正随新客户端身份换分区的是 workbench.layout、layout-template 和 editor.tabs，包括打开的文件、光标与布局。
- **为什么是问题**：把 boot.ts 的读缓存误当成配置真相源，夸大了语言/主题永久回默认，却把工作上下文不可见缩成无关紧要的前端设置。此时数据未删除，只是切到新客户端分区，端口恢复后旧分区还在。开发服务缺省同时占 4217/4218/4219，开发与正式实例可以并存但必有一方顺延 100；这不只发生在不认识的“别的程序”占端口时。
- **如何核实**：settings/web/plugin.ts:2-3、57、265-278 明确用户层与快照后应用语言；workbench/shared/contracts.ts:146-155 定义主题配置。上述三个 Spec 将布局和标签定为 local、按客户端身份隔离。server-host.md:109 定义开发端口组。未启动开发服务或浏览器验证。
- **建议改法**：分清首屏缓存暂时缺失、用户/项目配置会恢复、客户端 local 工作上下文切换这三件事；把 dev/桌面与安装/便携并行时的顺延列为验收。可继续接受现有端口策略，不要求本轮加迁移机制，但不能用错误的受影响数据来接受取舍。

## 未发现问题的方面

- 第一轮 omp 2 的同状态根多个独立壳问题，改为一个壳统一持有全部窗口，这个方向可消除原来的窗口计数割裂。采用独立命名空间的内核持有套接字时，壳被结束后认领可释放；桌面锁不是让服务端自己拿的 server.sock。两个不同状态根各一把锁并不冲突；本轮第 1 条限定的是它们共用同一安装载荷时的更新排他。
