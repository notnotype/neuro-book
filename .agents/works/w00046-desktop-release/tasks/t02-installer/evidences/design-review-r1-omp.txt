### 1. 更新会覆盖用户改过目标的同名快捷方式
- **严重程度**：重要；**类别**：正确性
- **位置**：固定副本 plan.md:24-26,54；desktop-shell.md:172-175；Electrobun 2.0.6 src/extractor/main.zig:2822-2831,2923-2930,2973-2995,4588-4635,7503-7534。
- **现象**：清理旧快捷方式时，`deleteObsoleteWindowsShortcut` 遇到当前同名路径直接返回；目标比对只用于清理旧名称。随后更新无条件对当前桌面路径执行 `CreateShortcut`、赋新目标并 `Save`，再启动新版。若用户把同名的有效 `.lnk` 改指别处，更新会把目标改回本安装；设置为关时，新壳第一次同步又会删掉它。
- **为什么是问题**：计划的 `other` 分支只能保护壳自己操作时看见的文件，保护不了更新前的用户修改。仅做一次正常更新后再删会验收通过，却漏掉用户原快捷方式被覆盖。当设置为开时，更新也会恢复用户手删的同名链接；这是上游写入，不是壳启动补建。
- **如何核实**：源码调用链已核对；Windows 待验：测试标识安装后把桌面链接改指另一无害目标，分别在偏好开、关时换上更新，检查目标及是否仍存在，同时检查开始菜单。
- **建议改法**：保留已定的安装器，明确“不动”仅约束壳，不承诺安装／更新保住同名文件；把覆盖及更新重建写为已知限制并加验收。若产品要求更新也保留用户文件，需让安装集成在写入前决定是否写，事后同步做不到，不能只改核心判定。

### 2. 安装后迁移桌面会让 2.0.6 在更新和卸载前拒绝旧清单

- **严重程度** 重要　**类别** 不变量
- **位置** 固定副本 plan.md:13,25,54,72，desktop-shell.md:175；Electrobun 2.0.6 src/extractor/main.zig:2786-2791,3586-3602,4844,5051-5058,6800-6823。
- **现象** 安装写绝对的桌面和开始菜单链接路径。若装后才启用 OneDrive 桌面备份，清单仍记旧路径；`validateWindowsUninstallManifest` 重取现在的系统目录，任一路径不等就返回 `InvalidUninstallManifest`。卸载入口和更新 helper 换包前都调用该校验，更新只对清单文件本身不存在走旧版兼容。壳若跟随新路径删除或重建，同样不会刷新旧清单。
- **为什么是问题** 这是 2.0.6 既有兼容限制，会使本方案依赖的更新后再同步到不了新壳。只验“已经重定向，再安装”看不到这个分支。目录不变时，即使同名桌面链接已经不存在，也不会因此使清单失效。
- **如何核实** 源码路径已核对。待在隔离 Windows 用户中先经 Setup 安装，再切换系统桌面目录，分别验证应用正常打开、更新 helper 的结果和卸载诊断。也跑一组先重定向再装的对照。
- **建议改法** 计划区分两种重定向，记录装后迁移的上游限制与实测恢复路径。壳继续按系统目录操作，别从壳补写清单、去旧目录删文件或退回写 `%USERPROFILE%\Desktop`。如果装后迁移必须受支持，需修安装集成的清单校验，评估升级或受控修补的代价。

### 3. 用缓存当作上一次页面值会在启动时补建链接

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:19,24-26,60，desktop-shell.md:143,173-174；packages/neuro-book/desktop/src/bun/index.ts:219-226,375-385；packages/neuro-book/src/desktop/desktop-settings.ts:23-52,98-106。
- **现象** 上次缓存为关、桌面没有链接。关掉应用后用户经设置文件把值改成开。下次首次页面报告为开，计划代入 `first=true, previous=false, existing=absent`，第 24 行没有限制首次，结果是 `create`。第 19 行补齐旧缓存与第 26 行“缓存没有为 null”也没有说明是整份文件不存在、还是此字段不存在／无效，现有解析会抹掉字段层面的差异。
- **为什么是问题** 输出 33 明说“不在启动时补建”。缓存是可能过期的启动显示值，不是本次运行的用户切换历史。自启不同，输出 27 的同步是对账，首次为开就允许补登记，现有 `syncLoginItem` 从不拿缓存判断开关转换。
- **如何核实** 按实际壳回调顺序代入：冷装无缓存／首个设为开 → 不补；运行后关→开且空缺 → 建；更新重建、缓存与首次页面均为关 → 仍须在 `same` 提前返回前删；缓存关、首个页面开、链接空缺 → 计划现规则补建。再验第二个窗口重复提交不触发。当前只有设计反例，未运行未实现的代码。
- **建议改法** 单独记录进程内上一次有效页面偏好，首次为 `null`，只允许本次已收到关之后的开触发建；首次为关仍做一次对账。首次与否由 `previous` 表达即可，勿让 `first` 和缓存推导两套互相冲突的历史。

### 4. 快速反向切换会让较早的 PowerShell 操作留下错误结果

- **严重程度** 重要　**类别** 不变量
- **位置** 固定副本 plan.md:24-26,50,60；packages/neuro-book/desktop/src/bun/index.ts:375-385,612-619；packages/neuro-book/src/desktop/shell.ts:628-639。
- **现象** 第 25 行把探测与修改分给两个进程，第 26 行只规定何时触发。按现有同步回调并列发异步操作：偏好关且链接空缺 → A 切到开，探测为空、建链接尚未完成 → B 切到关，探测仍为空、不删 → A 保存成功，最终偏好关但链接存在。重复的关值会被去重。开始停止后，现有出口只等更新器收口，随后放锁，没有等本项子进程。
- **为什么是问题** 现有 `syncLoginItem` 在同步回调内读写完注册表，不能给新异步端口提供先后保证。若改成阻塞等待，又会在慢桌面上阻塞壳的关窗等事件。缓存写入已有串行队列，但它不串行化操作系统副作用。
- **如何核实** 以上交错可由两个窗口反向修改、或单窗连切产生。Linux 用真实测试子进程在保存前设可观测关卡，交次新值再释放，断言最终文件与最后偏好一致、重复值去重，且最后关窗后无迟写；Windows 再验实际 `.lnk`。
- **建议改法** 同步更新进程内收到的偏好，再把完整“重查现状 → 判断 → 修改”交给单写者。最新状态须按接收次序收敛；停止时封新动作，等在途有限结束或取消并回收子进程后再放锁。

### 5. 用户层恢复为有效而值不变时，可能整次运行都不去掉更新重建的链接

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:26,50,60，desktop-shell.md:143,145,173；packages/neuro-book/src/plugins/desktop/web/plugin.ts:82-93，src/plugins/settings/backend/layer-owner.ts:140-165，src/plugins/settings/shared/instance.ts:104-125，src/plugins/settings/settings.test.ts:185-203。
- **现象** 同版本 `nbook` 服务端先读到快捷方式为关，再看到文件改坏，按现有规则保留关值、标记层无效。此时壳启动并复用服务端，桌面有安装器重建的链接。桌面插件在激活时因 `user.status !== "ok"` 不报告。用户修好设置文件且保留原值，配置实例只更新层状态，`onDidChange` 没有变值就不调用，壳收不到第一次快照。
- **为什么是问题** 输出 33 要依靠首次有效报告删链接；打开另一个新窗口可能才修正。现有自启也有同一缺口，按第 26 行照搬会把缺口扩给另一个系统副作用。已有设置合同测试明确断言层坏掉／修好而值不变时通知为 0 次。
- **如何核实** 在真实配置层／浏览器宿主合同用例里先查快照已为 invalid，再激活桌面入口，修回同一份关值；等待用户层为 ok，断言真正送出第一条 `desktop-settings`，下接壳测试断言第一次关触发删除。
- **建议改法** 在报告方同时观察用户层可用性与有效值，恢复到 ok 时交一份完整快照，包括没有变值的情况。离线或无效时继续抑制缺省值，壳按有效输入去重。

### 6. 更新器能算出通道根，不等于当前运行的是安装版

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:20,24,64、desktop-shell.md:145,175,182,187；packages/neuro-book/desktop/src/bun/index.ts:115-127,630-646；Electrobun 2.0.6 src/sdks/main/core/Updater.ts:540-590,2493-2508。
- **现象** 有正常 `version.json` 的 Electrobun `dev` 构建，即使在安装目录外运行，`resolveInstalledChannelRootForPlatform` 也返回计算出的 dev 通道根。Windows 的非 dev 分支只比可执行文件派生根的父目录与 identifier 根，没核对固定的 app 布局或安装清单。按计划直接取 `managed`，开发构建用缺省状态根会显示前两项，并可能在收值时改 Run 项或链接。
- **为什么是问题** 输出 27、33 明确排除开发构建和便携版。启动顺序不是问题：`loginIdentity` 在 `new DesktopShell` 与 `shell.run()` 前已赋值。问题在于把更新器的路径推导当作安装证据，布尔常量测试不会碰到这个分支。
- **如何核实** 用实际 Electrobun 2.0.6 dev 构建在安装目录外启动，确认本地元数据有效，核对通道根、两项事实和系统写入。用 stable 安装、stable 便携、安装版外加状态根覆盖分别对照。
- **建议改法** 启动时统一判定一次：便携标记排除、只认发行频道、核对真实程序位置及安装证据；`defaultStateRoot` 单独按根来源算。自启、链接和发给页面的事实共用该结果。取不到证据时不做系统修改并诊断。

### 7. 照搬 ASCII 单引号转义，含弯引号的合法路径仍会破坏 PowerShell 脚本

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:13,25,54、desktop-shell.md:175；Electrobun 2.0.6 src/extractor/main.zig:2744-2782,2806-2845；packages/neuro-book/desktop/scripts/smoke/windows.ts:25-42。
- **现象** 桌面重定向到带 U+2019（如 `O’Brien`）的目录时，按计划把路径内插进单引号字面量，照抄的函数只转义 ASCII `'`。Windows PowerShell 5.1 也把弯单引号当引号。普通 ASCII 撇号按上游写法可处理，UTF-8 stdout 只控制回传编码，不能修复脚本输入。
- **为什么是问题** 合法重定向路径上的探测、创建或删除可因解析失败而不可用。#505 是旧版 WebView2 的窄字符路径问题，不能作为本调用链中文路径失真的证据。另按上游实际用的 `DesktopDirectory` 取物理目录，计划第 13 行写的是 `Desktop`。
- **如何核实** 用 Windows 5.1 在隔离账户取重定向桌面，在分别含空格、ASCII 撇号、U+2019、方括号和中文的目录下对照实际读取与保存。Microsoft 的 [PowerShell 引号规则](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_quoting_rules?view=powershell-5.1#including-quote-characters-in-a-string) 明列弯引号要求。本轮据文档和源码推断，未跑 Windows。
- **建议改法** 固定脚本，路径经变量或结构化数据传入而非拼进脚本文本。使用系统的 PowerShell 绝对路径、不经外层 shell，UTF-16LE `-EncodedCommand` 传脚本、显式 UTF-8 回传；文件操作用字面量路径。桌面取空、非绝对、不可访问时诊断并停，不退回另一个桌面目录。

### 8. 桌面插件直接写主题、明暗和语言会得到 denied

- **严重程度** 阻断　**类别** 正确性
- **位置** 固定副本 plan.md:38,53,63、desktop-shell.md:184,276；docs/specs/settings/configuration.md:138-142；packages/neuro-book/src/plugins/settings/shared/layers.ts:124-141、shared/contracts.ts:58-72,146-179；src/plugins/settings/settings.test.ts:225-244；src/plugins/workbench/shared/contracts.ts:151-162,254-268。
- **现象** 向导归 `nbook.desktop`，按计划从自己的配置门面提交。主题和明暗归 `nbook.workbench`，语言归 `nbook.settings`，三项都会在声明者检查失败。直接改用现有切换命令也有一处限制：主题和明暗允许项目层，命令以默认的 `auto` 写；在带覆盖的工作台里运行会写项目文件。
- **为什么是问题** 输出 34 与场景 19 要求用户层落盘和当场变化。向导还会在工作台挂载并允许从命令面板重开。强制写用户层可以保护项目文件，但已有项目覆盖时，有效值按配置合同仍由项目层决定。
- **如何核实** 用真实配置服务从 `nbook.desktop` 入口提交三个设定，核对落盘与有效值。另以带主题和明暗覆盖的项目重开向导，确认项目文件不改、用户层写入成功且显式处理当前有效值不变的情形。现有授权用例已覆盖非声明者返回 `denied`。
- **建议改法** 复用声明者自己的命令或窄写入门面，明确该调用写用户层，保留通用配置授权。明确项目覆盖时向导怎么说明当前值，或约束外观编辑的可用场景，别为即时生效绕过项目优先级。

### 9. 探测与修改之间，系统或用户换过的同名文件没有保护

- **严重程度** 重要　**类别** 不变量
- **位置** 固定副本 plan.md:24-26,54,60、desktop-shell.md:173-175；Electrobun 2.0.6 src/extractor/main.zig:2822-2831,2859-2871,2895-2905。
- **现象** 同步队列只有一个写者也挡不住桌面外部变化。探测看到本安装链接、删除命令尚未开始时，用户编辑链接目标或 OneDrive 恢复同名文件。如果删除命令只按上次读到的路径删，会删到新文件。探测为空后，另一程序先创建同名链接，随后的 `CreateShortcut(...).Save()` 同样可能覆盖它。
- **为什么是问题** 输出 33 保护其它目标与非快捷方式文件。两次 PowerShell 之间的任意间隔都足以换文件。上游的条件删除在一个命令内重读 `TargetPath`、展开环境变量并按 Windows 路径比较，不能只照搬它的最后一步。
- **如何核实** 在隔离 Windows 桌面让探测结束、修改先停在可观测关卡。分别在这期间替换目标和放入同名文件；释放修改，核对替换后的文件内容和目标未变。另放入同名目录、重解析点与不可读文件，核对本次不动。
- **建议改法** 修改端收预期现状，执行前用字面量路径复查目录、链接类型和目标，探测异常不算缺失。创建用同目录临时链接及不覆盖的提交。删除尽量让复查和动作在一个命令内完成；如需承诺抵挡任意并发替换，使用按文件身份操作的系统接口，或在合同中明示剩余窗口。每次至多一次探测、一次修改。

### 10. places 的 browser 调用方限制挡不住普通浏览器

- **严重程度** 重要　**类别** 不变量
- **位置** 固定副本 plan.md:20,28-31,51、desktop-shell.md:183,248；docs/specs/runtime/application.md:29-34、projects.md:176；docs/specs/settings/configuration.md:165；packages/neuro-book/src/web/host/window.ts:240-244、src/web/boot.ts:76-100。
- **现象** 普通浏览器与 WebView2 产品窗口都以 `kind: "browser", role: "client"` 接入。同一服务端会为两者登记新合同。按提案的调用方与输入校验，普通浏览器里的调用者也能读绝对状态根、请求服务端启动文件管理器。`inDesktop` 只决定客户端显示，固定枚举只限制可打开哪处。
- **为什么是问题** 现行应用、配置和项目合同都把状态根留在服务端；输出 34 只要求在桌面窗口展示。回环监听缩小接入范围，但不区分这两类窗口。失败详情也会随接口一起跨边界。
- **如何核实** 在真实服务端合同测试登记用桌面和普通浏览器身份的客户端；校验普通浏览器拿不到状态根，调用 `open` 不触发系统端口。传非法枚举不触发系统端口是另一条判据。当前结论基于握手与拟定 RPC 签名。
- **建议改法** 状态根由掌握本次运行根的壳按窗口给出。打开操作由可信桌面通道接收固定位置请求，或在服务端接入已认证的桌面窗口权限后才开放。若增加桥操作，同步约束输出 13 的许可面；错误用稳定原因码，原始系统错误留诊断。

### 11. 文件管理器启动器退出失败，复用的函数仍回成功

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:30-31,51、desktop-shell.md:183；packages/neuro-book/src/backend/open-folder.ts:15-24；node_modules/open/index.js:47-54,169-210,255-309。
- **现象** `openExistingFolder` 调用的 `open(path)` 默认只等启动器的 `spawn`，不核对退出码。子进程起来后打不开目录时，RPC 仍回 `ok: true`。`no-desktop` 则取决于服务端环境，复用从 SSH 启动的同版本 CLI 实例时，即使桌面窗口能启动系统程序也会被拒。
- **为什么是问题** 输出 34 要求打不开时有原因。切片 3 若只替换真正打开的函数，会放过这条生产分支；服务端环境与窗口所在会话也不总相同。
- **如何核实** 本轮用 Linux、scratch 下已有目录、LXQt 和空的可执行程序搜索目录运行真实 helper。返回 `{"ok":true}`；同一启动器等待退出得到 `Exited with code 3`。缺失目录回 `open-failed`，模拟 SSH 回 `no-desktop`。这些输出没有验证 Windows；在登录桌面实测系统打开失败及 CLI 服务端复用。
- **建议改法** 使用能对「系统是否接受这次打开」返回明确结果、带截止的本机端口，避免等待文件管理器窗口关闭。测试保留真实适配器，至少覆盖退出非零与启动失败。桌面版优先按窗口所在会话打开；错误详情留本地诊断，页面显示稳定原因。

### 12. 能用来新建作品的目录，向导会误报不是文件夹

- **严重程度** 重要　**类别** 正确性
- **位置** 固定副本 plan.md:30-31,51、desktop-shell.md:183；docs/specs/runtime/projects.md:119-120；packages/neuro-book/src/plugins/projects/backend/library.ts:19-22、src/plugins/projects/backend/browse.ts:55-74、src/backend/open-folder.ts:15-18。
- **现象** `library()` 只展开 `~`，会保留设置中的相对路径与目录别名。作品浏览、登记与新建把这些路径解析到真实目录。向导把同一设定交给 `openExistingFolder` 时，末级符号链接被 `lstat` 判成“不是文件夹”。上级目录不可搜索时，`EACCES` 被折算成“文件夹不在”。
- **为什么是问题** 向导会把可用目录说成无效，或在已有目录上提示“第一次新建作品时会建出这个文件夹”。显示相对路径还缺少解析基准，复用 CLI 服务端时基准是它的工作目录。
- **如何核实** 本轮用 Linux、实际 helper 和 scratch 目录：`library()` 规则保留 `./lib`，`browseDirectory` 返回别名指向的绝对目录，直接打开别名返回“不是文件夹”；已有路径的父目录设为不可搜索后返回“文件夹不在”。用模拟 SSH 阻止真正打开；Windows junction 待实测。
- **建议改法** 在作品目录的拥有者侧统一解析并给出可复制的绝对路径，打开仍由服务端按固定标识重取。明确是否接受用户配置的目录别名，按同一规则校验。区分不存在、权限拒绝和非目录，只对不存在提示新建作品时会创建。
