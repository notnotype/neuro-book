Analysis: correct as written. ToolStrip entries come from WorkbenchShell.toolEntries, which builds fresh objects on every recompute (map -> {id,label,...}), and projectRows builds fresh Row objects, so any real content change gives a different identity and next is returned; only pure resize steps (same objects, same order/indices) reuse the array. Template reads of other reactive state (selectedSet, focus, editing, rowHeight, placeholder, highlighted) happen in render, not in these computeds, so they are not cached. Vue 3.5.39 computed(previous): first run previous===undefined; after dependency changes previous is the last value; returning the same reference does not bump the version, so dependents do not re-render. The invariant "a row object never changes in place" is the only thing keeping this safe (types are readonly) and nothing tests it: ExplorerTree.dom.test.ts has no setProps case, WorkbenchToolStrip has no dom test (only e2e).
Failure scenario if someone later mutates/caches rows in place: explorer/tool strip would silently stop updating on content change.
Fix (optional, small): one ExplorerTree dom test: mount with rows, setProps rows with the same ids/indices but a changed label/expanded flag, assert the DOM shows the new value (and the same for a viewport change leaving it unchanged). Low risk, so skipping is acceptable.
