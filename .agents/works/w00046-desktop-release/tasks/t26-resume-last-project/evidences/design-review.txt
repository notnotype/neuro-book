### 1. `serverUrl + RESUME_PATH` 会拼出 `//api/...`，请求落到静态回退页，静默进书架（阻断）
类别：与现有合同不符 / 验收会假通过
位置：计划“桌面壳”与“命令行”两节；`src/desktop/windows.test.ts:71,275`、`src/cli/cli.test.ts:175`；`packages/nb-host/src/http/dispatch.ts` 的 `API_PATH_PATTERN`、`isApiPath`
现象：壳拿到的 `serverUrl` 与 `nbook start` 的 `instance.url` 都来自 `Bun.serve().url.href`，以斜杠结尾（测试里也写 `http://127.0.0.1:4217/`、`http://127.0.0.1:1/`）。计划写的是 `serverUrl + RESUME_PATH`、`instance.url + RESUME_PATH`，而 `RESUME_PATH = "/api/nbook.projects/resume"` 以斜杠开头，结果路径是 `//api/nbook.projects/resume`。
为什么是问题：我核实了两点。一，`new URL("http://127.0.0.1:4217/" + "/api/nbook.projects/resume").pathname` 是 `//api/nbook.projects/resume`；用 curl `--path-as-is` 打一个 Bun.serve，服务端 `request.url` 原样保留双斜杠（不会被规整）。二，分发器的 `^\/api\/([^/]+)(\/.*)?$` 匹配不上，`isApiPath` 也判不为 API 路径（不以 `/api/` 开头），于是交给 `staticFiles.serve`：无扩展名路径回退到 `index.html`，200。页面在地址 `//api/nbook.projects/resume` 下启动，`location.search` 为空、不绑定项目，直接显示书架，没有任何报错。也就是整个功能在真实入口上完全不生效，却没有失败信号。计划里的壳单测与 `cli.test.ts` 若也用同样的拼接来写期望值（很自然），会一起通过。
如何核实：`bun -e 'console.log(new URL("http://127.0.0.1:4217/"+"/api/x").pathname)'`；读 `dispatch.ts` 的 `createDispatcher`。
建议改法：用 `new URL(RESUME_PATH, serverUrl).href` 拼，两处共用同一个函数；测试断言写死完整字符串（`http://127.0.0.1:4217/api/nbook.projects/resume`），并加一条“尾斜杠的 url 不出现 `//`”的断言；合同测试用真实服务端 `fetch(new URL(RESUME_PATH, url))`，`redirect: "manual"` 看 302 与 Location。

### 3. 路由在任何失败时都会把一页 JSON 错误放进窗口，没有出路，托盘重开还会再来一次（重要）
类别：失败路径
位置：计划“路由”一节；`nb-host/src/http/dispatch.ts`（`errorResponse`、`plugin-unavailable`、准入 503）、`src/web/FailurePage.vue`
现象：壳与浏览器把这条路由当作整页导航的目标。路由处理器若抛错（`projectsKey.list` 抛、设置读取抛）、`nbook.projects` 服务端入口此刻不可用（503 `plugin-unavailable`，或 404 `not-found`）、或准入在排空中（503），响应是 `{"error":{...}}` 的 JSON，浏览器/WebView 直接显示这段文字。它不是 SPA，没有 `FailurePage` 的“重试”“不打开项目”，窗口里没有任何可点的东西。用户关窗再从托盘“打开”，没有窗口时仍走 resume，原样再来一次。对比：同一时刻打开 `/` 至少得到应用自己的页面与失败呈现（browser-host 的失败呈现）。
为什么是问题：“上次的作品打不开时停在出错页”这个已定决定依赖应用页面在，而 resume 路由本身的失败不在这个决定里。计划只写了“只读，不打开项目”和三种正常结果，没写 registry 损坏（`list` 返回 `registry-invalid`）、记录读不出（`corrupt`、`unsupported-version`、`error`）、设置读失败时怎么办。
建议改法：路由里整个 try/catch，任何内部失败都 302 到 `/` 并记诊断（`projects.resume-failed`，带原因），让应用页面去呈现 `registry-invalid` 之类；正常的三种结果之外不返回非 3xx 状态。Spec 里把这条写成“resume 路由总是 302”。入口不可用（404/503）的情形壳与命令行无法分辨，可以接受，但至少在 Spec 的失败与恢复里写明。合同测试加：记录损坏、登记表损坏各一例，断言仍是 302 到 `/`。

### 5. “此刻没有任何页面窗口时的第一个”在协调器里没有定义清楚，至少三种时序算不清（重要）
类别：时序与边界
位置：计划“`windows.ts` 的 `openWindow`”一条；`src/desktop/windows.ts` 的 `openWindow`、`serverReady`、`openFromTray`、`openWindowRequested`、`closeRequested`、`closed`
现象与依据（都读过实现）：
a) `run()` 无条件先 `openWindow()`（服务端未就绪，`kind: "startup"`）。启动期间第二次启动转交（`open-window`，经 `openWindowRequested`）会再开一个 startup 窗口。`serverReady` 把所有未关闭的 startup 窗口一并 `load`。计划写“在 `serverReady(url)` 时按同一规则算”，没说哪个窗口拿 resume：应是按 `#windows` 插入顺序的第一个未关闭的 startup 窗口，其余走根地址（符合“已有窗口时再开是书架”）。不定义会实现成“都 resume”（两个窗口同一部作品）或“都书架”。
b) “任何页面窗口”要不要算正在关闭的（`closing: true`，等 `closed` 事件）：用户关掉最后一个窗口（设置为托盘）到 `closed` 之间若转交或托盘“打开”到达，`openFromTray` 已按“不在关闭中”过滤；`openWindow()` 里同样要把 closing 的排除，否则这个窗口会走书架而用户期望的是 resume。反过来，在 `closed` 之前就开的新窗口不应该被“旧窗口里正显示的作品”影响。要写明判据是“不在关闭中的窗口数为 0”，并配测试：关闭中再开 → resume；startup 窗口被用户在就绪前关掉后再开 → resume。
c) `openWindow()` 同时服务于 `run()` 的启动页窗口、托盘、转交，三者的 `OpenTarget` 都是 `{kind:"page", url}`；规则要落在这一个函数里，不能在 `openFromTray`、`openWindowRequested` 各写一份。当前 `openWindow()` 没有参数，建议内部算，而不是让调用方传标记。
d) `pageWindowRequested`（页面请求的新窗口，如书架“在新窗口打开”）计划写“不变”，正确：它自带 URL。
壳里其它拼服务端根地址开窗的地方：在 `src/desktop`、`desktop/src/bun/index.ts` 里搜过，`openManaged` 只吃协调器给的 `target.url`，`#serverUrl`（shell.ts:154）只用于 `runningWork`，没有别处开窗。服务端意外退出后重启（`#serverExited`）复用 `#lastPorts`，URL 不变，协调器的 `#serverUrl` 不需要更新（这是现状，不是新问题）。macOS Dock “reopen”走 `shell.trayOpen()` 同一条，已覆盖。
建议改法：在计划与 Spec 里写成一条规则：“窗口开出时若没有不在关闭中的页面窗口、也没有排在前面的 startup 窗口，则加载 resume 地址”；`serverReady` 内按插入顺序只给第一个 startup 窗口 resume；单测覆盖 a、b 与托盘后台重开。

### 6. `opened` 与记录的写法没和 `projects.stats` 的做法对齐，四处空缺（重要）
类别：合同与失败路径
位置：计划“记最近打开”一条；`src/shared/storage.ts`（`update`、`reset`）、`src/plugins/projects/shared/stats-record.ts`、`src/plugins/projects/backend/plugin.ts`、`shared/contracts.ts` 的 `projectsRemoteContract`
1) 坏记录永久失效：`handle.update` 在记录是 `corrupt` 或 `unsupported-version` 时不改写并失败；计划写“失败只写诊断”，于是一旦记录坏掉（或将来升级换了 `version`），之后每次 `opened` 都失败，resume 永远落书架，没有自愈。`projects.stats` 的约定是“可重算缓存，坏记录由写入方条件 `reset`”（stats-record.ts 头注释）。这里同样应在 `update` 返回 `corrupt`/`unsupported-version` 时用带 `expect: revision` 的 `reset` 覆盖；resume 读到坏记录按没有记录处理并记诊断。
2) 不校验 id：`opened({id})` 没有写“id 不在登记表里怎么办”。服务端方法拿不到调用方的绑定信息（`RemoteMethodContext` 只有 `signal`、`ok`、`fail`），id 完全由调用方给；合同 `callers: ["browser","tui"]`，任何浏览器插件或 tui 都能写。建议在服务端先 `projects.resolve(id)`，未登记回合同错误 `unknown-project`（与 `update`、`unregister` 的错误码一致），并在 `input` 里用 `Type.String({minLength: 1})`。
3) `at` 字段没有用途：resume 只读 `id`，“后打开的覆盖先打开的”靠写入先后，不靠 `at`。计划的“不写推测的后续计划”与注释规则下，不需要 `at`；要保留则写明用来做什么（例如丢弃比现有记录更旧的写入）。
4) “最近打开”其实是“最近一次页面加载并绑定”：浏览器入口在窗口启动时调一次，刷新、`reloadDocument` 都会再调。场景：窗口 A 是作品甲，窗口 B 开作品乙后关掉，甲页面刷新一次，记录变回甲。这与“只恢复最近打开的一部”一致，无需改，但 Spec 要把术语写成“最近一次窗口绑定”，别让读者以为按使用时长。重连（`session` 重连、`rebind`）不会再触发浏览器入口激活，所以不会重复写；项目代次结束（`project-gone`）发生在绑定之后，记录仍是它，resume 时 `resolve` 成功、打开时再失败，属于已定的“停在出错页”。
另：调用要在浏览器入口 `activate` 里 fire-and-forget（不 await，不拖慢激活），失败只记 `warn`；写成 `void remote.opened(...).then(...)` 要有 catch，避免未处理的拒绝。
可选的更简单做法（未验证可行性）：不由浏览器报，而在服务端绑定处记（`manager.ts:366` 一带），但那里是宿主层，还要写插件的用户记录，且重连重绑会重复写；不推荐，只作为备选记下。

位置：`desktop/scripts/smoke-update.ts` 里的 `backups` 备份与 `cleanUp` 还原（只备份 `projects.json`、`settings.json`）；`smoke/app.ts:74-92` `seedState`；`src/plugins/storage/backend/plugin.ts:75`（用户记录在 `<状态根>/storage/user.sqlite`）
现象：计划已写到“升级后重启会经路由进上次的作品”，但没有展开两点。
1) 更新冒烟用缺省状态根，并往登记表里追加作品、不删前一个冒烟留下的条目（smoke-update 注释自己写了“同一个作业里安装版冒烟已经用过缺省状态根”）。前一个冒烟的 `launchUseClose` 打开过作品，所以 `user.sqlite` 里有 `projects.last-opened` 指向那部作品；更新冒烟的首次启动因此直接进作品页，而不是书架。更新提示在页面根上、不依赖书架，多半仍能出现，但这是未验证的假设，应实测一次，不能只靠“核对判据”。
2) 在开发机上用测试标识跑更新冒烟（缺省状态根是真实用户的）：冒烟结束后 `projects.json` 被还原，而 `user.sqlite` 里的记录被覆盖为冒烟作品的 id，开发者真实的“上次的作品”丢了，之后 resume 因 id 不在登记表而落书架。first-run 记录早已有同样的泄漏（先例），所以只算建议。
建议改法：冒烟脚本在首次启动前备份并结束时还原 `storage/user.sqlite`（应用关闭后复制即可）；或让冒烟在启动前把设置里 `startupOpen` 写成 `shelf`（`seedState` 写 `settings.json` 的现成位置），这样更新冒烟的页面与现在一致，也不依赖记录，同时 smoke-windows 里单独保留“上次的作品”那一次重启（第 2 条）。

### 11. 目标地址应复用现成的 `projectUrl`，并写明 resume 与 `/?project=` 的关系（建议）
类别：重复实现
位置：计划“路由”“不变量”；`src/plugins/projects/shared/project-url.ts`（`projectUrl(name)` 返回 `/?project=${encodeURIComponent(name)}`，浏览器里的“打开项目”、书架、开发模式样例作品都经它）
现象：计划另写一遍“302 到 `/?project=<短名>`，短名经 `encodeURIComponent`”。后端路由可以直接 import 同一个 `projectUrl`（它在 `shared`，两端共用，无 DOM 依赖），省掉第二份编码规则；不变量“302 目标只会是同源的 `/` 或 `/?project=`”也就由同一函数保证。另外 `projectsKey.resolve(reference)` 先按 id 再按短名匹配（`registry.ts` 的 `resolve`），记录里存的是 id，所以 `resolve(id)` 命中的 `record.name` 就是当前短名，“改过短名也对”无需额外处理，合同测试里的“改短名”用例要造的是“登记表里同一 id 的 name 变了”这一情形，需要有办法改登记表里的 name（登记表没有改名接口，测试只能直接写 `projects.json` 或重新登记同目录）；若造不出来，这条用例可以删。

### 未发现问题的方面
- 路由挂载与来源核对：`GET` 经 `dispatch.ts` 只核对 `Host`（回环名）与准入，不核对 `Origin`、也没有凭据；`http.routes` 的前缀 `/api/nbook.projects/`、转交后的路径 `/resume`、只许一个贡献 id 的规则与计划一致。桌面壳的导航规则 `["^*","views://*","${serverOrigin}/*"]` 放行同源跳转，同源的 302 不需要额外凭据；客户端身份存在页面自己 origin 的 localStorage，打开 resume 地址前没有要先带的东西。302 默认不被浏览器缓存。注意：这只是读代码，真实 WebView2/WKWebView 对重定向的行为没有跑过，靠第 2 条的冒烟覆盖。
- 多窗口、刷新、重连：重连不会重新激活浏览器入口，不会重复写记录（见第 6 条第 4 点）；项目代次结束不影响记录的一致性。
- 壳里没有别处拼服务端根地址开窗（见第 5 条）。
- 新状态根与升级用户：没有记录时一律书架，首次启动向导的条件与记录无关，和计划“不变量”一致。
- 现有 e2e 没有依赖“壳或 nbook 打开后是书架”的（见第 2 条）；受影响的只有 `windows.test.ts`（默认开窗与 `serverReady` 加载的期望）、`cli.test.ts` 的 `openedUrls` 断言、`smoke-update.ts`。
