### 1. 托管启动漏传 NBOOK_WEB_ROOT，服务端 ready 后仍不能打开产品页
- **严重程度**：阻断；**类别**：接口合同、正确性。
- **位置**：snapshot-r1/desktop-shell.md 输出 4、5、8；specs-r1.diff 的 runtime.server-host“托管宿主”（diff 439—449 行）。
- **现象**：固定稿规定壳以 --stop-stdin 运行托管入口，只给 NBOOK_STATE_ROOT；新增托管合同也没有要求设置 NBOOK_WEB_ROOT。现有服务端不会从 main.js 的位置推断 web/，缺省只提供 API。
- **为什么是问题**：hello 的 ready 与 url 只证明运行实例已就绪，不证明存在产品页面。照新增合同启动可以成功认领并返回 ready，但加载 url 得到 404，桌面版从第一窗起就不可用。该缺口不是此前“npm 包缺 main.js”的重复：即使 t07 补齐入口与 chunks，仍缺运行参数。
- **如何核实**：已读指定 worktree 的 src/server/main.ts:9—12、config.ts:61—79：webRoot 缺省 null；主工作区 runtime/server-host“页面资源”明确未设置时 /api/ 之外一律 404。snapshot-r1 的托管段确实只要求状态根，不能用作者同时修订的原文件替代本副本。此为代码与合同对照，未运行 Windows。
- **建议改法**：托管合同明确由宿主传入包内 web/ 的绝对路径，desktop-shell 启动规则链接该前置条件；验收除了 hello ready，还要核对真实根页面及其静态资源成功、工作台就绪。保留服务端不猜默认目录的既有边界。

### 2. 只汇总 activity 与后台任务清单，空闲会话的后台命令会无提示中断
- **严重程度**：重要；**类别**：遗漏、不变量。
- **位置**：desktop-shell 输出 16、场景 7；browser-host 输出 9、10；conversation 输出 40；background-tasks 输出 17；plan.md“有任务在跑”。
- **现象**：新增提供者只有“运行中或等用户的前台会话”与 nbook.tasks。Agent 启动 async shell 后本轮结束、会话空闲，命令仍运行，却不在两份数据中；background:true 的会话也不在 activity 中。最后一窗可以直接 allow，停止服务端会取消这些工作。
- **为什么是问题**：这违反开发者已确认的“有任务在跑，先提示、用户决定”，不是要求新建任务系统。agent.jobs 已明确这些任务不随父会话闲置/关闭结束，而停止应用会中断；workbench.background-tasks 的非目标又明确排除 Agent 后台命令与子代理。零项不能代表服务端无工作。
- **如何核实**：主工作区 agent.sessions 输出 15、12：activity 只列前台活跃会话；agent.jobs 输出 6—9、场景 1、4：后台命令独立存活，应用停止取消；background-tasks“非目标”明确排除 jobs。指定 worktree agent/web/activity.ts:23—48 仅调用 activity，没有 jobs 汇总。静态合同反例，未调用真实模型。
- **建议改法**：定义覆盖服务端所有会被停止的工作清单，纳入 jobs 与后台会话；无提供者、插件未加载/失败、数据过期不能等同无工作。可继续让页面呈现，但数据来源不应受视图装载影响；补“会话已空闲但 async shell 仍运行”“最后一窗是书架或提供方未加载”验收。

### 3. 编辑器在整窗关闭尚可被否决时丢稿，后续取消无法保持窗口正文
- **严重程度**：重要；**类别**：交互合同、不变量。
- **位置**：specs-r1.diff 的 editor 输出 66 第 3 项、browser-host 输出 10 第 2—4 项；desktop-shell 输出 15、16。
- **现象**：编辑器选“不保存”立即“同意，修改丢掉”；宿主随后仍会调用其余参与方、询问是否中断工作，甚至把 window 重新询问为 quit。后面的任何一步 deny，或原生“取消关闭”结束代次，都保留窗口，却已丢掉编辑器正文。
- **为什么是问题**：参与方的 allow 只是预许可，不是最终关窗提交。最简单反例：关闭自动保存的 dirty 文档，选“不保存”，下一步任务提示选“取消”。按字面窗口不关但内容已被丢弃，违背“取消后一切照旧”。同一事务没有失败回滚或最终提交通知；signal 只能终止询问，不能撤销已丢弃的输入。
- **如何核实**：新增 windowCloseKey 接口只有 request(reason, signal) → allow/deny，没有 commit；browser-host 明定按顺序调用并在参与方同意后才汇总工作；editor 输出 66 明定“不保存”丢修改。用两个参与方“编辑器 allow、第二方 deny”即可形成合同级反例，无须 Windows、无须臆造框架时序。
- **建议改法**：“不保存”只记录本代次的放弃意向，不在询问阶段清除正文/标签；仅最终 native close 提交时放弃，取消或代次作废必须保留。明确异步询问期间若继续输入，旧修订的许可不可覆盖新输入：冻结编辑或提交前再次结算、重验版本。增加“不保存后任务取消/第二方否决/原生取消”与询问期间新输入场景。

### 4. 宿主页分支提前 allow，最后一窗在终态页会跳过停止任务确认
- **严重程度**：重要；**类别**：状态转换、遗漏。
- **位置**：browser-host 输出 10 第 1、3 项；desktop-shell 输出 16、17；conversation 输出 40、background-tasks 输出 17。
- **现象**：宿主页没有抢救正文就直接 allow；有正文也只确认丢稿。quit 的工作汇总只放在“参与方都同意”之后，没有要求宿主页分支执行。项目被关闭但服务端仍活着、后台工作仍运行时，最后一窗处在“项目已关闭”宿主页，关它直接停服。
- **为什么是问题**：宿主页不等于服务端没有工作；未保存正文清单与在跑工作清单是两件事。现有宿主进入 server-restarted/project-gone/incompatible 时会销毁插件，不能再假设原 reportWork 提供者仍存在。即使第 2 条补齐 jobs 汇总，这个早返回仍绕过它；服务端重启后新 boot 上新起的工作也不能沿用旧窗口缓存判断。
- **如何核实**：指定 worktree src/web/host/window.ts:212—229 在收集 rescue 后改变页面状态并 host.destroy()；shared/host.ts:121—138 明确 rescue 同步、不能远程查询；browser-host 既有重连合同规定项目代次结束仅结束项目，不等于服务端停止。固定 diff 输出 10 的两个分支独立，未规定终态仍要取在跑工作。静态状态反例，未运行 Windows。
- **建议改法**：quit 的最终停服确认与工作台/插件是否存活解耦；任何页面状态都要取得当前自有服务端的工作快照，取不到则明确“无法确认”并让用户决定。抢救正文确认和停止任务确认都完成才 allow；补最后一窗为项目终态页、有无抢救正文两组场景。

### 5. 固定 90 秒与“不短于服务端预算”不能同时成立
- **严重程度**：重要；**类别**：停止合同、边界。
- **位置**：desktop-shell 输出 19；pending-confirmations 第 2 行；server-host“输入与前置条件”“停止序列”。
- **现象**：Spec 把截止定死为 90 秒，同时承诺不短于 20 秒排空加项目停止预算。服务端接受 NBOOK_PROJECT_STOP_MS=90000，此时仅这两阶段就是 110 秒，尚未计插件与 OMP 清理；该环境变量没有被桌面合同禁用或覆盖。
- **为什么是问题**：合法配置会在服务端自己的截止之前被壳杀树，把正常允许的清理窗口变成强杀。待确认理由把项目停止固定当 20 秒，却没有说明那只是缺省值。不是按项目数乘 20 秒：已读实现，子进程停止用 Promise.all 并行，这个维度没有发现问题。
- **如何核实**：指定 worktree config.ts:50—53、73—86：stopMs 可取 1..2147483647 毫秒；nb-runtime/src/application/children.ts:217—226 并行停止；manager.ts:559—599 等真实退出。实际运行 bun -e 导入 readServerConfig，缺省输出 projectStopMs=20000；同一解析器接受 90000。静态预算计算 20000+90000=110000>90000，未启动服务或等待超时。
- **建议改法**：选一种可判定规则：壳截止随实际配置与完整停止预算计算并留清理余量；或明确桌面托管入口限制/覆盖项目时限，并声明 90 秒是硬上限而非不短于全部预算。补自定义项目时限、启动中的项目和插件清理占用预算的验收。

### 6. 下次启动应用更新会被“未已停止一律否决退出”挡住
- **严重程度**：重要；**类别**：跨能力合同、状态转换。
- **位置**：desktop-shell 输出 19、“状态与转换”；desktop-update 输出 8。
- **现象**：更新在启动时、取桌面锁之前调用，壳尚不可能经过“最后一窗关闭 → 停止服务端 → 已停止”。但 shell 输出 19 要求只要没到已停止，框架每一次退出都拦下；Electrobun applyUpdate 正是在交接助手之前同步请求退出许可。
- **为什么是问题**：照两份合同实现，更新流程在 before-quit 被否决，助手根本不会启动；普通 quit 也不会补上更新。三态表没有“启动中发现待应用更新，安全交接”的转换或授权例外。此前已处理“不要关窗时更新”的决定没有问题，问题是 Spec 新加的无条件屏障没有给选定的启动更新留通道。
- **如何核实**：所给 Electrobun 2.0.6 Updater.ts:2396—2402：requestQuitApproval() 为 null 即 return，2405 行以后才启动助手；Utils.ts:133—161 同步读取 allow:false；events.mdx 的 Shutdown 明确不等待 Promise。固定 shell 表仅在服务端退出或 90 秒到后进入已停止。源码时序核实，未运行 Windows 更新。
- **建议改法**：明定无服务端、未取桌面锁时的更新交接可获得一次退出许可；安全交接和普通运行态退出分开，助手启动失败则撤回许可并恢复旧版正常启动。不要靠异步 before-quit 或把 starting 偷当 stopped。加入已下载更新的真实重启场景，断言助手启动、新版接管，而不只是断言旧壳退出。

### 7. 安装级排他只是瞬时检查，没有覆盖更新交接期间的新启动
- **严重程度**：重要；**类别**：并发、不变量。
- **位置**：desktop-update 术语“安装级排他”、输出 8、“时序与寿命”；desktop-shell 输出 1、3、场景 3。
- **现象**：安装级排他被定义成“没有别的进程在运行”，没有取得与保持许可的合同。A 启动时检查成立，交接后退出；B 在 A 检查之后启动、在助手换文件之前取得桌面锁并拉起旧服务端。安装级互斥已经失效，即使两个启动使用同一状态根也能发生。
- **为什么是问题**：桌面锁在换上之后才取，保护不了前面的区间；原生助手只等发起者 parent_pid，不阻止新 launcher，也不等待 B 的服务端。Windows 的文件占用重试或安装器互斥不是“运行中的应用不可被更新”的证明。两次同时启动彼此都判占用虽然安全推迟，但没有解决这个检查后启动的反例。此为 r2 处理增加“安装级排他”后仍未落实其寿命，不重复要求新增同一机制。
- **如何核实**：Electrobun Updater.ts:2364—2440 的计划只有单个 parent_pid；extractor/main.zig:7456—7470 等它退出后才取 WindowsUninstallLock 并开始 swapping。新壳的启动未加入该锁。固定稿只有一次确认和“不成立则旧版启动”，没有交接保持与等待者规则。源码时序分析，未做 Windows 双启动。
- **建议改法**：把安装级使用许可与更新排他作为跨进程合同：所有启动与服务端在使用载荷期间持有使用权；换上取得排他并跨旧进程退出、助手替换、新版接管保持，新启动只能等待或明确失败，不能继续运行旧版。补 A 检查后插入 B、不同状态根并发、更新失败后解除排他三个真实场景。

### 8. 替换待安装更新没有保留与单调规则，SDK 会先删掉已校验的旧包
- **严重程度**：重要；**类别**：数据寿命、失败恢复。
- **位置**：desktop-update 输出 2、5—8，“副作用与数据”。
- **现象**：输出 7 承诺已下载更新保留到换上、仅用更高版本替换；其余判定只比较远端和本地，没有定义待安装版本参与比较、替换提交点或失败保留。Electrobun 现成下载路径在准备 C 之前就删除已下载的 B；C 下载失败时 B 也没了。
- **为什么是问题**：例如本地 A、B 已下载但安装被占用而推迟，随后发现 C。直接复用 SDK 下载 C 会违反“B 保留到换上”；断网/磁盘不足后离线重启不能再应用 B。另外如果已下载 C，更新源后来回到 B（A<B<C），只用输出 2 的 B>A 门禁仍会把 C 换成 B，与输出 7 的“更高”不一致。两者都不是要求自动降级本地版本。
- **如何核实**：所给 prepare_update.zig:427—460 的 pruneSupersededStage 删除旧 stage、recipe、prepared 指针；576—612 在 patchChain/fullDownload 之前调用它。Updater.ts:2282—2315 无产品版本排序。待安装指针是跨进程共享的，downloadInFlight 仅进程内。固定稿无“C 校验成功后才提交替换”的规则或相应失败验收。源码核实，未运行真实更新。
- **建议改法**：写明候选需高于 max(当前版本, 已下载版本)，更高候选下载校验成功才原子替换待安装记录；失败保留 B。若上游 SDK 无法兑现，需要在实现计划明确扩展/绕开该破坏性替换，或将较弱保留语义交开发者改判，不能照字面宣称支持。验 B 已下载、C 半途失败、离线启动仍能装 B；验更新源回退不替换 C。

### 9. 更新通知要求两个动作，但依赖的通知合同只允许一个且点击即销毁
- **严重程度**：重要；**类别**：接口合同、隐含耦合。
- **位置**：desktop-update 输出 3、4、6、10；specs-r1.diff（未修改 workbench.notifications）。
- **现象**：更新提示指定同一通知带“下载 / 以后”两按钮，便携提示带“打开下载页 / 以后”；现有 NotificationInput 只有一个 action。点击动作立即把通知从弹出队列与中心一起移除，原句柄再 update 无效果，不能把它原地改成下载进度或完成状态。
- **为什么是问题**：实现者无法只使用链接的既有接口兑现这组输出，要么暗中扩展通知能力，要么绕过通知服务另做桌面专用视图，形成第二套提示语义。“每条有关闭按钮”不等于写了“以后”动作，也没有回传 dismiss、跨窗口迁移或刷新重投的合同。
- **如何核实**：主工作区 workbench.notifications“输入与前置条件”只声明 action?:{label,run}；输出 4、5、13 与“时序与寿命”明确点击动作即移除、已移除句柄更新无效。本次统一 diff 没有 notifications 的改动。合同对照，未运行 UI。
- **建议改法**：在同一真相源补 planned 多动作/动作后保持规则与完成条件，或沿用单动作，把“以后”明确映射到关闭动作，并让下载新建独立进度通知、丢失视口后从壳状态恢复；两条路线选一条写清。补关闭、刷新、焦点迁移时不会重复下载或丢失最终状态的组合验收。

### 10. 更新 Smoke 强制依赖上一桌面版本，首个桌面发行无可用基线
- **严重程度**：重要；**类别**：验收、发布。
- **位置**：desktop-update“验收与 Smoke”场景 1、2 与 Smoke 末行；desktop-shell Smoke。
- **现象**：Smoke 要求 Windows 作业用“上一版本的安装包与本次构建出的更新文件”跑升级与拒绝降级。本次正是新应用第一次桌面发行；已有 npm 版本没有 setup，也没有这套 identifier/channel/update-v2 清单，旧应用 0.10.x 更不是可兼容基线。
- **为什么是问题**：照字面落成发布门禁，首发无法构造场景 1 的 A 安装包；若实现者首发直接跳过，就没有任何一次真实 updater 换文件验证，关键路径留到用户第一次升级才执行。这不符合“所有验证与冒烟都在发布前跑完”的已定交付边界。
- **如何核实**：固定稿 Smoke 的输入依赖；提案第三节与 4.8 说明旧 Release 属旧应用、此次新建桌面链；t01 Windows runner 证据仅原型空书架启动/停止，不含真实更新。此为验收可执行性对照，未下载旧安装包或触发 CI。
- **建议改法**：明确首次发行的可重现 A/B 基线生成法：用同一真实桌面发行链构建仅版本有序的两个测试载荷，以本地更新源走安装、下载、退出、新版接管、拒绝降级；后续再增加上一正式版到本版。不得用 mock apply 或把首发记为更新已验收。补环境覆盖与状态根保持断言，旧用户的升级仍用真实历史包覆盖。

### 11. 更新接管没有保持本次启动的状态根，允许的相对路径会漂移
- **严重程度**：重要；**类别**：跨进程上下文、兼容。
- **位置**：desktop-shell“输入与前置条件”的 NBOOK_STATE_ROOT；desktop-update 输出 8、场景 1。
- **现象**：壳接受相对 NBOOK_STATE_ROOT、按启动工作目录解析；更新在取锁前让新版本“接着完成”，却没有传递本次已解析的绝对状态根。Electrobun 的更新助手重启 launcher 时把工作目录固定到 launcher 所在目录，且 Windows 走独立计划任务，计划里没有环境上下文。
- **为什么是问题**：从 D:\Work 启动、NBOOK_STATE_ROOT=.\state，更新前应使用 D:\Work\state；即使变量原样继承，新版也会按安装目录 app\bin 解析为另一份 state，显示空书架并创建新数据。进程级环境未进入计划任务时还会退回平台缺省。更新“不针对状态根”不等于可以丢弃用户选的启动上下文。
- **如何核实**：指定 config.ts:66—70 的 resolve(cwd,stateRootInput)；所给 extractor/main.zig:7299—7325 在 launchAppliedUpdate 明确 .cwd=dirname(launcher_path)、argv 仅 launcher；Updater.ts:2381—2393 的 NativeUpdatePlan 无 stateRoot/env/cwd；WindowsUpdateTask.ts:48—60 只登记 helper 与计划路径。相对路径漂移由源码可推出；Windows 环境丢失未实测，不冒称已复现。
- **建议改法**：把“本次启动由新版继续”的上下文合同写全：保留规范化的绝对状态根及必要启动意图，成功、失败回退都使用同一值；一次性交接完成后清理，不永久改变系统环境。更新验收加入相对和绝对 NBOOK_STATE_ROOT，断言没有写入默认根或 app\bin 下的新根。

### 12. abort 只废弃答案，没有规定终止串行参与链和宿主自己的对话框
- **严重程度**：重要；**类别**：取消语义、资源寿命。
- **位置**：browser-host 输出 9 的 signal、输出 10 的逐个调用与异常询问；editor 输出 66 的 abort。
- **现象**：壳取消/强制关闭时，Spec 只要求参与方收起自己的对话框、“结果不再被采用”。没有要求宿主停止遍历、跳过剩余参与方，或撤下宿主自己弹出的“检查出错”“中断工作”“抢救正文丢失”对话框。abort 导致参与方 Promise reject 时，还会命中“抛错或失败”规则，再弹一次错误确认。
- **为什么是问题**：第一个参与方正在保存，用户在原生框取消关闭；保存稍后完成后，按现有顺序仍可调用第二方，发起新保存或弹出任务确认。窗口已取消关闭，却继续产生这次关闭的副作用。Editor 的“不再发起新的保存”只约束它自己的那次调用，不能约束宿主后来启动的其它参与方或已结束代次的宿主 UI。
- **如何核实**：固定 diff 的 request 接口和输出 10：顺序循环的唯一停止条件是 deny，abort 没有单列转换；错误处理没有排除主动取消；signal 只传给 participant、不传给宿主对话框。这是可由“待决 P1 → abort → P1 完成/reject”推出的合同缺口，未以伪造运行时实验冒充实现复现。
- **建议改法**：明确代次结束后立即停止调度、关闭本代次所有宿主与参与方 UI、不收集工作、不发送结果；已发出保存可完成，但不得引发后续步骤。主动 abort 不作为检查失败；每个 await 后检查代次/取消态，新调用不能接收已 abort 的请求。验取消期间 P1 resolve/reject 两种顺序，并确认 P2 没有开始。

### 13. quit 许可没有绑定窗口集合，询问中开窗会产生两次停服确认
- **严重程度**：重要；**类别**：并发、关闭事务。
- **位置**：desktop-shell 输出 9、14—16、场景 5；browser-host 输出 10。
- **现象**：A 是唯一窗口，开始 quit 询问；询问未完成时同版本开窗转交成功，B 出现。A 同意后关掉，但此时服务端不能停止；随后 B 作为最后一窗又以 quit 询问。输出 16 只处理 window → quit，不处理 quit → window，也没有规定任务确认期间拒绝/排队新窗口。
- **为什么是问题**：A 上的“关闭后服务停止”事实上不会发生，B 再问一次；窗口级代次只能淘汰同一窗口的旧回答，不能让全局停止许可保持有效。“串行提交关闭”只序列化 close，不自动序列化 open，也不能证明“最后一窗恰好一次”。这正是 r2 第 5 条要求开窗与最后提交同一协调，而固定 Spec 少写的一半。
- **如何核实**：输出 9 只在“停止中”禁开新窗；询问阶段仍是运行中。按 A quit 待决 → open B → allow A → close B 的合法顺序，每步都符合字面但会两次 quit。属于合同反例，未声称已在 Windows 上复现。
- **建议改法**：定义应用级最后关闭事务及窗口集合变化的失效规则；quit 待决时新开窗排队/取消退出意图，或者将许可降回 window 并撤下旧的停服确认。最终许可、重验窗口集合、实际末窗关闭与进入 stopping 必须是一个不可插入开窗的提交段；取消解除屏障。加入询问中转交开窗、开窗取消退出和新窗随后又关闭的验收。

### 14. starting 期间接受开窗转交，但成功应答要求已经打开产品窗口
- **严重程度**：重要；**类别**：协议、启动并发。
- **位置**：desktop-shell 术语“产品窗口”、输出 2、3、5、9、场景 3。
- **现象**：同版 hello=starting 时第二个壳必须发送 open-window；ok:true 定义为“已开出一个窗口并置前”，输出 9 进一步要求新产品窗口加载服务端首页。然而此时服务端可能还未就绪、没有 url，甚至正在等待旧服务端退出或显示启动失败页；只显示启动页又明确不算产品窗口。
- **为什么是问题**：接收方只能排队等 ready 才回复，或先开启动页就回复，或拒绝，三条都没有明确合同：前者与 3 秒无应答分支冲突（正常启动允许等 60 秒），后两者分别违背产品窗口语义和协议只有 stopping/unknown-request 的失败集合。场景 3 承诺同时双启动最后两个窗口，不能依赖服务端恰在 3 秒内就绪。
- **如何核实**：固定稿条目组合；server-host hello=starting 时 url=null，就绪前不能加载产品地址。t01 既有冷启动证据是复制目录后 +3659ms 服务端监听、+4982ms 页面就绪，不能以“starting 很短”排除，未将该旧证据冒充本轮实测。
- **建议改法**：明确 starting 接受的是“开窗意图”，成功应答的保证是已创建可见启动窗口/已可靠登记一次意图，ready 后转换为产品窗口；或定义 pending 与等待截止、失败返回。写清启动失败/用户退出时这些意图如何收口。加入服务端超过 3 秒才 ready、永远启动失败时的双启动验收。

### 15. 同源新窗口到底打开首页还是原目标，两条输出互斥
- **严重程度**：重要；**类别**：接口合同、兼容。
- **位置**：desktop-shell 输出 9、12、13、场景 11。
- **现象**：输出 9 把“开窗转交”和“页面请求的新窗口”一起规定为加载首页、不带项目参数；输出 12 又要求同来源新窗口加载请求地址。页面打开 /?project=book&open=project://chapter.md 时，按 9 丢掉项目与文件，按 12 则保留，两种实现不能同时通过。
- **为什么是问题**：产品用 URL 区分窗口项目绑定，整页加载后不能在页内换绑定；被丢掉参数不是地址栏的小差异，而是本应打开作品却打开书架。输出 13 的“页面不能经壳开别的窗口”若连受控的 window.open 也包括在内，还与 12 冲突；应区分没有原生特权接口和正常 Web 新窗口请求。
- **如何核实**：固定 desktop-shell 逐条对照；runtime.browser-host“项目绑定”与输出 3 明确 project 参数在握手时决定一生绑定。现有场景 11 只断言开出了产品窗口，未断言目标地址、项目或文件，捕捉不到照 9 实现的参数丢失。静态合同反例，未运行 GUI。
- **建议改法**：只有无参数的开窗转交加载首页；同源页面新窗口保留已校验 URL 的路径、query、fragment，接收壳只允许当前精确来源。输出 13 改为不暴露任意原生开窗 API、受控 Web 请求按 12 处理；场景 11 核对真实项目与文件打开结果。

### 16. 无应答分支强制显示对端 pid，但 hello 正是唯一的 pid 来源
- **严重程度**：重要；**类别**：失败通道、可实现性。
- **位置**：desktop-shell 输出 3 第 4 项、输出 4 最后一行、“失败与恢复”。
- **现象**：两个协议都只在 hello 应答里带 pid，却规定 3 秒没有应答时启动页给出那个进程的 pid。服务端已有查询结果 unresponsive 只有 detail，没有 pid；未回应时解析不到应答字段，也没有另一个公共发现接口。
- **为什么是问题**：最需要定位挂起实例的分支无法满足承诺。实现者不能从“同状态根命名管道”凭空得到应用 pid，也不能把启动方自己的 pid、旧应答缓存或全机扫描当成当前拥有者。若要依靠 Windows 管道进程查询，必须把它作为新平台前置条件与失败通道，而不是说与 nbook 判定相同就已经提供了。
- **如何核实**：指定 nb-host/src/server/claim.ts:98—105 的 InstanceQuery 联合类型和 269—310 的 hello：超时只返回 state=unresponsive 与地址/时长，pid 只出现在 parseInfo 成功之后。desktop hello 也没有独立所有者元数据。静态接口核对，未跑挂起进程实验。
- **建议改法**：最低风险是显示状态根/管道地址，“能确定时附 pid”，不确定时直说无法取得；或补可验证的独立 pid 取得合同、权限失败分支及跨版本规则，禁止误杀建议依赖未经核实 pid。验对端从监听成功起一直不发 hello 与连接后即断开两种路径。

### 17. 启动窗口关闭与自有服务端异步拉起之间没有取消和回收合同
- **严重程度**：重要；**类别**：资源寿命、状态转换。
- **位置**：desktop-shell 输出 4、5、8、17—19，“状态与转换”。
- **现象**：启动页窗口可以直接关，且最后一窗关闭就退出；但状态表没有“启动中关闭最后一窗”的转换，也没要求取消正在执行的查询/重试/拉起意图。若关窗时仍在等旧实例停止，或已决定拉起但 spawn 尚未返回，当前还没有自有服务端可写 stop；晚到的成功回调如何处理没有定义。
- **为什么是问题**：照字面可以在用户退出后继续拉起服务端、重试开窗，或提前放桌面锁让下一壳进入，再把晚到进程误当正常启动。仅靠正常路径的“服务端退出才放锁”不涵盖尚未得到进程句柄的资源；末窗已没有 UI，不能再靠用户点关闭收口。
- **如何核实**：固定输出 4 明确可等待 60 秒、竞争失败重问；输出 17 直接关启动页；状态表只有“运行中”末窗转换；输出 19 的三态又没有启动中。不存在可引用的桌面实现来补此合同，因此这是缺失的异步寿命规则，不声称已经复现孤儿。
- **建议改法**：任意阶段最后窗口关闭都终结本次启动意图；禁止后续 spawn/开窗，已发起但晚到的进程必须收回并等真实退出，然后才能放锁。明确等待外部实例时退出不停止它，启动失败后的重试受同一代次约束。补分别卡在 hello 等待、spawn 返回前、ready 返回前关闭启动页的验收。

### 18. 90 秒到就进入已停止并放锁，破坏“服务端真实退出后才放锁”
- **严重程度**：重要；**类别**：停止时序、不变量。
- **位置**：desktop-shell 输出 19；“状态与转换”停止中一行及“时序与寿命”第 4 项。
- **现象**：状态表把“服务端退出”和“90 秒到”并列为进入已停止、放桌面锁、退出的条件；时序条目却要求服务端退出之后才放锁。达到截止只允许开始强杀，不等于树中的服务端和项目已经消失。强杀失败或尚未完成时的下一状态没有写。
- **为什么是问题**：新启动者拿到桌面锁后仍能遇到旧服务端 stopping/无应答，甚至旧项目仍持有文件；此时 Spec 保证的“不会撞上停止中的旧认领”不成立。强杀进程树是异步的 OS 操作，不能把发出终止请求当作观察到终止。正常 stdin 路径已明确“等它退出”，唯独超时路径缺了这个屏障。
- **如何核实**：固定稿两处条件直接冲突；指定项目实现 manager.ts:588—599 是 kill 后仍 await proc.exited，server-host 停止序列第 3 步也要求项目真实退出。所给 Electrobun 更新助手 main.zig:7034 起同样等待进程句柄，而非仅凭杀进程命令返回。此为合同及时序核对，未在 Windows 强杀。
- **建议改法**：90 秒触发进入强制收口状态，不立即进入已停止；等服务端及其自有项目树真实结束，再记录结果、放桌面锁与退出。定义终止请求失败的诊断和退出边界，不声称保证已释放。验强杀返回早于实际退出、重复退出、其间新启动仍等待且不会开出旧产品页。

### 19. 服务端重启若端口顺延，保留页面不会重连到新地址
- **严重程度**：重要；**类别**：重连合同、恢复。
- **位置**：desktop-shell 输出 5、6、11、21；browser-host“断线与重连”。
- **现象**：“重新启动服务”承诺旧页面重连后显示“服务端已重启”，但重新启动仍按缺省端口/成对顺延，可能得到不同 HTTP 来源。页面的重连只在原 HTTP 地址取引导，不从桌面认领重读地址；页面与壳的两件接口也没有服务地址更新事件。
- **为什么是问题**：旧 4217 在服务崩溃后被别的进程占用，新服务端起在 4317，旧页面永远请求 4217，不能到达新 boot；“刷新”也仍是旧地址。直接原生导航到新来源则会销毁为抢救正文保留的旧页面，不能拿它静默补洞。若旧来源恰好被另一状态根的 NeuroBook 占用，更不能让用户刷新到另一本书架。
- **如何核实**：server-host 启动参数允许端口成对顺延；browser-host 重连只重取既有连接对象的引导地址，以取得新的 RPC 端口，并不发现新的 HTTP 地址；shell 输出 13 与 browser-host 输出 11 无地址变更通道。固定稿只记录初次端口变更对客户端身份的限制，没有定义此重启路径。静态反例，未占端口或启动服务。
- **建议改法**：明确重启后认领 url 与原来源不同的处理：先在原页面进入可复制抢救态，再由用户确认切到经壳验证的新来源；或为自有重启固定原端口、占用时报启动失败并保留原页面。两种都应避免自动刷新命中别的服务端，补旧端口被占用后的真实恢复验收。

### 20. 编辑器场景 45 要求同一窗口同时开启与关闭自动保存，夹具不可构造
- **严重程度**：建议；**类别**：验收、文档。
- **位置**：specs-r1.diff 的 workbench.editor 场景 45；既有输出 52、63。
- **现象**：Given 要求同一桌面窗口里“一份自动保存的文档”与“一份自动保存关着的 dirty 文档”。产品只有 nbook.editor/autoSave 这个窗口所读的设置，没有每文档的 off 开关；并且输出 66 本次询问只取一个开关值。
- **为什么是问题**：照字面写 Windows 端到端验收只能捏造产品不存在的每文档配置，或改测别的场景而仍引用 45。可测试的近似其实是“自动保存开着，但第二份有冲突等不自动保存的阻碍”，不等于自动保存关着。
- **如何核实**：指定 editor/shared/settings.ts:92—108 只有一个 autoSave Setting；editor/web/plugin.ts:148 把同一 settings.get(autoSaveSetting) 交给本窗口 area。既有输出 63 的阻碍列表不提供独立开关。静态夹具可构造性核对，未运行 e2e。
- **建议改法**：拆成两个明确窗口/两次设置场景，或在同一窗口用“可自动保存的 A + 有阻碍的 B”，并另验全窗口 autoSave=off；分别锁定取消、保存失败与不保存的结果。不要为测试新增产品没有承诺的每文档开关。

## 参照与上游选择核对

- VS Code 把可否决的 onBeforeShutdown 与不再可否决的 onWillShutdown/onBeforeCloseWindow 分开；本稿只有 allow/deny，没有最终提交边界，第 3、12、13 条据此建议补事务寿命，不要求照抄其类或事件名。来源：microsoft/vscode 主分支 src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts，接口 100—121 行，2026-11-13 只读取得：https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/platform/lifecycle/electron-main/lifecycleMainService.ts 。
- VS Code 的 NativeWorkingCopyBackupTracker.onBeforeShutdownWithModified 会先保存可自动保存的文档，再重新取 modifiedWorkingCopies；保存失败或用户取消会 veto。本稿先结算、自动保存再询问的方向没有问题，第 3 条限定最终提交前丢弃与新增输入，未要求引入 Hot Exit。来源：https://raw.githubusercontent.com/microsoft/vscode/main/src/vs/workbench/services/workingCopy/electron-browser/workingCopyBackupTracker.ts 。
- Electron 的 second-instance 明确在 ready 之后才派发，relaunch 缺省保持工作目录与参数；app.quit 经过所有窗口许可，app.exit 则绕过。对照说明本稿第 14 条的 starting 转交与第 11 条更新接管必须另写，不能按“薄壳”推定框架替我们保证。来源：https://www.electronjs.org/docs/latest/api/app 。
- Electron 的 autoUpdater 同样把准备完成与退出安装分开，更新退出的事件次序与普通退出有差别；不是换成 Electron 就天然解决全局关闭事务。来源：https://www.electronjs.org/docs/latest/api/auto-updater 。

## 第 16 条撤回与依据校正

第 16 条《无应答分支强制显示对端 pid，但 hello 正是唯一的 pid 来源》（撤回）：补查 Windows 官方 API 后，GetNamedPipeServerProcessId 可以从命名管道句柄取得服务端进程 id，最低支持 Windows Vista，覆盖本稿 Windows 10/11 范围；Spec 只需承诺行为，不必指定此实现。现有 nb-host 查询不返回 pid 是实现扩展点，不足以据此断言目标合同不能实现。连接失败/查询失败仍宜显示“无法取得”，但不再作为有效发现。官方出处：https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getnamedpipeserverprocessid 。

外部参照均已实际只读取得：VS Code lifecycleMainService.ts 的 100—121 行区分 veto 阶段与不可再 veto 阶段；workingCopyBackupTracker.ts:102—124 自动保存后重新取 modifiedWorkingCopies、293—317 保存失败/取消 veto；Electron app 文档 second-instance 的 ready 顺序、relaunch 的 cwd/args 保持，以及 auto-updater 的退出次序均与上节引用一致。没有把这些参照当作 NeuroBook 的既有实现。

### 21. EOF 的有序停止被推广为壳所有退出路径，和已定强杀边界矛盾
- **严重程度**：建议；**类别**：合同、文档。
- **位置**：desktop-shell“时序与寿命”最后一项、输出 22、场景 8；server-host“托管宿主”。
- **现象**：时序条目说“壳退出时标准输入关闭，服务端读到结束同样有序停止，所以壳在任何路径上退出都不会留下自有服务端”；输出 22 却承诺强杀/注销/关机时树被结束、不保证有序停止。前一句把流结束的合作处理说成对所有退出的证明。
- **为什么是问题**：readline close 只有服务端仍活着且事件循环能执行时才触发。壳被 Job Object 连树结束时不存在这一步；反过来只关 stdin 且后端卡住，也不能单靠 EOF 保证它最终消失。若实现者拿 EOF 代替壳/launcher 的树收口机制，正常静态检查能过，异常时却可留进程。已接受强杀数据边界无需更改，应删掉错误推理。
- **如何核实**：指定 nb-host/src/server/host.ts:146—151 的回调只是 requestStop，不是 OS 级父子绑定；t01 两轮报告已区分 Job Object 强杀与 stdin 合作收口。固定输出 22 已明确不保证有序，两句话相互覆盖却给不同保证。无新增强杀实验，未把原型“不留孤儿”证据归因给 EOF。
- **建议改法**：正常/异常分开写：合作退出经 stop/EOF 并等真实退出；非合作结束由 launcher/进程树寿命边界约束，只保证已提交数据，不保证有序。强杀验收同时覆盖壳 Bun 与 launcher，不只结束整棵树后断言没有孤儿；第 18 条的超时路径继续独立验真实退出屏障。
