### 1. closing 重试没有覆盖旧壳在两次请求之间退出（第二轮 2 未解决）
- 严重程度：重要。
- 位置：snapshot-r3/desktop-shell.md:63—68、187，输出 2、3 与场景 5。
- 现象：3 秒现已只限制单次应答，不限用户决定时长；但收到 closing 后只能每秒重发，直到收到 ok 或 stopping。旧壳关闭成功后会放锁退出，不保证活到下一次请求。
- 为什么是问题：B 在第 0 秒收到 closing；A 在第 0.1 秒得到同意，服务端很快停止，A 在第 0.5 秒放锁退出；B 第 1 秒再连时地址上已没有实例。B 从未收到 stopping，既不满足输出 3 的等待放锁分支，也不满足“连上了但没有应答”，照重试规则会一直连一个已消失的地址。场景 5 要求同意关闭后 B 自动接续启动，在这个正常时序里没有可执行的转换。
- 核实：对固定稿作逐步时序对照；每次应答后连接关闭，停止没有最短时长，也没有保留 stopping 应答至所有等待者确认的约定。此为合同反例，未声称运行了 Windows。
- 建议改法：每次重试发现端点不存在或连接断开时，回到取桌面锁并重新 hello 的判定循环；只有取锁成功才能成为新壳，失败则重新核对当前持有者的版本与状态。补“closing 后旧壳在下一秒轮询前完成退出”的验收，不用延迟退出补竞态。

### 2. 项目工作汇总没有闭合 idle-grace 状态的漏报（第二轮 3 未解决）
- 严重程度：重要。
- 位置：snapshot-r3/specs-r2-to-r3.diff:159—160，server-host“在跑的工作”；依据 runtime/projects.md 输出 2、5、9、11，plot/checks.md“边界与兼容”。
- 现象：改成向“每个运行中的项目实例”取登记，并特意排除为宽限期中的项目唤醒；没有规定 idle-grace 必须查询或列入 failed。项目合同却把 running 与 idle-grace 明确分开，宽限期是开始停止之前的 5 分钟，并不代表项目工作已结束。
- 为什么是问题：A 项目发起剧情检查，然后关闭 A 的窗口，只留下书架窗口。A 进入 idle-grace，检查按既有合同继续运行。此时关闭最后的书架窗口，若按 running 状态枚举并沿用无租约项目访问规则，A 会被跳过或拒绝，而本稿没有要求将被跳过的存活项目标为未知；items/failed 仍可为空，关闭不提示即中断工作。这仍违反“有任务先提示、由用户决定”。
- 核实：projects 输出 5 规定宽限期满才停止，输出 9 拒绝无租约访问 idle-grace；plot/checks 的 run 明定调用方断开不影响检查。worktree plot/backend/checks.ts:63—72、95、116 只按入口停止或显式 cancel 中止，不按窗口离开中止。静态合同与真实入口对照，未调用模型。
- 建议改法：明确汇总所有仍存活且可能有工作的项目代次，至少包括 running、idle-grace；经宿主 IPC 只读查询，不 acquire、不续宽限期。存活但不能查询的代次进 failed，不能当空。补“项目窗口已关、项目处于 idle-grace，只有书架窗口”的验收。

### 3. onClose 把中心的移除按钮写成保留中心记录
- 严重程度：重要。
- 位置：snapshot-r3/specs-r2-to-r3.diff:239；workbench/notifications.md 输出 14、18 与状态表“在通知中心”。
- 现象：新增输出 18 把弹出通知与中心里的关闭按钮都纳入 onClose，并统一规定“只撤下弹出的那条，中心里的记录与动作照旧”。已有输出 14 规定中心的按钮是“移除”，点它只从中心移除；状态表也明确同一行为。这两处没有被修改。
- 为什么是问题：通知中心可见时新通知只进中心、不弹出（输出 16）。用户在中心点击这条更新提示的 X：按输出 14 应删除中心记录；按输出 18 却必须保留它、只撤一个根本不存在的弹出项。同一个现有动作无法同时满足两条合同。若以新增规则为准实现，中心的移除按钮变成点了仍在；若沿用旧规则又会违反新增 planned 合同，后续必须重裁决和返工。
- 核实：固定 diff 与主工作区同一 Spec 的输出 14、16、18 直接对照；worktree WorkbenchNotificationsView.vue:96 的唯一 X 调 center.remove(entry.id)，确认不是两个现有按钮。此为合同冲突，不以尚未实现 onClose 为缺陷。
- 建议改法：分开定义来源：弹出项关闭只撤弹出项并回告；中心“移除”继续删除中心记录，并明确它是否也表示“以后”、是否回告。保留现有删除语义即可补关闭回传，不必增加第二个 X。补中心可见且未弹出通知时点 X、刷新不重投的组合验收。

## 第 2 条撤回
第 2 条《项目工作汇总没有闭合 idle-grace 状态的漏报》（撤回）：进一步对照后，“每个运行中的项目实例”可以合理涵盖仍存活的 idle-grace；“不唤醒”不等于“不查询”。本轮指定的是宿主进程间链路，并未要求走受租约限制的插件远程调用，因此不能用后者的 denied 证明宿主查询必然漏项。worktree 项目管理器的 running(id) 也包括 idle-grace（manager.ts:403—415）。原第 2 条把一种不符合全部目标的实现选择写成合同允许的漏报，证据不足，不属于本轮要求的实质缺陷，撤回、不计有效。第二轮第 3 条不再重复报告。
