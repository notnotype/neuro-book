# t16 设计审查第 3 轮（Opus）：r3 计划（一个请求传整个文件夹、落点收窄到插件页）

## 1. Bun.serve 默认 maxRequestBodySize 是 128 MiB，nb-host 没有改；256 MiB 的总上限按现在的装配到不了路由，用户看到的是没有 {code, detail} 的空 413

- 位置：计划“行为”第 3 条（总 256 MiB）、“设计”的“路由”（“上限在流里数”）；packages/nb-host/src/http/plugin.ts:76-87（Bun.serve 只设 hostname、port、idleTimeout: 0、fetch、error，没有 maxRequestBodySize）。
- 核实：node_modules/bun-types/serve.d.ts:761-764 写明 `@default 1024 * 1024 * 128`。本机 Bun 1.4.4 实测（/tmp 下的探针，Bun.serve 边读边数）：100 MiB 的 Blob 请求体 200 通过；200 MiB 的 Blob 请求体与 200 MiB 的分块流（无 Content-Length）都直接得到 413、响应体为空，处理函数的结果不起作用。
- 触发：拖入一个 130 MiB 到 256 MiB 之间的插件文件夹（例如带大模型权重或大字体资源的构建目录）。页面数到的没超 256 MiB，照常上传；Bun 在 128 MiB 处回空体 413，页面解析不到 `upload-too-large` 的 `{code, detail}`，只能落到“读取或上传没有完成”或通用错误。上限的两条说法（页面 256、实际 128）对不上，Spec 写 256 也就错了。
- 建议：二选一并写进计划：(a) 把总上限降到 128 MiB 以内（留出分帧头的开销，例如 120 MiB），与 Bun 缺省对齐，不动 nb-host；(b) 在 nb-host 的 HttpPluginOptions 加 maxRequestBodySize（由装配方给，start.ts 传 256 MiB 加分帧余量），并在计划里说明这会放宽同一监听上所有路由的上限（各路由仍有自己的 bodyLimit，或像本路由一样在流里数）。不论哪种，计划都要写“总上限加上分帧头的开销不超过监听的 maxRequestBodySize”，并加一条测试：略超页面上限的请求得到的是本路由的 `upload-too-large` 而不是 Bun 的空 413。另外 dispatch 或页面要能把空体 413 也认成“太大”，免得以后有人改了一边又对不上。
- 严重程度：高（按计划写的上限照做，一段常见的大小区间会以错误的提示失败，且 Spec 写的数字不成立）。

## 2. 预览、确认框开着时，拖动落在 Dialog 的遮罩上（Portal，在插件页根元素之外）："正在处理上一个文件夹"的提示出不来，浏览器里松手还会把整个标签页导航走

- 位置：计划“行为”第 3 条末句与“页面”第 4 项（进行中再拖入给提示）、“页面”第 3 项（落在插件页以外照浏览器缺省）；packages/nb-ui/src/components/feedback/Dialog.vue:11-14（DialogPortal、DialogOverlay、模态叠放）；PluginsPage.vue:456-480（预览确认框就是这个 Dialog）。
- 问题：计划把“进行中”定义成“上传中，或预览、确认框开着”，要求这时再拖入给提示。但确认框是模态 Dialog，遮罩经 Portal 挂到 body 并盖住整个插件页，拖动的目标是遮罩而不是插件页根元素，根上的 dragenter、dragover 收不到；没有人 preventDefault，按计划“照浏览器缺省”。Chromium 里把文件夹落在没有处理的地方会把标签页导航到 file:// 目录列表（从行为推断，未在本机复现），NeuroBook 整页卸载，预览中的上传也就留在服务端（见第 3 条）。
- 触发：拖入文件夹 A，预览框弹出；用户发现拖错了，直接把文件夹 B 拖到框上或框外的遮罩上松手。
- 另外，dom 测试“进行中再拖入”若直接在根元素上派发事件，会在真实浏览器到不了的路径上通过。
- 建议：二选一写进计划：(a) 预览、确认框开着时，在 Dialog 内容与遮罩上（或经 Dialog 的一个插槽、包一层元素）也处理 Files 拖动：preventDefault、dropEffect = "none"、在框内显示“正在处理上一个文件夹”；(b) 把“确认框开着时再拖入”改成“替换当前预览”（先删旧上传、关框、走新的），同样要在遮罩上接住拖动。dom 测试按真实结构在遮罩元素上派发；Lab 里手动或 e2e 验一次。
- 严重程度：中。

## 3. 插件页根元素只是内容自身的高度，盖不住设置窗口的整个右侧：落在分区标题、留白、窗口左栏上就是“浏览器缺省”，而这个缺省在浏览器里是整页导航走、在桌面里是什么都不发生，两边都没有任何提示；t15 还没开工，计划把这一块整个推给它

- 位置：计划“页面”第 3 项（落点是插件页根元素、落在外面照浏览器缺省、归 t15）；PluginsPage.vue:372 与 :499-503（`.plugins-page` 只是 flex 列，没有 min-height）；settings/web/components/SettingsWindow.vue:375-395（滚动布局里插件页之上是 SettingsSectionHeading，外面是 ScrollArea 与列的留白）；SettingsPageFrame.vue:60-62；desktop/src/bun/index.ts:312-316 与 :616-618（导航规则先拦全部 `^*`，被拦的 will-navigate 只有 http(s) 交系统浏览器，file:// 被丢掉）；.agents/works/w00046-desktop-release/README.md:37 与 tasks/t15-drag-import/README.md（t15 排在 t16 之前，但状态 planned、下一步“待补充”）。
- 触发：(a) 浏览器里，第三方插件为空、列表短时，把文件夹拖到插件页底下的空白处或分区标题“插件”上松手：标签页导航到 file:// 目录列表，NeuroBook 卸载（Chromium 的缺省行为，从行为推断，未复现）；(b) 桌面里同样的动作：导航被规则拦下、不交给任何人，窗口毫无反应，用户以为拖放坏了。覆盖层只在根元素内出现，用户也不知道该往哪里拖。
- 建议：(1) 插件页根元素至少撑满它所在的内容区（`min-height: 100%` 对上 ScrollArea 的视口，或者把落点放在 SettingsPageFrame 一级、由插件页声明“本页接受文件拖入”），覆盖层用 sticky 或相对视口定位，长列表滚动时也看得见；(2) 设置窗口这个浮层自己（不是 window）对 Files 拖动统一 preventDefault、dropEffect = "none"，落点之外显示“拖到插件页”——这仍是“各管各的元素”，不接管工作台，也是 t15 要的“没有落点的地方”在设置窗口内的那一份；(3) 若坚持全交给 t15，计划写明 t16 依赖 t15 的这部分先合入，并在验收里加一条“拖到设置窗口的其它地方不会离开应用”。
- 严重程度：中。

## 4. 同时至多 8 个上传、且满了就拒绝：刷新或关掉标签页会留下没人删的上传（组件卸载与 keepalive 都不跑），开发插件时反复刷新几次就会被“上传太多，稍后再试”挡住最长一小时；正在接收的上传算不算进 8 个也没写

- 位置：计划“行为”第 5 条（页面离开时 keepalive 删除、10 分钟一次清扫、1 小时没用过才删）、“设计”的“服务端”末项（至多 8 个，第 9 个以 `upload-too-large` 拒绝）。
- 问题：(a) “页面离开”在这里是插件页组件卸载（设置窗口是工作台上的浮层，PluginsPage.vue 已用 onBeforeUnmount）。整页刷新、关标签页、桌面窗口关掉时 Vue 不卸载组件，keepalive 的 DELETE 不会发出；预览或确认框开着的那个上传就一直留到清扫（最长约 1 小时 10 分）。(b) 上传成功的响应与页面的 abort 赛跑：服务端已登记 id 并回了响应，页面恰好卸载、abort 了 fetch，页面永远拿不到 id。(c) “同时存在”只说了交回后的上传；若接收中的不算，8 个以上并发的 POST 会同时写盘（各自至多 256 MiB），上限形同虚设；若算，要写明在请求开始时就占位、失败或断开时归还。
- 触发：插件作者的常见循环：改代码、构建、拖进来看预览、发现问题、F5 刷新、再拖。8 次以内一小时内就满；第 9 次拖入得到“上传太多”，而那 8 个全都已经没有页面持有。错误码还是 `upload-too-large`，与“文件太大”同码，页面只能靠详情区分。
- 建议：满了时先淘汰最久没用的“可用”（不在使用中、不在接收中）上传，只有 8 个全在使用或接收中才拒绝；接收中的在请求开始时占位。页面另在 `pagehide` 上发 keepalive 的 DELETE（与卸载时同一个函数，去重）。“上传太多”用单独的码（例如 `upload-busy`，429 或 503），不复用 `upload-too-large`。
- 严重程度：中。

## 5. 分帧格式少了几条必须写死的规则：头长度 N 没有上限、头的 JSON 形状没定、没有结束帧或总数，空请求体与 N = 0 的含义未定

- 位置：计划“设计”的“请求体的分帧”；切片 2 的测试清单（“超长头”没有给出数字）。
- 问题与触发：
  - N 是 4 字节大端，最大约 4 GiB。解析器要先把 N 字节的头收齐才能 JSON.parse；没有上限时，一个 N = 0xFFFFFFF0 的请求会让服务端一直缓冲到总量上限（256 MiB，或 Bun 的 128 MiB）才失败。路径至多 1024 字节，头 `{"path":…,"size":…}` 至多约 1100 字节（控制字符不合规，JSON 不会产生 \u 转义），可以定 N ≤ 2048，超了立刻 `upload-malformed`，不再读。
  - 头的形状：要求恰好两个键，`path` 是字符串、`size` 是非负安全整数；`size` 大于单个上限时在读内容之前就回 `upload-too-large`；“已收字节 + size” 超总量时也在读之前回。这些都不写，实现者可能先读完内容再按实际字节判断，超限的那一段白写盘。
  - 没有结束帧也没有总数：流在两帧之间干净结束就是“完整”。Bun 下客户端中途断开时读流会以 AbortError 失败（本机 1.4.4 实测，分块与定长两种都是），所以断开不会被当成完整；但格式本身分不出“恰好在帧边界被截断”。建议加一个 N = 0 的结束帧（或开头一个 `{files, bytes}` 的总头），流在结束帧之前结束就是 `upload-malformed`，结束帧之后还有字节也是；顺带让页面预览的“N 个文件”与服务端核对。
  - 空请求体、只有结束帧（0 个文件）：写明按 `upload-malformed` 拒绝，或交回空上传让 inspect 报清单缺失，二选一。
  - 解析器按块读、按块写时要等每次写盘完成再读下一块（写不过来时不在内存里堆块）。本机实测 Bun 在处理函数读得慢时只多占约 27 MiB（100 MiB 请求体），背压是有的，但前提是解析器自己 await 写入。
- 建议：把上面几条写进“请求体的分帧”，切片 2 的测试按这些数字写（N = 2049、size 超单个上限、结束帧之前截断、结束帧之后多字节、0 个文件）。
- 严重程度：低。

## 6. “按小写比”与 Windows 文件系统的大小写折叠不一致，`wx` 撞名在 Windows 上是真实会发生的；它与 mkdir 的 ENOTDIR 该报哪个码没写，切片 3 的“wx 冲突”测试经路由也触发不了

- 位置：计划“设计”的“路径规则”（NFC 后按小写比）与“服务端”的 `receive`（`wx` 独占新建）；行为 6 的失败码；切片 3（“`wx` 冲突”）。
- 核实：本机 Bun 中 `"ς".toLowerCase() !== "σ".toLowerCase()`，`"ı"`/`"i"`、`"ſ"`/`"s"` 同样不等，但三对的 toUpperCase 都相等。NTFS 不分大小写的比较按它的大写表（$UpCase）做，这几对在 Windows 上是同一个名字（从 NTFS 按大写比较的行为推断，未在 Windows 上实测）。
- 触发：Windows 上拖入含 `λόγος.md` 与 `λόγοσ.md`（或 `ı.svg` 与 `i.svg`）的文件夹：规则判定不重名，第二个文件 `wx` 打开得到 EEXIST。按计划没写映射，多半落到 `upload-failed`（500，“写盘失败”），用户看到的是服务端出错而不是“文件名冲突”。Linux 上的测试无论怎么经路由都撞不出 EEXIST（大小写敏感，且上传 id 是新目录），“`wx` 冲突”这条测试只能伪造。
- 建议：比较键改成 `NFC → toUpperCase → toLowerCase`（覆盖上面几对，仍与 NTFS 不完全等价，写成已知限制）；`wx` 的 EEXIST、建父目录时的 ENOTDIR、EISDIR 一律映射为 `upload-path-invalid`（400，详情带路径），其余写盘错误才是 `upload-failed`。切片 3 把“`wx` 冲突”改成对映射函数的单元测试，或注入一个预先建好同名文件的目录工厂，写明它不经路由。
- 严重程度：低。

## 7. 暂存区生命周期还有三处时序没写：首次清空与第一个接收并发、清扫的范围（只看内存表，还是扫目录）、服务端停止时正在接收的请求

- 位置：计划“行为”第 4、5 条，“设计”的“服务端”（`receive`、`use`、`discard`、`sweep`、`clear`，计时器随能力建立、随服务端停止撤销）；nb-host/src/http/admission.ts:9 与 :128-145（HTTP 排空等在途请求，最多 20 秒）；nb-runtime/src/application/contracts.ts:50-57（宿主能力有 `release`）。
- 问题与触发：
  - 首次清空：“第一次用到暂存区时清空整个目录”若由第一次 `receive` 触发而不等它完成，或两个窗口几乎同时拖入，清空的递归删除会删掉另一个刚建好的上传目录，那次上传在写第一个文件时以 ENOENT 失败（报 `upload-failed`）。“第一次用到”与括号里的“插件页第一次打开”也是两个不同的时刻（打开页面只调 `list`，不经上传能力）。
  - 清扫：接收中的上传 id 在请求结束时才登记。若 `sweep` 实现成“扫 plugin-uploads 目录、删掉表里没有的子目录”来顺带清孤儿，它会删掉正在接收的目录。
  - 停止：一个大的上传正在接收时服务端停止，排空要等它最多 20 秒，然后 `listener.stop(true)` 强断；`receive` 的清理在读流失败后才跑，这时能力可能已 `release`、进程可能已退出，目录留到下次首次清空（这本身可以接受）。桌面关窗的握手（t09）有自己的时限，是否容得下这 20 秒没核对。
  - 安装后删除：计划写“安装结束（成功或失败）时删”，没说异常路径；`install` 里 `inventory.install` 抛错（不是返回失败）时也要删。
- 建议：清空做成一个只跑一次、可复用的 Promise（能力创建时或第一次调用任一方法时启动），`receive`、`sweep`、`discard` 都先等它；明确 `sweep` 只遍历内存表，扫目录只在首次清空里做；能力 `release` 时取消所有接收中的请求（各自的 AbortController），不让上传拖长排空，并写明 release 之后 `receive` 直接拒绝；入口里把 `discard` 放在 `finally`。测试：首次清空与第一个接收并发时接收成功；清扫期间有接收中的上传不受影响；停止时接收中的请求立即结束。
- 严重程度：低。

## 8. nb-host 转交插件路由时用 `new Request(target.href, request)`，在 Bun 里这会丢掉请求体的背压：路由“边读边写”，服务端照样把整个请求体收进内存

- 位置：计划“设计”的“请求体的分帧”（“fetch 边读边发”“能流式处理”）与“服务端”的 `receive`（边读边写，内存有界）；packages/nb-host/src/http/dispatch.ts:144（`handler.fetch(forwardedRequest(...))`）与 :173-178（`forwardedRequest` 返回 `new Request(target.href, request)`）。
- 核实（本机 Bun 1.4.4，/tmp 下的探针；客户端在子进程里发 100 MiB 的 Blob，服务端每读一块等 20 ms，记服务端进程 RSS 峰值，各跑 3 次）：
  - 直接读 `req.body`：峰值约 60 MiB（起点 34 MiB）；
  - 先 `new Request(newUrl, req)` 再读（即 dispatch 现在的写法）：峰值约 142 MiB，多出的约等于整个请求体；
  - 改成 `new Request(newUrl, {method, headers, body: req.body, signal: req.signal, duplex: "half"})`：峰值约 61 MiB，背压恢复；客户端中途断开时读流仍以 AbortError 失败（分块与定长两种都测了）。
- 触发：按计划实施后，任何一次大的上传都会让服务端 RSS 涨到约等于上传大小；第 1 条若把上限放到 256 MiB，几个并发上传就是上 GiB 的内存。路由层的测试（真实 Hono、不经 nb-host 的分发）看不到这一点。现有的附件上传（attachments.ts 的 `readLimited`）本来就整份读进内存，所以至今没暴露。
- 建议：改 nb-host 的 `forwardedRequest`，显式传 `body: request.body`、`duplex: "half"`、`signal` 与方法、头（GET、HEAD 不传 body），在 dispatch.test.ts 加一条“转交后读请求体仍有背压”或至少“转交保留 signal 与流式正文”的测试；这是 nb-host 的改动，计划里要列为本 Task 的前置切片或单独一个小 Task，并在切片 3 加一条经真实 Bun.serve 与 nb-host 分发的上传测试（同时覆盖第 1 条的监听上限）。
- 严重程度：高（计划的内存有界前提在现有分发层上不成立，不改上游就做不到“流式”）。
- 更正：上面“各跑 3 次”不准确，直接读与现有转交各 3 次，显式传 body 的写法 2 次。

## 9. 上传客户端会收到三种形状的失败，计划只写了路由自己的一种；总量上限算不算分帧头也没写，页面与服务端数的可能不一样

- 位置：计划“行为”第 6 条（路由返回 `{code, detail}`）、“页面”第 2 项（上传客户端）；nb-host/src/http/dispatch.ts:85、:101-104、:131-141、:150-151、:227-229（宿主自己的失败是 `{error: {code, message}}`：403 `origin-not-allowed`、503 `stopping`/`startup-failed`/`plugin-unavailable`、404 `not-found`、500 `internal-error`）；第 1 条里 Bun 的空体 413。
- 触发：服务端正在关闭时拖入（503 `stopping`）；`nbook.plugins` 入口失败或停止时（503 `plugin-unavailable`，或路由没挂上的 404）；超过监听上限（空体 413）。若客户端只按 `{code, detail}` 解析，这些都会解析失败，落到哪条提示取决于实现者。
- 总量：页面按文件内容数 256 MiB，服务端“字节在流里计数”若数的是线上字节（含每个文件约百字节的头，10000 个文件约 1 MiB），内容恰好在 256 MiB 附近的文件夹页面放行、服务端拒绝。
- 建议：计划写明客户端的判定顺序：先看状态码（413 一律“太大”，不论有没有正文），再按两种已知形状取 code，其余（含网络错误、正文解析失败）都是“读取或上传没有完成”；503 `stopping` 可以单独说“服务端正在关闭”。总量写明两边都只数文件内容，分帧头另算并计入第 1 条的监听上限余量。dom 测试给上传客户端的替身各回一次这几种形状。
- 严重程度：低。

## 10. “`new Blob([...File])` 不复制内容、fetch 边读边发”在 Chromium 与 WebView2 上是推断，计划写成了事实；没有安排任何一处去看它

- 位置：计划“设计”的“请求体的分帧”第 2 句。
- 判断：按 Chromium 的实现，由 File 拼成的 Blob 只保存对文件的引用，fetch 把它作为 blob 正文交给网络进程按块读盘，渲染进程不持有内容；Content-Length 已知（因此 Bun 会在第 1 条的上限处立刻拒绝，不等读完）；文件在拿到 File 之后被改写时上传以 ERR_UPLOAD_FILE_CHANGED 失败，正好对上计划的“读取或上传没有完成”。WebView2 与 Chromium 同一套网络栈，结论相同。以上都是从 Chromium 的设计推断，本次没有在浏览器里实测。另有一处没有把握：一万个 File 加一万段头拼成两万段的 Blob，构建与发送前的准备时间没有数据。
- 风险：若某个版本把拼接的 Blob 物化（例如头部是 ArrayBuffer 段时整体转成内存 Blob），256 MiB 的上传会在渲染进程里多占同样大小；桌面窗口内存小时会卡顿或崩溃。
- 建议：计划把这句标为“推断”，切片 5 的 e2e 或切片 6 的 Windows 实测加一次观察：用一个约 100 MiB、几千个文件的目录上传，记录渲染进程内存与“开始发送”前的耗时；结果写进 Task 记录。若不成立，退路是用 ReadableStream 正文（Chromium 105 起支持流式上传，但要求 HTTP/2 或 `duplex: "half"` 且只在 HTTP/2 下流式——本机回环是 HTTP/1.1，这条路走不通，要另想办法），所以早一点知道更好。
- 严重程度：低。

## 11. “被新拖入的文件夹取代时删”与“进行中再拖入不理”互相排斥，前者在现在的规则下走不到

- 位置：计划“行为”第 5 条（页面在“被新拖入的文件夹取代”时删除）与第 3 条末句、“页面”第 4 项（上传中、预览或确认框开着时再拖入不理，取消后才能拖下一个）。
- 问题：页面持有一个上传的时间段，恰好就是“预览中或确认框开着”，也就是“进行中”；预览失败与取消都会立即删。于是不存在“页面持有上传、又接受新拖入”的时刻，“被取代时删”是死规则；dom 测试若照着它写，只能伪造一个真实界面到不了的状态。
- 触发：实施者照计划为“取代”写删除分支与测试，或反过来，为了让“取代”可达而放开“进行中不理”，两者结果不同而计划没定。
- 建议：与第 2 条一起定：要么删掉“被取代时删”（保留“进行中不理”），要么改成“确认框开着时拖入新文件夹就替换预览”（删旧上传、开新的），并去掉“确认框开着”出“进行中”的范围。只留一种。
- 严重程度：低。
