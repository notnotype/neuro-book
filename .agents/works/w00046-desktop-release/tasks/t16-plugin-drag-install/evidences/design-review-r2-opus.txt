# t16 设计审查 r2（Opus，只读）

对照 r1 十七条与处理表逐条核对了 r2 计划；代码在 master 上核对。r1 第 1、3、7、10、11、16、17 条已解决；第 5、6、14 条“接受/不做”的取舍本身成立（第 14 条与下面第 5 条有交互）；第 2、4、8、9、12、13、15 条只解决了一部分，缺口写在下面对应各条。合同升到 6：消费方只有插件页、Lab 夹具与 agent 浏览器入口的 list()（packages/neuro-book/src/plugins/agent/web/plugin.ts:637），同一份构建一起发布，没发现问题。

## 1. 挂在 window 上的拖放监听会接管整个工作台页面，不只是设置窗口
- 位置：计划“设计/页面”第 3 条（“插件页挂载期间在 window 上监听”）；docs/specs/settings/settings-window.md:148（设置窗口是工作台挂在页面根上的页面浮层）、:196（“非模态浮动窗口”）、:239（“每个浏览器页面各一份”）。
- 问题：设置窗口与编辑器、文件树、书架在同一个文档里，而且是非模态的，用户可以一边开着插件页一边操作工作台。window 上的 dragover 对所有含 Files 的拖动 preventDefault、设 dropEffect = "copy"，drop 冒泡到 window 时插件页照收。于是插件页挂着时，拖到编辑器、文件树上的文件夹也会被当成“安装插件”；编辑器（Tiptap/ProseMirror）自己的 drop 处理也跑一遍，两边都动作。t15 接着要给文件树、编辑器、书架加拖入目标，到时候谁收到 drop 取决于监听登记的先后与冒泡顺序（全局规则里“结果靠加载顺序碰巧成立”的信号）。
- 触发：设置窗口开在“插件”分区、拖到窗口旁边露出的编辑器上松手；或者 t15 合入后，在开着插件页时往文件树拖文件夹。
- 改法：window 上只做“防导航”这一件事（含 Files 的 dragover/drop 一律 preventDefault，落点不在接收区时 dropEffect = "none"）；接收安装只在落点位于设置窗口根（含它经 Portal 挂出的确认框，按已知的容器判断）之内、且 event.defaultPrevented 为假时进行；覆盖层也只在落点在设置窗口内时显示。更好的做法是把“谁接这次拖放”的仲裁放进共用的 src/ui/dropped-folder.ts（登记接收区，按 DOM 包含取最内层，外面有一个全局防导航的兜底），t15 直接登记，不各自挂 window 监听。切片 5 的 Windows 实测加一条“插件页开着时往编辑器上拖文件夹”。
- 严重程度：中。

## 2. 在途的写入不在状态机里：封口、删除、过期清扫都可能撞上正在进行的 PUT（r1 第 2 条的 b 项没解决）
- 位置：计划“行为 4”（状态：写入中、已封口、使用中、已删除）；“设计/服务端”的 write、seal、discard、sweep；“页面 upload.ts”（并发 4 个 PUT、任一失败就删）。
- 问题：状态机只把预览、安装算作“使用中”，正在写的 PUT 不算。于是：(a) 页面并发 4 个 PUT，一个失败就 DELETE，其余 3 个已经通过“写入中”的检查、正在逐段 mkdir 与流式写，rm 之后它们会重新建出 <id>/sub/ 与文件，成了表里没有、只有下次启动才清掉的孤儿；“超过总量删掉整个上传”是同一情形。(b) seal 没说要等在途写入：第 N 个 PUT 还在写时收到 seal（页面的 bug，或者以后有人改成“发完就封”），封口后那个文件才落地，预览与安装看到的文件集合不同，又回到 r1 说的预览与安装不一致。(c) 1 小时清扫按 lastActive 判断，写一个大文件期间如果只在开始时记活动，慢链路（远程部署）上会被当成闲置删掉。
- 触发：上传中途某个 PUT 因磁盘满或单文件超限失败；用户上传中途关闭设置窗口（页面发 DELETE，浏览器同时取消在途的 PUT，服务端的写还在收尾）。
- 改法：把在途写入也计入（writers 计数或每个上传一把锁）：seal 在 writers > 0 时回 409 upload-state（或等它们结束）；discard 先把状态改成已删除、通知在途写入中止（把写入的流接到一个 AbortController），等 writers 归零后再 rm；每个写在 mkdir 之前与写完之后各核对一次状态，已删除就删掉自己写的文件并回 404；sweep 跳过 writers > 0 的上传，lastActive 在收到数据块时更新。页面在第一个失败时 abort 其余 PUT 再发 DELETE。测试加两条：“PUT 在途时 DELETE，结束后磁盘上没有这个上传的目录”“PUT 在途时 seal 得到 409”。
- 严重程度：中。

## 3. 确认安装后立刻离开，页面的 DELETE 可能先于 install 到达，用户确认过的安装静默失败
- 位置：计划“行为 5”（“页面离开时用 keepalive 请求删”）；处理表第 2 条（“页面确认安装后不再删”）。
- 问题：处理表写了“确认安装后页面不再删”，计划正文却没有这个例外：行为 5 只说“安装由服务端在结束时删，其余由页面请求删；页面离开时用 keepalive 请求删”。install 走 RPC（单独的 RPC 端口与连接，nb-host/src/server/rpc-listener.ts），DELETE 走 HTTP 端口，两条连接之间没有先后保证；“使用中的删除排队”只在 install 已经进入 use 之后才起作用。DELETE 先到时上传已删，install 得到 path-rejected，而页面已经卸载，没人看到这个失败；用户下次打开插件页，插件没装上。
- 触发：点“安装”后马上按 Esc 或点关闭按钮关掉设置窗口（设置窗口只在有未保存改动时拦关闭，busy 不拦），或者直接关掉浏览器标签。
- 改法：计划行为 5 写明“install 发出之后页面不再请求删除，交给服务端在安装结束时删”；页面里用一个“已交给服务端”的标记，卸载与 pagehide 时看到它就不发 DELETE。服务端兜底不变（1 小时清扫）。dom 测试加一条“确认安装后卸载页面，不发 DELETE”。
- 严重程度：中。

## 4. “写到临时名再改名”在 Windows 上会被杀毒软件偶发打断，而状态机已经让改名没有必要；删除失败也没有定义
- 位置：计划“设计/服务端”write（“流式写到临时名再改名”）、discard、sweep、clear；证据 packages/nb-history/NOTES.md:30（本仓库在 Windows 上实测过：刚写入的大文件被杀毒或索引器占用，删除报 EBUSY，重试 2 秒也不解）。
- 问题：(a) 一个插件可以有上万个文件，每个都要一次 rename；Windows 上刚写完的文件被 Defender 扫描时，rename 常报 EPERM 或 EBUSY（graceful-fs 为此重试改名长达 60 秒），一次就会让整个上传以 upload-failed 作废，桌面又正是 Windows。(b) 改名防的是“读到写了一半的文件”，可 r2 已经规定只有封口后才能预览、安装，写失败的上传整个作废，半个文件不会被读到；改名只增加了失败面与一倍的文件操作，临时文件还放在上传目录里，写失败没清掉时会混进安装的复制范围。(c) discard、sweep、启动清空的 rm 在 Windows 上同样会 EBUSY，计划没写失败时怎么办：DELETE 回什么、启动清空失败会不会让宿主起不来。
- 触发：Windows 桌面上拖入一个几千个文件的插件文件夹；装完后立刻删上传目录。
- 改法：直接以独占方式（flag "wx"）打开目标路径流式写，写失败时删掉自己这个文件并把上传标成作废（seal 一律 409）；"wx" 顺带在大小写不敏感的文件系统上把同名冲突报成 EEXIST（见第 6 条）。删除失败只记诊断、表里照样标为已删除，DELETE 仍回 204，残留交给下一次启动清空；启动清空失败只记诊断，不挡启动。若坚持保留改名，临时文件放到上传目录之外（例如 plugin-uploads/.partial/），改名加短时重试。
- 严重程度：中。

## 5. 路径规则作用在所有上传的文件上、而且只在服务端逐个 PUT 时才查，`files` 用不到的一个怪名字就能让整次上传白传
- 位置：计划“设计/服务端”路径规则；“行为 2”（除 node_modules、.git 外都上传）；“不做”第 2 条（不做 r1 第 14 条）；“待确认”第 5 条。
- 问题：规则按 Windows 也合法来查、而且一律拒绝，这本身在待确认清单里，取舍可以接受；但它和“别的都上传”叠在一起：`files` 根本不会复制的文件（docs/截图 10:30.png、测试夹具 aux.json、macOS 的 `Icon\r`、名字以点结尾的目录）也要过这套规则。页面上传前只判数目与大小，不判路径，于是可能先传了上百 MiB，到某一个 PUT 才收到 400，整个上传作废；同一个文件夹走路径安装却能装上。页面与服务端各写一份规则时还会慢慢走样。
- 触发：作者在 macOS 或 Linux 上拖入源码目录，里面有一个带冒号或问号的截图、或一个 aux/、con.ts 之类的名字。
- 改法：规则写成纯函数放共享层（例如 src/plugin-platform/shared/upload-path.ts），页面在 collectFolder / collectInputFiles 收集时就用它查，第一个不合格的路径在上传之前就提示（“<路径> 的名字在 Windows 上不合法”），服务端照样用同一份再查。另请主会话重新看一眼“不做第 14 条”的理由：只上传 `files` 命中的顶层目录（取超集，不复制 glob 语义）会同时降低撞上这条规则、撞上 10000 个文件上限的概率；不做也行，但待确认清单里把“`files` 不用的文件名字不合法也会拒绝”写明。
- 严重程度：低。

## 6. 重名判断只按 NFC 字符串比，没有处理大小写冲突与“文件/目录同名”；写盘用原名还是 NFC 没说
- 位置：计划“设计/服务端”write（“同一路径写两次是 upload-path-invalid”）与路径规则（“NFC 归一化后再比”）；r1 第 9 条提到的大小写冲突在处理表里没有回应。
- 问题：(a) `README.md` 与 `readme.md` 在 Windows、macOS 的服务端上是同一个文件，按区分大小写的 NFC 字符串比不出重名，第二个写入“临时名再改名”时 Windows 的 rename 直接覆盖，静默丢一个文件；在 Linux 服务端上两者都收，与“插件要能在 Windows 上装”的初衷不一致。(b) 先写 `a` 再写 `a/b.js`（或反过来）时 mkdir、rename 报 ENOTDIR/EISDIR，按计划会落成 500 upload-failed，其实是请求的路径冲突。(c) “NFC 归一化后再比”没说写到磁盘的是原名还是 NFC 形式；若写 NFC，而 package.json 的 main 或 `files` 里写的是 macOS 产生的 NFD 名字，安装时会报入口缺失。
- 触发：(a) 浏览器在 Linux 上、服务端部署在 Windows（少见）；(b) 只有非浏览器客户端才会发；(c) 插件里有带变音符号或用 NFD 存的文件名（少见）。
- 改法：重名表的键用“NFC 后再转小写”，命中就是 upload-path-invalid，detail 说明是大小写或 Unicode 形式冲突；文件与目录前缀冲突也报 upload-path-invalid；写盘用页面给的原名，NFC 只用于比较。测试加这三条。
- 严重程度：低。

## 7. 总量上限“写完再累加”在并发下会超出；bodyLimit 遇到没有 Content-Length 的请求会把整份正文读进内存，与“流式落盘”矛盾（r1 第 8 条只解决了一半）
- 位置：计划“设计/服务端”write（“写完用实际字节数累加，超过上限删掉整个上传”）、“路由”PUT（“bodyLimit 单文件上限”）；node_modules/hono/dist/middleware/body-limit/index.js（hono 4.12.30）：有 Content-Length 时只看头，没有时先把整个正文读进 chunks 数组再交给处理器。
- 问题：(a) 4 个并发 PUT 各自通过检查后才累加，总量最多超出 3 到 4 个单文件上限（约 256 MiB）才被发现，磁盘上已经写下了。(b) 分块传输（没有 Content-Length）的请求在 bodyLimit 里被整份缓冲到 64 MiB，之后的“流式写”拿到的是内存里的副本；浏览器 fetch(File) 会带 Content-Length，所以今天只影响非浏览器客户端。(c) 超总量时服务端删掉整个上传，页面在途的其余 PUT 会陆续收到 404 upload-not-found，页面若按最后一个失败提示，用户看到“上传已失效”而不是“超过上限”。
- 触发：(a) 一个文件夹里有几个几十 MiB 的大文件、总量接近 256 MiB；(b) 用 curl 之类分块上传。
- 改法：不用 bodyLimit，照 packages/neuro-book/src/plugins/agent/backend/attachments.ts 的 readLimited 写法在流里逐块计数：同一个计数同时对单文件上限与本上传的总量上限，有 Content-Length 时开写前先按它预留、失败或中止时退还，超限立即取消读取、回 413。页面只提示第一个失败。测试“并发写时的总量”按此断言磁盘上的总字节不超过上限加一个数据块。
- 严重程度：低。

## 8. `?path=` 经 Hono 的 c.req.query 解码时会把 `+` 变成空格
- 位置：计划“路由”PUT（“path 只解码一次”）；node_modules/hono/dist/utils/url.js:127-132（_decodeURI 先把 `+` 换成空格再 decodeURIComponent）。
- 问题：query 按表单编码的规则解码，`+` 是空格。页面若用模板字符串直接拼（或用 encodeURI），`a+b.js`、`c++/x.h` 到服务端变成 `a b.js`；用 encodeURIComponent 或 URLSearchParams 则没问题。计划只写了“只解码一次”，没写编码一侧的约定，测试列表里也没有 `+`。
- 触发：插件里有名字带 `+` 的文件（例如 `icons/zoom+.svg`）。
- 改法：计划写明页面用 URLSearchParams（或 encodeURIComponent）编码 path，服务端用 c.req.query 取一次；测试加 `+`、`%`、`#`、`&`、`=`、中文、`%2F`、`%2e%2e` 各一条。
- 严重程度：低。

## 9. 被新预览取代的上传没人删；“进行中”的范围不清
- 位置：计划“行为 3”最后一句（“上传或预览进行中再拖入……不理”）、“行为 5”（删除时机）；PluginsPage.vue:269-287（startInstall 直接覆盖 preview 与 previewPath）。
- 问题：删除时机列了预览失败、取消、安装结束、离开页面，没有“被取代”：上传 A 预览成功、确认框开着或已关（不算“进行中”）时，用户再拖入 B，或在路径框里输入路径重新预览，A 的 id 被覆盖，留到 1 小时清扫。“预览进行中”指 inspect 请求在途，还是确认框开着，也没写清；按现有 busy 只覆盖请求在途。
- 触发：拖错了文件夹，再拖一次正确的。
- 改法：行为 5 加“页面换了预览来源（新的拖入、选择文件夹或路径预览）时删掉旧的上传”；行为 3 写明确认框开着时再拖入怎么办（建议：不理并提示，与 busy 同样处理，免得确认框背后换了内容）。
- 严重程度：低。

## 10. 共用的 readDrop 按插件页的规则定了形状，t15 用不上；“types 含 Files”筛不掉页面内拖动图片
- 位置：计划“设计/页面”第 1 条（readDrop 交回 folder / file / many / none）、第 3 条（“页面内部元素的拖动（types 没有 Files）不理”）。
- 问题：(a) “恰好一个文件夹”是插件页的规则；t15 的文件树、编辑器要收多个文件与文件夹，`{kind: "many"}` 不带条目，t15 只能另写一份读取，r1 第 7 条想避免的重复又回来了。(b) Chromium 里从页面上拖一张 <img>（工作台里的封面、预览里的图片、主题编辑器的场景图）时 dataTransfer.types 也含 "Files"（浏览器把图片作为可落到桌面的文件提供），插件页会显示“松开以安装插件”，松手后走到“拖入一个插件文件夹”的提示。这一点是按 Chromium 的已知行为推断，没有在本仓库实测。
- 触发：(a) t15 实施时；(b) 设置窗口开着，把编辑器里的图片拖到别处。
- 改法：(a) readDrop 在同步段里取出全部条目，交回 `{entries: FileSystemEntry[], files: File[]}`，“只收一个文件夹”的判断留在插件页；(b) 在 document 上记一个“本页发起的拖动”标记（dragstart 置位、dragend 清除），有标记时不当作外部拖入。
- 严重程度：低。

## 11. e2e 的“合成 drop 验文件分支”按写法到不了文件分支，会因为错误的原因通过（r1 第 15 条 a 项没解决）
- 位置：计划切片 4（“拖入单个文件的提示（合成 drop，只验文件分支）”）。
- 问题：页面里 new DataTransfer() 加进去的 File 没有本机文件做后盾，Chromium 的 DataTransferItem.webkitGetAsEntry() 对它返回 null（从 Chromium 实现推断，未实测），readDrop 得到的是 `{kind: "none"}` 而不是 `{kind: "file"}`。如果页面对 none 也显示“拖入一个插件文件夹”，这条测试无论文件判定写对写错都会过，证明不了计划想证明的东西。
- 触发：实施切片 4 时。
- 改法：文件与文件夹的判定只放 DOM 单元测试（替身按真实形状给 isFile/isDirectory 的条目）；e2e 里合成的 drop 改为验证更值钱的一件事：在插件页、设置窗口侧栏、确认框上派发含 Files 的 dragover 与 drop 后 event.defaultPrevented 为真、页面没有导航（第 1 条的防导航）。若仍要在 e2e 里验提示，页面用 data 属性标出判定结果（例如 data-drop-kind），断言它而不只断言文字。
- 严重程度：低。

## 12. “提示哪个文件读不了”按现在的上传方式分不出来；只按文件数停的遍历遇到不含文件的链接环停不下来
- 位置：计划“行为 2”（读某个文件失败：作废、提示哪个文件）；“设计/页面”collectFolder（“数目与大小在收集时累计，过限立即停”）。
- 问题：(a) 页面用 fetch(PUT, body: File) 上传时，文件在拖入后被改写，fetch 只给一个笼统的 TypeError（Failed to fetch），与服务端断开、连接被拒同一个样子，页面知道是哪个 PUT 失败，却说不出“读不了”还是“连不上”。(b) 遍历只按文件数与大小停：目录里一个指向上层的目录链接、链接所在层没有别的文件时，每一层都是 0 个文件，计数不涨，递归一直往下。r1 第 12 条建议的深度上限没有采纳，处理表也没说理由。
- 触发：(a) 作者开着 build --watch 时拖入 dist；(b) 少见的目录结构。
- 改法：(a) PUT 失败时对该文件做一次 `await file.slice(0, 1).arrayBuffer()`，抛 NotReadableError 就按“读不了 <路径>”提示，否则按网络或服务端失败提示；(b) 收集时按相对路径长度（与服务端同一个 1024 字节上限）或深度（例如 32 层）即时停，复用第 5 条的共享规则。
- 严重程度：低。

## 13. 上传客户端怎么交给页面没写，Lab 夹具与 dom 测试只能去替换全局 fetch
- 位置：计划“设计/页面”第 2 条（插件页 upload.ts）、“配套”；packages/neuro-book/src/plugins/plugins/web/plugin.ts 的 withRegistry（页面现在经 props 拿 registry、locale、windowPlugins）。
- 问题：r1 第 16 条提到“页面还要一个可注入的上传客户端，夹具要给替身”，r2 只写了“夹具的新 props 与状态”。如果 upload.ts 在页面里直接调 fetch，Lab 场景（上传进度、读失败、超限、上传失效）要靠替换全局 fetch 才画得出来，dom 测试也一样，替身与真实路由的失败体对不上契约时测不出来。
- 触发：实施切片 3 的 Lab 夹具与 dom 测试时。
- 改法：定义一个窄接口（create、put、seal、discard，失败按 {code, detail} 与宿主的 {error:{code}} 两种形状归一），由浏览器入口建好、经 withRegistry 作为 prop 传给页面；夹具与 dom 测试给假实现，真实实现由切片 2 的路由测试与切片 4 的 e2e 覆盖。
- 严重程度：低。

## 14. 同时存在的上传个数没有上限；清扫计时器的归属与时钟没写
- 位置：计划“行为 4、5”“设计/服务端”（sweep(now)、clear()、“由宿主与 pluginInventoryKey 一起建”）；packages/neuro-book/src/server/start.ts:206-218（宿主能力按 create 惰性建立）；packages/nb-runtime/src/application/contracts.ts:55-56（能力有 create 与 release）。
- 问题：(a) 每个上传至多 256 MiB，但能同时存在多少个上传没有限制，页面的循环 bug、多个标签页反复拖入都能在 1 小时清扫之前把磁盘写满。(b) 宿主能力是在第一次被解析时才 create（插件页第一次调用时），计划说的“启动时清空”实际发生在那时；1 小时清扫要一个计时器，谁启动、在 release 里停掉、用不用注入的时钟（clockKey）都没写，测试“过期清扫”若要等真实时间就违反仓库的测试规则。
- 触发：(a) 少见；(b) 实施切片 2 时。
- 改法：(a) 限制同时存在的上传（例如 4 个，或所有上传合计 1 GiB），超出时 POST /uploads 回 413 upload-too-large 或 409；(b) 计划写明：清空与计时器都在能力的 create 里做、release 里停，sweep 用注入的 now，测试直接调 sweep(now)。
- 严重程度：低。
