# w00046 t13 设计审查第 3 轮（Claude Opus，只读）
审查对象：.agents/works/w00046-desktop-release/tasks/t13-tray/plan.md（r3）；对照 r2 的 17 条与处理、windows.ts、shell.ts、desktop-settings.ts、desktop/src/bun/index.ts、desktop-bridge.ts、desktop-shell.md、Electrobun 2.0.6 源码。拆出去的“缺省模式的后台选择”不算缺陷。

## 1. 应改：强制关闭按哪个原因提交，计划里有两种读法；照“提交按这次询问的原因”实现，模式 quit 下会进入没有图标的后台
- 位置：plan.md 77 行（强制关闭“按上表”）、111 行（“提交按这次询问的原因（quit 才停）”）、119 行（窗口都关完：最后一个以 window 提交、自有、不在停止 → 留在后台）；54 行（后台只在模式 tray 且图标显示着时进入）。
- 问题：页面同意时有“重算、变成 quit 就重问”兜底，所以提交时询问原因与 #reasonFor 一致；强制关闭没有重问的机会（页面卡死），两者可能不一致。例：模式 quit、自有，窗口 A、B。用户关 A（B 还在，以 window 问），A 的页面卡死、弹“没有响应”；这期间用户关 B，B 以 window 问并同意（A 不在关闭中，B 不是最后一个）、关掉。现在 A 是最后一个，用户点“强制关闭”。按 111 行的“提交按这次询问的原因”是 window 提交，窗口都关完时按 119 行（只看“以 window 提交、自有、不在停止”，不看模式与托盘）留在后台：模式 quit，托盘不显示，服务端带着工作在跑，用户看不到任何东西，只能从开始菜单再打开才发现。现有代码是 `#commit(id, this.#isLast(id))`，这里会停止。按 77 行“按上表”则是 quit、停止。两种读法实现者只能猜。
- 依据：windows.ts:192-205（强制关闭）、178-190（同意时的重问）、207-215（全关）；plan.md 54、77、111、119。
- 建议：(a) 写明强制关闭的提交：这次询问是 quit，或此刻 #reasonFor 为 quit，就以 quit 提交（停止）；否则 window。(b) 全关的后台分支改为在 `closed` 那一刻判断“不在停止、#appQuit 为假、自有、模式 tray 且 trayShown()”，否则 onAllClosed（它同样会停自有服务端）。quit 提交本来就让 #stopping 为真，所以“最后一个以 window 提交”这份记录可以不要，也顺带守住 54 行的不变量（提交到 closed 之间模式或托盘变化的情形）。windows.test.ts 补“模式 quit、两个窗口、先关的卡死，另一个关掉后强制关闭 → 停止”。

## 2. 应改：托盘退出的“对话框”阶段没有作废规则，壳发起的几种停止也没点名经协调器进入停止中
- 位置：plan.md 62-65 行（取工作、对话框、取回时已有窗口作废）、58 行（取工作时点“打开”作废）、61 行（服务端已退出时直接退出）、125 行（判断都在壳里）、132 行。
- 问题：
  - (a) 作废只写在“取工作”这一段（58、65 行）。对话框开着时用户点托盘“打开”、对话框里的“打开 NeuroBook”之外的开窗（开始菜单再打开），之后又在这个还开着的对话框里点“仍然退出”：照字面是“停止、退出”，刚开出的窗口不经询问就失去服务端。对话框开着时再点托盘“退出”、直接关掉对话框（X）算什么也没写；现有 `openDialog` 按 key 去重、关掉走 `onDismiss`，两个已有对话框把它分别当“继续等待”“稍后”。
  - (b) “取到没有工作”“仍然退出”“服务端已退出时直接退出”三处都是壳自己决定停止，计划没说经哪个入口。若直接调 `#stopAndExit`：协调器的 #stopping 仍为假，停止最长 90 秒里开窗转交照样开窗（openWindowRequested 只看协调器的 #stopping、#lastClose），窗口开出来随即随进程消失；服务端意外退出的对话框此时被关掉会走“稍后” → `serverAbandoned()` → 计划新加的“没有窗口时调 onAllClosed” → `#allClosed` 只看协调器的 stopping，会再跑一遍停止与放锁。
- 依据：windows.ts:114-118、142-144；shell.ts:412-422、438-454；desktop/src/bun/index.ts:426-452、502-510；plan.md 58、61-65、121、125。
- 建议：这三处一律调协调器的 `quitRequested()`（计划 87 行已定：没有窗口时直接停止，经 #stopping 与 onQuit），不另开停止入口；有窗口时它就是应用级退出，会逐个询问，不会误杀新窗口。对话框阶段与取工作阶段同一条规则：期间开出了窗口就关掉对话框、作废这次退出（或者保留对话框，但“仍然退出”照样只调 `quitRequested()`，二选一写明）；对话框开着时再点“退出”只把它置前；关掉对话框算“取消”。切片 4 的测试补“对话框开着时开窗再点仍然退出 → 不停止或改为询问”。

## 3. 可选：适配层的 setTray 每次都“setMenu 并注册点击”，监听会累积；更新提示文字的调用没写
- 位置：plan.md 144-149 行。
- 问题：setTray 在 trayView 任一输入变化时都会调（窗口数、取工作中都会变），146 行写的是“有对象时 setMenu 并按自己的 id 注册点击”。`Tray.on` 每次都 `electrobunEventEmitter.on("tray-clicked-<id>", handler)` 追加，没有去重或解绑，几次开关窗之后一次点击派发 N 次。按 r3 的规则重复派发目前碰巧无害（第二次“打开”变成置前、第二次“退出”被“正在取时不理”或“已在询问”吃掉），但这是靠巧合。另外提示文字要靠 `setTitle`（Windows 上改 `szTip` 再 NIM_MODIFY），计划没点名。构造失败后“告诉壳没显示出来”也没说壳拿它做什么：它不能是 trayView 的输入（否则 setTray → 失败 → 重算 → setTray 会同步循环），trayShown 已经直接读对象在不在。
- 依据：Electrobun src/sdks/main/core/Tray.ts:44-47、85-89、110-113；native/win/nativeWrapper.cpp:14855-14871；plan.md 131、144-149。
- 建议：新建成功（id 非 0）后立刻 setMenu、注册一次点击；已有对象时只在提示文字变了时 `setTitle`。构造失败只记诊断，不回报给 trayView，下次输入变化时自然重试。

## 4. 可选：trayView 的 `owned` 取哪个值没写；取成“壳此刻有服务端进程”时，服务端意外退出期间图标会消失
- 位置：plan.md 48 行（壳有自有服务端时显示）、61 行（服务端已意外退出、对话框开着时托盘退出直接退出）、92-94 行、131 行。
- 问题：壳里有两个像“自有”的值：协调器的 `#ownsServer`（serverReady 置真，选“稍后”才置假）和壳的 `#server`（意外退出一开始就置 null，重新启动失败后也是 null）。trayView 若用 `#server !== null`，后台时服务端一退出图标就没了，61 行“对话框开着时点托盘退出”这条路走不到，用户只剩一个对话框；重新启动成功后图标再新建一次。若用 `#ownsServer` 则与 61、92-94 行一致。
- 依据：windows.ts:86-87、129-144；shell.ts:412-435；plan.md 48、61、92-94、131。
- 建议：写明 `owned` 是“serverReady 时自有、还没选‘稍后’”（与协调器的 #ownsServer 同义），壳在 serverReady、serverAbandoned 时更新它并重算。收益不大，一句话的事。

## r2 的 17 条在 r3 里的核对（逐条一句）
1. 重问与提交：原因统一由 #reasonFor 定，同意时重算、变 quit 才重问，提交按询问原因。解决（强制关闭那一支见本轮第 1 条）。

4. #appQuit 被新窗口继承：应用级退出进行中开窗转交回 closing、页面新窗口被拒、托盘打开不开（82、115 行）。解决。

6. background 被改判时页面收口：随拆出消失。
7. Tray 构造失败后 id、菜单不重建：显示就 new、隐藏就 remove、不用 setVisible，id 为 0 丢掉对象。解决（注册点击的时机见本轮第 3 条）。

11. 停止中“正在退出”只在模式 tray 成立：停止中图标一律消失。解决。
12. 取不到时永不结束：随拆出消失。
