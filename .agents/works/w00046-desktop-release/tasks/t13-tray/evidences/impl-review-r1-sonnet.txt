F1 [中] “有工作在跑”对话框的缺省按钮只在颜色上是“取消”，键盘上不是缺省
位置：packages/neuro-book/desktop/src/views/shell/index.html:60-72（show 里只有 index===0 加 primary 类）、:87
问题：Spec（desktop-shell 输出 30）写“取消（缺省）”。页面里“缺省”只是蓝色底，没有 autofocus、没有 focus()，也没有处理 Esc。窗口刚开时焦点在 body：按 Enter 什么都不发生，要先 Tab；Tab 第一下才落到“取消”。这是破坏性确认（“仍然退出”会中断在跑的工作），原生对话框的惯例是 Enter 即缺省、Esc 即取消。同页已有的“没有响应”等对话框做法相同，所以不是本次引入，但这是第一个把“缺省按钮”写进合同的对话框。
触发场景：托盘“退出”后弹出对话框，用户直接按 Enter 或 Esc，对话框没反应（只有点右上 X 才等于“取消”）。
建议：show 渲染完后对 index===0 的按钮调 focus()（所有对话框都受益，焦点环是系统缺省样式）；Esc 可选：keydown 监听 Escape 时若 actions 含 stay 就点 stay。只给本对话框加也行（在 show 里按 actions[0] 是 stay 判断）。
验证：从代码推断，未在 Windows 上实测。
F2 [低] 高对比度（forced-colors）下“缺省按钮”的区分消失
位置：packages/neuro-book/desktop/src/views/shell/index.html:22（button.primary）、:31（forced-colors 只处理了窗口按钮）
问题：高对比度模式下浏览器把按钮背景、边框、文字都换成系统色，button.primary 的蓝底与白字被覆盖，三个按钮外观完全一样；页面里表示“取消是缺省”的唯一信号就没了。按钮本身仍可聚焦、可点，所以可用，只是看不出缺省。
触发场景：开启 Windows 高对比度主题时打开“有工作在跑”对话框。
建议：在 forced-colors 的媒体查询里补 `button.primary { border-width: 2px; font-weight: 600; }`（边框色系统会换成 ButtonText，粗细仍保留），并配合 F1 的 focus() 让缺省按钮至少有焦点环。
F3 [低] “计数”与“无法确认”两行同时出现时语义自相矛盾；只有“无法确认”时标题又断言“有工作在跑”
位置：packages/neuro-book/desktop/src/views/shell/index.html:87
问题：count>0 且 uncertain 为真（取到了一部分、另有取不到的）时正文是“有 2 项工作在跑。”紧跟“无法确认是否有工作在跑。”，后一句在前一句已确定有工作的前提下读不通，应该是“还有一部分无法确认”。count==0 且 uncertain（整个取不到）时标题“NeuroBook 有工作在跑，退出会中断它们”是断言，正文又说“无法确认是否有工作在跑”，两句互相打架。两种组合都是 Spec 字面允许的（“有工作时写出项数、取不到时写‘无法确认是否有工作在跑’”），实现照字面做了，没有违约；问题出在 Spec 措辞没考虑组合。
触发场景：服务端的在跑工作接口返回 failed 非空，或超时 8 秒、连不上。
建议：不改标题（Spec 定的），只改页面里组合时的第二行：count>0 && uncertain 时写“另有部分工作无法确认。”，count==0 && uncertain 时保留原句；顺手把 Spec 输出 30 这一句补成两种情形各写一次。若觉得收益小也可以只记为已知文案限制，不动。

F6 [低] 更新提示的文字在发出时定，之后改设置不改写（README 已记为一致的取舍；这里补两个边角）
位置：packages/neuro-book/desktop/src/bun/index.ts:497（tray: tray !== null）、packages/neuro-book/src/web/host/desktop-updates.ts:133-135
问题：1) 文字看的是“发这一条的那一刻托盘图标在不在”。用户在“下次打开时安装”的通知发出后把设置改成 tray（或反过来），通知里的文字就错了，而 downloaded 提示是非常驻的、会留在通知中心。README 说明了“两种做法一样”，我同意不值得加机制。2) tray 字段由适配层的 `tray !== null` 现算，适配层没有单元测试，核心的 windows.test 只测 sendHint 被调用、没有断言 tray；desktop-bridge.test 里 update-hint 的形状测试也没有带 tray 的用例，所以“字段缺省当假”“tray 为非布尔值时整条被丢弃”都没有断言。后者对页面是静默丢提示。
触发场景：开了托盘模式后下载更新，再切回退出模式；或壳误发 tray: "yes"（不会发生，壳只发布尔）。
建议：不改机制。若补测试，在 desktop-bridge.test.ts 现有 update-hint 那条（:42-46）加一个 `tray: true` 通过、`tray: "yes"` 被拒的断言，成本一行。
