[4] 重要 | 状态切换 / 悬挂 | 计划“浏览器宿主”第 51–56 行、“编辑器”第 72–73 行
现象：计划把窗口状态当作一次性输入（“窗口 ready 时按登记顺序调参与方”），询问进行中状态变化没有处理。真实路径：`window.ts:215-227` 链路 `onState` 转入 `server-restarted / project-gone / incompatible` 时先 `rescue.collect()`、设状态，再 `host.destroy()` 停全部插件；`PageOutlet.vue` 立刻把页面换成 `FailurePage`，EditorHost 随之卸载。此时若编辑器的 `windowDialog` 正开着，或 `closeWindow` 正在等保存：(1) 计划第 73 行只在 `signal` abort 时收对话框；插件停止走的是 `area.dispose()`（`area.ts:1034-1036` 只对旧的 `dialog` 调 `answerDialog?.("cancel")`），新加的 `windowDialog` 的 resolve 若不在 dispose 里一并结算，参与方的 Promise 永远不 settle，控制器永远停在这一步；(2) 控制器没有订阅状态变化，不会改走“失败页带 rescued → 确认丢失”那一支。结果：用户面对一个“正在关闭”层盖在失败页上，没有任何对话框；失败页上正是需要“复制正文”的时候，层又把它挡住。能走出来只有再点一次 X（壳的已接下分支弹“没有响应”→取消或强制）。
如何核实：`area.ts` dispose 与 `PageOutlet.vue` 的 v-if；窗口合同测试里有“服务端换进程”的用例，可以在询问中途触发。
建议：控制器订阅 `browserWindow.onChange`：状态离开 `ready` 时 abort 当前参与方的 signal 并从“失败页”一支重新评估（不是整次取消）；编辑器 `dispose` 里结算 `windowDialog`/失败说明的 pending 为 `deny`（控制器此时已因状态变化放弃它的结果）；验收映射补一条“询问中途服务端重启”。

[10] 建议 | 边界 / 恢复 | 计划“浏览器宿主”第 56 行（“以 allow 结束时层保留到窗口关掉”）；`src/desktop/windows.ts:142,174`
现象：(a) 以 `allow` 回答后层永远保留，页面完全冻结。若壳没有真正关掉窗口（`commitClose` 的 `win.close()` 失败、关闭被系统拦下），用户再点 X：`closeRequested` 在 `state.closing` 为真时直接返回（`windows.ts:97`），`state.ask` 也已经 `#endAsk` 掉，没有“没有响应”对话框，没有任何出口。概率低，但后果是整个窗口死掉、里面还有未保存的正文。(b) 同一路径的另一半：`window` 原因的 `allow` 之后若别的窗口先关了，壳以 `quit` 重新询问（`windows.ts:142-146`，不发 `close-end`）：控制器要能在“已 allow、层保留”的状态下接新询问，并重新调用参与方，编辑器会第二次弹窗问同一批文件（用户刚选过“不保存”）。这是 Spec 输出 16 的设计，但计划应写明控制器的状态机允许“allow 之后的新询问”，并在验收里覆盖；也可让编辑器参与方记住“同一批未改动的文档刚被同意过”，第二次直接 allow（需 Spec 同意）。
建议：allow 之后给层一个保险超时（例如 5 秒内窗口没有关掉就撤层并写诊断，页面恢复可用；此时仍有“同意之后不再有新的修改”的假设被破坏，但比死窗口好）；或只在 `closing` 状态下保留而超时后让用户能再点 X 触发壳的对话框——这需要壳侧配合（t08 的 `closeRequested` 在 closing 状态忽略），所以首选页面侧的保险超时。

[10 更正] 行号：`closeRequested` 对 `state.closing` 的提前返回在 `windows.ts:118`（上条写的 97 有误）；`quit` 重问在 `windows.ts:142-146`。

[11] 建议 | 遗漏 / 失败模式 | 计划“浏览器宿主”第 52–54、58 行
现象：(a) `Connection.work(signal)` 与等待参与方都没有时限也没有可见出口。服务端半死（TCP 通、不回包）时，“正在关闭”层上没有任何对话框，用户只能再点 X 靠壳的“没有响应”对话框取消。Spec 说“取不到（连接断开、服务端出错）”要提示“无法确认”，但“挂住”不在其中。建议给 `fetchWork` 一个固定时限（如 5 秒，与服务端取项目工作的 5 秒错开，留 3 秒余量不如 8 秒），超时按“取不到”走；层上给一条状态文字与“取消”（页面自己回答 `deny`，不需要壳）。(b) “participant-failed”选“仍然关闭”后，是继续调用后面的参与方还是直接进入后面各步，计划与 Spec 输出 10 都没写；若继续，后面的参与方若又抛错会再问一次，要说明。(c) 步骤 2（`rescued-lost`）按 `state.rescued` 的条数提示，但失败页上 rescued 来自抢救时刻的快照，条数 0 时 `rescued` 字段不存在（`window.ts:226`），计划写“带 rescued 时”是对的；但 Spec 写的是“列出未保存的正文”的提示，计划的 `{kind: "rescued-lost", count}` 只给条数，用户看不到是哪些文件，可以复用 `RescuedText.path`。(d) 多个窗口：每个窗口各自的控制器各自取工作；`quit` 仅最后一个窗口发，不会重复提示，没问题（desktop-shell 输出 16）。

[12] 建议 | 重复 / 隐含耦合 | 计划第 24 行、“编辑器”`plugin.ts` 的 `beforeunload`（约 200）
现象：`plugin.ts` 现有的 `beforeunload` 在 `needsLeaveConfirm()` 为真时 `preventDefault`。桌面壳路径里原生窗口关闭不触发它（Spec 输出 9 的前提），但这个前提在 macOS、Linux 与 WebView2 上都未验证（计划“未验证边界”也只列了 macOS 与 Linux）。用户在对话框里选“不保存”→ `allow` → 壳 `win.close()` 之后，如果某个 WebView 仍然触发页面卸载与 `beforeunload`，现有监听会请求离开确认，可能出现原生“离开此页？”对话框、或把关窗挡住，与已经确认过的一次询问重复。计划没有让两条路径互相知道。
建议：编辑器参与方在回答 `allow` 的同一刻置一个“关闭已同意”标记，`beforeUnload` 看到它就不拦；`deny`、`signal` abort 时复位。同时在 Windows 联合验收（切片 6）里记录 `allow` 之后是否有 beforeunload 触发。

[13] 建议 | 重复定义 | 计划“页面与壳之间的桥”第 43 行、“浏览器宿主”第 48 行
现象：`CloseReason = "window" | "quit"` 已定义在 `src/desktop/windows.ts:18`；计划再在 `desktop-bridge.ts` 与 `shared/host.ts` 各写一份字面量联合，正好是第 22 行想避免的“各写一份”。同时 `desktop/src/bun/index.ts` 里页面到壳的消息仍由它自己的 `parse` 与 `typeof` 检查接，计划的 `parseShellMessage` 只管壳到页面一个方向，两个方向的形状各校验一次且不在同一个模块里；t08 的评审（design-review-r1-omp.txt）已指出同页脚本可伪造这些消息，此处不重复，但共用模块应让双向的形状与校验放一起、由两端的测试共享同一份夹具。
建议：`desktop-bridge.ts` 导出 `CloseReason`，`windows.ts` 与 `host.ts` 引用它；页面到壳的 `parsePageMessage` 也放进这个模块，由 `desktop/src/bun/index.ts` 使用。注意 `src/shared` 受 `architecture.test.ts` 约束，按检查结果调整位置。

[11 更正] (a) 的时限数字写乱了：建议 `fetchWork` 固定时限取 8 秒左右（服务端取项目工作自己的上限是计划里的 5 秒，页面时限要比它长，才能收到服务端汇总的 `failed`），超时按“取不到”走。

未发现问题的方面（仔细检查后）：
- 自动保存“保存后重查”不会死循环：计划只重查一次，`savesOnClose` 排除被闸住（保存失败过）、冲突、未裁决、写不出的文档（`auto-save.ts:69,163`），它们由 `needsSettle` 找出后询问，不会漏。
- 通知视口 `WorkbenchNotifications` 渲染在页面根内（不 Teleport），`inert` 能盖住弹出的通知；nb-ui 对话框缺省 Teleport 到 body，工作台没有调用 `provideTeleportTarget`（只有 Lab 用），所以对话框确实在 inert 的 `#app` 之外。
- 消息形状与壳一侧对得上：`close-ack`/`close-answer` 带数字 `generation`，`index.ts:158-162` 的校验与计划一致，壳的 `parse` 接受对象 detail，e2e 假壳传对象与 preload 的 `send` 一致。
- `mount.ts` 的 HostPage→PageOutlet 重新挂载都在同一个 `container` 上，`inert` 设在 container 元素上不受重挂影响（前提是计划明写设在 `#app` container 上，目前写的是“其它挂载根”，见 [2]）。
- 编辑器以可选依赖解析 `windowCloseKey` 的写法与既有的 `windowRescueKey` 一致。
