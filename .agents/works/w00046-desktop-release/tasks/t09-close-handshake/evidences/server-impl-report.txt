== 与计划不同的地方 ==
1. collect() 还把“报告方交回的不是工作项列表”当作失败。计划只写了抛错。理由：形状不对的项会让整条应答过不了页面的 TypeBox 校验，结果是所有工作都看不到。
2. 标题缓存按会话 id 存，计划写的是按根 id 存。哪个会话是根由关系表决定，按 id 存就不必在关系变化时搬动；查询时用根 id 去取。每条只是一个短字符串。
3. 句柄表的新查询叫 activityWithBackground()（计划没有定名）。
4. 诊断事件名是自己定的：project.work.unavailable（warn）和 project.work.late（debug）。
5. 项目项的 project 字段用项目 id（registry 的 id），不用项目名。

== 没把握的点 ==
1. 发送失败一支（send-failed）只靠读代码确认，测试没有确定地走到。实验结论：对已 SIGKILL、但退出还没处理的子进程，proc.send 不抛错；await proc.exited 之后才抛 ERR_IPC_CHANNEL_CLOSED，而那时退出回调已先把子进程标为断开。所以“两个项目一坏一好”那条接受 disconnected 或 send-failed 两种原因。
2. 标题会话（SESSION_TITLE_PROFILE 的后台会话）没有 caller，自己就是根。tiny 角色绑定了模型时，它运行的那几秒会多报一项“未命名的 Agent 会话正在运行”。Spec 要求后台会话也算，所以照报。要不要把它归到它命名的那个会话，或者干脆不报，请主会话定。
3. 标题缓存只在 titleChanged 经打开着的会话写下时更新。外部进程直接改会话日志的情况不考虑：会话存储有锁，按设计不会发生。
4. 测试只覆盖了“改标题后立即查询”时 onLog 在 setTitle 交回之前已经触发这一种时序。这是现在内核的行为，测试依赖它。
5. 两个插件都把 runningWorkKey 设成必需依赖。所有装这两个插件的环境都必须提供这个能力，服务端、两个测试场地都已提供。将来有别的测试场地单独装 agent 或 tasks 的服务端入口时，也要装上这个能力，否则入口激活失败。
