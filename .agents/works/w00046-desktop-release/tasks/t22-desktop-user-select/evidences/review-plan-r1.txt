[6] 重要 ProseMirror 里 contenteditable=false 的节点：实验证实桌面全局 none 下选不了，.nb-markdown 的 text 是必须的，且要进 e2e
实验（/tmp/t22-sel/exp2.mjs，Chromium 无头）：html{user-select:none} 下，contenteditable 根自己用 auto 时，根内 contenteditable=false 的 span/div 里的字双击得到空、Ctrl+A 与拖选都不含它们；只读兄弟节点 <p> 同样选不了。根上写 user-select:text 后，这些岛里的字能双击选中、拖选包含。无全局规则时两种写法一致。所以计划里“可编辑元素不用写”只对可编辑文本成立，对 NodeView 的非可编辑岛不成立；计划把 .nb-markdown 写 text 是对的（MarkdownControl.vue:221 的 class 就挂在 contenteditable 根上，MarkdownDisplay.vue:140 是展示器根）。
风险点：计划的 e2e 里没有任何一条点编辑器里的非可编辑节点（图片、html 嵌入、公式、批注标记等）。去掉 .nb-markdown 的 text 后，“只读 Markdown 那条变红”可能没有入口（计划自己写了“没有就记为只由计算值覆盖”），而编辑器里的岛是现成入口。
建议：e2e 里在 Markdown 编辑器内选一个 contenteditable=false 的 NodeView（例如 callout 之外的图片 alt 占位、.nb-html-embed 或任一 [contenteditable=false] 节点），断言 selectAllChildren 后 toString 含它的文字；变异：去掉 .nb-markdown 的 text 应变红。提示词编辑器里的 chip 是有意不可选（chip.css:21,135），不要把它们算进来。

[8] 一般 CSS 语义核对（Chromium 实验，/tmp/t22-sel/exp.mjs、exp3.mjs）：计划的几条论断基本成立，有两处措辞要改
已验证成立：
  a. 祖先 none、后代 text：能起选区、能双击选词（txt、inner 都得到词）；后代 text 里嵌 none 孙节点则孙节点选不了（none2）。
  b. input、contenteditable 在 none 祖先下照常能选能全选（Ctrl+A 在 input 与 contenteditable 内得到全文）。
  c. 焦点在页面、按 Ctrl+A：选区 toString 只含可选文字，none 的框架文字不在内。拖选从 text 区拖过 none 区到另一端：toString 只含可选文字；从 none 区起拖得到空。
  d. :where([role=alert]) 在 nb-ui styles.css 里经 nb-ui/src/tailwind.css:43 进的是 components 层，所以 Tailwind 的 select-none（utilities 层）和组件 scoped（不分层）都盖得过它；这是层序的作用，不是 :where 的特异性（实验里 @layer c 的 :where 规则被 @layer u 的 .u 盖掉，alert2 得到 none）。计划里“:where 不抬优先级”的理由应改为“它在 components 层，低于 utilities 与不分层的规则”。
  e. 带 draggable=true 的元素即使写 text，双击与拖选也选不出字（实验 d2 得 ""）。仓库里 HTML5 draggable 只在 CropEditor 的 img（draggable="false"），布局拖放用的是指针事件，所以不受影响，只是 e2e 里不能拿 draggable 元素做“可选”的正向对照。
需要改措辞：
  f. 计划写“auto 在可编辑元素上算作 contain”：这是规范写法，Chromium 并不实现 contain，只是编辑宿主与 input 照常可选。更要紧的是 getComputedStyle 对 none 祖先下的 contenteditable 与 input 报的是 "none"（实验：ce:none、inp:none，实际能选）。计划的“逐个文本节点算有效 user-select”清点里把它们归为 editable 是对的，但 e2e 若直接断言计算值，遇到编辑区要排除。
  g. Range.toString 不看 user-select（含 none 文字），Selection.toString 才看；e2e 必须用 Selection（见下一条）。

[9] 重要 e2e “双击后选区为空”的反向断言容易空过；改用 selectAllChildren 加 Selection.toString，并要求变异前先在未改代码上看到红
问题：计划对“框架文字不可选”用的是双击后 getSelection().toString() 为空。空选区还可能来自：点到的不是文字（flex 容器中心、图标旁空白）、指针处理改了默认行为（标签、面板头走 nb-layout 的指针手势，drag-session.ts 里有多处 preventDefault）、被拖拽元素吞掉（实验 d2：draggable 元素双击得 ""）。这些在“补 select-none 之前”也为空，测试就空过了。
依据：e2e 计划（plan.md:63-64）；实验 exp3：Selection.toString 排除 none 文字而 Range.toString 不排除。
建议：
  1) 断言改成一次性的：page.evaluate 里 getSelection().selectAllChildren(document.body)（或按区域 selectAllChildren(区域根)），读 toString()，断言“含内容文案、不含框架文案”。同一次读数里内容文案的出现就是正向对照，不依赖指针落点、不依赖双击；框架文案用清点里的真实字符串（「欢迎」「资源管理器」「搜索命令」「外观」「没有会话」……）。
  2) 对“是否不可选”另加计算值断言作为快速线（none 的框架元素 getComputedStyle.userSelect==='none'；编辑区除外，见 [8f]）。
  3) 浏览器模式那一片（slice 2）必须先在未改代码的 worktree 上跑一遍确认变红（“补 select-none 之前，这些文字可选”），再改再变绿；计划的变异只列了全局规则与 .nb-markdown 两条，slice 2 的十几处 select-none 与 role=alert 规则没有任何变异，可能整片空过。
  4) 保留 1～2 条真实指针的行为用例（双击内容词得到该词、拖选），覆盖“起选区这件事本身”；这类正向用例落点要取文字元素的 getClientRects()[0] 内部，不取包围盒中心。

[12] 一般 Monaco 的双击断言判不出这次改动的风险；Monaco 自己的 hover 与小部件不用管
