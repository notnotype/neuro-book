重点核对：apply 返回 exiting 与 before-quit（未另列有效发现）：
- 源码 Updater.ts:2439 在任务已成功创建/配置/run 后 emitStatus(launching-new-version)，2440 同步调用 quitAfterApproval；Utils.ts:169-188 消费同一批准，不重新走 before-quit；core/main.zig:4335-4354 会停止原生循环、等待清理，再 force_exit。Windows 正常成功路径通常在 apply 的 Promise resolve/适配层读“最后一项”之前就结束进程，所以 exiting 不是原生“新版本已启动”的凭证；它至多表示本进程已武装交接。计划 86 不继续取桌面锁、只等退出，与此名义路径相符。
- 被否决时 Updater.ts:2398-2401 发 idle 并返回；prepared 无效时2355-2359 发 error；本地已是同 hash 时2361-2365 发 no-update；任务或 quitAfterApproval 抛错会到2454-2456发 error。按本次调用的最后状态做同步失败分流有源码依据，不能把通用 error 回调映成换上结果。
- 仍须实现为捕获本次调用范围内状态、捕获 reject/throw，不能无条件取全历史尾项或按英文 message 文案分支；因为 getLocalInfo 会排原生结果对账，history 还会收到 complete/error。按源码当前正常成功区间没有 await 可让对账插进 launching 与 quit 的同步段，未证明历史尾项必然在真实运行时误判，本轮不凑一条竞态发现。Windows 验收尚未执行，不能称真实 exiting 返回已测过。
- r3:101-104 已改成从头注册、pre-lock/applying 可退出、持桌面锁后到 stopped 否决；apply 先于服务端、最终 ports.exit 放行均应保留。核心阶段切换要在拿锁成功的同一续体、服务端拉起前完成，测试211已明确覆盖这个边界。按现有证据未见必须再改回“晚注册”的理由，不重新报告首轮 [14]。

一手参照复核（不新增编号）：
- Microsoft LockFileEx 文档明确共享锁可在同一范围共存、各句柄的独占与共享互斥，锁随句柄关闭/进程退出解除；因此第 [1] 不能用另一个文件上的终身共享锁证明状态 JSON 的事务串行，第 [3] 也不能把等 30 秒当已经获得共享锁。来源：https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex 。本轮 Linux 真实进程探针只验证该机制选择的读改写漏洞，未称 Windows FFI 已实测通过。
- Electron 官方 autoUpdater 文档把 update-downloaded 和 quitAndInstall/before-quit-for-update 分开，不能把“准备交接”当“安装已经成功”；本轮按 Electrobun 固定源码的实际顺序判定，不复用 Electron 的退出顺序。来源：https://github.com/electron/electron/blob/main/docs/api/auto-updater.md 。
- 上轮列的 VS Code state-bound download、取消调度与持久安装校验仍是参照；本轮没有重新读取 VS Code 当前源码，未把上轮行号当最新外部证据。固定版 Electrobun 官方 test-updater-lifecycle 的事实本轮也只沿用既有源文件依据，不把它当我们已执行 Windows 验收。

待确认项判断（plan-r3:187-192）：
1. 下载进度不确定：认可，固定 SDK 的 native prepare 路径不把百分比传回；本轮不重新要求百分比，也不以类型里存在 download-progress 推定该路径会发。
