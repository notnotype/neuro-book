8. **严重程度**：重要；**类别**：不变量；**位置**：`plan-r1.md:73-78`、`docs/standards/repository-workflow.md:28-30`

**现象**：`release:prepare` 被允许在 Work 分支或 master 上运行，预检只要求目录干净；计划没有检查当前提交已包含最新 master，也没有在提交后重新验证 master 未前进。仓库发布规范要求 Work 落后 master 且改到同一批代码时先合 master、解冲突并在合并后验证。

**为什么是问题**：在 Work 分支准备出版本提交后，master 可以继续加入产品代码、版本相关 CHANGELOG 或主题声明提交。此时把 release commit 合入 master 会产生冲突，或在人工解决时丢掉 master 的条目；若直接推标签，版本提交可能不包含当前 master 的发布输入。`registry` 判定和 CHANGELOG 日期也已在旧基线完成，重跑并不能保证原提交仍是要发布的那一批。

**如何核实**：建立 Work 分支与 master 分叉：在 Work 上运行等价的版本/CHANGELOG 修改，在 master 追加同一文件提交，再执行合并或按计划继续；会出现冲突或发布提交不含 master 新提交。检查当前计划步骤没有 `merge-base --is-ancestor origin/master HEAD` 或类似 CAS 复核。

**建议改法**：默认只允许基于已同步的 master 准备，或在开始前 fetch 并拒绝 Work 落后；若支持 Work，要求先合并最新 master、重新跑完整预检，再生成 release commit。提交后到推标签之间记录并核对发布提交的祖先关系，避免用旧分支快照定稿。
9. **严重程度**：重要；**类别**：正确性；**位置**：`plan-r1.md:73-78`

**现象**：`release:prepare` 的顺序是先改产品版本与阶段，再逐个发布单元查询 registry、检查 CHANGELOG 并定稿；计划只写“停下”，没有回滚或事务性写入策略。

**为什么是问题**：任一 registry 查询网络失败、包返回异常、版本与 CHANGELOG 不匹配，都会在一部分文件已改之后退出。下一次运行首先会遇到“发布目录不干净”，而当前版本可能已改、部分 CHANGELOG 可能已定稿、其余仍是 `[Unreleased]`；人工恢复时容易把一个包的定稿日期或版本段带进错误的 release commit。外部 registry 失败不应把本地工作区留在不可解释的半状态。

**如何核实**：在仓库外复制最小夹具，令第 1 个包的 registry 查询成功、第 2 个查询返回网络/权限错误，按计划步骤运行；检查第 1 个包和产品版本已经被写入而命令退出，随后再次运行会被干净检查拒绝。

**建议改法**：先只读收集并校验所有包的 registry 状态、阶段、版本和 CHANGELOG，全部通过后一次性写版本与定稿；或记录原文件字节并在任意异常时恢复，恢复失败也要明确报告恢复边界。提交前再做一次全量解析和 `[Unreleased]` 非空/空状态检查。

## 不做与风险判断

- **英文说明**：接受当前取舍。开发者已明确先只写中文；风险是非中文读者暂时需要自行翻译，不阻断当前发布合同。
- **应用界面显示阶段**：接受当前取舍。阶段已在 GitHub 标题和说明表达，计划明确不改关于页、标题栏；风险是用户在应用内看不到阶段，属于已确认的产品范围。
- **稳定版的 npm 标签与桌面频道**：当前不做可以接受，但第 6 条风险必须进入 ADR 0053 的后续合同；若不定义首个 stable 的版本和频道迁移，风险不是可忽略的后续工作。
