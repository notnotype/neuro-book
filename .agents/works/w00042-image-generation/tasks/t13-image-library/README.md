# 图片库与空间管理

## 目标与范围

这个 Task 负责：
- 生成记录与书里的副本；
- 内容快照与对账；
- 本机图片仓库 `user://images/`；
- 收藏与收藏夹；
- 书里的 `.image` 插图；
- 空间管理（上限、自动清理）；
- 图库页与检索条件（与 t08 的 Agent 检索工具共用）。

依据是提案 [图像生成第一版](../../../../../docs/proposals/image-generation-v1.md) 的第 1、6、7 节与 [ADR 0049](../../../../../docs/adr/0049-image-store-owns-generated-batches.md)。提案接受时把这一块从 t06 分出来（待定项 4）：t06 要等 t02 的后端实测，图片库不依赖后端的细节，可以先做。

合同：新写 `docs/specs/images/library.md`。

## 前置

- **对账：**与 t06 一起定。对账协议是仓库每行带“安装 id 加递增序号”，副本最后的序号就是游标。
- **缩略图的图片处理库：**技术选型在实施计划里做，候选是 sharp 与 WebAssembly 的 jsquash。
- **文件夹类型的渲染贡献点：**规范 `workspace/folder-kinds` 写了，代码里没有，按提案待定项 7 由本 Task 顺带补上。
- **三样平台能力：**记账与变更事件的排除贡献点；服务端代作者写入时带上发起者；仓库记录的追加写法。前两样要和 w00032 t13 一起定，即提案待定项 6。

## 写 Spec 时逐条定的机制

这些来自设计审查第 3 轮，方向写在提案“留给 `images/library` 的机制”一段里：
- 收进书里以后，引用由谁写；
- 仓库记录坏了怎么办；
- 副本在 Git 里被人改了怎么办；
- id 索引存在哪，`image.json` 的几个写者怎么协调；
- 同一张图属于几批；
- 别的机器生成的批次。

三轮审查的报告与处理在 [t03 的证据](../t03-core-contracts/evidences/design-review-round3.md)。

## 写 Spec 前的假设（2026-11-18 列出，待确认）

### 要开发者定的

1. **这一轮写哪些。** 推荐这一轮只写存放与协议：
   - 仓库、记录行与批次的状态、对账；
   - `.image` 与 id 索引；
   - 收藏与收藏夹、扔掉、清理与上限、看过；
   - 检索条件的数据类型，以及给工作台历史、图库页、Agent 检索用的查询。

   图库页与“图片空间”设置页是两块新界面，按 design-review 先出静态稿，定了再追加进 Spec。这一轮只定它们要显示的数据与能做的动作。
2. **平台前置怎么办。** 现状与推荐见下表。

   | 能力 | 提供方 | 现在 | 推荐 |
   |---|---|---|---|
   | 记账排除：排除的目录不记账、不发变更事件 | 改动记账（已转 w00048，未实现） | 只有写死的缺省名单（`.nbook/` 等）；记账还没接进新应用 | 把需求写进 w00048 t01，由它在自己的 Spec 里定。本 Spec 写“仓库目录不进记账”，并链接过去。记账接入之前没有影响 |
   | 服务端代作者写入时带上发起者 | `workspace/resources` 的写入来源 | 来源只有写作者、Agent 会话、系统、外部；服务端插件写书一律记成系统 | 同上，交给 w00048。在那之前，收进书里的写入记成系统 |
   | 追加写 | 写入接口 | 没有 | 不用它：仓库的记录行与原图由插件在服务端直接写文件，照 canon 世界日志“不经文件服务”的做法，并按上一行的排除规则不发变更事件 |
   | 文件夹的渲染贡献点 | `workspace/folder-kinds` 与资源管理器 | Spec 标着已实现，代码里没有（类型写死成三种，资源管理器只有右键菜单一个贡献点） | 照提案待定项 7，由本 Task 补上，改 `workspace/folder-kinds` 的条目，让它与代码对得上 |
   | 缩略图的图片处理库 | 新依赖 | `packages/neuro-book` 里没有 | 实施计划里选 |

   已核实可以直接用的：
   - 服务端经 `projects://` 写书时会先拿租约，项目没在运行就打开它（`workspace/resources` 的“跨项目访问”）；
   - 远程服务有事件，可以推“有新记录”（`runtime/plugin-channel`）；
   - 一个状态根只能有一个服务端（`runtime/cli` 输出 8），仓库只有一个写者。

### 主会话自己定、写进 Spec 的

- **与 `images/generation` 的分工：**记录行的格式与批次的状态归本 Spec。生成在什么时候追加哪一行，归 `images/generation`。
- **钉住**有几种来由：收藏，复制进书期间的临时钉住，以及等审阅的候选。候选那一种标为 planned，随 t10 做。
- **没用到的插图：**第一版不判断。图库里列出书里全部的 `.image`，复制成功、引用写失败时由发起方提示，并给“删掉这张插图”。等 t09 能扫到正文里的引用，再加“没用到”的标记。
- **自动清理的时机：**服务端启动时一次；每一批写完原图后，超过上限就清。
- **作者手动删掉的原图：**启动时与读到它时发现，记一行“原图已清”。
- **导出收藏：**浏览器下载一个 zip，每个收藏夹一个文件夹，每张图配一份来历文件。
- **书里副本的体积：**按重度抽卡（三个月约 1.5 万张）估：
  - 记录每批约 2.5 KB，未压缩时一年几十到一百多 MB。按天分的文件里重复的提示词多，进 Git 后会小很多。
  - 缩略图一年约 600 MB。
  - 不改提案定的记录内容。照提案：记录与快照建议提交，缩略图可选。

### 等 t02 的

- 同一个种子能不能重抽出同一张图：会影响“一张图属于几批”的例子与清理时的补偿说明，规则本身不变。
- 参考图（氛围迁移、精确参考）落进图片库的部分：
  - 从外面导入的参考图存在哪：推荐也存成书里的 `.image`，来历写“导入”；
  - 花了点数的编码缓存在哪。

  先在输出里留出位置，形状等 t02 测完再追加。
- PNG 元数据有哪些字段，原图里的元数据保留到什么程度。
