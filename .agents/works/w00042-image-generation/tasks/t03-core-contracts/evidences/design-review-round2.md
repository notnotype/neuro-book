# 提案设计审查第 2 轮的处理

审查对象是 `ee7675a66` 的修订稿，只审存储：第 1、6、7 节，以及“影响”“待定项”里有关存储的部分。审查者是一个 Opus，说明在 `/tmp/review-w00042-t03-design/r2/brief.md`，报告在 `design-review-r2-opus.txt`。共 14 条：阻断 0、重要 9、建议 5。

## 结论：问题在结构上，不再逐条打补丁

这一轮的发现集中在一处：同一件事由服务端和项目实例两个进程分着写，于是在时序上出缺口（第 1、2、3、4、5、14 条）。逐条补就会出现新的路径。照 reviewing 的规定，把它收成一个关卡：

- **每台机器的仓库是它生成的批次的唯一主人。**书里只存副本，按安装 id 分目录。
- **结果靠对账进书，不设待交付记录。**项目入口在激活时、读历史时、收到服务端的推送时，都会把仓库里属于本书、副本里还没有的记录补进书里，按批次 id 去重。
- **收进书里、清理、收藏都在服务端，用同一把锁。**收进书里时，服务端经文件服务写进 `projects://` 下的这本书。

## 逐条

| 条 | 归类 | 处理 |
|---|---|---|
| 1 扔掉有两个主人 | 成立，改 | 扔掉是仓库的事实，同步进书里的副本 |
| 2 没有哪个进程能完成“收进书里”的复制 | 成立，改 | 由服务端做：先临时钉住原图、核对哈希，再写进 `projects://` |
| 3 记录什么时候写；失败、取消、重启 | 成立，改 | 仓库依次记已提交、完成、失败、取消；服务端重启后，停在已提交的记为中断 |
| 4 待交付记录存在哪 | 成立，改 | 不设待交付记录，仓库自己的记录就是待交付 |
| 5 幂等写入的判据 | 成立，改 | 记录写进生成那天的文件；先写缩略图，再追加记录行；半行照 canon 世界日志的做法处理 |
| 6 判不出哪份是副本 | 成立，改 | 索引记着每个 id 上次所在的路径；没有记录时先不动，等作者打开时问；两台机器各自换新 id 列为已知限制 |
| 7 `user://images/` 对作者与 Agent 敞开 | 成立，改 | 仓库只认文件名等于内容哈希的文件，其它列为“不认识的文件”；收藏照常记账 |
| 8 自动清理前后矛盾 | 成立，改 | 扔掉的不受 7 天保护；能清的都清完了还超上限，才只提示；删去“正在打开的不清”；定义了“看过” |
| 9 快照与缩略图只增不减 | 部分成立，改 | 扔掉的图的缩略图随原图一起清掉；给出体积估计。这条是对“缩略图随书”这一已定决定的后果提出质疑，开发者要知道 |
| 10 与 ADR 0027 矛盾 | 成立，改 | 改成“记账排除贡献点”，见待定项 6 |
| 11 平铺的大目录 | 成立，改 | 按哈希前两位分子目录 |
| 12 别的机器生成的批次 | 成立，改 | 只读；“不在本机”与“原图已清”两种角标分开 |
| 13 用符号链接把仓库挪到别的盘 | 成立，改 | 第一版整个挪状态根；单独给仓库选位置以后再做 |
