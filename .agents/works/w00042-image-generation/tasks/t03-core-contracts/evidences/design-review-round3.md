# 提案设计审查第 3 轮（最后一轮）的处理

审查对象是 `578394397` 的修订稿，只审新的存储结构。审查者是一个 Opus，报告在 `design-review-r3-opus.txt`。共 13 条：阻断 1、重要 5、建议 7。

审查者点名核对、没发现问题的有这几处：
- 项目没在运行时，写 `projects://` 会把它打开；
- 服务端清理时读得到“扔掉”；
- 服务端写 `projects://` 的提交，在项目进程里那把跨进程的锁下进行；
- 别的机器把图收进书里，和本机清不清原图无关；
- 项目 id 不随换机器而变；
- 宽限期里回来时由对账兜住。

新结构本身没有被推翻，剩下的是协议细节与提案里写错的地方。

| 条 | 归类 | 处理 |
|---|---|---|
| 1 按批次 id 去重，但一批有多行（阻断） | 成立，改 | 每行带“安装 id 加递增序号”，按它去重，副本最后的序号就是游标；副本复制全部行，扔掉的图的缩略图在复制到“原图已清”那一行时删掉 |
| 2 对账没有协议 | 成立，改 | 用游标分页；同一本书的对账一次只跑一个；读历史时先给出已有的，补齐后再刷新 |
| 3 仓库里缩略图的寿命 | 成立，改 | 仓库里的缩略图不清 |
| 4 “收进书里”以后由谁写引用 | 成立，列为 Spec 的开放项 | 方向：服务端只复制，引用由发起方写，锁不跨进程的提交 |
| 5 “只缺一样平台能力”不成立 | 成立，改 | 列出三样：记账排除贡献点（含变更事件）、服务端代作者写入时带发起者、追加写或整份重写 |
| 6 安装 id 文件删得掉 | 成立，改 | 从仓库记录行里找回 |
| 7 仓库记录坏了怎么办 | 成立，列为 Spec 的开放项 | 方向：照 canon 世界日志；没有记录行的原图归进“不认识的文件” |
| 8 副本被人在 Git 里改了 | 成立，列为 Spec 的开放项 | 方向：删掉的补回，坏行跳过并写诊断；缩略图不进 Git 的话，别的机器上只有占位 |
| 9 “同时记进书里”，排队中的批次没有记录 | 成立，改 | 入队时记“排队”；第 3 节改成先记进仓库、再经对账进书 |
| 10 id 索引存在哪；`image.json` 有几个写者 | 成立，列为 Spec 的开放项 | 方向：索引存 `.nbook/images/`；`image.json` 一律带期望写入 |
| 11 同一个文件属于几批 | 成立，列为 Spec 的开放项 | 方向：它所属的每一批都允许清时才清；按书列出时算在最早生成它的那本书上 |
| 12 “书里的图”那一行的数据从哪来 | 成立，改 | 图片空间不显示书里的图，免得为了统计去打开每一本书 |
| 13 别的机器的批次不能扔掉 | 成立，列为已知限制 | 写进提案 |

## 结论

照 reviewing 的规定，三轮之后仍有实质问题，交开发者决定，不开第 4 轮。主会话的看法：
- 第 3 轮的发现都在协议这一层，存储结构没再变。
- 阻断与写错的地方已经改了。
- 其余 6 条写进了提案的“留给 `images/library` 的机制”，在写那份 Spec 时逐条定，并另行审查。
