# w00042 t03 设计审查第 2 轮（Opus）：存储架构

### 1. “扔掉”有两个主人；服务端清理要“先清扔掉的”，却只能从书里知道哪些被扔掉
- **严重程度：**重要
- **类别：**与已定设计一致（一件事实一个主人）、跨进程
- **位置：**image-generation-v1.md:87、250、268、294
- **现象：**主人表把“收进书里、扔掉”归书（87 行）；仓库的本机记录又列了“扔掉”（250 行）。清理在服务端做，顺序“先清扔掉的”（294 行），撤销扔掉要“在下一次清理之前”（268 行）。
- **为什么是问题：**
  - 只记在书里：书没运行时，服务端读不到 `.nbook/images/log/`，到上限时不知道哪些是扔掉的。撤销扔掉也只写书，服务端照旧按扔掉删掉。
  - 两边都记：扔掉与撤销各写两处，没有规定先写哪边、哪边失败怎样、对不上时谁为准。
  - 跨机器：机器 B 经 Git 拿到书、扔掉了机器 A 生成的图，这一行写在 B 的日志文件里。A 的仓库什么时候、由谁知道，没写。按现有说法，A 的原图要等它“最久没看过”才清，B 的扔掉对 A 无效。
- **如何核实：**对照 87 行与 250 行；查第 1 节，没有“书里的事实同步给仓库”的通道。
- **建议改法：**二选一写死。
  - 推荐：“扔掉”只归仓库，是本机事实，与“原图已清”同类。书的历史界面从仓库读角标，不往书里追加扔掉行。跨机器的扔掉不传播，写成已知取舍。
  - 或者：书为主人，仓库里的只是缓存。项目入口激活时把本书的扔掉与撤销（含别的安装 id 文件里的）推给服务端，服务端按批次 id 记最后一次的状态。再写明书没打开期间的扔掉与撤销以哪份为准。

### 2. “收进书里”的复制没有可用的执行进程；“照主题素材的互斥”只在服务端一个进程里成立
- **严重程度：**重要
- **类别：**依赖的机制、跨进程、并发
- **位置：**image-generation-v1.md:106、263、300
- **现象：**106 行说“原图经文件服务的写入接口以暂存文件落进作品目录”，263 行说插件动作“先把原图复制进 `.image` 文件夹，再写引用”。两处都没说哪个进程复制。300 行说清理与收进书里互斥，“照主题素材清理与上传互斥的做法”。
- **为什么是问题：**
  - 项目实例的写入接口只管 `project://`，读不到 `user://`。`packages/neuro-book/src/plugins/files/backend/plugin.ts` 的项目入口是 `provideWorkspaceFiles({own: {scheme: "project"...}, registry: null, projects: null...})`；`user://` 由服务端提供（resources.md:34、50）。`workspace/files.md:91` 写着“不跨根搬运”。
  - 主题素材的互斥是服务端进程内、两条路由之间的（theme/editor.md:69“互斥只管上传与清理这两条路由”“一个状态根只有一个服务进程”）。复制要是在项目子进程里做，这把锁管不到。
  - 照字面实现的人很可能在项目实例里拿状态根路径直接读盘。这样既绕过了文件服务，又不在互斥里，清理可以在读到一半时删掉原图。
- **如何核实：**读上述 plugin.ts 第 255–275 行与 resources.md:34、61、135。
- **建议改法：**
  - 写明复制由服务端入口做：在清理互斥里临时钉住原图，校验 SHA-256，再经写入接口 `stage("projects://<项目 id>/…/v1.png")`。这一步取租约、提交到项目子进程，resources.md 场景 11 测过 8 MB。提交结算后再放钉。
  - 项目实例只写 `image.json` 与引用。
  - 互斥写成“服务端入口内的一把锁”，不说“照主题素材”。

### 3. 书里的记录到底在“发出时”还是“交付时”写，前后两种说法；失败、取消与排队中的批次不在待交付里
- **严重程度：**重要
- **类别：**修订引入的矛盾、遗漏（失败路径）
- **位置：**image-generation-v1.md:99–103、186、230–231、278
- **现象：**
  - 186 行：“发出去。同时记进书里：展开后的每一节、配方当时的样子、所引用预设与片段的内容（快照）”。
  - 99–103 行：服务端“拿到结果”后才记待交付，项目入口交付时才“写进书里的记录与缩略图”。
  - 231 行：取消、失败、部分失败都写进生成记录。
  - 230 行：入队用的是当时的配方内容，含没保存的修改。
- **为什么是问题：**
  - 发出时写的话，就是项目实例在提交时写一行，交付时再写一行。这时第 1 节的幂等只覆盖第二行，第一行写了、批次却没交付的情况，书里会留下一条永远“进行中”的批次。
  - 交付时写的话，快照内容（没保存的配方、当时的预设）要随待交付记录从服务端带回。可提案说待交付“带项目 id”，没说带快照。
  - 失败、取消没有“结果”，按 99 行不会进待交付，书里就写不进失败记录。
  - 全局队列与进行中的批次存不存盘没写。服务端重启后，已扣点数、还没写原图的批次无声消失。
- **如何核实：**对照 186 行与 99–103 行；`images/generation` 的验收（370 行）只测“完成的批次进书一次”。
- **建议改法：**
  - 定为“只在交付时写书”。提交时把展开结果与快照内容交给服务端，服务端随批次持久化，作为待交付记录的一部分。
  - 待交付覆盖终态：成功、部分成功、失败、取消都交付一次。
  - 队列与进行中的批次写盘。重启后，已提交给后端的批次按“结果未知”交付，记进书里，不静默丢弃。

### 4. 待交付记录存在哪没写；照拓扑提案放 Storage 会撞上提案自己排除 Storage 的理由；坏了、书移出书架时怎样也没写
- **严重程度：**重要
- **类别：**接口与合同、遗漏
- **位置：**image-generation-v1.md:78、99、104、108
- **现象：**
  - 99 行“再记一条待交付的批次”，没说存在哪。
  - 拓扑提案的例子把 `pending-callbacks` 放在 Storage 的 `user / shared`（multi-instance-runtime-topology.md:308）。
  - 108 行不把安装 id 放 Storage，理由是“共享的 Storage 记录以后要跨设备同步”。
- **为什么是问题：**
  - 服务端入口没有客户端身份，只能开 `shared` 记录（storage/persistence.md:52、153）。照抄拓扑例子，待交付记录以后会被同步到另一台机器，可原图与缩略图只在本机。第 108 行的理由对待交付同样成立，提案却没套用。
  - 坏了怎样：Storage 记录 `corrupt` 只能 `reset`。待交付一丢，书就永远收不到那些批次，也没有重建的路。
  - 104 行说“不会出现孤儿”，但 99 行的顺序是先写原图、再记待交付，两步之间服务端崩了，就会留下没有记录的原图。
  - 书移出书架、从此不再打开时，它的待交付永不退役，也没写由谁处理。
- **如何核实：**读 persistence.md:30、52、153 与拓扑提案 308 行。
- **建议改法：**
  - 不另设待交付存储。仓库的本机记录本来就按图记“来自哪本书哪一批”（250 行），在批次上加“已交付”标记，待交付就是“没交付的批次”。
  - 批次记录与原图同在 `user://images/`，先写记录（状态是“写入中”）再写原图。启动对账时，“写入中”的批次补完或作废。
  - 移出书架的书，待交付在“图片空间”里列出，可以丢弃。

### 5. 幂等写入的判据没定：按哪天的文件查、写到一半被强制结束怎样、缩略图与日志行谁先写
- **严重程度：**重要
- **类别：**跨进程时序、失败路径
- **位置：**image-generation-v1.md:101、108、244
- **现象：**项目入口“按批次 id 幂等写进书里的记录与缩略图，然后确认”（101 行）；日志“只追加，按天加安装 id 分文件”（244 行）。
- **为什么是问题：**
  - **哪一天。**没写批次行落在“生成那天”还是“交付那天”的文件。按交付日写的话，代次 N 在 23:59 写了一行、没来得及确认就停了，代次 N+1 在 00:01 重新交付，查今天的文件找不到它，就写出第二行。runtime/projects.md 第 5、6 条允许这种交替：宽限期满停止、崩溃，下次打开是新代次。
  - **写一半。**停止截止（缺省 20 秒）到了会强制结束子进程。追加一行 JSON 写到一半时，文件末尾留下半行，下一次追加接在它后面，两行一起坏。幂等检查读到坏行，判不出这一批写没写过。
  - **先后。**先写日志行、后写缩略图的话，中途停下，下次按“已有这一行”跳过，缩略图就永远缺了。
  - 两个状态根同时打开同一本书（projects.md:21 允许），各自的安装 id 不同，所以不撞文件，这一点成立。
- **如何核实：**读 projects.md 第 5、6 条与“停止截止”，对照 101 行。
- **建议改法：**写进 `images/library`：
  - 批次行写进“生成那天”（取自待交付）加本安装 id 的文件，幂等只查这一个文件。
  - 先写快照与缩略图（按哈希命名，重写无害），最后追加日志行，日志行作为提交标记。
  - 每行独立成行、开头先补换行；读时丢弃没换行结尾的末行并记诊断。
  - 加一条验收：交付途中强制结束子进程，下次打开只进一次且缩略图齐全。

### 6. “复制出重复 id 时打开副本换新”：哪份是副本判不出；两台机器各自换新会让原 id 整个消失
- **严重程度：**重要
- **类别：**没写出来的假设、跨机器
- **位置：**image-generation-v1.md:265–267、367
- **现象：**索引“能发现重复 id，打开副本时换新 id”；验收写“资源管理器复制出的重复 id 在打开时换新”。
- **为什么是问题：**
  - **副本认不出。**两份文件内容相同。文件管理器 `cp -p` 保留修改时间；Git 检出把所有文件的时间都设成检出时刻。所以“副本”只能按“先被打开的那份”或“路径排序”算。作者先打开原件时，原件拿到新 id，日志里的批次（按配方 id 记，238 行）、正文的 `<image-generated id>`、预设引用就都指向了副本。
  - **`.image` 不“打开”。**插图文件夹在资源管理器里显示、在正文里被引用，没有“打开”这一步，换新的时机不存在。
  - **两台机器。**同一个重复经 Git 同步到 A、B 两台，两边的索引各自给“副本”换新 id。A 换了甲、B 换了乙，合并后两份都是新 id，原 id 没有任何文件持有，所有按 id 的引用一起断。
  - 换 id 要改写文件，在 Git 里是一处修改，作者没做事却出现 diff。
- **如何核实：**按 238、265–266 行推演上面三种情形。
- **建议改法：**
  - 换新只在“插件自己能确定谁是副本”的入口做：插件的复制、资源管理器经文件服务的复制（resources.md 的复制事件带源与目标）。这时目标是副本。
  - 别的来源（文件管理器、Git）出现的重复不自动改写，在工作台与图库页提示，让作者选保留哪份的 id。
  - 解析按 id 的引用时，遇到重复按确定的规则选一份（例如路径最短、再按字典序），并显示警告。

### 7. `user://images/` 对作者与 Agent 敞开，对账只规定了“原图不见了”一种情形；收藏所在的本机记录被删了无从恢复
- **严重程度：**重要
- **类别：**遗漏（边界）、修订引入的新风险
- **位置：**image-generation-v1.md:250、252、253、255、108
- **现象：**252 行只写“挪走或删了文件，下次对账时算作原图已清”。本机记录（收藏、来历、看过的时间、扔掉）与安装 id 文件同在 `user://images/`，又要求整个目录排除在改动记账之外（253 行）。
- **为什么是问题：**
  - **记录文件。**资源管理器对 `user://` 支持删除、改名、移动（files-explorer.md:14、54），只有根本身不能删。作者删掉或挪走本机记录，收藏与“书删了也还在”的来历就没了；目录又不进账本，没有 History 可以撤销。记录坏了（半写、作者手改）怎样也没写。
  - **对账没定义。**什么时候对账（启动、监视事件、每次清理前）没写；记录在、文件不在以外的情形也没写：
    - 作者放进来的文件，或改名成别的哈希名的文件：算不算占用？会不会被清？
    - 原地改了字节（外部编辑器）：名字还是旧哈希，“收进书里”会复制改过的字节，“后端交回的字节不改”（248 行）被悄悄打破。
  - **Agent。**写 `user://` 要审批（resources.md:189），批准后能改、删这里的任何东西，规则同上。
- **如何核实：**files-explorer.md:14、54；resources.md:189；对照 252–253 行。
- **建议改法：**
  - 本机记录用 SQLite（或带版本号的 JSON），放 `user://images/` 下的固定名字。坏了按 Storage 的做法：原件留一份、提示，不覆盖。另把“导出收藏”的来历当备份。
  - 对账写成表：记录在文件缺、文件在记录缺（不认、不计入上限、不删，单独列出）、名字与内容哈希不符（标成“已改动”，不复制进书）、启动时与清理前各做一次。
  - 复制进书与导出前校验哈希。

### 8. 自动清理：“扔掉”与 7 天保护谁先，正文与验收两种说法；“受保护超上限就什么都不删”连扔掉的也不删；“正在打开的批次”没有机制
- **严重程度：**重要
- **类别：**修订引入的矛盾、依赖的机制
- **位置：**image-generation-v1.md:268、294–297、299–300、371
- **现象：**
  - 295 行：最近 7 天生成的不清。
  - 371 行的验收：“只清扔掉的与没收藏、7 天以前的”，可以读成扔掉的不受 7 天保护。
  - 297 行：受保护的部分超过上限时，“什么都不删”。
  - 300 行：“正在打开的批次不清”。
- **为什么是问题：**
  - 两种读法会写出两种实现：刚扔掉的图，一种第二天就可能被清，另一种至少留 7 天。268 行说“在那之前可以撤销”，可撤销的时限依赖这一选择。
  - 照 297 行的字面，7 天内生成量超过上限时（测试里把上限设到很小，或作者调低上限），连 7 天以前、已经扔掉的图也不删，扔掉就永远不腾空间。
  - 清理在服务端，可是“哪些批次正被打开”只在浏览器里。服务端没有登记，窗口崩了也没有释放。浏览器正在显示的原图被删，`<img>` 的地址就成了 404。
  - “看过”的定义仍没写：滚过历史缩略图算不算？读原图的地址由 `nbook.files` 的路由提供（files.md:68–72），图像插件看不到这些请求，只能靠浏览器上报。
- **如何核实：**对照 295 行与 371 行；查 runtime 与 files 的 Spec，没有“浏览器正在看某文件”的登记。
- **建议改法：**
  - 写死顺序：扔掉的（不论是否在 7 天内，或者明确给扔掉另设 1 天保护）→ 7 天以前的、按最久没看过的顺序。297 行改成“清完能清的仍超上限时，只提示”。
  - “正在打开”改成临时钉住：浏览器经远程服务登记批次，登记随连接释放，并带到期时间。这与第 2 条复制时的钉住共用一种状态，t10 的候选也用它。
  - “看过”定义为打开大图或灯箱，由浏览器上报。

### 9. 书里的快照与缩略图只增不减：扔掉的图的缩略图也永远留在书里，体积与提案否掉“好图随书”的理由同一量级
- **严重程度：**建议
- **类别：**遗漏、别扭之处
- **位置：**image-generation-v1.md:88、245、268、284、304、315
- **现象：**快照“按哈希命名、去重”（245 行），没写何时可删。缩略图每张一张、随书（88 行）。扔掉只是“历史里不再显示”（268 行），原图清掉后“缩略图与记录还在”（284 行）。
- **为什么是问题：**
  - 日志只追加、永不删，引用快照的行一直在，所以快照永远不能删。这本身可以接受，但要写明。
  - 缩略图：重度三个月约 150 MB（304 行），一年约 600 MB，一个缩略图一个文件，三个月约 15000 个文件。其中大部分是失败品，扔掉的也留着。315 行否掉“好图随书”的理由是“书多约 0.7 GB”，同一量级的缩略图却照收。同步盘与 Git（“可选”）都要扛这几万个小文件。
  - 第 1 轮第 18 条建议“扔掉同时删缩略图、记录保留一行”，修订稿没采纳，也没写理由。
- **如何核实：**按 304 行的数字乘四；对照 315 行。
- **建议改法：**
  - 写明快照不删（随日志永久保存）。
  - 扔掉的图在清理时连缩略图一起删，记录行保留，历史显示“已扔掉”。这样第 9 条的体积主要来自没扔掉的图。
  - 或者缩略图按批次打包成一个文件（一批一个 WebP 拼图或一个小归档），文件数降到原来的约四分之一。
  - 在“图片空间”里显示每本书 `.nbook/images/` 的体积。

### 10. “不新增宿主能力”“第三方插件同样做得到”与要求平台把 `user://images/` 写进缺省排除名单矛盾
- **严重程度：**建议
- **类别：**与已定设计一致（ADR 0027）、说法与事实不符
- **位置：**image-generation-v1.md:74、253、338、397
- **现象：**74 行：“本稿用到的都是平台公开的能力，第三方插件同样做得到（ADR 0027）”；338 行：“不新增宿主能力”。253 行与待定项 6 却要求 `user://images/` 加进缺省排除名单，`.image` 里的图片只记哈希，插件代作者的写入不进审查收件箱。
- **为什么是问题：**
  - 记账提案的排除是一份固定的缺省清单（`.nbook/`、`.git/`、`node_modules/`、编辑器临时文件），只预告了“以后给用户一个设置”（file-access-and-history.md:135），没有让插件声明自己目录的入口。
  - 把一个插件的私有路径写进 `nbook.files` 或 History 的缺省清单，正是 ADR 0027 要消除的“内置特权”：第三方的图像或音频插件往 `user://<自己>/` 放几十 GB，照同一提案就会被全量记账，没有同等的路。
  - “只记哈希”“代作者写入”同样是对图像插件的特殊处理。
  - 这三样都是新增的宿主能力，338 行的说法不成立，`images/library` 的前置里也缺这一项。
- **如何核实：**读 file-access-and-history.md:135、149 与 ADR 0027 决策 1。
- **建议改法：**
  - 改成平台能力，在待定项 6 里提给 w00032 t13：记账排除做成贡献点（插件声明 `user://` 或项目里的一段路径前缀“只记哈希”或“不记”），图像插件用它声明。
  - 338 行改为“新增一项：记账排除的贡献点”。

### 11. 仓库是一个按哈希平铺的大目录，资源管理器、列出与 Agent 的 glob 都会碰到几万项
- **严重程度：**建议
- **类别：**遗漏（规模）、接口
- **位置：**image-generation-v1.md:248、252、292、304
- **现象：**“按 SHA-256 命名”“资源管理器……看得到 `images/`，里面是按哈希命名的文件”。目录结构没写。
- **为什么是问题：**
  - 40 GB 上限按约 1.5 MB 一张算，约 27000 张原图，加上同数量的缩略图约 54000 个文件。
  - 文件服务的列出一次读完整个目录，没有分页或截断（`packages/neuro-book/src/plugins/files/backend/files-service.ts` 的 `listAt`）。一项约 95 字节的 JSON，2 万多项就超过 2 MiB，而远程消息的单条上限是 1 MiB（`shared/rpc-socket.ts`，服务端收方向由 `server/rpc/listener.ts` 的 `maxPayloadLength` 限制）。发向浏览器这一方向会不会被拒，没验证（从代码推断）。就算发得出去，资源管理器展开时也要排序、渲染几万行。
  - 写原图时，监视的批量事件过多会推“失同步”（resources.md 的“订阅”），开着的资源管理器会整根重新核对。
  - 主题素材是同样的平铺，但量是几十个，不能当作先例。
- **如何核实：**读 files-service.ts 第 104–130 行；按 292、304 行估算文件数。
- **建议改法：**
  - 定下目录布局：`originals/ab/<哈希>.png`、`thumbs/ab/<哈希>.webp`，按前两位分 256 个子目录（Git 对象库的做法），每个目录约 100 到 200 项。本机记录与安装 id 放在根上，名字一眼可读，例如 `README.txt` 说明“别动这里的文件”。
  - 写原图不经文件服务的写入与记账（或用第 10 条的排除），避免每张图一条变更事件。

### 12. 书在另一台机器上打开时，别的安装生成的批次能做什么没写：收藏、收进书里、角标都会碰到“本机没有这条记录”
- **严重程度：**建议
- **类别：**遗漏（边界）
- **位置：**image-generation-v1.md:95、251、263、271
- **现象：**95 行说“原图已清”只记在本机。251 行说本机没有原图时（例如换了机器）用书里的缩略图。271 行的角标有“原图已清”。
- **为什么是问题：**
  - 机器 B 的仓库对机器 A 生成的批次没有任何记录。“原图已清”与“从来不在本机”是两回事，界面要分开显示（前者是作者自己清的，后者可以回 A 去拿）。按现有说法，B 只能把它显示成“已清”，或者什么都不显示。
  - 在 B 上对 A 的图按“收藏”“用作插图”，B 没有原图，第 1 节与第 6 节都没说按钮是否可用、失败时怎么提示。收藏要求“在仓库里钉住”，B 上没有可钉的东西。
  - 同一状态根拷到另一台机器、安装 id 相同时（108 行），B 会把 A 的批次误认作本机生成、原图已清。
- **如何核实：**按 95、251、263 行推演 B 上的三个按钮。
- **建议改法：**
  - 角标分“原图已清（本机）”与“不在本机（来自另一台安装）”，后者按日志行的安装 id 判定。
  - 不在本机的图：收藏、收进书里停用，提示“原图在另一台机器上”。
  - 复制状态根的情形写成已知限制。或者在安装 id 文件里同时记主机名，启动时发现主机名不同就换新 id。

### 13. 40 GB 落在状态根里，没有挪到别的盘的办法：用链接挪走以后读图路由会 404
- **严重程度：**建议
- **类别：**没写出来的假设
- **位置：**image-generation-v1.md:78、247、251、292、314
- **现象：**仓库固定为 `user://images/`，即 `<状态根>/user/images/`。上限缺省 40 GB，提案没提仓库能不能放到别处。
- **为什么是问题：**
  - 状态根通常在主目录下（系统盘），40 GB 是许多笔记本系统盘剩余空间的一大块。作者最自然的做法是把 `images/` 换成指向外置盘或数据盘的符号链接。
  - 文件服务的读与按地址读字节路由，对“经链接到根外”的目标一律 `outside-root`，按地址读的路由回 404（workspace/files.md:72–73、96）。写入接口也按 `outside-root` 拒绝解析后落在根外的目标（resources.md:115）。
  - 所以链接一换，所有原图都读不到，图像插件自己的写入也会失败。主题素材的路由对链接目录直接回 409 `invalid-target`（theme/editor.md:79）。
  - 这是修订时换位置带来的新约束。上一稿“插件私有目录”同样没提，但那时还没有“`user://` 的路由”这一依赖。
- **如何核实：**读 files.md:72–73、96 与 resources.md:115。
- **建议改法：**
  - 至少在提案里写明：仓库只能随整个状态根移动，并在“图片空间”里显示仓库所在的盘与剩余空间。
  - 如果要支持放到别的盘，就把仓库做成插件注册的挂载方案（resources.md 的 `files.schemes`，根可以是任意真实目录）。代价是要第三方注册方案（目前只收内置插件），读字节路由也要扩到挂载方案。交开发者决定。

### 14. 批次在宽限期里完成、作者又在宽限期内回来时，没有任何东西触发交付；同一代次里交付失败也没有重试的触发
- **严重程度：**重要
- **类别：**跨进程时序、依赖的机制
- **位置：**image-generation-v1.md:100–101、104
- **现象：**100 行：项目不在运行或处在宽限期时“不推、不唤醒，等它下次激活”。101 行：项目入口查询待交付。触发只有两个：“激活”与“有可交付结果”的推送。
- **为什么是问题：**
  - 常见情形：点生成、关掉窗口，批次在 5 分钟宽限期内完成，作者在宽限期内回来。按 projects.md 第 7 条与 application.md:68，新租约把同一代次从 `idle-grace` 拉回 `available`。项目入口一直激活着，不会再激活一次。`projectsKey` 只有 `list`、`acquire` 等方法（projects.md 第 8 条），没有状态变化的订阅，服务端也不知道该补推。这批要等下一批生成触发推送，或者项目彻底停掉、重开以后才进书。
  - 启动时的竞态：插件在代次报告“已启动”前激活（projects.md 第 4 条）。项目入口激活时查询为空，之后待交付在项目仍是 `starting` 时记下，服务端按“不在运行”不推，转为 `running` 后也没人推。
  - 同一代次里写书失败或确认结果未知时，101 行没有重试的时机，只能等下一次激活。拓扑提案的例子写“下次激活或重试时”，没说重试由谁触发。
  - 第 4 节撤回：“项目处于宽限期时的推送：没有发现”只核对了不推、不唤醒，没核对之后由谁来取，结论不成立。
- **如何核实：**读 projects.md 第 4、7、8 条与 application.md:67–68 的状态表。
- **建议改法：**
  - 交付改为由项目入口“拉”：窗口绑定项目时（浏览器入口激活），以及收到推送时，都让项目入口查一次。
  - 交付失败或结果未知时，项目入口按退避在同一代次里重试，直到成功或代次结束。
  - 服务端推送时机加“项目从 `starting` 变为 `running` 后补推一次”（需要 `projectsKey` 提供状态变化的订阅），或者靠上一条的“窗口绑定即拉”兜住。
  - `images/generation` 的验收补一条：宽限期内完成、宽限期内回来，书里有这一批。
