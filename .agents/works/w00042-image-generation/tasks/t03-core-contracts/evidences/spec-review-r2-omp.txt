### 1. `null` 同时表示合法字段值与删字段，差异往返仍不成立（首轮第 1 条未完全解决）
- **严重程度：**阻断
- **类别：**正确性
- **位置：**recipes.md:96, 215, 229-232；prompt.md:203
- **现象：**“改”用 `null` 表示删除字段；输出 12 又把 S 中不同字段的原值直接放进 `fields`。项允许保留未知字段，JSON 的 `null` 是合法字段值。
- **为什么是问题：**把一个字段改成 `null` 和删掉它编码成同一条改动，不可能同时满足“套回与 S 逐项相同”。这是自动算差异会生成的反例，不是只针对手写非法差异。
- **如何核实：**P=`{kind:"tag",text:"rain",weight:1,extension:"old"}`；S 只把 `extension` 改为 `null`。输出 12 得到 `fields:{extension:null}`；输出 10 却删掉 `extension`，结果不是 S。已执行最小套回实验，比较结果为 `false`。未知字段属于明确要求原样保留的公开数据。
- **建议改法：**把设值与删除分开表达，例如 `fields` 保留包括 `null` 的全部 JSON 值，另加明确的删字段列表；或为字段改动定义 set/unset 两种形状。补 `null` 与缺字段互换的往返验收。
### 2. 合法的 `raw` 预设没有可计算、可套用的差异（首轮第 1 条未完全解决）
- **严重程度：**阻断
- **类别：**正确性
- **位置：**recipes.md:91-96, 124, 213-232, 327；prompt.md:56-58, 151-156
- **现象：**预设的 `prompt` 允许整个 `Prompt` 联合，其中包括 `{raw:string}`；差异的全部操作却只能定位、增删或修改 `Item`，计算规则也只接受两边的项序列。
- **为什么是问题：**合法的原文预设没有项，编辑它或从快照恢复到另一个原文内容，都没有 Change 可以表示。不能以“原文不可拆”推出“原文不可编辑”；Spec 没禁止这种预设，也没有给它单独的替换动作。
- **如何核实：**P.prompt=`{raw:"A girl wears {red clothes."}`，S=`{raw:"A girl wears {blue clothes."}`。两者都对应 `unparsed-sentence`，且没有随机写法，配方展开允许使用。按输出 12 无法取 P/S 的项或键；即使取空序列，差异为空，套回仍得到红衣，不是蓝衣。恢复时 P 还在又被要求仍引用 P。
- **建议改法：**明确 raw 能否作为预设及参与引用差异；允许就提供整段替换的公开表达及恢复规则，不允许就禁止套用并给出确定失败码、转换路径。不能把这些输入保留为合法文件后让输出 12 无定义。
### 3. 结构化权重相乘超范围时，没有原文可回退，也没有展开失败码（首轮第 6 条未完全解决）
- **严重程度：**重要
- **类别：**正确性
- **位置：**prompt.md:69, 145, 179-192；recipes.md:265-269, 281-315
- **现象：**新增范围只把读文字的溢出退回 `{raw:原文}`。合法的片段引用与随机项还会在拆词、抽签、规范写出时相乘，这些输入可以完全来自 JSON，没有原文。配方的展开失败集合不含权重溢出。
- **为什么是问题：**两个各自合法的 10000 相乘得到 100000000，超上限 10000 达 10000 倍；既不能输出合法 Item，也不能调用不存在的“原文”，更不能按明确列出的失败码拒绝。仅在后端限制参数范围不能补上纯运算和公开展开合同的缺口。
- **如何核实：**片段 F.core 含 `rain@10000`，引用 F 的 weight=10000；或 choice.weight=10000、选项里 rain.weight=10000。JSON 均合规，展开或抽签必须得到 100000000。另有 1.2345×1.2345=1.52399025，要统一规定最终量化时点，不让先拆片段再抽签多次量化。上述十进制乘积已运行核对。
- **建议改法：**为所有产生新权重的运算定义同一结果域、量化时点与失败通道；没有原文的结构化运算明确返回权重失败，并把它纳入 recipes 输出 27。不得虚构原文、截顶或默默降成 0。
### 4. 先过滤停用项仍漏掉预设和片段里尚未取出的项（首轮第 26 条未解决）
- **严重程度：**重要
- **类别：**正确性
- **位置：**recipes.md:91, 158, 213-215, 265-268, 281-284, 309-315；prompt.md:76
- **现象：**输出 25 现在先去停用，再解析引用；但第 1 步时，引用预设的节还没有实际项，片段的核心词和陪衬词也未展开。第 2 步以及差异里的 add/set 会重新带入停用项，后面没有过滤步骤。
- **为什么是问题：**把原来的两步单纯对调不能实现“停用项展开时跳过”。合法停用引用仍会报缺失而阻止生成；普通停用词也会进入没有 `disabled` 字段的 Weighted，无法在后端可靠补救。
- **如何核实：**style 节只含 preset 引用，P.prompt.items 为 rain 和 `{kind:"fragment",ref:"deleted12345",weight:1,disabled:true}`。第 1 步在节里无项可去；第 2 步取出 P，随即解析片段得到 `fragment-missing`，第 27 条要求整批失败。把该项换成停用 tag 或让 fragment.core 含停用 tag，仍没有规定何时去掉。
- **建议改法：**每取得一段实际内容，先过滤这一层停用项，再解析仍活跃的引用；预设必须先套完差异再作这一判断，片段展开和随机选项也遵守同一规则。补“停用缺失引用藏在预设里”和“差异重新启用/停用引用”的组合验收。
### 5. 强制合并重复键改变了已接受提案，不是修复锚点的等价细化
- **严重程度：**重要
- **类别：**不变量
- **位置：**recipes.md:222-232；依据 docs/proposals/image-generation-v1.md:154
- **现象：**提案明确允许重复词：提示问题，但“万一出现，按出现的先后区分”。修订稿改为预设及引用节中每个键最多一次，读入或编辑时直接合并；这不在本轮给出的已确认决定中。
- **为什么是问题：**重复的项可能权重、停用或未知字段不同，删掉一项会改变项数和顺序。这是新产品取舍，不能作为解决首轮第 2、8 条的技术修补默默替换已接受合同。它还使“保存前的历史有效内容”与恢复后的唯一键要求冲突。
- **如何核实：**原提案可表示 P=`[rain@1, night@1, rain@2]`，两次 rain 按先后区分。修订读入后只能得到 `[rain@2, night@1]`，少了一项且最后的 rain 移到开头；提示一句不能恢复丢掉的信息。
- **建议改法：**若不重开决定，保留出现身份并补齐 remove/set/add 锚点的定位规则；若要采用唯一键，先由开发者确认改变提案，再定义迁移、冲突和历史恢复的边界。本条不是“对已定决定的质疑”，被质疑的是未经列明批准的偏离。
### 6. 重复项合并没有规定与差异计算、应用的先后
- **严重程度：**重要
- **类别：**正确性
- **位置：**recipes.md:213-232
- **现象：**输出 11 规定读入或编辑时合并重复键，输出 12 同时规定编辑后从 P/S 算差异；没有要求先把 P/S 合并到唯一键再取 LCS，也没规定手写差异应用中途出现重复键何时合并。
- **为什么是问题：**两个都照字面实现的顺序会保存不同差异；后合并的 UI 显示已改权重，重开却恢复旧值。随机项或手写 set 改变键后，立刻合并与整批改完再合并还会改变后续 key 查找的目标。
- **如何核实：**P=`[a@1,b@1]`，一次编辑得到 S=`[a@1,a@2,b@1]`。先合并再算得到 set(a,weight=2)；先算差异得到 add(a@2,after=a)，再按输出 10 因 a 已在删后内容中而作废，结果 `[a@1,b@1]`，不等于应显示的合并结果 `[a@2,b@1]`。已执行最小实验，比较为 false。
- **建议改法：**若唯一键设计获批，明确合并是 P/S 进入差异运算前的强制规范化；另定义差异执行的键坐标、变更键字段的限制，以及发生碰撞时的统一时点。把合并与差异的组合反例加入往返验收，不能只测预先去重的随机列表。
### 7. 句内 `::` 会清掉同权重分组，让符合条件的提示词仍不能往返（首轮第 4、7 条未完全解决）
- **严重程度：**重要
- **类别：**不变量
- **位置：**prompt.md:91-92, 118-121, 140-150, 167-174
- **现象：**句子内部的权重控制符原样保留，而相邻同权重项仍统一包在一个数值作用域内。句内 `::` 既结束数值权重又清掉括号，会提前关闭该组，影响后面的项。
- **为什么是问题：**输出 14 只排除了“词”的语法字符，没有排除句子里的控制符。它列出的全部条件成立时，写回仍能改变后续普通词的实际权重；这不是 P1 的分类代价。
- **如何核实：**无 source 的 items 为 sentence(`A girl stands ::.`,weight=2)、tag(`rain`,weight=2)。句子单独读还是句子、以句号结束，rain 无特殊字符，均满足输出 14；句内没有未闭合的权重。规范合并写成 `2::A girl stands ::., rain ::`。第一个句内 `::` 把 2 清掉，rain 读回为 1，不是 2。
- **建议改法：**不能把带权重控制语法的句子当作对外层状态透明的普通项。可把不能独立、无副作用序列化的句子退回 raw，或定义句内权重结构及独立写出边界；至少收窄往返条件，并在每个含控制符的句子后重建后续权重。
### 8. 片段写法丢掉 `part` 与 `off`，文件 source 校验又把名字直接和 id 比较（首轮第 3、4 条未完全解决）
- **严重程度：**重要
- **类别：**正确性
- **位置：**prompt.md:63, 70-73, 130, 146, 158-172, 242
- **现象：**持久片段引用存 id，并可带 part/off；规范写出却只能写 `@{名字}`，读回只得到名字。输出 12 要在 prompt 层重读 source 后直接与 items 比较，没有调用方完成名字到 id 的同一解析步骤；往返条件也没排除 part/off。
- **为什么是问题：**同一引用写出后可能换成主提示词部分、重新启用全部陪衬词；无改动的合法 source 也会稳定被判过期。名字解析明确不归 prompt，纯运算不能自行查书里的 id。
- **如何核实：**items=`[{kind:"fragment",ref:"abc123def456",part:0,off:["glasses"],weight:1}]`，调用方给名字“服装”。写成 `@{服装}` 后读回 ref=服装，part/off 均无，取主部分并带回 glasses。即使 items 不带 part/off，仅 source=`@{服装}` 与存 id 的 items 比较，也不相等。
- **建议改法：**把原文引用视图的解析/校验边界交给能解析名字的调用方，或注入明确的双向映射；定义 part/off 的可逆写法，做不到就明确从文字往返适用域中排除。source 的比较应在名字已解析为 id 后进行，并约定同名片段的歧义处理。
### 9. 随机项的键漏掉选项语义，又依赖会重命名的片段名字
- **严重程度：**重要
- **类别：**正确性
- **位置：**prompt.md:145-147, 161-166；recipes.md:215-230, 266
- **现象：**随机项以规范写出的文字作键；片段写成调用方给的名字，part/off 不写，停用状态也不写。这些都会改变随机选项的有效内容，却不进入键；片段名字变化反而会改变键。
- **为什么是问题：**唯一键合并会把两个不同选项行为的随机项当一项删掉；只改片段名字却会让按旧键保存的 remove/set 作废。键不再是由持久 Item 和稳定引用 id 决定的身份，纯差异运算还额外依赖未声明的名字查询。
- **如何核实：**两个 choice 都是 `[[fragment(F)],[rain]]`，第一个引用 off=[glasses]，第二个 off=[]。两者规范文字都是 `||@{服装}|rain||`，键相同，预设读入会合并成一项，但抽中 F 时本应一个无 glasses、一个有。再只把 F 名字改为“外套”，同一 choice 的键变了，旧差异定位失效。
- **建议改法：**为 choice 定义不经显示名字序列化的确定键，并明确哪些选项编辑保持身份；片段一律按稳定 id/part 参与键，不忽略会改变身份的结构。若随机项以完整内容作身份，应递归规范化公开数据，不复用有损的 NovelAI 显示文字。
### 10. `set.fields` 能改掉键本身，却没有改键后的定位与校验规则
- **严重程度：**重要
- **类别：**正确性
- **位置：**recipes.md:96, 214-224, 380；prompt.md:162-165
- **现象：**公开差异允许 fields 带任意字段；只在字段“不属于该项”时作废。text/ref/part/options/weight 都属于相应项，却参与键计算；fields 还可删除必填字段，或改成无效值。
- **为什么是问题：**只校验差异的 JSON 形状，不能保证实际内容仍是合法 Prompt，后续按键寻找哪项也无统一坐标。`diff-void` 被规定不阻止展开，但删除 text、把权重设成 10001 会产生没有失败通道的非法有效项。
- **如何核实：**P=`[a@1,b@1]`，diff 依次 set(a,{text:"b"})、set(b,{weight:2})。先合并得到单个 b，改的是合并项；后合并会有两个 b，定位规则又没有 nth。另把第二条换成 set(b,{text:null})：text 确实是 tag 的字段，按输出 10 必须删掉，但 tag 此后没有 text。这些差异均符合公开 Change 形状。
- **建议改法：**明确“改”只允许保持键的合法结果；改变身份用 remove/add，键在应用前绑定到同一基线。逐操作或统一阶段校验结果，并规定拒收、作废与展开失败的唯一归属。必填字段不能通过 null 删除，已知字段的值不能绕过 Prompt 有效域。
### 11. 恢复变化片段时，唯一键规则使历史实际内容无法表示（首轮第 25 条未完全解决）
- **严重程度：**重要
- **类别：**不变量
- **位置：**recipes.md:223-224, 265-269, 323-331
- **现象：**恢复必须保留仍存在的预设引用，并把已变化片段拆成当时的普通词；引用节的实际内容同时又必须每键只出现一次。片段展开可以与节里现有词重复，原始引用本身并不重复。
- **为什么是问题：**恢复把原来两个不同键变成两个相同键后，被强制合并，历史有效内容因此变少、权重或顺序改变。先拆片段还是先重算差异都消除不了这三个要求的直接矛盾。
- **如何核实：**当时 P.items=`[fragment(F)@1,rain@2]`，F.core=`[rain@1]`，生成的实际项为 `[rain@1,rain@2]`，预设中的键 `@{F}` 与 rain 唯一。现在 F 改为 snow，P 仍在。恢复必须拆回旧 rain，同时仍引用 P；目标 S 为 `[rain@1,rain@2]`，输出 11 却强制合成单个 rain@2，已不等于历史。
- **建议改法：**明确唯一键约束位于引用展开前还是展开后；历史恢复遇到不可表示目标时，允许脱离预设成为普通 Prompt，或恢复带快照绑定的稳定内容。不能同时绝对承诺仍引用当前预设、强制唯一键和历史逐项相同。
### 12. 引入 RFC 8785 后没有补齐它会拒收的数据与快照失败通道（首轮第 17 条未完全解决）
- **严重程度：**重要
- **类别：**正确性
- **位置：**recipes.md:57, 174-176, 309-322, 363, 380；prompt.md:61-66
- **现象：**引用 RFC 8785 解决了规范数字和键序，但文件有效域仍只是 UTF-8 JSON 加业务形状；任意 text、未知字段没有 JCS 输入约束。展开失败集合也没有快照规范化失败。
- **为什么是问题：**RFC 8785 第 3.1 节要求 I-JSON 输入，第 3.2.2.2 节要求遇到孤立代理项报错，不能用替换字符或 JSON.stringify 的转义结果继续算摘要。合法 JSON 文本不自动满足这条要求。
- **如何核实：**一个正常 tag 的 text 用 JSON 转义写成 `"\ud800"`：文件字节全是 ASCII、可按 UTF-8 读取，也符合 string 形状；JCS 却必须拒绝它。输出 27 要展开成功并给出 snapshots，输出 28 又不可能产生合规哈希。已核对 RFC 的上述两节。
- **建议改法：**把可快照的数据域写成文件/内存输入的公共前置条件，读入时拒绝重复属性名、非 Unicode 标量字符串及不支持的数值；映射到明确的 invalid-file 或展开失败。不要在算哈希时才发现错误后静默丢字段或替换文字。
### 13. 恢复只分预设在或不在，没有处理仍存在但不能再引用的预设（首轮第 25 条未完全解决）
- **严重程度：**重要
- **类别：**正确性
- **位置：**recipes.md:309-315, 323-333, 373
- **现象：**预设现在还在，恢复必须仍引用它并重算差异；当前文件的种类不匹配、格式坏了、版本更新或 id 无法唯一解析，都不在恢复分支里。snapshot-missing 只描述输入快照的问题。
- **为什么是问题：**有完整、有效的历史快照，也可能算不出相对当前预设的差异；即使勉强生成引用，下一次展开会失败，不能满足恢复后每一节实际内容与当时相同。
- **如何核实：**历史 style 节引用合法 style 预设 P，快照完整；现在用外部文件工具把同 id 的 P 改成合法 params 预设。P 仍“在”，但没有 prompt，不能算输出 12 的 LCS；把恢复节继续指向 P，又必得 invalid-reference。P 改成新版本、非法 JSON 或出现 duplicate-id 也一样。
- **建议改法：**按“当前目标能否合法且唯一地表示历史有效内容”而不是仅按存在性分支；不可用时可明确退成快照里的普通内容并提示，或定义专用恢复失败。参数引用和片段引用使用同一可用性判据。
### 14. 随机项回退 `raw` 的验收反例，不满足正文写出的任何回退条件
- **严重程度：**重要
- **类别：**正确性
- **位置：**prompt.md:126-129, 151-154, 262-263
