# w00042 t03 设计审查（Opus）：图像生成第一版提案

审查对象：/tmp/review-w00042-t03-design/image-generation-v1.md（仓库提交 39f08eb04 的副本）。行号按副本。

### 1. 原图与书里记录之间没有交付协议：窗口一关，结果就送不进书；“启动时对账”认不出孤儿原图属于哪本书
- **严重程度：**阻断
- **类别：**正确性
- **位置：**image-generation-v1.md:66-67、155、194、247
- **现象：**
  - 提案把一次生成拆成两步：服务端写原图，项目实例写生成记录与缩略图（247 行）。
  - 全局队列的承诺是“关掉标签页不丢结果”（155 行）。
  - 两步之间崩溃的补救只有一句“仓库启动时要对一次账”（247 行）。
  - 没写服务端怎样把结果交给项目实例，也没写项目实例不在运行时怎么办。
- **为什么是问题：**
  - `runtime/projects.md` 输出 9：服务端插件没有租约时，只有项目代次处于 `running` 才放行。`idle-grace` 一律 `denied`，到达的请求也不会取消宽限期。
  - 窗口握手取得的租约随窗口断开释放（输出 7）。所以最后一个窗口一关，项目马上进入 `idle-grace`，服务端此后就调不到项目实例，不用等 5 分钟。宽限期一满，项目实例停止。
  - 重度抽卡一次排几百张，跑几十分钟很常见。照字面实现，作者关窗口以后完成的批次只留下原图，书里没有记录，也没有缩略图。
  - 对账也救不回来：原图按内容哈希存（175 行），仓库本身不记“这张属于哪本书、哪份配方、哪一批”。启动时看到一张没有记录的原图，只能删（丢掉花过点数的图），或永远留着（不知道归哪本书，“按书列出”“单清一本”也算不进去）。
  - 仓库里早有现成做法。拓扑提案第 10 节的文生图走查（multi-instance-runtime-topology.md:281-309）就是这个场景：服务端记 `pending`（user 分区，带项目 id 与任务 id），项目入口激活或收到通知时领取，按任务 id 幂等写入，写完 `ackPending`，服务端才退役。提案没有引用它，另起了一个更弱的“对账”。
- **如何核实：**
  - 读 runtime/projects.md 输出 7、9（第 66、70-74 行附近）。
  - 读拓扑提案 281-309 行。
  - 设想：点生成 → 关浏览器 → 10 分钟后批次完成。按提案文字，没有一方负责把这批写进书。
- **建议改法：**在第 1 节或 `images/generation` 的边界里，二选一写明：
  - (a) 照拓扑第 10 节：服务端写原图时同时记一条待交付（项目 id、配方 id、批次 id、哈希列表、展开后的内容、费用），放在服务端自己的持久存储里。项目实例激活或收到推送时领取，按批次 id 幂等追加记录、写缩略图，再确认。孤儿原图由待交付记录归属，“对账”从此是重放待交付，不是猜。
  - (b) 队列里有这本书的批次时，服务端插件经 `projectsKey.acquire` 持有项目租约，批次全部交付后才释放。代价：项目子进程常驻，每个约 114 MB，带大世界时约 520 MB（projects.md 输出 12）。
  - 推荐 (a)：“关掉以后还在”本来就要求持久化。(b) 只覆盖“服务端没重启”的情形。
  - 另一个可以评估的简化：记录与缩略图都只追加或按内容寻址，可以由服务端在持有 `.nbook/locks/` 下的锁时直接写，省掉交付这一步。先例是 projects.md 第 123 行的封面上传，服务端直接写项目目录。代价：违背“项目实例拥有项目数据”的分工，且两个进程要共用同一把锁。需要开发者取舍。

### 2. 原图字节怎样从服务端到项目实例，缩略图由谁缩、用什么缩，都没写
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:66-67、183、196、247、109
- **现象：**
  - 缩略图、`.image` 文件夹由项目实例写（67 行）。
  - “用作插图或被引用”要把仓库里的原图复制进书（183、196 行）。
  - 画风预设存一份缩小的样图（109 行）。
  - 原图却在服务端的私有目录里。提案没写字节怎么过去，也没写缩略图在哪个进程生成。
- **为什么是问题：**
  - 远程服务单条消息上限 1 MiB，且明确“不经远程服务传二进制”（runtime/plugin-channel.md 第 21、117 行）。NovelAI 普通尺寸 PNG 按 1 到 2 MB 算（research/2026-11-10-artifacts-and-model-stress-test.md），整张原图过不了 RPC。
  - 插件之间也不经 HTTP 通信（plugin-channel.md 第 179 行，拓扑提案第 7 节）。
  - 现成的通道是写入接口的暂存加提交：服务端在项目的 `.nbook/staging/` 写暂存文件，项目实例提交（workspace/resources.md 第 157、198 行）。它只覆盖文件服务管的可见路径，能用于 `.image` 文件夹。
  - 缩略图在控制目录 `.nbook/images/thumbs/`，文件服务拒绝控制目录（files.md 第 63 行），暂存加提交用不上。只能由项目实例按服务端给的本机路径直接读原图，或由服务端缩好后经 RPC 传小图。两种都要在合同里写明。
  - 缩放要图片编解码。`packages/neuro-book/package.json` 里没搜到图片处理库：`sharp` 只在仓库根与 `neuro-book-legacy` 的依赖里。项目子进程要求与服务端同一个 Bun 可执行文件、同一产物目录（projects.md 第 177 行），原生模块能不能随产物发布要先查。
  - 主题素材的先例是在浏览器里缩（theme/editor.md 第 43 行），但生成完成时窗口可能已经关了（见第 1 条）。
- **如何核实：**
  - `grep -n sharp packages/neuro-book/package.json`：无结果。
  - 读 plugin-channel.md 第 21、117 行，resources.md 第 157 行。
- **建议改法：**
  - 第 1 节的分工表补“字节通道”一列：`.image` 走暂存加提交；缩略图由服务端在写原图时一并生成，作为待交付的一部分（几十 KB，装得进 RPC）交给项目实例写。
  - 技术选型（WASM 编解码或 sharp）列进 `images/library` 或 t06 的前置。只在浏览器里缩不可行。

### 3. 应用级状态的家没定，书里记录又追加同一批标记：两份真相；“按机器分文件”的机器身份不存在
- **严重程度：**重要
- **类别：**不变量
- **位置：**image-generation-v1.md:163-175、177、187、207-209
- **现象：**
  - 仓库要能回答几件事：每张原图属于哪本书（207 行“按书列出”“单清一本”），收藏钉住与否（177 行），最近一次查看时间（209 行“最久没看过”），是不是 7 天内生成的。这要一份应用级索引。提案的数据表（74-79 行）只有“图片仓库（全部原图与收藏）”，没有这份索引，也没说它放在 Storage user 分区还是私有目录里的数据库。
  - 同时，书里的生成记录又追加“收藏、删除、清理、收进书里”的标记（174 行）。
- **为什么是问题：**
  - **两份真相。**收藏是应用级的（已定），清理也由应用级仓库执行。作者在跨书的“我的收藏”里取消收藏，或自动清理清掉某本书的原图时，那本书多半没打开。服务端不能为此隐式打开项目（拓扑提案第 2 节“不能隐式打开”，projects.md 输出 9）。所以书里的“收藏”“清理”行会长期缺失或过时。
  - 调研自己总结过，库类工具最主要的故障就是外部索引与文件对不上（artifacts-and-model-stress-test.md“现有工具的做法”，InvokeAI 的文件加 SQLite 两份真相）。
  - **跨机器。**书经 Git 带到机器 B 后，A 写的“收藏”行在 B 上显示收藏角标，而 B 的仓库里没有这张图，也没有钉住；A 的“清理”行在 B 上分不清“清掉了”与“本来就不在这台机器上”。历史角标“原图已清”（187 行）应当由本机仓库实时判断，不该读书里的行。
  - **机器身份。**在 docs/specs、docs/proposals 与 packages/neuro-book/src 里没搜到机器或安装身份（machineId、installationId、deviceId 之类都无结果）。storage-service-and-sync.md 第 38 行写明“尚未提供可直接作为跨设备身份的字段”。如果拿主机名，同一台机器上两个状态根（开发与正式）会写同一个文件；如果放状态根里的 UUID，整个状态根恢复到另一台机器后两台同名。
- **如何核实：**`grep -rn 'machineId\|installationId\|deviceId\|hostname()' packages/neuro-book/src docs`，只有 storage/boundaries.md 第 50 行说主机名不够用。
- **建议改法：**
  - 按归属分账。
    - 书里的记录只记书级事实：生成、删掉这张、收进书里，以及每批的来历。
    - 收藏、钉住、查看时间、清理与原图在不在，只记在应用级索引里。
    - 角标按本机索引实时算。
    - 收藏的“来自哪本书哪份配方”在收藏时从书里复制一份（已定的“完整来历”正好是这一份）。
  - 机器身份写成状态根里首次启动生成的 UUID，文件名用它的短前缀。记录行另带写入进程的标识，同一文件允许多个写者时持 `.nbook/locks/` 下的锁追加（canon 世界日志的做法，canon/project.md 输出 8、22）。
  - 这条要改已定的“之后的标记也追加一行”（174 行），属于对已定决定的质疑。代价是书里看不到“收藏过”的历史；收益是不会出现书说收藏了、仓库里却没有的状态。

### 4. “复制出来的换新 id”没有执行者；按 id 引用要一份 id 到路径的索引，提案没有
- **严重程度：**重要
- **类别：**不变量
- **位置：**image-generation-v1.md:94、181-184、269
- **现象：**
  - 配方、预设、片段、风格组合、书里的图都带程序写的 id，“复制出来的换新 id；改名、移动都不影响引用”（184 行）。
  - `images/recipes` 的关键验收之一是“复制出来的配方换新 id”（269 行）。
- **为什么是问题：**
  - **复制不经过图像插件。**资源管理器的复制是文件服务的通用操作（files.md“文件操作”）。文件管理器、`cp -r`、Git 分支合并、同步盘冲突副本都在 NeuroBook 之外。在 workspace/files.md 与 resources.md 里没搜到给插件的复制钩子：记账槽只记账，不能改内容。所以复制出来的 `.image/image.json`、配方文件会带着原 id，必然出现两个文件同一个 id。
  - **id 解析没有落点。**按 id 引用需要一张“id 到路径”的表。它要扫描全书找配方、预设与 `.image` 文件夹，要跟着文件监视更新，还要定缓存在哪、冷启动扫多久、重名怎么报。提案对这些一句没写。
  - **对 Agent 不成立。**提案说 Agent 用文件工具就能读懂配方（43 行），但配方里只有预设 id，Agent 不经这张表找不到那份预设文件。
  - 活页夹有先例：编号重复“检测并提示，不自动改写文件”（folder-kinds.md 输出“编号分配”）。提案连这一层都没写。
- **如何核实：**
  - 读 folder-kinds.md“编号分配”，files.md“文件操作”。
  - 试想：在资源管理器里复制一个配方，两个文件 id 相同，生成记录按配方 id 查历史时把两份配方的历史混在一起。
- **建议改法：**在 `images/recipes` 与 `images/library` 里写明三件事：
  - id 索引由项目实例维护：打开时扫描，之后按监视增量更新。可以存进 project 分区 Storage 当缓存，丢了能重建。
  - 重复 id 的规则。推荐：保留最早出现的那个；后来的标“id 重复”，作者确认后由插件改写成新 id。不自动改写。验收改成“检测到重复并提示，确认后换新 id”。
  - 插件自己发起的复制（“复制配方”命令）直接写新 id。
  另外给配方、预设文件里的引用同时写 id 与当时的相对路径（只作提示），Agent 不经索引也能找到。

### 5. `.image` 文件夹靠的“已有的渲染贡献点”在实现里没搜到；就算按 Spec 有，它也只管显示，管不了打开、改名、复制
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:181-182、248
- **现象：**提案说资源管理器“经文件夹类型已有的渲染贡献点”把 `.image` 显示成一张图（182 行），并列为“用到的已有贡献点”（248 行）。
- **为什么是问题：**
  - **实现里没搜到。**在 `packages/neuro-book/src/plugins` 里没搜到文件夹渲染者的贡献点：
    - 文件夹类型是封闭的联合 `Type.Union([plain, content, binder])`（files/shared/contracts.ts 第 55 行）；
    - `folderKindOf` 写死了 `.content` 与 `.binder`（files/backend/folder-kinds.ts 第 13-16 行）；
    - 资源管理器把 `binder` 当成硬编码的标志处理（explorer/web/tree/rows.ts 第 139、183 行）；
    - explorer 只定义了右键菜单的贡献点（explorer/web/plugin.ts 第 89 行），workbench 的贡献点列表里也没有（workbench/web/plugin.ts 第 98-110 行）。
    - folder-kinds.md 的状态是 `implemented`，实现合同却只写“随 workbench.files-explorer 的后缀认领机制”。files-explorer.md 只有一句“活页夹由剧情插件注册的渲染者呈现”。
  - **按 Spec 也只管显示。**Spec 原文是“为某个后缀注册资源管理器渲染者”（folder-kinds.md“渲染贡献点”），只管显示。`.image` 还要几样，Spec 都没有：
    - 点它时打开当前版本，而不是展开；
    - 改名时保住 `-<短 id>.image` 后缀，提案的文件夹名规则是 `<说明>-<短 id>.image`（181 行）；
    - 复制时换 id（见第 4 条）；
    - 拖进编辑器时插入 `<image-generated id>`；
    - 搜索与 `find` 不把 `v1.png` 当成独立的图。
  - **History 要按路径认出 `.image`。**文件访问提案定的是 32 MB 以内的二进制全量快照（file-access-and-history.md 第 149、155 行）。提案的“`.image` 里的图只记哈希”（255 行），要求 History 按后缀认出 `.image` 文件夹，等于 History 依赖图像插件的约定。要么文件夹类型成为文件底座的公开概念，要么改成按大小或类型的通用规则。
- **如何核实：**`grep -rni renderer packages/neuro-book/src/plugins/explorer` 无结果；读上面列出的几处代码。
- **建议改法：**
  - 把“文件夹渲染者贡献点”作为前置工作单列：哪个 Task、扩展 folder-kinds 与 files-explorer 两份 Spec。
  - 贡献点的接口至少包括：行的显示、打开动作、改名约束（保留后缀）、复制后回调或“需要处理重复 id”的标志。
  - History 的豁免改成通用规则，例如“文件夹类型声明为资产的子树只记哈希”，不按 `.image` 写死。
  - 提案里“已有”改成“要新增”，影响一节同步改。

### 6. “没拆过、没改过的节原样写回”遇到跨节的权重，拼起来以后权重是错的
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:84-85、146、268
- **现象：**
  - 读入时算出每个词的实际权重，写出时没改过的节原样写回，改过的按规范写法写出（85 行）。
  - 粘贴默认按原文段落分节（146 行）。
  - 提案自己引了数字：约 36% 的社区提示词有一个权重同时管几节的词。
- **为什么是问题：**
  - NovelAI 的括号是线性的：每个 `{` 对右边所有内容乘 1.05，可以不配对，`::` 关闭全部括号（research/2026-11-06-tag-sources-and-novelai.md“权重语法”，官方 strengthening-weakening.md 第 35、45 行）。
  - 例：原文是 `{{a, b` 空行 `c}}, d`。按段落拆成两节以后，第一节原文 `{{a, b` 没有闭合。作者只改了第二节，第二节按规范写成 `1.1025::c::, d`，第一节原样写回。拼接结果是 `{{a, b` 空行 `1.1025::c::, d`：第一节没闭合的 `{{` 一直作用到 `::` 为止，c 被乘了两遍，而 d 在原文里本来不受影响。
  - 也就是说，“原样写回”只对自身括号平衡的节成立，而这正是 36% 的条目不满足的情况。
  - 拼接用什么分隔符（空行、逗号还是换行）提案也没写。没改过的节要原样写回，拼接就必须还原原文的分隔，否则“原样”也不成立。
  - `images/prompt` 的验收“没改过的节原样写回”（268 行）测不到这个情形。
- **如何核实：**按官方规则手算上例。拼接后 c 的权重是 1.1025 × 1.1025 ≈ 1.2155，原文是 1.1025。
- **建议改法：**
  - 规则改成以“节”为单位判断，不以“改没改”为单位：拆分时某节的原文自身不平衡（结尾时括号层数不是 0，或开头处继承了上一节的权重），这一节一读入就标成“必须按规范写出”。原样写回只用于自身平衡、且不继承权重的节。
  - 节之间的拼接分隔写进规范：缺省空行，与粘贴拆分按空行分段对称。
  - 验收补一条：跨节的权重区域拆分后改其中一节，拼接结果的每词权重与原文一致。

### 7. “也读 SD 的圆括号写法”会弄坏 Danbooru 里本来带圆括号的标签名；`[x]` 在两种写法里含义不同
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:85、88、143
- **现象：**
  - 读入规则“读 NovelAI 的花括号、方括号……，也读 SD 的圆括号写法；写出 NovelAI 的规范写法”（85 行）。
  - 体检把“SD 写法”列为毛病（88 行）。
- **为什么是问题：**
  - Danbooru 的角色、作品类标签大量带圆括号，用来区分同名，例如 `saber (fate)`、`hatsune miku (cosplay)` 这类形式。NovelAI 把圆括号当普通字符（社区结构调研第 92 行；权重语法表“圆括号：不表示加权”）。所以在 NovelAI 提示词里，`saber (fate)` 是正确写法。
  - 读入时把 `(fate)` 当成 SD 的 ×1.1 加权，就把正确的角色标签拆坏了。写回时变成 `saber, 1.1::fate::`，再标一条“SD 写法”的误报。
  - 同理，`[tag]` 在 NovelAI 是 ÷1.05，在 SD 是 ÷1.1（权重语法表）。同一段文字读成两种权重，提案没写按什么判断原文是哪种写法。
  - 社区数据里真用了 SD 写法的只有约 2%（社区结构调研第 92 行），带圆括号的标签名却是正常写法。照字面实现，误伤远多于收益。
- **如何核实：**
  - tagcomplete 的 `danbooru.csv` 里搜 `(`，角色类标签大量带括号后缀。
  - 对照调研第 92 行与权重语法表。
- **建议改法：**
  - 圆括号缺省按普通字符读。只有满足 SD 加权形式 `(词:数值)`，或括号内容不是词库里已有标签的后缀，才提示“可能是 SD 写法”，由作者确认后转换，不自动转。
  - 读入接口带“来源写法”参数（NovelAI、SD），由粘贴或读图元数据时的来源决定。方括号的倍率按来源写法取。
  - `images/prompt` 的验收补一条：`saber (fate)` 读入再写出不变，也不报 SD 写法。

### 8. 随机写法 `||a|b||` 放不进“一串项、每项带权重”的模型；按批记录对不上按张的抽签
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:83、86、120、172；t03“模型”一节“以后：‘几选一’项”
- **现象：**
  - 第一版要支持 `||a|b||`，在本地抽签，历史记抽到的是哪个（86 行）。
  - 项只有“词、句子、片段引用”三种（83 行）。“几选一”项被列为以后才加（t03 模型一节“以后”）。
  - 生成记录按批记“每一节展开后的内容”（172 行）。
- **为什么是问题：**
  - 官方文档（.local/novelai-docs/en/image/promptrandomizer.md）里，选项可以是：
    - 半个词：`||red|blue|| hair`；
    - 几个词：`||red hair, glasses|blue hair, sunglasses|,||`；
    - 权重前缀：`||1.5::|0.5::|::||rain::`。
  - 这些都跨越或切开“项”的边界。抽签之前，算不出每个词的权重，也画不成标签块。
  - 把它当一个不透明的文字项，就无法体检、无法显示中文；拆成项又表示不了半个词。第一版要支持它，数据上就已经需要“几选一”这类非文字项。这和“以后再加，不迁移”（38 行）的承诺冲突：现在不定形状，以后加“几选一”项就要迁移第一版存下的 `||` 文字。
  - 官方说即使同一种子，抽签也每次不同，看来是按张抽（第 9 行）。一批 4 张时，本地抽签是一批一次还是一张一次，提案没写。按张抽的话，按批记的“每一节展开后的内容”装不下 4 种不同的展开。
  - “没改过的节原样写回”（第 6 条）会把含 `||` 的原文发出去。若服务端也抽签（待 t02 测），记录里“抽到的是哪个”就和实际不符。
  - 从 NovelAI 图片读元数据时，官方区分原提示词与抽签后的 Actual Prompt（promptrandomizer.md“Actual Prompt”）。粘贴与读元数据要选哪一个，提案没写。
- **如何核实：**读 promptrandomizer.md 全文（52 行），对照提案 83、86、172 行。
- **建议改法：**
  - 第一版就定“几选一”项的数据形状：选项是一串项，或一段原文。展开前抽签，抽签粒度定为按张。
  - 生成记录改成每张记抽签结果，或者“每批记展开模板、每张记抽中的选项下标”。
  - 含 `||` 的节一律按规范写法写出，发给后端的永远是抽签后的文字。
  - 读元数据缺省取原提示词，Actual Prompt 作为选项。
  - 选项里出现权重前缀或半个词时，第一版可以只当原文保存、不画标签块、体检跳过，但形状要能装下。

### 10. 引用加差异的几处语义没定：项怎么认、锚点、同种节有几个时预设挂哪、“作废并提示一次”记在哪
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:101、105-108、111、189
- **现象：**
  - 改动只有加、去、改值三种，加一项带锚点（107 行）。

### 11. 记录只存预设与片段的哈希，恢复与收藏要的“当时内容”拿不回来
- **严重程度：**重要
- **类别：**正确性
- **位置：**image-generation-v1.md:170-172、178、189
- **现象：**
  - 每批记“每一节展开后的内容”与“引用的预设与片段，加上它们当时内容的哈希”（170-171 行）。
  - 恢复时“仍引用原来的预设，差异按当时的内容重算”（189 行）。
  - 收藏时另存“当时预设与片段的名字和内容”（178 行）。
- **为什么是问题：**
  - 哈希只能判断“现在的预设和当时一样不一样”，还原不出当时的内容。
  - **收藏。**收藏可能发生在生成几周以后，从历史缩略图带里点收藏。那时预设已经改过，“当时预设的内容”只能从记录里取，而记录里只有哈希。照字面实现，收藏的来历会写成收藏时的预设内容，标的却是“当时”。
  - **恢复。**“差异按当时的内容重算”，可行的读法是“以现在的预设为底，与当时展开的内容做差”。这只要展开内容，不要哈希。但展开内容是片段已经展开、随机写法已经抽完、停用的节与项已经去掉的结果，恢复出来以后：
    - 片段引用变成普通词；
    - `||a|b||` 变成抽中的词；
    - 停用的项消失。
    这和“恢复这批的配方”的意思不符，作者还得重新把片段拖回来。
- **如何核实：**设想：生成后改了画风预设，三周后从历史收藏这张图，看收藏来历里的预设内容来自哪里。
- **建议改法：**
  - 每批除了展开后的内容，再记一份展开前的配方快照：节的列表、各节的预设 id 与差异、片段引用与关掉的陪衬词、随机写法原文、停用状态。配方本身很小，一份约几百字节到 2 KB。
  - 预设与片段按内容哈希只存一份，放进书里 `.nbook/images/` 下按哈希命名的快照区。记录里的哈希就能还原内容，同一预设版本只存一次。
  - 恢复用展开前的快照。收藏的来历从快照里取，不读当前的预设。

### 13. 插件自己的读图路径没写授权与防护；书里的缩略图在 `.nbook/` 下，现有读法读不到；跨书的“我的收藏”用不了书里的缩略图
- **严重程度：**重要

  - **查看时间。**按调研的用量，重度抽卡三个月约 23 GB，按 1.5 MB 一张约一万五千张。每张都要一个“最后查看”时间。
    - 放进 Storage 记录不现实：一条记录缺省上限 64 KiB、最大 1 MiB（storage/persistence.md 第 56 行），而且每次写都是整值的条件保存。
    - “看过”的定义也没写：缩略图带滚过算不算？只有打开大图或灯箱才算？
    - 浏览图库网格时，一秒可能有几十次“看过”。不节流就是每秒几十次写盘。
  - **保护期内超额。**上限可以调低（例如 5 GB）。一周抽了 1.8 GB 以上（重度用法的周量，调研表）再加上收藏以外的旧图时，7 天保护会让清理清不到九成。是每次生成都再试一次清理，还是提示一次后停？提案没写。
  - **等审阅的候选。**它属于 t10，t10 还不存在。但仓库现在就要有“由别的功能临时钉住”这种状态，否则 t10 来时要改清理规则。
  - **并发。**“用作插图”要从仓库复制原图进书（见第 2 条，要经暂存与提交，跨进程）。自动清理恰好在两步之间删掉原图，复制就失败了。
  - **先例。**主题素材的清理（theme/editor.md 输出 22）已经处理过同类问题：保护期从“最近一次被交出”起算、真删前在互斥里重新核对、库没读完时拒绝清理、读目录失败不当成“空的”。提案没有引用。
  - **删除不可撤销。**调研总结的同类工具做法是“删除分档、删前查引用、默认进回收区”（Lightroom、Obsidian）。提案的“删掉这张：立刻删”既没有回收区，也没写确认。花过点数的图被误删就没了。
- **如何核实：**读 persistence.md 第 56 行，theme/editor.md 输出 22，研究报告“现有工具的做法”。
- **建议改法：**
  - 应用级索引（第 3 条）用插件私有目录里的 SQLite。“看过”定义为经读图路径取原图。查看时间在内存里合并，每分钟至多落盘一次。
  - 超额又清不动时，状态栏提示一次，之后每次生成前不再重试，直到占用变化。
  - 钉住分两种：收藏，与临时钉住（带持有者与到期时间），t10 用后一种。
  - “收进书里”前先临时钉住，提交后再放。
  - 清理照主题素材的做法，真删前重新核对。
  - “删掉这张”先进一个 7 天的回收区。回收区也归上限管，最先清。

### 15. `Text:` 与 `|` 多角色写法的边界：文字本身按空行分段，和“按段落分节”冲突；角色框里也能写 `Text:`
- **严重程度：**建议
- **类别：**正确性
- **位置：**image-generation-v1.md:87、122、145-146
- **现象：**
  - 图中文字单独一项，“展开时总放在主提示词最末”（87 行）。
  - 粘贴“默认按原文的段落分节”（146 行），一次收整套：主提示词、负面、角色框（145 行）。
- **为什么是问题：**
  - 官方 textrendering.md：几段不同的文字之间用空行分开，`Text:` 之后到结尾都是文字。按“空行分段”的粘贴拆分，会把第二段文字拆成一个新节，落进“通用”节，被当成标签做体检、按逗号切词。
  - 同一文档说 `Text:` 也可以写在角色框里。提案只说放主提示词最末，没写角色框里的 `Text:` 算什么。
  - 各模型的文字长度上限不同：V4、V4.5 是 118 字符，V5 Curated 374，V5 Full 750。这是只靠语法就能查的毛病，体检可以带上，提案没列。
  - 官方 multiplecharacters.md 第 46 行：没有角色框时，`|`（不在 `||` 里）用来分隔主提示词与各角色。社区与官方的示例提示词就是这样写的（textrendering.md 的例子）。粘贴拆分要“一次收整套角色框”，就必须认这个分隔符，提案没写。
  - `Text:` 内容里的逗号、括号、`::` 都是文字，读入时不应按权重语法解析。
- **如何核实：**读 .local/novelai-docs/en/image/textrendering.md 全文与 multiplecharacters.md 第 46-50 行。
- **建议改法：**在 `images/prompt` 里写明三条：
  - `Text:` 起到这一段提示词的结尾是一个文字项，内部的空行与符号原样保留，粘贴拆分不在其中分节。角色框里允许各有一个文字项。
  - 体检加“文字超长（按模型）”。
  - 粘贴时认 `|` 多角色写法：`||…||` 之外的 `|` 分出角色框。

### 16. 上游选择：控制目录 `.nbook/` 正在变成“插件随书数据”的落点，每个插件各写一份目录、锁与 Git 规则
- **严重程度：**建议
- **类别：**代码质量
- **位置：**image-generation-v1.md:74-76、163-164、246、259
- **现象：**
  - 生成记录与缩略图放 `.nbook/images/`，由插件直接写，不经文件服务；记录“建议提交”，缩略图“可选”（74-75 行）。
  - 先例是 canon 的世界日志（canon/project.md 输出 13）。
- **为什么是问题：**
  - 控制目录最初的定义是“项目身份、项目层配置与 Storage”（files.md 第 63 行）。它不经文件服务，理由是保护这几样。现在同一目录里有四种处理：
    - 必须忽略的 `storage.sqlite*`（persistence.md 第 139 行）；
    - 必须提交的世界日志（canon/project.md 第 142 行）；

    - 可选的缩略图。

    - 跨进程锁在 `.nbook/locks/`；
    - 只追加文件的写一半修复与冲突副本处理共用一份实现；
    - 是否进 Git 由插件声明，宿主生成 `.gitignore` 片段；
    - 经资源地址方案给 Agent 只读访问。
  - 插件私有目录（应用级）同时定，路径为状态根下的 `plugins/<插件 id>/`，不对 `user://` 暴露。
  - 代价：多一份 Spec，canon 已有的路径要不要迁移需要另议。不改的话，至少在 `images/library` 里照 canon 写全写一半修复、冲突副本与锁。

### 21. “一被引用就自动收进书里”没有观察者：只有图像插件自己的命令能做到，Agent 和外部编辑写进去的仓库引用没人接

  - **正文：**`<image-generated id>` 的入口在 t10，同样由插件命令先复制。
  - **配方的源图与参考图：**配方是普通文件，Agent（经文件工具）与外部编辑器都能写。提案没定配方里的图引用写什么：书里图的 id，还是仓库哈希。若允许写仓库哈希，就没有一方观察到这次写入并触发“收进书里”。那张图照样会被自动清理，配方从此引用一张不存在的图。
  - 所以，“自动”在三处里都没有观察者，实际是“插件命令先复制再引用”。
- **如何核实：**读 canon/components.md 第 113 行。在提案里找监视配方写入的机制：没有。
- **建议改法：**
  - 把规则改写成“图像插件提供的引用命令先收进书、再写引用”。
  - 配方里的图引用只能是书里图的 id。展开时遇到仓库哈希或找不到的 id，报“引用无效”，不生成。
  - 验收相应改成“经插件命令建立引用时收进书；配方里的无效引用在展开时报错”。

### 22. “原图字节不改、按内容哈希存”与“写进图片的元数据只写白名单字段”互相拉扯
- **严重程度：**建议
- **类别：**安全与性能
- **位置：**image-generation-v1.md:175、178、251
- **现象：**
  - 仓库按内容哈希存，同一张只存一份（175 行）。
  - 收藏时“原图字节不改，NovelAI 写在图里的元数据留作备份”（178 行）。
  - 安全一节又说“写进图片的元数据只写白名单字段，不写凭据与本机路径”（251 行）。
- **为什么是问题：**
  - 没写清白名单作用在哪份图上：后端返回的原图、`.image` 里的版本、还是导出的收藏。
  - 若要清掉后端写进去的字段（以后的 ComfyUI 会把整个工作流嵌进 PNG，提案自己举了这个例子），就要改字节。改了以后，哈希与生成记录里的“图片哈希”对不上。
  - 若不改，白名单就只约束“我们自己写的”，而 NovelAI 返回的图里有什么字段要等 t02（待定项 1 的“PNG 元数据的字段”）。
- **如何核实：**对照 175、178、251 行与待定项 1。
- **建议改法：**
  - 写明三点：原图按后端返回的字节存，哈希就是这份字节的；白名单只作用于导出与收进书里的副本；收进书里的版本另记自己的哈希，与原图哈希的对应写进 `image.json`。
  - ComfyUI 接入时，在适配器里先清洗再入库，哈希按清洗后的字节算。

### 23. 多本书共用一个上限：同一张图属于两本书时怎么算没写；全局“最久没看过”会先清空几个月没开的书
- **严重程度：**建议
- **类别：**正确性
- **位置：**image-generation-v1.md:175、207-209
- **现象：**
  - 仓库按内容哈希、同一张只存一份（175 行）。
  - 空间页按书列出占用、可以单清一本（207 行）。
  - 到上限时按全局“最久没看过”清（209 行）。
- **为什么是问题：**
  - **一张图属于两本书。**同一张图可能属于两本书，例如把 NovelAI 的图拖进两本书读元数据，或在两本书里重抽出同一张（种子能否重抽待 t02）。这时：
    - “每本书占多少”是重复计算还是只算一次？
    - “单清一本”要不要删另一本书也在用的原图？
    提案都没写。仓库索引的形状因此是“哈希对一本书”还是“哈希对多本书”，现在就要定。
  - **全局 LRU 先清冷门的书。**一本连载配图的书一个月才开一次，另一本书在重度抽卡（一周约 1.8 GB）。全局“最久没看过”会先把前一本的原图全部清掉。这是 LRU 的本来后果，但提案没写，作者也不会预期到。
  - **与结果区、灯箱并发。**最近一批在 7 天保护内，不会被清。打开大图算“看过”的话，正在看的那张也不会成为最旧的。剩下的窗口是：清理与读取同时发生时，读图路径返回 404。界面要显示“原图已清”，不能当成网络错误。
- **如何核实：**对照 175、207-209 行与调研体积表。
- **建议改法：**
  - 仓库索引是“哈希对多本书”。按书占用只算这本书独有的。“单清一本”只删没有别的书引用、也没收藏的原图。
  - 空间页的“到上限自动清”旁写一句：“最久没打开的书最先被清”。
  - 读图返回 404 时，结果区与灯箱显示“原图已清”，记录里的配方仍可恢复。
