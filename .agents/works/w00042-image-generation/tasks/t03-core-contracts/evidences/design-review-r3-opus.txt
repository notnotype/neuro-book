# w00042 t03 设计审查第 3 轮（Opus）：新存储结构闭不闭合

依据：主工作区 HEAD `bb72ef757`；`git diff 578394397 HEAD -- docs/specs docs/proposals packages/neuro-book/src/plugins/files` 为空，副本与 HEAD 的提案逐字相同，行号按副本。

### 1. 对账“按批次 id 去重”，可一批在仓库里有多行：工作台开着时，书里的批次会永远停在“已提交”；撤销扔掉、删书里缩略图也没有通道
- **严重程度：**阻断
- **类别：**修订引入的新矛盾、跨进程时序
- **位置：**image-generation-v1.md:89、98、99、100、239、268
- **现象：**
  - 98 行：仓库先记一行“已提交”，拿到结果再记“完成”；失败、取消、中断各记一行。
  - 99 行：项目入口把“副本里还没有的记录”补进副本，“按批次 id 去重”。
  - 100 行：服务端在项目运行期间推“有新记录”。
  - 89、268 行：扔掉也要同步进副本。扔掉可以撤销；扔掉的图原图被清时，书里的缩略图一并删掉。
- **为什么是问题：**
  - **主路径就会出错。**作者开着工作台点生成。“已提交”这一行写下就是新记录，服务端推送，项目入口把它补进副本。几秒后“完成”行到了，批次 id 已在副本里，按 99 行的字面被当成重复跳过。书里这一批就永远是“已提交”：没有图片哈希、没有费用，别的机器上也只看到“已提交”。
  - **扔掉同理。**扔掉是另一行（或一个标记），批次 id 早在副本里，同样会被跳过。撤销扔掉在副本里怎么表示，没写。
  - **删缩略图没人做。**书里的缩略图在控制目录 `.nbook/images/thumbs/`。服务端经文件服务写不进去，会得 `protected-path`（files.md:63、resources.md:171）。所以只能由项目入口删，可对账只补“记录行”，不传“哪张原图已清”。“原图已清”按 88 行只在仓库里，不进副本。项目入口无从知道该删哪张缩略图。
  - **“生成那天”。**补进副本时按哪一天找文件，要由仓库在行里给出日期字段，不能由项目入口按当地时区重算：时区一变，就会查错文件、写出第二行。这一点也没写。
- **如何核实：**按 98 到 100 行推演“工作台开着、生成一批”：推送会在“已提交”与“完成”之间各来一次。再对照 resources.md:171（控制目录不能经文件服务写），以及 88、89 行副本里的字段。
- **建议改法：**
  - 去重键改成“行”。仓库给本机写的每一行一个单调递增的序号（每个安装 id 一条序列），副本原样带着它，按序号去重。批次的当前状态，由读副本的人按同一批的最后一行算。
  - 扔掉、撤销扔掉、扔掉的图被清，都作为仓库行进副本。项目入口读到“扔掉的图已清”这一行时，删掉对应的缩略图。
  - 行里带仓库写入时定下的日期字段，副本按这个字段选文件。
  - `images/library` 加验收：工作台开着时生成，书里这一批最后是“完成”；扔掉后撤销，在另一台机器上看也是没扔掉。

### 2. 对账没有协议：凭什么知道“副本里还没有”没写；照字面每次读历史都要全量比对，且同一实例里会并发补同一批
- **严重程度：**重要
- **类别：**接口与合同、跨进程时序、并发
- **位置：**image-generation-v1.md:99、100、104、310
- **现象：**99 行只说“把仓库里属于本书、副本里还没有的记录补进副本”；100 行的触发点是激活、工作台或图库读历史、服务端推送。三种触发之间怎么排队、读历史等不等对账，都没写。
- **为什么是问题：**
  - **差集怎么算。**只能二选一：
    - 项目入口把副本里全部批次 id 发给服务端；
    - 服务端把本书全部记录发过来，由项目入口比对。
    
    两种都要服务端扫一遍仓库里所有书的全部记录。仓库按天分文件、不按书分，只追加、永不删。量按 310 行“每批约 2.5 KB”与 304 行“三个月约 15000 张”估算：每本重度使用的书一个季度约 4000 批、10 MB；仓库是所有书的总和，逐年增长。100 行把触发放在“每次读历史”，等于每次打开工作台都全扫一次。
  - **缩略图的量。**远程帧是 JSON（rpc-socket.ts 第 5 行，项目子进程的链路是同一编码，projects.md 第 4 条），缩略图要转成 base64。10 KB 约变成 13.3 KB，单条 1 MiB 约装 75 张。作者离开一周回来补 2000 张，就是二十多条消息。读历史要是等对账结束，打开工作台就卡在这里。
  - **并发。**两个窗口打开同一本书时，共用同一个项目实例（拓扑提案第 131 行）。两个窗口同时打开工作台或图库，再加上一次推送，同一实例里就有三次对账。每次各自算出“缺 B1”，各自追加一行，副本里就有了重复行。99 行的去重说的是“补之前查”，不是互斥，挡不住这种情况。
  - **激活时对账。**插件在代次报告“已启动”前激活（projects.md 第 4 条）。激活要是等服务端回话，项目打开就多了一次跨进程往返，再加上可能的整批缩略图。
- **如何核实：**按 99、100 行，分别写出项目入口和服务端各要做什么，看哪一方能不扫全量就知道差集。对照拓扑提案第 131 行、rpc-socket.ts 的 `RPC_MAX_MESSAGE_BYTES` 与 JSON 编码。
- **建议改法：**
  - 用第 1 条的“每安装一条行序号”做游标。项目入口启动时读一遍自己目录里的副本，记下最大序号，之后只问服务端“本书序号大于 N 的行”。服务端为每本书维护一份序号索引，可以重建。游标从副本本身算出，副本被删或被 Git 回退时自然从更小的序号补起，不另存游标。
  - 项目入口里对账单飞：同一时间只跑一次，期间来的触发合并成“跑完再跑一次”。
  - 读历史先交回副本现有的内容，对账在后台跑，补进来的批次按事件推给浏览器。激活只发起对账，不等它结束。
  - 每次回话按条数与字节数分页，缩略图单独分批。

### 3. 仓库里缩略图的寿命没写：原图在书对账之前就被清掉时，书永远拿不到这批的缩略图；副本被删后能不能补齐也取决于它
- **严重程度：**重要
- **类别：**没写出来的假设、遗漏（边界）
- **位置：**image-generation-v1.md:104、247、268、284、290、292、294–295
- **现象：**
  - 247 行：“每张原图有一张缩略图”。
  - 104 行：缩略图由服务端生成，“对账时随记录成批交给项目入口”。
  - 284 行：“原图被清掉以后，书里的缩略图与记录还在”。
  - 292 行：上限只管原图，保护期 7 天（295 行）。
  - 268 行只写了书里那份缩略图什么时候删。仓库里那份什么时候删，全文没写。
- **为什么是问题：**
  - **284 行的承诺依赖时序。**它默认书在原图被清之前已经对过账。可对账只在书被打开时发生（100 行）。全局队列是跨书的，X 书的一批可能排在 Y 书后面，在 X 已经停掉之后才完成。之后 X 一直不打开，Y 把空间用到上限，7 天后 X 这批原图（从没被看过）排在最前被清。仓库的缩略图要是跟着原图删，X 再打开时只拿到记录，历史里这一批没有图，284 行不成立。
  - **副本能不能补齐，也取决于这一点。**作者在 Git 里删掉或回退了本机的副本，下一次对账会从仓库补回记录。缩略图还在不在仓库，决定补回的历史有没有图。
  - **两种做法都要写明。**
    - 仓库缩略图永久保留：它不受上限管，量约每年几百 MB（按 292、304 行，40 GB 约存 27000 张原图，重度约 5 个月一轮）。“图片空间”的“缩略图”一块要能清，清了以后上面两种情形都没有图。
    - 跟着原图删：清理顺序要把“还没对过账的批次”当作受保护，可服务端不知道哪本书对到了哪里（见第 2 条）。
- **如何核实：**按上面的情形推演，对照 247、284、292、295 行。全文搜“缩略图”，没有一处写仓库那份何时删。
- **建议改法：**
  - 写明仓库缩略图与原图分开管：原图清掉时保留缩略图；缩略图只在原图是“扔掉”时随原图删（与 268 行对书里那份的规则一致），另在“图片空间”里给一个手动清缩略图的入口。
  - 在 `images/library` 验收里加一条：X 书停着期间完成的批次，原图被清以后再打开 X，历史里有这批的缩略图。

### 4. “收进书里”只写了复制原图：引用由谁写、写进打开着的文档怎么办、复制成功引用失败怎样、结果未知时怎么重试，都没写；锁跨着跨进程提交持有
- **严重程度：**重要
- **类别：**依赖的机制、接口与合同（失败通道）、跨进程
- **位置：**image-generation-v1.md:104、261、280、299、310、349、352
- **现象：**
  - 261 行：“服务端先把原图复制进 `.image` 文件夹，再写引用”。
  - 引用的四种去处：用作插图、设为定妆图、设为配方的源图或参考图、单纯收进书里。
  - 299 行：清理、收进书里、收藏“同一把锁里做；收进书里复制期间临时钉住原图”。
- **为什么是问题：**
  - **定妆图服务端写不了。**canon 的 `image` 值是世界日志里的一次修订（canon/components.md:81）。世界日志由项目实例里的世界服务直接写，不经文件服务（canon/project.md 输出 13），服务端经 `projects://` 碰不到 `.nbook/`。所以“再写引用”在这里必须回到项目实例去做，而第 1 节和第 6 节没有这条回程。
  - **配方的源图与插图会撞上已有的冲突。**作者是在工作台里点“设为源图”的，这时配方正开着，常常有没保存的修改。服务端按文件写配方，就是 310 行用来否掉“历史写进配方文件”的那个冲突：编辑器只能“重新载入”或“覆盖”。插图往打开着的章节里插，352 行自己承认“现在没有这个入口”。这两种引用只能作为编辑器里的一次编辑写，服务端做不了。
  - **半途失败。**图复制进去、引用没写成时，`插图/` 里会多一个没人引用的 `.image`。作者重试，又复制出第二个，id 不同、内容相同。
  - **结果未知。**`projects://` 的写入可能得到 `unknown-outcome`（resources.md:121、135）。按原期望重试是安全的，但对 `absent` 的目标，已经提交的那次重试会得 `conflict`。插件要把“目标已存在且哈希相同”认作成功，否则会换名再写一份。这一点没写。
  - **锁的范围。**`projects://` 的写入从暂存起持着项目租约，没在运行的项目会被打开（resources.md:122）。打开要约 0.3 到 0.5 秒（projects.md 第 12 条），再加上传送最多 32 MB 的原图。锁要是跨着这段持有，同一时间所有书的收藏、清理都得排队。已经临时钉住原图了，锁只需要罩住“钉、核对哈希”和“放钉”两小段。
- **如何核实：**对照 canon/components.md:81、canon/project.md 输出 13、resources.md:121–122、135，以及提案 310、352 行。
- **建议改法：**
  - 把“收进书里”拆成两段写明。服务端只负责“原图进书”：在锁里钉住原图、核对哈希，然后放锁；接着以 `absent` 期望写 `.image/v1.png` 与 `image.json`，结算后放钉；交回图片 id。引用由发起方写：编辑器里打开着的配方或章节，作为一次可撤销的编辑；canon 经世界服务。
  - 幂等：同一本书里，同一个图片哈希已有 `.image` 时，直接交回它的 id，不再复制。`conflict` 与 `unknown-outcome` 都按这条判定，不换名重写。
  - 引用写失败时，`.image` 照样留着（它是一张普通的书里的图），界面提示“图已收进书里，引用没写上”。

### 5. “只缺一样平台能力”仍不成立：服务端代写的来源是 `system`，记成作者需要新能力；仓库“只追加”没有对应的写法；排除没覆盖变更事件
- **严重程度：**重要
- **类别：**依赖的机制、违反现有合同、第 2 轮第 10、11 条与其更正没到位
- **位置：**image-generation-v1.md:99、241–242、251、339、398
- **现象：**
  - 339 行：“只缺一样平台能力：改动记账的排除要做成贡献点”。
  - 待定项 6（398 行）却推荐了三样：排除贡献点；`.image` 里的图片只记哈希；插件代作者执行的写入记作作者发起、不进审查收件箱。
  - 仓库的本机记录“只追加，按天分文件”（242 行）。半行的处理只写了副本那份（99 行）。
- **为什么是问题：**
  - **来源。**写入的来源由调用方身份决定，服务端插件一律是 `{kind: "system", plugin}`。只有 `nbook.agent` 能注明代表某个会话（resources.md 写入来源表）。这一轮把“收进书里”挪到了服务端，作者点按钮收进来的图在账本里就成了系统写的。Agent 从对话里触发的，也丢了会话归属，Agent 的“本轮改动的文件”看不到它。要“记作作者”，就得让发起者经远程调用传到服务端的写入接口。resources.md 写明这一步还没有（“在发起者沿命令调用链传到执行边界之前也记为写作者”）。这是第二样平台能力；“只记哈希”按路径改记账粒度，是第三样。
  - **只追加。**写入接口只有整份替换：`stage`、`write`、`update`（resources.md:118–124），没有追加。
    - 经接口写：每追加一行就整份重写当天的文件，记一次版本、发一次事件。
    - 直接追加：违反“写入只有文件服务一个入口”（resources.md:14）。监视会把它当外部改动；`user://` 又没有控制目录（files.md:63），canon 的先例套不上。
    
    第 2 轮的更正已经指出这一点，第 2 轮的处理表没有收进来。
  - **事件。**每张原图、缩略图、每次“看过”的批量写入，都会给开着的资源管理器（“用户资产”根）发事件，量大时触发“失同步”、整根重新核对（resources.md 的“订阅”）。待定项 6 只排除了记账，没提事件。第 2 轮第 11 条的更正要求两者都排除，没收进来。
- **如何核实：**读 resources.md 第 14 行、写入来源表、第 118–124 行与“订阅”一段，对照提案 339 行与 398 行。
- **建议改法：**
  - 339 行如实列出要提给 w00032 t13 的平台能力，写进 `images/library` 的前置：
    - 记账与监视事件的排除贡献点（被排除的前缀只给订阅方一条合并后的粗粒度事件）；
    - 按前缀只记哈希；
    - 发起者经远程调用传到服务端写入接口。
  - 写明仓库记录怎么写，二选一：
    - 本机记录不按天分 JSONL，改成仓库里的一个 SQLite，并把它放到排除前缀里（数据库自己的写入在监视上算外部改动，所以排除必须覆盖监视）；
    - 或者用平台新提供的“追加”操作。
  - 发起者不能传递之前，把“收进书里在账本里显示为图像插件”写成已知限制。

### 6. 安装 id 文件放在作者能删的地方：丢了就换新 id，本机的批次会全变成“不在本机”，而且每本书的历史都会翻倍
- **严重程度：**重要
- **类别：**没处理的边界、修订引入的新风险
- **位置：**image-generation-v1.md:89、94、106、248、250、398
- **现象：**
  - 106 行：安装 id 存成 `user://images/` 里的一个小文件，插件第一次运行时生成。
  - 94 行：“不在本机”按副本目录的安装 id 判定。
  - 99 行：对账只看本机自己那个目录。
  - 250 行：`images/` 在资源管理器的“用户资产”下看得到，Agent 也读得到（获批后可写）。
  - 待定项 6 把仓库的原图、缩略图、记录与快照排除在记账之外，安装 id 文件算不算没写。
- **为什么是问题：**作者在资源管理器里清理“用户资产”时删了它，或者 Agent 获批后删了它，或者它被写坏了。下一次启动，插件看到“第一次运行”，生成新 id。之后：
  - 书里旧 id 目录下全是本机生成的批次，现在按 94 行算作“另一台机器”：角标“不在本机”，不能收藏、不能收进书里。可原图明明都在仓库里。
  - 对账在新 id 目录里什么都找不到，把仓库里属于本书的全部记录重补一遍。历史里每一批都出现两次：旧目录一份，新目录一份。
  - 每本书都会这样，而且这本书经 Git 到了别的机器，那边也看到两份。
  - 文件不进账本，没有可恢复的旧版本。
- **如何核实：**按 94、99、106 行推演“删掉安装 id 文件、重启、打开一本旧书”。
- **建议改法：**
  - 仓库的每一行都带上写它的安装 id（第 1 条的行序号本来就按安装 id 分）。启动时没有 id 文件，先从仓库记录里取最近一行的 id 恢复，仓库里一行都没有时才生成新的。
  - 或者把安装 id 放到状态根里不经 `user://` 暴露的位置，跟登记表 `projects.json` 并列。
  - 在 `images/library` 加验收：删掉安装 id 文件并重启，本机批次的角标不变，副本不重复。

### 7. 仓库的记录成了唯一主人，却不记账、可被删改，坏了没有规则；“没有记录的原图”有两种来路，都没写怎么处理
- **严重程度：**建议
- **类别：**遗漏（失败路径）；第 2 轮第 4、7 条没到位的部分
- **位置：**image-generation-v1.md:88、98、250、251、291、398
- **现象：**
  - 98 行：拿到结果后“写原图与缩略图，再记完成”。
  - 250 行只处理文件这一侧：原图不见了算“原图已清”，名字与哈希不符的列为“不认识的文件”。
  - 记录文件被删、被改坏、写到一半，提案都没写。这几样都在 `user://images/` 里，按待定项 6 排除在记账之外。
- **为什么是问题：**
  - **崩溃留下的原图。**写完原图、还没记“完成”时服务端崩了，重启后按 98 行把这一批记成“中断”。这时原图已在仓库、费用已扣，记录却说没有结果。原图的文件名等于哈希，所以被认作原图，但没有一行记录指向它：属于哪本书（291 行“一张原图只属于生成它的那本书”）、按什么顺序清，都无从判断。作者花了点数，图却看不到。第 2 轮第 4 条指出过“先写原图再记录，两步之间崩了会留下没有记录的原图”，这次修订只把顺序换了个说法。
  - **记录被删或改坏。**作者在“用户资产”里删了某天的记录文件，或者 Agent 获批后改了它。上一稿这些事实有书里的一份兜底；现在仓库是唯一主人，副本只是复制品，提案没有从副本反建仓库的路。那几天的原图同样变成“没有记录的原图”。有过扔掉标记的，扔掉也跟着丢了。
  - **坏行。**仓库记录里的坏行按什么规则处理没写。要是照 canon 的做法，中间一行坏就只读（canon/project.md 输出 4），整台机器就生成不了图了。
- **如何核实：**按 98 行推演写原图之后、记“完成”之前崩溃；对照 250 行只覆盖的那两种文件侧情形。
- **建议改法：**
  - 拿到结果后先记“完成”（带哈希），再写原图。启动时扫最近几天“完成”了却没有原图的，记成“原图丢失”；扫没有记录的原图，按哈希对回“中断”的批次，对上的补记“完成”，对不上的列进“不认识的文件”。
  - 写明仓库记录坏了怎么办：坏行另存、跳过并写诊断，不让整个仓库只读。
  - 写明记录文件丢了的后果：那几天的原图归入“来源不明”，不再按书列出；书里的副本不受影响。这一条作为已知限制。

### 8. 作者在 Git 里改动副本后的行为没写：删了会被补回、改了不会被修、冲突标记让副本卡住；缩略图“可选进 Git”与“别的机器能看缩略图”矛盾
- **严重程度：**建议
- **类别：**没处理的边界、修订引入的新矛盾
- **位置：**image-generation-v1.md:89、94、99、106
- **现象：**
  - 89 行：副本的记录与快照“建议提交”，缩略图“可选”。
  - 94 行：别的机器的副本只读，“能看缩略图、能恢复配方”。
  - 106 行：同一个安装 id 在两台机器上撞同一个文件时“按行合并即可”。
- **为什么是问题：**
  - **删自己的副本。**按 99 行的字面，下次对账会把整份补回来。作者要是为了缩小仓库、或者不想把抽卡历史推到公开仓库才删的，删了也没用，提案应当说明这一点，并给一个“这本书不再往副本里写”的办法。
  - **删别人的副本。**本机不会补别人的目录，那台机器的历史在这边就没了。等那台机器拉到这次删除、再对一次账，它会把整份补回来。这是可以接受的，但要写出来。
  - **改自己的副本。**按“批次 id 已在”去重，改过的行留着，不会被修正。删掉的会补回，改掉的不会，两种情形的行为不一致。
  - **冲突标记。**106 行让作者“按行合并”。合并没做完就提交时，文件里留着 `<<<<<<<` 这样的行。照 99 行援引的 canon 做法，中间一行坏就只读（canon/project.md 输出 4），本机这个目录就再也补不进记录，界面上也没有地方告诉作者。
  - **缩略图不进 Git。**`.nbook/images/thumbs/` 不提交的话，别的机器上根本没有 A 的缩略图，94 行的“能看缩略图”不成立。“可选”的后果要写明，或者别的机器的批次也提供“没有缩略图”的显示。
- **如何核实：**按 99 行的去重规则，逐一推演上面四种 Git 操作。
- **建议改法：**
  - 在 `images/library` 写明：副本是仓库的派生物，本机目录以仓库为准修复，删掉的补回、改坏的另存后重写；别的机器的目录只读、不修。
  - 坏行与冲突标记不让整个目录只读：跳过并诊断，在图库页提示。
  - “哪些进 Git”的表里注明：缩略图不进 Git，别的机器上就只有记录、没有图。

### 9. 第 3 节仍写“发出去，同时记进书里”，与“只靠对账进书”相反；排队中的批次没有记录，服务端重启时会无声消失
- **严重程度：**建议
- **类别：**修订引入的矛盾；第 2 轮第 3 条没到位
- **位置：**image-generation-v1.md:98、184、228
- **现象：**
  - 184 行（第 3 节“展开”第 5 步）：“发出去。同时记进书里：这一批展开后的每一节；配方当时的样子……”。
  - 98 行：书里只有对账补进来的副本，仓库在“调后端之前”才记“已提交”。
  - 228 行：全局队列，“关掉标签页或窗口都不丢结果”。
- **为什么是问题：**
  - 照 184 行实现的人会在项目实例里提交时就写一行，书里就有了不经仓库的第二条写入路径，这正是这一轮要消掉的结构问题。第 2 轮第 3 条指出了这两种说法，处理表写“改”，但第 3 节没跟着改。
  - “已提交”在调后端之前才写，排在队里、还没轮到的批次在仓库里一行都没有。服务端重启或崩溃时，这些批次既不算“中断”，也不留痕迹，作者看到的就是点了生成、什么都没发生。全局队列跨书、跨窗口，排几十批是正常情况。
- **如何核实：**对照 184 行与 98 至 99 行；按 98 行推演“排队 10 批时重启服务端”。
- **建议改法：**
  - 184 行改成“交给服务端入队；记录由仓库写，经对账进书（第 1 节）”。
  - 入队时就在仓库记一行“排队”（带配方快照）。服务端重启时，停在“排队”的记为“未发出”（没扣点数），停在“已提交”的记为“中断”，两者在界面上分开显示。

### 10. id 索引存在哪没写；`.image` 没有“打开”这一步，重复的图片 id 永远没人问；`image.json` 有三个写者，没定期望
- **严重程度：**建议
- **类别：**没写出来的假设、并发；第 2 轮第 6 条没到位的部分
- **位置：**image-generation-v1.md:258、259、264–266、398
- **现象：**
  - 264 行：项目入口激活时扫描，维护“id 到路径”的索引，“记着每个 id 上次在哪”。
  - 265 行：没有记录时（第一次扫描、换了机器）先不动，“等作者打开其中一份时问一句”。
- **为什么是问题：**
  - **索引存在哪。**只放在内存里的话，每次激活都是“第一次扫描”。项目停着期间出现的重复（Git 拉取、文件管理器复制）每次都落进“先不动”，“路径对得上的是原件”这条规则永远用不上。持久化的话，要写明放哪里，`.nbook/` 还是 Storage 的 project 分区；以及进不进 Git，进 Git 时“换了机器”这一情形就不存在了。
  - **`.image` 不打开。**插图文件夹只在资源管理器里显示、在正文里被引用，没有“打开”。两份同 id 的 `.image` 永远等不到那句问话，按 id 的引用（插图方言的 `<image-generated id>`，351 行）解析到哪一份也没写。第 2 轮第 6 条指出过这一点，这次只改了配方的情形。
  - **`image.json` 的写者。**有三个：
    - 服务端：收进书里、换版本（398 行）；
    - 浏览器：插件里的“改名”只改说明（259 行）；
    - 项目入口：换新 id。
    
    三者都经写入接口，可期望没定。用 `any` 时后写的覆盖先写的，例如改名与换版本同时发生，丢掉一样。
- **如何核实：**全文搜“索引”，只有 264 至 265 行，没有存放位置；对照 351 行的解析规则。
- **建议改法：**
  - 写明索引存在 Storage 的 project 分区（随项目、不进 Git），坏了能重建。
  - 遇到重复的 `.image`，在图库页与资源管理器里提示，作者确认前，解析按确定的规则选一份（例如最先创建的），并给出警告。
  - `image.json` 一律用 `update`，按读到的基线写回（resources.md:124）。

### 11. 按哈希去重后，一个原图文件可能属于几批、几本书，可“扔掉”“清理”“按书列出”都按“一张一主”写
- **严重程度：**建议
- **类别：**没写出来的假设
- **位置：**image-generation-v1.md:246、252–253、268、291、294
- **现象：**
  - 246 行：原图“按 SHA-256 命名……同一张只存一份”。
  - 291 行：“一张原图只属于生成它的那本书”。
  - 268 行：扔掉是对“这张”的标记，清理时“先清扔掉的”。
- **为什么是问题：**
  - 去重既然写进了合同，就说明同一份字节可以出自两批：同一个种子加同样的参数重抽，或者两本书用同一份配方。后端是否每次交回完全相同的字节，要看 NovelAI 写在图里的元数据带不带时间，这一点没验证。
  - 一旦出现，就有三处冲突：
    - 在 A 批扔掉，清理会删掉 B 批（也许还在 7 天保护期里，也许被收藏了）也在用的文件；
    - “按书列出”会把同一个文件算进两本书，或者只算进其中一本；
    - 书里的缩略图也按哈希命名，扔掉 A 批时删缩略图，会连 B 批的一起删。
- **如何核实：**对照 246 行与 291、268 行。
- **建议改法：**
  - 写明删一个原图文件的条件：引用它的每一批的这一张都可清（扔掉，或者过了保护期且没收藏）。收藏的钉住按哈希算。
  - 按书列出时，一个文件被几本书引用就在每本下都列，合计只算一次。
  - 或者干脆不跨批去重：文件名加上批次 id，这样“一张一主”就是真的。

### 12. 两处显示没写数据从哪来：历史的“在书里”角标，“图片空间”里“书里的图单列一行”

- **现象：**

  - 271 行的历史仍有“在书里”角标。
  - 290 行的“图片空间”里，书里的图“单列一行，只显示”。
- **为什么是问题：**
  - **角标。**只能由项目入口扫 `.image/image.json` 里各版本的来历快照，按哈希对回批次。可第 6 节没把“来历快照里带批次 id 与哈希”列成 `image.json` 的必有字段，第 1 节的项目入口职责里也没有这一项。
  - **单列一行。**“图片空间”在设置里，跨书显示。要算每本书里 `.image` 的体积，服务端得列出每本书的文件。经 `projects://` 列出会给每本书取租约、把没在运行的项目都打开（resources.md:135），等于打开设置就启动全部书的子进程，与拓扑提案“不得为了一次请求启动项目子进程”的精神相反（multi-instance-runtime-topology.md:112）。

  - 290 行写明“缩略图”指仓库里的那份。

### 13. 别的机器生成的批次在本机不能扔掉，失败品在历史里永远藏不掉
- **严重程度：**建议
- **类别：**遗漏（边界）
- **位置：**image-generation-v1.md:94、268
- **现象：**94 行只说别的机器的批次不能收藏、不能收进书里。268 行的扔掉是“在仓库里标成扔掉”，而仓库只认本机的批次。
- **为什么是问题：**两台机器合写一本书时，B 上的历史和图库里永远混着 A 抽出来的失败品，B 没有办法把它们藏起来，只能回 A 上去扔。94 行没把“扔掉”列进不能做的事，照字面实现的人会在 B 上给 A 的批次写一个扔掉标记。可写到哪里？B 的仓库里没有这一批，B 的副本目录又只放 B 生成的批次。
- **如何核实：**按 94、268 行推演 B 上对 A 的批次点“删掉这张”。
- **建议改法：**二选一写明。
  - 不能扔，按钮停用，提示“在生成它的机器上扔掉”；
  - 或者另设“本机隐藏”，只影响本机的显示，不传播。

### 检查过、没有发现问题的方面
- **项目没在运行时“收进书里”：**仔细检查后没有发现问题。`projects://` 的写入会取得租约、把没在运行的项目打开（resources.md:122、135），所以 Agent 以后从对话里触发、项目没开时也能完成。代价只是多打开一次项目（约 0.3 到 0.5 秒，projects.md 第 12 条），以及第 5 条的来源问题。
- **书在别的机器上收进书里，会不会影响本机清原图：**仔细检查后没有发现问题。收进书里是复制，书里那份与仓库无关；别的机器只能收进它自己生成的批次（94 行），本机仓库不知道、也不需要知道。本机清掉原图，不影响任何一本书里的 `.image`。
- **“属于本书”靠项目 id：**仔细检查后没有发现问题。项目 id 写在作品目录的 `.nbook/project.json`，移出书架再登记、换机器克隆都还是同一个 id；复制出来的目录登记时得到 `identity-conflict`（projects.md 术语与验收 1）。两个状态根同时打开同一本书时，安装 id 不同，不会写同一个文件。
- **服务端写 `projects://` 与项目入口换新 id 的竞争：**图片 id 由服务端新生成，不会与已有的撞。剩下的只是 `image.json` 的期望问题，已并入第 10 条。
- **第 2 轮第 14 条（宽限期内回来）：**读历史时对账可以兜住，已到位。
