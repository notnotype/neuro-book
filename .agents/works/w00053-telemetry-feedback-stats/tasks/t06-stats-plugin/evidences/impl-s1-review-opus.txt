## 1. [重要] 正确性：lifecycle.failure 在真实运行时里永远取不到码，三个机制事件里它那一份是死代码
- 位置：store.ts:50（MECHANISM_EVENTS 含 "lifecycle.failure"）、store.ts:438（取码）；对照 store.ts:468-477（mechanismObservers.lifecycle.failureRecorded）与 lifecycle/scope.ts:70（summarizeFailure）
- 现象：lifecycle.failure 记录的 data 只有 {sequence, phase, stage, attempt, resourceId}，没有 reason，也没有 plugin；它的 error 是 summarizeFailure 产出的 FailureError {name, message}，宿主错误的 code 在这一步已经被丢掉。所以三个来源对它全部落空。经真实 createApplication 探针（/tmp/review-w00053-t06-s1/lab/probe/real-runtime.test.ts）：一个 activate 抛 Object.assign(new Error,{code:"ELOCKED"}) 的插件、一个 release 抛 code "EBUSY" 的资源，lifecycle.failure 共 4 条（warn 2、error 2），交到观察者的 2 条全部是 code=undefined、plugin=null；记录里 error 也只剩 {"name":"Error","message":"boom"}。同样，plugins.diagnostic 与 services.diagnostic 的 error 也是 FailureError，第三个来源“错误对象的 code”对所有机制事件都不可能命中，只对业务插件直接 record 的 Error 有效。
- 为什么是问题：Spec 写“生命周期、服务与插件三类机制事件的 reason”，实现把 lifecycle.failure 列进来，读者会以为释放、关闭失败能按码计数；实际 error 级的 lifecycle.failure（释放与关闭失败，正是“收口停在停止中”的那类）进不了 3.3 的错误码计数（那里只数带 code 的）。设计审查第 2 条要的“内核失败数得到”在这一类上没有做到，而现有用例只用手造的 plugins.diagnostic 记录验证了 reason，lifecycle 那条只测了插件回退为 null，所以测试全绿。
- 如何核实：跑上面的探针；或读 store.ts:474 与 scope.ts:70-84。
- 建议改法（交主会话取舍）：要么给 lifecycle.failure 一个码来源（例如 data.stage 映射成 "acquire-failed"/"release-failed"/"close-failed"，写进 Spec 第二来源的定义），要么让 summarizeFailure/FailureError 保留合格的 code（改 lifecycle 合同，影响面大）；至少从 MECHANISM_EVENTS 的注释与 Spec 里把 lifecycle 的“reason”删掉或写明它没有 reason，并在用例里放一条经真实 lifecycle 机制产生的失败，断言它交出的码。

## 2. [重要] 正确性：data.plugin 回退对真实机制记录从不生效；真正缺插件的 services.diagnostic 被记到 runtime 名下
- 位置：store.ts:437（plugin 回退）、store.ts:486-500（services.diagnostic 的 data 与 source）、store.ts:510-526（plugins.diagnostic）
- 现象：三个机制事件里只有 plugins.diagnostic 的 data 带 plugin，而它的 source.plugin 与 data.plugin 取自同一个 diagnostic.plugin（source 为 null 时 data 也为 null），所以“来源没有插件就用 data.plugin”这条分支对真实记录永远不会改变结果；lifecycle.failure 与 services.diagnostic 的 data 里没有 plugin。探针里 x.provider 的服务初始化失败：error 级 services.diagnostic，reason=initialization-failed，data.key="x.provider/svc"，data.entryId="plugin:x.provider/main@4:x.provider/svc"，交出的 origin.plugin=null。按计划 3.3 它会记成 "runtime:initialization-failed"，而插件 id 明明可以从 key 前缀得到（registration.ts:95 强制服务键以 "<插件 id>/" 开头）。
- 为什么是问题：设计审查第 2 条(d) 要的是“机制事件的失败归到插件”，实现只做到字面（data.plugin），对唯一真正缺插件的那类事件没有效果；“来源里没有插件而机制事件的数据里有插件 id 时用它”的用例（diagnostics.test.ts 第 418 行附近）只用手造记录证明分支存在，证明不了行为。
- 如何核实：跑探针，看 services.diagnostic 那一行；或读 store.ts:486-500。
- 建议改法：services.diagnostic 的插件从 data.key 按 "<插件>/" 前缀取（或在 mechanismObservers 里直接把它写进 source.plugin，这样查询的 plugin 过滤也受益），并把 Spec 那句改成实际的规则；用例改用真实 createApplication 让一个提供者初始化失败，断言 origin.plugin。若决定不做，至少删掉 data.plugin 这条对真实记录无效的分支或在注释里写明它只服务手造记录。

## 4. [建议] 安全/不变量：异步观察者的 reject 逃出 #deliver，成为进程级 unhandledRejection；服务端会因此 fatal 停机，observerFailures 不加
- 位置：store.ts:413-421（#deliver 只 try/catch 同步抛错）；contracts.ts 的 `type DiagnosticObserver = (observation) => void`
- 现象：`(o) => void` 在 TS 里接受 async 函数，`const o: DiagnosticObserver = async () => { throw … }` 能通过类型检查。探针 /tmp/review-w00053-t06-s1/lab/probe/async-observer.test.ts：record 照常返回 accepted，但 rejection 从 #deliver → #observe → record 的栈上冒成未处理的 rejection（bun test 直接把用例判失败，错误栈指向 store.ts:415），observerFailures 仍为 0。nb-host 的 server/host.ts:93 对 unhandledRejection 走 #fatal → requestStop("fatal:unhandled-rejection")，即整个服务端停机。
- 为什么是问题：Spec 写“观察者抛错不影响记录调用的结果与各出口，只计入状态里的观察者失败次数”；DiagnosticsService 经 SDK（packages/neuro-book/src/sdk/index.ts:35）交给第三方插件，写成 async 的观察者是很自然的错误，后果从“计一次失败”变成“进程退出”。
- 如何核实：跑探针；读 server/host.ts:92-93、120-126。
- 建议改法：#deliver 里看返回值，是 thenable 就挂 `.then(undefined, () => { this.#observerFailures += 1; })`（不 await，仍是同步交付），并在 DiagnosticObserver 的注释里写明返回的 Promise 不被等待、其失败只计数；补一条 async 观察者 reject 的用例。

## 5. [建议] 不变量：登记不随调用方的激活收口，忘了撤销的入口在停用、重载之后仍被同步调用
- 位置：plugin.ts:70、76-84（诊断服务用 provideService 共享一份，observe 直通 store）；store.ts:150-180
- 现象：observe 的登记挂在 store 上，只能靠调用方自己把撤销函数登记到 context.scope（测试 diagnostics.test.ts 第 520 行附近就是这样手写的）。没有这样做的插件入口被停用、换代（generation 递增）之后，旧代码里的观察者仍在每条记录的同步栈里执行，并持有旧激活的闭包；内核里已有 provideServicePerConsumer（plugins/plugins.ts:40-45，“release 在该调用方的这次激活结束时调用”）专门解决这类按调用方收口的问题。
- 为什么是问题：这是本运行时其它订阅类能力（贡献、远程订阅）都由宿主按激活收口的既有约定；observe 是第一个让任意插件代码进入 record() 同步栈的入口，又经 SDK 对第三方开放，漏撤销的代价是“已停用插件的代码继续跑”，测试与类型都提示不出来。
- 如何核实：读 plugin.ts:60-84 与 plugins/plugins.ts:40-60；写一个激活时 observe 不撤销的插件，停掉它的入口后再 record，观察者仍被调用（从代码推断，未跑）。
- 建议改法：诊断服务改用 provideServicePerConsumer，门面里的 observe 把登记记在该调用方名下，release 时统一撤销（record/query/status 照旧直通）；这是改上游的做法，代价是门面每个调用方一份。若决定不改，至少在 observe 的注释与 Spec 里写明“调用方负责在激活收口时撤销”。

## 7. [建议] 交付形状：来源里的空串插件原样交出，与 data.plugin 回退的“空串当没有”不一致
