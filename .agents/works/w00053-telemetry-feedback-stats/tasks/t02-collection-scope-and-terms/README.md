# 遥测收集范围与条款

## 目标与范围

与开发者讨论匿名使用统计收集哪些数据、不收集什么、保留多久，以及给用户看的说明与条款怎么写；结论写进提案与 Spec。服务端落在新官方站的统计模块（w00037）。

合同：只做讨论，行为合同未变；结论写进 w00053 的提案与新 Spec，并遵守 [`runtime/diagnostics`](../../../../../docs/specs/runtime/diagnostics.md) 的“诊断不联网”边界（遥测是独立插件与独立通道）。

## 数据清单与能做的分析（主会话，2026-11-24，未经开发者确认）

### 一、收什么

**匿名档，每天最多一份**（默认发，有独立开关）

1. 应用版本、发行渠道、运行形态（桌面、命令行、网页）
2. 操作系统及大版本、架构
3. 界面语言
4. 大区（客户端由本机时区换算成七八个取值之一，不发时区本身）
5. 距上次上报过了几天（分档）
6. 安装所在周
7. 使用统计、自动发送诊断这两个开关各自是否开着
8. 首次启动向导的结果（完成、跳过、还没走）

**匿名档，在线心跳**（应用开着时每 15 分钟一次）：应用版本、运行形态。服务端只累加计数。

**一级 使用统计**（要同意；随每天那一份一起发，不带持久标识）

1. 功能使用：固定名单里每一项当天的使用次数分档（写作编辑、Agent 对话、世界设定、剧情、图像、bot、定时任务、文件管理、联网工具、第三方插件管理等，名单公开）
2. 每一项功能距上次使用过了几天（分档）
3. 里程碑，这份安装至今是否做过：建过项目、写满一千字、配过模型、发过第一次 Agent 请求、装过第三方插件、登录过官方站
4. Agent 用量：会话数、请求数、失败请求数、工具调用数、输入与输出与缓存 token，都是分档；模型提供方类别；公开名单内的模型名及其请求数分档
5. 稳定性：按“拥有者加错误码”的次数、崩溃次数、升级结果（成功或失败及失败码）
6. 耗时分档：启动、打开项目、Agent 首次回应
7. 规模分档：项目数、最大一部作品的字数、总字数、当天净增字数、累计活跃天数
8. 第三方插件数量分档、界面主题（内置名单内的名字，其余记“自定义”）

崩溃与升级失败另在下次启动时立即补发一条，只有错误码与次数。

**二级 诊断报告**（要同意）：错误码、堆栈（函数名与行号）、去掉用户名的路径、出错前的操作类别序列（不含内容）、应用版本与环境。

**三级 含内容的反馈**（每次确认）：用户写的文字、类别、用户选择附上的日志片段与截图与对话片段、用户愿意留的联系方式、应用版本与环境。

**账号档**（登录后，官方站）：用户名、显示名、邮箱、密码哈希；Google 或 GitHub 的账号标识与公开资料；注册时间、用的注册码与邀请人；会话（创建时间、最后活跃、IP、浏览器标识）；已登录的设备（设备名、应用版本、最后活跃、是否在线）；授权过的 OAuth 客户端；管理操作的审计记录。

**永不收**：正文、设定、提示词、对话内容、文件名、项目名、本机路径（诊断报告里的路径去掉用户名）、密钥、模型服务的地址、硬件指纹；匿名档与一级不存 IP、不带持久标识、不与账号关联。

### 三、回答不了的

1. **按天的精确留存**（次日、7 日）：只有按周的。要精确到天得把“安装所在周”换成“安装日期”，取值变多、更容易区分出某个安装。
2. **操作的先后与漏斗**：没有事件流，只能用里程碑近似。
3. **同一个安装跨天的变化**：没有持久标识，看不到“这个人上周用 A、这周改用 B”。
4. **国家一级的地域**：只有大区。要国家得让服务端按 IP 查国家后只存国家代码。
5. **一级的样本取决于同意率**：开关默认不勾选，同意的人可能只占一小部分，功能、Agent、稳定性这些结论只代表同意的人。匿名档里的“开关是否开着”能告诉我们这个比例。
6. **第三方插件各自的使用量**：只收数量，等市场上线再定。
7. **写作的题材、体裁、内容特征**：不收。

### 四、主会话的判断

第一版够用：增长、留存、版本、平台、在线、同意率不依赖同意，一定拿得到；功能与稳定性的结论要看同意率。同意率过低时的退路，是把一两个是否项（例如“当天是否用过 Agent”）挪进匿名档，届时另行决定并更新告知。

## 第四版：按“能不能认出人”分级（主会话，2026-11-24，未经开发者确认）

分界不在数据属于哪个功能，而在三件事：能不能把两次上报认成同一个人、里面有没有用户写的内容、有没有绑到账号。个人信息保护法第四条把匿名化处理后的信息排除在个人信息之外，第七十三条把匿名化定义为“无法识别特定自然人且不能复原”。以下是主会话对规则的理解，不是法律意见。

### 不用同意、默认就发的（匿名档）

条件：不带任何持久标识；服务端不存 IP；每一项只有少数几种取值，几项合在一起也不足以把一个安装从人群里区分出来。要在首次启动时告知，设置里有关闭的开关。

- 应用版本、发行渠道、运行形态、操作系统大类与架构、界面语言；
- 距上次上报过了几天、安装所在周（算活跃与留存用）；
- 在线心跳：应用开着时每 15 分钟一次，只带版本与运行形态；服务端只给那个时间段的计数加一，不存单条记录。

### 要同意的，分三级

| 级 | 内容 | 为什么要同意 | 怎么同意 |
|---|---|---|---|
| 一 使用统计 | 当天各功能的使用次数、Agent 的会话数与请求数与 token 分档、模型提供方与公开名单内的模型名、按错误码的计数、启动耗时分档、项目数与总字数分档；仍不带持久标识 | 项目多、组合起来在用户不多时有可能把一个安装区分出来，算不上稳妥的匿名 | 向导里的开关，默认不勾选；设置里随时改 |
| 二 诊断报告 | 崩溃与错误的详情：堆栈、出错时的操作步骤、去掉用户名的路径 | 堆栈与路径里可能带出用户的信息 | 可以给一个“以后自动发送”的开关，默认关；没开时每次崩溃后问一次 |
| 三 含内容的反馈 | 用户写的反馈文字、Agent 代写的反馈、用户选择附上的日志片段、截图、对话片段 | 是用户写的内容 | 没有长期开关，每一次提交都要用户看过并点确认 |

### 登录后的（账号档）

- 账号本身：用户名、邮箱、Google 或 GitHub 的账号标识、密码哈希、会话与登录 IP。依据是用户注册时主动同意服务条款与隐私政策，以及提供账号服务所必需（第十三条第二项）。
- 已登录的设备：设备名、最后活跃时间、是否在线。是给用户自己看的功能，写进隐私政策的账号一节。
- 这一档的数据不与匿名档、使用统计关联。同时在线人数用匿名档的心跳算，不用账号数据。

### 级别能不能自己定

能。法规不规定分几级，只规定几条边界：

1. 每一级写清目的与数据清单，处理前以显著、易懂的方式告知（第十七条）。
2. 同意要用户主动作出，不能预选（第十四条；国家标准把主动勾选、主动点击作为明示同意的动作）。
3. 不同意不能影响基本功能（第十六条）；几个不同目的不能捆成一个“全部同意”。
4. 撤回要与同意一样方便（第十五条）。
5. 目的、方式、数据种类变了，要重新取得同意（第十四条）。
6. 法律点名要“单独同意”的不能并进普通级别：敏感个人信息（第二十八、二十九条，含不满十四周岁未成年人的信息）、提供给别的处理者（第二十三条）、公开（第二十五条）、向境外提供（第三十九条）。

### 两处要另外留意

- **服务器在境外时的账号数据。** 匿名档与使用统计不带标识，不涉及个人信息出境；账号档的邮箱等是个人信息，生产主机若在境外，适用第三十八、三十九条（告知并取得单独同意，另需满足出境条件）。这一条要在写隐私政策之前查清并找人确认。
- **欧盟。** 欧盟的规则管的是“读取并外发设备上的信息”，不以是否个人信息为界；严格按它，匿名档也要同意。第一版按国内的口径做，面向欧盟分发时再评估按地区把匿名档也改成默认关。

## 调研（2026-11-24，子代理联网查一手来源，主会话未逐条复核）

- [各产品怎么分档](../../research/2026-11-24-telemetry-tiers-survey.md)：VS Code、Firefox 与 Glean、Go、Homebrew、Syncthing、Next.js、.NET、Zed、JetBrains、Obsidian，更新检查带出的字段，登录后的数据。
- [上报形态与隐私技术](../../research/2026-11-24-reporting-shapes-survey.md)：Glean、Go 遥测、Aptabase、TelemetryDeck、Plausible、Umami、PostHog、Homebrew、Sentry，以及几种隐私增强的聚合技术。
- [条款与合规](../../research/2026-11-24-terms-and-compliance-survey.md)：个人信息保护法、App 违法违规收集认定方法、GB/T 35273，欧盟的同意规则与 EDPB 指南，Google 与 GitHub 的 OAuth 要求，别人的遥测说明怎么写。它只整理公开资料，不是法律意见。

对设计影响最大的几条：

1. **默认勾选在规则层面站不稳。** 国内：认定方法把“以默认选择同意等非明示方式征求同意”列为未经同意收集，GB/T 35273 把用户主动勾选或点击作为明示同意的动作，个人信息保护法没有“正当利益”这条依据。欧盟：只要依赖同意，预先勾选无效；应用外发设备上的信息（含唯一标识）落入 ePrivacy 第 5(3) 条。这些规则针对的是个人信息或设备上的信息；数据做到匿名化（无法识别到人且不能复原）时，个人信息保护法不把它当个人信息。
2. **随机安装标识很可能算个人信息。** 标准的示例把唯一设备识别码与软件使用记录列为个人信息；没有查到官方说随机标识不算。
3. **不带标识也能数活跃。** Chrome 的更新协议让客户端上报“距上次上报过了几天”，服务端据此算日活、周活、月活，不需要稳定标识。Go 遥测与 Homebrew 都不带标识。代价是算不了按安装的留存，除非上报里带一个粗的“安装所在周”。
4. **混合形态有先例。** Glean 是每天一份汇总，加单独的事件上报，可以逐类决定带不带标识。
5. **基础档与使用档分开控制有先例**（Firefox 的每日使用 ping、VS Code 与 Obsidian 的更新检查），默认开的产品几乎都有先告知的一步（Homebrew 在通知出现的那一次运行里不发数据）。
6. **账号数据与匿名数据是否关联，各家不同**：JetBrains 与 Mozilla 声明分开，Zed 明说登录后可能关联。
7. **Google 登录上线的前置条件**：公开的主页（含功能说明）与同域名的隐私政策，并在 Search Console 验证域名。只用登录所需的基础范围时不强制应用验证。
8. **可照着用的写法**：收集清单带版本号、清单变了就重新告知（Syncthing 重新询问，Firefox 在重新通知前暂停上传）；“我们明确不收集”单独成节；关闭路径写到具体开关并说明关闭的代价；主动反馈里自动附带的内容提交前可见、可取消。

桌面版的自动更新向 GitHub Releases 检查（[桌面发行提案](../../../../../docs/proposals/desktop-distribution.md)），不经过官方站，所以基础信息不能搭更新检查的便车，要单独发一个小请求。

## 第三版（2026-11-24；分档与开关已被第四版修订，其余仍有效）

### 原则：不带持久标识

基础信息与使用统计都不带安装标识，服务端无法把两天的上报认成同一个安装。活跃数靠“距上次上报过了几天”，留存靠“安装所在周”。每份上报带一个只用于重发去重的随机编号，下一份换新的。

- 换来的：数据更接近匿名化，默认勾选的风险明显降低；条款里可以写一句用户看得懂的承诺：“我们无法把你两天的上报认成同一个人”；不需要“重置标识”与“按标识删除”。
- 失去的：不能跨天分析同一个安装（例如“用了 A 的人第二周还用不用 B”）；有人伪造上报时无法按安装去重，只能靠限流。

### 分档

| 档 | 内容 | 何时发 | 默认与开关 |
|---|---|---|---|
| 基础信息 | 应用版本、发行渠道、运行形态、操作系统大类与架构、界面语言、距上次上报过了几天、安装所在周 | 每天最多一次 | 默认开；设置里有单独的开关；首次启动的告知显示之前不发 |
| 使用统计 | 当天的计数：各内置插件的使用次数、Agent 的会话数与请求数与 token 分档、模型提供方类别与公开名单内的模型名、按错误码的计数、启动耗时分档、项目数与总字数分档 | 随基础信息的那一份一起发；升级失败与崩溃在下次启动时立即补发一条 | 向导里的开关；向导被跳过则关 |
| 主动反馈 | 用户写的文字；自动附带的环境与诊断信息在提交前可见、可逐项取消；Agent 代写的反馈要用户点确认 | 用户发起时 | 没有开关，每次都是用户的动作 |
| 登录后 | 账号数据（用户名、邮箱、Google 或 GitHub 的账号标识）；为“已登录的设备”这类功能所需的设备名、最后活跃时间 | 登录期间 | 登录即适用官方站的隐私政策；与前两档的匿名上报不关联 |

### 本机统计

用户自己看的数据（模型使用、字数、日历热力图）在本机的统计插件里，全量、不联网。遥测插件只读其中分档后的白名单子集；设置页“查看将要发送的内容”显示的就是下一份上报。

### 服务端

- 原始上报留 90 天后整月删除；聚合结果长期保留。参照：Homebrew 保留 365 天，法国 CNIL 对免同意的受众测量建议数据最长保存 25 个月。
- 不存 IP；反向代理对写入口不记访问日志里的 IP。
- 收集清单是合同包里的 schema，带版本号与中英文说明；清单变了，客户端在重新告知用户之前暂停上传。

### 条款的结构

1. 应用里的遥测说明：一句话说明目的与能关；分档表；“我们明确不收集”单独一节；每一档怎么关、关了有什么代价；存在哪、存多久；清单版本与变更怎么通知；联系方式。
2. 官方站的隐私政策：处理者与联系方式；账号数据逐项列出各自的用途与保存期限；Google 与 GitHub 登录时取哪些数据、怎么用；Cookie 与会话；怎样查看、更正、删除与注销；变更怎么通知。
3. 主动反馈一节：反馈不公开、只用于改进产品；附带了什么；保留多久。
4. 服务条款：账号规则、禁止的行为、服务可用性与免责。

官方站第一版因此要多三个公开页面：主页（含功能说明）、隐私政策、服务条款；Google 登录上线前要在 Search Console 验证域名。

## 开发者的七点意见（2026-11-24）

1. 收什么可以分等级：不太敏感、也不需要长期持续上报的（安装、操作系统这类）可以默认就收。
2. 要一份“每天一份计数汇总”与“逐条事件流”的比较。
3. 向导被跳过时，同意保持关闭。
4. 有些数据用户自己也想看：模型使用统计、“泳池图”、字数统计。
5. 还要有主动反馈的通道。
6. 还有一档是登录状态：通过 OAuth 登录后有对应的条款，登录后可以收在线状况。
7. 可以派几个子代理调研遥测通常是怎么做的。

## 第二版初稿（主会话，2026-11-24，调研回来前；未经开发者确认）

### 分档

| 档 | 内容 | 默认 | 条款 |
|---|---|---|---|
| 基础信息 | 应用版本、发行渠道、运行形态、操作系统大类与架构；只在安装后首次启动与每次升级后发一次，不带持久标识 | 默认收 | 应用里的遥测说明 |
| 使用统计 | 随机安装标识、活跃、功能使用次数、Agent 用量分档、稳定性计数、规模分档 | 向导里的开关，默认勾选；向导被跳过则关 | 应用里的遥测说明 |
| 主动反馈 | 用户自己写的文字，可选附带他看过并同意的诊断信息；Agent 代写的反馈要用户点确认才发 | 每次由用户发起 | 反馈一节 |
| 登录后 | 与账号关联：已登录的设备、最后活跃时间、在线状况 | 登录即适用 | 官方站的隐私政策与服务条款 |

登录后的数据与匿名的安装标识不互相关联。

### 本机统计与遥测共用一份计数

用户自己想看的数据（模型使用、字数、日历热力图）在本机的统计插件里，全量、精细、不联网；遥测插件只读其中一份分档后的白名单子集。“用户看得到的”包含“发出去的”，设置页的“查看将要发送的内容”就是这份子集。

### 两种上报形态的比较

| | 每天一份计数汇总 | 逐条事件流 |
|---|---|---|
| 能回答 | 多少安装、活跃、留存、各功能用了多少、分布 | 另加操作的先后、漏斗、单次操作的耗时 |
| 隐私 | 没有时间点，整份可以给用户预览 | 带时间序列，能还原一段时间里做了什么，难以预览 |
| 数据量 | 每个安装每天一个请求 | 随使用量增长，服务端分区与聚合压力大 |
| 客户端 | 累计器加每日发送，离线补发按天幂等 | 队列、批量、重试、去重、满了怎么丢 |
| 时效 | 次日才看到 | 接近实时，发版后几小时内能看到崩溃上升 |
| 事后换问法 | 只能看当初定好的计数 | 可以对已有事件换一种方式分析 |
| 条款 | 一张表说清 | 事件目录长、变动多 |
| 与本机统计 | 直接共用计数 | 要再聚合一遍 |

主会话的倾向：以每日汇总为主，另加少数几个立即发送的事件（升级失败、崩溃），补上时效这一项。

## 讨论稿第一版（2026-11-24；已被上面的第二版初稿修订的部分以第二版为准）

### 一、上报形态：每天一份计数汇总

客户端在本机累计计数，每天最多发一次，内容是“这一天、这个安装、每项各多少次”。不发逐条带时间的事件流。

- 好处：用户能看懂也能核对（设置页原样显示将要发送的那一份）；每个安装每天一个请求；不暴露几点几分做了什么。
- 代价：看不到操作的先后与漏斗，只能看量。
- 参照：Go 工具链的遥测是同一思路（只有计数器、按周上报、上报内容公开）。

### 二、收什么

| 类别 | 字段 | 用来回答 |
|---|---|---|
| 安装 | 随机安装标识（本机生成，可在设置里重置，不绑账号与硬件）、首次上报日期 | 有多少安装、留存 |
| 版本与环境 | 应用版本、发行渠道、运行形态（桌面、命令行、网页）、操作系统大类与架构、界面语言 | 升级速度、该优先支持哪些平台 |
| 活跃 | 当天是否启动、启动次数 | 日、周、月活跃 |
| 功能使用 | 每个内置插件当天被用到的次数（按固定名单：Agent 对话、世界引擎、剧情、图像、bot、任务等） | 哪些功能有人用 |
| Agent 用量 | 会话数、请求数、token 量级分档；模型提供方的类别；模型名只报公开名单里的，其余记“其他” | 用量规模、该默认推荐哪些模型 |
| 稳定性 | 错误计数（按“拥有者加错误码”，不带文字与堆栈）、启动耗时分档、升级失败次数 | 哪里最常出错 |
| 规模分档 | 项目数分档、总字数分档 | 性能目标该按多大的书定 |
| 首次启动 | 向导完成还是跳过 | 向导有没有用 |

### 三、绝不收

正文、设定、提示词、对话内容、文件名、项目名、本机路径、密钥、模型服务的地址、账号信息（即使登录了官方站也不关联）、IP（服务端不落库，反向代理对写入口不记访问日志里的 IP）、硬件指纹。

### 四、用户的控制

- 首次启动向导里有开关，默认勾选；点了“完成”之后才发第一份。
- 设置页：开关、收集项说明、“查看将要发送的内容”、重置安装标识。
- 关闭后不再发送；本机已累计、未发送的计数丢弃。
- 以后新增收集类别时提高“收集清单版本”，新版本第一次发送前在应用里告知一次。

### 五、服务端怎么存

- 原始汇总留 90 天后整月删除；聚合结果（不含安装标识）长期保留。
- 收集清单是合同包里的 schema，每个字段带中英文说明；官网的“我们收集什么”页面、应用里的收集项说明与服务端校验都由它生成，三处不会不一致。

### 六、条款怎么写

要两份文字：

1. **应用里的遥测说明**（向导一段话加设置页全文）：收什么（上表）、不收什么、为什么、存哪存多久、怎么关、怎么重置标识、清单变更怎么通知。
2. **官方站的隐私政策与服务条款**：账号数据（用户名、邮箱、Google 或 GitHub 的账号标识、登录 IP 与会话）、Cookie、保留与删除、联系方法。Google 登录上线前，Google 的 OAuth 审核要求公开的隐私政策链接与已验证的域名。

写法：先写“一句话版”，再给完整字段表；用平常的中文，不用法律套话；中英两版；每版有生效日期与变更记录。主会话可以起草，但它不是法律意见。

### 七、合规提示（未做法律审查）

默认勾选属于“默认同意、可退出”。带持久安装标识时，这在欧盟的同意规则下有争议，在国内个人信息保护法下是否构成个人信息也取决于能否识别到人。降低风险的做法已在上面：不存 IP、标识可重置、不关联账号、向导里明示。面向欧盟分发时再评估是否按地区默认不勾选。
