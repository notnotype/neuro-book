[01] 严重程度：阻断   类别：正确性
位置：plan 第 3 节（命令 id `nbook.markdown.<动作>`）；packages/neuro-book/src/plugins/commands/shared/registry.ts:81、:131-134；docs/specs/workbench/commands.md “命名与域词表”
现象：计划把全部编辑命令登记成 `nbook.markdown.bold`、`nbook.markdown.heading-1`、`nbook.markdown.toggle-toolbar` 等，但内置命令 id 的域必须在词表 COMMAND_DOMAINS（view、editor、edit、quick-open、settings、account、project、app、help、files）里。
为什么是问题：`commandDeclarationProblems` 对 `nbook.` 开头的插件，域不在词表时给出“未登记的命令域：markdown”，这一条声明被拒（贡献点校验与命令表登记共用这一份规则）。后果是约 25 条命令一条也进不了命令表，菜单项“命令不在目录里不显示”，工具栏与全部菜单整体不出现。Spec 明说“内置命令的域表示功能领域，不等于提供方插件 id”。S0 的文档改动表里没有改 commands.md 的域词表，也没有改 registry.ts。
如何核实：读 registry.ts:81 与 :131-134；`commands/shared/registry.test.ts:124` 有同类断言。可在 S1 写一条真实注册的测试看到被拒。
建议改法：二选一并写进 S0：(a) 在词表里新增域 `markdown`（改 registry.ts 的 COMMAND_DOMAINS 与 commands.md 的域词表和命令目录，并在计划里列为改动文件）；(b) 把命令放进现有域，例如 `edit`（`nbook.edit.bold` 与已有 `nbook.edit.undo` 同域，且和“撤销、重做复用 nbook.edit.undo”一致）。(b) 不用扩词表，但域名撞“功能领域”的含义要在 Spec 里说一句。另外计划里 `when` 写的 `nbook.markdown.writable` 应是限定名 `nbook.markdown/writable`（public-state 的贡献 id 是 `<插件 id>/<名>`），文中几处点号写法在 S0 写 Spec 时要统一，否则 `when` 引用的键“未登记”，命令永远不可用。

[02] 严重程度：重要   类别：正确性
位置：plan 第 6 节、第 10 节；packages/neuro-book/src/plugins/markdown/web/components/MarkdownControl.vue:155-157、:405-419；node_modules/@tiptap/extension-bubble-menu/src/bubble-menu-plugin.ts（BubbleMenuPluginProps.element、constructor）；node_modules/@tiptap/core/src/Editor.ts:192-222、:132-141（mount/unmount）
现象：BubbleMenu 扩展的 `element` 在扩展配置时就固定（`BubbleMenu.configure({element})`，插件工厂 `view => new BubbleMenuView({view, ...options})` 每次都用这同一个 element）。但 MarkdownControl 的编辑器实例存在组的实例槽里，组件因布局变化重挂时走 `kept` 分支：`editor.mount(root)`，旧组件卸载。Editor.unmount() 会 `editorView.destroy()`，mount() 会 `createView` 重新建全部插件视图，用的还是第一次配置的 element。
为什么是问题：Vue 的 MarkdownBubbleMenu 组件随旧的 MarkdownControl 卸载，它渲染的 DOM 元素（内容是 Vue 渲染的，非响应式）留在插件里；新挂的组件渲染的是另一个元素，插件不认识它。表现是拆分、关闭相邻组让 grid 重建后，选区浮动菜单显示的是死的旧元素（点不动或内容过期）或根本不出现。计划第 10 节说“不改 Editor 实例的生命周期”，但没处理“扩展选项里捕获了组件级 DOM”这一点。块按钮、斜杠菜单若同样把 DOM 或回调在扩展配置时绑定，也是同一类问题。
如何核实：读上列源码；在 dom 测试里让同一个 Editor 实例卸载再挂到新的 MarkdownControl 上，选中文字后检查气泡元素是否是新组件渲染的那一个。
建议改法：气泡的外框 DOM 由 KeptEditor（槽里的实例记录）持有，随编辑器实例一起建、一起销毁；Vue 内容用 `<Teleport :to="外框">` 渲染进去，每个 MarkdownControl 实例挂载时把自己的内容挂到外框、卸载时撤掉。不要用 `registerPlugin/unregisterPlugin` 在控件挂载时动态加：保存在 `binding.slot.state` 里的旧 EditorState 带着旧的插件集，`enter` 里 `updateState(view.state)` 会把动态插件换掉（见 [03]）。回调类的东西（块范围、触发状态交给 Vue）同理走“实例级的可替换回调”，不要在扩展配置时闭包住某个组件实例。

[03] 严重程度：重要   类别：不变量
位置：plan 第 10 节“新插件的状态按文档各一份，视图级的东西在换绑定时清掉”、风险 2；MarkdownControl.vue:158（load）、:195（enter）；node_modules/prosemirror-view/src/index.ts:256-273（updatePluginViews）；node_modules/prosemirror-state/src/state.ts:45-60
现象：计划把“换文档”理解为共用一组插件、只有插件状态各一份。实际上 `EditorState.create({plugins: editor.state.plugins})` 每次都 new 一个 Configuration，`state.plugins` 是新数组。`updatePluginViews` 用 `prevState.plugins != this.state.plugins`（数组身份）判断，所以每次 `load()`（新文档），以及在两个不同 Configuration 的保存状态之间切换（A↔B 的 `enter`），都会销毁并重建全部插件视图（BubbleMenuView、计划的触发插件视图、块按钮插件视图都会 destroy 再 constructor）。
为什么是问题：(1) 计划写的“换文档时菜单残留”风险方向不对：实际是插件视图每次都重建，要保证 destroy 干净、constructor 可重入（事件监听、定时器、交给 Vue 的“当前块/触发”状态必须在 destroy 时清空，否则 Vue 持有的是旧视图的数据）。(2) BubbleMenuView 的构造函数会 `getShouldShow()` 并直接 show：切回一个存着非空选区的标签，焦点一回来（focusHandler 的 setTimeout）就弹出气泡，切标签时闪一下。(3) 每次切标签都重建 DOM 监听，成本小但要有人负责释放。
如何核实：在 dom 测试里给插件视图加一个 constructor/destroy 计数，对同一 Editor 先 load 再 enter 另一份状态，看计数；或读 prosemirror-view 的 updatePluginViews。
建议改法：S1 的那条“换绑定后菜单都收起”测试改成真实判据：A、B 两文档来回切，插件视图 destroy 后 Vue 里的菜单状态为空、气泡不因恢复选区而弹出；气泡的 shouldShow 加“用户刚做出选择”的条件（见 [05]），不能只看选区非空。第 10 节的描述改成事实。

[04] 严重程度：重要   类别：正确性（合同缺口）
位置：plan 第 2、3 节（`enabled` 用 `editor.can()`、命令 `when` 只要求 writable）；docs/specs/workbench/commands.md “可用性求值”；menus.md 输出 2
现象：计划说格式动作在代码块、原样块里“不可用，按钮置灰”，来源是动作目录里每个动作的 `enabled(editor)`。但命令的可用性只有一个口径：声明里的 `when`（公开布尔键的 all-of 正条件）。第 3 节给命令的 `when` 只写了 `writable`，公开键只有 `active`、`writable` 和每个动作的“已勾选”布尔键，没有任何键表示“这个动作此刻能不能做”。
为什么是问题：(1) 命令面板、插件贡献的菜单项、Agent 以外的所有命令触发面都按 `when` 判断，代码块里的光标下粗体命令仍列在面板里、可点，执行时 `run` 返回“没生效”，计划没写这时 CommandResult 是什么码和原因（commands.md 规定失败必须结构化，面板与快捷键执行失败还会弹通知，需要原因文字）。(2) 工具栏按钮、右键菜单的置灰若直接读 `editing.state`，就出现“同一动作两套可用口径”：内置按钮灰、同一条命令从命令面板却可用。(3) 约 25 个布尔键里是“勾选态”，没有“可执行态”，插件贡献的菜单项（菜单项禁用取命令的 `when`）永远不会因代码块而灰。
如何核实：读 commands.md “可用性求值”和“执行顺序”（`when` 是执行前的固定一步）；计划第 3 节没有任何 `can*` 键或对应的 `when.requires`。
建议改法：不要一动作一个“可执行”键（会翻倍）。按可用性分类发粗粒度布尔键，命令的 `when.requires` 引用它们：例如 `canFormat`（行内格式能用：不在代码块、原样块）、`canConvertBlock`（块类型转换能用）、`hasSelection`。再规定 `run` 在条件失效时返回 `{ok:false, code:"unavailable", reason: 文字引用}`，工具栏、菜单一律读命令的可用性（`commands.isEnabled`），不再另读 `editing.state.enabled`。动作目录里的 `enabled` 只留给 `run` 内部做最后校验。

[05] 严重程度：重要   类别：不变量（首屏体积、包边界）
位置：plan 第 2、3 节（动作目录在 `nb-markdown/src/editor/editing-actions.ts`，`markdown/web/editing/commands.ts` 与 `state.ts` 登记命令和键）；markdown/web/plugin.ts 文件头注释；nb-markdown/src/editor/index.ts
现象：`markdown/web/plugin.ts` 的头注释明确一条设计：nb-markdown 的组件、语法模块、解析器与编辑内核“只从 .vue 组件引用，入口本身不引它们，所以首屏不含它们”。计划把命令声明放在 `markdown/web/editing/commands.ts`（由 plugin.ts 静态引用），声明要从动作目录取 id、标题、图标、快捷键文字；而目录文件“纯 Tiptap”，与 `run/active/enabled` 写在同一处，从 `@notnotype/nb-markdown/editor` 导出（该入口的 index 还导出 `createMarkdownEditorExtensions`）。
为什么是问题：插件入口一旦静态引用该目录，Tiptap core/pm/StarterKit 与（间接的）语言模块就进了首屏 chunk，违反上面这条已有设计，也让后端类型检查展开浏览器插件时多展开一批类型。计划没有提这件事，也没有首屏体积的验收。
如何核实：看 plugin.ts 头注释；在实现后用构建产物检查入口 chunk 是否含 `@tiptap/core`（或 vite 的 manualChunks 报告）。
建议改法：动作目录分两份：纯数据的（id、分类、参数 schema、图标、快捷键文字，不 import Tiptap）放 nb-markdown 的一个无 Tiptap 的子入口或 nbook 的 `markdown/shared/`，供命令声明、菜单与 Spec 对照；带 `run/active/can` 的实现留在 `.vue` 能到达的懒加载路径。命令的 `run` 本来就走 `editing.run(id,args)`，不需要静态引用实现。S1 加一条“入口 chunk 不含 Tiptap”的检查。

[06] 严重程度：重要   类别：正确性
位置：plan 第 4、5 节（工具栏按钮状态由公开键给出）；第 1 节“目标取活动控件”；EditorGroup.vue:252-253；editor/web/state.ts（active、writable 都按活动组）
现象：工具栏是每个 MarkdownControl 自带的，拆分后每个 Markdown 组一份。按钮的勾选态与可用性来自 `nbook.markdown/*` 公开键，而这些键只反映“活动组”的控件。
为什么是问题：拆分成左右两个 Markdown 组时，非活动组的工具栏显示的是活动组光标处的粗体/标题状态与活动组的 writable（例如活动组可写、非活动组是只读文档，非活动组的按钮仍是可用样子）。点击时 pointerdown 先 `focusGroup` 再执行，所以执行目标是对的，但点之前看到的状态是错的，键盘 Tab 进入或悬停提示也是。计划只写了“点按钮之前已把这一组设为活动”，没有处理显示。
如何核实：计划第 3 节“由 connectActiveControl 给出的句柄的 editing.state 算出”只有活动句柄一个来源。拆分两个 Markdown 组实测即可（e2e）。
建议改法：工具栏读自己控件的 `editing.state`（控件内部直接拿，不经公开键），公开键只服务命令的 `when`、插件菜单项与命令面板；执行仍走命令（先 `focusGroup`）。非活动组的工具栏要么按自己控件的状态显示，要么整体置灰直到点进去，计划里写死其一，并在 e2e 里加“拆分后非活动组的粗体状态不被活动组带偏”。

[07] 严重程度：重要   类别：正确性
位置：plan 第 1 节（connectActiveControl）；editor/web/plugin.ts:100-110（依赖 markdownKey）、:236-251（activate 返回）；editor/web/area.ts:460（activeHandle）；markdown/web/plugin.ts
现象：两个插件的依赖和激活顺序其实支持计划的方向（editor 依赖 markdownKey，markdown 先激活，editor 激活时才能调 connect）。但计划没有写：(a) 释放时机：editor 的 activate 只有 `context.signal` 的 abort 可挂，计划没写“abort 时调返回的释放函数”；(b) markdown 先于 editor 激活，`nbook.markdown/*` 公开键和命令在 editor 连上之前就已登记，此时读到的是“未连接”，必须当 false，不是抛错；(c) 同一个 MarkdownService 对象在 editor 停止后重新激活时被再次 connect：旧连接没释放就连新连接时是覆盖还是报错没定；(d) `EditorControlHandle` 的 `editing` 字段需要 `editor/shared/contracts.ts` 引 `markdown/shared/contracts.ts` 的 `MarkdownEditing`，而 `markdown/shared/contracts.ts` 为了 `connectActiveControl(source: () => EditorControlHandle|null)` 又要引 editor 的类型：两个 shared/contracts 互相 `import type`。type-only 在 TS 里不报错，但这是 plan 自己说“不可接受就挪”的那一条，且这样 `nbook.markdown` 的公开合同第一次依赖 `nbook.editor` 的合同，方向与“editor 依赖 markdown”相反。
为什么是问题：这些都是后续切片“照字面实现会返工”的地方；(a)(c) 不写，插件热停启后命令仍指向已释放的控件。
如何核实：读两个 plugin.ts 的 dependencies 与 activate 返回；区内 `activeHandle` 是 computed，source 在 computed 里读是响应式的，这一点计划成立。
建议改法：见 [08]（更简单的做法）。若仍保留 connect：写明 connect 只允许一个来源（第二次 connect 抛错或后者替换前者并释放前者）、`source` 在 computed 里读、editor 在 `context.signal` abort 时释放；`MarkdownEditing` 的形状放 editor 的 shared/contracts（markdown 不 import editor 合同，用泛型或最小结构 `{editing?: unknown}` 接收），避免互相引用。

[08] 严重程度：建议   类别：代码质量（更简单的做法）
位置：plan 第 1 节“限制”、第 3–4 节
现象：为了让命令与五个菜单位置归 `nbook.markdown`，计划造了一个反向连接、一个 `MarkdownEditing` 句柄形状、markdown 插件新增对 commands、state、settings、workbench 菜单、编辑器设置分区的依赖（视图菜单勾选项、`nbook.markdown/toolbar` 设置、五个菜单位置、公开键、命令，全在 markdown 里）。这是在迁就“Markdown 控件放在 nbook.markdown、editor 又依赖它”这个上游拆分。
为什么是问题：这个上游决定的理由是首屏懒加载（见 [05] 引的头注释），并不要求命令与菜单位置也在 markdown 里。`nbook.editor` 本来就拥有“活动组 → 活动控件句柄”的全部机制、`editor.title`/`editor.tab-context` 两个菜单位置、设置分区 `EDITOR_SECTION`、视图菜单项和 `nbook.editor/*` 公开键，并且已经依赖 commands、state、settings、workbench。把命令/菜单位置/公开键放进 `nbook.editor`，`EditorControlHandle.editing` 是 editor 自己合同里的可选字段（MonacoControl、HtmlPreview 照样可以以后提供自己的 `editing`），不需要 connectActiveControl，不需要 markdown→editor 的反向类型，设置分区也不必借用别人的（markdown 没有设置分区，计划写“照 breadcrumbsSetting”，但那个设置的 section 是 `EDITOR_SECTION`，markdown 要用就得 import editor 的 shared/settings，又是一条反向依赖）。
如何核实：对比 editor/web/plugin.ts 的依赖列表与 markdown/web/plugin.ts 的依赖列表。
建议改法：向开发者提“把命令、公开键、菜单位置、显隐设置归 nbook.editor（命令域选 edit 或新增 markdown 域）”作为候选，代价是 editor 合同里出现“编辑动作”的概念，但它是控件能力的泛化（`editing` 能力），不是 Markdown 专有。若坚持归 markdown，则回答 [05]、[07] 的问题。上游选择“命令与菜单跟着控件所在插件”没有记录的理由（Task README 与 plan 都只写了依赖方向）。

[09] 严重程度：重要   类别：正确性（数据）
位置：plan 第 5 节（工具栏“清除格式”）、选区菜单（决定 10 的“清除格式”）；plan 第 2 节没有列这个动作；packages/nb-markdown/src/language/syntax/comment/index.ts:102-135（`comment` 是 Mark）、ruby/text-marks 同为 Mark
现象：计划里“清除格式”没有定义。最顺手的实现（Tiptap `unsetAllMarks`，即 `tr.removeMark(from, to)`）会移除选区内的全部标记，包括 `comment`（批注）、`markdownRuby`（注音）、`link`（t09 之后的链接）。
为什么是问题：批注是审阅数据，不是“格式”；用户在带批注的段落上点“清除格式”，批注被静默删除，写回后文件里的 `<comment>` 标签消失，撤销之外没有恢复路径。选区菜单、工具栏、命令面板三处都有这个动作。块级“清除格式”（`clearNodes`）还会把提示块、引用、对齐、批注块一并拆开，计划也没写。
如何核实：在 dom 测试里对带 `comment` 标记的选区执行候选实现，读回 doc。
建议改法：S0 的 Spec 写明“清除格式”只移除哪些标记（粗体、斜体、删除线、行内代码、文字颜色、高亮、上标、下标，列成明确集合），保留 `comment`、`link`、`markdownRuby`；是否同时清块级（标题→正文）单独定，默认不清。测试用带批注的段落断言批注仍在。

[10] 严重程度：重要   类别：正确性
位置：plan 第 6 节 + 风险 1；node_modules/@tiptap/extension-bubble-menu/src/bubble-menu-plugin.ts（默认 shouldShow、updateDelay=250、show/hide、blurHandler、transactionHandler）
现象：读了源码，计划里留给 S3“先核对”的结论现在就能下：(1) 默认 shouldShow 只看“有焦点、选区非空、可编辑”，没有鼠标状态，拖选过程中每次选区变化后 250 ms 防抖就会弹出，与 `r2-bubble`“松开鼠标后出现”不符；(2) `shouldShow` 只在编辑状态更新时调用，松开鼠标不产生事务，所以只在 shouldShow 里判断“鼠标是否按下”，松开后气泡不会出现，要额外派发事务或 meta，而 meta `'show'` 会绕过 shouldShow；(3) 插件没有“按 Esc 收起”“打字时收起”的状态，要自己写一份状态机；(4) `show()` 把元素 `appendChild` 到编辑器父元素、`hide()` 把它 `remove()`，元素 `tabIndex` 被设成 0，blur 时是否隐藏取决于 `relatedTarget` 是否在 `element.parentNode` 里。

(c) 快捷键：计划让 Ctrl+B 等继续由 Tiptap 处理、命令不写 `keybinding`，“按钮提示里的快捷键文字写在动作目录里”。这有两个后果：命令面板、菜单项按 menus.md 输出 2“快捷键取命令声明的键位”显示不出快捷键，插件贡献项和内置项显示不一致；快捷键文字与 Tiptap 实际 keymap 是两份，改一边另一边不会提示（还要自己做 Mac 的 ⌘ 写法，命令系统已有平台写法）。要么在命令声明里写 `keybinding`，让命令系统分发并拦下（`when` 里加 `nbook.editor/focused`），要么给动作目录加一条测试：用真实 Tiptap 按文字里写的键触发，断言生效。
(d) Alt+↑、Alt+↓：计划没写它是 Tiptap 的 keymap 还是命令 `keybinding`。若是命令 `keybinding`，全局分发在焦点不在编辑器时（例如 Composer 输入框、命令面板）也会命中，`when` 只有 writable 不够，必须带 `nbook.editor/focused`。macOS 上 Option+↑/↓ 是浏览器的“跳到段首/段尾”，会和它冲突；这条已由开发者确认，仅提示平台差异需要在 Spec 里写明。

[17] 严重程度：建议   类别：代码质量
位置：plan 第 7 节“触发”（`nb-markdown/src/editor/trigger.ts` 从 `prompt-editor-extensions.ts` 抽出）
