### 1. “整行复制后从菜单粘贴插成完整一行”的 e2e 判据区分不出有没有用上 InMemoryClipboardMetadataManager
**严重程度**：重要
**类别**：测试（判据没被真正测到）
**位置**：packages/neuro-book/e2e/editor-code-menu.e2e.ts:98-113（用例“剪切后正文与剪贴板都变；光标在一行里不选中、复制后到另一行粘贴……”）；对应实现 packages/neuro-book/src/plugins/editor/web/code/context-menu.ts:103-112
**现象**：用例的文档是 `{"alpha": 1,\n"beta": 2}\n`，剪掉 beta 后在 alpha 行复制（空选区，整行），`Control+End` 到文档末尾，再右击 `.view-line` 的最后一个元素点“粘贴”。文档末尾有换行，所以光标在第 3 行，一个空行的第 1 列。把整行文本 `{"alpha": 1,\n` 粘贴到“空行第 1 列”，带不带 pasteOnNewLine 结果完全一样。
**为什么是问题**：这段元数据（pasteOnNewLine、multicursorText、mode）正是设计审查第 6 条、Spec 输出 64“整行复制之后从菜单粘贴，插成完整的一行”要求的东西，也是实现里唯一依赖 Monaco 内部模块（`clipboardUtils.js`）的地方；e2e 是它的唯一兜底，却不能在它坏掉时失败。两个后果：(a) 把 `pasteOnNewLine` 恒写 false、或把整段 import/get 删掉，这条用例照样通过；(b) “生产构建里这个动态 import 与 Monaco 自己用的是不是同一个模块实例”（InMemoryClipboardMetadataManager.INSTANCE 是单例）至今没有被任何测试证明。开发模式里 `optimizeDeps.noDiscovery` 让 monaco 按源码逐文件提供，路径相同所以是同一份；生产构建靠 Rollup 的模块去重，从代码推断也是同一份，但没有证据。
**如何核实**：scratch/paste.mjs（scratch/site/paste.html）在真实 Chrome 里对 Monaco 做 `editor.trigger("t","paste",{text:'{"alpha": 1,\n', pasteOnNewLine})`：
- 空行第 3 行第 1 列：false 与 true 结果都是 `{"alpha": 1,\n"": 2}\n{"alpha": 1,\n`（相同）；
- 第 2 行中间（第 2 列）：false 得 `…\n"{"alpha": 1,\n": 2}\n`（插进行中间），true 得 `…\n{"alpha": 1,\n"": 2}\n`（整行插在上面）。
所以只有粘贴点在非空行中间时判据才有区分力。断言第 112 行（每个含 alpha 的行都以 `{"alpha"` 或 `"alpha"` 开头）在中间插入时会失败，但这条路径没人走。多光标各段（multicursorText）也没有任何用例。我没有在实现 worktree 里做变异（e2e 不让跑），这条结论来自上面的实验加读代码。
**建议改法**：粘贴点改到一行中间（例如右击 `"beta"` 行里的某个 token，光标落在行中），断言多出的是完整的一行、原行没被切开；补一例两个光标分别复制、再粘贴到两个光标的用例（或在报告里写明多光标不测）。顺带这条用例在生产构建里就证明了模块实例是同一份。

### 2. 语法色 e2e 只量了 JSON 的四种成分；规则表对 Monarch 语言的覆盖、注释与括号、明暗切换都没被测到
**严重程度**：重要
**类别**：测试（Spec 场景 43 的判据缺口）
**位置**：packages/neuro-book/e2e/editor-code-menu.e2e.ts:212-232（语法配色 4 例）；packages/neuro-book/src/plugins/editor/web/code/monaco-theme.ts:25-48（SYNTAX_RULES）；packages/neuro-book/src/plugins/editor/web/code/monaco-theme.test.ts
**现象**：场景 43 写的是“`.ts`、`.json`、`.css`、`.html`、`.md` 的样例……关键字、字符串、注释、括号与选区的颜色等于主题的语法变量……When 切到暗色、护眼绿，Then 这些颜色随之改变”。实际 e2e 只开 `{"key": "value", "n": 12, "t": true}`，量键、字符串值、数字、true 四个 token，四个 (theme, appearance) 组合各开一个新页面。
**为什么是问题**：
- JSON 的 token 来自 JSON 语言服务自己的分词（`string.key.json`、`string.value.json`、`number.json`、`keyword.json`），不是 Monaco 的 Monarch 语法。这次改成 `inherit: false` 之后，风险全在 Monarch 语言的前缀匹配上：`comment`、`type.identifier`、`tag`、`attribute.value.number.css`（按前缀落到 `attribute.value`，CSS 的数字会用字符串色）、`delimiter.bracket`、`keyword.md`、`string.link.md`、`variable.source.md` 等，没有任何一条被量过。规则表错一行，e2e 都不会失败。
- monaco-theme.test.ts 只断言规则表的形状（每个 --syntax-* 有人用、token 不重复、两对键值不同色），不涉及 Monaco 真实的 token 名。
- 注释色（对比度判据是 3，本表里最低）与括号着色（本任务特意关掉了按层数分色）没有被量。
- 运行时切换主题或明暗（MutationObserver → applyTheme）没有被测：每例都是新 goto，主题在加载前就写好了。
- verification.txt 与 editor.md 第 407 行写“语法色在 nbook 亮暗、macos 亮、护眼绿亮下量计算颜色与对比度”，这句话成立，但“.ts/.css/.html/.md 的样例”没有出现，Spec 场景 43 的 Given 没有被满足。
**如何核实**：读 e2e 全文，语法色用例的 Given 只有一个 JSON；`grep -n "\.ts\|\.css\|\.html\|\.md" e2e/editor-code-menu.e2e.ts` 只有 `a40.css`（量的是菜单）。
**建议改法**：加一例同一页面里依次开 `.ts`（注释、关键字、字符串、type）、`.css`、`.html`、`.md` 的样例，各量一两个 token 对 `--syntax-*` 的计算色；再加一例在同一页面里通过设置把 appearance 从亮切到暗，断言 token 色变成暗色那一套。规则表的覆盖不足也可以写进 monaco-theme.ts 的注释，说明哪些 Monarch token 故意落到前景色。

### 4. 用 `button !== 2` 区分“键盘触发的 contextmenu”不可靠；触摸长按、macOS 的 Ctrl+点击可能被当成菜单键，菜单开在光标处而不是指针处
**严重程度**：建议（从代码与平台行为推断，没有在对应平台验证）
**类别**：正确性 / 边界
**位置**：packages/neuro-book/src/plugins/editor/web/components/CodeContextMenu.vue:57-64
**现象**：非鼠标右键（`event.button !== 2`）的 contextmenu 一律按“键盘”处理：焦点在文字区就 `showAtCursor`，忽略 `clientX/Y` 与 `target`。
**为什么是问题**：
- 触摸屏长按（Android Chrome、iPad）发出的 contextmenu 一般 `button` 为 0、坐标是手指处；macOS 上 Ctrl+点击在不同浏览器里 `button` 也可能是 0。这两种情况下用户期望的是指针处的菜单、点在选区内外的光标规则，现在得到的是“光标处”的菜单，且不做 `setPosition`。Monaco 自己的 mouse handler 也把 mac 的 Ctrl+左键当右键处理（mousedown 里 `isMacintosh && leftButton && ctrlKey` 不处理），说明这个组合是真实存在的。
- Windows 上菜单键的 contextmenu 是在 keyup 之后由系统补发的；本组件在 keydown 里已经开了菜单（Reka 把焦点移进菜单），这时补发的 contextmenu 若落在文字区之外会因 `hasTextFocus()` 为假直接 `return`、不 preventDefault，浏览器自己的菜单可能叠出来；若焦点还没移走，则会再开一次。这是对 Chromium 行为的推断，没验证。
**如何核实**：没有可复现的实验（无头 Chrome 里 CDP 的按键不发 contextmenu，见第 3 条 (d)）；读代码即可看到判据。
**建议改法**：改用 `PointerEvent.pointerType`（Chrome 的 contextmenu 是 PointerEvent，键盘触发为空串）或坐标是否落在文字区内来分；键盘触发的 contextmenu 在 keydown 已经处理过的情况下，用一个短时间内的标记吞掉（或始终 preventDefault 而不再开菜单）。至少在注释里写明“键盘触发的只有菜单键，触摸与 Ctrl+点击不在支持范围”。

### 5. `createColorReader` 的“表达式不合法就用后备色”只对语法错误成立；变量缺失时读到的是继承来的正文色，后备色永远用不上
**严重程度**：建议
**类别**：正确性 / 与注释不符
**位置**：packages/neuro-book/src/plugins/editor/web/code/monaco-theme.ts:68-79、89-97
**现象**：`probe.style.color = "var(--x)"` 对任何 `var()` 都在解析期接受（`style.color` 回读为 `var(--x)`），变量不存在时计算值是“无效于计算时”，`color` 继承自 body。所以第 73 行 `probe.style.color === ""` 只能拦住字面量写错的情况（实验：`"notacolor"` → 空串 → null），拦不住缺失的变量。
**为什么是问题**：注释写“表达式不合法时这一行不生效，`color` 是继承来的正文色：宁可用后备色”，函数签名与 `solid(name, fallback)`、`translucent(name, fallback)` 都在承诺后备色；变量缺失时实际得到的是 body 的 `color`。对 `--syntax-*` 和 `--text-main` 影响不大（本来就近似正文色），但对 `translucent("--selection-bg")` 意味着选区底色变成不透明的正文字色（文字被选区盖住）。产品里这些变量都在配色合同里有声明，所以目前不会触发；第三方主题把 `--syntax-keyword: var(--不存在)` 这种写错会静默得到 body 的颜色，而不是 `foreground`。
**如何核实**：scratch/probe.mjs：`var(--nothing-here)` → `style.color` = `var(--nothing-here)`，计算色 `rgb(18, 52, 86)`（= body 的 color），画布读回 `[18,52,86,255]`，返回非 null。
**建议改法**：读完后用 `getComputedStyle(root).getPropertyValue(name).trim() === ""` 先判变量是否有值，空就走后备；或把 probe 的初始 `color` 设成一个哨兵色（例如 `transparent`），读到哨兵就当成“没解析出来”。

### 6. 画布换算在半透明色上有预乘误差，e2e 的容差 1 只对恰好那一个主题的透明度成立
**严重程度**：建议
**类别**：正确性（精度）/ 测试
**位置**：packages/neuro-book/src/plugins/editor/web/code/monaco-theme.ts:74-78；packages/neuro-book/e2e/editor-code-menu.e2e.ts:232-245
**现象**：把 rgba 画到 1×1 画布再 `getImageData`，读回的是从预乘 8 位存储还原的值。实验（scratch/probe.mjs，Chrome）：`rgba(173,214,255,0.25)` 读回 `[171,215,255,64]`（R 差 2）；`rgba(38,79,120,0.2)` → `[40,80,120,51]`（R 差 2）；`rgba(255,200,10,0.1)` → `[255,196,10,26]`（G 差 4）。不透明色与 `color-mix()` 到 `color(srgb …)` 的结果没有这个问题。
**为什么是问题**：误差本身肉眼看不出来（选区底色本来就是半透明叠色），不是显示缺陷；但（1）这一步的存在理由写的是“认 color-mix() 与带透明度的写法”，而最需要精确的恰是透明度；（2）选区色的 e2e（场景 43）用容差 `≤ 1` 比较 `--vscode-editor-selectionBackground` 与 `--selection-bg`，当前只跑 nbook 亮色一个主题，其透明度恰好误差 ≤1；换成 alpha 更低的配色（macos 亮、护眼）同一断言会失败，是潜在的间歇红。
**如何核实**：同上实验；e2e 只在 `nbook`/`light` 下跑选区用例（第 232 行起）。
**建议改法**：计算色已经是 `rgb()/rgba()/color(srgb …)` 文本时直接解析数值（e2e 的 `resolved` 就是这么做的），只有 `oklch()`、`lab()` 这类才走画布；或者把容差放到按 alpha 估算（`ceil(0.5/alpha)`），并在 e2e 里多跑一个半透明更重的主题。

（第 6 条补注，收窄）核对了仓库里的 --selection-bg：nbook/macos 的 alpha 在 0.22–0.34 之间，误差都 ≤1，所以现有四套配色下 e2e 不会失败；“间歇红”只对 alpha 低于约 0.2 的第三方或用户配色成立，是假设。这条维持“建议”，主要理由是“这一步的存在理由与精度不匹配”。

### 9. 魔法数字与动态 import 的取舍没写理由
**严重程度**：建议
**类别**：代码质量
**位置**：packages/neuro-book/src/plugins/editor/web/components/CodeContextMenu.vue:42（`1 satisfies Monaco.editor.ScrollType.Immediate`）；packages/neuro-book/src/plugins/editor/web/code/context-menu.ts:43、105
**现象**：
- CodeContextMenu 的 `showAtCursor` 用数值 1 表示 `ScrollType.Immediate`，而同一文件的 `onContextMenu` 已经在用 `props.monaco.editor.MouseTargetType`；`showAtCursor` 的调用点（`onKeyDown` 的监听里）在 `watch` 回调里同样拿得到 `monaco`，传进去即可，不必用 satisfies 的数字。context-menu.ts 里 `EMPTY_SELECTION_CLIPBOARD = 45` 同理（`runCodeMenuItem` 只多收一个参数）。`satisfies` 保证了 Monaco 升级时编译期报错，所以不是缺陷，只是不必要地依赖“枚举值不变”。
- 第 105 行在 `editor.focus()` 之后才 `await import(...)`：开发模式第一次可能真的是一次网络请求，焦点与光标可能在这期间被改（读剪贴板那一段已经有同样的窗口，注释只提了读剪贴板）。注释也没说为什么要动态 import（静态 import 会把 Monaco 内部模块带进 context-menu.ts 的依赖图；它只被按需加载的 MonacoControl 用到，这个理由可能不成立）。
**建议改法**：枚举值从已有的 `monaco` 取；先 import 后 focus，或者在注释里写明为什么动态；如果静态 import 在构建里没有副作用，直接静态引入更简单。
