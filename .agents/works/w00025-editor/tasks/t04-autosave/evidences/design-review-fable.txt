### 1. “停手后”的定时会在输入法组字途中强制结算并保存
**严重程度**：重要；**类别**：正确性
**位置**：plan.md 4.1“触发”与“可自动保存”；packages/neuro-book/src/plugins/markdown/web/components/MarkdownControl.vue:371-381（commitWhenSettled）、136-167（commitNow）、41-42
**现象**：计划用文档的 revision 重排定时，到点先 `documents.settle(document)` 再 `save`（save 自己也 flush）。Markdown 控件只在停手 150 毫秒后把输入交给文档，而且组字期间不交：`commitWhenSettled` 见 `view.composing` 就每 150 毫秒再等一轮，注释写明原因是“交出被接受后的写法回填会重画这一块，打断组字”。于是连续用拼音输入时文档的 revision 长时间不动，定时停在上一次提交之后的 delay 处；它到点时用户正在组字，`settle` 直接调 `commitNow`（没有组字判断），把半截拼音写进正文并回填重画，再存到磁盘。
**为什么是问题**：(1) “停手后”量的是“距上一次提交”，不是“距上一次按键”，连续中文输入时用户并没有停手；(2) 控件特意避开的打断组字被自动保存重新引入；(3) 磁盘上会短暂出现带拼音字母的正文，Agent、别的窗口、文件监听读到的就是它。缺省延迟 1000 毫秒，一次组字加选词超过 1 秒很常见，这个产品的主要用户正是中文写作者。缺省模式（失焦时）不受影响：失焦时控件本来就立即提交。
**如何核实**：读上面三处；真实浏览器里可以用 e2e/markdown-input.e2e.ts:72 现成的 CDP `Input.imeSetComposition` 写用例：设“停手后”100 毫秒，输入一段后开始组字、保持 300 毫秒不上屏，读磁盘与组字状态。本条是从代码推断，未在浏览器里跑。
**建议改法**：定时到点时不强制结算正在组字的视图。两种做法任选：(a) `attachView` 登记时多交一个“现在不能结算”的查询（组字中、或缓冲的输入不足 delay 那么久），定时到点遇到它就顺延一个 delay；(b) 控件每次有用户输入时通知一次“有输入活动”，定时按活动重排而不是按 revision。Spec 输出 63 写明“停手”从最后一次输入算、组字期间不触发；验收加一条组字用例。

### 2. “停手后”的定时只跟 revision 与 dirty 走：文档重新变得可保存而修订没变时，再也不会排上
**严重程度**：重要；**类别**：正确性
**位置**：plan.md 4.1“触发”第三项；packages/neuro-book/src/plugins/editor/web/documents/store.ts:340-348、333-338、760-771、793-796
**现象**：计划写“dirty 的文档每次修订变化都重排一次，到点保存”。到点时文档不可自动保存（有 saveProblem、未裁决、写不出、已删除）就跳过，这次定时用掉了。之后让它恢复资格的几件事都不改 revision、也不改 dirty，所以没有新的定时：
- 结果未知的保存被核对为已落盘：store.ts:343-346 清掉 saveProblem、把 saved 设成当时的快照；断线期间用户接着写的字仍是 dirty（断线重连后的常见情形）；
- 未裁决输入选“采用当前正文”（resolve 的 adopt-current 不动正文）、写不出选“采用当前正文”（unblock）；
- 被删除的文件又出现（store.ts:333-338：status 回到 ready，只标“磁盘已变化”）；
- 手动保存或“覆盖”慢于 delay：保存期间的输入重排的定时在 saveProblem、冲突还没清的时候到点，被跳过，保存成功后正文仍 dirty。
这些文档在“停手后”模式下一直 dirty，直到用户再敲一个键；而这个模式下失焦不触发，没有别的兜底。
**为什么是问题**：用户选了“停手后保存”，界面上也没有任何阻碍保存的提示了，文档却不保存。VS Code 为同类情形另记一张“等条件”的表（waitingOnConditionAutoSaveWorkingCopies），条件变了再存。
**如何核实**：读上述行号；auto-save.test.ts 里加用例：保存请求扣住并断开造成 unknown-outcome，继续输入，推进时钟让定时到点被跳过，重连核对成功后再推进 delay，断言磁盘是最新正文。本条是从代码推断。
**建议改法**：定时的重排条件改成“修订变了，或可自动保存从假变真”：把 eligible 写成读 dirty、status、conflict、unresolved、blocked、ended、saveProblem 的计算值，`watch([revision, eligible])`；从假变真时排一次。验收映射“停手后”一行补上这几种恢复。

### 3. 拿 saveProblem 当“上次保存失败”的闸：它在文档已经干净之后还留着，自动保存会被无声地一直挡住
**严重程度**：重要；**类别**：不变量
**位置**：plan.md 4.1“可自动保存”的 saveProblem 一条、待确认项 4；store.ts:346、461、586（仅有的三处清除）、563、362-369（adopt）、809-822（revert）；EditorGroup.vue:132-133
**现象**：计划假定“上次保存失败后停下，直到一次手动保存成功”。但 saveProblem 只在三处清掉：一次真的写成功（586）、结果未知被核对为已落盘（346）、最后一个文本标签关闭（461）。下面几条路径文档已经没有问题，它却还在：
- “重新载入磁盘版本”或还原命令（revert → adopt）不清；
- 不 dirty 时的手动保存在 store.ts:563 提前返回 `{ok: true}`，不清；
- 外部修改被采纳（adopt）不清。
实测（scratch/save-problem.test.ts，真实 Files 场地，把目录设为只读造成 permission-denied）：保存失败后 revert，dirty 为假、saveProblem 仍在；此时手动保存返回 ok、saveProblem 仍在；再输入变 dirty，saveProblem 还在，按计划的 eligible 不自动保存；要等一次 dirty 状态下的手动保存成功才清。
**为什么是问题**：用户改回去或重新载入之后接着写，“失焦时保存”对这份文档不再生效，而他按“手动保存一次”去做也可能是空操作。保存失败的横幅（EditorGroup.vue:133）没有任何按钮，自动保存的用户不一定想到 Ctrl+S；状态栏的错误态只在文档需要保存时才列它。
**如何核实**：`cd .worktree/w00025-editor/packages/neuro-book && bun test /tmp/nb-review-w00025/t04-design/scratch/save-problem.test.ts`，看打印的四行。
**建议改法**：二选一并写进 Spec：(a) 闸由自动保存模块自己记（“这份文档上次自动保存失败”），在文档变干净、任何一次保存成功、订阅 resync 时复位，不借用 saveProblem；(b) 仍用 saveProblem，但让 adopt 清掉它（这也修了现在“重新载入后横幅还写保存失败”）。两种都给保存失败的横幅加“重试保存”按钮。变异检查里加“revert 之后再输入仍会自动保存”。

### 4. e2e 清单漏了 workbench-titlebar，而且“跑一遍看谁失败”查不出会空过的用例
**严重程度**：重要；**类别**：测试
**位置**：plan.md 第 8 节的 9 个文件与第 9 节风险 2；packages/neuro-book/e2e/workbench-titlebar.e2e.ts:237-269
**现象**：按 `data-editor-tab-dirty`、“未保存”、`beforeunload` 与在编辑器里输入逐个文件 grep，依赖“输入后失焦仍未保存”的文件里，workbench-titlebar 不在计划的清单中。它的用例“重新载入：有未保存正文时浏览器先问……”先在正文输入“丙”，再点标题栏“视图 › 重新载入”，用 `page.once("dialog", …)` 在回调里断言对话框是 beforeunload。缺省改成失焦时保存后，点标题栏菜单这一下正文失焦、文档被保存，不再有离开确认：第一次“重新载入”直接刷新，`once` 的回调不执行，后面 `toContainText("丙")` 因为字已落盘照样通过，第二次重载的 `waitForEvent("load")` 也通过。这条用例会通过，但已经不验证“有未保存正文时先问”。

**建议改法**：清单加 workbench-titlebar。先静态过一遍再跑：凡是用例的前提是“输入后去点别处、文档仍未保存”的（editor-area 的 281、301、1151、1231、1352、1603、1763 行起的用例，bookshelf-stats:119，titlebar:237），在启动处显式关掉自动保存，不等它失败；titlebar 这条把断言移到回调之外（记下收到的对话框类型再断言）。

### 5. “失焦”拿控件现成的 focus(false) 当判据：一边多触发，一边靠没验证过的 DOM 行为
**严重程度**：重要；**类别**：设计
**位置**：plan.md 4.2、第 3 节表格第 3 行、第 9 节“不做”与风险 1；MonacoControl.vue:299-303；MarkdownControl.vue:399-404；EditorGroup.vue:256；area.ts:534-542（leave）
**现象**：
- 多触发：源码编辑器发的是 `onDidBlurEditorText`，焦点进 Monaco 自己的查找框、右键菜单、F1 面板都算失焦。VS Code 的失焦保存挂在编辑器部件一级（含内嵌的查找框等；现版本具体挂哪个事件不确定，旧版是 `onDidBlurEditorWidget`），按 Ctrl+F 不会保存。Markdown 控件用 Tiptap 的 blur：工具栏按钮有 `@mousedown.prevent` 不触发，但下拉菜单、右键菜单、块菜单、注音与链接的输入框都拿走焦点。保存的是操作中途的正文（例如块按钮“+”刚插进去、之后可能被放弃的空块），随后操作完成又变 dirty。
- 漏触发：第 9 节说“焦点在视图里时换标签已经有失焦”，表格同一行却写“换活动编辑器时保存它：做”，两处不一致。键盘换标签（Ctrl+Tab、命令）时旧控件是被隐藏或停放，不是用户把焦点移走；聚焦元素被隐藏时发不发 blur 各浏览器不一致（不确定），计划没有验证。VS Code 不靠它：`onDidActiveEditorChange` 里明确把换活动编辑器当成一次失焦。
**为什么是问题**：缺省模式的核心触发建在一个原本只用来记“焦点在不在编辑器区”的事件上，语义是“文字区失焦”，不是“离开这个视图”。漏触发的表现是开着“失焦时保存”，换走的标签还挂着未保存圆点。
**如何核实**：读上述行号；e2e 加一条：输入后用键盘换到同组另一个标签，断言旧文件已落盘。
**建议改法**：换标签不靠 DOM：`leave(groupId)` 放行换下活动视图时，模式是失焦时就保存它的文档（那里已经结算过输入）。源码编辑器另发一个部件级的失焦（`onDidBlurEditorWidget`）给自动保存用，现有的 focus 事件不动。Markdown 的浮层若不单独处理，在 Spec 写明“焦点进入编辑器自己的菜单与输入框也算失焦”，不要只当风险。第 3 节表格那一行改成与第 9 节一致。

### 6. 关闭时不问（4.3）与 save 合同的几处边界没写
**严重程度**：建议；**类别**：正确性
**位置**：plan.md 4.1“保存”、4.3；store.ts:690-694（live）、808、539-549、651（租约结果未知不释放）；area.ts:544（needsSettle）、550-560（changeEditor）、588-628
**现象**（循环本身核对过：保存成功后回到开头、保存期间又输入就再存一次、用户停手即结束；保存失败的每种结果码都留下冲突、未裁决、写不出、订阅结束或 saveProblem 之一，不会反复自动重试；另一组此时打开同一文件则 shared 为真直接关；不会吞掉取消）：
- `documents.save(document)` 对已丢弃的文档是同步抛 RangeError，不是 reject（scratch/open-documents.test.ts 实测：关掉标签后调 save，同步抛出）。计划只写“Promise 的拒绝交 report”。定时回调、窗口失焦遍历里若拿着一份刚被资源管理器删除而关闭的文档，会在回调里直接抛出。自动保存调 save 之前要核对 `documents.get(地址) === document`，或包一层 try。
- “失败则落到原来的询问（只试一次，之后 saveProblem 使它不再可自动保存）”靠的是状态恰好都留了记号。照 VS Code 的写法用一个局部的“已经自动试过”标志更直接，也不受第 3 条怎么改的影响。
- 4.3 的条件是“可自动保存”（含 dirty）。文档不 dirty 但有排队的保存时（needsSettle 因 saving 为真），仍会弹“保存 / 不保存 / 取消”。建议这种情形只等保存队列，不问。
- 自动保存没有对话框，`await documents.save` 期间用户看不到任何东西。租约结果未知时（store.ts:651 不释放）保存一直排队，点关闭没有反应、也没有取消的地方。至少在等待超过 800 毫秒时给出与读取相同的进度提示。
- 同一判据的另一个入口没提：`changeEditor`（文本换到字节编辑器）在文档需要结算时拒绝（area.ts:559）。缺省模式下经命令面板或标题菜单换编辑器，失焦触发的保存可能还在途，拒绝与否取决于时序。要么这里也先等保存，要么在计划里写明不动。
**如何核实**：`bun test /tmp/nb-review-w00025/t04-design/scratch/open-documents.test.ts` 的第三行输出；其余读行号。
**建议改法**：见各项。验收映射的“关闭”一行补：保存期间继续输入、保存期间另一组打开同一文件、批量关闭遇自动保存失败停在询问。

### 7. dirty 且“磁盘已变化”时照常尝试：点“重新载入”会先触发一次注定冲突的保存，资源管理器的改名也被它挡住
**严重程度**：建议；**类别**：设计
**位置**：plan.md 4.1“可自动保存”最后一项；EditorGroup.vue:131（磁盘已变化的横幅只有“重新载入”）；store.ts:595-598、642-646（begin 遇冲突拒绝）、809-822
**现象**：计划的理由是“用户在失焦时就看到冲突，不用等到手动保存”。但“磁盘已变化”的横幅在检测到时已经显示，用户是知道的。按计划：
- 用户去点横幅上的“重新载入”：按下鼠标时正文失焦，自动保存先发出一次用过期基线的写入，然后点击才执行 revert。写入的冲突回应与 revert 的读取谁先到取决于通道顺序；冲突回应晚到时，文档已经是磁盘内容、却又被标上冲突。磁盘内容恰好又变回基线时这次写入会成功，用户要丢弃的修改反而落了盘。
- 用户去资源管理器给这份文件改名或移动：失焦把“磁盘已变化”变成“冲突”，租约的 begin 对冲突拒绝（store.ts:642-646），而原来只是“磁盘已变化”时可以改名。
**为什么是问题**：这次保存基线已经过期，除了把一种提示换成另一种，没有别的结果；副作用是让用户正要去点的那个按钮与它竞争。
**如何核实**：读行号；auto-save.test.ts 里对 dirty 且磁盘已变化的文档先调 viewBlurred 再立刻 revert，断言结束后没有冲突标记。本条从代码推断。
**建议改法**：把 diskChanged 也列入不可自动保存，与冲突同样等用户处理；想让用户早点看到“覆盖磁盘版本”，就给“磁盘已变化”的横幅加这个按钮（走手动保存），不用自动保存去撞出冲突。保留现方案的话，在 Spec 写明上面两个后果。

### 8. 窗口失焦的判据：点进同页的 iframe 也会让 window 发 blur
**严重程度**：建议；**类别**：设计
**位置**：plan.md 4.4、待确认项 5；packages/neuro-book/src/plugins/html-preview/web/components/HtmlPreview.vue:150-162；packages/neuro-book/src/shared/host.ts（没有窗口焦点相关的宿主能力）；packages/neuro-book/src/plugins/projects/web/components/BookshelfHost.vue:65-66（现有做法也是直接监听 DOM）
**现象**：焦点进入页面里的 iframe 时，顶层 window 会收到 blur，这时用户并没有离开应用。HTML 预览是沙箱 iframe，点一下预览、或预览里的脚本自己取焦点，都会触发“保存全部”。后果只是多存一次（保存不改正文，侧边预览读的是文档正文不是磁盘），但“窗口失焦时”模式的语义被冲淡：用户选它就是不想在应用内切换时保存。
在 `shared/host.ts` 与 `web/host/` 里按 focus、blur、visibility 搜过，没有可用的宿主能力；直接监听 DOM 与书架页的现有做法一致。
**为什么是问题**：判据比名字宽，Spec 若照“窗口失去焦点”写，行为与文字不符。
**如何核实**：e2e 里打开 HTML 侧边预览，设“窗口失焦时”，在源码里输入后点预览内部，看磁盘有没有更新。未在浏览器里验证。
**建议改法**：blur 处理里加一句 `if (document.hasFocus()) return`：焦点在子 iframe 里时顶层文档的 hasFocus() 仍为真，真正切走窗口时为假。`visibilitychange` 为 hidden 保留（移动端与切浏览器标签）。两个事件常常先后都到，第二次调用时文档已不 dirty 或合并到排队的保存，不用另外去重。
另：页面卸载时也会发 `visibilitychange`（hidden），这时触发的保存与计划 4.4“卸载时不触发”的说法不一致，但无害（写入要么整份落盘要么没发出），在注释里写一句即可。

### 9. 对照 VS Code：第 3 节记对的、记得不全的，与没列出的项
**严重程度**：建议；**类别**：设计
**位置**：plan.md 第 3 节表格、待确认项 1
**记对的**（按记忆核对）：四种模式与 `autoSaveDelay` 缺省 1000；窗口失焦在 onFocusChange 与 onWindowChange 下都保存全部（`getAutoSaveMode` 按保存原因判）；afterDelay 下失焦不触发；文档处于冲突或出错状态时自动保存被忽略、手动保存才执行（`TextFileEditorModel.save` 开头）；短延迟下隐藏未保存圆点（`hasShortAutoSaveDelay`，阈值是不超过 1000 毫秒）。
**记得不全的**：
- 关闭时不问：VS Code 是 onFocusChange 下先保存；onWindowChange 只在桌面版的 Windows 与 Linux 上先保存（原生对话框会让窗口失焦）；短延迟的 afterDelay 是把编辑器当作“正在保存”直接关掉标签，并不等保存，因为它的文档模型不随标签丢弃。长延迟照常询问。待确认项 1 的括号要按这个改。
- 保存失败后再问：VS Code 用 `skipAutoSave` 参数重走一遍确认，见第 6 条。
**VS Code 有、计划既没做也没写“不做”的**：
1. 换活动编辑器算一次失焦（见第 5 条）。
2. 改了自动保存的设置就立即把全部 dirty 的文档按新模式存一次（`onDidChangeAutoSaveConfiguration`）。计划只在切到 afterDelay 时排定时；从“关闭”切到“失焦时”，已经 dirty 又不在焦点里的文档要等下一次窗口失焦。
3. 自动保存失败与冲突都有通知，带“重试”“比较”“覆盖”。计划是“失败不提示”，只靠横幅与状态栏（见第 3 条）。
4. 条件恢复后补存的“等条件”表（见第 2 条）。
5. “文件 › 自动保存”菜单项与切换命令。计划只有设置项。
6. `files.autoSaveDelay` 最小值是 0；计划取 100（合理，见待确认项 3）。
7. 桌面版关窗时，开着自动保存会先保存全部再决定要不要问；网页版做不到，计划保留离开确认是对的，但桌面端落地时要回来看。
8. 按资源临时停用自动保存（`disableAutoSave`，Agent 正在改这份文件时用）。不确定各版本是否都有；本产品 Agent 写的是磁盘不是编辑器文档，可以写“不适用”。
**建议改法**：第 3 节表格补上 2、3、5 三行并各写“做”或“不做”及理由；其余按所指的条目处理。

### 11. 计划在迁就的三个上游选择
**严重程度**：建议；**类别**：设计
**位置**：plan.md 4.1、4.3；docs/specs/workbench/editor.md“时序与寿命”第 1 条、“副作用与数据”第 1 条；MarkdownControl.vue:41-42、371-381；store.ts:551-555
**现象与判断**：
- “文档只在内存，最后一个标签关闭即丢弃”。4.3 因此必须等保存完成才能关标签，VS Code 则是标签先关、模型留到存完。editor Spec 把它写成事实与“不承诺”，没有搜到记录的理由（在 docs/adr、docs/proposals、docs/specs 按“只在内存”“跨页面刷新”搜过，命中的文件没有逐个读）。就这个任务而言等保存再关是更稳的做法：失败时标签还在，可以落回询问；代价是关闭的延迟等于一次写入，以及第 6 条说的无提示等待。不建议为自动保存改它。
- “控件停手 150 毫秒后才把输入交给文档，组字期间不交”。理由写在代码注释里（回填会打断组字），现在仍成立。但它使文档的 revision 不等于“用户有输入”，计划把 revision 当输入活动用，是第 1 条的根因。要改的是自动保存取信号的地方，不是这个延迟。
- “保存总是先结算全部视图”（saveNow 开头的 flush）。对手动保存是对的（保存用户看到的内容）；对定时触发的自动保存，它就是把组字中的输入强行交出的那一步。若第 1 条采用“定时只存已经交出的正文”，需要给 store 的保存加一个不结算的入口，这是对 store 合同的改动，计划现在写的不变量“自动保存只调 settle 与 save”要随之改写。
**别扭之处**（逐处判断）：`EditorAreaOptions.autoSave` 缺省是关、设置项缺省是失焦时，同一功能两个缺省。理由成立（Lab 与合同测试不经插件，不该被改变），在选项的注释里写明即可。`autoSaveDelay` 在别的模式下一直显示：设置窗口确实没有按另一项显示或隐藏的能力（settings-window Spec 里按“条件”“显示或隐藏”搜不到），说明文字的做法可以接受。
**如何核实**：读所列位置。
**建议改法**：见第 1 条；其余不动。

### 12. 计划没想到、对写作者有用的补充
**严重程度**：建议；**类别**：设计
**位置**：plan.md 全文；packages/neuro-book/src/plugins/editor/web/commands.ts:30（已有还原命令）

## 对 5 个待确认项的判断

1. 关闭时不问推广到三种开启的模式：同意。这里文档随标签丢弃，开着自动保存还弹“保存 / 不保存 / 取消”只是噪音。括号里对 VS Code 的说法要按第 9 条改；同时写明“不保存”这个出口没有了（第 12 条）。

3. 延迟范围 100–600000、缺省 1000：范围与缺省都可以。Markdown 下实际的停手时间是 150 毫秒加这个值；先解决第 1 条，否则取多少都会在组字途中触发。
4. 被删除后不自动重建：同意。上次保存失败后停下直到手动保存成功：方向同意（与 VS Code 一致），但不能直接借用 saveProblem（第 3 条），并且要给“重试保存”的入口。
5. 窗口失焦的判据：同意用这两个事件，blur 里加 `document.hasFocus()` 过滤掉焦点进 iframe 的情形（第 8 条）。
