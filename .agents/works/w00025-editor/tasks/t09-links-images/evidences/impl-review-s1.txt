== 1. 代次只在请求到达时核对，写入时的 acquire 会重新启动已停止的项目并写进新一代（实测）==
严重程度：重要；类别：正确性 / 不变量
位置：packages/neuro-book/src/plugins/files/backend/upload-route.ts:238-242（核对）与 :260-288（排队、读体、写入）；backend/projects-scheme.ts:79-86、98-104（hold/call 都调 projects.acquire）
现象：代次核对在 gate.run 与 readBody 之前做一次，之后不持有任何租约。写入经 projects:// 的 hold → projects.acquire，而 acquire 对没在运行的项目会起一个新代次（docs/specs/runtime/projects.md 状态表“没在运行 + acquire → 新代次 creating”）。rename 路径的 list 也经 projects.call → acquire。
实验（真实 Bun.serve、真实项目子进程，临时测试文件已删，副本 /tmp/review-w00025-t09-s1/exp/zz-review-exp.test.ts）：流式 PUT 先发 PNG 头，服务端进入处理器后释放场地租约、clock.advance(GRACE_MS) 等第 1 代被撤销（running()=null），再发完请求体。结果：201 {"address":"project://插图/late.png"}，manager.running() 变成 {"generation":2,"state":"idle-grace"}，文件 15 字节写在磁盘上。
为什么是问题：违反 Spec“写入图片”的“不会为了一次上传启动项目”与“代次不符为 410”。设计审查第 2 条接受的是“核对与取租约之间极窄的竞争”；实际窗口是排队等待加整个请求体的传输时间（32 MiB 的慢上传、或排在两个大上传之后），并不窄，后果也不止“落在同一目录”，而是凭一次 HTTP 请求起了一个项目子进程。
建议改法（不需要给 ProjectsService.acquire 加代次参数）：租约本身带 generation（projects.md 输出 3：lease 是 {id, name, generation, revoked, release()}）。路由在 list 确认 running/idle-grace 之后立即 acquire 一次，比对 lease.generation === URL 代次，不等就 release 并 410；把这份租约持有到写入结算（finally release）。这样写入链里的 acquire 必然拿到同一代，“已知限制”整条可以删掉；sources.projects 的 Pick 加上 acquire。另补一条测试：上传途中项目停止 → 410、不起新代次、没有文件。

严重程度：重要；类别：正确性 / 文档

现象：

== 3. 名字超过 255 字节：exists=fail 得 500 io-failed，exists=rename 得 400 且说明写“加了序号的名字太长”（实测）==

== 5. 客户端 upload：响应头到了以后取消或读体失败，201 被报成 io-failed；宿主层的 403 origin-not-allowed 被兜底成 permission-denied ==
严重程度：建议；类别：正确性
位置：packages/neuro-book/src/plugins/files/web/client.ts:31-34（failureOfStatus）、:52-64
现象：
- fetch 在响应头到达时就 resolve；之后 signal 触发或连接断开，`response.text().catch(() => "")` 吞掉错误得到空串，parsed 为 null，走到最后：failureOfStatus(201) 在码表里找不到 201，返回 "io-failed"。文件其实已经写下，调用方拿到的是“其它写入失败”，而不是 Spec 要求的 cancelled（调用方取消）或 network（图可能已经写下）。按 io-failed 处理的调用方可能重试同一个名字，得到 conflict 或多一张 `名字 2`。
- 宿主分发层（nb-host http/dispatch.ts:85）对不允许的 Origin 回 403 {"error":{"code":"origin-not-allowed"}}，这个码不在上传码表里，兜底取 403 的第一个码 permission-denied（“目录不可写”）；421 misdirected-host 成了 io-failed；503 plugin-unavailable / 准入关闭成了 project-unavailable（这一个合理）。
为什么是问题：Spec 让“调用方只按 code 判断”，兜底给出的码语义要对；“同一个状态有几个码时取第一个”依赖对象键的书写顺序，换个顺序结果就变。
建议改法：读体失败时按 signal 区分 cancelled / network，不吞成空串；201 但体不合格时也不要报 io-failed（可报 unknown-outcome：已写成但不知道地址）。兜底表写成显式的 status → code 映射（403 → cross-site 或单独的 forbidden 说明，404 → not-found，409 → conflict，410 → generation-gone，413 → too-large，415 → unsupported-type，502 → unknown-outcome，503 → project-unavailable，其余 io-failed），不靠键顺序。测试 upload-route.test.ts:374-380 只测了 413、502、418 三个，没测到 403、404 的兜底。

（行号更正：第 1 至 3 条里 upload-route.ts 的行号误取自 diff 输出，按 ef9a1b942 的源文件应为：第 1 条 核对 :135-139、排队读体写入 :157-185；第 2 条 failureOf :47-58、未登记 id 回 410 :137-139；第 3 条 fail 分支 :170-174、rename 的长度检查 :184、建议加检查的位置 :148 旁。第 4、5 条的行号是源文件行号，无误。）

== 9. 读请求体没有任何超时：两条停住不发的上传占满 Gate 后，之后的上传无限期排队 ==
严重程度：建议；类别：安全 / 不变量（拒绝服务）
位置：backend/upload-route.ts:157-159（gate.run 里 readBody）；nb-host http/plugin.ts:80（idleTimeout: 0）
现象：HTTP 监听关闭了空闲超时（为长请求与事件流）；readBody 的 reader.read() 只在数据到达或连接关闭时返回。一个发了部分请求体后停住、但不断开的连接会一直占着名额；两条这样的连接之后，所有上传都排在 Gate 的 #waiting 里，没有上限、没有超时。服务端停止时这些请求还拖住 HTTP 排空，直到 HTTP_DRAIN_LIMIT_MS 才以“排空未完成”结束。
已排除：未读的请求体不会被 Bun 缓存在内存里（实测 300 MB 上传在处理器 3 秒不读期间 RSS 36 → 39 MB，/tmp/review-w00025-t09-s1/exp/buffer.ts），所以排队本身不放大内存；Content-Length 说谎（声明小、实发大）由边收边数挡住。
为什么是问题：端口只接受回环与允许的来源，恶意方已经是本机进程，危害有限；但本应用自己的浏览器页在系统休眠、标签页被冻结时也可能留下半发的上传，之后同一服务的所有上传卡住，用户只看到插图一直在“上传中”，没有任何诊断。
建议改法：读体时设一个“两块数据之间的最长间隔”（例如 30 秒，用注入时钟），超时就 reader.cancel() 并回 408 或 io-failed；或者至少对在 Gate 里等待的请求监听 request.signal，断开的不再占位（现在是轮到它时才看 aborted，:158）。Spec 写一句上传的空闲上限。

== 10. 扩展名查表读到原型链：名字以 `.constructor`、`.tostring` 这类结尾时得 415 extension-mismatch，而不是 unsupported-type ==
严重程度：建议；类别：正确性 / 代码质量

== 11. 写在作品根时 rename 的 list 地址带结尾斜杠、恒失败：根下同名的悬空链接得 409 而不是 `名字 2`，所有根下重名都退化成“写一次、冲突、重暂存整份字节”（实测）==
严重程度：重要；类别：正确性
位置：backend/upload-route.ts:165（`const parent = \`projects://${id}/${directory}\``）与 :179-180（list 失败时静默当作空）
现象：directory 为 "" 时 parent 是 `projects://<id>/`，路径以空段结尾，parseAddress 回 invalid-address（resource.ts pathProblem“路径含空段”），list 失败，taken 为空，而 :180 只在 existing.ok 时收名字，失败不留任何痕迹。实测：作品根下放 `dangling.png -> missing.png`，PUT `dangling.png?exists=rename` 得 409 {"code":"conflict","message":"dangling.png 指向不存在的目标"}；同样的链接放在 `子/` 下得 201 `子/dangling 2.png`。
为什么是问题：违反 Spec“不覆盖”：rename 把悬空链接当作被占用、取下一个空名。插图存放设置的“作品根”（决定 4 的四种之一）与根下文件的“与当前文件同目录”都会写到根；根下有普通文件同名时虽然靠 conflict 重试仍能成功，但每次重试都重建暂存、重写最多 32 MiB，`名字 2` 到 `名字 N` 被占时就是 N 次整份写入。现有测试的 rename 用例都在 `插图/`、`图/` 下，碰不到根。

== 12. failureOf 的兜底：远程路由层的码（target-gone、unavailable、not-provided、timeout、provider-error）一律 500 io-failed；注释说“原码写进说明”，实现没写，也没有诊断 ==
严重程度：建议；类别：正确性 / 代码质量（静默吞码）
位置：backend/upload-route.ts:43-58（failureOf 及其注释）、:174、:188（`failure(failed.code, written.detail)`）
现象：projects:// 的 commit 是一次远程调用，flatten（projects-scheme.ts:29-40）把路由层失败原样交回，码可能是 nb-runtime remote/protocol.ts:27-38 里的 target-gone、unavailable、not-provided、timeout、provider-error、cancelled、denied。failureOf 的 default 分支把它们都变成 io-failed；注释写“不认识的码一律 io-failed，原码写进说明”，但调用处传的是 written.detail，原码丢了；路由也不记诊断。
为什么是问题：Spec 码表把“项目实例不可用”定为 503 project-unavailable，项目子进程崩溃、未就绪的 target-gone / unavailable / not-provided 属于这一类（确定没写），现在报成“其它写入失败”。原码不进说明也不进诊断，用户报“上传失败 500”时无从查起。这属于禁止清单里的“静默吞错”。
如何核实：读 failureOf 与两处调用；grep `原码` upload-route.ts。触发需要项目子进程在租约内崩溃，未做实测，标为从代码推断。
建议改法：显式映射 target-gone、unavailable、not-provided → project-unavailable；timeout → unknown-outcome（写请求超时不知道结果）；其余 io-failed，并把原码拼进 message（`${written.code}: ${written.detail}`），记一条 warn 诊断（服务端入口已有 record 可用）。

== 未发现问题的方面 ==
- 路径包含：URL 里的 `..` 被请求自己折叠，`%2E%2E`、段内 `%2F` 解码出的 `..` 由 pathProblem 拒绝；`%2F` 解码成分隔符，等同于子目录，响应里的 address 与实际落盘一致（实测 `图%2Fsub/a.png` → `project://图/sub/a.png`）。NUL、反斜杠、空段由地址规则拒绝；根外链接 404 outside-root、指向 `.nbook` 的别名 404 protected-path、`.NBOOK/` 404（均实测）。

- 暂存：stage 在 fill 失败、取消、提交失败各路径都 discard 或 release；本轮所有实验（413、断开、冲突、rename）之后 `.nbook/staging/` 为空。
