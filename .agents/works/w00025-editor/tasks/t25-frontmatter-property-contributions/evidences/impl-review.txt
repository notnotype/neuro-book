## 1. 空的显示名通过 schema，面板上名字消失、输入的可访问名称变成空串
- 严重程度：重要；类别：正确性（前端专项：可访问名称）
- 位置：packages/neuro-book/src/plugins/markdown/shared/properties.ts:22-24（`label` 用 `TextSchema`）；packages/nb-markdown/src/editor/properties/MarkdownProperties.vue:111（`labelOf` 用 `??`）、:501、:521-540
- 现象：`label: ""`、`label: {}`（TextSchema 的语言映射允许零个键）、`label: "  "` 都是合格声明（`{name, label: ""}` 满足 minProperties: 2；`Value.Check` 实测返回 true）。窗口翻译端口把 `{}` 解析成 ""（`resolveLocaleMap` 末尾 `?? ""`）。`labelOf` 用 `descriptionOf(row)?.label ?? row.name`，"" 不触发回退。实测挂载 `describe: () => ({label: ""})`：名字列是一个无文字的 `<button title="（视角）">`（零宽、鼠标点不到，只能 Tab 到）；值输入 `aria-label=""`；收起摘要变成 "林雪 · 时间 · …"，视角那一项没有名字；`nameTitleOf` 给出 "（视角）"。读屏用户既拿不到显示名也拿不到真名，这正是计划要求“可访问名称用 label、title 带真名”要避免的情形。
- 如何核实：/tmp/review-w00025-t25/exp/probe.dom.test.ts（"empty label" 用例，配置 /tmp/review-w00025-t25/exp/vitest.config.ts，在 packages/nb-markdown 下 `bunx vitest run --config <该配置> -t "empty label"`），输出里能看到 `title="（视角）"` 与 `aria-label=""`。
- 建议改法：两层都防。(1) 取得层 `properties-catalog.ts`：`sources.text(label)` 结果 `.trim() === ""` 时不给 `label`（按“没给”处理，同没有声明）。(2) schema：字符串形态 `minLength`/`\S` 约束，语言映射 `minProperties: 1` 不好在共享的 TextSchema 里改，就只靠第 (1) 层。再补一条测试：空显示名的行照旧显示真名。

## 3. 点显示名改名、回车写回后，改成的新名字也有显示名时，焦点掉到 body
- 严重程度：建议；类别：正确性（键盘操作）
- 位置：MarkdownProperties.vue:206-217（settle 名字分支）与模板 :500-502（`v-else-if` 切换元素）
- 现象：点名字的按钮 → 变输入框 → 改成“视点”（另一个声明里 label 为“视点L”的名字）→ Enter。`settle` 清了 `renaming`，这一行的名字格马上变回 `<button>`，输入框被卸载，`document.activeElement` 是 `BODY`（实测，输出 `AFTER ENTER active: BODY`）。改成没有显示名的新名字时输入框留在原地，焦点不丢，所以只有“新名字也有声明”才掉焦点，很少见但没有处理。同一文件的 `remove`、`settle` 的新属性分支都写了“焦点不能掉到页面上”并用 `nextTick(focusStop)`，这里漏了。回车写回后焦点停在哪一格，Spec 输出 47–50 的键盘约定也没有说要掉到页面上。
- 如何核实：/tmp/review-w00025-t25/exp/probe.dom.test.ts 的 "rename keyboard focus"。
- 建议改法：回车结算后，若这一行回到按钮形态，`nextTick` 后把焦点给这一行的名字按钮（或值输入），与 `remove` 一致；或让改名后保持输入框直到离开。不改也行，但要么在 `.md` 里写明。

## 5. 显示名在别的属性的真名或显示名相同时，名字列与读屏名称无法区分；显示名按钮没有“属性名”语义
- 严重程度：建议；类别：正确性（可访问性）/ 设计
- 位置：MarkdownProperties.vue:501（名字按钮）、:521-540（各输入 `:aria-label="labelOf(row)"`）
- 现象：(a) 视角声明 `label: "地点"`，同一文件另有真名 `地点` 的行：实测名字列两行都写“地点”，两个值输入都是 `aria-label="地点"`，摘要里是“地点 林雪 · … · 地点 青石镇”；只有 `title` 才带真名（“地点（视角）”），而 title 在触屏与多数读屏下读不到。(b) 没有显示名的行，名字输入是 `aria-label="属性名：时间"`；有显示名的行，名字是一个 `<button>`，可访问名称就是“叙述视角”，读屏听不出它是“点了改属性名”，也不含真名。Spec 输出 60 写的是“各输入的可访问名称显示 label，名称的提示带真名”，实现按字面做了，所以问题在 Spec 层：读屏用户没有任何手段确认“叙述视角”对应哪个键，改名按钮的名称还和普通行的约定（“属性名：…”）不一致。
- 如何核实：/tmp/review-w00025-t25/exp/probe.dom.test.ts 的 "label same as other name" 用例（看输出里的两个 `aria-label="地点"`）。
- 建议改法：名字按钮用 `aria-label` = 已有目录键 `properties.rename`（“属性名：{{name}}”，带真名），可见文字仍是显示名；值输入的可访问名称可以用“显示名（真名）”与 title 一致。若开发者认为 label 重名属于贡献者自己的责任，写进 Spec 输出 60 的不承诺里即可，但按钮的名称仍建议修。

## 7. `describe` 每行每次渲染被调用约 4 到 5 次，每次重新校验所有 `markdown.properties` 声明；摘要与行可能给出不同的快照
- 严重程度：建议；类别：安全与性能 / 不变量
- 位置：MarkdownProperties.vue:102（`descriptionOf`）、:106、:111、:120（`kindOf`、`labelOf`、`iconOf` 各自调用）、:290-300（`summary` computed）；properties-catalog.ts:48（`declarations.list(...).filter(...)`）；nb-runtime/src/plugins/host.ts:293-302（`list` 遍历整张贡献目录，对本贡献点的每条登记重新跑 `#validation`，含一次 TypeBox `Value.Check`）
- 现象：实测（/tmp/review-w00025-t25/exp/count.dom.test.ts）5 行的面板一次挂载调用 `describe` 22 次，敲一个键重画一次又是 22 次（约 4.4 次/行）。`Value.Check(PropertyDeclarationSchema, …)` 实测约 10 微秒/次（/tmp/review-w00025-t25/bench.ts，Bun），每次 `list` 对每条声明做一遍，所以代价约为 声明数 × 10 微秒 × 4.4 × 行数 / 每次渲染；估算 30 条声明、20 个属性时每次按键约 26 毫秒（估算，未在真实页面量）。目前只有设定插件这类少量声明，不构成问题；但这是在输入框每次按键都跑的路径。另一个后果是同一次渲染里同一行被查多次，结果依赖“目录在这几次调用之间不变”，而 `summary` 是 computed（按响应式依赖缓存，声明变了不重算）、行是每次渲染现查，两处在“插件装卸后又触发一次无关重画”时会给出不一致的名字（摘要旧、行新）。这是已知限制“面板正显示着时插件增减不即时重画”的一个更具体的表现，不算新回归，但只要改成每行每次渲染查一次就能一并消掉。
- 如何核实：运行上面两个脚本；看 host.ts:298 的 `#validation(record)`。
- 建议改法：面板里用一个 `computed(() => new Map(rows.value.map(row => [row.name, props.describe?.(row.name) ?? null])))`，`descriptionOf` 查这张表（摘要与行共用同一份快照，声明变化的刷新语义不变：下一次 rows 或 locale 变化时更新）；若要严格保留“每次渲染现查”，改成在 `v-for` 里每行取一次再往下传。目录层也可以在 `createPropertyDescriptions` 里不用改。

## 8. `PROPERTY_KINDS` 与 schema 联合的“一致性检查”只检查一个方向；联合字面量在四处各写一份；`PROPERTY_KINDS` 没有使用者
- 严重程度：建议；类别：代码质量
- 位置：shared/properties.ts:17、:25、:31-33；web/properties-catalog.ts:26-30（`PropertyDescription` 副本）；lab/web/fixtures/index.ts:117（`kind?: "text" | "number" | …` 再写一遍）；nb-markdown model.ts 的 `EditableKind`
- 现象：`const _sameKinds: Array<NonNullable<PropertyDeclaration["kind"]>> = [...PROPERTY_KINDS]` 只证明数组里的每个字面量都在联合里；联合里多一项（例如有人加 `Type.Literal("complex")`）仍编译通过，注释却写“不一致时这里编译失败”。`PROPERTY_KINDS` 全仓库除这里与 `contracts.ts` 的再导出外没有使用者，schema 里的联合又手写了一遍五个 `Type.Literal`。web 端 `PropertyDescription` 副本与 nb-markdown 的 `PropertyDescription` 的核对是靠 `MarkdownControl.vue` 把 `DescribeProperty` 传给面板的 `describe` 属性时的赋值检查（vue-tsc 通过了，我跑了 web/backend/nb-markdown 三个类型检查都是 exit 0），也是单向：web 副本比 nb-markdown 窄时不报错。
- 建议改法：schema 用 `Type.Union(PROPERTY_KINDS.map(kind => Type.Literal(kind)))`（或相反，用 `Type.Unsafe`/`satisfies` 保证联合与数组互为子集），删掉再导出的 `PROPERTY_KINDS` 若没有消费者；或把检查写成两个方向（`Exclude<联合, 数组元素>` 为 never）。Lab 里的联合改成引用类型（`PropertyDescription`）。

## 9. 同名冲突的诊断只在“渲染到这个名字的行”时才记；`reported` 永不清空
- 严重程度：建议；类别：不变量 / 设计
- 位置：web/properties-catalog.ts:41-52；web/plugin.ts（`conflict` 回调）
- 现象：冲突检测寄生在 `describe(name)` 里：只有某个文件的面板里出现了 `视角` 这一行，才会记 `markdown.properties.conflict`。两个插件同时声明了 `视角` 但没有打开过带这个属性的文件，诊断面板里什么也没有；Spec 输出 61 写的是“同名冲突时被忽略的声明各记一条诊断”，没有说要等到用上。另外 `reported` 是 `Set<string>`，永不清空：插件卸载再装回（同一对 id）时，冲突解除又复现也不再记（只有第一次）；不会无界增长（上界是 id 对的数量），所以只是语义问题。诊断记录发生在 Vue 渲染里，属于渲染期副作用（`diagnostics.record` 在这里只是追加到 store，实测没有导致重复渲染）。
- 如何核实：读 properties-catalog.ts:41-52；集成测试 properties-contribution.dom.test.ts:99-105 的冲突用例里文件本身就带 `视角:`，所以没有暴露这一点。
- 建议改法：二选一，并在 Spec 输出 61 写明：要么保留“用到才记”（注释里写明理由，并在 `.md` 或 Spec 里说“冲突在第一次用到这个名字时记”）；要么在插件入口里按贡献目录整体检测（激活时与目录变化时对 `list()` 按 name 分组），不依赖渲染。对窄场景倾向前者，只是补一句说明。
