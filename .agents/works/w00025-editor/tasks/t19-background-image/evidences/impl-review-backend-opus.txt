### 2. 所有用例都走 body-limit 的流式分支，浏览器实际走的 Content-Length 分支没有被测到
严重程度：建议
类别：测试
位置：plugins/files/background-route.test.ts:63、87、105
现象：hono/body-limit 按请求头分两支：有 Content-Length 且无 Transfer-Encoding 时只比较头的值；否则逐块读并计数。测试的 put 用进程内 `new Request(url, {body: Uint8Array})`，Bun 1.4.4 不给它补 Content-Length（实测 bytesHasCL=false），所以 PNG、边界 20 MiB 这些用例全部走流式分支。浏览器 `fetch(url, {body: file})` 带 Content-Length，走的是另一支。“超过上限但带 Content-Length”这条路径没有用例。
为什么是问题：生产路径和被测路径不是同一分支，边界值只在流式分支上验过；升级 hono 或换限长写法时，真实路径出错测试不报。
如何核实：probe.test.ts 输出 {"bytesHasCL":false,"streamHasCL":false}。真实行为目前是对的：真实 Bun.serve 上 Content-Length: 20971521 只发 1 MiB 就收到 JSON 413 too-large（wire.test.ts）。
建议改法：在 put 上给字节请求显式写 content-length，或增加“超过 1 字节、带 Content-Length”和“正好上限、带 Content-Length”两个用例，判据是 413 too-large 与 200。第 1 条若改成经真实端口发请求，这条随之解决。

### 3. 超过 128 MiB 的文件得到空正文的 413，设置页显示 JSON 解析错误，不是“超限”；封面在前端先查了大小，背景图片没有
严重程度：建议
类别：正确性、与封面上传的一致性
位置：plugins/files/backend/background-route.ts:21；plugins/workbench/web/components/BackgroundSettingsPage.vue:42-45；对照 plugins/projects/shared/cover.ts:10、plugins/projects/web/components/ProjectInfoDialog.vue:146
现象：Bun.serve 没有设 maxRequestBodySize，默认 128 MiB。Content-Length 超过它时请求到不了分发和路由，Bun 直接回 `HTTP/1.1 413 Request Entity Too Large` + `Connection: close`，正文为空。前端 `await response.json()` 抛错，落到 uploadFailed，显示的是 JSON Parse error: Unexpected EOF。
为什么是问题：workspace/files.md 要求超限 413 `too-large`，ui/backgrounds.md 的失败表要求设置页显示原因（超限）。21 到 128 MiB 的结果正确（JSON too-large），问题只在 128 MiB 以上，比如一张未压缩的大扫描图。封面的做法是把上限放在 shared/cover.ts，前端发请求前就比较 file.size；背景图片把 BACKGROUND_MAX_BYTES 放在 backend/background-route.ts，前端拿不到，所以没法这样做。这也是“相邻上传不一致”的具体后果。
如何核实：wire.test.ts 对 Content-Length: 135266304 的原始响应是 "HTTP/1.1 413 Request Entity Too Large\r\nConnection: close\r\n\r\n"；probe.test.ts 用真实 fetch 传 129 MiB 得到 {"big":413,"body":"","parsed":"SyntaxError: JSON Parse error: Unexpected EOF"}。Chrome 上可能表现为连接被重置而不是 413（未验证），两种都不是“超限”的提示。
建议改法：把 BACKGROUND_MAX_BYTES 移到 plugins/files/shared/contracts.ts（BACKGROUND_UPLOAD_URL 已经在那里），设置页发请求前比较 file.size，超限直接显示 backgrounds.failure.tooLarge，服务端的限长不变。这同时省去把大文件发到服务端再被拒。前端部分的改动归前端审查者一并看。

### 4. 冲突分支重读整个文件比较摘要，提交的结果里已经带着当前摘要
严重程度：建议
类别：代码质量
位置：plugins/files/backend/background-route.ts:68-72
现象：written.code === "conflict" 时再调一次 existing()，重新 lstat 并把文件整份读进内存算哈希。而写入接口的冲突结果已经带 `current: {hash}`（ServerFilesResult 的 current 字段；decide 在写入锁里算出）。existing() 返回 null（文件在冲突后又被删）时会走到第 72 行，得到 500 且 code 是 conflict，状态码和错误码互相矛盾。
为什么是问题：多一次最多 20 MiB 的读取，多一个 Bun.file 可能抛错的位置（见第 5 条），还多一条状态码不对的路径。这条分支的判断其实一行就够。
如何核实：concur.test.ts 打印的冲突结果：{"ok":false,"code":"conflict","detail":"backgrounds/915a….jpg 已存在","current":{"hash":"915a…"}}，hash 与文件名相同。实测这条分支确实走到（5 轮并发每轮一次 conflict），测试“两个窗口并发”是真竞争，不是碰巧串行。
建议改法：`if (written.code === "conflict") return written.current?.hash === digest ? Response.json({address}) : failure(409, "conflict", ...)`。前面的第一次 existing() 另按 report.txt 第 2 条的修法处理。

### 5. 路由抛出的异常被 Hono 默认处理器吞掉：纯文本 500、没有诊断（base 上就有，这条路由也踩到）
严重程度：建议
类别：不变量、诊断
位置：plugins/files/backend/background-route.ts:41、59；plugins/http/backend/dispatch.ts:139-145（base）
现象：background-route.ts 第 41 行读请求体、第 59 行 Bun.file 读文件都可能抛错。Hono 应用没有设 onError 时，默认处理器 console.error 后返回 text/plain 的 "Internal Server Error"，所以 handler.fetch 不抛，dispatch.ts 的 reportError 和 JSON 形式的 internal-error 都不生效。plugins 与 server 下没有任何 `.onError(`，这对所有 Hono 写的插件路由都成立；dispatch.test.ts:119 的用例用的是裸 `{fetch: () => {throw}}`，所以它通过而真实路由不走这条路。
为什么是问题：DispatchOptions 注释写“处理器抛错时的诊断”，实际插件路由的错误进不了诊断，只到标准错误。对这条路由有两个可观察后果：已存在的文件读不出来（权限 000）时响应不是 {code, detail}，设置页显示 JSON 解析错误而不是原因；客户端中途断开时标准错误打一整段 DOMException。后者每次取消上传都会发生。前者少见，单独不值得报，所以按 base 问题记一条。
如何核实：concur.test.ts：chmod 000 的同名文件得到 {"unreadable":500,"type":"text/plain; charset=UTF-8","body":"Internal Server Error","reported":0}，同时标准错误有 EACCES 栈。wire.test.ts：六种断开方式 errors=0，标准错误都有 AbortError。
建议改法：在 base 上单独修，不放进本 Task：让插件路由的错误能到分发层（例如给各 Hono 应用设把错误重新抛出的 onError，或由 http 插件提供建应用的工厂，未实测），断开类错误不当错误报。本路由可以只做一点：第 59 行的读取失败转成 failure(500, "io-failed", ...)。

### 未发现问题的方面（仔细检查后没有发现，均为真实 Bun.serve 实测）
- 请求体上限（无 Content-Length）：原始 chunked 持续发 400 MiB，收到 413 too-large 时最多发出 25 MiB；此后 Bun 丢弃后续字节、连接不断，RSS 全程只增 23 MiB，不留文件和暂存。上限确实有界。body-limit 不取消 rawReader 没有造成内存增长。
- 中途断开：chunked 与 Content-Length 各配 destroy、FIN、RST 共 6 种，都没有把截断的请求体当完整内容提交：无文件、无记账、无暂存残留，在途计数归还（排空能结算）。
