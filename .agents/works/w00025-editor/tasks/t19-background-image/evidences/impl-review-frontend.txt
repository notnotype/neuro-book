[2] 重要 / 交互正确性 / 遮罩滑块松手或按键后先弹回旧值，写入回来才到新值
位置：packages/neuro-book/src/plugins/workbench/web/components/BackgroundSettingsBlock.vue:55、62、112-120（draftScrim、shownScrim、onScrimCommit）
现象：onScrimCommit 一上来就 draftScrim.value = null，shownScrim 立刻回到 imageValue.scrim（设置里的旧值），这时才发出 change。settings.update 不是乐观更新（plugins/settings/shared/instance.ts:250-266，先 await link.write 再 apply），所以从松手到写入回来这段时间，滑块受控值和预览遮罩都回到旧值，再跳到新值。
为什么是问题：1) 松手后拇指和预览先回弹再前进，用户会看成“没生效”。2) 键盘：Reka SliderRoot 每次方向键都是 update 加 valueCommit（node_modules/reka-ui/dist/Slider/SliderRoot.js:128、175），下一次按键从受控的旧值起算，按住方向键时步进丢失。3) 设置里已有的 value-commit 语义（输出 9 “松手才写”）要的是“写之前不写”，不是“写之前显示旧值”。
如何核实：把 settings.update 的 link.write 延迟 300ms（或看 e2e 慢机），松手后看滑块数值；或 vue test 里 stub update 返回未决 Promise，断言松手后 [data-background-scrim-value] 仍是新值（现在会变回旧值）。
建议改法：commit 时保留 draft，等 props.value.scrim 变成提交的值（watch）或写入失败（Page 的 write 返回结果交回 Block）再清；写入失败时清 draft 回到旧值，符合“显示保持原样”。

=== 建议 ===

[7] 建议 / 界面规范 / 缩略图焦点环手写，选中态与焦点态看起来一样
位置：BackgroundSettingsBlock.vue:190-191
现象：焦点环是手写的 outline 类（focus-visible:outline-2 focus-visible:outline-[var(--accent-main)]），选中态是 outline-2 outline-[var(--accent-main)]。选中的那一张拿到键盘焦点时，外观与未聚焦的选中态完全相同。
为什么是问题：ui-development-spec 自检清单（“同类交互状态一致”）要求复用基座类 nb-ui-focus-ring（nb-ui/src/styles.css:56），不手写近似样式；键盘用户看不出焦点在哪张选中的图上。
建议改法：按钮加 nb-ui-focus-ring，选中态用另一种表示（例如加粗的 outline 偏移，或角标），不与焦点环同色同宽。

[8] 建议 / 竞态 / 上传期间切了种类或另选了图，上传完成后仍按“选中这张”覆盖用户的选择
位置：BackgroundSettingsBlock.vue:123-135（onFile 里 await 之后无条件 pickImage）
现象：上传进行中把种类切到“无”或“纯色”，或在图库里点了另一张，上传一完成就 pickImage(result.address)，写出 {kind:"image"}，随后 watch(props.value.kind) 把 mode 拖回 image。
为什么是问题：用户的最后一次操作被覆盖。组件卸载后的 emit 是无效的（所以退出设置窗口那种不算），这里指同一页内。
建议改法：开始上传时记下 mode 与一个序号，完成时 mode 还是 image 且序号一致才选中；否则只刷新图库。

[9] 建议 / 失败语义 / 写入失败后种类选择器停在新种类，与真实显示不一致
位置：BackgroundSettingsBlock.vue:76-88（selectKind 先改 mode.value 再 emit），watch 只在 props.value.kind 变化时同步（:36）
现象：设置原来是 image，用户点“无”，写入失败（例如用户层文件不可写，Page 的 write 走 reportWriteFailure）：mode 已是 none，设置仍是 image，真实显示还是图。因为设置的 kind 没变，watch 不触发，选择器一直停在“无”。
为什么是问题：spec 失败表“设置写入失败：设置页显示原因，显示保持原样”，选择器本身属于显示。
建议改法：selectKind 不预先改 mode（除了“图片但还没有图”这种不写设置的情形），写成功后由 watch 带过去；或写失败时由 Page 把结果交回，Block 把 mode 重置为 props.value.kind。

[10] 建议 / 性能与交互 / 自定义色的取色面板每次拖动都写一次设置
位置：BackgroundSettingsBlock.vue:90-99（pickColor 直接 emit change），nb-ui ColorPickerPanel.vue 的 set() 每一步都发 update:modelValue
现象：拖取色面板，每一个 pointermove 都经 Page 的 write 走一次用户层设置写入（文件写、快照、所有窗口同步、各编辑组重新读颜色和 getComputedStyle）。当前明暗下中途的不合格色会弹错误、不写，面板拇指却停在不合格的位置。
为什么是问题：滑块有“松手才写”的约定（输出 9），取色面板没有；写入频繁。
建议改法：用本地草稿在拖动时只改预览，面板关闭或停顿后再写，或者只写通过检查的值并把面板拇指约束回上一个合格值。

[11] 建议 / 正确性（边角）/ 采样用非线性亮度挑最亮最暗，格数固定 64，与显示尺寸无关
位置：use-background-image.ts:59-75（level = 0.2126*r + 0.7152*g + 0.0722*b 对 8 位通道直接加权），:55-57（非 repeat 时固定 64 格）
现象：1) 挑“最亮、最暗”的排序用伽马编码值的加权和，而 contrast() 用线性化后的相对亮度；饱和蓝（0,0,255）的 level 为 18、灰 40 的 level 为 40，排序里蓝更暗，但相对亮度蓝 0.0722 大于灰 0.021，选出的“最暗”不是真正最暗的。2) 注释写“每格约等于模糊半径”，但格数固定 64：显示宽度约 1800px 时格宽才等于 σ=14px 的模糊；4K 宽屏或大窗口里格宽 60px，比实际模糊粗一倍多，小而极亮的细节被平均掉，真实的最亮最暗比算出的更极端。窄窗口则偏保守。
为什么是问题：下限是“保证 4.5”的依据，两处都可能让个别图在极端屏幕下低于 4.5。影响面不大（需要饱和色或大屏加小而极端的细节），所以只是建议。
如何核实：从代码推断。用 /tmp/t19/sonnet-exp/ 里建一张 4000×2250、中间有 20px 白点的黑图，4K 窗口截图量对比度。
建议改法：排序用线性化后的相对亮度（background-legibility.ts 的 luminance 导出来复用）；格数按显示宽度除以 σ 取，或固定取更细（例如 128）并把注释改成真实依据。

[12] 建议 / 视觉 / 窗口背景下标签条叠了三层半透明，比其它卡片实得多，活动标签与正文接不上
位置：EditorGroup.vue:406（.editor-group__header background: var(--editor-tabs-surface)）加 EditorTabBar.vue:242（.editor-tabs 又是 var(--editor-tabs-surface)）加外层 EditorArea.vue:125（--shell-card-surface）；EditorTabBar.vue:276、280
现象：WorkbenchShell.vue 注释写“里层透明、不透明度不相乘”，但标签条外层 header、内层 .editor-tabs 都画 face(tabs)，再叠 EditorArea 的卡片面：scrim 0.75 时有效不透明度约 1-(0.25)^3 = 0.98，标签条看起来几乎是实心。活动标签 is-active 是单层 --shell-card-surface，叠在实心的标签条上，颜色与它下面的正文区域（只有一层）对不上，“活动标签从正文里长出来”的效果破了。.editor-tab-frame:hover 的 color-mix(--panel-surface 50%, --editor-tabs-surface) 也用不透明的 --panel-surface，悬停时那一块更实。
为什么是问题：非对比度问题（更实只会更清楚），是视觉不一致；从代码推断，需要截图复核。
建议改法：窗口背景下让 .editor-tabs 本身透明（只由 header 画），hover 的混合用 transparent 代替 --panel-surface，或为标签条另设变量。

[13] 建议 / 层叠 / 编辑器控件还没交付时的“正在加载”提示被遮罩盖住
位置：EditorGroup.vue:342-349（BackgroundLayer 是第一个子元素，absolute）与 :365（.editor-group__pending 非定位）

[15] 建议 / 规范 / 组件文档的“验证入口”写错，BackgroundLayer 与设置页组件没有 Lab 场景

[16] 建议 / 代码质量 / 重复的观察者与诊断，编辑组特有的开关放在颜色模块里
位置：EditorGroup.vue:249-264（useBackgroundImage 里已有一份 useDocumentThemeVersion，EditorGroup 又自己调一次 backgroundTheme）；BackgroundSettingsBlock.vue:29（同样两份）；use-background-image.ts:95-108（report 每个实例都调）；document-colors.ts:91-99（setEditorTransparent）

[18] 建议 / 无障碍 / 状态行是条件渲染的 role=status
位置：BackgroundSettingsBlock.vue:233
现象：<p v-if="status !== null" role="status"> 是出现时才插入 DOM，多数读屏器不会播报动态插入的 live region（要先有空的 live region 再改内容）；错误态应更强（role=alert）。
建议改法：外层始终渲染 role=status 的容器，内容变化；错误用 role=alert。
