### 1. `user://` 的根内检查不等于 `backgrounds/` 子目录隔离
严重程度：重要
类别：安全与性能
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:44-46；审查 worktree packages/neuro-book/src/plugins/files/backend/rooted.ts:157-200、241-254、349-374。
现象：计划只说“只允许 user://backgrounds/”，没有定义链接解析后仍须落在该子目录。现有 RootedRoot 的包含检查只保住整个 user 根，允许指向同一 user 根内其它目录的链接；提交还会跟随已有文件最后一段的链接。
为什么是问题：例如 `<user>/backgrounds -> <user>/notes`，请求地址即使由服务端生成 `user://backgrounds/<sha256>.png`，现有 resolveSlot 仍把实际新文件放进 notes。它没有越过 user 根，因此常规“路径越界”测试会通过，但已经违反上传路由自己宣称的写入范围；允许覆盖时，最后一段链接还有同类问题。不需要恶意并发替换，预先存在的一条链接就够。
如何核实：代码核实：rooted.ts:192 只比较 this.real（user 根），:195 返回真实相对路径；:248-254 把解析后的父目录用于创建；:350-357 明确跟随最终目标。需在 S1 真实文件服务测试增加 backgrounds 指向根内其它目录、根外目录、悬空链接、最终文件链接四种场景，核对被拒且目标目录未改变。尚无新上传路由，未把本发现写成已运行的上传漏洞。
建议改法：明确 backgrounds 必须是 user 根内的真实目录、不可为符号链接；服务端只生成单段哈希文件名，目标已有时不得跟随链接当成可复用文件。若有意支持目录链接，则须按真实路径再核对 backgrounds 的子目录边界，并在提交时沿用既有根身份与冲突保护，不能只做字符串前缀检查。

### 2. 新 HTTP 写入口没有接入现有暂存、来源、记账与变更链的合同
严重程度：重要
类别：不变量
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:44-46、65；主工作区 docs/specs/workspace/resources.md:61-80、100-128、153；审查 worktree packages/neuro-book/src/plugins/files/backend/plugin.ts:48-61、155-184、205-211，http/shared/contracts.ts:12-27。
现象：计划从“浏览器没有二进制 write”直接跳到“新增写字节路由”，没有说明 HTTP 上传怎样转入 Files 的既有提交链、写入归谁。服务端其实已有 WorkspaceFiles.stage/write（二进制 Uint8Array、流式 sink）；现有 raw-route 只拿 RootedRoot，不持有 changes、ledger、scope 或调用方身份。HTTP 的 HttpRouteEnv 也没有远程合同中的 ConsumerIdentity。
为什么是问题：把 raw-route 扩为直接 fs 写入不会自动获得活性锁暂存、原子提交、精确 created 事件、回声抑制、记账槽和入口停止等待；只靠文件 watch 至多报 external，且没有订阅就不保证及时发现。直接套服务端插件的 WorkspaceFiles 门面，来源又会是 system，而不是这次浏览器用户操作。resources 合同规定所有写入走唯一入口、来源不能由请求自报，并在锁内按“提交 → 记账 → 回声/事件”结算；新传输入口不是豁免。断线、类型拒绝、超限、磁盘写满与进程中断如何丢弃暂存，也因此没有可执行的约定。
如何核实：代码核实：execute.ts:31-55 的 WriteTarget/saveText、staging.ts:70-97 的活性锁与 discard、:196-227 的提交/记账/事件、workspace-files.ts:184-203、367-410 的 fill/settle。现有 workspace-files.test.ts:119-168 已覆盖 8 MiB 二进制、抛错与取消后目标不变且暂存不留；ledger.test.ts 是独立记账合同。S1 当前只列“类型、大小、路径越界”，没有来源、事件、ledger 或中断场景。实际运行结果另列于末尾。
建议改法：新路由应并入 nbook.files 现有 server 入口的一份 http.routes 贡献（/api/nbook.files/），以薄传输层调用既有暂存/提交实现，不另造磁盘写入权威。明确上传的可信用户来源（由服务端固定并验证，不收业务参数 as/source），把 request.signal 与入口停止信号交给暂存过程；明确提交前失败不改变目标、确定失败清暂存、结果未知保留由现有恢复机制收口。提交成功照常进入 user 根的 ledger 与 changes，不承诺此时已有持久 History 贡献者。为来源、精确事件、回声、记账失败不反报写失败、取消与写满补 S1 验收。

### 3. “图片类型受限 + 按哈希命名”还不足以接上现成 raw 路由
严重程度：重要
类别：正确性
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:46、79；审查 worktree packages/neuro-book/src/plugins/files/backend/raw-route.ts:27-56、177-190；packages/neuro-book/src/plugins/projects/shared/cover.ts:53-59。
现象：计划没列允许的图片格式、判定方法和哈希文件名的扩展名规则，也没说明 SVG 与动图怎么处理。raw 路由不探测内容，只按地址最后一段的扩展名返回 Content-Type；无扩展名的 `<sha256>` 一律是 application/octet-stream。上传时的 File.type、Content-Type 或原文件名不能充当内容证明。
为什么是问题：照“按哈希命名”存成裸哈希，再照计划交给现成 rawUrl，并不会得到计划隐含依赖的 image/* 响应；保留用户给的扩展名又会使同一份字节因 a.jpg/a.jpeg/a.png 产生不同键，破坏去重及响应类型的一致性。SVG 是 XML，没有可当作图片安全证明的固定 magic；GIF、APNG、WebP 也可能有动画，单看图片魔数不能兑现第 79 行“不做动图”。现有 raw 响应已经带 CSP sandbox 与 nosniff，不能把“允许 SVG 就必定可执行应用同源脚本”当成现存漏洞，但这也不替上传入口决定格式白名单。
如何核实：代码核实：raw-route.ts:52-56 对裸哈希返回兜底类型；:190 使用请求路径推导类型。已有封面路由 cover-routes.ts:87-90 先 sniffCoverType，再由服务端类型映射生成扩展名，且明确拒绝 SVG；这是可沿用的现成规则。S1 需验证真实 PNG 配假文件名/假 MIME、相同字节换文件名、SVG、非图片、截断头与动画容器；当前新路由尚未实现，不能声称这些上传测试已通过。
建议改法：在计划固定白名单与规范文件名 `<服务端计算的 SHA-256>.<按字节判定的规范扩展名>`，不接收客户端目标名与客户端哈希作为权威。最小方案明确只收指定栅格格式、拒绝 SVG；若坚持支持 SVG，另定解析/净化及显示上下文合同，而不是按 image/svg+xml 自报放行。对“动图不做”明确是拒收还是只承诺静态显示，并按该决定检查相应容器字段。保留现有 raw 的 sandbox、nosniff、no-cache 与跨站拒绝，不为背景图放宽 CORS。

### 4. 20 MB 只有产品口号，没有传输层可执行的上限
严重程度：重要
类别：安全与性能
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:46、65；审查 worktree packages/neuro-book/src/plugins/http/backend/plugin.ts:74-83、dispatch.ts:137-146；projects/backend/cover-routes.ts:69-89。
现象：计划没有决定上传方法、请求体编码、20 MB 是 20,000,000 还是 20,971,520 字节，也没区分文件上限与整个请求体上限。通用 HTTP 分发器只把标准 Request 原样转交；没有替此路由施加 20 MB 限额或读取背压。若等 formData()/arrayBuffer() 完成再看文件大小，检查发生时整个超限正文已经读完。
为什么是问题：不带 Content-Length 的流式请求、虚报长度或 multipart 携带额外大字段，都能绕过仅检查请求头或 file.size 的早期限额；“最后回 413”也保护不了之前的内存/磁盘消耗。20 MiB 整份内存化时，每个并发请求光文件字节就有 20,971,520 字节，10 个为 209,715,200 字节，尚未算表单解析、字节复制与 raw 读取。用户写盘中断/写满时还要保证不会发布半份最终文件，不能只覆盖正常的大小测试。
如何核实：代码核实：通用 HTTP 的 Bun.serve 未设置本业务上限；现有封面路由已用 hono/body-limit 在接收时限长，文件 5 MiB + multipart 64 KiB 包络，并再次核对 file.size；cover-routes.test.ts:131-150 用无 Content-Length、256 KiB 分块的流验证收到 413 时没读完整个正文。本次执行该合同测试包含在 8 文件命令中，整体结果见末尾，非新上传路由的验证。
建议改法：固定 POST/PUT 与原始二进制或 multipart 的一种合同，列出精确最大字节数、状态码与错误体。原始字节的单文件入口最简单：读 Request.body 时逐块累计并 await 暂存 sink.write，超限即停读、取消 reader 并丢弃暂存；使用 multipart 则给整个请求体另设有限包络、拒绝多余文件/不受限字段。前端 File.size 只用于提前反馈，服务端仍按实际收到字节强制限制。S1 增加无长度流、超限中止、客户端断开与写满失败后的目标/暂存状态断言。

### 5. 哈希命名没有定义“已有同名文件”的结果，现有 absent 提交不会自动去重
严重程度：重要
类别：正确性
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:46、65；审查 worktree packages/neuro-book/src/plugins/files/backend/staging.ts:196-227；backend/staged-commit.ts:76-110、142-165；files/workspace-files.test.ts:140-188。
现象：计划把“按哈希命名”当成“同一张不存两份”的完整机制，但现有提交合同没有“已存在且相同即复用”的分支：expect=absent 一遇已有目标就 conflict；expect=any 则真覆盖、再记账/发事件。先查是否存在、随后普通 rename 也不是排他去重。
为什么是问题：两个窗口同时选同一张图，现有 absent 提交只会让一方成功，另一方冲突；重复上传一张已经存过的图也一样。若把所有 EEXIST 当成功，又会把同哈希文件名下被外部改坏的字节、目录或链接当成有效图片。若改用覆盖，已经被其它窗口引用的内容会在未核对现状的情况下替换，破坏哈希名代表固定内容的前提，产生额外 write 事件与账本记录。
如何核实：代码核实：staging.ts:203 在已存在时返回 conflict 并附 current.hash；staged-commit.ts 在写入锁内判定，再用排他 link/复制提交 absent。现有 workspace-files.test.ts:170-188 断言并发 absent 与 create 恰好一方成功，不提供幂等成功。实际运行包含此用例，本次 8 文件结果见末尾。
建议改法：固定服务端 SHA-256、规范扩展名及结果 `{address, ...}`；首次使用 absent 排他提交，冲突时只在目标是允许的普通文件、当前字节摘要等于本次摘要时返回同一个地址，并丢弃本次暂存；内容不同或类型不符明确报冲突/资产损坏，不覆盖、不自动删。复用不再发 created/write、不重复记账。哈希收齐之前的暂存与最终地址绑定要写清：现有 stage(address, ...) 要先有目标地址，不天然支持“流完才决定名称”；选定有界内存预哈希或在现有暂存实现内增加完成后定址，不能另建无清理 owner 的第二套临时文件。S1 增加重复上传、两个窗口并发同内容、预占坏文件三项验收。

### 6. image:string 与 scrim:number 没有把地址和可读性限制变成配置合同
严重程度：重要
类别：正确性
位置：主工作区 .agents/works/w00025-editor/tasks/t19-background-image/plan.md:12-24、30、46；docs/specs/settings/configuration.md:65-78、131-144；审查 worktree packages/neuro-book/src/shared/settings.ts:181-208、248-281，plugins/settings/shared/layer-text.ts:41-65。
现象：计划只有 TypeScript 联合类型和“image 是 user:// 地址”的注释；没有写出设置 schema。一个 Background 类型又同时包含 color 分支，无法单靠这份类型保证窗口设置只有 none/image。scrim:number 也不包含 75–100 的约束。配置层接受何值只由 TypeBox schema 决定，不会理解注释或设置页滑块。
为什么是问题：用户可直接编辑 settings.json 或设置文件视图，不必经过上传或滑块。把类型直译为 image:Type.String()/scrim:Type.Number()，则 scrim=0、image='project://...'、越界地址和窗口的 color 分支都可进入有效快照并即时同步到所有窗口；上传路由仅允许 backgrounds 对这些入口不起作用。rawUrlOf 还本来就支持 project:// 与整个 user://，不是背景地址验证器。于是“用户层/所有作品共用/遮罩不低于 75%”只对正常点击路径成立。
如何核实：代码核实：settings 的默认值与层文件均经 Value.Check(schema, value)，没有每个配置项的第二套业务验证器；rawUrlOf 仅 parseResource 后转 URL，user 根下任意合法路径都可返回。defineSetting 本身能表达对象判别联合，现有接口不构成阻碍。用实际配置服务定义原样宽松 schema，再从一个窗口写 scrim=0 或 project://，另一个窗口能读到该值；收紧 schema 后应返回 invalid-value，外部无效项应被丢弃但原文件保留。该专项运行结果另列于末尾。
建议改法：第 1 节写出两份可 JSON 序列化的 TypeBox 判别联合：editor=none/color/image，window=none/image；对象拒绝额外字段，image 仅允许有效的 user://backgrounds/<规范文件名>，fit 固定三值，scrim minimum=75、maximum=100，默认完整值 {kind:'none'}，切到 image 时显式填 scrim=85；声明 layers:['user']。读取后仍经资源解析器核对字节长度/路径，永不把设置字符串直接交 CSS url 或接受远程 URL。文件是否存在、能否解码是独立的运行状态：保留配置引用、只退回显示，不因短暂失败自动把全局设置改成 none。
