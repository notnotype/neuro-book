# 小说记忆模型设计与数据结构 spike

## 目标

把「小说剧情如何进入可检索的记忆结构」从设计文档推进到可运行的数据结构，并提供一个数据查看器，让开发者直接看模型装下真实剧情之后是什么样。

**定位是全新模型。** 不在 `packages/nb-memory/` 基础上演进，也不受其既有决策约束；spike 独立建库、独立验证。`nb-memory` 只作为先验参考。若本模型验证效果好，再单独讨论是否替换其模型。

本 Task 的代码只在 Task 目录内，是 spike 产物，不是业务源码：不写 `packages/`、不改公开 API、不建数据库、不接任何产品模块。

来源是开发者与 Agent 的一次长对话：从人类记忆的分类（情节记忆 / 语义记忆 / 个人语义）出发，推导一个用于 LLM 外部记忆的实体模型，再用样书第一章做落地检验。t01 提供了样书第一章的既有证据与 canonical 摘要。

## 开发者参与

2026-08-28：设计文档审查通过。两条结论已写回：

1. `Summary` / `Question` / `Mention` 是**可选三类**，不是核心模型；核心是 `Kind` / `Individual` / `Predicate` / `Fact` / `Episode` 五类。
2. 第 11 节的 9 条设计选择全部采纳，其中 D5、D7 为「同意方向、结论待实测」，分别落到 spike 的 S2 与 S1。

随后开发者要求先 spike 数据结构、加数据查看器、页面改亮色，本轮据此交付上表七个文件。

（这一段记的是 v2 那一轮。当时的 `viewer.html` 按 `Individual.since` 切片、`Alias.since` 改名，那套字段在 2026-09-02 那一轮已经不存在了；同一件事现在由 `chapter-01.json` 的披露段号和 `schema.ts` 的 `displayName()` 承担，效果一样。）

**2026-08-31：模型立场被推翻，本 Task 重开。** 开发者在 `t03` 的讨论中指出两件事，都成立：

1. **`storyAfter` 是错误设计。** 它要求模型在世界时间线上给场景排序，而文本不给这个信息。`t03` 那次真实 S1 调用同时**算错了 `storyAfter`、抄对了 `storyOffset`**，正好把这条分界跑了出来。
2. **模型记错了东西。** 现在的 `Fact` 和 `Episode` 在记「世界里什么为真」，但我们是读者不是作者。「现在爱丽丝深爱着罗兰，殊不知三年前她对他恨之入骨」——翻转点在哪，文本永远不说，世界真相模型只能编一个或者留一个它没有词汇去描述的洞。开发者提出改记**读者视角**：图里存的是「文本向读者披露了什么」。

本轮据此交付 `memory-model-v3.md`，**只写设计，不动任何代码与数据**。开发者已裁定两条范围：产物落在 t02 内、先只写文档；本期只做读者视角，给上帝视角（World Engine）留一个对齐点即可，不定义差值算法。

v3 里 8 条待裁决（V1–V8）需要拍板，其中 V1（`Fact` 改名 `Disclosure`）和 V8（第一章数据集迁移还是重建）决定下一轮的工作量。v2 第 11 节那 9 条设计裁决里，至少 D5 与 D7 的度量口径要重开（见 v3 的 V7）。

**2026-09-01：补上 v3 缺的另一半，交付 v4。** v3 只说了记什么，没说正文怎么切开。开发者在这一轮里连续推翻了三处设计，都成立：

1. **`Fact` 不能是派生函数。** v3 把 `Fact` 改成了一个求值函数，但函数的返回值没有 id，导航不过去；而「苏天晴的关系网是什么」这类问题恰恰要按主体导航到事实节点。改成 **`Fact` 是槽（主体 + 谓词），值由披露填**，身份和值拆开，两边都要得到。**v3 的待裁决 V1 因此作废**——不是改名，是拆分。
2. **逐段打标签没有意义。** 开发者原话：「不如直接引用原文，把 prose 拆成多个区段才有用」。标注的载体是区段不是段，产物就是那份区段表。这一层最后定名 **Beat**。
3. **场不是叙述的基本单位。** 小说里不止有剧情，还有副文本（三国演义开头那首诗、本书第 3 段的作者声明）、设定说明和系统通知，这些进不了场。改成 Beat 全覆盖、场从 Beat 派生之后，它们各归各位。

开发者另外裁定四条范围：场不跨章、场改成 Beat 序列上的区间、本 spike 不做 Thread、预制类等模型跑起来之后再考虑。

本轮交付 `memory-model-v4.md`、`evidences/chapter-01-beats.json` 与 `beats-viewer.html`，**仍然只写文档、人工数据与查看器，不动任何现有代码与数据**。v4 的第 11 节有 8 条待裁决（W1–W8），其中两条挡着后续工作：W1（槽在「读」的时候建还是等「做梦」阶段建）决定抽取管线那一节能不能写完；W8（视角怎么存）是开发者追问「视角漂移是什么」时暴露的——三处漂移里只有一处能从现有字段算出来，另两处的载体是「叙述者 + 带保留」，持有者按定义为空，现在只能靠 `povDrift` 人工标注。

**2026-09-02：补第 5.7 节「时刻」。** 开发者指出 Moment 没怎么设计。核对下来属实：v3 的第 3.3 节写过一版，**v4 第一版漏抄了**，只在词表里留了一句「故事时间的身份锚」。补写时在第一章上翻出两处，都是原设计会出错的地方：

1. **锚点写成时刻会凭空造出一条推论。** 相对时间词（「五分钟前」）原先锚到场的时刻 `M_a` 上，而 `M_a` 是一条从第 5 段铺到第 77 段的区间。第 16 段的「五分钟前」和第 29 段的「两分钟前」都锚到它，直接推出「面摊比开场白早 3 分钟」——文本没说过这句。改成锚在各自的叙述位置（叙述当下）之后，只能推出「开场白至少比面摊晚 3 分钟」，一个老实的下界。
2. **有一个时刻从来没被演出来。** 第 29 段说古书「重复了一遍两分钟前的开场白」，而那次原话在正文第 5 段之前，读者没读到过。这一刻没有 Beat、不属于任何场，却被一条量化的时间关系指着——**证明时刻不能由场生成**，v3 的 `Moment.ofEpisode` 方向是反的（那个字段现在还是悬空引用，`Episode` 节点早已删掉）。

另外改了 v3 三处：`approx` 字段删掉（精度由单位承担，「大约」由来源的保留度承担）；`Moment.label` 只许存绝对时间词（「三年前」当名字等于存了一条没锚点没来源的时间指示，违反规则 6）；时刻关系的宾语拆成锚点加偏移。**新增待裁决 W9**：跨章的两个「当下」默认没有关系，于是第 5.6 节的判据会把全书绝大多数同槽披露推进人工队列，需要拍板放宽哪一头。

**2026-09-02：把数据、算子和页面全部换到 v4。** 开发者要求「用这个 v4 的设计去更新 v4 的 json 金标和几个 html」。做法上有一处自己拿的主意，先说明：**v4 的模型有两半，而当时的金标只覆盖了一半**，所以把第一章拆成两份真源——`evidences/chapter-01-beats.json` 记正文怎么切，`chapter-01.json` 记记住了什么，靠段号和主体 id 对接。这等于把 W6（迁移还是重建）按「重建」结了，方向与 W6 自己的倾向一致。

装数据的过程翻出四件事，都记在两份 JSON 的 `findings` 里：

1. **第 5.6 节那张表少一行。** 五行判据默认两个值互斥，而互不互斥由**基数**说了算。不看基数就照表判，第一章会凭空判出三处「竞争」（同一个人的两个愿望、同一份契约的两个相对方、同一条尾巴的外观与触感）。补第六行「并列累加」，这不是新裁决，是把第 5.3 节已有的基数接进第 5.6 节。
2. **模型给了一个错答案，记为 W11。** `(契约, 契约状态)` 读完全章为真的是「尚未签订 \| 成立 \| 成立」——三条披露的 `timeRef` 都是 `M_a`（整场对话是一个区间），来源通道不同，判成「认识论并存」，两个互斥的值一起留着。文本里这明摆着是先后。出口只有一个：**承认叙述位置可以在同一个时刻内部排序**。走查页最后一段就是这个错答案，没有遮。
3. **「造物主」「魔法少女」这类词各要两个节点，记为 W10。** 一个类（回答「谁属于它」），一个主体（回答「它自己有什么属性」）。v4 没说这两个节点怎么连，现在靠名字撞上才看得出来。
4. **尾巴的外观和触感判不了，记为 W12。** 绕法是把谓词基数写成多值，可她只有一条尾巴，这个名分不正当。

顺带补了第五个时刻 `M_nightshifts`：B05 停在面摊那一刻，可它产出的披露说的是「连续三个夜班」那一段——**Beat 挂时刻和披露挂时间指示是两个挂钩，指向同一种节点**（第 5.7.3 节）。这一章之前没有这条的实物证据。

**这一轮开始，页面上的数不再手写。** `build-viewer.ts` 调 `schema.ts` 算完再注入，`chapter-01-graph.html` 自己一个数都不算。v2 那一版把数写死在页面里，结果文档、数据、页面三处各自漂移——第 6 节引的 Fact 计数、第 7 节那五个段号，核对下来全是旧的，这一轮一并改了。`viewer.html` 是例外：它**故意**另写一套求值与校验，作为 `schema.ts` 的第二意见，两边都报 0 错误才算数。

**W1（槽在「读」还是「做梦」阶段建）仍然挡着**第 7 节写不完；W8、W9、W10、W11、W12 等开发者裁决。

## 非目标

- 不写正式 Spec 或 ADR，不改 `packages/` 或任何业务源码，不建数据库。
- `memory-model-v4.md` 是**设计稿，未实测**。本目录的数据、算子与页面已按它重做，但那只证明模型装得下这一章，不证明抽取管线跑得通。
- **不改 `t03`。** 那条管线仍建在 v2 上，S1 的输出契约会因 v4 变化，等本稿通过之后另开一轮。
- 两份 JSON 全部人工装填，不是抽取管线输出，**不构成任何召回率或准确率证据**。
- **这一章验不到的规则原样留着。** 第 5.6 节的「竞争」「接续」「候选同指」三行，以及整套「反驳」机制，第一章一次都没触发。没被用过的规则等于没验过，要等第二章。
- 不声称单章推导已验证全书或跨作品适用性。
- 不做性能与规模验证，规模不是本次约束。
- 冒烟测试只覆盖脚本执行与渲染结构，**不覆盖视觉呈现**；浏览器人工验收未获授权，未执行。
- `beats-viewer.html` **只读不写**：它不生成也不修改 `beats.json`，是一个查看器不是编辑器。它内置的校验只做 v4 第 3.3 节说「代码能做」的那部分（连续、不重叠、覆盖、取值合法），**软边界（一句话能不能概括）它判断不了**，那条只能由人或模型判。
