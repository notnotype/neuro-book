### 1. 规范化后的请求被拿去算授权的 binds：带非规范主文字的已签名请求被拒 binds-mismatch
- 严重程度：重要；类别：不变量 / 正确性
- 位置：packages/nb-canon/src/world/world.ts:475（`input = normalizeRequestText(this, input)`）、:526（`this.#decisionWrites(input, request, ids)`）、:441（`authorizationBinds({project, request: input, ...})`）；`#decisionWrites` 的注释（:423）写明“`input` 是请求原样（授权按它算）”
- 现象：`#publish` 把形参 `input` 直接重新赋成规范化后的请求，后面 `#decisionWrites` 用它算 `binds.request`。宿主按将要发出的原样请求签名（tests/fixtures/authorization.ts 的 `sign`），请求里只要有一块主文字不是规范写法（`<V of="x"/>` 少空格、CRLF、BOM），摘要就对不上，整次拒收 `author-source-invalid`/`binds-mismatch`。提交范围里的注释说“重试与授权按原样的请求比”，只有重试（requestDigest 在规范化之前算）做到了，授权没有。修订里存的 `requestDigest` 是原样请求的，与授权里存的 `binds.request` 本该相同（decisions.test.ts 断言过），现在对非规范请求两者走的是不同的请求。
- 如何核实：/tmp/review-w00055-t02-s5/lab-opus/auth.test.ts（公开入口 `World.publish`，同一请求里放一条 pending→decided 的决策与一个新条目，按 fixtures 的 `sign` 签原样请求）：主文字是规范写法时通过；`名字 <V of="entry.name"/>` 与 `名字\r\n<V …/>` 两例都得 `{"code":"author-source-invalid",…,"reason":"binds-mismatch"}`。`bun test /tmp/review-w00055-t02-s5/lab-opus/auth.test.ts`（在 packages/nb-canon 里跑）：1 pass 2 fail。
- 建议改法：规范化的结果另起名（例如 `normalized`），`#decisionWrites` 照旧收原样的 `input`、换临时 id 用 `normalized`；或在 `#decisionWrites` 调用处显式传原样请求。补一条用例：带授权的请求里含非规范主文字照常发布，且 `revision.authorizations[0].source.binds.request === revision.requestDigest`。

### 3. 纯文字里条件的判断读不到值时写“未知”且不报 unavailable：与同义的 `V expr` 三元式、与旧三元式都不一样，简报关卡不再拦这块

### 4. normalizeBlockSource 对开头有两个 BOM 的文字不幂等；editEntries 规范化两次，结果按 result-mismatch 整次拒收
- 严重程度：建议；类别：正确性
- 位置：packages/nb-canon/src/grammar/tags.ts:160（只去掉一个开头的 U+FEFF）；packages/nb-canon/src/render/syntax.ts:202 的注释（“对规范的源文不变，可以重复做”）；entry-edits.ts:528（`planEntries` 先规范化一次）与 world.ts:475（`#publish` 再规范化一次）
- 现象：`normalizeBlockSource("﻿﻿x")` 得 `"﻿x"`，再做一次得 `"x"`。`editEntries` 的方案里存的预期值是第一次的结果，`#publish` 的第二次把它改成 `"x"`，读回核对对不上：`{"code":"result-mismatch","got":"x","op":0}`。直接 `World.publish` 只做一次，存下的仍带一个 BOM，与 Spec 输出 1“检查之前先去掉开头的 BOM”不符。其余 72 个组合（6 种标签写法 × 12 种上下文：链接文字、强调、setext 标题、列表续行、表格、缩进代码、引用、行内代码并列等）都是幂等的，见 /tmp/review-w00055-t02-s5/lab-opus/idem.ts。
- 如何核实：`bun /tmp/review-w00055-t02-s5/lab-opus/bom.ts`（公开入口 `editEntries`）。
- 建议改法：去掉开头所有的 U+FEFF（`replace(/^﻿+/u, "")`）。更稳的做法是同一份文字只规范化一次：`#publish` 认出“已规范化”（例如 entry-edits 在合成请求时标明，或只在 `World.publish` 的公开入口做），这样两处的读法以后再出现不幂等也不会变成读回失败。

### 5. 没登记标签的基线比 Spec 输出 19 宽：收进了已撤销、别的线、按计划的全部补丁；`change.kind` 的过滤是空操作
- 严重程度：建议；类别：正确性 / 代码质量（从代码推断，未做公开入口实验）
- 位置：packages/nb-canon/src/world/world.ts:1391-1405（`existingTagsOf`）
- 现象：Spec 输出 19 的例外是“这个条目当前的主文字里（任一块）已经有”。实现收的是初值的块，加上世界里每一条变更（`world.data.changes` 全部）里改这个条目主文字的补丁。`StoryChangeSchema.kind` 只有 `written` 与 `plan` 两种（core/schema.ts:219），所以 `if (change.kind !== "written" && change.kind !== "plan") continue` 永远不跳过任何变更，看上去像在筛选、其实没有；`status` 为 `undone`、`held` 的，别的世界线上的，删掉的块的，都算进基线。结果是：一个标签只要在任何一版、任何一条线、甚至已撤销的补丁里出现过，就永远可以写回这个条目。影响有限（没登记的标签只显示“需要插件”、纯文字报 `unknown-tag` 被关卡扣下），但这与 Spec 写的判据不同，审查者与后来的人会按 Spec 推断行为。
- 开销：基线只在遇到能免的 `unknown-tag` 时才算（`blockProblem` 里 `existing` 是惰性的），每次校验每个条目一次，O(全部变更的补丁数)；变更上万时一次几毫秒，可以接受。顺带每个历史版本的源文都经 `analyzeBlock` 进缓存。
- 建议改法：二选一并让 Spec 与代码一致。(a) 照 Spec：基线取这个条目在写入位置（或全部线的当前位置）上的主文字，即引擎读出的 `view.text`；(b) 保留“出现过即可”，把 Spec 输出 19 改成这个说法，并删掉无效的 `kind` 判断，注释里写明已撤销、别的线也算是有意的。

### 6. 一块新文字每次写入要解析 2 到 4 遍：规范化的解析结果不复用，editEntries 还规范化两次；在 marked 的超线性输入上把单写者队列卡几十秒
- 严重程度：建议；类别：安全与性能
- 位置：packages/nb-canon/src/render/syntax.ts:203-208（`normalizeBlockSource` 用 `readable` 解析，结果丢掉）、:185-194（`blockProblem` → `analyzeBlock` 缓存未命中再解析一遍，并且 `checkEntryText` 在 `analyzeUncached` 与 `blockProblem` 里各跑一遍）；entry-edits.ts:528 与 world.ts:475（两处规范化）
- 现象：用解析一次要 0.6 到 0.9 秒的一块（`"*a ".repeat(1500)+"x"+" b*".repeat(1500)`，9 千字）量公开入口：`World.publish` 新建条目约等于 2 次解析的时间，`editEntries` 整段替换约 3.7 次（/tmp/review-w00055-t02-s5/lab-opus/parsecount.ts）。旧实现在 `blockProblem` 里只解析一次、结果进缓存。marked 与旧的 micromark 链在这种嵌套强调上都是超线性的（24 千字一次 9 到 13 秒，lab-opus/em.ts 与 em-legacy.ts），写入的块没有长度上限（BlockSchema 的 `source` 是不限长的 `Type.String()`，只有预览限 5 万字），所以同一份粘贴来的文字现在占住写入队列的时间是原来的 2 到 4 倍：24 千字的这种文字经 `editEntries` 约 45 秒。条目文字来自模板与分享的世界观，属于外部输入。

### 11. 缓存里存的不只是词法：`error` 与 `meanings` 依赖登记表，`readable` 把任何 RangeError 都当成“嵌套太深”且不留诊断
- 严重程度：建议；类别：代码质量 / 不变量（为 t04 埋的耦合）
- 位置：packages/nb-canon/src/render/syntax.ts:140-147（`readable`）、:149-168（`analyzeUncached` 与按源文的缓存）、:107（`meaningOf` 的 default 分支）
- 现象：计划第 2 节的前提是“词法与登记表无关：解析结果可以按源文缓存；判写坏的标签时才用登记表”。实现缓存的 `BlockAnalysis` 里还有 `error`（`checkEntryText(parsed)` 不带 `registered` 算出的第一个问题）与 `meanings`（`BUILTIN_TAGS` 以外一律 `unregistered`），三种渲染都直接读它们。现在登记表恒为空，结果正确；t04 一旦有登记的标签，带缓存的渲染会把登记了的标签照“需要插件”给，`blockProblem` 与渲染对同一块的判断也会分叉，而缓存键只有源文，装卸插件后不会失效。另：`readable` 捕获全部 `RangeError`，除了栈溢出，`Invalid string length`、`Invalid array length` 或 grammar 里将来的一个越界 bug 也会被报成 `unsupported-markdown`“Nested too deeply”，没有任何诊断，违反“不用静默的 catch 吞掉错误，至少写一条诊断”。
- 建议改法：缓存只放与登记表无关的部分（`parsed`、`conditions`、字段引用），`error` 与“是不是登记的标签”在取用时按当时的登记表算，或把登记表的版本并进缓存键；在 BlockAnalysis 的注释里写明这个前提。`readable` 至少把捕获到的错误交给诊断出口（或记一条 `console.warn` 级别的内核诊断），并在注释里写明“只指望栈溢出”。
