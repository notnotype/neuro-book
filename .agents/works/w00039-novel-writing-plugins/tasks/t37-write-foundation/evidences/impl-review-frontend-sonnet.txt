# w00039 t37 前端实现审查报告（范围 46a224460..9b88b4232）

### 1. 元素、主文字块、移动对话框的保存不带读到的值，基准版本取确认那一刻的，别处在对话框开着时的改动被无声覆盖
- 严重程度：重要
- 类别：正确性 / 不变量
- 位置：`packages/neuro-book/src/plugins/canon/web/components/EntryPageHost.vue` 的 `runEntries`（335-347 行，`baseVersion: version()`）、`confirmElement`（465-515）、`confirmBlock`（543-557）、`confirmMove`（397-416）
- 现象：三类对话框打开时只存了“初值快照”（`original`、`moveFrom`），保存时 `set` 操作不带 `read`，`editEntries` 的 `baseVersion` 取的是确认那一刻条目读取的版本（`entry.value.version`）。对话框开着时别处（Agent 或另一窗口）改了同一个子字段或同一块正文，条目读取会重读到新版，保存时基准版本也跟着是新的，内核没有任何东西可比，作者的旧草稿直接覆盖别人的改动。对话框里显示的还是旧值，也没有任何提示。
- 为什么是问题：revisions.md 验收 1“两人同时改”要求“读了版本 10、别人改成 11、再保存改同一个对象得到 version-conflict”；作者“要用户和 agent 都能改”是开发者说最重要的一条，而这条正好是两方同时写的路径。原有的就地改（`useInPlaceEdit`）是对的：打开时存 `read: {value, version}`，保存带 `read`，世界变了还会写“这个值刚刚变了”。新路径等于把这条不变量丢了。`EntryEditsSchema` 的 `set` 本来就有可选 `read`，也有 `readStamp`，接口是够的。
- 如何核实：已做实验（临时在 `entry-page.dom.test.ts` 里加一条再 `git checkout` 恢复，已恢复，`git status` 干净）：真实世界里打开“改这一段”对话框，另一窗口用 `editEntries` 把 `text[b1]` 改成“别处改过的内容”，等条目页重读到新内容，再在仍开着的对话框里填“作者的覆盖”保存：写入成功，世界里正文变成“作者的覆盖”，没有冲突、对话框里也没有任何提示。
- 建议改法：打开时记 `{version, value}`（元素：改的各子字段的原值；块：`original`），保存时 `set` 带 `read: 原值`（内核已支持，`value-conflict` 带当前值），`baseVersion` 用打开时的版本；`value-conflict` 时按就地改的做法把对话框里“原值”换成当前值并写一句“这个值刚刚变了”。移动的 `place` 没有 `read`，至少用打开时的 `baseVersion`，让别人动过这个条目时得到 `version-conflict`。

### 2. 已选条目的名字显示不出来：选了以后再打开、搜不到词后失焦、改一项时的引用子字段，输入框是空的
- 严重程度：重要
- 类别：正确性（基本 UX）
- 位置：`components/MoveDialog.vue:57,81`（选中后 `parentName: ''`、`sameAsName: ''`）；`EntryPageHost.vue:811`（`keyName: ''`）；`EntryPageHost.vue:793-818`（`ElementDialog` 没传 `:ref-names`，组件有这个 prop）；`packages/nb-ui/src/components/form/SearchSelect.vue` 的 `display`（`selected?.label ?? (modelValue === "" ? "" : selectedLabel ?? "")`）；`EntryPicker.vue` 的 `items`（只有 `done` 才有选项）
- 现象：远程模式下输入框显示的名字只来自“当前这批结果里有这一项”或宿主给的 `selectedLabel`。宿主在选中后把名字清成空串，所以：(a) 在移动对话框里选了上级，再点开列表，打开时立即发 `search("")`，结果变 `searching`，选项变空，输入框立刻变空白（值还在）；结果回来时若所选条目不在前 20 条里仍然空白；(b) 输入一个搜不到的词后失焦，输入框同样是空白；(c) 元素对话框改一项时，引用子字段已有值，但宿主不传名字，输入框一开始就是空的（Task 记录写的是“显示 id”，实际是空白，与记录不符）；(d) 以条目为键的列表“加一项”里选了条目后同样（`keyName: ''`）。
- 为什么是问题：作者看见空输入框会以为没选，可能重选、清空，或误以为保存会丢掉这一项；而值其实还在，保存会照发。这是“能改”的基本可用性。
- 如何核实：已做实验（临时改 `entry-page.dom.test.ts` 的移动用例后恢复）：选中“学院”后 blur、focus、click 再读输入框，值是 `""`；再输入“不存在的词”等 600 毫秒、blur，值仍是 `""`。输出 `seen=["","不存在的词",""]`。
- 建议改法：选中时宿主记下候选的名字（`EntryPicker` 的 `update:modelValue` 额外带 `{id, name}`，或宿主在 `useEntryFind` 的最近结果里按 id 查），写进 `parentName`、`keyName`；元素对话框的引用子字段按 id 读一次条目取名字，传进 `refNames`；或让 `EntryPicker` 自己缓存“最近选中的名字”，不依赖外面给。

### 3. 从 Agent 提示撤销成功后，Agent 提示还留着，“撤销”仍指向已被还原的那次修订
- 严重程度：重要
- 类别：不变量 / 正确性
- 位置：`components/EntryPageHost.vue:675`（`@undo="pageNotice.undo(props.notices.agent.value)"`，`ReceiptPageHost`、`ChangePageHost` 同）、`notices.ts` 的 `usePageNotice.undo`、`revert.ts:216-217`
- 现象：还原成功只调 `notices.show(...)`（换掉作者自己那一格 `current`），没有任何地方调 `dismissAgent()`（全仓 `grep dismissAgent` 只在三个宿主的关闭按钮与测试里）。所以撤销 Agent 的修订成功后，页顶同时有“撤销成功”的提示和仍写着“Agent 改了设定：建校长”的那一行，那一行的“撤销”“看回执”仍指向被还原的修订。
- 为什么是问题：再点那个“撤销”，补偿修订改过同一批地址，按 revisions.md 输出 12 它依赖原修订，预览会得到 `has-dependents` 并给“连同这些一起还原”，选了就是把 Agent 的改动重做回来，作者以为是在撤销。Spec 输出 18 对作者自己的提示写的是“还原成功后换成还原的那一条”，输出 42 说 Agent 提示的撤销“按输出 22”，没有写成功后怎么办；按同一个道理，被还原的那条不该再提供撤销。e2e 只断言树里“校长”没了，没看提示的状态，所以没测到。
- 如何核实：从代码推断（未跑）：e2e 第二条用例在撤销后追加 `await expect(page.locator("[data-agent-notice]")).toHaveCount(0)` 应失败。
- 建议改法：还原成功时，若还原的修订 id 等于 `agent.value.revision`，清掉 Agent 提示（或把 Agent 提示的“撤销”在成功后置灰）；`usePageNotice.undo` 对两类提示共用，可在 `createRevertRequests().open` 的成功回调里按修订 id 清。并补 e2e 断言。

### 4. 页头写入的失败原因 `actionError` 是全页一份、没有关闭路径：取消对话框后残留在页头，对话框开着时页头与对话框各写一遍
- 严重程度：重要
- 类别：正确性（基本 UX）/ 共享状态
- 位置：`components/EntryPageHost.vue:332`（`actionError`）、336-339（`runEntries` 开头清、失败时写）、`@update:open` 各处（791、810、827、844、864、883、897 附近，只改开关不清错误）；`EntryPage.vue:136,179`（`actionError` 画在页头下面）
- 现象：同一个字符串同时给 `EntryPage`（页头下面）和每个对话框（对话框里）。(a) 元素/块/移动/加设定/去设定对话框里保存失败、或校验不过（`list.badValue`、`list.needLabel`、`block.emptySource`）时，错误既写在对话框里，也写在被遮住的页面里（两个 `role="alert"`，读屏会读两遍）；(b) 作者看了错误后点“取消”或按 Escape，对话框关了，页头下面那行红字还在，没有关闭键，直到下一次任何页头写入或打开别的对话框才被清掉；(c) 在别的对话框失败后再打开“添加一组设定”等，打开前才清，顺序依赖每个 open 处手写的 `actionError = ''`，漏一处就串（`removeBlockDraft` 打开处写了，`blockOpen`/`elementOpen` 的取消没写）。
- 为什么是问题：开发者的“基本 UX”范围。显示一个已经无关的错误，会让作者以为刚才取消的操作还有问题；这也违背 Spec 输出 29 “失败时原因写在对话框里”（对话框里写了，页头不该再写）。
- 如何核实：从代码推断，可用 dom 测试复现：让 `editEntries` 失败（例如去掉有 `element-from-change` 的元素）后取消对话框，断言 `[data-entry-action-error]` 不存在。
- 建议改法：对话框各自持有错误（每个 `runEntries` 调用方传入要写的错误槽，或 `runEntries` 返回失败原因，由调用方写进对话框的 `error`）；`actionError` 只留给没有对话框的页头操作（别名、恢复），并加关闭键或在下次渲染前随位置、标签变化清掉。取消对话框时一并清它自己的错误。

### 5. 元素对话框里有两个以上引用子字段时共用一份查找结果与一个“当前字段”，列表与目标种类会串
- 严重程度：建议
- 类别：正确性 / 共享状态

- 现象：一个 `useEntryFind` 与一个 `elementRefField` 服务所有引用子字段。`ref-results` 对每个引用子字段都是同一份：先在 A 字段里搜，再点开 B 字段，B 的下拉在新结果回来前先列 A 的结果（按 A 的 `targets` 查的）；打字去抖 200 毫秒里切到另一个字段，`run` 执行时 `elementRefField` 已是新字段，结果按新字段的 `targets` 查却可能被标成上一个词的。内核会按声明校验，写进去的引用不会错种类，但作者会短暂看到不该出现的候选。

- 建议改法：窄场景，可记为已知限制；或 `ElementDialog` 内每个引用子字段一个小的包装（各自 `useEntryFind`），不必在宿主里共用。
