# w00039 t37 写入底座后端设计审查

## 审查基点

`HEAD` 为 `46a224460`（detached），本机 `refs/heads/master` 为 `b95e3fc54`，两者不是同一提交；已核对 t37 计划、Work 记录、主要 Spec 和内核／Agent／远程相关路径在两提交间无差异。以下按指定检出的代码和计划审查。

### 01｜阻断｜不变量：提交前核对
位置：计划 95、111；`world/edits.ts:240–252`，`service/service.ts:1191–1205`。
现象：“发布后逐项核对 `set`，失败报 `result-mismatch`”若落在服务发布之后，调用方会收到拒收，日志、版本、请求 id 和 `changed` 却已生效。
理由与核实：现有 `finish` 的 `world.publish` 只算候选世界，`checked` 通过后服务才 `appendRevision`；两处的“发布”不可混用。按计划可用“初值写入被剧情赋值遮住”的一批做门禁：预览与写入同错，`status.version`、`outcome`、日志与事件均不变。
改法：明确 `previewEntries`、`editEntries` 共用候选计算和全部读回核对；只把都通过的候选交给 `WorldService` 追加，不能事后补偿或仅报错。

### 02｜阻断｜去重：会话内不同写入会撞请求 id
位置：计划 138、237；`nb-harness/src/kernel/api/tool.ts:108–113`，`harness/runtime.md` 输出 87，`nb-canon/src/world/world.ts:458–467`。
现象：同一会话两条回复可以各有 `callId: "1"`。第一条写入成功后，第二条用同一个请求 id，要么被拒为 `request-id-reused`，要么被当成第一次的重试；`outcome` 也只能查到第一次。
理由与核实：`callId` 只在同一条回复内唯一；`ToolContext.invocation` 才是全局唯一的调用身份。现有去重的键是世界内 `requestId`，不会再区分回复。F3 的脚本化会话应在两条回复复用 `callId`，两次写入各产一条修订，再模拟第一次的链路恢复并确认不多写。
改法：从可信 `ctx.invocation` 派生有命名空间的请求 id。同一次调用的重发复用已经解析的整份请求；不同调用不能仅凭相同 `callId` 合并。

### 03｜重要｜正确性：批内新建后写入，story 有两个相反的落点
位置：计划 95–107、227；`canon.revisions` 输出 8；独立设计 4.2 第 2、4 项。
现象：`story` 下 `[create(tmp:人), set(tmp:人, entry.summary, "改后")]` 一处要求把 `set` 放进新变更，另一处要求后续操作直接改初值。前者在该章之前读到空简介，后者此前也读到“改后”。传来的是新条目、现有条目的新 Component，还是 `listAdd` 的新行，也不能按同一条“原世界来历”处理。
理由与核实：`planEdit` 从原世界 `currentAt` 读，新对象不在那里；`World.publish` 可在同一修订落条目和剧情变更，内核无需把 `story` 当创作修改。验收应分意图断言一个 create put 加什么、旧位置值、route 和整批还原；同一变更的两个不同补丁，以及同时改初值和旧补丁，各断言只出一个对象的 put、两处均保留。
改法：限定“新数据直接改初值”适用的操作与意图。创作修改以原世界定位旧数据的来历、向已复制对象按补丁身份合并；新数据从副本读。剧情变化始终在落点上用新条目／新命名空间的初值与此前批内补丁求值，不暗改开局。

### 04｜阻断｜不变量：Agent 写入遗漏它读过的剧情值
位置：计划 79、97、149–153、234、252、276；`canon.revisions` 输出 7、8、19；`world/world.ts:469–507`。
现象：作者新加一条剧情变更，不必改条目对象；Agent 用之前的版本和旧设定写入。`story` 生成的又是新对象，按 `puts` 查版本，两次写入没有共同的冲突键。把版本粒度从对象改到叶子也不能补这个缺口。
理由与核实：真实 `WorldService`：v2 读到简介“初值”，作者的剧情赋值于 v3 生效；旧 `editInPlace` 带原值时返回 `value-conflict`，按计划生成的普通 story 请求不带读前提，`baseVersion: 2` 仍发布 r4、当前位置读到“Agent 改”，`outcome` 确认已发布、事件为 v3 和 v4。复现命令 `bun /tmp/w37/review-design-backend/probe.ts` 的 `stale` 场景；工具和批量入口尚未实现。`creative` 打回后来新增的那条补丁时可能由对象冲突兜住，不等于有通用读前提。
改法：不用模型复述值也可以保护读前提：最小改法是 Agent 提交在项目写队列内校验同一读取戳（至少版本，若省略线或用名字还须捕捉读输入改变）；先判请求重放再判戳。若要允许不相关修改并行，改上游为显式的读集比较（值、来历与解析目标），保留 `puts` 的写集冲突。F3 加跨对象的真实并发例，不是只改同一条目对象。

### 05｜阻断｜正确性：章首读界不能验证在本章最前写下的值
位置：计划 74、97、111、228；`core/position.ts:46–60`、`world/edits.ts:99–110,246–250`；`canon.model` 输出 2、`canon.revisions` 输出 8、9、23。
现象：第 N 章开头的读界在所有本章记录之前（章内键 −∞）；“最小键减一”仍是本章的一条有限键记录。若照计划在同一个章首读界核对，第一条 `set`/`add` 也读不回，或只有无需读回的 `note` 能写。
理由与核实：探针 `edges` 在真实 `WorldService` 的空章章首：预览、就地改都报 `result-mismatch`，读到旧简介；`recordDelta` 同码，读到 100；`recordNote` 在键 0 成功，只有它推进版本／发事件。是现有位置不变量和旧入口的缺口，不能用差分把缺口当正确性门禁。
改法：写前仍读公开的章首边界；候选按新变更之后、下一记录之前的精确点核对（引擎已有 `slotAfter`），或明确拒绝章首写并修订 Spec。不要改全局章首读取的含义。F1 断言章首旧值、刚插记录后的值及章末以后值，并覆盖切口章的合法落点或 `line-out-of-bounds`。

### 06｜阻断｜正确性：显式主线被抹成“按章选线”
位置：计划 63、74、96–97、149；`world/edits.ts:113–128,144–149,225–237`；`world/world.ts:216–225`；`canon.worldlines` 输出 12、19。
现象：在一章讲子线时显式传 `line: "main"`。旧入口 `onLine` 删除该字段，后续查值、来历又按章节选了子线。无 `read` 的批量路径若照搬，连本会报 `value-conflict` 的保护也没了。
理由与核实：探针 `explicit-main` 经真实服务建分叉并设置章分段：显式读到“主线值”，省略线读到“子线值”；用主线值保存被拒，若把 `read` 设为子线值，预览竟给出子线的补丁 `c3`。不是安放里省略主线的规则错误，是把该规则误用于读取位置。
改法：用明确的线 id 贯穿解析、工作副本、来历、结果核对与 `laterRecords`；只在构造持久化 `Placement` 时省略主线。F1/F3 断言显式主线、缺省子线和计划线不能写，旧入口差分对此列预期修正。

### 07｜重要｜正确性：列表来历记录“碰过”，不表示给出了这一行
位置：计划 96、98–100、107、118；`engine/incremental.ts:417–441`、`model/apply.ts:320–337`；`canon.components` 输出 19。
现象：只按列表地址的前缀或来历最后一步，给初值里的 i1 改数量会误路由到后加 i2 的剧情补丁。同一个 id 被 `listRemove` 后再 `listAdd` 时，初值里含 i1 也不能证明此刻显示的 i1 来自初值。子线的 `carry` 不是能改的剧情补丁。
理由与核实：真实服务探针 `bun /tmp/w37/review-design-backend/probe.ts origins`：只新增 i2，`origins(物品[i1].数量)` 仍列该步 `listAdd`，结果仍为 1；随后移除 i1、用同 id 重加，两个发布均成功，当前值的来历换为后一次 `listAdd`、结果为 3。当前 `OriginStep` 没有补丁索引；一条变更可含多个同列表 `listAdd`。以引用为键时元素 id 更不能靠另发新号避开历史。
改法：内部路由按有效元素的历次赋值、增删及 carry 跟踪到变更 id 和补丁索引，不改变公开“来历”展示的口径。只在当前行确由初值给出时删除初值行；否则给真实出处或 `carried-value`。补同名单元删后重加、同行子字段、另一行增删、整表赋值和载入知情列表的子线；生成普通 id 要定义历史保留域，不能只扫描初值。

### 08｜重要｜正确性：单项包装的去重合同不能用批量摘要替换
位置：计划 63、69、79、112、228、275；`world/edits.ts:139–141,217–237,255–266,277–287`；`canon.revisions` 输出 16、22–24。
现象：已落盘的旧 `recordDelta`、`recordNote`、`editInPlace` 重发时，若包装直接用转换后的 `EntryEdits` 算摘要，同一次写入会变成 `request-id-reused`。另有明确的行为改动：旧单项拒绝由 `listAdd` 给值，现在计划要求写回；“所有输入的修订、失败码不变”与此矛盾。
理由与核实：旧日志的 `requestDigest` 是以原入口名为键、加入其原输入和规整位置，重发先比较摘要后才进 `planEdit`。仅比较新旧的 `ops`/`impact`、在新版本内重发，不能发现重放旧日志后的问题；只比 `ops`/`impact` 也不覆盖 `what`、章字段、缺省标题、失败码和 `route`。
改法：共用路由与候选计算，但旧包装按原输入与算法重放已发布的请求，预览仍绕开去重；保留各入口的原有修订元数据。对旧日志重放、相同/不同输入重发、语义档及旧失败逐项测。将新列表路由与 05、06 的修正列为明确例外，差分只守其余合同。

### 09｜重要｜权限：冷会话的只读模式拒绝预览
位置：计划 133、155；`agent/backend/tools.ts:167–177`、`nb-harness/src/kernel/run/tools.ts:390–395`。
现象：新会话第一次调用 `canon_write({preview:true})` 时，内核先按静态声明判为 `write`；`readOnly` 会在工具激活前硬拒，因而参数级 `read` 永远拿不到。计划承诺的预览只读权限失效。
理由与核实：以真实 `agentWorld` 和本机脚本端点跑冷会话，设置 `readOnly: true`、`approvalMode: "ask"` 后直接得到 `read-only`；提供方激活和工具执行均为 0，无审批事项。探针在 `/tmp/w37/review-design-backend/runtime-preview-probe.ts`。内核 `effectOf` 对函数声明的错误回退是 `exec`，不会因参数读失败而放行。
改法：只读分支须在审批前对预览输入作可靠识别，使冷、热会话的权限一致；或撤回 `preview` 是 `read` 的承诺，统一按写权限。保留硬 `readOnly` 拒绝真实写入，并测冷/热、预览/写入、规则与模式闸门。
### 10｜重要｜正确性：`findEntries` 的删除过滤语义未定义
位置：计划 113–116、148–152、178；`nb-canon/src/service/service.ts:1015–1033`、`canon/project.md` 输出 24。
现象：接口公开 `includeDeleted?`，但规则没有说明缺省值、设为 true 时哪些墓碑可返回，也没有说明删除后名字与别名按初值还是查询位置取值。现有 `lookup` 会排除存储墓碑、位置视图里的墓碑及未出场条目；`tree` 则会为仍有可见后代的已删除父条目保留墓碑。照计划实现时，Agent 名字解析和 UI 的父级／马甲／引用候选可能把不可写或不可引用的墓碑当作候选，也可能无法按产品需要找回墓碑。
理由与核实：`WorldService.#lookupOn` 明确按位置的 `view.name` 与 `view.aliases` 查找，并跳过墓碑和未出场项；计划在同一查询参数中加入 `includeDeleted`，却没有覆盖这一语义差异。F1/F2 应分别断言缺省与显式包含时墓碑、仍有活后代的墓碑、未出场项及位置上改过的名字／别名；视图令牌路径仍须拒绝并审计。
改法：写清 `includeDeleted` 的缺省与含义、墓碑名字／别名的读取位置，以及哪些调用场景允许传 true；默认的名字解析与 UI 候选保持只返回可用条目。
### 11｜建议｜测试：`findEntries` 性能验收没有通过阈值
位置：计划 117、213、229、247；`canon/project.md` 输出 14、18–19。
现象：计划要求“按三百万字样本书的条目数量一次中位数”，但没有写样本条目数以外的运行次数、是否预热、调用路径、预算阈值或超预算处理；F1 只写新增查找测试，F2 写远程 `findEntries`，验证命令也没有性能判据。测试即使报告任意耗时也无法判断实现是否满足承诺，远程编码与结果分页还可能把单次内核扫描性能掩盖掉。
理由与核实：现有 `canon.project` 输出 14 给出约 520 个条目与约 1000 章的参考规模，输出 18 给出远程消息预算；这两者不能替代性能验收的样本次数和目标阈值。t34 的旧规模证据测的是另一项发布记账，不能作为 `findEntries` 的实测或门槛。
改法：明确计时对象是内核方法还是完整远程调用，固定参考数据规模、预热与重复次数、中位数阈值及负载条件；验证结论报告实际样本与耗时，不把旧发布测量当作本次证据。

## 未发现问题的方面

- 条目查找的视图令牌：计划禁止带令牌枚举；现有服务合同对未列入允许清单的方法统一拒绝并审计，语义一致。
- 条目查找的位置名与别名：现有 `lookup` 按读取位置的有效名字与别名匹配，计划沿用位置有效名字，没有发现相反的实现依赖。
- Agent 写入的项目租约与服务端入口生命周期：所依赖的 `projects.acquire`、远程 `{project}` 绑定与调用方释放机制均已存在；具体请求 id 冲突与冷会话预览问题见 02、09。
- 列表游标所需的读取戳：现有游标机制绑定 `inputDigest` 与影响结果的查询参数；若 `findEntries` 分页，应复用该合同并把位置、类型、删除过滤和排序参数纳入游标摘要。
- 现有新建与删除的底层发布合同：新建仍须生成临时 id 并从回执 `ids` 取正式 id；删除是保留对象数据的墓碑写入，Spec 要求回执可还原。计划改走统一写入通道本身没有改掉这些合同。
