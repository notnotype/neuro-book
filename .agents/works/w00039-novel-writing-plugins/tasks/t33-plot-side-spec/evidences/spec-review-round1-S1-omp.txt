### 1. “同一版本确定”与正文驱动的讲述结果互相冲突
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/model.md:16,194-205`；`docs/specs/canon/project.md:83,118`；`docs/specs/canon/revisions.md:79-80`
**现象**：`model` 输出 1 声明同一世界版本、章序和 Component 登记集合的读取结果逐字相同，但输出 24、26 明确按当前正文重新定位讲述；`project` 输出 25 又规定正文变更不增加世界版本，却会改变发生点、失联、读过的讲述及依赖诊断。正文不是“同一份世界”的版本输入，因而同一版本可以得到两份不同结果。
**为什么是问题**：读取结果、预览、游标和诊断缓存无法仅以世界版本标识。两个进程各自持有不同正文视图时，即使都读版本 N，读者知情/伏笔阶段和待处理诊断也会不同；把版本 N 的结果当作可复用快照会把旧正文的讲述位置或诊断带到新正文。现有 `WorldService.entry` 也只返回世界版本，没有正文快照或正文版本标识（`packages/nb-canon/src/service/service.ts:179-187`），后续实现没有可绑定的输入身份。
**如何核实**：以同一世界日志和同一章序，令正文进程 A 含原句、进程 B 删除原句；分别读取同一版本的 `tellings`/`pending`，按输出 25 应分别得到生效与 `telling-lost`，但返回版本相同。再用同一个版本游标或预览结果交叉读取，无法判断它属于哪份正文。
**建议改法**：把宿主提供的正文快照（至少每章的内容摘要、最好是可复用的正文版本号）纳入读取上下文、游标、预览与诊断缓存键；规定一次读取使用的正文快照和跨章读取的原子性。相应地把确定性表述改成“同一世界版本、章序、正文快照、登记集合与插件诊断快照”，或明确哪些结果不承诺稳定。

### 2. 待处理的大小上限没有可用的分页入口
**严重程度**：阻断；**类别**：接口与合同
**位置**：`docs/specs/canon/model.md:186,204-205`；`docs/specs/canon/project.md:60,111-112,120`
**现象**：`project` 的 `pending` 方法只有读取位置参数，没有 `cursor` 或 `limit`；方法表返回待处理、提示、已处理诊断和未计算诊断。`model` 输出 16 还把插件诊断合并进待处理并排序，但没有分页形状。与此同时，`project` 输出 27 说这些结果受输出大小上限和游标约束，输出 18 又规定结果超预算返回 `too-large`、列表方法用游标分页。
**为什么是问题**：一章出现超过消息预算的诊断时，调用方既不能拿到第一页，也没有游标继续取；如果直接返回 `too-large`，作者无法查看或处理任何待处理。把游标规则写在通用输出上不能补出 `pending` 的输入、游标所属版本、分页后的稳定排序和“已处理”与“未处理”各自是否共用游标。
**如何核实**：构造一个插件诊断在同一读取位置返回超过 1 MiB 的发现，调用 `pending`。按输出 18 应返回 `too-large`，但按当前方法表没有任何 `cursor`/`limit` 可改变请求；即使实现内部截断，也没有合同告诉调用方下一页如何取得。
**建议改法**：给 `pending` 明确的 `limit`、游标和分页结果，规定游标绑定世界版本、正文/章序/插件登记快照以及读取位置；定义截断诊断和诊断发现的分页排序。若 `status` 的诊断也会进入同一结果，单独定义它是否分页，避免把大小上限写成无法恢复的失败。

### 3. 时间说法与分叉里的引用没有进入统一引用合同
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/components.md:116-123`；`docs/specs/canon/model.md:98-105,133-143`；`docs/specs/canon/worldlines.md:38-58`；`docs/specs/canon/time.md:51-63`
**现象**：引用输出 18 列出了 `involves`、`lines`、参与者、计划链接、决策 `about`、条目 `parent`/`sameAs` 和 Component 位置，但没有列出分叉的 `line`、`parent`、`cut`、`trigger`、`who`、`carry[*].entry`、`endAt`，也没有列出时间说法的 `after/before.of`、`age.who`、`birth.who`。这些值都指向条目、变更或生成的世界线 id；`worldlines` 还明确要求分叉的 `line` 用临时 id。
**为什么是问题**：临时 id 替换、写入存在性校验、条目筛选和还原依赖只对列出的引用位置成立。按字面实现会出现同一次请求里 `when.age.who`、分叉 `line` 或 `cut` 仍是 `tmp:*`，或者删除/还原被引用对象后没有依赖闭包；世界线的失败码虽单独写了，仍没有规定它们如何走统一替换和修订路径。现有内核也仍是固定键表（`packages/nb-canon/src/world/world.ts:544-589`），不是可覆盖这些新路径的声明机制。
**如何核实**：在一个请求里新建人物、剧情变更和回溯分叉，同时以临时 id 填入 `age.who`、`fork.who`、`fork.cut` 或 `fork.line`；逐项检查发布后的 idMap、依赖和还原。当前固定替换表只能覆盖已有键，Spec 没有另一份可执行规则补上这些位置。
**建议改法**：在 `model`、`time`、`worldlines` 的公开形状旁列出完整的引用路径表，区分条目引用、变更引用和世界线引用；为每类规定临时 id、目标存在/墓碑、改动记录筛选和还原依赖。`refs` 的路径声明只解决插件载荷，不能代替内核固定对象的完整清单。

### 4. 世界线没有闭合到共用的安放、读取位置和待处理合同
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/specs/canon/model.md:39,98-107,124,149-153,186-197`；`docs/specs/canon/worldlines.md:54-69,78-80,102-114`；`docs/specs/canon/project.md:42,58-70`
**现象**：`model` 定义的安放只有前史、章和未排章，读取位置只有初值/章首/章末；核对点的 `place` 也只写“安放”。`worldlines` 又要求剧情变更和核对点的安放带 `at.line`、读取位置带 `line`，并加入 `line-missing` 与已存越界记录的待处理。可是 `model` 输出 16 的待处理清单没有 `line-missing` 或 `line-out-of-bounds`，排序也没有定义带线位置与普通位置的比较；`project.pending` 只引用这一清单。
**为什么是问题**：照字面实现时，核对点到底怎样写入和比较、`line` 是安放对象的字段还是位置键的一部分、越界旧记录是打开诊断还是普通待处理，都没有唯一答案。读者能得到 `line-out-of-bounds` 失败码，却无法从 `pending` 合同知道它是否返回、怎样排序、怎样分页；子线线视图也无法复用 model 的全序而不自造第二套位置模型。
**如何核实**：尝试写一个 `at.line = r1` 的核对点，再读取 `r1` 第 8 章末尾；需要同时构造 `ReadPosition`、`Check.place`、排序键和待处理项，但六份 Spec 没有这些联合形状。再把已有子线记录因切口移动变成越界，`worldlines` 要求它进入待处理，`model` 的编号清单没有对应项。
**建议改法**：在 `model` 的安放和读取位置定义中正式给出带线联合形状，并明确 `Check.place`、章首/章末、前史与线的比较规则；把线缺失、线越界、活页夹线未知分别登记为 model/project 可返回的待处理或诊断，给出稳定排序、游标和打开坏日志的边界。不要只在 worldlines 另写一组扩展字段。

### 5. 计划分叉定义的线可以被写入事实，但没有转换规则
**严重程度**：重要；**类别**：不变量
**位置**：`docs/specs/canon/worldlines.md:38-56,61-70,83-90`；`docs/specs/canon/model.md:97-107,149-153`
**现象**：分叉是剧情变更，`kind` 可以是 `plan` 或 `written`；输出 1 又规定分叉可以是计划，子线照样存在，并可在上面记计划。线的存在条件只写“定义它的分叉生效”，没有区分按实际/按计划模式，也没有规定计划分叉存在时子线上 `written` 变更是否允许。`line` 的安放和写入者所在视图也没有这个约束。
**为什么是问题**：按现有规则，发布一个 active 的计划分叉后，调用方可以把 `written` 变更安放在该线；实际模式会出现没有已写分叉事实却已有子线事实，之后把分叉计划撤销或改成另一种走向时，这些记录是应被拒收、变成线不存在、还是随计划一起回滚都没有定义。`model` 的实际/按计划折叠和 worldlines 的线存在性因此会给出不同结果。
**如何核实**：先在主线发布一个 `kind: plan, nature: fork` 的分叉，再发布 `at.line` 为新线的 `kind: written` 变更，分别按实际和按计划读取；现有合同没有任何失败码或状态转换覆盖这个序列，也没有回溯/还原它的验收场景。
**建议改法**：明确计划分叉只在按计划模式建立“计划线”，并拒绝其上所有已写事实；或者定义计划线的实际写入、分叉兑现和计划撤销的转换，以及这些记录的依赖和回滚。线的存在条件、`line-not-found` 与读取模式必须共同定义，不能只用 `active` 这个剧情变更状态。

### 6. `return` 与 `stop` 在线读取上没有可观察区别
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/worldlines.md:51-52,75,78,83-95,123-129`
**现象**：分叉的 `end` 有 `continue`、`return`、`stop` 三种值，`endAt` 是子线上最后一条变更。合同只规定 `return`/`stop` 之后不能再写（`line-ended`），却没有规定章序后续默认读哪条线、`return` 怎样回到父线、`stop` 是否仍可显式读取，或活页夹后续章节如何绑定。输出 12 只说显式在线上读取时“照常”。
**为什么是问题**：这两个值在所有已写数据、读取位置、`line-not-found` 和写入结果上都可能完全相同；“梦境/IF 线结束后回到父线”的提案语义没有落到 Spec。作者无法只按合同得到后续章节应该读父线还是终止线，调用方也不能验证两种结束方式的差异。
**如何核实**：建立同一父线上的两个分叉，分别设置 `end: return` 与 `end: stop`、相同 `endAt`，为结束后的第 N 章不给显式线读取；按输出 12 只能得到活页夹输入的线或显式子线，无法从 `end` 推导结果。现有 worldline 原型只覆盖分叉和越界，没有结束方式场景，`bun lines.ts` 输出也未验证这两个值。
**建议改法**：定义结束线在章序中的继续规则（`return` 的默认线切换点、`stop` 的可读范围/失败码）和活页夹显式线覆盖规则；若第一版不自动切线，应删除其中一个值或明确它们只影响写入且不承诺回到父线。

### 7. 世界线缓存只有容量，没有键和完整失效合同
**严重程度**：重要；**类别**：安全与性能
**位置**：`docs/specs/canon/worldlines.md:33-34,74-81,92-100`；`docs/specs/canon/project.md:42-48,83-120`；`docs/specs/canon/model.md:16,242-243`
**现象**：世界线输出 9 只规定当前线常驻、其它线按最近使用最多留 3 条，输出 8 规定写入后已建线的结果与从头重建相同；没有定义线视图/实际模式/按计划模式/读取位置/章序/Component 登记/正文/历法/诊断登记的缓存键，也没有规定这些输入变化时淘汰哪一层。`project` 输入明确允许章序、正文、Component、诊断和历法在世界版本不变时变化。
**为什么是问题**：只按线 id 保留结果会把旧计划覆盖层、旧章序排序、旧 Component 版本或旧正文驱动的诊断复用到新输入；按计划和实际还共享缓存时，carry 值与计划进展也会串。只写“淘汰后重建逐字相同”不能证明未淘汰时不会读到旧结果，也不能判断“哪些线更新”的值比较应在哪个输入快照上做。
**如何核实**：先读取并缓存 r1 的实际和按计划结果，再新增/取消一个父线计划、移动切口、改变 Component 登记或章序，不增加世界版本，重复读 r1；按现有文字没有必须失效的键或事件。当前内核的 Component 登记自身已有 digest 触发整本重算机制（`packages/nb-canon/src/components/registry.ts:1-6`），但世界线 Spec 没有把它接进线层。
**建议改法**：规定派生缓存的完整输入身份和层级：世界版本、章序快照、正文快照、Component/标注/诊断登记版本、历法版本与词表版本、线定义版本、模式；定义每类输入变更的失效范围，并把按值比对使用的旧/新视图绑定到同一快照。3 条应是容量上限，不应代替一致性规则。

### 8. 作者来源没有绑定到被授权的决策变更
**严重程度**：阻断；**类别**：安全与正确性
**位置**：`docs/specs/canon/revisions.md:108`；`docs/specs/canon/model.md:201-205`
**现象**：作者来源的形状含作者、消息/确认 id、摘要、范围、时间和签名；内核只把整个 `source` 交给宿主校验，Spec 没规定签名覆盖哪些字段，也没要求来源绑定决策 id、允许的状态转换、结论/约束等具体修改、项目或请求 id。模型输出 31 只说“带宿主签发、校验通过的来源”，输出 35 的一键沿用也只是重新带来源新建决策。
**为什么是问题**：在“Agent 不可信、插件可信”的威胁模型下，Agent 可以拿到一次合法的作者确认来源，把它复制到另一条决策或同一决策的不同结论/约束上。只验证作者消息确实存在并不能证明作者授权了当前 payload；可变的 `quote` 摘要和可选 `range` 也没有防止重放或改字段的合同。这样会让“Agent 不能自己定”在有效签名被复用时失效。
**如何核实**：先让宿主签发一份把决策 A 定为结论 X 的合法来源，再在同一或另一请求里把同一个 `source` 附到决策 B，或把 A 的结论改成 Y；按现有 Spec，校验函数只收到来源，无法据合同区分这三种请求，验收场景只覆盖了伪造签名而没有覆盖重放。
**建议改法**：定义宿主签名/校验的规范载荷，至少绑定项目身份、决策 id、转换类型、被作者确认的字段/规范化 payload 和请求摘要（必要时加一次性 nonce 或有效期）；内核校验时把这些上下文一并交给宿主，并规定同一来源不可授权另一项修改。把一键沿用定义成重新确认当前诊断版本和当前决策 payload，而不是只复制 source。

### 9. 诊断发现的稳定键、合并和排序无法按字面实现
**严重程度**：重要；**类别**：正确性与测试
**位置**：`docs/specs/canon/model.md:64-75,186,204-205`；`docs/specs/canon/project.md:60,120`
**现象**：登记只允许诊断从 `objects`、`line`、`telling`、`range` 中选择稳定键组成；发现另有 `at`、`objects`、`params`。Spec 没定义对象列表的规范顺序、缺省值和重复项如何编码，也没定义“同一诊断、同一 key 合并”时保留哪一条的 `at`、对象和参数。待处理排序只说按“位置”排序，但发现的 `at` 既可以是安放也可以是讲述位置，二者与前史、章首/章末、段/偏移之间没有总序。
**为什么是问题**：两个插件实现者会为同一组对象产生不同 key；同 key 的不同发现可能丢掉真实证据或把一条诊断挂到错误位置。分页游标、作者挂诊断的 `about.key` 和版本也无法稳定复现，无法写“同一输入逐字相同”或变异测试。
**如何核实**：构造同一规则返回两条发现：对象列表次序相反、参数不同、一个带讲述 `at` 一个带安放 `at`。按现有合同不知道它们是否合并、合并后的载荷是什么、应排在一个章的哪一项；再把该 key 放进决策 `about`，输出 33 只校验诊断 id 格式，不校验 key 是否符合登记声明。
**建议改法**：把 key 定义成带类型和固定顺序的元组，明确数组集合/序列语义、空值和规范 JSON 编码；规定重复发现的合并与参数冲突行为，或禁止同 key 多发现。分别定义安放位置和讲述位置的排序投影，并给 `about` 的 key/version 做结构校验和版本兼容规则。

### 10. 同步诊断计算没有时间、结果数或失败隔离上限
**严重程度**：重要；**类别**：安全与性能
**位置**：`docs/specs/canon/model.md:62-75,204-205`；`docs/specs/canon/project.md:60,120,157`
**现象**：诊断计算要求在世界服务所在项目实例同步调用，传入整个只读世界和读取位置；插件可以返回任意长度的发现，Spec 只在最终返回层引用 1 MiB 消息预算和游标。没有单个诊断的耗时、扫描对象数、发现条数/字节数、取消或超时合同，也没有规定一个诊断抛错或超时后其它诊断是否仍返回。
**为什么是问题**：一个剧情插件的检查可以在作者每次读 `pending` 时同步扫描全书或产生无限发现，阻塞项目实例的所有读写；在返回前才做大小检查不能限制计算期间的 CPU 和内存。`diagnostic-unavailable` 只覆盖“没启用、没登记计算、抛错”，没有区分超时、被截断和部分结果，作者也无法知道待处理是否完整。
**如何核实**：注册一个同步计算循环扫描全部变更并返回超过消息预算的发现；调用 `pending` 时服务必须先完成计算才能知道要截断，过程中不能处理其它请求。再让该插件抛错，合同只给一个 unavailable 结果，没有其它诊断的保留/失败顺序。
**建议改法**：为贡献点定义每次读取的诊断预算（耗时、发现数、序列化字节），规定超时/取消/截断的可观察码和继续分页方式；明确单个诊断失败是否隔离、其余诊断如何返回，以及结果不完整时不得伪装成完整的 pending。预算应同时覆盖计算和输出，不只覆盖 RPC 消息。

### 11. 模型窄问题的结果没有进入诊断输入或待处理生命周期
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/specs/canon/model.md:62-75,204-205`；`docs/specs/canon/project.md:19-21,45-48`；`docs/proposals/world-engine-plot-side.md:229-241`
**现象**：内核诊断计算被限定为同步、确定、不调用模型的纯函数；插件贡献点只有登记声明和计算入口。提案的剧情检查却明确包含记账 Agent 的窄问题、读者试读、写作指示层和新事实层，并要求它们的结果成为待处理。六份内核 Spec 没有持久化窄问题答案、证据原句、问题对应候选/世界版本/正文快照的对象或 Component，也没有把“等待模型结果”转换为诊断输入的接口。
**为什么是问题**：剧情插件不能一边遵守“diagnostic 计算不调用模型”，一边让模型回答直接出现在 `pending`；若把结果只留在后台任务内，重启、正文变化或重新读取后就没有稳定结果，作者对待处理的处理也无法绑定到一次可复现的答案。若把答案写成普通决策，又会把“模型观察”错误地当成作者决定。后续六份剧情 Spec 照字面接入时必须临时另造存储和版本规则。
**如何核实**：以“本章可能穿帮”为例：先由插件圈出候选，再让模型回答并引原句。尝试把回答交给 `canon.diagnostics`：纯函数签名没有写入入口；尝试直接在诊断计算里调用模型：违反输出 34 的同步确定合同；尝试只挂一条作者处理决策：决策只能表达处理，不保存模型答案本身。
**建议改法**：明确插件拥有的答案/检查结果存储形状和写入通道，至少绑定候选 id、问题版本、世界版本、正文快照、模型/提示版本、原句证据和结果状态；内核诊断只消费这一份已持久化输入，并规定缺结果时是“未完成”而不是 `diagnostic-unavailable`。作者处理决策继续只表示作者裁决，不能替代模型证据。

### 12. 回溯的 `back` 没有可表达“往回多久”的值形状
**严重程度**：阻断；**类别**：正确性
**位置**：`docs/specs/canon/worldlines.md:45-50`；`docs/specs/canon/time.md:51-63,71`
**现象**：世界线把 `back` 声明为“时间说法”，但时间说法的 `kind` 只有 `date`、`after`、`before`、`lasts`、`age`、`birth`。其中 `lasts` 表示事件 E 的结束时间减开始时间，`after`/`before` 必须引用另一件剧情变更；没有独立的持续时间/间隔值能表示“回溯约半天”或“触发处往回 6 小时”。输出 6 只说从触发处时间减去 `back`，没有定义如何从这些说法取一个区间并做减法。
**为什么是问题**：作者或 Agent 无法按公开形状构造世界线输入；拿 `lasts` 代替会把回溯分叉自身当成有持续时间的事件，拿 `after` 代替又多出无意义的事件引用。跨线下界、`fork-time-mismatch` 和按历法格式化因此没有唯一计算。
**如何核实**：尝试编码提案与时间验收中的“往回半天”：`{kind:"lasts",...}` 缺少“这是 back 的区间”语义，`{kind:"after",of:...}` 只能表达事件相对另一事件；两者都无法给出 worldlines 输出 6 所需的直接 duration。现有时间原型虽演示了数值下界，但没有对应的 Spec 输入联合类型。
**建议改法**：增加独立的 `Duration`/`gap` 形状（`min`、`max`、`unit`、可选原话/词表和不确定性），让 `fork.back` 明确使用它；定义触发处范围与 duration 范围的区间运算、开放端和历法变化后的重算，再给 `fork-time-mismatch` 的精确判定。

### 13. 自定义历法的合法性和年龄计算不足以得到唯一结果
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/time.md:28-49,55-62,66-82,96-103,112-116`
**现象**：历法允许 `unit` 为 `minute`、`hour` 或 `day`，但日期说法仍可同时给 `hour`、`minute`；没有规定这些字段在较粗最小单位下是非法、被舍弃还是换算。`months`、`leap`、`eras`、`periods` 的唯一性、范围、重叠/缺口和端点规则也未定义，而 `calendar-invalid` 只举了月天数和闰年指向不存在月份两类错误。年龄只写成 `E.s - birth` 落在 `min` 到 `max + 1` 年，没有定义可变月长/闰年下的周年、生日边界和纪年转换。
**为什么是问题**：同一历法配置可被不同实现接受为不同时间轴；例如 `unit: day` 的“612 年霜月 5 日清晨”是否仍能落到“几个小时”没有合同。用绝对分钟差除以某个年长不能表达自定义历法的生日年龄，验收要求“出生在 597 年、事件在 612 年答 15 岁”也无法判断跨年边界和事件范围。
**如何核实**：构造一天 48 小时、月份天数可变、`unit: day` 的日期并分别给 minute；再构造生日落在年末、事件范围跨生日的 15 岁说法。输出 9、10 没有拒收码或区间算法能决定这些情况；原型证据只说明按最短/最长年近似，且明确从简，不能替代当前合同。
**建议改法**：定义历法校验的完整约束（字段依赖、整数/正值、月与纪唯一性、闰年覆盖、时段端点和 unit 精度）；把日历日期的精度与最小单位关系写成可测试规则。单独定义年龄的日历周年算法和区间边界，或明确年龄只做绝对单位的保守范围并修改验收期望。

### 14. 非正文讲述的锚点被声明为可选，无法稳定定位来源
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/specs/canon/model.md:36,112-123,194-196`；`docs/specs/canon/revisions.md:72-76`
**现象**：术语和提案说细纲、消息、界面确认、种子和手记要用各自锚点；但讲述输入表把 `anchor` 定为可选，且没有按 `source` 规定哪些字段必填、锚点引用哪个宿主对象、对象删除/改版后怎样失联。`quote` 对非正文来源也可选。这样 `{source:"message"}` 可以既没有 `anchor` 也没有 `quote`。
**为什么是问题**：这类讲述没有可观察的出处、无法在修订中稳定改同一条、无法和作者来源或计划节点关联，也不能判断它是否仍然存在。实现者只能自行选择“永远有效”“立即失联”或把它当正文定位；而 model 输出 24、26 只为正文定义了发生点和失联。
**如何核实**：发布一条只带 `source: "message"`、无 `anchor`/`quote` 的讲述，再读取 `tellings`、修改原消息或还原写入它的修订；现有输入表没有失败码、定位点或失联规则。当前内核校验也只对正文讲述调用 `chapterText`（`packages/nb-canon/src/world/world.ts:642-643,698-700,737-738`）。
**建议改法**：按来源列出必填锚点和可选原文的精确形状，规定宿主对象的存在/删除/版本与失联语义；若允许无锚点的作者备注，应明确它只是不可定位的历史来源，不能参加计划、读者钟或依赖它的诊断。

### 15. 决策状态表没有规定转换时的字段清除与同请求原子关系
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/model.md:126-145,220-240`；`docs/specs/canon/revisions.md:70-77,107-108`
**现象**：状态表只列每个状态“必有”字段和允许的状态转换。它没有规定 `decided -> pending` 或 `dropped -> pending` 时是否必须清除 `conclusion`、`reason`、`risks`、`constraints`、`source`；也没有规定 `pending -> decided` 时建议、候选、到期章、旧来源是否保留。`decided -> superseded` 要求目标决策同时或更早已定，但没有说明同一写入请求内新建目标决策的校验顺序、作者来源分别绑定哪一项。
**为什么是问题**：同一个状态的对象可能带着上一状态的结论和来源，渲染时“待定”却仍显示旧结论；不同实现会选择保留、删除或转成历史字段。取代关系若允许同请求创建，来源校验和临时 id 替换的顺序会影响 Agent 能否用一次原子修订完成开发者确认的生命周期。
**如何核实**：从已定决策重新打开而不提交字段删除，再读取对象；或在一次请求里新建已定决策 B、把 A 转 `superseded` 并用临时 id 指向 B。当前状态表与失败表都没有对字段残留、操作顺序和失败回滚给出可测试结果。
**建议改法**：为每个转换列出保留、清除和迁移的字段，禁止不属于目标状态的旧字段或将其放入明确的历史区；规定同请求对象的拓扑校验、来源签名覆盖范围和失败时整批回滚。把“必有”与“允许但不展示/历史保留”分开写。

### 16. 标注 `refs` 声明没有定义 schema 路径和版本兼容的可执行边界
**严重程度**：建议；**类别**：接口与合同
**位置**：`docs/specs/canon/components.md:86-95,115-123`；`docs/specs/canon/model.md:198`
**现象**：`refs` 只说路径用 `.键` 逐级写、`[]` 表示数组每个元素，校验时要求“路径在 schema 里存在、是字符串”。没有指定 JSON Schema 方言、对象属性与数组索引的语法、`oneOf`/`anyOf`/`$ref`/可选属性的路径是否成立，以及同一 schema 位置能否声明多个目标类型。标注版本只在登记声明中按整数比较，没有规定版本 2 如何解释旧载荷、旧版本是否还能被旧插件共同登记。
**为什么是问题**：内核与两个插件实现者会对同一载荷得出不同引用集合，导致临时 id 不换、错误校验或还原依赖漏报；复杂载荷只能把 `refs` 路径删掉来绕过校验。版本对不上时“只读”虽然保住原文，但没有定义旧插件声明是否可同时存在、一个标注是否能被多个版本读取，插件恢复时会出现不可判断的可用状态。
**如何核实**：用 `schema: {oneOf:[...]}`、`nodes: [{point: ...}]`、可选 `point` 和 `$ref` 的载荷各声明一条 `refs`，按“路径存在且是字符串”没有唯一结果；再分别登记同一 `id` 的版本 1/2，Spec 只有 namespace 冲突规则，没有标注 id 冲突/版本集合规则。
**建议改法**：固定 JSON Schema 方言并定义可遍历的子集与路径语法；明确数组、联合、缺省属性和重复 refs 的行为。规定同一标注 id 只能有一个当前版本、旧版本载荷的读取/停用规则，并把版本变化与 schema/引用路径变化的兼容边界写成验收场景。

### 17. 带过去的内部快照没有地址约束和补偿依赖
**严重程度**：重要；**类别**：不变量
**位置**：`docs/specs/canon/worldlines.md:32,49-50,57,72-73,77`；`docs/specs/canon/components.md:60-70`；`docs/specs/canon/revisions.md:99`
**现象**：`carry` 只给 `{entry, path}` 列表；缺省值按 `who` 的 `carry: true` 字段补上，但显式 `carry` 没有限制必须属于 `who`、必须是声明过的叶子、不能重复，也没有约束列表元素/引用目标/类型版本。带过去的值是线视图中的内部事件，不是日志记录；跨线还原只规定“子线上修订依赖定义线的分叉修订”，没有把这个内部事件的来源快照和分叉参数变更纳入依赖或补偿顺序。
**为什么是问题**：同一分叉可以把任意条目的隐私/状态带到新线，或者把一个列表整体快照当作回溯者携带；切口、触发、`carry` 或父线相关修订被修改/还原时，哪些子线状态必须重建、哪些后续修订应被列为依赖没有唯一规则。原型用固定的 `carry` 地址和简单 `set` 合成事件验证了数值与列表，但没有覆盖地址合法性和还原。
**如何核实**：构造 `who = e1`、`carry = [{entry:e2,path:"secret.x"}]`，再把 `carry` 指向不存在字段、已删除元素或语义列表；当前输入表没有对应失败码。随后还原定义 r1 的修订，比较 r1 上一条修改了带过去地址的修订是否应被列为依赖，输出 11 与 revisions 的地址规则没有给出答案。
**建议改法**：定义 carry 地址的完整校验和所有权规则（显式地址是否仅限 `who`、列表元素如何选择、版本/未知值如何处理）；给合成事件稳定的线内身份和父线快照依赖，规定修改分叉参数、父线来源或还原时的重建、依赖发现和补偿顺序，并补对应差分场景。

### 18. 删除目标后的引用与补丁语义前后矛盾
**严重程度**：重要；**类别**：正确性
**位置**：`docs/specs/canon/components.md:116-121`；`docs/specs/canon/model.md:184,203`
**现象**：引用规则说目标条目后来删除时，已有引用继续显示“已删除的条目”，并写“对它的补丁照常套上”；条目删除规则又说“对它的补丁套不上”。前者的“它”没有明确是引用字段、被引用条目还是引用所在列表元素，后者明确按被删除条目的地址拒绝补丁。
**为什么是问题**：实现者可以让删除目标后的补丁继续修改墓碑条目，也可以让引用所在对象的后续补丁全部失效；两种结果会改变回溯、来历、`keyedBy` 的显示名和还原依赖。新增引用又要求目标未删除，因而“旧引用保留但能否改它”也没有闭合。
**如何核实**：建立条目 A 的字段引用 B，删除 B；分别发布对 B 的字段补丁、对 A 的引用字段补丁和对 A 的 keyed 列表行子字段补丁，再读取 B/A。按两处文字无法判定三者哪些应套上；现有内核校验只按补丁 `target.deleted` 报 `entry-missing`（`packages/nb-canon/src/world/world.ts:738-741`），没有新规则可消除歧义。
**建议改法**：把对象写全：明确“被引用条目 B 的补丁”与“保存引用的字段/列表行的补丁”分别适用什么规则；定义删除后改引用、改行和还原删除的校验、显示名和来历。若 B 的墓碑只读，应统一使用 `component`/`model` 同一个失败码，不能用“对它”代称。

- **讲述发生点的基本定位算法**：段的定义、UTF-16 偏移、`nth`、重复原句首处提示、失联/重新定位的基本规则彼此一致；发现的问题是它与正文快照/缓存身份的交互，不是这套定位字段本身缺少编码。
- **现有内核的基础折叠与线原型的已验证部分**：在真实 `nb-canon` 上运行 `bun test`，结果为 `237 pass, 0 fail, 69889 expect() calls`；从主工作区运行 `bun lines.ts`，原型报告了回溯、多层分叉、计划跨线、越界和按值比对场景的结果，未据此发现原型已覆盖规则的反例。原型不是新 Spec 的合同测试，仍不能替代报告中的缺口。
- **精确数、语义档、版本只读、分段日志和单写者的既有规则**：本批新增条目没有发现另一个独立于上述问题的矛盾；它们仍需按修改后的格式 2 重新做合同测试。
- **时间原型已测的规模数字**：证据中的 10,000 件和 50,000 件时间网络测量分别为 29.0 ms/5.3 ms/6.7 ms 与 100.2 ms/26.1 ms/47.6 ms，未据此认定“速度要求必然不可达”；报告的问题是输入和边界不足以保证同样的测量口径。
- **视图的线/位置上限和拒绝审计**：`openView` 的绑定、`view-denied`、最近 500 条审计和“按知情过滤交给剧情插件”的分工已写出；未另列超出已报告缓存快照身份问题的发现。
