## 新发现

### 42. 授权只绑这条决策自己的字段；同一请求里被它引用的对象（新建的 tmp:k、或同时改了内容的已有知识点）不受约束，同一个 requestId 下可以换掉授权的对象
**严重程度**：重要；**类别**：不变量 / 泄露（授权被挪用）
**位置**：revisions.md:109-112（binds 是 `{project, requestId, decision, transition, fields}`，fields 按请求原样只取这条决策需要来源的字段）、:163（验收 7 新加的 tmp:k 与 tmp:d）、:104（输出 16：request-id-reused 只在同一 requestId 已经发布过时才判）
**现象**：binds.fields 只是这条决策的那几个字段。按请求原样算以后，tmp:d 的 about 里存的是字面上的 `tmp:k`，它指什么完全由同一请求里另一条 puts（新建 tmp:k 的那条）决定，而那条不在任何 binds 里。Agent 拿到宿主为请求 Q（“知识点 tmp:k = 甲是内鬼；决策 tmp:d：这个秘密留到第 30 章”）签发的授权后，可以不发 Q，改发 Q′：同一个 requestId，tmp:d 原样，只把新建 tmp:k 的内容换成“乙是内鬼”。内核按请求原样算出的 binds 与签发时逐字相同，校验通过；Q 从没发布过，所以也不会得到 request-id-reused。挂已有知识点 e5 时同理：同一请求里再放一条改 e5 内容的 puts，授权照样通过。
**为什么是问题**：验收 7 写的是“Agent 把为‘决策 A 定为结论 X’签发的合法来源……用到另一个结论上都是 author-source-invalid”，作者来源这套机制要防的就是 Agent 改换作者授权的内容。第二轮第 19 条（S1b）也提醒过“不能靠忽略这类摘要差异解决，否则重新打开了替换授权对象的路径”。本版改成按请求原样算，正好把“同请求新建并引用”变成了推荐写法（验收 7），而被引用对象的内容恰恰没有绑定。这个缺口在第二轮版本里也有（按结果值算时 tmp:k 换成 e1，e1 的内容照样不绑），本版的改法与新验收让它成了主路径。
**如何核实**：读 revisions.md:109-112 的 binds 组成，与 :104 的 request-id-reused 判定条件对照；按上面的 Q 与 Q′ 逐项算 binds，两者的 project、requestId、decision、transition、fields 都相同。内核还没实现授权，结论从 Spec 推断。
**建议改法**：binds 里加一项 `request`：写入请求去掉 `authorizations` 与 `baseVersion` 以后按规范 JSON 取的 SHA-256（宿主签发时有整份请求，能算；去掉 authorizations 避免循环）。这样同一请求里任何别的对象被改，授权都失效；fields 可以保留，用来说明授权的是哪几个字段。验收 7 补一条：同一 requestId、只改新建 tmp:k 的内容：author-source-invalid。

### 43. 还原要带的授权按 fields 的“补偿后的值”签，但公开接口上拿不到补偿：没有还原的预览，改动记录也不给 ops
**严重程度**：重要；**类别**：照字面做不出来
**位置**：revisions.md:114（还原：每条受影响的决策一项，`binds.requestId` 是还原请求的 id，`fields` 按补偿后的值算）；project.md:73（`preview` 的参数只有“写入请求”）、:70（`revisions` 返回改动记录，即 revisions 输出 14：谁、种类、标题、时间、带来的变化的摘要、能不能还原）、:77（`revert`）；revisions.md:163（验收 7：作者带来源还原，决策回到待定）
**现象**：普通写入的 fields 宿主照着自己手上的请求就能算。还原请求里没有决策的值，只有修订 id、是否连同依赖与请求 id；补偿要恢复成什么、哪几条决策受影响、各是哪个转换（例如 decided→pending），只有内核算得出。宿主要签 `binds = {…, decision, transition, fields}`，就得先知道这三样。可是 `preview` 只收写入请求，`revisions` 只给摘要，`author-source-required` 的详情（revisions.md:133）也没说会列出需要哪些授权、各自的 fields 摘要。连同依赖还原时，补偿是几次修订合起来的结果，宿主自己更算不出。
**为什么是问题**：验收 7 的“作者带来源还原，决策回到待定”与第二轮第 20 条要的“多决策连同依赖还原”都做不成测试；照字面实现，宿主只能自己重写一遍补偿与依赖的计算，再和内核逐字对上摘要，等于在宿主里复制内核。
**如何核实**：在 project.md:50-80 的方法表里找能返回补偿 ops 或补偿后决策值的读方法：没有。
**建议改法**：二选一写死。（a）`preview` 也收还原请求（修订 id、是否连同依赖），返回补偿，并列出需要授权的 `{decision, transition, fields 摘要}`；（b）还原缺授权时 `author-source-required` 的详情列出这些项。还原的 fields 改成内核给出的摘要，宿主照抄签名。验收 7 补“还原一次修订，它改过两条已定决策”：先预览（或先得到 author-source-required），按列出的两项签发，再还原成功。

### 44. 兑现过的计划线，已写分叉撤销后变回计划线，上面已经写下的记录在实际模式下不进任何视图、也不成任何待处理，静默消失
**严重程度**：重要；**类别**：引入新的不确定性（修正引入）
**位置**：worldlines.md:61（输出 1：有生效的已写分叉时由它定义，否则由生效的计划分叉定义；计划线上的记录“在实际模式下不进任何视图，也不成线不存在”）；model.md:191（输出 16 同一句）；worldlines.md:77（输出 11：要去掉一件事又留着子线记录，用撤销而不是还原）、:111（line-planned 只是写入时的拒收码）
**现象**：序列：先写计划分叉 pf（line = if1）；再写已写分叉 wf 兑现它（同一 line），if1 成为真线；在 if1 上记了第 20 到 30 章的账（已写记录）；作者撤销 wf（剧情变更 active→undone，普通写入，不受还原依赖限制）。pf 仍生效（兑现以后计划照旧是计划），于是按输出 1 if1 变回“只由生效的计划分叉定义”的计划线。if1 上那十一章的已写记录：实际模式下不进任何视图，按本版新加的那句也不成“线不存在”；line-planned 只在写入时拒收，已存的记录不会再报。实际模式的待处理里，这批记录一条都不出现。
**为什么是问题**：本版加“也不成线不存在”是为了让计划线上的计划不在实际模式下变成一堆 line-missing（第二轮第 22 条），这对计划是对的；但它把计划线上的所有记录一起豁免了，而计划线上恰恰可能有已写记录（就是上面这条路径）。没有 pf 时同样撤销 wf，这些记录会成 line-missing 待处理；有 pf 时反而什么都不报。作者只在按计划模式下才看得到它们。
**如何核实**：按上面的序列读 worldlines.md:61 的三句（已写分叉定义、否则计划分叉定义、计划线上的记录在实际模式下不进视图也不成线不存在），以及 :111 的 line-planned 只在写入时报。
**建议改法**：把豁免收窄到计划：“计划线上的计划在实际模式下不进视图、不成线不存在；计划线上的已写记录（兑现它的已写分叉撤销或被替代后留下的）在两种模式下都各成一条待处理 `line-planned`（或 line-missing），根因是那次撤销”。worldlines 失败表 line-planned 的含义改成“写入时拒收；已存的成待处理”。验收补这条序列。

### 45. R 被定成“相对元年的常量”，在没有任何说法连到元年的故事里退化成无约束：回溯的时间检查与验收 5 都不再成立
**严重程度**：重要；**类别**：照字面做不出来（修正引入）
**位置**：time.md:74（输出 6：先在父线上算出触发处起点的范围 [a, b]，R 落在 `[a - back.max, b - back.min]`，当作 R 与元年之间的常量约束）、:63（输出 1：没有任何说法连到元年的事件，范围是相对的，只能回答与别的事件相差多久）、:124（验收 5）
**现象**：大量作品只写相对时间（“三天后”“第二天傍晚”），没有一条 date 说法。这时父线上触发处相对元年的范围是 (-∞, +∞)，R 的常量约束也是 (-∞, +∞)：子线里 R 与切口、与共同过去之间没有任何关系。父线上明明知道“触发处在切口之后两天”，这条信息在常量化时丢掉了。父线上触发处的分量也不是“不可确定”，所以连“R 不加约束”的那条待处理也不报。
**为什么是问题**：fork-time-mismatch（切口一定晚于 R）在这类作品里永远不会报；验收 5 的“子线上第一件事不早于触发处减半天”也只在作品有绝对日期时成立。第二轮第 24 条要的是一种能落地的写法，常量化选对了“触发处不在子线视图里”的那一半，却只保留了与元年的关系。
**如何核实**：`bun /tmp/w00039-specs-review3a-lab/rollback-relative.ts`（在 nb-canon 包目录；一个 20 行的最短路 STN）：父线只有“触发处 = 切口 + 2 天”，没有连到元年的说法，往回 3 天。打印：父线上触发处相对元年的范围 [-Infinity, Infinity]；按本版写法，cut − R 的范围 [-Infinity, Infinity]，判不出“切口一定晚于 R”；按相对写法（R − 切口 = 触发处 − 切口 − back），cut − R = [1440, 1440] 分钟，切口一定晚于 R，应报 fork-time-mismatch。
**建议改法**：不只取“触发处相对元年”，而是取触发处相对子线视图里、与它在父线上同一分量的各点的差：至少对切口与元年两点各加一条常量约束——`R − 切口.s ∈ [d⁻ − back.max, d⁺ − back.min]`，其中 [d⁻, d⁺] 是父线上“触发处起点减切口起点”的范围；连到元年时再加现有那条。这样父线上的打架照样不传进子线（只引入算好的常量），相对时间的作品也能检查。验收 5 写明有无绝对日期两种情形。

### 46. 年龄的“按顺序取第一个适用的”与新验收 6 的第三句给出相反的答案；time-age-disagree 在有出生事件时几乎到不了
**严重程度**：重要；**类别**：新规则互相矛盾
**位置**：time.md:86（输出 12 的顺序：分量不可确定 → 有 age 说法答交集（空则并集加提示）→ 没有出生事件答“不知道” → 尚未出生 → 公式）；time.md:125（验收 6）
**现象**：
- 输出 12 把“有 age 说法”排在“没有出生事件”之前。一个没有出生事件的人，这件事上有一条“十五岁”的说法：按顺序第二步就适用，答“15 岁”。验收 6 第三句写的是“答‘不知道’，这条说法不进网络”。两者只能有一个对。
- 同一份修订记录（round2-resolution.txt）写的也是“不可确定、age 说法取交集、交集空答并集并提示、没有出生事件答不知道”的顺序，与验收 6 的第三句一致的是另一种顺序。
- 有出生事件时，两条 age 说法都进网络。用公历（L(15) = [5477, 5479] 天、L(16) = [5843, 5844] 天、L(17) = [6209, 6210] 天，按第二轮第 21 条的实算），“十五岁”与“十六岁”两条约束的交集是差值落在 [5843, 5844) 天，只有生日前后一天的窗口；这件事或出生只要还有别的说法把差值挪出这一天，分量就打架，按第一步答“不可确定”，不给 time-age-disagree。年长固定（没有闰年）的自定义历法里 L_min(16) = L_max(16)，交集恒为空，有出生事件时这条提示永远到不了。验收 6 第一句之所以成立，靠的是公历的这一天窗口。
- time-age-disagree 是“提示”，但它出在 `time` 查询的结果里还是 pending 的提示组里，没写（pending 是按读取位置算的，年龄是一次查询）。

### 52. “同一个 id 被声明不止一次（不论哪个插件）时这几条都不登记”：前缀不对的非法声明也算一次，能把别人合法的那条挤掉
**严重程度**：建议；**类别**：新规则的副作用
**位置**：model.md:68（诊断：前缀必须是声明者；“不合规则或同一个 id 被声明不止一次（不论哪个插件）时，这几条都不登记”）；components.md:115（标注种类：同样两句）
**现象**：既然前缀必须等于声明者的插件 id，两个插件能声明同一个 id，只有一种情况：其中一个前缀写错了（插件 A 声明 `B.x`）。按字面，A 的这条非法声明与 B 合法的 `B.x` 一起算“声明不止一次”，两条都不登记。于是“不论哪个插件”这半句的唯一作用，是让一条本来就不合规则的声明把另一插件的合法诊断（与挂在它上面的作者决策、已存的标注）一起废掉。
**为什么是问题**：一个写错的插件让另一个插件的诊断全部 diagnostic-declaration-invalid、标注全部 mark-kind-unknown，排查方向会指向无辜的插件；第二轮第 33 条要的是“撞 id 时不让作者的处理挂到别人的诊断上”，前缀规则已经解决了，不需要连坐。

**建议改法**：写成两步：先按前缀筛，前缀不是声明者的那条不登记、写诊断，不参与重复判定；再在剩下的（因此都来自同一插件）里，同一 id 出现不止一次的全部不登记。

**建议改法**：输出 13 写明“不存在”指两种模式下都不存在，计划线在实际模式下按输出 12；输出 1 的括号改成“所有不带模式参数、或模式为实际的读取”，并写明 lookup 按实际模式算（与 model 输出 14 一致），tellings、changes 按线筛时计划线照常可筛（它们不是视图）。

### 56. 提示组的种类不在排序的种类表里，“排序是全序”对提示组不成立
**严重程度**：建议；**类别**：可测性（修正引入）
**位置**：model.md:191（输出 16：同一位置按种类（核对点不符、套不上、待定、章已删除、世界线、时间、插件的诊断）排序；“排序是全序”）、:209（输出 34：提示与待处理排序规则相同；本能力自己的提示 telling-lost、duplicate-quote、mark-kind-unknown、mark-version-unsupported）；worldlines.md:78、:79、:82（binder-line-planned、telling-line-mismatch、binder-line-ended、binder-line-unknown）；time.md:86（time-age-disagree）
**现象**：本版把输出 16 的排序声明为全序，并定义了各类待处理的排序位置与排序 id。可提示组里的十来种提示（上列）都不在“同一位置按种类”的七类里，它们排在哪、彼此怎么比，没有定义；它们的排序位置（例如 binder-line-planned 是一段活页夹，没有安放）与排序 id 也没定义。整项规范 JSON 的兜底只在种类比较有定义之后才用得上。
**为什么是问题**：提示组同样用游标分页（project.md:60），顺序不唯一时翻页会重复或漏项，这是第二轮第 30 条要解决的同一个问题。
**如何核实**：对照上列原文。
**建议改法**：种类表后加“提示组里，本能力自己的提示按（列出顺序）、各 Spec 的提示按（列出顺序），插件的诊断在最后”；没有安放的提示（活页夹一段的）以那一段所在章的开头为排序位置，排序 id 取涉及对象引用的规范 JSON。
