### 1. 章首读取仍报告整章检查结果
严重程度：重要；类别：正确性；位置：packages/neuro-book/src/plugins/plot/core/checks/diagnostics.ts:2852-2858。
现象：`findingsAt` 只用 `view.chapters.indexOf(record.chapter) > now` 截断记录，没有处理 `at.edge === "start"`（也没有段内位置）。因此读取第 N 章章首时，已经存有第 N 章检查记录仍会进入 `validFindings`，报告本章正文产生的 `possibleSlip`、规则违反、新事实等。
为什么是问题：canon 的诊断计算按读取位置返回结果；章首尚未读到第 N 章，写完第 N 章的检查发现不应出现在章首视图。当前实现把“同章”直接当成“不晚于读取位置”，会在开写前或读取章首时泄露未来结果，破坏位置隔离与待处理截断。
如何核实：在实现工作树运行以下实验，输出了非空的 `possibleSlip`：
`bun -e 'const {PlotWorld, chapter, present} = await import("./src/plugins/plot/testing/world.ts"); const {runOk, scripted, digest} = await import("./src/plugins/plot/testing/checks.ts"); const {checkDiagnostics} = await import("./src/plugins/plot/core/checks/diagnostics.ts"); const {CHECK_DIAGNOSTIC_IDS} = await import("./src/plugins/plot/shared/declarations.ts"); const cs=Array.from({length:6},(_,i)=>\`ch\${i+1}\`); const w=new PlotWorld(cs); const hero=w.person("勇者"), guard=w.person("卫兵"), k=w.point("勇者左手有星形的疤",hero,{保密:"secret"}); const q="卫兵盯着旅人的左手，说：你是勇者吧"; w.texts.set("ch4",\`\${q}。\\n\`); w.change(chapter("ch4"),{cast:[present(guard)]}); const r=await runOk(w,"ch4",scripted((_,x)=>x.answer==="yesNo"&&x.user.includes("把这件事当真")?{answer:"yes",quotes:[q]}:undefined).models); const c=checkDiagnostics({all:()=>[r],valid:()=>true},digest); console.log(JSON.stringify(c[CHECK_DIAGNOSTIC_IDS.possibleSlip](w.view(),{kind:"chapter",chapter:"ch4",edge:"start"},"actual")));'`
建议改法：按 `ReadPosition` 完整截断：章首对 `record.chapter` 直接跳过；段位置只保留发生点不晚于该段的记录（或者将检查诊断合同明确限制为章末，并在计算入口拒绝/不注册其它位置）。补充章首、章内段与章末三种位置的行为测试。
### 2. 依赖摘要回写会覆盖同章刚保存的新检查记录
严重程度：重要；类别：不变量；位置：packages/neuro-book/src/plugins/plot/backend/plugin.ts:248；packages/neuro-book/src/plugins/plot/backend/checks.ts:81-85；packages/neuro-book/src/plugins/plot/core/checks/source.ts:446-475。
现象：诊断读取旧记录 R1 时，`source.valid` 发现依赖摘要变了且 R1 仍有效，异步排入 `store.queued(() => store.write(records, R1'))`。如果同章新的 `run` 已经先排入并完成保存 R2，随后 R1' 仍用当前 revision 正常写入，会把 R2 的新调用、答案与发现覆盖掉，只保留 R1 的旧内容和新的 dependencies。回写没有比较记录身份、世界版本或调用摘要，也没有调用 `changed` 之外的冲突保护。
为什么是问题：检查记录“同一章只留最新一条”且新跑的结果应替换旧结果；旧诊断回写只能更新它验证过的那条记录的摘要，不能把较旧答案写回去。发生后 `source.valid` 看到 R1' 的 dependencies 已等于当前摘要，会直接返回有效，旧的答案持续成为待处理结果，且数据版本没有变化，问题不会自愈。
如何核实：在真实项目子进程场景中，先保存一条有效 R1；让世界变化使 `pending` 触发 `source.valid`，在它已排队回写但尚未执行时，对同一章调用 `checks.run` 保存 R2；让队列先执行 R2、再执行此前的回写，随后调用 `checks.record` 并读取持久化记录，记录的 `calls`/`usage` 会回到 R1 而不是 R2。代码路径上，`source.valid` 捕获的是传入的旧 `record`，`createChecks.run` 的保存只按章写入，两个 `store.queued` 没有版本或记录摘要条件。
建议改法：回写时在队列内重新读取当前表值，只有当前值仍是回写所基于的记录（至少比较 `contentOf` 摘要、调用集合摘要或存储 revision）才写入；更简单的是让 `source.valid` 只返回新 dependencies，把回写交给一个按章的去重写回任务，并在任务执行时丢弃已被新 `run` 替换的旧记录。为该竞态加真实项目存储测试，断言 R2 的 `calls` 与答案不被回写覆盖。
### 3. 提前泄底没有附上挂在知识点地址上的决策
严重程度：重要；类别：正确性；位置：packages/neuro-book/src/plugins/plot/core/checks/diagnostics.ts:2756-2761。
现象：`decisionsOn` 只匹配 `decision.about` 中 `kind === "entry" && about.id === point`，不匹配 `kind === "address" && about.at.entry === point`。因此同样挂在知识点 K 的 `K.name`、`K.summary` 或 Component 地址上的读者守卫/决策，在 `earlyReveal` 发现的 `objects` 中不会出现。
为什么是问题：`checks.md` 输出 8 要求提前泄底附上挂在 K 上的读者守卫与决策；`decisions.md` 输出 7 与 `involvedDecisionObjects` 已把 address 的条目作为挂点对象处理。当前结果让作者看不到实际约束来源，且同一决策改用 address 形状就改变了泄底诊断内容。
如何核实：在实现工作树运行以下实验：创建答案 K、悬念与第 20 章明说揭示，在第 12 章触发试读，再创建 `about: [{kind: "address", at: {entry: K, path: "entry.name"}}]` 的决策。实验输出 `earlyReveal.objects` 只有 K，没有该决策；把 about 改为 `{kind: "entry", id: K}` 后同一实验会附上决策。实际运行命令已验证前一种输出，结果 `objects:[{kind:"entry",id:"e2"}]`。
建议改法：将挂点判断抽成与决策涉及逻辑一致的 helper，匹配 `entry` 与 `address.at.entry`；读者守卫仍按 `marks` 匹配 point。补充 address 挂点的真实诊断测试，并同时检查账本 `revealDependencies` 的同形遗漏。
### 4. 取消在模型完成后仍可能把检查记录落盘
严重程度：重要；类别：不变量；位置：packages/neuro-book/src/plugins/plot/backend/checks.ts:79-87。
现象：`runCheck` 返回成功后，`createChecks.run` 无论 `controller.signal` 是否已取消，都会把 `result.record` 排进 `store.queued` 并写入。若同章已有存储队列工作，`cancel` 可以在模型调用完成、等待队列期间发生；队列回调没有再次检查信号，仍保存记录并返回成功。
为什么是问题：失败表明确规定 `plot-check-cancelled` 被 `cancel` 或入口停止时“这次检查没有存”。当前取消时序会出现调用方收到取消/或停止路径正在收口，但持久化结果已存在；下次 `record`/待处理会把一条调用方已取消的半成品当成有效候选，违反资源收口与记录状态不变量。
如何核实：在真实项目合同测试的“同章检查正在运行”场景中，让前一条 `store.queued` 持有项目记录写入队列，再让模型调用全部返回；在 `checks.run` 返回 `runCheck` 成功、进入队列等待后调用 `checks.cancel({chapter})`，释放前一条队列，随后读取 `checks.record`。当前代码会读到刚写入的记录，而不是 `status: none`。静态路径也直接成立：`runCheck` 成功后第 81 行没有 `controller.signal.aborted` 检查，队列闭包第 82 行没有检查。
建议改法：在入队前和队列闭包内都检查 `controller.signal.aborted`，取消则返回 `plot-check-cancelled` 且不调用 `store.write`；入口停止还要让已排队但尚未写入的回调失效。补充“模型完成后、存储排队期间取消”的真实项目存储测试。
### 5. `available()` 阶段不可取消，模型服务卡住会永久占用 busy
严重程度：重要；类别：不变量；位置：packages/neuro-book/src/plugins/plot/core/checks/run.ts:87-90；packages/neuro-book/src/plugins/plot/backend/check-models.ts:19-25。
现象：`runCheck` 在创建 `AbortController`、注册取消 relay 之前先 `await models.available()`；`CheckModels.available` 没有 `AbortSignal`，远程实现也用没有超时/信号的 `use.available({})`。因此模型服务端入口或 RPC 在可用性探测阶段挂住时，`cancel` 与入口停止只能 abort `createChecks` 的 controller，不能结束这个 await，`running` 一直保留，后续请求持续返回 `plot-check-busy`。
为什么是问题：Spec 的 `cancel`/`plot-check-cancelled` 覆盖整次检查，不能只覆盖已经开始的答案调用；阶段 F 也明确把挂住的模型通道列为会卡住 busy 的风险。一次服务端异常就会把这一章永久卡在运行中，直到进程重启。
如何核实：让真实项目合同测试中的 `nbook.plot/model.available` 请求不返回（或让服务端入口在解析角色时阻塞），调用 `checks.run` 后立即调用 `checks.cancel`；当前 `status` 仍是 `running: true`，`run` Promise 不结束。纯端口复现也只需让 `CheckModels.available` 返回永不结算的 Promise；代码在第 89 行前没有任何 signal/timeout。
建议改法：先建立批次 AbortController 并把 signal 传给 `available(signal)`，给可用性探测独立的短超时；或在 `Promise.race` 中监听取消/入口停止并返回 `plot-check-cancelled`。远程 `available` 合同同步补上取消与超时，测试覆盖服务未响应、cancel、入口停止三种路径。
### 6. 并发失败返回的用量漏掉同批已完成调用
严重程度：重要；类别：正确性；位置：packages/neuro-book/src/plugins/plot/core/checks/run.ts:99-103、122-139、160-166。
现象：`fail(failure(...))` 在第一个 fatal/长度错误完成时立即把 `total` 的当前值复制进 `failed`。`Promise.all` 随后仍等待同批其它调用，但这些调用的 usage 只更新外层 `total`，不会更新已经保存的 `failed.usage`。返回的 `plot-check-failed` 因而不是“到此为止”的实际用量。
为什么是问题：失败表明确要求 `plot-check-failed` 带到此为止的用量；并发调用已经向模型付费，漏报会让费用回执与真实消耗不一致，尤其是一个调用 auth 失败而其它窄问题仍完成的常见情形。
如何核实：在实现工作树用真实 `runCheck` 端口替身让第一个 ask 返回 `{failure:"fatal", kind:"auth", usage:USAGE}`，其余调用正常返回同样 usage；运行结果为 `usage.input: 10`，但同批共发起 3 个调用、实际 usage 应为 `30`。已运行的最小实验输出：`{"ok":false,"code":"plot-check-failed","kind":"auth","usage":{"input":10,"output":2,...}}`。
建议改法：失败只记录 `failedKind`，等待 `Promise.all` 收口后用最终 `total` 构造返回值；或在返回前把 `failed` 的 usage 更新为最终合计。保留取消时在途调用的实际 usage，测试 fatal/length 与并发收口两种场景。
### 7. 已被替代的揭示计划仍触发试读

### 9. 晚出场伏笔的答案进入本章候选，却不进入依赖摘要
严重程度：重要；类别：正确性；位置：packages/neuro-book/src/plugins/plot/core/brief/context.ts:128-139；packages/neuro-book/src/plugins/plot/core/checks/dependencies.ts:139-144、181-194。
现象：`pointsReferencedBy` 遇到计划讲述上的 node 时，直接读取伏笔条目的 fs.答案，不检查该条目是否 appeared。dependencies 按条目 appears 分桶，认为晚于本章的条目不会被计划读取而排除。修改这个晚出场伏笔的答案后，旧记录携带的 points/concerns 没变、世界前缀没变，快速路径依然有效；实际重新圈候选已换了知识点。
为什么是问题：checks 输出 7 允许摘要优化的前提是与重拼完全一致。这个反例直接使已过期的检查结果继续进入待处理，且重新启动后相同摘要仍跳过重拼。

建议改法：统一计划路径上条目的出场过滤；如果有意允许晚出场伏笔提供答案，则按实际引用将它加入前缀依赖，不能继续假设只有已出场条目被读。把此反例补进 dependencies.test.ts 的“摘要相同则重拼结果相同”场景。

### 11. 取消监听在判一致之前被移除，取消不能中止判一致模型调用

### 12. 存储发生 revision 冲突后无法靠重试恢复
严重程度：重要；类别：不变量；位置：packages/neuro-book/src/plugins/plot/backend/store.ts:111-118、150-164、240-246。
现象：清单保存冲突后仍永久保留旧 #listRevision；章记录保存冲突后虽删 #slots，下一次 #slot 只 open、不 read，又把 revision 设为 null。已有清单/章记录永远不再满足 expect。一次其它实例写入后，清单冲突使这个实例不能新增任何章；已有章冲突使该章永远不能更新，直到插件重启。
为什么是问题：storage.persistence 明确允许两个打开同一库的进程做条件写入，冲突恢复要求重读。PlotStore 的注释也承诺“下一次写之前重读 revision”，实际没有读；checks 的失败恢复让调用方重跑，重跑会反复花模型费用后再次存储失败。
如何核实：固定源码、两个真实 PartitionOwner/StorageFacade/PlotStore 打开同一 SQLite，`bun /tmp/review-w00039-t34-I6/scratch-omp/store-conflicts.ts`。清单场景：A 写 ch1 成功，B 写 ch2、重试 ch2、改写 ch3 均为 `conflict: 期望 null，当前 1`。章记录场景：两份 store 都已 load ch1，A 更新成功，B 三次更新分别是 `期望 2，当前 3`、`期望 null，当前 3`、`期望 null，当前 3`。未伪造 storage 返回码。
建议改法：缓存失效后的打开必须 read 当前状态/revision；清单冲突时重读并合并已存章集合，再让调用方明确重试。保护 corrupt/unsupported-version 的 reset 语义，不以无条件覆盖解决冲突。补一条双实例冲突后重试成功的真实存储测试。

### 13. 有效性缓存只按章和依赖命中，新记录沿用旧记录的过期结论

建议改法：memo 同时绑定记录身份或记录内容摘要，不仅绑定 chapter/dependencies；新检查替换记录时失效这条 memo。回写摘要不能作为记录身份，因为它本身可变且被排除在内容外。补新检查进行中读旧记录的行为测试。

### 16. 被取消的检查仍须等待其它检查释放并发槽位
严重程度：重要；类别：不变量；位置：packages/neuro-book/src/plugins/plot/core/checks/run.ts:35-46、111-114、160-165。
现象：项目共用 limiter 的 waiting 只存 resolve，不接 AbortSignal。检查在槽位里尚未开始、用量为零时取消，batch 虽然 aborted，排队的 limiter.run 仍不结算；runCheck 的 Promise.all 要等其它章的在途调用结束才返回。卡住的其它章最多占满 4 个槽位，取消一个尚未开始的章也不能立即结束 busy。
