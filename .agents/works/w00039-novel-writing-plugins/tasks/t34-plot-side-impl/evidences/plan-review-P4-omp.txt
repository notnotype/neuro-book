### 1. 合法大周期历法在校验时抛 RangeError
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:340`；`packages/nb-time/src/calendar.ts:239`
**现象**：输出 13 允许“闰年周期 × 月数”不超过 2,000,000。C1 的 `compileCalendar` 用 `Math.max(...yearDays)` 求最长年；合法周期达 1,000,000 年、只有 1 个月时，`validateCalendar` 在该展开调用处抛 `RangeError: Maximum call stack size exceeded`，而不是返回合法历法。
**为什么是问题**：规格内的合法自定义历法无法通过校验；设置读取/编辑调用方会收到未声明的异常，违反历法校验作为纯结果返回的合同。
**如何核实**：在 `packages/nb-time` 运行 `bun -e 'import {validateCalendar} from "./src/index.ts"; const c={version:1,unit:"day",hoursPerDay:24,minutesPerHour:60,months:[{id:"m",name:"M",days:1}],leap:[{every:1000000,months:{m:2}}],eras:[],periods:[]}; console.log(validateCalendar(c))'`；实际输出为 `RangeError: Maximum call stack size exceeded`。该历法的周期乘月数为 1,000,000，符合上限。
**建议改法**：用循环归约 `yearDays` 求最大值，不把整周期展开为函数参数；增加周期接近 2,000,000、仍合法的校验用例。

### 2. 冲突环提取会漏掉重叠环并静默漏报第 21 个环
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:343`；`docs/specs/canon/time.md:70`
**现象**：计划要求取出一环后删除环上全部说法再求，且每个分量最多取 20 环。两个不同负环若共享一条说法，删除该说法会同时抹掉另一个环；一个分量有 21 个互不相同的可报告负环时，第 21 个及之后只留在内部 `truncated`，没有对应 `time-conflict`。
**为什么是问题**：输出 2 要同一环合并为一项，但不同环各成一条。当前算法既不能保证区分共享说法的不同环，也把明确要求的每环报告改成无提示的上限截断；作者看不到所有冲突依据。
**如何核实**：构造两个负环共用一条说法，再构造 21 个互不相同的矛盾环并用零间隔约束连成同一分量；按计划算法删除首环说法或达到 20 次后，后续环不会进入 `items`。
**建议改法**：在 Spec 明确“每个环”的边界与超过上限的用户可见语义；按规范化环身份去重，不删除会抹掉其他环的共享说法。若为性能必须截断，待处理结果须明确不完整并给未报数量，不能当作完整的每环报告。

### 3. 被允许的 `approx` 与间隔可越过安全整数范围
**严重程度**：阻断；**类别**：正确性
**位置**：计划 `plan.md:340-342`；`packages/nb-time/src/calendar.ts:299-347`、`packages/nb-time/src/fuzzy.ts:101-113`
**现象**：历法上限只约束一年 tick 数乘 10,000,001；词表 `approx` 与间隔 `min/max` 可是任意非负安全性未限制的整数。C1 当前实现对公历年份 0 使用 `approx.year = Number.MAX_SAFE_INTEGER`，得到约 ±4.737×10^21 的不安全 tick；使用同等大小的年间隔也得到不安全 tick。
**为什么是问题**：网络距离与差分边权进入 JS `number` 后已不再精确，松弛比较、负环检测和“紧边”相等判断会把可行网判错或给出不稳定范围，违反输出 10 的确定性与精确整数约束。历法年长上限本身不能约束说法放宽量。
**如何核实**：在 `packages/nb-time` 执行 `bun -e 'import {compileCalendar,dateRange,GREGORIAN,resolveFuzzy,gapRange} from "./src/index.ts"; const c=compileCalendar(GREGORIAN); const r=dateRange(c,{year:0},{year:Number.MAX_SAFE_INTEGER,month:1,day:1,hour:1}); const f=resolveFuzzy({words:{huge:{min:Number.MAX_SAFE_INTEGER,unit:"year"}}},GREGORIAN); const g=gapRange(c,f.table,{word:"huge"}); console.log(Number.isSafeInteger(r.lo),Number.isSafeInteger(r.hi),g)'`；实际两个边界均非安全整数，间隔下界约 `4.737e21`。
**建议改法**：对所有进入网络的 tick 运算设置并验证统一的安全范围（包含 `approx`、间隔、年龄上界及日期放宽后的端点），越界按确定的 `time-invalid` 或写入拒绝合同处理；测试边界值与加减溢出，不只校验日历年长。

### 4. 带令牌的计划模式把上限后的兑现进展带入网络
**严重程度**：阻断；**类别**：正确性
**位置**：计划 `plan.md:358`；`docs/specs/canon/model.md:182-188`、`docs/specs/canon/project.md:118`、`packages/nb-canon/src/engine/incremental.ts:192-224`
**现象**：令牌方案按上限过滤网络事件，却未规定用该上限计算计划进展。引擎的 `progress(plan, position)` 会检查该位置之前是否有已写兑现；当前默认计划事件集按全书末尾进展筛出未兑现计划。若某计划在令牌上限之后被兑现，缺省位置会把计划排除，虽其计划安放在上限之前、兑现记录不可见。
**为什么是问题**：持有者读上限前的计划模式视图时看不到任何可见的兑现变更，却会因上限后的事件改变而失去该计划及其时间范围；同一上限的视图输出不再是只由上限前输入决定，违反令牌过滤“只用上限之前的事建网”及单一冻结视图合同，并泄漏未来写入是否兑现计划。
**如何核实**：用实际引擎构造：上限前安放一个带时间说法的 active 计划；上限后安放一条 `fulfills` 它的 active 已写变更。比较在兑现发布前后、同一上限与计划模式下的可见计划时间查询。当前全书进展筛选在兑现后会从计划集合删掉它。
**建议改法**：令牌视图在裁剪后的事件集上计算 `progress` 与 `splitFrom` 组进展；缓存键必须包含裁剪进展所需输入，不能只用模式与上限。增加真实 WorldService 令牌回归用例，兑现记录在上限后时前后结果相同。

### 5. 时间网络缓存身份漏掉计划进展所依赖的引擎
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:354`；`packages/nb-canon/src/engine/incremental.ts:192-214`、`packages/nb-canon/src/world/world.ts:186-198`
**现象**：计划把网络放在 `WorldData` 对象缓存，并只额外计入设置与模式；同一 `WorldData` 下 `withOptions` 可以重建引擎。实际模式不依赖引擎，但计划模式事件集明确依赖 `engine.progress(plan, defaultPosition)`。引擎重建可改变已写兑现变更是否 `applied`，从而改变计划是否未兑现，而数据身份不变。
**为什么是问题**：组件登记变化会使 `withOptions` 重算引擎的计划进展，但按 `WorldData` 命中的计划网络仍含旧计划集合；读取输入摘要已变，网络输出却沿用旧快照，违反读取结果等于新输入从头计算的合同。世界线 Spec 也要求登记或发布变化后的计划进展与待处理等结果等于重建结果。
**如何核实**：构造同一 `WorldData`，一条已写兑现的计划因旧 Component 登记下套上，后通过登记变更使它套不上；调用 `withOptions` 后比较计划模式缓存网与按新引擎 `progress` 重新组网的事件集。计划缓存键没有引擎身份或计划集摘要。
**建议改法**：计划模式缓存键包含引擎身份或规范化的未兑现计划 id 列表摘要；实际模式继续只按数据、章序、历法与词表缓存。对已建缓存后调用 `setRegistries` 的计划进展变化加行为测试。

### 6. 输出 5 的 (b) 把相对坐标差当作绝对时间顺序
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:344`；`docs/specs/canon/time.md:73`
**现象**：判据 (b) 按 `after` / `before` 的相对说法直接报告安放反序，没有要求两事件属于同一坐标系或都锚定元年。无锚分量的范围仅是相对各自 `relativeTo` 的偏移；跨两个无锚分量，甚至无锚事件与有锚事件之间，数值零点不可比较。Spec 明确只在同一坐标系内比较无锚分量。
**为什么是问题**：例如 A、B 各自只有相对坐标，B 的说法写“在 A 之后三天”，但 A 的故事时间不锚定元年、B 的安放又早于 A。两件事没有绝对范围，单条说法只定义相对次序，不提供“故事时间”对安放是否颠倒的依据；(b) 仍会报 `time-placement-mismatch`。此外若事件关系跨越有锚和无锚分量，也不能比较。
**如何核实**：对照计划 (b) 与 time 输出 5 末句“没有锚的分量各自比”；构造两个各自无锚的事件，仅以 `after` 约束相连、安放顺序与 `after` 方向相反。该例即便合成同一网络分量，仍只有相对坐标、没有可供输出 5 比较的安放时间锚。
**建议改法**：仅当直接关系两端共享一个可比较坐标系且相对约束能推出起点严格先后时才应用 (b)；否则不报。为不同无锚分量各自按 `relativeTo` 分桶，不能把约束跨分量的原始势值拿来比较；补充“仅相对关系”反例测试。

### 7. 设置只补打开期间的变化，没有规定打开后的设置订阅
**严重程度**：重要；**类别**：不变量
**位置**：计划 `plan.md:355,362`；`packages/neuro-book/src/plugins/canon/backend/world-host.ts:233-247`
**现象**：计划规定打开时用 `settingsKey` 的当前值初始化、打开期间的变化在完成后比对补交，但没有规定在 `settings.onDidChange` 中把后续有效值变化送进 `WorldHost.setTime`，也没有规定监听释放。`world-host.ts` 现有登记监听只覆盖 Components、marks、diagnostics。
**为什么是问题**：作品打开后修改项目历法或词表，不会触发 `setTime`，`WorldOptions.time`、读取输入代次、时间诊断与查询缓存继续使用旧值；正是 Spec 输出 4 的重算行为失效。只做打开期比对只能修复竞态，不是持续同步。
**如何核实**：对照计划 C7 的设置入口条目与 `world-host.ts` 的现有监听：当前协议没有任何设置变化回调；按“打开→修改已声明设置→再次 time 查询”推演，除非另行增加订阅，否则世界服务没有收到通知。
**建议改法**：明确注册 `SettingsService.onDidChange`，只处理两个配置键，把有效值经宿主的串行写入队列调用 `setTime`；设置监听的取消函数并入项目入口/宿主停止收口。保留打开期间的初值与补交逻辑，补真实项目子进程的打开后修改测试。

### 8. 带令牌的分页没有定义裁剪网络的读取戳
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:358`；`docs/specs/canon/project.md:113,118`
**现象**：计划只规定同一上限的令牌共用裁剪网络缓存，没有定义带令牌 `time` 的分页游标使用哪个读取输入摘要。项目服务的游标按完整 `inputDigest` 生成；其中包含全世界版本与全书历法/词表摘要。令牌时间结果却承诺只由上限之前的事件计算。
**为什么是问题**：上限之后发布不相关修订会令全局游标立即 `cursor-stale`，虽然该令牌可见的事件、裁剪网络及分页结果完全没变；如果改用裁剪输入却不把位置/模式/令牌过滤条件纳入游标参数摘要，又可把旧页续到另一裁剪结果。计划没有给出能同时满足两种语义的戳与参数键。
**如何核实**：对照 `pageOf`/`ReadStamp.inputDigest` 合同（project 输出 19）与计划视图裁剪后的事件集；构造同一 token 上限之后新增一件无关事件，再用旧 cursor 翻第二页：当前全局戳会因世界版本变化而过期。
**建议改法**：明确时间分页的戳口径。若严格复用 project 输出 19 的完整输入摘要，应接受并写明未来修订导致游标过期；若要求视图结果稳定，则定义视图裁剪后的摘要，覆盖裁剪事件、模式、上限、设置与 query，并把其作为 `pageOf` 的显式输入，而不是沿用全局戳。加入真实服务分页跨上限后修订的判据。

### 9. 相等时段在含分钟历法中并非整整一天
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:340`；`packages/nb-time/src/calendar.ts:335-340`
**现象**：计划把 `period.to === period.from` 定义为整整一天，但 C1 以闭区间 tick 转换时段为 `[from, to)`；对同一时刻，通用跨夜分支算出 `to * ticksPerHour - 1`，没有按全天补上完整一天。现有代码用 `period.to > period.from ? ... : ...`，同样把相等当跨日端点。
**为什么是问题**：如 24 小时/60 分钟历法中时段 `{from: 5, to: 5}` 应是 24 小时，当前 `dateRange` 却返回 5:00 到次日 4:59，共 24 小时? 实际为 `hi=(day+1)*tpd+5*tph-1`，范围从第 1 天 05:00 到第 2 天 04:59，是 24 小时；问题在“整整一天”应从给定日期的 00:00 开始，当前实现偏移了 5 小时：遗漏首日 00:00-04:59 并纳入次日 00:00-04:59。对任意非午夜起点均不是该日期的整天，语义与计划不符。
**如何核实**：在 `packages/nb-time` 执行 `bun -e 'import {compileCalendar,dateRange} from "./src/index.ts"; const c=compileCalendar({version:1,unit:"hour",hoursPerDay:24,minutesPerHour:60,months:[{id:"m",name:"M",days:30}],leap:[],eras:[],periods:[{id:"p",name:"P",from:5,to:5}]}); console.log(dateRange(c,{year:0,month:"m",day:1,period:"p"}))'`；结果为 tick `[5,28]`（小时单位），而该日期整天应为 `[0,23]`。
**建议改法**：对 `from === to` 明确返回日期起点至下一日开始前一 tick；测试 0 点、非零时刻与 `approx` 扩展。注意当前 C1 只测跨夜及 `from < to`，没有相等端点场景。

### 10. `time-placement-mismatch` 键只用 B 会把多种违规对压成一条
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:344,356`；`docs/specs/canon/time.md:73,89`
**现象**：每个较晚安放的 B 只有一项，并用 B.id 作待处理键；同一 B 可能与前缀中多个 A 成对，但计划只留“最早时间最大的代表 A”和数量。若修改或删除代表 A，而另一些 A 仍然违规，项键不变且代表/范围改变；`revisions` 输出 6 的差集会把变化当作没有变化，带来的变化不记录更新后的依据。Spec 输出 5 要显示代表项，而输出 14 指定 mismatch 键只用 B，计划需说明这一不可避免的更新盲区或稳定代表规则。
**为什么是问题**：修订 impact 以 pending 键作差集，修订不可变；相同 B 键不能表达一项内部 representative、count、criterion 的变化。回执会漏掉由本次修改引起的代表依据与数量变化，之后作者看到的当前项与修订回执不一致。
**如何核实**：构造一个 B 与两个较早安放的 A1、A2 都满足 (a)，A1 是最早时间最大的代表；改 A1 的范围使它不再成对但 A2 仍满足。按计划键前后都是 B.id，所以 pendingAdded/Resolved 均为空，但展示代表从 A1 变成 A2、count 变化。
**建议改法**：明确待处理项本体可变而稳定键不变时，修订 impact 应比较同键项内容并记录更新，或将“代表、count、criterion”纳入稳定身份并修订 Spec 输出 14 的键合同。不要仅凭项键相同认定无变化。

### 11. 按规范 JSON 给 `time-invalid` 定键无法区分同一变更的重复说法
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:356`；`docs/specs/canon/time.md:89`
**现象**：计划说同一变更内的说法键按规范 JSON、不按下标；当同一条非法说法在 `when` 中出现两次时，两项键完全相同。Spec 输出 3 要每条不成立说法各成一条待处理，输出 14 的键也没有定义重复项如何保持唯一。
**为什么是问题**：实现若按键去重，两条作者输入只呈现一条，违反每条单独列出；若保留两个完全相同键，分页排序与增删差集无法稳定区分，移除其中一个时 impact 会误认为两项都还在或都消失。计划没有可实现且满足两个合同的身份。
**如何核实**：给同一事件的 `when` 两个完全相同且在当前历法无效的日期说法，逐条按计划键（变更 id、规范 JSON、原因）序列化，结果完全同串。
**建议改法**：在持久形状没有说法 id 的前提下，使用规范内容加同内容出现序号（按序号只区分完全重复项；插入不同说法不扰动它们），写入待确认清单与输出 14，并测试前插不同项、删去一个重复项后的键差集。

### 9. 相等时段在含分钟历法中并非整整一天（撤回）
**撤回理由**：计划中的“整整一天”是从时段的 `from` 时刻到次日同一时刻，长度 24 小时，并非该日期的 00:00 到 24:00。C1 返回 `[5,28]` tick，在每小时一个 tick 的例子中恰是 05:00 至次日 04:59，符合这一定义；原报告把“一整天”误当成日历日边界。此项不计入有效发现。

### 6. 输出 5 的 (b) 把相对坐标差当作绝对时间顺序（撤回）
**撤回理由**：判据 (b) 直接使用事件间 `after`/`before` 说法，而不是比较两个分量的势或绝对 tick。若 B 明确在 A 起点之后且安放顺序相反，这条说法本身已经证明 B 的时间在 A 之后；即使整个分量没有锚，结论仍对平移不变。原报告把“不能比较两个未锚定分量的绝对坐标”误套到两端被同一直接约束连接的情形。该项不计入有效发现。

### 8. 带令牌的分页没有定义裁剪网络的读取戳（撤回）
**撤回理由**：project 输出 19 明确规定任何读取输入变化都使旧游标 `cursor-stale`；世界版本是完整读取输入的一部分。上限后的修订即便不改变视图裁剪后的时间结果，也必然改变该输入摘要，因此旧游标失效是既有合同要求，不是缺陷。计划无需另造视图摘要；此项不计入有效发现。

### 12. 被引用变更所在章删除时事件集定义互相矛盾
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:343`；`docs/specs/canon/model.md:156`；`docs/specs/canon/time.md:17,92`
**现象**：计划把“所在章已删”的目标列为 `of` 不在事件集、说法静默不进网络；但其事件集定义是所有生效、非叙述的已写变更，未按 `placementRank` 是否为 null 过滤。C5/C6 又把时间引用加入引用系统，删除章序不会删除剧情变更对象或清空它的 `at`。现有时间网络构造将所有此类变更加入事件，只把其安放 rank 设为 null 并排最后。
**为什么是问题**：同一条说法对于位于已删章的被引用目标究竟静默略过还是连到“未排章、排在最后”的事件，计划给了相反行为。会改变分量、冲突、范围与 (b) 失配，并影响 pending 截取与发布 impact；章序变化本身会持久化 `reorder` 修订，不能靠含糊的“所在章已删”分支。
**如何核实**：读取计划 C3 的事件集与目标解析列表；对照 `model.md` 输出 3（删章记录继续保留、安放不套）及 `position.ts:39-44`（章不在章序返回 null），再看 `network.ts:71-80` 将所有 active written 变更加入并把 null rank 排到末尾。
**建议改法**：明确时间事件是否排除“安放在当前章序外”的生效记录。若排除，事件集必须同时按安放可见性过滤，并定义该事件自身的说法如何报；若仍作为事件，则删去 target resolver 中“所在章已删”分支，并把未排章排序与截取规则写明。将章删除/重排后的自引用与外部引用分别加入 C3/C6 测试。

### 13. 计划模式首次查询预算没有覆盖全部计划位置集合
**严重程度**：建议；**类别**：安全与性能
**位置**：计划 `plan.md:381`；`docs/specs/canon/project.md:106`；`scripts/perf/canon-scale.ts:198-207`
**现象**：当前规模脚本按计划模式只抽 5 个随机位置建缓存，再在这 5 个位置上测 50 次；Spec 的 1 秒预算是计划模式第一次读取，计划中的时间方案另会为每个不同计划事件集/读取位置建网络。计划 C7 只说分开量一次首次查询和热查询，没有规定覆盖最坏计划事件集或多位置冷建；同一章节计划大量且读取位置不同会有不同网络。
**为什么是问题**：只测一个选定位置的一次冷查询不能证明任意首读在预算内；把其他位置的网络预热后测同一批位置，测量口径偏向缓存热路径。若某位置包含大量计划形成的大连通分量，冷建时间可能比抽样位置高很多。
**如何核实**：查看现有 perf 脚本 `plannedPositions` 仅 5 个随机位置；对比 project 输出 14 的计划模式“第一次读取 1 秒以内”。C7 的模拟规模含每章 5 个计划，事件集随位置变化。
**建议改法**：固定生成位置集合，包含最新章末尾、最后一章有已写变更时其计划计入边界、以及所有计划链集中在单一位置的最大计划集；每个新事件集独立计冷建并报告最大值，之后同输入另测热查询。避免用已预热的网络作为首次查询预算证据。

### 14. 发布 100 毫秒兜底把不可行的复用优化留到测量后
**严重程度**：建议；**类别**：安全与性能
**位置**：计划 `plan.md:354,381,397`
**现象**：计划承诺发布时对新数据建网、首次查询复用；风险段却把超预算后的动作写成“再复用旧数据的降约束与只重算被碰到的分量”。降约束已经按内容缓存；一个新增事件通过相对约束连接到既有分量后，受影响分量的范围、冲突和 mismatch 都会变，不能安全复用旧组件求解结果。发布/记账连续进行时每次产生新的 `WorldData` 身份，按数据弱缓存的旧网络自然不复用。
**为什么是问题**：若首次实现超过 project 输出 14 的 100 毫秒发布预算，计划里给的兜底需要新的增量求解器、失效拓扑与边界证明，不是“只做被碰到分量”的小改；计划又要求遇超预算再找开发者，意味着关键预算失败时无法在已定范围内闭环。
**如何核实**：现有 `canon-scale.ts` 连续 10 次最新章发布，不在每次之间读取时间；计划 C7 将另加时间说法并将建网纳入发布预算。用新增 `after` 把新事件连到旧大分量的最坏形状，旧分量解不能复用，且新 `WorldData` 必须另建时间网络。
**建议改法**：在 C3/C7 的实现前置验收明确发布路径要在实际测量中通过；移除“只重算被碰到分量”作为现成兜底。若超预算，先根据实测决定缩小算法工作或向开发者提交改变预算/延后增量求解的决策，不把未设计的增量维护写成可直接执行的后备方案。

### 15. 判据 (b) 的违例没有进入代表项与件数聚合
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:344`
**现象**：计划先定义两类违例：范围判据 (a) 与单条说法判据 (b)，随后规定用前缀最早范围最大值给代表、按最早时间树状数组计数。这一聚合只能识别 (a) 的配对；(b) 可在两范围重叠时单独成立，既不保证前缀最大 lb 高于 B 的 ub，也不会进入范围树状数组。计划未说明如何将 (b) 的独立边并入每个 B 的代表选择与去重计数。
**为什么是问题**：Spec 要求每个 B 报告代表性 A 与满足条件的 A 总数。仅按 (a) 聚合会漏掉只有 (b) 成立的 A；直接另加一条而不与 (a) 合并，又会重复计算同时满足两判据的同一对。以双方都被日期限制在六月、B 又明确在 A 起点之后三天、安放却把 B 放前的输入，(a) 不成立而 (b) 成立，正是遗漏用例。
**如何核实**：用计划给出的日期范围判据与 `after` 说法构造两事件：A、B 的时间范围重叠，额外约束 `B.s - A.s ∈ [3天,+∞)`；安排 A 在 B 之前。前缀范围判据不成立，直接说法成立，但范围前缀结构无法产出此 partner/count。
**建议改法**：把每个 B 的候选 partner 集合定义为 (a) 的范围违例并集 (b) 的直接边违例，按 partner id 去重；证明代表选择覆盖并集中的最大 `lb(A)`，计数对并集去重。若保留 O(N log N)，说明如何用范围树状数组与直接边候选合并，并加“重叠范围且仅 (b) 成立”及双判据同一 pair 的测试。

### 16. 待处理截取要求“所有所涉事件已发生”与输出 2 的环报告不相容
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:356`；`docs/specs/canon/time.md:70,89`
**现象**：计划对三类时间项统一要求“所涉事件都安放在读取位置之前”。冲突项本身所涉的事件是环上各说法所在的变更；输出 2 规定环上说法各成冲突项，但不要求这些变更已安放在读取位置之前。若环中任一变更安放在未来位置或未排章，当前规则会把整条环冲突隐藏，即使其余环上变更已在读取范围内。更根本地，输出 2 的冲突是约束系统上的全线属性；Spec 输出 14 另规定按位置截取，却没有在“所涉事件”上排除冲突环说法的来源变更。
**为什么是问题**：冲突项没有唯一“发生事件”可当过滤锚点；按全部来源事件截取会使同一冲突在各位置消失/出现，按某一代表事件截取又未在计划或 Spec 中定义。作者在已读位置可能看不到已参与前史约束的冲突，或无法解释为什么稍后才安放的一件事使旧位置的冲突变化。
**如何核实**：构造负环涉及 A、B、C，其中 A、B 安放在前史、C 安放在第 5 章；读取第 3 章末尾时按计划的 `every(change rank < position)` 过滤会删掉整项，而冲突环由全线约束计算得出。对照输出 2、14。
**建议改法**：为冲突项单独定义截取锚点与时间语义（例如不随位置截取、按环中最晚安放过滤，或按每条说法分别呈现）；不能把三种 pending 共用“所有事件均在前”的未经 Spec 定义规则。将前史与未来章混合的环列入 C6 测试并同步写入 time.md。

### 13. 计划模式首次查询预算没有覆盖全部计划位置集合（撤回）
**撤回理由**：计划时间网络接口是 `timeNetwork(data, time, mode)`，按全书末尾进展构造一个 planned 事件集；不接收读取位置，缓存身份也只有模式与视图上限。因此 5 个随机位置不会建立 5 份不同的计划时间网络，先后查询会共用同一张 planned 网络。把现有 canon 引擎的按位置计划快照成本套用到时间网络上，属于误判。此项不计入有效发现。

### 17. 合法的两百万周期月上限允许单次日期查询线性扫描 50 万个月
**严重程度**：建议；**类别**：安全与性能
**位置**：计划 `plan.md:340`；`packages/nb-time/src/calendar.ts:211,242,321-323`
**现象**：周期上限只限制 `cycle × 月数 ≤ 2,000,000`，但 `dateRange` 每次用 `ids.indexOf(id)` 查月、`monthStart` 再对该年月前缀做 `slice(...).reduce(...)`。合法历法可有 500,000 个月、无闰年规则；单次日期查询因此线性扫描月表，不是计划所述的周期前缀和常数时间。
**为什么是问题**：C1 公开 `compileCalendar` 已构造 month id 映射，但实现的 `dateRange` 没用它；输出 11 规定时间查询热路径 20 毫秒，限制允许的自定义历法规模下会把一次说法降约束变成 O(月数)，规模测试只覆盖 12 月公历与王历，不会触发此退化。
**如何核实**：在 `packages/nb-time` 执行 `bun -e 'import {compileCalendar,dateRange} from "./src/index.ts"; const months=Array.from({length:500000},(_,i)=>({id:`m${i}`,name:`M${i}`,days:30})); const calendar={version:1,unit:"day",hoursPerDay:24,minutesPerHour:60,months,leap:[],eras:[],periods:[]}; const c=compileCalendar(calendar); const t=performance.now(); dateRange(c,{year:1,month:"m499999",day:30}); console.log(performance.now()-t)'`；本次实测编译约 340 ms，单次日期查询约 11 ms。重复降约束或批量说法会按查询次数重复该扫描。
**建议改法**：编译时为月 id 建 Map，并为月长周期预计算每年内前缀和，使 `monthStart` O(1)；或把 Spec 的周期×月数上限收紧到能满足热查询预算的实测边界。增加大月数下多次日期转换的基准，不只测一次冷查询。

### 16. 待处理截取要求“所有所涉事件已发生”与输出 2 的环报告不相容（撤回）
**撤回理由**：输出 14 明确要求时间待处理随读取位置截取，并规定“所涉的事都安放在读取位置之前才列出”。冲突项所涉对象就是环上各说法所在的变更，故环含未来安放时不列该项，正是既定截取合同；输出 2 定义整条线上的冲突计算，并不要求每个读取位置都展示整条线的所有冲突。原报告把“先算全线网络”误解成“不能按位置筛冲突项”。此项不计入有效发现。

### 17. 合法的两百万周期月上限允许单次日期查询线性扫描 50 万个月（严重程度调整：建议 → 重要）
**严重程度**：重要；**类别**：安全与性能
**严重程度依据**：每次说法降约束都需执行一次 `dateRange`；在合法 500,000 月历法上单次测得 11 ms，C7 的规模输入最多约 2,250 条日期说法时，仅日期转换就可超过 24 秒，超过首次查询 1 秒预算。超时不是罕见大图路径，而是历法输入上限允许的确定性热路径成本。

### 18. 最近合法历法文件缺少原子写入与多进程协调合同
**严重程度**：重要；**类别**：不变量
**位置**：计划 `plan.md:355,381`；`docs/specs/canon/time.md:91,101`；`docs/specs/canon/project.md:98`
**现象**：计划把最近合法历法保存在 `.nbook/world/calendar.json`，但没有定义临时文件原子替换、文件损坏恢复或跨进程写入锁。该文件是恢复自定义作品历法的唯一持久副本，而项目 Spec 允许两个 NeuroBook 进程打开同一作品。
**为什么是问题**：进程在原位写入时崩溃会留下截断 JSON；重开时无法取得最近合法历法，若按“没有可用记录”处理就落回公历、使说法大面积失效。两个旧实例在设置通知/启动竞态下也可能先后写入不同有效历法，最后写入者覆盖新状态；结果取决于进程调度，不符合输出 16 的跨进程一致性。
**如何核实**：对照计划只定义文件路径与宿主所有权，未列原子替换/锁；对照 project 输出 8 的跨进程打开与设置 Spec 输出 13 的同文件锁写模式。对持久文件按“写到一半进程退出”和“两实例先后更新历法”推演即可复现风险。
**建议改法**：用同目录临时文件加原子 rename 保存，附带格式/摘要并在损坏时保留旧文件；对跨进程读写用项目锁串行，或以设置层修订戳拒绝陈旧写。C7 增加中断写入后重开、两个实例更新顺序交错的验证场景。
