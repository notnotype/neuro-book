### 1. 修订 refs 字段没有进入当前 Spec
**严重程度**：重要；**类别**：文档
**位置**：计划 `plan.md:43,67-69,168-174`；`docs/specs/canon/revisions.md:54-58,100,102`
**现象**：计划要求把本次新写或改过的引用位置写入持久修订 `refs`，并让依赖与按条目筛选只读该字段；但本 worktree 的修订持久形状没有 `refs`，输出 12、14 也没有定义其形状、覆盖范围或旧修订如何处理。计划称 P1 已把“修订存 refs”写进 Spec，当前指定依据并未包含这项改动。
**为什么是问题**：`refs` 成为世界日志的持久合同，缺少规范会让实现无法从合同判断存对象级全量引用还是本次改动的引用、覆盖引用前后值的规则，以及没有 `refs` 的既有格式 2 修订如何参与依赖与过滤。后两者会直接改变撤销是否被拒和修订列表结果。
**如何核实**：读取 `docs/specs/canon/revisions.md` 输入与前置条件的“存下来的修订”及输出 12、14；全文没有 `refs` 字段定义。计划 `plan.md` 关键设计已依赖该字段。
**建议改法**：先把 `refs` 的持久形状、按修订收集的精确语义、旧日志缺字段时的行为写入并审查 `revisions.md`；再按该合同实现，别只在计划里引用未落到本 worktree 的 Spec 改动。
### 2. 游标摘要没有绑定查询参数
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:55-59,129-134,191`；`docs/specs/canon/project.md:112`
**现象**：计划把游标定义为“摘要加偏移”，摘要是读取输入摘要；但 Spec 输出 19 明确要求游标同时记所属读取输入摘要与读取参数。当前服务游标仅是 `version:offset`，每个列表各自重新应用调用时的筛选参数。
**为什么是问题**：同一读取输入下，把 `changes` 的 `entry=A` 查询游标接到 `entry=B` 查询，摘要仍相同、偏移却继续从 B 的中间开始，导致漏项；不同 `tellings` 筛选、位置范围或 `pending` 位置/模式/分组也会混页。版本摘要只能发现状态变化，不能发现调用方换了查询。
**如何核实**：`project.md` 输出 19 原文要求“游标记着它所属的读取输入的摘要与它的读取参数”；当前 `service.ts:570-578` 的游标只编码版本与偏移，`changes()` 在每次调用时独立套用 `filter`。
**建议改法**：游标绑定规范化后的方法标识与所有影响结果的参数（含筛选、位置、模式、组及分页语义），并绑定读取输入摘要；参数不匹配时拒绝续读或返回明确的过期码。补一条跨筛选复用游标的合同测试。
### 3. refs 的抽取没有限定到本次修订改动
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:63-68`
**现象**：计划说引用扫描输入为写入后的整份对象，并把“本次新写或改过的引用”存入修订 `refs`，但没有说明如何从整对象筛出本次 op 改动的引用，也没有定义删除引用时保存 before 还是 after。现有修订只存变化叶子（`revisions.md` 输入 58、59）。
**为什么是问题**：若扫描 after 对象的全部引用，一次只改普通字段的修订会把对象上未改的引用也记成该修订的依赖，造成撤销无关地报 `has-dependents`，按条目筛改动记录也多出结果；若只扫 after，则删除引用的那次修订会漏掉被删除引用的位置，无法按条目筛到它。引用登记与增量 diff 的边界必须有合同。
**如何核实**：计划 `plan.md:67` 指定整份对象作为输入、`plan.md:68` 要把新写或改过的引用存入修订；`world.ts:289-296` 先对对象算叶子 diff，现有依赖在 `world.ts:458-497` 按这些修订操作判断。对象同时有引用字段和普通字段，只改普通字段即可复现“全对象扫描”产生的伪依赖。
**建议改法**：按 create/delete/modify 的 op 计算引用变化：create 记 after 引用，delete 记 before 引用，modify 只比较发生变化的引用位置并保留前后目标；给 `refs` 明定路径、目标与去重规则，并用“只改无关字段不新增依赖”“移除引用仍能筛到修订”的合同用例锁定。
### 4. 临时 ID 替换方案违反文本原样保留合同
**严重程度**：阻断；**类别**：正确性
**位置**：计划 `plan.md:192`
**现象**：计划改称临时 ID 替换“不另列清单”，按“与本次发出的某个临时 id 完全相同的字符串”及地址路径 `[临时 id]` 段替换；它没有要求字符串处于引用位置。
**为什么是问题**：正文、引文、决策文字、Component 文本等可能恰好等于 `tmp:k`。若同一写入请求新建 `tmp:k` 对象，全局按值替换会把自由文字改成正式 id。`components` 输出 18 明确规定不在引用位置的 `tmp:` 文字原样存下；当前 `world.ts:544-594` 也只按声明的 ID 键替换，避免改动叙述文本。该方案会改变用户输入并造成数据损坏。
**如何核实**：对照 `docs/specs/canon/components.md` 输出 18 的临时 id 规则；读取当前 `world.ts:544-594` 的 `ID_KEYS`、`ID_LIST_KEYS` 与 `replaceTempIds`。样例请求同时新建 `tmp:k` 对象和含 `tmp:k` 的普通文本即可复现。
**建议改法**：保留明确的引用位置遍历，只在 Spec 声明的引用位置及明确列出的对象自有 id、新世界线 id、稳定键对象引用和地址路径段替换；禁止按任意字符串值全局替换。测试同一临时 id 同时出现在引用字段与普通文本中，两者只应替换引用字段。
### 5. A3b 列表语义档没有独立验收映射
**严重程度**：重要；**类别**：测试
**位置**：计划 `plan.md:192-195,212-213`
**现象**：切片把 components 输出 20 的列表子字段语义档从 A3 拆成 A3b，但验收映射仍把 components 输出 18 到 20 与场景 5 全部列在 A3 的 `references.test.ts`。A3b 没有独立映射或测试文件。
**为什么是问题**：按计划每片一个提交、每片都跑测试，A3 尚未实现语义档时，若映射测试照字面覆盖输出 20 就会失败；若将输出 20 用例延到 A3b，当前映射又没有指定该片的验收。后续无法证明 A3b 单独交付，也无法确认两引擎的元素子字段事件、归纳缓存与去元素语义都被差分测试覆盖。
**如何核实**：对照 `plan.md:193` 的 A3b 范围与 `plan.md:212` 把输出 18 到 20 全列在 A3；`components.md` 输出 20 明定元素子字段的起点、事件、缓存与去元素行为。
**建议改法**：把映射拆成 A3 的输出 18、19 与场景 5 引用行为、A3b 的输出 20 与具体场景；在 A3b 列明两引擎的可观察结果与 `differential.test.ts` 的随机序列需生成元素语义档事件、删除元素及重新读缓存。
### 6. 已回答问题样本没有决策迁移规则
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:42,186-190,208-211`
**现象**：A1 把 `question` 改名为 `decision` 并要求更新样本转换与回放，但没有说明旧状态 `answered` 与旧字段 `answer` 如何转换。星瑕样本的 `q7` 在第 1 章已是 `answered`，带答案；新决策的已定状态要求 `conclusion` 与作者来源 `source`，后续写入还要求 `authorizations`。
**为什么是问题**：机械改 kind/id 会留下新合同不接受的 `answered` 对象；直接映射成 `decided` 又缺合法作者来源，无法经新 `World.publish` 的授权校验；映射为 `pending` 会丢失“已确认答案”的语义并改变样本结果。现有回放转换器只重排旧形状，计划没有给迁移来源或明确的样本重基线。
**如何核实**：`tests/sample/xingxia-prototype.json:1300-1315` 是 `q7` 的 `answered` 更新，含 `answer`；`docs/specs/canon/model.md` 决策状态表要求 `decided` 有 `source`；`revisions.md` 输出 21 要求带授权；计划 A1 只写“样本转换与回放跟着改”。
**建议改法**：先定义旧已回答样本的目标语义和作者来源如何合法产生（测试端口可以验证新来源合同），再把转换及样本预期写清；不要将 `answered` 直接改成 `decided` 或静默降为 `pending`。
### 7. RFC 8785 摘要缺少浏览器可用实现
**严重程度**：重要；**类别**：架构与可测性
**位置**：计划 `plan.md:30-31,51-59,98-103,137-140,191`
**现象**：读取输入摘要要求浏览器端也计算并返回，但 `digest` 端口只存在于 `WorldOptions`/服务端（`world.ts:42-51`、`service.ts:27-35`），浏览器客户端只经 RPC，不持有项目正文快照或同步 SHA-256 实现。计划称浏览器宿主“同样注入同步实现”，没有指出浏览器端实际 owner/接口；同时 `canonicalJson` 负责规范序列化，`digest` 端口负责摘要，却把摘要与序列化当成一项通用解决方案。
**为什么是问题**：若每个浏览器调用方各自算摘要，同一输入可能因端口实现不同而产生不同游标/视图绑定；若读取结果只带服务端摘要，浏览器端无法验证/生成以本地读取输入为依据的授权绑定。现有同步 SHA-256 只在 Node 宿主的 `world-host.ts` 用 `node:crypto`；浏览器已有的 `crypto.subtle.digest` 是异步，端口所需的同步 API 并未由现有宿主机制提供。
**如何核实**：检索 `packages/neuro-book/src` 中 SHA-256 调用：canon 宿主使用 `node:crypto.createHash`，浏览器文档用 `crypto.subtle.digest`；`createCanonClient` 只经远程接收结果，`WorldOptions.digest` 由后端宿主注入。`project.md` 输出 19/`model.md` 输出 36 要求服务端结果带摘要与游标绑定读取输入。
**建议改法**：明确摘要由唯一 owner（项目服务端）计算并在远程结果/游标中携带、浏览器只透传，还是引入一个真实可同步供两端共用的实现；分清 canonical JSON 的拒绝输入与 SHA-256 的编码边界。不要让无输入来源的浏览器端口承担摘要职责。

### 8. 正文快照监听不会收到经文件服务的章节保存事件
**严重程度**：重要；**类别**：正确性
**位置**：计划 `plan.md:49-53,137-140,191,228-232`
**现象**：计划把 `textChanged(chapter)` 接在 canon 的 `world-host.ts` 目录监视上；当前宿主只对 `manuscripts.binder` 的目录调用 `fs.watch`，章节保存由文件服务通过同目录临时文件原子替换，且文件服务已有精确保存事件/变更源机制。计划没有把它接入正文快照，也没有为该路径指定验收。
**为什么是问题**：原子替换是对文件名的 rename 事件，不保证被监视目录本身收到回调；按文件名监视目录也无法依靠现有 binder 回调识别章节文件内容改变。打开时读一次的快照因此会在应用正常保存章节后继续返回旧正文，讲述失联状态、正文摘要、读取输入摘要和绑定它们的游标都不更新，违反 `model` 输出 24、26、36 与 `project` 输出 19、25。若转而直接监听目录，文件服务自身保存引发的 rename 也需正确处理和去抖。
**如何核实**：`world-host.ts:120-125,169-176` 对 binder 目录的回调仅 `reloadBinder()`；`files/backend/changes.ts` 说明文件保存为原子替换并由服务精确发事件；`canon.test.ts` 现有测试覆盖清单替换，未覆盖章节正文保存后 `tellings` 与摘要更新。
**建议改法**：让 canon 宿主订阅文件服务的正文保存/变更事件，基于活页夹映射将章文件变更转成 `textChanged(chapter)`；若选择独立 watcher，明确原子 rename、文件删除/重建与自写事件的处理。新增真实应用集成用例，经文件服务保存章节后观察讲述重新定位、世界版本不变且读取输入摘要变化。
