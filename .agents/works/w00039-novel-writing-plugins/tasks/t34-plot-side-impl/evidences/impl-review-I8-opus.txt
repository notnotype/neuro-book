### 1. 联动戳漏：同一章里没被选进 linked 的变更不进戳（“同一章不细分”只对 linked 成立）
严重程度：阻断
类别：正确性（输出 7，走摘要的结论与重拼不同）
位置：packages/neuro-book/src/plugins/plot/core/checks/dependencies.ts:522-539（worldFold 的联动戳；stamp 用的 running 只含更早的章，这一章的值在算完戳之后才加）
现象：第 4 章同时有只改路人的变更 A（单目标）和联动计划 P。A 排在 P 之前时决定 P 能不能套上，但 A 不满足 linked 的条件（目标少于 2 个），它的值既不在 linked 的摘要列表里，也还没进 running。改 A、撤销 A、往这一章加 A，P 的戳都不变，K 的历史不变，摘要不变，重拼的结论已经变了。
为什么是问题：注释写“同一章的先后不细分，几条一起算一个戳”，实际只有 linked 的几条算在一起。第 4 章既写已写变更又留计划是作者最常见的状态（S2c 就是“写这一章时加一条变更”）。同一章内还可以传递：W1{X,Y} 排在 W2{Y,Z} 之后、P{Z} 在同一章时，W2 因 P 进 linked，W1 的筛选先于 W2 把 Y 记进 touched，可能漏掉（推理，没单独跑）。
如何核实：scratch/s1.test.ts、s1e2e.test.ts（bun test 跑，世界如上）
    MISS S2a 撤销同章单目标计划: signature变=true 摘要变=false
       调用差: [ "presence:main#1:e3:e2" ] -> []
    MISS S2b 撤销同章单目标已写: signature变=true 摘要变=false
    MISS S2c 同章加单目标已写: signature变=true 摘要变=false
       调用差: [] -> [ "presence:main#1:e3:e2" ]
    E2E-MISMATCH S2c 同章加单目标已写: 改前=true 全量重拼=false createCheckSource=true
    E2E-MISMATCH S2a 撤销同章单目标计划: 改前=true 全量重拼=false createCheckSource=true
建议改法：一章里有 linked 时，把这一章全部带补丁的变更的值（不论目标几个、kind 是什么）都算进戳；因为值本身可能依赖戳，先用“对象摘要 + 套没套上 + 粗定位”这一段不带戳的键进戳。touched 的更新放在同一章筛选之前跑到不动点。

### 2. 联动戳漏：P 的另一个目标的初值不进 running
严重程度：阻断
类别：正确性（输出 7）
位置：packages/neuro-book/src/plugins/plot/core/checks/dependencies.ts:515-547（running 只累加带补丁的变更的值，从 0 开始）
现象：路人的知情行写在初值里（不是变更加的）。改路人的初值删掉这一行，P 在覆盖层上套不上，K 进本章；路人不在 R，P 的戳不变，摘要不变。
为什么是问题：模块头写的不变量是“放决定这个结论的东西：它改的条目到这里为止的全部项”，而条目历史的定义里初值就在“全局那一桶”。两者不一致。已写变更不受影响（引擎的结论进键），只有按计划模式的路径漏。出场、是否删除、namespace 启用这些写在条目本体上的东西同理。
如何核实：scratch/s1.test.ts
    MISS S1 删路人初值里的行: signature变=true 摘要变=false
       调用差: [] -> [ "presence:main#1:e3:e2" ]
    E2E-MISMATCH S1 改路人初值: 改前=true 全量重拼=false createCheckSource=true
建议改法：running 的初值是条目本身的值（entryDigest 算的那个，`folder`、`order` 仍不算）。注意这会让计划的目标里的条目本体一变，这条计划提到的条目都要重拼，量一下普通条目改简介的场景。

### 3. 联动戳漏：计入与否由链接决定的计划，翻转不进戳（兑现、替代、拆分的 by）
严重程度：阻断
类别：正确性（输出 7、canon.model 输出 5、13）
位置：packages/neuro-book/src/plugins/plot/core/checks/dependencies.ts:515-547（只收 `patches.length > 0` 的变更；P1 的键里只有它自己的对象摘要）
现象：P1 只改路人（去掉那一行），P 在 P1 之后。新写一条 W 兑现 P1（无补丁，或补丁改别的条目），或新写一条计划替代 P1，或撤销 P1 拆分所依赖的 `by`：P1 这时不再计入，P 才套得上，K 的计划值翻转。P1 的对象没变，它在 running[路人] 的值没变；W 没有补丁，或者目标不是路人，不进 running[路人]。P 的戳不变，K 的历史不变。链接成组只把 W 与 P1 的提到合起来（路人），组里没有 K。
为什么是问题：计划“算不算数”和“它的对象内容”是两件事，戳只看后者。兑现计划是写作的主流程。第一轮修的是“计划覆盖层上的联动”，这条路是修法本身没覆盖的第二个入口：P1 的计入状态。
如何核实：scratch/s1.test.ts
    MISS S3a 兑现 P1: signature变=true 摘要变=false
       调用差: [ "presence:main#1:e3:e2" ] -> []
    MISS S3b 替代 P1: signature变=true 摘要变=false
    MISS S3c 撤销 by: signature变=true 摘要变=false
    E2E-MISMATCH S3a 兑现 P1: 改前=true 全量重拼=false createCheckSource=true
    E2E-MISMATCH S3b 替代 P1: 改前=true 全量重拼=false createCheckSource=true
    E2E-MISMATCH S3c 撤销 by: 改前=true 全量重拼=false createCheckSource=true
（S3d：W 的补丁改的条目恰好在 R 里时摘要会变，是碰巧。）
建议改法：running 按“提到”而不是按“补丁的目标”累加（链接成组以后 W 提到路人，running[路人] 就变了），再按安放排的时候链接要算到被链的计划那一章之前。第 1、2、3 条是同一个根因，见下一段。
上游问题（交开发者）：戳这一套是在“内核不给覆盖层的结论”的约束下推理“决定结论的全部东西”，第一轮和这一轮已经漏了 4 个入口（同章、初值、计入状态、桶），下一个入口还会有。P8 第 3 条选它的理由是“不改内核接口”和“读值每张新视图多读几万次”。候选：内核加一个只读的“这个位置上覆盖层里哪些计划与已写变更没套上”（覆盖层本来就算了，`planned` 模式的快照里有 outcomes），依赖摘要按 bucket 取这个结论的摘要进 `own` 或 `entries`。代价是每个读到按计划模式的位置都要建覆盖层（OVERLAY_LIMIT 8 份循环），要量；好处是漏法从“推理全不全”变成“内核的结论变没变”，和已写变更一个口径。

（第 2 条补充）删除也是同一条路：scratch/s2.test.ts，计划的另一个目标 `路人甲` 被作者删除（条目本体的 `deleted`），计划报 entry-missing 整条不套。

       调用差: [] -> [ "presence:main#1:e3:e2" ]

### 4. 备忘把整份 CheckPlan 留在内存里：一次全书重拼后常驻多 100 MB 以上
严重程度：重要
类别：性能、资源
位置：packages/neuro-book/src/plugins/plot/core/checks/source.ts:78-80（`const concerned = plan ?? NOTHING;` 然后 `verdicts.set(chapter, {of, concerned, ...})`）
现象：`Concerned` 只要 `points`、`concerns`，但存进去的是整个 plan，每个 call 的 `request.user` 都是“这段正文 + 题面”的完整文字。verdicts 按章一份，活到重启。
为什么是问题：阶段 G 量的是耗时与记录的堆，这块没量。(h)、(i) 这种全书重拼以后每章留一份。
如何核实：scratch/mem.ts（300 章，每章约 3000 字，4 人在场，8 个秘密），scratch/mem-plugin.ts 只在加载时把这一行换成只留两个数组，别的不变。
    一章计划：调用 18 个，request.user 共 53049 字符
    SLIM=0 重拼 300 章后 heapUsed 19.1 MB -> 54.3 MB
    SLIM=1 重拼 300 章后 heapUsed 19.1 MB -> 19.9 MB
按 0.115 MB 一章线性外推，1000 章约 115 MB；正文更长或调用更多时更大（推算，没有跑 1000 章）。
建议改法：`const concerned = plan === null ? NOTHING : {points: plan.points, concerns: plan.concerns};`。

### 6. 套没套上没有按线分组取：活页夹讲到 4 条以上子线时，每次发布的摘要慢 20 倍
严重程度：重要
类别：性能（计划没做到）
位置：packages/neuro-book/src/plugins/plot/core/checks/dependencies.ts:416-421（`appliedOf` 按 thing 的先后逐条 `on.outcome(change.id)`），`anchorState` 同样；nb-canon/src/lines/set.ts:39（`DEFAULT_RESIDENT_LINES = 3`）
现象：计划第二版写明“按线分组一次取完”，理由正是“免得超过常驻名额反复淘汰”。实现按变更的写入顺序逐条问，子线上的变更交错时，每问一条就可能把另一条线淘汰、下一条再重建引擎。worldFold 每张新视图跑一遍，每次普通发布后的第一次读都付。
为什么是问题：scale-g4 的世界只讲一条子线（第 3 到 5 条线的 3 条回溯没进活页夹），量不到；规模脚本没有这个形状。一部有四五条支线的书会把“普通发布后第一次读”从几百毫秒推到几秒。
如何核实：scratch/lines-perf.ts（300 章，主线 900 条带补丁的变更，每条子线 40 条交错写入，每条子线活页夹讲一章），scratch/group-plugin.ts 只在加载时把 `appliedOf` 换成先按线取完。一次发布后 dependenciesOf 的耗时：
    LINES=2 GROUP=0 一次发布后建折叠（毫秒）: 88 31 45 31 24
    LINES=6 GROUP=0 一次发布后建折叠（毫秒）: 1836 1845 1430 1596 1466
    LINES=6 GROUP=1 一次发布后建折叠（毫秒）: 148 71 78 75 76
（这里走 createWorldReadView，线集与世界服务同一份代码；没有在世界服务上量。）负载 3 到 15，绝对数偏慢，比值差 20 倍。
建议改法：在算项之前按线分组，一次把这条线要的 `outcome` 取进一张 Map，`appliedOf`、`anchorState` 只查表。`plot-scale.ts` 的世界加一个讲 5 条子线的形状。

（第 1 到 3 条补充：根因定位）把联动戳换成最保守的写法（这一章含以前全部对象的摘要、全部条目本体、全部链接状态，只要目标数 >= 2 就进戳）后，第 1 到 3 条的所有场景都变成“签名变、摘要变”，没有留下别的漏法。实验在 scratch/stamp-plugin.ts，加载时替换文本，不改仓库。输出：

所以这三条的根因都在 dependencies.ts 的联动戳这一处（对象本身、桶前缀和读集没有另外的洞）。这个保守写法本身不是建议改法：它让任何同书修改都使带戳的计划失效，失效面要另外量。

### 7. 随机序列几乎只靠确定用例兜底：27 个变异只杀 9 个，第 1 到 3 条的洞它一个也碰不到，提交 a2c08aa8b 又放宽了空转门槛
（报告只追加，这条按影响应排在第 4 条前后，排在这里只因为最后才拿到完整数据。）

- 严重程度：重要
- 类别：测试强度
- 位置：packages/neuro-book/src/plugins/plot/testing/random-edits.ts（操作表）；packages/neuro-book/src/plugins/plot/core/checks/dependencies.test.ts:814-860（readsOfPlan）、869-890（expectReadsCovered）、929-931（核对频率）、935-938（空转门槛）；dependencies.ts:193（没有测试守的一行）
- 现象：
  1. 不变量“摘要没变，结论就没变”由随机序列守，但默认 240 步、66 种操作，每种只试 3 到 4 次。真实代码上第 1 到 3 条的 9 个场景都能漏，随机序列仍然通过。
  2. 操作表里没有这些洞需要的动作：改计划另一个目标的初值、删除它、在同章放单目标的已写或计划再撤销、兑现或替代更早的单目标计划。
  3. 提交 a2c08aa8b 把离线 800 步以上的 expect(idle).toEqual([]) 放宽成不足 10%，默认仍是不足 40%。现在默认种子有 9 种操作从未让结论变过（上限 26.4），包括 toggleSecrecy、mask、rebind、newForeshadow 这些按设计就该影响结论的操作。
  4. expectReadsCovered 只包了 entry、onLine、origins、changes。entries()、object()、allChanges()、outcome()、progress() 不记录，而第 3 条走的正是 outcome 与 progress 这条路。注释承认只守“读了哪个条目的哪个字段”，所以它不能作为“读集完整”的证据。它还只在每 40 步核对一次，240 步里共 7 次。
  5. dependencies.ts:193 的 if (lower(link.plan, own)) moved = true 删掉后 70 个用例全部通过。我试了“兑现在 ch3、计划在 ch9、读者 ch5，改计划补丁或撤销计划”两个场景，变异后也都是签名不变，所以没有证据说它漏，但也没有测试说明这一行要防什么。
- 为什么是问题：计划和提交把随机序列当成“摘要不漏”的兜底。实际杀伤力主要来自确定用例，而确定用例只覆盖作者想到的场景，第二轮找到的 3 类洞正好都在这之外。门槛放宽后，操作在这个种子上是否真的走到了会影响结论的路径，测试也不再要求，后面操作退化成空转时不会报错。
- 如何核实：加载时替换文本做 27 个变异（scratch/mut-plugin.ts、run-mut.sh，不改仓库），只跑 dependencies.test.ts 与 source.test.ts，结果在 scratch/mut-results.txt：

  no-stamp 确定用例失败=4 随机序列失败=0；stamp-plan-only 2/0；no-coarse 2/0；no-applied 5/0；no-anchorState 2/0；no-lineDigests 2/0；no-foreshadow 5/0；no-material 1/0；no-link-lower 0/0。

  变异的两点限制：这里只跑了默认种子 240 步，步数加大后杀伤力可能上升；no-link-lower 可能是等价变异（行为上不产生漏读）。
- 建议改法：
  1. 按第 1 到 3 条加定向操作：编辑或删除计划的另一个目标、同章兄弟变更的增加与撤销、兑现或替代更早的单目标计划，并提高撤销的比例。
  2. 把每种操作的尝试次数改成按操作保底，例如轮转选择操作，不靠均匀随机；固定种子时门槛就可以回到确定的集合（把已知空转的操作逐个写明理由），不用比例。
  3. 把这张变异矩阵留成一个离线脚本或至少把结果写进证据：把“杀了几个”作为改随机序列时的回归基准。
  4. dependencies.ts:193 要么补一条能说明它防什么的用例，要么写明它是只多不少的保守处理。

（第 1 到 3 条补充的更正）上面说保守写法“让任何同书修改都使带戳的计划失效”说过头了：准确的是“这一章含以前的任何修改”。同一补充的 stamp 输出里 S3d、改线名、改切口三项在真实代码上已是 ok，没有列入。

- 更正现象第 2 点：我写“操作表里没有这些动作”不准确。操作表有 fulfill、replace、split、undo、deleteEntry、sameChapterPlans、breaker、planBreaker 这些基本动作，缺的是洞需要的组合：
  带两个目标的计划，第二个目标固定是 touch 那一行（bystander 的 know.知情）；editInit 与 toggleInitEnabled 只改 person() 或 point()，没有操作改 bystander 的初值；deleteEntry 只删 people[3] 以后的人，碰不到这个目标；sameChapterPlans 放的是同一目标的两条单目标计划，不和带 touch 的计划同章。fulfill、replace、undo 都从全部计划或变更里均匀抽，碰上“同章、位置在前、影响 touch 的兑现或替代”要靠运气。
  因此建议改法第 1 点改为：让已有的操作定向选中这些组合，并加上改、删第二个目标的操作。
