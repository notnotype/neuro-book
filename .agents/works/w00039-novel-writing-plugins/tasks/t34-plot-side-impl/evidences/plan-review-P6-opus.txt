== 3. [重要] 数据版本用“后缀加一”的计数：重启后归零会撞号，旧游标可能在不同数据上被当成有效；且每次替换都让整个世界的游标作废
类别：接口与合同 / 并发与重启 / 隐含的耦合
位置：计划 E0 “写作指示快照……换一个快照就把 `PLOT_DATA_VERSION` 的后缀加一……经 `canon.register` 重登记”
现象与核实：
- 内核把插件的数据版本放进整份读取输入的摘要（model.md 输出 36 的 `pluginData`；packages/nb-canon/src/service/service.ts:729-734 `reportDataVersion` 只在版本串不同时 `#inputGeneration += 1`）。canon 自己的分页（`tree`、`changes`、`pending`……，service.ts 的 `#page(stamp, …)`）与剧情的 `pagedList`（backend/plugin.ts:47-57）都按这个摘要判 `cursor-stale`。
- 计数后缀是进程内状态：进程 A 里 setInstructions 两次到 “1+2”，重启后内存清空回到 “1+0”，再 setInstructions 两次又到 “1+2”，但数据不同。游标里绑的是 inputDigest，世界版本与正文没变时两边摘要完全相同，A 时期发出的游标在新数据上被接受，分页结果与第一页不属于同一份输入（canon.project 输出 18 的游标保证被破坏）。简报记录（输出 15）里的 `inputDigest` 同样撞。
- 同一内容重复 setInstructions 也会加一，平白作废所有游标、清空剧情的 `perViewCache`（core/view-cache.ts 按 inputDigest 缓存知情索引）与世界服务的诊断缓存；写作任务每章开写前推一次快照，作者在界面上翻条目树、待处理的分页就会时不时 `cursor-stale`。计划只写了“旧游标 cursor-stale，内核已有这条规则”，没写这个副作用波及 canon 全部列表。
- 计划写“经 `canon.register` 重登记”：canon 已有专门的 `reportDataVersion`（canon/shared/contracts.ts:372，backend/plugin.ts:110，world-host.ts:334-339）；重登记会 detach 再 attach 全部计算（world-host.ts:320-329，service 侧 `#inputGeneration` 再加一次），不是设计里的做法。
建议改法：数据版本取快照内容的摘要：`"1+" + sha256(canonicalJson(按章 id 排好的快照))`，同内容不变、重启后可复现；用 `canon.reportDataVersion` 报告，不重登记。在计划里写明“换快照会让整个世界的游标作废”是接受的代价，或者只在内容确实变了时报。测试除“旧游标 cursor-stale”外加“同内容再设一次游标仍有效”“重启（新建插件实例）后同内容得到同一数据版本”。

== 4. [重要] `setInstructions` 的通道没想清：只读合同里的写方法、整体替换让两个调用方互相覆盖、重启后诊断静默消失、全量快照可能超过单条消息上限
类别：遗漏（并发、重启、失败路径）/ 接口与合同
位置：计划 E0 第 2、3 条；“开工前要确认的事实”第 3 条
现象与核实：

- `provideRemote(plotWorldContract, () => {...})`（backend/plugin.ts:189-194）每个调用方一份实现；快照表必须放在 `activate` 闭包里、所有调用方与诊断计算共用。计划写的 `backend/instructions.ts` 的“插件内存里的 Map”若照字面做成模块级单例，同一进程里两个项目实例会共用一张表（`viewpointSequence` 这种模块级计数不要照抄）。

- 重启后表是空的：`povAbsent`、`flashbackMismatch`、`repeated` 的计算返回空数组，内核把这当成“算过、没有发现”（model.md 输出 34 只有“没登记计算、计算抛错”才报 `diagnostic-unavailable`），作者在待处理里看到这几条提示无声消失，直到宿主再推一次；`beforeWriting`、`brief` 读不到快照时怎么办也没写（brief 输出 1 的“写作指示”段写“无”还是报错）。

建议改法：E0 明确：(1) `setInstructions` 设 `effect: "write"`，callers 只给 `server`（写作任务）或在说明里写明由谁调用；(2) 表放在 `activate` 闭包；(3) 改为按章替换 `setInstructions({chapter, snapshot | null})` 或带 `base` 数据版本做比较后替换，冲突回 plot 失败码；(4) 读不到快照时，三项写作指示检查对“没推过快照”的项目返回 `diagnostic-unavailable` 语义（抛出带原因的错误，内核会记成 unavailable），而不是空数组——或者在计划里写明接受“重启后提示消失”并记待确认；(5) 输入大小按 `encodedBytes` 校验、超了回 `too-large`。

== 7. [重要] 地址守卫的算法在现有读取上算不出“值不完整”，“无法检查”的报法与 `Finding` 的形状、诊断级别冲突
类别：与现有代码不符 / 算法能否算出
位置：计划 E2 “地址守卫（输出 2）”
现象与核实：
- `OriginStep`（packages/nb-canon/src/engine/types.ts:107-113）没有完整性标记：`patch` 步只有 change、op、result；套不上的变更不出步骤（incremental.ts:377 `if (!item.applied) continue`），之后的值在引擎里是不完整（`FieldState.incomplete`，types.ts:53-56），但来历里看不出来。计划“完整性：值不完整不判”没说从哪取。
- 来历的第一步总是 `init`（incremental.ts:368、393 `[initStep, ...steps]`），“没有步骤是初值”的分支不存在；还有 `check`（核对点，精确档不改值、只带 written）与列表末尾的 `reduce`（语义档归纳，无值）两种步，“范围前最后一步的值”照字面取会取到没有值的步骤。
- `Finding.params` 的类型是 `Record<string, string | number>`（service/diagnostics.ts:27），`unchecked: true` 放不进去；诊断的级别是按诊断 id 登记的（`addressGuardViolated` 是 `pending`），同一诊断的发现全部进待处理，不存在“这一条带标记就不入待处理”。
为什么是问题：照字面写 E2b 会卡在三处：完整性无从判断、起点取错、“无法检查”无处安放。Spec decisions 输出 2 的“记‘无法检查’”与内核核对点的“只在诊断里记‘无法核对’，不成待处理”（model.md 输出 11）对应，但插件诊断没有这种“只记不报”的通道。
建议改法：起点值与完整性用 `view.entry(at.entry, {kind:"chapter", chapter: from, edge:"start"}, mode)` 的 `fields[path].incomplete` 取（没有 `from` 用初值），范围内每一步用 `patch`/`carried` 步的 `result`，并在每一步对应的位置（这条变更之后）用 `entry()` 查完整性，或接受“只看起点与最后一步的完整性”并写明；`check`、`reduce` 步跳过。“无法检查”另登一个 `hint` 级的诊断（例如 `nbook.plot.decision.addressGuardUnchecked`，键同违反那条），或只在 `decisionsFor` 的守卫结果里带“无法检查”而不出发现——两种都超出 Spec 的诊断表，记待确认。

== 8. [重要] E1 的三项检查有几处照字面实现会出错：没有变更 id 的知情变化、`changesOf` 的“变更取触发处”、`skippedStep` 的“中间”怎么列
类别：算法能否算出 / 没处理的边界
位置：计划 E1 第 1、3 条；风险 (4)
现象与核实（core/knowledge.ts）：
- 带过去的候选不记变更：`#explicitOf` 里 carried 那一步 `history.push({key, explicit: true, row: …})`（第 172 行）没有 `change`；隐秘目标推出的候选（第 223 行）也没有 `change`，只有目标出场的安放键。`premiseChanged` 的稳定键第三项是“让知情变了的那条变更”，这两类变化没有现成的变更 id。
- 计划说 carried “变更取触发处”：触发处是父线上的变更（reads.ts:178 `change: fork.trigger ?? fork.cut`），它的排序键在子线视图里可能不存在（`eventKey` 只认这条线事件序列里的），之后判断“这条变更之后有没有改过 G”若用触发处的键去比，会和子线上切口之后的目标改动比错位置。应当用候选自己的键（合成事件的键，reads.ts:178 的 `key`）比先后，只把触发处 id 用于稳定键。
- 隐秘目标推出的 `knows` 从目标出场起生效：若 G 的 `基于` 里含它自己的 `隐秘` 知识点（或另一个隐秘目标的），出场时“有效知情变了”却没有变更，计划没说报不报、键写什么。
- `skippedStep`：计划写“对每个变化的变更查 involves/补丁地址；‘涉及它’指这条变更本身以外的别的变更”，但没说怎么列出“中间”的变更。要的是“进行那一步（或 init/出场）与达成那一步两个排序键之间、`changes({entry: G})`（reads.ts:342 `concerns`）里的变更”，只查两端变更自己的 `involves` 得不出 Spec 的判断。另外 `状态` 初值就是 `achieved`、或在同一条变更里由进行改达成（同一变更两个补丁）时算不算，没写。
- 同一条变更既让 H 知情变了、又改了 G 的 `goal` 命名空间：Spec 说“这条变更之后没有……改过 G”，照字面同一条不算“之后”，会报；作者把两件事记在同一条变更里是最自然的写法，报出来是误报。
- 计划只对“最后一次变化”报一条；Spec 写的是“在某条变更里……变了，而这条变更之后没有改过 G”，照字面每一次这样的变化各报一条（键各不同）。只报最后一次是合理的降噪，但它让作者挂在旧键 `[G, K, c1]` 上的“有意为之”决策在 c2 出现后失效——这是行为取舍，计划里没说。
建议改法：E1 第一步给 `KnowingIndex` 的候选补上 `change`（carried 记触发处、合成事件的键另存；隐秘目标推出的记 null 并在 premiseChanged 里跳过），`changesOf` 的返回带 `{key, change, before, after}`，先后一律按 `key` 比；`skippedStep` 写成“两步的键之间 `changes({entry: G})` 里，除这两条以外是否还有变更”；“同一条变更也改了 G 算已跟着改”写进计划并在 E1 的固定场景里各加一条；“只报最后一次”与上面两条一起记进待确认清单。

== 9. [建议] `stalled` 与 `overdue` 的“最新一章”在计划里两种取法，和 Spec 也不一致
类别：与 Spec 不一致 / 别扭之处
位置：计划 E1 `stalled`、E2 `overdue`
现象：
- `stalled`：计划取“到读取位置所在章（`view.chapters` 的下标之差）”；Spec goals 输出 4 写“从最后一次被改到最新一章超过 30 章”。
- `overdue`：计划取“`view.chapters` 里最新一章不早于第 N 章”。`view.chapters` 是整份章序（reads.ts:192 `chapters: deepFreeze([...order.ids])`），不随读取位置截断；`due` 是章 id，只要那一章在章序里，“最新一章不早于它”恒成立——等价于“到期章在章序里就报”，与读取位置无关。若活页夹里预先排了还没写的章（细纲先行的写法），到期章一建出来就 overdue。
- 两项都是在 `(view, at, mode)` 里算的；一个按 `at`，一个不按 `at`，读第 10 章末尾的待处理时会看到第 15 章到期的决策已“到期没定”，却看不到按最新一章算已经停滞的目标。
为什么是问题：Spec 两处都写“最新一章”，计划一处改成读取位置、没有说明；另一处照字面成了“到期章存在即报”，与验收 3“活页夹到第 15 章时进待处理”在“活页夹已排到 20 章、只写到 12 章”的情形下读法不同。
建议改法：统一一种口径并写进计划：要么两项都按读取位置（`at` 所在章，读最新章末尾时即 Spec 的“最新一章”），要么都按章序末尾；“活页夹里最新一章”是否只算已有正文的章，作为 Spec 没写清的一项记待确认。`appears` 在前史或没有出场时 `stalled` 的起点也写明。

== 17. [建议] 开写前的视图：跨线聚合与“本章计划会触发”不符，“涉及本章的 premiseChanged”没有定义
类别：与 Spec 不一致 / Spec 没写清
位置：计划 E2 地址守卫最后一句“`beforeWriting` 与 `decisionsFor` 的聚合跨线（Spec 写‘每条线各自报’）”；`beforeWriting` 一条
现象：
- 第 N 章讲在某条线上（或分两段讲两条线）。Spec decisions 输出 6 要的是“本章计划会触发的地址守卫违反”：本章计划只在本章讲的那条（或两段的两条）线上；把所有线上的违反聚合进来，会让作者看到与第 N 章无关的线上的违反，还要为每条线建一次线视图（线多于常驻名额时就是风险 (1) 的重建）。括号里引的“每条线各自报”恰好是反对跨线聚合的依据。
- “涉及第 N 章的 `premiseChanged`”：稳定键是 [G, K, 让知情变了的那条变更]，“涉及本章”可以指那条变更安放在第 N 章之前、G 的持有者在本章计划里在场、或 G 在本章涉及的条目里——计划没定，三种结果差别很大（第一种几乎是全部）。
建议改法：`beforeWriting` 只在本章讲的线（`positionLine({chapter: N, edge: "start"})`，分段章取各段的线）上算；`decisionsFor` 是读取视图，可以带 `lines` 参数、缺省同样只取本章的线。`premiseChanged` 的“涉及本章”定为“G 的持有者在本章计划里在场或被提到，或 G 在本章涉及的条目里”，写进计划并记待确认。

== 18. [建议] 目标表把“主要角色”定义成“有 `轻重 = major` 目标的持有者”，只有次要目标的角色会从表里消失
类别：与 Spec 不一致
位置：计划 E1 “目标表（输出 5）”
现象：`轻重` 是目标的属性（goals.md 输入表：`轻重` enum major/minor），不是人的。Spec 的非目标写“次要角色的目标：只给作者选定的主要角色建”——建了目标的人就是作者选定的主要角色。计划用“有 major 目标”反推主要角色：一个主要角色此刻只剩 `minor` 的目标（或主要目标已达成、只剩次要的进行中），整个人连同他的态度表从目标表里消失；`stalled` 等检查却照常报他的目标。
为什么是问题：目标表是作者看“主要角色此刻想要什么”的入口，按这个定义会漏人；“每个人的态度表”是全部有 `att` 的人还是只这些主要角色，也随之含糊。
建议改法：主要角色 = 在这个位置上至少有一个已出场目标的持有者（不论轻重、状态，由筛选再收窄）；态度表的“每个人”写明是这些主要角色，还是所有有 `att.态度` 的条目。若作者真想用 `轻重` 区分人，应作为 Spec 补充记待确认。

== 19. [建议] 切片与验收映射的缺口：E2a 没有测试、几条 brief 输出没有落到文件、映射里有重复
类别：验收映射 / 切片边界
位置：计划“切片（阶段 E）”3、5、6；“验收映射（阶段 E）”
现象：
- 切片 3（E2a：决策取数、`overdue`、`dangling`、开写前的视图骨架）没写测试；decisions 验收 3（到期没定）的实现在 E2a，测试却归到切片 4（“decisions 验收 1 到 4”）。E2a 单独提交时没有任何断言兜底，违背“每片各自提交验证”。
- brief 输出 1（组成与顺序、空段写“无”、上一章不存在写“无”）、输出 3（通则，整份只出现一次）、输出 6（场景条件）、输出 13（涉及条目的样子）在 E3 的文件清单里没有对应文件（`fixed.ts` 只放句子；`allowed.ts` 是输出 11）。切片 5 写了“场景条件”，但没说谁拼、按“计划的先后”用哪个排序键。
- 输出 14 的“回溯后读子线带过去的那一点之后”与“共同部分只写一次”在 `read.ts` 一句带过，验收 5 却要“存款是带过去之后的 20000”——这一条依赖第 1 条的渲染取值问题，切片 6 放在最后才暴露。

建议改法：E2a 加 decisions 验收 3 与 `dangling` 的固定场景（含第 11 条的空 `about`）；E3 文件清单补 `compose.ts`（输出 1、3 的组成、顺序、空段）与 `scene.ts`（输出 6，按 `eventKey` 计划模式的先后）；验收映射改成“brief 输出 N → 切片 → 测试名”的逐条表；E3b 补变异检查（例如删掉绝密“不暗示也不揭示”分支、去掉裁剪里“真相那句不裁”的保护，各应让一条测试失败）。

== 20. [建议] 裁剪：只有分段上限却要“段间的裁剪顺序”，没有总上限就无从排；“字数”怎么数没定
类别：Spec 没写清 / 确定性
位置：计划 E3 `budget.ts`（输出 12）
现象：Spec 输出 12 给的是每段各自的上限（写作指示 600 … 上一章末尾 600），又给了“裁的先后按段”的顺序。每段各自超限各自裁时，段与段之间互不影响，“先裁哪一段”只有在存在一个总上限（或总上限由各段之和、某段可以借用别段余量）时才有意义；Spec 没有总上限，计划照抄了两句，没说段间顺序在什么情况下起作用。另外“字数”按 UTF-16 码元、码点还是字形数，项的“文字”含不含标题与固定句，都影响裁到哪一项，同样关系到输出 15 的逐字相同。
为什么是问题：实现者只能自己补一个总上限或忽略段间顺序，两种结果不同；验收 4 只调低“涉及条目的样子”一段，测不出段间顺序。
建议改法：计划写明“只按段裁、段间顺序暂不起作用（等有总上限再用）”或补一个缺省总上限（例如各段之和）并说明超了按段间顺序裁；“字数”定为码点数（`[...text].length`），不含段标题；两者记待确认。测试加一条“总量超限时先裁涉及条目的样子再裁读者已知”（若采用总上限）。

== 21. [建议] 写作指示三项检查的边界没写：没记参与者的变更、回溯者“记得的”变更、“前后各一条”、`repeated` 的“同一句”
类别：没处理的边界 / Spec 没写清
位置：计划 E2 “写作指示的检查（输出 8）”
现象：
- `povAbsent` 用 `experienceChanges`：它返回的 `changes` 含回溯者“记得原线上的”父线变更（core/knowledge.ts:308 的返回里有 `remembered`、`parent`），父线上第 N 章的变更会让“在本章在场”误成立；它还只给 `uncast` 计数。本章有没记参与者的变更时，“视角人物不在场”其实不知道，计划没说报不报；本章一条变更都没有时照字面“没有任何一条里在场”为真，也会报。应直接用 `view.presence(pov, {from: N, to: N, mode})`（只算这条线），`uncast > 0` 或本章没有变更时不报。
- `flashbackMismatch`：“前史里它的前后各一条”是计划自己加的“附近”的定义，Spec 只写“在前史里它的前后”；安放在章内（不是前史）时“附近”只剩“同一章”，也没写。
- `repeated`：`avoid` 是列表、`other` 是一段文字，“同一句”对 `other` 是整段相等还是按句切；“连续 3 章”中间隔着没有快照的章算不算断开；读取位置之后的章算不算。键是 `range: {from, to}`，同一句在两段不连续的区间里各报一条还是一条，也没定。
- 三项的稳定键都不带 `line`，D8 起每条线的视图各算一次：第 N 章只讲在一条线上，别的线的视图里算出同一条发现，会出现在每条线的待处理里。应只在第 N 章讲的那条线（`positionLine`）的视图上报。
建议改法：把上面四点逐条写进 E2b 的算法与测试（尤其 uncast 与“只在本章的线上报”），“附近”与“同一句”的定义记待确认。

== 22. [建议] 简报的确定性有一个 Spec 自带的例外没处理：语义档的归纳缓存补上后，同一读取输入拼出的简报会变
类别：确定性（brief 输出 15）/ Spec 之间的缝
位置：计划 E3 `record.ts`；“同输入逐字相同由测试做两遍比较断言”
现象：model.md 开头与输出 9 写明唯一例外：语义档字段有事件时，值取归纳缓存，缓存没有时是“起点；之后：事件一；事件二……”并标“未归纳”；缓存补上以后同一版本、同一读取输入的读取会变成归纳的那句（`OriginStep` 的 `reduce` 步带 `cached`，engine/types.ts:111）。简报里大量是语义档：目标的 `为什么`、态度的 `态度`（输出 2 的例子“冷淡 → 冷淡（略松动）”正是语义档）、`听过的说法`。记录里只有 inputDigest，归纳缓存不在读取输入里。
为什么是问题：写作任务开写时拼一次、检查时再拼一次比对，中间后台把归纳补进缓存，两份简报文字不同而记录相同——输出 15 说“任何一项不同就算上下文已变”，这里项都相同、文字却不同；测试“两遍逐字相同”在同一测试里不会触发归纳，测不出。
建议改法：记录里加“用到的语义档值是否都已归纳”或用到的归纳的摘要（例如对 `[地址, 起点, 事件 id 列表, cached]` 取 SHA-256），比对时一并比；或在计划里写明“简报的确定性同内核：归纳补进缓存是唯一的例外”，并把这句补进 brief 输出 15（记待确认）。
