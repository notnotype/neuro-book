### 1. 决策的 `about` 会被 diffValues 当成“有 id 的列表”，挂在同一诊断上的两条处理在重放后变成同一条
**严重程度**：阻断
**类别**：代码事实 / 持久化格式
**位置**：plan.md “关键设计 schema.ts”（决策换成 model 的决策表）与切片 A1、A6；代码 packages/nb-canon/src/core/paths.ts:34-55、117-122（isIdList）
**现象**：diffValues 判断“有 id 的列表”是结构性的：数组每个元素都是带字符串 `id` 的对象就按 `[id]` 拆叶子。model 的 `about` 元素是 `{kind: entry, id}`、`{kind: change, id}`、`{kind: decision, id}`、`{kind: diagnostic, id, key, version}`，全部带 `id`；稳定键里的 `objects`（`{kind, id}` 的有序列表、不去重）也一样。revisions 输入明确写“没有 id 的数组（……标注、决策挂的对象……）整体是一个叶子”。计划没有提 paths.ts。
**为什么是问题**：同一条决策挂两条同一诊断 id、键不同的发现（场景 10 的“一键沿用”、一个决策处理多条发现都会这样写），两个元素 id 都是 `plot.x`，按 id 建的 Map 互相覆盖，修订里存的叶子是错的，重放得到错误的对象；这是写进日志的持久化格式，事后改不了。`objects` 里同一个对象出现两次（Spec 说不去重）也一样。标注载荷里只要有 `id` 键，`marks` 也会被拆。
**如何核实**：/tmp/w00039-t34-plan-review-lab/about.ts：before 的 about 有一条键为 [e1] 的诊断，after 再加一条键为 [e2] 的同 id 诊断。diffValues 给出 `about[plot.x].key.objects[e1]` 删除、`[e2]` 新增、`about#order` 为 ["plot.x","plot.x"]；applyChanges 重放后两条 about 都是 e2，e1 那条丢了。
**建议改法**：A1 就把“哪些数组按 id 拆”改成按路径声明（块、列表字段元素、实例字段声明、讲述；与 revisions 输入那份清单一一对应），其余数组一律整体一个叶子，并在 tests/core.test.ts 补“about 有重复 id”“objects 有重复”的往返用例。这条要在第一行格式 2 日志写出之前定。

### 2. 正文仍走 `chapterText` 拉取端口：读取输入的摘要每次要读全书正文，量出来一次 264 到 392 毫秒；“按章正文的摘要缓存”的键要先算摘要，自相矛盾
**严重程度**：重要
**类别**：架构与可测性 / 性能
**位置**：plan.md “tellings.ts”第 1、3 条（“结果按章正文的摘要缓存”“正文从现有的 WorldOptions.chapterText 取”）、“service.ts”第 1 条（所有读取结果都带读取输入的摘要）、“不做与风险”第 2 条；代码 packages/neuro-book/src/plugins/canon/backend/binder.ts:74-87、world-host.ts:140
**现象**：现在的 `chapterText` 每次调用都 readdirSync 活页夹目录再 readFileSync，注释写明“只在写入带讲述原句时用到，不值得维护缓存”。model 输出 36 要求每个读取结果都带“正文快照的摘要”（各章 UTF-8 的 SHA-256），project 输出 19 说读取结果都带它；计划没写这份摘要怎样得来。讲述定位的缓存“按章正文的摘要”做键，意味着每次读取都先读正文、算摘要，缓存省不掉主要成本。
**为什么是问题**：(1) 性能：按规模测量的形状（1000 章，每章约 3000 字）用现在的端口取全书正文并算快照摘要，本机 5 次 290.5、263.9、297.7、392.4、302.2 毫秒，其中 readdir 就占约 233 毫秒；project 输出 14 要求随机读一个条目中位数 20 毫秒以内（本机负载 2.3，不是参考机，但差了一个数量级）。(2) 语义：Spec 的正文快照是“宿主最近一次给出的各章正文”，拉取端口每次读盘，读到的是此刻的文件，不是快照；宿主改了文件、50 毫秒合并期内还没调 `textChanged` 时，定位用的是新正文，摘要与游标却可能还是旧的，违反“一次读取从头到尾用同一份输入”。(3) 写入校验（原句在不在）读盘、读取按缓存，两边可能对不上。
**如何核实**：/tmp/w00039-t34-plan-review-lab/perf.ts 按 canon-scale.ts 的正文形状建 1000 个章文件，按 binder.ts 的写法取正文并算快照摘要；数字见上。
**建议改法**：把正文改成宿主推的快照：服务持有每章 `{text, digest}`，打开时全量读一次，`textChanged(chapter)` 时只重读、重算这一章；快照摘要随之增量维护，讲述定位按章缓存、由 `textChanged` 失效（不必再按摘要做键）。写入校验与读取都读这份快照。A3 的基准要量“改一章后第一次读”与“随机读”两项，并把带快照摘要的读取放进 A8 的规模重测。

### 3. 还原的作者授权照字面做不出来：摘要的对象、`source` 的恢复、表外的转换都没定
**严重程度**：重要
**类别**：Spec 覆盖 / 返工风险
**位置**：plan.md “authorization.ts”第 1、5 条，切片 A6；代码 packages/nb-canon/src/world/world.ts:197-220（revert）、238-310（#publish）
**现象与为什么是问题**：
- `bindsOf(request, decisionRef, transition)` 收的是写入请求。revisions 输出 21 的“还原”说 `request` “按还原请求（去掉 authorizations）算”，还原请求是 project 方法表里 `revert` 的参数（修订 id、是否连同依赖、请求 id、授权），不是 World.revert 在内部拼出的补偿请求（world.ts:217-218，`puts` 是补偿后的整份对象，宿主事先算不出来）。计划没说还原时对哪个对象取摘要；照现有签名做，宿主签的与内核算的必然不一致。
- 补偿修订不跑 validate（world.ts:309 `if (!compensation)`）。计划把授权检查写在“写入路径的新校验”旁边，没说补偿走不走它；不走就收不到 `author-source-required`，走则要单独接一条路径。
- 补偿把决策的 `source` 恢复成改前的值（Spec 原话），这在请求层面就是“改了 source”；计划写的“请求里改了它得到 source-not-writable”没有给补偿开例外，照字面做所有带决策的还原都被拒。Spec 还说还原用的授权“不写进决策的 source”，与普通写入“接受授权就把 source 写成它”相反，计划也没区分。
- 补偿得出的转换可能不在状态表里：还原一次 `decided→superseded` 得到 `superseded→decided`；还原新建一条已定决策的修订会把它真正删掉（revisions 输出 20）。这些要不要授权、`transition` 写什么（输出 21 的“转换的写法”只列了 7 种），Spec 与计划都没有答案。
**如何核实**：读 world.ts 上述行；对照 revisions.md 输出 21 的“还原”一条与输出 20。
**建议改法**：A6 前先定（必要时先改 Spec）：还原授权的 `request` 取 `{revert: 修订 id, withDependents, requestId, by, title?}` 的规范 JSON；补偿修订走一条专门的授权检查（只查 `author-source-required/invalid`，不做 `source-not-writable`，不写 `source`）；补偿产生的表外转换按“恢复到改前状态”统一记成一种 `transition`（例如 `revert`），列入需要授权的项。

### 4. 授权的校验端口把 `binds` 的比对也交给宿主，测试端口“同一密钥签、同一函数验”测不出内核漏比；`binds.project` 从哪来没有交代
**严重程度**：重要
**类别**：架构与可测性
**位置**：plan.md “authorization.ts”第 1、2 条，“不做与风险”第 3 条；代码 world.ts:43-51（WorldOptions）
**现象**：计划写“校验交给宿主注入的 verifyAuthorSource(source, binds)”，没说内核自己是否先比较 `source.binds` 与算出的 `binds`。测试端口用同一函数签与验，自然会顺手比 `binds`。`bindsOf` 的参数里没有项目；`binds` 的第一项是 `project`，WorldOptions 与 ServicePorts 里都没有项目标识。端口是同步还是异步也没写，而 World.publish、preview 都是同步的。
**为什么是问题**：“binds 与实际不一致就拒收”是这套机制防“来源挪用”（场景 7 的四种情况）的唯一手段。比对若只在测试端口里，将来 t20 的宿主只验签名时内核测试仍全绿，挪用就能通过。宿主签发时也要算同一份 `binds`：若宿主自己实现规范 JSON 与字段集合，内核与宿主两份实现迟早漂移。缺 `project` 则跨项目重用来源（同一 requestId 碰巧相同）挡不住。将来宿主若要异步查会话日志，同步端口接不上。
**如何核实**：读计划原文；`grep -n project packages/nb-canon/src/world/world.ts` 没有项目标识。
**建议改法**：内核先按规范 JSON 逐字比 `source.binds` 与算出的 `binds`，不一致直接 `author-source-invalid`；宿主端口只验签名（签名覆盖的字段由内核拼好交给它），写明同步。nb-canon 导出 `authorizationBinds(project, request | revertRequest, decision, transition)` 给宿主签发时用，测试端口签发时也调它。项目标识作为 WorldOptions 的一项由宿主给。另加一条测试：端口对任何签名都答“通过”时，挪用到另一条决策照样被拒。

### 5. “替换与依赖用同一份位置清单”与 Spec 不符：要换临时 id 的位置比引用位置多，以引用为键的列表的元素 id 还藏在地址路径里
**严重程度**：重要
**类别**：Spec 覆盖 / 返工风险
**位置**：plan.md “references.ts”第 2、4 条，切片 A2；代码 world.ts:545-548（ID_KEYS 含 `id`）、585-594（replaceTempIds）
**现象**：现在的 replaceTempIds 靠 ID_KEYS 里的 `id` 一并换掉 `puts[].ref.id`、对象自己的 `after.id` 与 listAdd 元素的 `value.id`。计划要用 `referencesOf` 的清单同时做替换与依赖，并把“同一份清单”写成不变量。
**为什么是问题**：Spec 要求替换、但不属于引用位置（因此不该进依赖、不做存在校验）的有：对象自己的 id；新线的 `fork.line`（components 输出 18 单独点名）；稳定键里的对象引用（model 输入：“不是引用位置……临时 id 照样换成生成的 id”），也就是 `about` 里 `{kind: diagnostic, key}` 的 `key.objects`。反过来，以引用为键的列表（components 输出 19）的元素 id 除了出现在 listAdd 的 `value.id`，还出现在 listRemove 的 `value`（一段文字）和同一请求后续补丁的地址路径里（`know.知情[tmp:k].程度`）；`{path, target, value}` 的清单只能表达“对象里某个键的值”，表达不了“地址路径里的一段”。照字面做，A2 要么漏换对象自己的 id（`id-taken`），要么把稳定键算进依赖、存在校验，要么“新建知识点并在同一请求里给这一行设程度”失败（`element-missing`）。
**如何核实**：读 world.ts 上述行与 components.md 输出 18、19，model.md 输入里“稳定键”一条。
**建议改法**：拆成两份清单：引用位置（校验、依赖、改动记录筛选共用）和替换位置（引用位置，加上对象自己的 id、`fork.line`、稳定键对象、地址路径与 listRemove 里以引用为键的元素 id），在 references.ts 里由同一个遍历分别给出；不变量改成“替换位置包含全部引用位置”，测试覆盖上述三类只替换不引用的位置，以及同一请求里新增一行再给它的子字段赋值。

### 6. 引用清单要靠当前登记才能算，插件停用后依赖与改动记录就变了；还原可能真删掉仍被引用的条目
**严重程度**：重要
**类别**：架构 / 正确性
**位置**：plan.md “references.ts”第 2、3 条（“字段与列表的引用从 Component 登记取，标注的从标注种类登记取”；用于 `dependsOn` 与 `revisions` 筛选）；代码 world.ts:458-497（dependsOn）、service.ts:271-276（revisions 按条目筛）
**现象**：`ref` 字段、以引用为键的列表、标注里的 `refs` 路径，只有查登记才知道是引用。`dependsOn` 与改动记录筛选都是对历史修订现算的。另外，实例字段声明在条目自己的 `init.data.*.declared` 里（components 输出 4），也可以是 `ref`，计划的签名 `referencesOf(object, kind, registry, marks)` 拿不到它；modify 操作只有叶子的 `{path, before, after}`，不是整份对象，签名也接不上。
**为什么是问题**：剧情插件停用（标注种类与知情 Component 不在登记里）期间，“给讲述加一条揭示指向知识点 K”的修订不再被认作依赖“新建 K”的修订；这时还原新建 K 的修订不会报 `has-dependents`，按 revisions 输出 20 会把 K 真正删掉，留下悬空引用，而 Spec 写明“删的时候没有别的记录引用它们”。改动记录按条目筛的结果也随插件启停变化。同样的问题在 Component 版本对不上、类型不在时也会出现。
**如何核实**：读计划原文与 dependsOn；components 输出 12、model 输出 28 都规定类型或种类不在时数据照常保留，说明这种状态是常态而非异常。
**建议改法**：发布时把这次修订新写或改过的引用（目标种类与 id）算好，存进修订（例如 `refs` 字段；格式 2 正在定，现在加最便宜）；依赖与改动记录筛选只读这份存下的结果，不再按当前登记重算。`referencesOf` 只在发布时用，入参改为“写入后的整份对象加条目的有效字段声明”。

**现象**：Spec 的公开接口包括“计算的签名”`(world: 只读世界, at, mode) => 发现[]`（model 边界与兼容），计划只写了“同步调用 compute(world, at, mode)”。剧情插件要读的讲述发生点（A3，依赖正文快照）、在场（A5）、决策（A6）、按位置读条目，在计划里都是 WorldService 的方法，不在 World 上；diagnostics.ts 却放在 src/world/。现有的 WorldSnapshot 只露出 data、engine 等内部结构。`pending` 每页都要带“各组的总数”（project 方法表），即每页都要把待处理、提示、已处理三组全部算出。
**为什么是问题**：签名不先定，阶段 B 写诊断时只能直接摸 engine 与 data，等于把内部结构变成插件合同，之后改不动；放在 world/ 又拿不到服务层的讲述与在场，层次会倒过来依赖。不缓存的话，翻 N 页就把每个诊断算 N 遍，100 毫秒以上的诊断会让分页线性变慢；同一份读取输入两次计算若有任何不稳定，游标翻页还会漏项或重项。

**建议改法**：A7 先写一个 `CanonReadView` 接口（entry、changes、tellings、presence、decisions、lines 占位等只读方法，都按同一份读取输入），World 与服务都据此实现，诊断只拿它；把诊断的计算放在服务层；同一读取输入摘要加同一位置与模式的诊断结果缓存一份，翻页与三组总数都读缓存，读取输入一变就作废。

### 14. 讲述 id 的分配与几个 id 前缀：嵌套的讲述 id 重放时不会被记下，“不复用”靠不住；线的 id 与修订同用 `r`

**位置**：plan.md “tellings.ts”第 5 条（“讲述 id 前缀 t，在讲述所在的列表里全局分配，不复用”）、“schema.ts”第 3 条（决策前缀改 d）；代码 core/ids.ts:56-77（IdAllocator）、world.ts:123-134、399-400（只 observe 修订 id 与 op.ref.id）

### 15. 把标注种类与诊断并进 Component 登记的 `digest`，插件每次启停都会整本重算
**严重程度**：建议
**类别**：架构 / 性能
**位置**：plan.md “components/”最后一条（“登记集合的摘要扩成三项……引擎据它判断要不要整本重建”）；代码 registry.ts:105-108、world.ts:154、engine/incremental.ts:336
**现象**：`registry.digest` 变了，withOptions 与增量引擎都按“结构性变化”整本重算。标注与诊断不参与引擎的补丁计算。
**为什么是问题**：剧情插件激活、停用，或只是它的标注种类、诊断升版本，都会触发整本重算；project 输出 14 的打开预算是 2 秒，在大书上这是一次接近“打开”的开销，且没有必要。读取输入的摘要（model 输出 36）要的是 `[[id, version]]` 三张表，本来也不是这份 digest。
**如何核实**：读上述三处代码。

### 16. `stableStringify` 对合法 JSON 与 RFC 8785 一致，但对 NaN、Infinity、孤立代理项、非普通对象静默输出，计划要加的附录向量会撞上；“前后端都能用”的同步摘要在浏览器里并不存在
**严重程度**：建议
**类别**：技术选型
**位置**：plan.md “技术选型”第 2、3 行；代码 core/stable-json.ts:5-16
**现象**：实验 /tmp/w00039-t34-plan-review-lab/jcs.ts：RFC 8785 第 3.2.4 节的样例逐字相同；第 3.2.3 节的排序样例（`\r`、`1`、U+0080、ö、€、😀、U+FB33）顺序正确；附录 B 的 8 个有限数向量全部一致。偏差：`NaN` 与 `{a: Infinity}` 输出 `null`、`{"a":null}`（RFC 要求报错）；孤立代理项 U+D800 输出 `"\ud800"`（RFC 要求 I-JSON，应报错）；`Date`、`Map` 输出 `{}`；数组里的函数输出 `null`。浏览器的 Web Crypto 只有异步摘要，nb-canon 自己不带 SHA-256。
**为什么是问题**：附录 B 的向量表里 NaN、Infinity 标的是“错误”，照计划“加 RFC 8785 附录的几个向量”会直接失败或被删掉了事。插件诊断的 `params`、稳定键在项目内同步传进来，不经 JSON 编码，NaN 会和 `null` 得到同一个规范 JSON，排序 id 与已处理的匹配就会撞。浏览器侧现在没有构造 World 的调用方（只有 web/client.ts 走远程），所以这不是眼下的问题，但计划把“同步、前后端都能用”当成否决 Web Crypto 的理由，并不成立。
**如何核实**：bun /tmp/w00039-t34-plan-review-lab/jcs.ts；grep 包内没有 sha256 实现。
**建议改法**：另写 `canonicalJson`：遇到非有限数、孤立代理项、非普通对象抛错，稳定键、作者来源、读取输入都用它；`stableStringify` 继续做请求摘要与深比较。附录 B 的向量连同错误项一起测。技术选型里把理由改成“摘要由宿主注入，浏览器侧若要用需注入同步实现”。
