### 9. 新建的待定决策可以直接带结论、理由、约束，读取时显示成“重新打开前定下的”
**严重程度**：重要；**类别**：不变量。
**位置**：`packages/nb-canon/src/world/decisions.ts:51-56`（新建只看目标状态）、`decisions.ts:35`（待定里能改的字段）、`decisions.ts:108-121`（`earlier`）。
**现象**：`classifyDecisionWrite` 对新建的决策只按 `new→${status}` 查表，`new→pending` 直接算 `free`，不看带了哪些字段。所以 Agent 不带任何来源就能新建一条 `pending` 决策，同时写上 `conclusion`、`reason`、`risks`、`constraints`、`marks`。同一条决策建好以后，在待定状态里改 `conclusion` 会被拒（`invalid-transition: a pending decision cannot change conclusion`），新建与修改的口径不一致。读取时 `decisionView` 把这些字段放进 `earlier`，按注释与 model 输出 31 的说法，这是“重新打开前定下的”内容，也就是作者定过、后来重新打开的。
**为什么是问题**：model.md“状态与转换”把结论、理由、风险、约束、标注写成只有已定时才起作用、改它们要作者来源的字段；“重新打开前定下的”只应来自一次带授权的 `→decided`。现在 Agent 可以伪造一段“作者定过”的历史，读的人（作者面板、别的 Agent）无从分辨。之后转成已定时“没给的沿用”，伪造的理由与约束也会被沿用；虽然整份请求进了 `binds.request`，但宿主按“作者说了什么”签发，作者只说“就定第 3 章”时，Agent 预先塞进去的 `constraints` 也会跟着签进去。
**如何核实**：在实现 worktree（cb4aa74c5，这几处与 5318a94bd 相同）用真实 `WorldService.open`（带 `project` 与 `verifyAuthorSource`）运行 `bun run /tmp/w00039-t34-impl-review-lab/opus/pending-with-conclusion.ts`（`CANON_SRC` 指向实现 worktree 的 `packages/nb-canon/src`）：以 Agent 身份新建带 `conclusion/reason/constraints` 的待定决策发布成功；`decisions()` 读到 `earlier: {conclusion: "第 3 章揭开", reason: "作者说过", constraints: [...]}`；随后对同一条决策只改 `conclusion` 得到 `invalid-transition`。
**建议改法**：新建时也按目标状态限定字段：`new→pending` 只许待定里能改的那些字段（`text`、`candidates`、`due`、`about`、`suggestion`、`hints`、`quote`）。带了只在已定时起作用的字段就报 `invalid-transition`，或者把它当成需要来源的转换。补一条“新建待定决策带结论被拒”的验收用例。

### 10. 还原拿一个已经用过的 requestId，不论内容是否相同都返回“已发布”，还原并没有发生
**严重程度**：重要；**类别**：正确性。
**位置**：`packages/nb-canon/src/world/world.ts:223-225`（5318a94bd）；实现 worktree 当前仍在同一处。
**现象**：`revert` 第一行按 `meta.requestId` 查 `index.requests`，查到就返回 `{ok: true, repeated: true, revision: 第一次的修订}`，不比内容。这个 requestId 原来属于一次普通写入、另一个还原目标或别的 `withDependents` 时，调用方也拿到成功。A7 把这一步挪到了 `not-found`、`not-revertable`、`has-dependents` 之前，所以连目标不存在的还原也会被答成功。普通写入走 `#publish`，会按 `requestDigest` 比，不同就报 `request-id-reused`；只有还原这条路没有比。
**为什么是问题**：revisions 输出 16 要求同一个 requestId 内容不同就拒收（`request-id-reused`），project.md 写明 `revert` 的结果“同 `publish`”。调用方（Agent 工具、面板）按 `ok: true` 判断还原完成，作者以为决策已经回到待定，世界其实没有变。这一步还在授权检查之前，所以不带授权也能拿到“成功”。
**如何核实**：在实现 worktree 用真实 `WorldService` 运行 `bun run /tmp/w00039-t34-impl-review-lab/opus/revert-auth.ts`（`CANON_SRC` 指向实现 worktree）：新建待定决策（requestId `c1`）、带授权定下（r3），再用 `requestId: "c1"` 还原 r3，得到 `{"ok":true,"repeated":true,"revision":"r2","what":"creative"}`，决策状态仍是 `decided`。
**建议改法**：还原的重发也按内容判定：给还原修订存下还原请求本身的摘要（`{revert, withDependents, requestId, by, title}`，与 `binds.request` 同一口径），或者存 `withDependents` 与原样的 `title`，重发时对得上才返回第一次的结果，对不上报 `request-id-reused`。查重放在算还原计划之前没有问题，但对不上时不能返回成功。补一条“还原用别的请求的 requestId 被拒”的用例。

### 11. 存进修订的授权只能验签名，不能事后核对它绑定的就是这次修订；还原修订的 `binds.request` 用存下的内容算不出来

**建议改法**：两种做法选一种，并写进 revisions 的“存下来的修订”。一种是在修订里存够重算所需的内容：还原存 `withDependents` 与原样的 `title`；写入存 `binds.request` 的原像，或者至少存每项授权对应决策的原样 `after`，好算 `fields`。另一种是在 Spec 里写明，事后只验签名与 `requestId`、`decision`、`transition` 这三个可以对上的字段，内容的绑定只在发布时校验一次。

### 12. 表里没有的转换带上授权时报 `authorization-unused`，真正的错 `invalid-transition` 被盖住
**严重程度**：建议；**类别**：正确性。
**位置**：`packages/nb-canon/src/world/world.ts:306-314`（`#decisionWrites` 先查授权并提前返回）、`world.ts:412`（`invalid-transition` 在校验阶段才报）；`packages/nb-canon/src/world/authorization.ts:94-96`。

**如何核实**：在实现 worktree 用真实 `WorldService` 运行 `bun run /tmp/w00039-t34-impl-review-lab/opus/unused-masks-invalid.ts`：把待定决策直接写成 `superseded`，不带授权时得到 `invalid-transition`（两条）；带上宿主签好的 `pending→superseded` 授权时只得到 `author-source-invalid / authorization-unused`。
**建议改法**：被分成 `invalid` 的决策有对应的授权时，先报 `invalid-transition`，或者在 `authorization-unused` 的详情里附上这条决策的分类结果。也可以把“授权是否无效”的判断整体挪到 `decisionProblems` 之后，与缺来源同样放在校验之后报。补一条带授权、转换不合法的用例。

**严重程度**：建议；**类别**：不变量。
**位置**：`packages/neuro-book/src/plugins/canon/backend/world-host.ts:166-187`（`WorldService.open` 的端口里没有 `project`）；`packages/nb-canon/src/world/world.ts:230`、`world.ts:311`（`const project = this.options.project ?? ""`）。
**现象**：计划 A9 写的是“`backend/world-host.ts` 接上正文快照与 `textChanged`、项目标识、`verifyAuthorSource`（宿主给；没有时不注入）”。正文快照接上了，项目标识没有接，实现 worktree 当前也没有。`verifyAuthorSource` 暂时没有，按计划不注入，所以应用里需要来源的转换现在一律是 `no-verifier`，这一点符合预期。内核这边，`project` 没给时 `binds.project` 用 `""` 去比，照常往下校验，不当成缺少输入。
**为什么是问题**：revisions 输出 21 把 `project` 定为“宿主打开世界时给的项目标识”，靠它保证一个来源不能挪到另一个项目里用。以后宿主接上签名校验时，如果漏传 `project`，所有项目的来源都按 `""` 签、按 `""` 验，可以互相挪用，内核不会提醒。
**如何核实**：`grep -n "project" packages/neuro-book/src/plugins/canon/backend/world-host.ts` 找不到传给端口的项目标识；读 `world.ts:230`、`:311`。
**建议改法**：在 world-host 里把项目标识（`currentProjectKey` 给的项目 id）传进端口。内核在 `project` 缺省时，把需要来源的项判成 `author-source-invalid`（与 `no-verifier` 同一种处理），不要按空字符串静默放过。补一条“没给项目标识时带合法签名也被拒”的用例。

### 18. 诊断的项目内接口“随调用方入口停止失效”没有测试
**严重程度**：建议；**类别**：测试。
**位置**：`packages/neuro-book/src/plugins/canon/backend/plugin.ts:76-91`（`provideServicePerConsumer` 的 `release` 撤销登记）、`world-host.ts` 的 `registerDiagnostics` 返回的撤销函数；测试 `packages/neuro-book/src/plugins/canon/canon.test.ts:389-414`。
**现象**：唯一的集成用例只核对“登记以后诊断算出来了”。没有用例让探针插件的项目入口停止，再看这条诊断变成 `unavailable`（`not-registered`），也没有用例核对读取输入摘要随之变化、旧游标 `cursor-stale`。视图令牌随调用方失效有用例（`canon.test.ts:358-387`），诊断登记这一半没有。实现 worktree 当前同样没有（`grep -n "not-registered" packages/neuro-book/src/plugins/canon/*.test.ts` 无结果）。
**为什么是问题**：model.md“诊断的计算”与本插件的模块注释都把“入口停止时登记随之失效”写成合同。撤销要经过三层：运行时的按调用方释放、门面里的 `detaches`、host 的 `computers` 按对象身份比较，任何一层接错都会留下一份引用着已停止插件闭包的计算，而且它还会继续算。
**如何核实**：读上面的测试文件；nb-canon 的 `tests/diagnostics.test.ts` 只在服务层直接调撤销函数，没有经过插件运行时。
**建议改法**：在 `canon.test.ts` 的探针用例后面停掉探针插件（或它的项目入口），断言 `pending` 的 `unavailable` 列出 `test.canon-probe.lost`（`not-registered`）、旧游标得到 `cursor-stale`。

## 未发现问题的方面

- `binds` 的算法与 revisions 输出 21 逐项对照，没有出入：六个字段一致；`request` 去掉 `authorizations` 与 `baseVersion`，取规范的 JSON 再取 SHA-256；`fields` 取九个键里出现了的，按请求原样（临时 id 换掉之前）算，内核用下标取原样那一条，与宿主用的 `authorizationBinds` 口径相同；还原的 `request` 取 `{revert, withDependents, requestId, by, title?}`；校验先逐字比 `binds`，再交给宿主验签；没有校验函数、签名不对、用不上、重复，都报 `author-source-invalid`；缺来源报 `author-source-required`。
- 别的写入路径不能不带授权改决策：`editInPlace`、`recordDelta`、`writeBack` 都走 `world.publish`，同样经过 `#decisionWrites`；补偿只经 `revert`、`previewRevert` 进入 `#publish(…, compensation=true)`，`revert` 在这之前先按补偿结果核对授权；`absorb` 按设计不校验别的进程写的行。同一请求里对同一条决策写两份 `puts`，每份都按改前的世界分类，需要来源的各自要一项授权，拼不出绕过（从代码推断）。
- 出处只由内核写：请求里改了 `source` 报 `source-not-writable`；只改候选的整份写回不需要来源；`binds.decision` 里的临时 id 不在引用位置上，不会被替换（P2 第 2 条的修正有效）。
- 两个引擎在按计划模式下的待处理、`plannedAt`、没有补丁的变更、带参与者的本章涉及条目上一致：原差分测试用 16 个种子、每个 80 步，扩展版（见第 13 条）用 12 个种子、每个 70 步，都全部通过。`update` 对改动的变更按新旧两版弄脏条目，`touchesNothing` 让没有补丁的变更在重算区间里都记下结果。覆盖层的核对结果按快照缓存，没有跨版本复用。
- canon 插件：带令牌的方法表与 project 输出 24 一致（`object`、`tree`、`revisions`、`decisions`、`suggestions`、`pending`、写入与预览一律拒，并记审计）；调用方释放时关掉它打开的视图、结束它的独占；`closeView` 只关自己打开的；诊断计算按声明它的插件找，一个插件登记不了别的插件的诊断；同一插件再次登记时，旧的撤销函数不会删掉新登记。
- 第 1 段的 8 条与已修正的视图问题（`presence` 的 `uncast` 按上限计数等）不再重复。
