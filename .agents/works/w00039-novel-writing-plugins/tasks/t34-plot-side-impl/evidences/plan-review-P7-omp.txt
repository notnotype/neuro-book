### 1. F1 没有把 Storage 依赖接进剧情项目入口
严重程度：阻断；类别：接口与合同
位置：plan.md:831-839（F1），对应入口 packages/neuro-book/src/plugins/plot/backend/plugin.ts:214-226
现象：F1 新增 `ChapterTable`，要求用 `nbook.storage` 的 project/shared 记录读写，但计划没有把 `storageKey` 加入 `plotProjectPlugin` 的 dependencies，也没有说明从 `context.services` 取得 `StorageService` 并在入口停止时释放句柄。当前剧情入口只声明 `canonProjectKey` 依赖；现有代码中 `InstructionTable` 完全是内存对象。
为什么是问题：照字面实现时 `store.ts` 没有可用的 Storage 服务，三张记录既不能打开也不能在项目子进程落盘；即使另行从远程合同绕路，也违反 storage.persistence 的“项目记录只能经项目入口访问”和插件只依赖 `storageKey` 的合同。这不是测试遗漏，而是 F1 的实现前置不存在。
如何核实：对照 `packages/neuro-book/src/plugins/plot/backend/plugin.ts:219-226` 的依赖列表与 `docs/specs/storage/persistence.md:62-70,94-102`；实现 F1 后启动真实项目子进程，若不补依赖，入口不会得到 Storage 服务。
建议改法：在 F1 的切片契约中明确加入 `storageKey` 依赖、三条记录定义的共享位置、打开/读/写失败的返回映射和入口 scope 的收口；同时把 `plotProjectPlugin` 的依赖与测试场地的 storage 插件列入验收。

### 2. 三张记录的写入没有定义并发收口，`plot-chapters` 会丢更新
严重程度：重要；类别：不变量
位置：plan.md:831-839（F1），尤其 `ChapterTable.put` 的写入顺序
现象：计划要求先更新 `plot-chapters` 清单，再写 keyed 记录；只说“带 revision 的 save”，没有说用 `update` 重试、串行队列或按 revision 冲突重读合并。Storage 合同明确 `save` 是条件写入，同一 revision 的并发写入最多一次成功；而项目入口的远程方法可被 browser、tui、server 多个调用方同时调用。
为什么是问题：两个不同章节同时保存时都读到同一清单 revision，各自追加自己的章后 save，必有一个 `conflict`。若后一方不重读合并，清单丢一章；该章的 keyed 记录即使写成功，重启时不在清单中，`load()` 永久看不到。先清单后记录只能处理崩溃窗口，不能处理并发冲突。instruction、自陈、检查的不同表也需要避免同一进程内读改写竞态。
如何核实：用两个真实项目调用方同时 `putSelfReport` 两个不同章，令两次 list save 共用同一 revision；按 `docs/specs/storage/persistence.md:109,113,127`，观察一个 save 返回 `conflict`，随后重启项目并检查丢失的章。
建议改法：把清单更新做成 `handle.update(current => ...)`，或在 `ChapterTable` 内按存储合同串行化并在 conflict 后重读合并；记录写成功而清单写失败时还要有可恢复的重试/重建策略，不能把“清单多一章”当成所有部分失败的处理。

### 3. F1 在激活期间串行读完整项目记录，既没有上限也没有降级
严重程度：重要；类别：正确性 / 性能
位置：plan.md:835-839（`load()` 与“读完再 register”）
现象：计划要求入口激活时从清单逐章读三张 keyed 记录，全部读完后才登记完整诊断；没有列出并发读取、总耗时上限、取消、`unavailable`/`busy`/`io-error` 的状态或重试策略。Storage 没有列举接口，因而每章至少需要一次 `read`，并且每个方法都是 Promise。
为什么是问题：记录数量随章数增长，激活时间无界；单个分区锁、IO 错误或中止会让项目入口长期处于 activating，期间 `canon` 仍只有静态声明而没有剧情计算，结果是 `diagnostic-unavailable`，并且所有依赖这个项目入口的远程调用都等待或失败。计划把“读完后再 register”当作一致性措施，却没有说明激活失败后怎样恢复、怎样释放已经打开的句柄。`runtime` 的 10 秒上限只约束激活期远程调用，不是对任意本地插件 `activate` 自动提供的总预算，不能替代本计划的生命周期设计。
如何核实：在真实项目子进程中准备大量章节记录，并让 Storage 分区返回 `busy` 或让某次 `read()` 挂起；观察 `plot` 项目入口一直不完成激活、`canon.pending` 将该诊断列为未登记。对照 `docs/specs/storage/persistence.md:92,106,141,157-162` 与 `docs/specs/runtime/plugin-channel.md:95-97`。
建议改法：明确一次性加载的可取消、可恢复协议和失败状态；至少并行读并设总 deadline，记录未加载状态，或把持久化形状改成一个可原子加载的索引/快照。若坚持“未完整加载不注册”，要定义项目入口怎样在失败后重试而不阻塞整个项目。

### 4. F8 的指纹漏掉检查依赖的更早正文，旧讲述改稿会错误保留有效结论
严重程度：阻断；类别：正确性
位置：plan.md:885-897（F8 正文依赖与世界前缀）
现象：正文依赖只列“第 N 章、上一章、记录的试读材料列到的章”。但 `planCheck` 和它调用的函数会读上一章以前所有能定位的讲述：`readerKnowing`/`readerTellings` 判定上一章末尾的读者知情，`foreshadowIndex` 扫描有效讲述、伏笔节点和揭示，`composeBrief` 的读者段也依赖这些结果。更早章节的一句旧引文被删或改掉，即使它不在试读材料清单里，也会改变候选、试读资格、材料节点集合或固定调用输入。
为什么是问题：F8 的核心承诺是“依赖没变才直接复用；摘要只能多算不能漏”。该改稿不会改变 N 章、N-1 章或本次试读材料列出的章，却改变 `tellings({effective:true})` 的定位和读者状态；指纹不变，`validity` 直接沿用旧结论，违反 `checks.md` 输出 7 对“重新圈候选、重新拼每次输入”的合同。
如何核实：先在第 3 章写一处 `explicit reveal`，以第 12 章跑一条已有记录；再删掉第 3 章原句并通知 `textChanged`。若第 3 章不在该记录的试读材料列，按 F8 当前依赖应判 fingerprint 未变，但 `readerKnowing`/`readerTellings` 的结果已经变了。
建议改法：把所有参与 `readerTellings`、`ForeshadowIndex`、`firstReveal`、`composeBrief` 读者段的正文快照纳入摘要，至少按“截至检查位置的全部讲述所在章”滚动摘要；更简单的是使用 canon 的整份正文快照摘要，先量测后再做安全的分片。

### 5. F8 的世界范围没有覆盖补叙位置，`framesOf` 可把读取位置换到另一章
严重程度：重要；类别：正确性
位置：plan.md:842、853-857、888-895；现有 packages/neuro-book/src/plugins/plot/core/brief/context.ts:22-39
现象：`framesOf` 在 `timeMode.flashback` 时把 frame.position 改成补叙安放所在章的章首或初值；`composeBrief`、`pointsBeforeWriting`、`origins`、计划状态和涉及决策都可能从这个位置读。F8 的世界依赖却只取“段的线的视图上不晚于 N 的变更”，并把章 N 当边界，没有把补叙安放位置的章、前史顺序和该位置对应的线纳入边界。
为什么是问题：同一章正文的写作指示改成补叙某处安放时，或者补叙目标章之前的世界发生变化时，固定调用材料会改变；当前 fingerprint 仍可能复用旧结论。反方向，若目标安放在 N 之后，实际读取的计划/字段也可能依赖 N 之后的变更，而摘要只到 N，直接漏依赖。输出 7 要求的是重拼输入，不是按正文章号近似。
如何核实：建第 10 章的补叙指示，目标安放在第 4 章；在第 4 章前插入一条改变简报条目值的变更，不改第 10、9 章正文及其普通前缀，比较 `composeBrief` 与 F8 fingerprint 的输入。再把目标安放换到第 12 章，验证当前“截至 N”的范围甚至没有覆盖读取位置。
建议改法：把每个 frame 的实际 `position`、线、目标安放及其前缀作为依赖边界；不要用 N 代替 `frame.position`。计划还应明确同一检查记录中多 frame 的世界依赖取并集。

### 6. 多段章的按章检查错误地只用第一段的线
严重程度：重要；类别：正确性
位置：plan.md:875-879（F6“只按章的…在这一章第一段的线的视图上报”），F3:855-857
现象：Spec 输出 11 要求一章可以多段讲多条线；在场、叙述、伏笔物件、时间按段做，但固定调用、读者层按整章做。按章的规则项还包括涉及本章的已定/待定决策。计划却规定按章的诊断全部在“第一段的线”上算，并且 F3 的 `involvedDecisions(view, chapter, ...)` 也只写了单个 view。现有 `involvedDecisions` 对剧情线决策和 chapter entries 按传入线过滤，不能用第一段线代表其它段。
为什么是问题：第 2 段所属线上的计划、参与者或剧情线决策不会进入第一段线的 `view`; 固定调用既缺题面规则，也不会报出对应的约束/未定决策。读者知情本来不分线，若 `revealTable`/`readerKnowing` 随 segment view 扫描，还会反过来漏掉其它线的揭示。键中虽然有些诊断没有 line，但这不允许静默丢掉其它段的输入。
如何核实：用一章两段，第一段 main、第二段 r1；只在 r1 放一条涉及本章的待定决策或约束，运行计划的固定调用/诊断并检查题面与 `decidedInText`/`constraintViolated` 是否出现。再把唯一的 explicit reveal 放到另一段线，检查试读资格是否仍能看到。
建议改法：固定调用的章节级输入取所有 frame 的并集，按“决策/条目/线”去重；章节级诊断按全章视图或明确的多线合并规则算。读者层使用不分线的活页夹讲述视图，不要借用第一段的世界线。

### 7. 成功写入检查记录后没有明确让 canon 使诊断缓存失效
严重程度：重要；类别：不变量
位置：plan.md:831-839、859-866、875-879；现有 packages/neuro-book/src/plugins/plot/backend/plugin.ts:242-252 与 packages/nb-canon/src/service/service.ts:371-375、728-734
现象：F1 说三张表有数据版本，F4/F6 说检查记录和自陈落盘，但计划没有规定 self-report/check 的每次成功写入调用 `canon.reportDataVersion(plugin, dataVersion)`。现有剧情入口只在 `plotInstructionsContract.put` 成功后报告 `instructions.dataVersion`；而 `WorldService.#groups` 以读取输入摘要缓存 pending 结果，数据版本变化才会让缓存失效。
为什么是问题：检查记录从 none 变 valid、旧记录替换、self-report 改动或记录被删除后，如果不报告新数据版本，`canon.pending` 会命中旧的 groups cache，继续返回旧的 stale/possibleSlip/earlyReveal 结果。即使 `ChapterTable` 内存值已更新，诊断计算不会再次调用。这个缺口也会让“记录有效性读的是当前表”在实际服务上不成立。
如何核实：真实项目中先读一次 `pending` 建缓存，再经 `run` 写入一条检查记录，立即再次读同位置 pending；观察没有 `reportDataVersion` 时世界服务仍按同一 inputDigest 返回第一次的结果。对照 `WorldService.reportDataVersion` 的失效逻辑。
建议改法：把三张表封装成带变更回调的 store，所有成功的 put/remove/reset（包括 self-report、check、instruction）统一在写入成功后报告同一新的数据版本；把回调和注册/停止的寿命写进 F1/F4 合同，并测试“先读后写后读”。

### 8. `nbook.plot/model` 没有给模型请求设 1 MiB 边界，远程合同会在超限时断链
严重程度：阻断；类别：接口与合同 / 安全与性能
位置：plan.md:868-874（F5 的 `nbook.plot/model`）；docs/specs/runtime/plugin-channel.md:47-50、117；plan.md:853-856（F3 的整章材料）
现象：F5 的 `ask` 输入只列 `role、system、user、schema、maxTokens`，没有对 system/user/schema 的字节总量、单字段长度或序列化后的工具声明设置上限，也没有在项目侧调用前做预算。F3 的固定调用明确携带整章正文和简报，远程链路单消息上限是 1 MiB；通道超过上限不是一个剧情业务码，而是链路层断开/在途请求失败。
为什么是问题：长章、长细纲、多个节点材料或较大的 TypeBox schema 会让项目到服务端的 `ask` 帧超过上限。一次检查可能已经并发发出其它请求，部分调用成功并产生费用，剩余请求以链路失败结算；F4 只定义 `plot-check-failed`，没有说明如何区分可重试的传输失败与确定的输入过大，也没有办法让作者知道是材料预算而不是模型不可用。把 `plot-check` 记录的 1 MiB 上限当作模型请求上限也不成立：记录不保存请求原文，而且远程帧还有协议字段开销。
如何核实：用真实项目子进程把一章正文/简报构造到 1 MiB 以上，经 F4→F5 的真实进程间链路调用，观察 `encodeJsonFrame`/RPC 以链路失败结算而不是返回一个声明的 `too-large`；再确认同一检查的其它并发调用可能已经到达本地端点。
建议改法：在共享合同和 `CheckModels` 端口中定义按 UTF-8 编码的请求预算，项目侧在发远程调用前按同一序列化规则拒绝或按 Spec 允许的材料裁剪；F5 对编码后的请求再做边界保护并返回声明的业务码。为每种材料定义截断/失败结果，不能让协议层断链充当输入校验。

### 9. F4 对所有模型失败盲目重试，会重复收费并破坏取消语义
严重程度：重要；类别：正确性 / 安全与性能
位置：plan.md:859-866（F4 `runCheck`）与 plan.md:868-871（F5 返回 `retryable`）
现象：计划写“单次调用失败或结构不对时重试一次”，但 F5 明确把失败标为 `retryable`，F4 没有说只对 retryable 失败重试，也没有说在 signal 已取消、`auth`、`quota`、`context_overflow`、`unsupported-content` 等确定失败时停止。记录虽保存 usage，却没有定义一次逻辑调用的重试用量怎样累计。
为什么是问题：一次已经发出 HTTP 请求且返回 `quota` 或上下文超限时再发第二次没有恢复可能，反而重复计费；调用方停止或用户取消后仍可能进入重试，违背模型端口的 aborted 合同和远程调用的取消传播。若只保存第二次 usage，费用记录少算；若累加，又需要明确重试是否算一次调用还是两次调用，当前记录形状没有这条规则。
如何核实：让本机真实 OpenAI 兼容端点第一次返回 401/429/502、并在第一次调用中 abort；观察 F4 是否发第二个请求。对照 `docs/specs/harness/models.md:57-68` 的失败分类、`complete:false` 与中止规则。
建议改法：只对 `retryable: true` 且 `signal.aborted === false` 的失败重试；把一次逻辑调用的 attempts、每次 usage 与最终结算写入记录，或明确失败检查不存费用；重试前后都检查取消信号。

### 10. 模型通道没有写明把远程终止信号接到 `ModelPort.call`
严重程度：重要；类别：不变量
位置：plan.md:870-873（F5），plan.md:861-866（F4）
现象：远程合同实现的 `ask` 必须接收 `RemoteMethodContext` 的终止信号，但计划只说“call 后取工具参数”，没有规定把调用方取消、项目入口停止、服务端入口停止的 signal 传给 `resolution.call(request, signal, onDelta)`。`ModelPort.call` 的 signal 是模型适配器中止 HTTP 请求的唯一合同入口。
为什么是问题：项目停止或 `run` 超时后，RPC 可能已经结算，但服务端若继续用一个永不终止的 signal 调模型，会继续占用模型请求和用量；项目侧随后重跑还可能与旧调用并发。反过来只在远程层取消而不让 OMP 收口，也不满足 harness 的资源释放不变量。
如何核实：在真实项目→服务端→本机假端点链路中让端点保持请求，停止项目入口或取消 `run`；检查端点请求是否收到 abort、`ask` 是否在停止前结束，以及 F4 是否把该次检查标为未保存失败。
建议改法：F5 明确使用 `context.signal` 传入 `call`，不创建永不结束的替代 signal；F4 用同一个 signal 管理并发 worker、禁止取消后的重试，服务端入口停止时等待已接纳调用按 runtime 的收口规则结算。

### 11. 分段候选没有定义“变更归段”的完整规则，跨段讲述会产生漏问或重复问
严重程度：重要；类别：正确性
位置：plan.md:840-849（F2），尤其 `segmentsOf`、`candidates`；docs/specs/plot/checks.md:85
现象：计划只给出段的范围、`inSegment(segment, quote)` 和候选 id 的形状，没有规定一条已写变更有多个正文讲述且这些讲述落在不同段时，变更如何分别归段；也没有规定没有正文讲述、讲述失联、同一段多处相同引文和引文跨段时的归属。现有 `change-index.ts` 只按章和讲述所在章建索引，不按段建立归属。
为什么是问题：输出 11 要求在场/叙述/伏笔物件/时间按段执行，且引文必须落在该段。一条变更在段 A 有 `present` 参与者，在段 B 还有另一处正文讲述时，按变更对象归一段会漏掉一个段的候选；按每个 telling 复制又必须定义去重键和每个段的题面。没有正文发生点的变更按计划要求“归这条线的每一段”，也不能由当前的章级索引直接得到。后续实现者会在“按变更归段”上各自做不同决定，进而改变候选、预算和稳定键。
如何核实：构造一章两段同线，给同一已写变更两条 `told`，分别引用两段；再构造一个无正文发生点但有参与者的变更。比较两段候选是否各有一条、`budgeted` 是否只计一次，以及答案引文是否能在对应段核对。
建议改法：在 F2 明确归属函数：每个可定位正文 telling 按 occurrence paragraph 加入其段；无定位 telling 按 Spec 归入该线的每个段；同一段同一知识点/人按候选 id 合并，跨段保持不同候选；失联 telling 不制造正文候选，必要时单独列出未覆盖原因。

### 12. F8 写入了一个未经批准的 20 ms 目标和异步“验证中”状态
严重程度：建议；类别：代码质量 / 安全与性能
位置：plan.md:897-898、938-944；docs/specs/canon/project.md:104-108、120-121；docs/specs/plot/checks.md:69-70、89-95
现象：F8 把“读待处理不多过 20 ms”作为剧情负载预算，并在超过 1 秒时计划返回 `verifying: 1`，后台继续校验，完成后通过 `reportDataVersion` 切换到准确结论。现有 Spec 没有 `verifying` 状态：检查记录只有 none/valid/stale，过期时只报 stale；canon 的 200 ms 是单个插件诊断耗时标记，不是整个 pending 读的 20 ms 预算。
为什么是问题：这把全书重拼的成本转成了一个新的可观察状态，却没有定义后台任务的取消、项目入口停止、多个章同时验证、验证失败、报告版本与 `validity` 结果之间的竞态。更重要的是，20 ms 测的是包含内核 pending 与所有剧情诊断的整体调用，而 scale-e4 的同口径读待处理中位 204 ms，剧情诊断合计 112 ms；不能把该数字当成 F8 自己的预算或把低于它当成已满足 Spec。
如何核实：按 `scale-e4.txt` 的负载分别量一次完整 `pending` 和只调用 `validity` 的耗时；同时启动两个章的后台验证后停止项目入口，检查是否仍会调用 `reportDataVersion` 或把已释放表写回。对照 `canon.model` 的同步诊断合同和 `checks.md` 的三态表。
建议改法：先按现有 Spec 只实现同步的 stale/valid 判定，量清“完整 pending”“剧情诊断”“F8 fingerprint”三项；若确需后台分片，先补 Spec 的状态、数据版本、取消与最终一致性合同，再实现，不要在细计划里预埋 `verifying`。

### 13. F1 要求“坏记录写诊断”，却没有声明诊断服务或定义诊断落点
严重程度：重要；类别：接口与合同
位置：plan.md:831-839（F1 `ChapterTable.load`）
现象：F1 规定 `load` 读到 `corrupt`/`unsupported-version` 时写一条诊断并按没有算，但阶段 F 的入口依赖清单没有列 `diagnosticsKey`，当前剧情项目入口也没有 diagnostics 服务；Storage 本身只把状态作为 `RecordSnapshot` 返回，不替调用插件写运行时诊断。
为什么是问题：照字面实现要么无法调用诊断服务，要么把存储损坏静默当成“没有检查/没有指示”，重启后作者看不到数据为何消失。若把它伪装成剧情 `hint`，又会把存储故障混进 `CanonReadView` 的同步诊断，改变 `checks` 的数据版本语义。Storage 合同还区分 `corrupt`、`unsupported-version`、`error`；计划只说坏记录，没有定义 `error`、`unavailable`、`protected` 的可观察结果。
如何核实：对真实 `.nbook/storage.sqlite` 写入一个 JSON 合法但 schema 不符的 keyed 记录，启动项目插件；按 `docs/specs/storage/persistence.md:83-88,106-110,162`，Storage 只返回 `corrupt`，而 `plotProjectPlugin` 当前没有 `diagnosticsKey` 依赖可报告该事件。
建议改法：明确这是 runtime diagnostic 还是剧情提示；若是 runtime diagnostic，F1 增加 `diagnosticsKey` 依赖、稳定事件码和错误详情脱敏规则；若按缺失恢复，则把损坏状态留在 `ChapterTable` 与数据版本中，并在 `record`/`status` 公开，不要写成正常缺失。

### 22. FS1 把已批准的“重拼模型输入”改成保存写手上下文，不能由计划自行决定

### 23. 全量加载所有章节记录的激活期成本仍未按增长口径量化
严重程度：重要；类别：安全与性能
位置：plan.md:839-848、907、925
现象：第二版把 `load()` 定为入口激活时读取清单中的每章三张 keyed 记录，并以“窗口几百毫秒”作为经验描述，但没有给章节数、记录大小、并发读取数或最坏 Storage 锁等待的测量口径；F8 只量检查诊断和激活耗时，没有把 F1 的加载作为独立规模项。Storage 没有列举接口，所以记录数线性增长，且每项都是异步 `read`。
为什么是问题：在 1000 章、每章三份接近预算的记录时，启动要把数百 MB 的 JSON 交给内存和校验；一次项目入口激活既阻塞剧情服务可用，又把所有历史答案当作常驻状态。项目内路线没有 10 秒远程调用上限，并不等于没有资源/停止边界；当前计划没有说明停止中如何取消 load、部分已读结果如何释放、或重启后如何重试 `busy`/`io-error`。
如何核实：按 F8 同一台机器分别测 100、1000、5000 章，三张表取 1 KiB、64 KiB、接近 1 MiB 记录三档，记录 `load` 总耗时、峰值堆、Storage 读次数与项目入口激活耗时；在 load 中途停止项目，检查入口是否能收口。结果按“章数 × 记录字节数”分开，不把 F8 的 pending 读混入。
建议改法：把 F1 加入独立的激活规模预算和取消/恢复合同；至少并行受限读取、对历史记录使用摘要/投影而不是全文常驻，或重新评估把表合成可流式加载的快照。若确认必须全量读，也要把实测上限和超过上限的失败码写进计划，而不是用“几百毫秒”作未验证前提。

### 24. 试读仍可从原文材料直接看到命题或真相，当前隔离测试只检查程序添加的文字

位置：plan.md:858-865、927；docs/specs/plot/checks.md:62-66
现象：第二版为程序添加的材料标注去掉章 id、标题、线名、段身份，并把读者问题含名字/别名时跳过；但试读材料仍是 `readerNodes` 选出的原文段落加上一章与本章全文。计划没有对这些原文做“命题/真相”检查或遮蔽。原文可能直接写出 K 的命题、K 的答案名字、同义表述或另一处明说；“程序加的部分没有命题、名字、别名”这个测试不会覆盖原文自身的泄露。

如何核实：构造一个悬念 K，早于揭示计划的节点段直接包含 K 的命题或答案名字，但没有 `reveal` 标注；把该段纳入 `readerNodes`，检查 F3 生成的 `user` 是否仍包含原句。再在上一章全文写出同一命题，验证全文路径也能泄露。
建议改法：在试读计划里定义原文材料的泄密检查和处理：能确定的命题/答案文本拒绝该 K 的试读并给 `noReaderQuestion`/新提示，不能安全判定时不要声称满足 Spec；或经开发者批准改成不提供会泄密的原文。测试必须分别断言程序添加部分和原文材料部分都不包含命题、id、答案及可用的名字/别名。
