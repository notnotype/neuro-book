# 世界引擎的存储方案

2026-11-02 主会话起草，开发者同日按推荐确认了文末四条（“可以，没问题”），长期决定写成 [ADR 0039](../../../../../docs/adr/0039-world-engine-segmented-revision-log.md)。依据：已接受的[内核提案](../../../../../docs/proposals/world-engine-kernel.md)（下称“提案”）、[ADR 0037](../../../../../docs/adr/0037-world-engine-story-change-log.md)、t16 第 3 轮原型的类型（[`r3/model.ts`](../t16-plot-workbench-ui/artifacts/review/r3/model.ts)）与 Work README 决定表里 11-02 的各条决定。规模数字见 [`evidences/log-scale.txt`](evidences/log-scale.txt)。

## 一句话

每部作品一份**只追加的修订日志**，是按大小分段的文本文件，一行一次修订，是世界模型唯一的真相源。打开作品时在项目进程里把它重放成当前的六种对象，之后的折叠、查询、检索都在内存里做。不用数据库，条目不做成文件，第一版也不开放 Agent 直接改文件。

## 1. 六种对象放哪：都在修订日志里

**现在的模型已经是一份日志。** 修订（`Revision`）存着每个操作的改前和改后：新建存整份，修改只存变了的字段，删除存整份旧值（11-02 定）。所以把全部修订按顺序重放一遍，就得到当前的条目、剧情变更、核对点、未决问题、正文建议。六种对象不必再各存一份“当前值”；如果再存一份，两份就要一起原子更新。

| 方案 | 原子发布（一次修订改好几个对象） | 打开与查询 | Git、同步盘、外部查看 | 结论 |
|---|---|---|---|---|
| **A. 修订日志是只追加的文本文件（JSONL，按 256 KiB 分段），当前状态在内存里重放** | 追加一行就是提交；写一半的末行在打开时识别出来丢掉 | 百万字约 6 MB，读入、解析、重放共 25 到 40 毫秒；三百万字 65 到 120 毫秒（参考机器实测） | 只在末尾加行，Git 看得到每次修订；旧段不再变，每次提交只多存最后一段；放在同步盘里最坏是末尾一行没同步完，能识别；能用文本工具查看 | **推荐** |
| B. 同样的日志放进 SQLite 的一张表 | 事务自带 | 一样快 | 二进制，Git 只能看到“文件变了”；SQLite 放在坚果云、OneDrive 这类同步盘里有损坏的已知风险 | 备选 |
| C. 六种对象各存成文件（一个条目一个文件、一章的变更一个文件），修订另存 | 一次修订要同时改几个文件，得自己做预写日志，等于再写一个数据库 | 文件多，打开要读几千个 | 好看，但外部一改就绕过了修订 | 不推荐 |
| D. 六种对象各一张表（旧 WorldEngine 的做法） | 事务自带 | 要迁移、要建索引 | 同 B | 不推荐：表结构跟着模型改，模型还在变 |

推荐 A，理由按分量排：

1. **作者的数据最怕坏。** 写手常把作品放在同步盘里。只追加的文本文件即使被同步工具弄出冲突副本，也能看懂、能恢复；同步工具在写入途中复制 SQLite 库、或把 `-wal` 文件和主文件分开同步，得到的是损坏的副本（SQLite 官方文档《How To Corrupt An SQLite Database File》列了这类情况）。
2. **没有要数据库才能做的查询。** 百万字约 6600 条剧情变更、185 个条目（按每章 15 条情节估，比 t16 原型第 2 章多一倍）。全部在内存里：按章、按条目、按剧情线的索引在重放时建好；关键词检索扫一遍几千条变更描述，按重放的速度估在毫秒级（没单独量）。提案第一版的检索只要关键词，语义检索要嵌入，那是派生数据（第 5 节）。
3. **和仓库的同类做法一致。** nb-story 的书库是 JSON 文件；提案定了“日志只有一个写者、所有写入在项目进程里排队发布”，单写者正好对应只追加。

A 要自己做三件事，都不大：

- **写一半**：一次修订写成一行，带换行，写完 fsync（实测中位约 0.7 毫秒）。打开时最后一段的末行不完整或解析不了，就把这段字节另存到旁边、截掉、进诊断；中间的行坏了（手改、合并出错）就只读打开到坏行之前，报出第几行，不写入。
- **两个进程**：项目子进程是唯一写者；为防两个 NeuroBook 实例开同一个作品，追加时持跨进程锁（仓库已有 `holdLock`），并核对文件长度还是自己上次读写后的长度，不是就重读、按版本判冲突（提案第 5 节“并发”的同一口径）。
- **版本连续**：每行带版本号，必须比上一行大一，跨段也一样；Git 合并两个分支的日志会出现重号，打开时报错，不自动合并。第一版不支持分支合并。
- **分段**：当前一段超过 256 KiB 就开新的一段，文件名是这一段第一个版本号（`000913.jsonl`）；旧段不再写。理由见下面“硬盘”。

**硬盘**（[`evidences/disk-growth.txt`](evidences/disk-growth.txt)，文字字段用样本书原文，压缩率接近真实）：

- **日志本身不大**：百万字约 6.3 MB，gzip 后 1.1 MB；同样字数的正文 UTF-8 约 3 MB，日志约是正文的两倍。
- **不进 nb-history**：`.nbook/` 是控制目录，文件服务不列出、不读写（[`workspace/files.md`](../../../../../docs/specs/workspace/files.md)），日志由世界引擎直接写，和 `storage.sqlite` 一样属于“不经 nbook.files 的应用数据”（[文件访问与改动记账](../../../../../docs/proposals/file-access-and-history.md)）。如果经文件服务写，nb-history 每次修订都会存一份全文快照，它不做增量压缩。日志本身就是改动记录，不需要再记一遍。
- **Git 是唯一的大问题，分段解决**：只追加的单个文件，每次提交都存一份整个文件的压缩副本。每记完一章提交一次，百万字 330 次后 `.git` 是 274 MB，三百万字 1000 次是 2.5 GB；手动 `git gc` 以后只剩 1.4 MB、5.8 MB，但作者一般不会去跑，Git 默认要攒到约 6700 个零散对象才自动打包。按 256 KiB 分段以后，旧段不再变，每次提交只多存最后一段：百万字 13 MB，三百万字 41 MB。段数是 26 段、77 段，打开时多读几十个文件，可以忽略。B（SQLite）在这一点上不会更好：每次提交存整个库文件（没量）。
- **同步盘同理**：单个文件每次修订都变，同步工具如果不做块级增量，就要重传整个文件；分段以后只有最后一段在变（各家同步工具的行为没有逐个核实）。
- **缓存**：语义档的归纳是几句话一条，很小；以后的语义检索嵌入，按 6600 条变更、每条 1024 维浮点估算约 27 MB（百万字），放 `cache/`，可以删。

已知代价：

- **删掉的东西还在日志里。** 删一个条目，它的整份旧值留在那次修订里，这是还原要用的。要彻底清除（例如把作品发给别人前去掉草稿设定），以后做一个“重写日志”的工具。
- **内存**：当前对象加全部修订都放在内存里，实测百万字约 14 MB，三百万字约 42 MB（[`evidences/engine-scale.txt`](evidences/engine-scale.txt)），不用只记偏移。

## 2. 条目与 `lorebook.content/`

**推荐：条目不是文件。条目树（父条目、文件夹、顺序）就是条目上的字段，在日志里；由世界引擎自己的设定树显示（t16 原型的左栏），不在资源管理器里。**

- 主 MDX 按块存在条目的状态里（`text: [{id, source}]`），块 id 跟着块存，不写进正文，所以也不需要块标记。
- 条目的标签页是提案已经列为要先做的“带参数的虚拟文档”（每个条目一个地址，可以多开、拆分、刷新后恢复）。这一条原本写着“主 MDX 若定为文件，按文件认领能承接一部分”；不做文件以后，全部要靠虚拟文档（t16、t28 的范围）。
- `lorebook.content/` 不再是条目的家。内容文件夹仍是通用功能，作者可以拿它放资料、手记；新建作品的模板（t12）不再建它。旧项目的 `lorebook/` 由迁移（t13）读进来变成条目。
- 理由：作者经界面改，不直接编辑条目文件夹（11-01 定）；条目的样子随位置变，一个文件只能放初值，Agent 读文件会把初值当成现在；改了文件还得再读回来，就是下一节那条路。

**另一种读法：渲染出来的只读文件视图（开发者 11-02 提出，做不做由检索实验定）。** 把条目按某一个位置（默认最新记完账的那一章末尾）用带值写法渲染成文件，每个条目一个，每章的情节一个，Agent 用 read、grep、glob 读。它是派生数据，可以删除，不是真相源，所以不影响上面的结论。

- 好处：模型用 grep、glob 很熟，比用自定义工具少出格式错误；外部 Agent 也能读。
- 要解决的：只渲染一个位置，往回看的场景（审早先章的细纲、改稿后重记）仍要用带位置的工具，读文件会读到“未来”；每次修订后重渲染改到的条目（整份重渲染，百万字约 0.13 秒，三百万字约 0.4 秒，按章留中间结果以后只渲染改到的）；Agent 的写入工具要拒绝这个目录；视图不能放在 `.nbook/` 下（控制目录，Agent 的文件工具经文件服务读不到），要另找位置；产品 Agent 先要有 grep、glob（w00032 t12）。
- 检索实验：用“回指”出题（第 N 章里依赖前文的细节，答案是它在前文或条目里的位置），比较只用世界引擎工具、只读文件视图、两者都给三组，量找全、找错、读错位置、工具调用、token 与费用。

## 3. 修订与改动记录

日志本身就是改动记录：一行一次修订，存谁写的、改了什么（改前改后）、发布时算好的“带来的变化”（11-02 定）。还原是在末尾再加一次补偿修订，不改写旧行。

正文、细纲、手记是文件，历史归 nb-history（`.nbook/history.sqlite`），与世界的修订各管各的。记账修订里引用正文用“章加原句”，不引用 nb-history 的版本。

章序的真相在活页夹的 `binder.xml`。世界引擎发现章序变了（包括它没运行时被改的），就在日志里记一次“章序调整”，存改前改后的章序：重算用日志里最新的章序，还原调整章序也就是还原这一次。

## 4. Agent 能不能直接改文件：第一版不做

提案第 5 节“并发”留了一条路：把条目导出成文件给 Agent 改，旁边放旁车记录，导出的主 MDX 每块前有块标记 `{/* block:b7 */}`，改完按对象判冲突再读回来；并写明“具体格式随 t09 定；全放数据库时没有这条路”。11-02 的决定里也写了“所有写入（包括直接改文件）走同一条发布通道”。

**推荐第一版不做，Agent 改设定只经 `write` 工具；读的方式见第 2 节（工具，或渲染出来的只读文件视图）。** 这改了 11-01 的决定“直接读写文件暂时只留给 Agent”，以及 11-02 那条决定里“包括直接改文件”的前提，请开发者定。Agent 照样用文件工具读写正文、细纲、手记。

- **能力上不缺**：Agent 改一块文字用 `write` 的“把 A 换成 B”，和改文件时的字符串替换一样省 token；读和找有 `read`、`search`，比读文件多了位置与来历。
- **省掉一整套机制**：导出、旁车、块标记、监视、按对象判冲突、“有未导入的改动”这个状态和它的待处理，都是同一份数据的第二条写入路径。开发者 11-02 提醒过架构里同类的东西有点多。
- **和已接受的项目文件底座一致**：底座把数据在库里的叫“虚拟型”，写入只走结构化的工具，“不接受改文本后解析回写”（[项目文件底座](../../../../../docs/proposals/project-file-foundation.md) 第 1 节）。
- **代价**：在作品目录里直接跑的外部 Agent（Claude Code、Codex 这类）看不到设定。要时以后加一个只读导出（按当前位置渲染成 Markdown 放进临时目录）或命令行，不影响日志格式。

## 5. 派生数据

| 数据 | 放哪 | 丢了怎样 |
|---|---|---|
| 当前对象、按章与按条目的索引、各位置的折叠结果 | 只在项目进程的内存里：按章留折叠的中间结果（见下） | 打开时重放，百万字 25 到 40 毫秒，再整本折叠一次；不存到磁盘 |
| 语义档的归纳（`reductions`，键是输入的摘要） | `.nbook/cache/reductions.jsonl`，只追加 | 可以删，删了要重新调小模型；同样的输入重新归纳出来的字可能不同，稳定性由 t26 量 |
| 关键词检索 | 不存，内存里扫 | — |
| 语义检索的嵌入（第一版不做） | 以后放 `.nbook/cache/` | 可以删，重算要花嵌入费用 |

归纳结果不写进日志：它是从日志算出来的，写进去会让每改一笔事件都多一次修订。

**折叠不能每次从头算**（[`evidences/engine-scale.txt`](evidences/engine-scale.txt)）。t16 原型每次都从初值把整本书折叠一遍：

- 折叠到书末：百万字约 0.1 秒，三百万字约 0.3 秒（原型原样 0.85 秒），随变更条数线性增长。作者翻到一章、Agent 读一次、算待处理、渲染文件视图，每次都要付这一笔。
- 发布一次记账：原型要复制整个世界，再在发布前后各折叠一次，比较出“带来的变化”。百万字约 0.7 秒，三百万字约 2 秒。

所以内存里要按章留折叠的中间结果：

- 每章末尾只留这一章改到的条目，其余与上一章共用；
- 读第 N 章，从第 N−1 章的结果往下折叠这一章，按线性关系推算约 0.3 毫秒（没量）；
- 在最新一章发布，只重算这一章；改早先的章，从那一章往后重算，最坏等于一次整本折叠。

这些中间结果是派生数据，不写到磁盘，不影响日志格式。它是内核实现要满足的性能要求，交 t27 写进 Spec，比如“三百万字时，读任意一章的一个条目、在最新一章发布一次，各在多少毫秒以内”，实现时再量。

## 6. 项目目录（原 t11）

```text
<作品>/
├── manuscripts.binder/      正文（剧情插件，已有约定）
├── assets/                  立绘、插图：普通文件夹，世界数据里按作品内路径引用
├── cover.png                封面（书架页，已有）
└── .nbook/
    ├── project.json         作品身份（已有）
    ├── world/log/           世界模型的修订日志（000001.jsonl …，按 256 KiB 分段）：唯一真相源，要备份，用 Git 的应该提交
    ├── history.sqlite       正文、细纲、手记的文件历史（nb-history）
    ├── storage.sqlite       插件 Storage：界面状态（已有合同）
    ├── cache/               可以整个删掉：语义档的归纳，以后的嵌入
    └── locks/               跨进程锁（已有）
```

- **要备份的和可以删的分开放**：`world/` 是作者的数据，`cache/` 删了只花钱重算。目录名直接说明这一点，不靠文档。
- **图片**：作者在表单里上传的立绘写进 `assets/`，世界数据里存作品内路径。项目文件底座定了普通文件没有稳定身份、不做引用维护，所以图片被挪走后显示“图片找不到”的占位，作者重选。
- **细纲**：是作者写的原文，按章一个文件，不进世界日志（计划记着来自细纲的哪句，细纲改了按原句重新定位，和正文的讲述同一套）。放在活页夹里还是旁边的文件夹，要动活页夹的文件名规则，随 t19 和剧情插件一起定。
- **手记**：作者随便放，世界数据里按路径加原句引用。
- **用英文目录名**，展示名交给清单与界面；`.nbook/` 下的名字作者看不到。
- **不替作者写 `.gitignore`**：用户文档里写清哪些该提交（作品文件、`project.json`、`world/`）、哪些是本机的（`history.sqlite`、`storage.sqlite`、`cache/`、`locks/`）。
- 旧项目里的 `AGENTS.md`、`agents/`、`manual/`、`reference/`、`upload/`：不属于世界引擎的存储，交 t12 定模板时再看（Profile 已移到状态根，w00032 t05）。

## 7. 系列作品（原 t24）

**第一版不做**，一部作品一个项目；一部里分卷用活页夹的分组（已有）。

以后要做时，推荐先做“接着上一部开新书”：把上一部最后一章末尾的状态复制成新书的初值（新书的第一次修订），两本书此后各自独立。跨作品实时共享一份设定库（放 `user://`）要处理两本书的位置怎么比、改了一边另一边怎么办，等有人要再说。日志的格式不妨碍这两种做法。
