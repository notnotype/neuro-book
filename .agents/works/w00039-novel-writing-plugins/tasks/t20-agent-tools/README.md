# Agent 工具与写手的上下文

## 目标与范围

定提案第 9 节六个工具（查条目、读、列变更、检索、看条目树、写入）的参数、条数与字数上限、错误；工具名加前缀，不和 harness 自带的读写文件工具撞名（11-02 定，缺口 8）；自动预查；Component 用法提醒的小扩展；写手的上下文怎么拼（原 t21，有字数上限、与书长无关）。

合同：讨论 Task，只定设计，行为合同未变；定稿后的 Spec 改动在实施时另定。

前置：t27、t19。

## 重切后要定的（2026-11-02）

1. 六个工具的参数与返回：位置参数的默认值、带值写法的回写请求（意图、多来源时的处理）、条数与字数上限与续读游标。
2. 名字：统一前缀（原型里写成 `world_lookup` 这类，只是占位）。
3. 自动预查与“不作为触发词”的别名。
4. 写手的上下文：本章计划与写作指示、涉及条目在本章开头的渲染、最近一两章、按需检索；字数上限。

## 10-31 的原问题

10-31 按“与 nb-story 合成一套故事模型”的方向写，原样保留作参照。第一组 1、2、3、6 条已由提案定（六个工具；作者不直接编辑文件夹；写入走发布通道、留改动记录）。

### 小说创作的 Agent 工具

1. 工具清单：查对象、读设定、写设定、记状态变动、查某时刻状态、查谁知道什么、读剧情、改大纲、查差异……数量多时怎么让 Agent 找得到（w00032 t04 搁置了工具发现）。
2. 设定是文件时，Agent 直接用 read、edit 改文件，还是必须走专用工具（专用工具能校验 schema、维护引用）。
3. 旧版 `execute_world`（CodeAct 沙箱）的教训：bigint 时间、日历字符串、两套问题码；新工具的参数怎么让模型少出错。
4. 防剧透与权限：写手只读；按阅读位置限制写手能看到的未来设定（见下面“写手的上下文”）。
5. nb-story 命令行与 Skill 已有一套查询接口，插件工具与它共用到什么程度。
6. 写入的审批与 History 记录（w00032 t06、t13）。

### 写手的上下文：章级 brief 与检索（原 t21）

1. 旧版 brief 的七段（章目标、参数、信息控制、节奏、禁写、剧情点、建议读取）哪些留；由程序编译、Agent 起草还是作者手写。
2. 按位置取上下文：只给写到本章为止的状态与已揭示的秘密，未来的计划给不给写手（给了容易提前写出来）。
3. 检索：按引用、按在场者、按名字匹配、向量检索（旧版 `EmbeddingText`）；要不要向量检索、索引放哪。
4. 前文怎么给：全文、摘要、nb-story 的章节变化；长篇写到几百章时的上限。
5. 旧版写手 curated 模式因工具在 Profile 定义期固定而延后；新 Profile 机制（w00032 t05、t20）下能不能做。

- 写世界在 `ask` 模式照旧每次问，`auto` 模式直接放行；
- 写手第一版只做按细纲写；
- 先后按五档。

开发者同时定：写手任务、记账管线先不考虑；现在最首要的是世界引擎的管理与记录；**Agent 这条线暂且不推**，先做作者一侧（主文字的编辑器 [t28](../t28-entry-mdx-editing/README.md)，再做人物设定组）。开发者举的四个例子与对照出的缺口（列全条目、改历法、人物关系的存放处、`canon_record`）记在工具地图里。

2026-11-26 在 [w00055 t01](../../../w00055-entry-rich-text/tasks/t01-demos/eval.md) 搭评测台时用真实工具证实一个缺陷：`canon_read` 的 `text` 给的是带值写法（`{panel.存款 = 300}`），`canon_write` 的 `replace` 与 `set` 却按源文字匹配，照读到的文字抄 `find` 得到 `replace-not-found`，回话没提读到的文字与源文字不同；工具说明里也没讲带值写法。主文字给 Agent 时带不带值由 w00055 的评测定，恢复本 Task 时按那边的结论一起改。
