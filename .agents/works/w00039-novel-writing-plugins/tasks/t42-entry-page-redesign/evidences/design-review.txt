[F3] 重要 / 并发与共享状态 / plan.md「PageNotices 自己收起」与 notices.ts
现象：6 秒计时、指着暂停放在 PageNotices 组件里（“三处宿主共用”），但提示的数据是窗口级一份（notices.ts `current`/`agent`，注释写明“切到另一个这样的页面时它跟过去”）。编辑区拆成两组、各开一个条目页时两个宿主同时挂着（`attach()` 计数就是为这个，notices.ts:96-105），各有一份 PageNotices、各有一个计时器：A 页的计时到点调 `notices.dismiss()` 会清掉窗口级的 `current`，B 页正被指着/焦点在里面也一起消失，暂停形同虚设。反过来切到别的标签时组件卸载、计时随之取消，`current` 还留着：回到条目页（哪怕一小时后）旧提示重新出现并重新计 6 秒。计划“notices.ts”整份没出现在改动清单里。
为什么是问题：违背“指着或焦点在里面时不收”（输出 18 新写法）与“同一时间只有一条”；陈旧提示复活；复本各自播报 role=status。
如何核实：读 notices.ts `show/dismiss/attach`；在 Lab 或 dom 测试里挂两个宿主、一个 hover、另一个到点。
建议改法：计时与暂停状态放进 createNotices（按 notice 的单调序号计时，暂停用窗口级计数，宿主只上报 hover/focus），到点时只收起“与当时序号相同”的那条；没有页面挂着时不计时。验收映射加“两个宿主同时挂着，一个被指着，另一个到点不收”“卸载再挂上不复活”。

[F4] 重要 / 可访问性与焦点 / plan.md「PageNotices」
现象：浮在滚动区下方、6 秒收起，里面有“查看详情”“撤销”按钮。键盘用户保存后焦点留在输入处（refocus 回到原值按钮），要 Tab 到浮层需要穿过整个页面（它在 DOM 里排在内容后面或前面均如此），6 秒内几乎不可能；“焦点在里面时不收”只对已经到达的人有用。`role="status"` 现在是 v-if 出现时才插入的元素（NoticeBar.vue:23），读屏对“新插入且带内容的 live region”常常不播报；计划说“外框不动原地换字”，没说外框常驻。撤销确认框关闭后焦点要回“撤销”按钮（notices.ts 注释 usePageNotice），若计时在对话框开着时只“暂停”、对话框取消后恢复计时但没有聚焦，按钮可能在焦点回来前被收掉。
为什么是问题：设计语言第 6 条“不打断人手上的事”要求不抢焦点，但必须给键盘一条不靠 6 秒的路；WCAG 2.2.1（可调时限）。撤销的另一条路是改动记录视图，但那是“多步”。
如何核实：读 NoticeBar.vue、notices.ts 末段 usePageNotice 的注释；真实页面上用键盘保存一次。
建议改法：外框（role=status 的容器）常驻、只换里面的文字；给一个命令/快捷键“撤销上一次保存”或让 Alt+某键聚焦提示，并在 Spec 输出 18 写明；对话框开着的判据用 RevertRequests.target（revert.ts 已有，可观察）而不是新造状态；确认框关闭回到按钮后再重新计时。

[F5] 重要 / 技术前提错误 / plan.md「不与风险：浮动提示挡住最后几行」
现象：计划用“滚动区的 scroll-padding”，“只在提示出现时加，不改版面”。scroll-padding 只影响 scrollIntoView/吸附的目标位置，不扩大可滚动范围；底部最后几行仍被浮层盖住、滚不上来。要让它们露出来只能在内容尾部加 padding-bottom/占位，而这正是“出现时改变滚动高度”。此外滚动区属于编辑组的页面容器（EntryPage.vue:128-170 的 scrollParent 注释：“本组件只量它、不改它”），canon 组件从自己的模板里设不了它的 scroll-padding。Agent 的提示又不自己收，会一直盖在每个条目页最下面；Spec 51 的“成段编辑层打开时整个滚进可见范围”（EntryPageHost.vue:872 `scrollIntoView({block:'nearest'})`）与它的“保存与取消”按钮会落在浮层下面。
如何核实：CSS 规范；读 EntryPage.vue 的 scrollParent 与 EntryPageHost.vue reveal。
建议改法：浮层作为 sticky 零高容器放在根的末尾，同时在根的末尾放一个与浮层同高的占位（在 PageNotices 内用 ResizeObserver 量，出现时过渡 height，不用 scroll-padding）；reveal 的 scrollIntoView 用 scroll-margin-bottom 让开浮层高度；计划里写明谁拥有滚动区。

[F6] 重要 / 缺口 / plan.md「其他状态」「positionGone 与 actionError 不再插行，分别走浮动提示与对应的浮层」
现象：(a) `positionGone` 是标签状态（state.positionGone，“留到作者再选一个位置为止”，EntryPageHost.vue:125-131），不是一次修订；PageNotices 吃的是 CanonNotice `{revision,title}`，按钮是“查看详情/撤销”，没有“无修订的文字提示”这种数据形状；而且 6 秒后收起与“留到再选位置”矛盾。(b) `actionError` 有四个来源（EntryPageHost.vue:408、484/488、695/699 以及 runEntries head）：别名写入失败、恢复失败（deleted 分支也用它，EntryPage.vue:178）、移动前读取失败、文字分页“开始写”失败。除名字简介（已有确认框里的 error）外，其余三个没有“对应的浮层”可去。Spec 43 还明说“页头下面只写页头自己的写入（别名、恢复）与打开对话框前读不到条目的原因”。
为什么是问题：计划把页内插行的两处“搬走”但没给去处，实施时会再变成临时方案；失败原因走 6 秒自动收的提示会让人没读完就消失。
建议改法：定义 PageNotices 的第二种条目“只读文字、无按钮、可带 tone”，错误不自动收（role=alert），positionGone 作为标签状态的常驻小标记（时间点旁，同“还没出场”），并在 Spec 43 与 38 改写。

[F10] 重要 / 与既有约定冲突 / plan.md「分页：竖排与横排按容器宽度切换」与 `wide`
现象：EntryPage.vue 已有 `wide`（主文字开预览时内容列放宽到 1560）和 `WIDE_MIN = 880 + 64`（EntryPage.vue:188-190，注释：放宽了但编辑视图还是上下排会让页头白白变宽一次）。竖排导航占内容左边约一栏（计划没给宽度），内容与页头的有效宽度被它吃掉，WIDE_MIN 仍按滚动区宽度判断：竖排开着时内容列只剩约 (滚动区 − 64 − 导航)，达不到 EntryTextEditor 要的 880 仍会放宽、仍上下排。另外阈值本身不自洽：内容净宽 760 + 导航（假设 168）+ 间距 + 内边距 64 > 960，则“约 960 以上竖排”时内容列在 960 到约 1010 之间小于 760；“多留 16 像素”是单阈值加余量，不是滞回，来回切时一个纵向滚动条的出现与消失（两种排法页头高度不同、内容高度不同）会让滚动区 clientWidth 变 15 像素，正好跨阈值，抖动。
如何核实：读 EntryPage.vue 的 `measure`、WIDE_MIN、column；估算宽度。
建议改法：竖排时 WIDE_MIN 加导航宽度；阈值按“内容 760 + 导航 + 间距 + 内边距 + 余量”算出；用 JS 滞回（已有 ResizeObserver）而不是纯容器查询，或滚动区设 scrollbar-gutter: stable。

[F16] 建议 / 隐含耦合 / plan.md「别名失焦时非空就加上」
现象：EntryPage.vue 的别名输入同时有 `@keydown.escape.prevent="adding = false"`、`@keydown.enter` 与 `@blur="adding = false"`。改成“失焦时非空就加上”后：(a) Escape 先把 adding 置假、输入被卸载，Chromium 在卸载聚焦元素时会派发 blur（需在真实浏览器核实），blur 里非空就加，于是“按 Escape 放弃”反而加上了；(b) Enter 的 commitAlias 与随后的 blur 各发一次写入，第二次被 `acting` 吞掉不报错但看着正常，换成快速点击时会错位；(c) 输入里有字时点另一个别名的“×”：mousedown 先触发 blur→提交写入（`acting` 置真），随后 click 的移除 `runEntries` 因 `acting` 直接返回 false（EntryPageHost.vue:421），移除被静默丢掉。
建议改法：用一个“已提交/已放弃”标志，Escape 先清空草稿再收起；blur 提交走与 Enter 同一个函数并去重；写入在途时排队而不是丢弃，至少给出反馈。

[F21] 建议 / 回车保存 / plan.md「回车不被吞」
现象：“预览等 300 毫秒时按回车，立刻发预览，回来没被拒就保存”。Spec 51 与 ConfirmBar.md 现在明写“按回车就是保存（预览回来以后）”，预览是作者保存前看到“写回哪里、带来什么变化”的一步；新做法让作者没看到变化就保存了（story 意图下影响条数可能是“还有 N 项”）。计划要改 Spec 51 是对的，但没有说明“没被拒”是否包含“有影响提示”，也没有处理：回车后立即预览期间世界版本又变了（in-place-edit.ts 的版本 watch 会换 `read` 与 requestId），以及回车触发后用户又改了值。
建议改法：写明保存的是回车那一刻的值，发保存前核对预览所基于的值与版本没变；影响多于一条时仍等预览显示。
