# Component 类型、字段与设定表单

## 目标与范围

定第一版内置的 Component（人物、面板、情节）与身份（马甲）的字段清单，以及字段怎么声明：类型、精确档还是语义档、会不会在正文里重述、约束与溢出、显示名与 id；字段预设（金钱、体力、等级）；schema 版本与升级函数；按 schema 由 nb-form 画出的设定表单（原 t15）与要补的控件（图片、引用、语义档字段的显示）；“记一笔”。

合同：讨论 Task，只定设计，行为合同未变；定稿后的 Spec 改动在实施时另定。

前置：t09。

## 重切后要定的（2026-11-02）

1. 人物：外观用一段文字还是拆成几项（发色、毛色）；本体只放原身外观，每个马甲放自己那个样子的外观（11-02 定）；“现在的样子”这类字段要不要内置。
2. 面板：哪些字段默认精确、哪些默认语义（开发者 11-02：游戏文要精确，大部分小说不需要确切的数）；作者怎么切换，切换时已有的加减与文字怎么处理。
3. 字段声明的写法：`precision`（精确或语义）、`retold`（会在正文里重述，改设定后要找旧写法）、`min`/`max` 与溢出策略、字段 id 由显示名生成后不变。原问题 1 的 JSON Schema 加 `x-form` 提示可以接着用。
4. 表单的编辑规则：在看到的样子上直接改，默认算改设定、写回给出这个值的记录；几笔累出来的数不直接改，在流水里改某一笔或补一笔（11-02 定）。
5. schema 演进：带确定的升级函数，旧数据与旧补丁在读的时候升级（提案第 6 节）。

## 10-31 的原问题

10-31 按“与 nb-story 合成一套故事模型”的方向写，原样保留作参照。第一组的 6 条（哪些字段会随剧情变化、引用怎么声明）已由提案定：所有字段都能由剧情变更改，引用写 `ref("id")`。

### 设定类型与 schema 演进

1. 写法：JSON Schema 加 `x-form` 提示（nb-form 直接用，不执行代码，Agent 能生成），还是旧版的 Zod TS（单文件、不能 import 是痛点）。
2. 放在哪：项目里（`lorebook.content/<类型>/schema.json`）、模板里、插件里；三层覆盖（内置、插件、用户、项目）要不要。
3. 内置哪些类型、各有哪些字段；用户自定义类型与自定义字段的上限。
4. 演进：加字段、改名、改类型、删字段时已有文件怎么处理（旧版不做版本化与迁移）；校验失败的旧文件怎么显示。
5. Agent 生成或修改 schema：走 nb-form 的 `policy: "agent"` 检查；Agent 改 schema 要不要审批。
6. 哪些字段会随剧情变化（接 t04），引用别的设定的字段怎么声明（接 t02）。

### 设定表单与设定库界面（原 t15）

1. 旧版其实有人物表单，用户仍觉得复杂：先弄清复杂在哪（字段多、要懂 frontmatter、两份状态、找不到入口），再定界面。能不能找到原始反馈。
2. 表单与文件的分工：结构化字段进 frontmatter、自由描述是正文；表单里怎么同时编辑两部分。
3. nb-form 要补的控件：引用另一条设定（可搜索的下拉）、图片（立绘）、随剧情变化的字段（显示当前值、点开看各章各线的变化）、标签。
4. 列表层面：卡片墙、表格（批量改字段）、按类型与标签筛选、搜索。
5. 新建设定的入口：表单、从正文选中文字创建、让 Agent 起草。
6. 表单与文件同时被改（Agent 写文件、用户开着表单）时的冲突处理。
7. nb-form 的 Spec 还是 `planned`，这里是它的大使用方，要不要一起推它定稿。
