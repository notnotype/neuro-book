# 简报的保密：一个关卡，不再逐处判断

## 目标与范围

写给写手的简报里，保密以上的名字与内容经一个关卡：每处写名字的地方不各自判断。处理 t34 第三轮实现审查（I12）里简报保密的 10 条，并让 plot/brief.md 晋升为 implemented

合同：[`plot/brief.md`](../../../../../docs/specs/plot/brief.md)（输出 4、5、8、9、13）；写法上的改变见下，Spec 里“主体是用马甲的人时写什么”要先由开发者定。

## 起因

t34 晋升前逐条核对时，简报三轮实现审查每轮都找出新的泄漏路径（[I11](../t34-plot-side-impl/evidences/impl-review-I11-opus.txt)、[I12](../t34-plot-side-impl/evidences/impl-review-I12-opus.txt)）。根因：每处写名字、写内容的地方各自判断“这个能不能写给写手”，漏一处就泄漏一处。开发者 2026-11-07 定：先晋升别的 12 份 Spec，`plot/brief.md` 留在 `planned`，保密单开本 Task。

## 要处理的（I12 的简报部分，复跑脚本在审查时的 `/tmp/review-w00039-t34-H/opus2/`，已不保证存在，以报告为准）

1. 涉及条目的样子：`maskRefNames` 只改 `<Ref>` 的文字，表达式注记里的名字照写（`{ref("e2").entry.name = …}`）；
2. 本章才出场（或之后才出场）的隐秘目标：`readGoal` 按出场筛，章首读不到，名字与状态变化照写；
3. 隐秘目标被删、隐秘指向已删的知识点：名字照写，同一份简报一边遮一边写；
4. “有一件涉及某某的绝密设定”的主体本身是隐秘目标或别的绝密知识点；
5. 到期的待定决策地址挂在绝密知识点上，原话写给写手；
6. 伏笔回收主文字被扣下以后，涉及条目的样子又给了整块主文字与答案引用；
7. 伏笔主文字里引用字段的值（`{fs.答案}`）写成 JSON 与条目 id，也没算进 `references`；
8. 图片标签原样留在纯文字里；
9. 用了马甲的人：除本章计划外各段照写本名，回溯章的称谓表写“灰袍客 = 王爷”；
10. 变异检查里还没抓住的用例（P5、P14）。

## 做法（推荐，开工前先写计划、审查）

所有写给写手的文字经一个关卡：每段拼完后，把要遮的名字（保密以上的知识点、要遮的隐秘目标、用了马甲的人的本名）集中算一份，扫一遍；渲染一侧给“引到了哪些条目”（`references`，表达式与字段值都算），不在文字上做替换。用 Spec 里的所有验收场景加上述 10 条做用例。
