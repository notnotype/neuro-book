### 1. 本章计划改“用马甲的本体”的名字、别名、简介时，原值与新值照写，本名直接写给写手
严重程度：阻断
类别：正确性 / 关卡被绕过
位置：packages/neuro-book/src/plugins/plot/core/brief/parts.ts:88-96（planItems 的值行）、parts.ts:34-37（fieldPhrase 的 ENTRY_FIELDS 分支）
现象：planItems 对 `entry.name`、`entry.aliases`、`entry.summary` 的补丁同样走 origins 取前后值，再经 `gate.value(string)` 原样写出。gate.value 对字符串直接返回，所以条目的名字、别名、简介作为“值”写进本章计划，不经 gate.name、gate.summary、gate.aliases。
- 王爷这一场用马甲灰袍客、揭穿是绝密，本章计划把王爷改名：本章计划一段写出“灰袍客的名字：王爷甲 → 摄政王戊”（exp3.test.ts 的 D）。本名与新名一起写出，还把两者对上了。
- 同一场景计划给王爷加别名、改简介：写出“灰袍客的别名：镇北王乙 → 镇北王乙”“灰袍客的一句话描述： → 先帝之弟丙”（exp1.test.ts 的 A）。
- 同理，身份不给写手的马甲条目的简介与别名，gate.summary/aliases 特意不给（输出 13，P2 第 10 条），本章计划改它们时照样整句写出。
为什么是问题：Spec 输出 16 的“名字”一条管“每一个条目的名字”，用马甲而身份是秘密的本体只能写马甲；输出 16 的“揭穿按组”写明本名只出现在给了内容的那一组真相与称谓表左栏。这里本名出现在本章计划。“字段里的字符串照写”说的是作者写的字段值，条目名、别名不在这条豁免里。这正是 t35 要堵的“各段各自判断”：值行把 entry.* 当普通字符串处理，关卡没机会判断。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp3.test.ts`（D）、`exp1.test.ts`（A）。
建议改法：fieldPhrase/planItems 遇到 `entry.name` 时值写 gate.name 的口径（kind 不是 plain 的条目不写名字的变化，或只写“改了名字”）；`entry.aliases`、`entry.summary` 在 gate.summary/aliases 给空的条目上不写值（只写“改了别名/一句话描述”或整行不写）。最好把“条目自己的三个地址的值”收进关卡一个方法（例如 gate.entryField(id, field, value)），planItems 不再自己判断。种子网与 gate.test.ts 各补一条：用马甲的本体与身份不给写手的马甲条目被本章计划改名、加别名、改简介。

### 2. 本章计划改主文字的一块（text[块]）时，把 MDX 源文、条目 id 与路径原样写给写手
严重程度：重要
类别：正确性 / 关卡被绕过（作者文字没经纯文字渲染）
位置：parts.ts:34-39（fieldPhrase：路径不匹配时写 `${owner}的${at.path}`）、parts.ts:91-96（值经 gate.value 原样输出字符串）
现象：内核允许剧情变更改主文字的块（nb-canon model/apply.ts:211 applyBlockPatch，set/addBlock 等）。planItems 不区分 `text[...]` 地址，取 origins 的前后值（块的 MDX 源文）经 gate.value 原样写出，地址写成原始路径。实测本章计划把怀表的 b1 改成引绝密知识点的写法，本章计划一段写出：
  怀表的text[b1]：表盖有划痕。 → 它和 {ref("e2").entry.name} 有关，<Ref id="e2" />。
（exp1.test.ts 的 B）。条目 id、块 id、`{ref(`、`<Ref` 都进了上下文；块里若用字面写了被引条目的名字，或用 `<Image>`，同样原样写出。
为什么是问题：输出 16 写明“每一块作者文字”都按 canon.rendering 输出 15 读、写不干净或写到占位条目的块不给，且“上下文里不出现条目、变更、章的 id 与 JSON”；种子网的判据也要求不出现 `<Ref`、`{ref(`。这一处作者文字完全没经关卡。种子网没造“计划改主文字”的补丁，所以没抓到。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp1.test.ts`（B）。
建议改法：planItems 对 `text[...]` 地址不写源文：只写“某某的主文字改了一块”，或把新值交给内核的纯文字渲染（块源文需要按那一刻的条目渲染，现有 renderPlain 按条目读，不收任意源文，可能要在内核加一个渲染单块源文的入口）再按 gate.blocks 的同一判断给或扣。fieldPhrase 的兜底不要写原始路径。生成器补“计划改主文字的块”这一类补丁。

### 3. 身份不给写手的马甲条目，别的条目用表达式读它的简介、别名，照给
严重程度：重要
类别：正确性 / 关卡内部判断不一致（summary/aliases 与 blocks 用的不是同一个判断）
位置：gate.ts:260-262（described：withheldMasks 里的马甲不给简介、别名）对比 gate.ts:287-297（blocks 只按 kind 判 reads，马甲条目 kind 是 plain）
现象：关卡在涉及条目的样子里不给“身份不给写手的马甲条目”的一句话描述与别名（P2 第 10 条：作者最可能在这里写出身份）。但另一个条目的主文字写 `{ref("马甲").entry.summary}`、`{ref("马甲").entry.aliases}` 时，reads 里是马甲，kind(马甲) 是 plain，块照给。实测马甲简介“其实是王爷甲的化身”、别名“王爷甲的影子”经怀表的主文字写进涉及条目的样子（exp1.test.ts 的 C，`C leak 王爷甲: true`）。

### 4. 伏笔回收的“答案能不能给”另做一套判断，与关卡的秘密种类不一致：秘密段说不给，伏笔段照给回收方式
严重程度：重要
类别：正确性 / 关卡不是唯一判断
位置：parts.ts:216（`secretAnswer = isSecretPlus(gate.secrecy(answer)) && !reveals.has(answer)`）
现象：伏笔段判断答案用的是“档位 + 本章计划有没有揭示”，不是 gate.secretClass。两者在“揭穿按组”时分叉：答案 A1 是揭穿灰袍客的绝密知识点，本章计划暗示它；同组还有一条保密档的 A2 不在本章涉及的集合里（不给内容），关卡于是把整组按不给内容处理。实测（exp5.test.ts 的 F）：

  伏笔：回收：灰袍客当众摘下兜帽，露出真面目。
没有 payoffWithheld 提示。写手一边被告知这是不能写出的绝密，一边被要求按主文字回收（揭面）。反方向同样分叉：答案是已删除的知识点（关卡算 withheld）、或是不给写手的那组揭穿里的普通档知识点时，secretAnswer 为假，回收主文字照给。

如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp5.test.ts`。

### 5. 揭穿组里有一条不在本章涉及的集合里，就压过作者在本章计划写的揭示；整组静默不给，没有提示
严重程度：重要
类别：过头的扣下 / 边界
位置：gate.ts:182（shown 只取 input.points 里的）、gate.ts:187-197（组里有一条保密以上不在 shown 就整组不给）
现象：shown 只从本章涉及的集合（pointsBeforeWriting 加参与者目标藏着的）取。揭穿同一个马甲的另一条保密档知识点 A2 若与本章参与者无关（例如主体是别人、没人知情），它不在集合里，于是“不给内容”，整组被扣：本章计划明确暗示 A1（“灰袍客就是王爷甲”）也只得到“有一件涉及灰袍客的绝密设定”，没有“只能写到：暗示”，也没有任何提示告诉作者为什么揭示没生效（exp5.test.ts 的 F 的秘密段）。
为什么是问题：保密档按 Spec 是“写手知道”的档，A2 只是因为没被集合选中就成了“不给内容”，结果把作者显式的揭示吞掉。这一场用了这个马甲，揭穿它的每一条都和这一场有关，集合漏选它们是集合的问题，不是作者要扣。作者看不到任何提示，只会发现写手没按计划暗示。
如何核实：同上，exp5.test.ts。去掉 A2 后 A1 正常给真相与“只能写到：暗示”（可以把 a2 那行注释掉再跑）。
建议改法：关卡里把这一场戴着的马甲的整组揭穿并进本章涉及的集合（简报一侧，与 participantGoalPoints 同理），保密档的自然给内容；组里仍有不给内容的绝密，而本章计划又揭示了组里另一条时，给作者一条提示（例如 payoffWithheld 之外新加一个码，或在 Spec 里写明这种情况怎么办）。输出 16 的“揭穿按组”补一句组成员怎么进集合。

（第 5 条补充核实：去掉 A2 的版本是 /tmp/review-w00039-t35-impl/exp/exp5b.test.ts，秘密段给出“真相：灰袍客就是王爷甲…”与“只能写到：暗示”，确认是 A2 不在集合里导致整组被扣。）

### 6. 内核纯文字渲染：引另一块原文（quoted-block）时 text 里照写那一块的 MDX 源文，含条目 id
严重程度：重要
类别：违反合同（canon/rendering.md 输出 15）/ 测试漏了这条路径
位置：packages/nb-canon/src/render/render.ts:309-316（read 只记 problems 的 quoted-block）与 :336-341（拼接照写 plainValue(result.value)，字符串原样返回）
现象：`{ref("旧信").text[b1]}` 在被引的块存在时，resolve 返回块的源文（字符串），plainValue 直接返回它，于是 text 是“引：写给 <Ref id="e1" />，{ref("e1").character.状态}”；reads 只有被引条目 e2，源文里的 e1 不进 reads、mentions（exp6.test.ts）。
为什么是问题：输出 15 写明“有问题的那一处不写文字”，syntax 以外的问题都应留空（raw-value、unavailable 的实现确实留空）。现在简报靠 gate.blocks 见到 problems 整块扣下，所以简报没泄漏；但内核的合同是给“不回写的读者”通用的，下一个调用方若只想去掉有问题的那一处而保留其余文字（输出 15 的写法暗示可以这样用），就会把 MDX 与 id 交出去。rendering.test.ts 的“引另一块原文”用例里 e2 没有 b1，走的是 unavailable 分支（期望里同时有 quoted-block 与 unavailable、text 为空），真正有源文的分支没测到。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp6.test.ts`，看输出的 text。
建议改法：read() 判出 `text[...]` 的引用后，这个表达式的 splice 写空串（与 unavailable 一样 continue）；rendering.test.ts 的那一条改成被引的块存在、源文里有 `<Ref>` 与表达式，断言 text 不含 `<Ref`、`{ref(`、id。

### 7. 本章计划改“对用马甲的本体的态度行”时，把对本体的态度挂到马甲名下写出，绕过在场的人一段的认人判断

### 8. 称谓表的“之前只和用着马甲的他在场过”一条，把旧马甲与本名并排写出，等于写出不给内容的揭穿
严重程度：阻断
类别：正确性 / Spec 本身的规则造成泄漏（输出 7 的顺序第 4 条）
位置：gate.ts:355-358（narrativeName 的 together/masked 分支）；Spec plot/brief.md 输出 7

如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp8.test.ts`。
建议改法：左栏用旧马甲名的那一分支，要求视角人物对揭穿那个旧马甲的某条知识点有 knows、且那组揭穿按输出 16 的组规则给了写手（关卡要把“揭穿组”的计算扩到这里用到的旧马甲）；否则落到泛称“一个陌生人”。Spec 输出 7 的顺序第 4 条随之改写，验收 8 补一句“之前只见过他戴马甲、这一场他不戴”的期望。

### 9. 身份不给写手的本体，他的目标（名字与为什么）照写在马甲名下；与涉及条目的样子跳过本体字段的理由相矛盾

类别：对照需求 / 设计一致性（需要开发者定）

现象：王爷这一场用马甲灰袍客（揭穿绝密、本章不揭示），王爷有一个不隐秘的目标“夺回先帝传下的王位”（为什么：他是先帝之弟）。在场的人一段写“灰袍客 / 目标：夺回先帝传下的王位（他是先帝之弟）”（exp9.test.ts）。

### 10. 种子网的覆盖与计划的判据有几处缺口，第 1、2、7 条的泄漏都在缺口里
严重程度：重要
类别：测试
位置：packages/neuro-book/src/plugins/plot/testing/brief-world.ts:197-228（计划补丁）、:232（补叙只在一段的书里）；core/brief/secrecy.test.ts:9-10、:25（称谓左栏整列不判）

### 11. 内核与关卡都用“行的 id 是不是条目”区分以引用为键的行与作者写的行，作者行的 id 撞上条目 id 时写成那个条目的名字
严重程度：建议
类别：正确性 / 边界（与 Spec 的写法不一致）
位置：render.ts:283-287（plainValue 的 isEntry(row.id)）、gate.ts:282（row 的 isEntry(id)）、render.ts:312（行键进 reads 的判断）
现象：canon/components 的校验里两种列表的区别是清楚的：以引用为键的列表（keyedBy: "ref"）存下的行没有 label，作者写的列表的行必须有 label（values.ts listItemProblem）。纯文字渲染与关卡却按“id 是不是条目”猜。作者行的 id 只要求是标识符，写成 e3 这样的 id 是合法的；实测作者写的清单一行 `{id: <绝密知识点 id>, label: "短剑"}`，涉及条目的样子写出“清单：一件绝密设定（数量：1）”，引这张清单的正文块也被整块扣下（exp10.test.ts）。撞上普通条目 id 时，作者写的“短剑”会被写成那个条目的名字。
为什么是问题：Spec rendering.md 输出 15 写的是“以引用为键的列表写各行条目的名字……作者写的列表写各行的 label”，按列表的种类分，不是按 id 猜。不会泄漏，但会写错、多扣，而且错误与作者写的 id 有关，很难查。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp10.test.ts`。
建议改法：按字段声明的 keyedBy 判断（resolve 已经拿到字段声明，可把 keyedBy 随值交给 plainValue；关卡的 value 拿得到命名空间与字段时也按声明判，拿不到的地方用“存下的行有没有 label”判）。路径里的行键同理按字段声明判断要不要进 reads。

### 12. 纯文字渲染的结果说明与 Spec、实际行为不一致：“两者都不含本条目自己”
严重程度：建议
类别：代码质量 / 注释
位置：render.ts:253-256（PlainBlock 的说明）
现象：说明写“reads 与 mentions 两者都不含本条目自己”。实际上 `{ref("本条目").字段}` 进 reads、`<Ref id="本条目" />` 进 mentions；Spec 输出 15 写的是 reads“写了 ref(...) 的条目（含本条目自己）”。plan.md 第四节又写“本条目自己不算”。三处三种说法。
为什么是问题：关卡的 blocks 有“调用前提：这个条目自己是 plain”的隐含约定（gate.ts 的接口说明里没写，plan.md 写了），读者照这个注释会以为自引用不会影响判断。现在跳过的都是非 plain 条目，所以没出错；以后有人对 rename 的本体调 gate.blocks（例如照第 9 条的乙方案给本体的正文）就会被自引用整块扣下或漏判。
建议改法：注释按 Spec 改成“reads 含写了 ref 的本条目自己；不写 ref 的本条目字段不算；mentions 含写到本条目自己的 <Ref>”；在 Gate.blocks 的接口说明里写明调用前提（条目自己是 plain）。

### 13. 热路径上的重复读取：关卡每写一个名字读一次引擎，内核判断“是不是条目”也读一次引擎
严重程度：建议
类别：性能
位置：gate.ts:228（realName 每次调 view.entry）、gate.ts:129（stored 每次调 view.object）；nb-canon render/entry.ts:68-71（isEntry 调 engine.entry）；secrets.ts:45、gate.ts:113、gate.ts:170（三次 view.entries() 全表扫）
现象：一章 10 个在场的人、185 个条目的书拼一份简报（exp2.test.ts），读取视图被调用 view.entry 627 次、view.object 671 次、view.entries() 17 次、renderPlain 10 次，约 15 毫秒。engine.entry 每次都做一次 foldAtPoint 加 buildEntryView，读取视图还要 deepFreeze 一遍，没有缓存。内核的 isEntry 只需要“这个 id 在不在世界的条目表里”（engine.entry 返回 null 的唯一条件就是 world.entries.get 为空），却做了一次完整折叠；一张 50 行的以引用为键的列表就是 50 次折叠。关卡里 participantGoalPoints、hidingGoals 都是“全表扫找参与者的目标”，同一件事扫两遍。
为什么是问题：现在的规模下不慢；一章的简报在写作任务开始与发布前比对时都要拼，书变大（几千个条目、几十个在场的人）时线性放大。改法都很便宜。
建议改法：内核 isEntry 改为查条目表（world.data.entries.has 或 engine 层的同义方法）；关卡里 realName 与 readAt(id, frame.position) 按 id 缓存（关卡本来就是一次性的，生命周期与这一份简报相同）；参与者的目标在关卡里扫一次，participantGoalPoints 与 hidingGoals 共用。

### 14. 补叙安放是“未排期”或章不在章序里时，写作指示写成“补叙前史里的事”
严重程度：建议
类别：正确性 / 边界
位置：packages/neuro-book/src/plugins/plot/core/brief/index.ts:96-98（timeModeText）
现象：Placement 有三种：prehistory、chapter、unscheduled（nb-canon core/schema.ts:16-20）。timeModeText 只认 chapter，其余一律写“补叙前史里的事”；chapter 安放的章不在章序里时同样落到“前史”。
为什么是问题：输出 16 只给“补叙第 N 章的事”“补叙前史里的事”两种写法；unscheduled 不是前史，写手会被误导到故事开头之前。读取框架（context.ts flashbackPosition）也把 unscheduled 当初值读，这一处是 t34 留下的近似，但写给写手的文字是 t35 新写的。
建议改法：unscheduled 写“补叙一段还没排进章序的事”之类的中性句（先在 Spec 输出 16 补一条）；chapter 安放而章找不到时不写“前史”，写“补叙另一章的事”。

### 15. 不是参与者的人的隐秘目标写成“见这一场的秘密”，秘密段里却没有这个目标
严重程度：重要
类别：正确性 / Spec 输出 4 与输出 16 的口径不一致
位置：gate.ts:241（name：藏着的知识点都给了内容就加“，见这一场的秘密”，不看持有者在不在场）对比 secrets.ts:42-50（hidingGoals 只取参与者的目标，只有它们的名字、为什么写进那一项）
现象：管家不在本章计划的参与者里，他的隐秘目标“拿到借据”藏着保密档的“男爵欠了赌债”；本章计划让勇者得知这件事，并把管家的目标改成受挫。本章计划一段写“管家的一个隐秘目标，见这一场的秘密”，秘密段“男爵欠了赌债”一项里只有真相与名单，没有这个目标的名字、为什么与状态（exp11b.test.ts）。写手被指去看一个不存在的条目，本章计划里“目标受挫”这件事也就无从写起。
为什么是问题：输出 16 的“名字”一条对所有目标都加“见这一场的秘密”，输出 4 却只把参与者（含只被提到的）的目标写进那一项，两条的范围不同，实现照字面各做一半，出现悬空的指向。关卡的承诺是“同一个条目各段写法一致”，这里同一个目标在本章计划与秘密段之间对不上。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp11b.test.ts`。
建议改法：二选一并写进 Spec：甲，秘密段的那一项列出“藏着它、且在本章任何一段被写到”的全部目标（hidingGoals 的范围改成关卡里 hiding 非空、state 为 shown 的全部目标，或至少加上本章计划改到的目标）；乙，name 只对参与者的目标加“，见这一场的秘密”，别的写成不带指向的“某某的一个隐秘目标”。推荐甲：本章计划改到的目标写手需要知道是哪一个。

### 16. 关卡内部不一致：之后才出场的知识点，名字写成占位，真相却照给
严重程度：重要
类别：正确性 / 关卡自身判断不一致（shown、truth 与 kind、secretClass 各算各的）
位置：gate.ts:182（shown 只看档位与揭示，不排除 late）、gate.ts:311-315（truth 只看 shown）对比 gate.ts:222、250（kind、secretClass 先判 late）
现象：保密档的知识点“密室在钟楼下辛”记在第 9 章出场，第 4 章的计划让勇者对它起疑并暗示它。秘密段这一项写成
  一个之后才出场的人或物
  真相：密室在钟楼下辛（密室在钟楼下辛）
本章计划写“勇者对一个之后才出场的人或物：没有记录 → 怀疑”（exp12.test.ts）。同一个条目，名字按“之后才出场”遮了，真相与简介整句给出。
为什么是问题：输出 16 把“之后才出场的”列在“不给内容”一类，名字写占位；truth 给了内容，等于一处当 withheld、一处当 shown。种子网只造了之后才出场的人与目标，没造之后才出场的知识点，所以没抓到。也说明 late 的口径对知识点要想清楚：P2 第 7 条对“计划里在场的人”选择按在场写，计划里涉及的知识点是不是同理（按出场算还是按计划算），Spec 没写。
如何核实：`bun test /tmp/review-w00039-t35-impl/exp/exp12.test.ts`。
建议改法：先定口径。若按 Spec 现文：shown 构造时排除 late 的知识点（与 kind 同一个判断），这一项按不给内容写；若按 P2 第 7 条的思路（计划涉及就算在场），把本章计划涉及的知识点也排除出 late，名字照写、真相照给。无论哪种，shown/truth 与 kind/secretClass 要出自同一个判断函数，种子网加“之后才出场的知识点被本章计划涉及”。

（第 9 条补充：同一个矛盾也在本章计划一段。本章计划改用马甲（身份绝密）的本体的普通字段时，planItems 把“灰袍客的<字段>：旧值 → 新值”照写；涉及条目的样子为了“封号这类字段会把人对上”跳过本体字段，本章计划却把这些字段的变化挂在马甲名下写出。处理第 9 条时一并定。）

### 17. 分两段讲两条线的章：一段把知识点升成绝密，另一段照写它的名字，同一份简报一边遮一边写
严重程度：建议
类别：边界 / 已知限制没写全
位置：index.ts:128-136（每一份各算一个关卡，遮挡事实不跨份）；plan.md“不做与风险”只记了马甲的那一种
现象：第 8 章前段讲主线、后段讲回溯线（并且是补叙）。回溯线上的本章计划把“管家想继承爵位壬”升成绝密，主线上它仍是普通档。回溯后那份写“管家对一件绝密设定”“有一件涉及管家的绝密设定”，回溯前那份的本章计划写“卫兵对管家想继承爵位壬：没有记录 → 知道”（exp13.test.ts）。写手拿到的是一整份上下文，两段都读。
为什么是问题：按“份内的段按那一份的真值判”，两份各自都对；但对写手来说，绝密那一份的名字在另一份里明写着，与 I12 第 3 项“同一份简报不能一边遮、一边写”是同一类。计划只把“一段用马甲、一段不用”记为已知限制，升档、设隐秘的跨份情况没写，种子网又刻意不造两段的升档（见第 10 条），所以这条既没有被判定为接受，也没有被测到。
