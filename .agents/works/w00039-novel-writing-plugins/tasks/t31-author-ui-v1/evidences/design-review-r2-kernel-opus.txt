### 3. changedAt（project 输出 32）若照“来历的最后一步”算，entry 的读取从 0.24 毫秒变成几十毫秒，破输出 14 的 20 毫秒预算
严重程度：重要
类别：安全与性能
位置：docs/specs/canon/project.md 输出 32；plan.md K5“entry 的每个字段状态加最近一次改它的安放”
现象：输出 32 让 `entry` 无条件地给每个字段带 changedAt。现成的最近数据来源是 engine.origins（incremental.ts:412-457）：每个地址从初值 structuredClone 起把这个条目的整条时间线重放一遍，每个相关补丁再 structuredClone 一次结果。同一实验里，随机位置读常出场条目：只读 entry 中位数 0.24 毫秒；entry 加 4 个字段的 origins 中位数 36 到 47 毫秒；在最后一章末尾读 4 个字段的 origins 中位数 76 到 114 毫秒（机器负载 6 到 12，绝对值偏大，但比值约 150 到 200 倍）。project.md 输出 14 的预算是“随机读一个条目（实际模式，不要来历）中位数 20 毫秒以内”，输出 32 让“不要来历”的读取也付这笔。
为什么是问题：K-b 照最省事的做法（复用 origins 取最后一个 patch 步）就会破预算，且这个成本在 author-ui 的每个条目页、每次换位置都付。
如何核实：同上脚本的 plainMedian 与 entryPlus4OriginsMedian、last4OriginsMedian。
建议改法：Spec 不变，但在 K-b 的计划与实现合同里写死算法：在 foldAtPoint 已经走过的那遍时间线里顺手记每个地址（含祖先地址）最后一次被生效补丁碰到的变更，一遍 O(事件数)，不复制值；两个引擎各实现一次并进差分测试。或者把 changedAt 改成 entry 的可选参数（像 withOrigins），只有条目页要时才算，并在输出 14 加一行带它时的预算。规模脚本加一项“带 changedAt 的随机读”。

（第 3 条补充：incremental 的 entry 不是整条重放，而是 foldAtPoint 从检查点 foldThrough（incremental.ts:705-718），所以“顺手记”要进快照。更省的做法：拿到 count 之后，从 timeline.items[count-1] 往前扫，对每个字段用 addressesOverlap 找第一条 applied 的 change 事件，不复制值；只在初值设过的字段要扫到头，约 8000 项的比较，量级在毫秒以下到一两毫秒。reference 引擎同样倒扫事件序列。）

### 4. changedAt 进带视图令牌的 entry，会经剧情插件的按视角视图原样漏出被遮住的字段的改动时间与变更 id
严重程度：重要

现象：剧情插件按视角过滤条目时，对每个字段写的是 `fields[fieldId] = {...state, value: this.#maskValue(...)}`，只换 value，FieldState 上的其它属性原样展开。输出 32 给 FieldState 加 changedAt（变更 id 与安放）后，指向 V 读不到的知识点、被换成占位的引用字段（例如目标的“隐秘”、知情列表行），照样带出“哪条变更、在第几章第几个键改过它”。plot/knowledge.md 输出 9 对视图只给“经历”里 V 在场的变更 id、并拒绝剧情变更列表，changedAt 给了 V 不该知道的变更 id 与时间。

### 5. changedAt 的定义在几种情况下不唯一：子线上带过去的值、套不上的补丁、核对点给的起点
严重程度：重要
类别：正确性 / 文档
位置：docs/specs/canon/project.md 输出 32；model.md 输出 37“带过去的一步照旧”
现象：
- 子线：带过去的值在引擎里是一条合成变更，id 就是分叉那条变更的 id、安放是切口（lines/set.ts:210-213，service/reads.ts:203-207 才把它换成 carried 步）。照“最近一条改过这个地址的生效变更”算，子线上每个被带过去的字段的 changedAt 都是“分叉那条、切口那章”，哪怕值在父线上几百章前就定了；而那条分叉变更存下来的 patches 里并没有这个地址。
- 补丁没套上：两个引擎的来历只在整条变更 `applied` 为假时跳过（incremental.ts:430、reference.ts:271-272），变更套上了而其中这个补丁 notApplicable（命名空间停用、类型不在）时照样记一步；照来历算的 changedAt 会指向一条并没有改动这个值的变更。
- 核对点作为语义档的起点（anchor）改了值，但不是剧情变更，changedAt 不算它；界面会在“第 30 章核对改成了 X”之后仍写“第 12 章改过”。
为什么是问题：两个引擎要给出相同结果、差分测试要覆盖，定义有歧义时两边各自猜，差分测试未必能发现（两边都复用同一个 origins 时一起错）；界面“第 N 章改过”在子线上会集体指向切口，误导作者。
如何核实：读上述行；子线情形可在 tests/ 的世界线样本上读子线 entry，看 origins 里 patch 步的 change 是否等于 fork 变更 id。
建议改法：输出 32 补三句：子线上带过去而本线没再改过的，changedAt 取 carried 步的 `{line, change}`（原线上那条），不取分叉；只算这个补丁本身套上了的；核对点给起点的不算（或明写“核对点给起点时为空”）。都是一行规则，不加机制。

### 6. chapters、components 说“带世界版本”，但章表与登记变化时版本不动、也没有任何事件，按版本缓存的读取层永远读不到新的
严重程度：重要
类别：正确性 / 不变量
位置：project.md 输出 28（chapters）；components.md 输出 21（components）；plan.md K3“章序变了随 changed 事件失效”、“三、读取层”（按 version 与 changed 事件重读）
现象：
- 登记变化：WorldService.setRegistries（service.ts:1054-1062）只 withOptions 换登记，不加版本、不发事件。components.md 输出 21 自己写了“登记变了（插件启用或停用）以后重读得到新的”，但调用方没有任何信号知道该重读。
- 章讲的线变了而章序没变：setChapters（service.ts:996-1009）里 World.reorder 只比 order.ids（world.ts:633），只改 `<segment>` 或章的 line 时不发修订、不加版本、不发事件；输出 28 的章表里却含“各段讲的线”。

### 8. 就地改与记一笔重发同一请求 id 得到 value-conflict，不是第一次的结果；recordNote 照 editInPlace 的路子写会继承这个错
严重程度：重要
类别：正确性 / 不变量
位置：packages/nb-canon/src/world/edits.ts:63-72（先比读到的值、后进 publish）；revisions.md 输出 16、23；project.md 验收 7
现象：editInPlace 先在当前世界上重算值并与 read.value 比较，再合成写入请求交给 publish；请求 id 的去重在 publish 里（world.ts:463-467）。第一次已经发布以后重发同一个输入：值已经是新值，与 read.value 不同，直接回 value-conflict，根本走不到去重。即使走到，合成出的请求也随世界变（键、baseVersion 之外的内容），摘要对不上会变成 request-id-reused。recordDelta 同样。
为什么是问题：输出 16 承诺“带同一个 requestId 的写入请求……再次提交时返回第一次的结果”，断线重试（验收 7、revisions 验收 6）对就地改与记一笔不成立；输出 23 的 recordNote 若按 recordDelta 的样子包一层 editInPlace，原样继承。previewEdit 的“同样的输入写入”也依赖请求 id 语义清楚（见第 9 条）。
如何核实：/tmp/review-w00039-t31-design2/opus/retry.test.ts（在 nb-canon 包目录 `bun test /tmp/review-w00039-t31-design2/opus/retry.test.ts`）：对样本世界 editInPlace 一次成功后，在新世界上用同一输入再调，输出 `retry after success: {"code":"value-conflict","current":41000}`；recordDelta 同样输出 `{"code":"value-conflict","current":41500}`。
建议改法：editInPlace、recordDelta、recordNote 开头先查 world.requested(requestId)：有的话按这次输入本身（不是合成的请求）的摘要比，相同返回第一次的结果，不同回 request-id-reused；发布时用 publish 的 requestDigest 参数存输入的摘要（writeBack 与 revert 已经这样做，world.ts:322-339）。K-c 里顺手改，加一条重试用例。

### 9. previewEdit：请求 id 已用过时预览返回什么没定；route 的三种盖不住输出 8 表里两行 planned 的路由
严重程度：建议
类别：规范 / 正确性
位置：revisions.md 输出 22
现象：
- 预览走的是同一个 editInPlace 的计算（plan 的意思），编辑结果里的修订 id、新对象 id 由 allocator 按世界确定地发，时间不进操作与带来的变化，所以同一世界上预览与写入逐字相同是成立的（实验：同一世界上两次 editInPlace，ops 与 impact 的 JSON 完全相同，retry.test.ts 第三行输出 `ops equal: true impact equal: true`）。但请求 id 已经发布过时，publish 会返回第一次的修订并标 repeated（world.ts:463-467），预览就会把旧修订当成“预览的修订”交出去，route 却按当前世界算；摘要不同又会回 request-id-reused。输出 22 只说“预览不记请求 id”，没说预览看不看已有的请求 id。
- route 只有 init、patch、change 三种。输出 8 表里“起点由核对点给出时改那个核对点（planned）”一旦实现，路由到的是核对点，三种都装不下；“增元素带的值改那个补丁（planned）”能装进 patch，但 change 的补丁是哪一个没说（同一条变更里可能有多个补丁碰到这个地址）。
为什么是问题：前者让界面的确认条显示一份与写入无关的旧修订；后者让 route 的形状在下一次补口时要破坏性地改。
如何核实：读 world.ts:463-467、edits.ts:113-128。
建议改法：输出 22 加一句“预览忽略请求 id 的去重（按没用过算）”；route 的 patch 带上补丁下标 `{kind: "patch", change, patch}`，并说明 route 是可扩展的联合，planned 的核对点路由将来加 `{kind: "check", check}`。

### 10. 语义档的“读到的值”含归纳文字，归纳在读与写之间落地时 recordNote 与 previewEdit 后的写入会无故 value-conflict

### 13. tree 的 remaining 与 author-ui 的“已删除的只在有子条目时列出”冲突；hasChildren 把已删除的子条目也算进去

### 15. previewEdit“返回与写入相同的失败”只对世界层成立；服务层的失败预览给不出；origins“空结果”不要做进引擎
严重程度：建议
类别：规范 / 正确性
位置：revisions.md 输出 22；model.md 输出 37 末句
现象：
- 写入的失败有一部分出在服务的 #write（service.ts:913-918）：stopping、world-read-only、write-unknown、busy（别人持有独占）、exclusive-lost。previewEdit 不带独占令牌、也不排队，照现有 preview（service.ts:872-876）的做法会在这些情况下预览成功，随后写入失败。输出 22 的“会被拒收的输入返回与写入相同的失败”读起来包括它们。
- 输出 37“条目不存在、路径不是声明过的地址时结果是空的”：现在两个引擎对未声明的路径返回只有初值一步的来历（incremental.ts:413-421、reference.ts:254-261），editInPlace 与 laterRecords 都直接用 Engine.origins，并对结果取 `steps.at(-1)!`（edits.ts:105-106）。若把“空”做进引擎，editInPlace 在某些没被前面拦下的路径上会拿到 undefined 而抛错。
如何核实：读上述行。
建议改法：输出 22 写成“世界层的拒收（输出 8、9、23 与写入校验）与写入相同；只读、独占等服务层状态不在预览里判断，界面按 status 与租约另行处理”（author-ui 输出 28 已经这样做）。输出 37 的“空”在服务的 origins 方法里判断（条目不存在或 parsePath 不认、字段没有声明时返回空），引擎不变。

未发现问题的方面
- previewEdit 在同一世界上的确定性：新对象 id、修订 id 由 allocator 按世界确定地发（world.ts:470-477、595），剧情变化的排序键 keyAt 只看线视图里的记录（edits.ts:54-61），时间不进操作与带来的变化。实验里同一世界两次 editInPlace 的 ops 与 impact 逐字相同。仔细检查后没有发现问题（请求 id 那一点见第 9 条）。
- 章序未发布时 chapters 返回新章序：其它读取全部按 world.options.order 算（recordedChapters 只用于判断要不要发章序调整，world.ts:632），返回新章序与“按世界里记下的章序算的东西”没有对不上的地方。仔细检查后没有发现问题（失效信号见第 6 条）。
- revision 带视图令牌拒绝：够用。plot 的按视角视图本来就拒绝改动记录，作者与主 Agent 不带令牌，`object` 同样能读到全文，revision 没有多漏东西。
- components 的“声明原样”：ComponentType 的字段声明经 TypeBox 校验，是纯 JSON，agentView 等是字符串，可以原样过远程合同；实例声明的字段存在条目初值的 `declared`（core/schema.ts:106），数据来源有。
- tree 的计算量：一层 50 项各读一次 entry，规模夹具上单次约 0.24 毫秒，合计十几毫秒；按计划模式第一次读受输出 14 的 1 秒预算约束，已有。
- changes 的 total 与 before：listChanges 本来就先筛全部再分页（reads.ts:385-398），total 不另付；before 可以用 Engine.eventKey 与 plannedAt 按模式判断，与 model 输出 5 的“之前”同一套先后（含已写章上的计划按“章序加 0.5”）。
- recordNote 的补丁形状：note 补丁的值是字符串，数的依据校验只对数值且非 note 的补丁（world.ts:1400），非叙述的变更不要求讲述；与现有校验不冲突。排序键与就地改同一个 keyAt，核对点的键也在它的取值范围里，是同一套。
- 编号只在末尾追加、新条目末尾标 planned、失败码都在已有失败表里：符合 docs/specs/README.md（第 7、12 条另有两处写法问题）。
