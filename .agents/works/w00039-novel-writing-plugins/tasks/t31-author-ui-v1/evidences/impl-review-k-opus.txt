### 1. 就地改、记一笔、语义档的记一笔对“值为 undefined 的键”直接抛 TypeError（K9 的输入摘要引入的回归）
- 严重程度：重要
- 类别：正确性 / 错误路径
- 位置：packages/nb-canon/src/world/edits.ts:225-227（inputDigest 用 canonicalJson），被 editInPlace:139、recordNote:219、recordDelta:274 在一切校验之前调用

  得到的不是失败结果，而是被拒的 Promise（TypeError "canonical JSON: key \"title\" is undefined"）。同一份输入走 previewEdit 却是 ok：预览不算摘要，
  于是“预览通过、写入抛异常”。

  得到 undefined 也是合法输入。产品当前只经链路（JSON 序列化，没有 undefined）调用，所以眼下没触发；但内核的公开函数 editInPlace/recordDelta/recordNote

### 2. tree 每次调用用展开复制建“父到子”表，条目数的平方级；比 base 更慢
- 严重程度：重要
- 类别：性能（热路径）
- 位置：packages/nb-canon/src/service/service.ts:925（`below.set(entry.parent, [...(below.get(entry.parent) ?? []), entry])`）
- 现象：每处理一个条目就把同一父条目下已有的数组整个复制一遍。条目都挂在根下（三百万字夹具就是 520 个条目全在根下）时是 n²/2 次复制。
  这张表每次 tree 调用都重建，而条目树每展开一层、每翻一页都调一次 tree。
- 为什么是问题：同样的写法隔离测量（exp/tree-bench.ts，只量建表这一步）：520 条 3.5 ms、2000 条 16.8 ms、5000 条 78 ms、10000 条 360 ms；
  改成 push 分别是 0.06、0.19、0.30、0.38 ms。base 的 tree 是 O(页长 × n)（50 × 520 次比较），新写法在 520 条时就已经更慢，条目一多直接出预算。
  tree 不在规模脚本里，所以输出 14 的测量看不到它。
- 如何核实：bun /tmp/review-w00039-t31-impl-k/exp/tree-bench.ts
- 建议改法：`const list = below.get(entry.parent); if (list === undefined) below.set(entry.parent, [entry]); else list.push(entry);`。
  更进一步：`below` 与 `listed` 只依赖 world.data.entries，可以按 WorldData 用 WeakMap 缓存（同 lineTable 的做法），同一版本翻页、展开各层不重建；
  规模脚本补一项“根这一层的 tree”。

### 11. 几处小的一致性与可简化之处
- 严重程度：建议
- 类别：代码质量 / 边界
- 位置与现象：
  a. packages/neuro-book/src/plugins/canon/shared/contracts.ts:59-71 的注释说 EditFields、DeltaFields、NoteFields“写入与预览共用，两边的字段才不会各写各的”，

  b. 预览的修订带的是 `requestId: "preview:<id>"` 与合成请求的 requestDigest（world.preview 不传摘要覆盖），与随后真正写入的修订这两项不同；
     远程层 previewEdit 原样交出 revision。界面若把预览的修订当回执展示或比对会看到假 id。返回前把 requestId 换回调用方的，或者只交 ops 与 impact。
  c. service.ts:1207-1209 setChapters 在排进写入队列之前就换上新标题：写入队列里有别的写入时，这段时间 chapters() 给的是“旧章序 + 新标题”；

  d. service.ts:1217-1219 只读世界里每次 setChapters 都无条件追加一条 reorder-not-recorded 诊断（不看章序到底变没变）；base 上就有，打开时一条、活页夹每变一次一条，

  e. scripts/scale.ts 新加的两项量的是引擎（engine.lastTouched、engine.origins），输出 14 的口径是“项目进程里直接调用”服务；服务层的 #withChangedAt
     （逐个命名空间复制、每个字段查一次 #changedAt）与 service.origins（每页重算整条、再按变更补 at 与 text）不在测量里。我在负载 11 到 15 下跑规模脚本副本：
     带 changedAt 的随机读中位 5.13 ms、最慢 42 ms；来历一页中位 56 ms、最慢 327 ms（主会话负载 3.5 时是 2.05/15 与 20/111）。建议改成调 WorldService，或另加一项服务层的。

## 汇总

1. 第 10 条（重要）打开后补读活页夹触发空的“章序调整”，canon.test“订阅：释放后不再收到事件”在负载下稳定失败

### 未发现问题的方面
- 两个引擎的 lastTouched：对按计划模式的覆盖层、已删除的条目（时间线被删、参照实现先判 deleted，结果同为空）、核对点给起点、条目不在时间线里，逐条对照后口径一致；
  差分测试在“增量引擎忽略套没套上”的变异下三个种子都失败，说明两引擎比较本身有效（缺的是两引擎共用部分的口径测试，见第 3 条）。
- #changedAt 往父线找的循环：每轮换到 definer.parent，线表是树，不会死循环；父线不可建时 originsAfter 为 null，退出得 null。用真实 WorldService 构造回溯线与两层回溯线，
  rb.次数 的 changedAt 都正确给到主线的 c3（exp/t1/changed-at-child.ts）。窄处：originsAfter 只收与字段地址完全相同的核对点，父线上“元素子字段的语义档核对点”
  在映射时会被跳过，只有回溯者带过去的列表字段里有语义档子字段时才会遇到，记为已知限制即可。
- origins 的游标参数（method、address、position、mode）完整；paged 减半重取时每次重算整条来历，成本见第 11 条 e，正确性没问题。
- edits.ts 重构：result-mismatch 的核对、laterRecords 的位置（规整过线的位置）、各失败码与 base 一致；repeated 遇到被普通 publish、回写、还原用过的请求 id 时摘要不同，
  得到 request-id-reused（合理，但没测，见第 9 条 d）；预览与写入共用 plan*，新对象的 id 由分配器按世界发号、与请求 id 无关，所以预览与写入的操作逐字相同。
- setChapters / setRegistries 的 inputChanged：只读世界（#write 不调 compute、.then 换上新章序后比表）会发；invalid 不发（章表也没变）；标题从有到无会发；
  发布了章序调整时只有 changed，不重复；setRegistries 在写入队列里比较、只比 types，登记同一份不发。只改段的线也会发（exp/t1/lines-only.ts）。
- 视图令牌：entry 带令牌走 #viewedOn，拿不到 ancestors、sameAs、folder、changedAt；origins、revision、previewEdit、recordNote 带令牌拒；chapters 夹到上限所在章；
  changes 的 before 经 within 校验上限与线、total 只数视图里的。与 Spec 输出 35 一致。窄处（不记为发现）：上限所在那一章的 lines 会列出这一章后面几段讲的线 id。
- ./schema 的导入边界：新加的都是 type 导出，architecture.test 通过；nb-canon 的 tsc --noEmit 通过。
- tree 现有调用方：在 packages/neuro-book/src/plugins 与 nb-story 里没搜到别的 tree 调用（只有远程层），墓碑规则对它们没有影响；service.test 原有的墓碑用例仍过。

### 对主会话自定七条的判断
1. before 列已写变更不论生效状态、计划按模式与计入：合理，Spec 输出 31 已同步，用例覆盖了实际与按计划两种模式。
2. changedAt 与来历同口径（整条套上、补丁碰到字段就算）：合理且简单，两引擎一致；但“碰到元素与子字段也算”没有测试保护（第 3 条 D）。
3. 来历页里核对点也带安放 at：合理，Spec model 输出 37 已写，用例有断言。
4. 墓碑规则对不带位置的 tree 同样生效：合理，没有别的调用方受影响；hasChildren 的规则缺测试（第 3 条 G、H）。
5. 存调用方输入的摘要：方向对，修好了重发报 value-conflict；但摘要用 canonicalJson 引出第 1 条，且没先规整（位置写不写 line 会算成不同请求）。
