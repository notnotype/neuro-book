### 1. 项目进程重启后仍接受旧的待处理游标

- **严重程度**：重要；**类别**：正确性。
- **位置**：packages/nb-canon/src/service/service.ts:258、534、932；细计划 plan.md:295。
- **现象**：诊断代次每次打开从 0 开始。进程前后各登记同一个插件一次后，代次都为 1；世界、正文和插件数据版本相同时，旧游标的两段摘要均会相同。重开后用它翻页，返回第二条而不是 cursor-stale。
- **为什么是问题**：K-d1 的计划明确说进程重启后旧 pending 游标作废。代次只计实例内变化，不能区分实例；按同一数据版本更换计算（本次特意支持的场景）若发生在重启之间，旧偏移还会在不同列表上继续。base 的游标原本只按输入摘要和参数，因此跨重启可复用；这是本次新增约束未落地，不是把 base 的既有行为算作回归。
- **如何核实**：在实现 worktree 的 packages/neuro-book 跑 bun /tmp/review-t31-kd-impl/diagnostics-live.ts restart（21ed0568b）。用产品 createWorldHost、真实日志与锁打开，生成 2 条发现，取 1 条一页，停止宿主后另起 Bun 进程打开同一作品。带旧游标返回 1 条发现，输入摘要相同。
- **建议改法**：在 pending 游标参数中绑定每次创建 WorldService 都不同的实例标识，另保留诊断代次使同实例内失效；不要更改通用输入摘要或其它方法的游标。补跨进程翻 pending 旧游标的合同用例。

### 2. 同批修改 Component 和诊断声明时，第一条事件交出旧分组与旧游标

- **严重程度**：重要；**类别**：不变量。
- **位置**：packages/nb-canon/src/service/service.ts:531–555、1325–1335；packages/neuro-book/src/plugins/canon/backend/world-host.ts:293–306。
- **现象**：宿主会把多张登记表合并到一次 setRegistries。服务先装上全部新表，随即同步发 components，直到监听器返回以后才增加诊断代次。只改 Component 显示名和诊断级别时，读取摘要不变；在第一条通知里同步读 pending 命中上一批的分组，旧游标也仍过关。
- **为什么是问题**：监听器已观察到新世界的所有登记，却拿到旧声明算出的分组，违反 model.md 输出 36。不是单独重登记仍旧缓存（那条已处理），而是批处理内过早发事件；第二条通知到达后才恢复。base 没有诊断代次，本项是新增失效顺序未覆盖组合更新。
- **如何核实**：在实现 worktree 的 packages/neuro-book 跑 bun /tmp/review-t31-kd-impl/diagnostics-live.ts simultaneous（21ed0568b，产品 createWorldHost）。先缓存 2 条待处理，随后在同一轮调用宿主的 setComponents 和 setDiagnostics。components 监听器读到待处理 2、提示 0，旧游标返回一项；diagnostics 监听器才读到待处理 0、提示 2，旧游标返回 cursor-stale。
- **建议改法**：先确定本批哪些输入变了，完整换世界、刷新相关的代次，再依次发事件。把测试的重读移进监听器，加入两张表同批更新且 inputDigest 不变的用例。

### 3. 按条目索引把任意查询串长期保存在当前版本

- **严重程度**：重要；**类别**：安全与性能。
- **位置**：packages/nb-canon/src/service/reads.ts:453–477；packages/nb-canon/src/service/service.ts:1032–1045；packages/neuro-book/src/plugins/canon/shared/contracts.ts:85–90。
- **现象**：远程 changes 的 entry 允许任意字符串，没有查验它是否存在。changesOfEntry 在 grouped 未命中时，仍用查询串作键，把新空数组写入 sorted。外面的 WeakMap 只能在世界数据或章序被回收时释放它，不能限制同一版本里的键数。
- **为什么是问题**：固定在一个空世界也能增长：N 个不同的未命中查询持有 N 个字符串键和 N 个空数组。作者只读或反复翻页时世界不必前进，内存上限变成调用次数，而不是条目或变更数。base 每次筛选后只返回临时空数组，没有常驻条目。
- **如何核实**：静态追踪远程 changes → WorldService.changes → changesOfEntry；对照 8a43f89e2 的 reads.ts，旧实现没有按查询参数写入缓存。即使 grouped.size 为 0，471–475 行也对每个不同的 entry 执行 sorted.set。
- **建议改法**：grouped 未命中直接返回共用空数组，不缓存缺失的键；命中的列表私有持有并在首次读取时原地排序、标记即可，避免同时保留原数组和排序副本。

### 4. 早章和窄查询的“发布后首读”已被同轮前面的读取预热

- **严重程度**：建议；**类别**：测试。
- **位置**：packages/neuro-book/scripts/perf/canon-scale.ts:278–310、374–402；packages/nb-canon/src/service/service.ts:1507–1513；packages/nb-canon/src/engine/incremental.ts:326–350。
- **现象**：每轮发布后固定先读最新章的 entry 两次，再读早章 entry；固定先读按条目的 changes 两次，最后才读只筛一章的 changes。发布前的窄查询也量在条目页十组读取之后。
- **为什么是问题**：早章的“第一次”跳过了当版第一次算读取戳、为条目建立精确核对点分组等开销。窄查询的两个采样点都在带 entry 的查询之后；若日后误改成按世界懒排序、两条路径共享列表，昂贵排序会在前一项发生，窄查询证据抓不到设计审查要求防住的冷读回退。base 没有这些首读采样，本项是 K-d5 新测量的口径问题。
- **如何核实**：静态顺序：374–379 行的数组由 382–388 行逐项连续执行两次；两条 changes 中间没有任何发布。未运行规模脚本，不据此判断耗时是否达标。
- **建议改法**：早章和窄查询各在独立的一组发布上先读、再重读，或按轮次明确轮换谁先读、只把先读的轮次纳入冷样本。常规条目页的这一组读取仍可另报联跑数据。


### 5. 稀疏来历差分用例漏掉了跳快照时少重放一步

- **严重程度**：建议；**类别**：测试。
- **位置**：packages/nb-canon/tests/differential.test.ts:331–357；packages/nb-canon/src/engine/incremental.ts:503–526。
- **现象**：长时间线里只有 `character.态度` 是稀疏地址，所有入页的补丁都是 `note`，只增加语义事件、不改变该地址的值。页尾归纳又独立从 `foldAtPoint` 取值。
- **为什么是问题**：跨稀疏间隔取值时若只折叠到目标补丁之前，补丁的 `result` 在这组数据里仍完全相同。base 没有这段分页跳转；K-d3 新增的差分用例不能辨别这个分支的取值错位，不是发现了现实现的折叠错误。
- **如何核实**：仅在 `/tmp/review-t31-kd-impl/origins-mutant/` 的副本中，把后续稀疏跳转的 `foldThrough(..., index)` 换成 `foldThrough(..., index - 1)`，首次取值与其他分支不变。在实现 worktree 的 `packages/nb-canon` 跑 `bun test /tmp/review-t31-kd-impl/origins-mutant/packages/nb-canon/tests/differential.test.ts -t '几百个事件'`，仍 `1 pass, 29 expect() calls`。
- **建议改法**：让同页两个相隔足够远的补丁设置不同的值（例如稀疏地改 `character.外观`），另保留语义档用例核对归纳。比对各步 `result`，上述变异就应在第二步失败。

### 6. 项目入口替换一次诊断计算，窗口收到两次失效通知

- **严重程度**：建议；**类别**：不变量。
- **位置**：packages/neuro-book/src/plugins/canon/backend/plugin.ts:103–109、142–146；packages/neuro-book/src/plugins/canon/backend/world-host.ts:323–331；packages/nb-canon/src/service/service.ts:908–919；packages/neuro-book/src/plugins/canon/web/world.ts:134–157。
- **现象**：项目门面约定再登记是替换。它先调旧注销函数，宿主直接替换时也有同样的先注销逻辑。K-d1 之后，这会先为注销发一条 `diagnostics`，再为新登记发一条。内核原本能够覆盖旧登记，旧的停止函数不会删除新登记。
- **为什么是问题**：这不是调用方发起两次变更。每条通知都让窗口整代作废；若第二条到达时第一轮读取已发出，可多重读一轮。同步服务监听器在第一条通知时还处于没有该计算的状态（由调用顺序可知）。base 的先注销顺序已存在，但没有通知暴露这个中间状态，也不触发两次失效。
- **如何核实**：在实现 worktree 的 `packages/neuro-book` 跑 `bun --tsconfig-override tsconfig.json /tmp/review-t31-kd-impl/diagnostics-remote.ts`。探针用真实应用实例、项目门面、世界宿主、远程路由和浏览器入口（进程内 JSON 链路）；首次登记收到 1 条，随后同数据版本替换一次收到 2 条。版本仍是 0，输入摘要相同；远程重读拿到 `new-A`，旧游标返回 `cursor-stale`。未观察到窗口读到未登记状态。
- **建议改法**：门面只记当前的停止函数；宿主把替换交给内核的带令牌登记，不先调用旧停止函数。用项目门面补合同测试：同版本替换一次只通知一次，通知后重读取到新发现、旧游标作废；实际停止入口仍注销一次。

### 7. 稀疏来历样本改变了原有末尾指标的测量世界

- **严重程度**：建议；**类别**：测试。
- **位置**：packages/neuro-book/scripts/perf/canon-scale.ts:346–349、426–475、498–505。
- **现象**：稀疏用例在主测量作品上多发布 1 次、写入 20 条变更，此后才算原有的待处理与嫌疑数、采样堆大小。带 `--fork` 时，继承区间预览与发布也从这份加过稀疏变更的日志重开。
- **为什么是问题**：这些指标与 base 取的不是同一份世界。即使外观补丁没有改变存款核对点的嫌疑，额外日志与时间线事件仍进入堆样本以及 `--fork` 的冷建输入，不能把这些指标的差异都归给读取优化。改初值和前面的 `pendingMs` 都发生在这次发布前，不受这 20 条记录影响。
- **如何核实**：对照 `git diff 8a43f89e2..21ed0568b -- packages/neuro-book/scripts/perf/canon-scale.ts`；base 在改初值后直接读末尾的 `pending`，K-d5 在同一位置插入 `scale-sparse` 发布；重开使用同一 `root`。静态核对，未运行规模脚本。
- **建议改法**：保持旧指标在原有样本上取完，把稀疏发布放在所有旧指标之后，或在单独的样本上量；在稀疏输出里记录该页实际返回的步数和测量版本。

### 8. 发布调用栈采样把条目读取计入发布热点

- **严重程度**：建议；**类别**：测试。
- **位置**：packages/neuro-book/scripts/perf/canon-scale.ts:374–423。
- **现象**：`CANON_SCALE_PROFILE=publish` 从第一轮发布前开始采样，发布后执行 `readTwice()`，十轮结束后才取采样结果。五种读取各调用两次，每次运行共有 100 次读混在发布采样里。
- **为什么是问题**：该模式用自身耗时的热点定位发布慢在哪；条目索引构建、来历取值都会进入同一份热点榜，不能直接和 base 的发布采样相比。`publishes` 的计时在读取前结束，不受这项口径错误影响。
- **如何核实**：静态对照 8a43f89e2 的采样区间与本版 393–417 行；K-d5 在区间中插入了 `readTwice()`，没有另起采样区间。未运行规模脚本。
- **建议改法**：采集发布热点时跳过这组读取并标明模式；正常测量仍按发布后首读与重读分别计时。

### 9. 不足三页的来历让小规模试跑丢掉整份指标

- **严重程度**：建议；**类别**：测试。
- **位置**：packages/neuro-book/scripts/perf/canon-scale.ts:26、131–154、290–303、460、479–505；packages/nb-canon/src/service/service.ts:465。
- **现象**：命令仍接受任意章数。以不带 `--fork` 的 6 章为例，除第一个热门条目外，每个热门条目每章只有 6 条存款补丁，没有存款核对点，合计 36 步。第二页结束时没有下一页游标，脚本把这个正常结果当成错误抛出。
- **为什么是问题**：K-d5 新增的一个不可采样项中断了原有读取、发布等指标的输出，也跳过后面的宿主停止和临时目录清理。base 没有至少三页的前置条件。默认 1000 章不触发。
- **如何核实**：按 131–154 行的生成规则计数；来历每页 20 步，第三页至少要有 41 步。对照 base 的同一脚本，确认异常分支为本次新增。静态核对，未运行规模脚本。
- **建议改法**：样本不足时将第三页标为未测，继续跑其余指标；真实读取错误仍失败。若只支持达到最低规模的样本，应在创建临时项目之前校验并说明最低章数。

### 10. 应用合同用例没有验证首次登记诊断计算后窗口收到通知

- **严重程度**：建议；**类别**：测试。
- **位置**：细计划 plan.md:312；packages/neuro-book/src/plugins/canon/canon.test.ts:535–555；packages/neuro-book/src/plugins/plot/plot.test.ts:207–234、246–259。
- **现象**：计划要求经真实链路验证项目入口登记计算后的通知。现有 canon 用例是在插件已经启动后轮询 `pending`，验证能读到发现，没有订阅登记事件。剧情用例订阅后推写作指示，断言的是 `reportDataVersion` 的通知；它用 `tree` 游标测数据变化，重启段也没有拿旧 `pending` 游标翻页。
- **为什么是问题**：首次登记若漏发事件，计算仍能在主动重读时生效，报告数据版本也仍可单独通知；这两个用例都抓不到已经打开的窗口没有随登记重读。第 6 条的问题是替换多发一次，本条是首次登记没有链路回归断言。
- **如何核实**：静态对照 K-d1 的应用差异和上述用例的订阅、读写顺序；原审查的临时远程探针已实测首次登记收到 1 条通知，不是现有首次登记漏发。
- **建议改法**：在 canon 的真实项目子进程合同用例中，让窗口先订阅，随后由探针插件经项目门面首次登记；断言收到一条 `diagnostics` 后重读能看到新发现。保留剧情用例验证数据版本，把它的跨重启注释限定于实际核对的行为，不把它当作 `pending` 游标合同。
