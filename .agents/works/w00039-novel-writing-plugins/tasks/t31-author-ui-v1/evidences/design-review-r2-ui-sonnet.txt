### 1. “改这一笔”与变更详情页的“改”在内核合同里没有路径：editInPlace 与 previewEdit 都不能改一条加减补丁带的数
严重程度：阻断
类别：正确性（合同缺口）
位置：author-ui.md 输出 16（累出来的数）、21（变更详情页“数的改动旁有改”）、23（核对点不符“每笔一个改这一笔”）、验收 4、5；revisions.md 输出 8 的路由表与输出 22；plan.md 零、K1；packages/nb-canon/src/world/edits.ts:108-120
现象：editInPlace 的入参是（位置、地址、新值、读到的值、意图），路由由“这个值来自哪”决定。值来自加减（op 为 add）、归纳或核对点时，创作修改一律返回 accumulated-value（edits.ts 第 108-110 行：last.kind 为 reduce、check，或 patch 且 op 为 add、note 时直接 return）。revisions.md 输出 8 路由表第四行也写“改其中某一笔，或记一笔”，但没有说用哪个方法、什么入参去改“其中某一笔”。K1 的 previewEdit 只是“入参同 editInPlace、recordDelta、recordNote”，它的返回里有 route 为 patch（改那条变更里的那一笔），但这个 route 只在“值来自赋值、整段替换、增块”时才会出现。于是：待处理里嫌疑区间每一笔的“改这一笔”（输出 23）、变更详情页里“星瑕的存款 −300”旁的“改”（输出 21）、累出来的数展开来历后“由作者改其中一笔”（输出 16），三处都没有可调用的读写方法。验收 5 的最后一步“点改这一笔改成对得上的数并保存，这一条从待处理消失”是 Smoke 的 e2e 场景，同样做不出来。
为什么是问题：只剩两条路：界面自己从 object 读整条变更、改补丁、拼 WriteRequest 走 preview 和 publish，等于把路由和“发布后值要等于预期”的校验在界面再写一份（上一轮第 1、23 条已经指出过这种“同一规则两份”）；或者内核再补一个“改这条变更的第 N 个补丁的值”的读写方法。第二轮计划的八项补口里没有它，K1 的描述还让人以为 previewEdit 已经覆盖。
如何核实：读 edits.ts 第 95-122 行；grep -n "accumulated-value" docs/specs/canon/revisions.md；读 author-ui.md 输出 16、21、23。
建议改法：在内核补口里加第九项，例如 editChange {change, patch 序号, 新值}（读与写各一个，预览的 route 固定是 patch），写进 revisions.md 输出 8 与 22；或者 Spec 明说第一批的“改这一笔”只对赋值类补丁可用，加减的那一笔只显示、不给“改”，并把验收 4、5 改成可做的场景。二选一，现在两头都不成立。

### 3. 条目页页头的面包屑与“是谁：某某”的数据没有来源：entry 的返回里没有上级、分组、马甲关系，tree 又只能由上往下取
严重程度：重要
类别：正确性（合同缺口）
位置：author-ui.md 输出 6；plan.md 四的读取表（条目页只列 entry、render、chapters、origins、changes、components）；packages/nb-canon/src/engine/types.ts:81-92（EntryView）；project.md 输出 30（planned，tree 的 sameAs）
现象：输出 6 要页头写“设定 › 分组 › 上级条目 › 名字”，上级条目可能是多层；马甲条目要写“是谁：某某”并链接到本体。EntryView 只有 id、deleted、appeared、name、aliases、summary、text、namespaces、upcoming、components，没有 parent、folder（分组）、sameAs。新加的 K4 把 sameAs 给了 tree 的每一项，而 tree 是按父条目往下取一层，不能从子条目反查父。要取只能用 object 读存下来的条目（字段 parent、folder、sameAs 在 EntrySchema 里），再对每一级上级重复 object 加取位置上的名字。计划的“条目页主要读取”一栏没有 object，每个条目页打开的读取次数、以及一个页面里要为上级链各发几次请求，都没有算进去。
为什么是问题：面包屑是 editor.md 里已经有“待回话”标记的东西（开发者问过要不要），而它的数据要 N 次读取，标签条下面那一行在每次切标签时都要重算；输出 6 的“名字变了标题跟着变”也只管本条目，上级改名后面包屑不会跟着变（上级不在“可见的读取”里）。
如何核实：读 types.ts 第 81-92 行与 schema.ts 第 120-130 行；grep -n "sameAs" docs/specs/canon/project.md（只在 tree 的 planned 条目）。
建议改法：二选一：在 K4/K5 里让 entry 的返回带 parent 链（每级 id、nameAt）、folder、sameAs（一个字段，不另发请求）；或者把第一批的页头只写本条目的名字，面包屑与“是谁”降到下一批。（以上是第 3 条建议改法的完整写法，上一行被截断。）

### 4. 标签标题只读“读取层里已有的名字”：刷新后没激活过的条目标签全是“条目”，别处改名后不可见标签的标题也不更新，与输出 6 矛盾
严重程度：重要
类别：正确性
位置：author-ui.md 输出 6、26、验收 2；plan.md 一（title）；editor/web/components/EditorGroup.vue:159-162（页面只在活动时渲染）；EditorGroupHead.vue:78（标签名由 tabLabel 在 computed 里算）
现象：计划写“条目页的标题读的是读取层里已有的名字，不为标题单独发请求；条目还没读到时先显示声明的标题”。页面标签只在活动时才挂载（EditorGroup.vue 的 pageId 取自 activeTab），而读取层只给“前台可见”的读取重读。因此：(a) 刷新后恢复出来 N 个条目标签，只有活动的那个会读到条目，另外 N-1 个标签一直显示“条目”，直到作者逐个点开（输出 6 写了这个回退，但没写它会持续多久，验收 2 只验“两个标签都还在”，不验标题）；N 个同名“条目”标签作者分不出谁是谁，同名提示又只对文件标签生效（输出 56，tab-hints.ts 只喂文件标签）。(b) 条目在别处被改名后，不可见标签的标题要等回到前台才更新，而输出 6 写“名字变了标题跟着变”，输出 26 写“不可见的标签与视图回到前台时重读”，两条没有交代怎样同时成立。
为什么是问题：刷新恢复是开发者明确要的功能，恢复后的标签条是它最先暴露的地方。
如何核实：读 EditorGroup.vue 第 158-162 行与 pages.ts 的 source().title；写一个测试：恢复两个条目标签，只激活其中一个，读另一个标签的标题。
建议改法：恢复出来的页面标签的标题由 title(arg) 触发一次轻量读取（只要名字，缓存，不跟随每次发布重读），读取层给“标题读取”一个独立的类别：可见与否都读，但只读 tree 级别的 nameAt（K4 已有，一页多个 id 合并成一次）；或者 Spec 明说“恢复后没有激活过的标签保持‘条目’”并让标签的悬停提示至少写出条目 id（会违反“界面上不出现记录 id”，所以更倾向前一种）。

### 5. “恢复”由什么记录、谁来判：快照是纯模型，不知道页面声明；声明晚到或贡献方停掉时存盘会把带参数的标签抹掉
严重程度：重要
类别：不变量
位置：editor.md 输出 33 planned 段与“副作用与数据”；plan.md 一（恢复）；editor/web/groups/groups.ts:453-460（snapshot）、466-476（restoreTabs）；editor/web/tabs-record.ts:24-45（schema）；pages.ts
现象：现在 snapshot() 对页面标签一律写 `{page: true}`，restoreTabs 看到 `page` 就把标签从布局文档里拿掉；两个函数都是纯模型，手里没有页面声明。planned 文字只说“声明 restore: true 的页面记页面 id 与 arg，照文件标签恢复”，没有写：(a) 记录的形状（tabs-record.ts 的 schema 是 `Union[{page: true}, 文件标签]`，additionalProperties 为 false，要加第三种；arg 的上限与字符集；版本是否要升）；(b) 判断“这个页面要不要记 arg”靠声明还是靠 PageTab 自带的字段。如果靠声明：刷新后贡献方的入口还没交付（或这次启动激活失败、被禁用）时，恢复出来的标签存在，但此刻声明不在，下一次存盘（任何一次切标签、关别的文件都会触发）就按“不可恢复”写成 `{page: true}`，所有条目页标签在下次刷新时永久消失；规格里“声明在而实现没交付时是‘正在加载页面’”这句保证的是显示，保不住记录。PageTab 要自带 restore 与 arg（恢复时从记录读，打开时从声明抄），snapshot 只看它自己。
(c) 同一个原因，“一直不交付”的终态没写：声明在、实现永远不来时标签停在“正在加载页面”，没有失败文字，也没有超时。
为什么是问题：这条决定刷新恢复会不会静默丢标签；而且是在“canon 入口启动慢或失败”这种平时看不到的路径上丢。
如何核实：读 groups.ts 第 453-476 行；写模型测试：恢复一个带 arg 的页面标签，声明不在的状态下触发 snapshot，再恢复。
建议改法：Spec 写明 PageTab 带 restore 与 arg，snapshot 与 restoreTabs 只看标签自己；记录形状 `{page: true, id, arg}` 写出来，restore 为假的页面仍写 `{page: true}`；“一直不交付”在 Spec 里给一个终态（例如声明在而实现 N 秒未交付仍显示加载，由诊断记录，不加机制），明说是已知限制即可。

### 7. 上一轮第 13、14 条的前提部分不成立：编辑器区本来就是每个标签一个 EditorGroup 实例；真正的缺口是“不活动即卸载”会丢掉未提交的输入，而 Spec 没把它放进标签状态

### 8. ComponentViewContext 对第二批的两个界面不够：没有世界版本信号，record 返回 void 看不到结果，edit 只开确认条但输入控件在谁手里没说
严重程度：重要
类别：规范（接口）
位置：author-ui.md “数据分页的贡献点”、输出 12、14、16、17；plot/shared/contracts.ts（nbook.plot/world 的 knowing、conflicts、experience、goals）
现象：(a) 第二批“谁知道什么”“目标与态度”的数据在 nbook.plot/world 的远程方法里（knowing、conflicts、goals），不在命名空间字段里，而且依赖别的条目（谁知道某个知识点要看很多人的知情列表；一个目标的冲突依赖别的目标）。context 里 fields 只在本条目的这个命名空间变化时才变。别处的发布改了别人的知情，本界面没有任何信号知道要重读：context 没有 version（上一轮第 9 条的建议是给只读的 version，新稿删掉了）。结果是专门界面要么自己去订阅（拿不到读取层），要么显示过期数据，违反输出 26。
(b) record(path, input) 返回 void：专门界面里“记一笔”的输入框在界面自己手里（输出 14），提交后要清空输入、显示失败原因（value-conflict、validation-failed、busy）。record 不返回结果也没有 pending/error 的响应式状态，界面做不到；输出 29 说失败时“确认条或对话框留在原处”，记一笔没有确认条，原因写在哪里没人规定。
(c) edit(path)“让条目页对这个地址打开就地改的确认条”：输出 16 写的是“值的位置变成输入控件，下面是确认条”。值的位置在专门界面的 DOM 里，条目页没法替它换成输入控件。如果输入控件在确认条里，Spec 要写出来（输出 16 的“按字段的声明：数、文字、选项”是在确认条里出控件）；如果在界面里，edit 就还需要把新值交回条目页的 API。现在两种读法都成立。
(d) open 只能开条目或变更；第二批需要打开别的东西（伏笔账本、某一章）时没有出口。第一批可以不管，列一行。
为什么是问题：窄接口公开后就是第三方合同（“公开接口”一节），第二批一开工就要改。
如何核实：用 plot/shared/contracts.ts 的 knowing 与 conflicts 对着 ComponentViewContext 逐项找入口。
建议改法：context 加 `readonly version: number`（响应式，世界版本）；record 与 edit 返回 Promise 或结果对象（成功、失败原因），失败原因由界面自己显示；输出 16 写明输入控件在确认条里。

### 9. 从“改动记录”还原（和任何没有三种页面在前台时的写入）没有反馈：输出 18 的提示只出现在三种页面里

### 10. 条目树的“再显示（还有 N 项）”与墓碑规则不一致：输出 2 隐藏的已删除叶子条目仍计入 N

### 11. 读取层规则里仍有三处没定：写入结果与 changed 事件谁先、缓存的淘汰、标签切回时用不用旧数据
严重程度：建议
类别：正确性
位置：plan.md 三；author-ui.md 输出 26、验收 3、7
现象：(a) 写入返回的 Published 带 version，但 changed 事件走另一条订阅，两者到达的先后没有保证（client.ts 里 publish 是一次调用，订阅是另外几条）。计划没有写读取层是否在写入返回时就把已知版本抬到 Published.version 并触发重读。不抬的话，“保存”成功后提示已经出现，值还是旧的，随后点“撤销”或再改会带着旧的读到的值得到 value-conflict；验收 3 的“保存，Then 值变了、顶上有提示”要等事件才成立，测试要能区分这两种顺序。
(b) 缓存：键是（方法, 输入），输入里有位置、条目、模式，作者来回切位置就产生新键；“没人用的”读取在计划里到底丢还是留没有写，两种都有问题：丢则输出 26 要求的“回到前台时保留旧内容、不出现占位”做不到（页面卸载后读取没人用）；留则没有上限。需要一条规则，例如保留最近的 K 个键，K 取一个数写进 Spec 或计划。
(c) 页面标签不活动即卸载（见第 7 条），所以“切回标签”总是重新挂载一个页面，读取层要给它一份旧数据加后台重读；这对 entry 带 render 的几个读取要一起拿到才不闪，计划没写“同一页面的几个读取一起换”。
如何核实：读 client.ts 的 publish 与 subscribe；读 plan.md 三。
建议改法：写进读取层的三条规则（写入返回抬版本；保留最近 K 个键，K 取一个数；切回时先用旧数据）并各配一条读取层测试。

### 12. Lab 的“录像回放”：只能答录过的输入，写入类场景没有演示办法，并且录像用的服务配置与产品不同
严重程度：建议
类别：测试
位置：plan.md 二（Lab 场景）、技术选型表第四行；packages/nb-canon/tests/sample/replay.ts:30-46
现象：(a) 回放客户端按（方法, 输入）精确匹配。Lab 里作者（或 e2e）一点别的位置、展开另一个来历，读取的输入就是没录过的，回放客户端只能报错或空；条目页的位置选择有 2N+1 个选项，场景若允许切换，要把这些位置都录上，计划只写“每个场景要的那几次读取”，没写没录到的输入怎么办。(b) 写入类场景（确认条的预览、保存、撤销、失败的几种呈现、busy）要预览和发布的返回；回放客户端不会改世界，所以保存之后值不会变，场景只能停在静态。计划没有写这类场景演示什么。(c) 录像用 replay.ts 的服务配置录：reducer 是原型的查表小模型、now 固定，所以人物的“现在的态度”在录像里是归纳过的一句话；产品的世界宿主没接小模型（计划“审查核实出的现状”自己写了），同一份样本在产品里和 e2e 里永远是“还没归纳”。Lab 场景展示的和产品里作者能看到的不一致，Spec 又声明归纳后的写法是 planned。(d) 录像里不能含 status 的 performance.now() 耗时一类，否则“重新生成后一致”的测试不稳；replay 的 now 与 clock 是固定值，所以可行，但要把这条写成约束。
