### 1. “带来的变化”把条目名、简介、主文字块的地址写成 `name`、`summary`、`text[b1]`，违反术语“不出现字段路径”
- 严重程度：重要；类别：正确性（界面文字）
- 位置：`web/entry-heads.ts:61`（`label`）、`web/entry-heads.ts:29-36`（`namespaceField`）、`web/impact.ts:26-29`
- 现象：世界算出的 `impact.values` 的地址除 `<命名空间>.<字段>` 外还有 `entry.name`、`entry.summary`、`entry.aliases` 与 `text[<块 id>]`（`packages/nb-canon/src/world/world.ts` 约 1578-1593 行 `computeImpact`）。`heads.label(path, entry)` 先按 `.` 切命名空间，再找声明，找不到就退到“路径最后一段”：`entry.name` 得 `name`，`text[b1]`（没有点）得整串 `text[b1]`。回执页与还原对话框的“带来的变化”因此写成“星瑕二的name：星瑕 → 星瑕二”“星瑕二的summary：…”“星瑕二的text[b1]：…”。
- 如何核实：在真实世界里（node-world 加 `pageStandIn`，实验文件 `/tmp/review-w00039-t31-s6/x.dom.test.ts`，用 `--config /tmp/review-w00039-t31-s6/vitest.config.ts` 跑）发布一次改名字、简介、主文字块与存款的修订，挂回执页，页面文字里“带来的变化”依次是：`星瑕二的name：星瑕 → 星瑕二`、`星瑕二的summary：星瑕的简介 → 新简介`、`星瑕二的存款：1,000 → 2,000`、`星瑕二的text[b1]：她有 {panel.存款} 元。 → 她有很多钱 {panel.存款} 元。`。同一次修订上方“改了什么”一节倒是把它们写成“名字”“简介”“主文字”，两处不一致，说明 `receipt.ts` 的 `entryField` 已经有这几个词，而 `useEntryHeads.label` 没有。测试只覆盖了外观、存款，没有一例改名字、简介或主文字。
- 建议改法：`EntryHeads.label` 认 `entry.name|summary|aliases` 与 `text[...]`，复用 `receipt.fields.name/summary/aliases/text` 这几个词；找不到声明的字段退到“一个字段”之类的话，而不是 id。补一个改名字与主文字块的回执页测试（这一条与第 2 条在同一个入口修）。

### 2. 未归纳的语义档在“带来的变化”里被写成原始 JSON
- 严重程度：重要；类别：正确性（界面文字）
- 位置：`web/impact.ts:26-29`（`displayText(value.before/after)`），数据来源 `packages/nb-canon/src/world/world.ts:1606`
- 现象：Spec canon.revisions 输出 6 规定：语义档未归纳时存 `{notReduced: true, anchor, events}`，不存全文。`impactLines` 对它调用 `displayText`，对象走到 `JSON.stringify`。实验（`bun run /tmp/review-w00039-t31-s6/a.ts`）：`before={notReduced:true,anchor:"提防",events:1}` 得 `impact.value {"label":"星瑕的态度","before":"{\"notReduced\":true,\"anchor\":\"提防\",\"events\":1}","after":"{\"notReduced\":true,...,\"events\":2}"}`，也就是作者会看到 `星瑕的态度：{"notReduced":true,"anchor":"提防","events":1} → {...}`。人物的“态度”这类语义档是 canon 内置人物界面的主角（`FieldTable` 已经单独处理 `notReduced` 写“还没归纳”），所以这是常见路径，不是边角。S5 的预览（“follows”写法）原先就走同一个 `displayText`，S6 把它抽成 `impactLines` 供回执与还原共用，把问题带进了两处新界面。
- 建议改法：`impactLines` 在值是 `{notReduced: true}` 时按“起点：X，之后 N 条”之类的话写（`fields.notReduced` 已有“还没归纳”），不走 `displayText`；补一个含未归纳语义档的回执或还原测试。

### 3. 还原对话框的预览过期后确认得到 `has-dependents`，对话框停在“没有依赖”阶段、只写“这次改动没有成功”，无法继续
- 严重程度：重要；类别：正确性（时序与状态不一致）
- 位置：`web/revert.ts:176-197`（`submit`）、`web/revert.ts:194`（失败原因只认 `not-revertable`、`author-source-required`）、`web/failures.ts:41`（`has-dependents` 落到 `failure.other`）
- 现象：预览在打开时算一次（`start`），之后不随世界变化重取。对话框开着、预览写着“没有依赖”（phase `ready`）时，如果别处发布了依赖这次修订的后续修订，点“还原”，写入返回 `has-dependents`；`submit` 把它按“别的失败”写成“这次改动没有成功”，`phase` 仍是 `ready`，“还原”按钮仍可用，再点同样失败（每次还换新请求 id）。作者只能取消、重新打开才会看到依赖列表。Spec 输出 22 的失败表把 `has-dependents` 列为对话框要处理的码（有依赖时列出、给“连同这些一起还原”）；“预览只对它基于的版本有效”（状态与转换）。同一份对话框对世界变化没有任何反应，这也是它与确认条（输出 16、条目页 S5 已做自动重取）的不一致。
- 如何核实：真实世界实验（`/tmp/review-w00039-t31-s6/y.dom.test.ts`，输出 `/tmp/review-w00039-t31-s6/out2.txt`）：A 改外观为“银发”，打开 A 的回执页，点“还原这次修订”，等到 `data-phase="ready"`；另一个窗口再发布 B（红发，改同一个字段）；点“还原”。结果：`after confirm: phase=ready | text=还原以后：星瑕的外观：银发 → 黑发这次改动没有成功 | buttons=取消,还原`；第二次点“还原”同样。顺带：对话框里仍写着“银发 → 黑发”，已与世界不符。测试里没有这一条（`receipt-page.dom.test.ts` 的还原用例都是预览后世界没变）。
- 建议改法：`submit` 收到 `has-dependents` 时按同样的写法转到 `dependents` 阶段（失败里带 `dependents`，已有 `start` 里的那段逻辑可抽成函数共用），或在世界版本变了以后重取预览（与输出 16 一致）；补一个“预览之后世界变了”的用例。

### 4. 回执里改“涉及的条目”的剧情变更，条目名读不到，写成“一个条目”

### 5. 变更详情页“每一处改动”对非数值的补丁只写一个地址，不写改了什么
- 严重程度：重要；类别：正确性（对照需求）
- 位置：`web/rows.ts:174-178`（`patchLine`，S6 从 `patchText` 改名导出）、`web/change.ts:93`
- 现象：`patchLine` 只认两种补丁：`add` 数值写“存款 −300”，`set` 写“样子 → 哥哥”；别的操作（`note`、`listAdd`、`listRemove`、`aliasAdd`、`aliasRemove`、`replaceBlock`、`addBlock`、`removeBlock`）一律 `return label`，只剩一个地址。变更详情页的“每一处改动”整页就是为了写出这条变更改了什么（Spec 输出 21），对语义档的 `note`（人物“态度”这类，canon 内置人物界面的主角）只会写“星瑕的态度”，一句“被救了一次”的内容不出现。回执页的 `changeField("patches")` 同样走这个函数。S4 的“情节”分页用它做摘要时这样还说得过去，S6 把它搬进详情页当主内容就不够了。
- 如何核实：`bun run /tmp/review-w00039-t31-s6/c.ts`（对 `note`、`listAdd`、`aliasAdd`、`replaceBlock` 各一条，输出里只有地址，没有值）。测试里的补丁只有 `add` 与 `set`。

### 6. 从设定树新建条目时，提示走了工作台通知，不在新开的条目页顶上
- 严重程度：建议；类别：正确性（对照需求）
- 位置：`web/entries-view.ts:154-155`（先 `notices.show` 再 `options.open(id)`）、`web/notices.ts:44-52`
- 现象：`createNotices.show` 在调用的那一刻按“有没有页面挂着”分流。新建条目时前台若是章节文件（没有三种页面挂着）、窗口里又有工作台通知，`show` 先走工作台通知（只有“看回执”，没有“撤销”），随后 `open(id)` 才让条目页挂上，页面顶上没有提示。Spec 输出 4 写“打开它的条目页，并按输出 18 给提示”，输出 18 写前台是条目页时提示在页面顶上、带“看回执”“撤销”。S5 之前没有这个分流，所以这是 S6 引入的行为差别。
- 如何核实：从代码推断（未复现）：`entries-view.ts` 的调用顺序加 `createNotices` 的分支。
- 建议改法：`options.open(id)` 先发，再 `show`；条目页挂载是异步的（命令、懒加载），所以更稳的做法是新建这条路径把提示交给“将要打开的页面”（例如 `show` 带一个 `forPage` 提示，或开页后再 `show`），并写进待确认清单；也可以接受现状并在 Spec 输出 4 注明。

### 7. 变更详情页：取消或保存完成之后，在途预览的失败会把已取消的草稿重新写回标签状态
- 严重程度：建议；类别：不变量（竞态）
- 位置：`web/change-edit.ts:124-145`（`runPreview`）、`web/change-edit.ts:108-122`（`applyFailure`）、`web/change-edit.ts:232-237`（`cancel`）
- 现象：`cancel`、保存成功都只 `setDraft(null)` 与 `reset()`，不让 `previewRun` 加一。预览已经发出去、结果还没回来时取消，结果回来仍满足 `mine === previewRun`，走 `applyFailure(draft, failure)`；除 `version-conflict` 外都执行 `options.setDraft({...draft, requestId: newRequestId()})`，用捕获的旧草稿把确认条又打开，并把原因写出来。最常见的失败是 `validation-failed`（测试里就有“原文里没有这个数”的用例），在途窗口是一次往返的时间。
- 如何核实：从代码推断，未复现：进程内往返只有几毫秒，窗口很窄，且没有办法在真实运行时里稳定停在这一段。
- 建议改法：`cancel` 与保存成功时让 `previewRun += 1`；或 `applyFailure` 开头先判 `options.draft() === draft`（同一份），不再是当前草稿就丢掉结果。
