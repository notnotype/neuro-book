## 当前状态

2026-11-02 按已接受的内核提案重切 w00039 时新建（Work README 决定表同日）。尚未开工。

2026-11-23 开发者定为下一步，范围改成上面的样子。主会话查了编辑器的做法（一个 Explore 子代理盘点 nb-markdown 与章节编辑器，主会话读 ADR 0038、`canon/rendering.md` 与相关代码），结论是能做：

- **现成的**：章节的富文本编辑器是 nb-markdown 的 Tiptap 扩展组（`createMarkdownEditorExtensions`）加一套编解码器（`src/language/codec/`）。编解码器按块写回：没编辑的块写原文字节，编辑过的块重新写出并读回校验，有 20 来份语料的往返测试。语言是拼出来的（`createMarkdownLanguage([...语法])`），一种行内原子语法（表情，`syntax/sticker/index.ts`）约 120 行：一个 Tiptap 节点、一个分词器、读与写各一个函数。核心语法已有 CommonMark、GFM 的表格与删除线、中文标点旁的强调。
- **要新做的**：一份“条目主文字”的语言，等于核心语法加三种新语法（花括号表达式、`<Ref />`、`<Image />`，都读成原子节点、原文记在节点上原样写回），不带章节方言的批注、提示块、注音那些；内核加一个“整篇主文字换成这样”的写法，由内核切块、与原来的块对比、合成增删改（`splitBlocks` 只从 nb-canon 的根入口导出，浏览器只能用 `./schema`，对比放在内核里）；条目页的文字分页换成编辑器；条目树的就地新建、改名、移动、删除（资源管理器的行内改名与拖动在它自己的插件里，`explorer/web/components/ExplorerRow.vue`、`tree-drag.ts`，不是共享组件）。
- **最大的风险**：同一段文字有两个解析器在读。编辑器用 marked，内核用 micromark 加 mdxjs。MDX 不认缩进代码块、原样 HTML 与尖括号自动链接，文字里的 `{`、`<` 要转义，这几处两边可能读得不一样。兜底有三层：对照语料（编辑器读入再写出逐字节相同，写出的内核必须收）；内核每次保存照 `canon/rendering.md` 输出 1 检查并指出块、行、列；认不出的语法由 nb-markdown 的“原样”语法整段保留。计划的第一片先做对照语料这个探针，过不了就退到“在块里就地改源文字”。
- 章节编辑器的控件 `MarkdownControl.vue`（855 行）绑的是文件文档（`TextEditorBinding`），带工具栏、批注栏与 frontmatter 面板，经 `markdownKey` 交给别的插件；条目用它还是另做一个瘦的控件，写计划时定。

开发者 2026-11-23 定：

1. **编辑器与章节用同一个富文本编辑器。** 同时问“解析器能用一个吗？直接扩展现有的解析器？”，见下一段。
2. **保存：作者自己点“提交”才发布成修订；编辑中的内容默认暂存，防止丢失。**（没按主会话推荐的“离开编辑器时存一次”。）
3. **分组先不变成真的文件夹**：最上层的分组照旧从条目的种类算出来，任何条目下面都可以再建条目。

**一个解析器（待开发者定）。** 主会话的探针（[`evidences/parser-probe.txt`](evidences/parser-probe.txt)）：编辑器用的 marked 加上花括号表达式与标签的分词器，一份带标题、引用、嵌套列表、表格、代码的样本上，顶层切片拼回原文，表达式与标签的位置都对，代码与转义里的花括号不被当成表达式，表达式内容能直接交给 acorn 得到语法树。所以可以只留编辑器这一个解析器，内核改用它：

- 内核的渲染代码约 1100 行（`nb-canon/src/render/`，测试 776 行），要换的是解析那一层与跟着语法树走的地方；给写手简报的纯文字（`renderPlain`）与带值写法的输出不该变，用星瑕样本做新旧对照；
- 反过来让编辑器去接内核现在的解析器不可取：编辑器的读入建在 marked 的词法单元上，换解析器等于再写一套读入；内核现在的解析链在浏览器的开发模式下也加载不了（`docs/modules/monorepo-boundaries.md`）；
- 作者与 AI 写的写法不变（`{panel.魔力}`、`<Ref id="…" />`、`<Image … />`）；变的是不再用 MDX 的解析器，缩进代码块、原样 HTML 这些边角按章节编辑器的规则读。这改了 [ADR 0038](../../../../../docs/adr/0038-world-engine-entry-text-is-whitelisted-mdx.md) 决策 1 的一部分，要另写一份 ADR 部分取代它；
- 探针留下两处：单独成块的 `<Image />` 被读成 HTML 块，要加块级的认法；有一个叶子没在原文里定位上，原因待查。

- 值的显示：把世界里的文字读一遍，按顺序记下“原文到显示”，编辑器里的小块按原文贴；有暂存时没动过的表达式仍显示值，新打的显示原文。
- spike 里与正式做法不同的：分词规则没有与内核共用（内核仍用旧解析器检查）、暂存在 localStorage、拆块在浏览器里做且连续的新段落合成一块、界面文字写死、没有来历与条目跳转、没有“看源文字”。

2026-11-23 三份意见到齐（都在 `evidences/`）：后端 omp 15 条（阻断 6、重要 8、建议 1，[报告](evidences/design-review-backend-omp.txt)），前端 Sonnet 21 条（阻断 2、重要 15、建议 4，[报告](evidences/design-review-frontend-sonnet.txt)），[独立设计](evidences/independent-design.txt)。逐条处理还没写；主会话读完后的判断是计划第 1 稿的核心数据流要改，三处：

- **换解析器比计划写的深，而且牵涉保密。** omp 用真实数据证实：按叶子的 `raw` 回搜定位会静默定位错（链接标题里有同样的表达式、引用与列表去前缀、CRLF、表格的转义竖线）；marked 把认不出的写法当普通文字、acorn 只解析前缀，旧内核拒收的写法（没闭合的 `{`、`{a; b}`、注释里带 `}`）会变成放行；缩进代码、`$…$`、脚注这些新出现的不透明容器会吞掉原来认得出的表达式，简报的保密关卡因此从扣整块变成放行；带值回写的 `scanAnnotations` 另有一套对 Markdown 上下文的猜测。独立设计对照旧解析器跑了 3 万个随机块，约 0.3% 定位不一致，并列了一张读法变化的表。
- **整篇文字表达不了块的身份与顺序。** 分开存的块拼成整篇再读，边界会变（没闭合的围栏吃掉后面的块、相邻的两个列表并成一个、引用定义跨块生效）；两段文字相同的块删哪一段、连续插入的先后、放在剧情新增的块后面，整篇字符串都分不出来；只带世界版本拦不住并发（别处只动了影响显示的剧情对象、章讲的线变了）；“以我的为准”按整篇覆盖会把别处改过、自己没碰的块改回去。方向：逐块读入并带着块 id 装成一份编辑器文档，提交有序的块清单（留下的带 id、新加的不带），内核在写队列里按草稿读到的基线核对，冲突按块判。
- **页面标签这条路要补的东西比计划写的多。** 工具栏与菜单的动作经编辑区的命令找活动的文件文档，页面里点了没效果（spike 实测）；未提交的圆点与保存要挂在页面的声明上，不能挂在只在活动时存在的页面组件上；提交在途、暂存写失败、多窗口、换位置、只读各情形都要有状态。前端审查第 21 条提出上游的另一条路：把条目主文字做成编辑区的一种文档，文档层已有的未保存、保存队列、冲突、关窗确认、控件绑定都能直接用，代价是编辑区要有文件之外的文档来源、页面与文档的关联、只能手动保存的模式，以及刷新后保留未保存内容的能力（文档层现在没有）。
