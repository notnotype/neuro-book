### 1. 叶子 `raw` 回搜会静默换错花括号，不能作偏移算法

- **严重程度**：阻断；**类别**：正确性。
- **位置**：计划 3.1 `sites.ts`、3.2、8；探针 62–84 行；`canon/rendering.md` 输出 8、12、13、15。
- **现象**：`[x](/x "{entry.name}"){entry.name}{entry.name}` 的两处表达式本应在 UTF-16 偏移 `22,34`，探针却给出 `8,22`（第一处落在链接标题里），且零落空，两处都显示 `ok`。引用每行的 `> `、列表续行缩进、CRLF、表格里的 `\|` 又会使多行或表格里的表达式 `raw` 根本不在原文中。实体、反斜杠转义、硬换行和相邻重复表达式在对照样本里不一定失败，不能据此证明游标已落在正确容器内。
- **为什么是问题**：正常渲染会改掉不该动的链接标题，漏掉真正的表达式；拼接、编辑器节点配值和回写的一一对应都失据。探针先用 `indexOf` 取位置，再确认那个位置确实是同样的字，不能证明位置的来源。把范围限到顶层块也挡不住同一段里的反例。
- **如何核实**：`bun /tmp/claude-review-w00039-t28-design/scratch/marked-sites.ts`：真实 marked 执行原探针算法，与当前内核的 `parseBlock` 对照。引用、列表、CRLF、表格各有一处实际表达式找不到；旧内核四处都能读出。
- **建议改法**：不要保留回搜作为优先方案。在 marked 消费输入时携带范围，并把 CRLF、容器去前缀、表格去转义的片段映回源文；JS 解析用逻辑文本，诊断与替换用源跨度，跨行回写还要保住容器前缀。扩展 tokenizer 收到的是转换后的后缀，仅记本地偏移不够；现有 `normalize.toSource` 只覆盖进 lexer 之前的转换。若 marked 无稳定扩展点，比较维护一个锁版本的带位置 lexer 补丁与换上游的代价；前者需守住容器映射并跟随升级，后者需重接章节编解码。映射不可证时显式报问题，不能猜下一个同样的字符串。

### 2. 用 marked 的普通文本兜底与 Acorn 的前缀解析，留不住现有的写入合同

- **严重程度**：阻断；**类别**：不变量。
- **位置**：计划第 2 节、3.1、3.2；`nb-canon/src/render/syntax.ts:91–105,115–162,194–221`；`canon/rendering.md` 输出 1、4。
- **现象**：旧内核把 `说 {entry.name` 和 `<Ref id="e1">` 报为 `cross-block`；探针没有产出任何条目单元，分别落为段落、HTML。计划又把未配平的 `{` 指定为 `mdx-invalid`，实质改码。`{}` 现报 `no-field-expression`，直接走 Acorn 则抛语法错；`{/* 注释里的 } */}` 现放行，探针提前闭括号。`{entry.name; entry.summary}` 现拒收，`parseExpressionAt` 却成功返回只消费 `10/25` 字符的 `MemberExpression`，原有 AST 白名单检查拦不住尾部。`<https://example.test>` 现报 `mdx-invalid`，marked 当自动链接；普通行内代码和链接地址、标题里的 `{` 两边都可原样保留，不能靠全源搜索识错。合法多行 `<Image>` 属性可被探针识别，属性字符串或表达式有 `>` 时则漏认。
- **为什么是问题**：只校验成功识别的单元会把旧的拒收变为普通正文；只检 Acorn 返回的树会放过非白名单尾部。两者都不等于执行代码，但会改变写入、旧块诊断和下游保密结果。原样 HTML 的分词结果也不只 `rawHtml*`：核心先认领 `<br>` 和 `<strong>` 等（`syntax/core/index.ts:135–160`），按“编辑器读成原样 HTML 才报错”守不住白名单，也没定义富文本写出这些标签时内核是否收。
- **如何核实**：`bun /tmp/claude-review-w00039-t28-design/scratch/marked-sites.ts`；核对旧内核的错误码、Acorn 消费长度、合法行内/多行属性和 marked 的分词结果。探针不是尚未实现的新内核。
- **建议改法**：先把候选语法分为「非语法」「形成的条目语法」「形成错误的条目语法」；给未闭合标签、跨存储块、空和纯注释、尾随输入、未知属性与非白名单标签定义失败优先级和源文行列。用完整 JS 词法辨别注释、字符串和标签边界、校验整个表达式而非前缀；明确列出有意改变的输入与旧数据处置，不从编辑器是否能画出来推导放行。

### 3. 合法旧表达式被转成普通源码时，简报关卡从扣整块变成放行

- **严重程度**：阻断；**类别**：安全与性能。
- **位置**：计划 3.1、3.2、5、6、8；`nb-canon/src/render/render.ts:298–345`；`plot/core/brief/gate.ts:334–345`；`plot/brief.md` 输出 8、13、16。
- **现象**：真实 `World → CanonReadView → composeBrief` 中，带四格缩进的 `{ref("e2").entry.name == "保密哨兵值" ? "相等" : "不同"}` 是旧内核接受的存储块，报告 `reads:["e2"]`，简报整块扣下。同一表达式放在 `$…$`、脚注定义内也如此。按拟共用的真实章节 lexer 加表达式扩展分词，三者分别被 `code`、`mathInline`、`footnoteDef` 吞为不含表达式的单元。
- **为什么是问题**：按计划只登记已识别处、沿用纯文字拼接，则三处都没有 `reads/mentions/problems`，关卡按现行逻辑会放行原源码中的绝密条目 id 和作者写在表达式里的秘密字面量；不是未求值的动态秘密凭空出现。`Ref` 漏认同理会让 id 原样出现；图片属性漏认还会消掉 `raw-value`。原本就明确写在普通正文或围栏代码里的秘密不在这条回归内。计划把「缩进代码」单列为允许改输出，更不能以相同样本的快照通过来证明保密。
- **如何核实**：`bun /tmp/claude-review-w00039-t28-design/scratch/brief-and-writeback.ts` 以真实已发布数据和简报入口证明旧关卡扣下；`bun /tmp/claude-review-w00039-t28-design/scratch/editor-blocks.ts` 证明拟共享的 lexer 优先级。新内核未实现，放行是按计划的数据流推导。现有关卡与 40 种子测试覆盖直写引用和表达式，未覆盖这些吞语法的容器。
- **建议改法**：对以前能认出、但现在被当成不透明单元的条目语法保留其依赖，或给出阻止简报输出的诊断，而非静默放行。用实际发布的旧数据及新版写入分别穿过纯文字和真实简报，覆盖缩进、多行引用、转义表格、原样数学和脚注、单独与嵌套的 `<Ref>`、含表达式的图片属性及坏块；断言可见文字、`reads/mentions/problems`，并断言简报无 id/哨兵值、普通对照块仍给出。

### 4. 带值回写还有一套 Markdown 上下文猜测，换 `sites` 不会一起修好

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划 3.2 `writeback.ts` 逻辑不动、第 6 节；`nb-canon/src/render/writeback.ts:52–90,231–274`；`canon/rendering.md` 输出 8、12、13；ADR 0038 决策 3。
- **现象**：回写的 `scanAnnotations` 扫整块的每个 `{`，只跳过反斜杠、反引号和自判的代码围栏；不读链接地址/标题、缩进代码或原样 token 的边界。已经发布的 `[链接](/x "{entry.name}")` 与 `[链接](/x/{entry.name})`，Agent 正常读出原文，原样交回却得 `annotation-mismatch`（既有缺口，不是本次新增）。计划新接受的缩进代码若照章不产注记，扫描器仍会把里面的 `{` 当注记开头；未知标签或引号属性若新增透传，也有同类不一致。
- **为什么是问题**：计划验收只比读出的字符串，既抓不到既有读写冲突，也守不住新增语法的原样交回。注记文法应保持独立（ADR 0038 决策 3），但不能再独立猜哪些位置属于 Markdown 正文或属性。
- **如何核实**：`bun /tmp/claude-review-w00039-t28-design/scratch/brief-and-writeback.ts`：实际发布、从真实只读视图取带值写法，再经内核 `writeBack`，两条链接均失败；同脚本的正文、跨行、图片属性和围栏对照均无新修订。
- **建议改法**：让同一语法入口持有 Markdown/标签的识别范围；回写只在它允许的位置解独立的注记文法（可用注记模式扩展），逐处核对新旧对应。将「原样交回无修订」「只改一个值不会改其余字节」「删/重排注记整批拒收」纳入切换验收，不只比读路径。

### 5. 相同词法器分别解析存储块与拼接整篇，会丢块边界并让 `parts` 移位

- **严重程度**：阻断；**类别**：正确性。
- **位置**：计划 3.1、3.2 `parts`、3.3、3.5 的拼接；`nb-markdown/src/language/codec/read.ts:234–263`；`canon/rendering.md` 输出 3、4、7。
- **现象**：三个分别可保存的块 `b1="\u0060\u0060\u0060\n甲"`（未闭合代码围栏）、`b2="末尾 {entry.name}"`、`b3`（普通段落）按双换行拼起来时，围栏会吃掉后续全部；两个分别可保存的 `- 一`、`- 二` 拼起来则是一个列表。分开的 `[文档][x]` 和 `[x]: /doc` 拼起来后第一块从正文变成有效链接。共享 `segment` 或加空行不能维持原存储边界。
- **为什么是问题**：内核承诺按存储块独立解析，其结果与坏块诊断隔离；编辑器的整篇 lexer 按整篇范围做合并、吸收与引用定义解析。一段字原样往返成功不等于 `parts` 与节点还能一一对应，也不等于修改另一段不会重写原块 id。
- **如何核实**：`bun /tmp/claude-review-w00039-t28-design/scratch/editor-blocks.ts`，旧内核接受例中各个独立块，真实章节 lexer 的 `normalize/segment` 对双块分别和拼接读取得到上述不同结果（围栏、列表均为 2 → 1；引用式链接的 token 类型改变）。
- **建议改法**：把存储边界作为输入，不用合法 Markdown 字符冒充边界；按块解码、带着 id 和来源装配为一个编辑器文档，改变边界时明确提交哪些块被拆并。若坚持持续以整篇为唯一真相源，须先重新设计块的存储/解析合同和历史转换；不是加一个 lexer 一致性快照就能切换。


### 6. 只带世界版本不能为整篇草稿拦住并发写入
- 严重程度：阻断
- 类别：正确性／并发
- 位置：计划 3.3、3.5 的“提交”“世界变了”、6、8；`canon/revisions.md` 输出 7、8、25，`canon/worldlines.md` 输出 12；`entry-edits.ts` 的 `planEntries`/`routeSet`、`world.ts` 的发布冲突检查。
- 现象：提交前，别处只动了影响本条目显示的剧情对象，条目对象本身没动。按当前块对比旧草稿，别人删掉的段能被当作“我的新增”重新写入；作者看不到承诺的冲突确认。即使没有新修订，换“跟着章”的线也能把旧稿拿到另一条线上重算。
- 原因：`baseVersion` 按最后实际写入的对象查，不保护参与读取、却没被改写的剧情对象；按当前状态先对齐再发布，更换了比较基准。普通 `ReadPosition` 不带 `line` 时依赖活页夹，后者会在世界版本不变时变化。暂存虽记旧块，计划里的 `text` 请求不带旧块/可核对的读戳；仅窗口先重读仍挡不住重读和进入写队列之间的竞争。
- 核实：`bun …/scratch/entry-edits.ts` 经 `WorldService` 的写队列和真实分段日志：版本 3 读到 `b1=甲·剧情值,b2=乙`，别处在版本 4 加 `c2` 删 `b2`；按计划对当前块生成 `set b1`、`addBlock 乙 after b1`，用旧版本 3 仍发布成版本 5，路线是改 `c1` 和初值，读回 `b3=乙`。这是现有增改操作的真实行为，不是尚未实现的 `text` RPC。`entry-edits-service.test.ts:60–74` 已有位置所用的线变化、版本不变的用例，现有 Agent 路径因另带 `readStamp` 才拒收；`render/entry.ts:50–51` 的带值回写已有固定实际线的先例。
- 改法：在同一写队列、对齐前校验草稿真正读过的基线：固定解析后的线、位置、模式，比较有序的块 id、源文及路由依赖的来历；若要把与本条无关的修订也视作冲突，可以沿用更严格的读取戳，但要明定产品语义。“以我的为准”也应比较作者刚确认的那一份新基线，不能只抬版本；再次竞争要再问。用真实服务覆盖 `c2`、章讲的线变了、确认后又有新写入，以及无关条目更新不被误报（若选择按条目比较）。

### 7. 整篇文字无法无损表达部分合法的块顺序和身份
- 严重程度：阻断
- 类别：正确性／合同
- 位置：计划 3.3、3.5、S3 与验收映射；`entry-edits.ts` 的 `addBlock`/`removeBlock`、`routeSet`、`usedBlockIds` 和候选读回；`canon/revisions.md` 输出 25。
- 现象：连续插段的次序、放在剧情新增块后面、拖动或删除两个同文不同来历段中的一个，都不是“按原文对比”就能得到的结果。例如原来 `b1=相同,b2=相同`，删第一段与删第二段得到完全相同的 `value`，却应保留不同 id；若其中一个来自剧情变更，连该不该拒收都不同。在当前规则下局部增块有效，不等于拼起来的整篇顺序正确。
- 原因：整篇字符串没有保留来源 id；`addBlock` 改设定只认初值锚点，省略 `after` 是追加，多个操作复用同一个锚点是逐个往它后面插；批量候选读回核对各块取值，不比整篇有序序列。`set` 可以就地修改提供当前值的剧情记录，`removeBlock` 却不能按创作修改删掉被剧情碰过的块，不能用删加替代移动或修改而保持来历。见第 5 条：原存储块也不等于一个词法顶层单元。
- 核实：`bun …/scratch/entry-edits.ts` 经真实 `WorldService`：紧跟 `b1` 按 `X,Y` 发送两个增块，实际读回 `甲,Y,X,乙`，且一次发布成功；省略 `after` 到末尾；指定剧情块 `b99` 或同批先删除的锚点得到 `element-missing`；改设定删剧情块得到 `element-from-change`；删完纯初值段成功且读回 `[]`。同文两块是输入合同的不可区分性，不是声称复现了未实现的差分。
- 改法：把编辑请求改成保留原块 id 的有序快照或显式块编辑序列，新块交内核分配 id；保留旧块边界，明确拆、并、移动、空文与缺省锚点的语义。若不做移动/重排或不能把初值块准确放到剧情块后，先拒绝并解释，不交换源文或删加来伪造结果；若要支持，先设计初值和剧情各自的顺序规则。候选发布前按选定位置核对整篇有序块；S3 增加同文不同来历、连续头插/中插、剧情锚点、同批删锚点与删空。

### 8. 展开操作后的上限与零改动的发布语义没有定义
- 严重程度：重要
- 类别：合同／测试
- 位置：计划 2、3.3、S3、6；`core/schema.ts:405–416`，`entry-edits.ts:419–420`，`world.ts` 的 `publish`。
- 现象：外面是 1 项 `text`，粘贴 51 段便能展开为 51 项。照现有上限执行会拒收；拆批又违反一次提交只发布一条修订。只有一项且新旧相同，照常调用底层发布会写出一条没有对象改动的修订。
- 原因：现有 1–50 是公开入参和 `planEntries` 自己的校验；新设计没有分开定义公开项数与内部分解预算，也没有定义零改动时的返回和草稿清理条件。
- 核实：`bun …/scratch/entry-edits.ts` 实走写队列：51 项 `addBlock` 返回 `validation-failed/type-mismatch`（“a batch has 1 to 50 operations”），日志不动；同一服务低层 `publish` 空 `puts` 成功推进版本并追加 `ops:[]`。这验证了两条现有路径，不是 `text` 已实现。
- 改法：明确公开批项数、单篇字节/块数、内核展开工作量的边界，不拆成多个修订；零变化走明确的“不发布”结果，混合批只发布剩余真实变化。验收覆盖 50/51、大块数的短段落、改回原文再提交、只剩其他项的混合批。

### 9. 暂存只按条目寻址，没定义窗口、位置与线的并发归属
- 严重程度：重要
- 类别：不变量／存储
- 位置：计划 2、3.5 的“暂存”“世界变了”、6、8；`storage/persistence.md` 输出 1、4–8；`shared/storage.ts:41–69,182–215`；`EntryPageHost.vue:108–119`。
- 现象：两个窗口在不同章或线上编辑同一条目，按计划会争同一格；第二个窗口自动保存或第一个窗口提交后的清理可能盖掉／删掉另一份。恢复时若只看条目 id，会把子线草稿带进主线或另一读取位置。计划还漏了 `defineRecord` 必填的 `locality`。
- 原因：`scope: project` 仅选分区；`local` 按客户端身份，不按窗口。同一浏览器配置的多个窗口同名记录共用；Storage 的条件写删必须用记录 `revision`，不能用草稿的世界 `version`。`update` 冲突后重算不等于可以用旧草稿覆盖新载荷。
- 核实：`bun --tsconfig-override tsconfig.json …/scratch/drafts-storage.ts`（从应用包运行）经真 Storage 插件、路由与 SQLite：客户端 1 的窗口 B 读到 A 的 local 草稿，客户端 2 看不到；B 按旧 `expect` 写返回 `conflict`，B 写下另一位置的草稿后 A 按旧戳删也返回 `conflict`；删除后旧保存不能复活；项目入口打开 local 为 `no-client`。不同位置存在值里，不影响寻址。
- 改法：明确作者草稿是单份独占还是允许多份。前者第二窗口/另一位置须提示接管或打开原位置，条件保存与条件删除保留别人的版本；后者用可恢复的草稿 id 隔开。写下固定线与读取位置，打开时同条目也不跨位置套稿；删除／还原、位置失效时保留待处置的草稿，不自动套用或清空。验收用同配置两个窗口，以及同窗口切章、切线、删除后还原。

### 10. 暂存和发布缺少待确认态，立即退出或断线可丢稿、复活或重复尝试
- 严重程度：重要
- 类别：不变量／失败恢复
- 位置：计划 3.5 的“暂存”“提交”、3.6 不加关闭确认、S7/S8；`canon/project.md` 输出 7、16 与场景 7，`storage/persistence.md` 写入失败合同；`canon/web/world.ts:485–503`，`editor/web/area.ts:685–730,1177–1184`。
- 现象：最后一次输入还在防抖或 RPC 未确认，立刻刷新或关窗就可能取回旧稿。一次提交已发布、回复丢了或草稿没删掉，刷新后仍可能显示“未提交”；提交在途时继续打字，成功回调若删除最新快照会误删较新的输入。
- 原因：草稿 SQLite 与世界分段日志没有共同事务。现有编辑器关窗结算只遍历文件文档；浏览器卸载不等异步 RPC。`world.write` 会查 `outcome`，但链路仍断时把 `unknown-outcome` 交还；草稿格式不保留待提交的 `requestId` 与冻结输入，重开的实例无从区分“没提交”和“发过且已落日志”。Storage 自己的未知结局要重读，并非查世界 `outcome`。
- 核实：计划明确“停一会儿写”“成功后删”，没有关窗结算协议。`entry-edits.ts` 探针实际复用同一请求 id，拿回版本 5、`repeated:true`，日志只有一条该请求；`tests/service.test.ts:774–788` 有写盘结果不明后重开的持久化合同。未模拟新编辑器或浏览器卸载。
- 改法：分清内存编辑代次、已确认的存储 revision、发出的世界请求。提交前冻结这一份草稿并耐久记住请求；重开／重连先查结局，确定成功才条件清理该快照，确定失败留稿，结果不明不另发新 id。串行化暂存保存与清理，晚到回调不得清掉后来输入。宿主可等待的关窗先结算草稿；浏览器刷新/卸载需要本地耐久路径，或只在确实还未存下时阻止退出，不把防抖 RPC 当作已保存。用停在具体确认点的验收覆盖立即刷新、响应丢失、清理失败和提交期间继续输入。

### 11. 1 MiB 暂存上限与整篇可提交范围不一致
- 严重程度：重要
- 类别：正确性／容量
- 位置：计划 2、3.5 的“暂存”、6；`storage/persistence.md` 定义表，`canon/project.md` 输出 18，`canon/web/client.ts:22–30`、`canon/shared/contracts.ts:37`。
- 现象：存在已暂存但只要原样提交就会被拒的大稿；也存在正文远没到 1 MiB、却因为与基线各存一份而无法暂存的大稿。标“超了就不暂存”不说明发布／读取是否还可用，尤其和“关窗后还在”的承诺冲突。
- 原因：1 MiB 是 Storage 的 UTF-8 JSON 值上限，不是正文字数或端到端 RPC 预算。暂存同时含现稿、旧块原文与元数据；Canon 请求预算仅 983040 字节（1 MiB 减 64 KiB），整篇回传也有响应预算。
- 核实：`bun --tsconfig-override tsconfig.json …/scratch/drafts-storage.ts`：真实 SQLite 接受 1000100 字节的草稿；它的拟提交入参用产品 `encodedBytes` 计算为 1000186 字节，按现有客户端预算会在发送前被拒（`text` RPC 尚未实现）。两份 17.5 万中文字符的正文各约 525 KB，暂存包 1050089 字节，真实 Storage 返回 `too-large`。`canon.test.ts:374–395` 已有现有链路请求超限与读回超限的例子。
- 改法：发布与暂存各量实际编码包；明确最大支持的整篇编辑范围和旧大稿仍可用的块级路径。不必为了并发再存一份大原文时可用有序摘要或轻量基线。提前报告无法耐久暂存／无法提交并保留作者输入；测试覆盖多字节、JSON 转义、草稿能存而 RPC 不能发及反向场景。

### 12. 文法子路径不等于纯内核依赖闭包，现有验证也不检查这个闭包
- 严重程度：重要
- 类别：包边界／发布
- 位置：计划 2、3.1、3.2、4、S1/S2、7；`nb-markdown/package.json:15–28,34–51,67–80`，`nb-canon/package.json:2–12`，应用 `architecture.test.ts:81–84,109–125`；ADR 0029 决策 2–5。
- 现象：`nb-canon → nb-markdown/grammar` 能让服务端在运行时不加载 Tiptap/Vue，但 `nb-markdown` 的包级依赖仍会随安装拉进 nb-ui、Tiptap 与 Vue peers。反向让已发布的 nb-markdown 引 `nb-canon/text` 也不成立：后者是私有包，除非另作发布决策；两边互用还会变成环。现有应用架构测试只匹配 canon 根与 `/node` 的直接导入，不递归验证新子路径，更不是发布入口的安装验证。
- 原因：`exports` 管源码入口，不改变安装清单。直接单向依赖在当前应用内可行：应用已装两个包、服务端包由 `pack-app.ts:133–144,254–257` 打入 bundle；不能因此宣称单装内核不拉 UI，也不必因此发布 nb-canon。`scripts/release/packages.ts:18–29,218–227` 的发布校验不允许已发布包依赖未发布的内部包；`pack-smoke.ts:217–254` 只抽查既有 nb-markdown 入口，计划未给 `/grammar` 独立消费者取证。
- 核实：对照两份 manifest、应用 bundle 外置清单、发布包清单与 smoke 的导入列表；未跑打包，新入口尚未存在。
- 改法：明确要求的是“运行/打包不触及 UI”还是“安装也不带 UI”。前者保留单向子路径，在真实 Bun 冷导入、浏览器构建和已打包的 nb-markdown 最小消费端各走一次，检查传递 import；后者才把纯文法下沉到独立包，同时把它作为 nb-markdown 的发布依赖纳入 ADR 0029 与烟测。两个方案都不让 nb-markdown 引私有 canon，也不为此扩大 canon 根入口的浏览器可见面。

### 13. S2 提前换掉作者渲染 DTO，现有消费方要到 S7 才迁移
- 严重程度：重要
- 类别：正确性／切片
- 位置：计划 3.2 的 `{id,source,parts}`、5 的 S2/S7、6；`render/render.ts:170–182`、`canon/shared/contracts.ts:387`、`EntryPageHost.vue:190–193`、`EntryText.vue:48–49,115–122`。
- 现象：S2 按表删掉 `tree` 并返回新 DTO 后，S7 之前现有文字页收到成功块时仍取 `block.tree` 并访问 `node.children`。S2 所列内核、简报与静态架构测试不执行这条作者读路径；TypeScript 也不替它拦。旧块的失败分支现在另带 `error` 和原文，新形状还没写怎么保留诊断。
- 原因：远程合同把 `blocks` 声明成 `unknown[]`，应用作本地断言；生产者与消费者迁移摆在不同提交，没在同一个黑盒合同下验证。原 `canon.test.ts:390–395` 用 mdast 比源文大作为“响应超限”样本；换 DTO 后不能靠这个形状继续触发超限。
- 核实：跟踪现有 `WorldService.render → CanonOutputs.render → EntryText` 的字段与测试断言；访问 `undefined.children` 是按新计划推导，不是已实现版本的运行结果。
- 改法：远程 DTO 与唯一生产消费方安排在同一可独立验证切片；给作者响应定义带诊断的失败块，将 `blockId`、行列与可用于核对 `parts` 的来源纳入合同。加真实 canon 远程读取的成功与坏块场景；超限压力用实际超预算的响应，不绑旧树大小。

### 14. 批量失败的现有路径不能定位到作者刚编辑的草稿块
- 严重程度：重要
- 类别：合同／失败恢复
- 位置：计划 3.2、3.3、6、8；`canon/revisions.md` 输出 25；`nb-canon/src/world/world.ts:99–106,1338–1342,1392–1399`；`canon/web/failures.ts:18–29`。
- 现象：在真的服务里新增非法源文 `新写\n{entry.name`，返回 `cross-block`，路径为 `init.text[b4]`，行列只拼在说明末尾 `(2:12)`。`b4` 是服务端为候选世界分配的 id，失败后没有发布；它不是草稿里的标识。改给出该块的剧情补丁时，校验路径是那个记录的 `patches[n]`，也不是本次输入的位置。
- 原因：分解后的项序号、内部记录路径和作者编辑快照的位置是三套坐标。现有 `Problem` 没有结构化行列；当前 UI 只取第一条 `message`，计划只写“照现有规则校验”，没有规定回映。不能从文案解析括号行列或用候选块 id 去找编辑器节点。
- 核实：`bun …/scratch/block-id-history.ts` 经真实 `WorldService` 写队列；坏块请求没有进入分段日志，重开后只有合法的三块。剧情路径依据现有验证函数；新 `text` 未实现。
- 改法：编排层把内部失败回映到原输入项和该快照内的草稿块键（或有明确合同的序号），语法诊断带块内结构化源跨度；区分不能归到某个草稿块的整批失败。验收用同批合法改段和非法新段、路由到旧剧情补丁的改段；检查能定位、整批不发布、草稿不丢，返回过期诊断时不把光标跳到后来的内容。

### 15. 现有规模脚本不能给出新解析器的冷读回归证据
- 严重程度：建议
- 类别：测试／性能
- 位置：计划 S2、第 7 节、第 8 节“热路径”；`nb-canon/scripts/scale.ts:109–128`；`neuro-book/scripts/perf/canon-scale.ts:78–88,171–175,213–217,266–289`；`scripts/perf/plot-scale.ts:244–251`。
- 现象：内核规模脚本抽 50 次 `engine.entry`，不走文字渲染。应用的 Canon 脚本确实量 10 次作者渲染，但这 5 个热门条目的 `source` 完全相同，建样本时的发布校验已读过；重开服务也没重启进程。清楚看到热读变化不代表测到了新 lexer、跨度映射或坏语法失败的代价。简报在另一脚本量，不能从作者渲染耗时推出。
- 原因：`parseBlock` 的缓存按源文、保存在模块内，不按条目 id 或服务实例分开。大量条目重复同一块不会制造大量冷解析。另一个容量假设是“几十到几百块”：一万行各一个汉字、以空行分段，源文只约 50 KB，常规二维 LCS 在展开限制生效前就可到一亿个格，即使实际上只改一处。这里是算法成本推导，不是实测的性能退化。
- 核实：对照两份规模脚本的样本和调用链、`render/syntax.ts:78–88` 的缓存；未跑性能脚本。
- 改法：原脚本继续守现有世界读写预算；S2 另以同一份预先生成的旧日志在两个新进程打开后首次渲染不同源文块，分开报冷／热读、响应字节与真实 `composeBrief`。包含长嵌套块与坏语法，不把数据生成统计进渲染。S3 先限定实际对齐工作量；若请求已保留块 id，优先按 id 对齐，不为相同段落重做全文 LCS。

## 未发现问题的方面

- 仔细检查后没有发现范围安排与已确认决定冲突：复用章节富文本与解析基础、保留白名单解释不执行 JS、直接编辑为改设定而剧情变化仍走块操作、条目树另做且分组不变成文件夹。这里是意图一致，不是写法、回放与退出恢复已经兑现。
- 仔细检查后没有发现必须给 `canon_write` 加整篇操作或给应用新开远程方法：`canon_write` 有独立的操作输入与转换，不是直接把 `EntryEditsSchema` 给 Agent。沿 `editEntries` 的真实写队列，候选校验可在落盘之前执行；跨进程尾部前进时会吸收日志再重算，前提是基线比较与展开也在同一个 `compute(world)` 内。
- 仔细检查后没有发现常规 Agent API 必须看见草稿：只要草稿留在 `nbook.canon` 的 Storage 命名空间，不注入 Canon、简报和文件读接口即可。探针证明同名的 `nbook.agent` 记录读不到；这是服务接口隔离，不是获批 `shell`/`eval` 的宿主文件权限隔离。Spec 验收应覆盖常规 Agent 只见提交前旧版、提交后新版，且提交前没有改动记录。
- 仔细检查后没有发现必须把章节的完整方言带进内核：`createRawSyntax` 依赖配置的标签名，脚注、数学、原样 HTML 与重复引用定义的兜底是共享分词，但本身会影响条目读法（#2–3）。公用词法器允许按语言装配；明确定义条目装哪一组，不引用章节注册表，也不让 `nb-markdown` 回引私有 canon（#12）。

## 第 8 节风险逐项判断

1. **旧文字读法：未兜住。** 快照是必要基线，但必须区分可直接读、有意改义、只能保留并诊断，以及旧块允许怎样修；用旧日志真正重放，再经作者／Agent／简报读取和原样回写，并验只改其他内容不重写旧块（尤其 `world.ts:1392–1399` 会重验被改剧情记录的每条文字补丁）。新旧两边都没认出依赖也不能算通过（#2–5、#13）。
2. **marked 偏移：已证可静默定位错，不是待观察的单个叶子。** 把源跨度与容器映射前置为 S1 的切换门槛；探针中 `slice` 再比相同的字不足以验位置，不能在 S2 仍以回搜为主（#1）。
3. **章节控件嵌入：退路可行，但不等于已验证主方案。** 主工作区 spike 记录已证实文件命令不认识页面标签里的编辑器；S5 要取“动作实际改了该文档”的证据，且不能让 Canon 直接导入 Markdown 插件内部组件。若抽不出共同宿主，才用公开编解码器和扩展拼瘦壳；同一个编辑核心的决定不变。
4. **并行改动：现有缓解部分成立。** 短切片、合入最新基线与章节 e2e 可减小冲突，不能替代可独立验证的生产/消费切片与依赖闭包；给 S1/S2 添浏览器与 Bun 的入口消费证据，作者 DTO 切换不要跨 S2/S7 留断层（#12–13）。
5. **暂存与世界不同步：未兜住。** 当前块重比加旧版本有真实反例；明确固定读取位置与条件发布、恢复后的存储冲突、未知结局与关窗耐久。验收至少穿过两窗口或两项目进程、同版本换线、确认覆盖后再竞争、未确认保存时刷新（#6、#9–11）。
6. **某一块校验失败：整批拒收的底座已有，定位和边界未兜住。** 现有错误指向候选块或剧情内部补丁，需回映原草稿，验有序全文、零改动、展开上限、失败后版本/日志/事件不动且稿仍在（#7–8、#14）。
