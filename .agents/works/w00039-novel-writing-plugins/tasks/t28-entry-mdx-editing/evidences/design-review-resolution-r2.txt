处理写进了计划第 4 稿（plan.md）。

核心改法有两处，多条发现由它们一起解决：
甲. 提交带内核现有的读取戳（readStamp）。探针 stamp.ts 的结果：别处改了不相干的条目，只带 baseVersion 的请求照样发布，带旧戳的请求得到 stale-read、世界不动；重读后的戳通过；同一个请求 id 原样重发先判请求 id、拿回第一次的结果；被拒收的请求晚到仍是 stale-read。所以“世界还是我读的那一版”由内核在写队列里保证，界面被拦下后重读、把改动对到新的块上（纯函数 rebase），没有冲突才自动再发。
乙. 内核给一个读取 textBlocks，逐块给出改字会写到哪、碰过它的变更、加块该写的锚点、在初值里的位置；与写入的拒收用同一份判断。界面按它决定按钮能不能用。

1. 用前一个初值块当锚点，新块会放错位置（阻断）：成立，已复现（初值 [A,B]、剧情在 A 后加 X，作者在 A 后加 Y 读回 [A,X,Y,B]）。改：内核里“A 与 X 之间”表达不出来，界面不提供这个位置（不能插在剧情加出来的块前面）；紧跟在 X 后面的位置用 X 的 anchor（追到的初值块）表达，读回就是 X 后面。addBlock 的 after: null 与同一处几项的先后只改这一次请求怎样排，不改补丁的执行与旧日志的重放（照审查的建议）。Agent 工具把 null 传下去。别处同时在同一处加了剧情块时，新块排在它后面，这是内核现有的确定顺序，不算冲突。
2. 删掉被当作锚点的初值块，连带抹掉剧情加出来的块（阻断）：成立，已复现（[A,X,B] 删 A 读回 [B]）。改：这是内核现有规则的缺口：touchedBy 的注释写的就是“从初值去掉它会让那些变更套不上”，却只查了地址是这一块的补丁。匹配加上“以它为锚点的增块”，拒收仍是 element-from-change。textBlocks 的 fixed 用同一个函数。不改输出 4（别的线上的变更因此套不上，仍照输出 4 记为这次修订带来的影响）。
3. 抬高 baseVersion 再发会放行写错身份或来历的块（阻断）：成立。改：甲。重读以后由 rebase 按块的原文、write、fixed 对，来源变了的与原文变了的都落成冲突交作者选。块 id 复用（删掉尾块后新块用同一个编号）不改发号：带着读取戳，旧稿不可能写到复用的 id 上；Agent 的写入工具从 t37 起也带读取戳（待确认清单 2026-11-19 的那一行），同样不会。已删除的条目上删块会成功、加块得到 result-mismatch（探针 stamp.ts 证实）：改成拒收 field-unavailable。
4. “选我的”保证不了在原处恢复消失的块（重要）：成立，改。冲突分三种：两边都改了（选我的是把读到的原文换成现在的，选现在的是去掉我的改动）；这一块被删了（去掉我的改动，或当作新加的一块留着，新编号、位置照加块的规则，放不进去时在那一块下面写明）；现在不能删了（只能撤掉删除）。两边改成一样的、两边都删了，当作已经一致，不问、不多发修订。
5. touchedBy 的“最近改动”不是可删判据（重要）：成立，改：乙。不再给通用的 entry 读取加 inInit、touchedBy（S0 的 Spec 草稿里拿掉）；textBlocks 的 fixed 就是删块的拒收条件（这条线上没撤销的变更，不看先后、实际还是计划、生效与否），用例断言两者一致。扫一遍这条线上的变更，不逐块重扫；只在进入编辑与重读时调用。子线上删初值的块让主线的变更套不上，是现有语义（输出 4），不改。
6. 锁住“按计划”开关不能代替冻结读取位置与模式（重要）：成立，改。只有实际模式能进编辑；textBlocks 随块一起返回服务器解析后的位置（写明线），稿存的是它；有稿时位置与开关锁在上面。位置失效（章被删、线不在）时只给复制与放弃，不自动改绑到别的位置（窄，取简单的做法）。
7. 暂存的写入、放弃与清理要按同一代结算（重要）：成立，改。这个窗口对一个条目的写串行，都带上一次确认的 revision；别的窗口写过就停止自动暂存、告诉作者、由作者选用哪边；放弃与提交成功以后迟到的保存按本地代次丢掉；提交成功后按冻结那一版的 revision 条件删除。
8. outcome 的“没发布”可能早于原请求落盘，不能据此换请求再发（阻断）：成立。改：发出前把请求 id 与读取戳写进稿并等存储确认；pending 在的期间稿不能改，请求能逐字重建；结局不明时留着 pending，只原样重发同一个请求。不用 outcome 判“没发布”；world.write 返回的 write-failed 在这里同样当作结局不明。迟到的原请求带同一个戳，世界一动就过期。没有存冻结的整份输入（审查的另一个选项）：稿不变时重建出来的输入相同；代码升级使重建的输入不同、而原请求其实发布过时，内核返回 request-id-reused，按已发布处理。
9. 拆或并跨了写回来源，别的时点的文字变了（阻断）：成立，已复现。改：拆与并只在没被碰过的初值块上提供（并还要求两块在初值里相邻）；被剧情碰过的块只能改字。这改了第 3 稿“能拆”的说法，告诉开发者。内核不加拆、并的专门操作：一批里的 set、addBlock、removeBlock 各自合法，判断在界面这一层，依据是内核给的 fixed 与 write；读取戳保证判断时看到的就是写入时的世界。
10. 阅读视图的剧情改与删只带版本（重要）：成立，已复现（旧版本的剧情 set 盖掉了别处刚换的字）。改：三个剧情对话框的写入带打开时的读取戳；被拦下时重读这一块，原文没变就带新戳再发，变了就在对话框里写明、把“原来的”换成现在的。
11. 200 KB 的进入上限保证不了存得下、发得出（重要）：成立，改。稿只存动过的块，不再按条目大小限制进入编辑；存不下与请求超预算各有状态，那一行分清“已暂存”与“没有暂存”。
12. 现有的错误字段对不回草稿的块（重要）：成立，已复现（加块的原文不合法时指到 init.text[b3]，没有序号）。改：checkPlan 给能对上的校验细项补 op；整批的失败（章不在、太大）走页面那一行。冲突的两边不由内核返回，界面重读后自己对，所以没有“一次回几块原文超出输出预算”的问题。块内的行列不结构化，原因的文字里有。
13. 超过 200 KB 的旧条目失去小块的创作修改入口（重要）：成立。随第 11 条解决：没有按条目大小的门槛了。
14. 50 项是一次能发布的上限，不是草稿能编辑的上限（建议）：成立，改。compile 先算净变化，超过 50 项时提交不可用并写项数，稿照常能改；净变化是零时不发请求、直接删暂存。
