### 1. 冻结暂存实际没写进去，确认却直接发布，重开能把同一块再发布一次

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`packages/neuro-book/src/plugins/canon/web/text-drafts.ts:214–226,252–272,414–420,482–500`；`text-drafts-link.test.ts:204–235`。
- **现象**：先正常暂存增块稿（SQLite revision `1`，无 `pending`）。另一 SQLite 连接持写锁，冻结保存返回 `busy`，在真实回复帧丢失后窗口得到 `unknown`。锁释放并重连，“确认”直接发 Canon，没有先核对或写回冻结；Canon 发布了，回执再丢。SQLite 仍只有 revision `1` 的普通稿。重开同一客户端身份下的条目，提交这份稿又发布一次，读回 `A、只想加一次、只想加一次`，同一条目有两条增块修订。
- **为什么是问题**：首轮修法只覆盖“冻结确实写了、回执丢了”。`confirm` 把内存 `pending` 当成了持久化凭证，绕过 `freeze` 的“确认冻结成功才发”门禁。请求 id 去重只保护原 id，重开的普通稿会生成新 id。base 的 `freeze` 对这次存储失败会回 `not-saved`，不会在同一窗口继续发布，故是此次修法引入的独立分支。
- **如何核实**：在 `packages/neuro-book` 执行 `bun --tsconfig-override tsconfig.json /tmp/claude-review-w00039-t28-impl-r2/scratch/app-cases.ts freezeNotStored`。真实 SQLite `BEGIN IMMEDIATE` 制造争锁，只丢 Storage `save` 与 Canon `editEntries` 的真实回复；断言两次独立发布、见证窗口两次都读到原 revision。
- **建议改法**：分别表示“冻结的存储结局未定”和“已持久冻结、发布结局未定”。确认前在存储队列里核对同一请求的冻结值；没写入就以旧 revision 再冻结，冲突或读不出来就不发。补上冻结实际未落地、而非仅回执丢失的分支。

### 2. 放弃与确认可同时开始，已确认放弃的未发送请求仍能发布

- **严重程度**：阻断；**类别**：不变量。
- **位置**：`packages/neuro-book/src/plugins/canon/web/text-drafts.ts:465–475,482–500,552–571,613–624`；`packages/neuro-book/src/plugins/canon/web/text-tab.ts:224–237,269–278`。
- **现象**：冻结写进 SQLite 后断线，Canon 从未收到请求。重连后先放弃，扣住 Storage 删除的成功回执；见证窗口已经读到 `missing/revision:2`，本窗口还呈 `confirming`。此时另一共用入口可启动确认，进真实日志追加。先送达删除回执：`discard()` 返回 `true`、稿退出；再放行追加，`confirm()` 因代次不对返回 `busy`，世界却已经出现被放弃的块。
- **为什么是问题**：`discard` 在 `await drop()` 前没有占住会话；`confirm` 只看 `submitting`，不检查放弃在途。代次检查在发送之后，拦不住发布。确认期间能放弃本机稿，许可的是已经发出的请求可能成功；这里是放弃已开始、且本机记录已删以后才首次发出。base 的 `clear` 在等待存储前同步清稿，此具体交错不会再发；新修法把清稿移到等待之后，没补互斥。
- **如何核实**：同第 1 条的运行方式，参数 `discardConfirm`。真实 SQLite 删除、真实 RPC、追加前栅栏；不构造任何业务回复。页面的确认与放弃分开调这两个入口，重连也会调确认。
- **建议改法**：放弃开始就原子取得稿的操作权，直到删除结算才释放；确认、提交与换稿使用同一个门禁。把“删的是哪份稿”绑定代次和 revision，并在发 Canon 之前核对，不能靠发布后丢结果收场。

### 3. 两个页面同时开始编辑，迟到的存储读取会覆盖未暂存的新字

- **严重程度**：重要；**类别**：不变量。
- **位置**：`packages/neuro-book/src/plugins/canon/web/text-drafts.ts:508–525,579–596`；`packages/neuro-book/src/plugins/canon/web/entry-page.ts:109–142`。
- **现象**：同一窗口同一条目的两个页面共享一个会话。第一次 `begin` 读到无稿，块读取在途；此时另一窗口先暂存自己的稿。第二个页面 `begin` 读到这份稿，存储回复在途。第一个页面的块先回来，作者输入尚未暂存的字。第二次回复回来便把当前 `draft` 换成别的窗口版本，提示为 `saved`；即使再失焦暂存，本窗口刚打的字也找不回来。
- **为什么是问题**：`begin` 只在进 `pull` 前看有无稿，`pull` 在读返回后直接换稿并换条件写基线。队列只管读调用的顺序，既不管开始编辑的整个事务，也没给读结果绑定稿代次。输出 45 要作者选择才换稿。base 的两个 `begin` 共用一次 `loading`，并在读块完成时再次看有无稿；不会开始这里的第二次存储读取。
- **如何核实**：同第 1 条的运行方式，参数 `pullWithOtherDraft`。两个真实窗口同客户端身份，本窗口两次 `session(entry)` 得到同一实例；只扣真实 `textBlocks` 和 Storage `read` 回执，用真实保存产生另一个窗口的稿。
- **建议改法**：同一次开始编辑共享在途操作；用同一份代次与内存快照贯穿读取、接纳 revision、安装稿。返回时若已进入编辑，保留本地内容与旧条件写基线，照常走 `diverged` 和显式选择，不因迟到的读取越权覆盖。

### 4. 重开冻结稿，重发被确定拒收后，稿仍不可编辑

- **严重程度** 重要。**类别** 正确性。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-drafts.ts:390–406,482–505,528–545,579–587,600–605`，`web/text-tab.ts:121–130,230–237,242–251`。
- **现象** 重开一个有 `pending` 的稿，自动确认收到真实日志写入的 `write-failed`。稿已解冻且仍已暂存，却留下 `phase: idle`、`read: null`、`blocker: null`。再次 `begin()` 返回成功但仍没有读取，编辑被拒。提交可触发重读并再次尝试发布，作者无法先改字。
- **为什么是问题** `resume` 有 `pending` 时不读块。新的 `confirm` 只在确定失败且返回 `again` 时对稿，没有处理其余确定拒收。`text-tab` 遇到 `read: null` 会把输入冻结，重连也不会为无 `blocker` 的普通稿补读。基线的同读取戳重发分支先填充 `read`，切换到先查结局的修法丢了这一步。输出 46 要确定失败后恢复普通稿。
- **如何核实** 在 `packages/neuro-book` 运行 `bun test /tmp/claude-review-w00039-t28-impl-r2/scratch/resume-reject-read-null.test.ts`。真实 SQLite 保留冻结稿，通过真实链路重开，从日志追加前注入失败。记录上述状态、`edit` 无效果，且再次 `begin` 未恢复读取。
- **建议改法** 确定未发布后统一恢复普通稿并读块，保留块级拒收原因。读失败时给出 `blocker`，允许重读。覆盖从存储载入的稿在首次确认收到确定拒收的分支。

### 5. 并入的旧块后来被剧情碰过，提交仍静默删掉另一块

- **严重程度** 重要。**类别** 正确性。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-draft.ts:203–212,240–244,325–347,425–438`。
- **现象** 第 1 章编辑两块 `甲、乙`，把 `乙` 并进 `甲`。此后另一个窗口在第 2 章记一笔剧情，把 `甲` 换成「第二章的新甲」。提交前重读得到 `b1.write: init`、原文仍是 `甲`，但 `b1.fixed` 已非空。界面此时已认定该块只能改字，提交却无冲突地发布 `r4`。第 1 章读到 `甲\n\n乙`，第 3 章只剩「第二章的新甲」，原本第 3 章还在的 `乙` 消失。
- **为什么是问题** 首轮修法把 `moved` 的重新检查缩成写回去处变化。读在剧情替换以前，去处和字仍相同，合块却已违反输出 39 的全线限制。`compile` 把动作拆成合法的改字和删另一块，内核看不到两者本是一项合块操作。基线 `rebase` 有 `edited && moved → freeProblem(info)`，会在这个读取位置拦住这次合块。
- **如何核实** 同第 1 条命令，参数 `mergeBeforeFutureStory`。走真实剧情写入、`textBlocks` 和稿提交，断言新快照禁止拆块、提交却成功，以及第 1、3 章的两组原文。
- **建议改法** 针对实际移动过旧块文字的结构操作重验两端的 `fixed`、写回去处与初值相邻条件。不把只给旧块加字的新块合入算成移动；不能保留结构操作时让作者查看并整理整项。

### 6. 冻结重复存两份原文，让能暂存且能发出的单块修改无法提交

- **严重程度** 重要。**类别** 正确性、大小边界。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-drafts.ts:33–52,262–273,414–420,447–457`；`packages/neuro-book/src/plugins/canon/text-drafts.test.ts:427–448`。
- **现象** 把原文 `A` 改成 530,000 个 ASCII 字符。普通稿 530,153 字节，已暂存。同一块写入经 Canon RPC 成功，输入约 530,398 字节，预算 983,040 字节。但从编辑会话提交得到 `not-saved/too-large`，没有修订。冻结稿约 1,060,418 字节，超过 Storage 的 1,048,576 字节记录上限，且 RPC 帧也容不下。
- **为什么是问题** 新冻结在保留 `base`、`texts` 的同时，把相同原文再写进 `pending.ops`。基线仅加 id、标题和戳，这个输入可通过它的两个门禁。现有大小测试只覆盖普通暂存或 Canon 请求本身过大。这里两者都装得下，完整可提交的单块字节数却因冻结格式降到约一半。
- **如何核实** 同第 1 条命令，参数 `freezeSize`。先看真实 SQLite 的普通稿，再断言稿会话冻结失败，最后用同一 RPC 发送等价的单块改字，读回 530,000 字节原文。
- **建议改法** 冻结表示只存一次文本，例如操作按稿键引用不可变字符串、独立保存所有其余请求字段，解码按冻结格式生成逐字段相同的请求，不按世界现状重编。补齐普通稿与请求均在限内、冻结也必须能写的正向测试。单独抬高记录上限仍受 RPC 帧上限约束。

### 7. 合块后再拆或再并，恢复被并块会重复发布同一段字

- **严重程度** 重要。**类别** 正确性。首轮第 15 条的修复只覆盖直接恢复。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-draft.ts:163–178,191–212`，`web/text-draft.test.ts:114–122`，`web/text-tab.ts:264–267`。
- **现象** 两块 `A、B`，把 `B` 并进 `A`，再从 `A` 和 `B` 的连接处拆开，最后从删除标记恢复 `B`。一次提交发布了 `A、B、B`。三块 `A、B、C` 依次做 `C→B`、`B→A`，再恢复 `C`，发布的是 `A\n\nB\n\nC、C`。两个例子都没人修改被移动的那段字。
- **为什么是问题** `merged` 只认合块时的直接目标及尾段。拆块或再次合块会把尾段迁到别处，记录没跟着移动；`restoreBlock` 找不着它就只撤掉删除。首轮旧实现连直接恢复也重复，新实现修好两块直接恢复，仍漏掉可连续使用的结构动作。
- **如何核实** 同第 1 条命令，参数 `restoreAfterSplit`、`chainedMerge`。在真实条目会话做这几步，再经 RPC 发布，核对初值与章末的块原文，两处结果一致。
- **建议改法** 用结构操作的归属跟踪被移动的段落，组合拆并时同步更新归属。如果文字已无法确定归属，恢复前说明要作者整理，避免静默生成第二份。测试核对最终发布的块序和全文。

### 8. 同一条变更删后重加同号块，锚点取到已经删掉的第一份

- **严重程度** 重要。**类别** 正确性。
- **位置** `packages/nb-canon/src/world/text-blocks.ts:115–138`，`packages/nb-canon/tests/text-blocks.test.ts:399–415`。
- **现象** 初值 `A、B、C`。一条合法剧情变更依次在 `A` 后加 `b9`、删 `b9`、在 `B` 后重加 `b9`，原文为「第二次」。`textBlocks` 正确读到「第二次」，但给出 `anchor: b1`。从窗口在「第二次」后加设定并提交成功，读回 `A、要紧跟第二次、B、第二次、C`。
- **为什么是问题** 新算法在来历里找最后一次 `addBlock`，但来历只带变更 id。回到该变更的 `patches.find` 就取了第一项同号 `addBlock`。基线的锚点表逐项覆盖，对同一条变更的这组操作取到 `b2`。跨线同号的用例放在两条变更里，未覆盖同一变更里的两项。此处比的是明确不同的落位，与首轮第 3 条接受的同字同位置编号复用无关。
- **如何核实** 同第 1 条运行方式，文件换 `anchor-cases.ts`，参数 `replaceInsideChange`。经真实 `publish` 写入三个补丁，比较同一世界上的基线与当前锚点，再经窗口和 RPC 提交并读回排序。
- **建议改法** 让来历保留命中的补丁位置，按该补丁取锚点。结构上可改成在线上重放时直接记实际新增实例及其锚点，覆盖同一变更内重加的情形。

### 9. 变基把连续的剧情块误当同一插槽，发布到另一块后面

- **严重程度** 重要。**类别** 正确性。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-draft.ts:247–261,349–365`，`web/text-draft.test.ts:151–164`。
- **现象** 读到 `A、剧情 X、B、剧情 Y、C`，其中 `X` 挂在初值 `A`，`Y` 挂在初值 `B`。作者在 `X` 后加块。别处在剧情里删掉 `B` 后，`X`、`Y` 在当前章节相邻。提交无冲突，发布成 `A、X、Y、跟在 X 后面、C`，新增设定落在初值 `B` 后面。
- **为什么是问题** 新变基跨过所有连续剧情块，只按 `init === undefined`，没有比较锚点。输出 44 只要求越过同一处新增的剧情块。`Y` 原本已存在，锚点也与 `X` 不同。基线保留块跟着 `X`，读到后面现在是剧情块时报告该插槽放不进去，未静默改成另一个锚点。
- **如何核实** 同第 8 条，参数 `differentSlots`。从真实 RPC 读块并编辑，另记一条剧情删除，提交后核对章末原文顺序。
- **建议改法** 只在同一初值锚点的剧情组内越过剧情块。前后变成不同锚点、原插槽已不可表示时保留原稿并报出原因，让作者选择新位置。

### 10. 每追一跳锚点就重放条目时间线，120 个剧情块把热读拖到 2.16 秒

- **严重程度** 重要。**类别** 性能。
- **位置** `packages/nb-canon/src/world/text-blocks.ts:115–138`，`packages/nb-canon/src/engine/incremental.ts:417–450,595–599`。
- **现象** 两个初始块，之后每条剧情变更加一块并挂在前一剧情块上。同一内核、同一世界对象、预热后基线和当前交替各测 6 次。20、60、120 个剧情块的单次 `textBlocks` 中位数分别从 0.86、7.98、36.40 ms 增到 9.01、231.58、2159.65 ms。122 块的结果远小于消息预算，2.16 秒不含建世界或写入。这个同步读取会占住项目进程，开始编辑与提交前重读都走它。
- **为什么是问题** 基线为锚点一次扫描补丁，每一跳是表查找。现在每一跳重新做带值来历，120 块的链为锚点重放 7,260 次时间线，另有既存的 `writeBack` 回放。每次回放还从初值复制条目并重放该条目的各项补丁。基线自身的逐块写回路由代价不计入回归。
- **如何核实** 在 `packages/nb-canon` 执行 `NS=20,60,120 bun test /tmp/claude-review-w00039-t28-impl-r2/scratch/textblocks-cost.test.ts`。真实 `WorldService` 逐笔发布；基线函数取自 `82b254a12`，两版都在同一份实际世界上读。测量口径是同步内核热读，同次负载比较，不用它判 Spec 对普通 `entry` 的延迟预算。
- **建议改法** 从增量引擎取这条线在这一位置实际应用的补丁，一次建当前块实例的锚点和最近写回去处；对锚点链做记忆化。用层层锚定及不同线同号的场景验证正确性与读取成本。

### 11. 放弃再开新稿，旧的冲突选择仍会决定新稿的去留

- **严重程度** 重要。**类别** 正确性。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-tab.ts:149–173,254–273,282–290`。
- **现象** 第一份稿有块 `b1` 的「第一份稿／第一次在别处改」冲突。选「现在的」，回去再改，再放弃。第二份稿有同号块的「第二份稿／第二次在别处改」冲突。新对话框已带上「现在的」，这次未选过。点确认后第二份稿退出，世界只剩「第二次在别处改」。修订列表仍只有建条目和两笔别处的改动。
- **为什么是问题** 新实现按块 id 保留选择。放弃成功、重新开始与换入另一份暂存均未使旧选择失效。输出 44 的保留选择发生在回到同一稿编辑时。基线每次出现冲突都清空选择，因此新稿不会继承第一份稿的决定。
- **如何核实** 在 `packages/neuro-book` 执行 `bun --tsconfig-override tsconfig.json /tmp/claude-review-w00039-t28-impl-r2/scratch/conflict-choice.ts`。调用 `useTextTab` 的宿主入口，实写两笔 Canon 修订，走真实 SQLite 放弃与开始流程。断言第二份冲突的两侧文字、预选项及确认后状态。
- **建议改法** 选择绑定到同份稿里的同一冲突。稿被放弃、换入或重新打开时清掉旧选择。两侧参与选择的文本或去处变了时重新询问。

### 12. 确定拒收后解冻未落盘，重开会自动发布已报失败的请求

- **严重程度** 重要。**类别** 不变量。首轮第 21 条漏修的分支。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-drafts.ts:263–273,385–406,482–500,528–545`，`packages/neuro-book/src/plugins/canon/text-drafts-link.test.ts:156–181`。
- **现象** 冻结已写入 SQLite（revision `1`），日志追加前返回确定的 `write-failed`。解冻保存也写失败时，会话返回 `failed/write-failed`，内存稿已解冻，存储里的 `pending: case-1` 仍在，世界此时只有「建条目」修订。存储恢复后，另一个窗口只调用 `load()` 就发布了「磁盘满的提交」，原文从 `A` 变为 `A、日志拒收的字`。
- **为什么是问题** `settle` 无条件去掉内存中的 `pending`，忽略解冻保存的失败。重开后的 `resume` 把盘上冻结当作结局不明，原样发出。基线直接把明确的写盘失败当成结局不明。首轮修正了返回码和解冻成功的情形，未阻止持久化失败时再次发布。输出 46 要求明确未发布后由作者决定是否再提交。
- **如何核实** 同第 1 条命令，参数 `rejectedButUnfreezeNotStored`。日志追加前注入一次 `ENOSPC`，扣住真实的失败回执。用另一个 SQLite 连接 `BEGIN IMMEDIATE` 阻止解冻写入，再放行回执。核对内存、SQLite 与日志，解除锁后只开稿、不调用提交。
- **建议改法** 把明确拒收的结论持久化成可查询、不可重发的状态，或让恢复协议必须重新取得作者确认才可发送查不到结局的冻结请求。解冻写失败时保留明确的恢复警告并重试清理，单靠改页面状态无法阻止重开重发。

### 13. 拆块冲突选「现在的」，稿里仍留下拆出的另一半

- **严重程度** 重要。**类别** 正确性。首轮第 4 条漏修的分支。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-draft.ts:85–97,191–198,330–347,377–380`，`web/text-tab.ts:282–290`，`web/text-draft.test.ts:224–241`。
- **现象** 把 `甲\n\n乙` 在 `甲` 后拆开。别处把这块改成 `别处改甲\n\n乙`。冲突中选「现在的」，对话框关闭并正确停在编辑，没有立即发布。稿里却变为 `别处改甲\n\n乙` 与一块独立的 `乙`。按提示检查后再次提交，成功发布两处 `乙`，初值与章末一致。
- **为什么是问题** `splitAt` 只记旧块的 `moved`，没有记拆出的新块。`resolve(changed, theirs)` 撤掉旧块的改字后，`tidy` 也清掉了该旧块的 `moved`，新块继续作为独立新增编译。基线同样只撤一端且会自动提交。本轮修法拦住了自动提交，仍未落实首轮处置所说的「不再只撤拆并的一端」。现有拆块冲突用例覆盖去处变了的 `manual`，未覆盖去处相同、原文不同的分支。
- **如何核实** 同第 11 条命令，加参数 `lookAtStructuralChoice`。通过宿主选择与确认，核对返回编辑后的块内容和日志。再显式提交，核对该次发布的原文。
- **建议改法** 记录拆分的两端。放弃拆分的冲突选择时一并撤销拆出的块。如果作者后来改了新块，无法无损撤销时按 `manual` 处理，明示应整理哪些块。

### 14. 合法块 id 为 `__proto__` 时，校验原因落不到该块

- **严重程度** 建议。**类别** 正确性。首轮第 16 条未覆盖的错误映射分支。
- **位置** `packages/neuro-book/src/plugins/canon/web/text-drafts.ts:394–403`，`packages/neuro-book/src/plugins/canon/web/text-tab.ts:134–145`，`packages/neuro-book/src/plugins/canon/web/text-draft.test.ts:72–86`。
- **现象** 导入编号为 `__proto__` 的合法块以后，输入一个未闭合的 MDX 表达式。稿可暂存，内核返回 `validation-failed`，唯一细项为 `cross-block`，带 `op: 0`。会话只返回整批失败，块级原因数为 0，原稿保留，世界未修改。
- **为什么是问题** `keys[0]` 对到了正确的块，但给普通对象执行 `problems[key] = …` 时设置的是该字典的原型，没有写入自有属性。基线已使用相同的赋值方式。首轮修复了读稿、编译与暂存字典，这个分支仍漏掉，违背输出 44 的块级拒收合同。
- **如何核实** 同第 1 条命令，参数 `legacyKeyRejection`。通过真实 `publish` 导入块，走 SQLite 暂存与 Canon 校验，核对 RPC 的 `op: 0` 和空的块级错误表。
- **建议改法** 收集原因时用 `Map` 或无原型字典。也可与编译失败分支共用 `Object.fromEntries` 的构造方式。用编号为 `__proto__` 的块走一次真正的拒收并断言块级原因。

## 基线已有的现象

- 在原始锚点链 `A → X → Y` 上另记剧情，删掉 `X`，在 `C` 后重加同号但不同文的 `X`。`anchor-cases.ts twoStoryAncestors` 在同一实际世界上比较两版读取，`Y` 均得到 `anchor: b3`，而 `Y` 实际还在 `A` 后。当前稿按此发布，新增块排到了 `C` 后的重建 `X` 之后。两版都按锚点 id 追到读取时的当前块，未按 `Y` 被加出时的锚点实例追溯。这个基线现象单列，不纳入第 8 条的同一变更补丁定位回归。
- 第 7、12、13、14 条记录首轮修复后仍能触发的分支。基线分别已存在恢复重复、重开自动重试、撤销拆块只撤一端、错误表按任意 id 赋值的问题。本轮计为漏修，不列作新增回归。

## 未发现问题的方面

- 内核定向用例中，直接读取两条线的同号剧情块各取自己的锚点，带着支线锚点的后续插入落位正确。`fixed` 与删块拒收仍共用全线触及判据，覆盖未来章、计划、撤销和支线。主文字块不支持跨线带入，未把无法从正常写入构造的合成块当作可达失败。
- 实际写入路径中，正常的同 id 重发能拿回原修订，重复提交不多写。已有链路用例覆盖独占在内核去重之前拒绝重发、已发布但 `textBlocks` 读不回时仍能确认，以及提交已经在途时拦截新提交、开始编辑、放弃和打字。静态对照 `#write` 与 `editEntries` 的顺序，`REJECTED` 表中的业务拒收位于请求 id 判定之后。`request-id-reused` 表示同 id 已有修订，未见默认发号下无关请求占用该 id 的路径。
- 普通两窗条件暂存、显式接管与换稿、在途旧保存回执不把新字标为已暂存，及首次读暂存断线后重读，用现有目标用例验证通过。逐段检查 `enqueue` 中的任务，没有发现任务在队列内等待同一队列后继项的环。入口刚开始时的检查不能代替异步返回后的代次核对，见第 2、3 条。
- 普通改字、新增、删除混编时，`compile` 对同一有序项表生成 `ops` 和 `keys`。常规块编号的真实校验拒收定位到新增块；第 14 条的问题在之后收集诊断的字典，不是操作序号错位。纯模型的同槽剧情追加和普通同块冲突用例通过，越过不同锚点的反例见第 9 条。
