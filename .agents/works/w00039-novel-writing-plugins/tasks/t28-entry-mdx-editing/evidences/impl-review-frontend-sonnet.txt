### 1. 提交入口按条目 id 记一份：两个编辑组里各开一页时，后卸载的那页把另一页的入口删掉，Ctrl+S 静默什么也不做还回报成功
**严重程度**：重要　**类别**：正确性
**位置**：canon/web/entry-page.ts:131-133（`onCommitReady` 写 `commits`）、:143-145（`commit`）；canon/web/components/EntryPageHost.vue:617-624（onMounted 交入口、onBeforeUnmount 交 null）
**现象**：`commits` 是 `Map<条目 id, 提交函数>`。同一个条目在两个编辑组各开一页（右侧拆分、`split-right` 命令都会这样）时，两个 Host 先后挂上，后挂的 `set` 覆盖前一个；其中任何一页卸载（切标签、关页）都执行 `commits.delete(id)`，把还挂着的那一页的入口一起删掉。之后活动标签是那个还挂着的页面：`commit` 是 `async (arg) => { if (arg !== undefined) await commits.get(arg)?.(); }`，取不到就什么也不做，`area.save()` 随后返回 `{ok: true}`。标签上的圆点还亮着、稿还在，Ctrl+S 却无声无息。
同一个出口还有一条：活动标签刚切过来、`defineAsyncComponent` 的页面还没 `onMounted`（Host 的入口在 onMounted 里才交）时按 Ctrl+S，同样“成功”而没有提交。
**为什么是问题**：输出 68 的合同是“保存调用它的 commit 并等它完成；失败由页面自己显示”。这里既没提交、也没有任何显示，还让“保存”命令报成功，作者以为已经提交。entry-page.ts 注释里“活动的页面一定挂着”这个前提在上面两条路径上不成立。
**如何核实**：代码推断即可成立。可写一个 dom 测试：同一条目挂两个 Host（两份 `page.load()` 的组件），卸载先挂的那个，再调 `page.commit!(id)`，断言稿被提交（现在不会）。
**建议改法**：入口按“页面实例”记（`Map<实例, fn>` 或每次挂上返回一个只删自己的注销函数），`commit` 取最近挂上的；一个都没有时不要假装成功：直接对会话提交（提交本来只依赖 `session`、`world` 与标题，`textTab.submit` 可以挪到不依赖界面的层里，页面没挂也能提交），或者 reject 让保存命令报 `pageCommitFailed`。

### 2. 编辑视图的状态行吸顶在 top:0，与条目页自己的页头吸顶位置重合：滚动时盖住页头
**严重程度**：重要　**类别**：界面（从代码推断，未在真实浏览器里看）
**位置**：canon/web/components/EntryTextEditor.vue:187-198（`.text-editor__bar { position: sticky; top: 0; z-index: 1 }`）；对照 canon/web/components/EntryPage.vue:142（页头 `z-[1] … min-[481px]:sticky min-[481px]:top-0`）
**现象**：宽度 ≥481px 时条目页页头在编辑组的滚动区里吸顶在 0（里面是名字、位置、线、按计划、分页标签），同一个滚动区里编辑视图的状态行也吸在 0，z-index 同为 1，状态行在 DOM 里靠后所以画在上面。往下滚到状态行的自然位置到顶，它不会停在页头下面，而是压在页头最上面那 2.25rem 上，遮住名字与控件；加上整批说明（`basis-full` 另起一行，高度再加一行）遮得更多。Lab 夹具里没有页头，所以场景里看不出来。
**为什么是问题**：状态行里是“提交”“放弃”和暂存状态，本意是随时点得到；现在它与页头互相抢位置，页头的位置选择、分页标签在编辑中滚动后一部分被盖住。条目页的 `.md`/Spec 没写两个吸顶元素的叠放。
**如何核实**：在 e2e 环境或开发服务里打开一个有 10 块以上文字的条目（宽 1280），点“编辑”，滚动到中段，截图看页头；或用 Playwright 量 `[data-text-editor] > div` 与 `header` 的 `getBoundingClientRect().top` 是否都是 0（我没有跑）。
**建议改法**：让状态行的 `top` 等于页头高度，而不是 0。页头高度会随换行变，办法之一是让条目页把页头高度写成 CSS 变量（例如 `--entry-head-height`，用 ResizeObserver 或让页头与状态行同在一个吸顶容器里）；或者把状态行放进 `EntryPage` 的 `#bar` 插槽同一个吸顶页头里。窄屏（≤480）页头不吸顶，那时 `top: 0` 是对的，变量要有回落值。

### 3. 新写的过渡都没有缓动令牌；阅读与编辑视图的切换在 scoped CSS 里复制了一份“内容换页”配方，而且配错了
**严重程度**：建议　**类别**：界面
**位置**：canon/web/components/EntryPageHost.vue:1082-1099（`.canon-text-swap-*`）、:861（`<Transition mode="out-in">`）；canon/web/components/EntryTextEditor.vue:215、255、271-288；canon/web/components/TextConflictDialog.vue:130；canon/web/components/EntryText.vue 的 `transition-opacity duration-[var(--motion-fast)]`
**现象**：
- `canon-text-swap` 是 `out-in` 换页，却两段都取 `--motion-base`（design-language.md“内容切换走 `--motion-base`”一节的表：`out-in` 入场与退场都取 `--motion-fast`，两段相加要短于 `--motion-move`）；位移是 `translateY(4px)`（该节写的是短横向位移约 6px，不用 scale）；没有缓动。基座里已经有这条配方：`packages/nb-ui/src/styles.css:858-878` 的 `.nb-ui-switch-*`（`<Transition name="nb-ui-switch" mode="out-in">`），该节写明“不要各自在 scoped 里复制一份同配方”。（该节还写“新应用还没有用到这个类名”，已过时：FirstRunWizard.vue 在用。）
- 所有新写的带位移或淡入淡出的过渡（`text-editor-item-*`、`text-editor-dot-*`、`canon-text-swap-*`）都只写了时长，没写缓动，浏览器回落到默认的 `ease`。design-language.md“缓动”一节与 ui-development-spec.md 第 3 节第 86 行都写“组件不得写死时长或缓动、曲线来自令牌”，有位移的要取 `--motion-move` 配 `--ease-layout`，退场（列表项离开）按该节“退场不用它”配 `--ease-dialog-leave`。`text-editor-item` 用 `--motion-base` 搭位移，按该节“沿用 180ms 的 `--motion-base`，45ms 就走了八成，看着是跳过去的”也偏短。
- 为 `prefers-reduced-motion` 又写了一遍 `@media`（EntryTextEditor.vue:289-298、EntryPageHost.vue:1093-1098、TextConflictDialog.vue:157-161）：tokens.css:333-340 已经把全部时长令牌在该偏好下置 0，这几段是多余的（无害）。
**为什么是问题**：开发者 2026-11-23 点名“状态变化要有过渡、时长与缓动取令牌”是反复犯的；同一动作（内容换页）在多处时长不同正是该节要避免的事。
**如何核实**：读上面几处 CSS；`rg "nb-ui-switch" packages` 看现有消费者；用 Lab 的 EntryTextEditor 场景切换看手感（我没有看真实浏览器）。
**建议改法**：Host 的换页直接用 `name="nb-ui-switch"` 并删掉 scoped 里的那份；列表项进出与圆点按 design-language 的缓动一节补 `var(--ease-layout)`（进场）与 `var(--ease-dialog-leave)`（退场），位移档用 `--motion-move`；删掉三处多余的 reduced-motion 媒体查询。

**严重程度**：建议　**类别**：界面（从代码推断，逐处读模板得出）
**位置与现象**（都没有 `<Transition>`、也没有 CSS 过渡）：

### 5. 提交被拦（只读、独占、断开、位置在按计划）时，Ctrl+S 与“保存”命令没有任何反馈；禁用的“提交”的原因只在 `title` 里
**严重程度**：重要　**类别**：正确性 / 界面
**位置**：canon/web/text-tab.ts:203-208（`submit` 开头 `if (state.draft === null || state.phase !== "idle" || options.blocked() !== "" || !dirty.value) return;`）；canon/web/components/EntryTextEditor.vue:121-129
**现象**：`dirty` 公开状态只看稿有没有未提交内容，不看世界能不能写。世界变成只读、被别的调用方独占、连接断开、或作者把位置开关切到“按计划”（这些都在 `blocked()` 里）以后，稿仍是脏的，Ctrl+S 照样走到 `commit` → `textTab.submit()`，第一行就静默返回，`message` 不设、没有弹提示；`area.save()` 返回 `{ok: true}`。作者按了 Ctrl+S，什么也没发生，界面上没有一个字解释。点按钮那条路径看得到“提交”变灰，但原因只写在 `title`（悬停才有；键盘用户永远拿不到，禁用的按钮也不可聚焦，读屏读不到）。
同样的静默还有 `!dirty`（没有改动）与 `phase !== "idle"`（正在提交或等结局）：这两种静默可以接受，但被拦的原因（需要作者去处理的）不行。
**为什么是问题**：开发者 2026-11-23 的决定里“Ctrl+S 等于提交”，作者的预期是提交成功或看到原因。输出 68 写“失败由页面自己显示”，这里被拦属于失败的一种，却没有显示。
**如何核实**：代码推断；也可补一个 dom 测试：把世界置为独占（canon 的 dom 测试已有“别的调用方独占写入”的做法，entry-page.dom.test.ts:945）、编辑一块、调用 `page.commit!(id)`，看 `[data-text-message]` 是否出现。
**建议改法**：`submit` 在 `blocked() !== ""` 时把原因写进 `message`（就是 `submitBlocked` 的那句），按钮路径与 Ctrl+S 路径一样可见；提交按钮的禁用原因同时作为一行可读的状态行文字（或 `aria-describedby`）而不只放 `title`。

### 6. 代码输入框是异步组件：`ref` 要等它加载完才有，焦点交接有三处依赖“这时已经有了”；加载失败时输入框消失且没有退路
**严重程度**：建议　**类别**：正确性 / 健壮性
**位置**：editor/web/plugin.ts:433-434（`defineAsyncComponent(() => import("./components/CodeInput.vue"))`，没有 errorComponent 与 onError）；canon/web/components/EntryTextEditor.vue:63-77、151-153；canon/web/components/EntryPageHost.vue:599-611（`focusFirst`）
**现象**：
- Vue 3.5.39 对异步包装组件的函数 ref 只在内层组件解析之后才转发（runtime-core.cjs.js:1754-1759）。所以窗口里第一次出现 CodeInput 时，`setInput(key, instance)` 要等 chunk 到了才调。`startEditing` 的 `focusFirst` 在 Transition 的 `after-enter`（`--motion-base` 180ms 以后）一次性消费：chunk 还没到（开发服务第一次转译、慢盘）时 `focusBlock` 落空，`focusFirst` 已被置回 false，没有重试——点“编辑”后焦点不进第一块。从代码推断，生产环境多半赶得上，开发服务与冷启动不一定。
- `focusAfter` 同理：用 `nextTick` 以后按“新的块序”找键，宿主是同步给块的（`session.edit` 同步改 `state.draft`）所以现在可行；但 EntryTextEditor 的 `.md` 把它写成受控组件的合同（“宿主给出新块以后焦点进新块”），宿主晚一拍（例如先等存储）给块时落空。更稳的是组件自己 `watch` 块序出现目标键后再 `focusBlock`。
- 异步组件加载失败（chunk 404、版本换了）：没有 `errorComponent`，渲染 null，每个块只有框头与按钮、没有输入框，作者没法编辑，也没有错误提示。`loadMonaco` 失败时 CodeInput 自己写原因，但同样“不能编辑”（CodeInput.md 把这写成已知状态）。EntryTextEditor 有现成的 `PlainSourceInput`，却只在“窗口里没有编辑器插件”时才用，加载失败时不回落。
- `activate()` 里 `monaco.editor.create(...)` 抛错（worker 建不起来等）没有 catch：`started` 已为真、`stage` 停在 plain，之后聚焦也不会重试，只有一条未处理的拒绝。
**为什么是问题**：输入框是这个功能的核心，失败时作者看到的是空框；焦点落空是“点了编辑却不能直接打字”的小回退，但每次冷启动都可能遇到。
**如何核实**：代码推断；失败路径可在 Lab 里把 CodeInput 的 import 改成 reject（我没有做）。
**建议改法**：`defineAsyncComponent` 给 `onError`/`errorComponent`，EntryTextEditor 在输入框不可用时用 `PlainSourceInput` 回落；CodeInput 的 `failed` 阶段也可以直接渲染一个只含原文的 `<textarea>` 并继续交回改动，而不是只读 `pre`；焦点交接改成“目标键的输入框就绪后再给”（`setInput` 记下待聚焦的键，登记时检查）。

### 7. 内嵌的 Monaco 默认吞 Tab：键盘用户进了一块就出不来，只能靠不可见的 Ctrl+M；输入框回落到普通文本框时行为又不同
**严重程度**：重要　**类别**：界面（可访问性，从代码推断）
**位置**：editor/web/components/CodeInput.vue:72-95（`monaco.editor.create` 的选项里没有 `tabFocusMode`，也没有别的离开输入框的办法）；canon/web/components/EntryTextEditor.vue:97-100
**现象**：Monaco 默认 Tab 在文字区里插入制表符，焦点不离开（`IEditorOptions.tabFocusMode` 默认 false；离开要按 Ctrl+M 切“Tab 移动焦点”，界面上没有任何提示，仓库里也没有处理，grep `tabFocusMode|toggleTabFocusMode` 在 packages/neuro-book/src 无命中）。编辑视图一页里是“框头三个按钮 → 输入框 → 在这里加一块”重复排下去，键盘用户 Tab 进第一个输入框（`pre` 聚焦即建 Monaco 并把焦点交进去）以后，再按 Tab 只会往主文字里插制表符，到不了这一块的“在这里加一块”，也到不了下一块与顶上的“提交”。Esc 在“有改动”时又不接（EntryTextEditor.vue:99），所以没有任何键能离开。对写小说的主文字，Tab 插入的缩进放在段首还会让 Markdown 把这一块变成代码块。回落到 `PlainSourceInput`（普通 `<textarea>`）时 Tab 正常移焦点，两条路径的键盘行为不一致。
**为什么是问题**：开发者要求“先保证功能与 UX”，输出 69 要求代码输入框能嵌进别的插件的页面；嵌进有大量按钮的页面时，焦点陷阱（WCAG 2.1.2）是这个组件的责任。仓库里已有类似问题的做法：SettingsFileView.md 第 24 行（`Tab` 插入空格，第一次 `Esc` 先“放开 Tab”，再按一次才交给窗口）。
**如何核实**：Lab 里 CodeInput 的 `stack` 场景，点进第一个框按 Tab，看焦点是否去了第二个框（我没有跑）；或 `getContextKeyValue`/截图看不到，需要真实浏览器。
**建议改法**：CodeInput 默认把 `tabFocusMode: true`（嵌入的输入框里 Tab 是导航，缩进用空格键或 `Ctrl+]` 这类 Monaco 命令），并在 CodeInput.md 里写清；或照 SettingsFileView 的做法加“Esc 放开 Tab”。同时 EntryTextEditor 的 Esc 取消要避开“正在组字”（`event.isComposing`，中文输入法按 Esc 取消候选时不要把整个编辑取消），目前只判了 `defaultPrevented`。

### 8. “有没提交的主文字时剧情入口不可用”那条分支在组件树里到不了，对应的用例不会失败
**严重程度**：建议　**类别**：测试 / 代码质量

### 14. 稿锁住位置以后，页内还有三处仍按 `state.planned`/`state.position` 判断；`TextTab.lockedAt` 是没人用的重复实现

**现象**：

### 15. `uncommitted(entry)` 在标签条的计算里发起存储读取、读块、乃至重发上一次提交；会话登记只增不减
**严重程度**：建议　**类别**：代码质量 / 不变量
**位置**：canon/web/text-drafts.ts:540-548（`uncommitted`：`if (!current.state.loaded) void current.load();`）、:422-447（`load` 在有 `pending` 时 `await confirm()`）、:531-538（`sessions` Map）；调用方：editor/web/components/EditorGroupHead.vue:96-97（`tabs` computed）、editor/web/state.ts:90（`dirty` computed）
**现象**：
- 计算（computed）里的读取带副作用：第一次读某个条目就开存储记录、读稿、读 `textBlocks` 并 `rebase`，稿带 `pending` 时还会走 `confirm()`——对世界发一次 `editEntries` 重发或 `outcome` 查询。这些发生在“标签条渲染”这个与页面是否打开无关的时机（刷新后每个条目页标签都会触发），而且发布成功时 `settle` → `clear()` 没有给作者任何提示（`report()` 里的提示只在页面挂着时才有）。幂等（`loading ??=` 只跑一次）所以不会循环，但 pages.ts 的约定只说“它读的状态不能放在页面组件里”，没有说读它可以发请求。
- “第一次问时为假，读到之前为假”：刷新后有稿的标签，圆点与 `dirty` 在存储读完之前是灭的；活动标签恰是这个条目页时，这段时间里“保存”命令不可用。窗口很短，但这是“读取返回值依赖谁先问”的写法。
- `sessions` 条目页标签关了也不删（稿放弃、提交都不删会话），一个窗口里开过多少条目就留多少份响应式状态。量小，但没有上限。
**为什么是问题**：副作用放在响应式读里，换一种渲染时机（例如标签条虚拟化、懒渲染）行为就变；读者看 `EditorGroupHead` 不会想到它会触发一次重发。
**如何核实**：读代码；写一个测试：存储里放一份带 `pending` 的稿，只挂 `EditorGroupHead`（不挂页面），看 `editEntries` 是否被调用（预期被调用）。
**建议改法**：让“恢复有稿的条目页标签”显式做一次预载（页面实现的 `initialState`/插件激活时对 `restore` 的标签调 `drafts.session(id).load()`），`uncommitted` 只读状态；或者保留现在的写法但在 `text-drafts.ts` 注释里写明“读它会发起存储读取，有 pending 时会确认”，并让会话在稿清掉且没有页面挂着时从 `sessions` 里删。

### 16. 组件文档与 Lab 场景的几处缺口，以及输入框一些小问题
**严重程度**：建议　**类别**：文档 / 界面

### 17. 点“编辑”但读不出块时，原因写进了只有编辑视图才显示的 `message`：阅读视图上什么也没有；`focusFirst` 的一次性旗标会在之后无关的时机偷焦点
**严重程度**：建议　**类别**：正确性
**位置**：canon/web/text-tab.ts:238-244（`start` 失败时 `message.value = blockerText(failed)`）、:233（`editor.message`）；canon/web/components/EntryPageHost.vue:601-611、:861-896
**现象**：
- `start()` 调 `session.begin(position)`，读块失败（`chapter-not-found`、`line-not-found`、`entry-missing`、`unavailable`）时 `begin` 返回原因、不建稿，`start` 把原因写进 `message`。`message` 只经 `textTab.editor.value.message` 传给 `EntryTextEditor`；失败时 `textTab.editing` 为假，页面仍是阅读视图（`EntryText`），它没有任何地方显示整批的说明。作者点“编辑”，没有任何变化，也没有错误。
- `startEditing` 先把 `focusFirst = true` 再 `await textTab.start()`。`focusFirst` 只在 `focusEditor`（编辑视图的 `after-enter`）里清掉。读块失败、或读块期间作者切到了“情节”分页，旗标一直留着，等以后任何一次编辑视图进场（比如从别的窗口 `adopt` 来一份稿、刷新后恢复稿、几分钟后回到文字分页）才把焦点抢到第一块。
**为什么是问题**：主入口的失败没有反馈；旗标的作用域是“这一次点击”，却存成了页面级变量。
**如何核实**：代码推断即可。复现：把世界客户端的 `textBlocks` 换成返回 `unavailable`（entry-page.dom.test.ts 的 `countedClient` 一类的包装），点“编辑”，看 `[data-text-message]`（不存在）。
**建议改法**：`start` 失败时把原因放进阅读视图能显示的地方（例如页头下面的一行 `role="alert"`，同 `actionError` 的写法），或直接用 `actionError`；`focusFirst` 在 `start()` 返回（成功或失败）后与 `focusEditor` 一并清掉，或改成 `start()` 返回成功时才置位。

## 未发现问题的方面（仔细检查后）
- Ctrl+S 与浏览器保存：`useEditorGroupRoot.ts:13-27` 对 Ctrl+S 一律 `preventDefault` 后交给“保存”命令，Monaco 自己不绑 Ctrl+S，不会既弹浏览器保存又触发命令。
- `theme-follow.ts` 的计数：组件加载失败（没走到 `followMonacoTheme`）、卸载发生在加载途中（`unmounted` 判断在它之前）、重复释放（`released` 标志）三种情形计数都对；MonacoControl 与 CodeInput 共用一个观察器，最后一个释放后断开。
- CodeInput 的回声：与模型相同的值不重设（`model.getValue() === text`），换文字时保留光标；组件在加载 Monaco 途中卸载时 `editor`/`model` 不泄漏（`activate` 在每个 await 之后都判 `unmounted`）；`IntersectionObserver` 在 `activate` 与卸载时都断开，一页二十个也没有遗留监听。
- `setInput` 函数 ref：Vue 3.5.39 对函数 ref 每次更新用当前实例调用、卸载时置 null，函数身份每次不同不会丢实例（只有异步包装组件在解析前拿不到，见第 6 条）；TransitionGroup 离场的 `li` 里组件已先卸载，`inputs` 已清。
- 页面合同：`uncommitted` 读的是会话里的响应式状态，在标签条与公开状态的计算里调用不会循环；贡献撤回后 `implementationOf` 返回 null，圆点灭、`commit` 为 null，保存回到 `noActiveDocument`；`hasUnsavedDocuments`、全部保存与关窗结算仍只看文件文档（输出 68），`dirty` 公开状态只让“保存”命令可用；`commit` 重叠由页面的 `phase !== "idle"` 早退合并。
- 命令与状态之外的既有行为：别的页面标签（没给 `uncommitted`/`commit`）圆点与保存可用性不变；文件标签的 `dirty` 圆点路径没改。
- 组件文档与实现：EntryTextEditor、CodeInput、TextConflictDialog、PlainSourceInput、EntryText、LineSelect、EntryPage、EntryPageHost 的 props、emits、expose 与隐藏通道标签与实现一致（除第 9 条那一句）；zh-CN 与 en-US 的键对齐（locales.test 通过）。
- 跨插件引用：canon 只引 `editor/shared/contracts` 与既有的 `editor/web/pages`，editor 没有反向引 canon。
