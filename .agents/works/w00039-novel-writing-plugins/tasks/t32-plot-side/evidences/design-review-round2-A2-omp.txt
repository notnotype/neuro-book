### 20. 子线自己的变更没有被限制在分叉之后
**严重程度**：重要；**类别**：正确性
**位置**：提案第 7 节第 120、126、133、147 行；原型 `prototype/worldline/lines.ts` 第 45 至 70 行。
**现象**：线视图把祖先线截口前的记录与“本线的变更”直接相加，但没有规定本线变更的安放必须不早于分叉激活点，也没有写入失败码或读取时的处理。原型的 `own(id)` 只按 `lineOf` 等于当前线就加入，未与 `cutAfter` 或触发点比较。
**为什么是问题**：分叉在父线第 5 章之后建立时，若一条标为子线的变更安放在第 4 章，子线第 4 章的读取就会看到尚未产生的本线状态，甚至能改写分叉前的计划、核对点和带过去地址。多层分叉和“子线引用父线切口后才建条目”都会因此得到非因果的线性视图；“只更新看得到的线”也无法修复错误的可见集合。
**如何核实**：在原型的 `LineViews.visible` 中给子线增加一个安放在 `cutAfter` 之前的变更，再读取该线切口前的位置；当前筛选会无条件执行 `changes.set(id, change)`。现有内核的 `Placement` 也只有全局安放，没有线激活下界。
**建议改法**：把分叉激活点和线内安放范围写成可校验不变量：子线变更只能落在触发点之后，或明确规定它们在分叉前完全不可见；多层线按父线读取位置传递下界。写入时拒收越界安放，已有异常进入稳定待处理，并为切口前后、同章切口和多层分叉加差分验收。
### 21. 带过去的合成赋值没有定义切口后的排序和来源
**严重程度**：阻断；**类别**：正确性
**位置**：提案第 7 节第 126、139 至 141 行；原型 `prototype/worldline/lines.ts` 第 55 至 68 行；内核 `docs/specs/canon/model.md` 输出 2、7、12 和 `packages/nb-canon/src/engine/incremental.ts` 的事件排序。
**现象**：提案只说把父线触发处的值“记成切口处一条合成的赋值”，没有规定它在切口变更之前还是之后、是否进入 `outcome`/来历/嫌疑区间/待处理以及它的依据和稳定 id。原型把合成变更的 `at` 设为与 `cutAfter` 相同，并把 `createdAt` 设为切口版本；现有排序再按 id 数字部分排时，`carry-child` 的数字部分为 0，会排在例如 `c12` 之前。实测排序结果为 `carryBeforeCut: true`。
**为什么是问题**：若切口变更或切口同章后续变更改过被带过去的地址，正确语义应先得到父线触发处的最终值，再从切口之后开始沿子线折叠；当前形状可能先套合成值、再套切口补丁，导致子线起点丢失。把它伪装成普通已写变更还会让计划兑现、原句校验、来源、嫌疑区间和跨线还原把引擎内部产物误当作者记录。
**如何核实**：运行 `/tmp` 中的最小排序脚本可复现 `cut=[1,7,3,12,12]`、`carry=[1,7,3,12,0]`、`carryBeforeCut=true`；再构造切口同时写同一地址的线视图，比较合成赋值在切口前后两种折叠结果。仓库原型命令本身因其相对 import 指向不存在的 `.worktree/w00039-t32-review2-a/.worktree/w00039-t29-canon-kernel` 而未能启动。
**建议改法**：给合成赋值定义非作者的内部事件形状和来源，使用明确的“切口之后、触发快照之前”的排序锚点，而不是复用普通 `Placement`；规定它是否出现在来历、计划、检查和待处理中。把父线触发位置、带过去地址的旧值/新值及多次修改的快照写进跨线依赖，并用“切口同地址修改、同章触发、多层分叉”验收。
### 22. 计划与兑现跨线没有可判定的归属规则
**严重程度**：重要；**类别**：不变量
**位置**：提案第 7 节第 120 至 127、139 至 141 行；内核 `docs/specs/canon/model.md` 输出 13；`packages/nb-canon/src/core/schema.ts` 第 126 至 130 行与 `docs/specs/canon/revisions.md` 输出 3。
**现象**：第二版说计划进展、结果和按计划模式“自然按线分开”，但没有说明父线切口前的计划能否在子线兑现，子线的计划能否指向祖先计划，以及 `fulfills`、`replaces`、`splitFrom` 在不同线或分叉之后的有效范围。现有 Link 校验只检查链接种类和对象类型，不检查线关系；按线过滤也只过滤变更集合，不定义跨线链接的可见性。
**为什么是问题**：同一条父线计划在原线和子线可能分别被兑现或撤销，子线读取应有独立进展；若子线兑现父线计划，原线不应被反向标为已兑现。若计划在切口之后才创建，则不应回溯进入子线的切口前缀。没有这些规则，写手的按计划简报、部分兑现、拆出计划和还原后的进展会依赖调用顺序或“是否被过滤”的偶然结果。
**如何核实**：构造父线切口前的计划、切口后的子线兑现变更和兄弟线的另一条兑现，分别调用三条线的 `progress` 与 `planned` 读取；当前内核 `progressAt` 按当前输入集扫描链接，但没有线字段，无法表达“同一计划在三条线的进展”。
**建议改法**：定义计划的线归属与继承规则，至少规定切口前计划是否是每个后代线的只读前缀、兑现链接是否必须在同一线或允许指向可见祖先计划、`replaces/splitFrom` 的跨线范围，以及回到父线时是否合并进展。把线 id、计划 id、读取位置和模式纳入计划进展缓存键，并为“父计划跨线兑现、兄弟线各自兑现、计划在切口后创建、按计划读取”写验收。
### 23. 活页夹排除规则不能唯一确定 RP 与多线读者钟
**严重程度**：重要；**类别**：正确性
**位置**：提案第 7 节第 131 至 135、147 行；内核 `ReadPosition` 现为 `initial|chapter-start|chapter-end`（`packages/nb-canon/src/core/schema.ts` 第 21 至 24 行）。
**现象**：提案新增“没有排进活页夹的线不算读者读过”，但读者位置仍只有活页夹章序和段，未定义活页夹条目怎样携带线、同一章是否允许多个线版本、RP 读档后新线是复用原章还是生成新章，以及作者把 IF 线排进活页夹后何时开始计入。
**为什么是问题**：回溯旧线与新线可能共用第 8 章；平行视角可能在同一章序下各有揭示。按“所有活页夹章的讲述、不分线”会把未读兄弟线的揭示并入读者知情，按“排除整条线”又无法表达一章里只排一场或回溯后读者已经读过旧稿的情况。于是读者层守卫、提前泄底、伏笔阶段和“读者现在知道什么”不能从日志重放唯一得到。
**如何核实**：建立两条线各在同一活页夹章写一个不同揭示，分别以 RP 存档点读档并读取读者账本；现有 `ReadPositionSchema` 没有 reader path、presentation id 或 line 维度，提案也没有活页夹记录与世界线的连接形状。
**建议改法**：把读者呈现路径作为独立的有序输入，明确每个活页夹单元的章、线、段范围和版本；定义旧线已读后回溯、新线重写同章、兄弟线揭示、IF 线加入/移出活页夹的规则。读者账本的缓存键和守卫范围必须包含呈现路径，而不是只用章节号。
### 24. 在场推出的知情与显式知情行没有优先级和撤销语义
**严重程度**：重要；**类别**：正确性
**位置**：提案第 5 节第 95 至 100 行、第 8 节第 153 至 157 行；`docs/specs/canon/model.md` 输出 5、7、13。
**现象**：提案同时允许知情行由剧情变更加/改，也允许“揭示给在场的人”自动得到“亲历”的知情行，但没有定义自动结果是持久化行还是读取时派生、显式行与派生行同点冲突时谁优先，以及后续“不知道/忘了/误信”如何覆盖一次亲历揭示。经历和回溯记忆也没有说明使用哪一份口径。
**为什么是问题**：例如角色在场并被自动推出“知道 K1”，下一条显式变更把 K1 设为“忘了”，再次读取若每次都把在场揭示叠加，就会重新得到“知道”；若显式行优先，则需要稳定记录派生来源和遮蔽范围。跨线回溯时同一知识点还可能有带过去的显式行与当前线的在场推导，未定义优先级会让写手简报和角色记忆不一致。
**如何核实**：按三步写入同一角色同一知识点：在场揭示、显式忘记、另一线带过去知情，分别读取每个位置的知情和经历；当前内核对列表元素只按补丁折叠，提案没有派生行的地址、来源或覆盖规则。
**建议改法**：把自动知情定义成带 `source=presence`、发生点和变更引用的派生记录，写出与显式行的合并优先级及遮蔽区间；规定“忘了/不知道”是永久覆盖、覆盖到下一次揭示，还是只对显式来源生效。回溯携带时同时携带哪些来源、跨线新揭示如何覆盖，也要成为线视图和经历计算的验收合同。
### 25. 讲述发生点只覆盖正文原句，无法覆盖计划与非正文讲述
**严重程度**：重要；**类别**：接口与合同
**位置**：提案第 3 节第 81 至 84 行、第 9 节第 162 至 164 行；当前 `TellingSchema`（`packages/nb-canon/src/core/schema.ts` 第 35 至 39 行）；`docs/specs/canon/revisions.md` 第 57 行。
**现象**：第二版规定所有讲述由原句在章内定位得到段与偏移，并把计划节点、兑现继承、揭示和伏笔都依赖这个发生点，但 `Telling` 的来源可以是 `outline`、`message`、`ui`、`seed`、`note`，这些来源没有正文段可定位；原型和提案也没有定义细纲段落 id、消息范围、界面确认或“无正文位置”的排序锚点。
**为什么是问题**：计划中的节点本来需要在正文写出之前参与按计划模式和章节完成检查，不能等待正文原句；补叙、同句重复、跨段移动和多版本改稿还会让“原句 + 段偏移”对应多个或零个发生点。若随意回退到章级，第一轮要解决的同章先埋后收、读者段级知情和计划继承又会失效；若把非正文来源当正文发生点，则状态会错误地进入读者已读账本。
**如何核实**：分别建立一条 outline 讲述、一条正文中重复两次的相同原句和一条改稿后跨段移动的讲述，运行发生点排序与失联检查；现有修订把无 id 数组整体作为叶子，没有能保留、匹配和迁移每个讲述 id 的路径合同。
**建议改法**：为发生点区分正文呈现锚点与计划/来源锚点：正文用章节、正文版本、段稳定 id、段内范围，细纲用细纲版本与块 id，消息/UI 用不可变消息或确认 id；定义无正文来源只参与计划模式、不进入读者钟。重复匹配必须有作者确认或稳定选择规则，失联/多匹配要保留标注并进诊断。
### 26. 通用标注与诊断贡献点仍没有插件可独立实现的注册合同
**严重程度**：重要；**类别**：接口与合同
**位置**：提案第 4 节第 63 至 77、81 至 84 行；ADR 0027 第 25 至 30 行；`docs/specs/canon/components.md` 第 36 至 49 行。
**现象**：第二版把揭示、伏笔节点和检查放入剧情插件，并说 `kind` 由插件登记、载荷由插件 schema 校验、诊断贡献点由插件注册，但没有定义标注/诊断贡献点的 id、版本、schema、校验时机、未知插件类型的保留与只读行为、诊断输出或插件停用后的结果。现有 `canon.components` 只覆盖条目 Component 类型，ADR 0027 只规定插件能力相同和完全信任，不提供这类贡献点的合同。
**为什么是问题**：照字面实现，内核无法在写入和还原时知道一个标注的载荷是否可校验、引用声明从哪个插件版本取得，也无法决定停用剧情插件后揭示/节点是原样读取、只读、失效还是进入待处理。若每个插件自行解释同一标注，跨插件引用、统一临时 id 替换、依赖闭包和诊断合并会重新分叉，违背“内核只加通用机制”。
**如何核实**：在当前仓库中，组件登记只接受 `id/namespace/version/fields` 等字段，没有 annotation 或 diagnostic contribution 的入口；构造未知 `kind` 后，当前核心 schema 会按未知字段保留，但不会产生插件校验或稳定诊断，无法证明第二版声称的独立实现路径。
**建议改法**：新增并引用明确的贡献点合同：登记 id、版本、载荷 TypeBox schema、引用声明、检查输入/输出、稳定诊断键和停用行为；写入时保存贡献点版本或不可变 schema 摘要，未知类型按组件同样只读并给诊断。把“内核存储/通用引用/还原”与“插件语义/检查”分别列出接口和差分验收，避免把揭示或伏笔语义重新写回内核。
### 27. 待处理的稳定键与处理生命周期仍不可落地
**严重程度**：重要；**类别**：接口与合同
**位置**：提案第 13 节第 202 至 210 行；内核 `docs/specs/canon/model.md` 输出 16、22；`packages/nb-canon/src/world/world.ts` 第 159 至 180、809 至 868 行。
**现象**：第二版列出稳定键的组成（规则、对象、线、讲述点、范围）、根因、生命周期、同源合并、上限与优先级，但没有定义这些字段的规范化编码、缺省值、线/讲述点失联时的键、相同候选的合并矩阵，也没有定义“作者确认、改、标有意为之”写入哪个持久对象、如何关闭或再次打开。当前内核的待处理只在读取时计算，按根因只合并 `cannot-apply`，没有剧情诊断的处理状态。
**为什么是问题**：同一穿帮在正文改稿、世界版本前进、分叉淘汰或讲述失联后如果键稍变，作者会看到重复事项或无法确认原项；若提示升级/抑制不进入世界日志，刷新或换线后会恢复。每章超过上限后的合并也必须保留可展开的候选，否则记账无法逐条回答“引原句”，而全局合并会掩盖绝密优先项。
**如何核实**：对同一知识点、同一角色在相邻两章和两条线生成相同候选，再读取实际/计划模式、改稿失联和处理后的 `pending`；现有 `Impact` 只比较 `check/cannot/held/deleted` 字符串键，剧情插件没有可写的诊断处理记录或分页摘要结构。
**建议改法**：为每种诊断定义版本化的 canonical key、根因图、状态转换（open、acknowledged、resolved、intentional、suppressed 及重新出现条件）和持久化入口；定义候选聚合后的成员游标、优先级、上限和解压协议。把线、模式、读者路径、发生点与世界版本的哪些项属于键、哪些只影响结果，写入 Spec 并用重复读取、跨线、改稿和撤销验收。
### 28. “只有系统能生成”的决策来源没有接到当前发布合同
**严重程度**：重要；**类别**：安全与不变量
**位置**：提案第 11 节第 178 至 181 行、第 5 节影响第 266 行；当前 `ActorSchema` 与 `TellingSchema`（`packages/nb-canon/src/core/schema.ts` 第 28 至 39 行）；`docs/specs/canon/revisions.md` 第 49 至 57、66 至 74 行。
**现象**：第二版把作者消息 id、会话、原文和引用范围或界面确认称为“不可伪造来源”，并规定只有系统能由它生成已定决策；但当前发布请求的 `by` 只有 author/agent/task/system，`Telling` 仍只有 source、chapter、quote，修订也没有被引用消息的不可变版本、作者身份或确认凭据。提案没有定义系统生成入口、插件/Agent 能否直接提交 `decision` 对象、消息删除/编辑后的校验和重开时的来源保留。
**为什么是问题**：自由文字加 `source: message` 仍能伪造作者原话；即使前端正常生成，重放日志也不能验证来源是否真来自作者或是否超出引用范围。决策的守卫又直接决定写手上下文和发布拦截，来源校验缺失会把最关键的不变量降成提示词约定。
**如何核实**：按当前 `WriteRequestSchema` 构造一个 `by: agent` 的决策对象，把 `source: message` 和任意 quote 塞进讲述或字段，现有 schema 没有来源凭据可拒绝；再修改原消息文本，现有日志没有可验证的不可变引用。
**建议改法**：在修订/决策合同中引入系统签发的 `AuthorSource`：作者身份、消息/确认 id、会话、不可变原文摘要、引用范围、确认时间与来源类型；只允许专用系统入口把它绑定到已定/放弃/重开转换，普通 Agent 请求只能生成待定或未确认建议。定义消息编辑、撤回、会话重连、来源失效和重开后旧结论的审计与失败码，并以伪造/越界引用验收。
### 29. 守卫的逐变更决定没有同步到 Task 合同
**严重程度**：重要；**类别**：文档与正确性
**位置**：提案第 11 节第 180 行；`.agents/works/w00039-novel-writing-plugins/tasks/t32-plot-side/README.md` 第 301 至 307 行。
**现象**：第二版明确守卫“在范围内每一条变更之后检查”，但同一 Task 的决定说明仍写“守卫在范围内每章末尾检查，按计划模式也查计划”。第二轮的提案与决定表因此给出了不同的检查时序，且没有说明哪一个是真相源。
**为什么是问题**：按逐变更实现会报告同章先违反后恢复的中间状态，按章末实现则漏报真实违约；计划模式还会因“每章末尾”与“每条计划/变更”不同而给写手和作者两套结果。该冲突不是文字润色，会直接改变守卫的可观察结论和待处理数量。
**如何核实**：以同章内 `禁止值 -> 合法值` 的两个补丁分别对照提案与 README：前者应产生逐变更违约，后者章末不报；当前 t32 README 的表格仍保留章末措辞。
**建议改法**：在 Task README、提案和后续 ADR/Spec 只保留一个权威定义；若采用第二版的逐变更语义，删除章末表述，并补充“实际/按计划、同章恢复、地址删除、分叉”四类守卫结果的验收。
### 30. 线视图增量更新的失效集合由调用方猜测
**严重程度**：重要；**类别**：安全与性能
**位置**：提案第 7 节第 126 至 128、139 至 140 行；原型 `prototype/worldline/lines.ts` 第 37 至 105 行；内核 `packages/nb-canon/src/engine/incremental.ts` 第 335 至 373 行。
**现象**：提案要求只更新“已经建好且看得到这条变更的线”，并说改初值要重算每条已建线；但没有定义从变更/分叉参数到受影响线集合的算法、线定义变化如何触发结构重建、淘汰中的并发读取如何处理。原型的 `update` 接收可选的 `seenBy`，由调用方传入；省略时遍历所有缓存引擎，传错或漏传都不会由核心校验。
**为什么是问题**：改父线切口前的初值会影响所有后代线，即使某后代当前没有直接可见该变更；改切口、往回多久、带过去地址或父线归属会改变可见集合和合成赋值，不能只按当前变更的 `lineOf` 判断。淘汰后重新建立的线还必须与未淘汰的线逐字一致，否则同一版本读结果取决于缓存命中。错误的失效会产生静默错误，过度失效则使“当前线常驻、其它线按最近使用”的性能结论失效。
**如何核实**：建立三层父子线，先缓存祖先、父、孙三条引擎，再修改祖先切口前地址、分叉参数和带过去地址，分别从缓存命中与淘汰重建路径读取；当前原型没有线定义版本或后代索引，`seenBy` 也没有由 `changed` 推出的可验证结果。
**建议改法**：把世界线树、分叉参数和可见前缀摘要纳入缓存状态；定义受影响线闭包（祖先前缀、直接/间接后代、兄弟排除）及结构变更的强制重建规则。更新 API 不接受调用方自由的 `seenBy`，由内核根据变更类型和线树计算；淘汰只丢派生缓存，重建后用按线 reference/incremental 差分验收，并给出常驻上限和并发读写语义。
