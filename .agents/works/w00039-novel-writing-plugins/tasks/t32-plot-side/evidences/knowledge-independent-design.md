# nb-canon 知情第一版：独立设计

依据：canon Spec（model、components、project）、t32 时间方案、nb-story 的知情实现、三份对比研究。标“推断”的没有证据。

## 一、质疑

**精简。** 知情不该是全书都填的表。全知问题有两类：泄露（写手拿到全知上下文，卫兵认出勇者）与按常理推（铁匠药师）。前者靠“藏起来、标出来、写完查”，后者靠一句规则。结构只给重要设定，其余让写手推。互动小说与桌游常见做法是“信息卡加持有者标签”（推断，未查证）；旧应用只有手填自由文本，程序用不上，也没人查。

对主会话第十三节的意见：
1. “每件事带知道范围”要收窄，只有建成知识点的才带。
2. “角色背景写成字段”不必做，职业出身已在人物主 MDX，另建会重复。
3. “读者的知情由内核按讲述整体推导”过头：nb-story 的知情抽取三次只有约 36% 一致。只需在讲述上加“揭示了哪个知识点”的标记。
4. 知情者列表我存到人物上，不存在秘密上。

**成本。** 记账 Agent 不逐章问谁知道什么，只在三种时机动手：作者标过的知识点出现新知情；看起来像秘密的，用现有未决问题问作者“要不要保密”；写完后程序圈候选、再问窄问题查穿帮（nb-story t34 验证过窄问比泛问可靠）。

**使用者。** 作者要一句话保密；写手要短简报不是表；记账要知道何时写、写哪。

**与 nb-story 统一。** 读者的钟是叙述位置，角色的钟是故事位置与世界线，必须分开存。nb-story 把读者与角色放进同一张知情表，“读者知道被当成角色知道”才成了各组最大错因。

**排障与维护。** 每个答案带来源（记录的行、规则推出、无记录）；行是补丁，现有来历直接可用。不加第七种存储对象，不另造位置、世界线、计划、撤销。

## 二、推荐设计

### 知道的东西：知识点

知识点是种类为 `知识点` 的**条目**，命题放在一句话描述里（“勇者的额头有星印”）。带内置 Component `know.point`：

- `scope`：`common`（常识）、`trade`（行内，按 `rule`）、`secret`（没记录的人一律不知，写手不许推）、`sealed`（绝密，给写手只说“存在涉及某某的保密设定”）；没标就是没标。
- `rule`：一句话，粗略档（“药师、草药商认识”）。
- `about`：涉及的条目。

现有机制缺三样：字段没有**条目引用种类**（“谁”只能写文字，改名、删除、`sameAs` 不跟着走）；没有按引用值的**反向索引**；讲述没有**揭示标记**。设置 `sameAs` 时提示作者建“甲就是乙”知识点，本体那行由程序补。

### 知道的人：存在人物或组织条目上

```ts
type Degree = "knows" | "believes" | "suspects" | "unaware" | "forgot";
type How = "witnessed" | "told" | "inferred" | "read" | "rumor";
interface KnowRow {          // 人物 Component know.mind 的列表 knows
  id: string; point: EntryId;
  degree: Degree;
  holds?: string;            // 误信：他自己以为的那句
  how: How; from?: EntryId;  // 谁告诉的
}                            // 行由 listAdd、set 补丁产生，原句与“推断”用补丁已有的 basis
interface Telling { /* 现有字段 */ reveals?: { point: EntryId; level: "hint" | "plain" } }
interface Knows { degree: Degree | "none"; holds?: string; how?: How; source: "recorded" | "rule" | "none" }
declare function knowsAt(who: EntryId | "reader", point: EntryId, pos: ReadPosition, mode: Mode): Knows;
```

**存在人物上的理由**：写手要“这场戏每个人知道什么”，读一个条目即可；回溯只需让分叉带过去 `星瑕.know` 这个地址，别人的 `know` 按父线切口处的值回到那时；马甲与组织也落在条目上。代价是“谁知道这个秘密”要反查，知识点只建重要的，量小。

**精度三档**：精确是行；粗略是知识点的 `rule`，不建行；没记就是没记，写手推。写手的推断不直接进世界，记账时写成行，basis 为推断，作者确认后改为作者定的。

### 读者

读者不是条目，不存行。`knowsAt("reader")` 由讲述的 `reveals` 算：读取章之前有 plain 为知道，只有 hint 为怀疑，否则不知道；按计划模式再加细纲里的揭示。读者的钟是章序，与世界线无关，被回溯抹掉的六小时读者读过就算读过。

### 时间、世界线与目标

行是补丁，按安放折叠；“第 3 章国王告诉贤者”是第 3 章的一条剧情变更。程序检查传话链：`from` 在那个位置上必须已知。目标与态度用人物上普通的 Component，信念并进 `know`，记忆是 `witnessed` 的行，失忆是改 degree；不做角色自主行动。

### 给写手的上下文与查穿帮

简报按场景出：在场每人“知道、不知道”的、与本章涉及条目有关的 `secret` 以上知识点，`trade` 的附规则。示意：“卫兵（不知道：勇者的额头有星印；只有国王、贤者知道；不得写成被认出）”。先记后写：细纲的计划行按计划模式进简报；先写后记：记账从对话记行，并问是否保密。

写完查穿帮：本章涉及条目关联的 `secret` 以上知识点，乘以在场且无行的人，对每个候选问窄问题“某某有没有按这件事说话，引原句”。结果进待处理，不自动改。新待处理种类：`leak-suspect`、`early-reveal`、`chain-broken`（传话链断）、`unrecorded-knowledge`（正文有人知道却无行）。

### 揭示计划与提前泄底

揭示计划是一条计划的剧情变更，细纲讲述带 `reveals`，现有计划、兑现、取消机制直接用。提前泄底：读者最早的实际揭示早于计划，或程度更强，报 `early-reveal`；作者可改计划接受。

### 与 nb-story 共用

抽出共用类型：`Telling`（含 `reveals`）、`Degree`、`How`、知识点形状。nb-story 的 `state` 拆成 degree 与 how（heard、read 是 how），`Secret` 对应知识点，读者那行改由揭示算；它“听者台词推出听说、本人身份推出知道”的规则可给记账当提示。

## 三、备选

**A：只做保密标记与规则，不存知情行。** 最便宜。没选：误信、传话链、穿帮候选、回溯后谁记得都无处放。但它是推荐设计的第一档，作者可只用这一档。

**B：知情者列表放知识点上。** 反查最直接。没选：写手视角要全表扫描，回溯要选择器不是地址，马甲与组织难表达。

**C：新增第七种“知情记录”对象。** 灵活。没选：要重做位置、世界线、计划、撤销、修订，nb-canon 刚做完这些。

## 四、例子

**卫兵与勇者。** 第 3 章国王与贤者谈星印：记账问作者后建知识点标 `secret`，两人各一行，讲述 `reveals plain`，读者第 3 章知道。第 4 章简报里卫兵一行是“不知道”。若仍写出“卫兵盯着额头喊勇者”，候选（卫兵无行、本章涉及勇者）问出，进 `leak-suspect`。

**铁匠、药师与草药。** 草药建知识点，`trade`，`rule: 药师、草药商认识`，不建行。写手按规则让药师认出并标推断，铁匠不认；记账把药师那句记成推断的行，等作者确认。

**妹妹的误信。** 知识点“哥哥是被软禁”，`secret`；哥哥 knows；妹妹 believes，`holds: 哥哥不想回家`，how 为 inferred。写妹妹视角时简报给她信的那句，不给真相。哪章她知道了，一条剧情变更把 degree 改为 knows，来历能看到之前的误信。

**命案。** 知识点“管家是凶手”：管家 knows；女仆 believes，`holds: 是园丁`；侦探第 18 章 knows（inferred）。细纲计划第 20 章 plain 揭示。第 12 章的那句被记账标成 `reveals hint`：读者从第 12 章起“怀疑”，报 `early-reveal`，作者选“故意让人猜”就改计划为 hint，否则改正文。

**回溯。** 第 8 章分叉带 `星瑕.know`。新线上别人的 `know` 回到切口处，不认得被抹掉的六小时里的事，星瑕的行保留。读者按章序算，读过的揭示仍有效。

## 五、没把握

1. 简报里“相关知识点”按 `about` 与本章涉及条目的交集圈，会漏间接相关的（推断）。
2. 穿帮的窄问题准确率要真实模型测，不能只按 t34 外推。
