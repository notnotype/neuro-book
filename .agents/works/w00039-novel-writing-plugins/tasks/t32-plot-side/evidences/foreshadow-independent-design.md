# 伏笔第一版：独立设计

只读了 Spec、t32 的时间与知情方案、旧应用账本、nb-story 对照；没改任何文件。标“推断”的没有读到代码或运行证据。

## 一、先质疑

**反对与精简。** 伏笔本身不是新东西，要做成结构的只有一件：读者的债，即向读者许了什么、还欠多少。它和别的概念各有重叠，但主人不同：剧情线归并“发生了什么”，计划与兑现管“写没写”，未决问题是作者自己没想好，知识点的揭示是读者“知道到什么程度”。所以不合并，但要复用：节点的计划与兑现沿用计划机制，悬念的揭示不重复记（第二部分第 5 点）。业界：旧应用调研引到的开源工具 storyforge 有伏笔实体、四态、逾期检测、上下文注入、候选到确认两层（见旧 Task 93 README）；Plottr、Campfire、Scrivener、Aeon Timeline 有没有伏笔对象：未查证（印象是靠情节线、标签、元数据约定，没有账本，未验证）。

**成本。** 旧版 beat 一场一线一条，作者和 Agent 都要逐条登记，真实项目里是否被用起来也没有证据（Task 93 的验证被降级为单测）。所以：只有作者或 Agent 建了的伏笔才被检查，不追求记全；节点尽量由已有记录算出来（兑现计划、揭示标记），少让人填。

**使用者。** 作者要的是“我欠读者什么、哪些没排回收”；写手要的是本章埋、提、收什么，什么不能碰；记账 Agent 要的是窄问题而不是通读。三者读同一份算出来的账本。

**与 nb-story 统一。** nb-story 的悬念是 raised、partial、answered 三种进展，挂读者位置，没有计划。两边共用的是“节点 = 角色 + 读者位置 + 原文讲述”，所以节点应记在讲述的位置上（见第二部分第 3 点）。

**可观测。** 阶段、逾期、顺序都不存，读取时算，能给来历（这个节点从哪条记录来、是显式的还是揭示标记推出的）；撤销记录后自然消失。

**长期维护。** 内核只多认一种不透明的链接，种类、角色、检查规则放进插件的 Component 与规则表；旧版 10 条节奏 lint 无使用证据，不搬。

## 二、推荐设计

**1. 伏笔是什么、存哪。** 伏笔是一个条目（种类“伏笔”），加一个 Component `foreshadow`（命名空间 `fs`）。条目的名字与一句话描述写“许了什么”（对写手可见的面）；主 MDX 写兑现预期（真相，按需给）。不加第七种对象，不另建账本表。

**2. 节点记在哪。** 节点是剧情变更上的一种新链接，不是补丁：

- 不用补丁，因为伏笔的节点是写法上的手段，不是故事里的状态；补丁会让“伏笔条目被删”拖垮整条故事变更（一条变更里一个补丁套不上，整条都不算数）。
- 一件已有的事（袖扣被捡到）直接挂链接，不重复记；没有故事事件的节点（一句预言、一处意象）记一条补丁为空的变更。
- 计划节点是计划变更上的同样链接；写出来的变更用 `fulfills` 兑现它，**默认继承计划的节点链接**，写手只说“兑现了 c7”就够。

**3. 位置用讲述，不用安放。** 节点的读者位置：第一条正文讲述的章，没有则细纲讲述的章，再没有才取安放的章；未排章的另算。理由与知情一致：读者的钟是章序，故事时间不是；补叙里埋的伏笔，读者是在补叙那一章读到的。同章内先后用排序键，两边都能比时才比。

**4. 种类与角色。**

| 种类 | 要回收 | 特点 |
|---|---|---|
| `setup` 埋设回收 | 是 | 必须先埋后收 |
| `mystery` 悬念 | 是 | 可挂答案知识点（第 5 点） |
| `prophecy` 预言 | 是 | 兑现方式（字面、反讽）写进兑现预期 |
| `motif` 意象 | 否 | 靠可选的参考间隔提醒 |

镜像并入意象，不单列。节点角色五种：`plant`（埋，悬念里是提出问题）、`echo`（呼应）、`mislead`（误导）、`partial`（部分回收）、`payoff`（回收）。旧版的 setback 与误导合并。链接另有可选 `note`，是给本场写手的具体指示（旧版 beat note 有用）。

**5. 与知识点的揭示不重复记。** 悬念可以把“答案”指向一个知识点。读者对这个点的揭示标记，在伏笔账本里自动算成节点：暗示算 `echo`，明说算 `payoff`（作者想标成部分回收的，在讲述上显式挂 `partial`）；计划变更的细纲讲述里带标记，就是计划的回收。同一处讲述只记一次，账本从两边合并读。副作用：知情原型报的“提前泄底”改成两级——明说早于计划回收才算泄底；暗示由有账本的悬念认领，不报；没有伏笔认领的暗示只给低级提示。

**6. 状态怎么算。** 作者意图存一个字段 `状态`（进行、放弃），用创作修改改，放弃带原因，不随章变。阶段不存：在读取位置与模式（实际或按计划）下，按节点算 未埋、已埋、呼应中、部分回收、已回收；放弃时显示“放弃（已埋）”。计划节点算不算沿用 [`canon.model`](model.md) 输出 13：已兑现的不再算计划，被取消、被替代的不算。待定与已撤销的变更不进账。

**7. 检查。** 分两级，避免撑大待处理：

- 进待处理（要作者拍板）：`foreshadow-payoff-before-plant` 没埋就回收；`foreshadow-plan-missed` 计划的节点所在章已有章写完、没兑现（逾期）；`foreshadow-order` 回收后又埋；`foreshadow-leak` 明说早于计划。
- 只进账本提示：已埋但没排回收（意象除外）；设了参考间隔而太久没提；放弃但正文留着已埋的句子（列原句，作者要不要改）；没有伏笔认领的暗示。
- “正文里像伏笔的句子”：程序不猜。借 nb-story 的教训（自动找错准确率 5% 到 27%，程序圈候选再问窄问题有效），只做两种窄问题：本章计划里有节点的，问“引出做到它的原句，或答没写”；有活跃伏笔的名字或别名出现在本章的，问“是不是呼应，引原句”。新伏笔的发现留给作者和细纲阶段，第一版不自动提。

**8. 给写手的上下文。** 简报一段：本章要埋、要推进、要回收（回收时才给真相与兑现预期）；已埋、回收排在后面或没排的：只给“面”和“不要回收、不要点破”；`答案` 知识点保密或绝密的，不给内容，照知情的规则只说有一件设定。意象列出上次出现的章。

**9. 内核要补的。** (a) 条目引用字段（`答案`；与知情共用，写入校验、改名删除跟得上、还原查依赖）；(b) 剧情变更的链接加 `{kind:"beat", thread, role, note?}`，内核只校验 `thread` 存在、角色是不透明短字符串，规则由 Component 的插件管；(c) 讲述上的揭示标记（知情已定）；(d) 读者位置函数（章序加排序键），供伏笔、知情、nb-story 共用；(e) 新的待处理种类与简报段由插件登记。推断：`involves`、`lines` 已有条目引用的校验可沿用，需读代码确认。

```ts
type ForeshadowKind = "setup" | "mystery" | "prophecy" | "motif";
type BeatRole = "plant" | "echo" | "mislead" | "partial" | "payoff";

// Component fs 的字段
interface ForeshadowFields {
  kind: ForeshadowKind;
  importance: "main" | "normal" | "minor";
  intent: "open" | "abandoned";   // 作者意图，创作修改
  abandonReason?: string;
  answer?: EntryId;               // 条目引用：悬念的答案知识点
  cadence?: number;               // 可选，参考间隔（章）
}
// 新链接，加进 StoryChange.links
interface BeatLink { kind: "beat"; thread: EntryId; role: BeatRole; note?: string }

// 读取时算出的
interface Beat {
  role: BeatRole; chapter: ChapterId | null;        // 读者位置，见第 3 点
  source: "link" | "reveal" | "inherited";          // 显式、揭示标记、继承自兑现的计划
  change: ChangeId; plan: boolean; fulfilledBy?: ChangeId; quote?: string;
}
type Stage = "unplanted" | "planted" | "echoed" | "partial" | "paid";
interface ForeshadowRow { entry: EntryId; fields: ForeshadowFields; stage: Stage; beats: Beat[]; flags: ForeshadowFlag[] }
declare function foreshadows(world: World, at: ReadPosition, mode: "actual" | "plan"): ForeshadowRow[];
```

## 三、备选

**备选 A：节点做成补丁。** 伏笔条目上加“节点”列表字段，每个节点是一次 `listAdd`，阶段由现有折叠、来历、撤销算出，内核几乎不用改。没选：事件与伏笔记账绑在一条变更里，伏笔条目一删或没启用，真实事件的状态补丁也跟着套不上；节点位置变成安放而不是讲述；每个节点都要重写事件描述。

**备选 B：照搬旧版账本。** 单独的 Promise 与 Beat 对象、独立的状态机。没选：违背“只存六种”，同一件事要在计划、账本两处各记一遍，正是旧版的手工双维护痛点（旧应用对照第三节第 4 条）。

**更省的做法 C：只用剧情线条目加标签。** 零内核改动，但种类与角色不是机器可读的，检查做不了；可当没上线前作者的临时用法。

## 四、例子走一遍

| 例子 | 记什么 | 结果 |
|---|---|---|
| 魔偶（埋设回收） | 条目“魔偶会再派上用场”（`setup`）；第 1 章“靠魔偶逃脱”那条变更挂 `plant`；第 15 章一条计划变更挂 `payoff`，细纲讲述作为位置 | 第 1 章写完：已埋，排了第 15 章回收。第 2 到 14 章简报写“不要回收”。第 15 章简报给兑现预期。第 16 章开写时计划还没兑现：报 `plan-missed`。放弃：状态改“放弃”并取消计划，已埋的原句列在提示里 |
| 袖扣（悬念） | 条目“命案凶手是谁”（`mystery`），`答案` 指知识点“管家是凶手”（保密）；发现尸体那条挂 `plant`；第 12 章讲述带暗示标记，第 20 章计划讲述带明说标记 | 第 12 章起账本自动出现 `echo`，没有重复记；第 20 章是计划回收。第 18 章侦探知道不算泄底，读者明说早于第 20 章才报。简报不给“管家”，只说一件涉及某人的保密设定 |
| 预言 | 开篇一句话作补丁为空的变更，挂 `plant`，条目 `prophecy` | 没排回收：账本提示一行，不进待处理。作者排了第 40 章计划后消失 |
| 银白长发（意象） | 条目 `motif`，别名“银白长发”，参考间隔 8 | 每章别名出现就问一条窄问题；确认的呼应记补丁为空的变更。超过 8 章没出现，账本提示。无需回收，不查逾期 |
| 让读者以为是园丁 | 同一个悬念条目上，第 14 章“窗下的靴印”挂 `mislead` | 第 20 章回收后误导被拆穿；回收没排时账本提示“有误导没有拆穿”。女仆误信园丁仍记在她的知情里，两边不互相推 |

## 五、没把握

- 读者位置在同章内的先后精度只到排序键，同章里“先埋后收”可能漏报，选择不报。
- 两条 `answer` 指向同一知识点的伏笔会同时认领同一揭示，是否允许，先报提示，留到真实写作里看。
- 意象的窄问题成本和准确率要用真实模型测。
- 参考间隔与“逾期”的阈值：旧版也没有使用证据，第一版只当提示。
