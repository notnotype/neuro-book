### 1. 世界线没有独立身份，和剧情线字段混在一起
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 3 节、第 5 节；内核 `packages/nb-canon/src/core/schema.ts:134-143`
**现象**：提案把分叉定义为剧情变更，并要求安放、读取位置带世界线，但没有定义世界线的稳定 id、父线、切口、触发变更、结束或回到父线的持久化形状。现有 `StoryChange.lines` 已有明确语义：只能指向 `type="剧情线"` 的条目；它不是世界线。提案没有说明世界线是新字段、条目，还是复用 `lines`。
**为什么是问题**：照字面实现会把“叙事剧情线”和“世界线”混为一个集合，或者每个读取 API 各自猜一套线身份。分叉后的默认读取位置、回溯后第 9 章读哪条线、梦境返回父线、IF 线结束等都无法由日志重放唯一决定；多层分叉也没有可验证的父子关系。该缺口先于引擎实现，不能靠在 `Placement` 上加一个字符串补上。
**如何核实**：现有 `StoryChangeSchema.lines` 只是 id 数组；`revisions.md` 的引用、`project.md` 的 `changes` 筛选与 `incremental.ts` 的事件构造都把它当剧情线。搜索 `world-line`、`branch`、`parent line` 的规范和 schema 没有对应定义。
**建议改法**：先定义独立的世界线标识与分叉记录字段：根线、父线、切口事件、触发事件、分叉类型、结束/返回规则；明确一条变更能否属于多个世界线以及与现有 `lines` 的关系。把默认线、显式线和无效线的失败码写进 `ReadPosition` 与服务合同。

### 2. 增量引擎的状态键和结果键都不是按世界线索引
**严重程度**：阻断；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 3 节；`/home/notnotype/CodeRepository/neuro-book/.worktree/w00039-t29-canon-kernel/packages/nb-canon/src/engine/incremental.ts:34-36,116-245,529-650`
**现象**：现有引擎的 `Snapshot` 只有一张全序事件表、按条目的一条时间线和 `outcomes: Map<changeId, ChangeResult>`。`actualEvents()` 每条已写变更只生成一个事件，`positionRank()` 只有初值/章开头/章末尾，`snapshotFor()` 的按计划覆盖层只按计划 id 集合缓存。
**为什么是问题**：同一条父线变更在子线可能已被切口排除，也可能被继承；同一个 `changeId` 的套用结果、地址不完整范围、核对点结果和计划兑现进展因此可以随读取线不同而不同，现有单值 `outcomes` 无法表示。切口取父线快照还要求父线的历史折叠结果能作为子线前缀，而当前增量更新只按条目和一个 `Point` 传播脏区；它没有线的祖先链、切口快照、分叉层级或线内计划覆盖键。按计划模式、`origins`、嫌疑区间、`pending`、`chapterEntries` 也都直接消费这套单线时间线。只在读取位置上加 `line` 参数会得到“能传参但算错”的实现。
**如何核实**：读 `Snapshot`、`actualEvents`、`recompute` 和 `snapshotFor` 可见所有缓存键分别是条目、变更 id 或计划 id，没有 line path；`Engine` 接口的 `entry/origins/progress/pending` 的 `ReadPosition` 也没有线。
**建议改法**：先给出线感知的折叠不变量和缓存键：线节点及祖先、切口前缀、每线的变更可见性、每线的变更结果与不完整传播。明确 `outcome`、核对点、计划兑现、嫌疑区间和待处理是否按线返回；再按该合同重做 reference/incremental 双引擎与差分验收，而不是只改 `Placement` 类型。

### 3. 讲述标记没有可排序的稳定发生点，两个钟在同章和改稿时失去顺序
**严重程度**：阻断；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 4、5、9 节；`packages/nb-canon/src/core/schema.ts:36-38,134-143`；内核 `docs/specs/canon/revisions.md` 输入表第 57 行
**现象**：提案把揭示和伏笔节点放到 `told` 的具体讲述上，但只说“位置是该处讲述所在的章”。现有 `Telling` 只有来源、可选章和原句，没有稳定讲述 id、段/偏移或章内排序键；现有排序键属于剧情变更或核对点，不属于 `told` 元素。无 id 数组在修订中按整个数组记录。
**为什么是问题**：同章先埋后收、先暗示后明说、同一事件在回忆和当前叙事中各讲一次时，程序无法判定节点先后，也无法判断“没埋就回收”“明说早于计划”或读者在章中哪一刻知道。改稿后同一句原文重复出现也无法稳定定位标记。把被抹掉的段落算作已读更要求每个讲述发生点能区分旧线、重写版本和读者路径；当前形状会把整章或所有分支的标记混成一个章级集合。
**如何核实**：`TellingSchema` 没有 position/line/occurrence 字段；`fillDefaults` 只给剧情变更的 `at.key` 和核对点的 `place.key` 赋值，不能给 `told` 元素排序；`revisions.md` 明确无 id 数组作为一个叶子处理。
**建议改法**：定义稳定的讲述发生点（章、段/块或正文版本锚点、章内顺序、必要的世界线/读者呈现身份）并把标记挂到该发生点。规定同一发生点上的多个标记排序、正文改稿后的失联诊断、重讲与计划兑现继承的来源和范围；读者钟按这些点折叠，而不是只按 chapter id。

### 4. 时间约束矛盾和非法历法说法没有“局部降级”合同
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 2 节；`docs/specs/canon/project.md` 第 88 行
**现象**：提案说负环是矛盾、环上的说法是打架的；又说改历法后不成立的日期报诊断。但没有规定负环存在时哪些事件仍返回范围、哪些说法从网络中排除，也没有规定一条月长越界或被删除月份的说法如何参与其余约束。`nb-time` 的精度、约、不确定、开放区间以及自定义闰年/月份也没有持久化的结构和错误码。
**为什么是问题**：最短路在负环上没有有限的最早/最晚值；若直接照 STN 算，单个写错的说法会让整个网络的查询失效，正好违反“不能让整张网失效”的验收要求。若把非法日期静默丢掉，作者也无法知道哪些范围是建立在它之上。改历法还会改变所有相对“天/年/月”的约束，必须使旧缓存和范围依据失效，否则查询会返回旧历法结果。
**如何核实**：现有内核只有 `pending` 的四种固定项和 `project` 中没有时间诊断；时间原型的证据只覆盖无矛盾的网络、负环列出冲突和简单日历，未展示负环后的局部范围或非法日历的降级。
**建议改法**：定义每条说法的结构化约束、历法版本/摘要、有效性诊断及网络分量策略：冲突分量返回不可确定并保留其余分量的范围，非法说法单独标记且不污染可独立计算的网络；所有范围依据列出被排除的说法，改历法或模糊词表时使相关缓存整体失效。

### 5. 目标“按故事时间折叠”与总原则“时间不决定折叠”互相冲突
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 2 节第 6 条、第 3 节第 2 条、第 6 节
**现象**：已定决定要求角色目标“按故事时间算”。同一提案又明确时间不决定状态折叠顺序，状态仍按安放的前史序号、章序和章内排序键折叠；目标章节随后写成“按安放（故事时间）折叠”。时间是区间/偏序，且可能与安放顺序不一致。
**为什么是问题**：照字面实现有两个互斥结果：按安放折叠时，补叙和回溯中的目标状态不按故事时间；按推导的时间范围排序时，所有目标状态都要接受未定、并列和矛盾的拓扑结果，且会与内核已有状态值不一致。写作上下文、前提变了检查和“当时目标”会因此在同一版本给出不同答案。
**如何核实**：时间原型明确“安放与时间对不上”仍可存在，内核 Spec 的状态公式只按安放；目标方案没有定义“时间范围重叠/未知时的折叠规则”，也没有目标专用的读取模式。
**建议改法**：在决定表的“按故事时间”下明确是仅查询筛选，还是目标状态的真折叠轴。若保持内核单一安放折叠，应把目标的故事时间作为约束和诊断，不能声称按故事时间折叠；若确需按故事时间折叠，须定义偏序下的唯一性、未知值、冲突和与世界状态的双轴结果。
### 6. 条目引用只列了概念，没有定义可校验、替换和依赖闭包的字段合同
**严重程度**：重要；**类别**：不变量
**位置**：`docs/proposals/world-engine-plot-side.md` 第 5 节第 1 条、第 4 至 7 节；`packages/nb-canon/src/world/world.ts:545-591`
**现象**：提案列出知情元素 id、“谁告诉的”、讲述标记、伏笔答案、目标基于/冲突、决策挂靠对象等应算引用，也要求临时 id 替换、删除和还原跟得上，但没有定义引用的持久化形状、引用目标种类、每个嵌套键的校验规则、显示/墓碑语义或依赖路径。
**为什么是问题**：当前内核的临时 id 替换和还原依赖是键白名单驱动的：只识别 `entry/plan/by/change/cause/check` 等键，列表只识别 `involves/lines`；讲述标记的 `point/foreshadow`、知情行里的“知识点 id/谁告诉的”、目标的语义字段和伏笔答案不会自动成为引用。只补一个“reference 字段种类”仍不能覆盖 `told` 无 id 数组、列表元素 id 与对象引用的区别。照字面新增字段会出现原型已经证实的两个坏结果：临时 id 残留，或还原建条目后保留悬空引用且不报依赖。
**如何核实**：`world.ts` 的 `ID_KEYS`、`ID_LIST_KEYS`、`REFERENCE_KEYS` 和 `referencedIds` 是显式键集；`dependsOn` 只从这些结果和地址前缀判依赖。`core/schema.ts` 当前所有业务字段值仍是 `unknown`，没有引用类型。
**建议改法**：在组件/剧情插件合同中定义统一的 `EntryRef` 值形状或引用声明，列出每个引用路径、允许的目标类型、临时 id 归属、删除后的墓碑行为和显示方式。让临时 id 重写、发布校验、`opReferences`、依赖传递闭包、改动记录筛选共用同一份声明；给 `told` 标记和列表元素写专门的验收场景。

### 7. “在场”没有数据来源，知情穿帮检查会把涉及者误当在场者
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 4、8、10、12 节；`.agents/works/w00039-novel-writing-plugins/tasks/t32-plot-side/README.md` 第 168 至 205 行
**现象**：简报和穿帮候选定义为“本章涉及的保密知识点 × 在场而不知道的人”，有限视角又要求对白按在场的人查。现有内核的 `involves` 只表示剧情变更涉及条目，不能区分出场、听见对白、在场、叙述提及和仅被补丁修改。提案第 12 节也承认角色对话要补“情节上记谁在场”，但第 10、11 节已经把在场作为当前流程输入，没有规定它从哪里来、由谁确认、如何随线折叠。
**为什么是问题**：没有在场记录时，程序只能让主 Agent 手传一个数组或把 `involves` 当代理。前者不在世界版本和修订依赖内，后者会漏报卫兵、误报作者只改了状态的角色；回溯、补叙和同章多场景还会需要不同的在场集合。最终的“可能穿帮”不是可重放的检查，窄问题候选会随调用方输入变化。
**如何核实**：`model.md` 输出 20 的本章涉及条目只取 `involves`、补丁地址和核对点；`project.md` 的 `changes` 与 `chapterEntries` 也只按这些字段筛。旧应用的 Scene 才有 `subjectIds`，nb-story 的 episode 才有在场者，本提案没有对应字段或适配规则。
**建议改法**：决定第一版是否记录场景/讲述发生点上的参与者和听见者；若不做，删除“程序按在场检查”的保证，改成显式作者/主 Agent 输入并标注未核实。若要做，定义其修订、线、章内顺序、来源和缺失时的 fail-closed 行为。

### 8. 分叉后的时间关系自相矛盾：跨线“不比先后”却又要求子线不早于回溯点
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 2 节第 7 条、第 3 节第 3 条；时间原型 `evidences/time-examples.txt` 第 51 至 56 行
**现象**：提案要求新线上的事不早于“触发处往回多久”的时刻，同时规定不同线上的事不比较先后。回溯后的子线事件与父线触发事件必然需要一条跨线下界；同样，年龄、章节故事时间和查询“某段时间里发生的事”都需要知道哪些父线事件是子线的前置上下文。
**为什么是问题**：若严格不比较跨线事件，回溯下界无法进入 STN，原型第 8 章的时间保证就无法重现；若隐式把父线切口当作子线前置，又需要定义哪些父线事件可继承、父线未来事件为何不继承，以及多层分叉的传递规则。当前提案没有这组规则，时间诊断和世界线状态会对同一事件给出不一致的结果。
**如何核实**：原型证据依赖“新线上的事不早于触发处往回多久”来输出回溯时间；提案没有给 `nb-time` 一个线祖先/切口输入形状，时间网络的普通约束只描述事件相差范围。
**建议改法**：把线的祖先和切口建模为时间网络的结构化边界约束，明确跨线只允许哪些比较（父线切口到子线事件），其它兄弟线保持不可比；定义多层回溯和线结束后的时间投影，并为跨线查询写验收例子。

### 9. “已定必须有作者原话”当前无法由合同验证
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/proposals/world-engine-plot-side.md` 第 7 节；`packages/nb-canon/src/core/schema.ts:30-38,134-143`
**现象**：提案要求已定决策必须带作者原话出处，作者直接说出的决定可以直接建成已定，并禁止 Agent 自己定。但现有出处只有 `source`、可选章和自由文字 `quote`；`Actor` 只表示本次修订的作者/Agent/任务，不表示原话作者、消息 id、不可变消息版本或原文摘要。
**为什么是问题**：任何 Agent 都能构造一条 `source: message`、`quote: “作者已决定……”` 的 telling，程序无法判断这是不是作者原话、是否被截取、是否来自当前会话。结果是最关键的防护只停留在提示词，重放和审计都不能验证；“理由没说不许编”也同样没有可检查的来源边界。
**如何核实**：现有 `TellingSchema` 的 `message` 来源没有消息引用字段，`QuestionSchema.quote` 也只是文本；`revisions` 记录的 `by` 是写入者，不是被引用的作者消息。任务 README 第 324 行仍把“怎么认定作者原话”列为未定。
**建议改法**：定义作者消息/作者确认的不可变来源合同（消息 id、会话/作者身份、原文、引用范围和摘要），只允许系统从该来源生成已定决策；普通文字只能生成待定或“作者未确认”的候选。明确作者在 UI/主 Agent 对话中确认的落点和撤回/重开后的来源保留规则。

### 10. 守卫只在章末检查会漏掉同章短暂违反，按计划模式也没有读取合同
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 7 节；`.agents/works/w00039-novel-writing-plugins/tasks/t32-plot-side/README.md` 第 298 至 307 行；`packages/nb-canon/src/engine/types.ts:75-86`
**现象**：守卫定义为“范围内某地址不准取某些值”，决定检查写成“每章末尾检查”，同时按计划模式也要检查计划。现有 `pending(position)` 没有模式参数，`Engine` 的 `ReadPosition` 只有章节开头/末尾，也没有守卫结果或计划覆盖层的检查接口。
**为什么是问题**：同一章中先把地址改成禁止值、后又改回合法值时，章末状态正常，守卫永远不报；若约束的意图是“任何时刻不得发生”，这会漏掉真实违约。若只要求章末，提案必须明确它不是逐变更守卫。按计划模式还需要说明计划与已写变更的覆盖顺序、计划中途违反是否进待处理，以及实际/计划结果如何并列返回，否则写手简报和作者工作单会读到不同口径。
**如何核实**：现有引擎事件有章内排序键且逐变更套补丁，守卫若挂在地址上可以在每个事件后计算；但现有 `pending` 的合同只接受一个读取位置，`Mode` 只出现在 `entry/origins/render` 等接口。
**建议改法**：先写守卫的时序语义：逐变更、章末，还是两者都查；定义未知/不完整/删除/分叉时的结果。为计划模式增加显式模式参数或单独的检查视图，并给出同章先违约后恢复、计划违约、线范围和地址删除的验收测试。
### 11. 读者钟不分线会把未选择世界线的揭示和节点算进同一读者账本
**严重程度**：重要；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 3 节第 7 至 9 条、第 9 节
**现象**：提案规定读者钟不分线，抹掉的小时“读者读过就算读过”，同时允许平行世界各章把事件标到不同世界线，并让作者书的读者视角从 canon 按讲述过滤出来。没有定义读者正在阅读的世界线/章节路径，也没有规定同一章或相邻章节中另一条线的讲述是否对当前读者可见。
**为什么是问题**：如果两条线有各自的章节，或者回溯后同一章产生旧线与新线的两版讲述，按 chapter-only 的投影会把两条线的揭示、暗示和伏笔节点全部并入一个读者状态。读者可能在未读到的线里已经“知道”答案，导致提前泄底、悬念自动回收和反讽判断错误；反过来，若产品意图是所有线都算读过，也无法表达只读一条线的平行/IF作品。所谓“被抹掉的段落算读过”只解决回溯后旧内容的一个特例，不能替代读者路径合同。
**如何核实**：提案的读者位置只有“讲述所在章”，第 9 节只说按讲述过滤；现有 `ReadPosition` 也只有章开头/末尾，没有 reader path。原型只演示单层回溯的状态，未演示两条线各自讲述后的读者账本。
**建议改法**：明确作者书的读者出版路径是全线并集、选定线，还是每个读者项目独立选择；若有选择，给讲述发生点和读者位置加呈现路径/线可见性，并规定抹掉内容、重写章节和 IF 线的“已读”规则。为“旧线已读后回溯”“兄弟线分别揭示”“同章双线”写可判定验收。

### 12. 分叉形成的隐式快照没有进入还原依赖
**严重程度**：重要；**类别**：不变量
**位置**：`docs/proposals/world-engine-plot-side.md` 第 3 节；内核 `docs/specs/canon/revisions.md` 输出 12；`packages/nb-canon/src/world/world.ts:458-511`
**现象**：子线状态由“父线切口快照 + 带过去的地址 + 本线变更”计算，快照不是独立存储对象。现有还原依赖只按同一地址/前缀、引用新建对象或同一组计划兑现判定；它没有“子线变更依赖分叉/切口快照”的关系。
**为什么是问题**：还原分叉、切口之前的父线变更或带过去地址后，子线可能仍保留，但其隐式基线已经改变。若子线后续改的是不同地址，现有地址重叠和引用扫描不会把它列为依赖，作者可以单独还原父线并留下不再对应的子线状态。若把整条世界线都强行当依赖，又会使普通父线修订的还原范围和性能失控；提案没有选择。
**如何核实**：`dependsOn` 只扫描修订的对象路径和显式 id；`revert` 的补偿修订只恢复这些字段，不知道事件曾被哪条线的切口作为基线。提案只说“与还原的依赖”要补，没有定义分叉依赖的闭包和跨线的补偿顺序。
**建议改法**：把分叉的父线、切口、继承地址和子线变更写成可追踪的依赖边，定义分叉还原时是拒收、连同后代线一起还原，还是把后代线置为待处理。依赖结果必须能在修订记录和 `revert` 预览中列出，并覆盖多层分叉。

### 13. 待处理种类没有去重、聚合和保留期限，候选量会按角色与分支乘法增长
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/proposals/world-engine-plot-side.md` 第 1、4 至 7、10、11 节；`packages/nb-canon/src/engine/types.ts:75-86`
**现象**：提案把可能穿帮、提前泄底、传话链断了、前提变了、多个伏笔检查、多个决策检查等都放入“待处理”或提示，但没有定义待处理的稳定 id、根因、相同问题的合并键、按线/按章的归属、作者处理后的关闭方式或提示转待处理的转换。现有内核的 `PendingItem` 只有四种固定形状，并按位置和种类排序。
**为什么是问题**：一章有 `p` 个保密知识点和 `n` 个在场但未登记的人，可能穿帮候选至少产生 `p×n` 条窄问题；多个读者线、重复讲述和同一目标的连续前提变化还会复制候选。若每次读取都生成新 id，作者无法确认一个问题；若全保留，工作单会淹没真正需要拍板的项。提案的“常见有意为之只提示”没有说明哪些规则属于此类，也没有说明提示持续多久。
**如何核实**：当前 `pending` 结果是读取时计算、没有持久状态，根因只按现有变更/核对点合并；新增剧情侧检查没有对应 `PendingItem`、分页、排序和 `impact` 形状。原型只打印固定样本，没有规模或重复读取测试。
**建议改法**：为每种诊断定义稳定键（例如规则、对象、线、讲述点、范围）、根因和生命周期；把可自动确定的违约与需要作者判断的候选分层，规定提示的升级/抑制和汇总计数。给多知识点、多角色、多线、重复读和处理后重算写数量上限验收。

### 14. “绝密不进写手上下文”没有服务端角色隔离作为保证
**严重程度**：重要；**类别**：安全与性能
**位置**：`docs/proposals/world-engine-plot-side.md` 第 8、10 节；`/home/notnotype/CodeRepository/neuro-book/.worktree/w00039-t29-canon-kernel/packages/nb-canon/src/service/service.ts:177-292`
**现象**：提案要求主 Agent 能读作者真相，写手只能得到按视角过滤的简报，且写手自由发挥时可调用只读 `lookup`、`read`。现有 `WorldService.entry`、`object`、`lookup`、`render` 只接受普通 id、位置、模式和 `audience: author|agent`，没有 writer/bookkeeping/role 身份、能力令牌或绝密过滤参数；`agent` 渲染不是按角色视角过滤。
**为什么是问题**：把过滤留在“程序拼上下文”而让写手继续调用通用只读工具，就不能保证绝密不泄露：调用方可以请求另一个人物或知识点的完整条目，或把 `actual`/作者视角结果作为查询输入。模型提示词不是信任边界。即使当前所有 Agent 受信，错误的上下文拼接也会把绝密写入正文，且没有可审计的拒绝结果。
**如何核实**：服务入口的 `entry` 直接调用引擎并返回条目，`render` 仅按作者或 agent 选择渲染格式；`Engine` 也没有 `audience`/视角参数。提案第 10 节没有新的远程合同或权限失败码。
**建议改法**：定义只读视图的受众/角色能力和不可绕过的服务端过滤：写手令牌绑定视角人物、章节、线和最大调用次数；绝密返回结构化占位而非内容；主 Agent/作者视图另走权限。记录每次被拒的查询并为“直接读答案、换人物、换线、读绝密伏笔”写安全验收。

### 15. 伏笔自动认领和计划节点继承没有消歧规则
**严重程度**：建议；**类别**：正确性
**位置**：`docs/proposals/world-engine-plot-side.md` 第 5 节第 3 至 5 条；Task README 第 224 行
**现象**：提案规定悬念连到答案知识点后，该知识点的揭示自动成为呼应/回收节点；又规定兑现计划的已写变更默认继承计划上的节点。没有说明两个悬念共享一个答案时一处揭示由谁认领，也没有说明一个计划有多处讲述/多个节点、已写变更有多处正文讲述时继承哪一个、节点来源如何在计划改动或撤销后保持稳定。
**为什么是问题**：两个悬念会同时被同一个暗示推进或同一个明说回收，账本的“上次出现”和阶段会一起跳变，可能不是作者意图；多处计划讲述时“第一处”或“全部继承”都会改变节点顺序和写手上下文。只靠名字、答案知识点或 `fulfills` 无法恢复作者选择，也无法在撤销计划后判断实际正文节点是否仍存在。
**如何核实**：Task README 把“两个悬念答案相同”列为未把握项，但提案的待定项和验收没有覆盖它；现有 `LinkSchema` 只有 `fulfills`，没有节点继承来源或认领关系。
**建议改法**：明确自动认领是允许一对多、按优先级选一个，还是要求作者确认；为计划节点和实际节点存稳定发生点及来源/覆盖关系；计划修改、部分兑现、撤销和重复讲述都写出预期阶段与依赖测试。

### 16. “共用一层骨架”无法承接 nb-story 的段级、渠道和情节参与者语义
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/proposals/world-engine-plot-side.md` 第 9、13 节；`.agents/works/w00039-novel-writing-plugins/research/2026-11-04-nb-story-vs-canon.md` 第 5 至 6、51 至 63 行
**现象**：提案把一件事、涉及、出处和位置作为共用骨架，但明确承认 nb-canon 不记录角色说法的渠道/持有者、段级阅读位置、情节步骤/地点/在场者和说法间印证反驳；同时又声称作者自己的书的读者视角由 canon 投影出来、不再抽一遍。
**为什么是问题**：显式揭示标记只能回答“作者标了什么知识点在第几章被展示”，不能复现 nb-story 的 `fact/belief/claim`、说话人/听者、可靠度和段级可见性。读者问答、角色经历、渠道可信度和同章多场景会得到比 nb-story 更少或不同的事实。若把这套投影当共用骨架，后续重写 nb-story 仍需第二份抽取/适配；若接受降级，则“读者视角”目标必须明确只保证揭示/伏笔账本。
**如何核实**：对照文档列出 nb-story 的 `statements`、`episodes`、段落位置和参与者；提案第 13 节把它们列为“做不了的”，但没有把缺失能力转成接口边界、失败码或实验验收。
**建议改法**：在目标中明确作者视角投影的保证集合和不兼容集合；为段级阅读位置、渠道说法、角色/地点参与者另立能力或明确留在 nb-story 适配器，不再使用“共用骨架”暗示可互换。验收至少应验证样例书的可迁移覆盖率和缺失字段清单。
### 17. 决策扩展没有落成可发布的状态机和挂靠对象形状
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/proposals/world-engine-plot-side.md` 第 7 节；`packages/nb-canon/src/core/schema.ts:157-173`
**现象**：提案把未决问题扩成“待定→已定→被取代/放弃”，允许已定重新打开，并允许挂到条目、剧情变更、地址、章、另一条决策和范围。现有 `Question` 只有 `open|answered|dropped`、可选 `quote/about/answer`，`about` 只接受条目、剧情变更或地址；没有候选、最晚章、结论/理由/风险、取代关系、约束、守卫、章节范围或决策之间的引用。
**为什么是问题**：状态转换、重新打开后旧结论是否仍对写手生效、被取代决策是否能再次取代、放弃是否允许恢复，都无法由日志重放判定。`about` 若继续沿用，挂在章、范围和决策的对象会被自由字段塞进去，引用校验、还原依赖和悬空检查不一致；若新建一种存储对象，又违反“不加新的存储对象种类”的取舍。
**如何核实**：当前修订发布校验只认识 `QuestionSchema` 的三种状态和 `about` 三种目标；`LinkSchema` 只有计划连接，没有决策生命周期连接。提案的“六种对象之一”没有给出 schema、转换表或发布失败码。
**建议改法**：保留未决问题对象但写出完整持久化 schema 与状态转换表：每个状态的必填字段、允许动作、作者确认来源、取代/重开关系、范围和守卫；把所有挂靠对象统一成已定义的引用联合类型，并为非法转换、悬空引用、缺作者原话提供验证错误和验收场景。

### 18. 章级写作指示被纳入上下文却没有文件、版本和并发合同
**严重程度**：重要；**类别**：接口与合同
**位置**：`docs/proposals/world-engine-plot-side.md` 第 7、8、10、11 节；Task README 第 309 至 315 行；`docs/specs/canon/project.md` 第 17 至 23 行
**现象**：提案要求写作指示挂在活页夹章上、和细纲放在一起、不进世界，并要求程序拼接它、检查它与计划的冲突；但 t19/t11 的项目布局尚未定，canon 的宿主输入只有章序和正文，`project` Spec 明确不承诺 Agent 工具、写正文任务和作者界面。
**为什么是问题**：写手上下文无法确定读哪个文件版本，记账期间作者修改指示时也没有和“固定开始时的世界版本”一起做冲突检查。若指示不进世界，章节重排、分支读取、重写和审稿回放没有可审查的版本锚点；若把它放文件，又需要 nb-history/文件锁/并发和正文引用校验。提案当前同时依赖两种真相源，却没有选定一种合同。
**如何核实**：现有 `WorldService` 没有章指示读写方法，`WriteRequest` 的 `chapter` 只是修订元数据；内核只校验 `told` 的原句，不能校验指示文档的版本或与计划的对应关系。
**建议改法**：在提案范围内明确宿主侧数据合同：文件路径/章节稳定 id、结构化字段、版本与读取游标、作者修改与后台任务的冲突、章删/挪时的处理，以及 canon 只消费的快照接口。若这属于 t19 另一个能力，当前提案应把上下文和检查标为未承诺，而不是写成可运行流程。

### 19. 两份新 ADR 的取代范围和日志兼容策略没有写清
**严重程度**：建议；**类别**：文档
**位置**：`docs/proposals/world-engine-plot-side.md` 第 3 节第 9 条、第 6、7 节；`docs/adr/0037-world-engine-story-change-log.md:21-42`；`docs/adr/0039-world-engine-segmented-revision-log.md:26-33`
**现象**：提案只说要用两份 ADR 分别记录“时间不决定折叠”和“两个钟”，并说世界线部分取代 ADR 0037 的位置模块约定；没有列出 0037 哪一项被取代、0039 的分段日志/重放/修订依赖哪些新不变量，也没有说明 `format: 1` 的旧读者遇到带线安放和带线读取位置时如何处理。
**为什么是问题**：ADR 0037 仍写着以后只换位置模块、日志与补丁形状不变；0039 仍规定第一版不开放分支合并、世界在内存中按章留折叠结果。世界线不只是位置比较：它改变事件可见性、计划覆盖、结果键、还原依赖和服务方法。若不写精确的部分取代范围，接受后会同时存在互相冲突的长期决策；若新日志字段被旧实现当作未知字段保留但忽略，打开同一作品可能静默算错而不是只读失败。
**如何核实**：ADR 索引要求部分取代写明“旧 ADR 的哪一项”，而当前提案没有拟定条目；`project.md` 的日志合同只允许未知字段原样保留，`Placement`/`ReadPosition` 的语义变化并不等于只加未知字段。
**建议改法**：在接受前列出两份 ADR 的精确取代矩阵：0037 的位置、世界线、读者/故事轴分别由哪份取代，0039 的日志版本、重放和分支合并是否保持；定义旧日志的升级/拒读/只读策略。同步更新五份 canon Spec 的非目标、公开接口、失败码和 smoke，而不是只在“预期改动”列文件名。

## 对提案第七节六项待定项的判断
1. 审查方式：按推荐做深入审查是合适的，但应把多线真实运行、角色过滤和待处理规模列为必须验收，不应只审文字方向。
2. 实施切分与先后：先做引用是对的；时间和世界线应在知情、伏笔、目标、决策的线依赖落定前完成，当前“先知情/伏笔、后世界线”的顺序会返工。
3. ADR：两份 ADR 的主题足够覆盖两个钟和时间取舍，但必须补上世界线的精确取代范围、日志兼容和还原依赖，否则不具备接受条件。
