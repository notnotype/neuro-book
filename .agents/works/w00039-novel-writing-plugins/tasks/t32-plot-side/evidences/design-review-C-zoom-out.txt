### 1. 内核与剧情插件的边界没有讲，剧情词汇正在被写死进内核的数据格式（Q4、Q5）

事实：
- 总 Work 叫“novel-writing-plugins”，内核提案的 Component 走贡献点，内置与第三方同一套（ADR 0027，内核提案 L288-290）。
- 但本提案把知情、伏笔、目标、决策的语义全写进 `docs/specs/canon/`（P:263-269，新建 `canon/plot.md`），并把“揭示”“伏笔节点（埋下、呼应、误导、部分回收、回收）”正式加进内核 Telling 的形状并由内核校验（P:252）。
- 新的待处理种类“由 nb-canon 或剧情插件提供”（P:256）：同一份提案里没有定谁提供。待定项 7 条里也没有这一条。
- 现在的 Telling 是封闭形状，写满了就是内核格式：code src/core/schema.ts 的 TellingSchema 与 StoryChangeSchema（`told: Type.Array(TellingSchema)`）。

为什么重要：
- 内核格式一旦收下“五种节点、两档揭示”这套枚举，以后每加一种叙述手法（反讽、RP 的回合标记、悬念的分次进展）都要改内核格式和 Spec，而不是插件自己登记。这正是 ADR 0027 想避免的。
- 本提案自己也说“伏笔是写法，不是故事里的状态”（P:92）。写法层的东西放进“故事里发生的事”的日志，再让内核认识它，是把插件的概念升格成内核概念。

建议（作为候选交开发者，不是定论）：
- 内核只提供两样通用的东西：条目引用字段种类（P:251 第 1 条，确实需要），以及讲述上的“标注”`{kind, ...}`，由登记的贡献者校验，内核不认识具体 kind。
- 揭示与节点的语义、账本、检查全部放到剧情插件。待处理种类同理走贡献点。
- 在提案里加一节“内核与插件的分界”，并把待定项里补上这一条。
- 代价：内核要多做一层标注的登记与校验；好处是 Spec 的 canon/plot.md 变成插件 Spec，内核格式只为“引用”和“标注”这两个通用概念改一次。

### 2. 世界线假设“章序是一条线”，对 RP 读档和平行世界讲不通；而且 §14 没有任何世界线的备选（Q1、Q2、Q4）

事实：
- 读者的钟“按讲述所在的章序”，且“读者的钟不分线”（P:51、P:78）。章序来自活页夹，是一条线：code src/core/position.ts 的 ChapterOrder 与 Rank `[段, 主序, 次序]` 是全序。
- 世界线要把这个全序换成树（P:69-71），增量引擎整个按“全序前向遍历、每条目一条时间线、每 8 个事件存快照”写（code src/engine/incremental.ts:3-8），按计划模式还有按计划集合缓存的覆盖层（同文件 L12-15）。加线以后，这些缓存要再乘一维。这是内核里最贵、最难回头的改动。
- RP 的读档“从那里开一条新线”（P:214）。但新线上新写的正文放进哪一章？章序只有一条，读者钟不分线，新线的讲述在读者钟上排在哪里？提案没答。要么读档时旧线的正文被丢弃（那“原来那条线留着可以回看”只剩世界状态，没有正文），要么章需要带线，这等于读者钟也要分线，和 P:78 矛盾。
- 平行世界（P:79）“各章的事各标在哪条线上”：两条线的章交错排在同一条章序上，读者读到第 12 章时“读者知道什么”按哪条线？也没答。
- §14 的备选里没有一条是关于世界线的（P:236-245）。至少有两个该比较的：
  (a) 回溯这个具体需求（开发者自己的故事）用线性折叠加一种“恢复到某位置的值、带过去这些地址除外”的补丁就能表达。被抹掉的几个小时在安放序上仍排在回溯变更之前，要回看就读回溯之前的位置。不用树，不改全序。
  (b) 分支、IF、RP 存档当作独立的世界实例（复制日志到切口），代价是存储，换来内核不变。
  我没有说 (a)(b) 更好，只是提案没说明为什么它们不够。
- 提案自己承认 ADR 0037“换掉位置模块”的说法不成立（P:80）。这说明当时的接口承诺没有被验证过，现在的“折叠沿线走”同样没有原型：P:72 的原型只验证了一次回溯。

建议：
- 实施顺序里世界线排第 4（P:277），这是对的；但提案要先回答“带线的章序”再接受，至少说清读者钟在有线时怎么定义。
- 补 (a)(b) 的比较。如果回溯只有一个真实使用者，先用 (a)，把线推迟到 RP 或平行世界真的开工时。

### 3. 知情的存储形状（稀疏、手记的行）对世界推演与角色对话是锁定，且“按视角过滤”只对知识点条目有定义（Q4）

事实：
- 只有建成知识点的事才有知情，其余靠常理（P:84）；知情行是人物上的列表，“怎么知道”是记下来的字段（P:85）。谁在场、谁亲历，不是知情的来源，而是人工或记账 Agent 写的一个字段。
- P:205 承认“现在的 `involves` 分不出在场”，把“谁在场”推到以后（P:199、P:280）。
- 推演和角色对话要的是稠密的：每个角色对每件事“亲眼看到/听到”的全部感知。若存储是稀疏的“行”，推演每一步都要生成大量知识点条目（每个命题一个条目，种类“知识点”，P:84），这些条目住进作者浏览的条目树，污染作者视图。nb-story 样例书 100 章有 1356 条知情（P:222），哪怕只有一部分升格成条目，也是几百个条目。
- 另一种形状是：事件上记“在场/知情者”（感知），知道什么由事件派生，稀疏的“知识点行”只用来覆盖（保密、误信、忘了）。这能同时服务写手（保密）、推演（感知）、角色对话（经历，P:204），而且“谁在场”本来就是 §12 要补的东西。提案在 §14 比较了“知情记在知识点上”与“记在人物上”（P:241），但没有比较“由在场派生”。
- “读工具按角色视角过滤”（P:198、P:132 的 lookup/read 按视角人物过滤）只有知识点条目有过滤规则（隐藏内容靠“保密”档）。条目自己的状态与主文字不含知情标记。例：国王与贤者对话写出“勇者额头有星印”，条目“勇者”的字段里也会有这个特征，过滤读工具时没有任何规则遮掉它。写手简报里“涉及条目在本章开头的样子”（P:115）更是全知的，防穿帮靠简报里的一句约束加写后检查。这一点 P:196-200 的“同一个投影”说得太满：写手拿到的是程序拼的文字加约束，角色 Agent 拿到的需要字段级遮罩，这是两种东西。

建议：
- 在提案里把“稀疏行 vs 由在场派生”作为一项正式取舍写进 §14，并说明选稀疏行的理由；若理由是“作者端先不要推演”，就把 §12 对推演的“承接得住”降为“要先重做知情的来源”。
- 把“视角过滤”的定义范围写清：只保证知识点条目与简报；字段级遮罩不在本版范围。

### 4. “两个钟”里的故事钟实际仍然是叙述序；闪回章的写手上下文会读到“现在”的状态（Q1、Q5）

事实：
- 总原则：故事里的事实按安放（故事时间与世界线）算，读者按讲述章序算（P:51）。
- 但安放缺省是“第一次讲到它的那一章”（内核提案 L202 “生效位置默认是第一次讲到它的那一章”）；时间不决定折叠顺序（P:61）；“按故事时间读状态”是非目标（P:37）。所以“故事钟”在默认情况下与讲述章序重合；只有作者把事放进前史才分开。
- 写手的上下文读“涉及条目在本章开头的样子”（P:115），读取位置只有“初值、第 N 章开头/末尾”（code src/core/position.ts:4-9、:41-48）。写一个闪回章（回到 590 年）时，章 N 的开头位置读到的是所有已安放事件之后的现在：角色已经知道后来才知道的事、目标已经是后来的目标。这恰恰是提案要解决的“全知问题”。
- 提案 P:20 把“放不进十五岁那年、三百年前”和“回溯”算作缺口，却没有一处提到闪回、回忆、补叙；只在 §14 提了一句“补叙与回溯会让相对加减断掉”（P:239）。前史（研究文档说“前史是经历的主体”，plot-capabilities.md 第三节）与写闪回章的上下文是同一个问题。

建议：
- 要么承认故事钟默认就是叙述序，把 §1 的“两个钟”改成“安放（作者排定的序）与讲述（读者序）”，不暗示已经按故事时间算；
- 要么给读取位置加“按前史位置读”（或章可声明自己的故事位置），让闪回章读到当时的状态。第二种改动小：读取位置多一种 `{kind: "prehistory", order}`，折叠本来就支持。
- 无论选哪个，在非目标那条旁加一句“闪回章的上下文怎么办”。

### 5. 伏笔节点“没有补丁的剧情变更”其实是叙述层记录混进了事件日志，§14 反对第七种对象的理由对它不成立（Q1、Q2）

事实：
- P:92：“只是提了一句的，记一条没有补丁的剧情变更”。ADR 0037 决定 1：“只有一种记录：故事里发生的一件事”。“提了一句”不是故事里发生的事。
- 后果：情节视图（`changes` 按涉及筛，research 的 legacy-plot-vs-canon 第四节“情节视图”建议）会混进大量非事件；每条这样的变更也要安放、进时间网络（说法）、进待处理。
- P:244 否决第七种对象的理由是“同一件事在两处各记一遍（旧应用的手工双维护）”。但旧应用的双维护是两份各自带状态的数据要手工同步（legacy-plot-vs-canon 第三节痛点 4）；一个只按 id 引用讲述的节点对象不复制状态，不属于这种。
- 这和 P:92 自己的理由（“伏笔是写法，不是故事里的状态”）矛盾：写法层的东西没有自己的家。

建议：节点和揭示若进内核，就做成讲述的一个子记录（不建空变更）；若只能挂在变更上，就要求变更可以标 `kind: "mention"` 并在所有“事件视图”里默认过滤。与第 1 条一起解决最干净：叙述层标注由插件持有，引用讲述的 id。

### 6. 没有证据支撑或现在不需要的部分（Q3 YAGNI）

逐项：
1. **目标与态度**（P:98-104）：包括基于、冲突、后继、前提变了检查。研究文档对“动机、目标、内心、记忆”的建议是“第二版，先不设计；canon 的语义档字段已能装现在的目标或态度，别急着加对象”（legacy-plot-vs-canon.md 第四节建议表）。提案没有说明为什么改了主意。使用者证据：旧应用没有这个结构，nb-story 也没有（nb-story-vs-canon.md 第一节“动机、目标、记忆：无记录”）。
2. **伏笔检查与账本**（P:96）：进待处理 4 条、只提示 4 条，外加两种窄问题。旧应用同样的 10 条规划检查全部暂缓，“真实项目实测被降级为单测覆盖，缺少真实写作中伏笔与决策是否被用起来的证据”（legacy-plot-vs-canon.md 第三节痛点 7）。研究文档对规划检查的建议是“第二批搬，先观察”。提案把它全放进第一版。
3. **决策的守卫**（P:108）：程序检查“某个地址在范围内不准取某些值”。没有使用者，也没有原型。决策本身（带理由与出处，防 Agent 擅自改定）有旧应用的证据，守卫没有。
4. **保密分四档**（P:84）：“行内”是一句给写手的自然语言规则，没有程序能判定；“绝密”只是简报里的不给内容。四档里只有“保密”（没记的当不知道）是程序可检查的。可以先只做“保密”一档，其余当文本备注。
5. **STN 的规模数字**：“5 万件事几十毫秒”（P:64）来自一条链加稀疏锚点的合成数据（prototype/time/scale.ts），不是现实形状；一部三百万字的书的事件数是千到万量级，没有需要这个数字的使用者。对论证“用 STN 而不是更简单的排序”没有帮助，反而像是提前优化。STN 本身（P:60）能给出矛盾定位，是加分项，但“推不出的一端用最近邻居补上”等细节还是实现层。
6. **§12、§13（共约 45 行）和 §10、§11 里的 RP、推演、分场推进、找旧写法**：开发者要求的是“检验会不会堵死”，不是现在设计。§13 的结论是“数据层不换”，却写了评测方案、预算（¥10 到 20）、投影可行性。这些应该是 Task 记录而不是提案正文。
7. **12 个工具、每章预算、至多 6 次读**（P:138-153）：t20 要定参数，提案正文不需要。

### 7. 与 nb-story 的关系：10-31 否决“对齐”的理由没有被回应，同一部书可能出现两份读者视图（Q1）

事实：
- ADR 0037 背景：“与 nb-story 合成三个来源层再对齐：两种视角出发点不同，对齐太复杂。开发者 2026-10-31 否决”。后果段：“与 nb-story 合并时，共享出处与位置的写法”。
- nb-story 对 canon 的评估（nb-story-vs-canon.md 第四节）：做法 B（只共用骨架）的代价是“两套存储与修订；同一部作品两边各抽一遍会有两份，就是 10-31 否决过的对齐”，解法是“作者自己的书不用抽取，读者视角是过滤”。
- 提案采用 B，但：(i) nb-story 现有“项目导入整本书”的流程（nb-story-vs-canon.md 第四节障碍 3）对作者自己的书仍可用，没有说停用；一本作者的书如果有些章没记账，canon 的读者视图和 nb-story 抽取出来的读者视图不一样，哪一个是真相没写。(ii) §13 的“canon 到 V9 的投影”是第三条管线，要随 V9 数据文件格式（已发布 npm 0.2.1）演化，与 nb-story 本体并存。(iii) `nb-time` 说要 nb-canon 与 nb-story 共用（P:65），但 nb-story 没有承诺改用，它的 `day/part/rel` 只是“映射成相对历法上的说法”（P:120），映射由谁维护也没说。
- 开发者原话是“最好，不强求”（P:24、P:287）。提案目标 6 把它写成了目标（P:35），§13 又花了大篇幅。

建议：把 nb-story 一节缩成“不改数据层；共用 nb-time 与 Telling 的公共类型；读者视图的权威来源按作品分：作者自己的书看 canon，第三方书看 nb-story”，并明确 nb-story 的整本导入对作者自己的书是否保留。投影与评测方案挪到 Task。

### 8. 方案最关键的假设至今没有被模型实际验证（Q1、Q3）

事实：
- 全知问题能否压住，取决于记账 Agent 能不能稳定地记下知情与揭示标记。nb-story 的实测是“知情最不稳（同配置抽三次，53 条里 22 到 29 条不一致）”（P:43）。提案的缓解是“只记建成知识点的事”，规模变小，但小到什么程度、便宜模型能不能稳，没有数。
- 证据目录 knowledge-kernel-run.txt 与 foreshadow-kernel-run.txt 都是手写数据直接调内核 API（“确认能做的与要补的”，P:44），不涉及模型。review-plan.md 里的 F1、F2（用 deepseek-flash 写手与记账）是还没做的审查。
- 提案把这些 F1、F2 当作审查环节，而方案的取舍（例如读者标记完全由记账标、不从角色知情推，P:86）正依赖它们。

建议：把“记账对知情与揭示标记的漏记率/错记率”写成接受前必须量的验收（提案内核部分已有 t26 的量法，P:233），并写明如果不达标，知情退回什么形状（例如只留“保密名单”这一档）。

### 9. 做法与业界、仓库已有模块的对照（Q2）

- 时间：约束网络加历法与 Aeon Timeline 等写作软件的“事件之间的相对关系加自定义日历”同一路数（凭记忆，未联网核实），World Anvil、Kanka 一类是精确或部分日期加自定义历法，没有一致性求解。提案选择求解是为了矛盾定位与范围，这是合理的差异。没有发现问题。
- 双时间轴（位置与修订）与 Graphiti/Zep 等的 valid_at/created_at 双时间做法一致（凭记忆）。没有发现问题。
- 仓库已有模块：nb-memory 有“带有效区间的事实、主体注册表、缺坐标时不可见（fail-closed）”（内核提案 L105），与“知情行”“没记的当不知道”接近。内核提案已为状态层否决了复用（“只复用检索”），但提案没有重新比较“知情/信念”这一类。这一类正是 nb-memory 设计时考虑的对象，值得一句“为什么不用”。属于第 3 条的一部分，单列便于查。
- 知情用“条目加人物列表”表达，复用现有补丁与折叠，这条路没有新增存储对象，是正确的方向。没有发现问题。
