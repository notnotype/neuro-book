# 剧情侧提案的深入设计审查方案

审查对象：[作者视角的世界引擎：剧情侧（第一版）](../../../../../docs/proposals/world-engine-plot-side.md)（草稿）。

本文件只是方案，还没有开审。开发者 2026-11-04 同意按推荐做深入审查（提案待定项第 1 条）；按全局规则，开审前要由开发者批准审查者的安排与预算。

## 为什么用深入审查

- 这份提案改到内核的数据格式：讲述上的标记、条目引用、世界线（安放与读取位置带线、按线折叠）、未决问题扩成决策、时间说法；还新加一个共用包 `nb-time`。合并以后再改，代价比现在高得多。
- 五个讨论项是分开谈的，合在一起以后，两个钟（安放与讲述）、视角投影、检查分级这些贯穿全篇的规则，有没有互相打架，没人从头到尾看过。
- 开发者最担心的“全知问题”能不能靠简报与窄问题压住，只读文档看不出来，要让模型真的照着做一遍。

几个取舍：

- **按 reviewing Skill 的分工**：后端、领域与数据合同交 omp；拉远看与作者体验交 Claude Sonnet。提案几乎没有界面部分，不开前端审查。
- **不再开独立设计**：五个讨论项每一项都已经由一个只拿到目标的 Sonnet 子代理另出过一版并合并（t32 的 `evidences/*-independent-design.md`）。
- **两个 Agent 体验都用 deepseek-flash**：记账费用的口径本来就按它算；写手与窄问题能不能靠便宜模型做对，是这份提案成立的关键前提。要省额度可以先砍 F2（记账的格式第一轮内核审查测过）；F1 建议保留。
- **作者体验分两种写法**，对应提案第 11 节的两条路。

## 体验环节的材料（主会话开审前准备）

材料放在 git 忽略的 `.local/agent/works/w00039-novel-writing-plugins/tasks/t32-plot-side/review/` 下；审查报告与答案文件存进 Task 证据。

- **星瑕**：开发者给的故事种子与第一章大纲（t02 审查时已摘出），加主会话写的第 8 章细纲（回溯）。
- **命案（示意）**：主会话写 4 段短章（每段约 800 字），埋好：保密的知识点“管家是凶手”、女仆的误信、第 12 章的暗示、一处已定的决策（“第 20 章前不揭晓”），以及一处故意的穿帮（某人按他不该知道的事说了话）。
- **勇者（示意）**：国王与贤者的对话一段；卫兵的那场戏的细纲。
- **写手上下文**：照提案第 8 节，用 t32 的知情、伏笔原型在真实内核上生成简报（不手写），保证 F1 拿到的就是程序会给的东西。
- **答案文件**（不给审查者）：每章应记的知情行、揭示与节点、分叉；故意埋的穿帮在哪一句。

**F1 的任务**

| 任务 | 做什么 | 怎么判 |
|---|---|---|
| 1. 写卫兵那场戏 | 按简报（卫兵不知道星印，不得写成被认出）写一场 800 字的戏 | 有没有让卫兵认出勇者；三次各写一遍，数穿帮次数 |
| 2. 写星瑾视角的一场 | 有限视角，按简报（她误信哥哥不想回家，此刻不要让她知道真相）写 | 叙述层有没有写出她不知道的事 |
| 3. 回答窄问题 | 对命案里埋了穿帮的那章，逐条回答程序圈出的窄问题（引原句） | 查出埋的那一处没有；误报几条 |

**F2 的任务**

| 任务 | 做什么 | 怎么判 |
|---|---|---|
| 1. 记账：知情与揭示 | 给命案的两章记账：谁知道了什么（程度、来源、谁告诉的），哪句向读者暗示或明说 | 对照答案数漏记、错记；“读者知道”有没有被当成“角色知道” |
| 2. 记账：伏笔节点 | 同两章，标埋下、呼应、误导 | 对照答案 |
| 3. 记账：分叉 | 星瑕第 8 章（回溯）正文：提出切口、往回多久、带过去什么 | 切口与带过去的对不对 |

**E1、E2 的走法**：每一步写四样：作者想做什么；照提案会发生什么；哪里不清楚、哪里麻烦、缺什么；严重程度。

- E1（先记后写，星瑕）：写第 8 章细纲（回溯）→ 主 Agent 提计划与分叉 → 看预览 → 写手写 → 审稿 → 记账 → 第 9 章按新线读条目 → 想回看原来那条线。
- E2（先写后记，命案）：只给粗纲与几个保密知识点 → 写手自由发挥 → 审稿报出可能穿帮与新名字 → 记账、确认推断 → 想把揭晓提前（改决策与计划）。

## 重点

### A 的重点

1. **两个钟**：故事里的事实按安放、读者看到的按讲述章序。分叉之后，读者钟与线的关系、伏笔节点在被抹掉的那段里、知情的“带过去”与读者揭示，有没有自相矛盾的情况。
2. **世界线进内核**：安放与读取位置带线、按线折叠、增量引擎在切口取父线快照；与现有的章序调整、还原的依赖、核对点、嫌疑区间、计划兑现怎么相处；多层分叉。
3. **条目引用**：哪些键算引用（知情行的元素 id、“谁告诉的”、讲述上的标记、伏笔的答案、目标的基于与冲突、决策挂的对象）；临时 id 的替换；删除与改名；还原的依赖。原型实测的两个缺口是否都被方案覆盖。
4. **时间说法与 `nb-time`**：时间不决定折叠、安放不进网络，这两条在平行视角、同章补叙、前史序号上的后果；矛盾时网络怎么降级（一处说法写错不能让整张网失效）；改历法的诊断。
5. **决策**：未决问题扩成决策以后的状态机、“已定必须有作者原话”怎么校验、守卫的语义（在范围内每章末尾检查）与按计划模式。
6. **检查的口径**：新增的待处理种类很多（可能穿帮、泄底、传话链、前提变了、违反决定、写死未定、到期没定、没埋就回收……），会不会把待处理撑爆；哪些应该降成提示。
7. **与 ADR 0037、内核 Spec 的关系**：哪些已实现的合同要改、怎么改；两份新 ADR 的范围是否合适。

## 流程

1. 开发者批准本方案后，提交提案，状态改成 `reviewing`，让审查者读同一个版本。
2. 主会话准备材料，约 2 小时（含用原型生成简报）。
3. 同时开六路：A、F1、F2 各用一个 detached 的只读审查 worktree 与独立的会话目录（放 `.local/agent/works/w00039-novel-writing-plugins/tasks/t32-plot-side/reports/`）；C、E1、E2 是 Claude 子代理，只读主工作区。每份说明写明：不开子审查，每核实一条就追加写进报告，报告只追加。
4. 等待期间每 50 分钟看一次 omp 的进度。审查进行时不跑性能测量。
5. 报告到齐后逐条核实、归类（说明没写清、成立要改、成立但接受取舍、不成立）；修订提案；向开发者汇报。
6. 同一份提案最多审三轮。

与审查并行：开发者同意先做的 nb-story 转换器与覆盖率报告（提案待定项第 6 条）由主会话在等待期间做，不碰审查对象。
