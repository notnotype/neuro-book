# t41 内核与后端计划审查

## 发现（按影响排序）

### 高：新加实例字段未接入同批地址追踪，后续写入不会得到计划承诺的错误码

**静态核实。** §一第 73 行用 `$declared.<namespace>[+序号]` 表示 `fieldAdd` 的地址，但现有批处理入口只把新设定组与列表元素记进 `Draft.fresh`；地址重叠比较又只按字符串路径前缀。若在已有实例字段组上先 `fieldAdd`，再以 `set` 写该字段，后项的 `currentAt` 仍查原世界登记，查不到新声明；既不命中 `created-in-batch` 检查，也不与 `$declared...` 地址重叠，实际会落到 `field-unavailable`。这违反计划列明的批内合同，也使“初值只能在声明它的操作中给”不再统一。

实现前应给批内新增字段建立可按实际字段 id 查询的登记，并在路由/冲突检查前识别其创建操作；或明确拒绝此类地址并统一合同与 Agent 工具文案。新操作尚未实现，本条基于计划和现有路由静态判断，未运行动态探针。
### 高：沿用人物 v1 同时改字段集会静默隐藏旧项目数据并使旧地址失效

**静态核实。** 计划 §三保留 `nbook.canon.person` 版本 1，却从固定字段中移走 `外观`、`状态`、`态度` 等字段，并把 `外观` 移到新命名空间 `look`。Spec `canon/components.md` 规定字段 id 稳定，字段种类改变或拆分需升级；版本不同时，旧命名空间只读且仍显示原值。当前 `World.replay` 不重验旧日志，但读取只公开当前声明字段，因此旧 `character` 值仍在日志中，不等于作者界面或 MDX 还能读取；旧补丁地址也会因未声明而不适用。计划写明“值留在数据里、界面读不到”，却未将此明确列为旧作品兼容性取舍；补丁豁免只解决被改动变更的拒收，不恢复旧值、渲染或字段可写性。

实施前需明确旧项目是否接受这组静默不可读数据。若要求可读，需保留旧字段/稳定地址或设计显式迁移；若接受丢失可见性，应把影响和仍有效的旧补丁边界写入验收，不能以“版本仍为 1”表述兼容。
### 3. 高：旧补丁豁免规则未限定匹配与校验边界

严重程度：高。位置：计划 `plan.md:78-79`；现有校验 `packages/nb-canon/src/world/world.ts:1406-1444`、`packages/nb-canon/src/world/world.ts:1483-1503`。

现象：计划要求“原样留着”的不适用补丁免于拒收，但没有定义补丁数组重排时如何认定原样、相同补丁重复时如何逐一匹配，也没写明豁免只针对 `disabled`、`removed`、`undeclared` 的不适用拒收。现有校验另行检查数值依据，引用也有独立校验；整条变更仍可能因其他补丁失败而未套用。

为什么是问题：补丁没有稳定元素 id，补丁数组在修订中整体保存；按下标或“存在一个相同项”比较会误拒重排补丁，或让新增的重复补丁借旧项逃过校验。若豁免包住整段验证，还会漏掉依据、引用或整条套用失败。

建议：明确按完整补丁内容做一对一消费式匹配，不因重排误杀；只跳过命中的旧补丁对应的不适用错误，保留依据、引用、目标、版本和整条套用校验，并分别覆盖重复、重排、改动及重新安放场景。静态依据如上；本轮未运行探针。
### 4. 高：样本字段归属与“外观”迁移不完整

严重程度：高。位置：计划 `plan.md:95-100`；样本 `packages/nb-canon/src/sample/xingxia-prototype.json:301-323`、`:1816-1827`、`:2365-2377`；转换 `packages/neuro-book/scripts/canon-sample.ts:39-48`、`:63-79`。

现象：计划把“身体”“现在的样子”“现在的态度”都写为星瑕的实例字段；但样本中星瑾的 `character.态度` 初值及 `initBasis` 在 301-323，剧情补丁也明确以 `xingjin` 为目标（1816-1827、2365-2377）。计划所说的“原型里对它们的补丁地址不变”与把固定字段迁为实例字段的方案不相容：实例字段还须在对应条目的初值声明。另，现有生成转换只重编号章节和替换 `source` 字符串，`reshape` 只改命名空间/类型与字段声明，不迁 `initBasis`、`retold` 键或补丁地址；原型的外观地址出现在初值依据、重述、补丁 `at.path`、`held.against.path`，以及 `{ref(...).identity.外观}` 表达式中。

为什么是问题：生成样本会留下未声明旧地址，语义值和依据不能随新字段读取；地址键与正文引用未迁时，外观重述/补丁会失效或指向旧字段。现有样本转换不是通用字段地址迁移器。

建议：按每个原型条目的实际字段所有者生成声明，星瑾也须声明 `态度`；定义按字段语义迁移的映射，覆盖 `fields`、`initBasis`、`initTold`/`retold`、补丁及冲突地址和主文字引用，并用生成后重开、渲染与剧情结果验收。上述样本位置已静态核实；完整迁移载体清单未核实，生成样本未运行。
### 5. 中：展示元数据进入结构摘要会触发整本重算与子线缓存淘汰

严重程度：中。位置：计划 `plan.md:87-91`；`packages/nb-canon/src/components/registry.ts:109-115`、`packages/nb-canon/src/world/world.ts:239-243`、`packages/nb-canon/src/lines/set.ts:77-89`。

现象：计划要求将 `suggestions`、`kinds`、`presets` 加进 `digest`，并把新增元数据随登记类型透传。现有 `digest` 被 `World.withOptions`、引擎和 `LineSet.advance` 当作结构性输入；变化会整本重算并丢弃已建子线视图。与此同时，`WorldService.setRegistries` 会比较完整类型并发送 `inputChanged`，浏览器据此重读；但 Agent 写入读取戳的登记摘要只包含 `[id, version]`，同版元数据改变不会令旧 Agent 读戳失效。

为什么是问题：纯提示/展示属性变化造成与数据结构变化同级的计算成本；同版元数据更新后，Agent 仍可能拿旧建议值或默认组决定写入，而戳不变。

建议：先区分影响字段值/补丁解释的结构摘要与展示/写入辅助元数据；避免展示属性改变淘汰子线缓存。明确 Agent 写入是否必须对这些元数据保持新鲜，若是则将相关摘要纳入读取戳或给该类输入独立代次，并测试同版更新后的重读与 stale-read。刷新路径静态核实；具体性能影响及 Agent 是否可观察到竞态未动态验证。
### 6. 中：默认设定组与适用类型只定义了数据形状，未定义三端合并合同

严重程度：中。位置：计划 `plan.md:103-118`；当前新建界面 `packages/neuro-book/src/plugins/canon/web/entries-view.ts:143-153,185-201`，Agent 翻译 `packages/neuro-book/src/plugins/canon/backend/agent-tools.ts:355-391`。

现象：计划要求种类登记供新建对话框、条目页和 Agent 共用，但没有说清未登记种类、重复 kind、缺失/重复/不可用 component id 的统一诊断与回退；新建界面须把默认组与作者改选结合，Agent 又区分省略 `components` 和显式空数组。现有 Agent `create` 把省略与非数组值都当空列表，且只依据 `fields` 隐式添组；现有 Web `newEntryOp` 总是发送 `components` 数组。运行时可用 `ActivationContext.declarations` 查询接受的声明，无需为读取再加 contribution receiver，但计划未指定各宿主的来源、冲突处理和刷新事件。

为什么是问题：实现容易让 Web 默认人物两组、Agent 默认组及显式 `[]` 的语义分叉；默认所指类型撤回或冲突时也可能出现客户端与内核不一致。

建议：写出共享归并函数/合同：默认仅在字段省略时套用，显式 `[]` 表示作者/Agent 明确不启用；重复 kind 全部无效并诊断；逐项验证默认 component 已登记且无重复，作者选项覆盖规则一致。分别验收 Web 默认与取消、Agent 省略/空数组/显式列表/fields 隐式组，以及贡献撤回和冲突。静态核实当前 Agent 的归并行为；新方案实现结果未验证。
### 7. 中：条目种类适用性与默认组排序描述互相冲突

严重程度：中。位置：计划 `plan.md:18-20,118`；类型读取 `packages/nb-canon/src/service/service.ts:994-997`。

现象：计划开头说“添加一组设定”只列适用于该种类的组件，后文又规定适用的排在前，其余收在“全部”里。开发者已决定支持后者，但计划前段仍与决定及后段矛盾。当前 `components()` 只返回登记类型列表，现有组件类型没有 `kinds` 筛选合同；Agent 的类型解析也按所有登记类型列出。

为什么是问题：实现与验收可分别按“隐藏不适用项”或“分组展示全部项”开发，导致功能和测试互斥；种类贡献还需定义撤回/冲突时的可用项。

建议：统一全文为“适用组优先、其余归入全部”，并明确 `kinds` 为空/缺省视为通用、重复或无效声明如何处理；将 Web 条目页、添加组对话框和 Agent 可见类型的差异边界写进验收。冲突文本与当前读取行为静态核实。
### 8. 中：预设字段的 id 与建议值合同缺少改名、重声明边界

严重程度：中。位置：计划 `plan.md:87-91,149`；`packages/nb-canon/src/components/registry.ts:125-155`、`packages/nb-canon/src/world/world.ts:1329-1337`。

现象：计划要求 presets 的 id 固定、与固定字段及其他预设不重复，并按 `fieldsProblem` 校验；但 `fieldsProblem` 只校验字段形状、id、max/options 等，不会核验 `suggestions` 是否只用于 text，也不会定义预设与用户已添加的实例字段同 id、预设后续撤回或改声明时如何处理。重声明现有 id 时，内核还会以旧值符合新 kind 为条件，否则拒收。

为什么是问题：预设目录更新可能让既有实例字段从可选项消失，或与固定/自定义字段撞名；Agent 与“添加一项资料”将无法一致地决定可否重加及是否保留旧值。

建议：明确预设是创建时模板而非持续约束；给出 preset id 与既有实例声明、已删除 id、改名/撤回的优先级与诊断，并验证 suggestions 仅用于 text、子字段同样校验。以上属于计划合同遗漏；实施后的具体行为未核实。
### 9. 低：把语义档“现在的态度”声明到星瑕会改变剧情事实归属

严重程度：低。位置：计划 `plan.md:100`；样本 `packages/nb-canon/src/sample/xingxia-prototype.json:301-323,1816-1827,2365-2377`。

现象：样本里星瑾初值为“生哥哥的气”，有对应依据；两条 `note` 补丁都写到条目 `xingjin`。计划把该字段说成“星瑕这个条目上自己加的三项”，但又说原补丁地址不变。

为什么是问题：若仅给星瑕声明，星瑾的已有语义值与两条剧情记录将落在未声明地址，既不显示也不参与语义归纳；若要保留地址，就必须由星瑾声明该实例字段，或明确迁移目标条目和旧修订策略。

建议：将条目归属按样本实际写明：星瑕声明“身体”“样子”，星瑾声明“态度”；保留初值依据和两条补丁目标，并在样本生成验收中分别读取两名角色。静态核实；样本未运行。
### 10. 低：计划未覆盖重声明字段后引用和还原的专项边界

严重程度：低。位置：计划 `plan.md:70-81,199-206`；现有引用遍历 `packages/nb-canon/src/world/references.ts:67-76,103-110`，字段校验 `packages/nb-canon/src/world/world.ts:1329-1350`。

现象：计划覆盖字段增删改名、还原和补丁豁免，但没有明确删除被 `max` 引用字段、重新声明成不同 kind、字段内 ref/list 引用、字段声明变动对修订依赖的验收。现有引用索引按当前有效字段声明遍历初值与补丁；字段声明重放则作为条目初值的日志叶子。

为什么是问题：删除声明会让当前有效字段表不再遍历其值里的引用；重新声明同一 id 后引用位置可能重新出现。还原/依赖与引用快照如何相互作用，单测仅覆盖重声明值符合性不足以证明。

建议：补充通过真实 `editEntries` 发布与还原的场景：删除/重声明 ref 字段、其目标删除及还原依赖、列表引用键、被 max 引用的字段，以及字段增删后的 `refs` 和引用校验。当前遍历规则静态核实；这些交互未运行，本结论的具体故障为未核实。
