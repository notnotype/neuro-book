# w00039 t41 计划审查（内核与后端，Opus）

### 1. 重新加同名的一项会复用删过的 id：种类不同时世界层照收，旧剧情变更整条套不上（连同别的条目的补丁）
- 严重程度：重要；类别：正确性
- 位置：plan.md 设计一 `fieldAdd` 规则（“重新声明删过的 id 时留着的值恢复……种类不合由世界层报 field-redeclare-mismatch”）；world/world.ts:1329-1333（只拿初值核新声明）；model/apply.ts:115（一个补丁 type-mismatch 就 `fail` 整条变更）。
- 现象：`fieldAdd` 按 label 生成 id 时不把删过的 id 算占用，作者去掉“种族”后再加“种族”就拿回同一个 id。世界层的 `field-redeclare-mismatch` 只比**初值**里留着的值；初值是未知（null）时任何种类都合，照收。旧剧情变更里对它的补丁按新声明套，种类不合就是 `type-mismatch`，`applyChange` 让**整条变更**套不上，同一条里别的字段、别的条目的补丁一起失效。
- 核实：`lab/opus/p1-redeclare.ts`（真实 `World.publish`）：面板实例字段“种族”（number，初值 null），第 45 章一条变更 `set 种族=5` 加 `set character.外观=黑色`；去掉声明、再声明成 text：发布成功，修订的 impact 是 `broken: ["c1"]`，第 50 章末尾的外观从“黑色”退回“银白”，`outcome` 为 `{applied:false, reason:"type-mismatch", failedPatch:0}`。之后改这条变更走 `detail.applied` 为假的分支，放宽也救不了它。
- 另一面（种类相同时）：带了 `value` 只改初值，很久以前的剧情变更里的旧补丁照样盖在后面章节上，作者在新加的空字段里看到多年前的旧值（例如第 30 章读到“精灵”），这是“恢复”语义而不是“新加一项”。
- 建议：内核已经有同类先例：`usedElementIds`（entry-edits.ts:310-326）给列表元素生成 id 时避开“初值与全部变更里用过的”。`fieldAdd` 生成 id 时同样把“`fields` 里有键或任何补丁指过”的 id 算作占用，新加的一律得到新 id；“恢复去掉的一项”若要保留，另做显式入口（指定 id、种类必须与留着的补丁和值都合，否则 `field-redeclare-mismatch`），预览里列出会回来的补丁所在的变更。至少要在 `fieldAdd` 里把“旧补丁按新声明套不上”算作 `field-redeclare-mismatch`，不能只看初值。

### 2. “补丁与写入前的逐字相同就不报”会放过本次写入造成的不适用：挪安放、待定转生效、重复的新补丁
- 严重程度：重要；类别：不变量
- 位置：plan.md 设计一“世界层补两处”第 2 处；world/world.ts:1368-1445（`changed.changes` 的校验，1438-1443 是要放宽的那段）；revisions.md 输出 3 第 5 小条与输出 17；canon/web/change-edit.ts:101-104（待定转生效是同一对象只改 `status`）。
- 现象：判据只看“这处补丁本身没变”，不看“它在写入前是不是已经不适用”。下面几种写入里补丁逐字没变，不适用却是这次写入造成的，放宽后都会被放过：
  1. **挪安放**：把一条变更从第 5 章挪到第 2 章（设定组第 3 章才启用），补丁原样，现在报 `component-disabled`，放宽后照收，补丁静默跳过。换世界线（`at` 落到另一条线、那条线上没启用）同理。
  2. **待定转生效**：`held` 的变更不进 1418 行之后的检查；作者点“生效”时 `change-edit.ts` 只改 `status`，补丁原样。revisions.md 输出 17 要求“按新写的生效变更完整校验”，放宽后对已去掉的设定组、已删字段的补丁照收，违反输出 17。
  3. **计划原地改成已写**：计划不查套不上（1418 行），世界层也不禁止同一对象把 `kind` 从 plan 改成 written；补丁原样即放过。
  4. **重复**：若照 `statementProblems`（world.ts:1516）的先例按集合判“旧的里面有没有”，新加一份与旧补丁逐字相同的不适用补丁也会放过；它此刻不起作用，但字段再声明或设定组加回时会多算一次（例如两笔 `add -300`）。
- 另外：第一次写入（没有旧对象）、还原后重建（被还原掉的新建，旧对象是 undefined）都会全按新写的查，这是对的；但“撤销后再恢复”（undone 转 active）在下面的判据里也算新写，需要明确取舍。
- 建议的判据（四条都满足才不报）：旧对象存在且是 `written`、`active`（与 1418 行的门槛一致）；`at` 与所在的世界线没变；按 `stableStringify` 计数比较，这处补丁在新列表里出现的次数不超过旧列表（多出来的那几份照新写的查）；原因属于 `undeclared`、`removed`、`disabled`。同一请求里删字段又改这条变更时照收（删字段本身就不查旧变更，二者一致）。测试要逐条覆盖上面 1、2、4，并对“不比 `at`”“不比旧状态”各做一次变异。

### 3. 放宽只改“不适用”那一段，旧补丁的依据检查照样挡住整条变更：面板数值字段去掉后仍改不了文字
- 严重程度：重要；类别：正确性
- 位置：plan.md 设计一第 2 处（目标是“删字段……以后，旧的剧情变更还能改别的地方”）；world/world.ts:1406-1409（每次对全部数值补丁跑 `checkBasis`，不分新旧）、1496-1502（`derived` 按 `valueBefore` 复算）。
- 现象：`checkBasis` 在不适用判断之前、对每个数值补丁都跑。字段去掉后，前面对它的补丁都被跳过，`valueBefore` 读到的是没被套过的初值，“由核对点推出”的差额复算不上，报 `basis-mismatch`。只放宽 1438-1443 行，这条变更照样改不了。`quote` 依据同理：正文改过以后原句不在了，旧补丁报 `quote-not-found`（这是今天就有的同类限制，与 `tellingProblems`“原样留着的不查”的做法不一致）。
- 核实：`lab/opus/p2-derived-basis.ts`（真实 `World.publish`）：面板实例字段“金币”初值 100，第 44 章 `add -10`，第 45 章 `add -20`、依据是值为 70 的核对点；只改第 45 章那条的文字：声明在时通过；去掉“金币”后同样的改动得到两条问题 `basis-mismatch` 与 `unknown-field`，都在 `patches[0]`。
- 为什么是问题：本期正是让面板这类实例字段可以“去掉一项”，面板的数正是 Agent 记账、带依据最多的地方；验收映射里“原样留着的补丁不拒收”只列了“字段没声明、设定组去掉各一例”，用文字字段写就测不出这条。
- 建议：同一个“原样留着”判据（见第 2 条）也用于 `checkBasis`：逐字相同、安放没变的旧补丁不再查依据（与讲述、时间说法“只查新写或改过的”一致）；或者至少对不适用的补丁跳过依据检查。验收用例加一条带 `derived` 依据的面板数值字段。
