### 1. 保存成功分支会清掉保存在途时新开的另一份草稿（applyFailure 修了，成功分支同样的缺陷没修）
严重程度：重要　类别：正确性 / 时序
位置：packages/neuro-book/src/plugins/canon/web/in-place-edit.ts 的 submit（约 255 到 270 行，`if (result.ok) { options.setDraft(null); resetFeedback(); options.saved(...); options.refocus(draft.path); }`）
现象：保存 A 的请求在途时，浮层里点别的值 B：FieldEditor 的 dismiss 因 saving 为真不放弃（点外面被拦），但这一下点击本身是 B 按钮的 click，会走 context.edit(B) -> edit.open(B)，直接换掉 state.edit（open 不看 saving）。A 的结果回来：ok 分支无条件 `setDraft(null)`、`resetFeedback()`、`refocus(A)`，B 刚开的草稿（可能已经敲了字）被清掉，B 的浮层在作者没动手时消失；`saving` 在 B 的编辑条上也显示了一段“保存中”。失败分支这次加了“草稿已不是同一份就不写回”，成功分支没有对称处理。
为什么是问题：计划与 Spec 输出 51 写的“保存失败回来时这次填写已经放弃或换了就不写回”是同一类时序，作者只补了一半；窗口是一次保存的往返，但作者明确让“保存在途时点外面不放弃”，等于主动允许了这条路径。
如何核实：从代码推断。可在 entry-page.dom.test 里给 write 加延迟：A 保存在途时 `context.edit("B", {inline:true})`，A 结果回来后断言 state.edit 仍是 B。
建议改法：成功分支同样先比 `options.draft()` 的 requestId 与 path，只在还是同一份时清草稿与反馈；`open` 在 `saving` 为真时要么拒绝要么让 B 不继承 saving。

### 2. 上传中“按 Escape 取消上传”在真实页面上多半按不到：点上传后焦点丢到 body，Escape 到不了 ImageInput 的处理器
严重程度：重要　类别：正确性（对 Spec 输出 53 的可达性）
位置：components/ImageInput.vue 模板（`<Button v-if="picking.uploading" ... data-image-cancel>` / `<Button v-else ... data-image-upload>`）与 `onKeydown`
现象：Escape 的处理挂在 `[data-image-input]` 外框的 keydown 上，只有焦点在外框里才触发。选完文件框的文件后焦点在“上传”按钮上，`upload()` 把 `uploading` 置真，v-if / v-else 两个分支是两个不同的 Button，旧按钮被卸掉，焦点掉到 body。此后 Escape 的 keydown 目标是 body：外框收不到；浮层变体里 reka 的 window 级 Escape 监听会触发 dismiss，但 FieldEditor.dismiss 因 `imagePicking.uploading` 直接 return，所以既不取消上传也不关浮层；页顶确认条变体里 Escape 什么都不发生。只有作者再 Tab 到“取消上传”按钮才行。
为什么是问题：Spec 输出 53“可以按 Escape 取消”与输出 51“上传在途时 Escape 不算放弃”两句配合的前提是 Escape 真能取消上传；dom 测试直接在 `[data-image-input]` 上 trigger keydown，绕开了焦点已丢的现实，e2e 没有上传中 Escape 的用例。
如何核实：从代码推断。e2e：setInputFiles 之后（上传在途要用慢路由或拦截）`page.keyboard.press("Escape")` 看上传是否取消；或 dom 里点上传后读 document.activeElement。
建议改法：上传开始后把焦点交给“取消上传”按钮（或让两个状态共用同一个按钮、只换文字），或把 Escape 监听放到 ImageInput 的宿主层（imagePicking 所在处）按 `uploading` 处理；补一条 e2e。

### 3. 段落类的值与立绘、衣柜没有“第 N 章改过”的来历入口：Spec 要求它是按钮，实现里只有短资料与现在穿的是按钮

### 4. 图片候选与上传的原因在整个条目页生命周期里只读一次、从不刷新，失败原因会带到下一个字段
严重程度：重要　类别：正确性 / 状态
位置：components/ImageInput.vue `onMounted`（`if (picking.value !== null && picking.value.candidates === null) picking.value.browse();`）；images.ts `createImagePicking`（整页一份、`reason` 共用）
现象：候选只在 `candidates === null` 时列一次；之后每次打开别的图片字段（立绘、衣柜里某套的图、元素对话框）都用同一份缓存。作者在章节里贴了图、别处新增了图片、或上一次上传结果不明（“图可能已经写进作品，看一下图片文件夹”）后，候选里都看不到，除非关掉整个条目页再开。`reason` 也是整页共用的：上一个字段上传被拒（“只收 PNG…”）后换去改另一个图片字段，一打开就显示那条红字，因为 `candidates` 已经非空不会再 browse（browse 成功才清 reason）。
为什么是问题：Spec 输出 53 写的是“图片文件夹里最近的 12 张”，不是“本页第一次打开时的 12 张”；“上传结果不明”那句话指示作者去看候选，而候选不会更新。
如何核实：从代码推断。dom：注入 recent 两次返回不同结果，卸载再挂 ImageInput 断言第二次的候选；或上传失败后换挂一个 ImageInput 看 `[data-image-problem]`。
建议改法：每次一处选图片的编辑开始时（FieldEditor 变 active、元素对话框开、确认条挂上）重列并清掉 reason；上传结果不明或取消后也重列一次。

### 14. 浮层里有报错时原因被压成一行省略号，英文界面更明显

如何核实：真实页面里设英文并制造一次保存失败（例如 world-locked）。
建议改法：原因这一行允许折两行，把“写回哪里”让位（有原因时不显示 route）；或把预览区高度定为三行。

### 15. “改起点”在没有 FieldEditor 的现在的状态上退回页面顶上的确认条，Spec 说的就地改与它不符，且没有测试
严重程度：建议　类别：Spec 符合性 / 测试
位置：components/FieldDetail.vue（`@click="context.edit(props.path, {inline: true})"`）、CharacterCard.vue（condition 这一行没有 `editor` 插槽）、EntryPageHost.vue `inlineHere`
现象：现在的状态展开细节后点“改起点”，草稿标了 inline，但 CharacterView 没有为 `现在的状态` 挂 FieldEditor（`editor` 插槽只在短资料行里，`passage-editor` 只给三段文字），`inlineEditors` 里没有这条路径，于是 `editHere` 为真，出的是页面顶上吸顶的确认条，而细节面板在下面浮着。entry-page.dom.test 的“展开语义档”只测记一句，没有一条覆盖“改起点”，e2e 也没有。
为什么是问题：计划“六、两个界面”写“语义档的项点了展开细节：起点…与改起点”，评审板确认的是“就地展开”，这一条的体验是细节在中间、编辑条在页顶、两处视线分离；而“退回确认条”本是给加载失败等情况的退路，这里变成了常规路径。
如何核实：真实页面点“现在的状态”→“改起点”；或 dom 里断言 `[data-confirm-bar]` 存在。
建议改法：在细节面板里挂 `FieldEditor`（layout=block 或放进细节里）；或在 Spec 里写明改起点用页顶确认条并补测试。

### 16. 衣柜卡的菜单写“改名”却打开整套的编辑；改名对话框回车可以绕过按钮的停用条件
严重程度：建议　类别：文案 / 代码质量
位置：components/LookCard.vue（`items: [{id:'edit', label: text('card.rename')}, ...]`，选中发 `outfit-edit`）；components/CharacterView.vue 改名对话框 `<form @submit.prevent="confirm(() => context.fieldRename?.(renaming!.id, newName.trim()), ...)">`
现象：(a) 衣柜里一套的“更多”菜单第一项文案是“改名”（复用 `card.rename`），触发的是元素对话框（名字、样子、图片都能改）；aria-label `look.outfitMore` 写的是“改、去掉”。菜单项与行为不一致。(b) 人物的改名对话框里：确认按钮在名字为空或没变时停用，但输入框回车触发的 form submit 不看这个条件，空名字或原名会直接发 `fieldRename`，靠服务拒收再把原因显示出来。
为什么是问题：(a) 文案误导；(b) 停用条件与提交入口不一致，两处各写一份判据，改一处会漏另一处。
如何核实：读代码；dom 里在改名输入框里清空后触发 submit。
建议改法：(a) 菜单用“改”的文案（新键）；(b) 把 `canRename` 抽成一个 computed，form submit 与按钮共用。

### 17. 候选缩略图加载的是原图，没有缩略
严重程度：建议　类别：性能
位置：components/ImageInput.vue 候选方格里的 `<CanonImage :path="candidate.path" />`；images.ts `url`（`files.rawUrl`）
现象：12 个 64 像素高的方格各自拉原文件（上限 32 MiB，立绘常是几 MiB 的 PNG）。`loading="lazy"` 只管看不见的，浮层一打开 12 张全在视口内，同时解码；网络慢时方格一片空白。
为什么是问题：Spec 输出 53 写的是“缩略图”；计划里没有写缩略服务，可以接受作为本期限制，但没有记进“不做与风险”。
如何核实：e2e 里 route 记下 rawUrl 的请求数与大小。
建议改法：记进“不做”并在 README 里写明；或经文件服务取缩略（若有）。

### 18. 作者自己取消上传，结果以红色报错写出来
严重程度：建议　类别：界面 / 文案
位置：images.ts `upload`（`code === "cancelled"` 归入 `kind: "unknown"`，文案 `images.cancelled`）；ImageInput.vue 的 `<p role="alert" class="...--status-danger">`
现象：作者点“取消上传”或 Escape，随后下面出现红色 `role="alert"` 的“上传取消了，图可能已经写进作品”。这是作者自己的动作而不是失败；读屏会以 alert 打断。
为什么是问题：把用户操作的正常结果当失败报；“图可能已经写进作品”倒是需要告知的，但应该是中性提示。
如何核实：读代码；真实页面上传中点取消。
建议改法：取消时用中性色、`role="status"`，或只在服务确实可能已写入时（unknown-outcome）才写那一句。

### 19. 浮层关闭时内容已经被插槽清空，退场动画播的是一块空的浮层（未验证）
严重程度：建议　类别：界面 / 过渡
位置：EntryPageHost.vue FieldEditor 的 popover 分支（`{default: () => (active.value ? content() : null)}`，`open: active.value && inner.anchor !== null`）
现象：`active` 变假时 `open` 同时变假，reka 的 Presence 会让 PopoverContent 留着播退场，但默认插槽此刻已经返回 null，退场动画里只剩一个 `p-3` 的空表面（约 24 像素高），不是“同一块内容淡出”。block 版式用的是 `Transition` 包着整个 div，没有这个问题。
为什么是问题：保存或取消时浮层会先塌成一小块再消失，像闪一下；“过渡”一条要的是内容连着一起离场。
如何核实：未验证。真实页面（不减弱动效）点保存，用录屏或在 Presence 动画期间读 DOM 看浮层里还有没有 `[data-field-editor]`；e2e 的 `toHaveCount(0)` 只看终态。
建议改法：退场期间保持最后一次的内容（保存最近一次 `content()` 的 vnode，或不按 `active` 置空而是让 `open` 单独控制）。

## 未发现问题的方面（读过并认为成立的）
- in-place-edit.ts `applyFailure`：失败分支“草稿已放弃或换了就不写回”的比较（requestId 加 path）本身成立；value-conflict 与 recheck 的两条写回都用 current 而不是发请求时的 draft，是对的。
- 按路径计数的 `holdInline`：卸一份不影响另一份，换分页时新的先挂旧的后卸成立（dom 里有用例，`inlineEditors` 每次换新 Map，响应式没问题）；`watch(inner.path)` 里先 release 再 hold 在同一个同步段内。
- Popover 与 ConfirmBar 的 Escape 同时触发：ConfirmBar 的处理器对 Escape 总是 `preventDefault`，reka 的 window 级监听看到 defaultPrevented 就不再 dismiss；SuggestInput 开着列表时 `stopPropagation` 挡在 window 监听之前；AnchoredPopover 对自己的 Escape 做了 `.prevent`，嵌套层按“最高层”处理。两者不会重复放弃（即使重复，第二次 `edit.cancel()` 草稿已是 null 无副作用）。
- 浮层里点嵌套的 reka 层（SuggestionMenu、EntryPicker 的下拉）：reka 的 `isLayerExist` 按 DOM 顺序把后挂的层当里面，不会被当成点外面（e2e 的“点建议值‘女’”实际过了）。
- 人物条目的分页顺序与 `leadingTypes`、`firstTab`：空主文字时先看第一个数据分页成立；有稿时的 `watch(draft !== null)` 只在 `state.tab === null` 时写 "text"，作者已点过分页时不覆盖。
- NewEntryDialog / entries-view：`chooseKind` 在每次失焦时重套默认，只在种类没变且作者没动勾选时是幂等的；`typesTouched` 在勾选组件的 `update:modelValue` 上置位；登记类型晚到的 watch 以“勾选还等于旧默认”为条件，不会冲掉作者的选择，空种类失焦也不改勾选。
- `ConfirmBar` 原有的页顶版式（`variant="bar"`）、通用字段表与面板：本次对它们的改动只有 `FieldsDataView` 抽出 `useFieldDetail` 与 `semanticNotes` 删除，没有看到行为破坏（已跑：CharacterCard、ImageInput、ConfirmBar 三份 dom 测试 11 条通过；entry-page 与 e2e 没跑）。
- CanonImage：路径换了重置 loaded/failed；`:key=url` 保证地址换了重新加载。
- 没有按错误文案做程序分支；本次范围里的 catch 没有静默吞错（第 6 条是返回值被丢弃，不是 catch）。
- 没有逐条核对 docs/standards/code/components.md 的标签规则与各 `.md` 的细节，只确认了新组件都带同名 `.md` 且 ConfirmBar.md 与实现的 inline 描述一致。
