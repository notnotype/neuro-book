## Context

开发者 2026-11-23：“第一个设定组——人物，能放图片，并且提供一份生动的表单给作者填数据”；11-24 定了[内置设定组的清单](../t10-setting-schema/component-catalog.md)（第 3 稿）与评审板第 1 轮的四条答复（见 [README](README.md)）。本计划做清单的第一期：

- 人物重整成十个通用字段，形象（立绘、外貌、服装、现在穿的）单独成组；
- 人物分页是角色卡，立绘读自同一条目上的形象组；形象分页是大图、外貌、衣柜、现在穿的；
- 作者能在某个人物上自己加一项资料（预设里点，或自己写名字），能改名、去掉；
- 改一项时就地展开，不再跳到页面顶上的确认条；
- 图片能显示、能从作品里选、能上传；
- 新建人物直接带人物与形象两组；“添加一组设定”里适用于这个种类的排在前面，其余收在“全部”里。

依据：[`canon/components.md`](../../../../../docs/specs/canon/components.md)（输出 4 写了实例字段的增、改名、删，内核的写入操作里没有）、[`canon/revisions.md`](../../../../../docs/specs/canon/revisions.md) 输出 25（一次改几处）、[`canon/author-ui.md`](../../../../../docs/specs/canon/author-ui.md)（输出 4、12、13、16、38 与输入一节的两个贡献点）、[`canon/agent-tools.md`](../../../../../docs/specs/canon/agent-tools.md) 输出 6。

开发者已定的（不再讨论）：

1. 一个设定组是数据加展示，一个分页对应一个设定组；展示部分先用 Vue 组件，MDX 模板的想法记在 t38。
2. 形象单独成组，人物的展示可以引用它。
3. 改一项时就地展开；“添加”分两个入口（添加一项资料、添加一组设定）。
4. 预设选项做成可以自己填的建议值；模板不写示例内容。
5. 重整人物字段时直接改声明、重做样本，不做升级函数。
6. 界面的三处打磨要求：短项就地改不推动别的区域；有建议值的项用选择控件；引用条目的项用能搜索的条目选择。

设计审查做了两轮（2026-11-24；记录在 [README](README.md)，报告在 `evidences/`）。第 1 轮 Opus 审内核、Sonnet 审界面、omp 在后台，三路都被额度或时限打断，各写了 3、6、10 条；第 2 轮 Opus、Sonnet 各接着审修订后的计划与没审到的部分，写了 11、18 条。逐条核实（内核的发现多数带真实内核上的探针）后，改了这些设计：

- 去掉一项从“删声明、再加同名时恢复”改成“在声明上打标记、另有恢复”；
- 声明上的规则只查这次新写或改过的，原样留着的由读取这一侧容忍：还原是补偿写入、不经校验，原来的做法下还原能把一整组锁死；
- 类型的固定字段与条目上的实例字段同 id 时固定的生效；
- 原样留着的旧补丁不拒收，判据细化成四条，连依据检查与分叉的 `carry` 一起；
- 样本按字段的实际归属迁（“现在的态度”在星瑾身上），用一张地址映射表换；
- 种类的登记从“撞名两条都不用”改成同一个词的几条登记合并；
- 界面：点值就改、谁来画就地改、浮层里放弃的规则与三个例外、建议值的控件改用输入框加候选菜单、图片输入改成由宿主上传、两个界面各拆成展示层与绑定层。

写计划前跑过的探针（真实内核，脚本在本机 `/tmp/t41-probe/`，不入库）得到的事实：

- 条目初值里的 `declared` 改了以后，修订记成 `init.data.<命名空间>.declared[<字段 id>]`（新增、删除整项）、`….declared[<id>].label`（改名）与 `….declared#order`，都是现有的叶子写法。**日志格式不用改。**
- 删掉声明后值留在初值里、读不到；对它的 `set` 得到 `field-unavailable`；再声明同一个 id 时值与补丁都回来，种类不合时 `field-redeclare-mismatch`（审查另查出：只比初值，初值是未知时什么种类都收，旧补丁套不上会让整条剧情变更失效）。
- 还原“加字段”的那次修订：之后的改名算依赖，之后剧情变更里对这个字段的补丁不算；还原后那些补丁按“不适用”跳过。与删声明的效果相同。
- 删掉被另一个字段的 `max` 指着的声明，世界层报 `type-mismatch`，路径是数组下标，看不出原因。
- 类型没开 `instanceFields` 时，直接写 `declared` 的请求世界层照收（值存下、读不到）。
- **旧限制**：一条剧情变更里有对已删字段的补丁时，之后再改这条变更的任何地方（哪怕只改文字）都被拒收（`unknown-field`）。去掉一整组设定今天就是这样（`component-disabled`），加了“去掉一项”以后更容易碰到。

## 关键设计

### 一、内核：实例字段的声明（`packages/nb-canon/src/core/schema.ts`、`components/registry.ts`、`world/world.ts`、`world/entry-edits.ts`、`model/apply.ts`、`world/references.ts`、`world/forks.ts`）

两轮设计审查之后定下四条原则，下面的操作与校验都从它们来：

1. **去掉一项是打标记，不是删声明。**实例声明多一个可选的 `removed: true`：声明连同种类留在 `declared` 里，读取、渲染、补丁都当它不在；恢复就是去掉标记。和去掉一组设定的做法相同（components.md 输出 7）。去掉过的 id 一直占着，恢复时种类不可能变（原稿是删声明、再加同名时恢复：审查复现过，去掉数的“种族”再加成文字，第 45 章那条剧情变更整条套不上）。`removed` 只属于实例声明：另起 `InstanceFieldDeclarationSchema`（字段声明加 `removed`），只用在数据的 `declared` 上；固定字段、列表的子字段、预设里写了它，登记时整条不登记（`component-declaration-invalid`）。
2. **生效的声明 = 类型固定的字段，加上没去掉的实例声明；同一个 id 两边都有时固定的生效。**`effectiveFields` 一处实现（过滤与去重），读 `declared` 的地方都经它（审查逐处核过：补丁、约束、读取视图、主文字的字段引用、决策的 `about`、分叉的 `carry`、条目读取的 `declarations` 都经它或 `namespaceFields`）。类型以后加了一个与某条目上实例字段同 id 的固定字段时，那一项从此按固定字段的声明读写，值留用；审查复现过现在的行为是这一组整组写不进去。
3. **声明上的规则只查这次新写或改过的声明；原样留着的不查，读取这一侧容忍。**还原是补偿写入、不经校验（`world.ts` 的 `compensation`），所以“上限指着一个去掉的字段”“两项同名”这些组合造得出来（审查用还原各造出一例），不能让它们把整组锁死。世界层（`validate`）是这些规则唯一的出处，`planEntries` 只是提前给出同一个码：
   - 类型没开 `instanceFields` 而新写了声明：`fields-not-declarable`；
   - 新写的声明，id 不能与这一组里任何声明相同（固定的、实例的、去掉过的）：`id-taken`；
   - 新写或改了显示名的生效声明，显示名在生效的声明里唯一：`label-taken`（去掉过的不算，所以去掉“种族”以后可以再加一个新的“种族”；恢复旧的那一项撞名时同样是这个码，先改名再恢复）；
   - 新写或改过的生效声明，`max` 要指向一个生效的精确数字段；去掉一项时，还有生效的声明的 `max` 指着它：都是 `field-referenced`，路径写 `declared[<id>].max`（现在写的是拼接后的数组下标，对不上）；
   - 值：只核这次值变了或声明变了的字段（现在是这一组只要有改动就把每个字段的值重核一遍）。
   读取这一侧：约束的上限指着一个不生效的字段时，这一条上限不查（同“上限是未知时不查”）；`constraintViolation` 现在直接读 `fields[<上限的 id>]`，要改成先看它生不生效。
4. **留着的东西照旧算数，只是不显示。**去掉的字段里的值、对它的补丁、值里的引用都保留；引用照旧记在引用里（`references.ts` 对去掉的声明照常遍历），所以恢复时它们不算新写的引用，指着的条目在这期间被删了也恢复得回来（审查复现过不这样做时恢复被拒 `ref-invalid`，而去掉的字段又改不了值，是死路）。

**写入操作。**`EntryOpSchema` 加四项，照 `listAdd`、`listRemove` 的命名：

```ts
// 字段声明去掉 id 必填：不写时由内核按 label 生成（generateFieldId）
{op: "fieldAdd", entry: Id, namespace: Text, field: FieldDraft, value?: unknown}
{op: "fieldRename", at: Address /* <命名空间>.<字段 id> */, label: Text}
{op: "fieldRemove", at: Address}
{op: "fieldRestore", at: Address}
```

`component` 的 `add` 与 `create` 里的 `components[]` 各加可选的 `declare: FieldDraft[]`：这一批新加的设定组，自己的字段在加它的那一项里声明（沿用“这一批新建的东西初值写在建它的那一项里”）。

`planEntries` 里的做法（改的是条目初值的工作副本，路由是 `entry`）：

- `fieldAdd`：写了 id 就先用它，没写就按显示名生成；这个 id 已经占着（任何声明用着，或照 `usedElementIds` 的先例，初值里留着这个键、任何剧情变更的补丁指过它）时换一个生成的，不拒收（预设带写死的 id，作者先自己加过同 id 的一项时照样加得上）。数据里还没有 `declared` 时先补空数组；`value` 不写是未知。
- `fieldRename`、`fieldRemove`、`fieldRestore`：只能动实例声明的；指到类型固定的字段：`field-fixed`；没有这个声明、去掉已经去掉的、恢复没去掉的：`field-missing`。
- 同一批里：两项 `fieldAdd` 可以并存；`Draft.fresh` 另记这一批新加的字段，对它再 `set` 在取当前值之前就得到 `created-in-batch`（现在的 `fresh` 只认设定组与列表元素）；同一个字段既改名又去掉、或既 `set` 又去掉得到 `duplicate-address`（后三个操作的地址就是字段地址，`fieldAdd` 用 `$declared.<命名空间>[+序号]`）。
- 只在创作修改里有意义：`intent` 是 `story` 的一批里照样按改初值处理，同 `component`、`place`。
- 条目读取另给 `removedFields`（命名空间到去掉过的各项的 id 与显示名，没有时不写），同 `removedComponents`。

**原样留着的补丁与 `carry` 不因为“不适用”拒收。**被碰到的剧情变更里，一处补丁同时满足下面四条时不报问题，也不查它的依据：

- 写入前这条变更已经存在，并且是已写、生效的（待定转生效、计划改成已写、撤销后恢复都算新写，照旧整条校验，revisions.md 输出 17）；
- 安放与所在的世界线没变（挪到设定组还没启用的章是这次写入造成的不适用）；
- 把补丁稳定序列化后计数，这处补丁在新列表里出现的次数不超过旧列表（多出来的那几份照新写的查）；
- 不适用的原因是字段没声明、设定组去掉或没启用。

依据检查一并跳过：审查复现过，面板的数值字段去掉以后，后面那条带“由核对点推出”依据的补丁复算不上，只放宽不适用那一段的话这条变更照样改不了。分叉的 `carry` 同理：现在每次碰到这条分叉都整份重查“是声明了的字段”，带着的某个实例字段被去掉以后这条分叉就改不了了；改成只查新写或改过的 `carry` 项。这一段改的是已有的校验，是本计划里风险最高的一处。

不改：修订的形状、`core/id-lists.ts`、日志格式（`removed` 是声明上多一个可选属性，按“只加字段”处理）、还原与依赖的算法、类型版本的比较。

已知的限制（接受，写进 components.md 的“不承诺”）：

- 类型后来才开 `instanceFields` 时（人物就是），旧条目的数据里没有 `declared`。在这样的条目上第一次加一项，修订把整个 `declared` 记成一处改动，之后这一组的字段操作都算依赖它：还原第一次加的那一项要连同之后的一起还原。新建的条目与重做的样本一开始就带空的 `declared`，不受影响。不为此改修订的差分（它管着所有带 id 的列表）。
- 被固定字段盖住的实例声明，留着的值若不合固定字段的种类，读出来还是原来的值，由作者改掉；内置类型以后把某个预设提成固定字段时种类不变。

### 二、内核：声明多三个只转交的属性（`core/schema.ts`、`components/registry.ts`）

| 属性 | 在哪 | 规则 |
|---|---|---|
| `suggestions?: string[]` | 字段声明 | 只用于 `text`；内核不校验值在不在里面；列表的子字段也可以带 |
| `kinds?: string[]` | 类型声明 | 这组设定适用的条目种类（条目的 `type` 那个词）；不写是没有特别适用的种类。只是提示，内核不拒收不适用的 |
| `presets?: FieldDeclaration[]` | 类型声明 | 只在 `instanceFields` 为真时可写；“添加一项”里列出的预设字段，id 要写。逐个校验：每个预设与固定字段放在一起按 `fieldsProblem` 查（id 不与固定字段、别的预设重复；`max` 只能指固定字段，不能指另一个预设，因为作者可能只加其中一个） |

`ComponentDeclarationSchema` 是 `additionalProperties: false`，三个都要加进 schema；`ComponentDeclaration`、`ComponentType` 两个接口与 `buildRegistry` 里逐项复制的那一段也加上。`components` 读取返回的是登记的类型原样，界面与 Agent 都读得到，远程合同不用另改。

- **`digest` 只含影响计算的部分**：`kinds`、`presets` 不进；算 `digest` 时把字段声明里的 `suggestions` 去掉（子字段的也去掉）。`digest` 是“要不要整本重算、丢掉已建的子线视图”的判据，这三样都只是提示。登记变了的通知不靠它（服务比的是整份类型，`service.ts` 的 `setRegistries`），界面照样会重读。Agent 的读取戳只含类型 id 与版本，同一版本里改了这三样不会让它读到的戳失效，接受。
- `fieldsProblem` 补一条：`suggestions` 只用于 `text`（子字段同样查）。
- **预设是加的时候用的模板，不是持续的约束**：加上以后就是这个条目自己的声明，类型以后改了、撤了某个预设都不影响已经加的。点预设时把它的 id 交给 `fieldAdd` 作首选，占着就换一个生成的（设计一）。界面上，预设的 id 在这个条目上已经有生效的声明时不列；去掉过的列在“恢复”。

### 三、内置类型与样本（`packages/neuro-book/src/plugins/canon/shared/components.ts`、`scripts/canon-sample.ts`）

- **人物**（`nbook.canon.person`，命名空间 `character`，版本仍是 1，开 `instanceFields`，`kinds: ["人物"]`）。十个固定字段的 id 就是显示名：性别（建议值：男、女、不明）、年龄、身份、所属（引用，`targets: ["组织"]`）、性格（`retold`）、背景、说话方式（`retold`）、现在的状态（语义档）、现在在哪（引用，`targets: ["地点"]`）、生死（建议值：活着、已故、失踪）。除“性格”外都不沿用旧的 id（旧的是外观、状态、态度、身体、样子、性格）：沿用了的话，试验作品里旧的值与补丁会按新的意思回来（例如旧的普通文字“状态”变成语义档的起点）。`presets`：种族、生日、身高、喜好、弱点、动机、初次登场（都是文字，id 同显示名）。
- **形象**（新，`nbook.canon.look`，命名空间 `look`，版本 1，开 `instanceFields`，`kinds: ["人物"]`）。固定字段的 id 就是显示名：立绘（图片）、外貌（文字，`retold`）、服装（列表：样子、图片；元素的名字用列表自带的 `label`）、现在穿的（文字）。
- 版本不升：升了以后旧数据整组只读、又没有升级函数。这是一处明说的取舍，不是兼容：还没有发布过带世界引擎的版本，真实数据只有样本与开发时的试验作品（开发者定“直接改声明、重做样本，不做升级函数”）。不升的后果：试验作品里旧字段（外观、状态、态度、身体、样子）的值与对它们的补丁留在数据里，界面与主文字里读不到，主文字里引用它们的地方显示占位，不报错；这些作品里的人物也没有形象这一组，要作者自己加。设计一里“原样留着的补丁不拒收”那一段保证旧的剧情变更还能改别的地方。
- **面板**先不动（显示名改“数值”与它的预设项在第二期），只加 `kinds: ["人物"]`。
- 剧情插件的五个类型按各自的用法补 `kinds`（`plot/shared/declarations.ts`，实施时逐个对照它们 `targets` 的用法）。
- **星瑕样本**：按原型里每个条目实际用到的字段来迁（审查核对过原型：“现在的态度”的初值与两处补丁都在星瑾身上，“身体”“现在的样子”在星瑕身上）：
  - `character.外观` 与马甲的 `identity.外观` 写到形象组的 `look.外貌`，有这个值或补丁的条目带上形象这一组；`性格` 不变；
  - “身体”“现在的样子”在星瑕这个条目上声明成她自己的字段，“现在的态度”在星瑾身上声明（种类照原型：两个选项、一个语义档文字）；原型里对它们的补丁地址不变；
  - 要跟着换地址的不只是字段的值：初值的依据与讲述里以地址为键的几处（原型里有 9 处）、补丁与待定项里的地址、建议的目标、主文字源文里的引用（带前导点的 `.identity.外观`、`.character.外观` 与星瑕自己写的不带点的 `{character.外观}` 都换成对应的 `look.外貌`），都由生成脚本里的同一张“旧地址到新地址”的映射表换，不逐处手写、不做字符串替换；现有的转换是按命名空间整组换类型，做不到把一个命名空间拆成两组、按条目给声明，要改写这一段；
  - 两个马甲条目（原型的 `identity`）照种类“人物”的默认带人物与形象两组，外观进形象的外貌，人物这一组的各项先空着；
  - 验收：生成以后重开世界、逐章读两个人物的各项与算出来的数，和迁之前的原型逐项对上。
- 写死了旧字段名的地方跟着改：应用这一侧按字段名粗搜到 36 个文件（`canon` 与 `plot` 插件的测试与测试夹具、`canon-write`、`canon-author` 两份 e2e、样本的脚本与测试、两个性能脚本、Lab 的场景登记），其中一部分是剧情插件同名的“态度”，实施时先分清再改。内核的测试用自己的夹具与原型自带的声明，不受影响。先列全读法再逐处迁移，不批量替换。

### 四、条目的种类（新贡献点 `canon.entry-kinds`，`canon/shared/entry-kinds.ts`）

种类仍然只是条目上的一个词，内核不知道这张表。登记的是“这个词默认带哪几组设定”：

```ts
// 贡献 id 按插件 id 的前缀核对；不交实现；声明在插件清单里，各个位置都读得到
interface EntryKindDeclaration {
    kind: string;                 // 存进条目的那个词，例如 "人物"
    components?: string[];        // 新建这个种类时默认带的设定组（类型 id）
    order?: number;               // 新建对话框里的先后
}
```

- 内置登记四个：人物（人物、形象）、组织、地点、物品（后三个现在没有默认的设定组，第三期补）。
- 同一个词可以有几条登记（别的插件可以给“人物”追加默认的设定组）：默认的设定组按登记的先后并起来、去重，`order` 取最小的。不设“撞名两条都不用”的规则：默认组是可以合并的列表，不像命名空间那样放不下两份。默认里写到没登记、不可用的类型时，那一项当作没写，另写一条诊断。种类的几个词（人物、组织、地点、物品）在 `entry-kinds.ts` 里导出成常量，内置类型的 `targets` 与 `kinds` 都用它，不各写一遍。
- 默认只在“没说要哪几组”的时候用，三处用同一个函数算（`shared/entry-kinds.ts`）。Agent 的 `create`：不写 `components` 时套默认，写了（空数组也算，表示不要默认）就照写的；最后启用的是这一份再并上 `fields` 里写到的设定组（agent-tools.md 输出 7）。没登记的种类没有默认。
- 设定组的 `kinds` 不写时，它在哪个种类的条目上都收在“全部”里，不排在前面。
- 用它的三处：
  - 新建条目的对话框：种类的候选是登记的，加上已有条目用过的。点一个种类的按钮、或种类输入框失焦时，作者还没动过勾选就把勾选整组换成这个种类的默认（没登记的种类是空的）；作者动过以后不再跟着换（草稿里记 `typesTouched`，同现在的 `folderTouched`）。不在每敲一个字时套用。
  - 空状态的“新建人物”改走这张表，不再写死人物的类型 id；表里没有“人物”时这个按钮不出现，只剩“新建条目”。
  - 条目页的“添加一组设定”：还是一个下拉，适用于这个条目种类的排在前面，其余接在后面，不另加一层收起（审查指出登记的类型一共只有几个、nb-ui 的下拉也没有分组；与开发者确认过的“其余收进全部”有出入，记进待确认清单）。
  - Agent 的 `create`：见下一条。
  - 条目页的分页顺序（评审板第 2 轮答复“人物在前”）：条目种类的默认设定组的数据分页排到“文字”前面，次序同命名空间的顺序；其余数据分页、附加分页、“情节”照旧。宿主的分页表按条目的种类查这张表，种类改了分页跟着重排，选着的分页不变。

### 五、展示组件的接口（`canon/shared/component-views.ts`、`canon/web/component-views.ts`、`components/EntryPageHost.vue`）

贡献点 `canon.component-views` 的声明加 `uses?: string[]`（会用到的别的设定组的类型 id）。它只是依赖的声明，不是权限：设定的读取对作者这一侧本来就全开。加载时 `uses` 里没登记的 id 写一条诊断。

`ComponentViewContext` 现有的成员不变；新增的都是可选的，条目页给全，别的宿主（Lab、测试场地）可以不给，界面缺哪一项就退到哪一项的退路上：

```ts
/** 同一条目上另一组设定此刻的情况。只对声明里 `uses` 列了的类型有意义，没列的一律是 `absent` 并写一条诊断（不抛错）。
 *  在渲染或 computed 里读，不要存起来；`peer` 对同一组是同一个对象。 */
other?(type: string):
    | {status: "present"; peer: ComponentPeer}
    | {status: "absent"}                       // 没加过
    | {status: "removed"}                      // 去掉过，可以恢复
    | {status: "later"; from: string}          // 加了，所选位置上还没启用（from 写成“第 N 章”）
    | {status: "unavailable"};                 // 类型没登记或不可用
/** 给这个条目加上（或恢复）`uses` 里的一组设定。写不了时的原因在 `blocked` 里，界面据此停用按钮。 */
addComponent?(type: string): Promise<{ok: true} | {ok: false; reason: Text}>;
/** 切到那一组的分页；没有这个分页时什么也不做。 */
showTab?(type: string): void;
/** 就地改的编辑器，放在值的旁边、和值一起挂着；这个字段正在就地改时它画输入、意图、预览与保存取消，别的时候不画。 */
readonly FieldEditor?: Component<{path: string; layout?: "popover" | "block"; suggestions?: readonly string[]; anchor?: HTMLElement | null}>;
/** 一个值的细节：来历、语义档的起点与各句、记一句。 */
readonly FieldDetail?: Component<{path: string}>;
/** 正在就地改的字段、正在看细节的字段（本组里的路径），没有时为 null。 */
readonly editing?: string | null;
readonly detail?: string | null;
showDetail?(path: string | null): void;
/** `inline` 为真且有编辑器接手时不出页面顶上的确认条；`value`、`intent` 预先填好（换装用）。没有 `FieldEditor` 的宿主里照旧出确认条。 */
edit(path: string, options?: {inline?: boolean; value?: unknown; intent?: "creative" | "story"}): void;
/** 在这个条目的这一组上加一项、改名、去掉、恢复（类型开了 `instanceFields` 才有）。 */
fieldAdd?(field: FieldDraft): Promise<…>;  fieldRename?(path, label): Promise<…>;  fieldRemove?(path): Promise<…>;  fieldRestore?(path): Promise<…>;
/** 这一组上去掉过的各项，给“恢复”用。 */
readonly removedFields?: readonly {id: string; label: string}[];
```

`ComponentPeer` 只有读的那几项（`namespace`、`fields`、`declarations`、`origins`），没有 `edit`、没有 `FieldDetail`：改别的组的字段、看它的来历都到它自己的分页去（`showTab`）。`FieldEditor`、`FieldDetail` 像现在的 `FieldTable` 那样按命名空间各缓存一个组件定义，不在每次读取时新建。`canon/testing/` 放一个 `createViewContext(overrides)` 造假的 context，dom 测试与 Lab 的台子都用它。

就地改沿用现有的那一份编辑状态（`in-place-edit.ts` 的草稿、预览、保存、冲突处理），只是换一个地方画。规则：

- **谁来画**：`FieldEditor` 在 `setup` 里向宿主登记自己的路径、卸载前撤掉，登记表按令牌计数、是响应式的（同一路径挂两份时卸一份不影响另一份；换分页时新的先挂、旧的后卸也不出错）。草稿标了就地、并且此刻有登记了这条路径的编辑器时由它画；别的情况（专门界面还在加载、加载失败、贡献方停了退回通用字段表）一律出页面顶上的确认条。
- **浮层里的短项**：点浮层外面、按 Escape、点“取消”都是放弃这次填写，草稿不留。三个例外不算放弃：保存请求在途时；系统的选文件框开着、图片上传在途时；Escape 落在输入法组字里时。保存或放弃以后焦点回到触发它的那个值。
- **保存失败回来时草稿已经不在**（作者放弃了，或换了别的字段）：不把旧草稿写回。这是现有 `applyFailure` 的缺陷，确认条上同样成立，一并改。
- **浮层的大小按字段的种类分档、各档固定**：短文字、建议值、引用是一档，图片是一档。预览占两行的位置（更多的收成“还有 N 项”），报错与预览共用这块位置，保存与取消的位置不动。
- **成段的文字**：编辑层浮在原处、向下长，盖在后面的内容上，原来那一段的占位不变，别的内容不动；输入框从原文的行数起步。草稿照旧存在标签状态里，切走再回来还在。
- 草稿所在的字段被去掉或改名时清掉草稿。
- 本期只有人物、形象两个界面用就地的；通用字段表与面板照旧用确认条。

**有建议值的文字**用一个小组件 `SuggestInput`（设定插件里）：nb-ui 的 `Input` 下面挂 `SuggestionMenu`。值始终是输入框里的字；点一条建议是把它填进输入框，不点也行。不建在 `SearchSelect` 上：它打的字只是搜索词，不选就失焦会丢掉输入，回车会选中最像的一条（审查读实现确认）。只用于单行的短文字；确认条、元素对话框与 `FieldEditor` 三处都用它（`ConfirmBarKind` 加一种）。

**来历与记一句**：`FieldsDataView` 脚本里的那一套（按页读来历、语义档的各句、记一句的草稿与“一次只记一笔”）抽成 `useFieldDetail`，通用字段表与 `FieldDetail` 共用，不写两份。`accumulated-value` 被拒时宿主把“正在看细节的字段”设成它，`FieldEditor` 让位给 `FieldDetail`。人物改用专门界面以后，`FieldsDataView` 的 `semanticNotes` 参数没有调用方了，连同文档与测试里的对应部分删掉。

### 六、两个界面（`canon/web/components/`，各带同名 `.md` 与 Lab 场景）

每个界面拆成两层：只收属性、事件上抛的展示层 `CharacterCard.vue`、`LookCard.vue`（Lab 里挂它们：填好的、空的、没有形象、没有立绘、390 宽、英文），与绑 context 的薄层 `CharacterView.vue`、`LookView.vue`（读来历、发写入，只在 `entry-page.dom.test.ts` 与 e2e 里验证）。

- **人物分页**：左边立绘，右边性别、年龄、身份、所属、现在在哪、生死、作者自己加的各项与“添加一项资料”，下面是现在的状态，再下面性格、说话方式、背景。立绘那一格按 `other(形象)` 的五种情况画：有立绘是图（点了切到形象分页）；有形象没立绘是“添加立绘”（切到形象分页）；没加过是“添加形象”；去掉过是“恢复形象”；所选位置上还没启用时写“第 N 章起有形象”；类型不可用时这一格空着。立绘的来历入口不在人物这一页，到形象分页看。
- **形象分页**：大图、外貌、现在穿的（建议值是衣柜里各套的名字）、衣柜（一套一张卡：图、名字、样子两行截断；“换上”打开现在穿的的编辑器，锚在点的那个按钮上，填好这一套的名字，意图预选“从这一章起”）。
- **每一项上的入口**：
  - 值本身是按钮（带 `data-edit="<完整路径>"`），点了就改；写不了时（按计划、只读、独占写入、已删除）停用并在提示里写原因，同通用字段表的“改”。
  - 值在剧情里变过时旁边有“第 N 章改过”，它也是按钮，点了在浮层里看来历。只有初值的值没有这个入口。
  - 语义档的项（现在的状态）点了展开细节：起点与之后记下的各句、记一句、改起点。
  - 自己加的项行尾有常显的“更多”（低对比度）：改名、去掉。
- **添加一项资料**：浮层大小固定、里面滚动。列类型的 `presets` 里还没加的、去掉过的各项（写“恢复‘某某’”），另有自己写名字的一栏（本期只加文字的项；被拒时原因写在这一栏下面）。去掉一项时确认里写“数据会保留，可以恢复”。
- **过渡**：立绘从占位换成图、衣柜加一套或去掉一套（别的卡滑开）、值保存后换成新值、预览回来、编辑层与细节面板的出现与消失，都按设计语言的动效表给过渡。
- **宽度**：390 宽时立绘在上、资料排成一列；宽窗口里内容列封顶，立绘按比例裁切、不随窗口变大。
- 版式与文案以评审板第 2 轮的答复为准。

### 七、图片（`canon/web/images.ts`、`components/ImageInput.vue`、新的 `CanonImage.vue`）

- **存放的目录**：条目不是作品里的文件，章节插图“与文件同目录”那两种规则用不上。设定这边上传的图固定存到作品设置里的图片文件夹（缺省 `插图`，取编辑器插件设置里的那一项、经 `editor/shared/contracts` 公开的 `normalizeImageFolder` 规范化），不另定目录。
- **取图**：`CanonImage` 经注入的函数把作品内路径换成取图地址（纯计算，没有读写）；图片懒加载、异步解码；加载失败（文件不在）时画“图片找不到”的占位（components.md 输出 15）。文件在别处被换掉以后要重新打开页面才看到新图，本期不跟文件的变化（记进“不做”）。
- **`ImageInput` 是受控的零件**，自己不读写：选了文件发 `pick-file`，要看作品里的图发 `browse`；候选的图、上传中、原因由宿主经属性给。上传与列目录由宿主一层做（条目页宿主为确认条与元素对话框，`FieldEditor` 为就地改），用文件插件的服务：
  - 候选是图片文件夹里最近的 12 张；别的目录里的图手填路径（按名字搜整部作品先不做）；
  - 上传只收 PNG、JPEG、GIF、WebP，上限 32 MiB（文件服务的规则），选文件框按这四种过滤；重名时用服务返回的实际地址；
  - 失败分三类写原因：类型或大小不合；网络失败或结果不明（图可能已经写进作品）；别的；
  - 上传可以取消（Escape）；上传的文件写进作品就留在那里，放弃草稿、撤销修订都不删它。
- 三处（确认条、元素对话框、`FieldEditor` 的图片那一档浮层）共用同一个版式：固定大小的缩略图方格、说明一栏、手填路径作退路。没有文件服务的窗口里没有候选与上传，只剩手填路径与说明。

## 不做与风险

不做（本期）：

- 数值的显示名与预设项、技能、物品栏、关系（第二期）；组织、地点、物品三组与作品级“各种类默认带哪些设定组”、新建条目的模板（第三期）。
- 通用字段表与面板的就地展开；剧情插件给自己的种类登记默认设定组。
- 用显示名写字段（components.md 输出 8 的 planned 句子）、类型版本的升级函数、按引用反查（角色卡上列重要物品）。
- 图片：按名字搜整部作品里的图（别的目录里的图手填路径）；文件在别处被换掉后自动换成新图（要重新打开页面）；上传的文件随撤销删除。
- 条目页页头与内容列差 32 像素的对齐（记在 README，另行处理）。

风险：

- **世界层的校验改了两类**（设计一）：声明与值从“这一组有改动就整组重查”改成只查新写或改过的；原样留着的补丁与 `carry` 不再因不适用拒收。都是已有的写入校验。兜底：每条规则各有用例，放宽的用例先在旧代码上失败；新写的仍被拒收的用例保留并做变异检查；实现审查把它列为第一重点。
- **实例声明多一个 `removed`** 是存进日志的数据多一个可选属性。兜底：读 `declared` 的地方审查已逐处列出，都经 `effectiveFields`，另两处直接读的（约束的上限、分叉的 `carry`）在设计一里各有处理；还原“去掉”“恢复”各有用例。
- **旧条目没有 `declared`** 时第一次加一项的那次修订不好单独还原，接受为已知限制（设计一末尾）。审查建议改修订的差分来消掉它；没采纳：差分管着所有带 id 的列表，为只影响试验作品的情况去动它不值得。
- **重整人物字段牵动的文件多**（粗搜 36 个），样本的转换要改写成按地址映射。兜底：S2 单独一片，先列全读法再逐处改，改完跑两份 e2e；样本用“生成后重开、逐章读两个人物的各项与算出来的数”对照原型。
- **就地改与确认条共用一份状态**：切走再回来、世界在别处变了、保存失败这几条路径要在两种画法下都成立。兜底：`entry-page.dom.test.ts` 里现有的确认条用例照旧通过，就地的另写同样几条，用真的过渡。
- **图片端口在没有文件服务的窗口里不在**：两个界面与输入都要有退路，Lab 里各登记一个没有端口的场景。
