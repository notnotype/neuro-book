# 条目主文字的整篇编辑器

## 目标与范围

条目的主文字用一个完整的富文本编辑器整篇编辑，让作者像写一份文件一样写条目的 index、引用设定组的数据并看到值（开发者 2026-11-24：“编辑还是直接给用户一个完整的编辑器更加好”“第一版没必要分节”“我们继续先推这个编辑器”）。

范围：

- 第一版主文字不分节：每个条目的主文字只用一块，提交是整篇替换，别处也改了时按整篇问一次。
- 写法（`{字段}`、`<Ref>`、`<Image>`）与内核都不动，内核仍用它现在的解析器把关。
- 阅读与编辑是同一个界面，排版与章节一致。
- t28 的暂存、提交、多窗口留用；拆、并、加块、删块与它们的冲突处理从界面这一层拿掉。

不做：主文字的“这段在剧情里变了”；换解析器、换写法、标签登记表、沙箱块（[t38](../t38-kernel-shared-parser/README.md)，等用过之后再定）；人物设定组与加字段的入口（另建 Task）。

合同：[`canon/author-ui.md`](../../../../../docs/specs/canon/author-ui.md) 的文字分页（输出 39、44 到 47）要改，写计划时定具体条目；内核的 Spec（[`canon/rendering.md`](../../../../../docs/specs/canon/rendering.md)、[`canon/revisions.md`](../../../../../docs/specs/canon/revisions.md)）不变。来由与讨论见[调研记录](../../research/2026-11-24-entry-text-direction.md)。

## 当前状态

2026-11-24 新建。[实施计划](plan.md)第 1 稿开发者当天确认：“打开就能打字当然还要有只读模式（现有的章节编辑器也应该有阅读模式）”“其他都同意”（值的来历先到数据分页看；带章节同一套的工具栏；多块的旧条目提交时并成一块、有随剧情变的段落的条目只读；保留“源文字”切换）。第 2 稿加了阅读模式与“插入”菜单（本条目的字段、条目引用）。

2026-11-24 前端设计审查回来（Sonnet，审在 `cb582b64a`，[报告](evidences/design-review-frontend-sonnet.txt)）：17 条，阻断 1、重要 13、建议 3，没有撤回。逐条处理还没写，因为处理方式取决于下面这件要开发者定的事。

主会话读完后的判断：第 4、5、6、7、12、15 条是同一个来源，富文本编辑器建在章节的解析器（marked）上、内核却用另一套解析器（MDX 官方的）把关。主会话用内核真实的写入检查复核了几条：`1<2`、`<br>`、没配平的 `{`、正文里的 `好感度{+5}` 内核拒收；四个空格开头的段落内核读成段落、编辑器读成代码块，作者在里面改一个字就会被写成围栏代码、换了意思而内核不拒收。要让富文本在两套解析器上站住，得改发布的 nb-markdown 包（转义的口子）、给条目语言关掉缩进代码与 frontmatter、换硬换行的写法、四个菜单组件按白名单过滤、条目语法改经贡献点登记、编辑器侧的词法与内核做双向对照；其中条目语法那一层还取决于没定的写法（花括号还是标签，t38）。

开发者 2026-11-24 定：“可以，先做乙，这种模式用起来也还算顺手，以后再做实时预览。也不阻塞。同意尽快把垂直切片做通，用起来。”乙是第一版做整篇源文字的编辑（一个代码输入框），阅读视图保留并换成章节的排版；富文本等解析器与写法定了（t38）以后再做，实时预览以后再做。

[逐条处理](evidences/design-review-resolution.txt)与[计划第 3 稿](plan.md)已写；Spec 的 planned 条目改回按“编辑”进源文字的说法。计划缩小了很多（不再有可嵌入的富文本组件、条目语法、值的小块），所以不再开第二轮设计审查，做完交实现审查。

范围随之改成：第一版主文字不分节，点“编辑”在一个输入框里改整篇源文字，提交是整篇替换，别处也改了时按整篇问一次；阅读视图保留（点值看来历照旧），去掉每块的剧情菜单。
