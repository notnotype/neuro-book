# t39 实施计划：条目主文字的整篇编辑器

状态：第 2 稿（2026-11-24）。开发者同日确认第 1 稿：“打开就能打字当然还要有只读模式（现有的章节编辑器也应该有阅读模式）”“其他都同意”；本稿据此加了阅读模式，并补上“插入”菜单（第 1 稿没写清作者怎样在富文本里加一处写法）。

## 1. Context

开发者试用 t28 的按块编辑后说“编辑起来不顺畅，查看起来也不好看”“编辑还是直接给用户一个完整的编辑器更加好”，并定“第一版没必要分节”“我们继续先推这个编辑器”（[调研记录](../../research/2026-11-24-entry-text-direction.md)）。期望结果：作者打开条目页，像写一份文件一样写它的主文字，引用设定组的数据并看到当时的值；排版与章节一致。

已定的（开发者 2026-11-24）：第一版主文字不分节；用一个完整的编辑器；先做编辑器，写法（`{字段}`、`<Ref>`、`<Image>`）与内核不动；换解析器、换写法、标签登记表、沙箱块等用过之后再定（[t38](../t38-kernel-shared-parser/README.md)）。

约束：内核仍用它现在的解析器（MDX 官方的）在写入时把关，编辑器用章节的解析器（marked）读写，两边读法不同的边角在本 Task 里只做到“写出去的内核收得下，收不下的告诉作者是哪里”。

依据的 Spec：[`canon/author-ui.md`](../../../../../docs/specs/canon/author-ui.md) 输出 9、10、39、44 到 47；[`canon/rendering.md`](../../../../../docs/specs/canon/rendering.md) 输出 1、7；[`workspace/markdown-dialect.md`](../../../../../docs/specs/workspace/markdown-dialect.md) 的往返规则；[`workbench/editor.md`](../../../../../docs/specs/workbench/editor.md) 输出 68、69（页面的未提交内容、可嵌入的代码输入框，t28 已做）。

## 2. 技术选型

| 问题 | 选用 | 理由与否决的 |
|---|---|---|
| 富文本内核 | 章节已用的 Tiptap 加 nb-markdown 的语言、编解码器与编辑器扩展（`createMarkdownLanguage`、`createMarkdownEditorExtensions`、`codecFor`，包的公开入口） | t28 的 spike 在真实浏览器里走通过；不另写编辑器 |
| 工具栏与菜单 | markdown 插件现有的 `MarkdownToolbar`、`MarkdownMenus`，经它的服务交出一个可嵌入的编辑组件 | 否决 canon 直接引 markdown 插件内部的组件（跨插件深导入，spike 的做法）；否决把条目页接成 `MarkdownControl`（它绑定文件文档、frontmatter、批注页边与编辑区的命令，页面标签没有文档，要动编辑区的文档层） |
| 暂存、提交、多窗口 | t28 的稿会话（`text-drafts.ts`）原样用，上面加一层“整篇”的换算 | 否决重写一份只管整篇的会话：那套提交在途、结局不明、另一窗口的处理过了三轮审查 |
| 源文字的编辑 | t28 做的可嵌入代码输入框（Monaco） | 现成 |

## 3. 关键设计

### 3.1 markdown 插件：可嵌入的 Markdown 编辑组件（`plugins/markdown/web/components/`）

新组件（暂名 `MarkdownEmbed`，同名 `.md` 先写），经 `nbook.markdown` 的服务 `components` 交出，与 `PromptEditor` 同一条路。它不绑定文件文档：

```ts
type Props = {
    /** 源文字。外面换了值、与编辑器现在写得出的不同，就按新值重载（不进撤销历史）。 */
    modelValue: string;
    /** 调用方加的语法（条目的 `{…}` 与标签）；语言是核心语法加这些，不带章节的项目方言。 */
    syntaxes?: readonly MarkdownSyntax[];
    readonly?: boolean;
    label: string;
    placeholder?: string;
};
type Emits = {
    /** 停止输入 150 毫秒后、失焦时交出写出的源文字。 */
    "update:modelValue": [text: string];
    /** 写不出（编解码器的 `Unrepresentable`）：给出原因，不交出。 */
    problem: [reason: string];
    save: [];   // Ctrl+S
    blur: [];
};
/** 句柄：聚焦；在光标处插入一段源文字（按语言读成行内内容，例如调用方语法的一个小块）。 */
type Exposed = {focus(): void; insert(source: string): boolean};
```

- 工具栏、选区菜单、斜杠菜单用现有组件；它们从注入的 `editorMenusKey` 取菜单，本组件在自己的子树里重新提供一份，把 `run`、`execute`（撤销、重做）换成对这个编辑器执行（spike 第二个提交验证过）。语言里没有的动作（批注、注音、双语、表情）试跑为不可用，不显示。
- 写回按编解码器的规则：没编辑的块字节不变，编辑过的块重新写出并读回校验。
- Lab 登记场景（空、有内容、只读、英文），dom 测试覆盖：打字后交出、外面换值重载、只读、Ctrl+S、工具栏动作改的是这个编辑器。

### 3.2 canon：条目语法（`plugins/canon/web/entry-syntax.ts`）

一个 `MarkdownSyntax`：`{…}`（按 JS 的词法配平）、`<Ref … />`、`<Image … />` 读成行内的原子节点，原文记在节点上、原样写回；单独占一行的标签认成只有它的段落。节点显示成小块：文字由宿主给的“原文到显示”的表决定（3.3），查不到显示原文。

作者在正文里打的 `{`、`<` 写出去时转义（`\{`、`\<`），否则内核拒收。

对照测试（bun，不挂界面）：一组在富文本里会出现的内容（标题、列表、表格、粗斜体、换行、行内代码、链接、`{`、`<`、三种条目写法）经编解码器写出，逐条过内核的写入检查 `blockProblem`。过不了的逐条定：改写法，或记为已知限制并在提交时把内核的原因指给作者。

### 3.3 canon：文字分页换成整篇编辑器

- **整篇与块的换算**（`web/text-whole.ts`，纯函数，建在 `text-draft.ts` 上）：`wholeText(draft, read)` 是各块现在的文字用空行连起来；`setWholeText(draft, read, text)` 把第一块的文字设成整篇、其余的块删掉，没有块时加一块；整篇与读到的相同时稿回到没有改动。多块的条目因此在第一次提交时并成一块。
- **进不了编辑的条目**：有被剧情变更碰过的块（`textBlocks` 的 `write` 不是初值，或删不了）时只读，写明“这个条目的文字里有随剧情变的段落，现在只能看”。星瑕样本里没有这样的条目。
- **界面**：文字分页一打开就是编辑器，不再有“编辑”按钮与每块一个框。第一次改动时才建稿（`session.begin`）；有未提交的改动时位置选择禁用（t28 的做法）；顶上一行状态：未提交、暂存状态、“提交”“放弃”；Ctrl+S 与标签上的圆点照 t28。右上“源文字”切到 Monaco 里的整篇源文字，切回来按新文字重载。
- **两种模式**：编辑（缺省）与阅读（同一个编辑器只读，不显示工具栏与“插入”），状态行右边的开关切换；选择记在这部作品的本机记录里（`defineRecord`，`locality: "local"`），下次打开条目沿用。不能写时（按计划、只读、别人独占、断开、条目里有随剧情变的段落）只有阅读并写原因。阅读模式下单击条目引用的小块打开那个条目，编辑模式下按住 Ctrl（⌘）单击（与章节的链接一致）。
- **加一处写法**：作者在正文里打的 `{`、`<` 是文字。状态行的“插入”菜单列出本条目各命名空间的字段（显示名）与“条目引用……”（现有的条目选择器），选了在光标处插入小块（可嵌入组件的 `insert(source)`）；别的写法（条件、跨条目的字段、图片）在“源文字”里写。
- **值的小块**：内核给作者的渲染（现有的树）里每处值、算出来的结果、条目引用、图片的显示文字按出现顺序取出，与世界里的文字读出的原子节点按顺序对上，记成“原文到显示”。没动过的表达式显示当时的值，新打的在提交前显示原文。条数对不上时全部显示原文。
- **冲突按整篇问**：提交被拦下、重读后与稿对不上时，只问一次：左边我的整篇、右边现在的整篇，选“用我的”（在新读到的块上重建只含这篇文字的稿再发）或“用现在的”（放弃稿）。
- **内核拒收**：原因、行、列写在状态行下面，编辑器不离开。
- **拿掉的**：`EntryTextEditor` 的块操作（加、拆、并、删、恢复）与 `TextConflictDialog` 的逐块选择；阅读视图 `EntryText` 的“编辑”按钮与每块的剧情菜单、文末的“在剧情里加一块”。`text-draft.ts` 里拆与并的函数留着不删（不分节是第一版的决定，用过之后可能再议），不再有调用方。

## 6. 开发者定的（2026-11-24）

1. **打开就能打字，另有阅读模式**（开发者：“打开就能打字当然还要有只读模式”）。章节编辑器也应该有阅读模式（同一句），那是章节编辑器所在 Work 的事，不在本 Task，记在本 Work 的决策记录里待转过去。
2. **文字里的值点了看来历**（现在阅读视图有）：第一版小块只在悬停时提示它的写法，来历到数据分页看；之后再加“点小块弹出来历”。同意；代价是少了一个已有的入口。
3. **工具栏**：带上与章节同一套的工具栏与斜杠菜单（去掉批注、注音、双语、表情这些章节才有的）。同意。
4. **多块的旧条目**：第一次提交时并成一块；有随剧情变的段落的条目只读。同意。
5. **“源文字”切换**：保留，用 t28 做的 Monaco 输入框看和改整篇源文字。同意。

## 9. 不做与风险

- 不做：主文字的剧情变化；换解析器与换写法；标签登记表；沙箱块；图片在正文里的实际显示（小块写“图片：说明”）；新打的表达式在提交前求值。
- 风险一：编辑器与内核是两套解析器。兜底是 S2 的对照测试用真实的内核检查函数，与提交时内核的原因能指给作者。
- 风险二：值的小块靠“按顺序对上”，两边认出的条数不同时退回显示原文；用星瑕样本的全部主文字做一条测试，断言条数一致。
- 风险三：可嵌入组件在自己的子树里重新提供菜单，可能与编辑区后续的改动脱节；dom 测试断言工具栏动作落在嵌入的编辑器上。
- 留下的债：`text-draft.ts` 的拆与并没有调用方；t38 定了以后要么用上、要么删。
