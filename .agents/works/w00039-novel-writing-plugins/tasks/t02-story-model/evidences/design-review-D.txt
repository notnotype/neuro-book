独立设计 D：作者视角的世界模型内核（w00039 t02）

读过的材料：brief、星瑕种子与第一章大纲、样本书第 1、3 章开头、仓库现状调研、nb-memory 与 nb-history 的 README、forms 与 folder-kinds 两份 Spec、V9 提案的设计概览与第五节。没读 nb-story 代码，也没通读样本书；凡关于它们的说法是从文档推断。没读被禁止的文件。

==== 0. 结论先行 ====

内核只有四样东西，其余都是它们的视图：

1. 原文（Source）：作者写下的字，一字不改，永远是第一手材料。种子、细纲、笔记、正文都是原文。
2. 条目（Entry）：世界里一个有名字的东西（人物、组织、地点、物品、概念、剧情线、情节……）。条目 = 名字别名 + 介绍 + 若干字段。种类（kind）只是创建条目时给的一套默认字段，不是需要迁移的 schema。
3. 变更（Change）：挂在“书中位置”上的一条记录，说“从这里起，这个条目的这几个字段变成这样 / 多了这段补充”。字段在某个位置的值 = 基础值按书的顺序折叠此前的变更。设定补充、剧情里的变化、数值流水都是同一种东西。
4. 待定（Open question）：作者“没想好”的和 Agent 拿不准的，是一等公民，不猜、不编。

三条规矩贯穿全部设计：

- 摘录优先于转写。Agent 整理种子时，条目介绍引用种子里的原句（带出处），不改写成自己的话。Agent 自己写的字只放在明确标了“Agent 写”的位置（变更的文字、摘要视图），作者改过一次就变成作者的字。Agent 不能改作者的字，只能提建议。
- 改正与变化是两件事。“原来写错了”改基础值（只留版本历史，不进叙事）；“剧情里变了”追加一条挂位置的变更。界面和 Agent 的每一次写入都必须选其一。
- 视图可以丢、可以重算，从不当真相源。人物卡、前情提要、关系图都是派生物，每句带出处，条目或变更变了就标过期。

记账（作者最想交出去的事）：写完一章，Agent 读本章加相关条目的“截至上一章”状态，写出一批变更；默认立刻生效、整批可一键撤销、拿不准的进待定。作者看的是一张回执，不是一份要逐条批的清单。

==== 1. 各视角的质疑 ====

【反对与精简：要不要做，能不能用现成的】
- 不要做图数据库、关系管理、日历与 bigint instant、知情矩阵。旧 WorldEngine 的 instant 与日历让作者和 Agent 都要先学一套时间；nb-story 的说法与知情矩阵是读者视角的精细推导，作者视角用不上这么重。位置用“书的章顺序”就够：章有稳定编号，顺序由活页夹给，作者本来就按这个想。
- 人物关系不专门管。关系能从正文读出，由同场情节和提及算出来，Agent 写成可重算的摘要。只有三种关系值得显式存：所属 / 位于（地点层级、组织成员，要进地图和成员列表）、身份同一（马甲，审查吃设定时要用）。其余关系是视图。
- 种类不做成可迁移的 schema。旧版“schema 不版本化”是已知痛点（调研第五节第 4 条）。把字段定义拷贝到条目上，种类只是新建时的模板，就没有迁移问题；代价是同类条目会漂移，让 Agent 按需“把这套字段补给所有人物”。
- 能直接用的：表单用 nb-form（字段列表转 TypeBox，Agent 生成的字段走 agent 策略检查）；版本、审查收件箱、一键还原用 nb-history；章编号与卷用活页夹清单；检索用 nb-memory 的混合检索索引（只用它的索引与查询计划，不用它的事实抽取与主体注册表）。
- 要精简的：条目与情节不分两套模型。情节只是“数量大、要分页查询”的条目种类，界面不同，数据同一种。

【成本：开发、运行、模型额度】
- 开发：新写的只有折叠规则、位置模型、提及索引、记账校验器和几个视图；其余是拼现成件。
- 运行：折叠按条目取变更再算，量级是条目数乘章数，几百章不成问题，派生索引放 SQLite，可整库重建。
- 模型：记账每章一次，读一章正文（约 3 至 9 千字）加上提及到的条目卡，估计输入 2 万 token 量级、输出 2 千以内；三百章约 600 万 token，用便宜档模型可接受，但必须按“本章写完”触发，不能每次保存都跑。提及查找、数值折叠、过期检测、健康检查全部零模型。审查细纲的“先查条目”这一步也是零模型的（别名匹配），模型只读它的结果。

【使用者体验】
- 作者：什么都不用先填。可以只贴种子，也可以直接写第一章。打开条目看到的是自己的字加一张表单；想知道“读到第 N 章时是什么样”拖一个位置条。
- 写代码的 Agent：模型小、字段少、校验有错误码（不靠文案分支）；每个变更自带出处，调试时能问“这个值是谁、依据哪句话改的”。
- 产品里的 Agent：工具一个只做一件事（查提及、读条目、查情节、提交记账批、提问），写入工具在底层拒绝改作者的字，不靠提示词自觉。

【迁移与兼容】
- 旧 lorebook 条目可以直接导入：index.md 正文是条目介绍（作者的字），frontmatter 变字段。旧 Plot 的 StoryThread、StoryScene 变成剧情线条目与情节条目。旧 WorldEngine 的 patch 绝对值部分可转成变更，相对操作和 instant 对不上章位置的丢进待定，不承诺无损。
- 与 nb-story：两边都是“挂位置、带出处的记录”，所以保持位置、出处、稳定 id 的写法一致，以后可以把已写部分的事实对到 nb-story 上；作者视角比它多的是计划、未揭示的设定、待定和数值字段。

【可观测与排障】
- 每个值都能展开“来历”：基础值 + 哪些变更按什么顺序折叠成它，每条带批次、谁写的（作者 / 哪个模型 / 提示词版本）、依据的原文。
- 零模型的健康检查：引用悬空、两个条目别名撞车、数值与正文“写明的总数”对不上、变更的出处句已被改走找不到、章正文改过而该章记账没更新、计划中的情节已过其章仍未写、有多少条待定。
- 记账是幂等的：同一章重记，会撤销上一批里没被作者碰过的项，作者改过的保留。

【长期维护与技术债】
- 最大的债会是“Agent 写的字”渐渐变成事实上的设定，作者没意识到。对策是 origin 字段与界面上的颜色区分，加上“采用 Agent 的话”这个显式动作。
- 第二个债是位置模型：只靠章顺序，倒叙、故事时间、同章内顺序都要另想办法（见最没把握的第三条）。

==== 2. 方案 ====

2.1 核心概念与关系

原文（Source）
- 种类：种子、细纲、笔记（作者的意图与备忘）、正文（活页夹里的章）、素材（图片等）。
- 故事种子的定义（开发者问过）：整本书层面的、没有结构的、作者给 AI 的指令文字，里面混着三类内容：设定（是什么）、计划（大致怎么走）、未定项（我还没想好）。它是指令，不是数据，所以原样存作原文，结构化的东西从它里面摘出来，不替代它。
- 不可变：作者改它是改，AI 不能改。每段可以被引用（引用 = 原文 id + 一句原话 + 偏移，偏移失效时按原话重新定位，找不到就标“出处失联”，不静默丢）。

条目（Entry）
- id 稳定（不用名字当 id）；名字、别名；种类；介绍；字段；父级（可选）；图片。
- 介绍由若干块组成，每块要么是作者写的字，要么是对原文的摘录，要么是 Agent 写的字，每块有 origin。表单上“介绍”就是这几块，作者在里面写，写下的字归作者。
- 字段：每个字段有 id、标签、类型（文字、数字、单选、多选、列表、条目引用、图片）、是否“追踪”（追踪 = 数值或持有物，改动走变更流水）。字段定义存在条目自己身上，种类只是新建时的默认字段集。
- 种类默认字段（起步一套，作者或 Agent 随时能改）：
  - 通用：只有介绍（“灵魂宝石”就是这样）。
  - 人物：介绍 + 外貌等文字字段 + 立绘（图片）+ 追踪字段；
  - 组织：介绍 + 成员（列表，每项 = 条目引用 + 一句话）+ 历史（由挂在它身上的变更自然形成，不单设字段）；
  - 地点：介绍 + 位于（父级引用，层级与地图由它推出）；
  - 身份（马甲）：介绍 + 是谁（引用）+ 谁知道（引用列表）；
  - 剧情线、情节：见下。

变更（Change）
- 结构：{条目, 位置, 批次, origin, 补充文字?, 字段操作?, 出处, 状态}。
- 位置 = {章 id, 可选一句原话}。章内顺序按原话在当前正文里的先后算；没有原话就当作章末。以后加 {线}（世界线）这一项，缺省为主线。
- 字段操作只有这几种：set（设为）、add（数值增减 / 列表加项）、remove（列表去项）。set 可以带 assert，表示“正文里写明了这个总数”，折叠时用它校对前面累加的结果，对不上报告而不是中断，以后者为准。
- 补充文字：只追加。显示在条目上，晚于该位置的视图才可见。
- 状态：生效 / 撤销（撤销不删，折叠时跳过）。
- 折叠：位置之前所有生效变更按（书顺序，批内顺序）依次应用到基础值上。因为 set 和 assert 都会重置基线，往前面补写一条变更只会让后面的累加重算，不会像旧 WorldEngine 那样断（相对操作 broken-relative）。

待定（Open question）
- 内容：一句话 + 关联条目 + 来源原文 + 状态（open、answered、dropped）。回答它时追加一条变更并指向这条待定。作者种子里的“这里我没想好”直接成为待定，不让 Agent 补全。

2.2 设定、状态、剧情、情节各怎么存、怎么变

设定（相对稳定的“是什么”）
- 在条目的介绍与文字字段里，没有位置的是“一直如此”的基础值。
- 随剧情补充、解释：追加变更（补充文字，位置 = 揭示它的那一章）。
- 作者发现写错：改基础值，走版本历史，叙事视图里不留痕。这就是“改正”。改正之后系统做一次零模型的涟漪检查：哪些变更、哪些情节引用了这个字段，把它们列出来给作者或 Agent 复核。
- 作者发现正文跟设定对不上（吃书），有三个处理：改设定（改正）、改正文（作者的事）、当作剧情变化（在那一章追加一条 set 变更并写原因）。审查报告把这三个选项并排给出。

状态（作者也要自己维护的：钱、物品、面板）
- 就是“追踪字段”的折叠值，没有第二套机制。表单上追踪字段显示当前值，旁边“来历”看流水。
- 编辑追踪字段时默认问“从第几章起”（缺省 = 当前读到的章），生成变更；编辑非追踪字段默认是“改正”。每个字段旁有一个小开关可以换。这是整个设计里最敏感的交互，见最没把握。
- 面板文：数字由程序按流水格式化生成（`panel.render(条目, 位置)`），Agent 写进给作者的草稿时调用它，不心算，避免模型算错。面板文本身要写进正文时仍是作者的稿子，Agent 只能给草稿建议。

剧情
- 承载树：卷与章，就是活页夹清单，本设计不改它。
- 因果树：剧情线条目（字段：状态 计划中 / 进行中 / 已收 / 放弃，所属阶段 = 父级，意图文字）。情节挂在剧情线下。
- 两棵树交汇在情节：情节有两个坐标，所属剧情线与位置（章或卷，计划阶段可以只写到卷）。章页列出它的情节（计划与已写），线页列出它的情节（排在哪些章）。伏笔是一种剧情线：状态 open / 收了 / 放弃。

情节（数量多、分页、查询）
- 情节是条目的一种，字段：一两句概括、剧情线、位置、状态（计划 / 已写 / 放弃）、在场者与地点（条目引用）、起因（可选，指向别的情节，形成因果边）、出处（已写时指向正文原话）。
- 它是“大宗”种类：界面是分页表格加查询控件（结构化筛选 + 一个自然语言框）。自然语言框走“嵌入检索，可选地让小模型把问句改写成筛选条件”，沿用 nb-memory 的查询计划思路，嵌入后台补，没嵌入时字面检索照样能用。
- 细纲不强制拆成情节。作者给的细纲先作为原文挂在章上；只在讨论或记账需要时才抽取成计划情节，抽取结果带出处。

2.3 视图（整理过的，给人和 Agent 读）
- 人物视图：作者的介绍 + 截至当前位置的字段 + 最近几条变更 + 一段 Agent 写的摘要（带“Agent 写”标签、每句出处、是否过期）+ 同场多的人物与所在组织（算出来的，不是管出来的）。
- 剧情视图：每条线的“前情提要”、未收线 / 伏笔表、待定清单、按卷分组的章概览。章概览的一句话是记账顺带产出的。
- 地图：地点的父级树，以后可加坐标。
- 视图的账：记录它用了哪些变更的版本，条目或变更动了就标过期，点开再重算。Agent 做审查时只读条目、变更、正文，不读摘要，防止摘要套摘要逐轮漂移。

2.4 作者怎么开始、日常怎么用

开始（三条路，终点一样，什么都不是必填）
- 先贴种子：作者贴一大段话。系统存为原文，Agent 做“接种”：切出条目草案（带摘录）、待定、作者备忘，给作者一页“我是这样理解的”，一键确认或逐项改。
- 先写第一章：直接在活页夹里写。写完点“记账”，Agent 从正文里建出第一批条目和变更。设定靠脑子记的作者就这样用，只有技能、数值和要构思的东西，作者想起来时才对 Agent 说一句“记一下”。
- 先搭设定：用表单填，或者把已有设定文档整篇贴进来，Agent 只做分条与摘录。

日常循环
1. 想一章：把细纲发给 Agent 聊，系统自动附上相关条目卡（作者没要求也附，是零模型的）。
2. 写正文，自己写。
3. 点“记账”：回执出现，里面有新条目、变更、情节状态更新、新的待定、发现的矛盾。作者扫一眼，可以整批撤销或点具体一项改。
4. 需要时看条目、拖位置条、查情节。

作者的字永远不被 Agent 改：写入工具在底层检查目标块的 origin，作者块拒绝，只能走“建议”队列；Agent 若直接用文件工具改了作者的文件，nb-history 的收件箱会把它列为 Agent 改动，健康检查也会发现作者块的哈希变了。

2.5 Agent 怎么查、怎么审查细纲、怎么记账

查（系统先做，Agent 补）
- 系统对作者发来的细纲做提及解析：别名精确匹配，匹配不上的名字候选交给嵌入检索，产出“相关条目卡包”（每张卡限长：介绍前几句 + 截至上一章的字段 + 最近三条变更 + 相关待定）。同名条目返回候选，不替作者挑。
- Agent 工具各做一件事：解析提及、读条目（可给位置）、条目来历、查情节、读章节原文（用现有文件工具）、提交记账批、提出建议、提出待定。

审查细纲（不写任何数据，产出是讨论）
- 三类发现，每条必须带出处：吃书（和已写正文冲突，指向章与原话）、吃设定（和条目 / 变更冲突，指向条目与变更）、不严谨（自相矛盾、数目对不上、没有动机、计划里提到的东西找不到）。
- 细纲里出现的新名字单列为“可能的新条目”，不创建。
- 所用的世界状态是“截至上一章”的折叠值，不看计划中的未来。

记账
- 输入：本章正文、本章细纲（如果有）、截至上一章的相关条目卡、本章计划情节。
- 输出一个批次：新条目（带摘录或原话出处）、变更（字段操作 + 出处）、情节（计划转已写、新增、放弃）、剧情线状态、待定的新增与回答、发现的不一致。
- 写入前程序校验：引用的条目存在、字段类型对得上、数值加减由程序算、assert 校对、出处原话确实在正文里。校验不过的项不入账，退回 Agent 重试一次，仍不过进待定。
- 默认生效，回执展示，整批可撤销。以下情形不自动生效，进待定等作者：与已有条目冲突、要合并两个条目、身份同一、删除、模型自己标了低把握的项。
- 幂等：键是（章，正文哈希）。正文变了，健康检查标“账可能过期”，重记时撤销上一批里作者没碰过的项。

2.6 不堵死的路
- 平行宇宙：位置里预留“线”，折叠改成按线的祖先链取值（主线到分叉位置，再接支线）。只有“两条线交替叙述”才需要线；单线的“死亡回档、重来一遍”按书顺序加一条 set 变更就能表达，不需要线。
- 死亡回档（Issue #144）：同上，数值回到重来时的值由一次 set 完成，旧账留在历史里。
- 与 nb-story 合并：见上，位置、出处、稳定 id 的写法一致。
- 揭示时点：变更可选地带“揭示于”（作者设定从某处就成立，读者要到第 N 章才知道）；第一版不做，但字段预留，写悬疑的作者审查时需要。

==== 3. 用星瑕的例子走一遍 ====

步骤 A：作者贴种子，要求加魔法精灵面板
- 系统把整段存为原文“故事种子”，不动一个字。种子里“我这里会记一下，做个笔记”的两句（前期舞台在蓝星，宇宙里还有高魔世界）存为作者备忘，挂在“世界”条目上。
- Agent 接种，给出理解页，不是直接入库。条目草案（介绍都是摘录种子原句，不改写）：星瑕（人物）、星瑾（人物）、蓝星（地点，介绍摘录“联邦统一社会，表层与里层”）、超凡种类（概念：魔法少女、魔女、异能者、天使）、魔法少女对策局（组织）、官方（组织）、魔法精灵（概念或人物，待作者定）。
- 三个身份建成三个“身份”条目：男性形态（认知魔法幻化，妹妹只知道这个）、魔法少女变身形态（认知干扰，官方知道）、女性原身（现在这个，无人知道）。每个身份有“谁知道”字段，值来自种子原文，不够的留空。
- 主角经历（幸福家庭、六岁灾难、父母双王、觉醒回溯救妹妹、被带走、晋升成最强、被诬陷隐退）建成已发生的背景情节，状态“已写”改为“背景”，没有章位置，出处指向种子原话。
- 种子里作者自己没定的，一律建成待定而不是补全：兄妹矛盾的缘由、被官方带走的具体原因。
- Agent 发现的不一致也进待定：种子里先说“对策委员会，魔法少女部”，后文又说“魔法少女对策局”，注释说它是官方的外包组织、不属于官方，这是同一个组织的两个名字还是两个组织？Agent 不替作者决定，提出来，作者答一句就会变成别名或拆分。
- 面板：Agent 在星瑕身上提出一组追踪字段，如“魔法精灵面板”分组（魔力、体力、等级、技能列表……具体项由作者定；Agent 给一个最小草案），以表单形式展示让作者增删，字段定义经 agent 策略检查。值全部留空：种子里只说了“钱不多但够用”，不编数字，转成待定“初始存款多少”。面板属于星瑕本人还是属于魔法少女形态，这也是个待定。

步骤 B：作者发第一章细纲，先聊
- 系统先解析提及：星瑕、星瑾、彗、魔偶、认知滤镜、《如何做个好哥哥》、魔法少女马甲、好姐姐。前几个命中条目，“彗”“魔偶”“那本书”是新名字，进“可能的新条目”。“认知滤镜”别名匹配不上，嵌入检索候选是种子里的“认知魔法”“认知干扰”，列为候选并请 Agent 问作者。
- 条目卡包含：星瑕的三个身份、谁知道哪个身份、存款（空）、最近变更（暂无）、相关待定。
- 审查发现（每条带出处）：
  1. 不严谨：大纲说“这三点”，列了五条建议，数目对不上；末句说“被弟妹抱着哭”，但种子里只有妹妹。
  2. 吃设定风险：大纲写“关闭认知滤镜，展露美少女真身”，种子里有两个女性相关形态：魔法少女变身形态（有认知干扰）和女性原身。读者看到的是哪一个？这影响“官方知道哪个”“妹妹会不会看见”，请作者确认是女性原身。
  3. 新设定要不要入库：“主角被软禁，彗做魔偶帮她逃脱”种子里没有，只说被诬陷后隐退。它可能解释了“官方明面上还按魔法少女的身份报道”，建议作者确认是否这样，确认后建成背景情节和彗这个条目。
  4. 张力：“用钱说话”建议与“隐退后钱不多”并存，不算矛盾，提醒作者决定这是不是想要的戏剧效果；种子有写作意图“低情商做事搞砸”，这条意图存为挂在第一章上的作者备忘，供后面审查和写作时引用，不做成世界事实。
- 这一步 Agent 没写任何数据。作者回答的结论，要作者说“记下”才写（或在回执里确认）。

步骤 C：写完第一章，记账
- 作者点“记账”。Agent 读第一章正文，加星瑕、星瑾、彗等条目卡，提交一个批次：
  - 新条目：彗、魔偶、《如何做个好哥哥》（物品，持有者星瑕），介绍均摘录正文原句。
  - 变更：星瑕“当前形态”从男性形态变为女性原身（位置 = 关门关滤镜那句原话）；“知情”字段无变化（妹妹仍只知道男性形态）；《如何做个好哥哥》加入星瑕持有物（若写了存款支出，存款追踪字段按流水 add，程序加总）。
  - 情节：细纲里的早餐、妹妹赌气出门、独白、阳台阅读、联系彗，由计划转已写，出处指向正文原话；“彗的五条建议”未写完的部分保持计划。
  - 待定：新增“魔偶是否解释了官方的明面报道”，若作者在步骤 B 已答，则直接回答并关闭相关待定。
  - 发现：正文里“关滤镜”出现的次数与细纲一致，没有冲突。
- 回执：“新增 3 个条目，6 条变更，5 个情节转已写，1 个新待定，0 个冲突”。作者点开看一眼，要改就在回执里改；不满意整批撤销。
- 之后作者在人物页看到星瑕：“当前形态：女性原身（第 1 章起）”，来历里点开能看到这条变更和它的出处原话。拖位置条到“第 0 章”，看到的是种子时的状态。

步骤 D：以后某天发现设定写错
- 作者在种子里写的灾难是“城市大灾难”，写到第 40 章决定改成“星际入侵”。这是改正：作者在表单里改基础值，涟漪检查列出引用它的 3 个情节与第 2、5 章里的一条补充，请 Agent 复核正文。
- 如果是剧情里揭示“其实那场灾难是人为的”，则是变化：在第 40 章追加变更，叙事视图里第 1 至 39 章仍显示旧说法。

附：样本书（反派魔法少女）也能套：苏天晴与原主同名不同人 = 两个条目，别名撞车由健康检查报；风信子与南小风是两个身份条目加“是谁”引用；神典石的数量是追踪字段，流水加总，正文写明总数时 assert 校对。但“谁在第几章知道风信子是南小风”这种读者向的知情矩阵留给 nb-story，作者侧只有“谁知道”这一个字段。

==== 4. 备选与取舍 ====

备选 B：沿用旧 WorldEngine 的“主体 + 切面 + patch + instant”，加日历。
- 好处：事件溯源已想清楚，折叠语义现成。
- 不选：instant 和日历强迫作者先有时间系统；相对操作补写会断；Agent 门槛高；schema 不版本化；调研已经列了七条痛点。我的方案保留事件溯源的折叠思想，把时间换成作者本来就有的章顺序，把 schema 换成拷贝式字段。

备选 C：纯文档，不做结构化（chatbot 模式 + Agent 维护 Markdown 设定文档和 state.md）。
- 好处：最便宜，作者的字最自然地保留，上下文够用时体验最好。
- 不选作主线：数值会算错、没有“截至第 N 章”的视图、审查只能靠模型全文阅读、条目一多没法分页查询。但它是我的方案的退路：条目只有介绍时就是文档，Agent 写不出结构化变更时也只退成“补充文字”，所以可以渐进启用。

备选 D：以 nb-story 的读者向事实图为底，作者侧只加一层计划与字段。
- 好处：只有一套模型，抽取管线与评测已有。
- 不选：读者图是“书里已经写出的”，没有未写的设定、计划、待定与作者备忘；抽取成本和复杂度（说法、知情、12 个大类）对不管数据结构的作者过重。两者通过位置、出处与 id 对接，留待合并时再决定谁做底。

为什么选 A：它把“作者的字不可改”“改正与变化分开”“视图可丢”三个对作者最重要的承诺放在数据模型里，而不是放在提示词里；并且每一项都能零模型降级（没有 Agent 时是文档加表单，Agent 来时才有记账与审查）。

==== 5. 我最没把握的三件事 ====

1. “改正”与“变化”能不能让人不犯错。
   整个折叠模型依赖每次写入选对这两者。选错的后果是静默的：把剧情变化当作改正，历史章节的视图就被改写，审查会拿着错的“截至上一章”去判断；反过来把改正当作变化，会给旧章留下一条永远存在的假历史。我用“追踪字段默认变化、其余默认改正”加涟漪检查来缓解，但没有实测，作者会不会注意到那个小开关也没有证据。如果证明不可靠，退路是不让作者选，一律先记为变化并请 Agent 在回执里问“这是改正还是剧情变化”。同时，“摘录代替转写”会让条目介绍成为碎片，读起来是否通顺也没验证。
2. 记账默认生效的误差会不会累积。
   我押注“默认生效、可撤销、拿不准的进待定”，因为逐条批准违背“无心智负担”。但误记会污染之后所有章的条目卡，进而让审查误报或漏报，错误还会被模型当成既有事实继续引用。几百章下来的准确率、哪类项必须强制待定、条目卡的召回（该装进上下文的相关条目装没装全）都没有数据。需要先在样本书前 5 章上跑一遍，把误记率和回执复核成本量出来，再决定默认值。成本估算（每章约 2 万 token）也是推算。
3. 位置只用“章 + 原话”是否够用。
   它简单，也与活页夹贴合，但倒叙、回忆章、章内形态切换（如第一章里同一章中男身变女身）、重排章节后折叠结果变化、以及“故事时间”与“阅读顺序”不一致的书，都靠原话顺序和 set 变更凑。星瑕的“时间回溯能力”一旦在正文里真正使用（救妹妹的回溯），同一时刻会出现两个版本的世界，那时是否仍能用 set 变更表达，还是已经必须引入“线”，我没有把握。引入线的时机也没想清楚，我只保证了数据里留位置，没有验证折叠改成祖先链后表单与审查是否还能保持简单。
