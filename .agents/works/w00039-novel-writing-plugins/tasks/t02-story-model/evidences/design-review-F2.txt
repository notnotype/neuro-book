2. 任务产出：审查意见

（先说结论：细纲有三处硬冲突必须先改——位置/距离、余额 300 对 200、战力；其余是动机和机制缺依据。）

吃书（和已写的第 1–3 章冲突）

A1. 位置错了，且和“见面礼”的伏笔冲突。
    正文 3.43–3.50 她已经坐地铁到市中心走进公园，3.54 是中饭时间，3.73–3.75 入夜后她还在公园里（关手机、接充电宝），3.80–3.87 怪人出现时她就在现场，还留了“我可是给你准备了一份——美妙的见面礼哦”。
    细纲写“苏天晴接到秘典的提示，从蓉城东部的家里出发”，等于把她的位置搬回了家。
    改法：第 4 章开头直接接 3.87，她在公园里；要写她在公园里“下午研究秘典时发现商店”，就在公园长椅上发现，不需要回家。

A2. 距离和时间对不上。
    3.36 与条目“蓉城”都写明：东部到中心城区坐地铁要两个小时。细纲的“打车十分钟赶到绿心公园”在这本书的地理下不可能成立。
    改法：她的位置按 A1 留在公园（最省事）；如果一定要写她回家再回来，按两小时写，或者给她一个能解释的快速手段（秘典传送之类），但那要先进设定。

A3. “接到秘典的提示”是重复。
    c11 / 3.29–3.34 秘典已经给过“今晚蓉城市绿心公园将出现怪人”的预测，她正是照这个来蹲守的。细纲再让她“接到提示”，读者会觉得她忘了自己上午看过的东西。
    改法：删掉这句；若要给她一个新提示，写清楚是新的（例如“怪人已出现，风信子已出发”）。

吃设定（和条目里的设定冲突）

B1. 300 神典石买不了，硬冲突。
    - 苏天晴.panel.神典石 = 200（初值 200，流水里没有任何入账）；
    - 墨丘利秘典条目写明“余额不够就买不了，不能赊账”；
    - 每日任务1 的 100 神典石奖励只有在“找茬魔法少女”完成后才有，本章里她帮的是风信子，不能算完成。
    所以 200 − 300 = −100，既付不起，也不能赊。
    改法（三选一，按作者意愿）：
    (a) 药价改成 150 或 200，正好把启动资金花光，更能解释她为什么急着赚神典石；
    (b) 先让她完成“找茬”拿到 100，再买 300 的药（200+100=300，余额归零，且顺带把每日任务推进了）；
    (c) 让秘典“赊”一次——但这与条目里“不能赊账”直接冲突，要改设定就得同时改条目，不建议。

B2. 战力不成立。
    3.15–3.18 她看完风信子的战斗视频，明确“担心自己打不过肉搏型的她”“对自己变身后的力量没有任何直观的感受”；守护之星条目只给了变身，没有战斗技能。
    细纲却让她打倒“刚把风信子抓住的强化黑狼”。这等于她比风信子强，和前面整章的紧张完全相反。
    改法：要么给她一个明确的招式来源（守护之星/秘典给的技能，先写进条目），要么改结果（她只是干扰/用秘典的道具骗怪人松手，真正打倒怪人的还是风信子），要么让她翻车——这也更符合“反派”的定位。

B3. “强化药让黑狼复活”没有依据。
    秘典只写了“有一个商店，可以用神典石买道具”，药名是“怪人强化药S”，强化的语义里没有复活。复活是个新能力，必须在这个道具的条目里写明（比如“对怪人使用后恢复并强化一次”）。
    改法：买药前用一句正文交代药效，或者把药改成“续命/狂暴”这类能解释第二次站起来的名字。

B4. 白灵 / 观星者 / 精灵是全新的设定，没有任何落点。
    lookup 与 tree 都没有白灵、观星者、精灵；世界观“兽人”只写了猫娘狐娘，风信子条目里也没有同伴。
    这不是冲突，但它是这一章第一次出现的常驻角色：不建条目，下一章写手就查不到她，后面再让她出场只能凭记忆，迟早吃书。
    改法：本章记账时新建条目“白灵”（人物，位置放人物/魔法少女或人物/配角），一句话描述 + 人物组件；如果“观星者”是一类存在，另建世界观条目。

B5. 风信子的学生身份没有依据（不是冲突，是资料缺口）。
    风信子条目只有外貌、能力、所属、真名，没有年龄、学校、住处；第 1 章开头声明“本书出场角色均已满18岁”，写“补暑假作业”需要能对得上（大学暑假、或者成人教育都行，但至少要能写圆）。
    另外 3.37 是“蓉城医学院后天开学”，也就是开学前两天；如果风信子也在读书，两边的校历要对得上。
    改法：在风信子的人物组件里补“年龄/学校”两个字段，或者细纲改成“在家赶报告/开学前的作业”，避开暑假这个具体说法。

C. 严谨（逻辑与动机）

C1. 动机断裂（最需要改的一条）。
    她花光所有钱强化黑狼 → 目标是找茬风信子、拿 100 奖励；风信子被抓后她又“担心她受伤”，打倒黑狼然后走人。
    中间没有任何转折点：她只见过风信子的视频，谈不上感情；“担心她受伤”与“刚花 300 强化怪人打她”互相抵消。
    改法（给一个能同时立住反派和出手的理由）：
    - 怪人失控，围观居民还在，她要的是“找茬”，不是“出人命”；
    - 她要的是让风信子欠她一次人情，好接近她、拿关注者（正好接夙愿任务）；
    - 或者干脆让她见死不救、由第三方收场，反派定位更稳。
    建议把理由写成一句内心独白，放在出手前。

C2. 药效时序没交代。
    她下午买药，入夜怪人出现才灌药；风信子先占上风、把黑狼打倒，然后药才发作、怪人复活抓住她。读者会读成“作者需要反转才让药起效”。
    改法：写明“药在怪人被打倒后才完全吸收/发作”，或者改成她在风信子快赢时当场灌药（更主动，也更反派）。

C3. 协会为什么知道。
    英雄协会条目只说“管辖并委派”，没有监测或预测机制。风信子在补作业时被“紧急通讯”叫到具体地点，缺一句依据（协会的监测网、市民报警、秘典之外的预测）。
    改法：一句“协会监测到绿心公园有怪人反应”即可。

C4. 当面自称反派的后果没写。
    魔法少女“真实身份保密”，她当众以金毛狐女的身份自称反派并出手，风信子所属协会之后一定会追查。细纲让她“然后离开”，把后果整个跳过了。
    改法：至少写风信子的反应（震惊/警惕/上报），并在本章计划变更里留一条“协会注意到反派魔法少女”的计划，供后面章节使用。

C5. 第 4 章从哪一刻开始没说。
    第 3 章结束在入夜、公园现场；细纲的场景是“下午研究秘典”，读起来像倒叙。作者可能没意识到这是个时间跳跃。
    改法：在细纲开头标一句“接第 3 章末尾，同一晚”或“当日下午，倒叙”。

D. 不需要改、但记账时要区分的

D1. “风信子真名南小风第一次交代”不是世界的变化，是叙述信息。名字本来就在（风信子条目的真名 = 南小风），正文第一次说出来不改变任何状态，所以不该写 write.change；同理“她发现秘典能买东西”也不是变化（商店本来就有）。
D2. 风信子条目里真名的值写成了“南小风（第 4 章揭晓）”，把创作备注混进了字段值。带值渲染会原样给 Agent，写手会把括注当成名字的一部分。建议记账时用一次 write.edit 把值改成“南小风”，把“第 4 章揭晓”挪到时间线/备注。

4. 这个任务里，模型、工具或格式不够用 / 别扭 / 差点做错的地方

(1) 自动预查漏了状态字段，差点直接判“300 能付”。
    现象：预查目录只给名字、位置、描述、组件，没有任何状态值；我要自己去 read 面板才知道余额是 200。如果我省一次 read，就会写出“神典石不足”以外的结论，或者干脆漏掉这条最硬的冲突。
    绕过：凡涉及数字的句子，都补一次对应组件的 read。
    建议：预查目录在组件后面带一条“关键状态摘要”，例如“面板：神典石 200”，或者至少在描述里注明“有数值组件，读 read(…, view: 面板)”。不需要全量，给一行就够。

(2) lookup 查不到面板字段，和“新设定”长得一样。
    现象：lookup(神典石) 无结果，但神典石是面板里真实存在的字段；lookup(黑狼)、lookup(白灵) 无结果是真的没有条目。三种情况在工具返回里没有区别，我只能靠猜。
    绕过：凡“没找到”的词，再判断它是数值字段、道具名还是人名，必要时补 read。
    建议：lookup 的“没找到”后面加一句归类提示（“未找到条目；若它像数值/货币，请读面板视图”），或者让 lookup 也索引组件声明的字段名。

(3) 对照正文时没有“按词检索正文”的工具。
    现象：我要确认“黑狼”在第 1–3 章有没有出现过，只能把三章通读；search 只查变更日志和条目文字，不查正文。三章不长还读得动，章节多了这就是主要成本。
    绕过：通读，靠段落编号记证据。
    建议：search 加一个“章”参数能过滤正文，或者提供 read(第 N 章, 段范围) 精确读。

(4) 没有“细纲段落”这种出处。
    现象：tasks 里 出处 只允许“正文段落（章.段）”或“手记段落”。这一章的变更全部来自细纲，我写“细纲（第 4 章）”是编的；写“正文 4.x”更是编造。
    绕过：出处写“细纲（第 4 章）”并在报告里说明。
    建议：出处增加“细纲/章计划”这一类，或允许“暂空”，等正文写完再补。

(5) 计划变更没有“待定”表达。
    现象：p02 的金额和 p07 的战力都还没定，但字段只有描述/补丁。补丁写 −300 就是已经定性了，写 −150 又是我替作者决定。
    绕过：在描述和备注里标“待定”，补丁照细纲原值写并加括注。
    建议：补丁允许“待定占位”（例如 `苏天晴.panel.神典石 -= ?`），或者变更本身有个“草稿/待决”状态，避免 Agent 把审查意见偷偷变成数值决定。

(6) 真名字段把创作备注当成了值。
    现象：{character.真名 = "南小风（第 4 章揭晓）"}。渲染约定说“= 值”是可以打补丁的值，读起来像名字就叫这个。
    绕过：按正文 3.x 与细纲判断真名是“南小风”，括注是作者的备注。
    建议：这类“计划到第几章交代”的信息不该进字段值，应该有个专门的“揭晓计划”或时间线字段，渲染时也不混进值里。

(7) 人物组件没有“年龄/学校/住处”之外的常用字段，判断“补暑假作业”只能猜。
    现象：风信子没有年龄和学校字段，我没法判断“暑假作业”与她 18 岁、与苏天晴开学前两天的校历是否矛盾。
    绕过：标成“资料缺口”而不是冲突，让作者决定。
    建议：人物组件的常用字段里补年龄、身份（学生/职业），这对判断时间线很有用。

3. 带值渲染 {路径 = 值} 用起来顺不顺

顺的地方：
- 看到 “{character.外貌 = "……金色眼眸"}” 就知道这是字段，能按路径打补丁，不用去猜哪部分是设定、哪部分是散文。
- 消息 3 那种重复最容易发现：面板里已经有余额，主 MDX 里又写了一遍，一眼就能看出是两条来源。
- 改初值的影响面清楚：这个路径从来没有被变更改过（流水里没有），所以改它不会把后面的变更弄旧。

不顺的地方：
- 同一个值有两个入口：外貌既可以在 人物 视图里改，也可以在 主 MDX 的渲染行里改。我如果直接改渲染行里的文字，系统会把它当主 MDX 的文本 diff 还是字段赋值？两种理解都讲得通，而结果是“改字段”（影响所有位置）还是“只改这一段文字”，差别很大。
- 字符串只能整值覆盖，没有局部替换。短句还行，外貌这种一长串，整值覆盖等于每次都要抄一遍，抄错的风险比改一个词大。
- 渲染里读不到“这个值有没有被后续变更改过”。我是靠 search(外貌) 在日志里找的；真实系统里应该在渲染行上直接标“此后被 cNN 改过”，否则改初值前的那一步检查很容易漏。
- 图片行 “{character.立绘 = 图片 assets/...}" 只给路径，看不到图；改外貌时无法判断立绘是否已经不一致。

4. 不确定该改状态还是改主 MDX 的情况

(a) 消息 1、2 都是身体设定，值在 character.外貌 里，但显示在主 MDX 的一行里。我的原则是：值有路径（{路径 = 值}）就改状态，不在渲染文字上动手。问题是渲染行看起来就是一段文字，很容易顺手改字。
(b) 消息 3 反过来：句子在 {} 之外，是主 MDX 的散文，但它紧挨着一个表达式。删整句时，系统要能分清哪些是源文、哪些是渲染出来的 “= 200”。
(c) 立绘：既不是状态字段（它是路径值，但内容是一个资产），也不是主 MDX 的散文。剪发后要不要换图，没有工具能表达。
(d) 风信子真名那种“值里带作者备注”的情况：改的是值还是备注？没有备注字段，只能改值。
(e) 同一个字段的两条消息先后作用（消息 1 改眼睛、消息 2 改头发），如果两条都写成整值覆盖，后一条会覆盖前一条。文本 diff 不会，但整值覆盖会；顺序和合并方式需要明确定义。

3. 到第 100 章会不会变长

基本不变的部分：
- 条目渲染：大小只取决于这个条目自己（外貌字段、主 MDX 长度、面板字段数），与书的总长无关。这是这套设计的核心好处，实测这几份文件都是几百字符量级。
- 最近一章正文：线性于“这一章多长”，不是“书多长”。作者越写越长会让它变大，但那是章长问题。
- 提醒（人物/面板/情节的用法）：每类注入一次，固定。
- 预查目录：与作者消息里出现的名字数相关，与书长无关。

会变长的部分：
1. 情节视图的召回会变差，而不是变长。它固定 10 条一页，第 100 章时第 1 页只剩最近 10 条，c03（重生）、c05（契约）这类奠基性变更会掉出第一页；写手要么再翻页（页数 = 总变更数 / 10，线性增长），要么改用 query 检索。也就是说，只要 Agent 老老实实只读第 1 页，量是不变的，但会漏；要补全就得付随书长增长的代价。这是“量与书长无关”这句话最容易被误解的地方。
2. 检索命中：同一批关键词在 100 章后的命中更多。必须限定 top-N（比如每条查询 3 条、合计 400 字符），否则检索会成为唯一线性增长项。
3. “本章的计划变更”取法：如果只能靠 search 或逐页翻情节，那么每章都要扫描全书计划，成本随书长线性增长。这是写手上下文里最危险的一项，必须给“按章取变更”的专用读取。
4. tree()：条目数随书增长（11 → 几百），任何“每章都调 tree()”的流程都会线性增长；只能全书开头一次或按需。
5. 立绘图片：随书增长（每个形态一张），但只在需要看外表时按需读，不是每章都读。

结论：按上面的清单，第 5 章与第 100 章的单章上下文量级相同（约 1 万字符），前提是 (a) 计划变更按章取、(b) 检索限条数、(c) 不每章调 tree。缺了任一条，就会有随书长线性的项。

一、按影响排序的问题清单

【P0｜会让 Agent 写错账或写错章节】

1. 任意位置的状态读不到，只有“第 4 章开头”。
   现象：任务 2 记账完想复核“第 5 章开头余额是不是 150”；任务 4 写手要“第 5 章开头的苏天晴”，都只能拿第 4 章开头 + 自己算。
   影响：记账无法自校验（补丁写错也看不出来）；写手上下文可能带着旧值开写。这是所有问题里唯一会直接导致错的。
   建议：read 的位置参数必须支持任意“第 N 章开头/末尾”，且记账提交前能预览“本章末尾”。夹具只准备一个位置，正是这个缺口的证据。

2. 没有“按章取变更”的读取。
   记账要“本章计划中的变更”，写手要“本章计划变更”，两处都只能靠 search（只搜文字）或翻情节页（固定 10 条、从近到远）。
   影响：第 100 章时要么漏，要么线性增长；写手会在不知道本章要兑现什么的情况下开写。
   建议：read(变更, at: 第 N 章, 状态: 计划/已写) 或 search 支持“章 + 状态”过滤；情节视图补上章与状态参数（提案里作者界面有，Agent 视图没有）。

3. 没有新建条目/添加组件的写入工具。
   现象：白灵、黑狼怪人、怪人强化药A、观星者都需要新建；write.edit 的补丁只能“条目.命名空间.字段 操作 值”。我只能在报告里说“需新建”。
   影响：新角色永远进不了账，下一章写手查不到；只能靠 Agent 直接写作者文件（提案允许，但没有格式与校验）。
   建议：给 create(条目) 与“添加组件”的写入，并同样记创作修改；否则提案要明确写“第一版新条目只能作者手建”。

4. 三类变化没有落点：道具/持有、地点、知情。
   现象：买了强化药没地方存（面板只有神典石/关注者/任务）；公园被砸只能写进作者的主 MDX；风信子知道有另一个魔法少女，只能硬记成剧情变更。
   影响：Agent 每次都要自己发明塞法，不同章节会塞到不同地方，最后查不到。
   建议：第一版至少给自由命名空间一个明确说法（能不能用、怎么渲染），或者明确规定“这三类只记在变更描述里”。

5. 状态与主 MDX 的边界没有路由规则。
   现象：{character.外貌 = "……"} 既出现在主 MDX 的渲染行里，也出现在人物视图里。同一句“改一下眼睛颜色”，改字段（影响所有位置）和改 MDX（只改这一段）差别很大，而渲染上看不出该改哪个。
   影响：我差点在渲染文字上直接改字；如果系统把它当 MDX 文本 diff，设定就没改到。
   建议：渲染里明确标“这一段是字段引用，改它等于改字段”或者“这一段是作者文字”；编辑入口按路径路由。

6. lookup 与预查目录不带状态，数字类审查差点漏判。
   现象：预查目录只有名字/位置/描述/组件。任务 1 里“花 300 神典石”与账上 200 的冲突，只有去 read 面板才能发现；lookup(神典石) 返回“没找到”，但它是面板字段，与“新设定”不可区分。
   影响：这是最容易让 Agent 自信地给出错误审查的地方（不读面板就会说“金额没问题”）。
   建议：预查目录每个条目后附一行关键状态（“面板：神典石 200”）；lookup 的未命中要区分“没有这个条目”和“它是某组件的字段”；lookup 索引组件字段名。

【P1｜会让结果质量下降】

7. 字符串只能整值覆盖，没有局部替换。
   改“金色眼眸→碧色眼眸”必须抄整串；抄错一个字就是静默的设定破坏。提案说“长文本用文本 diff”，但没说什么算长文本；外貌这种一句话的字段落在缝里。
   建议：字段支持“替换 'A' → 'B'”，或者明确规定“带引号的多句字符串一律走 diff”。

8. 出处没有“细纲/作者消息”这类凭证。
   计划变更来自细纲，作者口头指令（“从第 5 章开始剪短”）来自对话，两者都不属于“正文段落/手记段落”。我写“细纲（第 4 章）”“作者消息（手记未编号）”都是自造格式。
   建议：出处增加“细纲/章计划/作者消息”，并给一个稳定的引用 id。

9. “讲于”一个字段担两件事。
   c01 出处是正文 1.15（第 1 章讲的），讲于却是“前史”；ch4-h1 发生在半年前、讲于第 4 章。写的时候要反复确认“讲于”到底指发生还是指讲述。
   建议：拆成“发生时间”和“讲于（讲述位置）”，或者把规则写成明确一句话。

10. 计划与兑现没有连接，悬案也没有状态。
    工具里没有“兑现 cNN”的操作；第 4 章章末风信子还被抓着，所有变更都是“已写”，但故事没收束。
    建议：变更加“兑现/未收束”标记，或者连接里允许“兑现 <计划编号>”。

11. 字段值里混作者备注。
    风信子真名 = “南小风（第 4 章揭晓）”；面板流水里也有“（创作修改：作者设定契约时的启动资金，第 4 章才在正文交代）”。带值渲染会原样给 Agent，写手会把它当名字/当前值。
    建议：备注有独立字段（计划、备注），渲染只给值。

12. 情节视图固定 10 条，靠“从近到远”排序。
    第 100 章时 c03/c05 这类奠基变更掉出第 1 页；要么翻页（线性增长），要么漏。
    建议：情节视图给“按章、按剧情线、按状态”的过滤（作者界面已有），或者给“本章相关 + 最近 N 条”的混合视图。

13. 正文不能检索。
    审吃书必须通读第 1–3 章；第 100 章时不可能。search 只查日志和条目文字。
    建议：search 支持章/正文过滤，或提供 read(第 N 章, 段范围)。

【P2｜体验细节】

14. 渲染结果本身不带位置。read 的返回以值为主，粘到上下文里之后，Agent 无法判断这是第几章的渲染（我在报告里靠文件名区分）。
15. 列表用索引路径（panel.任务[0]）打补丁，插入/删除会让索引错位；用名字或 id 更稳。
16. 计算字段 {表达式 = 值} 在这批夹具里一次都没出现，无法检验“只读、要改就改依赖字段”这条规则；建议审查时补一个例子。
17. 提醒只讲组件怎么用，没讲“什么时候该先读哪个视图”；预查目录也没有“建议读哪个组件”。第一版可以接受，条目多了会浪费轮次。
18. 图片只给路径，改外貌时无法判断立绘是否已经不一致；道具/场景图同理。

二、带值渲染 {路径 = 值} 用起来怎样

总体可行，方向对：路径让人一眼知道“这是状态、能打补丁”，主 MDX 里用引用（{panel.神典石}）而不是写死数字，余额一改，主视图跟着变，这一点在任务 2 里直接帮了忙——我只需要记 −50，不用改任何文字。

具体问题：
1. 同一值有两个入口（主 MDX 行 + Component 视图），且渲染上看不出哪个是权威。任务 3 的三条消息里，两条都撞在这个问题上。
2. 字符串整值覆盖：外貌、说话方式这种带中文引号的长串，整值抄写风险高；局部替换缺失。
3. 值里混备注：真名成了“南小风（第 4 章揭晓）”，面板流水里混了创作修改的说明。说明“= 值”这一侧必须是纯值，备注走别的字段。
4. 列表索引路径（panel.任务[2]）会随插入/删除错位；改任务状态时我犹豫过要不要按索引写。
5. 图片只给路径，视觉信息要另外读图；这本身合理，但写手上下文里如果不读图，描写会和图不一致。
6. 渲染不带位置、不带“此后被哪条变更改过”。改初值前要查“有没有后续变更动过这个字段”，只能靠 search（任务 3 工具调用 3）；真实系统应该在值旁边标出来，否则改初值的检查会被跳过。
7. 计算字段只读的规则没有样本，无法验证还原性（去掉 “= 值” 是不是源文）；任务 3 里我删除整句（含表达式）时，靠的是人判断“这句是 MDX 文字不是字段”，系统能不能正确对应回源文，夹具给不了答案。
8. 还原性本身：我删掉“目前有 {panel.神典石 = 200} 神典石”这半句时，源文是“目前有 {panel.神典石} 神典石”。如果 Agent 只删了渲染出来的“= 200”那一段，源文会变成什么？没有规则说明。建议补一条“删除渲染值的操作一律视为删除整个表达式”或明确禁止。

三、剧情变更与创作修改分得清分不清

分得清的部分：
- 有明确时间点的（“从第 5 章开始剪短发”）→ 剧情变更（计划）。
- 有明确“写错了/改正”措辞的（“正文写的是碧色，改一下”）→ 创作修改。
- 纯排版去重（“面板里有了，不用重复”）→ 创作修改。
任务 3 的三条消息，我都是几秒内就能归类，说明这个二分在实践中够用。

分不清的部分（都要求 Agent 追问或按措辞猜）：
1. 没有时间标记的“改一下”。作者说“眼睛改成碧色”，可能是改正，也可能是她化形/变身导致的变化；同一句话两种归类，影响面完全不同（一个改全书，一个从某章起）。
2. “从第 N 章开始”但没有事件。剪头发是我按“她剪了”理解的；如果作者的意思是“设定从第 5 章起改成短发”，那它是创作修改，而且第 1–4 章要保留长发——这时候“创作修改”这个词本身也不够，需要“设定分叉”。提案里没有这个概念。
3. 删除类：删掉重复的余额句是排版；但如果作者删它是因为“余额写错了”，背后可能有一条漏记的剧情变更。
4. 初值与变更的混用：作者眼里的“改第 4 章那个值”，在系统里是改初值（影响所有位置）。提案要求改初值时列出后续改过同一字段的变更，但 write.edit 的格式里没有这个提示位，Agent 容易直接写。
5. 角色知道的事：既不是世界变化，也不是设定修改；第一版没有知情字段，只能塞成剧情变更或者丢在正文里（任务 2 的 ch4-10）。
6. 作者在界面上的操作（提案说界面会问“变化还是改正”）：Agent 这一侧没有对应的询问机制，只能从措辞推断。建议 write 时强制填一句“为什么归这类”，并在拿不准时直接问作者。

结论：二分法在“作者说得清楚”时好用；真正需要补的是三件事——(a) 无时间标记时的追问/默认规则，(b) 设定分叉（从第 N 章起不同的设定）这个第三类，(c) 知情这类知识变化的落点。这三件事不解决，Agent 会在边界上静默选一个，而选错的方向都是全局性的。
