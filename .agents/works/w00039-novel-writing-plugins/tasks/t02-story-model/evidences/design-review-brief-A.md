## 重点

1. 一条日志同时承担真相、计划与经历：计划中的变更与已写的变更混在一起时，状态计算、记账时判断“兑现”、检索会不会互相污染；计划被改写、删掉、提前或推后时，日志与状态怎么变。
2. 第一版按“讲于”排序加前史：补叙章、同一章里几个时间点、前史内部的先后，状态会不会算错（举出具体的书里的情形）；以后切到故事时间（t04）与世界线时，现在的数据能不能平滑过去，还是要重写。
3. 改过去：改初值、改某条变更、在中间插一条；后面状态重算、核对点、文本三方合并冲突怎么处理，结果是否确定；作者改的是“第 N 章时的值”时，系统如何决定是改初值、改某条变更还是新加变更。
4. 剧情变更与创作修改的区分：谁判断、判断错了的后果、能不能事后改类；两者对“第 N 章的状态”的影响是否在所有情况下都说得清。
5. Component 的生命周期：增删、schema 变化、命名空间冲突、自由命名空间；“情节”这类不存数据的视图型 Component 与日志的关系；主 MDX 引用其他条目的数据时的依赖与失效。
6. 渲染：MDX 怎样做到沙箱、纯函数；带值渲染 `{路径 = 值}` 能否做到可还原（开发者要求专门查：列出还原失败的具体写法，例如同一个值出现两次、表达式、条件分支、Agent 改了值又改了周围文字）；作者文字里的 `{`、`<`。
7. 与 nb-memory（双时间轴、带失效区间的状态、fail-closed）、nb-history（操作日志、审阅收件箱）、nb-story（V9）的重叠：有没有该复用而没复用的，有没有重复造了一套。
8. Agent 工具与提醒：五个工具够不够完成提案里的场景（审查细纲、记账、写手上下文）；提醒的去重要 harness 记哪些状态，现有 harness 是否支持。

## 审查维度

1. 与已定设计一致：开发者的决定逐条覆盖，没有悄悄改变已定项。
2. 依赖的机制真的存在：方案依赖现有机制的顺序、时序或寿命保证时，读该机制的 Spec 或实现确认，不按名字推断。
3. 接口与合同：类型与语义一致；失败有通道；后续切片照字面实现会不会返工。
4. 遗漏：失败路径、并发（作者与 Agent 同时改）、兼容与迁移。
5. 对照需求与参照：对照开发者的决定与旧应用（WorldEngine、剧情工坊）的能力，列出参照有、提案没有的项，并判断是否该有。
6. 验收映射：提案的每个主张以后能不能写成可测的判据。
7. 别扭与反常之处：和普遍做法（事件溯源、双时态数据库、CMS、游戏 ECS、同类写作工具）不一样的地方，以及要绕一下才说得通的地方，判断是有理由的取舍还是能优化，给出改法。
8. 上游选择：方案在迁就的更底层选择（例如 MDX、按讲于排序、Component 不存数据），查它的理由现在是否成立；不成立的把“改上游”列为问题并给出代价。
