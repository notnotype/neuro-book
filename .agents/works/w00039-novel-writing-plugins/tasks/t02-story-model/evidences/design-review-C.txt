### 1. 渲染层选 MDX：没有记录的理由，且“MDX、沙箱、表达式”三者互相矛盾
- 方向：Q1、Q2、Q4
- 严重程度：重要；类别：接口
- 位置：提案“四、方案”的第 1 小节（第 96 行起）、第 2 小节、第 6 小节（第 206 至 226 行）；待定项 11
- 现象：
  - 全仓库（除本提案与 w00039 的文档外）没有任何 MDX 的使用或决定记录。`adrs: []`，决策记录里没有一条说“为什么是 MDX”。Work README 的决定表只写了“主 MDX”这个词。
  - 提案第 209 行说渲染“不能 import 任意模块，不能读写文件，不能联网；只能用表达式和少数内置标签”。真正的 MDX（@mdx-js）里 `{...}` 是任意 JS 表达式，编译产物要执行。“不能 import”挡不住 `{(()=>{while(1);})()}` 这类死循环，也挡不住访问全局对象。要真的做到安全，只能自己对表达式做 AST 白名单，那就已经不是 MDX，而是自定义模板语言。
  - “表达式”到底是什么语言，提案没定义。待定项 10（年龄、历法）和第 5 节“计算字段”都依赖它。
  - 调研第 389、409 行（作者领域分析第八节）曾明确建议“只允许引用路径，不允许表达式”，理由是“模板变成一门编程语言，Agent 会写错，沙箱、调试、报错都是成本”。提案悄悄绕回了表达式，没有解释为什么上次的理由不再成立。
  - 带值写法 `{panel.魔力 = 3110}`（第 217 行）在 JS 里是赋值表达式，不是合法的只读求值。它是一个另造的协议，不是 MDX。
  - 与已实现的 Markdown 方言冲突：workspace/markdown-dialect（status: implemented）把 `<comment>`、`<span style=>`、`<ruby>`、`<html>` 当方言，自动链接 `<https://…>` 是合法写法。真 MDX 把 `<` 开头的都当 JSX，自动链接在 MDX 里是语法错误。nb-markdown 的编解码器、往返规则、提示词编辑器的“文字是唯一真相”（ui/prompt-editor）都建立在这个方言上，提案一次也没提到 nb-markdown。
- 为什么是问题：最底层的选择（用 MDX）没有记录理由，上面的沙箱、转义（第 210 行）、还原（第 225 行）、作者编辑器全是在给这个选择打补丁。作者文字里 `{`、`<` 要转义，等于把已有的作者文件格式（Markdown 方言）变成另一种格式。
- 如何核实：读 docs/specs/workspace/markdown-dialect.md 输出 9、25 和自动链接一行（第 82 行）；对一段含 `<https://x.cn>` 的文字跑 @mdx-js/mdx 的 compile，会报语法错。
- 建议：
  1. 先回答“为什么不是现有的 Markdown 方言加一小块插值语法”。nb-markdown 已有语言扩展点（MarkdownSyntax）、行内小块（InlineChip）和往返保证，正好是“引用字段的小块”需要的。
  2. 如果确实要模板：定一门只含“路径引用、少数内置标签、可能的几个纯函数”的语言，写成 ADR；不叫 MDX，也不用 MDX 的编译器。业界常规是逻辑极少的模板（Mustache/Liquid 一类，凭记忆）加白名单函数。
  3. 要求提案先把“表达式”的文法写出来（哪怕只有路径与四则运算），否则沙箱和 Agent 能否写对都无法评估。

### 2. 主 MDX 与长文本用“文本 diff 加三方合并”：理由没有记录，有更简单的做法，两个写者改同一份文本的语义也没定
- 方向：Q1、Q2、Q3
- 严重程度：重要；类别：接口、不变量
- 位置：第 160 至 165 行（补丁种类、改过去）；第 307 行备选表；第 118、154 行
- 现象：
  - 备选表第 307 行“主 MDX 只有创作修改，不随剧情改：否决（开发者 11-01）：理由：MDX 也能打补丁，文本 diff 用三方合并”。这只是决定本身，不是理由。Work README 决定表对应一行也只有结论。查不到理由，就是“没有记录的理由”。
  - 作者领域分析第 363 行曾给出更简单的做法：会变的描述“写成带章节的段落（第 30 章起：……），渲染时按章挑出成立的那段”。换成整段赋值（某个字段在第 N 章起变成新的完整文本）也比 diff 简单：没有合并问题，旧值保留下来就能显示 diff。
  - 三方合并要解决的是“初值被改了，后面的 diff 还能套上”。提案自己在第 165 行承认：“程序看不出语义上的过时（初值改成银发，第 30 章那条剪成黑色短发还写着黑色）”。也就是说合并只解决了机械冲突，没有解决真正的难题，却引入了合并算法、冲突界面、Agent 提合并写法这一整条功能链。没有任何数据说明作者会频繁改初值而不是追加一段。
  - 同一份主 MDX 有两条写入路径：作者在界面改（创作修改，改初值）与剧情变更打补丁。作者在“第 30 章末尾”的渲染视图上编辑主 MDX 时，这次编辑是改初值，还是在第 30 章加一条 diff？提案第 154 行说“界面要问”。第 225 行又说 Agent 可以直接在渲染结果上改主 MDX，“系统把改动对应回源文”，却没说对应成哪一种。这个二选一决定了后面所有位置的显示，不是界面细节。
- 为什么是问题：它是整个方案里实现成本最高、风险最大的一块，而且建立在没有记录理由的决定上。
- 如何核实：读第 307 行和 Work README 决定表 2026-11-01 第 4 行；对照作者领域分析第 363 行。
- 建议：
  1. 第一版文本字段按“位置起整段替换”存，diff 只用来显示；主 MDX 里随剧情变化的文字用状态字段加模板引用（`{character.appearance}`），主 MDX 本身只由创作修改改。这样三方合并整块可以删掉，等有证据再加。
  2. 如果保留文本 diff：先写清渲染视图上的编辑固定落成哪一种，以及补丁套不上时的状态（该条变更标记为“失效”，其后的值是否照算）。
  3. 业界参照（凭记忆）：Novelcrafter 的 Codex progression 是在场景上追加一段说明，不是 diff。

### 3. 位置与排序模型会锁死数据格式：讲于存序号还是稳定编号没定，同章内顺序没有显式的键，补丁又不满足交换律
- 方向：Q4
- 严重程度：重要；类别：不变量、接口
- 位置：第 124 至 144 行（字段表、排序）；第 158 行；第 246、259 行（位置参数）；对照 docs/specs/workspace/folder-kinds.md 第 55 行
- 现象：
  - 排序规则是“按讲于的章序排；同一章里按出处的段落顺序排；前史内部按作者给的先后排”。已实现的 Spec（folder-kinds 第 55 行）规定章节的稳定身份是五位编号，不是序号。作者在写作过程中调整章序、插入新章、删章是常态。提案的“讲于”字段存什么没说：存序号，则调章序后全书所有变更的位置漂移；存编号，则需要一张编号到序号的映射，每次比较都要查。
  - 同一章里按“出处的段落顺序”排，但计划中的变更、界面操作产生的变更、前史的变更都没有段落出处（字段表第 129 行写出处可以是“界面操作”）。这些变更和同章有出处的变更怎么比，没有规则。出处的段落号在改稿后又会漂移（t22 才讨论），所以它不适合当排序键。
  - 补丁里同时有赋值（`= 女`）和加减（`-= 90`），两者不满足交换律。顺序一错，折叠结果就变。提案第 163 行承认插入中间会让后面重算，但顺序本身必须是全序、稳定、可存储的。
  - 提案还把“位置”做成枚举（章开头、章末尾、按计划，第 208 行），工具参数 `at` 也是这样。以后加世界线、故事时间（t04），所有调用点都要改。
- 为什么是问题：这是数据格式里改起来最贵的地方。每一条存下来的变更、每份章级快照（第 166 行）、每个核对点都依赖它。
- 建议：
  1. 日志里每条变更存一个显式的、与出处无关的排序键（例如分数索引或可重排的序列号）；“讲于”存章节稳定编号，章序由活页夹清单即时给出。
  2. 把“位置”定义成一个不透明的坐标类型，只由一个模块提供比较和序列化；工具、快照、核对点都只经过它。第一版的实现是“章序加章内序”，以后换成带世界线的坐标不用改调用方。
  3. 在提案里写明：同一位置上的两条变更，赋值与加减的先后由排序键决定，不由出处。

### 4. “事件溯源”只覆盖了一半：初值是可原地修改的快照，创作修改不在可重放的日志里，路径寻址的补丁和追加式日志冲突
- 方向：Q1、Q4
- 严重程度：重要；类别：不变量
- 位置：第 98、146 至 154、158、164 至 165 行；待定项 2、6
- 现象：
  - “状态 = 初值加前面所有已写变更的补丁”，初值“由创作修改设定”，创作修改“只记什么时候、谁改的、为什么”（第 151 行）。也就是说初值是一份会被原地改写的基线，它的变迁不进入可重放的日志，只靠 nb-history 的文件历史（待定项 2 还没定）留痕。开发者的决定是“骨架用事件溯源”，实际只有剧情变更是事件。
  - 后果：任何一个核对点是对着“当时的基线”记下的，基线一改，旧核对点的意义就变了；“第 5 章写的时候这本书是什么样”无法重现。nb-memory 的做法是 tick 轴（叙事推进序）和事务轴并列，提案只借了其中一轴。
  - 补丁用 `星瑕.panel.魔力` 这样的路径寻址（条目、命名空间、字段）。待定项 6 的推荐是“schema 改字段名时生成一条创作修改，把旧数据迁过去”。但日志是追加式的，旧补丁的路径里还写着旧字段名；要么改写历史事件（违反追加式），要么另有升级层（事件溯源的常规做法是读取时做 upcasting，凭记忆，Greg Young 的事件版本化文章），提案没有。
  - 同样，“Agent 可以直接写作者的文件”（第 154、319 行）：如果条目的主 MDX 或初值落在文件里，Agent 的直接写入绕开了日志，没有描述也没有出处，与目标 3“每一处变化都有描述和出处”矛盾，提案用“靠修改历史与作者审阅兜底”带过。
- 建议：
  1. 明确说“日志里是剧情变更，创作修改是基线的审计记录”，或者把创作修改也做成日志事件（带前后值），让整个状态可重放。两者都行，但要选。
  2. 路径用条目 id 与字段 id 寻址，字段改名通过 id 不变来解决；schema 变化用读取时升级，不改写历史。
  3. 在存储（t09）决定之前，先写下“哪些写入口会绕过日志”以及每个绕过口怎么补记。

### 5. 比较基线是稻草人，现有系统的重叠没有讲清：nb-story 已经在做“按章抽取加数值核对”，nb-memory 的拒绝理由针对的不是它要借的部分，`*.content/` 条目树也没有对照
- 方向：Q1、Q2
- 严重程度：重要；类别：遗漏
- 位置：第 40 至 46 行（三种朴素做法）；第 77 至 84 行；待定项 3；第 334 行
- 现象：
  - “三种朴素做法”（一个文件夹、不可变 lorebook、lorebook 加模板引擎）是三个都不可能被认真选的基线。真正的对手没有出现：
    - **A. lorebook 加按章追加的变更说明**（Novelcrafter 的 Codex progression 一类，凭记忆）。作者面向的做法，不需要补丁语言、不需要三方合并。
    - **B. 让 nb-story 的抽取直接跑在作者自己写的章节上**。nb-story 已经产出情节、状态变动（带出处）、数值流水与核对（调研第 一 节、提案第 80 行自己也说“数值逐笔累加并与原文核对”），评测里前 4 章是 28 个对象、11 段情节、12 条状态变动。作者侧需要增加的只是“设定与计划”两层。开发者 10-31 决定先不合并，这条应保留；但提案没有说明“记账”这一步与 nb-story 的抽取在流水线、出处地址、核对规则上共享什么，结果是同一类规则（“角色说的想的不算世界的变化”第 271 行、数值核对第 162 行）要写第二遍。
  - 待定项 3 拒绝直接依赖 nb-memory，理由是“每批写入都要把主体注册表全量放进上下文做消解，书长了会超”。README 确认这一点属实（“消解在写入时完成：注册表全量进上下文”）。但这是它的摄入流程；提案要借的是状态带失效区间和双时间轴。这两样可以只复用存储层、完全不用它的 LLM 消解，README 也写明“消解是增强不是闸门”。理由和被拒绝的对象不对应。
  - 条目树：folder-kinds 已实现 `*.content/` 内容文件夹（子目录是内容节点，正文是 `index.md`，清单管顺序和展示名）。提案的“条目树”是另一棵树，第 334 行只说“随存储一起定”。如果条目树就是 `lorebook.content/`，那么“作者不直接编辑文件夹”这个决定让 folder-kinds 里这一类的投入变成了只给 Agent 用的格式；如果不是，就是多了一棵树。这个问题影响模型（条目 id、位置），不只是存储。
  - 仓库里会有三套“按章排序的事实与状态”的实现（nb-story、nb-memory、本提案）。合并推迟是开发者的决定，但提案应当至少说清共享的最小面（出处地址格式、章节坐标、数值核对规则），免得合并时三套各有一种格式。
- 建议：在“备选方案”里补 A、B 两条，写出各自缺什么，并说清为什么要新建而不是在 nb-story 上加一层作者层；把待定项 3 的理由改成针对存储与状态层的比较；条目树与 `*.content/` 的关系提到模型层回答。

### 6. 核对点只“报”不“修”，没有消除 broken-relative 的根因，只是改成了永远报警
- 方向：Q1
- 严重程度：重要；类别：遗漏
- 位置：第 162 行；调研 repo-survey 第 五 节第 3 点
- 现象：提案说核对点“替代了旧版 broken-relative 那种断掉的失败方式”。但旧版问题的根因是“相对操作依赖前面全部状态，补写过去后链条不成立”。新方案保留了全部相对操作（`-= 90`），只是在对不上时多报一条。没有写：
  - 对不上之后，作者的修复动作是什么（插一条校正变更？把核对点当作新的绝对值重置？改旧变更？）；
  - 报警期间，面板显示哪个数（累加值，还是正文里写的数）；
  - 一次错误之后，后面每个核对点会不会连环报警。
  - 业界对“累加加断言”这件事有成熟做法：Beancount 的 `balance` 断言（凭记忆）失败时报错，并要求用户插入一条调整分录，断言本身不改数。提案可以直接借来：核对点失败等于待处理项，处理方式是插入一条带描述的校正变更。
- 如何核实：读第 162 行；找提案里“核对点”出现的所有位置（第 162、196、268 行），没有一处写失败后的流程。
- 建议：补一小节“核对失败的处理”，把校正变更定为唯一的修复路径，并说明显示规则。

### 7. 给 Agent 的问题和证据对不上，也没有记账准确度的数据
- 方向：Q1
- 严重程度：建议；类别：文档、遗漏
- 位置：第 28 至 30 行；第 79 行；第 321 行
- 现象：
  - Agent 问题 2 的论据是 V9 评测里“把读者知道的当成角色知道的”最常见。但知情与秘密是第一版的非目标（第 61 行）。第一版只解决数值累加，提案没有给出“模型算不准数值”的证据。
  - 提案第 79 行引的评测结论里，有两条和方案方向相反：100 章以内读全文作答最准；用图作答的失分多是照搬了图里记错的内容。这支持“结构化记账一旦记错就会污染后面”，也就是方案依赖的正是评测显示最容易出错的那一步。提案把这个风险转给“作者审阅”，但没有给出每章要审的条数。

- 建议：把目标 4（“要读的量与书的长度无关”）和目标 2（“作者只审阅”）各配一条可量的验收：记账每章条数、作者审阅的耗时上限、漏记率与错记率；在没有数据前不要把“作者只管说话”写成已达成的目标。

  - Component 类型提供七项（命名空间与 schema、Vue Tab、文字视图、查询视图、计算字段、记账说明、用法说明）。第一版只有三个内置类型，其中“情节”不存数据，只是日志上的视图，它并不占命名空间。计算字段在第一版没有使用者（待定项 10 说年龄先当普通字段，历法不做）；“三类按数据位置分”里的第三类“自有数据加收集”第一版没有任何实例。
    这些抽象是为关系与地图预留的，开发者说过它们“只用来验证内核架构”（决定表 2026-11-01 第 11 行）。验证用的是纸面推演就够，不需要把接口里的槽位先做出来。
  - 变更的“连接”字段（在其后、接续、导致、动机、前提，第 132 行）：第一版没有任何消费者（剧情表只用讲于与剧情线）。nb-story 里它有消费者，这里没有。
  - 按章的状态快照缓存（第 166 行）：没有数据说明重算有多慢。粗估一部 500 章的书每章 20 条变更，一万条补丁；折叠几千条小补丁是毫秒级，文本 diff 的折叠可能慢些，但没有测量。先不做，等测到慢再加。
  - 自由命名空间（待定项 7，推荐要）：与第 2 节“状态按命名空间分块、每块有 schema”相矛盾，等于给无 schema 数据开了后门，以后迁移与检查都要绕开它。作者要随手记，用主 MDX 或手记即可。
  - 故事时间字段“先留空”（第 134 行）：保留一个永远为空的字段属于预留，要么删，要么在“位置”坐标里统一预留（见第 3 条）。
- 建议：第一版只实现用到的槽位（schema、Vue Tab、文字视图、查询视图），其余在需要时加；快照缓存与自由命名空间先去掉；连接字段推迟到有消费者。

### 9. Component 的接口“第一版只给内置，以后开放”与 ADR 0027 的原则相反，也没有说明挂在插件平台的哪里
- 方向：Q4
- 严重程度：建议；类别：接口
- 位置：第 64 行、第 316 行；ADR 0027、0030；Spec runtime/plugin-api
- 现象：
  - ADR 0027 决定内置插件与第三方插件能力相同、使用同一套贡献点，没有“内置专用接口”。提案第 316 行说“Component 类型的接口第一版只给内置类型用，以后开放给插件”。先给内置用一套、以后再改成开放，容易让接口被三个内置类型的需要定形，开放时又要改一遍。反过来，如果 Component 类型一开始就是一个贡献点（ADR 0026 的“定义写成常量”），内置的三种就是第一批实现，开放时不用改接口。
  - 提案 `adrs: []`，全文没有一处写这套东西属于哪个包、哪些部分在后端、哪些在浏览器、用哪个贡献点登记 Vue Tab 与 Agent 工具。“发布与回滚”一节只有一句“作为新插件发布”。ADR 0030 要求内核与应用无关、作者材料留在应用包，这些落点影响 Component 的合同，应在模型层先定。
- 建议：先用贡献点的形态设计 Component 类型（哪怕只登记三个内置），在提案里写清包与进程的落点。

### 10. 该讲的架构取舍没讲，细节占了大头
- 方向：Q5
- 严重程度：建议；类别：文档
- 位置：全文；第 7、8 节；第 211 至 226 行
- 现象：
  - 写得很细的部分：Agent 工具名与参数、悬停显示路径、立绘按形态各存一张、情节 Tab 的“问一句”、`{路径 = 值}` 的写法示例、记账的审阅粒度。这些是 Spec 或 Task 的内容，而且很多自己也标了“以后再定”。
  - 没讲的取舍，每一项都会改变数据与接口：
    1. **谁拥有日志**：单写者还是多写者。作者、Agent、多个会话同时往一本书的日志追加；nb-history 的已知限制 1 是“单进程单写者”，提案借用它（待定项 2）时必须面对这条。
    2. **折叠在哪一端做**：后端算好再给界面和 Agent，还是前端也算？渲染需要“在浏览器和 Agent 工具里得到同一个结果”（第 207 行），两端都要用同一份渲染代码，这决定包的依赖方向。
    3. **读写分离**：日志是真相，状态与渲染是读模型；写入如何校验（schema 校验在写时还是读时）。
    4. **失败语义**：补丁套不上、引用悬空、渲染出错时，状态与界面的行为（第 210 行只写了解析失败显示源码）。
    5. **带值渲染是不是一个协议**：它既是显示格式，又是 Agent 的写入入口（第 225 行），这是双向的接口，应当独立成一小节，写清哪些写法可逆、不可逆时怎么办。
  - 其中第 1 到 4 点没有出现在“备选方案与取舍”表里（第 298 至 311 行），那张表里的行基本是对开发者已决定事项的复述（9 行里有 6 行写着“开发者 11-01”）。
- 建议：把备选表改成真正的取舍表，增加“日志的所有权与并发”“渲染运行位置”“失败语义”三行；工具参数与界面细节移到 Task 或后续 Spec。

## 待定项逐项判断
1. 名字：无异议，但“法典”与 canon 对中文作者的含义（宗教、法律）可能引起误解，用户界面上用“设定集”之类的平常词更不容易误会。
2. 存储形态：先定模型再定存储合理，但第 3、4 条说明模型里有几处（位置坐标、日志所有权、创作修改是否进日志）必须先于存储定下来，否则存储的选择会反过来定形模型。nb-history 单进程单写者的限制也要在这里一并回答。
3. 与 nb-memory 的关系：结论（不直接依赖）可以接受，但理由要改成针对存储与状态层的比较，见第 5 条。
4. 剧情线和章要不要做成条目：同意做成条目，前提是章条目只引用活页夹的稳定编号，不复制章序，见第 3 条。
5. 马甲的做法：推荐子条目会把“身份同一”和“目录归属”两种关系压在一棵树上，而第 93 行刚说条目树不表示任何语义上的从属；与“只用来组织浏览”矛盾。建议用显式的身份同一关系，不靠树。
6. 去掉 Component、schema 变化：“数据保留隐藏”可以；“生成一条创作修改迁移旧数据”与追加式日志冲突，见第 4 条，改用 id 寻址加读取时升级。
7. 自由命名空间：建议第一版不做，见第 8 条与更正。
8. 记账结果怎么审阅：整章接受加逐条驳回合理，但要先补核对失败的处理（第 6 条）和每章条数的量级（第 7 条）。
9. 自动预查：精确匹配合理，成本低。需要补一句：别名冲突（两个条目同一别名）时全部列出，不择一。
10. 计算字段与历法：第一版不做是对的，同时应把第 5 节“计算字段”这一项从类型清单里去掉（第 8 条）。
11. 带值渲染能否可还原：这条不是“审查时查一查”的细节，而是个双向协议，需要独立成节；而且 `{路径 = 值}` 里值的写法不一致（`星瑕` 不加引号，`"黑色长发……"` 加引号，图片是 `图片 路径`），读回来要靠值类型猜，应先统一值的文法再谈还原。与第 1 条合并处理最省事。
