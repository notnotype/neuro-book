### 1. 就地改“累加字段默认改初值补差额”与核对点互相打架；来历是混合链时没有规则
- 严重程度：重要；类别：正确性
- 位置：第 4.8“就地改”第三条；第 4.5“核对点”与“改过去”
- 现象：作者在“第 30 章末尾”看到存款 39800，认为应是 41800，直接改。第 4.8 说默认“改初值，差多少补多少（开局多一万）”。但第 4.5 的核对点规则里，正文写明的数（例如第 4 章“余额 …”、第 12 章“还剩 …”）已经记成核对点；改初值会让这些早先已经对上的核对点全部对不上，它们被重算为不符，进待处理。也就是说，默认动作在作者眼里是“把一个数改对”，在系统里是“制造 N 个不符”。
- 为什么是问题：
  1. 同一个情形（某位置上的值不对）在两处给了相反的默认：核对点不符时默认“插一条校正变更”（4.5），就地改累加字段时默认“改初值”（4.8）。系统其实知道出错的区间：最后一个对得上的核对点与第一个对不上的核对点之间，必有一笔漏记或错记，应当默认建议“在这个区间插校正”，或至少在保存前那一行里写“会让第 4、12 章的核对点对不上”。第二版的保存前提示只写“将修改哪条记录”，不写下游后果。
  2. “来历”常是混合链：初值 + 第 20 章赋值 + 第 25、28 章加减。“给出这个值的记录”是哪一条？按 4.8 的四个例子没有对应：不是只有初值，不是单个赋值，也不是纯累加。最合理的是“最近一次赋值，其后的加减保持”，但提案没写；照字面写的实现者会按“有加减就改初值”，改了初值后第 20 章的赋值把它盖掉，作者看到保存成功、值却没变（与第一轮 B1“改完弹回去”同类）。
  3. 保存前一行是否列出“后面改过同一字段的变更”（4.5 要求列给作者）没有说清它与那一行的关系：是同一个确认，还是第二个确认？
- 如何核实：对照 4.5“核对点”三种处理与 4.8 第三条；构造 初值 41800（实际 40000 + 漏记 +1800）：第 4 章核对点 41800 对得上，第 12 章核对点 39800 对不上，作者在第 30 章改成 41800。按 4.8 改初值，第 4 章核对点变成不符。
- 建议：就地改累加字段时，系统先算“最近一个对得上与最早一个对不上的核对点”，把默认改成“在该区间补一笔校正”，改初值作为明确的第二选项并标出会让哪些核对点不符；4.8 补一句混合链的取值规则（最近一次赋值，加减保持）；保存前那一行同时写出下游后果（核对点与后面的赋值），只在有后果时才展开，见第 11 条。

### 2. 条目页做成“编辑器区的标签页”：现有 editor.pages 的约束与提案要的东西几乎相反，影响一节只写了一行
- 严重程度：重要；类别：接口
- 位置：第 4.8“条目页”；第五部分“平台与共享包要先做的”第一条；第六部分 editor.md
- 现象：影响一节写“编辑器贡献点：不按文件认领的文档（条目页）”。核对 docs/specs/workbench/editor.md：现有最接近的是页面贡献点 editor.pages（输出 33），它的合同是：每个页面 id 在窗口里只有一个标签（`open-page {id}` 已开着就切过去）；不进会话记录，刷新后不恢复；不能拆分、不能换编辑器；没有文档，不 dirty、没有光标与字数；`nbook.editor.open` 不接受页面地址；组件只收到 `{context: {recent}}`，没有参数。提案要的条目页是：每个条目一个标签、可以多开、可以并排（拆分）、刷新后要恢复（作者会期待重开项目还在原来的几个条目页）、有“保存前显示将修改哪条记录”的保存语义。
- 为什么是问题：缺的不是“一个不按文件认领的文档”，而是一整套虚拟资源模型：
  1. 地址与身份：标签、会话记录（editor.session 里标签存的是地址与编辑器 id）、面包屑、`nbook.editor/activeDocument`、同一条目在两个组里的“同一份文档”都以地址为键，条目需要自己的地址方案与改名/删除处理（条目删除留墓碑时，已打开的标签怎么办；输出 18 只讲文件被删）。
  2. 脏状态与保存：输出 12–16 的 dirty、输入回执、未裁决输入、磁盘冲突、关闭询问全是围绕“正文 + 磁盘基线”建的。条目页的草稿放哪？两个组里的两个同一条目标签是否共享草稿？保存时遇到版本冲突（Agent 同时改了这个条目，4.5 说读取带版本、写入过期报冲突）作者界面是什么，提案只写了 Agent 的一侧。
  3. 拆分：输出 2 的拆分是“两个组的视图共用一份文档”，页面标签明确不能拆分。提案要“可以多开、并排看”，等于改写页面的语义。
  4. 关闭、离开、终态页（输出 4、21、22）对有未保存草稿的条目页如何处理。
  另有一层不确定性：主 MDX 若在 t09 定为文件（待定项 2 的候选），则现有 `editor.editors` 的 selector 已能认领它，只缺条目页的多 Tab 外壳；若不是文件，才需要新模型。提案把“条目没有文件”当作前提，但存储是待定项，前提不成立时这一节的方案选择会变，应在“影响”里写成依赖 t09 的条件。
- 如何核实：editor.md 输出 33、2、5、12–16、22；`editor.pages` 的 `open-page {id}`。
- 建议：把“条目页”从一行提升为一节前置设计：先在 editor.md 层面定“带参数的页面”或“虚拟资源”（地址方案、会话恢复、拆分共享状态、草稿与保存、墓碑），再估平台工作量；在影响里注明这件事与 t09 的先后。

### 3. 改设定后“采用”正文替换，会自己造出“出处失联”和“可能过期”，还会与已打开的章节文档冲突
- 严重程度：重要；类别：正确性
- 位置：第 4.8“改设定以后”第 3 步；“出处”一段；第 4.5 修订
- 现象：银白改成淡金色后，正文第 1 章写着“银白的长发披在肩上”，这句同时是记账时登记的出处原句（4.8“出处：正文出处存章加原句”）。作者在第 3 步点“采用”，正文改成“淡金色的长发……”。
- 为什么是问题：
  1. 出处存的是“章加原句”，改过正文以后“按原句重新定位，找不到就标出处失联”。采用本身就把原句改掉了，于是登记着这句话的那条变更立即变成“出处失联”，进待处理。协助越成功，待处理越多。除非采用时同步更新相关讲述的原句，提案没写这一步。
  2. “一章的正文在记账后改过，这章的账标可能过期”：采用修改了第 1 章正文，这一章就整章标“可能过期”；第一版的补救是“整章撤销后重记”。改设定协助的每一次采用，都让所涉及的章触发这个流程。
  3. “采用的每一处都是一次修订，可以还原”：正文是文件，不属于世界模型的修订（第 3 节：nb-history 只管文件层面历史，改动记录管世界模型）。这里的“修订”是哪一套？还原走哪一套？
  4. 正文章节可能在编辑器里已打开且未保存。世界引擎插件写文件，对编辑器是“外部来源的变化”：按 editor.md 输出 16，dirty 的文档只标“磁盘已变化”，作者下次保存得到磁盘冲突。协助的“采用”应经编辑器的文档协调（或直接在已打开文档里改），提案没提这条路径。
- 如何核实：对照 4.8“出处”一段与“改设定以后”第 3 步；editor.md 输出 16。
- 建议：规定采用时的联动：同步更新对应讲述的原句；采用产生的正文改动标注“来自设定协助”，不触发“可能过期”（或只在改动涉及已记账的事实时才触发）；写明采用经编辑器文档（已打开则改文档，不直接写盘）；“可以还原”落到 nb-history 的文件层面，不要说成世界模型的修订。

### 4. 改设定协助：几十处候选时没有排序、批量、静音与触发条件；第 1 步和第 2 步对近义词的说法互相矛盾
- 严重程度：重要；类别：体验
- 位置：第 4.8“改设定以后”三步
- 现象：以“金色”在前 4 章出现 18 次为例（金色十字星、金毛狐狐……真正指她发色的只有几处）。提案只写了“每条有原句、建议的改法和理由；采用、自己改、不改；字面替换的可以一起采用”。
- 为什么是问题：
  1. 排序与分组没定：按章顺序？按 Agent 的把握？字面相同的合并成一组？“字面替换的可以一起采用”之前，谁判断哪些是“字面替换”？18 条里 14 条是“金色十字星”，合理的呈现是按匹配上下文分组（“金色十字星”14 处全部不改，一次处理），而不是 18 张卡片。
  2. “不改”没有记忆：下次再改设定、或同一次协助重新运行，“金色十字星”会再次出现。没有“对这个短语不再提示”的落点（挂在哪：条目？全书？）。
  3. 触发条件没定：每次创作修改都触发吗？改一个数值字段（存款初值）也要搜“41800”吗？改名字、改别名呢？Agent 自己做的创作修改触发吗？没有范围，就等于每次保存后都会弹出一批候选。
  4. “不挡写作”只落到“留在待处理里”。待处理同时装着记账问题、冲突、出处失联（第 8 条），18 张候选卡片进去后，“作者每章要处理的待处理条数”（目标里要量的指标）被稀释，也会淹没真正需要拍板的冲突。候选应有自己的类别与独立计数。
  5. 第 1 步写“按旧值搜索”（关键词），第 2 步却要“换了说法的也找出来（‘那抹银色’）”。关键词搜索永远找不到“那抹银色”；要找得到，只能把涉及该条目的章节整章交给 Agent，这与“只把候选段落交给 Agent，不通读全书”相反，成本也与“成本”一节声称的量级对不上（第五部分：“改设定后的正文协助只把候选段落交给模型”）。第一版检索是关键词（第五部分“成本”），语义检索不在范围内。要么删掉近义词承诺，要么写明成本。
- 如何核实：第 4.8“改设定以后”与第五部分“成本”并读；用“银白”在样本书前 4 章做一次关键词搜索，看命中里指发色的占比。
- 建议：候选按“匹配上下文”分组、组内批量；每组有“全部不改（记住）”；写明触发范围（只对 Agent 读得到并在正文里重述的字段，数值字段默认不触发）；候选单列一类，不混入待处理的计数；近义词承诺降为“第一版只做字面与别名，语义留给检索有嵌入服务之后”。

### 5. 主 MDX 在渲染视图里编辑：提案把它写成“新增 MDX 的读写”一行，实际是另做一套与项目方言不同的编解码器；方言里作者习惯的写法在 MDX 下有的报错、有的静默变意思、有的不被白名单放行
- 严重程度：重要；类别：遗漏
- 位置：第 4.8“条目页”最后一条；第 4.7“条目里的 MDX 是项目数据”白名单；第五部分第三条；第 4.11“渲染用项目 Markdown 方言”那一行
- 现象：第五部分写“批注与文字颜色和项目方言对应。nb-markdown 现在只有 Markdown 方言，要新增 MDX 的读写”。工作量被说成“新增读写”，风险没写。我核对了 nb-markdown 与 markdown-dialect.md，并用 MDX 3.1.1 默认选项（无 remark-gfm）编译了一批方言写法（/tmp/review-b2-probe/p.mjs）：
  - 项目方言认的、MDX 不认：`他说：**“走吧。”**然后离开。`在方言里“走吧。”是粗体（输出 6，CJK 友好的强调）；MDX 编译通过，但星号原样留在文字里，不成粗体。同样的 `==高亮==` 留成字面；GFM 表格 `| a | b |`、任务列表 `- [ ] 事项`、脚注 `[^1]` 都留成普通文字（`> [!WARNING]` 只是引用块，不是提示块）。同一个作者在章节（.md，方言）里写粗体引号是粗体，在条目的主 MDX 里写同样的字是星号，且没有任何报错。
  - 方言明确“不转义也能读”的写法，MDX 报错：方言输出 4 规定 `a < b`、`5*3=15` 原样写出，不转义；实测 `HP<10` 在 MDX 下编译失败（`<` 后面跟数字）。`a < b` 倒能过。也就是说方言的“最小转义”规则（输出 4，293 行的 escape.ts 与整套“读得回来”保证）不能复用，转义集合要重推。
  - 方言用 HTML 标签表达的格式，白名单不放行：第 4.7 白名单“标签只有内置的几个：条目引用、图片，以及项目方言的批注与文字颜色”。方言的 `<mark>`（高亮的规范写法，输出 24）、`<sup>`/`<sub>`（输出 15）、`<br>`（硬换行，输出 5）、`<ruby>`（输出 12）、`<align>`、`<bilingual>`、`<strong>`/`<em>`（输出 3 的写不出回退写法）都会被拒收。作者在富文本里点“高亮”或“上标”，编辑器写出的是 `<mark>`、`<sup>`，保存即被拒收。MDX 本身接受这些标签（实测 `<mark>`、`<sup>`、`<ruby text=…>` 都编译通过），是白名单挡的。
  - 方言的“认不出的语法原样保留”（输出 9：HTML 注释、数学公式、脚注定义、未知 HTML 原样块）在 MDX 里没有对应：认不出在 MDX 下是编译失败，不是原样保留。从章节复制一段含这些写法的文字进条目，要么报错要么变意思。
- 为什么是问题：
  1. “字段是小块、自动转义、批注与文字颜色对应”只是方言的一个子集。作者在主 MDX 里还会用粗体、列表、标题、引用、高亮等，需要一个明确的“主 MDX 允许的 Markdown 子集”，以及每一项在 MDX 下的读写与转义。现状是项目内两处编辑 Markdown，显示结果不同。
  2. 现有 nb-markdown 的语言与编解码器约 5800 行（language/ 目录，非测试），其中 codec 的读、写、转义、源码三份约 1700 行，是围绕 marked 与方言的“以块为单位写回、读得回来、未编辑字节不变”（输出 1–3）建的。MDX 的解析器（micromark-extension-mdx）对这些保证一个也不提供；未编辑字节不变在 MDX 下要自己做，第 4.7 的“按块解析”还要求一块出错只影响这一块，而 MDX 编译是整篇的。这个量级与已有的 markdown-dialect 同级，不是“新增读写”。
  3. 决定表写明开发者 11-02 的 MDX 是“主会话补‘作者的字由编辑器转义’，开发者未反对”，开发者是在不知道上面这些差异的情况下追认的；备选方案表里“代价：作者的编辑器要新做 MDX 的转义与往返”也没写量。
  4. nb-markdown 已有 `MarkdownSyntax` 扩展点与 InlineChip（行内小块），“字段是可点开的小块”的前一半可以复用；第 4.11 驳回“方言 + 一小块插值语法”的理由只有“MDX 表达力更强”，没有对上面这些代价做比较。这是第一轮 C 报告的质疑，第二版加了条件但没有量化。
- 如何核实：运行 /tmp/review-b2-probe/p.mjs（需 /tmp/mdx-probe 的依赖）；对照 markdown-dialect.md 输出 3、4、6、9、15、24。
- 建议：
  a. 在提案里列一张“主 MDX 允许的写法”表，逐项写 MDX 下的读、写、转义、是否在白名单；
  b. 第五部分把 MDX 编辑器单列为与 markdown-dialect 同级的工作，估人天，并写明未编辑字节不变与按块隔离怎么做；
  c. 把“方言 + 插值”与“MDX”的比较补上这一节的代价，交开发者重新确认（追认是在信息不全时给的）；
  d. 至少写明：第一版是否允许作者在主 MDX 里用 `**` 等 Markdown 强调；允许就必须解决 CJK 强调与章节不一致。

### 6. 面板“记一笔”和随后的“记账”会重复记同一笔；“整章可以一键撤销”是否包含作者手记的那几笔没有说
- 严重程度：重要；类别：正确性
- 位置：第 4.6 面板“记一笔”；第 4.8 日常循环第 4、5 步；第 4.9 记账输入；第 4.4“重讲不重记”
- 现象：作者写第 12 章时，在面板里先记一笔“魔力 −90（打了一场）”（落在当前章，来源“作者”，出处“界面操作”）。写完点“记账”，Agent 读本章正文，正文里写着“耗掉了大半魔力”。第 4.9 记账的输入是“本章正文、涉及条目在本章开头的状态、本章的计划、各 Component 的记账说明”，没有“本章已有的变更”。
- 为什么是问题：
  1. “重讲不重记”是针对“记账时发现事情已经记过”，前提是 Agent 看得到已有记录。输入里没有它，Agent 会再记一笔 −90，且因为正文没有写出具体数字，核对点不会触发，这个重复无声地存在，直到某个后续核对点对不上才暴露。
  2. 反方向：作者先点了记账、再记一笔时，记一笔的出处是“界面操作”，没有正文讲述，后来“整章撤销后重记”（改稿流程）重记不出这一笔；整章撤销是否同时撤销作者手记的这一笔，也没说。如果撤，作者的手工输入被无声丢弃；如果不撤，重记之后又是重复。
  3. “这一章的账”到底包含哪些记录（来源 Agent 的？全部？）是第 4.8 第 5 步“整章可以一键撤销”的对象，需要定义。
- 如何核实：4.9 记账输入清单与 4.6 记一笔并读。
- 建议：记账输入加“本章已有的变更（含作者记的）”，规则写成“已有的不重记，只补讲述”；整章撤销的范围写成“来源为这次记账的变更”，作者手记的保留并在回执里列出“与重记的结果可能重复”；记一笔时在界面上提示“写完这章后记账会读到这一笔”。

### 7. 还原与撤销：“逐条”的单位、“后面有依赖”的定义、撤销的实现方式三样都没定，作者会看到一长串“依赖”
- 严重程度：重要；类别：正确性
- 位置：第 4.8 日常循环第 5 步、“改动记录”；第 4.3 生效状态；第 4.5 修订
- 现象：
  1. 单位：改动记录“每条”是一次修订；一次记账是一次修订（4.9“输出：一次修订”），里面有十几条变更、几个新建条目。作者发现回执里一条错误的“兑现 c20”，想只撤销这一项。“逐条还原”的“条”是修订还是修订里的一个操作？若是修订，只能连同本章其余十几条一起撤；若是操作，4.5 要说明操作级还原怎么做。
  2. 两套机制并存：变更有“生效状态：已撤销（保留，不生效）”（4.3），修订有“还原也是一次修订”（4.8）。整章撤销是把这章的变更置为已撤销，还是发布一次逆向修订？两者在改动记录和剧情表里的呈现不同；新建条目、未决问题、条目树位置没有生效状态，只能靠逆向修订；条目在整章撤销后是删除（墓碑）还是保留？
  3. “后面有修订依赖它时，列出来一起处理”：依赖没有定义。若按“碰了同一条目同一字段”算，存款每章都有加减，撤销第 3 章的记账会把后面每一章的记账都列成“依赖”。第 4.5“改过去”已经给出区分（加减自动跟着变、赋值与整段替换要看一眼），还原这里没有沿用。结构性依赖（后面的修订修改了这次创建的条目）才是真依赖，也要单独说。
- 为什么是问题：整章撤销是第 4.8 对“默认生效”的安全阀（开发者 11-02 的决定）。作者按下去如果看到 40 项“依赖”，这个阀就不可用；如果实现者按“不管依赖直接撤”做，后面的补丁套不上，会批量进“未解决”。
- 如何核实：第 4.3 生效状态、4.5 改过去、4.8 改动记录三处并读。
- 建议：规定还原的单位为修订，修订可含“不可分”的操作组；撤销统一实现为逆向修订，“已撤销”状态只用于单条变更的软删除；依赖沿用 4.5 的分类，只把结构性依赖和会变值的赋值类依赖列出。

### 8. 回执、待处理、改动记录、面板流水、情节：五个视图没有入口、生命周期与互相跳转；改稿的日常动作会触发“整章撤销重记”，把作者已做的决定一并扔掉
- 严重程度：重要；类别：遗漏
- 位置：第 4.8 日常循环第 5 步、“改动记录”、“出处”；第 4.6 面板 Tab 与情节
- 现象：
  1. 提案里作者能看到“同一批数据”的地方有五处：回执（新建几个条目、记几条变更……）、待处理、改动记录（所有修订按时间）、面板 Tab 的流水、情节 Tab（涉及本条目的变更）。每处的入口（侧栏？状态栏徽标？条目页的一个 Tab？），回执在作者看过之后是否保留、过多久消失、能否重新打开，待处理从哪里进、能否按类型和章筛选，没有一句话；“界面的布局放到 t10、t16”不覆盖这件事，因为是否能跳转是 4.8 自己承诺的行为（“待处理的逐条处理”）。
  2. 跳转关系缺失：回执里的“3 处待处理”跳到待处理的哪一条；待处理里的一项“核对点不符”要同时给出出处（正文原句）、涉及条目和那条变更，三个目标分别在编辑器、条目页、改动记录；改动记录里一条“记账”修订能否跳回回执。
  3. 改稿路径：第 4.8“出处”写“一章的正文在记账后改过，这章的账标可能过期；第一版可以整章撤销后重记”。改错别字也会令整章标过期（没有区分改动大小）；重记之前整章撤销，把作者已经在待处理里做过的决定（采用校正、确认估计值）、作者手记的记一笔（第 6 条）一并撤掉，重记后同样的问题再来一遍。对一个要反复改稿的写作者，这是常态流程，却没有任何成本说明。
- 为什么是问题：回执与待处理是“默认生效、有问题才叫作者”的全部作者界面；它们没有入口，这一设计取向就没有落地处。
- 如何核实：通读 4.8，查“回执”“待处理”“改动记录”各自出现的位置，没有一处写入口。
- 建议：先在提案里列一张“作者可见的四类通知”的表：回执、待处理、改动记录、候选（第 4 条）各自的入口、保留多久、能跳到哪；改稿时按“改动是否触及已记账的出处原句”决定是否标过期，不是任何改动都标；重记保留未被重记结果取代的作者决定（按变更 id 对应）。

### 9. “点出处跳到正文原句”在提案里反复出现，编辑器没有这个能力，影响一节没列
- 严重程度：重要；类别：接口
- 位置：第 4.6 情节“问一句”（每句标出处）；第 4.8 改设定协助“每条有原句”“自己改”；“出处失联”；待处理项里的“核对点不符”；第五部分
- 现象：出处是“章加原句”，作者要点出处跳到那一句。核对编辑器控件句柄（packages/neuro-book/src/plugins/editor/shared/contracts.ts 的 EditorControlHandle）：有 `revealEnd`、`revealHeading`（按大纲标题）、`revealRange`（只给“写不出”的定位，坐标是控件自己交出的块坐标）、`navigation.revealLine`（只有源码编辑器）。章节文件默认用 Markdown 富文本打开，输出 28 说明富文本不给源文件行号。没有“按一段原文定位并选中”的入口，也没有从文本到富文本坐标的映射。
- 为什么是问题：协助改设定（“自己改”）、出处失联的处理、核对点不符的处理（给作者建议改正文里的数）、情节的“每句标出处”都靠这条跳转；少了它，作者只能看着一句话自己到章节里找。第五部分的平台清单有条目页、图片控件、MDX 编辑器，没有这一项。
- 如何核实：contracts.ts 的 EditorControlHandle；editor.md 输出 28、29、60、61。
- 建议：把“按原文片段定位并选中，找不到返回失联”列为编辑器控件句柄的新能力（富文本与源码各一份），写进第五部分与 editor.md 的预期改动。

### 10. 位置选择器的“当前（跟着正在写的章）”没有定义；并排看时它会随焦点变，编辑目标会在作者手下改变
- 严重程度：重要；类别：正确性
- 位置：第 4.8“条目页”第二条；第 4.8“就地改”
- 现象：
  1. “正在写的章”是什么：活动编辑组的活动标签？最近一次获得焦点的章节标签？editor.md 里 `nbook.editor/activeDocument` 是活动组活动标签的地址，页面标签没有文档（输出 33）。作者点进条目页的那一刻，活动标签就是条目页本身，没有“正在写的章”；左右分栏各开一章（左写第 12 章，右看第 5 章对照）时更不明确。
  2. 章不一定有位置：活页夹里“未编排”分组的章节文件（folder-kinds.md）没有章序，“第 N 章”无从谈起；正在写的不是章节而是一份手记或细纲时，“当前”是什么。
  3. “当前”会动：作者在条目页里编辑一个值（4.8 就地改，保存前显示“将修改哪条记录”），切去章节标签、再翻到第 13 章，再回来保存。位置变了，“将修改哪条记录”变了，但作者之前看到的那一行是旧的。就地改的目标记录取决于位置，所以开始编辑时必须冻结位置。
  4. 位置作用域：“所有 Tab 跟着同一个位置”指同一个条目页内的 Tab。但“可以多开、并排看”：同一条目的两个条目页各选一个位置并排放，正是第一轮处理里“并排比较两个位置不进第一版”想排除的用法，现在变成了条目页多开的副作用。各页的位置是否独立、能否锁定、“当前”的页是否跟着变，都没写。
- 如何核实：editor.md 输出 28（富文本无位置）、33（页面无文档）；folder-kinds.md 的“未编排”。
- 建议：定义“当前”= 最近一次获得焦点的、有章序的章节标签；没有时退回“初值”或最近一次的位置并提示；每个条目页有自己的位置，可以“锁定”；开始编辑某个值时冻结页的位置，直到保存或放弃；“未编排”章节不提供“当前”。

### 11. 就地改的交互：保存前那一行每次都出现会变成噪音；“剧情变化”勾选没有入口；改一次主 MDX 到底产生几条修订没说
- 严重程度：重要；类别：体验
- 位置：第 4.8“就地改”；第 4.5 修订（每次写入都是一次修订）
- 现象与问题：
  1. 触发频率：提案写“保存前显示一行‘将修改哪条记录’，可以改选”。四个例子里有三个是“来源明确，只有一个候选”（只有初值设过；某一章设的；一块文字来自某章整段替换）。每个字段、每个小块的每次修改都要先看一行字再点保存，一天改几十个字段，这一行很快就被作者无视；在作者无视的状态下，唯一一次真正要看的提示（比如改的是累加字段，会让早先的核对点对不上，见第 1 条）也被一起无视。应当只在“有歧义或有下游后果”时才打断，其余在保存后用一行可撤销的提示（“已改初值，撤销”）代替。
  2. 勾选入口：“勾‘这是剧情里发生的变化’”放在哪没说：保存前那一行里？每个字段旁？整个条目页顶上？是否记住上一次的选择？这决定了它是顺手的快捷还是被忘记的选项。默认“算改设定”由开发者 11-02 追认；但对数值类字段和“当前”位置，作者的真实动作多半是剧情事件（打了一场损失魔力），默认落到初值，会静默改写整本书的起点，而唯一的提醒就是那一行。因此保存前那一行必须随字段种类与位置变色：对累加字段、对“当前”位置提示更强。
  3. 位置不可勾：位置是“初值”“前史”“按计划”时勾选无意义（初值上不会有剧情事件；按计划上改的是计划）；“尚未出场”位置上编辑的含义也没写。勾选应随位置禁用或改语义。
  4. 修订的粒度：编辑主 MDX 一块文字时，什么时候发布一次修订（每个字符？失焦？停手几秒？显式保存？）。提案说“每一次写入都是一次修订，版本加一”，而编辑器区的做法是“输入先存在文档里，Ctrl+S 才写盘”，没有自动保存（editor.md 不承诺里写了自动保存）。如果每次失焦就发布，改动记录里会塞满几十条“改了一个标点”，也让第 7 条的“逐条还原”失去意义。需要规定“草稿 → 保存 → 一次修订”，同一条目页的一次保存可合并多个字段为一次修订。
  5. 与 Agent 同时改：作者的草稿基于读取时的版本；Agent 在这期间发布了对同一字段的修订（记账很常见），保存时报冲突。作者一侧的冲突界面（“采用当前值/保留我的修改”之类）提案没写，只写了 Agent 一侧“报冲突、返回当前值”。
- 如何核实：4.8“就地改”四个例子；4.5“并发”；editor.md 不承诺第二条。
- 建议：保存前的确认只在有歧义（两个以上候选）或有下游后果（核对点、后面的赋值）时出现；勾选放在保存确认条里，位置为初值/前史/按计划时置灰，累加字段与“当前”位置默认不勾但把“改设定会改写全书起点”写在确认条里；规定一个条目页一次保存 = 一次修订；补作者侧冲突。

### 12. “已有成稿”路径：字段没有初值怎么办没有规则；一百章逐章记账是一百次人工点击与一百份待处理
- 严重程度：重要；类别：遗漏
- 位置：第 4.8“开始一部作品”第二条；第 4.5 写入时校验与核对点；第 4.6“加一个 Component 是创作修改”
- 现象：作者带着已写好的 100 章来，第 1 章就已经是“存款 41800、魔力 3110”这类中途的状态，没有人写过初值。第 4.5 核对点规则是“只确认已有值，不产生补丁”，加减要求字段已有值，约束要求“在生效位置上满足”。第一章的记账“同时建出第一批条目”，但字段的初值从哪来：设成 0（那么第 1 章的核对点 41800 与初值 0 不符）；设成第一次提到的值作为初值（即“前史”）；还是 Agent 填估计？schema 里也没有“未知”这个值，第 4.5“可能不准”标记是重算失败后的状态，不是初始状态。
  同一问题出现在“从第 3 章才得到面板”：Component 从头就有，魔力的初值是多少？
- 为什么是问题：第二条路是现有作者最大的一类用户（有旧稿的人）；第一章记账就会撞上，每个数值字段都是一次待处理。
- 如何核实：读 4.5 核对点与校验，想一个第 1 章就写“还剩 41800”的样例。
- 建议：规定“初值”允许为“未知”，加减在未知上报“缺初值”并引导作者或 Agent 用最早一次出现的数作为初值（标估计）；Component 启用时同样；并说明已有成稿的批量记账怎么用：一次排队记账、汇总成一份总回执，而不是逐章点击逐章审阅。

### 13. 起步：故事种子的“确认”与“默认生效”矛盾；首次审阅用到的时间线、逐个确认界面在 nb-ui 里没有；空状态入口没考虑 Agent 未配置
- 严重程度：建议；类别：体验
- 位置：第 4.8“开始一部作品”第一条与空状态
- 现象与问题：
  1. “首次审阅分三组：未决问题在前；条目逐个确认或改；前史排成一条时间线”：确认的是什么状态？第 4.8 日常循环的原则是默认生效、有问题才叫作者。种子产生的条目是否在作者确认前已生效？不确认会怎样（Agent 写手拿到的是已生效的，还是等确认的）？“确认”若只是浏览，就不要叫确认。
  2. 界面件：nb-ui 的组件目录（controls、display、feedback、form、layout、navigation、popup）里有 Tabs、Table、Dialog、Drawer、SearchSelect、Tree，没有时间线、分页、差异对比（改设定协助的“原句与建议改法”要并排或行内差异）、向导/步骤条；nb-form 的支持写法表里没有只读时间线。第五部分只列了 nb-form 的图片控件与标记，没有这些。
  3. 空状态“把故事种子交给 Agent”的入口：项目没有配置模型时这个入口是死的。第三条路“先搭设定”应当是空状态里同等可见的另一个入口，并在没有 Agent 时是唯一入口。
- 如何核实：ls packages/nb-ui/src/components/*；forms.md 支持写法。
- 建议：明确“确认”只是已读还是生效门槛；时间线、分页、差异对比列入平台前置的 nb-ui 工作（或明确第一版用现有 Table 替代）；空状态按 Agent 是否可用显示入口。

### 14. 存在区间：记账建条目时“出场”默认“从头就有”，会让没登场的角色出现在早期章节的作者视图和 Agent 预查里
- 严重程度：重要；类别：正确性
- 位置：第 4.2 存在区间；第 4.9 记账规则“新出现、有名字、可能再出现的人和物建条目”
- 现象：存在区间“默认从头就有”。记账第 8 章时 Agent 为新出场的“夜王”建条目，规则里没有要求同时设置“出场 = 第 8 章”。于是“夜王”在第 1 到第 7 章的作者视图里不标“尚未出场”，条目列表“按名字搜”能搜到，Agent 的自动预查（按当前位置精确匹配用户消息里的名字）也会在写第 3 章时把“夜王”当作存在的条目返回，给写手的上下文泄露剧透。
- 为什么是问题：存在区间是用来防这种泄露的（第 4.2 写“Agent 的查询不返回它”），默认值却使它不起作用，除非 Agent 记得设。
- 如何核实：4.2 与 4.9 记账规则并读，规则里没有“出场”一词。
- 建议：记账建条目时出场默认取“第一次讲到它的章”（与 4.4 生效位置默认同一规则）；作者手动建条目才默认从头。

### 15. 马甲：作者界面一个字没写——怎么建立“身份同一”、马甲的页面显示不显示本体的共享数、情节要不要合并
- 严重程度：建议；类别：遗漏
- 位置：第 4.2 马甲；第 4.6 情节；第 4.8
- 现象：第二版把“子条目”改成“显式的身份同一连接”，规则只写了数据层（共享的数放本体，马甲只放自己的）。作者一侧：在哪建这条连接（条目页的一个按钮？新建条目时选“是 X 的马甲”？）；马甲的页面里面板 Tab 显示什么（本体的魔力，只读？可改并写到本体？）；“记一笔”在马甲页上改的是本体；情节 Tab 里本体和马甲的变更要不要合并显示；改设定后协助改正文时“她”以马甲的名字出现是否算（第 4.8 第 2 步写了“马甲、滤镜下的样子不改”，但这是 Agent 的判断，不是作者可见的设置）。
- 为什么是问题：马甲是网文常见机制，也是第二版刚修订的地方；作者界面不定义，实现时每个视图各猜一次。
- 建议：补三句：创建入口；马甲页对共享字段的显示与可编辑性；情节默认显示本体与全部马甲的并集，可切换。

### 16. 情节 Tab 与面板 Tab 要的控件，nb-ui 与 nb-form 都没有，影响一节只列了图片控件和字段标记
- 严重程度：建议；类别：接口
- 位置：第 4.6 情节与面板；第五部分
- 现象：情节 Tab 要“分页；按章、剧情线、已写或计划筛选；关键词与语义检索；问一句（回答每句标出处）”。nb-ui 的目录里没有分页、没有筛选条，Table 是展示件；“问一句”是一个嵌入式对话，需要流式输出与出处链接（nb-agent-ui 能提供一部分，但“调用和 Agent 同一套读取与检索”意味着在 Tab 里再起一个 Agent 会话，用哪个会话、用什么模型、怎么计费，没写）。面板 Tab 的“当前值与流水”“记一笔”是自定义界面，nb-form 的受控模型不管（第一轮已处理为专用界面，没问题），但“流水”本身是一份可筛选的列表，同样没有控件。语义检索在没有嵌入服务时退回关键词（已写），“问一句”在检索退化时的回答质量没有说。
- 为什么是问题：t16 会据此估工作量，漏列会低估。
- 建议：第五部分补“nb-ui：分页与筛选条、时间线、差异对比”；“问一句”明确为“带着筛选结果新开一个 Agent 对话”，不在 Tab 内嵌。

### 17. 细纲与计划是两份内容，没有同步规则
- 严重程度：建议；类别：遗漏
- 位置：第 4.8 日常循环第 1 步
- 现象：“细纲挂在章上，是作者写的原文，不是剧情变更。讨论时，Agent 从细纲提出这一章的计划，作者可以直接增删改计划。”作者之后改了细纲（重写第 12 章的走向），已经提出的计划怎么办：Agent 再提一遍会得到重复的计划；作者直接改了计划后再改细纲，哪个为准。第一轮处理里“手记转设定的同步提示放 t10 细化”只覆盖手记。
- 建议：计划记下来自细纲的哪一段（出处）；细纲改动后，来源为它的未兑现计划标“细纲已变”，由作者选择更新或保留，不自动重提。

### 18. 作者承诺了十几种“改一条变更”的操作，却没有变更本身的界面：情节 Tab 只查询，条目页只管条目
- 严重程度：重要；类别：遗漏
- 位置：第 4.4“可以手动往前挪”；第 4.5 核对点三种处理的第三种“改前面的某条记录”；第 4.8 就地改“从来历里挑一笔改”、“给旧变更补剧情线是创作修改”、“作者可以直接增删改计划”；第 4.6 情节“只查询”
- 现象：作者要能做：把一条变更的生效位置往前挪（回忆章的往事改成前史）；改某一条变更的补丁、描述、涉及的条目；给旧变更补剧情线；取消、替代、拆分一条计划；从累加字段的来历里挑一笔改。第 4.6 把情节 Tab 定义为“只查询，不占命名空间”，界面是分页、筛选、检索、问一句，没有编辑；条目页是按条目的。第 4.9 的 `read` 可读“一条变更的原记录与出处”，Agent 一侧有对象，作者一侧没有页面。第 4.8 说“剧情表是章乘剧情线的格子”，也没说格子里的变更怎么编辑。
- 为什么是问题：这些操作是第二版为了解决第一轮发现新加的（就地改、核对点处理、生效位置挪动、计划进展），它们的落点都是“一条变更”，却没有承载的界面；t16 的剧情工坊界面（“布局放到 t10、t16”）如果不知道这件事，只会做“看”不会做“改”。
- 如何核实：通读 4.6 与 4.8，列出每个“作者改某条变更”的动作，看是否有对应的页面。
- 建议：在 4.8 增一小节“变更的详情”：一条变更打开后看到什么（描述、位置、讲述、涉及、补丁、核对点、连接），能改什么；情节 Tab 的每一行、面板流水的每一行、待处理的每一项、改动记录的每一条都打开它。这样第 8 条里的跳转也有了统一的目标。
