### 3. 重算时“整条不生效、进待处理”却“不改生效状态”：同一条记录同时是“生效”和“没套上”，兑现推导、列表过滤、计划视图都读错

- 严重程度：重要；类别：正确性 / 不变量。
- 位置：第四部分第 3 节字段表“生效状态”（167 行：生效、待处理（处理前不生效）、已撤销）与“计划怎么走”（172、175 行）；第 5 节“重算时算不下去”（243—245 行）；第 9 节 `changes` 按生效状态列（436 行）。
- 现象：243 行说套不上的变更“整条在这个位置不生效，进待处理”，245 行又说“这些是每次重算的诊断，不改记录的生效状态”。于是“待处理”一词同时指两种东西：167 行记录上的持久状态“待处理（处理前不生效）”，和 404 行作者的待办队列里的一项。重算失败的记录，持久状态仍是“生效”，实际没有任何补丁进入状态。
- 为什么是问题：凡是按“生效状态”推导的规则都会把它当成已生效：
  1. 172 行“已兑现由生效的兑现连接推出”。已写变更 E 兑现计划 P，E 里有 `panel.任务[t3].奖励 = 5`；作者后来在初值里删了任务 t3（创作修改），重算时 E 整条套不上。E 的生效状态仍是“生效”，P 仍算已兑现，按 175 行 P 的补丁不进任何视图；E 的补丁也没进。结果是真实状态与“按计划”视图里，这件事都凭空消失，计划也不会回到未兑现提醒作者。
  2. `changes` 按生效状态筛选“生效”时会列出 E，Agent 读到的是“这条已生效”，与 `read` 出的状态（没有 E 的效果）互相矛盾。
  3. 第 5 节“还原”的依赖、核对点嫌疑区间（252 行“列出……之间的记录”）都没有说要不要把“生效但没套上”的记录算进去。
- 如何核实：按 172、243、245 三行逐字代入上面的 E、P；没有任何一条规则能让 P 回到未兑现，也没有任何字段能让 `changes` 区分“生效且已套上”与“生效但没套上”。
- 建议改法：把两件事分开命名并写进字段表：持久的“生效状态”（作者或记账决定：生效、待定、已撤销）只由修订改变；“本次重算的结果”（已套上 / 没套上 + 原因 + 根因记录）是派生诊断。然后逐条写清各规则读哪一个：建议兑现推导读“已套上”（没套上的兑现不算兑现，P 回到未兑现并在待处理里与 E 合并成一项），`changes` 与 `read` 返回两者，嫌疑区间包含没套上的记录。持久状态里的“待处理”改个名字（例如“待定”），与待办队列区分。

### 4. “整条不可分”与“去掉 Component、未启用、元素没了”相乘：一次可逆的隐藏会让全书大部分变更连带别的字段一起失效，待处理被同一个根因刷满

- 严重程度：重要；类别：正确性 / 遗漏。
- 位置：第 5 节 243—244 行（整条不生效，涉及字段标不完整）；第 6 节“生命周期”298—299 行（没启用时补丁拒收；去掉时数据隐藏、保留）；第 10 节例子 482 行（c09 同时改 `character.形态` 与 `panel.魔力`）。
- 现象：去掉 Component 是创作修改（297 行“加一个 Component 是创作修改”，去掉同理），对所有位置生效。去掉以后命名空间不可访问，按 243 行，每一条含有该命名空间补丁的剧情变更在重算时都“套不上”，整条不生效。
- 为什么是问题：
  1. 连带损失：例子里的 c09 同时把形态改成“原身”、魔力 −90。作者暂时去掉星瑕的面板（299 行把它设计成可逆的隐藏），c09 整条不生效，第 1 章以后星瑕的形态也回到旧值，形态字段被标“不完整”。“转账不会只记一边”的理由在这里不成立：形态与魔力没有守恒关系，去掉面板的作者也不期望人物字段跟着变。
  2. 刷屏：一个跨 50 章、几乎每章都动魔力的面板，去掉一次就产生约 50 项待处理，根因只有一个。启用变更本身没套上（例如它和别的补丁在同一条里）时同样如此：之后所有对该命名空间的补丁都失败，而不是“标不完整”。
  3. 再加回来（299 行“恢复”）时这些项按 245 行自动解除，作者在中间看到的是一大批随后又消失的待处理。
- 如何核实：取第 10 节 c09，执行“去掉 panel”这一次创作修改，按 243、244 行重算第 1 章；c09 整条不生效，`character.形态` 在第 1 章末尾回到 c09 之前的值。
- 建议改法：区分“结构不存在”的两种原因。被作者有意隐藏的命名空间（去掉、未启用）上的补丁，重算时视为“不适用”，只跳过这几条补丁、不判整条失败、不进待处理，变更其余补丁照常生效；不可分只用于真正的套不上（元素被删、约束破了、类型不符）。待处理按根因归并：同一个根因（一次创作修改、一条没套上的启用）引起的连锁失败合成一项，列出受影响的记录数与范围。若坚持全部不可分，至少把“去掉 Component”改成在有剧情变更引用时拒绝，并列出这些引用。

### 5. 还原的依赖按“同一个对象”判，而记账要给旧记录补讲述：重讲一次就把两章的记账修订绑在一起，“整章撤销”变成“撤到最后一章”

- 严重程度：重要；类别：正确性 / 接口。
- 位置：第 5 节“修订”209 行（存每个被改对象的改前与改后的值）、“还原”266—268 行；第 4 节 199 行（重讲只给原记录补一条讲述）；第 9 节记账规则 459 行；第 8 节日常循环 397 行（整章可以一键撤销）。
- 现象：267 行把“后面的修订改过同一个对象”列为依赖，268 行规定有依赖就不能单独还原；“对象”的粒度没有定义。按 199、459 行，记账遇到重讲时修改的是那条旧记录（往它的讲述列表里加一项）。
- 为什么是问题：前史 c07“被软禁、靠魔偶逃脱”在第 5、8、12 章各被回忆一次。三次记账修订 R5、R8、R12 都改了 c07 这个对象。作者想撤第 5 章的记账：R8、R12 后来改过 c07，是依赖；按 268 行只能连同 R8、R12 一起倒序还原，也就是把第 8、12 章的整次记账一起撤掉。回忆、转述在长篇里很常见，越靠前的章节越撤不动。同样的问题出现在：初值若按条目整体算一个对象，改 A 字段的初值会挡住还原改 B 字段初值的修订；作者在第 N 章“记一笔”之后，记账给它补讲述（396 行），这一笔就和记账修订互为依赖。
- 如何核实：按 199 行构造 c07 的三次重讲，按 267 行逐条判依赖，R5 的依赖集合是 {R8, R12}。
- 建议改法：把对象粒度定到“可独立还原的最小单位”并写进合同：状态按字段（列表按元素 id），记录按字段，讲述、核对点、连接这类列表按各自的元素 id。只往列表里加元素、互不覆盖的修订之间不算依赖；补偿修订只移除本次加的元素。依赖要写明取传递闭包（R8 依赖 R5，R12 依赖 R8 时一起列出）。

### 6. 就地改的冲突只按写集判，而作者填的是一个算出来的值：并发记下的一笔会被静默算进去；“保存后核对结果等于作者填的值”不等时怎么办没有写

- 严重程度：重要；类别：正确性 / 遗漏。
- 位置：第 5 节“并发”272 行（要改的对象在那之后被改过才报冲突）；第 8 节“就地改”375、380 行（以最后一次完整赋值或初值为基准；保存后核对结果等于作者填的值）；第 7 节回写 351、353 行。
- 现象：作者在第 5 章末尾看到存款 41800（初值 40000，第 2 章 +2000，第 4 章 −200），把它改成 41000，选“改开局数”，写回的对象只有初值：40000 → 39200。
- 为什么是问题：
  1. 读到 41800 之后、保存之前，Agent 记账给第 3 章补了一条 −300（新记录，不是初值这个对象）。按 272 行，作者这次写入要改的对象（初值）没被改过，不报冲突，照常发布；第 5 章末尾变成 40700，不是作者填的 41000。作者的输入是“这一点上的值”，依赖的是基准到这一点之间的全部记录（读集），冲突检测只看写集就会漏。
  2. 380 行要求“保存后核对结果等于作者填的值”，但没写不等时怎么办：拒收、重算差额再写、还是提示。上面的并发、选“撤某一笔”（撤掉的那笔正好不等于差额时，结果必然不等于作者的值）、选“改某一笔”而那一笔是多补丁的转账，都会走到这一步。
  3. 带值回写 353 行写“版本过期（报冲突）”，与 272 行“对象级”判冲突是两种口径：前者照字面是任何新版本都拒收（Agent 在作者打字时随便写一处就让作者的保存失败），后者漏掉读集。两条路径对同一个就地改给出不同的冲突语义。
- 如何核实：按上面的数，代入 272 行判冲突与 380 行的基准规则逐步计算。
- 建议改法：就地改（作者界面与带值回写共用）在提交时带上“读到的值与它的来历（基准记录加其后的加减记录的版本）”；发布时重算该位置的值，与读到的值不同就报冲突，返回新值与新增的记录，不按写集放行。核对结果不等时整次拒收并说明原因（例如“你选的那一笔是 +10，差额是 −800”），不发布半成品。353 行的“版本过期”改成与 272 行同一口径。

### 7. 带值回写第 5 步把字段操作交给“就地改的规则”，而那套规则在来源不止一个时要作者选、还有“这是剧情变化”的勾选：Agent 走这条路时没有定义

- 严重程度：重要；类别：接口。
- 位置：第 7 节回写第 5 步（351 行）；第 8 节“就地改”379—381 行；第 3 节 192 行（Agent 写入时自己标明是剧情变更还是创作修改）；第 9 节 `write`（439 行“就地改”“交回改过的一块”）。
- 现象：Agent 交回一块，把 `{panel.存款 = 41800}` 改成 `{panel.存款 = 41000}`。存款由初值和几笔加减累出，按 380 行属于“来源不止一个”，要弹确认条让作者在“改开局数／改或撤某一笔／补一笔漏记”里选，不预选；381 行另有“这是剧情里发生的变化”的勾选。回写协议（346—353 行）里没有任何字段承载这两个选择。
- 为什么是问题：照字面实现只有三种走法，各有返工：直接按“改开局数”写（违背 380 行“不预选”，也正是第二轮 R1 取消的默认）；挂起等作者确认（Agent 的一次 `write` 变成异步，预览与提交的语义都要重定）；拒收（那 `write` 列出的“交回改过的一块”对数值字段基本不可用）。另外 192 行要求 Agent 自己标明剧情变更或创作修改，回写协议也没有地方标；Agent 想表达“第 5 章她又花了 800”时，只能另走“记剧情变更”。
- 如何核实：对照 346—353 行的五步与拒收清单，找不到“来源选择”“剧情变化”两个输入；再对照 380 行的“不预选”。
- 建议改法：带值回写的请求里加两个参数：意图（改设定 / 剧情变化，剧情变化时数值生成加减、落在读取的位置）与多来源时的处理（改基准、改某条记录并给记录 id、补一笔并给位置）；多来源而没给处理方式时拒收，返回来历流水（与 `read` 的“来历”同一格式），让 Agent 补上参数重交或转给作者。写明 Agent 回写不弹确认条，改动记录与“可以撤销的提示”照常给作者。

### 8. 带值写法只定义了表达式注记，标签、标签属性里的表达式、注记左边的表达式怎么写与怎么切都没定义；“同一字段改成不同的值”遇到“只改了其中一处”是两种读法

- 严重程度：重要；类别：接口。
- 位置：第 7 节 322—325 行（白名单：表达式、内置标签“条目引用、图片”）、331—353 行（带值写法与回写五步、拒收清单）。
- 现象与为什么是问题：
  1. 内置标签在给 Agent 的结果里长什么样没有写。`<条目引用 id="e12">星瑾</条目引用>` 若渲染成“星瑾”，Agent 把它改成“星瑾妹妹”，第 3 步拆出的文字操作在第 4 步“还原源文”时无法判断新字落在标签内还是标签外；若原样输出标签，则要写明 Agent 看到的是 id 还是名字（名字随剧情变，144 行）。
  2. 标签属性里的表达式（`<图片 src={character.立绘[原身].图片} />`，MDX 里是 mdxJsxAttributeValueExpression）是否算第 2 步“按顺序一一对应”的表达式、渲染成什么，没写；按“表达式”的白名单它是合法的。
  3. 第 1 步只说 JSON 值用 JSON 解析器读边界，注记左边的部分没有文法。`{地址 = 值}` 与 `{表达式 -> 值}` 靠什么区分：`{panel.魔力 == 3110 ? "满" : "缺" -> "满"}` 的左边含 `=`；`{panel.a > 0 ? "->" : "x" -> "->"}` 的字符串里含 `->`。注记也不能交给 JS 解析器：`panel.魔力 = 3110` 是合法的 JS 赋值，`"缺" -> "满"` 是 JS 语法错误。照字面实现，实现者会各自发明切法，结果在这类表达式上互不兼容。
  4. 353 行拒收“同一字段在一块里被改成不同的值”。一块里两处 `{panel.魔力 = 3110}`，Agent 只改了一处为 3000：一种读法是一处 3000、一处 3110，值不同，拒收；另一种读法是没改的那处不算操作，接受。两种实现对同一输入给出相反结果。
- 如何核实：1、2 对照 322—325 与 346—350 行；3 用 acorn 的语义自行推演（本审查实测 `{panel.魔力 == 3110 ? "a" : "b"}` 在 MDX 里是 ConditionalExpression，probe2.mjs）；4 对照 353 行字面。
- 建议改法：在提案里给带值写法一张完整的小文法：注记 = `{` 地址 `=` JSON `}` 或 `{` 源表达式原文 `->` JSON `}`，其中“源表达式原文”按 JS 词法（字符串、模板串）扫描到顶层的 `->`；地址只许第 5 节的地址文法，`=` 两侧必须是“地址 + 单个 `=`”。写明两个内置标签在结果里的形态（建议原样输出标签、属性里的表达式也写成注记、条目引用显示 id 并在注记里附当时的名字只读），以及“只改一处”的判定（建议：只要有一处改了且其余未改，按改了的那处；两处改成不同的新值才拒收）。

### 9. 直接改文件的版本标记：导入后标记不更新，第二次保存必然冲突；“对不上”与“按版本判冲突”是两种口径；MDX 文件里按现有白名单没有地方放标记

- 严重程度：重要；类别：接口 / 遗漏。
- 位置：第 5 节“并发”275 行；第五部分“安全”540 行；第 7 节白名单 323—324 行；MDX 实测记录 evidences/mdx-probe-2026-11-02.txt。
- 现象与为什么是问题：
  1. 连续保存：Agent 打开导出于版本 V 的文件，第一次保存被导入成修订 V+1，改了对象 X。Agent 接着在同一文件里再改一处保存，文件里的标记仍是 V；X 在 V 之后被改过（就是它自己那次导入），按 275 行报冲突。要避免，导入后系统得把新标记写回文件，这又会和 Agent 手里的旧内容（编辑工具的条件保存基线）冲突，并产生一次需要按回声识别的写入；提案两种做法都没写。
  2. 口径：275 行前半句“按这个版本判冲突”是对象级（标记旧但对象没被别人改过，应当接受），后半句“标记缺失或对不上的进待处理”若把“对不上”读成“不等于当前版本”，任何别处的写入都会让整份文件导入失败。540 行“标记对不上的保留原样”同样含糊。
  3. 放在哪：主 MDX 文件里，`{/* version: 42 */}` 是一个不引用任何字段的表达式（实测 mdxFlowExpression，estree 的 body 为空，只有一条注释），按 324 行“一个字段都不引用的表达式也拒收”会被拒；HTML 注释在 MDX 里编译失败（实测记录第一节）；`export` 被 323 行禁止；`---` 开头的 frontmatter 在默认 MDX 里被解析成分隔线加一个二级标题（本审查实测，probe.mjs 的 frontmatter 一例）。标记只能放在旁边的文件或文件名里，提案应当写明，否则实现时会先往 MDX 里塞，再返工。这条也说明白名单把作者与 Agent 唯一可用的 MDX 注释写法一并拒掉了，是否有意需要写明。
  4. 导入被拒以后，磁盘上的文件与模型不一致（540 行“保留原样，不成为真相”）。下一次 Agent 改这份文件的别处，整份文件再次导入时会把上次被拒的内容一起带上，又被拒或被当成新改动；没有写拒收后文件怎么回到真相（重新导出覆盖、还是留着让 Agent 处理待处理）。
- 如何核实：1、2 按 275 行逐字推演两次连续保存；3 运行 /tmp/review-w00039-t02-design-r3/tmp/probe.mjs 看 comment、flowComment、frontmatter 三例；4 对照 540 行。

### 13. “补丁里的数没出现在讲述……里必须标估计”作为写入校验，对中文数字与推算出的差额会大量误拒，对恰好出现过的无关数字又会放行；“估计”的粒度也不一致

### 14. 地址在 MDX 里落成 JS 成员表达式后，有四处没有定：根标识符指什么、元素 id 的字符集、`[3]` 是 id 还是序号、不是合法标识符的对象键

- 严重程度：重要；类别：接口。
- 位置：第 5 节“地址”214—219 行；第 7 节白名单 322 行（取字段：本条目的，或按 id 引用别的条目的）；第 6 节 297 行（保留字段“启用”）；第 7 节例子 334 行（`entry.name`）。
- 现象（实测，probe.mjs、probe2.mjs）：`{panel.任务[t3].奖励}` 中 `[t3]` 是 computed 成员、属性为 Identifier；`["t3"]` 是 Literal；`[t-3]` 是 BinaryExpression；`[3]` 是数字 Literal 3；`[0f3a]` 编译失败（Could not parse expression with acorn）；`{星瑾.panel.魔力}` 的根是 Identifier“星瑾”。
- 为什么是问题：
  1. 根标识符：`panel.魔力` 的根是本条目的命名空间，`entry.name` 的根是保留名，别的条目“按 id 引用”时根是条目 id，内置函数（数字格式化）也是根标识符。提案没有给解析顺序与保留名清单：条目 id 恰好叫 `panel` 或 `entry`、命名空间与内置函数同名时，同一段 MDX 有两种意思；条目 id 若不是合法 JS 标识符（以数字开头、含连字符），在 MDX 里根本写不出“按 id 引用”。Agent 若按名字写（219 行允许工具参数写名字），名字随剧情变（144 行），存下来的 MDX 必须在写入时改成 id，这一步没写。
  2. 元素 id 的字符集：217 行只说 `[]` 里只许常量。若元素 id 由程序生成成 `t-3`、UUID 之类，`[t-3]` 会被当成动态下标拒收，`[0f3a…]` 直接编译失败；`[3]` 是数字字面量，按“元素 id 不是序号”应当读成 id "3"，但 MDX 作者与 AI 都会按 JS 习惯读成第 4 个。
  3. 对象键：`.键` 只能写合法标识符。键是“HP-max”或“2024”时只能写 `["HP-max"]`，而 216—217 行把方括号定义成列表元素 id，地址的语法区分在这里失效，只能靠 schema 判断。
  4. 保留名：“启用”是每个命名空间里的保留字段，schema 里不许有同名的普通字段，这条要写进登记校验（296 行只拒重名命名空间）。
- 建议改法：写一张地址文法与保留名表：根标识符的解析顺序（保留名 `entry`、内置函数、本条目的命名空间、条目 id）及冲突时登记或写入拒收；条目 id 与元素 id 由程序生成成合法标识符且不以数字开头（或规定别的条目一律写 `ref("e12").panel.魔力` 一类的内置函数）；数字字面量下标拒收；对象键与列表元素在 MDX 里都可写方括号，按 schema 区分，规范地址（补丁、核对点存储）里仍用 `.键` 与 `[id]`。写入时把名字解析成 id 并回写源文。

### 15. “不完整”标记在给 Agent 的带值写法里没有表示，算出来的 `->` 值和就地改的差额会把不完整的数当成确定值继续用

  1. 一条变更内的补丁顺序：同一条里 `panel.魔力上限 = 15000` 与 `panel.魔力 += 5000`，若逐补丁检查，先加后提上限会因中间值超限而整条失败；提案没说一条变更内补丁有没有顺序、约束是不是在整条套完之后查。
  2. 跨字段约束的归属：一条只降低魔力上限的变更，让魔力（它没动的字段）超限。按 243 行这条整条不生效，但 244 行“它涉及的字段”标不完整，标的是上限还是魔力，没写。
  3. 溢出的语义：剧情里“魔力回满”“恢复 5000”超过上限时，是失败、还是截到上限。面板类网文里这是常见写法；按现行条文是整条失败、进待处理。
  4. 对后文的影响：作者在第 2 章插一条 −300（或就地改把初值调低），237 行只检查第 2 章，写入通过；第 7 章原本合法的 −1000 因余额为负整条不生效，同一条里的别的补丁一起丢失，进待处理的是第 7 章那条，而不是刚写入的第 2 章那条。439 行的预览只看“改后各条目在本章末尾的样子”，看不到第 7 章。
- 如何核实：按上面四个输入逐条代入 237、243、244 行。
- 建议改法：写明约束在“一条变更全部补丁套完之后”检查；跨字段约束失败时，标不完整的是被约束的字段，待处理指向改动约束来源的那条；每个数值约束声明溢出策略（拒绝或截断，截断时差额写进流水）。写入时把“发布后重算会新增的套不上项”算进预览与回执，并把它们记在这次写入名下，作者可以直接还原这次写入。

### 19. 核对点存在变更记录上，随记录撤销而消失：作者按待处理“撤前面的某条记录”时，可能把证据本身撤掉，不符静默消失；嫌疑区间的起点也少了“最后一次完整赋值”

- 严重程度：建议；类别：不变量。
- 位置：第 3 节字段表“核对点”（166 行，是剧情变更的一个字段）；第 5 节核对点 250—255 行；“重算时算不下去”243 行。
- 现象与为什么是问题：
  1. 核对点是正文写明的数，是独立于记账对错的证据，却作为字段挂在某条变更上。“花了 50，还剩 150”记成变更 E（−50，核对点“之后 = 150”）。重算后 150 对不上（真正的错是第 2 章漏记了一笔），作者在 253 行的选项里选“撤 E”，E 已撤销，它的核对点不再参与比较，待处理消失，账面仍是错的。E 重算没套上（第 3 条）时它的核对点是否还比较，也没写。
  2. 252 行的嫌疑区间从“上一个对得上的核对点”开始。区间里若有一次完整赋值，赋值之前的记录不可能影响这里的值，却仍被列为嫌疑；没有任何对得上的核对点时，区间应从初值开始并把初值本身列为嫌疑（创作修改改错了开局数），条文没写。区间按字段算还是按条目算，也没写。
- 建议改法：核对点存成独立的对象（地址、值、讲述、比较位置，可选挂到某条变更的之前或之后），挂靠的变更撤销或没套上时，核对点保留并改为按讲述原句的位置比较；撤销一条带核对点的变更时，确认条提示“会丢掉这条正文证据吗”。嫌疑区间写成“同一地址上，从 max(上一个对得上的核对点, 最后一次完整赋值) 到这里，没有时从初值起并包含初值”，没套上的记录也列入。

### 20. 拆出的剩余计划排在哪里没有写：留在已写的那一章时，那一章的“按计划”视图会把没发生的部分算进去

- 严重程度：建议；类别：遗漏。
- 位置：第 3 节 174—175 行。
- 现象：174 行只说“没写的部分拆成一条新计划（连接拆自），带着没实现的补丁”，没写新计划的生效位置。原计划排在第 5 章，第 5 章已写。
- 为什么是问题：新计划若继承第 5 章，按 175 行（生效、未兑现、排在第 N 章及以前的计划都进“按计划”视图），第 5 章末尾及以后的按计划视图里，风信子已获救，而正文第 5 章没写；作者要逐条把剩余计划挪走。若默认“未排章”，它从所有视图里消失，作者可能忘了它。两种默认都可以，但实现必须选一种；它也影响第 2 条的修复（omp 的例子假定排在下一章）。
- 建议改法：写明默认值（建议：排在下一章开头，回执里列出并可一键改成未排章），以及在已写章节上的未兑现计划是否进该章的按计划视图（建议不进，只进之后的章）。

### 21. “块是闭合的语法单元”没有覆盖跨块的引用定义：引用式链接、脚注在按块解析时会变成纯文字

- 严重程度：建议；类别：遗漏。
- 位置：第 2 节 139 行；第 7 节 328 行（按块解析，一块出错只影响这一块）。
- 现象（实测，probe.mjs 的 refA、refAB）：`见[设定][s]。` 与 `[s]: https://example.com` 在同一次解析里得到 linkReference 加 definition；只解析前一块时得到纯文字 `见[设定][s]。`。
- 为什么是问题：139 行只禁止块级标签跨块，没有禁止引用定义与使用分在两块。按块解析（328 行）与整篇解析给出不同结果；若以后加 remark-gfm，脚注定义有同样问题。AI 写 MDX 时常把链接定义集中放在文末一块。
- 建议改法：在“闭合”的定义里加一条：引用定义（以后加 gfm 时含脚注定义）只在本块内有效，写入时发现块内有未定义的引用就拒收或提示；或者白名单直接不放行引用式链接。

### 22. 补偿还原恢复的“改前的值”可能是旧 schema 的数据，提案没要求存值时带 schema 版本，读时升级无法判断要不要升级

- 严重程度：建议；类别：遗漏。
- 位置：第 5 节 209—210 行（存改前与改后的值；不冻结 schema 与升级函数）、266 行（还原 = 把对象恢复成改前的值）；第 6 节 300 行（旧数据和旧补丁在读的时候升级，不改写历史）。
- 现象：Component 的 schema 从 v1 升到 v2（例如把“存款”拆成“现金”“存折”）。之后作者还原一次 v1 时代的修订，补偿修订把初值恢复成 v1 的形状。
- 为什么是问题：300 行靠“读的时候升级”，前提是读的人知道这份值是哪个版本。提案只在 285 行说 schema 带版本，没要求每个存下的值、每条补丁、修订里的改前改后值记着自己的 schema 版本。不记，恢复回来的 v1 值会被当成 v2 读，或被 237 行的类型校验拒收；而 schema 升级本身也不在 208 行的修订清单里，不能靠“还原到那时之前”绕过。
- 建议改法：写明状态值、补丁与修订里的改前改后值都带所属 Component 的 schema 版本，补偿修订恢复旧值时按版本升级后再写；把 schema 升级列为一种修订（不改写历史，只记一条），让改动记录能解释“这个值为什么变了形状”。

### 23. “不完整”按字段标，截止却按补丁判：对一个不完整的列表或对象做子键赋值，该截止还是不截止没有定义

- 严重程度：建议；类别：接口。
- 位置：第 5 节 244 行（它涉及的字段标不完整；遇到不依赖旧值的赋值或整段替换就截止）；216 行（地址可以到子键与列表元素）。
