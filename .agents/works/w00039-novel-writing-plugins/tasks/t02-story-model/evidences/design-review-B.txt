# 审查 B：前端部分（world-engine-kernel.md 第四节 2、5、6、7 及其对前端包的要求）

审查对象：docs/proposals/world-engine-kernel.md（master）。已读：nb-form README 与 docs/specs/ui/forms.md（status: planned），nb-markdown README 与 docs/specs/ui/markdown-display.md、workspace/markdown-dialect.md，nb-ui Tabs.md，nb-history README，packages/neuro-book/src/plugins/editor 的编辑器贡献点，workbench 两份提案，旧应用 Character Workbench 提案与人物表单，t10/t16 的 Task 记录。
说明：本稿很多界面细节被推给 t10、t16，本报告只列"内核提案现在就必须回答、否则界面做不出来或做出来别扭"的问题。

### 1. 在"第 N 章开头"视图里改值，改完值弹回去；界面操作没有段落位置，排序不定
- 严重程度：重要；类别：不变量
- 位置：第四节 3（排序）、4（状态怎么算）、7（按章看）、第四节 3 末段"作者在界面上改一个值时界面要问……"
- 现象：位置分"第 N 章开头"和"末尾"。"开头"视图 = 初值 + 第 N 章之前的变更，不含第 N 章自己的变更。作者在"第 30 章开头"视图里改魔力，按"剧情变化"记，只能是"讲于第 30 章"（提案没有别的选项），而这条变更按定义落在第 30 章内部，所以"第 30 章开头"视图里看不到它：保存后值弹回原值，作者会以为没存上。反过来在"末尾"视图里改，则落在本章所有已写变更之后还是之前？
- 排序规则是"同一章里按出处的段落顺序"。界面操作的出处是"作者在界面上的操作"，没有段落位置。若同一章里既有正文 1.21 的"魔力 -= 90"又有界面操作的"魔力 = 3000"，赋值与加减不可交换，顺序不同结果不同，而提案没有定界面操作排在章内哪里。
- 核实：对照第四节 3 的"排序（第一版）"一段与 4 的第一条，全文没有给界面操作定章内位置，也没有说"开头"视图里的编辑落在哪一章。
- 建议：界面编辑的落点按视图位置定：开头视图的编辑落在"上一章末尾之后、本章第一段之前"，末尾视图的编辑落在本章末；章内排序给界面操作一个明确的槽（章首槽、章尾槽），并写进排序规则。或者干脆规定非"末尾/前史/初值"位置的界面编辑只能是改正。

### 2. "改正"在非初值位置没有语义，界面无法实现"改正"选项
- 严重程度：重要；类别：不变量
- 位置：第四节 3（剧情变更和创作修改要分开记）、4（改过去）
- 现象：提案说创作修改"改变的是设定本身，所有位置都跟着变"，初值也是创作修改设定的。但作者在第 30 章视图里看到魔力 = 3110，说"这个值错了，应当是 3200"并选"改正"时，系统到底改了什么：初值加 90？改第 9 章那条"-= 90"为"-= 0"？还是在第 30 章前插一条抵消变更？不同选择对后面章节的影响完全不同（改初值会让后面所有位置都差 90，若中间有赋值又会对不上）。文本字段同理：三方合并只讲了合并，没有讲"改正"应当落在哪一版文本上。
- 为什么是问题：这是界面里最常用的编辑动作之一，选项出来了但后果无法向作者解释，作者无法判断选哪个。提案现在只对"改初值"列出后面改过同一字段的变更，对其他"改正"一字未提。
- 建议：先让领域审查者定"改正"的定义；界面层的最小做法是：改正只允许对"产生当前值的那条变更"或"初值"二选一，并在确认框里列出下游受影响的变更与新旧值。

### 3. nb-form 的"每次提交整根新值"模型表达不了面板的加减与流水
- 严重程度：重要；类别：接口
- 位置：第四节 5（面板：补丁做加减、Tab 显示当前值和流水）；docs/specs/ui/forms.md 输出 3、15
- 现象：nb-form 受控，每次提交"一个新的根值"，未改动的分支保持引用；它不知道"加减"。作者在面板 Tab 里把存款从 41800 改成 39800，表单只能出一个新根值，由调用方 diff 成补丁，得到的是"赋值 39800"，不是"存款 -= 2000"。而提案的面板要求补丁做加减、正文里写出的数当核对点、Tab 显示流水。赋值一旦进账，流水就断了（和旧 WorldEngine 的 broken-relative 同类问题，只是换了入口）。
- 另外，字段的"当前值 + 流水 + 核对点"不是 nb-form 的任何控件：forms.md 的控件清单里没有"数值带历史"的形态，需要自定义控件（输出 22 允许登记），且表单整体的 commit/draft 语义要与"一次加减需要写原因"协调。
- 建议：面板 Tab 不要用 nb-form 画值，改成专用的"记一笔"界面（输入增减量、原因，生成加减补丁），nb-form 只用来画面板的声明；在提案里写明这一点，不要让读者以为表单能直接承接。

### 4. 未审阅的记账结果是否参与状态，提案没有字段承载
- 严重程度：重要；类别：不变量
- 位置：第三节日志字段表、第四节 3、4，待定项 8
- 现象：变更的状态只有"已写/计划"。Agent 记账后到作者点"接受"之前，这些变更是否算进"某个位置上的条目"？若算，审阅就是事后审计，驳回会让之后已经基于这些状态做的渲染、再下一章的记账一起失效；若不算，作者不审阅（现实里经常），下一章的写手上下文里就缺本章的账。提案的日志字段里没有"待审/已接受/已驳回"，界面无法标出哪些变更作者没看过，也无法实现待定项 8 的"整章接受、单条驳回"。
- 如何核实：第三节字段表和第四节 4 全文搜"审阅"，只出现在流程描述里，没有进入数据模型。
- 建议：日志增加审阅状态；默认值与"未审阅是否参与状态"必须在提案里定死。界面上推荐"默认接受、只对有问题的项（核对点不符、待确认、超出计划）标红要求处理"，减少逐章审阅负担。

### 5. 记账审阅不能复用 nb-history 的审阅收件箱；创作修改的审阅无人负责
- 严重程度：重要；类别：接口
- 位置：第三节 nb-history 一行、第四节 7、第五节安全、待定项 2、8；packages/nb-history/README.md；docs/proposals/project-file-foundation.md 第 4 节
- 核实结果（读包与 grep 得出，不按名字推断）：
  1. nb-history 的审阅单位是"文件路径"：`inbox(userId)` 按路径分组，`accept/revert(userId, path)` 以文件为粒度；`revert` 把整份文件还原到已接受基线。没有"按章分批"，也没有"单条驳回"，一次还原会连带同一文件里别的修改。
  2. 它只记工作区文件的写入（performWrite/registerObservedWrite）。若 t09 选"全部放进数据库"，条目与变更日志对它不可见；即使选"文件加索引"，剧情变更日志要拆成每条一个文件才能按条审阅，与"全书一条日志"的模型冲突。
  3. 收件箱只在存在 agent/system 条目时出现；作者自己的改动不出现，与提案"作者自己的修改也记 diff"并存时，作者改的内容不会进任何审阅界面（可接受），但"创作修改"由 Agent 做时才进收件箱，两个入口并存。
  4. 新应用里没有 `nbook.history` 插件，也没有收件箱界面（packages/neuro-book/src/plugins 下无 history，全仓 neuro-book/src 中没有 inbox）。nb-history 只被旧应用依赖。所以"复用"不是接界面，而是先建插件再建 UI。
  5. 并发：nb-history 的 `acceptAtRevision` 用 revision 防止"页面上看到的 10 条，点接受时已经变成 12 条"。记账审阅同样有这个情况（Agent 还在补记、作者正在审），提案没有提并发条件。
- 为什么是问题：待定项 2 把"nb-history 能否承担创作修改的历史与作者审阅"留给审查，结论是：承担不了"记账审阅"；对"创作修改"，只有在条目与主 MDX 都落成文件时才能承担，并且会出现作者要看两个审阅入口（文件收件箱管创作修改，记账审阅管变更）的局面。
- 建议：提案明确两套审阅：记账审阅是日志层自己的"批次 + 条目级状态 + revision"，只借 nb-history 的接受位点与 revision 条件式写入这个想法；创作修改的审阅要么并入同一个界面（日志层同样记 diff），要么只靠 nb-history 并写明只覆盖落成文件的部分。同时写明审阅批次的边界（一章一批？一次 Agent 运行一批？）。

### 6. 主 MDX 在界面里怎么写，提案没有回答；现有 nb-markdown 不是 MDX
- 严重程度：重要；类别：接口/遗漏
- 位置：第四节 2、6、7（"写主 MDX，或者先留空"）；开发者决定"作者也能直接看 MDX 渲染出的文字"
- 现象：作者不碰文件（决定），所以主 MDX 必须有界面内的编辑方式。提案只写了"渲染后显示值，悬停显示路径"（只读）和"作者文字里的 { 与 < 要转义"。没有写：
  - 编辑的是源码（文本框/Monaco）还是所见即所得；两者怎么切换；渲染视图能不能直接点中一个值去改。
  - packages/nb-markdown 是 marked + TipTap 的 Markdown 方言（见 README 与 workspace/markdown-dialect.md），全仓没有 MDX 解析/编辑支持（grep：只有 Monaco 的 mdx 语法高亮和文件图标）。表达式 `{panel.魔力}`、`<引用条目 .../>` 在所见即所得里需要新的 TipTap 节点（带值显示、悬停路径、点击跳转）和新的"写回必须读得回来"规则，工作量与 markdown-display、prompt-editor 同级，不是接一个现成组件。
  - 若只给源码模式：作者要自己学 `{ }` 表达式语法与路径写法，违反目标 6（零门槛）。
- 作者看到值后想改：渲染视图里的 `{panel.魔力}` 点它应当去哪（面板 Tab 的"记一笔"？弹一个行内小框？）；只读的计算字段（`{表达式 = 值}` 一类）怎么提示"改它依赖的字段"；提案只对 Agent 说了"算出来的，只读；要改，就改它依赖的字段"，作者这边没有。
- 建议：提案补一节"主 MDX 的编辑界面"，至少定：(1) 默认是渲染视图，值是可点击的小块，点开进入对应字段的专用编辑（与第 3 条的"记一笔"一致）；(2) 源码模式作为"高级"切换，文本字段用 Monaco；(3) 所见即所得里 `{ }` 小块是 TipTap 节点，输入普通 `{` 时自动转义；并把"新增 TipTap 扩展组"列入第五节"影响"。

### 7. MDX 解析是全有或全无：作者一个字符能让整个条目的渲染失败（作者看到、Agent 读到的都是）
- 严重程度：重要；类别：正确性
- 位置：第四节 6（"作者文字里的 { 和 < 要转义。解析失败时显示源码和错误，不挡住作者"）、7、8（自动预查、read）
- 现象：MDX 编译器遇到第一个语法错误就整篇失败。小说作者文字里的 `<`（"HP<10"、颜文字"<3"）、`{`（从 SillyTavern 角色卡粘贴的 `{{char}}`、`{大括号}` 里的台词）在 Markdown 里无害，在 MDX 里是语法错误。提案只写了"要转义"，没有说：谁转义（作者？编辑器自动？）、粘贴/导入（t25）的文本怎么处理、整篇失败时 Agent 的 `read` 得到什么。若 Agent 读到的是错误信息或整篇源码，则一个未转义的字符让这个条目的"带值渲染"在所有读取中失效，并且作者可能在自己的界面里完全没有察觉（渲染视图显示的是源码+错误，而 Agent 那边是 Agent 的事）。
- 建议：渲染按块隔离：以段落为单位解析，哪一块失败就把那一块当纯文本输出并标一个诊断，其余照常渲染；编辑器对输入的 `{`、`<` 自动写成转义，粘贴和导入走同一个入口；提案在"失败与恢复"里写明 Agent 看到的是什么。

### 8. "条目页（顶上选章，下面是各 Component 的 Tab）"放在工作台哪里，现有机制承接不了
- 严重程度：重要；类别：接口
- 位置：第四节 5、7（"条目页顶上可以选'第 N 章开头或末尾'"）；packages/neuro-book/src/plugins/editor/shared/contracts.ts 的 `EditorDeclarationSchema`；docs/proposals/workbench-shell-abstractions.md 对象模型
- 核实：编辑器贡献点 `editor.editors` 的声明靠 `selector`（文件后缀/文件名）认领文件，输入是文本或字节，文档是文件。Editor Part 是"组与标签归编辑器插件"。工作台的 View 是工具面板（侧栏/辅助栏/面板），不是文档。提案从头到尾没说条目页是：
  1. 编辑器区里的一个标签页（那它的"文件"是什么？条目若在数据库里就没有文件，`selector` 无从匹配；就算条目是文件，页面还要带位置参数和 Tab 状态，不是一个文件一个编辑器）；
  2. 侧栏或面板里的一个视图（那就没有"标签页"可开多个条目，作者无法并排看两个人物）。
  条目树放在哪（资源管理器的 `.content` 渲染，还是独立视图）、点正文里的人名打开条目、从情节 Tab 的变更跳到章，也都依赖这个。t09（存储）与本提案互相等对方；但如果存储选了"全部放进数据库"，现有编辑器贡献点就需要新增"虚拟文档"类型，这是平台改动，应当列入第五节影响和第六节 Spec 预期改动（现在 Spec 清单里没有 workbench.editor）。
- 建议：提案补一段"条目页的载体"，并把对编辑器贡献点（虚拟文档、不靠 selector 认领）或对 View 模型的要求写进"影响"；多开条目、从正文人名跳转、并排比较两个位置各给一句。

### 9. 立绘/图片字段：nb-form 没有图片控件，"按形态各存一张"落在 Record 上又退成 JSON 文本框
- 严重程度：重要；类别：接口
- 位置：第四节 5（人物：带表单和图片，"立绘按形态各存一张"）、第六节 Spec 预期（"ui/forms.md：Component 的表单与图片控件"）
- 核实：packages/nb-form/src 全文搜 image/upload/file 无命中；docs/specs/ui/forms.md 非目标明写"文件选择"不承诺，内建控件清单里没有图片；Spec 状态仍是 planned。可以登记自定义控件（输出 22），所以做得出来，但要写：上传入口（作者不碰文件，所以需要一个"把图片放进作品并生成稳定路径"的服务）、缩略图（`MarkdownImage` 的 `resolveAsset` 是现成的解析接口，可复用）、替换/删除、被条目改名后路径跟随。
- "形态各存一张"：这是 `形态 -> 图片` 的映射。nb-form 对 `Record`（patternProperties）降级为 JSON 编辑，作者会看到一个写路径字符串的 JSON 文本框。要画成对象列表（形态名 + 图片）就要在 schema 里写成 `[{形态, 图片}]`，并且形态名要与 `character.形态` 的枚举联动（动态选项源可以做到，但是调用方的事）。
- 另外提案说 Agent 拿到的是"图片路径和说明"，作者表单里没有"说明"字段。
- 建议：把"图片控件 + 资产上传服务"作为 nb-form 与平台的前置依赖列入第五节，并把立绘的 schema 写成列表形式；字段清单（t10）里补"图片说明"。

### 10. 自由命名空间在 nb-form 里就是 JSON 文本框；"这个值随剧情改过"的标记没有承接
- 严重程度：重要；类别：接口/遗漏
- 位置：第四节 2（自由命名空间）、待定项 7；docs/specs/ui/forms.md 输出 1、14；t10 README 的"要补的控件"
- 现象 A：自由命名空间"作者随手加字段，不需要 schema"，意味着形状开放。forms.md 输出 1 明确：没有 `properties` 的开放对象、`Record` 都"用 JSON 编辑"。作者想随手记一个"血型：O"，看到的会是等宽 JSON 文本框，要自己写 `{"血型": "O"}`，对作者是反门槛；而且没有 schema，数值加减、核对点、"数值/文本"的补丁种类都无从判定（补丁种类要知道字段类型）。
- 现象 B：作者在"第 30 章末尾"视图的人物 Tab 里看到外貌，想知道它是不是初始设定、哪一章改过。提案只有面板 Tab 有"流水"，人物 Tab 没有；t10 把"随剧情变化的字段（显示当前值、点开看各章各线的变化）"列为 nb-form 要补的控件，但内核提案没有把它当作必要依赖。没有这个标记，作者在按章查看里无法区分"这是初值"和"这是第 12 章改的"，"按章看"就失去一半价值，而且前面第 2 条的"改正"确认也缺少依据。
- 建议：自由命名空间限制为"键值对列表"（键、值、类型三选一：文字/数字/开关），用对象列表控件即可画出；字段装饰（"此值与初值不同，最近一次改在第 N 章"）进 nb-form 的 FieldShell 扩展，列入依赖。

### 11. 每次改值都问"剧情变化还是改正"、每次都要描述，会打断写作
- 严重程度：重要；类别：体验
- 位置：第四节 3 末段、7（"填的都是初值，记为创作修改"、按章看）
- 现象：提案要求"作者在界面上改一个值时，界面要问这是剧情里的变化还是改正"，并且"作者和 Agent 的修改都记录在案，并且带描述"。设想一个作者在 30 章视图里连改外貌、年龄、两个数值，每个字段弹一次二选一加一次描述输入，会严重打断。
  对照同类工具：Notion、World Anvil、Scrivener 的设定页都是直接编辑、没有"改的是故事还是设定"的区分；Plottr 把"随时间变化"做成单独的时间线卡片，由作者主动建，而不是每次编辑时问。
- 更别扭的是：这个问题的答案多半能推断。
  - 在"初值/前史"位置编辑 → 只能是创作修改；
  - 在"写作进度"（最新）位置，作者通常在补设定 → 创作修改，除非他明确点了"记一笔剧情变化"；
  - 在第 N 章位置 → 默认剧情变化（因为位置是明确的）。
  "写作进度"本身也没有定义：是最后一个"已写"变更所在的章，还是编辑器里当前打开的章？没有"跟随当前编辑的章"的选项，作者在正文里点一个人名打开条目，应当自动落在那一章，而不是停在上次的位置。
- 建议：默认按位置推断，改值不弹框，在值旁边留一个"这是剧情变化 / 这是改正"的可改标签（事后可更改）；描述自动生成（"魔力 3200→3110"），作者想写再写；条目页位置默认跟随正在编辑/阅读的章，从正文点人名时带着那一章打开。

### 12. 面板的字段声明是"每个条目各声明一遍"，作者要懂 schema，也没有复用
- 严重程度：重要；类别：体验/遗漏
- 位置：第四节 5（面板：作者声明字段；类型提供，实例只给数据和配置）、7（手动建一个人物第 3 步）
- 现象：声明发生在实例上。写一个有 20 个人物的 RPG 向小说，每个人物都有"魔力/存款/回溯次数"，作者要重复声明 20 遍，星瑕的每个马甲（子条目）也各有自己的面板，再来一遍；没有"复制自另一个条目的面板""题材预设面板""改一处，全体跟着改"。声明本身要作者回答：字段名、类型、上限、枚举、能否为负——这是在设计 schema，对非技术作者负担重。
- "上限"是个坑：示例里 `魔力 3110/12000` 的 12000 看上去是静态配置，但魔法少女升级后上限会变，上限若是静态 schema 属性（nb-form 的 `maximum` 是静态的），则剧情里升级需要改声明；若上限是另一个字段，则面板需要"字段引用字段"这种声明。提案没有说。
- schema 改动（改字段名、改类型）的后果在待定项 6 里只说"生成一条创作修改迁移"，界面上要展示什么、会不会弹出一堆受影响变更，也没有写。
- 建议：面板的字段声明放在"可复用的字段集（模板）"上，条目上选用；上限允许写成另一个字段；声明界面用预设起步（金钱、体力、等级……）。若这样改动较大，至少把"重复声明"写入待定项，让开发者知道代价。

### 13. 几百个条目怎么找、怎么看：条目树之外没有任何导航能力；条目树的语义被重载
- 严重程度：重要；类别：遗漏/不变量
- 位置：第四节 1（条目树"只用来组织和浏览，不表示地理上的包含或组织上的从属"）、待定项 5（马甲做成子条目，"父子关系就表示身份同一"）；旧应用 Character Workbench 提案第一、六、七节
- 现象 A（遗漏）：提案里作者找条目的路径只有条目树。旧应用的 Character Workbench 提案对这件事花了大量篇幅：收藏（Pinned）、主要角色/绑定角色分组、按标题前缀→标签→摘要→关系对象分级的搜索、底部可折叠信息面板。本稿既没有标签/状态（草稿、弃用）/收藏，也没有搜索条目的入口（`lookup` 是 Agent 的工具；作者界面的搜索没有提到），也没有"最近打开""本章涉及的条目"这类写作中最常用的入口（写到第 30 章，要的是"这一章出场的人"，而不是整棵树）。几百个条目只靠树，是 Scrivener 的文件夹式体验，没有 Notion/World Anvil 的筛选与视图。旧提案本身标记为"历史素材，不是现行合同"，但它里面的需求是真实的。
- 现象 B（不变量）：概念表说树只用来组织，待定项 5 却让树里的父子关系表示"身份同一"（马甲）。作者把一个人物拖进"人物"文件夹，或把马甲拖到别处整理，就在改变身份关系，而界面上看不出来；反过来，要建 5 个马甲需要先把它们挂在本体之下，与"按类型整理"互相打架。
- 建议：A：把条目列表的搜索、按 Component 类型/标签筛选、"本章涉及"（由变更日志直接给出）列入作者界面的最低要求；B：马甲的身份同一不要靠树的父子表达，用待定项 5 的另一种（连接）。或树的父子关系对马甲有明显的视觉区分并限制拖动。

### 14. 情节 Tab：语义检索没有基础设施，"问一句"与 Agent 对话重复
- 严重程度：建议；类别：体验/接口
- 位置：第四节 5（情节：关键词与语义检索、"问一句"调用模型在筛出的结果上回答，每句标出处）、第五节成本
- 核实：新应用的 packages/neuro-book/src、nb-harness/src、docs/specs 里没有嵌入（embedding）服务；第五节只写"检索要算嵌入"。nb-markdown 的出处约定是"宿主先把出处改写成链接，本包不认纯文字的出处"（README 宿主接入第 5 条），所以"每句标出处"需要宿主定一种变更/章/段落的链接目标并做点击打开，这部分也是新写。
- 问题：
  1. "问一句"是 Tab 里的小型对话，作者本来就有 Agent 对话，且 Agent 有 `read(条目, view: 情节, query, …)`。两处同样的能力会有不同的行为（Tab 里的模型、上下文、格式不同），出错还要各修一次。nb-story 的评测（提案第三节自己引用）说"用图作答的失分多是照搬图里记错的内容"，直接在 Tab 里给一个看上去权威的回答，会比在对话里更容易被信。
  2. 语义检索在第一版没有嵌入就做不了。
- 建议：第一版情节 Tab 只做分页、按章/剧情线/状态筛选和关键词检索（SQLite FTS 即可）；"问一句"改成按钮"带着这些筛选结果去问 Agent"，跳进 Agent 对话；语义检索等有嵌入服务再加。

### 15. 新建作品、发故事种子之后，作者第一次看到的是什么：没有设计，也没有创作修改的审阅
- 严重程度：重要；类别：体验/遗漏
- 位置：第四节 7（开始一部作品第 3 步"作者审阅：建了哪些条目，记了哪些前史，还有哪些待确认"）、待定项 8
- 现象：一份故事种子之后，Agent 可能一次建 20 到 40 个条目、几十条前史变更、10 来个待确认。提案的 9 节例子只有 7 条前史、2 个人物，没有量级概念。界面上要回答的问题至少有：
  1. 审阅的单位：条目（创作修改）和前史变更（剧情变更）是两类东西，前面第 5 条说过创作修改不在记账审阅里。作者第一眼应当先看哪个？
  2. 待确认是阻塞项（"双王"指什么，不回答 Agent 后面的记账都会带着猜测）还是普通项；作者的回答怎么进系统（回复一句话？表单？），回答后是由 Agent 改条目，还是作者直接改；这个闭环提案里没有。待确认可以借 nb-form 的"Agent 向用户提问"（forms.md 的调用方之一），但那里是一问一答的对话，而不是一张清单。
  3. 一次看 40 个条目的体验：建议按"待确认 → 条目（按 Component 类型/按重要性）→ 前史时间线"三步，每步一屏，而不是一张长表。
  4. 空状态：新建后没有任何条目时条目树、条目页和按章视图显示什么？提案没有写，第一次打开 Component 的 Tab 是空表还是引导。
- 建议：提案第七节补一个"首次审阅"小节，至少定：审阅分三组，待确认优先，条目逐个"确认/改"，前史做成时间线；空状态给"把故事种子交给 Agent"的入口。

### 16. 渲染失败、引用悬空、条目在该位置不存在：作者界面没有定义
- 严重程度：建议；类别：遗漏
- 位置：第四节 2（条目身份）、5（去掉 Component）、6（渲染）、待定项 6
- 现象：
  1. 主 MDX 引用 `{panel.魔力}`，而这个条目在该位置没有面板（Component 被去掉并隐藏数据、字段改了名、面板是第 10 章才加的）。MDX 表达式求值得到 undefined，作者看到的是空白、报错还是字面量？
  2. 条目没有"出场/创建于哪一章"这个属性（身份只有 id、名字、别名、描述、位置）。第 3 章的视图里，第 5 章才出场的人物是否出现？作者看到会剧透自己的计划，Agent 自动预查把它当作已知名字注入会让写手提前引用。
  3. 引用别的条目 `<引用条目>` 指向被删除或改名的条目：悬空怎么显示，改名后引用是否跟随（引用靠 id 还是名字）？
  4. 渲染时出错的 Tab（Vue 错误边界）工作台已有"重试"（workbench-shell-abstractions 第 4 节），可以直接用；但"状态读不出来"（快照缺失、重算失败）没有对应的界面。
- 建议：引用统一靠 id 且悬空时显示"已删除的条目"灰色小块；条目加一个可选的"出场章"，在更早的位置默认隐藏或标"尚未出场"；MDX 里读不到的字段显示成带警告的占位小块，而不是空白或整篇失败。

### 17. 审阅界面要展示"出处"，但出处是对一份还在被作者修改的正文的段落引用
- 严重程度：建议；类别：接口
- 位置：第三节日志字段"出处：正文 1.21–1.30"、第四节 7（审阅本章的变更）
- 现象：记账审阅的核心是对着出处核对变更对不对：左边变更，右边它依据的那段正文。出处写成"正文章.段"的位置范围，而作者写完一章记账后常常还要改稿；改稿后段号漂移，审阅或之后回看时出处指到别的段落。v2 的正文是用户编辑的 Markdown 文件，没有稳定的段落身份（nb-story 的段号是只读书库里固定的）。提案把改稿后的重新记账推给 t22，但界面上"点出处跳到正文那一段"的体验在 t22 之前就会坏。
- 建议：变更记录同时存一份被引用段落的摘录（几十字的原文片段）；审阅界面显示摘录，点击跳转时用摘录做模糊定位，找不到时提示"正文已修改"，而不是跳到错的位置。

### 18. 位置选择器：选项不全，几百章时不可用，且"按计划"视图在作者界面里没有入口
- 严重程度：建议；类别：遗漏/体验
- 位置：第四节 4（"按计划"视图）、7（按章看）
- 现象：第 4 节定义了三类位置：某章开头/末尾、初值（前史之前，创作修改设定的）、按计划视图；第 7 节的选择器只有"第 N 章开头或末尾"加默认写作进度。作者在哪里看"初值"（创作修改的对象，第 7 节手动建人物时填的正是它），在哪里切到"按计划"（看"照计划第 N 章会是什么样"，提案自己说这是用途），选择器没有写。连载几百章时"第 N 章"也不能是一个下拉；开头与末尾又让每个选项翻倍。大多数作者并不会用"章开头"思考，他们想要"现在""写这章之前""某个剧情点"。
- 建议：选择器写成"初值 / 前史末 / 第 N 章（开头·末尾切换）/ 按计划 / 当前"，N 用可搜索的章列表（复用 nb-ui 的 `SearchSelect`，nb-ui 有该控件），"当前"跟随正在编辑的章；默认只露出"当前"与"初值"两个，其余折叠。

### 19. 旧应用里有、本稿没有的"控制 Agent 是否看到这个条目"的能力
- 严重程度：建议；类别：遗漏
- 位置：第四节 8（自动预查：只按名字与别名精确匹配）、待定项 9；旧应用 Character Workbench 提案 J 节（retrieval.keywords、injectionPriority、aliasTriggers）与"Lorebook/注入"页签
- 现象：旧应用人物表单有"检索与注入"一组（触发关键词、注入摘要、优先级、是否启用），因为人名/别名在中文里常是普通词（"彗""书""任务""魔偶"），按名字精确匹配会误命中并把一串目录注入。本稿的自动预查只有"匹配名字与别名"，作者没有地方关闭某个别名的匹配、或者设置只在某些情况下匹配，也没有"这个条目作者想让 Agent 一直带着"的置顶。作者界面唯一的入口是别名列表本身。
- 这是旧版积累的真实需求，不是过度设计；但它也可能放进 t10/t23，所以只作为建议：至少让别名带"只在带引号/上下文时匹配"或"不作为触发词"的开关，条目带"常驻"开关，并在提案里写明这件事归谁。

## 对"七、待定项"的判断
1. 名字：这是界面文字的一部分，作者每天看到，推荐"法典"可以，但最好先用作者的话测一下（"设定库/世界书"这类词在 SillyTavern 圈已经通用），结论不挡审阅。
2. 存储形态与 nb-history：见第 5、8 条；nb-history 只承接"落成文件"的部分，记账审阅必须自己做，存储选数据库时条目页的载体还要平台改动，这一项应当和条目页载体一起定。
3. 与 nb-memory 的关系：与前端无关，没有意见。
4. 剧情线与章做成条目：界面上会给条目树多出两类特殊条目，章条目需要与活页夹同步（folder-kinds 里章节编号是稳定身份）；如果做，条目页载体要能区分"可编辑的条目"和"只读投影的条目"，建议在第 8 条里一并定。
5. 马甲做子条目：与条目树"只用来组织"冲突，见第 13 条；建议用连接，或把父子关系做成明显的特殊标记。
6. 去掉 Component、schema 变化：推荐"保留、隐藏、可恢复"在界面上要有"已隐藏的数据"入口，否则作者不知道它在；改字段名生成迁移会让作者面对一堆受影响变更，见第 12 条。
7. 自由命名空间：推荐"要"有理，但在 nb-form 里就是 JSON 文本框，见第 10 条，要限制为键值对列表。
8. 记账结果的审阅：推荐的"整章接受、单条驳回"缺少审阅状态字段和并发条件，见第 4、5 条；"待确认"的闭环见第 15 条。
9. 自动预查：只按名字精确匹配可行，但作者需要至少一个关闭误命中的开关，见第 19 条。
10. 计算字段与历法：第一版不做合理；界面上"年龄先当普通字段，由作者或记账员修改"与按章视图联动，年龄在不同章里取值不同，由手动维护，要有"这一章年龄是不是该变了"的提示，否则第 30 章的年龄会一直停在第 1 章；可进记账说明。
11. 带值渲染能否还原：属于领域与实现审查；从前端侧看，还原到的是主 MDX 源文，作者界面里没有展示"带值写法"，所以不影响作者，但必须保证渲染块隔离（第 7 条），否则 Agent 对源文的反向定位在某一块失败时会连累整篇。
