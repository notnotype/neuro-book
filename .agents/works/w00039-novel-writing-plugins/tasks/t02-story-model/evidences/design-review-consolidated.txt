一、发现编号写法
- A1 到 A18、B1 到 B19、C1 到 C11：各报告自己的 `### N.` 编号。
- E1-N、E2-N：作者体验记录末尾“问题清单”的第 N 条（E1 共 21 条，E2 共 19 条）。清单条目注明的“步骤”另写成 E1-步骤5a、E2-步骤7 这样，只在清单没有单独成条、但内容有用时引用。
- F1-任务M-第K条：F1 第 M 个任务“体验问题”里的第 K 条；F1-汇总N：F1 最后“体验汇总”的第 N 条；F1-回写N：F1 末尾“复盘回写建议”的第 N 行。
- F2-任务M-(K)：F2 第 M 个任务第 4 节“不够用、别扭、差点做错”的第 K 条；F2-汇总N：F2 最后“汇总”问题清单的第 N 条（共 18 条，分 P0、P1、P2）；F2-带值N：汇总里“带值渲染 用起来怎样”的第 N 条；F2-分不清N：汇总里“分不清的部分”的第 N 条；F2-任务4-长N：任务 4 第 3 节“会变长的部分”的第 N 条。
- C 报告另有一条“更正”（修正 C10 的数字、C8 对自由命名空间的说法），不算发现；A 到 C 报告里对“七、待定项”的逐项判断不单独编号，用到时写成“待定项 N（某报告）”。

二、严重程度
- A、B、C、E1、E2、F1 使用阻断、重要、建议。E1 的唯一一条阻断标注为“条件性”（见主题 6）。
- F2 不用这三级，用 P0（会让 Agent 写错账或写错章节）、P1（结果质量下降）、P2（体验细节）。本文把 P0 折算为“重要”，P1 折算为“重要或建议”（按内容判断并写明），P2 折算为“建议”，同时保留 F2 的原标签。
- “最高严重程度”取各报告给出的最高一级，并写出各报告各自的级别。

三、质疑决定
- 决定一栏以 decisions.txt 为准，用决定里的原话引用。“是”表示报告明确指出决定本身有问题或没有理由；“弱”表示只质疑决定的某个后果、依据或预留的槽位，没有要求推翻；“否”表示没有。
- 报告对提案里“七、待定项”（尚未成为决定）的质疑不算质疑决定，但会写明。

四、范围
- 只归并设计与工具层面的发现。F1、F2 在任务 1、2 里对第 4 章细纲和正文给出的“吃书、吃设定、严谨”意见（例如 300 神典石付不起、东部到中心城区两小时）是对样本书内容的审查，不是对提案的发现，不在这里。
- 有的发现同时说了两件事，会在主要主题里完整列出，在另一个主题里标“（部分）”。

五、主题顺序
- 第一部分正确性与不变量（主题 1 到 11），第二部分接口与工具（主题 12 到 22），第三部分作者体验（主题 23 到 31），第四部分文档与范围（主题 32、33）。每部分内按影响排序。
- 文末有“只出现在一份报告里、没归进任何主题的发现”“各报告认为做得好的地方”和主题索引。

主题 1：计划、已写、待审三种状态混在一起，兑现、取消、替代计划和未接受的记账结果都没有规则
----------------------------------------------------------------
涉及发现：A1、B4、E1-2、E2-2、F1-任务1-第1条、F1-任务2-第3条、F1-汇总1、F1-回写1、F2-任务2-(5)、F2-汇总10（兑现这一半；“章末悬案”那一半见主题 30）。
最高严重程度：阻断。各报告：A1 阻断；B4 重要；E1-2 重要；E2-2 重要；F1 三处都是重要；F2-汇总10 为 P1，F2-任务2-(5) 未分级。
问题描述：日志的状态只有“计划／已写”，而记账又要求先由 Agent 提出、再由作者审阅、可逐条驳回。提案没有定义未接受的已写提案是否参与真相，也没有定义兑现计划是把原记录转成已写，还是新增实绩并连接计划；取消、改排章、只兑现一部分、重复记账都没有状态转换。A1 的反例：初值 100，已接受的第 3 章计划 -20，记账又产生一条已写 -20，按“折叠所有已写和计划”得 60 而不是 80；原地改状态则实际只花 15 或分两章兑现时又保留不了原计划。F1 在样本书上遇到同一件事：细纲计划“-300 买药 S”，实际正文是“-50 买药 A”，救人和离场没有发生，两种状态表达不了“被替代的计划”，旧计划留着会让按计划状态继续扣 300、继续等救人。E2-2、B4 从另一头说同一件事：作者不审阅时，未接受的变更若不算进状态，下一章写手拿到的是旧状态，若算，Agent 的错误已经成了真相；E1-2 补充，前史默认“已写”，Agent 起草的内容与作者原话在界面上没有区别。
质疑决定：否。A1 明确“保留‘计划是未写变更’的决定”，问题是缺转换规则。
各报告的改法：
- A：把发布／审阅状态与计划／实绩分开；变更给稳定 id；兑现采用唯一一份有效补丁，或显式 supersedes／realizes 连接；规定部分兑现、取消、重排、重复记账的幂等规则；真实状态、按计划状态和搜索统一用同一个“有效记录”判据；整章接受原子发布。
- B：日志加审阅状态（待审、已接受、已驳回），并把“未审阅是否参与状态”的默认值定死；界面推荐“默认接受，只把有问题的项（核对点不符、待确认、超出计划）标红要求处理”。
- E1：前史、草案、已定三态明显区分，作者没确认的不算进状态。
- E2：写明未接受的变更是否参与渲染，并在渲染里标“有 N 条未确认”。
- F1：给出更新既有变更、兑现引用、取消或替代的持久表示；计划修订和本章实际补丁放进同一审阅批次、原子提交；被取代的计划保留审计但不参与按计划状态（F1-回写1）。
- F2：write.change 加“兑现 <编号>”字段或让连接允许“兑现”；变更可带“未收束”标记。
D 的做法：变更状态只有“生效／撤销”（撤销不删，折叠时跳过），没有“待审”态；记账默认生效、整批可一键撤销，拿不准的进“待定”而不是挂成待审变更；情节自己有“计划／已写／放弃”三态，计划转已写；记账幂等键是（章，正文哈希），重记时撤销上一批里作者没碰过的项。

主题 2：补丁没有可执行合同，核对点只报不修、覆盖有限，也替代不了 broken-relative
----------------------------------------------------------------
涉及发现：A2、C6、E1-步骤6b（属 E1-6）、E2-4、E2-步骤5c（属 E2-18 后半）、F1-任务2-第1条、F1-任务2-第2条、F1-汇总2、F1-回写2、F2-汇总15、F2-带值4；F2-任务1-D1（“真名第一次交代不是世界变化”）作为同类例子。
最高严重程度：阻断。各报告：A2 阻断；C6 重要；E1-步骤6b 重要；E2-4 重要；F1 三处重要；F2-汇总15 为 P2。
问题描述：提案保留数值加减和列表增删，却说核对点“替代了旧版 broken-relative 那种断掉的失败方式”。但提案没有规定补丁遇到缺字段、类型错、列表元素已不存在、上限或非负约束被历史修改破坏时的结果；核对点对不上之后也没写修复动作、报警期间面板显示累加值还是正文值、一次错误后后面每个核对点会不会连环报警。A2 的反例：初值 100，第 2 章 -20，作者删掉初值字段后 -20 无法运算，正文没报余额就连核对点都没有；缺值当 0 会算出 -20，跳过坏补丁则伪造有效状态。F1 在样本书上的反例：正文 4.49 的“200 启动资金”已经是面板初值，按文字“给了启动资金”记账会重复入账成 +200；4.50 与 4.51 两次提到 50 其实是同一笔；而 write.change／edit 根本没有保存核对点的字段。E2-4 指出范围太窄：任务奖励这类不在面板上的数字记错了，没有任何程序报警。
质疑决定：否。
各报告的改法：
- A：先定可执行补丁合同——类型、缺值、数值精度、列表元素稳定寻址、约束与前置条件；核对点只负责正文与计算值的差异；重算失败返回定位到变更或字段的持久问题，受影响位置标 unresolved／conflicted，不当作完整状态交给写手；多条目变更要么整体可用，要么整体报冲突。
- C：借 Beancount 的 balance 断言（凭记忆）：核对失败等于待处理项，唯一的修复路径是插入一条带描述的校正变更；写明显示规则。
- E1：报警里直接给三个选项：改设定、改正文里的数、放弃改正。
- E2：任务、奖励这类数字也要能被核对，或至少集中列出来让作者对原文；随填的初值没有凭证，与以后正文冲突时的规则要写。
- F1：核对点最小合同（字段路径、正文原值、出处、比较位置与顺序、结果），允许“只确认既有值、不产生新补丁”，同一笔交易的重复提及引用同一账项；数值输出附稳定来源或流水 id，区分“披露”和“新交易”。
- F2：列表补丁用名字或 id 寻址，不用 `panel.任务[2]` 这样的索引。
D 的做法：set 可以带 assert（正文写明的总数），折叠时与前面累加的结果校对，对不上是“报告而不是中断，以后者为准”；set 和 assert 都重置基线，所以往前补写变更只让后面重算，不会像旧 WorldEngine 那样断链。数值加减由程序算；入账前程序校验引用的条目存在、字段类型对得上、assert 通过、出处原话确实在正文里，不过的退回重试一次，仍不过进待定。

主题 3：“改正”（创作修改）在非初值位置没有语义：改初值、改某条变更还是新增事件，界面和 Agent 都无从落笔
----------------------------------------------------------------
涉及发现：A3、B2、B11、E1-6（含步骤6a、6e、6f；步骤6c 见主题 31）、E1-8（步骤3c）、E2-15（含步骤4f）、F1-任务2-第6条、F2-分不清1至6、F2-汇总（结尾“剧情变更与创作修改分得清分不清”的结论）。
最高严重程度：阻断。各报告：A3 阻断；B2 重要、B11 重要；E1-6、E1-8 重要；E2-15 建议；F1-任务2-第6条 重要；F2 认为二分“在作者说得清楚时好用”，但边界上 Agent 会静默选错，选错的方向都是全局性的。
问题描述：提案说创作修改“改变的是设定本身，所有位置都跟着变”，状态公式却只有一个初值加剧情补丁；界面在历史位置改值时只问“剧情变化还是改正”，没有改正的目标（初值、产生当前值的那条变更，还是新增抵消事件）、作用区间，也没有误分类后的改类协议。A3 的反例：初始存款 100，第 3 章设为 80，第 8 章 -10；作者在第 5 章视图把 80 改成 90 选“改正”——改初值会被第 3 章覆盖（第 5 章仍是 80），改第 3 章赋值则影响第 3 章起所有位置，在第 5 章加 +10 又把创作纠错写成虚构剧情。E1-步骤6a 是同一场景：作者在第 10 章看着存款，想表达“开局存款应是 52000”，系统理解成倒推初值还是只改此刻不明。反方向的问题是每次改值都弹二选一再要描述会打断写作（B11），而 E2 的“Agent 记错了”两个选项都不是（E2-15）；F2 补充了第三类：“从第 N 章起设定不同”既不是剧情变更也不是改正，需要“设定分叉”。
质疑决定：否。决定里没有规定改正的目标；F2 要求补“设定分叉”第三类，属于补充，不是推翻。
各报告的改法：
- A：创作修改定义为对某条初值、剧情变更或主 MDX 版本的修订，显式记录 targetId、基准版本、修订 diff；作者在历史位置改值时先解析来源，让其选择“修订来源”还是“新建剧情事件”，预览实际受影响区间；允许分类纠正并原子重算，保留原决定与修订史。
- B：界面层最小做法——改正只允许对“产生当前值的那条变更”或“初值”二选一，确认框里列出下游受影响变更与新旧值（B2）；按位置推断默认值、改值不弹框（初值或前史位置→创作修改；最新位置→默认创作修改；第 N 章位置→默认剧情变化），值旁留可事后修改的标签，描述自动生成（B11）。
- E1：改正时直接选“改开局初值”并说清影响哪些章；原因可不填；改完给“改了什么、影响哪几章”的汇总并可撤销；作者填的初值永远是“第 1 章开头的样子”，系统自己倒推（E1-8）。
- E2：选项用大白话——“是故事里发生的”“是我记错了、改主意了”“Agent 记错了”。
- F1：记账结果显式分成“事件补丁”“设定与正文冲突”“修订候选”，不让一个自动 apply 路径混用。
- F2：无时间标记的“改一下”要有追问或默认规则；增加“设定分叉”第三类；write 时强制填一句“为什么归这类”，拿不准时直接问作者。
D 的做法：把“改正”与“变化”作为数据模型里的二选一，界面和 Agent 的每次写入都必须选其一；追踪字段（数值、持有物）默认记为变化，其余字段默认记为改正，字段旁有小开关；改正后做一次零模型“涟漪检查”，列出引用该字段的变更和情节。D 自己把“改正与变化能不能让人不犯错”列为最没把握的第一件事，退路是不让作者选，一律先记为变化，由 Agent 在回执里问。

主题 4：文本补丁与三方合并没有基准、没有持久的解决记录；整值覆盖易抄错；这条路线没有记录的理由
----------------------------------------------------------------
涉及发现：A4、C2、F1-任务3-第5条、F2-汇总7、F2-任务3（“补丁写法上的问题”、“不顺的地方”第2条、“不确定”(e)：同一字段两条消息先后作用）、F2-带值2；E1-21（主 MDX 要能看“相对上一章改了哪几行”）与本主题相关，主归主题 27。
最高严重程度：阻断。各报告：A4 阻断；C2 重要；F1-任务3-第5条 重要；F2-汇总7 为 P1（折算为重要）；E1-21 建议。
问题描述：主 MDX 与长文本存 diff，改过去时做三方合并，失败让 Agent 起草、作者确认；同时提案又承诺快照随时可重建、渲染结果只依赖输入。没有规定 diff 绑定哪个基准文本或版本、作者确认后的合并结果作为哪条记录保存、冲突期间能否发布新状态。A4 的反例：初始 MDX“黑色长发”，第 3 章补丁改成“黑色短发”；作者把初值改成“银色长发”，模型合并出“银色短发”，只写进快照则删缓存后重放又要调模型、可能得“黑色短发”，写回初值则第 3 章以前提前变短。C2 补充：提案自己承认“程序看不出语义上的过时”，所以合并只解决机械冲突，却引入了合并算法、冲突界面和 Agent 提合并写法这一整条功能链，且备选表对“主 MDX 只有创作修改、不随剧情改”只写了“否决（开发者 11-01）”，没有理由。实际任务里：苏天晴的外貌是一整串长文本，改眼色只能整值覆盖，抄错一个字就是静默破坏设定，先 edit 再计划 change 还容易用旧整串回滚刚改的眼色（F1、F2）。
质疑决定：是（C2）。C2 质疑决定“主 MDX 也能打补丁”以及其理由“文本 diff 用三方合并”：决定表和备选表只有结论，没有理由，属于“没有记录的理由”，并给出更简单的做法。A4 不推翻决定，只要求补合同。
各报告的改法：
- A：每个文本补丁保存 source revision 或 base hash 与可重放内容；合并建议只是待审数据，作者接受后形成绑定冲突输入版本的持久解决记录，再原子发布整条变更；重放和 read 禁止调用模型；未解决的分支或字段给结构化冲突，旧的有效版本可读但必须标明。
- C：第一版文本字段按“位置起整段替换”存，diff 只用来显示；随剧情变化的文字用状态字段加模板引用（例如 `{character.appearance}`），主 MDX 本身只由创作修改改，三方合并整块删掉，等有证据再加；若保留 diff，要先写清渲染视图上的编辑固定落成哪一种，以及补丁套不上时标“失效”、其后的值是否照算。业界参照（凭记忆）：Novelcrafter 的 Codex progression 是追加一段说明，不是 diff。
- F1：经常独立变化的特征（头发、眼色）给独立字段，或至少返回字段级版本与三方合并冲突。
- F2：字段支持“把 A 替换为 B”的局部替换，或规定“带引号的多句字符串一律走 diff”；同一字段两条消息先后作用时，整值覆盖会互相覆盖，顺序与合并方式要明确定义。
D 的做法：没有文本 diff，也没有主 MDX。条目介绍由若干“块”组成，每块是作者写的字、对原文的摘录或 Agent 写的字，各带 origin；随剧情的补充文字“只追加”，晚于该位置的视图才可见；字段操作只有 set、add、remove。

主题 5：没有读写版本和原子发布的边界，过期提案能被写成当前真相，缓存失效条件也没定
----------------------------------------------------------------
涉及发现：A5、B5（部分：第 5 点并发条件，主归主题 6）、C10（部分：日志所有权与并发、读写分离、失败语义，主归主题 33）。

问题描述：提案允许作者与 Agent 同时改，Agent 还可直接写文件，但工具的读写、记账审阅、跨条目补丁和快照都没有 expectedRevision、冲突结果或事务边界；缓存只有“按章”一维，没说初值、变更版本、章节编排和计划模式变化如何使其失效。A5 的反例：Agent 读到余额 100，准备设为 80；这期间作者已纠正为 150，接受旧提案就覆盖了作者的修改；一次转账 A -20、B +20 若只发布 A，读者会看到钱凭空消失；后台重算期间读到旧 A、新 B，得到的“同一章状态”不是一份世界状态。B5-5 指出记账审阅有同样问题：页面上看到 10 条，点接受时已变成 12 条（nb-history 为此有 acceptAtRevision）。C10 补充，提案没回答日志归谁所有（作者、Agent、多个会话同时往一本书的日志追加，而 nb-history 的已知限制是单进程单写者）、折叠在后端还是前端算、写时校验还是读时校验。

- B：记账审阅同样要并发条件，并写明审阅批次的边界（一章一批，还是一次 Agent 运行一批）。
- C：把“日志的所有权与并发”“渲染运行位置”“失败语义”补进取舍表；写清读写分离（日志是真相，状态与渲染是读模型）。

主题 6：Agent 直接写作者的东西后，作者看不到改了什么、还原不了；nb-history 承担不了逐条审阅和创作修改
----------------------------------------------------------------
涉及发现：E1-1（含步骤5a、6f、8b）、E2-3（含步骤4e、7d）、A18、B5（第 1 至 4 点）、C4（第 4 个现象：直接写入绕开日志）、A5（部分：外部修订导入）。
最高严重程度：阻断（条件性，来自 E1-1）。各报告：E1-1 阻断，条件是“若有一个按时间排、每条能还原的‘Agent 改了什么’清单则解除”；E2-3 重要；A18 重要；B5 重要；C4 重要。
问题描述：决定允许 Agent 直接写作者的文件，提案用“靠修改历史与作者审阅兜底”带过，但作者流程里的“审阅”只覆盖本章变更，创作修改（Agent 顺手改初值、改彗的外貌、重排主 MDX）没有任何查看或还原入口。支撑这个兜底的 nb-history 实际上不能用：审阅单位是文件路径，按文件接受、整份还原，同一日志文件里的第 3 条记账无法单独驳回（A18）；全放数据库时它看不到；Agent 绕文件服务写入只归因 external，不会触发收件箱；新应用里还没有 history 插件和收件箱界面，“复用”是先建插件再建 UI（B5）；保留策略会稀疏旧历史，不能当永久凭证。C4 补充，绕开日志的直接写入没有描述和出处，与目标 3“每一处变化都有描述和出处”矛盾。E1-1 的放弃条件是“没有这个我不让 Agent 碰设定，更不敢开自动记账”；E2 步骤 7d：自动记账加直接写文件，“两个兜底我都关掉了，就只剩理论上的历史”。
质疑决定：弱。涉及决定“Agent 可以写作者的文件，作者自己的修改也记 diff，不限制死”。C4 认为它让写入绕开日志；E1-1、E2-3 把“看不到、还原不了”当成作者不敢放权的条件；A18、B5 指出兜底依赖的 nb-history 接口不成立。没有报告要求推翻“允许 Agent 直接写”。
各报告的改法：
- E1：一个按时间排的“Agent 改了什么”清单，每条带描述，可一键还原。
- E2：“最近改动”列表，每条一句话加前后对比，可一键撤销。
- A：世界模型自己保存创作修订的目标、diff、描述、基准版本与审阅状态，逐条和整章操作都作用于模型变更集；nb-history 只复用于正文、手记、MDX 文件恢复和跨会话未见修改；若扩展 nb-history 支持逻辑资源审阅，须先定义新的操作与快照接口、保留策略和跨存储提交合同；直接写文件的导入审阅必须有明确来源或按外部变更进入模型队列。
- B：明确两套审阅——记账审阅是日志层自己的“批次加条目级状态加 revision”（只借 nb-history 的接受位点和条件式写入思路）；创作修改的审阅要么并入同一界面（日志层同样记 diff），要么只靠 nb-history 并写明只覆盖落成文件的部分。
- C：先写下“哪些写入口会绕过日志”以及每个口怎么补记；创作修改要么只是基线的审计记录，要么也做成日志事件（见主题 8）。
D 的做法：作者写的字块带 origin，写入工具在底层检查目标块，作者块一律拒绝，Agent 只能走“建议”队列；Agent 若仍用文件工具改了作者的文件，nb-history 收件箱列为 Agent 改动，健康检查发现作者块哈希变化。这与决定“Agent 可以写作者的文件”的方向相反。

主题 7：位置模型——“讲于第几章”不是全序，也不等于生效位置，补叙、回忆、开场状态和界面操作都没有落点
----------------------------------------------------------------
涉及发现：A7、A8、B1、C3、F1-任务1-第4条、F1-任务2-第8条、F1-任务3-第6条、F1-汇总4、F2-任务2-(7)、F2-汇总9。
最高严重程度：重要。各报告：A7、A8 重要；B1 重要；C3 重要；F1-任务1-第4条、任务3-第6条、汇总4 重要，任务2-第8条 建议；F2-汇总9 为 P1。
问题描述：提案只定了“按讲于的章序排，同一章里按出处段落顺序排，前史按作者给的先后排”。作为全序它不够：同段多事件、一个事件多出处、手记或界面出处、没有正文的计划、未排章的计划都没有落点和同位次序；章的稳定编号（folder-kinds 示例的章 id 顺序就是 1、3、2）和活页夹编排序没有区分，删章后引用怎么办没写；界面操作没有段落位置，B1 的现象是作者在“第 30 章开头”视图里改值，这条变更按定义落在第 30 章内部，保存后值弹回原值。作为生效位置它也不够：“讲于”同时扮演“在哪章讲出来”和“从何时起成立”。A7 的反例：前史已记“研究花掉 1 万”，第 20 章用回忆第一次写出这件事，记账新增已写 -10000 就重复扣钱，把原记录的讲于挪到第 20 章则第 1 至 19 章的余额多出 1 万。F1、F2 在样本书上撞到同样的缝：第 4 章补叙“下午买药”实际早于第 3 章末的夜袭，按讲于重放显示不出先后；“从第 5 章开始已剪短头发”不能由讲于第 5 章的补丁出现在“第 5 章开头”的渲染里；c01 出处是正文 1.15 却讲于“前史”。
质疑决定：弱。决定是“第一版的故事时间按‘讲于第几章’排序加前史”。A7 明说不重报这条决定本身，F1-汇总4 明说“故事时间精细化留 t04 是已接受的取舍”；但 F2-汇总9、F2-任务2-(7) 建议把“发生时间”和“讲于”拆成两个字段，C3 建议把“位置”做成不透明坐标类型，与“按讲于排序”的写法有分歧。
各报告的改法：
- A：第一版仍可用章序作近似的生效顺序，但记录须有稳定事件 id、有效位置（含前史序）、多个讲述或凭证锚；正文重述只补出处，不再加一次补丁；补叙放不准时标 unresolved 交作者安放；用 chapterId 引用身份，在 binder revision 下解释编排序；每个事件显式 orderKey 或稳定 tie-breaker，凭证只作证据；未排章计划不参与任何具体章状态；章被删或失联时产生待安放记录；编排变更参与 revision 与缓存失效。
- B：界面编辑的落点按视图位置定——“开头”视图的编辑落在“上一章末尾之后、本章第一段之前”，“末尾”视图的编辑落在本章末，给界面操作章首槽、章尾槽并写进排序规则；或规定非“末尾、前史、初值”位置的界面编辑只能是改正。
- C：每条变更存显式的、与出处无关的排序键（如分数索引）；“讲于”存章的稳定编号，章序由活页夹清单即时给出；“位置”定义成不透明坐标类型，只由一个模块提供比较与序列化，以后换成带世界线的坐标不用改调用方；同一位置上赋值与加减的先后由排序键决定。
- F1：第一版至少明示“讲述顺序不等于发生顺序”，章内补叙显示重放限制；为“开场已完成”定义最小表示（章边界事件或开场状态覆盖）。
- F2：拆成“发生时间”和“讲于”，或把规则写成一句明确的说明。
D 的做法：位置 = {章 id, 可选一句原话}；章内顺序按原话在当前正文里的先后，没有原话就当章末；预留“线”（世界线）一项，缺省为主线；set 与 assert 重置基线。D 自己把“只用章加原话是否够用”列为最没把握的第三件事（倒叙、回忆章、章内形态切换、重排章后折叠结果变化、回溯造成两个版本的世界）。

主题 8：事件溯源只覆盖了一半——初值可原地改写，schema 改名、组件装卸后历史补丁怎么重放没有定义
----------------------------------------------------------------
涉及发现：A9、C4（第 1 至 3 个现象）、E2-9、B12（部分：schema 改动界面展示，主归主题 26）。
最高严重程度：重要。各报告：A9 重要；C4 重要；E2-9 重要；B12 重要。
问题描述：状态定义为“初值加前面所有已写变更”，但初值是一份可被原地改写的基线，它的变迁不进可重放日志，只靠文件历史留痕；核对点是对着“当时的基线”记下的，基线一改，旧核对点的意义就变了（C4）。推荐的“schema 改字段名时生成一条创作修改，把旧数据迁过去”只迁当前对象，历史补丁的路径仍指向旧字段名——A9 的反例：把 `panel.魔力` 改名为 `panel.mana`，只迁初值后，第 2 章的 `魔力 -= 90` 仍打旧路径，产生两个字段或缺基准；迁最新快照则重建时丢失；追加式日志要么改写历史，要么读取时升级（upcasting）。组件装卸也没有重放语义：卸下 Component 若停止解释它的补丁，历史状态会变，若继续解释则必须保留旧 schema 和约束；E2-9 的体验版本是：第 3 章才决定加神典石面板，选“第 1 章开头”看苏天晴仍有“神典石 0”，Agent 以为面板早就存在，Component 没有“从哪章生效”。
质疑决定：弱。C4 指出决定“骨架用事件溯源”实际只有剧情变更是事件，初值和创作修改不在可重放日志里，并指出路径寻址的补丁与追加式日志冲突，要求二选一，不要求推翻骨架。
各报告的改法：
- A：把 schema 与实例配置的版本纳入模型，规定历史事件按原版解释还是经确定性 upcast；字段改名必须同时映射初值、补丁路径、核对点、主 MDX 引用和计算字段依赖，迁移有可重放记录并原子发布；明确卸载是只移除视图还是停止某个生效区间的能力，保存足够的旧版本保证重放。
- C：明确“日志里是剧情变更，创作修改是基线的审计记录”，或把创作修改也做成日志事件（带前后值）使整个状态可重放，二者选一；补丁路径用条目 id 与字段 id 寻址，改名靠 id 不变，schema 变化用读取时升级，不改写历史。
- E2：Component 带“从第几章生效”，或让 Agent 知道早于此的章节不该提它。
D 的做法：字段定义拷贝到条目自身，“种类”只是新建时的默认字段集，不做可迁移的 schema，因此没有迁移问题（代价是同类条目会漂移，让 Agent 按需“把这套字段补给所有人物”）；“改正”只留版本历史，不进叙事。

主题 9：条目的存在区间、名字和别名随剧情变化、悬空引用，没有进入状态公式和查询位置
----------------------------------------------------------------

- E1：第 12 章才出场的人在第 1 章视图里是否存在，需要定义。
D 的做法：D 没有存在区间；同名条目返回候选，不替作者挑；别名撞车由零模型健康检查报告。

主题 10：用条目树的父子关系表示“身份同一”（马甲），推翻了“目录只管整理”的不变量，也没说面板和历史归谁
----------------------------------------------------------------

最高严重程度：重要。各报告：A14 重要；B13 重要；E1-5 重要；E2-13 重要；C 在待定项 5 里判为与“条目树只用来组织浏览”矛盾，未单独编号。

质疑决定：否（待定项，不是决定）。四份报告方向一致：不要靠树表示同一性。

- B：用待定项 5 的另一种（连接），或让马甲的父子关系有明显视觉区分并限制拖动。
- C：显式的身份同一关系，不靠树。
- E1：定下一种做法，共享的数（存款、魔力）只有一份；“谁不知道什么”见主题 30。
- E2：用词分开，身份同一单独叫“同一个人的另一个身份”，别借用树的父子。
D 的做法：“身份”是单独的条目种类（介绍、是谁（条目引用）、谁知道（引用列表）），马甲各有一个身份条目；显式存的关系只有三种：所属／位于、身份同一，另有条目的可选父级用于地点层级和组织成员，其余关系是视图。

主题 11：作者的元信息（写作指示、未决问题、揭晓时点、披露备注）被塞进世界状态的同一个字段
----------------------------------------------------------------
涉及发现：A13、F1-任务1-第2条、F1-任务4-第7条、F1-汇总7、F2-任务1-(5)、F2-任务1-(6)、F2-汇总11、F2-带值3、E1-步骤4c（创作意图应是计划里的明确字段）。F2-任务2 的 edit-2（秘典主 MDX 里“正文还没写”过期）是同类实例。
最高严重程度：重要。各报告：A13 重要；F1-任务1-第2条、汇总7 重要，任务4-第7条 建议；F2-汇总11 为 P1；E1-步骤4c 重要；F2-任务1-(5)(6) 未分级。
问题描述：一个日志项或字段被迫同时装“世界里发生了什么”和“作者要写手怎么做、何时揭晓、还没想好”。A13 的反例：同一段细纲里，“星瑕花 2000”应兑现成补丁，“用戏剧化的方式搞砸、这次只让妹妹误会”是给写手的要求，不能因正文写完就变成一件已发生的事；伏笔的回收计划转成已写后，只凭标签和自然语言，程序分不清是已回收、忘记计划还是取消伏笔；作者没想好兄妹矛盾的原因时，写手还要有“不得自行写死”的信息。样本书上的实例：风信子的 `character.真名 = "南小风（第 4 章揭晓）"` 把揭晓时点写进了值，带值渲染原样给 Agent，写手会把括注当成名字的一部分；秘典主 MDX 里“作者设定（正文还没写）……打算第 4 章交代”在第 4 章记账后就过期，常规状态补丁不会自动改这句；面板流水里也混着“创作修改：……第 4 章才在正文交代”。F2-任务1-(5) 的同类问题：金额、战力还没定时，补丁写 -300 就是定性，写 -150 又是替作者决定，没有“待定”的表达。
质疑决定：否。F1-汇总7 提到即使第二版才做知情，第一版输出也应标明“设定凭证、正文披露、角色推测”，这不推翻“知情与秘密第一版不做”。
各报告的改法：
- A：保留单一事件日志，但把写作指示、未决问题归为章或剧情线条目的作者元数据，不参加世界状态折叠，计划记录引用它们；伏笔至少有显式的承诺状态和推进角色，或撤回“伏笔从标签自动得到”的主张并说明人工边界；章与剧情线若做成条目，要给出这些信息以及工具读取方式。
- F1：把“何时揭晓”从姓名、数值字符串里移出，read 标明作者设定与已写依据；披露状态从日志派生，或记账时提出元说明更新，不把正文进度永久塞进无校验的设定字符串。
- F2：备注有独立字段（计划、备注），渲染只给值；补丁允许“待定占位”（例如 `-= ?`），或变更本身有“草稿／待决”状态。
- E1：创作意图（作者注释）是进入计划的明确字段，不是普通描述。
D 的做法：“待定”是一等公民（一句话、关联条目、来源原文、状态 open／answered／dropped），作者没想好的直接成为待定，不让 Agent 补全；作者的写作意图存成挂在章上的作者备忘，“不做成世界事实”；变更可选带“揭示于”，第一版不做但字段预留。

主题 12：带值渲染 `{路径 = 值}` 作为阅读格式可用，但不是可逆的回写协议
----------------------------------------------------------------
涉及发现：A6、C1（部分：带值写法在 JS 里是赋值表达式、值文法不统一）、待定项 11（C）、F1-任务3-第2条、F1-任务3-第3条、F1-任务3-第4条、F1-汇总3、F2-汇总5、F2-带值1、F2-带值7、F2-带值8、F2-任务3（“不确定该改状态还是改主 MDX”(a)(b)(d)）。
最高严重程度：阻断。各报告：A6 阻断；C1 重要（随 MDX 选型）；F1-任务3-第2、3、4条与汇总3 重要；F2-汇总5 为 P0（折算为重要），F2-带值各条与 F2-任务3 的各项未分级。
问题描述：开发者认可带值写法，并写明“能不能做好在实现审查时专门查”；这批发现就是那次专门查的结果：阅读体验好，回写不成立。提案同时允许表达式、引用、少数标签，又承诺 Agent 可以编辑带值渲染、系统据此恢复主 MDX，但没有源节点身份、基准版本、值编码，也没有“改值还是改模板”的判据。A6 的反例：`余额 {panel.money}，可用 {panel.money}` 渲染成两处 100，Agent 分别改成 90 和 80，无法同时成为一个字段的新值；`{panel.money / 100}` 显示 1，改成 2 时无法唯一推出是把 money 改成 200 还是改除数；值含 `}`、` = `、换行、引号，或作者字面写了 `{panel.money = 100}`，没有转义协议。样本书上同样出现：改眼色该改字段 `character.外貌`（影响所有位置），删“目前有 {panel.神典石 = 200} 神典石”该删主 MDX 里含表达式的整句，渲染行看上去都是一段文字，Agent 差点直接改字；旧渲染里的 200 在记账后已变成 150，展示值不能当文本身份；只删渲染出的“= 200”会让源文变成什么，没有规则（F1、F2）。C1 补充，值的写法不一致：`星瑕` 不加引号，`"黑色长发……"` 加引号，图片是 `图片 路径`，读回来要靠值类型猜。
质疑决定：是，但落在决定自带的条款上：决定「给 Agent 的渲染用 `{路径 = 值}` 的带值写法，认可；能不能做好在实现审查时专门查」。A6、F1、F2 的结论是阅读格式应保留，可逆性未获验证；C1 和待定项 11（C）更进一步，认为写法本身要先统一值的文法，并与 MDX 选型一并处理。没有报告要求取消带值写法。
各报告的改法：
- A：保留 `{路径 = 值}` 作为可读呈现，首版可回写语法收窄为明确的字段占位符；读取同时保留 source revision、节点 id 或源码范围、原值与可写标记；字段修改和模板修改分别提交；表达式、条件、标签只读，复杂模板用原始源码编辑；同一路径的矛盾改值直接拒绝；若坚持任意 MDX 渲染后编辑，须作为独立的编辑映射协议设计，不能用字符串删值当证明。
- C：把带值渲染独立成一小节，写清哪些写法可逆、不可逆时怎么办；先统一值的文法再谈还原。
- F1：写入目标带稳定的文本块或表达式来源与版本，动态值只用于阅读、不用于定位；工具接受结构化目标（字段或文本块）并显示预览，状态值改动与文本删除分别预览，对不明确的渲染编辑拒绝猜写。
- F2：渲染里明确标“这一段是字段引用，改它等于改字段”或“这一段是作者文字”，编辑入口按路径路由；规定“删除渲染值的操作一律视为删除整个表达式”或明确禁止。
D 的做法：没有带值渲染，也没有 MDX。Agent 的写入走结构化批次（字段操作加出处），写入工具在底层拒绝改作者的字，Agent 对文字只能提建议；面板文里的数字由程序按流水格式化（`panel.render(条目, 位置)`），Agent 不心算。代价是介绍块不能随状态自动变。

主题 13：选 MDX 没有记录的理由，表达式语言、沙箱和跨条目依赖都没有定义
----------------------------------------------------------------
涉及发现：C1、A12、F2-汇总16；待定项 10（C）的“计算字段先别放进类型清单”。
最高严重程度：重要。各报告：A12 重要；C1 重要；F2-汇总16 为 P2。
问题描述：除本提案外，全仓没有任何 MDX 的使用或决定记录（提案 `adrs: []`），决定表只出现了“主 MDX”一词，没有理由。提案说渲染“不能 import、不能读写文件、不能联网，只能用表达式和少数内置标签”，但 MDX 的 `{...}` 是任意 JS 表达式、编译产物要执行：`Date.now()`、`Math.random()` 破坏纯函数，`(() => { while (true) {} })()` 卡死渲染，`globalThis`、Function 构造器、动态属性访问都不受“禁止 import”约束；要真隔离只能自己对表达式做 AST 白名单，那就不再是 MDX 而是自定义模板语言（A12、C1）。“表达式”到底是什么语言没定义，而计算字段、年龄和历法都依赖它；调研曾明确建议“只允许引用路径，不允许表达式”，提案悄悄绕回而未解释（C1）。跨条目引用也没有合同：A 的 MDX 引用 B 的魔力，改 B 的过去时若只清 B 的章快照，A 仍显示旧值；A、B 的计算字段互相依赖时要拒绝循环或定义求值规则（A12）。与已实现的 Markdown 方言还有冲突：`<https://x.cn>` 自动链接在真 MDX 里是语法错误，nb-markdown 的往返保证和提示词编辑器“文字是唯一真相”都建立在方言上，提案一次也没提 nb-markdown（C1）。F2 补一句：计算字段 `{表达式 = 值}` 在夹具里一次没出现，“只读、改依赖字段”这条规则无从检验。
质疑决定：是。C1 质疑决定「条目由主 MDX 加一份随剧情变化的状态数据组成」里“MDX”这一选择：没有记录的理由，MDX、沙箱、表达式三者互相矛盾，建议先回答“为什么不是现有 Markdown 方言加一小块插值语法”；A12 同样提出“优先重新评估上游”，主 MDX 可限定为 Markdown 加字段占位符与少数标签。
各报告的改法：
- A：渲染输出定义为（固定的模型 revision、条目 id、完整位置、实际或计划模式、渲染器版本）的函数；跨条目只能显式按稳定 id 读原始状态，共用这次快照，记录依赖与反向依赖，检测计算环与缺目标；优先收窄为 Markdown 加字段占位符加少数标签，用 AST 白名单解释；若坚持通用表达式，必须补隔离执行、步数、深度、输出预算和结构化失败。
- C：先回答为何不用 Markdown 方言加插值（nb-markdown 已有 MarkdownSyntax 扩展点、InlineChip 和往返保证）；若确实要模板，定一门只含“路径引用、少数内置标签、几个纯函数”的语言，写成 ADR，不叫 MDX、不用其编译器（业界常规是 Mustache／Liquid 一类加白名单函数，凭记忆）；先写出“表达式”的文法。
- F2：审查时补一个计算字段的例子。
D 的做法：不用 MDX 或模板。条目介绍是“块”，视图（人物卡、前情提要等）是派生物，每句带出处，条目或变更变了就标过期；Agent 做审查时只读条目、变更、正文，不读摘要，防止摘要套摘要漂移。

主题 14：作者怎么在界面里编辑主 MDX 没有回答，解析又是全有或全无
----------------------------------------------------------------
涉及发现：B6、B7；E1-7（步骤3e：要学标记语言才能把“星瑕”做成链接）、A12（“字面 `{`、`<` 统一转义”这一点）与本主题相关，主归主题 26、13。

- A：字面 `{`、`<` 以统一转义在作者与 Agent 两端保留，不靠一次解析错误后回显源码代替合同。
D 的做法：没有这个问题（没有 MDX）；条目页是作者的字加一张表单。

主题 16：读取工具缺口——读不到任意章的状态、提交前无法预览、不能按章取变更、正文不可检索、没有稳定 id 和原账

问题描述：决定要求 Component 的用法说明“首次出现、隔一定 token 或压缩之后以提醒的方式给”。A16 核查了现有 harness：`reminder()` 只在 turnStarted 运行，一次 read 的工具结果才首次暴露“面板”，本轮下一次模型请求前不会再检查；`every` 的单位是轮，一轮跑 20 次工具和跑 1 次工具无法满足同一个 token 间隔；压缩后虽清掉 told，也要等下一轮才提醒；Profile 的 commit=finalOnly 或自定义 render 还能把提醒从历史里移除，“发过”不等于“当前上下文仍有”。C11 从相反方向看：现有 `reminder({every, watch})` 按轮数、压缩后再提醒一次，“第一次、隔一段、压缩后”基本能用 watch 取已出现的 Component 集合、every 取轮数直接做；要按 token 就得说明轮数为什么不够。F2-汇总17 补一句：提醒只讲组件怎么用，没讲“什么时候该先读哪个视图”。
质疑决定：是。两份报告从相反方向质疑决定「Component 的用法说明不随每次查询重复给出，改为首次出现、隔一定 token 或压缩之后以提醒的方式给」：A16 认为要实现它，现有助手不够，须另写扩展并把 harness 合同补进预期改动；C11 认为“隔 token”没必要，用轮数即可。
各报告的改法：
- A：由插件定义可重放的 Component 说明扩展，按 Component 类型 id 加说明或 schema 版本保存已交付事件、token 距离或估算基准以及压缩后的状态；在工具结果写入后、压缩事件后、下一次请求前的已定义边界补提醒，按批合并去重，path 片支持回退、fork、重开；明确自定义 Profile 是否必须保留提醒，或由请求级槽补齐；相关 harness Spec 与验收时序列进第六节。
- C：先用现有 reminder（watch 加 every=轮）做；确需按 token，说明理由。
- F2：预查目录里提示“建议读哪个组件视图”。
D 的做法：D 未涉及提醒机制。

质疑决定：否。决定里“改稿后重新抽取”按范围延期，E1-4、B17 只要求第一版显示出处过期，不要求提前做重新记账。
各报告的改法：
- B：变更记录同时存被引用段落的摘录（几十字原文片段）；审阅界面显示摘录，点击跳转时用摘录模糊定位，找不到时提示“正文已修改”，不跳到错的位置。
- E1：第一版至少要把“出处已过期”显示出来。E2：出处做成可点击链接；加 Component 时 Agent 主动问“要不要把前几章里相关的数补进去”；支持整章撤销重记。
- F2：出处增加“细纲、章计划、作者消息”这类，并给稳定引用 id，或允许“暂空”等正文写完再补。F1：输入消息和手记自动给稳定段落定位，批量写入允许局部引用并返回正式 id。
D 的做法：引用 = 原文 id + 一句原话 + 偏移，偏移失效时按原话重新定位，找不到就标“出处失联”，不静默丢；入账前校验出处原话确实在正文里；记账幂等键（章，正文哈希），正文变了健康检查标“账可能过期”，重记时撤销上一批里作者没碰过的项；细纲作为原文挂在章上，只在需要时才抽成计划情节。

主题 23：审阅负担和信任模型——没有“默认生效、有问题才叫我”，看不出每条的来源和把握，没有抽查
----------------------------------------------------------------
涉及发现：E2-1（含步骤7a、7b、7c）、E1-3（含步骤5b）、E1-15、E1-16、E1-步骤2g、C7、E1-2（部分，主归主题 1）。
最高严重程度：重要。各报告：E2-1 重要（含抽查与摘要）；E1-3 重要；E1-15、E1-16 建议；C7 建议。
问题描述：日常循环固定为“写正文、记账、整章审阅”，没有自动接受模式，也没有“按条件叫我”。E2 的作者不想每章逐条看，希望核对通过、没有待确认的章直接生效，只把核对不上、不确定、改动大的排队；但“有疑问”由 Agent 自己标，Agent 自信地记错（比如把秘典的预言记成事实）不会被标，提案没有抽查，也没有“这几章记了 N 条，其中较大或不确定的是……”这类摘要。E1-3 的反例：示例补丁 `魔力 -= 90` 来自“关闭滤镜”，正文并没有写扣多少，出处却标“正文 1.21–1.30”，核对点只对正文写出的数有效，面板会被 Agent 的猜测悄悄推动，作者因此要求凡正文或手记没出现的数都单独标“Agent 估的”。C7 从评测数据看同一件事：提案把风险转给“作者审阅”，却没给出每章要审的条数，而 V9 评测的结论之一恰是“用图作答的失分多是照搬图里记错的内容”，方案依赖的正是最容易出错的一步；样本书前 4 章是 11 段情节、12 条状态变动，约每章 6 条，负担看起来可接受，但没有量过漏记率和错记率。
质疑决定：否（待定项 8 是推荐，不是决定）。
各报告的改法：
- E2：核对通过的章默认生效，只把核对不上、不确定、改动大的排进待确认并提示（提案的零件——核对点、待确认——都在，缺“默认接受”开关和接受的语义）；定期给摘要；要有抽查手段。B4（主题 1）同样建议“默认接受，只标红有问题的项”。
- E1：凡正文或手记没出现的数在审阅时单独标出“Agent 估的”；记账报告里明说“下列内容被当作对话、没有记账”；审阅时计划与兑现并排对照；“整章接受、单条驳回”写成正式规定；种子这类一次性大批量，希望按条目分批接受。
- C：为目标 4 和目标 2 各配一条可量验收——记账每章条数、作者审阅耗时上限、漏记率与错记率；在没有数据前不要把“作者只管说话”写成已达成的目标；在 t26 评测里量出漏记率与错记率。
D 的做法：记账默认立刻生效、整批可一键撤销、拿不准的进待定，作者看的是一张回执（新增几个条目、几条变更、几个情节转已写、几个新待定、几个冲突），不是逐条批的清单；每个变更带 origin（作者、哪个模型、提示词版本），用颜色区分 Agent 的字，并有“采用 Agent 的话”这个显式动作；不自动生效的情形（与已有条目冲突、合并条目、身份同一、删除、模型自己标了低把握）进待定。D 自己把“默认生效的误差会不会累积”列为最没把握的第二件事，需在样本书前 5 章量出误记率。

- 计划就是还没写的变更：E1、E2 都说“还剩什么”“按计划看第 N 章会是什么样”直接能看到，伏笔也是同一种东西，不用多学一套；A 确认计划补丁不进入实际状态、与决定一致。
- 变更日志样例一眼看懂、每条有章、出处、涉及、补丁（E2）；作者的原话被原样保存成“手记”，变更指回它（E1）；情节视图“问一句”每句标出处（E1、E2 称是愿意信任它的前提）。
- 按章看某个人物当时的样子：E1、E2 认为对写补叙和改稿很实用。
- 带值渲染 `{路径 = 值}` 作为阅读格式：F1（任务3-第1条）、F2 都认为发现字段路径很顺，主 MDX 引用字段后余额一改主视图自动跟着变；E1 称“我看不见这套复杂的东西”。（可逆性见主题 12。）
- 条目只有一段文字也合法、不是所有条目都要 Component：E1、E2 称让懒作者可以随手记；A 确认无 Component 条目、Component 视图不嵌入 MDX、经历不复制进主 MDX，与决定一致。
- 范围控制得当：A、B、C 都认可关系、地图、知情、世界线、第三方 Component、合并 nb-story 明确列为非目标，没有悄悄变成前置条件；B 认为 Component 的界面放进 Tab、nb-ui 的 Tabs 机制够用。
- 问题本身是真的、依据有出处：C 核对了调研和旧版痛点，提案对旧 WorldEngine 的复盘（两份真相源、全库唯一的 bigint instant、无外键字符串 id）与调研一致，对 nb-story、nb-memory、nb-history 的描述与各自 README 对得上。
- 审查细纲分“吃书、吃设定、严谨”三类，结论指向具体条目或变更（E1）；F1、F2 用这套模型完成审查与拟记账是可行的，抓出了细纲的位置矛盾和付不起的购买，没有重复入账、没有把角色的想法写成世界法则。
- 条目渲染的大小只取决于条目自己，与书长无关（F2 称这是设计的核心好处，前提见主题 18）。
