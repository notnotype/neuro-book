### 1. “计划／已写”同时承担执行与审阅状态，兑现计划没有唯一记账规则

- 严重程度：阻断；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.3（122—144）、四.4（158）、四.8（265—269）、七.8（349）。
- 现象：状态只有“计划／已写”，而记账又要求先提出、再由作者审阅、可逐条驳回和进入待确认；没有定义尚未接受的已写提案是否参与真相，也没有定义兑现计划是把原记录转成已写，还是新增实绩并连接计划。计划取消、改排章、只兑现一部分与再次记账都没有状态转换。
- 为什么是问题：初值 100，已接受的第 3 章计划是 -20；记账再产生一条已写 -20。真相应为 80，但“按计划”把两条都折叠会得到 60；若直接原地转状态，实际只花 15 或分两章兑现时又无法保留原计划与逐条驳回的含义。若“已写”在审阅前就参与折叠，待确认的 AI 提案直接污染后续状态与检索。
- 如何核实：对照以上四处，唯一折叠条件是“已写”，没有接受状态、计划与实绩连接、失效／取代规则；story/revisions.md:26—31、79—99 的 pending/adopted/rejected/stale 是独立的修订生命周期，不能靠“沿用待确认机制”自动获得本模型的记账语义。本条为静态合同核查，不声称运行结果。
- 建议改法：保留“计划是未写变更”的决定，但把发布／审阅状态与计划／实绩分开；给变更稳定 id，明确兑现采用唯一一份有效补丁或显式 supersedes/realizes 连接，规定部分兑现、取消、重排与重复记账的幂等规则；真实状态、按计划状态和搜索统一使用同一个有效记录判据，整章接受原子发布。

### 2. 核对点不能替代 broken-relative：缺基准时根本没有可核对的数

- 严重程度：阻断；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.4（159—165）、四.5 面板（195—198）。
- 现象：提案保留数值加减、列表增删，却说核对点“替代了旧版 broken-relative 那种断掉的失败方式”，没有规定补丁遇到缺字段、错误类型、已不存在的列表元素、上限／非负约束被历史修改破坏时的结果。
- 为什么是问题：初值为 100，第 2 章 -20；作者删掉初值字段后，第 2 章的 -20 无法运算，正文未报余额时也没有核对点；即便报了 80，核对点也只能指出问题，不能推导缺掉的历史基准。把缺值当 0 会算出 -20，把坏补丁跳过会伪造有效状态。列表按索引删除时，过去插入元素还会删除另一个元素，数值核对点对此无能为力。
- 如何核实：旧 WorldEngine 的 assets/reference/world-engine/issues.md:54—62 明确区分 E1 缺基准、E3 坏路径与 A1 基准改变；subject-lifecycle.md:106—123 区分 list 与按值去重的 collection。nb-story 的 docs/specs/story/queries.md:131 则只是余额对账，起始未知时明确给 relative，不声称所有结构化补丁都可执行。本提案把两个不同问题当成替代关系。
- 建议改法：先定可执行补丁合同：类型、缺值、数值精度、列表元素稳定寻址、约束与前置条件；核对点只负责正文与计算值的差异。重算失败返回定位到变更／字段的持久问题，明确受影响位置为 unresolved/conflicted，不能当成完整状态继续交给写手；一次多条目变更要么整体可用，要么整体报冲突。

### 3. 把全部创作修改折进初值，不能表达“改第 N 章时的值”且会在后续赋值处失效

- 严重程度：阻断；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.3（148—154）、四.4（158、163—165）、四.7（246）。
- 现象：创作修改被定义为“设定本身，所有位置都跟着变”，状态公式却只有一个初值和剧情补丁。界面允许选第 N 章看状态，再改值时只问“剧情变化还是改正”，没有改正的目标版本／字段来源，也没有把误分的记录事后改类的规则。
- 为什么是问题：初始存款 100，第 3 章设为 80，第 8 章 -10；作者在第 5 章视图把 80 改成 90，并选择“改正”。改初值会被第 3 章覆盖，第 5 章仍是 80；改第 3 章赋值会影响第 3 章起所有位置；在第 5 章加 +10 又把创作纠错写成了一件虚构剧情。仅凭新值 90，程序无法知道作者要哪一种。若后面赋值为 70，“所有位置都跟着变”也不成立。
- 如何核实：按四.4 的公式逐项代入以上三个位置即可得到歧义；四.3 未给创作修改的目标、作用区间或记录改类协议。这里审的是尚未定存储也必须成立的模型合同，不是要求先定文件格式。
- 建议改法：将创作修改定义为对某一条初值／剧情变更／主 MDX 版本的修订，显式记录 targetId、基准版本和修订 diff；作者在历史位置改值时先解析来源，让其选择修订来源还是新建剧情事件，结果预览实际受影响的区间。允许分类纠正并原子重算，保留原决定与修订史，不声称任意初值改动会越过后续绝对赋值。

### 4. 文本三方合并缺少基准与持久化的解决结果，重建快照无法保证确定

- 严重程度：阻断；类别：不变量。
- 位置：docs/proposals/world-engine-kernel.md 四.4（161、163—166）、四.6（209、225）。
- 现象：主 MDX 与长文本存 diff；改过去时三方合并，失败让 Agent 起草、作者确认；同时又承诺快照随时重建、渲染结果只依赖输入。没有规定 diff 绑定哪一个基准文本／版本、确认后的合并结果作为哪条记录保存，以及冲突期间能否发布新状态。
- 为什么是问题：初始 MDX 为“黑色长发”，第 3 章补丁改成“黑色短发”；作者把初值改成“银色长发”，此时第 3 章补丁的原基准与新基准分歧。模型合并出的“银色短发”若只写入快照，删缓存后重放又需调用模型，可能得出“黑色短发”；若直接写回初值，又使第 3 章以前提前变成短发。把冲突标记塞进 MDX 也不等于一个可供写手使用的状态。
- 如何核实：四.4 只规定“Agent 提出、作者确认”，没有对应的解决事件、基准哈希、提交时序与失败通道；按给出的 diff 链即可得到三个不同版本的分歧。本轮没有运行合并库，结论是合同缺失，不声称所有三方合并算法都会把这个例子判冲突。
- 建议改法：每个文本补丁保存 source revision／base hash 与可重放内容；合并建议只是待审数据，作者接受后形成绑定冲突输入版本的持久解决记录，再原子发布整条变更的新版本。重放和 read 禁止调用模型；未解决的分支／字段给结构化冲突，旧的有效版本可读但必须标明，不静默伪造新状态。

### 5. 缺少一次读写的版本与原子发布边界，作者和 Agent 能把过期提案写成当前真相

- 严重程度：阻断；类别：不变量。
- 位置：docs/proposals/world-engine-kernel.md 四.3（154）、四.4（163—166）、四.6（208—209）、四.8（251—269）、五“安全”（317—319）。
- 现象：允许作者与 Agent 同时改、Agent 直接写文件，但工具读写、记账审阅、跨条目的补丁和快照都没有 expectedRevision、冲突结果或事务边界；缓存只有“按章”这一维，未说明依赖初值、变更版本、章节编排和计划模式的失效。
- 为什么是问题：Agent 读余额 100，准备把值设成 80；作者期间已纠正为 150，接受旧提案会覆盖作者修改。一次转账涉及 A -20、B +20，如果只发布 A 就让读者看到钱凭空消失。后台重算期间读取旧 A／新 B 或缓存未失效，得到的“同一章状态”也不再是一份世界状态。事后文件 diff 能看到损失，不能阻止损失或给记账提案正确的基准。
- 如何核实：提案没有读版本、条件写与原子发布字段；已存在的 story/queries.md:190—195 和 story/revisions.md:94—105 明确固定查询版本、失效分页游标、并发写入不丢，nb-history/README.md:37—39、72、120 也明确条件式审阅与单写者边界。这些合同不能从“靠修改历史与作者审阅兜底”推导出来。
- 建议改法：先定项目模型 revision 与一次发布的变更集，所有读取（含跨条目引用与分页）固定在该 revision；写入／审阅携带读取基准，过期给冲突或基于最新状态重新提出，不静默覆盖。跨条目补丁与计划兑现原子发布；快照标注 revision、编排版本和实际／计划模式。直接文件改动作为外部修订导入同一发布管道，坏文件保留原字节并报告，不能绕过校验直接成为有效真相。

### 6. “去掉 = 值 就还原源文”只对受限占位符成立，不能承担 MDX 编辑回写

- 严重程度：阻断；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 四.2（108、116）、四.6（211—225）。
- 现象：提案同时允许表达式、引用、少数标签，又承诺 Agent 可以编辑带值渲染结果，系统据此恢复主 MDX；没有源节点身份、基准版本、值编码与“改值／改模板”判据。
- 为什么是问题：以下写法会丢失信息或产生互相冲突的写入，不能靠删一段文本解决。
  1. 同一字段两次：`余额 {panel.money}，可用 {panel.money}` 渲染两处 100，Agent 分别改成 90 和 80，无法同时成为一个字段的新值。
  2. 表达式：`{panel.money / 100}` 显示 1，改成 2 时不能唯一推出要把 money 改成 200，还是把除数或整个模板改掉；标为只读也仍需要拒绝／改源码的明确通道。
  3. 条件分支：`{panel.hp > 0 ? "活着" : "已死"}` 渲染成“活着”会丢掉另一分支；若保留整段表达式再附值，虽然可保留源码，却仍不能把 Agent 对“活着”的修改唯一回写到状态或某个分支。
  4. 相同显示值：`{character.title}` 与 `{entry.name}` 都是“星瑕”，字段路径只能区分值来源，不能为普通文字与重复出现的节点提供稳定编辑锚。
  5. 值含 `}`、` = `、换行、引号，或作者字面写了 `{panel.money = 100}`：没有转义协议就分不清值结束与正文；按 JSON 编码可以解决部分问题，但图片示例不是 JSON，提案没有统一编码。
  6. Agent 同时把 `存款 {panel.money = 100} 元` 改成 `可用现金 {panel.money = 80} 元（余额已扣手续费）`：是写状态 80 加改模板，还是把固定余额 80 写进主 MDX，现合同无法决定；再叠加历史位置更不能确定写到初值还是哪条事件。
- 如何核实：逐项按四.6 声称的反向操作推演即可；本轮未运行 MDX 编译器。已核实 nb-profile/src/loader.ts:23—27 是直接 import TSX，不能提供该反向映射；nb-markdown 内检索也未找到 MDX／可逆表达式机制，不能视作已有能力。
- 建议改法：保留开发者认可的 `{路径 = 值}` 作为可读呈现，收窄首版可回写语法为明确的字段占位符；读取同时保留 source revision、节点 id／源码范围、原值与可写标记，字段修改和模板修改分别提交。表达式、条件与标签只读，复杂模板用原始源码编辑；遇到同一路径的矛盾改值必须拒绝，不猜。若坚持任意 MDX 渲染后编辑，就要把它作为独立的编辑映射协议设计，不能用字符串删值当证明。

### 7. “讲于”兼作生效位置，前史后来写进正文时无法保持同一事件只生效一次

- 严重程度：重要；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.3（127—144）、四.4（158）、四.8（266—271），第二节（54、62）。
- 现象：前史排在第 1 章前、已写变更按“讲于”折叠；故事时间统一留空。模型没有“同一事件在多处讲述”的身份与重述规则，也没有区分“没有写进正文但作者认定发生了”和“已经写进正文”。
- 为什么是问题：星瑕的前史已记“研究花掉 1 万”，第 1 章余额据此正确；第 20 章用回忆第一次写出这件事，记账若新增已写 -10000，就重复扣钱；若把原记录的讲于从“前史”移到第 20 章，第 1—19 章的余额又多出 1 万。即使新补叙一件从未登记的旧事，按讲于生效也会把过去受伤写成第 20 章再次受伤。这不是要求第一版实现历法或世界线，而是避免已知近似破坏同一事件的身份与可迁移性。
- 如何核实：沿用提案的星瑕前史及 -90 魔力同类补丁作账本推演；开发者确认的是“按讲于排序加前史”，没有确认前史重复记账或同一事件只能有一个叙述位置。nb-story 的 dataset.ts:25、64—81、130—145 已有 retells 与独立 time/evidence；nb-memory/README.md:20—33 明确叙事轴和世界状态轴不可互换。
- 建议改法：第一版仍可用章序作近似生效顺序，但记录须分别有稳定事件 id、有效位置（含前史序）、多个讲述／凭证锚；正文重述只补出处，不能再加一次补丁。补叙不能可靠放置时标 unresolved 并交作者安放，明确该位置状态不完整。为 t04 增加真实时间时替换有效位置，保留讲于与事件 id；仅留一个空故事时间字段无法从后来被合并的叙述记录自动恢复这些信息。

### 8. 章序和出处段落还不是全序，计划与手动变更没有可用的排序坐标

- 严重程度：重要；类别：不变量。
- 位置：docs/proposals/world-engine-kernel.md 四.3（127—144）、四.4（158、166）、七.4（345）；docs/specs/workspace/folder-kinds.md（43—55、63、71—75）。
- 现象：排序只定章序和出处段落；同段多事件、一个事件多出处、手记／界面出处、没有正文的计划、未排章的计划都未定义落点与同位次序；前史虽说由作者给先后，日志字段却没有这项。也没有区分章节稳定 id 与编排序、删除章节后的引用状态。
- 为什么是问题：同章同段两条补丁分别“设魔力 100”和“-20”，顺序不同结果是 80 或 100；计划尚无段落，不能靠未写出的正文排序。活页夹规范示例的章 id 顺序就是 1、3、2，按编号比较会把“旧账”与“夜雨”的状态颠倒；调整 binder.xml 的顺序还会使全部后续快照失效。删除章如果默默把记录丢掉、移到未排章或继续用旧章序，会产生三种不同真相。
- 如何核实：folder-kinds.md:55 规定编号是稳定身份、63 规定清单才是顺序权威；这不是“第 N 章”天然同时拥有的两个属性。提案没有解决同段／多出处／无段时的比较器或章节移除规则；以上 set 与 increment 直接证明并列记录不可依赖任意数据库返回顺序。
- 建议改法：使用 chapterId 引用身份、binder revision 下的编排序解释位置；每个事件给显式 orderKey／稳定 tie-breaker，凭证只作证据而不是唯一排序键，计划和前史也用同一定位类型。规定未排章计划不参与任何具体章状态、删除／失联章产生待安放记录并显式报不完整；编排变更参与 revision 和缓存失效。这些模型字段应在 t09 选存储前确定。

### 9. schema 改名只迁“旧数据”会遗留全部历史补丁，组件装卸也缺少重放语义

- 严重程度：重要；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.5（170—204）、七.6（347）、四.4（158—166）。
- 现象：推荐 schema 带版本、改字段名时用一条创作修改迁数据；但状态真相由初值与所有历史补丁生成，不是可一次迁完的当前对象。组件实例的 schema／配置版本、装卸生效范围、旧补丁用哪个版本解释都没有定义。
- 为什么是问题：把 `panel.魔力` 改名为 `panel.mana`，只迁初值或最新状态后，第 2 章的 `魔力 -= 90` 仍打旧路径，产生两个字段或缺基准；迁最新快照又会在重建时丢失。卸下 Component 若停止解释它的补丁，历史状态变了；若继续解释，则必须保留旧 schema、计算字段与校验语义，不能只把数据“隐藏”。面板的字段由每个实例声明，仅有类型版本号也不足以确定某条旧补丁当时的字段类型与非负约束。
- 如何核实：四.4 明确快照可重建、四.5 明确实例配置字段，七.6 却只提“把旧数据迁过去”；旧 WorldEngine 的 schema-system.md:13—18、61—69 已把不迁历史补丁列为既有痛点。nb-form 的 forms.md:108—117 只编辑／校验当前传值，不提供历史迁移。
- 建议改法：把 schema 与实例配置的版本纳入模型，规定历史事件按原版解释还是经确定性 upcast；字段改名必须同时映射初值、补丁路径、核对点、主 MDX 引用和计算字段依赖，迁移有可重放记录并原子发布。明确卸载只是移除视图还是停止某个生效区间的能力，保存足够的旧版本保证重放；不能等 t10 填字段时再补这些内核合同。

### 10. 名字和别名允许随剧情变，却不在状态公式和查询位置合同里

- 严重程度：重要；类别：正确性。
- 位置：docs/proposals/world-engine-kernel.md 四.2（105—115）、四.3 补丁（133）、四.4（158）、四.6（214、222）、四.8（252—259）。
- 现象：身份单列在状态之外，字段补丁只说“状态与主 MDX”；但名字、别名又明确能随剧情打补丁，渲染还给出可写的 entry.name。lookup 与自动预查未带位置，而 read 才有位置。条目的创建、生效前是否存在、删除后的引用也未进入模型。
- 为什么是问题：角色到第 10 章才获名“夜王”，第 3 章主 MDX 应显示旧名，当前身份表却可能已是“夜王”；lookup 用未来别名成功、read 在历史位置再按名字找不到，会让同一套工具对同一个条目给出不同身份。若把新名反写主 MDX，又产生两份真相。计划新建的宝剑若始终有初值，则尚未铸造时已能读到有效状态。
- 如何核实：四.2 的三个部分与四.4 的公式缺少身份投影；四.3 补丁目标没有 entry；四.8 的 lookup 不含 at。对照 nb-story dataset.ts:47—59 的实体出现位置与带位置称呼，以及 story/queries.md:56—57、115—118 的统一可见／歧义判据，可见这里不能靠读工具事后单独补上。
- 建议改法：明确稳定 id 与可变身份数据的边界，名字／别名纳入同一历史投影并拥有标准可写地址；建立条目存在区间及删除／墓碑规则，引用始终用 id。lookup、预查、read、search 共用同一上下文位置与模式；作者若需要全局别名目录可另显式标注“跨时期检索”，不要冒充第 N 章有效称呼。

### 11. Component 一律拥有命名空间，与情节“只查询、不存数据”的内置例子矛盾

- 严重程度：重要；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 四.1（96）、四.2（109）、四.5（172—204）、七.7（348）。
- 现象：Component 被统一定义为申请状态命名空间并给 schema，但第一版情节只读全书日志、不拥有条目数据；另有自由命名空间。没有可选数据能力的类型区分、命名空间占用与保留规则、同类型能否挂多实例、实例配置到底存在哪的合同。
- 为什么是问题：照前一个定义实现，情节必须造一个空 schema／空状态块；照后一个定义实现，表单、迁移、卸载代码都要特判情节。卸载的 panel 数据被保留时，后续再申请 panel 是恢复旧实例还是抢占旧数据也不明确；同条目挂“人物基础面板”和“战斗面板”会对同一 panel 块发生冲突。自由字段若能落到任何命名空间，还会绕过已声明的 schema／只读计算字段。
- 如何核实：四.5 的三类数据归属已能证明“所有 Component 都拥有一块状态”不是统一事实；提案只列命名空间与 schema，没有注册冲突、实例基数、配置区与自由区的边界。这里不要求第一版开放第三方类型，内置情节和作者可配置的面板已经碰到这些问题。
- 建议改法：采用带可选能力的 Component 描述：查询／视图能力不要求 state namespace，自有数据能力才声明 namespace、schema 和实例基数；配置与随剧情状态明确区分。内置登记时拒绝重名，卸载仍保留 namespace 所有权，恢复必须验证类型／版本。自由数据限定到独立的 custom 块，路径可稳定转义，不能写入 Component 的保留区；基础 JSON、数值运算与引用校验仍由内核执行。

### 12. 跨条目引用和计算字段没有依赖合同，沙箱限制也不足以得到纯函数

- 严重程度：重要；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 四.2（108、116）、四.5（178）、四.6（208—210）、四.4 缓存（166）。
- 现象：MDX 可以引用其他条目、使用表达式和计算字段；输入只列“条目、位置、给谁看”，未定义引用地址、解析到同一位置／计划模式的规则、缺目标与循环的结果、依赖变化如何失效。所谓沙箱仅禁止 import／文件／联网，没有表达式语言或能力边界。
- 为什么是问题：A 的 MDX 引 B 的魔力，改 B 的过去时若只清 B 的章快照，A 仍显示旧值；A 的计算字段依赖 B、B 又依赖 A 时，必须拒绝循环或定义求值规则。即便不用 import，JavaScript 的 `Date.now()`、`Math.random()` 会破坏纯函数，`(() => { while (true) {} })()` 会卡住渲染；`globalThis`、Function 构造器、动态属性访问和内置图片／链接也需要分别受控，不能因叫 MDX 就认为隔离成立。
- 如何核实：提案只给正面能力与三个禁止项，没有语法白名单、跨条目读取协议或预算；nb-profile/src/loader.ts:23—27 是直接 import，不能复用其执行信任边界。检索 nb-markdown 仅找到 HTML iframe 沙箱（language/syntax/html-embed/index.ts:38—43、230—232），该沙箱允许脚本，与这里“可确定、无网络的字段表达式”合同不同。
- 建议改法：把输出定义为固定模型 revision、条目 id、完整位置／实际或计划模式、渲染器版本的函数；跨条目只能显式按稳定 id 读原始状态，共用这次快照，记录依赖／反向依赖并检测计算环与缺目标。优先重新评估上游：主 MDX 可限定为 Markdown 加字段占位符与少数标签，用 AST 白名单解释，保留作者认可的文字视图而不开放通用 JavaScript；若坚持通用表达式，必须补隔离执行、步数／深度／输出预算及结构化失败。字面 `{`、`<` 以统一转义在作者与 Agent 两端保留，不靠一次解析错误后回显源码代替合同。

### 13. 把细纲和伏笔都化成变更描述，丢掉了“不应兑现成世界事实”的作者意图

- 严重程度：重要；类别：遗漏。
- 位置：docs/proposals/world-engine-kernel.md 四.3（136—142）、四.8（260—272）、四.10（305）、七.4（345）。
- 现象：一条计划只有“会发生什么”的描述、补丁、出处、涉及与标签；提案声称计划、剧情线、伏笔和写手上下文都可由它得到，却没有作者写作指示、备选／待定与计划事件的边界，也没有“埋下／推进／回收／放弃”的机器可辨字段。
- 为什么是问题：同一段细纲里，“星瑕花 2000”应当兑现成补丁，“用戏剧化的方式搞砸、这次只让妹妹误会”是给写手的要求，不能因正文写完就变成一件已发生的事。回收计划改成已写后，仅凭标签和自然语言，程序也不能确定这是已回收、忘记计划还是取消伏笔；空补丁虽能装文字，不能区分这三种语义。作者没想好兄妹矛盾的原因时，写手还需要“不得自行写死”的信息。
- 如何核实：旧 assets/reference/plot/system.md:180—220 明确 Promise 的 open/fulfilled/abandoned、plant/advance/setback/payoff 与 open Decision；writer-brief.md:20—42 将章级要求、伏笔任务和未决警告分别交给写手。当前作者种子分析 research/2026-11-01-author-domain-analysis.md:242—249 已有“戏剧化、搞砸、迟钝”等原始需求，提案的单一日志字段没有对应承载语义。本条不要求恢复旧两棵树或把知情重新拉入第一版。
- 建议改法：保留单一事件日志，但明确写作指示／未决问题属于章或剧情线条目的作者元数据，不参加世界状态折叠；计划记录引用这些要求。伏笔至少有显式的承诺状态及推进角色，或明确撤回“伏笔从标签自动得到”的主张并说明人工边界；章节与剧情线若做条目，给出这些信息及工具读取方式，不能只为 lookup 同名入口而增加空条目。

### 14. 用条目树父子表示“身份同一”，直接推翻“目录只管整理”的不变量

- 严重程度：重要；类别：不变量。
- 位置：docs/proposals/world-engine-kernel.md 四.1 条目树（93）、四.2（107、118）、七.5（346）。
- 现象：正文规定条目树只用于组织浏览、每条目只有一个树位置；待定项却推荐“父子关系就表示身份同一”。
- 为什么是问题：作者把“魔法少女身份”从“星瑕”移到“官方人物”分组，纯整理操作会改变它究竟是谁；把“星瑕的灵魂宝石”放到星瑕下，又会把物品认成同一身份。若给父子加特殊种类才能免除误判，实际上已经引入了独立身份连接，只是藏在目录边上。第一版虽不做视角合并，马甲各有面板与经历仍要稳定地指向同一主体，不能跟树的摆放走。
- 如何核实：四.1 与七.5 两句话按字面即可构成冲突；nb-story 的 novel-memory-v9.md:109—119 与 dataset.ts:94—126 采用独立身份说法，使展示组织和同一性不耦合，没有依赖目录的保证。
- 建议改法：条目树继续只管整理，马甲各有稳定 id，用显式 identityOf／同一身份连接表示同一性；可以默认把马甲摆在本体下，但搬动不改关系。作者是否共享面板字段、历史在哪个身份上记，分别定，不从目录父子推断。

### 15. 五个工具没有形成“读原账、核对、改同一条”的闭环，也没有落实上下文上限

- 严重程度：重要；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 第二节（54—55）、四.5 情节（199—202）、四.8（250—272）、五“成本”（321）。
- 现象：lookup 只列名字／位置／描述／Component，不承诺稳定 id；read 只列主 MDX 和 Component 呈现；search 只搜变更和条目文字；写入只说记一条变更／一次修改。未给按变更 id 读补丁与凭证、读完整状态及核对点、编辑／取消／兑现原记录、读正文与手记原段的接口或明确的文件工具依赖。只给 page，没给 pageSize／字节或 token 上限、截断与续读合同。
- 为什么是问题：作者可把 `panel.money` 完全不放进主 MDX，Component 视图也可只显示“富裕”；记账员仍必须拿到精确数值和原补丁，不能从展示文字反推。审查查到“和 c08 冲突”后，要读 c08 的原账与正文凭证、修订它而不是再加一笔；当前清单没有这条可寻址路径。即使每页 50 条，每条 1000 字就是 5 万字，整棵 tree 和一次匹配 500 个名字的预查也都无界，因此“与书长无关”的硬目标还无法验收。
- 如何核实：逐项对照四.8 五项的参数和返回值；旧 WorldEngine 的 subject-lifecycle.md:82—92、183—203 明确 get(sliceId)、精确补丁编辑、投影和 listLimit，nb-story 的 story/queries.md:56—87 明确 id／歧义／cursor／limit 与 source.read/source.records。本条没有要求照搬旧 CodeAct；现有通用文件工具也不自动知道章 id 到正文的映射、数据库里的补丁或带值渲染的编辑基准。

### 16. 现有提醒助手按轮触发，不能直接实现 token 间隔和本轮首次出现时送达

- 严重程度：重要；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 三（76）、四.8（258）、六“相关的已有 Spec”（332—335）。
- 现象：提案把 Component 说明的首次／token 间隔／压缩后提醒交给 harness，但未定义扩展状态和触发时序，也没把所需 harness 合同补入预期改动。harness 有提醒注入能力，不等于已经实现这三个触发条件。
- 为什么是问题：一次 read 的工具结果才首次暴露“面板”，`reminder()` 只在 turnStarted 运行，本轮下一次模型请求前不会再检查；中途压缩虽会清 told，助手也要等下一轮才提醒。`every` 的单位是轮，1 轮跑 20 次工具与 1 次工具不能满足同一个 token 间隔。Profile 的 commit=finalOnly 或自定义 render 还可以把提醒从历史中移除，单纯记“发过”不等于“当前上下文仍有”。
- 如何核实：nb-harness/src/kernel/helpers/reminder.ts:21—38、api/helpers.ts:17—29 明确 path 状态 `{value, turn}` 与 turnStarted；docs/specs/harness/extensions.md:111 同样按轮。loop.ts:209—242 压缩后直接算请求，工具循环在 287—309 继续本轮；profile.md:86—89 允许提交只留最终回复。运行时有 toolResult.details、assistant.usage、compaction 事件和 path 片，足以另写扩展，但不是现成 helper 的保证。
- 建议改法：由插件定义可重放的 Component 说明扩展，至少按 Component 类型 id＋说明／schema 版本保存已交付事件、token 距离／估算基准及压缩后的状态；在工具结果写入后、压缩事件后、下一次请求前的已定义边界补提醒，按批合并去重，path 片支持回退、fork、重开。明确自定义 Profile 是否必须保留提醒或由请求级槽补齐，不能在纯视图里写去重状态；把相关 harness Spec 和验收时序列进第六节。

### 17. 排除 nb-memory 复用的关键理由不成立，混淆了摄入策略与公开存储能力

- 严重程度：重要；类别：文档。
- 位置：docs/proposals/world-engine-kernel.md 三（81—83）、七.3（344）、四.10 备选方案。
- 现象：提案以“每批写入都要全量主体注册表做模型消解”作为不依赖 nb-memory 存储与写入流程的理由；实际这是 ingestBatch 在注入 llm 时的增强路径，不是所有写入的要求。
- 为什么是问题：作者模型可以直接以稳定 id 写入，不需要消解；依据不存在的强制依赖另造状态失效、时间过滤与混合检索，会重复一套已有能力。另一方面，直接把 nb-memory 当本提案的完整内核也不成立：它的 StateEntry 是 topic/view 文本与有效区间，不是带类型的字段补丁，也不包含计划、MDX 与作者修订的第三条轴。选复用边界必须按这些真实差异决定。
- 如何核实：packages/nb-memory/src/index.ts:31—35 的 llm 可选，229—233 的 addFact 直接落事实，237—259 的 ingestBatch 仅在 llm 非空时消解，274—279 的 setState 不消解；603—615 已从包公开入口导出 SubjectRegistry、StateStore、SemanticIndex、passesFilter。core/state-store.ts:51—84 与 retrieval/search.ts:244—283 提供直接状态写入、双轴区间与缺坐标过滤，不要求全量注册表上下文。
- 建议改法：先修正排除理由，做一个有限的复用决策：比较“组合现有纯查询／索引能力、提取公共时间过滤内核、独立实现并说明格式／事务差异”三种边界，保留一份权威可见性判据。无需强行合并 nb-story 或马上改包；t14 决定包切分时要有真实 API 与生命周期的依据，而不是把一个可选 LLM 流程当成硬耦合。

### 18. nb-history 只能兜文件字节历史，不能直接承担本模型的创作修改与逐条记账审阅

- 严重程度：重要；类别：接口。
- 位置：docs/proposals/world-engine-kernel.md 四.3（98、146—154）、五“安全”（319）、七.2（341—343）、七.8（349）。
- 现象：提案允许全部数据放数据库，并把创作修改的历史与审阅寄望 nb-history；但后者的现行操作类型只针对文件、收件箱按文件接受／还原，不记创作理由，也没有剧情变更的待确认语义。
- 为什么是问题：若一章的 10 条记账记录同存一个日志文件，按文件接受不能实现驳回其中第 3 条；若放 SQLite，把二进制数据库当文件快照既不支持语义 diff，也不能在还原一条记录时保留作者同时修改的其他条目。Agent 绕文件服务写入若只能归因为 external，不会触发 nb-history 收件箱，因而“直接写文件靠作者审阅兜底”也不是自动成立。保留策略还会稀疏旧文件历史，不能把它当必须永久保留的剧情凭证与修订真相。
- 如何核实：packages/nb-history/src/types.ts:22—53 只有 FileOperation、actor、occurredAt，没有理由／模型记录 id；65—68 默认快照上限 2 MiB、90 天全量；workspace-history.ts:415—443 的收件箱只有 agent/system 触发。README.md:91—94、120—125、129—137 说明按文件、稀疏、单进程单写者、二进制不可恢复和宿主接线责任。workspace/resources.md:67—78 的外部监视不能保证还原全部中间写入及准确创作者意图。
- 建议改法：世界模型自己保存创作修订的目标、diff、描述、基准版本及审阅状态，逐条与整章操作作用于模型变更集；nb-history 复用在正文／手记／MDX 文件恢复与跨会话未见修改，不让它代替模型事务和永久凭证。若决定扩展 nb-history 支持逻辑资源审阅，需明确定义新的操作／快照接口、保留策略与跨存储提交合同；直接写文件的导入审阅必须有明确来源或按外部变更规则进入模型队列。

待定项逐项判断（对应提案第七节）

1. 名字：中文“法典”、英文 canon 在当前范围没有技术阻碍，但应先明确它包含未兑现计划，不能让名称暗示所有可检索记录都是已确定事实。
2. 存储形态：支持先定模型再定存储，但修订身份、发布原子性、直接写入边界和审阅粒度必须现在定，nb-history 只能复用到文件历史而非直接替代模型账（第 3、5、18 条）。
3. 与 nb-memory 的关系：不能接受基于“所有写入都全量消解”的排除理由，应按公开的无 LLM 写入、状态文本形状与时间过滤接口重新决定复用边界（第 17 条）。
4. 剧情线和章也做条目：可以作为同一查询入口的投影，但章的稳定 id／排序／文件归属仍以 binder 为权威，剧情线的身份与作者意图需要定义，不能另存一份同义章树（第 8、13、15 条）。
5. 马甲：不接受树父子本身表示同一身份，应显式 identityOf／身份连接，树只决定摆放（第 14 条）。
6. 去掉 Component、schema 变化：保留数据可取，但版本化必须覆盖实例配置、历史补丁、核对点与引用，单条创作修改搬当前数据不足以保证重放（第 9、11 条）。
7. 自由命名空间：支持独立 custom 块，不免除稳定寻址、合法 JSON、数值与引用的基础校验，也不得侵入 Component 或计算字段的保留地址（第 2、11 条）。
8. 记账结果审阅：整章接受与逐条驳回可并存，前提是未接受补丁不进真相、依赖被驳回时整笔复核、发布原子且绑定基准版本，nb-story 待确认机制只能借鉴生命周期不能原封迁入（第 1、5、18 条）。
9. 自动预查匹配：精确匹配可以作为第一版策略，但同名歧义、长别名优先、历史位置与注入限额必须明确，未命中词列表还需要定义候选词从哪里来，不能声称单靠字典匹配就能识别所有新设定（第 10、15 条）。
10. 计算字段与历法：支持暂不做历法、年龄按普通字段记，但这没有回答已写进类型接口的计算字段如何声明依赖、拒绝写入和处理循环，应与日期功能拆开定（第 11、12 条）。
11. 带值渲染可还原：字段占位符加明确编码、源节点与基准版本可以设计可逆协议，任意 MDX 求值输出不能靠“去掉 = 值”自动还原且无歧义回写（第 6、12 条）。

证据边界与补充澄清

- 本报告中的数值与文字例子是按提案合同逐项推演的反例，不是运行测试输出；harness、nb-memory、nb-history 的能力结论来自已读取的实现及 Spec，没有新跑其历史测试。
- 第 7 条不把开发者接受的章序近似本身再报一遍缺陷，实质问题是前史后来被正文重述时事件身份、补丁去重和迁移信息无处保存。
- 第 16 条关于 finalOnly 的范围：现有 reminder() 在轮开头写入的附带内容会被 finalOnly 保留；会被它删掉的是为满足本提案而新增在工具结果后的提醒，普通 render/withoutEvents 也可删除事件，因此需要规定实际送达与保留合同，不能把所有“发过”当成“上下文仍有”。
- 第 6 条对表达式／条件的结论是“保留源码再附值可以保信息，但改求值结果不能唯一反推源码／数据”；不是声称任何 AST／源映射方案都做不到，也不是要求给已声明只读的表达式自动求逆。
- 第 11 条不主张取消开发者已定的“自有数据 Component 在状态申请命名空间”，只要求视图型 Component 不必伪造自有状态，且独立自由命名空间有明确边界。
- 关系、地图、角色知情、世界线、细粒度历法、旧项目迁移和改稿后重新抽取按已定范围延期，没有因它们第一版未实现而另报缺陷。

未发现问题的方面

- 在静态模型层面，计划补丁明确不进入实际状态、经历不复制进主 MDX、无 Component 条目合法、Component 视图不嵌入 MDX，这四点与已定决定一致；具体生命周期缺口见相关发现。
- 第一版不合并 nb-story、不开放第三方 Component、不要求 CodeAct，与确认的范围一致，没有发现悄悄把这些扩大为前置条件。
- 不执行分享模板的任意模块、把文件历史与世界状态区分开、把章快照作为可重建缓存的方向本身没有发现问题；问题在尚缺少使这些承诺可实现的合同。
- 只有内置类型，不必为了未来插件一次设计完整 ECS；现阶段最小必要边界是字段地址／版本、可选查询能力和持久修订，见第 9、11 条。

验收映射建议

- 状态与修订：固定输入版本，逐项验证计划取消／部分兑现／重复记账不重复应用；删基准、改类型、列表插入有可观察的冲突；历史值修改准确落到作者指定记录。
- 重放与并发：删除派生快照再重建结果逐字／逐值相同且不调用模型；并发作者修改与旧提案接受只会条件成功或显式冲突；跨条目转账不能读到半笔。
- 时间与身份：按 binder 的 1、3、2 编排与同段 set/increment 得到唯一结果；前史后被重述只补证据不重复扣数；名字变更与条目尚不存在的位置具有统一查询口径。
- 组件与渲染：改 schema 字段名后全部历史仍可重放；卸载恢复不改变旧账；重复字段矛盾改值被拒，表达式只读、字面大括号和尖括号按原文保留；跨条目依赖更新、缺目标与计算环有确定结果。
- 工具与提醒：Agent 只经声明入口能完成查原账／原文、修订与兑现；每次返回可量出的条数及字节／token 上限；本轮首次出现、运行中压缩、重开与回退时，Component 说明在正确的下一次请求可见并按版本去重。

以上为后续可执行的黑盒判据建议，本轮没有执行这些验收。
