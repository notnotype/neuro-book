# 统一故事模型：两个视角、来源层与记录类型

## 目标与范围

把 nb-story 的读者视角与旧应用 WorldEngine、剧情工坊的作者视角合成一套故事模型：定共用的记录类型（对象、身份、说法、秘密、伏笔与悬念……）、每条记录的来源层（正文、设定、计划），以及对象怎么跨层对上。开发者 2026-10-31 同意尝试合并（原打算做两套）。

合同：讨论 Task，只定设计，行为合同未变；定稿后的 Spec 改动在实施时另定。

前置：—。

## 要讨论的问题

### 统一故事模型：两个视角与三个来源层

1. 合并的边界：哪些概念两个视角共用（对象、说法、秘密、知情、状态变动、情节、悬念、时间点），哪些只属于一边（读者侧的出处与可见位置；作者侧的计划、决策、章级 brief）。
2. 来源层是否就三层：正文（抽取，必须有出处）、设定（作者写的真相，可以没写进正文）、计划（打算写，挂目标章节）。要不要第四层“草稿或备选”（作者还没拍板的设定）。
3. 同一事实在两层都有时：是两条记录加对齐关系，还是一条记录带多个来源。
4. V9 数据集与新模型的关系：V9 原样作为正文层，还是改形状；nb-story 已发布的数据格式与命令行要不要保持兼容。
5. “读者视角”对作者自己的书还有没有用：作者写到第 N 章时，读者层就是“写出来的东西”，阅读位置防剧透对作者无意义，对试读与写手 Agent 有意义（见 t06 的试读者、t20）。
6. 旧 WorldEngine 的事件溯源（任意时刻的状态等于之前变更的折叠）是否作为作者层的基本形态。
7. 合并失败的退路：到哪一步发现合不了，就回到两套系统。

### 对象、身份与引用（原 t03）

1. 对象的稳定 id：nb-story 的 id 带章号（`e4-2`），旧 WorldEngine 用 `subject://<id>`，设定文件按路径。作者层的对象 id 由谁分配、写在哪。
2. 引用写法：统一成一种 URI（例如 `entity://`），还是沿用文件路径；文件改名后引用怎么维护（项目文件底座只给章节稳定身份）。
3. 抽取出来的对象（读者层）与设定里的对象（作者层）怎么对上：自动按名字与称呼匹配、人工确认，还是 Agent 提议。
4. 马甲、转世、失忆、同名不同人、跨世界的同一人：作者知道真相，读者层按可见位置合并；作者层要不要也拆成多个对象。
5. 引用完整性：旧 Plot 与 World 之间是无外键的字符串 id；新设计是否要校验、在哪校验、悬空引用怎么提示。
6. 称呼与别名：作者层的别名表与 nb-story 的称呼（带首次出现位置）是否同一份。

### 伏笔与悬念（原 t07）

1. 伏笔与悬念是不是同一个东西：作者有意埋的伏笔读者可能没察觉；读者产生的悬念作者可能没打算回答。两者怎么对齐。
2. 状态：open、fulfilled、abandoned 之外要不要“已埋但读者未察觉”“读者已猜到”。
3. 挂在哪：场景、章节、段落；回收距离太远、长期没推进的提醒要不要做。
4. 旧版的 Decision（ADR 式创作决策）放在这里还是单独一类。
