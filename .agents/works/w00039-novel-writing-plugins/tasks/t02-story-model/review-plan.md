# 内核提案的深入设计审查方案

审查对象：[作者视角的世界引擎内核（第一版）](../../../../../docs/proposals/world-engine-kernel.md)（草稿）。

本文件只是方案，还没有开审。按全局规则，深入审查要先由开发者批准审查者的安排和预算。开发者 2026-11-01 要求：审查里至少有两个环节，分别以作者和 Agent 的视角去体验这套模型。

## 为什么用深入审查

- 这份提案决定了一整套插件的数据模型。日后改起来代价高：项目数据格式、Agent 的工具、Component 的接口都建在它上面。
- 方案里有技术选型和架构取舍：事件溯源、MDX 模板、带值渲染、Component 不存数据。
- 模型是在会话里一轮轮讨论出来的，很可能有没写出来的前提。
- 单靠读文档，看不出作者用起来顺不顺、Agent 能不能照着格式做对，所以要加体验环节。

## 审查者与分工

| 编号 | 环节 | 谁 | 模型 | 看什么 | 产出 |
|---|---|---|---|---|---|
| A | 设计审查：领域与后端 | omp 会话 | `@default`（gpt-6.1-sol） | reviewing Skill 的九个设计审查维度，加下面的“A 的重点” | 报告 |
| B | 设计审查：前端部分 | Claude 子代理 | sonnet | 作者界面：条目页与 Tab、表单与图片、按章查看、记账审阅、情节 Tab；nb-form、nb-markdown、nb-ui 能不能承接 | 报告 |
| C | 拉远看 | Claude 子代理 | sonnet | 只拿提案，回答五个方向问题；不给已确认的决定，也不给重点 | 报告 |
| D | 独立设计 | Claude 子代理 | sonnet | 只拿目标和开发者的原话需求，不看提案；先按挑战视角提质疑，再出自己的方案和备选 | 方案 |
| E1 | 作者体验：先设计后写 | Claude 子代理 | sonnet | 扮演先搭设定再写的作者，用星瑕的故事种子和第一章大纲，照提案一步步走 | 体验记录与问题清单 |
| E2 | 作者体验：先写后补 | Claude 子代理 | sonnet | 扮演直接写第一章、设定靠脑子记的作者，把样本书前 3 章当成自己写的 | 同上 |
| F1 | Agent 体验：强模型 | omp 会话 | `@default` | 扮演 NeuroBook Agent，只用预先准备好的工具结果，完成下面的四个任务 | 任务产出，以及格式与工具的问题 |
| F2 | Agent 体验：便宜模型 | omp 会话 | `deepseek/deepseek-flash` | 和 F1 做同样的任务，看产品常用的便宜模型能不能照格式做对 | 同上，与 F1 对比 |

几个取舍：

- **按 reviewing Skill 的分工派人**：后端与领域交给 omp；前端、拉远看、独立设计交给 Claude Sonnet。
- **体验环节有三个，比要求的两个多一个。**
  - **作者体验分两种作者。** 开发者说过有两种写法：有的作者先搭设定，有的直接动手写第一章。两种用法走的流程不同。
  - **Agent 体验用两个模型。**
    - 开发者认为 Agent 写 MDX、用带值写法没有问题。
    - F2 用便宜模型验证这一点；记账费用的口径本来就是按 deepseek-flash 算的。
    - 如果要省额度，F2 可以砍掉。
- **E1、E2 用 Sonnet。** 体验环节偏使用体验，按开发者“体验、可维护性交给 Claude”的分工派 Sonnet。如果想让作者扮演得更像，可以改用 Opus，额度相应增加。

## 体验环节的材料（主会话开审前准备）

材料放在 git 忽略的 `.local/agent/works/w00039-novel-writing-plugins/tasks/t02-story-model/review/` 下。小说原文是第三方素材，只读，不进 Git；审查报告和答案文件存进 Task 证据。

- **星瑕**：开发者在 2026-11-01 会话里给的故事种子和第一章大纲，从会话记录里原样摘出来。
- **样本书**：`.local/novels/转生反派萝莉，找茬魔法少女.epub` 的前 5 章，共约 1.3 万字。nb-story 书库里已经有这本书 100 章的 V9 图，前 4 章含 28 个对象、11 段情节、12 条状态变动。
- **Agent 夹具**（主会话照提案的格式手工整理）：
  - **条目**：从 V9 图的前 3 章挑 8 到 10 个对象，例如苏天晴、墨丘利秘典、魔法少女、契约、英雄协会、任务、神典石。每个写成条目（主 MDX、状态、Component），再渲染成“第 4 章开头”的带值文字。
  - **剧情变更日志**：把 V9 前 3 章的情节和状态变动改写成剧情变更。
  - **工具结果**：`lookup`、`read`、`search` 按提案的格式预先生成，放在按“工具加参数”命名的文件里。审查者想查、但夹具里没有的查询，记下想查什么、为什么；这本身就是发现。
  - **第 4 章细纲**：主会话照真实的第 4 章改写，故意埋 3 处问题：一处吃书、一处吃设定、一处动机说不通。埋在哪里写进答案文件，不给审查者。
- **F1、F2 的四个任务**：

| 任务 | 做什么 | 怎么判 |
|---|---|---|
| 1. 审查细纲 | 审查第 4 章细纲的吃书、吃设定和严谨，列出这一章会产生的变更 | 3 处埋的问题找到几处；查了什么、漏查了什么 |
| 2. 记账 | 给真实的第 4 章正文记账，写成剧情变更：描述、补丁、讲于、出处 | 和 V9 第 4 章的情节、状态变动对照，数出漏记、错记和格式错误。第 4 章有神典石的“设定”与“花掉 50”，还有道具的“得到”与“用掉”，正好能检验面板补丁和核对点 |
| 3. 在渲染结果上改设定 | 在带值渲染的条目上改一处设定（例如外貌），写出补丁，并标明是剧情变更还是改正 | `{路径 = 值}` 能不能被正确地拿来修改；能不能还原回源文 |
| 4. 写手的上下文 | 列出写第 5 章要取哪些材料，以及大概多少字 | 要读的量是不是与书的长度无关 |

- **E1、E2 的走法**：每一步写四样东西：作者想做什么；照提案会发生什么；哪里不清楚、哪里麻烦、缺什么；严重程度。
  - **E1**：
    1. 新建作品；
    2. 发故事种子；
    3. 审阅 Agent 建的条目与待确认；
    4. 手动建一个人物，带面板；
    5. 写第一章的计划，和 Agent 讨论；
    6. 写完后审阅记账结果；
    7. 回头把开局存款改掉；
    8. 按章回看星瑕。
  - **E2**：
    1. 直接贴进前 3 章；
    2. 看系统从正文里长出了什么；
    3. 要写第 4 章时找回设定；
    4. 发现一处记错的数值并改掉；
    5. 想加一个面板，但前 3 章已经写完了。

## 重点

### A 的重点

1. **一条日志同时承担真相、计划和经历。** 计划中的变更和已写的变更混在一起，状态计算、记账时的兑现判断、检索会不会互相污染？
2. **第一版按讲于排序，外加前史。** 补叙章、同一章里有几个时间点、前史内部的先后，状态会不会算错？以后切到故事时间（t04）时，数据能不能平滑过渡？
3. **改过去。** 改初值、改某一条变更、在中间插一条：后面的状态重算、核对点、文本三方合并的冲突，都怎么处理？
4. **剧情变更与创作修改的区分。** 由谁判断，判断错了有什么后果，事后能不能改类？
5. **Component 的生命周期。** 增删、schema 变化、命名空间冲突；情节这类视图型 Component 和数据是什么关系？
6. **渲染。**
   - MDX 怎么做到在沙箱里渲染、结果只取决于输入？
   - 带值渲染能不能做到可还原？这一条是开发者要求专门查的。
   - 作者文字里出现 `{` 和 `<` 怎么办？
7. **和已有模块的重叠。** 与 nb-memory（双时间轴、状态失效区间、fail-closed）、nb-history（操作日志与审阅收件箱）、nb-story 有重叠，有没有该复用却没复用的？
8. **Agent 工具与提醒。** 五个工具够不够？提醒的去重，要靠 harness 记哪些状态？

### B 的重点

1. 主 MDX 怎么编辑：源码与渲染之间怎么切换，值显示出来以后怎么改。
2. 表单与图片字段：nb-form 有没有图片控件；立绘按形态各存一张。
3. 按章查看的选择器，以及“这是剧情变化还是改正”的提问，会不会打断写作。
4. 记账审阅的收件箱，和 nb-history 的审查收件箱是什么关系。
5. 情节 Tab 的分页、筛选、检索，以及“问一句”。

## 流程

1. 开发者看过提案要点、批准本方案后，提交提案，并把它的状态改成 `reviewing`，让审查者读同一个版本。
2. 主会话准备材料，约 1.5 小时。
3. 同时开八路审查：
   - A、F1、F2 各用一个 detached 的只读审查 worktree 和独立的会话目录，会话目录放在 `.local/agent/works/w00039-novel-writing-plugins/tasks/t02-story-model/reports/`；
   - B、C、D、E1、E2 是 Claude 子代理，只读主工作区；
   - 每份说明都写明：不开子审查，每核实一条就追加写进报告。
4. 等待期间，每 50 分钟看一次 omp 的进度。
5. 报告到齐后，主会话逐条核实、归类：说明没写清、成立要改、成立但接受取舍、不成立。D 的方案和提案有差异的地方，原样交开发者。
6. 修订提案，向开发者汇报：审查方式、条数与各级数量、每条怎么处理、还要开发者决定的事。
7. 同一份提案最多审三轮。
