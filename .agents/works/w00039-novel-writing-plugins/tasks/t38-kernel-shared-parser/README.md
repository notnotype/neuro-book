# 内核改用与章节相同的解析器

## 目标与范围

条目主文字只留一个解析器：扩展章节编辑器现有的解析器（marked），内核也改用它，作者与 AI 的写法不变（开发者 2026-11-23 定，另写 ADR 部分取代 0038 决策 1）。从 t28 拆出来单独做（开发者 2026-11-23 同意），排在主文字的编辑与条目树之后。

合同：待补充（链接具体 Spec，或说明行为合同是否改变）。

## 来由与已知的难点

t28 的设计审查（2026-11-23，[后端 omp 报告](../t28-entry-mdx-editing/evidences/design-review-backend-omp.txt)第 1 到 5 条、[独立设计](../t28-entry-mdx-editing/evidences/independent-design.txt)）指出换解析器比 t28 计划第 1 稿写的深，而且牵涉保密，所以单独成 Task、要有自己的设计与审查：

- **定位**：marked 的词法单元不带位置。按叶子的 `raw` 在原文里回搜会静默定位错（链接标题里有同样的表达式、引用与列表去前缀、CRLF、表格里转义的竖线）。要在分词时带着范围，或按容器逐行对齐，每处定位都校验、对不上就报错。
- **写入合同**：旧内核拒收的写法（没闭合的 `{` 或标签、`{a; b}`、空表达式）不能因为“marked 当普通文字”而变成放行；花括号的配平要用完整的 JS 词法（注释里的 `}`），表达式要整段校验、不只看 acorn 解析出的前缀。
- **保密关卡**：缩进代码、`$…$`、脚注、裸网址这些新出现的不透明容器会吞掉原来认得出的表达式与条目引用，给写手的简报因此从扣整块变成放行原文。要么条目的文法不带这些容器，要么认出“不透明容器里有条目写法”并照样记依赖或拦下。
- **带值回写**：`writeback.ts` 的 `scanAnnotations` 自己猜哪些 `{` 在 Markdown 的代码与链接里，要改成由同一份文法给出范围。
- **读法变化的清单**：独立设计实测的那张表（`a < b`、自动链接、缩进代码、单个波浪线、任务列表、引用定义、裸网址吞表达式、中文强调的边角）。
- 做法上先拍旧实现的快照、加随机生成的对照测试（独立设计的生成器与 omp 的反例脚本在本机 t28 的 `reports/` 下），用真实的旧日志穿过作者读取、Agent 读写与简报。

共用的文法放在哪个包、nb-canon 能不能依赖 nb-markdown 的纯入口（omp 第 12 条）也在这里定。

## 当前状态

2026-11-23 新建。t28 的 spike（分支 `spike/w00039-t28-entry-editor`）演示过富文本编辑主文字的效果；当时定的是富文本编辑器等本 Task 做完再接。

2026-11-24 开发者试过 t28 的按块编辑（每块一个源文字的编辑框）：“我觉得这个块编辑确实是不好用。还是直接开这个 t38 吧。”本 Task 因此提到条目树之前。开工前开发者先要听四件事：MDX 语法是什么、要支持哪些语法、MDX 有没有自己的解析器（现在用的是什么、基于哪个做）、自动分块要不要做。主会话已在会话里解释，要点与推荐：

- **解析器**：照 2026-11-23 定的不变（扩展 marked，内核也换过去，作者与 AI 的写法不变）。现状是两套：内核用 MDX 官方的（micromark 加 mdxjs 扩展，花括号里交给 acorn），章节的富文本编辑器用 marked；我们只用了 MDX 的花括号表达式与两个标签。
- **要支持的语法**：就是 `canon/rendering.md` 白名单现有的那些，不增不减；两套解析器读法不同的边角（`a < b`、自动链接、缩进代码、单个波浪线、任务列表、数学、脚注、裸网址、引用定义）在设计里逐条定，主会话的建议是会吞掉表达式的容器在条目里都不当语法。
- **分块**（待开发者定）：主会话推荐继续由作者与 Agent 分，但编辑方式换成一篇连续的富文本文档：默认一个条目一块，回车只是新段落；某一段要单独随剧情变或对写手保密时才分。不推荐系统按段自动分：删段、换序都会变成受限制最多的增删块，内核也没有移动块的操作。
- **先后**（待开发者定）：分三段，①共用的文法并对照旧解析器（不改行为），②内核换过去，③条目页接富文本编辑器。原定①②③；主会话推荐①③②，让开发者更早试到编辑器，代价是中间一段时间编辑器与内核是两套解析器，①的对照结果出来后差异比预期大就改回原定顺序。
