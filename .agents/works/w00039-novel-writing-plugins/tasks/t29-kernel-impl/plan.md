## 技术选型

| 问题 | 选用 | 理由 | 否决 |
|---|---|---|---|
| MDX 解析 | `micromark` + `micromark-extension-mdxjs`（表达式、JSX、ESM）+ `mdast-util-from-markdown` + `mdast-util-mdx` | 只出语法树、不编译成 JS；表达式自带 estree；`import` 识别成 ESM 节点可以拒收（依赖试验已核实） | `@mdx-js/mdx`：编译成可执行 JS；手写解析器 |
| GFM 表格与删除线 | `micromark-extension-gfm-table`、`-strikethrough` 与对应的 `mdast-util-gfm-*` | 同一生态，按需取两项 | 整个 GFM：带进脚注、自动链接 |
| 中文标点旁的强调 | `micromark-extension-cjk-friendly`（导出 `cjkFriendlyExtension`） | 已核实生效 | 自己改强调规则 |
| 带值写法的扫描 | acorn，**声明为 nb-canon 的直接依赖**（版本与 mdxjs 用的一致）：`parseExpressionAt` 取 JSON 值的边界、`tokenizer` 找顶层的 `->` | 都是 JS 词法，直接用解析器；不靠提升链接里碰巧装上的版本 | 手写扫描 |
| 中文数字 | 自写，表格测试覆盖“两”、口语省略（三千五、四万五）、全角数字、千分位、“3万” | nzh 1.0.14 实测不认“两”（“两千”→0）、“三千五”→3005（依赖试验） | nzh |
| 摘要（归纳缓存的键、请求摘要） | 宿主注入 `digest(text) => string`（插件传 `node:crypto` 的 SHA-256，测试同样用 `node:crypto`）；稳定序列化自写（键排序的 JSON） | 只在项目进程里用，不必让主入口带新依赖；不偏离“只依赖 TypeBox 与 MDX 解析库” | ohash（新增直接依赖）；Web Crypto（异步） |
| 精确档的数 | 按 10⁴ 缩放成整数的 `number` 做加减（Spec components 输出 14：小于一千亿、最多 4 位小数，缩放后小于 10¹⁵，在安全整数里） | JSON 读写不失真，也不用 BigInt | BigInt；十进制文字存储 |
| 持久化对象的校验 | TypeBox，只用 `Value.Check`，不用 `Clean`（未知字段原样保留） | 仓库标准 | 手写校验 |
| 跨进程锁 | 宿主注入；canon 插件用 `packages/neuro-book/src/backend/locked-replace.ts` 的 `holdLock`（等锁约 3 秒，Spec project 输出 22 已改成同一口径） | 与 Files、配置层同一把锁的写法 | nb-canon 自己加 proper-lockfile |
| 活页夹清单 | 插件里用应用已有的 `fast-xml-parser` 读 `binder.xml`；监视 `manuscripts.binder/` 目录、按文件名过滤（改名替换后直接监视文件会失效，审查实测） | 应用已有依赖 | 监视文件本身 |

## 关键设计

### `packages/nb-canon/`（新包）

- `package.json`：`@notnotype/nb-canon`，`private`，`exports` 两个：`.`（前后端共用，不引用 `node:*`）与 `./node`（只在 Bun 里用：分段日志、归纳缓存文件）。依赖：TypeBox、MDX 解析链（上表）、acorn。测试用 `bun test`。登记进根 `package.json` 的 workspaces 与 `docs/modules/monorepo-boundaries.md`。
- 模块（依赖从上往下单向）：
  - `src/core/`：六种对象、修订（含 `ops` 与 `{kind: "chapters"}`）、写入请求的 TypeBox schema 与类型；修订里的路径规范（有 id 的列表用 `[id]`，没有 id 的数组整体是叶子，字段不存在用缺省的 `before`/`after` 表示）；地址；位置的比较与序列化（排序键相同时按写入版本、再按 id 的数值部分）；精确档的数；中文数字；稳定序列化；
  - `src/components/`：类型登记、声明校验、实例字段 id 生成、撞名、版本与“类型不在”的判定，以及登记集合的摘要；
  - `src/model/`：补丁的执行、整条套上、语义档的起点与事件；
  - `src/engine/`：状态计算（见下）、来历、待处理与根因、计划进展；
  - `src/revisions/`：写入请求转成 `ops`、校验、带来的变化、冲突、就地改路由、记一笔、文字替换、还原与依赖、章序调整、请求 id 与请求摘要；
  - `src/render/`：白名单（表达式节点表，负数字面量）、切块、三值求值、给作者的结构、带值写法与装饰、回写解析、出错块；
  - `src/service/`：世界服务的语义：打开与重放、单写者队列、独占租约、事件、补归纳的排队、别的进程的行。外部能力经接口注入：日志存储、锁、章序、正文、小模型、摘要、时钟；
  - `src/node/`（子路径 `./node`）：分段日志的存储，经一个很窄的文件句柄接口（打开、读、追加写、fsync、截断、列目录）做 I/O；产品用 `node:fs` 的实现，测试另有按脚本注入失败的实现，两者跑同一组契约测试；写一半与坏行的识别、分段、截回、尾部核对、归纳缓存文件。
- **状态计算不从头算**：
  - 增量引擎的输入从第 3 片起就是修订的 `ops` 列表，与写入请求怎样转成 `ops` 无关。
  - 一条剧情变更套没套上只取决于它之前的状态，与读取位置无关。打开时做一次整本前向遍历，得到每条变更的结果，以及**每个条目的时间线**：按位置排好的事件（补丁、语义档的起点与事件），每隔 8 个事件存一份共享结构的快照。读任意位置上的一个条目：二分找到最近的快照，再重放最多 7 个事件。
  - 跨条目的原子性：处理一条变更时，从各个涉及的条目的时间线取它在该位置的状态，在草稿上套全部补丁，成就一起提交，不成就都不套、标不完整。
  - 发布：新建、改、删的对象让相关条目从某个位置起“变脏”，按全序只重算涉及脏条目的变更；一条变更的结果翻转时，它涉及的别的条目也变脏。每次发布得到新的引擎对象，整体换上，读取总是看到某一个版本；预览走同一个纯函数，只是不换上。章序或登记的 Component 类型集合（按摘要判）变化时整本重建。
  - 精确档的核对点不改状态，在前向遍历之后按时间线比较（挂靠的变更套上了就比它前后，否则比 `place`）；语义档的核对点是起点，按 `place` 进时间线。
  - **按计划模式**：读取位置 P 上计入的计划集合 S(P) 由实际模式的结果算出（Spec model 输出 5、13），随 P 变化。按计划读 P：取 S(P) 里最早一条计划的位置之前最近的实际快照，把 S(P) 的计划插进去，在受影响的条目闭包（计划的补丁地址，加上与它们同条变更的条目，传递）上前向重算到 P；结果按 `(版本, S(P) 的摘要)` 缓存，同一个 S 的其它位置复用同一条时间线。最坏情况（很早的计划一直没兑现）接近一次整本重算，在 Spec project 输出 14“按计划第一次读取 1 秒以内”的口径里。
  - 待处理按记录维护（每条变更的套不上、每个核对点的不符各一张表）；带来的变化只比较这次被重算的记录与地址的前后，只存结构化的位置与地址；嫌疑区间在读到具体条目时扫它的时间线。
  - 另外三份缓存：MDX 块的解析结果（按源文）、名字到条目的索引（给 `lookup`）、语义档的摘要。
  - 可观测：每次发布与打开记下重算了几条变更、几个条目、各段耗时，进 `status` 的诊断。
  - **最重要的测试是差分**（见验收映射）。整本重算保留在测试里当参照。
- **修订的依赖**：按“对象加路径”建倒排索引（同一对象内按路径前缀判重叠）、“谁建的”表、“谁引用了它”表、兑现组索引；只往没有 id 的数组里加元素的修改不计入；传递闭包用 BFS。都在重放时建，不存盘。
- **请求 id**：重放时建“请求 id → `{修订 id, 请求摘要}`”的索引；发布前查它（Spec revisions 输出 16）。
- **独占租约**：令牌、持有者说明、到期时间（注入的时钟）存在 service 里；插件在申请独占的调用方的租约订阅结束时通知 service 结束独占（Spec project 输出 10）。
- **别的进程写的行**：目录变化只是提示；service 去抖后持锁核对尾部、只读以换行结尾的完整行，在新的世界上重放、整体换上、逐行发 `changed`；尾部变短转只读（Spec project 输出 17）。
- **id**：每种对象一个前缀（`e`、`c`、`k`、`q`、`s`、`r`），编号取日志里出现过的最大号加一（删掉的也算），所以不复用；列表元素与块在各自的列表里同理；比较按数值部分。
- **错误的形状**：所有失败码与诊断都带“对象、路径、说明”同一形状。

### `packages/neuro-book/src/plugins/canon/`（新插件）

- 照 `src/plugins/storage/` 的写法：插件 `nbook.canon`，入口 `project`（拥有世界）与 `browser`（经远程服务调用）。第一版不建 `server` 入口：Agent 工具与后台任务还不做，没有服务端调用方。
- 登记：产品插件清单（`nbook/manifest` 的 `productPlugins`）、项目实例的插件表（`src/project/plugins.ts` 的 `manifestProjectPlugins`）、浏览器的插件表；项目入口在清单里 `receives: ["canon.components"]`，订阅贡献的变化交给 service。
- `project` 入口：激活时只建 service 并开始异步打开，不等打开完成（世界打开最长 2 秒，不能推迟项目实例就绪）；方法在打开完成前到达时等待。锁放 `.nbook/locks/`；读 `manuscripts.binder/binder.xml` 得到章序与章节文件（清单不存在是“没有章”，读不出或不合法时不给新章序、写诊断）；正文按章 id 读章节文件；小模型第一版不接（语义档一直是“未归纳”的写法），接口留着。
- 世界服务的语义在 nb-canon 的 `service`；插件只把方法与事件接到远程服务上，并把日志存储、锁、章序、正文、摘要接成 nb-canon 要的接口。照 Files 的写法（`plugins/files/shared/contracts.ts` 的预算、`plugins/files/web/client.ts` 的客户端）：共享合同里定义预算（远程消息上限减 64 KiB），浏览器入口的服务发出前量请求，世界服务对结果与分页按同一预算判。
- 贡献点 `canon.components`：插件清单声明；内置的人物、面板两个最小类型（字段只够测试与样本用）先登记在本插件里，完整字段清单等 t10。

## 不做与风险

- 不做：Agent 工具、记账与写正文的管线、正式的作者界面、内置 Component 的完整字段、检索、schema 升级、截到上限、`server` 入口。
- 风险：按计划模式的最坏情况（很早的计划一直没兑现）接近整本重算；规模脚本的第二组形状会量出来，超出 1 秒时交开发者收窄 Spec。
- 风险：活页夹现在只有清单格式的 Spec（`workspace/folder-kinds.md`），没有剧情插件；本插件只读清单、不写，新建章节靠作者在资源管理器里建或测试夹具。
- 风险：浏览器包体随 MDX 解析链约增 200 KB，第 9 片接进 Lab 时量。
