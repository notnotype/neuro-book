
### 1. Bun-only 导出名与目录子路径不一致
**严重程度**：重要；**类别**：一致性；**对象**：计划。
**位置**：`plan.md`「关键设计」新包（第 30、39 行）。
**现象**：包的 `exports` 声明只有 `.` 与 `./log`，并称后者只在 Bun 使用；模块清单却把分段日志实现放在 `src/node/`，明确称子路径为 `./node`。
**为什么是问题**：照计划创建 package.json 与导入时，插件要么导入未导出的 `@notnotype/nb-canon/node`，要么把 Node 专用 API 错放进面向 Bun 的 `./log`；第 6 片的 node 存储与第 7、8 片无法按计划定义的包边界接线。
**如何核实**：逐字对照计划第 30 行 exports 与第 39 行的 `src/node/`、`./node` 声明；两者子路径字符串不同。
**建议改法**：统一成一个公开子路径（建议 `./node`，并从 `packages/neuro-book` 通过包名导入），同时在包 exports 与模块清单注明 `./node` 是 Bun/Node 专用、`./log` 是否保留。若命名 `./log`，则目录与所有调用方都统一为该入口。


### 2. `holdLock` 的等锁时长约 3.3 秒、不可配置，与 Spec project 输出 22 的“5 秒”不符
**严重程度**：重要；**类别**：一致性；**对象**：计划（技术选型“跨进程锁”）与 Spec project 输出 22。
**位置**：计划技术选型表“跨进程锁”行；Spec `canon/project.md` 输出 22“跨进程锁 5 秒内拿不到……失败（`world-locked`）”。
**现象**：计划说 canon 插件直接用 `packages/neuro-book/src/backend/locked-replace.ts` 的 `holdLock`。`holdLock(lockPath, report, options: {stale?})` 只开放 `stale`，退避写死为 `LOCK_RETRIES = {retries: 12, factor: 1.5, minTimeout: 20, maxTimeout: 600}`（第 28 行，注释“约 3 秒仍等不到为失败”）。按 proper-lockfile 的 retry 不加随机，累计等待 20+30+45+67.5+101+152+228+342+513+600×3 ≈ 3.3 秒。
**为什么是问题**：照计划接上 `holdLock`，第 22 条“5 秒内拿不到”测不出来也做不到；要做到就得给共享的 `holdLock` 加 `retries` 选项（改 Files、配置层共用的文件，计划的允许改动里没有），或改 Spec 的数字。崩溃锁 10 秒接管与 `LOCK_STALE_MS = 10_000` 一致，这一半没问题。
**如何核实**：读 `locked-replace.ts` 第 26–28、91–96 行。
**建议改法**：二选一并写进计划：Spec 改成“约 3 秒”（与 Files、配置层同一把锁的手感一致，推荐）；或给 `holdLock` 增加可选的等待上限参数，并把 `locked-replace.ts` 列进第 8 片的改动范围与回归测试。

### 3. nb-canon 不依赖 proper-lockfile，但 `two-process.test.ts` 与输出 22 的测试放在 nb-canon 里，拿不到真实的跨进程锁
**严重程度**：重要；**类别**：测试；**对象**：计划。
**位置**：技术选型“跨进程锁”（nb-canon 不依赖 proper-lockfile、锁由调用方传入）；验收映射“project 输出 2–4、7、12、18、20–22 → `node-log.test.ts`”“输出 8、17、22，场景 4 → `two-process.test.ts`”；切片 6“跨进程锁与长度核对（真跑两个子进程并发写）”。
**现象**：真实的锁实现是 `packages/neuro-book` 里的 `holdLock`，nb-canon 不能反向依赖应用包（`docs/modules/monorepo-boundaries.md` 的依赖方向）。nb-canon 的测试要么自写一个锁（测的不是产品用的锁，违反测试规范“依赖能用真的就用真的”），要么不加锁，两进程交替写只能靠运气不撞。输出 22 的“5 秒拿不到为 `world-locked`”“崩溃锁 10 秒可接管”是 `holdLock` 与 proper-lockfile 的行为，在 nb-canon 里根本测不到。
**为什么是问题**：第 6 片“真跑两个子进程并发写”的验收照字面做不出来，或者做出来的测试不能证明产品里的组合正确；第 22 条会被映射到一个测不到它的文件。
**如何核实**：`grep -rn proper-lockfile packages/*/package.json` 只有 `packages/neuro-book`；计划第 23 行明说 nb-canon 不依赖它。
**建议改法**：nb-canon 里只测“锁接口的契约”（持锁后核对尾部、`stillHeld` 失效时放弃提交），两进程与输出 22 的测试挪到插件侧（`packages/neuro-book/src/plugins/canon/`），子进程里用真实的 `holdLock` + nb-canon 的 `./node` 存储；或把 proper-lockfile 列为 nb-canon 的 devDependency 并在测试里接一个与 `holdLock` 同参数的锁，同时在计划里写明这一取舍。验收映射表相应改行。

### 4. “调用方实例停止或断开即结束独占”没有现成的推送机制，计划的“由插件通知 service”没有落点
**严重程度**：重要；**类别**：遗漏；**对象**：计划（关键设计“独占租约”）与 Spec project 输出 10。
**位置**：计划第 53 行“调用方断开由插件通知 service（Spec project 输出 10）”；Spec project 输出 10 与“时序与寿命”第 3 条“调用方断开即失效”。
**现象**：插件能拿到的钩子只有两个：`provideRemote(contract, facade, {release})` 的按调用方 `release`，以及订阅的 `signal`。查 `packages/nb-runtime/src/remote/node.ts` 第 950–960 行，`release` 只在收到 release 帧（调用方入口这一代结束）或提供入口停止时触发；`router.ts` 第 364–373 行成员链路关闭时只删成员、释放绑定，不向项目实例发 release 帧。所以浏览器窗口断网、关页、崩溃时，项目实例里的门面不会被释放，`release` 不会调用。`context.remote.instances()` 只能拉取，没有“实例离开”的事件。
**为什么是问题**：照计划接 `release`，场景“申请独占的窗口断开”时独占不会结束，只能等 60 秒到期；Spec 写的“断开即失效”做不到，测试也会在真实运行时失败（只有用进程内链路正常停止入口时才“通过”）。另外按调用方门面的身份是“实例 + 插件 + 入口 + 代次”，比 Spec 说的“调用方实例”细，两者要说清用哪个。
**如何核实**：读上面两处源码；`grep -rn "instances()" packages/nb-runtime/src` 只有查询接口。
**建议改法**：计划写明机制：申请独占的调用方必须同时持有一个订阅（例如 `exclusive` 事件或专门的租约订阅），服务端在该订阅的 `signal` 触发（plugin-channel 输出 7：所经连接结束、实例失效、入口停止都会触发）时结束独占；`release` 钩子作为第二条路径。Spec project 输出 10 相应改成“持有者的租约订阅结束”。若不想加订阅，就把 Spec 改成只靠 60 秒到期，删掉“断开即失效”。测试用真实项目子进程 + 真实客户端链路关闭来测。

### 5. “按计划”覆盖层建成一条时间线，表达不了 Spec 的语义：计入哪些计划随读取位置变
**严重程度**：阻断；**类别**：正确性；**对象**：计划（关键设计“状态计算不从头算”第 6 点）。
**位置**：计划第 46 行“‘按计划’模式是覆盖层：把有效的计划当作插入的变更，只重算计划涉及的条目，其余复用实际模式的时间线；第一次用到时建”；Spec model 输出 5、13，场景 3 最后一句。
**现象**：Spec model 输出 5：读取位置 P 上按计划模式计入的是“安放在 P 之前、生效、在 P 上尚未兑现的计划”；输出 13：是否兑现按 P 之前有没有套上的 `fulfills` 判定。所以同一条计划在 P1 计入、在更晚的 P2（兑现之后）不计入。场景 3：计划在第 4 章、兑现在第 6 章，第 5 章开头按计划读“原计划在”，第 6 章末尾“不在”。第 6 章末尾的状态等于“第 4 章起从没套过这条计划”的整段折叠，它不是第 5 章开头那条时间线的延续：第 4–6 章之间的已写变更在“有计划”与“没计划”两种前态下可能一个套上一个套不上。一条“插入计划后的时间线”只能给出“计划一直在”的结果，答错兑现之后的所有位置。
另外“只重算计划涉及的条目”不够：计划的补丁改了某条目的值，后面涉及这个条目的已写变更可能翻转套上与否，再按跨条目原子性传染到别的条目（计划第 43 行的脏传播在覆盖层里也必须做）。
**为什么是问题**：照字面实施，按计划读兑现之后的位置会得到错误的状态；`model.test.ts` 的场景 3 会失败，或者为了过测试临时改成每次读取整本重算，Spec project 输出 14“按计划模式之后 20 毫秒”随之守不住。
**如何核实**：对照 Spec model 第 95、119–125、179 行；在三章的小例子上手算：计划 c4 “存款 +1000”、已写 c5 “存款 −1500”（初值 1000、下限 0）、已写 c6 兑现 c4。按计划读第 5 章末尾：c5 套上（2000−1500=500）；读第 6 章末尾：计划不计入，c5 在 1000 上套不上，存款应是 1000 且不完整。单条覆盖层时间线在第 6 章末尾给 500。
**建议改法**：计划写清按计划模式的计算单位：“计入集合”只在兑现事件处变化，按兑现位置把全书切成若干区间，每个区间一个覆盖层（键是计入的计划集合），各自从最早的差异位置起按脏传播重算，按需懒建并设缓存上限；或者改为“在 P 上按计划读 = 从 P 前最近的实际快照起，把计入的计划插进去，在受影响的条目闭包上前向重算到 P”，并量它在三百万字上的耗时。无论哪种，差分测试要把“按计划模式、随机读取位置、随机兑现与撤销兑现”纳入（见第 7 条）。若性能不可达，交开发者把 Spec 改成“按计划模式只在最新一章之后有意义”之类的收窄。

### 6. Spec model 输出 5 的“已写章节”没有定义，引擎也拿不到判定它的输入
**严重程度**：重要；**类别**：遗漏；**对象**：Spec model（第二版新加的句子），连带计划。
**位置**：Spec model 输出 5“安放在已写章节上的计划，从下一章开头起才算‘之前’”；Spec project“宿主提供”表只有章序、正文、小模型、Component 类型。
**现象**：五份 Spec 里“已写章节”只出现这一次（`grep -n 已写章节 docs/specs/canon/*.md`），没说按什么判定：这一章有已写的剧情变更？章节文件正文非空？在“最新一章”之前？宿主也不提供“哪章已写”的输入；按正文判定会让计算依赖正文内容，与 model “计算是确定的：同一份世界、同一章序……结果逐字相同”冲突（正文不在这三样里）。
**为什么是问题**：这是第一轮处理第 12 条（并入独立设计的“安放在已写章节上的计划”）新加的句子，照字面写不出判定；实现者会自定一个口径，测试只能测自己的口径。它还影响第 5 条：计划的有效位置可能随“哪章已写”变化，又是一个让覆盖层失效的来源。
**如何核实**：上面的 grep；Spec project 第 38–45 行的输入表。
**建议改法**：Spec 定义成只依赖世界内数据的判据，例如“这一章上有生效的已写剧情变更”或“排在最新一条已写变更所在章之前或同章”，并补一个验收场景（计划在第 4 章、第 4 章出现第一条已写变更后，第 4 章末尾按计划读不含它、第 5 章开头含它）。计划在“Spec 与文档改动”第 4 条里把这一句列上。

### 7. 差分测试的覆盖面没写清：只列 5 条输出，随机序列不含按计划模式、章序、墓碑、出场与还原，也没说在哪些位置比较
**严重程度**：重要；**类别**：测试；**对象**：计划（关键设计“最重要的测试是差分”、验收映射第 3 行、切片 3）。
**位置**：计划第 49 行、第 94 行“model 输出 7、8、11、13、22（增量与全量一致）→ `differential.test.ts`：随机修订序列，每步比较增量结果与整本重算”。
**现象**：增量引擎里最容易与全量分叉的路径是：按计划模式的覆盖层（第 5 条）、章序变化后的整本重建、条目删除与还原（墓碑让对它的补丁套不上，还原后又套上）、`appears` 改动、变更在 `active/held/undone` 之间切换、核对点 `anchor` 的挂靠变更翻转（比较时点从挂靠处跳回 `place`）、语义档起点（`set` 与核对点）、跨条目的转账在一边翻转后传染另一边、补丁改约束字段（`max` 引用另一个字段）。计划只说“随机修订序列”，映射只列输出 7、8、11、13、22，没有输出 3、5、9、12、14、16，也没说每步比较的是哪些读取位置与模式、比较哪些产物（状态、来历、不完整、诊断、待处理、计划进展、根因）。另外均匀随机的数值几乎碰不到约束边界，生成的序列大多“全部套上”，翻转与传染路径很少被走到。
**为什么是问题**：差分测试是计划自己定的“最重要的测试”，也是增量引擎唯一的整体正确性保障；覆盖面不写进计划，实施时自然只生成最容易写的“加一条已写变更”。第 5 条那类错误（覆盖层在兑现之后答错）在这样的生成器下永远不会出现。
**如何核实**：对照计划第 43–46 行列出的增量机制与第 94 行的映射；Spec model 输出 3、5、9、11、12、14、16 都在增量路径上。
**建议改法**：计划里写清生成器至少包含：新建与改初值、已写与计划变更（含 `fulfills`、`splitFrom`+`by`、`replaces`）、状态切换（待定、撤销、还原）、条目删除与还原、`appears` 改动、核对点（有无 `anchor`、精确与语义档）、章序的插、挪、删，以及跨条目转账；数值从小范围取并设下限 0，保证有一定比例的套不上（例如断言整组序列里套不上的变更至少占 10%）。每一步在全部读取位置（初值、每章开头与末尾）的两种模式上比较完整的读取结果与待处理，失败时把序列缩小后打印（固定种子、可复现）。映射表把输出 3、5、9、12、14、16 加进差分行。

### 8. Spec revisions 输出 16 的 `request-id-reused`（“内容与第一次不同时拒收”）在存下来的修订里没有可比的东西
**严重程度**：重要；**类别**：遗漏；**对象**：Spec revisions（第一轮处理第 13 条新加的内容），连带计划“请求 id”。
**位置**：Spec revisions 输出 16、第 53 行“存下来的修订”的字段表；计划第 52 行“重放时建‘请求 id → 修订’的索引；发布前查它”。
**现象**：修订存的是 `ops`（请求转换后的结果：临时 id 已换成正式 id、文字替换已展开成全文、就地改已路由到某条记录），以及 `baseVersion`。同一请求重发时，世界可能已前进，再转换一次得到的 `ops` 与第一次不同；临时 id 也会换成新号。存下来的修订里没有原始请求或它的摘要，“内容与第一次不同”无从判定；尤其是重开项目之后（输出 7 的 `write-unknown` 场景，正是最需要它的时候），内存里也没有第一次的请求。
**为什么是问题**：照字面实现只能二选一：比较 `ops`（同一请求重发会被误判为 `request-id-reused`，与“返回第一次的结果”冲突），或不比较（`request-id-reused` 永远不出现，测试写不出来）。
**如何核实**：读 Spec revisions 第 53–58 行与输出 16；Spec project 输出 7、16。
**建议改法**：Spec 的修订形状加一个 `requestDigest`：原始写入请求（去掉 `baseVersion` 之外不影响意义的字段，或整份）按稳定序列化后的 SHA-256，与归纳缓存同一个摘要函数；输出 16 写明“按 `requestDigest` 判内容是否相同”。计划“请求 id”一节同步写出索引的值是 `{修订 id, 摘要}`，并在 `revisions.test.ts` 加“同 id 同内容返回第一次结果”“同 id 不同内容 `request-id-reused`”“重开后同 id 重发”三例。

### 9. 星瑕样本“与原型逐项相同”做不到：原型的计算语义与数据形状在多处与 Spec 第二版不同，计划没给差异的处理办法（Spec project 场景 1 同样照字面做不到）

**为什么是问题**：“逐项相同”在上述每一处都会失败。实施者只能临时决定是把原型的行为当期望（把原型的已知缺陷写进夹具），还是逐处放宽比较（测试规范禁止为通过而放宽断言）。差异的取舍属于 Spec 的事，不该在写测试时临场定。
**如何核实**：读上面列出的行；样本里有 `held` 冲突、`splitFrom`、语义档 `money(mode, …)` 两种模式，都会走到差异处。
**建议改法**：把场景 1 改成“与原型对照、差异逐条有据”：先用导出脚本出原型结果，再写一份差异清单（每条：哪个读取位置、哪个值、原型值、Spec 值、依据的 Spec 输出编号），清单进 t29 证据；`sample.test.ts` 断言的期望值是“原型值按清单修正后”的 golden 文件，不在运行时与原型比较。样本改写时把 `splitFrom` 补上 `by`、`text.b2` 换成 `text[b2]`，语义档在没接小模型时期望“未归纳”。Spec project 场景 1 的措辞相应改成“与原型对照，差异只出现在差异清单列出的地方”。

### 10. 目录监视触发的“读尾部”没说要不要持锁，不持锁会读到别的进程正在写或随后截回的行
**严重程度**：重要；**类别**：并发；（类别按说明归入“遗漏”）**对象**：计划（关键设计“别的进程写的行”）与 Spec project 输出 17。
**位置**：计划第 54 行“`node` 子路径提供‘日志尾部’的读取与目录监视（`fs.watch`，变化后去抖再读尾部）”；Spec project 输出 4（写一半的末行截掉）、7（写盘失败“已写的部分已截回”）、8、17。
**现象**：别的进程的追加是“持锁 → 写 → fsync → 再核对 → 释放”。`fs.watch` 在写的途中就会触发；去抖只能降低、不能消除读到中间态的可能（一行最大 4 MiB，fsync 慢时写到一半的时间可达几十毫秒以上）。不持锁读尾部会遇到两种中间态：(a) 末尾一截没有换行，若按打开时的规则当作 `torn-tail` 处理，就会去截别人正在写的行；(b) 别的进程写完整行后 fsync 失败、按输出 7 截回：本进程已经把这行读进来、版本前进、发了 `changed`，而那行在磁盘上已消失，别的进程随后用同一个版本号写另一行，本进程记下的尾部长度又大于实际文件，Spec 输出 8 只定义了“尾部变长”的情形。
**为什么是问题**：照计划实施会出现两进程版本分叉或误截别人正在写的行；这类竞态单元测试抓不到，`two-process.test.ts` 交替写也很难碰上。
**如何核实**：对照计划第 54 行与 Spec project 输出 4、7、8、17；`fs.watch` 的 change 事件按写系统调用触发，不等 fsync。
**建议改法**：计划与 Spec 输出 17 写明：监视只当提示，真正读入别的进程的行一律在持锁时做（与输出 8 同一段代码：取锁、核对尾部、读新增的完整行、释放），读到的末尾不完整片段在持锁时才可能是 `torn-tail`；尾部比记下的短时视为日志被外部改动，转只读并写诊断。测试里用两个真实子进程，让写方在写完半行后停住（例如子进程在两次 write 之间等父进程的信号），断言读方不前进版本、不截文件。

### 11. 已登记的 Component 类型变化时，增量引擎没有失效与重建的设计
**严重程度**：重要；**类别**：不变量；**对象**：计划（关键设计“状态计算不从头算”、插件“贡献点 `canon.components`”）。
**位置**：计划第 43 行只写“章序变化时整本重建”；Spec components 第 108 行“类型随插件的登记与启用可用、随停用与卸载不可用；变化在下一次读取时生效”，输出 2、11、12；Spec model“计算是确定的：同一份世界、同一章序、同一组已登记的 Component 类型”。
**现象**：补丁套不套得上依赖类型登记（约束 `min/max`、数值范围、字段种类、命名空间是否“只读”或“类型不在”）。插件可以在项目实例运行中启用、停用（`runtime/plugin-hot-plug.md`），撞名也会让两个类型同时不可用。计划的时间线、脏传播、覆盖层、名字索引、MDX 块缓存都没有以“登记的类型集合”为键，也没有说插件怎样拿到贡献的变化并交给 service（项目入口要在清单里 `receives: ["canon.components"]` 并订阅贡献的变化）。
**为什么是问题**：停用一个提供约束的插件后，读取仍返回按旧约束算的套上与否，违反 components 第 108 行；`status` 的诊断与待处理也不更新。差分测试只随机修订、不改登记，测不到。
**如何核实**：读 Spec components 第 81–92、104–108 行与计划第 40–49、63 行。
**建议改法**：把“登记的类型集合”（按命名空间排序后的 `{namespace, type id, version, 字段声明}` 的摘要）作为计算的输入之一，变化时与章序变化一样整本重建并换上；插件侧写明接贡献变化的方式（`receives` 与宿主给的贡献列表的变化通知），并在 `canon.test.ts` 用真实项目子进程验证“停用提供类型的插件后，该命名空间得到 `component-unknown`，再启用后恢复”。差分测试的生成器加入“登记集合变化”这一步。

### 12. 规模模拟的形状里计划要么本章兑现、要么永不兑现，测不到 Spec 输出 14“按计划模式”的真实代价
**严重程度**：建议；**类别**：测试；**对象**：计划（验收映射“project 输出 14”、切片 3）与 Spec project 输出 14 的口径。

### 15. ohash 与 acorn 成为 nb-canon 的直接运行时依赖，超出开发者定的“只依赖 TypeBox 与 MDX 解析库”，计划没把它列为偏离
**严重程度**：重要；**类别**：一致性；**对象**：计划（技术选型“归纳缓存的键”“带值写法的扫描”）。
**位置**：计划第 19、21 行；第 9 行“运行时只依赖 TypeBox 与 MDX 解析库”（Work README 决定表 2026-11-02）。
**现象**：
- ohash：计划的理由是“锁文件里已有 ohash 2.0.11”。核对：没有任何 `packages/*/package.json` 或根 `package.json` 直接依赖 ohash，它只是锁文件里的传递依赖（依赖试验用的还是 2.0.12）；对 nb-canon 来说是新增的直接依赖，且不是 MDX 解析库。
- acorn：计划写“随 mdxjs 已在依赖里”，打算直接 import 它的 `parseExpressionAt` 与 `tokenizer`。同样没有任何包直接声明 acorn；仓库是 `linker = "hoisted"`，不声明也能 import，但版本由别人的依赖决定（锁文件里是 8.17.0），换版本或改 isolated 链接就会断。acorn 可以算“MDX 解析链”的一部分，但必须作为直接依赖声明。

### 16. 排序键相同“按 id”与计划的 id 写法（前缀加十进制号）一起用，会把同一章末尾后记的变更排到先记的前面
**严重程度**：重要；**类别**：正确性；**对象**：Spec model 输出 2、revisions 输出 18，连带计划“id”与 `src/core` 的“位置的比较”。
**位置**：Spec model 输出 2“章内按排序键，排序键相同时按 id”；revisions 输出 18“没有正文讲述的，排在本章最前……或最后”、输出 8“开头位置落在本章最前，末尾位置落在本章最后”；计划第 55 行“每种对象一个前缀（`e`、`c`、`k`……），编号取最大号加一”。
**现象**：“最前”“最后”没有给出具体的键值，最直接的实现是两个常量，于是同一章里所有“记一笔”“就地改的剧情变化”“没讲述的变更”键相同，只靠 id 排。id 是 `c9`、`c10` 这样的字符串，按字符串比较 `c10 < c9`，后记的排到先记的前面；跨种类时 `c…` 总在 `k…` 前面，核对点与变更的相对先后由前缀字母偶然决定。Spec 没说 id 怎样比较，计划也没说。
**为什么是问题**：同一章末尾先“+100”再“−150”（下限 0、原值 80）：按记的先后两条都套上；按字符串序 `c10`（−150）先套、套不上。作者看到的是“我刚记的一笔莫名其妙套不上”，而且只在编号跨位数（9→10、99→100）时出现，测试很难碰上。
**如何核实**：Spec model 第 92 行、revisions 第 90、102 行；计划第 55 行。
**建议改法**：Spec 写清“最前”“最后”的取值：最前 = 本章现有最小键减一，最后 = 本章现有最大键加一（写入时算好存下，之后不变），使键在章内基本不重；键相同时的次序定义为“写入的版本先后，再按 id 的数值部分”，不按字符串。计划在 `src/core` 的位置比较里写明这条，并在 `model.test.ts` 加一个跨位数的用例。

### 17. 系统发布的章序调整与独占写入、两个进程同时打开的关系没定义
**严重程度**：建议；**类别**：遗漏；**对象**：Spec project 输出 9、10，连带计划插件“监视活页夹”。
**位置**：Spec project 输出 9“章序……不同，就发布一次章序调整修订”；输出 10“持有期间，不带这张令牌的写入都得到 `busy`”；输出 8。
**现象**：
- 后台任务独占写入期间作者在活页夹里挪章，系统要发布的 `reorder` 不带令牌，按输出 10 得到 `busy`。Spec 没说这时怎么办（只对“只读”写了“不发布，只按宿主给的章序计算并写诊断”），也没说之后何时补发。
- 两个进程同时打开同一项目、活页夹在两边都与世界记下的章序不同：两边各自准备 `reorder`；`reorder` 没有 `puts`，按 revisions 输出 7 永远不冲突，后到的一边在输出 8 读进对方的行之后仍会再发一次，日志里出现两条相同的章序调整（第二条 `before` 与 `after` 相同，带来的变化为空）。
**为什么是问题**：前者让独占期间的计算用新章序、日志里记的还是旧章序，独占结束后谁来补发没人负责；后者是无意义的修订，还会出现在改动记录里。
**如何核实**：对照 Spec project 输出 8、9、10 与 revisions 输出 7、13。
**建议改法**：Spec 输出 9 写明：章序调整是系统写入，不受独占限制（或：独占期间延后，独占结束时补发）；发布前在持锁、读完新增行之后再比一次，相同就不发。计划的插件一节与 `service.test.ts` 各补一例。

### 18. 精确档“小于一万亿、4 位小数”经 JSON 数存取不保真，BigInt 只管计算、管不到读日志与远程传输
**严重程度**：重要；**类别**：正确性；**对象**：Spec components 输出 14，连带计划“精确档的数”。
**位置**：Spec components 第 94 行；计划第 51 行“按 10⁴ 缩放成 BigInt 做加减，比较与输出时再转回十进制文字或 JSON 数”；Spec project 输出 2（日志是 JSON 行）、rendering 输出 8（给 Agent 的值“数不带引号”）。
**现象**：日志、写入请求、读取结果都是 JSON，数是 JSON 数，`JSON.parse` 先变成双精度，再缩放成 BigInt 已经晚了。实测（`tmp/json-precision.ts`）：一万亿以内随机取 4 位小数的数，10 万个里 8263 个经 `JSON.parse` 再 `JSON.stringify` 回不到原文（例如 `900719925474.0993` 读回是 `900719925474.0992`）；一千亿以内 10 万个全部保真（双精度保证 15 位有效数字，11 位整数加 4 位小数正好 15 位）。
**为什么是问题**：Spec 承诺“加减按十进制精确计算”，计划的 BigInt 设计照做了计算这一段，但数进出世界的每一处（日志重放、远程调用、带值写法回写）都会在边界值上悄悄改数；差分测试与 `components.test.ts` 若只用小数值也测不到。
**如何核实**：运行 `bun .local/agent/works/w00039-novel-writing-plugins/tasks/t29-kernel-impl/reports/plan-review/tmp/json-precision.ts`。
**建议改法**：二选一，先改 Spec：把范围收到“绝对值小于一千亿（10¹¹）”，此时 JSON 数足够、BigInt 也可以换成整数缩放后的 `number`（10¹¹×10⁴ = 10¹⁵ < 2⁵³），计划里的 BigInt 可以去掉；或保留一万亿，但精确档的数在日志与远程消息里存成十进制文字（例如 `"1234.5"`），schema 与带值写法相应改。计划在 core 的测试里加边界值（`99999999999.9999`、`-99999999999.9999`、`0.1+0.2`）。

### 19. 远程消息上限：超限的请求到不了世界服务，`too-large` 只能在调用方一侧判；结果也要留帧头的余量
**严重程度**：重要；**类别**：遗漏；**对象**：计划（插件“browser 入口经远程服务调用”、验收映射“project 输出 18”）。
**位置**：Spec project 输出 18“一个写入请求或一个读取结果编码后超过远程消息的上限（1 MiB）时，得到 `too-large`”；计划验收映射把输出 18 放在 `node-log.test.ts`（nb-canon，没有远程链路）。
**现象**：服务端 WebSocket 的 `maxPayloadLength: RPC_MAX_MESSAGE_BYTES`（`src/server/rpc/listener.ts` 第 76 行），plugin-channel“单条消息上限 1 MiB，超过即断开”。浏览器发出一个超过 1 MiB 的写入请求，连接直接断开，这条链路上所有在途请求变成 `unknown-outcome`，世界服务根本收不到请求，也就无从回 `too-large`。结果一侧，帧头（请求 id、调用方、合同版本等）也算在 1 MiB 里，结果本身接近 1 MiB 时同样断线。Files 插件的做法是 `TEXT_BUDGET_BYTES = RPC_MAX_MESSAGE_BYTES - 64 * 1024`（`plugins/files/shared/contracts.ts` 第 36 行），在浏览器侧的客户端包装里先量再发（`plugins/files/web/client.ts` 第 44、85、97 行），服务端对结果同样按预算判。计划只写“经远程服务调用”，没有客户端包装，也没有预算。
**为什么是问题**：照计划实施，大请求（整篇替换的长条目、连同依赖的还原）会把作者的整个连接打断；`node-log.test.ts` 里测不到这一条。
**如何核实**：读上面三处源码与 `plugins/files/transport.test.ts` 第 120–135 行的边界测试。
**建议改法**：照 Files 的写法：canon 的共享合同里定义预算（上限减 64 KiB），浏览器入口给世界服务包一层客户端，发出前量请求、超了直接 `too-large`；世界服务对结果与分页按同一预算判。输出 18 的测试挪到插件的 `canon.test.ts`，经真实的 WebSocket 或进程间链路各测一次请求与结果的边界。（注：若插件按 plugin-channel 的规则“同一实例里的调用方直接用合同、不另包一层只转发的本地服务”，这层包装要放在浏览器入口的服务里，而不是只转发。）

### 21. “写入失败用只读目录”测不到追加失败；输出 7 的“截回”与“结局不确定”两条分支计划没有测法
**严重程度**：重要；**类别**：测试；**对象**：计划（验收映射 project 输出 7 行、切片 6“fsync 失败截回”）。
**位置**：计划第 97 行“写入失败用只读目录”；第 80 行“fsync 失败截回”；Spec project 输出 7（三种情形：写之前失败、已写部分已截回并落盘、不能确定 → `write-unknown`）、输出 16、场景 2。
**现象**：实测（`tmp/rodir`）：目录设成 555 后，向目录里已有的段追加照常成功，只有新建段才 `EACCES`。所以“只读目录”只能测到“开新段时写之前就失败”这一种；正常追加的失败、写了一部分后截回、fsync 失败、截回本身也失败（→ `write-unknown`）这几条都不会发生。真实文件系统上很难让 `write` 或 `fsync` 按需失败（要满盘的 loop 设备或 FUSE），计划没说用什么办法。
**为什么是问题**：输出 7 是持久性合同里最要紧的一条，`write-unknown` 又牵动只读状态与 `outcome`（输出 16）；照计划只会测出最简单的一条，其余分支没有任何测试。
**如何核实**：`tmp/rodir` 的实验（追加 ok、新建 EACCES）；对照 Spec project 输出 7。
**建议改法**：`./node` 的分段存储把“打开、写、fsync、截断”收成一个很窄的文件句柄接口；产品用 `node:fs` 的实现，测试另有一个按脚本注入失败的实现（第 n 次 `write` 只写一半后抛 `EIO`、`fsync` 抛错、`ftruncate` 抛错），并按 docs/testing“替身要与真实实现对过契约”写一组契约测试，让两种实现跑同一套正常路径。输出 7 的三种情形与 `write-unknown` 后 `outcome` 的结果都用注入实现测；只读权限另测一次“开新段失败”与“对已有段 `chmod 444`”。

### 22. 表达式白名单拒收负数字面量：ESTree 里 `-100` 是 `UnaryExpression`，白名单只放行 `!`
**严重程度**：建议；**类别**：一致性；**对象**：Spec rendering（第一轮处理 36、53、59 新加的表达式节点表）。
**位置**：Spec rendering“表达式只许下面这些语法节点”表：`Literal` 写“字符串、数、真假、`null`”，`UnaryExpression` 只许 `!`。
**现象**：acorn（mdxjs 用的解析器）把 `panel.存款 > -100` 的右边解析成 `UnaryExpression`（`operator: "-"`，参数是 `Literal 100`），实测确认。按节点表照字面实现，负数比较一律 `forbidden-syntax`；精确档允许负数（components 输出 14“绝对值小于一万亿”），作者写“存款 < -1000 ? 欠债 : …”这类条件会被拒。
**为什么是问题**：表里 `Literal` 的“数”读起来包括负数，但照节点名检查时不包括；两个实现者会做出不同的结果。
**如何核实**：`bun -e 'require("acorn").parseExpressionAt("panel.存款 > -100",0,{ecmaVersion:"latest"}).right'` 得到 `UnaryExpression -`。
**建议改法**：节点表加一行：`UnaryExpression` 的 `-` 只许直接作用于数字字面量（当作负数字面量）；`rendering.test.ts` 加一例。

### 23. 活页夹清单读不出、不合法或写到一半时，章序怎么给没有定义；照直实现会发布“删光所有章”的章序调整
**严重程度**：重要；**类别**：遗漏；**对象**：计划（插件 `project` 入口“读 `binder.xml` 得到章序……监视它的变化后把新章序交给世界”）与 Spec project“宿主提供：章序”、输出 9。
**位置**：计划第 61、117 行；Spec project 输入表“章序”与输出 9；`docs/specs/workspace/folder-kinds.md` 第 55、70 行（清单不存在、是目录、读不出、XML 不合法都按普通文件夹显示，不让整次失败）。
**现象**：插件监视 `binder.xml`，变化后读它、交给世界；世界与记下的章序比较，不同就发布 `reorder`。外部编辑器保存时的截断再写、作者手改出错、清单被删，都会让一次读取得到“没有章”或解析失败。计划与 Spec 都没说这时交给世界的是什么。最直接的实现（解析失败当空列表）会发布一次 `after: []` 的章序调整：所有安放在章上的变更与核对点都变成“章已删除”，进日志、进改动记录；下一次读到正常清单又发布一次调回来。章序调整“不能单独还原”（revisions 输出 13），这两条修订永久留在日志里。另外“未编排”的章节文件（文件在、清单里没有）算不算章、读取位置能不能指向它，也没说。
**为什么是问题**：一次手误或编辑器的非原子保存就会在世界里留下大面积的假删除与两条无法还原的修订；这是“只追加”日志里最不该出现的噪声。
**如何核实**：对照计划第 61 行、Spec project 输出 9 与 folder-kinds 的失败处理。
**建议改法**：Spec project 写明：清单不存在时视为“没有章”（只有这一种情况会把章序交成空）；清单读不出或不合法时不交新章序，保持上一次的章序计算，并写诊断 `binder-invalid`；监视触发后去抖并在解析成功时才比较。“未编排”的章节文件不进章序。插件测试加“清单写坏 → 世界不发 `reorder`、有诊断；改好 → 照常”。

### 24. 监视 `binder.xml` 这个文件，第一次改名替换之后就再也收不到变化（Files 的保存正是改名替换）
**严重程度**：重要；**类别**：正确性；**对象**：计划（插件 `project` 入口“监视它的变化”）。
**位置**：计划第 61 行；`packages/neuro-book/src/backend/locked-replace.ts` 文件头（Files 的条件保存“写同目录的临时文件 → 改名替换”）。

**严重程度**：建议；**类别**：接口与合同（归入“一致性”）；**对象**：Spec revisions 输出 6，连带计划 `src/revisions/` 的“带来的变化”。

### 26. 独占写入只在一个项目实例的内存里，两个 NeuroBook 进程打开同一项目时挡不住另一边
**严重程度**：建议；**类别**：遗漏；**对象**：Spec project 输出 10，连带计划“独占租约存在 service 里”。

### 27. 规模脚本放在 nb-canon 里量不到“含写入落盘”的真实发布：拿不到产品用的锁与插件的接线
**严重程度**：建议；**类别**：测试；**对象**：计划（验收映射“project 输出 14，场景 6 → `scripts/scale.ts`”、切片 3 与 8）。
**位置**：计划第 77、100、110 行；Spec project 输出 14“在最新一章发布一次记账（……含校验、计算、写入落盘……）：10 次的中位数在 100 毫秒以内”“在项目进程里直接调用”。
**现象**：发布的耗时包括取跨进程锁（proper-lockfile 建锁目录、`stat` 核对身份、释放）、核对尾部、追加、fsync、再核对。nb-canon 不依赖 proper-lockfile（第 3 条），它的规模脚本只能接一个假锁或不加锁；切片 3 时连 node 存储都还没有（第 6 片才有）。“打开到可以读”也应包含插件读活页夹、建锁目录这些步骤。计划写“第 8 片的测量脚本”，又把脚本放在 `scripts/scale.ts`（按上下文是 nb-canon 的），两处不一致。

**如何核实**：对照计划第 23、77、100、110 行。
