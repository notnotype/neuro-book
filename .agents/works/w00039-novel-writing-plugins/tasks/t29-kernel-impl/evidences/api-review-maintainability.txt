### 1. 补丁 op 的"分类"散在 5 个源文件的约 12 处字符串比较里，没有一张表
- **严重程度**：重要；**类别**：可维护性 / 耦合
- **位置**：packages/nb-canon/src/core/schema.ts:112；model/apply.ts:114、263、308；world/edits.ts:92、114、125、127；world/world.ts:468、742、747、795、803；engine/reference.ts:215；engine/incremental.ts:287；tests/differential.test.ts 的 Sim.patch()
- **现象**：接入草稿"加一种补丁 op `multiply`（数值字段乘一个系数）"，要逐处查下面这些地方，没有哪个文件告诉你"一种 op 要回答哪几个问题"：
  - schema.ts:112 加一个 Literal；
  - apply.ts 的 applyFieldPatch（case "add"，263 行）和 applyElementPatch（308 行的 `else if (patch.op === "add")`）各写一份几乎相同的"数值运算 + 精确位数检查 + 未知值检查"，要改两处；
  - apply.ts:114 `clearsIncomplete`（赋值类解除不完整，加减不解除）：新 op 属哪类要自己判断；
  - edits.ts:114 `last.op === "add" || last.op === "note"`（累加类，就地改不能改）；edits.ts:125 `set || replaceBlock`（可被就地改写的类）；
  - world.ts:747 `patch.op !== "note"`（带数值就要依据）；world.ts:795 `patch.op === "add" ? Math.abs(value) : value`（依据原句里的数是取绝对值还是原值）；world.ts:803 `patch.op === "set"`（核对点推出的是值还是差额）；world.ts:468 `listAdd`（依赖分析里"补丁加进列表的元素"）；
  - reference.ts:215 与 incremental.ts:287 各写一份 `patch.op === "set" && addressesOverlap(...) && path.length <= ...`（"最近一次赋值"的判定，用于核对点不符时的嫌疑列表）；
  - 差分测试的生成器 Sim.patch() 硬编码了 add/set/note/listAdd/listRemove 五种，新 op 不会自动被覆盖。
  漏掉其中任何一处，编译都过：全是 `patch.op === "字符串"` 比较，不是穷尽的 switch。例如 edits.ts:114 漏了，multiply 写的值会被当成"可改写"，就地改的结果会走到 `sameJson(patches, change.patches)` 的兜底才报 accumulated-value，行为碰巧对但原因不对。
- **为什么是问题**：每个 op 要回答的问题是固定的（是否赋值类、是否累加类、是否数值带依据、依据取绝对值还是原值、核对点推出差额还是值、是否改列表元素），但答案分散在 12 处，新增 op 的人只能靠 grep `"add"`。这正是"加一种补丁"这个最常见的扩展。
- **建议改法**：在 core/ 加一张 `PATCH_OPS: Record<PatchOp, {resets: boolean; accumulates: boolean; numeric: boolean; ...}>`（schema.ts 的 PatchOpSchema 用 `Object.keys(PATCH_OPS)` 派生或反过来用 `satisfies Record<PatchOp, ...>` 保证穷尽），导出 `resetsValue(op)`、`isAccumulating(op)` 等谓词，上面 12 处改用谓词。apply.ts 的两份 add 逻辑抽成一个 `applyNumeric(current, patch, field)`。差分 Sim.patch() 改成"对表里每种 op 至少生成一次"。这样加 multiply 的清单变成：改表一行 + 写一个 apply 分支 + 测试。

### 3. 两个引擎之间不只是"安排先后与缓存"不同：语义档核对点的起点、计划纳入规则、待处理拼装都各写了一份

### 6. 服务的失败有四种表达，浏览器收到的失败只有 `{code: string}`，不能按码窄化
- **严重程度**：重要；**类别**：API 形状 / 使用体验
- **位置**：service/service.ts:130-200（读）、:307-356（写）、:420-440（独占）；backend/remote.ts:21-46、59、89-98；shared/contracts.ts:148-154
- **现象**：草稿 draft2-service-use.ts 里直接调 WorldService，每个方法的失败要换一种判法：
  - `WorldService.open` 与 `acquireExclusive`、`renewExclusive`：失败是 `{code}` 对象，成功是另一种对象，用 `"code" in x` 区分；
  - `entry`、`pending`、`lookup`、`tree`、`changes`、`questions`、`suggestions`、`revisions`：失败是字符串哨兵 `"chapter-not-found"` / `"cursor-stale"`，成功是对象，`entry` 还有 `view: null`；
  - `render`：`null`（条目不存在）、`"chapter-not-found"`、对象三种；
  - `publish`、`editInPlace`、`recordDelta`、`writeBack`、`revert`：`{ok: false, failure}`；
  - `outcome`：成功是 `{published}` 联合，失败是 `{code: "write-unknown"}`，混在同一个返回联合里。
  remote.ts 再把它们统一成 `{ok:false, code:"canon", detail}`，每个方法按自己的约定挑助手（`typeof page === "string"` / `"code" in lease` / `result.ok`）。这就是 remote.ts 里 `"code" in x`（56、82、91、97 行）、`typeof page === "string"`（41 行）、`result.ok`（25、78 行）三种判法并存的来源。
  浏览器侧：`CanonFailure` 是 `{code: string; [detail: string]: unknown}`（contracts.ts:149-152）。草稿 draft3-browser.ts 里 `if (f.code === "busy") f.holder` 的 `f.holder` 是 `unknown`。失败码在源码里共有约 52 个字面量，分在 ServiceFailure（只从 `./node` 导出）、WriteFailure/EditFailure/WriteBackFailure/RevertFailure（从主入口导出，浏览器只想要类型却要引入整个 MDX 解析链的模块图）、ApplyFailure、ValueProblem 里。契约文件顶部注释解释了为什么不逐个声明为业务失败码（与路由层同名），但没给浏览器一个可窄化的联合类型。
- **为什么是问题**：每个新调用方（TUI、Agent 工具）都要重新学一遍"这个方法用哪种判法"；浏览器的错误处理只能写 `f.code === "字符串"` 加强转型。
- **建议改法**：
  1. 读方法统一成 `Result<T> = {ok: true; value: T} | {ok: false; failure: Failure}`（`chapter-not-found`、`cursor-stale`、`world-locked` 都是 `Failure`），`entry` 里"条目不存在"用 `value.view === null` 或 `failure: {code: "entry-not-found"}` 二选一，不要 null 又有哨兵。remote.ts 的 `read/paged/fail/published` 助手收成 `passthrough(result)` 一个；
  2. 在 `./schema` 导出 `CanonFailure` 联合类型：把 ServiceFailure、WriteFailure、EditFailure、WriteBackFailure、RevertFailure 的类型（只是类型）放进 core/ 的一个 failures.ts，主入口与 `./schema` 都从那里导出；CanonResult 的 `failure` 类型改用它，浏览器就能 `switch (f.code)` 窄化。

- **现象**：一个文件同时是：对象表的重放与持久不变量（World）、写入前校验（validate：条目树、命名空间、字段值、块语法、依据、出场、链接、未决问题……逐对象种类）、还原（补偿、依赖闭包）、id 引用扫描、缺省值填充、影响计算。`validate` 是一个 151 行的函数，按对象种类串着 if；`opReferences` 导出给 service.revisions 用，所以 service 还从 world.ts 导入一个"纯函数工具"。加一条写入校验规则（例如新的 `invalid-tree` 检查）要在 151 行里找位置，且 validate 与 checkBasis 里再次重复 `patch.op` 的分类（发现 1）。
- **为什么是问题**：文件大本身不是错，但这里每一块的变化原因不同：校验随 Spec 的失败码变，还原随修订 Spec 变，id 扫描随 schema 变。放一起，每次改动都在 870 行里找、评审 diff 也大。
- **建议改法**：纯拆文件，不改行为：world/validate.ts（validate、checkBasis，再按对象种类拆成 validateEntry / validateChange / validateCheck 三个函数）、world/revert.ts（compensate、dependsOn、pathsOverlap、isAppend、readPath）、world/references.ts（ID_KEYS…referencedIds、opReferences、replaceTempIds，和发现 8 的集合一起放），world.ts 留类和 computeImpact。预计 world.ts 降到约 450 行。

### 10. 宿主要自己装配 12 个端口，`.nbook/world/log` 等目录布局在 3 处各写了一遍
- **严重程度**：建议；**类别**：使用体验 / 耦合

### 11. `WorldService` 的位置、边界与自身实现里的几处小重复
- **严重程度**：建议；**类别**：耦合 / 文档
- **位置**：service/service.ts:1-4、114-116、358/384/417、339/375；src/node/index.ts:9；AGENTS.md "边界"；tests/architecture.test.ts:7-13
- **现象**：
  - 目录与出口不一致：服务在 `src/service/`，但只从 `./node` 导出，README 说 `./node` "只在 Bun 里用"；service.ts 头注释说"所以本模块不引用 `node:*`"。实际 service.ts 依赖 `../node/log`，而 log.ts 引入了 `node:path`（只为一个 `join`），所以 service 间接依赖 `node:*`。architecture.test 只排除 `node/` 目录，没有对 `service/` 的闭包做检查，所以这条"可以放在任何宿主"的说法没人守。
  - `get world(): World` 让调用方拿到内存世界：它的 `publish`/`revert` 返回新世界但不落盘，调用方可以绕过写入队列与租约；world-host.ts 只是为了读 `world.data.entries.size` 写日志。`diagnostics` 是公开可变数组。
  - 同一段"排进队列"的代码三份（358、384、417 行：`const next = this.#queue.then(run, run); this.#queue = next.catch(() => undefined); return next;`）；`changed` 事件对象的拼装两份（339、375 行）。
- **为什么是问题**：多一个入队路径的人忘了 `.catch` 就会让队列在第一次失败后永远拒绝；`world` getter 是一个"不推荐但可用"的第二套 API。
- **建议改法**：① 要么把 `service/` 并进 `node/`，要么把 log.ts 里的 `join` 换成字符串拼接，并给 `service/` 加和 `./schema` 一样的闭包测试；② `world` getter 改成 `stats()` 之类的只读摘要（entries 数、版本），或至少文档写"只读，不得调用其写方法"；③ 抽 `#enqueue(run)` 与 `#announce(revision)` 两个私有方法。

### 12. 主入口 93 个值导出，外部只用到 1 个；README 与 AGENTS.md 没有模块地图，也没有"怎么扩展"清单
- **严重程度**：建议；**类别**：文档 / API 形状
- **位置**：src/index.ts:7-38；README.md（8 行）；AGENTS.md（23 行）
- **现象**：`Object.keys(await import("…/src/index")).length` 是 93（./schema 32，./node 11）。neuro-book 里对主入口只导入 `buildRegistry` 一个值（world-host.ts:20），其余都是类型。测试里则大量绕过入口深导入 `../src/world/world`、`../src/engine/incremental`、`../src/render/syntax` 等（11 种深路径）。入口里导出了 `parseSegments`、`applyChanges`、`compareTie`、`placementRank`、`readNumbers` 这样的内部积木，两行超长的 `export {…}`（index.ts:15-35 每行 200 字以上）也难以评审。

### 13. 同一组枚举与声明字段在 schema、服务签名和合同里各手写一遍
- **严重程度**：建议；**类别**：可维护性
- **位置**：core/schema.ts:142、168、187（status 联合）；service/service.ts:218、240、249（changes/questions/suggestions 的 status 内联联合）；shared/contracts.ts:32、54-55、65-66、72（Mode、kind、status、by 再写一遍）；components/registry.ts:20-47、78-86（ComponentDeclaration 接口、ComponentType、复制构造）
- **现象**：
  - 变更/问题/建议的状态联合在 schema.ts 内联各一次，在 service.ts 的方法签名里再抄，在 contracts.ts 的入参 schema 里第三次写。加一个状态要改 3 个文件，漏改编译不报（入参 schema 比服务签名宽或窄都能过）。

### 14. 临时 id 与局部 id 的前缀约定一半没导出、一半用正则重写

## 好用的地方
1. model/apply.ts 把"套一条变更"收成一个模块，两个引擎共用，头注释把"整条套上或整条不套、不完整标记"的语义写得很清楚；这是整个包里最容易维护的部分。
2. 三个出口的边界有机检：`tests/architecture.test.ts` 用依赖闭包守住了 `./schema` 只依赖 TypeBox，与主入口不碰 `node:*`；这种"用测试守住边界"的做法值得推广到发现 11 的 service。
3. `LogFiles` 窄接口 + 按脚本注入失败的替身 + 契约测试跑同一组用例，加上 `ServicePorts` 注入时钟、定时器、摘要，让服务的并发与断电类测试可以确定地写。
4. 注释普遍写"为什么"和"调用方要遵守什么"（例如 incremental 里不留对旧引擎的引用以免拉住历史版本；write 的 `compute` 必须是纯函数），并引用 Spec 编号；测试名也用 Spec 编号，从行为追到代码很快。
5. 差分测试的设计（固定种子、失败时打印种子与步骤、断言套不上的变更至少占 10% 防止生成器退化）是维护引擎时最重要的安全网；只缺发现 4 说的覆盖面。
