# 作者视角的领域分析（第一轮）

开发者 2026-11-01 提出从作者视角做领域建模，给了一个例子：故事种子加第一章大纲。本文是那一轮的分析，供后面逐项讨论用，**不是定稿**。例子里的书下文称“本书”。

> 后几轮讨论推翻了本文的一部分：第四节的星瑕.md 写法开发者认为程序处理起来麻烦；第八节的“状态块”与卡片改为 MDX 模板；“作者只维护正文推不出来的东西”仍成立，但骨架改为事件溯源（剧情变更日志加状态补丁）。现行结论以 Work README 的决定表为准。

## 术语（暂定）

“设定”这个词在讨论里有两个意思：作者脑子里认定的东西，和存它的文件。本文只用前一个意思，文件另说。

| 术语 | 意思 | 不是什么 |
|---|---|---|
| 设定 | 作者认定在故事里成立的东西：世界、人物、规则、前史 | 不是 `lorebook` 文件，文件只是存放它的一种方式 |
| 状态 | 设定里随故事时间变化、并且要求精确的那部分：钱、物品、魔力、形态、所在地、生死 | 不是人物的全部属性；外貌、性格一般不算 |
| 计划 | 作者打算怎么写：剧情线、章、场景，打算在哪一章揭示什么 | 不是故事世界里的事实 |
| 作者笔记 | 作者给写作者（自己或 Agent）的要求和意图，例如“要戏剧化地搞砸” | 在故事里不成立 |
| 待定 | 作者明说还没想好、或者给了备选还没拍板的事 | 不能当事实写进正文 |
| 手记 | 作者原话，原样保存 | 不是整理后的设定 |
| 正文 | 写出来的章节 | |
| 故事种子 | 见第五节的定义 | 不是一句话梗概，也不是大纲 |

三条时间轴，后面反复用到：

| 轴 | 意思 | 本书的例子 |
|---|---|---|
| 故事时间 | 故事世界里事情发生的先后 | 6 岁灾难早于觉醒，觉醒早于隐退，隐退早于开局的早餐 |
| 叙述位置 | 在第几章讲出来，也就是读者读到的先后 | 早餐在第 1 章；6 岁的灾难也许到第 20 章的回忆里才讲 |
| 创作时间 | 作者什么时候定下、什么时候改的 | 种子写于 10-31；11-01 的第一章大纲补了“被软禁、靠魔偶逃脱” |

nb-story 只有前两条（阅读位置、故事时间）。作者视角多出第三条。数据库里管这种情况叫双时态（valid time 与 transaction time），这里还要再加一条叙述位置。

## 一、创作由哪些操作组成

开发者列了作品内七项、作品外四项。下面按“产出什么”展开，不按先后：作者会来回跳，而且有的作者直接写第一章，设定靠脑子记。

### 作品内

| 操作 | 细分 | 产出 |
|---|---|---|
| 立项 | 选题与定位（题材、目标读者、平台、篇幅、卖点与标签）；书名；简介文案 | 立项笔记 |
| 故事种子 | 第一份整体构想 | 手记 |
| 世界观 | 规则与力量体系；舞台与地理；势力与组织；历史与年表；社会表层与里层；术语 | 设定 |
| 人物 | 定位与功能（主角、对手、配角各起什么作用）；取名；外貌与服装；性格与说话方式；前史；欲望、恐惧与弱点；成长安排（弧光）；能力与数值；身份与马甲；人际；立绘 | 设定、状态的初值、图片 |
| 体系与数值 | 面板有哪些字段、等级、技能、物品、货币、规则（游戏文、面板文、系统文） | 状态的字段声明 |
| 剧情 | 总纲（核心冲突、结局）；分卷；剧情线与支线；伏笔与揭示安排（第几章揭哪个马甲）；节奏与爽点分布；故事年表 | 计划 |
| 细纲 | 章纲：场景、视角、本章冲突、结尾钩子 | 章计划 |
| 正文 | 起草、续写、扩写与缩写、改写与润色 | 正文 |
| 记账 | 写完一章后：更新状态，补新出现的人物与地点，记伏笔推进，核对计划写到了没有 | 设定、状态、计划的更新 |
| 审查 | 设定一致性、数值、时间线、知情泄漏（马甲被写漏）、节奏、文风与 AI 味、错字、平台审核 | 问题清单 |
| 改稿 | 局部改；结构改；吃书之后的连锁修改 | 正文与设定 |
| 记灵感与待定 | 随手记；没想好的事 | 手记、待定清单 |

开发者原来的清单里没有“记账”。它其实是最累、最想交给 Agent 的一项，也是 nb-story 的抽取最直接能帮上的地方：从写好的章节里读出发生了什么，作者只核对。

### 作品外

竞品分析与拆书（产出可复用的套路与结构）、查资料（考据）、读者反馈（评论，追读、收藏、订阅数据）、跨作品的素材与灵感库、文风学习、写作技巧学习、发布与运营（更新计划、作者有话说）。

### 两种开写方式都要支持

- **先设计后写**：种子、世界观、人物、大纲都齐了再写第一章。
- **先写后补**（开发者说的“比较懒的”）：直接写第一章，只把技能、数值和还要构思的东西记下来。这时知识库靠记账从正文里长出来，不是开写的前提。

开发者的另一条观察：作者是承载树与因果树一起想的。叙事学里管这两样叫故事（fabula，事情按因果、按时间怎么发生）和讲法（syuzhet，按章节怎么讲出来）。本书的第一章大纲就同时含两样：三个场景是承载树，“好哥哥建议清单”是一条跨好几章的剧情线，属于因果树。所以一次输入要能同时写进两棵树，哪棵也不能只当另一棵的派生视图。

## 二、设定会怎么变

开发者举了两种：随剧情推进补充解释，以及作者补漏改错。按“动的是哪条轴”和“旧的还算不算”可以分得更细：

| 变化 | 本书的例子 | 动的轴 | 旧的还算不算 | 系统要做什么 |
|---|---|---|---|---|
| 世界变了（剧情推进） | 存款从很多变成不多；第 20 章妹妹撞见女性原身 | 故事时间 | 在更早的时刻仍然成立 | 记成带时间的变化，不覆盖旧值 |
| 补充 | 第一章大纲补了“被软禁、靠魔偶逃脱”；种子只说“隐退” | 创作时间 | 成立，只是不全 | 合进去，查和已写章节、已有设定有没有冲突 |
| 定下来（填空） | 兄妹为什么闹矛盾（现在没想好） | 创作时间 | 原来是空的 | 从待定里划掉；查已写章节有没有暗示过别的原因 |
| 改正（补漏） | 发现某人年龄前后算错 | 创作时间 | 错的 | 改；列出已写章节里沿用旧值的地方 |
| 改主意（重设定、吃书） | 把对策局从外包组织改成官方直属 | 创作时间 | 当时是对的决定，现在不要了 | 同改正；已写章节要么改稿，要么接受吃书 |
| 揭示 | 父母的“死亡”其实是“双王”（如果理解没错，见第六节待确认） | 叙述位置 | 世界没变，变的是读者和角色知道的 | 设定不动，记在哪章揭示、谁知道 |
| 计划落地或走样 | 大纲说每条建议都搞砸，写出来只搞砸了两条 | 叙述位置与创作时间 | 计划变成正文，或者计划跟着改 | 对照计划与正文，问作者改哪边 |
| 备选与暂名 | 对策局的名字；“可能是主角也不想暴露身份” | 创作时间 | 还没拍板 | 留在待定里 |

由此得出的两点：

1. **只有第一行是故事世界里的变化**，也就是要建模的“状态”；其余几行都是作者那边的变化。作者那边的变化不必在世界模型里存版本，文件历史就够用（仓库里已有 `nb-history`）。它们真正需要的是**影响检查**：改完以后，已写的章节、已定的计划里哪些地方跟着不对了。
2. **Agent 要分得清剧情变化和改正。** “她花了一万”是一条新的变化；“开局其实是五万，不是四万”是改一条旧记录。两句话在聊天里长得很像，记错了状态就全乱了。分不清时要问。

## 三、哪些要作者维护：状态、关系、知情

一条原则：**作者（以及替作者干活的 Agent）只维护正文推不出来、或者推出来不可靠的东西。**正文推得出来的，记账时从正文抽。

推不出来的有四类：

- 还没写的：计划、将来的走向；
- 写了也不会明说的：真相、秘密、前史里不打算写出来的部分；
- 作者的意图和要求：作者笔记；
- 要求精确、却不一定在正文里出现的数：状态。例如存款，正文不会每章报一次余额，但写到第 30 章买东西时必须知道还剩多少。

按这条原则看开发者问的三样：

| 东西 | 谁维护 | 理由 |
|---|---|---|
| 状态（钱、物品、魔力、HP） | 作者与 Agent 维护，写完一章由 Agent 从正文提出变化、作者确认 | 正文只零星出现数，要有一本账；面板文的面板就在正文里，读者会对账 |
| 结构关系（兄妹、好友、所属组织） | 是设定，开写前就定，在人物文件里用链接写，不另设关系管理 | 很少变；变了按“世界变了”记 |
| 态度的变化（妹妹生气、慢慢和好） | 从正文抽，不维护 | 正文里写得出来；作者对它的安排（从疏远到修复）是计划里的一条剧情线 |
| 量化的好感度（面板里的） | 是状态 | 作者决定把它量化了，就要精确 |
| 知情（谁知道哪个身份） | 开写前作者就要有一张表；写完后从正文抽出来与表核对 | 本书三个身份全靠它；写漏一句就穿帮 |

关系图因此不是一份单独维护的数据，而是从链接、正文抽取与状态算出来的视图。

这条原则也是 nb-story 的经验在作者这边最直接的用处：抽取当成记账的帮手，不需要先把两套系统合起来。

## 四、作者的话能拆成哪些部分

开发者问 `星瑕.md` 能写什么：能写过去和未来吗，能写作者笔记吗。答案是都能写。作者的人物文件本来就是“作者对这个人的全部想法”，过去、将来、笔记都在里面。问题不在能不能写，而在于每一段话要带着几种信息，读它的程序和 Agent 才不会用错。

### 五个维度

| 维度 | 取值 | 本书的例子 | 用错了会怎样 |
|---|---|---|---|
| 作者在做什么（言语行为） | 宣布（在故事里为真）、要求（给写作者的指令）、打算（以后要写）、评论（感受与动机）、留白（没想好） | “主角有三个身份”；“要用戏剧化的方式实施”；“宇宙中还有更大的舞台”；“有很多值得写的”；“具体怎么回事我还没想好” | 把要求当成事实写进正文 |
| 说的是哪一层 | 故事世界（发生了什么）、讲法（怎么讲：章、场景、视角、揭示顺序）、创作（意图、风格、市场） | 父母死亡；第一章是早餐场景；冲突和感情值得展开 | 因果树和承载树混在一起 |
| 时间 | 前史（开局之前）、开局、将来、不随时间（规则） | 6 岁的灾难；钱不多但够用；更大的舞台；认知魔法不能改变生理结构 | 写第 1 章时把将来的事当成现在 |
| 谁这么认为（视角） | 真相、表面说法、某个角色的认知 | 官方明面上报道隐退（表面）；被软禁（真相）；妹妹只知道男性身份 | 马甲穿帮，或者把官方说法当成真相 |
| 确定到什么程度 | 已定、倾向、备选、暂名、待定 | “这里是双王”；“可能是不想暴露身份”；对策局的名字；兄妹矛盾 | 待定的被当成事实写进正文 |

第一个维度有一处要特别说明。作者关于故事世界说的话是**宣布**：说了就成真，不需要证据，作者对自己的故事有这个权威。读者从正文读出来的却是**判断**，要有出处，可能看错。nb-story 每条记录都要求原文出处，作者这边的设定不需要，两边“感觉不一样”的根源就在这里。不过宣布也会和已写的正文打架，那时由作者决定哪边算数。

### 程序要知道多少

五个维度不必都写成结构。大部分让模型读文字自己判断就够了；程序必须知道的只有会造成上表最后一列那种错误的地方：

- **时间**：写手按章取材时，要分得出前史、开局与将来。
- **视角**：秘密与知情表要能被程序读到，揭示检查才做得了。
- **确定性**：待定与待确认要能列成清单。
- **作者笔记**：要和故事事实分开。

做法上，用固定的小节标题分开时间、确定性与作者笔记（作者也看得懂），只有身份与知情用一张表。其余都是自由文字。

## 五、故事种子，以及作者原话怎么记

### 定义

**故事种子**是作者在动笔前对整部作品的第一份构想，用作者自己的话写，用来长出后面所有的设定、计划和正文。它至少要回答“这是一个关于谁、在什么处境下、面对什么冲突的故事”，通常还带着作者已经想到的世界、前史、开局和走向。

它有四个特征：

1. 它是作者意图的陈述，不是作品内容本身；
2. 不完整，有意留白（“没想好”）；
3. 时间是混着的：前史、开局、将来写在一起；
4. 确定程度是混着的：已定、倾向、备选、暂名写在一起。

它和几个相近的东西不同：

- **一句话梗概（logline）**只是从种子里提炼出来的核心。本书的可以是：“被官方卸磨杀驴的蓝星最强魔法少女隐退回家，用认知魔法扮回哥哥照顾疏远的妹妹，而她早已习惯了女性的身体。”
- **大纲**是排好了先后的剧情。
- **设定集**是整理过的东西。

开发者给的那段文字是故事种子，里面五样都有：核心（梗概）、世界观（蓝星表层与里层、超凡种类、更大的舞台）、前史（灾难到隐退）、开局状态（钱、回家、私下用原身），以及身份设计（三个身份与谁知道）。另外还夹着待定和作者的评论。

### 两种记法都要，各管一件事

开发者提了两种做法：Agent 总结后分门别类放进各个文件，或者原文保存作参考材料。只用其中一种都有问题：

- **只总结**：会丢信息。本书的例子：“父母死亡（不是双亡就是双王，这里是：双王）”。总结成“父母死亡”，反转就没了。
- **只存原文**：前后会打架（种子说隐退，第一章大纲说软禁），越积越长放不进上下文，也没法给作者看。

所以两样都做，并且分开职责：

1. **手记**：作者原话原样保存，带日期，不再改。它是出处，也是 Agent 理解错了时回头查的地方。
2. **整理后的文件**：Agent 把原话分发到设定、计划、状态里，每段标出它出自哪份手记的哪一段。这一点借鉴自 nb-story“每条记录都有原文出处”。整理后的文件代表当前的认定，后来的原话和它冲突时改文件，手记照旧留着。
3. **待确认**：原话里有歧义的，Agent 不替作者拍板，列成问题。只有挡住眼前写作的才立刻问，其余攒着。

开发者对 chatbot 模式的判断（上下文有限，只负责做、不负责展示）正好说明整理后的文件有两个读者：模型要的是压缩过、能检索、不丢关键事实的上下文；作者要的是一眼看得清、能改的展示。是同一份文件，看的视图不同。

开发者还说“作者的描述文字表达力最强，NeuroBook 管理的格式不如它”。对应的做法有三条：保留原话；整理后的文件以文字为主，结构只用在程序必须计算的地方（第四节“程序要知道多少”）；每段都有出处，可以回到原话。

## 六、例子：第一章大纲进来以后

### 分发

| 大纲里的话 | 去哪 | 属于 |
|---|---|---|
| 早餐，妹妹依旧生气、傲了一下、出门上学；主角感叹“这个哥哥真难当” | 第 1 章计划，场景 1 | 承载树 |
| 回房关门，关闭认知滤镜，露出真身，在阳台读《如何做个好哥哥》 | 场景 2；状态变化：形态从哥哥变为原身 | 承载树、状态 |
| 联系好友彗，问“如何做一个好姐姐”，得到五条建议 | 场景 3；新人物彗；道具：那本书 | 承载树、设定 |
| 彗帮她做了魔偶，从软禁中脱身 | 星瑕的前史（补充）；新道具魔偶 | 设定 |
| 建议看似都好，但要用戏剧化的方式实施：低情商、搞砸、主角迟钝、事后才发现 | 剧情线“做个好哥哥”：每条建议一段，跨好几章；这条线的作者笔记 | 因果树、作者笔记 |
| “被弟妹抱着哭、钻被窝说悄悄话”姐姐做可以、哥哥不行 | 同一剧情线里的笑点；依赖“妹妹只知道哥哥身份” | 计划、知情 |

一段大纲分进了六七个地方。这正是作者不该自己维护结构的原因：作者讲一遍，分发是 Agent 的事。

### 待确认

Agent 读到这里应该提出这些问题，而不是自己猜：

1. “不是双亡就是双王，这里是：双王”：是指父母其实没死，而是成了（隐藏的）大人物吗？种子同时写着“父母死亡”。
2. 魔偶现在还在软禁处替她吗？官方知道她跑了吗？
3. 彗知不知道哥哥这个身份？她问的是“好姐姐”，看起来不知道。
4. 官方当年答应安置妹妹，说明官方知道魔法少女和星瑾有关系。官方知不知道魔法少女就是星瑾的哥哥？这关系到哥哥身份安不安全。
5. “这三点看似都是好建议”，列的是五条：指前三条，还是五条都要搞砸？

其中 3 和 5 影响第一章怎么写，应该立刻问；1、2、4 可以攒着。已经明说没想好的（兄妹矛盾的原因、对策局的名字）只进待定，不追问。

还有一处值得注意：种子说“隐退”，大纲说“软禁后靠魔偶逃脱”。这属于第二节的“补充”：对外报道隐退，实际被软禁、逃了出来。两段原话合起来才是完整的设定，任何一段单独看都会误解。

### 加一个面板（开发者要的数值）

建议加魔法精灵：魔法少女契约附带的小精灵，隐退后跟着主角，能展开面板。字段按“能把模型的难点都用上”来挑：

```text
【星瑕】
形态        哥哥（认知滤镜）   维持消耗 每小时 30 魔力
魔力        3,200 / 12,000
时间回溯    剩余 1 次（每月恢复 1 次）
存款        ¥41,800
星瑾好感度  -30（冷淡）
今日任务    让星瑾吃完早餐（失败）
```

| 字段 | 考验什么 |
|---|---|
| 形态与维持消耗 | 状态随场景变（第 1 章场景 2 就变了一次）；扮哥哥耗魔力，把“维持起来累”变成了数 |
| 魔力 | 连续消耗与恢复，正文不会每次都报数，要靠账算 |
| 时间回溯次数 | 和世界线有关：回溯以后存款、好感度回到回溯之前，回溯次数却不回去，像记忆一样跨线（t04） |
| 存款 | 最普通的流水，面板一出现就要对得上账 |
| 好感度 | 关系被作者量化以后就是状态（第三节） |
| 今日任务 | 精灵派的任务把“做个好哥哥”这条剧情线变成游戏里的任务，计划和状态挂在一起 |

精灵的名字、面板是不是只有主角看得见、精灵知不知道哥哥身份，留给作者定。

## 七、跑团

### 类型

几种分法是交叉的：

- **按规则轻重**：
  - 重规则：D&D 5e、Pathfinder。职业、等级、战斗网格，数值多。
  - 中等：《克苏鲁的呼唤》（CoC）第 7 版。技能是百分比，有理智值（SAN），以调查为主。
  - 轻规则、叙事向：PbtA 一系（例如《启示录世界》）、FATE、《暗夜刀锋》。数值少，靠叙事动作和进度钟推进。
  - 中文圈另有各种自制规则，例如无限团。
- **按剧情来源**：
  - 模组团：主持人用现成或自写的模组，模组里有预设的真相、场景、线索和结局。
  - 沙盒团：只给世界与势力，玩家去哪，剧情就在哪长出来。
- **按长度**：单次团（一两次跑完）与战役、长团（几十次，跨月甚至跨年）。
- **按形式**：
  - 线下桌面；
  - 线上语音团，配合 Roll20、Foundry VTT 这类在线桌面；
  - 文字团，在 QQ 群或论坛里跑，靠骰娘机器人掷骰、记录属性与日志；
  - 单人团，用随机表代替主持人。
- **相近但不完全是跑团**：
  - 剧本杀：一次性，每人拿自己的剧本，目标是推理。
  - 日本的跑团 replay：把跑团记录整理成出版物，《罗德岛战记》就出自 D&D 的 replay。这是跑团变成小说的现成先例。

### 数值和剧情怎么被主持

- **主持人**（D&D 叫 DM，CoC 叫 KP）手里的模组一般有：
  - 背景真相：只有主持人知道到底发生过什么；
  - 导入；
  - 场景与地点；
  - 线索：每条线索在哪、靠什么检定拿到；
  - NPC：动机与数值；
  - 时间表：玩家不插手的话，坏人第几天做什么；
  - 结局分支。
- **玩家**每人一张人物卡：属性、技能、HP、SAN、物品、背景、经历。卡上的数由玩家自己改，主持人裁定。
- **数值怎么变**：玩家宣布行动，主持人判断要不要检定，掷骰，再按规则改数。受伤扣 HP，看到怪物扣 SAN，此外还有花钱、得物品。数值的变化来自规则和骰子；剧情来自玩家的选择和主持人的即兴。
- **剧情怎么推**：主持人按模组摆出场景，玩家自由行动，偏离模组时主持人即兴补。
  - 常用“三条线索原则”：每个关键结论至少准备三条线索，防止玩家漏掉一条就卡住。
  - 叙事向规则用“进度钟”：把一件将要发生的事分成几格，推进一次涂一格，涂满就发生。

### 怎么“存档”

- **人物卡**：当前状态。纸卡用铅笔写、橡皮擦，是快照，不是流水。
- **团录**：
  - 文字团由骰娘记下整段对话，跑完导出，再染色、整理；
  - 语音团靠主持人或玩家写战报。
- **主持人笔记**：进度到了哪个场景，玩家拿到了哪些线索，NPC 现在的处境和态度，时间表走到哪，埋下的哪些线还没收，下次要准备什么。
- **开场回顾**：下次开团先“上回说到”。
- **在线桌面**：Foundry 之类把地图、角色、日志都存在一个“世界”里，下次打开接着用。

### 对 NeuroBook 的启示

| 跑团 | NeuroBook |
|---|---|
| 模组的背景真相 | 设定里读者还不知道的部分（秘密） |
| 线索与“谁拿到了哪条” | 揭示计划与知情 |
| 人物卡 | 状态 |
| 时间表、进度钟 | 计划里“不管主角做不做都会发生”的事 |
| 团录 | 正文 |
| 主持人笔记 | 记账：写完一章后更新的东西 |
| 上回说到 | 写下一章之前给写手的提要 |

最大的不同是：跑团只往前走，不改已经跑过的部分，所以人物卡用快照就够。写小说会回头改前文、插补叙、回档，只存快照不够，要记下每一次变化。这支持开发者想法 2 的事件溯源。

## 八、开发者的四个想法

### 1. 文件跟着剧情走

可行。会变的内容分两种，办法不同：

- **会变的数**（年龄、存款、魔力）：用想法 3 的引用，按章渲染。
- **会变的描述**（性格成长、外貌变化，例如断了一臂）：写成带章节或时间的段落，例如“第 30 章起：……”，渲染时按章挑出成立的那段。

“跟着剧情走”要先说清按哪条轴走。写手写第 N 章，看的是叙述位置 N 时的样子；补叙章、回档章要按故事时间与世界线取值。默认按叙述位置，复杂的情况放到 t04。

### 2. 状态是一个大 JSON，用事件溯源

方向同意，有五点补充：

- **存的是变化**（流水），JSON 是算出来的快照，作者看到的是面板。
- **字段要先声明**：这本书有哪些数、各是什么类型。不声明的话，Agent 一会儿写“存款”一会儿写“钱”。字段声明就是面板的 schema，表单（t10）和正文里的面板文字都能从它画出来。
- **相对值与绝对值都收**：
  - 相对值（花了两千）是剧情里发生的事，绝对值（面板显示剩 3.8 万）是正文里出现过的数。
  - 程序累加相对值，碰到绝对值就核对，对不上就报。这是 nb-story 数值流水的做法。
  - 它能避开旧版的 `broken-relative`：补写过去时插进一条，后面的核对点会报出“对不上”，而不是整条链断掉。
- **什么才算状态**：会随剧情变、要求精确、错了读者会发现的东西，例如钱、物品、魔力、次数、形态、所在地、生死、伤势。心情、关系的远近一般不进状态，除非作者明确要量化（好感度）。
- **剧情变化与改正要分开**（第二节第 2 点）。

### 3. 文件引用状态（`%{ xingxia.age }%`）

能大大增强表达力，也会带来几个问题：

1. **在什么时刻取值。** 同一份 `星瑕.md`，写第 1 章时和写第 50 章时显示的不一样。模板里没写时刻，渲染时必须给出时刻（章节，或者故事时间加世界线）。界面上要标明“按第 N 章显示”，否则作者看到的数和自己记的对不上，会困惑。
2. **周围的文字不会跟着变。** “年龄：%{ xingxia.age }%，刚上高中”：年龄变了，“刚上高中”还留着。引用适合放在字段和表格里，不适合嵌进叙述句。
3. **有些值本来就不该存。**
   - 年龄是出生日期加故事时间算出来的，存成状态就得每过一年改一次。
   - 于是会想要“计算字段”；再往前一步就是表达式、条件、循环，模板变成一门编程语言。到那一步，Agent 会写错，沙箱、调试、报错都是成本。
   - 建议只允许引用路径，不允许表达式；年龄这类由少数几种内置算法给（例如按历法算年龄）。
4. **改的时候往返不清。**
   - 作者在渲染后的视图里把“17”改成“18”，其实该改的是状态。
   - Agent 读到的是渲染后的文字，改文件时可能把引用写成死值，或者引用一个不存在的路径。
   - 需要三件事：编辑器把引用显示成一个小块，不当普通文字；Agent 读文件时同时拿到原文（带引用）和渲染值；写入时校验引用存在。
5. **引用悬空。** 状态字段改了名、人物删了。写入时和检查时都要报出来。
6. **搜索。** 搜“3,200”搜不到原文，搜 `%{` 又没有意义。索引要按渲染后的文字建，还要记下渲染时用的时刻。

另一种做法是**状态块**：文件里留一整块位置，程序在那里画出面板（第四节样例的“状态”小节）。它没有语法问题，哪块归机器一目了然，只是不能嵌进句子。建议以状态块为主，行内引用为辅，并且只在字段和表格里用。

### 4. 星瑕.md 能写什么

见第四节：过去、将来、作者笔记都能写。关键在于分清时间、确定性与笔记，用小节标题就能做到；只有身份与知情用表。

## 九、要开发者看的

1. 术语表里的分法：设定、状态、计划、作者笔记、待定、手记。尤其是“状态只算要求精确的那部分”，以及“结构关系是设定、态度变化从正文抽、量化的好感度是状态”。
2. “作者只维护正文推不出来的东西”这条原则。
3. 设定变化的分类：只有剧情推进是故事世界里的变化，其余都是作者那边的变化；后者靠文件历史加影响检查，不在世界模型里存版本。
4. 手记加整理后的文件加待确认，三样并存。
5. 状态以状态块为主，行内引用为辅；只允许引用路径，不允许表达式。
6. 面板与精灵的设计，作为本书例子的一部分；样本书（t26）要不要就用这本。

这一轮还没有触及的：剧情计划（承载树与因果树）的具体形态、伏笔账本、写一章前写手拿什么材料。按作者视角重新整理 Task 时一并排进去。
