# 条目主文字的方向与内核怎样存条目（2026-11-24 的讨论）

开发者试用 [t28](../tasks/t28-entry-mdx-editing/README.md) 的按块编辑后说“确实是不好用”，要求直接开 [t38](../tasks/t38-kernel-shared-parser/README.md)。接下来的一轮讨论从“用哪个解析器”走到“主文字要不要分节”，再到内核怎样存条目、架构站不站得住。本文记下定了什么、搁置了什么、讲清了哪些事实。引用的开发者原话加引号；没加引号的是主会话的说明或建议。

## 一、开发者定下的

1. **第一版主文字不分节。**“我觉得现在分节有点太早了，最理想的情况是使用 Component 外貌容器。我们现在似乎绕到一个死胡同，总是想把一个条目的 index 分节……我觉得第一版没必要分节。index 是交给作者自由发挥组装的，作者可以用 mdx 引用其他 Component 的数据搭建自己觉得好看的看板。这里还是需要实际体验才能知道后续该怎么做。”
2. **编辑用一个完整的编辑器。**“编辑起来不顺畅，查看起来也不好看”“编辑还是直接给用户一个完整的编辑器更加好”。
3. **先推编辑器。**听完架构评估后：“没问题，可以先把我们这讨论记一下。然后我们继续先推这个编辑器。”主会话据此建 [t39](../tasks/t39-entry-text-editor/README.md)。
4. **对架构评估里的四条建议答“没问题”**：内核先不加东西、没人用的能力不开入口；界面只露条目的文字、条目的数据、“这是改设定还是剧情里变了”；整篇编辑器与人物设定组做完后，尽快拿一本真实的书跑最小闭环（模型读一章、提议变更、作者确认、再写下一章）；闭环里看三个数（每章要作者确认几条、漏记多少、下一章写手用错多少）。

主会话对“不分节”的理解（开发者没有逐条确认，随“先推编辑器”一起往下做，有异议再改）：

- 内核不改。它存的是块的列表，第一版每个条目的主文字只用一块。
- 整篇一个编辑器，提交是整篇替换；别处也改了时按整篇问一次。
- 主文字不提供“这段在剧情里变了”；随剧情变的内容放设定组的字段。
- 代价：主文字里引用了保密内容时，这个条目的文字整篇不给写手；Agent 改主文字是整篇交回。
- t28 的暂存、提交、多窗口留用；拆、并、加块、删块与它们的冲突处理从界面这一层拿掉。

## 二、搁置到用过之后再定的

这几条讨论过、主会话给了看法，开发者没有定；等整篇编辑器与人物设定组用过之后再议。

| 提议 | 谁提的 | 主会话的看法 |
|---|---|---|
| 解析器只留 marked（2026-11-23 已定），内核也换过去 | 11-23 的决定 | 仍推荐。MDX 的表达力来自执行 JSX，不来自它的解析器；条目文字不执行（[ADR 0038](../../../../docs/adr/0038-world-engine-entry-text-is-whitelisted-mdx.md) 决策 2） |
| 去掉 `{}`，取值与条件也用标签（“要不我们干脆不支持 `{}` 这种写法，取变量也用 xml 标签？”） | 开发者 | 赞成。t38 的难点一半来自在 Markdown 里找表达式的结尾；给 Agent 的带值写法现在是另一套语法，换成标签后源文与带值写法是同一套（源文 `<V of="panel.魔力" />`，给 Agent 看 `<V of="panel.魔力">1200</V>`）。代价：取值变啰嗦；条件要写成标签；渲染、白名单、带值回写与用例、样本、Agent 工具说明要返工，另写 ADR 取代 0038 的决策 1 与 3；编辑器写出的新写法旧内核不认，只能内核先换 |
| `<html>` 里写 HTML、`<jsx>` 里写 JSX，都在沙箱里跑，可以往沙箱注入接口（持久化保存变量、导入其他组件） | 开发者 | 同意。章节方言已有沙箱里渲染的 `<html>` 块（`sandbox="allow-scripts"`，与宿主只经 postMessage，数据接口预留、默认拒绝）。建议“持久化的变量”存成条目的字段，沙箱的写入限定在它所属的条目；沙箱块对模型是界面不是文字 |
| 支持 MDX 那样的 `<StatBar>` 写法，由插件提供标签 | 开发者 | 同意。靠一张标签登记表，每个标签登记三样：给模型看的文字、属性声明（哪个是字段地址，依赖与保密靠它）、界面组件；没装对应插件时原样保留。属性建议一律用带引号的字符串 |
| 分块用 `##` 或 `---` 这种语法来分 | 开发者 | 当时赞成（比“连续文档加淡分界”好）；随后开发者自己叫停分节，这条不做 |
| 被剧情改过的块：删改成确认后连剧情变化一起删；加保留编号的移动操作 | 主会话 | 不分节以后第一版用不上 |
| 人物设定组允许实例字段，并给加字段的入口 | 主会话（开发者：“这个功能可能还是挺常用的吧”） | 做人物设定组时一起做 |
| 记账（模型读一章、提议变更）紧跟在人物设定组之后 | 主会话 | 开发者 11-23 说记账先不考虑；这次对“不要拖太久”答“没问题” |

开发者给的以后的方向（输入，不在本 Work 现在的范围里）：NeuroBook 以后可以做 roleplay 玩法，“用户说一句，LLM 就跑一章出来，给用户看到的应该是精美的界面。例如一个显示当前任务面板的状态栏。这个状态栏可以是这个角色卡作者提供的页面”；生成式 UI（JSX 配 Tailwind，LLM 还能生成让用户填的表单）。主会话的回答：角色卡作者的页面与 LLM 生成的界面是不可信内容，哪种写法都得进沙箱，安全性由沙箱决定；让用户填表单可以只让 LLM 给字段的 schema、由 nb-form 画。

## 三、内核怎样存一个条目

依据 [`canon/model.md`](../../../../docs/specs/canon/model.md)、[`canon/components.md`](../../../../docs/specs/canon/components.md)、[`canon/worldlines.md`](../../../../docs/specs/canon/worldlines.md) 与 [ADR 0043](../../../../docs/adr/0043-world-engine-placement-and-telling-orders.md)，都是 `implemented`。

**条目自己只存初值，不带时间轴。**随剧情的变化存在条目外面的剧情变更里；读“第 N 章的某个条目”时，内核拿初值加上到那一点为止的变更现算。

| 部分 | 内容 | 会不会随剧情变 |
|---|---|---|
| 身份 | 编号、种类 | 不会 |
| 在条目树里的位置 | 父条目、分组、同级顺序 | 不会 |
| 出场位置 | 从哪一章起才有；不写就是从头就有 | 不会 |
| 马甲 | 可选，指向本体条目 | 不会 |
| 名字、别名、一句话描述 | 文字 | 会 |
| 主文字 | 带编号的块的列表 | 会（按块整段替换） |
| 设定组（Component） | 每个一个命名空间，下面是字段 | 会 |

**设定组**分类型与实例。类型由插件声明（名字、命名空间、版本、字段声明、可选的给 Agent 的文字视图与记账说明）；实例是某个条目上的一份（属于哪个类型、是否启用、各字段的初值）。字段的种类：数、文字、选项、真假、列表、图片、引用；数与文字分精确档（程序按变更算）与语义档（记“发生了什么”，小模型归纳成现在的样子）。内置的只有人物（`character`，6 个文字字段，是为样本凑的最小集）与面板（`panel`，没有固定字段，每个条目自己声明）；剧情插件另有五个。

**实例字段**：只有声明了 `instanceFields` 的类型（现在只有面板）能在条目上加字段、改显示名、删字段；删掉时值与补丁留着，再声明同一个编号就恢复。缺口：人物加不了字段；改类型本身要升版本，而第一版没有升级、版本对不上的那份数据只读；作者不能自己定义类型；在 canon 插件的非测试代码里没搜到作者界面或 Agent 工具调用加字段。

**两个轴。**章序是一条直线（书的顺序，来自活页夹）；世界线是一棵树（主线总在，每次分叉分出一条新线）。一条剧情变更有两个坐标：在哪条线上、安放在哪一章的哪个位置。每一章（每一段）讲的是哪条线由活页夹给。状态按安放的先后算（前史、各章按章序、章内排序键），不按故事时间；故事时间只是变更上可选的说法，用来算范围与查矛盾，内核不支持按故事日期读状态。内核里的“剧情线”是另一个意思（故事线的分类）。

**回溯**是一条性质为分叉的剧情变更，记在父线上。切口是父线上的一条剧情变更（回到的不是某一章）；触发处是回溯发生的那件事；子线继承切口及之前的全部记录；切口到触发处之间“被抹掉的那段”照常留在父线上；声明了“回溯时保留”的字段与列表（例如知情、回溯次数）在子线开始时取父线在触发处的值。两条线不能合回一条。界面能选“在看的线”，没搜到新建分叉的入口。

例子（初值：发色红，魔力 1200，回溯次数 3；回溯次数与知情声明了保留，魔力没有）：

```
章序      50 ──── 52 ──── 54 ──── 55 ──── 56 ──────── 57
主线     ●醒来   ●魔力-300  ●得知真相  ●染白    ●发动回溯
          │切口                                │触发处
新线      └───（52 到 55 在这条线上没发生）──────●─────── ●魔力-100
```

| 读哪里 | 发色 | 魔力 | 回溯次数 | 知道哥哥是叛徒 |
|---|---|---|---|---|
| 主线，第 55 章末尾 | 白 | 900 | 3 | 是 |
| 主线，第 56 章末尾 | 白 | 900 | 2 | 是 |
| 新线，第 56 章末尾 | 红 | 1200 | 2 | 是 |
| 新线，第 57 章末尾 | 红 | 1100 | 2 | 是 |

**设定会不会跟着回溯。**不会，前提是那次改动记成“改设定”而不是“剧情变化”。初值是各条线共用的；设定不带“写于第几章”的标记。作者在第 55 章把红发改成白发：意思是“一直就是白发”的，改的是初值，所有章、所有线都是白发；意思是“第 55 章她染白了”的，是第 55 章的一条剧情变更，新线上回到红发。作者在看到的样子上直接改，默认算改设定。新建的条目缺省“一开始就在”；记在前史的事早于任何切口，子线照样继承。主文字的块不能“带过去”，能保留的只有声明过的字段与列表，所以会跟着回溯者保留的能力要记成字段。主文字里引用的值按读取的线与位置取，同一段文字在两条线上显示不同的数。

## 四、怎么绕进“分节”的

块的来历：[内核提案](../../../../docs/proposals/world-engine-kernel.md) 2026-11-02 定“主 MDX 按块存，每块有稳定 id”，用处是随剧情变化的文字不做 diff 与三方合并、按块整段替换；Agent 交回改过的一块；一块出错不连累别的块；就地改时知道每块文字来自哪条记录；11-10 的 t35 又加了简报按块扣下。“按块整段替换”是主会话提的、开发者未反对（本 Work 决策记录 11-02）；同一处写着“作者在界面里怎么编辑主 MDX，先不定”。块是为剧情变化与 Agent 设计的，设计时没有考虑作者怎么编辑。

四次撞在同一处：t28 计划第 1 稿（整篇编辑）的设计审查指出整篇文字对不回块的编号；第 3、4 稿改成按块编辑后，第二轮设计审查指出被剧情碰过的块的删、并、插入；三轮实现审查的问题集中在拆与并；试用后讨论按标题分节，又回到认回编号与删并挪。每次都是“编辑器想把主文字当一篇文字、内核要每块保住编号”，主会话每次都在保住编号里找办法，没有回头问第一版要不要随剧情变的块。

为什么不分节站得住：随剧情变的内容放设定组的字段更合适（有类型、有来历、能核对）；主文字引用字段时值按读取位置取，显示出来本来就随剧情变；星瑕样本的 18 处剧情补丁全落在字段上（人物 10、面板 8），没有一处改主文字的块。样本只有 3 章，只能说明字段这条路够用。

## 五、对架构的评估

开发者问“这个架构怎么样？经不经得起考验，好不好用？作者用起来会不会麻烦？agent 用起来会不会失忆？”主会话的回答：

- **站得住的**：状态是从初值与剧情变更算出来的，结果确定、能查来历、能撤销；安放与讲述分开；世界线用同一套规则算。
- **没被检验的**：只在 3 章的手写样本上跑过；没有一本真实的书走完过“写一章、记账、写下一章”；评测（t26）没有结果。
- **超前**：主文字按块随剧情变在样本里一次没用上；计划、时间约束、决策、语义档都实现了，但没有被真实写作用过，哪些多余现在判断不了。
- **不好用的原因**：内核的概念直接露到了界面上；记账（最大的未知数）还没做，在 canon 与剧情两个插件里没搜到实现；人物只有 6 个凑数的字段、不能加。
- **Agent 的记忆**：记成字段的事实从日志现算，不靠上下文；会忘的是没被记下来的细节（要靠摘要与检索，都还没做）、没被选进简报的条目、语义档归纳丢的东西。主会话记录里的 nb-story 评测是 100 章以内用结构化的图回答不比全读强，结构化状态的好处要到长篇才明显。Agent 工具规划了 15 个、做了 4 个。

## 六、实测

- 星瑕样本 155 段主文字、6778 字（负载 0.8）：MDX 官方解析器（micromark 加 mdxjs）解析一遍 21.8 毫秒，marked 1.55 毫秒，约 14 倍；绝对值都小，不是决定因素。脚本是一次性的，没有入库。
- 样本里 110 处表达式，11 处带比较或条件（同一句 `{panel.魔力 >= 1000 ? … : …}` 重复出现），22 处跨条目引用；44 段带标题，11 段带列表。
- t28 的原型对照旧解析器跑 3 万个随机块：约 94% 完全一致，约 3% 旧的拒收、新的接受，约 0.3% 位置对不上（[独立设计](../tasks/t28-entry-mdx-editing/evidences/independent-design.txt)）。
