作者：Sonnet（独立设计，没读 t02 的 plan.md）
依据：读过 docs/proposals/neurobot.md 第三节与第四节第 2、3、8、10 小节、ADR 0025/0029/0030/0033、docs/specs/runtime/server-host.md，

====================================================================
0. 结论（先看这一节）
====================================================================

新建两个包，都不发 npm（private），都不动 nb-runtime 与 nb-harness：

  A. packages/nb-host    两端宿主的通用部分（服务端、浏览器、两端共用的协议），一个包，按子路径分层
  B. packages/nb-models  模型服务的通用部分（配置形状、纯规则、远程合同的定义对象、核心），依赖 nb-runtime 与 nb-harness

要点：
  1. 凡是“带应用名的字面量”（环境变量前缀、套接字名前缀、插件 id、服务键 id、远程合同 id、存储键、界面文案里的应用名、
     内核平台档案）一律由应用以 profile 或参数传入，包里不定义。内核硬性规定服务键与远程合同 id 要以“插件 id/”开头，
     所以 nb-models 只导出合同的定义对象（methods、events、version），应用自己用 `nbook.models/…` 的 id 调 defineRemoteService。
  2. 服务端不是“整份 start.ts 搬过去再参数化”，而是包里一个小编排函数 startServer，收四个钩子：assemble（能力与插件）、
     router（项目回调，可选）、attach（排空前后的额外步骤，可选）、claimExtra（认领应答的扩展字段，可选）。
     项目管理器、第三方插件清单、开发任务、引导路由全部留在 NeuroBook 的 start.ts，由它组装在包之上。
  3. HTTP 抽整个“准入 + 分发 + 静态 + http.routes 合同 + 插件工厂”，不是只抽那 20 行来源核对。理由是来源核对必须在分发器里
     “先于一切路由”执行，只抽判定函数，等于把“每条路由都被核对”这个性质交给每个应用的分发器各自保证。Hono 不进包。
  4. “来源核对放不放得过”不交给应用：包的 startServer 只给应用一个 ctx.plugins.http(...) 造 HTTP 插件，allowOrigin 由包按
     allowedOrigins 加实际监听端口算出来，同一个函数实例喂给 HTTP 与 RPC 升级，应用拿不到、也换不掉。
  5. 设置服务的依赖换成一个窄接口 ModelsConfigPort（五项配置各一个小槽位：读当前值、读用户层、带期望值写回、变化通知），
     NeuroBook 写一个约 60 行的适配器。包同时导出针对这个接口的契约测试，NeuroBook 与 NeuroBot 各用自己的真实适配器跑一遍。
  6. 安全不变量的测试分两层：包里用“acme 档案”的最小服务端，经真实子进程、真实回环套接字与真实 WebSocket 握手测每一条；
     包导出一个一致性套件，NeuroBook 与 NeuroBot 各自对着自己的真实产品入口再跑一遍，防“包对、应用接线漏了”。
  7. 有两个不在简报清单里、但包离不开的附带依赖，需要开发者拍板：诊断的 JSONL 日志出口（plugins/diagnostics/backend，约 600 行，
     含 proper-lockfile）和文件锁 backend/locked-replace（241 行，状态根认领用它的 holdLock）。建议一并进 nb-host，
     否则 NeuroBot 只能抄一份。理由与替代见第 2.9 节与第 6 节。

1. 六个视角的质疑
====================================================================

1.1 反对与精简：能不能更少
----------------------------------------------------------------
问：开发者已定要抽，那么最小切面在哪？依据的判据是“NeuroBot 不抽就得重写、且重写后会出现第二份有微妙时序的代码”。

  逐块过一遍：
  - 回环与来源判定（config.ts 的 LOOPBACK_HOSTS、loopbackOrigins、parseOrigins，dispatch.ts 的 LOOPBACK_HOSTS 与 SAFE_METHODS）：
    必须抽。现状 NeuroBook 里回环名单就有两份（config.ts 一份写 “::1”，dispatch.ts 一份写 “[::1]”），说明这块天然容易漂。
    抽包时合成一份，写在 protocol/loopback.ts。
  - 状态根认领（instance.ts 301 行）：必须抽。套接字探测、3 秒无应答不接管、崩溃留下的文件清理、只删自己建的文件，
    每一处都有真实进程测试在守，复制过去没有意义。
  - RPC 端口监听（rpc/listener.ts 141 行）与端口顺延（ports.ts 68 行）：必须抽。NeuroBook 的开发监督进程也用顺延的函数。
  - 宿主适配器（host.ts 162 行：信号、标准输入 stop、未处理异常汇合为一次停止）：必须抽。项目子进程（project/start.ts）
    已经在用它（location: "project"），所以它早就是被两个入口共用的东西。
  - start.ts（462 行）：只抽通用的一半（约 300 行：诊断存储、准入、远程节点与路由、RPC 监听与顺延、双排空、退出码、
    认领的 publish/stopping/release、致命通道）。这是全仓最容易写错时序的代码，注释里记着几处只有真实故障才暴露的顺序约束
    （例如启动失败要通知两次：紧急报告时先拒绝等待中的请求，内核关闭完成后再补报）。让 NeuroBot 重抄这段，等于每个应用重新踩一遍。
  - process.ts（189 行）：抽成通用的运行器，NeuroBook 特有的部分（第三方插件准备、OMP 清理）以钩子传入。
  - HTTP 的 admission、dispatch、static、插件工厂（约 630 行）：抽。判据见 2.4。
  - 浏览器：只抽 browser-host.ts（93）、connection.ts（118）、remote-session.ts（189）、client-identity.ts（46）。
    window.ts（538 行）不抽：它混着工作台、第三方插件装载、抢救未保存正文、项目标题、消息目录，全是 NeuroBook 的事。
    代价是 NeuroBot 的窗口要自己写约 80 行胶水（建节点、建会话、把状态映射成界面状态）。这是有意接受的重复，理由是
    抽象要看到第二个真实写法才抽得准，只凭 window.ts 一个使用者设计出来的钩子形状大概率不合 NeuroBot；
    触发条件见第 6 节。
  - 不抽：项目管理器与项目子进程（server/projects/）、开发监督进程（server/dev/，1666 行含测试，尚未有第二个使用者）、
    引导路由（browser-bootstrap.ts，内容是 NeuroBook 的插件集合）、插件文件端点、user-directories。

  问：有没有现成的库或仓库里的模块可以替代？
  - 实例认领：思路来自 VS Code 的 claimInstance，没有现成包；本仓库没有别的模块做这件事。
  - HTTP 分发：Hono 只管路由。准入、排空、事件流登记、响应体发送完毕才归还在途计数，这些是自写的；Hono 替代不了，
    反而要把 Hono 作为包的依赖。包里不用 Hono：现在 plugins/http/backend/plugin.ts 只在宿主自有路由（health 加引导）上用了一个
    Hono 实例，换成一个 Map<路径, 处理器> 的小路由即可（见 2.4）。
  - WebSocket：Bun 自带。端口探测：70 行，不值得为它引 get-port 这类库。
  - 仓库里别的“监听回环”的服务（nb-story 的 `nbstory serve`、dev-panel 的面板）：我在 packages/ 下的 ts 与 vue 里搜
    “421”“misdirected”“origin-not-allowed”“rebind”，只有 neuro-book 的命中（范围限定在这个搜索词，没有逐文件读 nb-story 与 dev-panel）。
    如果它们确实没有 Host 与 Origin 核对，这是现成的、本任务之外的缺口，包做好后它们可以直接用 server/http，但这不属于 t02，
    只在第 6 节提一笔，不扩范围。

1.2 成本：开发、发布、构建、类型检查
----------------------------------------------------------------
  - 新包两个，都是“以源码为入口”的 workspace 包（exports 指向 .ts），没有构建步骤，和 nb-runtime 一样。
    NeuroBook 的 `bun build`（build:server）与 Vite 直接把它们当源码打进 bundle，pack-app.ts 的 bundleProblems 只拦外部模块，
    不受影响（推断：未跑构建）。应用的 npm 产物仍然没有 dependencies（ADR 0033 决定 1）。
  - 不发 npm：NeuroBook 发的是 bundle，NeuroBot 第一版“只从仓库运行，不发 npm”（提案第五节）。发布意味着 ADR 0029 的“只承诺 Bun”
    之外再加两个 semver 面、release:check 的清单检查（要求每个源码导入的依赖都写进包自己的 dependencies）、
    根 README 的包表。没有使用者需要它们，等需要时 private 改成发布是机械的。
  - 类型检查：nb-host 仿 nb-runtime 两份配置：tsconfig.json（Bun 类型、不带 DOM，查 src/server 与 src/protocol）、
    tsconfig.browser.json（DOM、不带 Bun 与 Node 类型，查 src/browser 与 src/protocol）。这样浏览器入口误用 Bun 或 Node 全局
    会在类型检查时就失败，不靠 NeuroBook 的 vue-tsc 碰巧发现。nb-models 同样两份：./config 与 ./contract 查浏览器配置，
    ./core 查 Bun 配置。
  - 登记处（读 scripts/ci、.github 后确认没有按包名硬编码的清单）：根 package.json 的 workspaces；
    根 AGENTS.md 仓库结构图；packages/AGENTS.md 的成员列表；docs/modules/monorepo-boundaries.md 的当前布局表；
    NeuroBook 的 package.json 加两条 workspace 依赖；`bun install`。不需要动 scripts/release/packages.ts（不发布）。
  - 工作量估计（行数按现有非测试代码，推断）：nb-host 约 3,200 行（服务端通用 1,300、HTTP 630、诊断出口 600、文件锁 240、
    浏览器 450、协议 130），nb-models 约 700 行（core 555 加合同与规则 220 减去留在应用的部分）。测试随代码走，约 1,800 行。
    绝大多数是搬迁加去耦，真正新写的是：profile、startServer 的钩子、ModelsConfigPort 与适配器、一致性套件、两个扫描测试。

1.3 使用者体验：NeuroBook 与 NeuroBot 的宿主作者装配起来顺不顺
----------------------------------------------------------------
  判据：NeuroBot 的 gateway 入口应该是“一个 profile、一个 assemble、几行入口”，看不到端口顺延、排空顺序、退出码、认领细节。
  按本设计，NeuroBot 的服务端入口大致是（示意，不是最终代码）：

    // packages/neuro-bot/src/gateway/main.ts
    import "@notnotype/nb-host/server/startup-env";      // 第一条导入，零依赖，先于任何求值 OMP 的模块
    import "./omp-process";                              // 第二条，应用自己的 13 行（nb-host 不依赖 nb-harness）
    const {runServerProcess} = await import("@notnotype/nb-host/server");
    const {NEUROBOT_HOST, assemble} = await import("./host");
    await runServerProcess(NEUROBOT_HOST, {version: PRODUCT_VERSION, assemble, cleanup: () => ompProcess.cleanup()});

  profile 里是 displayName、envPrefix、socketPrefix、平台档案、缺省端口。assemble 返回 NeuroBot 的能力与插件。
  不需要项目管理器：router 钩子不给就是内核缺省（bindProject 缺省时拒绝绑定，projectAccess 缺省时拒绝，已在 nb-runtime
  remote/router.ts 确认两者都是可选）。
  浏览器一侧：`new BrowserRuntimeHost({platform})`、`createConnection(location.origin)`、`createRemoteSession({...protocolVersion})`。
  有意不顺的一点：NeuroBot 的窗口骨架还要自己写（见 1.1），换来的是不为单个使用者设计钩子。
  要写进 nb-host 的 AGENTS.md 的“怎样接一个新应用”清单：profile、第一条导入、assemble、引导协议版本号、一致性套件，共五步。

1.4 迁移与兼容：NeuroBook 现有行为、e2e、开发监督进程、npm 构建产物
----------------------------------------------------------------
  “行为不变”的可验证形式是下面这张可观察字面量表，抽包时一个都不许变，迁移后用现有测试对它们逐项核对：
    - 环境变量：NBOOK_STATE_ROOT、NBOOK_HOST、NBOOK_PORT、NBOOK_RPC_PORT、NBOOK_ALLOWED_ORIGINS、NBOOK_WEB_ROOT（由 envPrefix 推出），
      NBOOK_PROJECT_GRACE_MS、NBOOK_PROJECT_START_MS、NBOOK_PROJECT_STOP_MS（留在 NeuroBook，解析时复用包导出的 parseDuration）；
      命令行 --stop-stdin。
    - 标准输出两行：`Listening on <地址>`、`RPC listening on <ws 地址>`（backend-process.ts、scripts/smoke-server.ts、
      e2e/fixtures.ts 都在用正则解析它们；scripts/check-dist.ts 还要求服务端 bundle 里含 "Listening on" 与 "nbook.http" 两个字符串）。
    - 认领：文件名 server.sock、server.claim.lock，长路径回退 `$XDG_RUNTIME_DIR/nbook-<哈希>.sock`，Windows `\\.\pipe\nbook-<哈希>`
      （socketPrefix 传 "nbook"），hello 请求与应答的字段（schema: 1、pid、version、kind、status、url、rpcUrl、plugins）。
    - 诊断事件名与致命通道：`runtime.state-root.busy / unwritable / claim-failed`、`runtime.config.invalid`、`runtime.startup.failed`、
      `runtime.startup.causes`、`runtime.stop.incomplete`、`runtime.stop.emergency`、`runtime.diagnostics.flushFailed`、
      `server.ports.shifted`、`rpc.upgrade.failed`、`http.listening`、`http.request.failed`、`http.request.aborted`、`process.uncaught-exception`、
      `process.unhandled-rejection`、`instance.claim.*`、`instance.socket.*`；致命通道仍是同步写一行 `{level:"fatal", event, …}` JSON 到标准错误。
    - HTTP 响应码与错误体：421 `misdirected-host`、403 `origin-not-allowed`、503 `startup-failed` 与 `stopping`、503 `plugin-unavailable`、
      404 `not-found`、405 `method-not-allowed`、500 `internal-error`，错误体仍是 `{error:{code,message}}`；/api/runtime/health；
      RPC 端口的 404、426、503、403、400、500。
    - 退出码：0、1、75（租约失效，由 NeuroBook 的存储插件触发，不在包里）、76（看门狗，不在包里）。
    - 日志位置：`<状态根>/logs/server-current.jsonl`。
    - 服务键与远程合同 id：`nbook/state-root`、`nbook/startup-env`、`nbook/clock`（SDK 的 index.ts 还把 clockKey 与 stateRootKey 以
      hostClockKey、hostStateRootKey 导出给第三方插件，已确认），`nbook.models/models`、`nbook.models/settings`，设置键
      `nbook.models/providers` 与 `nbook.models/roles`（用户磁盘上的数据）。这些 id 一个都不进包，包里不 defineServiceKey。
    - 客户端身份的存储键 `nbook.client-identity`（Spec browser-host.md 写死了它）。
  开发监督进程（server/dev/run.ts）只改导入：`loopbackOrigins`、`freeGroupOffset`、`PORT_SHIFT_ATTEMPTS` 改从 nb-host 取；
  其余（Vite、监视、重启）留在应用。cli/*.ts 里取 `queryInstance`、`claimStateRoot`、`readServerConfig`、`runServerProcess`、`claimReport`
  的地方改成从 nb-host 取（套上 NeuroBook 的 profile）。project/start.ts 取 `startServerHost`、`ProcessEvents`、`FatalKind`，
  包里的宿主适配器必须保留 `location: "server" | "project"` 与 `signals` 参数（项目子进程只认 SIGTERM，已确认）。
  同时注意 startup-env.ts 与 omp-process.ts 的“第一条、第二条导入”规则：startup-env 搬进包后仍是零依赖模块，
  打包后的顺序由现有的 startup-env.test.ts（真实子进程探针）守住；omp-process 不搬（它依赖 nb-harness/process-guard），
  所以 runServerProcess 收一个 cleanup 钩子，替代现在的 exitAfterOmpCleanup。
  e2e：Playwright 起的是应用自己的探针服务端与产品入口，不直接引用被搬走的路径（e2e/fixtures.ts 只解析上面两行标准输出），
  预期不需要改 e2e 文件，但迁移每一片之后仍要跑覆盖服务端宿主、认领、dev 监督的那几组（推断）。

1.5 可观测与排障
----------------------------------------------------------------
  - 事件名与错误码见上表，原样保留。新增的只有一类：包的 profile 校验失败（envPrefix 不合法等）按 `runtime.config.invalid` 报。
  - 面向人的文案里的应用名（`NeuroBook 正在关闭。`、`NeuroBook 暂不接受 RPC 连接。`、`NeuroBook 启动失败。`、环境变量名）
    由 profile.displayName 与 envPrefix 拼出，NeuroBook 的字符串与现在逐字相同。
  - 两个应用同机运行时的排障：认领的 hello 应答加一个可选字段 `app`（取 socketPrefix），读者容忍缺失。
    这样 NeuroBook 命令行指到 NeuroBot 的数据目录时，报“已被 nbot 的实例占用”而不是“应答无法识别”。成本很小，但属于新增，
    列入第 6 节让开发者决定要不要。两个应用的缺省数据目录与缺省端口本来就不同，不加也不会互相认领。
  - 缺省端口建议：NeuroBot 的缺省 HTTP 与 RPC 端口个位数与 NeuroBook（4217、4218）不同（例如 4227、4228）。顺延步长是 100、
    至多 10 组，个位数不同就永远不会顺延到对方的端口上。这是 NeuroBot 自己 Spec 的事，只在这里提醒。

1.6 长期维护与技术债：同一类代码会不会出现两份；包会不会越长越大
----------------------------------------------------------------
  - 两份的风险点，逐个给对策：
    a) 回环名单在 NeuroBook 里已有两份（见 1.1），合成一份放 protocol/loopback.ts，配置解析与分发器都从那里取。
    b) NeuroBot 的窗口骨架（1.1）：接受重复，写明触发条件。
    c) 设置页的界面（models/web/components 下约 22 处导入对应的组件）：简报定“留在应用”。NeuroBot 要复制的话就是两份。
       NeuroBot 不依赖 neuro-book，不能直接用这批组件。预案：第一版做简版设置页，等界面稳定后再把这批组件抽成 nb-models 的
       ./vue 子路径（依赖 nb-ui）。两种都不属于 t02，列入第 6 节 D4。
    d) 开发监督进程（server/dev/ 约 800 行非测试）：NeuroBot 开发模式迟早要一份。本任务不抽，但把端口、回环这些共用件放进包，
       使以后抽 ./dev 只需搬监督进程本体。
    e) 防“应用里又手写一份”的守护：NeuroBook 的 architecture.test.ts 加一条规则，Bun.serve、node:net 的 createServer、
       `new WebSocket(` 只许出现在 server/dev/（试探端口）与测试里；NeuroBot 同样加。机检，不靠人记。
  - 包不会越长越大的约束不用行数，用“词汇”：
    * nb-host 的非测试源码（含注释）不出现应用名（正则 /nbook|neurobook|neurobot|nbot/iu，照抄 nb-runtime 的 app-neutral.test.ts，
      把 nbot 加进去），不导入 `nbook/` 别名，不导入 neuro-book 包名；
    * 依赖白名单：nb-host 只许 @notnotype/nb-runtime、typebox、proper-lockfile 与 node:*、bun；protocol 与 browser 子树不许 node:*、bun；
    * nb-models 只许 nb-runtime、nb-harness、typebox；config 与 contract 子路径不许值导入 nb-harness（只许 import type）与 node:*。
    进包的准入规则：不含应用词汇、不含“项目”“第三方插件安装”“工作台”这类 NeuroBook 概念、有第二个使用者（或第二个使用者已在计划里）。
    不满足的留在应用。
  - nb-harness 的边界：nb-models 依赖 nb-harness，反过来不行；另一个计划正在 nb-harness 加扫描测试禁止它依赖 nb-runtime，
    本设计没有任何要求让 nb-harness 依赖 nb-runtime 或 nb-models，所以不冲突。nb-host 不依赖 nb-harness
    （omp-process 留在应用），因此 nb-host 的使用者不会被拖进 OMP 原生模块（nb-harness 的依赖里有每平台约 122 MB 的原生插件，
    见 pack-app.ts 的注释）。这也是模型服务不能和宿主放同一个包的原因。

2.4 HTTP 抽到哪里为止（判据与结论）
----------------------------------------------------------------
  判据：被 NeuroBot 重写就会出现第二份、而且这份的安全性质依赖“位置”的最大连通块；且其中不含应用词汇。
  - 只抽 `rejected()` 那 20 行：不够。Spec 要求来源核对对所有路由（宿主接口、页面资源、插件路由）都先于准入执行，
    这是分发器里“调用顺序”的性质，不是判定函数的性质。函数在包里、分发器在两个应用里各一份，等于“核对是否先于一切路由”
    要在每个应用里各证明一次。
  - 抽到插件工厂：需要的东西是 admission（153，RPC 升级也用它做就绪门，所以 startServer 本来就需要它）、dispatch（230）、
    static（109）、RouteTable 与 http.routes 合同（约 45）、createHttpPlugin（94）。全部不含应用词汇，除了：插件 id `nbook.http`
    （改为参数）、三处 “NeuroBook …” 文案（改为 displayName）、Hono 的使用。
  - Hono 不进包：plugin.ts 里 Hono 只用来搭 health 和宿主自有路由，换成 Map<路径, HostRoute>。`rethrowRouteError` 只用 Error 与
    Response 的形状，本来就不 import hono，原样搬到 server/http。应用的插件路由仍然可以用 Hono（http.routes 的处理器只要有 fetch 方法）。
  - 结构性保证（这是本设计在安全上最关键的一处）：HTTP 插件只能经 startServer 给应用的 ctx.plugins.http(...) 造。
    它的 allowOrigin 由 startServer 按 config.allowedOrigins 加“实际监听后的 HTTP 端口在三个回环别名上的来源”算出一次，
    同一个函数实例喂给 HTTP 分发器与 RPC 升级；admission 同样。包不导出 createHttpPlugin 的“可自带 allowOrigin”版本。
    startServer 在启动前核对应用交来的 plugins 里确实包含 ctx 造出的那个 HTTP 插件对象与诊断插件对象（按对象身份），
    缺了抛 ServerAssemblyError，致命诊断照常。应用因此既换不掉判定，也漏不掉插件。
  - 现状里 allowOrigin 的依赖：现在 start.ts 的 allowOrigin 读 `url`（HTTP 端口监听成功后才有值），RPC 升级先过准入门（等就绪）
    再调它，所以顺序不能反。这一点原样保留，包里的 startServer 保持同样的先后，并在注释里写明（现有 listener.ts 头注释就是这个理由）。
  - `plugins/http/shared/contracts.ts`（HTTP_ROUTES_POINT、HttpRouteEnv、HttpRouteHandler、rethrowRouteError）搬到
    nb-host/server/http。NeuroBook 里有 8 个非测试文件按旧路径引用它（files、projects、agent 的路由文件与插件文件），改为从
    `@notnotype/nb-host/server/http` 导入；不保留旧路径转出。NeuroBook 的 `plugins/http/plugin.ts`（描述符 nbook.http）留着，
    `plugins/http/backend/` 整个目录删除。
  - 形状：

    // @notnotype/nb-host/server/http
    export interface HostRoute {readonly method: "GET"; readonly path: string; handle(request: Request): Response | Promise<Response>}
    export interface HttpPluginSpec {
        /** 插件 id，例如应用的 "nbook.http"。 */
        readonly id: string;
        /** 挂在 /api/runtime/ 下的宿主自有接口；/health 由包提供。 */

3.1 安全不变量（NeuroBook 现有规则，提案第四节第 10 小节要求 NeuroBot 同样满足并有验收）
----------------------------------------------------------------
  I1 只许监听回环。
     - 配置：`HOST` 取 0.0.0.0、::、公网名、空白以外的任何非回环值，启动失败（ServerConfigError "non-loopback-host"，致命诊断
       runtime.config.invalid，退出码 1）；ALLOWED_ORIGINS 里非回环主机、非 http、带路径的项失败（"invalid-origin"）。
     - 套接字层：HTTP 与 RPC 两个端口都只绑回环。测试用 os.networkInterfaces() 找一个非回环的本机地址，向它的 HTTP 端口与 RPC 端口建
       TCP 连接，必须被拒绝；机器上没有非回环地址时跳过并在输出里写明跳过原因（不静默通过）。这条比“配置被拒绝”更接近真实的安全性质。
  I2 HTTP 的 Host 必须是回环名，否则 421 `misdirected-host`（防 DNS 重绑定）。用裸 node:net 套接字手写请求（fetch 不保证能随意设 Host）：
     evil.example、127.0.0.1.evil.example、localhost.evil.example（后缀欺骗）、空 Host、HTTP/1.0 不带 Host，都是 421；
     127.0.0.1、localhost、[::1]（带端口、大小写混用）放行。对每一类路由都做：/api/runtime/health、宿主自有路由、一个插件路由、页面资源、
     不存在的路径、`/%61pi/x`（编码绕过的 /api 前缀）。另一个性质：应用尚未就绪时坏 Host 也立刻得到 421，不会挂着等就绪
     （核对先于准入）。
  I3 HTTP 写请求的 Origin：GET、HEAD 以外带了不允许的 Origin（含字面量 `null`）是 403 `origin-not-allowed`；
     允许集合 = 本进程 HTTP 端口在三个回环别名上的来源（端口取实际监听的端口，包括端口 0 与顺延之后）加 ALLOWED_ORIGINS，比较前按 URL 规范化。
     放行：允许的来源、不带 Origin 的写请求、任何来源的读请求。拒绝：同主机不同端口、同端口不同主机、http 与 https 不同。
  I4 RPC 升级的 Origin：带不允许的 Origin 的升级请求得到 403 且不升级；允许的来源升级成功并真的完成 nb-runtime 的 hello 握手
     （用真实 WebSocket 与真实的远程节点，不手写帧）；不带 Origin 的放行（已知限制，Spec 已写）；非 GET 或非升级请求 426；路径不是 / 404；
     就绪前升级请求等待，启动失败 503 `startup-failed`，停止中 503 `stopping`。次序：先过门、再核对 Origin（端口 0 时允许集合要等 HTTP 监听后才知道）。
  I5 HTTP 与 RPC 用同一个判定：测试对同一张来源表（含 `null`、大小写、尾斜杠、别名主机、其它端口）分别走 HTTP 写请求与 RPC 升级，
     两边放行与拒绝的结果必须逐项相同。结构上也是同一个函数实例（2.4），测试从行为上再证一次。
  I6 状态根认领：同一状态根只一个实例。真实子进程：先到者认领成功；后到者以 1 退出，致命诊断 runtime.state-root.busy 带对方 pid 与地址，
     不动状态根；SIGSTOP 暂停第一个实例后，第二个报 busy（3 秒内无应答不接管）；SIGKILL 第一个留下套接字文件后，第三个能认领；
     八个进程同时认领恰好一个成功；套接字文件权限 0600；长路径回退到运行时目录；hello 应答按 schema 校验，超过 1 MB 或 3 秒不发完请求的连接被断开。
  I7 停止与排空：信号、标准输入 stop、标准输入关闭、未处理异常汇合为一次停止；先封闭接纳再排空；在途请求完成后才关闭插件；
     排空超过 20 秒记为未完成、退出码 1；启动失败时等待中的请求得到 503 `startup-failed`；退出码表不变。

5. 考虑过又放弃的备选（各一句理由）
====================================================================
  1. 放进 nb-runtime 的新子路径：违反 ADR 0030 决策 1（只依赖 TypeBox、前后端共用、不碰 Bun 与 Node），且已发 npm，会把宿主 API 变成 semver 承诺。
  2. 放进 nb-harness 的新子路径：模型服务要 nb-runtime，而 nb-harness 不能依赖它（nb-story 依赖 nb-harness，另一个计划在加扫描测试）。
  3. 宿主与模型放同一个包：模型包带 OMP 原生依赖（每平台约 122 MB），宿主包的使用者不该被拖进来。
  4. 服务端与浏览器各一个包：两侧共享协议（RPC 链路、引导基础形状、回环名单），拆开要么再出第三个协议包，要么协议放一侧让另一侧依赖它；
     而 nb-runtime 已示范“一个包两份 tsconfig”能把两侧类型隔开，客户端与服务端的往返测试也能留在一个包里。
  5. 只抽叶子（来源核对函数、认领、RPC 监听、端口），start.ts 与 process.ts 留应用：NeuroBot 要重抄约 300 行有时序约束的代码，是最该共用的部分。
  6. 把 start.ts 整体搬走再参数化：它的结构跟着项目管理器、第三方插件、开发任务长出来，参数化的结果是满屏可选项；改为小编排函数加四个钩子，
     NeuroBook 在外面组装。
  7. 沿用 ADR 0030 对 plugin-platform 的做法（先在应用内按目录去耦、机检边界，等第二个应用再搬成包）：开发者已定直接抽包，NeuroBot 紧接着开工；
     但保留它的好处，每一片都“先去耦再搬”，并且边界机检从第一天就有。
  8. 包里定义 modelsKey 与合同常量：内核要求 id 以插件 id 开头，NeuroBot 得叫 nbook.models 或让 NeuroBook 改 id，后者会改用户磁盘上的设置键。
  9. 窄接口做成“按 SettingDefinition 读任意设置”的缩小版 SettingsService：会把 NeuroBook 的 defineSettings（依赖 nb-form、插件文字与目录）拖进包。
  10. 服务键 clockKey、stateRootKey、startupEnvKey 放进包：它们的 id 带 nbook，且 SDK 已把前两个导出给第三方插件，改 id 是兼容性变更。
  11. HTTP 只抽判定函数：“核对先于一切路由”依赖分发器的调用顺序，函数共用而分发器各写一份，等于每个应用重新证明一次（2.4）。
  12. 包里用 Hono：只有宿主自有路由用了它，换成一张 Map 即可，不让每个宿主应用被迫带 Hono。
  13. 把 window.ts 骨架一并抽成 createWindowLink：只有一个使用者，形状会照着工作台与项目来设计；等 NeuroBot 写出自己的版本再对比。
  14. 把开发监督进程（server/dev/）一并抽：约 800 行非测试代码，依赖 Vite 与 NeuroBook 的后端文件集合规则，NeuroBot 还没有对应需求；
      只把它共用的端口与回环件放进包，将来抽 ./dev 时只搬本体。
  15. 文件锁抽成独立小包 nb-file-lock：现在只值一个子路径，三个使用者里两个就在应用内（见 2.9）。
  16. 两个包发布到 npm：没有使用者（NeuroBook 发 bundle，NeuroBot 第一版只在仓库运行），发布会多出 semver 面与 release:check 约束。
  17. 不抽诊断出口，让应用传出口：NeuroBot 必须有日志，传出口等于每个应用抄 600 行。

7. 勘误与补充（交付前复核后追加；以本节为准，与前文冲突处按本节）
====================================================================
  7.1 2.4 的“按对象身份核对 ctx 造的插件”要改。读了 plugin-platform/shared/definitions.ts 的 definitionAt（NeuroBook 的 manifestServerPlugins
      就是经它把描述里的顶层贡献并上去）：它返回 `{...definition, version, contributions}`，是新对象，所以“对象身份”核对在 NeuroBook 上会误判缺失，
      启动即 ServerAssemblyError。改为：ctx 签发 HTTP 与诊断两个插件时记下 id 和各自的 `entries` 数组元素（spread 复制的是 entries 数组的引用，
      元素身份保留，已按源码确认），startServer 在拿到应用交来的 plugins 后，按 id 找到定义，核对其入口元素与签发时是同一批对象；
      id 不在、入口被换掉或被删，都抛 ServerAssemblyError。备选是在 ctx 造的定义上挂一个 symbol 品牌（spread 会复制自有可枚举的
      symbol 属性），两者任选，我倾向按 id 加入口身份，因为它不依赖属性是否被复制。这仍是 NeuroBook 与 NeuroBot 都绕不开的机制：
      应用换不掉判定，也漏不掉插件。实现这一片时先写“经 definitionAt 包装后仍通过核对”的用例，再写“换掉入口或漏掉插件时失败”的用例。
  7.2 1.1 与 1.4 里说的“回环名单两份会漂”不准确，更正：config.ts 本来就有两个集合，用途不同：LOOPBACK_HOSTS（127.0.0.1、::1、localhost）是
      NBOOK_HOST 的绑定地址写法；LOOPBACK_ORIGIN_HOSTS（127.0.0.1、localhost、[::1]）是 URL.hostname 的写法，IPv6 带方括号。dispatch.ts 里的
      LOOPBACK_HOSTS 与后者同形，是后者的重复。protocol/loopback.ts 要导出这两个集合（命名区分“绑定地址形式”和“URL 主机名形式”）
      以及 loopbackOrigins、isLoopbackHostname；config 用前者校验 HOST、用后者校验 ALLOWED_ORIGINS，分发器只用后者。
      合并时不得把两者并成一个集合，否则 `NBOOK_HOST=::1` 与 `Host: [::1]` 其中一边会坏。测试里各放一条用例钉住两种写法。
  7.3 2.6 的重连只按 BootstrapBaseSchema 检查会与现状有一处小偏差：remote-session.ts 的 refreshEndpoint 现在用完整的 BrowserBootstrapSchema 做
      Value.Check，不符就返回 null 继续退避；只查基础形状后，plugins 或 catalogs 字段损坏的应答会被接受、会话转 online。窗口重连不重新登记插件，
      后果多半无害，但与“行为不变”的字面有出入。采用的办法：RemoteSessionOptions 加可选的 `checkBootstrap?: (raw: unknown) => boolean`，
      NeuroBook 传完整 schema 的检查，NeuroBot 不传就只查基础形状。包的基础检查始终先做（取 rpc 端点要用）。
  7.4 实现时先跑的验证里再加一条：V4 definitionAt 包装之后的核对用例（见 7.1）。
  7.5 未验证项汇总：defineRemoteService 展开 spec 后的类型推导（V1）；startup-env 在包路径下的打包求值顺序（V2）；nb-host/browser 在
      NeuroBook 的 vue-tsc 下通过（V3）；pack-app.ts 对新 workspace 包的打包行为、Windows 命名管道、client-identity.dom.test.ts 能否去掉 DOM，
      都是从代码推断，没有运行证据。
