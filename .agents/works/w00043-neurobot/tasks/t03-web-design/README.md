# NeuroBook 里 bot 的界面设计评审

## 目标与范围

按 design-review 定 NeuroBook 里 bot 相关界面的外观与交互（[bot 提案](../../../../../docs/proposals/neurobot.md)第四节第 11 小节的合同是前提）：
- bot 视图：打开作品时的位置、书架案头的入口（看板娘）、未读的气泡与计数；
- 日程视图：列表、状态、两种表单、暂停与恢复、“待你确认”；
- 记忆的只读查看；
- 缓冲区的界面（[缓冲区提案](../../../../../docs/proposals/agent-input-buffer-states.md)第四节第 7 小节）：排队区的“已暂停 · 原因 · 继续”、停止的两个选项。

先排注意力顺序，再在草稿 worktree 的 Lab 里出静态稿。

合同：行为合同未变，本 Task 不写 Spec；定稿的外观与交互由 t06、t07、t09、t10、t14 写进各自的 Spec。

依赖：无。

来源：w00043 的 [Task 规划](../../README.md#task-规划)（2026-11-18 按已接受的 [bot 提案](../../../../../docs/proposals/neurobot.md) 与 [缓冲区提案](../../../../../docs/proposals/agent-input-buffer-states.md) 重排）。

## 当前状态

2026-11-10 经 nbdev 新建；2026-11-18 范围从 NeuroBot 的 web 改成 NeuroBook 里的 bot，同日开工。草稿在 `.worktree/w00043-t03-drafts`（分支 `w00043-t03/drafts`，不合并），组件 `drafts/web/components/BotMessenger/`。

决定：

1. 注意力顺序（开发者 2026-11-18“可以”）：bot 视图打开时先看最新的对话与输入框；等你处理的事（审批与提问停在停靠区、排队里已暂停的话与“继续”）出现时贴在输入框上方；日程与记忆默认收起，从视图头部的入口进；工具调用细节照现有对话视图折叠。关着时只留一个入口：头像加未读气泡，有等你处理的事时与普通未读区分。不自动收起。缓冲区的界面与 bot 视图放在同一轮看。
2. bot 的视图是 IM 式（开发者 2026-11-18：“bot 的最理想的视图就是 IM 软件视图，左侧是聊天、群聊，右侧是聊天界面”）。

第 1 轮评审板（[`artifacts/review/index.html`](artifacts/review/index.html)）问两题：左栏要不要放“会话”、打开作品时消息页放在哪。开发者 2026-11-18 的答复：

3. 左栏放“会话”（选 B）。开发者的评论：“这个想法可以。现有代码中是有单独的对话视图（用户可以随便拖拽，可以放到左侧边栏，也可以放到底部面板）。这里有两种选择：bot 视图也单独一个 view；bot 视图和 view 视图合并成一个多功能 view（就是 B 选项），要注意做好多种状态的切换，例如（过滤，搜索，纯 session，纯 bot，子 session，子 bot 等等）”。
4. 放在哪没有选，评论：“第二题我觉得这个 B 侧栏的设计比较不错，你觉得现在 bot 视图和 session 视图是不是应该用一个组件？”（主 Agent 的回答见会话，待开发者定）
5. 新需求：“这种 bot、session 模式下，一个对话窗口可能不够了，用户应该有多开对话窗口并自由排列的能力”。
6. 主 Agent 回答第 4 项：对话本身用同一个组件（对话视图加对话宿主，bot 与会话只差选项），导航（bot、会话、过滤、搜索、子会话）单独成一个组件；侧栏一个“消息”视图，多开另做。开发者 2026-11-18：“同意合并”，bot 与会话放进同一个“消息”视图，取代现在的会话面板（`nbook.agent.sessions`）与 Agent 对话视图（`nbook.agent.conversation`）。
7. 多开（开发者 2026-11-18）：“多开先放最后搁置，我觉得可以做成侧栏多开的，工作台的视图模型是一种一个这个改一下应该代价不大”。主 Agent 推荐过的编辑区页面多开不采用；做到时先查改工作台视图模型的代价。
8. 第 2 轮（评审板 v2）：侧栏窄时用 A 头像列加抽屉。开发者评论：“我觉得可以，就是这个导航的样式不是特别好看，还可以优化。还有这个 ‘还有 12 个会话’ 不要，做下拉刷新”（主 Agent 理解为列表滚到底自动加载更多，下一轮按这个画）。
9. 第 2 轮：导航的排法（搜索与过滤在顶上、bot 与会话、子会话挂在父下）同意，但开发者评论：“我不是很喜欢这个干巴地把 bot 和 会话放在这里作为一组的标题这种设计”。下一轮出导航样式的候选，去掉干巴的分组标题。
10. 第 3 轮（评审板 v3）问“不要分组标题，bot 和会话靠什么区分”，开发者在会话里纠正：“不是不要这种分组的模式，而是样式有点丑。希望优化一下。包括子 bot、子 session 展开后的这种展示”。分组保留，v3 那道题作废；下一版只改样式（分组头、行、子 bot 与子会话展开后的展示）。
11. 第 3 轮第三版（评审板 v5，照会话面板画、问两组标题怎么画）之后，开发者在会话里改方向：“我觉得还是别把 bot 和 session 放在一起展示了。这样应该好做一些，做成那种 IM 的会话列表”。bot 一侧做成 IM 的会话列表，不与会话混在一个列表里；v5 那道题作废。主 Agent 的理解（待开发者确认）：“消息”视图只放 bot 与以后的群聊，会话照旧用现有的会话面板与 Agent 对话视图，第 6 项的“合并”改成只共用对话组件；bot 的子会话与子 bot 进聊天头部现有的“子代理”入口，不挂在列表里。
12. 第 4 轮（评审板 v7）：会话与 bot 在同一个“消息”视图里，顶上两个标签切换（选 B，开发者 2026-11-18）；第 11 项里主 Agent 推荐的“分开两个视图”不采用，第 6 项的合并照旧成立，只是 bot 与会话分在两个标签里、不混排。开发者评论：“会话不要今天、昨天、更早这种分组”。
13. 第 4 轮：bot 的 IM 会话列表的画法同意（一行一个联系人；第二行平时是最后一句话，在跑时蓝字“正在……”，等你时黄字“等你批准：……”；未读数在右边；子会话与子 bot 不挂在列表里，进聊天头部的子代理入口）。
