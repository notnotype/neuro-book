### 1. 撤回入口检查与实际装配之间仍能变成损坏，必需扩展会漏清理

- **严重程度**：重要；**类别**：并发／资源寿命。
- **位置**：草稿 3 关键设计 2（42 行）、验收 67 行；`session/session.ts:659–682,696–709,716–727,739–744,768–795`（内核目录）。
- **现象**：空闲会话的 `setTitle` 已占队列，JSONL 的 `write` 还没返回。此时撤回必需扩展，重新装配入口见句柄健康，进入队列等待。放开写入并让它失败后，装配项才执行；缺必需扩展时直接进 `!assembled.ok`，清 `revoked` 并返回，根本不写日志也不抛 `LogBrokenError`。完成分支仍放行撤回。另一空档是队列外等待 `profiles.resolve`。
- **为什么是问题**：第二轮第 4 条修到了“撤回前已坏”，没有修到“排队期间才坏且装配不写”。`revoke()` 完成后宿主可释放服务，撤回的扩展仍未收到挂载中止或执行清理；只看 `broken` 和无新日志测不出来。
- **如何核实**：真实 `AgentHost` 和 JSONL；在一次空闲 `setTitle` 的文件写入前设门，发起必需贡献的 `revoke`，再让那一次写入失败。对照先写坏再撤回；两种顺序都断言撤回返回前挂载信号中止、清理完毕，无新事件。
- **建议改法**：入口保留快门；等待 Profile 解析后、进入拥有写入互斥的队列项时，再按 `core.broken` 决定“只摘撤回项”。在任何无写入返回、换装配或新挂载之前守住这条分界；写入导致损坏的已有兜底走同一收尾。

### 2. 公共受理改成成功回执，`changeProfile` 却未完成成功所承诺的切换

- **严重程度**：重要；**类别**：接口合同／范围。
- **位置**：草稿 3 关键设计 1（29–33 行）、Spec 改动第 50 行、验收第 65 行；`session/session.ts:322–350,356–366`；`harness/runtime.md` 输出 38。
- **现象**：按稿，`profileChanged` 和 `commandAccepted{value:{changed:true,…}}` 已提交，旧扩展的反应批失败；不跑 `written` 和 `after`，交回 `changed:true`，但快照仍是旧的 Profile／装配，旧挂载没有摘下。输出 38 明定成功切换要等新扩展装上并写完外部事实，且说写失败得 `log-broken`。第 50 行只新增一条通用规则，没有改输出 38；任务决定 1 明确的是应答，并未裁定所有指令的成功都只表示受理记录提交。
- **为什么是问题**：这是以前不会出现的**首次**成功回执（重放本来就只是历史回执）。调用方不能同时把 `changed:true` 当切换完成，又按验收得到旧装配。不能用验收条目替代这个合同取舍。
- **如何核实**：真实 JSONL 让旧扩展在 `on.profileChanged` 产出的批写失败，核对首次回执、`snapshot().profile`、清理与新挂载日志，再用原键重发。计划当前把首次 `changed:true` 和旧装配都列为通过。
- **建议改法**：不要为修应答暗改全部指令。明确非应答的回执策略；若明确扩大到 `changeProfile`，同步改输出 38，明示这个窗口内成功只确认落盘、要见 `broken` 后重开才完成切换。两种方案都不在坏句柄上换装配。

### 3. 停止新增 `log-broken`，但验收没有覆盖公开码表和远程回执

- **严重程度**：重要；**类别**：公开接口／验收映射。
- **位置**：草稿 3 第 41、50、66 行；`packages/nb-harness/src/kernel/api/codes.ts:20`、`host.ts:86,110`（同目录）；`packages/neuro-book/src/plugins/agent/shared/remote.ts:151–167`、`backend/remote.ts:176–179`（同插件）；`packages/nb-runtime/src/remote/node.ts:867–879`。
- **现象**：`abort` 的失败码表只有 `not-allowed`、`command-id-conflict`、`session-closed`。`CommandResult<"abort">` 和 `agent.sessions.abort` 的远程 `errors` 都从该表派生。只改入口与停止等待者（或沿用 `accept` 的类型断言）时，内核可交回 `log-broken`，草稿所列内核验收可通过，远程运行时却会记 `undeclared-error`，向调用方交回 `provider-error`。
- **为什么是问题**：第 7 条修的不只是内存释放，还改了调用方能判别的公开结果。通用的应用测试不等于经过 `nb-runtime` 检查这条新增失败路径。
- **如何核实**：码表 → 远程方法声明 → `context.fail` → 运行时校验能静态核实；另把远程 `abort` 合同用例接到真实坏句柄，断言收到的是 `log-broken` 而不是提供方异常。
- **建议改法**：在 `commandErrors.abort` 声明新码，从既有合同派生，不绕类型；验收加远程结果一例，或在已有 Agent 合同测试中明确断言该码被声明并可传输。

### 4. 异步应答验收能走到启动边界，但“模型没收到新请求”证明不了没启动

- **严重程度**：重要；**类别**：验收映射／故障隔离。
- **位置**：草稿 3 第 33、65、75、80 行；`packages/nb-harness/src/kernel/run/interaction.ts:199–207`、`run/control.ts:157–181`、`run/loop.ts:251–278`、`run/model-call.ts:121–137`、`run/tools.ts:95–108`（同目录）。
- **现象**：空闲异步回答确实有 `launch`，第一轮也已写在受理批里。但若只去掉“反应批失败不 launch”的保护，循环可进入第一个边界，先获取工具集并释放不再声明的工具。随后最迟在写 `modelStarted` 时撞上坏句柄，模型端口仍收到 0 个新请求；状态门也会吃掉阶段帧。第 65 行的断言仍能通过，第 80 行说的保护并没有被验收锁住。
- **为什么是问题**：工具释放等宿主动作已经发生，既不是新请求，也不在落盘与状态帧的断言范围内。这是第一轮第 18 条补上异步用例后，判据本身留下的盲区。
- **如何核实**：用真实异步提问工具跑完第一轮，保留它的已建实现；改变工具声明使下一轮边界会释放它，随后仅令回答的反应批失败。在显式关闭前断言工具未被释放；去掉启动保护时这条应失败，即使模型请求数不变。正常回答是释放的对照。
- **建议改法**：保留模型请求数断言，再断言一个执行循环在第一次写前就能产生的宿主可观察效果，单独对启动保护做变异，不把它与回执或状态门一起删。

### 5. 只清挂载还不算摘下：坏句柄的预览可以再调用已撤回扩展

- **严重程度**：重要；**类别**：资源寿命／公开查询。
- **位置**：草稿 3 第 42、67 行；`packages/nb-harness/src/kernel/dispatch/mount.ts:116–143`、`dispatch/core.ts:110–118`、`session/session.ts:659–673,430`、`session/preview.ts:105–144`、`run/chain.ts:65–82`；runtime 输出 55、57。
- **现象**：新增的损坏分支不能沿用“重新装配会替换 `core.assembly`”的假设。若只完成挂载中止和清理，空闲撤回不经过现有的 `core.revoked.add`，原装配仍列有这个扩展。坏句柄能查询；`preview()` 不看 `broken`，仍按装配运行槽和模型拦截。第 67 行两条断言均可通过，撤回后的预览却还能进已释放提供方的拦截。
- **为什么是问题**：宿主在 `revoke` 返回后可释放插件资源；清理挂载并不撤销独立的调用入口。关键设计说“不装配”是对的，但必须用另外的方式隔开留着的旧定义与仍能调用的入口。
- **如何核实**：已挂载的可选贡献加一个会在 `ctx.phase === "preview"` 时读提供方资源的模型拦截；让空闲会话写坏，撤回后从公开 `preview()` 发起新查询。断言清理完成、没有新日志，也没有调用这层拦截；正常撤回作对照。
- **建议改法**：坏句柄摘下时保留撤回标记并让仍开放的入口过滤它；至少把预览纳入验收，明确哪些查询能在坏句柄上执行扩展代码。若选择在坏句柄直接禁止执行式预览，要声明失败码，不影响快照和日志读取。

### 6. 只在重新装配入口判坏，覆盖不到一直进不了入口的撤回

- **严重程度**：重要；**类别**：运行收口／撤回等待者寿命。
- **位置**：草稿 3 第 39–42、67 行；`packages/nb-harness/src/kernel/run/control.ts:65–76,91–94,168–181`、`run/loop.ts:251–259`、`run/tools.ts:95–108`、`session/session.ts:659–682,824–841`。
- **现象**：`onBroken` 结算 `waitRun` 并触发中止，却不清 `#active`。这时撤回只触发挂载信号、排进 `pendingReassembly`，要等循环的 `onIdle` 才进草稿新增的坏句柄分支。循环可正在等已退役工具的 `dispose()`；这个钩子不接收中止信号，也不与中止竞速。句柄已终结、日志再也不能写，撤回仍能无限等，除非工具返回或宿主另行关闭会话。
- **为什么是问题**：`waitRun` 已返回不等于循环已退出；草稿把损坏时的挂载清理挂在未必触发的运行退出点上。只测空闲坏句柄，无法说明损坏后插件停用能收口。
- **如何核实**：在实现 worktree 运行 `bun /tmp/review-t16-design3/lab/revoke-running.ts`。真实宿主与 JSONL，工具在下一边界退役时卡在 `dispose()`，`setTitle` 写坏后 `waitRun` 已返回 `log-broken`。日志头为 14，随后撤回已待办、清理 0 次；不放行工具而显式关闭会话，撤回完成、清理 1 次，日志头仍为 14。这是基线观察；只加入口守卫不会改变这个调度路径。
- **建议改法**：明确损坏时由谁推进撤回，不只改重新装配入口。把待撤回项交给在损坏后仍保证推进的清理路径，与关闭共享清理所有权；仍可能使用撤回资源的在途工作要先隔离或等其完成，不能仅把 `#active` 置空就放行宿主。补一个先坏、运行尚未退出时发起撤回的门闩用例。

### 7. 停止的在途重放还不能保证“自己的受理记录”

- **严重程度**：重要；**类别**：同步重入／幂等。
- **位置**：草稿 3 第 41、66 行；`packages/nb-harness/src/kernel/run/commands.ts:349–374`、`run/control.ts:113–118,228–230,247–253`、`run/settle.ts:134–136`；runtime 输出 30、session 输出 17。
- **现象**：`recordStop` 登记后，`abortCommand` 在填入 `aborting` 表之前同步调用 `control.abort()`，此时已发布 `aborting` 帧。订阅者在这帧里用同键、不同 `keepQueue` 重入，两次都会登记并写收口批。即使没有重入，已在表里的同键也只比键、不比参数。草稿只改损坏门和“命中记录就成功”，留着这些路径时，第一条停止仍可能误拿第二条的 seq；坏句柄重放第一条反而得 `command-id-conflict`。
- **为什么是问题**：第二轮第 7 条要求有自己的记录才报成功。按键查到最后一条，并不能证明那条是这次请求。只换掉 `core.head` 的回退值，验收里的单个停止两支均可通过。
- **如何核实**：在实现 worktree 运行 `bun /tmp/review-t16-design3/lab/abort-reentry.ts`。真实 JSONL 只打坏 `runEnded` 的反应批：同一键落下 seq 17、18 两条不同哈希，两个首次回执均为成功、seq 18；在坏句柄上重发第一组参数得 `command-id-conflict`，第二组反而成功重放。
- **建议改法**：在触发状态帧和中止信号之前登记在途键、参数哈希与回执；同键同参只加入，同键异参立即冲突。处理停止等待者时按受理身份匹配，不借用另一条同键记录。收口批反应失败的既定用例同时断言一条受理记录、首次回执与重放的 seq 一致。

### 8. `waitRun` 的新规则没有替换会话 Spec 里相反的承诺

- **严重程度**：建议；**类别**：规范／公开接口。
- **位置**：草稿 3 第 39–41、50–51、66 行；`docs/specs/harness/session.md:169` 的“时序与寿命”；`docs/specs/harness/runtime.md` 输出 13；`packages/nb-harness/src/kernel/api/host.ts:550–551`。
- **现象**：草稿规定已有本次 `runEnded` 时按日志结算 `waitRun`，且把这一情形作为验收；`session.md` 的寿命规则仍无条件规定损坏时等待者以 `log-broken` 完成。草稿只列了对同文输出 12 的状态和撤回补充，没有列这处替换。SDK 上 `waitRun` 的注释同样无条件描述写失败结果。
- **为什么是问题**：同一个“收口批已提交、反应批失败”的场景分别被规定成日志结果与本地失败；维护者可能为保留旧文把已提交的结果改回失败。
- **如何核实**：把第 66 行 `runEnded` 已提交的用例代入 `session.md`“时序与寿命”的损坏条目与 `waitRun` 公共注释，两处都没有日志结果这一分支。
- **建议改法**：把结果选择写入 `runtime.md` 输出 13，`session.md` 的寿命条目与 SDK 注释引用该规则，明确只有无本次已提交结果才合成 `log-broken`；保留立即结算、无额外写入的约束。

### 9. 重开后只数恢复批，分不清保留完整批与丢弃后重写

- **严重程度**：建议；**类别**：恢复／验收判据。
- **位置**：草稿 3 第 46、69 行；`packages/nb-harness/src/kernel/log/jsonl-store.ts:274–285,301–325`、`log/codec.ts:33–41`；session 输出 5、6、12。
- **现象**：第二轮第 15 条的两种故障点和正确行为已写进设计；但两支验收都只约束重开后有一个恢复批。完整写入后同步报错时，若错误路径把该批当成未提交而截掉、下次打开再补，最终也只有一个批，仍可通过这条断言。
- **为什么是问题**：“故障后最终有结算”不能代替“完整批按原样归约、不再写”。后者是这次专门补的持久化合同；重写会替换已经写下的事件身份与时刻。
- **如何核实**：用同一只读崩溃夹具，设崩溃前最后 seq 为 `H`。第一次打开报错后、第二次打开前直接读 JSONL：写前失败仍为 `H`；完整写后同步报错已增加一个完整批。第二次打开时前者追加恢复批，后者追加 0 个事件、保留原 `batch.id` 和 seq。现有 `FilePort` 能分别在两点注入并记录追加。
- **建议改法**：在第 69 行增加两次打开之间的文件观测，并对同步失败分支断言第二次打开没有写恢复批；最终批数保留作补充断言。

### 10. 只读恢复的崩溃用例没有未完成的模型请求或已开始的工具

- **严重程度**：建议；**类别**：验收映射。
- **位置**：草稿 3 第 57、69 行；`packages/nb-harness/tests/kernel/fixtures/crash-session.ts:20–29,38–51,54–66`；`packages/nb-harness/src/kernel/run/recover.ts:13–32,74–87`；runtime 输出 34、session 输出 15。
- **现象**：`waiting-approval` 的模型已经给出了两条回复；`lab.asker` 已交回工具结果，`lab.gated` 尚未开始。即使重开后审批、未开始的工具和缓冲区都正确，这个用例也读不到 `modelFailed{interrupted}` 或 `toolResult{unknown, code:"interrupted"}`。现有 `control.test.ts` 的这两支走的是能装配的打开，不是本次改动的只读分支。
- **为什么是问题**：只读分支若误写成只处理等审批的运行，草稿里的子进程场景和既有可写恢复用例仍可通过。恢复的触发条件是本次改动的合同，不限于与用户交互的崩溃点。
- **如何核实**：复用已有 `in-tool` 和 `compacting` 检查点，以缺 Profile 打开：前者核对已开始与未开始的工具分属 `unknown`、`denied`；后者核对 `modelFailed` 结算的是原请求号。用真实 `modelStarted` 与工具进入信号作门闩。
- **建议改法**：在现有崩溃用例上参数化可写／只读打开，至少给模型在途和工具已开始各一个只读对照；审批夹具仍负责异步提问、缓冲和唤起门，不复制它们的全套断言。

## 未发现问题的方面

- **第二轮第 5 条，健康路径的先后**：仔细检查后没有发现草稿 3 仍允许在反应结束前唤醒认领到的等待者。把 `committed` 放在受理批成功后的反应阶段 `finally`，可在反应报错时也交回已提交的应答，不必吞掉非日志异常；主批写入或同步失败仍走不确定结果的旧收尾。验收可在真实 `on.interactionResolved` 内设门，以 `ctx.ask` 返回后的可见标记判定先后。
- **第二轮第 6 条，状态和运行等待者**：仔细检查后没有发现绕过 `#setStatus` 的状态帧发布路径；快照读同一个状态。按整张表结算覆盖了订阅 `runStarted` 时已登记、但循环还没开的运行；损坏后新到的等待者按同一日志证据结算，不必再登记。复用 run id 的跨分支歧义仍是已知限制；规范同步见第 8 条。
- **只读打开的顺序和应答重放**：仔细检查后没有发现需要扩展反应参与恢复，或需要更改日志格式。现有 `core.write`、`abandon` 与存储放锁路径足以实现“可装配时 `code-updated` → 恢复 → `mount`，只读时只补恢复批”。已提交键先匹配名字与参数哈希再进 `decide`，同键同参可重放、异参仍冲突、新键保持 `read-only`。真实 `rewind` 且没有后续路径事件时可作不恢复的对照，与转 t17 的真暂停误判不同。
