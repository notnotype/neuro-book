### 1. 普通打开会把仍可补写的 fork 永久变成另一条会话

- **严重程度**：阻断；**类别**：正确性／跨进程恢复。
- **位置**：计划关键设计 4（51–57 行）、验收映射 86 行；`packages/nb-harness/src/kernel/session/session.ts:300–307,610–648`；`harness/session.md` 输出 17、20。
- **现象**：fork 的目标先写带 `origin` 的头，再另写复制批；草稿不改存储，所以这个窗口每个新 fork 仍有，不是只有旧数据。复制批没写下时，另一进程按 id 打开目标，草稿会用 `{}` 新造 `sessionCreated`、装配事件和门，没有复制来源路径。随后同键重发 fork 会因首事件不符永久失败。草稿的验收 86 行正要求这个结果。普通 `createSession` 的头比对也没排除 `origin`，同参数新建可抢先做同样的事。
- **为什么是问题**：只要一次普通打开就能使本来可恢复的目标丧失同键补写能力；头仍标成源会话的子分支，内容却不是复制的路径。违反输出 17 的同键补写及输出 20 的 fork 内容；“失败可重试”对非空目标已经不成立。
- **如何核实**：按 `forkSession` 的 `create → append → 源 commandAccepted` 三步读代码；真实 JSONL 让目标第一次复制批未写下，先开、关目标，再用原键重发，核对来源路径与首批。这个顺序应保留可补写性，而非验收 86 行指定的永久失败。
- **建议改法**：锁内先按 `header.origin` 区分初始化所有者。只有头的 fork 不走普通 `open` / `create` 补完，不写普通创建事件；由来源的同键 `fork` 补复制批。验收加“先打开失败、随后原键成功、复制恰好一次”。

### 2. fork 的首事件不能证明是这次请求的目标

- **严重程度**：重要；**类别**：正确性／幂等。
- **位置**：计划关键设计 4（57 行）；`packages/nb-harness/src/kernel/session/session.ts:300–307,610–645`；`dispatch/core.ts:181–185`（同包）；`harness/session.md` 输出 17、20。
- **现象**：目标 id 只由来源 id 与 `commandId` 决定。一般一整个会话树共用第一个 `sessionCreated`，两个不同的 `leaf` 会有相同的根事件 id。目标复制 A 路径成功、来源受理批没写下时，拿同键指定 B 路径再发（或缺省 `leaf`、来源期间移到了 B），首条相同，草稿就会把 A 当 B 成功，并写一条 B 参数哈希的受理回执。反过来，`leaf: null` 公开有效，来源路径没有首条，真实复制批仍至少有 `wakeGate`，照字面会拒绝真正的同键重试。
- **为什么是问题**：前者是永久的成功错报；后者破坏已经发布的目标在源受理失败后可重试的合同。两者都不是上一轮“有任意事件就当完成”的同一个反例。
- **如何核实**：按 `session.ts:302–306,612,619,640–646` 推演；在真实 JSONL 让目标复制成功、只拒绝来源的 `commandAccepted{name:"fork"}`，重开来源，分别用相同 `leaf`、另一同根 `leaf` 与空路径对照，查目标 `header.origin` 和实际 path。
- **建议改法**：锁内校验来源会话与准确的 `origin.entry`，并按实际复制合同验证完整首批，明确零路径的合法形状；重试缺省 `leaf` 时明确是沿用已记录的来源节点，还是按不同请求拒绝，不用共享根当作身份。头不匹配的空目标也不要写。

### 3. 能校验 `{}` 不代表丢失的 `initial` 是 `{}`

- **严重程度**：重要；**类别**：数据完整性／恢复合同。
- **位置**：计划关键设计 4（53–55 行）与验收 85 行；`packages/nb-harness/src/kernel/api/host.ts:554–566`；`session/session.ts:135–142,506–508,514–525,534–539`（同包）；`packages/neuro-book/src/plugins/agent/backend/agent.ts:313–325`。
- **现象**：`initial` 是独立建会话参数，允许非空值；无 schema 时任何合法 JSON 都可用，允许可选字段的 schema 也可能同时接受 `{}` 与实际非空值。原值不在头，只在首批 `sessionCreated`。拿合法 `{}` 补完，相当于把丢失值确认为空；同一进程随后拿原值再建也只能得到 `session-exists`。`startTask` 确实传 `initial`，后续重复只查头里的 Profile、项目和后台标记。
- **为什么是问题**：两个不同初始输入能留下完全相同的头。一次查询能永久抢走原请求的补完机会；提示词／创建反应读到的是猜出的输入。这不是 schema 校验能防的，也不属于计划另行排除的 Agent 审批设置。
- **如何核实**：用允许 `{}` 的 Profile，以 `{topic:"原值"}` 建会话，锁持有期间停在头已写、首批未写并杀进程；先 `open`，再用原参数 `create`。按草稿会得到首批 `initial:{}` 与后续 `session-exists`；验收应核对模型／扩展实际看到的原值。
- **建议改法**：仅在有持久证据能还原默认或原输入时允许自动补；没有证据的旧头返回 `session-incomplete`，让原调用者以同 id 带回 `initial`。若产品要能自动补全新日志，需记录创建意图或让头和首批一起发布，不能靠“`{}` 合法”替代。

### 4. 撤回必需依赖时不触发 `LogBrokenError`，仍会放出未清理的扩展

- **严重程度**：重要；**类别**：资源寿命／撤回合同。
- **位置**：计划关键设计 2（43 行）与验收 82 行；`packages/nb-harness/src/kernel/session/session.ts:659–682,696–728,768–805`；`dispatch/mount.ts:116–143`（同包）；runtime 输出 57。
- **现象**：损坏且已空闲时撤回已挂载的必需扩展，`notifyAssemblyChanged` 不走运行中的即时 `revoke`。`reassembleOnce` 先 `assemble`；缺必需依赖时清 `core.revoked` 并在 781 行返回，不尝试写日志，也不摘下任何扩展。因此只在 `reassembleNow` 拿到 `LogBrokenError` 时清理，完全碰不到这个分支。其完成钩子随后放行撤回等待者。另一个无写入分支（哈希相同但 Profile 对象换了）甚至能在坏句柄上继续重新装配和 mount。
- **为什么是问题**：宿主收到撤回成功后就可释放插件服务，旧扩展的回调／计时器仍存活；坏状态帧保持不变也挡不住这条寿命错误。验收只造可选扩展撤回（装配成功、随后写失败）可全过。
- **如何核实**：真实 `AgentHost`＋JSONL；Profile 声明依赖一个已挂载的贡献，令会话空闲时一次日志写失败，然后撤回这个贡献。断言撤回完成时挂载信号已触发、清理已完成且无新日志；用不被依赖的贡献作对照。
- **建议改法**：以 `core.broken` 为入口条件，在解析、装配前就走“只撤回、等清理”分支；中途因写入坏掉也走同一分支。不要用是否执行到日志写入来裁决撤回责任。

### 5. 若在首批提交时立刻叫醒，工具能抢在结算反应之前做事

- **严重程度**：重要；**类别**：时序／既有合同。
- **位置**：计划关键设计 1（32–35、97 行）；`packages/nb-harness/src/kernel/run/commands.ts:72–83`、`dispatch/reactions.ts:43–49,64–90`、`run/interaction.ts:51–68,97–109`、`run/tools.ts:195–212`。
- **现象**：32 行写的是受理批落盘即执行 `committed`，34 行又把它列在反应写失败之后；两种读法不同。当前两种应答都等整条反应链完成才叫醒。一旦提前，真实工具中 `await ctx.ask(...)` 后的普通代码可在 `on.interactionResolved` 挂起时继续跑，不需要再取得写队列；这时反应批还未知，`onBroken` 也尚未触发中止。
- **为什么是问题**：把“按已提交的结算叫醒”改成“反应尚在跑就准许工具继续”不是已定决定。已有扩展能依赖等待过程中不交出应答，提前释放可产生不可撤销的外部副作用；验收只看最终返回值，没有锁住健康路径的原顺序。
- **如何核实**：真实工具在 `ctx.ask` 返回后记可见标记；真实 `on.interactionResolved` 进入后等一道门。反应仍阻塞时检查标记与信号，放行后再核对正常及反应批写失败两条路径。
- **建议改法**：首批成功立即记已提交，但把同步叫醒放在派发之后的保证收尾（成功或异常均以已提交值叫醒）；受理批失败继续走未提交／不确定的收尾。写明具体顺序，避免在 `core.write` 返回和派发之间插入叫醒回调。

### 6. 已登记的 `waitRun` 不一定属于 `#active`

- **严重程度**：重要；**类别**：并发／等待者寿命。
- **位置**：计划关键设计 2（42 行）、验收 81 行；`packages/nb-harness/src/kernel/dispatch/core.ts:324–330,422–433`；`run/commands.ts:68–83`、`run/control.ts:65–76,131–135,188–204,257–268`、`session/session.ts:491`（同包）。
- **现象**：`runStarted` 的日志帧在反应之前同步推出，订阅者看到这个已写下的 id 就可以 `waitRun(id)`。空闲受理时 `launch` 还没发生，调用会登记；如果反应批写失败，`onBroken` 只结算 `#active`，此处是空，且按草稿永不开该 run。同样，收口批带下一次 `runStarted` 时，`#active` 仍指前一次。故障后再等待同 id 会立即得 `log-broken`，原等待者可以永远不完成，关闭也不清这张表。
- **为什么是问题**：草稿承诺已登记等待者一律完成，不能只把 `onBroken` 对 active id 的返回值换成 `runResultOf`。经 `SessionTable` 等待的调用还持有一份引用，悬挂会阻止 30 秒空闲关闭。
- **如何核实**：公开订阅拿到空闲 `send` 或异步回答受理批的 `runStarted`，立刻登记 `waitRun`；只让其反应批写失败，再登记第二次，两次都应及时交回 `log-broken`。与草稿已有“`runEnded` 已提交”一例配对。
- **建议改法**：损坏时消费整个已登记等待表，对各 id 选已提交的本次结果或 `log-broken`，不要依赖循环必须启动。验收加一个尚未 `launch` 的 id；不借此改变健康句柄上未知 id 的行为。

### 7. 损坏前登记的 `abort` 仍能成功但没有受理记录

- **严重程度**：重要；**类别**：回执／幂等。
- **位置**：计划关键设计 2（41 行）、验收 81 行；`packages/nb-harness/src/kernel/run/commands.ts:349–374`；`run/control.ts:65–76,113–119,228–230`（同包）；runtime 输出 30、33 与 session 输出 17。
- **现象**：停止已同步登记，但包含 `runEnded`、缓冲处理与 `commandAccepted{name:"abort"}` 的收口批还没写下时损坏。`#releaseStopWaiters` 找不到受理记录会回退到 `core.head`；`abortCommand` 仍给 `{ok:true, aborted:true}`，并把这个没有受理记录的成功留在 `aborting` 表。加新键的损坏门不会改变它。同键重开后没法重放：空闲时得到 `aborted:false`，又有新运行时甚至会执行新一次停止。与“收口批已提交、只是反应批失败”的情况不能共用回执。
- **为什么是问题**：已触发停止信号并不等于缓冲处理和受理记录已提交。现有顺序已有这条裂缝；草稿明确保留“在途照旧”，却把新一版损坏／重放合同写成一致，且没有用例覆盖已登记的停止。
- **如何核实**：真实运行在等模型或工具时调用 `abort`；按 `commandAccepted{name:"abort"}` 区分收口主批故障和它的反应批故障。对照首次回执的 seq、盘上的受理记录和重开重发。
- **建议改法**：在途停止照常释放等待者；有已提交记录才回成功与该记录的 seq，否则回 `log-broken`（结果可能不确定），并明确同键在途加入、已提交重放和坏句柄新指令的优先级。

### 8. 用普通 `store.open` 判断能否补建，会先写盘再拒绝

- **严重程度**：重要；**类别**：存储合同／失败副作用。
- **位置**：计划 53、85 行；`packages/nb-harness/src/kernel/log/jsonl-store.ts:208–224,249–294`；session 输出 1、5、6、19。
- **现象**：合法会话头之后可能有没写完整的首批，也可能在完整会话后有未完成的尾批。原来同 id `create` 看见日志直接得 `session-exists`。按草稿先 `store.open` 再比头和事件，打开会在拿到锁后另存尾巴、截断并同步日志，并在需要时重建索引；`createSession` 拿到句柄、发现参数不匹配或已有事件并拒绝时，改动已经发生。
- **为什么是问题**：“参数不同、日志不动”和“存在完整会话时照旧拒绝”不能由收口时 `close` 实现。草稿的纯会话头夹具没有任何尾部字节，测不出这个违约；旧的验证失败行为也不能被默默变成完整读盘后的 `log-corrupt` 等结果。
- **如何核实**：真实 JSONL，首批只写下前一条完整记录即停进程；用同 id、不同 `owner` 再建。比拒绝前后日志和生成的 `.tail-*`。再用带完整首批与半个后续批的会话验证“已有事件”分支。
- **建议改法**：先读不修复的不可变头，淘汰显然不匹配者；已加锁的日志分类也需在修复前裁决“可补完／拒绝”。若保持存储接口不变，明确放弃哪条拒绝无写入的承诺，并给真实尾批用例，不能把普通 `open` 当成只读探测。

### 9. Bot 主对话遇到 `session-incomplete`，远程入口会抛错而不是返回恢复码

- **严重程度**：重要；**类别**：应用接口／失败恢复。
- **位置**：计划 54、66、85、90 行；`packages/neuro-book/src/plugins/bots/backend/main.ts:91–122`、`backend/plugin.ts:35–36,105–111`、`shared/contracts.ts:100–122`；Bot 主对话输出 1–3。
- **现象**：一份归属正确的主对话只写下头，重启时 Profile 暂不可用。`header` 能读到它，`#ensure` 无论是显式建还是后台持有都直接 `hold`，不会走带正确参数的 `create`。按草稿，`hold` 得 `session-incomplete`。主对话状态能存这个码，但 IPC 的 `MAIN_CODES` 不含它；`ensureMain` 会抛 `ensureMain failed with an undeclared code: session-incomplete`。Agent 远程端从 `storageErrors` 推出其码表，Bot 用的是独立白名单，改 Agent Spec 不会改掉这条失败。
- **为什么是问题**：同一个失败在列表里是可诊断状态，显式调用却是 `provider-error`；窗口无法按业务码解释，也没有“带同 id 再建”的署名调用路径。默认 Profile 不要求 `initial`，不能证明它在插件／依赖暂不可用时也会装配成功。
- **如何核实**：用真实 JSONL 留一个归属正确的 `bot-<id>` 的头，令原 Profile 暂不可装配；经 Bot IPC 调 `ensureMain`，对照远程失败、`list().main`、日志。恢复 Profile 后再 `ensureMain`。归属不匹配用例继续断言不打开、不写盘。
- **建议改法**：同步声明和转交新码，写明后台状态及显式 `ensureMain` 如何重试；如果 Bot 负责补建，仍以已核对的归属与原创建参数为前置条件。验收走真实远程入口，不只检查 kernel 的 `openSession`。

### 10. `startTask` 会在判断任务冲突之前打开并补完别的创建请求

- **严重程度**：重要；**类别**：调用方合同／跨进程失败。
- **位置**：计划 53–54、66、85 行；`packages/neuro-book/src/plugins/agent/backend/agent.ts:313–325`、`backend/remote.ts:349–353`；`packages/nb-harness/src/kit/sessions/table.ts:314–319,369–376`；Agent 会话输出 10、11。
- **现象**：`create` 因同 id 的头与本次 `project`／Profile 不同而得 `session-exists`。`startTask` 为了取 `header` 调的是 `view.snapshot()`，会触发普通 `open`；按草稿，符合缺省 schema 的那份日志会先被补写，调用才报 `task-conflict`。Profile 不可用或另一进程正持锁补完时，查询还会先抛 `SessionUnavailable`，`startTask` 不映射它，远程收到通道错误而非冲突或忙碌码。
- **为什么是问题**：内核 `create` 已拒绝的创建请求仍能经应用的冲突检查改变另一个任务的日志；锁争用／不完整也被降成不可按业务规则处理的异常。
- **如何核实**：给真实 `task-<uuid>` 写入带项目 A 的会话头，用相同任务 id 和项目 B 走远程 `startTask`；断言 `task-conflict`、日志未补写。用另一个进程持有同一头，发匹配请求，再验证失败码及放锁后同键可重试。
- **建议改法**：在打开之前用 `header(id)` 核对任务的不可变参数；检查通过才发同键 `send`，将打开失败按已有的指令通道转交。测试须把“头已出现”“持锁完成中”“任务参数冲突”分开，不能用已完成会话代替。

### 11. `rewind` 的真实暂停可以被合法路径事件误判为中断

- **严重程度**：重要；**类别**：恢复／分支状态。
- **位置**：计划 47、84 行；`packages/nb-harness/src/kernel/run/tree.ts:58–66`、`dispatch/core.ts:217–234`、`run/recover.ts:70–75`；runtime 输出 36、session 输出 27。
- **现象**：`rewind` 写 `leafChanged` 后启动的是暂停状态；但合法的 `on.leafChanged` 可以 `emit` 一个路径扩展事件。没有 `runResumed`，也没有循环，`#commit` 却因看到路径事件改掉 `leafSetBy`。旧的可写打开已经会为此补收口；草稿原样把判断扩到只读打开，缺 Profile 时也会永久改这条分支。
- **为什么是问题**：这是仍可接着跑的真暂停，不是进程中断。补写 `turnEnded`／`runEnded{interrupted}`、关门之后，原暂停点以及用原运行 id 恢复的行为变了。只测回退后日志没有任何路径更新，两个实现都能通过反例验收。
- **如何核实**：`lab/probes.ts rewind` 用公开 `send`、`rewind`、真实反应和 JSONL 对照：不发路径事实，重开增量 0；发出一条路径事实、始终 `idle` 且无 `runResumed`，可写基线重开却补 `turnEnded`、`runEnded`、`wakeGate`。用缺 Profile 重开同一场景验草稿；再与已写 `runResumed` 但未写第一条路径事件的正例对照（`run/wake.test.ts:448–475`）。
- **建议改法**：区分“叶子最后被什么移动”与“这条运行是否被接回执行”。只有明确的 `runStarted`／`runResumed` 等执行标记解除暂停，不让扩展事件把暂停变成崩溃。若本次不修原有判据，必须明确只读也会继承这一限制，不能承诺真暂停一律不写。

### 12. 成功补建的 Agent 会话会永久跳过配置的审批初值

- **严重程度**：重要；**类别**：调用方合同／初始权限行为。
- **位置**：计划 54、59、64、66 行；`packages/neuro-book/src/plugins/agent/backend/agent.ts:294–305,313–325`、`packages/neuro-book/src/plugins/bots/backend/main.ts:91–106`、`packages/nb-harness/src/kernel/state/kernel-state.ts:142`；`agent/contributions.md` 输出 13。
- **现象**：普通打开补第一批并成功，不经 `Agent.createSession` 的 `initial-approval-<id>`。Bot 对已有正确归属的头直接 `hold`，正好走这条分支。若 Profile 配了 `auto`、`allow-writes` 等而不是内核缺省 `ask`，第一次运行仍用 `ask`；之后同 id `create` 见完整首批也不会补设置。与第一轮已接受的“首批落盘后又崩于后续初始化”不同，这条新路径不用再失败一次。
- **为什么是问题**：同一个 Profile 与参数，正常新建和成功补建的审批行为不同，后台会话会多出需要人工回答的审批。这不是需要保证所有扩展反应成功的问题；当前 Spec 明定 Profile 设置是新会话初值，草稿只拟改 Agent 的失败码表，也只在 harness 记录创建反应的限制。
- **如何核实**：对照上述调用链。验收用已配置 `approvalMode: "auto"` 的 Profile，经 Agent/Bot 分别走正常创建与真实仅头打开，比较第一次执行前的 `snapshot.settings.approvalMode`；不要只断言 `hold` 成功。
- **建议改法**：用带原参数的 Agent 创建入口补建（Bot 先核对权威头、再走该入口），或将必需的审批初值作为第一批的确定事实；若接受补建行为不同，明确改 Agent 合同并验收，不能只记在计划里。

### 13. 仅头日志从 `open` 补建时，解析 Profile 抛错仍会泄漏锁

- **严重程度**：重要；**类别**：资源寿命／失败收口。
- **位置**：计划 54–56、85 行；`packages/nb-harness/src/kernel/session/session.ts:497–508,548–578,591–600`、`packages/nb-harness/src/kit/sessions/table.ts:369–394`；session 输出 11、12。
- **现象**：草稿把建会话的 `try` 扩到取句柄以后，但另开了一条从 `openSession` 补建的入口。后者先拿锁，再在 `try` 外解析 Profile、取扩展、构造并装载 `SessionCore`。首批还没开始，宿主 `profiles.resolve()` 的拒绝就能绕过 `abandon`；后续只读的恢复入口也经过同一段代码。
- **为什么是问题**：首次打开只报 `open-failed`（会话表摘掉自己的条目），随即重试报 `session-busy`。草稿的同 id 再建会因此回 `session-exists`，实际并没有完成首批，必须退出原进程才可接管。第 85 行的首次新建／`resources` 抛错只能验证另一条入口。
- **如何核实**：`lab/recovery.ts throw` 在真实 JSONL 上造仅头日志，经公开 `openSession` 让 Profile 解析拒绝；第二个存储的普通 `open` 实测 `session-busy`。原 `open` 没有交出可关闭的句柄。
- **建议改法**：普通打开与补建都从存储交出句柄时开始有一个清理所有者；即使 `SessionCore` 尚未构造也要直接关闭底层句柄。验收让仅头打开在解析处抛一次、接着用同 id 补建，并验证完整首批与可再开。

### 14. 运行中 `compact` 在受理批确定前就能调压缩方法

- **严重程度**：重要；**类别**：受理顺序／并发与副作用。
- **位置**：计划 30–35、70、92、97 行；`packages/nb-harness/src/kernel/session/session.ts:308–319`、`run/commands.ts:65–82`、`run/control.ts:138–146`、`run/loop.ts:253–289`、`compaction/compact.ts:194–212`；runtime 输出 52。
- **现象**：这里的 `decide` 直接调用 `requestCompaction`，既不返回 `written` 也不返回 `launch`。运行循环在队列外从边界取这份内存要求。若边界正等 `ToolBox.retire`，可以在 `commandAccepted` 的 append 尚未返回时继续，调用压缩方法；随后这个 append 可以失败且没有任何受理记录。
- **为什么是问题**：草稿只挪受理后的钩子，堵不住受理前逃逸的操作。调用方明确得到 `log-broken`，方法已经看到并执行这次请求；无论后来的压缩结果能否写下，方法或拦截层的外部动作已经启动。
- **如何核实**：`lab/compact.ts` 经真实 JSONL、公开 `rewind`／`start`／`compact`，在工具 `dispose` 和仅含该键的写入分别设门。先放工具，压缩方法在写入门未放时已收到 `require: ["保留原句"]`；令写入失败，实测回 `log-broken`。
- **建议改法**：把安排压缩从 `decide` 移到受理成功且仍健康的分支；还需让运行边界在同一单写者顺序中取得已提交的请求（只把 `requestCompaction` 后移会漏掉该边界）。验收同时覆盖写入失败时方法未被调用、成功时按实际受理顺序在边界消费。

### 15. “恢复写失败后下次再恢复”漏了已写完整批、同步失败的情形

- **严重程度**：重要；**类别**：恢复／验收与持久化合同。
- **位置**：计划 47、84 行；`packages/nb-harness/src/kernel/log/jsonl-store.ts:301–325`、`session/session.ts:552–560,579–600`；session 输出 5、6、12、15。
- **现象**：网络式重试不是恢复语义。存储先写整批，再同步；同步报错也使第一次打开得 `log-broken`、放锁。若完整批仍在文件里，再次打开必须归约它，不能再次写。当前验收把“写失败”与“下一次重新写恢复批”合成一格，只拒绝首个字节的实现可以全过。
- **为什么是问题**：恢复批含关联的审批结算、工具结果、运行结尾、关门和转留，不能由第一次返回码判断磁盘上应不应该再记一份。后一次以文件为准是输出 5、12 的合同，不是可选的新行为。
- **如何核实**：`lab/recovery.ts recovery` 用真实审批、异步提问、确认排话后 kill -9。注入恢复批 write 之前失败与真实 write 后 sync 抛错：可写基线首次打开均 `log-broken`，下次可开；前者新增 6 个事件，后者新增 0 个，两者磁盘上都恰有 1 个恢复批。缺 Profile 的基线打开增量 0；草稿的新增路径还须跑同一对照。
- **建议改法**：把“下次再恢复”写成“下次按完整批归约，尚未写全才补”；验收在只读打开上分别卡 write、sync，按真实批标记和 seq 断言顺序、幂等、放锁，不以调用返回码推断落盘结果。

### 16. fork 的目标忙会被误报为源会话日志损坏

- **严重程度**：重要；**类别**：接口合同／锁争用与错误分类。
- **位置**：计划 57、86 行；`packages/nb-harness/src/kernel/session/session.ts:300–307,625–639`、`api/codes.ts:25`、`run/commands.ts:65–68`；session 输出 11、12、17。
- **现象**：草稿把“目标被人开着”由成功改为失败（可重试），但 `forkSession` 的失败只有 `{ok:false}`，公开 `fork` 一律把它变成 `log-broken`。这次只争用目标目录锁，源没有尝试写受理批、也没有损坏。目标锁一释放，用原源句柄就能重试。永久的来源不匹配也会被同一码掩盖。
- **为什么是问题**：`log-broken` 的既有说明是关闭、重开损坏的句柄；关闭源既放不掉目标锁，也解决不了来源冲突。当前验收只写“交回失败”，错码能通过。这个问题独立于目标是否被误补建、首事件是否能证明身份。
- **如何核实**：让源受理写失败但目标复制完整；重开源，另一个句柄持有目标，再用同键 fork。断言忙的是目标、源仍能受理无关指令；放掉目标后同键成功。另用来源不符的目标验证不会当作可等的忙。
- **建议改法**：让目标打开的忙碌、目标冲突与实际写坏分开传递；在 `fork` 的公开类型、Agent 转交和失败表声明结果及重试方式，验收指明确切码和源的状态。

### 17. `changeProfile` 的首个新挂载能写坏日志，后续挂载仍继续

- **严重程度**：重要；**类别**：扩展生命周期／损坏后的推进。
- **位置**：计划 34–35、78–79、97 行；`packages/nb-harness/src/kernel/session/session.ts` 的 `changeProfile` 收尾；`dispatch/mount.ts:36–57,60–109`。
- **现象**：受理批及反应都成功，`after` 开始装新 Profile。首个扩展的 `mount` 用 `ctx.emit` 提交外部事实：这不是 `accept` 的反应批，由独立的写队列项执行，失败在 `Mounts.#external` 里记诊断后结束；`mountAll` 并不会因它而抛出。下一轮照样调用新扩展，即使 `broken` 帧已经发出。只在进入 `after` 之前判断健康，拦不住同一次换 Profile 内的这个路径。
- **为什么是问题**：在已知句柄坏了之后仍调用新挂载，可再开订阅、注册回调或触发外部副作用。这里只失败一次，不依赖第二条并发指令；也不同于首批后直接反应失败（第一轮第 2 条）。已提交的 Profile 变更仍可成功重放，不需回滚它。
- **如何核实**：`lab/lifecycle.ts mount` 用真实 JSONL，仅令第一个新挂载发出的事实写失败，并让它在观察到 `broken` 后返回。基线成功回执可重放、事实没入日志，但后续挂载调用 1 次，且发生在 `broken` 之后。
- **建议改法**：在挂载循环跨越异步边界后检查 `core.broken`，停止后续挂载，明确已取得清理函数的所有权；验收同时断言后续未挂载、清理不丢、回执和重放不变。
