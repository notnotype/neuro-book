# t15 阶段 ② 设计审查（plan-2.md 副本）

### 1. 列表第二行“正在……/等你批准：……”所依赖的数据不存在
严重程度：阻断。类别：依赖的机制不存在。位置：计划“归属插件的贡献”第 2 条（“`nbook.agent` 的活动按 sessionId 已经知道哪个会话在跑、在等什么”）。
现象：`agent/shared/remote.ts:180` 的 `ActivityItem` 只有 `{id, state: "running"|"waiting"|"held", root}`，没有任何文字；`agent/web/activity.ts` 也只存这三个字段。它知道“在跑/在等”，不知道“在跑什么”“等你批准什么”。t03 决定 13 的画法要的是具体的“正在整理读者评论……”“等你批准：写入 xx”。
为什么是问题：照字面实现，实现者只能写死“正在……”“等你批准”两个空壳，或临时去订阅每个 bot 主对话的 frames 取阶段与审批摘要（列表里每个联系人一个订阅，bot 多了就是常驻订阅，且 bot 主对话是否在本窗口订阅过也不确定）。这是新数据源，不是“已经知道”。
另一处遗漏：t03 评审板 r2/drawer 与 r5 里“资料收集 运行中”这类子代理的状态是挂在父会话下的；决定 13 把子会话挪进聊天头的子代理入口，但“bot 在跑”常常是子代理在跑、主对话本身空闲。按 `sessionId` 精确匹配会漏掉这种情况；`ActivityItem.root` 才是按会话树归并的字段（`activity.ts` 的 `running` 就是按 `root` 数的）。
如何核实：grep `ActivityItem`；读 `activity.ts` 全文 51 行。
建议改法：先定第二行文字的来源再写：要么第二行只写通用状态（“在跑”“等你处理”，不写具体内容，并改 t03 决定 13 的画法，交开发者确认），要么给 `ActivityItem` 或另一条轻量通道加一行摘要字段（后端改动，要进切片）。匹配用 `root === sessionId` 而不是 `id === sessionId`，并说明主对话空闲、后代在跑或在等时第二行写什么。

### 2. `last`：“补数已经按页倒读，只多取一个字段”不成立；已读完的 bot 没有最后一句话
严重程度：阻断。类别：依赖的机制不存在 / 边界。位置：计划“列表的最后一句话”；`bots/backend/unread.ts` `#catchUp`（约第 125 行）、`markSeen`；`nb-harness/src/kernel/session/session.ts:388` 的 `log`。
现象：
1. 补数读法是 `session.log({afterSeq: after, limit: PAGE})` 从“看到”的位置正向翻页；内核 `log` 只有 `afterSeq`，没有倒读（`host.ts:279` 签名）。没有“倒读”可用。
2. 补数从 `seenSeq` 之后读，只收集 `seq > seen` 的计数消息。用户读完一切（最常见的状态）时，读到的是空，`last` 只能是 null：重启后所有已读 bot 的第二行是空的。在线跟踪也只在新帧到达时才有值，所以也只对“进程启动后新来的”有。
3. 想“读 seenSeq 那一条”也不行：`markSeen` 记的是 `min(through, latest)`，`through` 是前端 `shownSeq`（已应用的最后一条任意日志），可以落在两条计数消息之间（例如夹在中间的工具事件），`seenSeq` 不一定是计数消息的 seq。
4. 无界读：`seen=0`（从没看过）时补数要翻完整个日志；加 `last` 若改成从头扫，已读 bot 每次启动都要整本扫。
5. 摘要取法没定：`assistant` 事件的 `content` 是 `ContentBlock[]`（`text`/`thinking`/`image`/`imageRef`，`nb-harness/src/kernel/api/model.ts:44`），“正文前 80 个字符”要只取 `kind: "text"` 并拼接；回复以 thinking 开头、只有图片（或 `stopReason: "length"` 被截断）、markdown 标题与 `<system-reminder>` 之类都没规定；“80 个字符”按 UTF-16 单元切会劈开代理对（emoji）。
如何核实：读 `unread.ts` 的 `#catchUp`；读 `session.ts:388`；构造“全部已读后重启”的真实用例，`list()` 的 `last` 为 null。
建议改法：把 `last` 和“看到”存在同一份 `bots-seen` 记录里（`markSeen` 时，跟踪器手里有这条消息，可顺手写 `last`，记录版本加字段）；补数只负责“看到之后”的那一段，`last` 取这一段最后一条，段为空时用记录里存的。或者给内核 `log` 加倒读，但那是内核合同改动，代价更大。摘要规则写进 Spec：只取 text 块、折叠空白、按码点切、没有 text 时用占位（如“[图片]”）。

### 3. 宿主的 `owner` 只在 `open()` 里读一次：重开、读失败和读到之前三处档位错位
严重程度：重要。类别：隐含的共享状态 / 失败路径。位置：计划“一个聊天区，档位跟着会话走”；`session-host.ts` 的 `open`（约 990 行）、`openHere`、`createSession`、`borrow`（约 2000 行）、`restore`。
现象：
1. `Current` 在每次 `openHere` 里重建（`current = target`），`owner` 若只在 `open()` 里读、传给 `openHere`，那么不经 `open()` 的入口都丢它：`borrow()` 在放开订阅（`closeCurrent()` 把 `current` 置 null，30 秒后）之后重新借用时走 `void openHere(sessionId.value)`，没有 owner，bot 会话会以通用档重新打开（出现归档、分支树、编辑、`/new`，发话不带 `settlePending`，有同步审批时向导会顶替输入框）。`restore` 与 `createSession` 也是 `openHere` 的调用方。`closeCurrent` 到下一次打开之间 `current === null`，`interaction` 按 `current.owner` 算也会变成通用档。
2. 读会话头失败时：现有 `ownerOf` 在 `header` 失败时交回 null（`plugin.ts:333`），按计划这会静默变成“无归属”，bot 会话以通用档打开，是失败时放宽限制，方向反了。阶段 ① 的实现审查处理（前端 7）为“揭示失败用户点了没反应”加了兜底，现在这条兜底在计划里没了替代。
3. “会话头读到之前（owner 未知）界面按哪个档画”计划没写。`open()` 里先 `await header` 再 `openHere` 的话，等待期间列表高亮、聊天区仍是上一个会话，没有加载态；若改成先开再补 owner，则这一段是通用档。
4. 快照里没有 `owner`（`SessionSnapshot` 无该字段），所以不能指望 `applySnapshot` 顺带给；`header` 是单独一次 RPC，每次打开多一个串行往返。
如何核实：读 `borrow()` 与 `closeCurrent`；`remote.header` 的定义在 `shared/remote.ts:240`。
建议改法：`owner` 存在宿主上（按会话 id 缓存一份 `Map<id, SessionOwner|null|"unknown">`），`openHere` 一律从缓存取，未命中再读头；读头失败按“加载失败、可重试”处理，不放宽档位；未知窗口里把交互全部置为受限档（保守），读到再放开。测试要覆盖：借用归零后重开、读头失败、读头期间切走。

### 4. 档位在视图层是静态属性，宿主只改 `ctx.interaction` 不够
严重程度：重要。类别：合同与遗漏。位置：计划“一个聊天区”“Spec 与文档改动”（`ui/agent-conversation-view.md` 用法档）；`ConversationHost.vue` 与 `FixedConversationHost.vue` 的模板差异。
现象：两档的差别不只在 `ctx.interaction`。`AgentConversationView` 上还有静态选项：`pending-placement`（bot 档 `dock`，通用档缺省 `wizard`）、`new-session`（通用档有，固定档没有）、`welcome`/`draft-profile`（通用档的第一屏，固定档没有）、`#sessions` 插槽与 `sessions-open`、`head-targets`。计划只写了 `interaction` 按 `current.owner` 算，没说这几项由谁在切换会话时切换。
为什么是问题：`pendingPlacement` 是 `props`，切会话时翻转它会让 `AgentConversationView.vue:322` 的“答完一项焦点放回”监听在两个会话的事项 id 之间比较，把跨会话的差异当成“答完了”；`new-session` 在 bot 档下如果仍显示，点了会把 bot 聊天区换成一个通用会话；bot 档在没有会话（owner 未知）时会画通用的第一屏。ui spec 的用法档表写的是“选项与 ctx 的取值”，按会话切换的选项在 spec 里没有来源。
如何核实：对比两个 Host 文件的 `<AgentConversationView>` 属性；读 `AgentConversationView.vue:311-330`。
建议改法：让这几项由 `ctx` 导出（例如 `ctx.interaction.placement`、`ctx.interaction.canCreate`），视图从 `ctx` 读而不是靠宿主组件的静态属性；`pendingPlacement` 翻转时清掉停靠区焦点监听的状态。用法档表补“按会话切换时哪些随会话变”。

### 5. `SessionOwnerProvider` 缺少从 `BotChatView` 搬走的那几种状态
严重程度：重要。类别：接口与合同 / 遗漏。位置：计划“归属插件的贡献”“没有模型、取不到主对话”；`bots/web/BotChatView.vue`（五种状态）、`bots/view.md` 输出 2。
现象：`BotChatView` 现在处理：没有模型引导卡（`noModel`，带“去添加服务商”按钮）、“还没读到有没有模型”时先等（阶段 ① 前端 4 的修正）、bot 列表读不到与列表为空的原因加重试、取主对话失败的原因加重试、`asking` 计数让较晚的结果作废。计划说“聊天区画现有的‘没有模型’引导”“聊天区写原因与重试”，但聊天区属于 `nbook.agent` 的 MessagesHost，它不认识 bots：
- 合同里没有 `noModel`、`listState`（加载中/失败/空）、`reload`、`openProviders` 这样的通道，引导卡的文案还在 bots 的 i18n 里（`useBotsText`）。
- `open(ownerId)` 并发没有作废规则：点 bot A（`ensureMain` 在途）再点会话 X，`host.open(X)` 之后 A 的结果回来再 `host.open(A 的 sessionId)` 抢掉用户后来的选择。现有 `open()` 的 `routing` 只管读头之后的阶段。
- 删掉 `BotChatView.dom.test.ts`（126 行 5 条）等于这些失败路径没有测试了，计划的验收映射里没有顶上的。
- 原来“打开视图自动取主对话”变成“点联系人才取”，`bots/view.md` 输出 2 与状态表要整体重写，计划只写“改写成 bot 标签与归属提供者”。
- 没写 bot 标签联系人的排序（按 `last.at`？），多个贡献方时的先后（按贡献 id 排？），多个贡献方里 `ownerId` 重名时 `open(ownerId)` 怎么路由。

### 6. 贡献接收器不是响应式的；`contacts` 里的 `owner.plugin` 可被贡献方伪造
严重程度：重要。类别：隐含的共享状态 / 合同。位置：计划“归属插件的贡献”；`agent/web/plugin.ts:322-341`（`openers` 与 `ownersReceiver`）、`agent/shared/contracts.ts:186-199`。
现象：
1. `openers` 是普通 `Map`，`published`/`revoke` 往里写不触发任何依赖。现在它只在点击时被读，所以没问题；改成“bot 标签列所有贡献方的 `contacts`”和 `badge()` 合计后，MessagesHost 与 `views.badge()`（外壳响应式读它）都要依赖“有哪些贡献方”。贡献方（bots 入口）与 agent 入口各自 `onStartup` 激活，先后不定：bots 晚到时，bot 标签为空且不会自己更新，`badge()` 也不更新，直到别的状态变化。撤回（插件被禁用）时同样列表不收。
2. 贡献点原本的安全性来自“只有归属插件自己接得到它的会话”（`owner.plugin` 与 `handle.plugin` 对）。现在联系人自带 `owner: {plugin, id}` 和 `avatar`、`name`，宿主“按 owner 在 contacts 里找”身份：第三方插件（点校验只限浏览器入口与 id 前缀）可以交一个声称 `owner.plugin = "nbook.bots"` 的联系人，冒用名字与头像，或者抢占 `open`/`seen` 路由。
如何核实：把 `ownersReceiver` 换成测试里先交付 agent、后交付 bots 的顺序，看 `contacts` 的消费方是否更新；第 2 点读 `sessionOwnersPoint.validate`，它不看联系人内容。
建议改法：`openers` 用 `shallowRef` 持有，MessagesHost 与 `badge()` 都经计算属性读；`OwnerContact` 去掉 `plugin`，宿主用 `handle.plugin` 盖章（与 `agent.sessionOwners` 原来的“门面按调用方盖章”同一规则，`sessions.md` 输出 23）；同一 `handle.plugin` 下多个贡献的合并规则写明（计划只在阶段 ① 审查里留下“按贡献 id 存，按插件找第一条”）。

### 7. 标签与当前会话谁说了算；没选会话时聊天区画什么；刷新后 bot 聊天不恢复
严重程度：重要。类别：遗漏 / 反常之处。位置：计划“消息视图”“一个聊天区”第 5 条与 restore；`session-host.ts` `restore` 与 `openHere` 里的 `deps.recent.write`。
现象：
1. “记住上次停在哪个标签，存插件存储”把标签做成独立偏好，当前会话是宿主状态，二者可以不一致：bot 标签上聊天区是通用会话（从状态栏活动条点进了通用会话、`nbook.agent.new-session` 命令新建、点子代理卡片进了子会话），或会话标签上聊天区是 bot 主对话（点 `nbook.agent.focus-session` 打开 bot 的会话）。列表的高亮取 `host.sessionId`，会出现“标签是 bot、高亮在会话列表里的一行”的错位。没有规则说标签跟不跟着 `current.owner` 走。
2. 没有选中会话（刷新后、新装、选中的会话被归档）时：聊天区是通用宿主的第一屏（最近对话、Profile 起手式、第一次发送自动新建 `createOnce`），放在 bot 标签下就是个通用输入框，发话会新建一个通用会话，与 bot 标签毫无关系。
3. 计划自己写“归属会话不写最近的会话”，又写“`restore` 遇到有归属的会话不再清记录，照常恢复”。`recent` 对归属会话不再写，所以刷新后 bot 聊天永远不恢复（阶段 ① 刷新后回到同一会话，`bots/view.md` 验收 1 的前提；plan-2 没有替代）；需要每个标签各记一个“最近选中”，或 bot 标签默认选第一个联系人。
如何核实：看 `openHere` 里 `if (deps.fixed === undefined) deps.recent.write(id)`；`ConversationHost.vue` 的 welcome 逻辑在 `messages.length === 0` 时显示。
建议改法：标签派生自当前会话的 `owner`（用户点标签只是改“列表看哪一页”，不换聊天区），空状态按标签给：bot 标签没选联系人时画“选一个联系人”的空态而不是通用第一屏；`recent` 各标签各存一份，恢复按标签取。

### 8. 计划只处理右栏的视图；编辑区页面、状态栏活动条、子代理卡片、请求页等入口没有着落
严重程度：重要。类别：遗漏 / 被破坏的既有约定。位置：`agent/web/plugin.ts`：`hostAt("page")`、`FOCUS_SESSION_COMMAND`（约 777-787 行）、`NEW_SESSION_COMMAND`、`reveal()`、`openElsewhere`；`agent/conversation.md` 输出 53 的 `focus-session` 一句、输出 44 “编辑区页面的对话头照旧画在内容里”。
现象：转交整体拿掉后：
1. 编辑区页面（`CONVERSATION_PAGE`）仍是 `ConversationHost.vue` 加会话下拉，下拉里 `SessionPanelHost` 列的会话含 bot 主对话（见下一条）。点了它，`open()` 不再转交，宿主按 `owner` 开成 bot 档，但页面没有 `contacts` 身份、没有 `seen`，顶栏写的是 Profile 图标与会话标题，也没有“消息”标签——一个页面里的半成品 bot 聊天。计划没说页面是否也换成 MessagesHost。
2. `nbook.agent.focus-session`（状态栏活动条、请求页的“打开会话”、`openElsewhere`）先 `ownerOf`→`open` 转交，再 `reveal()`+`host.open`。转交删掉后它要揭示的是“消息”视图并把标签切到 bot 或会话，再选会话；`reveal()` 里 `lastPosition === "page"` 时返回页面宿主，焦点会去页面。计划没写这条命令的新行为，`conversation.md` 输出 53 与 `bots/view.md` 输出 5、验收 2（“从状态栏的活动条目点主对话，揭示的是 bot 视图”）都要重写。
3. 在 bot 聊天里点子代理入口/子代理卡片，`session.select` 会就地把聊天区换成子会话（通用档），而阶段 ① 是在通用视图开子会话、bot 聊天原地保留。现在 bot 聊天被顶掉，回去只能靠面包屑或重新点 bot；`ancestors` 的面包屑里父会话写的是会话标题而不是 bot 名。计划没写“从子会话回主对话”的路径，也没说子会话是否要继续用 `pinned` 语义。
4. `NEW_SESSION_COMMAND` 在 bot 标签下：`host.create` 在 bot 标签里新建通用会话（同上一条标签错位）。
如何核实：读 `plugin.ts` 里 `FOCUS_SESSION_COMMAND`、`reveal`、`hostAt` 与 `conversationComponent("page")`；对照 `bots/view.md` 输出 5。
建议改法：列一张“入口表”（命令、页面、卡片、请求页、状态栏）各自的新行为；子会话从 bot 聊天里打开时的返回路径要写；页面位置要么不显示 bot 会话（下拉过滤，见下一条），要么也用 MessagesHost。

### 9. 会话标签会列出 bot 主对话及其子代理，与“子会话不挂在列表里”冲突
严重程度：重要。类别：与已定设计一致 / 遗漏。位置：计划“列表”“会话标签：现有的 AgentSessionPanel”；`agent/web/session-list.ts`（`items` 计算）；`SessionIndexEntry.owner`（`nb-harness/src/kernel/api/storage.ts:31`）。
现象：`list` 的条目带 `owner` 字段，但 `createSessionList` 的 `items` 对 `owner` 没有任何过滤。现在 bot 主对话（`bot-lyra`）会出现在会话面板里，它的子代理会话（`caller` 是主对话，`parent` 被挂上）作为它的子行展开。阶段 ① 点它靠转交绕到 bot 视图，所以问题被盖住。转交去掉后：点这一行在会话标签下就地开成 bot 档，高亮与标签错位（第 7 条），行菜单里还有“归档”“改名”（`act` 的 `session.archive`/`session.rename` 不受 `FIXED_COMMANDS` 约束，后端对 owned 会话 `refuse: "owned-session"`，用户看到失败）。t03 决定 11/13 明确 bot 的子会话不挂在列表里，进聊天头的子代理入口。

### 10. 抽屉“用 nb-ui 的 Drawer”：它是整页模态，不是视图内的抽屉
严重程度：重要。类别：依赖的机制与计划描述不符。位置：计划“技术选型”“版式”窄版；`nb-ui/src/components/feedback/Drawer.vue`、`composables/useTeleportTarget.ts`。
现象：`Drawer` 传送到 `body`，遮罩是 `fixed inset-0` 加 `backdrop-blur`，内容 `inset-y-0 left-0 w-[380px] max-w-[90cqw]`，`modal` 缺省真（锁整页焦点与指针）。t03 评审板 `r2/drawer.webp` 是在右栏里从左边拉出的、压在聊天上的一块，宽约列宽的 70%。按默认用法，抽屉会从浏览器窗口左缘（活动栏、侧栏之上）弹出，宽 380 像素（比默认右栏 400 像素的 90% 还宽），整个工作台被虚化、失去交互。唯一收进视图的办法是 `provideTeleportTarget(selector, {contained: true})`（现在只有组件 Lab 用），目标要有 `contain: layout` 与尺寸容器，选择器要指到“这个视图的根”且多开视图（t03 决定 7 的后续）时要唯一。

### 11. “容器查询加 `useLayoutExtent`”：这个组合在 nb-agent-ui 里拿不到；先例也不是这样做的

### 12. 宽窄切换会重挂聊天区、列表开合是同一个状态；底部面板宽而矮
严重程度：重要。类别：边界 / 隐含的共享状态。位置：计划“版式”“按面板头的标题收起、展开列表栏 / 拉出抽屉”。
现象：
1. 宽版（左列表栏加聊天区）与窄版（头像列加聊天区加抽屉）若是两套模板（`v-if` 切换），聊天区在分界两侧会被卸载重建：滚动位置、输入框焦点与撤销栈、停靠区状态丢失（宿主的草稿虽留着，`AgentConversationView` 内部的滚动跟随、焦点、展开状态没有）。还有：`useLayoutExtent` 首次挂载前是 null、区域被拖到零时是真实的 0（源码头部注释区分这三态），“停放”本身是 `visibility: hidden` 且保留尺寸（`NestedGrid.vue:399`），不会量成 0；但 null 与 0 这两个值落进“窄”会造成一次挂载时的误判再重挂，所以仍要规定这两态保持上一次的版式。
2. “列表开着没有”只有一个布尔：宽版默认开（列表栏常驻），窄版默认关（抽屉）。用户在宽版收起列表后把右栏拖窄，一个值会让抽屉在拖动途中意外弹开或相反；需要两个独立状态，并规定切分界时抽屉打开中怎么办（输出 44 要求 Esc 关后焦点回标题，宽度变化时这个焦点去哪里没写）。标题按钮的 `aria-expanded`（`titlePopup`）宽版是“列表栏展开”，窄版是“抽屉”，两种语义共用一个属性。
3. 分界只看宽度。底部面板里的视图宽而矮（例如 1000×220），也会进两栏版，聊天区只剩不足 150 像素高；`views.md` 输出 19 的下限还是按宽度算的。
4. 600 像素的依据：右栏默认 400 像素下是窄版，用户拖到 600 以上才是宽版，这条“待确认”开发者已答，不再评；但两栏版里聊天区最小宽度没有写（600 减 260 只剩 340，状态栏与输入框的窄档在 AgentConversationView 里是自己的容器查询，两层容器查询叠加没有验证）。
如何核实：读 `useLayoutExtent.ts` 头部注释；让右栏宽度来回过 600，观察聊天区是否重挂（`data-` 标记加 mount 计数）。
建议改法：聊天区只有一份 DOM，版式由 CSS 容器查询与定位切换，不用 `v-if`；两个开合状态各记各的；宽度为 0 或 null 时保持上一次的版式；分界条件加高度下限，或底部面板一律走窄版。

### 14. `replaces`：依赖方向倒置、绝大部分用例不存在、没有防误删规则

如何核实：`git tag --contains 0fcdedc83`；读 `reconcileViews` 与 `layout-doc-store.ts:117`；`nbook.agent.sessions` 声明在 `agent/web/plugin.ts:94`（`container: PROJECT_VIEW_CONTAINER`，它和资源管理器同属一个容器，不是唯一成员）。
建议改法：去掉 `nbook.bots.chat`；`replaces` 缩成“同插件前缀、目录里无声明才生效”，或者更简单：不加机制，把 `nbook.agent.sessions` 的占位留给用户关（`views.md` 输出 7 已规定可关闭），并在变更记录写一句。若坚持加，砍掉第三条，写清早退与各种位置的删法并加 dom 测试。

### 19. “不做与风险”逐项判断；`pinned` 与固定会话组件留成没有调用方的代码
严重程度：建议。类别：别扭之处。位置：计划“不做与风险”“一个聊天区”第 3 条。
逐项：
- 不做：会话标签滚到底分页：可以不做，但“一次取全部”会随会话数无界增长（`list` 没有分页），消息视图常驻右栏比旧会话面板（按需打开）更常加载；至少在窄版头像列只取最近若干条。
- 不做：多开（t03 决定 7）：成立。书房入口（③）、按天与未读分隔线（④）：成立，但 ③ 要用的 `pinned` 现在没有调用方（见下）。
- 风险“宿主档位改成按会话定，11 处读 `deps.fixed`”：低估。除 `session-host.ts` 的 8 处 `deps.fixed` 与 `fixed` 派生值外，还有视图层的静态属性（第 4 条）、`borrow()` 重开丢 owner（第 3 条）、`agent.sessionOwners` 接收者（第 6 条）、`FOCUS_SESSION_COMMAND` 与页面位置（第 8 条）；“阶段 ① 的固定会话测试照新档位改写，不放宽断言”应改成列出每条被改写的测试和对应新断言。
- 风险“e2e 迁移面大，先改辅助函数”：成立（和 `e2e-handles-before-wide-run` 的经验一致）；还要先列每个辅助函数依赖的旧选择器（`data-bot-chat*`、会话面板在侧栏的位置），因为删 `BotChatView` 与会话视图时这些钩子一起消失。
- `pinned` 与 `agentConversationKey.FixedConversation`“保留，阶段 ② 没有调用方”：阶段 ② 把它留成没有调用方、但仍要随宿主改动维护的分支（`openElsewhere`、`createSession` 的守卫、`restore` 的分支），测试要么继续跑一份没有真实调用方的用例，要么没有测试。倾向：阶段 ② 里整个删掉固定会话组件与 `pinned`（只留宿主按 owner 定档），阶段 ③ 要滑出聊天时再按那时的需求加，不推测未来；或者至少注明 ③ 的哪个决定要求它保持这个形状（t03 决定 22、23 只说“头部与内容同消息视图的聊天”，没有要求“固定到一个会话”）。
建议改法：同上各条。
