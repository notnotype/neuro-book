### 1. 一个消息视图的版式问题被放大成改工作台骨架，并且是在重开 w00026 t27/t28 已经否决过的“右栏右边一条活动栏”
结论：界面不满是真的（开发者原话 1、2），但“侧轨归区域、骨架变成 轨|侧区域|编辑区|侧区域|轨、右栏入口搬进轨”不是消息视图问题的根因解，而是把一个视图的诉求上推成全局结构。
依据：
- w00026 t27 的评审题 strip-1 的选项丙就是“右栏右边一条活动栏（照‘和 ActivityBar 一样’另画的）”，评审说明写它“作为树上的条有提案里查出的六处冲突”（.agents/works/w00026-layout-package/tasks/t27-region-entry-strips/README.md:30）；开发者 11-16 在 strip-3 选了甲“卡片顶上一行”（同文件:58）。ADR 0046 末行把同一件事留给“第二步另行设计”（docs/adr/0046-workbench-view-containers.md:42），docs/proposals/workbench-view-containers.md:78 列了六处冲突（条两侧的缝不能拖、区域拖不到零、放不下时只收面板不收条、校验写死两个条、默认右栏多一行重复标题等）。
- 活动栏现在是树上的节点：骨架是 `V[H[活动栏, sidebar, V[编辑组, panel], auxiliarybar], 状态栏]`（workbench-layout.md:97），ADR 0044 决策 1“活动栏…都是树上的节点”。第二条“轨”若也是树节点，上面六处冲突原样回来；若不是树节点，是区域外壳的一部分，草案没写，而这正是最该先讲清的取舍。
- 反复撞同一结构的信号：右栏入口条已经改了两轮（t27 乙到甲），现在又要换朝向。按全局规则“质疑上游选择”，应追问的不是“轨怎么实现”，而是“视觉上的需求能不能不动骨架满足”。
底层选择（“消息视图是塞在 400 像素右栏里的 IM 应用，要在宽窄两种版式之间切”）的理由：conversation.md 输出 51 与 AgentMessages.md 只写了版式规则，没有写为什么放右栏；没有记录的理由。
建议：先出一稿“头像列留在视图内部、不画竖线、底色比聊天区深一档、不通到顶”的真实页面对照（工作量小），让开发者确认“通到顶且在卡片外”是硬要求还是偏好，再决定是否值得改骨架。开发者原话 3 的不满是“竖线太生硬”，并没有说“必须在卡片外”。

### 2. 轨的中段是视图内容经 Teleport 进工作台外壳，且按条件出现，形成两条绘制路径与一个不稳定的轨
依据与影响：
- 草案：中段只在“区域此刻只显示一节、视图就绪时”给；浮动窗、底部面板、区域里不只一节时 slots 为 null，视图“在自己的内容里画头像列”。也就是同一组头像、未读点要维护两套摆法：轨里一套、内容里一套（AgentMessages.md:12-14 已有的头像列加这份），测试与视觉对齐要做两遍。
- 轨的宽度、内容随“右栏里是否恰好一节”这类布局状态跳变：用户把别的视图拖进右栏同一容器，轨中段消失、头像列就回到聊天区里，聊天区左右突然挪 48 像素。这与 spec 里“一个容器一张卡片”“切换时入口条不动”（workbench-layout.md:19、47、42）追求的稳定性冲突。草案没讲这个过渡。
- 对照现有先例 ViewHead（contracts.ts:403-440）：标题区是“一个固定位置、一个固定形状”，所以 Teleport 合适；轨中段是“一串可交互的项”（头像、未读点、最近 5 个会话，要 roving tabindex、F6 停靠站、读屏、拖动判定），把活的 DOM 交给外壳，键盘与读屏顺序（spec 输出 18、31）就要同时认视图内的元素。VS Code 活动栏、JetBrains 工具窗条都是声明式条目（图标/徽标/选中/菜单），外壳自己画，视图只给数据。若坚持要轨，建议条目声明式（`{id, image|icon, badge, selected, menu}`），不用 Teleport；消息视图的数据本来就只有这几项，不需要共用组件树。我只能说这是业界常规，没有查到本仓库里为什么 ViewHead 选 Teleport 的理由之外的约束（t36 决定里写的是“共用状态、注入与错误边界”，对头成立，对一串条目不明显成立）。

### 3. primarySide 设置与“布局只有一棵树”两处真相源
依据：ADR 0044 决策 1：一棵树、规范形；spec 输出 1“任何操作之后树都合这个骨架：活动栏、侧栏这一列、中间、右栏这一列从左到右”（workbench-layout.md:97）。草案写 `nbook.workbench/primarySide: left | right` 对调两个侧区域，并称“轨总贴窗口外缘”。
问题：
- 对调存在哪？若写进设置而树不变，渲染层做镜像，则“从左到右”的骨架判定、分隔线与拖动落点的左右含义、键盘方向键（输出 31 的“方向键逐个位置移动”）、F6 顺序、相连与“角接到活动栏”的圆角动画（输出 19、42，写的是“侧栏右边的两个圆角”）全要按镜像再算一遍；摆稿用的“整个外壳水平镜像再把内容翻回正向”只证明画得出来，不证明这些规则成立。
- 若改成树操作（交换两个区域的位置），则是一次提交、写回布局文档，符合“工作台是唯一写者”，也不需要设置键；但 ADR 0046 后果写明布局记录不加版本号、旧记录“回落默认布局并覆盖”，骨架合法性一旦改变又会覆盖用户布局，需要写明这次是否再来一遍。
- VS Code 的 `workbench.sideBar.location` 是业界先例（主侧栏连同活动栏换边，次侧栏不带活动栏——这点我记得但这次没有联网复核，标为“记忆，未核实”）。可借鉴的是：对调只换主侧，不要求两边对称。
建议：对调当成独立提案、独立 Task，不绑进消息视图的优化；做的话优先“树上的一次交换命令”，不引入第二个真相源。

### 4. YAGNI 与没有证据的设计
- **对调左右侧区域**：开发者确实提了（原话 3），但他问的是“是否要为这种模式提供支持”，不是“必须做”。目前唯一消费者是消息视图；没有证据说明对调是消息视图的前提。同条 3。
- **ViewRail 的 main/foot 两段 + 主侧轨再加全局项**：三段结构（容器入口 / 视图自己的项 / 底段）里，“视图自己的项”只有消息视图一个消费者，“底段”只有“全部 bot”“会话历史”两个按钮。为一个消费者设计两段通用接口，等第二个消费者出现再抽象不迟；草案自己也写了“先不进插件 SDK”，说明作者也不确定通用性。
- **右栏的容器入口搬进轨**：右栏现在的横向入口条（输出 47）刚在 11-16 定稿，实现与 e2e 才合入不久。搬走的收益只有视觉一致，代价是右栏与底部面板入口条朝向不同（草案写“底部面板保持横的入口条”）：输出 45、46 的落点指示、输出 42 的切换动画（右栏现在是横着滚）、输出 47 的“并进头那一行”都要分两种朝向写。
- **没有证据的部分**：没有任何一处写出“头像列在卡片外”相对“在卡片内无线”的用户可观察差别，只有开发者对稿面的审美反应；也没有量过窄版聊天区约 340 像素是否因多出 48 像素的轨再挤掉一块（现在窄版聊天区约 340 像素，右栏默认 400 减去 52 的头像列；轨变成 48 且在卡片外时净宽基本不变，但右栏卡片的外缘与内边距多占几像素，spec 对窄版聊天区没有写下限，应量一次）。这是应补的数据：轨加进来后聊天区的净宽。

### 5. 草案讲了实现细节，没讲该拍板的架构取舍
object.md 的“当前草案”大篇幅给了 ViewRail 的 TypeScript、Teleport、48 像素、F6 停靠站，但下面这些取舍一句没有：
1. 轨是树上的条节点，还是区域外壳的附属？（决定是否撞上 ADR 0046 的六处冲突；见 1。）
2. 区域隐藏时轨是否仍占 48 像素？右栏默认隐藏时（workbench-layout.md:97 “有容器的区域显示”，右栏有对话时显示）右边缘常驻一条，标题栏右上角三个开关按钮与它的关系；轨若随区域隐藏，则“轨总贴窗口外缘”和“隐藏时淡出/角接过去”的动画（输出 19）要为右侧再写一遍。
3. 视图声明的宽窄版（宿主量视图根宽 600 为界，AgentMessages.md:78）与“区域是否只显示一节”两个条件如何组合，浮动成窗口时轨去哪（草案：视图自绘，等于保留旧头像列路径）。
4. 谁拥有焦点与读屏顺序：轨在区域外，spec 输出 18 的“入口条在它区域的分节之前”如何落到“轨 | 区域”的镜像里。
5. 失败方式与成本：改 workbench-layout 输出 1、19、20、22、31、42、45–47，改 ADR 0044 的骨架句，改 nb-layout 的邻接算法（adjacency.ts）与相连圆角；按 t27/t28 的体量应先给估计。
6. 回滚：布局记录无版本号，回滚代码要清布局记录（ADR 0046 后果第二条）；这次同样适用，要在提案里写。
作者自己的“下一步”（Task README）写的是“先写提案”，方向对；建议提案正文先写这 6 条，再谈 ViewRail。

### 6. 窄版里打开完整列表：更好的交互（单独回答）
先说一个缺口：开发者否了抽屉和整页切换，但没说原因（object.md 原话 3、4 只有“不是更好的”“也不太好”）。先问清是“盖住聊天区”“多一次点击”“状态跳变”还是“列表本身在窄处不好用”，选项会不同；我不替他推断。
再说一个事实：头像列已经承担了高频切换（联系人头像 + 最近 5 个会话）。完整列表只在“找很久以前的会话、搜索、改名删除、按作品筛选”时用，是低频、管理型操作。低频管理型操作放进常驻的窄空间本来就别扭；这是推断，没有使用数据。
我确知的产品做法（标注把握）：
1. 主从导航，整页换：Telegram 窄窗口/移动端、iOS 的 NavigationSplitView 收缩态、Slack 与 Teams 手机端。即开发者已否的“整页切换”。（确知）
2. 抽屉：Discord 手机端、ChatGPT 窄窗口的侧栏、Material 的 modal navigation drawer。即已否的“抽屉”。（确知）
3. 快速切换器（覆盖层搜索，键盘优先）：Slack Ctrl+K、Discord Ctrl+K、VS Code Ctrl+P/“Show Chats”类快选面板、Linear/Notion 的 Cmd+K。小而短暂，打字过滤，回车跳转，用完即走，不占版面。（确知有此模式；VS Code Chat 的具体命令名我不敢保证）
4. 锚在头部按钮的下拉/弹出列表：Claude Code VS Code 扩展与多数编码助手侧栏的“过往对话”下拉、Cursor 旧版“Past chats”。（基本确知，细节有版本差）本仓库自己就有：conversation.md 输出 44 写了“按面板头的标题开会话列表”，t36 给 Popover 加了 `anchor`，所以不需要新组件。
5. 视图内的标签/底部条：Facebook Messenger 网页版把打开的会话收成屏幕底边一排小标签。（确知，但是桌面宽屏产品，对窄侧栏借鉴有限）
6. 把管理放到宽处：Zed 的 Agent 面板用历史按钮切到历史页（与整页切换同型）；对照产品里“完整历史”常有“在编辑器里打开”入口。（Zed 确知；“在编辑器打开”作为通用做法我只确知部分产品）
我的推荐（不是定论）：窄版不开“列表”，开“切换器”。点“会话历史”在轨旁弹一个以内容为高、宽度可压到聊天区内的浮层：顶部搜索框自动聚焦，下面是最近会话，当前作品筛选一个下拉；回车/点击选中即关，Esc 关。重命名、删除、跨作品浏览走右键菜单，或点“在编辑区打开完整列表”，那里宽度够，复用 AgentMessagesList 宽版，零新组件。理由：和抽屉的区别是它按任务大小，不盖住大半聊天区、不换页，也不需要“再点一次回来”；它与整页切换的区别是不产生“我在哪一页”的状态。风险：浮层仍遮挡聊天区下半，触屏窄宽上点击区要够大；需要开发者看一稿再定。
