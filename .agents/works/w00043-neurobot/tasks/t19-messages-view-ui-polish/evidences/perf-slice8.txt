== resize 剩下的差额：版面宽度造成，不是多做的工作 ==
1. 只跑 still 与 resize（3 轮，负载约 10）：基线 recalc 10.00、mutations 51.0；分支 10.00、48.0。分支自己的写入更少。
2. 按全量顺序跑 tree-scroll、sidebar-sash、resize（3 轮）：基线 62.6，分支 72.0，每轮数字完全一样，不随负载。
   来源对比（20 次改宽的合计）：
     childList BODY                     140 → 280
     childList SPAN.markdown-color-button 30 → 60
     childList 工具条列表                  0 → 40（右轨）
     childList 入口条列表                 120 → 80
     其余各项相同或分支更少
   BODY 下增删的是文本与注释节点（Vue 片段的锚点），来自编辑器 Markdown 工具条按宽度收放按钮。
3. 量宽度：分支的右栏一列宽 373（基线 316，多出右轨 48 与缝），第二个编辑组的工具条在 1300 与 1440 两档分别是 329/469（基线 381/521）。
   工具条更窄，两档之间跨过的按钮收放门槛更多，每次改宽多重画几颗按钮。右轨这一列是计划“关键设计”里定的版式（右栏外侧插右轨叶）。
结论：resize 超出的 9.5 条与 1 次样式重算来自编辑区变窄后工具条的收放，不是右轨或布局层多做的工作；判为通过，不再改。
其余已有场景都在 110% 以内（sidebar-sash 100%，float-dock 104%，其余持平或更少）。

== 记下的事 ==
- MutationObserver 计数会把同值的 setAttribute 也算进去；排焦点、同步属性这类每帧都跑的写入要先比较再写。
- resize 的写入数随前面场景留下的状态变（开着的编辑器工具条），对比时要按全量顺序跑、并拆来源，单看总数会误判为回归。
