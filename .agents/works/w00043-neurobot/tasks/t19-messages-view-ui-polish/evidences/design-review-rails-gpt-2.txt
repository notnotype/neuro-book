## 新发现

### R2-1

- 严重程度：高
- 类别：布局标识 / 校验
- 位置：`docs/proposals/workbench-side-rails.md` 第 69 行；`packages/nb-workbench-layout/src/layout-doc-validate.ts:25`
- 现象：提案称右轨投影叶使用固定 id `rail:auxiliarybar`，但现有 `collidesWithPresentedIds` 不保留该 id；我用合法默认布局把根树节点 id 改为 `rail:auxiliarybar` 后，`validateLayoutDoc` 仍返回有效。投影添加右轨叶时便与用户树节点重复 id。
- 影响：重复 id 会使布局节点查找、尺寸映射和渲染身份不再唯一；输入被当前记录校验接纳，不能依赖存档校验挡住碰撞。违反提案自身的“进 `collidesWithPresentedIds`”要求。
- 核实方式：在仓库根执行 `bun -e` 导入 `defaultLayoutDoc`、`validateLayoutDoc`，将 `doc.tree.root.id` 置为 `rail:auxiliarybar` 后验证；结果 `validOldDoc=true`、`rootId=rail:auxiliarybar`、`wouldDuplicate=true`。
- 建议：实现时把该合成 id 纳入呈现保留 id 校验，并覆盖根、分支、叶、面板 id 与归档读入；或采用不能与合法用户 id 冲突的 id 生成机制。

### R2-2

- 严重程度：高
- 类别：布局约束 / 极窄窗口
- 位置：`docs/proposals/workbench-side-rails.md` 第 81、84 行；`packages/nb-workbench-layout/src/layout-project.ts:252`
- 现象：开发者选择明确要求先压右栏聊天区到 320px，再决定展开是否可行；提案的第 81 行先压右栏，却未规定怎样临时越过当前视图约束。现有 `minimumOf` 只从投影约束读取面板最小尺寸；按当前 160px 最小值，固定布局宽预算 700px、编辑组最小 220px、右栏当前 400px、轨从 48 展到 260 时，分配得到 `[220,220,260]`，消息聊天区跌到 220px，小于开发者选定的 320px；若维持 320px 下限，同预算分配结果为 `[192.5,280,227.5]`，编辑组或轨都无法满足其目标。提案未给出跨分支预算求解/强制聊天下限的机制，已有 `presentationCollapse` 只按普通布局最小值收面板，不解这个展开预算。
- 影响：照已有单一网格分支与声明最小值实现，会违反聊天区下限；抬高右栏永久最小值会令收起状态和窄窗降级也被 320px 卡住，与“先压到最小、仍不足不展开”冲突。风险不是单纯实现参数，需要明确只在展开求解时使用的约束与编辑组补偿路径。
- 核实方式：用 `allocateSashPanels` 探针输入编辑组、右栏与轨三项并排、宽度预算 700，分别设置右栏最小值 160 与 320；输出为 `[220,220,260]` 与 `[192.5,280,227.5]`。现行右栏单节最小值由 `layoutProjectionOptions`/视图目录供给，轨则按提案在投影里另加一叶；两者不处于同一现有父分支。
- 建议：在实现前补全“展开轨”的整体宽度求解合同，说明如何从跨分支几何中扣预算、临时把聊天区压到 320 且不改普通布局意图；明确预算不足时保留 48px 收轨并拒绝展开。若要改视图最小值，应限于该呈现模式，避免污染收起、常态与拖放。

### R2-3

- 严重程度：中
- 类别：持久化 / 文档往返
- 位置：`docs/proposals/workbench-side-rails.md` 第 102–103、145 行；`packages/nb-workbench-layout/src/layout-doc-validate.ts:89-123`；`packages/nb-workbench-layout/src/layout-doc.ts:1119`
- 现象：提案把 `rail` 写到锚面板与浮动窗记录，要求旧版文档读入、旧未知字段原样写回，并把轨状态纳入形状比较；当前校验虽保留未知字段，但 `sameLayoutShape` 对面板记录只比显式字段，未知 `rail` 变化会被判成形状相同。普通锚面板的隐藏等对象展开操作会偶然保留该字段，但 `stripDynamicTabs`、`carryDynamicTabs` 这类模板/重置路径会丢锚上的 `rail`；浮动窗记录重建路径也需逐一处理，不能从校验保留推出更新全保留。
- 影响：用户只改轨展开/宽度时，若复用现有显式形状比较，状态变化可能不触发版本/保存或被操作合并吞掉；模板应用、丢弃更改或重置布局可丢失轨状态，违反“旧版本原样写回”和归位后可恢复同一轨意图的合同。
- 核实方式：探针在 `auxiliarybar` 与 float 记录添加 `rail` 后确认 `validateLayoutDoc` 接受并保留；`setPanelHidden` 与 `setFloatRect` 保留字段，而 `carryDynamicTabs(defaultDoc, customDoc)` 丢锚字段；现有 `sameLayoutShape` 的面板比较白名单不含 `rail`。
- 建议：把 `rail` 提升为显式、版本兼容的记录字段与形状比较字段；集中归一读入并仅对非法子字段给诊断。盘点所有面板/float 克隆、模板、丢弃、归位、重置、保存路径，逐条保证字段保留；对未知旧字段原样往返的要求也应和新字段语义分开定义。

### R2-4

- 严重程度：中
- 类别：视图位置 / 结构搬运
- 位置：`docs/proposals/workbench-side-rails.md` 第 102、119 行；`packages/nb-workbench-layout/src/layout-doc.ts:828-847`
- 现象：轨状态所有者按容器锚的 `containerId` 记忆，但提案又允许停靠视图的视图段由视图借用并 Teleport 到轨。用户把消息视图从右栏拖到另一个容器后，该容器可以存在于活动栏、底部或其他区域，不再天然属于 `auxiliarybar` 锚；文档未规定借用时状态归属应跟随视图还是原容器，也未规定换容器后宽度/展开态如何转移。该疑问不适用于浮窗：第 145 行已单独规定浮窗状态放在 float 记录。
- 影响：若状态随视图段但只存 `auxiliarybar` 锚，消息视图移出右栏后便无可用状态所有者；若随目标容器写入，后续搬回右栏又可能读取另一份旧状态，展开宽度和用户意图出现跳变。开发者只批准消息视图停靠在右栏或单独浮动，但提案显式以容器 id 为键，二者的结构关系需明确。
- 核实方式：现有 edge 结构操作允许拆分任意工具面板且生成的 section 符合当前布局骨架；投影中 `regionAnchors` 只为带容器的三个具名区域注册锚。提案中的状态映射以 `containerId` 为键，未写迁移策略。
- 建议：明确消息视图不可通过普通拖放离开右栏，或定义消息视图与右栏的接受约束并在所有结构提交出口执行；若允许其他容器，改为按视图身份存轨意图，或规定可预测的迁移、归并和归位规则。

### R2-5

- 严重程度：中
- 类别：浮动交互 / 输入模型
- 位置：`docs/proposals/workbench-side-rails.md` 第 145 行；`packages/nb-layout/src/vue/NestedGrid.md:225-238,261`
- 现象：提案要求浮窗右缘展开/收起时修正矩形 x、宽度并按屏幕边界夹取，同时轨内侧手柄和浮窗手柄各自只结算所属轴；然而它没有定义浮窗展开拖动的完整几何状态如何进入网格布局会话。公开 `NestedGrid` 手势事件只有 grid sash 的 start/update/end/cancel；其 `placeFloat` 只挪动拖动中的窗，不支持调整矩形宽度或将窗右侧空余预算反馈给其他兄弟。
- 影响：直接改窗口 DOM 矩形会绕开网格布局版本、原子提交和 Escape/失焦取消语义；复用 `placeFloat` 又只能位移，无法实现提案要求的宽度差值、夹取后可归位以及一次提交。当前描述不足以由现成公开交互 API 实现。
- 核实方式：查 `NestedGrid` 公开事件、expose 方法及 `GridHost` 接口；`placeFloat(id, offset)` 注释与实现只处理拖动位移，手势提交的接受路径是 `resizeBranches`。
- 建议：明确浮窗轨宽与矩形状态的独立手势事务：基线与版本冻结、连续预览、边界/归位夹取、取消与一次原子持久化；不要把网格 sash 或仅移动的浮窗 API 当作宽度手柄实现。

### R2-6

- 严重程度：低
- 类别：布局兼容 / 显式 ID 保留
- 位置：`docs/proposals/workbench-side-rails.md` 第 69 行；`packages/nb-workbench-layout/src/layout-doc-validate.ts:25,95`
- 现象：除树节点碰撞外，固定合成 id `rail:auxiliarybar` 也没有进入目前的面板 id 保留检查；合法布局的工具面板可使用同名 id，校验仍通过。即便树节点 id 被先行修复，这个面板 id 仍可与投影轨叶重名。
- 影响：轨叶和工具面板身份冲突会污染由面板 id 索引的文档记录、呈现映射与布局节点；新增树 id 禁止名单不能自动保护 `panels` 字典键。
- 核实方式：在合法默认文档新增 `panels["rail:auxiliarybar"]` 与指向它的树叶后，`validateLayoutDoc` 当前仅检查 `collidesWithPresentedIds` 是否包含该值；提案要求纳入的名单尚未改。
- 建议：与 R2-1 同一修复中覆盖树节点与 panel map key 两种命名空间，并明确发生在读入归一前还是之后拒绝；避免分别实现两套保留规则。

### R2-1

- 严重程度：阻断
- 类别：布局约束 / 极窄窗口
- 位置：提案第 81、84 行；`packages/nb-workbench-layout/src/layout-project.ts:252-277`；`packages/neuro-book/src/plugins/workbench/web/state/layout-constraints.ts:81-93`
- 现象：开发者决定要求先压编辑组、再压聊天区至 320px，仍不够就拒绝展开。提案规定次序却未说明该 320px 如何进入只影响展开请求的预算。现行 `panelConstraints` 取工作台与视图声明的最大最小值；消息视图声明未给最小宽，右栏系统下限为 160px。探针用总宽 700、轨 260、编辑最小 220、右栏当前 400：按现右栏最小值分配为 `[220,220,260]`，聊天区落到 220；临时将右栏下限设 320 时，总最小已达 800，网格会按比例降级，变成 `[192.5,280,227.5]`，反而压穿编辑组与轨宽。
- 影响：直接复用一棵 grid 与当前 constraints 会违反聊天区 320px；把右栏声明最小值永久抬到 320 又会污染收轨常态及现有窄窗降级。项目的 `presentationCollapse` 只以树中最小尺寸是否超出视口收面板，不求解“轨宽、聊天下限、编辑组余量”这组展开专属预算。
- 核实方式：已用 `allocateSashPanels` 对三项 fixed/weight 约束运行只读探针，结果如上；`panelConstraints` 与 `minimumOf` 当前实现分别见所列代码。该布局探针验证空间矛盾，不代表提案实现后的实测。
- 建议：补齐展开态预算算法与合同：如何从收着基线得出编辑组余量，如何仅在轨展开求解中把聊天压到 320px，如何保证轨最小 200px；余量不足时不改意图、维持 48px 并提示。需要跨分支求解时明确它在哪一层集中完成，不要把两个分支的局部 sash 调整当总预算。

### R2-2

- 严重程度：重要
