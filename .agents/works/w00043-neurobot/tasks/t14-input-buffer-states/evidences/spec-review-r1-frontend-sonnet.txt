# w00043 t14 对话视图部分 planned Spec 审查报告（frontend）

审查对象：提交 5cb584b1f 对 docs/specs/ui/agent-conversation-view.md、docs/specs/agent/conversation.md 的改动。以下均已对照 runtime.md 输出 103–110、提案第四节、session-host.ts、AgentConversationComposer.vue、AgentQueuedMessages.vue 核实。

### 1. 运行中还有留着的话：排队区头、发送键、占位文字、合并都没有定义，而 9 号自己的流程会造出这个状态
严重程度：阻断
类别：遗漏的状态组合 / 照字面实现会做错
位置：ui/agent-conversation-view.md“输入框与待处理区”排队区一条；conversation.md 输出 6、9
现象：Spec 只写了“有留着的条目时：头行有‘继续’，发送键是继续，空着发送发出 run.continue”，没有限定会话空闲。但留着的话在运行中是会存在的：runtime.md 输出 105 的表说宿主、会话发话只放行自己的，用户停止留下的（heldBy 是用户）不会被宿主开的运行带走；输出 106 写明“在跑时只放行”；conversation.md 输出 9 的“先 start、再在这次运行里 send{replaces}”在 start 成功、send 失败（input-stale）时，也停在“运行中、话仍留着”。
为什么是问题：照字面实现，运行中头行仍写“继续”，点了发出 run.continue，宿主按现有实现走 start，得 already-running；发送键在运行中要么是停止（空输入）要么是 steer/followup，与“同样是继续”矛盾；运行中用户写字回车走 enqueue，而 replaces 只在 send 上（输出 107），“合并”在这个状态下不可达，Spec 没说此时留着的话是否仍合并、是否被 enqueue 以 keep 放行。canStopClearing 的“缓冲区里有用户自己的话”也没说包不包括留着的。
如何核实：runtime.md 输出 105 的表、106 末句；session-host.ts 的 run.continue 现为 `remote.start`。
建议改法：写明运行中的规则，最简单的一条：运行中头行不出“继续”按钮，只写“已暂停，你下次发话时一起发出”；发送键与占位文字按运行中规则走；运行中用户发话的放行方式写清（enqueue 以 keep 放行，不合并，因为 enqueue 没有 replaces），并说明这是已知取舍；同时把 9 号的两步流程失败后的状态写进去（见发现 3）。

### 2. 占位文字与发送键的优先顺序没有跟着改；“中断且留着”是重启后的常态，却没说取哪个
严重程度：阻断
类别：合同冲突 / 遗漏
位置：ui/agent-conversation-view.md 第 332 行“占位文字按顺序取第一个”；排队区一条；conversation.md 输出 9
现象：第 332 行的顺序仍是“availability 不是 ready → composer.resume → 运行中 → 普通”，没有“留着”这一级；新增的“排队的话已暂停…”占位文字只在排队区那条里说了“这时”，没说排在哪一级。AgentConversationComposer.md 第 76 行同样的顺序（组件合同）也没提这次要改。
为什么是问题：服务端重启后，runtime.md 输出 104 与 session.md 输出 15 会把就绪的话转成留着（cause interrupted），同时 transcript.interrupted() 为真，所以“中断 + 留着”是重启后排着话的常态，不是边角。此时占位文字有两句候选（“上次运行已中断。按回车继续，或输入内容后继续”与“排队的话已暂停…”），发送键都是“继续”，但按钮标题、读屏文字、占位文字取哪句 Spec 没定；availability 不是 ready（只读）时头行的“继续”按钮是否禁用也没写（发送键有 readonly 禁用，头行是新控件）；interaction.canSend 为假时同理。
如何核实：AgentConversationComposer.vue 的 placeholder 计算属性与 sendTitle 只有 resuming 一支；留着需要新增分支。
建议改法：把顺序改成：availability 的原因 > 中断且留着时写一句合并的话（例如“上次运行已中断，排队的话已暂停。按回车继续”）> 只有中断 > 只有留着 > 运行中 > 普通；头行的“继续”在 availability 非 ready 或不允许发送时禁用并带原因；发送键标题与占位文字同源。

### 3. “先 start 再 send{replaces}”：适用范围含混，两步不是原子的，input-stale 重试会重复 start
严重程度：重要
类别：接口与合同 / 边界
位置：conversation.md 输出 9（planned 句）
现象：原文“空着按回车…；写了字…。同时有中断的运行时先接着跑它：合并时先 start，再在这次运行里 send{replaces}；另两种用户的 resume 自己先接着跑。input-stale 时重新读快照、重新合成再发一次”。
问题一：“同时有中断的运行时”接在“写了字”之后，读起来对空着和写了字都适用；但现行输出 9 是“写了字走 send”（新运行），且 runtime.md 输出 36 里 send 只能接着跑“暂停”的运行，已收口的中断运行要 start 或 resume 才接着跑。写了字时到底是 start+send（话变成运行中的插话）还是只 send（开新运行、不接着跑中断的那一轮）没写；另两种模式的“send{release: mode}”也没说是否先接着跑。
问题二：start 成功后 send 因 input-stale 失败，“重新读快照、重新合成再发一次”若字面重做整套流程会再 start，得 already-running；应只重做 send。再失败后留下的是“运行已接着跑、话仍留着”的半成状态（见发现 1），Spec 只说“把文字留在输入框并说明”，空着发送时没有文字可留。
问题三：start 失败（not-allowed、nothing-to-continue，快照已过期）时是否还继续 send，没写。
如何核实：runtime.md 输出 4、36、106、107；session-host.ts 现有 run.continue 只调 start。
建议改法：写成表：按“有无中断 × 有无留着 × 空着/写了字 × 三种恢复方式”列调用序列；写明“start 失败则整体停下并提示；send 失败只重试 send，不重做 start”；写明半成状态的显示。

### 4. 合并的退化与拼法：没有用户的话可合并、只有一条、附件编号与顺序
严重程度：重要
类别：照字面实现会做错
位置：conversation.md 输出 9、47
现象：（a）“空着按回车：合并时把用户留着的话合成一条走 send{replaces}”——留着的全是宿主、会话的话时，没有用户的话可合并，send 没有正文；只有一条用户的话时合并等于把原话原样重发一遍（并把原来的补充说明/排队模式改成普通新话）。Spec 没说这两种退回 resume。（b）输出 47 只写“附件随各自的文字保留”。附件在文字里是 `![image #N](目标)`、`[file #N · 名](目标)`、`[paste #N]`（prompt-editor.md 输出的文字写法），编号每条各从 1 起；两条按“之间空一行”拼起来会有两个 `#1`，粘贴块放到开头（blockPlacement start）的位置标记与 `<paste>` 块的先后也会错位。写不写“重新编号”、谁来做，没有说。（c）用户与宿主的话混排 A(用户) H(宿主) B(用户) 时，合并出的 A+B 排在 H 之后，原来 A 在 H 前的先后被改了；“前面还有 N 条”的 N 也没有定义（H 的条数？还是被放行出来的全部？）。
如何核实：prompt-editor.md 的文字写法表与“编号分两套”一条；runtime.md 输出 107 的 replaces。
建议改法：补三句：用户的话少于两条时走 resume（不 replaces）；拼接时按文字写法整体重编号，粘贴块位置标记随之改；N 定义为“放行出来、排在合并那条之前的宿主、会话的话的条数”。

### 5. 合并出的乐观消息：结果未知的重发、被拒后回填、去向、“前面还有 N 条”没有字段
严重程度：重要
类别：接口与合同
位置：ui/agent-conversation-view.md 第 336 行（harness 适配器的乐观消息）；conversation.md 输出 6
现象：（a）现有的“结果未知 → 重新发送”（message.resend，session-host.ts 的 unknownSends）只记了文字与投递方式；合并出的那条带 replaces 与 commandId，重发必须用同一组参数（提案第四节第 4 小节“结果未知时的重发用同一组参数”），否则内核会再放行一遍、留着的话还在，用户看到重复。Spec 没写。（b）“明确被拒时撤掉，文字放回输入框”：空着回车合并时输入框本来是空的，被拒后放回的该是什么？字面实现会把合并的长文塞进草稿，同时留着的话仍在排队区，同一内容出现两份。（c）输出 110 的 placement：later（停止中到的话）与 held 时，乐观气泡在日志里的 `input` 事件到来之前一直是 pending；Spec 没说 pending 要不要区别显示，以及 later 时气泡位置（末尾）与“前面还有 N 条”会随停止完成变化。（d）MessageView 的 user 变体没有承载“前面还有 N 条”的字段（现有字段只有 delivery、author、intent），“标 N 条”由哪个字段、什么文案给，没有写。（e）运行中接着跑后发出的合并那条实际是运行中的插话（steer），气泡 intent 取 normal 还是 steer 没定。
如何核实：session-host.ts message.resend 分支；ui spec 的 MessageView 类型块；runtime.md 输出 110。
建议改法：给 MessageView.user 加可选 `ahead?: number`，写明文案“前面还有 N 条”由视图的目录给；写明合并发送的重发沿用同一 commandId 与 replaces；被拒时空着发送不回填草稿，只给说明；pending 的消息在 placement 为 later/held 时显示“等待发出”。

### 6. ctx 队列项新字段没有命名与类型；“缺省是用户”没写；heldBy 与单一头行原因对不上
严重程度：重要
类别：接口与合同
位置：ui/agent-conversation-view.md ctx 的 composer 行；排队区一条
现象：composer 行只用中文列了“发出者的显示名与图标、能不能编辑、是否留着与留着的原因文案”，没有写字段名与类型（对照 MessageView 的 `author?: {label: Text; icon: string}` 是写成类型的）。照字面实现，宿主与视图各自起名，Lab 夹具、dom 测试都没法先写。具体缺口：（a）用户自己的话是不带 author（缺省）还是带？“用户自己的标签是补充说明/排队”靠什么判定，没写；（b）“能不能编辑”是 `editable` 还是看 author，没写；用户能取消任何一条（输出 108），所以“只有取消”是编辑位的显隐，不是权限；（c）原因文案是 `Text`（i18n 引用）还是已翻译串，没写，英文文案要走翻译端口；（d）头行只有一个“原因文案”，但每条各有 cause（输出 109：放行后再留着按那一次重新记，所以同一缓冲区里可以有不同原因的留着的话）。头行写哪一条的原因、不同原因怎么写（取最早的？“多种原因”？），没有定；（e）heldBy 不在字段里：停止是用户、宿主、父会话都可能，“你停止了”对父会话连带中止（heldBy 是父会话）是错的。
如何核实：ui spec 的 MessageView 类型块；runtime.md 输出 103、109；提案第四节第 1 小节 heldBy。
建议改法：给出 `queued` 项的类型，例如 `{id, text, delivery, author?: {label: Text; icon: string}, editable: boolean, held?: {reason: Text}}`，写明 author 缺省是用户；头行原因取第一条留着的话的 reason，原因不同时在头行后加“等”；原因文案按 cause 与 heldBy 的组合取。

### 7. 原因文案表没有覆盖输出 104 的全部收口方式，也没有兜底
严重程度：重要
类别：遗漏
位置：conversation.md 输出 48
现象：表是“出错、你停止了、应用重启过、交出结果之后、空闲时排的、开不起运行”六项。runtime.md 输出 104 列的收口方式是：正常结束、只压缩、交出结果、文字收口、出错、停止、进程内中断、打开会话时的恢复，另有 cause 的 `{queued: "idle", code?}`。对不上之处：（a）“正常结束”“只压缩”“文字收口”（这三类也会留下话，例如只压缩的运行收口、交出结果前的文字收口）没有文案；“交出结果之后”只对应交出结果，文字收口没有。（b）“应用重启过”：session.md 输出 15 的 `end: "interrupted"` 同时是进程内中断与打开会话时的恢复，进程内中断（不是重启）会被标成“应用重启过”，不准。（c）“你停止了”没分 heldBy（见发现 6）。（d）“开不起运行”对应 `{queued:"idle", code}`，“空闲时排的”是不带 code 的；两者是同一个 cause 形状的两种取值，文案要按有没有 code 分，文里没写。（e）没有兜底：旧内核之外未来新增的收口方式、未知的 code，视图应写通用的“已暂停”，而不是空文案或抛错。
如何核实：runtime.md 输出 104、42；session.md 输出 15、24。
建议改法：改成“按 cause.end 取表，表里列全 runtime 输出 104 的各收口方式，未知的写‘上一轮没有正常结束’之类的通用文案；cause.queued 按有无 code 取两句”；interrupted 一律写“上次运行被中断”。

### 8. 排队区三条上限遇到留着的话：第 4 条起既不能编辑也不能取消；就绪与留着混排时头行说谎
严重程度：重要
类别：与现有组件合同的冲突 / 遗漏
位置：ui/agent-conversation-view.md 排队区一条；packages/nb-agent-ui/src/vue/composer/AgentQueuedMessages.md、.vue
现象：AgentQueuedMessages 最多显示 3 条，其余收成不可点的一行“还有 N 条”。原来这没问题：就绪的话会被运行取走，队列自己缩短。留着的话不会被取走，会一直待在那里：留着 5 条时用户永远只能看到、编辑、取消前 3 条，另外 2 条要么“继续”一起发出去，要么“停止并清空”才处理得到。Spec 没提这条上限与头行的关系，也没说头行显示留着的总数。另外，缓冲区里可以同时有留着的话和就绪的话（宿主在用户留着话的时候又排了一条，运行中常见）：头行“已暂停”对就绪的行是错的，“留着的行改成虚线框”只区分了行，没有说排序（留着的在前还是入队顺序）、头行的“继续”对就绪行意味着什么；收起的“还有 N 条”里如果藏着留着的行，头行与虚线框都看不到它们。
如何核实：AgentQueuedMessages.vue 的 VISIBLE = 3；runtime.md 输出 105 表（宿主的话不放行用户停止留下的）。
建议改法：留着的行不受 3 条上限限制（或“还有 N 条”可展开），头行写“已暂停 · 共 N 条”；混排时留着的行在上、就绪的在下，头行只管留着的；组件合同 AgentQueuedMessages.md 里“只显示，没有操作”也已与现有 .vue（有编辑、取消）不符，应同时改。

### 9. “停止并清空排队”的清空范围、出现条件与键入文字时的行为
严重程度：重要
类别：与已定设计的偏差 / 边界
位置：ui/agent-conversation-view.md “停止的第二个选项”；conversation.md 输出 6；ctx 的 interaction 行
现象：（a）出现条件是“缓冲区里有用户自己的话”，但不带 keepQueue 的 abort 清空的是停止受理那一刻缓冲区里的全部（提案第 2 小节：每条 inputRemoved{reason: aborted}），包括宿主、会话排的话（例如每周简报）。用户看见的是“清空排队”，实际连用户看不见的（超过 3 条的收起部分、宿主的）也一起取消，菜单没有数量提示。（b）“有用户自己的话”算不算留着的：运行中留着的用户的话是否计入，Spec 没说（见发现 1）。（c）停止按钮只在“运行中且输入为空且 canStop”时出现（Composer.vue 的 showStop）；用户一旦在输入框里敲字，按钮变成发送，箭头同时消失、按钮宽度变化，发送区的布局在键入第一个字时跳动，用户也没法一边写着话一边选“停止并清空”。Spec 没提这点。（d）interaction 行里只写了“停止并清空排队”，没有给字段名；字段名 canStopClearing 只出现在排队区后面一条，两处对不上时容易各自实现。
如何核实：AgentConversationComposer.vue 第 200 行 showStop。
建议改法：菜单项写数量（“停止并清空排队（N 条）”，N 是会被清掉的条数，含宿主的）；canStopClearing 的定义写成“缓冲区里有用户自己的话（就绪或留着）”并在 interaction 行给出字段名；写明箭头随停止按钮一起出现与消失，不随文字变化而占位（或保留箭头位）。

### 10. 停止的下拉箭头：键盘、读屏、焦点、禁用态都没有写
严重程度：重要
类别：无障碍 / 对照参照
位置：ui/agent-conversation-view.md “停止的第二个选项”；packages/nb-ui/docs/ui-development-spec.md 第 143 行
现象：只写了“两段拼成一个按钮”“箭头打开的菜单”“停止进行中箭头不可用”。没有写：（a）语义：是两个按钮（停止、更多选项）还是一个分裂按钮；读屏标题（“停止”与“更多停止选项”？），aria-haspopup="menu"、aria-expanded；（b）键盘：两个控件各是一个 Tab 停靠点，还是箭头只能用方向键进入；Enter、Space、ArrowDown 打开，Esc 关闭；（c）焦点：nb-ui 规范第 143 行要求“从正在编辑的内容旁打开的菜单：选了一项后焦点回到内容，不回触发按钮”，选了“停止并清空”后运行随即收口、停止按钮整个消失，焦点若还留在触发器上会掉到 body；（d）禁用态：“停止进行中箭头不可用”若用 disabled 属性，聚焦着箭头时再按停止，焦点会丢；菜单打开时运行结束（按钮卸载）、或缓冲区变空（canStopClearing 变假）菜单要自己关上；（e）菜单项是危险动作，应用 nb-ui 的危险项（.nb-ui-menu-item-danger，只换文字与图标色），并说明用 DropdownMenu 而不是自制；（f）“同色”指什么：评审板里停止按钮是 danger 色实心，箭头与分隔线的对比与暗色主题的取值没有说。
如何核实：ui-development-spec.md 第 143、156 行；nb-ui 的 DropdownMenu.md 有 disabled 与 aria-description。
建议改法：补一条交互合同：箭头是独立按钮（aria-label“更多停止选项”，aria-haspopup=menu，aria-expanded），Tab 可达；选中后焦点回编辑器；禁用用 aria-disabled 保持焦点，并说明原因；菜单在运行收口或 canStopClearing 变假时关闭。

### 11. 没有编号验收，且旧验收 5 已过时；ui Spec 对“等你处理”与会话列表轻标没有合同
严重程度：重要
类别：验收映射 / 遗漏
位置：ui/agent-conversation-view.md 验收段；conversation.md 验收与 Smoke 第 5 条、输出 48 末句

### 12. 视觉与窄屏、英文、主题：颜色角色与截断规则缺位，留着状态只靠虚线与变淡
严重程度：建议
类别：遗漏（窄屏 390、英文、明暗主题、无障碍）
位置：ui/agent-conversation-view.md 排队区一条；t03 评审板 r6 的 queue-stopped、queue-error 图
现象：（a）头行是“暂停图标 + 已暂停 + 原因文案 + 右端继续”一行；英文原因文案与 390 宽下没有写截断规则（评审板只有桌面宽度的图）：该让原因先截断、“继续”按钮保留。（b）别的发出者的标签是“显示名与图标”，显示名可以是插件名、会话名，长度不定，行内是“标签 + 正文第一行 + 编辑 + 取消”，没有写标签的最大宽度与截断。（c）“强调色”“次要色”“变淡”没有对应 design-language 第五节的色彩角色（暂停、待处理按状态色表更接近 `--status-warning`，还是中性色？），虚线框用什么描边、暗色下对比如何；“标签变淡”叠加“次要色”会让宿主的留着行的标签对比度可能低于 4.5:1。（d）留着与否只靠虚线框与淡标签区分；读屏用户在行里拿不到“已暂停”（头行在列表外面），状态除颜色外应有文字（本 Spec 会话列表一节已有这条原则）。头行在运行收口时才出现，应是 role="status" 之类的播报，否则读屏用户不知道话被留下了。（e）占位文字“排队的话已暂停。按回车继续，或输入新消息一起发”约 26 个汉字，窄屏单行版式与英文翻译会被截断，关键的“按回车继续”在末尾被截。
如何核实：看评审板 r6 两张图；Composer 现有占位文字同样会被截断，但没有这么长。
建议改法：补三句：头行原因文案单行截断、继续按钮保留；标签最长 12em 截断；留着的行带 aria-label（“已暂停：…”）；占位文字把动作放前面（“按回车继续排队的话，或输入新消息一起发”）。颜色角色在实现计划里指明并要求暗色主题的对比量测。

### 13. Spec 写法：planned 标记范围含混、条目位置、组件合同需随之改
严重程度：建议
类别：别扭之处
位置：conversation.md 输出 6、9、47、48；ui/agent-conversation-view.md 各 planned 条
现象：docs/specs/README.md 规定“标在一句话后面的只有那一句”。输出 6 在“…以快照的状态收口。（planned）缓冲区里有用户自己的话时…”后面跟了三句，输出 9 在一句之后又接了六七句，标记写在句前，读者分不清范围到哪里为止；去标记时也没法逐句核断言。输出 47、48 是缓冲区与恢复方式的行为，却排在“子代理与后台任务”小节、紧跟输出 46（状态栏设置页）之后，与输出 6、9 隔得很远。ui Spec 排队区一条把头行、占位文字、发送键、空着发送、写了字几件事合在一条里，不便逐句标记与验收。AgentQueuedMessages.md 的“只显示，没有操作”与现有 .vue（带编辑与取消两个事件）已经不一致，AgentConversationComposer.md 的占位顺序（第 76 行）与发送表（第 33 行）都要随这次改，Spec 没有指出需要同步改的组件合同。
建议改法：planned 句子拆成单句各带标记（或把一整段做成“（planned）条目”，标在条目标题后）；输出 47、48 挪到“对话”小节；排队区一条拆成“排队区”“头行与继续”“发送键与占位文字”三条；在实现合同里列出要同步改的组件文档。
