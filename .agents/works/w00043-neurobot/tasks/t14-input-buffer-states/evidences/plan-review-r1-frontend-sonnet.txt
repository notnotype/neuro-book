### 1. 输出 50 的表按“中断”分行，内核的可接着跑还包括出错与停止；宿主拿不到判据，同一模式下一条与两条的行为不同
严重程度：重要　类别：合同与数据可得性
位置：conversation.md 输出 50 的表；plan“session-host.ts：run.continue 照输出 50 的表选指令”；runtime.md 输出 4、106
现象：表的第二行只认“留着的话加中断的运行”，宿主能读到的只有 `transcript.interrupted()`（kernel-transcript.ts 527 行：`reason === "interrupted" && !compactRun`，停止、出错都为假）。但 runtime 输出 4 的“可接着跑”明确包含出错与停止（最后一轮停在当中）。用户点停止（keepQueue）后留下一条用户的话：表第一行合并列写“少于两条走 `resume{mode:"keep"}`”，内核的 `resume` 会先接着跑被停止的那一轮（输出 106：已收口的开“继续”运行）；留下两条时走 `send{replaces}`，新开一轮、不接着跑被停止的那轮。右列 `resume{mode}` 一律先接着跑停止的那轮。
为什么是问题：conversation 验收 8（停止后写一句合并）与用户直觉都是“停了就停了”；同一合并模式下，一条与两条的结果不同，且宿主没有数据区分，照字面写出来的行为取决于内核实现细节。
如何核实：真实内核里让一次运行 abort，留一条用户排队，调 `resume{mode:"keep"}`，看是否写 `runStarted` 且 `turnStarted.inputId` 为 null。
建议改法：先定停止与出错后用户的 `resume` 要不要接着跑停止的那轮（Spec 一处统一定）；若不要，`resume` 只在叶子上是“中断”或暂停时才先接着跑；若要，表加“停止或出错后”一行，快照或 `session` 面暴露 `continuable`，宿主不自己猜。

### 2. “先 start 再 send{replaces}”两步之间没有进行中保护，界面状态与失败路径未定
严重程度：重要　类别：状态组合遗漏
位置：plan“session-host.ts”一节；conversation.md 输出 50 第二行；session-host.ts 的 `run.continue`（1372 行，每次点击 `commandId()` 取新 id）、`submit()`（1093 行起先清草稿）
现象：`start` 一返回运行就进入 running：界面立刻显示停止键、`stopClearing`，头行的留着条目仍在（要等 `send{replaces}` 才被移除）。两步之间用户可以：再点一次“继续”（现有代码每次新 id，第二次 `start` 得 `already-running`，界面报错，其实第一次已成功）、点停止（之后第二步的 `send` 在空闲时到达，开了新一轮，违背刚才的停止）、编辑或删除留着的条目（只靠 `input-stale` 兜，且兜不住停止）。`start` 结果未知时重试同理：现有 `rewriteHistory` 用 `rewriting` 标志加 `commandIdOf(key)` 防这类问题，计划没提这里照搬。
为什么是问题：这是开发者确认的第 11 项的核心路径，也是验收 5 的新文字。
如何核实：在 session-host 测试里让 `start` 的响应延迟，期间再触发一次 `run.continue` 或 `composer.stop`。
建议改法：复合操作加同样的进行中标志（头行“继续”与发送键期间不可用）；`start`、`send` 都用按操作身份固定的 commandId；第二步前确认运行仍是自己刚开的（停止或已收口就不再发 `send{replaces}`，把文字留在输入框并说明）；乐观消息放在 `start` 成功之后再加，失败不必撤。

### 3. 合并被拒或结果未知时，现有 `settleSend` 会把合成的整段文字放回输入框，重发也丢了 `replaces`
严重程度：重要　类别：与现有宿主接线冲突
位置：session-host.ts 51 行 `PendingSend`、1068 行 `settleSend`、1397 行 `message.resend`；plan“合并的那条结果未知时重发沿用原参数”；ui 规格“空着按继续发出的合并被明确拒绝时，不把合并的文字放回输入框”
现象：`PendingSend` 只存 `{commandId, input, restore}`。合并后的 `input.text` 含留着条目的文字：被拒时 `settleSend` 执行 `setDraft(sent.input.text)`，把已经在排队区里的两条话又灌进草稿，用户再发就是重复；`message.resend` 用 `sent.input` 重发，没有 `replaces`，若第一次其实没受理，这次会把留着的话与合成的话都跑一遍。计划只说“沿用原参数”，没说 `PendingSend` 要带 `replaces` 与“用户自己写的那一段”。另有一处：`input-stale` 没有进 `REJECT_KEYS`，会显示成通用的“其它：input-stale”。
为什么是问题：两个方向都会重复发话；计划的单元测试清单（resume-merge 与表逐行）测不到这条接线。
如何核实：session-host 测试里让 `send` 返回明确失败，看草稿内容；让它返回 `unknown-outcome` 后点重发，看日志里有没有 `replaced`。
建议改法：`PendingSend` 加 `replaces` 与 `typed`（用户本次写的字）；被拒只还原 `typed`，空着继续时不还原；`input-stale` 再失败单独写文案；加上述两个用例。

### 4. `resume-merge.ts` 的重新编号：现成的解析与换号函数在 nb-markdown 里，但没有公开出口；计划写成“纯函数、配单元测试”，会手写正则
严重程度：重要　类别：选型与包边界
位置：plan“新增 web/resume-merge.ts”与“技术选型：无”；prompt-editor.md 的“文字写法”表；packages/nb-markdown/src/prompt/prompt-text.ts 的 `parsePromptText`、`renumberInsertion`、`usedPromptNumbers`、`promptNodeText`
现象：文字写法有四种带号写法（`![image #N](..)`、`[file #N · 名](..)`、独占几行的 `<paste id="N">…</paste>`、位置标记 `[paste #N]`），两套编号（图片一套，文件与粘贴块共用），粘贴块与位置标记要成对换号，粘贴块内容里和代码片段里长得像标签的文字不能换。nb-markdown 已有 `parsePromptText`（读成节点）、`renumberInsertion`（撞号换新号，粘贴块与标记一起换）、`promptNodeText`（写回文字）。但包的公开出口只有 `src/prompt/index.ts` 的 `parsePromptText`、`promptReferenceText`、`stickerOnlyMessage`；`./prompt-text` 子路径只放技能函数，且受 `boundary.test.ts` 约束；其余几个函数不导出，跨包深导入又被规则禁止。`session-host.ts` 现有的 `findPromptLinks` 能按地址回找附件范围（`attachmentsFor`），所以附件那半边可复用，换号这半边不行。

建议改法：在 nb-markdown 的纯 TS 子路径（`prompt-text`）新增一个导出（例如“按顺序拼接几段文字并换号”，内部用 `parsePromptText` 加 `renumberInsertion` 加 `promptNodeText`），`resume-merge.ts` 只负责“按入队顺序、空一行、整理附件候选”；计划补上这个小改动与它的测试，并把技术选型写成“复用 nb-markdown 的解析”。

### 6. 路径上宿主发来的 `input`、`steer` 仍被画成用户自己的话；`KernelIssuer` 与 `authorOf` 只认会话
严重程度：重要　类别：与现有组件合同冲突
位置：plan“kernel-transcript.ts：queue 的条目带 by…”；kernel-transcript.ts 255 行 `KernelIssuer`、418 行 `by = … data.by.kind === "session" …`；session-host.ts 850 行 `authorOf`；ui 规格“`user` 消息带 `author` 时…`authorOf(by)` 由宿主给”；runtime 输出 85
现象：内核加了宿主发出者（`{kind:"host", source:{plugin,label,…}}`）后，周期任务与 bot 的话会以 `by: host` 写进路径上的 `input`（或 `steer`）。转录器只在 `by.kind === "session"` 时取作者，宿主的话得到 `by = null`、`author` 缺省，消息流里画成用户自己的头像与名字，与排队区里“标来源”的同一条话前后不一致。`authorOf` 只查 `target.ancestors`，宿主没有 id，也不在祖先里。计划只改了队列条目的 `by`，没有改路径事件的归约与 `authorOf` 的形状。

如何核实：用转录器喂一条 `input{by:{kind:"host",source:{plugin:"x",label:"每周简报"}}}`，看 `messages()` 里的 `author`。
建议改法：`KernelIssuer` 扩成会话与宿主两种，`authorOf` 的入参随之变化（宿主取 `source.label` 与插件给的图标，会话照旧）；`kernel-transcript.test.ts` 加宿主的 `input` 与 `steer` 用例；Lab 的 `subagent-samples` 或消息场景加一条宿主的话。

### 7. 乐观消息：`commandAccepted` 的撤掉条件、重建路径与“前面还有 N 条”三处计划没有改到
严重程度：重要　类别：增量归约与快照重建不一致
位置：kernel-transcript.ts 622 行（`data.name === "send" && value.runId === null`）、799 行（`optimistic.slice(1)`）、`applyPath`（762 行起，不碰 `optimistic`）；plan“乐观消息按 commandId 确认…合并发出的那条乐观消息带‘前面还有 N 条’”
现象：(a) 计划只把 799 行改成按 `commandId`。622 行的判据是 `runId === null`（send 撞上运行中），而内核新增了 `placement`（taken、later、held）；`later` 与 `held` 时 `runId` 的值计划没写，乐观消息要么撤晚了、要么在没有 `input` 事件的那段时间里整条消失又不在排队区。(b) 重连、重开走 `applyPath`：路径里已有带 `commandId` 的 `input`，但 `applyPath` 不清乐观消息，结果未知的那条会和真实消息并排出现，直到用户点重发。现在没有 `commandId` 所以这条只能靠 `settleSend` 兜；计划引入了 `commandId`，正好可以在重建时按它去重，但没写。(c) “前面还有 N 条”由宿主在发送时算好、静态放进乐观消息；放行出来的宿主的话被取走后已经显示在它上面，数字就成了假话，而 `addOptimistic` 的签名（只收 id、commandId、text、timestamp）也没地方放它。
为什么是问题：风险一节只列了“重发要对上”，上面三处是同一机制的另外三个出口。
如何核实：转录器测试里先 `addOptimistic`，再 `applyPath` 带同 `commandId` 的 `input`，看 `messages()` 是否出现两条。
建议改法：按 `placement` 判撤销；`applyPath` 与 `applyEvent` 同按 `commandId` 清乐观消息；`ahead` 由转录器按“这个 commandId 放行出来、尚未取走的条数”现算，不由宿主写死；三处各补一个 `kernel-transcript.test.ts` 用例。

### 8. 停止的下拉：nb-ui `DropdownMenu` 的 `disabled` 是原生禁用、焦点由上游还给触发器，与 ui 规格与验收 39 的写法冲突
严重程度：重要　类别：与现有组件合同冲突
位置：plan“AgentConversationComposer.vue：下拉箭头（独立按钮、nb-ui DropdownMenu、选中后焦点回编辑器）”；ui 规格“停止进行中箭头用 aria-disabled 不可用、保留焦点”“选中…焦点回到编辑器”；验收 39；DropdownMenu.vue 123 行、DropdownMenu.md“交互”
现象：(1) `DropdownMenu` 的 `disabled` 直接传给 `DropdownMenuTrigger`，是原生 `disabled`，按钮失焦、读屏跳过；规格要的 `aria-disabled` 加保留焦点只能受控 `open` 并自己吞掉开关，或改 nb-ui。(2) DropdownMenu.md 写明“菜单关闭时…上游负责把焦点归还触发器”，选一项后焦点在箭头上，不在编辑器；要回编辑器得经 `contentProps` 传 `onCloseAutoFocus` 并 `preventDefault`，现有组件文档没有这个用法，也没有测试守着。(3) 菜单项要危险色加图标，已有 `tone: "danger"` 与 `iconClass`，可用；但“运行收口或 stopClearing 变空时菜单自己关上”依赖整段 `v-if` 卸载，卸载时焦点落到 body，规格没写这时焦点去哪。
为什么是问题：验收 39 的两条断言（`aria-disabled`、焦点回编辑器）按计划的做法都会直接测出相反的结果，返工点在 nb-ui 而不在 nb-agent-ui，影响面更大。
如何核实：Lab 里挂一个 `disabled` 的 DropdownMenu，用 Tab 看焦点是否还能到；选一项后读 `document.activeElement`。
建议改法：计划写明走哪条路：受控 `open` 加触发器自带 `aria-disabled`，`onCloseAutoFocus` 经 `contentProps` 传入（并在 DropdownMenu.md 记这个用法）；或给 DropdownMenu 加 `softDisabled`。卸载时的焦点去向在规格里补一句。

### 9. 会话列表行的“有暂停的话”与状态栏的“等你处理”没有数据来源，重启后留着的话也不可见
严重程度：重要　类别：数据可得性
位置：plan“session-list.ts、activity.ts：会话行轻标‘有暂停的话’；状态栏活动只算只有用户能放行的”；sessions.md 输出 15（activity 只列打开着的句柄，`state: "held"` 只给“只有用户能放行的”）；ui 规格“宿主在会话列表条目的 note 写‘有暂停的话’”；session-list.ts 77、108 行

建议改法：二选一并写进 Spec：缩小——列表行只标当前会话、或标 activity 里 `held` 的项（改规格措辞，“其余的”一句删去）；扩大——索引里存留着条数（后端计划要加，且重启后读索引）。选缩小时，在“不做与风险”里写明“重启后未打开的会话不提醒留着的话”。

### 12. 停止进行中（`stopping`）时头行的“继续”与发送键的行为没有规定，按字面会在停止刚发出时放行留着的话
严重程度：建议　类别：状态组合遗漏
位置：ui 规格“有留着的条目时…`availability` 不是 `ready` 或不允许发送时，‘继续’不可用”“运行中也可能有留着的条目，头行照样有‘继续’”；runtime 输出 104、30
现象：`run.status` 有 `stopping`（abort 已受理、运行还没收口）。这时留着的条目可能已有（上一次停止留下的，或宿主开的运行里排的），头行的“继续”不受 `availability` 影响，仍可点。内核对运行不再取输入期间受理的 `resume` 的处理是推迟到收口，然后放行并开新运行（输出 104）：用户刚点了停止，随即点“继续”，会在停止收口的同一批里又开一次运行。规格与计划都只在 `availability` 不可用时禁用“继续”，没有写 `stopping`；同样，停止键换成“正在停止”的那段时间里，发送键的 `run.continue` 路径也没定。
为什么是问题：这是用户最容易连点的两个按钮；结果是“停不住”，与停止键的承诺相反。
如何核实：Lab 加 `run.status: "stopping"` 且有留着的条目的场景，看“继续”是否可点；真实内核里 abort 后立即 `resume`，看收口批里有没有 `runStarted`。
建议改法：规格补一句：`stopping` 时“继续”不可用，悬停说明“正在停止”（与 `availability` 同一处判断）；`ctx.interaction` 不必新增字段，`run.status` 已够。

### 13. 留着原因的文案：`cause.code` 到“码的说明”的映射、会话作者名的来源、两份语言文件都没有落到文件清单里
严重程度：建议　类别：计划漏登记
位置：plan“session-host.ts：原因文案按 conversation 输出 48”；conversation.md 输出 48（“运行没开起来：<码的说明>”“派它的 Agent 停止了”“<来源名>停止了”）；plugins/agent/locales/、nb-agent-ui/src/locales
现象：`cause.code` 的取值来自内核多处：`no-model`、`no-credentials`、`unknown-model`、`role-unbound`、`profile-invalid`、`read-only`、`reassembly-pending`、`session-closing`、`not-allowed`；输出 48 要求写“码的说明”，但没有一张表，也没写认不出的码怎么显示（输出 48 末尾只写了“认不出的写‘上一轮没有正常结束’”，指的是 `end`，没有覆盖带未知码的 `queued`）。模型类的码在界面里已有说明文字的来源（模型选择器的不可用原因），应复用而不是再写一份。`heldBy` 是会话时“派它的 Agent”假定停止者是祖先，`authorOf` 只在 `ancestors` 里查，非祖先写“另一个会话”，与“派它的 Agent 停止了”不一致。文案分两处：nb-agent-ui 的 `locales/`（头行、“已暂停 N 条”“还有 N 条”“更多停止方式”“停止并清空排队（N 条）”）与 plugins/agent 的 locales（原因文案、设置项），计划只写了前者。
为什么是问题：原因文案是规格里最长的一条，且每个分支都要中英两份与测试；漏登记会在片 6 临时补。
