## 发现

### 1. settle 项把会话翻成空闲之后，已排在队列里的 send 会在重新装配之前开运行，重新装配随后在运行中进行
- 严重程度：重要
- 类别：时序、与重新装配冲突
- 位置：计划 control.ts 一节 settleRun 第 3、4 步（“有待做的重新装配时不开”只管推迟的放行）；session.ts:214-216 的 closedGuard（只在进队列前看 `state.reassembling`）；session.ts:628-632 的 onIdle、647-656 的 scheduleReassembly；session.ts:690 起的 reassembleOnce（不看 control 是否空闲）
- 现象：探针 N1（真实内核）：运行中撤回扩展 lab.victim（notifyAssemblyChanged），runEnded 批的反应被扩展卡住时发一条 send，然后放开。日志顺序是 `… runEnded(completed) inputQueued profileChanged`，说明这条 send 的受理项排在重新装配的队列项之前。原因：send 进队列时 reassembling 还是 null，过了 closedGuard；onIdle 到收口之后才被调用，reassembleOnce 的 `core.queue.run` 是那时才排进队列的。现有内核里这条 send 看到的是“不空闲”，只入队；照计划，settle 项在同一项里把 control 翻成空闲，这条 send 会看到空闲、`startProblem` 为 null，于是按旧装配写下 runStarted 开运行。随后重新装配的队列项在这次运行里执行 `mounts.unmountAll()` 与 `core.reassemble(next)`。同类情形还有一种：notifyAssemblyChanged 在 settle 项的反应期间到达，这时 settle 已决定开下一次运行；计划又说 onIdle 要“整体搬进这一项”，如果开了下一次运行之后仍调用 onIdle，重新装配会和下一次运行并行。
- 为什么是问题：违反 runtime 输出 57“重新装配做完之前不受理指令”与 104“重新装配仍在运行之间先做”。验收 14 只覆盖压缩期间到达、被推迟的 send，覆盖不到这个空档。
- 如何核实：探针 N1，输出 `N1 order: profileChanged inputQueued runStarted runEnded(completed) inputQueued profileChanged`。按计划实施后，第二个 inputQueued 后面会跟着 runStarted，并排在第二个 profileChanged 之前。
- 建议改法：任选其一写进计划。一是 accept() 在队列项里、decide 之前再看一次待做的重新装配（`pendingReassembly` 或 `reassembling` 非空时，按 104 的“推迟”处理或让它等待）；二是 settle 项在有待做的重新装配时不把会话翻成空闲，等重新装配做完再翻。同时写明：settle 开了下一次运行时不调用 onIdle，待做的重新装配留到下一次收口。验收 14 加一例：在 runEnded 批的反应期间到达的 send 遇上待做的重新装配。

### 2. 关闭开始于受理批（或收口批）的反应期间时，那一项写完后照样 launch 新运行，关闭不等它；计划的“关闭开始后不开”只在组批时判断
- 严重程度：重要
- 类别：时序、与 closeSession 冲突（现有缺口，计划把它带进 settleRun）
- 位置：commands.ts:51-64（accept 在 decide 之后、写批之前看 `host.closed()`，写批与反应之后无条件 `launch`）；session.ts:771-779 closeNow（`closed = true`，`control.shutdown()` 在 #active 为 null 时立即交回，然后才 `queue.drain()`）；计划 settleRun 第 3 步“会话已开始关闭”时不放行
- 现象：探针 N3（真实内核）：空闲时 send，扩展卡住 runStarted 的反应，这期间调 `closeSession({reason: "interrupted"})`，再放开。结果：send 交回 `{runId: …}`，closeSession 正常完成，模型一次也没被请求；之后循环往已关闭的日志写入，抛出 `SessionClosedError: the session is closed; the write is dropped`（core.ts:309），control.ts:119-122 的 catch 只吞 LogBrokenError，这个错成了未处理的拒绝（bun test 因此判这一例失败）。日志里留下没有 runEnded 的 runStarted，要等重开时恢复。照计划，推迟的放行在 settleRun 里“写批、开下一次运行”，判断“已开始关闭”放在组批时；如果关闭开始在 settle 批的反应期间，会同样 launch。验收 14 的第二个场景（只压缩期间 send 后立刻 closeSession）就落在这个空档附近。
- 为什么是问题：runtime 输出 53 规定关闭开始后“不写日志、不开运行”，104 规定“会话已开始关闭时不开运行”；实际会多出一次没收口的运行和一个进程级的未处理拒绝。
- 如何核实：探针 N3，输出 `N3 send: {"inputId":…,"runId":"…"} close: closed`、`N3 model requests: 0`，随后是 SessionClosedError。
- 建议改法：launch 之前（写批与反应之后）再看一次 closed，已关闭就不 launch。这时 runStarted 已经写下，由重开时的恢复收口，与崩溃一致，在 Spec 53 写一句。或者在 closeNow 的 drain 之后再看 control.active，不为空就再 shutdown 一次。settleRun 与 accept 共用同一个检查。验收 14 加“关闭开始于 settle 批的反应期间”一例。

### 3. 第三轮第 2 条 (c) 没有消失：用户停掉父会话开的子会话运行后，父 Agent 不带话的 agent_send（resume）立即接着跑那一轮
- 严重程度：重要
- 类别：权限，与第二轮决定（用户停止子代理后只有用户能放行）不一致
- 位置：Spec runtime 输出 4、106、108（非用户“只能接着跑 runStarted.by 是它的运行”）；subagents 输出 10（“叶子上有父会话开的、可接着跑的运行时先接着跑”）；计划 commands 一节 start 与 resume
- 现象：探针 R2c（真实内核）：子会话的运行由父会话身份 send 开出，用户 `abort{keepQueue}`，运行 aborted；父会话身份 `start` 交回新 runId，跑出“父会话续上了”，turn 依次是 `id`、`null`，也就是接着用户停掉的那一轮“继续”。照计划，这次运行的 `runStarted.by` 是父会话，start、resume 的权限检查都放行，结果不变。`heldBy: user` 只挡缓冲区里的话，挡不住接着跑运行本身。第三轮第 2 条 (c) 写的正是这一情形，处理表把规则写成“只接着跑自己开的”，没有覆盖“自己开的、但被用户停了”。
- 为什么是问题：用户在子代理卡片上点停止，父 Agent 下一步工具调用就能把同一轮接着跑起来，用户的停止没有效果。
- 如何核实：探针 R2c，输出 `R2c parent start: {"runId":…}`、`R2c continued: completed 父会话续上了 turn inputs: ["id","null"]`。
- 建议改法：交开发者确认后写进 Spec 4、108：运行以 `aborted` 收口、停的人是用户时，非用户不能接着跑它（得 `not-allowed`，或 resume 只放行不续跑）。要从日志判断，runEnded 或停止的受理记录得带停的人，计划 api 一节相应加 `runEnded.by`（或 `stoppedBy`）。验收 11 加一例。

### 7. settleRun 的失败分支没写：写批抛错、收口批的反应抛错、开下一次运行前查模型时抛错，都会让“翻转空闲、onIdle、结算 waitRun”被跳过

### 9. abort 的几处没定：范围取哪一刻、第二个 abort 的受理记录写在哪一批、停止后运行以 finished 收口时怎么算
- 严重程度：建议
- 类别：没写出来的假设
- 位置：计划 control.ts 一节 abort 一条（“受理记下范围（此刻缓冲区的条目 id）”）；Spec runtime 输出 30（“范围是受理排进队列那一刻”）、26（宽限期内完成的收尾结果照常写下，运行以 finished 结束）
- 现象：(a) 计划在同步步骤里把受理排进队列，再说“受理记下范围（此刻…）”。Spec 的“此刻”是排进队列的同步时刻；照计划的行文，容易实现成受理项轮到时。两者之间，排在前面的队列项可能写下新的 inputQueued，例如输入拦截慢的 send（输入拦截缺省最长 5 秒，在受理项里跑）：按 Spec 不在范围里，转成没有 heldBy 的留着；按受理项时刻算，会被缺省清空删掉。(b) 两个 abort 都在收口前受理：Spec 说受理记录与 runEnded 同批，计划只写了“第二个 abort 不改它们”，没说第二条的 commandAccepted 是否也进 settle 批、交回 `aborted: true` 还是 false。重发时要交回第一次的结果，这个值必须写进日志。(c) 停止受理之后，收尾工具在宽限期内完成，运行以 finished 收口：settle 批是否照样执行停止的范围（清空，或 heldBy 留着），abort 交回什么，都没写。
- 为什么是问题：这三处都会写进日志，发布后改不了；实现者只能自己挑一种。
- 如何核实：对照计划原文与 Spec 30、26；commands.ts:151-184 现有的 inflight 与重发处理。
- 建议改法：计划写明：范围在同步步骤里读（`readyEntries` 加上留着的，记 id）；收口前受理的每个 abort 都在 settle 批里写自己的 commandAccepted，只有第一个是 `aborted: true` 并决定范围；运行以 finished 收口时停止的范围照样执行，abort 交回 `aborted: true`（或写成 false，二者择一写进 Spec 30）。

### 10. inputConsumed.runId 与 runStarted.by 的代价不大，但旧日志按第一条 input 认发出者会认错一类运行；只压缩的运行没有 by
- 严重程度：建议
- 类别：日志合同、归约
- 位置：计划 api 一节、commands 一节 start 一条（“新增 history 的 continuableRun(leaf)”“旧日志没有 by 时按那次运行第一条 input 的 by 认”）；Spec runtime 输出 4、85、108；session.ts:279-291 compact；kernel-state.ts:46-52
- 现象与代价：(a) inputConsumed.runId：写 inputConsumed 的 7 处（loop.ts:208、238、395，commands.ts:114、142，interaction.ts:145，tree.ts:78）在写的时候都知道 runId，preview.ts:116-118 只投影、不落日志；会话级归约只按 id 删条目，用不到 runId。代价可以忽略。(b) runStarted.by：abort 在同步步骤里判权限，要拿到在跑那次运行的 by；start、resume 要拿到“最后一次对话运行”的 by、收口方式与最后一轮的状态。如果 continuableRun 每次沿路径往回扫，代价是每条指令 O(路径长度)；更省的办法是在 path 归约里记 `run.by` 与 `lastChat: {runId, by, ended, lastTurn}`，每条事件 O(1)。旧日志的推断也可以放在归约里：遇到没有 by 的 runStarted 之后的第一条 input，就用它的 by。(c) 认错的情形：旧内核的 `start` 取 buffer[0] 开新运行（探针 p2-G、p1-C，interaction.test.ts:412 的形状），这次运行第一条 input 的 by 是排话的人，不是开运行的人。用户点“重试”带走了会话排的话，这次运行会被认成会话开的，会话因此能停它、接着跑它；没有 input 的“继续”运行则一律认成用户。(d) compact 指令现在不把发出者写进 runStarted（session.ts:290），计划没提给只压缩的运行写 by；宿主开的压缩没有 by，按输出 108 宿主停不了它。
- 为什么是问题：(c) 只影响升级前的日志，范围小，但它正是第三轮第 2 条防的那种“接着跑别人的运行”；(d) 与“宿主能停自己开的运行”不一致。
- 如何核实：grep takeInputDrafts、takeSteerDrafts 的调用处；读 commands.ts:130-149、session.ts:279-291；p2-G、p1-C 的输出（probe-outputs.txt）。

- 更正（第 10 条的建议改法）：旧 start 取 buffer[0] 时也把 runStarted 与第一轮的 input 写在同一个受理批里，“同批”分不出这两种运行，上面那个判据作废。可行的取舍只有两个，交开发者：一是照现稿按第一条 input 认（第一轮审查第 16 条的处理，父 Agent 能接着跑旧子会话里自己开的运行），代价是 (c) 的误认，在 Spec 4 写成已知限制；二是旧日志一律按用户认，代价是父 Agent 接不上升级前自己开的中断运行。
