## 第 3 节 把一条输入放进缓冲区或直接开一轮的入口（内核 5 个指令，调用方 12 处）

## 第 6 节 与提案假设冲突的事实（6 条）
6.1 “收口之后受理的按空闲处理”不能只靠把决定与 runEnded 放进同一批。control.idle 由内存里的 #active 决定，只在 runLoop 结束后的 .finally 里清（control.ts:123-124），晚于 runEnded 批连同它的反应。探针 p1-A：排在 runEnded 批之后受理的 send、enqueue 仍看到“在跑”，交回已收口运行的 currentRunId，话留在空闲会话里。提案第三节把窗口写成“回复写下后、运行收口前”，实际一直延到收口批的反应写完之后。实现时空闲判断要和 runEnded 在同一个队列项里翻转（或改按日志里的 run 状态判断），否则“同批写 inputHeld”之后仍会有就绪的话进空闲会话。
6.2 停止时 idle 先于清空：abortCommand 等 control.abort 连同 finally 结束（idle 已真）后，才读缓冲区（commands.ts:171）并另排一项写 inputRemoved 与受理记录。这段空档里别的发出者 send 会开新运行，新运行的第一个边界会取走本该被清空的插话。提案只说“受理记录写在 runEnded 之后的另一个写入批里”，没提 idle 已经先变真。
6.3 异步提问的回答在空闲又开不起运行时不失败：resolve 成功、交回 {}，回答作为 followup 入队（interaction.ts:136-147，探针 p2-E）。NeuroBook 依赖这一点（subagents/tools.ts:476 的“回答已排进子会话的缓冲区”）。提案失败表写“开运行的各指令：开不起来时照现有的码失败，话仍留着”，但这个入口现在根本不报码；若改成失败，事项也不会被结算（整条指令不写），与现有的 agent_answer 文案矛盾。
  （6.2 的“空档里别的 send 会开新运行”是从代码推断，没有复现；空档只有几个微任务，p1-A 的时序说明排在收口批之后的指令更可能仍看到“在跑”。确定的是清空列表在 idle 之后、队列项之外读取。）
6.4 start 不是“接着跑中断或失败的那一轮”：runEnded 之后 run 为空，start 总是新开一次运行（新 runId）；缓冲区非空时取 buffer[0] 开新一轮（探针 p2-G、p1-C），只有缓冲区空、且末轮不是 completed 时才写 turnStarted{inputId:null} 续写（commands.ts:143-147）。提案里“宿主只能 start 自己开的那次运行”“用户的 resume 先接着跑中断的那一轮”都要先定义“那一轮/那次运行”指什么：现在两者之间没有 runId 关联，只能按叶子上最后一轮的状态推断。另外照提案（空闲时全部留着）实施后，新日志里 start 的“缓冲区非空取 buffer[0]”分支只剩旧日志会走到。
6.5 任务中心停子代理并不经远程的 abort：任务中心是 remote.ts:216 killJob → jobs.kill(null, jobId) → children.ts:52-55 用父会话身份的视图 abort。提案第 2 节说“任务中心里用户停子代理，经远程合同进来，按用户停的记”，实际进来的是 killJob，身份在 children.ts 换成了父会话；子代理卡片的停止（session-host.ts:338-339）才是远程 abort、用户身份。
6.6 提案第三节列 NeuroBook 的入口时没有 nb-harness kit 的标题会话：kit/sessions/meta.ts:149、162 以用户身份（table.view 缺省）往标题会话 send，标题会话已有运行时只记失败，话留在它的缓冲区里。按提案的权限表它会被当成“用户的话”，只有用户能放行，而用户看不到标题会话。另外不带 reason 的 closeSession（agent-host close 无 options）是第三种停止：写 runEnded{aborted}、不清缓冲区、没有发出者，提案的停止规则没覆盖它。
  （6.6 补充：v2 里不带 reason 的关闭只来自 kit 句柄表的空闲关闭 table.ts:335，它只关 idle 的会话，所以这第三种停止在 NeuroBook 的产品路径上碰不到，只在直接用内核 API 的宿主与测试里会出现。）
