# w00043 t06 第二轮只读设计审查

### 1. 认领后、主批写入前开始关闭，日志会留一个永远无人答的同步事项（收窄，见第 1 条）

- **对应第一轮**：11。**严重程度**：重要；**类别**：正确性。
- **位置**：`copy/plan.md:50–57,195,226`；`packages/nb-harness/src/kernel/run/interaction.ts:38–42,65–89,165–183`；`packages/nb-harness/src/kernel/run/commands.ts:63–79`；`packages/nb-harness/src/kernel/session/session.ts:787–795`。
- **现象**：第 2 稿改对了结算权的方向，但只写了 `giveBack()` 把等待者交还。现有 `onAbort` 是一次性的：`closeSession` 在认领之后触发信号时，它从表里删不到等待者，不兑现 `aborted`。随后 `accept` 因 `host.closed()` 不写主批；此时只把等待者放回表，已发生的 abort 不会再派发。
- **为什么是问题**：旧做法至少会叫醒工具；若按“放回等待表”实现，工具也会悬着，运行过宽限期收口时仍能留下无结算事项。另不能把“`written` 没执行”当作“首批没写”，否则会把设计明确保留的反应批故障改成再次结算或挂起。
- **如何核实**：第一轮已用公开 `resolve` 紧接公开 `closeSession({reason:"interrupted"})` 触发这个顺序。本轮核对新增合同与真实等待者代码；`giveBack` 尚未实现。
- **建议改法**：规定 `giveBack` 恰好一次，尚未停止才恢复等待，信号已触发时直接启动原等待者的中止结算（保留 `ProcessInterrupt`），不只回填表。对确定没提交、首批提交后反应失败、写入结果未知三种路径明确谁唤醒、谁能写；不必在 t06 改掉后两种已知的磁盘错误，但不得让它们挂住。现有关闭回归断言调用结果、`interactionResolved` 恰好一条且在 `runEnded` 前、重开无旧事项。

### 2. 缺省 bot 的复制与记录提交之间没有可重试的发布协议（收窄，见第 2 条）

- **对应第一轮**：10。**严重程度**：重要；**类别**：正确性。
- **位置**：`copy/bots.md:18–20,51–58,102`；`copy/plan.md:140–144,201`；`docs/specs/storage/persistence.md:108–113,127`。
- **现象**：固定 `lyra`、暂存改名和重读已消掉同版正常重试时的半棵目录问题。但改名前不保存这次创建的记录内容或标记；第二版会把任何 `<bot id>/`（连空目录也一样）认作自己已经发布的副本。若改名后被杀、升级后预设改了名字、Profile 或头像扩展名，旧文件还在，补写只能从新预设取元数据。
- **为什么是问题**：可能把未知目录登记成已建 bot，或产生不属于任何一代预设的“旧文件＋新记录”。状态根认领排除了并行的第二个产品进程，不证明旧目录是一次成功的发布。`plan.md:201` 的手放目录夹具反而会固定这种误认。
- **如何核实**：按改名后记录提交前的验收现场，分别放空目录、或用实际暂存步骤留下旧 `avatar.webp`，重启前将缺省预设改为 `.png` 与另一 Profile；按当前规则两种都补记，盘上没有能区别这两类现场的证据。未运行未实现的 bot。
- **建议改法**：暂存目录内先写并校验创建凭据（格式版本、id、这次待提交的记录、文件布局），一并改名；只补交读得懂的自有发布物，按读取到的 revision 条件保存、再读确认。未知目录只诊断、不覆盖、不登记；暂存清扫只删能判明自有的项。用跨两版预设和未知目录验证，而不只手放最终目录。

### 3. 门面作废不传到返回的会话视图，旧代次保留宿主接续权（收窄，见第 3 条）

- **对应第一轮**：17。**严重程度**：重要；**类别**：不变量。
- **位置**：`copy/plan.md:82–87,197`；`docs/specs/agent/sessions.md:85,88,109–110`；`packages/nb-harness/src/kit/sessions/table.ts:387–412`；`packages/nb-runtime/src/services/composition.ts:603–619`。
- **现象**：新门禁能拒绝旧视图与 `as` 派生物的新调用，宿主归属接续也已退出 t06。没收口的是作废前通过视图建立的 `subscribe`：计划只登记并归还 `hold`，已建立的监听会继续推帧；冷订阅也可能在作废后才拿到引用。调用门禁不能取消已登记的回调。
- **为什么是问题**：只停消费方、`nbook.agent` 照常运行时，旧插件仍收帧，空闲 30 秒也不释放会话文件锁；只测旧方法抛错或释放 `hold` 都会漏掉。
- **如何核实**：真订阅在 `#subscribe` 拿 `#acquire`，只在它同步交回的取消函数里标记 `cancelled` 并 `#release`；`#subscribe` 已能正确处理取消早于冷打开。第一轮真门面已证明只停调用方不会停 Agent，本轮按资源引用路径核对。
- **建议改法**：同一代次登记视图返回的订阅取消函数，门面 release 时调用它们，与 `hold` 一起清空；调用者先取消时从登记里摘掉。取消函数是清理，不受作废门禁阻拦。只停消费方分别测已建立、尚在打开的订阅：不再回调、取消幂等、无其它引用时 30 秒后锁释放。

### 4. 缺省预设没收到 `published` 时，已有 bot 也不恢复（收窄，见第 4 条）

- **对应第一轮**：5、16。**严重程度**：重要；**类别**：不变量。
- **位置**：`copy/plan.md:118–139`、`copy/bots.md:51,76–78`；`packages/nb-runtime/src/plugins/host.ts:893–919,1550–1566`。
- **现象**：第 2 稿把读所有 bot 记录、创建缺省 bot、持有已有会话都绑到缺省预设的成功 `published`。缺省声明被平台拒绝时没有这个回调，连 `bots.default-preset-missing` 与启动任务终局也没入口；收到回调但文件不合时同样不读记录。顶层声明的 `published` 也不等于接收入口已发布，Spec 对这一时点的保证不成立；主 Agent 探针只证明那份夹具的岗位 Profile 已可用。
- **为什么是问题**：预设只在建 bot 时用一次；升级后缺一份头像或默认声明无效，不应让已有 bot 消失、不重持有，或让 `ensureMain` 一直等一个没启动的任务。
- **如何核实**：实现 worktree `f5f642cd5` 的 `packages/nb-runtime` 执行 `bun test /tmp/t06-design-review-r2/published-order.test.ts`（2 通过）：真应用中顶层声明回调观察到接收入口仍为 `activating`；重复 id 时入口照常 `available`、两条声明都被拒、回调 0 次。bot 行为按拟议依赖推导。
- **建议改法**：把读已有记录和恢复持有从缺省预设可用性解耦；只有空记录分支才消费缺省预设的明确终局（可用／不可用）。缺省项是自带文件，可直接核验而不等待一条可能不存在的回调，但须保留平台拒绝语义；若必须经发布屏障，使用受当前代次和停止信号约束、且不让激活反等会话 I/O 的任务入口。分别验收已有记录但缺省资源失效，以及空记录但平台拒绝缺省声明，两者的 RPC 都须有终局。

### 5. 冷会话 `refuse` 没定义读头失败后是否还可打开

- **对应第一轮**：新（第 3、22 条改法的边界）。**严重程度**：重要；**类别**：正确性。
- **位置**：`copy/plan.md:44–47,68–73,95,199`；`docs/specs/agent/sessions.md:90,92`；`packages/nb-harness/src/kit/sessions/table.ts:119–131,244–268,289–305`。
- **现象**：`refuse` 只收成功读到的 `SessionHeader`；不像 `ensureMain`，计划没规定 `header` 返回失败时是否短路。若把“没有读到头”当成“没有 owner”而继续走 `#use`，冷读得到 `session-not-found` 后、`#acquire` 前可以由另一次 `create({id, owner})` 登记同 id，随后命中已有句柄、执行本该拒绝的指令。
- **为什么是问题**：在第 26 条修好后，同 id 已存在的头不会被正常创建替换；风险是把一次读失败当作授权。遇到读失败或损坏再退回 `open`，也不能保证冷拒绝无打开副作用。
- **如何核实**：从实际 `SessionTable.create` 能独立在异步读期间登记句柄、`#acquire` 优先复用该句柄推导。计划目前只验冷读成功且发现 `owner`，没有读头先见缺失、同 id 随后出现的场景；未运行拟议 `refuse`。
- **建议改法**：三个受限指令才预查；头读失败就把已有存储码交回，不调用 `#use`。只有得到有效且无归属的头才打开或复用；不把 `storage-failed`、`needs-migration` 等降成“无归属”。用真实存储读端口暂缓一次缺失的结果、期间完成同 id 有归属创建，断言没有写入；另核对迁移、损坏码与正常无归属会话的原行为。

### 6. 持有状态缩窄后，运行状态帧不能通知只读解除（收窄，见第 6 条）

- **对应第一轮**：15。**严重程度**：重要；**类别**：接口合同。
- **位置**：`copy/plan.md:154–156`、`copy/main-conversation.md:22,53–54,64`；`packages/nb-harness/src/kernel/api/host.ts:134–140,194,292–300`；`packages/nb-harness/src/kernel/session/session.ts:709–727,748–752`。
- **现象**：`held` 只报引用、不缓存只读原因是对的；但新合同把后续可写性托给快照和状态帧。快照有 `readOnly`，`status` 帧只有 `RunStatus`。热会话的 Profile 消失后再以相同哈希回来，可以解除只读且不写日志、不发任何帧，`botsChanged` 也不变。
- **为什么是问题**：按目前“拿快照、订阅帧”的协议，已打开的读者知道它因 Profile 丢失而只读后，没有信号再取快照；不重开或盲轮询会停在陈旧状态。`log-broken` 的状态帧已有明确码，不需要另造 bot 健康状态。
- **如何核实**：实现 worktree `f5f642cd5` 的 `packages/nb-harness`，`bun test /tmp/t06-design-review-r2/header-state.test.ts`。真 JSONL 热会话经 `AgentHost.profilesChanged` 进入、解除只读；丢失只发 `diagnostic`，解除发 0 帧，日志 `head` 不变。
- **建议改法**：要保留实时可写性保证，就由会话源在重装最终态变化时推状态或快照失效通知，远程原样透传，测试同哈希恢复；若本片只交付查询，明确只有重取快照可知当前 `readOnly`，写明 t15 的刷新合同，不声称现有状态帧足够。

### 7. 浅冻结会话头仍允许改动真实 `yield` 的结果合同（收窄，见第 7 条）

- **对应第一轮**：9。**严重程度**：重要；**类别**：不变量。
- **位置**：`copy/plan.md:37–43,68,191`；`docs/specs/agent/sessions.md:87`；`packages/nb-harness/src/kernel/api/events.ts:289–307`；`packages/nb-harness/src/kernel/session/session.ts:485–500`；`packages/nb-harness/src/kernel/run/tools.ts:53–56`。
- **现象**：冻结 `owner`／`caller` 已能挡住原归属反例；第 2 稿额外承诺整个头不可变，并把冻结的权威对象同时给快照、新 `header(id)`。若照列出的外层与两子对象冻结，`origin`、`result.schema` 及其任意嵌套仍可写。创建会话当前还直接引用调用方的 `options.result` 或 Profile 声明，不能在调用方对象上就地深冻了事。
- **为什么是问题**：工具的 `yield.parameters` 直接取该 schema，热会话的模型请求可脱离落盘合同，重开又回到原值。`header` 的热／冷结果因此不等价。
- **如何核实**：实现 worktree `f5f642cd5` 的 `packages/nb-harness`，`bun test /tmp/t06-design-review-r2/header-state.test.ts`。真会话从快照把 schema 的嵌套属性类型改成 `number`，模型请求里的 `yield` 使用 `number`，重开读到 `string`；只包浅层不封住这次写入。
- **建议改法**：构造头时先拥有输入的嵌套 JSON（至少 `owner`、`caller` 与 `result`），对自有权威头深冻结一次；读盘的头直接深冻，不在每次查询克隆整份头。验收同时修改原创建参数、热 `snapshot`／`header` 的嵌套属性，核对真实工具参数与重开一致。

### 8. 首次创建已打开会话，随后量 `hold` 并不是冷打开

- **对应第一轮**：新（第 18 条改后的验收）。**严重程度**：重要；**类别**：正确性。
- **位置**：`copy/main-conversation.md:56,87,90`；`copy/plan.md:62–64,145–161,204,211`；`packages/nb-harness/src/kit/sessions/table.ts:119–131,257–285`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:293–305`。
- **现象**：输出 6 只给实际冷打开记 `bots.main-opened`，验收 1 却要求在空库里的第一次 `ensureMain` 后已记一条。`table.create` 返回前就把已打开的会话放进表；紧接着的 `hold` 复用该句柄，只加引用。已有会话也可能被另一个调用者先打开；新 `hold` 回执只有 `release`，不能区分冷热或等待同一次打开。
- **为什么是问题**：照验收记一条，量到的是热引用而不是打开，真实创建即使用时超过 2,000 毫秒也可能没有正确的告警；照输出 6 做，首启的验收断言不成立。
- **如何核实**：核对真实 `createSession` → `table.create` → `#entries` 与 `#acquire` 的分支；`hold` 按计划复用该分支，首建不再走 `#open`。这是设计路径推断，没有测未实现的指标。
- **建议改法**：由实际执行 `#open` 的一侧标记并计时，同一次共享打开只报一次，不靠调用前查 `isOpen` 猜。若只量冷打开，把该指标的首条断言移到已建会话重启后；若也要量首建，定义单独的创建口径。验收拆开首建、热持有、既有冷开与两个调用共享打开。

### 9. 建会话期间的冷打开失败会摘掉已持有的句柄

- **对应第一轮**：新（固定会话 id 与 `header` → `hold` 的并发边界）。**严重程度**：重要。**类别**：不变量。
- **位置**：`copy/plan.md:62–68,145–151`、`copy/main-conversation.md:37–43`；`packages/nb-harness/src/kit/sessions/table.ts:119–131,257–310,351–379`；`packages/nb-harness/src/kernel/session/agent-host.ts:118–125`。
- **现象**：`bot-lyra` 的头发布后、`create` 登记前，另一调用可按这个已知 id 打开会话。冷打开取锁失败并异步读取持有者详情时，`create` 能完成、替换 `opening` 表项，第三个调用已从新表项取得引用。旧 `#open` 随后用 `delete(id)` 清理失败，删掉最新的表项。第 26 条加锁后的日志复查不涉及这张表。
- **为什么是问题**：下一次查询会从内核宿主取回同一个 Session、另建一个引用数为零的表项，30 秒后关闭它。原持有 token 仍在，bot 仍报 `held`，文件锁却已释放。
- **如何核实**：实现提交 `f5f642cd5` 的 `packages/nb-harness` 执行 `bun test /tmp/t06-design-review-r2/hold-create-table.test.ts`，1 通过。真 JSONL 与真文件锁，文件端口只延后两次 I/O 的交回。用真实 `subscribeOpened` 持有拟议 `hold` 共用的引用，晚回的 `session-busy` 后查询、推 30 秒，另开存储成功取锁，此时还未释放原订阅。
- **建议改法**：`#open` 的失败与异常路径只摘自己那代 `Entry`，和 `#close` 一样核对对象身份。把同 id 的新建、冷打开与拿引用作为会话表的不变量验证。走 `create`、并发读或订阅、`hold`，断言晚回的失败后仍持锁，释放末尾引用后才空闲关闭。

### 10. 索引齐全时，子会话 fork 仍可能短暂出现在普通列表（收窄，见第 10 条）

- **对应第一轮**：8。**严重程度**：重要；**类别**：正确性。
- **位置**：`copy/plan.md:89–94,198`；`docs/specs/agent/sessions.md:89`；`packages/nb-harness/src/kit/sessions/table.ts:145–148`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:275–289`；`packages/neuro-book/src/plugins/agent/backend/subagents/relations.ts:63–65,97–110`。
- **现象**：全量索引修好了筛选条件先丢掉根的问题；但 `fork` 保留 `caller`，把新索引写下后，表只触发 `void registerFork(id)`，不等异步读索引就交回。此时 `list` 能读到 fork 的索引（含 `caller`），`relations.rootOf` 却把尚未登记的 id 当作根。这里所有祖先索引都在，不属于已写明的断链限制。
- **为什么是问题**：普通列表仍能短暂显示不该列出的后代，且下一次刷新又消失；远程和门面都经这个过滤。不是按 id 读取的权限问题，也不是第 26 条磁盘竞态。
- **如何核实**：静态核对真 fork 的落盘、异步登记与 `rootOf` 的缺项分支；第二轮没有执行未实现的列表过滤。回归应在实际 `fork` 与并发 `list` 之间只挂住关系登记的索引读取，保留列表能读到已发布的 fork 索引。
- **建议改法**：列表已经取全量索引，用同一次读取的 `caller` 构建或补足本次判断的父链，不依赖内存表的更新时机，也不增加磁盘查询；缺失索引的限制可保留。只让 `fork` 回执等登记，挡不住进行中的并发 `list`。

### 11. 异步预设校验可在撤回后重新登记旧代次

- **对应第一轮**：16（收窄）。**严重程度**：重要；**类别**：不变量。
- **位置**：`copy/plan.md:118–124`；`copy/bots.md:48,76–78`；`packages/nb-runtime/src/plugins/contracts.ts:245–259`；`packages/neuro-book/src/plugins/stickers/backend/plugin-roots.ts:21–43`。
- **现象**：文件查询是异步的，而 Runtime 的 `published` 是同步回调，`revoke` 会等待接收方收口，却不会等待先前 `published` 启动的异步工作。计划只说撤回时从“可用预设”表拿掉，没有规定撤回期间或撤回后的过时代次如何拦截旧校验结果。旧查询若晚于 `revoke` 完成，可以把已撤回的声明重新加入表；同 id 新代次发布时，迟到的旧结果还可覆盖它。
- **为什么是问题**：旧插件文件或预设可能在插件已停用、升级后继续用于建 bot；重启碰巧改变文件时序，又会改变旧贡献是否可用。表情包 `plugin-roots` 已用 generation token 避免相同的异步发布／撤回竞态。
- **如何核实**：Runtime 合同规定 `published` 为 `void` 同步回调、`revoke` 独立调用；插件包目录查询返回 Promise。对照现有 `plugin-roots.ts` 的 `live` token、`revoke` 删除 token 与查询回来后的代次比较。未实现 bot 接收方，未伪造运行时序。
- **建议改法**：接收方按贡献 id 递增代次；校验前登记 token，撤回立即失效，读取回来后在没有 `await` 的提交段再次核对 token／`handle.published` 后才写表。测试卡住真实包文件查询，先撤回、再放行；旧贡献不得复活；再发布同 id 新代次，旧结果不得覆盖新声明。

### 12. `settlePending` 的关键拒绝与重放语义没有映射到验收

- **对应第一轮**：23（收窄）。**严重程度**：建议；**类别**：测试。
- **位置**：`copy/plan.md:50–57,195,200`；`docs/specs/harness/runtime.md:206`。
- **现象**：计划已写“所有检查通过后才认领”、`input-rejected` 时事项不结算，也明定同 `commandId` 重放不比发出者；但验收表只列一个“重发同一个 `commandId`”，没有覆盖重开后由非用户重发、`input-stale` 失败后等待者仍待处理。`send` 在输入拦截之后还会检查 `replaces`，它可以因条目不存在或 `edits` 已变而拒绝。
- **为什么是问题**：新语义刻意允许“用户才能新受理、但非用户可重放用户已受理结果”；只测同发出者重发不能锁定这个合同。漏测 `input-stale` 则不能确认 claim 没有提前发生，失败后等待调用仍能得到原事项结算。
- **如何核实**：对照第一轮第 23 条的两条测试建议、修订后的 runtime 输出 111，以及 `run/commands.ts` 中拦截后 `replaceDrafts` 的失败路径。未运行尚未实现的 `settlePending`。
- **建议改法**：在行为验收里加同键先由用户受理、重开后换非用户重发且回原结果不写新结算；另用真实拦截与过期的 `replaces` 条目分别触发 `input-rejected`、`input-stale`，检查事项仍待处理且原等待者之后正常收到一次结算。
