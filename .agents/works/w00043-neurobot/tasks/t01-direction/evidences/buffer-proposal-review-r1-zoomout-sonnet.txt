# 拉远看审查：Agent 内核的输入缓冲区（Sonnet，只读）
审查对象：proposal-89af44967.md。外部出处：OpenClaw 队列文档 https://docs.openclaw.ai/concepts/queue ；Claude Code 定时任务 https://code.claude.com/docs/en/scheduled-tasks ；Codex 的 Esc 把排队消息放回输入框（openai/codex #2687，由搜索摘要得知，未读原文）。

### 1. 三件互相独立的事被捆成一份内核提案，bot 一个下游的需要决定了全部范围
严重程度：重要；类别：范围与替代方案。
位置：提案第一节三个毛病、第四节、第八节“备选方案”。
现象：第一节的三个毛病性质不同。(a) 手动压缩与 `finished` 之后话卡在缓冲区，是现有内核的缺陷（`kernel/run/loop.ts:183-197、358-364` 两处收口都不看缓冲区），普通会话就受影响，与 bot 无关；(b) 指令不看发出者、`inputEdited` 记错发出者，是授权合同缺口；(c) “留着”做成状态、按发出者放行、三种恢复模式，是为了让系统消息与用户的话共用一个缓冲区。bot 提案第三轮审查（`bot-proposal-review-r3-disposition.md`）里主 Agent 当时的推荐是“宿主不和用户共用缓冲区，只在目标空闲、缓冲区为空时发”，这样 (c) 整块不需要，(a) 只剩一个小补丁。
为什么是问题：第八节对这条路只写了一句代价（周期任务不能设成插话、排队区看不到），没有给出内核路线的量级：第六节列了 6 份 Spec、1 条 ADR，加 3 个新事件、`release`/`resume` 两条新指令、放行模式参数、快照与远程合同改形、对话视图与一项用户设置。开发者拍板时看到的是“架构上会不会更好”这个问句和一句话的对比，两边成本不对称。业界对照：Claude Code 的定时任务“低优先级入队，只在两轮之间、Claude 空闲时触发，错过的不补”（上面的官方文档）；OpenClaw 的缓冲是平的 FIFO 加 `collect` 等模式，显式 Stop 是终态（排队的取消，不留着），没有“留着”这种状态。本提案比两者都重，需要有理由；现有理由只有 bot 的“周期任务可以是 steer”，这是开发者 2026-11-18 的愿望，没有场景证据说明周期任务需要在运行中插话。
建议：把 (a)、(b) 拆成独立的小提案或同提案的第一阶段先落地（它们对所有会话是纯修复）；(c) 单独成阶段，并补一段量级对比，让开发者在知道成本的前提下确认“周期任务可以是 steer、排队区可见”值不值这些改动。

### 2. “停止后留着”是现有界面的默认路径，改成“留着的先跑”等于改了每个普通会话最常见的一步，提案没有评估
严重程度：重要；类别：影响面、产品行为。
位置：提案第四节第 3 小节“留着的先跑”、第五节“普通会话的行为变化”、第四节第 7 小节停止按钮。
现象：现在界面的停止按钮就是 `abort{keepQueue: true}`（`packages/neuro-book/src/plugins/agent/web/session-host.ts:1359-1365`，注释“排队的消息留着（开发者 2026-11-05 定）”；子代理的 `kill` 也是它，`backend/subagents/children.ts:53`）。用户点停止多半是因为模型走偏，接着会打一句纠正。现在的行为：纠正的话先开一轮，之前排队的跟在后面。提案：之前排队的先跑，缺省 `merge` 把它们与纠正的话合成一条输入。也就是用户停下模型后，下一次发出的话会和停止前排的话粘在一起、排在后面。
为什么是问题：这是对所有普通会话的行为反转，不只是 bot；提案第五节只写了“排在新话前面”一句，没有说明为什么“纠正的话在最后”对用户是对的。开发者 2026-11-18 的话是“留着的先跑”，指的是恢复时的顺序，不一定覆盖“用户刚打断模型、随后给出纠正”这一场景；提案没有把二者区分开。第七节也没有说两个停止选项里哪一个是主按钮、缺省是哪个。
另一个同类问题：宿主发的留着的话没有过期。bot 周期任务在 `error` 或 `stopped` 后留着，用户一周后回来发一句话，缺省是一周前的周期提示词先跑（或并进用户那句话）。bot 提案用“目标忙时跳过”限制了每条一份，但多条目、多天仍会攒；提案没有任何数量上限或过期。OpenClaw 为此有 `cap: 20` 与 `drop` 策略（上面的官方文档）。
建议：把“留着的先跑”限定在“因出错或重启而留着的、同一发出者”，停止后用户的新话缺省排最前（或让两种顺序都进用户设置，只发一种缺省并写理由）；宿主的留着的话在放行时由宿主决定是否还要，给宿主消息加过期或上限；写明停止按钮的缺省。

### 3. 回滚说法与 Spec 的降级规则相反；提案依赖的“宿主”发出者尚不存在，两份提案互相引用
严重程度：重要；类别：数据格式与演进、依赖顺序。
位置：提案第五节“迁移与回滚”、第四节第 4 小节权限表；`docs/specs/harness/session.md:181`；`packages/nb-harness/src/kernel/api/basics.ts:55`。
现象一：提案写“回滚时新事件会被旧内核当作未知的会话级事件，需要随内核一起回滚”。但 session.md 第 181 行规定：“不支持降级：旧版本读到它不认识的内核事件名……得 `log-corrupt`，不改动文件”。所以回滚后带 `inputHeld`、`inputReleased`、`inputMerged` 的会话打不开，不是“当作未知事件忽略”。同文件第 179 行：事件名与字段只加不改；这三个事件一旦发布，名字与字段就是永久合同，要改只能升格式版本并写迁移脚本。提案没有评估这一点，也没有给出“发布后事件形状不对怎么办”的出路。
现象二：`Issuer` 现在只有 `user | session` 两种（`basics.ts:55`）。权限表里的“宿主”依赖 bot 提案（`neurobot.md` 第六节）新增的 `host` 发出者，而 bot 提案又把本提案当作前置（缓冲区取法那一节）。两份提案都在 `reviewing`，没有定先后：本提案能不能脱离 bot 提案单独落地、`host` 的 `source` 形状变了会不会牵动本提案的 `by`、`inputReleased{by}`、`runStarted` 的字段，都没说。
建议：回滚一句改成与 session.md 一致（回滚前新日志不可读），或者把三个新事件的字段先做最小集；写明落地顺序（先 `Issuer` 与 `by`，再状态，或反过来），让本提案不依赖尚未定稿的 `host` 形状（权限表先只写 `user`、`session`）。

### 4. 内核里放进了 bot 才需要的策略：按发出者分别放行、五种原因、“只有用户能放行 stopped”
严重程度：重要；类别：过度设计（YAGNI）、扩展锁死。
位置：提案第四节第 1、3、4 小节。
现象：状态不是一个开关，而是“就绪 / 留着 × 五种原因（error、stopped、interrupted、finished、cannot-continue）× 原因详情”。放行有四条路（发新话、`start`/`resume`、`release`、`agent_send`），每条再按发出者（用户、会话、宿主）和原因分权限，另有三种模式、`stopped` 的例外。数一下表：收口 6 行、放行 4 条路、发出者 3 类、模式 3 种，上界 6×4×3×3=216 个组合（不是每个都可达，但每个不可达的也要在 Spec 里说明为什么），权限表另有 4 行 × 3 列。
这些组合里，凡是“会话或宿主放行自己排的”都只有 bot 需要：普通会话里只有用户发话，`session` 发出者仅用于子代理的 `agent_send`。提案第四节第 3 小节自己写明“bot 提案里，日程插件在出错后用 `release` 放行自己的周期任务”。把“出错后系统自己重试”的策略放进所有会话共用的内核，是下游需要决定上游形状：重试本该是日程插件的策略（它能 `remove` 自己的条目、再决定重发或标记“等你处理”）。
更简单的内核做法（供开发者比较，非定论）：留着只有一个整体开关，缓冲区在出错、停止保留、重启中断、收尾后整体“暂停”，只有用户的 `send`、`start`、`resume` 清除；原因只作显示用的一个字段；没有按发出者放行，也没有 `release`。这与 t07 决定 3 的原话（“重启后队列还在但不自动发出，等用户确认”）一致，也与开发者“停止后等恢复”一致。代价：宿主的周期任务在出错后要等用户回来，不能自己恢复，bot 提案要接受“出错就停到用户回来”。
没有记录的理由：t07 决定 1 的“出错或中止时不处理”写的是“照搬分支”（`.agents/works/w00032-agent-integration/tasks/t07-run-control/README.md:38`），没有写原因；合理的推断是避免失败运行被自动重跑烧钱，这个理由对“整体暂停到用户回来”同样成立，但不要求“按发出者放行”。
建议：开发者先定“周期任务在出错后要不要自己恢复”；不需要就用整体暂停，状态与权限表缩到现在的三分之一。

### 5. 合并输入做进内核：会话事实被改写，且没有证据说明需要
严重程度：重要；类别：YAGNI、数据格式锁死。
位置：提案第四节第 3 小节 `merge`、`inputMerged{from, into}`、用户设置“恢复方式”。
现象：缺省模式 `merge` 把“同一发出者相邻的留着的话与新话”合成一条输入。内核因此要新增事件 `inputMerged`、一个新的输入 id、“已合并”这种离开缓冲区的原因，并决定：文本用什么分隔；`payload`、`attachments`（`loop.ts:83` 的 `steer` 事件带这两项）怎么合；合成后是否重跑输入拦截链（`edit` 要经拦截链，`runtime.md` 输出 29）；`steer` 与 `followup` 混在一起时合成什么模式；审批模型按 `by` 分类的材料合并后是否仍可追溯。提案一条都没写。
为什么是问题：(1) 合并是产品策略，不是缓冲区的机制：Codex 的排队消息是客户端草稿，Esc 把它们放回输入框由用户自己合并（上面的出处）；OpenClaw 的 `collect` 是排队时的到达模式，不是恢复方式。(2) 日志里留下的是合成后的一条加一个 `inputMerged`，原话只能从 `from` 追；事件形状按 session.md 第 179 行“只加不改”一旦发布就锁死，后悔只能升格式版本。(3) 三种模式、一个用户设置、远程合同参数，用来支持的用户场景只有开发者那一句话，没有出现过用户抱怨的记录。
建议：内核只提供机制：`release` 与 `resume` 带两种模式（原样保持 `keep`、全部按排队 `followups`）；`merge` 作为宿主在界面层的操作（取出留着的话，拼成一条再 `send`），不进内核、不进日志格式。若开发者坚持内核合并，先在 Spec 草稿里把上面五个问题写出来再定事件形状。这条是开发者 2026-11-18 点名的缺省，所以只当作建议，由开发者定。

### 6. “留着”既写成事件又能由旧事件推出，同一份状态两条来源
严重程度：建议；类别：与 ADR 0035 的一致性、可维护性。
位置：提案第四节第 5 小节“旧日志没有这些事件：归约时按收口方式补出状态，规则同第 2 小节”；`docs/adr/0035-harness-log-driven-kernel.md:25`。
现象：提案自己承认，留着的状态可由已有事件推出：缓冲区非空而且最近一次 `runEnded` 是 `error`、`aborted`（保留队列时缓冲区非空，`commands.ts:171` 只在不保留时才写 `inputRemoved`）、`interrupted` 或 `finished`，就是留着，原因取自 `runEnded`，错误码取自 `runEnded.error`。第 5 小节为旧日志写了这套补算规则，新日志却再写一遍 `inputHeld`。于是归约里有两条路径（读事件、补算），而且补算的结果“只在内存里，不回写”，同一个会话在新旧日志混合的时候（旧日志开头、新事件在后）要保证两条路径衔接一致，提案没有写衔接规则（例如旧日志里的留着的话，之后用户发新话写 `inputReleased`，这时归约要认旧话是补算出来的留着）。ADR 0035 的核心是“一个来源”，这里违背了它的精神。
另外：留着的原因取自一次 `runEnded`，回退（`rewind`）之后这次运行可能已不在当前路径上，缓冲区是会话级、不随回退撤销（提案自己写了），留着的话的原因就指向一条旁支上的收口；提案没有说回退后原因怎么显示。
建议：二选一并写进 ADR 补条：(a) 状态始终由事件与收口推出，只为放行写 `inputReleased`（含按条放行），不写 `inputHeld`；(b) 始终写 `inputHeld`，旧日志在打开时一次性补写（一次迁移，带版本标记），之后只有一条路径。(a) 更小，也最符合“状态由日志归约”。

### 7. 提案细节多、取舍少：该讲清的几处架构问题没讲，“待定项：无”不成立
严重程度：建议；类别：缺失的取舍。
位置：提案第三节（行号引用）、第四节第 2 小节、第七节。
现象：
- 提案用大量篇幅引 `loop.ts` 行号、输出编号，却没有一张状态转换图或一条不变量：留着的话与就绪的话谁先、合并后的顺序、放行后在跑的会话里“转成就绪”排在已有就绪之前还是之后（第 3 小节只写了空闲时的顺序）。“留着的先跑”是对 FIFO 的反转，提案没有说这条反转的边界。
- “只压缩的运行压完后在同一次运行里接着开一轮”：这次运行以 `runStarted{kind: "compact"}`（`loop.ts:183` 一带按 `run.compact` 分支）开始，却会含对话轮。依赖运行种类的消费者（界面、`agent_send` 的任务登记按 `runId` 跟随、`runResult`、`waitRun`）会看到一次“压缩”运行带着对话回复。提案只说“不另记一次启动”，没有评估这个种类与实际内容不一致的后果，也没有对比它在第八节否决的“另开一次运行”之外的第三种做法（例如压缩运行收口后，由发起压缩的指令自己检查缓冲区并调 `start`，保持种类干净）。
- 输入缓冲区这个概念的位置：Codex 把排队当客户端草稿（Esc 放回输入框），OpenClaw 是会话级队列带 `cap`、`drop`，而本仓库按 ADR 0035 放在日志里。放进日志是对的，但提案没有写“为什么暂停语义属于内核而不是宿主”，这是本提案最该写的取舍，现在只能从 bot 提案的审查历史里反推。
- 空闲时 `enqueue`（`runtime.md` 输出 3 只写入队，不开运行）遇到留着的话怎么办，第 3 小节的“谁发新话放行自己留着的”没有覆盖：`enqueue` 算不算“发新话”、放行后谁开运行。
- 第七节写“无”，但上面几条加上第 2 条的停止缺省、第 5 条的合并细节都是未决事项；第三轮审查已经三次显示，这个区域每次都在“表里没列到的路径”上出问题。
建议：补一小节“不变量”（几条：顺序、谁能取、谁能放行）与一张状态图；补“为什么在内核”的取舍段；把上面几条列进待定项。

## 未发现问题的方面
- 问题本身是真的：只压缩的运行与 `finished` 收口不看缓冲区，读 `loop.ts:183-197、358-364` 可核实（复现脚本在提案引用的 evidences 里，我没有重跑）；“留着”不是状态也成立（`loop.ts:381-395` 的取法不看来源）。
- 第 2 小节里“出错、中止保留、重启之后不取”与 t07 决定 1、3 的原话一致，没有越过开发者已定的决定。
- 子代理一节与现有 `agent_send` 规则（`subagents.md` 输出 10）没有发现冲突。
- 提案没有改变插话与排队的基本含义，这条非目标与内核现状相符。

## 我认为应交开发者决定而提案自己定了的事
1. 周期任务要不要“可以是 steer”并出现在排队区里：这决定了要不要走内核路线（第 1、4 条），提案把它当前提，没有给出成本对比。
2. 缺省的恢复顺序“留着的先跑、合并成一条”，对停止后用户的纠正话的影响（第 2、5 条）。
3. 宿主发出的留着的话是否过期、是否有上限（第 2 条）。
4. 出错后周期任务是否要能自己恢复（决定第 4 条的整体暂停方案能不能用）。
5. 三个新事件的发布时机与回滚说法（第 3 条）。
