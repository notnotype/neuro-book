# 《Agent 内核的输入缓冲区》第三稿审查（Claude Opus，内核与日志合同为主，兼看前端）

审查对象：/tmp/review-buffer-r3/proposal-54de248e4.md。第二轮处理表 29 条逐条对过第三稿正文：文字上都改到了；其中 B6、B7、B17 改到的做法本身引出了下面第 4、6、1 条的问题，单列。

### 1. 子会话：在“交出结果”那一轮或收口窗口里到达的父 Agent 的话，agent_send 交回的是上一个结果，话留着或跑在没人跟的运行里
- 严重程度：重要（话静默不达、结果错配）
- 位置：第四节第 1 小节“决定收口与写下收口在同一步”；第 3 小节“运行不再取输入时”“子会话”第一条；`plugins/agent/backend/subagents/tools.ts:442-444`（`runId ?? currentRunId`）
- 现象：(a) 子会话的最后一轮在调 yield 时父 Agent 插话：`send` 交回 `{runId: null, currentRunId: X}`，X 以 finished 收口，插话没被取、留在缓冲区。已用真实内核复现：`cd packages/nb-harness && bun test /tmp/review-buffer-r3/yield-steer.test.ts`，输出 `currentRunId` 等于这次运行、`run: finished`、`buffer: [["steer","改成两个字以内"]]`。agent_send 按 X 认任务，等到的是 yield 的结果，工具结果写“话已送达”。按第三稿这条插话以 `cause: finished` 留着，只有父 Agent 再发话才放行；父 Agent 已拿到结果，多半不会再发，话永远留在子会话里。(b) 父 Agent 的话落在“已决定收口”之后：按第 3 小节回到空闲后放行并开新运行 Y，但 send 已交回 `currentRunId: X`，Y 没有任务跟，Y 的结果不会交给父 Agent。
- 为什么是问题：“在那之前受理的话由这次运行取走”只对正常结束成立；yield、文字收口、出错、只压缩的运行都不取。`send` 的成功值分不出“这次运行会取走”“会留着”“会在之后的新运行里跑”，调用方只能按 currentRunId 错认。
- 建议：`send`、`enqueue` 的成功值只在这次运行确实还会取输入时带 `currentRunId`，否则带 `deferred: true`；给调用方一个按 `inputId` 等它被哪次运行取走的办法（或在 `inputConsumed` 后的帧里可查）。subagents.md 输出 10 写明：收口时插话被留着的，工具结果写“未送达，已暂停”，并给 N 条。

### 2. “宿主只能 start 自己开的运行”只拦了 start：resume 与 send 都能接着跑用户的运行，父 Agent 能绕过用户对子会话的停止
- 严重程度：重要（权限与开发者 2026-11-18 第二轮决定不符）
- 位置：第 3 小节“只放行、不送新话”（`resume`：“会话里有中断或失败的那一轮时，先接着跑它”）、失败表只有 `start` 一行 `not-allowed`；第 1 小节“暂停的运行按空闲算”；第 5 小节权限表 `release、resume` 一行
- 现象：(a) 宿主对用户的普通会话调 `resume`：没有发出者限制，先接着跑被中断的那一轮，正是开发者说“只有用户能点继续”的那件事。(b) 叶子停在用户运行中途（回退、重试前）时，宿主 `send`：现有代码 `commands.ts:109-110` 直接 `launch(paused)`，第三稿只说写 `runResumed{by}`，没说宿主不能接着跑别人的暂停运行。(c) 用户在子代理浮层停止子会话后，父 Agent 调不带话的 `agent_send` 改走 `resume`，`commands.ts:146` 只在最后一轮正常完成时拒绝，aborted 的轮会被接着跑。用户停的那一轮被父 Agent 立刻续上，`heldBy: "user"` 只挡住了缓冲区里的话，挡不住续跑。
- 建议：把“接着跑一次没收口或没完成的运行”定成一个权限，`start`、`resume`、`send`（暂停的运行）共用：用户全部；宿主与会话只能续 `runStarted.by` 是自己的、或会话归自己的；不能续时 `resume` 只放行、不续跑，`send` 开新运行或得 `not-allowed`（交开发者选一种）。用户停止的那次运行，父 Agent 能否续跑，按第二轮决定应只有用户能。

### 3. 用户在任务中心停子代理，记成父会话停的：没有 heldBy: user，父 Agent 能马上放行
- 严重程度：重要（发出者失真，违背第二轮决定“用户停止子代理后，父 Agent 排给它的话也只有用户能放行”）
- 位置：第 5 小节“前提”只列了 `agentKey` 与 `startTask`；代码 `plugins/agent/backend/remote.ts:219` `jobs.kill(null, jobId)`（用户经远程停）→ `jobs/center.ts:222` `job.driver.kill()` → `subagents/children.ts:46-53` 用 `{kind: "session", id: job.owner}` 的视图 `abort{keepQueue: true}`
- 现象：任务中心（远程）的停止与父 Agent 的 `kill` 工具走同一个 driver，内核看到的发出者都是父会话。按第 2 小节，这次收口写 `inputHeld{cause: 停止·父会话}`、不带 `heldBy`，父 Agent 下一次 `agent_send` 就放行全部。浮层的停止（`web/session-host.ts:339` 走远程 `abort`）是用户，同一个“用户停子代理”两个入口结果不同。
- 建议：`kill` 带发出者（`kill(by)`），远程任务中心传用户；第 5 小节“前提”与 Spec 改动清单加上 jobs.md 输出 11 与 `children.ts`。顺查 `jobs/center.ts` 其它停止入口（停服务端时的 `kill("interrupted")` 只对 shell）。

### 4. agentKey 的 session(id, issuer?) 仍让调用方自填身份：“缺省是宿主”挡不住插件自称用户或别的会话
- 严重程度：重要（权限表的前提不成立）
- 位置：第 5 小节“前提”（“插件拿到的会话视图缺省身份是带它插件名的宿主”）；`plugins/agent/shared/contracts.ts:110` `session(id: string, issuer?: Issuer)`；`backend/agent.ts:331-333` 原样传给 `table.view(id, issuer)`；`backend/plugin.ts:199` 现在是普通共享服务 `provideService(agentKey, runtime.service)`
- 现象：第三稿只改“缺省”，没说去掉或限制 `issuer` 参数。按调用方门面盖章之后，插件照样能写 `session(id, {kind: "user"})` 拿到用户的全部权限（放行 heldBy: user 的话、清空别人的话、续跑用户的运行），或写 `{kind: "session", id: 父会话}` 冒充父 Agent。第三稿“安全”一节的结论建立在盖章上，而盖章只是缺省值。
- 建议：门面上的 `session(id)` 不收 `issuer`，身份一律是 `{kind: "host", source: {plugin: 调用方插件}}`；`nbook.agent` 自己代父会话发话用内部的 `SessionTable.view(id, issuer)`，不经 `agentKey`。若确有插件要以会话身份发话（例如插件工具在会话里替这个会话发），给出受限入口（只能是调用它的那个会话，从 `ToolSessionContext` 来），写进 sessions.md。改 `agentKey` 为按调用方提供是破坏性的服务形状变化，要列进第五节“接口”。

### 5. enqueue 在空闲时自相矛盾：自己留着，却放行并跑起更早留着的话；早 1 毫秒（收口窗口里）到达又会自己跑
- 严重程度：重要（同一指令的结果取决于时间窗，话卡住或意外发出）
- 位置：第 1 小节“空闲时排进来的：inputQueued 直接带 state: held”；第 3 小节“放行跟着新话走”把 `enqueue` 列为放行入口、“放行时会话空闲就开运行”、“运行不再取输入时…回到空闲时…再按这次的放行处理”
- 现象：(a) 会话空闲、缓冲区里有用户停止留下的 A、B，用户（或插件）`enqueue` C：按放行规则 A、B 被放行并开运行；C 本身是“空闲时排的”留着，A、B 跑完后 C 不会被取。没有 A、B 时，同一个 `enqueue` 只是把 C 留着、不开运行。(b) 只压缩的运行、停止进行中或收口窗口里 `enqueue` 的 C：回到空闲时“按这次的放行处理”，C 跟着跑掉；晚一点（已经空闲）到达就一直留着。现行验收 2“空闲时入队的排在下一句之后”与这两种都对不上。(c) 第 4 小节的恢复方式只给 `send` 定了 `replaces`/`release`，界面在运行中回车走的是 `enqueue`（`web/session-host.ts:1105`），用户选的“合并一起发”在这条路径上不生效，文中没说。
- 建议：先定“新话放不放行它自己”：要么 `enqueue` 不是放行入口（只排、只留着，t07 的本意），收口窗口里到达的 `enqueue` 也只留着；要么 `enqueue` 也放行、空闲时自己也就绪并开运行（那它就成了 `send`）。二选一后把三种时间窗的结果写成一张表；`enqueue` 是否带恢复方式选项一并定。

### 6. compact({release: "arrived-during"}) 在第三稿的通用规则下不起作用；“系统发起的压缩压完留着”实际不成立
- 严重程度：重要（新增一个指令选项与 Spec 条目却没有可观察的效果；与开发者决定的说法冲突，应交开发者）
- 位置：第 3 小节最后一条“用户自己发起的压缩”；同节“运行不再取输入时（只压缩的运行…）到达的新话与放行…回到空闲时…再按这次的放行处理”；第五节“手动压缩时发的话…改成压完自动放行”
- 现象：只压缩的运行里到达的每条话都来自 send、enqueue 或异步回答之一，按“放行跟着新话走”与“运行不再取输入时”的规则，回到空闲时这条话的发出者会放行自己排的（含这条本身，第 3 小节停止的例子写明“然后是这句”）。于是：用户发起的压缩，期间到达的话不靠 `release` 选项也会全部跑；系统（宿主）发起的压缩，期间用户发的话同样会跑，“压完留着”只剩一个空集。`release: "arrived-during"` 能多放行的只有“压缩期间到达、它的发出者自己又不放行”的话，而按现规则不存在这种话（除非第 5 条改成 enqueue 不放行，那时它才有对象）。
- 建议：与第 5 条一起定。若保留“系统发起的压缩压完留着”的本意（用户在系统压缩时打的话要等用户再确认），就要把“运行不再取输入时到达的话回到空闲再放行”限定为停止与收口窗口、不含只压缩的运行；否则删掉 `compact` 的 `release` 选项与 sessions.md、conversation.md 里对应的条目，并把开发者决定表述改成“压缩期间到达的话压完照常跑”交开发者确认。

### 7. 编辑重发（rewind{resend}）也是放行入口：被放弃那条分支上留着的话，会排在编辑后的这句前面、在更早的位置先跑
- 严重程度：重要（改变“编辑重发”的含义，应交开发者；“留着的先跑”是在“停止后恢复”的语境里定的）
- 位置：第 3 小节“放行跟着新话走”列入 `rewind{resend}`，“留着的先跑：放行出来的排在这次新话前面”；第 4 小节恢复方式只给 `send` 定了 `replaces`；界面的编辑走 `remote.rewind({to: before-turn, resend})`（`web/session-host.ts:604-661`）
- 现象：用户停止后留着 A、B（写给停止时那段上下文的），然后上翻编辑第 3 轮的话重发。按第三稿：回退到第 3 轮之前，A、B 被放行并先跑（各开一轮，或保持原插话），然后才是编辑后的话。A、B 引用的上下文在被放弃的分支上，模型在第 3 轮之前收到它们。缺省的“合并一起发”在这条路径上不存在（`rewind` 没有 `replaces`）。目标在运行中途时还有一层：暂停的运行接着跑时 `loop.ts:205-208` 取缓冲区第一条，不是重发的这条。
- 建议：交开发者二选一：编辑重发不放行（留着的继续留着，重发的这句直接开轮，`rewind{resend}` 从放行入口里去掉），或放行但按用户的恢复方式（那要给 `rewind` 加 `replaces`/`release`）。无论哪种，暂停的运行接着跑时应先取重发的这句（受理批里直接取走它），在 runtime.md 输出 36 写明。

### 8. 停止进行中到达的别人的话，按字面会一起盖上 heldBy: "user"；两个发出者同时停时取谁的没定
- 严重程度：重要（发出者失真，宿主或父 Agent 自己的话放不出来）
- 位置：第 2 小节“保留时 inputHeld{cause: 停止与谁停的, heldBy}（用户停的带 heldBy: "user"）”“清空只清停止受理那一刻在缓冲区里的”；第 3 小节“运行不再取输入时…回到空闲时，先把剩下的转成留着”
- 现象：(a) 用户点“停止，排队的留着”，停止进行中（宽限期可达 `ABORT_GRACE_MS`，工具与模型端口迟迟不交回时更久）bot 的周期任务或父 Agent 的话到达。收口批把“剩下的”转成留着，`inputHeld` 只有一个 `cause` 与 `heldBy`，字面上这几条也是 `heldBy: "user"`：用户从没停过它们，宿主与父 Agent 却再也放不出自己的话（第 3 小节表“不带 heldBy: user”）。清空的范围已经按“受理那一刻”划了线，保留的范围没有。(b) 子会话同时被父会话连带中止（session，keep）与用户在浮层停止（user，keep 或清空）：`control.ts:138-144` 第二次 `abort` 只等第一次收口，发出者与是否保留只能取第一个；若父会话在先，用户的停止不留痕，回到第 3 条的结果。
- 建议：写明 `heldBy: "user"` 与清空只作用于停止受理那一刻在缓冲区里的条目；之后到达的另写一条 `inputHeld`，`cause` 为“停止进行中到达”、不带 `heldBy`（一个收口批可有多条 `inputHeld`，形状够用）。并发停止：用户的停止优先，或按“清空 > 用户保留 > 其他保留”合并，并让后到的停止也把发出者交给运行循环。

### 9. “决定收口与写下收口在同一步”能做到，但 control.idle 要到 finally 才变；之后的“回到空闲再放行”是内存里的延后动作，与收口不在一个批
- 严重程度：建议（实现结构与时序，Spec 里要写清，否则返工）
- 位置：第 1 小节第 3 条；第 3 小节“运行不再取输入时”；`run/loop.ts:125-139`（`end` 先 `queue.drain()` 再把在队列外算好的 drafts 交给 `write`）、`loop.ts:378,393-394`（读缓冲区在队列项外）；`run/control.ts:118-133`（`#active` 在 `.finally` 里才清、之后 `onIdle`）；`commands.ts:100-107`（按 `control.idle` 判断）
- 现象：(a) 要照字面实现，收口批（含 `inputHeld` 的 ids）与“有没有可取的”判断必须在同一个 `queue.run` 回调里算，`write` 要改成收一个在队列项里求值的构造函数；`end()` 的 drain 与写之间现在能插进别的受理。可行，但不是改几行。(b) 收口批写下之后、`.finally` 之前，`send` 仍看到 `active`，只写 `inputQueued` 并交回 `currentRunId`：这段也是“运行不再取输入”，由延后放行接手。延后放行只在内存里：与收口不同批，中间能插进宿主的 `send`（它先开运行，“留着的先跑”被打乱）；进程在两批之间退出，用户刚发的那句以上次运行的原因“已暂停”；开不起来（没有模型）时没有调用方可交失败；还要排在 `onIdle` 的重新装配之后。
- 建议：二选一写进 runtime.md：收口批里一并写延后的放行与新运行（`inputHeld`、`inputReleased`、`runStarted`、取第一条同批，崩溃安全、无交错），或在收口队列项里置一个“已收口”标记，让之后的受理直接按空闲开运行（`launch` 在旧循环 finally 前开新运行，`control.ts:124` 的 runId 守卫已能容下），只把只压缩与停止进行中留给延后处理。延后放行开不起来时的 `cause` 码一并定。

### 10. 旧日志里空闲会话的就绪条目不补成留着：升级后第一次重试或任何人开的运行仍会顺手带走它们
- 严重程度：建议（一次性，但正是问题一第 2 类要消除的行为）
- 位置：第 1 小节“旧日志…条目都是就绪的，行为同现在，不另做补算”；第五节“错误气泡的重试不再顺带发出排着的话”
- 现象：现有会话里用户停止留下、或出错后排着的话，在新内核下是就绪的：重试走 `start`，暂停的运行接着跑时 `loop.ts:205-208` 取第一条、一轮结束时 `loop.ts:393` 取排队；宿主的 `send` 开的运行在第一轮结束时同样取走它们。行为变化清单里“重试不再顺带发出”对所有升级前的会话都不成立，直到下一次收口。
- 建议：打开会话时，若会话空闲且缓冲区里有就绪条目、日志里没有任何 `inputHeld`，与打开时的恢复一样写一条 `inputHeld{cause: legacy}`（旧内核本来就读不了新事件，不增加降级成本）；或在行为变化里写明旧会话的这条例外。

### 11. 权限与事件形状的几处空白：start 依赖别的提案才有的 owner；宿主不能 abort；heldBy 是字符串、cause 没有形状
- 严重程度：建议（日志格式与内核接口，发布后改不了）
- 位置：第 3 小节“会话头的 owner 是它自己的会话”；第 5 小节权限表 `abort` 一行；第 6 小节事件表
- 现象：(a) 会话头的 `owner` 是 bot 提案（neurobot.md“归属”）新加的字段，本提案改的是对所有会话生效的内核，却把权限判断建在它上面，第 6 小节与 Spec 改动清单都没有 `owner`；两份提案的落地次序一旦反过来，`start` 的这条规则无从实现。(b) 权限表的 `abort` 只写了用户与会话，宿主一栏是空的，按“不允许时得 not-allowed”，bot 停不了自己开的周期运行（超时、用户在 bot 视图点的停止若经插件发出也会被拒）。(c) `heldBy: "user"` 是字符串，`inputRemoved.by`、`inputReleased.by`、`runStarted.by` 都是发出者对象；以后要表达“只有某个宿主能放行”时只能再改形状。`cause` 只写了“收口方式与码”“停止与谁停的”“空闲时排的”，界面要按它取文案（第 7 小节），不先定成带判别字段的联合（例如 `{kind: "run-ended", runId, reason, code?} | {kind: "stopped", by, runId} | {kind: "queued-idle"}`），`inputQueued` 与 `inputHeld` 两处会各写各的。
- 建议：(a) 把 `owner` 写进本提案第 6 小节（会话头字段），或改成内核只认 `runStarted.by`，“会话归谁”由宿主在调用前判断；(b) 宿主能停自己开的运行与归自己的会话里的运行；(c) `heldBy` 用发出者对象，`cause` 现在就定判别联合，旧日志读法写进 session.md。
