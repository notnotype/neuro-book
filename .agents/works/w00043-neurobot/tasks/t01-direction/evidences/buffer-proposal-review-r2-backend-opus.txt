# 后端审查报告第二轮（Opus）：提案《Agent 内核的输入缓冲区：每条带状态》第二稿
审查对象：/tmp/review-buffer-r2/proposal-1e9c0cce4.md（1e9c0cce4）。按核实顺序追加；复现脚本在 /tmp/review-buffer-r2/repro/，在 packages/nb-harness 下 `bun test <文件>` 运行。

### 1. “一轮正常结束时取排队，照旧、不受影响”不成立：循环读缓冲区与写 runEnded 不在同一个队列项里，用户在回复末尾发的 send 交回“已排进当前运行”，随后被当成“completed 后留着”
严重程度：重要；类别：并发与时序、与代码不符（重点 1、2）
位置：提案第四节第 1 小节最后一条“一轮正常结束时取排队、同一次运行接着跑，照旧：这时会话没有回到空闲，不受影响”；代码 run/loop.ts 第 393–394 行（先读 buffer，再 `write([...turnEnded, runEnded])` 排进队列），run/commands.ts 第 100、107 行（send 的受理按 `control.idle` 判断，而 `#active` 要到 control.ts 第 124 行的 finally 才清掉）。
现象：循环在第 393 行读缓冲区是在队列项之外做的；之后它把 runEnded 的写入排进队列。若一条 send 的受理项已经排在它前面（例如输入拦截还在等），send 受理时 `control.idle` 仍为 false，只写 inputQueued、交回 `{runId: null, currentRunId}`；接着 runEnded 写下，话留在空闲会话里。
核实：/tmp/review-buffer-r2/repro/end-race.test.ts（真实内核；用一个 assistant 反应与一个输入拦截卡住时序，不绕过运行时）。输出：`late send: {"inputId":…,"runId":null,"currentRunId":…}`，`events: inputQueued runStarted inputConsumed inputQueued runEnded`，`status: idle buffer: ["迟到"]`。
为什么是问题：按第二稿的规则，这条 inputQueued 在 runEnded 之前，回到空闲时算“留着”，原因是“completed”。用户点的是发送（不是排队），界面拿到的是“已进入当前运行”，结果却是一条“已暂停”、要再点继续的话；原因码 completed 也解释不了它。问题一第 1 类（空闲了还有话没人取）在这条路径上并没有消失，只是换成了留着。同样的窗口也在第 378 行（还有插话就不结束）与第 388–389 行（文字收口）之前。
建议：把“读缓冲区决定接着跑还是收口”与写 runEnded 放进同一个队列项（例如在队列项里重新读缓冲区、有就绪的 followup 就改写成取它），或让 send/enqueue 在受理时把“运行已决定收口”视为空闲（control 增加 ending 状态，由循环在排 runEnded 前同步置上）。提案应写明这条不变量：“运行收口的判断与 runEnded 在同一个写入批里，之后受理的输入按空闲处理”，并加一条验收：回复写下后、runEnded 之前到达的 send 开新运行或被同一次运行取走。

### 2. 暂停的运行（回退到运行中途）让“留着由日志推出”与内存判断不一致：接着跑不写任何事件，日志分不出“暂停时排的”与“运行中排的”；`runStarted` 记发起者在这条路径上无处可写（第一轮 B13(b) 未处理）
严重程度：重要；类别：接口与合同、遗漏（重点 1、3）
位置：提案第四节第 1 小节“空闲时排进来的话（enqueue）也算留着”“留着由日志推出”，第 5 小节“`runStarted` 记下开这次运行的发出者（send、start、resume 都算）”；代码 run/control.ts 第 73–80 行（`idle` 只看有没有循环，`paused` 是叶子上没收口的运行），run/commands.ts 第 109–110 行（send 遇暂停运行：只写 inputQueued，直接 launch 原 runId）、第 136–137 行（start 遇暂停：`drafts: []`），run/tree.ts 第 73–75 行（rewind{resend} 遇暂停同样），run/interaction.ts 第 139–141 行（异步回答同样），run/recover.ts 第 71 行（叶子由 leafChanged 定时不恢复）。
现象：叶子停在运行中途时 `control.idle` 为 true，按提案“空闲时排的”应留着；但日志里那次运行没收口（path 状态 `run !== null`），与“运行中排的”在日志上长得一样。接着跑（send、start、resend、异步回答、提案新加的 resume）都不写事件，所以从日志重算时无法知道某条 inputQueued 发生时循环在不在跑。同理，接着跑之后、第一条 path 事件写下之前崩溃，重开时叶子仍由 leafChanged 定、不走恢复、不写 runEnded：这次“回到空闲”在日志里没有任何痕迹，期间排进来的话按日志是就绪的，之后任何人（权限表允许宿主 `start`）让暂停的运行接着跑都会把它取走——正是问题二要消灭的情形。
为什么是问题：第二稿把“一处”落在“回到空闲”，又说状态只由日志推出、新旧同一条规则；暂停运行是现成的、已有 Spec（runtime.md 输出 36）与界面入口（错误气泡的“重试”走 rewind + start）的路径，在这里两条承诺互相矛盾。`runStarted` 记发起者在这里也落空：接着跑不写 runStarted，“这次运行是谁开的”在 retry/swipe 之后无从查起。
建议：二选一并写进提案：(a) 接着跑暂停的运行时写一条 path 事件（例如 `runResumed{runId, by}`），它同时承担“谁开的”与“从这里起循环在跑”；崩溃恢复对“resumed 之后没收口”的照常补 runEnded{interrupted}；(b) 明确“暂停算运行中”，空闲时排的只看叶子上有无未收口的运行，并接受“暂停时 enqueue 的话由之后接着跑的运行取走”。另需写清 rewind{resend}、异步回答进缓冲区这两条也是“进缓冲区并开/续运行”的入口，各自是否放行留着的话（见第 5 条）。

### 3. “停止的另记谁停的”与“用户选停止留着的只有用户能放行”在日志里没有落点：abort 的受理记录写在 runEnded 之后的另一批，且不含发出者与 keepQueue；两批之间受理的指令看不到这条例外
严重程度：重要；类别：接口与合同、并发与时序（重点 1、3）
位置：提案第四节第 1 小节“原因记这次运行的收口方式与码，停止的另记谁停的”，第 2 小节，第 3 小节“例外”，第 6 小节“新事件只有一种”；代码 run/commands.ts 第 159–184 行（abort 不经队列：先 `control.abort()` 等运行收口，再把 inputRemoved 与 `commandAccepted{name: "abort", value: {aborted}, argsHash}` 作为之后的一项写入），api/events.ts 第 106–112 行（runEnded 只有 reason、result、error）。
现象：runEnded{aborted} 由循环写，它不知道是谁发的 abort、带没带 keepQueue；abort 自己的记录是下一批，只存 `value` 与参数哈希，keepQueue 与发出者都不在日志里（abort 现在也不收发出者，session.ts 第 264 行）。从日志推“留着、原因停止、谁停的、是不是‘停止，排队的留着’”要把 runEnded 与之后某条 commandAccepted 拼起来，而两者之间队列可以受理别的指令（runEnded 那一项结束后、abort 那一项排进去之前），句柄损坏时 abort 的记录根本不写（第 170、178 行）。
为什么是问题：(a) 两批之间到达的宿主 `release` 或会话身份的 send，按当时的状态看不到“用户停止”，例外不生效，用户留着的话被系统带走——这正是 2026-11-18 决定要防的事。(b) 只读日志的重算拿不到 keepQueue，分不清“停止，排队的留着”与“停止并清空”之后停止进行中才到、按第 1 小节留着的话（第 2 小节），而例外只覆盖前者。(c) 第六节的 Spec 改动与“新事件只有一种”都没提 runEnded 要加字段。
建议：abort 受理时把发出者与 keepQueue 交给 RunControl，由循环写进 runEnded（例如 `stoppedBy: Issuer, keepQueue: boolean`），使“回到空闲”与它的原因在同一个写入批；清空的那几条（停止受理时刻的快照）也放进这一批，而不是收口后再算。session.md 的改动清单补上 runEnded 的新字段；验收加一条“停止收口与 abort 受理记录之间到达的宿主 release 得 not-allowed”。

### 4. 内核之外还有读缓冲区的地方：NeuroBook 的 `watchSteer` 把“缓冲区里有 steer”当成“用户插话了”，留着的插话会让每次前台等子代理立刻结束；放行把留着转成就绪时它又收不到通知
严重程度：重要；类别：隐含耦合、遗漏（重点 2、4）
位置：提案第四节第 1 小节“运行只取就绪的：内核读缓冲区的每一处都只看就绪的……第六节列全”；第六节没有列 NeuroBook 后端；代码 packages/neuro-book/src/plugins/agent/backend/jobs/steer.ts 第 19–26 行（订阅 `inputQueued{mode: "steer"}` 帧，再看 `snapshot.buffer.some(mode === "steer")`），调用方 backend/subagents/tools.ts 第 245–248 行（前台等子代理以它为中断条件，subagents.md 输出 6、jobs.md 输出 3）。
现象：(a) 父会话里有一条留着的插话（停止进行中到达的、出错后留下的、用户停止时留下的）时，系统或父 Agent 开的下一次运行里，模型一调 agent_spawn/agent_send/wait 前台等待，watchSteer 在第 26 行立刻 arrive，工具以“被插话打断”交回；而这条插话在这次运行里永远不会被取走（只取就绪的），模型每次重试都同样被打断。(b) 用户 send 或 resume 在运行中放行一条留着的插话时，只写 `inputReleased`，没有 inputQueued 帧，watchSteer 不会醒，前台等待不会被这条插话打断，与“插话结束等待”的合同不符。
为什么是问题：第二稿把“只看就绪的”写成内核不变量，但 BufferedInput 与快照的 buffer 是公开合同，NeuroBook 已经按“buffer 里的 steer = 待送达的插话”使用它。第一轮 B12 列的 8 处只在内核里；这一处在提案里没有出现。
如何核实：读上面两处代码；从代码推断，未跑真实子代理。
建议：第六节加 `agent/subagents.md`、`agent/jobs.md` 的改动与 NeuroBook `jobs/steer.ts` 的适配：只认 `state` 为就绪的 steer，并把 `inputReleased` 里转成就绪的 steer 也当作到达。更一般地，在提案里写明“读快照 buffer 的宿主代码要按 state 过滤”，并在实现时 grep 全部 `snapshot.buffer` 与 `inputQueued` 帧的读者。

### 5. 放行的入口只列了 send、resume、release；会把话放进缓冲区并开或续运行的还有异步回答（resolve）、rewind{resend}，以及 agent_send 不带 message 时的 start，它们在新规则下各怎样没写
严重程度：重要；类别：遗漏、接口与合同（重点 3、4）
位置：提案第四节第 3 小节“用户：发新话（send）或点继续（resume），放行全部留着的”“排话的人：以自己的身份发新话或用 release”“start……不放行、不取留着的”；第六节 subagents.md 一行“agent_send 放行自己排的”。代码 run/interaction.ts 第 128–146 行（异步提问的回答以 issuer 身份 inputQueued，空闲时开新运行或续暂停的运行，开不起来就留在缓冲区）；run/tree.ts 第 66–78 行（rewind{resend} 以用户身份入队并开/续运行）；plugins/agent/backend/subagents/tools.ts 第 437–440 行（agent_send 不带 message 调 `view.start`），subagents.md 输出 10、11。
现象与问题：
(a) 用户在空闲会话里回答一条异步提问：开一次新运行，第一轮是这条回答。按提案它既不是 send 也不是 resume，留着的话不放行；但同样是“用户发了新话”，用户看到的是自己留着的话没跟着走、也没先跑，与“留着的先跑”相反。父 Agent 用 agent_answer 时同理。回答开不起来运行（输出 11“回答进了缓冲区却没有运行可开”）时，它是“空闲时排的”留着，还是就绪？第 1 小节只说 enqueue。
(b) 错误气泡的“编辑重发”走 rewind{resend}（输出 36），是用户发新话；按提案不放行，留着的话会排在重发的话后面、等下一次放行，与普通 send 的行为不同，提案第五节的“普通会话的行为变化”没列。
(c) agent_send 不带 message 现在走 start，start 改为“不取留着的”之后：父会话连带中止留下的、父 Agent 排的话，父 Agent 用“继续”再也送不进去（start 只接着跑被中止的那一轮，或得 nothing-to-continue），而提案第 3 小节说这类“父 Agent 能放行”。
建议：把“放行”定义成输入入口的属性而不是逐个指令：凡以某发出者身份把一条新输入放进缓冲区并开/续运行的指令（send、resolve 的异步回答、rewind{resend}），都按同一条“放行这个发出者能放行的”规则处理，或明确列为例外并写理由；agent_send 不带 message 改走 `resume`（会话身份只放行自己排的），subagents.md 输出 10 同步改。

### 6. 权限表建在“发出者可信”上，而 NeuroBook 现在的缺省身份就是用户：`AgentService.session(id)` 不带 issuer 即用户、`startTask` 以用户身份 send，任何依赖 agentKey 的插件不用盖章就拥有“用户”的全部权限；第五节“安全”一句说过了头
严重程度：重要；类别：安全、隐含耦合（重点 4）
位置：提案第四节第 5 小节（宿主发出者、权限表、“source.plugin 由宿主应用按调用方盖章……在 bot 提案”），第五节“安全：发出者不能再改写或取消别人的话，宿主的话不会被别的发出者顺手带走”；代码 plugins/agent/shared/contracts.ts 第 110–111 行（`session(id, issuer?)`，“缺省以用户的身份”），backend/agent.ts 第 309、317、331–334 行（startTask 用 `table.view(sessionId)` 即用户身份 send；`session` 原样接受调用方给的任何 Issuer），backend/remote.ts 第 171 行（远程一律用户）。
现象：一个插件经 agentKey 拿到 AgentService 后，(a) 什么都不传就是用户：能 edit/remove/release 任何一条、放行“用户停止留下的”、它的 send 放行全部留着的；(b) 也能自己构造 `{kind: "session", id: 任意}` 或将来的 `{kind: "host", source: {plugin: "别人"}}`，冒充别的会话或插件。内核的判等再严，身份是调用方自报的。
为什么是问题：提案把“系统开的运行不会带走用户留着的话”“用户停止留下的只有用户能放行”写成内核保证，但在现有宿主上，最常见的系统入口（startTask、日后 bot 若直接用 `session(id)`）缺省就是用户，这两条保证对它们不成立；而“怎样盖章”被列为非目标、放到 bot 提案，两份提案之间的这条前提没有写成任何一方的验收。
建议：本提案至少写明前提与归属：“宿主发出者的身份由 NeuroBook 在 agentKey 的边界上按调用插件盖章，`session(id)` 的缺省身份对插件改为该插件的 host 身份、只有远程合同（用户界面）是用户”，并把这条列为第六节 `agent/sessions.md` 的改动；在盖章落地之前，第五节“安全”改成“前提是宿主正确盖章”。startTask 的发出者是谁（用户还是发起任务的插件）也要定，它决定任务会话里的话谁能放行。

### 7. “用户自己点的压缩，压完由 NeuroBook 自动 resume”放行的是全部留着的，不只压缩期间到达的；由谁、在哪一层、压缩失败时怎样都没写，放在网页里还会随标签页关闭而失效
严重程度：重要；类别：合同不完整、与开发者决定的边界（重点 3）
位置：提案第四节第 3 小节“用户自己发起的压缩……压完由 NeuroBook 自动 resume，系统发起的压缩压完留着”、第 3 小节“用户……点继续（resume），放行全部留着的”、第 3 小节“例外”；第五节“手动压缩时发的话：现在卡住；改成压完自动放行”。代码 plugins/agent/web/session-host.ts 第 1173–1202 行（/compact 在网页里发，`current !== target` 时直接返回）；session.ts 第 279–291 行（空闲时 compact 开只压缩的运行，运行中、暂停时排到下一个边界，不开运行）。
现象与问题：
(a) 范围：resume 按第 3 小节放行全部留着的。用户先“停止，排队的留着”（只有用户能放行的那几条），再点 /compact，压完自动 resume 会把停止时刻意留下的话一起发出去；出错后留着的宿主消息同理。开发者的决定针对的是“压缩期间用户发的话”，不是“压完把会话恢复运行”。
(b) 层次：内核看得出这次只压缩的运行是谁发起的（compact 的发出者），NeuroBook 网页看得到的只是自己发过 /compact。若放在 session-host（网页），用户切走会话（第 1185 行已有 `current !== target` 早退）、关掉标签页、或从另一个窗口发的 /compact，都不会自动放行，话一直“已暂停”。若放在后端，提案要写清后端怎样知道“这次压缩是用户点的”。
(c) 失败：压缩失败（compaction-failed、no-model）或被停止时还自动 resume 吗？resume 开不起来（只读、没有模型）时失败、话仍留着，用户看不到原因。
建议：改成“只放行这次只压缩的运行期间到达、因它收口而留着的那几条”（`release({inputIds})`，或 resume 带 `since: runId`），只在压缩运行以 completed 收口时做；并写明放在后端（例如 `agent` 插件在 compact 指令受理后等这次运行），或者干脆由内核做：compact 的发出者是用户时，压完的回到空闲不把运行中到达的那几条算留着。

### 8. `send{replaces}` 只写了“同一个受理批里移除、放行、送进”，没写它校验什么、失败得什么码：宿主按快照拼的文字与受理时的缓冲区可能已经不同，照做会重复发出或丢掉用户的编辑
严重程度：重要；类别：接口与合同、并发（重点 3）
位置：提案第四节第 4 小节表格第一行与“拼法……由宿主定，内核只看到一条普通的新输入”，第 6 小节“send 加可选的 replaces 与 release”；代码 run/commands.ts 第 41–70 行（受理在队列一项里：查重发 → 校验 → 写批），第 186–190 行（bufferProblem 的 input-not-found / input-consumed），api/host.ts 第 121–130 行（BufferedInput 有 `edits` 计数）。
现象：宿主先读快照、按“留着的用户的话”拼出一条，再发 send{replaces: ids}。两步之间：另一个窗口的用户点了继续或编辑了其中一条、宿主自己排的话被它取消、停止收口把就绪的转成留着、或其中一条在运行中被取走（它若是就绪的）。提案没规定：(a) replaces 里有已不在缓冲区的 id 时整条失败（哪个码），还是忽略——忽略就把已经发出的内容又发一遍；(b) 其中一条在拼之后被 edit 过时怎样——照做会用旧文字替掉用户刚改的；(c) replaces 能不能含就绪的、别的发出者的条目（第 4 小节说“只合并用户自己的话”是宿主的做法，内核是否校验）；(d) 输入拦截拒绝了拼好的这一条时，留着的话是否保持原样（应当：整条失败不写日志）；(e) replaces 与 release 同时给时谁优先。
为什么是问题：第二稿把合并移出内核的理由是“内核只做移除几条、送进一条”，但这一步的正确性完全取决于“宿主拼时看到的”与“内核受理时的”是同一份缓冲区，这个前提要由内核在受理项里校验，否则就是一条没写出的竞态。commandId 的重发只解决同一条指令重放，不解决上面的过期。
建议：给 replaces 写成条件写入：每项带 `{id, edits}`（或快照的 head），受理时任一项不在缓冲区、`edits` 不符、或不是这个发出者能移除的，整条以新码失败（例如 `input-stale`，加进 commandErrors.send），什么都不写；拦截拒绝同样不写。宿主拿到失败重新读快照再拼。验收补“拼之后另一窗口编辑其中一条，send{replaces} 失败且缓冲区不变”。

### 9. 不带选项的 send 怎样放行没定；按“留着的先跑”它会把 runtime.md 验收 2（空闲时入队的 followup 排在下一句之后）倒过来，行为变化清单与 Spec 改动清单都没列
严重程度：重要；类别：接口与合同、兼容（重点 3、5）
位置：提案第四节第 1 小节“空闲时排进来的话也算留着”，第 3 小节“用户：发新话（send）……放行全部留着的。留着的先跑”，第 4 小节表格（三种方式都由宿主带 replaces 或 release 调）；第五节“普通会话的行为变化”；第六节 runtime.md 一行。Spec：harness/runtime.md 验收 2“空闲时入队的 followup 在这一轮结束后开下一轮，同一次运行”；测试 packages/nb-harness/src/kernel/session/session.test.ts 第 122–130 行（enqueue A，再 say B：请求顺序 B、A）与第 132–138 行。
现象与问题：
(a) 内核 API 的 send 不带 replaces、release 时（测试工具、startTask、bot、子代理工具都这样调），是放行全部？按哪种方式（保持原模式，还是都转成排队）？还是不放行？第 4 小节只定义了宿主的三种调用。
(b) 若按第 3 小节“放行全部、留着的先跑”，验收 2 就从“B 然后 A”变成“A 然后 B”；在 NeuroBook 缺省“合并一起发”下更是合成一条。验收 2 与上面两条测试是现行合同，第六节没把它列进 runtime.md 的改动，第五节的行为变化只写了“子代理……空闲时排进来的话：留着”，没写普通会话里“先排后发”的顺序反了。
(c) 用户在空闲时用排队键（session-host.ts 第 1105 行的 enqueue）排一条，本意多半是“等下一次运行之后再说”；“留着的先跑”与此相反。这是开发者“留着的先跑”决定在“空闲时排的”这一类上的外推，提案没有说明开发者的决定是否覆盖这一类。
建议：写明内核 send 的缺省（建议：不带 release 时等同 `release: "keep"`，并写清空闲时“第一条开第一轮”指的是缓冲区里最早的就绪项），把验收 2 改写或删掉并列进第六节；第五节补“空闲时排队的话改为在下一句之前”；“空闲时排的”是否也按“留着的先跑”列为交开发者确认的一项。

### 10. 事件形状还不够“长期不改”：`inputRemoved` 只加 `replaced` 原因，不记谁移除、被哪一条取代；`reason: "user"` 在宿主与会话也能取消自己的话之后成了错名；“由日志推出”的状态在对话视图里要再推一遍
严重程度：建议（事件形状一发布就不能改，所以现在定）；类别：接口与合同、兼容（重点 5）
位置：提案第四节第 5 小节权限表 remove 行“会话、宿主：只能取消自己排的”，第 6 小节“inputRemoved 加原因 replaced”“快照与远程合同里，缓冲区的每条带 by 与 state”；代码 api/events.ts 第 74 行（`inputRemoved{id, reason: "user" | "aborted"}`），run/commands.ts 第 209 行（remove 一律写 `reason: "user"`），nb-agent-ui/src/kernel-transcript.ts 第 509–523 行（对话视图从 inputQueued/inputRemoved/inputConsumed 帧自己归约排队区）。
现象与问题：
(a) 宿主或父 Agent 取消自己排的话，按现有代码写成 `reason: "user"`；日志读者（审计、对话视图的说明文字）会把它读成用户删的。提案给 inputEdited、runStarted 加了发出者，唯独 inputRemoved 没加。
(b) `replaced` 不带取代它的 inputId：对话视图要显示“这几条已合并进下一句”或乐观消息要对上，只能靠“同一批里紧跟着的那条 inputQueued”去猜，而批的边界不是事件上的字段。
(c) 对话视图现在自己从日志帧归约排队区（不读快照）。第二稿的状态要从 path 级的 runEnded（还有第 3 条说的停止发出者）推出，视图也得照同一条规则再推一遍，规则就有两份实现；若改成帧里带状态，第六节要写出帧的形状。
建议：`inputRemoved` 加 `by: Actor`（停止清空时是停止的发出者，取代时是 send 的发出者），`replaced` 时加 `replacedBy: inputId`；reason 用 `cancelled | aborted | replaced`，旧日志的 `user` 读作 cancelled。远程合同写明对话视图从快照的 `state` 起步、之后靠 `inputReleased` 与收口事件增量更新的规则，或在状态帧里推缓冲区的派生状态，二者选一写进 `agent/sessions.md` 的改动。

### 11. “留着由日志推出”的规则字面有歧义，且要让 session 级归约读 path 级事件，打破内核现有的分层；第六节与 ADR 一行都没写这一点
严重程度：建议；类别：接口与合同、架构（重点 1）
位置：提案第四节第 1 小节“看一条话进缓冲区之后、被取走或移除之前，有没有一次回到空闲、之后有没有放行”，第六节 ADR 0035 一行；代码 dispatch/core.ts 第 203–215 行（path 事件只进 `reducePathKernel`，session 事件只进 `reduceSessionKernel`），state/kernel-state.ts 第 108–117 行（缓冲区在 session 片），dispatch/core.ts 第 269–283 行（reassemble 从头重归约）。
现象与问题：
(a) 字面：“有没有一次回到空闲、之后有没有放行”在多轮时读不通：放行后又被一次出错的运行收口、没取走（例如宿主放行了自己的 followup，开的运行出错），按字面“有过回到空闲且之后有过放行”判成就绪，实际应留着。应写成“入队或最后一次放行之后，有没有回到空闲”。
(b) 分层：回到空闲的事实是 runEnded（path 级），缓冲区是 session 级；现在两片的归约互不相见，所以“由日志推出”要么让 session 归约也看 runEnded（以及第 2 条的接着跑、第 3 条的停止发出者），要么在快照时临时扫日志。前者是对 ADR 0035“path 片随叶子、session 片线性”的修改，后者每次快照 O(日志长度)。按全局日志顺序（不按当前路径）判断能保证回退与切分支不改变状态，这一点也应写明，否则实现者照“叶子上的运行状态”去判会随回退变化。
(c) enqueue 交回的 `position`（run/commands.ts 第 126 行，按整个缓冲区计）在“只看就绪的”之后含义不清：是在就绪队列里的位置还是在全部条目里的位置，第一轮 B12 列过，第二稿的“第六节列全”实际没列。
建议：把规则改写成上面的形式并给一个归约草图（session 归约在 runEnded 上把当时缓冲区里的就绪项改为留着、记原因；inputQueued 时按全局顺序上的“当前有无未收口且在跑的运行”定初值；inputReleased 改回就绪），写进 ADR 0035 的补充；第六节补 enqueue position 的含义。

### 12. 权限表的两处空白：用户改了父 Agent 排的话之后这条归谁（问题一第 3 类“编辑保留原发出者”并没有解决）；宿主可以 `start` 接着跑用户会话里被中断的那一轮，这是新给宿主的权力，提案自己定了
严重程度：建议（第二点应交开发者）；类别：权限、合同（重点 3、4）
位置：提案第一节问题 3“inputEdited 换了内容却保留原来的发出者”，第四节第 5 小节权限表 edit 行（用户“任何一条，宿主排的除外”）、start 行（会话、宿主“能（例如 bot 重启后的自动接续）”）与“inputEdited 记下编辑者”；代码 run/commands.ts 第 192–203 行（edit 不改 `by`），run/commands.ts 第 143–147 行（缓冲区空时 start 开“继续”运行），run/recover.ts 第 7 行与 runtime.md 输出 34（重启后“不自动发出”）。
现象与问题：
(a) 用户改了子会话里父 Agent 排的话：内容是用户的，`by` 仍是父会话。之后父 Agent 能 release、remove 它（“自己排的”），`input.by` 进路径时也仍记父会话（loop.ts 第 73、83 行取 `item.by`）。问题一把“编辑保留原发出者”列为毛病，第二稿只是另记编辑者，没有定“改过之后按谁算”，权限与路径上的出处都还按原发出者。
(b) 宿主 start：缓冲区里的话都不取（只接着跑中断或失败的那一轮），但它会在用户没有任何操作的情况下，把用户会话里被重启打断的那一轮接着跑下去、继续花钱和改文件。t07 决定 3 的原意是重启后“等用户确认”；第一轮 B13(c) 指出过这一点，第二稿把它写成了允许（括号里的例子是 bot），但没有标为开发者的决定。
建议：(a) 二选一写明：编辑之后 `by` 改成编辑者（推荐：内容和权限跟着最后写内容的人走，路径上的 `by` 用编辑者），或保留原发出者并说明理由；(b) 把“宿主能否 start 用户会话”列为交开发者的一项，可选的限定是“只在宿主自己开的、被中断的运行上”（runStarted 记了发起者，第 2 条修好后可判断）。

### 13. 停止的缺省说的是哪一层不清楚；子代理浮层的停止按“用户停止”算之后，父 Agent 排给子会话的话只有用户能放行，父 Agent 再发话时自己的新话反而跑在旧话前面
严重程度：建议；类别：合同不清、子代理交错（重点 3）
位置：提案第四节第 2 小节“缺省沿用 2026-11-05 的决定：停止时排队的留着（keepQueue: true）……子代理浮层里的停止走缺省”，第 3 小节“例外”；代码 run/commands.ts 第 171 行（内核 abort 缺省清空，runtime.md 输出 30，来自 t07 决定 2“中止默认清空队列”），plugins/agent/web/session-host.ts 第 338–339 行（子代理浮层 stopRun 以用户身份 `abort{keepQueue: true}`）、第 1365 行。
现象与问题：
(a) “缺省”指界面的缺省还是内核 abort 的缺省？若是内核，t07 决定 2 被改掉了（第一节只把 t07 决定 1、3 列为来源，没说改决定 2），runtime.md 输出 30 也要改；若只是界面，提案应写“内核缺省不变（清空），界面一律传 keepQueue: true”，第二节目标里“把……2026-11-05 的停止时排队留着写成同一种状态”才不至于读成内核行为。
(b) 用户在子代理浮层里点停止：子会话里父 Agent 排的话按例外只有用户能放行。父 Agent 随后 agent_send 带 message：按第 3 小节只放行“自己排的”，但这些恰是被例外锁住的，于是子会话只带着新话开一轮，父 Agent 之前排的指令留在后面、等用户；与“留着的先跑”相反，父 Agent 也不知道（agent_send 的结果不含缓冲区状态）。subagents.md 输出 16 只写了连带中止，没写用户停止子会话的这条。
建议：(a) 明确写“内核 abort 缺省不变”或列为对 t07 决定 2 的修改；(b) 在 subagents.md 的改动里补：用户停止子会话后父 Agent 发话，工具结果写明“子会话里还有 N 条你排的话被用户暂停，未发出”，或者让父 Agent 的话不受这条例外（例外只管用户自己与宿主的话）——后者是产品取舍，应交开发者。

### 14. “旧日志按同一条规则推出”在停止这一类上推不出来：旧日志里的停止不记谁停的、也不记 keepQueue，例外“只有用户能放行”落在旧会话上要有缺省，提案没写；现有会话打开后的可见变化也只列了一半
严重程度：建议；类别：兼容（重点 5）
位置：提案第四节第 1 小节“新旧日志同一条规则”，第五节“数据：旧日志照读，状态按同一条规则推出”“普通会话的行为变化”；代码 run/commands.ts 第 172 行（旧的 abort 受理记录只有 `value: {aborted}` 与参数哈希），backend/subagents/tools.ts 第 259 行（连带中止以父会话身份 abort）。
现象与问题：
(a) 旧日志里的 runEnded{aborted} 之后留着的话，按新规则原因是“停止”，但“谁停的”与“是不是选了留着”都不在日志里（第 3 条）。缺省当成用户停止：旧的子会话里父 Agent 连带中止留下的话，父 Agent 再也放行不了（与第 3 小节“父 Agent 能放行”相反）；缺省当成非用户：用户在旧会话里停止时留下的话，任何宿主都能放行（与例外相反）。两种都要明说。
(b) 可见变化：现有会话里已经“卡住”的话（只压缩之后、文字收口之后、空闲时排的）重开后都变成“已暂停”，原因码各不相同；第五节只按“以后会怎样”列，没写“升级后第一次打开，排队区里的旧话会显示为已暂停、要点继续”。乐观消息改按 inputId 确认，对正在进行中的旧乐观消息（升级瞬间）无影响，可不管。
(c) 旧日志里没有 `inputReleased`，“入队后经历过回到空闲”的话一律留着；旧内核下用户“发一句把卡住的带走”的习惯，在新内核下变成“发一句、留着的先跑”，与 (b) 一起是用户可见的顺序变化。
建议：在第五节写明旧日志的停止按什么缺省（建议：旧的停止一律按“用户停止”，旧子会话里 `by` 为父会话的那几条例外地允许父会话放行——这条可以由 inputQueued.by 判断，不需要停止的发出者），并补上“升级后第一次打开”的可见变化与验收（拿一份含卡住 followup 的旧日志打开，排队区显示已暂停、原因码稳定、重开两次结果相同）。

### 15. 一条话留着之后又经历别的运行收口时，原因被不被改写没写；按“回到空闲时剩下的都留着、原因记这次运行的收口方式”的字面，“用户停止留下的”这条例外会在下一次任何运行结束后失效
严重程度：重要；类别：规则歧义、权限（重点 1、3）
位置：提案第四节第 1 小节“会话回到空闲的那一刻，缓冲区里还在的话全部算留着……原因记这次运行的收口方式与码，停止的另记谁停的”，第 3 小节“例外：用户选‘停止，排队的留着’留下的，只有用户能放行”，第 6 小节“快照……留着与原因”。
现象：设用户停止时缓冲区里有宿主排的 H（按例外只有用户能放行）。随后宿主以自己的身份发一条新话 N：放行它“自己排的”，H 被例外挡住不放行，N 开一次运行；这次运行正常结束，会话又回到空闲，H 仍在缓冲区里。按字面，此刻“缓冲区里还在的话全部算留着，原因记这次运行的收口方式”，H 的原因变成 completed；之后宿主 release(H) 就合规了。同理，用户停止时留下的父 Agent 的话，在父 Agent 再开一轮并结束后也不再受例外约束。反过来，若原因保留第一次的，“空闲时排的”在一次出错之后仍显示“空闲时排的”，原因码也会误导界面。
为什么是问题：例外是开发者 2026-11-18 的明确决定；它能不能活过下一次运行，取决于一个提案没写的细节。由日志推出时，这还决定重开前后的结果是否一致（同一条规则要在归约里写死）。
如何核实：按提案文字推演，代码里尚无此功能；未运行。
建议：写明“原因只在从就绪变成留着时记下，已经留着的话在之后的回到空闲时不改原因”，并让“只有用户能放行”作为条目上的独立属性（例如 `heldBy: user`）而不是从最近一次收口推出；验收加“用户停止留下宿主的话，宿主自己的一次运行结束后，宿主 release 它仍得 not-allowed”。

### 16. 新指令 `resume`、`release` 的失败码与边界情形没写，而 commandErrors 是“表即合同”、远程合同按它自动暴露
严重程度：建议；类别：接口与合同（重点 3）
位置：提案第四节第 3 小节“resume：放行留着的并开运行；开不起来（只读、没有模型）时失败，话仍留着”“放行时会话空闲就开运行……在跑就把它们转成就绪”，第 6 小节“新增指令 resume({mode?})、release({inputIds})”；代码 api/codes.ts 第 1–31 行（“指令与失败码只加不改”，远程方法的 errors 由它而来），plugins/agent/backend/remote.ts 第 42 行（COMMANDS 取 commandErrors 的全部键，除 hostOnly 外都暴露给远程，即都以用户身份可调）。
现象与问题：没定的情形：(a) resume 时没有留着的话（是成功空操作、`nothing-to-release`，还是退化成 start）；(b) release 的 id 已被取走、已删除、本来就是就绪的、属于别人（not-allowed）、被例外锁住；(c) release 在空闲时也开运行（第 3 小节“放行时会话空闲就开运行”对所有放行生效），开不起来时是整条失败还是只转成就绪——后者又回到“空闲而就绪”的状态；(d) resume、release 遇到暂停的运行（第 2 条）；(e) 运行正在中止（aborting）时到达的 resume/release：是转成就绪、随后被那次停止的回到空闲又改回留着，还是得一个可区分的码（agent_send 已有 child-stopping 的先例）。每个码一经发布不能改，远程合同还会把它们原样给界面。
建议：在提案里给出两张小表（情形 → 结果或码），把要新增的码（例如 `nothing-to-release`、`not-allowed`、`input-held-by-user`）列进第六节 runtime.md 与 sessions.md 的改动；明确 release 是否属于用户可调的远程方法（若只给宿主，加进 hostOnlyCommands）。

### 17. “在跑就转成就绪”对不会再取输入的运行没有意义：只压缩的运行、正在中止的运行里点继续或发话，指令交回成功，话随即在回到空闲时又成了留着
严重程度：建议；类别：边界情形、用户可见行为（重点 2、3）
位置：提案第四节第 3 小节“放行时会话空闲就开运行……在跑就把它们转成就绪，按取的规则在之后的边界或一轮结束时取”，第 1 小节“回到空闲时剩下的都留着”；代码 run/loop.ts 第 188–203 行（只压缩的运行不读缓冲区，压完直接 runEnded），session.ts 第 284–290 行（只压缩的运行在 control 看来就是“在跑”），run/control.ts 第 141 行（中止中 status 为 aborting，但 `idle` 仍为 false）。
现象：只压缩的运行期间，用户在输入框点“继续”或再发一句（send 放行全部）：内核按“在跑”处理，写 inputReleased、交回成功；这次运行不取任何输入，压完回到空闲，刚放行的话按第 1 小节又全部留着。中止进行中的 resume、send 同理。用户看到的是“点了继续，话先变成排队，过一会儿又变回已暂停”。
为什么是问题：inputReleased 写进日志却没有效果，状态在两次推送之间来回翻；放在系统身份上（日程插件在压缩期间 release 自己的话）还会让它误以为已经送达。
建议：写明“运行不会再取输入时（只压缩的运行、aborting、已决定收口）放行得一个可区分的码（例如 `run-not-taking-input`）或推迟到回到空闲后再执行”；对用户发起的压缩，这和第 7 条“压完自动放行压缩期间到达的”一起定即可。
