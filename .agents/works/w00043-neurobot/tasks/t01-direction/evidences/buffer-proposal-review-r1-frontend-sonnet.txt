# 前端审查（Sonnet）：提案《Agent 内核的输入缓冲区：每条带状态》第四节第 3、7 小节

### 1. 错误气泡的“重试”与“编辑重发”走 `start`，会变成“放行全部留着的”
严重程度：重要；类别：接口与合同、遗漏。
位置：提案第四节第 3 小节（用户点继续：`start` 放行全部留着的）；`packages/neuro-book/src/plugins/agent/web/session-host.ts` 第 635–670 行（`rewriteHistory` 末尾 `remote.start`，由 `message.retry` 第 1435 行触发）。
现象：现在“重试”是 `rewind` 加一次不带参数的 `start`。`start` 在缓冲区非空时取 `buffer[0]` 当新输入开跑（`nb-harness/src/kernel/run/commands.ts` 第 142 行），不是重跑失败的那一轮。提案把 `start` 定成“放行全部留着的”，并且 `error` 收口的结果恰恰是“缓冲区里有一批 `error` 状态留着的话、界面上同时出现带重试按钮的错误气泡”。所以出错之后用户点“重试”，会把留着的话按 `merge` 合成一条当作用户输入发出去，而不是重试。这是现有的潜在问题（今天缓冲区非空时就这样），但提案让它成为出错后的常态，也没写 `start` 要如何区分“继续放行”和“重试”。
核实：读上面两处代码即可（从代码推断，没有跑 e2e）。
建议：`start` 带显式参数（例如 bot 提案里的 `take: "none"` 一类），重试与编辑重发用“不取缓冲区”的形式；“继续”按钮用 `resume`。在第四节第 3 小节写明三个入口各调哪个指令。

### 2. 乐观消息按“先后”确认，留着的先跑会让新话的气泡消失或错位；合并后的文字没有来源
严重程度：重要；类别：接口与合同、照字面实现会返工。
位置：提案第四节第 3、5 小节；`packages/nb-agent-ui/src/kernel-transcript.ts` 第 704 行、第 730–753 行、第 512–523 行。
现象：
- 第 704 行：实时收到任意一条 `input` 或 `steer` 路径事件，就吞掉最早的一条乐观消息，注释写明“只按先后，不按内容”。提案让留着的先跑：用户发新话 U 时，`keep` 与 `followups` 下路径上先到的是留着的那几条的 `input`，这会把 U 的乐观气泡吞掉，U 自己的 `input` 要等前面几轮跑完才到，这段时间对话里根本看不到 U；`merge` 下合成的一条文字和用户刚输入的不一样，气泡先显示 U、随后整条替换成“旧话加新话”。
- `inputMerged{from, into}` 只有 id。界面的归约（第 512–523 行只认 `inputQueued`、`inputEdited`、`inputRemoved`、`inputConsumed`）拿不到合成后的文字、附件，也不知道拼接格式（空行？换行？）。提案没说 `into` 是否另写一条 `inputQueued`，也没说合成条的模式（插话还是排队）。
- 第 489 行：不认识的事件记 problem“不认识的事件”，三个新事件不加进归约或 `IGNORED`，老界面会报问题；`harness.contract.test.ts` 一类契约测试也要改。
建议：提案补两点：（a）确认乐观消息改成按 `commandId` 对应，`send` 的结果带上它放行了哪几条留着的、合成条的 id；（b）`inputMerged` 带合成后的 `input`，或者保证 `into` 先有一条 `inputQueued`。并写明对话里合并后是一条用户气泡，气泡里写拼接格式。

### 3. “继续”的指令与作用范围没定，并且会和“上次运行已中断，按回车继续”出现两套入口
严重程度：重要；类别：交互自洽、接口。
位置：提案第四节第 3 小节与第 7 小节；`docs/specs/agent/conversation.md` 输出 9；`packages/nb-agent-ui/src/vue/composer/AgentConversationComposer.vue` 第 165、180、206 行；`kernel-transcript.ts` 第 440 行 `interrupted`。
现象：
- 第 7 小节写“旁边有继续”。是每行一个，还是排队区一个？第 3 小节同时有 `start`/`resume`（放行全部）与 `release({inputIds})`（按条）。每行一个继续若调 `release([id])`，就和“继续=放行全部”矛盾；整区一个继续则要写在排队区的哪里，3 条上限折叠后（`AgentQueuedMessages.vue` 的 `VISIBLE = 3`，“还有 N 条”一行没有操作）是否露出。
- 输出 9 现有的继续在输入框：由 `interrupted()` 决定，只看当前路径最后一次运行是否 `interrupted`，路径级。留着的状态是会话级。重启中断且缓冲区有留着的话时，输入框的“继续”与排队区的“继续”同时出现，调的是两个指令吗？`error`、`stopped`、`finished`、`cannot-continue` 的留着只会有排队区的继续；用户回退（rewind）之后路径上的“已中断”提示没了，留着的 `interrupted` 条目还在，写着“重启中断”，继续会把一条上一条路径的话放到新叶子上。
- 提案第六节说“输出 9 一并改”，但没说怎么改。`interrupted` 且缓冲区有话时，“继续”想要的是接着上次没跑完的那轮，而 `start` 现在是拿缓冲区里的话开新一轮（见第 1 条），`merge` 下还会把几条合成一条。
建议：在提案里列一张“界面动作到指令”的表：输入框空着回车、排队区继续（行与整区）、错误重试、编辑重发各调哪个指令、带什么参数；规定缓冲区里有留着的话时输入框的继续不再单独出现，统一在排队区一处。

### 4. 停止的“两个选项”只覆盖输入框的停止按钮；其它停止入口没写，现有的“排队留着”决定没提
严重程度：重要；类别：与已定设计一致、遗漏。
位置：提案第四节第 7 小节；`session-host.ts` 第 339 行（子代理浮层 `stopRun`）、第 1359–1365 行（`composer.stop` 与 `input.cancelRun` 合在一起）；`AgentConversationComposer.vue` 第 162、229 行；`AgentWizard.vue` 第 143 行；`.agents/works/w00032-agent-integration/tasks/t17-conversation-ui/plan.md` 第 196、281 行。
现象：
- 现在所有停止都是 `keepQueue: true`（t17 计划“按停止时排队的消息保留”，conversation.md 输出 6、子代理浮层“子会话与排队的消息都保留”，session-host 代码注释“开发者 2026-11-05 定”）。提案只写“缓冲区不空时给两个选项”，没提这条已有决定，也没写缺省是哪个。提案第一节写“中止缺省清空，同现在”只对内核默认成立，界面一直在覆盖它。
- 停止入口至少有四处：输入框的停止按钮、同步向导里的“终止本轮”（`input.cancelRun`）、子代理浮层悬停停止、子会话顶栏的停止。向导与浮层没有位置放菜单，必须定一个静默的选择。写明各入口选哪个，否则实现者各自挑。
- 输入框停止按钮只在输入为空且运行中才显示（`showStop`）。用户写了字就没有停止按钮；两个选项是弹出菜单、拆分按钮还是两个按钮，没写。Esc：输入框编辑器会发 `escape`（`PlainPromptEditor.vue` 第 61 行），但 `AgentConversationComposer.vue` 没有接，现在 Esc 不停止。没有现成约定，需要提案定：Esc 是否停止、走哪一个选项；菜单要键盘可达，打开后焦点、Esc 关菜单而不是停止。
- “缓冲区不空”包含留着的话吗？若包含，“停止并清空排队”会把之前别人（宿主、父 Agent）留着的、`stopped` 状态的话也删掉，菜单上应写条数。若只算就绪的话，则缓冲区里只有留着的话时仍直接停止。两个窗口同时开着、一个点了“留着”另一个再点“清空”（`stopping` 状态）时第二次点击的行为也没写（`abort` 在中止进行中重发是幂等的，但换了 `commandId` 和 `keepQueue`）。
建议：补一张“入口、缺省选项、键盘”的表；缺省保持现状（留着）更符合 2026-11-05 的决定；“清空”需要菜单里主动选。

### 5. “合并一起发”的语义对界面不够：相邻、混合发出者、宿主消息先于用户新话
严重程度：重要；类别：接口、交互自洽。
位置：提案第四节第 3 小节 `merge` 条。
现象：
- “同一个发出者的、相邻的留着的话与这次的新话合成一条，不同发出者的不合并，宿主的消息单独成条”。缓冲区 [宿主 H，用户 U1，（父 Agent 的）P，用户 U2]，用户发 U3：U1 与 U3 隔着 P，算相邻吗？按字面不相邻，结果是 H、U1、P、U2、U3 各一轮（五轮），用户只想说一句话却触发五轮运行。反过来若跳过其它发出者去合并，“相邻”就没有意义，顺序也变了。
- 用户发了一句话，先跑的是宿主的周期任务（H 单独成条、排在前面）。用户看到自己的话没有被回应、先出现别人的任务。这是开发者定的“留着的先跑”的字面后果，但提案没有给界面任何说明，也不确认这是否是开发者想要的（开发者说的是用户自己留着的话）。
- 合成后在对话里是一条用户气泡，其中混有用户先前写的话；排队区里原来的几行在合并时消失（`inputConsumed` 或 `inputMerged`），用户点发送的瞬间看不到“这几条被并进来了”。
- `keep` 下留着的插话怎么处理：运行在空闲时开新一轮，插话与排队没有区别；`followups` 与 `keep` 对空闲会话的差别是什么，提案没说。
建议：把 `merge` 的相邻定义改成“从缓冲区头部起，连续的同发出者的留着的话”；宿主、会话发出的留着条目按用户设置也先跑还是排在用户话之后，交开发者再确认；在对话里把合并条目标出“含 N 条留着的话”，鼠标悬停可看原来的几条。

### 6. 排队区的数据：现有条目类型丢了 `by`，原因文案没有来源，3 条上限会藏住“继续”
严重程度：重要；类别：接口与合同。
位置：提案第四节第 5、7 小节；`nb-agent-ui/src/types.ts` 第 410 行（`composer.queued` 只有 `id/text/delivery`）；`kernel-transcript.ts` 第 667–672 行（快照只取 `id/mode/text`）；`AgentQueuedMessages.vue` 第 17–18 行；`nb-harness/src/kernel/api/basics.ts` 第 55 行（`Issuer` 只有 `user` 与 `session`）。
现象：
- `state` 与 `by` 要加进快照、远程合同、`KernelQueued`、`composer.queued` 四处；`composer.queued` 的新形状（建议 `held?: {reason: Text; releasable: boolean}`、`origin?: Text`、`editable: boolean`）提案没给，只写“显示已暂停与原因”。
- 原因文案：界面现有的出错文案由 `errorText` 按 `{kind, code}` 两个字段取（`kernel-transcript.ts` 第 151 行，类别 `network/rate_limit/...`，码覆盖 `cost-limit` 等）。提案的 `inputHeld.detail` 写“例如出错的码”，只有码，缺 `kind` 时只能落到“本地错误”那句。`cannot-continue` 的码（`no-model`、`no-credentials`、`unknown-model`、`role-unbound`）的文案在 `neuro-book` 宿主的 `model-notice.ts`，不在 `nb-agent-ui`；宿主要自己把码转成 `Text` 再交给组件。要写明 `detail` 的类型：与 `runEnded.error` 同形（`{kind, code}`）最省事。
- `by` 的形状：`Issuer` 目前没有“宿主”这一种（bot 提案第 143–145 行才加 `host` 与 `source{plugin,label,ref}`）。第 7 小节“只有宿主排的”依赖另一份还没生效的提案；没有它，界面只能写“某会话”，看不出是哪个周期任务。提案要写清自己依赖哪一份的 `by` 形状。
- 新旧并存：旧服务端的快照没有 `state` 时，条目当“就绪”显示；这条降级路径没写。
- `AgentQueuedMessages.vue` 最多显示 3 条，其余只写“还有 N 条”。已暂停的条目与“继续”若落在被折叠的第 4 条之后，用户看不到暂停；留着的条目应排在可见区前面或不折叠，数量上限也要定。
建议：在第五节把快照条目、`composer.queued` 的新字段、原因 `detail` 的形状写成表，并写明折叠规则。

### 7. 暂停的话只在这个会话的排队区里可见，没有别处的提示；子会话里“谁能继续”没写
严重程度：建议；类别：遗漏。
位置：提案第四节第 6、7 小节；`docs/specs/agent/conversation.md` 输出 2（会话列表状态）、子代理浮层（第 120–122 行）。
现象：
- “等用户放行”的话进了一个空闲会话后没有任何提醒：会话列表只有运行中、等你处理、已中断；子代理浮层有“已停止、已中断”，没有“有暂停的话”。父会话连带中止子会话后（`children.ts` 第 53 行 `keepQueue: true`），子会话缓冲区里留下 `stopped` 的话，只有用户进入那个子会话才能看到。后面的行为也会改变：父 Agent 之后 `agent_send` 能放行自己排的、但放不了 `stopped` 的（提案第四节第 3、6 小节），`children.ts` 注释写着“后面的放话照常送达”会不再成立（后端审查者负责，这里只说它的界面后果：用户在子会话里会看到父 Agent 的旧话和新话一前一后）。
- 子会话里父 Agent 的话与用户的话混在一起：“编辑”只对用户自己的话显示（见第 8 条）；“继续”谁点都是放行全部，包括 `finished`（子代理已把结果交给父 Agent）。用户在已完成的子会话里点“继续”会让它再跑一遍，产生第二份结果，而父 Agent 的任务早已收口；提案没说这个结果去哪。原因文案应写明“已交出结果”，并给用户确认。
- 只读会话（`readOnly`）、已归档会话的排队区：继续应当禁用并说明原因，`start` 的预检是 `read-only`。
建议：会话列表与子代理浮层的状态里加“有暂停的话”；`finished` 的继续要二次确认。

### 8. “只有宿主排的不显示编辑”与权限表不一致，而且“编辑”其实是删除后重发
严重程度：建议；类别：别扭与反常。
位置：提案第四节第 4、7 小节；`session-host.ts` 第 1382–1390 行。
现象：
- 界面的“编辑”不调内核的 `edit`：它是 `remove` 加把原文放进输入框，由用户当作新话重发（第 1382–1390 行）。内核的“`edit` 只能改自己发的”对它没有约束。对别人发的话，这等于用户拿走原文以用户身份再发一遍，发出者从宿主或父 Agent 变成用户，正是提案第五节“发出者不失真”想防的事。所以别人发的话不仅宿主的，会话（父 Agent）发的也不该显示“编辑”，第 7 小节只写“宿主排的”，漏了会话。
- 留着的用户自己的话能不能编辑，没写；`edit` 对留着的条目是否允许、会不会改状态也没写。
建议：规则统一成“`by` 不是用户（或不是当前用户）的条目：只有取消，没有编辑”；“编辑”留着的话时是取出到输入框，按提案的取出语义写明。

### 9. 恢复方式的用户设置：位置、缺省值、生效时点与替代做法没写
严重程度：建议；类别：接口、对照参照。
位置：提案第四节第 7 小节“用户设置里选恢复方式”；`packages/neuro-book/src/plugins/agent/shared/settings.ts`（所有项 `layers: ["user"]`，按分区放）。
现象：
- 没写放进哪个分区（`nbook.agent.reliability` 的“运行可靠性”，还是新分区）、键名、三个取值的内部名与文案、缺省值落在哪（提案第 3 小节写 `merge` 为缺省）。`defineSettings` 的项要加进 `agentSettings`，浏览器端读取后经 `session-host` 在 `send`、`enqueue`、`start`、`resume`、`release` 上传 `mode`，提案没列哪些指令带 `mode`，只说“放行的指令带一个模式”。
- 改设置对已经留着的条目生效吗：因为 `mode` 在放行那一刻由宿主传，所以对留着的条目也生效（我认为是对的）；提案不写，界面上也没有地方显示“点继续会合并还是按顺序”。建议排队区的继续旁用文字提示当前方式。
- 多窗口、其它宿主：设置是浏览器侧读的，非网页的调用（`nbook` 命令行、bot）拿不到，只会得到内核缺省，要写缺省值。
- 对照（凭记忆，未联网核实）：Claude Code 按 Esc 时把排队的消息放回输入框供编辑；Cursor 的排队消息每条带“立即发送”与删除。两者都没有“暂停状态加合并发送”，都是把控制权给用户逐条处理。提案的状态机可行，但缺省 `merge` 对“停下来是想换个话题”的用户有风险：旧话被拼到新话前面并先跑。至少该在排队区有显眼的“继续/丢弃全部”二选一，而不是让新话隐式放行。
建议：写出设置的完整声明；提示当前方式；缺省值交开发者再确认一次（见下）。

### 4 的更正
第 4 条里列的“子会话顶栏的停止”不是独立入口：子会话里的停止就是它自己的输入框停止按钮，与输入框那一处相同。独立的入口是三处：输入框停止按钮、同步向导“终止本轮”（`input.cancelRun`）、子代理浮层悬停停止（`stopRun`）。结论不变。

## 未发现问题的方面
- 多窗口下的“继续”或放行同时点：`release`、`start` 按 `commandId` 幂等，后到的得 `input-consumed` 一类结果，界面按现有的 `queued.remove` 做法静默忽略即可，没有新问题。
- 重启后条目留着、不自动发出：与 t07 决定 3 一致，快照读取路径（`kernel-transcript.ts` 第 667 行）本来就从缓冲区重建。
- 子会话 `finished` 之后留着、父 Agent 用会话身份放行自己的：界面侧无额外要求（后端合同由另一位审查者审）。

## 应交开发者决定、而提案自己定了的事
1. 停止的缺省选项：现状是所有停止都保留排队（2026-11-05 的决定），提案没说两个选项里哪个是缺省，也没说向导的“终止本轮”与子代理浮层的停止选哪个。
2. `merge` 缺省下“宿主的消息先于用户新话单独成一轮”：开发者说的“留着的先跑”是否包含宿主消息，提案按字面扩到了宿主；用户发话先等宿主的周期任务跑完，是否接受。
3. 合并后的对话显示：一条用户气泡、里面拼了几条旧话，还是每条各一个气泡；拼接格式。
4. 用户发新话是否应隐式放行留着的话：提案定为是；另一种是排队区里显式“继续/丢弃”，新话不碰留着的（Claude Code 一类产品的做法，凭记忆）。
5. `finished` 的子会话用户点“继续”是否允许再跑一次。
6. 第七节“待定项：无”与上面各条不符；提案没有验收场景的清单（没有列“Given/When/Then”），界面部分没法对照验收。
