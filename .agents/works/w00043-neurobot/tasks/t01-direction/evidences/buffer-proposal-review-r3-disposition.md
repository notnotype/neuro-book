# 《Agent 内核的输入缓冲区》第三稿的审查处理（第三轮，2026-11-18）

审查对象：第三稿，提交 `54de248e4` 时的固定副本。同一对象的最后一轮：一位 Claude Opus，前后端都看（[报告](buffer-proposal-review-r3-backend-opus.txt)，11 条：重要 8、建议 3，没有阻断）。审查者核对了第二轮处理表的 29 条，正文都有对应的改动，其中 B6、B7、B17 的改法带出了新问题（第 4、6、1 条）。

主 Agent 的核实：在主工作区用真实内核重跑了第 1 条的复现（[yield-steer](buffer-proposal-review-r3-yield-steer.test.ts.txt)，`packages/nb-harness` 下 `bun test`，通过）：子会话调用收尾工具的那一轮里到达的插话，`send` 交回的是正在收口的这次运行，运行以 `finished` 收口后这句话留在缓冲区里。这也是现有内核的缺口。

## 判断

三轮下来，提案的方向（每条带状态、回到空闲时剩下的留着、运行只取就绪的、由用户或排话的人放行、留着的先跑、指令按发出者有权限）没有被推翻；第三轮的问题都在“这套规则落到现有内核与 NeuroBook 的每个入口时怎样”：哪个入口算放行、`send` 的成功值要分清话的去向、任务中心的停止记成谁停的、`agentKey` 允许调用方自填身份。这些要对着真实内核写测试才能一条条定死，再写一轮散文提案收益很小。按审查 Skill 的轮数上限交开发者：推荐提案在方向上接受，下面的处理作为实现 Task 写 Spec 与计划时必须落下的项，计划审查时用真实内核验证。

## 处理（进实现 Task 的 Spec 与计划，两项交开发者）

| 条 | 归类 | 处理 |
|---|---|---|
| 1 交出结果那一轮里父 Agent 的话：`agent_send` 拿到上一个结果，话留着或跑在没人跟的运行里 | 成立（已复现） | `send` 的成功值分清三种去向：被这次运行取走、留着、推到之后的运行；`agent_send` 按去向告诉父 Agent（例如“子会话已交出结果，这句话没有被处理，留着”），不按 `currentRunId` 认任务 |
| 2 宿主只拦了 `start`，`resume`、`send` 能接着跑用户的运行 | 成立 | 开发者 2026-11-18 的“系统只能接着跑自己开的运行或在自己持有的会话里接着跑”用到所有会接着跑中断或暂停的运行的入口：非用户的 `resume`、`send` 只放行自己的、开新运行，不接着跑别人开的那一轮 |
| 3 任务中心里用户停子代理，记成父会话停的 | 成立 | 任务中心的停止经远程合同进来，以用户的身份停；`children.ts` 区分“父 Agent 停”与“用户在任务中心停” |
| 4 `session(id, issuer?)` 仍让调用方自填身份 | 成立 | 按调用方门面的视图不收调用方给的身份，只有 `nbook.agent` 自己的门面能指定；写进 `agent/sessions.md` |
| 5 空闲时 `enqueue` 自相矛盾 | 成立，交开发者 | 第 1 项（与第 6 条一起定） |
| 6 `compact` 的放行选项在通用规则下不起作用 | 成立，交开发者 | 第 1 项 |
| 7 编辑重发也成了放行入口 | 成立，交开发者 | 第 2 项 |
| 8 停止进行中到达的别人的话被盖上 `heldBy: user`；两个发出者同时停 | 成立 | `heldBy` 只盖在停止受理那一刻已在缓冲区里的；之后到达的按各自发出者处理；同时停时以先受理的为准 |
| 9 回到空闲后的放行是内存里的延后动作 | 成立 | 收口与 `inputHeld` 同批不变；“运行不再取输入时到达的放行”改成在收口的同一个写入批里一并写 `inputReleased`，不另起延后动作 |
| 10 旧日志里空闲会话的就绪条目升级后仍会被带走 | 成立，接受取舍 | 旧会话里卡着的话本来就是现有缺口留下的；打开旧日志时不补算，升级后由用户在排队区看见并处理。写进行为变化 |
| 11 `start` 依赖 bot 提案的 `owner`；宿主不能 `abort`；`heldBy`、`cause` 没有形状 | 成立 | 依赖写明（缓冲区提案先于或与 bot 提案的 `owner` 一起实现）；宿主能停自己开的运行；`heldBy` 写成发出者（`Issuer`），`cause` 写成 `{end: 收口方式, code?}` 或 `{queued: "idle"}` |
