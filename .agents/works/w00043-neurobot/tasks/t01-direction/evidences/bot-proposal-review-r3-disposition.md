# 《NeuroBook 的 bot》第七稿的审查处理（第三轮，2026-11-18）

审查对象：第七稿 `docs/proposals/neurobot.md`，提交 `c283bc9ff` 时的固定副本。开发者定完第七稿的两项后，按主 Agent 的建议做一轮窄的第三轮：一位 Claude Opus，只审缓冲区的取法表、指令按发出者的权限、授权、`settlePending`、期限与 `expired-run`、`owner` 盖章与自动接续。[报告](bot-proposal-review-r3-backend-opus.txt)，11 条：阻断 1、重要 7、建议 3。

主 Agent 的核实：在主工作区用真实内核重跑了第 1 条的复现（[retained](bot-proposal-review-r3-retained.test.ts.txt)，`packages/nb-harness` 下 `bun test`，3 条通过）：运行以 `error` 收口后空闲时再发一条，输入顺序是“用户问题 → 宿主消息 → 用户排的 followup”；`abort{keepQueue}` 之后发新消息，留着的 `steer` 与 `followup` 都并进了新消息开的那次运行；重开后 `interrupted` 的会话缓冲区还在、会话空闲。读代码核实了第 5 条：`AgentService.session(id, issuer?)` 缺省以用户身份，`agentKey` 在 `plugins/agent/` 之外没有使用方。

## 结构上的判断

“收口后缓冲区里的话归谁取”这一类问题三轮各找出新的路径：第一轮 `error` 与只压缩的 `followup`，第二轮 `finished`、只压缩时的 `steer`、`interrupted`，第三轮“留着”在内核里不是一种状态，之后任何人开的运行都会把留着的话取走。第七稿的表把宿主的话和用户的话放进同一个缓冲区，再在缓冲区之外按发出者分别定谁来取；可内核在边界上是整个缓冲区一起取的，所以只要宿主开了一次运行，用户留着的话就会被带走，逐条补收不了口。按审查 Skill 的轮数上限，这一类交开发者决定，不再接着补。

主 Agent 的推荐：宿主不和用户共用缓冲区。周期任务只在目标“可注入”时发：会话空闲、缓冲区是空的、没有等着接续的运行、不是只读、循环守卫没停。发出就是一次空闲时的 `send`，立刻开一轮、被取走，从不在缓冲区里排着；目标不可注入时，这条在 `nbook.schedule` 里等，日程视图与对话里看得到、能取消，目标变成可注入时再发，下一期到点仍没发出就跳过。这样缓冲区的规则完全照 w00032 t07 的决定与现有内核，缓冲区里只有用户自己的话，“留着、等恢复”就是现有内核的行为（用户下一次发消息或点继续时一起跑）。代价是开发者 2026-11-18 说的“周期任务可以是 `steer`”做不到：空闲时发，`steer` 与 `followup` 没有区别。

## 处理（按推荐的做法，待开发者定）

| 条 | 归类 | 处理 |
|---|---|---|
| 1 “留着”不是内核状态，之后任何运行都会取走 | 成立（已复现），结构问题 | 交开发者：宿主不和用户共用缓冲区（见上） |
| 2 `finished`、只压缩之后“开下一次运行”没有发起者，开不起来时又卡住 | 成立 | 按推荐的做法，宿主的话不会排在缓冲区里，这条只剩用户的话在手动压缩、子会话以收尾工具结束时卡住，是现有内核的缺口，与 bot 无关；从本提案拿掉，另记一条现有问题 |
| 3 宿主的 followup 进了父 Agent 在等的子会话运行 | 成立 | 按推荐的做法消解：子会话在跑时不可注入；子会话空闲时注入开的运行不经 `agent_send`、父 Agent 收不到结果，写成已知限制（产品上子代理不排周期任务） |
| 4 消息自带的期限没有载体，传不到派出的子代理 | 成立 | `send` 给宿主一个 `waitLimit` 选项，记在这条输入上，作用于它开的那一轮；`subagents.md` 输出 3 的继承名单加上它 |
| 5 `agentKey` 缺省以用户身份，任何插件都能造“用户亲手打的字” | 成立（已核实） | `agentKey` 按调用方门面提供时，`nbook.agent` 以外的调用方缺省身份是宿主（盖章）；循环守卫的解除条件写成“开这一轮的输入或插话的 `by` 是用户”，`turnStarted` 要能读到那条输入的 `by` |
| 6 重启后两个注入方抢同一个空闲会话 | 成立 | 按推荐的做法消解：有等着接续的运行时不可注入；`nbook.bots` 的自动接续只在缓冲区为空时做，否则显示“已中断”等用户 |
| 7 确定性错误下宿主消息一条条烧进失败的轮 | 成立 | 宿主消息开的运行以 `error` 收口时，日程视图记下码；同一条目连续失败几次自动暂停，数值在 Spec 里定 |
| 8 用户离开前排下的话会解除 `expired-run` | 成立 | 按推荐的做法消解：注入时缓冲区是空的，之后进来的用户的话都是用户在场时发的 |
| 9 带条件的 `start` 没定义叶子上有暂停运行时的语义 | 成立 | 按推荐的做法不再需要带条件的 `start`；“有暂停的运行”算“有等着接续的运行”，不可注入 |
| 10 父会话连带中止也保留队列，日志分不出谁停的 | 成立 | 按推荐的做法消解：宿主的话不在缓冲区里，中止只涉及用户的话 |
| 11 `ensureMain` 遇到 `session-exists` 不核对 `owner` | 成立 | `session-exists` 时读会话头，`owner` 不是这个 bot 就失败（`main-conflict`），不打开、不持有 |
