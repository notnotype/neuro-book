### 1. 对话视图的数据层不在可复用的包里，提案没有说谁来写（严重程度：高）
位置：提案第三节、第四节第 3 小节（依赖列表）、第五节“接口”
问题：提案把前端依赖写成“nb-runtime、nb-harness、nb-agent-ui、nb-ui、nb-markdown”，第三节还把“复用 nb-agent-ui（对话视图，核心带 harness 适配器）”当作现成能力。但 nb-agent-ui 只是纯受控视图，不订阅、不取数、不发请求；把快照、路径分页、日志帧、乐观消息、向导状态、草稿、断线重连合成 ctx 并把 action 换成远程指令的整层，在 NeuroBook 的 `nbook.agent` 浏览器入口里。t32 的补回清单明确把“给界面的远程接口”留在 nbook.agent。所以 NeuroBot 要自己写这整层，提案只在“HTTP 与设置自写最小版”里提到 HTTP，没把对话宿主算进工作量。
依据：docs/specs/ui/agent-conversation-view.md:19（非目标：不含会话数据层，不订阅 SSE、不调用接口）、:399（数据层与接口调用属于宿主）；packages/neuro-book/src/plugins/agent/web/session-host.ts 共 1459 行；docs/specs/agent/conversation.md 第 5 到 31 条几乎全是宿主行为（打开会话先订阅再取快照、乐观消息、结果未知、草稿、向导收起、两个窗口同步）；.agents/works/w00032-agent-integration/tasks/t32-harness-backfill/README.md“留在 nbook.agent：……给界面的远程接口、附件的 HTTP 路由”。
建议：提案补一条“对话宿主的归属”。三种做法各有代价：（a）把 session-host 里与 NeuroBook 无关的部分抽成包（nb-agent-ui 的宿主层或新包），NeuroBook 与 NeuroBot 共用，要加进 t32 或另开 Task，但 NeuroBook 现有行为有 e2e 兜底；（b）NeuroBot 抄一份，之后两份分叉；（c）NeuroBot 直接复用 `agent.sessions` 的远程指令形状，只换会话的选择逻辑。选哪种要在提案里写，并把工作量算进第一版。
### 2. “一条连续流跨多个会话”没有任何一层负责拼接，消息 id、历史分页、旧会话的动作都没处理（严重程度：高）
位置：提案第四节第 4 小节“界面”（“跨越压缩与轮换连续显示”）、第四节第 1 小节“会话……用户看不到它”
问题：现有视图与适配器都是“一会话一份 transcript”。拼成一条流至少要回答：（1）消息 id：旧适配器的 id 是 `h<seq>`，新内核适配器用事件 id 或 `seq-<n>`，两个会话必然撞 id，而 ctx 的 `branches`、`editing`、`message.*` action 都按消息 id 索引；（2）“更早的内容”：视图有 `history.hasMore` 与 `history.loadPrevious`，但 NeuroBook 的宿主在打开时 `loadPath` 循环取完整条路径、从不设置 `hasMore`。常驻 bot 的对话要长得多，打开页面就全量读所有会话在规模上不成立，提案没写分页，也没写“更早一页”在会话边界上怎么接；（3）旧会话里的消息不应出现“编辑、重试、从此处分支、回退”这类会话操作，这些都会改写已经轮换掉的会话，提案没有说这些入口在连续流里怎样关掉；（4）滚动锚点、切换会话时“清空全部纯界面状态并定位到最新”的规则（:375）在拼接流里不该触发。
依据：docs/specs/ui/agent-conversation-view.md:99（ctx.session 是单个会话）、:263（history.loadPrevious）、:375；packages/nb-agent-ui/src/harness.ts:174、packages/nb-agent-ui/src/kernel-transcript.ts:539（id 的生成）；packages/neuro-book/src/plugins/agent/web/session-host.ts:282-296（整路径循环读取到 more=false）；grep 该宿主没有 hasMore。
建议：在提案或 `conversations.md` 里定“流的合同”：gateway 提供按“对话”读取的接口（分页、从后往前，返回带全局唯一 id 的消息），视图仍只吃一份 messages；会话边界处插一条由 gateway 生成的分隔项；对话流里关闭所有会话级消息操作（用消息操作的显示条件，规范 :163）。把“分页往前取”列入第一版验收，不能只靠“全量读”。
### 3. 会话轮换在流里长什么样，提案的两句话自相矛盾（严重程度：中）
位置：提案第四节第 4 小节“会话轮换”与“界面”
问题：“会话轮换……新会话从上一次的摘要开始，对用户不可见”，而“界面”写“压缩在流里显示成一条分隔线，可以展开看摘要”。轮换产生的摘要在视图里属于哪一类 system 消息？视图的 `SystemMessageView.source` 只有 prompt、reminder、compaction、branch_summary、custom；只有 `compaction` 与 `branch_summary` 画成分隔线。新会话开头那段摘要是写给模型的上下文，若显示成 reminder 会变成一行淡色提示，若不显示则流上看不出发生过轮换，用户翻到那里会发现内容断了。另外 `shake` 方法不调模型、不产生新摘要（compaction.md 输出 1），所以“可以展开看摘要”并不总成立，分隔线展开后可能只有“省了多少 token”。
依据：docs/specs/ui/agent-conversation-view.md:129-131（source 取值）、:222（compaction 分隔线与展开的字段）；docs/specs/agent/compaction.md:39（shake 不调模型）。
建议：写明三种分隔的显示：压缩（有摘要或无摘要）、轮换、手动。轮换用 `custom` 或新增一类分隔线，内容是“轮换”的元数据和摘要，默认折叠，要看就能看，不要写“对用户不可见”这类与界面行为冲突的话。
### 4. 没有用户消息开头的内容（提醒、任务结果、静默回合）会被分轮规则并入上一轮（严重程度：高）
位置：提案第四节第 6 小节（提醒“bot 在对话里主动发一条消息给用户”；任务“把结果作为一条消息发进对话”）、第四节第 4 小节“压缩前刷记忆……静默回合”
问题：对话视图的分轮规则是“轮次从一条普通用户消息开始，到下一条普通用户消息之前结束”，最终回复是本轮最后一条正文非空的 assistant 消息。bot 主动发的消息、任务结果、压缩前的静默回合都没有前导的用户消息，会被并入上一轮：上一轮原来的最终回复变成“中间 content”被折进过程摘要，新消息变成它的最终回复，整轮摘要的计数和用量跟着变。用户看到的是：昨天的回答被收起来了，今天的提醒像是昨天那一轮的结尾。已结束并收起的轮次还会被改写，与规范里“已结束的轮次整轮收起”的稳定性矛盾。静默回合如果真在会话日志里写成了 assistant 工具调用，同样会生成一个看不见 user 的“开场轮”或并入上一轮。
依据：docs/specs/ui/agent-conversation-view.md:34（轮次的定义）、:41（最终回复）、:49（角色只有用户与 Agent，“为第三种角色预留”）；packages/nb-agent-ui/src/conversation-turns.ts 文件头注释（“轮次从一条普通用户消息开始”）；packages/nb-agent-ui/src/types.ts:111 与 registry.ts:125 只有角色登记项，消息的 kind 仍是 user、assistant、system、error 四种。
建议：提案要定这些消息在会话日志里是什么（系统注入的用户输入？带来源标记的事件？），并在视图侧加一种“由事件开启的轮次”（带来源角色，例如“日程”“任务”），把它写进 `agent-conversation-view.md` 的预期改动。第六节“对 Spec 的预期改动”目前没有列这份 Spec，应补上。压缩前的静默回合要么显式隐藏，要么用同一机制标出。
### 5. 周期任务会话里的审批，用户在界面上找不到入口（严重程度：高）
位置：提案第四节第 6 小节（任务在单独的会话里跑）、第四节第 7 小节（shell 与工作目录外写入缺省要用户在 web 上批准）
问题：审批向导是绑定在“当前会话”的：向导读 `ctx.pendingInputs`，来自当前会话的待处理事项。任务在另一个会话里跑，若该会话需要 shell 或工作目录外写入（周期简报很可能要联网、写文件），它会停在“等用户”，但（1）主对话流里没有任何东西指向它；（2）NeuroBook 的“Agent：1 运行中 · 1 等你处理”活动条目只列“前台会话”，而且是工作台状态栏的条目，NeuroBot 不用工作台布局，没有对应物；（3）该会话若按 NeuroBook 惯例标成后台会话，会话列表缺省也不列它。结果：任务悄悄停住，没有人知道，直到用户碰巧去看。仓库里现成的参照是 t14 决定 37 与 42（父会话的审批向导列出子会话的审批，标明来源），但 t14 未实施，提案又说第一版不用子代理。
依据：docs/specs/agent/sessions.md:52（`running()` 不含后台会话）、:77（activity 只列前台会话）、:73（后台会话 list 缺省不列）；docs/specs/agent/conversation.md 第 19 条；.agents/works/w00032-agent-integration/tasks/t14-multi-agent/README.md 决定 37、42；参照产品：Grok Bot 的后台审批卡片 30 分钟后过期（.agents/works/w00043-neurobot/research/2026-11-09-commercial-bots.md:111）。
建议：二选一并写进提案：（a）任务按 t14 的子会话机制派生，审批进主对话流的向导并标明“来自任务‘周报’”，这样第一版就依赖 t14 的审批冒泡；（b）第一版任务不允许需要审批的工具，遇到就标“需要你处理”失败并通知，用户在任务记录里手动重跑。无论哪种，要有一个全局的“待你处理”入口，不依赖工作台状态栏。
### 6. 主会话停在审批上时，整个 bot 的收件箱被堵住，无人值守的审批没有过期或回收（严重程度：中）
位置：提案第四节第 7 小节（审批沿用 harness 判定）、第四节第 6 小节（到点主动发消息）
问题：NeuroBook 的审批没有超时：运行停在“等用户”，向导一直在，输入框被替换，向导收起后规范还写“这时不能发新消息，要先处理它”。NeuroBook 里用户总在场，这没有问题。NeuroBot 是常驻的：用户晚上让它干活，shell 要批准，用户睡了。此后所有到点提醒、任务结果、新消息都要排在同一个主会话后面，或绕开会话直接发（提案没写）。第二天回来看到的是一个等了八小时的批准，加一串排队的消息。Grok Bot 对来自后台工作的审批卡片 30 分钟过期、拒绝后 bot 不重试直到用户再发话，聊天里的不过期；提案没有对应设计。gateway 重启时，harness 把在跑的运行写成 `interrupted`、不自动续跑，主会话回来是“上次运行被中断，回车继续”，用户不在场的话就一直是这样。
依据：docs/specs/agent/conversation.md 第 11 条；docs/specs/agent/sessions.md 输出 14（停止时按 interrupted 关闭，不自动续跑）；commercial-bots.md:111。
建议：在提案里补“无人值守的审批”：（1）审批请求带过期，过期后按拒绝处理并在流里落一条说明；（2）区分“用户正在聊的审批”和“任务引起的审批”，后者不阻塞主会话；（3）提醒与任务结果的投递不依赖主会话是否在等用户；（4）网关重启后的“中断”要有一个用户看得到的提示，不要只在输入框占位里。
### 7. 第一版只做 web，而“提醒”这个功能偏偏要在用户不看页面时触达（严重程度：高）
位置：提案第二节目标（“到点 bot 主动找用户”）、第四节第 6 小节、决策记录（QQ 第一版不做，先做 web）
问题：日程里的“提醒”和周期任务都假定用户会被找到。第一版只有 web，页面关着、标签页在后台或电脑休眠时，提案没有任何机制让用户知道有消息。规范和参照产品对这一点是明确的：Grok Bot“在你离开时继续工作，完成后通知”，Muse“仅在真正有新内容或需要你输入时通知”。提案没提未读标记、标签页标题角标、浏览器通知（localhost 是安全上下文，Notification API 可用，不需要 Web Push）、gateway 在本机时调用桌面通知等廉价做法。用户回来时，视图规范只会“定位到最新内容”，没有“离开期间新增了什么”的锚点；一个常驻几天的标签页，`ctx.now` 与按天分组也没提。结果是：第一版交付后，“提醒”这个目标基本只在标签页开着并且用户盯着时成立，和“像真人员工”的定位差距很大。
依据：docs/specs/ui/agent-conversation-view.md:264（切换会话后定位到最新）、:265；commercial-bots.md:104（Grok：完成后通知）、:199（Muse：仅在真有新内容时通知）；提案第二节目标与第三节同类产品。决策 5 是开发者定的，这里不质疑它，质疑的是“只做 web”之下的最低触达手段没有写。
建议：第一版加三个很小的东西并写进验收：（1）未读边界：记最后已读位置，回来时在流里插“从这里开始是你离开后的”分隔线，并滚到那里而不是最底部；（2）标签页标题角标与 favicon；（3）用户授权后用浏览器 Notification（页面开着但在后台时有效），页面完全关闭时的触达（桌面通知或邮件）写成已知缺口，在第二节非目标里明确，不让读者以为提醒一定到得了。未读状态存 gateway 而不是浏览器本地，多标签才一致（推断）。
### 8. 任务结果消息缺少“看过程”的入口，失败路径也没写（严重程度：中）
位置：提案第四节第 6 小节“任务在单独的会话里跑……做完把结果作为一条消息发进 bot 与用户的对话”
问题：只写了成功路径。用户想知道这份简报怎么来的、为什么今天少了一项、有没有失败重试，需要看任务会话的工具调用与失败原因；提案没说结果消息与任务会话怎么关联、入口在哪（点消息？日程页的运行记录？）、读者能不能只读地打开那个会话。失败时（模型失败、审批过期、gateway 重启中断、超时）对话流里发什么、发不发，也没写，容易变成“静默不产生结果”，用户无从知道任务没跑。另外“长输出不挤占主对话的上下文”与“结果作为一条消息发进对话”在结果很长时自相冲突：长结果进入主会话照样占上下文，在界面上也是一屏长文。
依据：提案第四节第 6 小节；参照：Grok Bot 每个 routine 保留最近 20 条运行记录（commercial-bots.md:102），OpenClaw 的 cron 每次新会话且可在 Control UI 看（open-source-architecture.md:128）；t14 决定 39、40 的“点卡片切到子会话、顶部路径可点回”是已有的界面做法，但未实施。
建议：（1）结果消息带 `sessionId` 附注（视图的 `MessageAnnotationView` 与条目渲染器正好可以挂一张“查看运行过程”卡片）；（2）日程页每个任务有“最近 N 次运行”列表：时间、状态、耗时、费用、打开会话；（3）失败也发一条短消息，说明原因与重试方式；（4）结果消息超过一定长度时，流里只放摘要，全文放到工作目录文件或任务页。
### 9. 日程页：谁改的、改了什么、运行状态、错过的处理，界面都没有定义（严重程度：中）
位置：提案第四节第 6 小节（“用户在 web 上改，bot 用工具改”）、第六节 `schedule.md`（“错过的处理”）
问题：（1）双写：用户在表单里改的同时 bot 通过工具改同一条，后写覆盖先写，提案没有版本或冲突检测；（2）归属：条目没有“谁创建、谁最后改”，用户无法分辨哪些条目是自己建的、哪些是 bot 自己加的（bot 可以自己给自己排周期任务，这类条目的数量没有限制，也没有用户确认）；bot 的改动也没有在对话流里留痕，用户只能在日程页发现有变化。原始记录只覆盖消息（第四节第 5 小节），日程的改动不在真相源里；（3）状态：下次运行时间、上次运行结果、已暂停、已错过，页面上都没提；第六节 `schedule.md` 写了“错过的处理”，第四节却没有规定 web 上怎么显示错过；（4）时区与夏令时：周期条目“每天几点”用哪个时区，在页面上怎样显示，没写。
依据：提案第四节第 6 小节；参照：Grok 每个 routine 有运行记录并限额（commercial-bots.md:101、:102）。
建议：每条日程记 `createdBy` 与 `updatedBy`（用户或某个 bot、某次工具调用）和时间，条目带 `rev` 做乐观并发，写冲突时界面提示“已被 bot 修改，刷新”；bot 通过工具创建或修改日程时，在对话流里落一条信息条目（视图的 system 提醒或附注）；条目列表显示下次运行、上次结果、状态；加数量或频率上限。
### 10. 记忆文件只读，用户发现记错了没有纠错路径，也看不到 bot 改了什么（严重程度：中）
位置：提案第四节第 5 小节“用户在 web 上能看记忆文件”；决策记录“记忆文件查看”
问题：（1）记忆是 bot 自己维护的，压缩前还有一个静默回合自动往里写；用户发现记错（日期、人名、偏好）只能在对话里让 bot 改，是否改对要再回去看；bot 不听或改错，用户没有任何办法，只能去数据目录手改文件，而核心记忆“每次请求都放进提示词”，手改后什么时候生效、会不会被 bot 的下一次写入覆盖，提案没说；（2）不知道什么时候、因为什么改了：静默回合里的写入不在对话里显示，用户永远看不到“这次压缩往记忆里加了什么”；（3）核心记忆有长度上限，页面上看不出哪份是核心、离上限多远、超限时 bot 的写入怎么办；（4）参照产品 Muse 的做法是用户可以编辑、下载记忆文件（commercial-bots.md:52），且提案第三节自己引了这一条。只读不是错，但应当写明为什么第一版不要编辑，以及纠错的替代路径。
依据：提案第三节“Muse：记忆是用户能编辑、下载的几个 Markdown 文件”；提案第四节第 5 小节；commercial-bots.md:52。
建议：二选一：（a）第一版就允许编辑，写入走与 bot 相同的文件接口，带修改时间的冲突检测（nb-markdown 已在依赖里）；（b）保持只读，但页面显示每个文件的最后修改时间与引起修改的会话或运行（链接到对应的消息或任务），核心记忆单独置顶并显示长度，加一个“告诉 bot 修正”的快捷入口，把文件与段落作为引用填进输入框。无论哪种，把“压缩前刷记忆”的写入在流里留痕。
### 11. “用户不感知会话”与视图里大量会话级概念并存，提案没有逐项处置（严重程度：中）
位置：提案第四节第 4 小节“用户没有‘新建会话’的入口”；第四节第 7 小节（审批）
问题：直接复用 nb-agent-ui 与 NeuroBook 的对话宿主，会带出许多以“会话”为单位的界面与语义，对用户不感知会话的产品是错的：（1）审批向导的“本会话都批准”与“审批模式”都是会话设置，会话每次轮换都会失效，用户点过“本会话都批准”后，下次轮换悄悄恢复询问，而按钮上的字让人以为是持久的；“以后都允许”写进 NeuroBook 的“我的规则”，NeuroBot 没有这个页面（permission-page 在 nbook.agent 里）；（2）顶栏、会话列表、分支树、`/new`、`/fork`、`/rename`、编辑历史、从此处分支；（3）状态栏的上下文圆环、累计 token 与费用按会话算，轮换时从满跳到零，累计费用清零，而常驻 bot 的花费恰是用户最需要看到的（空闲压缩、周期任务都在花钱）；（4）模型与思考档位选择器写的是会话设置，轮换时是否继承没说。
依据：docs/specs/agent/conversation.md 第 7、8、11、15、17、30 条；docs/specs/agent/permissions.md:98（“本会话都批准”的规则不跨 fork）与:112（“以后都允许”写进“我的规则”）；docs/specs/ui/agent-conversation-view.md:209（`newSession` 与 `header` 可关）、:279（输入框工具栏）。
建议：提案增加一小节“视图里关掉或改义的东西”：`header: false`、`newSession` 关、`interaction.commands` 只列 NeuroBot 做了的命令；审批的记住范围改为“这个 bot”并存在 bot 的设置里，设置页列出可撤销；用量与费用按 bot 累计并按天显示，不按会话；模型与审批模式按 bot 设置，轮换时由系统带到新会话。
### 12. 没有重置或遗忘的入口，而 NeuroBook 现有的失败提示正是“开新会话”（严重程度：中）
位置：提案第四节第 4 小节“用户没有‘新建会话’的入口”
问题：压缩失败时规范让用户“换压缩模型或开新会话”；上下文被一次坏的工具输出、坏的摘要或提示词注入污染时，NeuroBook 用户的出路也是开新会话。NeuroBot 把这个入口拿掉了，提案没写替代：压缩连续失败（`compaction-failed`）、模型一直报上下文溢出时，自动轮换是否兜底？用户想让 bot“忘掉这段对话”、想清掉敏感内容，原始记录是只追加的，记忆是 bot 自己维护的，用户也没有删除的办法。OpenClaw 保留 `/new`、`/reset`，参照产品也没有完全去掉重置。
依据：docs/specs/agent/conversation.md 第 21 条（失败显示“可以换压缩模型或开新会话”）；open-source-architecture.md:166（OpenClaw 默认不重置，但有 `/new`、`/reset` 手动重置）；提案第五节“原始记录与会话日志只追加”。
建议：保留一个用户可见但不叫“新会话”的出口，例如“让它从摘要重新开始”（强制轮换）；压缩失败时界面文字改成这个出口；删除或脱敏原始记录至少有一个文件级的说明，别让用户以为界面里清了就没了。
### 13. 页面范围在决策记录里，提案正文没有 web 一节；设置、首次运行、gateway 没起来时的状态都没有（严重程度：中）
位置：提案第四节（没有 web 的小节）、第六节、第七节“无”、决策记录末行
问题：“bot 列表、对话流、日程、记忆文件查看，不用工作台布局”只出现在决策记录里，正文第四节只有对话流一处讲界面。后果：（1）页面怎么组织（侧栏还是顶部导航，路由结构，落地页是什么）没有；只有一个 bot 时“bot 列表”是只有一项的页面；（2）设置没有页面：模型要绑定“对话”和“压缩”角色，缓存过期前压缩、空闲压缩都依赖“压缩”角色，没绑定时 `no-compaction-model`；NeuroBook 的这个提示是“到设置里绑定”，跳到 `nbook.models` 的设置页，NeuroBot 没有对应物，模型密钥“沿用 OMP 凭据库”但怎样登录、怎样选模型、怎样改审批规则，提案没提界面；Profile、人设、头像也一样；（3）首次运行：没有任何消息时的空状态（规范只给“还没有消息”），没有模型时的引导，gateway 没起来时 web 打不开用户看到什么，都没写；（4）第六节只列了 `docs/specs/bot/` 四份行为 Spec，没有界面 Spec，页面行为会被塞进 `conversations.md` 里。
依据：提案第四节、第六节、第七节、决策记录；docs/specs/agent/conversation.md 失败与恢复表（“没有模型、没有凭据、角色未绑定”）；packages/neuro-book/src/plugins/agent/web/permission-page.ts 与 profile-page.ts 属于 nbook.agent 的前端。
建议：正文补一节“web 界面”：页面清单、导航、路由约定（建议路径带 bot 与对话场所，例如 `/bots/:botId/chat`，单 bot 时跳转到唯一的 bot，这样以后多 bot 不改路由）、设置页的最小范围（模型与角色、审批规则、通知）、首次运行流程与各空状态；第六节补一份 `ui` 下的 Spec。
### 14. 流的真相源没选：原始记录还是会话日志，决定了以后群聊会不会推倒重来（严重程度：中，推断）
位置：提案第四节第 5 小节“原始记录是真相源”与第四节第 4 小节“界面”；第九节路线（多 bot、群聊）
问题：提案把“原始记录”称为真相源，只记入站与出站消息（时间、来源、内容），工具调用与结果在会话日志里。而界面上的对话流要显示过程摘要、工具详情、压缩分隔线，这些只在会话日志里。所以 web 的流只能从会话日志拼，原始记录只作重放用。到群聊和多 bot 时，同一个“对话场所”里有多个 bot 的发言，每个 bot 有自己的会话，流只能由原始记录排序，再按消息挂会话日志里的过程；现有视图的说话者身份来自会话级的 Profile 图标，不是消息级，规范说角色“为第三种角色预留”。如果第一版把流建在“会话日志拼接”上，群聊那一步就要重做流的来源；如果现在就建在“原始记录加按需取过程”上，第一版会复杂一些，但以后不用推倒。提案没有把这两个来源的关系写成合同，第一版选哪个也没写。
依据：提案第四节第 5 小节；docs/specs/ui/agent-conversation-view.md:216（Agent 的头像优先用会话 Profile 的图标）、:49（角色预留）；packages/nb-agent-ui/src/types.ts 中 MessageView 没有说话者字段。
建议：在 `conversations.md` 里先定“流 = 原始记录的有序视图，每条消息可挂会话日志里的过程”，第一版即使只有一个 bot 也这样建；视图加消息级的 `speaker`（bot id）而不是会话级身份。若认为成本太高，至少把“第一版流直接来自会话日志，群聊时重建”写成已知取舍。
### 15. 常驻单流缺少长流的导航：按天分隔、搜索、跳转（严重程度：低到中）
位置：提案第四节第 4 小节“一个 bot 一条对话流”
问题：视图的时间只显示在每条消息的角色行里，没有按天分隔；NeuroBook 的会话搜索只搜标题和说明，“搜对话内容”明确不承诺。单流跨月、跨年之后，“上周二她让我约的那个人是谁”只能靠问 bot 或手动一路向上滚；原始记录已经有数据，却没有任何入口。参照产品的 Control UI 有会话列表与分类。
依据：docs/specs/agent/conversation.md 非目标“搜对话内容：只搜标题和说明”；docs/specs/ui/agent-conversation-view.md:216（时间显示在角色行）、:301-323（会话列表按日期分组，是对多会话设计的）。
建议：第一版至少加“按天的分隔线”和一个按文字搜原始记录并跳转到对应位置的入口（依赖建议 2 里的分页接口）；若不做，写进非目标。
### 16. 断线、重启与长时间离开：常驻 gateway 的重连与页面状态没有设计（严重程度：低到中）
位置：提案第二节“gateway：常驻进程”、第五节“接口”
问题：NeuroBook 里服务端换进程后，浏览器节点是终态，只能“重新加载页面”，会话显示中断的样子。对常驻 gateway，重启（升级、崩溃、休眠唤醒）是常态，标签页可以开几天：（1）每次重启都要用户手动刷新是否可以接受，或者页面自动重载并回到流的位置、保留草稿；（2）重启时正在跑的主会话和任务会话都按 interrupted 关闭、不自动续跑，用户回来时流里没有提示，任务会话里的中断更是没人看见（见第 5 条）；（3）休眠唤醒后 `ctx.now`、日程的“下次运行”显示是否更新；（4）页面不在时 gateway 写出的消息，重连后按日志补齐，提案没提和未读边界的关系。这些在 NeuroBook 里被“用户总在场”的假设掩盖了。
依据：docs/specs/agent/conversation.md:112（服务端换进程后重新加载页面）；docs/specs/agent/sessions.md 输出 14。
建议：在 `conversations.md` 预期改动里加“重连与重启”：重启后页面自动重连，不要求用户刷新，被中断的运行在流里落一条说明（含任务），草稿保留。
### 17. 手动压缩与压缩模型选择在“用户不管会话”的产品里没有处置（严重程度：低）
位置：提案第四节第 4 小节“压缩触发点：沿用阈值、溢出、手动三种”
问题：“手动”触发点在 NeuroBook 是用户在输入框里敲 `/compact`；用户不管会话的 NeuroBot 里要么保留这个命令、让用户理解“压缩”，要么作为开发者入口，提案没有说。空闲压缩和缓存过期前压缩是为省钱，开发者确认过；它们发生时用户可能正好回来发消息，视图有“只压缩的运行”的状态（“正在压缩”，规范第 21 条）和下一条消息排队语义，但提案没有提这个竞态：用户刚回来，第一条消息卡在一次空闲压缩后面，界面上会显示“正在压缩”并等待多久，没有说明。
依据：docs/specs/agent/conversation.md 第 20、21 条；提案第四节第 4 小节两种新触发点的描述（“空闲压缩”）。
建议：写一条规则：用户消息到达时，后台压缩可以被取消或让位（取消时回到原上下文），或者界面文字明确“正在整理记忆，约 N 秒”；`/compact` 在 NeuroBot 里保留为命令但不出现在入门提示里。
审查结束，共 17 条
