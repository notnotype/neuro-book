# 《Agent 内核的输入缓冲区：每条带状态》第一稿的审查处理（2026-11-18）

审查对象：`docs/proposals/agent-input-buffer-states.md`，提交 `89af44967` 时的固定副本。三位审查者：Claude Opus 审内核与后端合同（[报告](buffer-proposal-review-r1-backend-opus.txt)，15 条：重要 12、建议 3），Claude Sonnet 审对话视图（[报告](buffer-proposal-review-r1-frontend-sonnet.txt)，9 条：重要 6、建议 3），Claude Sonnet 拉远看（[报告](buffer-proposal-review-r1-zoomout-sonnet.txt)，7 条：重要 5、建议 2）。下表用 B、F、Z 指三份报告的条目。

主 Agent 的核实：在主工作区用真实内核重跑了 B 的三个复现（`packages/nb-harness` 下 `bun test`，都通过）：[带结果要求的会话以文字收口](buffer-proposal-review-r1-result-text.test.ts.txt)后 `followup` 留在空闲会话里；[空闲时 `enqueue`](buffer-proposal-review-r1-idle-enqueue.test.ts.txt) 的用户的话被之后以会话身份开的运行带走；[停止进行中到达的话](buffer-proposal-review-r1-abort-window.test.ts.txt)交回成功后被清空。读代码核实：界面的停止一律 `abort{keepQueue: true}`（`plugins/agent/web/session-host.ts`，注释“开发者 2026-11-05 定”，`agent/conversation.md` 输出 6）；旧内核读到不认识的内核事件名得 `log-corrupt`，不支持降级（`harness/session.md` 的“边界与兼容”）。

## 结构上的判断

第一稿仍按“收口方式”逐行列表，审查又找出三条表外的路径（文字收口、进程内的中断、空闲时排队）和一处时间窗（停止进行中）。这与 bot 提案三轮的情形相同：按入口逐条列，总会漏。改法是不再按收口方式列，而在**会话回到空闲**这一处定：会话回到空闲（不论怎样收口，包括进程内中断与打开时的恢复）时，缓冲区里剩下的话都算“留着”，原因取最后一次运行怎样结束；空闲时排进来的也算留着。运行只取就绪的。这样新的收口方式不会漏，也不需要单独写 `inputHeld` 事件：留着由日志推出，只有放行写事件（Z6 的“一个来源”）。

第二点是合并：合成一条输入放在宿主做，内核只给 `send` 一个“同时移除这几条”的选项，原子地完成（Z5、B8、F2、F5）。第三点是把宿主这种发出者从 bot 提案移进本提案，两份提案不再互相依赖（Z3、B11）。

## 处理（第二稿，部分待开发者定）

| 条 | 归类 | 处理 |
|---|---|---|
| B1 带结果要求的会话以文字收口不看缓冲区 | 成立（已复现） | 由“回到空闲”一处覆盖 |
| B2 回滚说法与 Spec 相反 | 成立（已核实） | 改成“不支持降级，同现有规则”；新事件只有放行一种 |
| B3 正常退出的进程内中断不经过恢复 | 成立 | 由“回到空闲”一处覆盖 |
| B4 只压缩的运行接着开一轮照字面做不出来 | 成立 | 不再接着开一轮：压完回到空闲，排着的话留着；用户自己发起的压缩由宿主在压完后放行（交开发者，第 3 项） |
| B5 空闲时排进来的话一直就绪 | 成立（已复现） | 空闲时排进来的算留着 |
| B6 子会话连带中止与 kill 只许用户放行，与 subagents.md 输出 16 冲突 | 成立 | 放行规则交开发者（第 1 项）；推荐排话的人能放行自己的，连带中止留下的父 Agent 能放行 |

| B9 停止进行中到达的话被清空 | 成立（已复现） | 只清停止受理之前排着的，之后到达的留着 |
