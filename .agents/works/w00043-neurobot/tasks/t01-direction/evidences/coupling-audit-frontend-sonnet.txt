NeuroBook 前端耦合审查（二）：工作台、各插件的界面与前端包
日期：2026-11-18；只读审查；仓库 master；范围见派发说明。nb-agent-ui 内部不审，只看 NeuroBook 怎么用它。
路径省略前缀 packages/neuro-book/src/（除非写全）。“读代码核实”= 直接读到该行；“推断”= 由依赖图与规则推出，没有运行验证（按规定没跑 e2e 与开发服务）。

【结论】
1. 前端的插件分层本身是好的：工作台、视图、页面、命令、设置、状态都经贡献点；跨插件运行时导入只指向 `shared/contracts.ts`（architecture.test.ts 守着）；工作台不写死任何业务视图 id，缺省布局由视图声明算出；贡献点的拥有者不在时，贡献挂起、不报错（plugin-manifest.md 输出 10）；没有项目的窗口是一等状态。所以“界面不加载、别的照常”在设计上基本成立，叶子插件很多。
2. 卡点不在界面分层，在三处：(a) 没有停用内置插件的机制（Spec 一刀切拒绝，服务端把全部内置插件当启动必需）；(b) 对话界面的接线层闭在 agent 的浏览器入口里，没有对外服务，bot 视图要么抄要么先抽；(c) 几个封闭名单与字符串引用让“新增或关掉一个内置插件”要改别的插件。
3. 前端包（nb-ui、nb-layout、nb-form、nb-markdown）里没有应用特有的概念漏进去，只有注释里的旧路径与命名痕迹。

==== 附 A：核心与可选（回答第 2 问，浏览器一侧；依据是各入口 `dependencies` 里 `required` 的写法，读代码核实；“关了”的效果是由依赖图与 plugin-manifest.md 输出 10 的“拥有者未登记则贡献待校验、不报错”推断，没有运行验证）====
核心（实际上不能关）：runtime.diagnostics、nbook.state、nbook.commands、nbook.settings、nbook.storage、nbook.workbench（window.ts:139 必需；workbench 与 commands 把 settings、storage、state 声明为必需依赖）；nbook.http（宿主适配器）；nbook.files（editor、explorer、markdown 都把 `filesKey` 声明为必需，它只是一个没有界面的门面）。

可选、叶子（没有别的内置插件把它们声明为必需依赖；读代码核实）：nbook.agent（没有任何内置插件向它的贡献点贡献，在 plugins/ 里搜 agentTool、agentExtension、agentProfile、PROFILES_POINT 只命中 agent 自己与 Lab 场景；别处对它只有第 3 与第 4 条两处软引用）、nbook.tasks、nbook.stickers（markdown、agent 都是可选依赖）、nbook.html-preview、nbook.image-viewer、nbook.theme-study（只有声明与素材）、nbook.desktop、nbook.explorer、nbook.editor（工作台在没有编辑器槽提供者时“回到欢迎文字”，plugins/workbench/web/editor-area.ts:1-4）、nbook.projects（没有它 `/` 没有首页、没有“回书架”，命令不在目录里时标题栏不画入口，WorkbenchShell.vue:480-482 与 spec 输出 36）、nbook.models 与 nbook.plugins（浏览器入口只有设置页，按页面激活）、nbook.canon 与 nbook.plot（没有界面；plot 只有 project 与 server 位置，canon 的浏览器入口只提供一个没人用的 `canonClientKey`：在 src 范围内除它自己外没搜到使用者）。
业务功能的核心与可选：对“写作”这个产品，核心是 files + markdown + editor + explorer + projects + workbench；agent 对产品是主功能，但在架构上是叶子，可以整体关闭；canon、plot 是后台能力，plot 硬依赖 canon（plot/backend/plugin.ts 的依赖 `canonProjectKey`）；tasks、stickers、html-preview、image-viewer、theme-study、desktop 是增强件。
注意：服务端与项目子进程把所有内置插件当启动必需（第 1 条），所以“可选”今天只是依赖关系上的可选，不是运行上的可选。

==== 附 B：bot 界面的接点清单（回答第 3 问；只列接点与耦合性质，不做界面设计）====
以下每一项都是 bot 插件要接的地方；“怎么接”是现有合同，“耦合”是接上之后产生的依赖。
1. 插件登记（装配登记，机检会兜底）：manifest.ts 的 `productPlugins`、`plugins/bot/plugin.ts` 描述、web/plugins.ts 的 `browserPluginDefinitions`（:64-84）与 `builtinPluginCatalogs`（:102-115）、静态素材表 `builtinPluginAssets`（若有）、plugins/plugins/shared/builtin-names.ts 名单与两份语言目录（第 6 条）。如果要有后端，还有 server 与 project 的定义表。耦合：登记，可以接受。
2. 工作台里的视图：向 `workbench.views` 贡献（workbench/shared/views.ts:128）。`location` 取 sidebar、auxiliarybar、panel；不写 `container` 就拥有自己的隐式容器，在活动栏有一个入口（workbench-layout.md 输出 41）；写 `container: PROJECT_VIEW_CONTAINER`（views.ts:141）就并进“项目”容器，这个容器名带“项目”语义，bot 不该进。视图标题后的计数用 `badge()`（web/contracts.ts:36-42）；活动栏入口是否显示这个计数，我没核实。耦合：只依赖 workbench 的 `shared/contracts`，与 explorer、tasks 同一做法。可以接受。
3. 活动栏底部条目、状态栏、标题栏：`workbench.activitybar-items`、`workbench.statusbar-items`、`workbench.titlebar-items`（shared/items.ts:25-54），显示条件 `when.requires` 写公开状态键。耦合：公开状态键是字符串，插件间读取没有机检（第 3 条）。
4. 独立页面：`workbench.pages`（workbench/web/pages.ts:19-33）：路径必须是小写段，贡献 id 必须等于路径，`/api`、`/assets` 保留，页面标题是普通字符串（没有语言目录的引用）；可选 `reloadOnLeave`。耦合：路径唯一，路由归宿主 web/router.ts；页面没有工作台的外壳。这是“单独页面”的做法，也是 Lab 在用的做法（plugins/lab/web/plugin.ts:23）。
5. 编辑区页面（把 bot 对话当一个标签开在编辑区）：`editor.pages`（editor/shared/contracts.ts 的 `EDITOR_PAGES_POINT`），agent 就是这样做它的“页面”位置（agent/web/plugin.ts:536）。耦合：需要 `nbook.editor` 在；没有它时贡献待校验、不报错，bot 只剩视图。可以接受。
6. 无项目首页：`workbench.home` 单提供者（workbench/shared/home.ts，“几个首页同时在时全部不采用”）。书架占着，bot 不能直接要它；要进入工作台的方式是 `/workbench` 或自己的页面路径。耦合：能力的两面，可以接受，但要在设计里明确 `/` 属于谁。
7. 对话组件：见第 2 条，没有现成的接点，需要 agent 提供浏览器服务，或复制接线层。耦合：不推荐复制。
8. 渲染 Markdown 与输入框：`markdownKey` 服务（markdown/shared/contracts.ts:43-47，`MarkdownDisplay`、`PromptEditor`、`PromptTextView`），agent 就是必需依赖它。耦合：bot 也会硬依赖 markdown，而 markdown 硬依赖 files（markdown/web/plugin.ts:96）；这条链在没有项目的窗口里照常工作，可以接受。
9. 命令：`commands.definitions`，id 受域词表约束（第 6 条）；命令声明里 `expose.agent` 决定 Agent 能不能调它（agent/web/plugin.ts:95-100 的写法）。快捷键写在命令声明里。耦合：封闭词表。
10. 设置：`defineSetting` 写进 `shared/contracts.ts`，设置页用 `SETTINGS_PAGES_POINT`；`category` 只有 app、ai、plugins（第 6 条）；`layers: ["user"]` 或含 project。耦合：封闭联合。
11. 公开状态与存储：`state.public`（键 `nbook.<插件>/<名>`）；`storageKey` 的记录，`scope: "user" | "project"`，没有项目时只有用户层（agent/web/plugin.ts:117 的写法）。耦合：按作用域，没有项目也能存。
12. 远程服务：服务端入口提供合同，浏览器入口 `context.remote.use(合同)` 订阅事件（agent/web/plugin.ts:195、:263-282 的写法）。耦合：合同放在 bot 自己的 `shared/contracts.ts`，没问题。
13. 通知、快速选择：`notificationsKey`、`quickPickKey`（workbench 提供，agent、tasks、projects 都在用）。耦合：依赖 workbench，可以接受。
14. 主题“工作中”信号：第 3 条。
15. 窗口的项目绑定：窗口一生只绑定一个项目代次；在绑定了项目的窗口里，Agent 会话创建时默认归该项目（session-host.ts:145-146 的注释“新建的会话归它”）。bot 的会话是不是该归项目，是设计问题；复用会话宿主时要有一个“覆盖 project”的参数。耦合：设计决定，可以接受。
16. 对话位置键：agent 的最近会话记录与对话位置名绑定（第 2 条），bot 位置要有自己的名字。

说明：证据标“读代码核实”的是直接读到的行；标“推断”的是由依赖图或规则推出、没有运行验证。路径省略前缀 packages/neuro-book/src/，其它包写全。

### 1. 内置插件不能停用：没有机制，且服务端把全部内置插件当“启动必需”
类别：可以拆开（代价中）
位置（读代码核实）：docs/specs/runtime/plugin-install.md:19、:51、:123（内置插件的启用、禁用一律拒绝，`builtin-fixed`）；manifest.ts:44（`productPlugins` 常量表）；server/main.ts:13-14、project/main.ts:10（两个进程入口直接传它）；server/start.ts:123（`options.manifest ?? productPlugins`）、:242 与 project/start.ts:152（`requiredPlugins` 取全部非第三方插件，任何一个内置入口失败整个服务启动失败，plugin-manifest.md:135）；web/host/window.ts:139、:447-489（浏览器只登记服务端引导集合里出现的内置插件，构建里的 `browserPluginDefinitions` 是全集，web/plugins.ts:64-84）。
现象：今天没有任何办法让用户停用内置插件，设置、Profile、命令行参数都没有（在 src、docs/specs、docs/adr 里搜 disabledPlugins、停用、disable plugin、NBOOK_*PLUGIN，只命中第三方插件的启停）。能缩小插件集合的只有改 manifest.ts，或测试里传 `startServer({manifest})`。没有测试从产品清单去掉一个内置插件再起整套应用（在 src、e2e 里没搜到），所以“关了坏什么”只能从依赖图推。有利的一面：浏览器已经跟着服务端走，服务端少一个插件，浏览器就少一个，不用改前端构建。
追到上游：“内置不能禁用”不是原始决策。ADR 0022:30 与提案 extensible-application-platform.md:351、:464 写的是“启动必需的内置插件不能禁用”，并要求禁用前列出连带受阻的范围、由用户确认（:462）；w00027 t01 计划写“本轮不能禁用；哪些非核心内置插件可以禁用以后再定”（.agents/works/w00027-plugin-platform/tasks/t01-requirements/plan.md:75），是明写的“以后再定”，之后 Spec 收成一律拒绝。放开它不违反已接受的 ADR，改的是 Spec 一句话。
挡住的场景：用户关掉某个内置功能；bot、日程做成内置插件后让不想要的人关掉；第二个应用从内置插件里挑一部分。
建议：加“按配置过滤产品清单”一层，不改插件本身。(1) 状态根里一份停用名单（或环境变量、命令行参数），服务端启动时读、过滤后传给 `startServer`，项目子进程经已有的 `plugins` 启动消息（project/start.ts:99-110）带同一份；(2) 停用前对过滤后的清单跑内核的受阻推导，必需依赖缺失就拒绝或列出连带范围；(3) 描述符加“核心/可选”标记，核心不许停用；(4) 改 plugin-install.md 输出 4，`builtin-fixed` 只对核心；(5) `BUILTIN_PLUGIN_IDS` 与清单的相等测试改成子集；(6) 补“逐个去掉可选插件再启动”的合同测试，把本报告表里的推断变成证据。下次启动生效，与第三方插件一致。

### 2. 对话界面只能在 `nbook.agent` 内部用：没有对外的浏览器服务，bot 界面无处可接
类别：可以拆开（代价中；是 bot 界面复用的第一道门）
位置（读代码核实）：plugins/agent/web/plugin.ts：入口 `activate`（:185-726）是约 540 行的闭包，本入口没有 `provides`，只返回 `receivers` 与 `contributions`（:692-722）；:311 与 :464 对话位置写死为 `"view" | "page"`，最近会话的存储键按位置名分；:464-640 `conversationComponent` 把 nb-agent-ui、Profile、Skill 菜单、文件提及、附件、模型角色、子代理卡接成组件；session-host.ts:143-250（`SessionHostDeps`，约 20 个注入项）；agent/shared/contracts.ts:124（`agentKey` 只在服务端）。nb-agent-ui 在应用里只有 `plugins/agent/web/` 引用。
现象：nb-agent-ui 是视图包，“怎样把一个会话挂到界面上”的接线层（`session-host.ts` 1751 行加 `ConversationHost.vue`、`SessionPanelHost.vue` 与各种适配）只在 agent 浏览器入口的闭包里被创建，不经任何服务键或 `shared/contracts.ts` 公开。`SessionHostDeps` 的注入面做得好（外部能力都是参数，不碰全局），问题只在没人能拿到这个工厂与接线。
挡住的场景：bot 要在工作台里做“一条不断的对话”的视图，会话由 bot 自己的身份决定（固定会话、没有列表与新建）。bot 插件不能 import `nbook/plugins/agent/web/*`（architecture.test.ts:118-120），只能抄一份接线，或让 agent 先对外开服务。
建议：在 agent/shared/contracts.ts 定义浏览器服务键（例如 `agentConversationKey`），`mount({session: 固定 id 或自由, position: 调用方给的名字, features})` 返回组件与控制句柄。要动的：把 `conversationComponent` 与 `hostAt` 抽成独立模块，位置名改成参数，会话列表与新建做成可关的特性，会话归属项目可由调用方覆盖（session-host.ts:145-146 现在“新建的会话归窗口绑定的作品”）。nb-agent-ui 不用动。代价中：纯搬运加一个服务键，agent 现有 `session-host.test.ts` 与 dom 测试覆盖搬运。
追到上游：对话宿主留在应用里、各应用自己写，来自 ADR 0045 决策 6 与提案 neurobot.md:52、:351。ADR 的备选方案给的理由是“接口只会照着 NeuroBook 设计、等写出来再比重复多少”，同一节写明开发者没有另外说明理由，不当作开发者的理由引用；那是 2026-11-10 的判断，当时 bot 还不是内置插件。现在 NeuroBook 内会有 agent 视图与 bot 视图两个使用者，“等写出来再比”的条件已具备：先在 NeuroBook 内做服务，不急着做共享包；会话合同 `agentSessionsContract` 是 NeuroBook 专有的，抽包要再加传输抽象，等 NeuroBot 网页宿主（w00043 t06、t07）写出来再判。

### 3. 工作台按字符串读 Agent 的公开状态，主题“工作态场景”只认 Agent
类别：可以拆开（代价小）
位置：plugins/workbench/web/plugin.ts:167-171（`stateService.read("nbook.agent/active")`）、:284（`themes.resolve(…, agentWorking())`）；plugins/agent/web/plugin.ts:116-118（`definePublicState(descriptor.id, {active})`）。（读代码核实）
现象：工作台决定要不要换成主题的“工作态场景”（书房主题的忙碌版插图）时，直接读 Agent 插件的公开状态键，键写成字符串字面量，不在 agent 的 `shared/contracts.ts` 里（别的插件读公开状态的键是 `publicStateKey` 加字符串，没有机检）。没装 Agent 时读不到，按空闲，所以降级是对的；耦合只是“方向与形状”：工作台认识一个具体业务插件，而且只认它。
挡住的场景：bot 在后台干活、日程在跑任务时，主题的“工作中”不会亮；以后每加一个“AI 在忙”的插件都要改工作台。
建议改法：工作台自己定义一个“忙碌”贡献点或公开状态约定（例如 `nbook.workbench/busy`，任何插件用 `state.public` 贡献并写 true），工作台读它的并集；agent 插件把现在的 `active` 同时发布成这个键。代价：小（工作台约 10 行、agent 约 5 行、一条 Spec 说明）。同类的“读别的插件公开键”还有 plugins/html-preview/web/plugin.ts:106-107（`"nbook.editor/activeEditor"`、`"nbook.editor/activeDocument"`），应把这两个键常量放进 editor/shared/contracts.ts。

### 4. models 的设置挂在 agent 的分区下，靠字符串反向引用
类别：不推荐耦合（代价小）。理由：这是为绕开依赖环而写的反向字符串引用，让 `nbook.models` 隐含地认识 `nbook.agent`；它挡住“关掉 agent 之后设置页仍然干净”这个场景，也与“插件之间只经贡献点与 shared/contracts 协作”的目录约定（packages/neuro-book/AGENTS.md）的精神相反
位置：plugins/models/shared/settings.ts:18-19（注释：“Agent 依赖模型服务，反过来引用会成环，所以按 id 写”）、:28、:54（两项设置 `section: "nbook.agent.reliability"`）；agent 的分区声明在 plugins/agent/plugin.ts:16、agent/shared/settings.ts。设置分区缺失时的降级见 docs/specs/settings/settings-window.md:32、:166、:253（落到“其它”并记诊断）。（读代码核实）

建议改法：把这两个设置项的“分区归属”改由 agent 声明（agent 在自己的描述里把别的插件的设置键加进它的分区，或者分区在 settings 一侧有“按键列表收录”的写法），models 不再写 `nbook.agent.*`。代价：小到中（需要 settings 贡献点支持“分区认领别人的键”，或者把这两项设置挪到 agent 的 `shared/settings.ts` 去声明，属于数据迁移：键名按插件 id 前缀，挪了会改键）。若不愿动键，可以接受维持现状并在 models 的 AGENTS 里登记为已知反向引用。

### 8. 产品插件按路径名认 Lab 页面
类别：可以拆开（代价小）
位置：plugins/agent/web/plugin.ts:156（把 `globalThis` 收窄成带 `location.pathname` 的形状）、:217（`if (browser.location?.pathname.startsWith("/lab") !== true) void activity.start(…)`）；docs/specs/agent/conversation.md:42 写了“Lab 窗口不启动活动条目”。在 plugins/ 里除 lab 自己外没搜到第二处（grep `"/lab"`、`pathname`）。（读代码核实）
现象：Agent 的浏览器入口认识“当前页是不是 Component Lab”，是产品代码里唯一一处按路由名为开发工具开分支的地方。字符串 `/lab` 因此进入生产构建（Lab 自身的代码被 `check:dist` 排除，这个字面量不会被它拦下，推断：门禁扫的是 Lab 模块与 fixture 的标记，没有逐个核对）。

### 9. 业务界面对“打开了项目”的假设：浅，可以接受（读代码核实）
类别：可以接受
位置：shared/projects.ts:174（`windowProjectKey`）、web/host/window.ts:282、:326（窗口一律提供它，值可以是 null）；十个浏览器入口声明它为必需依赖：workbench/web/plugin.ts:129、explorer/web/plugin.ts:96、editor/web/plugin.ts:100、files/web/plugin.ts:26、storage/web/plugin.ts:24、settings/web/plugin.ts:123 与 :182、canon/web/plugin.ts:23、html-preview/web/plugin.ts:67、agent/web/plugin.ts:171、projects/web/plugin.ts:92（markdown 是可选，markdown/web/plugin.ts:96）；各入口对 `project === null` 的处理：explorer/web/plugin.ts:108、editor/web/plugin.ts:118、145-146、165、299（标签与最近文件不持久化、只在内存）、html-preview/web/plugin.ts:86（`denial: "no-project"`）、files/web/plugin.ts:33-34、agent/web/plugin.ts:188、:117 与 :293（最近会话按有无项目落作品层或用户层）、markdown/web/plugin.ts:110-124（上传不可用、列表为空）、workbench/web/state/layout-doc-store.ts:56-58、577-578（布局按“有无项目”分作品层与用户层两份记录）、WorkbenchStatusBar.vue:70、WorkbenchShell.vue:94（“未打开项目”文字）。
结论：这是“值可为空的宿主能力”，不是“没有项目就起不来”。没绑定项目的窗口是一等状态：`/workbench` 页面“不打开作品、直接进入空工作台”（docs/specs/ui/workbench-shell.md:105，输出 37），`/` 在没有项目时由 `workbench.home` 的贡献者接管（输出 36）。所以 bot 的视图可以在没开项目的窗口里用，前提是它不依赖 explorer、editor 的项目文件功能。要注意的三点（见下面“接点清单”）：（a）窗口一生只绑定一个项目代次（files/web/plugin.ts:32 注释、window.ts 启动序列），切换项目是整页导航，bot 视图随之重建，服务端的会话不丢；（b）`workbench.home` 是单提供者，书架已占着，bot 想做 `/` 要另做一个“有项目 / 没项目”的分流，或自己用页面贡献点占一个路径；（c）`/workbench` 是直接输入地址进入的，没有产品入口，bot 的“常驻”入口要自己提供。这些是能力的两面，拆开的代价高于收益，故可以接受。

### 11. editor 必需 markdown，markdown 又向 editor 贡献编辑器：一个能力的两面

现象：两个插件互相有运行时导入，但都只经对方的 `shared/contracts.ts`，没有环依赖（服务依赖只有 editor → markdown 一个方向）。Markdown 同时是“富文本组件库”（显示、提示词编辑器）与“编辑器的一种”，拆成两个插件能让 bot、agent 不为用显示器而加载编辑内核，但 nb-markdown 包已经做了这个分层（显示与编辑器扩展分入口），插件层再拆收益小；`AGENTS.md` 的前端一节已要求带 DOM 的部分放进按需加载的 `.vue`，所以实际上不会多加载。
结论：不用拆。需要注意的是 bot 与 agent 一样会因此硬依赖 markdown 与 files（见附 B 第 8 项）。

### 12. 约 40 处“只引类型”的跨插件导入落在 `shared/contracts.ts` 之外
