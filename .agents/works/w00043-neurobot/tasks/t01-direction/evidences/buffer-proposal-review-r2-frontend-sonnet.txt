# 第二轮前端审查（Sonnet）：提案第二稿（1e9c0cce4）第四节第 2、3、4、7 小节的界面与 nb-agent-ui 部分
审查方式：读代码，未跑运行时实验；下面标“从代码推断”的都是。

### 1. “乐观消息按 inputId 确认”在现有事件流上做不出来
严重程度：重要；类别：接口与合同不足。
位置：提案第四节第 6 小节末条；`packages/nb-agent-ui/src/kernel-transcript.ts` 第 704 行；`packages/nb-harness/src/kernel/run/commands.ts` 第 50、59 行；`packages/neuro-book/src/plugins/agent/web/session-host.ts` 第 1063–1103 行。
现象：
- 现在的确认是 `applyEvent` 里见到实时的 `input`/`steer` 就 `optimistic.slice(1)`。提案要改成按 `send` 交回的 `inputId`。但 `inputId` 只在两处出现：`send` 的响应，和 `commandAccepted`。`accept()` 把 `commandAccepted` 排在受理批最后（commands.ts 注释“排在批的最后”）；`input` 事件的 `queued` 字段有 inputId，却没有 `commandId`；`settleSend` 的注释写明 `input` 帧先于响应到达。
- 所以转录收到“留着的那条”的 `input` 时，既不知道哪条乐观消息对应哪个 inputId，也不知道这个 `input` 是不是新话的：响应没回来、批内 `commandAccepted` 还没到。按 inputId 确认只能“先攒着、等响应或批尾再对账”，期间旧话的气泡与新话的乐观气泡会同时出现、顺序不定；对账又依赖“只看实时到的”这条（重连重建时帧被跳过，`settleSend` 兜底移除）。
- 照字面实现的人会写成“拿响应里的 inputId 去匹配 `input.queued`”，而响应永远晚于帧，匹配永远落空，最后全靠 `settleSend` 的 `removeOptimistic` 兜底：气泡不是被确认，而是被删。
为什么是问题：这是第一轮 F2 的核心，第二稿只改了一句话，没给出能实现的键。留着的先跑时（保留原插话、按排队顺序两种方式）新话本来就不会产生 `input` 事件，只进排队区。
如何核实：读上面几处；`takeInputDrafts` 的 `input` 事件数据里有 `queued`，没有 `commandId`。
建议改法：二选一写进合同。一是 `inputQueued` 与 `input`/`steer` 带上受理它的 `commandId`，转录按 commandId 确认；二是乐观消息只靠 `commandAccepted`（同批的 `value.inputId`）：在 `commandAccepted` 到达时把乐观气泡换成“排队中”或删掉，`input` 事件不再触发任何乐观消息的移除。无论哪种，都要写合并方式下新话的 `input.queued` 就是 `send` 交回的 inputId。

### 2. 合并发送：宿主拼文字与内核受理之间的时间差，失败与重发的状态没写
严重程度：重要；类别：边界与并发。
位置：提案第四节第 4 小节表第一行；`session-host.ts` 第 1063–1103、1392–1397 行（`settleSend`、`message.resend`、`PendingSend`）。
现象：
- `replaces` 是宿主在发出那一刻读到的留着的 id 列表。内核受理在队列里排着，之间留着的可能变了：另一个窗口先放行了、周期任务刚排进一条用户的话之外的、父 Agent 取消了某条。提案没写 `replaces` 里有一个 id 已经不在时怎么办：整条 `send` 失败（`input-consumed`）、还是忽略不在的。整条失败的话，用户看到的是“发送被拒、文字放回输入框”，而放回的文字是宿主拼好的合并文字，不是用户打的那几个字。
- 现在被拒后 `setDraft(sent.input.text)`。合并时 `sent.input` 是合并后的文字：用户打了“改成英文”，被拒后输入框里是“旧话 1 旧话 2 改成英文”，而旧话 1、2 还留在排队区里；用户再点发送，宿主又拼一次，旧话出现两遍。要还原的应是用户自己打的那部分，`PendingSend` 要分开存“用户原文”与“合并后的输入与 replaces”。
- 结果未知（网络断）时“重发”用同一个 `commandId` 与同一份参数：`argsHash` 校验要求 `replaces` 与 `input` 都和第一次一模一样，所以 `PendingSend` 必须冻结 `replaces`，不能重新读队列。提案没写。重发时旧 id 若已经被第一次受理消耗，应得到 `replayed`；若第一次没受理而这些 id 在此期间被别人放行，重发会失败，界面却没有“你的话没丢，旧话已被放行”的说法。
如何核实：从代码推断；`command-id-conflict` 在 `commands.ts` 第 82–86 行。
建议改法：合同里写明 `replaces` 里的 id 不在时的结果（建议整条失败并带出哪几条已不在，宿主据此重拼一次）；`PendingSend` 分存两份；结果未知的重发冻结参数。

### 3. 运行中与“停止进行中”用户打的话走 `enqueue`，既不放行也不合并，和“用户发新话放行全部、留着的先跑”不一致
严重程度：重要；类别：合同矛盾，违反既有约定。
位置：提案第四节第 2、3 小节；`session-host.ts` 第 1099–1109 行；`nb-agent-ui/src/composer-actions.ts` 第 35–42 行。
现象：
- 界面里空闲时发话走 `send`，运行中（含停止进行中，`running` 仍为真）走 `enqueue`（`steer` 或 `followup`）。提案的放行只写了用户的 `send` 与 `resume`；`enqueue` 没有 `release`、`replaces`，也没说用户的 `enqueue` 算不算放行。
- 场景 A（停止进行中）：用户点停止，立刻打字回车。`abort` 要等模型请求与工具收尾，这段时间 `run.status` 不是 idle，回车走 `enqueue`。第 2 小节规定这条话在回到空闲时按第 1 小节留着，原因“停止”，“只有用户能放行”。用户刚发出的纠正话于是显示成“已暂停”，要再点一次继续；合并方式也不生效（这条话不是 `send`，不在合并里，留着的旧话和它各自按原样放行）。这正是提案想让“停止后打纠正话”合成一条的最常见路径，却落在时间窗外。
- 场景 B（系统开了运行）：周期任务在空闲时以自己的身份 `send`，只放行自己排的并开了运行；用户原先留着的话仍留着，会话在“运行中”。用户这时打字，走 `enqueue`，新话是就绪的，宿主的运行一结束新话先跑，用户留着的旧话仍留着、排在后面。顺序是“新话先于旧话”，与“留着的先跑”相反，且用户没有选恢复方式的机会。
- 空闲时竞态：界面以为空闲、发 `send`，内核已因别的发出者开了运行，`send` 在运行中只入队（`commands.ts` 第 83 行，缺省 `followup`），`commandAccepted` 的 `runId: null`。提案没说这时 `release`/`replaces` 是否仍生效。
为什么是问题：第 3 小节“输入框只有一个入口”说的只是空闲时。运行中输入框的入口是 `enqueue`，“放行全部留着的”在这里没有定义，两种用户最常见的操作（停止后立刻打字、系统任务在跑时打字）都撞上。
建议改法：二选一并写进第 3 小节：一是用户的 `enqueue` 也放行全部留着的（带与 `send` 一样的 `release`/`replaces`）；二是界面在 `stopRequestedAt` 非空时把回车改成“等会话空闲后以 `send` 发出”，运行中且有留着的话时在排队区头的“继续”旁给明确的选择，不让新话悄悄抢在旧话前面。

### 4. “已暂停 · 原因”的状态在客户端转录里没有来源：快照有、实时事件没有，客户端要把“回到空闲时留着”的规则再实现一遍
严重程度：重要；类别：隐含的耦合与共享状态。
位置：提案第四节第 1、6、7 小节；`nb-agent-ui/src/kernel-transcript.ts` 第 509–523、670–674 行。
现象：
- 转录自己用实时事件维护排队区：`inputQueued` 加一条、`inputRemoved`/`inputConsumed` 去一条，只存 `{id, mode, text}`；只有打开会话时才从快照的 `buffer` 整体读一次。提案把留着的状态定为“由日志推出”，且明确不写“转成留着”的事件（第 1 小节、第 8 小节“单独写转成留着的事件”被否决），第 6 小节只让快照与远程合同带 `state`。
- 结果：打开会话之后，运行收口（`runEnded`）的那一刻，内核知道缓冲区里的话全变成留着了，转录却只收到 `runEnded`，没有任何事件告诉它哪些条目变成留着、原因是什么。要画“已暂停 · 原因”，转录得自己按“回到空闲”的规则推：哪些收口算回到空闲（只压缩的运行、交出结果、文字收口、进程内中断、打开时的恢复——第 1 小节列了六种）、空闲时的 `inputQueued` 要看当时是否空闲、`inputReleased` 要把谁转回就绪、权限（用户停止留下的只有用户能放行）。这等于把内核的规则在 nb-agent-ui 再写一遍，且必须与内核同步演进，而 ADR 的新条写的是“取与放行只在内核”。
- 原因里的“谁停的”在哪个事件上也没写：`abort` 命令现在不收发出者（`commands.ts` 第 156–175 行），`runEnded` 的数据里也没有；第 5 小节只让 `runStarted` 与 `inputEdited` 记发出者。
- 快照与实时并存时，读到快照后再收到旧事件的去重只靠 `seq`，状态要两边一致更难验证。
如何核实：读上面两处；转录没有 import `nb-harness` 的 reducer（`package.json` 里 `nb-harness` 是依赖，但 `kernel-transcript.ts` 的 import 只有 nb-ui/text 与本包类型）。
建议改法：要么每次留着状态变化时发一个会话级事件（让转录无状态地读），要么 `runEnded` 的数据里带“这次回到空闲时缓冲区里留着的 id 与原因”，要么把推导函数放在 `nb-harness` 的公开入口、转录直接调用。同时写明停止者记在哪个事件上。

### 4 的更正
第 4 条“如何核实”里的依赖说法不准：`nb-harness` 在 `nb-agent-ui/package.json` 里是 devDependencies（只有测试用），运行时依赖只有 nb-ui。所以第 4 条建议改法的第三种（转录直接调用 nb-harness 的推导函数）要新增运行时依赖，与“核心纯 TS”的包边界冲突，优先考虑前两种（事件或 `runEnded` 带出留着的 id 与原因）。

### 5. “有留着的话”算进“等你处理”：很多留着的话该由父 Agent 或插件放行，不该叫用户；`activity` 的数据也装不下
严重程度：重要；类别：数据不足，别扭与反常。
位置：提案第四节第 7 小节第二条与第 3 小节“例外”；`docs/specs/agent/sessions.md` 输出 15、20；`docs/specs/agent/conversation.md` 输出 19、38、44；`session-list.ts` 第 77–114 行。
现象：
- 现在 `activity` 是 `{id, state: "running" | "waiting"}`，只列“打开着的句柄”里运行中或等用户的前台会话，`waiting` 只算停在审批、交给用户的提问、模式切换请求上（sessions.md 输出 19 明确说：停在交给派它的 Agent 的提问上算 `running`，不叫用户）。空闲且有留着的话的会话今天不在这张表里，所以光改文案不够：`activity` 要新增条目类别，或让空闲会话也进表。
- “等你处理”这个词的含义是“等用户动手”。留着的话里有大量不是用户要动手的：子代理交出结果后排着的话（第 3 小节：父 Agent 才放行）、父会话连带中止留下的（父 Agent 放行）、周期任务出错后留下的（日程插件放行自己的）。把它们都算进去，所有子会话行会亮“等你处理”的红点（输出 38、44 的 `childWaiting`、子代理入口红点），状态栏写“Agent：1 等你处理”，点击还要切到它——点进去用户什么也放行不了（用户虽然能放行任何一条，但这不是他在等的事）。与输出 19 刚确立的“子会话在交给 Agent 的提问上不叫用户”正好相反。
- 输出 20（在跑的工作：停止服务前警告“…在等你处理”）会不会也把留着的话算进去，提案没写：算了，则一个周期任务出错留下的话会挡住退出。
- 只看打开着的句柄：重启后没被打开的会话里留着的话，状态栏看不到；提案第 7 小节没说这是预期。
建议改法：条目要带原因类别，状态栏只把“用户能放行且只有用户能放行”（用户停止留下的、用户自己的话留着）的算进“等你处理”；其它的在会话行上标一个不抢注意力的“有暂停的话”。同时写明 `activity` 与 runningWork 对空闲会话的处理，以及未打开的会话不提示这件事。

### 6. 用户压缩压完自动放行：谁来做、怎样知道“是用户发起的”、放行范围与失败都没定，放在浏览器宿主里做不稳
严重程度：重要；类别：边界与并发，隐含假设。
位置：提案第四节第 3 小节“用户自己发起的压缩”、第 8 小节末条；`session-host.ts` 第 1177–1200 行（`compactCommand`）、第 806–808 行。
现象：
- “NeuroBook 自动 `resume`”没有说是浏览器里的 `session-host`、还是服务端的 agent 插件。`session-host` 只有一个 `current` 会话，`compactCommand` 在 `await remote.compact` 返回后若 `current !== target` 就直接返回；压缩常要几十秒，用户切到别的会话、关掉窗口、刷新，自动放行就丢了。两个窗口同开则两边都可能发 `resume`，第二次的结果（空放行）没写。放在浏览器里，“压完”也要靠订阅 `runEnded` 并记得“这次压缩是我发起的”，这条记忆刷新即丢。
- “是用户发起的”日志里没有记录：第 5 小节只让 `send`、`start`、`resume` 开的运行记发出者；`compact` 指令没列，运行中受理的“下一个边界压缩”（`scheduled: "next-boundary"`）根本不是单独的运行，没有“压完回到空闲”这一刻，压完时运行还在跑，放行什么？
- 放行范围：用户点压缩时留着的话里可能有早先“停止，排队的留着”留下的，那是用户明确选了“不要自己继续”的；`resume` 放行全部，压缩一结束这些话就自己发出去，开了一次用户没有要求的运行，还可能按合并方式把用户的几条话拼成一条发出。应只放行压缩期间新来的，还是全部，提案没说，字面读是全部。
- 失败：压缩出错、被中止（`runEnded` 不是 completed）时不放行，话留着、原因是压缩失败；界面怎么说，没写。放行时开不起来（只读、没有模型）按第 3 小节“话仍留着”，但这时用户没有在看，没有人会收到通知。
建议改法：由内核或服务端在压缩的运行收口那一刻做（`compact` 加一个选项，例如 `thenRelease: "arrived-during"`，内核在同一批写放行），客户端只传选项，不记忆；放行范围收窄到压缩期间到达的；失败时留着并在排队区写原因。

### 7. 合并所需的数据界面拿不到：排队条目只有 `text`，`resume({mode})` 也不可能由内核合并
严重程度：重要；类别：接口与合同不足，内部矛盾。
位置：提案第四节第 4 小节表与最后一条、第 6 小节；`kernel-transcript.ts` 第 31 行（`KernelQueued`）、第 509–514、670–674 行；`nb-harness/src/kernel/run/input.ts` 第 28–47、62–74 行；`kernel/api/basics.ts` 第 35–39 行。
现象：
- 宿主要把留着的几条合成一条，要读到每条的完整输入。内核里 `UserInput` 是 `{text, payload?, attachments?}`，缓冲区条目还可能带 `original` 或 `originalHash`。转录的 `KernelQueued` 只有 `{id, mode, text}`，附件、`payload` 都被丢掉；提案第 6 小节只给快照与远程合同的条目加 `by` 与 `state`，没说条目要带完整 `input`。照字面做，合并出来的新话没有留着的那几条的附件与 `payload`，而旧条目已经被 `inputRemoved{reason: "replaced"}` 删掉，附件就丢了。
- 缓冲区里的 `input` 是输入拦截链处理之后的（`interceptInput` 的 `final`），“原文”只在 `original` 里，开了 `redacted` 时连原文都没有、只剩哈希。第 4 小节说“拼法（……原文与脱敏）由宿主定”，宿主能拿到的只有已改写的文字；再把它交给 `send`，输入拦截链会对已经处理过的文字再跑一遍（提案写“输入拦截照常经过它”）。非幂等的拦截（加前缀、展开引用）会处理两次，脱敏的文字则把“已脱敏”的结果当作新原文记哈希。提案没有说这是接受的还是要避免。
- 内部矛盾：第 4 小节末条写“点继续、没有新话时，`resume({mode})` 同样三种；合并时只合并留着的几条”。但合并要宿主拼出新输入，`resume` 没有 `input` 参数，内核又被明确不拼；所以“合并”那一种只能是 `send({input: 拼好的, replaces})`，不是 `resume`。`resume` 的 `mode` 实际只有两个取值（`keep`、`followups`）。这与第 6 小节写的 `resume({mode?})` 形状、第 4 小节“同样三种”都对不上，实现者要么给 `resume` 加一个宿主不该有的“合并”，要么在界面里把“继续”分成两条路径。
建议改法：快照与远程合同的条目带完整 `input`（含 `payload`、`attachments`）与是否改写过；写明合并时用哪份文字（建议用缓冲区里已处理的，并声明拦截会再跑一遍，要求拦截幂等，或让 `replaces` 的新输入标明“已拦截过”）；把 `resume` 的模式写成两个，空输入框点继续时界面按设置在“`send` 合并”与“`resume` keep/followups”之间选。

### 8. 第一轮 F8 的处理表写“已改”，第二稿正文没有：界面“编辑”是 `remove` 加放进输入框，仍把宿主、父 Agent 的话洗成用户的话
严重程度：重要；类别：违反合同，核对“已改”条目。
位置：提案第四节第 5、7 小节；`session-host.ts` 第 1382–1390 行；处理表 F8。
现象：
- 处理表 F8 写“按 B15 的权限；编辑留着的话用 `send{replaces}`，发出者是用户”。第二稿里 `replaces` 只出现在第 4 小节的合并表和第 6 小节的指令形状里，没有任何地方写“编辑留着的话”；第 7 小节也没写哪些条目显示“编辑”。
- 界面现有的“编辑”不调 `edit`：`queued.edit` 是 `remove` 然后把原文放进输入框，改完再发。权限表允许用户 `remove` 任何一条，所以对宿主排的话（例如周期任务的提示）和父 Agent 排的话，用户点“编辑”后拿走原文、以用户身份发一遍：第 5 小节表里“`edit`：宿主排的除外”被绕过，发出者由 `host`/`session` 变成 `user`。bot 提案把“算不算用户的授权”单独管，这条路径正是把非用户的话变成用户的话，授权判断会被整个越过。
- 即使只对用户自己的话：留着的话被编辑成新话后，位置跑到队尾，而第 3 小节“留着的先跑”要求按原顺序；“`edit` 一条留着的话”会不会改变它的状态（留着还是就绪）也没写。
建议改法：规则统一写成“`by` 不是当前用户的条目只有取消，没有编辑”，第 7 小节写明；用户自己的条目的“编辑”保留“取出到输入框”的语义，并写明取出后它从缓冲区消失、重发是新话，不假装“原地编辑”。

### 9. “输入框只有一个入口”：界面合同只有一个布尔值和一个无参数的动作，中断与留着同时存在时的“继续”含义没定
严重程度：重要；类别：接口与合同不足，别扭与反常。
位置：提案第四节第 3 小节“继续与重试分开”、第 7 小节；`nb-agent-ui/src/types.ts` 第 407 行（`composer.resume?: boolean`）、第 622 行（`{type: "run.continue"}`）；`AgentConversationComposer.vue` 第 159–207 行；`kernel-transcript.ts` 第 440 行；`session-host.ts` 第 635–672、1367–1368 行；`runtime.md` 对 `paused`。
现象：
- 现在 `composer.resume` 是个布尔值，由 `interrupted()`（最近一次运行以 `interrupted` 结束、其后没有新一轮、用户停止不算）算出，占位文字是“上次运行已中断，按回车继续”，动作 `run.continue` 无参数，宿主一律 `start`。提案要求“有留着的话时是继续（`resume`），没有而上次中断时是接着跑（`start`）”，但没给界面合同：`resume` 要变成能区分“放行留着的”“接着跑”“两者都有”的值，`run.continue` 要带出选哪个，占位与按钮的文案各不同。用户“停止”后有留着的话，`interrupted()` 为假（用户停止不算），可是要显示“继续”：需要新的显示条件与新的占位文案。
- 中断加留着同时存在时，一个“继续”要做两件事：接着跑被中断的那一轮，再放行留着的。`resume` 的定义是“放行留着的并开运行”，没写它对被中断的那一轮怎么处理（内核里叶子上有暂停的运行时，`send` 是“入队后让它接着跑”）；开一条新轮把中断的那一轮扔在后面，模型看到的是半截历史。出错后留着的话与错误气泡的“重试”（`start`，只重跑失败那一轮）并存，输入框的“继续”（放行留着的）与气泡的“重试”是两个不同动作，提案只写“不顺带放行”，没写两者同时出现时界面怎样让用户分清。
- 单一入口漏了几条会开运行的路径：编辑重发走 `rewind{resend}`（`rewriteHistory`，不经 `start`、也不经 `send`）、异步提问的回答在空闲时开新一轮（`interaction.ts` 第 130–150 行）。这两条都是用户的新话，却不在第 3 小节“放行”的名单里，是否放行留着的没写；按字面它们不放行，用户编辑重发之后旧的留着的话仍然显示“已暂停”。
- 键盘：空着回车在有留着的话时就是继续，用的是设置里的恢复方式；空着时默认的“合并”，把用户的几条留着的话悄悄拼成一条再发，用户没有机会看到拼出来的是什么。Esc 在输入框里没有任何绑定，提案也没提，不构成冲突。
建议改法：写出 `composer` 的新形状（例如 `resume: null | "release" | "continue" | "both"` 加留着条数）与 `run.continue` 的参数；规定“两者都有”时先接着跑中断的那一轮再放行；把 `rewind{resend}` 与异步回答列入第 3 小节放行的名单（或明说不放行）；合并发送前至少在排队区把拼好的预览留给用户一次。

### 10. 合并之后，新话在排队区与对话里都看不见：先后与气泡位置没有定
严重程度：建议；类别：别扭与反常。
位置：提案第四节第 3、4 小节；`AgentQueuedMessages.vue` 第 21–24、36 行；`session-host.ts` 第 1099–1103 行。
现象：
- 合并时留着的话在前、新话在最后（第 5 节“新话在最后”）。排队区一行只显示 `firstLine(item.text)`。如果合并出来的那一条因为前面有宿主的话要先跑而在排队区等着，用户看到的那一行是合并文字的第一行，也就是旧话的第一行，自己刚打的话在最后，不展开就看不到；悬停提示才是全文。用户刚点发送，转眼“发送中”的气泡也被 `settleSend` 的 `removeOptimistic` 删了（受理成功就删），所以对话流里与排队区里都看不到自己刚打的那句。
- 宿主的话与合并的那一条的先后：宿主的消息“按原顺序在合并的那一条前面放行”，等于用户打了一句话、却先跑了若干个系统任务的轮，用户没有得到“你的话排在第几位”的提示。
- 不同恢复方式下新话出现的位置不同：合并（缺省）且前面没有宿主的话时，新话的 `input` 直接进路径；保留插话、按排队顺序时新话进排队区。界面没有统一的位置说法。
建议改法：排队区对“合并出来的”或“已被放行等着跑的”那一类，显示“第 N 位”与新话的首行；或者发送后在对话流里保留一条显示“已排队，前面还有 N 条”的气泡直到真正进入路径。

### 11. 停止的第二个选项：入口形态、清空范围与多窗口都没写
严重程度：建议；类别：边界与并发。
位置：提案第四节第 2 小节；`session-host.ts` 第 1360–1366 行；`AgentConversationComposer.vue` 第 163 行（`showStop`）、第 575–585 行（按钮）；`commands.ts` 第 156–175 行（`abortCommand`）。
现象：
- “输入框的停止按钮在缓冲区不空时多给一个”：现在按钮是一个图标按钮，点一下就是停止，没有菜单。第二个选项是分裂按钮、长按、还是点开菜单，会让缺省的“一点就停”多一步还是不变，没写；e2e 的定位点（`data-composer-action="stop"`）与键盘可达性也跟着变。“缓冲区不空”按什么算：含留着的？含宿主排的？
- 清空范围：`keepQueue: false` 清的是受理那一刻缓冲区的全部，含已经留着的（早先停止时用户选了“留着”、后来又在跑）与宿主、父 Agent 排的话；用户在“停止并清空”时看到的只是排队区里的几行，清掉宿主排的周期任务，宿主那边不知道自己排的话没了（`inputRemoved{reason: "aborted"}` 是不是通知排话的人，没写）。第 2 小节写的“只清停止受理之前排着的”在两个窗口时还有一个具体问题：窗口 B 的用户在 A 点“停止并清空”的受理前一瞬排了一条，B 的排队行无通知地消失。
- 停止进行中再点一次停止、或另一个窗口又点另一个选项：`abort` 按 `commandId` 重发返回同一结果，不同 `commandId` 的第二次在没有运行时 `aborted: false`、不写日志，但两次选项不同（一次留着、一次清空）时哪一个算数，没写；界面上第一次点了“留着”，第二次想改成“清空”会没有效果，也没有提示。
建议改法：写明按钮形态与缓冲区不空的算法（建议只数用户自己的就绪或留着的话，宿主的另算）；`inputRemoved{aborted}` 对被清掉的非用户条目要通知排话的人；停止进行中界面只提供“再点一次也不会改选项”的说明，或在进行中禁用第二个选项。

### 12. 恢复方式设置：只写了“放在 Agent 对话的设置里”，层、读取方与非网页调用方没定（第一轮 F9 只改了一半）
严重程度：建议；类别：接口与合同不足。
位置：提案第四节第 7 小节末条；`packages/neuro-book/src/plugins/agent/shared/settings.ts`；conversation.md 输出 45（用户层、全局一份、不分会话）。
现象：
- F9 的处理写“写进 `agent/conversation.md` 的设置，缺省‘合并一起发’”。第二稿只有一句“放在 Agent 对话的设置里，缺省合并”，没有分区、键名、层（输出 45 的状态栏设置是用户层、全局一份；恢复方式是否同样跟着人走、不分会话）、三个取值的内部名。
- 读取方是浏览器里的宿主：服务端发起的放行（日程插件、父 Agent 的 `agent_send`、用户压缩后的自动放行若放在服务端）与命令行拿不到这个设置，只会得到内核的缺省；`resume` 的 `mode` 不带时缺省是哪一种，提案没写。生效时点：宿主在点“继续”或发送那一刻读，对已经留着的话也生效；这一点没写，用户也看不到“现在点继续会合并还是分开发”。
- 对“停下来是想换个话题”的用户，缺省合并会把旧话拼在新话前面并先跑（第一轮 F9 已提过）；第二稿保留缺省，决定权在开发者，但应在第 7 小节写出这个代价。
建议改法：写出完整的设置声明（分区、键、层、取值）；写 `resume` 不带 `mode` 时的内核缺省；在排队区的“继续”旁用文字提示当前方式。
