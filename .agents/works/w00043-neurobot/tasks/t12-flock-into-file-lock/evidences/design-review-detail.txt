## 5. 新测试与发布验证的缺口：子进程收口、边界断言写法、`.` 入口与 `src/testing` 排除都没有被验证到

- 严重程度：建议（其中第 2、3 点偏重要）；类别：测试
- 位置：计划“`packages/nb-file-lock`”测试一条、“发布链”、“验证”
- 现象与建议：
  1. **子进程收口**：`docs/testing/README.md` 第 48 行要求测试起的子进程在用例失败时也收口（`afterEach` 里停止）。计划只写“另起子进程……杀掉子进程后能拿到”，没写失败收口。现有 `src/index.test.ts` 的 `child()` 也没有失败收口（子进程靠 stdin 关闭自停）。新测试要在 `afterEach`/`finally` 里 `kill("SIGKILL")` 并 `await exited`，并用 `waitUntil` 等“held”行，不用固定时长。可照 `packages/nb-harness/src/kernel/log/store.test.ts:454-470` 的 try/finally 写法。
  2. **子进程脚本只能导入 `../flock`**：计划说“同 `lock-child.ts` 的做法”。`lock-child.ts` 顶部 `import {holdLock, replaceLocked} from "../index"` 会加载 `proper-lockfile`；若把 flock 的模式加进它，就无法证明 `./flock` 单独可用。要另起一个 `src/testing/flock-child.ts`，只导入 `../flock`。
  3. **边界断言能写**：`typescript` 已在 nb-file-lock 的 devDependencies，可照 `packages/nb-harness/src/kernel/architecture.test.ts` 的 `importsOf` 用 TS 语法树读 `src/flock.ts` 的导入，或用 `Bun.Transpiler().scanImports`（发布清单检查 `scripts/release/packages.ts:300-309` 就这样做）。要求：静态、动态 `import()`、`require`、`export ... from` 都扫，说明符只能是 `bun:ffi` 与 `node:` 开头，相对导入也不行（否则 `import "./index"` 能绕过）。这条断言管得住 `flock.ts` 的源码，管不住“npm 用户仍会装上 proper-lockfile”，计划“风险”里已承认，这里不用再强调；但它也不检查 `exports["./flock"]` 真指向 `src/flock.ts`，可顺带加一句断言。
  4. **`.` 入口没有任何发布验证**：`release:smoke` 的 nbstory 段（`scripts/release/pack-smoke.ts:114-170`）只走 `serve` 的 `acquireServeLock`，即 `./flock`。nb-file-lock 的 `.`（README 要对外说明的入口）从 tarball 装出来能不能用（`/// <reference path>` 带类型声明、`proper-lockfile` 解析）没有人跑。建议在冒烟的空项目里加一步 `bun -e 'import {holdLock} from "@notnotype/nb-file-lock"; …'` 取放一次锁。
  5. **`src/testing/` 排除没有机检护栏**：我在 `/tmp/review-t12-design/scratch-detail/root/packages/nb-file-lock` 按计划的 `files`（`src`、`!src/testing`、`!src/**/*.test.ts`、`README.md`、`LICENSE`）跑了 `bun pm pack --dry-run`，只打进 6 个文件（`package.json`、`LICENSE`、`README.md`、`src/flock.ts`、`src/index.ts`、`src/types/proper-lockfile.d.ts`），排除是生效的，`bun scripts/release/packages.ts --root <scratch> --package nb-file-lock` 也通过。但 `pack-smoke.ts:32` 的 `FORBIDDEN` 没有 `testing/` 一项（因为 nb-harness 的 `./testing` 是公开入口），以后有人改 `files` 把 `src/testing` 带进去，冒烟不会报。可接受，也可以在 `entryTargets` 旁加“包里不含 exports 未指向的 `src/testing/`”。

## 7. `tryLock` 变成 npm 公开接口后，抛错通道与 POSIX 分支的两处老毛病要在注释里交代

- 严重程度：建议；类别：代码质量
- 位置：合并后的 `src/flock.ts`（现 `packages/nb-harness/src/kernel/log/flock.ts:20-23,50-57`）
- 现象：
  1. 接口注释只写“已被别的持有者拿着时返回 null”，实际 `openSync` 失败（ENOENT 目录不存在、EACCES）、平台不支持、Windows 打不开或锁不上都是**抛错**。调用方里 `qa/config.ts:225-229` 显式捕获并包成 `qa_config_write_failed`，`registry.ts` 与 `ingest/store.ts` 让它直接抛给上层，都依赖这个约定。现在要发到 npm 且 README 要写“两个入口各做什么”，应在 JSDoc 与 README 里写明“返回 null = 被占用；其它失败抛 Error”。
  2. POSIX 分支 `flock(...) !== 0` 一律当“被占用”，不看 errno（Windows 分支只把 `ERROR_LOCK_VIOLATION` 当被占用，其它抛错）。NFS 等不支持 flock 的文件系统上会表现成“永远被别人占着”。Bun 的 ffi 读不到 errno，改不了，只能在注释里写成已知限制。按“窄场景选简单改法”，写注释即可，不加机制。
  3. `tryLockPosix` 里先 `openSync` 再 `loadFlock()`：平台不支持（`loadFlock` 抛错）时 fd 泄漏。两份副本都有，合并时顺手把 `loadFlock()` 提到 `openSync` 之前即可，POSIX 路径之外无影响，不触发第 2 条的 Windows 复测。
- 如何核实：读代码；`loadFlock` 抛错的分支在 `process.platform` 非 linux/darwin/win32 时。

## 8. 版本与发布的衔接：不改版本号后，下次发布的行为在计划里没有交代

- 严重程度：建议；类别：文档
- 位置：计划“发布链与锁文件”最后一条、“不做与风险”
- 现象：我核实了计划的事实：`@notnotype/nb-harness` 在 registry 的 `latest` 是 0.1.1（time 2026-10-28），`./file-lock` 是 2026-11-11 提交 `c65f67311` 才加，确实从没发布；`@notnotype/nb-file-lock` 在 registry 返回 404，包名未被占用。但这意味着合并后 master 上 nb-harness 与 nb-story 的源码依赖 nb-file-lock，而版本号仍与 registry 上不依赖它的同号版本一样。`scripts/release/publish.ts:176-199` 的行为：已发布的同号版本跳过并提醒“源码改过但没提版本号，这次不发它们”，所以此时跑 `release:publish` 只会发 nb-file-lock 一个孤包，没有任何已发布的包依赖它。
- 建议改法：Task README 的“下一步”或 ADR 0052“后果”里写一句“下次发布必须同时提 nb-harness、nb-story 的版本号（并 `bun install` 刷新 `bun.lock`），否则 nb-file-lock 发出去也没人用”；这与“这次不改版本号”不矛盾。

## 未发现问题的方面（仔细检查后）

- **两份 flock 的差异**：逐行 `diff` 后，除三处报错文字与 `releaseOnce` 提取（见第 2 条）外只有注释不同；POSIX 的 `openSync(path, "a")`、`LOCK_EX|LOCK_NB`、失败时 `closeSync`，Windows 的常量、`>>> 0`、`OVERLAPPED_SIZE`、`ERROR_LOCK_VIOLATION` 处理、失败时 `CloseHandle`、`release` 幂等，两份相同。计划“只差三处报错文字与 releaseOnce”这句事实属实。
- **导入点**：代码、测试与子进程脚本里的导入方列全了（见第 6 条）；`@notnotype/nb-harness/file-lock` 的使用者仅 `install.ts:13` 与 `install.test.ts:99` 的内联脚本。该内联脚本在 `packages/neuro-book` 下 `bun -e` 解析，应用本来就直接依赖 `@notnotype/nb-file-lock`（`packages/neuro-book/package.json:38`），改完能解析。`.worktree/` 里旧分支的副本不算。
- **发布链**：按计划的字段我用 `bun scripts/release/packages.ts --root <scratch> --package nb-file-lock` 跑通（license、LICENSE 与根相同、README、`files` 含 LICENSE 与 README、`engines.bun`、`publishConfig.access`、`repository`、`internal_dependency`、`undeclared_import`：`flock.ts` 只有 `bun:` 与 `node:` 导入，`index.ts` 的 `proper-lockfile` 已声明、`lockfile_version`）；`bun.lock` 里 `packages/nb-file-lock` 有 `name`、`version` 记录，`staleLockfileVersions` 的正则能匹配；`publishOrder` 确是按 `dependencies` 与 `peerDependencies` 做深度优先排序，nb-file-lock 会排在 nb-harness、nb-story 之前，devDependencies 里的 `@notnotype/neuro-book-test-support` 被允许（同 nb-story 的做法）；`bun pm pack --dry-run` 排除 `src/testing` 与测试生效。当前仓库 `bun run release:check` 通过（9 个包）。
