## 2. 建议 / 代码质量：`tryLock` 新写的注释说“经 ffi 读不到 errno”，这不对

- 位置：`packages/nb-flock/src/index.ts:28`（“POSIX 上 `flock` 的任何失败都当作被占用：经 ffi 读不到 errno。”）
- 现象：这是这次新写的注释，把“读不到 errno”当成“任何失败都当作被占用”的原因。在 Linux 上实测，经 `bun:ffi` 调 `__errno_location` 再 `read.i32` 读得到 errno：`flock(-1, …)` 读到 9（EBADF），第二个句柄 `flock(LOCK_EX|LOCK_NB)` 读到 11（EWOULDBLOCK）。
- 为什么是问题：注释给了一个不成立的理由。以后的读者会以为没法区分“被占用”和“不支持 flock”，不会去考虑这个改进；而实际的理由是这次有意保持与 Windows 上实测过的代码逐行相同（计划里写的）。
- 如何核实：`bun /tmp/review-w00043-t12-impl/scratch/errno.ts` 输出 `{r1: -1, e1: 9, r2: -1, e2: 11}`。
- 建议改法：改成实话，例如“现在不读 errno（glibc 的 `__errno_location`、macOS 的 `__error`），`flock` 的任何失败都当作被占用；所以在不支持 flock 的文件系统上……”。要不要真去区分 EWOULDBLOCK 留到以后另做，这次不改代码。

## 3. 建议 / 测试：跨进程用例里读子进程第一行的调用放在 try 之外，子进程打第一行之前卡住时不会被收口

- 位置：`packages/nb-flock/src/index.test.ts:55`、`:74`（`const {child, first} = await holdInChild(path);` 在 `try` 之前），`:27-38`（`holdInChild` 内部 spawn 之后一直 `await reader.read()`）。
- 现象：`holdInChild` 先 spawn，再等第一行。子进程正常打出 `held`/`busy` 或退出时没问题：分块输出由 while 循环拼起来，提前退出时 `done` 跳出、断言失败、`finally` 收口，这些都对。但如果子进程起来后没打第一行就卡住（例如加载 ffi 时卡住），用例会在 bun test 的默认超时上失败，而 `child` 还没交给 `try`/`finally`，不会被 kill。`lock-child.ts` 靠“标准输入关闭就退出”兜底，可子进程卡在 `console.log` 之前时还没走到那段循环，这条兜底也不起作用。用例三的 `mine` 也在这条路径上不 release（进程退出时会放，影响小）。
- 为什么是问题：brief 要求子进程在失败时也收口。这个窗口窄，但写法本身可以不留这个窗口。
- 如何核实：读代码；或者在 scratch 副本的 `lock-child.ts` 开头加一个永不 resolve 的 await，跑测试后用 `ps` 看到残留的 `bun …/lock-child.ts`。
- 建议改法：把 spawn 和读第一行拆开，`const child = Bun.spawn(...)` 之后马上进 `try`，在 `try` 里读第一行。和参照的 `nb-harness/src/kernel/log/store.test.ts:457-471` 一样。

## 未发现问题的方面

- 逐行对照：`packages/nb-flock/src/index.ts` 和 base 上的 `nb-story/src/platform/flock.ts` 比，除了注释，只有三处报错文字不同（第 43、104、110 行），代码逐字相同，Windows 段（常量、`>>> 0`、kernel32 签名、`GetLastError` 的时机、`CloseHandle`）和实测版一致。新注释里的失败通道（null 只表示被占用；打不开文件、平台不支持、Win32 其它错误都抛错）和代码对得上（errno 那一句除外，见第 2 条）。
- 子进程继承：实测持锁进程用 `Bun.spawn` 和 `node:child_process` 起的子进程都没有继承锁文件的 fd（`/proc/<pid>/fd` 里没有），持锁进程被 kill -9 后锁立即能再拿到，“进程怎样结束都放锁”成立。
- 发布形状：`bun pm pack --dry-run` 只有 `package.json`、`LICENSE`、`README.md`、`src/index.ts`，测试和 `src/testing/` 都排除了；打出的 manifest 没有 `dependencies`，`exports` 只有 `.`；`bun scripts/release/packages.ts --package nb-flock` 通过。`pack-smoke.ts` 的 `FORBIDDEN`、`entryTargets`、`sources` 的 overrides 都按清单自动覆盖新包，不用另加登记。README 写的接口、例子和失败语义与代码一致。
- 导入点：worktree 里（不含旧应用和 `.agents` 历史记录）已经没有代码、测试、子进程脚本或注释指向 `platform/flock`、`kernel/log/flock`、`@notnotype/nb-harness/file-lock`。worktree 里 `docs/specs/agent/skills.md:176` 是旧副本，主工作区那份已经改了。
