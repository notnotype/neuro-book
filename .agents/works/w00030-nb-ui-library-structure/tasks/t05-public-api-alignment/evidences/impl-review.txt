[F6] 建议 | 正确性 | styles.css 里 `round()` 的“兜底”声明不起作用，注释的说法不成立
位置：packages/nb-ui/src/styles.css:385-389（.nb-ui-menu-label：`line-height: var(--leading-tight);` 后接 `line-height: round(down, calc(var(--text-xs) * var(--leading-tight)), 1px);`）
现象：注释说“上一条是不认 round() 的浏览器的兜底（design-language 坑 56）”。坑 56 的做法对字面量值成立（不认的值语法在解析时整条丢弃，前一条留下）。但第二条声明里含 var()：含 var() 的声明在解析时一律被接受，到计算值阶段才判定有效性；不认 round() 的浏览器会得到“计算值时无效”，属性按 unset 处理（line-height 是继承属性，取父级的值），前一条兜底声明已经被覆盖，不会回退。
为什么是问题：兜底在恰好需要它的浏览器里不生效，而注释和坑 56 的引用让读者以为有保障。round() 的基线（Chrome 125、Firefox 118、Safari 15.4）对现在的目标环境大概率不是问题，所以只是建议；但真有不认的宿主（旧 Electron、旧 Safari 之外的内嵌浏览器）时，分组标题的行高会掉成继承值而非 1.3。
如何核实：从 CSS Variables 规范推断（“invalid at computed-value time”），未在旧浏览器里实测。
建议改法：用 `@supports (line-height: round(down, 1px, 1px))` 包住第二条（@supports 对含 var() 的值也能在解析时判断 round() 的支持），或改注释不再说“兜底”。

[F10] 建议 | 副作用 | AlertDialog 改用 useOverlayLayer 后，trigger 插槽的内容也拿到“模态的局部浮层层级”
位置：packages/nb-ui/src/components/feedback/AlertDialog.vue:58-59；packages/nb-ui/src/composables/useOverlayLayer.ts:36-39
现象：provide 发生在 AlertDialog 的 setup 里，其后代包括 `trigger` 插槽（渲染在 AlertDialogRoot 内，AlertDialog.vue:85-87）。此前 AlertDialog 只 provide 了 NB_DIALOG_LAYER，现在多 provide 了 NB_POPOVER_Z_INDEX（9010）与 NB_DIALOG_WINDOW_DEPTH。触发器里若放有自带浮层的控件（Tooltip、Select），它们的浮层层级从页面级 60/70 变成 9010，盖过页面里的普通浮层。NB_DIALOG_LAYER 的同类问题此前就在（触发器里的 Dialog 会被判成二级），这次扩大了范围。
为什么是问题：层级随“挂在 AlertDialog 下”而非“在对话框里”决定；当前仓库内没有带 trigger 插槽的 AlertDialog 调用方（grep `<AlertDialog` 的结果都无 trigger），所以只是潜在问题，也没有在 AlertDialog.md 写明。
如何核实：读码；仓库内调用方 grep。
建议改法：AlertDialog.md 的 trigger 一句写明“触发器内容与对话框内容同在一棵注入树”，或把 provide 限定到 AlertDialogContent 的插槽里（需要一个小的内部提供者组件）。
[F11] 建议 | 对外影响 | aria-attributes.ts 的模块增强随 nb-ui 源码发给所有使用方，且依赖 nb-ui 没有声明的 `@vue/runtime-dom`
位置：packages/nb-ui/src/components/aria-attributes.ts:14-23；packages/nb-ui/src/components/index.ts:1-2；packages/nb-ui/package.json（peerDependencies 只有 vue，没有 @vue/runtime-dom）
现象：(a) `declare module "vue" { interface AllowedComponentProps extends AriaAttributes … }` 对使用方整个程序生效，不只是 nb-ui 组件：任何组件（含第三方）都接受 ARIA 与 role。对 nb-ui 自己合理，但这是对使用方类型环境的改动，migration-0.4.md 与 nb-ui README 都没提，只在 ui-development-spec.md:73 一句话。(b) `declare module "@vue/runtime-dom"` 要求这个模块能从 nb-ui 源码所在位置解析。nb-ui 作为 .ts 源码发布（package.json files: src），使用方的 TypeScript 会检查它；在严格解析的包管理器（pnpm 默认布局）下 `@vue/runtime-dom` 只是 vue 的依赖、不在 nb-ui 旁边，会得到 TS2664（增强的模块找不到）。本仓库用 bun 的提升布局，所以看不出。（从包管理器行为推断，未在 pnpm 下验证。）
为什么是问题：下一个 npm 版本（0.4.0）就带着它发出去；使用方升级后类型检查突然报错时，原因在一个“补 aria-description”的小项上。
建议改法：aria-description 这一项直接删掉（ARIA 1.3 的属性，Vue 3.5 的类型里仍无，需要的人可以用 data 或自己增强），或把它改成不依赖 @vue/runtime-dom 的写法（给 "vue" 的 AllowedComponentProps 直接加 `"aria-description"?: string`）；(a) 在 migration-0.4.md 的“宿主打开检查”那段写一句。
