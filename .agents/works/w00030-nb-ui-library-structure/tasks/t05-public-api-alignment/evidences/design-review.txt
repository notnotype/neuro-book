## 1. [阻断][回归] “遮罩在不在最上层”改读 useModalLayer 序号，会让“下拉开着时点遮罩”把对话框一起关掉；现有用例已锁定这条行为
- 位置：计划关键设计第 5 节末条；`packages/nb-ui/src/components/feedback/Dialog.vue:311-317`（`onTop`）、`Dialog.test.ts` 第二个用例“对话框里开着下拉时，点遮罩只关下拉，不关对话框”。
- 现象：`onTop()` 现在查的是“有没有层级更高的 reka 可关闭层”，其中包括 Select、DropdownMenu、Popover（它们都不在 `useModalLayer` 里，`useModalLayer` 只登记 Dialog/AlertDialog/Drawer 三个模态）。`useModalLayer` 的序号只能回答“我是不是最后打开的模态”，回答不了“我上面有没有一个非模态浮层”。
- 为什么是问题：读 reka 源码 `DismissableLayer/DismissableLayer.js:59`，pointer-down-outside 对所有非模态层都发（只有 Escape 才限最上层，`:74-75`）。所以遮罩上一次按下，下拉和对话框都会收到“外部按下”。现在靠 `onTop` 在遮罩 `pointerdown` 那一刻（早于 reka 在 document 上的处理，下拉还没关）判定“上面还有层”，把这次点击记为不算。改读模态序号后这一刻判定为“我是最上层模态”，松开时发 `request-close('overlay')`，点一下遮罩同时关下拉和对话框。表单对话框里最常见的就是 Select；`ProjectInfoDialog` 这类有脏表单守卫的最容易吃亏。
- 如何核实：在主工作区 `packages/nb-ui` 跑 `bunx vitest run src/components/feedback/Dialog.test.ts`，7 个全过，第二个用例断言 `request-close` 为 undefined；把 `onTop` 换成只比模态序号，该用例会失败。reka 行为见上面两处源码行。
- 建议改法：不要删这条判定，换一种不读 `[data-dismissable-layer]` 属性与 `getComputedStyle().zIndex` 的实现。可选：让 `usePopoverLayer` 的使用者（Select、DropdownMenu、Popover、SuggestionMenu、ColorSwatches）在打开时向最近的模态登记“我开着”，`onTop` = 模态序号最高且登记数为 0。如果坚持只用序号，计划要明确写“放弃这条行为”，同时改验收映射和 Dialog.test.ts，并给开发者决策。

## 2. [阻断][迁移风险] 计划只盘点了 `@confirm`，真正会坏的是 `@request-close`（12 处）和 `@cancel`；`closeOnRequest` 缺省 true 加 `defineModel` 会让带守卫的调用方静默失守
- 位置：计划第 5 节“去掉看监听器的分支”与“风险”第二条；`Dialog.vue:255-275`。
- 现象（数字，核实于 worktree）：`<Dialog` 用法共 26 处（nb-ui 之外 `llmlint/web` 用的是自己的 `common/Dialog.vue`，不算）。
  - 挂了 `@request-close` 且没有 `@update:model-value` 的：dev-panel 4（DeveloperMessageDialog.vue:31、ScreenConfirmDialog.vue:10、TakeoverDialog.vue:17、UncommittedDialog.vue:15）、neuro-book 的 EditorArea.vue:169、FilesExplorerView.vue:230/250/273、PathPickerDialog.vue:168、ProjectInfoDialog.vue:182、SettingsWindow.vue:261、AddProviderDialog.vue:84（另挂了 update），共 12 处。它们现在都靠“挂了监听就不自动关”，由宿主自己改 `open`。
  - 其中三处是“守卫式”：DeveloperMessageDialog 在 `replaced` 时 `@request-close="!replaced && emit('cancel')"` 故意不关；ProjectInfoDialog.vue:92-93 `if (reason === "overlay" && dirty.value) return`（脏表单点遮罩不关）；AddProviderDialog.vue 的 `reason === 'cancel' ? (custom = false) : emit('update:open', false)`。
  - `confirm` 的“没挂 @confirm 靠自动关”只剩 Lab 夹具：DialogFixture.vue:45（默认页脚，只有 v-model），DialogFixture.vue:24 走 `v-bind`；生产代码 0 处。计划的风险描述（“漏补关闭的调用方点确认没反应”“S3 开工时统计没挂 @confirm 的用法”）把力气花在了几乎为 0 的一类上。
- 为什么是问题：迁移后 `request-close` 照旧存在、类型检查和未知事件检查都不会报错，但行为变了：缺省 `closeOnRequest=true` 会随后发 `update:open(false)`。（1）守卫式调用方如果忘了加 `:close-on-request="false"`，守卫静默失效，脏表单一点遮罩就丢。（2）`defineModel` 的实际语义（我用 `useModel` 做了等价实验 model.test.ts）：宿主只传 `:open`、没挂 `@update:open` 时，子组件会本地更新。实验结果：请求关闭后子组件显示 false、宿主状态仍是 true；宿主再置 true 是空操作，必须先 false 再 true 才会重新打开。也就是说漏改的调用方得到的是“看着关了、宿主以为开着、再也打不开”的状态，不是报错。
- 如何核实：`python3 -I /tmp/review-w00030-t05-design/exp/tags.py <worktree> Dialog` 可重列 26 处属性；model.test.ts 的 EXP 输出。
- 建议改法：（a）计划把 S3 的盘点对象改成“所有 `@request-close`、`@cancel`、`@update:model-value` 的 Dialog 用法”并在计划里列出这 12 处各自怎么改（多数是加 `:close-on-request="false"`）；（b）重新权衡缺省值：`Dialog` 是由宿主 `open` 持有的受控浮层，缺省 `closeOnRequest=false` 同时保留 `defineModel` 的“宿主不挂就本地更新”会更安全；缺省 true 的好处只在“没写任何处理”的调用方，而这类调用方（26 处里）几乎没有。若仍取 true，建议 `closeOnRequest` 缺省 true 时在开发模式下，宿主既传了 `open` 又挂了 `request-close` 却没挂 `update:open` 就给一条诊断；（c）风险段改写成上面的真实数字。

## 3. [重要][回归] “关闭原因合并”和“`cancel` 只在取消按钮路径发”会破坏两个现有调用方
- 位置：计划第 5 节“关闭原因”对照（`cancel`、`close-button` 都→`button`）与“`cancel` 只在取消按钮路径发”；`AddProviderDialog.vue:~96`、`nb-story/src/web/parts/ModeNotice.vue:36-38`。
- 现象：
  - `AddProviderDialog` 用 `reason === 'cancel'`（页脚“返回”按钮，退回列表）与其它原因（× 、Esc、遮罩，关闭整个窗口）区分。计划把 `cancel` 和 `close-button` 都映射成 `button`，这个区分没了：“返回”和 × 同为 `button`，调用方没法判断是退一步还是关窗。
  - `ModeNotice`（nb-story）是整个仓库里唯一一个挂 `@cancel` 在 `Dialog` 上的生产调用方（其余 `@cancel` 都在 AlertDialog 或包装组件上），QaPage 靠它把 `pendingMode` 置回 null。现在自动关闭路径对 Esc、遮罩、×、取消按钮一律发 `cancel`（lib-review L12 第 2 点说的就是这个）。计划让 `cancel` 只在取消按钮路径发后，Esc、遮罩、× 关闭对话框但 QaPage 不知道，`pendingMode` 卡在非空。
- 为什么是问题：映射表是“对照”而不是迁移清单，没列这两处；`DialogCloseReason` 是公开类型（SDK `components.ts:27` 导出），改词表对外也算不兼容。
- 如何核实：`rg -n "reason ===|reason ==|@cancel" packages --glob '!node_modules'`；读 ModeNotice.vue 与 QaPage.vue:599。
- 建议改法：词表里把“用户点的是页脚取消/返回按钮”单独留一个原因（计划里的 `action` 被 ContextMenu 的 `select` 占了；可用 `cancel` 或把 Dialog 的取消按钮定为 `button`、× 定为 `close-button` 都保留），或者在计划里写明 AddProviderDialog 改成给“返回”按钮自己挂 `@click`（走 footer 插槽）。ModeNotice 需改成 `@update:open`。两处都写进 S3 迁移清单。

## 4. [重要][接口] 事件词汇没定义：`request-close`、`close(reason)`、`update:open`、`cancel`、`closed` 五个事件谁在什么时候发、哪个能被拦
- 位置：计划第 5 节“关闭原因”与“去掉看监听器的分支”两条。
- 现象：计划一处说“各浮层关闭前发 `close(reason)`，退场完成发 `closed`”，另一处说“`request-close` 总是发，`closeOnRequest` 缺省 true 时随即关闭”，验收行也在测“挂一个空的 `request-close` 监听”。读起来 Dialog 同时有 `request-close(reason)`、`close(reason)`、`update:open`、`cancel`。
  - 现有的 `close(reason)` 语义是“请求”而不是“通知”：QuickPick 的 `close` 紧跟在 `update:open(false)` 后发，QuickPick.md 写明“组件不自行改变受控 open”（`QuickPick.vue:138-143`）；ContextMenu 的 `close` 也是请求（宿主把 `visible` 置假，并且焦点去向由 reason 决定）。计划的“关闭前发”是通知语义。
  - `defineModel("open")` 加到 QuickPick 会改变它的受控合同：QuickPick.md 写的是“open 必填且受控”，宿主不接 `update:open` 就保持打开；`defineModel` 在宿主传了 `:open` 却没挂 `@update:open` 时会本地翻转（见发现 2 的实验）。
  - Drawer 的 reka 根（DrawerRoot）自己发 `update:open(value, {reason})`，reason 取值 `escape-key`、`outside-press`、`close-press`、`swipe`（`reka-ui/dist/Drawer/DrawerRoot.js:111-115`、`DrawerContentImpl.js:113,159-171`）。`swipe`（滑动关闭，`swipe-direction` 已在用）不在计划的 5 个原因里，Drawer 的表格行没有这一格。
  - AlertDialog 没有 `outside`（reka AlertDialogContent 把 pointer-down-outside 拦了，实验 overlay.test.ts：点外面 `update:open` 无事件，Escape 才发），`confirm` 路径 reka 的 AlertDialogAction 自己关；而 `Dialog.confirm` 计划里改成不自动关。同一个“确认”，两个浮层一个自动关一个不关，合同表里没说。
- 为什么是问题：S3 的人照字面实现，会为 Dialog 同时放 `request-close` 和 `close`，QuickPick 的 `close` 语义被悄悄改成通知；表驱动测试的“每个浮层×每种关闭方式”表有一半格子是“不适用”，而计划没列哪些格子适用。
- 如何核实：实验 overlay.test.ts：`bunx vitest run --config /tmp/review-w00030-t05-design/exp/vitest.config.mjs overlay`（在 packages/nb-ui 下），输出：AlertDialog 外部按下无 `update:open`、Esc 有；Drawer Esc 与外部按下各发一次；QuickPick 外部按下发 `close('outside')` 和 `update:open(false)`。
- 建议改法：在计划里写一张事件表：每个浮层的“请求关闭”事件（统一叫 `request-close(reason)` 还是沿用 `close`）、“已关闭”事件（`closed`）、`update:open`；明确哪些浮层的请求可以被宿主拒绝（Dialog、QuickPick、ContextMenu 可以；AlertDialog、Drawer 由 reka 直接关）。原因词表加 `swipe`（或归入 `button` 并写明），验收表列出适用格子。QuickPick 的 `open` 保持必填受控，不套 `defineModel`；`defineModel` 的“本地更新”只给确实支持非受控的浮层（带 trigger 的 AlertDialog、Drawer、Popover）。

## 5. [重要][设计] `ModalShell` 作为“拥有传送与遮罩的组件”装不下四个浮层：遮罩、Portal 必须和 reka 原语同族；四个浮层的差异计划没有列
- 位置：计划第 5 节“`ModalShell`”条；`Dialog.vue:339-361`、`AlertDialog.vue:95-106`、`Drawer.vue:78-87`、`QuickPick.vue:287-292`。
- 现象（读实现）：
  - 原语族不同：Dialog 与 QuickPick 用 `DialogRoot/Portal/Overlay/Content`；AlertDialog 用 `AlertDialog*`（内部转到 Dialog 的上下文，但 `AlertDialogContent` 加了 `role="alertdialog"`、拦外部按下、打开时把焦点放到取消按钮，`reka-ui/dist/AlertDialog/AlertDialogContent.js`）；Drawer 用另一族 `DrawerRoot/DrawerOverlay`，`DrawerOverlayImpl` 自带 body 滚动锁、`data-state`、`data-swiping` 与 swipe 变量（`dist/Drawer/DrawerOverlayImpl.js`）。遮罩必须是对应族的 `*Overlay`，否则 Presence 的退场、滚动锁与 swipe 联动丢失。所以 `ModalShell` 自己画遮罩，要么得 Dialog/AlertDialog/Drawer 各传一个“遮罩组件”，要么只能画个普通 div。
  - Dialog 的遮罩有三种分支：`pageModal` 用 reka 的 `DialogOverlay`（锁整页），`contained`（Lab 画布）用普通 div（不锁），`modal=false`（现在是窗口）没有遮罩；还有 `overlayType`（transparent/blur/opaque，缺省 opaque 且注释说明“遮罩先糊一遍会让玻璃面板没东西可采”）、`closeOnOverlay`、按下与松开同一个键才算一次点击。AlertDialog 与 Drawer 用 `backdrop-blur-[4px]`，QuickPick 是透明遮罩且 z-index 固定 `NB_Z_INDEX.commandPalette`（9200）。计划只写了“`.nb-ui-overlay`，`--overlay-bg`”一个外观，没说这些差异怎么表达。
  - 只有 Dialog 处理 `contained`（`useTeleportContained`）；AlertDialog、Drawer、QuickPick 在 Lab 里照旧锁整页。外壳统一后是顺手修好还是保持差异，计划没有说，e2e `lab-nb-ui.e2e.ts` 里“模态对话框在 Lab 画布里只遮住画布”只覆盖 Dialog。
  - `Drawer` 有 `modal=false`（Lab 场景“左侧、非模态”，feedback.ts:97），但仍画遮罩、仍进 `useModalLayer`。“ModalShell”里放一个非模态的 Drawer，名字和合同对不上。
  - lib-review L16 的建议里 `ModalShell` 有 `layer: "modal" | "palette" | "drawer"` 与 `overlay: "dim" | "none"` 两个参数；计划抄了摘要却把这两个参数丢了。
- 为什么是问题：S3 的人拿这一节开工，会先发现“套它”的前提不成立，再自行决定遮罩、Portal 谁画，结果是各浮层的外观与行为被无意改变（尤其 QuickPick 的层级和 AlertDialog 的取消焦点）。
- 如何核实：读上面的行号；`sed -n 1,60p node_modules/reka-ui/dist/AlertDialog/AlertDialogContent.js`；`DrawerOverlayImpl.js`。
- 建议改法：把可共享的部分拆成两层，并让计划写清边界。（1）一个 composable（暂名 `useModalSurface()`）：返回 `zIndex`（按 `layer` 取模态序列或固定档）、`teleportTo()`、`contained`、并做 `provide(NB_POPOVER_Z_INDEX)`、`useCloseHandoff` 与 `closed`。（2）真正的外壳组件只做 `.nb-ui-overlay` 的样式（`variant: "dim" | "blur" | "none"`）与关键帧，遮罩元素由各浮层用自己那一族的 `*Overlay` 以 `as-child` 或插槽套进来。计划里写一张“四个浮层各自保留什么”的表（根原语、遮罩元素、Escape 与外部点击由谁处理、初始焦点、contained 行为、层级来源）。

## 6. [重要][设计] 嵌套分档搬进 `ModalShell`/`FloatingWindow` 后，“在哪里 inject、在哪里 provide”是最容易错的一步，计划没写；Drawer、QuickPick 不该获得 nested 类
- 位置：计划第 5 节“`ModalShell`”条（“嵌套分档随层级提供一起搬进来”）、风险第三条；`Dialog.vue:142-149`、`AlertDialog.vue:34-35`、`theme/z-index.ts:41-49`。
- 现象：

- 建议改法：计划里写“`DialogSurface` 单根、`inheritAttrs` 透传、`defineExpose({panel, body})`，props 为 `size/width/height/maxHeight/title/showHeader/…` 的外观子集，不含任何关闭逻辑；窗口专属属性（拖动、缩放手柄、`data-dialog-drag`）由 `FloatingWindow` 通过插槽或 `variant` 传入”。

# 设计审查：API 形状、对外兼容与迁移可行性

## 问题

### 1. 阻断｜对外兼容｜内置主题的 `hostVersion` 没有纳入 0.4.0 迁移

### 2. 重要｜对外兼容｜共享包的 `nb-ui` 依赖会把 0.3.0 与 0.4.0 安装成两份，计划没有发布迁移

- **位置**：`packages/nb-form/package.json:25-27`、`packages/nb-agent-ui/package.json:27-29`、`packages/nb-markdown/package.json:33-35`、`packages/nb-story/package.json:42-49`；`packages/nb-ui/package.json:1-35`；计划 `plan.md:76-80、91-99`。
- **现象**：当前可发布共享包仍用 `"@notnotype/nb-ui": "workspace:^"`；当前 nb-ui 版本是 0.3.0。发布后该范围会成为以 0.3.0 为基准的 npm `^0.3.0` 范围，而 0.4.0 不满足 0.x 的 caret 范围。计划只迁移源码调用方、应用和 SDK，没有要求同步发布 nb-form、nb-agent-ui、nb-markdown（及构建 nb-story 所需的开发依赖）或更新它们的已发布依赖元数据。
- **为什么是问题**：消费者安装新应用/新 nb-ui 与现有 npm 共享包组合时，包管理器会为旧共享包保留或嵌套安装 `@notnotype/nb-ui@0.3.x`。同一页面可能同时存在 0.3 与 0.4 的组件、类型、Vue 组件实例和 token 合同，迁移表声称“一次对齐”却没有覆盖这个公开组合；若旧共享包源码继续被构建，还会继续编译旧属性名。
- **如何核实**：读取上述 package.json 可见发布包的依赖协议与版本；以 `bun pm pack`/npm 安装一个未升级的共享包和 `@notnotype/nb-ui@0.4.0`，检查依赖树即可复现范围不满足与嵌套副本。当前工作区 `bun pm ls @notnotype/nb-ui --all` 只显示 workspace 副本，不能证明 npm 发布组合已被迁移。
- **建议改法**：在迁移表中列出所有已发布共享包的版本发布顺序、`@notnotype/nb-ui` 目标范围和安装树验收；至少发布依赖 0.4.0 的新版本后再发布 nb-ui 0.4.0，或明确这些包不随本次兼容承诺并阻止它们与 0.4.0 混装。对 `nb-story` 还要核对 `prepack` 生成的 web 产物是否已经用新 API，而不能只看它的 `devDependencies`。

### 3. 重要｜关闭原因兼容｜`cancel` 与 `close-button` 合并会改变现有调用方的业务分支

- **位置**：计划 `plan.md:61-68`；`packages/neuro-book/src/plugins/models/web/components/AddProviderDialog.vue:98`；`packages/neuro-book/src/plugins/projects/web/components/ProjectInfoDialog.vue:92-94`；`packages/nb-ui/src/components/feedback/Dialog.vue:27`、`packages/nb-ui/src/components/feedback/Dialog.md:23、70、134-135`。

- **建议改法**：先决定合同是否真的允许丢失区分。若允许，迁移 `AddProviderDialog` 为显式业务动作或另一个事件并加入行为验收；若不允许，保留 `cancel`/`button` 的可区分编码，或把“取消按钮”继续作为独立的 `cancel` 事件而不是并入 `close(reason)`，同时更新 `OverlayCloseReason` 的定义和所有调用方。

### 5. 重要｜词表合同｜`Tone` 与现有 `default`/`error` 取值不闭合，计划没有给出逐组件映射

- **位置**：计划 `plan.md:40-46、53-59`；`packages/nb-ui/src/components/controls/SegmentedControl.vue:21、39、53`；`packages/nb-ui/src/components/popup/context-menu.types.ts:18`；`packages/nb-ui/src/components/popup/dropdown-menu.types.ts:18`；`packages/nb-ui/src/components/popup/Menubar.vue:22、25`；`packages/nb-ui/src/components/feedback/Banner.vue:7`；`packages/nb-ui/src/components/feedback/Notification.vue:6`。
- **现象**：计划定义 `Tone = "neutral" | "accent" | "info" | "success" | "warning" | "danger"`，但现有 SegmentedControl 的 `SegmentedControlTone` 仍含 `"default"`，三个菜单项类型的 `tone` 仍含 `"default"`，菜单栏的 `type` 还含 `"default"`；Banner/Notification 的公开类型仍含 `"error"`。计划只明确了 Notification/Banner 的 `error → danger`，只明确了 AlertDialog 的另一档叫 `neutral`，没有说明菜单的 `default → neutral`、SegmentedControl 的 `default → neutral`，也没有说明菜单 `type: "default" → "item"` 的所有类型、文档和调用方边界。
- **为什么是问题**：这些值不是 `ControlSize` 那种组件特有子集，而是直接落在计划声称的共享词表之外。照计划把类型改成 `Tone` 会先让现有组件定义和 `MenuNodes` 的泛型约束不再成立；保留 `default` 又会留下第二套公开词表。应用内 `EditorGroup` 还把 `BannerTone` 和 `"error"` 业务值直接传给 `<Banner>`，仅改 nb-ui 类型名不能完成迁移。
- **如何核实**：上述文件中的类型声明与默认值可直接读到；`packages/neuro-book/src/plugins/editor/web/components/EditorGroup.vue:157、171-186、302` 明确把 `"error"` 存进 `BannerTone` 并传入 Banner。`packages/neuro-book/src/plugins/explorer/web/components/FilesExplorerView.vue:107` 也明确生成菜单 `tone: "default" | "danger"`。
- **建议改法**：为每个共享词表列出“公共值、组件子集、旧值映射、业务域值是否另保留”的表；至少明确菜单与 SegmentedControl 的 `default` 是否统一为 `neutral`、菜单 `type` 是否统一为 `item`，并把 `EditorGroup` 等边界适配列入迁移表和 typecheck 验收。不要用全仓无差别替换 `error`，因为 `Collapsible*` 状态和 nb-form 问题严重度是不同域。

### 6. 重要｜列表数据形状｜`ListItemBase` 的必填 `id` 与现有 ContextMenu/Select/Menubar 形状不兼容

- **位置**：计划 `plan.md:53-59`；`packages/nb-ui/src/components/popup/context-menu.types.ts:5-13`；`packages/nb-ui/src/components/popup/dropdown-menu.types.ts:7-25`；`packages/nb-ui/src/components/popup/Menubar.vue:14-34`；`packages/nb-ui/src/components/popup/Select.vue:32-42`；`packages/nb-ui/src/components/form/SearchSelect.vue:18-25`。
- **现象**：计划把共同字段写成 `{id, label, hint?, description?, icon?, tone?, disabled?}`，并说菜单 `value → id`、`shortcut → hint`。但 ContextMenu 项没有 `value/id`，依赖 `action` 回调；DropdownMenu、Menubar、Select、SearchSelect 仍用 `value`；QuickPick/SuggestionMenu 才已有 `id`。计划没有说明 ContextMenu 是新增稳定 id、把 id 设为可选、还是根本不纳入 `ListItemBase`，也没有说明 Select/SearchSelect 的 `value` 是否只是业务值而不应改名。
- **为什么是问题**：若 `ListItemBase.id` 真是必填，共享类型不能直接承载现有 ContextMenu 项；若为可选，`MenuRow`/键盘高亮/分隔项 key 的稳定身份合同就没有统一。若把 Select 的 `value` 机械改成 `id`，会把“提交给 `update:modelValue` 的值”与“列表渲染身份”混为一谈，影响 nb-form 当前用 `optionKey` 做序号/原值映射的边界。
- **如何核实**：现有类型声明分别显示上述字段；`SearchSelect.vue:100-103` 把业务 `option.value` 映射成 SuggestionMenu 的 `id`，说明这两个概念当前已经有意区分。`ContextMenu.vue:30-32` 选择时只发 `close("select")`，动作执行在 `ContextMenuPanel`，没有可供统一 id 迁移的现有字段。
- **建议改法**：先把“渲染身份”和“提交值”拆成两个命名明确的字段合同：例如基础项只要求 `label` 等视觉字段，只有需要键盘/回溯的列表声明 `id`；Select/SearchSelect 保留 `value` 并在内部生成/承载 id；ContextMenu 明确 action 项的身份与 key 策略。迁移表逐组件写出是否继承 `ListItemBase`，不要用一个强制接口覆盖六种语义。

### 7. 重要｜SDK 公开面｜新增共享类型不会自动进入插件 SDK，`components.ts` 是手写白名单

- **位置**：`packages/neuro-book/src/sdk/components.ts:6-8、23-37`；`packages/neuro-book/src/sdk/sdk.test.ts:46-53、69-74`；`packages/neuro-book/plugin-sdk/pack.ts:65-78、171-180、314-319`；计划 `plan.md:40-46、76-80`。
- **现象**：nb-ui 的 `components/index.ts` 是显式导出，插件 SDK 另有一份显式的 `src/sdk/components.ts` 值/类型白名单。`pack.ts` 的类型路径只把 `@notnotype/nb-ui/components` 映射到源码，并不会把新文件的类型自动加到 SDK 入口。计划要新增并从 `./components` 导出的 `ControlSize`、`Tone`、`OverlayCloseReason`、`ListItemBase`（以及计划中的 Orientation/Side/Align）不在 SDK 类型白名单中；`sdk.test.ts` 的组件对照只检查值导出，`pack.test.ts` 只核对生成声明与这份手写名单一致，因此两者都可能在“SDK 少导出一个公共类型”时通过。
- **为什么是问题**：应用内 `@notnotype/nb-ui/components` 类型通过，不等于第三方插件的 `@notnotype/nb-plugin-sdk/components` 类型可用。插件作者拿不到新关闭原因和列表项类型，或者生成的 `components.d.ts` 只把类型作为内部展开内容而不能按名导入，公开 API 会在两个入口分叉；这违反 `src/sdk/components.ts` 文件头写的“每一项都是兼容承诺”。
- **如何核实**：当前 `components.ts:23-37` 没有任何共享词表名；`sdk.test.ts:46-53` 的 `exportedValues` 明确过滤 `type`，所以它不会检查类型白名单；`pack.ts:171-180` 的组件清单也只读非 type 的具名导出。
- **建议改法**：把所有计划公开的共享类型逐一加入 `src/sdk/components.ts`，并给 `sdk.test.ts` 增加“nb-ui components 的公共类型清单与 SDK 类型清单”的断言；`pack.test.ts` 增加从生成 `components.d.ts` 按名导入/使用 `OverlayCloseReason`、`ListItemBase` 的外部插件 typecheck。若 `FloatingWindow` 是给插件用的公开组件，也必须同时加入值白名单；若不是，计划应明确它是内部组件并从 SDK 对照中排除。

### 8. 重要｜未知属性/事件检查｜S0 不能兜住动态 `v-bind` 与动态组件，计划把局部静态检查当成全迁移证明

- **位置**：计划 `plan.md:36-38、104-110`；`packages/neuro-book/src/plugins/lab/web/fixtures/nb-ui/ContextMenuFixture.vue:22`；`packages/nb-form/src/vue/NodeField.vue:265-275`；`packages/nb-ui/src/components/feedback/Dialog.vue:23-24、369-371`；`packages/nb-ui/src/components/form/SearchSelect.vue:68-73`。
- **现象**：当前各 Vue 配置没有 `checkUnknownProps`/`checkUnknownEvents`；工作区同时解析到 `vue-tsc@3.3.7` 与 nb-ui 自己的 `vue-tsc@2.2.12`，两者都支持这些开关，但开关只对模板中能静态识别的组件属性/事件有意义。`ContextMenuFixture` 用 `v-bind="subject.bindings.value"`；`NodeField` 用 `<component :is="control">` 加 `v-bind="controlProps"`，这些对象键不会被静态组件 prop/event 签名逐项检查。Dialog、SearchSelect 等又关闭自动 attrs 继承并手动把 `$attrs` 转到内部节点，旧名字落入 attrs 的运行时路径仍然存在。
- **为什么是问题**：S0 的“故意写错一个属性报错”只能证明一个静态模板点。旧 `visible`/`placement`/事件名若藏在 Lab binding、动态组件 props、包装组件的 attrs 对象里，typecheck 可以通过而运行时继续静默丢失。反过来，计划没有列出哪些 `data-*`、ARIA、class/style 和包装事件是有意透传，无法据此区分开关带来的真实错误与预期 attrs。
- **如何核实**：已核对工作区依赖：`bun pm ls vue-tsc --all` 输出 `vue-tsc@3.3.7` 与 `vue-tsc@2.2.12`；静态检查开关的可用版本不构成动态绑定检查。读取上述三个模板可见动态 `v-bind` 与手动 `$attrs` 透传入口。对 fixture binding 或 `controlProps` 的旧键做故意改名，静态 prop 检查没有一个具体组件声明可供它比较。
- **建议改法**：S0 把开关可用性、现有误报清单、动态绑定清单分开验收；为 `v-bind` 对象建立显式类型/映射并迁移键名，必要时在动态组件边界按 widget 分支渲染已知组件；对 attrs 透传组件列明允许的原生/ARIA/data 属性和事件转发合同。把“全仓旧属性/旧事件零命中 + 动态对象键审查”作为迁移门禁，不能只依赖 `checkUnknownProps`/`checkUnknownEvents`。
