## 决定 D-PRODUCT-01：第一版首先服务哪类宿主？

问题：第一版的首要宿主是哪一类？（不是“所有人都服务”。）

### 候选

| 候选 | 内容 | 主要支持证据 | 主要风险 |
| --- | --- | --- | --- |
| C1 | CLI coding agent（001 候选宿主 A） | 单进程、终端可端到端观察；001 H1 的五类失败成本都可在本地构造；不依赖后端基础设施 | 若真实第一消费者是产品型宿主，Session 恢复事实可能先按 CLI 惯例成形 |
| C2 | 嵌入式后端服务（候选宿主 B） | 与“库嵌入服务”常见形态一致；S-OPENAI-SESSIONS、S-LANGGRAPH-PERSISTENCE、S-TEMPORAL-WORKFLOWS 证据集中 | 需要宿主级 Job/Lease/Outbox/交付与租户；本机无法端到端验证；失败成本最高 |
| C3 | 需要持久 Session 的产品宿主（候选宿主 C） | 与“可恢复 Session”首版重点直接对齐；S-OPENAI-RESULTS、S-OPENAI-SESSIONS、S-LANGGRAPH-PERSISTENCE 证据集中 | 需要真实产品或等价测试产品才能验证；产品投影语义有倒灌 Core 的风险 |
| C4 | C1 为首要宿主 + C3 为契约压力测试（同一 Core，两个宿主形态的最小对照） | 直接服务“多宿主/通用”目标；001 横表三个画像的共同失败成本可同时受约束 | 首版成本更高；“第二宿主对照”可能被推迟成形式 |
| C5 | `evidence-insufficient` | 本次观察为声明式无补充；真实旅程证据缺失 | 阻塞全部下游；需要开发者补充真实旅程或明确授权“以现有材料为准” |

### 建议

**C1（首要宿主 = CLI coding agent）**，理由：

1. 可验证性最高：001 H1 的“可观察结果素材”全部可在单进程 + 终端中复现（状态可区分、工具边界、结果面、恢复），不需要生产环境。
2. 失败成本可控且可测量：误修改 / 上下文丢失 / 结果不可判断都能在本地构造并观察，符合本 Task“成功标准必须是宿主可观察或可测量结果”的完成门禁。
3. 不预设宿主基础设施：不要求先造 Job、交付通道或租户系统，就能得到 run kernel + 可恢复 Session 的完整端到端证据。
4. `[推论]` Core 需求是三者共同子集：turn/tool/approval 生命周期与 Invocation/Session 恢复边界在 001 的三个画像中都出现（见 001 横表）。

若采纳 C1，建议在 003 中同时把 C2/C3 的以下失败成本明确写入“首版不服务”：请求与运行脱钩、外部副作用重复、租户边界错误、交付与事实分离、历史丢失或错序、错误归属、审批无法继续、展示与真相不一致。

### 选错代价

- 选 C1、但真实第一消费者是 H3 型产品：Session 恢复事实可能按单进程 CLI 语义（continue/resume 惯例）先成形；产品宿主接入时需补 durable facts、多入口 admission、用户隔离语义，Session/Store 合同返工。
- 选 C3、但当下没有真实产品宿主：验证只能靠自造测试产品，容易把产品投影细节（消息、UI 状态）写进 Core，通用性受损，且首版行为证据弱。
- 选 C2：验证成本最高（worker/交付/租户环境当前均未授权、不可运行），最可能得到“设计完成但行为未验证”的结果。

### 可逆性

- 运行内核（turn/tool/approval/结果面）与宿主选择耦合低，返工成本中等偏低。
- Session/Store 合同一旦按某宿主语义成形，更换首要宿主会同时波及两者，返工成本中等偏高。
- 本决定可通过 003 的重开条件调整；重开越晚，返工面越大。

### 证据缺口

- 无开发者真实旅程观察（本次为声明式无补充）。
- 没有“同一 Core 支撑两个不同宿主”的对照实验数据。
- 没有 H2/H3 的并发、多入口、跨进程实验数据。
- 缺少真实第一消费者承诺：llmlint 正在退出（见 Work 路线图 llmlint consumer exit 阶段）；NeuroBook 接入由 #117 另管，不在本轮范围。

## 决定 D-PRODUCT-02：第一版怎样才算成功？

问题：宿主观察到什么结果，才算第一版成功？（必须是宿主可观察或可测量的结果，不是内部实现清单。）

### 候选成功标准

| 候选 | 内容 | 来源 |
| --- | --- | --- |
| S1 | 状态可判定：一次任务能明确区分运行中 / 等待审批 / 成功 / 失败 / 取消 / 未完成 | 001 H1 结果 1、H2 结果 1、H3 结果 3 |
| S2 | 恢复不重复副作用：进程中断后能继续同一任务；已发生的外部副作用不被静默重复；未知结果显式暴露 | 001 H1 结果 4、H2 结果 3、H3 结果 3 |
| S3 | 工具边界与可追溯：工具只在宿主允许的边界内执行，每次调用可追溯到对应调用与结果 | 001 H1 结果 2 |
| S4 | 结果面完整：终端/脚本结果同时保留最终答案与判断成功所需的错误、退出码、流结束状态 | 001 H1 结果 3、S-CLAUDE-HEADLESS |
| S5 | 第二宿主最小对照：同一 Core 在第二个宿主形态（H3 或 H2 的最小切片）上完成一次最小对照运行 | 001 横表；Issue #193“通用/多宿主”目标 |
| S6 | `evidence-insufficient` | — |

### 建议

**S1 + S2 + S3 + S4 全部在真实宿主（C1 场景）端到端可复现；S5 作为首版收口前最后一步的最小对照。**

理由：

- S1–S4 直接对应三个画像中共同出现、且失败成本最高的观察面（001 横表），且全部可在本地复现。
- S5 是“通用/多宿主”主张的最小反证：没有第二宿主，任何“通用”结论都只是单宿主声明。建议把“最小”写死：一次运行、无并发、无多租户、无交付协议。
- S6 保留给“开发者判定现有证据不足以定标准”的情形；选择它需要写明缺口与所需材料。

### 选错代价

- 标准过弱（例如“跑通一次文本任务”）：第一版通过但不能支撑后续 Session/Store/API 决策，后续 Task 会反复重开未决行为。
- 标准过强（例如“跨进程 exactly-once 业务副作用”）：把宿主职责（Job/幂等/交付）写成 Core 承诺，超出 001 中 Harness 候选职责范围。
- 要求 S5 但未限制“最小”：会显著推迟首版收口。

### 可逆性

- D-PRODUCT-02 是验收口径；口径变化改变后续 Spec 的验收条件，但不直接删除已有能力，可逆性中等。
- 一旦把 S5 写入成功标准，任何“单宿主跑通”都不能宣布完成——这是有意约束，需要开发者明确接受。

### 证据缺口

- 与 D-PRODUCT-01 相同：无真实旅程观察、无第二宿主实验、无并发/多入口数据。
- 缺失败成本的量化材料（频率、损失），001 只提供素材分类；量化需要真实宿主数据。

## 两个决定的组合影响（供 003 记录）

若选择 C1 + S1–S4（+S5），下一阶段（首版场景）的输入为：

- 首要宿主边界：单进程 CLI 任务旅程；工作目录、权限、进程信号与终端结果归宿主；Harness 候选职责见 001 H1 段。
- 首版明确不服务：H2 的跨进程 Job/交付/租户与 H3 的产品投影/账户/隐私/同步（全部归宿主）。
- 成功标准：S1–S4 宿主可观察结果 + S5 最小第二宿主对照。
- 需要重开的条件：出现与 C1 不一致的真实第一消费者；S5 被判定不可行；开发者补充的旅程观察与本简报假设冲突；001/manifest 被修订。
