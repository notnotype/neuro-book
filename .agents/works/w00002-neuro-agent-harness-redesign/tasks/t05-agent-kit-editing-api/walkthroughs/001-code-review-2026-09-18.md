## 集成 owner findings（含修复）

### Required 1（已修复）：锚定 hunk 的匹配窗口与合同/上游不符

- 现象：`@@ beta` + `-gamma` + `+GAMMA`（锚行是 body 之前的一行，codex/OMP 的常规写法）实际返回 `no_match`。
- 原因：实现要求「匹配区间**包含**锚行」，而合同（`editing.md`）与上游 `patch.rs` 的语义是「匹配起点位于锚行或其后」（上游 `line_index = found | found+1`）。
- 证据：公开 API 复现输出 `A 锚为前导行(不在 body) => ERR no_match`。
- 修复：候选匹配起点改为 `>= anchorIndex`；锚本身的唯一性检查保留（上游同样要求锚唯一）。修复后 `=> OK "a\nbeta\nGAMMA\ndelta\n"`。

### Required 2（已修复）：相邻 hunk 共享 context 被误拒

- 现象：`@@\n a\n-beta\n+BETA\n gamma` 之后接 `@@\n gamma\n-delta\n+DELTA`（第二个 hunk 的 leading context 是第一个的 trailing context）返回 `no_match`。
- 原因：搜索窗口推进到上一个 hunk **整个匹配区间**之后，而合同只要求「变化段不得重叠」，并明确允许共享只读 context。
- 证据：复现输出 `C 相邻 hunk 共享 context => ERR no_match`。
- 修复：搜索窗口推进到上一个 hunk 的**变化段末尾**（新坐标 `start + newLines.length - trailingContext`）。修复后 `=> OK "a\nBETA\ngamma\nDELTA\n"`。
- 同步：`editing.md` 的「共用 hunk 匹配」段改写为可执行的窗口规则，并新增验收项 4b。

### Required 3（已修复）：hashline 同 uri 多段被一律拒绝

- 现象：同一 `[PATH#TAG]` 出现两次时直接 `invalid_input`，而计划要求「按段序虚拟执行，用旧 tag 操作已改变原文才失败」。
- 证据：复现输出 `11 两段同旧 tag => ERR invalid_input | 同一 reference 只能有一个 hashline section，请合并。`
- 修复：`inspectSections` 允许同 tag 的重复段（tag 不一致仍是 `invalid_input`）；planner 在每段开始时校验「当前虚拟文本 == 绑定原文」，否则 `stale_snapshot`。修复后 `=> stale_snapshot ...（前序 section 已修改），请合并为一个 section`。
- 同步：`editing.md` 说明该规则；`hashline.test.ts` 增加同 tag 重复段（`stale_snapshot`）、tag 不一致（`invalid_input`）、首段无净变化后可继续（成功）三种断言。
