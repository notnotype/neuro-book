## 发现 1：expiresAt 为过去、0、NaN 时形成请求死循环（重要 / 正确性 / 安全与性能）

- 位置：`packages/neuro-book/src/plugins/workbench/web/scene-providers.ts:178-184`（`#schedule`），`:167` 调用处。
- 现象：`delay = Math.max(0, expiresAt - now)`。`expiresAt` 已过期（例如作者把秒级时间戳 `Date.now()/1000+3600` 当毫秒交上来）、为 0、或为 NaN（`Math.max(0, NaN)` 与 `Math.min(NaN, …)` 都是 NaN，`setTimeout(NaN)` 按 0 处理，且 `delay > MAX_TIMER_MS` 对 NaN 为假）时，每次完成后立刻 `setTimeout(…, 0)` 重新 `#run`：请求提供者、建对象 URL、解码、替换 `#results`，而 `#results` 一变 `WorkbenchDocument` 的 `watchEffect` 就整套重算并 `apply`（重写全部皮肤变量和图标样式表）。没有最小间隔，也没有对 `expiresAt` 类型和有限性的校验。
- 为什么是问题：提供者是第三方插件代码，单位写错（秒/毫秒）是最常见的失误；后果是主线程被占满、界面卡死，而不是“用后备图 + 一条诊断”。计划“不防写死循环的提供者”针对的是提供者自己的死循环，这条是宿主把一个返回值当作可信定时输入。
- 如何核实：在 `/tmp/review-w00041-t06-impl/exp.test.ts` 里用 `SceneProviders` 发布一个返回 `{image, expiresAt}` 的提供者，`expiresAt` 分别取 `NaN`、`0`、`Date.now()-1000`，各等 300 毫秒：请求次数 245、258、261。（Chromium 对嵌套定时器有 4 毫秒下限，仍是每秒约 250 次。）
- 建议改法：`expiresAt` 不是有限数就当“没有”并记一条诊断；对有限值设下限（例如不早于“现在 + 1 分钟”，Spec 里写明）；加单元测试覆盖过期值、NaN、很远的值。

## 发现 2：提供者没发布时没有诊断，与 Spec 输出 18 不一致，也是最容易踩的作者错误（重要 / 不变量 / 文档）

- 位置：`scene-providers.ts:77-80`（`sceneFor` 在提供者没发布时直接返回 undefined），`scene-providers.test.ts` “提供者没发布、主题没写 sceneProvider 时没有动态图，也不发请求”。

- 为什么是问题：Spec 与实现不一致；最常见的失误（忘写 `onStartup`）恰好静默。
- 如何核实：读 `sceneFor`；测试里该用例没有断言 `reports`。
- 建议改法：二选一，并改 Spec 或测试使其一致：(a) 主题条目在目录里存在、提供者在窗口启动稳定后（例如首次 `apply` 之后若干秒，或入口激活完成的事件）仍没有，按提供者 id 记一次诊断；(b) 把 Spec 括号里的“提供者没发布”去掉，明确只在失败时记诊断。

## 发现 3：用户层主题替换/删除不让场景缓存失效；缓存键不含提供者（建议 / 正确性 / 不变量）

- 位置：`packages/neuro-book/src/plugins/workbench/web/themes.ts:136-147`（`setUserThemes`）；`scene-providers.ts:81`（键 = 主题 id + 明暗 + working）。
- 现象：插件主题在 `receiver().published/revoke` 里调 `generationChanged`，用户主题（我的主题，计划里“`sceneProvider` 用户层保留”）整体替换 `#mine` 时不调。后果两条：

  2. 我的主题被删除后，它名下的任务、对象 URL、定时器留到页面结束，`expiresAt` 还会每小时重新请求并解码一次。
- 为什么是问题：违反 `scene-providers.ts` 头部“主题条目有代次，主题重新发布或撤回时加一”的约束；用户层条目是 `sceneProvider` 的合法持有者（复制 scene-clock 的“天空”得到的我的主题就带着它）。
- 如何核实：`/tmp/review-w00041-t06-impl/exp.test.ts` 第二个用例：目录发布两个提供者，`setUserThemes` 放一个 `sceneProvider: one` 的我的主题，等画好；再 `setUserThemes` 同 id 改成 `two`：`resolve` 的 `--skin-scene` 仍是同一个 blob（输出 `url("blob:725a4def-…")` 两次相同）。删除一条的泄漏从代码推断。
- 建议改法：`setUserThemes` 里对比前后条目，id 被删或 `sceneProvider` 变了的调 `generationChanged`；或把提供者 id 放进缓存键，并在目录里没有对应主题时清掉键。

## 发现 4：对象 URL、定时器的生命周期只在“撤回/重发/dispose”收口，未用的键永不停止刷新；离开工作台页面不 dispose（建议 / 安全与性能 / 不变量）

## 发现 6：生成代次（generation）在 stale 判断里是死代码（建议 / 代码质量）

- 位置：`scene-providers.ts:60,84,146`。
- 现象：`generationChanged` 同时做两件事：`#generations` 加一、`#drop` 掉该条目名下所有任务（abort 并从 `#jobs` 删除）。`#run` 的 `stale()` 里 `signal.aborted || this.#jobs.get(key) !== job` 已经覆盖所有“代次变了”的情形，`(this.#generations.get(...)) !== spec.generation` 永远不会是唯一为真的一项。变异验证：删掉这个比较，11 个用例全过。
- 为什么是问题：读者会以为迟到结果靠代次拒绝（头注释、计划都这么写），实际靠 abort 与 `#jobs` 身份比较；多一张 Map 与 Spec 字段，没有独立作用。
- 建议改法：要么删掉 `#generations` 与 `Spec.generation`（改头注释为“任务被撤销即作废”），要么让 `generationChanged` 不再主动 `#drop`（只靠代次丢弃迟到结果、懒清理），二者不要重复。

## 发现 7：刷新失败后刷新循环就此结束，旧图永远停在过期状态；诊断只记一次且重发布后不再记（建议 / 正确性）

- 位置：`scene-providers.ts:168-175`（catch 不重新排定时器）、`:61,171`（`#reported` 只增不清）。
- 现象：`scene-clock` 这类带 `expiresAt` 的提供者，某次到点重画失败（提供者暂时不可用、解码失败）时，旧图保留，但没有重新 `#schedule`，这个键从此不会再刷新，天空停在失败那一小时直到整页刷新或提供者撤回重发布。`#reported` 也不随撤回清空，提供者重新发布后再失败，一条诊断都不会有。
- 对任务提问的回答：提供者撤回会 `#drop` 掉失败的任务，所以“撤回后重新发布”会重新请求（正确）；但“提供者没撤回、只是暂时失败”的情形永不恢复，这与“失败不重试”的 Spec 文字一致，却对带过期时间的图（已经有过一张好图）不合理。
- 如何核实：读代码；单元测试没有“刷新失败”用例。
- 建议改法：已有成功结果时失败，按原 `expiresAt` 之后的退避（例如 1 分钟起翻倍）重试并只记第一次诊断；`revoke` 时清掉该提供者的 `#reported`。第一次就失败的键保持 Spec 现在的“不重试”。

## 发现 8：第一次换键（工作态、明暗）时先掉到后备/无场景再弹回动态图（建议 / 正确性）

- 位置：`scene-providers.ts:77-89`、`web/themes.ts:52`。
- 现象：`sceneFor` 对每个新键返回 undefined 直到画好并解码。Agent 第一次转入工作态，或第一次切到另一个明暗时，`themeVars` 取后备静态图（提供者主题常常没有后备，如 `scene-clock`），所以 `--skin-scene` 与 `data-nb-skin-scene` 先被去掉再在几十毫秒后加回来；换明暗走 View Transition 时，新快照里还没有场景图，渐变到“没图”的页面，图随后跳出来。
- 为什么是问题：Spec 17 要求“换图不触发整页渐变”，这里在换图的几十毫秒里整个场景消失一次，是可见的闪烁；每个键第一次出现时都发生。
- 如何核实：从代码推断（`e2e/plugin-code.e2e.ts` 只轮询最终值，不会发现中间态）。
- 建议改法：同一条目同一提供者下，新键没画好之前沿用最近一次已显示的结果（旧键的 URL），画好后再换；或明暗切换的写入在新键画好或短超时后再进 View Transition 回调。

## 发现 10：第三方主题的图标路径指到不存在的文件时，图标会整个消失而不是保持原图标（建议 / 正确性，从规范推断，未在浏览器验证）

- 位置：`web/themes.ts:68-73`（`themeVars` 注释“图标文件解析不出……的那一个不换”）；`window.ts:264-267`（第三方插件 `fileUrl` 不查文件是否存在，永远返回 URL）；`document-theme.ts:iconRules`。
- 现象：只有内置插件的素材表能让 `assetUrl` 返回 null；第三方插件里 `icons: {files: "assets/typo.svg"}` 只要后缀是 `.svg` 就得到一个 404 的 URL，样式表写成 `.i-lucide-files{--svg:url("…/typo.svg")}`。按 CSS Masking，加载失败的 `mask-image` 是全透明的遮罩层，该图标（例如活动栏的“文件”）变成不可见，而不是回退到 lucide。场景图加载失败只是少一张背景，图标没了是功能入口不可见。
- 为什么是问题：Spec 输出 16 “没写的保持原图标”以及失败表“场景图不见或解码失败：那一位置没有图”，没有给图标写失败行；`themeVars` 里的注释对第三方插件不成立。
- 如何核实：无法在本机跑 Chromium（缺浏览器）。可以在 e2e 里装一个图标路径拼错的主题，看对应图标元素的 `getBoundingClientRect` 仍在但 `mask` 为全透明；或写一个 `page.setContent` 的小探针：`--svg:url(http://127.0.0.1:1/missing.svg)` 的 div 截图为空。
- 建议改法：写入样式表前对每个图标 URL 做和场景一样的 `Image.decode()` 预检，失败的不写并记一条诊断（异步，写入在全部预检后进行）；至少把 `themeVars` 的注释改成与现实一致，并在 Spec 失败表里补一行。

## 发现 12：e2e 里两处断言偏弱（建议 / 测试）

- `e2e/themes.e2e.ts` 图标集用例：`await writeSettings({…STUDY, dark}); await expect.poll(mask).toBe(study);`。此刻 `mask()` 本来就等于 `study`（还没切到暗色），`expect.poll` 第一次采样就通过，没有等暗色写入完成，所以“暗色用同一批文件”的判据可能在更新落下之前就判过；若暗色 Look 漏写了 `icons`，之后才变化，这一步不会失败。先 `await expect(page.locator("html")).toHaveAttribute("data-nb-appearance", "dark")` 再断言。其余步骤（高对比度来回、换回 NeuroBook）的起点与目标值不同，是有效的。该用例只模拟 `contrast: more`，没有模拟 `forced-colors: active`，Spec 输出 16 两者都写了（同一条媒体查询，风险低）。
- `e2e/themes.e2e.ts` “图标 SVG 当蒙版用时不加载外部资源”：哨兵 `/control.png` 证明探针服务器能收到请求，但没证明这份 SVG 的内部引用在“允许加载”的上下文里确实会被请求（例如 `<img>` 之外、直接作为文档导航就会）。如果 SVG 因为任何原因没渲染出来（解析失败、`about:blank` 页的跨源蒙版被拒），`/inner-*` 同样不出现，断言仍成立。建议加一个正对照：同一份 SVG 用 `<object data=…>` 或 `<iframe>` 加载，断言 `/inner-image.png` 被请求，再断言蒙版路径不请求。Spec 输出 16 里“不执行里面的脚本”也没有断言（探针只看外部资源）。

## 发现 14：每次 apply 都重写图标样式表（建议 / 安全与性能）

- 位置：`document-theme.ts:74-82`（`writeIcons`）。
- 现象：`iconSheet.textContent = iconRules(entries)` 每次 `write` 都赋值，即使内容相同；赋值会让浏览器重新解析这张样式表并使样式失效。Spec system.md 运行时流程第 6 条写“只改配色变量（编辑器里改色、拖动）直接写”，拖动取色时每帧一次 `apply`，书房主题下每帧重解析 10 条规则的样式表（以及发现 1 的死循环放大它）。
- 建议改法：保存上次写入的文本，相同则不赋值。
