[1] 重要 / 接口与合同 / plan.md:34、13-15、38-40
现象：plan 让 nbook、macos 也改成 workbench.themes 贡献，且“贡献 id 以插件 id 为前缀”；themeSetting 现存值与默认值是裸字符串 "nbook"、"macos"。
为什么是问题：贡献点若写 idPrefix: "plugin"（plan 说要前缀），内核核对规则是“以插件 id + '.' 开头，保留发布者的内置插件可只以 'nbook.' 开头”（packages/nb-runtime/src/plugins/host.ts:839-849）。裸 "nbook"/"macos" 不带点，必被拒；不写 idPrefix 则第三方可以抢注 "macos"。若 id 改成 nbook.workbench.macos 之类，用户设置文件与项目层里已存的 "macos"、默认值 "nbook"、现有测试（settings/commands.test.ts:206、window.test.ts、SettingsWindow.dom.test.ts:149、e2e/settings.e2e.ts）全部落空，会退回缺省主题，S1“产品外观不变”不成立。plan 没提迁移。
如何核实：读 host.ts:839；grep themeSetting；themeSetting 定义在 plugins/workbench/shared/contracts.ts:130-144。
建议改法：二选一并写进 plan：(a) 内置两套保留裸 id，贡献点自定义 validate（内置点可写 validate）规定“无点的 id 只许保留发布者 nbook.workbench 贡献”，其余走前缀；(b) 换成带前缀的 id，并写明读取设置时的别名映射（"nbook"→新 id）与是否改写存量设置。别名必须在 S1 完成，不能留到 S2。

[2] 重要 / 依赖的机制不存在 / plan.md:33、59-61
现象：plan 只说“Asset 是插件目录内相对路径，经现有插件文件端点取；内置插件在构建里给 URL”。
为什么是问题（内置侧）：插件文件端点只服务 <State Root>/plugins 下已登记的第三方版本目录（plugin-code-loading.md 输出 8），内置插件的文件不在其中。内置插件的声明写在 plugins/<插件>/plugin.ts 的 descriptor.contributions 里，这个文件被 src/manifest.ts 引用，服务端、项目实例、浏览器三处都 import。若在其中 import "./assets/day.webp" 取 URL：实测（/tmp/w41/review/exp/bun1）bun build --target bun 会把图片作为 asset 复制进输出目录，产出字符串 "./a-<hash>.webp"（相对路径、与 Vite 的 URL 不同）；bun 直接运行得到的是磁盘绝对路径。即“服务端构建会把图片打进 dist/server，且两端 URL 不一致”。又 plugin-manifest.md 要求内置插件的代码定义必须能表达为 package.json 形式，所以声明里应是相对路径字符串，由浏览器侧再解析。
如何核实：见上实验；architecture.test.ts 对 ui/ 与各位置的导入有限制，descriptor 在 shared 位置。
建议改法：声明里一律是相对路径字符串；内置插件在 web 侧另有一个解析表（import.meta.glob("…/assets/*.webp", {query: "?url", eager: true}) 按相对路径取 URL），只在浏览器模块里引用，描述文件不 import 图片。plan 要写明这张表放哪、谁登记（例如 theme-study 的 web 入口位置没有入口，需要一个无入口也能被登记的位置，见 [3]）。

[3] 重要 / 依赖的机制不存在 / plan.md:33、59-61、97
现象：第三方侧，workbench 要把相对路径变成 /api/runtime/plugins/<id>/files/<摘要>/<路径>，需要文件 URL 前缀。
为什么是问题：前缀由引导接口给窗口（browser-host.md 启动序列第 4 条），目前只被 src/web/host/window.ts 与 plugin-platform/web/styles.ts 用（pluginFileUrl），没有任何窗口能力（src/shared/host.ts 的 WindowPlugins 只有 entryState、onChange、retry、activationEvents、problems）交给插件。workbench 浏览器入口读不到它。内置侧“无入口的内置插件”描述机制是存在的（locations: [] 加 contributions，见 definitions.ts 的 definitionAt 与 window.test.ts:330 的测试用例），但产品里至今没有这样的内置插件；内置没有入口就没有 web 模块可放解析表。
建议改法：plan 增加一条：新增窗口能力（例如 windowPluginFilesKey：pluginId → URL 前缀或 resolve(plugin, path)），内置插件的解析表也经同一个能力提供（内置资源用 Vite URL，第三方用文件端点），workbench 只调这一个函数。并把它写进 S3 范围。

建议改法：声明改成 scene.{light,dark}: Asset 一张，加 empty/margins/sidebarCorner 各自的 position、size（字符串，白名单校验）；或明确“每个位置各一张”是有意改动并让开发者确认。contentX 写明单位（0–1 比例？相对内容区宽）与方向。

[6] 重要 / 遗漏（配色缺键）/ plan.md:19-24
现象：colors?: {light: ColorVars; dark: ColorVars}，ColorVars、RoleVar、Both 在 plan 里都没定义；“没有就用 base 的缺省配色”只覆盖整体缺省，没有说明“给了但不全”。
为什么是问题：配色契约 33 个键（nb-ui colorway-contract.ts:15-70），NbColorwayVars 是 Partial；nb-ui 与 neuro-book 的 CSS 里没有给任何配色变量的 :root 缺省（grep "--bg-main:" 无结果）。所以第三方只写 10 个变量时，其余变量在页面上是未定义，var(--bg-main) 失效，界面出现透明、继承色。theme-loader 的装载校验也不要求自带配色写满（theme-loader.test.ts 里有只写两个键的合法用例），不会兜住。vars 是一张平的表，没有亮暗分档，而草稿里一些角色变量（阴影、sheet 的边）亮暗取值不同；Both 的形状（{light,dark} 还是 [亮,暗]）也和 colors（先分明暗再分键）、margins（先分明暗再分左右）的嵌套方向不一致。
建议改法：定义 ColorVars：要么 schema 要求写满 33 键（可由 nbColorwayVarKeys 生成 JSON Schema，纯 JSON 合规）、要么说明与 base 的 defaultColorway 合并（缺的键取 base）；vars 与 activityBar 一样按 {light,dark} 分档；整份声明统一一个“先明暗再键”的形状；RoleVar 白名单从 nbThemeTokens 的 Role 与 Decor 子集里列出（plan 说“从书房实际用到的开始”，但白名单取值与 nbThemeTokens/nbReservedTokens 的关系没写，白名单里不能混入 --font-ui 这类设计 token，也不能和 fonts 重叠）。

[7] 重要 / 位置的画法 / plan.md:52-55
现象：空状态“由 editor 的 EditorGroup 画（没开文件、欢迎页）”。
为什么是问题：EditorGroup 里 activeTab===null 是 .editor-group__empty，欢迎页则是页面标签：渲染在 <div class="absolute inset-0 overflow-auto" :data-editor-page>，由 nbook.projects 通过 editor.pages 贡献（id nbook.projects.welcome）。EditorGroup 不知道哪个页面是欢迎页，也不该按 id 判断（违反跨插件只引 shared/contracts）；editor.pages 的声明 schema 是 additionalProperties:false 且只有 title、icon、openOnFirstVisit（editor/shared/contracts.ts:162-166），没有“要场景”的字段。如果所有页面标签都铺场景，插件设置页、作品设置页等表单页会盖在场景上，对比度要求不止于欢迎页。再有 contentX 的消费者：WelcomePage.vue 的根是 max-width:720px; margin-inline:auto，居中的栏要偏到留白上必须由页面自己（或容器的 padding）读变量；plan 没说谁读 contentX、怎么读。

[8] 重要 / 失败路径与验收映射 / plan.md:99、77-85

[10] 建议 / 热插拔与首屏的描述不准 / plan.md:40、84、97
现象：风险写“第三方主题的声明要等插件登记才有，首屏可能先画缺省主题再切；S5 实测”；验收“装、选、禁用、恢复”；“插件回来后恢复”。
为什么是问题：browser-host 启动序列第 4 步先登记全部插件（含第三方的顶层贡献）、第 5 步才激活 workbench 并挂载页面，所以 WorkbenchDocument 首次写文档根时目录已齐，这条首屏风险不成立；真正的首屏差别在加载页只有颜色（appearance-hint 只记四种颜色，场景图在页面挂载后才加载，会有图片晚到）。另外运行期热插拔还没实现（plugins 页的提示仍是“下次启动后生效”，plugin-hot-plug 状态 planned），“禁用、启用”在窗口里要到重启后才变，e2e 需要重启服务或刷新；并且 context.declarations.list() 是激活时快照，只有走 receiver（published/revoke，顶层声明也会 backfill 给接收者）才跟随变化。plan 没说用哪一种。
建议改法：改写这条风险；计划里写“主题目录用 receiver，不用 list 快照”，验收写成“重启后”；图片晚到用预加载或在写变量前 decode，另算一条。

[13] 建议 / 无障碍偏好用 JS 写入 / plan.md:46、90
现象：“prefers-contrast: more、forced-colors: active 下不写场景变量”。
为什么是问题：写变量要在 WorkbenchDocument 再加两个 matchMedia 监听和清理（目前只有一个），而各位置本来只读变量；用 CSS 的 @media 在消费处把场景层 display:none 就够，也不需要写变量的分支。另 plan 第 9 行写“没有遮罩”，但四个位置都要往正文“淡出”，草稿用的是 mask-image 渐变，措辞会让实现者困惑。

[14] 建议 / 项目层回退 / plan.md:40、96
现象：设置里的 id 找不到时“显示缺省主题”，主题设置继续允许项目层。
为什么是问题：项目层设置文件跟着作品走（可能被带到没装这个皮肤的机器上），这时应先退到用户层的值，再退到缺省，而不是直接跳缺省；plan 的“缺省主题”可能被读成后者。诊断也要按 id 去重，否则每次 computed 重算都记一条。

[15] 建议 / 变量合同的位置 / plan.md:44、50

========== 未发现问题的方面 ==========
- 顶层声明式贡献到达窗口的时机：第三方清单在引导第 4 步登记、早于 workbench 激活，WorkbenchDocument 首次写文档根读得到（见 [10]，只是 plan 的风险说法不准）。
- 无入口的内置插件：descriptor.locations: [] 加 contributions 的装配路径存在（definitions.ts 的 pluginsAt、definitionAt），机制本身不缺；缺的是资源解析（见 [2][3]）。
- 声明用 TypeBox 表达：只要不用 Refine/Codec/自定义 format，内置点可纯 JSON Schema 通过；“不能含 url()”需要内置点的 validate 函数（内置点允许写），不是 schema 表达。
- 正文两侧的定位：MarkdownControl 的工具栏经 Teleport 放在 EditorGroup 的 toolbarSlot，控件根（.markdown-control-root）本来就在工具栏以下；滚动容器是整宽的 scroller，正文列 .markdown-control 在它里面（max-width 720px，margin-inline:auto）。场景层放在根里、与 scroller 同级即可不随滚动；放进 scroller 会随内容滚走。plan 没写此点，可在 S3 补一句，但不构成缺陷。
- nb-ui 不改：配色与主题变量都可由文档根内联覆盖（writer 现状已如此），未发现阻碍。
