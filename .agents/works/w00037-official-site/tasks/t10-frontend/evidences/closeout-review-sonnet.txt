为什么是问题（根因，部分是从代码推断，已标出）：
1. 失败的行有共同点：都发生在“同一个测试里把一个浮层关掉、立刻开第二个”的那一步。菜单的两条是 Escape 之后 `waitFor(menuitem 为 null)`，随即对另一行的触发器 `dispatchEvent(ArrowDown)` 一次；Codes 与“密钥”是 `waitFor(对话框元素为 null)`，随即点开再开。
2. nb-ui 的关闭不是“元素消失”那一刻完成：packages/nb-ui/src/components/feedback/close-handoff.ts 文件头写明，Reka 的 FocusScope 在卸载清理里才排 `setTimeout(0)` 去摘焦点栈，`closed` 要再晚一个宏任务（queueMicrotask 加 setTimeout 0）才发，重开会让没发出的 `closed` 作废（`watch(isOpen)` 里 `invalidate()`）。`vi.waitFor` 靠 50ms 的轮询：机器忙时轮询计时器已经过期，会排在“元素移除之后才登记的 setTimeout 0”前面先跑，于是测试在清理之前就继续往下走（推断，但与“空载 0 次、满载几乎必挂”吻合）。
3. 对 Codes 与密钥对话框：`closed` 被重开作废后，`issued` 仍是上一次的值，再开直接显示“已发出”那一步，所以读到 'issued'。这也是产品侧的一个小缺口：状态只在 `@closed` 里复位，而 `closed` 可以因重开不发。真人在一个宏任务内重开不可能，所以不是用户可见问题，但“每次打开都从空白开始”的注释（IssueCodeDialog.vue:65）与实际依赖的不是同一个信号。
4. 对菜单：第二个 ArrowDown 只发一次、没有重试，也不查触发器是否已回到可开状态；`waitFor` 只重试“有没有菜单项”这个断言，不重发事件。第一次菜单的清理计时器随后才到，把焦点还给第一个触发器，很可能让刚开的第二个菜单被判为焦点移出而收掉（这一步是推断，没有单独抓到），之后菜单项永远是 null，所以是等满 10 秒而不是慢几秒。
5. 另有一类相关写法：Codes :343 等 `waitFor` 用默认 1 秒上限，满载时本来就不够；同文件别处用了 SETTLE_TIMEOUT_MS，不一致。

如何核实：见上面的负载复现命令（8 个 `while :; do :; done` 加 6 份并发 vitest）。

建议改法（测试侧，不加固定毫秒数）：
- 关掉之后等“真的关完”的可观察状态：菜单等 `document.activeElement` 回到触发器（Reka 在清理里还焦点），或在 harness 里加一个 `closedAfter()`：先等元素消失，再 `await nextTask()` 一次（harness 已有 `nextTask`，src/testing/site-harness.ts:198；清理是 setTimeout 0，一个任务就够），把 Clients :135-139、Users :419-420、各处“关掉再打开”前统一换成它。
- openRowMenu 里把 dispatch 放进 `waitFor`（`aria-expanded` 不是 "true" 时重发），事件丢了会重试。
- Codes :343 等处补上 SETTLE_TIMEOUT_MS。
- 可选的产品侧加固：把 `issued`、`secret`、`created`、`password` 的复位同时放进已有的 `watch(() => props.open)`（打开时），保留 `@closed` 作为退场动画结束后的复位；这样“重开作废 closed”不会漏状态。
同类写法（等元素消失后立刻再开）已列在位置里；Users :418-428、Clients :134-140 的菜单两处是主要的。

### B. 合同测试底座的“起不来”报错丢了原因：`spawn` 失败时 `cause` 永远是 undefined
严重程度：建议
类别：错误处理（本机依赖缺失时报错说不清）
位置：packages/nb-site-contract-tests/src/testing/process.ts 的 `spawn` 里 `subprocess.once("error", …)` 与紧接着的 `if (subprocess.pid === undefined) throw new Error(`could not start ${program}`, {cause: spawnError})`
现象：拆分把 `Bun.spawn` 换成了 `node:child_process`。Node 的 `spawn` 在程序不存在时同步返回、`pid` 为 undefined，`error` 事件在之后的 tick 才发。注释写“照同步失败报出去”，可检查 `pid` 的这一刻 `spawnError` 一定还是 undefined，所以抛出的是 `could not start bun`，没有 `ENOENT`、没有路径。
如何核实：/tmp/review-w00037-t10-close/lab/spawn.mjs，输出 `pid undefined err at check undefined`，50ms 后才拿到 `ENOENT`。
为什么是问题：新入口的使用方是在 Node 里跑的 Playwright，那时程序是 `PATH` 上的 `bun`（defaultCommand 里 `process.versions.bun === undefined ? "bun"`）。开发者的 Playwright 若不是从装了 bun 的 shell 起（子进程环境只放 PATH）会只看到 `could not start bun`，不知道是找不到还是没权限。
建议改法：同步抛不出原因就别装作能抛：把“起不来”的判定放进等待里（`await once(subprocess, "spawn")` 与 `error` 竞争），或抛错时把错误消息写成“找不到或不能执行 ${program}（检查 PATH）”，并在 `cause` 里放真的 error（异步登记后再抛）。openssl 缺失时 `execFileSync` 的报错是 `spawnSync openssl ENOENT`，够清楚，不用改；Chrome 缺失是 Playwright 自己的提示，也清楚。

### C. 进程级信号兜底在 Playwright 的 worker 里与它自己的信号约定冲突
严重程度：建议
类别：收口（失败与中断时的进程、临时目录）
位置：packages/nb-site-contract-tests/src/testing/process.ts 的 `installExitHook`（SIGTERM、SIGINT 处理）；调用点 `createSiteSandbox` 内
现象：拆分后这条兜底第一次跑在 Playwright 的 worker 里。Playwright 的 worker 启动时就 `process.on("SIGINT", () => {})`、`process.on("SIGTERM", () => {})`（node_modules/playwright/lib/common/index.js:1974-1977），有意忽略信号、等主进程经 IPC 做有序收口。兜底的处理函数在收到信号时同步 SIGKILL 全部子进程，再 `process.off` 掉自己，然后给自己再发同一个信号；因为 Playwright 的空处理函数还在，这第二次信号被吞掉，worker 继续活着。
为什么是问题：Ctrl-C 时同一进程组的 worker 先收到 SIGINT，被测进程被无声地杀掉，随后 worker 里的 `server` 夹具的 finally 走到 `sandbox.endTest()` → `cleanUp`，发现子进程已经 137 退出，`zeroOnStop` 为真就抛“site processes left running did not stop cleanly on SIGTERM”。中断时报告里多出一条与原因无关的失败，并盖住真正的中断原因。（推断；我没有对真实 Ctrl-C 做录像，只核对了 Playwright 源码与 `cleanUp` 的判据。）注释里“Bun 按信号缺省动作直接结束进程”的前提在 Node 的 Playwright worker 里不成立。
建议改法：在 Node（`process.versions.bun === undefined`）下不装 SIGINT、SIGTERM 的处理，只留 `exit` 兜底（worker 真的被 SIGKILL 时本来就什么也跑不了）；或者让 `cleanUp` 认“已被兜底杀掉”的子进程。要保留就在注释里写清这是 Bun 专用。

现象：我在包目录里执行 `NB_SITE_DEV_API=http://127.0.0.1:4310 bunx vite build --outDir /tmp/review-w00037-t10-close/lab/dist-a`，配置加载阶段就抛错（`NB_SITE_URL must be set when NB_SITE_DEV_API is set`），构建没有开始。配置文件在 dev、build、preview 里都会求值，抛错设计原本只想拦“开发时设错”。另外 Vite 的 `preview.proxy` 缺省继承 `server.proxy`（按 Vite 文档，我没有单独跑 preview 验证），所以 e2e 用的 `vite preview` 在这个环境变量存在时也会转发 `/api` 并改 `Origin`；假接口的场景由 `page.route` 在浏览器一侧拦截，不受影响，但转发在进程里是活的。

### G. 合同测试底座起的 stdin 写入没有 `error` 监听：子进程来不及读就退出时，进程级未捕获的 EPIPE
严重程度：建议
类别：异常输入下的失败（拆分带来的行为差异）
位置：packages/nb-site-contract-tests/src/testing/process.ts 的 `spawn` 里 `if (stdin.kind === "text") subprocess.stdin!.end(stdin.text)`；`spawnWithOpenStdin` 里的 `sink.write`、`sink.end`
现象：旧代码用 `Bun.spawn` 与 `Blob` 作标准输入，失败是 Promise 的失败；现在是 Node 的可写流，没人监听它的 `error`。我在 /tmp/review-w00037-t10-close/lab/epipe3.mjs 里 spawn 一个立刻 `exit 2` 的 `sh`，紧接着 `stdin.end("short text\n")`：Node 与 Bun 各跑了几次，每次都是未捕获的 `EPIPE`（`uncaughtException`），不是被 `result` 或 `exited` 接住。
为什么是问题：合同测试里 create-admin 的参数校验类失败很多（operations.test.ts:698-709 的十几个并发用例，标准输入里都带着密码）。现在它们过，是因为被测程序启动要几十毫秒，文字早已写进管道；一旦被测程序换成启动更快的实现（这个包的目的就是“换语言重写后照样跑”），或者起不来的子进程，这类测试会变成整个测试进程崩溃，而且报错与原因无关。拆分之前不会这样（Bun 的 sink）。
建议改法：`subprocess.stdin!.on("error", ignoreEpipe)`（只吞 `EPIPE`、`ERR_STREAM_DESTROYED`，其它重新记到 `child.stderr` 或抛），并让 `write` 的回调在 `exited` 之后给出“子进程已退出”的明确错误。
