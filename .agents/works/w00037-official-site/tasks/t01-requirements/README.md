# 需求与范围讨论

## 目标与范围

与开发者讨论官方网站与服务的需求、重写策略与架构范围：账号与 OAuth 登录、备份与跨设备同步、Skill / 插件 / Profile 市场及其安全措施、小说发布、用户交流与论坛，以及 Cloudflare Workers 与自托管架构的取舍。

## 当前状态

2026-10-30 经 nbdev 新建。2026-11-23 补记开发者提出的官网重写倾向、扩展能力清单与 Cloudflare Workers 架构评估入口（见 [w00053 调研报告](../../../w00053-telemetry-feedback-stats/research/2026-11-23-telemetry-feedback-and-stats.md)）。2026-11-24 开工：开发者给出重写方向（下一节），主会话给出架构看法，等开发者答复四个问题。

## 开发者定的方向（2026-11-24）

1. 重写 NeuroBookSite，与 [w00053](../../../w00053-telemetry-feedback-stats/README.md) 一起推进。
2. 用微服务的思想搭；按一台 2 核 2 GB 的机器承接 100 同时访问来设计。
3. 技术栈与 monorepo 一致：Bun、TypeScript；前后端分离，前端继续用 nb-ui。
4. 后端的测试用例很重要：以后可能用别的语言重写后端，这些测试要能留下来用。
5. 第一版只做管理面板：用户管理、邀请码管理、类似 Umami 的使用数据收集、OAuth 等；相对旧站先不做市场。

这一条取代 Work README 里 2026-11-23 记的“不建议前期拆微服务、推荐模块化单体”。

## 主会话的架构看法（2026-11-24，待开发者确认）

- 边界照微服务，进程数从少起。第一版两个后端服务、一个静态前端、一个现成的反向代理、一个 PostgreSQL：
  - 账号服务：用户、会话、注册码与邀请码、GitHub 登录、用户管理接口，签发短期 JWT 并公开 JWKS；
  - 统计服务：收匿名事件、按日聚合、给面板查询（w00053 的服务端落在这里）；
  - 管理面板：Vue 加 nb-ui 的单页应用，构建成静态文件，由反向代理直接发；
  - 反向代理只做 TLS、按路径分流、静态文件与粗限流，不放业务。
- 四条规则：服务之间在请求路径上不互相调用（别的服务用 JWKS 本地验令牌）；数据库不共享（同一个 PostgreSQL 实例里每个服务一个 schema 加一个数据库角色）；合同是 HTTP（每个服务一份入库的 OpenAPI 文件，由 TypeBox schema 生成）；迁移用纯 SQL 文件。
- 测试分两层：合同测试是黑盒，只认服务地址与一个空数据库，起真实进程、全走 HTTP，不 import 服务代码、不直接改库造状态，换语言重写时原样复用；服务内部只留少量纯逻辑的单元测试。容量用一份压测脚本作为验收。
- 按用户管理、邀请码、OAuth 各拆一个服务不划算：注册时消费注册码与建账号要在同一个事务里，三者读写同一批表；每多一个进程约占 80 到 120 MB（估算，未实测）。
- 身份部分不手写协议：候选 Better Auth（MIT，2026-11-24 核对 npm 最新 1.7.27，文档有 Device Authorization、OAuth 2.1 Provider、Admin、JWT 插件与 Hono 接入）；对外合同只取 RFC 定的标准端点加自家路由，不让前端依赖库自带的路由。细节留给选型 Task 核实。
- 已核对的事实：新应用 `packages/neuro-book` 里没有调用官方站的代码（搜 `nbook.notnotype.com` 只在旧应用与 llmlint 的部署配置里命中），重写没有来自新应用的合同包袱。旧站（GitHub `notnotype/neuro-book-site`）是 Nuxt 全栈加 Prisma 与 SQLite，含 Passport、设备码、OAuth 提供方、GitHub 登录、备份、工坊与管理后台。
