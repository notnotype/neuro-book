## 主会话的架构看法（2026-11-24，待开发者确认）

- 边界照微服务，进程数从少起。第一版两个后端服务、一个静态前端、一个现成的反向代理、一个 PostgreSQL：
  - 账号服务：用户、会话、注册码与邀请码、GitHub 登录、用户管理接口，签发短期 JWT 并公开 JWKS；
  - 统计服务：收匿名事件、按日聚合、给面板查询（w00053 的服务端落在这里）；
  - 管理面板：Vue 加 nb-ui 的单页应用，构建成静态文件，由反向代理直接发；
  - 反向代理只做 TLS、按路径分流、静态文件与粗限流，不放业务。
- 四条规则：服务之间在请求路径上不互相调用（别的服务用 JWKS 本地验令牌）；数据库不共享（同一个 PostgreSQL 实例里每个服务一个 schema 加一个数据库角色）；合同是 HTTP（每个服务一份入库的 OpenAPI 文件，由 TypeBox schema 生成）；迁移用纯 SQL 文件。
- 测试分两层：合同测试是黑盒，只认服务地址与一个空数据库，起真实进程、全走 HTTP，不 import 服务代码、不直接改库造状态，换语言重写时原样复用；服务内部只留少量纯逻辑的单元测试。容量用一份压测脚本作为验收。
- 按用户管理、邀请码、OAuth 各拆一个服务不划算：注册时消费注册码与建账号要在同一个事务里，三者读写同一批表；每多一个进程约占 80 到 120 MB（估算，未实测）。
- 身份部分不手写协议：候选 Better Auth（MIT，2026-11-24 核对 npm 最新 1.7.27，文档有 Device Authorization、OAuth 2.1 Provider、Admin、JWT 插件与 Hono 接入）；对外合同只取 RFC 定的标准端点加自家路由，不让前端依赖库自带的路由。细节留给选型 Task 核实。
- 已核对的事实：新应用 `packages/neuro-book` 里没有调用官方站的代码（搜 `nbook.notnotype.com` 只在旧应用与 llmlint 的部署配置里命中），重写没有来自新应用的合同包袱。旧站（GitHub `notnotype/neuro-book-site`）是 Nuxt 全栈加 Prisma 与 SQLite，含 Passport、设备码、OAuth 提供方、GitHub 登录、备份、工坊与管理后台。

## 第一版先不拆进程（开发者 2026-11-24 第二轮）

开发者：第一版不做成真正的微服务，注意解耦，让以后想拆时不困难；这样也能加快开发。主会话同意，上一节的“两个后端服务”改为一个进程里的两个模块，其余规则照旧。保证以后拆得动的做法：

- 每个模块一个目录、一个公开入口，跨模块只经公开入口导入，由架构检查机检；
- 每个模块一个 PostgreSQL schema 加一个数据库角色与连接池，没有跨 schema 的 JOIN、外键与事务；
- 每个模块是一个挂在自己路径前缀下的 Hono 子应用，各有 OpenAPI 文件与黑盒合同测试；进程入口只负责把模块装起来，拆分时加第二个入口文件；
- 模块之间只有一个窄接口：统计模块向账号模块问“这个请求是谁、是不是管理员”。第一版在进程内调用，浏览器对两个模块都用同源的会话 Cookie；拆分时这个接口换成反向代理的转发鉴权或 JWT，对外合同不变。第一版因此不做 JWT 与 JWKS。

少掉的是进程级隔离：统计入口被刷会连带登录变慢，一处内存泄漏影响全部。第一版靠反向代理对统计入口限流、限请求体大小来挡。

## 开发者对四个问题的答复（2026-11-24 第三轮）

1. OAuth：能用 Google、GitHub 登录，本站也对外提供 OAuth 服务。
2. 旧站数据不弃用。
3. 代码放进本 monorepo。
4. 机器与“100 同时访问”的验收口径不做硬性要求与限制。

答复之后查到的事实（影响迁移与 OAuth 服务的合同）：

- 旧站生产库是 SQLite，含账号（`username` 唯一且不可改、`displayName`、可空的 `passwordHash`、角色、状态、`sessionVersion`、头像等）、上游身份（GitHub）、注册码、邀请码、工坊条目与版本及点赞收藏评论举报、设备码关联与令牌、实例备份、OAuth 客户端与令牌。工坊压缩包与加密备份是数据卷里的文件。
- 旧站密码哈希是 `scrypt:<盐>:<十六进制>`（Node `crypto.scrypt` 默认参数、64 字节）。迁移后要能用原密码登录，新站得能验这种哈希。
- 旧站的 OAuth 服务已有一个在用的客户端：llmlint 的网页（`packages/llmlint/web`，`client_id` 为 `llmlint-web`，授权码加 S256 PKCE，`client_secret_basic`）。它读发现文档、换一次令牌、调一次 `/userinfo`，要求返回 `{id: 数字, username, displayName, status: "active"}`，并按这个数字 id 在本地认人。迁移时用户 id 不能变；`/userinfo` 的形状要么保持，要么同时改 llmlint。
- 旧站生产已开放凭注册码的密码注册（2026-07-31），不能假定只有站点所有者一个账号。

主会话的理解（待追认）：第一版不做市场与备份，所以切到新站后，工坊页面、云备份、旧应用的设备码关联在重建之前不可用；它们的数据原样留存（数据库快照加文件卷），重建对应模块时再导入。旧应用与官方站之间的旧接口不保持兼容。
