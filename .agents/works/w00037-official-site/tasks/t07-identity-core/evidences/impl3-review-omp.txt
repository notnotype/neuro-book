### 1. 账号列表对非 ASCII 显示名的搜索区分大小写（撤回）
- **严重程度**：重要；**类别**：正确性。
- **位置**：/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/admin/users.ts:139-150；/home/notnotype/CodeRepository/neuro-book/docs/specs/site/admin.md:33。
- **现象**：显示名设为 `Élodie` 后，`GET admin/users?q=Él` 和 `?q=ÉLODIE` 都回 200、`total: 1`；`?q=él` 回 200、`total: 0`，`counts.all` 也从 1 变成 0。
- **为什么是问题**：合同对用户名、邮箱、显示名三种前缀都要求不分大小写，显示名可以是 Unicode。SQLite 的 `LIKE` 只折叠 ASCII；现有代码保住了字面通配符与占位邮箱规则，却没有实现显示名的大小写规则。
- **如何核实**：在 HEAD 为 `f8eb66f1e` 的实现树运行 `bun --no-env-file /tmp/review-w00037-t07-impl3/lab-omp/verify-profile-http.ts`；经真实 CLI 创管理员、HTTP 登录、同意、改资料，再对照上面三次查询。
- **建议改法**：为显示名和查询使用同一 Unicode 折叠规则，再做字面前缀匹配；同时覆盖已有/导入账号、总数与筛选计数。补一个非 ASCII 大小写前缀的合同用例，不用 SQLite 内置 `LOWER` 代替 Unicode 折叠。
- **撤回依据**：本轮并行的 Opus 审查也发现了此现象；主工作区提交 `a491b21e2` 已明定显示名只对 ASCII 字母不分大小写。实测仍成立，按现行合同不计作缺陷。

### 2. 严格 UTF-8 解码仍会把转义的孤立代理项改存成替换符
- **严重程度**：建议；**类别**：正确性。
- **位置**：/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/errors.ts:99-109；/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity-contract/src/fields.ts:13-20；/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/me.ts:85-105。
- **现象**：发送字节全是合法 UTF-8 的 `PATCH me` 请求体 `{"displayName":"\ud800","bio":"\udc00"}`，真实服务回 200，两个值已经变成 `�`；显式发送 U+FFFD 也回 200，结果相同。
- **为什么是问题**：`fatal: true` 只检查 JSON 源的字节，JSON 解析仍会产出孤立代理项，字段正则明确允许它们。写 SQLite 时字符串不能原样编码，调用方收到成功，却存了不同的文字。这与修正上一轮“无效文本变成 U+FFFD 再入库”的目标相悖。
- **如何核实**：在 HEAD 为 `f8eb66f1e` 的实现树运行 `bun --no-env-file /tmp/review-w00037-t07-impl3/lab-omp/verify-profile-http.ts`，比较最后两次 `PATCH me` 的真实 HTTP 响应。
- **建议改法**：在 JSON 解析后校验文本字段是良构 Unicode；拒绝孤立代理项，保留合法代理对与显式 U+FFFD。让合同包和服务端对可存文本的定义一致。

### 3. 改角色与登录并发时，登录响应的角色和新会话的角色相反
- **严重程度**：重要；**类别**：正确性。
- **位置**：/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/login.ts:200-233,239-254；/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/admin/users.ts:284-300。
- **现象**：让另一个管理员改同一账号的角色，同时请求登录。8 次升降角色均复现：两个请求都回 200；降级时登录回 `user.role: "admin"`，拿该响应的新 Cookie 问 `whoami` 是 `"user"`；升为管理员时正好反过来。新 Cookie 有效，服务端权限判断正确。
- **为什么是问题**：第 7 片加入在线改角色后，登录最初读到的资料不再保证是发会话时的资料；事务只复核封禁和密码，响应最后还从哈希之前的 `candidate.profile` 组装。`site.accounts` 输出 4 让客户端同时拿到公开资料和会话；这个响应会给客户端一个该会话并不具备的角色，也可能漏掉它已具备的管理员权限。
- **如何核实**：在 HEAD 为 `f8eb66f1e` 的实现树运行 `bun --no-env-file /tmp/review-w00037-t07-impl3/lab-omp/verify-admin-session-http.ts`。通过真实 HTTP 并发改角色和登录，再用本次登录的 Cookie 调 `whoami`。
- **建议改法**：让发会话事务返回同一快照上的公开资料，提交后用它组响应；可由事务内已有的账号查询带出，不要改成事务外再读一次。补升、降角色时登录响应和新会话一致的用例。

### 4. 资料保存的地址与网页实际解析的地址可以不同
- **严重程度**：建议；**类别**：正确性。
- **位置**：/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity-contract/src/fields.ts:84-100；/home/notnotype/CodeRepository/neuro-book/.worktree/w00037-t07-review3/packages/nb-site-identity/src/me.ts:91-99,127-133。
- **现象**：真实 HTTP `PATCH me` 提交 `website: "https:example.org"` 得 200，响应原样返回。无基准时平台解析出 `https://example.org/`；按 HTTPS 账号页的基准 `https://site.test/account` 解析却得 `https://site.test/example.org`。
- **为什么是问题**：校验用无基准的 `URL.parse`，页面的链接和图片属性却带文档基准。通过校验、回填原文，并不保证前端直接用这个值访问的是校验时解析的地址。这里的输入没有空白、控制字符或双向控制符；并行审查已定的字符限制不能消除这个差异。不是脚本协议绕过。
- **如何核实**：在 HEAD 为 `f8eb66f1e` 的实现树运行 `bun --no-env-file /tmp/review-w00037-t07-impl3/lab-omp/verify-profile-http.ts`，对照 `withoutBase` 与 `withSiteBase`。网页效果按 URL 解析规则推断，未跑前端。
- **建议改法**：既然要按原样保存，在共享字段规则里要求显式 `http://` 或 `https://` 和主机，拒绝这种缺少绝对地址分隔符的写法；若要兼容它，则明确由消费方使用无基准解析得到的 `href`，不把原文直接当链接或图片地址。
