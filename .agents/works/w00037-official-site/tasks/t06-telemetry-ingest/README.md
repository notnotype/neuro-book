# 统计模块：三个写入口、原始上报留 7 天、聚合

## 目标与范围

统计模块的服务端：每日上报、在线心跳、立即事件三个写入口，按收集清单校验，重发去重，原始上报留 7 天后按日删除，定时聚合；不留 IP 的清单里属于进程的几项。

合同：[`telemetry.protocol`](../../../../../docs/specs/telemetry/protocol.md)、[`site.telemetry-ingest`](../../../../../docs/specs/site/telemetry-ingest.md)。

- 表：两张原始表（各存声明的与生效的清单版本；使用档的生效版本与使用段同在同不在，`CHECK` 守着）、聚合游标、七张聚合表（单维度份数、活跃、安装周交叉、使用档份数、按 `owner` 加 `code` 的错误、立即事件、心跳），都是 `STRICT`。
- 数据库错误按 SQLite 的主结果码分：忙、锁、只读、读写错误、满、打不开算“库一时用不了”（写入口回 503），约束类的照常抛。
- 最坏情况的存储（每天 65 个应用版本、27 个 `owner`、6 个分档）：聚合每天约 1.27 MiB，一年约 0.45 GiB，其中心跳与错误两张表各占一半。第 1 版每个 `owner` 只有 `other` 一个码，所以一份上报至多 27 项错误，到不了协议写的 50 项。
- 与计划不同、接受的：包内测试不能经入口的迁移运行器建库（模块包不许依赖入口包，会成环），改成测试辅助照运行器的做法建库，真实运行器由合同测试覆盖；立即事件省略的 `code` 在原始表里存空（聚合表的主键列不能为空，存空串）；没有加“每天的应用版本登记表”，第 4 片从当天的聚合里数已有的版本。
