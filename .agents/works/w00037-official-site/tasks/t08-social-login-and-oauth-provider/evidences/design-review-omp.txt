# w00037 t08 社交登录与对外 OIDC：只读设计审查

审查固定稿，对照 master 的 t07 实现、现行 Spec、Better Auth 1.7.27 源码与既有探针。以下是 Opus 处理之后仍独立成立的问题；区分源码推导、既有探针和本轮实测。

### 1. 关联写入没有在生效时复核发起会话，结束会话后仍可建立关联

- **严重程度**：重要。**类别**：并发与授权边界。
- **位置**：计划 3.10 `callback.ts`、`account.create.before`；`site.accounts` 输出 15、实现合同；`link-account.mjs:29–39、47、73–95`。
- **现象与影响**：模块先复核发起会话，再交库做上游网络往返；库核对发起会话后，也要另行查 `account` 并插入。关联钩子的写事务只认领上游名字，不复核会话，库写 `account` 又在该事务外。结束该会话的事务可以夹在最后一次复核与真正建关联之间，之后新关联仍然成为登录方式。这不是 Opus 第 11 条的失败孤行问题，也不是已接受的换码竞态。
- **核实**：源码控制流与队列边界足以确定；已有验收 12 只覆盖回调开始前就已结束的会话，未覆盖写入时复核。t07 的 `site.accounts` 实现合同明确要求写入第一步在同一事务复核会话。
- **改法**：上游网络往返仍在事务外，拿到上游身份后，用同一短写事务复核发起会话、认领上游身份并写 `account` 和名字；不要用更早的一次复核或独立写钩子代替。验收在上游已返回、关联尚未生效时结束会话，断言没有新增登录方式。

### 2. 新库可以由旧版启动，但旧版结束会话会让部分访问令牌在切回新版后仍有效

- **严重程度**：重要。**类别**：相邻版本兼容与撤销。
- **位置**：计划 3.2、3.5、第 5 节；`site.operations` 输出 7；`session.ts:72–104`；`authorize-DXnMh0ha.mjs:2674–2688`。
- **现象与影响**：迁移是追加的，旧版可以容忍 0002/0003，并继续提供登出、封禁、会话清理等功能。但旧版只删 `session`，不会跑新版的撤销 SQL。外键把令牌的 `sessionId` 置空，切回新版时校验不再检查那次会话。就绪通过并不证明令牌失效合同也兼容；例如在回退期间已完成的登出，切回新版后其未到期令牌仍可读用户信息。
- **核实**：`migrate.ts:247–251、284–285` 接受更新的迁移编号；0002 按原样保留 `ON DELETE SET NULL`；既有 `out7.txt` 的 Q2 对照直接删会话后，新版行为的 UserInfo 仍为 200。未重跑进程级回退。
- **改法**：发布前定清回退语义。若承诺相邻版本仍能任意互换，撤销要能覆盖旧写方（同一库的兼容约束或先发兼容版本；保留当前会话的改密也要覆盖），不要只在新路由补 SQL。用真实的旧版本写入、新版再读取做验收，至少保住登出与改密；若改为回退时额外失效凭据，要明确批准并写进运维合同。

### 3. 授权端点明确拒绝 POST，与已批准的标准 OIDC 不兼容

- **严重程度**：重要。**类别**：协议互操作。
- **位置**：计划 3.6、第 5 与第 6 节；改写稿输入表、输出 1、验收 2；Task README 的「对外 OAuth 按标准 OpenID Connect 做」。
- **现象与影响**：设计用白名单和测试固定 `POST /oauth2/authorize` → 404。合法地以表单 POST 发起授权的 OIDC 客户端因而不能登录。这不是“不支持 `form_post` 响应模式”：请求入口的 HTTP 方法和回到客户端的响应模式是两回事。
- **核实**：[OIDC Core 3.1.2.1](https://openid.net/specs/openid-connect-core-1_0.html#AuthRequest) 明确要求授权服务器同时支持 GET 与 POST；库 `authorize-DXnMh0ha.mjs:7453–7461、8542–8544` 已按方法读取查询或表单。缺口在产品白名单，不在库。
- **改法**：允许 `application/x-www-form-urlencoded` 的 POST，与 GET 共用客户端、回调、会话和跳转的判定，沿用请求体上限；仍只公布代码流需要的响应模式。改验收为两种请求方法各完整走一次，其他方法仍 404。若产品刻意只支持 GET，先改「标准 OIDC」决定并把偏差告知接入方。

### 4. 发现文档和响应模式的真实能力不一致

- **严重程度**：重要。**类别**：协议互操作。
- **位置**：计划 3.6、3.8；改写稿输出 2、3；`oauth-provider.md` 输出 2、3；Better Auth `authorize-DXnMh0ha.mjs:3417、8505–8513、8724–8729、8954–8980`。
- **现象与影响**：计划自建的 OIDC Discovery 与 RFC 8414 Authorization Server Metadata 共用文档，只列 Spec 常量，未列 `response_modes_supported`。RFC 8414 第 2 节规定省略时默认支持 `query`、`fragment`。OIDC Discovery 的同一默认只明确适用于 Dynamic OpenID Providers；本服务关闭动态注册，不以该条单独主张静态 OP 一定默认支持 fragment。RFC 8414 元数据已足以使客户端按 `fragment` 发起请求。本轮真实库探针中，`response_mode=fragment` 的授权码成功响应与 `invalid_scope` 错误响应都写入 query；成功响应路径固定追加 query，错误路径则有的使用请求模式、有的固定 query。客户端按 fragment 读取会拿不到这些结果。
- **核实**：RFC 8414 第 2 节；OIDC Discovery 第 4 节的动态 OP 限定；RFC 6749 §4.1.2 的授权码 query 默认；源码及 `/tmp/nbsite-spike/review-protocol.ts` 实测。库自己的 `authServerMetadata()` 已列 `response_modes_supported: ["query"]`，但计划的自建文件不复用完整库能力对象。
- **改法**：两份发现文档显式列 `response_modes_supported: ["query"]`；在授权入口拒绝 `response_mode=fragment` 及其它未支持值，按 RFC 6749 §5.2 用 HTTP 400 `invalid_request`，不能只让查询响应继续。补两份自家发现文档及成功、错误请求的黑盒合同。

### 5. 续接参数尺寸与入口上限不闭合

- **严重程度**：重要。**类别**：容量边界与端到端验收。
- **位置**：计划 3.1 第 2 条、3.6、3.7、3.8 第 2 步；改写稿输出 3、4、12、14。
- **现象与影响**：授权入口允许原始查询串至多 8192 字符；库在签名后把查询串完整序列化，再追加签名字段并编码为 base64url；`resolveContinue` 又以编码结果 8192 字符为界。一个 `state` 为 6500 个 ASCII 字符的合法入口请求，其 state 单项编码即约 8667 字符，续接必被丢弃。匿名用户可能完成登录或同意，却无法回到这次授权请求；已登录且无需页面的请求则可能照常获得码。
- **核实**：计划 3.6、3.7、3.8 的双重上限；库 `serializeAuthorizationQuery`、`signParams`；库签名参数约有 `sig`、`exp`、`ba_iat` 与多个 `ba_param`。以实际长度作算术反例；尚未执行整条登录/同意链的临界值探针。
- **改法**：令入口限额与最坏情况下签名后续接令牌上限一致，或用固定长度的服务端句柄；超限应在授权入口跳回 `invalid_request`，不要在登录成功后静默丢失续接。对匿名登录、补同意、确认三条页面路径分别测临界值两侧。

### 6. 已关联账号若上游完全不返回邮箱，库在身份查找前拒绝登录

- **严重程度**：重要。**类别**：依赖库行为与账号恢复。
- **位置**：计划 3.4 的 Google `mapProfileToUser`、GitHub `getUserInfo`，3.10、第 9 节 P12；`site.accounts` 输出 12、16；Better Auth `callback.mjs:125–149`。
- **现象与影响**：P12 只测邮箱仍存在但未验证；邮箱缺失是另一条路径。非 link 回调在进入 `handleOAuthUserInfo`、按稳定 `(provider, accountId)` 查已有关联之前，就因 `userInfo.email` 为空返回 `email_not_found`。无密码且只绑定这个上游身份的用户因此无法登录。计划只要求注册时拒绝无邮箱，没给已关联身份适配。
- **核实**：Better Auth 1.7.27 源码控制流：`callback.mjs:125–149` 的邮箱必填在 `link-account.mjs` 中已有账号查找之前；未实测仿真上游删邮箱后的真实回调。
- **改法**：只对已按稳定上游身份找到的账号支持缺邮箱登录；不能伪造共用邮箱或退回按邮箱识别。以真实回调验证上游证明校验仍成立、未关联身份不会建号。若库限制使其不可支持，明确账号恢复路径并改写“已关联身份可登录”的合同。

### 7. 隐式 UserInfo 资源可绕过访问令牌行撤销

- **严重程度**：重要。**类别**：协议边界与撤销。
- **位置**：计划 3.4、3.5、3.6、3.8；改写稿输出 6、8、10；Better Auth `authorize-DXnMh0ha.mjs:1903–1921、2122–2141、2287–2298、2612–2647、7133–7167`。
- **现象与影响**：计划未拒授权或换码请求中的 `resource`。即使没有显式资源表，库也把自己的 UserInfo 地址视为隐式资源；授权码换取带受众的 JWT 时不写 `oauthAccessToken` 行。JWT 带 `sid`，库会在 introspection 与 UserInfo 检查会话是否仍有效；所以结束会话后会失效，不能概括成所有撤销均绕过。保留当前站点会话的自行改密会按账号撤销已有令牌行，却不会让这种 JWT 的 `sid` 失效；资源 JWT 的撤销端点也明确回 `unsupported_token_type`。客户端可在站点已承诺令牌失效后继续使用它至到期。
- **核实**：库源码分支相互印证；`/tmp/nbsite-spike/review-protocol.ts` 真实装配实测：UserInfo 资源授权换得 `200 Bearer`，introspection 为 `200 true`，revoke 为 `400 unsupported_token_type`，撤销后 UserInfo 仍为 `200`。这是保留会话时单条令牌撤销的直接探针，不等同完整改密端到端测试。
- **改法**：本站不提供资源指示扩展，在授权与换码入口一致拒绝 `resource`（或明确忽略并确保不签 JWT）；验收资源参数不能得到 JWT 访问令牌、改密后已有访问令牌失效、id_token 照常签发。把“允许的访问令牌均有可撤销的服务端记录”加进库升级清单。

### 8. 确认标识没有绑定确认页会话，也没有一次性消费

- **严重程度**：重要。**类别**：授权时序与交互合同。
- **位置**：计划 3.7、3.9；改写稿输出 5、14 与“状态与转换”；Better Auth `authorize-DXnMh0ha.mjs:205–300、7648–7662、8982–9005`。
- **现象与影响**：有效确认标识可在另一个会话中读取并提交；库以提交者会话写同意并给该用户发码，而非确认页显示时的用户。已拒绝或已同意的标识在有效期内仍可再次提交，未形成单次状态转换。
- **核实**：计划 GET 与 POST 检查都只验签、时限及客户端状态；`ba_pl` 仅用于 `postLogin` 判定，不是会话绑定。既有 `/tmp/nbsite-spike/out7.txt` Q1.2e 裸库探针实测另一用户会话可提交；不是最终装配端到端测试。
- **改法**：把确认标识绑定到显示确认页时的会话及单次授权决定，原子消费一次；对换账号、结束原会话、重复提交及同意/拒绝并发补行为验收。无效标识不得记同意或跳回客户端。

### 9. 社交注册时已关联身份的判断依赖注册码事务之外的查询

- **严重程度**：重要。**类别**：注册原子性与并发。
- **位置**：计划 3.10 `session.create.before` 注册意图判断、`account.create.before`、`claimUpstreamName`；`site.accounts` 输出 13。
- **现象与影响**：已关联身份可由钩子阻止建会话；但确认“没关联”后，Better Auth 在 `account.create.before` 返回后才插入 `account` 行。注册码消费、用户与资料在库事务内，而关联名与 session 又由钩子单独提交或库在事务提交后写入。并发时，注册回调可能把 social flow 判作可新注册，却在新身份抢先关联完成后继续创建账号和注册码消费，形成“身份已关联时不得注册”的竞态窗口。当前列出的验收覆盖一个已关联身份的顺序场景和并发注册码场景，没有“关联与注册同身份并发”。
- **核实**：Better Auth 1.7.27 `db/with-hooks.mjs:7–31` 表明 `account.create.before` 在 account adapter insert 之前执行；计划 3.3/3.10 明确关联钩子的写独立于库事务，注册钩子的写 join 到库注册事务。未实测注册与关联并发。
- **改法**：在身份名表上为注册认领与关联共用同一唯一约束/写事务，并在会话创建前确认注册赢得身份认领；或在身份冲突时让整个注册事务回滚。增加同一个上游身份的关联与注册并发用例，断言最多一个身份归属、失败注册码不扣、无孤立用户或会话。

### 10. 新版撤销记录无法覆盖旧版在回退时删除会话的动作

- **严重程度**：重要。**类别**：相邻版本兼容与撤销。
- **位置**：计划 3.2、3.5、第 5 节；`site.operations` 输出 7；t07 `session.ts:72–104`；Better Auth `authorize-DXnMh0ha.mjs:2663–2688`。
- **现象与影响**：迁移追加后旧程序仍能就绪，但旧版不会执行新版 OAuth 撤销 SQL。旧版结束会话只删 `session`，`oauthAccessToken.sessionId` 的 `ON DELETE SET NULL` 随之清空；新版对 opaque token 只在 `sessionId` 非空时检查会话，故回退窗口内登出的 OAuth 令牌切回新版仍可能有效。会话保留的自行改密更无法由旧版按新合同处理。未发现上线运维合同承诺能任意回退；这是兼容/回滚策略缺口，不主张已验证的进程级回退失败。
- **核实**：Better Auth schema 源码确有 `sessionId` 外键 `onDelete: "set null"`；既有 `/tmp/nbsite-spike/out7.txt` Q2 直接删会话后，新版 UserInfo 仍 200。迁移执行器允许新版账本的更大编号留在旧版库中；相邻版本合同测试在未设 `NB_SITE_PREVIOUS_SERVER_COMMAND` 时跳过。未跑真实旧版进程回退。
- **改法**：发布前明确回滚期望。若要求旧版回退期间会话结束后 OAuth 令牌仍不可复用，需要旧写方兼容撤销字段或发布先行兼容版本，并实测旧版写入、新版读取；若接受回退期间的令牌语义例外，写入运维合同并限制适用版本窗口。

### 11. HEAD 对外合同与授权端点实现不一致

- **严重程度**：重要。**类别**：协议互操作与端点合同。
- **位置**：计划 3.6、3.8、P1；改写稿输入表、输出 1、验收 2；Hono `hono-base.js:261–263`。
- **现象与影响**：Spec 说所有 GET 地址也收 HEAD，计划还把 HEAD 授权请求列入白名单。Hono 将 HEAD 分派到 GET handler 时仍保留 `c.req.raw.method === "HEAD"`；授权中间逻辑或 Better Auth 随后按 HEAD 查端点，实际转发可能回 404。JWKS 也可能由挂载方式决定不匹配 GET handler。反之，根发现由库显式支持 HEAD，但计划自家 well-known 子应用只登记 GET，最终行为不能从库根端点推出。
- **核实**：Hono 源码；本轮按 t07 的 `makeEnv` 启动 Better Auth 装配，裸 `/oauth2/authorize` GET 为 302、HEAD 为 404；`/jwks` GET 为 200、HEAD 为 404。库根发现 GET/HEAD 均为 200/200 且 HEAD 无正文；挂在身份前缀下的发现路径本来 404。另对带有效会话与 PKCE 的 HEAD 授权请求实测，入口回 404 且未生成授权响应；跟踪显示 Hono handler 收到 method=`HEAD`。这是 spike 装配，不是计划最终 mount。
- **改法**：只在能保持 GET 语义的路径上显式处理 HEAD：发现、JWKS 回同状态与头但不返回 body；对授权端点要么按合同也做 GET 等价并屏蔽副作用，要么从 Spec 与计划移除“授权地址收 HEAD”的承诺。最终通过实际挂载层逐项验收状态、头与响应体。

### 12. 错误响应路径绕过计划的 Location 归类，可能向用户暴露 Better Auth 错误页

- **严重程度**：重要。**类别**：错误路径与浏览器边界。
- **位置**：计划 3.8 第 4 步、`rewriteLibraryLocation`；`site.oauth-provider` 输出 3、失败与恢复。
- **现象与影响**：成功响应的 `Location` 会按登录、站点同意、OAuth 确认与库错误页分类；但 Better Auth 一些失败是先经 `redirectOnError` 直接扔出 redirect，而非从 `auth.handler` 返回普通 Response。计划只写“Location 交 rewriteLibraryLocation”，没有说明 Hono/Better Auth 抛出的重定向异常如何进入此分类。若错误码与授权查询参数可控，错误页可能穿过改写层到 `/api/identity/auth/error`；该地址在白名单中不可达，用户得到 404，或标准客户端拿不到预期错误码。
- **核实**：Better Auth `authorizeRedirectOnError` 与错误端点源码；`authorizeQuerySchema` 错误、部分非 `code` 类型及多处协议拒绝直接由错误跳转产生。既有 `spike7-mount.ts` 把授权路径的 `auth.handler` 直接 await，未显式捕获这类跳转异常；没有在计划最终 adapter/mount 上做异常传递探针。
- **改法**：明确挂载层接住框架 redirect/异常响应并将其规范化为 Response，再统一交 `rewriteLibraryLocation`；分别测安全回调错误应跳回客户端、坏客户端/回调不跳回客户端且落站点错误页，以及用户导航与 fetch 方式，确认库私有错误路由不外露。

### 13. social flow 未明确绑定浏览器，重放保护只绑定 state

- **严重程度**：建议。**类别**：安全边界与社交登录。
- **位置**：计划 3.2 `identity_social_flow`、3.10 `callback.ts`；`site.accounts` 输出 11、12、23 与时序第 100 行。
- **现象与影响**：流程表只有 state、intent、provider、payload、可选的 link session，没有发起浏览器的 Cookie/浏览器绑定。库自己的 state Cookie 仍由回调检查，但计划没有写明自家 flow 必须从同一浏览器带回且失败时不建立会话。回调 state 若被转发给另一浏览器，库的 Cookie 通常会挡住；但若该浏览器已有同一 Better Auth state Cookie、或响应流程分离后仅以 state 查到 flow，自家一次性认领自身并不能证明这次 callback 的浏览器就是 start 的浏览器。注册/登录意图可能在目标浏览器建会话。
- **核实**：计划 `identity_social_flow` schema 与 `callback.ts` 行为未见浏览器绑定；`site.accounts` 输出 23 只要求带 state 错误一律显示 social_failed，时序只写“回调时浏览器不是发起的那个”但没定义可验证的绑定。Better Auth 需要 state Cookie 是源码事实；没有构造跨浏览器同 state Cookie 场景的实测。
- **改法**：明确 state Cookie 是充分且唯一的浏览器绑定，写入 Spec 并用两个独立 Cookie jar 做完整仿真回调；或自家 flow 绑定发起浏览器的一次性随机值。验收从另一个浏览器回调时不发会话、不消费注册码、不关联身份。

### 14. 历史 OAuth 迁移与现有迁移合同的接缝未覆盖到回退行为

- **严重程度**：建议。**类别**：迁移与版本兼容。
- **位置**：计划 3.2 第 65 行、切片 2 与 8；`packages/nb-site-identity/src/migrations.ts`、`db/schema.test.ts`、`migrations.test.ts`、`nb-site-contract-tests/src/adjacent-version.test.ts`。
- **现象与影响**：迁移方案本身是增量 `0002`/`0003`，但现有账号包清单只含 `0001_init`；结构测试也只把库基准与 `0001` 对照。计划明确要扩这两处，当前无直接矛盾。未闭合的是端到端兼容：通用相邻版本合同当前只测遥测，本身未测身份迁移与 OAuth 表；环境变量未提供上一版命令时整组 skip，不算通过。计划切片 2 的“相邻版本能启动”被作为探针结果而不是新增合同验收，且未覆盖回退期身份写操作与 OAuth 撤销语义。
- **核实**：`identityMigrations` 只有 `0001_init`；`schema.test.ts` 断言清单仅 `0001_init`；adjacent-version 测试文件说明 unset 时跳过。计划 3.2、切片 2 与 8 规定新增迁移及 schema 覆盖；Task README 记有第 2 片一次临时相邻版本启动验证，但未记录重复为 t08 黑盒合同。
- **改法**：把迁移顺序与新表的现行行为测试纳入对应切片；对“相邻版本互换”明确是否属 t08 必须保持的合同，若是，给 identity 加真实前后版本迁移与登录/令牌行为合同；若只验新版本兼容启动，改写措辞，别把遥测的 adjacent-version 覆盖误当账号覆盖。

### 15. 站点称忽略 `claims`，实际授权决策仍把它送入库

- **严重程度**：建议。**类别**：协议合同与依赖库行为。
- **位置**：计划 3.8 第 2 步、第 9 节 P6；改写稿非目标、输出 3；`site.oauth-provider` 输出 23、失败与恢复；Better Auth `authorize-DXnMh0ha.mjs:8831–8835`。
- **现象与影响**：计划说去掉 `claims` 参数再交库；Spec 也说 `claims` 不起作用。但 P6 把“库收到 claims 时做什么”列为未来探针，没有把“删除参数”作为确定实现/验收要求。若照 P6 探明库会按 `claims` 约束 `acr` 或用户信息，再决定是否忽略，执行者可把客户端的 `claims` 当成有效输入，和公开合同矛盾。OIDC 允许 OP 不支持 claims 参数，但应按不支持的行为处理，不应一边宣称忽略一边让它影响授权。
- **核实**：Better Auth 1.7.27 解析 claims 并会因无法满足 essential `acr` 返回 `access_denied`；计划第 9 节 P6 明列待探 claims 影响。源码推导，尚无本轮具体 claims 请求探针。
- **改法**：将授权入口移除 `claims` 参数列为不可变实现要求，并将 P6 收窄为确认移除后库不见该参数；在黑盒合同里提交无效及 essential ACR claims，对比应与不带 claims 同样处理。发现文档 `claims_parameter_supported: false` 已由 Spec 禁止输出，不再暴露两套语义。

### 16. `response_mode=fragment` 的错误处理不能照改法要求一律 HTTP 400

- **严重程度**：建议。**类别**：协议错误语义。
- **位置**：本报告第 4 条改法；计划 3.8 第 2 步与授权失败码表；RFC 8414 §2、RFC 6749 §5.2。
- **现象与影响**：RFC 8414 的省略默认确实让授权服务器元数据声明 query 与 fragment；但 RFC 6749 §5.2 的 HTTP 400 `invalid_request` 是令牌端点错误响应合同，不直接规定授权端点响应必须 HTTP 400。授权端点的 OAuth 错误一般经可信 redirect_uri 返回，不能复用令牌端点状态码规则。第 4 条的机制错误在，建议中“按 RFC 6749 §5.2 用 HTTP 400”不成立，照搬会额外改变授权错误通道。
- **核实**：RFC 6749 §5.2 的适用场景是 token endpoint error response；授权端点错误见 RFC 6749 §4.1.2.1，可信 redirect_uri 时以响应参数回跳；本轮未实测本计划挂载下未支持 response_mode 的目标码。
- **改法**：Discovery 显式声明仅支持 `query`；在可信客户端/回调地址下以 `invalid_request`（或产品明确的其他适用授权错误）按协议安全地跳回，不可信客户端/回调则只去本站错误页。把错误码与是否允许 redirect_uri 的判定写入黑盒验收。

### 5. 入口接受的授权请求可以超出续接令牌的上限，正常登录后授权静默丢失

- **严重程度**：重要。**类别**：容量边界与端到端验收。
- **位置**：计划 3.1 第 2 条、3.6、3.7、3.8 第 2 步；改写稿输出 3、4、12、14。
- **现象与影响**：入口以原始查询串 `8192` 为界，续接验的是库追加签名字段后整段 base64url 令牌的 `8192`。仅 `state` 是 6500 个 ASCII 字符时，入口的查询仍可低于 8192，但编码后的令牌光这一个值就占至少 8667 字符，尚未算 `sig`、`exp`、`ba_iat`、`ba_param`。匿名或缺站点同意的用户可以看到页面并完成操作，却得不到继续地址；同样的请求若直接发码则能成功。
- **核实**：计划明确这两道阈值与编码方式；库 `authorize-DXnMh0ha.mjs:8944–8951、8993–9005` 保留 `state` 并追加签名参数。验收只压 8193 的入口拒绝、篡改、超时，没有证明入口接受的尺寸能走完需要页面的路径。
- **改法**：定义能贯穿原始授权、编码后页面参数、自家接口和继续地址的一组尺寸，或改成固定长度的服务端句柄；超出时在授权入口跳回 `invalid_request`，不要登录成功后丢授权。按实际上限两侧验匿名、补同意和确认，不只验入口的一侧。

### 6. 已关联账号如果不再给邮箱，库在按上游身份查找之前就拒绝登录

- **严重程度**：重要。**类别**：协议依赖与账号恢复。
- **位置**：计划 3.4（GitHub `getUserInfo`、Google `mapProfileToUser`）、3.10、第 9 节 P12；`site.accounts` 输出 12、16。
- **现象与影响**：P12 只测邮箱从已验证变未验证；邮箱完全缺失时不同。库在非关联回调里先要求 `userInfo.email` 非空，再进 `handleOAuthUserInfo` 找账号。已经关联的用户会被当成登录失败；账号若没有密码且只绑定了这一种上游，就没有另一种登录方式。
- **核实**：`callback.mjs:125–149` 的 `email_not_found` 在 `link-account.mjs:119–157` 身份查找之前；库的账户键并不需要邮箱。计划只规定注册拒缺邮箱，未给已有关联的这条路径做适配；旧探针未走邮箱被完全省略这一格。
- **改法**：只对已按 `(provider, stable id)` 找到的关联账号走无上游邮箱的登录；不能全局填同一个假邮箱，也不能按邮箱找主人。几种方案必须用真实回调证明仍共用上游证明校验且未关联身份不会建号。若库限制决定无法支持，先定恢复路径并修订「已关联就能登录」合同。补仿真上游撤掉邮箱后的登录用例。

### 7. 标准挂载放行库的资源扩展，访问令牌不保证不透明，也不保证可撤销

- **严重程度**：重要。**类别**：协议边界与撤销。
- **位置**：计划 3.4、3.5、3.6、3.8；改写稿输出 6、8、10；`authorize-DXnMh0ha.mjs:792–824、2122–2141、2287–2295、7133–7170`。
- **现象与影响**：`resource` 会被送进库。即使不配置资源表，库仍隐式承认自己的 UserInfo 资源。授权码流程一旦有资源受众且启用 JWT 插件，库就发 JWT 访问令牌，不写 `oauthAccessToken`。站点 SQL 撤销够不到这类令牌：例如自行改密码保留当前会话时，旧令牌仍可能有效；客户端也不能通过库的撤销端点撤销这种 JWT。
- **核实**：源码中的隐式资源、授权码的资源选择、令牌签发分支与 JWT 撤销出口相互闭合；既有探针的「不透明」只覆盖未带资源参数的请求，不证明这个不变量。
- **改法**：本站不提供资源指示扩展，在授权和换码两入口一并明确拒绝（或经合同约定一致忽略）；验收证明含资源参数时无法得到 JWT 访问令牌，并证明签名 ID Token 的能力不受影响。同一条「被允许的访问令牌一定有撤销记录」进升级清单。

### 8. 确认标识只验签和时限，没有绑定当时的会话或该次决定

- **严重程度**：重要。**类别**：授权时序与交互合同。
- **位置**：计划 3.7、3.9；改写稿输出 5、14 与「状态与转换」；`authorize-DXnMh0ha.mjs:205–298、8982–9005`。
- **现象与影响**：已签的确认标识在另一个有效会话中仍可读和提交，库会给实际提交者写同意并用其身份发码，而不是给显示确认页时的会话。`ba_pl` 只决定是否跳过 `postLogin`，不拒绝换会话。已经拒绝或同意的标识在有效期内也仍可再次决定；「待确认 → 已同意或已拒绝」实际上没有一次性的转换。
- **核实**：计划给 GET 和 POST 的检查清单都没有会话归属或消费记录；库先取当前会话，再按它写 `oauthConsent`。已有 `out7.txt` Q1.2e 实测裸走库的跨会话确认；该原型不是最终装配，也不单独作为结论。新计划虽加同意门槛，但仍不检查生产确认页时的会话。
- **改法**：区分可跨登录的续接和只属于当前会话的确认标识；将后一种绑定到会话和本次请求，原子消费一次决定。验收旧页面换账号、结束原会话、确认后重试及同意/拒绝并发；已失效的标识不给客户端跳转、不写同意。

### 9. 库的原样错误透传与模块自判错误共用一个通道

- **严重程度**：建议。**类别**：社交回调错误来源。
- **位置**：计划 3.10 `mapSocialError`；`site.accounts` 输出 23、验收 11；`callback.mjs:79–87、163–169`。
- **现象与影响**：模块保护了与自家码同名的参数，但把其余若干库码翻译成本站事实。库既用同一失败地址报告自己诊断的错误，也原样反射入站的上游错误；两者没有可辨来源。结果是未经模块判定的错误也能显示成「邮箱已被占用」或「身份已被关联」等站点结论。现有验收 11 只守直接写入自家码的情况。
- **核实**：库在验证 state 后、交换授权码之前直接把入站 `error` 交同一个 `redirectOnError`；模块映射用库 `Location` 的 `error`，帧没有记录这条分支的来源。与 Opus 已处理的「自家同名码不可信」不同，这是翻译后的别名也能混用。
- **改法**：先把上游输入与模块/库在本地得出的诊断分开；只从前者认标准的「取消」，其它归 `social_failed`，不拿上游输入走本站判断表。验收让仿真上游报告一个形同内部错误的码，确认只给通用失败。
