审查基线：固定副本 `official-site-rewrite.md`、`telemetry-stats-feedback.md`，仓库提交 `75b5ef4fc`。以下是设计与证据核对，不是对尚未实现链路的复现。

### 1. 注册码只证明了「存在才建用户」，没证明「只消费一次且消费成功才建账号」
- **严重程度**：阻断；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.5「注册」、4.8、4.9；t01「主会话的架构看法」第 5 条。
- **现象**：旧站要求注册码并发不双花，用户邀请码只记归因。两轮探针的 `REG-OK` 都是 `Set` 成员检查，从未消费；第二轮甚至用同一码先注册密码账号，再注册社交账号。没有规定码额度、用户行、凭据或上游身份、可选邀请归因在哪个提交点一起生效。
- **为什么是问题**：「先校验、交库创建、再扣额度」允许两个入口同时通过；反过来先扣，则用户名冲突、上游关联失败或中途退出会吞掉额度。两套入口各做一次检查、或把浏览器 `additionalData` 写进库的 state，都不提供数据库原子性。
- **如何核实**：读 t02 `better-auth-spike.txt` 62–97、`better-auth-spike-2.txt` 69–95、176–195；由主会话用真实 PostgreSQL、最终自家入口并发走密码注册与社交回调，断言末次额度只产生一个可登录账号、失败和重试不留下账号或误扣；导入后同样测已用码与仅有邀请资格的码。
- **建议改法**：两个入口共用一个服务端注册提交点，条件扣额度、创建用户及凭据／绑定、归因与同意凭据在同一事务；失败不发会话。先证明 Better Auth 的回调、适配器和钩子能共用该事务。不能时改上游选择：站点拥有账号开通事务，库只处理已开通账号的会话与协议；代价是显式接持久化适配与社交完成流程。换成仅提供注册前 webhook 的服务并不能解决原子性。

### 2. 「不按邮箱合并」没有覆盖账号绑定与人工找回
- **严重程度**：阻断；**类别**：安全与性能
- **位置**：`official-site-rewrite.md` 4.5「邮箱」「找回密码」、4.7 账号设置、4.9 占位邮箱。
- **现象**：第二轮 P1e 只证明一个返回 `emailVerified:true` 的仿真 GitHub 身份撞上未验证密码邮箱时没合并；没有证明所有提供方与验证状态组合都禁止合并，也没有走显式绑定、解绑或管理员重置。提案未指定绑定回调怎样固定「哪次操作、哪个已登录用户」；用户找回时又没有已验证邮箱可用作身份凭据。
- **为什么是问题**：邮箱由注册者自报；有注册码的人可先占用另一个人的唯一邮箱，后者的社交注册被挡住。即使不合并，若绑定只依赖回调时的当前会话，或客服把未验证邮箱当归属证明，仍可把登录凭据发给错误的人。导入的 `.invalid` 地址更不能用于找回。拒绝自动合并本身是必要取舍，不是所有权校验。
- **如何核实**：读 t02 `better-auth-spike-2.txt` 40–43、103–116、205–210 和提案账号设置；主会话应验显式绑定中会话切换/撤销、已绑定别人的上游主体、解绑最后一种登录方式、第三人只知道邮箱请求重置时均拒绝。
- **建议改法**：写清关闭库自动关联的配置和负向验收；显式绑定需由已登录且经过近期再认证的账号发起，回调绑定一次性、有限期的原账号／会话／提供方／用途，唯一键取提供方及稳定主体而非邮箱。未验证邮箱只作声明值，不作找回凭据；上线前选一种能证明归属的人工恢复流程，证明不足就拒绝，管理操作做审计，重置凭据一次性交付、不进日志。对邮箱先占造成的阻断给出不转移原账号的处理路径。

### 3. 两轮 OAuth 探针没有验证生产白名单，照字面挂载会丢失正常流程
- **严重程度**：阻断；**类别**：安全与性能
- **位置**：`official-site-rewrite.md` 4.4、4.5「库」「对外 OAuth 服务」、4.8、4.10。
- **现象**：两轮脚本都把 `GET`/`POST /api/identity/auth/*` 整段交给库；第二轮 83 是 API 描述里有 `path` 的项数，不是逐路由可达性的验证。P1 从库的 `/sign-in/social` 开始，P2 向库的 `/oauth2/consent` 提交；它们不是草稿允许直接开放的标准端点或上游回调。第一轮还签了 ID Token，但没验证对外发现文档能取到的 JWKS 和验签。
- **为什么是问题**：只按文字保留标准端点＋回调而不给这两步自家路由，登录开始或外部授权确认会断；直接放宽通配则让浏览器绕过自家入口的输入、来源、限流与审计策略。`Jar` 忽略 Cookie 的域、路径、Secure、SameSite，脚本还替每个请求填同源 `Origin`，不能证明真实浏览器的跨站回调和没有 `Origin` 的后端换令牌能走通。
- **如何核实**：读 t02 `better-auth-spike.txt` 19–25、134–145，`better-auth-spike-2.txt` 124–169、224–245；主会话对最终挂载（含部署代理）测公开方法＋精确路径的正反清单、合法的两种提供方回调、授权确认、无浏览器会话换令牌；若发布 OIDC，则从发现文档取公钥验签。
- **建议改法**：社交发起、授权确认经自家具名接口；把精确的方法＋路径、签发者及所支持的 OAuth/OIDC 能力写进合同，库升级时未列端点默认不可达。浏览器写入检查来源，协议端点按各自的状态绑定和客户端认证检查，不用一个同源规则挡全部；保留真实浏览器 Cookie 验收，不把探针当证据。

### 4. 旧哈希升级、密码重置、签发和撤销没有共同的生效顺序
- **严重程度**：阻断；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.5「找回密码」「会话」「密码」「对外 OAuth 服务」、第六节。
- **现象**：第一轮只验证 scrypt 验真／验错和封禁后的数据库会话；`password.verify` 只返回布尔值，没升级哈希。第二轮 P2 直接改库向一个已有会话的用户赋管理员角色，没有走「改角色使会话失效」；两轮未验管理员重置、改密或不透明访问／刷新令牌在撤销时的行为。
- **为什么是问题**：旧密码已验证但 argon2id 尚未算完时，管理员可完成重置和撤销；若随后无条件写回或按先前结果签发，旧密码能被恢复或旧登录能在撤销以后产生新会话。删 `session` 行不等于已签授权码、访问令牌和刷新令牌都不可用，封禁后 `/userinfo`、换码、刷新需分别定合同。
- **如何核实**：t02 `better-auth-spike.txt` 48–59、75–83、174–186、246–253；`better-auth-spike-2.txt` 212–218。主会话在最终入口验证登录与改密／封禁交错、升级只成功一次、当前及其它浏览器会话失效，以及撤销前签发的各类 OAuth 凭据随后能否使用。
- **建议改法**：哈希升级以已验证的旧凭据做条件更新；签发与封禁／角色／密码变更检查同一账号修订或在同一锁／事务下决定，过期验证结果不签发；数据变更、撤销和安全审计不得出现半完成。为授权码、访问令牌、刷新令牌分别定撤销和并发语义；若选择只撤站内会话，明确外部凭据剩余的授权期，不能用「立即失效」替代这项取舍。

### 5. 进程内限流没有定义统一键、状态上限或哈希过载行为
- **严重程度**：重要；**类别**：安全与性能
- **位置**：`official-site-rewrite.md` 4.5「密码」「限流」、4.10、第六节。
- **现象**：「按 IP 加用户名」未说明是交集键还是两个独立限额；应用同一账号还可用邮箱，社交注册在回调才提交。没有规定用户名／邮箱归一化、IP 的代理信任链、桶上限/清理，以及哈希并发用满后拒绝还是排队。两探针没有限流实验。
- **为什么是问题**：仅限组合键时，在同一来源变换用户名会不断开新桶，同一账号也可分散到不同来源与登录别名；仅限制哈希并发而排队无上限会把压力搬到内存。双栈、共享出口和重启丢桶会让看似相同的合同产生不同结果；这与「2 核 2 GB 不设硬指标」无关。
- **如何核实**：对照 t03 J、提案 4.5 与旧站验收来源 4.8；主会话对真实代理入口验证别名、失败账号、不同来源、两类注册以及限额耗尽／重启，观察拒绝、恢复和队列是否有界。
- **建议改法**：先定经可信代理得到的客户端来源、统一归一化及来源与账号的独立预算，再定进程全局哈希并发和有界等待/拒绝（含 `429` 或过载错误）；约束桶基数/过期并写明单副本、重启重置。对仍未分辨出账号的请求也有限额，错误不得泄露账号是否存在。

### 6. 匿名档的完整日快照可以区分安装并给跨日匹配提供线索
- **严重程度**：阻断；**类别**：安全与性能
- **位置**：`telemetry-stats-feedback.md` 4.1–4.2、4.7；`official-site-rewrite.md` 4.6。
- **现象**：「每项只有少数取值」不推出联合样本足够大。仅运行形态 3 种、大区 7 种、两个各 2 值开关、向导 3 种结果，笛卡尔积就有 252 格（不是实测分布），还没加版本、渠道、OS 大版、架构、语言、安装周和上报间隔。若小批预发布只有一份带某个稀有组合的报告，次日同组合、同安装周且间隔为 1 天，就提供了很强的关联线索。更换随机编号不能消除该线索。
- **为什么是问题**：看板不查原始表也挡不住默认档先收整条稀有记录并保留 90 天；只按单字段枚举限值或查询时抑制小桶不等于收集端匿名。这里证明的是设计没有保证，不是断言已识别任何自然人。4.7 还以「不带标识」直接排除一级的出境问题，与 4.1 承认一级组合可区分安装、合规调研第 1 节区分匿名化与去标识化相抵触；二、三级的境外收件也没单列判断。
- **如何核实**：人工构造稀疏相邻日样本并检查联合桶和可持久化的时间、请求元数据；对照 t02 4.2 字段清单、`2026-11-24-reporting-shapes-survey.md` 第 8 节（Brave 加了时间剥离、低样本抑制等条件）、`2026-11-24-terms-and-compliance-survey.md` 第 1、3 节。
- **建议改法**：保留不传持久 ID 的决定，反查每张图最小所需维度，删掉或拆开稀有维度组合，并明确小样本/预发布的禁止默认发送条件；无法证明符合默认档判据的数据移到同意档或不发。分别评估各档实际外发与存储，不把「无 ID」写成合规结论。

### 7. 只改代理访问日志不能兑现「不存 IP、不与账号关联」
- **严重程度**：重要；**类别**：安全与性能
- **位置**：`official-site-rewrite.md` 4.3、4.4、4.6、4.10；`telemetry-stats-feedback.md` 4.1、4.6。
- **现象**：草稿只约束反向代理访问日志和限流存内存；同一进程仍写 JSON 日志、同一主机还跑有账号会话的站点。没有约束代理默认虚拟主机与错误日志、超限/解析失败/上游超时、应用与数据库异常上下文、崩溃转储、持久化的请求 ID、精确接收时间、头或请求体。三级反馈之外的写入口也没写明拒收或剥掉 Cookie 与 Authorization。
- **为什么是问题**：这些都是落盘或事后关联渠道；禁止存表的字段与禁止 HTTP 链路留存并不等价。即使正常请求无 IP，错误路径和共用请求上下文仍能把地址或其它可关联元数据跟上报保存在一起；内存限流键不设上界和寿命，又会放大内存压力。尚无部署配置可据此断言哪项已经落盘。
- **如何核实**：按 4.3、4.6 画出从 Nginx 到数据库与日志保留的链路；由主会话以最终代理配置分别走成功、限流、非法请求、后端故障路径，查访问／错误日志、容器标准输出和库/备份，验证同源账号访问与写入域名不会共用可关联记录。
- **建议改法**：把来源 IP 限定在最早的可信限流点，有界、短期、不可持久化；转发给收件路由时不带地址、账号凭据或可关联追踪材料，落盘仅保留必要的粗时间和固定字段；对错误与默认路由实行同一禁止留存政策，运维日志只记类别和计数。接入新代理/CDN 或观察系统时把这些判据重跑。

### 8. 单向前迁移后，仅换回旧镜像不是数据库回滚
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.3、第五星「发布与回滚」。
- **现象**：启动前跑只往前的迁移；升级失败就换回上一镜像，数据导出只写了「升级前做一次」，没有恢复步骤或相邻版本兼容约束。就绪检查还要求「迁移已全部执行」，没规定旧进程遇到更新的迁移版本怎样判。
- **为什么是问题**：任何改名、删除或改语义的迁移提交后，旧镜像对的仍是新 schema；上一镜像即使启动，也可能误读或无法写入。启用新站写流量后直接恢复升级前的导出，也会抹掉其间的有效注册与更新。
- **如何核实**：对照 4.3 的执行顺序；由主会话在独立数据库演练「迁移已提交、就绪失败」与「已经接纳写入才发现问题」，检查旧镜像能否读写及还能保留哪些变更。
- **建议改法**：要求允许仅换镜像的升级保持相邻版本能读写（扩展、迁移数据、淘汰旧结构分发布）；对不兼容升级明确冻结写入、备份验证、恢复或向前修复的条件与损失。把 schema 版本的就绪判据也纳入兼容窗口。

### 9. 「问身份」只有成功或空，不能无差别替换为转发鉴权或令牌
- **严重程度**：重要；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.1、4.4、4.5、4.6、4.10。
- **现象**：查询只返回用户 id＋角色或空，没覆盖账号模块不可达、无效/过期凭据、角色正在变更，也没说明若身份检查续期，谁把 `Set-Cookie` 带回浏览器。当前身份判定用 Better Auth 的数据库会话；拆分后本地验短期令牌与每请求查会话的一致性不同。
- **为什么是问题**：把鉴权不可用映射为空会把故障当未登录，或误启用匿名退路；不查实时撤销状态的令牌至少有一段有效期，不能继承「封禁、改角色、改密码立即失效」。把库会话表、私钥或 Cookie 解析交给统计模块又违反所有权。第二轮的手写 Cookie 罐不是域、路径或续期的证据。
- **如何核实**：查 4.1 的唯一模块接口和 4.5 的撤销合同、t02 `better-auth-spike.txt` 8、246–253；主会话用同一套网关 HTTP 场景跑同进程与双进程：登入看板、续期、降级角色、撤销、账号服务不可达和客户端自带身份头，分别断言语义。
- **建议改法**：保持同一公开源及 Cookie 路径，只有账号模块持有会话及签发状态；把窄接口定成带匿名／已认证／不可用的判定，分别定义 401/403/503 和续期责任。若必须即时撤销，默认用可信入口实时转发鉴权、隔离内部地址且清除外来身份头；若改用有撤销延迟的令牌须另行改变合同。换语言还要明确已签发会话、授权码及令牌沿用还是失效，不把 HTTP 兼容等同数据兼容。

### 10. 合同包与被测服务的反向关系让增量 CI 漏掉黑盒套件
- **严重程度**：重要；**类别**：测试
- **位置**：`official-site-rewrite.md` 4.1 第 4 条、4.2、4.8；`docs/testing/README.md` 66、100–124、169–193。
- **现象**：按草稿，测试只在 TypeBox 合同包，被测实现依赖合同包，反方向没有依赖。现有 `test:affected` 从改动包沿「谁依赖它」选目标。只改账号实现、SQL 或入口且不改锁文件时，不会挑到上游的合同包；`--files` 也不跟只按路径启动的进程。4.8 说起真实 PostgreSQL，但当前 CI 的 `check` job 不准备数据库，也没有约定哪个编排入口启动/等待/回收三类进程。两轮探针用 `app.fetch`、直接 SQL 造状态、仿真 GitHub，不等于这套测试已可跑。
- **为什么是问题**：CI 可以在实现违反合同或迁移失败时仍绿；把测试进而默认放入无条件的通用快速任务，又没有数据库前置和失败时清理合同。只不依赖实现包无法约束脚本去导入实现，亦不能证明替身和 Google、GitHub 真实行为相符。
- **如何核实**：读 `scripts/ci/workspace-graph.ts` 33–60、`scripts/cli/test-affected.ts` 的 `selectAffectedTargets` 和 `.github/workflows/ci.yml` 的 `check`；主会话用仅改实现的提交做 affected 干跑，再在干净 runner 用当前/替换实现分别启动套件。
- **建议改法**：套件继续只接受服务 URL；将真实服务启动、迁移、管理员初始化、随机名测试库与仿真提供方的准备／收口放进外部编排。给 affected 与 CI 显式登记「实现、入口、迁移改动→合同测试」的验证边，或由入口包的集成命令调用合同套件；缺前置时报错，不默默跳过。替身补对真提供方的契约验收，普通 HTTP 合同与部署/导入测试分开。

### 11. 复用首次启动向导无法证明任何安装看过当前遥测说明
- **严重程度**：阻断；**类别**：不变量
- **位置**：`telemetry-stats-feedback.md` 4.1、4.5、第六节、第八节 11 月 24 日决定。
- **现象**：`runtime/desktop-shell.md` 输出 34 与当前代码显示，`FirstRunWizard` 仅桌面产品窗口出现，普通浏览器返回空浮层；`onSkip` 与 `onFinish` 共用 `close`，`nbook.desktop/first-run` 用户层记录只存 `{at}`，不能区分跳过、完成或展示了哪一版说明。已有桌面用户有旧记录，CLI 无窗口也不会经过这页。
- **为什么是问题**：把旧记录或关闭向导当作「已告知」会让升级用户或首步 Esc 的用户在未见通知时发送默认档心跳／日包；只等该向导又会让普通浏览器和无窗口运行永远不发。「展示前不发」也还没给默认档用户一个在首包前关掉的机会。把开关写入照搬现有向导逐项保存，会违背使用统计「完成才写、跳过保持关闭」。
- **如何核实**：读 `packages/neuro-book/src/plugins/desktop/web/first-run-entry.ts` 56–81、151–165 与 `first-run.ts` 26–50、240–250；发包验收覆盖两个同时打开的窗口、首步跳过／Esc、既有安装升级、普通浏览器、无窗口、保存失败或结果未知。
- **建议改法**：由遥测 owner 在状态根持久化「已告知的版本」与各档选择，不复用桌面完成标记；为哪些产品形态能完成告知以及何时能首发定义可观察条件，无法告知就不发。把完成、跳过、退出、已有有效选择和多窗口竞争区分开；只有确认且保存成功的使用统计设置才打开对应发送闸门。

### 12. 每日报告没有对齐「汇总日、去重键、提交结果和重算窗口」
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.6 109–113；`telemetry-stats-feedback.md` 4.2–4.6。
- **现象**：客户端读昨天的计数，字段未定义汇总日和时区；服务端只重算最近 2 天，随机编号只说明「重发去重」。没有规定编号何时生成/持久化、首包提交但回执丢失后重启怎样复用、同一天再启动时的状态、接受多迟的数据，以及部分拒收后重发怎样结算。
- **为什么是问题**：同一份报告提交后丢回复，重启用新编号会计两次；若按接收日汇总，离线 3 天补发落到错误日期，若按发生日却接受旧于两天的包，会出现已接收但看板永久不纳入。每日计数跨午夜或跨升级时，按发送时版本给旧计数贴标签也会误报。随机报告编号是重发幂等键，不是每安装每日的证明；在重试期间能连上同一份报告的各次尝试，应写清这个例外与寿命。
- **如何核实**：对照上报形态调研第 1、2 节（Glean 固定待发 ping 与 `document-id`、Go 逾期 7 天不再上传）及 `docs/testing/README.md` 22；主会话在真实链路丢掉已提交的回复、重启、改时区/时钟、离线三天补发并升级，用已公布看板和响应验证。
- **建议改法**：固定并持久化有界的待发快照（约定的日期桶、来源版本、清单版本、每份随机 ID）；约定允许乱序／迟到的期限，和聚合重算、删除、去重 TTL 一致。服务端原子地记录接受结果及幂等键，同键重发不重复接纳；规定未知字段、不合格项与重发的逐项回执/最终性或改整份接受；不把编号复用到不同报告，也不承诺防住新编号伪造。

### 13. 按月删除不能兑现原始报告保留 90 天，数据库导出也能延长保留
- **严重程度**：重要；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.3、4.6 113、4.10、第八节；`telemetry-stats-feedback.md` 4.6 131、4.7。
- **现象**：已定原始上报留 90 天，方案按月分区并整月删除。一份 3 月 1 日和一份 3 月 31 日的记录同一分区；等后者满 90 天再删，前者已留至少 120 天，反过来则后者只能约 60 天。方案另规定每晚导出整库，没规定导出是否包含原始行、何时淘汰、恢复时如何避免复活过期报告。线上角色只有自己 schema 的读写权限，没指定谁执行需 DDL 权限的建/移除分区。
- **为什么是问题**：时间上限、磁盘容量和谁有权履行删除承诺都不是「整月」自然保证的。删除热表也不会删除数据库导出的副本；靠运行时拿属主角色会削弱分权承诺。
- **如何核实**：按上面两个日期与 90 天承诺核对；主会话用部署角色、受控时钟和实际备份恢复合同，验证分区首末日、作业停启、过期副本与故障恢复，不用超管凭据蒙混。
- **建议改法**：按接收时间还是汇总日定一条保留时钟；若 90 天是上限，用日分区或先逐日删过期行再退月分区，别暗中放宽 30 天。选择明确的维护角色／任务；原始报告默认从通用导出排除，若确有恢复要求则让备份和恢复也遵守同一保留期限。

### 14. 工作区包的公开入口不是「两个实现绝不互相依赖」的检查
- **严重程度**：重要；**类别**：测试
- **位置**：`official-site-rewrite.md` 4.1 第 1、3、4 条、4.2 54–74；t03 20、35、73。
- **现象**：统计直接引用账号实现的公开入口，就满足「只经公开入口」，却绕过唯一的「问身份」接口。`scripts/ci/agent-governance-contract.ts` 332–339 的 `verifyPackageScriptBoundary` 只检查 `#scripts/`；457–465 检查 workspace 依赖是否存在、是否依赖新旧应用。`packages/neuro-book/src/architecture.test.ts` 109–125、213–216 查应用自己的导入，不能覆盖六个站点包。合同包不声明实现依赖，也不等于不能用相对路径导入实现。
- **为什么是问题**：同进程黑盒用例可以全绿，以后拔掉账号实现包时统计连加载都过不了；测试也可以从实现包取常量或夹具，让重写目标无法替换。
- **如何核实**：按上述检查的扫描范围跟一条统计→账号的公开导入，以及合同测试→实现源码的相对导入；让主会话在架构门禁的负例中确认两条都被拒，并从同一套 HTTP 用例针对独立启动的服务地址跑验收。
- **建议改法**：把依赖方向写成允许表并在脚手架验收机检：只有站点装配入口能同时依赖两份实现，调用方只消费相应合同，合同与其测试不引用任何实现；同时检查清单依赖、源码与测试的导入目标。地址、启动和初始化通过外部运行器注入，不经合同测试套件回引实现。

### 15. PostgreSQL 的 schema 名与连接池不能替代运行凭据和迁移权限验收
- **严重程度**：重要；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.1 第 2 条、4.3、4.8；t03 42。
- **现象**：只约定每模块一个 schema、角色与池。探针成功只能证明 Better Auth 在指定 schema 建表并运行；未证明运行账号不是属主、无另一角色的成员权限、默认授权不会把对象权限给错人，也未证明迁移、连接初始化与健康检查用的是预期凭据。`search_path` 决定未限定对象名怎样解析，不是权限边界；进程同时持有两池时也能在业务代码里协调双写。
- **为什么是问题**：用迁移账号跑黑盒可把越界依赖藏到上线；用错池时不是「必然报没权限」，而是可能用另一角色成功写入；日后拆库才发现跨模块数据或提交顺序依赖。反过来，权限真的收紧后，正常插入还可能因序列未授予使用权限而失败。
- **如何核实**：主会话用生产同款的非属主角色和真实迁移演练，测试双方可完成自己业务（包括自增 id），但不能读写对方表、用对方序列或创建跨 schema 外键、不能切换到属主；改变默认搜索路径以及重启重建连接再核对。权限负例独立于只走 HTTP 的行为套件。
- **建议改法**：模块只收到本模块池，迁移属主独立，不把迁移凭据注入常驻进程；明确 schema、表、序列及新增对象的授权清单和连接初始化；机检装配以外不得拿两池，运行权限测试证明同库隔离，不宣称一个进程里的角色是对同进程失陷的隔离。

### 16. 两个真实社交提供方的邮箱与身份形状未被所选通用 OAuth 路径覆盖
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.5 93–97、4.8、4.9；t02 第二轮 P1。
- **现象**：`better-auth-spike-2.txt` 40–42、112–115 的假 GitHub 总是给出字符串邮箱和 `email_verified:true`，映射直接读两者；实际 Github 登录不能假定公开资料带邮箱，代码也尚未有 Google 的稳定 `sub`、邮箱验证字段与预期发行者的用例。第一轮只证明 Better Auth 在没有邮箱时拒绝建用户，不证明必填邮箱政策下，两个真实提供方都能注册或已绑定者都能回登。
- **为什么是问题**：第一次登录无可用邮箱时可能掉进笼统错误并丢失注册上下文；老 GitHub 账号改邮箱或不公开邮箱时，若只按当前资料重新选择用户，会把可登录账号锁在补资料之前，或误走注册/关联分支。这不是已复现的提供方故障，而是探针覆盖缺口。
- **如何核实**：主会话按两家实际响应形状做独立协议夹具，再经授权各跑一次真实流程；分别覆盖首次登录无邮箱、私有/未验证邮箱、已绑定身份修改或隐藏邮箱、旧导入 GitHub 账号；核验旧数字 id 和会话主体不变。
- **建议改法**：把 provider 与该 provider 的稳定主体作为回登依据；确定首次注册可用邮箱的来源、请求范围和补填/拒绝流程，不把浏览器自报邮箱当上游已验证数据，不因资料变更重选已绑定账号。若通用适配器无法保留这些语义，先比较可替换 HTTP 输送下的原生 provider 适配与换库代价，再锁死选型。

### 17. 分档间隔和安装周不能直接产出草稿承诺的活跃、留存与同意率
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.6 110、115；`telemetry-stats-feedback.md` 4.2、95；w00053 t02 72–108。
- **现象**：不带 ID 时可以数「窗口内的首次合格报告」：前一次合格报告在窗口之前或从未有过，当前这份才加一；这要求知道前次所属日期或等价的窗口判定。例：窗口是第 10–16 天、当前是第 12 天，间隔 2 天不能加、3 天应该加；若放在同一档，看板无法区分。安装周只标 cohort，没给全体安装的分母；日包中开关开启占比也只代表发送日包的人，关匿名档者不在分母。一级分档的请求数和错误数只能估计整体失败率。
- **为什么是问题**：按天直接相加重复计数；重装／新状态根使首报数增加，一人多设备也算多份；离线首次补发、关闭再开启、时间回拨会改变「前一次」含义。服务端只能拒绝同一个报告 ID，无法识别使用不同 ID 的伪造报告。把曲线标成独立用户、全体安装留存或同意率会误导决策。
- **如何核实**：对照分档调研第 8 节 [Omaha 协议](https://github.com/google/omaha/blob/main/doc/ServerProtocolV3.md) 的独立活跃标记、日计数和成功应答后的状态；先用上述两种间隔外加重装、多设备、离线与无提交回执逐图推导，再把期望变成黑盒用例。
- **建议改法**：为每张图写明计量单位、日期窗口、估计式、分母和缺测，按第 6 条的隐私约束取最少信息；做不到时显示「有效报告/首报」「可观测 cohort 报告率」「日包内开启比例」，或去掉该图，不靠引入持久标识补救。

### 18. 15 分钟心跳计的是投递，不是同时在线人数，也不能列出账号设备
- **严重程度**：重要；**类别**：正确性
- **位置**：`telemetry-stats-feedback.md` 4.1、4.2 76、第八节 182；`official-site-rewrite.md` 2、4.6 109–115；w00053 t02 115、140–142。
- **现象**：服务端每收一条就给一档加一，心跳字段只有版本与运行形态。一个进程 12:00 发完即关、另一个 12:14 才开，两条都加在同一档但从未同时在线；重启丢失「本档已发」或提交后丢回复再发也是同样的增量。一个状态根上的多个窗口与项目子进程不等于多个安装；不同状态根又可并行运行。已登录设备是另一个既定用途，站点第一版又明确不做设备码、应用未接入站点登录。
- **为什么是问题**：不能从桶内增量反推出同时在线人或账号设备；服务端看不到该请求是本档第几次发、是补发还是新状态根，靠 IP 去重还会把共享出口的人合并。试图从这条匿名链路补设备列表会直接破坏不关联的决定。
- **如何核实**：主会话用真实部署接口与可控时钟验证同桶不重叠、边界前后、托盘无窗口、两个窗口、重启及回执丢失；看板读出的应是按已声明口径计算的桶值，不是测试按安装去数。
- **建议改法**：只有后端单一 owner 发，先定义托盘/后台是否计入；每桶本机持久化一次发送资格、只发当前桶、不追补；若要重发，复用仅在该桶有效的幂等键，否则明确选择少计而非重复。看板命名为「15 分钟收到的心跳数（运行状态根样本）」；用户的已登录设备留在独立的账号合同，明确何时交付，不借匿名心跳。

### 19. 按总清单暂停与按档开关之间缺少可执行的发送授权
- **严重程度**：重要；**类别**：不变量
- **位置**：`telemetry-stats-feedback.md` 4.1、4.3、4.5 123–126、第五节 159。
- **现象**：一级随匿名日包发，同时四个开关独立；没有规定「关匿名日包但开一级」「只关心跳」各发什么。清单一变全部停发，又只在「一级新增类别」时重取同意；已预览或排队的数据没有记录允许发送时的档级与版本。关闭再打开时，仍照记的本机日统计会包含同意前的数据。
- **为什么是问题**：如果权限只在生成快照时判，429/离线重试在撤回或变更后会把旧包发出；如果只读取最新开关，首次打开可把同意前的计数和崩溃事件带出去。「预览下一份原文」也可能展示一个新建样本，实际先发队列里的另一份。使用档新增一项不该不经定义就让未变的心跳在无窗口运行里永久停摆。
- **如何核实**：主会话用真实接收端覆盖四开关组合、首次同意前后、生成→撤回→重试、清单变更或回退后重启、预览和排队顺序；核对实际请求体及哪个档确实没有请求。
- **建议改法**：为各档分别记录当前告知、有效同意和生效边界，写出开关组合真值表；每次发送/重试前重验不可变待发快照的档、清单与授权，有变化清除或暂停待发副本，保留本机统计但不追溯已禁止的内容。定义在途请求与撤回的先后，预览同一份快照；只为受影响的档重走告知／同意。

### 20. 旧库逐字段导入、校验与失败重跑没有合同，条数相同也会改写身份与码的状态
- **严重程度**：阻断；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.5、4.9 134–138、第五节 160–164；w00037 t01 61–74、t02 第一轮 S1/S2。
- **现象**：t01 记录旧用户有可空密码、角色、状态、`sessionVersion`、头像和 GitHub 身份。草稿只列要导入的部分字段，没规定其余是有意不迁、如何保留，以及两种码的剩余额度、停用/过期状态、旧使用关系和邀请归因怎样逐项核对。探针只插一位有密码用户 `1000`，手动 `setval` 后创建 `1001`；没有覆盖空库、非连续 id、原本无密码的账号、被封状态及失败半程重跑。
- **为什么是问题**：条数相同，账号和 GitHub subject 也可能指到错误用户，已用码也可能复活，漏调序列则首个新注册就可能撞旧 id。占位 `.invalid` 字符串也不能当真实登录邮箱、已验证身份或人工找回凭据。
- **如何核实**：由主会话用 t01 字段与最小合成 SQLite 冻结副本做迁移验收：包含禁用用户、仅 GitHub 用户、有空洞 id、耗尽/部分用过的码；模拟导入中断，再通过密码/社交回登、下一次注册、码余额与邀请人查询核对。不需要接触生产数据。
- **建议改法**：先列旧→新的字段、状态、缺值和舍弃理由，按旧主键、上游身份与使用关系对账，不只数行；占位邮箱独立标记且不可用于认领/重置，协议约定回登与补填。离线在隔离库导入、检查并调到正确序列后一次交接；失败库有明确丢弃或重跑语义，不让导入半成品接流量。

### 21. 旧站切换需要成对归档，开放新站写入后也不是一次代理回切
- **严重程度**：重要；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.9 136–138、第五节 160–164；w00037 t01 63、68–74、t03 89–95。
- **现象**：旧站的工坊压缩包、加密备份在文件卷，SQLite 留引用。草稿没定义如何冻结所有旧站写者、取得一致的 SQLite 快照（包含已提交的 WAL 内容）与文件卷、校验引用及保留恢复所需的旧格式/配置。正文知道回切丢新数据，却无可回切的截止点和安全操作规则。
- **为什么是问题**：「不迁工坊」不等于可以只留 SQL；若快照与文件不在同一写入水位，日后有账号 id 也可能找不到文件。新站已经重置密码、封禁用户、消费注册码或改授权之后回旧站，不只是丢新注册：在旧数据/凭据没更新时，还可能恢复此前已撤销的访问或额度。
- **如何核实**：主会话在隔离副本演练有已提交 WAL、工坊文件和加密备份的一次停写切换及还原，逐一核对文件引用和校验值；另从新站刚开放写入的时点模拟回切，看禁用状态、旧会话/令牌与码余额的实际结果。
- **建议改法**：冻结写者，归档一致的数据库、文件卷、清单与可恢复所需的旧运行信息，密钥另按受控方式保留；演练读出代表性归档。只在新站仍封写且核对失败时允许直接回切；开放写入后默认向前修复，若必须回切，明确变更的对账、凭据失效、损失清单和授权人，不由健康检查自动翻回旧站。

### 22. 两个注册勾选没有覆盖社交回调、旧账号导入与同意证据
- **严重程度**：阻断；**类别**：不变量
- **位置**：`official-site-rewrite.md` 4.5 95–97、4.9、4.7 120、第七节第 4 项；`telemetry-stats-feedback.md` 4.7 137–143；w00053 条款调研第 1、7 节。
- **现象**：方案只有「条款/隐私政策」「境外存放」两处不预选的 UI 文案；社交流程由浏览器带注册意图回回调并在其间取上游资料，未定义哪一步先完成告知、怎样把两个独立选择绑定到这次注册和告知版本、回调重放/换版怎么办。旧库里的账号会在第一次新站登录前整体导入境外，无该流程。已引调研没有给出本部署数据接收方、适用出境路径或豁免的核实结果。
- **为什么是问题**：UI 无法证明服务端检查两个选择；把勾选放在回调取数或批量导入之后，也不能称为事前告知。「主机境外」不是由该调研得出每类数据具体适用路径的证据，两只复选框更不能证明出境前置条件已满足。
- **如何核实**：对照调研引用的[个人信息保护法](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)第 14、17、38、39 条；主会话在公开密码/社交接口验证缺任一同意、过期或重放、版本变更时无注册提交，再核对上游取数及旧数据导入的先后。
- **建议改法**：将两个版本化的选择及对应告知作为服务端注册前置，使用短期单次的注册流程记录，与获准建号同一提交留证，不信客户端布尔值。分别列出密码注册、社交开始和回调、存量导入、管理员初始化的数据流与适用门槛；生产开放和旧数据出境前由懂相关规则的人确认接收方、权利渠道及适用依据，不把补一段文案当审阅完成。

### 23. 远程计数批次未区分已入账、可重试与结果未知
- **严重程度**：重要；**类别**：不变量
- **位置**：`telemetry-stats-feedback.md` 4.4 109–117；`runtime/plugin-channel.md` 输出 5、6；ADR 0024 决策 1、3、4。
- **现象**：窗口与项目子进程各攒小批再发，但没有定义业务 owner、何时把批次从待发移走、何时停收以及跨午夜的归属。内核写 RPC 一旦派发后断线/超时就是 `unknown-outcome`，不自动重放；窗口卸载也不保证有序完成异步写。草稿只接受进程崩溃丢最后一批，没有处理正常刷新、重连和停止。
- **为什么是问题**：服务端入账后丢回执，重发普通增量会重复；派发后尚未执行就断开，一律丢弃则在重连时也少计，不只崩溃才少计。比如 23:59 的项目保存到 00:00 才送达，用接收日会画进错误的热力图；UI 和后端都记录最终成功还会多算。
- **如何核实**：主会话在真实两个窗口、项目子进程和后端，用可控时钟与链路分别切断入账前、后，跨午夜与退出边界，观察相同一次保存给出多少计数、在哪天，以及工作本身是否受影响。
- **建议改法**：各指标指定唯一发生处和日期桶，计数不得进入原业务的成功门槛；有界缓冲与截止的正常收尾归各入口资源。若要保住正常断线的计数，用仅本机的批次键、事务内记账去重和可查结果；若明确接受该路径少计，写明不重放、可见缺测和寿命，不按成功计无回执的批次。

### 24. 滚动字数快照和可关闭的请求追踪不是长期日统计的权威数据源
- **严重程度**：重要；**类别**：正确性
- **位置**：`telemetry-stats-feedback.md` 3、4.4 112、115；`runtime/projects.md` 输出 16、17；`agent/request-trace.md` 非目标与输出 9–11。
- **现象**：`projects.stats` 每项目只存最新总量和 `today:{date,baseline}`；跨午夜时换基线，没为昨天留历史行；未打开过的项目没统计，关闭的项目可能只有旧快照。模型请求记录可关闭、清空，默认只保留 14 天，漏掉 `complete()`、非内核会话和写失败；`harness/runtime.md` 输出 70 的会话总用量则会在 fork 新会话里重算复制历史。
- **为什么是问题**：每天读取「昨天」时，项目和模型两个输入都可能没有那天的值；关追踪但继续使用模型的用户会看到 0 或历史曲线断层；按会话总费用求和会把 fork 之前的真实请求算两次。直接复用项目完整快照，还会不必要地把其中的路径、片段名和正文摘要交进统计读路径。
- **如何核实**：主会话验证项目整天未打开、午夜前后修改、方言口径变更，与 Agent 关闭追踪、清空、fork、有实际用量的失败重发这几种场景；比对日历格、总量、失败率与源侧实际发生量。
- **建议改法**：由项目 owner 在日期切换前结算有日期的数值事实，区分未测、过期、真实零，不为补数私自打开作品；Agent owner 在真实尝试结算处提供无正文、按发生时计一次的数值，不回扫可关闭的完整 trace，也不叠加会话快照。明确 `complete()` 等不在统计范围还是另接其实际 owner；遥测只能读这些数值投影。

### 25. 本机统计「不联网」与「第三方不进清单」还没有可证的边界
- **严重程度**：重要；**类别**：不变量
- **位置**：`telemetry-stats-feedback.md` 4.4 105–117；`runtime/plugin-api.md` 的服务与贡献点；ADR 0027 决策 1–3。
- **现象**：现有 `packages/neuro-book/src/architecture.test.ts` 109–125、213–216 是导入方向检查，既不查直接 `fetch`，也不保证不经通用服务中转。允许第三方记本机指标，只按「声明过＋清单有同名指标」筛选时，没有绑定登记及记数调用方；带标签计数若允许任意标签，甚至内置指标也可能携带自定义 provider 名、项目名或错误文字。ADR 0027 明确同进程插件互信，不是沙箱。
- **为什么是问题**：一个新埋点可能通过启用默认档把第三方或自由字符串送上网，或者把网络能力作为统计依赖；也可能把可选的统计服务设为硬依赖，统计库坏了就让核心插件受阻。仓库现有测试不能证明上述情形被拒。
- **如何核实**：主会话用合法第三方与两个内置入口验证同名/越权记数及未列标签不会进入实际 HTTP 载荷；只装配本机统计、让网络不可用和统计存储失败，验证业务照常、统计退化可见，并给架构符号/依赖规则加确定会失败的负例。
- **建议改法**：按内核可验证的 owner 认领指标，绑定指标的记数来源、标签枚举与容量；只把白名单的数值投影交给遥测。允许统计软不可用，只有联网 owner 拿外发能力，明确检查本机统计及可达依赖的网络调用；用运行验收验证实际外发，而不声称能限制恶意同进程插件自行联网。

### 26. 崩溃与升级失败既可能没有产生计数，也可能被两条通道计两次
- **严重程度**：重要；**类别**：正确性
- **位置**：`telemetry-stats-feedback.md` 4.2 84、4.3、4.4 113、4.6；`official-site-rewrite.md` 4.6 109–115。
- **现象**：「失败处记数」覆盖不了失败前尚未起的服务端、被操作系统结束的进程；`runtime/desktop-update.md` 输出 1、8 和实现合同明确更新检查失败写壳日志，换上实际在壳退出后完成，成功/失败靠壳启动时对账，而且新版本起来后再崩溃不算换上失败。业务插件无现成统计出口可取代日志；同一个崩溃或升级失败又出现在日汇总与立即入口，没定两条账的关系。
- **为什么是问题**：只在后台插件捕获会系统性漏掉启动及更新阶段；把一个失败算在紧急图和日图，加总会变成两个。把所有未见干净退出都报成崩溃，会把系统结束和骤断算到错误的版本。若为补全而订阅所有诊断日志并上传，就越过 `runtime.diagnostics` 不联网及实例归属边界。
- **如何核实**：主会话分别演练项目异常退出、服务端强制终止、正常退出及更新助手失败后重开，核对从观察者到待发记录及看板只出现一次、记录正确版本；关闭一级时检查立即入口也不收到包。
- **建议改法**：以能观察结果的 owner 输出固定分类的数值事实（项目由宿主，更新由壳实际对账），定义未知结束和未再次启动等漏测；独立于查询诊断，使用有界的本地交接。指定日汇总唯一入账，立即入口只作告警，或用单次事件键做明确合并；不把立即计数误作二级崩溃详情。

### 27. Agent 的反馈草稿可以留在本机却永远无法审阅，确认也未绑定所见内容
- **严重程度**：阻断；**类别**：不变量
- **位置**：`telemetry-stats-feedback.md` 4.1 65、4.2 91、第六节、第八节 179；`runtime/plugin-channel.md` 非目标与输出 5；`workbench/notifications.md` 18–22、105。
- **现象**：提案写先落本机、右下角提醒，但没指定持久的待审阅入口、草稿与附件寿命、并发确认规则。通知只在本窗口的内存里，刷新会清空；Agent 可从没有前台工作台的运行发起；插件 RPC 明确不为等用户回答挂起、也不替写操作重放。
- **为什么是问题**：通知消失后草稿可能无法找到或删除；若工具等待确认会卡住对话；若把「已确认」和实际附件分开引用，另一窗口或日志变更可令上传内容不是用户看到的那份。两次点击、服务端接收后回执丢失可造成重复收件；把草稿正文回显为工具结果还会把内容带回模型上下文。
- **如何核实**：主会话验证工具只等本机接纳、无需在线窗口即继续对话；刷新、重启与换窗口后仍可审阅和丢弃；在审阅途中改附件、双窗提交、丢回复重开，核对无确认时无请求、有确认时仅收到所见快照。
- **建议改法**：反馈 owner 提供有界的本机草稿登记与可重新进入的待审阅视图，通知只链接草稿；Agent 只得草稿已落地或失败的结构化结果，不能调用提交。明确 `draft`／已确认待发／发送结果未知或成功／撤回的转换，用草稿修订和拟发快照做并发判定，不对不同内容沿用确认；幂等尝试及回执同一份内容绑定，显式决定失败是否需用户重试。

### 28. 「永不收」与诊断、反馈附件冲突，二级自动发送没有可执行的脱敏合同
- **严重程度**：阻断；**类别**：安全与性能
- **位置**：`telemetry-stats-feedback.md` 4.1 64–65、4.2 89–95、4.7、第五节；`runtime/diagnostics.md` 26、79–89 与 `agent/request-trace.md` 22。
- **现象**：三级允许日志、截图、对话片段，「永不收」又列对话内容、正文、文件名、密钥等。二级只写去用户名路径与堆栈；去掉 `/home/<用户>/` 后还可能留下项目目录、文件名；栈函数名、外部错误码或操作序列也不是天然的有限枚举。诊断 Spec 的日志脱敏是本机防误用，不是可直接导出的授权，模型请求记录明确不进诊断包。
- **为什么是问题**：允许把日志或图片原封附上就无法保证密钥永不外发；若按「永不收」字面全拒，又做不到已承诺的主动附对话。二级自动档没有逐次审阅来补救脱敏失误，复用本机日志或异常全文会把更高档内容交给境外收件。
- **如何核实**：主会话对不同档检查真正发出的字节，在路径、堆栈、错误、截图和对话各放合成金丝雀；测试去除失败、取消附件、配置/模式变化、人工确认前无上传和二级开关不启用三级；不使用真实秘密。
- **建议改法**：把自动采集禁项与用户逐次选择的内容例外写成互不矛盾的合同；若不能保证截图等不含绝对禁项，明确限制附件能力或收窄承诺。二级独立构建白名单诊断投影，路径只交有限的类别/已知代码符号，未知内容丢弃，失败不发送；三级对不可变附件逐项预览、确认并限制大小和保留，不自动导出完整日志或请求记录。

### 29. 第一版与二阶段没有定义收件不可用时的开关和告知
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 第二节、4.6、第八节 191；`telemetry-stats-feedback.md` 第二节、4.1、4.5、4.6、第五节；w00037 t03 24、107–109。
- **现象**：站点第一版只收日包、心跳和立即计数，诊断详情、反馈、问卷在二阶段；应用方案则同时列出自动发送诊断的开关、崩溃询问与反馈，匿名日包甚至记录诊断自动发送开关。没有约定 app 先发布或服务器回退至第一版时的行为；三个写入口中唯一类似的是一级崩溃计数，合同明确只带错误码与次数。
- **为什么是问题**：用户可能勾选一个目前没有收件人的功能；若保存这份勾选，后来的客户端或服务器回升就可能把旧诊断上传到同意时未告知的收件模块；若为了不报错把详情退化发到一级，混掉分档和授权。一直重试不存在的端点也违背「关闭即停」与本地可用优先。
- **如何核实**：主会话以 V1 和含二阶段收件的两个真实服务版本验证客户端前后互配，检查明确禁用／未就绪的可见状态、404/503 后的收口及上线恢复后不自动追送过期草稿和旧诊断。
- **建议改法**：写客户端、站点与说明的发布先后和降级矩阵；无该档收件能力就不提供可生效的自动发送授权、不发请求，一级只保持自己的计数；主动反馈可保留明确的本机草稿，等收件合同可用后重新审阅与确认，已有安装不从「功能未开放」推导任何同意。

### 30. 清单版本若只用来丢未知字段，聚合会混合不同口径的同名指标
- **严重程度**：重要；**类别**：正确性
- **位置**：`official-site-rewrite.md` 4.6 112–115；`telemetry-stats-feedback.md` 4.2、4.5、4.6。
- **现象**：两稿约定清单带版本，旧站接收新客户端时丢弃不认识的字段，却没说旧服务端如何处理「认识名字但不认识这版定义」；长期聚合未列定义版本。例如 v1 的 `medium` 是 10–99 次，v2 改成 5–49 次，同字段、同枚举都可过结构校验。
- **为什么是问题**：分档结果不可还原为原值，两个桶一旦混进同一长期趋势，原始数据 90 天删掉后也无法拆回；缺失、不合格或未同意的指标若计成 0，还会造成发布后使用率凭空下跌。
- **如何核实**：主会话向同一服务发送这两种版本，以及未知版本、部分缺失和真实零的日包，走完整聚合与看板；旧版本不应以旧定义接受或解释新语义，图上应能解释口径变化。
- **建议改法**：为指标固定定义和桶，语义变更新增可区分的指标版本；服务端只对已登记的定义校验及聚合，长期表带足够的口径标记，图上断开不能比较的序列。兼容未知字段只适用于已知语义不变的增量版本，不把未知、拒收和缺测转成零。

## 两份提案「七、待定项」逐项判断

**官方站重写**

1. **OAuth 签发者地址**：可以在隔离探针里临时取值，但应在第一次公开发现文档前定下 HTTPS issuer、路径与发现文档、令牌的对应关系，不等外部客户端先接入（第 3、9 条）。
2. **异地备份**：不能以注册量作为决定点；首次承接不可重建的生产数据前就要定恢复目标以及可验证的离机副本，或由开发者明确接受单机损坏时的数据损失，并排除不该长期保留的原始报告（第 8、13、21 条）。
3. **图表库**：同意到看板切片再选，先确定每张图的观测对象、分母和可比较的口径，库的体积其次（第 17、18、30 条）。
4. **境外数据的出境条件**：把数据流、接收方、告知、单独选择与适用路径或例外的核实列为生产开放和存量导入前的门槛，不只审隐私政策的这一节（第 6、22、28 条）。

**本机统计、遥测与反馈**

1. **同意率过低**：允许先看日包发送者中开关开启的比例，但不把它叫全体同意率，也不因样本小就把行为项移入默认档，迁档须重新证明该字段组合满足默认档判据并告知（第 6、17、19 条）。
2. **面向欧盟分发的默认档**：不能靠本机时区大区决定适用范围，[EDPB 2/2023 指南](https://www.edpb.europa.eu/system/files/2024-10/edpb_guidelines_202302_technical_scope_art_53_eprivacydirective_v2_en_0.pdf)第 33、34、44、56 段讨论设备信息外发但不判具体豁免，因此在确认实际分发范围和适用依据前不对未确认场景默认发（含心跳），不是对当地法律作结论。
3. **调查问卷**：同意和主动反馈安排在第二阶段，可以共用收件但须分别定义邀请、提交同意及保留，不把问卷藏成首阶段匿名日包的绑定能力（w00053 t04 是设想；第 27–29 条）。
4. **是否另找人审条款**：需要在外发或导入前按实际数据流核对哪些默认档和哪些授权档能上线，覆盖标识、IP、接收地、附件、保留和撤回，而不是仅审一句「存放在境外」（第 6、7、13、19、22、28 条）。

## 未发现问题的方面

- **第一版不拆进程，也不把机器规格与并发数当硬门槛**：仔细检查后没有发现与开发者决定冲突；第 9、10、14、15 条针对可拆分和可验证的承诺，不要求现在拆服务。
- **旧功能的兼容范围**：仔细检查后没有发现两稿漏掉已确认的非目标；不保留 llmlint 的旧 OAuth 合同，工坊、云备份和设备码可暂不可用，符合 w00037 t01 68–74；归档与身份连续性另见第 20、21 条。
- **桌面自动更新与官方站解耦**：仔细检查后没有发现两稿要求把更新检查迁到本站或让它依赖遥测开关；这与 ADR 0051 决策 6、`runtime.desktop-update` 的 GitHub Releases 更新源一致，能否获得升级计数是另一问题（第 26 条）。
- **OpenRouter 应用归属与站点遥测分开**：仔细检查后没有发现两稿把它接进统计模块的约定；与 w00053 t02 23 及遥测稿第八节一致。
