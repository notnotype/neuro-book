# 拉远看审查：w00037 t03 官方站重写 与 w00053 t02 遥测提案
审查者视角：刚加入的架构师；只读。引用的“官方站提案”“遥测提案”指 /tmp/review-w00037-w00053-design/ 下的固定副本（与仓库 docs/proposals/ 同名文件同提交 75b5ef4fc）。

### 1. 第一版的账号、OAuth 服务、社交登录与旧站迁移没有消费者，却和唯一有客户端的遥测捆在同一个交付里
结论：这是整套方案里最大的范围问题（问题 1、3）。第一版里真正有一个“客户端”的只有遥测的三个写入口；账号一侧的大块功能在第一版里没有使用者。
依据：
- 官方站提案第 44 行：新应用没有任何调用官方站的代码；第 101 行：OAuth 服务“第一版没有真实的外部客户端”，只做到合同测试走通；第 137 行：切换后工坊、云备份、旧应用设备码关联全部不可用；第 28 到 31 行非目标：不做市场、备份、设备码、发布、论坛。也就是旧站里账号存在的理由（工坊发布、备份、设备关联）在第一版全部被关掉了，迁过去的账号登录后能做的只有“改资料、进管理面板”。
- 账号一侧的这些功能没有一项被某个已存在的使用者要求：Google 与 GitHub 登录、对外 OAuth 服务与授权确认页、邀请码链、必填邮箱、账号设置里的“已关联账号”。遥测只需要“管理员能看看板”。
- 它们带来了遥测用不到的合规与上线门槛：Google 登录上线要公开主页、同域隐私政策与 Search Console 验证（官方站提案 4.7）；账号数据在境外要单独告知并单独勾选（4.5，遥测提案 4.7，出境条件“没有核实”）；邮箱“必填、唯一、不验证、不发信”（4.5）：第一版收集了邮箱这类个人信息，却没有任何一个功能会用它，只是因为库要求非空（w00037 t02 README 的“要迁就的地方”第 1 条）加开发者定了“账号要邮箱”。
- 旧站真实账号数没有记录：官方站提案第三节只写“不能假定只有站点所有者一个账号”。在本仓库的 w00037、Task 128 与两份提案范围内没查到实际注册人数。迁移命令、占位邮箱、scrypt 兼容、`.invalid` 标记这一整条链路的大小取决于这个数；如果是个位数，手工重建或按需导入更便宜。
建议（作为候选交开发者，不是我替他定）：
- 先取旧站的账号数与最近登录数，再决定导入范围。
- 把第一版切成“遥测服务端加一个够看板用的管理登录”，Google、GitHub、OAuth 服务、邀请码等在第一个真实消费者（市场、备份、同步、应用内登录）出现时再加。Better Auth 的探针已经证明这些之后能加上，推迟没有技术风险。
- 如果开发者坚持第一版就做全，提案至少应写明：每一块账号功能在第一版服务谁。现在的写法只有“开发者定了”，没有用户价值的描述。

### 2. “重写”与“PostgreSQL”两个底层选择：给出的理由一条已过期、一条随方向变了、其余没有记录；为“以后拆开”预付的成本没有触发证据
结论：问题 1 与问题 3。底层选择当初的理由现在不一定成立，提案没有回头查。
重写本身：
- 官方站提案第 17 行把“旧站的前端依赖用链接方式引 nb-ui，干净构建机装不上”列为理由，并引 Task 128。但 Task 128 自己在 .agents/tasks/128-neuro-book-site-deployment/README.md 第 164 行已定“首轮用锁定 Git commit 的依赖、`bun.lock` 固定”，同一份记录的状态行写着 `deploy:server` 已经过真实 push、Actions 与两轮固定摘要升级。这条理由在旧站里已经解决过，它支持的只是“代码放进 monorepo”，不支持“重写”。
- 其余理由是“不再背历史包袱”“以后要拆、要换语言”（官方站提案第 12 到 14 行、w00037 README 2026-11-23 条）。在 w00037、w00053 与 Task 128 范围内没查到旧站的一个具体缺陷记录（性能、安全、维护事故）；旧站仓库也不在本机工作区（../neuro-book-site 不存在），提案里“2026-11-24 读取”的结论无法复核。这是开发者的明确决定，我不质疑决定，但提案应写成“偏好与以后的扩展”，不要把已过期的构建问题当作根因。
PostgreSQL：
- 官方站提案 4.11 末条给的理由全部是为拆进程服务：按模块分 schema 与角色、分区表、以后多个写者。代价是常驻 200 到 300 MB（估算）（第 154 行），占 2 GB 机器的一成以上，并且是本 monorepo 第一次引入 PostgreSQL（在 docs 与各包 package.json 范围内没搜到别处使用；`.github/workflows` 里没有 services 或 docker 步骤，CI 要新增容器）。
- PostgreSQL 的来历在 w00053 的第一份调研 research/2026-11-23-telemetry-feedback-and-stats.md 第 111 行：选它是为了与 Cloudflare Workers 经 Hyperdrive 互通、“零 SQL 方言迁移，无需从 D1 SQLite 迁库”。w00037 README 的 11-23 条也是在“可兼容 Cloudflare”的前提下推荐 Hono 加 PostgreSQL。现在 Cloudflare 路线已经降为“可选外层”，这条根因理由基本不成立；w00037 t02 的选型只比了身份库与访问层，没有比 SQLite。
- 分区表：原始上报只留 90 天，按每个安装每天一份算，即使一万个安装也只有九十万行；按日期索引删除足够。没有量级证据支持提前分区。
- 真正只有 PostgreSQL 才有的好处是“运行时角色只有自己 schema 的权限”，它的收益也是以后拆分时才兑现。
建议：把“为拆分预付”的项分成便宜与昂贵两类。公开入口、每模块独立的表前缀或 schema、合同测试黑盒，几乎没有成本，保留；独立数据库角色与连接池、分区表、PostgreSQL 本身，需要在提案里写出触发条件，或者先用 SQLite（旧站就是；Better Auth 支持 SQLite，我凭记忆写，本次未核对）起步，拆分触发时再换。至少补一段 PostgreSQL 与 SQLite 的对比，并把“Cloudflare 兼容”这条已过期的来历从理由里去掉。

### 3. 默认就发的匿名档：“不可识别”的前提没有对本产品的人群规模验证，备选里也没有“全部选择加入”这一档
结论：问题 1、2、4。整套遥测的合规立足点是“匿名档不是个人信息，所以不用同意”，这个前提是本提案最重的一块承重墙，却只有断言，没有按真实人群规模核对。
依据：
- 遥测提案第 68 行断言“每一项只有少数几种取值，合在一起也不足以把一个安装从人群里区分出来”；而第 70 行在解释为什么一级要同意时承认“用户不多时组合起来有可能把一个安装区分出来”。同一份文件对“用户不多”的判断前后不一致：匿名档每天一份里有应用版本、渠道、运行形态、系统及大版本、架构、语言、大区、距上次上报天数、安装所在周、两个开关状态、向导结果（第 72 行起）。对 NeuroBook 这样处于预览期（PROJECT-STATUS.md 记 0.11 预览，桌面版刚在 w00046）的小人群，这些维度组合后很可能每个安装独一无二；而“安装所在周”加“距上次上报几天”恰好让同一安装的多天上报可以被串起来（原始上报留 90 天）。
- 个人信息保护法第七十三条把匿名化定义为“无法识别特定自然人且不能复原”（w00053 t02 README 第 118 行起自己引的），提案并没有做任何检验，比如对“版本×系统×语言×大区×安装周”算最小组大小，或服务端对小组做合并。没有这个检验，“默认发、不用同意”的结论站不住，而错了的后果是默认开启的出网信标。
- 备选一节（遥测提案 4.8）只比较了随机安装标识、默认勾选、事件流、谁提供埋点、Umami。没有比较两条常规做法：Go 工具链的全部选择加入（w00053 research/2026-11-24-telemetry-tiers-survey.md 第 41 行，经公开讨论后从默认开改为选择加入），以及同一份调研里的 Obsidian（第 98 行：完全无遥测，且作为卖点）。NeuroBook 是本地优先的长篇写作工具，作者对“应用在后台联网”的敏感度有别于 CLI 工具，这个产品层面的取舍没有被讲出来。
- 没被讲到的数据质量问题：这个仓库自己就有大量开发、e2e 与多个 worktree 实例，容器与临时状态根会让“新增安装”虚高；提案没有写开发与测试环境如何保证不发（“运行形态”只是一个上报字段，调研里 Homebrew 的“是否 CI”是同类做法）。写入口没有登录、不能验证，看板上的数字只能当参考，提案也没有写明这一点。
建议：
- 在提案里补一个小实验（用候选字段对一批假想人群或现有安装算最小组大小），并选一种做法：服务端按最小组合并或丢弃，或把匿名档里区分度最高的字段（安装所在周、大系统版本）挪到同意的一级。
- 4.8 补一条“全部选择加入”与“不上报、只用 npm 与 GitHub Release 下载数估规模”的备选，并写明不采用的理由；如果是开发者定的，写成决策记录。
- 写明开发、测试、CI 的静默开关归谁、怎么由机检守住。

### 4. 应用侧的“三个插件加指标登记框架”先于任何要回答的决策；一级数据只代表少数同意者，却承担了框架里的大部分复杂度
结论：问题 3。收集的是“能回答的问题”清单，不是“要做哪个决策”清单。
依据：
- 遥测提案 4.4 在第一版就定了：三个插件、四种指标类型（计数、带标签计数、耗时分布、里程碑）、每个内置插件在合同里声明指标、指标 id 前缀规则、按“日期、指标、标签”的本机存储、遥测只读接口、收集清单与声明的双重过滤、第三方插件可记数但进不了清单、跨进程攒批、架构测试守“不联网”。这是一个小型指标库。
- 它的消费者是什么：一级使用统计（4.2 里八大类、几十项）默认不勾选，提案和 w00053 t02 README 第 94 行自己写了“同意的人可能只占一小部分，结论只代表同意的人”。w00053 t02 的“能回答的问题”表（第 72 到 94 行）是按数据列出能回答什么，没有写哪个具体产品决策在等这个答案。开发者对用户自己看的统计明确说了“其它图不是重点，先有底层数据”（w00053 README 11-24 条）。
- 已有的权威数据源不需要新框架：字数来自 `projects.stats`，token 与费用来自请求记录（提案 4.4 自己承认“已经有权威数据的不重复记”）。给用户看的日历热力图与模型用量，只需要“每天一个快照”的存储，不需要指标登记与四种类型。匿名档的字段本来就“来自运行时信息，不经统计插件”（4.4 末句）。
- 和这份框架一并带来的是重新同意的流程负担：清单每变一次版本，客户端暂停上传直到重新告知，一级新增类别要重新取得同意（4.5 末条）。同意率本来就低，这条会让每一次新增指标都付一次同意率的代价，与“埋点由各内置插件随手加”的设计方向相反。
建议：
- 提案里写出分阶段：第一阶段只做匿名档的每日上报与心跳加给用户看的本机统计（快照存储，直接读现有数据源），不做指标登记框架；等第一个一级指标真的有决策在等时，再用那个指标倒推框架的最小形态。
- 一级的清单从“能收”改为“每一项写出对应的决策”，没有对应决策的不进清单。这样同时缩小了告知文字、隐私政策与重新同意的面。
- 在线心跳（每 15 分钟、默认发）要回答的是“此刻多少人在线”；对一个本地写作应用，这个数字能支持什么决策没有记录。心跳是匿名档里持续联网频率最高、对用户感知最强的一项，建议同样要求写出决策，否则先不做。

### 5. 统计看板自写：否掉现成工具的理由与第一版范围不匹配，没考虑“聚合表加通用看板工具”
结论：问题 2。
依据：
- 官方站提案 4.11 否掉 Umami 的理由是“事件属性限 500 字符、不适合承载以后的反馈文本”。但反馈与问卷在第二阶段、是第三个模块（官方站提案第 37 行与 4.6 第一句），第一版的遥测数据是每天一份计数汇总，与 500 字符无关。这条理由对第一版不成立。真正不适配的原因更可能是 Umami 的模型（网页访问、会话、逐条事件，靠 IP 与 UA 的哈希认访客，见 w00053 research/2026-11-24-reporting-shapes-survey.md 第 56 到 60 行的 Plausible 与 Umami 一节）与“每日预聚合、不存 IP、距上次上报几天”的形态不合，但提案没有这样写。
- w00053 的第一份调研（research/2026-11-23-telemetry-feedback-and-stats.md 第 90 与 136 行）曾推荐“薄网关加 Umami，今天就能做，不必等官网重写”。后来改成落在官方站里自写，开发者的决定见 w00053 README 11-24 条，但没有记录为什么放弃“先用现成的看到数字”这条更快的路。
- 提案里的聚合表本身就是普通的关系表（官方站提案 4.6）。对它直接接一个通用的看板工具（Grafana 一类，只读角色，看板配置文件进仓库）是更省的做法：看板里的八类图（活跃与新增、留存、在线、版本与平台、同意率、功能使用、Agent 用量、错误与耗时）几乎都是时间序列加分布。在 w00037、w00053 范围内没搜到 Grafana 或 Metabase 的评估记录，所以这是个“没评估过”而不是“评估后否决”的候选。代价需要核实：内存（2 GB 机器上再加一个常驻进程）、与自家管理登录的对接、中英双语与 nb-ui 风格。如果开发者要的是“看板在管理面板里、与站点同风格”，那是产品要求，应当写成要求而不是靠“Umami 装不下”来推出。
建议：提案补一段，写明：看板自写还是用通用工具，取决于“要不要在站内、要不要与 nb-ui 同风格”；并把第一版的图表范围缩到开发者当前真的会看的几张（活跃、版本、同意率），其余等数据积累后再加。

### 6. 以后难回头的几处：数据格式与同意绑在一起、分档写死在客户端、账号库的表形状，以及“拆分时合同不变”只守了 HTTP 一面
结论：问题 4。没有发现“现在就走进死胡同”的设计，但有四处锁定值得在提案里明说，并各写一条退路。
1. 分档边界写死在客户端的每日上报里。字数、项目数、耗时、token 都在客户端分档后才发（遥测提案 4.2），已发出的数据无法重新分档；改边界等于断开时间序列。提案 4.3 承认“事后不能换一种方式分析”，但没有写“分档表也是公开合同的一部分，边界变更按版本处理”。建议：收集清单里每个分档字段带分档表与版本，看板按版本分段显示，并写进 Spec。
2. 收集清单版本与同意绑定（遥测提案 4.5）：每次新增一级类别要重新同意，这把“清单能不能变”变成了用户界面问题，会反过来阻止产品演进，也让第 4 条所说的框架更难用。需要在提案里写明：新增匿名档字段是否也要重新告知，以及哪些变化只是“细化分档”、不触发重新同意。
3. 账号库的表与令牌形状。Better Auth 拥有表结构、会话与令牌的存放（w00037 t02 README 记“建出 12 张表”）。合同测试守住的只是 HTTP 一面（官方站提案 4.8）。以后换库或换语言，需要迁的是：密码哈希（有 scrypt 与 argon2id 两种前缀）、第三方账号关联、OAuth 客户端与已发令牌；会话可以丢。提案没有写这份“可迁出清单”，只写了“整体换实现靠合同测试守”。建议写一段：哪些表是自己拥有的稳定形状（用户 id、用户名、邮箱、哈希、关联），哪些是库内部的，并让导出命令存在于第一版（旧站导入命令是一次性的，它的反方向没有设计）。
4. 邮箱占位值。旧账号导入时把邮箱填成以 `.invalid` 结尾的占位并“打标记”（官方站提案 4.9），占位值进了非空唯一列；以后改成“邮箱可空”或要发邮件验证时，要先清理这批值。标记字段的名字与语义最好在第一版就定成稳定合同。
另有一点：官方站提案 4.1 说“拆分时对外合同不变”，但统计模块依赖账号模块的方式是“同源会话 Cookie 加进程内问身份函数”，拆分时换成转发鉴权或令牌。浏览器一侧不变，没问题；但管理看板这一类“管理员才能读”的统计接口，鉴权形状（角色、状态）也是合同的一部分，建议“问身份”函数的输入输出写进账号合同包，现在只写在 4.1 的文字里。
已经处理好的、我认为方向对的：遥测写入口单独域名（客户端里的地址改不了，这一条有证据）；OAuth 签发者地址要在第一个外部客户端接入前定死（已作为待定项）；合同包不依赖实现包。

### 7. 细节写得很深，几个该讲清的架构取舍没有讲：客户端失败语义、数据可信度、单机上的拆分触发条件、遥测由谁运营
结论：问题 5。两份提案对账号一侧的实现细节很具体（Cookie 属性、哈希并发、限流键、会话失效规则，官方站提案 4.5 与 4.10），这些属于 Spec 与实施计划；而下面几项是架构层的取舍，目前缺位或只有一句话。
1. 客户端失败与负载形状没有设计。“按整 15 分钟的时间段每段至多发一次”（遥测提案第 76 行）让所有在线客户端在整点与一刻、半刻同时发心跳，在 2 核机器上形成周期尖峰；每日上报的发送时刻也没写抖动。没有写：失败后的退避、离线积压的上限、时钟错误的客户端怎么处理、重发与“每个安装每天至多一份”由谁保证（服务端不能，因为没有标识）。这些决定服务端的限流与去重语义，是合同的一部分，该在提案里定个原则，细节留给 Spec。
2. 数据可信度的取舍没有讲。写入口无登录、无标识，任何人可以伪造上报；提案只在第五节写了“无法按安装去重”。应写明：看板数字的定位（趋势参考，不作指标考核），以及伪造的上限（限流与体积限制能挡到什么程度）。
3. “出现下面任一情况再拆”（官方站提案 4.1 末段）的触发条件都是定性的。建议至少给统计写入对登录延迟的观测口径（同一进程里两个模块的请求耗时分开记），否则触发时机只能靠感觉；这是第一版就该埋的观测点，成本低。
4. 谁是个人信息处理者。官方站提案 4.5、遥测提案 4.7 都写了“境外存放要单独同意”“出境条件没有核实”，并说条款“不是法律意见”。这是方案能否上线的前置，不只是文字问题：如果结论是出境条件对本站不成立，账号档的设计（注册时收邮箱）要整体变。该项在两份提案里都是待定，建议提高到“上线门禁”级别，并放在写账号模块实现之前问，而不是上线前问（官方站提案待定项第 4 条把它排在最后）。
5. 提案归属：两份提案在仓库里相互引用，遥测提案的“服务端”一节与官方站提案 4.6 在内容上重复了写入口、保留期、聚合方式三段。以后改一处漏一处的可能性高；建议让遥测提案只写协议与合同（收集清单与写入口语义），官方站提案只写落点，并让合同包成为唯一真相。
