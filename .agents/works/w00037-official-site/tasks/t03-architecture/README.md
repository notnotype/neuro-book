# 架构细节讨论与提案

## 目标与范围

与开发者逐项讨论第一版的架构细节（包与目录、进程与部署、地址布局、账号模块、统计模块的结构、模块间接口、前端、合同与测试、旧站数据导入、安全与运维），定稿后写成提案。

合同：只做讨论与提案，行为合同未变；提案接受后新建官方站的 Spec。

## 当前状态

2026-11-24：开发者对讨论稿答复“A：为什么没有 nb-site-identity 的 contract；其他全部同意”。主会话据此改了 A（见下），把讨论稿写成提案草稿 [官方站重写](../../../../../docs/proposals/official-site-rewrite.md)（`draft`）。提案还没交审查、没请开发者接受。

对 A 的修订：原稿只给统计的事件 schema 单独成包，账号模块的合同放在实现包的子路径里。这样实现包换语言重写或删掉时，前端依赖的合同会跟着没。改为两个模块各有一个合同包（`nb-site-identity-contract`、`nb-site-telemetry-contract`），合同测试也放在合同包里：合同包不依赖实现包，测试没法 import 被测代码。原来的 `nb-telemetry-contract` 并进 `nb-site-telemetry-contract`。

主会话的理解（待追认）：“其他全部同意”包含上一轮列出的两处倾向，即沿用旧站的两种码、第一版不发邮件。

2026-11-24 稍后：按 w00053 的讨论结果改了提案的统计模块一节（每日上报、在线心跳、立即事件，不带标识，原始上报留 90 天），加了三个公开页面（主页、隐私政策、服务条款）与注册时对境外存放的单独同意；反馈与问卷的收件列为第二阶段的第三个模块。

## 讨论稿（2026-11-24；开发者同意 B 到 K，A 已按上面修订，以提案为准）

### A 包与目录

- `packages/nb-site-identity`：账号模块。入口 `.` 交出 Hono 子应用、“问身份”的函数与迁移；`./contract` 是它的接口 schema，不带服务端依赖。
- `packages/nb-site-telemetry`：统计模块，同样的两个入口。
- `packages/nb-telemetry-contract`：事件的 schema，只依赖 TypeBox；NeuroBook 里的遥测插件与统计模块都用它。
- `packages/nb-site-server`：进程入口，只做装配（读配置、建连接池、挂模块、健康检查、迁移命令、管理员初始化命令）；镜像与部署脚本也在这里。
- `packages/nb-site-web`：前端。
- 用包当模块边界，是为了让仓库已有的“跨包只经公开入口”的检查直接生效。备选是一个后端包里分目录，另写架构测试。

### B 进程与部署

- 一个 Bun 进程加一个 PostgreSQL，Docker Compose；反向代理用生产主机上已有的 Nginx。
- 前端的构建产物打进同一个镜像，由这个进程发静态文件（改了上一轮“由反向代理发”的说法）：接口与页面永远同一个版本，升级与回滚都是换一个镜像。
- 镜像在 CI 里从 monorepo 构建，主机上按固定摘要升级；升级前导出一次数据库，健康检查不过就换回上一个镜像。
- 迁移是每个模块自带的纯 SQL 文件，只往前；进程启动前由入口命令执行。迁移用属主角色，运行时每个模块用只能读写自己 schema 的角色。
- 配置只来自环境变量，启动时校验，缺密钥就不启动。日志是 JSON，写标准输出。

### C 地址布局

- 同一个域名：`/` 前端；`/api/identity/v1/*` 账号模块自家接口；`/api/identity/auth/*` 只放行标准 OAuth 端点与 Google、GitHub 回调；`/.well-known/*` 发现文档；`/health/*`。
- 统计的写入口单独一个域名（如 `telemetry.nbook.notnotype.com`），第一版指向同一台机器。发出去的客户端里地址改不了，单独的域名让它以后能独立搬走。
- OAuth 的签发者地址与端点路径在第一个外部客户端接入之前可以改，之后不能，接入前要定死。

### D 账号模块

- 库用 Better Auth；登录、注册、资料、管理这些接口写自家路由、内部调库；库自带的路由只放行标准 OAuth 端点与社交登录回调，其余不挂。
- 登录方式：用户名或邮箱加密码、Google、GitHub。
- 注册一律要注册码；Google、GitHub 首次登录不自动建账号，先填用户名与注册码。
- 邮箱：新注册必填、唯一，第一版不发验证邮件。因为本地邮箱没验证过，不按邮箱自动合并账号：社交登录的邮箱撞上已有账号时拒绝，提示先登录再到账号设置里关联。
- 第一版不发邮件，所以没有自助找回密码，由管理员在面板里重置。
- 会话存数据库，封禁、改角色、改密码都让已有会话立即失效。
- 密码：新密码用 argon2id；旧站的 scrypt 哈希照验，登录成功后换成 argon2id；哈希限并发。
- 对外 OAuth 服务：客户端只能由管理员在面板里登记；授权码加 PKCE、授权确认页、不透明访问令牌、可选的刷新令牌。设备码流程等 NeuroBook 应用要接登录时再加。
- 管理接口：用户列表与搜索、封禁、改角色、踢下线、重置密码；注册码与邀请码；OAuth 客户端；管理操作留一张审计表。

### E 统计模块的结构（收集什么在 w00053 t02 讨论）

- 写入口收一批事件，不带登录；每条事件带客户端生成的 id，重发不重复计数。
- 事件名与属性按登记表校验：不认识的事件名丢弃并计数（新客户端不被旧服务端拒掉），属性不合格只拒那一条。
- 原始事件表按月分区，留若干个月后整月删除；每日聚合表长期保留，看板只查聚合表。
- 不存 IP，IP 只在内存里用于限流。
- 网站自身的访问量统计、Agent 与用户的反馈收件箱不在第一版。

### F 模块之间的接口

只有一个：统计模块声明它需要一个“问身份”的函数（给请求，返回用户 id 与角色，或空），由进程入口把账号模块的实现接进去。统计模块不 import 账号模块。

### G 前端

- 一个单页应用：登录、注册、社交注册补全、账号设置（资料、邮箱、密码、已关联的 Google 与 GitHub、会话）、OAuth 授权确认页、管理（用户、注册码与邀请码、OAuth 客户端、统计看板、审计）。
- Vue 3、Vite、vue-router、nb-ui、Tailwind 4，与仓库里其它前端一致；中英双语，沿用仓库的消息目录做法。
- 接口类型直接取模块 `./contract` 里的 schema，不做代码生成。
- 界面按仓库的设计评审流程走：先出静态稿与评审板，开发者定了再实现。图表库到做看板时再选。

### H 合同与测试

- 合同测试起真实进程、真实 PostgreSQL 与仿真的 Google、GitHub，只用 HTTP；每个测试文件一个随机名的库。
- 造状态只经公开接口、管理接口与管理员初始化命令；与时间有关的用环境变量把时限配短，等可观察的过期状态。
- 旧站五份集成测试里的场景（注册码并发双花、封禁、限流、OAuth 流程等）当作验收场景的来源。
- 行为写成 Spec（`docs/specs/` 下新开官方站一栏），验收编号对到合同测试。

### I 旧站数据导入

- 一次性的导入命令：只读旧站的 SQLite 快照，写进新库。
- 导入：用户（id、用户名、显示名、角色、状态、时间不变；邮箱填占位值并打标记，登录后提示补填）、密码哈希、GitHub 身份、注册码与邀请码及其使用关系。
- 不导入：会话（所有人重新登录）、设备码与令牌、旧 OAuth 客户端与令牌、工坊、备份。后几样连同文件卷原样留在快照里。
- 先在副本上演练并核对条数；切换是停旧站、取快照、导入、起新站、改反向代理；退回是把反向代理指回旧站。
- 读生产快照与切换都是生产操作，动手前另取开发者授权。

### J 安全与运维

- Cookie 设 HttpOnly、Secure、SameSite=Lax；改状态的请求核对来源；只信任来自反向代理的转发头；请求体有上限。
- 遥测由 NeuroBook 的后端进程发出，不从浏览器发，写入口不开跨域。
- 登录按 IP 加用户名限流，注册按 IP 限流；第一版记在进程内存里，拆进程或多副本时要换成共享存储。
- 第一个管理员由命令行创建，密码从标准输入读。
- 数据库每晚导出一份留在本机；要不要异地备份另定。

### 补充探针

为核对报告里关于库行为的几条，并看改用 SQLite 是否可行，跑了第三轮探针（[evidences/better-auth-spike-3.txt](evidences/better-auth-spike-3.txt)）：

- SQLite 上能建出同样的 12 张表、保留数字 id 并接着发号、用旧 scrypt 哈希登录。
- Opus 第 2 条属实：普通用户调库的建客户端端点得到 201。
- Opus 第 3 条属实：管理员改角色、重置密码后，那个用户的旧会话仍有效；旧密码不能再登录。
- Opus 第 5 条属实：本地邮箱已验证时第二个上游被自动并入；打开 `disableImplicitLinking` 后被拒。
- Opus 第 4 条只部分属实：用户名被转成小写后撞唯一约束，以库的内部错误收场，没有出现只差大小写的两个用户名并存。

## 开发者对审查后待定项的答复（2026-11-24）

原话：“入库即聚合先不接受，留 7 天吧，现在还在开发，没做大规模的上限，我们要哪些聚合还不太清楚。境外存放和‘匿名档算不算匿名化’这两处找谁确认先不确认。其他的都同意。”

据此：

- 遥测的原始上报留 7 天后按日删除，不改成入库即聚合；大规模上线前再定。
- 境外存放与“匿名档算不算匿名化”先不找人确认，作为已知的未核实风险留在两份提案的待定项里。
- “其他的都同意”对应主会话给出推荐的几项：数据库用每个模块一个 SQLite 文件；遥测按阶段做；给诊断加一个只给本机的观察接口来按错误码计数；第一版的范围先查旧站的账号数再定。
- 查旧站的生产库是生产操作，主会话没有把这句“都同意”当成授权，动手前另问一次。

### 第四轮探针（SQLite）

数据库定为 SQLite 后补探（[evidences/better-auth-spike-4.txt](evidences/better-auth-spike-4.txt)）：

- 注册码表与身份库的表放在同一个库文件里，在建用户的钩子里做“还有额度才扣”的更新：社交注册因用户名重复而失败时码没有被扣（与建账号在同一个事务里回滚）；一个额度的码 8 个并发注册只成功 1 个、额度只扣 1 次。
- 对外 OAuth 的完整流程在 SQLite 上走通（授权、登录续接、确认、换令牌、`/userinfo`、授权码重放被拒）。
- 封禁之后，此前发出的访问令牌调 `/userinfo` 得到 401。

[t02](../t02-selection/README.md) 里“数据库访问用 Kysely 加 `pg`、合同测试用 PostgreSQL 容器”的结论被这里取代：身份库直接用 `bun:sqlite`，合同测试每个文件一个临时目录。
