# NeuroBook `ui` 工具实测结论与改进建议

## 一、实验概况

本次测试围绕 `eval` 环境中的 `ui` 工具（`ui.find`、`ui.snapshot`、`ui.highlight`）展开，实际演练了两个典型引导场景：

1. **场景一：引导添加表情包**（逐步拆分为多次 `eval` 调用）
   - 路径：活动栏「设置」 → 设置分区「表情包」 → 拍局部快照 → 高亮「新建表情包」并说明用法。
   - 暴露问题：每步单独走一次模型往返，体感延迟明显；`ui.find` 仅索引到 `settings.section` 层级，无法直接定位页面内按钮。
2. **场景二：引导配置 API Key**（尝试在单次 `eval` 内串联多步）
   - 第一段 `eval`：`ui.find` 查入口 → 探测当前进度 → 串联导航进入「服务商与模型」 → 拍设置弹窗局部快照。
   - 第二段 `eval`：一次串联 5 步 `until: "next"` 高亮讲解（服务商列表 → API 密钥 → 接口地址与协议 → 检测与启用模型 → 模型角色），支持上一步/下一步与容错回退。
   - 插曲与发现：用户在第 1 步高亮期间顺手点击了「添加服务商」弹出子弹窗，导致第 2 步高亮「API 密钥」时等待约 5 秒后抛出 `not-found`，但错误信息未说明当前已有新弹窗遮挡。

---

## 二、核心实验结论

### 1. 能否一次性把所有 `highlight` 步骤做好？

- **技术上可以，无需等工具改版**：在单次 `eval` 内编写循环，将 `ui.find`、进度探测、多步 `ui.highlight` 串联执行，并将 `timeout` 调大（如 600 秒）。用户点完一步后下一帧即可切换下一步，**步骤间几乎零延迟**。
- **真正需要拆成两段的原因是“信息依赖”而非工具无法串联**：
  - **标准设置项（现在即可 1 次跑完）**：如 `ui.find` 已经给出完整 3 步 `path`（设置 → 分区 → `settings.row`），Agent 无需中途看快照，一次 `eval` 即可从头导到尾。
  - **复杂自定义页面（目前通常需 2 次）**：如「服务商与模型」「表情包」这类自定义交互页，`ui.find` 只索引到分区级别；Agent 在打开页面前不知道内部控件名称与布局，必须先导航并拍一次快照，读懂页面后再串联页内引导。
  - **动态分支场景（固有边界）**：当用户中途触发了未预期的子弹窗，或页面状态依赖前置数据（如服务商列表为空需先新建）时，回交模型重新观察界面是合理的。

### 2. 用户中途手动关掉菜单或点开新弹窗会怎样？

- **高亮挂起期间关闭父容器**：目标消失，`ui.highlight` 返回 `outcome: "gone"`（或因点到关闭按钮/外部先返回 `missed`）。
- **步骤切换间隙关闭父容器**：下一步 `ui.highlight` 等待约 5 秒后抛出 `ToolCallError`（`code: "not-found"`）。
- **在 `until: "next"` 期间点出新弹窗**：底层表单被遮挡或卸载，下一步同样干等 5 秒后报 `not-found`，且 Agent 从报错中无法直接得知出现了新弹窗，只能额外补拍快照排查。

### 3. 要不要自动获取 `snapshot`？

- **结论：不要默认全量自动附带，应坚持“按需 + 局部”获取。**
- **原因**：
  1. **Token 开销大**：全窗口快照常达 1500~3000 token，包含大量无关的侧栏、编辑器标签、历史会话等噪音。
  2. **中间步骤无需求**：沿 `ui.find` 的 `path` 导航时使用稳定的 `{ target, key }`，不需要快照。
  3. **时机易失真**：点击后界面可能处于动画或异步加载中，立刻自动快照容易拿到半成品。

## 三、给 `ui` 工具的改进建议

### 1. 返回值与错误详情中默认附带轻量 `layers` 摘要（高优先级）
- 在 `ui.highlight` 的正常返回值和 `not-found` / `stale-ref` 等 `ToolCallError.details` 中，附带当前窗口的层级栈（如 `layers: ["base", "dialog: 设置", "dialog: 添加服务商"]`）。
- 仅几十个字符的开销，却能让 Agent 瞬间判断“菜单是否被关掉”或“用户是否点开了新弹窗”，大幅减少无谓的排查快照。

### 2. 加深 `ui.find` 目录粒度，为自定义页面补充稳定定位（高优先级）
- 目前普通 `setting` 可索引到 `settings.row`，但自定义复杂页面（服务商与模型、表情包等）只停留在 `section` 层。
- 建议将自定义页面中的核心表单项与操作按钮（如 API 密钥输入框、添加服务商、检测全部、新建表情包、导入 zip 等）也纳入 `ui.find` 目录并赋予稳定的 `{ target, key }`，使高频流程也能 1 次 `eval` 一镜到底。

### 3. `highlight` 增强对新层出现与误触的感知
- **`until: "next"` 期间出现新顶层弹窗**：可考虑及时感知或在 `next` 返回时标记层级变化，避免下一步干等 5 秒才报 `not-found`。
- **区分“误触”与“主动偏离”**：提供可选参数（如允许误触时不立刻销毁气泡、仅提示/抖动），降低引导脚本处理 `missed` 的复杂度。

### 4. 支持可选的轻量局部快照 / 等待条件
- 可为 `ui.highlight` 增加可选参数，例如 `waitFor`（对应 `find` 里的 `appears`）和 `snapshotScope`（到达后顺手返回指定小范围快照），在“按需局部”的前提下再省一次工具调用。

### 5. 更新 `docs://eval/ui.md` 的用法示范
- 文档中“一步一次调用，按结局决定下一步”容易误导 Agent 按“每轮回复调一次 `highlight`”来写，造成严重卡顿。
- 建议明确推荐：**“在单次 `eval` 中通过循环串联完整引导路径，仅在用户提问（`asked`）、中断或需阅读新页面时交回模型。”**
- 也可在 `docs://` 中为高频配置流程提供简明界面路径参考，减少首次探索成本。

## 四、给后续使用 `ui` 工具的 Agent 的实战经验

1. **一条引导，一次 `eval` 跑完**
   - 将 `ui.find` 与 `while (i < steps.length)` 的 `ui.highlight` 循环写进同一次 `eval`，调大 `eval` 的 `timeout`（如 `600` 秒），避免每一步都回模型空转。
2. **先探测进度，跳过已完成步骤**
   - 开导前先检查 `path` 上各节点是否已经处于打开/选中状态（例如设置弹窗已打开、目标分区已选中），从当前实际所在步骤起跳，避免重复框选已打开的入口。
3. **内置状态机回退，不要遇错即崩**
   - `outcome === "back"`：索引减 1，重新高亮上一步。
   - `outcome === "gone"` / `missed` 或抛出 `not-found` / `stale-ref`：短暂停顿后重新探测当前停留在 `path` 的哪一步并回退重亮；仅当连续多次偏离（如 3 次）或点击了关闭按钮时退出交回模型。
   - `outcome === "asked"` / `dismissed` / `timeout` / `window-gone`：立即退出循环并返回结构化状态，由模型回应用户。
4. **优先用 `{ target, key }` 定位，少用临时 `ref`**
   - `ref` 跨重渲染容易触发 `stale-ref`，而 `ui.find` 提供的 `{ target, key }` 稳定可靠；仅在页面无稳定 `target` 且确定未重渲染时使用 `ref` 或带 `within` 的 `{ role, name }`。
5. **拍 `snapshot` 必须限定 `scope`**
   - 已知目标位于某个弹窗、侧栏或面板内时，务必传入 `scope`（如 `{ role: "dialog", name: "设置" }`），可减少 70%+ 的无关 token；需要阅读提示说明文案时再开启 `includeText: true`。
6. **确保 `eval` 最后一行显式返回结果**
   - 用统一的状态对象记录结束原因、所在步骤、用户提问或最终局部快照，并在脚本末尾直接输出该对象，避免 `if/else` 分支导致返回“（没有输出）”而不得不额外补查状态。
