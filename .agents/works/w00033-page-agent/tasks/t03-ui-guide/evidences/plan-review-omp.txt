### 1. 订阅成功不代表高亮装上，建立中的订阅也还不能退订
**严重程度**：阻断；**类别**：正确性。
**位置**：计划“nbook.page-agent”第 64–65 行、Spec 输出 9、11；`packages/nb-runtime/src/remote/node.ts:635–681,882–946`，`peer.ts:150–170,216–245`；`docs/specs/runtime/plugin-channel.md:51,97`。
**现象**：内核先 `channel.accept()`，然后才调用窗口的 `handler.subscribe()`；窗口在其中等目标至多 5 秒，也可能还在加载。若服务端等 `subscribe` 成功就暂停时限，查找和加载被错扣；若只接“结局”事件，服务端收不到应开始暂停的时刻。查找失败若从异步 handler 抛出，只得 `onEnd(provider-error)`，不是 `not-found`。首个事件或 `onEnd` 还可能早于句柄返回。建立期间没有内核截止，公开 `subscribe` 也不收调用方 `signal`；`Promise.race` 只停止等待，拿不到尚未交回的 `release()`。
**为什么是问题**：按计划的窗口合同，无法同时兑现“装上才暂停”“建立失败有界”“停止后不装高亮”。与前轮改掉的独立回报合同不同，这是选用订阅后 ACK 本身的含义和取消 API 的缺口。
**如何核实**：顺读上述执行顺序并对照实验 7 情形 8b；新增真实路由用例，阻住提供方激活／目标查找，分别在完成前取消、返回后才完成，以及提供方紧接发 `installed` 和结局。现阶段未运行新协议。
**建议改法**：定义这条订阅自己的有界安装阶段，事件至少区分 `installed` 与终结（含业务失败）；调用前建单一结算器和取消监听，处理事件早于句柄及晚拿到句柄的释放。第 2 片给建立中的订阅接真正的按调用 `signal`／取消句柄（取消还须结算建立 Promise）；或者给安装另定有界通路并明示代价，别把内核 ACK 当安装回执。

### 2. 停止 eval 后既交不回 JS 的 `cancelled`，`release()` 也不确认窗口已撤高亮
**严重程度**：阻断；**类别**：正确性。
**位置**：Spec 输出 9、状态与转换、验收 7；计划“nbook.page-agent”第 65 行；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:301–330,344–351`，`kernels.ts:157–180,200–208`；`packages/nb-runtime/src/remote/peer.ts:166–170,251–255`。
**现象**：停止或单元超时触发 `scope.abort`，同一次信号派发就 `kernel.kill()`；之后嵌套调用结算可写 `nestedToolResult`，但 IPC 回信不再能交给被结束的 JS。父工具返回的是 `aborted` 或 `timeout`。`release()` 则同步删服务端监听、单向发送 `unsubscribe`，窗口收到才触发 abort；没有撤除回执。
**为什么是问题**：Spec 把 `cancelled` 写成与 `clicked` 相同的代码返回，且要求每一种返回时高亮已撤掉；这两个保证都不能从计划里的 `release()` 推出。期内清理可以实现，但不能让死掉的单元继续 `await`。断网与应用自己停止时也不存在可等的窗口回执。
**如何核实**：追读两条信号链并对照实验 7 情形 2a、2c：服务端已经 `release` 后，窗口仍可短暂见 `signal.aborted=false`。真实测试分别观察父结果、恰一条嵌套结算、窗口最终撤除；让取消与推结局交错。
**建议改法**：不改既定的 eval 停止语义。将 `cancelled` 定为服务端结算并明确可观察载体（嵌套日志/诊断，非 JS 正常返回）；正常窗口结局先撤自己的高亮再推；取消、断线靠提供方信号收口，明确这里是最终撤除，若坚持等撤除确认则需另加有界确认协议。

### 3. `capture({token})` 没有路径把 `of` 和 `annotate` 交到窗口
**严重程度**：阻断；**类别**：正确性。
**位置**：计划“nb-page-agent”及“nbook.page-agent”第 54、64–65 行；Spec 输入表、输出 8；`docs/specs/runtime/plugin-channel.md:47–50`，`packages/nb-runtime/src/remote/node.ts:824–861`。
**现象**：工具接收 `of?` 与 `annotate?`，定位与画编号都在窗口，服务端却只传凭证。该凭证的另一个出口只是上传 PUT，不是读取截图任务配置的接口。严格对象合同下临时给 `capture` 多带字段也会被拒。
**为什么是问题**：照字面无法剪到指定控件或叠引用；甚至能发生审批的判定对象为 `screen:element`、实际截了整窗。现有截图验收只检查审批和大小，整窗替代也能通过。
**如何核实**：对照上述两条签名与通道入参校验，找不到从工具参数到窗口实现的第二条路径。加真实服务端到窗口验收：用不同的可见标记验证元素截取没有整窗其余区域、`annotate` 真正改变图像，参数出错时不产图。
**建议改法**：共享截图业务输入，窗口远程方法额外收 `token`，响应只带小型回执；服务端不要在没有定位结果时默认改截整窗，也不要为读本次配置再建 HTTP 回读接口。

### 4. 本地实例目录可能在 `onEnd(target-gone)` 里仍列出已断开的成员
**严重程度**：重要；**类别**：不变量。
**位置**：计划“nb-runtime”、Spec 改动第 72 行；`packages/nb-runtime/src/remote/router.ts:144–167,207–220,306–337,364–373,449–453,487–495`，`peer.ts:167–170,229–245,337–357`，`node.ts:1027–1061,1121–1148`。
**现象**：目录是 `hub` 加 `#members` 的 Map 插入序；等绑定的 Peer 在 `#handshaking` 而非成员表。同 id 接管先换成员再关旧链路，Map 保留原顺位。普通断开时，Peer 先置 `closed`、调用订阅结束，再让路由删成员。按计划直接让本地 `instances()` 使用这份表，同时把 `disconnected` 翻成 `target-gone`，在 hub 插件的结束回调内现查就能看见已经关闭的旧成员；客户端经转发收到对应结束帧时通常已删除它。同进程还会直接拿到路由的描述对象，而远端拿的是 JSON 副本。
**为什么是问题**：新 API 是同一瞬时目录，不应因调用路径不同而把关掉的通路列为在线，或把路由可变元数据交给插件；也不应把窗口作订阅方的上游断线改成终止。Spec 输出 7 只说“仍有效”，仅加验收不足以说明两种断线的差别。
**如何核实**：对照实验 7 的 `harness.ts`（`router.accept`、节点 `connect`、真实内核与 JSON 进程内链路；不是 WebSocket）；`routing.test.ts:301–324,763–810,1045–1066` 已有同类夹具。新增 hub `onEnd` 内查目录、绑定待定、旧链路接管、`close` 已发送事件与 `cut` 丢在途帧、先 release/先掉线和窗口重建的矩阵。
**建议改法**：公共目录同用 `#members` 生成，只列 `!peer.closed`、保持顺序、描述不可变且保留调用方已中止检查。只在 hub 的 router 上游订阅适配层改报 `target-gone`；保留 Peer 先摘订阅后通知的顺序。输出 7 写清是目标链路消失，窗口那一侧可重连的上游断线仍按原规则。

### 5. `foreground` 只加在 harness 不会从 eval 对象里消失，直接访问也不是 `unknown-tool`
**严重程度**：重要；**类别**：正确性。
**位置**：计划第 3、4 片及 Spec 改动；Spec 输入、失败表 `no-window`；`packages/nb-harness/src/kernel/session/session.ts:139–146,524–537`，`run/tools.ts:64–89,539–544`；`packages/neuro-book/src/plugins/agent/backend/agent.ts:256,454,537–545`，`backend/eval/tool.ts:232–235,306–315`，`kernel-entry.ts:169–178`。
**现象**：后台由创建时写入并深冻结的会话头 `background: true` 决定，不是窗口隐藏、Profile `hidden` 或运行状态；原会话不能就地转前/后台，fork 是新前台会话。模型工具表经 `SessionEnv.tools.declarations`，eval 的方法另经 `runtime.codeTools`，后者绕过 ToolBox。只在 harness 过滤，后者仍会装 `ui`；两侧都过滤后新代码 `ui.snapshot({})` 则在 JS 解析标识符时得 `ReferenceError`（父结果 `code-error`），没有发出工具调用。`unknown-tool` 只适用于实际询问未准入的工具（例如留存的方法引用）。
**为什么是问题**：计划要求“对象不存在”与“直接调得 unknown-tool”，Spec 却写后台是 `no-window`。三者不能同时满足；只把 `no-window` 放进服务端 handler 会让不该暴露的工具走到准入/审批之后。
**如何核实**：对照 `docs/specs/harness/session.md:54–74,151–152` 与上面两条声明路径；真实后台会话按同一 Profile 试 `typeof ui`、直接 JS 调用、显式 `invoke`，断言未触发审批或选窗。测试还应覆盖 `added`、`defaultForAll` 和用户 Profile 写了 `required` 时按通用 `tools-missing` 收口。
**建议改法**：`AgentToolDeclaration` 严格 schema、SDK 转换、公告和代码方法表共用后台准入；harness 保留对宿主直接给它的声明的兜底。Spec 删除后台属于 `no-window` 的说法，分开不存在的 JS 名与调用准入拒绝；明确 Profile 绑定变化按已有请求边界生效，不用窗口可见性去更新会话头或重置已跑单元。

### 6. 停掉 eval 时钟后，窗口不送结局没有服务端到期路径
**严重程度**：重要；**类别**：不变量。
**位置**：第四稿“等待的机制”第 160 行，计划第 31、33、65 行，Spec 输出 9、11；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:301–325,451–500`；`packages/nb-runtime/src/remote/node.ts:929–946`；`packages/nb-host/src/server/rpc-listener.ts:42,79–84`。
**现象**：`Deadline` 是宿主里的累计计时器，经过 `ctx.invoke(..., {onWaiting})` 直接暂停，无须另外跨 Bun IPC。任一个等待即可停，最后一个结束才恢复；设计已接受这期间同单元并发代码也不计时。但第四稿只安排窗口到点推结局：若连接活着、窗口实现没再发（例如结局不合 schema，被 `RemoteSink.next` 丢弃），通道既不 `onEnd` 也不超时。`release` 只在已有终点时才执行，不能成为到期来源。
**为什么是问题**：一个已装上的步骤就能让单元无限等，违背 300/3600 秒的业务上限和“最后一个等待离开后恢复”的合同。WebSocket 的空闲检测只解决链路消失，不解决业务事件没来。与既有审批故意等待不同，引导有明确的最长等待时间。
**如何核实**：对照上述宿主路径及 `packages/neuro-book/src/plugins/agent/eval.test.ts:347–367` 的真实 Bun 子进程、手动时钟先例。新增安装已确认、连接仍活且不推结局的用例；叠加两个等用户操作，一个结束/取消/拒绝时不恢复，两个都离开才按原剩余量计时。
**建议改法**：从 `installed` 同时开始服务端独立的业务截止，结局、截止、链路结束、入口撤回或取消进同一结算器，取消计时并 release。`waitingForUser` 先处理已 abort，再为每个仍活跃的标记配一份幂等的收回；明确 abort 是只收回标记还是还会拒绝业务 Promise，监听与迟来的 reject 都必须有人收口。顶层透传无父计时器，不改 `RunStatus.waiting` 或伪造审批事项。

### 7. `details` 的大小检查不能承担 JSON 校验，失败时也不能把 IPC 回信一起丢掉
**严重程度**：重要；**类别**：正确性。
**位置**：第 4 片、第 74 行、Spec 输出 12；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:413–421`、`protocol.ts:1–6,36–51`、`kernels.ts:200–208`；`packages/nb-harness/src/kernel/run/tools.ts:187–192,558–564`、`api/json-value.ts:9–44`。
**现象**：`NestedOutcome.details` 已从最终拦截结果取得、尊重 `redacted`，但嵌套日志只写预览，运行时并不校验该详情。Bun IPC 用 advanced，而不是 JSON。只 `JSON.stringify` 量长度再发送原值会让 `NaN`、`Map` 等通过（被量的是 `null`、`{}`，实际跨 IPC 的仍是原类型）；有环或 `BigInt` 则量长度就抛。`kernels.ts` 的回信只接 `call(...).then(...)` 的成功分支，异常会使这次 JS 调用收不到回信。
**为什么是问题**：第 4 片是通用桥，不仅处理受页面合同约束的对象，第三方工具或拦截器能把一个原本可捕获的拒绝变成挂起；不能挪用成功的 `returns` 验证错误详情。这条落实二轮已定的“超限丢弃”，不是给业务错误再加一个新状态。
**如何核实**：`bun --no-env-file test src/plugins/agent/eval.test.ts -t '一个单元至多 8 张|ToolCallError 带工具名与说明|等审批的时间不算进时限|运行被停止：结果码 aborted'`（应用包目录，隔离临时根，4 pass、0 fail）覆盖现行基线；新增真实子进程用例：合法详情、8,192/8,193 个 JSON UTF-8 字节（含多字节和转义）、非 JSON、脱敏、无详情的审批拒绝，均断言错误码不变且后续调用能继续。
**建议改法**：在 `replyOf` 的最终失败分支做明确的 JSON 结构与编码上限校验，超限或不合格时只省略详情并说明；将可选字段移到 `CallReply` 失败支与 `ToolCallError`，保留本地构造的 `invalid-arguments` 和宿主的 `parent-finished` 等无详情支。文档写 `details?`，不把诊断内容作为业务字段递给代码。

### 8. 现有工具绑定的普通编辑会把新增的对象关闭状态抹掉
**严重程度**：重要；**类别**：正确性。
**位置**：计划第 39、76、87 行；`docs/specs/agent/profile-settings.md:55–61`；`packages/neuro-book/src/plugins/agent/shared/settings.ts:18–39,111–118`、`shared/profile-tools.ts:20–35,61–82`、`backend/tools.ts:82–119`、`web/profile-page.ts:189,221`（仅核对持久化调用）。
**现象**：除了读时的 `profileToolIds`，工具的普通增减会经 `changeToolBinding()` 重组并写回整项，只保留 `added`、`removed`；`withToolBinding()` 在两表为空时直接删项。关闭对象之后再增减一个普通工具，会让该对象在下一轮或重启后重新出现，除非两条写路径的合同一起变。现有 `ToolBindingSchema` 严格且还给 agents、skills、stickers 复用；用新必填字段改共享形状会让旧设置不合 schema。
**为什么是问题**：对象关闭是持久意图，普通工具修改不能清除它；反过来，旧用户绑定里单独移除某方法不等于关闭整个已有插件对象，不能无损地迁成对象关闭。第四稿已经定了存对象名，本条是旧读写路径与数据兼容，不是重新建议存对象。
**如何核实**：看 `changeToolBinding` 返回值、`withToolBinding` 的删项条件及旧设置校验。验收用真实设置持久化：读只有 `added`/`removed` 的旧文件，关对象，再增减普通工具、重开应用，同一对象仍关；加一个新方法也仍关；恢复默认才清掉整项。另测既有插件对象的部分绑定和 required 项。
**建议改法**：给工具绑定加专用的可选对象关闭集合，缺省为空；其它三类形状不变。普通读写、去空与恢复默认保留同一份规范化规则；对象归属按有效声明 `global.object`，明确对象关闭与旧 method id 覆盖、required 和后续新增方法的优先级，不猜测旧设置的意图。保持通用必需工具语义，`ui` 只由内置 Profile 作可选。

### 9. 并发 `ui` 调用能各自选窗，迟到的旧调用还能覆盖会话的最近窗口
**严重程度**：重要；**类别**：不变量。
**位置**：决定 3；第四稿第 160、164–182 行；计划第 65 行；Spec 输出 1、2、状态与转换；`packages/nb-harness/src/kernel/run/tools.ts:581–619`，`packages/nb-runtime/src/remote/contract.ts:284–288`。
**现象**：四个方法按决定全是 `shared`，选窗要跨 `instances()` 和异步 `info()`。同一个会话的 A、B 都看到小表没有记录，A 取到窗口甲的状态后，用户切到乙，B 先选乙；A 的旧回复后到，再派往甲。若等整个方法成功才记最近窗口，一个已在等点击的 A 还会在 B 之后数分钟再覆盖表。另一个空洞：计划漏了第四稿的 800 毫秒 `info()` 截止；常态 RPC 在不显式传 `timeout` 时没有缺省时限。
**为什么是问题**：同一段代码的快照、定位和下一步会被分到两个窗口；活动最久的高亮结束后反而切回旧窗口。目录成功但候选全未应答也不能当作用户没有开窗。
**如何核实**：在真实路由的 `info` 回复边界挂闸门，交错同会话两调用，保持甲可见、把焦点切给乙；验收同时观察实际派发目标、最近表的 2 分钟过期以及目录成功但探测全超时。单纯依次给 `choose()` 喂数组看不到竞争。
**建议改法**：给同会话的“选窗并更新小表”一个提交点（只串行化短暂选择，不串行化工具），把最近使用定义在派发而非结果；失效清理只针对对应记录。保留第四稿的候选超时并把 `ToolContext.signal` 传到底；明确全部确定不合格才得 `no-window`，没查清且无可选项则 `window-unresponsive`。以宿主时钟做可控 TTL、进程内有界 LRU；不用删会话事件。

### 10. «换窗后旧引用作废»只靠页面加载前缀做不到
**严重程度**：重要；**类别**：正确性。
**位置**：t01 决定 3；第四稿第 75、178–183 行；计划第 56、65 行；Spec 输出 4、状态与转换、验收 3。
**现象**：窗口甲发了 `a3.12`。甲转后台，服务端改选乙；再把甲切回来而甲从未刷新。当一次调用重新选甲时，旧 `a3.12` 的前缀与元素身份仍通过计划的全部检查。现有验收只在刷新后用旧引用，无法发现这一差异。跨窗时另有矛盾：输出 4 让前缀不符也尝试同层重找，但窗口乙只收到短编号，未保存甲发号时的层、稳定名或 key。
**为什么是问题**：二轮的处理 D 修正了何时重选，不会使引用作废；决定 3 明确说换窗后重新快照。若把外窗引用当成本窗 `rebound`，还可能无声高亮另一个页面的控件。
**如何核实**：静态代入甲→乙→甲；真实三窗口验收另分同实例重连和实际换窗后又选回未刷新的甲。删除「换窗使旧引用失效」逻辑后，刷新场景仍通过，这两例应能区分。
**建议改法**：先裁定引用寿命。若保留决定 3，让服务端的会话选窗世代参与引用准入，同一实例重连续用、实际换窗后旧世代不能复活；异窗/异加载前缀直接 `stale-ref`，同一次加载里已登记的本窗引用才按身份重找。若只要求“引用不能用在另一窗口”，需要明确修订决定而不是悄悄放宽。

### 11. 老订阅的迟到退订不能清理新引导；抢占需要明确提交点
**严重程度**：重要；**类别**：不变量。
**位置**：计划第 64–65、105、117 行；Spec 输出 9 与状态转换；第四稿第 148、158、176 行；`packages/nb-runtime/src/remote/peer.ts:166–170,229–255`、`node.ts:917–943`。
**现象**：窗口装 A，再装 B、向服务端推 A 的 `replaced`。服务端处理 A 终态后才发 `release`；该帧自然可能在 B 画好后才到。若各订阅结束都调用同一 `clearCurrent()`，A 的清理撤掉 B。反过来，A 正在异步等目标时，后到的 B 可能先装好；没定义是按订阅开始还是安装成功判断“另一个高亮开始”，A 的迟到安装也能反抢。
**为什么是问题**：共享并发与同窗替换都是已定，不应靠它们恰好没有交错来保证唯一高亮。通道给的是每条订阅自己的 signal，不认识窗口里的当前步骤。窗口仍连着时，先被替换的调用必须能结算，第二个则应在自己的终态前保持可用。
**如何核实**：测试用真实订阅在那里扣住 A 的 `unsubscribe`，等 B 的安装事件送达才放行；再扣住 A 的查找完成让 B 先装。断言 A、B 各一个结局、A 的回调不能撤 B；再对照 B 查找失败、A 被单独取消的分支。无需假冒一条在真实通道不会出现的事件。
**建议改法**：窗口只在明确的抢占提交点交接当前所有者。每条订阅只拆自己的资源；清空共享槽前核对是否仍属于自己。明确较早的安装何时失效、未安装成功是否抢占。不要把一个业务取消映射成无身份的全窗清除，不新增跨会话租约。

### 12. 提供方抛错时订阅已结束，但窗口的清理信号不触发
**严重程度**：重要；**类别**：不变量。
**位置**：计划第 26、64–65 行；Spec 状态与转换；`packages/nb-runtime/src/remote/node.ts:917–946,1095–1104`、`peer.ts:294–329,345–356`、`contract.ts:275–278`。
**现象**：窗口的 `subscribe` 装了部分资源后抛错时，`handleSubscribe` 捕获并调 `channel.end("provider-error")`。`Peer.end` 摘掉入站 controller，再发结束帧，却不 abort；订阅方收到结束后，Peer 已摘掉出站项，`release()` 发不出退订，之后链路断开也找不到原 controller。现有 729 行的 `routing.test.ts` 用例测的是「事件编码失败」的另一支，那一支会 abort。
**为什么是问题**：按合同约定把清理挂在订阅 signal 上，安装中途失败的监听器、定时器或描边可能一直留到窗口插件停止；业务层收到错误且主动释放也救不了。这是提供方终止的资源缺口，与第 1 条的 ACK、建立期取消不同。
**如何核实**：在 `packages/nb-runtime` 用 `bun --no-env-file -` 跑内联探针，真实 `createApplication`、节点、路由与进程内 JSON 链路。窗口的真实订阅实现先交出 signal、等闸门后抛 `Error('installation failed')`；服务端收到 `onEnd=provider-error` 时、随后 `release()` 后、再 `cut()` 后，窗口 `signal.aborted` 都是 `false`，提供入口 `stop()` 后才是 `true`。不是 WebSocket，也未运行 t03。
**建议改法**：第 2 片将提供方 `end` 与入站取消接到同一个幂等清理状态，既发出恰一次原结束原因，又 abort；同实例路径一起核对。第 8 片自己的部分安装也用异常安全的所有权收口，别把失败后的 `release()` 当成窗口唯一清理动作。

### 13. 一次性上传凭证没有定义读体占位和终止后的回收
**严重程度**：重要；**类别**：不变量。
**位置**：计划第 65、104 行，第四稿“截图”第 191 行；`packages/nb-host/src/http/dispatch.ts:144–153,182–185`、`admission.ts:119–144`、`server/start.ts:324–343`；`packages/neuro-book/src/plugins/files/backend/upload-route.ts:68–114,157–177`。
**现象**：方案已规定上传、RPC 成功两者齐备才交图，但没有规定何时独占凭证、何时截断读体。同一 token 若在读完后才标使用，两笔 PUT 会一起占住正文缓存；若只到期删表项，不会取消已持有它的 reader。宿主转交的是 HTTP 请求信号，不是这次截图的信号；文件上传先例的 `Gate` 会排队，`readBody` 只在越字节上限时主动取消，不能原样用于 15 秒凭证。
**为什么是问题**：到期、RPC 失败、窗口断开与 eval 取消都能先于 PUT 完成；若不废弃在读的那次，迟到的字节可改写暂存结果，或在调用已失败后继续占用资源。`shared` 调用的单图上限不是在途总上限。宿主先排空再停插件，只挂入口停止信号不能让在排空中的请求及时结束。
**如何核实**：在 `packages/nb-host` 用 `bun --no-env-file -`，真实 Bun HTTP、现有分发器及半上传连接，测试路由等待正文；手动触发 `HttpAdmission` 的 20,000 ms 排空截止。结果是 `active=1`、`Request.signal.aborted=false`，主动取消正文 reader 后 `active=0`。不是 t03 路由。实现验收还要卡住 RPC 回执与 PUT，覆盖重复、无 `Content-Length`、只到一边、成功回执时未收到上传、最后一块与取消同到、停机后迟回，断言没有图且暂存、reader、容量都归零。
**建议改法**：签发时扣在途额度，首笔合格 PUT 在第一次 `await` 前占用，不能重放；统一以宿主时钟检查 15 秒截止，读体受 HTTP 断开、调用结束及截止控制并可主动 cancel。完整校验后才能标上传就绪；只在回执成功、上传就绪、调用仍有效时一次提交，其余终态废弃并清引用；已失败的槽不能被晚到回调复活。停机若要求立刻废弃，从宿主开始停而非插件 dispose 触发；无该钩子则明确允许剩余截止内排空。

### 14. 文字、元素数量和详情各自合格，整条窗口回包仍可超过 1 MiB
**严重程度**：重要；**类别**：正确性。
**位置**：计划第 55、64、107 行，Spec 输出 7、9、12 与验收 5；`packages/nb-host/src/shared/socket.ts:12–16,32–43`、`server/rpc-listener.ts:79–91`、`server/rpc-listener.test.ts:80`。
**现象**：当前三条限制分别是快照文字 64 KB、元素 500 个、失败详情 8 KB；WebSocket 却对编码后的整条入站消息限 1,048,576 字节。只算 500 个元素各有 2,048 字节的结构化字段与 65,536 字节的文字，就已达 1,089,536 字节，尚未加 JSON 键、转义、窗口信息、警告与帧信封。草稿也没给 `find` 的 `limit` 硬上限或路径预算，以及 `asked.question` 的边界。
**为什么是问题**：各字段分别通过 schema 不保护链路；过大的快照、目录或终态能断开整窗连接，牵连其他在途调用。仅让单测看到 `truncated` 不证明下一条 RPC 仍可用。这是把二轮已定的上限落到正确的计量层，不重报原先把图走 RPC 的问题。
**如何核实**：核对上述 `maxPayloadLength` 真实 WebSocket 用例；实现用生产消息形状测长名字、嵌套路径、多字节与密集转义，断言实际结果帧低于上限、保留完整结构和截断提示，随后在同一连接再成功调用一次。进程内 JSON 链路不作为该扇门的验收。
**建议改法**：第 1 片给整个成功/失败结果与订阅结局定编码后字节预算，预留信封余量；第 8 片用同一预算对可裁部分稳定裁切，给单项文本和目录条数设上限，必要时以小而明确的失败结算，不能把无效终态丢掉。验收量转义后的 UTF-8，不用 JS 字符数或按元素条数代替。

### 15. PUT 收到的图满足 512 KB，实际发给模型的图仍可更大
**严重程度**：重要；**类别**：正确性。
**位置**：Spec 输出 8、验收 4、副作用与数据；计划第 59、65、104 行；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:293–315,368–375`；`packages/nb-harness/src/kernel/model/omp.ts:187–212,378`；`docs/specs/harness/session.md:102–105`。
**现象**：窗口可交 WebP；现有模型适配器会为不支持 WebP 的端点（含普通回环地址）转 PNG，PNG 不超过 4 MiB 就直接发。若 Spec 的 512 KB 也约束“交给模型”的那张图，上传测试测的是另一份字节。会话日志不会再压缩图片，只把 base64 外置；若限额取 512 KiB，一张 base64 至多 699,052 字节，八张合计 5,592,416 字节，未计日志元数据，也不是整条模型请求的上限。图仍适用 eval 的八张上限；`eval` 当前还会丢掉 `ToolImage` 的可选宽高，不能把图片元数据当提交校验的来源。
**为什么是问题**：路由、日志和出站走不同尺寸边界。只验窗端小样本、上传头或 RPC 声明的 `width/height`，既没证明服务端交付的是已校验图，也没证明不支持 WebP 时仍兑现模型侧上限。
**如何核实**：在 `packages/nb-harness` 用 `bun --no-env-file -`，以合成的 960×640 灰阶图走实际 `Bun.Image` 编码：WebP 326,474 字节，按适配器同样的调用转 PNG 后 1,002,759 字节，落在直接发送 PNG 的档内。不是真实模型请求。实现测试应以实际文件类型和解码尺寸核对边界，拒绝伪报与坏图，并检查日志回读及脚本化端点收到的图。
**建议改法**：统一常量和单位，服务端以实际字节/MIME/尺寸为准产出元数据，不照抄回执；声明 512 KB 是上传与持久化前的单图限额、模型传输遵守现有适配器合同，或保留模型侧限额并用有界的兼容编码（第一批统一 JPEG 是较小改动）。两种口径的验收必须分开；不因截图扩展所有 eval 图像的合同。

### 16. PUT 没有 RPC 窗口身份，路径里的凭证还会进 HTTP 诊断
**严重程度**：重要；**类别**：安全与性能。
**位置**：计划第 64–65 行，第四稿“截图”第 189–191 行；`packages/nb-host/src/shared/http-contracts.ts:12–27`、`http/dispatch.ts:144–153,182–185`、`http/plugin.ts:62–70`；`packages/neuro-book/src/plugins/files/backend/upload-route.ts:62–66`。
**现象**：RPC 能点名一个窗口实例，HTTP 插件处理器只拿到标准 `Request` 和事件流登记口，拿不到经路由核对的实例身份。来源检查区分网页来源，不区分同源标签页；客户端自报的 `instanceId` 也不是证明。`/captures/<token>` 在处理器抛错或读体因断开失败时还会作为 `url.pathname` 进诊断，含完整凭证。
**为什么是问题**：“凭证绑定窗口”只有服务端记录该凭证发给哪个实例的含义，不能写成 PUT 还认证了窗口。若 token 是唯一凭据，把它放进可记录的路径与“只交给这次的窗口”相冲突。这个问题不要求恢复被删掉的多主体安全边界。
**如何核实**：核对实际路由环境与错误分发；现有 `http/dispatch.test.ts:161–186,300–309` 分别覆盖半上传断线和来源检查，均没有 RPC 身份。实现验收让只有选中的 RPC 实例获得凭证，其他调用的票、旧实例或过期票不能提交；检查半上传断线的诊断不含凭证原文。
**建议改法**：明确 PUT 是同源、短时、一次性的持有凭证协议。服务端关联本次调用与派发的窗口实例（不是跨刷新稳定的客户端 id），签高熵不透明凭证，只经该 RPC 发，PUT 放请求头而不是 URL，且不写入诊断；用相对同源路径和现有来源检查。不新建窗口认证体系，不相信请求体或头里自报的窗口 id。

### 17. 只存关闭的对象名，不能推出这个 Profile 已获准用对象的全部方法

**现象**：现有 Profile 可以在 `required`、`optional`、`added`、`removed` 里按方法 id 配出一个对象的任意子集；实现按 id 计算，再按全局对象的有效登记筛掉非法方法。加 `disabled` 对象名单不会把未绑定的方法变成已绑定，也不决定对象关闭与 `required` 谁优先。当前 `toolCatalog` 只给 id、提供者、模型名等，没有有效的对象身份；`profileToolIds` 单凭 id 列表不能做同一分组。比如现有场景 10 的 `stats.count` 就可能是必需方法。

**现象**：输出 13 唯一指向 `ui` 的真实 schema，但第 4 片先交 `tsType`，第 6 片才有 API schema、第 8 片才装对象。改成多行后，现有 `objects.test.ts` 与 SDK 场景 10 都对旧的一行签名有断言，不能只更新 `ui` 快照。另一个边界是工具参数只用 `Value.Check` 校验，不填 schema 的 `default`；将 `description` 原样塞进 JSDoc 也没处理 `*/` 及独占行的 Markdown 围栏。
**为什么是问题**：计划照写要么提前引下游包，要么先交一片没有可运行验收的通用文档改动；文档打印了“缺省 300”也不能证明调用者省略时真获得 300。描述是插件 schema 里的普通字符串，合法描述不应破坏生成签名或把正文移出代码块。
**如何核实**：应用包内 `bun --no-env-file test plugin-sdk/examples/scenarios/10-eval-object.test.ts` 为 4 pass、0 fail。另用实际 TypeBox 对 `Type.Optional(Type.Integer({default:300}))` 验 `{}`，结果是通过且仍为 `{}`。这是校验与打印探针，不是 t03 的缺省执行测试。
**建议改法**：第 4 片用独立的嵌套 schema 验可选、单位、`default:false/0` 和说明转义，随片迁移现有 SDK 场景断言；第 8 片再以产品装配和 `docs://eval/ui.md` 核对真实签名，并让实际 eval 省略、显式给值、给边界外的值，观察实际生效的默认值和失败。缺省解析归业务输入，不在 `tsType` 或通用 IPC 偷填。

### 20. 窗口有序退出可能先报 `provider-stopped`，只翻译 `target-gone` 会漏验收 3
**严重程度**：重要；**类别**：正确性。
**位置**：计划第 26、64–65、102、118 行；Spec 输出 9、验收 3；第四稿第 160、178–183 行；`packages/nb-runtime/src/remote/node.ts:917–928`；`packages/nb-host/src/web/browser-host.ts:49–64,72–75`；`packages/neuro-book/src/web/host/window.ts:419–425`。
**现象**：补 hub 的断链回调只能解决先掉链的一支。窗口入口先停止时，订阅先结束为 `provider-stopped`，窗口显式 stop 在 destroy 后才关链路；刷新触发的 `pagehide` 也会请求入口停止，但浏览器不保证消息送达。有序停止与直接掉链是同一个用户行为的两种可见途径，不会在先收到前者后再收到一遍 `target-gone`。
**为什么是问题**：Spec 给刷新一个确定的 `window-gone`，若只照第四稿第 160 行把 `target-gone` 转译，另一支会暴露内部码或挂到业务截止。反过来，单纯窗口插件停用也可能以 `provider-stopped` 结束，协议没有提供一个能区分“刷新”与“入口主动撤回”的原因。
**如何核实**：实验 7 总表有现成的有序刷新、直接刷新以及撤回对照；`routing.test.ts:899` 已验提供入口停。新增业务路由夹具分别让提供入口先停止、链路先断，断言对用户的结局、单次写回及不重建；真实 Chrome 刷新仍留第 8 片。
**建议改法**：在业务合同把「目标窗口提供端已结束」作为一类失败，两种终止原因均可得 `window-gone`，内部诊断保留原码；若确实要区别插件撤回，先补能区分它的信号。建立前没提供、安装业务失败、已安装后端点消失分开，不把 `provider-error` 一概当作掉线。

### 21. `screen` 判定对象能匹配规则，但当前到不了 `auto` 的审批模型
**严重程度**：重要；**类别**：正确性。
**位置**：计划第 65、69–76、104 行，Spec 输出 8、验收 4；`docs/specs/agent/permissions.md:77,99,103–105,114`；`packages/nb-harness/src/kit/approval/hook.ts:84–110,147–170`、`types.ts:9–15`、`review.ts:136–146`。
**现象**：`subjects()` 交出的 `{kind: "screen", value: "element"}` 会进规则匹配器的 `others`，但送审批者的 `ReviewRequest` 只有 `call`、`effect`、`paths`，`modelReviewer` 序列化的 `pending_action` 同样没有 `screen`。这不是二轮已修掉的“value 类型不合”。
**为什么是问题**：草稿说按现有审批判定，而 `permissions` 输出 20 承诺审批模型看到判定对象。照计划只交 `subjects()`，人工询问场景会通过，自定义规则也能生效，自动审批却只能从工具 id 和参数重新猜范围。现有“本会话都批准”记整个非 shell 工具，不会因为 `screen` 分两种值就缩窄已记住的授权。
**如何核实**：追 `buildViews` 到 `pending_action`，对照 `review.test.ts:47–58` 现有路径断言。用脚本化审批端点分别走无 `of`、有 `of`，检查实际待判输入；另用 `subject` 规则断言拒绝时不签票、不调窗口。问询模式的审批卡不能代替这条验收。
**建议改法**：若遵守输出 20，把已有的扩展判定对象从 `ReviewRequest` 传到模型请求并计入长度限制；若此轮只给规则用，在权限 Spec 明示审批模型只收哪些数据，别声称 `screen` 已跨该边界。两层审批及已有记住规则不变。

### 22. 会话小表有上限，但远程入口仍保留历史探窗和已结束订阅
**严重程度**：重要；**类别**：不变量。
**位置**：计划第 25–27、65、100 行；`packages/nb-runtime/src/remote/node.ts:447–479,595–625,659–681,1041–1051,1111–1118`；`packages/neuro-book/src/web/host/window.ts:236`。
**现象**：第 8 片用一个长期存活的服务端入口对候选做 `info()`。每次真正调用在派发前就把目标写入 `RemoteAccess` 的 `contacted`，按目标 id 去重，只在调用方入口释放时遍历；窗口刷新换 id，所以写过的旧目标不会随小表淘汰。订阅还另有两份登记：自动 `onEnd` 只删节点的 `#subscriptions`，没有从入口的 `owned` 移除；只有随后显式 `release()` 才删后者。补 `target-gone` 并不自动收回这份引用。
**为什么是问题**：即使会话小表和同时在线窗口都有界，入口保留量仍随本次服务进程见过的窗口 id 和未显式释放的终态订阅增长。按调用方门面的释放也依赖 `contacted`，不能为了清内存一见断链就删同实例可重连的使用关系。
**如何核实**：从源码核对两张订阅表的入表和退表路径，及每次窗口启动生成的新实例 id；未做堆测量。第 2 片可用接管/刷新夹具配合提供方释放观察，区分已结束的监听、临时探测、可重连实例上的门面仍须释放三件事。
**建议改法**：订阅终态统一摘除两份登记，再通知调用方；第 8 片所有分支仍及时释放拿到的句柄。对大量动态目标的短探测，不要把联系记录永久挂在插件长寿入口上：用有明确结束的调用方作用域，或在路由层按确认退役的实例回收。若复用现有 `RemoteAccess`，计划至少写明仍未有界的是哪张表，不把会话 LRU 的上限当作整个插件的上限。

### 23. 第 8 片自验用例在交付之后才写，注入插件也不能代验产品装配
**严重程度**：重要；**类别**：测试。
**位置**：计划第 91、96–118、123–126 行；`packages/neuro-book/src/manifest.ts:43`、`src/server/plugins.ts:79–91`、`src/web/plugins.ts:74–98,152–153`、`src/plugin-platform/shared/definitions.ts:26–34`、`e2e/fixtures.ts:55–86`；`docs/testing/README.md:80,117`。
**现象**：第 8 片的自跑验证要求 `page-agent.e2e.ts`，同一文件却安排第 8 片之后才写；收口又把它算进开工前的基线清单，而检出里没有该文件。插件测试若给 `AgentWorld` 或窗端直接注入定义，可以完全绕过产品清单和两侧入口表。变异清单点到退订和等待收回，但没有把删除双路提交条件、漏登记入口等改坏后的结果，指向一条实际用例与对应构建。
**为什么是问题**：开工基线不能把新文件的无用例当失败；第 8 片也不能先宣布通过自验再补指定证据。遗漏整个插件时，私有夹具仍能通过；遗漏其中一侧定义时，生产装配才报错。只重跑 Playwright 而不重建被测产物，变异还能误测到原代码。
**如何核实**：核对基线检出、`definitionAt` 的缺项错误、真实产品与带探针的两个启动器；后者用源码服务端和 `dist/e2e/web`。`src/plugins/web-tools/assembly.test.ts:30–39,49–86` 是实际产品清单加真实 WebSocket 的先例。本轮没有执行 e2e 或变异。
**建议改法**：开工只给已有用例记基线；保留两段测试分工，但第 8 片业务就绪后派第二段，合回并跑过才记该片验收完成。业务夹具负责可控交错；至少一条用例从真实产品装配进入 eval，验证 `ui` 已注册、能到窗口并取得结果。变异表写清改坏哪条合同、哪条用例应失败、该用例实际加载哪份产物；对照第 13 条让“两路少一路仍交图”的变异失败，相关构建重建并恢复后再通过。
