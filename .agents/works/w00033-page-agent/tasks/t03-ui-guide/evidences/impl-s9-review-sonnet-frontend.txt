### 1. ui.find 的“视图”路径终点是 workbench.view，但视图叠成标签或标题并进入口条时页面上没有这个目标
严重程度：重要　类别：正确性（从代码推断，未在真实窗口里复现）
位置：packages/neuro-book/src/plugins/page-agent/web/catalog.ts:96-103、126；packages/neuro-book/src/plugins/workbench/web/components/WorkbenchPanelHead.vue:194、231、252（只有 `titleOnly` 且 `activeTab !== null` 的三个分支写了 `viewTarget`）、268-285（TabStrip 与 `titleInEntry` 分支没有）
现象：`candidates()` 对每个视图都给出路径“容器入口 -> `{target: "workbench.view", key: 视图 id}`”，视图命令的终点同理（viewSteps 的第一步总是容器入口，最后一步的 at 是 `command`）。而 `workbench.view` 只写在“面板只有一个标签（`titleOnly`）”时的标题按钮上。同一面板里叠了两个以上视图（用户拖标签合并是常规操作）时，标题区画的是 TabStrip，标签上没有 `data-nb-target`；`titleInEntry`（分节并进入口条）时标题在入口条里，同样没有。此时路径最后一步的 `at` 在页面上找不到，`ui.highlight` 等 5 秒得 `not-found`。
为什么是问题：Spec page-agent 输出 6 末尾写明“几个视图叠成标签时的视图标签，按角色与名字在所在的组里定位（within）”，也就是承认叠标签时没有稳定名；但 catalog 并没有按这一情形换定位，`ui.find` 给出的 `path[].at` 在这一布局下必然落空。`appears` 又写 null，`remaining()` 也无从发现这一步已经走不通。catalog.test 只测了浮动与默认布局，没有“视图叠成标签”的用例。
如何核实：在 Lab 或工作台里把两个视图拖进同一个面板，调 `ui.find({query: "<其中一个视图名>"})`，对返回的最后一步 `at` 调 `ui.highlight`，预期 not-found（对应 e2e 可在 page-agent-guide 里加）。
建议改法：二选一。(a) 在 TabStrip 的标签上也写 `workbench.view` + 视图 id（拥有者写稳定名本来就是 Task 决定 1，标签是同一个控件的另一种画法）；(b) catalog 读到视图所在面板有多个标签时，改给 `{role: "tab", name: 视图标题, within: <面板>}`。(a) 更简单，且和 Spec 写的“按角色与名字定位”不冲突。无论哪种都补一条 catalog 用例。

（对第 1 条的修正）WorkbenchPanelHead.md 第 25 行写明 `titleOnly` 是“侧栏这一列，别的工具面板只有一个标签时”：侧栏每个视图自己一节，不叠标签，所以受影响的是右栏、底部面板与浮动窗里有两个及以上标签的面板，以及底部面板并成一行时标题写在入口条上的（`titleInEntry`）视图。范围比我上面写的“用户拖标签合并”窄，但这些位置的视图仍会被 ui.find 列出且路径终点落空。严重程度仍按“重要”，因为 Spec 输出 7 没有把它们排除在“视图”之外。

### 3. inOtherEditable 的判据方向反了：焦点在可编辑区域的祖先上时仍把选区放回去，焦点被拉进编辑器
严重程度：建议　类别：正确性（已在 Chrome 里用纯 DOM 复现判据与后果；没有经 GuideView 整条链路复现）
位置：packages/nb-page-agent/src/guide/view.ts:91-96（`return focused === null || !focused.contains(element)`）
现象：函数想表达“焦点不在这个可编辑区域上就不放回选区（Chrome 会把焦点一并拉进去）”，实际写的是“焦点元素不包含选区所在元素”。三种情形：
- 焦点就在编辑宿主上（`focused === 宿主`）：`focused.contains(element)` 为真，放回，对。
- 焦点在编辑器的祖先（带 tabindex 的容器、对话框根）上，编辑器里仍有选区：`focused.contains(element)` 也为真，于是放回选区。我在 /tmp/review-w00033-t03-impl/lab-frontend/probe.mjs 里用 Chrome 复现：`#wrap`（tabindex=-1）包着 contenteditable `#ed`，选区留在 `#ed` 里、焦点在 `#wrap`，按 restoreFocus 的做法 `removeAllRanges(); addRange(range)` 后 `document.activeElement` 变成 `ed`（输出 `A_focusAfterRestore: "ed"`）。这正是注释里要避免的“焦点被选区拉走、弹层随之关掉”。
- 焦点在可编辑区域里的非可编辑子元素（例如节点视图里的按钮，contenteditable=false）上：`focused.contains(element)` 为假（`B_focusedContainsElement: false`），不放回，选区丢失；此时放回会让焦点从按钮挪到编辑宿主，所以不放回是对的，但原因不是 contains 的方向。
为什么是问题：第二种情形里用户的焦点被说明框的收起动作带进了别处的编辑器；用例只测了“焦点在编辑器里”和“焦点在无关按钮上”两种，抓不到这一类。
如何核实：运行 probe.mjs（`node /tmp/review-w00033-t03-impl/lab-frontend/probe.mjs`，用本机 Chrome）；整条链路的复现需要在核心夹具里放 `<div tabindex=-1><div contenteditable>…</div></div>`，选区放进里面、焦点给外层，提问再收起，看 `document.activeElement`。
建议改法：判据改为“选区在编辑宿主里，且焦点正是这个编辑宿主（`focused === host`，或 `focused.isContentEditable` 且同宿主）才放回”，其余一律不放回：`const host = element.closest('[contenteditable]:not([contenteditable=false])'); return host === null ? false : focused !== host;`（`isContentEditable` 取到的是继承值，不能直接当宿主用）。补一条“焦点在祖先容器上”的用例。

### 4. 高亮自绘头浮动窗里的视图标题：目标是透明且不接指针的按钮，悬停显示钩子不覆盖它
严重程度：建议（只在视图单独浮出且自绘头时发生）　类别：正确性（从代码推断）
位置：packages/neuro-book/src/plugins/workbench/web/components/WorkbenchPanelHead.vue:194-199（自绘头标题按钮带 `workbench.view`）与 612-626（该按钮 `opacity: 0; pointer-events: none`，聚焦才显示）；packages/neuro-book/src/plugins/page-agent/web/engine/PageAgentEngine.vue:71-76（`reveal` 只认 `closest("[data-hover-actions]")`）
现象：Agent 对话视图（ConversationHost、MessagesHost 声明了 ownHead）单独浮出时标题按钮写了稳定名，所以 `ui.find` 能给出它、`ui.highlight` 能定位到它，但它是透明的、点不到的。引擎的 `reveal` 在它外面没有 `[data-hover-actions]` 祖先，返回 undefined，什么也不显示。结果是描边框和说明框指着左上角一块空白；`until: "click"` 时用户点那个位置落到视图内容上，得 `missed`。

如何核实：把对话视图浮出（单独一个标签的浮动窗），`ui.highlight({at: {target: "workbench.view", key: "<对话视图 id>"}})`，看页面。
建议改法：给自绘头标题按钮加一条 `[data-nb-agent-reveal]` 的显示规则，并让 `reveal` 在目标上没有悬停区时对目标自己写同名属性（`target.hasAttribute("data-nb-target")` 时写在目标上）；或者 catalog 对浮动自绘头的视图不给 `workbench.view` 步骤。前者改动更小。若判断“浮出的自绘头视图不会被引导”，在 Spec 里写明并保持现状。

### 5. 窗口一侧的 highlight 订阅：订阅在开始前已被退订时高亮永远撤不掉；`candidates as never` 绕过类型
严重程度：建议　类别：不变量（竞态，从代码推断）／代码质量
位置：packages/neuro-book/src/plugins/page-agent/web/plugin.ts:189、191、207
现象：(1) `ready(signal)` 在页面已连上时直接 `Promise.resolve(page)`，不看 `signal` 是否已经 abort。nb-runtime 的 node.ts:943 在 `await handler.subscribe(...)` 之前还要先做若干异步查找，退订可能先到；此时 `call.signal` 已 aborted，subscribe 接着调 `side.highlight(filter)` 画出高亮，再 `addEventListener("abort", …, {once: true})`——已经 aborted 的信号不会再触发，`handle.cancel()` 永远不被调；`installed`、`outcome` 的 `.then` 又都因 `call.signal.aborted` 把事件吞掉。页面上留下一个没有主人的说明框，直到用户点“跳过引导”或下一次高亮把它替换。Spec“状态与转换”写明窗口收到退订时撤掉高亮、页面上不留描边框与说明框。(2) 第 191 行 `candidates as never` 把任意 `readonly unknown[]` 塞进事件的类型，类型检查在此处不再起作用；候选来自 `PageFailure.details.candidates`，本来有确切类型，应该沿用。
为什么是问题：(1) 窗口很快被退订（eval 单元刚开就被停止）时才触发，概率低，但后果是残留；修法一行。(2) 项目规则不用 `as never` 绕过类型系统。
如何核实：(1) 在 plugin.ts 单元测试或 e2e 里用已 abort 的信号调 subscribe，看页面有没有 `[data-nb-page-agent]`；没有现成测试覆盖这条路径。
建议改法：(1) `const side = await ready(call.signal); if (call.signal.aborted) return;`，并在 `side.highlight` 返回之后再核对一次 `call.signal.aborted`，已 aborted 就 `handle.cancel()` 后返回；或改成 `call.signal.aborted ? handle.cancel() : call.signal.addEventListener(...)`。(2) `fail` 的 `candidates` 参数用 `PageFailure` 里候选的类型。

（对第 5 条的撤回与修正）复核 nb-runtime 的 node.ts:882-945 后，第 5 条里的 (1) 不成立：`handleSubscribe` 在调用 provider 的 subscribe 之前已核对 `signal.aborted`，之后到 `await ready(...)` 返回之间只隔微任务，退订消息到不了其间；所以“订阅已被退订、高亮撤不掉”这条竞态撤回，不算有效发现。第 5 条只保留 (2)：plugin.ts:191 的 `candidates as never` 是类型绕过，严重程度建议、类别代码质量，改法同上（沿用候选的真实类型）。另：`ready(signal)` 在引擎未挂上时被 abort 会 reject，让 subscribe 抛出，nb-runtime 记一条 provider-threw 并以 provider-error 结束；退订之后无人收，只多一条诊断，不处理也可。

现象：去掉或加回对象行时整行直接出现、消失（`v-for` 里没有 TransitionGroup）；Profile 里 eval 被去掉或加回时，每个对象行的说明文字与警示图标/颜色直接切换，说明文字宽度变了行里的省略位置也跟着跳。整个文件没有一条 `transition`。
为什么是问题：Task 决定 4 写“状态改变尽量少造成布局的不同；布局的不同要加动画”，设计语言也要求状态变化有过渡。不过这个组件的其它行（工具、子代理、Skill）原本就没有过渡，对象行与它们一致。
建议改法：要补就整节补（行增减用 TransitionGroup 的高度与不透明度，警示色用 `transition: color`），不只给对象行；不补则在 Task 记录里写明“这一节沿用既有行为”。

## 未发现问题的方面（仔细检查后没有发现）
- 组件卸载：PageAgentEngine 卸下时只摘输入监听并交还 `connect`，不结束进行中的高亮；但订阅的寿命由服务端退订、插件停止、窗口断开三条路径结算，`handle.cancel()` 都会被调，我没找到引擎先于订阅被卸下而留下残余的路径（页面间导航是整页加载），所以不算问题。
- 事件顺序：`installed` 在 `outcome` 之前，`failed` 只在 outcome 阶段发一次；同一页面第二个高亮时旧的先 `replaced`、再装新的（engine.ts 里 `previous?.end` 在 `session.start()` 之前），各订阅内每个事件至多一次。悬停显示的撤销闭包只摘自己写的那个动作区的属性，同名属性只有引擎一个写者，没发现会误删别处的情形。
- 主题变量：`GUIDE_THEME` 里 17 个 `--*` 都在 nb-ui 的 colorway 契约或 tokens.css 里有定义（`--accent-main`、`--text-*`、`--overlay-bg` 来自 colorway-contract.ts），明暗两套都有值；说明框是在目标所在层里挂的 shadow 宿主，继承该层的变量。
- 语言：`guideText(props.text)` 每次高亮开始时按窗口当前语言取，切换语言后下一次高亮生效（一次高亮进行中切换不换文字，属 Spec 写的“每次高亮开始时取”范围）。英文文字按 300px 固定宽度与按钮的 padding 估算四个按钮 230px 内，未发现截断，未在页面上量。
- Profile 页：等级取最高、计数按对象、已卸载按对象、对话框按对象加回、动对象时清方法旧条目，shared/profile-tools.ts 与页面共用同一份，`changeToolBinding` 的各分支（去掉再加回、本来只有部分方法、defaultTools:false、插件已停）都推演过，没发现错误。服务端 `methodsOf` 与页面 `catalogMethodsOf` 取同一份目录数据（`#objectOf`），规则一致。
- 稳定名取值：`command`+命令 id、`workbench.activity`/`container`/`view`+id、`settings.layers`/`section`/`row`+id 都是业务身份，不随语言或顺序变；`nbTarget` 在渲染时校验名字。
- hover-actions.css：新增的 `:not([data-nb-agent-reveal])` 只让规则更难命中，不会让平时就显示悬停动作；该规则新增一项属性选择器抬高了特异性，但仓库里没有别的规则覆盖这块的 opacity（grep 过），没有被盖住的风险。
