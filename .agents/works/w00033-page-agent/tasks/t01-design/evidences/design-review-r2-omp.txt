### 1. 引导回报把拓扑角色 `client` 写成调用方运行位置，正常浏览器也无法结算
**严重程度**：阻断；**类别**：接口与合同
**位置**：第三稿“结构”第 40 行、“引导”第 150 行；`packages/nb-runtime/src/remote/contract.ts:65-73`、`node.ts:805-812,828`；`docs/specs/runtime/plugin-channel.md`“术语与参与者”、输出 3。
**现象**：`nbook.page-agent/host` 写 `callers: client`。`client` 是拓扑角色，可用于 `provider: "client"`；`callers` 实际拿 `location` 逐字匹配，窗口的运行位置是 `browser`。写成 `["client"]` 能过合同定义的非空检查，但正常窗口的完成回报到方法之前就得到 `denied`。改成 `browser` 后也只是允许该类实例进入；没有按等待记录上的实例身份核对，不等于只有被选中的窗口能结算。
**为什么是问题**：照字面接线时，用户点了目标、下一步或跳过，服务端都收不到有效结局。若只按输入里的等待 id 或自报窗口 id 查表，回报也没有绑定真正的来源窗口。这里要求的是同一受信拓扑内的归属，不是新增本机鉴权。
**如何核实**：对照 `callers.includes(frame.$nbConsumer.location)` 与 Spec 输出 3。验收用真实服务端入口加两个浏览器实例：B 将同一等待 id 回报给后端不能结算，A 的回报成功；A 重复回报不产生第二次结算。
**建议改法**：明确 `provider: "server", callers: ["browser"]`。在 `provideRemote` 的按调用方门面里，用内核给的 `instanceId`（不能用跨刷新稳定的 `client`），与后端登记的目标实例、等待代次核对；参数只报等待 id 与结局，不自报权威身份。要区分重连链路时另外定义等待代次，不能把实例 id 当连接代次。
### 2. 第一轮 G10 未改到位：等待标识只在短调用返回，早到回报与安装回执丢失无法收口
**严重程度**：阻断；**类别**：不变量
**位置**：第三稿“引导”第 145、150 行、“测试”；`packages/nb-runtime/src/remote/peer.ts:178-184,265-291`、`node.ts:839-856`。
**现象**：稿子写的是窗口装好后「交回等待身份」，此时才开始服务端等待；没有在派发前登记的阶段，也没有定义在途安装被取消时撤哪一个。窗口安装后可以马上因为目标移除或用户操作而回报；回报是独立请求，不会等安装结果被服务端接收。另一条顺序是窗口已装好并结束安装方法，服务端却在收到结果前取消或丢回复：此时 `Peer` 已从在途表删除该入站请求，迟到的 RPC `cancel` 不会再触发对应的清理。
**为什么是问题**：前一顺序可把真实结局当无主消息丢掉，模型误等到超时；后一顺序服务端不知道该撤掉哪个高亮，用户仍能点一个所属 eval 已停止的说明框。只丢弃「迟到」消息不处理这两个顺序。不能改成不带身份的 `clearHighlight`，否则会撤掉同窗上随后装好的高亮。
**如何核实**：静态对照上述请求结算和终止信号寿命。验收在真实 `RemoteNode` 链路扣住安装结果，分别让终态回报先通过、让调用中止后再交付安装；检查只结算一次且无旧高亮。
**建议改法**：由服务端在发送前分配等待 id 并登记目标实例与调用世代。登记区分安装中、已装、终态，允许正确来源的终态先到且只消费一次；正常 ACK 后只为仍在等用户的记录记暂停。取消/超时先本地结束，再发带同一 id 的有界撤销；窗口对撤销先于安装、晚于安装、重发各有明确规则，未收到撤销也由窗口本地硬到期清理。
### 3. 第一轮 G10 未改到位：断线后的引导没有补报或结束规则
**严重程度**：重要；**类别**：正确性
**位置**：第三稿“引导”第 145、150 行、“目标窗口”第 175-179 行；`packages/nb-runtime/src/remote/node.ts:118-127`、`router.ts:211-220,345-372`；`docs/specs/runtime/plugin-channel.md` 输出 7、8。
**现象**：寿命表保留同实例重连后的高亮，但回报只规定「发一条」。短安装调用完成后，服务端没有在途的安装 RPC；窗口若离线时接到点击，或结算请求/回执在链路关闭时丢失，不会随重连重放。刷新则换新实例，旧页面没义务完成异步回报。`instances()` 即使修好，也只是在线快照，没有通知和连接代次。
**为什么是问题**：旧说明框可以消失，服务端仍把 eval 算作等用户，最长拖到自己等候的 300 秒（可设 3600 秒），甚至报告 `timeout` 覆盖已经发生的点击。永久离开、临时断线与刷新不能只靠同一个 `gone`（当前指目标元素消失）推断。
**如何核实**：核对运行时只收口当前链路上的请求/订阅。验收在真实通道安装成功后断链：离线点击后同实例重连、丢回报 ACK、以新实例刷新，各断言一次且正确的终态以及暂停撤销；不依靠页面卸载 RPC 成功。
**建议改法**：明确选择一种合同：断线结束本次等待并撤高亮（可保留引用/粘住），或在有限重连期内保留、窗口缓存终态直到服务端收到幂等回执，重连双方核验。定义如何观察离线/刷新（例如绑定短期限监视与窗口连接状态），以及服务端独立超时和窗口本地到期；不可只靠下一次 `ui.*` 来收本次。
### 4. 第一轮 G11 未改到位：默认嵌套独占锁让清除和替换排在等待后面
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿“引导”第 144-150 行、“要先补的上游”；`packages/neuro-book/src/plugins/agent/backend/tools.ts:197-209`、`packages/nb-harness/src/kernel/run/tools.ts:581-619`；`docs/specs/harness/runtime.md` 输出 90、94、98、100。
**现象**：`agent.tools` 的 `concurrency` 缺省是 `exclusive`。锁在工具真正执行前拿到，直到 `execute` 交回才释放。把长等待从窗口 RPC 挪到服务端工具不会缩短这段锁寿命。安装后，同一单元并发发起的 `ui.clearHighlight` 或另一个 `highlight` 不能执行；不同会话则整窗 `window-busy`。
**为什么是问题**：照缺省配置，清除/替换不能提前结束已有等待，`replaced` 的正常入口也没有了；解决计时的方法本身不会改变这点。`onWaiting` 只通知父工具计时；仅复用该回调不产生 `waiting{pending}`，现有界面和前台子代理不会凭它知道在等用户。
**如何核实**：读独占锁与默认声明；验收经真实 `ctx.invoke` 装好一条引导后再在同一父调用发清除，不靠固定延时，断言在 300 秒期限前收口。注入时钟验证与其它审批等待重叠、窗口未装好、先取消后确认都不留暂停。
**建议改法**：明确并发策略和标记所有权。若支持提前清除/替换，允许这些调用经过共享调度，把安装、替换、清除的并发裁决放回窗口；别把整段等待的锁当窗口租约。等用户用当前嵌套调用持有的幂等标记，到终态、异常与取消自动撤回，通过现有 `onWaiting` 计数；不要假借 `ctx.ask` 生成重复的向导事项。另写清它是否只影响计时，还是还要在会话/父会话显示状态。
### 5. 引导返回类型不能表示默认成功，示例还会把点错或超时当作完成一步
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿“给模型的接口”“引导”第 129-150 行；`docs/specs/agent/eval.md` 输出 7、14、15；`docs/specs/harness/runtime.md` 输出 100。
**现象**：`until` 可省略，`none` 是合法方式，要求显示后立即返回，但九个结局没有「已显示」这一支。示例只处理 `dismissed`、`asked`；`missed` 分支只有注释、随后循环自增，`gone`、`replaced`、`timeout` 也直接推进。`cancelled` 同时被写成方法结局和 eval 停止/超时的结果；后者按现有合同结算嵌套调用、终止内核，不保证模型代码能收到并处理这个返回值。
**为什么是问题**：按同一份 schema 校验，安装成功不能交回合法结局，或只能冒充点击/下一步；模型照文档写，用户第一步点错、目标没了或等待过期，第二步仍会执行，造成错误引导。
**如何核实**：逐个把 `none`、`missed`、等待超时、单元超时代入示例，并对照 eval 的 `returns-mismatch` 与内核停止合同。验收分别断言立即显示不记等待、点错和提问不推进、两种时限走各自的收口。
**建议改法**：定义互斥返回（例如 `shown` / `clicked` / `next` / 各退出原因），`asked` 与 `missed` 各有必填内容；只在符合 `until` 的成功结局推进。明确同一次事件如说明框提交与页外点击的优先级。宿主停止/单元超时是撤销及日志结算原因，不承诺给已被停止的代码一个正常返回。给可直接运行的示例，而不是以注释代替重试。
### 6. 第一轮 O7、G8 未改到位：动作超时被同时写成窗口无响应和执行结果未知
**严重程度**：重要；**类别**：正确性
**位置**：第三稿“失败”第 119 行、“目标窗口”第 169、181 行；`docs/specs/runtime/plugin-channel.md` 输出 4；`packages/nb-runtime/src/remote/peer.ts:113-145,178-184`。
**现象**：失败表加了 `outcome-unknown`，但「动作 10 秒，到时得 `window-unresponsive`」没有例外。远程写调用从帧交给链路那一刻起，超时就是 `unknown-outcome{cause: "timeout"}`，不以 ACK 为分界。`window-gone`「没派发」也不能用所有读方法的 `target-gone` 推断：读的已确认阶段断链同样用这个码，而 `highlight`/清除虽按读档审批，实际会写页面状态。
**为什么是问题**：动作可能已经生效，只是回执未到；若按超时段映射成无响应，文档的「先快照核对、不自动重试」便不会触发。把工具的审批档直接复用成 RPC effect，会对高亮等页面写入丢掉同样的不确定性。
**如何核实**：对照阶段表和 `Peer.#interrupt`，检查同一次写请求在 ACK 前后超时均为 `unknown-outcome`。验收在真实链路扣住已执行的写结果再推进 10 秒，另外发到已不在线的实例作对照。
**建议改法**：在每个窗口方法标出独立的 RPC effect；明确未派发缺窗、已派发写请求结果未知（保留 `cause`，不改投、不重试）、确定可重试的读超时和窗口明确拒绝的映射。`window-unresponsive` 不得覆盖写的 `unknown-outcome`。
### 7. 截图的 PUT 与窗口 RPC 缺少共同的提交点
**严重程度**：重要；**类别**：正确性、不变量
**位置**：第三稿“目标窗口”第 167-171 行、“截图”第 185-187 行；`packages/nb-host/src/shared/http-contracts.ts:12-26`、`packages/nb-host/src/http/dispatch.ts:79-86,144-153`；`docs/specs/runtime/plugin-channel.md` 输出 4。
**现象**：只有「一次性、绑定调用和窗口、30 秒有效」，没有规定何时占用、何时消费或谁触发成功。HTTP 处理器只有 `Request` 与事件流登记口，没有内核盖章的窗口身份或 RPC 取消信号。图可能在 RPC 失败前已上传，也可能在服务端取消后才读完；如果窗口完成 RPC 时没有有效图片，方案没定义该等还是失败。
**为什么是问题**：凭证只在开始时核对，会放过过期/取消期间仍读完的上传；只在结束时删凭证，两个 PUT 可以同时读体、竞相写同一暂存槽。RPC 与 HTTP 的响应也没有跨连接的到达顺序保证；直接用其中一路发布会把取消或缺图误报为成功。30 秒有效期也不能代替工具/RPC 的截止。
**如何核实**：静态对照两路宿主；实现后用真实 HTTP + RPC 分别扣住请求体和回执，覆盖重复 PUT、读体中取消/过期、PUT 成功而 RPC 断线、RPC 成功但未提交图。断言最多交付一张、失败不留图或挂起、不重新截图。
**建议改法**：把随机凭证作为一次调用的持有者凭证，通过已选窗口的 RPC 交给窗口，HTTP 不接受自报窗口作身份证明。入口同步把凭证从待用变成占用，限制在途读体数；边读边限长并受调用的截止与撤销控制，取字节、按实际编码校验类型和尺寸后再核对调用仍有效并提交。窗口等 PUT 成功后才回小 RPC 结果；服务端只在两者成功且同一调用仍活跃时取走暂存图，任何终止清空槽位并取消在途读。为超限/格式错误和缺图规定失败码。
### 8. 决定 3 与草案的转后台规则相反；断线清除与重连保留也缺分界
**严重程度**：重要；**类别**：正确性
**位置**：Task README 决定 3；第三稿“引用”第 68 行、“目标窗口”第 156、167、175-176 行。
**现象**：决定 3 说窗口转后台可结束粘住，草案反而说「不改选别的窗口，等用户切回」，还把这句归于决定 3。另有「断开时重选」与「同实例重连保留」：A 断线期间一次调用已经选了 B，A 重连后照表保留谁、旧引用是否仍有效，没有同一张状态表回答。
**为什么是问题**：A 已转后台、B 正在使用时，新的无引用操作按两处文字分别会去 B 和一直失败，用户能直接看到差异。只用页面加载前缀也无法兑现「换窗旧引用作废」：A→B→A 没刷新，A 可再次接受第一次粘住时发的号。带旧引用的操作自动改投 B 不能代替让无引用操作重新选窗。
**如何核实**：分别走 A→隐藏→调用、A→断开→B→A 重连、A→B→A 未刷新；验收同时断言选窗归属和引用是否作废。
**建议改法**：按已定决定把后台、断线与换窗写成明确的转移；区别「没有换窗的同实例恢复」和「已经提交新选择」。B 接手后不被 A 的重连或迟到结果改回；换窗淘汰的引用按选择代次核对，不只按页面前缀。若要永久等用户切回，需明确改决定 3，不把现稿写成它的结论。
### 9. 第一轮 O12、G9 未改到位：租约没有运行身份来源，默认等待长于租约
**严重程度**：重要；**类别**：不变量
**位置**：第三稿第 150、171、175-179、193、223-229 行；`packages/nb-harness/src/kernel/api/tool.ts:106-130`、`run/tools.ts:614-619,668-676`、`api/host.ts:545-558`。
**现象**：窗口租约要绑定 `{sessionId, runId}`，运行结束即释放。现有嵌套 `ToolContext` 有 `sessionId`、唯一 `invocation`，没有 `runId`；调用的 AbortSignal 不表示正常运行结束。租约又规定 2 分钟没调用可释放，一次默认引导等待 300 秒（上限 3600 秒），安装后没有后续调用续租。第 121 秒另一会话的普通读取就能遇到已到期的租约，原会话却还在等。
**为什么是问题**：从当前会话快照补取 `runId` 不是调用自己的身份，不能覆盖停止后异步迟到、切到下一运行；正常运行收尾也不会自动通知窗口撤租约。等待和租约各跑各的时限，会让一个仍在等用户的引导失去所有权，或让正常结束的 A 无故挡住 B 两分钟。
**如何核实**：核对 `ctx.invoke` 构造的上下文与 `SessionApi.waitRun`；验收用实际运行与注入时钟覆盖 A 正常结束后 B 立即取得、A 的引导仍在等待时 B 访问、A 的释放跨断线晚到而 B 已接手。
**建议改法**：内核向调用交出不可变的本次运行身份，后端按它接现有运行收口，窗口释放与取消按租约代次比较，断线靠窗口端的有界到期兜底。把进行中的等待计入租约寿命，或明确租约到期就是该引导的有界终态；不能让 120 秒和 300 秒各自成立而没有转移规则。
### 10. 子会话继承窗口，但不继承准入或取得租约的权利
**严重程度**：重要；**类别**：正确性
**位置**：第三稿第 60、154-167、171、177、228 行；`packages/neuro-book/src/plugins/agent/backend/subagents/tools.ts:325-329,351-357,382-387`、`subagents/relations.ts:45-51,63-75`；`docs/specs/agent/subagents.md` 输出 2。
**现象**：父会话 A 已持有窗口租约，同步派临时帮手 B 后 A 等 B；B 继承同一窗口但带不同 `{sessionId, runId}`，按条文得 `window-busy`。反过来，插件后台 A 派出的子会话默认不写 `background: true`，仅查子会话头会让 B 取得 `ui`；A 本来没有选窗时，B 还会走「任何有焦点/最近输入的可见窗」。`caller` 记录永久父子关系，fork 也照抄，不能当作这次运行正由父会话发起或有人在看。
**为什么是问题**：内置临时帮手的正常同步委派用不了同一窗，后台任务的后代却会选到无关前台窗；两个边界方向相反。放宽成同一祖先共享租约也会让异步子运行与父运行同时操作。
**如何核实**：从真实 `spawn` 的建会话与发话入口走父持租约的同步委派、没人看的后台根派子、用户独立打开子会话，以及 fork 子会话。不要用手造 `caller` 的上下文当成可达性证据。
**建议改法**：把会话树、这次运行来源、窗口选择和租约分别定义。说明同步委派是否显式交接租约；若不交接，继承仅用于定位、会返回 `window-busy`。明确后台派出的运行在声明/准入阶段如何排除，及用户独立打开后如何区别；不要用持久 `caller` 或未继承的 `background` 单独推导。fork 按草案另选，不因 `caller` 复用。
### 11. `info()` 的「正显示会话」不能从当前会话字段或订阅读出
**严重程度**：重要；**类别**：正确性
**位置**：第三稿第 156-165、231、251 行；`packages/neuro-book/src/plugins/agent/web/plugin.ts:513-527,692-715,725-761`、`session-host.ts:2180-2204`、`MessagesHost.vue:133-159`；`docs/specs/workbench/views.md` 的 `ViewContext.visible`。
**现象**：右栏消息、编辑区页面与书房案头各有一个会话宿主，按插件寿命缓存。视图停放不必卸载；即使卸载，`borrow()` 归零也只延迟放订阅、保留选择。消息视图还会给旧对话加盖层和 `inert`。任务中心的运行列表不是显示列表，窗口焦点也覆盖不到这些区别。上游改动没有给页面插件读取这些事实的合同。两个窗口同时落入第 2 档时也没有稳定的并列顺序；`lookup` 若先单独筛选，平时没有可传调用级超时的参数，800 毫秒只给 `info()` 不能约束整次选窗。

**如何核实**：按三个对话位置的真实寿命构造用例；比较收起/停放、切换编辑区标签、关闭书房聊天前后的 `info()`，并测部分窗口不回与同档并列。
**建议改法**：由对话渲染方按各位置的有效显示和挂载代次给窗口内的只读投影，不枚举缓存宿主；窗口内集合去重，规定同档排序。可直接对浏览器实例短调 `info()`，用 `not-provided` 排除未提供者，把探测失败与确定没有候选分开；并发首次调用只提交一个选窗结果，较晚的探测不得覆盖它。

### 13. 「命令面板」不能作为所有命令的兜底步骤
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿第 103-106、203、230-231 行；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchCommandPalette.vue:59-63,88-108,154-156`、`editor/web/commands.ts:91-93,117`、`packages/nb-ui/src/components/popup/QuickPick.vue:304-337`；`docs/specs/workbench/quick-open.md` 的“排序”。
**现象**：面板只显示 `expose.human !== false`、当前可用且能用空参数执行的命令，普通候选点击时交 `{}`。例如 `nbook.editor.go-to-line` 只经行号模式生成有参数的候选，不是按命令标题可搜到的行。面板入口（搜索按钮、菜单或热键）、面板搜索框和候选行也是不同的触发面；拟加的菜单项/`TitleActions` 自动标记不覆盖 `QuickPick` 候选或搜索框。
**为什么是问题**：条目能搜到不代表有可点击路径。对无参不能执行、当前不可用、仅快捷键或只在特定菜单出现的命令返回面板路径，模型能要求用户打开面板，下一步却不可能定位或成功执行。仅标记通用 QuickPick 的 item id 还会把非命令选择误认为命令。
**如何核实**：对照实际候选过滤与渲染。验收取一条无参命令、一条仅受上下文参数的命令和行号模式，验证已给路径的每步在对应界面上确有唯一目标；无路径的条目带原因，不伪造兜底。
**建议改法**：复用命令面板的候选资格，把「可查到」与「现在能到达」分开；路径表达「打开面板→用户输入→选实际候选」，为真实命令模式行提供所属命令与入口身份。条件不满足时保留发现结果而省略这条路径，不扩张为给 Agent 执行命令的接口。
### 14. 命令 id 和视图声明不能唯一标出菜单入口及当前布局路径
**严重程度**：重要；**类别**：正确性
**位置**：第三稿第 64、103-105、203-207、231 行；`packages/neuro-book/src/plugins/editor/web/title-actions.ts:32-43,82-126`、`workbench/web/titlebar/menu-items.ts:17-22`、`workbench/web/components/WorkbenchTitleBar.vue:118-167,360-364`、`WorkbenchShell.vue:145-156,562-574`、`WorkbenchRegionStrip.vue:135-136,171-196`；`docs/specs/workbench/views.md` 的 `ViewDeclaration.location`。
**现象**：同一菜单中“侧栏”“右栏”“活动栏”“面板”都调同一个命令，用 `args.part` 区别；同一编辑组里「打开预览」与「在侧边打开预览」也共用命令。`{command}` 即使在同一容器仍会歧义，`nth` 会随宽度、`when` 和溢出移位。标题栏窄时改成 ≡ 再进子菜单；视图可以被移动、合并或浮动，声明 `location` 只是默认位置，入口条的按钮标的是容器，多视图容器没有单一 `viewId`。
**为什么是问题**：目录按声明写出的上一步在当前窗口可能不在 DOM；按命令 id 能匹配到多个不同效果的项，路径说「点面板」却得到 `ambiguous`，或用序号静默指向侧栏。移动视图后目录仍会把用户带去原区域。

### 15. 第一轮 G16 未改到位：按会话生成对象文档，不能继续共用同一个挂载文件
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿第 60、123、229 行；`docs/specs/agent/resources.md` 输出 16、`agent/eval.md` 输出 16；`packages/neuro-book/src/plugins/agent/backend/plugin.ts:160-165`、`backend/schemes.ts:151-166`、`plugins/files/shared/schemes.ts:60-81`。
**现象**：第三稿要求对象文档随会话方法集，但现行 eval 只给同一个 `docs://eval/<对象名>.md`。这是激活时生成的全局文件，`mount(name)` 共用物理目录；`authorize` 能判断能否取，不能换成调用方的文件内容。后端已有调用方标记，不等于现成挂载能按它选不同结果。
**为什么是问题**：例如 A 开了对象所有方法，B 手写绑定只留一个：两个会话并发读同一地址，无法都读到自己的接口。沿用全局文件则违反新合同；按最近一次读取覆盖该文件还会使已公告的 eval 版本与文档竞态。即使签名列表过滤了，静态 `docs` 中的完整引导示例若引用被关闭的方法，仍会教模型调用不可用的方法。
**如何核实**：对照文件挂载合同与生成入口。验收同进程用两个有效方法集不同的会话，并发经实际资源工具读各自说明里的地址；再改一个会话的绑定，断言该会话下一请求的版本、可读文档和调用名称都变化，另一会话不变。
**建议改法**：定清无会话读取得到什么、有效集版本怎样落到地址或读取入口。可按有效方法集内容寻址，保留共享只读挂载而不覆盖文件；若必须保留原地址语义，须另接会话资源读取并定义与普通文件服务的差异。方法清单和适用示例取同一快照；同步更新资源与 eval 的公开合同。
### 16. 第一轮 G12 未改到位：新增失败详情的 IPC 出口没有可验证的边界
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿第 46、64、119、229、248 行；`packages/nb-harness/src/kernel/run/tools.ts:188-192,531-532,558-564`；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:413-421`、`protocol.ts:36-41`、`kernel-entry.ts:33-37`；`packages/nb-runtime/src/remote/contract.ts:44-51`。
**现象**：窗口业务失败用 RPC `errors[code]` 校验详情，通道失败的 `detail` 又是另一种值。进了 harness 后，`NestedOutcome.details` 虽标为 `JsonValue`，归一过程只检查 `text`；2 KB 只约束日志预览，不约束交给内核的值。现有 eval 只用工具的 `returns` 校验成功值，失败没有对应 schema。第三稿只说 `ToolCallError` 加 `details`，没有定义哪些失败可带、如何限长或校验、取执行原值还是经拦截的最终值。
**为什么是问题**：直接透传会把整个 Agent 工具集原先不经失败 IPC 发出的字段接到内核。单项字符串/数组限长不等于嵌套对象和编码字节总量有界；宽泛的拦截结果也未必能作为 JSON 传递。若试图改从窗口原始响应拿详情，会绕过内核已有的 `redacted`，与既有拦截语义冲突。这不是重开决定 10 的窗口内容投影。
**如何核实**：核对现有 `replyOf`、IPC 和 `invoke` 的结果来源。验收走真实 eval 子进程和工具拦截层：合法 `ambiguous` 详情可捕获；脱敏、错误形状、超量时仍保留正确的状态与码，且同一单元能接着执行。
**建议改法**：只从最终 `NestedOutcome` 取值；按业务码明确有界 JSON 详情，候选/遮挡者只带定位所需字段，整体另设编码字节和结构上限。不合格详情舍弃并诊断，不改原结局；通道失败做独立映射。将失败详情合同写进工具/eval 文档，而不是对失败沿用成功 `returns` 或原样透出 `unknown`。
### 17. `confirm: true` 提升等级，不等于决定 12 要的本次人工确认
**严重程度**：重要；**类别**：正确性
**位置**：Task README 决定 12、13；第三稿第 57、114 行；`docs/specs/agent/permissions.md` 输出 1、18、19、24；`packages/nb-harness/src/kit/approval/judge.ts:42-56`、`kernel/run/tools.ts:388-402`；`packages/neuro-book/src/plugins/agent/backend/tools.ts:184-208`。
**现象**：按现行审批，工具升级为 `exec` 只改变缺省档位。即使正处「可以写文件」，匹配整个 `ui.click` 的用户放行规则或先前的「本会话都批准」仍先于档位放行；`auto` 可由审批模型放行，`yolo` 也不必询问。等到工具执行才解析真实窗口目标，通用审批请求则只有工具、原参数、档位、原因与来源；参数若只有 `ref`，审批卡无法从中取得真实名称。尚未激活的工具还只看静态档位，不能假定动态 `effect` 第一次调用就生效。
**为什么是问题**：决定说删除、清空一类点击「要确认」。照稿实现，模型补一个布尔字段即可在上述路径执行，即便用户没有就这一步确认；即使出现卡片，也可能只显示不透明引用，或显示由模型给而非窗口解析的名字。这里审的是一次动作的确认合同，不是决定 10 搁置的防止 Agent 操作审批控件。
**如何核实**：静态对照判定顺序及请求构造；第二批合同验收以无副作用的标记控件，走冷启动、已有会话记忆、`allow-writes`、`auto` 与重新选窗，并断言未确认前执行器没收到动作。
**建议改法**：先明确「要确认」是逐次人工同意，还是仅走执行档、接受记忆及 `auto`/`yolo`。前者需要在现有内层审批中显式逐次询问（保留规则拒绝、不记住），用窗口解析的名字及一次调用的目标/选窗代次核对实际执行；不要将模型的 `confirm` 视作批准。若选后者，修改承诺并列明例外，不能称为每次确认。
### 18. eval 对象公告、内核的方法表与实际 `invoke` 准入取自不同快照
**严重程度**：重要；**类别**：不变量
**位置**：第三稿第 60、229 行；`packages/neuro-book/src/plugins/agent/backend/agent.ts:256,454,537-547`、`backend/eval/tool.ts:232-234,306-315`；`packages/nb-harness/src/kernel/run/tools.ts:64-88,538-544,578-596`、`run/loop.ts:256-275,392-404`。
**现象**：宿主先按 Profile 生成 eval 对象说明，`ToolBox.current()` 随后才做工具名校验与去重。实际嵌套准入用这一批保留的工具集。eval 启动单元时却再读一次 `forProfile`（当前设置，没有前一层去重）。即使加了后台过滤和方法哈希，两处各自调用同一 helper，也不是同一份生效快照。
**为什么是问题**：模型请求在途时用户关闭 `ui`，等响应回来时，`invoke` 仍按发请求的工具集，eval 的全局又已消失；反向打开会让代码看见 `ui`、调用却被核心拒绝。即使没人改设置，配置里同提供商名先到的工具也能让一个出现在文档和内核的对象方法不进入核心的 `byId`。下一次请求的 `tools-changed` 不能修正已经发出的这次说明。
**如何核实**：实际 harness + eval 子进程，用脚本化模型卡在已收到请求未回模型结果的位置，在此时改绑定；检查对应版本的文档、全局列表和嵌套准入一致，下一请求再切代。另测同名工具取舍后最终只呈现可调者。
**建议改法**：在既有工具集改变生效的边界，先按会话筛选并解析去重，再从同一份只读工具快照派生公告/文档版本、单元的全局和 `invoke` 白名单。若移除要立即中止旧调用，则单独写清收口，不在执行时悄悄用一个新目录替换旧的调用合同。
### 19. Profile 的一行开关如果只改现有工具 id，关闭 `ui` 无法跨第二批保持
**严重程度**：重要；**类别**：正确性
**位置**：Task README 决定 2、14；第三稿第 60、229 行；`packages/neuro-book/src/plugins/agent/shared/settings.ts:18-21,36`、`shared/profile-tools.ts:29-35,61-74`、`shared/contracts.ts:89-100`、`backend/tools.ts:82-106`、`web/profile-view.ts:477-507`。
**现象**：现行绑定只保存每个工具的 `added`、`removed`；`ToolCatalogEntry` 没有 `global` 归属。把现有行折叠、关闭时逐一删方法，并不会记住「这个对象已关闭」。第二批新方法加入主创的 optional 时，旧的 `removed` 没有这些 id。手写绑定只去掉一部分、某个方法是必需工具、关闭 `eval` 等情况下，一个普通开关也不能如实表达状态。
**为什么是问题**：用户第一批关闭整个 `ui`，升级第二批反会看到 `ui` 重新出现，且冒出点击、填写等能力。按字符串前缀分组或只检查显示行既不能排除已被内核拒绝的声明，也不能修正用户绑定。主创与伴聊 bot 目前共用 `MAIN_PROFILE_TOOLS`，在共用常量加方法还会让 bot 缺省获得它们，违反第 60 行。
**如何核实**：按现有合并式列出第一批关闭后的绑定，再代入第二批的默认新增 id；对照 `backend/builtin/profiles/main.ts:21,36` 与 `plugins/bots/backend/profile.ts:21,37`。验收覆盖升级、部分启用、必需方法、禁用 eval、两窗口并发改不同绑定。
**建议改法**：按有效声明的 `global.object` 给目录分组，持久化对象级意图并定义与方法级绑定、必需工具和 `eval` 的优先级/呈现。组关闭要压住后来新增的方法；如果只做当前方法的批量编辑，不能标成持久的对象开关。缺省方法只加到主创与临时帮手各自的声明，不改 bot 共用基表。
### 20. 前台限定工具与后台 Profile 的 `required` 合同没有交代
**严重程度**：重要；**类别**：接口与合同
**位置**：第三稿第 60、228 行；`docs/specs/agent/contributions.md` 输出 4、14；`docs/specs/harness/runtime.md` 输出 15；`packages/neuro-book/src/plugins/agent/backend/profiles.ts:71-79`、`shared/profile-tools.ts:29-35`；`packages/nb-harness/src/kernel/run/loop.ts:256-265`。
**现象**：现行 Profile 可把已登记工具列入 `required`，用户绑定不能去掉必需项。目录检查工具是否已登记，不按会话来源检查。把带前台限定标记的工具从后台生效集过滤掉后，内核在第一次模型请求前把这种 Profile 判成 `tools-missing`，并将会话置只读直到重开，不是「正常运行但没有 ui」。
**为什么是问题**：内置主创用 optional 不触发，但共享的上游标记仍可用于用户级/第三方 Profile，且没有限制这些 Profile 只能开前台会话。后台任务失败会看起来像插件安装损坏；若为了避免只读把工具留在列表，又违反了后台不暴露及不先产生审批的要求。
**如何核实**：用已登记、标为前台限定的无副作用工具，给 Profile 声明为 required，再用该 Profile 开前台和后台会话各跑到首个请求。以 optional、用户绑定加入两例对照，检查模型清单、内核方法表及是否产生审批事项。
**建议改法**：在准入合同中选定 required 的语义：限定标记禁止用于 required 并在 Profile 检查/后台创建时给清楚的配置错，或让 required 按同一适用条件判断。不要全局放宽 `tools-missing`；条件筛选在产生文档、工具可用集与审批之前，不能靠执行阶段返回 `no-window`。
### 21. 第一轮 G6 未改到位：截图移出了 RPC，结构化消息仍没有整帧字节合同
**严重程度**：重要；**类别**：正确性
**位置**：第三稿第 14、46、87、94、145、181、248-253 行；`packages/nb-host/src/shared/socket.ts:15-16,37-43`、`server/rpc-listener.ts:79-91`、`server/rpc-listener.test.ts:80-90`；`packages/neuro-book/src/plugins/agent/backend/frames.ts:15-32`、`remote.ts:154-158`。
**现象**：第三稿只规定估算 token、条数与字段长度。`snapshot` 同时回树文本和结构化元素；`find` 还包含嵌套路径；`asked` 与失败详情也另有字符串。单字段的字符长度和数组条数不能替代给整个 JSON 编码后的 UTF-8 字节设上限。例如 100 条各长 4,000 字的中文描述，光描述约 1,200,000 字节，已超过 1,048,576；转义与包络还有开销。这是限长策略的反例，不是稿件规定了这组数字。
**为什么是问题**：窗口回的是正常业务结果而非图片，仍可被宿主当超长帧而断线，连带同链路上的其他调用与引导。对 `maxTokens`、`limit` 的缺省建议也不能保证调用者请求更大时仍在预算内。
**如何核实**：现有宿主用例覆盖「超限后断开」，本轮未重跑。新增验收应经实际 WebSocket 传多字节与需转义内容，覆盖返回、失败详情与回报，断言有界降级/失败、随后小调用仍成功；第三稿的超大视口截图用例只覆盖 HTTP 图片。
**建议改法**：在调用双方派发前给输入、成功、失败和回报各定聚合编码预算，并留 RPC 包络余量。大快照/目录结果按结构截断或分段；不适合裁剪的消息返回明确定义的尺寸错误。按字节检查的先例在 Agent 的 `whole` / `PAGE_BYTES`，别用 token 估算代替传输检查。
### 22. 第一轮 G10 未改到位：工具撤回不会自动中止已受理的引导等待
**严重程度**：重要；**类别**：不变量
**位置**：第三稿第 150、171、175-179 行；`docs/specs/agent/contributions.md` 输出 6；`packages/neuro-book/src/plugins/agent/backend/tools.ts:247-264,277-305,329-355`；`packages/nb-runtime/src/plugins/host.ts:571-587`、`remote/node.ts:617-624`。
**现象**：工具提供方撤回时，现有包装最多等 5 秒，再给上层 `tool-unavailable`；它不会触发那次调用的 `ToolContext.signal`，真正的 `dispose` 要等底层执行结束。引导这时在服务端等独立回报，短 RPC 已完成，不再持有能把撤回传到窗口的信号。若用 `dispose` 去结束等待，会变成双方互等；进入提供入口停止之后，原 `context.remote` 又会带一个已触发的停止信号，不能把最后一条撤销 RPC 当保证。
**为什么是问题**：调用者已经得到工具不可用，底层却继续持有等待登记、暂停标记及旧引导；窗口端若没同一时刻停，用户仍看得到已失效的步骤。超时能最后兜底，却不能代替撤回时的结算驱动。
**如何核实**：对照撤回、运行取消与入口停止的三个信号来源。验收通过真实插件撤回工具贡献，保持窗口连接和会话运行，分别卡在安装中和已进入等待，检查本地结算、暂停和租约收回；窗口没收到撤销也必须到期。
**建议改法**：让等待登记和上传槽位受服务端提供入口代次所有，入口停止或贡献撤回时主动终止本地登记，不依赖工具 `dispose`。窗口端随其入口停止清理；后端仍可发消息时按等待 id 撤销，不能发时明确靠窗口的有界到期或已约定的失联终态。
### 23. 截图上传成功不一定有图片进入模型结果或会话日志
**严重程度**：重要；**类别**：正确性
**位置**：第三稿第 54、185-188 行；`docs/specs/agent/eval.md` 输出 4、`docs/specs/harness/runtime.md` 输出 61、96；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:293-315,368-374`、`packages/nb-harness/src/kernel/run/tools.ts:558-564`、`kernel/model/omp.ts:170-183`。
**现象**：嵌套工具结果只记预览和 `imageCount`，图片不随该条事件写入。真正入日志、给模型的图片在外层 eval 返回；同单元所有工具和 `display` 合计只接受前 8 张，多余的只增加丢弃计数。第 9 次 `ui.screenshot` 仍可完成 PUT、交回 `ok`，却没有它那张图。非视觉模型另有现成的文字占位。
**为什么是问题**：设计把「上传校验通过」「用户付出一次审批后截图成功」「图进会话日志且模型看到」连成一个结局，实际是不同层。当 8 个槽已被占用时，再重画、上传乃至询问也不能兑现图像结果；代码没有可用的图片句柄，不能补看第 9 张。
**如何核实**：静态对照嵌套日志与外层合并。合同验收用脚本化模型走真实 eval IPC，混合 `display` 和截图令最后一张越过 8 张，比较代码返回、外层结果和日志；再用非视觉端口验证占位，不需要真实模型。
**建议改法**：写明继承 eval 的共享图片限额与模型能力限制；若方法的成功承诺有图，须在实际捕获前预留本单元结果位，没额度就给可判的失败，预留随失败或取消释放。若保留现有丢弃语义，则不要承诺每次成功都会入日志和给模型；说明如何分单元捕获。
### 24. `clicked` 只证明点中入口，不能证明目录下一步已可定位
**严重程度**：重要；**类别**：正确性、验收
**位置**：第三稿第 94-107、129-150、251 行；`docs/specs/settings/settings-window.md` 输出 22；`packages/neuro-book/src/plugins/settings/web/settings-window.ts:713-733,763-767,788-805`；`workbench/web/commands/view-commands.ts:131-135`。
**现象**：即使用实际设置键和左栏入口，用户在有草稿的设置页点击「外观」时，`select` 先经 `requestLeave` 弹确认，并未切节。用户可选「继续编辑」，目标设置永远不出现。打开视图的成功也只表示布局已改，视图在下一次渲染才出现。回报合同的 `clicked` 能早于两种转换，不应被当作后一目标已出现的信号。
**为什么是问题**：模型按第三稿只等 `clicked` 就高亮下一步，用户正确点击也会得到 `not-found`；若一律扩大 DOM 等待时间，又会把「用户选择不离开」变成不可解释的超时。修正示例 id 或处理 `missed` 不能覆盖这条路径。
**如何核实**：对照设置模型的暂存动作、确认和取消，以及视图的渲染边界。应用验收从有未保存草稿的设置页走实际路径，正确点左栏后分别取消和确认；不要求用户放弃草稿，只有目的节及其控件可见才推进。
**建议改法**：明确 `clicked` 是输入回执，路径的后续标识只有在对应状态实现后才可用。对导航等步骤写明可观察的到达条件和阻塞后的重新观察/结束规则；首批示例可复查快照或目录，不依赖第二批的 `waitFor`，也不把用户取消当作点错或自动替用户确认。
### 25. 第一轮 G14 未改到位：停止调用还缺 `commandId`，`runId` 只标识逻辑运行
**严重程度**：建议；**类别**：接口与合同
**位置**：第三稿第 20、193、251 行；`packages/neuro-book/src/plugins/agent/shared/remote.ts:112,177-182`、`backend/task-rows.ts:181-194`；`packages/nb-harness/src/kernel/run/commands.ts:375-394`、`run/tree.ts:79-83`；`docs/specs/agent/sessions.md` 输出 30。
**现象**：稿已修复普通的点名停止，带 `runId` 不会误停另一个 id 的运行。但远程 `abort` 的对象还必填 `commandId`；第 193 行的实参不能直接登记到现有合同。`runId` 在回退到运行中途再继续时会复用，窗口只用租约代次保护提示条清理，并没有约束已经发往服务端的停止命令。任务清单已将这个边界写成已知限制。
**为什么是问题**：照写示例会在参数校验就失败；若把「不会停下一次」理解成对每次恢复执行也成立，测试只换一个新 `runId` 会过，却不覆盖回退后继续同一 id 的路径。
**如何核实**：静态核对远程方法生成和 `abortCommand` 的比较条件。第二批可把停止扣在真实通道上：常规 A 收口后开 B 应得 `{aborted: false}`，同 id 恢复场景按选定合同断言；两者都检查 `keepQueue: true`。
**建议改法**：调用既有停止入口时生成 `commandId`，一次用户操作只用一个身份，保留点名和保留队列。明确继承任务清单对同一逻辑运行的已知限制；若提示条必须只停贴条时的那一段执行，则要在服务端用运行排程代次核对，不能仅在窗口检查租约。

**核实口径**：本轮对照固定第三稿、决定、首轮处理记录、现行 Spec 与 `16b45166c` 检出代码；各条所列验收是拟议场景，不是本轮运行结果。首轮实测及既有用例未重跑；未运行合同测试、类型检查、e2e、实验或开发服务。决定 10 搁置的安全边界不在本轮范围。
