### 1. 窗口 RPC 没有规定谁有权截屏或代替用户操作
**严重程度**：阻断；**类别**：安全与性能
**位置**：设计稿“结构”“截图的同意与不公开的内容”；`packages/nb-runtime/src/remote/router.ts:105–110,170–191,398–415,434–459`，`node.ts:810–849`。
**现象**：设计只把审批与选窗放在 eval 的服务端工具里，没有规定浏览器提供方的 `callers`、调用方身份或请求授权。`{client}` 的路由不做 `{project}` 那套项目租约检查，普通项目插件和其它窗口都能路由到目标；是否拒绝取决于目标的合同。命令先例不是无条件可调：其 `contracts.ts:193–204` 明写 `callers: ["server"]`。这一限制对正常内核调用成立，但不是恶意本机对端鉴权：WebSocket 宿主 `rpc-listener.ts:70–88` 检查 Origin、不带认证地接入路由，登记描述的 `kind` 来自握手，转发时从该描述取位置，不能据此把 `location`/`plugin` 当服务端凭据。
**为什么是问题**：直达窗口的方法不经过 `ui` 工具的规则、审批、会话检查；不给窗口端定义授权，产品正常的跨实例调用就没有明确边界。若还承诺防同机非受信客户端，复用现有路由的信任模型本身也不够（`plugin-channel.md`“边界与兼容”与 ADR 0022 明确完全信任）。
**如何核实**：静态沿 `{client}` 分支、`handleRequest` 的 `callers` 检查和命令合同对照；`plugin-channel.md` 输出 2–4。未构造违规对端或调用实际窗口。
**建议改法**：窗口端每个方法限制为服务端及指定入口，按内核调用方身份拒绝其它常规入口；在合同中写明本机受信边界，不把过滤当认证。若截图同意要约束不受信本机客户端，先在宿主区分真实服务端与外部链路的身份，或用宿主签发、绑定窗口代次与调用的一次性授权；代价是握手/授权协议与宿主测试，而不是换一个 RPC 名字。用三个真实实例测项目、另一窗口、非预期服务端入口均拒绝，且窗口无副作用。

### 2. 服务端插件的 `context.remote.instances()` 列不出任何窗口
**严重程度**：阻断；**类别**：正确性
**位置**：设计稿“现状里要用到的事实”“目标窗口”第 1 步；`packages/nb-runtime/src/remote/node.ts:1140–1148`，`router.ts:144–151,418–425,449–453`。
**现象**：`instances()` 返回 `Promise<RemoteResult<InstanceDescriptor[]>>`，不是数组。服务端插件的调用也走 `#upstream.request`，目标写 `server`；路由给 hub 装的上游只接 `member`，对自己返回 `target-gone`。`runtime/instances` 的成功分支只在接收成员请求时走；命令系统的例子是已知窗口 id 的 `.at()`，没有证明服务端能列窗。
**为什么是问题**：字面实现时，每个 `ui.*` 都在发现窗口的第一步失败；甚至会把查询故障错误报成“请打开窗口”。这与 `plugin-channel.md` 输出 8 不符，是已有合同缺口，不是 `nbook.page-agent` 的实现回归。
**如何核实**：检出 `7c1844e0693150c5379a92650f6d256f0b754073`，`bun --no-env-file -e` 用检出源码的 `createApplication`、`createRemoteRouter`、`createLinkPair` 起一服务端一窗口，由两个真实激活入口各调 `ctx.remote.instances()`。握手成功，路由表有两项；服务端插件得到 `{ok:false,code:"target-gone",cause:"target-gone",detail:"服务端自己的目标不经路由转发"}`；窗端插件得到 `{ok:true,value:[…两项]}`。使用正式插件入口与查询（进程内 JSON 链路，不是真 WebSocket），未直调私有函数。
**建议改法**：先让 runtime 的服务端插件查询兑现输出 8（同一份路由目录的本地查询），在 `routing.test.ts` 用服务端插件入口断言列表含已握手浏览器、绑定项目 id/代次，断开后不含它；不要把路由对象暴露给 page-agent 或让窗口替服务端查询。应用区别“目录查询失败”和“成功但没有合格目标”。

### 3. 页面动作能触达代表用户授权的控件，移出设置 API 不等于隔离权限
**严重程度**：阻断（第二批）；**类别**：安全与性能
**位置**：设计稿第 63–66、87、129、133、173 行；`packages/nb-agent-ui/src/vue/wizard/AgentApprovalWizard.vue:63–69,114–124`；`packages/neuro-book/src/plugins/agent/web/session-host.ts:1606–1622`、`backend/remote.ts:168–179`。
**现象**：稿中未命名控件仍能按角色和名字操作，`never` 只举了删除账号、显示密钥。审批按钮用普通 `@click`，单项选择立即提交；会话 RPC 以用户身份处理，界面的永久批准还可写入用户规则。移出设置读写 API 没有移出这些页面上的写入口。`press` 的间接作用也不由目标元素上的一个标记自动约束。
**为什么是问题**：普通 `write` 动作一旦能碰到审批与权限控制界面，服务端会把它当成人的决定；“先批准外层 eval”不等于批准它随后代替人做授权。即使一个会话的调用严格串行，多个会话/对话位置也共用窗口，不能靠 eval 串行保护窗口里的授权控件。
**如何核实**：静态对照代理的定位与合成动作合同、向导事件、用户身份盖章和规则写入链。没有实现 `ui` 或操作真实向导。
**建议改法**：把不能委托给 Agent 的授权与执行控制面列为第二批前置：审批/持久规则/模式或等价权限设置，含其键盘入口、浮层与 Portal；从动作真正接收者和命令边界拒绝，不只给稳定名加标。保留普通动作 `write`；选一条权限设置、一个待审批会话和一条快捷键路径，用真实窗口证明 Agent 动作不能产生用户审批或规则变更，人工输入仍正常。未来换可信输入时沿用能力边界，不能仅看事件 `isTrusted`。

### 4. “始终遮挡”尚未覆盖所有会返回隐私的出口
**严重程度**：阻断（隐私验收）；**类别**：安全与性能
**位置**：设计稿第 66、70、83–91、109、123–131、166 行；`packages/neuro-book/src/plugins/models/web/components/HeadersEditor.vue:34–53,110–121`；`packages/nb-harness/src/kernel/run/tools.ts:531–534,559`。
**现象**：稿中具体规则是把 `value` 换成 `•••`、图中盖色块，但同时返回元素数组、可访问名、文字、业务 `key`、候选与遮挡者说明、变化摘要和标注。没有规定这些都消费同一份已经裁剪、脱敏的视图。例如私有子树中的文字可经祖先可访问名被拼进未标私有的一行；只盖图的矩形也不保证克隆/渲染阶段未处理过私有子树。模型的请求头编辑器现在是普通文本输入，凭据形状只有警告，不能靠 `type="password"` 兜底。
**为什么是问题**：屏幕结果会进工具消息和会话存储；上游 `redacted` 是结果/日志的传播机制，不会识别 DOM 私有值。截图批准也不放开这些数据。一个出口遗漏就违反“总是遮住”，且旧图或旧差异不会随 UI 变化自行收回。
**如何核实**：静态对照各输出形状、组件和工具结果路径；未读取实际设置、未做截图。
**建议改法**：在窗口设置统一的私有投影：结构化字段、名字来源、错误与差异、截图标注一律从裁剪后的数据取；私有子树在截图克隆和编码前排除/遮挡，模型设置入口同时标记。用完全合成的假值验证普通与已批准截图、`annotate`、文本树/元素数组、动作前后与失败响应均不含假值；再覆盖子树、Portal 或产生外部可访问名的关联节点。页面文本按非可信数据编码，转义/截断不要破坏字段边界。

### 5. 现有审批没有把一次截图的同意绑定到实际窗口
**严重程度**：重要；**类别**：不变量
**位置**：设计稿第 97–108 行；`packages/neuro-book/src/plugins/agent/backend/tools.ts:139–148`、`web/session-host.ts:1606–1622`、`web/permission-rules.ts:98–105`；`packages/nb-harness/src/kit/approval/hook.ts:84–121`、`review.ts:141–148`。
**现象**：稿中写 `{kind: "screen", value: "<窗口标题>"}`；通用 Subject 能按 `kind`/`value` 匹配规则，但 `subjects(args)` 不拿会话上下文，提供方未激活时有路径压根不取 Subject。审批模型拿工具、参数、档位和路径，不拿 screen Subject；人工卡片也不自动显示这个 Subject。非命令工具的 `remember` 缺省记整个工具，永久批准同理。窗口可以在用户回答、并发排队期间转后台、断线重连或过 2 分钟租期；标题不是窗口身份。
**为什么是问题**：无法兑现“审批卡上写明截哪个窗口”；实现若在批准后照普通选窗规则重选，就会把对窗口 A 的单次同意用在 B。记忆若实际覆盖所有窗口，卡片却只展示 A，授权范围也会误导用户。
**如何核实**：静态串起工具判定对象、审批请求、模型输入、记忆写入与选窗顺序；稿中没有准备目标和执行重验的合同。未调用真实模型、未批准截图。
**建议改法**：审批前由宿主解析窗口和截图范围，向规则、人工与 `auto` 传同一份受信的目标描述；一次批准绑定该次调用、窗口文档代次和范围，执行前核对，失效就失败或重新审批，绝不把旧批准转用。保留“本会话都允许”，但明确它是记某窗口/范围还是允许后续任意合格窗口，永久规则同样明示；可匹配的身份不要用可重名/改名的标题。优先补现有审批的受信目标接口，不另起一套许可流程。

### 6. 截图没有约定从浏览器向服务端的二进制通路，文字预算也不是帧预算
**严重程度**：重要；**类别**：正确性
**位置**：设计稿第 38–47、59–60、70、85、89、110、141、144 行；`docs/specs/runtime/plugin-channel.md` 非目标和“WebSocket 传输与握手”第 2 条；`packages/nb-host/src/shared/socket.ts:15–16`；`packages/neuro-book/src/plugins/agent/backend/remote.ts:154–158`。
**现象**：设计只指定现有远程服务，没定义浏览器生成的图片怎么交给服务端；规范要求二进制走有时效的 HTTP 资源地址。若把图直接填进远程结果的 JSON，1 MiB 帧上限扣掉包络后连 768 KiB 原始字节都装不下。`maxSize` 无单位、无缺省和硬上限；8,000 字符仅约束文本树，元素数组、标签、错误和差异没有合计字节上限。传进 eval 后“最多 8 张”是数量限制，不约束单图编码字节或画布大小。
**为什么是问题**：一张大图或一次大型快照可以让正常调用断线，而不是得到可恢复的结果；前端裁图与服务端持久化也没有共同预算。把快照上限定得小不等于远程返回有界。
**如何核实**：静态对照 WebSocket 上限和 base64 的 4:3 膨胀、现有 Agent RPC 按编码字节报 `result-too-large` 的先例；宿主调研中的 omp 给模型图另设 1024×1024、150 KiB。这不是现有 `ui` 的实测上限。
**建议改法**：控制帧只回传小结果和短时传输句柄；服务端为本次获准捕获建立受限上传/取用路径，窗口只传已脱敏图片，校验归属、期限、像素、MIME、编码与字节，在取消、断线、成功及超限时回收。最终由服务端转成 eval 图，不把中转地址当长期附件。给整帧留包络余量，对结构化快照、错误、操作参数都设硬上限和明确失败。验收包含多字节文本、超限画布/图和句柄过期，不只测小图能解码。

### 7. 选窗没有定义“同项目但没在看本会话”，隐藏时又有两个互斥结局
**严重程度**：重要；**类别**：正确性
**位置**：设计稿第 97–104 行；w00032 t16 决定 2；w00033 t01 决定 3；`packages/neuro-book/src/plugins/agent/web/session-list.ts:46–64`；`packages/neuro-book/src/web/host/window.ts:236–253`。
**现象**：目录的项目绑定是窗口的，不是它展示的会话；窗口信息只问焦点、可见性、输入时刻。会话面板可切到“全部”，因此“用户正看会话的窗”“同项目有焦点的窗”“有项目/没有项目的窗”不是一回事。第 101 行规定粘住的窗口变隐藏就重选，第 104 行又允许读和动作在隐藏窗口照做；没说明仅剩隐藏窗、`info` 超时、项目会话从另一个项目窗打开时走哪条。
**为什么是问题**：两窗同书也可能在不同文档/对话。把窗口标题和动作结果事后告知不能补回误操作。浏览器实例默认只绑定一个项目，切换会重载，没有“把选中的会话主项目切进目标窗”的隐式机制。
**如何核实**：静态对照目录、窗口启动与会话筛选权限；逐条代入“只剩隐藏窗”和“可见窗只显示另一个会话”。未跑实际窗口焦点实验。
**建议改法**：把候选与退路写成表：是否优先显示该会话的前台同项目窗、没有这类窗是否允许下沉到另一可见同项目窗、没有可见窗的结果、查询失败与并列排序。转后台依已定决定解除粘窗，不把可见性的未知当成可操作；动作/截图派发前在目标窗重验，失败不暗换对象。若要优先识别显示本会话的窗口，只在私有 `info` 返回必要的匹配结果，不恢复被移出范围的通用公开状态 API。

### 8. `window-gone` / `timeout` 不能概括已派发动作的结局
**严重程度**：重要；**类别**：正确性
**位置**：设计稿第 91、104 行；`docs/specs/runtime/plugin-channel.md` 输出 4；`packages/nb-runtime/src/remote/protocol.ts:63–84`、`remote/routing.test.ts:511–523,548–586`；`packages/nb-harness/src/kernel/api/tool.ts:56–96`。
**现象**：设计规定途中断开/刷新得 `window-gone`，失败表未区分写动作是否已派发。RPC 写请求一发出，未收到 ACK 也可能已执行；断线、取消、超时都交回 `unknown-outcome`。普通工具实现的 `ToolResult.status` 没有 `unknown`；该状态由内核结算 `NestedOutcome` 时产生，不能假定适配层把远程失败展开就会保留。
**为什么是问题**：例如点击已创建章节，响应前刷新；模型把 `window-gone` 当作“没执行”，在新窗口再点就会重复创建。选窗故障转移也不能改投一次已派发的动作。
**如何核实**：静态对照 `failureFor`、既有 ACK/断线/超时测试和嵌套工具结果类型；没有重跑已存在的用例。
**建议改法**：分别写明未派发、已派发结果未知、窗口确认拒绝的映射；原样保留 `unknown-outcome` 与原因，向 eval 明说先核对、不自动重试。若需要 `ToolCallError.status === "unknown"`，把远程不确定结局接入 harness 的结算合同，而非把它转成普通已知错误。验收覆盖动作生效后回复丢失、动作未派发两种分支。

### 9. 窗口粘住、独占租约与元素引用缺少共同的身份和失效规则
**严重程度**：重要；**类别**：不变量
**位置**：设计稿第 25–26、68、101–104、114–116 行；`packages/nb-runtime/src/remote/router.ts:207–220,411–415`；`packages/neuro-book/src/web/host/window.ts:233–253`；`packages/nb-harness/src/kernel/api/tool.ts:127–136`；`agent/eval.md` 输出 11。
**现象**：引用示例为窗内从头编号的 `eN`。换窗后若目标也有 `e12`，仅收到这个编号的窗口无法区分旧引用和本地引用；整页刷新生成新实例 id，网络重连却可沿用同一 id 并替换链路，`.at({client})` 不绑定旧链路。服务端按会话粘 2 分钟，与窗口互斥的 5 秒空闲租约不是同一寿命；稿中没定义怎样原子取得/续期、等待点击算不算空闲、换窗或过期的迟到清理能否释放新租约。首批已经允许两会话争用唯一的高亮，但把互斥租约放到第二批。工具实例每会话每工具一份，不能自然共用这份状态。
**为什么是问题**：逐方法实现会造成 `snapshot`、`highlight`、后续 `click` 的权威不一致；旧引用能命中新窗口的同号元素，或未结束的调用被另一个会话覆盖。eval 重置也不是所有 `ui` 工具状态的释放钩子。
**如何核实**：静态代入 A、B 两窗各有首个 `eN` 和一条同 id 重连，核对路由、页面启动 id、工具和 eval 的寿命。没有实现引用或租约。
**建议改法**：给引用加可验证的文档/引擎代次（或等价的不复用令牌）；胜出的窗口在同一个同步步骤核对租约代次和调用身份后才操作。服务端所有 `ui` 方法用同一个按会话的选择器，窗口统一持有互斥与清理，从首批有状态的高亮就生效。写清断线/重连、转后台、在途调用、超时释放和回退/分支、fork、Profile 切换、会话关闭/重开、服务重启时哪份状态留、哪份失效。验收至少覆盖两窗编号相同、同窗两会话争抢、旧调用清理晚于新租约三个反例。

### 10. 等用户点击缺少短 RPC 受理与独立的收口通路
**严重程度**：重要；**类别**：不变量
**位置**：设计稿第 61、114、144、150、166–167 行；`docs/specs/runtime/plugin-channel.md`“非目标”；`packages/nb-runtime/src/remote/peer.ts:113–145,178–185,265–285,342–356`；`docs/specs/harness/runtime.md` 输出 100。
**现象**：`until: "click"` 对 eval 是一次等到用户动作的调用，但设计只定了普通 RPC，没有说明如何拆成短受理与后续完成。通道合同明确不把等用户的长交互挂在一次 RPC。RPC 的超时独立于 eval；收到取消或断开只会触发窗口处理函数的 `signal`，不会自动移掉浮层、监听与租约。若用户永远不点，单靠“这一轮结束清理”又会循环等待：这一轮正等这次工具先结束。
**为什么是问题**：窗口断线重连、Esc、关闭按钮、取消或被替换都可能让服务端继续等、或让旧浮层和监听留在页面。迟到的点击或完成消息不能结算后来那一次高亮。
**如何核实**：静态沿 RPC 请求、取消和关链；对照嵌套调用的 2 秒取消宽限结算。没有起浏览器或运行 `ui`。
**建议改法**：沿现有通道合同，先用短请求装上引导并受理一个有身份的等待事项，点击/退出经独立短消息按身份结算，考虑完成早于订阅、断线和重复通知。只认绑定窗口/文档/租约及该目标的真实点击。给实际等待设独立到期与用户取消入口；将单元停止/超时、目标丢失、失焦到隐藏、窗口/会话/插件停止和通道中断明确映射为终态，撤销等待标记、浮层、监听与租约只做一次。不要用延长 RPC 超时替代这一闭环。

### 11. 把高亮接进 `onWaiting` 前，须定义暂停的是哪段时间
**严重程度**：重要；**类别**：不变量
**位置**：设计稿第 150 行；`docs/specs/agent/eval.md` 输出 14；`packages/nb-harness/src/kernel/api/tool.ts:99–104,123–129`、`run/tools.ts:197–205,405–413,600–617`；`packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:293–327,451–499`、`kernels.ts:272–304`。
**现象**：现有 `onWaiting` 是父工具传给内核的回调，内核只在同步提问或审批前后调用；嵌套工具执行者没有设置入口。eval 用一个等待计数暂停整个单元的计时，第一个等待暂停、最后一个结束才恢复。等待期间 JS 不被冻结，其它已并发执行的调用也可以继续；若高亮用缺省 `exclusive` 并在执行期间等点击，其余嵌套调用则排在它后面。进行中的内核不被空闲回收，登记表在全忙时允许超过 8 个。
**为什么是问题**：把“请求还在途”或“浮层仍在”直接当作等用户，连窗口定位、RPC 和其它工作也可能不再计时。遗漏结束通知会永久暂停；相反，使用随 RPC 的短超时又误伤正常引导。单元缺省 30 秒和最多 2,000 个嵌套调用都不能替代等待寿命。
**如何核实**：沿 `invoke → judge/askUser → execute → Deadline` 与并发锁、内核登记表静态核对；未添加等待标记或运行内核实验。
**建议改法**：在 harness 提供随当前调用/取消自动收回的等待标记，仅从窗口确认已挂上、能接收响应之后开始；连接、装载、查找与清理照常计时。明确并发政策：例如限制引导等待期间的其它 `ui` 操作，同时说明该段按全单元暂停的取舍，并设独立等待上限。用注入时钟测运行耗时扣除、两个等待重叠、RPC 未受理、取消早于/晚于挂上；每种都要证明计时恢复且没有旧等待者。

### 12. 同一份方法声明不能原样同时登记为工具和窗口 RPC
**严重程度**：重要；**类别**：正确性
**位置**：设计稿第 39–47、57–66、91–93、148 行；`packages/nb-runtime/src/remote/contract.ts:44–51,76–85,121–139`；`packages/neuro-book/src/plugins/agent/shared/points.ts:43–72`、`backend/eval/objects.ts:60–69,89–121`。
**现象**：窗口 RPC 的顶层 `input` 必须为对象 schema。直接用 `Type.Union` 表达平铺的互斥定位不被接受。工具的 `exec` 档不属于 RPC 的 `read | write`，公共失败表里的 `timeout`、`denied` 是 RPC 保留码，不能原样进业务 `errors`。即使通过合同登记，当前签名生成器也不显示字段说明、范围和缺省，不会从 TypeBox 的业务失败表自动生成文档。
**为什么是问题**：若实现把稿中的“唯一来源”理解成三处原样登记，合同会在启动时被拒。若各自手写等价接口，模型文档、远端校验和工具执行容易对同一参数给出不同结论。
**如何核实**：`bun --no-env-file -e` 使用现成 TypeBox、检出的正式 `defineRemoteService` 与 `tsType`。互斥定位顶层联合、在 `errors` 中登记 `timeout`/`denied`、RPC `effect: "exec"` 分别被拒。带字段说明的联合仍只打印 `{ref: string} | {target: string; key?: string}`。直接调用合同构造与文档打印，未走插件激活或 RPC 传输。
**建议改法**：保留一个业务 schema 集，从它明确派生模型参数/返回和 RPC 的受信信封、效果与错误映射。先定平铺定位的表述及运行时互斥校验，再让文档输出可选、范围、单位、缺省和失败码。不要用宽泛的 `{}` 或 `Unknown` 绕过校验。锁一个含联合、说明、合法与非法样例的契约测试，兼顾现有 eval 对象的生成结果。

### 13. 后台拒绝要发生在选窗和人工询问前，不能从审批模式推出
**严重程度** 重要　**类别** 正确性
**位置** 设计稿第 63–64、104、108、173、184–185 行。`packages/nb-harness/src/kernel/run/control.ts:58–64,173`、`tools.ts:383–417`，`packages/nb-harness/src/kit/approval/judge.ts:42–56`，`docs/specs/agent/modes.md` 输出 1–3。
**现象** `background: true` 是会话头属性。后台会话仍创建 `RunControl.interactions`，并照常交给运行。只有缺少交互通道且判定 `ask` 才返回 `approval-unavailable`。如果后台判定放在工具 `execute` 里的选窗逻辑，`ask` 和转人工的 `auto` 会先挂出事项，甚至到不了设计规定的 `no-window`。另一处笼统称 `discuss`、`plan` 自动拦动作，但闸门配置为 `ask` 时会询问。拒绝规则优先，`yolo` 不能越过模式闸门，`allow-writes` 仅对已通过前置判定的写动作免问。
**为什么是问题** 两处写法不能预测同一次后台截图会立即失败还是挂起。`auto` 放行、`yolo` 或命中规则的后台调用也必须遵守不可选窗的决定，不能只补一个“没人点审批卡”的分支。
**如何核实** 静态对照 `agent.ts:341–361` 的后台任务创建、`session.ts:136–146` 的会话上下文、运行交互通道和权限判定顺序。现有 `ask` 工具的后台早退有单独用例（`builtin-tools.test.ts:532–541`），不代表审批也早退。
**建议改法** 为 `ui` 规定独立于审批模式的后台准入，在解析目标、启动审批模型或建人工事项前短路。选定统一的结果码并区分外层 eval 已被拦的情形。列出规则拒绝、闸门 `deny` / `ask`、四种审批模式与后台矩阵，验收断言后台没有选窗/截图和新增待审批事项。

### 14. 停止条需要绑定正在操作的那次运行
**严重程度** 重要　**类别** 不变量
**位置** 设计稿第 116、167 行。`docs/specs/harness/runtime.md` 输出 30、120。`packages/neuro-book/src/plugins/agent/shared/remote.ts:112`、`backend/task-rows.ts:181–194`。`packages/nb-harness/src/kernel/run/commands.ts:375–394`。
**现象** 稿中只有会话标题和调用 `abort` 的描述。远程 `abort` 要带 `sessionId`、`commandId`，还支持 `runId`、`keepQueue`。省略 `runId` 就停受理那刻在跑的运行。旧提示条会在空闲几秒后才收起，命令也会在跨进程途中延迟。
**为什么是问题** 用户按了 A 的停止，命令到达时会话已开 B，就会误停 B。缺省处理还会取消停止者有权取消的缓冲区条目，与对话中普通“停止”保留排队的行为不一致。
**如何核实** 静态核对 `abortCommand` 的点名分支、任务中心和对话停止先例（`web/session-host.ts:1783–1789`）。没有触发真实运行。
**建议改法** 提示条由宿主传入对应的 `sessionId`、`runId` 和当前租约代次。复用任务中心 `abort({sessionId, runId, commandId, keepQueue: true})` 的点名规则及有界清理。收到 `{aborted:false}` 或租约失效后收起旧条，断线期间给明确结果，迟到的清理不得撤掉下一运行的新条。验收增加 A 收口后延迟送达停止，断言 B 和缓冲区不受影响。

### 15. `highlight` 的说明文字必须在窗口按纯文本渲染
**严重程度** 重要　**类别** 安全与性能
**位置** 设计稿第 32、61、114、140、158 行。[Driver.js Popover Configuration](https://driverjs.com/docs/configuration.md#popover-configuration) 和 [1.14.0 发布产物](https://cdn.jsdelivr.net/npm/driver.js@1.14.0/dist/driver.js.mjs)。
**现象** `ui.highlight` 收模型提供的 `title`、`text`，权限为 `read`。Driver.js 的标题和描述允许 HTML。1.14.0 产物把两者经同一个 `innerHTML` 写入函数插进窗口 DOM，随后才运行 `onPopoverRender`。稿中没有规定受信窗口的文字渲染边界。
**为什么是问题** 如果适配层原样传递模型文字，禁用 `evaluate` 仍未隔离模型与窗口 HTML。标题、说明可来自快照里的非可信文字。即使 CSP 拦住脚本，页面也会出现可伪装成应用界面的内容。
**如何核实** 静态查看官方配置说明和固定版本的 ESM，核对内容赋值及挂钩先后。没有装依赖或在页面执行内容。
**建议改法** 把纯文本契约写进服务端参数和窗口适配层。在交给库之前转义，或由适配层创建只用 `textContent` 的说明。用含普通标签形状的合成文本验收呈现内容为字面值、窗口没有对应新增元素。将其与点击真伪和不抢焦点一同纳入选型门槛。

### 16. 全局对象文档与方法实际可用集不是同一份清单
**严重程度** 重要　**类别** 正确性
**位置** 设计稿第 93、148–150 行；`packages/neuro-book/src/plugins/agent/backend/tools.ts:113–119,151–158`；`backend/agent.ts:536–547`；`backend/plugin.ts:160–165`；`backend/eval/objects.ts:60–68,125–134`；`backend/eval/tool.ts:72–78,424–434`；`packages/nb-harness/src/kernel/run/loop.ts:267–275`。
**现象** 设计要求每个会话按实际工具集列出全局对象，并从 TypeBox 生成方法文档；Profile 工具绑定可去掉可选方法。运行时只把当前 Profile 的方法传给内核，但 `docs://eval/<对象>.md` 在插件激活时从全部有效声明一次性生成，内含未绑定方法。与此同时 eval 版本哈希仅含对象名与摘要，不含当前方法集；Harness 会过滤代码专用方法的版本变化通知。当对象至少仍有一个方法时，增删该对象的方法既不会改 eval 的说明版本，也不会让模型收到 `tools-changed`。
**为什么是问题** 模型可能照文档调用当前会话不可用的方法，得到 `unknown-tool`；方法变更后继续使用旧的接口假设。用户移除工具绑定属于明确支持的 Profile 行为，不是插件实现偶发故障。
**如何核实** 静态沿 `forProfile → sessionDeclarations → codeToolsOf` 与 `writeEvalDocs → evalMethods → objectDoc` 的数据来源；核对 `objectsSection` 的哈希字段，以及内核对 `code: true` 工具变更的通知过滤。没有修改绑定、激活插件或跑模型。
**建议改法** 让方法文档和版本都由同一份会话有效方法清单生成；渐进式文档需带会话身份/代次，或采用能反映每会话方法清单的地址。清单改变时递增 eval 工具版本并通知模型。验收覆盖同一对象保留一个方法、移除另一个方法，以及方法签名变化时文档内容、调用准入和下一请求通知一致。

### 17. “随会话删除”没有现行删除路径，归档也不会删除截图
**严重程度** 重要　**类别** 不变量
**位置** 设计稿第 110 行；`docs/specs/agent/sessions.md:37–49,122–124`；`docs/specs/harness/session.md:100–105,134–145`。
**现象** 设计承诺截图存会话日志并“随会话删除”。现行 Agent 会话远程合同没有删除操作，Spec 明确写“删除会话不在本 Spec”；归档只改会话状态。截图作为 `ToolResult.images` 进入日志，超过 16 KiB 的图片字符串外置到该会话的 `blobs/`；fork 还会复制所选路径引用的 blob。因此当前没有兑现设计所说的删除语义，归档与删除不等价，fork 也会保留副本。
**为什么是问题** 即使 UI 永不公开截图，批准捕获后的页面内容仍会跨重启长期留在状态根中。用户不能用现有会话操作清除它；删除来源会话（若未来增加）也不能清除 fork 的副本。以现有事实无法给出图像保留时限或删除保证。
**如何核实** 静态核对会话远程方法表、会话数据生命周期合同、日志大块内容存储及 fork 对 blob 的复制规则；未创建、归档或删除会话。
**建议改法** 在设计里明确截图是持久会话数据，并说明归档不删除、fork 复制保留，删除保证留待独立的会话删除合同；若本功能必须承诺可删除，就先定义跨 fork 的保留与清理语义，再落地入口，不把“随会话删除”当作现成能力。

## 未发现问题的方面
- eval 的 `ToolResult.images` 已有端到端日志、会话大块存储与 fork 复制通路，也会按对话格式作为工具结果图片交给模型；这条现有链路不解决窗口 RPC 的跨进程图片传输，后者见 #6。
- `ToolResult.status` 不能表达 `unknown`，但 `ctx.invoke` 返回的 `NestedOutcome` 可表达；eval 的 `replyOf` 保留此状态并告知先核对再重做。遗漏的是窗口 RPC 的映射合同，见 #8，不是 Harness 完全缺少未知结局通路。
- 主创和临时帮手声明 eval 为可选工具；`defaultTools: false` 的 Profile 不自动装入 `defaultForAll`，但显式 `optional` 仍生效。此设置与设计拟让用户从 Profile 绑定中移除 UI 方法相符。
