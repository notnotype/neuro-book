## F1 通知卡片仍画在详情对话框与遮罩之上，`inert` 只挡指针与读屏、不改绘制

- **严重程度**：重要；**类别**：UI 与不变量（需真实浏览器复现）
- **位置**：`packages/nb-ui/src/components/feedback/NotificationStack.vue:123-134`（`:inert="detailOpen"`）；层级登记 `packages/nb-ui/src/theme/z-index.ts`（`notification` 9050，`dialog` 9000）；计划依据 `plan.md:101`
- **现象**：对话框打开期间视口只是 `inert` 加 `aria-hidden`，`z-index` 仍是 9050，高于对话框遮罩与面板（9000 起）。所以最多 4 条通知（加折叠小条）照常画在遮罩上面，也画在对话框面板上面。计划第 101 行写的“改成 inert 后……也不会盖住对话框的关闭与复制按钮”不成立：inert 元素不接收指针事件，是点击穿透到下面的按钮，但视觉上按钮被通知卡片盖住，用户看见的是卡片、点下去触发的是看不见的“关闭”或“复制原文”。底部居中或右下的视口在 390px 宽、对话框居中偏下、或 4 条通知叠起来约 300 到 400px 高时，最容易压到页脚。
- **为什么是问题**：模态对话框之上还浮着一列可见通知，与“模态”的视觉语义矛盾；而且这正是计划与 Spec 输出 11 想避免的情形，只是把“能点”改成了“看得见但点不到”。
- **如何核实**：真实浏览器里 Lab `NotificationStack` 场景 `six`（已有夹具）点“详情”，390 与 1600 两种宽度下 `nbdev shot`，看对话框页脚是否被通知卡片盖住；或在控制台读 `getComputedStyle` 的 z-index 比较。静态可核对：`NB_Z_INDEX.notification > NB_Z_INDEX.dialog`，且 `NotificationStack.vue` 没有在打开期间改 z-index 或隐藏。
- **建议改法**：对话框打开期间让视口不参与绘制（例如 `visibility: hidden` 或 `opacity: 0` 配合已有的 inert，进出用同一个短过渡），或把视口在对话框打开时降到遮罩之下；两者都要在 Spec 输出 11 里写明。至少在 Lab 用 `six` 场景补一张打开对话框的截图证据。

## F2 展开态下“滚到最新”在任何一次条数变化时触发，包括移除与到时消失

- **严重程度**：重要；**类别**：正确性（从代码推断，happy-dom 没有布局，需真实浏览器复现）
- **位置**：`packages/nb-ui/src/components/feedback/NotificationStack.vue:55-57`
- **现象**：`watch(() => notifications.value.length, () => { if (expanded.value) scrollToNewest(); })`。条数变少也会触发。展开着、列表已滚到中间读较早的通知时：点任意一条的关闭键、或一条限时通知到时消失，列表都会被拽到底部。注释与 `NotificationStack.md`（“展开与新通知到达时滚到最新一条”）说的是“新通知到达”，实现是“条数变了”。
- **为什么是问题**：用户在展开的长列表里逐条关掉较早的通知（这正是展开的主要用途）时，每关一条视图就跳到底部，要重新滚回去；与文档不符。
- **如何核实**：Lab `six` 场景展开后把列表滚到顶，点上面某条的关闭键，读 `list.scrollTop`；或读代码即可确认触发条件不区分增减。
- **建议改法**：只在条数增加（或最新一条的 id 变了）时滚：`watch(() => notifications.value.at(-1)?.id, …)`，或比较新旧长度。补一条 e2e 或 Lab 取证：展开、滚到顶、关一条，`scrollTop` 不变。

## F3 展开态下卡片比收起态窄 8px（`margin: -4px` 配 `w-full`）

- **严重程度**：重要；**类别**：UI（从 CSS 盒模型推断，需真实浏览器复现）
- **位置**：`NotificationStack.vue:137-141`（列表层 `flex w-full flex-col gap-2` 加展开态类）与 `:210-215`（`.nb-notification-list--expanded {margin: -4px; padding: 4px}`）
- **现象**：列表层是 `width: 100%`（border-box）。给 `width:100%` 的块写负外边距不会让它变宽，只是整体平移；根容器是 `items-end` 或 `items-center` 的列式 flex，按外边距盒对齐：外边距盒宽 W-8，靠右时边框盒落在 [4, W+4]、内容盒（扣掉 4px 内边距）为 [8, W]；居中时内容盒为 [4, W-4]。结果：展开时卡片宽度从 W 变成 W-8，文字重新折行，整列发生布局位移；同时 4px 的“给阴影留位”也被滚动容器裁掉（`shadow-lg` 向外扩十几像素，`overflow-y:auto` 在内边距盒处裁切）。作者的意图（四周多出 4px）只有在宽度为 auto 时才成立。
- **为什么是问题**：违反 `ui-development` 的“零布局位移”；展开瞬间每条通知换行、变高，折叠小条与卡片宽度也与收起态不同。
- **如何核实**：真实浏览器 Lab `six` 场景展开前后各量 `.nb-notification` 的 `getBoundingClientRect().width`；预期差 8px。
- **建议改法**：展开态不用负外边距，改为 `width: calc(100% + 8px)` 配 `margin: -4px`（并让根容器对齐不影响），或用一层固定的 4px 内边距始终存在于收起态（收起态也留 4px，根容器相应收 4px），保证两态卡片同宽。

## F5 `Notification` 的动作行是否出现用 `computed` 读 `slots`，插槽有无动态变化时不更新（相对 base 的回归）

- **严重程度**：建议（目前没有找到动态插槽的调用方）；**类别**：正确性
- **位置**：`packages/nb-ui/src/components/feedback/Notification.vue:37,41`（`const slots = useSlots(); const hasAction = computed(() => slots.action !== undefined || props.actionLabel !== "")`）
- **现象**：`useSlots()` 返回的对象不是响应式的，`computed` 只依赖 `props.actionLabel`，第一次求值后一直缓存。父组件用 `v-if` 或渲染函数让 `action` 插槽后来才出现或消失时，动作行不跟着变。base 的模板直接写 `$slots.action || props.actionLabel`，每次渲染重新求值，没有这个问题。
- **如何核实**（已实跑）：lab 里 `slot.lab.test.ts`：宿主用渲染函数在 `show` 为 false 时不给 `action` 插槽，改成 true 后 `nextTick`，`[data-notification-action]` 仍不存在（`expected false to be true`）。配置 `vitest.lab.config.ts`，命令 `cd packages/nb-ui && bunx vitest run --config /tmp/review-w00028-t04-impl/lab/vitest.lab.config.ts`。
- **建议改法**：模板里直接用 `$slots.action`，或把 `hasAction` 写成普通函数（`const hasAction = (): boolean => …`）在模板中调用，不缓存。

## F6 `CopyButton` 走 execCommand 退路后把焦点“交还”按钮：鼠标点击也可能画出焦点环

- **严重程度**：建议；**类别**：UI（浏览器行为，需真实浏览器复现）
- **位置**：`packages/nb-ui/src/components/controls/CopyButton.vue:69-72`（`finally` 里的 `button.value?.$el.focus(...)`）
- **现象**：退路里先 `area.focus()`（textarea 总是匹配 `:focus-visible`），再由脚本把焦点移回按钮。Chrome 的 `:focus-visible` 规则是：脚本移动焦点时，上一个获得焦点的元素若匹配 `:focus-visible`，新元素也匹配。所以用鼠标点“复制原文”后，按钮会带着键盘焦点环出现。计划第 84 行与 `DetailDialog.vue` 的初始焦点注释都专门避免“一打开就在复制按钮上画焦点光晕”，这里在退路上又画出来了。只在没有 `navigator.clipboard`（`http://` 局域网地址）或被拒绝时发生，剪贴板 API 路径不动焦点。
- **如何核实**：真实浏览器里用 e2e 同款的“去掉 `Navigator.prototype.clipboard`”页，鼠标点“复制原文”，读 `button.matches(":focus-visible")` 或截图。
- **建议改法**：只在焦点确实被拿走时才还（`const had = document.activeElement === button` 之前记下），且还时用 `focus({focusVisible: false})`（Chrome 与 Firefox 支持；不支持的浏览器忽略该选项）；或者鼠标点击后根本不还焦点，只在 textarea 被删后让对话框的焦点陷阱自己处理。

## F7 对话框打开时同一次更新里给聚焦着的子树加 `aria-hidden`，Chrome 会拦下并在控制台报错

- **严重程度**：建议；**类别**：UI 与可访问性（需真实浏览器复现）
- **位置**：`NotificationStack.vue:131-132`（`:inert="detailOpen"` 与 `:aria-hidden="detailOpen ? 'true' : undefined"`）
- **现象**：用户点“详情”时，焦点正在视口里的那颗按钮上（Chrome 点按钮会聚焦）。`aria-hidden` 在 `open` 变 true 的同一次渲染里加到包含焦点的祖先上；Chrome 对“后代仍持有焦点”的 `aria-hidden` 会拦下，并在控制台输出 “Blocked aria-hidden on an element because its descendant retained focus”。拦下之后效果上只剩 `inert`（inert 本身已把子树从辅助技术树里拿掉），所以功能不坏，但：1）Lab 的 `lab:shot` 读 `report.json` 的控制台，这条消息会被当作控制台错误；2）`aria-hidden` 在这里是多余的，`inert` 已足够。
- **如何核实**：真实浏览器打开 Lab `NotificationStack` 的 `detail` 场景，点“详情”，看开发者工具控制台；e2e 用例没有断言控制台，所以不会暴露。
- **建议改法**：去掉 `aria-hidden`，只留 `inert`（同时在 `NotificationStack.md` 与 Spec 输出 11 里把“inert 并 aria-hidden”改为“inert”）；`inert` 不支持的旧浏览器（Safari 15.4 以前）不在 nb-ui 的支持范围时无需兜底。

- **F3 补充**：展开态还挂了 `nb-ui-scrollbar-stable`（`scrollbar-gutter: stable`，`src/styles.css:6`）。经典滚动条的平台（Linux、Windows）上，展开的瞬间不论是否溢出都在右侧预留一条滚动条宽（thin 约 8 到 11px），而收起态没有。所以展开前后卡片宽度差可到约 16 到 19px（负外边距的 8px 加滚动条槽），且折叠小条与卡片的“同宽”只在展开态内部成立。若要保持两态同宽，收起态也要留同样的槽，或展开态只在真正溢出时才出现滚动条（去掉 `scrollbar-gutter`，接受溢出那一刻的 8 到 11px 变化）。同样需要真实浏览器量一次。

## F10 `hasNotificationDetail` 用了类型谓词 `detail is string`，否定分支的类型是错的

- **严重程度**：建议；**类别**：代码质量
- **位置**：`packages/nb-ui/src/composables/useNotification.ts`（`hasNotificationDetail` 的签名）
- **现象**：对 `string | undefined` 写 `detail is string`，函数返回 false 时 TypeScript 把参数收窄成 `undefined`；但全空白字符串也返回 false，它仍是 `string`。现在三处调用方都只用肯定分支（`detailFields` 里提前返回后、`openDetail` 里提前返回后），所以没出错，但谁写 `if (!hasNotificationDetail(x)) { x /* 类型是 undefined，运行时可能是 "  " */ }` 就会得到一个说谎的类型。
- **建议改法**：返回普通 `boolean`，调用处自己 `item.detail as string`；或保持谓词但把形参类型换成 `string | undefined` 并在注释里写明否定分支不可用。

## F12 新用例“折起来的限时通知照常到时消失”用 30ms 时长，在负载高时可能不再覆盖它要测的状态

- **严重程度**：建议；**类别**：测试
- **位置**：`NotificationStack.test.ts` 的“折起来的限时通知照常到时消失”
- **现象**：先发 30ms 的通知再发常驻，`flushPromises` 后断言“只显示常驻”。机器负载高（本次审查期间 `loadavg` 16 到 20）时 30ms 可能在首次渲染前就到了，此时“被折起来”这个前提不成立，用例仍然通过，等于没测折起来时的计时。同一问题在 base 的“限时通知到点消失”（30ms）已经出现：我跑变异实验时它因此失败（`expected [] to have a length of 1`）。
- **建议改法**：不要用毫秒级真实时长去赌渲染先于到时：折起来之后再断言 `fold()` 存在（此时限时通知还在），再等它消失。例如 `duration: 300`，先断言 `fold()?.textContent` 是“还有 1 条较早的通知”，再 `vi.waitFor` 到它消失。

## F14 退路在 `await` 之后才调 `execCommand("copy")`，Safari 与 Firefox 对用户激活的要求没有核实

- **严重程度**：建议；**类别**：正确性（未验证）
- **位置**：`CopyButton.vue:78-79`（`(await writeWithClipboardApi(text)) || writeWithExecCommand(text)`）
- **现象**：没有 `navigator.clipboard` 时 `writeWithClipboardApi` 是 async 函数，`await` 让后续在微任务里执行；`execCommand("copy")` 要求处在用户手势里。Chrome 用时间窗口的“短暂激活”，没问题；Safari 对“手势”的传递更严（经 Promise 微任务是否保持，没有查到确切记录）。e2e 只在 Chromium 跑。写进 `CopyButton.md` 的“交互”时没有限定浏览器。
- **建议改法**：没有 `navigator.clipboard` 时同步走退路，不经过 `await`（把“有没有 API”的判断提到 `copy()` 里，没有就直接同步调 `writeWithExecCommand`）；被拒（reject）的那一支仍然只能在 `await` 之后。
