## 新发现

### 1. [建议] “同一实例直接调用同一实现”与按调用方门面/插件隔离的关系含糊，最容易误读的一处

- 位置：`docs/proposals/multi-instance-runtime-topology.md`（第 4 节“提供”与“按调用方生成门面”两条）；`docs/proposals/plugin-data-model.md`（第 5 节“内核按调用方生成 Storage 服务实例，每个插件只能访问自己的命名空间”）。
- 现象：拓扑稿一面写“`ctx.remote.provide(合同, (consumer) => 门面)` 登记一次。**同一实例内的调用方直接调用同一实现**、不序列化”，另一面规定门面按“消费方实例 + 插件 + 入口 + 激活代次”生成、底层数据按插件归属隔离；数据稿要求“每个插件只能访问自己的命名空间”，K1 验收又有“两插件隔离”（进程内传输下）。三处文本并存，同实例调用到底走共享单实例还是按消费方门面没有单一判据。
- 为什么是问题：若“同一实现”照字面实现为共享单实例，服务端实例内两个插件本地调用 `nbook.storage`（user 分区在同实例）会拿到同一门面，按插件隔离失效；若要隔离成立，同实例也必须按消费方生成 single-flight 门面，则“直接调用同一实现”是不当措辞。两种读法导向两套 K1 实现，写错一侧会返工。
- 如何核实：三份文本交叉；未运行程序。现行 `services.md` 的 single-flight 按提供者作用域，本次按调用方门面是明确要改的合同（预期改动表已登记），同实例路径属于该改动的边界，需要写清。
- 建议改法：写明“同一实现”指同一提供者登记与同一 factory；同实例调用同样按消费方取得 single-flight 门面、同样校验调用方身份与激活代次，差别只在参数/结果不序列化、开发模式按合同校验。或反向：若同实例有意豁免按调用方门面，则写明 Storage/配置的同实例隔离改由消费上下文在调用时判定（并给出该判定入口）。

### 2. [建议] 消费上下文的跨进程防伪边界未写明（内核帧还是业务参数）

- 位置：`docs/proposals/multi-instance-runtime-topology.md`（第 4 节“受控代理的委托”）；`docs/proposals/plugin-data-model.md`（第 5 节客户端代理段）。
- 现象：委托规定“上下文由内核签发、随调用转发，**不能由业务参数自报**；普通插件之间的业务调用仍按本跳身份标记”，但没有说服务端如何区分“内核签发的上下文”与客户端自报的数据：若上下文作为业务参数 JSON 的一部分转发，跨进程需要签名/密钥与验证方；若作为内核路由帧的独立字段（业务参数中的同名字段被拒绝），防伪由内核协议自身保证。两稿都没有选边。
- 为什么是问题：消费上下文是 Storage/配置按插件、按客户端隔离的入口，防伪边界属于 K1 前置“委托上下文”的合同内容，实现两个方向工程量差别大；且现行合同已有一致的既有模式可沿用（`platform/files.md` 根能力“不能仅凭公开根身份获得它”、`workspace/resources.md` 写入来源“由宿主依调用路径填写……调用方不能自称为其它来源”），不写等于放着两个现成口径不用。
- 如何核实：拓扑稿与数据稿原文；platform/files.md:33、resources.md 来源段。未运行。
- 建议改法：写明消费上下文由内核路由帧携带、与业务参数分离，业务参数中出现同名字段被拒绝（沿用 resources.md 的来源填写模型）；或写明签发方、验证方与凭证机制。同时把这条口径写进预期改动表 `runtime/services.md` 的委托上下文条目。

### 3. [建议] “底层数据按插件归属、跨激活代次保留”的创建与释放规则未定义

- 位置：`docs/proposals/multi-instance-runtime-topology.md`（第 4 节“按调用方生成门面”）。
- 现象：门面寿命已定（消费方停止释放、提供方停止永久失效、重激活新门面），但“底层数据按插件归属，**跨激活代次保留**”没有规定：谁创建（首个消费方解析时？提供方激活时？）、提供方入口停止/插件禁用/实例停止时何时释放、跨代次保留是否连带运行状态（重激活后新门面看到旧状态还是新状态）。提供方停止时门面永久失效，底层数据却“保留”，两者的收口边界没有写。
- 为什么是问题：与现行合同有张力：`runtime/plugins.md` 输出第 13 条要求提供者服务实例在依赖者释放后释放、入口停止即撤回本次激活产出；`runtime/lifecycle.md` 要求所有运行资源有 owner 并登记收口。“跨激活代次保留”若无释放规则，要么每次停止再激活累积数据，要么与入口作用域收口冲突。K1 前置列了“门面与订阅的两端寿命”，底层数据属于该前置的一部分，未定义会在 K1 实现时临时造语义。
- 如何核实：拓扑稿原文对照 plugins.md 输出 13、lifecycle 收口合同；未运行。
- 建议改法：把“底层数据”限定为提供方插件显式登记的插件作用域持久对象（生命周期=插件实例/登记撤销，受 lifecycle 收口），并明确重激活后是否恢复状态（建议：不承诺恢复运行状态，跨代次保留只指 Storage/配置这类已有持久 owner 的数据）；内存态 per-consumer 门面状态不跨代次保留。补一条验收：提供方停止→重激活后旧状态不复活、底层数据释放路径可诊断。

### 4. [建议] 文生图走查“通知 project 入口”与租约规则未接上

- 位置：`docs/proposals/multi-instance-runtime-topology.md`（第 10 节文生图“回调”与“交付”段；第 4 节 `.at({project: id})` 目标规则）。
- 现象：走查写“项目在运行：**通知 project 入口**有可交付结果”，这是服务端实例内 server 入口到项目实例的跨实例动作；但 `.at({project: id})` 规定“只对已在运行的项目，且调用方需持有该代次的租约”，server 插件不持租约（长期持租约会阻止项目进入 idle-grace），通知是 RPC、订阅推送还是短租约借用没有写；项目处于 `idle-grace` 时收到通知是“取消关闭回到 available”还是丢弃也没有定义。
- 为什么是问题：正确性有兜底——设计同时写“项目入口**激活时或**收到通知时”查询，通知丢失也不丢结果，所以不构成阻断；但实现时通知路径需要一个设计决策，且借用类实现会在 idle-grace 期间打断宽限期，属于走查到实现之间必填的空白。
- 如何核实：拓扑稿第 10 节与第 4 节交叉；未运行。
- 建议改法：把通知定为服务端侧经路由的事件推送（不经租约），或明确 server 入口申请短租约借用且 idle-grace 中的借用不视为重新打开；并写明 idle-grace 期间到达的回调只置 ready、不通知（等下次激活时查询）。补一条验收：项目 idle-grace 中回调到达不唤醒子进程。

### 5. [建议] “连接代次”只有标题、正文未定义该量

- 位置：`docs/proposals/multi-instance-runtime-topology.md`（第 3 节“**连接代次与绑定代次分开**”）。
- 现象：标题用“连接代次”，正文只有连接表、绑定表与重连规则，没有定义连接代次/连接身份；断线重连恢复原绑定时，旧连接上未完成请求与订阅的结算归旧连接、新连接重建订阅，这个“旧连接 vs 新连接”的区分没有显式建模（走查里连接表只标“W 在线”）。上一轮建议的实质规则（恢复/拒绝重启/不改投/旧请求订阅作废/同代次 resync）都已写全，缺的只是这个量本身。
- 为什么是问题：不构成返工；但 K2 前置列“重连规则”，连接身份是连接表与断线结算的实现前提，正文用词与内容不符会让 K2 认为重连规则尚未完全固定。
- 如何核实：拓扑稿第 3 节全文；未运行。
- 建议改法：在握手与连接表处给连接一个身份/代次，写明“连接断开即结算该连接上全部在途请求与订阅；重连建立新连接代次，绑定代次按第 3 节规则恢复或拒绝”。

### 6. [建议] 公开键的清单声明与 store public 的一致性校验、重名冲突未写

- 位置：`docs/proposals/plugin-data-model.md`（第 4 节“键名与类型静态声明”）。
- 现象：清单静态声明（限定名、标量类型、未就绪取值、owner）与 store 激活时绑定读取函数已接上，但两条校验没有写：清单声明与 `defineStore` 的 `public` 键集合不一致时（声明了未实现、实现了未声明）如何处理；两个插件声明同一限定名时（重名冲突）如何处理。上一轮建议原文明确要求“明确重名冲突、跨插件引用与非法类型的校验”，修订稿只收了非法类型（登记时拒绝）与未绑定（按未就绪），没收重名。
- 为什么是问题：`when` 校验依赖键表的唯一性与正确性；重名会让同一键的 owner/类型二义，破坏“未就绪/拒绝”判定。`workbench/commands.md` 已有同款先例（命令重复 id 两条一起拒绝、未登记键在登记时被拒），照抄即可，属于 K5 前置“公开键的静态声明”内的小缺口。
- 如何核实：数据稿第 4 节与 commands.md 登记冲突规则对照；未运行。
- 建议改法：写明同名公开键冲突在登记期整体拒绝该键（与命令重复 id 规则一致）；入口激活时逐键核对清单声明与 store public，缺绑定按未就绪、多余键拒绝或记诊断。

### 10. [轻微建议] 服务端镜像“按未就绪处理”的三类条件缺“连接结束”，与 K5 验收不对齐

- 位置：`docs/proposals/plugin-data-model.md`（第 4 节“在本实例求值；镜像按客户端隔离”）。
- 现象：正文列“镜像缺失、重连后等待基线、来源入口停止，都按‘未就绪’处理”，没有列“连接结束”；K5 验收却有“断线后旧镜像撤回”。断线时客户端入口并未停止，按正文三类条件推不出撤回。
- 为什么是问题：镜像寿命少了断线这一触发条件，正文与验收不一致，实现时需自己补语义；不返工。
- 如何核实：数据稿第 4 节与拓扑稿 K5 验收行对照；未运行。
- 建议改法：条件补“连接结束（断线）即撤回该客户端的全部镜像，重连后重新同步基线”。
