### 1. [建议] RPC 失败码需要区分确定未执行与结果未知，目标停止规则应注明适用阶段

- 位置：`docs/proposals/multi-instance-runtime-topology.md:114`、`:133`、`:135`、`:191`。
- 现象：RPC 总则说“请求已送出而连接断开时返回 `unknown-outcome`”；Files 的只读 `list` 走查规定“途中 P#1 停止返回 `target-gone`”。后者没有写入丢失问题，不能据此认定稿件已经规定写请求返回确定失败；但若实现把同一目标停止分支用于写请求，写盘后、成功响应返回前退出就会出现分类重叠。`timeout`、`cancelled` 也未说明如何表达执行结果未确认。
- 为什么是问题：`runtime/lifecycle.md:54` 明确“调用方断线不证明远端已终止”，`:111` 规定非幂等动作断线后可能结果未知；`storage/persistence.md:133` 要求保存中断为“未确认”，不能报成明确未写入。仅按目标是否存活给错误码，会让已提交写入与尚未派发的失败无法区分；RPC 错误分类与后续领域恢复会各自实现不同判据。
- 如何核实：已核对总则、只读走查和现行生命周期/保存状态表，确认具体失败码尚无阶段映射；沿用到写请求的错误分类属于条件推断，未发生运行验证。因此列为 K1 定稿建议，不把只读走查当作已核实的写请求矛盾。
- 建议改法：给请求补一张派发/接纳/执行/回包与取消的状态表。能够证明未派发或未执行时才返回确定失败；写请求派发后无法证明结果时统一 `unknown-outcome`，附 `cause: target-gone | timeout | cancelled | disconnected` 等原因。明确 ACK 不能证明未产生副作用，并修订 Files 走查及验收。

### 2. [阻断] 远程订阅只绑定连接与实例，遗漏两端插件入口的激活寿命

- 位置：`docs/proposals/multi-instance-runtime-topology.md:117`。
- 现象：正文规定“订阅同时挂在订阅方连接与提供方实例上，任一结束即取消”。提供方插件禁用、激活失败后收口、或订阅方入口停止时，实例与 WebSocket 都可以继续存活；按这两个条件订阅不会结束。同实例调用还没有可绑定的订阅方连接。
- 为什么是问题：`runtime/plugin-channel.md:30`、`:44`、`:71` 现有合同把订阅同时登记到连接与插件入口作用域，且浏览器句柄随激活作用域释放；`runtime/plugin-hot-plug.md:57` 要求入口停止后交出和借入的订阅都关闭。`runtime/plugins.md:27`、`:33` 区分实例与入口激活代次，`:113` 要求订阅归激活作用域。新定义会留下旧入口的 sink、事件回调与提供方引用，违反撤回与旧代次失效。
- 如何核实：对照三项 Spec 的订阅与激活身份合同，以及 `packages/nb-runtime/src/plugins/host.ts:589`、`:710` 中每次激活独立的 `entry-work`；推演“保持实例和连接 → 单独停用一端入口”，设计列出的取消条件均不成立。未运行程序。
- 建议改法：订阅归两端精确入口激活代次，跨实例时另绑定相关连接；任一入口开始停止、提供服务撤回、实例失效或连接结束均触发取消并阻断迟到事件。本地调用采用相同入口作用域规则；重连只能重建当前仍有效的订阅，不能恢复旧代次。

### 3. [阻断] 客户端 Storage 代理缺少保留原消费插件与客户端上下文的委托规则

- 位置：`docs/proposals/multi-instance-runtime-topology.md:111`、`:112`；`docs/proposals/plugin-data-model.md:132`、`:139`。
- 现象：数据稿要求客户端 `nbook.storage` 提供本地服务并转发到分区拥有者，同时要求“每个插件只能访问自己的命名空间”。若插件 A 先调用客户端 Storage 代理，再由代理通过自己的 `ctx.remote` 发 RPC，拓扑规定的真实调用方变成 `nbook.storage`；服务端会为 Storage 自己生成实例。若反过来让请求任意填写 owner 或 caller，又破坏内核按调用方隔离。相同问题适用于配置代理以及 `local` 记录需要的稳定客户端身份。
- 为什么是问题：拓扑只定义每跳 caller 的“实例、插件、入口”，没有内核代理的委托能力、原始消费上下文或稳定客户端上下文的传递；`storage/persistence.md:58` 要求句柄绑定主体、客户端与 owner，`:67` 禁止凭 owner 字符串取得他人的句柄，`:79` 禁止无客户端上下文的服务端调用默认选某个浏览器。当前本地装配只把提供者的同一值交给消费者（`packages/nb-runtime/src/services/composition.ts:423`），`ActivationContext` 按激活入口建立（`plugins/host.ts:706`），不会自动穿透下一跳代理。直接落地会让所有消费方写同一个 owner，或迫使 K4 再改变 K1 的 caller 合同。
- 如何核实：按“A 入口 → 本地 nbook.storage 代理 → 远程 nbook.storage/server”的规定路径逐跳核对身份；对照源码的服务解析/激活上下文和 Storage 身份合同。这是已核实的设计接口缺口，运行效果未验证。
- 建议改法：在 K1 明确区分立即调用入口与由内核签发的消费上下文。为受控代理提供不可由业务参数伪造的委托/绑定能力，保留消费插件、入口激活代次、主体、稳定客户端与精确项目代次；普通插件间业务调用仍使用本跳身份。补本地直用与客户端代理访问同一命名空间、两个插件隔离、local 客户端分区的等价验收。

### 4. [阻断] 按调用方生成服务实例没有定义激活代次、释放 owner 与失效规则

- 位置：`docs/proposals/multi-instance-runtime-topology.md:111`、`:112`、`:235`；`docs/adr/0024-multi-instance-runtime-topology.md:39`。
- 现象：caller 只有“实例、插件、入口”，工厂签名只有 `(caller) => 实现`。同一运行实例中的同一入口停止再激活，caller 三元组完全不变；正文未说明工厂按什么身份缓存、是否 single-flight、实例归谁释放、调用方停止时如何撤回，也未区分原有共享服务与新增的按调用方门面。
- 为什么是问题：`runtime/plugin-api.md:99` 规定转发器“有效 → 已撤销”，撤销后“不再变回有效”；`runtime/plugins.md:33` 要求旧激活代次与旧句柄一律失效。现有 services 的 single-flight 归提供者作用域（`runtime/services.md:51`、`:83`），源码 `services/composition.ts:63` 的 `ProviderEntry.current` 只有一次共享尝试；插件产出只交付一次，重复交付被 `plugins/host.ts:1244` 的 `provided.adopted` 拒绝。这些可以演进，但不能仅增加 caller 参数：按插件共享数据的持久寿命与按入口代次借用/撤回的运行寿命需要两层，否则会复用旧门面或无限保留退出窗口的实例。
- 如何核实：对照服务 single-flight、产出接管、旧转发器失效合同，推演“同实例入口 A#1 取得服务 → A#1 停止 → A#2 再取得服务”；现有 caller 身份不能区分两次激活。未运行程序。
- 建议改法：K1 先固定 caller 的激活代次、可取消使用 scope 与工厂实例的 owner/release 合同。保留普通共享服务的既有语义；为按调用方服务明确缓存键与 single-flight，按插件拥有底层数据，按消费者代次签发门面。任一侧停止后旧门面永久失效，释放失败继续可诊断，不让下一代复用旧门面；增加调用方重激活、提供方恢复与退出窗口回收的验收。

### 5. [阻断] 服务端停止顺序没有先封闭项目打开与租约接纳，关闭期间仍可创建新子实例

- 位置：`docs/proposals/multi-instance-runtime-topology.md:76`、`:78`、`:89`；`docs/adr/0024-multi-instance-runtime-topology.md:21`。
- 现象：正文指定“先停全部项目子进程……再停服务端实例”，但握手仍由服务端路由申请项目租约，项目不存在便启动。若按现有宿主的前置停止钩子逐个关闭项目，服务端根作用域此时仍 available；关闭项目期间新握手或后台任务能重新打开刚关闭的项目、或创建没在待关闭集合里的项目。“最后租约释放 → 宽限期 → 停止”的流程也没有定义 stopping 项目遇到新租约时的结果。
- 为什么是问题：`runtime/lifecycle.md:51` 要求停止开始就拒绝新业务与新可用资源。现有 `packages/neuro-book/src/server/host.ts:120` 在 `beforeStop` 完成后才于 `:130` 触发内核停止；HTTP 的排空不能封闭本次新增、独立于 HTTP 的 RPC 端口。`runtime/application.md:112` 又规定停止未完成的同身份实例继续存活共享，不能按“没在运行”直接创建第二个拥有相同目录的新项目。只定释放顺序不足以约束上述接纳竞态。
- 如何核实：交叉读取握手/租约/停止文字、现有宿主的 `beforeStop → abort → application.stop` 顺序与实例表合同，走查“服务器开始关闭 P → 新连接申请 P/Q”以及“宽限期结束进入 stopping → 新租约到达”。这是已核实的状态机缺口，未运行竞态实验。
- 建议改法：区分停止接纳与释放资源。服务端开始停止时先原子封闭新握手、子实例创建与租约取得，保留在途收口所需的 RPC；随后排空消费者、停止子实例并等待真实退出，最后释放服务端提供者。固定项目 creating/available/idle-grace/stopping/terminated 的租约结果：宽限期内可取消关闭，已进入 stopping 不复活；退出且旧锁/owner 已收口后才能以新身份重开。强制退出按外部观察到的终止处理，不伪报内核正常 closed。

### 6. [阻断] 服务端的客户端公开状态镜像没有按目标客户端隔离，多个窗口的 `when` 无法正确求值

- 位置：`docs/proposals/plugin-data-model.md:124`、`:127`、`:128`；`docs/proposals/multi-instance-runtime-topology.md:90`、`:167`。
- 现象：每个客户端各有公开状态，但“服务端命令若要按客户端状态判断，由客户端把那部分公开状态同步给服务端”没有规定镜像的键空间、选用哪一个客户端，也没有连接/入口停止后的撤回语义。两个窗口同时推 `workbench.compact` 或活动编辑器状态，服务端只有一张命令表、一套本实例键表；同名键无法同时表示 W1 与 W2。
- 为什么是问题：正文要求窗口界面状态“各一份”，Agent 默认作用于发起会话的窗口。现行 `workbench/commands.md:66` 又要求执行与确认后复查“当前 when”；源码 `commands/shared/registry.ts:300`、`:322` 经同一无参数 `availability(entry)` 读取上下文。镜像覆盖或取最近窗口会让发往 W1 的动作被 W2 的焦点/紧凑状态允许或拒绝；断线后残留的 true 也会错误放行。仅保持同步求值并不能解决目标归属。
- 如何核实：对照一实例一张命令表、两个窗口各自状态与客户端同步规则，推演 W1.compact=false、W2.compact=true 后服务器按 W1 执行命令。现有设计不能确定该取哪份值；未运行程序。
- 建议改法：保持 `when` 本实例同步求值的已定取舍，镜像按精确客户端实例与入口代次保存，执行/枚举上下文显式选定目标；缺失、重连待基线、来源停止均按未就绪处理。客户端命令仍在目标客户端复查本地条件，服务端需要镜像的命令按调用上下文选择，禁止做进程级“当前窗口”。增加两窗口互相矛盾状态与断线后旧镜像撤回的验收。

### 7. [建议] K6 配置设计需补通用用户编辑的授权路径，否则普通插件写权限无法承接设置界面

- 位置：`docs/proposals/plugin-data-model.md:163`、`:174`、`:175`、`:192`、`:193`；`docs/adr/0024-multi-instance-runtime-topology.md:39`。
- 现象：正文规定普通插件写配置只限声明者，同时描述设置界面枚举所有插件声明并直接 `update(键, 值, 目标层)`。若该路径采用普通插件服务调用，其 caller 为设置入口，保存 `workbench.theme` 或第三方项时不满足声明者限制。配置插件可以另有受控用户编辑入口，但当前走查未区分这两种能力；K6 已明确另开设计轮，首版界面形式也未决定。
- 为什么是问题：读取、存放和展示已经统一，保存的授权主体却仍只定义为插件。把设置界面等同普通插件调用就无法完成通用设置；让任何入口声称“这是用户修改”则掏空已拍板的只写自己规则。VS Code 调研 `docs/research/vscode/05-configuration-system.md:205`、`:219` 与 `07-extension-system-deep-dive.md:255` 正好区分宿主的用户编辑流程和扩展更新设置的代理。这里需要的是调用合同补全，不是放宽普通插件权限。
- 如何核实：将设置走查的 `update` 输入与普通插件命名空间规则组合，确认同一普通接口不足以完成跨 owner 设置。没有源码证明将来设置界面一定采用该接口；列为 K6 设计前置建议，不阻断 K1–K5，也不把未定界面作为已交付承诺。
- 建议改法：保留普通插件只写自己的规则，另给用户编辑流程由宿主签发的明确能力，或通过键拥有者的受控 action 执行。规定该能力的来源、可写目标层、结构校验与审计，不能靠任意 RPC 参数取得；设置界面的保存图与 K6 设计问题同时更新，补第三方项可编辑而普通插件不能冒充用户的验收。

### 8. [阻断] 断线超过项目宽限期后，重连未区分恢复旧绑定与绑定新项目代次

- 位置：`docs/proposals/multi-instance-runtime-topology.md:78`、`:80`、`:86`、`:89`、`:113`、`:117`、`:134`。
- 现象：连接断开释放项目租约，宽限期后 P#1 退出；同一未卸载客户端 W 随后重连。握手按项目 id 申请租约会启动 P#2，订阅规则又只要求重连发 `resync`。这没有规定 W 是拒绝恢复并重启客户端实例，还是继续存活、更新其绑定。项目崩溃后“重新打开”也有同一缺口。
- 为什么是问题：“一生只绑定一个项目”没有明确该绑定是否包含项目运行代次，不能据此单独断言同项目 P#2 必须重启客户端。需要补的是失效合同：`runtime/services.md:54`、`:120` 要求旧绑定不可用、不自动改投新目标；`storage/persistence.md:81`、`:83` 要求 Project 句柄绑定精确代次，重启后重新初始化。若只更新 W 的绑定表并自动恢复订阅，旧 `remote(...).at("project")` 与旧 Storage 保存可被重新解释为 P#2；若不更新，重连何时失败、提示如何恢复也没有合同。刷新防串结果的论证不覆盖没有页面刷新的重连。
- 如何核实：沿“W→P#1 → 断线 → 最后租约释放 → 宽限期结束 → P#1 退出 → 同一 W 握手”走查；交叉核对旧请求、订阅 resync 与精确 Project 句柄的规则。未运行重连实验。
- 建议改法：明确连接代次与客户端/项目实例代次分离。重连先尝试恢复原精确项目绑定；若原代次已结束，明确执行客户端实例重启，或由宿主先撤销全部旧项目绑定、句柄和查询状态，再显式取得同项目新代次。选前者可复用已定的重启路径，状态机更小；两种都不能把旧写改投 P#2。旧请求和订阅先失效，同一 P#1 内重连才直接重建仍有效订阅并取基线。增加宽限期内恢复、超过宽限期与服务端重启后三种验收。

### 9. [建议] HTTP 资源地址需明确沿用读取时根能力与精确项目代次校验，签发检查不能替代它们

- 位置：`docs/proposals/multi-instance-runtime-topology.md:158`、`:218`。
- 现象：项目入口先校验资源，再由应用级入口签发绑定“项目实例、相对路径、过期时间”的令牌；HTTP 路由简写为“校验令牌，直接从磁盘读取”。这没有明确服务端根授予、项目结束后的撤销与读取时包含校验。短时有效和签名本身不能证明路径仍属于原项目，但现稿也未明确允许省略既有 platform.files 校验。
- 为什么是问题：字节读取从项目入口移到应用级入口，需要把既有根授予约束接到新 owner。若实现只做签名/过期检查，签发后将 a.png 替换为根外链接，或原项目退出后复用同路径，都可能命中新目标；这是条件风险，未证明现有或拟定实现会这样读取。`platform/files.md:43`、`:46`、`:86` 及 `workspace/resources.md:43` 已有读取约束，新应用静态服务 `http/server/static.ts:45`、`:69` 也在读取时检查真实路径包含性，可以直接沿用。
- 如何核实：核对资源地址步骤与根授予、包含校验、Project 代次合同，确认新跨进程 owner 的接线尚未明示。未发 HTTP 请求、未做攻击实验；列为资源地址定稿建议，不宣称已经存在越界读取漏洞。
- 建议改法：保持字节不经项目进程的已定方案，由宿主给服务器签发只读、精确项目代次的根授予，令牌只缩小该授予。每次 GET/HEAD/Range 重新核验授予寿命、项目代次和根包含性；项目停止/删除撤销新读取，已接纳流按 owner 收口。明确令牌是 bearer 能力还是还需会话校验，登录上线后绑定主体与授权变化。补过期、项目结束、同路径重建、根外链接与 Range 读取的验收。

### 10. [建议] `persist()` 定稿应保留确认基线、当前显示和未保存意图，不能把 Storage 状态压成一份值

- 位置：`docs/proposals/plugin-data-model.md:81`、`:85`、`:88`、`:90`、`:93`、`:116`、`:126`、`:196`。
- 现象：示例给出 `persist(record)`，action“改 customizations → 提交 Storage”，订阅进入 store 内存状态，多窗口表又要求“共用记录，不强行改对方显示”。完整返回 shape 尚未定义；若它只有一份直接回填的值，外来订阅、迟到初始读取与保存确认就可能覆盖拖动或新意图。`ready` 尚未区分各读取分类是否允许普通保存，但字段封装本身可以保留这些状态，示例不足以证明其必然丢失。
- 为什么是问题：`storage/persistence.md:113`、`:115`、`:116`、`:127`、`:131`、`:132` 已要求基线/显示/意图分离及损坏保护。t50 审查第 2 条已经指出原 LayoutStore 抹平这些语义；本条是换成统一 store 后仍需保留的同一接线要求，不作为另一条独立的已核实数据丢失阻断，也不要求本轮补完整 Storage API。
- 如何核实：对照 store 示例与“W1 拖动中、W2 保存”“初始响应晚于订阅”“save1 确认晚于新意图”“损坏记录显示默认”四项现行合同，确认示例未说明如何组合它们。错误效果依赖将来采用单值回填的实现，属于条件推断；未执行实验，列为 K5 定稿建议。
- 建议改法：在 store Spec 与 K5 前置设计中固定持久化绑定的最小模型：读取分类及可写性、已确认值/revision、当前显示、未确认意图与保存状态；可以由 owner 的窄 reducer/action 提供，不强制通用 JSON 合并。默认呈现不自动保存；订阅只更新基线，恢复时机由 owner 明确；按条串行提交并保留失败意图；公开状态投影当前显示与明确就绪/可写键。用上述四场景证明封装没有抹平 Storage 合同。

### 11. [阻断] 公开状态缺少静态键声明与激活 getter 的接线，懒激活命令的声明校验没有替代通路

- 位置：`docs/proposals/plugin-data-model.md:87`、`:106`、`:124`、`:128`；`docs/proposals/multi-instance-runtime-topology.md:239`。
- 现象：稿中公开键来源是 `defineStore(...).public`，store 实例随入口激活创建，公开状态登记时交出读取函数；没有规定如何在清单层取得键名、类型与 owner。若实现只在创建 store 时登记键，一个懒激活插件 A 的命令引用本插件 `ready`，或插件 B 的命令引用 A 的公开键时，命令描述校验发生在 A store 出现之前，会得到“未登记的 when 取值”。为让命令通过而提前激活 A，又破坏登记不执行和按需激活。纯 `defineStore` 声明可以作为静态提取源，但稿中尚未定义该通路。
- 为什么是问题：现行 `workbench/commands.md:62`、`:68`、`:143` 要求 `when` 引用未登记键在登记期拒绝；`runtime/plugin-manifest.md:52` 把上下文键放在顶层的纯声明贡献，`:63` 要求贡献校验不依赖拥有者激活。源码 `commands/shared/plugin.ts:28` 在贡献校验时调用 `commandDeclarationProblems`，`context-keys.ts:22` 立即检查键表；`plugins/host.ts:763` 在产出交付前即按该规则决定贡献是否合格。本次“上下文键不再单独一套机制”没有给出静态声明向 store.public 绑定的替代路径。
- 如何核实：对照公开键来源、store 寿命、现有命令/贡献校验时机，走查一个未激活入口的命令引用其公开键。已核实声明层与运行值层的接口缺口；未运行程序。
- 建议改法：仍让公开状态统一拥有值，但在不执行插件代码的描述层登记稳定的限定键名、标量类型、默认/未就绪语义与 owner；store 激活时只绑定该入口代次的 getter。getter 停止即撤回值，合法键未绑定按未就绪求值；插件声明被禁用撤回时按既有声明规则处理。明确重名冲突、跨插件引用与非法类型的校验，并补懒激活命令通过静态校验、值尚未就绪时不能执行的验收。

### 12. [阻断] 待交付回调在项目确认完成前由 `takePending` 删除，项目失败或回包丢失后没有可恢复的交付记录

- 位置：`docs/proposals/multi-instance-runtime-topology.md:215`、`:216`、`:217`、`:226`。
- 现象：项目没在运行时，服务端保留回调以便下次打开领取；领取接口却规定“读出并删除原子完成”。服务端已删除、RPC 回复尚未被项目收到时断线，或项目收到后写 Files/更新 jobs 失败，待交付记录已经消失。该“原子”只覆盖服务端取出与删除，不覆盖项目真正完成。
- 为什么是问题：本稿 `:135` 明确不重放未确认请求，写请求断线返回 `unknown-outcome`，因此不能靠 RPC 重试追回已经删除的数据。文生图例子需要证明离线项目下次打开能收到已完成的外部任务，但此序列只能保证“取走一次”，不能保证结果落入项目；服务端与项目子进程之间也没有跨实例事务。`runtime/lifecycle.md:31`、`:111` 明确收口不是回滚，不恢复已发生的删除。
- 如何核实：按“server 删除 pending → RPC 回复丢失”及“project 领取成功 → Files 写入失败/子进程退出”逐步检查，走查中没有仍存活的交付状态或确认路径。这是确定的设计失败窗口，未调用 Provider 或运行文生图。
- 建议改法：让领域 owner 以稳定外部任务 id/任务 id 记录待交付状态；领取不删除唯一恢复依据，项目落盘并确认完成后再退役原记录。领取与完成需要可识别的重复结果及结果未知后的查询/核对，按领域合同恢复，不把通用 RPC 改成自动重放，也不引入跨存储事务框架。例子补领取后崩溃、回包丢失与项目写盘失败的收口路径。

### 15. [建议] VS Code 的跨宿主依赖仍会等待激活，不能作为“远程调用不阻塞激活”的证据

### 16. [建议] RPC 需要分别定义 wire 协议兼容与目标服务合同兼容，不能只写“两端核对插件版本”

- 位置：`docs/proposals/multi-instance-runtime-topology.md:89`、`:110`、`:136`、`:186`、`:187`。
- 现象：握手只列各插件版本；请求中的“版本”未指明是发起插件版本、目标插件版本还是消费的合同版本。原同插件 channel 两端天然只有一个插件 id，新路径可以由 A 调 B，也可以跨两个客户端的不同生效集合；只比较 A 的版本不足以证明 B 的输入/输出及事件合同兼容。RPC 的帧/握手格式也需要独立于业务插件集合的版本判定。
- 为什么是问题：现有 `runtime/browser-host.md:43`、`:92` 已区分引导协议与插件版本，源码 `web/host/window.ts:99` 在建立实例前做兼容判定；Storage 还单独要求消费定义与注册定义匹配（`storage/persistence.md:138`）。这些层次可以沿用，不必增加复杂协商，但 K1/K2 要有一个确定的校验来源及失败阶段，否则旧外壳可能被错误地当成业务 schema 错误。
- 如何核实：检查拓扑全文的握手、请求字段与版本段落，并对照既有浏览器引导及记录定义合同；未验证任何版本不兼容运行场景。
- 建议改法：K1 固定 wire 协议版本，不兼容在解析业务帧/激活前拒绝；目标合同按其实际提供插件与消费方编译所依赖的定义核对，优先复用既有插件版本/兼容范围，不为每方法另建版本体系。所有路由跳只转发原期望，不因重连改用“当前版本”；补 A 调 B、目标热升级、旧外壳与不支持协议的场景。

## 整体评估

结论：**从现有源码与合同推断，架构方向可实现；当前设计尚不足以按实施表直接进入 K1。** 最终保留 16 条发现：9 条阻断（2、3、4、5、6、8、11、12、14），7 条建议（1、7、9、10、13、15、16）。这里的“阻断”指需要先补齐才能避免改动公开接口、失效语义或实施验收范围的合同问题，不表示运行失败已经复现。所有运行行为均未验证。

- 内核可复用的基础：实例身份退役、入口独立激活代次、作用域停止与释放、提供方服务 single-flight、贡献接管/撤回、停止期限都已有 owner。开放运行位置、增加子实例控制与 RPC 传输不要求推翻这些基础。跨进程应传输声明、请求和可撤回远程引用；不能把本地 ResourceHandle 序列化后当作同实例借用，`lifecycle/scope.ts:501` 已限定同实例签发。
- 必须先固定的新边界：即时 caller 与委托消费上下文、入口代次与按调用方门面寿命、实例与连接代次、项目停止时的租约接纳、公开键声明与运行值绑定。这些属于 K1/K5 对外接口和不变量，留到 Storage/外壳消费时再定会向前返工。
- 数据分层：Config、Storage、运行状态、查询缓存、领域数据与 URL 的 owner 已写清；`when` 同步读当前公开状态与配置/Storage 经服务访问可以组合。`persist()` 的状态 shape 和配置用户编辑能力仍需在各自定稿时承接现行合同；本轮没有把短示例当作完整实现，相关条件风险已降为建议。
- 安全方向：回环监听、WebSocket Origin 检查、业务端口分离、密钥不发往客户端及数据访问按 caller 隔离与已接受的信任模型相容。资源地址应沿用 platform.files 授予规则；客户端互调权限是稿中明列的待定项，需要在 K1/K2 合同定稿时明确，不能把“可路由”直接当作“允许调用”。本次没有安全实测，也不为当前范围追加登录或沙箱。
- 文档状态：ADR 0024 的 Accepted 记录已确认的长期决定，两份提案的 reviewing 表示接线细节仍待审；这两个状态本身不矛盾。当前 Spec 保留旧合同符合 t51 只做设计的范围；需要补的是后续修订清单及各切片 owner，不能把尚未修改 Spec 当成本次越界或遗漏实现。
- 整体质量：角色、所有权与推进方向清楚；精确寿命、失败恢复和端到端完成条件尚未形成同一套可执行合同。修复重点应是收敛这些接线，保持已批准的四类实例、项目子进程、内核对称路由、WebSocket、分端口、TypeBox、按调用方服务及 K1–K5 先于外壳的方向。
