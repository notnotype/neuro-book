## 1. 重要：合法的 160px 面板宽度把容器标签带压成 0px，并裁切“移动到”入口

- **类别**：界面。
- **位置**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchPanelSurface.vue:95`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:230`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:308`。
- **现象**：真实测试插件产品页在 `840×900`、默认底部居中面板、左右工具栏均显示时，面板被合法夹取到 `160px`。五个框架按钮共占 `138px`，导航槽只剩 `10px`，Tabs 的可见宽度是 `0px`（内容宽 `93px`）。上提的“移动到”宽 `26px`，其中心已落在“面板位置”上；真实鼠标中心点击打开位置选择的命令面板，没有打开移动菜单。Playwright 自动点击能找到按钮残留的边缘，不能据此认定入口未裁切。键盘可以打开移动菜单，但容器名称与标签的焦点提示没有可见空间。
- **原因**：外壳一的 `160px` 最小宽只考虑五个框架按钮；外壳二新增标签带和上提动作后仍沿用它。`__actions` 不收缩，`__nav` 允许收缩至零并 `overflow:hidden`，内部 Tabs 又允许缩至零。Spec 输出 25、PanelSurface 文档的“标签带自己横向滚动”无法在零宽盒内成立。
- **如何核实**：`chrome-transcript.jsonl` 的 `stale-focus-clipped-nav`、`panel-clipping-final`：实测 `panelWidth=160`、`nav.width=10`、`list.width=0`、`list.scrollWidth=93`、`nativeHit="面板位置"`；Playwright `mouse.click` 后 `centerClick.palette=true`、`menu=0`。截图 `product-840.png`、`panel-840-final.png`。本轮 `workbench-views.e2e.ts` 12 例全通过，但其窄屏用例只核对 `390px` 下框架按钮，未覆盖宽屏最小面板宽度。
- **建议改法**：在外壳的宽度下限与降级规则里计入面板标题行新增的导航和动作；为导航保留非零标签宽度与完整的 `26px` 移动按钮，装不下时提前采用既有紧凑呈现。不要只取消裁切，那会让导航覆盖框架按钮。补一条 `840px` 产品页的鼠标与键盘检查，断言标签盒宽度大于零、移动按钮的中心命中自身。

## 2. 重要：矮屏降级把视图内容压到 0px 后，隐藏输入仍进入 Tab 顺序

- **类别**：界面。
- **位置**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchViewInstances.vue:77`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchViewSection.vue:53`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchViewContainerHost.vue:117`。
- **现象**：真实产品页把乙并进甲的 Sidebar 容器后，调整到 `390×260`。甲、乙的网格叶各只有 `21px`，小于固定 `32px` 标题行；甲的内容盒与 ViewFrame 实测高度均为 `0px`，但 `context.visible=true`，未停放、没有 `inert`。从状态栏开始按真实 Tab，第 6 次进入甲的样例输入；该输入有焦点，却被 `0px` 的父内容盒完全裁切，截图无输入与焦点环。这会产生看不见的键盘停靠点，并向插件报告错误的有效可见状态。
- **原因**：实例层的有效可见只检查所在 Part、选中容器、收起偏好和“存在落点”；落点在几何降级中压到零仍算可见。ViewSection 也只按收起偏好隐藏正文，不消费网格实际分配的尺寸。外壳层对 0px Part 已有停放策略，新增的视图层没有覆盖同一边界。
- **如何核实**：`chrome-transcript.jsonl` 的 `product-390-short`、`zero-content-focus`。前者从状态栏真实按 Tab，记录 `sequence[5].sample="test.sample-views.alpha"`；后者读取甲输入 `focus=true`、`sampleVisible="true"`，祖先 `workbench-view-frame.h=0` 与 `workbench-view-section__body.h=0`。截图 `zero-content-focused.png`、`product-390-short.png`。没有替换尺寸 API，没有伪造焦点事件。Spec 外壳一验收 5 明确包括 `390×260`；输出 10、18 与 `workbench/views.md` 输出 9 要求有效可见与不可交互内容的行为一致。
- **建议改法**：让容器宿主从现有 `useGridLayout` 的实际分配发布内容是否有非零可用空间，实例层据此把内容停放或设为 `inert`，并让 `ViewContext.visible` 同步变为 false；视图标题与展开控件保留。正文重新可用时恢复同一实例、滚动与焦点规则。补真实矮屏 Tab 用例，不新增第二套测量。

## 3. 重要：`focusedPart` 没有界面事件入口，始终停在 `editor`

- **类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:173`；`packages/neuro-book/src/plugins/workbench/web/state/layout-store.ts:184`；`packages/neuro-book/src/plugins/workbench/web/state/public-state.ts:51`。
- **现象**：真实开发产品页中，依次聚焦 Panel 的“面板位置”按钮、状态栏的“隐藏面板”按钮，实际焦点分别在对应节点，但 `layout.state.focusedPart` 两次仍是 `editor`。全范围搜索 `focusPart|focusin|focusedPart`，`focusPart` 的调用仅在 store 测试；两个组件的 `focusin` 监听只更新 Teleport 的私有记忆，不更新 store。
- **为什么是问题**：Spec `ui/workbench-shell.md` 输出 27 与计划第 49 行规定最近获得焦点的 Part 必须上报，公开状态供插件读。该公开键目前对 Sidebar、Panel、AuxiliaryBar、ActivityBar、StatusBar 均不会反映用户焦点。现有测试直接调用 action，只证明 setter，不保护真实接线。
- **如何核实**：真实 Chrome `151.0.7922.71` 打开 `http://127.0.0.1:42166/`；实验 `focus-state-dev` 通过 Playwright `.focus()` 依次聚焦 `[data-panel-action="nbook.view.set-panel-position"]` 与 `[data-shell-focus-target="panel-toggle"]`，只读组件 props 中的真实 store。结果 `panel.focused="editor"`、`status.focused="editor"`，见 `chrome-transcript.jsonl`。驱动的完整启动命令与实验代码位置见“本次验证与边界”。没有伪造 focus 事件或替换运行时。
- **建议改法**：在 `WorkbenchShell` 根上接一条 `focusin`，从目标最近的 `[data-shell-slot]` 或 `[data-leaf]` 求 Part，调用现有 `focusPart`；菜单和对话框不在根内，自然保持原值。把现有 setter 测试的界面合同补在真实页面用例中。

## 4. 重要：Panel 与 AuxiliaryBar 的标签没有和内容建立无障碍关联

- **类别**：界面。
- **位置**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchToolPartHost.vue:53`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchToolPartHost.vue:65`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:230`。
- **现象**：真实测试插件产品页中，“样例戊”“样例丁”具有 `role=tab`、`aria-selected=true`，但 `id=""`、`aria-controls=null`；页面 `role=tabpanel` 数量为 `0`。两个选中容器的目标均无 `role`、`id`、`aria-labelledby`。从 DOM 的关联属性缺失可推断，辅助技术无法据这些属性把标签与对应内容联系起来；未运行真实读屏软件。
- **原因**：nb-ui `Tabs.md:31` 明确把标签与内容的程序化关联交给消费者；本次直接复用 Tabs 后没有补这条消费合同。计划 `plan.md:56` 要求 PanelSurface 与 ToolPartHost 定清关联，两个组件文档也没有记录具体关联。
- **如何核实**：真实 Chrome 产品页实验 `tab-association`（`chrome-transcript.jsonl`）读取上述 DOM 属性。没有用静态源码代替浏览器结果；没有做实际读屏软件的听觉检查。`7/7` 组件测试、`12/12` 外壳二 e2e 均通过，现有用例没有断言这条关联。
- **建议改法**：给选中容器的内容目标一个稳定 `id`、`role="tabpanel"` 与 `aria-labelledby`，标签补同源 `id`、`aria-controls`；Panel 与右栏共用同一规则并同步组件文档。可在现有 Tabs 项合同中加可选的关联字段，由工作台传入，不新包一层只转发的组件。
