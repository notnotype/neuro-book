### T4：focusedPart 没有接入真实 focusin；只调用 action 的测试掩盖公开状态一直为 editor

- **严重程度**：重要；**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:173`；`web/home-page.ts:36`；`web/state/layout-store.test.ts:470`；计划 `plan.md:129`。
- **现象**：外壳和页面根都没有 focusin 处理，`focusPart` 在产品代码中没有调用者。真实页面依次聚焦侧栏甲的输入和 Panel 戊的输入，DOM 最近 Part 分别为 `sidebar`、`panel`，公开键均返回 `{status:"ready",value:"editor"}`。
- **为什么是问题**：输出 27 与计划要求最近获得焦点的 Part 对外可读；当前声明为已实现却永远保留默认值。S2 测试直接调用 `store.actions.focusPart("sidebar")`，只证明赋值和公开绑定，S7 完全不读该公开键，因而接线缺失仍全绿。
- **如何核实**：全仓搜索 `focusPart|focusedPart|@focusin` 只有 action 定义与直接调用 action 的测试，无产品事件上报；隔离副本的测试插件只增加公开服务读取器（`review-observer.ts`），没有修改外壳、store 或 public-state 实现。`node browser-review.mjs` 使用真实浏览器 focus 操作，经真实 `PublicStateService.read("nbook.workbench/focusedPart")` 读取；`browser-observations.json` 保存两次DOM与公开状态的对照。
- **建议改法**：在唯一外壳根处理真实 focusin，按有效 Part 标记调用现有 action；无 Part 或外部 portal 保持原值。将现有直接 action 用例改成真实浏览器消费公开键：侧栏→面板→外部菜单/body，断言最后两步保持面板值，无需第二套焦点状态。

### T3：计划声称真实串行锁窗口已锁定，实际 8 例注册表测试抓不到删除 published 门禁

- **为什么是问题**：这是上一轮 L3 明确要求补的关键寿命门禁；Spec 实现合同却声明 `registry.test.ts` 用真实内核串行窗口锁定。没有该判据，未来简化门禁会把失效插件的迟到组件当作有效组件接纳。

### T1：e2e 的记录查询没有绑定本用例客户端，取消的“零写入”断言可以读取上一用例的记录

- **严重程度**：重要；**类别**：测试。
- **位置**：`packages/neuro-book/e2e/workbench-views.e2e.ts:67`、`:83`、`:97`、`:190`。
- **现象**：12 个用例共用一个后端和 `user.sqlite`，Playwright 每个用例使用独立浏览器上下文、生成不同的 `nbook.client-identity`。`customizations()` 和 `hideSidebarInRecord()` 只按 owner/key 查询 revision 最大的行，没有 `client` 条件。未写布局的当前用例读取的是前一个用例留下的行；取消后立即比较 revision，也没有等待当前用例保存通道结束。
- **为什么是问题**：断言与被操作窗口没有同一身份约束；“取消无写入”可以通过一条与本窗口无关的记录，直接改库隐藏 Sidebar 也建立在“恰好这个用例最近写过”的隐含前提上。后端目前串行运行且 revision 是数据库全局计数，成功写入之后多数读取恰好来自当前用例，不能替代明确隔离。
- **如何核实**：对照 `client-identity.ts:26` 与 `storage/backend/partition.ts:149`、`:150`。真实页面 `t66-focus-move` 经移动视图与选择乙写入记录，另开独立上下文 `t66-other-case` 只打开默认页面；SQLite 按 e2e 相同 owner/key 条件查询，返回 `client="t66-focus-move",revision=3`，加 `client="t66-other-case"` 则无行。第二窗口的三个失败开关均为 null、甲正常可见。因此开关按上下文隔离成立，SQL 判据的跨客户端读取已动态核实；尚未把故意取消后写入的产品变异送进该取消用例，不能声称已经证明这种变异必然存活。
- **建议改法**：记录读取与更新同时筛选当前页面的客户端身份和 resource，或每用例建立独立后端/状态根。取消路径等待选择层真实关闭、确认本客户端的记录与保存完成状态，不能用全库最新行作为窗口证据。

- **为什么是问题**：真实宿主retry只处理稳定失败，正常scope-closed返回not-failed，不能把同一关闭入口复活；Lab把停止与恢复做成对称按钮，若把Lab截图或这条交互当寿命证明，会掩盖源实际能力。它目前用于UI展示，不把这一点认作产品运行故障。
- **如何核实**：真实开发Lab `views-merged` 初次终端generation=1，点“入口停止”样例卸载，再点同一按钮回ready、generation=2。真实 `lifecycle-contract-probe.ts` 关闭贡献方激活作用域后返回 `delivery=entry-stopped/scope-closed,loadResult=stale,retry=not-failed`，入口仍closed；两轮shutdown均closed。全包搜 `ViewSource`/`ShellViewsScene` 没有局部source的契约测试。QuickPick替身则使用Promise结果、包含item/cancelled/unavailable，真实命令面板e2e以及既有选择模式组件测试消费了关层与焦点归还，没有发现同样的类型或同步结算矛盾。
- **建议改法**：让局部source只模拟明确列出的UI状态，恢复按钮标明是“模拟新交付”；失败retry遵守只对failed有效的最小规则。共用一组来源合同场景跑局部实现和真实Registry，或将Lab寿命声明限定为展示状态，真实寿命证据继续用内核/产品页测试。
