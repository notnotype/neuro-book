## 已核实的发现

### 1. 重要：浏览器装配没有核对表项与实际定义的插件 id，可激活不在引导集合中的插件

- **严重程度**：重要；**类别**：正确性 / 装配不变量。
- **位置**：`packages/neuro-book/src/web/host/window.ts:174`、`:277`；对照 `src/server/plugins.ts:63` 与 `src/project/plugins.ts:42`。
- **现象**：把浏览器定义表的 `"nbook.projects"` 项错配成 `id: "example.rogue"` 的合法定义，引导集合仍只有产品插件，真实窗口宿主却执行 `example.rogue` 的激活函数，并以 `ready` 结束；`nbook.projects` 的“打开项目”贡献被静默丢掉。缺少定义表项则能正确失败，只有 id 错配被放行。适配器工厂返回错 id 时同样没有核对。
- **为什么是问题**：按清单装配必须保证“选中的 id 就是登记的 id”，否则浏览器的有效插件集合与服务端的引导集合不一致。必需插件的集合检查只针对 `SelectedPlugin.id`，内核登记却看实际 `PluginDefinition.id`；非必需插件错配不会被 requiredPlugins 补抓。计划第 3 节明确要求产出 id 与清单不一致直接失败，server/project 已保留这项检查，browser 迁移后的两张表没有落实。旧浏览器工厂路径也缺这项核对；这是本次触及的装配边界遗留缺陷，不能称为按位置唯一性引入的回归。
- **如何核实**：仓库外 `window-boundary-probe.ts` 经公开 `createBrowserWindow` 启动，连接真实 `createRemoteNode` / `createRemoteRouter`，链路为公开进程内 JSON 传输；未直接调用私有装配函数。命令：`bun --tsconfig-override /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t59/tsconfig.probe.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t59/window-boundary-probe.ts`，退出 0；输出 `missing-definition → startup-failed`、`ACTIVATED_UNLISTED_PLUGIN`、`mismatched-definition-id → ready`。各窗口均正常 `closed`。Bun 另输出已存在的 `directory mismatch` 内部诊断，不影响业务结果。
- **建议改法**：在同一个 `selected.map` 装配步骤中得到定义后核对 `definition.id === plugin.id`，不符合就抛错，沿现有启动失败与会话清理路径收口；定义表与适配器返回值共用这一次检查。窗口合同测试补一个可选插件 id 错配，断言 `startup-failed` 且错误指名两个 id，错误定义的激活没有产生副作用。

### 2. 重要：适配器表仍接受任意插件 id，普通插件可以重新通过工厂取得宿主参数

- **严重程度**：重要；**类别**：不变量 / 类型边界。
- **位置**：`packages/neuro-book/src/server/plugins.ts:46`、`:60`；`src/project/plugins.ts:30`、`:39`；`src/web/plugins.ts:36`；`src/web/host/window.ts:64`、`:277`；`docs/adr/0026-plugin-definitions-as-constants.md:35`。
- **现象**：三端的适配器表都是 `Readonly<Record<string, …HostPluginFactory>>`，键完全开放。把 `"nbook.commands": (context) => …` 放入浏览器适配器表，类型检查通过，真实窗口启动时优先调用它，收到 `store` 等宿主上下文，再返回 `commandsPlugin`；定义表已有的 commands 常量被绕过。同样的类型允许服务端 commands 工厂、项目 Storage 工厂读取 config。
- **为什么是问题**：普通定义表本身能挡住函数值，但第二张任意键工厂表提供了同等有效的旁路，未守住“只有 nbook.http、nbook.diagnostics 保留工厂”的边界。ADR 的“普通插件能不能带参数由表的类型挡住”和计划的类型验收因此不成立；此处没有证明当前内置插件共享状态或运行错误，而是已批准长期装配约束仍可被合法代码绕过。
- **如何核实**：仓库外 `window-boundary-probe.ts` 构造 `typeof serverHostPlugins`、`typeof projectHostPlugins` 与 `typeof browserHostPlugins` 三份有普通插件工厂的表；`bun x tsc --noEmit -p /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t59/tsconfig.probe.json` 退出 0。前述真实窗口实验输出 `ordinary-plugin-in-adapter-table → ready`、`ordinaryFactoryCalls: 1`，工厂断言拿到了真实 DiagnosticsStore。该 typecheck 首次缺应用的 proper-lockfile 与 Vue 声明输入，加入现有 `src/types` 后通过；没有安装依赖或修改产品。
- **建议改法**：把适配器表收窄为明确的适配器 id：server 只允许 `nbook.diagnostics | nbook.http`，project/browser 只允许 `nbook.diagnostics`；装配只对这些 id 查询工厂，其余 id 必须查询定义表。可用显式属性或窄联合键类型配合按已知 id 分支，不需要品牌标记、源码扫描或第三种注册机制。测试插件继续在仓库外或 `testing/` 中带参数构造后交入定义表，无需开放产品适配器名单。

### 3. 建议：commands 的实现合同仍说工作台的命令服务键由宿主传入

- **严重程度**：建议；**类别**：文档。
- **位置**：`docs/specs/workbench/commands.md:210`；实际代码 `packages/neuro-book/src/plugins/workbench/web/plugin.ts:13`、`:32`、`:38`。
- **现象**：同一份修订后的 Spec 先写 `commandsPlugin` 与定义表，后面仍保留“工作台依赖命令服务的键由宿主装配时交进来”。实际工作台常量直接从 commands 的 `shared/contracts.ts` 导入 `commandServiceKey`，静态声明 dependency，宿主不再传键。
- **为什么是问题**：这句仍描述已经删除的工厂接线方式，和 ADR 0026 第 2、3 条相矛盾；插件作者按实现合同照做会重新依赖宿主参数。它是存量遗漏，位于本次明确修订的 commands 实现合同中。
- **如何核实**：逐行对照 `workbenchBrowserPlugin` 的 import、dependencies 与 activate；本轮已运行 commands 的真实内核合同测试与整个应用 typecheck，现行代码无普通工作台工厂，也没有宿主传键入口。
- **建议改法**：直接删掉这句旧接线描述；`shared/contracts.ts` 的公开键与静态 dependencies 已由同节及 ADR 0026 说明，不再添加重复的机制说明。

- **内核按位置唯一性**：登记校验仍拒绝同一入口内或同位置多入口重复提供，并允许跨位置提供同 id；本地装配仅声明本位置入口，受阻推导先找本地提供方，远程候选也筛选本位置。catalog 与诊断保留入口身份，调用方门面与委托签发记录不按整份定义的第一个同名入口识别。除完整内核测试外，仓库外真实应用实验同时验证本地 / 远程提供项、按调用方门面、委托、foreign-location、受阻路径和停止隔离。
