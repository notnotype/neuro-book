## 设计错误与遗漏

### 1. 阻断：双位置定义会被现有内核作为重复服务整体拒绝

- **严重程度**：阻断；**类别**：设计错误 / 正确性 / 合同与改动面遗漏。
- **当前状态**：计划层面已关闭。修订版 `plan.md:19–23,72,86` 已加入内核前置片与两个 Spec；本次重读 `registration.ts` 已为 `providedByLocation`。初稿 smoke 的失败是改动前证据，不能用于判断现实现。
- **位置**：`plan.md:30–31`（`commandsPlugin` 含 server/browser、`storageBackendPlugin` 含 server/project）；`plan.md:45–54`、`plan.md:63–65`（未列内核与对应合同变更）。
- **现象**：把现有 commands 两侧入口放入同一份定义，在 server 与 browser 都启动失败，原因 `plugin:browser:duplicate-service`；把 Storage 的 server/project 入口放入同一份定义，在两类宿主都启动失败，原因 `plugin:project:duplicate-service`。失败发生在登记阶段，尚未进入能力解析或激活。
- **为什么是问题**：当前内核以整份插件定义为范围检查 `provides` 的服务 id 唯一性。commands 两入口都必须提供 `nbook.commands/service`，Storage 两入口都必须提供 `nbook.storage/storage`；计划不能仅改应用插件与宿主便完成。S1 按原边界不能通过，验收中的 foreign-location 与缺能力受阻也会先被登记失败挡住。
- **依据**：`packages/nb-runtime/src/plugins/registration.ts:74–90` 的单个 `providedNames` 集合跨全部入口共享，位置过滤直到 `:120` 才发生；`src/plugins/host.ts:292–315` 任一拒绝导致整个插件不登记。`docs/specs/runtime/plugins.md:45` 明确要求“同一插件内不重复（包括不同入口之间）”；`runtime/plugin-manifest.md:29` 也写服务由该插件恰好一个入口提供。宿主后续装配已仅给本位置声明提供者（`host.ts:335–378`），因此修正唯一性校验的范围即可保留同一实例唯一提供者，不必另造两套服务 id。
- **运行核实**：scratchpad 的 `multi-location-smoke.ts` 只合并现有公开工厂返回的真实入口，经公开 `createApplication` 启动；四组双位置启动均得到以上登记失败，作为对照，现有按位置 commands 在 server/browser 两组都 `available`，全部应用正常 `closed`。命令：`bun --tsconfig-override /home/notnotype/CodeRepository/neuro-book/.worktree/w00017-runtime-foundation/packages/neuro-book/tsconfig.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t59-plan/multi-location-smoke.ts`（退出 0；Bun 另输出 directory mismatch 内部诊断，不影响六组结果）。首次运行的报告脚本预期少写了入口 id，断言失败；已按真实结构化结果更正后重跑，未修改产品。
- **建议改法**：在 S1 之前增加内核前置片，或把它显式纳入 S1：以 `(location, service id)` 校验插件提供项，同位置不同入口仍拒绝，不同位置允许复用；同步修订 `runtime.plugins`、`runtime.plugin-manifest` 的唯一性措辞与验收。新增真正多位置的同一 `PluginDefinition` 经两宿主启动、foreign-location 不激活、同位置重复仍被拒绝的用例，再迁移 commands 与 Storage；不要在宿主裁掉 foreign 入口来绕开已批准的一份定义目标。

### 2. 重要：S1 的装配范围漏了真正消费工厂表的窗口宿主和测试宿主

- **严重程度**：重要；**类别**：改动面遗漏 / 验收可执行性。
- **当前状态**：计划层面已关闭。修订版 `plan.md:43–54` 明确列出窗口/boot/开发/e2e/fixture/projectHarness 与自建测试宿主，产品迁移现归 S2；完整实现验收不属于本次计划审查。
- **位置**：`plan.md:25`、`plan.md:33–34`、`plan.md:63`（只列“各宿主”“三个宿主的定义表、相关测试”）。
- **现象**：三张表改成“定义或工厂”后，现有调用方仍全部按函数调用。浏览器实际装配与能力提供在 `src/web/host/window.ts`，并非只在 `src/web/plugins.ts`；`boot.ts` 及产品/开发/e2e 入口又把工厂表类型一路传到窗口宿主。Storage 的真实项目子进程测试使用的 `projectHarness` 另建服务端应用，当前只提供 `projectsKey`，没有新增的 `state-root` 能力。
- **为什么是问题**：若照表中列出的文件实现，窗口里的 `factory(...)`、开发 Lab/e2e 引导仍无法消费常量，新增导航能力也没有提供者；仅把测试中 `createStorageServerPlugin(...)` 换成常量，会让真实子进程验收的父实例 Storage 缺能力受阻。计划应明确这些必改接点与各自责任，不能把普通测试插件仍可带参数理解为测试宿主不必迁移。
- **依据**：`packages/neuro-book/src/web/host/window.ts:56–58,91–93,165–175,243–263` 存在工厂类型、选择与直接调用，并在这里给 `ApplicationManifest.capabilities`；`web/boot.ts:22–43`、`web/main.ts:5–12`、`web/development-plugins.ts:5–13`、`web/testing/e2e-main.ts:8–15` 传递/合并工厂表。`server/testing/fixture-entry.ts:31–34` 直接调用服务端工厂表。`server/testing/projects.ts:108–136` 在内部选择状态根、创建父应用且只提供 `projectsKey`；`plugins/storage/project-child.test.ts:47–52,98` 目前在外部给另一条 user 库路径。`plugins/storage/storage.test.ts:103–166` 自建 server/project/browser 应用；`plugins/projects/projects.test.ts:158–164` 自建浏览器应用。现有 `web/host/window.test.ts`、`web/mount.dom.test.ts` 也消费该表。
- **建议改法**：给 S1 增加明确装配清单：`server/start.ts` 提供状态根，`web/host/window.ts` 提供窗口导航并解析常量/例外工厂；更新 `web/boot.ts`、`main.ts`、`development-plugins.ts`、`testing/e2e-main.ts` 与服务端 fixture。测试辅助宿主 `server/testing/projects.ts` 从自己选出的状态根提供能力，删掉测试外部拼 user 库路径的额外入口；三个自建应用的测试补对应 capability。`web/mount.ts` 的导航属于宿主路由，行为可保持，若统一导航对象则和 `boot.ts` 一起复用它，不必强迫宿主内部再经内核解析自己的能力。

### 3. 建议：例外应按宿主启动与停止的接点说明，现有“进程级资源”判据不精确

- **严重程度**：建议；**类别**：设计判据 / 文档。
- **当前状态**：已关闭。修订版 `plan.md:61–65` 与新 ADR 0026 第 5 条按启动/停机依赖解释两项例外，不再用“进程级资源”放行。
- **位置**：`plan.md:8,32,43,88`。
- **现象**：计划说“需要在插件激活之前就建立、或由宿主直接持有生命周期的进程级资源才留在工厂”。但 HTTP 监听在插件激活时才建立、归插件激活作用域释放；浏览器 diagnostics 根本不是进程级资源。反之，HTTP 的 host/port/staticRoot、diagnostics 的 exporter directory 都是每实例不变的配置，也同时符合前半句“数据走能力”。
- **为什么是问题**：当前两个例外的名单已获同意，执行上没有障碍；长期判据却无法解释它们的全部参数，容易让以后任何持有文件/数据库的普通插件也自称“基础设施”保留工厂，或迫使人把已同意的例外再次拆分。
- **依据**：`packages/neuro-book/src/plugins/http/backend/plugin.ts:55–85` 在 activate 中 `Bun.serve` 并以 `context.scope.register` 释放监听；`server/start.ts:116–117,206–227` 提前建立并持有 admission、在内核停止之前排空；`plugins/diagnostics/backend/plugin.ts:5,17–29` 与 `plugins/diagnostics/web/plugin.ts:14–25` 接收运行实例建立前创建的 store，浏览器还接收宿主 console。`nb-runtime/src/application/contracts.ts:49–56` 本地能力本来就能表达有生命周期的资源，资源是否进程级本身不足以决定要不要工厂。
- **建议改法**：保持两个明确例外，不增加新的通用“基础设施插件”类别。ADR 写实因果：diagnostics 的宿主 store/紧急出口必须覆盖内核启动前的诊断；HTTP 的 admission 与监听结果参与宿主就绪和停机前排空，故整体作为宿主适配器装配，其配置随适配器工厂传入。普通插件的依赖和配置仍从声明的能力取得；新增例外需要说明同样的启动/停机循环依赖，不能仅凭使用文件、端口或“按实例不变”放行。

## 写法与验收

### 5. 重要：按 `export function create…Plugin(` 扫描不能守住“定义是常量”的边界

- **严重程度**：重要；**类别**：测试设计 / 漏报与误报。
- **当前状态**：已关闭。修订版 `plan.md:45–49` 删除源码形状门禁，普通定义与宿主适配器分表，普通项类型为 `PluginDefinition`；无需继续完善正则。
- **位置**：`plan.md:36–38`、`plan.md:76`。
- **现象**：拟议规则只识别直接导出的、特定名称的带参函数声明。`export const createXPlugin = (options) => …`、局部函数后 `export {createXPlugin}`、别名重导出都绕过；现有的无参工厂也照样通过。按字符判断括号内“有参数”还会把注释当参数，若扫描原始文本也会命中注释里的示例。
- **为什么是问题**：已批准目标是普通插件导出定义常量，规则却仅阻止一种写法的带参工厂，重写为箭头函数便失守。只给这种形状配一条反例只能证明它会匹配自己，不能证明禁止项被覆盖；额外放宽命名/空白正则无法解决导出绑定的语义问题。
- **依据**：当前源码确有四个无参普通工厂（lab、projects backend、storage browser、workbench），它们均不受拟议判据约束。scratchpad `export-shape-probe.ts` 对第 3 节的形状判据作最小演示：带参直接函数被拦，带参箭头、局部再导出、重导出及无参函数均放行。此实验针对计划描述的判据，不声称尚未编写的精确正则已存在。
- **运行核实**：`bun /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t59-plan/export-shape-probe.ts`，退出 0，逐例打印预期策略与形状判定差异。另运行 `bun test src/architecture.test.ts src/plugins/commands/shared/plugin.test.ts`（cwd 为本 worktree 的 `packages/neuro-book`），当前基线 8 pass / 0 fail；它没有覆盖新增规则。
- **建议改法**：优先删除这条脆弱的源码形状检查，以三张宿主表中普通项必须为 `PluginDefinition` 的类型约束和独立的两个例外字段守住消费边界；迁移时删掉全部普通工厂。确需源码门禁时，用已有 TypeScript 编译器解析实际 `backend/web/shared/plugin.ts` 的导出绑定，约束普通入口导出为 `PluginDefinition` 常量，并明确定义允许的初始化形式；至少覆盖箭头、局部导出、重导出、无参函数、注释和两个例外。不要以遍历所有插件源码时禁止名字含 Plugin 的函数代替入口合同检查。

### 6. 建议：验收映射要补到新增能力的真实消费路径，不能仅沿用 helper 测试

- **当前状态**：真实能力消费、双实例隔离与变异区分已由修订版 `plan.md:95–103` 吸收；`projects.test.ts` 现有真实命令窗口用例也已出现。剩余仅为验收表缺 Spec 场景编号的建议，见下节，不再按初稿整个缺口计数。
