# 主 Agent 审查意见（第 3 轮）

Manager 公开入口、依赖声明与 `bun.lock` 的变化都接受。禁止清单自查也接受。剩下的问题集中在 smoke 本身的可诊断性与稳定性，阶段 1 要以它为验收标准，同一份代码两次运行的结果必须可解释。

## 必须修改

1. **产品进程的输出必须进入检查项日志。** L10 本轮“Product 在 ready 前退出：1”，但 `L10.log` 只有 6 行，产品自己的 stdout 与 stderr 没有记录，无法判断原因。所有经 Manager 或直接启动的产品进程、dev 进程，把它们的输出（至少最后若干 KB，或全部写入单独的文件并在日志中给出路径）记入该检查项的证据；进程在就绪前退出时，失败证据里要包含这段输出。

2. **查清 L10 本轮失败的根因。** 补上输出后重跑 L10（以及与它相邻、可能影响它的 L9），说明是产品自身启动失败、前一个检查项的残留（进程、端口、租约、临时目录），还是 smoke 的问题。如果是残留，修 smoke 的收口，确保每个检查项开始前上一个检查项启动的进程已经结束；如果是产品问题，写清现象与日志依据，不修产品。

3. **证明稳定性。** 修完后用 `--skip-build` 连续跑两次完整 smoke，把两次的结果并列给出。生产侧检查（L1、L3、L4、L5、L6、L9、L10）两次结果应一致；开发模式的 L7、L8 若两次不同，结合日志说明是否是产品已知的启动竞态（#244：dev 启动或重载期间 worker 重启，新实例拿不到旧实例持有的租约），这种情况在报告该项的证据里注明，不需要让它稳定。
