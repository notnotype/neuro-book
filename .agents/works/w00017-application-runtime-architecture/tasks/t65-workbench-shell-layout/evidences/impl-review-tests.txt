## 发现 06：最大化时没有停放编辑器，Tab 会进入不可见内容，而 e2e 要求它“可见”

- 严重程度：重要；类别：正确性。
- 位置：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShellLayout.vue:169`、`:239`；`packages/neuro-book/e2e/workbench-shell.e2e.ts:309`；Spec 外壳一输出 7、10、验收 6。
- 现象：`syncTargets()` 仅按 `[data-leaf]` 是否存在选择 Teleport 落点。最大化投影仍保留尺寸为 0 的 editor 叶，于是编辑器没有进入 `hidden inert aria-hidden` 停放区。真实 Lab 的 left 场景最大化后编辑器宽 0、样例自身宽 24（padding），`parked=false`、`inert=false`；从面板标题按一次 Tab 就聚焦编辑器输入，下一次聚焦编辑器滚动区。键盘可达已实测；从 DOM 属性推断也没有主动排除读屏访问，未运行读屏软件。新 e2e 对每一步（含最大化）无条件要求 sample 可见，只检验输入和滚动，不检查停放与 Tab 排除。
- 为什么是问题：最大化应该挤走并停放编辑器；0px 裁切不等于不可交互，也不能触发基于 parkingEl 的焦点交接。当前测试恰好接受了错误形态；正确把编辑器放进 hidden 停放区会先让这条 `toBeVisible()` 失败。
- 如何核实：未修改 `WorkbenchShellLayout` 的真实开发会话：打开 `/lab?c=WorkbenchShellLayout&s=left`，点击“最大化”，等 editor 叶宽为 0，读取样例祖先的 parking/inert 状态；聚焦面板标题后实际按 Tab 5 次，前两次分别在编辑器 INPUT 和滚动 DIV。基线 shell e2e 8 例全通过。场景内布局动作与 Tab 都走浏览器真实输入，没有直接调用内部函数。
- 变异补证：实验副本删除 `restoreMemory` 的焦点恢复 4 行，以及 `becameMaximized` 到 `panel-title` 的交接行；组件测试仍为 3 pass；重建真实生产前端后再次运行完整 `workbench-shell.e2e.ts`，仍为 8 pass（19.8s）。说明全部现有 shell e2e 没有保护可见内容搬动后的焦点恢复或最大化交接，外部浮层不抢焦点也没有独立断言。
- 可重复 smoke：全部源码变异恢复后，运行 `bun x --no-install playwright test -c e2e/review.config.ts review-parking.e2e.ts`，1 failed（9.13s）；输出 `{"state":{"parked":false,"inert":false,"id":"1"},"inEditor":true}`，停放断言 `Expected: true / Received: false`。该新增脚本只在实验副本中，走真实开发服务、浏览器点击与 Tab，未加入原仓库。
- 建议改法：在拥有呈现事实的 `syncTargets()` 中把最大化时的 editor 排除出可见目标（仍保留零几何叶），沿用现有唯一停放区；不用另造隐藏分支。改 Lab e2e：最大化时断言样例在停放区、不在 Tab 顺序，恢复后再断言可见、实例/输入/滚动不变；补输入聚焦后最大化的标题落点和外部浮层不抢焦点。

## 发现 07：文件头列“别处已覆盖”的恢复验收并未闭合

- 严重程度：重要；类别：测试。
- 位置：`packages/neuro-book/e2e/workbench-shell.e2e.ts:5`；`packages/neuro-book/src/plugins/workbench/web/state/layout-store.test.ts:203`；`plan.md:105`、`:106`；Spec 外壳一验收 7、10。
- 现象：坏记录用例只破坏 `views-customizations` 的 JSON，不放入不支持版本或有效但越界的尺寸记录；纯几何用例传越界参数，但不读取记录、比较原件或 revision。恢复用例断线时让 side/customizations 两条同时暂停，随后重试 customizations、放弃 side；真实运行观察两条均为 `unknown/unknown-outcome`，该用例没有断言保存失败分类，也没有一条正常写、一条确定失败后只重试失败记录的路径。新 shell e2e 没有任何真实布局保存失败，S5 只手传 problems 并断言 emits，产品状态栏到 retry/discard 的完整接线没有运行证据。
- 为什么是问题：通用 store 的 protected/unknown/retry 测试不能保护布局特有的 problems 汇总、记录选择与状态栏接线。文件头笼统说恢复已由布局 store 覆盖，会掩盖这些缺口；计划 S7 明确承诺“一条真实失败路径”。
- 如何核实：实验副本只删除布局 `problems` 对 `unsupported-version` 的分支，保留底座的记录保护；聚焦布局/命令测试仍为 13 pass、0 fail、148 expect() calls（变异存活）。运行 `bun src/plugins/workbench/web/testing/review-recovery.ts` 实测断线后的 side/customizations 都是 `{state:"unknown",code:"unknown-outcome"}`，两个应用都正常 closed。移除 unknown 汇总的另一变异被现有断线用例抓到（12 pass、1 fail），因此未知结果处理有覆盖，缺口是确定失败/一条正常另一条失败/产品恢复入口。代码核对：全部 shell e2e 没有断线、改库、未保存提示、重试或放弃；组件用例自行提供 problems 后只接收事件。共享 store 的版本保护不能记成布局 owner 的诊断验收。
- 建议改法：扩展已有坏记录用例为坏 JSON/不支持版本/越界尺寸三组，检查默认或夹取、布局问题、原件及 revision；在现有真实场地让 project 尺寸库失败而 user 定制仍正常，断言重试只补失败记录。S7 增加一条真实保存失败后点击状态栏重试/放弃的用户路径，覆盖拥有者接线，不重复实现通用 store 的重试算法。

- 建议改法：扩展现有拖动和紧凑用例：通过真实输入启动手势，期间调整容器再释放，并比较变更前后三条记录的 revision；一次有效手势断言涉及记录各增 1、其余不变；取消、测量变化和未就绪操作断言不变。补 Home/End、零边界指针恢复，以及 `390×260` 下实际完成显示/还原并核对按钮可见矩形，复用现有测试而不是增加伪手势场地。

## 发现 02：样例的实例身份与累计计数每次重挂都会重置

- 严重程度：重要；类别：测试。
- 位置：`packages/neuro-book/src/plugins/lab/web/fixtures/shell-scene/ShellSampleEditor.vue:10`；`packages/neuro-book/e2e/workbench-shell.e2e.ts:292`。
- 现象：`counters` 位于 `<script setup>`，实际在每个实例的 `setup()` 内建立；每次实例都是 `instance=1`、`created=1`、`unmounted=0`。卸载回调只改变这个旧实例的普通对象，新实例又创建自己的对象。e2e 的 `identity()` 只读取实例编号和卸载数，没有读 `data-created`，也没有断言“创建 1 次、卸载 0 次”。
- 为什么是问题：计划把生命周期计数作为“内容未卸载”的独立判据；这两个属性即使卸载再挂也不变。当前输入和滚动断言仍能抓到丢状态的重挂，不能把它们的通过说成身份/次数已经核实：允许状态恢复的重建会通过这套身份断言。注释“计数放在模块里，跨实例累计”与实际 Vue 编译结果相反。
- 如何核实：源码静态核对和 Vue 真实 SFC 编译；编译探针 `node lifecycle-counter.mjs` 输出的 `setup(__props)` 内含 `const counters = {next: 1, created: 0, unmounted: 0}`。未变异基线：8 个 shell e2e 全通过。真实 Chrome 在 Lab 从默认场景切到左侧场景后，旧样例 DOM 的 `isConnected=false`，新旧样例却同为 `{id:"1",created:"1",unmounted:"0"}`，证明卸载重建未被这些计数揭示。
- 变异补证：让 editor 的 Teleport key 随 `effectivePanel` 变化，真实 Lab e2e 为 1 failed；身份数组断言仍通过，先失败的是输入从“草稿”变为空（`workbench-shell.e2e.ts:313`）。说明生命周期变异被状态断言拦住，编号与卸载计数本身确实没有判别力。
- 建议改法：把计数放到一个场景拥有、跨子实例存活的对象，由 fixture 传给样例，样例每次 setup 分配新的 id，生命周期钩子更新同一个可观察计数；同一场景转换后分别断言 id 不变、created=1、unmounted=0。不要用产品代码的状态恢复充当实例保留证据。

## 发现 04：命令测试绕过命令系统，错误的 when 声明可以通过全部四例

- 严重程度：重要；类别：测试。
- 位置：`packages/neuro-book/src/plugins/workbench/web/commands/panel-commands.test.ts:72`、`:114`；`plan.md:87`、`:109`；Spec 外壳一验收 11。
- 现象：测试直接执行 `panelCommands(...)[id].run()`，只有声明格式和“when 引用的是已声明键”的检查；没有登记真实命令系统，没有实际非法参数/额外字段返回 `invalid-args` 的断言，没有逐条验证五个命令在未就绪、左右位置、justify、紧凑、隐藏时的可用与原因。
- 为什么是问题：状态绑定值正确不等于命令的 `when` 读对键；handler 直接调用也完全跳过参数校验和 when 求值。通用 commands 测试证明通用执行管线，不证明这五条产品声明与发布接线正确。计划明确要求 S3 使用真实命令系统，这一承诺没有落地。
- 如何核实：实验副本把 `set-panel-alignment` 的 `when: requires("panelHorizontal", "nonCompact")` 改成 `when: requires()`，保持合法声明；运行 `bun test src/plugins/workbench/web/commands/panel-commands.test.ts` 仍为 4 pass、0 fail、42 expect() calls。该变异取消了左右/紧凑禁用条件，当前合同测试存活；不宣称整个 e2e 也会存活（紧凑 e2e 会检查对应按钮禁用）。
- 建议改法：在已有真实 Storage 场地装入真实 `nbook.commands` 与 `nbook.state`，经 `isEnabled/execute` 表格驱动检查五条命令与参数边界，复用产品声明和实现。删除只调用声明校验再复述其内部字段的用例，选择服务仍可由合同已验证的内存选择器作答。

## 发现 05：最大化清除只测了位置与隐藏，改对齐漏清除的变异存活

- 严重程度：重要；类别：测试。
- 位置：`packages/neuro-book/src/plugins/workbench/web/state/layout-store.test.ts:132`；`packages/neuro-book/src/plugins/workbench/web/commands/panel-commands.test.ts:82`；Spec 外壳一输出 7、验收 4；`plan.md:104`。
- 现象：store 用例名称提“隐藏时清除”但该用例实际没有在最大化后隐藏；公开状态测试补到了隐藏。两者均未在最大化后改变对齐或收起并核对最大化清除；e2e 只验证换位置。
- 为什么是问题：对齐与位置共用 action，不代表四种转换都受测试保护；该变异违反 action 的瞬时状态清除合同而不失败。产品的呈现事实回写可能另行清除最大化，本实验没有跑该变异的完整产品页，不把“最大化会在产品中复活”列为已复现缺陷。
- 如何核实：实验副本将 `setPanel` 的无条件清除改为 `if (patch.alignment === undefined) maximized.value = false;`。运行 `bun test src/plugins/workbench/web/state/layout-store.test.ts src/plugins/workbench/web/commands/panel-commands.test.ts`：13 pass、0 fail、146 expect() calls。另一个“只在 position 清除”的粗变异被公开状态隐藏用例抓到（12 pass、1 fail），因此缺口精确落在未测的转换，而非所有清除均未覆盖。
- 建议改法：扩展现有最大化用例，分别在位置、对齐、隐藏、收起变化与进入紧凑后断言最大化为 false，并证明回到允许最大化的组合也不复活；同值动作保持不写入，不另造最大化状态机。

## 发现 03：主题测试只测三块底色，却宣称文字、字体与边框验收已覆盖

- 严重程度：重要；类别：测试。
- 位置：`packages/neuro-book/e2e/workbench-shell.e2e.ts:249`；`packages/neuro-book/e2e/settings.e2e.ts:93`；Spec 外壳一验收 1、12，计划验收映射 `plan.md:114`。

- 为什么是问题：截图记录布局外观，不能证明主题 token 的解析值。面板或状态栏字色硬编码、边框使用错 token、边界重复绘制，以及 editorial/aurora 覆盖错误均能漏过当前验收。Spec 与计划审查已明确不准把截图当 token 证明。

- 建议改法：修正现有 token 用例，分别断言三块区域的背景、字色与实际绘制的 border/outline token，并检查相邻边界只有一个 owner；复用同一个测量函数在约定的 Lab 主题/配色和产品默认明暗组合运行。标题和证据只声明实际检查过的属性。
