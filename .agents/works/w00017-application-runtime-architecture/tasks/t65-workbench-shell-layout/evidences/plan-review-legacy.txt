# t65 计划对抗审查：旧外壳迁移完整性

审查对象：`.agents/works/w00017-application-runtime-architecture/tasks/t65-workbench-shell-layout/plan.md`。代码依据均来自审查 worktree `/home/notnotype/CodeRepository/neuro-book/.worktree/w00017-t65-plan-legacy`，固定 revision `1c146c67`。本报告审查计划与合同；设计稿 accepted、外壳参照旧应用这两个决定作为前提。

核实方式：逐项阅读计划、设计稿、Spec 与源码。下列缺口是已核实的文档/接口事实；对将来实现的后果明确写为推断。审查期间不启动开发服务或 e2e，不修改仓库。

## 发现（按影响排序，编号保留核实顺序）

### L1 — 重要｜不变量：替换旧保存会话时丢了用户可达的失败恢复通道

- **计划位置**：关键设计第 3 节“工作台 store 与布局记录”、第 5 节“外壳组件”、验收映射“两个窗口共用记录”与“坏记录回落默认”。计划行 34–36、52–58、98–100。
- **现象**：计划列出的 action 只有布局修改，没有重试、放弃、重新打开记录；组件只安排项目名、面板按钮与空状态，没有“未保存”反馈。验收也只覆盖正常保存、坏记录和多窗口正常窄改。计划把 `layout-session.ts` 的职责交给 store，但没有接出失败后的用户操作。
- **为什么是问题**：store 的 `failed` / `unknown` 会暂停该字段队列；普通新布局 action 只往队尾追加，不能恢复队首。打开失败或订阅确定结束不会自动恢复，需要拥有者 `reopen()`；读取错误在后续正常快照到达时可以恢复，不能把它与 `ready` 等同。**推断**：一次保存失败后用户仍可拖动并看到变化，却无法知道未落盘，也无法让后续布局修改继续保存。accepted 设计要求读取失败后可临时调整并明确显示“未保存”，保存再失败时保留意图并提供重试与放弃。这属于外壳一的布局恢复，不应推给容器/拖放切片。
- **依据**：`docs/proposals/workbench-shell-abstractions.md:229–232`；`docs/specs/state/store.md` 输出 11、13–16 与“失败与恢复”（行 102–107、137–143）；旧 `packages/neuro-book-legacy/app/utils/workbench/layout-session.ts:195–196,136–145,1518–1543` 已拥有重试/放弃。新 `packages/neuro-book/src/shared/store/persisted.ts:311–320,388–400` 在失败时暂停并等待拥有者处理，不会由下一次 `commit` 自动重启。旧 Shell Spec 验收 10（`docs/specs/ui/workbench-shell.md:275`）仍要求保存失败可重试或明确放弃。
- **实验**：真实内核、真实 Storage/SQLite 的现有 store 场地覆盖双窗口窄改、冲突后暂停与重试、放弃、读取恢复、两种 `unknown-outcome` 恢复、提供方停止，共 7 个用例通过。实际命令与结果见报告末尾；未声称尚未实现的外壳已复现故障。
- **建议改法**：继续使用现有 store，不搬旧会话。工作台 store 为三条字段接出按记录的 `retry` / `discard`，需要时先 `reopen`；在一个外壳反馈区集中显示失败码对应的可读原因与“未保存”。不增加另一个保存队列。验收增加真实 Storage 的确定失败、`unknown-outcome`、读取失败恢复，以及一条记录成功/另一条失败时只重试失败记录。

### L3 — 重要｜正确性：严格必填参数的四条面板命令无法按计划从当前命令面板执行

- **计划位置**：关键设计第 4 节“公开状态与面板命令”、验收映射“五条面板命令”；计划行 41–47、101。
- **现象**：位置、对齐、隐藏、收起命令都要求参数严格且必填，S6 却指定“e2e 经命令面板”。当前命令面板对普通候选只执行 `{}`，没有按 schema 收集参数的机制；只有行号模式特殊构造参数。计划没有给这四条命令安排选择模式，也没有修改该触发面。
- **为什么是问题**：现有调用载荷是 `{}`，真实命令运行时对缺必填字段返回 `invalid-args`。**推断**：按计划把这四条严格命令登记后，用户即使在 `when` 为真时选中，也不会改变布局；只有 `{}` 的最大化命令能照现有入口工作。问题是计划的参数合同与指定验收入口不相容，不是已实现的外壳故障。
- **依据**：`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchCommandPalette.vue:137–149` 固定给普通候选 `{}`；`docs/specs/workbench/commands.md:53,73,156–164` 要求缺字段拒绝；现有带选择的设置命令在同一 Spec 行 139 明确允许省略参数，项目打开命令行 135 用 `{}` 后进入选择，而四条面板命令没有该合同。
- **实验**：现有命令经真实内核在 server/browser 两位置装配，用例同时断言带必填参数成功与 `{}` 为 `invalid-args`，2 个用例通过。四条面板命令与新外壳尚未实现，本次没有从浏览器命令面板运行它们。
- **建议改法**：最小方案是在本 Task 保留五条严格命令，S6 让真实面板/状态栏控件带参数经命令服务执行，命令面板只验最大化与可用性；对必填参数命令是否应出现在直接执行候选中另明确交互。若产品要求从命令面板操作位置/对齐等，就在 S3 明确使用现有 `QuickPick` 的选择流程及取消语义，并同步 `commands.md` 的参数合同；不要加通用 schema 表单或新命令总线。

### L4 — 重要｜正确性：进入紧凑呈现只投影为非最大化，没有安排清除宿主的最大化意图

- **计划位置**：关键设计第 3 节“工作台 store 与布局记录”、第 5 节“外壳组件”、验收映射“紧凑呈现”与“四种消失”；计划行 34、51–52、95、97。
- **现象**：计划明确列出清除瞬时最大化的触发器只有位置、对齐、隐藏、收起变化；布局事件只描述为发布事实，未规定 store 接到紧凑/降级事实时清除 `maximized`。验收只说回宽屏恢复偏好，没有“宽屏最大化 → 紧凑 → 宽屏不再最大化”。
- **为什么是问题**：旧 `projectShell` 只把此次输出的 `effectivePanel.maximized` 置为 false，不改输入。旧产品 `WorkbenchShell` 另有 `onLayout` 把这条事实写回宿主的瞬时 ref；迁移几何与纯布局组件而省掉这段接线不会得到相同状态转换。**推断**：若只由 `compact` 遮住最大化，回宽屏会从仍为 true 的内存偏好重新最大化，而合同要求进入紧凑时即清除；布局命令读到的状态也可能与画面不一致。这是外壳一职责。
- **依据**：`docs/specs/ui/workbench-shell.md:87` 明确“进入紧凑呈现即清除”；`packages/neuro-book-legacy/app/utils/workbench/layout.ts:740–766,781–787` 是纯投影；`packages/neuro-book-legacy/app/components/workbench/WorkbenchShell.vue:151–164` 明确回传 `update:maximized(false)`；旧 Lab 同样在 `packages/neuro-book-legacy/app/component-lab/fixtures/WorkbenchShellLayoutFixture.vue:1000–1011` 清自己的内存 ref。
- **建议改法**：在现有布局事实接入口一次更新 `compact` 与生效状态，并在 `maximized && !effectivePanel.maximized` 时清内存 ref，不写任何布局记录；Lab 用同一规则。S2/S6 增加宽屏最大化后进入紧凑、再返回宽屏的往返断言，核对两条尺寸意图及记录 revision 不变。

### L2 — 重要｜测试：把“不卸载”当成完整生命周期验收，漏了焦点、滚动与键盘恢复

- **计划位置**：关键设计第 5 节“外壳组件”、第 6 节“Lab 场景”、验收映射“编辑器内容不卸载”；计划行 51、58、64、102。
- **现象**：计划只明确挂载计数与输入保留，未规定换位置/紧凑切换时恢复焦点与滚动，也未要求状态栏按钮提供焦点标记；没有键盘调整、Enter 恢复拖收起、Escape 取消、按键连发只在结束保存的外壳验收。旧纯模型 `layout.test.ts` 本身没有这些 DOM 场景，搬入它不能补齐覆盖。
- **为什么是问题**：Teleport 保留实例不等于浏览器保留焦点与滚动，`inert` 停放还会使原焦点不可达。旧布局组件的焦点策略依赖两个槽提供 DOM 落点，单独复制布局组件不能保证产品接线正确。**推断**：编辑内容虽然没有重挂，键盘用户仍会在换拓扑或隐藏/最大化后丢失输入焦点，或者回到壳根而找不到恢复入口。尺寸 sash 的键盘操作属于外壳一；视图/容器的键盘搬移才属于外壳三。
- **依据**：`packages/neuro-book-legacy/app/components/workbench/WorkbenchShellLayout.vue:186–226,237–276,297–303,453–465`；`WorkbenchPanelSurface.vue:83–86` 标 `panel-title`，旧页面 `packages/neuro-book-legacy/app/pages/index.vue:3408–3413` 标 `panel-toggle`。`WorkbenchShellLayout.md:57–62` 要求焦点、滚动与挂载共同保留。`docs/specs/ui/nested-grid.md` 输出“鼠标和键盘调整具有开始、更新和结束边界”（行 38）及 Enter/方向/Home/End 转换（行 56–57）；`packages/nb-ui/src/components/layout/GridRenderer.md:15–17` 明确取消与键盘提交合同。
- **建议改法**：在现有 Lab lifetime 场景加滚动内容与可聚焦输入，保留原焦点策略及两个稳定标记；验收明确隐藏 → 状态栏显示入口、最大化 → 面板标题、仍可见的 Part 搬移 → 原输入与滚动保留、外部菜单/对话框焦点不被抢。真实浏览器增加一条 sash 方向键连发/keyup、Enter 恢复、Escape 与尺寸/结构变化取消场景；不另建焦点管理器。

### L5 — 建议｜代码质量：原样搬布局宿主会保留已被 nb-ui 共享能力替代的测量与发布路径

- **计划位置**：Context“现状”、关键设计第 2 节“外壳几何的纯模型”、第 5 节“外壳组件”；计划行 12、25、51、119。
- **现象**：计划以旧 `WorkbenchShellLayout` 的自有测量、`layout`、`revision` 和 `settleShellGesture` 原子落账为搬入单位，却没有接入当前 `useLayoutExtent`、`useGridLayout`。旧组件自建 `ResizeObserver`，同时在 `measure()` 和 `watch(extent, …)` 两条入口重建布局；`settleShellGesture` 内部又直接调用 `grid.resizeBranches`。
- **为什么是问题**：`nested-grid.md` 已规定共享测量与宿主，原样复制会保留两份生命周期和发布策略；以后修未挂载/零尺寸、版本失效或预览收口要改两处。也不能只把旧结算函数塞进 `useGridLayout.onApplied`：那是落账后的通知，会形成第二次落账，通知失败还不能拒绝几何。本项是已核实的职责重复与接入缺口，未声称发生浏览器故障。
- **依据**：`docs/specs/ui/nested-grid.md:66–67`；`packages/nb-ui/src/composables/useLayoutExtent.ts:16–60` 与 `useGridLayout.ts:33–47,81–118`；旧 `packages/neuro-book-legacy/app/components/workbench/WorkbenchShellLayout.vue:307–319,358–394`；旧 `packages/neuro-book-legacy/app/utils/workbench/layout.ts:861–877`。
- **建议改法**：优先复用 `useLayoutExtent`，删掉局部 observer/measure；明确一次手势只经一个原子落账入口。接 `useGridLayout` 时，把工作台可保存叶的校验与补丁求值留在纯模型，几何落账与匹配布局发布交给共享宿主；不要再包一层保存会话，也不要在 nb-ui 加 v2 适配。若暂留旧结算宿主，计划应写明这项与既有共享宿主合同的偏离及证据要求。

- **旧 Storage 依赖**：`layout.ts:44–47,143–145` 仍运行时导入旧 `nbook/shared/storage/workbench-state`；该文件 `workbench-state.ts:16–17,37–38` 又导入旧存储定义。v2 的 `nbook/*` 指向 `src/*`，没有这些旧入口。把 340/400 的默认宽度收回新纯几何常量，同一源供新记录默认显示读取；不用搬旧 Storage 文件或加别名兼容。
- **Part 改名需要全路径一致**：`activity/left/right` → `activitybar/sidebar/auxiliarybar` 不只改数组；还包括树引用、`hiddenParts`、`dragCollapsed` 键、size patch 与 `applyShellSizeField`、slots、Teleport 落点、`data-leaf`/`data-shell-slot`、compact 渲染与 scoped CSS、测试几何 id 和 Lab fixture。旧布局组件中这些接点见 `WorkbenchShellLayout.vue:72–79,124–137,231–232,375–390,438–456,474–483`。新应用无旧布局数据，不需要迁移别名。
- **测试器**：旧 `layout.test.ts:1,25–26` 用 Vitest 与旧路径；新应用纯 TS 用 `bun:test`，组件用 `*.dom.test.ts` 与真实 Vue/nb-ui。已实际验证 Bun 1.4.2 导入 `@notnotype/nb-ui/layout` 不报错、`createGrid` 是函数；`.vue` 导出只是文件路径字符串，不能据此在 Bun 挂组件，也不能把 barrel 中有 `.vue` 判为纯模型导入阻断。模型测试需改测试器和路径。
- **Nuxt**：所选纯布局、PanelSurface、StatusBar 组件的 Vue imports 已显式给出，没有发现必须搬 Nuxt 自动导入或旧 store 的理由。`defineProps`/`defineEmits`/`defineSlots` 是 Vue 编译宏；其它旧子组件按需逐一检查，不搬 `DesktopTitleBar` 和业务宿主。
- **页面与主题寿命**：计划保留 `WorkbenchDocument`、命令宿主在 `/` 页面上是正确的；二者卸载清理与 Lab 的文档主题相容。store 则按插件入口代次创建和释放。不能把文档 theme/media 或键盘监听迁入一直存活的插件作用域（`WorkbenchDocument.vue:21–43`、`WorkbenchCommandHost.vue:41–46`）。
- **根盒与已有消费者**：替换 `.nb-empty-workbench` 时去掉其居中、padding、`min-height:100vh` 对新 grid 的约束，给壳可测的确定高度；`data-workbench-root` 与单根 attrs 仍接 `PageOutlet.vue:27–29` 的 ready/instance/rpc 标记，项目短名保留 `data-workbench-project`。`settings.e2e.ts:92` 的背景观察器应改到新外壳真实表面；`window.test.ts:146` 的 `EmptyWorkbench` 名称断言是实现细节，应删除，不改钉另一个组件名。
