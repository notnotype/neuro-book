## 1. unknown-outcome 被普通 retry 重放会重复应用已落盘意图

- **严重程度**：阻断；**类别**：正确性。
- **位置**：计划第 3 节 `plan.md:64`、验收 `plan.md:118-120`；`docs/specs/storage/persistence.md:106,127-128,154`；`docs/specs/runtime/plugin-channel.md:75`；`packages/neuro-book/src/plugins/storage/shared/remote-route.ts:32-37,61-62`。
- **现象**：计划把所有失败都归成保留 reducer 的 `failed`，`retry()` 重来，未区分保存确定失败与 `unknown-outcome`。后者可能已经提交，只是回包丢了；重连订阅只给当前基线，不能还原每一次意图的完成记录。
- **为什么是问题**：窄 reducer 不等于幂等 reducer。`count => count + 1` 已写成 1 后断线，重连看到别处又写成 2，再从当前基线重试会写成 3；同一主动意图执行两次。若等订阅精确出现那次写入的 revision 才结算，也可能因重连不重放中间状态而永久等待。Storage 只返回新 revision，不替 store 记操作 id。
- **如何核实**：已在真实两个内核实例、内核路由、进程内链路与真实 SQLite 上复现：在真实保存完成后的传输回包处切断连接，保存返回 `unknown-outcome`，数据库已是 count=1；离线期间另一保存写成 2，重连基线为 2；按计划的重算 retry 写成 3。实验 `storage-runtime-smoke.ts` 位于指定 scratch 目录，两个应用最终均 `closed`。这是现有 Storage 的真实行为，不是把假的 Storage 结果喂给 store；K5 本身尚未实现。
- **建议改法**：为结果未知保留“发送时基线 revision + 具体待写值”，与确定失败分开。最少机制的方案是只重新发送同一个具体值和原 expect，不对新基线自动重放 reducer；若已冲突且不能确认该意图是否生效，返回单独的 unresolved 状态，由调用方显式核对/放弃后再决定新意图，不能宣称普通 retry 已安全完成。若要自动且精确恢复任意 reducer，则需持久化操作 id/去重合同，属于额外设计，不应藏在 retry 内。补派发前失败、落盘后丢回包、断线期间同记录后续写入、重连跳过中间 revision 的真实链路验收。

## 2. 持久化基线丢失无值记录的 revision

- **严重程度**：阻断；**类别**：正确性。
- **位置**：计划第 3 节，`plan.md:61-64`；`docs/specs/storage/persistence.md:78-82,104-105,115-119`；`packages/neuro-book/src/plugins/storage/server/partition.ts:140-146,314-319`。
- **现象**：基线只有 `confirmed: {value, revision} | null`；`status` 只有分类。删除后的 `missing` 带非空 revision，`corrupt`、`unsupported-version` 也带 revision，却没有可放进 `confirmed` 的合法值。计划又要求以 `confirmed.revision` 条件保存、对保护记录显式 `reset`。
- **为什么是问题**：从未写过、已删除和损坏记录不能都归成 `confirmed = null`。已删除记录以 `expect: null` 保存必定 `conflict`；保护记录丢失 revision 后无法构造合法的条件重置。若沿用上次正常值的 revision，同样使用过期条件。正常首次缺失时 reducer 的 `base` 取哪里也未定义，显示用 `initial` 不能自动充当已确认值。
- **如何核实**：Storage 输出 4、5 与状态表明确要求所有写入按当前 revision；实现先比 revision，再判 protected。读取分类将删除标记保留为 `{status: "missing", revision}`，保护记录保留 revision 而不给 value。
- **建议改法**：把已确认基线改为带分类的完整快照，直接复用 `RecordSnapshot<T>` 的非 error 分支，保留无值状态的 revision；显示继续单独保存。明确 `missing` 下 reducer 使用 `initial` 作为本地计算起点，但 `expect` 仍来自该 missing 快照；保护状态只允许 `reset` 使用当前快照的 revision。补从未写过、删除标记、corrupt、unsupported-version 四条真实 SQLite 用例。

## 3. 失败队首与后续提交、retry/discard/adopt 的规则未固定

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 3 节，`plan.md:63-65`；`docs/proposals/plugin-data-model.md:128-133`。
- **现象**：同字段可排多个意图，但失败时只有一个 `save = failed`，没有定义失败是否暂停队列、后续意图的显示如何投影、`retry/discard` 处理队首还是全部意图、在途时 `discard/adopt` 是否允许。
- **为什么是问题**：A 的窄修改失败后，B 如果仍从 confirmed 执行，会把显示改成只含 B 的值，A 虽保存在队列里却从当前显示消失。若 A 后来重试，又打破提交顺序。`discard` 若清空队列会丢 B，只清 A 则必须重算 B；在途 discard 也不能撤销已派发的保存。照此计划无法确定哪些结果满足“失败保留意图与当前显示”。
- **如何核实**：配套稿要求同记录按提交顺序串行、失败保留意图与显示；Storage 不拥有本地队列，也不回滚已发生的写入。属于合同遗漏，K5 代码尚不存在，未宣称实测。
- **建议改法**：固定一个简单规则：失败的队首暂停发送，后续意图继续保留；`retry` 只重试队首，`discard` 只移除失败队首并重新投影余下意图；`adopt` 只改显示、不能静默清意图。若允许在途 discard，必须明确只是放弃本地意图、不能宣称取消保存，否则直接拒绝该时机。给这些操作写结构化返回与状态表，补 A失败→B入队→retry/discard、在途 adopt/discard、关闭时结算每个排队 Promise 的验收。

## 4. readonly 视图仍能调用持久化字段的写方法

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 3 节，`plan.md:58,60-64`；`docs/proposals/plugin-data-model.md:115-117`。
- **现象**：计划以 Vue `readonly` 对外交出视图，但 `s.$fields.<名>` 同时含 `show/commit/reset/discard/adopt` 等可改变显示或保存记录的方法，没有定义只读视图是否剔除这些方法。
- **为什么是问题**：readonly 只约束属性写入，不阻止调用对象上的函数。若公开视图保留相同的 `$fields`，组件可直接 `store.$fields.sizes.commit(...)` 绕过 action；如果函数闭包持有内部可写状态，类型 readonly 与运行时代理都不拦截。这会破坏已定的“只有 actions 写”的单一写入边界。
- **如何核实**：配套稿第 3 节明确只经 actions；计划既公开 readonly 视图又把写能力挂在字段对象上。独立 `readonly-smoke.ts` 实测：Vue 3.5.39 的 readonly 对象仍可调用 `$fields.sizes.commit`，内部 display 从 300 改为 600，保存计数为 1。K5 新 store 尚未实现，此为计划未约束的接口边界。
- **建议改法**：分别定义 action 内部字段句柄与对外字段快照；对外仅含读取分类、confirmed、display、意图/保存状态，剔除所有写方法。actions 作为显式可调用入口独立暴露。补消费方无法通过公开字段方法或嵌套赋值写入、action 仍可提交的行为与类型验收。

## 5. 缺失 public getter 的常量实现无法表达 unready

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 2、3 节，`plan.md:33-34,59`；`docs/proposals/plugin-data-model.md:157`；`docs/specs/runtime/plugins.md:68,194`；`packages/nb-runtime/src/plugins/host.ts:1035-1044`。
- **现象**：每条入口贡献必须给实现，因此助手为没有 getter 的声明补 `{read(): 标量}`，返回声明的 unready 值。但是公开服务的 ready/unready 判定只有“有无绑定”和读取异常/类型不符；这个补出的函数已绑定、类型正确，会被报告为 ready。
- **为什么是问题**：合法 getter 也完全可以返回与 unready 相同的标量，不能按数值判断是否未就绪。常量补齐满足了内核输出检查，却丢掉配套稿要求的“声明了却没绑定”状态，读取者无法区分真实 ready=false 与 unready=false。
- **如何核实**：核心检查只看贡献实现是否为 undefined，不要求改内核才能承载未就绪；公开服务的两种状态是计划新增的可观察合同。此发现为接口语义核对，尚无新实现可运行。
- **建议改法**：贡献实现显式区分未绑定与已绑定，例如 `{kind: "unbound"}` 或 `{kind: "bound", read(): 标量}`。助手给缺失 getter 交出 unbound 对象，公开服务据它返回 unready，不把默认标量当假 getter。补真实 getter 返回 unready 同值但仍 ready、缺失 getter 为 unready、停止后为 unready 的独立断言。

## 6. 一层嵌套禁令使同一声明的 accepted 结果依赖查询入口

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 5 节，`plan.md:76-78`；`docs/specs/runtime/plugins.md:68,165,187`；`packages/nb-runtime/src/plugins/host.ts:757-787`。
- **现象**：A 的校验查询 B，B 的校验查询 C，C 只做结构校验。这是无环引用。直接查询 B 时 B→C 可以成功；经 A 查询 B 时 B→C 被“被查询点不能再查”禁止。B 在两种路径中分别成为 accepted 与 invalid-declaration。
- **为什么是问题**：`get/list` 承诺只返回“此刻 accepted”的声明，不能把同一条 B 在 A 内临时判为 rejected。禁令防住了递归，却也拒绝无环组合，且“外层这条”是哪条、异常是否会被 B 的 `#validation` 捕获后转为空查询，也未定义。以后配置贡献校验若再依赖公开声明，会直接触碰这条限制。
- **如何核实**：从计划所写嵌套规则推导；新 API 尚未实现，未宣称实测。现有 `#validation` 对每条声明独立推导、捕获校验异常并返回 invalid-declaration；Spec 输出 15 要求按存活登记推导，与登记顺序无关、查询不产生诊断。
- **建议改法**：查询保留本次推导的访问路径，只有重新进入路径中的同一贡献身份时判环；允许 A→B→C 的无环嵌套。定义环错误如何向依赖方传播，使顶层查询与嵌套查询得到相同判定。补无环三级链、两点互查、同点自查、get/list 及打乱登记顺序的行为测试；保持查询不记诊断。

## 7. 公开键来源没有固定绑定、撤回时的响应式失效规则

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 2、4 节 `plan.md:33-34,70-71`、验收 `plan.md:116-117`；`packages/neuro-book/src/plugins/commands/shared/contracts.ts:114-115`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchCommandPalette.vue:45-49`；`packages/neuro-book/src/plugins/workbench/web/commands/palette-host.ts:86-88`。
- **现象**：新键来源只有 problem/value，公开读取服务只有 read/declaration；没有约定绑定表变化如何被 Vue 消费者跟踪。getter 内的 store 值虽可响应式，合法但未绑定键的读取尚无 getter 可供跟踪，绑定和撤回也不是 store 字段变化。
- **为什么是问题**：命令由 A 提供、when 引用懒激活 B 的键时，面板第一次求值未就绪；B 随后只交付公开状态、不增减命令，现有命令 onDidChange 不会通知。若公开服务用普通 Map，面板缓存会一直保留不可用，撤回也可能保留旧候选；快捷键和直接 execute 重新求值却得到另一结果。单次 read 正确不能保证验收要求的面板更新。
- **如何核实**：从计划缺失的响应式合同与现有实现推断，新 API 未实现。命令服务明确 onDidChange 只通知命令增减；面板 computed 仅依赖 host.revision 与读取期间收集的响应式依赖。Lab 当前 context 回调直接读取 ref，保留这种依赖即可适配。
- **建议改法**：固定公开读取的响应式合同：每次 read 包括 unready 路径都读取可跟踪的绑定 Map 或 revision，绑定、撤回在同一响应式内核中使它失效，再同步调用 getter。这样不必增加另一套通知总线，也不必改变命令 onDidChange 的含义。补命令已登记且面板保持打开→独立状态插件激活/撤回→候选即时变化，以及值变化后的快捷键不拦截、确认等待后本地复查。

## 8. 直接引入 @vue/reactivity 缺少浏览器共享模块的构建接线

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划 `plan.md:39,105-109,144`；`packages/neuro-book/vite.config.ts:22-29`；`node_modules/@vue/reactivity/package.json:17-24`。
- **现象**：计划仅添加 @vue/reactivity 的直接依赖并要求与 Vue 同版本，未把新的浏览器直接依赖纳入 Vite optimizeDeps。当前 noDiscovery 为 true，清单预构建 Vue，却没有 @vue/reactivity。
- **为什么是问题**：相同版本不等于同一个响应式运行时。现有预构建 Vue 已内嵌 reactivity 的 activeSub/targetMap；新库直接加载原始 reactivity 模块会有另一份依赖跟踪状态。组件的 computed 读取 store 后不会被 store 修改触发，命令与布局可能只在首次读取时正确。生产构建可以合并模块，不能代替开发模式验收。
- **如何核实**：读取当前 Vite 缓存仅作为模块形状证据，未把旧缓存当新浏览器验证。scratch 的 reactivity-smoke.ts 实际同时加载当前预构建 Vue 与直接依赖的 ESM：独立模块的 state=true 而 computed=false；都经同一 Vue 模块时 state=true 且 computed=true。未启动开发服务或浏览器；新依赖进入后 Vite 实际图仍待实施期验证。
- **建议改法**：将 @vue/reactivity 加入现有显式预构建清单，确认它与 Vue 的 reactivity 被提取为同一共享模块；若选另一个浏览器导出入口，也必须保证同一运行时。保持三端库分层，不需把 Vue 放进内核。S2/S4 的接线边界列入 vite.config.ts，实施期增加开发模式实际表面的响应式 smoke，不能只靠版本一致和 Bun/Vitest 通过。

## 9. provider-stopped 不保证 store 所属实例结束，永久停订阅的前提错误

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 3 节 `plan.md:66`；`docs/specs/storage/persistence.md:125-127`；`docs/specs/runtime/plugins.md:129`；`packages/nb-runtime/src/remote/node.ts:723-724,831-840`；`packages/neuro-book/src/web/host/window.ts:145-147`。
- **现象**：计划说 provider-stopped/project-gone 都伴随实例或项目代次结束，store 会换代，因此不用恢复订阅。
- **为什么是问题**：provider-stopped 表示提供方入口停止，跨实例调用方没有依赖停止传播。浏览器的 store 可以继续活着；项目实例经代理订阅服务端 user 分区也一样。将字段永久置 error 是可选失败策略，但不能靠“store 必然换代”证明无需恢复；server-restarted、released、provider-error 和重建失败也未纳入结束规则。订阅结束后 canSave 必须立即失效，失败/排队意图必须有出口。
- **如何核实**：真实内核与 SQLite 实验先按依赖顺序停止服务端本地消费入口、再关闭 nbook.storage 提供入口；浏览器收到 onEnd("provider-stopped")，浏览器调用方工作作用域仍为 available，服务端应用 admission 仍 open，后续读为 error/unavailable。两个应用最后均 closed。项目结束与服务端换进程在真实窗口宿主中会触发 destroy，但 provider-stopped 不进入那个分支。首次独立关闭提供方因本地借用未释放而超时，修正实验按正常依赖顺序释放后得到上述结果，未把超时当产品缺陷。
- **建议改法**：分清“调用方自己结束”“连接/实例终态”“提供方入口结束/订阅重建失败”。可保留不自动重开的简单策略，但必须给仍活 store 一个显式恢复/重建入口或明确要求重建 store/刷新，并同步 ready/canSave、队列失败与返回值；不要承诺所有 onEnd 都随 store 换代。补提供方单独停止而调用方存活、恢复/刷新、结束早于建立返回的验收。

## 10. 释放时丢弃意图的论证误用了 Storage 门面的释放顺序

- **严重程度**：重要；**类别**：文档。
- **位置**：待确认 5 `plan.md:147`、第 3 节 `plan.md:58,65`；`docs/specs/runtime/plugins.md:66,190`；`docs/specs/runtime/services.md:166-168`；`packages/neuro-book/src/web/host/window.ts:195-199`。
- **现象**：计划以“入口停止时 Storage 服务对象也随之释放，发不出去”为由，建议丢弃尚未发出的保存意图。
- **为什么是问题**：正常收口时，store 登记的入口工作资源先释放，必需依赖借用后释放；Storage 按调用方门面位于必需借用一侧。浏览器宿主也在插件收口完后才关链路。因此至少正常关闭路径仍有使用 Storage 完成收口的时段，丢弃不是机制强制，而是主动选择数据丢失。另一边，队列不能继续接受新意图或无限等待，因而也不应简单改成无界 flush。
- **如何核实**：runtime.plugins 输出 13 明确依赖者资源先于必需借用结束；实现合同把 `context.scope` 放在持有必需借用的激活作用域的子层。runtime.services 的门面先于自身借用释放；窗口实现注释和 stopped 回调明确链路最后关闭。
- **建议改法**：保留待确认，但换成真实取舍：停止信号到达时封闭 actions、暂停新发送；可选策略为丢弃尚未发出的意图，或在宿主截止内结算已接纳队列，强制退出仍不保证。若推荐丢弃，说明正常关闭也可能丢掉已经由 action 接纳的修改、每个调用必须返回 cancelled/unsaved，外壳的正常退出协商需要另行承接；只记诊断不足以向消费者结算保存结果。补 action 已接纳→入口正常关闭与队列 Promise 全部结算的验收。

## 11. 推迟镜像的代价少算了整条跨实例命令验收链

- **严重程度**：重要；**类别**：文档。
- **位置**：计划 `Context` 的 `plan.md:12`、第 2 节 `plan.md:35`、待确认 1 `plan.md:143`；`docs/proposals/multi-instance-runtime-topology.md:321,361,373,380`；`docs/proposals/plugin-data-model.md:158`。
- **现象**：待确认 1 把代价写成“两窗口只测本地求值”和“不验证断线撤回”；但拓扑 K5 的范围还明确包含“命令跨实例执行”。计划没有给出这条范围推迟后如何重新分配、哪些消费者会被阻断；S0 文档表也未记录拓扑 K5 行的范围偏离。
- **为什么是问题**：两个本地命令表各自正确，不能证明服务端显式选窗口后列出/执行正确，也不覆盖客户端收到命令后的本地复查、连接和入口代次失效。这是已接受 K5 的一段完整能力后移，不能按少测两个场景表达其代价。“现在没有消费者”也不能当成验收不需要它：K1–K4 与本片都已采用真实测试插件验证平台机制。
- **如何核实**：拓扑稿 K5 行同时列出客户端镜像键空间、跨实例命令范围和断线镜像验收；配套稿第 4 节明确了目标客户端选择和到达客户端后复查。代码事实确有服务端清单只装配本位置入口的限制，因此需要设计，但限制不等于消费者缺席就可验收该能力。
- **建议改法**：若保留推迟建议，明确交开发者批准的是 K5 范围调整，列出延期项：远程命令目录/执行、目标客户端上下文、镜像来源入口代次与连接收口、本地复查；给出一个确定承接 Task 的触发条件与前置设计工作，并在拓扑稿决策记录追加本次范围决定、Task README 和相关 Spec 边界同步。若不批准缩减，则把这条真实远程链并入本计划；内核路由和测试插件已可用于验收，不必等 Agent/TUI 产品消费者。

## 12. 验收映射没有给出真实依赖下强制时序的办法，且漏掉关键边界

- **严重程度**：重要；**类别**：测试。
- **位置**：计划 `plan.md:116-124,130,135`；`packages/neuro-book/src/plugins/storage/server/partition.ts:158-159`、`server/owner.ts:95-96`；`packages/nb-runtime/src/remote/node.ts:662-675,329-345,898-913`；`docs/specs/README.md:20,77,129-130`。
- **现象**：表中写了“保存结果早于本次快照”“两个 store 以同 revision 提交”“第二次冲突”，却没有控制这些顺序的真实切口；e2e 顺序操作两个自动订阅的 store，第二个执行前很可能已经拿到新基线，根本不会冲突。另未映射删除 revision、unsupported-version、首次/结束早于订阅建立返回、readonly/action 写边界、同字段排队、unknown-outcome、provider 独立停止与读取函数返回错误类型。新 Spec 编号也尚未分配。
- **为什么是问题**：现有正常活订阅路径先通知后返回保存结果；不能为了覆盖“结果先到”把假 Storage 或任意重排 FIFO 帧当真实依赖。光断言最后成功不能证明冲突重放发生；两次全文替换同一个 text 字段也不能证明窄修改保留了对方修改。缺失的边界正好会漏掉前述设计错误。
- **如何核实**：真实 SQLite write 在返回结果前同步派发通知；远程保存实现返回 write 结果，节点再 await 后回包。重连订阅重建是异步启动、不等基线再让 connect 返回，所以可利用这个真实边界或未建立完成阶段覆盖相反顺序。现有 e2e 的显式 expect 能固定冲突，计划新 store 自动选 confirmed 后则不再具有同一切口。Spec/计划规则要求按编号映射验收；本片还未写 Spec，编号需在 S0 后收口。
- **建议改法**：S0 后把表换成稳定 Spec 编号到具体场景；补上述边界。合同测试用真实内核/Storage，利用连接、订阅建立和受控传输发送门闩暂停发送真实请求，同时保留同链路 FIFO，先让两个提交取得同 revision 再释放；第二次冲突在真实订阅/读快照回调或第二个真实写者处安排。e2e 探针提供明确的准备/释放门闩并输出结构化冲突次数/保存结果，记录值至少有两个独立字段，由两个窗口分别窄改，最终同时保留。不能在传输或初始化阶段制造所需顺序的场景，应删除该假时序判据或标明真实适用阶段。
