## F1（高）内置插件表的“消费能力”列无法判定依赖方向，按字面 `project-runtime` 与 `workspace-files` 互为依赖

位置：行 236（列名）、241–243、244；首个受影响切片在 284。

原文摘录（第三列“消费能力与运行位置 / 作用域”）：

- 241 `storage`：身份、持久化适配、Project 绑定能力；user/project
- 242 `project-runtime`：文件/数据库等必需服务；后端进程管理 Project scope
- 243 `workspace-files`：授权、Project/用户资产访问；后端资源 scope

问题：该列同时引用具名 module（244 行“生命周期”= `runtime-lifecycle`）、具名插件（`Storage`、`配置`）和未具名对象（“持久化适配”“配置后端”“恢复存储”“领域数据库”“资产/模型服务”“受管进程能力”）。表头只写“消费能力”，行 234 只解释了“提供”列的语义（合同边界，不是同名服务类），没有任何规则说明“消费”条目是否构成激活依赖。两种读法都有缺陷：

- 按字面把引用插件的条目当激活依赖：“文件…服务”指向表内唯一的文件服务 `workspace-files`，而 243/241 又要求 workspace-files 与 storage 消费 Project 访问/绑定 → `project-runtime ↔ workspace-files`（并牵入 storage 的 Project 绑定）互为依赖。行 103 规定依赖环必须在业务副作用前拒绝装配，行 110 又禁止用惰性解析隐藏依赖环；两者合并意味着这批插件按字面在任何环境都无法装配。
- 按“底层适配器”解读：表中没有任何行提供“文件/数据库”适配器对象，行 315“依赖图和 owner 清单能被查询”与行 169（`runtime.services` 验收含“缺依赖、环”）无从编写。

影响场景：行 284 的 Files 纵向链要求第一切片从启动清单装配 Project、文件服务、View、命令与 Storage；实现阶段必须把本表当依赖输入，两种读法分别得到“永远装配失败”与“边界不可判定”，Spec 无法验收。

最小修正：在表后（行 258 之前）补列语义规则，并把 242 的“文件/数据库等必需服务”改为具名对象。

```text
- 本表“消费能力”列中具名的插件或 module 条目是激活依赖；底层适配器、宿主能力与窄协议运行期绑定必须显式标注（如 `适配器：name`、`运行期绑定：capability`），不参与依赖环检测。
- Project 领域所需的文件/数据库访问来自底层适配器（如 `fs-adapter`、`persistence-adapter`）；`project-runtime` 不得激活依赖 `workspace-files` 或 `storage` 服务本体。
```

同类未具名消费项应按同一规则命名或标注：251“角色领域能力”、253“资产/模型/持久化服务”、257“受管进程能力”。

## F2（中）“拒绝装配”的对象未定义，与局部失败承诺并存

位置：行 103；关联 104、116、120、169、171、299、302。

原文 103：“同一服务键与解析作用域默认只有一个选定提供者。重复提供、缺少必需依赖和依赖环在产生业务副作用前拒绝装配；确需多个贡献的能力由专用注册表管理，不借 DI 覆盖规则实现。”

最小修正（二选一，推荐前者以与 120/302 保持一致）：

```text
（推荐）…重复提供、缺少必需依赖和依赖环在产生业务副作用前拒绝该插件/服务绑定的装配：该插件不发布可用能力，其消费者显式失败；只有启动必需插件失败才阻止所属应用 ready。

```

## F3（中）实例级排他租约在生命周期矩阵与插件表中没有 owner 与门禁落点

位置：行 210；关联 44、133–134、214、241–242、253、287、291、308。

原文 210：`| 后端运行实例 | 本次进程实例；启动适配器 | 门禁与必需服务成功，才接纳业务 | 拒绝新请求，收口消费者，再释放提供者；失败保留诊断 | 用户数据保留；进程退出不代表所有外部副作用成功取消 |`

问题：提案三处承认“租约”（134 强制关闭/崩溃/租约丢失必须区分；291 不能同时启动新旧 owner 访问同一有排他要求的数据根；308 不提前释放排他租约），行 44 也把“迁移与 Session Store 租约有先后要求”列为现状证据，但矩阵与插件表都没有把“本次实例对 state root 的排他持有”归给任何 scope 或 owner；唯一的相邻规定是行 214 的 Project 级“占用”（不同层级）。主树现状是实例级门禁：`product-startup.ts` 在 migrations 之后获取 Session Store runtime lease（56），失败重抛（57–70），`00-product-startup.ts` 让所有 HTTP 能力等待同一 startup、失败即终止进程（4–9、12–15）；租约被其他进程接管时按 ADR 0010 §loopback 9 有序关闭并以退出码 75 结束，原因是“继续写入会让两个 owner 同时操作同一份 Session Store”。

影响场景：编写 `runtime.application`（行 171 验收含“真实停机”）或执行 Files 纵向链（284）时，若只按行 210 的“必需服务 ready”接纳业务，装配可能缺少实例级门禁；或把租约挂在某个可停止的插件实例（如 `storage`/`agent-runtime`）上、随工作台或 Project 关闭释放，直接违反 287 的禁止项与 291。

最小修正：改 210 行，并在插件表标注该 owner（现状实现属 Agent Session Store；若迁移到持久化适配器，须在表内显式改名）。

```text
| 后端运行实例 | 本次进程实例；启动适配器 | 取得并持有对本次 state root 的排他租约，且门禁与必需服务成功，才接纳业务；获取失败不得接纳业务 | 拒绝新请求，收口消费者，再释放提供者；租约释放或失效关闭的顺序与退出语义由持久化/Agent 领域 owner 提供；失败保留诊断 | 用户数据保留；进程退出不代表所有外部副作用成功取消；租约寿命不随 Project、工作台或插件实例结束而提前终止 |
```
