## 发现明细

### F1（P2）诊断：文件位置的出口定义与轮转/保留责任不兼容

- 位置：`docs/specs/runtime/diagnostics.md` 37（并 19、27、43、55、65、78、79、98、111）。
- 原文：37 "诊断出口（sink）：宿主按运行位置提供的窄写入能力，只接受结构化记录（文件追加、console、有界内存缓冲）。它不提供读取、目录管理、任意路径寻址或通用文件句柄，诊断不能借它代行文件操作。"；43 "…该运行位置的诊断出口（有文件系统时提供日志位置，无文件系统时提供 console 与有界内存缓冲）"；55 "有文件系统时写入运行实例日志位置，达到单文件上限轮转并按保留预算（文件数、总字节、时限）回收"；79 "有文件系统时日志文件、轮转与保留由 runtime-diagnostics 拥有"。
- 问题：轮转＝重命名当前日志文件＋按预算回收旧文件，属目录管理；而"出口"被统一定义为不含目录管理的只写通道，且 45/98 明确"持有出口不等于获得文件能力语义""诊断不能借出口读写任意文件"。两者不能同时成立：若宿主交付的是"日志位置"，则提供者必须自行用文件系统 API 做目录操作，"出口不承担文件能力语义/缺少文件能力不影响诊断启动"的框架失效；若宿主交付的是只写 sink，则提供者无任何被许可的路径去轮转与回收。43 与 37 用同一个词（出口）指两个不同的东西，是实现分歧的直接来源。
- 违反场景：第二切片"诊断插件…窄 sink 适配与测试；复用现有日志输出能力"（implementation-plan.md 切片二单元表）按 37/78 字面实现，只拿到 append 通道 → 无法 rename/prune；验收 6（"轮转且总量受预算约束"）与验收 1（真实文件读回）无法满足；或者实现者私自直接操作日志目录，于是"谁能读/枚举日志目录"没有任何合同约束，后续消费者审计无从判定。
- 最小修正：区分两类出口并在术语表拆词——有文件系统时宿主提供**已校验的日志位置（路径/根能力）**，日志文件、轮转与保留由 runtime-diagnostics 在该位置内执行；`文件追加` 只描述"写这一动作"，窄 sink 的"不提供读取/目录管理"限定为 console、紧急输出与浏览器缓冲通道（与 F2 一并改）。

### F2（P2）诊断：内存缓冲同时是"只写 sink"与"需要查询/淘汰的存储"

- 位置：`docs/specs/runtime/diagnostics.md` 55（并 37、65、78、79、113）。
- 原文：55 "…无文件系统时写入宿主 console 与有界内存缓冲，超过缓冲上限按保留预算丢弃最旧记录，不要求落盘。"；78 "出口是宿主提供的窄 sink：仅追加诊断记录，不读取、不枚举目录、不寻址任意路径、不代行文件能力；无文件系统位置的缓冲上限由保留预算约束。"；79 "宿主拥有 console、紧急输出通道与缓冲能力"；113 "以宿主提供的 console 与有界内存缓冲出口创建运行实例 → 能记录并查询事件，超过缓冲上限时按预算丢弃最旧记录"。
- 问题：56 要求提供者"读取当前运行实例最近的诊断"并提供按级别/来源过滤的查询，55/113 要求"按预算丢弃最旧记录"。但缓冲被定义为宿主拥有、只接受追加、不提供读取的出口：提供者既读不到记录（查询无从实现），也淘汰不了（无读/无删）。唯一出路是宿主另暴露一套有界读/淘汰接口或提供者自己再存一份——前者 Spec 未定义，后者与"宿主拥有缓冲能力"和"不建立第二份日志正文"（100）冲突。
- 违反场景：浏览器/无文件系统位置（第一片验收与切片二"无文件系统出口"验收 8）按 37/78 实现 → 只能 write-only，验收 8 的"能记录并查询事件、按预算丢弃最旧"不可满足；或实现者暗中双写缓冲，查询结果与宿主 console 不一致，且没有 owner 负责淘汰。
- 最小修正：把无文件系统位置的缓冲明确为**提供者拥有的有界内存存储**（可追加、可按级别/来源读、可按预算淘汰最旧），宿主只负责 console 与紧急输出；或保留宿主拥有但把出口操作扩展为显式的"有界读 + 淘汰最旧"，并写明 owner 与上限来源。

### F3（P2）诊断：多实例共享同一物理日志目录时，轮转/保留没有按实例划分 owner 与预算口径

- 位置：`docs/specs/runtime/diagnostics.md` 79–81（并 21、56、106、111）。
- 原文：81 "既有日志位置解析入口（含显式日志目录环境变量 `NEURO_BOOK_LOG_DIR`）保持兼容，不新增第二套位置解析；既有布局允许多个运行实例共享同一物理日志目录，本能力不要求为每个实例新建独占目录，也不改变该布局。"；79 "有文件系统时日志文件、轮转与保留由 runtime-diagnostics 拥有"；111 "…回收只作用于本能力拥有的日志，不触碰用户或业务数据。"；106 验收要求两个运行实例共享同一物理日志目录。
- 问题：同一物理目录下多个**存活**实例各自"拥有日志文件、执行轮转与保留"时，文档没有规定：哪个实例拥有哪个文件、预算是每实例还是每目录、以及"本能力拥有的日志"在共享目录中如何判定。lifecycle 要求每个资源同一时刻只有一个关闭 owner，此处同一批物理文件被多个实例同时声明拥有与回收权。兼容基线（`server/app-logs/logger.ts`）以固定名 `server-current.jsonl` 作为"当前文件"、轮转靠重命名该文件、回收按目录预算只保护本实例当前路径，因此两个实例共享目录时天然互相改名/回收对方仍在写入的文件。
- 违反场景：实例 A 首次写入触发回收或达到单文件上限触发轮转 → 重命名/删除实例 B 正在写入的文件：POSIX 下 B 继续写入已删除的 inode（B 的诊断静默丢失），Windows 下对占用文件 rename/删除失败，进入异常路径；或两实例各自满足自身预算，目录总量达到 2× 预算，验收 111 的"总量受预算约束"不可判定。静默丢失发生在诊断能力自身，属于最不该丢证据的路径。
- 最小修正：规定共享目录下的实例分区与预算口径，例如"每个运行实例在日志目录内独占一个以实例身份命名的文件/子目录；预算按实例计算；回收不得触碰仍存活实例的文件"；若确实要沿用"共享同一文件"的既有布局，则必须写清多写者下的轮转/回收仲裁与失败可见性（谁 rename、失败如何报告），并把验收 106 的两实例期望改写成可判定的形式。

### F4（P3）诊断：实例身份是查询过滤的依据，却是"可缺失"且"不改变数据格式"的字段

- 位置：`docs/specs/runtime/diagnostics.md` 56（并 53、99）。
- 原文：56 "…只返回本运行实例的记录——同一物理日志目录被多个实例共享时按记录中的运行实例身份过滤，不返回其它实例、其它进程或其它设备的记录。"；53 "事件可观察结构：时间戳、级别、事件名与消息保真；来源字段提供时保留、缺失时标记为未知，不伪造归属。"；99 "既有可观察行为（逐行结构化日志、脱敏、轮转与保留预算、位置解析入口）在后端运行位置保持兼容；`packages/neuro-book/server/app-logs/` 是兼容基线。本切片不改变日志数据格式，不做日志迁移。"
- 问题：过滤依赖"记录中的运行实例身份"，但 53 允许来源字段缺失并标记为未知，99 又声明本切片不改变日志数据格式；兼容基线的记录结构（`AppLogEntry`）没有运行位置/实例身份字段。三条合并后的可判定性缺口：按 99 字面不新增字段 → 共享目录读回时无法判定归属（他实例记录要么泄漏、要么丢弃本实例记录）；新增字段 → 与"不改变日志数据格式"的字面冲突，且来源缺失记录该如何过滤（泄漏还是丢弃）没有规则。
- 违反场景：验收 1（两实例共享目录、按实例过滤）在实现侧二选一都会与文档某一句冲突，测试只能按实现者的解读写成"期望"，失去防回归价值。
- 最小修正：写明"提供者在每条记录写入运行位置与运行实例身份（属于来源字段，允许对既有 JSONL 单向增补）"，并把 99 的"不改变日志数据格式"限定为"保持逐行 JSONL、级别/事件语义与既有字段含义，不迁移既有文件"；同时规定身份缺失记录在查询中的处理（例如按"未归属则不返回"），或改用 F3 的每实例文件划分让过滤不依赖记录字段。

### F5（P2）平台文件：权限按消费者授予，操作入参却只携带"根身份"

- 位置：`docs/specs/platform/files.md` 45–46（并 33、34、106）。
- 原文：45 "权限按最小授予：只读、读写（写含创建与替换）、删除单独声明。借用者不能把只读升级为写；同一根对不同消费者可有不同授予。"；46 "每类操作携带取消信号与根身份；写操作只在资源约束允许时创建目标父目录，且不得在根外创建。"；33 "根能力（root capability）：宿主或更高 owner 签发、已经校验的位置，附带允许的操作集合与身份。"；34 "资源约束：owner 签发的一次操作声明，包含根身份、根内相对路径、访问模式与预期变更。"
- 问题："同一根对不同消费者可有不同授予"要求机制能区分每个消费者的授予，但操作只携带"根身份"，而 33 把"允许的操作集合与身份"绑在根能力上、34 的资源约束又自含访问模式。同一根上两份不同授予（只读 / 读写）因此无法在机制里被区分：按根声明校验会让只读持有者越权写，按请求自报模式校验则"只读不能升级为写"（45）直接失效，而 106 的验收（"只读授予不能执行 rename，缺少写或删除权限时整体拒绝"）要求前者可判定。
- 违反场景：只读消费者持该根的公开身份发起写/删除/rename；实现只能二选一——越权落盘（权限模型失效），或把合法写判为拒绝（能力不可用）。
- 最小修正：把"根身份"拆为稳定根身份 + 每消费者一份授予（授予身份唯一、携带允许操作集合），操作入参改为携带**授予身份**并写明校验为"请求操作 ⊆ 授予集合 ∩ 根声明"；若坚持不引入授予身份，则必须写明每次签发产生独立身份且该身份即入参，同时把 106 的"只读根"改为"只读授予"。

### F6（P3）平台文件：订阅释放语义自相矛盾，验收比正文更严

- 位置：`docs/specs/platform/files.md` 55（并 107）。
- 原文：55 "…释放语义只覆盖未来投递：释放后不再有新的投递，已经进入执行或已排队的回调不会被撤回（不能时光撤销）；消费者回调须容许在被释放后仍完成一次执行，应幂等或在入口检查自身有效性。"；107 验收 4 "…释放订阅后不再投递新事件（释放瞬间已进入执行的回调允许完成，测试不要求撤销已开始的通知）…"。
- 问题："已排队但尚未调用"的回调在释放后发生，正是"新的投递"：正文允许它发生，同时又说释放后不再有新投递，两句互斥；验收 107 只豁免"已进入执行"，比正文严格。实现者必须在"取消排队投递"（违反正文）与"保留排队投递"（违反 107）之间二选一，写不出稳定验收，且测试既可能钉死实现也可能放过真实回归。
- 最小修正：改为"释放只阻止释放之后新排队的投递；释放时已进入执行或已排队的投递仍可能完成，消费者须幂等"，并同步 107 的期望（允许一次已排队投递完成）。

### F7（P2）插件：激活的取消未区分"单个触发方取消"与"入口作用域停止"

- 位置：`docs/specs/runtime/plugins.md` 66（并 48、55；对照 `docs/specs/runtime/services.md` 51、66、99、114）。
- 原文：plugins 66 "| 激活中 | 取消或作用域关闭 | 收口中 | 迟到的成功不发布；已登记资源收口 |"；48 "同一激活实例的并发触发合并为一次激活；成功后同代次的后续触发直接复用，不重复发布贡献"；55 "激活被取消或作用域关闭后，迟到的成功不发布…"。对照 services 51 "…某个等待方取消或断线只结束它自己的等待，不取消共享初始化、不改变其他等待者的结果；共享初始化只由提供者 owner 作用域的停止/取消或初始化自身失败收口"，66/99 "某个等待方取消不取消共享初始化（只有提供者 owner 作用域停止/取消才收口共享初始化）"。
- 问题：services 对"共享初始化"的单等待方取消有明确规则，plugins 对"共享激活"只写"取消"，没有说明谁有权取消一次已被合并的激活。由于激活同样是合并执行的一次事务，若把"某个触发方（消费者请求中止/断线）的取消"当作激活取消，就会撤回其他等待者仍要使用的暂存贡献并让他们拿到失败——这正是 services 禁止的"单个等待方改变其他等待者结果"，只是对象从初始化换成了激活。两文对同一并发情形给出不同默认，实现会按各自解读分叉。
- 违反场景：消费者 A、B 并发首次触发同一入口激活；A 的调用被中止 → 若按 66 取消共享激活，B 的等待失败且本激活贡献被撤回（B 健康且仍需要该能力）；若实现选择忽略 A 的取消，则与 66 的字面"取消即收口"不符。
- 最小修正：在 66/55 补一句"只有提供入口自身作用域停止/取消、或激活自身失败才取消共享激活；单个触发方或等待方取消只结束其等待，不取消共享激活、不撤回暂存项"，并在验收 5（118）后补"一个触发方取消后，另一等待者仍取得同一结果"（确实要支持"取消即整激活收口"的话，须同时说明它如何不违反 services 51/99）。

### F8（P3）SQLite：借用面是否可关闭/可转移未定义，与"归还借用不等于关闭数据库"冲突

- 位置：`docs/specs/platform/sqlite.md` 34（并 47、58、71、98）。
- 原文：34 "借用（borrow）：消费者（领域 repository 或不同驱动，如 libsql、Prisma、内置驱动）从 owner 取得的连接与事务使用权；归还借用不等于关闭数据库。"；71 "借用：借用中 → 已归还（归还幂等）；owner 关闭前必须收口借用，未归还导致的关闭失败必须可见，不静默强关正在使用的连接。"；58 "关闭：owner 先拒绝新借用、收口消费者，再关闭登记连接；借用归还后关闭成功。"
- 问题：借用被定义为"连接与事务使用权"，但没有规定借用返回给消费者的是受限使用面（执行/事务/归还）还是物理驱动连接本身。若借用面带着驱动的 `close()`（现状 World/Plot/`agent-sql` 就是各自持有 libsql/Prisma client），借用者随时可以关闭/替换物理连接：owner 的登记表会指向已失效连接、"借用归还后关闭成功"与"不静默强关正在使用的连接"的判定失效，也违反 lifecycle"borrower 释放借用只结束自己的使用关系，不关闭共享资源""不得转交新 owner"。文档既未禁止，也未规定越权关闭后的可见结果。
- 违反场景：领域在归还前自行关闭连接（或把句柄转交另一模块），owner 关闭阶段只能观察到"已关闭连接"：要么按成功路径收尾（违反"不受管"），要么报出与借用无关的驱动错误，而"借用未归还导致的关闭失败"与"连接被借用者销毁"无法区分。
- 最小修正：明确借用面不得暴露物理连接关闭与所有权转移，只能执行语句/事务并归还；并补一条"借用者越权关闭或外部销毁连接时，owner 在归还/关闭时探测到失效必须报告为未完成并保留 owner 与原因，而不是当作已释放"。

### F9（P3）SQLite：缺少"同一物理文件"的身份判定规则

- 位置：`docs/specs/platform/sqlite.md` 74（并 44、98、100）。
- 原文：74 "…同一物理文件在同一运行实例内只有一个物理资源 owner 登记（协作登记），不允许第二套 owner 体系并行管理。该唯一性不跨进程强制…"；98 "物理资源归属：每个物理文件在运行实例内恰有一个 owner 登记"；100 "兼容：…通用机制只消费已解析定位，不重复实现解析。"
- 问题：唯一性以"同一物理文件"为单位，但 100 把机制限定为"只校验形态"（拒绝 UNC/非法 URL/越过 State Root 的相对 URL），没有规定物理身份如何判定。同一文件的不同写法（`file:` URL 形态、大小写差异、经符号链接/junction 的父目录、相对与绝对等价路径）在形态校验下都合法，于是两个具名资源可以分别登记、各自打开连接、各自 flush/checkpoint，唯一 owner 与关闭语义实际不可判定；验收 4 只覆盖"非法定位"，没有覆盖"两个具名资源指向同一文件"。
- 违反场景：Project 库被上层用规范化路径注册一次、又被另一个入口用等价写法注册第二次 → 两个 owner 同时管理一个文件，"Project 关闭先拒绝新借用并收口消费者，再关闭登记连接"（98）在其中一个 owner 上无法执行，关闭后仍可能有另一 owner 的连接在写。
- 最小修正：规定物理身份以规范化绝对路径判定（对父目录做 realpath 并做 Windows 大小写归一；要求宿主交付的定位为规范化绝对路径），同一身份重复注册即冲突；验收补一条"同一物理文件的两个具名资源注册被拒绝"。

## 按分配清单的反证结果（已检查、未发现问题）

1. **关闭/取消/超时/迟到获取**：lifecycle、services、plugins、application、diagnostics、files、sqlite 七项都采用"创建中→可用→停止中→已关闭"同构阶段与"关闭未完成不是第五阶段"的规则，并都写明迟到成功不发布、超时不映射为 closed、失败保留 owner 与原因；未发现"按成功路径提前释放"或"迟到资源复活已关闭作用域"的允许项（唯一出口缺口见 F1–F4，属诊断出口能力定义，与阶段语义无关）。
2. **复用与 scope**：services 的 single-flight 按提供者作用域隔离、子作用域复用祖先实例、不同窗口/实例不共享结果（services 51/66/67/114），与 lifecycle 的作用域树、寿命合法性（services 53）方向一致；未发现"每个消费者子作用域重复实例化"或"跨窗口共享实例"的允许项。
3. **单等待方取消**：services 在术语、输出、失败与恢复、验收四处一致（31/51/66/99/114）；plugins 缺同款激活规则 → F7。
4. **必需消费者闭包**：services 的闭包定义（30/50）+ plugins 失败隔离（输出 7）+ application 门禁（输出 2、状态表 49）三者一致：闭包内不发布半成品、健康上游不被隔离、涉及启动必需能力才阻止准入；未发现首轮提案 F2 那样的"整实例拒绝 vs 绑定拒绝"双读残留。
5. **动态等待环**：services 把静态依赖边与运行时等待边合并成图（输入、失败与恢复、验收 4），静态环零副作用拒绝、动态环不回滚但阻断发布并按 lifecycle 收口，且明文禁止用惰性解析隐藏环与禁止把动态环报告成"无入口被激活"；与 lifecycle 收口、plugins 失败收口一致。
6. **贡献跨 receiver 发布/撤回**：plugins 输出 5（暂存 + 全接收者成功才开放调用门禁 + 失败撤回全部暂存项）、状态表"撤回事务内未发布的贡献项→移除本次未发布项、描述保留"、失败与恢复"本地注册事务可撤回、外部副作用不可撤回"三者自洽；跨位置非原子与"不要求目录一致快照/网络事务"已显式限定；未发现"某接收者已可调用的半成品"被允许，也未发现撤回会越界删除他人贡献或静态描述。
7. **日志 fallback/浏览器/owner**：降级（39/52/58）、紧急最小输出（20/34/57）、"无 Storage 依赖"（45/108）、"诊断不反向依赖"（45/97）自洽；问题集中在出口能力与归属定义 → F1、F2、F3、F4。
8. **可信文件路径/锁**：根约束、根内相对寻址、包含校验（目标/父目录分别处理）、rename/unlink 权限组合、TOCTOU 与"不对抗恶意外部进程"的显式边界相互自洽，与既有 `file-path.ts` 的校验集合"等价或更严格"可满足；协作锁的 advisory + 延迟失效探测 + 不 fencing，与其链接的 `agent.session-store-lease` 既有语义一致，未发现"可发现=已授权"或"锁=强互斥"的表述。缺口见 F5、F6。
9. **SQLite 事务/多驱动 owner/关闭权限**：定位由 adapter 解析、机制只校验形态；借用上界（44）、autocommit 与显式事务（46）、已知失败与结果未知的区分（36/57/89/111）、关闭重开代次（38/58/72/114）、"四个库各有独立 owner"与"借用人只归还"边界自洽；未发现自动迁移、隐式提交或自动重放写操作的允许项。缺口见 F8、F9。
10. **七模块互相等待或责任空白**：按各文声明边重算依赖方向为 DAG——diagnostics 不依赖任何产品能力、files/sqlite 只依赖宿主能力与资源 owner、lifecycle→services→plugins→application 单向向上，未发现"诊断等 Storage""文件等 Project""SQLite 等 Project"一类闭环，也未发现必需资源缺少 owner（诊断出口的 owner 归属问题见 F1/F2/F3）。首片"两种作用域 × 两个 host"与 implementation-plan 的单元拆解一致，实施路径对测试/类型检查配置的现状判断已核实为准确。
