## 发现

### 3. 阻断｜接口与合同：计划中的业务失败码 `denied` 不能定义为远程合同

- **计划位置**：“关键设计 / 3. 受根约束的文件原语”“4. 读、列出与三类文件夹”；`plan.md:44,57`。
- **现象**：计划明确把 `denied` 列为远程合同的业务失败码，用于控制目录等拒绝。现有 `defineRemoteService` 会在定义合同时拒绝与路由层重复的业务码；`denied` 正是路由保留码。
- **为什么是问题**：照计划定义两份合同会在模块加载时抛 `TypeError`，插件无法登记，更无法进入 S1–S4 验收。让 rooted 层直接抛出同名普通错误也不能补救：未声明的提供方异常按运行时变成 `provider-error`，丢失计划要求的业务拒绝分类。
- **依据**：`packages/nb-runtime/src/remote/protocol.ts:27–38` 列出 `denied`；`packages/nb-runtime/src/remote/contract.ts:125–140` 显式拒绝重名并抛错；`docs/specs/runtime/plugin-channel.md:90,164` 规定未声明异常的结果。实验 A 直接运行真实 `defineRemoteService`，得到明确的业务码与路由保留码重名 `TypeError`。
- **建议改法**：业务权限失败用一个不保留的码，例如旧平台合同的 `permission-denied` 或 `protected-path`；路由的 `denied` 原样保留。同步改失败码表与验收，避免在文件客户端按错误文本重新分类。

### 1. 重要｜接口与合同：8 MiB 文本合同超过现有 RPC 消息上限，保存会断开连接

- **计划位置**：“关键设计 / 4. 读、列出与三类文件夹”“6. 浏览器文件客户端”“7. 测试场地与样本”；`plan.md:55–56,69,74`。
- **现象**：文件读取允许至 8 MiB；保存把整个 `text` 放在一次远程调用中。当前 RPC 端口的入站单条消息上限为 1 MiB。2 MiB 的 ASCII 文本即使完全符合计划的文件上限，保存请求也已超过真实 WebSocket 传输上限。JSON 转义还会让部分不到 1 MiB 的文件超过单帧上限。
- **为什么是问题**：正常文件保存会被传输中断，并按写请求规则得到 `unknown-outcome`，同时影响同一窗口链路上的其它请求与订阅。计划的进程内 JSON 链路场地不实施 WebSocket 的大小限制，会漏掉这一真实链路差异；3000 个 5–30 KB 文件也覆盖不到上限。
- **依据**：`docs/specs/runtime/plugin-channel.md:115` 明定单条消息 1 MiB；`packages/neuro-book/src/shared/rpc-socket.ts:15–16` 定义 `RPC_MAX_MESSAGE_BYTES = 1024 * 1024`；`packages/neuro-book/src/server/rpc/listener.ts:74–79` 把它传给 Bun 的 `maxPayloadLength`；同 Spec 输出第 4 条规定已发出的写请求中断为 `unknown-outcome`。实验 A 使用真实端口：64 KiB 成功，2 MiB 导致关闭码 `1006`、`unknown-outcome/disconnected`，提供方只执行了前一次小请求。
- **建议改法**：t68 先明确内容传输合同。部件最少的做法是暂时沿用现有 RPC，只接受编码后完整请求能装入单帧的文本，发送前返回可区分的 `too-large`，同时明确写入端限制，不能只限制读取。若保留 8 MiB，就在 t68 加入已接受拓扑的 HTTP 大块内容通道，并明确上传、基线校验及寿命；不能等 t71 才发现需要更改服务接口。验收至少通过真实 RPC 端口覆盖临界大小及转义膨胀。

### 5. 重要｜正确性：条件保存只定义“核对 hash 再替换”，没有把核对与提交放在同一互斥边界

- **计划位置**：“关键设计 / 3. 受根约束的文件原语”“4. 读、列出与三类文件夹”“验收映射”；`plan.md:45,55–56,107`。
- **现象**：两个窗口用同一基线同时保存 A、B；两个请求都能在任一个 rename 前读到旧 hash，随后各自替换并成功。原子 rename 只保证完整文件，不能把前面的基线比较变成 compare-and-swap。计划只验收“已经过期的基线”，没有同基线并发保存、读内容与元数据来自同一版本的场景，也没有删除／换类型后使用旧基线的结算规则。
- **为什么是问题**：t68 的核心承诺是过期基线不覆盖；两个经本服务的写入都成功将静默丢失其中一份正文，t71 无法靠文档模型修复服务端已经宣称成功的保存。项目支持多个窗口和多个服务端进程，不走锁的外部编辑器是另一种明确限制，不能用它解释本服务自身的可避免竞争。这里是按计划算法的推断，尚无 t68 产品实现可运行。
- **依据**：`docs/specs/workspace/files.md:33–37,45,78–80,101` 要求并发不绕过版本保护；`docs/specs/runtime/plugin-channel.md:152` 明确同一方法的并发调用各自执行；`docs/specs/runtime/projects.md:74` 多窗口共享项目代次；`docs/specs/storage/persistence.md:170` 把两进程同 revision 保存仅一条成功列为验收（本轮未运行该测试）。现有 `settings/backend/layer-file.ts:4–13,98–127,172–181` 明确支持两个服务端同时打开同一项目，在从重读到提交之间持写入锁、复核身份，并单独注明外部编辑器的残留竞态；这是可参照的现有约定。
- **建议改法**：把“读当前字节／算基线 → 比较 → 替换 → 确认此次提交基线”定义为一个受控提交，按解析后的真实目标串行，跨服务端采用项目现有协作锁策略，直接在 rooted 保存原语持有，不新建协调服务。改名前重核对目标类型、身份与基线，检测变化返回冲突／身份改变；读取通过同一文件句柄取得内容及匹配元数据。验收两窗口和两进程同基线保存恰好一条成功，另一条冲突；明确外部编辑器不参与锁时的可检测与不可消除边界。

### 2. 重要｜不变量：控制目录保护没有落到真实路径，根内链接别名仍能绕到 `.nbook/`

- **计划位置**：“关键设计 / 3. 受根约束的文件原语”“验收映射”；`plan.md:43–44,91,109`。
- **现象**：计划对符号链接只检查解析后是否在方案根内，控制目录则写成隐藏并拒绝 `.nbook/`。例如项目内 `alias -> .nbook`，请求 `project://alias/settings.json` 的真实目标仍在项目根内，不能被根外链接校验拒绝。计划没有要求对解析后的地址再做控制目录判定，也没有大小写不敏感文件系统上的 `.NBOOK` 别名规则；验收只列 `.nbook/` 字面地址与根外链接。
- **为什么是问题**：项目身份、配置与 Storage 的独占边界会依赖每个调用点自行补判断；自动读取 `content.xml` 等服务内部读操作也必须经过同一个边界。只隐藏目录行不能防止显式地址或链接别名访问。Windows／默认大小写不敏感卷上，仅比较字面小写目录名同样不足。此处是计划的设计与验收缺口；代码尚未实现，绕过结果属于按所写算法的推断。
- **依据**：`docs/specs/workspace/files.md:35,74,78–79` 保留服务端路径、权限与控制数据保护；`docs/specs/storage/persistence.md:133`、`docs/specs/settings/configuration.md:30` 和 `docs/specs/runtime/projects.md:47` 给出 `.nbook/` 的三个真实落点。旧应用 `workspace-storage-boundary.ts:56–88` 对词法和真实相对路径分别做保护，解析失败上抛；`workspace-storage-boundary.test.ts:120–155` 已有 Windows 大小写与根内 Storage 链接别名用例。旧证据只作设计参照，本轮未重跑旧应用测试。
- **建议改法**：在唯一 rooted 原语里统一执行“词法路径与解析后真实路径均不得进入项目根的控制目录”，使用根的路径比较语义，不把保护散落到读、写、列出和清单加载。补 `alias -> .nbook` 的读／列出／新建／替换拒绝、失效链接失败关闭，以及大小写别名验收；嵌套普通 `notes/.nbook/` 与 `user://.nbook/` 按本方案明确的范围处理。

### 7. 重要｜不变量：改成临时文件 rename 保存后，未规定只读位、权限和目标链接的保存语义

- **计划位置**：“关键设计 / 3. 受根约束的文件原语”“4. 读、列出与三类文件夹”“验收映射”；`plan.md:43–45,56,109`。
- **现象**：计划以同目录临时文件 rename 替换现有文件，只写了根包含性和内容基线。POSIX 上 rename 受父目录权限控制：父目录可写时，即使目标文件只有 `0444`，仍可以用可写临时文件替换。临时文件没有约定沿用原文件 mode；目标本身是根内文件链接时，也没明确 rename 落到链接地址还是 realpath 后的目标地址。
- **为什么是问题**：原先不可写的用户文件可能被普通保存改写，原有执行位／共享读取权限可能被重置，链接可能被换成普通文件而真实目标不变。路径“在根内”不能证明该写入被允许。t71 只读反馈与同一文档身份依赖服务语义，此处不能留给编辑器补救。这是计划缺少关键替换语义；具体 t68 结果尚未实现，属于推断。
- **依据**：`docs/specs/workspace/files.md:35,78–79,103` 要求只读／权限不足在服务端拒绝；`docs/specs/platform/files.md:36,86–89` 要求目标身份／类型变化拒绝。旧 `workspace-files.ts:401–409` 原地 `writeFile` 的权限检查由 OS 完成，迁成 rename 后不能再依赖该行为。新应用现有 `settings/backend/layer-file.ts:12–13,38–51,156–181` 专门先核对目标可写、临时文件沿用权限位、解析并替换链接最终目标；`settings/configuration.md:125` 已固定相同边界。
- **建议改法**：rooted 替换明确先核对目标可写与类型、临时文件保留目标权限、替换解析后目标且保留原链接；悬空链接拒绝或显式另定语义，不能误当不存在的新文件。与发现 5 的提交边界共用一处实现。验收 `0444` 文件原字节不变、`0755` 文件保存后仍有执行位、根内文件链接保存更新目标且链接保留、目标换类型时失败。

### 11. 重要｜不变量：地址校验未保留 Windows 盘符与备用数据流的拒绝集合

- **计划位置**：“关键设计 / 2. 资源地址”“3. 受根约束的文件原语”“切片 S1”；`plan.md:36,41–43,91`。
- **现象**：计划列出空段、点段、反斜杠和 NUL 的限制，没有拒绝盘符、盘符相对路径和 Windows 地址段中的 `:`。`project://notes.md:hidden` 不含上述禁用项，在 Windows 上可指向 `notes.md` 的备用数据流；rooted 的根内检查也不会把它变成根外路径。`project://C:notes.md` 则包含另一种不应当作普通相对文件名处理的寻址形式。
- **为什么是问题**：备用数据流无法作为普通目录项列出，却可能经显式地址读写，同一套地址／基线／事件规则因此不能描述实际资源；它还可能绕开按普通文件名实施的控制文件规则。这不是要求原样接收旧路径拼写，而是保留旧实现对特殊 Windows 寻址的拒绝。Windows 实际读写本轮未验证；此项是计划拒绝集合与旧合同的可核对缺口，不宣称已复现根外访问。
- **依据**：旧 `platform-files/paths.ts:53–79` 明确拒绝盘符和 Windows `:`（注释明确包含数据流）；`docs/specs/platform/files.md:44,98` 要求相对地址、拒绝绝对／UNC 并保持既有拒绝集合等价或更严格。资源地址合同 `workspace/resources.md:20` 定义路径相对方案根，计划的 S1 没有特殊 Windows 地址验收。
- **建议改法**：共享地址格式先拒绝盘符与绝对地址；服务端按宿主文件系统规则拒绝 Windows 数据流、UNC 和设备命名空间，并复用同一包含检查。不要全平台小写路径或用 URI authority 解析把第一段改成主机名。S1 补 `C:notes.md`、`C:/notes.md`、`notes.md:hidden` 的拒绝用例，Windows 用真实临时文件核对无备用流产生；Linux 上合法含冒号的文件名是否保留明确写入地址策略。

### 4. 重要｜接口与合同：项目合同仅允许浏览器／TUI，计划自己的系统来源与下一位插件消费者不可达

- **计划位置**：“关键设计 / 1. 插件与位置”“5. 来源与变更事件”“验收映射”；`plan.md:28,61,102`。
- **现象**：`nbook.files/project` 的 `callers` 只写 `browser`、`tui`，同时承诺服务端／项目实例插件写入会产生 `{kind: "system", plugin}`。当前运行时同实例调用同样校验 `callers`；项目插件也不能借这份合同写文件或订阅事件。
- **为什么是问题**：resources 验收 2 的“系统写入来源正确”在项目方案上无法成立；t68 承诺的基础层缺少合法插件消费入口。以后 History、剧情以及服务端 nb-harness 必须改变公开合同或另建一条本地权威路径，违背本片先固定底座接口的目的。推迟 Agent 会话来源合理，拒绝所有服务端与项目插件不是实现该推迟的必要条件。
- **依据**：`docs/specs/workspace/resources.md:26–28,64–65,102` 把插件与系统写入列为消费者与验收；`docs/proposals/project-file-foundation.md:38,143–149` 让 History 独立订阅底座；`docs/proposals/multi-instance-runtime-topology.md:245,274–278` 明确项目文件写入经项目实例、History 在项目实例订阅。`docs/specs/runtime/plugin-channel.md:71,81` 与 `packages/nb-runtime/src/remote/node.ts:780–782,858–860` 表明同实例／远程都核对 `callers`。
- **建议改法**：同一份项目合同允许 `project` 与 `server` 调用，不另加转发服务；服务端访问指定项目仍由已有路由的项目租约与访问检查保护。验收通过真实内核让项目插件本地写入、服务端插件定址调用，并让订阅方得到正确系统来源；另确认另一个项目不能越权调用。

### 12. 重要｜正确性：仅看事件后的 `lstat` 无法区分新建和修改，监视分类缺少前态

- **计划位置**：“关键设计 / 5. 来源与变更事件”“切片 S3”“验收映射”；`plan.md:62–64,93,103`。
- **现象**：计划规定每批对路径 `lstat` 一次就定出 `created`、`changed`、`deleted`。本轮真实 Bun 递归 `fs.watch` 实验中，临时文件 rename 为一个原先不存在的 `entry.md`，和临时文件 rename 替换已有 `entry.md`，目标路径都给出 `rename`，之后 `lstat` 都是存在的普通文件、内容都是 `new`。事件和后态相同，正确分类却不同。
- **为什么是问题**：临时文件替换是普通编辑器保存方式，不能一律把存在的 `rename` 当新建；反过来一律当修改又会错报真实新增。外部删除后同路径重建、短暂文件创建后删除的批合并也需要前态才能解释。目录事件丢失后不能凭一次 `lstat` 推断遗漏的全部子项。事件虽不承诺逐条可靠，已发布的确定类别仍要有依据，不能靠事件名猜。未来 t68 未实现，此项核实的是计划算法信息不足。
- **依据**：`workspace/resources.md:65,105` 要求新建／修改／删除以及外部改名的删除加新建；`workspace/files.md:50,82` 要求消费者协调与恢复。`docs/research/vscode/16-file-service-explorer-editor-latency.md:55–59` 的合并规则建立在已经分类的事件上，不是由 Node 的 `rename` 名字得到。下方实验 C 使用真实 `node:fs.watch`、真实文件写入和 rename，两个场景输出完全相同。
- **建议改法**：明确前态由已列目录快照或监视器的目录项状态提供；有可核对前态时差分，只检查受影响目录，不读正文。不知道前态、事件没有文件名或目录变化无法准确枚举时发 `resync`／目录失效，让消费者重列，不伪造 `created`。先注册监视再确认 `ready`，补原先存在／不存在目标的替换保存、外部改名、目录移动和删后重建；不要为分类重新引入全树正文预读。

### 13. 重要｜正确性与恢复：清单缓存只按 `mtimeMs + size`，失同步后的“重列”可能仍返回旧投影

- **计划位置**：“关键设计 / 4. 读、列出与三类文件夹”“5. 来源与变更事件”“不做与风险”；`plan.md:51,62–64,122`。
- **现象**：清单以 `mtimeMs + size` 为缓存键，变更事件触发失效；监视只在有订阅时存在。先列过一个内容目录，最后订阅释放后外部程序换成同长、保留时间戳的清单，再列出时缓存键仍相同且期间没有事件。本轮真实文件实验得到键完全相同、缓存标题 A 与磁盘标题 B 不同。计划没有规定无监视时停用缓存、再次订阅或监视 `resync` 时清空缓存。
- **为什么是问题**：断线后重列、视图重新打开或焦点恢复都不能保证新状态：服务会把旧清单再次投影给消费者。清单修好后恢复、展示名和整棵清单的子树顺序也可能继续错误。事件不逐条可靠的取舍要求有可信重读路径，不能用同一个弱缓存键作为最终恢复依据。这是计划遗漏失效条件；未来 Files 缓存未实现，实验仅核实缓存键不能证明内容未变。
- **依据**：`workspace/folder-kinds.md:84,95,112` 要求外部修改重读与非法清单修复后恢复；`workspace/resources.md:65,90`、`workspace/files.md:82` 要求失同步后核对当前状态。下方实验 C 实际修改清单后以 `utimes` 保留 mtime，`size` 同为 45、`mtimeMs` 同为 `1767268800000`，无需同毫秒竞争即可产生碰撞。
- **建议改法**：把清单缓存有效性绑定到真实监视的连续有效期；没有监视时不保留跨请求缓存，最后订阅结束、监视出错、首次／重新订阅前清掉对应缓存；恢复重列强制重读清单而不只查旧键。清单事件要失效该内容根的整棵投影。保留正常展开期读一次清单的优化，不另建持久索引；补无订阅期间保留时间戳替换、监视失同步后清单修复、已展开深层目录标题刷新。

### 6. 重要｜接口与合同：列出结果不足以让 t70 判定内容节点与无正文节点

- **计划位置**：“第 6 步分解”“关键设计 / 4. 读、列出与三类文件夹”；`plan.md:17,49–54,106`。
- **现象**：目录项只含名字、真实类型、按自身后缀算出的 `folder`，再可选清单标题／图标。对 `lorebook.content/chen-yao/` 这种普通后缀的内容节点，父目录结果没有正文入口是否存在的信息；`list` 的结果本身也没约定当前目录所属内容根、清单是否合法后的有效模式。两个除了一个有 `index.md`、另一个没有外完全相同的子目录，父层列出合同给出相同的节点形状。
- **为什么是问题**：Spec 要求节点行在点击前就区分“打开正文”与“只选择／创建内容”，不能先读正文失败再猜；任意深度子目录直接列出、外部删除／新建 `index.md`、清单损坏后退回普通模式也要能正确协调。如果把这些都留给视图，只能为了给父层每行分类而列出每个子目录，或在浏览器复写清单／内容祖先规则；这会削弱按需读取并在 t70 返工服务合同。
- **依据**：`docs/specs/workspace/folder-kinds.md:21,64–66,95,115` 定义子目录正文、缺失与非法清单回退；`docs/specs/workbench/files-explorer.md:43–47,59,97–98` 定义有／无正文节点不同交互，`53` 要求展开时才列该目录。旧应用 `workspace-files.ts:36–55` 明确返回 `hasIndex`／`contentNode`，`workspace-file-tree.ts:93–115` 据实际 `index.md` 构造投影；不要照搬其全树扫描，但要保留供交互判定的事实。新应用尚无该合同（已按 `hasIndex`、`content.xml`、`folder-kinds`、`ContentNode` 搜索）。
- **建议改法**：t68 先写清目录自身的有效类型／清单状态，以及子目录正文入口存在性由哪一层、何时获取；保持原始文件名与地址。可只在列出内容文件夹时对每个直接子目录做 `index.md` 存在性／普通文件类型检查，不读正文、不递归列子目录，返回可选正文入口；普通目录继续一次 readdir。若选择更懒的探测，应显式定义“未知”状态与首次交互，且不能改变已确认的无正文节点行为。补深层节点、缺失正文、外部新增删除正文、非法清单回退的服务验收。

### 8. 重要｜合同覆盖：`baseline: null` 已经在 t68 新建文件，却把必须同步的清单维护全部推到 t69

- **计划位置**：“第 6 步分解”“关键设计 / 4. 读、列出与三类文件夹”“Spec 与文档改动”；`plan.md:15–16,45,56,83`。
- **现象**：t68 的 `write(..., baseline: null)` 排他创建文件，成功后只改该文件内容；t69 才负责“内容文件夹内的操作同步清单”。因此通过 t68 文件服务创建 `project://lorebook.content/new.md` 后，文件成功出现但 `content.xml` 不增条目，会被当成“未列入项”。
- **为什么是问题**：未列入规则是给 bash／文件管理器等外部改动兜底，不能替代服务自己的新建合同。计划一边宣称新建文件归 t69，一边在 t68 发布等价新建路径；t69 后来只给 `create` 加清单维护也堵不住这条 `write(null)`。目录祖先中的子项一样受整棵清单管理，不能只看当前目录自身有没有 `.content` 后缀。
- **依据**：`docs/specs/workspace/folder-kinds.md:70–71,82,97` 要求经文件服务新建在同一操作更新清单、文件成功而清单失败报部分完成；外部改动才不更新。`docs/specs/workspace/files.md:70` 同样要求这些显式操作同步清单。t68 的计划没有部分完成或清单失败结果，也没有这一路径的验收。
- **建议改法**：最少范围的改法是 t68 的 `write` 只接受已有文件的非空基线，排他创建连同清单维护在 t69 通过唯一 `create` 入口实现；已有 `content.xml` 的文本编辑仍走普通条件保存。若必须保留 `write(null)`，就在 t68 接入同一套创建与清单维护，并把部分完成结果和清单事件纳入合同，不能保持两条创建路径。

### 9. 重要｜接口与恢复：文件客户端的 `watch` 无法报告建立失败和订阅结束，重连核对也未接线

- **计划位置**：“关键设计 / 5. 来源与变更事件”“6. 浏览器文件客户端”“验收映射”；`plan.md:64,69–70,108,115`。
- **现象**：公开门面只有 `watch(scheme, onEvent) → 释放函数`，事件只含 `ready`、`batch`、`resync`；`resync` 的唯一触发写成文件监视器错误。合同未定义订阅建立被拒／提供者停止时如何告诉消费者，也没把远程层的 `onResync`、`onEnd` 接到共享的使用方。
- **为什么是问题**：读取仍可能成功，但变更订阅早已失败或结束；树与打开文档会持续使用旧状态却无法显示失同步。连接恢复时断线期间的事件不补发，收到新的 `ready` 不等于已核对当前目录和正文。项目结束由内核丢弃迟到事件，只保证不投错目标，不会替 Files 门面通知其本地监听者。t70／t71 无法从只有释放函数的 API 区分“已订阅”和“订阅不可用”。此处是计划合同缺口，未来客户端行为未验证。
- **依据**：`docs/specs/workspace/files.md:82,102` 与 `workspace/resources.md:65,76,90` 要求失同步可观察、恢复后核对；`runtime/plugin-channel.md:95,146,192,195` 规定建立失败不自动重建、同代次重连以 `onResync` 要求重取基线、终态以结束通知结算。真实实现 `remote/contract.ts:191–195` 提供两回调，`remote/node.ts:991–1000,1070–1085` 执行结束／重建通知；现有 `settings/shared/remote-link.ts:18–30` 区分可重试和终态，`settings/configuration.md:128` 定义建立失败恢复。
- **建议改法**：让每个本地使用方观察建立中、可用、失同步／结束及原因；远程 `onResync` 转为重新核对信号，`onEnd` 与建立失败广播给共享订阅的所有监听者。仍由一个方案一条订阅持有网络句柄，最后使用方释放时撤回，已释放者不再收到回调。补建立时断线、提供者停止、同代次重连期间外部改文件、一个使用方释放而另一个继续四种场景；不要把网络重放责任另建到视图。

### 10. 重要｜范围与决策：第 6 步移除了已接受的 History 验证，并另做 rooted 基础而未说明平台合同取舍

- **计划位置**：“第 6 步分解”“关键设计 / 3. 受根约束的文件原语”“Spec 与文档改动”；`plan.md:15–21,39–45,81–84`。
- **现象**：t68–t72 的范围里没有 History；第 21 行明确把它排除整个第 6 步。文件原语则放在 `nbook.files/backend/rooted.ts`，没有 `nbook.platform-files` 进入产品清单的安排。计划称推迟项会记入待确认清单，但固定审查基线的清单到末行仅有 t67，未登记这些 t68 偏离。
- **为什么是问题**：History 是已接受成功标准中的第一个独立事件消费者，并已决定默认启用、失败不影响文件功能；完全移出后，Files 完成只能证明浏览器自己刷新，无法证明底座事件能被另一插件独立消费。平台基础从独立授予／句柄 owner 换成 Files 私有原语可以另作合理取舍，但会影响受根约束权限与寿命合同，不能把未说明的替代当作原方案已经落实。这里要求补范围决策和验收，不要求 t68 一次搬入旧平台实现。
- **依据**：`docs/proposals/project-file-foundation.md:38,50,72,149,175,228` 明确 History、本次范围及平台基础；`docs/specs/workspace/resources.md:83,94` 仍保留它们；`docs/specs/platform/files.md:33–47,56–59,65–72` 规定授予、在途资源与收口。较新的 `neuro-book-v2-rebuild.md:129,139–140` 允许后端按 Spec 重写，并未撤销这些产品标准。`pending-confirmations.md:3,5–32` 是本轮已读取的现有登记；`autonomous-delivery/SKILL.md:36–40,50` 区分推进顺序内调整与放弃已接受范围。
- **建议改法**：在第 6 步保留一个明确的 History 接入／失败不影响 Files 的验收切片，或把“本轮缩小已接受成功标准”作为开发者决定项登记、说明后续承接与漏记边界。对平台基础选一个方案：沿独立平台合同提供本片需要的最小能力，或显式修订 accepted 决策与 resources/platform Spec，让 rooted 成为唯一基础并保留权限、作用域、取消与关闭不变量；不要并存两套根访问权威。提供者开放接口与虚拟方案可随真实插件消费者延期，Agent 的额外方案可随 nb-harness 接入，均要保留承接项而非标成完整 resources 已完成。

### 14. 建议｜文档与产品取舍：普通目录有两套不同排序，计划声称的旧行为也与新 Collator 不同

- **计划位置**：“关键设计 / 4. 读、列出与三类文件夹”“Spec 与文档改动”；`plan.md:50,53,82`。
- **现象**：第 50 行写 Unicode 码位排序，第 53 行写中文自然排序 `Intl.Collator("zh-CN", {numeric: true, sensitivity: "base"})`。同一组名字在码位顺序里 `chapter10.md` 在 `chapter2.md` 前，自然排序反过来；旧树的 `localeCompare("zh-Hans-CN")` 又把 `a.md` 放在 `A.md` 前，没有数字自然排序。
- **为什么是问题**：服务、视图和未列入项可能分别采用不同规则，排序会在刷新时改变；不能以“与旧树一致”解释这个明确的新产品选择。已接受决定只写“文件系统规则”，没有选定码位还是中文自然排序，采用自然排序本身没有违背 accepted 目标。
- **依据**：旧 `workspace-file-tree.ts:558–568`、`workspace-files.ts:1208` 是实际排序；`project-file-foundation.md:67`、`workspace/folder-kinds.md:20,63` 尚未规定具体比较器。实验 B 列出三种实际输出，不是凭 locale 名推断。
- **建议改法**：保留一条明确规则；建议沿计划第 53 行自然排序并保留原名兜底，只用于普通项和未列入项，清单顺序始终优先。将相对旧行为的变化登记为产品取舍。验收中文、数字、大小写及 Collator 相等的名字，不对每个目录另选比较器。

### 15. 建议｜接口与文本策略：`not-text`、BOM 与 hash 的字节含义未固定，默认解码不能证明安全往返

- **计划位置**：“关键设计 / 4. 读、列出与三类文件夹”“切片 S2”；`plan.md:55–57,92`。
- **现象**：计划以 UTF-8 解码失败判断 `not-text`，没有说明明显二进制内容、BOM 的处理或 hash 究竟针对原字节还是解码文本。真实实验中 `61 00 62` 可通过 fatal UTF-8 解码；带 BOM 的 6 字节 `EF BB BF 61 0D 0A` 默认解码后变成 3 字节 `61 0D 0A`，重编码 hash 不同。CRLF 本身未被解码改变。
- **为什么是问题**：只接受 UTF-8 是合理范围，但不等于拒绝二进制；未作修改的读取后保存也可能默默删掉 BOM。若基线算解码后文本的 hash，带／不带 BOM 的不同磁盘字节可能被当成同一基线。现有 Spec 尚未承诺 BOM 往返，不能宣称这是 t68 已产生的回归；这是应在资源合同先固定、避免编辑器另猜的策略缺口。
- **依据**：旧 `workspace-files.ts:220–275,391–395,2031–2056` 同时有 5 MiB 上限、二进制扩展、前 8000 字节 NUL 检查与 fatal UTF-8；旧测试 `workspace-files.test.ts:2462–2477` 覆盖二进制扩展、NUL、非法 UTF-8。本轮未重跑旧测试。旧解码同样吞 BOM，因此它不是应原样搬迁的正确性标准。实验 B 核实 Bun 文本转换结果；accepted 提案没有固定编码／BOM／8 MiB 数值。
- **建议改法**：基线 `hash` 明定对原始磁盘字节计算（128 位截断、32 个十六进制字符），大小按字节限制；采用 fatal 解码且保留 BOM，正文读写不主动归一化换行。`not-text` 至少明确 NUL 等明显二进制的处理；扩展名黑名单是否继续沿用单列取舍，避免误拒用户合法文本。验收 BOM＋CRLF、无 BOM＋LF、非法 UTF-8、含 NUL 和边界大小；永久测试只断言可观察字节与失败结果。

### 16. 建议｜测试：`chmod 000` 后列出成功不能证明没有正文读取

- **计划位置**：“切片 S2”“验收映射”；`plan.md:92,105`。
- **现象**：唯一“不读内容”的证明手段是把正文 `chmod 000` 后列出成功。实现即使逐个尝试 `readFile`，捕获权限失败后继续返回目录项，也能通过这个判据；它不覆盖其它可读正文被全量预读、空文件读取或失败的读取尝试。
- **为什么是问题**：按需读取是本次解决慢启动的核心合同，测试必须能拦住重新引入全量读取，而不只是保证不可读正文不会阻断浏览。权限用例仍有价值，只是不足以代表读次数为零。计划同时要求变异检查，插入一个读后降级的变异仍可通过现有判据。
- **依据**：`workspace/resources.md:107` 指定读取计数或文件访问记录核对。下方实验 D 在当前非 root 用户的真实目录中尝试读取 `000` 正文并继续列出，输出 `contentReadAttempts: 1`、`permissionFailures: 1`；`strace` 记录真实 `openat(...no-read.md, O_RDONLY...) = -1 EACCES`。这是验收判据的反例，不是未来 Files 实现缺陷。
- **建议改法**：保留权限场景，另用真实 OS 文件访问记录断言普通目录只开目录、不对任一正文发起读取；内容目录只允许清单读取。当前宿主已有 `strace`，可在隔离子进程记录目标路径的 `open/read`，不 mock 产品 FS。验收一次完整生成样本的根与深层目录，并用多一次可读正文读取的变异确认判据失败。
