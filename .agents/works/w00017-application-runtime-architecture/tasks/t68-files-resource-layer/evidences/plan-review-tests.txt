## R01：8 MiB 文本写入合同与真实 RPC 的 1 MiB 消息限制冲突

- **严重程度**：阻断。
- **类别**：接口与合同／测试。
- **计划位置**：“读、列出与三类文件夹”（第 55–56 行）、“浏览器文件客户端”（第 69 行）、“测试场地与样本”（第 74 行）、“验证”（第 115 行）。
- **现象**：文件读写以完整 `text` 经 RPC 传递，文本上限 8 MiB；现有服务端 RPC WebSocket 每条入站消息上限 1 MiB。计划的进程内链路只复用 JSON 编码，不执行消息大小限制。
- **为什么是问题**：一个符合文件合同的正文可以读取，却在保存时被传输层关闭连接，得到 `unknown-outcome`，而不是正常保存或明确的 `too-large`。限制还按 JSON 编码后的帧计：大量换行、引号、反斜杠会膨胀，即使文件不到 1 MiB 也会断线。正文样本只有 5–30 KB，原 e2e 仅探针握手，计划的验收全部可能通过而真实保存仍失败。
- **依据**：`docs/specs/runtime/plugin-channel.md:115` 明定单条消息 1 MiB；`src/shared/rpc-socket.ts:15–16` 明确大块内容经 HTTP，并定 `RPC_MAX_MESSAGE_BYTES=1024*1024`；`src/server/rpc/listener.ts:76` 实施该上限；`nb-runtime/src/remote/testing/in-process.ts:44–53` 编码投递而不限大小。真实实验 `rpc-boundary.ts` 注入测试提供者，经真实 `startServer`、内核、路由、生产 WebSocket 监听与真实磁盘运行：900 KiB ASCII 保存成功；1 MiB ASCII 编码为 1048883 字节后以 `unknown-outcome/disconnected` 失败、磁盘未变；600 KiB 换行编码为 1229107 字节同样失败；2 MiB 读取成功，进程内 2 MiB 保存也成功。命令与完整结果在 `rpc-boundary.output.txt`，退出码 0，服务端正常收口。未用 Chrome，实验没有伪造已实施的 Files 插件。
- **建议改法**：t68 的 S0 就定正文运输合同。少部件的做法是：若仍采用完整文本 RPC，把宿主消息上限与 Files 上限统一，并按最坏 JSON 转义膨胀（8 MiB 可达约 48 MiB，另有帧包络）设计明确拒绝；若沿现有大块内容合同，则用有时效 HTTP 资源地址传正文，RPC 只传地址与基线。两种选其一，不在 t70 才发现。S4 必加真实 WebSocket 的读→改→保存，覆盖帧包络、转义膨胀与上限两侧；进程内测试不能替代这条。

## R06：t68 的条件保存未定义互斥边界，两个相同基线的真实调用都能成功

- **严重程度**：重要。
- **类别**：不变量／可实现性／测试。
- **计划位置**：“第 6 步分解”t69 的排他提交（第 16 行）、“受根约束的文件原语”（第 45 行）、“读、列出与三类文件夹”（第 56 行）、“切片”S2 的基线冲突（第 92 行）。
- **现象**：条件保存只规定核对磁盘 hash 后替换，原语采用临时文件、fsync、rename。排他提交列在 t69，t68 没说明基线检查至提交是否串行、锁的资源身份、停止/失败时如何释放，也没列两个消费者从同一基线并发保存的判据。
- **为什么是问题**：rename 防止半截内容，但不会把“读旧 hash → 检查 → 写临时文件 → 替换”变成条件提交；内核不串行所有写方法，异步文件 IO 会交错。两个窗口可以都核对同一旧 hash、都返回成功，后提交的覆盖先提交的正文，绕过已有基线保护。这条是 t68 的保存不变量，不能等 t69 才补。外部程序不遵循锁的竞态是另一边界，不应借它省略 Files 自己可控的串行化。
- **依据**：`workspace/files.md:37,45,101` 要求并发不能绕过版本保护、冲突不得以覆盖替代；计划第 16、45、56、92 行没有互斥步骤。仓库外 `runtime-fs-proofs.ts` 将计划算法装为临时远程提供者，经真实 `startServer`、内核、生产 WebSocket listener、两个独立调用者和真实文件保存；无需暂停点或固定等待，两次都读到 hash `c516e69b05eff1a54017723c3489734b`，返回两次成功，磁盘只剩一份 65536 字节的正文。输出与 syscall 记录见 `runtime-fs-proofs.output.txt`、`runtime-fs-proofs.strace`，退出码 0，服务正常关闭。先前进程内同算法也观察到两次成功；这里已补真实宿主与运输。新 Files 尚未实施，结论是方案算法与验收缺口。
- **建议改法**：把每个真实资源的“重读/核对/提交/新基线确认”归同一个提供者内的互斥区，别让排他提交整体推迟；互斥键要对根内符号链接别名指向同一目标的情况给出规则，失败/取消释放、等待者按入口寿命结算。S2 用两个真实调用方从同一基线并发保存不同文本：恰好一个成功、另一个 conflict，磁盘等于成功提交；再验证失败后的下一次合法保存能完成，不需全局串行全部文件。跨不合作外部编辑器仅承诺提交前重验并如实写出剩余竞态，不宣称 rename 提供跨进程 CAS。

## R02：项目合同拒绝系统调用，验收映射却声称覆盖系统来源

- **严重程度**：重要。
- **类别**：接口与合同／测试。

- **为什么是问题**：内核对同实例与跨实例都核对合同 `callers`，项目内插件本地直用项目远程合同也会被拒；服务端插件写运行中的项目同样被拒。计划没有提供系统插件可用的替代入口。靠直接调用后端对象或伪造一个 consumer 测来源，不能证明合同可达，也绕过了“真实内核”的验收要求。
- **依据**：`docs/specs/runtime/plugin-channel.md:71,77–81` 说明本地也共用合同，服务端用 `{project: id}`；`packages/nb-runtime/src/remote/contract.ts:70–71` 的 `callers` 限制，`node.ts:548–549` 明确拒绝不允许的调用方种类。`runtime.projects:78–82` 已允许服务端插件访问运行中的项目；Files 的合同额外禁止了它们。`workspace.resources.md:102` 要求写作者与系统写同一项目的来源正确。真实 `world-lifetime.ts` 将同样的 `callers:["browser","tui"]` 装进项目内核：项目入口直用合同返回 `denied`，浏览器经路由成功，结果见 `lifecycle-watch.output.txt`。Files 尚未实施，服务端路径被拒是合同代码推断。

## R03：`chmod 000` 的成功列出不能证明没有内容读取

- **严重程度**：重要。
- **类别**：测试。
- **计划位置**：“切片”S2（第 92 行）、“验收映射”resources 验收 7（第 105 行）、“测试场地与样本”（第 75 行）。
- **现象**：计划把“对 `chmod 000` 的文件仍能成功列出”直接当作“列出不读内容”的证明。
- **为什么是问题**：在普通用户下，它至多证明列出不依赖读取成功；误加的 frontmatter 预读如果捕获 `EACCES` 后继续列出，同样通过。root、具有 DAC 绕过能力的进程或不按 POSIX 权限位授权的文件系统上，读取甚至可以成功。这个判据不能挡住本次要消除的全量预读回归。
- **依据**：`docs/specs/workspace/resources.md:107` 原判据要求读取计数或文件访问记录。现有 `settings/backend/layer-owner.test.ts:5` 也明确权限用例要求普通用户。初步 `fs-proofs.ts` 的脚本反例已补到真实运行时：`runtime-fs-proofs.ts` 把正常列出及“读失败后继续”的变异列出装为临时提供者，经真实 `startServer`、内核、生产 WebSocket 和磁盘调用；uid=1000、临时根为 tmpfs，两种都返回 `{ok:true,value:["ordinary.md"]}`，错误列出另记录真实 `EACCES`。`runtime-fs-proofs.strace:5823` 确认该正文的 `O_RDONLY` 打开被拒；输出与完整命令在 `runtime-fs-proofs.output.txt`，退出码 0，服务正常关闭。Files 尚未实施，这是验收判据的真实运行时反例；root、其它文件系统的行为是推断，未实测。
- **建议改法**：保留权限用例作为“不可读正文不妨碍列出”的独立行为；不把它当作性能证明。对装真实 `nbook.files` 的一次隔离列出，在 Linux 子进程上记录文件访问（例如 `strace -f -yy`，覆盖 open/read/pread/mmap），明确普通目录零正文访问、内容目录仅允许所属 `content.xml`。用一个“读失败也继续”的预读变异核对该证据会失败；无需给产品加读取计数、mock 或 spy。

## R04：监视只有事后 `lstat`，不足以区分新建与原子替换，验收还缺可等待的结束边界

- **严重程度**：重要。
- **类别**：可实现性／测试。
- **计划位置**：“来源与变更事件”（第 62–64 行）、“切片”S3（第 93 行）、“验收映射”files 验收 5（第 108 行）。
- **现象**：方案要求从 `fs.watch` 的 `rename/change`，合并后仅对涉及路径 `lstat` 一次，定出 `created/changed/deleted`；没说明订阅前已存在路径的状态来源。S3 要验证合并、回声去重、最后退订关闭和监视 error→resync，却没定义关闭完成、这一批处理完成或能稳定制造监视错误的场地。
- **为什么是问题**：新建与写临时文件后替换一个已有文件都可收到 `rename`，事后目标都是存在的普通文件，单凭当前 `lstat` 无法区分；新订阅时还没有任何目录列表可借。若补全根索引，会重新引入打开前扫描；若试图按等待 75 ms 断言“没有回声/没有后续事件/已经关闭”，又违反无固定等待。`watcher.emit("error")` 或耗尽整个宿主 inotify 配额也不符合本场地约束。当前验收映射把这些写成已可直接测的 S3 行为，实施者仍必须重新设计。
- **依据**：初步 `watch-observation.ts` 在真实 Linux/Bun 1.4.2 观察到新建、原子替换、外部改名与删除都使用 `rename`，之后新建子目录的事件可达。已补真实运行时：`runtime-watch-proof.ts` 在 `startServer` 的临时提供者内使用递归 `fs.watch`，原始事件经内核订阅与生产 WebSocket 抵达浏览器位置内核；等 ready 后做外部 IO，并等目标事件，新建 `fresh.md` 与替换订阅前存在的 `existing.md` 都得到目标 `rename`，事后 `lstat` 都是 size=3 的普通文件。输出与完整命令见 `runtime-watch-proof.output.txt`，退出码 0；停止订阅方后等到真实 watcher close，服务正常关闭。`lifecycle-watch.output.txt` 保留前一实验的删除、改名和新子目录结果。Files 尚未实施，这证明仅当前状态不足以分类，不声称新 Files 已有缺陷；合并、去重与 error/resync 路径尚未实施或实测。
- **建议改法**：若消费者只需按当前状态重列，最少部件是把外部事件收敛为“这些资源/父目录失效”，`created/changed/deleted` 精确类型只由服务自己的操作提供；这是对 `resources` 验收 5 的调整，须明确记录取舍。若保留现有精确事件合同，就明确最小状态来源、未知时 resync 的规则和成本，不能暗加整根预扫描。S3 先列等待协议：等 ready 后操作，正向事件按地址/来源等待；回声去重在后续外部事件对应的处理完成点核对该段事件；退订/停插件等真实关闭完成，再核对进程已无监视资源；error/resync 选一个可局部复现的真实失败，否则诚实标未验证，不用 mock 或系统级耗尽补“通过”。

## R07：样本只约束总数、深度和大小，不能保证覆盖 t72 的宽目录与可复现对比

- **严重程度**：建议。
- **类别**：测试／安全与性能。
- **计划位置**：“第 6 步分解”t72（第 19 行）、“测试场地与样本”（第 75 行）、“切片”S2/S4（第 92、94 行）、“不做与风险”（第 121 行）。
- **现象**：新 `scripts/files-sample.ts` 仅约定约 3000 个文件、3–5 层、5–30 KB 和一个内容清单。没有保证“单目录几百项”，没有种子、总字节数/布局/目标文件的稳定标识，也没定义同一脚本在 t68 无内容读取证据与 t72 性能测量之间怎样传样本。
- **为什么是问题**：同样的 3000 文件可以分在很多小目录里，全部满足生成条件却无法执行 `files-explorer` 验收 12 的宽目录场景。每次随机换布局/文件长度会把样本差异混入 p50/p95；手选文件又容易用热点或空白正文代替真实可编辑完成点。计划的监视事件量测量也没有场景，不应写成递归监视成本已覆盖。生成器不需要 t68 先写完整性能仪器，但最小样本合同必须现在稳定下来。
- **依据**：`workbench/files-explorer.md:77–85,147` 要求展开几百项并记录 p50/p95、请求数与模型/控件保留。旧 t42 的 `files-sample-generator.ts:34–38,123–130` 已采用 seed=42017、精确字节与 `notes/wide/` 400 项；t42 `evidences/delivery.md:59–65` 记录生成 3000 Markdown、总 52769090 字节、400 项宽目录、稳定正文 marker 与有效完成点。本计划没有这些保证，样本尚未实现，所以这是计划覆盖缺口，未声称新生成器已失败。
- **建议改法**：仍保留一个生成器，固定缺省 seed、精确 UTF-8 大小分布，并保证一个 400 项目录、普通正文与内容文件夹节点、缺失/未列入项；生成时输出机器可读样本描述（seed、count、totalBytes、wideDirectory、正文 marker 与供冷/热打开的地址）。S4 先用小样本验生成/读写，用正式 3000 样本一次取得文件访问证据；t72 复用同一参数与布局描述，补实际 UI 测量，不另生成第二套布局。报告声明 OS 缓存、构建、机器与首次/再次打开定义，避免拿 t42 旧数字当新验收。

## R09：普通排序两种描述冲突，新选项也不等于旧应用顺序

- **严重程度**：建议。
- **类别**：接口与合同／可实现性。
- **计划位置**：“读、列出与三类文件夹”（第 50、53 行）、“Spec 与文档改动”folder-kinds（第 82 行）。
- **现象**：第 50 行写 Unicode 码位、大小写不敏感；第 53 行写中文本地化自然排序、相等再按码位，并留“与旧应用一致性由实现时确认”。这两段只能以后者为主才不矛盾；旧代码本身也不采用这些选项。
- **为什么是问题**：同一目录可按两种不同规则列出，测试无法同时固定两者。自然排序是可接受的产品选择，但它会让 `chapter-2.md` 排到 `chapter-10.md` 前，且改变仅大小写不同的名称顺序；不应由实施者以“沿用旧顺序”名义悄悄决定。真正码位比较还不同于 JavaScript 的 UTF-16 字符串顺序，若合同真要求它，默认 `.sort()` 不能直接代替。
- **依据**：计划第 50、53 行；旧 `packages/neuro-book-legacy/app/components/novel-ide/workspace/workspace-file-tree.ts:558–563` 使用 `path.localeCompare(...,"zh-Hans-CN")`，没有 numeric/base。Bun 1.4.2 同一组 ASCII 文件名实测：旧规则为 `a.md,A.md,chapter-10.md,chapter-2.md`，计划选项为 `A.md,a.md,chapter-2.md,chapter-10.md`；命令与结果见 `sorting.output.txt`，退出码 0。`fs-proofs.ts` 的补充字符样本也证明 UTF-16 与 scalar 码位比较不同；未测其它运行时、平台或 ICU 版本，不声称跨平台顺序固定。
- **建议改法**：S0 只保留一个规范定义和两三组可见示例。若采用第 53 行自然排序，明确这是新规则，复用一个 Collator 实例与一个比较函数，码位只作为相等时的稳定次序；不要每次比较重新构造 Collator。若要保持旧顺序，直接沿旧选项并说明大小写规则。这个选择交开发者或已获自主决策授权的计划作者记录，不用新增排序抽象或依赖。
