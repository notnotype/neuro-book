### 1. [重要][不变量] 派发途中释放另一个本地订阅，它仍收到释放后的当前事件

- 位置：`packages/neuro-book/src/plugins/storage/server/partition.ts:276`、`:280`；停止监听在 `:174`；公开释放路线为 `shared/facade.ts:98` → `server/owner.ts:73`。
- 现象：同一真实消费插件建立两个本地订阅；第一位监听在收到新值时调用第二条公开订阅句柄的 `release()`。第二条已从监听集合删除，但仍收到此次值；之后的写入不再送达。本轮输出为 `seen: [missing, released-before-dispatch]`，应只有 missing。
- 为什么是问题：派发在回调前复制了全部 Watcher；释放只改原 Set，循环没有再次核对复制出来的条目是否仍有效。消费方可在一个状态变化中拆掉另一个观察者，释放返回后的迟到调用会进入已卸载投影；远程订阅合同明确丢弃释放后的迟到事件，本地路线也应遵守同一寿命。现有“停止后不再推送”测试只在两次写入之间停止，漏了通知回调里的停止。
- 如何核实：从 worktree 根运行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t55-impl/notification-release-probe.ts`。实验使用真 `createApplication`、真 Storage 插件、真 SQLite 和公开 `open/subscribe/save/release`，无私有函数、mock 或固定等待；两次保存成功，应用清理均为 closed。另一个“初快照里停止调用方”实验正常结束且只报一次 released，不列问题。
- 具体改法：保留遍历快照以免把途中新增监听纳入旧事件，但在每次调用前核对当前地址的 Set 仍含该 Watcher（同时覆盖 `close()` 清空集合）；或在 Watcher 上使用一个由 stop/close 置位的有效状态。不要只换成直接遍历 Set，新加监听的参与规则会一起变化。在现有真实内核订阅用例补“第一个监听释放第二个，第二个不收到本次及后续值”的行为断言。

### 2. [重要][不变量] 远程订阅在建立 Promise 返回前结束，门面仍把它登记为存活，随后重复调用 `onEnd`

- 位置：`packages/neuro-book/src/plugins/storage/shared/facade.ts:79`–`:93`、`:113`；远程路线的额外异步返回在 `shared/remote-route.ts:41`。
- 现象：真实浏览器消费插件订阅 user 记录，首快照监听中停止提供方应用。订阅先以 provider-stopped 结束；调用方稍后停止时同一订阅又收到 released。本轮输出 `ended: [provider-stopped, released]`，两端应用停止均为 closed。
- 为什么是问题：`onEnd` 可以先于 `await route.subscribe` 返回，此时 `entry` 仍为 null，无法从集合移除；返回成功后代码无条件建 entry 并加入集合，忘了这条订阅已经结束。随后服务对象释放直接调用另一份 `onEnd` 包装，违反 `storage/persistence.md:126`“订阅结束时调用一次”。“服务对象 released”与“这条订阅 ended”是不同事实；目前只有前者，entry／owned 两个别名和两份回调包装掩盖了缺失状态。常见终态原因与短时提供项停止都可能落入同一窗口。
- 如何核实：从 worktree 根运行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t55-impl/early-subscription-end-probe.ts`。只用真应用、真 Storage、真 SQLite、官方进程内链路与公开 subscribe/Application.stop；等待实际 onEnd 的 Promise，不造内部时序、不按时长等待。提供方结束时只有 provider-stopped；调用方随后停止新增 released。0.20 秒，finally 收口两端应用与路由。
- 具体改法：在调用路线前就创建一个订阅登记对象，由单个结束函数拥有“是否已结束”、从集合移除和 `onEnd` 的一次调用；路线返回后只补底层 release 句柄，若已结束就不登记为活订阅。主动 release 不发 onEnd，服务对象释放／提供方终态通过同一个结束函数。这样可合并 entry／owned 和两份 onEnd 包装，减少回调接线，并覆盖“结束先于建立返回”的真实运行时用例。不要仅按终止原因屏蔽第二次通知。

### 3. [建议][正确性] 上轮第 9 条仍有保存访问对象的缺口：旧签发身份已释放，却返回 `cancelled`

- 位置：`packages/nb-runtime/src/plugins/host.ts:579`–`:587`；已保存客户端的方法执行走 `remote/node.ts:439`–`:464`、`:477`。
- 现象：代理在身份有效时保存 `const access = context.remote.on(identity)` 和 `const client = access.use(contract)`。签发门面释放后，重新 on(identity) 为 denied；保存的 access 再 use 后调用、保存的 client 直接调用、保存的 access 建新订阅，均得到 cancelled。本轮 `beforeLate`／`afterLate` 都为 calls:2、sinks:1，没有派发新请求或订阅。
- 为什么是问题：修正把准入复查放在 on 的调用时，但其返回对象继续捕获旧 RemoteAccess，已保存的客户端又捕获同一 caller。底层已中止 signal 能阻止副作用，却把“签发身份失效”报告成普通取消，仍违反 `runtime/plugin-channel.md:85` 的统一 denied 合同。缓存访问／客户端是公开接口允许的正常用法；只复查 on 或 use 无法覆盖更早取得的 client。没有越权或旧门面复活，故保持建议，不采纳独立子审查的更高定级。
- 如何核实：从 worktree 根运行 `bun --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t55-impl/delegated-access-lifetime-probe.ts caller-only`。复用真应用、真代理门面、官方进程内链路与真实消费方激活代次停止；用公开实例查询做前序投递屏障。输出 heldAccessAfterRelease／heldClientAfterRelease 均为 cancelled/cause cancelled，heldSubscriptionAfterRelease 为 cancelled，remote.on 重取则 denied；停止 closed，0.19 秒。
- 具体改法：把委托身份准入核对保留到实际方法调用／事件订阅边界，同时仍复用底层访问的 contacted／owned 与 release 所有权；允许有效门面的释放函数完成后才判失效。可以由宿主交给 remote.access 一个动态准入回调，或由委托客户端包装在请求／订阅前统一核对；不要在 on、use、每个方法各复制一套规则。已有缓存与未缓存身份的用例增加“保存访问对象”和“保存 client”两种公开路径，断言 denied 且无远程副作用。

### 4. [建议][代码质量] 同一签发身份准入规则在 `issuedTo` 与 `#resolveFor` 分别实现

- 位置：`packages/nb-runtime/src/services/composition.ts:339`–`:350`、`:378`–`:387`。
- 现象：远程与本地委托分别执行同样三项核对：身份在 `#issued` 中、没有 closed、签发给当前插件／入口；三条拒绝文案也重复。两处当前规则一致，未发现本轮准入失效。
- 为什么是问题：这是同一装配拥有的信任与寿命规则。以后增加签发代次或作废条件时必须改两份分支，调用方还要自行维持本地／远程的等价性；原计划要求“核对与 resolveFor 相同”，目前靠复制实现，读者要逐项对照才知道是否相同。
- 如何核实：只读逐项比较以上两个分支、`runtime.services` 输出 13 与 `runtime/plugin-channel` 输出 10；内核 273 例及委托停止／旧身份公开实验通过。属于静态结构发现，不声称已有越权。
- 具体改法：在 composition 内用一个私有准入方法返回有效 `IssueRecord` 或拒绝原因，`issuedTo` 再交出 signal／attach，`#resolveFor` 再转换成现有 ResolveResult 失败形态。保持插件允许清单／合同或服务键声明分别由插件宿主拥有；只合并三项共同规则，删掉一套重复分支，不新增跨模块的“授权服务”或包装层。

### 5. [建议][代码质量] Storage 探针远程输出用 `Type.Unknown`，e2e 又手写一套弱结果类型

- 位置：`packages/neuro-book/src/shared/testing/remote-probe-contract.ts:67`、`:70`；`e2e/storage.e2e.ts:62`–`:69`、`:136`、`:145`。已有可复用合同在 `plugins/storage/shared/contracts.ts:21`、`:39`，探针命名类型在 `shared/testing/probe-storage.ts:21`–`:26`。
- 现象：新增 storageRead／storageSave 输入有 schema，输出却均为 Type.Unknown；浏览器已有 ProbeSnapshot／WriteResult，e2e 再声明 status:string 与多个可选字段的 Snapshot，并把 HTTP、项目输出断言成这个弱形状。`read` 的正常快照与 open 失败实际是不同联合分支，手写 Snapshot 连 status 都错误要求失败分支具有。
- 为什么是问题：三端数据路径已有同源记录，但结果合同到探针处丢失：输出不会被远程层检查，e2e 通过 cast 避开收窄，读者要从调用实现重新推断成功／失败形状。`echo`、tick 等既有探针有具体输出 schema；新增两方法形成第二套消费类型，增加维护点。现有 e2e 行为断言能抓住所用成功路径，未据此认定浏览器运行失败。
- 如何核实：只读对照探针接口、方法 output 与 e2e 的四处重声明／断言；两包类型检查成功，仅说明编译允许这些 cast，Chrome e2e 未运行。
- 具体改法：在共享探针合同复用 Storage 的快照／失败 schema，明确 read 为快照或 open 失败、save 为 WriteResult；探针模块命名导出这一联合结果，窗口 evaluate 与 HTTP 解码使用它并按 status／ok 收窄。删除 e2e 的 Snapshot 和匿名结果形状；结果值里的 text 可由同源 Text schema 描述。保留当前直接 Storage 与经项目 RPC 的两种观察入口，减少重复模型而不是另造探针协议层。

### 6. [重要][测试] `storage.test.ts` 的 `world()` 不收口应用与路由，测试结束仍有 19 个 SQLite 文件描述符打开

- 位置：`packages/neuro-book/src/plugins/storage/storage.test.ts:94`–`:177` 的 `world()`；返回的 `hub`、项目／窗口 `Application` 与 `RemoteRouter` 没有统一 owner，清理钩子只在 `afterAll` 删除临时根（`:46`–`:47`）。

- 为什么是问题：`world()` 每个用例创建至少一个 hub，很多用例再创建项目和多个窗口，但没有 `afterEach` 逆序停止它们；SQLite 连接拥有文件描述符和 WAL 资源，删除路径不等于关闭资源。从代码推断，未停止的实例与路由也把连接、订阅和生命周期回调留到运行器退出或垃圾回收，关闭的异常无法在当前用例被检查。各用例的数据根独立，未发现跨用例数据串扰；已核实的问题是测试没有确定性收口，而非产品存储泄漏。
- 如何核实：从 worktree 根执行 `bun test --tsconfig-override packages/neuro-book/tsconfig.json /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/omp-t55-impl/world-resources.probe.test.ts`。探针只导入该真实测试文件，在其 afterAll 后扫描 `/proc/self/fd`；15 pass、0 fail，19 个 Storage 文件描述符均标为 deleted。没有 mock、固定等待或产品内部直调。

- 按只读约束未运行 e2e、开发服务、构建或机检／格式化；未验证 Chrome 的新增三端交叉观察场景、Windows、macOS、TUI 与 K5。三端探针“已修好”限定为接线与合同使用的静态核对、两包类型检查；实际浏览器验收仍由主 Agent 执行。
- 本轮 smoke 使用真实应用、插件、SQLite 与官方 JSON 进程内链路，不能替代 WebSocket／项目 IPC 的全部实际调度。宿主 46 例覆盖真实服务器／项目宿主；第一轮的 `storage-host-probe.ts` 未重跑，不作为本轮新证据。
- `KernelQualityRoundTwo` 与 `ProbeTestQualityRoundTwo` 只读独立审查，未跑验证。前者的保存委托访问疑点经本轮真应用复现后合并到发现 3；后者的 world 收口与探针输出合同分别合并到发现 6、5。独立审查提出的更高定级不直接采用：保存访问没有新远程副作用，探针弱输出模型尚无运行失败证据，分别定为建议；测试残留 19 个文件描述符有实测，定为重要。

## 未发现问题的方面

- **已验证：** 基本读取分类、默认值不落盘、CAS、删除标记防旧写、坏数据／旧版本原件保存、64 份上限、定义冲突、插件／客户端隔离、服务端与项目分区，均由本轮 Storage 合同测试通过；跨进程争写与锁忙用真实 SQLite 和 Bun 子进程核对。公开实验另证坏库／外来库在 open 拒绝、外来库字节不变。
- **已验证：** 重入写入通知不倒序；途中开始的新监听不会被旧 revision 覆盖；转发项目的初快照不丢；同服务端进程重连补最新快照而不误结束。两项新订阅边界见发现 1、2，不把正常场景扩展为所有重入／终止路径安全。
- **已验证：** 整应用与单消费方停止时，代理门面 release 内委托调用仍成功，之后签发记录收口、远程门面释放、订阅中止；异常 onEnd 不妨碍其它订阅结束，失败仍报告 release-failed，recover 可完成。旧身份重新 on 得 denied；保存访问对象的残留错误码见发现 3。
- **从代码核对：** 分区先认库，只有无表的新库才在写锁内重认并建表；事务拥有 CAS 比较与写入，通知在提交后排队。`Watcher.last` 使用分区自己拥有的整数表示，公开调用方仍只回传 token，不与“不透明”冲突。`recognize`／`#transaction`／`#notify` 的职责有实际边界，没有为简化而合并它们的必要。
- **从代码核对：** `admit` 守远程输入与身份边界，门面核对给本地消费方及时反馈；本地路线与远程入口的部分相似检查不是无效重复。三端插件分别装配分区拥有者或代理，remote-route 做 Storage／RPC 结果转换；未发现需要再引入一个路由管理层的理由。facade 的简化应集中在每条订阅单一登记与终止函数（发现 2）。
- **从代码核对：** router 的 early 队列只处理接受前的事件／终止，接受后 FIFO 排出，未发现需要第二套通用队列的理由。每次 on 准入在 WeakMap 前，缓存只复用访问对象；签发记录／实际 release 拥有中止，未再次并入会提前触发的激活 stopSignal。相邻 K1–K3 未发现本轮新增破坏，不代表重新认证其全部旧实现。
- **从代码核对及既有测试：** partition 子进程对话用 ready／结果行作为因果屏障，失败清理由 afterEach 拥有；真实项目子进程也有收口。owner.test 在拥有者边界故意留下订阅来核对结束异常与关库，真实消费者先停的正常路径由应用级测试覆盖，这种分层测试有理由。storage.test 世界缺统一所有权是单列的重要问题（发现 6）。
- **本轮范围内未发现：** 按错误文案做产品分支、无诊断吞错、放宽断言隐藏失败、产品测试专用分支、跨包源码深导入，或为修正删改范围外源码／配置。三端 probe 共用记录定义，控制路由与项目 RPC 观察入口符合已有测试插件职责；结果合同与 e2e 第二套弱类型需按发现 5 统一。
