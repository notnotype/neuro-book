## D03 — 重要 — 不变量：按发起时成员数生成删除补丁，会在冲突重放中删掉仍有成员的自建容器

- **计划位置（节名）**：“关键设计 / 1. 自建容器与记录”“关键设计 / 2. 意图”“验收映射”（plan.md:16–17、22–27、85）。
- **现象**：计划规定自建容器只有同时存在记录项与实际成员才能成立，搬空时把删除和移动合成一个补丁；同时沿用 t66 的 `applyView`，接纳时合成补丁，保存冲突时只把同一补丁作用在最新值上。映射只列“身份复用、搬空清记录、刷新一致”，没有“另一窗口已经移入成员”的场景。
- **为什么是问题（推断）**：两个窗口共用记录，但订阅不强改本窗口显示。假设自建容器 C 只有 A：窗口一把 B 移入 C 并保存；窗口二仍看见 C 只含 A，把 A 移走，接纳时会冻结 `containers[C] = null`。冲突后把该补丁应用到最新值，会保留 B 的归属却删除 C 的身份记录，触发计划第 1 节“成员回默认”的规则，窗口一已接纳的 B 移动被无关操作推翻。反向场景也有缺口：两窗口分别搬走 C 的最后两个成员，各自接纳时都不空，重放后 C 真空却无人清记录。问题来自把按最终成员决定的清理当成无条件字段写入。
- **依据**：`docs/specs/ui/workbench-shell.md:156–162、169`（只重放主动字段、别的窗口其它字段保留、实际搬空时清记录）；`packages/neuro-book/src/plugins/workbench/web/state/layout-store.ts:178–182`；`packages/neuro-book/src/plugins/workbench/web/views/intents.ts:163–196`（`applyPatch` 对容器 null 无条件删除）；`packages/neuro-book-legacy/app/utils/workbench/view-placements.ts:1346–1379`（在候选表的最终成员上只清本次涉及的空自建容器）。
- **核实方式**：代码与合同逐行对照。两窗口时序是按真实 store 订阅/重放合同推断的新设计后果；尚无 t67 代码可运行，不宣称已复现 t67 缺陷。
- **建议改法**：保持 t66“接纳时检查来源、已接纳主动字段后写胜出”，不搬旧 CAS 会话或第三方移动冲突规则。把清理改成同一次 `change(latest)` 的最后一步：先应用本次归属/顺序/尺寸字段，再按最新候选记录计算本次涉及自建容器的实际成员；涉及集合包括发起时来源、目标，以及最新记录中被主动改归属视图的原容器。有成员保留身份，真空才清对应容器项与失效选中项，未知项不做全局清扫。创建仍复用已生成的 id。S2 真实 Storage 增加上述两个双窗口场景，以及同一个视图先后移入/移出不同自建容器的重放场景。

## D04 — 重要 — 不变量：旧半区算法把整张呈现尺寸表写回，违反未命中成员意图不变

- **计划位置（节名）**：“Context / 已定的”“关键设计 / 2. 意图”“验收映射”（plan.md:7、24、27、82）。
- **现象**：计划把旧 `resolveSplitSizes` 列为迁移参照，只说明按固定半区公式生成尺寸意图；S1 与 S5 的尺寸验证只列无约束的两组等比数。旧函数输出全部目标可见叶的实测 px，`applyViewSizes` 把这一整张表写进当前轴；它没有区分命中叶与未命中叶，也没有保留收起叶的展开意图。
- **为什么是问题**：v2 的记录是尺寸意图，不是当前像素；当前像素可能因 min/max、窄盒或收起而夹取。Spec 输出 21 明确要求“其它目标成员的尺寸意图不变”。真实组件实验中，目标 A 保存 `height:1000`、声明 `maximumSize.height:100`，实际显示 100；把 E 并到 D 的半区，照旧算法写整张表后 A 的记录变为 100，B/C 原本未记录的尺寸也被写成 205.65625。A 没参与分屏，其恢复意图却被改写。推断：若 A 收成 32px，照旧函数还会把 32 写成展开尺寸；跨窗口重放时这类非主动字段同样会覆盖别的窗口的合法调整。仅通过四个 25% 的例子抓不到此问题。
- **依据**：`docs/specs/ui/workbench-shell.md:129、153、168`；`docs/specs/ui/nested-grid.md:65–67`；`packages/neuro-book-legacy/app/utils/workbench/view-placements.ts:928–989、1334–1343`；`packages/neuro-book/src/plugins/workbench/web/views/presentation.ts:38–41、105–108` 与 `packages/neuro-book/src/plugins/workbench/web/views/container-grid.ts:26–44、53–66`（意图、呈现与主动字段分离）。
- **核实方式**：本机 Chrome 的现有 `WorkbenchViewContainerHost`、真实 nb-ui Grid 与现有意图/补丁链路，目标盒 400×720；从真实 DOM 读四叶几何，再按旧函数的输出规则写入新应用现有尺寸意图入口。`browser-probe-result.json` 记录 A 的 `1000 → 100`、B/C 的 `缺省 → 205.65625`。实验没有 t67 的原子拖放实现，证明的是直接迁移该尺寸表不可行，不能宣称 t67 已有此 bug；其余潜在后果标为推断。
- **建议改法**：仍用已定半区公式，但在合成边界明确坐标与权重单位：来源实测几何只作相对比例，目标命中叶的份额转换到目标当前轴的意图单位后分半；补丁只含命中叶与拖入可见成员，未命中叶、收起叶的展开意图、另一轴与未知字段原样保留。同容器重排不产出任何尺寸字段。S1 增加未命中叶触界、未命中叶收起、目标尺寸从未保存三种记录级判据；S5 同时核对几何分配与未命中记录逐字段不变。

## D01 — 重要 — 正确性：新增“移动到”目标绕过现有命令合同

- **计划位置（节名）**：“关键设计 / 2. 意图”“关键设计 / 6. 命令”“Spec 与文档改动（S0）”（plan.md:29、51–60）。
- **现象**：新建容器菜单项直接走 `detach-view` / store `applyView`；计划明确保持 `move-view` 命令参数不变，并把是否经过命令留给审查者判断。S0 只列修改外壳 Spec，不列命令 Spec。
- **为什么是问题**：外壳二输出 24 已规定“移动到”经 `nbook.view.move-view` 执行；命令 Spec 又规定菜单等触发面共用具名动作和单一执行入口。同一菜单新增项直接写 store，会缺少原有命令可用性检查、结构化结果与单次审计；命令面板的第二步也无法选择新建容器，菜单和命令的目标集合开始分叉。这是当前合同的明确偏离，不是要求把拖动逐帧命令化。
- **依据**：`docs/specs/ui/workbench-shell.md:107`；`docs/specs/workbench/commands.md:14–16、24、66–77`；`packages/neuro-book/src/plugins/workbench/web/commands/view-commands.ts:25–35、65–99、104–115`（现有命令只接已有容器，第二步目标与菜单同源）；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.md:30、54`。
- **核实方式**：逐行读取计划、外壳输出 24、命令合同与现有处理函数；未运行新行为，代码尚未实现。
- **建议改法**：采用计划自己列出的较小改法：给现有 `move-view` 增加与 `targetContainerId` 互斥的 `newContainerIn` 目标，菜单和无参命令面板共用一份目标表；命令处理函数只把新目标翻成 `detach-view`，稳定 id 在这次动作接纳时生成一次。拖放仍直接提交结构化意图。S0 补命令 Spec，S3 增加命令面板新建、选择取消、来源过期零写入的验收。

## D02 — 重要 — 正确性：键盘拖放需要的新适配没有落到设计中，旧传感器与 Tabs 不能原样复用

- **计划位置（节名）**：“Context / 需要先定的一项”“关键设计 / 4. 拖动会话”“关键设计 / 5. 组件”“验收映射”（plan.md:8、41、47、86）。
- **现象**：计划把键盘按键合同列出来，并推荐沿用旧会话，但没有定义键盘传感器改配、目标区域遍历、拖动期间标签导航的处理。旧 `workbenchDropSensors()` 直接使用默认 `KeyboardSensor`；同版默认把 `Tab` 列在结束键里。计划同时要求新的标签带照搬 Tabs 的方向键自动激活，而活动内容变化又必须取消拖动。
- **为什么是问题**：照旧传感器接线时，Tab 会结束手势，无法切换目标区域；照搬 Tabs 的导航时，拖动中的方向键仍可能触发选择保存、切活动内容并取消手势。已有库只给坐标移动与生命周期，不能凭空提供 Spec 的区域遍历。新 ViewSection 的可聚焦节点目前是收起按钮，标题行本身不能聚焦；旧传感器默认又要求 `event.target` 就是 handle，所以拿起的焦点入口也必须明确。S5 “键盘各走一遍”需要以这些具体冲突为判据，否则容易只测空格和 Enter 的局部路径。
- **依据**：`docs/specs/ui/workbench-shell.md:131、223`；`packages/neuro-book-legacy/app/composables/useWorkbenchDrop.ts:962–970`；`packages/nb-ui/src/components/controls/Tabs.md:24–29` 与 `packages/nb-ui/src/components/controls/Tabs.vue:45–73`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchViewSection.vue:37–51`。发布版本原始类型与源码：<https://unpkg.com/@dnd-kit/dom@0.5.0/index.d.ts> 的 `KeyboardSensorOptions`；<https://unpkg.com/@dnd-kit/dom@0.5.0/index.js> 的 `defaults`、`handleKeyDown`、`handleMove`（默认 start 为 Space/Enter，end 为 Space/Enter/Tab，方向键只移动 10px，不负责区域遍历）。
- **核实方式**：锁定 `0.5.0` 发布源码并在本机 Chrome 运行 `DragDropProvider + KeyboardSensor + 当前 Tabs`，直接按 Space → ArrowRight → Tab。实测 ArrowRight 先产生 `{x:10,y:0}` 位移，再发出 `select(tab.b, duringDrag:true)`；Tab 发出 `end(canceled:false)`。数据在本目录 `browser-probe-result.json`，脚本 `run-browser-probe.mjs`，截图 `probe-before.png`、`probe-after.png`。这是推荐接线的真实浏览器组合实验；尚无 t67 实现，不能当作已复现的 t67 产品缺陷。
- **建议改法**：在同一个 `drag-session.ts` 内定义显式键盘适配：start 只取 Space、end 只取 Enter；Tab/Shift+Tab 按已登记且可见的目标区域循环，方向键只沿该目标轴更新坐标/插入位，然后调用同一纯判定。手势进行中阻断普通标签导航、收起 click 与选择保存，结束后恢复；为 multiple 标题与 Sidebar single 标题明确一个可聚焦 handle 和放下/取消后的焦点。S5 从 Sidebar、AuxiliaryBar、Panel 各拿起，Tab 跨区、方向换位、Enter 提交、Escape 取消，断言 Tab 后仍在拖动、过程中无布局 revision 增长。

## 拖动依赖与更小替代

保留 `@dnd-kit/vue` 推荐，待开发者追认；它已有旧应用集成经验，真实浏览器组合可运行。锁定依赖是 `0.5.0`、MIT、`sideEffects:false`，peer 为 Vue `^3.5.0`；`@dnd-kit/dom` 同为 `0.5.0`、MIT。依据为本 worktree 的 `node_modules/@dnd-kit/{vue,dom}/package.json` 与上述发布类型/源码。许可检查到包元数据为止，未做完整第三方许可审计。

| 选择 | 能减少什么 | 仍须负责的工作 | 判断 |
|---|---|---|---|
| `@dnd-kit/vue` + 集中的 `drag-session.ts` | 复用 Provider、Vue composables、拖影与传感器，避免重写会话资源管理 | 产品键盘区域导航、v2 结构失效、可见/遮挡命中、原子意图；D02 不能依靠默认行为 | 本任务推荐；业务判定保持纯函数，库只留在会话/组件边界 |
| 直接 `@dnd-kit/dom` | 少一个 Vue 适配包；公开 `DragDropManager`/`Draggable`/`Droppable` 已有同一传感器接口 | 手动把 Vue ref、挂载/卸载、登记反登记与自定义 overlay 接起来，仍依赖 abstract/collision/geometry/state 核心 | API 层面可行的较小依赖集合；未测实际构建节省，不能声称减少多少 B。不能省掉键盘产品适配 |
| 原生 Pointer Events + 项目键盘会话 | 不增加 dnd 第三方运行时，复用 nb-ui 几何与反馈 | 门槛、pointer capture/cancel、触摸、blur/visibility、焦点、登记、反馈、尾随 click 和释放一致性均须重做 | 名义第三方依赖更少，总代码/验证成本未证明更小；本任务不推荐替换已验证的会话基础 |
| 只用 nb-ui 现有 grid/drop 原语 | 没有新增拖动库 | 现有 `grid-drop.ts` 求插入与 `DropFeedbackOverlay` 渲染反馈，都不提供视图/容器的完整起拖会话 | 无法单独替代源、传感器和生命周期管理，适合继续作为几何/皮肤层 |
