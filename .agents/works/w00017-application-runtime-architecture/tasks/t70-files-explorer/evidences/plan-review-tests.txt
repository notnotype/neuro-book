# w00017 t70 实施计划审查：可实现性、切片与测试

审查对象：`.agents/works/w00017-application-runtime-architecture/tasks/t70-files-explorer/plan.md`。

审查范围：逐片自证入口、逐条验收映射、真实 DOM/内核环境、否定判据与时序屏障、减少部件的切分方式。仓库保持只读；实验只放在本报告所在目录。结论按影响排序；每条确认后追加记录。运行证据与未验证边界在报告末尾列出。

## 1. 阻断：S2/S4 把需要真实布局的判据交给 happy-dom，切片无法按计划自证

- **类别**：测试 / 切片可实现性。
- **计划位置**：`plan.md:89`、`plan.md:91`、`plan.md:101`、`plan.md:112`。
- **现象**：S2 要用 DOM 测试证明“虚拟列表只渲染视口”；S4 要用 DOM 测试证明指针拖动移入与行间排序；统一验证又把“真实指针事件序列”作为这些 DOM 测试的证据。
- **为什么是问题**：happy-dom 没有布局，无法给出真实视口、行矩形、滚动后的命中、浮层遮挡与指针捕获。派发 `PointerEvent` 能验证监听器分支，不能证明屏幕上的落点与最终写盘对应。到 S5 才跑浏览器，会让 S2/S4 带着未自证的主要行为提交，且与本包明确的测试分工冲突。
- **依据**：`packages/neuro-book/vitest.config.ts:1-4,19,23` 明确 DOM 环境为 happy-dom，尺寸、拖放、滚动走 Playwright；`packages/neuro-book/AGENTS.md:37` 同样规定；`WorkbenchShellLayout.dom.test.ts:1-4` 记录容器测得为 `0×0`，几何、拖动与真实宽度往返由 e2e 覆盖。`packages/nb-ui/docs/ui-development-spec.md:173-175` 要求真实 client 矩形、遮挡检查、静止指针时重算与释放时复核。
- **建议改法**：DOM 层保留点击、按键、ARIA 属性、内联输入、对话框内容与真实控制器/磁盘结果；把虚拟滚动与拖动几何放进各切片当期的 Playwright 验证，不等 S5。S2 浏览器用实际侧栏高度滚动并核对可见行、焦点行及 ARIA 目标；S4 浏览器用鼠标/笔/触摸门槛、行内移入与行间排序、滚动/刷新/遮挡后释放，断言反馈和实际磁盘/清单一致。纯落点解析器另用真实数值输入测边界，无须伪造 happy-dom 布局。

## 2. 阻断：真实 `filesScene` 不能直接进入 S2–S4 的 Node/Vitest，且现有场地未装 Storage

- **类别**：测试 / 依赖可实现性。
- **计划位置**：`plan.md:88-91`、`plan.md:101`、`plan.md:112`。
- **现象**：计划要求 DOM 测试挂真实控制器、内核窗口和磁盘，并经真实 Storage 验证恢复，却没有给出跨宿主测试场地。现有 `filesScene` 是同一 Bun 进程内装服务端、项目与窗口的场地。
- **为什么是问题**：Vue 的 DOM 测试实际由 Node/Vitest 运行，`filesScene` 导入文件后端后会加载 `bun:ffi`；S2 的真实 Storage 还会加载 `bun:sqlite`。这不是增加一条 mount 即可复用的设施。现有 `filesScene` 只装 Files 与 settings，没有 Storage，也没有工作台/命令/视图插件，默认客户端身份又随窗口 id 改变，不能直接证明同一 user/local 的重新加载恢复。
- **依据**：`files/testing/scene.ts:91-97`、`settings/testing/world.ts:91,137,151,172` 是现有装配；`files/backend/exclusive.ts:10` 导入 `bun:ffi`，`storage/backend/partition.ts:12` 导入 `bun:sqlite`；`package.json:13-16`、`docs/testing/README.md:116,119-122` 明确 Vue 测试用 Node，并要求宿主专有模块在真实宿主子进程验证。运行指定目录的 `probe.dom.test.ts`（只导入真实 `filesScene`）得到：`Error: Cannot bundle Node.js built-in "bun:ffi" imported from "packages/neuro-book/src/plugins/files/backend/exclusive.ts"`，退出码 1，`0 test`。
- **建议改法**：在 S1 就交付一份浏览器侧可复用的测试场地：后端/项目在 Bun 子进程运行，Node DOM 场地只装真实浏览器内核、Files 客户端、Storage 与控制器，经现有 JSON/RPC 链路连接；子进程提供明确 ready/停止通道，在 `afterEach` 失败时也释放。场地可注入同一 client id 和项目绑定，覆盖未绑定与恢复。更少部件的选择是 Bun 合同测试负责树/控制器与真实磁盘，DOM 只测受控零件，产品接线和 Storage 恢复统一放各片 Playwright；两种方案选一种并明确到切片与命令，不能继续写成未存在的“真实窗口 DOM 测试”。

## 3. 重要：只刷新事件的父目录会留下过期的嵌套清单与“无正文”节点

- **类别**：正确性 / 增量刷新。
- **计划位置**：`plan.md:30`、`plan.md:33`、`plan.md:54`、`plan.md:88`。
- **现象**：设计只按事件路径的父目录（改名取新旧父目录）标脏已加载目录。`content.xml` 属于整个内容树，不只属于它自己的父目录；子节点有没有 `index.md` 又保存在其父目录的列出结果里。
- **为什么是问题**：修改 `lore.content/alice/leaf` 的展示名，唯一精确事件是 `lore.content/content.xml` 的 `changed`；只重列 `lore.content`，已经展开的 `alice` 仍显示旧标题/顺序/清单错误。创建 `lore.content/alice/index.md` 的事件只让 `alice` 重列，而 `lore.content` 缓存里的 `alice.body` 仍为 false；未展开的节点尤其会继续显示“无正文”与“创建内容”，不能从节点行打开新正文。删除/改名正文同样有此问题。这直接破坏 Spec 验收 1、2、4 以及外部修清单后自动恢复。
- **依据**：`files/backend/files-service.ts:5-6,109-128` 每一层列出都读取所属内容根的清单，目录项 `body` 在父层用 `index.md` 的 lstat 得到；`files/shared/contracts.ts:76-83` 已公开 `Listing.contentRoot`；`workspace/folder-kinds.md:69-70,89,100` 要求任意深度正文入口与修复清单后恢复。真实 `filesScene` 实验：创建正文前父层 `alice.body=false`，创建后的新父层为 true；嵌套展示名由 `Old` 改为 `New` 时只有根清单的精确 changed 事件，而新列嵌套层的 title 已是 `New`。这是现有数据合同的实测；t70 尚未实现，过期界面是按计划算法推断。
- **建议改法**：把“哪些列出依赖这条事件”集中成树模型的一份失效规则，不在每个 action 加手工 refresh。普通目录取父目录；正文变化再标脏存放该节点项的上一层；清单变化按已有 `Listing.contentRoot` 标脏所有依赖它的缓存层；目录改名/转换还要使子树的类型与 contentRoot 重新解析。S1 加真实窗口场景：嵌套层已展开时修改根清单、非法→修复、节点未展开时创建/删除正文、普通目录与内容目录互转；断言可见标题、顺序、打开资格和错误状态，而非只断言收到事件。

## 4. 重要：缺少未提交意图与已提交批量的冻结/取消合同，现有事件可以先于批量结果改写它们

- **类别**：不变量 / 时序与测试。
- **计划位置**：`plan.md:30`、`plan.md:49`、`plan.md:53-57`、`plan.md:91`、`plan.md:101-105`。
- **现象**：树事件会改写选择、焦点与剪贴板地址；剪切又在每项成功后删除剪贴板源。但计划没有定义批量返回下标怎样关联发起时的源/目标，也没规定提交后仍被刷新影响的记录应怎样结算。拖动只写“源是当时的选择”，没有规定 `identify`/`expected`、显示开关/源与锚点变化的作废条件；这些时序都不在自跑用例里。
- **为什么是问题**：批量开始后树可能因外部事件刷新，也可能先收到第一项的精确 renamed/deleted；等整批结果到达才按“当前选择/当前剪贴板地址”回填，会把结果归到错误项或漏清已成功的剪切源。另一条实际风险是拖动期间同路径对象被替换，若释放时才 identify 或不带冻结令牌，会操作新对象。Spec 还明确要求切换显示取消未提交菜单/拖动，不能改变已提交目标；仅在 keys/selection 的纯函数表里没有办法证明这些异步不变量。
- **依据**：`workbench/files-explorer.md:99-102,139-143`，`workspace/files.md:83,87-90`；`pending-confirmations.md:44` 明确 t70 在剪贴板与拖动时带源令牌。真实 `race-probe.ts` 持有内容清单写入锁，第一项实际移动后仍在途：外部刷新已到，列出呈现旧项 missing/新项 unlisted；放锁后顺序实测为 `renamed event: resultDone=false` → `batch result`，最终结果 `[done,cancelled]`。真实 `files-probe.ts` 还证明改名保留同一令牌，地址前缀改写后带原令牌能继续 move。因此剪贴板可重写路径，但已提交请求的原始索引关联不能跟着改。t70 尚未实现，错误结算的表现是按未规定状态规则推断。
- **建议改法**：不另建协调层；由计划中的 Controller 只持有一种操作意图：冻结的操作 id、源项 id/令牌、实际源/目标与结果下标。树的选择/剪贴板投影可以随事件变化，提交输入与结果归属不变；剪切结算按冻结项 id/令牌对应移除，并防止迟到结果清掉用户新建的剪贴板意图。拖动冻结源令牌的 identify 是异步的：令牌取得前不能提交，手势已取消或源槽失效时丢弃迟到结果；不能在释放后给新对象重新冻结令牌。未提交菜单/拖动遇显示开关、源/目标/顺序锚点失效、窗口失焦/隐藏或卸载则取消，释放时再核对最后显示的同一动作。S3/S4 加锁屏障用例：刷新期间改选择、首项事件先于结果、在途换剪贴板、同路径同字节替换、删/改名排序锚点；核对磁盘、逐项反馈与剪切标记，取消判据等操作终态后再查零写入。

## 5. 重要：首列与刷新在途时的失效规则缺少确定性场地，“只找已加载目录”会漏首列窗口

- **类别**：正确性 / 时序与测试。
- **计划位置**：`plan.md:27`、`plan.md:30`、`plan.md:88`、`plan.md:112`。
- **现象**：目录状态是互斥的 `unloaded | loading | loaded | error`，事件处理却只找“已加载目录”。计划承诺在途又标脏时再列一次，但没有说明从未 loaded 的目录在 loading 时如何匹配事件，也没有目录改名/删除/转换时缓存 key 与旧请求的失效规则。S1 自跑只列操作场景，不给控制响应到达顺序的入口。
- **为什么是问题**：首次列出已取得旧目录快照、结果仍在传输中时发生新建；如果事件以 loaded 过滤，这条事件会被丢掉，旧结果到达后树漏项，直到用户刷新。删除/改名后再创建同路径时，项目代次仍相同，旧请求也不能凭“不跨项目代次”防止给新对象回填。一次至多一个请求只限制并发，不能解决迟到结果与丢失标脏。这里是对计划状态表的推断，尚无 t70 实现可复现。
- **依据**：`files/backend/files-service.ts:95,111-128` 列出本身跨多个异步文件读取；`files/web/client.ts:54-58` 无目录版本，只有返回值与可选 AbortSignal；`remote/testing/in-process.ts:1-6` 的真实链路异步派发，但 `files/testing/scene.ts:62-75` 没有响应闸门。真实 `race-probe.ts` 只延迟向调用方交付真实 list 结果，在外部新建事件到达后放行，得到旧结果名字 `[a.md]`，再次真实 list 得到 `[a.md,new.md]`。它证明可制造这类时序；交付闸门是实验适配器，不冒充现有产品设施。
- **建议改法**：树模型的一份目录槽同时保留最后快照、请求状态与脏版本；事件能标脏 loaded 与 loading 的槽。响应只应用于仍拥有该请求的槽，目录被删除/改名/类型转换或模型释放时作废旧请求；仍脏就再列。无需第二套索引或项目状态。S1 测试场地增加可放行 Promise 的交付闸门：真实客户端先完成 list，拦交付；用真实磁盘写入并等 watch/模型已标脏；放旧结果，等后续列出完成后断言可见行。再覆盖 rename/delete/recreate、失败后外部变化与 resync 在列出中到达。`waitUntil` 只等待屏障，不靠多写文件、固定等待或大目录拖慢来碰概率。

## 6. 重要：验收表合并了会漏检的子判据；“磁盘字节不变”不能证明“不发写入”

- **类别**：验收覆盖 / 否定判据与变异。
- **计划位置**：`plan.md:96-108`、`plan.md:112`。
- **现象**：映射只按 Spec 的大编号列十行，完成条件多为“DOM 测试”或“磁盘字节”；没有拆开非写入、操作资格、打开模式、窗口隔离等子判据，未注明事件/请求的观察截止点。每条一个变异在这种粒度上可以只改坏其中一个分支，却把同编号的其它要求算作已覆盖。
- **为什么是问题**：验收 1 要求普通目录不读正文、活页夹降级提示、根禁改名/移动/删除；现有映射只明确标签与默认隐藏。验收 3 的 preview/permanent、修饰选择不打开，验收 4 的取消未提交意图/保留已提交目标，验收 5 的另一窗口隔离，验收 8 的授权失效停止，验收 10 的旧结果隔离，均没有具体入口和终态。验收 2、11 及状态表要求浏览不写文件；字节不变只能证明最终内容没变，不能证明没有同字节保存或被拒绝的写请求。异步 watch 的空数组在操作结算前检查也会假绿。
- **依据**：`workbench/files-explorer.md:104,136-146`；`docs/testing/README.md:12,18,22,24` 要求场景/失败方式、等待可观察完成点及逐判据变异。真实 `negative-probe.ts` 经完整 Files/RPC/磁盘链路模拟一次同字节保存：操作成功、前后字节相同，但 inode 改变且精确 `changed` 已到。因此计划中仅“浏览前后字节不变”的测试会放过这个审查用变异。`files/operations.test.ts:94-101` 已有后续外部变化事件屏障，可直接沿用；它只证明此前同一监视链上的事件已被处理，不证明未发被拒绝请求。
- **建议改法**：按独立可失败的子判据拆验收表，每行写真实入口、可观察终态、测试文件/用例、一个能使该判据失败的变异。否定事件先等动作结算与模型处理完成，再写同根的外部屏障文件、等对应 watch 事件，过滤屏障后断言；磁盘内容/清单比较排除控制目录与 Storage 偏好。对明确“不发写入/不读正文”的判据，用测试链路适配器记录经真实 RemoteLink 的 Files 方法帧（不替换 Files 结果），在所有已发起动作结算后查 effect=write 或 read 帧；不能用零事件替代零请求。取消批量须等 `handle.result`，不能把 `cancel().found=true` 当完成。删除/碰撞对话框交接等真实 `closed`，不用等待毫秒数。t70 源码不存在，本次只验证上述审查变异，未声称完成 t70 每条变异检查。

## 7. 建议：把控制器的浏览半边前移到 S1/S2，按完整交互交付，减少跨片空接口

- **类别**：切片 / 可维护性。
- **计划位置**：`plan.md:40`、`plan.md:47-49`、`plan.md:74`、`plan.md:88-92`。
- **现象**：S2 组件只经真实 `ExplorerController` 取数据、发动作，但 Controller 归第 4 节，S3 才开始交付这节；树内按键又拖到 S4。插件的命令从启动时就存在，Controller 却每个视图实例一份，尚未首次可见或已卸载时命令没有明确宿主。Lab 到 S5 才加，却计划让挂真实 Controller 的内存客户端只实现部分 FilesService 方法。
- **为什么是问题**：S2 要么提前带入下一片的控制器/动作，要么留下空实现，提交边界不清；S2 的基本浏览与打开模式也无法从真实键盘入口自证。Lab 的部分接口若由类型断言或成功空实现补全，会成为第二套行为，交互点击到批量路径时不能如实演示。插件命令与视图寿命不同是既有合同；增加全局 store 或第二份 Controller 来接命令会扩大状态同步问题。
- **依据**：`workbench/views.md:81,90,93`、`workbench/web/contracts.ts:29-41`：视图首次可见才建实例，停放不重建，撤回卸载；`files/shared/contracts.ts:169-186` 有真实单项、批量及取消方法，不是只含 list 的接口。可复用模式已在 `workbench/web/commands/open-commands.ts:27-47` 的 `PaletteSlot` 与 `WorkbenchCommandHost.dom.test.ts:28-47`：无宿主命令明确 unavailable，卸载后槽位释放。`src/web/testing/sample-views.ts:69-89` 贡献 load 包装组件，并经 props 明示依赖。
- **建议改法**：保留一个窗口剪贴板与一个视图 Controller；树缓存、选择、持久状态和操作意图只在 Controller 背后的模型内，不再加状态副本。S1 交付树模型与 Controller 的浏览入口并用 Bun 真实场地自证；S2 交付真实视图/插件、Storage、虚拟列表、点击与全部基本导航/打开按键，当期 Playwright 自证；S3 加单项、删除、反馈；S4 把粘贴与拖动统一翻译成同一种冻结 move/copy/reorder 意图，加真实浏览器拖动用例。命令用一个随视图 attach/release 的槽位或工厂接当前实例；无实例时返回可见不可用，不能静默成功。Lab 场景随各片登记，注入与当前片真实消费接口对应的可变适配器并显式呈现不支持；不为未来方法写空实现。S5 只做整体验收与证据收口，不再首次验布局、指针或产品接线。

## 验收映射逐行核对与建议补全

## 更少部件的实施安排

推荐保留现有五片编号，调整职责和证明位置：S1 是一个可经真实 Files 调用的树/浏览 Module；S2 是完整浏览视图（插件、持久状态、虚拟滚动、选择与打开入口）；S3 是写入与反馈；S4 是把剪贴板/手势译成同一操作意图；S5 收口。`rows`、`selection`、`keys` 可以作为纯函数留在模型内，不必把它们各变成公开状态持有者。缓存请求的有效性、所有刷新依赖、操作冻结与结算各由一个拥有者维护。

推荐验证分工：Bun 真实 `filesScene` 负责树/Controller/操作合同与磁盘，Node DOM 负责受控组件的按键、点击、输入、ARIA、对话框交接，Playwright 负责真实产品装配、Storage 重载恢复、尺寸/滚动/拖放。这样无需为“所有 DOM 都同时承载真实磁盘”新增跨宿主 fixture。若仍坚持该 DOM 约束，就把 Bun 后端子进程+真实 RPC 桥作为 S1 的明确交付物，不能让 S2 才遇到 Bun 专有模块导入问题。

Lab 是另一实际 Adapter：在相同明确 seam 注入客户端/宿主能力，逐片支持当前真实消费的行为。不要另造 Lab 专用 Controller，也不要为了满足完整 FilesService 类型添加成功空实现。对话框本身已可复用，不需要独立通用确认框架；用真实 `closed` 把关闭、焦点归还和下一步操作连起来。
