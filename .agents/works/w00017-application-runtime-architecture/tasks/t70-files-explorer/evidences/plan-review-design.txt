## 发现 3：结果未知后只去掉重试按钮，仍允许重新粘贴同一旧意图

- **严重程度**：阻断。
- **类别**：正确性、操作意图不变量。
- **计划位置**：`plan.md:43,55,57`。
- **现象**：计划只规定“一个批量在途”以及未知结果显示“重新列出/放弃”、不提供重试按钮，没有把未知批量的剪贴板和冻结源锁定。`unknown-outcome` 已经让句柄的 `result` 结算，按“在途”规则可以开始下一批；剪切只有已确认成功项才移除，未知项仍在剪贴板，Ctrl/Meta+V 或菜单粘贴仍可再次提交。
- **为什么是问题**：隐藏重试按钮不等于阻止旧意图重放。结果未知时旧写请求可能仍在提供方执行；立即重列也不能证明它已停。复制可重复，会在碰撞协商改名后再造一份，移动/删除也可能与未结束的旧请求交错。验收 8 的“未知先核对、绝不盲目重复”需要执行入口的门禁。
- **依据**：`docs/specs/workspace/files.md:88–91` 明确在途项结算后再停、列出不能证明旧操作已停止、不自动重试；`docs/specs/workbench/files-explorer.md:63–64,100,118,143`；`packages/neuro-book/src/plugins/files/web/client.ts:45–50` 的句柄 Promise 收到未知即结算。旧应用 `WorkspaceFilePanel.vue:77–86,251–253,281–323` 在未知时禁止复制/剪切/粘贴，核对源与目标后明确放弃才清旧意图。对 t70 的重放风险为从计划推断，旧防护已从代码核实。
- **建议改法**：在现有操作状态里加 `unknown`，保留这一次的完整源/目标及剪贴板身份；所有按钮、菜单、键盘和拖动入口共用该门禁，禁止再次使用受影响旧意图。只读重列/核对不自动解除门禁，明确放弃清掉意图后才允许重新选择；“放弃”文案说明不会取消仍可能执行的后台操作。S4 验证未知回包后再按 Ctrl/Meta+V 不产生第二批，再验证核对与放弃路径。

## 发现 5：改名事件改写剪贴板地址，会把冻结的旧操作意图搬到新位置；拖动又没有明确携带令牌

- **严重程度**：阻断。
- **类别**：正确性、源身份与并发。
- **计划位置**：`plan.md:30,55–56,91,102`。
- **现象**：计划让 `renamed` 改写剪贴板里的源地址，但剪贴板的身份令牌只是设备号、inode、创建时间和类型的摘要。普通改名保留这些值，改写地址后旧令牌会被新位置接受。另一方面，拖动只规定源是“当时的选择”，没有写明冻结时 `identify`、等待身份完成及 `move` 提交的 `expected`；t69 的令牌可省略。
- **为什么是问题**：剪贴板不是文档的持续追踪身份，是用户在具体地址冻结的一次操作意图。另一个窗口移走源后，旧意图应失效，不能由监视事件悄悄改投新地址；改写后会绕过现有服务端的 `source-changed`。拖动从激活到放下也可能遇到同路径替换；若只传路径，服务端会把新资源当作源执行。验收 5 的旧引用拒绝及 t69 已定的拖动令牌约束没有闭合。
- **依据**：`docs/specs/workbench/files-explorer.md:61,99,140`、`docs/specs/workspace/files.md:83`；已采用的取舍 `pending-confirmations.md:44` 明确“t70 在剪贴板与拖动时带上”，且令牌不是持久文件 id。`files/backend/rooted.ts:65–67` 计算令牌；`files/shared/contracts.ts:245–249` 的 `expected` 可选。**已运行**真实客户端：冻结 `plain/a.md`，经 `rename` 改成 `renamed.md` 后 `identify` 返回同一令牌，把旧地址改成新地址再 `copy` 带旧令牌，结果为 `done`，磁盘副本为原字节。拖动未带令牌的未来表现属推断。
- **建议改法**：改名可以迁移展开/选择/焦点，但不迁移冻结剪贴板或已经展示的操作源；源或祖先被移走时将旧意图标失效，提示重新选择，不自动重新 `identify`。拖动激活时冻结地址集合并取得令牌，身份尚未齐备不允许提交，放下时全部 `move` 项带 `expected`。S4 追加“另一窗口改名后旧复制/剪切拒绝”和“拖动中同路径换成同字节资源仍拒绝”。这一改法不增加身份服务，只消费 t69 已有接口。

## 发现 1：按事件父目录刷新，漏掉清单与正文入口的实际依赖

- **严重程度**：重要。
- **类别**：正确性、合同衔接。
- **计划位置**：`plan.md:27–34`，尤其第 30 行；S1 的增量刷新验证在第 88 行。
- **现象**：计划只重列事件路径的父目录，改名只改展开/选择/焦点/剪贴板地址，未处理目录缓存本身。`a.content/content.xml` 改动只刷新 `a.content`，已经展开的 `a.content/人物`、`a.content/人物/甲` 继续用旧清单投影。`人物/甲/index.md` 被创建或删除时只刷新 `甲`，父列表中 `甲` 的 `body` 仍是旧值。目录改名后的缓存仍以旧资源地址为键。
- **为什么是问题**：清单描述整棵内容子树；展示名、顺序、缺失/未列入状态及正文入口依赖的范围大于事件父目录。照当前规则实现，会在文件服务已经成功写盘后继续显示旧标题/顺序或错误的“无正文”；已展开目录改名还会丢失已加载子树或继续显示旧地址。验收 1、2、4 与“已展开部分由监视增量更新”不能闭合。
- **依据**：`docs/specs/workspace/folder-kinds.md:23,69–70,86–89`；`docs/specs/workspace/resources.md:77` 明确清单更新仅是清单文件的 `changed`。`packages/neuro-book/src/plugins/files/backend/files-service.ts:109–128` 显示每层 `Listing.contentRoot` 指向同一清单，`body` 在父目录列出时算出；`shared/contracts.ts:76–83` 提供了该依赖标识。目录缓存键与改名处理分别见计划第 27、30 行。**已运行**真实 `filesScene`、浏览器客户端与磁盘：嵌套展示名改动仅发 `lore.content/content.xml changed`，新列 `lore.content/people` 的标题已改变；创建 bob 正文仅发 `lore.content/people/bob/index.md created`，新列父目录的 `body` 从 false 变 true。t70 未实现，旧界面状态仍是按计划推断；运行命令与输出见报告末尾。
- **建议改法**：沿用一个目录缓存，不另建清单缓存。`content.xml` 变化时把同一 `contentRoot` 的已加载/在途目录统一标脏；`index.md` 增删/替换时同时标脏节点目录及拥有该节点条目的父目录。目录改名/删除按段边界改写或失效缓存和在途请求，迟到旧地址结果丢弃。S1 加“嵌套清单只改一次、所有已展开层更新”“创建/删除正文更新父行”“展开目录改名”三条实际场景。

## 发现 6：清单投影与现有 Listing 的字段不完全对应，非法清单和活页夹回退仍可能藏正文或漏清单

- **严重程度**：重要。
- **类别**：正确性、文件夹呈现合同。
- **计划位置**：`plan.md:31–34,98,101,118`。
- **现象**：投影按“普通/内容文件夹”分组，却未定义如何合用 `folder`、`contentRoot` 与清单状态。实际内容树的普通子目录仍返回 `folder: plain`；清单非法时仍返回 `role: body`。计划又仅以 `role: manifest` 隐藏清单，但 `*.binder/binder.xml` 在现有列出里没有该 role。活页夹推迟的是专用渲染，计划没有写明本片的普通回退提示。
- **为什么是问题**：仅按 `folder` 分支会让有效嵌套节点失去展示名与正文入口；无条件隐藏 `role: body` 又会在清单失败时违背普通回退，使 `index.md` 无文件行而节点操作仍不明确。活页夹的 `binder.xml` 会绕过默认隐藏与开关，且缺少“剧情插件未启用”的说明。验收 1、4 明确要求这些回退和清单行为，即使专用活页夹渲染已合法延期也不能一起省掉。
- **依据**：`docs/specs/workbench/files-explorer.md:50–51,59,120,136,139`；`workspace/folder-kinds.md:64–70,78,100`；`files/backend/files-service.ts:98,107,114,118` 与现有 `files.test.ts:163–168`。**已运行**真实客户端：`broken.content/child` 返回 `folder: plain`、`contentRoot: broken.content`、`manifest.status: invalid`，但 `index.md` 仍带 `role: body`；`story.binder` 的 `binder.xml` 只有 `name/kind`、没有 `role`。t70 尚无投影实现，未来显示偏差为推断。
- **建议改法**：在一份纯投影里明确：有效内容呈现由 `contentRoot != null && manifest.status == ok` 决定，不用 `folder` 单字段；失败时退回真实名称/普通目录点击/可见正文，并保留诊断。活页夹本片按普通显示且提示需要剧情插件，按所在目录类型和准确文件名识别其清单，不在普通目录里全局隐藏同名 XML。S1/S2 补有效嵌套节点、非法→修复、无剧情插件的 binder 清单开关三个场景；不新增通用渲染注册框架。

## 发现 10：无选择时把目标写死为项目根，遗漏第二个根的“当前根”语义

- **严重程度**：重要。
- **类别**：正确性、操作目标。
- **计划位置**：`plan.md:28,51,55,103`。
- **现象**：树有 `project://` 与 `user://` 两个根，但新建与粘贴都把“无选择”固定成项目根，没有当前根状态。用户在用户资产根浏览、清空资源选择后，从工具栏或树键盘粘贴仍会落到项目根。
- **为什么是问题**：Spec 固定的是“无选择用当前根”，不是一律项目根。用户资产源随后会被判跨根拒绝；若源在项目里，用户以为粘到用户资产却可能写入项目。验收 6 的三种目标只在项目根验证无法发现此差异。尚未实现，未来操作表现为按计划推断。
- **依据**：`docs/specs/workbench/files-explorer.md:23,52,62,141`；`docs/specs/workspace/files.md:66,91` 规定每批仅同方案且不能跨根搬运。现有 `files/shared/contracts.ts:284–291` 已把方案留在客户端边界，不会自行猜用户的当前根。
- **建议改法**：选择/焦点模型保留当前根（由根焦点或资源地址的 scheme 确定），新建、空白菜单与无选择粘贴统一使用它；无当前根时禁用并要求明确目标。控制器先冻结实际源、目标并可见展示，碰撞确认和无碰撞路径同样保留这个信息，不随之后焦点变化改投。S4 的三类粘贴目标分别在 project 与 user 两根覆盖，跨根明确拒绝且两端字节不变。

## 发现 2：Lab 接缝省略批量句柄，无法挂载同一完整控制器验证局部操作

- **严重程度**：重要。
- **类别**：合同衔接、测试。
- **计划位置**：`plan.md:49,53–57,74,92,108`。
- **现象**：第 74 行只让内存文件客户端实现 `list`、`watch`、`identify` 与单项操作，却宣称与 `FilesService` 同一接口并由类型检查保证；同一个控制器的删除、粘贴和拖动移动都调用批量方法。
- **为什么是问题**：`FilesService` 的 `move/copy/delete` 是必需方法，立即返回 `{result, cancel()}`，并不是单项 Promise。上述内存实现按字面既不能满足类型，也不能演示同一控制器的删除/复制/剪切/移动及取消、部分完成、清单失败。靠缺省成功或禁用整组动作填接口，会把验收 13 的“同一面板、客户端核心和控制逻辑、局部操作”缩成另一套简化路径；类型只证明形状，不能证明写入、身份与事件语义。
- **依据**：`docs/specs/workbench/files-explorer.md:130,148`（验收 13）；已接受首版提案 `packages/neuro-book-legacy/docs/proposals/files-explorer.md:119–123` 要求内存真实维护内容/版本/变更，不以 `return ok` 伪造写入；现有 `packages/neuro-book/src/plugins/files/shared/contracts.ts:141–162,252–291` 定义完整批量结果与句柄。已核对接口，无 t70 可运行实现。
- **建议改法**：保持一个控制器和一个文件客户端接缝。Lab 内存适配实现 t70 实际消费的方法（包括三种批量与取消），操作改变场景数据并发出同形事件；未消费的读写能力明确返回不可用，不假报成功。用少量场景覆盖全部成功、部分失败/清单失败、未知与取消，不另外造简化控制器或第二棵树；验收补一次 Lab 删除与剪切粘贴实际状态变化及离场释放。

## 发现 4：以“nb-ui 没有树”为新写树的前提不成立，应按能力缺口决定复用

- **严重程度**：建议。
- **类别**：代码质量、部件复用。
- **计划位置**：`plan.md:12,25–42`。
- **现象**：第 12 行写“nb-ui 没有树与虚拟列表”，但公开入口已导出 `FileTree` 与 `Tree`。

- **依据**：`packages/nb-ui/src/components/index.ts:50–52,131–133`；`navigation/FileTree.md:7–17,73–96`（受控展开、键盘、node/trailing 插槽；不支持多选/虚拟滚动）；`navigation/Tree.md:13,29–53,70–75`（支持多选，但没有插槽与虚拟滚动）。`docs/standards/code/components.md:115` 与 UI Skill 的通用组件优先复用规则。已静态核对导出、伴生文档与 `FileTree.vue:59–143`。
