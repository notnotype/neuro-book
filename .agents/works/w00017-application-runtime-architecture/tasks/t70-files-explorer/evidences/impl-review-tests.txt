## 1. 重要：偏好恢复只更新 Store，实际树没有恢复；测试只证明按钮发出事件

- **类别**：正确性 / 测试。
- **位置**：`packages/neuro-book/src/plugins/explorer/web/session.ts:55`、`:103`、`:110`；`web/preferences.ts:86`、`:98`；`web/view-host.ts:113`；`web/components/FilesExplorerView.dom.test.ts:49`；`session.test.ts:183`。
- **现象**：已保存 `showManifests=true`、展开 `plain` 后断开 Storage 窗口链路，在树中关闭显示与收起 `plain`，保存失败。调用真实“放弃” action 后，Store 的显示回到 `true`、路径回到 `["", "plain"]`，树仍为 `false`、只展开 `project://`，`problem=null`。另一个窗口在首读前断线，恢复后执行“重新读取”，Store 读到同样的保存值，树仍保留首次失败时的缺省值，提示也消失。
- **为什么是问题**：Spec 持久化（`files-explorer.md:117`）和验收 16 要求首读失败后可重新读取、放弃后显示回落到已保存值。`start()` 只在控制器创建时复制字段的 display；后续 retry/discard 没有把新 display 应用到控制器。现有 DOM 测试直接传 `problem` 再断言 emitted，真实 Storage 测试仅覆盖正常保存和新会话重载，无法抓住恢复时状态断开。
- **依据**：在源码副本运行 `env NBOOK_AGENT_TEMP_ROOT=<本报告目录> bun review-storage-smoke.ts`（cwd=`<本报告目录>/source/packages/neuro-book`），真实 `filesScene`、真实 `storageWorld`、真实 SQLite、真实断线/重连，未替换 Storage 返回值。输出：`discard.after={store:true,tree:false,storePaths:["","plain"],treePaths:["project://"]},problem:null`；`first-read-retry.after` 同样；7 个应用关闭均为 `closed`。实验直接使用产品会话与 Store 的公开 action；UI 的两个按钮分别接同一 action（`view-host.ts:113-114`）。
- **建议改法**：让会话在明确 retry/discard 完成后统一应用三份字段的 display 到同一个控制器，避免继续保留未同步的偏好副本；不要重建控制器而丢失选择/剪贴板。补真实 Storage 的失败→重试、失败→放弃、首读失败→重新读取用例，断言可见行、显示开关和提示消失后的状态。

## 2. 重要：批量取消没有从资源管理器入口到终态的测试；把取消变成空操作后全部现有相关测试仍通过

- **类别**：验收覆盖 / 变异。
- **位置**：`packages/neuro-book/src/plugins/explorer/web/controller.ts:477`；`transfer.test.ts:365`；`web/components/FilesExplorerActions.dom.test.ts:144`；`e2e/files-explorer.e2e.ts:334`。
- **现象**：只将 `runBatch` 的 `cancel: () => void handle.cancel()` 改为 `cancel: () => undefined`，explorer 的 Bun 73 项、DOM 19 项全部通过。DOM 只从传入的 `running` props 断言 `cancel-running` 被 emit；e2e 的 Escape 是未提交拖动取消，没有任何用例取消已经提交的批量。
- **为什么是问题**：`plan.md:171` 和 Spec 验收 8 要证明取消不回滚首项并停止后续项。底层 Files 有真实取消测试（`files/batch.test.ts:297`），它不经过资源管理器的 Running action，无法抓住这处用户入口失效。这是测试缺口，当前取消实现本身在真实实验中正常。
- **依据**：真实 `filesScene`、磁盘与 `holdLock` 锁住 `lore.content/content.xml`，等第一项移动落盘后经同一 Running action 取消；同链路 list 回复作请求处理屏障，再放锁并等 paste 终态。原实现结果为 `[done,cancelled]`，第二源仍在，cancel 帧 1；空操作变异下两项都移走、结果区为空（整批成功）、cancel 帧 0。`review-cancel-smoke.ts` 在原实现退出 0、变异退出 1（`unexpected cancellation result`）。还原 SHA-256 与备份相等：`7bb0230b07c03660e8a8c17309186c01e76673a197b49ad8aa4164d6e869e421`。
- **建议改法**：在现有“逐项结果”用例组补资源管理器真实取消场景，走 Running action 或产品按钮，持有真实清单锁，等首项落盘再取消，放锁后等 result；断言首项内容保留、第二源未移动、结果逐项 `[done,cancelled]`、剪切仅清首项。至少覆盖删除或移动的一个完整入口，不能只断言取消事件或 ACK。

## 3. 重要：切换显示时保留选择没有断言；清空选择的变异在三层测试全部存活

- **类别**：验收覆盖 / 变异。
- **位置**：`packages/neuro-book/e2e/files-explorer.e2e.ts:106`；`src/plugins/explorer/browse.test.ts:183`；`web/controller.ts:633`。
- **现象**：只在 `setShowManifests` 中增加 `selection.value = EMPTY_SELECTION`，Bun 73 项与 DOM 19 项通过；重新构建 web 后，产品 Chrome 的全部 10 项 e2e 也通过。`显示清单文件与展开记录` 用例只核对清单行、按下状态与展开恢复，没有在切换前选资源并核对切换后的选择和逻辑焦点。
- **为什么是问题**：`plan.md:159`、Spec 验收 4 要求可见资源选择与展开保留。清空选择会改变下一次新建/粘贴的实际目标：本来以选中文件父目录为目标，变成当前根；这是用户可见的操作合同，不是内部默认值。

- **建议改法**：扩展现有显示切换的产品用例：先选仍可见的资源，切换后检查 `aria-selected`、`aria-activedescendant` 与展开状态，再用新建/粘贴结果核对目标仍为其父目录。另测被隐藏的清单行选择按既定 prune 规则回落，不能对所有选择清空。

## 4. 重要：零写入判据没有闭合观察窗口；取消改名的同字节写入变异未被拦住

- **类别**：测试 / 否定判据。
- **位置**：`packages/neuro-book/e2e/files-explorer.e2e.ts:224`、`:238`、`:301`；`src/plugins/explorer/browse.test.ts:189`；`actions.test.ts:125`、`:159`；`transfer.test.ts:307`、`:396`。
- **现象**：取消改名的产品用例在输入行消失、焦点回树后只读取旧文件字节。Bun 有 Files 写帧记录，但没有调用取消改名的这一行为，也没有按 `plan.md:143` 在否定断言前等待同根屏障。拖动取消的 e2e 有树屏障（`:367`），仍只看源字节/目标不存在，没有写帧观察。
- **为什么是问题**：同字节写入仍然修改资源身份并发事件，字节相等不能证明没有写入。只看即时帧数组也不能证明动作触发的异步后续工作没有写入。不能将本次所有零写入测试一概判为无效：已 await 完整 action/result 的帧断言能覆盖同步发起写入；具体漏检已由取消改名的存活变异证实。
- **依据**：单处在 `cancelEdit` 中读取冻结地址，再经真实 Files 写回相同正文；Bun 73 项全部通过，重新构建后 `files-explorer` 中 `--grep 'F2 改名'` 的产品 Chrome 用例也通过。真实 `review-negative-smoke.ts` 等该路径 changed 及同根 `barrier.md` 事件后输出 `bytes:"A",inodeChanged:true,writes:["write"]`，两个事件分别为用户写入与外部屏障。副本已还原，SHA-256 与备份相等。日志 `M05-cancel-write-1.txt`、`M05-product.txt`、`negative-observed.json`。
- **建议改法**：在现有取消/浏览/原位无操作场景建立共同的完成点：先等动作或批量终态，再等同根外部事件屏障，随后核对该窗口完整区间的 Files `effect=write`/`read` 帧与排除屏障后的业务事件。产品取消入口应记录 WebSocket 请求帧或经真实产品链路 tap；继续保留字节比较作补充，不用增加固定等待。树屏障能推进 watcher，但不应在注释中声称单个外部文件能结束任意仍在等待锁或 Promise 的写操作。

## 5. 建议：订阅首列竞态通过重排同一链路帧制造，不能作为产品真实时序的证据

- **类别**：测试模型 / 竞态真实性。
- **位置**：`packages/neuro-book/src/plugins/explorer/browse.test.ts:283`；`packages/neuro-book/src/plugins/files/testing/tap.ts:65`、`:103`；`packages/neuro-book/src/shared/rpc-socket.ts:38`；`packages/nb-runtime/src/remote/testing/in-process.ts:44`。
- **现象**：`holdSend` 扣住先发出的 subscribe，只延迟这一帧，后发的 request 继续到达提供者。测试等 list 返回并外部写文件后，才交付 subscribe。实际 WebSocket send 与正常 in-process JSON 链路按发送顺序交付；窗口不能在同一连接上让后发 request 越过先发 subscribe。
- **为什么是问题**：该用例保护 `ready` 前的防漏变化逻辑有价值，但没有证明产品里能发生所声称的竞态。回复 `hold` 同样可让后发事件越过已到窗口的 result；它是抽象完成闸门，不是原样网络时序。真实清单锁实验则不重排帧，首项落盘→事件→批量结果是成立的。仅判为测试证据建议，不据此声称当前产品有漏项缺陷。
- **依据**：无发送重排的真实场地记录为 `hello, subscribe, subscribe, request, request`；延迟真实 list 结果、外部写 `early.md` 后，现有模型最终看到它，三应用关闭为 `closed`。服务端 changes 订阅建立 watcher 并同步发 ready（`files/backend/changes.ts:273`），`RemoteNode` 则先异步 lookup（`node.ts:763,847`）；订阅完成与请求完成仍可能不同序，不能据此宣称所有首列竞态不可能。已核实的限制只在于此 `holdSend` 实验改变了 transport 帧顺序，没有给出等价的真实完成顺序证据。脚本为 `review-ready-smoke.ts`，正常退出 0。
- **建议改法**：保留帧记录；将竞态门放到真实异步建立/调用完成边界，或用真实清单锁、提供入口生命周期制造事件先于尚未结算的调用，而不让同一 transport 的帧互相超车。若确实只能作为完成闸门，应明确测试名和证据范围，并另以产品有序链路证明对应竞态；不要将该门面当 WebSocket 的仿真。
