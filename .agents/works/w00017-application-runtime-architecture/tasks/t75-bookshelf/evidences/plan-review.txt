## 问题

### P4：统计记录的“后写者胜出”与 Storage 的条件保存不相容

- **严重程度**：阻断。
- **位置**：计划“P12 与 P13”第 50–52 行及统计记录第 96 行；`docs/specs/storage/persistence.md:73,104–105,121,128–129`；`packages/neuro-book/src/plugins/storage/backend/partition.ts:138–147,252–261`；`docs/specs/runtime/plugin-channel.md:118`。
- **现象**：计划仅说一个项目代次一个写入者、双服务端后写胜出，却没有 revision 的读取与保存协议。Storage 的 `save(value,{expect})` 必须比较 revision，同一 revision 的两次提交至多一次成功；失败者拿到 `conflict`，不会自动覆盖。项目 `generation` 只在一个服务端进程中有效，服务端重启又从头编号，记录只存代次不能辨别来源。
- **为什么是问题**：照计划实现，第二个写者会持续冲突，或为了“胜出”无条件重读重写旧快照，覆盖较新的统计与今天基线；遇到 `unknown-outcome`、坏记录、版本不支持也没有恢复路径。它既未建立单 owner，也未定义已有 Storage 合同要求的竞争结算。
- **建议改法**：在 S3 前定义一条可执行的发布协议：来源包含 boot/实例身份与代次；读取快照后带 revision 保存，单写者串行合并；`conflict` 重读并比较来源和快照顺序，丢弃过期快照或按明确规则重新计算，不能盲目覆盖；`unknown-outcome` 重读核对。坏记录可按缓存恢复政策条件 `reset` 并保留原件、诊断；不支持的版本先判断迁移/刷新，旧代码不得直接重置较新记录，原件区满或恢复失败降级为不可用。用两个真实写者争同一记录、服务端重启代次重号、保存结果未知各覆盖一次。若两个服务端使用不同状态根，说明它们本来就不是同一条 user 记录。

### P14：窗口绑定增加 title 会破坏严格 wire schema，业务合同 v2 不能覆盖

- **严重程度**：阻断；**类别**：接口 / 兼容。
- **位置**：计划第 25、85、129–132、142 行；`packages/neuro-book/src/shared/projects.ts:74–93`；`packages/nb-runtime/src/remote/protocol.ts:14–21,180–183,236,280–282`；`packages/nb-runtime/src/remote/router.ts:45–54`；`docs/specs/runtime/plugin-channel.md:117,122`。
- **现象**：`WindowProject.project` 来自内核握手的 `ProjectBinding`，目前只允许 `{id,name,generation}` 且 `additionalProperties: false`。计划只写项目远程合同升到 v2，却同时要在窗口绑定加入 `title`，没列内核 wire 版本、绑定类型、welcome 解析与宿主映射的迁移。当前真实解析入口接受原绑定，但 `title` 为字符串或 `null` 时都拒绝；若服务端不发送该字段，客户端又无法从握手取得计划承诺的标题。
- **为什么是问题**：已用当前 `parseFrame` 直接运行核实 schema 行为；跨新旧端握手后果从合同推断。只改业务 v2，旧浏览器会在项目业务请求之前拒绝新 `welcome`，表现成断线/握手失败，不能走明确的“版本不兼容、刷新”路径。反向的新端连旧服务端也需要确定拒绝或降级，不能临时填假标题。
- **建议改法**：S0/S2 明确选一个一致的边界：若标题继续随绑定交付，按内核规则提升 wire 版本，迁移 `ProjectBinding`、路由绑定回调、项目租约/启动配置、浏览器映射及相应协议 Spec 和夹具；旧页面在 hello 阶段得到 `wire-version`，不发送不认识的 welcome。若保持 wire 不变，就经项目业务合同读取元数据再提供本地标题，删除“握手中增加 title”的要求。业务 v2 同时明确旧/新调用方的 `version-changed` 刷新提示，验收两个版本方向及无 title 的旧项目，不能只测同构建端到端。

### P2：元数据更新的“后写者胜出”会覆盖不同字段，身份核对也不覆盖提交窗口

- **严重程度**：重要。
- **位置**：计划“P11：project.json 的更新”第 33–37 行和验收第 154、170 行；`packages/neuro-book/src/server/projects/registry.ts:48–49,96–108`；`packages/neuro-book/src/backend/locked-replace.ts:5–14,64–75,177–186`。
- **现象**：两个进程先读同一文件，A 只改 `title`、B 只改 `color`，B 的整份旧副本后落盘会撤销 A 的书名；未知字段也一样被覆盖。读取时核对 `expectedId`，不能阻止读后文件被删除或换成另一 id，随后改名把旧身份写回。计划把这一风险说成同一文件后写胜出，却仍承诺保留身份和未知字段。
- **为什么是问题**：从代码与提交时序推断，这不是同一字段的取舍，而是互不相干的编辑互相丢失；`expectedId` 的检查也无法证明被替换的还是原项目。项目 Spec 允许双服务端，并不意味着允许它们破坏用户可编辑的身份文件。当前仓库已有跨进程加锁替换原语，配置与 Files 已复用，没有必要建立第二种更弱的提交约定。
- **建议改法**：复用 `replaceLocked`，在锁内按当前字节解析、核对 `expectedId`、应用 patch；保留未知字段，改名前重新核对文件身份，外部编辑器的最后窗口按既有合同说明。明确区分字段省略与清空。验收增加两个真实进程分别改不同字段均保留，以及等待提交期间身份变化被拒绝；不要把跨进程用例列为“只写 Spec、不验证”。

### P5：运行状态不能证明统计新鲜，首次扫描与失败状态无法表达

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 49、51、55–59、96、158 行；`packages/neuro-book/src/plugins/files/backend/files-service.ts:134–143`；`docs/specs/workspace/resources.md:107–114,123,125`。
- **现象**：计划直接以“项目正在运行”判为 `fresh`。新代次启动后后台扫描尚未完成、统计入口失败、监视结束、Storage 保存失败时，项目都可以继续运行，旧记录却仍会标为新鲜。`.md` 文件不是 UTF-8、超过正文预算、无读取权限时，现有 Files 会返回失败；记录没有扫描完成、遗漏数量或失败状态，无法区别“总字数为 0”与“没有读到稿件”。
- **为什么是问题**：从合同推断，书架会把旧值或不完整值作为当前总量、排序和继续写作依据；`none` 也无法区别首次扫描正在进行、从未打开与持久化不可用。30 秒写入合并是允许的延迟，不能当成扫描或保存成功的证据。
- **建议改法**：统计 owner 维护代次、扫描阶段、监视健康和最后成功发布快照，`shelf` 结合快照来源及状态判定新鲜度；仅完整扫描、订阅有效且发布成功的当前来源称为 `fresh`，并显示 `computedAt`。首次扫描呈现“正在统计”；读取失败保留上次值并明确“不完整/可能过期”，不要按 0 提交；单项目错误不能拖垮整架。验收增加旧记录加新代次慢扫描、单个不可读/过大文件、监视结束和记录写失败。

### P7：最近编辑所需的历史信息不在 Files 合同中，扫描与目录操作也未定义合并

- **严重程度**：重要；**类别**：正确性 / 不变量。
- **位置**：计划第 47、49、63、94–96 行；`packages/neuro-book/src/plugins/files/shared/contracts.ts:57–86,206–220`；`docs/specs/workspace/resources.md:77–78`；`packages/neuro-book/src/plugins/files/backend/changes.ts:5–7,15–18,52–53`。
- **现象**：初次打开已有项目时，Files 的 `list/read` 不返回修改时间，变更事件也没有时间戳，owner 无法恢复“最近编辑的文件和时间”；不能把任意扫描顺序当编辑顺序。计划“先扫描，之后重读变化的文件”未规定先收到 `ready` 再扫描和期间事件重放，扫描与订阅之间的修改会漏掉。目录新建/复制/移入只发目录一项、删除/改名影响整棵子树，不能只重读该路径；重扫、同文件并发读的迟到结果也可能回盖新值。
- **为什么是问题**：从现有 Files 合同推断，这几条都会使总量、最近编辑或继续写作目标错误，直至下次碰巧重扫。删除“最近编辑”文件后是否清空 `last`、改名只更新地址还是也算编辑、最后一个非空段落能否只是 frontmatter/代码，计划同样没有定义。
- **建议改法**：补明确的统计启动状态机：订阅 `ready` 后做快照扫描，缓存并按顺序结算期间事件；扫描/resync 带轮次，逐路径串行或拒绝旧轮次结果；按段边界处理目录前缀、对新目录扫子树。首扫的最近编辑要么通过 Files 新增明确的元数据读取合同取得可信时间，要么仅用已观测编辑并在缺失时降级为“打开作品”，不能猜测。删除清空或重新选有效目标，改名保留编辑时间；把这些真实文件操作纳入 S3 验收。

### P6：今天的基线在变化后建立，会吞掉跨日第一笔写作

- **严重程度**：重要；**类别**：正确性。
- **位置**：计划第 46、49、95–96、157 行；`docs/proposals/bookshelf.md:160`。
- **现象**：按计划的字面算法，23:59 总字数为 100，00:05 首次保存增至 120，随后第一次统计把 120 设成当天基线，今天显示 0，20 字永久漏记；当天新建项目若先写第一篇再完成初扫，同样漏掉第一笔。当天停机期间外部修改没有保存事件，下一次扫描无法知道增量发生在哪一天。若当天没有文件变化，午夜也未约定触发统计，记录仍带昨天的日期。
- **为什么是问题**：从算法推断，“第一次观测后净增”不等于提案的“今天按保存时间计”。只有注入时钟的跨日测试名称，没有定义先换基线再应用文件变化的顺序、重启时是否沿用当天基线，以及断档时展示什么，测试可能恰好避开最常见的午夜首笔。
- **建议改法**：选定可执行的低成本语义：运行中以跨日前最后可信总量换日，再计入当天变化，跨日无修改也更新时间；启动时同日沿用持久基线，跨日离线变化无法归属时标明“本次打开后净增”或未知，不伪称今天完整写作量。区分写作增量与复制/移入/删除造成的净变化。验收明确上述 100→120 的时序、当天重启、无变化跨午夜与离线跨日。

### P13：关闭时最后一次统计未规定排空顺序与截止后的结算

- **严重程度**：重要；**类别**：不变量 / 验收。
- **位置**：计划第 49–51、95、158、167–169 行；`packages/nb-runtime/src/plugins/host.ts:565,594–596,1009–1015,1028–1039`；`packages/nb-runtime/src/lifecycle/scope.ts:829–832`；`packages/neuro-book/src/plugins/storage/shared/facade.ts:43–46,74–77`；`docs/specs/runtime/plugin-channel.md:98–100`。
- **现象**：入口停止时 Files 的直接远程调用随停止信号取消，最后一个变更的重读可能尚未结算；统计 owner 若直接把现有字数表写为“最后一次”，就会遗漏最后保存或把未完成扫描当完整结果。计划没有规定先停止接纳、结束定时任务、排空已接纳变更，再保存可信快照的顺序，也没有定义保存失败/截止时的记录与 UI 状态。验收把“关闭窗口”紧接着读书架，但缺省 5 分钟宽限期内项目未停止，可能根本未覆盖 final flush。
- **为什么是问题**：从生命周期合同推断，正常关闭也可能留下错误或仍显新鲜的缓存。Storage 的代理门面已有释放期间远程调用仍可用的保证，因此最后保存是可实现的；需要使用必需依赖的存储门面或显式释放依赖，不能靠无依赖资源的登记先后来保活，也不能等到该门面已释放后才保存。
- **建议改法**：S3 写清停止协议及快照完整性：取消定时/新工作、收束或明确丢弃未完成扫描和读取、只发布已确认完整的状态，在存储门面释放前等待条件保存结算；失败保留旧记录并诊断为过期，不宣称 final flush 成功。若要确保最后一次保存也计入，明确在停止信号触发前完成读取/快照的交接。验收使用真实项目停止与零/注入宽限期，在 30 秒合并窗口内修改后立即停止，同时覆盖扫描未完成、保存冲突/失败和关闭截止，不用固定等待 5 分钟。

### P8：新建的目录命名、包含检查与半成功恢复没有合同

- **严重程度**：重要；**类别**：正确性 / 不变量。
- **位置**：计划第 79、82、87、90、155、170 行；`packages/neuro-book/src/server/projects/identity.ts:33–55,84–93`；`packages/neuro-book/src/server/projects/registry.ts:84–90,128–134`；`docs/specs/runtime/plugin-channel.md:87–92`。
- **现象**：底层新建需要 `folderName`，远程 `create` 只接 `title`，没有说明从标题到目录名的规则。书名合法并不代表目录名合法（`/`、`..`、空白、Windows 保留名等），也未定义同书名、父目录不存在/不可写、父目录链接及状态根的处理。“建目录→写身份→登记”至少三步：后两步失败会留下目录；登记表已经损坏时，现有 `register` 的“先读表、失败不碰目录”不再成立。RPC 写请求结果未知后再次 `create`，还会因目录已存在而报失败，用户无法知道是否已建成。
- **为什么是问题**：从方案时序推断，可能在作品目录之外创建文件，或在禁止登记的状态根内留下作品；权限、磁盘故障或断线会产生未登记的半成品，重试又没有可识别的项目 id/路径。现有“登记同一目录幂等”的恢复方式不能自动套给“排他新建”。这不只涉及未实测的 Windows/macOS，Linux 的同名、包含和写失败即可触发。
- **建议改法**：先校验登记表与元数据，再 canonicalize 并核对父目录、单段目录名、包含范围、状态根边界和实际创建权限；把目录名与展示名的关系、同名提示写进 Spec。明确操作分阶段结果及补偿：只清理由本次独占创建且仍为空/身份一致的产物，不能递归删除别人已写入的目录；不能安全清理时返回实际路径及“加入此目录”恢复入口。为结果未知保存可核对的操作身份或确定目标路径，先核对再重试。S2 覆盖同时同名创建、坏登记表、身份写失败、登记写失败、父目录链接/只读与结果未知。

### P10：运行中拒绝移除只是一句状态检查，未与打开操作形成原子边界

- **严重程度**：重要；**类别**：不变量。
- **位置**：计划第 80、84、156 行；`packages/neuro-book/src/server/projects/manager.ts:167–177,253–265,281–289`；`docs/specs/runtime/projects.md:39,59,62–64,72–74`；`packages/neuro-book/src/server/projects/registry.ts:145–149`。
- **现象**：计划新增 `registry.unregister`，manager 仅承诺非 `stopped` 时拒绝。现有 `acquire` 先异步解析登记再开始创建，并不经登记的队列；检查 `stopped` 到异步写表之间可以插入打开。若打开已经读到登记，移除再成功落盘，就可能一边确认移出了书架，一边出现项目代次，或在子进程创建时因登记突然缺失而失败。两个服务端各自的状态也不同，A 判断停止不能证明 B 未打开。
- **为什么是问题**：从现有并发边界推断，单次按钮检查不能提供计划以此替代的“不影响窗口与租约”保证。另外关闭最后一个窗口后仍有缺省 5 分钟 `idle-grace`，所以“运行中”不等于“有窗口开着”；只提示关闭窗口不能使移除立即可用。
- **建议改法**：在 manager 按项目 id 把移除的检查与登记提交、打开的解析与建立 `starting` 状态串行化，写表完成前不接纳同 id 的新打开；失败保持原登记与租约。明确拒绝包含 `starting/running/idle-grace/stopping`，UI 显示真实状态与可恢复提示；跨服务端的保证明确限定为本进程管理的代次，不能声称全局停止。验收移除与 bind/acquire 的真实并发、宽限期、停止中、登记写失败和已有租约继续有效。

### P16：继续写作把“打开标签”当作“正文就绪”，失败与迟到定位没有结算合同

- **严重程度**：重要；**类别**：正确性 / 恢复。
- **位置**：计划第 61–70、145、161、166–169 行；`packages/neuro-book/src/plugins/editor/web/commands.ts:36–40,94–99`；`packages/neuro-book/src/plugins/editor/web/area.ts:447–455`；`packages/neuro-book/src/plugins/editor/web/documents/store.ts:601–625`；`packages/neuro-book/src/plugins/editor/web/area.ts:234–280,341–348`；`packages/neuro-book/src/plugins/editor/web/session.ts:56–68`。
- **现象**：计划要求跨页收到 `open` 后打开地址、等文档就绪、调用 `revealEnd`，但没有定义一个可等待的操作状态，也没有规定把资源地址通过 `URLSearchParams` 编码、按当前项目和允许的 Files scheme 校验，还是如何报告非法/跨项目地址。当前命令只校验参数并调用 `area.open`；`area.open` 同步 `groups.open` 后就返回 `{ok: true}`，正文读取随后才由文档协调开始。只有文档为 `ready` 或 `deleted` 时才产生 `ViewBinding`；读取失败会把文档置为 `failed`，不会产生可定位控件。项目会话记录也可能尚未读完，编辑器区此时命令直接 `unavailable`。

### P12：扫描与取数只有频率，缺少可验证的资源上限和退让机制

- **严重程度**：重要；**类别**：性能 / 验收。
- **位置**：计划第 49、51、123、143、181 行；`packages/neuro-book/src/plugins/files/backend/files-service.ts:94–120,134–143`；t72 README 第 40–53 行。
- **现象**：计划承诺“后台、分批读”，但没有并发数、单批字节/计算量、让出执行权、取消及 resync 合并规则。Files 每次正文读取仍要读全文件、解码、核对编码大小并算 hash；统计器还要逐字计数。多个已打开项目分别扫描，事件密集时反复 resync，都会和编辑保存争同一项目进程的 CPU 与 I/O。书架的定时及焦点刷新也没有单次在途限制或旧响应丢弃规则，慢磁盘下可能重复读取全架、迟到响应回盖新值。

- **建议改法**：先给出简单上限：有限并发、读完即丢正文仅保留字数/必要片段、分批让出执行权、逐路径合并和至多一个重扫轮次；停止取消扫描且迟到结果不得提交。书架刷新单次在途、合并定时/焦点触发、按请求代次丢弃旧结果，页面隐藏或卸载时停止。S3 用 t72 同规模样本覆盖初扫、批量外部变化触发 resync、多个项目与扫描中关闭，记录项目进程峰值内存、请求次数、输入/保存及打开耗时，明确可接受的回退幅度；书架另测多作品与慢/失败单项，不把历史 t72 数据当本次通过。
