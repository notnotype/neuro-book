### P1：编辑菜单的焦点条件并不存在，直接取命令可用性无法满足 P09

- **严重程度**：阻断。
- **位置**：计划“P07 与 F04”第 21、34–41 行；“P09”第 68–69 行。证据：`packages/neuro-book/src/plugins/editor/web/commands.ts:55-69`；`docs/specs/workbench/editor.md:56-57`；`docs/specs/workbench/commands.md:66-69`。
- **现象**：计划把 `nbook.edit.undo/redo` 写成“when 读编辑器焦点”，并要求编辑器、原生输入框、别处三种焦点得到不同禁用原因。真实声明只要求 `nbook.editor/active`、`nbook.editor/writable`；编辑器 Spec 明确命令的 `when` 不含焦点，以便命令面板取得焦点后仍能操作活动编辑器。
- **为什么是问题**：仅以 `isEnabled()` 输出生成菜单，焦点在别的输入框时仍可操作最近的活动编辑器。反过来直接把 `focused` 加进 canonical 命令的 `when`，菜单与命令面板夺取焦点后会使它们自己的撤销入口不可用，并破坏现有合同。计划尚未选定菜单的目标语义，P09 无法照字面验收。
- **建议改法**：保留 canonical 命令的活动编辑器语义，在菜单触发宿主明确捕获“打开前的目标/焦点”，决定何时允许执行并给出菜单专属原因；打开菜单、进入子菜单、Escape、执行后还焦点的全过程使用这一目标。若菜单一律操作活动编辑器，则改 P09 明确这一语义，不承诺原生输入框撤销。增加通过点击与 Alt/F10 打开菜单、随后执行撤销的真实场景，不能只在菜单打开前断言 `isEnabled()`。
- **核实**：已核实（合同与代码）；尚未运行浏览器。

### P2：整页导航服务不能兑现“刷新当前页”和“新标签打开文档”的合同

- **严重程度**：重要。
- **位置**：计划第 24、26、78、111 行。证据：`packages/neuro-book/src/shared/host.ts:21-28`；`packages/neuro-book/src/web/host/window.ts:56-61,103-107,205-211`；`packages/neuro-book/src/web/boot.ts:36-52`。
- **现象**：S1 把两条新命令接到 `windowNavigationKey`，但该服务只有 `navigateDocument(href)`，生产实现是当前页 `location.assign`。`location.reload` 只通过 `mountWindowUi` 的独立参数提供给终态页，插件没有此能力；服务也没有新标签页外部导航能力。
- **为什么是问题**：以现有接口直接实现文档命令会离开当前工作页，违反新标签页承诺；刷新也缺少保留当前地址的 reload 宿主端口。若实现时直接读 `window/location`，就绕过计划指定的宿主合同，真实内核的 Bun 测试与非 DOM 宿主不能沿用同一路径。命令完成表示“已请求导航”还是“已导航”也未说明；浏览器的离开确认取消不能由 `location.reload()` 的返回值判定。
- **建议改法**：在 S0/S1 明列最小宿主端口与装配：重载当前文档、用户触发的外部新标签打开；声明文档 URL、开窗拒绝的结果，以及 reload 只确认请求发出。复用编辑器已有 `beforeunload` 结算/确认，不新造第二份离开保护；验收“取消刷新保留正文”“确认后当前 URL 的项目参数不变”“文档打开后原工作页与正文仍在”。新命令的 `effect`、Agent 暴露逐项写明；项目打开已因整页重载中断窗口而声明 `agent: never`（`docs/specs/workbench/commands.md:135`），刷新应采用同一理由。
- **核实**：已核实（合同与代码）；尚未执行导航实验。

### P4：无项目不等于不可保存，P09 会误禁用用户资产文件

- **严重程度**：重要。
- **位置**：计划第 31、34、67 行。证据：`packages/neuro-book/src/plugins/editor/web/session.ts:41-58`；`packages/neuro-book/src/plugins/editor/web/commands.ts:57-60`；`docs/specs/workspace/resources.md:40-48`；`docs/specs/workbench/editor.md:87`。
- **现象**：计划要求未打开项目时“保存等”禁用并说明需要项目；真实编辑器在 `project === null` 时直接建立，`user://` 文件由服务端提供、跨项目共享，并不需要项目绑定。保存只要求活动文档 dirty，全部保存没有项目或活动文档的 `when`。
- **为什么是问题**：未绑定项目的窗口仍可编辑与保存用户文件；按窗口项目空值禁用文件组会移除这一已有能力。反过来若照计划只取 `isEnabled()`，无项目时的“全部保存”仍可用，P09 又会失败。无项目与无活动文档是不同前提，当前模型只有 `desktop` 也不能得出计划声称的项目禁用原因。
- **建议改法**：P09 分开“无项目且无活动文档”和“无项目但已编辑 user:// 文件”。是否可保存按实际文档与命令合同判断，不新增统一的项目门禁；确实只接收 project:// 的入口才给项目缺失原因。补无项目用户文件保存成功与有项目但无活动文档两种验收。
- **核实**：已核实（合同与代码）；尚未运行文件保存实验。

### P5：新显隐命令的必填 part 无法从命令面板执行，参数工厂仍未回答

- **严重程度**：重要。
- **位置**：计划第 34、41、43、77、111 行；Task `README.md:33` 明确要求参数工厂。证据：`packages/neuro-book/src/plugins/commands/shared/registry.ts:309-315`；`packages/neuro-book/src/plugins/workbench/web/commands/panel-commands.ts:5-6,124-140`；`docs/specs/workbench/commands.md:53,139,164`。
- **现象**：新命令写成 `set-part-hidden {part, hidden?}`，只有 `hidden` 可省略，却同时承诺标题栏、菜单与命令面板都走这一条。菜单能力模型只写固定参数，不给 F04 要求的参数工厂或省参交互；已有面板命令能从命令面板执行，是因为参数全可省略并由实现打开选择器。
- **为什么是问题**：命令面板普通候选执行空对象；必填 `part` 会在到达实现前得到 `invalid-args`，无法让用户挑选侧栏/右栏/活动栏。把三个按钮的固定参数照搬到一个候选也没有唯一可选目标。

- **核实**：已核实（严格参数合同与已有模式）；尚未运行命令面板。

### P6：侧栏/右栏的“显示”仍可能保持 0px，布局按钮也没有对应公开状态

- **严重程度**：重要。
- **位置**：计划第 43、77、83 行。证据：`packages/neuro-book/src/plugins/workbench/web/state/layout-store.ts:153-161`；`packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:155-172`；`packages/neuro-book/src/plugins/workbench/web/state/public-state.ts:18-28,37-51`；`docs/specs/ui/workbench-shell.md:73-78`。
- **现象**：计划只承诺把 Part hidden 位写进定制记录，并要求三个布局按钮从公开状态取值。现有 `setPartHidden(part, false)` 不清 `dragCollapsed`；真实 Sidebar 选择入口需要另行把拖到零的位清掉。公开状态目前只有 `panelVisible`，没有侧栏/右栏可见键。
- **为什么是问题**：侧栏或右栏拖到零以后 hidden 为 false，直接据 hidden 切换会先“隐藏”一条已经看不见的区域；随后显示仍是 0px。用户点标题栏按钮不能恢复内容。按钮亮态与菜单勾选态也无法按计划从既有公开键读取，临时直接读布局字段会形成与公开状态承诺不一致的第二套判断。

### P11：按优先级收起还不足以定义可复现的溢出行为，纯文字条目在“更多”里也未定形

- **严重程度**：重要。
- **位置**：计划第 49–55、71、89–91、113、126 行。证据：现有 `packages/neuro-book/src/plugins/workbench/web/components/WorkbenchStatusBar.vue:67-85,108-138` 把项目/布局问题放左、固定面板入口放右；旧 `packages/neuro-book-legacy/app/utils/workbench-chrome.ts:88-110` 已有“溢出时先为 More 预留完整按钮位”的边界规则。
- **现象**：排序规定了 order/id，收起只规定 priority 由低到高；同 priority 收谁、左右两侧是否共同竞争、固定内容与“更多”占多少预算、动态 text/语言/字体变化何时重算，都未定义。合同同时允许无 command 的纯文字，却说被收起条目在菜单里“可点执行”；当单条文字比整个菜单还宽时，“不截断”与不横向溢出的处理也没有约定。
- **为什么是问题**：相同声明集会因交付或测量顺序得到不同可见结果；没有预留 More 自身宽度时最后仍会装不下。左侧声明可能没有实际渲染槽，固定“显示面板”与布局失败的重试入口可能被挤走。把纯信息映射为普通菜单动作又会出现没有命令可执行的假入口。
- **建议改法**：S0 定义左右槽与固定区域的保留预算、More 所属侧/数量和同 priority 的稳定 tie-break（可沿 order/id），测量隐藏条目时不丢尺寸，文本与可见性变化后重算；极长项在溢出层允许换行/滚动而不丢信息。纯信息在 More 中保持不可执行、可读的语义。有 command 的条目明确按命令可用性禁用及原因。S3 覆盖恰好装下、只差一个 More 位、同优先级、两侧竞争、全收起、长文本与开着 More 时更新/撤回；两种贡献点分别验收。
- **核实**：已核实（计划尚未定义这些分支、现有固定区与旧预算模式）；未运行新收起算法。

### P12：Markdown 的“行列”没有坐标定义，也没有可兑现的跳行能力

- **严重程度**：重要。
- **位置**：计划第 60、96、115、127、139 行。证据：`packages/neuro-book/src/plugins/editor/web/components/MarkdownControl.md:32-38`；`MarkdownControl.vue:74-84,168-173`；`packages/neuro-book/src/plugins/editor/web/markdown/source-merge.ts:2-15`；`MonacoControl.vue:140-149`。
- **现象**：计划要求两种控件各自提供 `{line, column}`，但未说明是源文件行、富文本段落还是屏幕折行，是否从 1 起、列按什么单位、选区取哪个端点。Markdown 当前明确不提供行导航；frontmatter 不进富文本，序列化还可能改变行数，位置不能从 ProseMirror 的 doc offset 直接当作源文件行列。风险段又允许拿不到时仅 Monaco 显示，S5 和验收仍写两种控件。
- **为什么是问题**：例如带 frontmatter 的文档，正文第一段在富文本中的位置与源文件行号不同；窗口缩放还会改变屏幕行而不改变源行。仅提供 position 不会让 open-line 可用，Markdown 光标条目可能成为可见但无法兑现的点击动作。一个“出现了第 L 行”的断言不能证明其含义或跳转正确。
- **建议改法**：S0 先选择坐标合同并让显示与导航使用同一套含义。低成本方案是在当前无源映射的 Markdown 控件返回 null，仅对有可靠源位置与 navigation 的控件显示可点击行列；把这一范围明确写进正文与验收。若本 Task 要交付 Markdown 源行列，则先定义并验证源映射与导航，不能用序列化偏移或段落号替代。覆盖 frontmatter、多行段落、软折行、emoji/制表符、选区与 A→B→A，位置变化订阅随绑定切换和卸载释放。
- **核实**：已核实（两种控件与源保留合同）；未运行光标位置实验。

### P13：搜索按钮的 Ctrl+Shift+P 提示与 macOS 实际绑定不符

- **严重程度**：建议。
- **位置**：计划第 34、83 行。证据：`packages/neuro-book/src/plugins/workbench/web/commands/open-commands.ts:17-24`；`keymap.ts:50-73,146-150`；旧 `packages/neuro-book-legacy/app/components/desktop-title-bar/DesktopTitleBarCommandCenter.vue:25-30`。
- **现象**：搜索按钮固定显示 `Ctrl+Shift+P`，实际命令声明是 `Mod+Shift+P`，当前分发在 macOS/iOS 把 Mod 解析为 Meta。旧按钮至少按平台调整修饰键提示。
- **为什么是问题**：macOS 用户按新按钮给出的 Ctrl 组合不能打开命令面板；菜单直接显示原始 `Mod` 文本也不是用户键盘上的键名。另有保存/关闭等键位只定义在编辑器区，命令声明没有 keybinding，不能从全局默认键位推断它们的作用域。
- **建议改法**：搜索按钮与菜单复用同一按平台格式化的键位显示，来源是实际命令声明；局部键位若要显示，保留“编辑器内”的作用域，沿 owner 的局部键位定义读取，不能为了补文案把它们注册成全局键。验收 Windows/Linux 与 macOS 的实际组合和提示一致。
- **核实**：已核实（声明与键位解析）；未运行 macOS 浏览器。
