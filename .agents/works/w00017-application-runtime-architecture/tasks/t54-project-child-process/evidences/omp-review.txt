### 1. [重要] `sameInstance` 的绑定一致性判据没有测试覆盖：变异后内核 264 例全过
- 位置：`packages/nb-runtime/src/remote/router.ts:102`（`bind.project === existing.project.id && bind.generation === existing.project.generation`）
- 现象：把这个比较改成只看 `bind !== null && "generation" in bind`，`bun run --cwd packages/nb-runtime test` 264 例全过。现有 `routing.test.ts` 的 impostor 三例分别是“不同 client 身份”“只带引用不带代次”“不带 bind”，恰好都不覆盖“同 id、同 client 身份、但 bind 是另一个项目或另一个代次”的形状。
- 为什么是问题：这是“绝不把旧绑定改投新代次”在路由侧的唯一防线（节点侧 `#checkBinding` 只保护诚实客户端自己记下的绑定，伪造原始帧可绕过）。路由的实例表经 `instances()` 可见，本机进程可以拿到已绑定窗口的 id 与 client 身份，发同 id 的 hello 请求绑定另一个项目/代次；判据失效时 `#screen` 放行，绑定完成后的复查（router.ts 绑定分支里的 `sameInstance` 复查）同样失效，`#register` 会把成员描述替换为新绑定——原窗口的绑定被改投、原租约释放，之后原窗口重连会一直被 `duplicate-instance` 拒绝。Spec（`plugin-channel.md` 握手第 3 条）明确写了“任一不一致回 `reject {reason: duplicate-instance}`”。第一版信任模型下这是“防误用”而非“防恶意”，但正是 Spec 声明的公开判据。我在 scratchpad 用真实路由 + 伪造 hello 实验确认：正确实现下该 hello 在 `#screen` 被 `duplicate-instance` 拒绝、绑定回调从未被调用；即判据有效，只是无测试守着。
- 如何核实：变异实验（改后跑内核测试全过，已恢复原样，`git status`/`git diff` 确认干净）；scratchpad 的 `impostor-test.ts` 用真实 `createRemoteRouter` + `createLinkPair` 发伪造 hello，观察 `duplicate-instance` 拒绝且 `bindProject` 未被调用。
- 建议改法：`routing.test.ts` 的“同一实例重连接管旧链路”impostor 列表加一例：同 id、同 client、`bind: {project: 其它项目, generation: N}`（N 是已登记成员绑定的代次），断言 `duplicate-instance` 且绑定回调没有被调用、原成员绑定不变。同样补“同项目但不同代次”的 bind 一例。
### 2. [建议] `#spawn` 先交链路后起进程，`Bun.spawn` 抛错时这条链路没有收口
- 位置：`packages/neuro-book/src/server/projects/manager.ts`（`#spawn` 里 `router.accept(child.link, ...)` 在 `Bun.spawn(...)` 之前；`#create` 的 catch 只结算 children 的 create-failed，不关链路）
- 现象：`Bun.spawn` 一旦同步抛错（例如 `process.execPath` 丢失、OOM 类极端情形），`#create` 拒绝、子实例 `create-failed`，但已交给路由的链路留在路由里（Peer 与 link 对象），直到服务端停止 `router.close()` 才释放；对端永不 hello，也没有成员登记，`drain` 不看它。
- 为什么是问题：一条永不关闭的链路对象与服务端同寿命，属资源收口遗漏；也是唯一一处“spawn 失败”没有显式关链路的路径。
- 如何核实：读 `#spawn` 与 `#create`；实验确认入口文件不存在时 `Bun.spawn` 不抛错、子进程以 1 退出（`onDisconnect` → `started: disconnected` → `#create` 正常收口，链路经 `link.closed()` 关闭），所以这条路径实际不可达，仅防御性缺口。
- 建议改法：`#spawn` 里把 `Bun.spawn` 包进 try，抛错时 `child.link.closed()`（或先 spawn 再 accept，保持“先交路由再起进程”的注释语义时补 catch 关链路）。

### 3. [建议] 登记表的条目校验不核对 id 形状，坏表里的任意字符串 id 会被当作合法项目
- 位置：`packages/neuro-book/src/server/projects/registry.ts`（`isRecord` 只查 `id`/`name`/`path` 都是 string）
- 现象：登记表里 `{id: "not-a-uuid", name, path}` 通过结构校验；`resolve("not-a-uuid")` 能匹配它；打开时 `#create` 里 `readProjectIdentity` 与登记不符而 `create-failed`，但 `list()`、`resolve()` 都会把它当正常项目返回给 `nbook.projects` 与 `projectsKey`。
- 为什么是问题：Spec 规定身份是 UUID、坏文件不覆盖且相关操作以 `registry-invalid` 失败；id 形状是这条边界的最后一环，宽松后“半坏”的登记表（schema 对、条目形状松）不会触发 `registry-invalid`，而是带出一个永远打不开的项目。
- 如何核实：读 `isRecord` 与 `read`；`registry.test.ts` 的坏表用例只覆盖“JSON 不合法”与 `{projects: [{id: "x"}]}`（缺 name/path），没覆盖“id 非 UUID 但三个字段都是 string”的形状。
- 建议改法：`isRecord` 里对 `id` 用 identity.ts 已有的 UUID 形状检查（同一正则），不合格整表按 `registry-invalid` 处理；补一条坏表用例。
