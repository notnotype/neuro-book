### T04：内部门面释放测试绕过了内核撤销，真实服务释放后 get 抛错而不是返回最后值

- **严重程度**：重要。**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/settings/shared/instance.test.ts:168`；`packages/neuro-book/src/plugins/settings/shared/instance.ts:285`；Spec `settings/configuration.md:157`；`packages/nb-runtime/src/services/per-consumer.ts:54`。
- **现象**：Spec 承诺服务随调用方入口释放后，get 返回最后值、update 返回 unavailable。现有用例手工建 `createSettingsInstance().facade()` 并直接 `facade.release()`，只断言 update 与监听；产品经 `providePerConsumer` 交出的服务先被内核 revocableFacade 包装。真实插件经 `context.services.require(settingsKey)` 拿服务，关闭它注册所在的子作用域，再调用 get，直接抛 `ServiceRevokedError`（reason= released），连读取方法都取不到。
- **为什么是问题**：公开寿命合同与实际服务装配冲突。内部 helper 的测试不能证明调用方拿到的真实服务有同样行为，测试头部声称真实内核覆盖“同一组行为”也不成立。插件释放期或持有最后只读值的消费者不能按合同使用该服务。
- **如何核实**：`experiments/baseline/packages/neuro-book` 执行 `bun review-contracts.ts`，通过真实 createApplication、插件 register/activate、服务 require 与 `scope.close()` 走完整生命周期；首轮直接访问的脚本退出 1，错误为 `ServiceRevokedError: 服务 nbook.settings/settings 给 x.reader/server#1 的门面已随调用方释放`，栈位于 `per-consumer.ts:56`。脚本随后显式捕获实际错误以继续独立场景，退出 0，get 和 update 都是 `ServiceRevokedError`、reason= released，监听仍未被调用。未直接调用私有内核函数、未伪造消费者身份。
- **建议改法**：沿用已生效的内核统一撤销合同，修正配置 Spec 的释放后读取与 unavailable 承诺，并把寿命测试放到真实插件作用域释放路径。`runtime/services.md:65`、`:104` 明确释放后任何访问抛错；无需另造配置服务寿命或让内部 facade 的行为冒充消费者实际拿到的门面。

### T05：不存在的键被删除时仍创建目录和空文件，测试把副作用写成了通过条件

- **严重程度**：建议。**类别**：正确性。
- **位置**：`packages/neuro-book/src/plugins/settings/backend/layer-owner.test.ts:310`；`packages/neuro-book/src/plugins/settings/backend/layer-file.ts:83`、`:128`；Spec `settings/configuration.md:122`。
- **现象**：用例名称写“删除不存在的键无副作用”，却断言删除后父目录已经出现 `.nbook`，且未检查内部文件。真实窗口调用 `update(setting, undefined)` 删除不存在的用户层键，返回 `{ok:true}`，同时创建 `<状态根>/settings.json` 空文件。拥有者始终 mkdir、取锁、写临时文件、改名，即使 transform 返回原文本。
- **为什么是问题**：Spec 输出 11 明确“删除不存在的键成功、无副作用”；一个本应无事发生的删除主动触碰用户文件系统，当前测试还会阻止实现修正为真正的空操作。这是可观察行为，不是要求断言内部调用次数。
- **如何核实**：`experiments/baseline/packages/neuro-book` 执行 `bun review-contracts.ts`，真实内核窗口、真实远程写入及目录：输出 `deleteMissing.result={ok:true}`、`directory=["settings.json"]`、`file=""`，退出 0；各实例均 closed，临时根已收口。
- **建议改法**：在持锁读取并变换后，新文本与原文本一致时返回成功，不写临时文件；文件与父目录原先都不存在时，删除应在创建之前直接结算。把现有用例改为删除后原目录内容和文件存在性不变，并覆盖现有文件里不存在该键的空操作。

### T01：改名前冲突重做的验收没有对应测试，删除整段冲突检测仍全绿

- **严重程度**：重要。**类别**：测试。
- **位置**：`packages/neuro-book/src/plugins/settings/backend/layer-owner.test.ts:385`；`packages/neuro-book/src/plugins/settings/backend/layer-file.ts:137`；计划 `plan.md:171`；Spec `settings/configuration.md:124`。
- **现象**：计划明确要求“改名前文件被外部改动时重做后两边的键都在”。现有 15 个拥有者用例没有制造读文本到改名之间的外部保存；两个写入进程都遵守同一锁，不能覆盖不走锁的编辑器。实验副本删掉 `layer-file.ts:137–140` 的身份比较、删除临时文件与 `modified` 重试返回后，配置与 store 的 79 例仍全部通过（425 次断言）。
- **为什么是问题**：合作进程的锁和外部编辑器的冲突检测保护的是两条不同路径；失去后一条会把已在核对前完成的外部修改覆盖掉，两边都认为成功。计划列出的这条关键判据实际没有验收，已有“变异覆盖锁”不能证明它。
- **如何核实**：工作树基线执行 `bun test ./src/plugins/settings ./src/shared/settings.test.ts ./src/shared/store/store.test.ts`，79 pass / 0 fail；相同命令在报告同目录的 `experiments/no-cas/packages/neuro-book` 执行，79 pass / 0 fail，5.19 秒。另执行两个目录的 `bun review-cas.ts`：真实窗口调用 update，真实 fs.watch 观察临时文件创建（0 字节）时由外部编辑器式 rename 保存；基线保留 `other/editor="saved"`、退出 0，变异仍报写入成功却丢该键、退出 1。8 MiB 旧文件仅用于放大真实 IO 窗口，没有直接调用内部写函数或伪造帧。变异仅发生在实验副本，原工作树未改动。
- **建议改法**：在原拥有者行为测试中用真实文件事件或 IO 屏障控制一次“旧文本已读、临时文件已生成、外部保存完成、改名前核对”的交错；断言写入键和外部键都保留，并另覆盖 3 次冲突耗尽时 `write-failed`、原文件不被覆盖。保留现有单文件锁，无需新增另一套写入组件。

### T06：50 毫秒与 3 秒的断言取自实现本身，两处延迟变成 10 倍仍通过

- **严重程度**：重要。**类别**：测试。
- **位置**：`packages/neuro-book/src/plugins/settings/backend/layer-owner.test.ts:170`；`packages/neuro-book/src/plugins/settings/settings.test.ts:241`；`packages/neuro-book/src/plugins/settings/backend/layer-owner.ts:29`；`packages/neuro-book/src/plugins/settings/shared/instance.ts:300`。
- **现象**：合并测试按导入的 `RELOAD_DELAY_MS - 1` 和 `+1` 推进，未独立锁定合同的 49/50 毫秒；首快照用 waitUntil 每轮推进导入的 FIRST_SNAPSHOT_MS，也未断言 2999 毫秒时仍等待、3000 毫秒时降级。实验副本把 RELOAD_DELAY_MS=50 改成 500，FIRST_SNAPSHOT_MS=3000 改成 30000，两处各延长 10 倍，配置与 store 的 79 例、425 次断言仍全通过。
- **为什么是问题**：期望值由实现常量算出，测试与错误实现一起移动。50 毫秒影响外部修改延迟，3 秒是明确的启动等待上限；当前测试无法防止首屏停 30 秒或外部编辑延迟 500 毫秒。泛用时钟测试并不保护这两个产品合同值。
- **如何核实**：`experiments/deadlines/packages/neuro-book` 执行 `bun test ./src/plugins/settings ./src/shared/settings.test.ts ./src/shared/store/store.test.ts`：79 pass / 0 fail，4.82 秒。变异只改两个时间常量；没有假计时器或固定等待。
- **建议改法**：按 Spec 独立推进 49、1 毫秒和 2999、1 毫秒；边界前观察未发布/激活未完成，边界后观察最终快照/激活已降级。测试里的期望时间不要从被测实现导入，轮询推进也要有明确总时长边界。

### T03：inspect 的响应式层状态没有验收，移除依赖追踪仍全绿

- **严重程度**：重要。**类别**：测试。
- **位置**：`packages/neuro-book/src/plugins/settings/settings.test.ts:178`；`packages/neuro-book/src/plugins/settings/shared/instance.test.ts:149`；`packages/neuro-book/src/plugins/settings/shared/instance.ts:209`；Spec `settings/configuration.md:118`。
- **现象**：层坏/恢复用例在 waitUntil 中反复直接调用 inspect；从未在 computed/effect 中读取 inspect 并观察同值的 `ok → invalid → ok`。实验副本只给 inspect 加 `pauseTracking()` / `resetTracking()`，保留 get、直接 inspect 和全部文件/订阅逻辑；配置与 store 的 79 例仍全部通过（425 次断言）。
- **为什么是问题**：直接轮询仍能看到最新状态，消费者缓存的 computed 却不会失效，界面会继续显示旧的可写状态。store 的 setting 测试覆盖 get 的响应式值，不能覆盖 inspect 对层状态的独立承诺。
- **如何核实**：`experiments/inspect-untracked/packages/neuro-book` 执行 `bun test ./src/plugins/settings ./src/shared/settings.test.ts ./src/shared/store/store.test.ts`：79 pass / 0 fail，5.18 秒。再执行基线与变异两边的 `bun review-inspect.ts`，真实窗口从配置服务建立 computed、再改真实文件：基线状态序列 `["ok","invalid","ok"]`、退出 0；变异 `["ok","ok","ok"]`、退出 1，而直接 inspect 最终都是 ok、有效值和通知都没变。变异只改变 inspect 的依赖追踪。
- **建议改法**：在现有真实多实例文件坏/恢复用例中建 `computed(() => service.inspect(definition).user.status)`，先求值再保存坏文件、再修回相同值；逐次断言 computed 为 ok/invalid/ok，并断言有效值不变、onDidChange 不触发。这样直接覆盖消费方行为。

### T09：e2e 的控制台错误断言永远看不到后来的错误

- **严重程度**：建议。**类别**：测试。
- **位置**：`packages/neuro-book/e2e/settings.e2e.ts:98`、`:125`。
- **现象**：`const problems = [...watchConsole(a), ...watchConsole(b)]` 在刚注册监听时复制两份空数组；后面的 console/pageerror 只追加到 watchConsole 闭包里的原数组。125 行断言的 problems 从未再被写入，无论页面报多少错误都还是空。
- **为什么是问题**：用例声称验证两窗口切语言无运行错误，但这条判据实际上是常量空数组断言，不能发现变化中的 Vue/浏览器错误。
- **如何核实**：`bun console-check.ts`（在 experiments 目录）保留相同 watchConsole 收集与数组展开代码，通过 EventEmitter 各派发一个 pageerror 和 error console，输出 `assertedProblems=[]`，空数组断言仍通过。此实验只验证 JS 收集逻辑，未运行 e2e、未冒充页面错误复现。
- **建议改法**：分别保留 `aProblems`、`bProblems`，到断言时再合并；或让 watchConsole 接受调用方提供的同一数组。无需增加监控组件。

### T10：产品主题的文字颜色与字体没有计算样式验收，背景也只断言变化

## 异步时序与场地忠实性

- `ScriptedLink` 明确控制同步回调与异步建立结果，只用于确定性状态机；真实 settings.test.ts 没有强制“建立返回前结束”和较旧写结果晚到。头部“同一组行为由 settings.test.ts 覆盖”的表述偏宽。内核已有并本轮执行的两例是立即推送不丢、建立期间订阅方停止后 cancelled；后者不是配置层的 onEnd 先到且随后建立成功返回。恢复/结束的完整契约对照仍应由主 Agent 补齐，不把内部手写时序称为实际产品缺陷。
- `world.ts` 用真实 createApplication、definitionAt、远程节点/路由、真实文件与 ManualClock；位置、项目绑定、时钟与连接状态能力的方向一致。确定的不忠实点是复制的代理允许清单（T07）。项目注册表与进程边界有意缩成场地绑定；它不证明真实项目子进程的全装配。
- `standalone.ts` 是显式离线场地，后端用真实配置拥有者、窗口在远程层不可达时按默认值；没有返回假的成功配置结果。`settingsBrowserCore` 复用完整插件的同一个核心入口，只剔除需要工作台选择服务的命令入口，产品仍用完整定义；不把它定为产品后门。
- 示例 Stage 的 definitionAt、宿主时钟、连接能力与 product delegatingPlugins 均复用，额外测试代理显式追加；33 例中的示例场景已执行。未发现把 mock、spy、假计时器或非零固定等待混入本次配置/主题新测试的命中。
