## 审查发现（按影响排序）

### F01｜阻断｜正确性：合法 JSONC 删除会写出坏文件，保留承诺超出库能力

- **计划位置**：关键设计“3. 层与文件”（42、45 行）；验收映射“单键编辑”（134 行）。
- **现象**：按计划直接使用 `modify` + `applyEdits` 删除唯一且有尾随逗号的配置，输出非法 JSONC；删除首项还会删掉下一项前的注释。新增键可重排整个单行对象，库不保证“只改这个键所在文本、保留其余注释与缩进”。
- **为什么是问题**：`update(setting, undefined)` 是公开操作；输入格式又明确允许尾随逗号。照本设计成功改名后，自己的层就成为 invalid，后续所有写入被拒。只测试替换字符串值会漏掉这条数据损坏路径。
- **依据**：实验一，`jsonc-output.json` 的 `trailingComma/delete`、`keyComment/delete`、`inlineOther/insert`；真实 `jsonc-parser@3.3.1` 与计划指定 Bun。VS Code 当前 `src/vs/base/common/jsonEdit.ts` 35–38 行对空文档删除直接返回空 edits，61–67 行另有“删除唯一节点尾逗号”的扫描补偿，而 npm 库实测没有这个结果；55–60 行仍会把首项到下一项 offset 的注释一并删去。计划“同一个库”的表述不能推出行为一致。尚无 nbook.settings 实现，结论针对计划依赖的算法与合同。
- **建议改法**：单键编辑之后、写盘之前再次解析并校验根对象与重复键，不合格绝不落盘；修正末项删除时逗号范围。明确注释保留的边界与缩进探测，加入唯一键+尾逗号、首/中/末键删除、相邻注释、tabs/4 空格用例；无需另建通用 JSON 编辑框架。

### F11｜阻断｜健壮性：首快照等待没有实际截止，计划引用的激活期超时不覆盖订阅

- **计划位置**：“4. 每个实例的有效值与服务”就绪（67 行）；“风险”浏览器等待快照（167 行）；验收映射就绪与降级（140 行）。
- **现象**：计划把“等第一快照或订阅失败”描述成有内核激活期上限、超时默认继续；真实 subscribe 没有 timeout 参数，也没使用 maxActivationCallMs。提供方激活迟迟没完成时，调用方 settings 激活和依赖它的工作台一直等；订阅接受了却迟迟不发首快照同样没有请求超时可接管。
- **为什么是问题**：这是首屏可用性的承诺，不能只作为“服务端慢时首屏推迟”的风险说明。正常非默认文件路径测试与立即 not-provided 测试都无法证明有限时间降级；死等时连“配置不可达”的诊断也不出现。
- **依据**：实验七已在真实激活路径推进时钟超过上限后复现等待，提供方恢复后激活成功；`packages/nb-runtime/src/remote/contract.ts` 191–196 行 subscribe 选项只有 onResync/onEnd；`node.ts` 599–600 行只有请求接上激活上限，636、1009–1011 行订阅不接；`peer.ts` 150–176 行同样没有订阅计时。
- **建议改法**：给 settings 的每层首基线就绪加一个局部、可注入时钟的截止，明确订阅拒绝、建立期间结束、已接受但首快照没到与超时均如何结算。截止后按已批准的降级继续、保留 late baseline 恢复机会；补订阅未接受和接受后无快照两种真实内核场景，恢复时与 F06 的缺失订阅策略衔接，停止时取消截止/释放句柄。不扩大成内核全局超时重构，也不改变“get 同步不失败”的已定方向。

### F08｜阻断｜正确性：两个主题命令使用未登记的命令域，Agent 路线也未定暴露与结果转换

- **计划位置**：“6. 使用者一：界面语言”命令（82 行）；“7. 使用者二：主题”命令（90 行）；Spec 与文档改动表“commands.md”（108 行）。
- **现象**：`nbook.workbench.switch-theme` 与 `nbook.workbench.switch-appearance` 的 domain 是 workbench，现有域词表只含 view/editor/edit/quick-open/settings/account/project/app/help，会返回“未登记的命令域：workbench”。计划没有修词表，S0 对 commands.md 只写了翻译原因；三条命令没有列 effect、agent 暴露、严格 args 与 settings 失败→CommandResult 的映射。
- **为什么是问题**：照计划命名则两个命令不会进入命令表，首页与无项目窗口都无法通过命令切主题。Agent 即使带参数，默认 exposure=never 也先返回 not-exposed；默认改成 confirm 又会因产品没有确认通道返回 confirmation-required。直接返回 SettingsWriteResult 也不满足命令系统的失败合同，write-failed/layer-invalid 等会被折成 execution-error，原因可能丢失。
- **依据**：实验六通过真实 register/execute 复现命名拒绝与默认 not-exposed；`workbench/commands.md` 输出“结果合同”“参数校验”“暴露”、域词表（118 行）、安全“暴露默认关闭”；`src/plugins/commands/shared/registry.ts` 74、114–128、132–136、298、313–314、341–347 行；`shared/contracts.ts` 的 CommandResult/CommandFailureCode。结果映射与无 UI 分支仍属计划缺项、代码推断，未运行未来 handler。
- **建议改法**：优先沿用已登记的 settings 域，提供方仍是 workbench（内置命令域不等于插件 id），不新增域；命令表补三条精确 id、可选参数、effect=write、允许的 agent 暴露与参数缺省时的 UI 路线。带参数直接写，不依赖 QuickPick；缺参数而无 UI 明确 unavailable/取消无副作用。显式把失败转换成命令合同、保留原配置失败码/detail 在 reason/业务结构中，unknown-outcome 不自动重试。加入 Agent 带有效/非法参数、无面板、写失败的真实命令执行测试。

### F02｜重要｜正确性：原子替换绕过只读文件，与验收要求直接矛盾

- **计划位置**：“3. 层与文件”写入（45 行）；验收映射“只读文件为 write-failed 且快照不变”（135 行）。
- **现象**：真实 `0444` 文件在可写目录中被临时文件改名成功替换，内容改变且 mode 变成 `0644`；系统不会为这条写入路线报 `EACCES`。
- **为什么是问题**：照字面实现达不到验收，且会取消用户通过权限设置的保护。只读目录与只读文件必须分开测试，不能用前者冒充后者。
- **依据**：实验二 `readonly-file-direct-write`、`readonly-file-atomic-replace`、`readonly-directory-atomic-replace`。普通用户真实 Bun 文件 API，不是 root 下的无效 chmod 测试。
- **建议改法**：既然已承诺只读文件拒写，在替换前核对现有目标的可写性；新临时文件沿用原文件 mode。真实只读文件与只读目录各一例；测试明确普通 POSIX 用户前提，不按错误文案分支。失败不动原文件与快照。

### F03｜重要｜正确性：缺失目标和悬空链接没有定义读写结果

- **计划位置**：“3. 层与文件”落点与写入（41、45–46 行）；验收映射“新文件、符号链接”（134–136 行）。
- **现象**：最终目标不存在时 realpath 无法解析，`ENOENT` 与普通文件缺失相同；文件读不到，但 symlink 仍在。计划一面说不存在等于空层、首次写才创建，一面只描述 realpath 最终目标后的写法。
- **为什么是问题**：若把 ENOENT 一律当作不存在并直接 rename 到 `settings.json`，会覆盖 dotfiles 的链接；若一律拒绝，普通首次保存也失败。链接目标晚出现、消失后重建、链接被重指向时何时重绑目标监视同样不明确。
- **依据**：实验二 `target-deleted-realpath/read/atomic`、`plain-missing-realpath`、`dangling-missing-parent-realpath`。已有目标的成功路径与链接保留也已实测。
- **建议改法**：用 lstat 区分普通缺失与悬空链接。最小合同：普通缺失可创建；悬空链接保留并拒写，返回明确 detail、不替换链接；目标恢复/链接重指向后重新解析与更新目标目录监视。若产品要求创建悬空目标，再显式实现有环检测的 readlink 解析，勿以 realpath 已覆盖为依据。

### F04｜重要｜正确性：只监视当前目录不足以覆盖首次缺目录与删除重建

- **计划位置**：“3. 层与文件”首次写入与外部监视（41、46 行）；风险只列网络文件系统/容器限制。
- **现象**：`fs.watch(不存在的目录)` 抛 ENOENT；监视目录删除不会可靠地以 error/close 告知，旧 watcher 不跟随同一路径的新目录。计划没有目录缺失、父目录变化、watcher 重绑的步骤。
- **为什么是问题**：`.nbook` 来自仓库时可被切分支/整体替换；dotfiles 目标目录也可删除重建。这发生在本机普通文件系统，不属于计划声明的网络盘限制。初始化直接 watch 缺失目录可能使设置入口失败；运行中重建则可能永久停在旧设置直到重启。
- **依据**：实验三 `missing-directory-watch`、`delete-watched-directory`、`recreate-watched-directory`、`rearm-after-closing-old`；`runtime.projects` 输出 1/输入说明正常登记创建 `.nbook`，但失败与恢复允许运行中项目目录被移走/删除，各插件须处理自己的错误。VS Code `configurationModels.ts` 563–568 行使用的是具备宿主文件服务的目录+资源 watch，不是裸 fs.watch 能力的证据。
- **建议改法**：明确监视生命周期：目录不存在时不为读配置创建目录，监视最近存在的父目录；目标目录删除或路径身份改变时先关闭旧 watcher，再按当前路径重建，并重读基线。监听 filename 缺失时也重读，不能只按精确名字筛选。验收加“目录缺失→外部创建”和“.nbook 删除→重建→再次修改”，覆盖恢复后的第二次编辑。

### F05｜重要｜正确性：按有效键比较会吞掉 invalid 与恢复的层状态变化

- **计划位置**：“3. 层与文件”层快照与外部修改（44、46 行）；“4. 每个实例的有效值与服务”inspect（57–60 行）；验收映射“修好坏文件后恢复”（136 行）。
- **现象**：好文件 A → JSON 语法错误 → 修回 A，invalid 明确保留 A 的 values；两次转变均没有键值变化。如果按 46 行“逐键比较，只有变了才推新快照”实现，窗口拿不到 invalid/detail，也拿不到恢复。非法值 problems 改变但有效值不变时同样漏报。
- **为什么是问题**：拥有者会拒写 layer-invalid，而窗口 inspect 仍说 ok；修好后窗口也无法观察写入能力恢复。“外部修改即时生效”的合同同时包括可写状态。只等最终 value 正确的测试对此是空证明，因为 value 在错误前后都没变化。
- **依据**：计划自身层模型与通知条件；实验一 invalid 的部分解析结果说明不能只比较值；`docs/testing/README.md` 12、22、42 行要求失败、恢复与订阅顺序是验收清单。此条是计划逻辑矛盾，尚无产品实现可运行。
- **建议改法**：拥有者对完整公开层状态（status、values、problems/detail）比较与发布，内容相同只抑制重复；实例缓存仍须应用状态变化，使下一次 inspect 返回最新状态，onDidChange 只通知有效值变化键。补“有效 A→坏 JSON 保留 A 且 inspect=invalid/写拒绝→修回 A 且 inspect=ok/可写”的真实文件、多实例用例。

### F06｜重要｜正确性：首次订阅失败后的降级没有恢复路线，不能依赖内核自动重建

- **计划位置**：“4. 每个实例的有效值与服务”就绪（67 行）；验收映射“拥有者不可达→默认→断线重连”（140 行）。
- **现象**：真实内核只自动重建已成功登记的活动订阅。第一次建立返回失败后，连接恢复不会补建它。计划把“失败按默认继续”接到了“内核重建订阅”，两者没有实际桥梁。
- **为什么是问题**：握手后设置入口激活前掉线、或首次层订阅失败，会使已启动窗口永久使用默认语言/主题，而其它窗口正常；用户看到恢复在线但设置仍不恢复。正常已建立订阅断线测试抓不到这条路径。
- **依据**：实验四；`packages/nb-runtime/src/remote/node.ts` 636–648 行失败直接返回且只有成功才登记，1070–1086 行只遍历已登记项；真实产品窗口先握手后建运行实例，链路在其间或插件激活时切断是可出现的时序。`runtime/plugin-channel.md` 的订阅与重连保证只针对活动订阅；服务端重启/项目代次结束按其场景 11、15 是终态，不能归入同一次恢复。
- **建议改法**：为首次失败的层明确恢复策略：设置插件在宿主恢复在线时重新建立缺失订阅，活动订阅继续由内核重建；或保持 settings 未就绪并由已有宿主失败/重试路线恢复，若改变已承诺降级须重新明确。不要另造定时重试体系。补“握手成功→首订阅前掉线→降级→恢复→收到非默认快照”与首事件先于建立返回的测试；服务端重启与 project-gone 只停止/刷新，不重投新代次。

### F07｜重要｜正确性：删常量不能完成动态语言，打开中的选择请求与 Lab 面板缺少语言输入

- **计划位置**：“6. 使用者一：界面语言”（81–83 行）；验收映射“切换语言后命令面板文案即时变化”（143 行）。
- **现象**：七个 DISPLAY_LOCALE 命中文件中，Lab 的两个调用被改成 Lab 常量，但同一 Lab 场景还挂载真实 `WorkbenchCommandPalette.vue`，后者计划改成读产品设置；既有 props 只有 host，没有 locale 输入。产品的“打开项目”已经打开时，QuickPickRequest 的 title/placeholder/empty/items.detail 已经是字符串快照，语言切换不重新生成它们。
- **为什么是问题**：让面板直接依赖 settingsKey 会破坏 Lab 不读产品配置的合同/局部挂载；只把文本 helper 内的常量改成 get，也不会使已创建的字符串变语言。另一窗口/外部文件切语言时，当前窗口能出现英文面板 chrome + 中文标题/提示的混合状态。
- **依据**：`src/plugins/workbench/web/components/WorkbenchCommandPalette.vue` 21、74–94、155–157 行与同名 `.md` 数据合同；`src/plugins/projects/web/open-project.ts` 34–49 行将标题与候选说明折成字符串；`workbench/shared/contracts.ts` 38–45 行 QuickPickRequest 是字符串，`palette-host.ts` 49–56 行保存请求；`src/plugins/lab/web/fixtures/command-scene/lab-command-scene.ts` 与 `LabCommandSceneLayer.vue` 挂同一产品零件。`ui/component-lab.md` 输出 4–5（68–69 行）、副作用与数据禁止产品配置；计划本人也承诺 Lab 常量。代码推断；本次未运行 UI/e2e。
- **建议改法**：从工作台宿主传入响应式 locale 给 PaletteHost/面板，Lab 传自己的常量，文本 helper 接 locale 参数、保持无全局状态。选择请求保留 LocalizedText 到渲染时再 localize，或持有 getter 重算当前请求；无需在共享零件注入整个设置服务。测试面板与项目选择已打开时从另一窗口/真实外部文件切语言，保留输入与选择、所有当前可见提示都更新；Lab 使用常量不受影响。`commands/shared/plugin.ts` 31–34、53 行的缺声明/类型错误与默认不满足原因也是中文字面值，应纳入现时原因翻译；已记录的诊断与历史审计保留发生时文本即可。

### F09｜重要｜使用者落地：产品首页不在语言常量清单内，也没有消费产品主题变量

- **计划位置**：“6. 使用者一：界面语言”（81–83 行）；“7. 使用者二：主题”（87–89 行）；验收映射语言、主题（143–146 行）。
- **现象**：首页 `createEmptyWorkbench` 仍直接渲染“工作台已就绪。没有打开项目。”或“工作台已就绪。当前项目：…”，这些字符串不会被 DISPLAY_LOCALE 搜索覆盖。首页与启动失败页共用宿主 CSS；首页没有背景/前景主题变量，文档根 font-family 也使用系统字体而未消费 `--font-ui`。nb-ui 的 `.nb-ui-colorway` 只设置 color-scheme，不自动为页面填背景与文字颜色。
- **为什么是问题**：切成 en-US 后当前产品的唯一正文页面仍是中文；同为 light 或同为 dark 时切 nbook/macOS，不足以使首页背景、正文与字体随主题变化。只断言 data-nb-theme/data-nb-appearance 通过，不能证明用户看到了产品主题。系统明暗可能改变 UA 默认底色，但那不是主题包提供的配色。
- **依据**：`src/plugins/workbench/web/empty-workbench.ts` 11–20 行；`src/web/styles.css` 25–57 行；`src/web/boot.ts` 7–12 行；`packages/nb-ui/src/styles.css` 18–20 行；`theme/system.md`“消费规则”。这是从真实消费者与 CSS 推断的接入缺口；按审查限制未启动页面，未做视觉验证。
- **建议改法**：给已有首页传入响应式显示语言，并在渲染时取 LocalizedText；把产品页的字体、背景、文字颜色改为消费 nb-ui token，宿主启动/失败页保留原来的独立样式边界。验收在命令面板关闭后检查真实首页正文与计算样式，覆盖 nbook/macOS 各明暗、无项目/绑定项目，不能只查 html 属性。与 S6/S7 同片完成，不扩大到工作台外壳重设计。

### F10｜重要｜可测试性：只等通知不能验收“不重复”与截断恢复，缺少可排空的重读边界

- **计划位置**：“3. 层与文件”50 ms 合并（46 行）；S3 自跑验证（119 行）；验收映射“先截断再写入时最终值正确”“监视回传不重复通知”（136 行）。
- **现象**：正向 waitUntil 可以等新值出现；没有重复事件这个否定判据不会等出一个成功信号。update 已应用新值后立刻数通知，watch 回传和 50 ms 计时可能尚未开始，错误实现也会通过。截断与写入连在一起又可能合并为一个文件事件，未实际覆盖空文件读取分支。
- **为什么是问题**：计划明示不用固定等待、逐项做变异检查，但缺少时钟注入与重读完成的边界。将 50 ms 改成 0 或重复推送的变异，未必使这些测试失败；只读文件若在 root 环境跑 chmod 也可能不是有效权限测试。
- **依据**：实验三已观察截断空内容与事件合并；实验五以真实文件事件配合现有 ManualClock 跑通 49/50 ms、长截断间隔、同内容读取完成后不再通知。`docs/testing/README.md` 18、20、22、24 行明确允许注入时钟、要求资源收口、异步建立两种顺序与变异检查。不是建议 fake timers 或 mock fs.watch。
- **建议改法**：S3 拥有者接收 RuntimeClock（默认 systemClock）；在真实文件通知→调度→完成重读之间提供可等待的内部异步边界，由测试支持场地封装，不增加产品远程接口。纯合并算法以时钟推进验证，真实 watch 合同用真实保存方式等有效快照；对“自身回传不重复”等待同内容重读排空后再数通知，对截断分阶段明确完成一次空内容重读再写最终值。首快照先于 subscribe 返回、建立期间结束及停止时取消 timer/watcher 也加入验收；权限测试明确非 root 条件、只读文件与目录分别覆盖。

### F12｜建议｜文档与落地边界：新设置定义入口没有纳入既有导入规则与文档改动表

- **计划位置**：“2. 声明”一份常量三处使用（34 行）；“Spec 与文档改动（S0）”（99–110 行）。
- **现象**：计划让别的插件运行时引用对方 `shared/settings.ts`，但当前应用包 `AGENTS.md` 13–15 行、ADR 0026 决策 2 和 `architecture.test.ts` 77、96–97 行只允许对方 `shared/contracts.ts`；计划括号里的 ADR 0025 已被 ADR 0026 取代，旧文也没有允许 settings.ts。S0 没列这些位置。`docs/modules/monorepo-boundaries.md` 49 行甚至仍写不能在运行时 import 其它插件模块，与允许公开合同的当前裁决不一致。
- **为什么是问题**：设置定义成为新的共享运行期入口后，消费者会直接违反现有架构门禁；只改新 Spec 没有完成合同与治理的一致切换。文档表也没列被改组件的同名 `.md`（至少 WorkbenchCommandPalette 的语言输入）。
- **依据**：上述真实规则、架构测试与 ADR；依赖核对结果为 `packages/neuro-book/AGENTS.md` 21 行规定后端导入包放 dependencies，37 行只要求新前端第三方包进入 optimizeDeps.include，因此 jsonc-parser 按计划仅用于后端时应放 dependencies、更新根 bun.lock，**不需要**把它加入浏览器预构建或另造依赖登记表。
- **建议改法**：优先把供其它插件消费的设置定义并到既有 `shared/contracts.ts`，沿用一个公开入口，描述与插件实现取同一份定义；若坚持独立 settings.ts，明确修订 ADR/包规则/架构门禁并说明为何值得第二个公开入口。S0 加包入口、monorepo 边界的过时条款、受影响组件同名文档；S2 依赖与锁文件沿用现有规则，不扩大依赖到内核或浏览器。

## 场景核对

以下是合同推演，非 settings 产品运行结果；直接测得的原语行为已在实验节标明。

| 实际场景 | 结论与补齐点 |
|---|---|
| 首次启动没有 settings.json | 缺失文件作为空层、读时不创建文件合理；首次新增键的库能力已实测。缺失父目录不能直接 watch，普通缺失与悬空链接必须区分（F03、F04）。首次删除不存在键应明确为无副作用成功，不借删除空文档的异常实现。 |
| 编辑器把 JSON 改坏又改回 | 保留 last-good、拒绝在坏文件上写入合理；修回同一有效值时也必须传播 invalid→ok，否则 inspect 的写入状态一直错误（F05）。空文件确实能出现在截断保存中，50 ms 只能合并事件，不能保证每次都读到最终文本。 |
| git pull / 切分支整体改项目层 | 有效的项目层随外部内容更新；未知插件键保留、只允许用户层的键在项目层丢弃，合同明确。文件替换与 .nbook 整体删除重建须分别覆盖（F04）；命令仍按当时来源层写。不要为读配置创建缺失的 .nbook，项目目录登记与身份创建归项目管理器。 |
| 两个窗口同时切换主题 | 同一用户层由一个服务端拥有者串行，同一项目层由一个项目代次串行，最后处理的写入胜出，订阅最终一致，结构足够。update 成功后“自己的 get 已更新”只在该层此刻仍是有效来源时成立；显式写 user 而被 project 覆盖，应验收持久层更新且有效值保持项目值。加不同键并发不互相覆盖、旧写结果晚于新快照时不倒退。auto 依据调用窗口缓存选层，外部改动恰在选择与写入之间属于另一个时序边界，不能宣称用户层/项目层选择具有跨进程事务性。 |
| 已建立订阅的窗口断线重连 | 实验四证明同代次活动订阅由真实内核重建；新基线须按 owner 启动标识与序号防倒退。首次失败的订阅是另一条路径，必须显式补建（F06）；首基线等待还需实际截止（F11）。 |
| 服务端重启 | 已有宿主转入 server-restarted 终态并要求刷新；不能让旧节点自动改投新服务端。设置缓存仅支撑停止前的同步读，在途写依真实 remote 结果结算，unknown-outcome 不自动重发。刷新后从新的拥有者重读用户文件。依据 remote-session.ts 4–6、21–22、82 行与 plugin-channel 的代次合同。 |
| 项目子进程宽限期关闭后再打开 | 旧窗口重连得到 project-gone；新窗口取得新代次、从项目文件读新基线，文件数据保留。设置 watcher/timer/订阅由本代次收口，不能跨代次复用；这继承 runtime.projects 输出 5、7，不需要设置插件另起项目保活机制。 |
| 语言切换时面板、项目选择与提示已经打开 | 当前文本应按新 locale 重算，保留查询/选中项；已有 QuickPick 字符串快照和共享 Lab 面板必须调整（F07）。首页正文也应翻译（F09）。过去的诊断/审计无需追溯翻译，当前不满足原因须按新语言重新求值。 |
| appearance=system，系统明暗变化 | 读取 matchMedia 的当前 matches，监听 change 后只更新文档明暗与主题默认配色，不把 system 改写成 light/dark。显式 light/dark 不随系统变。监听由产品页面持有；切换到 Lab 或卸载后不再写文档根。验收系统变化发生在 Lab 显示期间与返回产品后的最新 matches；本次未运行浏览器。 |
| Lab 页面打开时另一个窗口改产品主题 | Lab 的偏好独立，产品配置缓存可以更新，但产品页面未挂载时不应改 html/body。离开 Lab 的 reloadOnLeave 会重新按最新产品配置启动。现有 lab/web/plugin.ts 14–16、LabShell.vue 595–599 与 workbench/shared/contracts.ts 19–23 支持此生命周期；抽取共用应用器时别共享当前偏好或全局清理归属。语言共享面板的隔离另见 F07。 |
| 服务端插件与绑定窗口读到同一键的不同值 | 服务端只用 defaults+user，绑定窗口再用允许的 project，差异是明确合同。例：用户 nbook、项目 macos，服务端和无项目窗口为 nbook、绑定窗口为 macos；locale 仅 user，所以项目中的 locale 被丢弃。服务端要操作某窗口命令时应调用那个窗口的命令服务，不拿自己的值推测目标窗口值。 |
| 无项目窗口执行切换主题 | auto 应选 user，两套主题都可使用，无需打开项目；显式 project 写返回 no-project。目前计划的命令 id 登记失败（F08）；改名后需通过真实命令管线验证文件落点、当前页外观与其它无项目窗口收到变化。 |
| Agent 带参数切换语言 / 主题 | 现有命令管线足够；严格 schema、effect、expose.agent、失败转换必须明确。有效参数不打开选择 UI；非法参数无写入；discuss/plan 返回 read-only。实验六只验证了 registry 门禁，没有运行未来的写配置 handler（F08）。 |

## 验收补齐与测试边界

- 文件解析再加：空文本、纯注释、嵌套重复键的边界、未知键保留；首次缺失文件做删除不能生成空文件或把 undefined 发成非法 JSON。后端 remote 写入须以可序列化的操作表达删除，不能依赖 JSON 编码保留 undefined；具体远程 payload 尚未写出，需在 S2 合同与 S4 真实 JSON 链路测试中落定。
- 文件落盘与监视增加 F01–F05 的真实场景；监听缺 filename 的处理只检查分支正确性，不声称本机 fs.watch 会产生该事件。同内容抑制要先完成对应重读；50 ms 边界用注入 RuntimeClock，真实文件事件无需固定等待。
- 多实例增加：同键与不同键并发、项目覆盖时显式写 user、旧结果晚于新订阅快照、未知结果与已落盘基线相遇；首次建立失败和活动订阅重建分测，首快照早于/晚于 subscribe 返回、建立期间 onEnd、停止后的晚回调均收口。
- UI 增加 F07、F09 的已打开状态与真实首页消费；system 从初始值到变化、切到显式明暗后再触发系统变化、Lab 显示期间外部切主题、返回产品读取最新配置。既有 Lab e2e 可以保留，新增产品用例必须覆盖主题所有权切换，而非只看根属性。
