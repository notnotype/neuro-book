## 已核实发现

### UI-01：关闭标签和组后焦点丢到页面根

- **严重程度**：重要；**类别**：正确性 / 可访问性；**核实状态**：真实产品浏览器已复现。
- **位置**：`packages/neuro-book/src/plugins/editor/web/area.ts:350`（`closeTab`）；`src/plugins/editor/web/components/EditorTabBar.vue:55`（Delete 只发关闭意图）。以上均相对于审查 worktree。
- **现象**：真实 Files 项目打开 `a.md`、`b.md`，聚焦 `b.md` 标签并按 Delete。标签关闭、`a.md` 被激活，但 `document.activeElement.tagName` 为 `BODY`。随后在 `a.md` 拆分两组，聚焦当前组唯一标签并按 Delete，组数从 2 变 1，焦点仍为 `BODY`，没有进入存活的相邻组。
- **为什么是问题 / 依据**：键盘用户关闭后失去所在编辑器的操作位置，后续方向键、Delete 和编辑器区内 Ctrl+S/W 不再作用于邻接标签。`docs/specs/workbench/editor.md:85`（输出 3）明确要求空组关闭后焦点到相邻组；`docs/standards/code/components.md:48` 和 `docs/standards/code/frontend.md:62` 要求出现/消失的焦点交接可用。
- **如何核实**：生产构建，产品服务 HTTP `45199`，内置 Chromium 的真实 click/focus/Delete；以 DOM 标签数与活动标签等待，不用固定等待。观测结果：关闭前 `BUTTON / project://notes/b.md`，关闭后 `BODY / activeTab=project://notes/a.md`；关组后组数从 2 变 1，焦点为 `BODY`。现有 `EditorTabBar.dom.test.ts:53` 只检查 emit，`e2e/editor-area.e2e.ts:156` 只检查标签/组数量，没有断言实际焦点。
- **建议改法**：关闭完成后由视图宿主按关闭目标选择仍存在的右侧/左侧标签或相邻组的活动控件，等待 DOM 更新再聚焦；取消关闭保留原焦点，异步保存期间用户移到其它区域时不抢焦点。给现有真实浏览器关闭场景加焦点及下一次键盘动作断言。

### UI-02：Monaco 未编辑文件切换后变 dirty，保存删除 BOM 或改写混合换行

- **严重程度**：重要；**类别**：正确性；**核实状态**：真实产品浏览器与真实磁盘字节已复现。
- **位置**：`packages/neuro-book/src/plugins/editor/web/components/MonacoControl.vue:38`、`:79`（`ITextModel.getValue()`），`:65`（原文交给 Monaco 模型）。
- **现象**：真实文件 `data/bom.txt` 初始为 `EF BB BF` 加 `甲\r\n乙\r\n`，用源码编辑器打开，不输入；切换到其它标签后 `bom.txt` 出现未保存标记。切回后 Ctrl+S，磁盘字节变为 `[231,148,178,13,10,228,185,153,13,10]`，初始三个 BOM 字节消失。
- **为什么是问题 / 依据**：Monaco 模型把 BOM 单独保存，默认 `getValue()` 不包含 BOM；结算把它与含 BOM 的权威原文比较，误判为用户输入并提交。无编辑的浏览产生修改，保存破坏原始字节。`docs/specs/workspace/files.md:57` 要求 UTF-8 BOM 保留、未改内容的读写往返字节不变，`:109` 要求浏览不改变文件内容；编辑器不能在进入 Files 保存前先把原文改掉。
- **如何核实**：产品页通过资源树双击 `bom.txt`，未输入，点 `a.md` 标签再切回，Ctrl+S；用 `Bun.file(.../runtime/Book/data/bom.txt).arrayBuffer()` 读真实磁盘。打开时 dirty=false，切换后 dirty=true，保存后 BOM 消失。源码核对两处 `getValue()` 都未传 `preserveBOM=true`。
- **同边界的第二个真实 Files 复现**：`data/mixed.txt` 原文 `甲\r\n乙\n丙\r\n`，打开不输入、切到其它标签后也变 dirty；切回 Ctrl+S，真实磁盘变成 `甲\r\n乙\r\n丙\r\n`。Monaco 的模型原文与磁盘原始字节不能直接用默认 `getValue()` 等同，混合换行同样被结算伪造成用户修改。
- **建议改法**：提交及结算统一保留 BOM（Monaco `getValue(undefined, true)`）；结算应只提交真实用户变更，不以模型规范化后的全文与原始字节差异推断输入。对混合换行保留源映射/原文合并，让未编辑部分仍沿原始换行；至少覆盖 BOM 与混合换行文件的“不输入、切换、保存，磁盘字节不变”真实浏览器场景。

### UI-03：外部删除后的文档仍接受编辑，没有转为只读

- **严重程度**：重要；**类别**：正确性；**核实状态**：真实 Lab 的 Monaco 与真实 Files 产品的 Markdown 均已复现。
- **位置**：`packages/neuro-book/src/plugins/editor/web/documents/store.ts:345`（`writable` 把 `deleted` 当作可编辑）；`src/plugins/editor/web/components/EditorGroup.vue:113`（该值原样传入两种控件）。
- **现象**：Lab `EditorArea/split` 打开真实 Monaco 控件的 `设定.json`，点外部删除，出现“文件已被删除。关闭会丢弃保留的正文。”；点击正文，Ctrl+End 并输入 `deleted-edit`，正文变为 `{…}deleted-edit`，标签变 dirty，状态条改称“保存会在原位置重新创建它”。
- **为什么是问题 / 依据**：`docs/specs/workbench/editor.md:106`（输出 18）明确规定外部删除后标已删除并只读、保留正文，只允许原有 dirty 保存重建；输出 20 也要求只读视图不接受输入。当前判据让本应只读的删除态成为正常编辑态，两种控件均受影响。
- **如何核实**：真实 dev Lab `45403/lab?c=EditorArea&s=split`，通过场景控件触发适配器契约内的外部删除，再真实键盘输入；读取可见 JSON 正文与 dirty 标记。输入前原文是 JSON 三行，输入后可见末尾 `deleted-edit`。不是直接调用编辑器内部函数制造时序。
- **补充真实 Files 复现**：在报告目录内真实项目删除 `notes/close.md`（Node `unlink`），产品文件监视到达已删除状态后，以真实键盘追加“仍可写”。可见正文由“关闭测试1”变为“关闭测试1仍可写”，`contenteditable` 仍为 `true`。确认不是内存适配器单独造成的偏差。
- **建议改法**：把“允许输入”与“删除后仍可保存重建”分开；视图可写仅 `status === ready && ended === null`，删除态保存重建逻辑继续保留。切只读前同步结算已产生的输入，并在产品的外部删除场景断言两种控件的新输入均被拒绝。

### UI-04：800 ms 慢读进度条透明且被读屏隐藏；Monaco 光标也未消费正确 token

- **严重程度**：重要；**类别**：正确性 / 可访问性；**核实状态**：真实 Lab 浏览器已复现。
- **位置**：`packages/neuro-book/src/plugins/editor/web/components/EditorGroup.vue:89`、`:90`；同一错名 token 也用于 `src/plugins/editor/web/code/monaco-theme.ts:32`。
- **现象**：Lab `EditorArea/live` 选择“扣住读取”，点击“打开设定.json”。800 ms 后 `[data-editor-progress]` 真实出现（220×2 px），但计算 `backgroundColor` 为 `rgba(0, 0, 0, 0)`；其 `--accent` 为空，正确合同变量 `--accent-main` 是 `#0a84ff`。父元素 `aria-hidden=true`，内容区和编辑器区无 `aria-busy`、无可播报加载文本。用户看到空白，读屏也得不到任何加载状态。主题切换实验还确认 Monaco 光标一直为 `rgb(59,130,246)`，没有跟随 light 的 `rgb(0,122,255)` 或 dark 的 `rgb(10,132,255)` 强调色。
- **为什么是问题 / 依据**：`docs/specs/workbench/editor.md:91`（输出 6）及 `files-explorer.md:127` 承诺 800 ms 后显示进度条，当前 DOM 存在但像素透明；`packages/nb-ui/docs/ui-development-spec.md:66` 要求加载可播报；颜色 token 唯一真相源为 `nb-ui/src/colorway/colorway-contract.ts:40` 的 `--accent-main`，组件不能消费未登记变量。
- **如何核实**：真实 dev Lab 的读取闸门只扣住客户端合法读取，用浏览器等待 `[data-editor-progress]` 后读取计算样式、几何和 ARIA；证据截图 `lab-held-read.png`。主题样式观测记录在 `theme-samples.json`。现有控制器进度测试只验布尔值，未发现像素始终透明。
- **建议改法**：进度条和 Monaco 光标改为消费 `--accent-main`；800 ms 阈值后提供可访问加载状态（不提前打破合同的 800 ms 空白），不把唯一反馈整体 `aria-hidden`。把现有加载场景的浏览器断言补为实际颜色非透明、加载信息可访问。

### UI-05：拆分会清空原组的富文本撤销历史，随后切回也无法撤销

- **严重程度**：重要；**类别**：不变量 / 正确性；**核实状态**：真实产品浏览器已复现；README 和同名文档已说明实现限制，但它导致主 Spec 的验收不成立。
- **位置**：`packages/neuro-book/src/plugins/editor/web/components/MarkdownControl.vue:48`（`rebuilt` 创建无历史的新状态）、`:98`；触发来自 `EditorArea.vue:74` 的 grid 叶挂载。
- **现象**：产品 `close.md` 初始“关闭测试”，输入 `1`，撤销恢复初始文字、重做恢复“关闭测试1”，证明历史可用。Ctrl+\ 拆分后回原组 Ctrl+Z，左右仍都是“关闭测试1”，原组已有撤销历史已丢。证据 `split-history.png`。关闭组也会重挂现有组并经过同一重建路径，此项从代码推断，未单独运行关闭后的 undo。
- **为什么是问题 / 依据**：同名 `.md:33` 与 Task README 的 S6 段记录了丢历史，但并非 pending-confirmations 的已接受产品取舍；`docs/specs/workbench/editor.md:95`（输出 10）与 `:142` 承诺状态/历史保留到标签关闭，验收 9 要求 A→B→A 后 A 的撤销仍可用。拆分是本期核心动作，不是历史失效边界；只在组件文档说明丢历史不足以满足主合同。
- **如何核实**：真实产品 Files/浏览器键盘输入与 undo/redo 对照，随后拆分回原组再 undo。操作前可撤销、拆分后不可撤销；未直接调用 `rebuilt` 或手造旧 schema。
- **补充完整切换路径**：真实项目另建 `history.md`，输入“输入”得到“历史甲输入”，拆分后在原组切到 `dialect.md` 再回 `history.md`，聚焦原组正文 Ctrl+Z，仍为“历史甲输入”。与只在拆分后直接 undo 的第一条实验结果一致。
- **建议改法**：保持已有组及其控件的 DOM/实例在 grid 结构变化时稳定（稳定组宿主搬到新叶，而不是由递归 grid 销毁重建）；或提供完整跨重挂状态恢复，包括历史。扩展现有 A→B→A 真实浏览器验收，在 A 输入后拆分/关闭其它组，再回 A 撤销，确保主合同仍成立。

### UI-06：Markdown“用源码编辑器重新打开”没有任何人类可用入口

- **严重程度**：重要；**类别**：正确性 / 集成；**核实状态**：真实产品命令面板已核实，调用点由全源码精确搜索核对。
- **位置**：`packages/neuro-book/src/plugins/editor/web/commands.ts:63`（`REOPEN_WITH_COMMAND` 的 `expose.human=false`）；`src/plugins/editor/web/components/EditorTabBar.vue:89`（标签只有激活/转正/关闭）；`MarkdownControl.md:43`（把 frontmatter 编辑交给源码模式）。
- **现象**：产品打开 Markdown 后 Ctrl+Shift+P，命令候选有保存、拆分、还原等，但没有“用其它编辑器重新打开”；搜索“重新打开”显示“没有匹配的命令”。标签与内容区也没有切换入口。全 `src` 精确检索 `reopen-with` / `reopenWith` / `REOPEN_WITH_COMMAND` 只有 `area.ts` 的接口/实现与 `commands.ts` 的声明/处理，没有组件/菜单/宿主调用。默认选择只为非 `.md` 文件打开源码编辑器。
- **为什么是问题 / 依据**：`docs/specs/workbench/editor.md:111`（输出 20）及 plan.md:7 明确承诺 Markdown 可以用源码重开，frontmatter 的唯一编辑方式也是源码模式（plan.md:74、MarkdownControl.md:43）。现在只提供隐藏命令，普通用户无法完成合同内的切换与 frontmatter 编辑；这不属于 README 已说明的命令面板行号未实现项。
- **如何核实**：真实产品命令面板列出全部人类候选，再键入 `>重新打开`；结果候选 0。`grep` 覆盖全部产品源码的精确字符串确认没有其它入口。LSP references 尝试返回“No language server found for this action”，因此引用核对用可见源码搜索，不声称已获 LSP 结果。
- **建议改法**：在人类入口提供无需手写 JSON 的编辑器选择（例如标签菜单或命令面板选择 Markdown / 源码），最终执行同一 `nbook.editor.reopen-with`；或拆为两条固定参数的人类命令。用真实产品 Markdown 切源码、编辑 frontmatter、保存、切回富文本并读真实磁盘验收。
