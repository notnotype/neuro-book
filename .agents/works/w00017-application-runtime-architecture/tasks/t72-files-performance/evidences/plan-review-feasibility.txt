## 已核实发现

### F1：运行临时根“留到下次删”违背清理合同，默认输出又与临时根绑在一起

- **严重程度**：重要；**类别**：不变量、测试。
- **位置**：`.worktree/w00017-t72-plan-feasibility/.agents/works/w00017-application-runtime-architecture/tasks/t72-files-performance/plan.md:21-25,100`；`docs/testing/README.md:91-102`。
- **现象**：计划明确把原始样本、项目、状态与缺省报告写进运行临时根，并在结束后保留整个根，直到下次运行前才删除。
- **为什么是问题**：测试自身必须清理目录；非测试脚本也必须在 `finally` 清理临时数据。下一次运行不一定发生，异常运行还会留下运行数据。若实现者直接改成 `finally` 删除，缺省报告也随运行根消失，测量证据无法交付。
- **如何核实**：已核对上述计划与测试规则原文；这是显式合同冲突，无需运行推断。
- **建议改法**：将可删除的项目/状态/原始运行数据与可保留的报告输出分离。运行根在 `finally` 中先停服务、关浏览器、再清理；汇总默认输出到 acceptance/task/run 专用目录，显式 `--out` 时使用该目录并打印路径。仅对异常残留使用 owner marker 的兜底清理，不依赖“下次运行”承担正常收尾。

### F2：计划的“第二次打开”测的是并发新窗口，不是 t42 的关闭后重开

- **严重程度**：重要；**类别**：正确性、测试。
- **位置**：`plan.md:45-49`；`.agents/works/w00017-application-runtime-architecture/tasks/t42-files-baseline-research/README.md:32-43,70-73`；`packages/neuro-book-legacy/scripts/perf/files-baseline.ts:271-280`。
- **现象**：计划把“第二次打开”定义为“同一服务上新开标签页再导航”，没有关闭第一次页面或释放项目租约。t42 的基线则在每轮服务冷启动后，先打开并关闭项目，再在同一服务上执行 `reopen`；其结果才用于“第二次打开”标准。
- **为什么是问题**：第二个标签页复用已经启动的项目子进程和服务端状态，不能代表第一次打开后的关闭再重开；若把它汇总为 Spec 的“第二次打开约 300 ms”，p50/p95 会对应错误场景，且无法与 t42 基线比较。
- **如何核实**：已读取 t42 实现。新应用项目管理器在 `packages/neuro-book/src/server/projects/manager.ts:177-186,241-245` 以租约计数管理同一项目，第二个窗口不会启动第二个项目实例；页面关闭/绑定释放后才进入停止流程。
- **建议改法**：第一轮打开完成后关闭页面并等待服务端释放项目租约，再用同一服务的新页面导航，明确记录为 `reopen`；如还要测并发第二窗口，另列场景，不纳入“第二次打开”标准。

### F3：计划指定的 300 文件小样本和规模扫描当前无法由样本生成器生成

- **严重程度**：阻断；**类别**：正确性、可实施性。
- **位置**：`plan.md:20,55,81,100`；`packages/neuro-book/scripts/files-sample.ts:51-58`。
- **现象**：计划把 S1 与规模扫描的低档写成 `--count 300`，并要求沿用样本生成器；生成器默认宽目录为 400 项，并在 `count < wide + 100` 时直接抛错。因此当前命令 `bun scripts/files-sample.ts <目录> --count 300` 以及 `bun run perf:files -- --count 300` 都不能进入测量。即使把 S1 临时改成 `--count 500`，当前分配比例只实际写出 200 个 `notes/wide` 文件，但描述仍声称 400 项。
- **为什么是问题**：S1 的最小跑通门槛和规模扫描的 300 档均在脚本入口处失败，无法按计划完成；若实现者绕过校验或偷偷减少宽目录，会改变 t68/t42 约定的样本布局，结果也不能直接和 1000/3000 档比较。
- **如何核实**：已读取生成器的 `planSample` 校验；随后用同一入口的小样本探针运行了 `bun scripts/files-sample.ts <临时空目录> --count 300`，命令以非零退出并报告“文件数 300 至少要比宽目录多 100”；另用 `planSample` 对比 `count=500/1000`，得到实际宽目录文件数 `200/400`，而 `count=500` 的描述仍为 `400`。
- **建议改法**：二选一并写进 CLI 合同：S1 使用至少 1000 个文件（只有这样按当前分配比例才有 400 项宽目录），或为探针/规模档显式传入更小的 `--wide`，并在结果元数据中记录该档布局与“不代表 400 项宽目录”。若验收必须保留 300 档，不能只改计划数字，需先修改生成器的参数与验证测试。

### F4：没有定义“场景失败/未执行”与进程退出码的合同

- **严重程度**：重要；**类别**：测试、可实施性。
- **位置**：`plan.md:20-26,41-56,80-102`；`docs/testing/README.md:146-149`；旧脚本 `packages/neuro-book-legacy/scripts/perf/files-baseline.ts:494-547`。
- **现象**：计划描述超时会报错、记录原始样本和汇总，但没有规定任一迭代失败、观察器不支持、服务启动/重启失败、构建失败或场景未执行时的报告状态和退出码，也没有规定失败报告中不得把未判定的场景当成完成。
- **为什么是问题**：性能验收命令可能只留下部分 JSON/Markdown 而以 0 退出；S2/收尾会把缺样本误当成“没有问题”，调用方无法区分标准未达标、探针失败和场景根本没跑。测试合同明确要求验收脚本在构建失败等原因导致检查未执行时非零退出，并由调用方核对没有未判定项；旧基线也有 `completed` 与 `process.exitCode = 1` 的显式收口。
- **如何核实**：已对照计划与测试合同、旧脚本的 `finally` 报告生成及第 546 行退出码实现；计划文本没有对应字段或规则。
- **建议改法**：先定义运行状态模型（`complete`、`failed`、`incomplete`，每个场景带 `pass/fail/not-run` 与错误），任意构建/服务/浏览器/观察器/场景失败或样本数不足时 `process.exitCode !== 0`；即使失败也在 `finally` 生成报告，汇总只统计成功样本，并让收尾命令校验无 `not-run`。

### F5：CDP Profiler 只覆盖浏览器页，无法定位计划列出的服务端/项目进程热点

- **严重程度**：重要；**类别**：可测性、性能。
- **位置**：`plan.md:22,38-39,57-64`；`packages/neuro-book/e2e/fixtures.ts:48-63`；`packages/neuro-book-legacy/scripts/perf/files-baseline.ts:125-130,398-410`；t42 README `:55-63,78-80`。
- **现象**：t72 要复用 `startProductServer` 启动普通 `bun dist/server/main.js`，再用 CDP `Profiler` 查找“不达标指标的时间花在哪里”。该 CDP 会话附着浏览器页面；服务端的项目启动、按需列目录、读取 `content.xml`、监视合批都在另一个服务端/项目子进程中。
- **为什么是问题**：若打开项目或后台不冻结的问题来自服务端/项目子进程，浏览器 CPU profile 只能看到等待 RPC 的空档，不能证明服务端 CPU 热点，随后 S3 的修正方向只能靠猜。t42 已使用带 `--cpu-prof` 的服务端启动和独立的 server profile 归因；当前 fixture 的启动参数没有 profile 开关或 profile 产物路径。
- **如何核实**：已真实启动生产服务并用 Chrome CDP 成功执行 `HeapProfiler.collectGarbage` 与 `Profiler.start/stop`，得到的是页面 profile；同时核对 fixture 的 spawn 参数只含 `dist/server/main.js --stop-stdin`，没有 inspector/profile 配置。
- **建议改法**：明确指标归因边界：浏览器 profile 与 RPC/Server-Timing 只能作为页面侧证据；需要服务端候选时给测量脚本专用的、可关闭的服务端 CPU profile 启动方式（例如与 t42 一致的 `--cpu-prof` 产物，或受控 inspector/CDP 端口），在 `finally` 收口并把 profile 压缩/摘要化。不要把浏览器 profile 的结果写成服务端热点。

### F6：修正阶段没有可执行的防回退门槛，只写“复测”和“不要把毫秒阈值写进测试”

- **严重程度**：重要；**类别**：测试、可实施性。
- **位置**：`plan.md:57-66,81-84,98-102`；`docs/testing/README.md:24,42-43`；t42 README `:55-81`。
- **现象**：计划要求每个修正单独提交、跑受影响测试并复测，但没有规定复测如何判定回退，也没有把各候选修正对应的可观察结构不变量写成测试。唯一明确的测试约束是“不把耗时阈值写进测试”。
- **为什么是问题**：t42 已证明切换耗时可由 3000 项 store 深度遍历随规模线性增长；若后续修正再次引入深层订阅、额外 `list/read`、控件重建或重复刷新，现有“能打开/能编辑”的 e2e 仍可能通过，README 的前后数字也只能人工发现回退，不能守住修正后的合同。
- **如何核实**：已对照 t42 的规模增长结果与测试规则；计划的 S3 验证表只列 `unit/DOM/e2e/复测`，没有场景到不变量的映射或失败判据。
- **建议改法**：每个 S3 明确一个不依赖毫秒的回退守卫：例如切换已打开文件不发 `read/list`、同组同类控件实例身份不变、展开只请求一次且滚动后不重复列目录、500 个外部改动期间每批只刷新展开目录、关闭标签后控件与订阅归零；用真实 e2e/进程测试覆盖。性能脚本仍记录固定参数的 p50/p95/规模曲线，修正交付必须有完整复测报告和“无未判定项”，但不把机器相关的毫秒数硬编码进产品测试。

### F7：只在场景结束查询进度条，不能证明“800 ms 内从未出现”

- **严重程度**：重要；**类别**：测试、正确性。
- **位置**：`plan.md:32-39,50-52,88-96`；`packages/neuro-book/src/plugins/editor/web/components/EditorGroup.vue:89-104`；`packages/neuro-book/src/plugins/editor/web/area.ts:283-312`。
- **现象**：计划把加载提示的生产验证写成“脚本只核对正常打开时从不出现 `[data-editor-progress]`”，但页面观察器设计只列了 rAF、LoAF、longtask、Event Timing、WebSocket 与资源统计，没有记录进度条节点的插入/可见时间。结束时的 `querySelector` 会错过已经出现并在结束前撤掉的提示。
- **为什么是问题**：Spec 要求正文未就绪超过 800 ms 才显示、800 ms 内不显示；一次短暂闪现会违反用户可观察合同，却会被末帧查询判为通过。控制器单测和 Lab 的“扣住读取”只证明注入时钟/开发场景，不能替代生产构建、真实 Chrome 的页面链路取证。
- **如何核实**：已核对进度条由 `area.progress` 条件挂载，读取完成后撤掉；控制器在 `PROGRESS_DELAY_MS` 到点切换状态。现有计划的观察器清单没有 `MutationObserver` 或按操作窗口保存进度条出现记录。
- **建议改法**：在每次操作开始前，用页面内 `MutationObserver` 记录 `[data-editor-progress]` 的首次插入、移除、可见性与相对时间，并将记录按组/文档归属到操作；结束状态同时保存“未出现、在 800 ms 后出现、超过截止仍未就绪”等结果。保留现有控制器/e2e 测试，但不要用末帧 DOM 查询替代真实页面观察。

### F8：证据产物没有体积、保留和可复跑元数据合同

- **严重程度**：重要；**类别**：可测性、文档。
- **位置**：`plan.md:23-26,54,57-59,68-74,80-84,98-103`；`docs/testing/README.md:101-102,146-147`；t42 README `:90-95`。
- **现象**：计划只说汇总 JSON/Markdown 由 `--out` 输出、正式结果由主 Agent 复制到 `evidences/`，并把“原始样本”留在临时根；没有定义正式文件名/schema、命令与 revision/浏览器/负载元数据、原始逐次样本是否压缩、CPU profile/截图/服务日志是否入库及大小上限。
- **为什么是问题**：30 次、多场景、两种编辑器、两种组数再加规模扫描会产生大量逐次记录；CDP profile 和失败页面产物也可能远大于汇总。如果按 `--out` 直接全部拷入 Task，证据会膨胀；如果只复制 Markdown，又无法重算 p50/p95、核对失败样本或复跑命令。测试合同要求证据命令可原样重跑，并把过滤/统计方式写全；t42 已采用压缩原始 JSON、保留摘要、排除截图/trace/日志的明确策略。
- **如何核实**：已对照计划的输出/收尾描述与 t42 的实际证据清单；计划没有对应的产物清单或保留规则。
- **建议改法**：在 S1 前定义 evidence manifest：小型摘要 JSON/Markdown 入库，逐次样本与 profile 默认压缩并只在临时根保留（需要审查时另存 `.json.gz`）；日志、截图和完整 profile 不入库，仅保留摘要或明确的例外。每个报告固定写入源 revision、完整命令、参数/样本布局、浏览器/构建/负载、成功/失败/未执行状态和输出路径，脚本直接生成该清单，避免手工复制改变证据。

### F9：宽目录重复迭代没有定义把父行重新滚回可点击视口

- **严重程度**：重要；**类别**：可实施性、测试。
- **位置**：`plan.md:31,36,50`；`packages/neuro-book/src/plugins/explorer/web/components/ExplorerTree.vue:253-282`。
- **现象**：场景要求“每次先收起”宽目录，再展开并从头滚到尾；但上一轮结束在列表尾部时，虚拟树的 `notes/wide` 父行可能仍在 DOM 中却已经在视口外。计划只明确了测量目标行要滚入可见区，没有给收起用的父行定义同样的重置/可点击条件。
- **为什么是问题**：若按计划的真实鼠标点击直接用父行坐标收起，坐标可能在树上方，点击不会命中；若改用 Playwright locator 自动滚动，则会把驱动器的自动滚动混入场景步骤，且下一轮起点不确定，导致重复展开/滚动场景不稳定。
- **如何核实**：已用生产构建、Chrome、500 文件样本展开并滚到尾部；`[data-explorer-row="project://notes/wide"]` 仍在 DOM，但 `boundingBox()` 为 `y: -4281`，树视口为 `y:111..971`，不能直接真实点击。
- **建议改法**：每轮开始先在页面内把树 `scrollTop` 设为父行所在位置（或滚轮回到头），等待父行的 `getBoundingClientRect()` 完全落入树视口，再用 `page.mouse.click` 收起；收起、展开和“全部子行可见”都等待可观察状态后才计时。

### F10：每个场景新开标签但没有定义关闭，跨场景租约和页面活动会污染重启/资源测量

- **严重程度**：重要；**类别**：不变量、可测性。
- **位置**：`plan.md:22-25,41-55`；`packages/neuro-book/e2e/fixtures.ts:42-63`；旧基线 `packages/neuro-book-legacy/scripts/perf/files-baseline.ts:234-263`。
- **现象**：计划要求“每个场景新开标签页”，只在整个运行结束时说停止服务、关闭浏览器；没有规定场景结束关闭页面、释放项目绑定、等待页面停止重连，也没有规定重启前必须没有旧页面。
- **为什么是问题**：未关闭的页面仍持有项目绑定租约并运行观察器/WebSocket。随后“第二次打开”或服务重启会变成多个并发客户端；后台文件事件会广播给旧页，旧页的网络与堆活动也会污染请求、卡顿、控件和堆统计。服务停止时只要服务端收口，浏览器页还可能在下一轮重连，造成测量窗口与项目子进程寿命不确定。
- **如何核实**：已对照现有 fixture 的 `stop()` 只等待服务进程退出，以及 t42 在 `restart` 前显式 `page.close()`、`closeProject` 后再创建新页的流程；项目协议规定绑定链路关闭才释放客户端租约。
- **建议改法**：把页面归属到场景并在 `finally` 中先停止场景输入/观察器、关闭该页，再进入下一场景；服务重启前关闭全部页并等待服务退出码为 0。若有意测并发窗口，单独建立并发场景并隔离其页与统计，不让它们留在后续场景。

### F11：复用的 `startProductServer` 在启动失败时无法收口已启动的服务

- **严重程度**：重要；**类别**：不变量、可实施性。
- **位置**：`plan.md:21-25,45-52`；`packages/neuro-book/e2e/fixtures.ts:22-63`；`docs/testing/README.md:20,91-100`。
- **现象**：fixture 先 `spawn` 服务进程，再等待输出；`waitFor` 超时或进程输出不符合预期时，`startProductServer` 在返回 `ProductServer` 之前抛错，调用方拿不到 `stop()` 句柄。计划只规定正常结束时停服务，没有规定启动失败路径如何保存/终止该 child。
- **为什么是问题**：构建后首次启动、每次冷启动和重启都是测量主路径；任一启动超时或端口/项目初始化失败都可能留下服务（及其已启动的项目子进程），占用状态根/端口并污染后续迭代。异常时只清理临时目录也不能关闭打开的文件与进程，违反测试资源收口合同。
- **如何核实**：已读取 fixture：`spawn` 在第 50 行，`handle.waitFor` 在第 55 行，返回对象和 `stop` 只在等待成功后构造；没有 `try/catch` 失败清理。测试规则明确要求失败用例也停止资源。
- **建议改法**：不要把该 fixture 原样作为性能脚本的唯一启动边界；给启动句柄一个“启动中也可停止”的 `finally` 路径，或在脚本内封装带 child 引用的启动器：等待失败时通过 stdin/信号终止并等待 exit，记录 stdout/stderr，随后再清理临时根。每次重启和项目打开失败都走同一收口函数，并把收口失败设为非零结果。

### F12：计划要求的 `.json` 源码样本不在当前样本生成器输出中

- **严重程度**：阻断；**类别**：正确性、可实施性。
- **位置**：`plan.md:6,34,48-49,81,92`；`packages/neuro-book/scripts/files-sample.ts:66-91,124-148`。
- **现象**：计划要求对“富文本与源码（`.json`）”分别测冷开、热切换和单/双组，但 t68/t72 复用的生成器只写 `lorebook.content/**/index.md|notes.md`、`manuscripts/**/*.md`、`notes/**/*.md` 和 `lorebook.content/content.xml`，没有任何 `.json` 文件或源码样本描述。
- **为什么是问题**：按计划生成的隔离项目没有 `.json` 目标，源码场景无法选出未打开文件、固定标签和对应标记；S1 的“全部场景”与 S2 的验收映射不能完成。若临时把 `content.xml` 当源码样本，它不是计划指定的 `.json`，且属于内容文件夹特殊清单，读取/列出路径会引入另一种行为。
- **如何核实**：已运行生产构建后的 Chrome 探针并生成 500 文件样本；`glob` 检查该样本 `**/*.json` 无结果，且逐行核对生成器的三类 `add()` 路径只有 Markdown，`content.xml` 是单独写入。
- **建议改法**：在样本生成器合同中加入确定性的 `.json` 文件配额、路径、字节范围和 `NBOOK-SAMPLE-*` 标记，并更新 `SampleDescription` 的源码候选；计数分配、宽目录大小和冷/热选择必须对所有规模可行。或者把计划改为使用实际生成的另一种普通文本源码扩展名，并同步验收报告，不能只在测量脚本里硬编码不存在的地址。

### F13：同一 Chrome 配置的新标签共享 `client identity`，会恢复 `editor.session` 并污染“未打开过/空项目”样本

- **严重程度**：阻断；**类别**：正确性、可测性。
- **位置**：`plan.md:23,45-49`；`packages/neuro-book/src/web/host/client-identity.ts:1-3,26-41`；`packages/neuro-book/src/plugins/editor/web/session-record.ts:1-5,36-42`；`packages/neuro-book/src/plugins/explorer/web/preferences.ts:28-31`。
- **现象**：计划在一个 Playwright 浏览器运行中为每个场景新开标签；当前产品明确规定同一浏览器配置的多个窗口共享稳定的 `nbook.client-identity`，编辑器会把项目的组/标签/活动项存入 `project/local`，资源管理器的展开记录也在 `local` 分区。
- **为什么是问题**：关闭页面再开新页仍会读回之前场景打开的标签和展开目录，因此“打开项目”的初始状态不再为空、“未打开过”文件可能已被恢复为已打开、“热切换”固定标签可能来自上一场景。第二次打开也同时混入会话恢复，而不只是项目打开路径；即使按 F10 关闭旧页，测量仍不独立。
- **如何核实**：已用生产构建、Chrome、同一 `BrowserContext` 的两个新页面实际验证：两页的 `nbook.client-identity` 相同；第一页打开 `project://notes/wide/note-0001.md` 后关闭，第二页仍恢复 1 个同地址编辑器标签（输出 `sameClient:true, restored:1`）。
- **建议改法**：冷开、未打开过和各规模档使用全新 BrowserContext/独立 profile，或在每个场景前清理并等待 `editor.session`、展开记录等真实 Storage 记录落盘；第二次打开场景单独定义“保留哪些持久化状态”。不要只用 `page.close()` 或新标签隔离，它们不改变客户端身份。

### F14：`bun run perf:files` 的入口与现有 Playwright 运行时约束没有接缝

- **严重程度**：重要；**类别**：可实施性。
- **位置**：`plan.md:20-24,81-83`；`packages/neuro-book/e2e/playwright.config.ts:1-4,20-21`；`packages/neuro-book/package.json:16-18`。
- **现象**：计划把测量入口写成 Bun 脚本，并在同一流程中直接使用 Playwright；仓库 e2e 配置明确规定 Playwright 必须由 Node 运行，Bun 启动浏览器会发生 CDP 握手超时。计划没有规定 Node runner、Bun/Node 之间的参数与退出码传递边界。
- **为什么是问题**：若按入口直译为 Bun 进程内 `chromium`/Playwright，S1 smoke 会在浏览器启动阶段失败，不能证明测量脚本可运行；若偷偷切换到 Node，又会改变计划未说明的入口和异常收口路径。
- **如何核实**：**从代码与仓库规则推断，未在 Bun 中重复启动浏览器**；现有 Playwright 配置的注释和 `test:e2e` 的 Node 运行合同是直接依据。
- **建议改法**：在计划中明确一种边界：性能 CLI 由 Bun 解析参数/生成样本，spawn 一个 Node `.mjs`/Playwright runner；runner 负责 Chrome、页面与 CDP，并把失败、信号和退出码传回 Bun。或把 `perf:files` 本身登记为 Node 入口并保留 Bun 侧纯函数测试；两种方式都要在 `finally` 收口浏览器/服务。

### F15：用 DOM 控件数量代替模型/控件创建记录，不能满足验收 12 的资源证据

- **严重程度**：重要；**类别**：可测性、性能。
- **位置**：`plan.md:39,54,96`；`docs/specs/workbench/files-explorer.md:201`；`packages/neuro-book/src/plugins/editor/web/components/MonacoControl.vue:77-90,154-185,195-203`；`packages/neuro-book/src/plugins/editor/web/components/MarkdownControl.vue:197-217,231-243`。
- **现象**：计划只统计 DOM 中 `.ProseMirror`、`.monaco-editor` 的数量并称为“控件实例”。源码编辑器的 `createModel` 在绑定进入时创建、模型存入 view-state slot；Markdown 的 Tiptap `Editor` 也可在 DOM 卸载后由 slot 保留。DOM 数量只表示当前挂载视图，不表示模型/编辑器实例的创建、保留上限或释放。
- **为什么是问题**：反复切换导致模型泄漏、模型超出保留上限，或控件实例被重建但最终 DOM 数量相同，都能通过计划的指标；“关闭全部标签后资源归零/回基线”也无法区分 DOM 已消失但模型仍被 slot 保留的情况，因此不能覆盖验收 12 的“模型/控件创建与资源保留”。
- **如何核实**：已核对 `MonacoControl.enter` 的 `monaco.editor.createModel`、`host.state` 保存及 `editor.dispose`，以及 Markdown 控件的 slot 保留与 `editor.mount/unmount`；现有生产 Chrome 探针的 DOM 统计不会观察这些对象。
- **建议改法**：把“挂载 DOM 控件数”“真实模型/控件实例生命周期”“GC 后堆/本机资源”拆成三类证据。为模型和控件生命周期选择已有的非测试专用诊断边界，或用真实行为测试证明 A→B→A 复用、关闭后释放/保留上限，并在测量报告中明确哪些是直接计数、哪些只是间接证据；不能把 DOM 数量字段命名成模型创建数。

### F16：C 场景缺少“从资源树再次点击已打开文件”的 hot-tree 路径

- **严重程度**：重要；**类别**：可测性、验收覆盖。
- **位置**：`plan.md:47-49,91-92`；`packages/neuro-book/src/plugins/explorer/web/controller.ts:696-715`；`packages/neuro-book/src/plugins/editor/web/area.ts:432-447`；`packages/neuro-book/src/plugins/editor/web/components/EditorTabBar.vue:89-90`。
- **现象**：计划覆盖的是树上轮流点击不同文件的 preview/cold 路径，以及两个固定标签间来回点击的 hot-tab；没有“文件已在标签中，再从资源树点击它”的 hot-tree。产品实现中树点击会走选择更新后 `open(..., "preview")`，标签点击则走独立的 `activate`，两者不是同一条状态路径。
- **为什么是问题**：验收要求覆盖已打开文件正文，但当前 hot-tab 只证明标签激活，不能证明树选择、preview 查找/替换和已存在标签处理在已打开文件上的性能。该路径也不能与 t42 的 `cold-tree`、`hot-tree`、`hot-tab` 基线直接对齐。
- **如何核实**：已静态核对产品两条入口；t42 交付矩阵明确将 `hot-tree` 与 `hot-tab` 分开统计。未额外运行该场景。
- **建议改法**：在 C 增加 `hot-tree`：同一编辑器组先保留 A/B 两个 permanent 标签，停在 B，再从资源树点击已打开的 A；与 `hot-tab` 使用同样的编辑器类型、组数、文件和起始状态，分别记录 selection、tab、正文完成、请求数。规模扫描也要包含该格，或明确报告为未验证。

### F17：B 的连续滚动与 D 的后台改写没有独立、可收口的测量窗口

- **严重程度**：重要；**类别**：可测性、事件归属。
- **位置**：`plan.md:31-39,50-51,93-96`；`packages/neuro-book/src/plugins/files/backend/changes.ts:147-200`；`packages/neuro-book/src/plugins/files/web/client.ts:172-226`；`t42-files-baseline-research/evidences/delivery.md:61-66,114-118`。
- **现象**：B 在“展开到子行出现”之后另写“再从头滚到尾”，但没有定义滚动起点、滚动结束、每帧 scrollTop/帧间隔或稳定帧，因此展开完成终点不能覆盖连续滚动流畅性。D 只写磁盘改写 500 个文件并记录 LoAF/键入时长，没有定义写入完成、watcher 批处理完成、前端重列完成或输入窗口结束的屏障。
- **为什么是问题**：后台 watcher 的 75ms 只是调度 flush；随后还有逐路径 classify、RPC `batch`/`resync` 和客户端投递，`batch` 到达不等于前端完成重列。B 若用固定等待或 D 若立即结束，会分别漏掉后续卡顿或把无关 GC/后续操作算入窗口，LoAF 和输入时长不能可靠归因于这两个场景；验收的“宽目录流畅”“后台不冻结”因此不可判定。
- **如何核实**：已核对 watcher 的 `schedule`/`flush`、客户端 `ready/batch/resync/ended` 合同，以及 t42 已记录的“B 只证明子行渲染、不证明持续滚动流畅”局限；未用固定等待替代验证。
- **建议改法**：将 B 拆成展开和连续滚动两个样本；滚动从真实树首端开始，记录 scrollTop 进度、rAF 帧间隔/长帧，并在到尾后的稳定帧结束。D 为每次注入定义 start/end：记录 500 项写入完成，等待可识别的批处理和前端应用完成屏障再结束；若生产合同没有 drain 信号，至少分别报告“收到 watcher batch”和“前端完成处理”，不能用 75ms 常量或固定等待作为结束条件。
