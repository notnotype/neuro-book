# t72 实施计划只读审查：产品性能结构

审查对象：提交 `69828b3c` 的 `.agents/works/w00017-application-runtime-architecture/tasks/t72-files-performance/plan.md`。

审查边界：不修改仓库；只报告导致测量失真、实施受阻或验收缺口的问题。已记录的 t68–t71 取舍与计划非目标不单独作为缺陷。代码路径未运行的判断标为“从代码推断”。实验和样本仅写在本报告目录。

## 已核实发现

### 1. 阻塞项：计划的 300 文件小样本入口无法运行

- **类别**：阻塞项 / 可实施性。

- **位置**：`plan.md:21,55,81`；`packages/neuro-book/scripts/files-sample.ts:52-57,66-91,139-147`。
- **现象**：计划复用现有生成器，用 `--count 300` 跑通全部场景并做 300/1000/3000 规模扫描。生成器默认 `wide=400`，强制 `count >= wide + 100`；300 文件直接抛错，还未生成样本。
- **为什么是问题**：S1 自跑验证和规模扫描的第一档都不能按计划执行；300 文件也不可能同时提供 400 个文件子项的宽目录。“每个场景新标签页”不能补上缺少的输入数据。
- **依据与核实**：在应用包执行 `bun scripts/files-sample.ts /tmp/claude-1000/-home-notnotype-CodeRepository-neuro-book/c38df555-3a36-49c9-bf4f-4027b5da6d32/scratchpad/t72-plan/product/sample-300 --count 300`，退出码 1，原文 `error: 文件数 300 至少要比宽目录多 100`。未运行正式测量。
- **建议改法**：明确小样本宽目录参数，按笔记份额约束 `wide <= count - floor(count*0.3)*2`，通过 API 传入；小样本只做功能 smoke，400 项展开指标只在可容纳该目录的正式样本中判定。更新 S1 命令和规模扫描说明，不能把小样本的较窄目录当作 400 项证据。

### 2. 重要：内容文件夹的实际列目录成本遗漏了按项 `lstat(index.md)`

- **类别**：安全与性能。
- **位置**：`packages/neuro-book/src/plugins/files/backend/files-service.ts:5-7,114-120`；计划 `plan.md:60-64`。
- **现象**：内容树的每次 `list` 不只重新读取所属 `content.xml`；对当前目录的每个子目录还并发执行一次 `lstat(index.md)`，用来计算节点是否有正文。3000 文件样本约有 900 个内容节点，按生成布局分到 3 个清单组；展开任一组目录约 300 项就会产生约 300 次 `lstat`，再次刷新仍重复执行。
- **为什么是问题**：计划的候选只记录“每次列出重复读 `content.xml`”，请求计数若只统计 RPC `list` 会把这批服务端文件系统访问隐藏掉；规模扫描可能看到列表 RPC 数量不变，却漏掉随节点数线性增长的服务端工作，S3 也不会有明确的优化目标。该成本直接位于“展开目录”和监视后重列路径。
- **如何核实**：从代码推断；`list` 先 `readdir`，再对 `disk.map` 的每个目录调用 `hasBody`，`hasBody` 在 `files-service.ts:166-172` 对 `index.md` 做 `lstat`。未改产品代码、未运行正式测量。
- **建议改法**：把“每个内容目录项的 `index.md` 探测”列为单独测量维度，至少在 300/1000/3000 节点下记录服务端耗时与实际 `lstat` 次数，并把 `content.xml` 重读与按项正文入口探测分开归因；只有测量证明需要时再设计缓存或目录项元数据方案，保持 `index.md` 增删后的呈现合同。

### 3. 重要：S3 的定位工具不能定位服务端文件监视与项目子进程瓶颈

- **类别**：测试 / 安全与性能。
- **位置**：`plan.md:57-59`；待分析的实现位于 `packages/neuro-book/src/plugins/files/backend/changes.ts:147-200`、`packages/neuro-book/src/server/projects/manager.ts:281-312`。
- **现象**：计划规定正式基线失败后“用 CDP 的 CPU 采样与 RPC 帧计数找到时间花在哪里”。CDP 采样的是 Chrome 页面线程；RPC 帧计数只能说明请求数量。服务端监视批处理会在 75 ms 后逐条串行 `await classify(path)`，每项至少 `lstat`，预期 hash 还要 `readFile` 与 SHA-256；项目首次打开则在 `manager.ts` 中等待子进程启动回执。这些时间不在浏览器 CPU profile 内，也没有列出服务端 CPU profile、分段计时或项目启动时序证据。
- **为什么是问题**：t42 基线已把服务端项目打开作为独立 profile 证据；若新实现的 1 秒打开或“后台不冻住”不达标，照计划只能看到浏览器等待/LoAF，无法区分项目子进程启动、RPC、监视分类、目录重列和文件读取，修正会变成盲改，S3 可能做不完也无法解释验收结果。
- **如何核实**：从代码推断；旧方法在 `packages/neuro-book-legacy/scripts/perf/files-baseline.ts:398-410` 另起生产服务 CPU profile 并读取 `server-project-open.cpuprofile`，而新计划仅写 CDP CPU 采样（`plan.md:59`）。未运行正式测量。
- **建议改法**：沿用 t42 的服务进程 profile 或增加不改变行为的服务端分段证据：项目绑定/子进程 ready、`list` 的 `readdir`/清单解析/`hasBody`、watch `flush` 分类、树重列与文件 read 分别可归因；报告必须能把浏览器等待映射到这些阶段。服务端 profile 与浏览器 profile 都用独立临时产物并在 `finally` 收口。

### 4. 重要：候选“空闲预取 Monaco”违反 t71 的按需加载合同

- **类别**：正确性 / 性能。
- **位置**：`plan.md:60-65`；`packages/neuro-book/src/plugins/editor/web/plugin.ts:91-97`、`packages/neuro-book/src/plugins/editor/web/code/load-monaco.ts:1-3`；既有验收 `packages/neuro-book/e2e/editor-area.e2e.ts:302-317`。
- **现象**：计划建议在编辑器区空闲时 `requestIdleCallback` 预取富文本或源码编辑器代码块，并认为只要不提前创建实例就不改变行为。当前插件把 `MonacoControl.vue` 和 `loadMonaco()` 放到首次挂上源码控件时才动态加载；现有 e2e 明确在打开 Markdown 后断言 `monacoRequests` 为空，再首次打开 JSON 后才要求 Monaco 请求出现。
- **为什么是问题**：预取即使不创建 Monaco 实例，也会改变首屏网络与 CPU/缓存行为，并会使“第一次打开源码文件之前不加载它”的 t71 合同行为及测试失效。它不是仅性能实现细节，不能在 S3 里按普通候选直接采用。
- **如何核实**：从代码推断；加载器注释写明“第一次打开源码文件时才加载”，e2e 用真实 Chrome 监听请求验证该边界。未运行预取（仓库当前没有该改动）。
- **建议改法**：默认保留当前严格按需边界；若要预取，先把它单列为待开发者确认的产品行为变更，更新 t71 合同与 e2e 的“首屏不加载”验收，并把预取请求/缓存命中/首开收益分开测量。只预取不会改变既有合同的实现不能满足当前计划所写候选。


### 5. 阻塞项：正式样本没有源码文件，计划列出的 Monaco 场景无法执行

- **类别**：阻塞项 / 可实施性 / 测试。
- **位置**：`plan.md:6,34,48-49,81`；`packages/neuro-book/scripts/files-sample.ts:1-8,78-91`。
- **现象**：计划要求未打开正文按富文本与源码（`.json`）分开，且 S1/S2 要跑源码路径；现有样本生成器的文件路径只有 `notes/.../*.md`、`manuscripts/.../*.md`、内容节点 `index.md`/`notes.md`，没有 `.json` 或其它非 Markdown 文本。`SampleDescription.open.cold` 只是按数组下标选任意文件，不提供源码样本。
- **为什么是问题**：按计划生成 3000 文件后，源码分组没有目标文件；脚本只能跳过、重复 Markdown 或临时手写额外文件，三者都会使验收矩阵与样本合同不一致。这样无法证明 Monaco 冷加载、源码正文出现和源码热切换的 100/200 ms 指标，也无法验证按需加载候选。
- **如何核实**：从代码核对；`files-sample.ts:84-91` 的所有生成分支后缀均为 `.md`，脚本顶端也明确写“约 3000 个 Markdown”。未运行正式测量。
- **建议改法**：在计划中明确扩展样本计划/生成器，固定比例生成可编辑源码文件（例如 `.json`）并把它们的地址、标记单独写入描述；或删掉源码性能矩阵并明确不验 Monaco。若扩展生成器，补充字节大小、样本总数、内容树比例和源文件不影响 Markdown 数量的约束，避免把“3000 个 Markdown”悄悄改成另一份基线。

### 6. 重要：每个场景新开标签页不能提供冷/热场景隔离

- **类别**：测试 / 性能。
- **位置**：`plan.md:23,45-49`；`packages/neuro-book/src/web/boot.ts:31-42`；`packages/neuro-book/src/plugins/editor/web/session-record.ts:1-4,36-54`；`packages/neuro-book/src/plugins/editor/web/session.ts:56-68`。
- **现象**：计划只规定“每个场景新开标签页”，但 Chrome 同一上下文的 `localStorage` 复用同一个客户端身份；`editor.session` 是 `project/local` 记录，新页面会读同一项目的上一个组、标签和活动项。页面启动时会在首读完成后从记录恢复标签，活动标签再按正常打开流程读正文。
- **为什么是问题**：前一场景留下的标签/会话会污染后一场景：计划中的“未打开过”文件可能已在恢复会话里，`热切换`可能变成跨页面恢复而不是当前页面已打开文档，前一页面仍存活时还会和后一页面竞争同一条 Storage 记录。展开记录也按相同客户端身份共享。这样 p50/p95 不是计划声明的冷/热定义，且多次新标签页的结果不可复现。
- **如何核实**：从代码推断；`boot.ts` 从 `localStorage` 读取跨页面身份，`EDITOR_SESSION_RECORD` 定义为 `scope: "project", locality: "local"`，`createEditorSession` 在记录 settled 后以 `snapshotOf(base.value)` 建区。未运行正式测量。
- **建议改法**：在场景矩阵中明确会话策略：冷开场景使用新 BrowserContext/新客户端身份，或在每次场景结束关闭全部标签并等待空会话写入后再开页；热切换在同一页内预热固定地址并核对请求数为零。项目首开/第二次打开若要保留真实用户的 Storage 与展开恢复，则单独记录该前置状态，不与冷打开样本复用。

### 7. 重要：后台 500 文件场景没有固定事件规模、并发文档数与收束条件

- **类别**：测试 / 安全与性能。
- **位置**：`plan.md:37,51,63-64`；`packages/neuro-book/src/plugins/files/backend/changes.ts:158-200`；`packages/neuro-book/src/plugins/editor/web/documents/store.ts:202-235`。
- **现象**：服务端对一批外部变化按路径串行 `await classify`；每个路径至少 `lstat`，超过编码预算则直接发 `resync`。浏览器文档订阅收到 batch 后，对每个事件重新取得该方案全部已打开文档的数组并逐项判断，单个文档的实际读会合并，但事件与文档的比较仍按事件数乘已打开文档数增长。计划只写“改写 500 个文件（含已展开目录与已打开文件）”，没有规定实际进入同一批的事件数、同时打开的文档数、修改是否与键入真正重叠，也没有定义所有迟到批次处理完的可观察终点。
- **为什么是问题**：同样写 500 个文件，可能因 inotify/75 ms 窗口得到多个小 batch、一个大 batch 或 `resync`，而且只打开一个文档与打开几十个文档的前端成本不同。若测量窗口在最后一次键入后结束，迟到的 watch flush、目录重列或文档重读不计入 LoAF，报告可能把未执行完的后台工作判成“不冻结”，也无法判断是服务端串行分类还是浏览器文档 fan-out 导致延迟。
- **如何核实**：从代码推断；`changes.ts:188-192` 明确逐条分类，`documents/store.ts:213-223` 明确每事件扫描当前文档集合；未运行正式测量。
- **建议改法**：把场景参数写死并分档（例如已打开文档数量、500 个修改在宽目录/多个已展开目录的分布、单批与跨批），记录 batch/resync、事件、`list`/`read` 次数和最终完成时间。键入用与磁盘写入重叠的真实并发流程；结束以 sentinel 变化已被页面观察到、所有相关文档 recheck 完成等可观察条件收束，禁止用固定睡眠截窗。

### 8. 重要：虚拟化场景没有覆盖“全树投影”的增长路径

- **类别**：测试 / 安全与性能。
- **位置**：`plan.md:35-36,50,55,93`；`packages/neuro-book/src/plugins/explorer/web/tree/rows.ts:110-177`；`packages/neuro-book/src/plugins/explorer/web/components/ExplorerTree.vue:71-75,261-281`。
- **现象**：浏览器只把窗口附近的行挂进 DOM，但 `projectRows` 仍从两个根递归遍历所有展开目录，把每个可见后代构造成完整 `Row[]`；`ExplorerTree` 的虚拟化是在拿到完整 `props.rows` 后才用 `renderedRows` 截取。展开 400 项只证明 DOM 控件数受限，不证明“上次展开路径较多”时的树投影、数组分配与 Vue 更新成本。
- **为什么是问题**：Spec 要求打开项目恢复上次展开路径，展开记录最多 2000 条；如果多个目录已展开，目录事件或任一状态变化都会重新计算整棵已展开树。计划的打开项目和规模扫描没有规定预置多少展开目录，宽目录场景只有一个 400 项目录，可能绕过随展开范围增长的热路径，导致打开项目或后台刷新随文件数变慢却没有证据。
- **如何核实**：从代码推断；`rows` 的 `computed` 在控制器中调用 `projectRows`，组件再对完整行数组计算可渲染窗口。未运行正式测量。
- **建议改法**：新增恢复态矩阵：根节点默认态、一个 400 项宽目录、跨 3–5 层且累计数百/上千个已展开目录；分别记录首个可操作帧、首次列表完成、`rows.length`、DOM 行数、变化后重投影与滚动 LoAF。规模扫描至少固定“同一展开路径比例”，否则不能把 300/1000/3000 的结果解释为树规模趋势。

### 9. 建议：展开状态的 Storage 写入热路径未纳入请求与资源指标

- **类别**：安全与性能。
- **位置**：`plan.md:38-39,50-55,96`；`packages/neuro-book/src/plugins/explorer/web/session.ts:102-106`、`packages/neuro-book/src/plugins/explorer/web/controller.ts:271-276`；`packages/neuro-book/src/shared/store/persisted.ts:303-313,320-341,372-386`。
- **现象**：每次展开或收起都会把两份路径数组重新整理后调用 `saveExpanded`；持久化字段把每次提交排进队列并串行经 Storage 保存，没有按交互帧或短窗口合并。计划的请求统计只按 `nbook.files/project` 的 `list`、`read` 等方法计数，未计 `editor.session` / `explorer.expanded` / `explorer.user-expanded` 的 Storage 远程写入、队列长度或写入耗时。
- **为什么是问题**：在连续展开深层目录或多分支恢复时，写入次数与每次序列化的路径数组长度同时增长；文件列表请求可能达标，但 Storage 写队列仍在后台积压，且保存暂停/冲突时会继续保留最新显示值。计划没有证据区分“树列目录慢”和“展开记录保存慢”，也不能确认后台工作期间 Storage 写入没有造成卡顿。
- **如何核实**：从代码推断；`onExpandedChange` 每次调用两个 `saveExpanded`，`PersistedFieldState` 的 `#enqueue` 每次加入队列并由 `#pump` 单个发送。未运行正式测量。
- **建议改法**：把 Storage 记录键、写入帧数、队列峰值、单次序列化字节和最终结算时间列入场景指标；至少增加连续展开深层目录的少量次数场景，并把文件 RPC 与 Storage RPC 分开统计。若测量证明需要合并，先保持显示即时，再在持久化边界做可观察的短窗口合并，且补 t70 的保存失败/重试合同验证。

### 10. 建议：性能脚本计划把大样本临时根留到下次运行，违反脚本清理合同

- **类别**：可实施性 / 资源安全。
- **位置**：`plan.md:20-25,100`；`docs/testing/README.md:91-102`；可复用的清理模式见 `packages/neuro-book/scripts/files-list-trace.ts:84-106`。
- **现象**：计划第 5 步规定停止服务、关闭浏览器后“临时根保留到下次运行前由脚本自己删除”，而测试规范要求脚本创建的临时数据必须在 `finally` 中清理。3000 文件样本、profile 与日志会在正常成功运行后继续占用磁盘。
- **为什么是问题**：异常中断时残留目录不一定能在下次运行立即回收；若 owner 仍被视为活跃，清理兜底也必须保留它。下一次运行若删除仍被遗留子进程使用的根，会把磁盘残留问题变成服务/监视器错误，且多次正式测量会受上一次未清理数据和磁盘空间影响。
- **如何核实**：计划文本与仓库清理合同直接矛盾；现有 `files-list-trace.ts` 已用 `try/finally/rm` 实现同类样本清理。未运行正式测量。
- **建议改法**：在 `finally` 中按顺序等待页面、浏览器、项目服务和子进程收口后删除样本及原始产物；只保留 `--out` 明确要求的报告。若为故障复现必须保留现场，提供显式 `--keep-temp`，并打印 owner、路径与清理责任，不把保留作为默认行为。

## 未发现问题的方面

- 页面内以真实 `pointerdown` 为起点、以 `requestAnimationFrame` 首次满足可见条件为终点的口径，与文件资源管理器性能合同的“下一帧呈现”要求一致；未发现计时点本身会把 Playwright 选择器等待计入结果的问题。
- 生产构建、本机 Chrome、参考机器、p50/p95/最大值、LoAF/Long Task/Event Timing 的总体观测框架已覆盖主要用户可见指标；缺口在服务端阶段归因和场景收束，不是这些浏览器指标本身多余。
- 800 ms 加载提示已有 t71 控制器与 e2e 合同，计划只确认正常性能场景不显示进度条，没有重复把不稳定的毫秒阈值写进性能自动化断言，这一取舍合理。
- 样本正文标记、编辑控件可输入、虚拟列表滚动到目标行后再取坐标的终点保护，能避免“选择器找到但正文/控件尚未真正可用”的假快结果；未发现这些保护在计划中缺失。
