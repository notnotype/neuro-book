### 1. [阻断] 隐式容器缺少稳定身份与恢复规则，t52 无法确定持久化引用语义

- **位置**：`docs/proposals/workbench-shell-abstractions.md:108-114,129-135,165-168`；`docs/specs/ui/workbench-shell.md:219,238-239`。
- **现象**：稿件只规定自建容器为 `custom:<UUID>`，隐式容器没有 id 推导、保留命名空间或恢复条件。视图声明中的 `container?: string` 与布局里的容器位置、选中项、视图归属都需要引用容器；声明式容器未来也使用同一引用面。
- **为什么是问题**：原文称“视图没有指定容器时，在其声明的默认位置自成一个容器”，同时规定“容器的实际成员数归零时，从 Switcher 移除（声明保留）”。仅凭这两句无法判定：把 A 移出其隐式容器后刷新是否重新生成空入口；B 已并入 A 的容器而 A 又移走时该容器是否还保持原身份；A 默认 Part 改变是否改变容器 id。Spec 已要求“恢复默认落位不得制造一个没有成员的空 Tab，也不把已移动 View 无条件拉回”（第 219 行）。这些不是 UUID 实现细节，而是覆盖记录、重置与未来声明式容器共享的身份合同；临场选择可能使已存引用失效。
- **如何核实**：完整读取设计稿，定向检索“隐式”“custom:”“originViewId”“containerId”和默认变更规则；稿件只给出自建容器身份。对照 Spec 的空成员及自建容器恢复合同，没有可直接套用到新隐式容器的身份定义。
- **建议改法**：先固定三类容器的互斥身份规则，例如以稳定 view id 推导、与 Part/当前成员无关的保留前缀，声明式 id 禁止占用该前缀和 `custom:`。明确声明身份与实际布局入口分离；先求默认加用户覆盖后的成员，再生成非空入口。补充上述 A/B 移动、刷新、重置、拥有者撤回的表格例子，并规定持久化记录统一如何引用三类容器。无需提前开放容器贡献点。

### 2. [阻断] `LayoutStore` 的值读写端口不足以兑现以后只换适配器、不改调用方的承诺

- **位置**：`docs/proposals/workbench-shell-abstractions.md:163-180,205,233`；`docs/specs/storage/persistence.md:54-64,81-84,110-120,124-134`。
- **现象**：端口全部定义为 `LayoutStore {read(key), write(key, value)}`，没有读写返回类型、异步语义、记录状态与确认结果，也没有上下文绑定或失效合同；同时宣称“换后端不改调用方”并在以后接入 Project 与 `storage.persistence`。
- **为什么是问题**：Storage 要求读取区分缺失、损坏、I/O 失败，返回 revision；条件保存可冲突或结果未确认，Project 句柄绑定精确代次。布局 owner 还须“只重放本次主动修改的字段”，不能让 Storage 通用合并 JSON（第 116–117 行）。仅收到整条 value 的适配器没有完整的布局意图、重放前置条件和用户决策信息，无法透明地完成这些语义；调用方若现在只认读到值/写完值，未来必然改状态机。将 scope 编在 key 中也不能替代有效 Project 代次与释放。
- **如何核实**：逐项对照端口与 Storage 的读取、条件保存、失败、上下文和排空合同；设计稿没有另一个承担上述 owner 状态机的接口。第 6 节已明确本期不迁 CAS，因此本问题不是要求本期实现 CAS，而是端口承诺与延期范围不相容。
- **建议改法**：二选一并写明：把端口限定为当前用户级 localStorage 过渡接口，明确接入 Project/CAS 时允许扩展调用方；或者现在只固定最小异步读写结果、上下文绑定/释放和“提交意图或字段补丁”的 seam，CAS 实现仍后置。无论选哪种，t51 先定义读取失败不等于缺失、保护原件时不可普通写入、保存失败不报 saved 的结果语义。

### 3. [阻断] 跨容器移动保留实例与已接受 P7 的“离开容器即释放”相反，预期修订清单未收口

- **位置**：`docs/proposals/workbench-shell-abstractions.md:10,103,120-124,235-244`；`docs/proposals/extensible-application-platform.md:296`；`docs/specs/ui/workbench-shell.md:16,216,278`。
- **现象**：设计稿保留 Teleport 实例，明确“隐藏、切换容器、移动、换轴都保留”；平台设计 P7 同时写“离开容器或所属插件被禁用时释放”。稿件仅声明取代旧提案的 descriptor 字段与持久化细节，没有列入 P7 生命周期修订。
- **为什么是问题**：这是同一次跨容器移动的两个互斥结果：保留输入/滚动/generation，或释放重建。Spec 的目标已要求“不因容器移动、合并、模式切换销毁视图实例”，所以应保留本稿选择，不应让 Files 实现者按 P7 再建立释放路径。当前称“沿用”却不明确覆盖关系，会使后续消费者、验收和插件状态归属不一致。
- **如何核实**：逐字对照设计稿三层生命周期、accepted P7 及 Spec 目标和模式切换验收；没有运行 Vue 或实例测试，结论仅为书面合同冲突。
- **建议改法**：把 P7 第 296 行及 View Host 的历史生命周期表述纳入预期修订，明确用户移动不释放；只有声明真正撤回、实现所属入口停止需撤销组件引用、插件禁用或工作台释放才销毁。分别写清“布局归属变化”与“贡献实现失效”，不改变本稿已选的实例保留策略。

### 4. [建议] “首个可见视图”不能覆盖全部成员不可见的容器，标题图标回落需补齐

- **位置**：`docs/proposals/workbench-shell-abstractions.md:110-114,187`；`docs/specs/ui/workbench-shell.md:31,288`；参照 `packages/neuro-book-legacy/app/utils/workbench/product-catalog.ts:362-380`。
- **现象**：隐式容器标题、图标取首个可见视图，但全部成员隐藏或条件不满足时仍保留 Switcher 条目，此时不存在首个可见视图。隐式容器起源视图已移走、其它成员留在其中时也不能只取起源视图。
- **为什么是问题**：Spec 明确“成员仍存在但全部隐藏或条件不可见”不能销毁容器。若元数据留给组件补算，ActivityBar、标签和“移动到”菜单可能各用不同回落，还违背“渲染只消费求值结果”。旧模型实际有声明或 `originViewId` 回落，新隐式来源不能自然等同于旧声明式来源。
- **如何核实**：对照保留入口规则与元数据取值规则；读取旧纯求值代码，确认其显式处理 `leader === undefined`，没有把空模式等同于无入口。没有运行隐藏场景。
- **建议改法**：在纯呈现求值里规定统一顺序，例如首个可见成员、首个实际成员、仍有效的起源/声明元数据、可诊断的稳定兜底；所有导航和菜单只消费同一结果。说明起源视图撤回但容器仍有其它插件成员时的回落。不要求现在提前实现视图隐藏贡献。

### 5. [建议] localStorage 阶段应明确双标签页覆盖风险，而不只写“本窗口顺序写”

- **位置**：`docs/proposals/workbench-shell-abstractions.md:178-180,205,221-222`；`docs/specs/storage/persistence.md:30,113-117,228`。
- **现象**：已决定暂不接入 CAS 与外来订阅，但没有说明 localStorage 的记录是否按标签隔离，或同 origin 多窗口共用两条键时的覆盖语义。
- **为什么是问题**：“每个窗口一个工作台”和窗口内唯一写者，不等于持久化键只有一个写者。同 origin 的 A/B 标签各持有旧整条定制记录时，A 改面板位置、B 改容器顺序，若各写整条值，后写者会覆盖另一项；没有订阅时，当前显示与刷新后的记录也可以不一致。这是批准的临时后端的具体代价，不是要求重新引入跨窗口同步。
- **如何核实**：对照稿件本窗口写入限制与 Storage 的客户端/标签页定义；稿件没有给出标签隔离键或同键并发策略。上述时序是从共享 localStorage 与整条写入推导的后果，未运行双标签实验，也未宣称某个尚未实现的适配器已出现数据丢失。
- **建议改法**：直接声明过渡阶段同 origin 共用键、整条 last-writer-wins、不同字段也可能互相覆盖，且当前窗口不追随另一标签的几何；或者明确采用何种隔离。把此限制列入 t51 验收与未承诺行为，保持 CAS/订阅后置的既定取舍。

### 6. [阻断] 两记录方案合并面板与侧栏尺寸，却声明不修改要求分键的 `storage.persistence`

- **位置**：`docs/proposals/workbench-shell-abstractions.md:165-180,235-244`；`docs/specs/storage/persistence.md:95-100`；`docs/specs/ui/workbench-shell.md:195,300`。

- **为什么是问题**：这不是旧键名不同，而是原子保存单元与失败结果不同：一条合成记录整体写入，和侧栏/面板两条可分别成功、失败的记录不能同时成立。t51 按新两记录方案实现后，将来按未修改的 Storage 合同接入必须再次拆键、修改写入回执与调用方，违背“换后端不改调用方”。

### 7. [阻断] t51 的条件命令早于上下文键接入，现有命令合同没有满足该切片的可用性通路

- **现象**：t51 贡献面板位置、对齐、收起与最大化命令，其 Spec 条件分别要求外壳就绪、非紧凑、水平位置等；稿件把上下文键服务推迟到编辑器。现有产品命令表的 `PRODUCT_CONTEXT_KEYS` 是 `{}`，没有 context 值来源，服务也没有登记键或提供可用性的入口。
- **为什么是问题**：Spec 第 143 行明确“在那之前产品命令表不认任何键，声明了 `when` 的命令贡献被拒绝”；源码由同一校验函数落实该规则。t51 若按第二批 `when` 贡献将无法登记；若删 `when`、只在处理器返回 unavailable，则命令面板枚举与执行前 `isEnabled` 不满足 Spec 的三面可用性。Lab 局部命令表可以注入键/值，但不能证明产品 `/` 中条件命令成立。只把“随 t50”改成“随 t51、t52”不能解决这个前置条件。

### 8. [建议] 呈现模型需区分导航、当前显示和常驻集合，才能直接约束两个实例层

- **位置**：`docs/proposals/workbench-shell-abstractions.md:71,116-124,187-189,215`；`docs/specs/ui/workbench-shell.md:216,281`；参照 `packages/neuro-book-legacy/app/utils/workbench/product-catalog.ts:399-436`、`app/components/workbench/WorkbenchContainerInstances.md:28-34,67-75`（同旧包）。
- **现象**：纯模型输出只列“各 ToolPart 的切片：Switcher 条目、选中容器、模式、可见视图”，但两层实例还需要未活动容器与已创建但当前不可见视图的保留依据。稿件没有列出这些集合与显示集合的关系。
- **为什么是问题**：若实例层只消费当前可见集合，切换容器就会把旧实例当作删除；若为保留实例自行扫注册表和落位，又形成第二套筛选。Spec 明确目标卸载要回常驻 parking，只有实际成员归零才退出容器；旧纯模型为此专门输出 `residentContainers`，不是复用当前选中项。现在的分层方向正确，但输出说明不足以直接成为纯 TS 的验证 seam。
- **如何核实**：对照稿件的输出描述、实例生命周期与 Spec 的 parking 验收，读取旧求值和容器实例合同确认常驻集合确有独立职责；没有运行 Teleport 场景。
- **建议改法**：给一份最小纯数据输入/输出示意：声明与可用性、完整持久化底本、内存选择/条件输入，输出实际成员、导航集合、选中切片、常驻资格、空态/不可用原因和诊断。组件、Element、load Promise 与“已创建”实例表仍留运行层。意图合成注明 rejected/unchanged/patch、来源/轴/锚点失效时整批拒绝，补丁只改主动字段；用切换容器、1→2→1、归零与隐藏、跨轴迟到提交的矩阵固定结果。无需在设计阶段写完整实现。

### 9. [阻断] 必须把实现撤回与声明删除分开，否则受阻恢复会清掉布局或保留已失效组件

- **位置**：`docs/proposals/workbench-shell-abstractions.md:120-124,152-155,215`；`docs/specs/runtime/plugins.md:30-33,55-59,65-66,95-107`；`docs/specs/runtime/plugin-manifest.md:98-104`。
- **现象**：稿件将“撤回与插件禁用”统一描述为释放实例、清理该插件布局项，又要求启用但受阻/失败时保留布局；实例销毁条件只列声明撤回、禁用、工作台释放，没有明确列贡献实现所属入口停止。没有给出实现撤回的独立状态转移。
- **为什么是问题**：现有内核的 `revoke` 不等于插件禁用或声明消失：普通入口停止产生 `scope-closed`，工作台接收者停止产生 `receiver-closed`，补交失败还有 `delivery-failed`；这些情况下静态声明可以仍在。Manifest 又要求运行入口因依赖不可用而先停止再受阻。若 t52 内部注册表把 revoke 当删除，恢复后用户位置会回默认；若按稿件列出的销毁条件保留已装载实例，停放层会继续引用停止入口的组件/闭包。两种自然实现都不能同时满足保留布局与撤回引用。
- **如何核实**：读取三层定义和清理规则，对照 implemented `runtime.plugins` 的撤回原因与目录状态表、planned Manifest 的受阻转移；这是未定义转换导致的合同缺口，没有宣称现有新工作台已发生泄漏。
- **建议改法**：补状态矩阵：用户隐藏/移动只停放；实现失效或所属入口停止时卸载组件、丢弃实现与 load 缓存、使当前代际失效，但保留声明和布局并显示原因；声明真正消失/插件禁用才按 P7 清理该视图布局项。`receiver-closed` 只清运行资源，不作为删除用户定制的意图；入口恢复后用新代次重新交付。布局清理按实际撤回的视图执行，不能误清同插件其它仍有效入口。

### 10. [建议] 分别定义激活、`load()` 与组件失败的重试，以及加载期间的代际失效

- **位置**：`docs/proposals/workbench-shell-abstractions.md:120-124,141-149,215`；`docs/proposals/extensible-application-platform.md:320`；`docs/specs/runtime/plugins.md:59,84,124`。
- **现象**：稿件规定组件出错时重建实例、代际加一，但实现层另有异步 `load()`；入口失败仅说显示原因，没有定义其重试与组件重建的区别，也没有说明 load 待决时禁用/重新启用后的完成判定。
- **为什么是问题**：组件错误、组件装载 Promise 失败和插件激活失败属于三个 owner。P7 明确错误边界“只覆盖 Vue 调用路径上的错误”，普通未被 Vue 接管的 Promise 不在其中；内核激活重试又要求上次资源先收口，不能用换组件 key 代替。按稿件只增加已创建实例的 generation，不能独自说明实例还未产生时如何拒绝旧 load 结果。具体实现尚不存在，因此不判定已发生异常穿透或旧实例复活。
- **如何核实**：对照异步实现签名、实例代际说明、P7 的错误边界限制和内核恢复前置条件。未运行异步竞态，也不将未验证风险当作已复现缺陷。
- **建议改法**：补三个失败类别及 owner：入口失败经内核显式恢复；load 失败由 View Host 捕获并允许重新装载；组件失败仅重建该视图实例。装载尝试绑定声明身份、实现入口代次与单调实例/请求代次，完成时复查仍有效；撤回清掉对组件、Promise 结果与旧上下文的引用。写清 `visible` 指当前显示而非已实例化/可用，停放与加载不等于可见。将待决 load→禁用→重新启用→旧结果完成、load 失败重试、组件失败重试列入 t52 局部宿主验证。

### 11. [建议] 公布 `ViewContext` 的投递协议与代际作用域，避免 Lab 和 Files 各自约定

- **位置**：`docs/proposals/workbench-shell-abstractions.md:141-150,231`；`docs/specs/workbench/commands.md:134,138`；`docs/specs/runtime/plugins.md:27,33`。
- **现象**：接口注释只说“组件收到 ViewContext”，没有指定是哪个 prop、工作台注入键还是实现工厂参数；generation 只说重建加一，没有指定同一 viewId 撤回再登记后是否复用编号。
- **为什么是问题**：组件 load 可以只负责取得组件定义，实例上下文稍后经 prop 传入，因此无参数 load 本身不是错误，也不必强改为 `load(context)`。缺的是消费者必须共同遵守的投递协议。另 `{viewId,generation}` 是命令迟到目标门禁：若计数随注册项一起删除再从初值开始，旧目标会与新实例重号；这是条件风险，尚无实现或复现，按建议处理。
- **如何核实**：检查完整实现/上下文签名，未发现组件 prop 或注入键约定；对照 refresh-files 的精确代际参数和内核独立激活代次。独立审查也指出同一协议缺口，但其“必然改 load 签名/必然复活”的判断缺少实现证据，本报告不采用。
- **建议改法**：明确组件经例如只读 `context: ViewContext` prop 收到上下文，或沿既有注入模式定义唯一合同，t52 样例与 Files 用同一路径；不要把 Component 定义加载与实例创建合成。规定工作台存活期内按 viewId 单调分配、撤回后不复用 generation，工作台重建时旧回调已失效；或用包含入口代次的不可复用 token。无需把运行代次写进布局记录。
