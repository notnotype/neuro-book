### F08（重要）停止条件只覆盖根丢失与显式 cancel，没有接远程请求的寿命信号

- **类别**：不变量 / 遗漏。
- **计划位置**：“批量操作”，plan.md:40–41；“验收映射”，plan.md:85,87；“验证”，plan.md:94。
- **现象**：计划逐项循环的停止条件只有 root-gone 与业务 cancel；files 验收 3 原文的绑定/授权失效被映射成了根不在。断线、调用方入口停止或提供入口停止时，根可以仍然存在。
- **为什么是问题**：一条批量 RPC 的路由授权只在接纳时通过，内核不会逐项重新派发、也不会中止方法内部的文件 I/O。若新循环不消费 `{signal}`，调用方已释放或项目正在收口后，余下 999 项仍可能继续修改文件。把客户端结果原样透出为 unknown-outcome 不等于停止这些尚未开始的副作用。
- **依据**：`docs/specs/workspace/files.md:52,71,73,110` 要求绑定/授权失效后停止后续项；`docs/specs/runtime/plugin-channel.md:59,95,165,167` 区分终止信号与物理终止。现有真实内核 `packages/nb-runtime/src/remote/node.ts:809–816` 在一次 ACK 后调用提供方法，并合并请求与提供方的 stopSignal；`backend/plugin.ts:37–47` 的短保存方法当前不消费此信号，不能直接复制到批量。此项是 t69 循环未规定消费边界的静态核实，实际批量还未实现。
- **建议改法**：把提供方法的真实 signal 传入同一个批量 runner；每项开始前检查它与显式 cancel。寿命失效与用户取消保留不同停止原因，已完成项不重复，当前项按实际结算；继续工作的 Promise/句柄登记到结算后再收口。用真实 content.xml 锁把第一项挡在清单提交中，窗口入口停止/断线/提供入口停止各验一次，释放锁后核对第二项没有文件或清单副作用，路由结果未知只按真实结果报告。不要另造一套项目代次表。

### F04（重要）“最多 1000 项”不能保证请求与逐项结果装进一条 RPC 消息

- **类别**：正确性 / 测试。
- **计划位置**：“批量操作”，plan.md:42；“浏览器客户端”，plan.md:58；“验证”，plan.md:93–94。
- **现象**：只有项数上限，没有 JSON 编码后的请求/结果字节预算或超限结算。1000 个各自合法且远小于 4096 字节的路径已经能超过真实 WebSocket 的 1 MiB 限制。
- **为什么是问题**：合法批量在客户端发出后会断线，调用方得到结果未知而不是可预测的输入拒绝；失败详情、清单诊断与递归残留还会增大返回消息。快速场地的进程内链路不限消息大小，不能自证这条约束。t68 已有正文的字节预算，但这里未复用同一边界。
- **依据**：实跑 `runtime-probe.ts`，通过生产 `startServer` 的真实 RPC 监听器连接 WebSocket：1000 个 path、每个约 1110 字节，按真实 `Frame` 编码为 `1115236` 字节，限制是 `1048576`；发出后实际 socket 关闭。所有路径段均为单段合法名、每段小于 255 字节，每条路径小于资源地址 4096 字节上限。该实验在提供方法存在与否的校验之前就被传输拒绝，因此无需伪造 t69 提供者。`docs/specs/runtime/plugin-channel.md:88–92,115` 规定已发出的写请求断线为 unknown-outcome；`docs/specs/workspace/resources.md:35` 固定地址上限；`shared/contracts.ts:27–35` 已有同类正文边界；`src/server/rpc/listener.ts:74–79` 使用该真实上限。
- **建议改法**：在发出前按编码字节做输入预算，两份合同提供者也核对；1000 仍可作为计算量上限，不称为消息保证。固定有界逐项结构与限长 detail，残留按最外层范围压缩；根据输入与最坏返回预算，不能同时容纳输入对齐结果的整批在任何副作用前拒绝。这样保留逐项结果而无需另建分页/结果存储协议。增加真实 WebSocket 的预算内/超限用例，变异掉客户端预算时必须观察到断线或断言失败。

### F09（重要）“同目标无操作”没有限定 move，复制自身/后代的拒绝判据缺失

- **类别**：正确性 / 测试。
- **计划位置**：“批量操作”，plan.md:39；“切片”，plan.md:76；“验收映射”，plan.md:85–86。
- **现象**：move/copy 共用的预处理写“目标等于源为 done（无操作）”，只给 move 写自身/后代拒绝；S3 也笼统验证“同目标无操作”。另一验收行却要求“同目录复制要求改名”，冲突没有在输入/用例上分开。
- **为什么是问题**：按这条测试实现，copy(A,A) 会错误报 done，消费方以为副本已生成。copy(dir,dir/child) 若没有单独拒绝，staging 就建在源树里，递归遍历可能把自己正在写的副本再次作为来源，至少不再是一个只读源的有限快照。这是循环结构带来的推断，t69 尚无代码，未运行这种可能无限生成的实验。
- **依据**：`docs/specs/workspace/files.md:47–48,52,115` 只对同目标移动承诺 no-op，对复制承诺实际副本、同目录须明确新名称；旧应用真实入口的合同测试 `workspace-files.test.ts:177–187` 对 copy(source,source/chapter/copy) 拒绝，给出既有边界参照。计划没有包含这一 copy 拒绝用例。
- **建议改法**：固定 move(A,A)=done 且零事件；copy(A,A)=conflict 且源不变；目录 copy 到自身后代=into-itself，必须在建 staging 前拒绝，并按 resolveEntry/resolveSlot 得到的真实父路径判断，不能只比字符串。分别覆盖普通路径与根内目录链接别名；后续独立项仍继续。变异掉 copy 的 containment 检查必须被这条真实入口测试拦住。

### F06（重要）只有源路径，t70 无法兑现“剪贴板源已被替换就拒绝”的合同

- **类别**：接口 / 遗漏。
- **计划位置**：“批量操作”，plan.md:38–39；“浏览器客户端”，plan.md:58；“不做与风险”，plan.md:98。
- **现象**：move/copy 输入只有 `{source,target}`，delete 只有 paths；没有捕获源目录项身份的入口，也没有提交时携带/核对 expected identity。t68 list/read 合同也不提供目录项身份。计划只把“剪贴板”整体交给 t70。
- **为什么是问题**：用户复制/剪切 A 后，外部把 A 改名并在同路径新建 B，稍后粘贴仍会按路径对 B 操作。即使 t70 先做一次 stat 检查，检查与提交之间再替换仍要服务端验证；这个服务端合同属于 t69。它不要求普通文件有永久 id，只要求冻结此次操作意图的源目录项。推给 t70 会返工 t69 的合同与实现。
- **依据**：`docs/specs/workbench/files-explorer.md:61,140` 明确“源消失或身份变化时拒绝旧意图”；`docs/specs/workspace/files.md:34,88` 要求提交时重验身份、类型/身份改变可区分；`shared/contracts.ts:52–61,80,105–111` 的列出、读取与现有方法没有此信息。旧应用只作可行性参照：`shared/dto/workspace-file-operation.dto.ts:11–25` 有 expectedSources；`server/workspace-history/tracked-workspace-files.ts:288–299` 比对 dev/ino/birthtime 后拒绝被替换的来源。此项是合同缺口的静态核实，未对尚未实现的 t69 操作运行复现。
- **建议改法**：在 t69 增加一个只读的批量目录项捕获入口，或在明确需要身份的列出查询中返回不暴露绝对路径的临时身份 token；避免为每次普通列出额外 stat 整层。操作输入携带该基线，在每项提交前按目录项（链接不跟随）核对。t70 只负责何时冻结/过期这个 token。测真实冻结 A → 外部换成 B → copy/move 拒绝、B 保留、后续独立项继续；另测父目录链接别名去重与硬链接两个目录项不误去重。无需引入持久身份数据库。

### F05（重要）把目录回声记成“还是 directory”会吞掉后续真实外部替换

- **类别**：正确性 / 状态设计。
- **计划位置**：“自己操作的回声”，plan.md:54；“切片”，plan.md:77。
- **现象**：预期登记的目录状态只有 `directory`；匹配就丢事件，只有不匹配才撤销。服务创建/移动了目录后，外部程序将它移走并换入另一目录，状态仍是 directory。若两次原始事件合并在一批，计划无法发现目录身份已经不同。
- **为什么是问题**：这不是同一次写入的回声，子树内容可能完全改变；已有消费者要重列父目录或该目录才能同步。只断言“没有外部重复事件”的 S4 用例会奖励这个错误实现。移动/复制目标整棵子树的回声处理也没有明确：不登记子文件会重复发外部事件，按 directory/subtree 直接忽略则会吞掉子文件的真实修改。
- **依据**：已通过原版 Files 的真实 `filesScene` 与 `fs.watch` 复现：外部移走 `target/`，换入包含 `nested/new.md` 的另一个目录，再等外部 barrier；旧 inode `12114807`、新 inode `12114808`，原版正确发出 `target`、`target/nested`、`target/nested/new.md` 的 external changed。两者 isDirectory 均为 true。按 plan.md:54 的谓词，父目录这条会被丢掉——这是对尚未写出的状态设计的推断，未变异仓库。`docs/specs/workspace/resources.md:77–78` 要求外部变化可观察、只去掉自己的回声；t68 的文件 hash 已在 `changes.test.ts:172–180` 保护“同长且恢复 mtime 的外部修改”。
- **建议改法**：目录登记最少携带操作后 dev/ino（链接另用 lstat 身份/readlink 内容）；匹配自己登记的目录项身份才抑制，身份改变即撤销并发 changed。沿操作已经遍历的 copy 子项登记其结果，不再额外全树扫描；move 若无法低成本证明子树各项状态，推有界 resync，不能粗略忽略整个目标子树。补“操作后同路径换目录”和“移动/复制后外部改子文件”的真实 watcher 用例；两者在 directory-only/blanket-subtree 变异下都必须失败。

### F10（重要）部分完成的结果字段未闭合，验收无法据返回值定位残留与两端清单

- **类别**：接口 / 验收映射。
- **计划位置**：“原语”，plan.md:16–17；“单项操作”，plan.md:24–31；“批量操作”，plan.md:40；“清单维护”，plan.md:47–49；“验收映射”，plan.md:87–88。
- **现象**：原语承诺复制清理失败报告残留、递归删除报告已删与未删；单项表只返回 `{path}`；批量结果列 `status/code/detail/path/manifest`，没有这些范围的结构；“清单维护”节却以 `done + manifest.status` 描述部分完成。在同一方案内跨两个内容树移动，涉及源、目标两份清单，只有一个未带地址的 manifest 诊断。
- **为什么是问题**：调用方不能仅据结果区分“全树已删”与“部分子项已删”，也不能判断迁移失败的是哪份清单。将范围塞进不固定的 detail 文案虽然能给人看，却不能支撑 t70 的逐项反馈、重列范围与不重复已成功项；验收“列出结果与清单文本”只证明某些文件变化，不证明调用方取得了完整部分结果。
- **依据**：`docs/specs/workspace/files.md:52,91,100,116` 要求返回逐项成功、残留与未知，部分成功不标全批完成；`docs/specs/workbench/files-explorer.md:63,100,143` 要求残留范围可见；`docs/specs/workspace/folder-kinds.md:100` 要求文件已改/清单未改的部分完成。t69 plan 在同一文件内的输出表与失败承诺不对应，静态核实成立，不需要伪造失败实现。
- **建议改法**：在 S0/S2 固定一个有界的 ItemResult，单项返回这一结构，批量返回其数组，减少两套结果约定。仅在相应状态带结构化的已改/残留范围；清单诊断包含相对资源地址，跨内容树为两条独立结果（成功与失败各可分辨）。残留压缩成最外层范围并与 F04 的字节预算一起定。补“文件成功/清单失败仍发文件事件、不发虚假的清单 changed”“只一端清单失败”和“递归删除部分失败仍报告范围及真实事件”的明确用例。

### F03（重要）取消句柄的交付时机和跨方案分派未定

- **类别**：接口 / 可实现性。
- **计划位置**：“批量操作”，plan.md:38–41；“浏览器客户端”，plan.md:58；“验收映射”，plan.md:87。
- **现象**：客户端生成 operation，返回 `{operation, result}`，取消入口是 `cancel(operation)`；但没有说明返回对象是同步句柄、`result` 是 Promise，还是沿现有客户端风格 await RPC 后返回的对象。也没有说明只拿 operation 的 cancel 如何在 project/user 两份合同间选目标。
- **为什么是问题**：沿现有 async 方法照字面实现，operation 只能在批量完成后取得，无法在第一项中发出取消；改为同步句柄也必须现在固定公开合同。为 cancel 再加 operation→scheme 注册表虽可实现，却让客户端多一份生命周期状态，正好是计划可减少的部件。t70 是调用方，不应到 UI 实施时才修这个合同。
- **依据**：`packages/neuro-book/src/plugins/files/web/client.ts:26–45` 的现有方法都等待远程结果；`shared/contracts.ts:162–166` 均为 Promise 返回；`docs/specs/workspace/files.md:76` 规定取消尚未开始项且不回滚；`docs/specs/runtime/plugin-channel.md:88–92` 证明直接中止已发出写 RPC 会丢失逐项结果。此项是公开返回形状的计划缺口，未声称现有实现已经有此 bug。
- **建议改法**：明确同步返回最小句柄，例如 `{result: Promise<FilesResult<BatchResult>>, cancel: () => Promise<CancelResult>}`，闭包捕获 operation 与 scheme；operation id 只在 RPC 边界存在，调用方无需再传回它或维护额外映射。服务端登记按完整调用方身份与 operation 分区，在 finally 删除，重用活动 id 明确拒绝；cancel 返回是否命中活动操作，以此为测试屏障。若保留 operation 公开，则直接规定调用方提供它和明确的方案目标。补真实窗口中“result 仍 pending 时能 cancel，第一项完成、第二项无副作用”的用例。

### F01（重要）“目标预先存在”的测试不能证明预检后的抢占仍被拒绝

- **类别**：测试。
- **计划位置**：“验收映射”，plan.md:86；“原语”，plan.md:13；“切片”，plan.md:74。
- **现象**：验收行写“预检后被占用时仍拒绝”，对应方法却只有“先建好目标再提交，得到 conflict、目标不变”。S1 同样只列目标已存在的测试。
- **为什么是问题**：在开始前检查 `exists(target)`、随后用普通 `rename` 的错误实现，也会通过这些测试；真正的回归只在检查之后、提交之前目标被其它进程占用时出现。因此这行与 files 验收 8 不对齐，逐判据变异检查也拦不住把排他提交改成覆盖式提交。
- **依据**：`docs/specs/workspace/files.md:34,52,115` 要求服务端在提交时排他重验，预检不授予资格；`docs/testing/README.md:24` 要求每条验收判据做变异检查。另实跑仓库外的 Linux syscall 屏障：先核对目标不存在，再通过 ptrace 停在真实 rename 系统调用入口，外部创建目标后继续。文件与空目录两种场景中，Bun FFI 的 `renameat2(RENAME_NOREPLACE)` 均返回 -1、源与外部目标均保留；普通 `rename` 均返回 0、覆盖外部目标。四个子进程退出码均为 0。这证明原语与变异判据可测，不是尚未实现的 t69 远程操作的运行结论。
- **建议改法**：保留“目标一开始就存在”的用例；另列直接调用排他原语的文件/空目录用例，以及真实远程 copy 的竞争用例。Linux 可从仓库外跟踪真实项目子进程，在最后提交目标的排他 rename 入口暂停、外部占用目标、再继续；必须匹配目标路径并跟踪实际执行 I/O 的线程。把 no-replace 变为普通 rename 时，外部目标保留的断言必须失败。`content.xml` 锁在计划的文件提交之后才取得，不能拿它当提交前竞争的屏障。若只能观察临时目录后抢占、不能保证仍未提交，标为竞态 smoke；其它平台的确定性屏障未验证。不要引入产品内测试专用 hook。

### F02（重要）权限故障夹具不成立，且“不 force”不能实现只读删除拒绝

- **类别**：测试 / 正确性。
- **计划位置**：“原语”，plan.md:16–17；“切片”，plan.md:74；“验收映射”，plan.md:87。
- **现象**：复制中途失败只给出“只读子目录”；删除以“不改权限、不 force”解释“只读子项删不掉”。真实 Linux 文件系统下，两者都不是充分条件。
- **为什么是问题**：源目录只读并不禁止读取/复制；普通文件的只读位不禁止在可写父目录里 unlink。照该夹具写测试会拿不到预期故障，或错误地以为它验证了故障路径。若希望产品按只读状态拒绝删除，仅依赖 OS unlink/rm 也会违反既有 files 的失败合同。
- **依据**：Bun `1.4.2`、uid `1000` 的真实权限实验中，源子目录 `0555` 时 `cp` 成功且副本字节为 `SOURCE`；`0444` 文件在可写父目录中 `unlink` 成功；源子目录 `0000` 时 `cp` 为 `EACCES`；含已创建文件的 staging 子目录 `0555` 时非 force 递归清理为 `EACCES`。另在独立子进程设置 `RLIMIT_FSIZE=4096`：小文件先复制成功，8192 字节文件实际产生 4096 字节副本后返回 `EFBIG`，源仍为 8192 字节，子进程退出 0。这些是计划所依赖的 OS 条件的真实实验，未冒充尚未实现的 t69 运行结果。`docs/specs/workspace/files.md:49,89` 要求不自动升级强删、服务端拒绝只读/无删除权限；`docs/testing/README.md:16,18` 要求真实依赖与状态等待。实际命令与证明范围列在报告后文。
- **建议改法**：复制故障可在隔离 Linux 子进程上设文件大小限制，以单个超过限制的真实文件证明复制过程中已有写入后失败；这不依赖 readdir 顺序。不可读源也可用，但必须先证明已有复制副作用。成功清理与清理失败分成两例，后者用真实不可写的 staging 子目录核对残留范围；不能把原语实验当成服务端结算通过。删除明确区分“只读文件位的产品拒绝”与“父目录无 write/search 权限的 OS 拒绝”，分别核对已删与未删范围。root、ACL、Windows 的权限场景按可制造的条件验收。

### F07（建议）S2/S3 的验证入口未固定，事件自证又依赖 S4 的回声实现

- **类别**：切片 / 测试。
- **计划位置**：“切片”，plan.md:75–77；“验收映射”，plan.md:84,88–89。
- **现象**：S2/S3 用“快速场地”验证单项、批量与事件，浏览器客户端方法直到 S4 才加；S2 已承诺核对磁盘、清单、事件，新的 absent/directory 回声到 S4 才实现。按计划的输入前置条件，reorder/display/createContent 只用于内容树，“每个单项操作在普通与内容文件夹各验一次”应区分支持与拒绝场景。
- **为什么是问题**：若沿 t68 的 `files(scene.window)` 门面写测试，S2/S3 的新方法不存在；若要求事件集合准确，则原版 watcher 会给新建/删除再发 external 回声。用直接内部 operations 函数验证虽能过，却不能证明远程接线和合同。切片本身能实现，但现在的“自跑验证”容易静默依赖后片，或者最后再补真实入口。
- **依据**：`testing/scene.ts:25–44,51–58,87–94` 同时提供真实 remote 与 filesKey 两个入口；`web/client.ts:26–55` 现阶段只提供 list/read/write/watch；`backend/changes.ts:168–185,199–205` 只登记保存 hash，缺失路径一定发 external deleted。这些机制已存在，故无需假设新的场地。
- **建议改法**：S2/S3 明确经 `remote(scene.window).use(projectFilesContract/userFilesContract)` 调新方法（真实窗口身份、真实路由、真实 Files），避免调用 operations 内部函数；每片只断言本片承诺的事件，精确且无回声的集合放在 S4。更好的切片是每加入一种写操作就同时补它的客户端入口和最小回声状态，S4 只留下真实项目进程/传输组合，减少一个暂时不完整的阶段。把“支持的场景”和“在普通文件夹拒绝且无副作用”的场景分开列，固定 S2/S3/S4 的实际测试文件、用例与命令。
