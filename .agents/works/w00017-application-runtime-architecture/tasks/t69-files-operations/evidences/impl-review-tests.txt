## T03（重要）：批量客户端漏算结构与 expected 字节，合法输入会断开真实 WebSocket

- **类别**：正确性 / 测试。
- **位置**：`packages/neuro-book/src/plugins/files/web/client.ts:37`、`:88`、`:271`；`transport.test.ts:107`。
- **现象**：`sameScheme` 只对字符串数组 `paths` 算编码大小；真正发出的 `items` 另含字段名、对象括号、每项 `expected`，还有 `operation`。真实探针使用 1000 个 `move` 项，每个源由 4 段 240 字节名字与 `a.md` 组成，目标 `t/0000.md` 等，每项带 32 字符身份令牌。地址数组 `983001` 字节，小于预算 `983040`；完整业务输入 `1049062` 字节，已大于 WebSocket 上限 `1048576`，帧包络还会增加字节。原实现发出了请求，调用得到 `{ok:false,code:"unknown-outcome",cause:"disconnected"}`；随后 `list("user://")` 得到 `unavailable/disconnected`。
- **为什么是问题**：Spec 要求超限在客户端发出前确定拒绝并保持连接；用户已冻结身份的正常批量不能被算成预算内再意外断线。提供者核对 `items` 来不及，因为超限帧在传输层就已被拒绝。现有传输测试只测 `delete` 地址数组、不带身份令牌，覆盖不了 `move/copy` 的结构开销。
- **依据**：`docs/specs/workspace/files.md:89`、`:90`；`docs/specs/runtime/plugin-channel.md:115`；Task `plan.md:67`、`:91`、`:112`。仓库源码未变异；仅在实验副本的 `transport.test.ts` 复用生产 `startServer`、RPC listener、Bun WebSocket、浏览器内核与 `filesKey` 客户端追加真实探针。命令 `NBOOK_AGENT_TEMP_ROOT=<本报告目录> bun test --tsconfig-override <本报告目录>/tsconfig.json <本报告目录>/app-src/plugins/files/transport.test.ts --test-name-pattern '完整 move 帧'`：0 pass、1 fail（25.73ms），失败原文为预期 `too-large`、实际 `unknown-outcome/disconnected`；第二次调用也已记录失败。全部路径段合法且小于 255 字节，条数为上限内。
- **建议改法**：在 `batch` 中先构造一次实际 `{operation,items}` 输入，再按其完整 JSON 字节预算判断，随后发送同一对象；三种批量共用该边界，减少 `sameScheme` 与 `send` 闭包之间的分离计算。增加真实 WebSocket 的 `move/copy/delete` 临界输入，包含 `expected` 和 JSON 转义，超限断言 `too-large` 且下一调用成功。

## T04（建议）：锁屏障与 WebSocket 窗口只在成功路径释放，失败等待会跑到下一用例

- **类别**：测试 / 不变量。
- **位置**：`packages/neuro-book/src/plugins/files/batch.test.ts:263`、`:278`、`:289`、`:302`、`:317`；`project-child.test.ts:245`；`transport.test.ts:108`、`:121`、`:132`、`:147`；`batch.test.ts:295`。
- **现象**：测试自己持有的清单锁没有 `try/finally`，`afterEach` 只关场地、删目录，不释放测试持锁句柄；锁获取后的等待或断言失败会跳过 `release`。WebSocket 的浏览器应用和 socket 只在用例最后 `window.close()`，没有登记到失败收口。断线例的状态等待与 Bun 用例均用 5000ms 截止，M05 实际出现测试已经超时后 `waitUntil` 才抛错的 `Unhandled error between tests`。
- **为什么是问题**：从代码推断，故障时继续持锁可能令场地关闭等到清单写的约 3.3s 退避预算耗尽；删目录不等于释放 proper-lockfile 的刷新计时器，也不关闭浏览器应用。M05 已实测原始失败后多出超时/后台错误，使变异结果和相邻测试难以归因。`transport` 两例共用一个后端和用户根，未正常结束的窗口可能带到下一例；本次没有复现原版窗口泄漏。
- **依据**：`docs/testing/README.md:20`、`:91`；`docs/specs/runtime/lifecycle.md:50`、`:54`。源代码直接核实正常路径以外无锁/窗口收口（推断失败后的持锁影响）；M05 的实际输出核实了跨用例异步错误。正常基线和 5 次重复均通过，不把它报告成常态资源泄漏。
- **建议改法**：所有测试持锁在 `try/finally` 释放；窗口统一登记到 `afterEach`，同时断言 `app.stop()` 返回 closed。条件等待截止小于用例截止，留出 finally/afterEach 的时间，失败时先结束自己启动的异步任务再结束用例。复用现有场地资源数组，不再建一套收口框架。
