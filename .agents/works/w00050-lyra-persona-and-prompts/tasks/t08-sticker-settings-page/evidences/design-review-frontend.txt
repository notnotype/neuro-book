### 1. 空表情包没有“添加”格也没有落点，新建后的第一步走不通
严重程度：阻断
类别：遗漏 / 照字面实现会返工
位置：计划“`stickers/web/`：页面”；Spec 输出 26、31；验收 9；草稿 `StickerPacksPageDraft.vue` 的 `lastGroup` 与网格模板

现象：草稿里“添加”格画在 `v-for="group in gridGroups"` 里面，只在 `lastGroup`（常用或其他的最后一组）末尾出现；`lastGroup` 在没有这两组时回落成字符串 `"common"`，但 `gridGroups` 里并没有这一组。`.sticker-sheet` 的高度由分组撑起，没有分组时高度为 0，`is-dragging` 的覆盖层（`inset` 绝对定位在 sheet 上）也是 0 高。
为什么是问题：输出 31 建好的包“只有一份写了 title 的清单”，零个表情；验收 9 的第一步就是“新建 cat、拖进 开心.png”。此时网格里没有“添加”格、也没有可以落的区域。同样的状态还有：导入的 zip 里没有图的情形（会被 `import-invalid` 挡掉，不算）、把包里最后一张图删光、只剩“认不出”或“没加进来”组但没有常用与其他组（也画不出“添加”格）。
建议：把“添加”格从分组里拿出来，作为网格区的固定成员：没有常用与其他组时单独占一块（带一句“把图片拖进来，或点这里添加”的空态，高度至少一个格子加组头），有这两组时仍跟在最后一组末尾（Spec 26 的位置不变）。拖放落点覆盖整个网格区，不依赖分组。Lab 加“空包”“只有认不出”两个场景，DOM 测试断言空包里能找到添加入口。同时 Spec 26 的“在常用或其他的最后一组末尾”要补一句“都没有时单独画”。

### 2. 导入冲突对话框：服务端只给文件名，画不出“要导入的”那一侧的缩略图
严重程度：重要
类别：接口与合同 / 与已定设计不一致
位置：计划“`stickers/backend/editor.ts`”的导入一条、“三条 HTTP 路由”的 `POST /import`；Spec 输出 36；决定 14；草稿 `conflict.webp`

现象：计划写 409 带“两边的显示名、表情数与前几个表情的文件名，页面据此画对话框”。但定稿的对话框（开发者在决定 14 同意）左右各是一排缩略图，右边是还没导入的包：此时冲突已判定，临时文件夹“删掉了”，图片没有取图地址，页面只拿到文件名画不出图。
为什么是问题：照字面做，右侧只能画文件名或灰框，与已同意的样子不符；要补救就得返工合同。还有几处没写：1）“另存为 cat-2”里的名字要由服务端定（`-2`、`-3` 取第一个空的），409 没带；页面自己从目录算会和服务端在竞态下不一致；2）冲突后“再带 `onConflict` 重传一次”意味着 64 MiB 的 zip 要传两遍，页面要一直持有 `File` 句柄（文件在这期间被改动或移走时读失败，没有处理）；3）对话框开着时“已有的”那个包可能被别处删除或改动，确认后 `pack-missing` 或结果与对话框所示不同。
建议：二选一并写进计划：a）409 里带右侧前 N 张图的缩小后的 data URL（每张限几 KB，总量限 100 KB 以内，同时带 `copyAs` 的包名），页面不再碰 zip；b）页面用 `fflate` 在浏览器里读 zip 的前几个图片画缩略图（只读本地 `File`，不依赖服务端），409 只给包名与数目。无论哪种，对话框确认时把 `pack-missing`、`pack-exists`（另存的名字又被占了）映射成文字，并说明 `File` 读失败的处理。

### 3. 拖放：只写了“拖进网格”，没有窗口兜底，落到别处整页会被浏览器导航走
严重程度：重要
类别：遗漏 / 对照参照（插件页已有的做法）
位置：计划“`StickerGrid.vue`（分组、格子、拖放）”；Spec 输出 26、29；参照 `plugins/plugins/web/components/PluginsPage.md` 的“拖入或选择文件夹”与 `nbook/ui/dropped-folder` 的 `dragHasFiles`、`readDrop`

现象：计划和草稿只在 `.sticker-sheet` 上画落点。没有写：1）窗口级兜底：含文件的 `dragover`、`drop` 一律 `preventDefault`，否则文件落在属性栏、标题、左栏或页面空白处时，浏览器把图片当文档打开、整个应用页面被导航走（插件页的 `.md` 专门写了这条，并解释了为什么落点要取整个设置窗口而不是页面根）；2）只认含文件的拖动（`types` 含 `Files`），页面内部元素的拖动（例如选中文字）不亮覆盖层；3）`dragenter/dragleave` 在子元素之间冒泡会让覆盖层闪烁，要用计数或 `relatedTarget` 判断；插件页的做法是离开窗口（`relatedTarget` 为空）才收起；4）插件的只读包上拖入：要显示“不能拖进来”（`dropEffect = "none"`）并忽略，计划只说“我的包”有添加；5）上传或导入进行中、对话框开着时再拖入怎么办；6）一次拖进来的文件夹或非图片（`.txt`）：由后端按 `image-rejected` 拒绝，但拖进来的“文件夹”条目 `File.size` 为 0，会产生一条莫名的“类型不符”。
建议：复用 `dragHasFiles` 与插件页同一套窗口兜底（挂载期间监听、卸载时移除），在计划的页面小节写明这六点，DOM 测试里补“落在属性栏不导航”（断言 `defaultPrevented`）与“只读包 dropEffect 为 none”。

### 4. 添加图片：没有“选择文件”入口，进行中没有任何显示，上传的归属没写
严重程度：重要
类别：交互状态遗漏 / 可测性
位置：计划“三条 HTTP 路由”的 `PUT .../images/<文件名>`（“页面一张一张传，几张并发至多 3 个”）、验收映射；Spec 输出 29；验收 9

现象：1）Spec 29“一次可以选或拖进多张”，草稿的“添加”格是个 `button`，没有写它打开隐藏的 `<input type="file" multiple accept="image/*">`，也没写选完要清空（选同一张再选才会再触发，插件页的 `.md` 专门写了这条）。验收 9 的“拖进 `开心.png`”在 Playwright 里无法真拖操作系统文件，只能对这个 input 用 `setInputFiles`，所以这个 input 是 e2e 的入口，必须在计划里存在并带稳定的 `data-*`。2）上传期间页面上没有任何变化：32 MiB 的手机照片、一次 20 张，等几秒到几十秒才出现第一个格子，用户不知道有没有在传。没有占位格、进度或“正在添加 N 张”的显示，也没写期间“添加”格与“全部加进来”是否可用。3）上传队列的归属没写：用户在上传中切到别的包、改包名（路由里的包 id 随之失效，后面几张得 `pack-missing`）、删包、关设置窗口，已发出的与未发出的怎么办；通知里的文件名没有包名，切走后读不出是哪个包的。4）后端先写图片再在清单末尾加项，两步之间若被一次重扫看到，这张图会先出现在“没加进来”组再跳到“其他”，格子位置闪一下；计划只说“150ms 内合并”。
建议：计划页面小节补：隐藏 input 与清空；占位格（带文件名与转圈，失败后消失并进汇总通知）；队列放在 `packs-page.ts`，按包 id 记，切走不取消，改包名或删包时先等该包的队列清空或禁用这两个入口；汇总通知写“加到 <包名>”。后端侧建议图片与清单同组写完后再触发重扫，或页面对刚上传的文件名在重扫结果里压住“没加进来”分组一小段时间，二者取其简单者。

### 5. 属性栏字段的提交合同没定，草稿也与 nb-ui 的校验规范相冲
严重程度：重要
类别：交互状态遗漏 / 对照参照
位置：计划“`packs-page.ts`”；Spec 输出 28、31、27；草稿 `.sticker-panel__error`、`<Input :model-value>`；`packages/nb-ui/docs/ui-development-spec.md` 第 5 节第 7 条；`NewProfileDialog.vue`

现象与问题：
1）提交时机未定。nb-ui `Input` 只发 `update:modelValue`（每次输入）与 `focus`，原生的 `change`、`blur`、`keydown` 要作为 attrs 落到原生 input 上。草稿是 `:model-value` 单向绑定，真实实现必须有本地草稿，否则打字上不了屏。计划没写：名字、说明是失焦（`change`）还是回车提交；说明是 `Textarea`，回车是换行，只能失焦；Esc 是否还原；与 Profile 页不同，Profile 页控件都是即时选择，没有这种打字提交的先例，不能照抄。
2）切换选中时的提交：点另一个格子会先让输入框失焦（`change` 触发）再 click，应以提交那一刻捕获的 `file` 为目标，不读当前选中；用 `:key="file"` 重挂载属性栏时，Chrome 对被移除的聚焦元素不一定发 `blur`，所以别用 blur，用 `change`，或在选中变化的 watch 里显式冲刷。
3）写入中再改、写入失败：Profile 页的做法是 `pendingEdits`（写成功才更新快照，队列清空后回到服务端值，失败即回到实际值）。表情包没有这个设施，计划只写了“写入走远程方法，失败走通知”。需写明：本地草稿在写入返回前保持显示；返回失败则回到目录里的值；同一包的写入串行（两次 `files.update` 并发只会靠 3 次冲突重试撞出来）；写入期间收到 `changed`，不能把正在输入的草稿覆盖。
4）名字清空的含义：Spec 允许名字省略（取文件名）。清空输入框是“恢复成文件名”还是不合规？没写；认不出的图清空后仍不合规。
5）校验时机与位置：Spec 28、31 写“在输入框下写原因”，草稿也是在字段下插一行 `p`。规范第 7 条明确禁止出错时在字段下插入文字（会改变排版），且“提交之后才知道的错”才标红并得到焦点，看得见的原因写在固定位置（对话框是页脚状态行，`Dialog` 的 `status`）。属性栏里没有页脚。草稿的这行 `p` 同时在 `Field` 之外，没有 `aria-describedby`、`aria-invalid` 的关联。
建议：计划补一小节“字段提交”：change 提交、Esc 还原、写入串行、草稿保持；校验错用 `Field` 的 `error`（只标红、读屏有关联）加属性栏里一个固定高度的状态行（或名字旁的 InfoTip），并同步改 Spec 28、31 的措辞；两个对话框用 `Dialog.status`（`NewProfileDialog` 的写法，含“提交过一次才标红”）。

### 6. “选中新包”与“选中的包没了回到第一项”冲突：改包名后会跳走，新建后可能被弹回
严重程度：重要
类别：合同冲突 / 时序
位置：Spec 输出 25、31、32、33、36、38；计划“`packs-page.ts`”（“先订阅 changed 再取 packs 与选中包的 pack，晚到的旧结果丢掉”）；参照 `profile-page.ts` 的 `createProfile`（`await load()` 之后才选）

现象：1）输出 25 写“选中的表情包没了（删了、改了包名）时回到第一项”，输出 33 说改包名“id 随之变”。照字面实现，用户改完包名页面就跳到第一项，用户要在左栏重新找。这显然不是想要的：新建、复制、导入后都选中新包，改名后也应选中改名后的包。2）新建、复制、导入、改名都要“选中新 id”。重扫有 150ms 合并，写入的远程调用返回时，`packs` 里未必已有这个 id；若页面立刻 `selected = newId`，“选中的没了就回第一项”的 watch 会马上把它弹回第一项。Profile 页靠 `createUserProfile` 交回时目录里一定已有它、并 `await load()` 再选来避免；计划没写表情包这几个方法有没有同样的承诺，`renamePack`、`createPack`、`copyPack`、导入的返回值（是否带新 id）也没写。3）改名时 `pack(id)` 详情请求、选中的表情（按 `file` 记）、打开着的属性栏草稿，都要随 id 迁移还是清空，没写。
建议：合同里定：这几个方法返回新的 `{id}`，并保证返回时目录已含它（服务端 `catalog.settled()` 之后再返回，现有 `catalog.ts` 已有 `settled()`）；页面对返回的 id 做“等到它出现在 `packs` 里再选”，超时（比如目录取失败）才回第一项。输出 25 改成“选中的包没了（被别处删掉）时回到第一项；改名、新建、复制、导入后选中结果包”，并在页面 DOM 测试里覆盖改名后仍选中。

### 7. 页面级状态缺：加载中、读失败、无效的表情包、没有缩略图的包
严重程度：重要
类别：交互状态遗漏 / 对照参照
位置：计划“`StickerPacksPage.vue`（整页与选中、对话框的开关）”；Spec 输出 25、26、38 与第 2 条（无效包）；草稿的 `EmptyState`、`thumbOf`；`ProfileSettingsPage.vue` 的 `state: "loading" | "ready" | {failed}`

现象：1）Profile 页有加载中（转圈）、读失败（图标加原因加“重试”，`role="alert"`）、已显示时重取失败不换成失败态；草稿只有一个“还没有表情包”的 `EmptyState`。照草稿做，目录还没到、服务不可用、`packs` 调用失败的时候页面都会显示“还没有表情包”。2）`StickerPackSummary` 里本来就有 `status: "invalid"` 与 `problem`（`stickers.json` 读不懂、文件夹名不合规、文件夹是链接等），Spec 第 2 条“照样列出”。设计稿、计划、输出 25 到 38 对无效包一个字没提：左栏行怎么画（0 个表情、没有缩略图）、右边显示什么（原因要写出来）、哪些操作可用（“在文件夹中显示”与“删除表情包”应该可用，改包名对 `folder-name` 不合规的包是唯一的修复手段，导出对读不懂的清单应不可用）、`pack(id)` 与 `updatePack` 在清单坏了时返回什么。用户手改清单改坏时，这是最需要这个页面的时候。3）`thumbnail` 为 null（零表情的新包、无效包）：草稿 `thumbOf` 取 `item.stickers[0]!`，零表情时是 `undefined`，真实数据下会抛错；左栏要有占位图标。4）“第一次打开选中第一项”：`packs` 按 id 码元排序，插件包的 id（如 `acme…`）会排在 `user.` 前面，页面上“我的”组在最前，选 `packs[0]` 会选中插件包；应取分组后的第一项。
建议：页面接口加 `state`，沿用 Profile 页三态；无效包写进计划与 Spec 输出 26（右边显示原因、可用操作表）；缩略图缺失时用图标；第一项按分组后的顺序取。

### 8. 左栏的“有认不出的图”提示图标，概要里没有数据来源
严重程度：重要
类别：接口与合同 / 与已定设计一致性
位置：计划“`stickers/backend/catalog.ts`：目录多记两样”（“`extras` 只进新的详情接口，不进浏览器目录与概要”）；Spec 输出 25；`stickers/shared/contracts.ts` 的 `PackSummarySchema`

现象：Spec 25 要求左栏行“有认不出的图时行尾出提示图标”，草稿截图里 cat 行也有。左栏的数据来自 `packs`（概要）。核对 `PackSummarySchema`：字段是 `status`、`problem`（只是整包无效的原因码）、`count`（有效表情数）、`thumbnail`，没有任何“认不出”或“没加进来”的信息；计划又明说 `extras` 不进概要。左栏要画这个图标，只能对每个包都调一次 `pack(id)`（N 次请求，还要订阅每次变化）。
为什么是问题：计划的页面与后端两节各自成立，合起来这条 Spec 实现不了；到第 4 片才发现要改概要合同，会回头改第 1 片。
建议：概要加 `unrecognized: number`（认不出的个数）与可选的 `unlisted: number`（没加进来的个数，决定要不要也提示），一个整数不影响字节预算；计划第 1 片写进去，并在 Spec 25 写明图标提示的是哪几类（草稿的图标提示文字是“有图片认不出”，没加进来的是否也提示，没定）。

### 9. `stickerAllowlistUsageKey`：激活顺序可能成环，“all”声明的语义不对，异步状态没写
严重程度：重要
类别：依赖的机制 / 时序 / 合同（从代码与 Spec 推断，未在运行时验证）
位置：计划“`stickers/shared/contracts.ts`”（浏览器服务键）、“`agent/web/`：白名单用到哪些 Profile”；Spec 输出 33；`docs/specs/runtime/services.md` 的“依赖环”；`stickers/web/plugin.ts`、`markdown/web/plugin.ts:96,136`、`agent/web/plugin.ts:171`

现象与问题：
1）环。表情包浏览器入口要可选依赖 Agent 浏览器入口提供的这个键；Agent 浏览器入口必需依赖 `markdownKey`；`nbook.markdown` 浏览器入口在 `activate` 里 `await context.services.resolve(stickerResolverKey)`，而该键正是表情包浏览器入口提供的。成环：stickers → agent → markdown → stickers。`services.md` 写“静态环（可选依赖的边也算）在装配阶段拒绝”，运行期的等待环也检测。我看了 `nb-runtime/src/plugins/blocked.ts` 的静态边只数 `required !== false` 的依赖，所以静态检查可能放过，但 `services.md` 与实现不一致本身就说明这条路径未被验证；若表情包入口在 `activate` 里 `resolve` 这个键，运行期等待环成立。计划没有写入口怎么接、也没有这条装配的测试。
2）没有它时：只写“不列 Profile”。但 Spec 33 要求的另一半（改名后要去 Profile 页重新勾选）仍应在文字里保留，不能因为键不在就整段警告消失。
3）“白名单里有这个 id 的 Profile”对声明 `allowed: "all"` 的 Profile 会算上（`declaredAllowlist` 把 `"all"` 展开成目录全部 id），但这类 Profile 改名后自动含新 id，不需要重新勾选，列出来是误报。应只列“显式写了这个 id”的：声明 `allowed` 数组里有它，或用户加的 `added` 里有它，且不在 `removed`。
4）`profilesUsing(packId): Promise` 是异步的（要取 Profile 目录），改名对话框打开到它回来之间怎么显示、失败怎么办、确认按钮是否等它，没写。
建议：1）把键的提供放在 Agent 的一个单独的轻量浏览器入口（只依赖 `settingsKey` 与远程合同，不依赖 `markdownKey`），或改成表情包定义贡献点、Agent 往里贡献（贡献不是服务依赖，不成环）；先写一个最小的装配测试确认启动顺序。2）无键时对话框仍写通用的“用到它的 Profile 要重新勾选”。3）改成“显式列出”的判断并在 Spec 33 写明。4）对话框打开时发起、显示“正在查找用到它的 Profile”，失败时按未知写通用文字，确认不被它挡住。

### 10. 窄窗口：属性栏排到网格下面后选了格子看不到变化；只有一个 600px 断点；草稿不是容器查询
严重程度：重要
类别：别扭 / 对照参照
位置：Spec 输出 25、27（“窄时属性栏排到网格下面”）；草稿 `narrow` 常量与 `.is-narrow`；`ProfileSettingsPage.vue` 的 `@container (max-width: 600px)`；截图 `narrow.webp`、`main.webp`

现象：1）窄时属性栏静态排在整个网格下面（`narrow.webp`）。网格可以有几百个表情、几千像素高，点一个格子后属性栏在屏幕外，页面上看不到任何反应；删除、改名这些操作要先滚到最底。草稿里的 `position: sticky` 在窄时被取消，没有补偿（选中后滚动到属性栏、或固定在底部）。2）草稿把“左栏收成下拉”和“属性栏排到下面”绑在同一个 `narrow` 上（场景属性 `scene === 'narrow'`，不是查询）。真实页面在 `.profile-page` 那样的容器查询里：页面宽 601px 时，左栏 168 加间距 20、属性栏 232 加间距 20 之后，网格只剩约 160px，两列都勉强；`main.webp` 约 900px 窗口也只有 4 列。属性栏下排应有自己的、更大的阈值（按网格能不能放下约 3 列算，大约 760px 以上才并排），与 600px 的左栏断点分开。3）属性栏在 sticky 时高度约 490px（预览 144、名字、说明、写法、开关、元信息、删除），比 600px 高的设置窗口内容区高，sticky 元素比滚动视口还高时，下半段（“删除表情”）无法与网格同时看到。
建议：窄时不要把属性栏排在末尾，改成点选后从下方弹出的 `Drawer` 或固定在底部的一栏（选中时出现，关闭回到网格）；至少选中时 `scrollIntoView` 到属性栏。两个断点分别用容器查询，不要用 prop。sticky 的属性栏给 `max-height` 与自己的滚动。Lab 的 390 宽场景必须选中一个表情后截图（现有 `narrow` 场景选中了“开心”，但截图只看到顶部，属性栏在可视区外，没人会发现这个问题）。

### 11. 网格的键盘与读屏语义没有设计；焦点去处没写
严重程度：重要
类别：无障碍 / 交互状态遗漏
位置：计划“`StickerGrid.vue`”；Spec 输出 26、27、30；草稿 `.sticker-tile` 与网格模板；`ProfileRail.vue`（roving tabindex 与方向键）、`ProfileSettingsPage.vue` 的 `onRemoveClosed`（输出 23）

现象与问题：
1）Tab 次序：每个格子都是 `<button>`，没有 roving tabindex，一个包最多 500 个表情加 500 个没加进来的，Tab 要按上千次才出网格去到属性栏。`ProfileRail` 已有 roving tabindex 加方向键的先例，计划没有对应设计。需要定：方向键（含 Home、End、跨组的上下换行）移动选中、Enter 或空格选中、Delete 删除（先确认）、Esc 取消选中。
2）语义：草稿用 `aria-pressed` 的按钮，语义是“切换按钮”，不是“选中某一项”。网格是单选的一组，更合适的是 `role="listbox"` 加 `role="option"` 与 `aria-selected`，或 `radiogroup`；若保留 `aria-pressed`，选中同一个再点会取消选中，这是 `aria-pressed` 的语义但没有任何可见提示。
3）读屏名字重复：格子里 `<img :alt="item.name">` 与下面的 `<span class="sticker-tile__name">` 是同一个名字，读成“开心 开心”；缩略图在有文字名时应 `alt=""`。认不出与没加进来的 `alt` 是（不合规的）名字，而文字是文件名，两者不同。组头（“常用 4”）是 `div`，没有 `role="group"` 加 `aria-labelledby` 或标题元素，读屏无法按组跳转。`title` 里放写法只对鼠标有用。
4）取消选中的入口：回到“表情包属性”（改包名、显示名、说明）要“再点一次选中的格子”，既没有可见提示也没有按钮，键盘用户靠 `aria-pressed` 才可能碰到。需要一个“返回表情包”的显式入口（属性栏顶上“‹ 星璃”，或点网格空白处）。
5）焦点去处：删除表情后属性栏的“删除表情”按钮消失，焦点落到 `body`；删除表情包、关闭改名与冲突对话框同理。Profile 页用 `closed` 事件加 `removal` promise 等关闭动画结束再 `focus()`，并有窄布局回落到下拉的选择器列表（输出 23）。计划没写表情包页的等价做法：删表情后应落到下一个格子（没有则上一个、再没有则“添加”格）；删包后落到新选中的左栏项（窄时是下拉）；对话框关闭后回到触发它的“更多”按钮；冲突对话框的取消也回到“导入 zip”。
6）格子名字单行截断（`text-overflow: ellipsis`），只有 `title` 给全名，英文长名在 72px 宽的格子里只剩十来个字符；全名在属性栏里能看到，可以接受，但要在 Lab 英文场景里确认。
建议：计划页面小节补“键盘与焦点”：用 listbox 或 radiogroup 的语义、roving tabindex、方向键与 Delete/Esc 行为表、删除后的焦点去处；组头用标题元素；alt 去重；属性栏加“返回”。DOM 测试补方向键移动与删除后的焦点位置。

### 12. 七个组件的 props 与事件一个也没定义；属性栏混了五种形态；同一件事写了几份
严重程度：重要
类别：接口与合同 / 别扭
位置：计划“`stickers/web/`：页面”；`ProfileSettingsPage.md`、`profile-page.ts`、`agent/web/sticker-packs.ts`、`agent/web/components/ProfileRail.vue`、`plugins/models/web/components/ProvidersPage.vue`

现象与问题：
1）计划只列了组件名。Profile 页的做法是：页面组件吃 `state`、视图模型、`writable`，改动用 emit，需要把失败原因回给对话框的用 `(…) => Promise<string | null>` 回调（`createProfile`、`addTools`），包装层负责取数与写入。表情包页要把哪些写入做成回调（新建、改名、导入、导出、复制、删除表情包、添加图片、改字段）、哪些是 emit、对话框的 `busy`/`status` 谁持有，都没写；第 4 片写 DOM 测试和 Lab 场景之前，这份接口必须先有（每个组件的同名 `.md` 也要写 props 表）。
2）`StickerPanel.vue` “属性栏的两种内容”其实是五种：表情（可改）、表情（插件只读）、认不出的（要改名才算表情）、没加进来的（只有两个按钮）、没选表情时的表情包（可改、只读）。五种放一个组件，里面全是 `v-if`，字段提交、校验、写入各自不同。建议拆成 `StickerFields`（表情的三种）与 `PackFields`（表情包），`StickerPanel` 只做切换与外框。
3）`NewStickerPackDialog` 与 `RenameStickerPackDialog` 的骨架相同（包名输入、校验、`Dialog.status`、busy、提交后焦点回输入框，即 `NewProfileDialog` 那套），差别只是多一个显示名与一块警告。写两份会在校验与焦点上漂移，建议一个 `StickerPackNameDialog`，`mode` 区分。
4）`packs-page.ts` 自己取 `packs` 并订阅 `changed`，与 `agent/web/sticker-packs.ts` 的 `createStickerPacksClient` 是同一件事（订阅加取概要加丢旧结果）。现在这个文件在 Agent 一侧，表情包插件里再写一份就是两份。建议把它挪成表情包插件的浏览器服务，Agent 和页面共用一个订阅；计划已经要改 Agent 的 `stickerAllowlistUsageKey`，顺手可改。
5）左栏第三份：`ProvidersPage`、`ProfileRail`、现在的 `StickerPackRail` 都是“分组列表加 600px 以下收成下拉加新建”。不一定要在这次抽公共组件，但计划里应写明“有意复制，原因”，并保留 `ProfileRail` 的键盘行为（草稿的左栏没有 roving tabindex 与方向键，也没有 `disabled`）。
建议：计划页面小节补一张接口表（每个组件的 props、emit、回调），拆分按第 2、3 点调整。

### 13. `writable` 对表情包页的含义没定
严重程度：建议
类别：遗漏 / 对照参照
位置：计划“登记”（`layers: ["user"]`）；`settings/web/contracts.ts` 的 `SettingsPageContext.writable`；Profile 页输出 20

现象：`writable` 是“当前标签那一层的设置能不能写”（层 `invalid`、`unavailable` 时为假），Profile 页据此停用所有写控件，因为它写的就是这层设置。表情包页写的是 `user://stickers/` 的文件，与设置文件的状态无关：用户设置文件读坏时，Profile 页整页只读，而表情包页仍能写文件。计划没说照不照 `writable`。
为什么是问题：两种选择都合理但结果不同（设置文件坏了时表情包页要不要也不让写），实现者会随手选一个，而 DOM 测试与 Lab 的“只读层”场景要对应。
建议：写明“表情包页不看 `writable`”（它不写设置），理由是写入对象不同；仍然对插件来源的包只读。若要照 `writable`，要说明理由。

### 14. 草稿里与决定、Spec 或计划相反的地方：照“实现照它的版式与类名”会带进去
严重程度：重要
类别：与已定设计不一致 / 照字面实现会返工
位置：草稿 `StickerPacksPageDraft.vue`、`samples.ts`；决定 16；Spec 输出 28、33；计划“`stickers/web/`”（“选中的表情按 `file` 记”）

现象（逐项，行为是静态稿写死的文字或数据结构，不是版式）：
1）改包名对话框的警告是“……Profile 里选了它的照常可用。”（草稿 `Banner message`）。决定 16 和 Spec 33 都改成“要去 Profile 页重新勾选”，决定 16 还说“第 2 轮稿里‘照常可用’一句改掉”，草稿里没改。
2）认不出的图的名字提示是“……改好后文件跟着改名。”。Spec 28 写“文件不改名”，决定 17 也是“文件不改名”；Spec 28 的清单写入对认不出的图是新增一项 `{file, name}`，文件名不动。
3）草稿以 `item.name` 作 `:key` 与选中标识（`selectedSticker`、`v-for :key="item.name"`）。认不出的图名取自文件名主干，`1.png` 与 `1.jpg` 同名为 `1`，会出现重复 key；计划写“按 `file` 记”，草稿要改成 `file`。

5）草稿全是中文字面量，没有走文字目录；计划已说“中英两份”，实施时要逐条迁移，别把“改成 xingli”这类带插值的整句拼接留着（英文语序不同，用占位符）。
建议：计划里加一条“静态稿只定版式，下列文字与数据以 Spec 为准”，并列出这几项；第 4 片的 DOM 测试断言改名对话框里写了“重新勾选”。

### 15. 写入失败的通知通道、结果未知与导出失败没有写
严重程度：建议
类别：交互状态遗漏 / 对照参照
位置：计划“`packs-page.ts`”（“失败走工作台通知”）、“`GET /export/<id>`”；Spec 失败表“表情包页”几行；`settings/web/contracts.ts` 的 `reportWriteFailure`；`skills-page.ts` 的 `notify`

现象与问题：
1）设置页有专门的失败通道 `context.reportWriteFailure(subject, {reason, uncertain})`，文案、色调与别的分区一致，晚到的失败离开页面后照样通知；Profile 页用它，Skill 页用 `notifications.notify` 发自定义通知。计划只说“工作台通知”，没有选。表情包写入是“用户操作的写入没成功”，与 `reportWriteFailure` 的意图一致，应选它。
2）结果未知：导入替换、上传 32 MiB 的图走 `fetch`，连接中途断了（`TypeError`、请求已发出）时服务端可能已写完。`reportWriteFailure` 的 `uncertain` 正是为此（标题变成“可能没有保存”）；计划与失败码表里都没有“网络断了”这一类，页面会把它当 `image-rejected` 或无码错误处理。
3）失败码映射：计划说“页面把码映射成文字，不按文案分支”，但没列出每个码对应的页面反应（哪个码在输入框、哪个在通知、哪个触发重取）。`conflict`（清单写入冲突 3 次后仍失败）、`pack-missing`、`sticker-missing` 应触发重取目录并提示“已被别处改动”。
4）导出用 `<a href download>` 还是 `fetch`→`Blob`：前者失败（`pack-missing` 404、413）时浏览器只在下载栏里显示“失败”，页面没有任何提示；后者可通知，但大包要整包进浏览器内存（计划里极端情形 1 GiB）。需选一个并写明失败怎么提示，倾向 `fetch` 失败时给通知、成功时再用 `a[download]` 的 blob URL（包都不大）。
建议：计划页面小节写：用 `reportWriteFailure`；网络断开按 `uncertain`；一张“码 → 页面反应”的小表；导出方式与失败提示。

### 16. 网格里 500 张原图全量解码，没有懒加载
严重程度：建议
类别：别扭 / 性能
位置：计划“取图路由放宽一条”；草稿 `<img :src>`；Spec 输出 36（“导入的图片不缩小”）、`IMAGE_MAX_BYTES`、`STICKERS_PER_PACK_MAX`

现象：网格每格是 72px，但 `<img>` 取的是原图地址（每张至多 2 MiB、1024 像素；导入的包不缩小，只按目录规则核对）。一个满的包是 500 个表情，加最多 500 个没加进来的图，浏览器一次请求并解码上千张大图，主线程会卡；左栏每个包一张缩略图也是原图。取图地址带 `?v=` 且 `immutable`，第二次便宜，第一次不便宜。
建议：格子里的 `<img>` 加 `loading="lazy"` 与 `decoding="async"`，分组容器加 `content-visibility: auto` 与 `contain-intrinsic-size`；不新增缩略图接口（加了要同步缓存与版本，得不偿失）。计划页面小节补一行；Lab 场景加一个 200 个表情的包看滚动。

### 17. 验收映射把页面行为都映到后端用例上；e2e 的“拖进”没法照字面做
严重程度：建议
类别：验收映射与可测性
位置：计划“验收映射”“切片 4”；Spec 验收 9、10；Spec 输出 28、29、30、31、32、34、36 与失败表“表情包页”行

现象：1）映射表里“输出 28、30、31、32、33、34”只指向第 2 片后端用例；“失败表的五行”只指向第 2、3 片。但输出 28（输入框下写原因）、29（加完后一条通知列出文件名与原因，几张并发）、30（“全部加进来”）、31、32（建好或复制后选中新包）、34（确认框写出包名与表情数）、36（冲突对话框对照）和失败表“不写，通知写原因；页面按重扫后的目录显示”里的页面一半，都是页面的行为，第 4 片列出的 DOM 测试只有“选中、分组、改名不合规、冲突对话框、跟着目录变”，缺：上传并发与汇总通知、删除确认文字、改名警告里的 Profile 列表、拖放覆盖层与兜底、键盘、写入失败回到实际值、插件只读包、选中的包被别处删掉、对话框里目标包已消失。
2）验收 9 的“拖进 `开心.png` 与一张 2000×1500 的 `大图.jpg`”在 Playwright 里不能拖真文件，只能对隐藏的 file input 用 `setInputFiles`，或构造 `DataTransfer`；“导出、再导入刚才的 zip”要接 `download` 事件、落盘、再 `setInputFiles`。这些要在计划里写成约定（file input 的 `data-*`、下载文件名）；否则 e2e 写到一半才发现入口缺。
3）可测性：Profile 页的做法是页面组件只吃普通属性，包装 `profile-page.ts` 吃依赖，DOM 测试可以直接摆页面组件。计划同样拆了 `packs-page.ts`，但没写它的依赖注入形状（远程客户端、`fetch`、通知、用途键），不写就测不了“并发至多 3”“写入失败回退”。
建议：映射表按“页面一半”与“后端一半”拆开；第 4 片 DOM 测试清单补上述项；写明 e2e 用 file input 与 `download` 事件；`packs-page.ts` 的依赖用一个 `deps` 对象（同 `ProfilePageDeps`）。
