### 2. 新前缀仍不是暂存归属，恢复也缺少原名和提交阶段
严重程度：阻断；类别：不变量。位置：计划 36、61、116、146；Spec 输出 36、失败表 184；`files/backend/commit.ts:92–120`。
现象：切片 1 按前缀递归删，名称相符的用户目录仍会被删，此时切片 3 甚至还未生产这些目录。`.nbook-stickers-replaced-<随机>` 不带原名，计划也无记录。即使另存原名，“空着再改回”不是原子判断：其它写入可能抢占；若原来已成功发布新包、清理旧备份前中断，而新包后来被用户删除，仅凭目标空闲又会复活旧包。
为什么：缩窄前缀减少碰撞，不改变数据删除权限；恢复不能把新包占位、成功后删除与未提交都当成一类。
如何核实：从设计及代码推断。分别覆盖同前缀用户目录、两次改名之间中断、发布后清理前中断、恢复检查后被占位；断言不覆盖、不误删、不复活已确认提交的旧包。
建议改法：先定义受管理的暂存位置、可核验归属、原名和阶段记录，再启用清理。恢复先于发布可写入口，仍用排他改名和源 `expected`，冲突保留并诊断；不明阶段不删除也不擅自恢复。移动恢复登记到同一切片，先写清启动副作用。

### 3. `identify` 能区分通常的同名新目录，但令牌必须绑定实际展示与最终提交
严重程度：重要；类别：正确性。位置：计划 40–42、53、61、69；Spec 33–36；`files/backend/rooted.ts:66–73`、`commit.ts:66–72,92–100`。
现象：`entryToken` 摘要含 dev、ino、birthtimeMs 和类型；正常文件系统上，同名新建甚至 inode 复用通常可区分。它不是内容版本，也不保证在身份字段不可靠的文件系统上唯一。如果详情或 409 拿 A 的目录快照再对同名位置 `identify` 得 B 的令牌，用户确认 A 会操作 B；若替换只做独立令牌比较、首次 rename 未传 `expected`，两者之间仍可换包。`replace` 二次请求发现目标消失时，也不能走无冲突的普通导入。其它按 id 排队的旧编辑同样可能落进同名新包。
为什么：令牌得对应用户确认的对象，不只是请求处理时同一路径上的对象。新版 Spec 已收窄为目录换代，不要求令牌识别原地内容变动；不采用短期令牌本身不是问题。
如何核实：从代码推断。在取详情/409 与取身份之间换包，再在确认与首次 rename 之间换包；覆盖目标消失及写请求排队时被替换。断言新包不动，替换按输出 36 给新冲突，或明确报告目标已消失。
建议改法：让扫描结果与实际目录身份一起发布，过期则重扫/重取预览；在首次移走旧包时把同一 token 传给文件服务 `expected`，不要只做前置判断。按意图保护需要抵御旧请求的编辑和上传；明确身份字段缺失时的退路。

### 4. 锁顺序可做到无环，但 `refresh` 不能等写锁或吞掉发布失败
严重程度：重要；类别：不变量。位置：计划 35、49、53–62；Spec 25、38；`stickers/backend/catalog.ts:127–151,267–320`。
现象：新版只列两种锁，没规定顺序和覆盖范围。若导出先拿包锁等全局锁、替换已拿全局锁等同包锁，会成环；若导出不用包锁，则连页面删图/改清单都能与它交错。改名涉及旧名和新名；仅锁旧名不能串行化目标位置的编辑。现有扫描不拿编辑锁，不存在已实现死锁；但若串行扫描新增任一编辑锁，写方持锁等 `refresh` 可形成反向依赖。现有 `#queue` 还会捕获失败，只记诊断，使等待者误以为发布完成。普通 debounce 与显式刷新若各排一遍会重复扫描；若无条件取消后来的监视事件，会漏掉扫描期间的外部变化。双改名的中间空窗也可能先被监视扫描发布。
为什么：锁和扫描串行是不同边界；提交成功不等于目录已发布，不能让监视器看见一半提交后还承诺选中状态稳定。
如何核实：静态推断。覆盖导出与替换、改名与目标编辑交错；扫描中注入外部变更、扫描失败、两个 rename 之间触发监视，核对最终发布及回包。
建议改法：全局归档名额→必要的包位置锁（多键固定顺序，同键只取一次）→文件服务单操作；无包锁路径反向等全局。扫描不取上述锁；对受影响位置延后或隔离中间态发布。显式刷新排入同一目录队列，只吸收入队前已覆盖的事件，扫描期间事件保留；将发布失败与写失败分开。

### 5. 隐式项、坏名项和无效项不能共用一种名字定位；“全部”不能依赖截断列表
严重程度：重要；类别：正确性。位置：计划 40–42、50–52、95；Spec 26–30；`stickers/shared/manifest.ts:83–115`。
现象：隐式有效项可在锁内按文件及当前推导出的 NFC 名匹配，但不能直接在原始清单找 `name`，首次物化也没写它。`1.png` 或因推导名冲突被忽略的图没有有效名字，`extras` 只有 `file`，必填 `name` 的改名 RPC 无法表达修复。显式项同一文件可有两个合法别名，按文件记选中会选错。无效原始项也可能引用同一文件，不能只按有效项计算末引用。每类最多 500、详情还可再截尾，但 `listFiles({files})` 无法表示全组；隐式包超过 500 张时只写文件可成功而新增项不可见，首次物化则总是超限。
为什么：选择器必须表达用户看到的对象；显示预算不是编辑范围或清单容量。
如何核实：静态推断。覆盖隐式有效图、坏名、同文件两个别名、无效项共享文件、已有 500 项及 extras 截尾。
建议改法：区分隐式文件、显式项、待修复项；显式项匹配时重算推导名并检查歧义，原始清单引用用于删图。全组由服务端重列并一次校验，有界失败而非只处理可见子集；定义隐式满包的增图和修复结果。

### 6. 归档的文件字节和、条目数与最终 ZIP 大小不是同一个限制
严重程度：重要；类别：正确性。位置：计划 54–62、67、118；Spec 32、35–36、验收 9。
现象：只存不压仍要写本地头、中央目录和文件名，文件总和贴着 64 MiB 时 ZIP 必超 64 MiB。导出也没套导入的单文件 32 MiB、600 项、目标名等价及路径规则；目录的 500 项不是磁盘图片数。有效的空包能导出但会因无图被拒。`parseManifest` 接受超 500、可选字段或部分项不合规并分别记录；只有扩展名不能证明存在合格图片。计划未规定整个 ZIP 的条目元数据（含过滤项）与完成校验，复制也没有总预算。对外部文件，`lstat` 预检不能替代读取实际字节。
为什么：可往返域须是两个入口的共同约束；单项字节和队列长度不约束归档条目处理或复制工作总量。
如何核实：静态推断。加精确边界、601 项、单项超限、空包、大小写等价名、伪图片和损坏/截断 ZIP，区分导入允许诊断部分项与必须不替换的情况；断言过滤项也计工作量，失败不发布。
建议改法：导出前按共同规则验证并核对最终 ZIP 大小，不能往返就明确拒绝或修订承诺；导入校验终结、实际字节、条目类型和全部条目数，先判定至少一张可接受图片的确切语义；复制限实际读入总量且不截断。用有界异步暂存或明确测量同步打包上界。

### 7. 条件重试不等于多步失败无副作用
严重程度：重要；类别：不变量。位置：计划 50–53、61、77；Spec 29–31、34、失败表 181；workspace.files 139–141，workspace.resources 118–127。
现象：新建目录后写清单可失败；删清单项后删文件可失败；写图后清单冲突，删图补偿也可失败或删掉外部刚放进来的同名新文件。删包本身也允许逐项或递归部分完成。仅把这些都映射为 `write-failed`／`pack-changed` 与“不写”冲突。无列表上传若遇外部首次写显式清单，文件级条件不会自动产生冲突；至少要明确成功可能只得到未列图。
为什么：文件服务锁和期望只管单次提交，不能回滚不属于该操作的内容。
如何核实：静态推断。逐步注入第二步失败、补偿冲突、权限导致部分删除，核对磁盘、刷新结果和响应。
建议改法：创建也可暂存发布；补偿限本次源身份且不能覆盖/删除别处的新数据。明确完整成功、未提交和部分完成并强制重扫；禁止把“通知失败”解释为“没有写入”。改失败表 181 及相应验收。

### 8. 三种排队须规定谁持有正文、谁能取消及何时放名额
严重程度：重要；类别：不变量。位置：计划 49、51、66–77、118；Spec 29、36、失败表 182–183；`files/backend/upload-route.ts:68–114`。
现象：HTTP 2 活动／8 等待、归档 1 活动／4 等待和包锁可以共存，但正文读完才排归档时，等候导入若继续占 HTTP 名额，两笔导入就可堵住所有上传；提前释放则已有正文和解压工作脱离上限。参考 `Gate` 没有取消和队列上限；参考读体拼接一度占两份，两个 64 MiB 正文读入可接近 256 MiB，未计解压和打包。5000 万像素单份 RGBA 约 191 MiB，两笔解码尚未计工作缓冲。信号触发不等于工作或内存已释放；慢读也可一直占满名额。计划 69 没列导入 `pack-changed`，导出没列全局 `busy`，上传未规定 `manifest-full`、只读来源、权限等状态和结构。
为什么：名额能否保宿主负载取决于预留、释放、实际字节和工作存续，而非数字本身；未定义的状态无法稳定验收。
如何核实：静态推断。经真实分发覆盖容量占满、慢读、等待中取消、解压与提交阶段取消、停机和导出写头前错误；核对取消后没有幽灵名额或超额执行。
建议改法：一处定义名额及次序，无 `await` 地占位；导入在缓冲前拿到归档容量或有界磁盘配额；加读超时，硬限制实际解压与像素预算，清理完成再放资源名额。逐 RPC 声明副作用和可达错误详情，逐路由补状态/结构和写头后传输中断的语义。

### 9. 末段 `lstat` 不能证明仍打开正确的表情包
严重程度：重要；类别：不变量。位置：计划 28、132；Spec 37；`stickers/backend/scheme.ts:33–39`。
现象：从目录按 id 现取仍是取扫描快照；末段 `lstat` 只检查最后一个目录项。用户容器若被换成链接，末段仍可能是普通目录；插件撤回后路径也可能仍存在。只测 `no-desktop` 且不建目录不能覆盖二者。
为什么：系统文件管理器打开的是路径当前解析的目标，而不是目录快照里的包；不要把共用 helper 当成来源授权。
如何核实：静态推断。覆盖包删除、包本身为链接、上级被替换、来源撤回及可打开的无效包，走真实 `revealPack` 合同；跨平台成功路径另验。
建议改法：在表情包调用方校验可信容器及当前包身份、贡献存续，复用不建目录的安全解析；helper 只负责桌面与打开器。协议不承诺防住系统调用前最后一瞬的外部换路径，且只在 Spec 37 允许的失败里公开路径。

### 10. 旧取图缓存风险不会随防抖窗口结束而消失
严重程度：重要；类别：正确性。位置：计划 71、147；Spec 175、189；`stickers/backend/routes.ts:34–49`、`catalog.ts:314–320`。
现象：待重扫时，现有路由检查了实际字节，却用旧目录版本返回 304 或 `immutable`。150 ms 是可重置的计时，还要等扫描排队；已用旧版本 URL 缓存的新字节也不会在重扫后自动失效。第二版把同样行为扩展到两类 extras，Spec 的授权范围却未更新。
为什么：可以将既有普通表情的修复另排，但新预览不能以防抖延迟为理由承诺缓存内容不变；包内链接不等同于包外读取，本次未认定包外读取。
如何核实：静态推断。目录保持原版本时换成另一张合规图，分别请求旧版本 URL 及带旧 ETag 的 GET/HEAD，核对旧版本不会得到错标的长期缓存或 304。
建议改法：本次至少对 extras 禁用基于目录版本的 `immutable` 和 304，或按实际读取的字节验证版本；明确两类 extras 预览的授权和 404，普通表情既有风险单独记录。

### 11. 清理暂存只处理报错，不检测成功的跨代复制
严重程度：重要；类别：正确性。位置：计划 54；Spec 32；`stickers/backend/plugin-roots.ts:21–42`、`scheme.ts:33–37`。
现象：插件贡献可撤回再登记，现有 `live` 代号防止撤回后异步登记，并不是复制租约；按同一挂载 id 逐文件解析时，前后可能命中不同登记。若都能读到，不会进入失败清理；即使先取真实路径，也需证明该目录内容在复制期间不变。
为什么：更新窗口窄是频率判断，不是源一致性保证。收窄复制范围已落实，不必锁住插件整个生命周期。
如何核实：静态推断。读完清单后撤回并重新登记同一 id，再读取同名图片，核对正式目录不会发布混合内容。
建议改法：固定一次源注册代次与根，提交前复核；若插件平台能提供不可变且保活的安装目录，可把该保证作为前置条件。否则代次不符就丢弃暂存并给可重试的错误。

### 12. 不保留任意精度数值可以取舍，但不能同时承诺未知值不变
严重程度：建议；类别：合同。位置：计划 50、145；Spec 28。
现象：计划一处排除超大整数，另一处仍说“值不变”；Spec 没有例外。常规 JS JSON 往返会改变不安全整数，超出 `Number` 范围的合法数字还可能写成 `null`。
为什么：收益小能支持不做任意精度编辑，不能证明重写未知值是无损的。
如何核实：按数字解析和序列化语义静态核对；实施后用未知字段里的大整数和超范围数字验收。
建议改法：保持未知值原始表示，或在会有损重写时拒绝保存；如选择允许变化，先把范围及失败行为写进 Spec 并确认，不再声称无损。
