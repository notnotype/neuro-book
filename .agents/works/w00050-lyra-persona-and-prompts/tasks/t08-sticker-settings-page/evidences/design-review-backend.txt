### 1. 启动清理会删除替换中唯一的旧包，也会删除用户自己的目录
严重程度：阻断；类别：不变量。位置：计划“catalog.ts”“editor.ts”“不做与风险”第 31、47、112 行；Spec 输出 1、36、“副作用与数据”；workspace/files.md:51、137–141。
现象：旧包改名成 `.nbook-replaced-*` 后，新包尚未提交时一旦进程退出，下次打开目录会把这份唯一备份和待提交的新包都删掉。新包提交遇到同名占位时，排他的回滚改名也会冲突；旧包仍是有效用户数据，不是可丢弃残留。另一方面，前缀匹配会把任何用户自建的 `.nbook-*` 目录视作可递归删除，即使从未在页面做过操作。`group` 不提供原子性；递归删除也可能部分完成。
为什么是问题：把可恢复的中断变成永久丢失，且违反启动时已有内容不动的合同。
如何核实：从设计及代码推断。实施后用真实文件服务在两次改名之间终止宿主，再启动；另覆盖回滚目标被占用、新包已提交而旧包清理部分失败、以及用户自建前缀目录。逐个断言原数据仍可找回。
建议改法：在受管理的同文件系统暂存区记录操作归属、目录身份和阶段；只清理确证未提交的暂存，未确认提交不删除备份。恢复冲突保留数据并诊断；已提交但清理失败与未提交分别报告。不要把通用前缀或目录名当删除授权。

### 2. 文件级条件写保护不了首次建列表和上传的跨文件不变量
严重程度：重要；类别：不变量。位置：计划“editor.ts”第 41–45 行与风险；Spec 输出 28–30、38、写入失败行；files/backend/workspace-files.ts:295–305、365；stickers/backend/catalog.ts:272–276、314–320。
现象：上传 A 读到没有列表；B 按仍未重扫的目录生成清单；即使 A 的图片已提交，B 的清单也可成功排他写入且漏掉 A，A 仍按原判断报告上传成功。有列表时，写图成功后更新清单失败、删图成功后删不掉清单项、新建目录后清单创建失败，也都不是失败表承诺的“不写”。两个上传选中同一个后缀时，`expect: "absent"` 只拒绝输家，不自动推进到下个后缀。清单 `{title: ...}` 没列表的分支没有建表办法；误走 `expect: "absent"` 永远冲突。
如何核实：从代码推断。真实目录与文件服务中交错首次物化、两次同名 PUT 与外部落图，并在图提交后制造清单冲突，断言响应、实际文件与最终目录；另测仅有 `title` 的清单。
建议改法：同包的页面写入串行化，锁内从磁盘重读列表模式与文件；缺清单时排他创建遇冲突重读，已有无列表时在同次 `update` 内保留字段并建表。只有目标实际被占用才有界尝试下一个后缀。定义外部并发落图的快照边界（边界后归为未加进来）；明确多步失败的补偿与部分完成回报，不能用 `group` 或 150 ms 重扫替代。

### 3. `file` 不是清单项主键，按缓存校验不能保护重名或修复坏名
严重程度：重要；类别：正确性。位置：计划“详情与远程合同”“editor.ts”第 36、43 行；决定 8、17；Spec 输出 4、27–28、30；stickers/shared/manifest.ts:86–98、105–115。
现象：解析器按表情名去重，不按 `file` 去重；同一张图可声明两个不同表情。只传 `file` 无法确定改哪项，删物理文件还会让另一项失效。两个并发更名若都在 `update` 外检查，会同时认为新名未占用；即使第二次因基线冲突重读，仍可写入重名。首次建表只序列化“当前目录认的表情”，会漏掉本次正要修复的 `1.png`。另外，输入已接近 256 KiB 或 500 项时，新增或格式化后会让包无效或让新项永不出现；普通 JS 解析再序列化也会改变未知字段中的不安全整数。
如何核实：从代码推断。用真清单覆盖同图不同名、两项改同一 NFC 名、无清单及有清单各修一次坏名、边界清单更新和未知大整数。
建议改法：为现有别名提供带基线的项选择器，或先修订公开格式并处理兼容；每次读取的编辑回调内重新验证目标、重名、项目数与最终 UTF-8 大小；物化保留该修复目标和文件语义，明确共享图片删除策略与未知值无损保留办法。

### 4. ZIP 形状过滤不能代替路径、条目类型和完整性校验
严重程度：重要；类别：安全。位置：计划“editor.ts”导入及切片 3；决定 19；Spec 输出 36；theme-editor/package-io.ts:69–74、90–135。
现象：计划只定义选取一层文件，没有定义如何拒绝不安全路径、重复目标和链接项。参考实现的 `safePath` 拦截绝对路径、`..`、反斜杠和盘符，但不拦隐藏段；参考实现最终 `Map.set` 会覆盖重复项，所示流式回调也不按外部属性识别链接项。仅把链接载荷当普通文件不会创建链接，但仍须决定拒绝还是忽略；不能在后续改用通用解包时继承创建链接的语义。
为什么是问题：归档里的名字不能充当写入地址；同一路径或同一文件系统等价路径命中两次，包内容不得由遍历顺序决定。非法清单或没有任何有效图片不能先替换旧包再由目录诊断兜底。
如何核实：从代码推断。为路径类别、隐藏项、同名/大小写等价项、链接属性、混合根级与包装目录、损坏或截断条目各写合同用例，断言失败时没有正式落盘。
建议改法：先校验原始路径段再挑选形状；只写服务生成的目标与通过校验的单段文件名，拒绝重名和歧义；选择能验证条目类型与归档完整性的读取方式，不恢复链接。统一包名转换：连字符折叠及去首尾、64 字符上限及后缀留位、空名失败、按最终名字判冲突。

### 5. 归档预算既挡不住进程峰值，也不保证自己的导出可导回
严重程度：重要；类别：正确性。位置：计划“技术选型”“editor.ts”第 15、47–48 行及切片 3；Spec 输出 35–36、验收 9；theme-editor/package-io.ts:104–132；files/backend/upload-route.ts:68–114。
现象：500 × 2 MiB 是 1000 MiB 原图，不是导出内存上限；`zipSync` 同时持有原图及 ZIP，压缩图片再压缩通常省不下多少；同步打包还阻塞宿主。合法的约 100 MiB 不易压缩图片包就可导出，却同时超过导入 64 MiB 入口；即使压到 64 MiB 内，超过 256 MiB 解压量仍导不回。反向也漏：500 项仅限有效目录条目，不限制磁盘图片数量；按前 500 张或每张 2 MiB 截掉都不再是“全部图片”。
如何核实：从代码推断。用不同内容的有效图片做超过 64 MiB 的包，验收导出后原样导入；并测试 501 张、超限原文件、并行导出、超限后取消。导入另测实际输出计数与伪小声明、跳过的文件和空目录洪泛；现有主题包整块 push 到同步解压器，回调看到超限不等于分配前已受限。
建议改法：先定可往返的包预算和超限合同，不静默截断；流式导出或异步有界暂存再下载。导入按实际输出计数，限制输入投喂粒度、全部条目元数据及进程级并发，拒绝超限后确保停止解压、清理暂存。保留 1 MiB RPC 上限，二进制传输仍走 HTTP。

### 6. 删除和替换未绑定用户确认时看到的包
严重程度：重要；类别：正确性。位置：计划“远程合同”“editor.ts”第 36、45–47 行；Spec 输出 33–36、38；workspace/files.md:137–145；files/backend/workspace-files.ts:308–325、337–339、360–363。
现象：用户看 A 的冲突预览并选替换，第二次请求只带 `onConflict=replace`；另一个窗口已删除 A、在同名位置建 B 时，服务器会把 B 当作被确认的旧包。`deletePack({id})` 和重扫未赶上时的编辑也把“同名位置”当“同一包”。旧清单的哈希不绑定父目录身份；没有鉴别目录代次，不能靠哈希补救。
如何核实：从代码推断。用真实文件服务替换同名目录且保留相同清单内容，再提交旧确认；断言 B 完全不动。再覆盖同一目录内容在确认后改变、确认重传的 ZIP 不是预览那份。
建议改法：冲突响应带短期令牌，绑定最终文件夹、旧目录身份/预览版本与归档摘要；提交重验，变化则返回新冲突。改名和删除传递 `identify` 的 `expected`，消费批量删除逐项结果；编辑也需要绑定打开时包代次。另存与复制的后缀分配以排他改名为准，遇目标占位有界递进，不覆盖。

### 7. 上传上限只限单请求，未约束宿主承载量或图片解码
严重程度：重要；类别：安全。位置：计划“技术选型”“routes.ts”第 52–55 行与切片 3；files/backend/upload-route.ts:62–114、157–172；nb-host/http/dispatch.ts:79–97。
现象：页面至多并发 3 个不是服务端约束。照现有汇总器，拼接时每个 32 MiB PUT 短时持有约 64 MiB，每个 64 MiB POST 约 128 MiB，还没计解压或像素。编码字节限制不能约束静态图解码的原始像素；例如 16384×16384 的 RGBA 解码面就是 1 GiB。计划没有随取消/停机释放读流和暂存的合同。另一个实际差异：项目写路由只接受 `same-origin` 或缺头，照取图则会放行 `none`；宿主有独立 Origin 检查，可能先返回 `origin-not-allowed`，不能把所有拒绝承诺成 `cross-site`。
如何核实：从代码推断。通过真实 HTTP 分发测试并发占位、无长度/超限 413、取消与停机、超大像素但编码很小的图片，以及两层来源拒绝码。
建议改法：按写/读分开来源规则；在读体前占用服务端有限额度，排队也有上限并可取消，实际读取按字节计数；为解码单设像素预算，明确静态图无法安全缩小时的拒绝语义。统一 413 的 JSON 码、上传业务拒绝的 HTTP 状态与信号传递。

### 8. 取图复核的是字节，不是扫描时批准的文件或版本
严重程度：重要；类别：安全。位置：计划“routes.ts”第 57 行；Spec 取图失败行与“边界与兼容”；stickers/backend/routes.ts:32–49、scheme.ts:33–39；workspace/resources.md:132–135。
现象：扫描时的 `lstat` 不保证读取时仍是同一文件。文件服务允许解析挂载包内的链接，表情包挂载对读路径没有额外授权规则；因此扫描批准后文件变成指向包内另一张图的链接，字节检查仍可通过。直接换成另一张合格图片也会在重扫前发新字节，但 ETag 与 `immutable` 仍来自旧目录项；反过来旧 ETag 也可得到错误的 304。这是既有缺口，扩至 extras 会沿用它。内容类检查通常会拒绝 JSON、非图片和越界链接，但不是“不跟包内链接”的证明。
如何核实：从代码推断。拿到版本后、在目录处理监视事件前用实际文件替换，分别断言内部链接 404、新旧字节的 ETag 不相同、旧版本无 immutable；同时覆盖 extras 的 404 与 HEAD。
建议改法：只对显式分类且通过文件名及图片核对的条目授权；读取时在可信根内拒绝链接，实际读出的内容或打开的文件身份决定版本；只有实际版本与查询一致才允许长期缓存，条件请求亦按实际版本判断。同步修订 Spec 对“只给有效表情”的明确限制。

### 9. 打开表情包不能复用 Skill 的“先建目录”语义
严重程度：重要；类别：不变量。位置：计划“shared/open-folder.ts”及切片 1；Spec 输出 37、“副作用与数据”；agent/backend/skills/folder.ts:12–22；stickers/backend/scheme.ts:33–39。
现象：旧 helper 在桌面检查和 `try` 外先递归 `mkdir`，删除或插件撤回后会尝试重建目录；无桌面照样做，创建失败也不会成为声明过的 `open-failed`。目录快照里的字符串不足以判现在仍是用户或插件的真实目录，不能直接给系统打开器。旧 helper 的失败值也不带路径，计划没有定义 `revealPack` 的通知数据。
如何核实：从代码推断。走真实远程方法，覆盖无桌面、正常插件快照、撤回/删除后的陈旧条目以及被换成链接；断言不创建任何目录，预期失败通道带合约允许展示的路径信息。成功打开需要额外的真实桌面验证。
建议改法：只共享服务端“打开已存在目录”的实现，建 Skill 目录留给 Skill 调用方及其失败处理。按精确 id 从目录解析来源，用不建目录的挂载或等效安全解析确认目录、包含关系与存续；拒绝链接，不从用户输入导出宿主路径。明确输出 37 的路径例外，不把其它 IO 错误里的宿主路径一并透传。

### 10. 包详情的 300 KiB 没有可证明的上界
严重程度：重要；类别：正确性。位置：计划第 29–36 行、切片 1；Spec 输出 18、25–27；stickers/backend/browser-catalog.ts:14–31、44–48；nb-host/shared/socket.ts:15–16。
现象：500 是有效表情上限，文件夹扫描没有天然的 500 个 extras 上限。即使截为 500，转义、UTF-8 和 URL 百分号编码也使按字符数估计的 300 KiB 不成立。若裁切，用户又看不到其余图片，也无法判断“全部加进来”的范围。输出 25 还要求列表知道坏名提示，不能只补详情，也不宜把整份 extras 塞进既有摘要。
如何核实：从代码推断。经真实远程链路读取长文件名、许多 extras 的包，同时断言窗口保持连接、列表坏名标记正确，以及翻页或超限状态可见。
建议改法：管理详情独立按 JSON 的实际 UTF-8 字节预算分页，保留跨页总数和稳定版本；文件数组输入也限制条数与字节。管理列表只给必要的标记与数量，明确与 Profile 摘要分离。扫描同样有独立预算，超限可见，而不是静默丢项。

### 11. “整个包”复制被实现计划收窄，源读路径也不绑定快照
严重程度：重要；类别：正确性。位置：计划第 46 行、切片 2；Spec 输出 13、32；workspace/resources.md 的挂载方案；stickers/backend/scheme.ts:14–39。
现象：只复制清单与至多 500 张图会遗漏插件目录内其它文件和子目录，与输出 32 的“整个复制”不同；对清单任意略过其引用图片，还会生成少项的新包。`realPath` 或一次地址解析只交付路径，不会在后续多次读取期间固定插件目录；撤回或更换版本后可能复制半旧半新的内容。
如何核实：从设计及代码推断。以清单、未列图片、子目录和附加文件组成插件包；在逐文件读中间更换插件来源或撤回，断言结果要么是完整一致的副本，要么没有正式用户包。
建议改法：明确复制是整个目录还是可移植表情内容；若收窄先改规范，若完整则给出递归的链接、文件数和字节政策，超限明确失败、不静默截断。读走能力范围内的文件服务，固定或重验源代次，撤回不继续发布混合副本；写仍经排他暂存提交。

### 12. 写入返回与目录发布之间缺一个可等待的边界
严重程度：重要；类别：不变量。位置：计划第 62、82–85、113 行；Spec 输出 31–32、36、38、验收 9–10；stickers/backend/catalog.ts:127–150、267–280、314–320。
现象：文件服务提交后，监视事件还要经过 150 ms 防抖才入重扫队列。`settled()` 此时只等已入队的扫描；写完立刻用新 id 取详情或上传能读不到，新 id 的选中也可能被页面回退到第一项。只改 extras 或 `listed` 时，若沿用旧目录内容相等判据，`changed` 还可能不发。
如何核实：从代码推断。用真实文件服务、两窗口和手动时钟，等待写入返回即选中或读详情，再覆盖只增删 extras、同包并发写、迟到的旧请求及重扫失败。不用固定等待。验收 9 断言导回文件名、尺寸、Markdown 取图和下一次槽内容；静态转 WebP 路径另测，不让替代格式掩盖验收样本的 JPG 断言。验收 10 断言原包内容不变，替换与恢复另测。
建议改法：文件服务提交后显式失效并等待对应扫描代次，或返回可关联的代次让页面等到再选中；同包请求合并，外部变更保留 watcher。把管理字段纳入适当的变更判据，扫描失败不可伪装成提交失败或新目录已可读。

### 13. 失败码清单不是调用方可依赖的合同
严重程度：重要；类别：正确性。位置：计划第 36、54–56、70–72、97–98 行；Spec “失败与恢复”；nb-runtime/remote/node.ts:699–705、867–872。
现象：计划说文件服务码原样交还，但未指定各方法声明的错误集及详情结构；未声明码或无效详情会变成 `provider-error`，页面无法按冲突或权限错误分支。上传有 `{rejected: reason}`，失败表却有 `image-rejected`；导入 409 未描述成功响应或完整失败结构，导出也缺无法读取和超过预算时的合同。若直接传底层 `detail`，还可能把非输出 37 所需的宿主路径带给窗口。
如何核实：从代码推断。通过真实 RPC 调用触发基线冲突、缺包、只读来源与权限失败，断言实际到达浏览器的码和详情；经 HTTP 检查 409、413 与业务拒绝的状态、内容类型及 JSON；导出在写出响应头前就能报告的失败应与传输中断区分。
建议改法：逐方法声明 `effect`、`errors` 及详情；文件服务失败映射到稳定业务码和受控详情。逐路由写下成功/错误的状态与响应结构；`image-rejected` 细分成稳定原因码，区分宿主先行拒绝；明确导出中断处理与附件文件名编码。切片验收经真实 provider 和 dispatcher，不只测 editor 或插件局部路由。
