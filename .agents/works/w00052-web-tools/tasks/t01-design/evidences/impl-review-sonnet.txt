### 1. “没检成”在结果未知时写成“可能没有保存”，与检测无关
严重程度：重要　类别：正确性、文字
位置：web/text.ts failureReason（行 28-29）、locales/zh-CN.json `failure.unknown-outcome`（en-US 同键）、web/components/SearchSettingsPage.vue checkLine（行 38-40）
现象：`failure.unknown-outcome` 的文案是“可能没有保存，以页面上显示的为准”，写入失败通知（输出 6）用它是对的。但 `check` 的远程调用链路中断时同样得 `unknown-outcome`，页面按 `failureReason` 写成“没检成：可能没有保存，以页面上显示的为准”。Lab 场景 `not-run` 的截图（shots/20261119T115547Z/SearchSettingsPage__not-run__free__light.png）就是这句，英文是 “Couldn't check: May not have been saved; the page shows the actual state”。
为什么是问题：检测不保存任何东西，也没有“页面上显示的”可对照；用户读到会以为密钥没存上，去重填。Spec 输出 8 要求“没检成（远程调用本身失败或结果未知）”，只是要显示“没检成”，不是借写入的原因。DOM 测试 `notRun` 只断言 `startsWith("没检成")`，所以这句错话没被发现。
如何核实：Lab 的 `not-run` 场景或 DOM 测试里 `check: "unknown"` 后读 `[data-search-check-result]` 的全文；上面的截图已有。
建议改法：检测的原因与写入的原因分开取：`failureReason` 带一个上下文（`"write" | "check"`），或给 `unknown-outcome` 加 `failure.checkUnknown`（“连接断了，不知道检测有没有发出去；可能已经按了一次计费”，计费这一点对 `effect: write` 的 `check` 是实情）。DOM 测试改成断言全文。

### 2. 已发出的检测在密钥改写之后才回来，旧密钥的结果被当成新密钥的结果显示
严重程度：重要　类别：不变量（先后、并发）
位置：web/search-store.ts write() 行 90-92（`if (checks.get(provider)?.status !== "running") checks.delete(provider)`）与 check() 行 119-125
现象：写入成功时，只要这家的检测是 `running` 就不清。作者的意图是保住“排在这次写入后面、还在排队的检测”（注释：排在它后面的检测已经标成进行中），但“在这次写入之前就已发出、正在服务端用旧密钥跑的检测”同样是 `running`，同样被保住；它回来后写成 `done`，页面显示“检测通过（时间）”，而这时密钥已经是新的。
为什么是问题：Spec 输出 8“写入或清除成功后，这一家的检测结果清掉”，计划与数据模块注释的目的就是“密钥变了旧结果不失效”（设计审查 Sonnet 第 2 条）。页面上检测进行中输入框并不停用，用户点了检测再改密钥是很自然的操作；结果是对新密钥的错误“通过”或“不认密钥”。
如何核实（已做，仓库外的脚本，直接 import search-store.ts，远程替身的 check 挂住、由脚本放行）：check("deepseek") 发出（替身记到 “check sent with OLD”）→ setKey("deepseek","NEW") 成功 → 此时 `checks.get` 为 `{"status":"running"}` → 放行旧检测 → `checks.get` 变成 `{"status":"done","result":{"ok":true},"at":1}`，没有任何标记说明它是旧密钥的结果。现有测试没有这个次序（`search-store.test.ts` 的“填完直接检测”只有写在前、检测排队的情形）。
建议改法：给每家的检测记一个代次（或在 check() 里区分“排队中”与“已发出”）：写入成功时让已发出的检测作废（丢弃它回来的结果并把状态删掉，页面回到空闲），排队中的不动。补一条数据模块测试：检测已发出、写入成功、放行旧检测，断言最终没有 done。

### 3. 检测排队等写入时入口被停用，写入结束后仍会发出（计费的）检测
严重程度：建议　类别：不变量（释放）
位置：web/search-store.ts check() 行 119-124、dispose() 行 131-136
现象：check() 先 `await pendingWrites.get(provider)`，之后才建 AbortController、登记进 `controllers` 并发请求；`disposed` 只在请求结束后查。如果写入在途时调用 dispose()（abort 遍历的是当时还空的集合），写入一结束，检测照样发出，没有人能取消它。
为什么是问题：数据模块注释与 Spec 都说入口停用时释放它；`check` 是 `effect: write`、会发一次按次计费的搜索。窗口卸载与停用入口通常很快，但这是一条漏掉的收口路径：停用之后还有网络请求在外面。
如何核实（已做）：脚本里让 setKey 挂住，随后 `store.check()`、`store.dispose()`，再放行 setKey；日志为 `["setKey done NEW", "check sent with OLD"]`，即 dispose 之后检测仍然发出。
建议改法：await 之后 `if (disposed) { checks.delete(provider); return; }`，其余不变。补测试（现有 6 条里没有任何一条碰 dispose，见第 6 条的变异结果）。

### 4. 写失败的提示把中文全角分号写死在组件里，英文界面成了“……；Please enter it again”
严重程度：重要　类别：文字、i18n
位置：web/components/SearchSettingsPage.vue 行 59（`const reason = \`${failureReason(text, outcome.failure)}；${text("failure.retry")}\``）
现象：连接词 `；` 是源码里的字面量，不在两份目录里。英文界面的窗口通知会是 “The key file couldn't be read or written；Please enter it again”（全角分号，句子之间也没有空格）。`unknown-outcome` 时是 “May not have been saved; the page shows the actual state；Please enter it again”，一句话里半角全角各一个。
为什么是问题：项目的 i18n 约定是句子整体进目录（同文件里其它句子都走 `text(...)`）；这是唯一一处在代码里拼标点的地方，英文界面直接可见。DOM 测试只在 zh-CN 下断言 “密钥文件读写失败；请重新输入”，所以没发现。
如何核实：看行 59；Lab 的 `write-failed` 场景只有中文，没有英文版；用英文端口挂载后 `reportWriteFailure` 的 reason 即上面这句。
建议改法：目录里加一条带占位的键，如 `failure.withRetry`: “{{reason}}；请重新输入” / “{{reason}}. Please enter it again.”，组件只调一次 `text`。同时给 Lab 加一个 `write-failed-english` 场景或在 DOM 测试里加英文断言。

### 7. 取状态因“目标已没了”等原因失败时，页面永远停在“读取中”，没有任何文字
严重程度：建议　类别：边界、正确性
位置：web/search-store.ts failed()/refresh() 行 62-80；web/components/SearchSettingsPage.vue keyState/keysUnreadable
现象：`failed()` 只把 `unavailable` 当“不可用”。读请求在服务端已回 ACK 后连接断了，运行时给的是 `target-gone`（nb-runtime/src/remote/protocol.ts failureFor）；`timeout`、`cancelled` 同理。这几种码到了 refresh()：`statusFailure` 被设置，`available` 仍为真，`status` 为 null，于是 keyState 是“读取中”、控件停用，顶上没有只读提示（只有 `unavailable` 与 `credentials-unavailable` 两种失败有文字）。`statusFailure` 对其它码根本不显示。
为什么是问题：Spec 输出 2 允许“一直没拿到”时显示读取中，但输出 7 要求“远程合同不可用（服务端入口已停止）时在页面上写原因”；入口在请求进行中停止正是 `target-gone`，用户看到的是一个永远转不出来的“读取中”，也不知道要离开页面再回来。检测与写入的同类失败都有文字（“没检成”“窗口通知”），只有取状态没有。
如何核实：fake-remote 的 `status` 返回 `{ok:false, code:"target-gone"}`，挂载页面：`[data-search-readonly]` 与 `[data-search-keys-unreadable]` 都不存在，框是“读取中”。
建议改法：把 `target-gone` 并入“合同不可用”（`failed()` 里与 `unavailable` 同处理），或让 `statusFailure` 非 `credentials-unavailable` 时在顶上写 `failureReason`；这是窄的边角，选前者最简单。

### 9. 无障碍：检测进行中与“已设置”两个状态读屏用户听不到

位置：web/components/SearchSettingsPage.vue 行 99-115（检测按钮与结果）、ApiKeyField.vue placeholder
现象：(a) 检测按钮 `aria-label` 固定为“检测 DeepSeek 的密钥”，进行中文字变成“检测中”但可访问名称不变；同时 `role="status"` 的结果段在 `running` 时是空串（checkLine 对 running 返回 ""）。读屏用户点了检测以后没有任何播报，直到结果出来。(b) “已设置”只存在于输入框的 placeholder；有 `<label>` 时 placeholder 通常不被读出，“清除”按钮的名字也没说是哪一把密钥（输出 10 要求按钮名称带服务名，检测按钮带了，清除没有）。

### 10. e2e 只走了“已有密钥后再换一把”，没有走“第一次填密钥直接点检测”
严重程度：建议　类别：测试、验收覆盖
位置：e2e/web-settings.e2e.ts 行 98-103；SearchSettingsPage.vue 行 100（`:disabled="disabled || keyState !== 'set' || checking"`）
现象：验收 2“填完密钥直接点检测：检测用到刚填的密钥”，e2e 里这一步发生在 FIRST 已设置之后，按钮本来就是可点的。第一次填密钥时按钮是停用的（没有密钥时“检测”停用，输出 8）：用户在框里填完、直接点停用的按钮，那一下点击只会让输入框失焦、触发写入，按钮在写入返回后才变可点，点击事件本身落在停用的按钮上。这条路径在不同浏览器里行为不同（鼠标按下与抬起之间按钮从停用变可用，Chrome 是否还发 click 我没有验证，未运行浏览器）。
为什么是问题：设计审查第 1 条描述的正是首次填写的场景；e2e 把“换密钥”当作“填完直接点检测”，没有覆盖首次。数据模块的排队保证了“按钮可点时”正确，但没有人验证用户第一次点能不能点到。
建议改法：e2e 里先在空状态下 `key.fill(FIRST)`、不按回车，直接 `check.click()`，断言最终收到的 Authorization 是 FIRST（并且若点击被吞掉，要有明确的预期：再点一次、或页面有提示）。这一条可能暴露“首次要点两次”，到时再决定要不要让按钮在草稿非空时可点（那样点击会先写入再检测，同输出 8 的排队）。
