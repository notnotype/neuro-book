### 1. 网页文本的边界可被正文打断，存档与 eval 又绕过边界
- **严重程度：重要；类别：安全与性能。位置：**计划第 47–49、63、71 行。
- **现象：**把网页字符串直接拼进 `<web-content source="网址">…</web-content>` 时，正文里的结束标记与宿主标记不可区分；网址插入属性也没有转义规则。即使文字预览转义正确，`returns.markdown`、`returns.results` 和 `services.artifacts` 写出的 Markdown 仍会被 eval、`read` 当作原文消费，计划没有为这些通道定义来源与信任边界。
- **为什么是问题：**同一页仅因顶层、嵌套或分页路径不同，就从“外部资料”变成无标记文字。允许 `read` 是已确认取舍；标记能维持来源结构，不是阻止模型联网外发的权限边界。
- **如何核实：**静态对照计划、`agent/eval.md` 输出 7、`agent/builtin-tools.md` 输出 30：后两者分别取结构值和文件原文，不继承网页工具的预览包装。
- **建议改法：**所有不可信字段按各自载体序列化；转义正文与属性，宿主提示不参与正文解析。结构值保留明确定义的来源字段，不把提示混进正文；给存档及后续读取明确的不可信来源规则。用带结束标记、引号和相同提示行的无害夹具，分别验收顶层、eval 和存档分页；不要把标记描述为安全隔离。

### 2. 内置插件不能在插件管理中停用
- **严重程度：阻断；类别：正确性。位置：**计划第 3–7、28 行。
- **现象：**计划承诺“做成内置插件……可在插件管理里停用”，实施切片只加产品清单和插件代码，不改管理合同。
- **为什么是问题：**`runtime/plugin-hot-plug.md` 第 44–45、102–104 行明确拒绝停用内置插件；清空密钥也不会撤掉工具声明。用户不能用计划承诺的方式停用这两个默认可见、可能收费的工具。
- **如何核实：**对照上述 Spec 与 `runtime/plugin-install.md` 输出 4；这是用户操作当前合同，不是 `onAgentTool` 或浏览器入口可以绕过的限制。
- **建议改法：**由开发者确认具体的停止方式：保留内置身份，明确用 Profile 工具绑定或用户层全局拒绝规则停用调用，撤回对插件管理的承诺；若必须从管理页停用，另定“可停用内置插件”的启动、持久化、跨窗口与撤回合同。把第 3 行“没表态”改成已确认，并注明这个实施冲突。

### 3. 凭据库打开失败会挡住整个应用启动，工具入口也不会懒激活
- **严重程度：阻断；类别：不变量。位置：**计划第 20、28、45–46、52、67 行；`packages/neuro-book/src/server/start.ts:240–243`。
- **现象：**产品服务端把所有非第三方插件列为 `requiredPlugins`，运行时启动它们在本位置的全部入口；声明 `onAgentTool` 并不能使内置入口变成惰性。如果照 `nbook.models` 在入口激活时 `await openCredentials`，新库损坏、不可读或目录不可写时，失败的是整个宿主的启动门禁，不只是网页设置和两个工具。若入口是可选但仍让打开失败抛出，声明仍在，调用分别只能得到 `tool-unavailable` 和远程 `unavailable`，而不是 `no-key`。
- **为什么是问题：**一个可选网页能力的私有数据库故障会令不使用它的会话和工作台也不能启动；当前切片的本机端点与 SQLite 重开测试不经过产品启动门禁。
- **如何核实：**对照 `runtime/application.md` 的启动规则（第 42 行）、`models/backend/plugin.ts:36–41` 和 `nb-harness/src/models/credentials.ts:31–40`。这是生产装配的静态调用链，未破坏真实数据库。
- **建议改法：**先明确选择：保留现有启动策略、让 `nbook.web` 入口发布可诊断且可恢复的 `credentials-unavailable` 状态而不抛出；或改产品宿主，把启动必需与内置身份拆开（也可解决可选内置插件的启动耦合）。两者都要验收损坏库、未配密钥、恢复三种情形，并断言核心应用仍可用。

### 4. 顶层 `returns` 会把全文另存进会话，绕开预览与存档限额
- **严重程度：重要；类别：不变量。位置：**计划第 47–48、63、71 行。
- **现象：**按字面让每次 `web_fetch` 都带 `{markdown: 全文}`，顶层调用的 `ToolResult.details` 会随结果持久化。长页因此在 `home/artifacts/` 和会话 `blobs/` 各留一份，重开会话还会读回 blob；超过 256 KiB 的事件不再以内联预览交付。搜索的完整标题、摘要等也会从 `details` 绕过 600 字窗口。反过来，嵌套日志的 2 KB 限额只限制 `text` 预览，不限制 `details`：eval 照常校验并经 IPC 收到整份结构值。
- **为什么是问题：**截结果文字并不限制持久化、重开或 eval 传输成本；同一返回对象可能大到压过工具预算。
- **如何核实：**`nb-harness/src/kernel/run/tools.ts:525–533,558–564`，`harness/session.md` 输出 9 与 16,384 字节规则，`agent/sessions.md` 输出 7；对照内置 `read.ts:255–269` 仅在 `ctx.within` 时给 `details` 与 `backend/eval/tool.ts:399–407`。
- **建议改法：**仿照 `read` 只给嵌套调用提供结构值；明确响应、单页、存档与 IPC 可用字节上限。超预算时结构值也给真实的截断标记和地址（或报明确定义的过大错误），不要无条件返回全文。验证顶层重开不重复载入全文、嵌套拿到约定内容。

### 5. 设置写入的确认、工具取密钥和停机次序没有合同
- **严重程度：重要；类别：不变量。位置：**计划第 45–46、52、63、71 行。
- **现象：**“串行写、入口停止时关库”只定义了两件事，没定义接纳与排空。远程方法停止时只收到中止信号，仍可能有已 ACK 的写在队列里；工具工厂每个会话只建一次，若在工厂捕获密钥，首个 `no-key` 会在设置成功后持续，或清除后还用旧密钥。若在用完网络后再读库，则入口撤回最多等 5 秒，45 秒读取在这之后仍可能访问已关闭的库。
- **为什么是问题：**现有基础设施不提供“关库前自动等完领域操作”或“设置保存后重建工具”的保证，不能靠重新开会话来更新密钥。
- **如何核实：**`agent/backend/tools.ts:223–257,261–320`，`nb-runtime/src/remote/node.ts:819–855`，`nb-harness/src/models/credentials.ts:14–24,41–53`；现有 Models 在 `backend/plugin.ts:36–41` 让核心先停，`nb-models/src/core/core.ts:545–549` 等写队列后才关库。
- **建议改法：**一个服务端入口代次拥有一个句柄。写 RPC 成功之前必须更新同一快照；`status`、`check` 和已有会话工具按约定时点取值，规定已发请求使用旧钥还是被取消。停止先封新工作、取消 `check`/网络与重试等待，收口已接纳的写后关库；任何在途工具在首次等待前只取一次密钥，不跨生命周期重读库。用同一会话先 `no-key`、写成功后立即调用、清除后再调以及写入与入口停止交叠验收。

### 6. `read` 的行分页无法读回存档中长行的尾部
- **严重程度：重要；类别：正确性。位置：**计划第 48、63、71 行。
- **现象：**例如正文只有一行、长 20,001 字：预览给前 20,000 字，原样写入全文存档后，`read` 只给该行前 2,000 字，下一页从下一行开始。eval 调 `read` 也一样，只有 `clipped` 告诉它哪一行没读完，并不提供行内偏移。因此最后一个字不能按计划给模型的方式取回。
- **如何核实：**`nb-harness/src/kit/tools/read.ts:20–21,97–130,199–206`；`read.test.ts:155–158` 已把代码调用时的这一行为锁为合同。`agent/resources.md` 输出 11 保证全局地址可读，不保证一个任意长的行可分页读完。
- **建议改法：**二选一：保存或另提供可无损分段的文本视图，明确分段边界不改变原始 Markdown；或者保持文件原样，只承诺 `read` 可预览，给准确取回长行的接口和用法。保存失败时返回明确状态，不给虚假的全文地址；在真实会话里测试单行长页、正常分页和存档提交失败。

### 7. 复用的凭据库会在清除未落盘时报告成功，重启后旧密钥又生效
- **严重程度：重要；类别：正确性。位置：**计划第 20、45、52、63 行；`nb-harness/src/models/credentials.ts:50–51`。
- **现象：**`clear` 走 OMP 18.14.0 的 `pool.remove`。SQLite 的 `deleteAuthCredentials` 吞掉 UPDATE 失败，然后 `remove` 仍清空内存快照并 resolve。锁竞争下，设置页能收到清除成功，当前进程也说没密钥，重启却恢复旧值。这个操作本身是软删除，不会擦除数据库里的原文。
- **如何核实：**在主工作区 `f3546dc75`，用真实 `nbook.models` 服务端入口、窗口 JSON 链路和独立的临时 SQLite，第二个连接持有 `BEGIN IMMEDIATE`，让窗口走真实 `clearKey`；释放锁后重开服务。`bash /tmp/review-w00052-t01-design/omp-scratch/run-local-probe.sh` 退出 0，输出 `{"whileLocked":"none","liveSnapshot":"none"}`、`{"afterReopen":"stored"}`。未直接调用 OMP 内部删除方法。对应 `pi-ai/src/auth/pool.ts:631–635`、`sqlite-credential-store.ts:500–502,1594–1599`；被审提交到实测提交之间，相关 model/凭据桥接与锁文件无差异。
- **建议改法：**先修上游持久化删除的错误合同（失败必须可观察，成功后再更新快照），或改用能确认提交的 API；不要把同一快照的 `hasKey: false` 当作写盘证明。不再把“已测的读写”当作本方案已满足清除保证。验收加失败后重开，并注明清除是停止使用，不等于安全擦除。

### 8. 只登记产品清单不会把新插件装进两个宿主
- **严重程度：重要；类别：正确性。位置：**计划第 28、46、53、63–67 行。
- **现象：**计划只明确把描述加入 `src/manifest.ts`。真实服务端、浏览器分别从 `src/server/plugins.ts` 的 `serverPluginDefinitions`、`src/web/plugins.ts` 的 `browserPluginDefinitions` 取入口定义。描述有运行位置但表里没有定义时，`definitionAt` 直接抛错。只向测试内核注入插件定义即使全绿，也证明不了第 2 片以后能从产品进程调 `nbook.web/settings`。
- **如何核实：**`plugin-platform/shared/definitions.ts:18–34`、`server/plugins.ts:56–83`、`web/plugins.ts:67–87,105–121`；`plugins/plugins/shared/builtin-names.test.ts:42–62` 另外核对内置插件的名称目录与产品清单一致。
- **建议改法：**第 2 片同时登记服务端入口并验收产品装配；第 3 片声明浏览器位置时同步登记浏览器入口及目录，不能先声明还没有定义的位置。登记内置插件名称与描述。共享描述只含声明，不从 `manifest.ts` 引入凭据库或服务端代码，保留 ADR 0036 的 OMP 装载顺序。

### 9. 设置 RPC 没有区分确定失败、写入结果未知与可能已计费的检测
- **严重程度：重要；类别：正确性。位置：**计划第 44、50、52、63–64、71 行。
- **现象：**计划写了方法名和检测结果，却没写 `provider`、`callers`、方法 `effect` 和分方法错误表。`setKey`、`clearKey` 在写帧已发出后断线，可能已提交，也可能没提交；错标为 `read` 会失去 `unknown-outcome`。`check` 一般会产生一次计费请求，若直接套搜索的重试，发送两次且断线可能重复检测，与“发一次”不符。
- **如何核实：**`runtime/plugin-channel.md` 输出 1、3、4（按发出及 ACK 划分）、`nb-runtime/src/remote/protocol.ts:63–81`；对照 `nb-models/src/contract/settings-spec.ts:64–91` 的 `provider: "server"`、`callers: ["browser"]`、读写和错误表分离。`nb-runtime/src/remote/node.ts:849–879` 会把未声明的失败码或详情变成 `provider-error`。
- **建议改法：**定版本 1、server 提供/browser 调用；`status` 读、`setKey`/`clearKey` 写，限定第一版只有 DeepSeek，分清无密钥、坏输入、库不可用；写成功只回状态，结果未知时重读服务端状态而不重放。`check` 明确单次 HTTP 请求、独立截止与取消，断线只能说“检测结果未知”，不推断未发送或未计费；按此确定检测的 RPC `effect`，即使沿用模型的 `read` 也不能自动重发。用真实远程链路断线及本机端点计数验收。

### 10. 两次网络尝试与 eval 单元需要共用各自不重置的预算
- **严重程度：重要；类别：不变量。位置：**计划第 44、50、63、65、81 行。
- **现象：**20/45 秒未定义为单次尝试还是整个工具。按单次算、到近截止时收到可重试错误，可以等 1 秒再起请求，搜索总计接近 41 秒、读取接近 91 秒。eval 的 30 秒计入工具等待，即使只抓一个慢页也会在工具的 45 秒前超时、内核变量丢失；顺序抓三个的工具预算是 135 秒，还没算代码、排队和收尾。`ToolWrapper` 的结算不等于底层 I/O 被取消，`services.artifacts.save` 也不自动接收工具信号。
- **如何核实：**`agent/eval.md` 输出 11、14，`harness/runtime.md` 输出 98、100；`agent/backend/eval/tool.ts:288–317` 把父单元信号传入 `ctx.invoke` 并杀内核，`agent/resources.md` 输出 11 说明存档的取消边界。内置工具未写 `concurrency` 时按 `exclusive`，不能假定 `Promise.all` 缩短总时限（`agent/backend/tools.ts:188`）。
- **建议改法：**从工具开始就设置一个 20/45 秒总截止，与调用和入口停止信号合并，覆盖请求头、响应体、退避、第二次尝试；取消后不启动重试、不开始新存档，并说明已提交的产物如何处理。说明用 `eval({timeout: …})` 设置大于串行最坏预算的单元时限，不改 eval 缺省值；用真实 eval 与本机慢端点验证默认超时重置、放大时限成功及中止后无重发。

### 11. 只遮盖截断的 HTTP 错误正文，不能保证密钥不进入工具结果和诊断
- **严重程度：重要；类别：安全与性能。位置：**计划第 44、47–52、63、71 行。
- **现象：**遮盖只写在 HTTP 错误分支；成功响应里回显认证值、响应解析错误与网络异常，没有同一出口。若先截后遮盖，截断点落在密钥中间时，完整密钥比对会漏掉已经交出的前缀。工具抛出的 `Error.message` 会变成 `tool-threw` 并进会话日志，设置 RPC 虽对调用方返回固定 `provider-error`，却把异常消息写进诊断。
- **如何核实：**`nb-harness/src/kernel/run/tools.ts:499–501,525–533`、`nb-runtime/src/remote/node.ts:843–852`；模型适配器的 `nb-harness/src/kernel/model/redact.ts:20–30` 在交出结果前先遮盖，再截断。只断言正常响应或模拟 401 不含完整密钥，会漏掉上述路径。
- **建议改法：**把所有上游失败转成固定短码及安全字段，诊断只记状态、阶段和有约束的请求 id，不转抄异常、请求头或上游错误原文。确需交出原文时先解析与遮盖再限长；成功响应也只取声明字段并防回显。用假密钥分别验收跨截断边界、成功回显、网络及解析失败，检查工具预览、eval、诊断和持久日志，而不是只查浏览器结果。

### 12. 上游响应没有读取上限，截预览发生得太晚
- **严重程度：重要；类别：安全与性能。位置：**计划第 44、47–48、63 行。
- **现象：**600 字摘要、2 万字正文和 2 KB 错误限制都写在交回结果的层次，没有规定读取 HTTP 原始响应体的上限。若先 `response.json()` 或 `.text()` 再切，异常大响应已经进入服务端内存；长页还可以继续写入存档。这个问题发生在第 4 条的工具日志与 IPC 之前。`services.artifacts.save` 负责写入提交，不提供 `shell` 的内容限额。
- **如何核实：**omp 的 `deepseek.ts:22–25,98–113` 在 JSON 解析前限制成功体 2 MiB、错误体 8 KiB，`providers/utils.ts:154–168` 超限时截断或报错；`agent/backend/resources.ts:110–117` 不限长，`shell` 的限额来自 `nb-harness/src/kit/tools/output-capture.ts:56–68,97–105`，不会随存档服务继承。
- **建议改法：**两条接口都按实际读到的字节限长（不能只信 `Content-Length`），达到上限取消响应体，区分超限、格式无效与无结果，不重试格式或大小错误。验收本机无长度头的大响应、分块跨上限与大错误响应，断言不会成功或留下冒充全文的存档；不要把 omp 的 2 MiB 当 DeepSeek 保证。

### 13. DeepSeek 请求和结果的字段映射不能只用 omp 搜索代码补齐
- **严重程度：重要；类别：正确性。位置：**计划第 12、30–44、47–48、63 行。
- **现象：**`/v1/tools/fetch` 只有路径与产品 `Page` 类型，没有请求字段、响应字段到 `url/title/markdown` 的映射，也没定义 HTTP 200 但无可用正文的结局。搜索把 `snippet` 与 `summary` 都设为必填，却没定义缺字段时是回退、跳过还是失败。`sites/after/before` 只写了拼法，含多个站点或原查询已有操作符时是硬过滤还是尽力而为不明。`score` 也没有说明是上游 `rerank_score`、是否筛结果。
- **如何核实：**omp `deepseek.ts:60–67,94,123–150` 使用 `{query, count}`，在拼完整查询后数 Unicode 码点，过滤非 HTTP(S) 结果并用 `summary ?? snippet`；它只实现搜索。omp 的 `search/index.ts:303`、`query.ts:833–849` 另做宽松后过滤，不能把单纯拼查询等同于该行为。Work README 只验证过搜索、抓取成功及回环拒绝；低分现象见计划第 12 行，不能推出阈值。
- **建议改法：**基于获授权的真实响应定两条 wire 映射、结果归一化与空/坏数据的不同结果；声明站点和日期的格式、冲突及约束强度；拼完再数 128 个 Unicode 码点，测多站点加日期与非 BMP 字符。`need_content` 关掉可保留，不承诺 `content`；`summary` 不可用时定短摘要回退。保留低分可解释，不按单次乱码实验设阈值。

### 14. 状态码不足以承诺“地址被拒”，也不足以判定付费 POST 可安全重试
- **严重程度：重要；类别：正确性。位置：**计划第 12、41、44、51–52、76 行。
- **现象：**把两条接口的 403 一律解释成 `blocked`，但搜索请求没有目标 URL；Work README 只记录了抓取回环地址被拒的一个 403。408、429、全部 5xx 固定等 1 秒重发也把不同结局混在一起：计划记录的是 500/504，没有 501 等证据；网关 504 不证明上游没处理第一次 POST。
- **为什么是问题：**模型或用户可能收到错误的修复指引；首次请求如果已成功但响应未送到，第二次有再次发送和潜在再次计费的代价。没有证据说 DeepSeek 会去重，或任何 5xx 都没计费。
- **如何核实：**对照 Work README“已知情况”、计划第 44 行与 omp `providers/utils.ts:109–126`：同一 403 的通用处理只是 `forbidden`，不能推出具体原因；`runtime/lifecycle.md` 第 112 行也不把取消当作撤回已发送的外部请求。
- **建议改法：**按接口和已确认的结构化上游码细分，未知 403 只写“服务拒绝此请求”，不猜原因。用允许名单界定何时重试，超出总截止的 `Retry-After` 不等也不重发；上游是否已经处理不能判定时，默认不重发，若接受重复计费须写明。用本机端点记录次数并模拟 429、504、明确不可重试状态与退避期间取消；真实拒绝码由获授权者另验。

### 15. 真实接口验收没有区分外部合同、本机行为与真实凭据的落盘限制
- **严重程度：重要；类别：测试。位置：**计划第 63–65、71、75–76 行。
- **现象：**本机端点可以验证我方发的请求和处理结果，不能凭从实测抄来的成功夹具证明错误码、过滤和计费重试与 DeepSeek 同义。真实 smoke 若为了验证整条设置链路而把真密钥经 `setKey` 填进去，会按第 45 行写进明文 SQLite，违反真实模型测试的“不落盘”；一条搜索、一条读取成功也不证明失败分类。
- **如何核实：**`docs/testing/README.md:18,124–130` 要求替身与真实系统有对照、真实模型测试显式 opt-in、通过 `llmTestConfig()` 且凭据不落盘；`models.llm.test.ts:19,33–42` 用启动环境和 `env:` 引用，不能照搬到首版明确不支持 `env:` 的网页设置。`scripts/ci/test-conventions.ts:69–74` 不检查 `*.llm.test.ts` 中的这类读取，这不是 lint 违规。
- **建议改法：**SQLite、RPC、顶层/嵌套调用、存档重开、取消和断线用假密钥、真实本机运行时验收。获授权后用光跑真实 HTTP 适配器、仅内存传真密钥的 `web.llm.test.ts` 核对两条接口的请求/响应映射；联合 Agent smoke 另用不落盘的凭据接线，不为此给产品加测试分支。区分实测失败样本、仅受控夹具和未测分支；缺钥或未授权记“未验证”。实测夹具只入库脱敏后的字段样本，不带认证头、用户数据或原始诊断。

### 16. 已有同名工具的会话中，模型能调 `web_search`，eval 却得到 `unknown-tool`
- **严重程度：重要；类别：正确性。位置：**计划第 7、13、29、47、65、71 行。
- **现象：**现有 Profile 已显式装入 `providerName: "web_search"` 的工具时，新默认工具排在它后面。内核的 `ToolBox.current()` 留先到者；eval 从未去重的 `forProfile()` 另算，再用 `Map` 留最末者。`ctx.invoke` 用内核的生效 id 校验，拒绝 eval 选中的 id。因此同一个工具名顶层成功，代码里失败。全局默认工具会把这个既有缺陷带进没主动配置新插件的会话。
- **如何核实：**`agent/backend/agent.ts:408`、`agent/backend/eval/tool.ts:293–300`、`nb-harness/src/kernel/run/tools.ts:73–85,539–544,578`。在隔离环境经真实 `agentWorld`、本机模型端点与 eval 子进程注册两个不同 id、同名的合成工具：模型收到 `["eval","web_search"]`，顶层执行 `test.alias.explicit` 回 `synthetic-first`；`tool.web_search({})` 对 `test.alias.added-default` 失败 `unknown-tool`。命令：`bash /tmp/review-w00052-t01-design/omp-scratch/run-local-probe.sh /usr/bin/bun --no-env-file --tsconfig-override tsconfig.json /tmp/review-w00052-t01-design/omp-scratch/tool-name-probe.ts`，退出 0。
- **建议改法：**让 eval 用与模型同一份已校验、已去重的生效声明或同一选取规则，不在网页插件另做冲突分支。验收升级后已有同名工具的真实会话，断言顶层与 eval 解析到同一 id；保留 `defaultForAll: true`，但不写成“每个会话都有”：`contributions.md` 输出 4 允许 Profile 不加默认工具及用户移除，已有会话在下一次请求按 id/version 写 `tools-changed`，换钥不升工具版本。
