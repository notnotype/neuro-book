### 1. 持久化合并成一条记录，但“每次手势结束写一次”对不上被并入的数据（editor.session 的写入节奏与作用域）
- **严重程度**：重要；**类别**：接口 / 遗漏；**位置**：提案第 8 节、第 6 节、“影响”。
- **现象**：提案把 `layout-sizes-side`、`layout-sizes-panel`、`views-customizations`、`editor.session` 合成一条，“每次手势结束写一次”。但被并入的 `editor.session`（packages/neuro-book/src/plugins/editor/web/session-record.ts:25-47）带每个标签的 address、editor、preview、pinned、cursor、language，光标由 `groups.ts:439 setCursor` 持续更新，打开、关闭、切标签都会写。这些都不是布局手势。并入后，每次切标签或光标变化都要整条重写布局文档，并和另一窗口的布局手势竞争同一个 revision。
- **作用域也变了，提案没点明**：现行 `views-customizations` 是 user/local（docs/specs/ui/workbench-shell.md:300 验收 9“面板与 Part 状态都在 user 分区”，:236），跨项目共享；`editor.session` 是 project/local；尺寸记录是 project/local。提案改成“绑定项目时 project/local，否则 user/local”，等于视图摆放从“用户级”变成“每个项目一份”。随后“新项目的初始布局取 user/local 那份最近的布局”：绑定项目的窗口从不写 user/local，所以这份布局只来自未绑定窗口，“最近”指什么不清楚。
- **为什么是问题**：现行 Spec 已为 `views-customizations` 写了按字段合成与多窗口冲突重放（workbench-shell.md:255，“另一个窗口改的其它字段保留”）。新的合并记录既没有写频率，也没有冲突粒度；视图实例表里的 `params` 由编辑器插件定义，工作台只持有记录，params 的校验与版本归谁没写。
- **如何核实**：对照 session-record.ts 与 workbench-shell.md:236、255、300，再读提案第 8 节。
- **建议改法**：提案补一句取舍：为什么合成一条，而不是“布局文档”和“编辑器标签会话”两条（标签在布局文档里只存实例 id）。若合并，写明写入节奏（光标与切标签是否去抖）、冲突粒度、`params` 由谁校验，并把“视图摆放从 user 级变成项目级”作为一项明确的行为变化单列，同时说清新项目的初始布局从哪来。

- **建议改法**：在 ADR 里写一小段“评估过 dockview 等库：许可证有付费档、搬 DOM、没有矩形摆放，不采用”，并引用上面的 2026-09-20 记录作为递归 DOM 失去理由的证据。

### 4. 键盘拖放在现行 Spec 里是已验收的无障碍功能，提案的拖动一节完全没提
- **严重程度**：重要；**类别**：遗漏；**位置**：提案第 3 节；docs/specs/ui/workbench-shell.md:132（输出 23）；t67 plan.md“键盘适配”。

### 5. 把“一棵树”与已经独立有价值的几件事绑在同一份提案里，且一棵树这一段没有回头路
- **严重程度**：重要；**类别**：结构；**位置**：提案“问题”1-6、“影响”的回滚与风险。
- **现象**：六个问题里只有第 1 个需要一棵树。第 2 个（递归 DOM）靠按矩形摆放解决，第 3、4 个（手势三份、落点多结果）靠手势会话与落点判定的统一解决，第 5 个（窄屏）靠手机呈现，第 6 个（nb-ui 占四成）靠拆包。我按目录统计，nb-ui 里 grid、splitter、sash、NestedGrid 等非测试代码约 5240 行，加三个 composable 约 845 行，约占 17528 行的 35%，与“约四成”大致相符。提案自己也说拆包、手势、渲染层、一棵树“可以分段合入”（影响一节）。
- **代价集中在最后一段**：一棵树要重写外壳二、三的大部分 Spec，改工作台约 10474 行（不含测试，核实属实）与测试 5915 行，加编辑器 groups、session 等约 1494 行；取消 ViewContainer、删 5 个面板命令与 3 个状态键、旧记录不迁移。v2 已发 0.11.0（PROJECT-STATUS.md:7），“已有用户的布局丢一次”是真有影响的。提案自己写“一棵树那段合入后再回退，用户在新布局里的调整会丢”。
- **判断**：开发者决定 2 已确认一棵树，我不推翻。但“值不值”目前只有一句话支撑，而前几段（拆包、手势会话、矩形渲染）即使不做一棵树也成立。
- **建议改法**：提案里明确 t04-t06 各自独立交付、各有自己的验收；一棵树（t07）合入前，用 t04-t06 之后的真实手感再确认一次（建议单列在“影响”里作为决策点）。把“编辑器节点移到外层很自然”落成一两条用户能观察到的验收场景（例如：编辑器标签拖到整个工作台的某一边拆分、与工具面板并排），让这一段的价值可以被检验。
- **未验证**：这几段的耦合程度——t06 的矩形渲染层能否在两棵树的情形下先落地，需要读 t06、t07 的任务书和原型代码，我没有逐一核实。

### 6. 每个标签一个内容实例，切走“隐藏不卸载”，没有上限也没有回收的合同
- **严重程度**：重要；**类别**：接口 / 遗漏；**位置**：提案第 6 节、“影响”的风险第三条。
- **现象**：提案承认“每标签一实例的 DOM 占用没有量过，开很多标签时可能要加回收”。证据只有：普通章节 JS 堆增量在噪声内、第二个 Monaco 约 6MB（t02 README“每标签一实例可以接受”）。现行记录允许每组 200 个标签、16 个组（session-record.ts:25-26 `MAX_TABS`、`MAX_GROUPS`），也就是理论上可以保持三千多个活实例。
- **为什么是问题**：“从不卸载”是写进合同的生命周期。以后加回收（LRU 卸载）意味着要保证卸载后能由 `params` 恢复光标、滚动、未保存输入，这些现在没有写在 `params` 里；Spec 里关于撤销历史与未裁决输入的规则（editor.md:251 输出 49）也要改。先把合同定成“实例可以被工作台回收，回收不丢状态”，比以后改合同便宜。另外，提案“按建议写、不再单独问”的几项（每标签一实例、一条记录、旧记录不迁移、绑项目存在项目分区）并不在决策记录的三条开发者批准里（t03/README.md 只写了“按建议写”），应有开发者的追认。
- **建议改法**：合同写成“工作台可回收不可见的实例，回收前把光标与滚动写进 `params`”，或明确写“本期不回收，上限为 N”；决策记录补一条开发者追认。

### 7. 手机呈现被当成产品规则替换紧凑呈现，但同一份提案把它归为“验证级”
- **严重程度**：重要；**类别**：不变量 / 遗漏；**位置**：提案“非目标”第二条与第 7 节。
- **现象**：非目标写“手机呈现的软键盘适配、触摸拖动与真机验收：这次是验证级”。第 7 节却把宽度小于 800 的一切窗口切成手机呈现：一次一个部件、没有拖动与分隔线、状态栏隐藏。现行的紧凑呈现（workbench-shell.md:72）是在 800 以下仍显示并排的活动栏与纵向堆叠，保持“其余主体 Part 纵向排布”。800 以下含桌面半屏窗口，也就是用户把窗口拖窄就失去分栏、拖动和状态栏，而软键盘问题（对一个写字应用，手机呈现下编辑区被键盘挡住是主流程）只“记录”。
- **建议改法**：二选一：手机呈现只在 `pointer: coarse` 或宽度小于 600（t01 原来的口径）时启用，600-800 仍保留紧凑呈现；或者接受 800 但把“窄桌面窗口一律单部件”作为明说的行为变化写进“影响”，并把软键盘处理列为这个呈现上线前的条件。

### 8. 可以现在不做的东西（YAGNI）
- **严重程度**：建议；**类别**：结构；**位置**：提案第 3、5、10 节。
- **现象 / 建议**，按“删除成本从低到高”：
  1. **最外层落点与“缝当落点”，“模型支持，工作台不开”**（第 3 节两处，决定 9）：没有调用者的分支，需要测试和文档维持。建议模型里不做，需要时再加；这条决定是开发者批准的“不开”，不是“模型要支持”，后者可以单独撤。
  2. **卡片、拖影、分区外观经“插槽”替换**（第 3 节“反馈样式是参数”）：开发者的原话是“样式应该提供可调节接口，不用动 sdk”，CSS 变量已满足。目前只有一个使用方，插槽把公开接口面扩大了，却没有消费者。建议先只做 CSS 变量，插槽等第二个使用方出现。
  3. **两种拖动手感都成为长期支持的用户设置**（第 3 节表）：需要的是对比验证，不一定要长期都发。每种手感有自己的反馈、取消、提交规则和测试，维护成本是翻倍的。决定 3 是开发者批准的，所以建议只补一句“发布一个版本后根据使用数据决定是否收一种”，不推翻。
  4. **标签条库里支持多行插入判定与固定标签分区**（第 5 节）：editor/web/tab-drag.ts（349 行）里现有的是编辑器自己的规则，搬进布局库后库要知道多行和固定区。这条是开发者认可的（t01 决定 13），但“库里支持，由宿主给规则”的界面没有写，等于把设计推给了实现。
  5. **条可以移到四边并随边改方向，竖排中文，放不下收进“⋯”**（第 1 节）：开发者原话是“我感觉也可以做成”，是一个顺手的可能性，而代价是竖排、溢出、图标不转的一整套 UI。第 1 节里已写“实现时在 Lab 出稿给开发者看”，我建议本期只把条做成树上的叶子（借动画），“可移到另三边”放到第二期。

### 9. 提案花篇幅写调参数值，却没讲清 nb-layout 与宿主的边界：谁拥有模型、谁给落点规则
- **严重程度**：重要；**类别**：接口 / 文档；**位置**：提案第 3 节表、第 10 节。
- **现象**：第 3 节的表和正文写了 28%、14%、150ms、6px、200ms、470ms、`cubic-bezier(.23,1,.32,1)`、最多 10 项等数值，这些是 Spec 与代码里的调参，不是架构。而下面这几个直接决定包界面的问题没有答案：
  1. **LayoutDoc（面板、条、浮动列表、视图实例表）归 nb-layout 还是应用？** 第 10 节“新增”列了“落点判定与登记、按矩形摆放的渲染层、标签条、浮动层”，“留在应用”列了“具名面板、视图声明、记录、命令”。但树本身（沿用 `createGrid`）和面板/条/浮动这些节点种类放在哪，没有说。面板的 `role: tool | editor` 是应用概念，却出现在第 3 节的落点表里（“工具视图到编辑组中央不接受”）。
  2. **谁表达“什么能落在哪里”？** Trellis 用 `allow`/`placement` 声明。提案落点判定是“纯函数”，规则却是写死在表里的。若这张表在库里，库就知道了“工具/编辑器”；若在应用里，库需要一个策略入口，这个入口没有出现在第 10 节。
  3. **纯 TS 的 `.` 不依赖全局 `window`/`document`，但手势会话需要指针捕获、失焦、页面隐藏、吞 click。** 这些事件源怎么注入没有写。这条约束的来由是 t12 的“操作系统级窗口”验证，那是尚未决定的备选，却先约束了整个包的结构。
  4. **应用内浮动与现有的 nb-ui 浮动窗口**：nb-ui 有 `useFloatingWindow`（295 行，拖动、六个缩放手柄、夹到容器内，被 Dialog 使用），提案“浮动层”写成“新增”，没说是否复用它的定位与缩放逻辑。
  5. **`data-editor-group` 的去留自相矛盾**：第 3 节写“落点改成统一登记，取代资源树读 `data-editor-group`”，“影响”又写“`data-editor-group` 标记保留，资源树不再依赖它”。没有读者的标记保留下来就成了没人维护的死标记。
  6. **`nbook.editor.open` 的 `group` 是“编辑组面板的 id”**：面板 id 在树里是动态生成的，用户拖动、被拖空重建后是否稳定、重启后是否稳定，没写；`"side"` 的含义要在没有“编辑区”概念的树里重新定义（取“当前编辑组右侧”？不存在时新建？）。
- **建议改法**：把第 3 节的数值移到 Spec，换成一张“nb-layout 的职责与扩展点”表：库拥有什么模型、宿主经哪几个入口给落点规则/事件源/标签内容；把 1、2、6 当成第 10 节必须回答的问题。

### 10. 窄屏、条、状态键等次要点（合并为一条）
- **严重程度**：建议；**类别**：文档
- **公开状态键改名**：`nbook.workbench/nonCompact` 换成表示“不在手机呈现”的键，提案没给名字。该键在 workbench-shell.md:88 已是对插件公开的合同，且 commands 的 `when` 依赖它（panel 命令已被删，但第三方插件可能引用）。需要在 SDK 变化一节写明它是破坏性改名还是别名过渡。
- **SDK “不变”的说法偏强**：`location` 的含义从“默认位置”变成“第一次放到哪个具名面板”，`ViewContext.location` 在非具名面板里给声明默认值，删了 `set-panel-position` 等命令和三个状态键。这些对第三方插件都是行为变化，应列在“接口”一节，而不是只写“SDK 形状不变”。
- **旧记录“不迁移、不删”的回滚说法**：新旧记录互不覆盖，但回滚到旧版本后，新版本里打开的标签不会回到旧 `editor.session`（旧记录停在升级前的内容）。这是一个可接受的损失，但“回滚”一节应该说清。

## 五个问题的总答复

1. **问题是真的吗？** 是。递归 DOM 当初的理由（reka-ui 嵌套分割原语）在 2026-09-20 的改造里已不成立（workbench-view-host.md:371-373），手势三份共 1110 行（drag-session.ts 451、tab-drag.ts 349、tree-drag.ts 310，数字属实）。但六个问题里只有一个需要“一棵树”，其余可独立落地（第 5 条）。
2. **有更简单的做法吗？** 现成库（dockview）搬 DOM，且多行标签/固定标签/键盘导航是付费档，不能满足提案（第 3 条）。自写的路线合理，缺的是记录。
3. **YAGNI：** 见第 8 条。
4. **死胡同：** 数据格式（第 1、6 条）、公开状态键与 SDK 语义（第 10 条）、nb-layout 的包界面（第 9 条）。
5. **细节与架构：** 提案详写调参，缺 ADR 与备选对比（第 2、9 条）；漏了键盘拖放（第 4 条）。
