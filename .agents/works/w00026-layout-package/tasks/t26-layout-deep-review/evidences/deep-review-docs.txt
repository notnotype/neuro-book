## docs-04

### 4. layout-drag Spec 与会话文档说 `resolve` 不产生副作用，宿主实现的 `resolve` 写 DOM、挪窗、登记粘滞候选，放下时的那一次也写

- 严重程度：重要；类别：文档（合同与实现不一致，交互合同缺一条）
- 位置：docs/specs/ui/layout-drag.md 输入与前置条件的 `DragSessionOptions.resolve`（“同步判定这一刻的落点，不产生副作用；可以读宿主维护的状态”）、输出 6（“用松手的坐标再判一次，这一次不发布”）；packages/nb-layout/src/vue/drag-session.ts:48（“放下时、自动滚动时也会调，所以宿主可以……记下最近的落点……不能假定一次移动只调一次”）；packages/neuro-book/src/plugins/workbench/web/layout-drag.ts:1-13 头注释（“判定是纯读”）与 :943-958 `resolve`（`setRejected`、`options.moveGhost`、`options.placeFloat`、`resolveDrop` 里的 `live.offer(drop)`）。
- 现象：三处说法互相矛盾。
  - Spec 与 `drag-session.ts` 的接口注释分别写“不产生副作用”和“宿主可以记下最近的落点”；
  - 工作台的 `resolve` 实际做了四类写：①`document.documentElement` 上的“被拒绝”标记；②拖影位置 `moveGhost`；③整窗拖动时 `placeFloat` 写窗的 translate；④`live.offer(drop)` 把候选交给实时布局的粘滞/等待状态机；
  - 会话在放下时也调 `resolve`（输出 6 的“再判一次，不发布”），所以上述四类写在松手那一刻也发生一次：`placeFloat` 把窗挪到松手坐标、`live.offer` 用松手点的候选推进粘滞，而这一次判定“不发布”。
  - layout-drag.ts 头注释又写“判定是纯读”，指的是 `resolveLayoutDrop`/`dropAt` 那一层，不是传给会话的 `resolve`。
- 为什么是问题：Spec 的“状态与转换”恰恰要写调用方能依赖的先后与次数：`resolve` 在一场里被调几次（每帧发布一次、放下一次、边缘滚动每一帧各一次、键盘每次移动）、哪几次发布、哪几次不发布、写不写。现在宿主靠 drag-session.ts 里的一行接口注释才知道不能假设“一次移动一次”，Spec 读者会照“无副作用”写出放下时会改状态的 `resolve`；反过来，想把 `resolve` 当纯函数缓存或重放的人会破坏实时布局的候选稳定计时。
- 如何核实：读上面的行号；在 `layout-drag.ts` 的 `resolve` 里打日志，实时布局拖一个标签到别的面板后松手，会看到 `live.offer` 在松手帧多调一次。
- 建议改法：Spec 把这条改成交互合同：`resolve` 每帧至多一次发布判定，另在放下与边缘滚动的每一帧各调一次（不发布）；宿主在 `resolve` 里只允许“记录最近一次判定”这一类可重入的写，不允许有不能重复的副作用；DOM 写放在 `state` 的订阅里。`layout-drag.ts` 头注释的“判定是纯读”改成“落点规则是纯读，会话的 `resolve` 回调另外记录候选、写拖影与窗的位置”。

- 现象：
  1. “输出与可观察行为”是无编号的圆点列表，README 要求“输出条目、失败码与验收场景都编号。编号稳定”。别的 Spec 引用它时只能写小节名：workbench-layout.md 写“nested-grid 的‘内容层’”“‘过渡’”“‘按矩形摆放’”，layout-drag 的证据行、nested-grid 自己的证据行（“输出‘按矩形摆放’‘取整’…”）也是这样。粗体小标题成了事实上的 id，但改名没有机检。测试名无法按 README 规定写“输出 N”，所以 nb-layout 的测试里引用 nested-grid 的只有零星几处。
  2. 单条过长、一条多件事。“过渡”一条约 2600 字，包含：程序与手势的区分、新叶、从零长出来、整棵子树新开、离开的叶留着缩回去（四个条件）、降到零的叶、leafShape 裁切、浮动窗例外、手势中的行为、减少动效，还夹着一个“（planned）”。“内容层”一条约 1500 字。README 要求每条一个可判定的行为；这两条没法对应一条测试，改一句要在整段里找。
  3. 写进了实现与 API 形状：第 76 行起的“`useLayoutExtent`共享clientWidth/clientHeight与ResizeObserver”“`useGridLayout`消费grid/extent/contextKey，发布node/layout/revision，结构API后invalidate”“`resolveGridInsertion`按显式轴……计算beforeId”是组合式函数的实现说明，换一种实现（比如不用 ResizeObserver）这些句子都要改，按 README 判据 1 属于代码注释或 `grid.md`。输出“内容层”里的 `insetTop`、`placeLifted(rect)`、`overlay` 插槽、`content-parked`、`lifted-head`，输出“浮动窗”里的 `float-chrome`、`placeFloat(id, offset)`、`data-*`、`translate` 也是 Vue 组件的 API，属于 `NestedGrid.md`。
  4. 同一内容两处写：这些组件细节在 `NestedGrid.md`“布局”“交互”两节里又几乎逐字写一遍（例如 `data-anchor-right`、贴右边平移、`leafShape` 裁切），两边已经有细微差别（Spec 里“新叶的主轴宽度从零长到终点…”与 md 里的“纵向不贴”），改一处会漏另一处。

- 位置：packages/nb-layout/src/vue/DropFeedbackOverlay.md“数据”节后半（几何入口三条）与“状态与边界”的“宿主使用须知”；packages/nb-layout/src/grid-drop.ts:133（`resolveGridInsertion`）、`resolveGridEdgeDrop`、`GRID_EDGE_RATIO_DEFAULT`；docs/specs/ui/nested-grid.md 第 79 行（“`resolveGridInsertion`按显式轴/给定成员顺序计算beforeId与指示线；`resolveGridEdgeDrop`保持Editor20%边缘与left/right优先”）；packages/nb-layout/src/index.ts 的导出。
- 现象：
  1. `grep -rn "resolveGridInsertion\|resolveGridEdgeDrop\|resolveListInsertion" packages --include=*.ts --include=*.vue --include=*.md`（排除测试）：新应用里只有 `tab-strip-geometry.ts` 用 `resolveListInsertion`；`resolveGridInsertion`、`resolveGridEdgeDrop` 的使用者是 packages/neuro-book-legacy（旧应用）、nb-layout 自己的测试（61 处）和上面两份文档。工作台的落点全走 `layout-drop.ts`（`resolveLayoutDrop`）。也就是说，包的公开入口里有两个函数、一份 Spec 条目和一份组件文档的“宿主使用须知”都围着一条没有人走的路线写。
  2. DropFeedbackOverlay.md 用的是已经删掉的词：`entryRect` 写“切换器条目高亮盒”、`areaRect` 写“空容器内容盒”（容器切换器是旧应用的），“宿主使用须知”第一条写“接入合同是‘显示落点、释放提交’……不要用边拖边改 DOM 顺序的乐观排序代替”，而 Spec workbench-layout 输出 38 的实时布局正是边拖边改布局（反馈就是布局本身）；这条“须知”现在对该组件的最大使用者不成立，却没有说明它只适用于落点指示那一种手感。
- 为什么是问题：新宿主会照 md 去用 `resolveGridInsertion` 与“切换器”词汇做反馈，又会把实时布局当作违反接入合同；包的公开面比实际能力大，留给维护者的是要不要替没人用的路线保持兼容的负担。（没有记录的理由：我没在 ADR 0044/0046 里搜到保留这两个函数的原因。）
