## api-01

### 1. 主入口的“布局文档”层是工作台的领域模型：第三方没有活动栏、状态栏就造不出合法文档，也没有构造器

严重程度：重要；类别：不变量（API 形状）
位置：packages/nb-layout/src/layout-doc.ts:20-22（LayoutBar、PanelName 写死）、1297-1374（validateLayoutDoc）；src/index.ts:5-9（和纯 grid 同一个入口导出）；src/layout-doc-fixtures.ts（唯一的构造器，package.json 的 files 里 `!src/**/*-fixtures.ts` 把它排除在发布之外）

现象（已跑实验 reports/api-exp-validate.ts，bun run 可复现）：
- 用只含 “nav 工具面板 + ed 编辑组” 两片叶的树造 LayoutDoc，`validateLayoutDoc` 返回 `{ok:false, code:"invalid", detail:"条要恰各一个"}`。校验硬性要求树里恰好一个 `bar:activitybar` 叶和一个 `bar:statusbar` 叶（layout-doc.ts:1314）。
- 同一函数还硬性要求：树里至少一个 role 为 editor 的面板（1372）；具名面板的 `name` 只能是 `sidebar`/`auxiliarybar`/`panel` 三个，且各至多一个（1360）；`hiddenBars` 只能含 `activitybar`/`statusbar`（1306）。“左侧栏 + 编辑区 + 底部面板” 的第三方应用只能把别人的活动栏和状态栏塞进树里，哪怕它没有这两样东西。
- 校验之后工作台还有一层 `fitsSkeleton`（default-tree.ts:186，`V[H[活动栏, 侧栏, V[编辑组…, 面板], 右栏], 状态栏]`）才是真正的骨架，库里没有，也没有文档。第三方要靠读 default-tree.ts 的 100 行手写树才能造出一份文档（panels、tree、`ref: panelRef(id)`、`activeContainer`/`entries` 的关系都要自己对）。
- 公开入口 `.` 把两层放在一起：`createGrid`（领域无关，Spec nested-grid 的“与领域无关的 grid”）和 `layout-doc`/`layout-project`/`layout-drop`/`live-drop`（工作台）。package.json 的 description 写“工作台的布局工具”，但 publishConfig.access 为 public，README 只有两行导入，没有一处告诉使用者“后一半只给工作台”。使用者按名字看到 `moveTabToEdge`、`applyLayoutDrop`、`LayoutDoc`，会以为这就是通用的“标签拖到边缘拆分”能力。

为什么是问题：
- “标签能在面板之间拖动、能拖到边缘拆出新的一块、能收起恢复、能存下来”正是第三方最想要的，而这一整块能力只对工作台那一种形状成立。使用者要么读完 1300 行 layout-doc.ts 才知道有这些限制，要么试一次被 “条要恰各一个” 拒绝，错误文案还不说为什么。
- 命名在误导：`PanelName`（只有三个值）、`LayoutBar`、`PanelRole`（tool/editor）、`TabRef`（`kind:"view"|"tab"` 加 `type`，内置了“编辑器标签”概念）、`TabRef.type` 为任意字符串但 `kind` 两种写死。
- 类型层面也防不住：`LayoutDoc.panels` 是 `Record<string, PanelRecord>`，`validateLayoutDoc(unknown)` 返回 `doc: value as unknown as LayoutDoc`（1373）是纯断言；手写的文档能编译，运行时才在 validate 里被拒。

如何核实：bun run reports/api-exp-validate.ts；或读 layout-doc.ts:1297-1374 与 default-tree.ts:65-107。

建议改法（优先让部件变少）：
1. 不改模型，改入口：把 `layout-doc`、`layout-project`、`layout-drop`、`live-drop` 移到子路径 `@notnotype/nb-layout/workbench`（或 `/doc`），`.` 只留 grid（createGrid、类型、手势会话、sash 命中）；README 与 package.json description 写明“`.` 通用，`/workbench` 是工作台那一种形状”。工作台里 20 多个文件的 import 路径要改，机械迁移。
2. 若要让第三方真的能用文档层：把“条”“具名面板”“编辑组至少一个”这三条从 validateLayoutDoc 里抽成宿主给的 `LayoutDocShape`（`bars: readonly string[]`、`regions: Record<string, {orientation}>`、`requireEditor: boolean`），默认值就是现在的工作台。代价是 `PanelName`、`REGION_ORIENTATION`、`isContainerAnchor` 等一串都要参数化，工作量大，只有确定要对外时才值得做；先做 1。
3. 不论哪种，发布一个 `createLayoutDoc({regions, editors})` 构造器（把 layout-doc-fixtures.ts 的 H/V/docOf 里能公开的部分拿出来），不要让第三方照抄 default-tree.ts。


## api-02

### 2. LayoutPolicy 里 `edgeTarget`、`seamAccepts` 只管判定，提交不守；同一个策略对象里 `accepts`、`canInsert` 守、这两个不守，类型上看不出来

严重程度：重要；类别：不变量 / 合同
位置：packages/nb-layout/src/layout-doc.ts:88-101（LayoutPolicy 的注释）；layout-doc.ts:981-1049（movePanelToEdge、moveTabToEdge 不调 edgeTarget）；layout-drop.ts:154、251-266、333、365、507-524（只有判定与键盘候选在调）

现象：
- `LayoutPolicy` 一个接口放了 5 个回调。`accepts`（moveTabToEdge:1036、movePanelToEdge:1000、moveTabToStrip:792）与 `canInsert`（799、829）在写入时会再验；`edgeTarget`、`seamAccepts` 的注释写明“提交时不再问它，宿主要在写入的出口兜底”（layout-doc.ts:94、96）。
- 实验（reports/api-exp-policy.ts，bun run 可复现）：策略 `edgeTarget` 让工具面板“左、右边没有窄带”（只能上下拆）。同一份文档、同一个策略对象，直接调 `moveTabToEdge(doc, {tab, target: {kind:"split", panel:"panel", edge:"left"}}, policy)` 返回 ok；`applyLayoutDrop(... {kind:"edge", target:{...edge:"left"}} ...)` 也返回 ok。策略声明“不允许”的落点被原样写进了文档。
- 工作台是靠 `apply()` 出口的 `fitsSkeleton`（layout-doc-store.ts:230）兜底的，这是它自己写的第三层；第三方不知道这件事就会以为策略是写入时的权威（命名上它们和 `accepts` 并排，没有任何区别）。

为什么是问题：
- 同一个对象里的回调，一半是“不变量守卫”、一半是“只用于画指示线”，使用者无法从类型或名字看出来。典型误用：命令、快捷键、插件 API 直接调 `moveTabToEdge`（工作台里 `EditorPanels.tabs.moveToEdge` 就是这条路，layout-doc-store.ts:229 的注释自己承认“服务能传任意目标”），绕过了策略。
- 想让“工具面板只能上下拆”成为真正的规则，只能第三方自己在每个写入出口复制一份判断；而库已经有 `accepts` 的写入守卫，说明“库在写入时验策略”是它自己的约定，这两个回调破了例。

如何核实：bun run reports/api-exp-policy.ts；或读 layout-doc.ts:88-101 与 moveTabToEdge 的实现（1024-1049）。

建议改法：
1. 最小：把 `edgeTarget`、`seamAccepts` 从 `LayoutPolicy` 拆到 `LayoutDropRules`（只给 `resolveLayoutDrop`、`enumerateDropCandidates` 用），`LayoutPolicy` 只剩写入时也守的 `accepts`/`canInsert`/`newId`。名字就能说明“哪些是写入的规则、哪些只是落点怎么画”。
2. 更彻底：`moveTabToEdge`/`movePanelToEdge`/`openPanelAtEdge` 提交时对 `target` 调一次 `policy.edgeTarget(doc, tabs, panel, edge)`，结果与传入的不一致就拒绝（“这条边不是落点”）；`between` 目标对应 `seamAccepts`。库少一个“宿主要兜底”的约定，宿主的 `fitsSkeleton` 保留作骨架校验。代价：每次提交多一次 findTreeNode，可忽略。


## api-03

### 3. “手势落账写回文档”和“结构操作前先写回意图”要宿主手写，库只给零件；漏一个输入不报错，只是静默写坏尺寸意图

严重程度：重要；类别：不变量 / 正确性（API 形状）
位置：packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts:208-215（`rebased()`、`untouchedFixed`）、:221-237（`apply`）、:420-440（`commitGesture`）；packages/nb-layout/src/layout-doc.ts:466-495（`rebaseIntents`）、layout-project.ts:36-47、95-107（`collapsedTo`、`regionAnchors`、`fixedNodesOf`）

现象（从代码推断；没有在浏览器里跑）：
- 拖一次边界之后文档要这样更新（工作台 commitGesture 的 20 行），第三方必须逐字照抄：
  1. 对 `collapsed` 里的每个节点 id，先用 `projection.regionAnchors.get(id) ?? id` 换成锚的面板 id，再 `setPanelCollapsed`；
  2. 锚是隐藏着的、又被拉开（`value === false`）时再 `setPanelHidden(锚, false)`；
  3. 再 `rebaseIntents(next, sizes, projection.collapsedTo, frozen)`，其中 `frozen` 是 `fixedNodesOf(projection.input)` 里“呈现尺寸和手势结果相差不到 0.5px”的那些（`untouchedFixed` 里写死了 0.5 的容差）。
- 每次结构操作（`moveTabToEdge`、`openPanelAtEdge`…）之前要先 `rebaseIntents(doc, presented, projection.collapsedTo, fixedNodesOf(projection.input))`（`rebased()`），不然新块是按旧意图分的。layout-doc.ts 头注释里一句“手势落账后和结构操作之前都走它”是唯一说明；`moveTabToEdge` 的签名与返回值上没有任何痕迹提醒“你该先 rebase”。
- 上面四个输入（`collapsedTo`、`regionAnchors`、`frozen`、`presented` 尺寸）都来自 `projectLayoutDoc` 的结果或呈现事实；`NestedGrid` 事件载荷（`GridGestureCommit`）里没有 `frozen`，也不知道“区域的锚”。这是库内部“呈现树 id ↔ 文档 id”的换算，没有包起来。

为什么是问题：
- 漏一步不报错：漏 `regionAnchors` 映射 → 单分节时把分节自己标成收起，区域本身没收起（commitGesture 注释自己写了这个坑）；漏 `frozen` → 窗口缩窄时被压缩的保留像素面板，在拖一下别的边界后把压缩后的尺寸写成意图，窗口放大后不再回到原宽；漏结构操作前的 rebase → 拆分比例按旧意图。三者表现都是“过一会儿布局不对了”，没有一处能在编译期或运行期被发现。
- 第三方要读懂这三步需要先理解 `collapsedTo`（呈现里塌陷的分支）、`regionAnchors`（区域节点）、`fixedNodesOf`（保留像素）三个概念，它们在 `LayoutProjection` 的注释里各占一大段。

如何核实：对照 layout-doc-store.ts:421-440 与 NestedGrid.md 的“接入”一节（只讲到 `host.onGestureCommit`，没讲文档层）；浏览器复现思路：在 e2e 环境里把窗口缩到放不下侧栏与右栏（保留像素的面板被压缩），拖编辑区与底部面板之间的边界，再把窗口放回原宽，看侧栏宽度是否回到原值；把 `frozen` 参数换成空集重试，对比。

建议改法：
1. 库里加一个 `applyGestureCommit(doc, {projection, presented, sizes, collapsed})`（工作台 commitGesture 的前半，不含 `schedule` 保存），返回 LayoutDoc；`untouchedFixed` 的容差作为常量一并进去。
2. 库里加 `rebaseForOperation(doc, projection, presented)`，包装 `rebaseIntents(... collapsedTo, fixedNodesOf(...))`；更好的是让结构操作接受可选的 `presented`/`projection`，内部自己 rebase，调用方少一个要记的前置步骤。
3. 工作台的 `commitGesture`、`rebased` 改成调它们；两处的差异（`schedule`）留在工作台。


## api-04

### 4. “标签拖到面板、拖到边缘拆分”没有可直接接的控制器：库只给零件，约 1400 行控制代码（layout-drag.ts 1041、live-drag.ts 340）留在工作台里

严重程度：重要；类别：代码质量 / API 形状（缺失的公共能力）
位置：packages/neuro-book/src/plugins/workbench/web/layout-drag.ts（1041 行）、live-drag.ts（340 行）、entry-drop.ts（174 行）、drag-presentation.ts（86 行）；库侧：packages/nb-layout/src/vue/drag-session.ts、src/layout-drop.ts、src/live-drop.ts

现象：
- 第三方想要的“标签能在面板之间拖、能拖到边缘拆出新块”，库给的是：`createDragSession`（泛型 `<S, D, R>`，7 个必填回调：`root`、`sourceAt`、`resolve`、`actionKey`、`commit`，另 `activate`/`onEnd` 等十来个可选）；纯函数 `resolveLayoutDrop(input)`、`layoutDropPanelAt`、`layoutDropSectors`、`layoutSeamsOf`、`previewEdgeDrop`、`applyLayoutDrop`；`measureTabStrip`/`resolveTabStripInsertion`/`tabStripInsertionIn`；三个反馈组件。没有一处把它们接成一条线。
- 接线要自己做的事（从 layout-drag.ts 看出来）：
  1. 把自己的 DOM 量成 `LayoutDropPanelGeometry[]`（`id`、`frame`、`body`、`strip`、`insertionAt`）：工作台读的是它自己的标记 `data-leaf`、`data-shell-card`、`data-panel-head`、`data-panel-strip`（layout-drag.ts:371-382），这些标记库不提供也不约定（`data-leaf` 是 NestedGrid 的，其余是工作台的）；`excluded`（条与标题栏）也靠工作台的标记取。
  2. 来源判定（`sourceAt`：`data-panel-tab`、`data-no-drag`、`data-no-drag-start`，layout-drag.ts 头注释）：`TabStrip` 写了 `data-panel-tab`，但 `data-no-drag*` 是工作台的约定，库里没有出现（`FloatWindowHandles` 写了 `data-no-drag`，却没有文档说明它的含义）。
  3. 预览缓存（`previews` Map，键里带容器尺寸，一场里文档被改了要作废，layout-drag.ts:193-196）、结构键（`structure()`，一场里结构变了整场取消）、被拒绝的落点怎么显示、放回原处怎么不提交（`inPlace`）、键盘拖动的区域与位置列表（`enumerateDropCandidates` 只给候选，拿起/停靠/回焦点还是自己的）。
  4. 标签条里排序跟手（`measureSorted`，layout-drag.ts:336-368：直接写元素的 `translate`、`visibility`、`z-index`，约 60 行）。
  5. 实时布局的整套：帧循环、卡片追赶指数逼近、来源收起与展开、`candidateDoc` 摆预览（live-drag.ts 全部，库里只有 57 行的 `stepLiveDrop`/`insideShownSlot`）。
- `LayoutDragOptions`（layout-drag.ts:68-108）有 22 个成员，其中纯布局相关的只有 `doc`、`policy`、`projection`、`extent`、`showPreview`、`placeCard`、`commit`；其余是工作台的（`catalog`、`editorTabs`、`titleOnly`、`maximized`、设置项 `sectors`/`feel`/`cardShrink`/`cardRefresh`）。74 行代码里出现活动栏、容器、编辑器标签、`data-shell-*`、`data-tool-*` 一类工作台才有的东西。库与工作台的分界不在这里，而是落在“拖动控制器”的中间。
- 该 Spec（layout-drag.md 末尾“公开接口”）只承诺 `DRAG_GESTURE_DEFAULTS` 与 `data-drag-feedback`；`data-drag-feedback` 一个自带的反馈组件里只有 `DropSectorsOverlay` 自己写了它，`DropFeedbackOverlay` 要宿主传 attr（靠 `pointer-events:none` 才碰巧不挡命中），没有写进 DropFeedbackOverlay.md。

为什么是问题：
- 第三方要重写 1000+ 行才能得到工作台那种拖动；其中“读 DOM 取矩形、起拖判定、预览缓存、结构键”和工作台无关，却没有从工作台里分出来。同一份代码在 Lab 里的 `DragSessionScene.vue`、编辑器区的 `tab-drag.ts`、资源树里各抄了一份相似的骨架。
- 库的拖动能力（落点规则、分区、预览函数）是按“宿主传矩形”写成纯函数，设计上是对的；缺的是把“矩形怎么来”收口的那一层。

如何核实：读 layout-drag.ts 全文；统计 `grep -c "data-shell\|data-tool\|data-panel-head" layout-drag.ts`。

建议改法：
1. 在 `@notnotype/nb-layout/vue` 加 `useLayoutDrag(options)`，只收布局相关的：`root`、`doc`、`policy`、`projection`、`extent`、`panelOf(element)`（给面板 id 的是宿主，取代 data-leaf/data-shell-card 的约定）、`measure(panelId) => {frame, body, strip}`、`commit(source, action)`；返回 `state`、`session`、`rejected`，内部做预览缓存、结构键、键盘候选。工作台的 `createLayoutDrag` 在它上面加活动栏、容器、编辑器标签。
2. 实时布局的帧循环（卡片追赶、来源收起、候选稳定）只有工作台一个用户，先不抽，但在 NestedGrid.md 里写“实时布局只有工作台实现；第三方只用落点指示”，让使用者早点知道边界。
3. `DropFeedbackOverlay` 自己写 `data-drag-feedback`（和 `DropSectorsOverlay` 一致），文档里写明。


## api-05

## api-10

### 10. 落点判定只有 `null` 一个“不行”：面板外、被拒绝、被排除三种情况要靠再调 `layoutDropOverPanel` 才分得开；同一个 `LayoutDropInput` 要喂四五个函数

严重程度：建议；类别：代码质量 / API 形状
位置：packages/nb-layout/src/layout-drop.ts:279-300（`layoutDropOverPanel`、`resolveLayoutDrop`）、:181（`layoutDropPanelAt`）、:219（`layoutSeamsOf`）、:319（`layoutDropSectors`）；使用方 packages/neuro-book/src/plugins/workbench/web/layout-drag.ts（`rejected` 的 ref、`overRejected`、`editorRefusal`）

现象：
- `resolveLayoutDrop(input)` 的返回值是 `LayoutDropAction | null`，注释写“`null` 是没有落点（工作台外、标题栏、条、被接受矩阵拒绝）”。`layoutDropOverPanel` 的注释写明为什么要另一个函数：“不用 `layoutDropPanelAt`：它在缝里只找能接收的那块，两块都不接收的缝会被当成不在面板上”。
- 于是宿主要的三态——在面板外（松手什么都不发生）、在面板上但被拒绝（松手取消、光标变禁止）、有落点——要写成 `const action = resolveLayoutDrop(i); if (action === null && layoutDropOverPanel(i)) { rejected }`，算两遍几何（草稿 createMyDrag.resolve 里就是这样；工作台把这个状态存成 `rejected` ref 和 `overRejected` 变量）。库里 `layoutDropOverPanel` 与 `resolveLayoutDrop` 内部各自重新找一遍面板。

## api-13

### 13. 小处的形状问题：`TabRef` 的身份不含 `type`、`TabRef` 把“标签”分成叫 `view` 与 `tab` 的两种、`DropFeedbackPreview.entryRect` 是必填的活动栏概念

严重程度：建议；类别：代码质量 / API 形状（类型与命名）
位置：packages/nb-layout/src/layout-doc.ts:25-27（TabRef）、:111（tabKey）；src/vue/DropFeedbackOverlay.vue:17-28（DropFeedbackPreview）

现象：
1. `TabRef = {kind:"view"; viewId} | {kind:"tab"; type; tabId}`，身份键是 `tabKey`：`view:${viewId}` 或 `tab:${tabId}`——**不含 `type`**。已跑实验（reports/api-exp-tabkey.ts，bun run 可复现）：`{type:"markdown", tabId:"1"}` 与 `{type:"image", tabId:"1"}` 的 key 都是 `tab:1`，同放进一块面板，`validateLayoutDoc` 返回 `标签重复：tab:1`；`findTab(doc, "tab:1")` 只找到第一个。`type` 在库里只是原样带着的字符串（grep 没有任何分支读它），可 `tabId` 在不同 `type` 间必须全局唯一没有写在 `TabRef` 的注释里，也不在类型上。第三方多种标签（文本、图片）自然会各自从 1 数起，这时第一次有两个标签同 id，才在存盘读回时被 validate 拒绝，运行时 `insertTab` 已经按 key 拒绝（`标签已存在 tab:1`）。
2. “标签”这个词有两个意思：`PanelRecord.tabs` 里装的元素叫 `TabRef`，其 `kind` 却分 `"view"` 与 `"tab"`；`kind:"tab"` 的是“编辑器的标签”。读者看到 `findTab(doc, "view:files")` 返回 `TabRef`，而 `kind:"tab"` 的又是 `TabRef` 的一种，容易混。命名上 `view`/`tab` 应是“工具视图”/“编辑器文档”这样的一对（工作台 Spec 里是这么叫的）。
3. `DropFeedbackPreview` 的 `entryRect: GridDropRect | null` 是必填字段（草稿第一次编译就因漏它报 TS2769，修成 `entryRect: null` 才过；reports/check/ 里有编译记录）。它是“活动栏切换器上接收条目”的概念，通用的第三方没有，却要在每次构造 preview 时写 `entryRect: null`；`armed`、`labelAt` 都是可选的，只有它漏了 `?`。

为什么是问题：1 是“按字符串键存、两个字段当一个键用”的老问题，类型上防不住；2、3 是读起来和用起来的小摩擦，累积起来让 API 显得是为一个应用定制的。

如何核实：bun run reports/api-exp-tabkey.ts；vue-tsc 编译 reports/check/draft.ts（去掉 `entryRect: null` 即复现 TS2769）。

建议改法：
1. 把 `type` 并进身份：`tabKey` 返回 `tab:${type}:${tabId}`（需要迁移已存盘的文档，工作台里 `EDITOR_TAB_TYPE` 是常量，可以在读的时候补）；或者把 `type` 从 `TabRef` 里去掉，由 `tabId` 全局唯一，并在 `TabRef` 注释写明。两者选一，不要保持“有 type 却不参与身份”。
2. 改名建议：`kind: "view" | "document"`（要跨包改，先在注释里标明意思，改名放到有大改时一起做）。
3. `entryRect` 改成可选（`entryRect?: … | null`）。


## api-14

### 14. 对照业界布局库的 API 形状：可借鉴三点（提交前的统一拦截点、一个实例持有文档与事件、通用 grid 与应用外壳分层）

严重程度：建议；类别：代码质量 / API 形状（借鉴）
说明：这一条的资料没有联网核对。WebSearch 报模型不可用，Bash 的 curl 需要审批，我没有绕。下面的描述来自我对这些库公开文档与源码的记忆，链接是它们的官方位置，没有逐条核对到具体版本，写进设计前请主 Agent 打开链接确认。

对照与可借鉴：
1. FlexLayout（https://github.com/caplin/FlexLayout ，README 的 “Layout”、`onAction`、`onAllowDrop` 部分）：模型 `Model.fromJson(json)`，所有改动都是 `Actions.*` 对象经 `model.doAction(action)`；`<Layout onAction={(action) => action | undefined}>` 是所有提交的统一拦截点，返回 undefined 就否决。
   对照本库：api-02（`edgeTarget`、`seamAccepts` 提交时不守）和 api-03（命令、快捷键绕过判定）说的是同一个洞。借鉴：给文档层一个唯一的提交入口（`commit(op)`），策略在这里统一验，判定函数只负责“画什么”。
2. dockview（https://dockview.dev/docs ，API 一节的 `createDockview`、`api.addPanel`、`toJSON`/`fromJSON`、`onDidLayoutChange`、`onWillDrop`）：一个实例对象持有布局状态，`addPanel({id, component, position: {referencePanel, direction}})` 一次调用表达“放在谁的哪一边”，`toJSON`/`fromJSON` 是实例的方法，布局变化是事件。
   对照本库：状态在宿主的 `shallowRef`、操作是自由函数、写回要宿主手动 `rebaseIntents`（api-03）、变更通知要宿主自己 `persist`（草稿的 `apply`）。借鉴：提供一个可选的 `createLayoutController({doc, policy, projectionOptions})`，内部持有 doc、投影与呈现尺寸，暴露 `apply(op)`、`commitGesture(...)`、`onChange`，宿主不再写 api-03 里的 20 行与 `rebased()`。`openPanelAtEdge` 的 `LayoutEdgeTarget`（between/split/spread 三种）对第三方过细，可以提供 `{reference, direction}` 的简化入口，在内部映射。
3. VS Code 的 grid 与 splitview（https://github.com/microsoft/vscode/blob/main/src/vs/base/browser/ui/grid/grid.ts ，`Grid`、`SerializableGrid`、`IView`；同目录 `gridview.ts`、`splitview.ts`）：`base/browser/ui/grid` 只有视图尺寸与方向，不认识活动栏、侧栏；工作台的区域、活动栏、状态栏在 `workbench/browser/layout.ts`。`SerializableGrid.deserialize(json, deserializer)` 的反序列化回调把“序列化数据里的视图引用”换成对象。
   对照本库：这正是 api-01 的建议：把 `createGrid`（通用）和 `layout-doc`（工作台）按层分开发布。VS Code 的 `deserializer` 回调与本库 `GridRefResolver`/`encodeRef` 是同一个思路，已经有了，不用改。
4. golden-layout（https://golden-layout.com/docs/ ，`LayoutConfig`、`registerComponentFactoryFunction`、`loadLayout`、`saveLayout`）：配置是纯 JSON，组件靠名字注册，存取是实例的两个方法。借鉴点同 2：存与读各一个方法，读失败的类型是一个。

不借鉴：dockview 与 FlexLayout 把“标签拖动”整个做进库里（含落点判定、反馈），第三方基本零接线；本库把判定做成纯函数、反馈做成组件，自由度高但接线多（api-04）。这是方向选择，不是错误；若目标用户包含第三方，应该提供一个“默认拖动控制器”，高级用户再拆开。

建议改法：见每点；优先级：2（控制器）> 1（统一提交入口）> 3（分层，已在 api-01）。

const BASE = {width: 1440, height: 900};

/**
 * [别扭 1][缺 A] 没有构造器，手写整棵树。必须有 activitybar 与 statusbar 两片叶（validateLayoutDoc 要求恰各一个），
 * 第三方没有这两样，只好放进去再用 hiddenBars 藏起来；叶的 `ref` 必须是 `panelRef(id)`、条的必须是 `barRef(..)`，写错 validate 才报。
 * 具名面板只能叫 sidebar/auxiliarybar/panel；树里至少一个 role 为 editor 的面板。

function initialDoc(): LayoutDoc {
    const leaf = (id: string, size: GridExtent) => ({kind: "leaf" as const, id, ref: panelRef(id), size});
    return {
        version: 1,
        tree: {
            version: GRID_SNAPSHOT_VERSION,
            root: {kind: "branch", id: "root", orientation: "vertical", size: BASE, children: [
                {kind: "branch", id: "body", orientation: "horizontal", size: {width: 1440, height: 900}, children: [
                    {kind: "leaf", id: "activitybar", ref: barRef("activitybar"), size: {width: 0, height: 900}},
                    leaf("sidebar", {width: 280, height: 900}),
                    {kind: "branch", id: "center", orientation: "vertical", size: {width: 1160, height: 900}, children: [
                        leaf("e1", {width: 1160, height: 600}),
                        leaf("panel", {width: 1160, height: 300}),
                    ]},
                ]},
                {kind: "leaf", id: "statusbar", ref: barRef("statusbar"), size: {width: 1440, height: 0}},
            ]},
        },
        panels: {
            sidebar: {role: "tool", name: "sidebar", tabs: [{kind: "view", viewId: "files"}], active: "view:files"},
            e1: {role: "editor", tabs: [{kind: "tab", type: "my.editor", tabId: "a.txt"}, {kind: "tab", type: "my.editor", tabId: "b.txt"}], active: "tab:a.txt"},
            panel: {role: "tool", name: "panel", tabs: [{kind: "view", viewId: "terminal"}], active: "view:terminal"},
        },
        floats: [],
        hiddenBars: ["activitybar", "statusbar"],
        currentEditor: "e1",

/** [别扭 6] newId 要“保证唯一”：载入文档后计数器要接着最大的往下数，否则 moveTabToEdge 会静默覆盖一块面板（api-06）。 */
let serial = 0;
const policy: LayoutPolicy = {

    accepts: (tabs, target, region) => region === "edge" || tabs.every((tab) => (tab.kind === "view" ? target.role === "tool" : target.role === "editor")),

/** [别扭 8] 必须 shallowRef：用 ref() 时所有操作抛 DataCloneError（api-08）；类型上看不出来。 */
const doc = shallowRef<LayoutDoc>(initialDoc());

const presented = shallowRef<Readonly<Record<string, GridExtent>>>({});

/** 放不下时先收走哪些面板：宿主给顺序与焦点（工作台的 collapseOrder 在 layout-doc-store 里，草稿给个空顺序）。 */

/**
 * [别扭 3][缺 B] 结构操作之前，先把呈现尺寸写回意图（rebaseIntents）。四个参数里三个来自 projection。漏了不报错，拆分比例按旧意图分。
 */
const rebased = (): LayoutDoc => rebaseIntents(doc.value, presented.value, projection.value.collapsedTo, fixedNodesOf(projection.value.input));

const STORAGE_KEY = "my-app.layout";
function persist(): void {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(doc.value));
}

/** 所有改文档的入口：先 rebase，再操作，成功才写入并存盘。 */
function apply(operation: (current: LayoutDoc) => LayoutResult): LayoutResult {
    const base = rebased();
    const result = operation(base);
    if (!result.ok) return result; // [别扭 5] 失败只有 code 三选一与中文 detail
    if (result.doc === base) return {ok: true, doc: doc.value};
    doc.value = result.doc;
    persist();
    return result;
}

/** [缺 B] 手势落账：工作台 layout-doc-store.ts:420-440 的 20 行，逐字抄；漏任何一步都是静默写坏意图（api-03）。 */
function commitGesture(sizes: Readonly<Record<string, GridExtent>>, collapsed: Readonly<Record<string, boolean>>): void {
    const near = (left: GridExtent | undefined, right: GridExtent | undefined): boolean => left !== undefined && right !== undefined && Math.abs(left.width - right.width) < 0.5 && Math.abs(left.height - right.height) < 0.5;
    const frozen = new Set([...fixedNodesOf(projection.value.input)].filter((id) => near(presented.value[id], sizes[id])));
    presented.value = sizes;
    let next = doc.value;
    for (const [id, value] of Object.entries(collapsed)) {
        const anchor = projection.value.regionAnchors.get(id); // 不用容器的文档里恒为空，但这一步还是要写
        const updated = setPanelCollapsed(next, anchor ?? id, value);
        if (updated.ok) next = updated.doc;
        if (anchor === undefined || value || next.panels[anchor]?.hidden !== true) continue;
        const shown = setPanelHidden(next, anchor, false);
        if (shown.ok) next = shown.doc;
    }
    doc.value = rebaseIntents(next, sizes, projection.value.collapsedTo, frozen);
    persist();
}

/** 读回：校验失败时宿主自己决定怎么办；校验只管形状，骨架（fitsSkeleton）这类应用规则要自己再写一层（api-01）。 */
function load(): void {
    const raw = localStorage.getItem(STORAGE_KEY);
    if (raw === null) return;
    const checked = validateLayoutDoc(JSON.parse(raw) as unknown);
    if (checked.ok) doc.value = checked.doc;
    else console.warn(checked.code, checked.detail); // 中文 detail，没有可程序化区分的子码
}

// ── 6. 拖动：标签在面板之间、拖到边缘拆出新块 ───────────────────────────────────────────────

const rectOf = (element: Element | null): GridDropRect | null => {
    if (element === null) return null;
    const {left, top, right, bottom} = element.getBoundingClientRect();
    return right > left && bottom > top ? {left, top, right, bottom} : null;
};

/**
 * [缺 C] 把自己的 DOM 量成库要的几何。`data-leaf` 是 NestedGrid 的外框标记（NestedGrid.md 公开表里有），`data-my-head` 是草稿自己的头。
 * 整块、标签条、正文的拆分，工作台还要处理拖到零的（量不到矩形）、离开中的（data-leaving）叶、编辑组头里的提示条（layout-drag.ts:371-382），草稿略。
 */
function measurePanels(root: HTMLElement, current: LayoutDoc): LayoutDropPanelGeometry[] {
    return treeLeaves(current.tree.root).flatMap((leaf) => {
        if (current.panels[leaf.id] === undefined) return [];
        const card = rectOf(root.querySelector(`[data-leaf="${CSS.escape(leaf.id)}"]`));
        const strip = rectOf(root.querySelector(`[data-my-head="${CSS.escape(leaf.id)}"]`));
        if (card === null) return [];
        return [{id: leaf.id, frame: card, body: strip === null ? card : {...card, top: strip.bottom}, strip}];
    });
}

export function createMyDrag(root: HTMLElement): DragSession<LayoutSource, LayoutDropAction> {
    const input = (source: LayoutSource, point: {x: number; y: number}): LayoutDropInput => ({doc: doc.value, source, point, panels: measurePanels(root, doc.value), policy});
    return createDragSession<LayoutSource, LayoutDropAction>({
        root,
        // 起拖：TabStrip 写的 data-panel-tab 就是 tabKey；`data-no-drag`（关闭按钮）是工作台的约定，草稿没有这样的按钮。
        sourceAt: (target) => {
            const key = target.closest<HTMLElement>("[data-panel-tab]")?.dataset.panelTab;
            return key === undefined ? null : {kind: "tab", tab: key};
        },
        // [别扭 10] resolveLayoutDrop 对“指针在面板外”和“指针在面板上但被拒绝”都返回 null，区分要再调 layoutDropOverPanel（api-10）。
        resolve: ({source, point}) => {
            const query = input(source, point);
            const action = resolveLayoutDrop(query);
            if (action === null && layoutDropOverPanel(query)) return null; // 被拒绝：宿主要自己记一个 rejected 状态才能给光标
            return action;
        },
        actionKey: layoutDropKey,
        commit: (action, source) => void apply((current) => applyLayoutDrop(current, source, action, policy)),
        structure: () => JSON.stringify(projection.value.input), // 一场里结构变了整场取消；用什么当“结构键”要自己想
    });
}

/** 落点预览：只有“边缘拆分”有真实矩形（previewEdgeDrop）；标签条的插入线要用 TabStrip 的 measureTabStrip/resolveTabStripInsertion 另算（草稿略）。 */
export function edgePreview(source: LayoutSource, action: Extract<LayoutDropAction, {kind: "edge"}>, origin: {x: number; y: number}): GridDropRect | null {
    if (extent.value === null) return null;
    const rect = previewEdgeDrop(doc.value, source, action, policy, {...projectionOptions(), removed: collapse.value.removed}, extent.value, window.devicePixelRatio);
    // 相对网格根的矩形，要自己加上网格根的视口坐标才能交给 DropFeedbackOverlay（视口坐标）。
    return rect === null ? null : {left: rect.left + origin.x, top: rect.top + origin.y, right: rect.right + origin.x, bottom: rect.bottom + origin.y};
}

export const DragLayer = defineComponent({
    name: "MyDragLayer",
    props: {root: {type: Object as () => HTMLElement | null, default: null}},
    setup(props) {
        const session = shallowRef<DragSession<LayoutSource, LayoutDropAction> | null>(null);
        // [别扭 11] createDragSession 要求创建时就给 root：onMounted 建、onBeforeUnmount 销毁、state 要再取一层（t06 第 6 条仍在）
        onMounted(() => {

        };
    },
});

const doc = docOf(H(["activitybar", "sidebar", V(["e1", "panel"]), "statusbar"]));

    walk(input);
    console.log(label, "→ 呈现树的叶:", leaves.join(", "));
};
show("原样           ", doc);
const hidden = setPanelHidden(doc, "sidebar", true);
const collapsed = setPanelCollapsed(doc, "sidebar", true);

if (collapsed.ok) show("setPanelCollapsed", collapsed.doc);
