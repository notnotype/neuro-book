## design-03

### 3. `useSashGesture` 换根元素时 `detach()` 摘的是新元素，旧元素上的监听与登记没摘；注释写的“先摘旧的”做不到

严重程度：建议；类别：不变量
位置：packages/nb-layout/src/vue/useSashGesture.ts:582-588（`watch(options.root, …)`）、557-580（`detach`）

现象：
- 注释与模块头都写“换元素先摘旧的（重挂不留下重复监听）”“根元素换掉即注销，因此重挂不会留下重复监听或幽灵命中”。
- 实际是 `watch(options.root, (element) => { detach(); if (element !== null && !disposed) attach(); })`。回调触发时 `options.root.value` 已经是新元素，`detach()` 里 `const root = options.root.value` 取到的就是新元素：`removeEventListener` 对新元素做（本来就没装），`scopeEntries.delete(root)` 删的也是新元素；旧元素上的 7 个监听与 `scopeEntries` 登记都留着。根变成 `null`（卸载）时 `detach()` 里 `root === null`，整段摘除被跳过，只靠旧元素随 DOM 一起被回收。
- 目前 NestedGrid 与 Splitter 的 `rootEl` 在组件寿命内是同一个元素，所以没有可见后果；`src/vue/*.dom.test.ts` 里没有换根元素的用例（`rg "换元素|重挂" src/vue/*.test.ts` 只有等值发布与 drop-targets 的两处，都不是这个函数）。

为什么是问题：合同写在头注释里，调用方（以后的第三个宿主）按它放心换根；实际换根后旧元素如果还留在 DOM（例如 `v-if`/`key` 换壳但旧节点被缓存复用），会出现两个 scope 都在响应同一批指针事件，并且 `winningScope` 沿 `composedPath` 找到旧元素上残留的 `entry`，旧元素的 `entry.blocked()` 在组件没销毁时为 false，会替已经换掉的根仲裁。注释说的保证没有机制，也没有测试。

如何核实：Vitest 里挂一个 `useSashGesture` 的宿主组件，`root` 先指向元素 A、再改成 B，对 A 派发 `pointerdown`，看 `begin` 是否仍被调用；或在 `detach()` 前打印 `options.root.value === 旧元素`。

建议改法：`watch(options.root, (element, previous) => { detach(previous); … })`，`detach` 接受要摘的元素参数；`dispose` 与 `onBeforeUnmount` 里传当前元素。补一个换根的用例。顺手一并处理：这个 composable 直接用全局 `window`、`document`、`requestAnimationFrame`（行 201、379、552-553），而 `drag-session.ts` 用 `root.ownerDocument.defaultView`；Lab 或嵌入文档里用后者才对。两个手势层沿用不同的取窗口方式，同一包里不一致。


## design-04

### 4. “条的叶 id 等于条名”“面板 id 不会是 `activitybar`”两个假设整个工作台都在用，`validateLayoutDoc` 与 `fitsSkeleton` 都不查

严重程度：建议；类别：不变量
位置：packages/nb-layout/src/layout-doc.ts:1312-1326（条的叶只验 `ref`）、packages/neuro-book/src/plugins/workbench/web/state/default-tree.ts:147（`isBar` 只比 `barOfRef(node.ref)`）；依赖这个假设的地方：components/WorkbenchSurface.vue:16-20、367、`node.id === STATUS_BAR`、layout-drag.ts:391（`[data-leaf='statusbar']`、`[data-shell-card='activitybar']`）、layout-drag.ts:154（`BAR_REGION = BAR_STRIP = "activitybar"`，entry-drop.ts:14 的注释“面板 id 是随机串或名字，撞不上”）

现象：
- 条在树里是 `{kind:"leaf", id:"activitybar", ref:"bar:activitybar"}`（`default-tree.ts:95、103`）。画条的地方一律按 **叶 id** 判：Surface 里 `node.id === STATUS_BAR` 才进状态栏插槽，`ACTIVITY_BAR` 才画活动栏，`PLAIN`、`BARS`（最大化的 `exclude`）、`layoutCardEdges({activitybar: ACTIVITY_BAR})`、拖动里排除区 `[data-leaf='statusbar']`、`[data-shell-card='activitybar']` 都是。
- 校验只管 `ref`：panel 叶要求 `panelId === leaf.id`（行 1323），条的叶却只要 `ref` 对（行 1317-1320 `continue`），`fitsFrame` 的 `isBar` 也只比 `ref`。所以 `{id:"x", ref:"bar:activitybar"}` 通过两道关；再配一个 id 为 `"activitybar"` 的 panel 叶（`ref:"panel:activitybar"`，`validateLayoutDoc` 对面板 id 只拒 `__proto__` 等三个）也通过。
- 这两种文档画出来：第一种没有活动栏插槽（叶 id 不是 `activitybar`，走 panel 分支，`roleOf` 为 null，卡片空着）；第二种把一块普通面板画成活动栏。`BAR_STRIP`（拖动的“标签条 id”与键盘区域 id）和面板 id 共用一个命名空间，注释里写的“撞不上”靠的是“没人会取这个名字”。

为什么是问题：`validateLayoutDoc` 的注释写“形状的唯一权威（读记录时调）”，记录来自磁盘、别的窗口、模板；一个类型对、骨架对、却画不出条的文档不会触发回落默认树，用户会得到一个没有活动栏的工作台并且“保存”也不会纠正。现在没有路径能产生这种文档（`default-tree` 与 `apply` 都不会），所以只是校验没守住自己写给下游的假设。

如何核实：`validateLayoutDoc` 喂一份把默认树里活动栏叶的 `id` 改成 `"bar-a"` 的文档，返回 `ok: true`，`fitsSkeleton` 也返回 true；浏览器里把用户记录（`LAYOUT_DOC_RECORDS`）里这个 id 改掉后重载，看活动栏（从代码推断，没有在浏览器里看）。

建议改法：校验里对条的叶加 `leaf.id === bar`（和 panel 叶同一行规则，一行代码）；`BAR_STRIP` 的“撞不上”改成校验里拒掉 id 为 `activitybar`、`statusbar` 的 panel 叶（同一处）。不需要再加机制。


## design-05

### 5. “隐藏的区域按拖到零画”靠同一个类型的文档改写实现：记录的文档与呈现的文档不可区分，同一个判定函数在两份上答案相反，选错编译不报

严重程度：建议（代价，不是对决策的质疑）；类别：代码质量
位置：packages/nb-layout/src/layout-doc.ts:259（`hiddenRegionsAtZero`）、234（`isPanelShown`）、288（`sectionCollapseBlock` 里的条件改写）；调用方：packages/nb-layout/src/layout-project.ts:110、packages/neuro-book/src/plugins/workbench/web/state/layout-present.ts:52、packages/neuro-book/src/plugins/workbench/web/components/WorkbenchSurface.vue:173

现象：
- 开发者 2026-11-15 的决定是“隐藏的区域按拖到零画”。实现是 `hiddenRegionsAtZero(doc): LayoutDoc`：把隐藏的锚改写成 `{...anchor, hidden 去掉, collapsed: true}`，返回的仍是 `LayoutDoc`。
- `isPanelShown(doc, id)` 的注释写“面板看不看得见只有这一个判定，别处不直接读 `hidden`”。但它在两份文档上答案相反：在记录的文档上，隐藏区域的分节是 `false`；在 `hiddenRegionsAtZero` 的结果上是 `true`（锚没有 `hidden` 了）。两种答案各有用处，调用方必须自己选对哪份文档：
  - 用记录：`regionOccupied`、`presentationCollapse` 的 `shown`（`layout-project.ts:189`）、Shell 里焦点回收（`WorkbenchShell.vue:445`）、`measureGeometry`（拖动落点，不落到零宽面板上）。
  - 用呈现：`projectLayoutDoc`（`layout-project.ts:110、148`）、`effectiveVisibleTabs`（`layout-present.ts:52`）、`WorkbenchSurface.sceneCorners`（`WorkbenchSurface.vue:173`）；`sectionCollapseBlock` 在 `layout-doc.ts:288` 里临时改写再问。
- 一共 5 处各自调 `hiddenRegionsAtZero`；`WorkbenchSurface.vue:173` 的调用写在 `flatMap` 回调里，每个区域各改写一次（2 次），不是 bug，说明调用方没有“拿到呈现文档”的单一入口。

为什么是问题：把“记录”与“呈现”两个事实做成同一个类型，等于靠每个调用点的注释自觉。新写一个看“这块面板显示吗”的功能（比如键盘落点、状态栏计数），拿 `store.doc` 还是拿改写后的文档，类型检查不报，行为只在“区域隐藏着”这一种状态下才分叉，所以最容易漏测。`WorkbenchSurface.vue:173` 的 `isPanelShown(presented, id)` 与 `WorkbenchShell.vue:445` 的 `isPanelShown(next, panel)` 同名同形、答案相反，读者只能靠上下文猜。

如何核实：`rg "hiddenRegionsAtZero|isPanelShown" packages --glob '!*.test.ts'` 数调用点；在一个侧栏隐藏的文档上分别对记录与 `hiddenRegionsAtZero(记录)` 调 `isPanelShown(…, 侧栏分节)`，得到 false 与 true。

建议改法：最少的改法是把改写结果做成名义类型，例如 `type PresentedDoc = LayoutDoc & {readonly [presented]: true}`，`hiddenRegionsAtZero` 返回它；`projectLayoutDoc`、`effectiveVisibleTabs` 这类只该吃呈现文档的函数参数写 `PresentedDoc`，`isPanelShown` 拆成两个名字（`isPanelShown` 只收记录，呈现里问的叫 `isPanelDrawn`）。不改行为，不加运行时机制，类型检查就能挡住拿错的那一种。store 再提供一个 `presentedDoc` 计算属性，Surface 与 `layout-present` 都从它取，改写只在一处做。


## design-06

### 6. 每个 NestedGrid 有两份设备像素比来源、两份窗口 resize 监听；分隔线对齐监听整页的捕获阶段 scroll

严重程度：建议；类别：代码质量（兼性能，从代码推断）
位置：packages/nb-layout/src/vue/NestedGrid.vue:112、114；packages/nb-layout/src/vue/useSashSnap.ts:34-36、57-60；packages/nb-layout/src/vue/useDevicePixelRatio.ts:25-33

现象：
- `NestedGrid.vue:112` 自己调 `useDevicePixelRatio()`（给 `placeGrid`、内容层、过渡用）；`NestedGrid.vue:114` 的 `useSashSnap()` 里又调一次（`useSashSnap.ts:35`），给分隔线对齐用。每次调用各挂一个 `window` 的 `resize` 监听与一个 `matchMedia("(resolution: …dppx)")` 的 `change` 监听。`useSashSnap.ts:34` 的注释写“设备像素比只有一个来源”，实际一个网格有两个，彼此独立更新：缩放变化时 `treePlacement` 按第一个 ref 重算，`snap(dpr.value)` 读第二个 ref，两份值在同一个事件里分别被改，中间的一次渲染里两者可以不一致。
- `useSashSnap.ts:59`：`window.addEventListener("scroll", schedule, {capture: true, passive: true})`，整页任何滚动容器滚动都排一帧，这一帧对该网格名下全部分隔线跑对齐函数（读 `getBoundingClientRect`，见文件头注释）。注释给的理由是“滚动改变接缝在视口里的位置”，但网格根是 `overflow: clip`、高度固定（`NestedGrid.vue` 样式），分隔线的视口位置只会被它的祖先滚动改变；编辑器正文、聊天记录、文件树这些在网格内容里的滚动不会移动任何分隔线，却同样触发。工作台一个页面一般有 1 个主网格加几个嵌套的，每个各挂一份。
- 同类的“每个实例各挂全局监听”：`useSashGesture.ts:552-553` 每个实例挂 `window` 的 `blur` 与 `document` 的 `keydown`（捕获）。

为什么是问题：
- 两份 dpr 是一个明确的违反自己注释的重复；而且“值不一致的一拍”是 dpr 这类取整依赖的典型来源（分隔线按 dpr 取整对齐，位置按另一个 dpr 取整摆放，发丝缝）。
- 滚动监听的理由不成立：不是本网格祖先的滚动不需要重新对齐。一次滚动手势 60 帧、主网格 N 条分隔线（默认树约 5 条，拖出几个分组后可到十几条）就是 60×N 次读几何；每次滚动编辑器、聊天记录都付这笔钱，换不到任何东西。

如何核实：
- 浏览器里：Performance 录制时滚动编辑器正文，看每帧是否有 `useSashSnap` 的 rAF 回调与 `getBoundingClientRect`；或在 `schedule` 里加计数器（本地临时，不提交）。
- 代码里：`rg "useDevicePixelRatio" packages/nb-layout/src/vue` 看到 NestedGrid、useSashSnap 各一次（Splitter 同理）。

建议改法：
- `useSashSnap` 接受外部传入的 `dpr` ref（`useSashSnap(dpr)`），NestedGrid 把自己那份传进去，删掉内部的第二个来源；`useDevicePixelRatio` 就剩一个调用方。
- scroll 监听改为只监听网格根的祖先滚动容器，或者去掉监听、改成在 `ResizeObserver`/`IntersectionObserver` 触发的 `schedule` 里就够（接缝位置改变要么是网格尺寸变，要么是祖先位移）。去掉前先确认当初加它的失败用例（`git log -S"scroll" -- packages/nb-ui/src/composables/useSashGesture.ts`）。
