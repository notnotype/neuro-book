### 1. 过渡、停放、焦点、提交保持的行为在 nb-layout 里没有任何单元测试，只有另一个包的 e2e 兜底
**严重程度**：重要
**类别**：测试能否支撑重构
**位置**：src/vue/useGridMotion.ts、useLeafParking.ts、grid-focus.ts（moveTab、noteFocus、moveGridFocus）、NestedGrid.vue 的 publishedMatches 与提交后保持预览；对照 NestedGrid.dom.test.ts、grid-rects.test.ts
**现象**：本轮新增的行为面里，只有 grid-rects.ts 的纯函数有测试（grid-rects.test.ts 325 行）。NestedGrid.dom.test.ts 改完后只有“按矩形摆放”“分界线手势”“命中映射”“预览布局”四类，没有一条覆盖 data-moving、growing、parked/inert、aria-owns、Tab 接管、moveGridFocus、“宿主接纳了这次调整但没有发布匹配布局”的诊断分支。这些只在 packages/neuro-book/e2e/lab-grid-structure.e2e.ts（12 条，要真实浏览器与 Lab 构建）里有。useGridMotion 的 update 是一个五个输入的判定（first、resized、rescaled、gesture、previous 为空、placementMoved），最近一次提交就是“按实现审查修过渡判定”，它没有用手动时钟的直接用例，计时 MOTION_SLACK_MS 与 nextTick 强制布局也没有。grep packages/nb-layout 与 packages/neuro-book 的 *.test.ts，没有一个测试引用 useGridMotion、useLeafParking、moveGridFocus。
**为什么是问题**：改过渡判定、停放条件或焦点走法的人，改完 bun run test 与 vitest 全绿，要到 e2e 才知道坏没坏；而 e2e 在 neuro-book 包里，是“被依赖方的行为只由使用方的场景验收”，改 nb-layout 内部结构（例如把 useGridMotion 拆开）时没有就近的回归网。验收场景 9 里“程序开关一块、过渡中内容尺寸不变、ResizeObserver 只报一次”这类要真实布局，确实只能 e2e；但判定逻辑本身（该不该过渡）不需要布局。
**建议改法**：不增加新部件，把判定从 DOM 里拿出来再测：useGridMotion.update 的“要不要过渡”部分是 (frame, 上次的 rootSize/extent/dpr, fromGesture) 的纯函数，放进 grid-rects.ts 旁边或 useGridMotion.ts 里导出一个 decideMotion，用 bun/vitest 直接表驱动测（首次、resize 两个来源晚一拍、dpr 变、手势、无变化、有变化）。useLeafParking.update 本来就是不碰 DOM 的，直接用 vitest 测（曾有尺寸现在是零、第一帧未量到、预览中不停放、预览中从零拉出来解除）。moveTab 的“要不要接管”分支（defaultPrevented、isComposing、keyCode 229、修饰键）用 happy-dom 的 KeyboardEvent 可以测，tabbable 在 happy-dom 里要传 displayCheck:"none"，如果做不到就在 grid-focus.ts 里把 focusablesIn 设成可注入的依赖，不然这块永远只能 e2e。publishedMatches 是纯函数，移到 grid-gesture.ts 与 GridGestureCommit 放一起并测。grid-rects.test.ts 第 39 行把 key 的字符串格式 'sash:["a","b"]' 写进了断言，这是内部身份的编码；要保留的行为是“结构变了线的身份跟着前后节点走”，断言改成“同一对前后节点在两次摆放里 key 相等、不同的对不相等”，改编码不会误报。

### 2. 宿主要靠两个没写进公开面的 DOM 属性才能接 NestedGrid
**严重程度**：重要
**类别**：API 形状 / 隐含合同
**位置**：src/vue/NestedGrid.vue:353（data-grid-scope）、:364（data-leaf-content）；宿主 packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:303、WorkbenchShellLayout.vue:242、:317、:351-358；文档 src/vue/NestedGrid.md、docs/specs/ui/nested-grid.md
**现象**：grep "data-grid-scope" 在 NestedGrid.md、Spec、grid.md 里都没有，只在 grid-focus.ts、NestedGrid.vue 和宿主代码、e2e 里出现。宿主实际在用：(a) WorkbenchShell 里 moveGridFocus(document.activeElement) 返回 false 时，自己 querySelector("[data-grid-scope]") 再调一次，才能“焦点在页面根时从第一块开始”；(b) WorkbenchShellLayout 用 [data-leaf-content="<part>"] 找 Teleport 目标，用 [data-grid-scope] 取 grid 根的矩形算预备区；(c) 紧凑模式下 WorkbenchShellLayout.vue:351-358 手写了六处 data-leaf + data-leaf-content 的 div，是在模仿 NestedGrid 的 DOM 形状，让同一套 Teleport 与 e2e 选择器继续成立。data-leaf-content 在 NestedGrid.md 第 11 行与第 91 行有写，data-grid-scope 没有。
**为什么是问题**：这两个属性是“组件不 expose API”之外的实际公开面：重命名它们会同时坏外壳、紧凑模式的手写副本、Lab、e2e，而文档上看不出它们是合同。紧凑模式的手写副本更危险：NestedGrid 改外框结构（比如给内容容器加一层）时，这份副本不会跟着改，两边悄悄分叉。
**建议改法**：二选一，都不加新部件。(1) 在 NestedGrid.md 的“布局”里把 data-grid-scope（grid 根，值是实例 id）、data-leaf、data-leaf-content 写成公开合同并说明改它要同步宿主；(2) moveGridFocus 直接接受容器：from 不在任何 grid 里时在 from 内找第一个 [data-grid-scope] 开始，宿主那行兜底的 querySelector 就删掉，F6 命令一次调用完成。紧凑模式的手写副本在 WorkbenchShellLayout.md 里注明“与 NestedGrid 的 data-leaf 形状同步”，或让紧凑模式也走 NestedGrid（单列树），这是另一个任务，不在本轮改。

### 3. “这次几何变化来自手势”是跨文件的一次性旗标，靠 watcher 创建顺序成立
**严重程度**：重要
**类别**：隐含的先后与共享状态
**位置**：NestedGrid.vue:187-195（watch(placement)）、:233-238（releasePreview）、:244（onPreview）、:340 附近的 watch(props.layout, releasePreview)；useGridMotion.ts:46-47、:65、:100-103（fromGesture、markGesture）
**现象**：判断“这次变化不过渡”靠 releasePreview/onPreview 调 motion.markGesture() 把 useGridMotion 里的 let fromGesture 置 true，由 watch(placement) 里的 motion.update 读一次并清零。成立的前提有三条，都只存在于注释或创建顺序里：(a) watch(placement) 必须在 watch(props.layout, releasePreview) 之前建（NestedGrid.vue:186 的注释专门写了这一条）；(b) 置位之后必须恰好有一次 placement 重算来消费，否则旗标留到下一次程序触发的变化，把该有的过渡吞掉；(c) 置位发生在 preview 改变之前，消费发生在 flush 里。改这段的人要同时读 NestedGrid.vue 三处、useGridMotion.ts 两处，才知道旗标不会漏。
**为什么是问题**：这是本轮最难读的一块，也是 AGENTS.md 说“先试着改结构消除它”的那种。而且信息本来就在手里：watch(placement) 回调里已经读了 preview.value !== null，缺的只是“上一次是不是在预览中”。
**建议改法**（从代码推断，未实现验证）：删掉 markGesture 与 fromGesture，让 useGridMotion.update 的入参多一个 previewing: boolean，useGridMotion 自己记 wasPreviewing；手势引起的变化就是 previewing || wasPreviewing。覆盖的情形：拖动开始与进行中（previewing 为真）、松手或取消或被拒后撤预览（wasPreviewing 为真，预览撤掉的那一次重算）、预览保持期间宿主发布布局（placement 不依赖 props.layout，不重算）。这样“来源”变成输入数据，watcher 的创建顺序不再是合同，NestedGrid 里的两个 markGesture 调用和那段顺序注释都可以删，useGridMotion 也少一个对外方法。parking.update(items, previewing) 已经是这个形状，两者统一。

### 4. renderItems 是带副作用的 computed，三个闭包变量是隐藏状态
**严重程度**：建议
**类别**：隐含共享状态
**位置**：NestedGrid.vue:96-110（renderedKeys、domIds、nextDomId、renderItems、domIdOf）
**现象**：renderItems 是 computed，却在里面改外部变量：renderedKeys = stableOrder(renderedKeys, ...) 把结果存回闭包，并且 domIds.delete(...) 清理。domIdOf 在模板与 sashProps 里被调用，每次可能往 Map 里写入。outOfOrder、ariaOwns、focusScope.items 又读它们。注释里说明了为什么不能放进 watch（外壳的 Teleport 要同一轮渲染里拿到新叶外框），这一点是对的，但“computed 必须幂等”这条 Vue 约定被打破，没有写明它为什么在这里是安全的（computed 只在依赖变化时执行一次，并且 renderedKeys 的更新是单调的）。
**为什么是问题**：以后有人在 computed 之外再读一次 renderedKeys，或让 computed 因额外依赖多执行，就会让 stableOrder 的“上一轮”漂移。这块逻辑 40 行、有三个状态、和手势无关，却占着 NestedGrid 的 script。
**建议改法**：抽成 useRenderOrder(items) 返回 {items, outOfOrder, domIdOf}（和 useLeafParking 同一种形状：一个小闭包加一个 update），内部注释一次说明“必须同步算、必须每轮只算一次”。NestedGrid 里减少约 40 行，三个闭包变量不再暴露给读者。

### 10. 设备像素比有两个来源，窗口监听各装一份
**严重程度**：建议
**类别**：重复 / 共享状态
**位置**：useDevicePixelRatio.ts（ref + window resize + matchMedia）、useSashSnap.ts:41（rAF 里直接读 window.devicePixelRatio）与 :57-58（又一份 resize、scroll 监听）
**现象**：NestedGrid 的摆放用响应式的 dpr，SashHandle 的对齐用 useSashSnap 在帧里读的 window.devicePixelRatio，两者平时相等；dpr 变化时靠 watch(placement) 里的 snapHost.schedule() 让后者跟上，这条依赖没有写在任何一边的注释里。一个 NestedGrid 会装两个 window resize 监听加一个 scroll 捕获监听，加一个 matchMedia 监听；Splitter 一份。
**为什么是问题**：以后有人把 placement 的触发条件改了（比如摆放不再随 dpr 重算），分隔线的对齐会在“拖到另一块显示器”时静默不更新。
**建议改法**：useSashSnap 内部直接用 useDevicePixelRatio()，在 dpr 变化时 schedule()，帧里用它的值，不读 window。useGridMotion 里的“rescaled”也从这里取，不再各自读。这样 dpr 是一个来源，监听少一份。
