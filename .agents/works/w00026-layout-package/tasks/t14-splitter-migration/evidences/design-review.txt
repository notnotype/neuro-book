### 1. 开发者面板的构建输入与“代码已更新”提示只认 nb-ui，迁移后 nb-layout 的改动不会触发重建
**严重程度**：重要　**类别**：遗漏
**位置**：`packages/dev-panel/src/server/build.ts:34-40`；`packages/dev-panel/src/server/state.ts:50`；`packages/dev-panel/docs/panel.md:381`；plan.md 没有提到
**现象**：`computeBuildHash` 的输入写死为面板的 `src/web`、nb-ui 整个包目录、`vite.config.ts`、`tsconfig.web.json`、`package.json` 和根 `bun.lock`。`CODE_PATHS = ["packages/dev-panel", "packages/nb-ui", "bun.lock"]` 与它一致，用来判断“代码已更新”。面板网页除 nb-ui 外没有别的工作区源码依赖，nb-layout 是第一个。迁移后 `dist/web` 里编进了 `packages/nb-layout/src/**`，但它不在这两处。第一次合入会因为 `package.json` 与 `bun.lock` 变了而重建一次。之后 nb-layout 的任何改动（w00026 里它改得最密）都不改 `.build-hash`，`panel serve` 不重建，“代码已更新”横幅也不出。
**为什么是问题**：面板是开发者每天用的工具，用旧前端不会有任何提示。nb-layout 的分栏修复，正是 t14 要让面板吃到的，送不到面板。nb-story 没有这个问题，因为 `web-stamp.ts` 按打包时见到的实际模块 id 记，路径含工作区其它包。这是面板独有的硬编码清单。
**如何核实**：读上述三处；`rg -n "packages/nb-ui" packages/dev-panel/src/server`。`tests/panel-server.test.ts:756` 用 `computeBuildHash` 造哈希，加路径不会破坏它，因为 `walk` 对不存在的目录直接返回。
**建议改法**：第 1 片把 `packages/nb-layout` 同时加进 `computeBuildHash`（整棵走，跳过 `node_modules`）和 `CODE_PATHS`。同步改 `build.ts:10-11` 的注释和 `panel.md:381` 的输入清单。补一条断言：改 nb-layout 里一个文件，哈希和 `readCodeKey` 都变，可加在 `panel-server.test.ts` 的夹具里。

验收表里把 `release:smoke` 那一行收窄为“发布”，分栏照旧那一行改写为靠这三条探针与既有 e2e。

### 7. nb-layout 变成 nb-story 发布产物的构建输入，但不在发布门禁盯的目录里
**严重程度**：建议　**类别**：边界（部分是已有做法）
**位置**：`scripts/release/packages.ts:46-49`；`scripts/release/pack-smoke.ts:425-428`；`scripts/release/publish.ts:115-116`；plan.md:24-34、56-60
**现象**：`prepack` 把 nb-layout 的源码编进 nb-story 的 `dist/web`（发布内容）。`releaseDirectories()` 只含 `RELEASE_PACKAGES` 的目录、应用包的源码目录与根 `LICENSE`，不含 `packages/nb-layout`。冒烟与发布的“没有未提交的改动、没有未跟踪的文件”门禁，以及“冒烟以来改过的文件”判断，都靠它。nb-layout 里有未提交的改动时，冒烟照样通过，打出的 nb-story 却“对不上任何提交”，`pack-smoke.ts:428` 要避免的正是这个。应用包 `packages/neuro-book` 早就把 nb-layout 编进去了，所以这是已有的缺口，t14 把它扩到 nb-story。

**为什么是问题**：不影响这次迁移是否正确，但“打出来的包对应某个提交”的门禁多了一个盲区，而 nb-layout 是改得最勤的包。
**如何核实**：读上述三处，对照 `RELEASE_PACKAGES`。
**建议改法**：不必在 t14 修。在汇报或待确认清单里记一句“发布门禁没覆盖 nb-layout，应用包同样，第二档发布 nb-layout 时一并处理”。或者把 `releaseDirectories()` 加上“发布产物的构建输入包”一类（`private` 的 nb-layout、nb-workbench-layout）。

## 未发现问题的方面
- **发布前提成立**：
  - `packages.ts:177-179` 允许 devDependencies 引用不在清单里的工作区包，`neuro-book-test-support` 已是 `workspace:*` 的先例。
  - `files` 排除 `src/web`，`undeclaredImports` 只扫发布文件，`pack-smoke.ts:34` 的 FORBIDDEN 也含 `^package/src/web/`。
  - 发出去的 nb-story 里 `src` 其余部分不导入 nb-layout，`dist/web` 是打包产物，没有运行时还要解析 nb-layout 的地方。
- **两份 Splitter 的公开面一致**：props、事件载荷（对比 `splitter-gesture.ts`、`splitter-session.ts` 的 diff，只有类型名与诊断形状不同）、插槽都一致。三处使用方没传 `branchId`、`sashLineEnds`、`restoreToShare`，也没用旧类型名（grep）。
- **`global.css` 对宿主**：只写 `--nb-layout-motion-*`（减少动效时归零）与 `.nb-layout-focus-ring`，宿主没有同名选择器。与 nb-ui `tokens.css:332-340` 归零 `--motion-move` 一致，`BookFrame.motionMs()` 读旧名结果相同。
- **scoped 样式与 Tailwind 分层**：宿主在 Splitter 上只传 `h-full`、`min-h-0 flex-1`，与 scoped 的 `width/height: 100%` 同值或不冲突。nb-ui 旧 Splitter 的 `<style>` 是 scoped，不会渗进 nb-layout 的元素。
- **同一页面两份**：迁移后两个宿主只有 nb-layout 一份。nb-ui、nb-agent-ui、nb-markdown、nb-form 都不导入 nb-layout，不会出现两份 nb-layout 的模块级注册表（`NestedGrid.md:210` 提醒的那个）。nb-ui 的 Splitter 只在 nb-ui 自己的 playground、e2e 与旧应用里用。
- **`test:affected`**：`scripts/ci/workspace-graph.ts` 把 devDependencies 也算依赖，nb-layout 改动会带出 nb-story 与 dev-panel 的测试。
- **nb-story 的“网页比源码旧”提示**：`web-stamp.ts` 按实际模块 id 记，nb-layout 的改动能被发现。
- **类型**：dev-panel 的 `lib` 是 ES2022，nb-layout 是 ESNext，grep 没找到 ES2023 及以后的 API。vue-tsc 没能运行，未验证。
- **体积**：`@notnotype/nb-layout/vue` 入口会带进整套 Vue 层与 `global.css`，nb-layout 没有声明 `sideEffects`，能否摇树我没验证（`vite build` 被拒）。计划已把这条列为风险并安排量产物，不重复。
