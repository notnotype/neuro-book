G0 【阻断】【不变量/并发】`editor.tabs` 记录一旦进入 failed/unknown，session 里的 watch、布局保存关卡、`record.retry()` 组成无间隔的重试死循环（连接断开时就能触发），实测不加上限时 1.5 秒计时器都不触发（整个事件循环被饿死）
位置：editor/web/session.ts 100-102 行（`watch(() => store.state.record.save.state, ... options.panels.flush())`）；editor/web/tabs-record.ts saveBeforeLayout（74-77 行 `if (paused()) await record.retry()`）；workbench/web/plugin.ts `flush: () => void layout.current.value?.actions.save()`；workbench/web/state/layout-doc-store.ts save（126-129 行）；shared/store/persisted.ts #send 先把 `save` 置为 `{state:"saving"}` 再置回 `failed`（348 行）
现象：循环是这样转的。
 1. 记录写失败，`record.save.state` 变 failed 或 unknown。
 2. session 的 watch 看到 failed/unknown，调 `panels.flush()`，即布局的 `save()`。
 3. `save()` 走关卡 `saveBeforeLayout`：`paused()` 为真，于是 `await record.retry()`。
 4. `retry` 重发，`#send` 把 state 置为 "saving"，再次失败后置回 "failed"。state 的值从 "saving" 变成 "failed" 是一次变化，watch 又触发。回到第 2 步。
 没有退避、没有“已经在重试”的判断，只要失败持续就一直转。
 实验（/tmp/review-w00026-t07-7b/exp/loop.test.ts，真实 Storage 测试场地，真实 editorTabsStore；watch 与 flush 按 session.ts 与 plugin.ts 的接线写，关卡直接调 saveBeforeLayout）：
 a) 连接断开（`WorldWindow.disconnect()`）后保存一份合法快照：state 变 unknown，随后 watch→flush→关卡→retry 反复。我在 flush 里加了 300 次上限，1.76 秒内 attempts=301、flushes=301，上限一去掉就停不下来。
 b) 不加上限：`bun test` 在 120 秒超时前没有输出，连 `setTimeout(…,1500)` 都没触发，说明循环全在微任务里，主线程被占满。
 c) 另一种永久失败（写入内容不过校验）同样 attempts=301。
 测试场地用的是与产品相同的远程层（createRemoteNode、链路对），断线后 Storage 调用立刻以失败返回（实验 a），所以我判断真实页面也会卡死；产品里 WebSocket 断线的行为我没有在浏览器里验证，请主 Agent 用 e2e 或手工断网确认。永久失败（实验 c）与连接无关，一定触发。真实页面会卡死：UI 不响应，WebSocket 重连需要的宏任务也跑不到，等于连接恢复不了。触发条件很宽：连接断开期间任意一次属性保存（光标停下 1 秒、固定）或布局保存（开关标签、聚焦换组，7b 起聚焦换组也写布局）。服务端重启、网络抖动都算。
为什么是问题：7b 之前布局记录与会话记录互不挂钩，会话记录写失败只是暂停，等拥有者重试。现在新加的“失败要亮出来：让布局走一次关卡”把“亮出来”实现成了自动重试，而重试本身又产生同一个失败信号。注释写的是“失败要亮出来，状态栏才显示‘布局未保存’和重试”，需要的是一次保存失败的通知，不是循环。
如何核实：运行 /tmp/review-w00026-t07-7b/exp/loop.test.ts（有上限版本，约 2 秒）；e2e 里让 Storage 断线后在编辑器里改一次光标，观察页面是否仍响应。可在 tabs-record.test.ts 增一条：失败后 flush 次数有界（例如失败一次只触发一次布局保存）。
建议改法：关卡里不要自动重试，只在用户点“重试”时重试。具体：a) saveBeforeLayout 在 paused() 时直接返回 false（不 `record.retry()`）；重试动作单独走 layout-doc-store.retry → 它先 `recover` editor.tabs（reopen 加 retry，顺带解决 G2）再 `save()`。b) session 的 watch 只在“从未失败到失败”时 flush，且布局已经 saveBlocked 时不再 flush（例如加一个“已通知”标志，retry 成功后复位）。a 与 b 都做更稳。

G1 【重要】【不变量/正确性】放弃（discard）把布局文档回滚到已确认值，但编辑器的标签属性、文档引用、视图绑定不跟着回滚：文档里的标签没有属性，组里出现“活动标签不在标签列表里”的幽灵状态
位置：workbench/web/state/layout-doc-store.ts discard（304-308 行 `local.value = readStored()`）；editor/web/groups/groups.ts 的 groups computed（约 187-196 行 `attributes.value.get(id) ?? []`）与 attributes 只在建立时恢复（185 行）
现象：布局保存失败（或 editor.tabs 写不下去使关卡返回假）时状态栏给“放弃”（WorkbenchShell.vue 461 行 `@discard="layout.actions.discard()"`）。discard 把整份布局文档换回上次确认的版本。7b 之前布局文档只有尺寸、摆放，回滚无害；7b 起文档里还有“有哪些编辑器标签、哪个活动”，而这些标签的属性（地址、编辑器、光标）、文档引用（references）、视图绑定、未保存正文在编辑器区里，不会回滚。
 实验（/tmp/review-w00026-t07-7b/exp/discard.test.ts，createMemoryEditorPanels + createEditorGroups，把文档换回旧值，与 discard 对文档做的事相同）：
 a) 放弃后文档里没有、属性里仍有的标签 b：组里看不到它（文档说了算），属性表与 snapshot() 里还留着它，下一次关卡把它写进 editor.tabs，成为没有主的记录项。
 b) 放弃前关掉的标签 a：文档回滚后仍列着 a，属性已忘掉它。实测 groups 为 `{tabs: 0 个, active: "t-…"}`：组里标签条空、活动标签 id 指向一个不存在的标签；这个标签没有任何入口能关（close 要先 locate，locate 只看 groups，groups 滤掉了它），也不会被占位（占位只在 restoreTabs 建立时做一次）。
 c) 未绑定项目的窗口同样走 discard：`local.value = readStored()` 把内存里所有打开的编辑器标签从文档里抹掉（未绑定窗口的已确认文档没有动态标签），而它们的 references、绑定和未保存正文还在 area 里。needsLeaveConfirm 遍历的是 references（area.ts 962-969 行），所以离开页面时仍会警告“有未保存的修改”，但用户已经没有任何标签可以打开、保存或放弃那份正文，只能整页离开丢掉（从代码推断，未跑）。
为什么是问题：Spec ui/workbench-layout.md“失败与恢复”写“放弃回到已确认值”指布局；输出 33 又把标签顺序、活动标签放进这份文档，两边靠 tabId 对上。回滚只回一边，对不上之后没有任何收敛路径。这是 7b 才有的回归（旧会话记录是编辑器自己的，放弃只影响布局）。触发要先有保存失败，所以概率低，后果是标签卡死与可能丢未保存正文，按重要记。
如何核实：运行上面的实验；真实运行时 e2e：让布局记录写失败（Storage 注入失败）、开一个标签、点状态栏放弃，读 `[data-editor-tab]` 与 `data-editor-notice`。
建议改法：二选一。a) 放弃只回滚“与编辑器无关”的部分：discard 时把已确认文档里的编辑器标签换成当前文档里的（编辑组结构与标签以当前为准），或 discard 在有编辑器会话时让编辑器区重新对账（对账：文档里有而属性没有的补占位，属性有而文档没有的丢并释放引用）。b) 把 groups 的 attributes 对账做成对文档变化的响应（watch 文档里的标签集合），而不是只在建立时做一次 restoreTabs；这同时覆盖别的“文档被外部整份换掉”的路径。

G2 【建议】【不变量】`editor.tabs` 的记录读取失败、打开失败或订阅结束后，布局的保存关卡永远过不去：重试不会 `reopen` 这条记录
位置：editor/web/tabs-record.ts saveBeforeLayout（74-77 行）；workbench/web/state/layout-doc-store.ts retry（296-302 行）
现象：布局字段自己的重试写了 `if (field.failure !== null) await field.reopen()`（layout-doc-store.ts 297 行），editor.tabs 记录没有对应的一步。persisted.ts 里 `#retry` 在 `#failure !== null` 时直接返回 `head.state`（persisted.ts 约 413 行 `if (this.#base.value === null || this.#failure.value !== null) return head.state;`），failure 只有两种方式清掉：`reopen`，或（仅 read 类）下一个正常快照。open 失败与 ended（订阅结束）两类只能靠 reopen。
 流程：editor.tabs 打开失败（或订阅中途结束）→ 编辑器区仍然建起（settled 里把 failure 也算已定，所有标签变占位）→ 任一次布局保存走关卡 → write 里 commit 排队即暂停，result 为 "failed" → saveBlocked=true，状态栏“布局未保存”→ 用户点重试 → layout-doc-store.retry → `field.retry()`（布局字段没有待重试的，返回 nothing）→ `save()` → 关卡 → paused() 为真 → `record.retry()` 返回 head.state（没有 reopen）→ 仍 paused → 返回 false。如此循环，直到刷新页面。期间所有布局改动（尺寸、摆放、拆分、移动）都不落盘。
为什么是问题：7b 之前布局记录与会话记录互不挂钩，会话记录读不出来只影响会话；现在一条记录的瞬时失败（Storage 服务断开、打开超时）会把布局的保存整个卡死，并且重试按钮看上去能用而实际永远不可能成功。Spec“失败与恢复”：“`editor.tabs` 保存失败同样显示”，并且“重试”应当能重试。
如何核实：从代码推断，未复现。我试过 Storage 测试场地的断线再重连（/tmp/review-w00026-t07-7b/exp/recover.test.ts）：断开时 `failure` 仍为 null、只有 save 状态 failed，重连后 saveBeforeLayout 第一次重试就成功，所以这条路径不触发本条；只有 `failure` 非空（打开失败、订阅结束、读取错误）才触发，场地里没找到注入办法。降为建议：触发窄，刷新页面可恢复，但重试按钮在这种状态下永远无效。可用 Storage 的测试世界让 `open(EDITOR_TABS_RECORD)` 第一次返回失败再恢复来复现。可在 tabs-record.test.ts 增一条：打开失败后恢复，`saveBeforeLayout` 应当在 reopen 之后返回 true。
建议改法：saveBeforeLayout 里 `if (record.failure !== null) await record.reopen()` 再 `record.retry()`，与布局字段同写法；或把“重新打开并重试”提成 store 的 `recover()` 动作，两处共用。

G3 【建议】【不变量】关闭标签时 `editor.tabs` 比布局早写约 150 毫秒以上：此间刷新或崩溃，重开后已关的标签显示成“记录丢了”的占位

G4 【建议】【正确性/数据】布局文档或其读取被保护（损坏、版本不支持、读取失败）时，`editor.tabs` 里打开时读到的旧项仍会在第一次保存时被清掉，布局原件保留、标签属性却没了
位置：editor/web/tabs-record.ts 51-54 行（`known` = 读到的全部键）、57-65 行（`removed`）；editor/web/session.ts 82-100 行；workbench/web/state/layout-doc-store.ts guarded（70 行）、readStored
现象：布局记录损坏或版本不支持时 store 回落默认树（`local = null`），原件不覆盖。编辑器此时从“没有任何标签”的文档起步：restoreTabs 不恢复任何属性，`known` 里却有记录里的所有键。用户随手开一个文件，属性变化触发 `write`，`removed` = known 里的全部旧键，`editor.tabs` 被整份清掉，布局原件仍留在盘上。之后用户（或新版本）把布局修好，标签全是“记录丢了”。Spec“失败与恢复”要求“原件保留”，这里只保了一条。
为什么是问题：两条记录的保护应当一致：一条被保护另一条就不该照常删。典型触发是同一个状态目录被两个版本的程序读写（开发时 master 与分支并存、升级后回退），不是纯理论。
如何核实：从代码推断。可在 session 测试里：布局记录放一份 version 不支持的值、`editor.tabs` 放几个标签，开一个文件，读 `editor.tabs`。
建议改法：布局被保护（store 的 `problems` 含 unread，或 `guarded`）时，编辑器区建好后 `known` 置空（不清别人的也不清旧的）；或 EditorPanelsService 加一个只读的 `protected` 状态，write 看到它时不带 removed。

G5 【建议】【对照需求/正确性】键盘拖动：关掉多行（`wrapTabs` 为假）且标签条横向滚动时，滚出视口的标签也被列为落点，停靠点落在标签条之外，实际解析成别的落点

建议改法：编辑组按树序加序号（“编辑器 1”“编辑器 2”）或用它活动标签的文件名；同一次列表里有重名时才加序号也行。
