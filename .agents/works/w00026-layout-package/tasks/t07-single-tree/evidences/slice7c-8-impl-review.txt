F1  重要 / 正确性  收起的具名面板被挨着开新面板后变零宽
==============================================================
位置：
  packages/nb-layout/src/layout-doc.ts:523-545（moveTabToEdge）、placeLeaf（约 432-485）
  packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts moveView 的 newPanelNextTo 分支
  packages/neuro-book/src/plugins/workbench/web/state/layout-present.ts moveTargetsOf 的 beside
现象：
  面板（底部 panel）处于 collapsed:true（收成标题行，它的父分支是纵向的 center）。对任意视图执行“移动到 -> 新面板（挨着面板）”
  （右键菜单、命令 nbook.view.move 带 newPanelNextTo，或键盘拖放到它的左右边候选），新面板放在它右边，它自己变成横向分支
  H[panel, 新面板] 的成员，但 collapsed 仍为 true。layout-project.ts:72 的 collapsedSize 按父分支方向取值，横向是 0，所以
  panel 变成零宽、里面的视图全部不可见；此时它的“收起”按钮又因为 collapsible 判据（父分支纵向）被隐藏，用户没有按钮可以展开。
为什么是问题：
  计划“片 7c”的设计审查第 5 条（收起的面板跨方向变零宽）只处理了“被移动的那块面板”（movePanelToEdge 清 collapsed）；
  同一个问题的另一半，“作为锚点被拆出横向兄弟的那块面板”没处理。moveTargetsOf 的 beside 只排除隐藏的面板，收起的面板仍被列出。
  骨架检查（fitsSkeleton）看不到这类问题，性质测试也只验证 fitsSkeleton 和校验，所以 20 个种子 x 60 步抓不到。
如何核实（已跑，/tmp/review-w00026-t07-impl/exp1.ts，bun run 即可）：
  defaultLayoutDoc(catalog) -> setPanelCollapsed(doc,"panel",true) -> layoutEdgeTarget(doc,[],"panel","right") 得到
  {kind:"split",panel:"panel",edge:"right"} -> moveTabToEdge(view:h, 该目标) 返回 ok、fitsSkeleton 为 true，
  结果里 panel 的父分支 orientation 是 horizontal，panels.panel.collapsed 仍是 true。
建议改法：
  最小：moveTabToEdge / openPanelAtEdge / placeLeaf 在锚点的父分支方向因此改变时清掉锚点的 collapsed（和 movePanelToEdge 对被移动面板
  做的一样）；或 moveView / 键盘候选对 collapsed 的锚点先展开。并在 default-tree.test.ts 的性质测试里加一条“收起的工具面板的呈现尺寸
  不为零（父分支为横向时 collapsed 为假）”的不变量。

F1 补充（同一根因的另一条路径，从代码推断，未跑）：
  侧栏这一列 V[sidebar, x]，x 是无名面板且 collapsed:true（标题行）。隐藏侧栏后，呈现树里 sidebar 不在，单子分支塌陷（layout-project.ts
  project() 先塌陷、后 assignByParent），x 直接成了 body 的横向子节点，collapsedSize 变 0，x 的视图跟着看不见。活动栏的条目点一下还能
  把它展开（revealView 对无名面板清 collapsed），所以能找回，严重程度低于上面那条；根因都是“collapsed 的含义取决于呈现里的父分支方向，
  而文档操作只在移动被拖的面板时清它”。

F4  建议 / 正确性  headReserved 仍按三个框架按钮算，收起按钮只给上下排之后多留了 26px
==============================================================
位置：packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:131-137（headReserved），对照 :189-200（frameActionsOf 的 collapsible）
现象：frameActionsOf 现在只在父分支纵向时给“收起”按钮。默认树里侧栏、右栏单独在 body 的横向分支里，它们的框架按钮是 2 个（最大化、隐藏），
  面板行里的无名面板只有 1 个；headReserved 仍是 `panel?.name === undefined ? 2 : 3`，具名面板一律按 3 个留。buttonBudget 每格 26px
  （title-actions.ts BUTTON_PX+GAP_PX），所以默认的侧栏头和右栏头少放一个视图动作按钮（放进“⋯”）。
为什么是问题：宽度账和真实按钮数不一致；Spec 输出 20 里写的“默认宽度的侧栏里资源管理器的五个动作只露三个”是按 3 个框架按钮量出来的，现在这个数字
  的前提已变。影响小（少一个按钮落进“⋯”），但是改收起按钮那一刻就该一起改的账。
如何核实：算术即可：reserved = 96 + 28*(tabs-1 或 0) + 26*frames + 20；frames 差 1 就差一格。e2e 可在默认 1440 宽读侧栏头里 data-title-action 的个数与 3 个框架按钮时对比。
建议改法：frames 取 frameActionsOf(panelId).length（或抽出同一个 collapsible 判据），不要两处各写一遍。

F5  建议 / 交互  从活动栏条目拿起后，第一个方向键跳进侧栏面板的落点，不是相邻条目
==============================================================
位置：packages/neuro-book/src/plugins/workbench/web/layout-drag.ts:384-390（keyboard.start）、:372-378（regions）
现象：start() 的起始区域取“来源所在面板”的下标（findIndex(candidate.id === home)），起点坐标却取条目中心。侧栏显示着、视图在侧栏里时，
  区域表是 [活动栏, 侧栏, …]，起始区域是下标 1（侧栏），不是下标 0（活动栏）。拿起时 session 把 cursor.stop 置 -1、point 置条目中心，所以直接 Enter 是原位（对）；
  但第一下方向键由 stops(侧栏区域) 决定：光标跳到侧栏的第一个候选（标题上的“添加为标签”或上下边），而不是活动栏里相邻的条目。要在活动栏里用键盘换序，
  得先按 Shift+Tab 回到区域 0。侧栏隐藏时 home 不在区域表里，findIndex 为 -1，Math.max 取 0，反而正好落在活动栏。两种情形行为不一致。
为什么是问题：Spec 输出 31 说“拿起时停在原位”，输出 22 说活动栏条目是拖动源并且活动栏上段是落点；从条目拿起、在条目之间换序是最直接的键盘用法，
  现在要多一步。e2e（workbench-dnd 895 行）只测了“从右栏的标签拿起，Tab 绕到活动栏”和“从条目拿起直接 Enter”，没有“从条目拿起、方向键换序”这一例，所以没被抓到。
  （从代码推断，未跑 e2e。）
如何核实：读 packages/nb-layout/src/drag-gesture.ts 的 startKeyboard 与 key()：at 为坐标时 cursor.stop = -1，方向键走 cursor.region 的 stops。
建议改法：origin 是 [data-tool-entry] 时 start 返回 BAR_REGION 的下标；补一条 e2e：条目拿起 -> ArrowDown -> Enter，顺序变了且活动标签不变。

F1 再补（实验数字，/tmp/review-w00026-t07-impl/exp2.ts）：
  按产品里能做的操作随机跑：拖动候选（enumerateDropCandidates）、只对纵向父分支的工具面板收起/展开（收起按钮的规则）、“移到新面板”。200 个种子、
  共 11047 个有效步骤，59 个状态出现“工具面板 collapsed 为真且父分支横向”（呈现里零宽）。最先出现的路径比 F1 主文更常见：

  的横向分支，collapsed 仍为真，整列变零宽（seed 2 第 5 步）。用户做的是“收起一块”和“拖走另一块的视图”两个各自合理的操作，结果是一整列消失，
  而且这时收起按钮也看不到了。性质测试（default-tree.test.ts 的“从默认树出发”）只断言 fitsSkeleton 与 validateLayoutDoc，没有这条不变量。

  这比在 movePanelToEdge、moveTabToEdge、openPanelAtEdge、settleEmptyPanel 各处分别清更不容易漏，也能一次盖住 F1 的两条路径。

1. dropAt 在活动栏上跳过预览缓存与 previewsOf/actionKey 的关系：barDrop 在 previews 与 previewsOf 检查之前返回，不读不写缓存；离开活动栏后下一次

   保存覆盖记录，行为与 Spec 输出 20 验收一致。usableDoc 对记录与模板一视同仁。
5. 旧键不读不写不删：records.ts 不再定义，store 不碰；单元用例用同键同分区的 defineRecord 验证了原样保留。仓库内没有别的代码再引用这三个键。
