[1] 重要 | 合同 / 不变量 | 骨架靠“调用方遵守”，库和 store 的出口没有闸门

位置
  packages/nb-layout/src/layout-doc.ts:482-489（edgeAnchorOf）、491-510（movePanelToEdge）、512-529（moveTabToEdge）、531-541（openPanelAtEdge）
  packages/neuro-book/src/plugins/workbench/shared/editor-panels.ts:85-95（moveToEdge 接收原始 LayoutEdgeTarget）
  packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts:160-173（apply）
  plan.md 片 7c “不变量”一段

现象
  计划说“任何操作之后树都合骨架”，靠 layoutEdgeTarget（落点只给合骨架的目标）和“具名面板不整块移动”两件事。但这两件事都发生在“生成目标”的一侧；所有写结构的入口在提交时
  都不验目标本身：
  - moveTabToEdge / movePanelToEdge 提交时只问 policy.accepts(tabs, anchor, "edge")，anchor 是 edgeAnchorOf 取的“目标 before 那块的第一片叶”。accepts 又被计划改成“只看角色相配”。
    between 目标的 after 一侧、split 的边方向、between 的 branch 是否是“同一列/同一排”，都没人验。
  - movePanelToEdge 没有任何具名面板的拦截（计划只是让 moveTabToEdge 不再调它）。
  - EditorPanels.tabs.moveToEdge(tabId, target) 是公开服务方法，直接把调用方给的 target 交给 moveTabToEdge。
  - 唯一的全局检查是计划里的“性质测试”：只枚举 enumerateDropCandidates 的候选，所以走不到命令入口（moveView、resetView、moveToEdge、openAtEdge）和伪造目标。

如何核实
  /tmp/review-w00026-t07-7c/exp/forged.ts（用按计划改好的 moveTabToEdge 副本 + 计划里的 accepts 角色规则，从默认树出发，bun forged.ts）：
  a. 编辑器标签 + 伪造 between(center, auxiliarybar)：accepts 通过（anchor 是编辑组），结果 body 变成 H[活动栏, 侧栏, V[g0,面板], 新编辑组, 右栏]，编辑组夹在中间列和右栏之间，走出骨架。
  b. 工具视图 + 伪造 between(sidebar, center) 或 split(sidebar, right)：anchor 是 sidebar，通过，新工具面板夹在侧栏和编辑区之间，走出骨架。
  c. movePanelToEdge(sidebar → auxiliarybar 上缘 / panel 右缘)：成功，具名面板被整块移走（计划说“具名面板不会被移走”，库里没有这条约束）。
  对照：同一个脚本里按计划的 layoutEdgeTarget 钩子生成目标的随机游走（exp/walk.ts，300 个种子、36000 步，含边缘拖放、标签条、隐藏/收起、moveView 新面板、插入视图）0 次走出骨架。
  所以“生成侧”的设计是对的，缺的是“提交侧”。

为什么是问题
  - 骨架是整个 7c 的核心不变量，现在它的成立依赖每个调用方都经过钩子。t09（浮动窗停靠）计划里明说要用 movePanelToEdge/movePanelToStrip，到时具名面板和骨架没有任何东西挡着。
  - 公开服务 moveToEdge 的 target 是原始数据，任何拿到 editorPanelsKey 的代码都能构造。
  - Spec 输出 26 写“接受矩阵在提交时再验一次”，计划里“提交时再验”只剩 accepts 的第一片叶。

建议
  1. 在 layout-doc-store.ts 的 apply 出口加一道 fitsSkeleton(result.doc) 闸：不合骨架返回 {ok:false, code:"rejected"}，文档不变（O(节点数)，节点上限 256）。fitsSkeleton 本来就要写，复用它。nb-layout 不知道骨架，放在宿主即可。
  2. nb-layout 侧补两处：edgeAnchorOf 对 between 要验 before 与 after 两侧子树的全部叶（accepts 逐叶）；movePanelToEdge 前加 policy 钩子（例如 policy.movable?(panel)）或直接拒绝具名面板。
  3. 性质测试再加三类序列：命令入口（moveView 两种目标、resetView、openAtEdge、moveToEdge 伪造目标）、显隐/收起/stripDynamicTabs/carryDynamicTabs 穿插、从旧版本留下的文档开始。我的游走脚本可以直接改成测试。

[2] 重要 | 合同 / 验收 | 活动栏换序、键盘“拿起直接 Enter”、预备区落在自己所在面板，都会改活动标签

位置
  packages/nb-layout/src/layout-doc.ts:364-383（moveTabToStrip 缺省 activate:true）
  packages/neuro-book/src/plugins/workbench/web/layout-drag.ts:190-213（dropAt 用 result.doc === doc 判原位）、327-333（start）
  packages/nb-layout/src/layout-drop.ts:167-185（isInPlace 只比位置，不比活动标签）、layout-doc.ts:571-580（showPanelAndInsert 同面板时把标签挪到末尾）
  plan.md “活动栏落点：目标……否则 strip”；spec 输出 22 “在这一列里换序不改显隐”，验收 9 “拿起后直接 Enter 不移动”，验收 14 “拖条目换序，Then 顺序变了，显隐不变”

现象
  活动栏条目对应的标签多数不是侧栏当前的活动标签（侧栏这一列只显示一个视图）。barDrop 给出的是 strip(panel, index)，提交走 moveTabToStrip，缺省会把被拖标签设为活动标签。
  - 在同一面板里拖一个非活动条目换序（或原位放下），侧栏当前显示的视图换成它。这就是“显隐”的改变（侧栏的内容变了，条目按下态也变了），不是 spec 说的“显隐不变”。
  - 键盘：拿起一个非活动条目后直接 Enter。dropAt 的原位判定是 result.doc === doc，而 moveTabToStrip 因为 active 变了返回新对象，所以不算原位，Enter 提交了一次“激活”，违反验收 9。
  - 预备区/reveal：隐藏的侧栏里的条目拖到侧栏自己的预备区（或 barDrop 的 reveal 分支，“来源不在同一面板”才走，但预备区没有这个条件），showPanelAndInsert 先显示再 moveTabToStrip(index = 末尾)：把这个标签挪到末尾并激活。旧外壳输出 20 写的是“容器本来就在这个 Part（侧栏拖到零时活动栏里的条目）时只选中它”，没有重排。
  标签条上的 isInPlace 候选列表也有同一个洞：isInPlace 认为 index 或 index+1 是原位，但 dropAt 实际按 doc 比，两者不一致。

如何核实
  /tmp/review-w00026-t07-7c/exp/activate.ts：侧栏 [a1, a2]，active=a1。moveTabToStrip(a2, sidebar, index 1 或 2)：返回新对象，active→a2；加 activate:false 才返回原对象。同面板换序默认也会把 a2 设为活动。

为什么是问题
  验收 9、14 的判据在计划的做法下做不到；用户最常见的操作是调活动栏条目顺序，结果是侧栏突然换了内容。VS Code 的活动栏换序不改选中。

建议
  1. barDrop 里来源与目标在同一面板时一律 activate:false（moveTabToStrip 已支持），跨面板才激活。
  2. reveal 带来源已在目标面板时只显示（setPanelHidden false），不重排不激活；showPanelAndInsert 同面板分支单独处理。
  3. 原位判定统一用“applyLayoutDrop 的结果 === 原 doc”，isInPlace 的便宜判定只作剪枝，且要和 activate 语义一致。
  4. 验收 9、14 各补一条：非活动条目原位放下 / 键盘拿起直接 Enter，断言文档对象不变、没有写盘。

[3] 重要 | 遗漏 / 设计未定 | 活动栏落点的位置映射、键盘区域与预览，计划只有一句话

位置
  plan.md “活动栏落点：barDrop(source, point) ……按条目中线算 (panel, index)”、“键盘：活动栏是第一个区域……位置是各条目之间”
  layout-drag.ts:217-256（pointOfCandidate / stopsOf 按面板几何）、:190-213（dropAt）、:102-205（previews 缓存与 previewOf 按 action.kind 分支）、:327-333（start 以来源所在面板为起点）
  WorkbenchToolStrip.vue:57-83（strip 计算：有效可见的总在外面，其余收进“更多”）

现象与缺口
  a. 平铺到面板的映射没有定义。条目是整列所有面板的标签按树序平铺（输出 22），面板之间没有可见分界。指针落在“上一块面板的最后一个条目”和“下一块面板的第一个条目”之间时，(panel, index) 是前者的末尾还是后者的开头？计划没有说。
  b. “条目下面的空白等于最后一个条目之后”。最后一个条目可能属于无名面板（列 V[sidebar, X] 时就是 X 的最后一个视图），于是拖到活动栏空白处进了无名面板，而输出 22/决定表写的是“视图拖到活动栏等于放进侧栏”。这时侧栏如果隐藏着，也不会被显示（目标是 X，不是隐藏面板，走 strip 不走 reveal）。
  c. “更多”折叠让 DOM 里的条目不是树序前缀（有效可见的条目因 priority 排在外面）。例如数据序 [A,B,C,D,E]，E 有效可见：DOM 是 A,B,E 加“更多”按钮。落在 B 与 E 之间是插到 B 后（索引 2）还是 E 前（索引 4）？折叠在“更多”里的条目既不能作为来源也不能作为插入位参照，被它们隔开的位置无法换序。
  d. 键盘：enumerateDropCandidates 是库函数，不认识活动栏的间隙。pointOfCandidate 对 strip/reveal 候选按“该面板的几何”取点，对活动栏候选会取到侧栏头（titleOnly 时 strip 候选被换成 center、stripCount 是 0），或侧栏隐藏时取不到点被 regions 过滤掉。要让“键盘与指针同一套规则”，需要一个 barPositions(doc) -> 有序间隙列表 [(panel,index)]，指针、键盘、预览共用。
  e. start 以来源所在面板为起点区域。从活动栏拿起条目时区域应是活动栏；而 own（条目对应的 data-panel-tab）在 titleOnly 面板里只有活动标签才有，非活动标签退到 origin（条目自己），再叠加问题 2 的 Enter 行为。
  f. 预览：previewOf 按 action.kind 画面板矩形或标签条里的线，barDrop 要画活动栏里的横线，缓存键 JSON.stringify([source, action, extent]) 不带来源（活动栏/面板），同一个 action 从两处进来会拿到对方的预览。目前 titleOnly 把 strip 换成 center，碰巧不冲突，但这是靠换算维持的。
  g. 最大化：revealZones 在 options.maximized() !== null 时返回空，barDrop 没有对应处理。最大化着别的面板时放到活动栏，视图进了被盖住的侧栏（reveal 写入显示了侧栏，但 apply 只在树形状变时退出最大化，这里形状不变），用户看到视图消失。

如何核实
  读代码得出（a、b、c、f、g）；d、e 对照 layout-drag.ts 的 regions/stops/start 实现；e 的 Enter 结果见问题 2 的实验。

建议
  1. plan 里补一节“活动栏位置模型”：barPositions(doc, shownEntryIds)，规定跨面板边界归哪边（建议：归前一块面板的末尾，但目标面板固定取“侧栏这一列里 sidebar，除非来源或落点明确在无名面板条目上”，或者干脆规定活动栏上的任何放下都落进 sidebar，无名面板的视图用标签条之外的办法排序）；列表空白处固定为 sidebar 末尾；折叠条目按数据序参与定位，间隙落在“更多”之前一律映射成数据序最后一个可见条目之后。
  2. 键盘区域、指针命中、预览矩形都从这一个函数取，缓存键加上来源（bar / panel）。
  3. 最大化时 barDrop 返回 null（和 revealZones 一致），或者 reveal 写入同时退出最大化。

[4] 重要 | 兼容与迁移 | “不合骨架回落默认树”漏了新项目模板，且回落没有诊断

位置
  packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts:73-85（readStored）、:123-142（save：每次都 template.commit）、:308-316（discard）
  packages/neuro-book/src/plugins/workbench/web/state/records.ts（workbench.layout-template）
  docs/specs/ui/workbench-layout.md 状态表“记录合法但不合骨架”一行；plan.md “readStored 过了校验还要合骨架，不合按没有记录处理”

现象
  a. readStored 有两个分支：record 为 ok 时读记录，为 missing 时读 template（新项目的初始布局）。计划只说“过了校验还要合骨架”，没说模板那条分支。模板由 save() 每次写入（stripDynamicTabs(current)），7b 时代的构建写下的模板就是不合骨架的（编辑器标签拆在工具面板旁边、具名面板被拖走）。7c 合入后，一个全新项目首次打开读到这份模板，直接成为 local.value，骨架被破坏，而且 layoutEdgeTarget 等所有后续判断都以“树已经合骨架”为前提。模板要等到某个 7c 窗口保存过一次才会被覆盖，新项目窗口先于它打开就中招。
  b. 文字不一致：状态表写“按没有记录处理：默认树”，而“没有记录”一行写“有模板用模板，没有用默认树”。按字面“按没有记录处理”就应该先试模板；计划与 Spec 的意图（只用默认树）不同，实现者会选其一。
  c. 回落时没有任何诊断。这和损坏记录（problems 里有 unread）不同：用户的布局被换成默认树，唯一信号是布局变了。更危险的是 fitsSkeleton 一旦有假阴性（把合法形状判成不合，见问题 6），所有用户的布局会在下一次保存时被静默覆盖，而且不是“原件保留”的 guarded 路径。
  d. 以“形状”而不是版本号做迁移判据，意味着以后每一次扩展骨架（t09 浮动、t13 条移到四边）都要同步改 fitsSkeleton，否则会把新版本合法的文档静默丢掉。

如何核实
  读 layout-doc-store.ts:73-85：missing 分支 validateLayoutDoc(template.display.doc) 之后直接返回；计划没有改它。7b 时代模板的形状可以用 exp/walk.ts 的 naive 模式造出来（5 类走出骨架的树）。

建议
  1. 抽一个 usableDoc(value) = validate && fitsSkeleton，readStored 两个分支都用；template 读到不合时按“没有模板”处理。在 layout-doc-store.test.ts 加一例：记录 missing + 模板不合骨架 -> 默认树。
  2. 回落时给一条诊断（不阻塞，不是 unread）：状态栏/外壳根的 data-layout-diagnostics 里写“布局记录不合骨架，已用默认布局”，e2e 验收 20 顺带断言它。
  3. Spec 状态表和计划统一写成“用默认树，不读模板”或“同没有记录（含模板）”，二选一。
  4. 给文档加一个骨架标记（例如 skeleton: 1，或把 LAYOUT_DOC_VERSION 升到 2 并在 validateLayoutDoc 里把 1 归为“可迁移但不合骨架”），让丢弃是显式的，而不是靠形状。

[5] 重要 | 失败路径 | 收成标题行的面板被整块移到另一个方向后变成零宽，且回来的路不多

位置
  packages/nb-layout/src/layout-doc.ts:491-510（movePanelToEdge 不动 collapsed）、:512-529（moveTabToEdge 单标签无名面板走整块移动）

现象
  collapsed 是面板记录里的一个布尔，呈现时由父分支方向决定是“收成标题行”（纵向）还是“拖到零”（横向）。侧栏这一列的无名面板 X 收起后（框架按钮），把它的标题拖到 panel 的左缘（面板这一排，横向）：片 7c 允许（无名面板整块移动），X 保留 collapsed:true，进入横向分支后宽度为 0，内容停放，视图从活动栏里也没有（它不在侧栏这一列了）。反方向（零宽的行内面板拖不动，因为头也是零宽，但可以通过别的方式让它跨方向，如“移动到”新面板）同理。
  输出 27 只写了“从别的面板放进收成标题行的面板时展开”，没有写来源收起的情况。
  回来的路：行内无名面板没有名字，输出 11 的“显示”（命令 set-part-hidden）和活动栏都不适用；只剩拖那条保留的 1px 边界。用户看到的是“视图拖过去之后消失了”。

如何核实
  /tmp/review-w00026-t07-7c/exp/collapsed.ts：b2 拆成列里的 X，收起，再 moveTabToEdge 到 panel 左缘：结果 X.collapsed=true，父分支 horizontal，树 V[H[活动栏, 侧栏, V[g0, H[X, panel]], 右栏], 状态栏]。

为什么是问题
  片 7c 之后“列 <-> 排”的跨方向移动是主要的整块移动路径（以前侧栏、右栏、面板都能整块拖，方向由名字固定）。

建议
  整块移动（movePanelToEdge 路径）遇到方向变化时清掉 collapsed（和输出 27 对目标的处理对称），并在输出 27 写一句；或者在 layoutEdgeTarget 之外加一个 policy 钩子 onMoved，宿主决定。同时给行内无名面板留一个回来的入口：例如“移动到”菜单对零宽面板仍可用，或不允许无名面板拖到零（只收成标题行 / 最小宽度）。

[6] 建议 | 设计缺口 | fitsSkeleton 的形状计划里没有写出来；validateLayoutDoc 不要求三个具名面板齐全

位置
  plan.md “default-tree.ts: fitsSkeleton(doc)”（只有一个函数名）；docs/specs/ui/workbench-layout.md 输出 1 的一句话
  packages/nb-layout/src/layout-doc.ts:661-720（validateLayoutDoc 只查具名面板“不重复”，不查“齐全”）

内容
  规范形（normalizeTree 同轴展平）之后，合法树的形状是：
    root = V[body, 状态栏]
    body = H[活动栏, S, M, A]，S/A = 单个叶，或 V[叶…]（叶全是工具面板，列里恰好一个 sidebar / auxiliarybar，列内不能再嵌 H）
    M = V[编辑区项…, 行]，至少两个子节点；行 = 单个叶 panel，或 H[叶…]（全是工具面板，恰好一个 panel，行内不能再嵌 V）；
        编辑区项是单个编辑组，或只含编辑组的 H/V 分支。中间列的编辑区可能是 H[…]，也可能是 V 展平后和行同在一个 V 里：V[E, E, 行]。
  我按这个写了一个 fitsSkeleton（exp/lib.ts），用 36000 步随机游走里出现的 700 多种中间列形状验证过，都判为合法；naive 模式（没有钩子）产生的五类越界树都判为不合法。形状规则本身是对的，只是计划没有把它写出来，实现者容易漏：
  - 把 M 当成固定的 V[编辑区, 面板]（漏掉 V[E,E,行] 的展平形和行是 H 的情况），会把合法布局回落成默认树（问题 4 的静默覆盖）；

[9] 建议 | 接口 / 无障碍 | “只有标题的头”（titleOnly）的几个缺口

位置

问题
  a. aria-labelledby 指向的元素 aria-label 是“拖动 X”。aria-labelledby 取的是被引用元素的可访问名称，aria-label 优先于文本内容，所以内容区的名称变成“拖动 资源管理器”。读屏用户听到的是操作而不是内容名。Spec 输出 20 把“可访问名称写明拖动 X”作为要求，两者冲突。做法：labelledby 指向标题里的可见文字 span（带自己的 id），按钮的 aria-label 才写“拖动 X”。
  b. 侧栏这一列没有 tablist 了，内容仍然是 role="tabpanel"（WorkbenchSurface.vue:231）。tabpanel 没有对应的 tab 属于 ARIA 误用；titleOnly 时应该是 region / group。非活动标签的内容节点（停放，inert）的 aria-labelledby 指向不存在的 id（标题只渲染活动标签）。
  c. “点它发 activate（收成标题行时展开）”：host 现在的 @activate 是 layout.actions.activate，只调 activateTab，不碰 collapsed（连现在的标签带点击也不展开，尽管输出 11 写“点标签”）。计划把“展开”写在头组件的描述里，没有写在宿主哪里实现。titleOnly 之后，收成标题行的侧栏列面板能展开的路只剩框架按钮和活动栏。需要在宿主的 activate 里：面板收起则先 setPanelCollapsed false，且点已经是活动标签的标题也要处理（nb-ui 的 Tabs.select 对同值也会 emit，所以事件能到宿主，但 activateTab 对同一个 key 返回原对象，什么都没发生）。
  d. headReserved 按 panel.tabs.length 给图标留宽（TAB_ICON_PX * (n-1)），titleOnly 没有标签带，会少放视图动作按钮。titleOnly 需要走另一个预算。
  e. 去掉头的 touch-action:none 之外还要核对：.workbench-panel-head 的 touch-action/user-select 是为整块拖动写的（注释“面板头的空白处是整块面板的拖动源”），片 7c 不拖了，应该只留给标题 / 标签。

建议
  这几条都小，写进 WorkbenchPanelHead.md 和 WorkbenchShell.md 的改动清单，并在 workbench-shell / workbench-views 各补一个断言（收成标题行点标题展开；侧栏内容区的 accessible name 不含“拖动”）。
