[1] 阻断 | 内容层/裁切 | plan.md「NestedGrid.vue：内容层」第 47-49 行
------------------------------------------------------------------------
现象：计划让内容元素成为叶外框的兄弟（不在外框里），又写“新项跟新叶从边上长出来”“扩展 following、entering 到内容项”，但没有任何一句讲裁切。
现行实现里，“新叶与从零出来的叶内容保持最终尺寸，外框长出来时露出它”完全靠外框 `.nb-grid-frame { overflow: clip }`；“前后都有尺寸的叶内容跟外框”靠内容 `width:100%; height:100%`（NestedGrid.vue:130-134 的 contentStyle，following 命中就写 100%）。内容挪出外框后这两件事都不再成立：
  1) 新叶的内容若按最终尺寸摆，没有外框裁它，会整块一次性出现，不是“被长出来的外框露出”；
  2) 若让内容矩形自己从零宽长出来（grownRect 的做法），内容每帧重排、ResizeObserver 每帧报，违反开发者 2026-11-06 的决定（“新叶与从零出来的叶保持最终尺寸”）和 nested-grid.md 验收 9（“新叶内容一开始就是最终尺寸，ResizeObserver 只报一次”）；
  3) following 项的“跟随”要靠内容自己的 transform/width/height 过渡，不再是 100% 继承，所以 following 集合的含义要重写，不是“扩展”。
为什么是问题：这是本次改造的核心视觉（开发者验收场景），而计划把关键机制留成了一句含糊的“长出来”，片 3 开工时必须当场设计，且各选项各有代价：
  a) 每个内容外面再包一层与叶同矩形、同令牌过渡的裁切壳（等于把外框又放回来）；
  b) 用 clip-path: inset() 在内容上做过渡（浏览器基线 Chrome 119/Safari 17.4 支持，但 clip-path 动画不影响命中，且飞过别的面板时又不该被叶裁，要区分“新叶揭示”与“跨叶飞行”两种裁切）；
如何核实：读 packages/nb-layout/src/vue/NestedGrid.vue:128-134、305-309（overflow: clip 在 .nb-grid-frame，行 328-333；contentStyle 的 following 分支）；对照 docs/specs/ui/nested-grid.md 输出“过渡”与验收 9。
建议改法：计划里先定裁切方案并写进“要守的不变量”。注意不能用“飞行时把内容从壳里摘出来”的做法，那会违反计划自己写的“内容元素从建到销毁不换父元素”。可行的是内容元素本身不换父元素，用它自己的 clip-path: inset() 表达“与目标外框的交集”，随同一组令牌过渡：新叶揭示时 inset 从“只露出长出来的那一条”过渡到 0，跨叶飞行和前后都有尺寸的跟随时 inset 恒为 0。或者每个内容项固定带一个同矩形的裁切壳、壳与内容都不换父元素，飞行时壳不裁（overflow 切成 visible）。两种都要在片 3 的 Lab e2e 里各有一条：“新叶揭示：RO 只报一次”和“飞行中不被邻叶裁”。

[2] 阻断 | 尺寸/约束 | plan.md「布局文档 store」第 61 行 + 提案第 4 节约束表
------------------------------------------------------------------------
现象：约束表把所有工具面板（侧栏、右栏、面板、其它工具面板）都定为 `fixed`，只有编辑组是 `weight`。计划的 `resolveRef`“按提案第 4 节的约束表由 PanelRecord 给 sizing”原样照搬。
为什么是问题：`allocateSashPanels`（packages/nb-layout/src/grid-geometry.ts，注释写明“没有 weight 节点时多余空间留白，不越权填满”）在一个分支里全是 fixed 时，剩余空间不分给任何人。开发者验收场景里的 `侧栏(视图 A | 视图 B)` 就是一个纵向分支 V[A, B]，两块都是工具面板、都是 fixed：高度合计小于侧栏高度时底部露出一块空白，A 拖到 B 之上、或把视图拆到侧栏下沿（规则 7）时都会出现。同理 H[工具面板, 工具面板] 里没有编辑组的分支。
如何核实：已实验（/tmp/review-w00026-t07-plan/exp/blank.ts）：createGrid 建 V[A fixed 200, B fixed 300]，layout(400×900) 得到 A=200、B=300、根分支高度 501，issues 为“没有按比例分配的节点，剩余 399 未被吸收”“有 399 未被任何子节点吸收”。
建议改法：sizing 不能只由面板角色决定，要由所在分支决定：每个分支至少要有一个吸收余量的子节点。在 `resolveRef`（或规范化出口）按树上下文补一条规则，例如“分支内没有 weight 子节点时，取最后一个（或拖入方向上的相邻）工具面板按 weight 对待”，并写明这种面板的 `fixed` 目标在被 weight 化时怎么写回（`resizeBranches` 对 fixed 直接把目标 px 写成意图，对 weight 反解权重，两者的写回单位不同，面板在两种状态间切换时 `size` 的单位要换算）。把“全是工具面板的分支不留白”写进领域操作的不变量和片 2/4 的单元测试。

[3] 重要 | 隐藏面板/缝宽 | plan.md「布局文档 store」第 62 行
------------------------------------------------------------------------
现象：“隐藏的面板是 collapse.collapsed 且尺寸 0，sashSize 函数在它相邻处给 0”。“相邻处”没有定义。
为什么是问题：`sashSize(branchId, index)` 的 index 是第 index 与 index+1 个子节点之间的缝。隐藏面板在分支中间时（具名面板“可以被整块拖走”，所以会出现：H[bar, 编辑组 A, 侧栏(隐藏), 编辑组 B]），若“它两侧的缝都给 0”，A 与 B 之间就没有缝了：看不见分界线，也没有可拖的分隔线，A|B 的比例从此调不了，直到面板重新显示。正确规则是“一段连续的隐藏面板两侧总共留一条缝（若两侧都有可见邻居），挨着条的缝仍为 0”，这是一个依赖整个分支内容的函数，不是局部判断；而且 `placeGrid` 的 `edgeOf`（grid-rects.ts）已经把“0 尺寸的缝”和“邻居也是 0”的情形做成端点判断，隐藏面板的相邻缝由 `sashSize` 闭包决定后，`ends`/`controls`（aria-controls 指向 lastLeafOf）也要按“可见的前一块”重算。
另外：隐藏面板仍在树里、尺寸为 0，`NestedGrid` 的 `useLeafParking` 按“曾经非零、现在为零”判停放，而隐藏面板如果从未显示过（新项目里空的右栏），lastSizes 里没有它，“第一帧还没有尺寸不算停放”的分支让它不被 inert，里面的内容（占位面板头）仍可 Tab 进入。
如何核实：读 grid-rects.ts 的 `placeBranch`（缝宽取 `layout.sashSizes[branch.id][index]`）、grid-geometry.ts 的 `layoutOf`（sashSizes 由 sashSize 函数逐 index 取）、useLeafParking.ts 的 update（`else if (lastSizes.has(...)) zero.add`）。
建议改法：计划里写出 sashSize 的规则（建议：缝 i 为 0 当且仅当 “i 的前面没有可见子节点” 或 “i 的后面没有可见子节点” 或 “前后任一侧是条”；隐藏面板两侧的缝由“可见的前一块与可见的后一块”之间是否都存在来决定，且整段只保留一条），并给表驱动单元测试（隐藏在首、中、尾、相邻两个隐藏、挨着条）。对从未有过尺寸的隐藏面板，停放判定改成“面板隐藏标记”直接 inert，不依赖 lastSizes。

[4] 重要 | 规范形/尺寸守恒 | plan.md「模型与领域操作」第 38 行
------------------------------------------------------------------------
现象：“展平时把子分支的意图按比例还给子节点”只对 weight 成立。
为什么是问题：意图的单位随 sizing 变：fixed 的 size 是像素目标，weight 的 size 是相对权重（grid-types.ts 的 GridSizing 注释）。子分支 B 的 size[axis] 是 B 在父分支里的外部分配（权重或 px），B 的子节点 size[axis] 是 B 内部的单位。展平后子节点直接加入父分支：
  - 子节点是 fixed 时，按“B 的外部分配 / B 内部合计”缩放会改写它的像素目标（300px 的面板变成别的值），不缩放则 B 的合计与原来的外部分配不守恒；
  - 子节点是 weight 且 B 里夹着 fixed 时，B 的总宽原来由父级按 B 的权重分，展平后 fixed 项先取 px、余量才按权重分，B 那一块的总宽会变，兄弟跟着跳。
举例：父 H 宽 1000，X(weight 1) 与 B(weight 1) [F(fixed 300), E(weight 1, min 220)]。展平前 X≈500，B≈500；展平后按比例还权重（E 取 1），F 先取 300，余 700 在 X 与 E 之间平分各 350，B 那一块变成 650，X 从 500 缩到 350。拖放落下的瞬间兄弟的宽度会跳，而“放回原处 no-op”“结果与现状相同（规范形相等）”的判据依赖这个展平是稳定的（同一结构两次展平要得到同一结果）。
同类：createGrid 的 `collapse(parent, survivor)`（grid.ts:157）塌陷单子分支时 `survivor.size = {...parent.size}`，直接把外部分配覆盖给幸存者，不做单位换算；计划把规范化放在领域操作出口，会在 createGrid 已经这样塌陷之后再展平，两次变换叠加。
如何核实：读 grid.ts:157-170 与 planBranchResize 对 fixed/weight 的区别（grid.ts:260-353）；grid-geometry.ts 的 allocateSashPanels。
建议改法：规范化前先给“意图守恒”下定义并写成可测的判据（例如：展平前后 `layout(container)` 得到的每个叶的尺寸相同，容差 1px），再据此设计换算：展平时按“当前呈现尺寸”重新写子节点的意图（fixed 取呈现 px，weight 取呈现 px 作权重），而不是按意图比例；片 2 的单元测试用“布局前后叶尺寸不变”做性质测试，覆盖 fixed、weight、混合三类。

[5] 重要 | 内容层/动画判定 | plan.md 第 49 行，useGridMotion.ts / grid-motion.ts
------------------------------------------------------------------------
现象：计划写“useGridMotion 的 following、entering 扩展到内容项”。现行判定 `decideMotion → placementMoved(items, previous)` 只比较叶与分隔线的摆放（`placement.items`），触发也只有 `watch(placement)`。
为什么是问题：内容项换叶（`leaf` 变了）而这两块叶的矩形都没变时，placement 不变，`placementMoved` 返回 false，`watch(placement)` 不触发，内容瞬间跳过去，没有位移。典型：把多标签面板 X 的活动标签 A 并入已有面板 Y（moveTabToStrip），X 与 Y 的矩形都不变，只有内容 A 的 `leaf` 从 X 变成 Y。这正是开发者原话要解决的“跨容器先消失再瞬移”的另一半（合并进已有容器，而不是拆出新容器）。此外 `contents` 是独立 prop，只改 `contents` 时 placement 的 watcher 不会跑。
如何核实：读 useGridMotion.ts:59-74 的 decideMotion（first/gesture/placementMoved 三个出口都不看内容），NestedGrid.vue:136-143 的 watch(placement)。
建议改法：把内容项的矩形纳入 `GridMotionFrame`（items 与 previous 都带内容矩形），`placementMoved` 比较内容矩形；触发改成同时 watch placement 与 contents；片 3 的 Lab 场景和单元测试必须有“标签并入已有面板，两块叶都不动，内容滑过去”一条（`decideMotion` 表驱动加 Lab e2e）。

[6] 重要 | 内容层/叠放顺序 | plan.md 第 49 行（只写“移动中的项 z-index 抬高”）
------------------------------------------------------------------------
现象：计划只在移动中抬高内容的 z-index，没有写静止时内容、外框、分隔线的叠放规则。
为什么是问题：内容元素的 DOM 位置是“叶头之后紧跟这块叶的可见内容”（plan 第 51 行），已有元素在 Vue 带 key 的 v-for 里不搬位置。内容 A 换到后面的叶 Y 之后，A 的 DOM 位置仍在 Y 外框之前。同一父元素里全是 position:absolute 且 z-index:auto 的元素按 DOM 序绘制。计划没有写卡片的底色和边框画在哪一层；若画在叶槽里（现行外壳如此，卡片按叶矩形画，plan 第 70 行说“卡片画在内缩之后的矩形里”），后面的 Y 外框会盖住 A（从代码推断，未在浏览器复现），A 在静止后消失，只在 z-index 抬高的移动中可见。分隔线的 SashHandle 有 `z-index: 1`（SashHandle.vue:284、412），内容若给了比 1 大的值又会盖住覆盖层的悬停线。
如何核实：读 NestedGrid.vue 的模板（叶外框与 SashHandle 同级）、SashHandle.vue 的 z-index，以及 .nb-grid-frame 没有 isolation/z-index。
建议改法：在“要守的不变量”里写固定的三层：外框 z 0、内容 z 1、分隔线与反馈 z 2（在 NestedGrid 内部用独立层级，不新增全局 z-index 令牌）；移动中只在内容层内部再抬一级。用 Lab 场景断言“内容移到 DOM 序靠前的叶之后仍可见（elementFromPoint 命中内容）”。

[7] 重要 | 内容层/焦点与 Tab | plan.md 第 51 行，grid-focus.ts / useGridFocus.ts
------------------------------------------------------------------------
现象：计划把 useRenderOrder、useGridFocus “纳入内容项”写成一句话。现行 `GridFocusItems.items()` 是“树序的叶外框与分隔线元素”，`noteFocus`/`moveTab`/`moveGridFocus` 都用 `element.contains(target)` 判断焦点属于哪一项。
为什么是问题：内容不在外框里，焦点在视图内容里时（几乎总是），`items.findIndex(({element}) => element.contains(target))` 得到 -1：`moveTab` 直接返回 "browser"（Tab 不接管）、`noteFocus` 把焦点记不到任何一块上（`moveGridFocus` 回到这块时找不到上次的焦点）。DOM 序与树序不一致（内容换叶之后几乎必然）这条路径在 t07 之后是常态而不是例外，nested-grid.md 的“已知限制”会在每次视图移动之后命中，不只是 t06 记录的那个特例。每个叶的一“站”要变成外框加（零个或一个）活动内容的并集：`focusablesIn(element)`、`atEdge`、`lastFocused` 的键、sentinel（enter/exit）都要按并集改。非活动标签的内容是 visibility:hidden + inert，要排除。
还有一个具体坑：嵌套 grid 的 F6 逻辑用 `from.closest("[data-grid-scope]")` 判层级，与内容层无关，可保持；但内容里有 Monaco 之类自己处理 Tab 的内容，`atEdge` 用 `compareDocumentPosition` 在外框与内容两个不相交的元素之间比较，要改为在站的并集里比较。
如何核实：读 grid-focus.ts 的 moveTab/noteFocus/moveGridFocus，useGridFocus.ts 的 scope.items。
建议改法：计划里把“站”定义为 `{frame, content}` 的并集并写进 GridFocusItems 的新接口；nested-grid.md 的 Tab 顺序/移动焦点/读屏顺序三条输出和验收 8 随之扩展（内容里的焦点：Tab 走出一块、F6、点空白后按 Tab、内容换叶后的树序）。t06 的遗留（从 grid 外 Tab 进来、点空白后 Tab）给出方案（计划只引用了遗留，没有给设计）：落在树序首/尾的 sentinel 加 focusin 进入时的重定向，并写明点内容空白时 tabindex=-1 的接住元素是哪个。

[8] 重要 | 内容层/取整 | plan.md 第 46 行「矩形是所属叶减去 insetTop」
------------------------------------------------------------------------
现象：内容矩形 = 叶矩形（已按设备像素取整）减 `insetTop`（32 CSS px），在 CSS px 上做减法。
为什么是问题：32 CSS px 乘设备像素比不一定是整数（dpr 1.1、1.15、1.33 等浏览器缩放档），内容上沿落在半个设备像素上，与上面的面板头之间出现发丝缝或抗锯齿模糊；nested-grid.md 的“取整”输出和验收 9 的整套取整（沿主轴累加、缝宽取整）就是为这个写的，内容层绕过了它。过渡中外框与内容各自对 transform/width/height 做线性插值，起终点若有取整差，两者之间每帧会差零点几像素，“同步”只在起终点取整一致时成立。
如何核实：读 grid-rects.ts 的取整（end = Math.round(idealEnd * scale)）；内容矩形没有对应实现。
建议改法：由 `placeGrid`（或它的并列纯函数）一次算出内容矩形：insetTop 先乘 dpr 取整后再减，保证“外框顶 + insetTop 取整 = 内容顶”，并把它加进 grid-rects.test.ts 的 dpr 枚举（1、1.1、1.25、1.5、1.75、2）。

[10] 重要 | 持久化/未绑定项目 | plan.md 第 56-66 行；提案第 8 节表格
------------------------------------------------------------------------
现象：提案第 8 节规定 `workbench.layout` 在“绑定项目 project/local，否则 user/local”，`editor.tabs` 在“project/local，未绑定只在内存”。计划原样接收，没有处理两者不对称。LayoutDoc 里编辑器标签是 `{kind:"tab", type:"nbook.editor", tabId}`。
为什么是问题：未绑定项目的窗口（现行代码里 `createStore: null`，编辑会话完全不持久，见 editor/web/session.ts）里，编辑器标签会随布局写进 user/local 的 `workbench.layout`，而它们的内容（地址、编辑器、光标）不会存。结果：
