拉远看审查：nb-layout 做成能发到 npm 的通用布局库（w00026 t31）

审查对象：docs/proposals/nb-layout-general-library.md。
读过：提案全文；ADR 0029、0033、0044、0053；t31 的 main-outline.txt 与 independent-design.txt；t26 的 deep-review-api.txt（逐条核对了几处）；packages/nb-layout 的 package.json、AGENTS.md、README、行数；neuro-book/src/sdk/components.ts；t14 的 README。
没做到的：我的 WebSearch 权限没放行，所有外部库（dockview、splitpanes、reka-ui、allotment 等）的现状我也没法核实，下文涉及它们的地方都标“未核实”。

总判断：方向（把 nb-layout 收窄成不带工作台领域模型的库）站得住，工作台层拆出去这一步我同意。但提案把“整理”和“发布准备”捆在一起，后者现在没有任何真实使用方来校验。最该改的是第 1、2、3 条。

### 1. 要解决的是“有人想用”，不是“有人在用”：发布准备全做在前面，没有第二个使用方校验

结论：问题里有一半是真问题（整理，对仓库内部也有价值），另一半（编译产物、API 报告、公开清单、`@stable`/`@experimental` 分级、MIT、中英文案、手感引擎进库）是为一个还不存在的外部使用方做的预备，而且提案自己的推理在别处否定了这种做法。

依据：
- 驱动只有开发者 2026-11-16 一句“后面可以发到 npm，其他项目依赖他”（提案“决策记录”，第 249 行）。没有点名的外部使用方、没有人的需求。t26 的“第三方”是审查者假扮的。
- ADR 0044 第 6 条当初的理由是“统一用一套库、Splitter 不留两份”，不是“给别人用”（提案第 19 行自己也承认）。这个理由现在仍成立，而且 t14（把 nb-story、dev-panel 迁到 nb-layout 的 Splitter、删 nb-ui 里冻结的那份）单独就能满足它，不需要发布。
- 提案拒绝备选 A 的理由是“只有一个使用方，形状没有第二个例子校验，发布之后受版本承诺约束，改不动”（第 91 到 92 行、第 177 行）。同一个理由对“手感引擎进库”（第 3 条）、`useGridHost`、CSS 变量表、错误码集合同样成立，提案却只对备选 A 用了它。
- 提案给的发布条件是“t14 迁完、有第二个使用方以后再发”（待定项 5）。但 t14 迁的 nb-story 与 dev-panel 只用 Splitter（packages/nb-story、packages/dev-panel 里只有 Splitter 的使用；nb-ui 里冻结的 Splitter 也只有这条线），不碰 NestedGrid、拖动会话与手感引擎。所以“t14 完成”并不校验提案要承诺的大部分公开面。
- 发布不一定是“可选的以后”：ADR 0044“后果”写明 t14 之后 nb-story 的发布依赖从 8 个包变 9 个，nb-story 下一次发布就必须带着已发布的 nb-layout。也就是 nb-story 的发布节奏会反过来逼 nb-layout 提前发 0.x。提案没写这个耦合。
- ADR 0029 决定 2 当初选源码发布的理由是“只承诺 Bun、仓库里本来就是源码”，提案说“目标变成别的项目用后这个前提不在了”。这个推论可以，但前提也是“目标是别的项目用”，而这个目标目前只有一句话。

建议：
- 把工作拆成两档：第一档，仓库内现在就有收益、也不依赖发布的：工作台层拆出（L2）、错误形状统一、去掉 nb-ui 依赖、入口改显式清单加导出名测试、t14。第二档，只为发布而做的：编译产物流水线、API 报告 CI、`@stable`/`@experimental` 全量标注、手感引擎进库、`./locales` 默认英文等，等有一个点名的外部使用方再做，并让这个使用方来定形状。
- 如果开发者仍想一次做完，至少把待定项 5 的“发布条件”写成可验证的：例如“有一个不在本仓库的真实宿主，用公开入口接过拖动”，不要用 t14 当第二个使用方。

### 2. 备选 B 是在“发源码”的前提下被否决的；改成发编译产物后，它的主要缺点大多消失，新包的真正理由也没写出来

结论：待定项 3 已定“发编译产物”之后，提案没有回头重评备选 B。单包、不发布 `./workbench` 子路径、发布目录由打包脚本生成，能解决提案列出的大部分痛点，新建 `nb-workbench-layout` 包的收益需要重新论证。

依据：
- 备选 B 的“不推荐”理由（第 195 到 198 行）：发布包仍带 2300 行无关代码；不承诺的子路径靠约定、一次深导入就破；源码发布门槛没解决。三条都以“照旧发源码、`exports` 对外”为前提。
- 提案自己的方案里，“打包脚本生成发布目录，源码包仍 private、`exports` 仍指向 `src`”（第 152 行）。发布目录的 `exports` 只列 `.`、`./vue`、`./style.css`，工作台文件根本不会进 dist，深导入没有路径可走；发布物也不含 2300 行。
- “为什么另起一个包”给的理由是：编辑器插件、共享合同与 SDK 要一个纯 TS、Bun 里能测、各插件都能依赖的位置（第 84 行）。这个理由是 t04 当初的理由，当时就在 nb-layout 里满足了，不需要新包。
- 没写出来的真实理由有两个，应写进提案与新 ADR：
  - 许可证：nb-layout 发 MIT，而工作台层是 AGPL 仓库里的领域代码；一个目录里放两种许可证，比分成两个包难管。如果是这个原因，应当明说，这才是拆包的硬理由。
  - 依赖方向的机器守卫：L2 不得被 L0 导入。这一点同一个包里的 `boundary.test.ts` 也能做（它今天已经按目录守核心不导入 Vue）。
- 代价：新包意味着约 40 个文件的导入改路径（提案第 212 行）、SDK 与插件作者可见的导入来源变化、包层面的 AGENTS.md、测试配置、工作区解析、Lab 的来源登记等；提案只说“机械改”，没估成本。

建议：
- 在提案里补一段“备选 B′：单包，发布目录白名单”的比较，把拆包的理由改写成“许可证加方向守卫”。若许可证是唯一硬理由，需要核对：现在 nb-layout 里有没有从 AGPL 兼容但不 MIT 兼容的来源搬来的代码（ADR 0044 第 5 条说 Trellis 的许可证与 AGPL 不兼容、“只借交互想法”；改成 MIT 之后应再确认没有逐字复制，没有记录说明核对过）。

### 3. “手感引擎进库”：范围没估、与单使用方原则矛盾、与 t26 的建议相反，`@experimental` 解决不了它的发布成本

结论：这是提案里风险最大的一块，且是 2026-11-18 才改的决定（待定项 2）。开发者的疑问是对的（调得最久、两种手感都靠它），但“进库”的代价和范围提案没给，决定前提是“编排一半已隔在接口后面”，而同一段又承认 `layout-drag.ts` 真耦合。

依据：
- 提案第 102 到 105 行：`live-drag.ts`（381 行）隔在 17 个回调的宿主接口后；`layout-drag.ts`（1130 行）“导入布局文档的操作、活动栏与入口条、编辑器标签、视图容器……配置项 22 个”。然后说“与领域无关的编排一起抽出来进库”，没有行数、没有清单、没有“抽完剩下多少”。这是开放式范围。
- t26 的 deep-review-api.txt 第 140 行：“实时布局的帧循环（卡片追赶、来源收起、候选稳定）只有工作台一个用户，先不抽，但在 NestedGrid.md 里写‘实时布局只有工作台实现’”。independent-design.txt 的结论 2 也是“不要把 1400 行拖动控制器搬进库”。提案采纳了开发者 11-18 的改判，但没有反驳这两条依据，只在“决策记录”里写了主会话的回答。
- 提案自己写“先标 `@experimental`：它还在改，例如按住不动时停下帧循环是 2026-11-18 才做的”（第 105 行）。工作台的手感调整是日常高频改动；引擎进库后每次调整都落在一个有 API 报告 CI、有变更记录规矩（ADR 0053 第 4 条：源码包各一份变更记录）、有独立版本号的包里。标 `@experimental` 只是不承诺兼容，不能免掉“改公开签名要更新清单与 API 报告”的流程成本。
- 引擎的泛型参数加 17 个宿主回调，是只对着一个宿主（工作台）设计出的接口形状。这正是提案反对备选 A 的原因。
- 没有说明：引擎的测试放哪里（现有实时拖动的测试大概依赖工作台夹具）；Lab 与 e2e 放哪里；引擎进库期间工作台的手感回归如何验证（依据 e2e 的负载敏感，见记忆里 editor-area 实时拆组怕负载的记录）。

建议：
- 分两步：第一步按 t26 做小的——`useDragSession`、`useGridHost`，以及把 `live-drag.ts` 里已经隔开的部分在 L2 里先整理成“状态收进一个对象、判定拆成纯函数”（提案第 112 行已经有这个要求），不进库。第二步等外部使用方出现、看到它真正需要哪些编排，再把已被两个宿主验证的部分提进 L1。
- 若坚持现在进库：先在提案里写出范围清单与行数估计（“进库的函数名”与“留在 L2 的函数名”），并给出验收：工作台手感不变的判据（哪些 e2e、哪些 Lab 场景）。

### 4. 会锁死的东西：公开面太宽、一次承诺的表面太多，且 SDK 已经是一个现有的公开消费者

结论：提案承诺的东西（`@stable` 符号、README 的 CSS 变量表与 `data-*` 表、`GridSnapshot` 版本规则、错误码联合、API 报告）加起来是一个大的兼容表面。有三处会让以后难回头。

依据：
- 插件 SDK 已是 nb-layout 的公开消费者：packages/neuro-book/src/sdk/components.ts 第 41 到 46 行从 `@notnotype/nb-layout/vue` 与 `@notnotype/nb-layout` 重导出 `NestedGrid`、`Splitter`、`TabStrip`、`DropFeedback*`、`FloatWindowHandles`，以及 `SplitterGestureCancelReason` 等一批 `Splitter*` 类型。提案第 129 到 130 行要把 `Splitter*` 改名为 `GridGesture*`，第 140 行要把 `TabStrip` 搬进 L2。这两件事对插件作者就是破坏性变更，而插件 SDK 是已经发布过的产物（ADR 0030、0033 的上下文）。提案的“影响”只写了“SDK 导出的名字搬前搬后各导出一份清单，要求一致”（第 213 行），那是布局文档类型的搬家，不是这两处。需要明说：这是 SDK 的破坏性变更，还是保留旧名的别名。
- 错误码是字符串字面量联合（第 117 到 119 行）。宿主按码写 `switch` 时，新增一个码就是类型层面的破坏。提案没有规定“码集合是开放的、宿主必须有默认分支”，也没有规定新增码算次版本还是补丁版本。要在 Spec 里写死，不然每加一个码都要走一次“次版本可以破坏”。
- CSS 变量约 45 个（第 34 行），其中一半是通用 token；全进 `--nb-layout-*` 命名空间并写进 README 表，作为承诺范围（第 162 行）。45 个名字是一大块要冻结的东西；而它们多是视觉微调。建议把承诺范围缩到“主题级”的十几个（颜色、间距、动画时长、层级），其余标内部、不进表。
- `GridSnapshot` 带版本号、“1.0 起新版本必须读得了旧版本”（第 163 行）：此条应只对 1.0 起生效，0.x 时明说可以不兼容；而工作台存盘的是布局文档（L2）而不是 `GridSnapshot`，所以 L0 的快照格式承诺是纯为外部使用方预设的，目前无人持有旧快照。
- 许可证改 MIT 对已发布版本不可逆：一旦发出，已发布版本永远是 MIT。开发者已定，提案无需改，但应明确：MIT 的 nb-layout 现在不得再从 AGPL 的代码取内容（反方向的搬运需要逐文件复核）。AGENTS.md 里应写这一条。

建议：
- 在 Spec 的“边界与兼容”里写：错误码集合开放、新增码不算破坏；CSS 变量只承诺列在表里的一小批。
- 单列一条：`Splitter*` 改名与 `TabStrip` 搬家对插件 SDK 的影响与处理（别名、弃用期，或认定 SDK 本来就是 0.x 并写进 SDK 变更记录）。

### 5. “更简单的做法与业界常规”：外部库对比未核实，定位没有对比最近的竞品

结论：提案承认外部库的现状“凭记忆，没有重新核实”（第 206 行），ADR 0044 第 5 条也未核实；这对“工作台自写”的结论影响小，对“第三方为什么选 nb-layout”的定位影响大，而提案把它简化成一句话定位（第 49、205 行）。

依据：
- 提案对备选 C 只讨论了 dockview，且是 ADR 0044 的旧判断（“停靠时搬 DOM，多行标签、固定标签、键盘导航是付费档”）。independent-design.txt 第 3.1 节指出自己的记忆是 dockview 为 MIT 并有 Vue 包装、可能有避免重挂载的渲染选项，说法与“付费档”可能不符；我这边也无法联网核对。这是一条待核的事实，会影响 ADR 0044 第 5 条（影响“为什么不选 dockview”的 README 回答）。
- 定位句“Vue 3 里 VS Code 手感的嵌套网格与分隔条”（第 43 到 49 行）真正的近邻是 allotment（VS Code splitview 的移植，React）、splitpanes（Vue 的分隔窗格）、reka-ui 的 Splitter（nb-ui 已依赖 reka-ui，见 packages/nb-ui/package.json 第 64 行；ADR 0044 背景里说嵌套 DOM 的来由就是它）。提案没有一句话说明与它们的区别（按矩形摆放、两轴约束求解、收起与吸附、过渡与交换）。这五个能力里至少“按矩形摆放不搬 DOM”和“两轴约束求解”是真差异，应当作为 README 与 ADR 的核心论点，并附证据（Lab 场景、对比实测），而不是只靠自己的评价。
- 常规做法上，业界库发布时多数是：编译产物加类型、peer 依赖框架、API 报告（api-extractor 一类）。提案这部分与常规一致，我没有异议。

建议：开工前花一轮核实 dockview、splitpanes、reka-ui 的现状（官方文档与仓库），在提案“备选 C”里换成有出处的结论；否则 README 里“为什么不选 X”的回答没有依据。

### 6. 掉进实现细节、该讲的架构取舍没讲清

结论：提案里实现细节很多，下面这些架构层面的取舍反而缺位。

依据：
- 已经够细的：45 处 `rejected` 与 8 个码名、`useDragSession` 与 `useGridHost` 的参数清单（第 109 到 110 行）、`z-index.test.ts`、`tabbable` 依赖、扫描 `var(--` 的测试。这些属于实施计划，放在提案里让读者以为它们是已定的设计。
- 缺位的：
  - 版本与发布的协调：L2 私有包依赖 L0/L1 用 `workspace:*`，L0/L1 发布后若有外部破坏性变更，工作台怎么同步（锁步还是各自）；以及发布流程怎样纳入 `release:publish`，其他 8 个包仍发源码、nb-layout 发编译产物，两种发布模式并存的维护成本（提案只说“照新应用与 SDK 的先例”，ADR 0033 的先例是整个应用打成 bundle、依赖全部打进去，与“Vue 组件库的库模式构建、peer 外置”是两回事，不能直接当先例）。
  - 与 ADR 0053 的关系：变更记录、阶段、版本号的既有规矩（源码包各一份 CHANGELOG、在它下一次提版时建、不进 npm 包）与提案“版本”一节自己写的“次版本可以破坏但必须在变更记录里单列”要对齐；提案没引用 ADR 0053。
  - 谁是目标读者与验收：定位里只有“第三方”，没有写“他想拿它做什么”。一个读者场景（例如“我要做一个左右两栏加底部面板的 Vue 应用”）写进提案，能直接检验入口收窄、样式默认值和 `useGridHost` 是不是够用。
  - 成本与顺序：提案没有给分步顺序和各步的工作量。独立设计里是八步，前七步仓库内；提案的“发布与回滚”一节有一句，但没有各步估计，也没有先做哪些、哪些可砍。读者无法判断“整体多大”，也就无法判断第 1 条的分档。
  - 回滚点：提案说“每一步各自能回退”，却没有说拆包这一步（约 40 个文件改路径）怎么回退、是否与 t14 的并行改动冲突（t14 排在去 nb-ui 之后，已写）。

建议：把实现细节挪到 Task 计划，提案里保留：分档（第 1 条）、新包的真实理由（第 2 条）、引擎范围（第 3 条）、对 SDK 的影响（第 4 条）、发布模式并存与 ADR 0053 的关系。

### 7. 小的 YAGNI（影响低，实施时顺手砍）

- `issues` 事件之外再留“最近 N 条的查询接口”（第 119 行）：现在没有使用方要这个；开发者面板如果已经靠累计列表，改成只发新增后让它自己累积就够。
- 开发模式下“配置错误各报一次”（第 120 行）：t26 里 `sashSize` 为 0 一类是真实踩过的，保留这几条具体的就行，不做通用机制。
- `./locales` 子路径加中文目录加默认英文（第 139、132 行）：第三方缺少文案时有英文默认即可；中文目录对工作台有用，但它可以随 L2 的适配器走，不必成为库的公开子路径。
- 提案对 `@stable`/`@experimental` 的“每个公开符号都标”：先标 `@experimental` 为默认，只给确有使用方的符号标 `@stable`，比一次标全省事，也不会过早承诺。

---
没有发现的项（按问题 4 的子项，不用处理）：
- 数据格式：布局文档 JSON 不变，提案说清了（“影响”第 210 行）。
- 在“拖动控制器分界”上，把适配层留在 L2、不做通用停靠模型（备选 A），我认为是对的，且与独立设计一致。
