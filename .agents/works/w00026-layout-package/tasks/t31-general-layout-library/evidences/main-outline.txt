t31 主会话的方案要点（写在看独立设计之前，2026-11-18）

问题：ADR 0044 第 6 条把 nb-layout 定位成“工作台的布局工具”。开发者 2026-11-16 选丙：通用、可发到 npm。API 审查（第三方视角，14 条）列出的门槛：
- 文档层是工作台模型：硬要求活动栏与状态栏、三个区域名、视图容器，没有构造器（api-01）。
- 拖动控制器约 1400 行在应用里（api-04）。
- 错误有两种形状、3 个码、中文串，诊断累计（api-05）。
- 入口过宽，内部名字都导出（api-07）。
- 落点规则写入时不查（api-02）；手势落账后要宿主手写 rebase（api-03）。
- 要整个 nb-ui 与 46 个主题 token，发布物是源码（api-12）。

推荐方案：三层，库里只留与领域无关的东西。
1. `@notnotype/nb-layout`（纯 TS，已基本通用）：网格树与求解、快照、分隔线拖动求解、拖动手势状态机、落点几何、过渡规划、标签条几何。只收窄入口、统一错误。
2. `@notnotype/nb-layout/dock`（新，纯 TS）：通用的停靠文档。
   - 内容：面板（带标签）、树、浮动窗、最大化；结构操作（移到外缘、标签条、中央，浮出、停靠、关闭）、校验、落点规则。
   - 骨架约束由宿主经 `DockPolicy` 给：固定的叶（今天的活动栏、状态栏）、接受矩阵、哪些边能分、新 id；写入时也按它查（修 api-02）。
   - 面板记录带宿主扩展字段（类型参数），操作原样复制、保存。工作台的 `container`、`entries`、`activeContainer` 放这里，持久化的 JSON 形状不变，不用迁移。
   - 手势落账的 rebase 由库做（修 api-03）。
3. `@notnotype/nb-layout/vue`：`NestedGrid`、`Splitter`、`TabStrip`、拖动会话适配层，加一个通用的停靠拖动控制器。
   - 控制器是今天 `layout-drag.ts` 与 `live-drag.ts` 里与工作台无关的那一半：拿起、落点判定、实时布局的预览循环、提交。
   - 宿主钩子：额外的落点（工作台的入口条）、来源怎么认、接受与拒绝的反馈。
- 工作台层搬回应用 `plugins/workbench/web/layout/`：区域、视图容器、条的骨架、投影（入口条、只显示当前容器）、入口条上的落点、实时布局的策略。
- 错误：一个结果类型，码加参数，文案经 `./locales` 由宿主取。
- 样式：库里不用 Tailwind 原子类，CSS 变量都给缺省值；不装 nb-ui 的 token 也能用，nb-ui 只留文案端口一类小依赖，或者挪进库里。
- 发布：照 ADR 0029 发源码，先不出编译产物；`files` 白名单；0.x 版本，破坏性变化写进变更记录。

备选：
- 乙：只把工作台专用的文件挪到子路径 `/workbench`，不做通用停靠文档。便宜，但第三方拿到的还是工作台形状的文档。
- 用现成库（dockview 等）：要求里有实时布局（Trellis 式）、卡片形状与交换过渡、入口条、设备像素对齐、无障碍顺序，换库等于重写工作台；ADR 0044 选自写的理由仍成立。

待定项：
- 布局文档做成通用停靠文档加扩展字段（推荐），还是整个搬出包；
- 拖动控制器进不进库（推荐进）；
- 源码还是编译产物（推荐先源码）；
- 子路径命名；
- 和 t14（nb-ui 冻结的 Splitter 迁到 nb-layout）的先后。

影响：
- 工作台的导入路径改，行为不变，布局记录格式不变。
- nb-story、开发者面板在 t14 之前不受影响。
- 首发由开发者执行。

Spec：
- 新建 `ui/dock-layout`：通用的停靠文档与拖动控制器，从 workbench-layout 的落点规则、结构操作里抽出与工作台无关的部分。
- workbench-layout 只留区域、容器、条与入口条。
- nested-grid、layout-drag 的 owner 与公开入口跟着改。
