t08 测量：长章节开着时拖标签的帧间隔（2026-11-07，无头 Chrome、软件渲染，负载约 4.5；别的会话在跑）。脚本 scripts/measure-live-drag.e2e.ts，命令见文件头。
样本：约 10.6 万字的 Markdown 章节开着，拖同组的短章标签在它的四条边和中央转两圈，每处停 300ms（预览换一次，长章重排一次）。单位毫秒。

第一次运行：
{
  "live": {
    "frames": 406,
    "median": 17,
    "p95": 67,
    "max": 100
  },
  "indicator": {
    "frames": 360,
    "median": 17,
    "p95": 17,
    "max": 33
  }
}
第二次运行：
{
  "live": {
    "frames": 375,
    "median": 17,
    "p95": 50,
    "max": 100
  },
  "indicator": {
    "frames": 365,
    "median": 17,
    "p95": 17,
    "max": 17
  }
}

读法：中位都是一帧（17ms）；实时布局 p95 50 到 67ms、最长 100ms，落点指示 p95 17ms。计划的线是卡片帧间隔 p95 超过 50ms 算不达标：第一次运行 67ms 不达标，第二次恰好在线上（负载 4.5、软件渲染）。

实现审查修正之后（卡片矩形没变不换对象，内容项不读卡片矩形，插槽不再是动态的；负载 8.5 到 5.5，软件渲染）：
第一次运行：live frames 328，median 17，p95 50，max 83；indicator frames 337，median 17，p95 17，max 17。
第二次运行：live frames 361，median 17，p95 50，max 83；indicator frames 344，median 17，p95 17，max 17。

读法：两次都在线上（不超过 50ms），最长从 100ms 降到 83ms，负载比上一轮高。没有改手感。退路（加长稳定时长、预览期间邻居内容用最终尺寸）要开发者定，后者和“内容跟随”冲突；这一轮便宜的修法已经做了。
