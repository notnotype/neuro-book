### 3. `resizeFloatRect` 下沉：它的类型是 L2 的 `LayoutFloatRect`，且 L0 公开入口要加值导出；计划列的“要补的 L0 名字”与实际不符
严重程度：重要
位置：plan.md 第 42、44 行；layout-doc.ts:52、:1164、:1176、:1182；grid-rects.ts:124 到 130；index.ts:8
现象：
- `resizeFloatRect(start: LayoutFloatRect, direction: LayoutFloatResize, …): LayoutFloatRect`。`LayoutFloatRect` 是 `{x, y, width, height}`，定义在要搬走的 layout-doc.ts:52，而 grid-rects.ts 里与 `GridFloatInput` 放一起的是 `GridRect`（`left/top/right/bottom`），形状不同。直接“下沉到 grid-rects.ts”必然反向导入 L2 的类型，或在 L0 新定义一个同形状的类型再让 L2 的 `LayoutFloatRect` 去对齐，计划没写用哪种。
- 同一段里紧挨着的 `clampFloatRect`（layout-doc.ts:1164，同样吃 `LayoutFloatRect`）留在 L2，结果一对浮动窗矩形函数分居两包。

- 按 import 逐行核对：L2 搬走文件今天不在 `.` 入口里的 L0 名字，源码里只有一个，`placeGrid`（layout-drop.ts:9，用在 :426、:441）；其余 `grid-types`、`grid-geometry`、`grid-drop`、`grid` 的名字都已经在公开入口（`export * from "./grid"` 带出 `grid-types` 全部）。计划写的“`GridPlacement`、`GridLeafPlacement` 一类”是臆测：layout-drop 只用 `placeGrid` 的返回值推断，没有按名字导入这些类型。把它们一并公开，会让“受版本承诺约束”的面无理由变大（提案第 162 行正是为剔出“无人使用”清点而写）。
为什么是问题：实施时会在“反向导入 L2 类型”与“L0 新建类型”之间当场做设计决定，而且公开面可能多出无人使用的名字。
建议改法：计划里定下：L0 在 grid-rects.ts 新增 `GridFloatRect`（`{x, y, width, height}`），`resizeFloatRect`、`LayoutFloatResize` 随它下沉，L2 的 `LayoutFloatRect` 写成该类型的别名或保持同形状（结构类型兼容，应用侧零改动）；`clampFloatRect` 同样下沉更自然（二者共用一个矩形），一起列入“要下沉的”。公开入口只补 `placeGrid` 与上面确实被 L2 导入的名字，清单以类型检查结果为准，不预先写 `GridPlacement` 一类。

### 4. `DropSectorsOverlay` 改泛型：应用侧并不需要映射；`labels` 改必填会破坏现有调用；换夹具会丢掉“真实形状”的覆盖
严重程度：重要
位置：plan.md 第 45、47 行；DropSectorsOverlay.vue:11 到 19；WorkbenchDragFeedback.vue:29、:69；layout-drop.ts:307 到 312、:324；DropSectorsOverlay.dom.test.ts:4 到 25；fixtures/nb-layout/index.ts（DropSectorsOverlay 场景）
