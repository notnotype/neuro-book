### 1. 展平与拆分继承来的属性不进快照，往返恢复后丢光，计划“旧快照不受影响”的说法不成立
- **严重程度**：重要
- **类别**：被破坏的既有约定、遗漏
- **位置**：plan.md 第 28 到 32 行、第 88 到 89 行（风险条）；`grid-snapshot.ts:54-58`（`currentConstraints` 注释“快照不带约束、sizing 与收起策略”）、`:192-208`（分支的 `sizing`、约束、收起只从当前树里同 id 的分支取，没有就是 weight、不限、无收起）；`grid-types.ts:143-147`
- **现象**：快照只存 `size`。`sizing`、约束、收起策略由 `restore` 按 id 回落到“当前树”或宿主的解析函数。`splitLeaf` 新造的分支 id 在宿主新建的树里不存在。
  - 探针 A7：nav 保留像素 188（150 到 300、可收起），main 600。按计划的结果手工搭树：新分支 `pair` 保留像素 188、150 到 300，里面 nav、extra 各 94。
    - 会话内，容器 1200：`pair` 188、nav 93.5、extra 93.5、main 1011。
    - 先 `serialize()`，再在宿主重新建出的初始树上 `restore`：`pair` 变成 `sizing: "weight"`，约束放开（实测 min 0、max MAX_SAFE_INTEGER）。nav 取回宿主声明的 `fixed`，意图却是权重量级的 94。
    - 恢复后容器 1200：`pair` 286.1、main 912.9。容器 800：`pair` 190.6、main 608.4。保留像素没了。
  - 展平同理：存活的叶继承分支的 `fixed` 与 240 px 意图，快照里只剩 240。恢复时 `sizing` 由宿主按这个叶自己的声明给，意图 240 被当成它自己的单位。
- **为什么是问题**：计划第 3 项“拆保留像素的叶，新分支保留像素、宽度不变”和风险条“快照存的是展平之后的结果”，只在同一会话内成立。StarterScene 与 README 起步例子都是“结构操作后 `serialize()` 存起来、下次 `restore`”。这条路径给出和计划目标相反的结果，也没有诊断。旧代码也丢（新分支本来就是 weight），但计划把“宽度不变”当验收，缺这条就是半截。
- **如何核实**：运行 `probe2.ts`，看 A7 的“计划后 session 内”与“计划后 往返恢复”两行。
- **建议改法**：二选一并写进计划。
  - 快照带上分支的 `sizing`、约束与收起（版本 3，旧版本仍按现在的回落）。
  - 或承认结构操作结果不可往返。`grid.md` 与 README 写明“`splitLeaf` 之后宿主要在恢复前把新分支声明进当前树”，验收改成会话内。
  - 测试补一条：拆保留像素叶、`serialize`、重新建树、`restore`、呈现不变。

### 2. 展平与拆分“继承五项属性”没有按轴写规则，整体替换会丢叶自己的约束；收起状态与根展平没有交代
- **严重程度**：重要
- **类别**：边界、遗漏
- **位置**：plan.md 第 30 到 31 行；`grid.ts:175-189`（`collapse`，根展平走 `tree = survivor`，不赋 size）；`grid-geometry.ts:344-361`（分支约束 = 子节点推导与声明相交）
- **现象与推演**：
  - **约束合并规则**。计划写“继承 `minimumSize`、`maximumSize`，它自己原来沿父轴的这些属性作废”，但 `minimumSize` 有宽高两个分量。
    - 叶 y 在竖向分支 B 里，`y.minimumSize.width = 100` 是 y 的交叉轴约束。它通过 B 的推导下限（交叉轴取子节点最严的）让 B 在父分支主轴上至少 100 宽。
    - 展平后若整体用 B 声明的 `minimumSize`（`splitLeaf` 与 `instantiate` 造出的分支是 0），这 100 就没了。窄容器里不再有 `over-constrained`，最小宽度失去保护。
    - 探针 A2：旧实现展平后 y 保留 `min {100, 50}`；整体替换是 `{0, 0}`。
    - y 沿 B 主轴（高）的 `minimumSize.height = 50`，展平后变成交叉轴约束，保留还是丢，计划没写。
  - **`splitLeaf` 对称**。新分支继承目标叶的两个分量，目标叶自己也保留，同一个约束记两遍。
    - 探针 A3：nav 约束 150 到 300，水平拆分后新叶最小 200，新分支继承上限 300。推导下限 150 + 200 + sash 超过上限，出 `conflicting-bounds`（pair 实测 350）。
    - 宿主避不开，因为新叶约束是它自己给的。这也许是对的（上限 300 本来装不下两块），但计划没说是有意的，也没说沿新轴的上限要不要继承。
  - **存活叶原来的收起状态**。计划让它整体作废，换成 B 的（可能没有）。B 里一块收起成 0 的叶，兄弟删掉后，叶原来不占宽，展平后没了收起标记，突然占满整列。没有返回值告诉宿主，`find(id).collapse` 也从有变无，宿主按叶 id 存的收起状态读不到。
  - **根展平**。`removeLeaf` 把根分支删到只剩一个孩子时走 `tree = survivor`，没有父分支。计划“继承被展平分支在父分支里的外部属性”对根没有意义。按字面实现，可能把根的默认属性（weight、无约束、无收起）盖到存活的保留像素叶上。
- **如何核实**：`probe2.ts` 的 A2、A3；`grid.ts:176-189` 对根的处理。
- **建议改法**：写成按轴的规则表。
  - 展平时，沿 B 的父分支主轴，下限取 `max(B 声明的下限, 叶沿同一根轴自己的下限)`，上限取交集。
  - 叶沿 B 主轴的约束保留（它变成交叉轴约束）。
  - 收起：B 有就用 B 的。B 没有而叶有、且叶沿的轴不再是主轴时，丢弃并写进文档，或让 `removeLeaf` 在存活者带 `collapsed: true` 时先展开它。
  - 根展平不继承。
  - `splitLeaf` 只继承沿父分支主轴的分量，目标叶保留自己的约束。
  - 测试补：叶带交叉轴最小值的展平、根展平、存活者原先收起。

### 3. 按比例分的叶跨分支移动时带着源分支的权重，目标分支单位不同就吞掉兄弟；计划只处理“缺意图”
- **严重程度**：重要
- **类别**：边界、被破坏的既有约定
- **位置**：plan.md 第 22、25 行（“单位由宿主定，同一分支里一致即可”）；`grid.ts:708-723`（`moveLeaf` 用叶原来的 `size[main]`）
- **现象**：竖向分支 L（p 600、q 400）与 R（r 1、s 1），把 p 移进 R。
  - 旧实现：p 600，r、s 被 `shiftSiblings` 写成 0（探针 A5）。
  - 计划后（兄弟不动，p 保持 600）：容器高 600 时 p 598、r 1、s 1。
  - 两种都坏，计划把第二种当成正确。
- **为什么是问题**：计划自己说单位在分支内一致，那么移动就是换单位，叶带过去的数就不对了。`moveLeaf` 是三个入口里唯一没有宿主能给意图的，却只处理了“缺意图”（跨方向时为 0）。
- **如何核实**：`probe2.ts` 的 A5。
- **建议改法**：`moveLeaf` 到别的分支时，按比例分的叶一律视同新叶，取目标分支按比例分兄弟的平均意图，没有取 1。保留像素的叶沿同方向移动则保持 px。同分支内换序不动。测试补“600 移进 1、1 的分支，呈现三等分”。

### 4. 跨方向移动把保留像素的叶改成按比例分，来回移动不可逆；根因是 `sizing` 只有一个值却只管父分支主轴
- **严重程度**：重要
- **类别**：被破坏的既有约定、上游选择
- **位置**：plan.md 第 25 行；`grid-types.ts:22-26`（`sizing` 单值）；`grid.ts:662-724`
- **现象**：现在 nav（保留像素 188、150 到 300、可收起）移进竖向分支后仍是 `sizing: "fixed"`、`size.height = 0`，即 0 高的保留像素面板（探针 A6）。计划改成“按比例分、取平均份额”，后果如下。
  - nav 再移回横向分支时，`size.width` 还是 188，但 `sizing` 已是 weight，188 被当权重，和 main 的 600 比只有约 24%。保留像素的性质不可逆地丢了。
  - 它的收起策略 `restoreSize: 188` 是宽度像素，在新方向里没有意义。
  - 约束的宽度分量在竖向分支里变成交叉轴约束，沿用没问题，但计划没说。
- **为什么是问题 / 上游选择**：t51 的 API 审查第 4 条已指出根因：`sizing` 只有一个值，节点换父分支方向它就不对。计划在补丁层（改 `sizing`）解决，没有把“按轴记 `sizing` 与意图”这个上游候选连同代价交给开发者，也没有提“失败”这个更保守的选项。
- **如何核实**：`probe2.ts` 的 A6。
- **建议改法**：交开发者选。
  - 候选 1：保留像素的叶跨方向 `moveLeaf` 返回失败（`invalid-argument`，`field` 新增一项），宿主先 `removeLeaf` 再 `addLeaf` 自己给 `size`。
  - 候选 2：`moveLeaf` 加可选的 `size`。
  - 候选 3：`sizing` 按轴存（类型与快照都要改，跨方向移动本来少，代价偏大）。
  - 不要静默改 `sizing`。

### 5. `splitLeaf` 把收起策略搬到新分支：拆收起中的叶会把新叶一起收没，宿主按叶 id 读写收起状态的入口失效
- **严重程度**：重要
- **类别**：被破坏的既有约定、边界
- **位置**：plan.md 第 31 行；`grid.ts:610-632`；`grid.ts:502-520`（`setCollapsed` 要求节点有 `collapse`）；Spec 输出 147、148、149
- **现象**：
  - 收起成 0 的叶 c 被水平拆开：现在 c 仍收起、新叶 n 占 333（容器 1000，探针 A4）。按计划，收起搬到新分支 `p`，`p` 收起成 0，n 与 c 都是 0 宽，新叶看不见。
  - 搬走以后，`grid.setCollapsed("nav", …)`、`host.setCollapsed("nav", …)` 对原叶 id 返回 `not-collapsible`，`grid.find("nav").collapse` 变成 undefined。Spec 输出 148 写“宿主要跨会话保存，从 `setCollapsed` 的结果或 `find(id)` 读”，nb-story 的 `book-grid.ts` 也按叶 id（nav、drawer）给收起状态。
- **为什么是问题**：计划的意思是“收起的是这一块”，但“这一块”的 id 变了，叶 id 上所有收起入口同时换了对象。`splitLeaf` 返回值只有 `{ok: true}`，宿主拿不到新的收起位置。
- **如何核实**：`probe2.ts` 的 A4。
- **建议改法**：目标叶收起中时 `splitLeaf` 失败，或先让它展开。或者收起策略不搬，留在叶上、新分支不带，写进文档。若坚持搬到分支，文档写明新位置的 id，并补“拆收起中的叶”“拆后 `setCollapsed(叶 id)`”两个用例。

### 6. `createGrid` 的“缺意图”核对没有失败通道，判据与合法的 0 冲突
- **严重程度**：重要
- **类别**：接口与合同、边界
- **位置**：plan.md 第 24 行；`grid.ts:97-99`（`createGrid` 返回 `Grid`）；`WorkbenchSurface.vue:123`（`computed(() => createGrid(...))`）；`layout-project.ts:237-240`；`layout-drop.test.ts:269,465`（`barThickness: () => 0`）
- **现象**：
  - **没有失败通道**。`createGrid` 返回 `Grid<T>`，“同样核对”只能抛异常。工作台在 `computed` 里每次重建网格，抛出会让渲染挂掉。这也违背 Spec 失败 1（返回诊断，不抛未处理异常）。计划没说抛不抛。
  - **判据冲突**。计划对保留像素的新叶写“没给主轴意图”，对按比例分的写“省略或主轴为 0”。保留像素的合法 0 存在：`barThickness: () => 0` 时 `layout-project` 给的保留像素叶 `size` 就是 0（探针 A9，`bar` 0 宽，布局正常）。按“主轴为 0”判会让这些树建不出来。
  - **只能判缺省**。`GridLeafInput.size` 是 `{width, height}` 两个分量一起给，README 起步写 `{width: 188, height: 0}`。在竖向分支里主轴分量就是 0，“忘了”与“要 0”分不开。
  - **三个入口不一致**。快照恢复路径（`resolveRef` 返回 `sizing: "fixed"`，快照里主轴为 0）没有核对。
  - **命名**。计划写“新失败码（`wrong-sizing`、`size-missing`）”，但 `size-missing` 是 `invalid-argument` 的 `field`，不是码。`GridFailureParams` 里 `invalid-argument` 的 `field` 联合要加一项并带 `id`，Spec 失败 5 表要改 `invalid-argument` 行，不是加码表行。
- **建议改法**：核对只看 `size === undefined`。`createGrid` 不抛，缺省时发 `layout().issues` 的诊断或开发警告（诊断码与失败码不相交）。只有 `addLeaf` 返回失败。`size-missing` 写成 `invalid-argument` 的 `field`。

### 7. `host.update` 的签名、异常与“没变也打断手势”
- **严重程度**：重要
- **类别**：接口与合同、边界
- **位置**：plan.md 第 44 到 47 行；`useGridHost.ts:118-124`（`setCollapsed`“没变不打断”）；`useGridLayout.ts:78-99`（`publish` 总是递增版本）
- **现象**：
  - **签名**。写 `update(edit: (grid) => R): R`，同一段又说没有网格时返回 `not-ready` 的失败。返回类型应是 `R | GridFailure<"not-ready">`。
  - **异常**。回调抛出，或前几步成功后一步失败，计划只说“返回后只发布一次”。抛异常时发布被跳过，树已改了一半、宿主没通知，正是 `update` 要消灭的“忘了通知”。需要 `try/finally` 发布，异常继续抛。
  - **多步没有回滚**。单步原子，多步不是：“结构操作改完又 `setSize` 失败”留下半成品。计划没说，应写成文档里的已知行为。
  - **没变也打断手势**。全部 `changed: false` 或全部失败，也递增版本，进行中的手势被取消。`setCollapsed` 的规则是“没变不打断”（Spec 输出 149）。`update` 不知道有没有变，除非 `Grid` 有变更计数（见第 8 条）。
  - **重入与 `onApplied`**。回调里再调 `host.setCollapsed`、`host.invalidate` 会各发布一次，与“只发布一次”矛盾。`onApplied` 不触发（同 `setCollapsed`），宿主要存的偏好得自己存，计划没写进文档。
- **建议改法**：签名、`try/finally`、没变不打断、重入行为都写进输出 156。用例补抛出、失败、没变三条。

### 8. 开发检查“意图与最近一次发布的布局对不上”在现有数据里没有可比的东西，且覆盖有限
- **严重程度**：建议
- **类别**：可行性
- **位置**：plan.md 第 46 行；`useGridHost.ts:96-106`（`onGestureStart`）；`useGridLayout.ts:62-63`（`publishedExtent` 私有）
- **现象**：意图是权重或像素，布局是呈现 px，不能直接比。可行办法是手势开始时用同一容器重算 `grid.layout(extent)`，与已发布布局逐节点比。这要求 `useGridHost` 拿到发布时的容器尺寸，现在它是 `useGridLayout` 里私有的。
  - **工作台每次重建网格**：`grid` 变了，`useGridLayout` 的 watch 立即重算发布，手势开始时一致，不误报。
  - **漏报一**：宿主改了树但没改变呈现（例如 `setSize` 改的是被约束夹住的保留像素叶），不报。
  - **漏报二**：宿主改了树但之后没再拖，根本不报。计划要消灭的症状“画面不变没有诊断”，只在下一次拖动才有提示，那时 `resizeBranches` 多半已因 `stale-baseline` 被拒。
- **建议改法**：给 `Grid` 加内部变更计数器（每个变更入口递增，不进快照、不从入口导出）。`useGridLayout.publish` 记下发布时的值，手势开始时比较。比重算布局便宜，也能实现第 7 条“没变不打断”。

### 9. `resize` 仍然把固定兄弟压到最小并写回意图，“导航 188 变 150”还能由它复现
- **严重程度**：重要
- **类别**：被破坏的既有约定（范围是作者定的，可以质疑）
- **位置**：plan.md 第 22 行（“`resize` 的语义本 Task 不改”）；`grid.ts:162-173`、`:263-267`
- **现象**：探针 A8：`[nav 保留像素 188（150 到 300）, a 300（最小 100）, b 300（最小 100）]`，`resize("a", "width", 400)` 返回 `applied: 238`（请求 400），意图变成 nav 150、a 538、b 100。nav 的 188 被永久写成 150，容器再变大也不回 188。这就是开发者决定要消灭的现象，只是入口换成了 `resize`。计划把 `shiftSiblings` 留给 `resize`，等于把 bug 留在公开入口里。
- **为什么是问题**：开发者的决定写的是“原地增删不压固定栏”，没提 `resize`。但 `grid.md` 把 `resize` 写成意图单位的单节点入口，t45 一类宿主很可能同时用它。有了 `setSize` 之后，`resize` 对保留像素兄弟的合理行为是不动。
- **如何核实**：`probe2.ts` 的 A8。
- **建议改法**：`shiftSiblings` 的候选集合改用 `sharesByWeight` 同一判据（`sizing !== "fixed"`、范围可分），不改保留像素的兄弟。`resize` 的 `applied` 会变小，要有测试。或者至少在 `grid.md` 与 README 写明“`resize` 会把保留像素的兄弟压到最小并改意图”，不要写“语义不变”了事。

### 10. `setSize` 的细节：不夹、`restoreSize` 低于 `collapsedSize`、返回值、码表形状
- **严重程度**：建议
- **类别**：接口与合同
- **位置**：plan.md 第 36 到 43 行；`grid.ts:493-500`；`grid-geometry.ts:300-310`（`normCollapse` 保证 `restoreSize ≥ collapsedSize`）；`grid-failure.ts:16-34`
- **现象**：
  - **`restoreSize` 过小**。收起中的节点同步 `restoreSize` 时，`setSize(10)` 而 `collapsedSize` 为 44，会写出低于 `collapsedSize` 的值。`collapsedRemembering` 用 `Math.max(collapse.collapsedSize, …)` 防着，这里要同样取最大。
  - **不夹**。`setSize("drawer", 200)` 而最小宽 280，意图存 200，返回 `changed: true`；`resize` 会夹（`shiftNode`）。约束是静态数据，不读布局也能夹，或在返回里给存下的值。
  - **返回值**。`{ok: true, changed, collapse?}` 没有存下的 `size`，宿主看不到有效值（API 审查第 8 条已提）。
  - **参数形状**。现有 `not-finite` 的 `field: "size"` 带 `side`、`id`，`invalid-argument` 的 `size-negative` 也带 `side`。`setSize` 没有基线与目标两侧，计划只写“加这两种形状”，要明确是两个新联合成员，不要让 `side` 变可选。
  - **失败 6**。`GridCommitFailureCode` 是 `GridFailureCode | …`，`wrong-sizing` 进了提交码的类型，但 `resizeBranches` 不会产生它。类型上无害，文档要说一句。
  - **Spec 输出 148**（谁记 `restoreSize`）要加一句 `setSize`，计划的 Spec 改动段没列。
- **建议改法**：以上逐条补进输出 155。

### 11. 平均份额的候选集合没有写成谓词
- **严重程度**：建议
- **类别**：边界
- **位置**：plan.md 第 23 行
- **现象**（探针 P3、P4）：
  - 兄弟 1、1、1：新叶取 1，四块各 250，对。300、700：取 500，新叶 333.3，对（取平均的叶总拿到 `1/(n+1)` 的权重份额，`n` 是候选个数）。

  - 收起的兄弟（意图保留展开值）：参与也无妨（c 意图 300、呈现 0，a、b、n 各 333.3），但文字没写。
