### 1. “只发新增”的键含连续变化的数值参数，窄窗口里每个像素都是新键，“每次布局都发”照旧
- **严重程度**：阻断；**类别**：正确性
- **位置**：计划“只发新增”的判据第 1、3 条，诊断表的 `unabsorbed-space {cause, ids, rest}`、`no-room-to-restore {id, available}`；`grid-geometry.ts:195`、`:533`
- **现象**：键是“`code` 加按键名排序后的 `params`”，`params` 含数值。`unabsorbed-space` 的 `rest` 是 `target - total`（533）或 `space - rigidTotal - fixedTotal`（195），随容器尺寸连续变。真实运行时实验：两个最大 100px 的叶、容器宽 400、399、398、397，issues 依次是“可用空间 400 有 200 未被吸收”“399 有 199”“398 有 198”“397 有 197”，`rest` 每个像素都不同。按计划，`useGridLayout.recompute` 把键集与上一次重算比，每个像素的键都是新的，于是每次重算都发，与今天一样。`ids` 也在键里：窗口变窄时受影响的节点越来越多，每多一个就是新键。
- **为什么是问题**：计划的验收（“窄窗口连续重算，持续的诊断只发一次”）对只有 `ids` 的 `over-constrained` 成立，对 `unabsorbed-space` 与带 `available` 的诊断不成立。用例若只用 `over-constrained` 写，测试会过，产品里最常见的“拖窗口”仍逐帧发。这是提案体验 10 与第一轮第 3 条要治的问题，第 2 稿只治了一半。
- **如何核实**：`bun run exp/rest-varies.ts`；读 `grid-geometry.ts:533`、`useGridLayout.ts:60-79`。
- **建议改法**：键只取身份类参数（`code`、`cause`、`id`/`ids`），度量类参数（`rest`、`available`、`actual`、`min`、`max`）不进键；诊断表把每个 `params` 字段标成“键”或“度量”。`ids` 进不进键也要定：进键则集合变化算新增（写明窗口变窄时会多发几次）；不进键则只按 `code` 加 `cause` 去重，更接近提案“一条一个码”。规则写进输出 139，并补一条用 `unabsorbed-space`、容器逐像素变化的用例。

### 2. 同一个码在 `issues` 事件里既是“提交被拒（已回滚）”又是“求解降级（没回滚）”，宿主无法区分
- **严重程度**：重要；**类别**：不变量
- **位置**：计划“L1 的两个出口”、L0 码表 298 行、诊断表 `not-collapsible`；`grid.ts:298`、`sash-drag.ts:178`
- **现象**：`NestedGrid` 的 `issues` 事件类型是 `GridIssue<GridIssueCode | GridCommitFailureCode | "not-published">`。`GridCommitFailureCode` 含全部 L0 失败码，`GridIssueCode` 含诊断码，两边都有 `not-collapsible`：提交被拒（`grid.ts:298`，`params: {id, branch}`，手势已回滚）与预览期诊断（`sash-drag.ts:178`，`params: {id}`，手势继续、只是不能折叠）同码不同形、不同后果，却在同一个事件流里。事件元素又没有“这是失败还是诊断”的字段，宿主只能按码集合猜。同类的还有 `GridFailureCode` 与 `GridRestoreFailureCode` 共用的 `limit-exceeded`、`duplicate-id`，`params` 形状不同（前者有 `actual`，后者没有）。
- **为什么是问题**：计划定的是“码集合开放、宿主按码写界面文字”，同一个码两种语义，宿主的 `errors.not-collapsible` 文案没法同时对；`switch` 在 `not-collapsible` 分支里读 `params.branch` 会在诊断那一支读到 `undefined`。第 1 轮的审查与第 2 稿都没有处理，因为第 2 稿只补了 `not-published`、`notify-failed`，没检查两个联合的交集。
- **如何核实**：`rg "not-collapsible"` 在计划里出现于 L0 码表与诊断表；读 `sash-drag.ts:176-179`。
- **建议改法**：二选一：给诊断码改名（`no-collapse-policy`，与 `no-room-to-collapse` 对称），使 `GridFailureCode` 与 `GridIssueCode` 不相交，并在计划里加一句“两个联合不相交”，写一个类型级测试（`Extract<GridFailureCode, GridIssueCode>` 为 `never`）；或给 `GridIssue` 加 `kind: "failure" | "diagnostic"`。前者更简单。

### 3. 快照恢复的码表漏了 `grid-snapshot.ts:209`：根是未解析的叶子时整体失败，没有码
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“L0 快照恢复”；`grid-snapshot.ts:139-142`、`:204-210`
- **现象**：计划列了 15 处：`invalid-snapshot` 86、111、116、131、136、164、168、173、200，`unsupported-version` 90、93，`duplicate-id` 120，`limit-exceeded` 107、126、177。代码里失败的出口是 16 处，`:209` “布局快照的根节点无法恢复”没有归属：根是叶子且 `resolveRef` 返回 null 时，`convert` 返回 null（141 行只往 `dropped` 推一条）、`failure` 为空，走到 209 整体失败，`dropped` 里有那条 ref。这正是 nested-grid 失败 3、4 的边界：格式没问题，只因引用全丢而整体失败。

- **如何核实**：`grid.restore({version: 2, root: {kind: "leaf", id: "a", ref: "ghost", size: {width: 1, height: 1}}}, () => null)`：`ok:false`、`dropped: [{ref: "ghost"}]`、原因“根节点无法恢复”。读 `grid-snapshot.ts:139-142`、`:204-210`。
- **建议改法**：加一个码（如 `unresolved-root`，不并入 `invalid-snapshot`），失败结果照常带 `dropped`；失败 7 与 `grid.test.ts` 补一条。

### 4. “同码同 cause 合成一条”没定义合成后的 `params`；`allocateSashPanels` 删掉 `context` 后分支 id 与轴也丢了
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“L0、L1 诊断”的表与“一次求解里同码同 `cause` 合成一条”、“`allocateSashPanels` 的 `context` 删掉”；`grid-geometry.ts:135-205`、`:415-421`、`:486`、`:502`、`:507`、`:533`
- **现象**：
  - 表里 `ids` 在不同 `cause` 下指的东西不同：`leaf-min` 是叶子 id，`sash-overflow`、`cross-min` 是分支 id，`min-total`、`fixed-overflow`、`no-share` 是 `allocateSashPanels` 的面板（一个分支的各子节点）id，`range-overflow`（`sash-drag.ts:247`）没有分支 id、只有面板。`allocateSashPanels` 内部只知道面板，不知道所在分支，`context`（`分支 ${branch.id} 的 ${axis}`，`allocateAxis` 传入）是今天唯一带分支与轴的地方；计划删掉它，只说“涉及的面板 id 进 `ids`”，于是 `min-total` 的 `ids` 是子节点 id，看不出是哪个分支、哪根轴。合成更糟：两个分支的 `min-total` 合成一条，`ids` 是两组子节点的并集，分组丢了。
  - `axis?` 没有合成规则：宽、高两根轴上的 `leaf-min` 同码同 `cause`，合成后 `axis` 取谁。`unabsorbed-space` 的 `rest`、`conflicting-bounds` 的 `{id, axis, min, max}` 没有 `ids`，“合成”对它们怎么做也没写。
  - `min-total` 的 `ids` 是全体面板还是只含 `low > 0` 的面板，实施者自己定。
  - 好的一面：仓库内 `allocateSashPanels` 只有 `allocateAxis` 会传第三、第四个参数（`grid-geometry.ts:420`；`grid.ts:290`、`:345` 传 `[]`，`Splitter.vue`、`sash-drag.ts` 不传），删 `context` 在仓库内没有别的调用方要改。
- **为什么是问题**：输出 140 与 `grid-geometry.test.ts` 的新用例（“`ids` 按顺序列全”）按字面会各人各写；合成后的诊断对宿主（要拼界面文字的人）信息量很低，而这正是码加 `params` 设计的唯一目的。
- **如何核实**：读 `grid-geometry.ts:415-421`（`allocateAxis` 是 `context` 唯一携带分支与轴的调用点）、`:486-507`、`:533`。
- **建议改法**：每个 `cause` 一行，写明 `ids` 放哪一类 id、`axis` 是否有；`allocateAxis` 给 `allocateSashPanels` 传一个内部的 `scope`（分支 id、轴），`min-total`、`fixed-overflow`、`no-share` 的 `params` 带 `branch` 与 `axis`；合成键用 `(code, cause, axis)`，不同轴不合并；`conflicting-bounds` 不参与合成（它已按 `id` 加 `axis` 去重，`grid-geometry.ts:356`），`rest` 这类度量不合并、取最后一次的值。

### 6. “只发新增”的作用域写得不全：`useGridLayout` 遇到空布局怎么办、`gesture-update` 载荷算不算、键盘手势没有诊断、出口从 `watch` 换成同步回调的行为变化
- **严重程度**：重要；**类别**：正确性
- **位置**：计划“只发新增”的判据、“scope 不再保留累积列表”；`useGridLayout.ts:60-79`、`useSashGesture.ts:238-243`、`:321-330`、`:456-508`、`NestedGrid.vue:483-494`、`:561-565`
- **现象**：
  - `recompute` 有一条空布局分支（`useGridLayout.ts:63-69`：`grid`/`extent` 为 null 或零尺寸），不产生诊断。“和上一次重算的键集比”在这条分支里要不要清空，计划没写：不清空，则面板隐藏再显示后持续的诊断不再发；清空，则隐藏再显示就重发。`WorkbenchSurface` 的 `grid` 是 `computed(() => createGrid(...))`（每次 projection 变化都换），`contextKey` 变化也走同一条 `watch`，键集该不该随它们重置同样没写。
  - `gesture-update` 的载荷 `GridGesturePreview.issues`（`grid-gesture.ts:197-244`）是每帧重算的完整快照，不是“新增”，计划只改了它的类型。输出 139 写成“`issues` 只发新增”后，这个字段是否豁免要写明，否则会有人给它也加去重。
  - 键盘手势根本不推诊断：`pushIssues` 只在 `finish()`（拒绝）与 `flush()`（指针每帧）调用（`useSashGesture.ts:291`、`:329`），`keydown` 路径（`:478-507`）里 `toggleCollapsed()`、`update()`、`jump()` 得到的 `session.issues` 从不发。今天 Enter 展开没有空间时没有任何诊断。计划写“手势里同一个键只发一次”，没写键盘算不算，也没把“键盘没有诊断”记为已知限制或补上。
  - 出口从 `watch(() => scope.issues)`（Vue 调度，一个 tick 合成一次、带上累积的最近 8 条）换成同步的 `onIssues(batch)`：指针松手时 `flush()` 与 `finish()` 在同一个同步段里各推一批，今天发一个事件，新做法发两个；`finish()` 里 `pushIssues`（`:291`）在 `active.value = new Set()`、`refreshHoverAfterGesture()` 之前，若宿主给的 `onIssues` 抛出，这两步被跳过（`active` 永远亮着）；今天走 Vue 调度，不会打断收尾。`NestedGrid` 自己用的是 Vue 的 `emit`（不抛），但 `SashGestureOptions.onIssues` 是公开选项。
- **为什么是问题**：这是计划唯一的行为变化，却有几个边界让实施者各自决定；其中 `finish()` 里的抛出会留下“分隔线一直亮着”的状态，与 `useGridLayout` 对 `onApplied` 的做法（`try/catch`，`:105-112`）不一致。
- **如何核实**：读上面几处；`rg "pushIssues" packages/nb-layout/src/vue/useSashGesture.ts` 只有 3 处命中（定义、291、329）。
- **建议改法**：输出 139 补三句：空布局分支清空键集（隐藏后再显示算重新出现）；`gesture-update.issues` 是状态快照、不去重；键盘手势暂不发诊断（已知限制，写进 Spec 边界）。`onIssues` 调用包 `try/catch` 或挪到收尾之后（`finish()` 末尾），并在计划里写明一次松手可能发两个事件、不合并。

- **严重程度**：建议；**类别**：代码质量
- **位置**：`grid-geometry.ts:117-126`（`index.ts:52` 公开导出）、`grid-snapshot.ts:37`、`useGridMotion.ts:77`、`:142`、`:163`
- **现象**：`collapsePolicyProblem` 返回 `string | null`，三种中文文字，只被 nb-layout 自己的测试用，应用里没人调用；`serializeTree` 对非字符串 ref 抛 `TypeError`，文字是中文；`useGridMotion` 的 `MotionDecision.swapSkipped?: string`（`:77`、`:142`）要随 `planSwap` 改成 `GridIssue`，计划只写了 `onSwapSkipped`。目标是“一种形状”，通用库里留着中文 `string | null` 的公开函数与中文异常没有说法。
- **建议改法**：计划写一句取舍：`collapsePolicyProblem` 要么改成返回 `GridIssue | null`（只有测试在用，成本很小），要么在“不做”里写明它是校验辅助不是失败结果；`serializeTree` 的 `TypeError` 文字改英文或列入“不做”；`swapSkipped` 并入第 2 片的改动列表。

### 10. `params` 没有类型，码表的 34 行只靠测试守；`duplicate-id`（L0）与 `id-taken`（L2）是同一件事的两个名字
- **严重程度**：建议；**类别**：代码质量
- **位置**：计划“共同形状”、L0 表、L2 `id-taken`；`grid-types.ts`
- **现象**：`params` 是 `Readonly<Record<string, GridParamValue>>`，计划里逐处定的字段（`{id, with}`、`{field, value}`……）编译器不管。拼错 `expected` 为 `expect`、漏 `id`，类型检查都过，只有写了断言 `params` 的用例才会失败；而 617、632 两处按计划不写用例。宿主读 `params.id` 也要自己断言成 `string`。再者，L0 的 `duplicate-id {id, with}` 与 L2 的 `id-taken {id, kind}` 是同一概念，`GridFailure` 又是两层共用的形状，宿主要同时认两个名字；L2 的 `not-found`、`limit-exceeded` 却与 L0 同名同形，规则不一致。
- **建议改法**：码已经是字面量联合，顺手写一张 `GridFailureParams`（码 → 参数形状）的映射类型，构造失败的辅助函数 `fail(code, message, params)` 按它检查，表就成了类型；L2 的 `id-taken` 改叫 `duplicate-id`（用 `kind` 区分），或在计划里写明为什么不统一。

### 11. 个别 `params` 的取值仍有歧义
- **严重程度**：建议；**类别**：正确性
- **位置**：L0 表 232、264、280、503、506；L1 `stale-context`、`stale-revision`
- **现象**：
  - 232 与 264 都是 `wrong-axis {id, orientation}`，232 的 `id` 是被调整的节点、`orientation` 是它**父分支**的方向（`grid.ts:232`），264 的 `id` 是分支自己、`orientation` 是它自己的方向（`:264`）；同一个字段在两处指不同的对象。
  - 280：`field: "size"` 没说是基线还是目标里的值（`change.baseline`、`change.target`）；“先判非有限、再判负数”若按子节点循环，今天的顺序是逐个子节点各判四个条件（`:276-281`），若实施成“先全体判非有限、再全体判负数”，同一输入的失败子节点与码会变，计划说“失败与否不变”，码与 `id` 却会变。
  - 503、506：`value` 是调用方传来的运行期任意值（类型声明是联合，运行期可以是对象），`String(...)` 的要求只写了“非有限数写成字符串”，这两处不是数，要明说一律 `String(value)`。
  - `stale-context`、`stale-revision` 的 `{expected, actual}` 没说哪边是提交带的、哪边是宿主当前的（代码里 `commit.contextKey` 对 `context`，`commit.revision` 对 `revision.value`）。
- **建议改法**：表里 232 加 `parent`（`{id, parent, orientation}`，`orientation` 明确是父分支）；280 写成“逐个子节点，先判非有限再判负数”并加 `side: "baseline" 或 "target"`；503、506 注明 `String(...)`；`expected` 是宿主当前值、`actual` 是提交带来的。

### 12. 和提案不同的不止一处，待确认清单只列了一处
- **严重程度**：建议；**类别**：文档
- **位置**：计划“和提案不同的一处（待开发者追认）”；提案“错误与诊断一种形状”
- **现象**：除了计划列的“提交码”一处，第 2 稿还有这些与提案文字不一致的改动，计划没记进决策记录：
  - 提案（体验 10）写“合并成一条一个码”，计划改成“同码同 `cause` 合成一条”，一个窗口里 `over-constrained` 最多有 6 条（提案没有 `cause`）；
  - 提案的候选表 229“根节点没有父分支”归 `wrong-node-kind`、617/632“目标父节点已不存在”归 `stale-baseline`，计划改成 `invalid-argument`、`not-found`（第一轮审查认可，但提案文字没改）；
  - 提案的 `GridLayoutResult.issues` 是 `{code, message}[]`，计划加了 `params`；
  - 提案“累计列表由宿主自己积累”，计划新增“键、三种作用域”的判据与 `scope.issues` 删除，这是公开面的破坏性变化，提案“影响”里没有。
- **建议改法**：决策记录追加一条，把这几项一并列为“t34 与提案不同”，待开发者追认；其中前两项的取舍理由已经在第一轮审查里，直接引用。
