# w00026 t50 设计审查报告（计划第 1 稿）

审查对象：`.agents/works/w00026-layout-package/tasks/t50-example-app/plan.md`。只读；实验在 `/tmp/claude-1000/review-t50-design/scratch/`。

## 发现

### 1（重要，验证）示例 tsconfig 照发布冒烟写成 `types: []`：在 TypeScript 6 下 `import "@notnotype/nb-layout/style.css"` 报 TS2882
- 位置：计划“关键设计”的 `tsconfig.json`（“同发布冒烟的空宿主”）与 `src/main.ts`；`scripts/release/pack-smoke.ts` 的 `smokeLayoutHost` 的 tsconfig
- 现象：仓库里 `packages/nb-layout/node_modules/typescript` 是 6.0.3，根 `node_modules/typescript` 与冒烟装的是 5.9.3，包的对等依赖写 `^5.4.0 || ^6.0.0`。实验（scratch/ts6）：同一份 tsconfig（`strict`、`skipLibCheck:false`、`types:[]`）、同一行样式导入，5.9.3 退出 0，6.0.3 报 `TS2882: Cannot find module or type declarations for side-effect import of '@notnotype/nb-layout/style.css'`（TS 6 起副作用导入默认要求有声明）。把 `types` 改成 `["vite/client"]`，5.9 与 6.0 都通过；含 .vue 的完整实验（scratch/ex，vue-tsc 5.9.3）加 `vite/client` 后也通过，没有新错误。
- 为什么是问题：示例是“第三方把目录拷走就能跑”的参照。计划让示例 `package.json` 的 `typescript` 与冒烟一致（^5.9.3），所以示例自己不会挂；但 README 起步和示例教的就是这行导入，用 TS 6 的第三方照抄会挂，而冒烟与示例都因为固定在 5.9 看不出来。两处 `types: []` 把这个空缺盖住了。
- 如何核实：`node packages/nb-layout/node_modules/typescript/lib/tsc.js -p <含该导入、types:[] 的 tsconfig>`（见 scratch/ts6）。
- 建议：示例 tsconfig 写 `"types": ["vite/client"]`（Vite 项目的标准写法，示例要教这个），并在 tsconfig 或示例 README 里说明原因；顺带把冒烟空宿主同样改了，或另开一条记进 Work“后续”：冒烟只测 TS 5.9，对等依赖声明的 TS 6 没有任何一处验证。

### 2（重要，遗漏/失败路径）关掉最后一个编组后只剩侧栏，且存了档就永远回不来
- 位置：计划 `model.ts` 的 `closeTab`（“编组空了就 `removeLeaf`”）、`App.vue` 的叶插槽；Context 里没有“空状态”
- 现象：实验 scratch/t1.ts：根 `[explorer(fixed 240), A, B]`，`removeLeaf("A")`、`removeLeaf("B")` 都返回 `ok:true`，之后快照的根节点是单个 `explorer` 叶（根分支被它唯一的孩子替换，这是 grid.md“已知限制·展平”写的行为），1000 宽下 `explorer` 占满 1000x600、`fixed` 与最小宽度都不起作用。再删 explorer 则根是空分支。
- 为什么是问题：计划没有“新建标签”或“新建编组”的入口（示例只有关、拖、拆），所以关掉全部标签后界面只剩一个满屏侧栏、没有任何办法把编组找回来；`closeTab` 后立刻 `save()`，下次载入读到的就是这个单叶快照（`restore` 成功、`dropped` 为空，不触发“读失败保留原件”）。验收表里“关掉编组的最后一个标签”只测一个编组的情形。
- 如何核实：`bun /tmp/claude-1000/review-t50-design/scratch/t1.ts`（用真实 `createGrid`）。
- 建议：二选一并写进计划与验收表：（a）最后一个编组的最后一个标签不给关（关闭按钮停用或 `closeTab` 返回失败，并说明原因）；（b）编组全空时显示 `empty` 状态加一个“新建标签”按钮，或重置回缺省布局。无论哪种，`load()` 对“没有任何编组叶”的快照也要判为结构坏。顺带：侧栏叶永远是根的直接孩子，要保证它在展平后还是 `sizing: "fixed"`（展平会丢分支策略）。

### 3（重要，接口/失败路径）新建编组与分支的 id 没有生成规则；载入存档后再拆分会撞 id，失败被当成“被拒”静默吞掉
- 位置：计划 `splitWithTab`（`splitLeaf` 出新编组，`branchId` 与新叶 id 由谁给没写）；“存取”一行的验收
- 现象：实验 scratch/t2.ts：`splitLeaf` 遇到已有 id 返回 `{ok:false, code:"duplicate-id", message:"Node id already exists: C"}`、树不变。计划把拒绝统一描述成“被拒，例如 `limit-exceeded`，就什么都不改”，没有通道告诉用户。
- 为什么是问题：新编组 id 若用模块内计数器（`group-4`、`split-5` 这类最自然的写法），页面重新载入后计数器从头数，而存档里已有同名 id，于是“载入后再拆分一次”必然在第一次拆分就静默失败。计划的存取用例只重新载入、断言还原，不会再操作，所以这个缺陷从示例过测试，到第三方照抄后才暴露。`GridFailure` 有 `code`，计划没写怎样显示。
- 如何核实：t2.ts 的 `dup` 一行；`grid.md` “拆分叶”写明 id 由宿主保证唯一。
- 建议：规定 id 的来源（从现存的最大序号续、或 `crypto.randomUUID()`），写进 `model.ts` 的注释；`splitWithTab` 把 `GridFailure` 原样返回，App 层把 `limit-exceeded`、`duplicate-id` 在界面上显示出来（见下一条的落点反馈）；验收表加“载入后再拆分一次”。

### 4（重要，时序）“`activate` 冻结几何”与过渡并存：量到的是过渡中间的矩形；计划没有 `settleMotion`、`dragging`、`structure`
- 位置：计划 `App.vue` 的 `useDragSession` 一段（“`activate` 冻结这一场的几何”）
- 现象：`live-drag-session.md` 第 47 行明写：“宿主的 `activate` 先于 `settleMotion`，它在 `activate` 里量到的矩形可能是过渡中间的”。`NestedGrid.md` 的过渡一节：关标签、拆分、收起侧栏都会触发 `--nb-layout-motion-layout`（缺省 470ms）的布局过渡；过渡中外框带 `data-moving`。`drag-session.md` 的 `structure?()` 与 `NestedGrid` 的 `dragging` 属性计划都没提。
- 为什么是问题：落点指示手感下布局整场不变，冻结几何本来没有必要；一旦冻结，起拖落在上一次拆分或收起的过渡里（用户连续操作、e2e 紧接着第二次拖）就把中间值冻成这一场的事实，指示线与半区整场错位，而 `resolve` 的 `top`（指针下的真实元素）读的是现场，两者不一致时指示线与实际落点对不上。另外标签条横向滚动（标签多了）时冻结的成员矩形也过期；`scroll` 缺省是 `reevaluate`，它重新判定读的仍是冻结值。窗口缩放时会话只排一次重新判定（`resized` 即 `schedule`），读的仍是冻结值；`structure` 变了才会整场取消。
- 如何核实：读 `live-drag-session.md` 第 47 行、`drag-session.md` 选项表的 `structure?`、`NestedGrid.md` 的 `dragging`；浏览器里需要 e2e，我没跑（规则不允许）。
- 建议：落点指示手感下不冻结，`resolve` 里现读各标签条与 `data-content-leaf` 的矩形（一场里只有几个元素）；若坚持冻结，`activate` 里先调 `NestedGrid` 的 `settleMotion()`，`structure` 返回 `String(host.revision.value)` 让布局变了就整场取消，`NestedGrid` 绑 `:dragging="state !== null"`。e2e 的拖动辅助函数在起拖前要等 `[data-moving]` 消失。

### 5（重要，验收映射）“存取”用例的操作顺序会掩盖“收起没存”；计划漏了几个关键的行为用例
- 位置：计划“验收映射”表第 8 行（“拖宽侧栏、收起侧栏、拆分之后重新载入”）；“关键设计”里 `useGridHost({onApplied: save})` 与“侧栏收起按钮走 `host.setCollapsed`”
- 现象：`useGridHost.md`“收起与展开”：`host.setCollapsed` “不触发 `onApplied`”，结果直接交回，要存盘“就存它”。计划只在 `onApplied` 上接了 `save`，收起按钮那一条没写要不要存；而验收用例把“收起”放在“拆分”之前，拆分之后的 `save()` 会把收起状态一并写进去，“收起没存”的缺陷在这条用例里是看不出来的。
- 另外对照计划自己描述的行为，验收表没有这些用例：
  1. 同一编组内重排标签（`drop.ts` 写了“拖到自己标签条上是重排”）；插到自己前面或后面一位（插入位等于原位）该是无动作，计划没写 `actionKey` 返回 null 还是照常提交，没有用例。
  2. 只有一个标签的编组拖到自己的边或自己的正文：计划写了“不是落点”，没有用例（这是否定断言，要先变异）。
  3. 拖到编组上边或下边的竖向拆分：只测了右边缘。
  4. 拆分被拒（`limit-exceeded`、`duplicate-id`）：计划写了“什么都不改”，没有用例。实验（scratch/t2.ts）里交替拆分 13 次就会 `limit-exceeded: Nesting too deep: 17 > 16`，e2e 不必真的拖 13 次，用存档种一个 15 层的快照（`restore` 允许 17 层）再拖一次即可。
  5. 载入存档之后再拆分一次（见第 3 条）。
  6. 关掉全部标签（见第 2 条）。
  7. 拖到侧栏或分隔线上（无落点，不提交）。
- 如何核实：读验收表与上面几个文档；t2.ts 的 `rejected at 13`。
- 建议：存取用例分成每一步各自重新载入一次（先收起、重新载入、断言收起；再拆分……）；`setCollapsed` 之后显式 `save()`，并在 `model.ts` 的注释写“为什么 `onApplied` 管不到它”；补上面的用例。另外所有拖动用例在松手前都要等 `[data-drop-feedback]` 出现：会话按 `actionKey` 与“最后显示的动作”相同才提交（`drag-gesture.ts` 的 `drop`），帧还没发布就松手会是 `no-action`，是测试自己造成的偶发。

### 6（建议，公开面）命中“编组正文”靠什么没写：内容层的内容与叶外框不是父子；应使用已公开的 `data-leaf`、`data-content-leaf`
- 位置：计划 `drop.ts`（“编组正文上：`resolveGridEdgeDrop` 判四边”）与 `TabBar.vue`（“带 `data-tab`、`data-group`”）
- 现象：计划把 `NestedGrid` 的内容放在内容层（`leave: "retain"` 需要），按 `NestedGrid.md`，内容层的项是叶外框的兄弟元素，不在叶插槽的 DOM 子树里，叶插槽里只放面板头（标签条）。所以 `top.closest("[data-group]")` 只会命中标签条，指针在正文上方时拿不到编组 id。
- 为什么是问题：计划只给标签条标了 `data-group`，正文的命中没有任何说明；照字面实现要么从冻结矩形里点在矩形内查（见第 4 条的过期问题），要么现场发现 DOM 对不上再补。README 的标记表（“宿主与测试可以依赖下面这些”）有 `data-content-leaf`（内容项的外层，值是所属叶 id）与 `data-leaf`，不需要库新增。
- 如何核实：`NestedGrid.md` “公开的标记与变量”表；`NestedGrid.md`“布局”一节“叶的内容放进内容层时 `leaf` 插槽只放面板头”。
- 建议：写进计划：正文命中用 `top.closest("[data-content-leaf]")?.dataset.contentLeaf`（停放的、`data-content-leaving` 的内容不接指针，不会命中）；编组的“正文矩形”用该元素的现场矩形，不另算 `leaf 矩形减标签条高度`。

### 7（重要，依赖的机制）`leave: "retain"` 的两条使用约束计划没写：留住的内容与面板头是冻结的插槽调用；`insetTop` 要与标签条高度同源
- 位置：计划 `App.vue` 第二条（“内容项标 `leave: "retain"`……关掉最后一个标签时编组缩回去再卸载”）与 `model.ts` 的 `closeTab`（“编组空了就 `removeLeaf`”，数据同步删除）
- 现象与依据：
  - `NestedGrid.md`“过渡”：被留住的内容项“冻住的只是这一项的插槽调用”，里面的组件照常按响应式更新；在宿主已删数据之后，交给子组件的插槽在子组件渲染里再调，按 key 查已删数据会抛错（库会补一条 `… is kept until the transition ends`）；“删数据与改 `contents`、改树要在同一次刷新里”。离开的叶的面板头（`leaf` 插槽）同样停在最后一次渲染。
  - 计划 `closeTab` 同步删 `groups` 里的编组，叶插槽用 `node.ref` 查编组、内容插槽用 `contentKey` 查标签：写成 `<Panel>{{ tabs[contentKey].title }}</Panel>` 这类（把正文放进带插槽的壳组件里），关最后一个标签的那一帧就会在控制台抛错。这正是“关最后一个标签”用例要走的路径，e2e 的 `pageerror` 监听会抓到，但示例教学代码本身就会错。
  - `GridContentInput.insetTop` 是叶顶部留给面板头的 px，库不量（体验审查第 16 条：“insetTop 是我写死的 32px，要与标签条 CSS 高度一致，库不量”）。计划只写了标签条和内容层，没有说 `insetTop` 与标签条高度从哪里同源（一个常数同时进 CSS 变量与 `contents`）。标签条一旦换行、字号放大，内容就盖到标签条上。
- 建议：计划写明：内容插槽只把当前项交给一个以属性接收的组件（`NestedGrid.md` 给了 `CardBody` 的写法），`closeTab` 保留被删编组的对象引用到过渡结束或让插槽按“查不到就渲染空”写；`TAB_BAR_HEIGHT` 一个常数同时用于样式和 `insetTop`，并在注释里写原因。

### 8（建议，模型）计划没有说模型的响应式：`groups` 是普通 `Map`，网格在 `shallowRef` 里原地改，谁触发标签条与内容的重渲染
- 位置：计划 `model.ts` 的“状态”与“操作”
- 现象：网格实例要放 `shallowRef`（`useGridHost.md`），原地改树后靠 `host.invalidate()` 递增 `revision` 通知；`groups`（标签与选中项）不在这条通知链里。`activate`（切标签）不改树，也不会调 `invalidate`；`contents` 的 `active` 字段、标签条的选中样式都依赖它。
- 为什么是问题：写成普通 `Map` 而不包 `reactive`/`shallowReactive`，切标签不会刷新；写成 `reactive(new Map())` 又会让 `Grid` 以外的结构被深度代理（计划里 `groups` 的值是对象，`tabs: string[]` 被代理没问题，但“被删编组的对象还要留到过渡结束”这件事与代理交织，见上一条）。
- 建议：在计划里写明用 `reactive` 的模型，`contents` 与标签条都从它派生，并把 `host.revision.value` 读进 `contents` 的 computed，让结构变化与数据变化走同一次刷新（`NestedGrid.md`要求）。

### 9（建议，库的已知限制未进“绕过的库空缺”）编组没有最小尺寸策略；同向拆分的嵌套、展平与深度上限在示例里的后果没写
- 位置：计划“绕过的库空缺”五条；`model.ts` 的“解析函数按 `ref` 查策略表（侧栏的 `sizing`、`minimumSize`、`collapse`）”
- 现象：
  - 策略表只有侧栏。`splitLeaf` 新建的编组叶、缺省布局里的三个编组都没有 `minimumSize`；README“约定”第一条本来就警告“只返回 `{ref}` 的话……没有任何诊断”。示例里每拆一次编组就对半，十来次后是几十像素的窄条，标签条放不下，布局没有任何 `over-constrained` 提示（没有最小尺寸就没有可违反的约束）。新建叶若在拆分时带了最小尺寸、载入时的策略表又没有，重新载入前后同一个编组的约束不同。
  - 体验审查第 9 条（同向拆分造出同向嵌套分支，连续拆越来越深，`splitLeaf` 拆 `fixed` 的叶会丢掉 `fixed`）与 README 的承诺（提案第 296 行：写明“16 层深度上限对拖拽拆分的实际影响”）没有出现在计划里：scratch/t2.ts 实测根 `[explorer, A, B]` 拆 B 的右边得到 `b1[B, C]`（嵌套的同向分支），交替拆 13 次被拒；`removeLeaf("C")` 把 `b1` 展平，B 拿到分支的 size 300，这个例子里宽度顺理成章由 B 接手、没有跳动；展平会丢掉分支自己的约束与收起策略（grid.md“已知限制”），所以示例里分支不能挂策略，这一点要写明。这些是库的已知行为，示例是最该演示“怎么绕”的地方，计划却只列了五条没有这一类。
- 建议：编组的策略（`minimumSize`）用同一个函数给建叶、缺省布局与载入时的解析函数；“绕过的库空缺”补上“同向嵌套与展平”并在示例 README 里写一句后果；拆分被拒要在界面上显示原因（见第 5 条）。

### 10（建议，读失败）`load()` 的“结构坏”只覆盖 `restore` 的结果，快照与编组表之间的一致性没人核对
- 位置：计划 `model.ts` 的 `save()`/`load()`（“网格快照、编组表、侧栏收起状态，带格式版本”）
- 现象：`restore` 只核对快照自己的结构，并按解析函数把不认识的 `ref` 报进 `dropped`。存档里还有第二份数据：编组表。下面这些存档，`restore` 都会返回 `ok:true`、`dropped` 为空：叶有对应的表项但某标签 id 同时出现在两个编组；编组表里有的编组没有叶（它的标签悄悄丢了，没有任何提示）；`active` 不在 `tabs` 里；编组 `tabs` 为空；没有任何编组叶（第 2 条）。
- 为什么是问题：这是示例要教的“读失败保留原件”的主体，计划的判据只写了“版本不认识、结构坏、`restore` 失败或 `dropped` 非空”，“结构坏”没有定义；验收表只测了一种坏法（存档被改坏，没写怎么改坏）。`localStorage` 不可用（隐私模式、被沙箱的 iframe 抛 `SecurityError`）时 `save()` 抛出还会落进 `onApplied` 的 `notify-failed`，计划也没提。
- 建议：写出 `validate(model)` 的判据清单（上面五条加 JSON 解析失败与读写抛错），用例至少覆盖“JSON 坏”“编组表缺编组”“标签重复”三种。

### 11（建议，仓库接线）`test:e2e` 与 `e2e/tsconfig.json` 要的依赖没列；示例的任何改动会牵出四个下游包的全套测试
- 位置：计划“`packages/nb-layout`（脚本与测试）”
- 现象：
  - nb-layout 的 `package.json` 没有 `@playwright/test`（nb-story、neuro-book 各自声明 `^1.62.1`），也没有 `@types/node`（nb-story 的 `e2e/tsconfig.json` 是 `types: ["node"]`）。根 `node_modules` 提升了 `@playwright/test`，所以本机能跑，但计划没有写加 devDependency、`bun install` 与 `bun.lock` 的变动。`test-affected.ts` 里 `bun.lock` 有改动算“全量选择”，这次提交会让 CI 的 `test:affected` 选中全部包。

### 14（建议，落点反馈）被拒的拆分可以事先知道，计划让用户白拖一次
