## 1. 重要｜读档判据：桌面与 IDE 的树结构与模式一致性没列，坏档会让示例崩溃而不是回缺省
- 位置：desktop“存取”（“平铺的窗与树里的叶对不上（树里有不是平铺窗的叶，或平铺窗不在树里）；同一侧两扇平铺”）；ide“存取”；“三个示例共用的检查”；两个验收表“存取”行。
- 现象：标签编组的判据里有结构项（“侧栏叶不是恰好一个”“树里没有编组叶”“编组表与叶一一对应”），这是它自己的，“判据同标签编组”继承不过来。两个新示例按字面只多出几条：窗 id、矩形有限、平铺窗与叶对应、同侧两扇（desktop）；工具窗 id、重复、`shown` 在条上、展开的区有按钮（ide）。没写的：
  1. desktop 树里 `desktop`、`dock` 各恰好一个、根竖向、`dock` 在末位、窗叶只出现在桌面叶同层的横向分支里。另：计划写的“树里有不是平铺窗的叶”照字面，`desktop`、`dock` 两块叶本身就满足，缺省布局的存档会被判坏；要写成“除 `desktop`、`dock` 外的叶都必须是平铺窗”。
  2. desktop 窗的模式是 `tiled-left` 而树里它在桌面叶的右边（或反过来）：模式与树是两个真相源，“最小化回原侧”“同侧换下旧的”按模式找，树却是另一个样子。
  3. desktop 模式字段的取值不在六个值里、“最小化之前的模式”缺失或不合法、层叠次序不是四个 id 的排列（重复、缺）。
  4. ide 树里 `editor`、三条、三区缺失或重复；区的收起状态表里有不是区 id 的键。
- 实测（ide3.ts）：把快照里的 `desktop` 叶删掉再 `restore`，返回 `{ok:true, dropped:[], clamped:[]}`，`find("desktop")` 是 `null`。库只校验结构合法，不知道示例要哪几块叶；`dropped` 只在 `resolveRef` 过滤时才有。示例里读 `deskLeaf` 的地方（`deskClamp`、最大化、试平铺）会拿到 `null`。
- 为什么是问题：计划验收“存档坏时用缺省布局、原件在备份键”，坏档的定义决定它做不做得到。子代理照列出的几条写，手改过的存档（缺叶、模式与树不一致）会在读档后的第一次渲染抛错，原件也不在备份里。每条坏法都要各一例（计划自己写了），列不全就测不全。
- 如何核实：`bun scratch/ide3.ts` 最后一行；对照 plan.md 第 236 行与第 257 行的判据原文。
- 建议改法：判据补一个“树的锚点”段：desktop 写上面 1 到 3，ide 写上面 4；并写明模式与树不一致按坏档，不悄悄修。ide 的树结构是静态的（只有尺寸变），也可以不存树快照、只存各区的 `size`，从缺省树建、读档时 `setSize`，坏档面就小得多；这是取舍，交实施时定，但要写进计划。

## 2. 建议｜桌面：落点判定有三处计划没写死，e2e 与实现各写各的
- 位置：desktop“移动先试拖动会话”的“落点”“松手”两条。
- 现象与依据：
  1. **边缘带含不含“越过”**：“指针在桌面叶左缘或右缘 20px 以内”。左边已有平铺窗时桌面叶左缘不是 0（r2 的 d1.ts：x=722），窗被夹在桌面叶里，指针却可以继续往左进到平铺窗上方。字面读“以内”是 `|x - 左缘| <= 20`，指针越过 20px 之后落点从 `tile:left` 掉回 `move`：用户一路往左拖，反馈在 702 处消失，松手时窗只是贴着平铺窗放下。验收“只剩一扇时再贴同一侧换下它”靠指针停在带内，量不出这点。
  2. **`blocked:*` 松手窗去哪**：`actionKey` 为 `null` 时 `drop()` 走 `no-action`（drag-gesture.ts 第 321 到 334 行），计划写的 `onEnd` 非提交分支是 `placeFloat(id, null)` 加去掉 `gesture`，窗瞬间（没有过渡）回到按下前的位置，不是停在松手处。`move` 是停在松手处，两者不一致，计划没写这是有意的；验收只写“松手不平铺”，没写窗在哪。
  3. **坐标系**：会话给的 `point` 是视口坐标；`placeGrid` 给的桌面叶、新叶矩形是相对网格根；`DropFeedbackOverlay` 要的是视口坐标（Teleport 到 body、固定定位，DropFeedbackOverlay.md）。计划在“夹取”里写了桌面叶相对网格根，在“落点”里写“按起拖时量到的桌面叶矩形”判边缘、“反馈画的就是新叶的矩形”，都没写加减 `origin()`。承载盒在页面原点时两者相等，测不出；示例要给第三方抄，嵌进别的页面就错位。
  4. **拖动中视口变了**：会话的 `resized()` 只是重新排一次判定（`resized: schedule`，drag-gesture.ts 第 482 行），不取消这一场。标签编组靠 `structure: () => String(host.revision.value)` 在网格重发布局时取消整场（App.vue 的注释写了原因）；桌面一节没写 `structure`，而边缘带用的是起拖时量到的桌面叶矩形、起点矩形是起拖时画着的矩形，视口一变这两样都过期，窗相对偏移会跳。（从代码推断，未在浏览器里验证。）
- 如何核实：1、2、4 读 drag-gesture.ts 与计划原文；3 读 DropFeedbackOverlay.md 的“布局与交互”与 NestedGrid.md 的 `origin()`。
- 建议改法：1 写成 `x <= 左缘 + 20`（右侧对称），含越过；2 二选一写明：blocked 松手按 `move` 处理（写进夹过的矩形）或明说“回到按下前”并在验收里断言；3 加一句“边缘判定与反馈矩形都在视口坐标里算：网格根坐标加 `origin()`”；4 照标签编组加 `structure: () => String(host.revision.value)`（ide 的拖按钮同理）。

## 3. 建议｜`placeGrid` 要四个参数，计划两处只写三个；模型层没有 `devicePixelRatio`
- 位置：desktop“夹取与缩放”的 `deskClamp`（“`placeGrid(root, layout, extent)` 里桌面叶那一块”）与“试平铺”（“用 `placeGrid` 取新叶的矩形”）；摩擦记录第 25 条同样写成三个参数。
- 现象：`placeGrid(node, layout, extent, dpr)`（grid-rects.ts 第 323 行）第四个是设备像素比；`NestedGrid` 自己用的是 `useDevicePixelRatio` 的值（NestedGrid.vue 第 156、177 行）。计划要在 bun 里测 `deskClamp`、试平铺（模型层，没有 `window`）。
- 为什么是问题：子代理照三个参数写类型检查过不了，改了之后又有两种做法：模型函数里读 `globalThis.devicePixelRatio`（bun 测试里没有，要么抛、要么 NaN；`placeGrid` 对非法值退成 1，测试默默过了），或者当参数传入。前者让模型层碰全局、后者要全链路传。取整口径与库不一致时，`deskClamp` 的结果与画面差一个像素，验收的 ±1 容差吃掉它。
- 如何核实：读 grid-rects.ts 第 323 行与 NestedGrid.vue 第 156 行与第 177 行。
- 建议改法：写明模型的几何函数把 `dpr` 当参数，界面层传 `window.devicePixelRatio`（与库同值）；摩擦记录第 25 条的参数写全，并记“宿主要自己再算一遍时还得知道库用的 dpr”。

## 4. 建议｜移动与缩放写回记录的是“夹过的矩形”，窗被夹小之后的宽高会永久写进 `floatRect`
- 位置：desktop“移动先试拖动会话”（`activate` 记“此刻画着的矩形”、`commit` “写回”）、“夹取与缩放”（`move` 的位置过 `deskClamp` 后写回；“记录的 `floatRect` 不改”）。
- 现象：画出来的矩形是 `deskClamp(floatRect)`，窗比桌面大时宽高被缩过。拖动以这个矩形为起点，加偏移再夹，整块写回，宽高也写回去了；键盘 `move` 同理（计划写“位置过 `deskClamp` 后写回”，没说只写位置）。库自己在 `FloatWindowHandles` 的 `move` 注释里写了“大小要留给宿主：窗被夹着时 `rect` 是夹过的，不能写回”。
- 为什么是问题：用户在窄视口里挪一下被夹小的窗，视口变回来时窗不再回原来的大小，违反计划自己写的“视口变回来窗回原处”；验收“视口缩小后…视口变回来窗回原处”只测没动过的窗，测不出。
- 如何核实：读 FloatWindowHandles.vue 的 `move` 注释与计划原文；模型测试里造一个比桌面大的窗，对它做一次移动，看 `floatRect.width`。
- 建议改法：写明移动（指针与键盘）只写 `x`、`y`，宽高保持记录里的；缩放的 `commit` 本来就改宽高，写回求交后的矩形即可。

## 5. 建议｜“按下浮动窗的任何地方抬升”没写挂在哪，挂在窗上收不到缩放带
- 位置：desktop“状态与操作”第二条（层叠）。
- 现象：手柄在 `float-chrome` 插槽里，渲染成网格根的直接子元素（NestedGrid.vue 第 630 到 632 行），不在窗的内容里；`FloatWindowHandles` 的 `pointerdown` 还 `stopPropagation`（第 61 行）。窗组件上挂冒泡的 `@pointerdown`，按在缩放带上（边 6px、角 10×6）收不到：窗在后面被缩放，不抬升。计划写的是“任何地方”。
- 为什么是问题：字面做不到“任何地方”；e2e “按下后面的窗它到最上面”按窗正文点，测不出这一块。
- 如何核实：读 NestedGrid.vue 与 FloatWindowHandles.vue 的上述行。
- 建议改法：写明在承载盒上挂捕获阶段的 `pointerdown`，用 `closest("[data-content-leaf], [data-float-chrome]")` 取窗 id（两个标记库都写了）；顺带知道：`float-chrome` 这一层是按 `floats` 数组序渲染的（第 631 行 `v-for`），抬升会搬这一层的 DOM 节点，库说明的“只改层级，不搬节点”只对外框与内容成立（从代码推断，未在浏览器里验证）。
- 这个改法引出一个要验的风险：按到后面那扇窗的缩放手柄时，先抬升（改 `floats` 次序），手柄随后 `setPointerCapture` 并 `focus`，被抬升那一扇的手柄层节点会被 Vue 搬动；在 Chrome 里搬动已连接的节点会解除指针捕获，走 `@lostpointercapture="finish(false)"`，这次缩放就被取消。按代码，捕获阶段的监听返回后，Vue 的渲染在微任务里先于手柄自己的 `pointerdown` 处理完成（原生事件的监听之间会跑微任务），搬动发生在捕获之前，应无事；但这依赖这个先后，没有在浏览器里验证。验收加一行“按后面那扇窗的缩放手柄：它到最上面，且这次缩放照常进行”；退路是缩放期间不抬升，等 `commit` 或 `preview(null)` 之后再抬。

## 6. 建议｜IDE（与桌面）缺省数值有几处缺口：编辑区无最小尺寸、`sashSize` 没给、收起时 `shown` 清不清
- 位置：ide“树”“区与缺省”“工具窗”；desktop“树”。
- 现象：
  1. **编辑区没有最小尺寸**。三区都给了最小值，`center`、`editor` 与三条没给。实测（ide4.ts，按计划的树）：宽 400 时 `editor` 只剩 68 像素宽、`issues` 为空；宽 700 时 368。左区最小 160 的限制没用在编辑区上，`center` 能被两侧的区挤到 0（保留像素的区没有最大值）。编辑区的标签条、`textarea` 在这个宽度上装不下，“最大化编辑区”也救不了拖分隔线时的这种状态。
  2. **新一节没给 `sashSize`**，也没写继承标签编组的 4（plan.md 第 48 行），缺省是 0（分隔线不占位、不可交互，grid.md“建树”）。验收里依赖它的：ide 的“条旁分隔线拖不动”“拖左区分隔线改宽”、已知限制里的“那条缝”；desktop 的“底栏上面那条分隔线拖不动”（零宽的线本来就拖不动，用例空过）、三块平分 477/478/477（r2 实测按 4px）。子代理自己挑一个数，条旁线给 0 最顺手，这时 `sashDisabled` 与对应用例都空转。
  3. **收起时 `shown` 清不清**：“点按钮 已显示它→收起这个区”没写 `shown` 此后是什么。存档判据写了“收起的区 `shown` 可为空也可保留”，是两种都放过；“拖分隔线展开、`shown` 为空的设成第一个”暗示收起不清。模型测试“点按钮的三种结果”要断言 `shown`，子代理会各自定。
- 如何核实：`bun scratch/ide4.ts`（1）；读 grid.md 开头“建树”（2）。
- 建议改法：1 给 `center`（或 `editor`）一个最小尺寸，例如 240×120；2 写明 `sashSize` 一律 4（或写 ide 的条旁线也是 4，用例才有东西可测）；3 写一句“收起不改 `shown`，下次展开仍显示它”。

## 7. 建议｜验收表仍缺几行，其中一行决定实现怎么写；变异清单没列项（第二轮第 8 条没处理到位）

## 该记进摩擦记录的库问题（审查中发现，未在 friction.md 里）
1. **`restoreSize` 对按钮路径不起作用**（实测，ide1.ts、ide3.ts）：快照里意图 400、策略 `restoreSize` 给 333，读档后 `setCollapsed(false)` 展开 400；`restoreSize` 只服务分隔线上的 Enter 与拖动。IDE 示例“`restoreSize` 另存”“重新载入后再收起展开也一样”的按钮用例，即使不存 `restoreSize` 也过；变异检查别把“去掉存 `restoreSize`”算成按钮用例的变异。说明（grid.md）有写，但宿主很难想到两种展开用两个数。
2. **会话的 `commit` 在 `onEnd` 之后调**（drag-gesture.ts `finish` 第 260 到 264 行）：宿主要在 `commit` 里清手势标记、在 `onEnd` 里只清非提交的情形；说明没写这个顺序。会话的 `resolve` 里写 DOM（`placeFloat`）说明里允许，但“`resolve` 不改布局”与“放下时、滚动时也调”要一起读才懂。
3. **会话默认起拖门槛 6px**（`DRAG_GESTURE_DEFAULTS`），手接指针的常见写法是 3 到 4px：同一个窗两种手感；触摸要 200ms 长按（计划写 `touch-action: none` 对触摸不够，要长按才起拖），示例只测指针。
4. **`FloatWindowHandles` 的 `commit` 把夹过的 `rect` 当起点**，宿主写回会把夹过的尺寸写进记录；只有 `move` 的注释提醒了这点（第 4 条）。
5. **`float-chrome` 层的 DOM 序跟 `floats` 数组走**，抬升会搬手柄层的节点（被聚焦的把手会丢焦点；与按在手柄上同时抬升的先后见第 5 条的风险），说明“只改层级，不搬节点”只对外框与内容成立（从代码推断）。
6. **`sashDisabled` 是渲染时调的函数**，它读的状态要是响应式的才会随按钮增减重算；`NestedGrid.md` 只写了类型，没写这条（从代码推断：`useSashPresentation.ts` 第 125 行在渲染里调它）。
7. **`placeGrid` 的 `dpr` 参数**：宿主要自己再算一遍摆放时得知道库用的值（并入第 25 条）。
