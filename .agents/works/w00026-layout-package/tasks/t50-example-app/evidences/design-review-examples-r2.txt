# t50 第 5 稿新增一节（桌面与 IDE）设计审查，第二轮

审查对象：plan.md “第 5 稿”一节（第 6 稿）。依据：库说明与实现（NestedGrid.vue、grid-rects.ts、grid-motion.ts、grid.ts）、第一轮报告、标签编组示例（worktree）。实验文件在 scratch/（d1.ts、c1.ts 等，用库源码在 bun 里跑；没有跑 e2e 与开发服务）。标“从代码推断”的没有在浏览器里验证。

## 1. 重要｜桌面：`clampFloatRect` 没有原点、也不认“比桌面大的窗”；计划写“夹进桌面那块叶的矩形”照字面做不对
- 位置：desktop“移动”“夹取”“缩放”（`clampFloatRect` 夹进桌面那块叶的矩形）；“最大化”（矩形取桌面那块叶的矩形）。
- 现象：库的 `clampFloatRect(rect, extent, keep)` 只收 `extent`（宽高），夹在 `[0, extent]` 里，没有原点参数，且会同时把窗的宽高缩到 `extent`。计划里的“桌面那块叶”在左侧有平铺窗时原点不是 0（d1.ts 实测：左平铺后桌面叶 `x=722`）。计划没写 `keep` 取什么。
- 实测（c1.ts，桌面叶 718×840）：
  - 窗 x=300、宽 400，不平移原点直接夹：原样返回（x=300，其实落在左边那扇平铺窗里，不在桌面叶里）；
  - 窗宽 800（比桌面叶宽）、`keep` 取窗自己的大小 800×300：结果 `{x:-82, width:718}`，窗被推出左缘 82px；`keep` 取 `min(窗, 桌面)` 才得 `{x:0, width:718}`。
- 为什么是问题：计划把夹取写成现成的一步，但示例要自己做三件库没做的事：减去叶原点再加回来、把 `keep` 取成 `min(窗, 桌面叶)`、夹之后宽高已被缩。平铺之后验收“视口缩小后浮动窗都在桌面里”只测不平铺的情形时，这两个坑测不出来。
- 如何核实：`bun c1.ts`。
- 建议改法：计划写一个 `deskClamp(rect, deskLeafRect)`：`rel = {x: rect.x - leaf.x, y: rect.y - leaf.y, ...}`，`keep = {width: min(rect.width, leaf.width), height: min(rect.height, leaf.height)}`，夹完加回原点；整窗在桌面里就是这个函数；验收加“左侧有平铺窗时，浮动窗被夹到平铺窗右边”。摩擦记录第 14 条（`clampFloatRect` 没提）顺带写“没有原点、`keep` 的含义不显然”。

## 2. 重要｜桌面：缩放时预览不夹进桌面，松手后“夹过的只用来画”让窗跳一大截
- 位置：desktop“缩放”（`min` 240×160、`max` 桌面叶的大小；`preview` 时把显示矩形换成它给的）与“夹取”（显示用夹过的矩形）。
- 现象：`resizeFloatRect` 只限宽高（`max` 是大小，不是边界），从右下角往外拉时位置不动，右缘与下缘可以伸出桌面。计划预览不夹，`commit` 写回记录，下一次渲染显示矩形又被夹一遍。
- 实测（c2.ts，桌面 718×840，窗 x=500,y=600、240×160，右下角拖 +400,+400）：预览矩形 `{x:500,y:600,width:640,height:560}`，右缘 1140、下缘 1160（盖到底栏上）；松手后夹成 `{x:78,y:280,width:640,height:560}`：x 一下跳 422px，y 跳 320px。第一轮例一 5 只对“移动”补了拖动中夹取，缩放漏了。键盘缩放同理（`FloatWindowHandles` 的方向键 `commit` 也不考虑位置）。
- 为什么是问题：验收“拖右下角缩放，到最小尺寸停住”量不出这种跳；按计划写，缩放一用力就跳。
- 建议改法：计划写明预览与提交的矩形都先和桌面叶的矩形求交（裁掉伸出去的部分，向固定的那一边收，不是平移），再取整；`min` 仍是 240×160，求交后小于 `min` 时按 `min` 贴着桌面缘放。验收加“向桌面外拉大，预览与松手后矩形相同、右缘不超过桌面右缘”。
- 摩擦记录：`resizeFloatRect` 的 `max` 是大小不是边界，宿主要自己把位置夹进去；`FloatWindowHandles` 的 `max` 每个方向一样，装不下“剩余空间”。

## 3. 重要｜键盘监听放在“示例的根上”会在焦点落到 body 时失效：IDE 快捷键、桌面移动的 Escape 都受影响
- 位置：ide“快捷键”（“只在示例的根上听”）；desktop“移动”（“Escape 或丢了捕获”，没写在哪里听）。
- 现象：在不可聚焦的元素上按下鼠标（桌面的标题栏 `div`、IDE 里没有可聚焦内容的工具窗或编辑区），焦点落到 `body`，`keydown` 的目标是 `body`，冒泡不经过根元素，根上的监听收不到。库自己的缩放把手不受影响：`FloatWindowHandles` 在 `pointerdown` 里 `element.focus()`（`FloatWindowHandles.vue` 第 58 行），Esc 才有地方收；标题栏是示例自己的元素，没有这一步。NestedGrid 的外框与内容层没有 `tabindex`（只有两个哨兵 `span`），不会替它接焦点。
- 两处会照字面出错：
  1. 桌面：按下标题栏、过了门槛起拖，按 Esc 不取消（目标是 body）。
  2. IDE：Alt+数字关掉正在显示的工具窗，而焦点在它里面：内容停放后 `inert`，焦点掉到 body，之后的 Alt+数字没人收；点一下编辑区的非输入区域也一样。验收“Alt+数字开关工具窗”若在一个用例里连按几次，第二次就可能空过或挂。
- 如何核实：真浏览器里按下非聚焦元素后读 `document.activeElement`（应为 body）；e2e 里点标题栏后 `page.keyboard.press("Escape")`。
- 建议改法：计划写明二选一。a) 示例根加 `tabindex="-1"`，使点击落在根上；工具窗被收起或换走时示例自己把焦点给编辑区；b) 键盘监听挂在 `window` 上，只在拖动期间（桌面）装、结束拆，IDE 的快捷键按 `event.target` 是否在示例根内放行。库的拖动会话自己就是 b) 的做法：拖动期间在 `view`（window）上装 `keydown`、结束拆（`drag-session.ts` 第 185 行）。桌面的移动选 b)，IDE 的快捷键选 a) 或 b) 都行，但要写明。验收加“点一下工具窗里不可聚焦处再按 Esc / Alt+数字仍生效”。

## 4. 建议｜桌面：整窗移动自己接指针，漏了几项会话本来就管的事；“库没有现成的”这句没查 `useDragSession`
- 位置：desktop“移动”，摩擦记录第 11 条（“整窗移动没有现成的组合函数”）。
- 现象：计划手写 pointerdown、4px 门槛、捕获、Esc、丢捕获。没写的几项 `useDragSession` 都管：`touch-action: none`（触屏与笔在标题栏上按下后浏览器接管滚动，收到 `pointercancel`；`FloatWindowHandles` 的手柄自己带 `touch-action: none`，标题栏是示例自己的元素）；失焦、页面隐藏、窗口大小变化时取消（会话 `blur`、`visibilitychange`、`resize` 监听）；拖完吞掉后随的 click；指针坐标（视口）到网格根坐标要减 `origin()`（计划只在摩擦记录里提了 `placeFloat` 的偏移，没写这一步）。
- 会话的 `activate(source, keyboard, {pressed, point})` 给按下处与过门槛时的位置，`resolve({source, point})` 每次移动都调，可以在里面 `placeFloat`（`drag-session.md`“可以记下这一场的判定、在读完 DOM 之后写跟手的反馈”），落点返回“左缘/右缘/无”，`commit` 做平铺，`onEnd`（`no-action`）里写回矩形，`cancelled` 里 `placeFloat(null)`。这条路没有被计划否定过：例一 3 只在“标题栏吞按钮 click”和 `gesture` 时机上定的做法，没有比较“用会话”。
- 为什么是问题：示例要演示的就是“拖动会话怎么用”；手写 60 行再在摩擦记录里写“库没有现成的”，结论可能不成立。若用会话确实不合适（例如落点要每帧都改窗位置、会话的门槛不可配），那条摩擦记录应写出具体缺什么。
- 建议改法：切片 3 的说明二选一并写明：用 `useDragSession` 驱动窗的移动（首选，先试），或手写并列出上面几项（触摸、失焦、`origin()`、Esc 在 window 上听，见第 3 条）。摩擦记录第 11 条按实际结果改写。
- 另有未验证的一点（从代码推断）：计划在门槛后把 `gesture` 设成 `"move"`，外框与内容层随即 `pointer-events: none`，而捕获正落在外框里的标题栏上。按 Pointer Events 规范被捕获的元素继续收事件，Chrome 实际如此（凭记忆），但没有在浏览器里验证；若有问题，用会话（在 root 上捕获，root 不在窗里）可以避开。

## 5. 重要｜切片 3：两个新示例照这一节还写不出 e2e 与模型测试：缺几个决定，旧稿的残留名字还在
- 为什么是问题：子代理说明是它们唯一的输入；缺的决定要么让它们各自发明（键位、`data-drop`、缺省状态），要么让 e2e 辅助函数用不上（`data-drop`）。
- 如何核实：每条都是对 plan.md 第 5 稿一节与 `e2e/drag.ts`、前面标签编组部分的逐字对照（`grep -n 'data-drop' plan.md` 在 desktop 一段没有命中）。
- 位置：“三个示例共用的检查”“两个新示例的验收”“切片”第 3 项。
- 缺的决定（逐条核对过计划原文，没有写）：
  1. **desktop 没有 `data-drop` 之类的钩子**。共用的 `e2e/drag.ts` 的 `moveTo` 等外框的 `data-drop` 变成期望动作，`dragTo` 末尾断言 `[data-drop]` 数量为 0；子代理“只能用、不能改”。ide 写了“`data-drop` 写完整动作”，desktop 没写，验收“拖到左缘出现半屏反馈”无处可断言；共用段的否定断言规则也说“`data-drop` 的先正后否”。要写成：desktop 的外框在拖动中带 `data-drop`，值如 `tile:left`、`tile:right`、`none`，松手后移除；手接指针的移动也要写这个属性。
  2. **边缘判定的参照与反馈的形状**。“桌面左缘或右缘 20px 以内”：桌面叶还是网格根？左边已有平铺窗时桌面叶的左缘在 x=722（d1.ts 实测），窗被夹在桌面叶里，指针却能越过它进入平铺窗；越过去算不算在缘上？反馈写“半屏”，但已有一扇时第二扇只占三分之一（477px），反馈该画落下后的矩形。建议：参照桌面叶，“指针 x ≤ 左缘 + 20（含越过）”算左缘；反馈矩形取落下后的目标矩形（第一扇半屏，第二扇三分之一，换下旧窗时同旧窗的位置）。

  4. **缺省状态**：ide 哪些区缺省展开、各区缺省宽、`minimumSize`、`collapseThreshold` 与 `expandThreshold`、面板头高度（`insetTop`）；desktop 四扇窗的缺省矩形与层叠、窗内容。验收表里的断言（“左条按钮：区收着时展开”“拖左区分隔线改宽”）都依赖它。同一个子代理写代码和 e2e 时不会不一致，但主会话写的 README 一句话与审查要对照时没有依据；至少写缺省的展开状态。
  5. **模型层单元测试的清单**：新节只说“一个示例一个文件”，没有像标签编组那样列覆盖项（旧稿有）。两个示例里最该固定的正是状态机：desktop 的“模式 × 操作”（含平铺换位、最小化后原侧被占、第 4 条漏的几格）、ide 的 `shown` 规则（点按钮三态、跨条后来源区与目标区、拖走显示中的、最后一个）、存档坏的判据各一例。不列的话子代理各写各的，审查时也无从对照。
  6. **“例一 N”**的编号只在审查报告里有含义。子代理说明要么带上 `evidences/design-review-examples-r1.txt`，要么把括号去掉；现在给它“同标签编组”“例一 16”会让它去翻一份没给的文件。
  7. **新 worktree 的准备**：从切片 2 的提交开分支后要 `bun install`（前面加 `prox`，网络慢时），再 `bun scripts/examples.ts build <名字>` 构建自己的示例；e2e 只跑自己的文件，过滤写 `e2e/desktop.e2e`（Playwright 的过滤词按绝对路径匹配，worktree 目录名含同样的词就选中全部）；跑前 `cat /proc/loadavg`。计划只写了“看负载、只跑自己的文件”。
  8. **三块平分的断言**要带容差：1440 宽、两条 4px 分隔线，三块是 477、478、477（d1.ts），断言“相等”会挂，写 ±1。
- 旧稿残留（同一份 plan.md 里互相矛盾）：前面标签编组部分仍写 `src/examples.model.test.ts`（“脚本与测试”一节、验收映射“放不下”一行）与 `package.json` 的 `typecheck` 末尾加 `vue-tsc … examples/tabbed-panels/tsconfig.json`；新节写的是 `src/examples-tabbed-panels.test.ts` 与 `scripts/examples.ts`，实际 worktree 也是后者。子代理两处都会读到。把旧处改成新名，或在新节开头写“以本节为准的名字”并列出替换表。

## 6. 建议｜桌面：状态机里还剩几格没定，其中两格会让子代理各写各的
- 位置：desktop“窗”“最大化”“最小化”“贴边平铺”。
- 没定的（逐条核对计划原文）：

## 7. 建议｜桌面：平铺没有放不下的挡法，平铺叶没有最小尺寸
- 位置：desktop“树”（只给桌面叶最小 240×160）、“贴边平铺”“夹取”。
- 实测（d1.ts，三块并排，宽 500）：桌面叶钉在 240，两扇平铺窗各 126px，布局没有任何诊断（平铺叶没有 `minimumSize`）。窗的缩放下限是 240，平铺窗却可以窄到 126，标题栏的按钮放不下；同样的情形，标签编组示例有 `canSplit` 试拆挡住，这里没有。视口缩小后再载入带两扇平铺窗的存档，同样。
- 为什么是问题：窄视口或重载带平铺窗的存档时，窗的标题栏装不下按钮，且没有任何诊断，e2e 的“视口缩小”只测了不平铺。
- 如何核实：`bun d1.ts` 的 500 宽那一段。
- 建议改法：平铺叶也给 `minimumSize`（与窗的缩放下限同，240×160）；平铺前用“复制树试拆再读 `layout().issues` 有无 `over-constrained`”挡住（同 `canSplit`，摩擦记录第 1 条的绕法），挡住时反馈变淡、松手不平铺。验收加“窄视口里贴第二扇被挡”。

## 8. 建议｜两个示例：IDE 最大化期间的“拖按钮跨条”没定义；验收漏了几条计划里写了的行为
- 为什么是问题：第 1 条会造出看不见的状态变化，第 2 条那几处行为没有用例就没有变异检查，改坏了不知道。
- 如何核实：读计划两张验收表与 ide“编辑区”原文。
- 位置：ide“编辑区”（最大化期间只定了点按钮与 Alt+数字）、“两个新示例的验收”（desktop、ide 两张表）。
- 现象与建议：
  1. 最大化期间按钮仍可拖；跨条放下后目标区展开，被编辑区盖在下面，还原时区突然出现。定一种：最大化期间不起拖，或放下先还原最大化。
  2. 计划写了、验收表没有的行为（对照两张验收表原文）：ide 的条与旁边分隔线、下条上方分隔线不能拖（`sashDisabled`）；desktop 的底栏上方分隔线平铺前后都拖不动（第一轮第 8 条要保住的，验收表没有这一行）；没按钮的区用 Enter 也展不开；拖分隔线或 Enter 展开、收起后按钮选中态同步（只写了点按钮）；下条跨条（验收只写左、右条）；桌面键盘移动窗（`FloatWindowHandles` 的 `@move`）；最大化窗不画手柄。变异清单“写进各自的 e2e 文件头”但没列项，建议列：去掉底栏 `sashDisabled`、去掉无按钮区的 `sashDisabled`、去掉最大化期间的拦截、去掉门槛后才设 `gesture`、去掉拖动夹取、去掉 `onApplied` 里补 `shown`。

## 9. 建议｜桌面：标题栏按钮与手柄带的重叠没写
- 位置：desktop“窗”“缩放”。
- 现象：手柄层盖在内容上面（`float-chrome` 外层 z 比内容高一档），右缘手柄 6px 宽（上下各让 8px），右上角手柄 10×6px，上缘手柄 3px 高（`FloatWindowHandles.vue` 样式）。标题栏右端的关闭按钮若贴边，边上的几像素点到的是手柄，起的是缩放而不是关闭。验收“点标题栏上的按钮不起拖、按钮照常生效”用按钮中心点，量不出。
- 为什么是问题：按钮被手柄盖住时点到的是缩放，用户看到的是“关闭不灵”。
- 如何核实：读 `FloatWindowHandles.vue` 样式段（`.nb-float-handle--right` 等）；真浏览器里点按钮右缘 3px。
- 建议改法：写明标题栏按钮离右缘与上缘各留至少 8px；e2e 点按钮取中心。

## 10. 建议｜IDE：存档判据漏了“展开的区必须有按钮、`shown` 非空”，坏档会造出收不起的空区
- 位置：ide“存取”（“另加：工具窗 id 不认识、一个工具窗出现在两条上、`shown` 不在它那条上”）。
- 现象：第一轮例一 10 的不变量是“条上没有按钮的区不能是展开的”，计划正文保住它靠 `sashDisabled`（拖不开）和按钮逻辑，但读档判据里没列。一份存档里某区标为展开而它的条上没有按钮：区撑开着，分隔线被禁用，又没有按钮可点，用户无法收起。`shown` 为空而区展开同理（内容层没有 `active` 项，是一块空区）。库不管这些：快照里没有收起标记，收起状态由示例另存、示例自己恢复（i2.ts 实测：`serialize()` 只含结构与 `size`，没有 `collapsed`）。
- 为什么是问题：见现象，坏档造出用户收不起来的区，而计划把读失败的保护定为“同标签编组”。
- 如何核实：`bun i2.ts`（快照里没有 `collapsed`）；对照计划 ide“存取”原文。
- 建议改法：判据加两条，各配一个坏档用例：“展开的区所在的条上至少有一个按钮，且 `shown` 非空”“收起的区 `shown` 可为空也可保留”；不满足就按坏档处理（用缺省布局、原件进备份键），不要悄悄修。

## 11. 重要｜桌面：只剩一扇平铺窗时“换下旧的”或在对侧再贴，照计划字面写会找不到 `row`，窗两头都没有
- 位置：desktop“贴边平铺”（“第一扇：`splitLeaf` 桌面叶……第二扇……用 `addLeaf` 加到这个分支的头或尾……同一侧已有窗时，新贴上来的换下旧的……取消平铺、最小化、关闭平铺的窗都是 `removeLeaf`”）；验收只有“第三扇贴左缘换下第一扇”（两扇已在时）。
- 现象：计划按“第几扇”选操作（第一扇 split，第二扇 add）。只剩一扇平铺（`row` 下是 `[a, desktop]`）时，用户把 c 贴到同一侧换下 a：`removeLeaf(a)` 让 `row` 只剩一个孩子，库把它展平（`row` 从树里消失，桌面叶回到根下），之后照“第二扇用 `addLeaf` 到 `row`”写就是 `addLeaf("row", 0, c)`。
- 实测（d2.ts）：`removeLeaf("a")` 后 `g.find("row")` 是 `null`；`addLeaf("row", 0, c)` 返回 `{ok:false, code:"not-found", message:"Unknown parent id: row"}`，c 不在树里。若示例已先把 c 从 `floats` 去掉、再改树，这扇窗两头都没有；“最小化的平铺窗点回原来那一侧”在对侧没有别的平铺窗时同理（那一侧空着、`row` 早已展平，要 `splitLeaf`，不是 `addLeaf`）。
- 为什么是问题：计划把两条路径按“第几扇”分，实际要按“桌面叶的父分支此刻是不是横向分支（`row` 在不在）”分。第一轮例一 7 处理的是两扇都在时的形状，没覆盖只剩一扇的几条路径。
- 建议改法：计划写成判定规则：平铺一扇时先看桌面叶的父节点，是横向分支就 `addLeaf`（头或尾），否则 `splitLeaf`；“换下旧的”先 `removeLeaf` 旧的、再按此规则（`row` 可能已不在）；`row` 的 id 固定，展平后可复用。树操作成功之后才把窗从 `floats` 拿掉，失败时窗留在 `floats` 里并报原因。验收加“只剩一扇左平铺时，另一扇贴左缘换下它”“一扇右平铺最小化后再恢复到右侧”，模型测试各一例。

## 该记进摩擦记录的库问题（审查中发现）
1. `clampFloatRect`：没有原点参数（桌面叶不在网格左上角时要宿主平移）、会同时把窗的宽高缩到 `extent`、`keep` 取窗自己的大小时窗比区域大会被推出区域（c1.ts：x=-82）。现有第 14 条只记了“README 没提”，要加这一层。
2. `resizeFloatRect` 与 `FloatWindowHandles`：`max` 是尺寸上限不是边界，缩放的预览与提交不看位置，窗可伸出区域；`max` 对各方向相同，装不下“该方向上还剩多少空间”（c2.ts：预览右缘 1140 > 桌面 718，松手后宿主一夹跳 422px）。
3. 宿主要知道“桌面那块叶此刻的矩形”只能自己 `placeGrid(root, layout, extent, dpr)`，`dpr` 要与库内部（`useDevicePixelRatio`）一致；`NestedGrid` 没有交出摆放结果。候选：expose `placement()` 或在 `useGridHost` 里交出。
4. 整窗移动能否用 `useDragSession` 驱动（第 4 条）：实施后记结果；不能时写出缺什么。
5. 键盘：库的组件没有“根可聚焦、点击落在根上”的约定，宿主在示例根上听 `keydown` 时焦点落到 body 即失效（第 3 条）；`FloatWindowHandles` 自己在按下时 focus 手柄，标签条与示例自己的元素没有对等的东西。
6. `removeLeaf` 把只剩一个孩子的分支展平，分支 id 随之消失，宿主按 id 找父分支再 `addLeaf` 得到 `not-found`（第 11 条）；没有“在桌面叶旁加一个兄弟，不管它现在的父是什么形状”的操作。
7. 手柄带（右缘 6px、右上角 10×6、上缘 3px）是写死在样式里的常数，宿主标题栏按钮要自己避开；没有 prop 可调（第 9 条）。

## 未发现问题的方面（逐项核过）
- 第一轮第 1 条的树形：根竖向 `[主行, 下条]` 时 `maximized {leaf: editor, exclude: 三条}` 的结果是 editor `{x:32,y:0,w:1376,h:872}`，下条 `y=876` 在外面，左区或右区收成 0 宽也成立（i1.ts）。
- 第一轮第 7 条的平铺形状：先 `splitLeaf` 再 `addLeaf` 到分支头或尾，1440 宽下 718/718 → 477/478/477；两扇都在时的换侧（先 `removeLeaf` 再加）、拆掉一扇、拆光后桌面叶展平回根下，都符合计划（d1.ts）；只剩一扇的路径见第 11 条。底栏分隔线的 `before` 在平铺后确是分支 id `row`，`after === "dock"` 成立。
- 第一轮第 2 条的做法在代码层成立：浮动窗只有矩形变化不触发过渡（`settleFloatMoves`；过渡样式只挂在 `data-moving` 上），先发布矩形再下一拍改树时，窗从发布的矩形飞进平铺；树里的叶转浮动窗时同 key 的叶不会被当作“离开的叶”留下（`leavingPlacements` 跳过 `present`）。
- 抬升浮动窗只改 `floats` 次序：渲染序用 `stableOrder` 保持已有项的相对次序，DOM 节点不搬，正文里的 `textarea` 不会因抬升而失焦；层叠靠写在元素上的 `z-index`。

- IDE：禁用的分隔线不进命中候选（`useSashGesture` 的 `enabled`），收成 0 宽的区旁边被禁用的条边线不会挡住能拖的那条；快照不带收起状态、`size` 保留意图，计划另存收起状态与 `restoreSize` 的做法成立（i2.ts）。
