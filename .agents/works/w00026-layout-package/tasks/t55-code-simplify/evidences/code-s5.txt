[1] app 1 提交 5fa65a246（layout-drag.ts，净 -5 行）
  改了什么：previewOf、stripDrop、floatDrop、dropFor、answeredByEditor 多收一个调用方已量到的 DragGeometry（seen），不再各自 geometry(doc)；调用点 windowDrop、dropAt、fileDrop 把自己已有的 seen 传下去；dropAt 里键盘“浮动”区域那一支在调 floatDrop 前现取一次 geometry(doc)（原来 floatDrop 里取，条件 canFloat 同）。
  改前改后同输入同结果的逐点说明：
   - 判定是同步段，段内没有 DOM 写（resolveLayoutDrop、applyLayoutDrop、answeredByEditor 的 dropOutcome、live.sticky/unmoved 均只读），所以同一段里 geometry(doc) 重量与复用调用方那份得到同一份矩形；实时布局里 geometry(doc) 本来就是 frozen()（引擎量到的或 run.transient）即同一个对象。
   - stripDrop 原先在 applyLayoutDrop 之后量，现用调用方在更早量的；两者之间没有写。stripDrop 内的 `[...seen.panels, ...seen.floats]` 仍是未按键盘区域过滤的整份，与原来一致（没有改用 dropAt 里过滤过 floats 的 panels 参数）。
   - previewOf 只用 origin，原来 geometry(doc).origin，现 seen.origin；缓存 run.previews 里存的矩形计算方式不变。
   - floatDrop 的 canFloat 为假时原来不量，现在也不量（量的位置挪到 canFloat 为真的分支里）。
  自测：typecheck exit 0（与第 2 项合并跑）；单元与 dom 见最后。

## 跳过或停下的项
- app 3（soleContainerOf 加 export、emptyRegionContainer 改调它）：没做。原因：两者统计口径不同，不是同输入同结果。emptyRegionContainer 数的是 doc.panels 里 container 相同的面板个数，对 container 没有限制；soleContainerOf 只在“来源所在面板是某个带容器锚的区域的分节”时才有结果（regionSections 要求 isContainerAnchor）。nb-workbench-layout 的 layout-doc.ts 注释明写“有 container 却不在带容器的区域里……归属不起作用，照常显示”，validateLayoutDoc 不拒绝这种记录，settleContainers 也不修它。对这种文档（来源是个 container 在区域之外、且全文档唯一的面板），旧版返回它的容器 id、新版返回这一场的新容器 id，是可观察差别。对满足“凡有 container 的面板都是带容器锚区域的分节”的文档两者一致（浮动窗不允许带 container，validate 拒绝）。按任务说明“说不清的不做”，没改。若开发者认可“区域外带 container 的记录不是合法状态”，改法是：soleContainerOf 加 export，emptyRegionContainer 写成 `soleContainerOf(doc, source)?.container ?? run.newContainer`，补一条同值对照用例。
- `drag?.live.active.value === true` 收成 computed（app 10 的一小条）：回退，见 [10]。
- `idleRun(judged)` 按计划不动；`actions.presentation()`、`issues` 事件按计划不动。
