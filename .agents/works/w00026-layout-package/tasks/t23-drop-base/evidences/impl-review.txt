## 2. placeSorted 按上一帧的状态写，状态一变的那一帧画面错一帧：吸收时什么都不显示，离开时标签和卡片同时在，每次换位被拖的标签偏一格
- 严重程度：重要；类别：正确性 / 交互（从代码推断，未在运行时逐帧复现）
- 位置：live-drag.ts:194-213（sortingAt 在 tick 开头、按上一帧的 offered 与 wantsCard 调 placeSorted）；layout-drag.ts:259-286（placeSorted 的 resting = rect - offset）；drag-presentation.ts:69-73（sorting 按本帧的 drop 与 lifted 算）
- 现象：Vue 的渲染在 tick 之后的微任务里、绘制之前，所以每一帧画出来的是“本帧 stepPreview/updateCard 的结果 + 上一帧状态下 placeSorted 写的样式”。三处对不上：
  (a) 吸收那一帧（别人的标签条等够 150ms，或刚进自己的标签条）：updateCard 把 card 置 null，presentDrag 的 sorting 变真、ghost 为假；但占位标签的 inline visibility 要到下一帧 placeSorted 才写，类上是 visibility:hidden。绘制出来的这一帧没有卡片、没有拖影、也没有标签。吸收进别人的标签条时那个标签元素本帧才由渲染创建，下一帧才找得到。
  (b) 离开标签条那一帧：card 重新出现，但占位上还带着 visibility:visible 与 translate（下一帧 placeSorted(null) 才清），标签和卡片同时画出来一帧。
  (c) 每次换位：本帧 stepPreview 换了预览，渲染把被拖的 frame 挪到新的静止位置 R_new，但 inline translate 仍是相对旧位置算的 T，这一帧画在 R_new+T，离指针差一个邻居的宽度；下一帧 placeSorted 读到 rect=R_new+T、offset=T，才改正。拖着走过 n 个标签就闪 n 次。Trellis 的 sortTabAtPointer 在同一次里算顺序和所有标签的 transform，没有这一帧。
  此外 TabStrip 的 frame 绑定 `:style="truncating ? {...} : undefined"`（TabStrip.vue:223）：truncating 由真变假时 Vue 的 patchStyle 走 removeAttribute("style")，translate、visibility、z-index 一起被清掉，而 sorting.offset 还记着旧值，下一帧 resting 算错 offset 那么多，又是一帧错位（注释“值对不上就重写”只修了值，没修 offset）。吸收一个标签让条从放得下变成放不下或反过来时就会发生。
- 为什么是问题：开发者第 4 条要的是“限位排序的感觉”，审查重点 2 也点名“一帧的错位会不会出现既没有拖影也没有标签”。(a)(c) 发生在最常见的路径上（每次进入标签条、每次换位）。现有 e2e 都用 expect.poll 等到最终状态，看不到中间那一帧。
- 如何核实：在“标签条里不拿起卡片”用例里挂一个 rAF 采样器（同本次 workbench-float 用例的写法），每帧记录被拖标签 frame 的 computed visibility、getBoundingClientRect().left 与 [data-lifted]、拖影的有无；指针从一个标签移到相邻标签的另一半。期望出现一帧 left 与指针相差约一个标签宽，以及吸收那一帧三者都不可见。
- 建议改法：让 placeSorted 与渲染同步，而不是与上一帧同步：stepPreview 换了预览或 card 变化时，在 Vue 渲染之后（nextTick 或 onUpdated 的 post flush）用本帧的指针再调一次 placeSorted；换位的那一帧 TransitionGroup 本来就要读位置（强制布局），不多付一次重算。offset 不靠记忆，改为读元素当前的 style.translate 解析或每次先 removeProperty 再读（这样也消掉 Vue 清 style 的问题），或者 resting 直接从预览后的条目位置算。

## 3. “不画拖影”的判断（presentDrag.sorting）和“标签自己显示出来”（placeSorted 找到元素）是两份真相；找不到元素时被拖的东西整个看不见
- 严重程度：建议；类别：正确性 / 结构
- 位置：drag-presentation.ts:69-73；layout-drag.ts:238-256（sortTargetOf 找不到 frame 时返回 null）；WorkbenchToolStrip.vue:86-89（活动栏放不下时按 pressed 排优先级）
- 现象：presentDrag 只要“卡片收回且落点是 strip/reveal”就关掉拖影；placeSorted 要在 DOM 里找到被拖的那个 frame 才显示它。t22 审查第 7 条（已接受为风险）指出：活动栏放满时，被吸收的条目 pressed 为假、优先级 0，可能被收进“更多”。t22 时这种情况至少还有拖影；本次之后 sorting 为真、拖影关掉，sortTargetOf 找不到 `[data-tool-entry]` 返回 null，画面上没有卡片、没有拖影、也没有条目，指针下什么都没有。
- 为什么是问题：把一个已接受的“差一两格”风险变成了“被拖的东西消失”。两个判断各写一份，以后任何一边再加条件（标题只写标题、分区不同）都会再错开。
- 如何核实：矮窗口（或多放几个侧栏视图）让活动栏刚好放满，实时布局把右栏的视图拖到活动栏最下面，等吸收后读 `[data-tool-more]` 是否出现、`[data-workbench-drag-ghost]` 数量与该条目是否在 DOM 里。
- 建议改法：二选一，部件少的优先：(a) 拖动中给占位条目 priority 1（t22 第 7 条的建议），保证它总在外面；(b) 让“要不要拖影”由 placeSorted 的结果决定（例如 LiveDrag 暴露一个 sorted 的 ref，只在 placeSorted 成功找到元素时为真，presentDrag 读它），一份真相。

## 4. held.drop 取的是 lastLiveDrop，不是触发收起的那个候选；判定绕过 dropAt 时它是旧值，松手可能提交一个早已离开的落点
- 严重程度：建议；类别：正确性（从代码推断）
- 位置：layout-drag.ts:213（`held = {point, drop: lastLiveDrop}`）、:563-566（只有 dropAt 更新 lastLiveDrop）、:721-731（resolveDrop 在 covered、onButtons 时不调 dropAt，直接 offer(null)）；nb-layout/src/drag-gesture.ts:321-331（放下时按此刻坐标与此刻的 top 元素再判一次）
- 现象：指针停在 `data-no-drag` 的按钮区（面板头的动作按钮）或被菜单挡住 150ms，offered 为 null，预览变成 source-removed，触发 collapseSource；这时 lastLiveDrop 还是指针进按钮区之前最后一次 dropAt 的结果（比如某块面板的外缘）。来源收起后布局挪动，指针下不再是按钮；不动指针直接松手，drag-gesture 的 drop() 按同一点再判，这次 onButtons 为假，走进 dropAt → judgeAt，held.point 相同，返回那个旧落点，commitsUnderPointer 为真就提交了。画面上是 source-removed（没有任何落点），结果却是早先经过的那个落点。
- 为什么是问题：违反“松手放到的就是屏幕上那个”（输出 38），而且这份旧值的来源要推演三处代码才看得出。
- 如何核实：读上面三处；运行时复现需要按钮区收起后被别的面板替换，主 Agent 可选做。
- 建议改法：held.drop 用触发收起的那个候选：LiveDrag 调 collapseSource 时把 `offered`（preview 为 source-removed 时就是 null）传过去，删掉 lastLiveDrop 这个字段与 dropAt 包装，judgeAt 直接作为 dropAt。少一个状态，也和“收起那一刻指针下的落点”字面一致。

## 5. 收起后的几何是“按矩形差平移量好的 DOM”，有两种情形差出一格：活动栏只按 sidebar 的条目上移，编辑组折行的头高度被当成不变
- 严重程度：建议；类别：正确性（从代码推断）
- 位置：layout-drag.ts:478-481（bar 的上移）、:333-339（measureBar 只留 `sidebar` 面板的条目）、:466-469（头的高度不变）；state/layout-present.ts:82-86（活动栏列的是侧栏这一整列的面板）；nb-layout/src/vue/tab-strip-geometry.ts:45-54（translateTabStrip 不重排）
- 现象：
  (a) 活动栏列的是侧栏这一列所有面板的视图（sidebarColumnPanels，按树序），measureBar 只留 `sidebar` 的条目。来源在这一列里排在 sidebar 之前的另一块面板（从侧栏上缘拆出来的）时，收起后画面上 sidebar 的条目整体上移一格，但 `kept.bar.findIndex(entry.tab === source.tab)` 为 -1，不移；barDrop 的插入位在收起后差一格。来源在 sidebar 里、但它下一个 sidebar 条目之间隔着别的面板的条目时，gap 也算大了。
  (b) 编辑组的标签条折行（wrap）时，头的高度随宽度变：收起后邻居变宽，折行变少，头变矮、正文上移，而 collapsed() 认为“头的高度不变”，translateTabStrip 也只平移、不重排，第二行的标签在快照里还在第二行。指针在新头下沿与旧头下沿之间时，判定是标签条（插入位），画面上是正文的上窄带；第二行的插入位也对不上。
- 为什么是问题：输出 38 写“标签条与活动栏条目跟着挪”，收起后判定要和静止布局一致。Trellis 的 dropBase 是按收起后的文档整份重算（layoutRects），没有这类近似。两种情形都不常见，但差的是一整格，不是几个像素。
- 如何核实：(a) 读上面几行代码即可确认；运行时：把一个视图拖到侧栏上缘拆出一块，再把它拖到别处等收起，指针回活动栏，读 data-live-preview 里的 index 与画面上指针所在的条目间隙。(b) 编辑组 overflow 为 wrap、标签多到两行时，拖走邻组唯一的标签等收起，再看邻组的头。
- 建议改法：(a) measureBar 量这一列全部条目（带上所属面板），收起时按全列下标上移，判定时再过滤到 sidebar；(b) 至少在注释与 Task 记录里写明 wrap 时的偏差；要消除就得在收起后等一帧重量这块面板的头（与“预览不进输入”冲突，需开发者取舍）。

## 6. 浮动窗把手加了 [data-moving] 过渡，却没有跟着加 [data-float-gesture] 的“手势中不过渡”：别的过渡还在走时缩放浮动窗，把手拖尾
- 严重程度：建议；类别：正确性 / 回归（从代码推断）
- 位置：packages/nb-layout/src/vue/NestedGrid.vue:470（chrome 只绑 data-moving，不绑 data-float-gesture）、:564-576（`.nb-grid-frame[data-float-gesture], .nb-grid-content[data-float-gesture] {transition: none}` 没有 chrome）
- 现象：bc3938ad7 给 `.nb-grid-float-chrome[data-moving]` 加了 transform/width/height 的 470ms 过渡。`moving` 是整个网格的标记：任何一轮布局过渡（刚落地一个窗、刚放下一个面板）的约 0.5 秒里都为真。这时缩放浮动窗，floats 的矩形每帧变，外框与内容有 `[data-float-gesture]` 压成 `transition: none` 跟手，把手层没有，宽高与位置按 470ms 缓动追，四边手柄落在窗后面。整窗拖动不受影响：placeFloat 写的是 `translate`，不在过渡列表里。base 上把手没有过渡，不会拖尾。
- 为什么是问题：输出 39“缩放”与开销条目要求跟手的东西不带拖尾；这条规则在外框与内容上已经有人专门写过（注释“手势中的窗跟手：别的布局变化正在过渡时也不带拖尾”），把手漏了。
- 如何核实：e2e 里拖出一个浮动窗，松手后立刻（`[data-moving]` 还在）拖它右下角手柄，逐帧比较 `[data-float-chrome]` 与 `[data-leaf][data-float]` 的宽度，期望出现几十像素的差。
- 建议改法：chrome 也绑 `:data-float-gesture="floatGestures.get(float.id)"`，把 `.nb-grid-float-chrome[data-float-gesture]` 加进 transition:none 那条规则。

## 7. 落地时“这块叶是不是新出现的”靠两个 watch 的先后，注释给的退路也不成立；land 还会盖掉同一轮 start 写的 growing
- 严重程度：建议；类别：不变量 / 结构
- 位置：NestedGrid.vue:214-218（leavesBefore 在 layers 的监听里写）、:383-394（lifted 的监听读它）；useGridMotion.ts:152-168（land 直接 `growing.value = entering`）
- 现象：(a) 两个监听都是 pre flush、同一个组件，Vue 3.5 的队列对同 id 的 pre 任务按入队先后跑，入队先后取决于依赖的通知顺序（props 键的设置顺序、computed 与 watcher 在 props.lifted 订阅链上的先后），不是“先建先跑”的公开保证。现在 layers 经 contentLayer 依赖 props.lifted、且先订阅，所以实际会先跑，结论大概率成立；但注释说“它要是还没更新，……只是不长外框”不对：lifted 的监听先跑时，leavesBefore 是“上上次布局之前”的叶，layers.value（惰性 computed）却已是放下后的，预览里刚长出来的新块会被误判成“这次才出现”，外框从卡片的矩形长出来，而不是“不长”。(b) land 在同一轮里紧跟 motion.update 之后调用，update 若因这次布局变化走了 start 并写了 entering，land 用只含一块叶的 Map 整个替换掉，别的新项就没有起点矩形、直接到终点。
- 为什么是问题：正确性挂在两个监听的隐含先后与一条不准确的注释上，后来的人调整 watch 顺序或 props 依赖就会静默出错。
- 如何核实：读上述代码；(a) 可在 happy-dom 里交换两个 watch 的声明顺序跑 NestedGrid 的单元测试（若有覆盖），或推演 edge 落点：预览已长出新块 → 放下时若 lifted 监听先跑，新块外框会从卡片矩形长出来。
- 建议改法：合成一个监听 `watch([layers, () => props.lifted?.key ?? null], ([next, now], [previous, before]) => …)`，同一次回调里拿到放下前后的叶集合，删掉 leavesBefore 这个模块级变量与那段先后注释；land 合并而不是替换：`growing.value = new Map([...growing.value, ...entering])`。
- 补充（第 6 条，整窗拖动）：整窗拖动也有拖尾，前提是拖出来的窗还在“从卡片长到终点”的那 0.5 秒里就按住它。activate 对 `source.kind === "panel"` 不调 settleMotion（layout-drag.ts:754-765），外框与内容靠 `[data-float-gesture="move"] {transition: none}` 当场跳到终点，把手层没有这条，它的 transform/width/height 过渡继续走完，translate 叠在一个还在长的矩形上：窗已经跟手，四边手柄还在从卡片大小往外长。所以审查重点 4 问的“整窗拖动时把手是否会带过渡拖尾”：会，只在落地过渡期间。修法同上（chrome 绑 data-float-gesture）。
