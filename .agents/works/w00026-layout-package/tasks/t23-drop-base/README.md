# 拖动判定照 Trellis：来源收起一次、按收起后的布局判，标签条限位排序

## 目标与范围

开发者 2026-11-09 试用后：按来源收起后的静止布局判定，来源不再重新展开；标签条与活动栏里限位排序；工具面板不分的那两条边没有落点；收起区域按建议处理

合同：[workbench-layout](../../../../../docs/specs/ui/workbench-layout.md) 输出 25（不分的边没有落点）、输出 38（判定的布局、标签条上的排序）、验收 22。

## 当前状态

开发者 2026-11-09 定的三条：来源收起后不再展开，接受；工具面板不分的那两条边（侧栏、右栏的左右，面板的上下）改成没有落点；收起的区域按建议：隐藏的具名面板只能经活动栏放进侧栏、放下才展开，收成标题行的照旧，来源自己被拖空的收起后不再展开。

这次照 Trellis 读了它的拖动代码（只读行为）：它判定用的是“来源收起后的静止布局”，按布局算、不量页面；来源在第一次碰到落点时收起，之后不再展开；指针再动才重判，松手放的是当前的落点。上一轮我对开发者说成“按预览后的布局判”，说错了，已在对话里更正。

三个切片都已提交在分支 `feat/w00026-t23-drop-base`，开发服务 4317 跑着这个分支给开发者试，没合入：

| 切片 | 内容 |
|---|---|
| 不分的边 | nb-layout `nearestEdge`：有边能分时，不允许的边的窄带返回“没有落点”；分区的中央让开这些窄带；浮动窗四边都不分，整块还是中央 |
| 收起一次 | `LiveDrag` 第一次摆到别处的落点时调 `collapseSource`；`layout-drag` 按收起前后两份文档里每块面板的矩形差，把拿起时量的几何、标签条快照（nb-layout `translateTabStrip`）、活动栏条目挪到收起后的位置；收起那一刻的落点留到指针再动 |
| 限位排序 | 卡片收回、指针在标签条上时不画拖影；被拖的标签就是它的占位，帧开头读它的静止位置，写 `translate` 夹在条里；占位不参与换位过渡（样式里压掉 `transform`）；活动栏竖着 |

验证：`live-drag.test`、`drag-presentation.test`、`layout-drop.test`、`layout-constraints.test`、`drag-gesture.test` 通过，类型检查通过；e2e `workbench-live-drag`、`workbench-dnd`、`workbench-drag-cost`、`editor-area`、`workbench-views`、`workbench-float`、`files-explorer` 181 项通过。新加的两条（来源收起后回到原处不再展开、排序时夹在条里）各做了一次变异检查：拿掉收起的几何、拿掉夹取，用例都会失败。改了期望的旧用例：侧栏左右窄带、骨架缝上、面板上缘从“添加为标签”或“原位”改成被拒绝；编辑器标签并入时，来源那一组收起后要按目标此刻的矩形瞄准。

没做：落点指示模式（键盘、减少动效、设置关）照旧按当前位置判；拖到排序位置后放下时标签直接到位，没有落回去的过渡；`lab-scenes` 没跑（master 上主题编辑器场景本来就 404）；实现审查还没做。

第一次试用后（2026-11-09）开发者提了五条，确认了其中三条的改法，已提交在同一分支：

| 意见 | 处理 |
|---|---|
| 拖走面板后标题头留在原地 | 拿起的是来源面板唯一的标签时，那块面板在来源收起之前算空位，头也不画（`presentDrag` 的 `slotPanel`）；e2e 补在“最后一个视图”那条 |
| 浮动时标题栏先到位、视图才慢慢就位 | 手势收尾的布局变化不过渡，新浮动窗直接画在终点、只有内容在飞。落地时内容落进这次才出现的叶，叶的外框与窗的手柄也从卡片的矩形一起长到终点（`useGridMotion.land` 带出现的矩形）；e2e 逐帧量新窗 |
| 落点分区不对了 | 实时布局不画分区，落点指示照旧；`DropSectorsOverlay` 去掉只给实时布局用的 `live`、`inline`，令牌 `--layout-live-sector-line` 删掉，设置说明改成只在落点指示下画 |
| 活动栏一个图标是一整个侧栏容器 | 开发者定：侧栏、右栏、底部面板都做；容器既有插件声明的，也能由用户拖出来。另开 Task 先写提案 |
| 用中文回复 | 照办 |

三条修正各做了变异检查（拿掉空位、拿掉落地时的出现矩形），用例都会失败。e2e 八个文件一轮 196 项通过、1 项失败：`workbench-float` 里“窗刚开、过渡还在走时拖它”原来量的是过渡中间的起点，改成量两次移动之间的位移后单跑通过。

留给审查一起处理的两处：`NestedGrid` 落地时依赖 `layers` 的监听先于 `lifted` 的监听跑，注释写的理由（先建先跑）未核实，真正的保证可能是父组件更新属性的顺序；浮动窗把手的 `[data-moving]` 过渡没有 `data-float-gesture` 的压制，别的过渡进行中拖窗的手柄缩放会带拖尾。
