### 重要｜时序合同｜t60：同帧分两次发布时，浮动窗先跳回按下处再停靠

- 位置：`packages/nb-layout/src/vue/NestedGrid.vue:388–403`、`:610–621`，`packages/nb-layout/src/grid-motion.ts:131–142`。对应 `ui/nested-grid` 输出 172。
- 现象：`placeFloat(id, null)` 后，宿主先清 `gesture`，等 Vue `nextTick()`，仍在下一帧之前发布停靠。外框和活动内容都从拖动前的位置开始过渡，不从松手处开始。
- 原因：清 `gesture` 触发 `layers` 的侦听；窗还在 `floats` 里，`releaseStarts` 不生成这个窗的起点，但 `clearReleased()` 仍把本帧所有偏移和清理帧一并清掉。真正停靠的更新读不到偏移。
- 复现与实际结果：在 Chromium 里挂载 Vue `NestedGrid`，通过公开的 `placeFloat` 把窗从 `x=100` 挪到 `x=305`，用上述两次刷新完成停靠。探针确认第二次发布早于下一次 rAF；读取实际 CSS 关键帧，HEAD 外框与内容 `left` 都是 `100px → 535px`，基线也是 `100px → 535px`。HEAD 同步发布停靠时是 `305px → 535px`，超过下一帧才发布时是 `100px → 535px`，两个对照符合合同。这不是基线已有合同的回归，是 t60 新增合同只覆盖了同步发布的情况。工作台当前同步落账的路径不受此复现影响。
- 建议：把偏移按窗保留到帧边界，只清这次已消费的窗；仅撤手势或与这扇窗无关的刷新不能消费偏移。若宿主已发布整窗移动的最终矩形，也要按窗消费，防止后来同帧停靠再加一次偏移。用公开组件补上分两次发布的验收。

### 重要｜行为回归｜t62：边缘滚到尽头后，不再移动指针就松手会丢掉落点

- 位置：`packages/nb-layout/src/drag-gesture.ts:381–399`、`:505–528`、`:535–538`。对应 `ui/layout-drag` 输出 14。
- 现象：边缘滚动最后一步改变了指针下的目标。滚到尽头后等滚动停止再松手，反馈仍指向上一步的位置，拖动以 `no-action` 结束。短列表或剩余滚动距离短时不用刻意等很久就会遇到。
- 原因：最后一次 `scrollBy` 产生的滚动事件到达时 `autoScrolling` 仍为真，`scrolled()` 不刷新；下一帧因方向没余量，`edgeScrollPlan` 返回 `null`，`autoScrollTick` 在 `publish()` 前退出。松手时 `autoScrolling` 已为假，走普通提交，对这次真正命中的动作与陈旧反馈做等值比较，拒绝提交。基线在尝试滚而读不到位移之前，会先发布最终位置的反馈。
- 复现与实际结果：Chromium 中经公开 `createDragSession` 绑定真实 `overflow-y: auto` 列表，高 200px、内容高 264px，真实鼠标停在距下沿 4px，待 `scrollTop=64` 且滚动帧结束后松手。两版浏览器滚动位置同为 `14,28,42,56,64`；HEAD 最后发布为 `12`，松手为 `no-action`，没有提交；基线最后发布为 `13`，提交 `13`。没有手工派发 `scroll` 或 `pointerup`，没有替换时钟。
- 建议：此前有实际位移时，即使下一轮已挑不到容器，也先用最终滚动位置发布一次，再把 `autoScrolling` 置假；不要为修复此处放宽普通松手的匹配规则。补一条从实际滚动到停止、指针不再动就松手的验收。

### 建议｜示例行为回归｜t60：横向缩放会临时撑高浮动窗，盖住底栏

- 位置：`packages/nb-layout/src/grid-rects.ts:219–225`、`packages/nb-layout/src/vue/FloatWindowHandles.vue:71–75`、`packages/nb-layout/examples/desktop/src/App.vue:138–141`、`:280–287`。对应 `ui/nested-grid` 输出 176、177。
- 现象：桌面高度不足最小窗高时，拖右边手柄只该改宽度，预览却把窗撑高并盖住底栏，松手又缩回。最小尺寸优先只应约束本次调整的轴；不动的轴应保留已夹取的呈现尺寸。
- 原因：`resizeFloatRect` 无论方向是否为 0 都夹到最小尺寸。基线纯函数也这样，但桌面基线用 `withinDesk` 裁掉越界预览；这次删除该裁剪，直接呈现手柄返回的矩形。
- 复现与实际结果：Chromium 加载仓库的桌面示例入口，1250×220 视口，用真实鼠标横拖 `Files` 窗右边手柄。两版开始都是 480×133，底边 `y=170`；HEAD 预览 507×160，底边 `y=197`，底栏内 `y=186` 命中 `Files` 内容，松手恢复 507×133。基线预览与松手都为 507×133，底栏同一点一直命中底栏。HEAD 存档保留未动轴的原高 300，未见存档回归。
- 建议：方向分量为 0 时直接沿用 `start` 在该轴的位置与尺寸，只对动轴应用 `min`、`max`、`area`；不要为修预览把夹取后的尺寸写回记录。补一条桌面小于最小尺寸、拖动正交边的组件或示例验收。

### 重要｜过渡隔离｜t60：另一扇窗的动画让刚松手的窗回弹重播

- 位置：`packages/nb-layout/src/vue/NestedGrid.vue:354–364`、`:389–401`、`:725`、`:848–856`，`packages/nb-layout/src/grid-motion.ts:53–65`。对应 `ui/nested-grid` 输出 105、172。
- 现象：同一次发布里 A 提交整窗拖动、B 用 `animate: true` 改宽，B 应过渡，A 应停在松手处。实际 A 的外框、正文和手柄一起跳回按下处，再动画回到松手处。
- 原因：`settleFloatMoves` 把 A 的矩形压回旧值只影响是否开过渡的判定。B 开启全网格的 `moving` 后，A 已撤掉 `gesture`，三个层仍收到过渡标记，写进 DOM 的新 `left`/`top` 都会走 CSS 过渡。按窗排除出判定并没有将该窗排除出渲染层过渡。
- 复现与实际结果：Chromium 中挂载实际 `NestedGrid`、`FloatWindowHandles`。公开 `placeFloat` 把 A 从 `x=100` 挪到 `x=305`，同一同步段调用 `placeFloat(A, null)`、撤手势、发布 A 的最终矩形与 B 的宽 280（原 200）。HEAD 中 A 的外框、正文、手柄各有 `left: 100px → 305px`、第一帧读到 `x=100`；B 的外框、手柄有 `width: 200px → 280px`。基线忽略 `animate`，A 无过渡、第一帧就为 `x=305`。没有在两个发布之间等待帧或修改 CSS 计算结果。
- 建议：把“仍是浮动窗、这次矩形变化不该过渡”的决定传到三层过渡标记，而不是只用它筛选是否启动整轮。单独的窗可以跳过本次矩形过渡，别的窗及树上的过渡照走；不要全局停掉过渡。补一条 A 松手与 B 程序改尺寸同轮发布的浏览器断言。

### 建议｜公开合同遗漏｜t62：横向边缘滚动不支持 RTL，接入说明没有写

- 位置：`packages/nb-layout/src/vue/drag-session.ts:107–133`、`packages/nb-layout/src/vue/drag-session.md:41`、`packages/nb-layout/CHANGELOG.md:14`。`ui/layout-drag` 输出 14 也未限定横向排版方向。
- 现象：RTL 容器在 `scrollLeft=0` 时仍可向物理左端滚，边缘拖动却不滚。这里不是工作台未接入的问题。t62 计划和源码注释已指出风险，但面向调用方的合同只列了计算溢出样式、方向余量和指针位置，没告诉宿主 RTL 不满足承诺。
- 原因：横向的 `room` 以 LTR 的 `[0, scrollWidth - clientWidth]` 为范围。Chromium 的 RTL 范围是负值到 0，初始真正可向左滚，代码却判 `left=0`；在右端也可能误判还有余量，遮住外层候选。
- 复现与实际结果：Chromium 中给公开 `createDragSession` 一条 `direction: rtl; overflow-x: auto` 的 200px 宽容器，内容 264px 宽，真实鼠标拖到左端内侧 4px；HEAD 不排后续滚动帧，`scrollLeft` 一直为 `0`。同一个元素的原生 `scrollBy({left: -14, behavior: "instant"})` 到 `-14`。基线没有横向边缘滚动，不算基线回归。
- 建议：若保留当前范围，在公开选项说明、包文档及变更记录明写横向只支持 LTR；若要兑现通用合同，按 CSS 方向折算物理左右余量，并加 RTL 两端及嵌套回退测试。

### 建议｜正确性｜t61：过滤掉整行成员后，把非空标签条当作空行接收拖放

### 重要｜正确性｜t60：桌面示例连续按 Tab 到不了浮动窗手柄

- 位置：`packages/nb-layout/src/vue/NestedGrid.vue:248–254,325–328,724–730`、`packages/nb-layout/src/vue/useGridFocus.ts:24–39,92–95,97–109`、`packages/nb-layout/examples/desktop/src/App.vue:182–185,319`。对应 `ui/nested-grid` 输出 103、121–127、173；不能只验直接聚焦手柄不掉焦点。
- 现象：从页面起点一路按 Tab，基线走过底栏与四扇窗的标题按钮、正文后可以进移动和缩放手柄；HEAD 从 `Notes` 正文按 Tab 先跨到浏览器界面，再次进入页面又从底栏开始。轮到每扇窗时重复。手柄留在 DOM、直接 `.focus()` 能用，但不等于键盘能走到。
- 原因：t60 为桌面接入焦点抬升，窗一得焦点就移到 `floats` 末尾，DOM 序和布局序分离。网格接管 Tab 时只枚举外框、内容与分隔线，不含手柄层；当前窗一抬升就是末站，正文最后一项的 Tab 被送到手柄之后的退出哨兵。焦点重入又按树序从底栏开始。旧的焦点接管遗漏在基线代码中已存在；本批把真实桌面示例从原生顺序变成正常键盘使用即触发的路径。
- 复现与实际结果：Chromium 打开真实桌面示例、默认四窗、1250×950，不用指针，`page.keyboard.press("Tab")` 从页面起点连按 24 次。基线第 21 次到 `Notes` 缩放手柄，第 22 次到移动手柄；HEAD 第 5 次进入 `Notes` 后出现 `aria-owns`，第 9 次就回到底栏首项，进入 `Calculator` 后第 17 次又回到底栏首项，24 次没有一个手柄获得焦点。报告的独立直接聚焦或点击手柄探针没有覆盖这条路径。
- 建议：焦点移动使用不因抬升改写的导航顺序，把手柄纳入 Tab 停靠点（可以独立保持现有稳定手柄顺序），不要用叠放顺序决定下一站；补从页面起点 `Tab` 与 `Shift+Tab` 能越过各窗正文并到达手柄的浏览器用例。

## 未发现问题的方面

- **t60 同步停靠和帧边界之后的停靠**：仔细检查后没有发现问题。Chromium 挂载实际 `NestedGrid`，同步停靠的外框和内容从松手的 `x=305` 出发；到下一帧才发布则从记录的 `x=100` 出发。 `flushGrowingStart` 在再写终点前实际让起点进了 CSS 布局。取消且不发布结果时由 rAF 清理，卸载时 `onBeforeUnmount` 取消该 rAF；这两条是代码核对，未另跑触摸和笔的手势。
- **t60 手柄节点身份、按下的抬升及存档**：对节点稳定性与此处职责，仔细检查后没有发现问题。真实桌面专门直接聚焦最底下的 `Notes` 移动手柄时，原节点仍连接、焦点还在、层级升高；手柄 DOM 仍为 `notes,calc,clock,files`。Chromium CDP 计数显示按非置顶的 `Calculator` 右下手柄后，两个版本各存档 1 次；再按置顶窗均不存档。只记请求、不更新顺序的宿主可收到按下和焦点两次通知；工作台 store 同步按当前顺序短路置顶请求，桌面探针没有重复结算。对照 `stableOrder`，删掉的 ID 不保留，完全换一批会按新数组插入；沿实际 DOM 父链能越过内容中的内嵌网格、命中当前网格直接子的标记。Teleport 进窗层按落地后的 DOM 归属；到 `body` 的覆盖层不冒入；`aria-owns` 不改事件路径。这些归属、全换 ID 是代码与既有合同测试核对，不是工作台全流程浏览器验证；Tab 导航与节点是否稳定是两件事，前者见重要条目。
