F1  [重要] [模型] 改矩形、提到最前会被 finish 当成“没变化”吞掉
位置：packages/nb-layout/src/layout-doc.ts:211-220（sameLayoutShape）、238-245（finish）、618-620（rebaseOriginal）；计划“模型”一节只列了 layoutStructureKey、stripDynamicTabs、carryDynamicTabs、rebaseIntents。

如何核实：已跑 probe1.ts：
  sameLayoutShape(矩形不同的两份文档) = true

F2  [建议] [编辑器/模型] 内存宿主的 newId 只查树，会覆盖浮动编辑组
位置：packages/neuro-book/src/plugins/workbench/shared/editor-panels.ts:136-146（createMemoryEditorPanels 的 policy.newId）；计划“编辑器”一节与验收映射里 `area.test.ts` 用的就是它。
现象：newId 用 `findTreeNode(doc.tree.root, id) === null` 判重。浮动面板在 `panels` 里、不在树里，所以 `g1` 这类 id 会被再分配；moveTabToEdge（layout-doc.ts:552-553）直接 `next.panels[id] = …` 覆盖，不查 `panels`。
为什么是问题：浮动窗里的标签静默丢失（记录里不再有它），单元测试和 Lab 夹具里复现；计划验收“拆分命令在浮动的编辑组上”恰好会撞上。生产的 createLayoutPolicy.newId 用 uuid，不受影响，所以只在测试里暴露，容易被误判成测试写错。

建议改法：newId 同时查 `doc.panels` 与树；moveTabToEdge、movePanelToEdge 这类用 newId 的操作在写入前断言 `next.panels[id] === undefined`，撞了就失败为 rejected，不覆盖。

F3  [重要] [模型/呈现] 最大化、收起对浮动窗没有定义，现有命令会把整个工作台弄空白
位置：
  - packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts:254-257（setCollapsed）、322-326（toggleMaximized：只要 id 在 doc.panels 里就接受）
  - packages/neuro-book/src/plugins/workbench/web/commands/panel-commands.ts（withPanel 缺省取 currentPanel，currentPanel 随焦点走，浮动窗会是它）
  - packages/nb-layout/src/vue/NestedGrid.vue:103-117（placement、obscuredLeaves）
  - packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:196-210（frameActionsOf 给每块面板收起、最大化按钮）
  - packages/nb-layout/src/layout-doc.ts:584-592、697-755（setPanelCollapsed 与校验不禁止浮动窗 collapsed）
现象：计划只说“框架按钮只有一个回到停靠”，没说命令与状态。焦点在浮动窗里执行 `nbook.view.toggle-panel-maximized`（命令面板、快捷键）时，effectiveMaximized 认它（面板存在、没隐藏、没收起）。NestedGrid 的 maximizePlacement 在叶摆放里找不到这个 id（浮动窗是追加的），而 obscuredLeaves 把“除它和条以外的全部叶”都标成被盖住：所有树里的面板 inert、内容停放隐藏，却没有任何东西盖在上面。`set-panel-collapsed` 同理：无名工具浮动窗被写上 collapsed:true，effectiveVisibleTabs 因此判它不可见，但窗口照常画着内容。
为什么是问题：一个快捷键把界面弄成空白或“可见性与显示不一致”，且状态会写进记录（collapsed）。反向也没定义：树里的面板最大化时，浮动窗是否继续压在上面、是否算被盖住、maximizePlacement 的外接矩形含不含浮动窗（计划里浮动窗是“追加到叶的摆放后面”，取决于追加在 maximizePlacement 之前还是之后）。
如何核实：代码推断（读 toggleMaximized 对任意 doc.panels id 的接受、obscuredLeaves 的定义）；实现前不能跑出来。
建议改法：计划里定下：浮动窗不可最大化、不可收起。模型层 setPanelCollapsed 对浮动窗返回 rejected，校验拒绝浮动窗上的 collapsed；store.toggleMaximized 与命令对浮动窗返回 unavailable；浮动窗的框架按钮只有“回到停靠”。NestedGrid 的 floats 在 maximizePlacement 之后追加，且不进 obscuredLeaves（“被浮动窗盖住仍算可见”的另一面：浮动窗始终在最大化的面板上面）；把这一条写进 nested-grid.md 的“最大化”。

F4  [重要] [编辑器] 整个浮动编辑窗停靠时绕过编辑器区的规则
位置：packages/neuro-book/src/plugins/workbench/web/components/WorkbenchShell.vue:385-390（commit：只有 `editorTabIdOf(source.tab)` 非空才走 `editorTabs.drop`，其余直接 `layout.actions.drop`）；layout-drag.ts:26（LayoutTabSource 只有标签）；计划“编辑器”一节只写了 `PanelTabs.float`、`area.moveToFloat`、`EditorTabDrag.drop` 的 float。docs/specs/workbench/editor.md 输出 49、55。
现象：计划的整窗拖动（source.kind === "panel"）和框架按钮“回到停靠”，对编辑器标签会走 `movePanelToStrip`/`movePanelToEdge`，把窗里全部标签一次并入树里的编辑组，不经 area。而 Spec 要求移动前先结算活动标签会变的组、有未裁决输入就不移动、目标组已有同地址同编辑器的标签就合并（不重复）、固定与 preview 跟着分区变。生产的 createLayoutPolicy 没有 canInsert（全仓只有 layout-constraints.ts:88 定义），所以固定分区也不会由布局层守。
为什么是问题：并入时目标组可能出现两个同文件标签；窗里的固定标签落在目标组普通标签之后（编辑器只在恢复时才把固定排前，editor/web/groups/groups.ts:456-461）；活动视图有未裁决输入时被直接搬走。这些都是 Spec 明确的不变量，计划只覆盖了“标签撕下来浮动”这一条路，没覆盖“窗停靠”。
如何核实：代码推断（commit 的分支与 EditorTabDrag 接口只收单个 tabId，contracts.ts:69-78）。
建议改法：EditorTabDrag 加 `dropPanel(panelId, action, keyboard)`（或让 area 提供 `moveGroupTabs`），由 area 逐个标签走 moveTab 的同一套结算与合并；`nbook.view.dock-panel` 对编辑组同样走 area。计划里把“窗停靠”单列一条，验收加“目标组已有同一文件”“窗里有固定标签”两个场景。

F5  [重要] [与已定设计一致/可访问性] 键盘既不能浮动，也不能移动或带回浮动窗里的标签；提案里的“浮动”按钮与命令被去掉且没写理由
位置：计划“操作：外壳”“Tab 与读屏”“待确认”；layout-drag.ts:461-495（keyboard.regions、start）；docs/specs/ui/workbench-layout.md 输出 31（“与指针同一套规则”）；提案 workbench-single-tree-layout.md 第 251 行（面板头按钮含“浮动”）、304-305 行（`nbook.view.float`、`nbook.view.dock`、move-view 的 target 可以是 `float`）。
现象：
  1) 键盘拖动的区域来自 enumerateDropCandidates，只列树里的面板，候选里没有“无落点”，所以键盘走不到“无落点就浮动”。计划不做“浮动”按钮、也没有 float 命令，键盘用户没有任何办法把东西浮出来。
  2) 整窗移动只有指针（`data-float-move`）；键盘只有“方向键缩放”，不能移动窗。
  3) 拿起浮动窗里的标签时，regions 只在树的叶里找（`treeLeaves(doc.tree.root)`），来源所在的面板（浮动窗）不是区域，start() 里 `regions.findIndex(home)` 是 -1，被 `Math.max(0, …)` 变成第 0 个区域（可能是活动栏）。Spec 31 要求“拿起时停在原位，直接 Enter 不移动”。这一点从代码推断，没有实际跑。
为什么是问题：Spec 31 现行合同被违反；提案把“浮动”按钮与命令写进了设计，计划的“待确认”里没有给出去掉它的理由（只说了不做）。
建议改法：（a）加命令 `nbook.view.float`（参数 panelId?、视图或当前活动标签，在当前面板旁给缺省矩形），面板头与标签右键菜单各放一个入口，键盘靠命令与菜单走通；（b）键盘拖动的区域里加一个“浮动”区域，放在预备区之后，Enter 就在该区域给出缺省矩形；（c）浮动窗的标签条或窗框上给键盘移动（例如拿起窗后方向键移动，沿用同一个 session），或至少 Alt 加方向键；（d）regions、stops、panelGeometry 把浮动窗纳入（见 F7）。若坚持不做按钮，要在待确认里写理由，并在 Spec 里把“键盘不能浮动”写进不承诺。

F6  [重要] [拖动] “得到 null 就浮动”把性质不同的 null 混在一起；“菜单挡住不浮动”与“工作台外浮动”在现有判据里是同一个分支
位置：layout-drag.ts:443（resolve 的守卫）、228（barDrop 里 applyLayoutDrop 失败）、278（stripDrop 量不到标签条）、290（stripDrop 里 applyLayoutDrop 失败）、341（dropAt 里 applyLayoutDrop 失败）、215（barDrop 最大化时返回 null）；计划“落点”一节：“被菜单、对话框挡住的（top 判定）不浮动：是 null；工作台之外（包括标题栏、状态栏）算无落点，也浮动”。
现象：
  1) resolve 里 `top === null || !root.contains(top) || top.closest("[data-no-drag]") !== null` 同时盖了：指针在视口外（elementsFromPoint 为空，top 为 null）、被传送到 body 的菜单与对话框挡着（!root.contains(top)）、按钮区（data-no-drag）。计划要求前者浮动、后者不浮动，现有表达式分不开；“工作台之外”如果指窗口外，正是 top === null。
  2) 按计划字面实现“dropAt 返回 null 且来源允许就给 float”，下面这些 null 也会浮动：最大化时拖工具视图到活动栏（barDrop 返回 null）；标签条量不到（stripDrop 278 行）；applyLayoutDrop 因 limit-exceeded（256 节点）或 not-found 失败；编辑器标签拖到活动栏上段（barDrop 因 viewIdOf 为 null 返回 null）。它们多数是“出错”或“暂时算不出”，不是“指针在没有落点的地方”。
  3) dropAt 里预览缓存的键是 `JSON.stringify([source, action, extent])`（337 行）。float 动作带每帧都变的矩形，缓存要么一直 miss、要么只增不减（Map 只在拿起时与文档变时清）。计划的“动作键只写 float”只覆盖了会话的 actionKey（448 行），没有覆盖这里的缓存键，也没有覆盖 live-drag.ts:57 的 keyOf（见 F8）。
为什么是问题：用户很容易在这几处“拖错了多一个窗”；而 Spec 25 规则 1 与 e2e（workbench-dnd.e2e.ts:577、755 一带）已经把“按钮区没有落点、被菜单挡住没有落点”写成合同，计划的改法没说哪些 null 保持取消。
如何核实：代码推断；resolve 与各处 return null 的位置已逐行读过。
建议改法：让 dropAt 返回三态（落点 / 明确的无落点 / 不接收），float 只在“明确的无落点”里给：指针在工作台内、不在 data-no-drag 与浮层之下、resolveLayoutDrop 返回 null 且 applyLayoutDrop 没有因错误失败。视口外（top === null）单独一个分支，按“夹进树区域”给矩形。计划里把 data-no-drag（面板头按钮区、标签上的关闭按钮）、barDrop 的 null、最大化时的行为逐条写进“不浮动”的清单。float 动作不进预览缓存。

F7  [重要] [拖动] 浮动窗先判的“叠放顺序”落在哪一层没写；判定与快照的输入全是树里的面板
位置：计划“落点”一节（“resolveLayoutDrop 不变”与“先按叠放从上到下看浮动窗，再看树”写在同一列表里，互相矛盾）；packages/nb-layout/src/layout-drop.ts:104-134（layoutDropPanelAt、resolveLayoutDrop）、67-81（resolveInPanel）；layout-drag.ts:164-178（panelGeometry 用 treeLeaves）、306-326（frozen 快照）、180-183（excludedRects）、461-495（regions）、497-506（stopsOf）。
现象：
  1) resolveLayoutDrop 先判 excluded（条、标题栏）再判面板，最后才判预备区（zones）。浮动窗可以盖在状态栏或活动栏上（计划的夹取只要求标题栏高度与 80px 宽留在树区域里），按计划“浮动窗先判”，必须在 excluded 之前；预备区也不该在“浮动窗拒绝了”之后穿透：现在 resolveLayoutDrop 在面板判定得 null 时会去找 zones，落到预备区。计划却说 resolveLayoutDrop 不变。要么改它，要么在 layout-drag 里先行判断，二选一，写明。
  2) LayoutDropInput.panels 的顺序是命中顺序（layoutDropPanelAt 用 `find`，取第一个命中的）；浮动窗要排在最前，并且按叠放从上到下、而 floats 数组是后面压前面，要反过来。缝的容差（SEAM_PX = 4，layout-drop.ts:20，“缝不是落点，归最近的能接收的那块”）也会把浮动窗外沿 4px 内的点吸进浮动窗，而浮动窗外沿不是缝。
  3) “整窗拖动时策略不接受 center”：LayoutPolicy.accepts(tabs, target, region) 只收标签，不知道来源是窗还是标签；单标签窗的标签和整窗的 tabs 相同，同一个 accepts 无法对一个说“中央可以”（撕下的标签）、对另一个说“中央不可以”。需要在拖动时包一层只对窗拒绝 center 的策略，或者改接口。
  4) 实时布局的基准矩形（frozen，306-326 行）与 panelGeometry、stopsOf、pointOfCandidate 都只遍历树；浮动窗的标签条（stripOf 用 DOM 现量，不在 frozen.strips 里）不会冻结，目标是浮动窗的标签条插入在实时布局里读的是预览之后的 DOM，而 t08 的合同是“基准是拿起时的矩形”（Spec 38）。
为什么是问题：不先写清楚，片 3 的落点会出现穿透到预备区、状态栏上方的浮动窗接收不到标签、整窗拖动经过面板中央仍被当成并入。
建议改法：把“浮动窗命中”做成 layout-drop 的一步，LayoutDropInput 加 `floats?: ReadonlyArray<{id; body; strip}>`（已按上到下排好），在 excluded 之前判；命中浮动窗后不再看 zones 与树。整窗拖动用显式参数 `source.kind === "panel"` 让 resolveInPanel 不给 center，不靠策略。panelGeometry 与 frozen 同时包含浮动窗。

F8  [重要] [拖动/实时布局] float 候选永远“不稳定”；整窗移动与卡片机制不合；窗停靠时没有东西跟手
位置：packages/neuro-book/src/plugins/workbench/web/live-drag.ts:57（keyOf）、79-86（candidateOf）、95-121（updateCard，按标签来源写死）、123-149（tick）；packages/nb-layout/src/live-drop.ts:41-51（stepLiveDrop）；计划“跟手”“实时布局”两节。
现象：
  1) 候选键是 `JSON.stringify([drop.action, drop.part])`，含 float 的矩形。指针每动一下键就变，stepLiveDrop 里 `changedAt` 每次重置，150ms 的“稳定”永远不满足，候选预览不会出现（只会停在 source-removed）。计划的“动作键只写 float”只提到会话的 actionKey，没提 keyOf。
  2) createLiveDrag 的接口全是 LayoutTabSource（homeOf、sourceRemovedDoc、candidateDoc 都按标签算），整窗来源（panel）要么扩类型要么绕开。计划说“整窗移动不走卡片”，但没写绕开的位置：activate 里 `live.begin(source, lastPointer)` 对任何来源都开帧循环、拿起卡片。
  3) “经过可停靠的位置时按当时的手感走”只有一句话，是最难的一段：整窗经过标签条或 14% 窄带，实时布局会把候选文档摆出来，浮动窗在候选文档里已经没了（并入树里），而整窗没有卡片，指针下什么也跟不上；落点指示下又要在“拖影”和“矩形反馈”之间选。需要明确：窗停靠候选时，是窗留在原处且半透明、还是缩成卡片跟手。
如何核实：代码推断（stepLiveDrop 的逻辑与 keyOf 的内容）；片 3 一做就会在手感上暴露。
建议改法：keyOf 对 float 用 `float:<panel 或 new>`，不含矩形；整窗移动不进 createLiveDrag，作为 layout-drag 里单独的分支（只改一份“浮动矩形预览”，见 F9）；窗停靠候选时复用卡片，把窗的活动标签内容抬成 lifted，其余标签随它走，先把这个手感在计划里定下来，再写进 Spec 38。

F9  [建议] [上游选择/性能] 整窗移动每帧换整份文档，会让不依赖浮动的投影、网格、可见性一起重算；风险写在计划末尾，“量一下”留到实现之后
位置：计划“跟手”与“不做与风险”最后一条；layout-doc-store.ts:122-126（renderedDoc、renderedProjection）、250-253（setLivePreview）；WorkbenchSurface.vue:89（`grid` 随 projection 重建 createGrid）；packages/nb-layout/src/layout-project.ts（projectLayoutDoc 不读 floats）。
现象：projectLayoutDoc 只读树与面板，不读 floats；但 setLivePreview 是整份文档，每帧新对象、新 tree（structuredClone），renderedProjection 随之重算，WorkbenchSurface 的 `grid` 重建、useGridLayout 重新发布布局、NestedGrid 的 layers 与 motion 重算、`watch(props.node, scope.invalidate)` 触发。计划已经承认并留给“量一下”。
为什么是问题：根因是把“只有矩形变”的状态塞进文档预览。每帧 O(树大小) 的工作白做，而且 acceptPresented 在 livePreview 非空时整个丢弃（layout-doc-store.ts:243-246），预览期间 presented 与可见性是旧的，和“每帧重建的布局”不一致，容易出现隐蔽的错位。
建议改法：浮动窗的移动与缩放预览不走 setLivePreview：在 store 里单独放 `floatPreview: Map<panel, rect>`（或 NestedGrid 的 floats 属性直接接这个），只影响 `floats` 的呈现；放下时写一次文档。这样 NestedGrid 的 `motionless` 也不需要“判定当手势”，浮动层本来就不走过渡。若仍保留 motionless：decideMotion（packages/nb-layout/src/vue/useGridMotion.ts:59-73）靠 `frame.previewing || memory.previewing` 判手势，“上一次还在手势中”的那一帧也不过渡，所以窗放下并入树的那一次布局变化（邻居让位）会瞬移，不会滑；要滑得靠 land()（t08 给卡片用的），计划没写。若仍想用文档预览，则在计划里写明测量门槛（例如 50 个面板的树，每帧耗时多少算过），而不是“慢了再说”。
