### 1. 目录一致性核对不存在，`layout-text.ts` 的注释和提案的前提都不成立
- 严重程度：重要。类别：已定设计、依赖的机制。
- 位置：`packages/nb-layout/src/vue/layout-text.ts:14`、`scripts/ci/message-catalogs.ts:46-75`、`docs/proposals/nb-layout-general-library.md:249-250`、`plan.md:5、35`。
- 现象（回答重点 3，查清了）：仓库里没有任何地方核对 nb-layout 的两份目录。
  - `message-catalogs` 只查 JSON，查的是 `CATALOG_DIRECTORIES` 登记的 20 项加清单里列出的目录，里面没有 nb-layout。
  - `i18n.md` 目录检查那段（第 123 行）写明共享包的 `.ts` 目录不在这里核对。
  - nb-form、nb-agent-ui、nb-markdown、nb-ui 各有 `locales.test.ts`，nb-layout 没有。
  - neuro-book 的 `host-text.test.ts` 只用到 `sortable.handle`、`floatWindow.move` 两个键，`text-engine.test.ts` 没提 nb-layout。
- 为什么是问题：`layout-text.ts:14` 写着“键与目录的对应由 `LayoutTextKey` 与消息目录检查守着”，这两样都没有。`LayoutTextKey` 的 14 个键与目录对象互不引用。en-US 少一个键，缺省路径就返回键名字符串。改源语言后 en-US 成了缺省和回退链的唯一兜底，这个洞更要紧。plan 第 5 行照搬了提案“message-catalogs 的检查要跟着改”，这个前提不成立。
- 如何核实：读 `message-catalogs.ts` 的 `CATALOG_DIRECTORIES`；`rg "NB_LAYOUT_CATALOGS"` 只出现在 `layout-text.ts`、`text-engine.ts` 和 `locales/index.ts`。
- 建议：补 `src/locales/locales.test.ts`，用 `const KEYS = {...} satisfies Record<LayoutTextKey, true>` 让联合类型和表双向穷尽。再核对两份目录的叶子恰好是这 14 个键，占位符规则见第 4 条。plan 的 Context 和提案 249-250 行改成“message-catalogs 不查 `.ts` 目录，由包内测试查”。

### 2. `layoutCatalogTranslate` 放进 `./locales` 会让核心依赖 `vue/text`
- 严重程度：重要。类别：已定设计、接口。
- 位置：`plan.md:21-23`、`packages/nb-layout/AGENTS.md` 边界一节、`docs/specs/ui/nested-grid.md:352`、`packages/nb-layout/tsconfig.json`（exclude `src/vue`）、`src/boundary.test.ts`。
- 现象：函数签名是 `(locale) => LayoutTranslate`，而 `LayoutTranslate` 和 `LayoutTextKey` 定义在 `src/vue/text.ts`，该文件 `import type ... from "vue"`。`src/locales/` 属于核心（“`src/` 下除 `vue/` 以外的文件”）。
- 为什么是问题：AGENTS 和 Spec 352 行都写核心“不依赖 Vue、DOM”，plan 说“只依赖目录与 `./text` 的类型”其实是核心导入 Vue 层文件。`boundary.test.ts` 抓不住，因为 CORE 规则只要求相对导入落在 `src/` 内（`within: SOURCE_ROOT`）。核心 tsconfig 虽然排除 `src/vue`，tsc 仍会顺着导入把 `vue` 类型拖进核心类型检查。
- 如何核实：读 `boundary.test.ts` 的 CORE 规则和 `import-boundary.ts` 的 `offendingSpecifiers`。
- 建议：把函数放进 `./text`（`src/vue/text.ts`）。Vue 层本来可以依赖核心，`layout-text.ts` 已经在导入 `../locales`。宿主已经从这里导入 `LAYOUT_TEXT_KEY`，两个名字出自同一个子路径。代价是改 `text.ts` 头注释“只放注入键与类型”一句，两份约 1 KB 的目录跟着进来。备选是把三个类型挪进核心再由 `text.ts` 重导出，改动更大，不推荐。

### 3. `layoutCatalogTranslate(locale)` 的行为细节没定
- 严重程度：重要。类别：接口与合同。
- 位置：`plan.md:21-23`、`layout-text.ts:15-25`。
- 现象与问题：
  - a. “不是目录里的语言按源语言”：如果用 `NB_LAYOUT_CATALOGS[locale]` 取，`"constructor"`、`"toString"`、`"__proto__"` 取到的是原型上的函数，不是 `undefined`，结果得到键名而不是回退到源语言。要用 `Object.hasOwn` 或 Map。
  - b. plan 只写了“未知语言”，没写“已知语言里缺键”。宿主引擎和 nb-ui 最小实现的链都是“当前语言 → 源语言 → en-US → 键名”（`i18n.md` 输出 4），现有 `lookup` 缺键直接返回键名。要写明缺键回源语言再回键名，并用测试固定。
  - c. 没有规范化：`"zh"`、`"zh-cn"`、`"zh-Hans"`、`"zh_CN"` 都会静默变英文。目标用户是只写中文界面的宿主，最容易传 `navigator.language`。建议把参数类型收窄成 `keyof typeof NB_LAYOUT_CATALOGS`，拼错时编译就报；运行期放宽的话要写明不做前缀匹配。
  - d. 返回的是固定一种语言的函数，README 现有的约束“函数要在每次调用时读宿主的当前语言”对它不适用。文档要写“不能运行时换语言”，否则第三方会拿它当通用入口。
  - e. 与 `useLayoutText` 缺省翻译共用一份实现后行为有没有变：把 `lookup` 加 `replace` 原样搬过去，行为不变。`PLACEHOLDER` 只用于 `replace`，带 `g` 标志也不受 `lastIndex` 影响。`inject(LAYOUT_TEXT_KEY, sourceTranslate)` 不传第三参数，函数默认值原样返回，不当工厂调用。风险只在重构时顺手改了缺键行为，所以 b 要先定。
- 有没有更小的做法：宿主自己写不会更小。nb-story 和开发者面板已依赖 nb-ui，可以用 `registerDefaultCatalog("nb-layout", …)` 加 `defaultTextPort().t(textRef(…))` 约 4 行，但每个宿主一份。第三方没有 nb-ui，需要一个公开函数。ADR 0054 第 8 条把 nb-story 定为第一个外部使用方，保留这个函数是合理的。

### 4. nb-layout 的翻译实现与另两处在占位符语法上分叉

### 8. 默认语言不对称：nb-ui 缺省端口仍固定 zh-CN

### 9. 上游选择：公开面被迁就的几处（不要求本 Task 改）
- 严重程度：建议。类别：上游选择。
- 位置：`Splitter.vue:339`、`NestedGrid.vue:348、369`、`Splitter.md:25-39`（`SplitterPanelConfig` 没有 `label`）。
- 现象：分隔线读屏名的 `before`/`after` 直接取面板 id 或叶 id。nb-story 的 id 是 `nav`、`main`、`drawer`，应用里是 `section:<id>`、`center`、`g0`（e2e 的正则就按这些写）。英文模板下读成 `Resize width between nav and main`，第三方得把 id 起成人话才可读，不传 id 时是 `panel-0`。
- 代价：宿主靠 id 兼做显示名，改 id 会破坏 e2e 和持久化的布局，因为 id 同时是身份。公开面补一个可选的 `label`（Splitter 的面板配置、NestedGrid 的叶）就能脱钩。这属于 ADR 0054 第 8 条“第二档由 nb-story 校验公开面”的自然一条，这里只列不做。
- 另外，英文目录 `splitter.pixels` 是 `{{size}} pixels`，size 为 1 时读成 `1 pixels`。库不处理复数（提案 248 行已写明），范围小，记为已知限制即可。
