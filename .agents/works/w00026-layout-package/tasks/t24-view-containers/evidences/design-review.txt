[F1] 阻断｜持久化、依赖的机制｜提案第 6 节、“影响”的数据与回滚
现象：提案说“布局记录……格式版本加一”，同时说旧记录“按输出 32 前后的读取规则，不合新骨架的记录回落默认树并给诊断（2026-11-06 的先例）”。这两句走的是 store 里两条不同的路径。
为什么是问题（读到实现）：2026-11-06 的先例是“合法但不合骨架”：validateLayoutDoc 通过、fitsSkeleton 不过 → 默认树、下次保存覆盖（packages/neuro-book/src/plugins/workbench/web/state/layout-doc-store.ts:88-94 的 outsideSkeleton）。版本加一以后旧记录在 validateLayoutDoc 里就返回 unsupported-version（packages/nb-layout/src/layout-doc.ts:887），recordProblem 非空 → guarded 为真（layout-doc-store.ts:72-79）→ save() 第一行直接 return（layout-doc-store.ts:160），状态栏是“布局未读”。即：开发者本机每一份 v1 记录在升级后都会让这个窗口的布局永远存不下去，每次刷新回到默认树。若改的是 records.ts 的 record version（records.ts:27-32 都是 version: 1），field.base.status 是 unsupported-version，同样 guarded。“回滚：格式版本退回即回落默认树”也一样不成立：旧代码读到 v2 记录同样 guarded、不保存。提案也没写加的是 LayoutDoc.version 还是 record version。
如何核实：layout-doc-store.test.ts 里放一份 version: 2 的 doc，改一次布局，断言 field.commit 没被调用；或读上面三处代码。
建议：二选一写进提案并进 Spec 的读取规则表：(a) 版本号不动，让新的 validateLayoutDoc/fitsSkeleton 把旧形状判为“合法但不合骨架”，真正复用 11-06 的先例；(b) 版本加一，同时新增一行“已知的旧版本（v1）：默认树、诊断、下次保存覆盖”，与“不认识的版本：保护原件”分开。回滚那句按所选方案改写。

[F2] 阻断｜依赖的机制、接口与合同｜提案第 1 节“模型”、“影响”的 nb-layout 一条；Spec 输出 2
现象：提案把容器栏、容器都建成“树上的一种分支”，容器“沿容器栏方向排列”，并称 nb-layout 只需“支持一次显示一个子节点的分支（停放已有）”。
为什么是问题（读到实现）：
1. 规范形会吃掉它们。normalizeTree（packages/nb-layout/src/layout-doc.ts:191-209）同轴嵌套展平、单子分支塌陷，每次结构操作经 finish()（:280-283）都过一遍；detachNode（:211-226）摘节点时也塌陷单子分支。容器栏的方向无论取哪个都会被展平一层：取纵向，侧栏的容器（纵向）展平进容器栏；取横向，容器栏本身展平进横向的 body。只有一个分节的容器（提案自己的例子 c2“对话”）是单子分支，下一次任何结构操作就塌成那块叶，身份 {id, origin, title?, icon?} 随之丢失；只有一个容器的容器栏也一样。
2. 分支上没有放元数据的位置。GridSnapshotBranch 只有 kind/id/orientation/size/children，parseSnapshot（grid-snapshot.ts:160-196）按字段重建对象，多余字段直接丢；validateNode（layout-doc.ts:860-879）只认 leaf/branch 两种 kind。active、容器身份、容器栏的 hidden 都没处放。若放在旁路记录（像 panels 那样按 id 索引），分支 id 又不稳定：placeLeaf 用 policy.newId("branch") 新建、塌陷时由幸存者代表（aliases），记录会成孤儿。
3. 比较函数看不见它们。sameTreeShape/sameLayoutShape（:247-265）不比分支 id、不比任何分支属性，finish() 在“结果与现状一样”时返回原对象：只改 active 的切换会被判成无变化，不提交。
提案没提输出 2，Spec 改动表也没列输出 2。
如何核实：用现有 normalizeTree 对 V[sidebarBar: V[c1: V[a, b]], …] 或 H[…, sidebarBar: H[c1: V[a]]] 跑一次即见；单分节容器调 detachNode 任一兄弟即塌陷。
建议：提案写明容器栏与容器在库里是什么：(a) 新的节点种类（GridSnapshot 版本、validateNode、parseSnapshot、normalizeTree、detachNode、countScale、projectLayoutDoc 都要认，“库里不加新种类”那句要改），或 (b) 分支加一个宿主不透明、规范形不展平不塌陷的标记（例如 pinned），元数据放 LayoutDoc 新字段按分支 id 索引。两种都要给 sameLayoutShape 与 layoutStructureKey 加上这部分。

[F3] 重要｜依赖的机制、隐含的共享状态｜提案第 1 节“别的子节点整棵停放”、“nb-layout……停放已有”
现象：提案认为不活动容器“只是看不见的子树，结构操作照旧”，停放“不需要新机制”。
为什么是问题（读到实现）：内容不卸载这一半确实有（nested-grid.md“内容层”：叶暂时找不到的内容项按停放处理）。但“这块叶此刻不在”在库里只有两条通道，都接不上：
1. 叶级 panel.hidden：校验只许具名面板隐藏（layout-doc.ts:936），而且隐藏一个容器要逐个改它全部分节，切回来时分不清哪些是用户本来隐藏的。
2. LayoutProjectionOptions.removed：这是“放不下被收走”的集合，presentationCollapse 的 overflowOf 用 {...options, removed} 整个覆盖它（layout-project.ts:144-146），工作台的 projectionOptions 也直接拿 collapse.value.removed 填（layout-doc-store.ts:118、120）。把不活动容器塞进去会被覆盖，或者让“放不下”的诊断与恢复把它们当成可放回的面板。
而判定“占不占地方”的 isNodeShown/countsInShare（layout-doc.ts:148-160）只看 panel.hidden 与条：不活动容器的分节对它们来说是“显示着”。后果：enumerateDropCandidates（layout-drop.ts:419、434）把不活动容器里的分节列成键盘落点（输出 31 的 Tab 区域里会出现看不见的面板）；edgeTargetOf（:503）、edgeTargetTouches（:601）在找相邻兄弟时把不活动容器当可见邻居；normalizeTree 的份额换算（:281）与 placeLeaf 的 shared 分配（:540）把不活动容器算进份额。presentationCollapse 的 shown 集合（layout-project.ts:150）也会把不活动分节排进“收走”队列。
如何核实：读上述行；或在 enumerateDropCandidates 的单测里放一个两容器的文档，断言候选里没有不活动容器的面板。
建议：提案写明“不活动”在模型里是什么（容器栏的 active 字段），并列出必须认它的函数：isNodeShown、countsInShare、projectLayoutDoc、presentationCollapse 的候选集、enumerateDropCandidates、effectiveVisibleTabs、moveTargetsOf、F6 顺序。最好让 isNodeShown 一处认它，其余经它，避免逐处特判。另：提案写“同输出 10 的停放”，停放的定义在输出 16 与 nested-grid“停放”，输出 10 是放不下只改呈现，引用改一下。

[F4] 重要｜遗漏、接口与合同｜提案第 1 节“三个容器栏……取代现在的具名面板”、“影响”、“对 Spec 的预期改动”
现象：具名面板 sidebar/auxiliarybar/panel 被容器栏取代，但提案只在“接口”“命令”两处列了影响。
为什么是问题（读到实现）：名字是工作台里一大串规则的挂钩点，grep 到 packages/neuro-book/src/plugins/workbench/web 下 14 个文件约 37 处按 name 或 "sidebar" 判断。提案没给它们去处的几类：
1. 尺寸约束：panelConstraints 按 panel.name 给侧栏 160–560、右栏 160–max(360, 0.45 视口)（layout-constraints.ts:69-70）；projectLayoutDoc 只对叶问约束（layout-project.ts:111），分支没有约束输入。具名面板没了以后分节各拿“其它工具面板”的约束（宽至少 160、无上限），侧栏上限 560 与默认 340 无处安放。并且切容器会改约束：不活动容器不在呈现树里，侧栏的最小宽就只取当前容器各分节声明的并，换一个容器最小宽可能变，侧栏宽度跟着跳。这违反提案自己的“切换不改任何尺寸”和输出 6“切标签不改布局”的同一原则。
2. 放不下时的收走顺序：COLLAPSE_ORDER = ["auxiliarybar","panel","sidebar"] 是面板 id（layout-constraints.ts:65），容器栏下面的分节都是无名面板，这张表失效，全部落到“其它工具面板”按树序收，侧栏的分节会先于右栏被收走（输出 10 的顺序被打破）。
3. 骨架判定：fitsSkeleton/isToolRun 要求这一列“全是叶、恰一个具名”（default-tree.ts:69-91），全部重写；提案只说“输出 26 的骨架约束不变”。
4. 其余按名字的：toolPanelAxis（:93-98）、sidebarColumnPanels/titleOnlyPanels（layout-present.ts:82-95）、panelTitle、canResetView（:139-143）、reconcileViews（default-tree.ts:56）、settleEmptyPanel 的“具名面板拖空隐藏”（layout-doc.ts:369-374）、moveTabToEdge 的“具名面板不移动”、layout-drag.ts 的 SIDEBAR 常量（t23 分支 :152、:357-367）、public-state 的 focusedPart 取 current.name（public-state.ts:49）。
Spec 改动表因此漏了输出 3、4、7（谁保留像素，侧栏现在保留、容器栏呢）、10、11、13、16、27（具名面板不移动）、35、36、39（回到停靠“各回声明的具名面板”），以及 views.md 输出 9、13、14。
如何核实：grep -rn '\.name ===\|\.name !==\|"sidebar"' packages/neuro-book/src/plugins/workbench/web。
建议：提案加一节“具名面板的去处”，逐项写替代：约束挂在容器栏上（nb-layout 要支持分支约束，或由工作台换算到当前容器的分节上，并说明切容器时取全部容器的并以免跳宽）；收走顺序按容器栏；骨架判定改按容器栏；focusedPart 取容器栏名。Spec 改动表补齐上面漏的输出号。

[F5] 重要｜边界、违反既有约定｜提案第 1 节“隐藏与显示仍按容器栏整体”、第 3 节活动栏点击；Spec 输出 11、12、22
现象：提案只处理了容器栏的“隐藏”，没有处理“拖到零”“放不下被收走”“被最大化盖住”；活动栏点击改成“是当前的就隐藏侧栏”。
为什么是问题：
1. 拖到零变得看分节数（读到实现）：收起状态只挂在叶上，assignByParent 遇到分支直接 continue（layout-project.ts:52-56），collapsed 也只在 PanelRecord 上。呈现里不活动容器摘掉后，容器栏塌成当前容器；当前容器只有一个分节时塌成叶，侧栏能拖到零；有两个分节时幸存者是纵向分支，没有收起状态，侧栏拖不到零。用户看到同一条侧栏边界，一个容器能拖没、另一个不能。拖到零记在当前分节上，切到别的容器侧栏又整宽弹开，切回来又是零宽。
2. 点击语义退化：现在是“不可见时显示、可见时隐藏”，按有效可见判（layout-present.ts:66-75 toolEntryIntent，输出 22）。提案改成“是当前的就隐藏侧栏”：侧栏被拖到零、放不下被收走、被别的面板最大化盖住时，点当前容器的图标会把侧栏隐藏，而用户要的是让它出来；输出 11 表里“拖到零 → 怎么回来：活动栏”这条恢复路径被断掉。
3. 按下态没定义：现在条目按下 = 视图有效可见。容器的按下态是“active 且容器栏有效可见”，还是“active”？当前容器全部分节收成标题行时算不算？提案没写，而“更多”溢出的优先级（WorkbenchToolStrip.vue:87 按 pressed 排）依赖它。
如何核实：读 layout-project.ts:48-70、layout-present.ts:66-75；拖到零的差异可用 projectLayoutDoc 对两种容器各投影一次看 collapse 字段。
建议：收起（零宽）与隐藏一样挂在容器栏上，由工作台在呈现时把它落到当前容器的外沿（或 nb-layout 支持分支收起）；点击按“容器栏里当前容器有效可见”判：可见就隐藏，不可见（隐藏、零宽、被收走、被盖住）就显示并展开；按下态 = 当前容器且容器栏有效可见，写进输出 22。

[F6] 重要｜依赖的机制、与已定设计冲突｜提案第 4 节“实时布局下预览就是切到那个容器”、第 5 节“吸收、来源收起一次、限位排序（t23）照旧”
现象：拖到不活动容器的入口上时，预览把侧栏整块换成那个容器。
为什么是问题（读到实现，t23 分支）：实时布局的判定几何是拿起时量的一份（layout-drag.ts:166 的 frozen），之后只按来源收起前后的差挪（collapseSource，:206-215）。不活动容器的分节拿起时不在 DOM 里，panelRect 返回 null（:217-220），frozen 里根本没有它们。预览切到 c2 之后，屏幕上是 c2 的分节，判定用的还是 c1 的矩形：指针移进侧栏，落点算成 c1 的某个分节（看不见）→ 预览按这个候选把侧栏换回 c1 → 指针下又变了，来回翻。这正是同一文件对隐藏侧栏已经写明不做的事：“隐藏的侧栏在预览里不展开，放下才展开：几何是拿起时量的，那时没有它，展开后指针进去会按旧矩形判到别处，预览又把它收回”（layout-drag.ts:197 注释，以及 Spec 输出 38 末句“侧栏隐藏时放到活动栏，预览里侧栏不展开，条目照样让位，放下才展开”）。切容器是同一问题的放大版。
另外，结构键 layoutStructureKey（layout-present.ts:150-153）只含拓扑与标签集合；命令或快捷键在拖动中切了容器，拖动不会取消，冻结的几何整块过期。
如何核实：读 layout-drag.ts:166、:190-220 与 live-drag.ts:6；用 t23 的实时布局把视图拖到一个预览会改变侧栏内容的落点上即可复现同类回摆。
建议：与隐藏侧栏一致：入口上的预览只让条目让位、侧栏不换内容，放下才切到那个容器、它出现在末尾；想放进不活动容器的指定位置，先放进去再在容器里换序。若一定要预览切换，就要写“切换时重量判定几何、并重置来源收起状态”，这与 t23 的“一场一次、拿起时冻结”冲突，需开发者取舍。同时把“容器栏的 active”加进结构键：拖动中被别处切了容器就整场取消。

[F7] 重要｜接口与合同、照字面实现会返工｜提案第 2 节“分节标题是插入位”“分节正文的中央不再是添加为标签”；Spec 输出 20、25、26、37、38、39
现象：提案只说中央“不再是”什么，没说“是”什么；“一个分节只有一个标签”这条不变量也没有执行点。
为什么是问题：
1. 中央没有结果。输出 25 第 6 行“正文中央：添加为标签”被拿掉后，分节正文中间 44%（外缘窄带各 28%）落在什么上没写。按现有规则（输出 25 第 3 段）工具面板只往一个方向分，不允许的边的窄带上“被拒绝”；若中央也拒绝，分节正文大半是禁止光标、松手取消，松手在那里也不开浮动窗。若归最近的外缘，enumerateDropCandidates 里只有“空面板整块是中央”的特判（layout-drop.ts:424），没有“整块都是外缘”的写法。
2. 与“只写标题的头”的现行规则逐条冲突：输出 20“只写标题的头没有插入位，拖到头上是添加到最后”、输出 25 第 4 行“头只写标题的面板没有插入位，等于中央”、输出 38“头只写标题的面板……算中央”、输出 37“只写标题的头算中央，分区照画”。提案说“分节标题是插入位（放成新分节）”，但没说放在这个分节之前还是之后（底部面板分节左右排时更不清楚），也没改输出 37 的分区形状。
3. “一个标签”没有执行点（读到实现）：insertTab、moveTabToStrip、movePanelToStrip、showPanelAndInsert（layout-doc.ts:386、443、464、788）都能往一块工具面板里塞第二个标签；LayoutPolicy 里唯一能拒的钩子是 canInsert。reconcileViews（default-tree.ts:51-62）也是往面板标签末尾 insertTab。浮动窗是“带标签的组”，可以有多个标签，整窗停靠“全部标签一起并入”（输出 39），停进分节就违反一个标签；“回到停靠：工具视图各回声明的具名面板”也要改成各回声明的容器、各成一个分节。
如何核实：读 layout-drop.ts:88-131（resolveInPanel）与 :408-430；读 Spec 输出 20、25、37、38、39 原文。
建议：明确写：分节没有中央，正文按指针在上半还是下半（底部面板按左右半）放成它前或后的新分节，与 VS Code 一致；分节头是“放到它之前”。“一个标签”由工作台在 policy（accepts/canInsert）与 store 的 apply 出口两处守，所有往分节加标签的入口（移动到、reconcileViews、停靠、视图打开）改成“新开分节”；多标签浮动窗停靠时拆成多个分节，按标签顺序。Spec 输出 20、25、37、38、39 列入改动表。

[F8] 重要｜遗漏、依赖的机制｜提案第 2 节“一个容器只有一个分节时，分节不画自己的头，标题由入口与容器栏的头给出”、第 3 节“右栏、底部面板：头上是容器的入口条”
现象：提案假定容器栏有一个“头”，但没说它是什么、占不占几何、侧栏有没有。
为什么是问题：
1. 头没有几何来源（读到实现）：nb-layout 只给叶画外框与头，内容项的 insetTop 是叶级的（layout-present.ts:19-27，PANEL_HEAD_HEIGHT），分支没有头、没有内边距。容器栏是分支，它的“头”（右栏的图标入口条、底部面板的标题入口条）要么是新的条叶（树上多一片，骨架判定要改），要么借第一个分节的头（多分节时入口条与第一个分节的标题挤一行），要么分支支持 insetTop（库要加能力）。提案的“库里不加新的叶子种类”与这三条都冲突，且没选。
2. 侧栏单分节容器没有头：侧栏的入口是活动栏，提案没给侧栏容器栏一个头。“会话”单独成一个容器时，分节不画头 → 这个视图的标题、视图标题动作（views.md 输出 10、11）、框架按钮（浮动、收起、最大化、隐藏，输出 20）、以及“侧栏这一列的标题是拖动来源”（输出 24、31）全都没地方放。现在单视图面板的头恰好承担这几样（WorkbenchPanelHead.vue:115-125 的动作区与框架按钮）。
3. 头里放什么没分配：右栏、底部面板的头是入口条之后，原来头上的隐藏、最大化、浮动、“⋯”放哪；最大化、浮动作用于分节还是整个容器栏；单分节时视图动作进不进容器栏的头。

建议：提案加“验收要点”小节，至少列：(1) 1440×900 下 c1 两分节、c2 一分节，切 c2 再切回，侧栏宽、各分节高与折叠逐项相等，记录只写 active；(2) c2 的视图在 c1 当前时 ViewContext.visible 为假、创建 1 次卸载 0 次；(3) 单分节容器经过一次别处的拆分/移动后，入口与身份不变；(4) 写一份 v1 记录，打开后改一次布局，记录被覆盖为新版本；(5) 实时布局把视图拖到不活动容器入口上停 1 秒再移进侧栏，预览不来回切；(6) 声明的容器所在插件卸载后入口与占位。同时把 views.md 输出 10 的悬停范围改成“分节”与“容器头”。

[F18] 建议｜上游选择、别扭之处｜提案第 1 节末段“为什么是树上的一个分支，而不是把不活动的容器存在树外”
现象：提案用单树提案“取消跨树移动”的理由否定了“不活动容器存在树外”。
为什么值得重看（从代码推断）：单树提案要消除的是“几棵树各有一套移动规则、编辑器节点移不到外层”（workbench-single-tree-layout.md 问题 1）。树外存放不活动容器时，进入不活动容器的操作只有两种：拖到入口上（提案已定为“作为最后一个分节”）与“移动到”某容器——都是往一份记录末尾追加一个分节，不需要树内的拆分、缝、外缘规则；切容器是一次“当前子树存回记录、目标子树换进来”的整体替换。反过来，把不活动容器留在树上的代价是 F2（规范形与元数据）与 F3（isNodeShown、countsInShare、投影、收走、键盘候选、edgeTarget 邻居等至少 8 个函数要认 active），以及 F4 的约束随容器跳。树上永远只有“看得见的东西”，现有不变量（树上的面板要么可见、要么隐藏/收起/零宽）也不用加第五种状态。
这不是说提案错了，而是理由只写了一边：两种做法的部件数与特判数没有对比。
如何核实：数 F3 列出的需要认 active 的函数；对照“树外”方案需要的操作：switchContainer、appendToContainer（记录内）、容器记录的校验。
建议：在“备选与取舍”里把两种做法并排写：各自新增的状态、要改的函数、规范形与比较函数是否要改、切换与拖入的实现；交开发者选。若仍选树上，就按 F2、F3 的建议补齐。
