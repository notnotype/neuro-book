# 第二轮设计审查：w00026 t24 工作台的视图容器（docs/proposals/workbench-view-containers.md 改稿，提交 011aa59f5）
# 审查者：Claude 子代理（只读）；代码以主工作区 master 为准。
# 每条：严重程度｜类别｜位置；现象；为什么是问题；如何核实；建议改法。“读到实现”与“从代码推断”分开标。
# 编号 R1、R2……按核实的先后追加，不是影响排序；影响排序见文末索引。

[R1] 阻断｜依赖的机制、遗漏｜提案第 1 节“区域取代具名面板的名字”“区域里是普通的工具面板”、第 5 节“区域没有容器时隐藏”
现象：改稿把三个区域的身份从具名叶改成“从树算”（regionOf），但没写一个区域里一块面板都没有时树上留什么、区域的“隐藏”记在哪。
为什么是问题（读到实现）：现在这三件事都挂在具名叶上：(1) 位置：具名叶拖空只隐藏、不移除（layout-doc.ts:369-375），默认树里三片具名叶一直在（default-tree.ts:17-47），所以 body 恒有 4 个子节点、center 恒是分支，fitsSkeleton 才写得成 children.length === 4（default-tree.ts:82-92）；(2) 隐藏：setPanelHidden 拒绝无名面板（layout-doc.ts:760），校验同样（:936）；(3) 默认尺寸：隐藏的具名叶上的意图。
空区域不是边角：产品里没有任何 location 为 panel 的视图（第一轮 Z7 的证据），所以默认布局的底部面板区域恒为空；视图目录是陆续交进来的（layout-doc-store.ts:53 注释），启动瞬间三个区域都为空。
没有锚时规范形会改掉骨架。实验（/tmp/review-w00026-t24-design-r2/exp/exp1.ts 实验 C，bun 直接跑 nb-layout 源码）：编辑区左右分着、底部只剩一块无名分节，removeTab 之后树是 V[H[活动栏, s1, g0, g1, x1], 状态栏]：center 分支塌陷、编辑组被展平进 body（5 个子节点）；再拿走侧栏唯一的分节是 H[活动栏, g0, g1, x1]。此时 regionOf 只能靠“在编辑组之前还是之后”猜，底部区域没有任何节点可问；往底部放回一个分节要把 [g0, g1] 重新包进一个纵向分支，nb-layout 没有这种操作（placeLeaf 只会分一块叶或插进已有分支，layout-doc.ts:512-570）。store 的出口现在会以“不合骨架”拒绝这类结果（layout-doc-store.ts:203），即最后一个分节拿不走。
如何核实：bun run /tmp/review-w00026-t24-design-r2/exp/exp1.ts 看“C”两行；读上面几处。
建议：提案写明选哪一种：(a) 三片具名叶留作区域的锚（零标签、不属于任何容器、永不进呈现树），regionOf 就是“和哪片锚同一列/同一排”，fitsSkeleton 的 isToolRun 基本不动，区域的隐藏仍是锚上的 hidden，set-part-hidden 与校验都不用改；(b) 记录里加 regions: {sidebar: {active, hidden, …}}，并给 nb-layout 加“在骨架的这个位置建一列”的操作、改写 fitsSkeleton 允许 3 到 5 种 body 形状。(a) 部件少得多，但它等于承认名字还在，第 1 节“不再按面板名”的说法要改成“规则按区域问，区域由锚定位”。

[R2] 重要｜违反既有约定、第一轮 D5 第 1 点没解决｜提案第 3 节“侧栏被拖到零或隐藏着就展开”；Spec 输出 11、12、22
现象：改稿默认“侧栏被拖到零”是区域的状态，但收起状态仍只挂在叶上，区域是几块叶时没有这个状态。
为什么是问题（读到实现）：assignByParent 只给叶配收起策略，遇到分支 continue（layout-project.ts:52-58）；状态存在 PanelRecord.collapsed，含义看呈现时父分支的方向（:63）。
1. 默认布局就撞上：改稿默认的侧栏容器“项目”有两个分节（会话、资源管理器），侧栏这一列在呈现里是纵向分支，没有收起策略。实验 A：两块叶的列 collapse = undefined，单叶的右栏 collapse = {collapsedSize: 0, …}。即默认侧栏从“能拖到零”（输出 11、12）变成只能拖到最小宽 160 就停，输出 11“拖到零 → 拉开边界，或活动栏”这一行对默认布局失效。
2. 单分节的容器能拖到零，零宽记在那块叶上。切到别的容器侧栏整宽弹回；再点回这个容器的图标，按第 3 节“不是当前的就切到它”，切过去的是一块 collapsed 的叶，侧栏变成零宽：点图标反而让侧栏消失。第 3 节的“拖到零就展开”只写了“是当前的”那一支。
3. 同一个 collapsed 两种含义：单分节时是零宽，往这个容器再放一个分节后它的父分支变纵向，同一个标志变成“收成标题行”，侧栏凭空回来、这个分节成了一行标题。expandWhereAxisChanged 只比文档树里的父方向（layout-doc.ts:268-277），而这里变的是呈现里的父方向，接不住。
4. 第二步更重：右栏、底部面板有入口条（条节点）之后，区域在呈现里恒是“入口条 + 分节”的分支，永远拖不到零（见 R5）。
如何核实：实验 A 的输出；读 layout-project.ts:49-69。grid 本身支持分支带 collapse（grid-types.ts:67-80 的 GridBranch.collapse），缺的是状态放哪、谁来配。
建议：零宽与隐藏一样是区域的状态（R1 选 (a) 时放在锚上，选 (b) 时放 regions 里），projectLayoutDoc 把收起策略配在区域这一列在呈现里的那个节点上（叶或分支都行）；分节自己的 collapsed 只表示“收成标题行”。第 3 节补一句：切到别的容器时清掉区域的零宽与隐藏。

[R3] 重要｜依赖的机制、第一轮 D8 的处理引入的新问题（只影响第二步：右栏与底部面板）｜提案第 3 节“入口条……是树上的一个条节点（同活动栏、状态栏）”
现象：改稿用“条节点”给右栏、底部面板的入口条找几何来源，并说它和活动栏、状态栏同类。现有的条在库里有四条专门规则，入口条照搬后每条都出问题。
为什么是问题（读到实现，加实验 /tmp/review-w00026-t24-design-r2/exp/exp2.ts）：
1. 条两侧的缝宽恒为 0（layout-project.ts:98），零宽缝不可拖（SashHandle.vue:62-63 标 aria-disabled，useSashGesture.ts:139-147 据此 enabled: false）。底部面板的入口条在分节上面，规范形把它展平成 center 的直接子节点（实验：["g0","panelentries","p1"]），它上下两条缝都是 0（实验：0 0）。结果底部面板的上边界拖不了：调高度、拖过最小值收起（输出 9、12）都没有入口。
2. 区域这一列在呈现里恒是“入口条 + 分节”的分支，分支没有收起策略（实验：auxcol collapse = undefined）：右栏从此拖不到零。唯一的分节的 collapsedSize 从 0 变成 32（父分支成了纵向），即右栏默认的“对话”能被收成一行标题，上面还留着一行入口条。
3. 放不下时收走的只有面板（presentationCollapse 的队列只列工具面板，layout-project.ts:150-151；条只看 hiddenBars，:101-103）。实验：520 宽时 x1 被收走，入口条还在呈现树里，并且继承了这一列的 400 宽（body 的子节点是 ["activitybar","s1","center","auxentries"]）：一条空的入口条占着右栏的位置。区域隐藏、区域里没有容器时同理，要另写“入口条跟着区域走”的派生规则，hiddenBars 是用户开关（set-part-hidden 的 part），不能混用。
4. 校验写死“条恰各一个”与两个名字（layout-doc.ts:856、:901、:906）。旧代码读到带入口条的新记录是 invalid（实验 D：“不认识的条”），见 R4。
5. 默认右栏只有“对话”一个容器一个分节：第 3 节“只有一个容器时入口条只写它的标题”，第 2 节“容器只有一个分节时，头照旧画”。两句合起来，默认右栏顶上是两行都写“对话”的标题（32 + 32px），比现在多一行。
6. 底部面板的区域不是一棵子树：入口条与分节（或分节那一排）是 center 的并列子节点，regionOf、fitsSkeleton、“整个容器搬到别的区域”都要按“入口条和它后面那一个兄弟”来认。
如何核实：bun run /tmp/review-w00026-t24-design-r2/exp/exp2.ts；读上面几处。
建议：先定“只有一个容器的区域不画入口条、不进呈现树”（默认布局就没有第 5 点，也和现在一样高）。有两个以上容器时再出现；并在提案里写明入口条与活动栏、状态栏的四处不同：它外侧那条缝可拖、位移传给后面的分节；收起策略配在整个区域上（同 R2）；跟着区域一起隐藏与收走；校验按“每个区域至多一个”。或者不进树：入口条画在区域外框的头里，几何由区域第一块与最后一块分节的矩形并出来（底部面板分节左右排，入口条横跨它们），拖动的插入位从 DOM 量，同现在的活动栏上段（layout-drag.ts:339-352）。

[R4] 重要｜遗漏（兼容与回滚）｜提案“影响”的“回滚：去掉两项字段即回到现在的模型，记录按‘不合骨架’回落默认布局”
现象：回滚这句只在很窄的条件下成立。
为什么是问题（读到实现，实验 D）：旧代码读新记录时，多出来的 containers、active 字段确实被忽略（实验：只多两项字段的记录校验通过），随后因为树里没有具名面板，fitsSkeleton 不过，走“不合骨架”那条路，可以覆盖。但只要新记录里出现下面任何一样，旧的 validateLayoutDoc 返回 invalid，recordProblem 非空，guarded 为真，save() 第一行就返回（layout-doc-store.ts:73-79、:160）：这个窗口的布局从此不保存，正是第一轮 D1 要避开的那条路。
- 入口条的叶（第二步）：“不认识的条：auxiliarybar-entries”；不用 bar: 前缀则是“叶的引用不对”（layout-doc.ts:906-910）。
- 无名面板带 hidden（若区域的隐藏落在分节上，见 R1）：“只有具名面板会隐藏”（:936）。
- 条的个数不是恰各一个（:901）。
反过来新代码读旧记录也有同样的约束：新的 validateLayoutDoc 不能因为缺 containers、因为旧记录里有 name 与具名面板的 hidden 而判 invalid，这两类检查必须放在 fitsSkeleton 一侧；提案第 6 节没有写这条分工。
如何核实：bun run /tmp/review-w00026-t24-design-r2/exp/exp1.ts 看“D”三行。
建议：回滚那句改成写清条件（第一步成立；第二步引入新的叶之后回滚会让窗口不保存，除非旧代码先发一版把“不认识的叶”改判为不合骨架）。第 6 节加一句：容器相关的一切不一致都由工作台的骨架判定处理（默认布局、可覆盖），库的校验只管形状且对旧字段宽容。

[R5] 重要｜隐含的耦合与共享状态、接口与合同｜提案第 1 节 containers 的 members、第 2 节“由文档操作保证”、“影响”的 nb-layout 一条
现象：members 记面板 id，但没有一处写谁在结构操作之后更新它；“影响”里 nb-layout 只列了“可见判定收到 isNodeShown；不加节点种类”。
为什么是问题（读到实现）：面板 id 的去留由 nb-layout 的操作决定，逐个事件看：
| 事件 | 现在跑的操作 | 面板 id | 清单要怎么变（提案没写） |
|---|---|---|---|
| 分节拖到另一个区域的分节旁 | moveTabToEdge → 只有一个标签的无名面板走 movePanelToEdge（layout-doc.ts:643-645、:607-633） | 不变，叶搬走 | 从原容器删、加进落点那块所在的容器；不改的话面板在右栏的树里、却列在侧栏容器的成员里 |
| 分节浮出 | floatTab（:680-695）：摘标签、policy.newId 建新面板，旧面板经 settleEmptyPanel → removePanelNode 删除（:369-384、:343-351） | 换新 id，旧 id 消失 | 旧 id 成孤儿；新 id 不该属于任何容器 |
| 浮动窗拖回某个分节旁 | movePanelToEdge 的浮动分支（:611-631） | 不变 | 加进落点所在的容器 |
| 多标签浮动窗停靠 | 同上，整块面板连同全部标签成一片叶 | 不变 | 第 2 节要“每个标签成一个分节”：现有操作做不到，要新操作并新建 N-1 个 id |
| 框架按钮“回到停靠” | store 的 dockFloat 逐个 moveTabToStrip 进具名面板（layout-doc-store.ts:287-307） | 浮动窗的 id 消失 | 整段要改成“各回声明的容器、各建一个分节”，提案第 7 节没列 dock |
| 关掉视图的占位 | closeTab → removeTab（:412-419），无名面板移除 | 消失 | 孤儿成员；容器空了要删（custom）或隐藏入口，当前容器空了要换 |
| 视图声明消失 | reconcileViews 只加不删（default-tree.ts:50-63），占位留在树上（输出 4） | 不变 | 不用变；但隐式、用户容器的标题图标取“第一个可见成员视图”的声明，声明没了取什么没写（外壳抽象第 3 节的第 4 级兜底没被带过来） |
| 插件装上新视图 | reconcileViews 现在是往具名面板 insertTab | 要新建面板 | 见 R6 |
说明：aliases 只把塌陷掉的分支 id 映射到幸存者（:211-232），面板 id 从不经它改名，所以“改 id”这条路不存在；真正会换 id 的只有浮出与拆出新面板（:654、:688）。
这些操作都在 nb-layout 里，而“一个分节一个标签”还要求 insertTab、moveTabToStrip、movePanelToStrip、showPanelAndInsert（:386、:443、:464、:788）与 applyNewTab（layout-drop.ts:304-318）认出目标是分节并改道成新建分节。库现在不知道区域（default-tree.ts:79-80 注释：骨架是工作台的规则，库不知道）。所以实际影响面是 nb-layout 的全部结构操作，不是一个函数。
清单与树对不上的记录怎么读也没写：第 6 节只列了“没有这两项”“区域里有多标签面板”两种。成员指向不存在的面板、区域里的面板不属于任何容器、一块面板在两个容器里、成员是编辑组或浮动窗、容器的 region 与成员在树里的位置不一致、active 指向没有成员的容器，这六种都能由上表的漏改产生。
如何核实：读上表各行的代码；layout-doc.test.ts 里任取 floatTab 的用例，看结果里旧面板 id 已不在 panels。
建议：归属记在面板上，不记清单：PanelRecord 加 container?: string（浮动窗与编辑组没有）。面板搬到哪归属跟到哪，面板删了归属跟着没，容器里的先后本来就是树序（第 1 节已这样定），sameLayoutShape 的逐面板比较加一项即可（layout-doc.ts:258）。记录里只剩入口的顺序 [{id, region}] 与每个区域的 active。要处理的只剩两处：新建的面板继承落点那块的 container（placeLeaf 一处），以及出口统一做一次对账（容器没有成员则删或隐藏入口、active 回落）。读记录时对不上的统一走“不合骨架”，不走 invalid（见 R4）。

[R6] 重要｜与已定设计冲突（改稿自己的“不预览切容器”）、依赖的机制｜提案第 5 节“当前容器被拖空：切到……前面的那个容器”与“实时布局下不预览切容器”；Spec 输出 38
现象：两条规则在“来源收起”时相撞：拿起当前容器唯一的分节，预览里来源一收起，当前容器就空了。
为什么是问题（读到实现）：实时布局的来源收起就是在已提交的文档上 removeTab，把结果当预览摆出来，并按这份文档重算判定几何（layout-drag.ts:202-214；live-drag.ts:174-195 的 host.show(host.sourceRemovedDoc(from))）。removeTab 之后这块无名面板被移除（layout-doc.ts:412-419、:369-384）。改稿下它是容器唯一的分节时：
- 如果“被拖空就切到相邻容器”是文档操作的一部分（记录要自洽，active 不能指向没有成员的容器），预览里这个区域立刻换成相邻容器的分节。这些分节拿起时不在页面上，冻结的几何里没有它们；collapsed() 只挪“两份文档里都有矩形”的面板（layout-drag.ts:471-486）。指针移到它们上面时没有面板可判，layoutDropOverPanel 为假，落到“明确的无落点”：松手开浮动窗（:598-604）。用户看到的是把视图放进了侧栏的某个分节旁，结果是开了一个浮动窗。这正是第 5 节给“不预览切容器”的那条理由。
- 如果预览里不切，区域在预览里是空的（或收起），放下才切：预览与结果不一致，要明写，而且“预览里这个区域是什么样”也要定（空着占位，还是让编辑区先占过去、放下再弹回）。
这是缺省情况：改稿定了“缺省每个视图各占一个入口”，右栏的“对话”也是单分节容器，所以“拖走当前容器唯一的分节”是新模型里最常见的一种拖动。
另：用户容器被拖空会从记录里删掉，预览里它的入口随之消失；冻结的活动栏条目现在按标签键找来源的条目（:493-496），改成容器之后“来源的入口没了、下面的补一格”只在来源是容器唯一成员时成立，这条也要跟着改写。
如何核实：读上面几处；现有实现里把只有一个标签的无名面板的标签拖出去，预览就是那块面板消失、邻居补位。
建议：写明“来源收起使当前容器变空时，这一场里该区域保持收起后的样子（不切到相邻容器），放下时才按第 5 节切换；键盘与落点指示手感不受影响”。实现上给 removeTab 之类的操作一个“不回落 active”的预览变体，或者把“active 回落”放在提交出口而不是每个操作里。

[R7] 重要｜破坏既有约定、接口与合同（第一轮 D9 只解决了一半）｜提案第 5 节“拖入口……整个容器搬过去；不能拖进分节区域”；Spec 输出 22、24、31
现象：入口从“视图的条目”变成“容器的条目”，拖入口只能在入口条之间走。
为什么是问题：
1. 现有能力被收走（读到实现）：现在活动栏条目起拖就是拖这个视图的标签（layout-drag.ts 的 fromElement：data-tool-entry → {kind: "tab", tab}；输出 22“条目是拖动源，拖它等于拖这个视图的标签”），能放到任何工具面板旁、能浮动。改稿下缺省每个视图一个单分节容器，这些条目全部变成“只能在入口条里换序或换区域”：把资源管理器的图标拖到右栏对话的下面、拖出去浮动，都不行了，只能先点开它、再去拖分节的标题。活动栏隐藏之外，这是缺省布局下最显眼的行为变化，提案没有当作变化写出来。
2. 新的来源种类没定义（读到实现）：LayoutSource 只有 tab 与 panel（layout-doc.ts:73-75），实时布局只支持 tab（layout-drag.ts:29-30 的注释与 LayoutTabSource）。拖入口走哪种手感、有没有卡片与预览、整个容器搬到另一个区域时分节的方向从上下排变左右排（底部面板）尺寸怎么分，都没写。
3. 容器里有 movable: false 的视图时（views.md 的声明字段），拖入口换区域是否允许没写；现在的判定只认单个视图（layout-drag.ts 的 movable）。
4. 键盘没写：输出 31 的可聚焦拖动源含“活动栏条目”，Tab 循环的区域含“活动栏”，停靠点是“每个条目的上方和最后一个的下方”（layout-drag.ts:375-381）。改稿多了“落在入口上（并入）”这一类停靠点和右栏、底部面板的入口条两个新区域，输出 31 不在 Spec 改动表里。
5. “之间”与“之上”的几何没给（D9 第 2 点）：条目 38px、间距 4px，各占多少算哪一种没写；现在是按条目中线分上下（:361）。
6. 放回原处没定义（D9 第 3 点）：只含它一个分节的用户容器，把这个分节拖到自己入口旁的“之间”，照字面是新建 custom:<新 UUID>、旧的删掉；容器进了文档比较（第 5 节），两个 UUID 不同就不是原处，会提交一次、还把这个区域切过去。
如何核实：读 layout-drag.ts 的 fromElement、barDrop、barStops 与输出 22、24、31 原文。
建议：只有一个分节的容器，拖它的入口等于拖这个分节（保留输出 22 现在的行为，落到入口条上按第 5 节的两种落点，落到“之间”且容器只含它时是换序、不换 id）；多分节的容器拖入口才是搬整个容器。写出“之上”取条目中间一半、“之间”取上下各四分之一之类的数；输出 24、28、31 进 Spec 改动表。VS Code 的做法凭记忆是“把容器图标拖到另一个容器的视图区会把它的全部视图并进去”，没有在这次核实，仅供参考。

现象：现在“补上文档里还没有的视图”是往已有的具名面板里加标签；改稿下每个视图要新建一块面板和一片叶，提案没写这些新面板的 id、位置与尺寸怎么定。

== 更正（写在最后，以这里为准）==
[R1 更正：严重程度看读法] 改稿的原话有两种读法，要分开说。
- 读法一（“区域里是普通的工具面板”“不再按面板名”：具名叶取消）：按 R1 正文，阻断。产品里声明的视图只有三个（grep 'location:' 于 packages/neuro-book/src/plugins，去掉 lab 与测试：explorer/web/plugin.ts:42 的 sidebar，agent/web/plugin.ts:71-72 的 auxiliarybar 与 sidebar），没有一个在 panel，默认布局的底部面板区域必然为空。
- 读法二（“树照旧”“set-part-hidden 不变”：三片具名叶留着）：空区域能表示，降为重要，但下面三件事仍没写，照现有代码各有一个具体后果：
  1. 具名叶自己是不是分节、属不属于某个容器。是的话，区域里第一个视图住在具名叶里，别的住在无名叶里，两种叶规则不同。
  2. 具名面板不移动：它唯一的视图被拖走时是拆出一块新面板、换新 id，具名叶拖空隐藏留在原地（layout-doc.ts:643-656、:369-375）。若它是成员，这是 R5 表里又一种“换 id”。
  3. 它的 hidden 只隐藏这一片叶：setPartHidden("sidebar") 现在就是 setPanelHidden(具名叶)（layout-doc-store.ts:351-357），partVisible 也只读它（:438-446）。区域里别的分节不受影响，“显示、隐藏侧栏不变”就不成立；要让它代表整个区域，可见判定得是三个条件（区域没隐藏、容器是当前的、面板自己没隐藏），第 1 节写的是两个。
  R1 建议里的 (a) 就是把读法二补全：具名叶只当锚，不是分节、不属于容器、零标签。提案需要明写选哪种读法。
[R2 更正] 第 4 点只对右栏成立：右栏这一列在呈现里是“入口条 + 分节”的纵向分支。底部面板的入口条与分节是 center 的并列子节点（R3 第 6 点），不构成一个分支，它的问题是 R3 第 1 点（上边界拖不了）。
[R4 更正：结论取决于 R1 选哪种] R4 正文说“旧代码读新记录时因为树里没有具名面板而回落”，只在读法一下成立。若具名叶留作锚（R1 的 (a)），新记录能通过旧代码的 isToolRun（default-tree.ts:70-76：这一列全是工具叶、恰有一个具名），旧代码既不回落也不进保护路径，而是原样读进来：没有“不活动”的概念，所有容器的分节同时叠在一列里显示，多出来的两项字段原样留在文档里、不再更新。所以回滚那句在两种读法下都不成立，只是错法不同：读法一加入口条或无名 hidden 后停止保存；读法二是把所有分节摊开显示。提案要按选定的读法重写这一句。
[R7 更正] 第 1 点的例子举错了：改稿默认的侧栏只有一个入口“项目”（会话加资源管理器），没有单独的资源管理器图标可拖，“缺省布局下最显眼”这句撤回。准确的说法是两件事：
- 只含一个视图的入口（没写 container 的视图，例如第三方插件的侧栏视图，以及验收 14 用的测试视图）失去“拖条目等于拖这个视图”：这是我建议“单分节容器拖入口等于拖这个分节”能补回来的部分。
- “项目”把现在的两个视图图标并成一个容器图标，想把其中一个视图拖走只能去拖分节的标题。这是开发者要的成组本身带来的，我的建议补不回来，也不该补；只需要在提案里写明“拖视图的入口从图标换成分节标题”。
