# w00026 t24 视图容器提案 拉远看审查

审查对象：docs/proposals/workbench-view-containers.md（下称“本稿”）。只读。按影响排序。

### 1. 容器与 ADR 0044 的规范形直接冲突，本稿没讲 nb-layout 的哪一层改、怎么改（问题 4、5）

结论：本稿把容器、容器栏放进“同一棵树”，但现行树的规范形会把它们抹掉；这是本稿最大的架构取舍，却只用一句“树要支持一次显示一个子节点的分支（停放已有）”带过，还写了“不另造一种节点”“库里不加新的叶子种类”。

依据：
- ADR 0044 决策 1：“同轴嵌套总是展平，单子分支塌陷，所以同一画面只有一种树形”（docs/adr/0044-workbench-single-layout-tree.md 决策 1）；实现见 packages/nb-layout/src/layout-doc.ts:188-208（normalizeTree：单子分支 `collapseInto`，同 orientation 的子分支展平）与 :210-224（detachNode 摘节点后单子分支塌陷并记 alias）。
- 分支快照只有 `{kind, id, orientation, size, children}`（packages/nb-layout/src/grid-types.ts:139-145），没有地方放容器身份 `{id, origin, title?, icon?}` 与容器栏的 `active`；LayoutDoc 只有 `panels` 一张记录表（layout-doc.ts:58-67）。
- 后果：只含一个分节的容器（本稿第 2 节明确是常态：“一个容器只有一个分节时……”）在任何一次结构操作后会塌陷成那个分节，容器 id、origin、标题随之消失；只有一个容器的容器栏同理。若实现者把容器栏当成普通的 vertical 分支，侧栏里同为 vertical 的容器还会被展平进容器栏，“一次显示一个”的语义整个没了。
- 要讲清的取舍（至少三件）：容器栏在文档树里是新的分支种类，还是普通分支加一张 `containers` 记录表；规范形对这两种节点的豁免规则（容器不塌陷、不与容器栏展平），以及这是否部分取代 ADR 0044 决策 1 的“同一画面只有一种树形”；容器身份存在哪里、`detachNode` 的 alias 机制对容器 id 怎么处理（“移动到”、命令的目标要按容器 id 找）。这些决定一旦落进布局记录格式（本稿第 6 节“格式版本加一”）就是数据格式，后面改要再升一次版本、再丢一次布局。

### 2. 本稿推翻了已接受的 ADR 0044 决策 3，却没有登记要改 ADR（问题 1）

结论：问题是真问题，方案也不是给更底层的选择打补丁；但它推翻的是一条已接受的 ADR，本稿 frontmatter `adrs: []`，“对 Spec 的预期改动”表里也没有 ADR 一行。

依据：
- ADR 0044 决策 3：“取消 ViewContainer……失去‘点一个入口，一组视图一起切换’”（docs/adr/0044-workbench-single-layout-tree.md 决策 3）。单树提案“备选与取舍”给的理由是“标签组和同屏分栏都能表达；内置视图目前不依赖”（docs/proposals/workbench-single-tree-layout.md 备选与取舍表“取消 ViewContainer”行）。
- 这条理由现在不成立：前半句当时就承认表达不了“一个入口整组切换”（ADR 自己写了“失去”）；后半句是“当时没人用”，2026-11-09 开发者的要求（本稿问题 1）直接推翻了它。本稿问题 3 对此的分析是对的。
- 更底层的选择“一棵树、按矩形摆放”（ADR 0044 决策 1、2）的理由仍成立：跨面板搬动不重建实例、滚动焦点不丢、实时布局的让位动画都依赖所有内容在同一父元素按矩形摆放；本稿把容器放在树上、拒绝“树外存放”的理由（本稿第 1 节末段）与此一致，所以不是在打补丁。
- 值得开发者知道的背景：2026-11-06 起骨架已固定（单树提案决策记录 2026-11-06“试过片 7b 后”：整块面板不能拖、侧栏这一列只上下分、活动栏改回只列侧栏视图），工作台实际已收敛到 VS Code 的“固定 Part”形态；本稿再加回 ViewContainer，等于在自写的树上复刻 VS Code 的 ViewContainer + ViewPane。这是合理的收敛方向，但应在 ADR 里写明“决策 3 被本稿取代”，并顺带记下决策 1 规范形的豁免（见第 1 条）。

### 3. 更简单的做法：“一次显示一个子节点”只在文档层，呈现层沿用已有的“隐藏的不进呈现树”，createGrid、求解器、矩形与动画不用认识新分支（问题 2）

结论：本稿“影响”一节写“nb-layout：树要支持‘一次显示一个子节点’的分支”，没有区分文档树与交给 `createGrid` 的呈现树。仓库里已有现成机制：隐藏面板留在文档树里、投影时不进呈现树，投影里单子分支塌陷由 `collapsedTo` 记下、尺寸据此写回文档。容器栏只投影 `active` 那个容器，就能复用这条路径，Grid、`sash-drag`、`grid-rects`、`grid-motion` 都不必新增分支种类。

依据：
- packages/nb-layout/src/layout-project.ts:1-5（文件头：隐藏的、被收走的面板不进呈现树；`collapsedTo` 用于写回）与 :109-110（`panel.hidden === true` 时投影返回 null）、:90-97（投影里的单子塌陷记 `collapsedTo`）。
- 单树提案决策记录 2026-11-06（确认 t07 计划第二稿）：“隐藏的面板留在文档树里，但不进交给 `createGrid` 的呈现树”——这正是本稿“不活动的容器是看不见的子树”所需要的同一个模式。
- 剩下要单独处理的只有文档层：规范形豁免与容器身份（第 1 条）、停放内容保持最后非零尺寸（现行输出 16 已有）。
- 与业界常规做法的对照：VS Code 是固定 Part 里放 ViewContainer，容器里是 ViewPane 组成的 PaneView（上下排、各自可折叠）；本稿的“分节”与此一致，差别只在容器放在自写的一棵树上而不是固定 Part 里，理由（不跨树搬、复用拖动与实时布局）本稿第 1 节写了，成立。没有发现更现成的第三方库可替代（ADR 0044 决策 5 已排除 dockview、Trellis）。
- 建议：本稿“影响”里把 nb-layout 的改动范围写成“文档模型与规范形，投影只出活动容器；Grid 与求解器不变”，或说明为什么不能这样做。这直接决定改动面是 layout-doc 一个文件还是 nb-layout 的整个几何内核。

### 4. 停靠的工具视图变成“分节、无标签”，浮动窗仍是“带标签的组”：同一种东西两套分组模型，之间的转换规则没写（问题 5）

结论：本稿把容器里的工具视图改成分节（中央不再是“添加为标签”），同时把浮动窗列为非目标、“浮动的单位仍是带标签的组”。工具视图于是有两种归组方式：停靠时按分节、浮动时按标签。两者之间的往返是常用路径，本稿没有规定。

依据：
- 本稿“非目标”最后一条与第 2 节“分节正文的中央不再是‘添加为标签’，因为分节没有标签”。
- 现行输出 39（docs/specs/ui/workbench-layout.md:212）：“回到停靠：……全部标签一起并入”“框架按钮‘回到停靠’：工具视图各回声明的具名面板”。具名面板在本稿里被容器栏取代，“回声明的具名面板”要改成“回声明的容器”还是“当前活动容器”；多标签的工具视图浮动窗整窗停靠到一个容器时，是变成几个分节、按什么顺序、落在哪个容器，都没写。
- 反方向：一个分节浮出去是单标签浮动窗；再把别的视图拖到这个窗的标签条上（输出 39 允许）就成了多标签组，于是容器外存在一种容器里不允许的结构。
- 要讲清的取舍：要么浮动窗里的工具视图也改成“分节”（与编辑器标签的浮动窗分开），要么承认两种模型并写出互转规则；本稿“对 Spec 的预期改动”表也没有列输出 39。

### 5. 底部面板的容器左右排，分节的“折叠成标题行”在横向分支里不存在，本稿目标里的“展开收起”在这一处没有定义（问题 5）

结论：本稿第 2 节说“收成标题行（输出 20）就是折叠”，第 1 节又说底部面板的容器“左右排”。现行合同里横向分支没有标题行收起，只有“拖到零”，而且收起按钮只给上下排的面板。所以底部面板容器里的分节，开发者要的“记住展开收起”具体是什么，本稿没回答。

依据：
- docs/specs/ui/workbench-layout.md:109-117（输出 11 的状态表）：“收成标题行……所在分支是纵向时”；“拖到零……所在分支是横向时，宽度为 0，保留 1px 边界”。
- 同文件输出 20（:135）：“收起按钮只给上下排的面板：横向分支里收起就是拖到零，和隐藏重复，无名面板还找不回来”。分节都是无名面板。
- 输出 12（:121）：横向分支里越过 24px 是拖到零。
- 业界做法：VS Code 的 PaneView 横排时，折叠的分节变成一条竖排标题的窄条，可点开。本稿要么照此定义“横向折叠 = 竖排标题条”（新的呈现状态，要进输出 11 的表），要么写明底部面板的分节不能折叠、只能调宽。这关系到 nb-layout 是否新增一种收起呈现，属于架构层面的决定。

### 6. 新的公开接口（`workbench.viewContainers`、视图声明 `container?`）留了几个会锁死语义的空白：缺省容器归谁、跨插件引用、声明消失的容器（问题 4）

结论：本稿给插件 SDK 加一个贡献点和一个声明字段，一旦第三方插件写进清单就难改；但几处语义没定，后面补的时候很可能要改已发布的含义。

依据与空白：
- **缺省容器没有主人**：第 4 节“不写时按 `location` 放进那一处的缺省容器”，而容器身份只有 `origin: "declared" | "user"`（第 1 节）。缺省容器既不是某个插件声明的，也不是用户拖出来的；它的 id、标题、图标由谁给、能不能被用户拖空后删除、是不是“声明的保留但入口不显示”那一类，都没写。
- **跨插件引用**：视图声明的 `container?` 可以写别的插件的容器 id 吗？现行 id 规则是“以自己的插件 id 加 `.` 开头”（docs/specs/workbench/views.md:68-70 的规则表）。允许跨插件时，那个插件没装、停用或撤回贡献时视图落在哪；不允许时开发者例子里“会话”（nbook.agent）和“资源管理器”（nbook.explorer）要同在一个声明的容器里，就只能靠用户拖或由某个插件声明一个容器、把别人的视图收进来（后者需要“容器列出成员”而不是“视图指向容器”）。两种方向的选择决定贡献点的形状，现在不定以后改就是破坏性变更。
- **声明消失的容器**：单树提案定了“未知条目留在树上，显示占位”（docs/proposals/workbench-single-tree-layout.md 第 2 节“未知条目留在树上”）。插件暂时缺失时，它声明的容器（以及里面属于别的插件的视图）在入口条上怎么显示、标题图标从哪来，本稿没覆盖；容器的标题与图标若只存在声明里、不进布局记录，这一处就画不出来。
- **`location` 的含义第二次改**：单树提案已把它从“容器”改成“第一次放到哪个具名面板”，本稿再改成“缺省容器所在的容器栏”，`ViewContext.location` 改成“所在容器栏”。连续改语义要在作者文档里写清楚。
- 说明：ADR 0027 决策 1 要求内置与第三方插件能力相同（docs/adr/0027-builtin-and-third-party-plugins-are-equal.md 决策 1），所以“先只给内置插件用”这条退路不太可用（单树提案对动态标签类型用过这条退路，与 ADR 0027 是否一致是另一个问题）；更稳的办法是在 Spec 里先把上面三处定死再开放贡献点。

### 7. YAGNI：右栏、底部面板的容器栏与入口条眼下没有用户；产品里一共 3 个视图（问题 3）

结论：开发者 2026-11-09 已定“右栏、底部面板也做”“容器既有声明的也能用户拖出来”，这里不建议推翻，只指出证据，供排切片顺序：现在真正被需要的是侧栏的容器（开发者例子），右栏、底部面板的入口条与它们的拖动落点是“为将来的视图”做的。

依据：
- 新应用里登记视图的产品插件只有两个：packages/neuro-book/src/plugins/explorer/web/plugin.ts:42（资源管理器，`sidebar`）与 packages/neuro-book/src/plugins/agent/web/plugin.ts:71-72（对话 `auxiliarybar`、会话 `sidebar`）；`location: "panel"` 只出现在 Lab fixture 与测试替身（src/plugins/lab/web/fixtures/WorkbenchSurfaceFixture.vue:43、src/plugins/workbench/web/testing/layout-doc.ts:27）。所以右栏现在只有一个视图，底部面板一个产品视图都没有。
- 本稿为这两处新增的东西：头上的入口条（右栏图标、底部标题）、入口条之间与入口上的落点（第 4、5 节）、只有一个容器时头的退化规则（第 3 节）、实时布局下“拖到入口上预览切到那个容器”（第 5 节）。每一项都要进 Spec、Lab 与 e2e。
- 建议（不改范围，只改顺序）：实施计划按“侧栏容器栏 → 声明贡献点 → 用户拖出容器 → 右栏、底部面板”切片，后两处有第二个视图时再排；模型上三处同构，先做侧栏不会锁死后面。`origin` 字段与“空了的声明容器保留但入口不显示”这类规则也可以等用户拖出容器那一片再定。

### 8. 尺寸归谁没讲：侧栏宽度与约束是容器栏的还是每个容器的（问题 5）

结论：本稿第 1 节只说“选择切换只改 active，不改任何尺寸”，隐含侧栏宽度属于容器栏；但现行约束是按具名面板给的，具名面板被容器栏取代后，约束挂在哪一层、视图声明的最小最大尺寸怎么合并，没写。这决定切容器时布局会不会跳。

依据：
- docs/specs/ui/workbench-layout.md:94-104（输出 6）：`sidebar` 160 到 560、默认 340 等约束挂在具名面板上；“视图声明的最小最大尺寸，面板取所有标签的并（最大的最小值），切标签不改布局”。
- 新模型下侧栏里的叶是分节（每个分节一个视图），具名面板不再存在。可选的两种：约束按容器栏、取全部容器全部视图的并（对应现行“切标签不改布局”，代价是一个宽视图拖累所有容器）；或只取活动容器（切容器会改宽度，和“不改任何尺寸”矛盾）。还有：容器里分节的高度比例存在各自容器子树里（切走切回保持），但侧栏宽度若某个容器允许的最大值更小，切过去时谁夹取、夹取写不写回（现行输出 8“测量、夹取……都不写文档”）。
- 第 1 条里的投影方案（只投影活动容器）会让“只取活动容器”成为默认行为，所以这条要和第 1、3 条一起定。

### 9. 实时布局下“拖到入口上预览切到那个容器”与现行两条合同冲突：落点几何不含预览、预览不改可见性（问题 5）

结论：本稿第 4、5 节规定拖到不活动容器的入口上时“预览就是切到那个容器、它出现在末尾”。按现行合同，这次预览之后侧栏正文显示的是新容器，但落点判定仍用拿起时（旧容器）的矩形，可见性也不变；本稿没说切过去之后指针离开入口、进到侧栏正文时按哪个容器判。

依据：
- docs/specs/ui/workbench-layout.md 输出 25（:143）：“按这一刻看到的矩形判（实时布局按拿起时的矩形，来源收起之后按收起后的布局），预览不进输入”。单树提案第 3 节也写“预览不进输入，否则让位会把落点从指针下挪走”。
- 同文件输出 17（:129）：“手势预览不改可见性”；“第一次有效可见才加载”。新容器里没加载过的视图在预览里会是空的。
- 可能的结果：用户看到容器 B、把视图放到 B 的两个分节之间，提交的却是按 A 的几何算出的落点（放进不可见的 A）。
- 要定的取舍：切容器算“这一刻看到的布局变化”（像“来源收起”一样进入几何输入，并让新容器的视图在拖动中加载，类似输出 12 从零拉回时的做法），还是切过去后只接受“放在末尾”、正文不再是落点。两种都可以，但要写进本稿或 Spec 的预期改动（layout-drag 那一行现在只写了“入口条的落点”）。

### 10. 活动栏隐藏时侧栏的容器没有切换入口（问题 5）

结论：本稿只给右栏、底部面板的头放入口条，侧栏的入口全靠活动栏（第 3 节）。活动栏是可以隐藏的条，现行合同为此专门留了退路，本稿没有对应规则。

依据：
- docs/specs/ui/workbench-layout.md 输出 20（:135）：“活动栏隐藏时侧栏这一列按别的工具面板算，否则切不了视图。”验收 14（:298）：“Given 活动栏隐藏、侧栏有两个视图，When 读侧栏的头，Then 有标签带。”
- 活动栏可隐藏：LayoutDoc 的 `hiddenBars`（packages/nb-layout/src/layout-doc.ts:65），公开状态 `activityBarVisible`（输出 36）。
- 本稿“对 Spec 的预期改动”列了输出 20、验收 14，但正文没说新规则。自然的做法是活动栏隐藏时侧栏头和右栏一样画入口条（与本稿第 3 节右栏的做法同构），写一句即可。影响小，但它是现有合同里明文的不变量，不写会在实现时丢。

## 按问题汇总（共 11 条）

1. 真问题、根因、底层选择：是真问题（开发者明确要求，ADR 0044 自己写了“失去一组切换”）。不是补丁；“一棵树、按矩形摆放”的理由仍成立。被推翻的是 ADR 0044 决策 3，其理由“内置视图目前不依赖”已失效，但本稿没登记要改 ADR（第 2 条）；还会动到决策 1 的规范形（第 1 条）。
2. 更简单的做法：分节模型与 VS Code 的 ViewContainer/PaneView 一致，属常规做法；与它的差别（容器放在树上）有理由。更省的实现路径是复用“隐藏的不进呈现树”的投影，Grid 与求解器不动（第 3 条）；仓库里已有一份审查过的容器身份设计没被引用（第 11 条）。
3. YAGNI：右栏、底部面板的容器栏眼下没有用户（第 7 条）；开发者已定要做，建议只调切片顺序。没有发现无证据的提前优化。
4. 难回头的死胡同：布局记录格式（容器身份与规范形豁免，第 1 条）和插件 SDK 的新贡献点（缺省容器、跨插件引用、声明消失，第 6 条）。
5. 该讲的架构取舍：nb-layout 改哪一层（第 1、3 条）、浮动窗与分节两套分组（第 4 条）、横向分节的折叠（第 5 条）、尺寸归属（第 8 条）、实时布局切容器的判定（第 9 条）、活动栏隐藏时的入口（第 10 条）。本稿篇幅花在入口位置、图标这类细节上，这些取舍没讲。

### 11. 仓库里已有一份审查过的容器身份设计，本稿没有引用，第 6 条的几处空白它都答过（问题 2）

结论：被 ADR 0044 取代的外壳抽象提案第 3 节“容器身份”给出过一套完整规则（经过审查第 1、4 条），本稿的 `origin: "declared" | "user"` 与“空了的容器”规则是另起的一套，比旧设计少了一类、也少了几条边界。旧稿被取代的原因是拓扑（几棵树、跨树移动），不是容器身份本身，这部分可以直接拿来比对或沿用。

依据：docs/proposals/workbench-shell-abstractions.md:104-135（第 3 节）：
- **三类容器、id 命名空间互不重叠**：隐式容器 `view:<起源视图 id>`（视图没写 `container` 时自己一个容器）、声明式容器（插件 id，不得以 `view:`、`custom:` 开头）、自建容器 `custom:<UUID>`。本稿的“缺省容器”（第 4 节）对应的是“每处一个共同的缺省容器”，与旧稿“每个视图一个隐式容器”是不同的选择，本稿没说为什么改；而第 6 条指出的“缺省容器没有主人”在旧稿里不存在。
- **容器是否出现看实际成员**，容器本身不单独记“存在”，所以恢复默认不会制造空入口；本稿是“用户的空了删除、声明的保留但不显示”，要单独存状态。
- **插件被禁用、默认位置变化**：旧稿的典型情况表逐条给了结果（容器保留、标题回落到剩下的成员、基于旧默认的覆盖失效并记诊断），正是第 6 条“声明消失的容器”的答案。
- **标题与图标的回落顺序**（首个可见成员、首个实际成员……）也覆盖了本稿待定项 2 的“用户容器用第一个分节的图标”，并且考虑了成员被隐藏的情况。
- 建议：本稿加一节“与旧容器身份设计的关系”，逐条说明沿用、改动及理由；没有理由的差异（尤其“隐式容器”变“每处一个缺省容器”）交开发者决定。
