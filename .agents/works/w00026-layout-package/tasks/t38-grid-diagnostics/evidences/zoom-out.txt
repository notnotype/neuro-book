### 1. “只发新增”的边沿合同是为没有消费者的出口设计的，而且把本该由宿主决定的策略写进了库（问题 1、3）

- **消费者现状**
  - 应用里 `WorkbenchShell.vue` 不监听 `issues`（该文件里搜 `issues` 无匹配）。计划 97 行自己也写“应用里没有监听 `WorkbenchSurface` 的 `issues` 的地方”。
  - `NestedGrid` 和 `useGridLayout` 在 `packages/` 里只被 `WorkbenchSurface`、`WorkbenchShell` 和 Lab 夹具用（`NestedGridAcceptanceFixture.vue:133,360,511`、`GridSwapScene.vue`）。nb-story、dev-panel、nb-agent-ui、nb-form、nb-markdown 里搜不到。
  - 提案 223 行说“开发者面板如今靠累计列表”。在这几个包的范围内没搜到这个用法。
  - ADR 0054 第 8 条说第一个外部使用方 nb-story 要到第二档才改造并校验公开面。所以现在没有任何一个真实宿主说明“要的是边沿”。
- **真问题与假问题要分开**
  - 真的有三个：
    - `NestedGrid.vue:562` 的 `watch(() => scope.issues)` 把累计列表整个重发（`useSashGesture.ts:236` 留最后 8 条）。
    - 没接 `onGestureCommit` 时失败发两条（`NestedGrid.vue:526` 和 `useSashGesture.ts:331` 之后）。
    - 键盘路径不发诊断。
  - 这三条各有小修法。没有证据说明“每次重算发一批”本身伤到了谁。
- **根因是出口选成了推送事件，才需要定义“什么叫新”**
  - 结果本来就是快照。`useGridLayout` 已返回响应式的 `layout`（`useGridLayout.ts:52,126`）。`gesture-update` 载荷已带 `preview.issues`（`NestedGrid.vue:101,494`）。
  - 宿主要日志或提示，`watch` 一下自己 diff 只要几行，还能按自己想要的键去重。计划 98 行 Lab 夹具“按键去重”，说明消费方会自己去重。
  - 把键定成“码、cause、axis、id”，是库替所有宿主挑了一种策略。
- **开发者批准的范围**
  - 开发者同意的是“拆开、先定结果是快照、通知只发边沿的合同再写计划”（计划 15 行转述 t34 README 的推荐原话）。
  - 键怎么取、作用域怎么清，是第 1 稿自己加的。提案决策记录 470 行写的还是“待开发者追认”。
  - 边沿本身是否必要，应作为“改上游”候选交开发者：结果与通知的最小面是“快照加事件型”，求解类诊断不设边沿出口。

### 2. 通知的作用域与键成了要写进 Spec 输出 140 的公开合同，发到 npm 后难改（问题 4）

- **三套规则**
  - 计划 88 到 91 行同时存在三套规则，再加“同批同键只发第一条”：
    - 布局重算：键集跨重算保留，`contextKey` 变化清空，`grid` 换实例不清空。
    - 一场手势：begin 清空。
    - 事件型：不去重。
  - 第三方宿主无法从类型推出这些规则，只能读 Spec。其中“`grid` 换实例不清空”是 `useGridLayout` 内部状态机的细节。
- **同批只发第一条会丢信息**
  - 计划 165 行承认 `range-overflow` 没有 `id`。两根轴同时装不下时，第二条只在快照里。
  - 通知里没有“被合并了几条”，宿主无从知道。
- **以后难改**：想加“诊断消失”的通知、想带次数，都会改变“什么时候发”的语义，属于破坏性改动。0.x 期间可以改，但这正是 ADR 0054 第 10 条要避免过早承诺的那类面。
- **保留字段在类型上看不出来**：`params` 类型是 `Record<string, string | number>`（计划 40 行），但 `cause`、`axis`、`id` 三个名字实际成了进键的保留字段。
- **二级判别字段名不一致**
  - `grid-failure.ts:13` 的注释写同一个码下靠 `field` 区分，诊断改用 `cause`。
  - 计划 53 行说“照 t34 的 `grid-failure.ts`……按 `cause` 判别”，但该文件里搜不到 `cause`。
  - 发布前统一成一个名字几乎没有成本，发布后有。
- **码与 `cause` 的两级结构没讲默认分支**
  - `over-constrained` 一个码下有五个 `cause`，参数形状相同（计划 62 到 69 行）。
  - ADR 0054 第 4 条要求码集合开放、宿主有默认分支。宿主遇到已知码下的未知 `cause` 该怎么办，计划没说。
  - 要么拆成平的码，要么在合同里写明默认分支落在 `code` 一级。
- **没有发现**：数据格式被锁死。诊断不持久化，不进快照，`GridSnapshot` 不受影响。

### 3. 有更简单的做法：保留形状改造，拿掉边沿，只修三个真问题（问题 2、3）

- **值得保留的部分**
  - `{code, message, params?}` 形状，ADR 0054 第 4 条已定。
  - 不合成。这比 t34 第 3 稿简单，合成正是三轮审查没收敛的原因。
  - 参数只有标量。
  - `allocateSashPanels` 去掉没有外部调用方的 `issues`、`context` 两个参数。
- **最小做法**
  1. 求解类诊断只作快照（`layout.issues`、`preview.issues`、`solveSash*` 的结果），逐条完整，宿主自己决定去重。
  2. 事件只留事件型：提交被拒（一个失败一条，删 `NestedGrid.vue:526` 那条）、`not-published`、`swap-skipped`、`notify-failed`。
  3. 删 `scope.issues` 与 `watch`。`SashGestureOptions.onIssues` 每帧原样交本批。键盘路径补上通知。
- **效果**
  - 输出 140 缩成几句。
  - 键集、`contextKey` 清空、`recompute` 记上一次的值、`flush` 后的清空逻辑都不需要。
  - 计划里最重的测试（逐像素重算、换 `contextKey`、换实例、一场手势一次）也不需要了。
- **业界对照（凭记忆，没有联网核实）**
  - VS Code 的 splitview/grid、allotment、dockview、react-resizable-panels、splitpanes 在约束不可满足时是夹紧或降级。
  - 它们没有“诊断流”这个出口，最多开发模式下 `console.warn`。
  - 没有常规做法可以照搬，所以更该只发布最小的一层，等 nb-story 这个第一个外部使用方提了需求再长。
- **仓库内已有的可复用物**：`layout` 响应式结果、`gesture-update` 载荷、`ui/i18n` 的 `TextRef.params`（标量约束的来源）。不需要新增模块或第三方库。

### 4. 回调抛出的处理是在补“同步通知放在状态机中间”这个根因，并把异常吞进 `console.error`（问题 1）

- **症结**
  - `flush` 里（`useSashGesture.ts` 约 323 行）先同步通知宿主，后面才轮到 `finish`。通知一抛，手势就卡住。
  - 计划的修法是每个出口包 `try/catch` 加 `console.error`（计划 93、164 行）。
  - 更根上的做法是把通知放到状态收尾之后（先 `finish` 再发），或推到微任务。这样库不用吞异常，宿主的错误仍到它自己的全局处理。
  - 计划 164 行已承认“宿主的全局错误处理看不到”。这是被选择的代价，不是必须的代价。
- **范围**
  - 现状里已有同类模式：`useGridLayout.ts:113-119` 对 `onApplied` 抛出做 `try/catch`，转成诊断。延续它可以接受。
  - 计划把它作为“和提案不同的第 3 条”并入 t38。它实际是 L1 通用的异常语义，不是诊断设计。放进来使范围变宽，还多一条要追认的决策。
- **事件出口的 `try/catch` 只在开发构建有用**
  - 计划 93 行关于 Vue 开发构建里 `emit` 监听抛出会向外抛的说法，与我记忆中的 Vue `logError` 行为一致，没有联网核实。
  - 生产构建里 Vue 自己就会 `console.error`。所以事件出口的 `try/catch` 主要对开发构建有用。
  - 真正需要的是选项回调（`onIssues`）那一处，可以只收窄到它。
- 影响中等偏低。

### 5. 计划写满了行号级细节，该讲的取舍没讲（问题 5）

- **篇幅分布**：集中在码表行号（计划 58 到 78 行）、测试迁移清单、切片。
- **缺的内容**
  1. 谁消费诊断，要拿它做什么（日志、界面提示、测试断言）。没有这个，“边沿还是快照”无从判定对错。
  2. 备选方案。没有写“不做边沿”这一档。“和第 3 稿、提案不同的地方”只对比了上一稿，没有对比最简单的做法。
  3. 码集合开放时，未知 `cause` 的默认处理（见第 2 条）。
  4. 提案 223 行“`issues` 事件只发新增”的原意，是“不再重发累计列表，累计由宿主自己存”，并没有要求按键去重。计划把它升级成了边沿合同，这个升级的理由应该写出来。
  5. 与第二档 nb-story 改造的衔接：哪些面在 0.x 期间允许再变。
- **数值参数的取舍没解释**：计划 58 行把数字参数写成“四舍五入到 0.01 前的原值”。`message` 里的数是取整的，`params` 里是浮点原值，这个取舍没有解释。宿主比较时要不要容差，合同里没写。

没有发现：问题 4 里的“锁死数据格式”；问题 2 里需要新增第三方库或新模块。
