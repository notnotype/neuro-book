### 1. 放下中那一帧里 move、withdraw、resized 三个守卫没有测试（变异存活）
**严重程度**：建议
**类别**：测试
**位置**：packages/nb-layout/src/drag-gesture.ts:410（move 里的 `current.dropping`）、:294（withdraw 里的 `current.dropping`）、:454（resized 里的 `!active.dropping`）；packages/nb-layout/src/drag-gesture.test.ts 的“输出 14：边缘滚动”一组（592 到 628 行）
**现象**：在副本里分别删掉这三个 `dropping` 判断，drag-gesture.test.ts 仍是 67 过 0 败（变异 N2、N3、N5）。现有用例只覆盖了“放下中失去捕获不算取消”“放下中 Escape 仍取消”“放下中到来的 click 被吞”。
**为什么是问题**：这三个守卫保护的是真实会发生的事：松手后同一帧里鼠标常有 buttons 为 0 的悬停移动，没有 move 的守卫，`current.point` 会被改到松手点之外，下一帧 `publish()` 与 `drop()` 就按移动后的坐标放下，违反 Spec 输出 6“用松手的坐标再判一次”。withdraw 的守卫保护的是边缘滚动最后一次滚动产生的 scroll 事件（在放下那一帧之前到达），没有它，`scroll: "withdraw"` 的资源树会在边缘滚动中松手时撤下落点、变成静默不写，正是验收 6 要防的问题。实现里这三处是对的，只是没有测试证明；以后有人整理“多余的判断”会静默破坏。
**如何核实**：`/tmp/review-w00026-t05-impl/mut/run.sh N2|N3|N5`（脚本把 `dropping` 判断删掉后跑 bun test，全部通过）。
**建议改法**：在“边缘滚动中松手”一组加三条用例：松手后、下一帧之前再 `move` 一次，断言提交的是松手点的落点；松手后派发 `scrolled()`（withdraw 配置），断言仍提交；松手后 `resized()`，断言不多排一帧。用手动时钟，几行即可。

### 5. 过门槛那一下 move 重复判定了一次
**严重程度**：建议
**类别**：性能 / 代码质量
**位置**：packages/nb-layout/src/drag-gesture.ts:386 到 417（`move` 里 `begin(from, point)` 之后继续往下走）
**现象**：`begin` → `start` 已经同步 `publish()` 了一次（按当前坐标判定并发布），接着 `move` 往下走又执行 `current.point = point; schedule()`，下一帧再判定、再发布一次，坐标没变。资源树每次起拖因此多一次 `resolve`（含 `elementsFromPoint`、`getBoundingClientRect`）和多一次 `drag-hover` 给控制器。注释写的理由是让边缘滚动能从过门槛这一下开始，但这只需要第 413 到 416 行的边缘检查，不需要 `schedule()`。
**为什么是问题**：每场拖动固定多一帧的判定与发布，行为上无害，但 `resolve` 在 Spec 里被强调为每帧都跑的热路径，而且“第一次发布”与“下一帧的第二次发布”在状态机测试里没有区分，以后有人在 `resolve` 里依赖“一帧一次”会踩到。
**如何核实**：已实测。/tmp/review-w00026-t05-impl/mut/base/probe.test.ts：press 加一次过门槛的 move 之后 `resolve` 调用 1 次、排着 1 个待跑的帧；跑完这一帧 `resolve` 变成 2 次。
**建议改法**：`begin` 之后只做边缘滚动检查，不 `schedule()`；或者让 `begin` 返回是否已发布。

### 7. 取捕获的 catch 把所有 DOMException 都当成“失去捕获”，没有诊断
**严重程度**：建议
**类别**：错误处理
**位置**：packages/nb-layout/src/vue/drag-session.ts:197 到 205（`capture`）
**现象**：`setPointerCapture` 抛出的任何 `DOMException`（期望的是指针已不存在的 `NotFoundError`，也可能是 root 已脱离文档的 `InvalidStateError`）都被吞成 `false`，上层按 `capture-lost` 取消，原始错误没有留下任何记录。
**为什么是问题**：项目的禁止清单要求 catch 至少写一条诊断。这里的取消原因会在 `onEnd` 里可见，但第二种异常（宿主把 root 卸下后还在拖）会被说成“失去捕获”，排查时误导。
**如何核实**：读代码。
**建议改法**：只收 `NotFoundError`（按 `error.name`，是错误类型不是文案），其余照常抛出；或者在 catch 里 `console.debug` 一条带 `error.name` 的诊断。

### 10. 每帧用 elementsFromPoint 取遮挡，资源树与标签原来用的是更便宜的 elementFromPoint

### 未发现问题的方面（仔细检查后）
- 工作台 `evaluate` 与 `publish` 的先后：新实现里 `resolve` 不再带副作用，`publish` 在 `evaluate` 之后写 `shown` 与 `state`，放下那次判定不发布，与旧代码一致；结构键由 `activate` 先验一次、`structure` 在每次判定与放下前再验，比旧代码多挡了触摸 200 毫秒里布局变了的情况。
- 预备区 `zones` 冻结：`frozen` 在 `activate` 里写，早于第一次发布，也早于键盘的 `regions`；`state` 这个 `computed` 只在 `session.state` 换对象时重算，而 `frozen` 只在一场开始前改，所以读闭包是安全的（`startKeyboard` 里 `activate` 先于 `keyboard.regions` 已核对）。
- 键盘起点、`refocus`：与旧 `begin` 里的起点计算、`returnFocus` 逐段对过，只有“起点区域是预备区且没有落点元素”时旧代码会拿预备区中心去试 `own` 矩形、新代码给空数组，实际走不到。
- `swallowClick` 各条路径：拖动结束、取消、`abort`、失败的捕获都置位；放下中那一帧在 `release` 里提前置位（click 在放下那一帧之前到）；`takeClick` 对 `detail` 为 0 不吞。放下中的路径上 finish 会再置位一次，之后没有 click 到来，但下一次按下的 `pressed()` 会清掉，无害。
- `finish` 重入：先 `active = null` 再回调，回调里再调 `cancel`、`abort`、`invalidate` 都是空操作；`commit` 抛出时监听、捕获已收；`grabbed` 失败走 `cancel("capture-lost")` 收场，`activeChanged(false)` 与 `ended` 都有，资源树的 `flyBack` 因 `props.drag` 尚为 null 不会飞。
- `release` 的“放下中”一帧里各入口：`move`、`withdraw`、`resized`、`invalidate`、`scrolled` 都有守卫；Escape 与 dispose 照常收场并清帧（只是第 1 条说的三个守卫没有测试）。
- 资源树：`watch(state, {flush: "sync"})` 建在 `onMounted` 里，处在实例作用域内，随组件卸载停止；`onBeforeUnmount` 的 `dispose` 先于作用域停止，所以 dispose 触发的 `publish(null)` 仍会清停留展开。`dropKey` 与旧 `sameDrop` 逐类等价（move 只比 target，不比 `ordered`；open 只比 group 与 addresses，不比 `skipped`）。`props.drag` 晚一拍时 `ghostAt` 返回 null、`flyBack` 直接不飞，不会抛。
- 落点登记：`useDropTarget` 的 `flush: "post"` 与 `immediate: true` 组合下，`section` 的 ref 在同一轮后置队列里先赋值再登记，早于下一个指针事件；`resolveTabDrop` 的 `root.contains(target.element)` 与旧的 `root.contains(groupElement)` 等价；`sourceAt` 对 `tab` 为 null 的情形先短路。
- 打包：`editor/shared/contracts.ts` 只被各插件的 web 侧与测试引用（grep 核实，后端、SDK 入口都没有），neuro-book 是 private 应用，nb-layout 在 devDependencies 里本来就被所有 web 组件运行时导入；`plugin-sdk/pack.ts` 与 `scripts/release/` 不涉及；`src/architecture.test.ts` 7 过。
- Lab 场景：`DragSessionScene.vue` 根上有 `data-lab-subject`，Teleport 的拖影随 `v-if` 与卸载清理，输入是占位（与 NestedGrid 的先例一致）；`DropFeedbackOverlayFixture.vue` 保留原三个场景的绑定，并多登记了 `settled` 事件（原先没有，属于无害的小增补）。
- 常见返工项：没有按错误文案分支（第 7 条是按异常类型）；没有 `as any`、`@ts-` 或跳过的测试；没有固定时长的等待（e2e 用 `expect.poll`/`toHaveAttribute` 与双 rAF）；没有跨包深导入。
