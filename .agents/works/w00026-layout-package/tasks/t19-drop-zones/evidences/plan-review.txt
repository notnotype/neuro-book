[1] 重要 / 与 Spec 和既有测试冲突 / plan.md:60,66,100
现象：计划让分区写字时 DropFeedbackOverlay 的药丸不显示（hideLabel），激活的那块分区只写“上方/右侧/添加为标签”这类固定词。
为什么是问题：
  a. 药丸现在承载的信息比分区字多：workbench-layout 输出 28 要求“放回原处……提示‘原位’”，药丸还区分“放到两块之间 / 拆到这一边 / 放在这里（标签条插入）/ 放到 X（预备区）”（WorkbenchShell.vue 的 dropLabel）。分区字只有方向，“原位”“两块之间 vs 拆”在可见层面消失，只剩 live 区（只给读屏）。Spec 28 计划没有改，等于违反。
  b. 既有 e2e 直接读药丸：workbench-dnd.e2e.ts 里 label(page) / labelText(page) 共 19 处调用（如 280、362、440、479、506、601 到 635、737、845、897），editor-area.e2e.ts 三处 [data-drop-feedback-label]（550、563、1017）。计划缺省开关为开，hideLabel 生效后药丸节点不渲染，这 22 处全部失败；计划的“验证”一节只写“workbench-dnd 新增用例”，没有迁移这些断言。
  c. “分区写了字时药丸不显示”的条件没定义。指针在标签条上、预备区上、活动栏上（zonesAt 为 null）时没有分区字，药丸必须照旧显示（插入标签、放到 X）；计划只写了有分区的情况。
如何核实：grep -n "drop-feedback-label\|label(page)\|labelText(page)" e2e/workbench-dnd.e2e.ts e2e/editor-area.e2e.ts；读 DropFeedbackOverlay.vue 的 labelVisible（标签为空则不渲染）。
建议改法：不隐藏药丸，改成把激活分区的字换成当前落点的 dropLabel（原位、两块之间、拆到这一边），未激活的分区才写方向词；药丸仍可保留，或只在分区没有激活项时显示。若坚持隐藏药丸，须同时改 Spec 28 并列出要迁移的 22 处断言，hideLabel 的条件写成“zones 非空且有激活分区”。

[2] 重要 / 隐含耦合与遗漏 / plan.md:64,65,67；layout-drag.ts:343-347,299-307；drag-gesture.ts:280-293
现象：zonesAt(source, point) 由 WorkbenchShell 在 computed 里另算，不经会话的 resolve。
为什么是问题（逐项核实）：
  a. 遮挡：会话的 resolve 先判“被菜单、对话框挡住、data-no-drag 不接收”（layout-drag.ts:345，读 elementsFromPoint）；这些不在纯函数输入里。zonesAt 只用同一份 panelGeometry、excludedRects、策略，不知道 top 元素，所以菜单或对话框盖在面板上时 drop 为 null 而分区仍然显示（压暗层还画在下面）。Spec 25 末句“被菜单、对话框挡住的不接收”。
  b. 键盘：dropAt 的 region 参数决定“键盘停在预备区上就是它”（layout-drag.ts:299-307，不按坐标）；zonesAt 的签名没有 region。键盘停在 reveal:<面板> 时，point 是预备区矩形中心，zonesAt 会给出它底下那块面板（若接收）的分区，激活项为空，画面与落点不符。
  c. 重复：每帧 dropAt 与 zonesAt 各做一遍 panelGeometry（每块面板 3 次 querySelector + 3 次 getBoundingClientRect）加 excludedRects（3 次），计划说“量级不变”，实际是每帧翻倍；放下那一刻会话又 evaluate 一次（drag-gesture.ts:316 以后）。
  d. 接线两份：WorkbenchShell 与 EditorAreaFixture（editor-scene/EditorAreaFixture.vue:206-262，各自 createLayoutDrag、各自算 dragState/dropFeedback）都要写 dropZones、activeZone、标签三段计算。
  e. 计划对缓存的推理本身是对的：previews 的键是 [source, action, extent]，同一个 between 从两块面板进来共用一个对象，分区不能存进缓存对象。
建议改法：让 dropAt 在返回前给结果挂一个每帧新的 zones 包装（{...cached, zones}，不进 previews 缓存；actionKey 不受影响），分区跟随 resolve 的遮挡、region 与同一次几何读取；LayoutDragDrop 加可选的 zones/activeZone，宿主两处只做透传。这样 a、b、c、d 一并解决，activeZone 也不必在宿主比对 JSON。（drop 为 null 时不画分区即可得到“被挡住不显示”。）

[8] 重要 / 不变量与测试设计 / plan.md:36,38,97；layout-drop.ts:119-122；layout-drop.test.ts:121
现象：
  a. “指针在……预备区上……返回 null”表述有歧义。现行规则是真实落点优先，预备区只在没有真实落点时才算（layout-drop.ts:119-122，测试 121 行“有真实落点就是它，预备区盖着也一样”）。如果 resolveLayoutDropZones 看到指针落在任何预备区矩形里就返回 null，那么预备区盖在接收的工具面板上时，drop 是真实落点而分区消失，违反“形状与判定一致”。
  b. 不变量测试只用“四种策略”（假策略）随机点。工作台策略 layoutEdgeTarget 的组合只有三种：编辑组四边恒非 null（edgeTargetOf 永不返回 null，只在 between 且邻居不全是编辑组时改写成 split）；工具面板只有所在轴的两条边。真实形状由策略 + 真实文档决定，假策略测不到。
  c. 随机点落在多边形边界上时（整数像素，宽高相等的正文对角线上），“点所在多边形”不唯一，测试必须定义归属或避开边界。
建议改法：规则写成“仅当该点的真实动作为 null 且落在预备区里时，分区为 null”；neuro-book 加一条单元测试：createLayoutPolicy + 默认树，对每块面板扫整数网格（含缝上 -4 到 +4 像素和夹角），断言 resolveLayoutDrop 的动作等于分区命中；nb-layout 里用浮点随机点避开边界。

[10] 建议 / 边界 / layout-drop.ts:76,89-90
现象：正文零高或零宽（收成标题行的工具面板：strip = 整个头，body 零高）时 nearestEdge 里 relative 是除零（NaN / -Infinity）。实验（/tmp/review-t19-design/exp/e1.ts）：宽松策略下零高正文，头下 1 到 2 像素的缝里指针得到 {edge, top}，不是 strip 也不是 null。

建议改法：零面积正文直接返回 null，并在不变量测试里加一例；resolveLayoutDrop 的同一处也应守住。

[12] 建议 / 无障碍 / plan.md:54,56
现象与问题：
  a. 计划写“缺省只读屏不读”，没写 aria-hidden；SVG 与字应 aria-hidden="true"，否则读屏虚拟光标会读到五个方向词。
  b. forced-colors 只处理了线用 Highlight；压暗层是背景色，强制颜色下作者背景色会被换成系统色（Canvas），压暗层可能变成不透明遮住内容。这一条我没有在浏览器里取证，需要在 Chrome 的 forced-colors 模拟里看一次再定（当前只能说计划没有处理）。
  c. 现有 DropIndicatorLabel 已经处理 prefers-contrast: more 与 prefers-reduced-transparency（DropIndicatorLabel.vue:50）；分区线、压暗层计划没有对应，高对比度下线与压暗对比不足时没有加强。
  d. “淡入 120ms，减少动效时直接出现”：120ms 就是 --motion-fast 的值，应使用 var(--motion-fast)（tokens.css:79，减少动效时被置 0ms !important），不要再写一条硬编码加媒体查询。
  e. live 区：DropFeedbackOverlay 的 live 区挂在 v-if="hasVisibleFeedback" 的根下，没有可见几何（区域、线、条目都无效）时整层连播报一起不在。分区模式下有分区没有药丸时，这一缝隙里读屏无声。预览 areaRect 全为 null 的落点极少（previewEdgeDrop 返回 null），但 hideLabel 把可见文字撤了，等于只剩这条脆弱通道。
建议改法：补 aria-hidden；强制颜色用 forced-color-adjust: none 加系统色或去掉压暗并只留线（待取证）；动效用令牌；live 区与可见几何解耦（独立于 v-if）。

======================================================================
未发现问题的方面
======================================================================

- “形状由 nearestEdge 的规则推出来”这个推导本身成立：读 layout-drop.ts:86-99。窄带是 depth < 比例，按深度升序、取第一个策略给的边；所以相邻边都可用时角按对角线切成梯形，相邻边不可用时窄带占满该角成矩形，最近边不可用且次近边不在窄带内时落到中央。四角、只有对边可用（工具面板）、空面板（centered 整块中央）、进不了中央（无中央块）都与计划描述一致。
- edgeTargetFor 的依赖：工作台的 layoutEdgeTarget 只读 doc、panelId、edge，忽略 tabs（constraints.ts），所以“某条边是否可用依赖被拖的标签”的组合在工作台里不存在；实际只有三种形状：编辑组四边恒可用（edgeTargetOf 对存在的面板永不返回 null），工具面板在所在轴的两条边可用（侧栏、右栏上下，面板左右）。计划“编辑组五块、列上下中、排左右中”与 Spec 输出 10 一致。
- dragState 每帧发布：drag-gesture.ts 的 publish 每次 current.last 是新对象，shallowRef 必然触发，rAF 每帧一次；拖影已依赖它，计划说法属实。
- 缓存不能存分区的推理成立（previews 键只含 source、action、extent）。
- activeZone 用 JSON.stringify 比较 action：zone 与 drop 的动作由同一批构造函数生成，键序相同；放回原处（inPlace）的 center/edge 动作与分区动作相同，自动算当前块，无须特判；strip 与 reveal 没有对应分区所以无激活项，行为符合预期。
- 指针在缝上：resolveInPanel 把点夹进正文再判，分区与落点一致；缝里的归属沿用 4 像素最近接收面板规则。
- 面板最大化：panelGeometry 只返回最大化的那块，分区随之只对它；收成标题行的面板正文零高，指针在头上走 strip，无分区（边界见 10）。
- Teleport 到 body + pointer-events: none 不影响 elementsFromPoint（见 15 的合同提醒）。
- 库边界：resolveLayoutDropZones 是纯函数，放在 layout-drop.ts 符合 nb-layout 核心不依赖 DOM 的约定（boundary.test.ts）。
- 依赖方向：nb-layout 依赖 nb-ui 的令牌，与 --motion-layout、--sash-line-* 的先例一致，不需要反向依赖。
