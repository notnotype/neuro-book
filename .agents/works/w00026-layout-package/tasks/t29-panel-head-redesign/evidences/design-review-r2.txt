## 新发现

### 1. 拖缝展开时，预览和松手后的布局不一致，松手那一刻跳变

严重程度：重要
位置：`packages/nb-layout/src/layout-project.ts:127-136`（垫底的叶没有 `collapse`）；计划“拖它上面那条缝……同一个情形”一句

**现象：** 全部收起（s1、s2、s3，s3 垫底，总高 776）时，拖 s2|s3 那条缝向下 120px：
- 预览是 s1/s2/s3 = 32 / 152 / 592，`changes` 里是 `{s2: false}`。
- 落账（`resizeBranches` → `setPanelCollapsed` → `rebaseIntents` → 重新投影）后是 32 / 712 / 32。

在 sash 0 上拖 +60，或在 sash 0 上按 Enter 也一样：Enter 的预览是 372 / 32 / 372，落账后是 712 / 32 / 32。

**为什么是问题：**
- 手势期间 s3 是吸收者，所以它被拉成 592。
- 一旦有一节展开，s3 在文档里仍是收起的，投影给它配回刚性收起策略（32），吸收者变成刚展开的那一节。
- 计划类比的“今天收起的分节在展开的分节上面”，吸收者本身是展开的，松手前后不变，所以不是同一个情形。
- 用户拖到哪松手，卡片就从预览的样子被动画拉到另一个样子。写回的意图也会丢：单个按比例分的节点，`rebaseIntents` 只保留原份额，拖出来的高度记不下来。

**如何核实：** `exp/filler.test.ts` 的 `describe("commit after drag")`，输出 `preview 32 152 592` 与 `after release 32 712 32`。

**建议改法：** 选一种，写进计划：
- 垫底的那一节上面的缝（以及垫底时与它相邻的缝）全部收起期间不可拖，只能点标题或用命令展开；
- 或者手势开始时就按“展开后的投影”预览，也就是拖动期间不让它吸收；
- 不要靠“已有路径”。

### 2. “垫底”有两套判定：投影按呈现、可见性按文档，会分叉

严重程度：重要
位置：计划“垫底的那一节”（“它是否垫底由文档算得出”）；`layout-project.ts` 的 `assignByParent` 只看得到 `node.children`，也就是已经去掉“放不下收走”（`removed`）的呈现子节点；`web/state/layout-present.ts:66-67`

**现象：**
- 文档里 A、B 收起，C 展开；窗口矮，`presentationCollapse` 把 C 收走。
- 投影里的子节点只剩 [A, B]，全部收起，B 垫底（外框约 700px）。
- 文档判定里 C 还展开着，所以 B 不垫底。
- 此时任何手势预览里 B 的预览高度大于面板头，`pulledOut` 为真，B 的内容露出来，第一轮第 3 条的问题原样回来。
- `geometryOf` 的“只取标题行”如果也按文档判，同样会错：B 的外框是满高，却被当成普通展开的面板取矩形。

**先例：** t28 已经遇到同类分叉，`regionStrip` 的 `merged` 明确写了“按文档数、不看放不下收走”。计划没有说 `assignByParent` 按哪个数。

**建议改法：** 让投影直接交出垫底的节点 id（像 `strips` 一样放进 `LayoutProjection`，比如 `fillers`）。`effectiveVisibleTabs`、`geometryOf`、预览的排除都读它，不各自从文档重算。并在计划里写明按文档数还是按呈现数。

### 3. 垫底的叶只改了最小高度，最大高度没处理；视图可以声明 `maximumSize.height`

严重程度：建议
位置：`web/state/layout-constraints.ts:77-78`；计划只写“最小高度是面板头”

**现象：**
- `panelConstraints` 的 `maxHeight` 取各标签 `maximumSize.height` 的最小值，`shared/views.ts:64` 的声明允许写它。
- 实验：垫底的叶最大高度 300 时，高度是 32 / 32 / 300，诊断为“分支 side 的可用空间 778 有 412 未被任何子节点吸收”，下面留空，卡片不满高。
- 仓库里目前没有视图声明，所以是潜在问题，但这个诊断会冒到 `@issues`。

**建议改法：** 垫底的叶最大高度一并放开（`GRID_UNBOUNDED`），并补一条单测。

### 4. 最大化的面板上点标题会把它收起并退出最大化

严重程度：建议
位置：`WorkbenchShell.vue:187`（`collapsibleHere`）；`layout-doc-store.ts:452-456`（`setCollapsed` 对被最大化的面板退出最大化）

**现象：** 最大化着的分节头上仍会有标记，点标题（“让焦点进来”的老用法）会同时收起它并退出最大化，布局整体变回去。今天点标题只是激活，无副作用。

**建议改法：** 最大化着的面板 `fold` 给 null，点标题保持激活，还原靠还原按钮。

### 5. `fold` 读的是实时布局的预览文档，拖动中标记出没，标题横向跳

严重程度：建议
位置：`WorkbenchShell.vue:187`（用 `renderedDoc`）；对照 `titleOnlyPanels`，它明确按已提交的文档算，“拖动中头不跟着变”

**现象：** 实时布局拖起一节时，预览文档里同一列只剩一节，该节变成 `lone-section`，`fold` 消失。标题左缘随之偏移一个标记宽（约 20px）。原先消失的是右端的按钮，不改标题位置。第 2 稿自己写了“有无标记的头左缘差一个标记宽”，所以这个跳变是新引入的。

**建议改法：** `fold` 和标题字色按已提交的 `doc` 算，或者拖动中给标记留位。

### 6. 对齐判据：“8px”前提没有实测，字形居中的量法依赖字体

严重程度：建议
位置：计划“对齐”第一、二条

**现象：**
- “标记左缘离卡片左缘 8px（和正文的左内边距一样）”：正文并没有统一的左内边距。
  - nb-ui 的 `Tree` 零级行缩进是 `calc(12px * 0 + 4px)`（`Tree.vue:92`）。
  - 资源管理器行是 `paddingLeft: 8px`，twisty 是 16px 的方框里放 14px 的箭头（`ExplorerRow.vue:77,224`），箭头往里约 1px。
- 开发者说的“对齐了没”最可能是标记和下面树的箭头，计划却没有对着任何一个真实视图量。资源管理器的箭头还有 `rotate-90` 过渡，标记若是换图标，两者动画也不一致。
- “字形竖直中心差不超过 1px”：`Range.getBoundingClientRect` 量的是行盒，不是字形墨迹。按常见 CJK 字体的 ascent 与 descent 算，行盒中心和 em 框中心差约 0.7px（12px 字号）。拉丁字母的标题差得更大，所以这条判据在 e2e 机器的字体不同时会误报或漏报。

**建议改法：**
- 指定参照视图（资源管理器），e2e 里量 `[data-explorer-twisty]` 里图标的矩形和标记图标的矩形，容差 ±1px，图标尺寸取同一档（`h-3.5`）。
- 竖直居中改成对头的 32px 盒量，或用截图像素。

### 7. 接管标题区的头，标题居中，和开发者选的甲（所有标题左对齐）不一致，计划却把它豁免出对齐判据

严重程度：建议
位置：计划“视图接管标题区时”一段

**现象：** 同一列里对话（接管）标题居中，别的行左对齐。开发者的附言正是“看看对齐了没”。计划自己把这个模式排除在对齐判定之外，没有告诉开发者。

**建议改法：** 在交付说明里点出这一处，或者接管模式也左对齐（标记之后），由开发者定。

### 8. 键盘与读屏：焦点依赖浏览器对点击的聚焦，Space 与 VS Code 的约定不同

严重程度：建议
位置：计划“点击只有一个事件”；`WorkbenchShell.vue:304-309`

**现象：**
- 展开 → 收起这条路径只调 `setCollapsed`，没有显式聚焦。Safari、macOS 上的 Firefox 点击按钮不聚焦，`focusedPanel` 与 `currentPanel` 不更新，后面按快捷键作用在别的面板上。
- 对照 VS Code 的视图分节头：Enter 与 Space 都切换，Left 与 Right 展开与收起，Up 与 Down 在各头之间移动。这里 Space 被拖动占用，Enter 之外没有其它键，可访问描述（`dragHint`）要能说清这一点。

**建议改法：** Shell 在切换后对标题按钮显式 `focus()`；`dragHint` 的文案里写明 Enter 切换。

### 9. 把 `aria-pressed` 加进豁免是改共享 CSS

严重程度：建议
位置：`web/components/hover-actions.css:13`

**现象：** 该规则对所有 `[data-hover-actions]` 生效，其中包括视图动作区（`TitleActions`）和 `EditorGroupHead`。给整条规则加 `:has([aria-pressed="true"])`，任何按下的切换类视图动作都会让那一组一直显示，改了 `views.md` 输出 10 的“视图动作随鼠标显示”。目前仓库里这几处没有 `aria-pressed`，所以暂时无影响。

**建议改法：** 只给框架按钮容器加一个修饰（例如 `data-hover-actions="frame"` 带豁免），不改通用选择器。

## 未发现问题的方面

- `rebaseIntents`：垫底的那一节在文档里仍是收起的，`isSkipped` 照常跳过，其余节全是收起，写回时 `before=after=0`，`scale=1`，不会误改意图。
- `minimumOf`、放不下收走：最小高度取面板头后，与收起时的 32 一致，列的最小值不变。
- 求解器：垫底的叶按比例分、没有收起策略，`boundsFit` 通过，不再有第一轮的拒绝。点上面某节展开，卡片总高不变。
- 内容停放：`!item.active` 时 `visibility:hidden` 加 `inert`（`useContentLayer.ts:83,148`），垫底的叶外框满高也不会拦指针。
- t28 包装分支：入口条加垫底，`:sections` 内层能吸收余量，无诊断。
- 落点几何：`geometryOf` 只取标题行后，`layoutDropPanelAt`、`layoutSeamsOf`、键盘候选三者一致。
- Space 的 keyup 拦截、拖动后 click 被吞：已有，不受影响。
- 触摸设备走 `@media (hover: hover)` 之外一直显示：已有。
- “点标题激活”：e2e 清单已列，我没有逐个核对用例。
