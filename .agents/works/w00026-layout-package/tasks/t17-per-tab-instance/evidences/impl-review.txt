F1 [重要] 不变量/正确性：settle 会让后挂的、还没追上新正文的视图把旧内容当输入提交，产生看不见的假冲突，并让保存返回 unresolved
位置：packages/neuro-book/src/plugins/editor/web/documents/store.ts:526（flush 逐个调 flushers）、MonacoControl.vue:158-161（attach 的 flush）、MarkdownControl.vue:136-163（commitNow）；放大它的是本次改动：隐藏的控件不再 detach（area.ts:325 tabBinding 的 attach、EditorGroup.vue 的 controls）。
现象：同一文档有两个活着的视图 A（先挂）、B（后挂，现在包括被盖住的标签），A 有缓冲输入（Markdown 的 150 ms）时调用 documents.settle / 保存 / 磁盘变化的 flush：A 先提交，正文与修订前进；B 的 Vue watch 要到下一个微任务才追上，它的 flush 看到“本地内容 != 正文”，用旧的 confirmed 修订提交，得到 conflict，B.held = true，documents.candidates 里多了 B 的 token。
为什么是问题：(1) 冲突记在被盖住的视图上，EditorGroup 的横幅只读当前标签的 binding，用户看不到、也无从裁决；(2) saveNow 在 candidates.size > 0 时返回 unresolved，保存静默失败；(3) base 里只有“两个组同时显示同一文档”才会有这个顺序依赖，本次让每个同文档标签（包括别的组里被盖住的）都挂着视图，暴露面变大。
如何核实：已在 store 层复现——/tmp/review-t17-impl/exp.test.ts 的 E4：拆出同一文档的第二个标签，给两个绑定各挂一个“Markdown 式”假控件（flush = 本地与正文不同就 commit(confirmed, local)），先挂的置本地内容为 "AX"，settle 后：doc.text = "AX"，第二个视图 held = true、unresolved() = true，documents.save 返回 {ok:false, code:"unresolved"}。注意这个实验绕过了真实控件，只证明 store 的 flush 顺序依赖；请主 Agent 在真实运行时复现：同一 Markdown 文件开在左右两组，左组先开，打字后 150 ms 内触发不经 onIntent 的 settle（例如外部程序写同一文件让 store.ts:352 的 flush 走一遍，或 Agent 调 nbook.editor.save-all）。
缓解（所以只算重要不算阻断）：键盘 Ctrl+S/Ctrl+W、标签菜单、标题动作经 plugin.ts:283/312/315 先调活动控件的 flushPendingChange，再异步执行命令，B 的 watch 在这之间已追上；点击标签/面板会先 blur 提交。剩下的是文件监视与无焦点切换的命令入口。
建议改法：控件侧——flush 只在“自上次确认/采用之后确有本地改动”时提交（Monaco 比较 state.source/base，Markdown 记 adopt 时的 doc 引用），不要拿“本地 != 正文”当判据；或 store 侧——flush(entry) 对 flushers 做两阶段（先让所有视图 adopt 最新正文，再收集提交）。同时补一个 area 级测试：两个绑定、先挂的有缓冲输入，settle 后另一个绑定的 unresolved() 为假。

F2 [建议] 正确性/性能：名额一释放，早已回收的标签的控件又被挂回来（后台悄悄多建一个编辑器）
位置：area.ts:359 mountedControls、EditorGroup.vue:62-66 mounted/binding。
现象：mountedControls 是“按最近使用次序取每种编辑器前 N 个”的纯计算。超过上限后，关闭任意一个留着控件的标签（或 preview 替换），排在第 N+1 位的、早已回收的标签就挤进前 N 位，它的 EditorGroup 立刻挂出控件，而用户并没有去看它。
为什么是问题：回收的意义是少养编辑器；这里每关一个标签就在后台新建一个（Monaco 每个实例约 6 MB，计划引用的 t02 数据；TipTap 重新 mount 并带起菜单层的监听），关一排标签就是一串后台创建，且没有任何用户动作对应它。Spec 的上限（≤20）仍然成立，所以不是合同违反，是成本与意图不符。
如何核实：实验 E1（area 层，不含 Vue 渲染）：上限 2，依次开 a、b、c（Markdown）后 mountedControls = {b, c}，a 不在；close(c) 之后 mountedControls = {a, b}，输出 "before close kept: [false,true,true]  after closing c, kept: [true,true]"。真实运行时请用 Lab 的 recycle 场景：6 个标签、每种 2 个，关掉第 2 个 Markdown 标签后数 [data-editor-kind="nbook.editor.markdown"] 应为 2 但其中一个是没有被点过的后台控件。
建议改法：把“留着控件的集合”做成显式状态——激活时加入、超限时踢最久没用的，释放名额不回填；或在 mountedControls 里只让“当前活动标签 + 此前已经挂着的”进集合（需要保存上一次集合）。补测试：超限后关闭活动标签，集合不增加。

F3 [建议] 不变量：dropEditorState 不清 bindings，连续两次换编辑器（中间没有渲染）会让绑定带着已释放的槽回来
位置：area.ts:543-559 changeEditor、245 dropEditorState、282-295 tabBinding 的复用判据。
现象：reopenWith 只删 slots/controlSlots 里换下编辑器的那两份，bindings.get(tabId) 里旧编辑器的绑定留着，等下一次 tabBinding 才被换掉。如果在渲染前又换回原编辑器（两次 reopenWith 同一轮里发生，例如 Agent 连发两条命令、脚本），tabBinding 的“同编辑器同文档就复用”判据命中旧绑定：它的 slot 对象已被 dispose、也不在 slots 表里，slot.state 还指着已释放的 Monaco 模型，控件 enter 时 editor.setModel(已释放模型)。
如何核实：实验 E2（直接调内部 API，绕过渲染，所以只证明状态不一致）：先拿到绑定 b0 并给它的槽放 state/dispose 标记，reopenWith(CODE_EDITOR) 再 reopenWith(MARKDOWN_EDITOR)，tabBinding 返回的仍是 b0，dispose 标记已触发，slot.state 仍是旧值。输出 "same binding object reused: true disposed: [b0.slot disposed] slot.state: {model:旧模型}"。真实触发要两次换编辑器之间没有 Vue flush，可达性窄，请主 Agent 决定是否值得处理。
同一个洞还有一个更窄的变体：tabBinding 在 existing.document !== document 时会新建绑定却沿用 slots 里同键的旧槽（键里去掉了 documentId）。我没找到当前可达的路径（references 只在 changeEditor 文本/字节互换时换文档，那时编辑器也变了），但失去了 base 里“键含 documentId”的保护。
建议改法：dropEditorState 同时 bindings.delete（若 binding.editor === 被换下的编辑器）；tabBinding 在 existing 存在但不可复用时先丢弃对应的旧槽。

F4 [建议] 正确性（从代码推断，极窄）：focusActive 的“这个标签已在等定位”只比 tabId，标签换组后等待被静默取消
位置：area.ts:469-473 focusActive、476-492 的 watch。
现象：pendingReveal 记 {groupId, tabId}。若同一个标签还在等（继续写作的 reveal:"end"、恢复会话的聚焦、上一次 focusActive 的等待）时被移到另一个组，moveTab 末尾的 focusActive 看到 pending.tabId === 活动标签 id，不重写；watch 的 getter 却用旧 groupId 找标签，找不到判 cancelled，等待清空，焦点没人给，reveal:"end" 也丢。

如何核实：未跑（需要扣住读取再拖标签）；读 area.ts:469-492 即可。
建议改法：focusActive 里同标签但 groupId 不同时也重写（保留 reveal 为较强的那个）。补一个 area 测试：open(reveal:"end") 扣住读取、moveToNewGroup、放行，句柄应拿到 focus。

F8 [建议] 性能（有数字的部分是实测，渲染部分是从代码推断）
(a) 实测（P1，模型层，30 个 Markdown 标签，不含 Vue 渲染）：一次 activate + mountedControls 重算 + 30 次 groups.find 共 0.18 ms，可忽略。
(b) 从代码推断：groups.groups 每变一次（切标签、preview 转正、改语言，以及停笔 1 秒后的光标记录），30 个 EditorGroup 的 found 都返回新对象（groups.find 每次造 {group, tab}），controls 每次返回新数组，所以 30 个实例全部重渲染一遍小模板；打字时约每秒一次。单次按键本身只波及同一文档的视图（tabWritable 只读 document.writable），与标签数无关。没测渲染耗时；若要数字请用 scripts/perf 在 30 标签下量切换与停笔后的长任务。可以让 found 只在 tab 对象变化时才变（computed 里比较 group/tab 引用）来消掉。
(c) 实例开销：每个 Monaco 实例各有一个 MutationObserver 监听 documentElement（MonacoControl.vue 的 themeObserver），主题变一次，20 个观察者各做一次 defineTheme+setTheme，setTheme 又会让全部编辑器重算；总计约 400 次重绘。计划第 14 条已接受，这里只给数字。
(d) 内存：视图状态槽不再有上限（base 的 RETAINED_VIEWS：每组每种最多 3 份干净的非活动槽）。现在打开并激活过的每个标签，其 Monaco 模型或 TipTap 实例（约 0.9 MB，见 evidences/measure-tabs.txt）一直留到标签关闭；回收只省 DOM。计划已记为接受的取舍并说“很大再定上限”，但相对 base 这是内存的无界增长，建议至少给“干净且无未裁决输入”的槽设一个全局上限（光标已在标签记录里，超限的槽可以按 base 的做法淘汰，只丢撤销历史）。

对照 VS Code 的差异（参照有、计划与实现都没有）：VS Code 隐藏的编辑器不保留控件，只序列化视图状态，并有 workbench.editor.limit 这类上限；这里为“撤销不丢”保留了 TipTap 实例，属于开发者已定的取舍（计划选项 c），不算遗漏。参照里另有“被回收标签的未保存输入仍提示”——这里 candidates/held 在文档上而不是控件上，回收不会丢，已核对。
