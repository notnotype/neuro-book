### 1. 答案、密钥与测量数据缺少执行者之外的信任边界

**严重程度**：阻断；**类别**：不变量

**位置**：设计稿“任务集／本地假站（主力）”“规矩”“两边怎么跑”“放在哪里”；`docs/specs/agent/eval.md:16-18,70-75,136-139`；browser-use 1.0.6 的 `browser_use/agent/service.py:224-227,349-356`。

**现象**：每次新建 Chrome 和假站，只隔离了浏览器数据与业务初始状态。执行者是能在宿主上运行任意代码的 Python/JS Agent；两边都明确没有 OS 沙箱。设计让评分规则、种子真值、其他运行记录、BU 明文与执行器处在同一宿主文件权限范围。环境变量传密钥也不是执行代码与密钥之间的隔离。尤其 NeuroBook 的 eval 内核继承服务端环境，代码的权限与服务端一致。

**为什么是问题**：本地规则评分与 BU 取证都要求真值和证据独立于被测对象。只有每次起一个不同端口的假站不足以建立这个不变量。即使无恶意，模型遵照网页上的不可信指令或误写文件也能污染其他 attempt；另外，模型生成的真实站操作有外部影响。保存结果的目录不进 Git 不等于对执行者不可读写。BU 的暗记只是事后信号，不能作为保密或隔离的证明。

**如何核实**：上述两个版本的源码/Spec 均明确声明代码执行非沙箱；检查 `Agent.workspace` 的寿命和 `eval.md` 的进程权限合同即可确认此设计未提供所需隔离。不接触实际密钥或数据做验证。实施时用合成无害标记做隔离验收，确认执行者只拥有本次任务所需输入、浏览器及交付目录，其他数据与测量方不可访问。

**建议改法**：评测宿主承担隔离（不改变 t01 已定的产品审批策略）。执行环境只放本次任务与合成附件，独立进程/系统权限和存储边界；裁判、真值、日志收集与模型认证由可信侧持有。两边的代码均不得获得主机真实凭据、日用 Chrome、其他 attempt 及判分数据。模型通道由可信适配层管理。真站活动仅限已授权的任务，受控出口与同一范围政策，先确认 BU 子集不涉及未经允许的真实站写入或敏感数据。隔离与评分证据不可由被测代码任意改写应列为第一阶段验收。这是评测场地的约束，不要求把产品 eval 改成沙箱。

### 2. BU 原评测运行器与 1.0.6 执行轨迹不兼容，两边都需要适配

**严重程度**：阻断；**类别**：正确性

**位置**：设计稿“判分／BU 评判器”“分阶段”；benchmark `pyproject.toml:6-15`、`run_eval.py:100-110,167-203`、`evaluation.py:196-318`；browser-use 1.0.6 `agent/views.py:40-76,83-172`、`agent/service.py:533-546`。

**现象**：设计只写“小适配，把 NeuroBook 的会话日志转成它的轨迹格式”。钉住的 benchmark 依赖实际是 browser-use 0.11.5；其 Python 执行路径直接调用 0.x 的 `history.agent_steps()`、`screenshot_paths()`、`agent.history`、`agent.file_system`、`usage.total_cost`。前四类接口在 1.0.6 已删除，最后一项也改为 `result.cost_usd`。1.0.6 提供的是 Pydantic AI 消息列表 `result.messages`、`result.usage`、`result.partial` 等。官方默认执行器已改为 BrowserCode 0.1.20（benchmark README:108-161）。

**为什么是问题**：不能把 1.0.6 装进评判器锁定环境，照原 `run_eval.py` 接它，也不能只转换 NB 的轨迹。两套不同年代的 browser-use API 混装或靠删掉不兼容字段，会造成无评分或证据缺失。已有 t01 脚本只在正常返回时序列化 `result.messages`，没有 BU trace、文件交付、失败证据合同。好消息是评判器自身的 `judge_trace(task, trace, llm)` 可以独立使用，不必重写判分规则。

**如何核实**：静态比较上述方法调用与 1.0.6 `agent/views.py` 的 `REMOVED`、`__getattr__`，以及 benchmark `evaluation.py:196-234` 接收的 dict 字段。t01 `experiments/run_browser_use.py:38-58` 已展示 1.0.6 的正常返回接口。无需解密或发模型请求。

**建议改法**：落实成独立 Python 1.0.6 执行环境、独立依赖锁的 0.11.5 评判环境，均通过明确版本化的、框架无关的执行结果/证据合同交接；两个执行器都负责转换。第一阶段就锁定 trace 形状、partial/timeout、文件与图片交付、错误与用量。用自造任务与本地无费用的记录样本贯穿两种适配器到评判请求构造；保留 t01 的 `judge=False`（否则内置评判也会计进执行用量），第三阶段接 NB 时复用相同合同。

### 3. Agent 测试场地的手动时钟改变被测运行循环

**严重程度**：阻断；**类别**：正确性

**位置**：设计稿“两边怎么跑／NeuroBook 一边”；`packages/neuro-book/src/plugins/settings/testing/world.ts:42-65,69-97`、`agent/testing/world.ts:76-89`、`agent/backend/agent.ts:139-158,250-261`、`agent/backend/eval/tool.ts:293-327,485-499`（后三个路径均相对于 `packages/neuro-book/src/plugins/`）。

**现象**：`settingsWorld` 写死 `new ManualClock()`，服务端的 `clockKey`、远程节点、项目及窗口都用它；`agentWorld` 没有选择真实时钟的参数。Agent 的重发等待与 eval 单元超时直接使用注入的时钟。现有 `web-tools/agent.llm.test.ts:115-145` 只等正常运行结束，未演示真实时间推进。

**为什么是问题**：时钟不推进时，NB 的默认 30 秒 eval 单元超时永远不触发，也不完成需要时钟的等待，发生模型失败后的退避重发会挂住。BU 用 `time.monotonic()`，默认单元 120 秒（`agent/loop.py:126-157,184`）。外层 600/1800 秒硬超时无法校正这种运行内行为差异。反过来测试者随轮询推进手动时钟，会把真实浏览器/模型的异步等待变成测试负载相关的计时。重复三次没意义。

**如何核实**：读 `settingsWorld` 的时钟装配、`agent.ts` 的 `kernelClock.wait`（使用 `clock.schedule`）及 eval 的 `Deadline`。以上调用链已落实到被测的真实插件。worktree 无 `node_modules`，此次不运行合同测试、不安装依赖。主 Agent 应在本地无模型费用的场地验收：正常单元、卡住的单元、一次临时模型传输失败、取消中的清理，检查 real-clock 的期限与重发真的经过。

**建议改法**：固定时间只作用于假站业务数据与其展示，不冻结执行器的时钟。给测试装配提取一条可选择的 real-clock 运行场地，或复用产品的隔离宿主，避免用评测专用逻辑修改 Agent 内部。明确用单调墙钟计时、统一外层总时限，另以产品正常配置的单元时限与重试策略体现整套能力。仅往 `hubCapabilities` 再追加一个同键能力并不是已定义的替换合同。

### 4. 两边的 input 用量口径不同，直接比较会把 1.5 倍判据算反

**严重程度**：阻断；**类别**：正确性

**位置**：设计稿“报表”“怎么算‘接近 browser-use’”；browser-use 1.0.6 `agent/loop.py:876-890,1210-1227,1321-1325`；`packages/nb-harness/src/kernel/model/omp.ts:493-501`、`kernel/compaction/compact.ts:52`。

**现象**：BU 汇总 `result.usage['input']` 为包含缓存的 `input_tokens`。其源码在转为 pi 格式时明确减去 `cache_read_tokens`、`cache_write_tokens`。NB 的 `Usage.input/cacheRead/cacheWrite` 来自 OMP，input 是不含缓存的部分（上下文估计的后备公式也将这三项相加）。设计没有规定统一计量方式，也没区分已返回的消息与线上实际尝试。

**为什么是问题**：t01 调研的发布任务，BU 总输入 54,636（44,800 缓存），omp 的输入为 25,863 未命中加 312,960 命中。按两个 `input` 字段直接除会得到 0.473，实际总输入比为 6.20。若以这种接线判定 1.5 倍，完全改变结论。这不是对后来 NB 效率的预测，而是用已有真实记录展示计量差错。另据 `eval.md` 和 harness 的用量合同，重试及取消时用量可能只是下界；BU 的 `requests` 仅数 `ModelResponse`，并不含所有 HTTP 重发。judge=True 默认还多发内置评判请求并算进用量（`service.py:238-241,600-616`）。

**如何核实**：按上述两边的换算公式手算；主 Agent 用合成的含缓存、无缓存、缺 usage、重试和取消的服务商回复验收两端归一化。NB 的 `ModelWireObserver.attempt`（`kernel/api/model.ts:225-259`）提供实际 HTTP 尝试的观测点。

**建议改法**：将统一指标定义为每次执行的总输入（含命中及缓存写）与输出，另列各缓存项、推理用量（服务商有给时）、线上尝试数、模型循环数、费用及计量完整性。NB 总输入 = input + cacheRead + cacheWrite，BU 已含缓存的 input 不再加缓存。压缩、内部重试等执行开销纳入，独立评判和重跑的开销分账。未知/不完整值不填零；若无法确定判据所需的用量，结论标未判定。先钉准同一口径再算中位数和比值。

### 5. 同名模型和档位配置不能证明两边实收条件一致

- 严重度：阻断
- 类别：比较公平性、接入可行性
- 位置：设计稿「两边怎么跑」第 51 行。t01 `experiments/run_browser_use.py:18-38`；BU `browser_use/agent/service.py:229-232`；NB `packages/nb-models/src/core/core.ts:242-261`、`packages/nb-harness/src/models/target.ts:97-102,271-298`、`kernel/api/reasoning.ts:22-38`、`kernel/model/omp.ts:429-458`；`docs/specs/agent/compaction.md:31-44`。
- 现象：稿中 Luna 固定 medium，两个 Gemini 先试 medium，网关拒绝再选 high。这只约束配置名。t01 的 BU Gemini 样本走原生 Google SDK，未覆盖 neon 或所提 OpenAI 兼容路径。开发环境已记录 extremelycat 直连 TLS 握手重置，NB 场地若没有注入网络出口，harness 的缺省是直连。
- 原因：BU 的兼容路径从 `ChatOpenAI` 取推理参数，`Agent(reasoning=...)` 在这条路径不生效。NB 的档位可按模型能力夹档或省略，`modelTargetOf` 当前不传配置的 `efforts`。视觉、上下文窗口、最大输出也由两套适配器各自解析。另有执行期的模型调用：NB `inplace` 用会话模型与档位，`summary` 走独立 `compaction` 角色，未绑定会失败。只记录主会话名称会漏掉额外模型或档位差异。
- 核实方法：静态追踪 t01 的模型构造、BU 推理参数说明与 NB 的模型物化和请求路径。`packages/nb-harness/src/kernel/model/reasoning.test.ts` 已示范用本地假端点核对实收请求。三组实际网关兼容性未联机验证。
- 建议：每组先冻结提供方、部署与线协议、两侧实收推理字段、视觉输入、上下文及单轮输出上限、网络出口、缓存策略与辅助模型配置。用假端点断言线上的字段和图片，再经授权用无评测内容的短请求核对实际模型、工具回合与档位。两侧都支持才改档且整组重测，禁静默换模型，无法验成的组标未比较。压缩策略可保留系统差异，但固定角色与档位，按本次执行记录其请求和用量。

### 6. 「接近」缺少固定的配对单位、取数规则与未判定出口

**严重程度**　阻断
**类别**　正确性
**位置**　设计稿第 14、65、77 行；t02 README 决定 3；`ref/coding-agent-browser-tools.json` 的 `taskScores`。

**现象**　已定的是逐题配对差的 95% 区间下界和输入中位数阈值。稿未规定本地每题三次如何合成题分、配对失败如何保留、两套题集在同一模型上必须各过还是合成一个结论。合并 72 条运行计算区间会将同题重复当成独立题。对固定且定向挑选的 25 道真站题做按题自助抽样，也不能直接把结果解释成整套 V2.1 或今后网站的区间。

**为什么是问题**　用公开分数中的 81 个均分合格题，按四工具极差取最高 25 个作诊断，对每个工具与 `browser-harness` 做 20,000 次按题配对抽样。三个差值的 95% 区间半宽约 19–20 分，远宽于 5 分界；全 100 题约 6 分。所用对照是外部工具，实际两边精度有待预试。24/25 题规模可能有用，却未证明有能力给出接近结论。下界越不过 −5 也可能只是精度不足。

**如何核实**　读取公开 JSON 的分数，按题保留两边，不分别抽样。用 `Random(20261126)` 算每次差值均值的 2.5% 和 97.5% 分位。例如极差最大 25 题的 `playwright-mcp` 减 `browser-harness` 为 −3.60 分，区间 [−22.76, 15.72]。

**建议改法**　预先定义每模型×题集的结论。每题先平均预定重复、各题等权，按题或预定共用场景簇重采样，整个配对一起采；若目标仅是固定题集上的运行波动，需估计题内重复的不确定性，BU 每题一次时注明无法单独估计。预定输入中位数分母和样本集，真实执行失败按细则打分，缺证与无效配对单列并报告覆盖率和敏感性。显示「达到」「有证据低于要求」「未判定」，冻结题数、覆盖率和扩样规则。逐模型维持已定口径；若要一句综合结论，事先写清哪些组必须通过，哪些只是描述性结果。

### 7. 独立截图连接缺少同一套取证时序，可能漏掉一边的成功证据

**严重程度**　重要
**类别**　正确性
**位置**　设计稿第 48、60 行；benchmark `bcode_runner.py:249-317`、`bcode_eval.py:185-188`、`evaluation.py:206-247`；BU `browser_use/agent/loop.py:137,197-198`；NB `packages/neuro-book/src/plugins/agent/backend/eval/tool.ts:293-370`。

**现象**　稿写「导航与页面变化后」截图，没定义等待什么变化、一次 Python/JS 调用内多次浏览器交互捕捉哪几次，也没有初始、终止、瞬态或多标签的取证规则。benchmark 的 V2.1 BrowserCode 适配器按完成的工具事件编号采所有 page target。V2.1 评判配置记的是 `before_action`，`judge_trace` 对未给时序字段的轨迹也默认 `before`；实现者不能将其与“页面变化后”对齐而不声明另一个裁判版本。同一个观察者还可能把 NB 的后置帧标成前置，或把工具中途出现又关闭的页面漏掉。

**为什么是问题**　工具批处理、SPA、弹窗、跨域 iframe、后台标签和下载不保证有主文档导航。两边可能做出同样业务结果，裁判却只看到一边证据。BU 的内部 `after_tool` 是等待式钩子，若仅一侧阻塞截图会把观察耗时带进单侧限额。裁判还会去重、抽样和压图，缺关键帧即使得到数字也不代表证据完整，尤其是依赖画面才能读取的任务。

**如何核实**　对照 BrowserCode 的采样基准、裁判对时序字段的读取和两边的工具边界。实施时在合成站人工构造无导航更新、短寿命弹窗、两标签、截图失败和超时留证，以同一组动作核对两边打包后仍有正确的目标与步骤引用。

**建议改法**　把观察时点、目标类型、去重范围和采样上限定为同一合同。记录单调时刻、工具调用及 target 标识，保留初/终帧和重要状态转移，显式填报截图时序、丢帧原因及压图后的证据覆盖。观察端只读，不抢焦点，不接管网络或执行端下载设置。两边同样限速，分别报观察开销和执行用时。在完成或取消后给留证一段固定的收尾时限，再关闭 Chrome。

### 8. 时限、失败归因与重跑规则会改变被计入的样本

**严重程度**　重要
**类别**　不变量
**位置**　设计稿第 53、65、87 行；BU `browser_use/agent/loop.py:110-115,1292-1329`、`agent/service.py:469-545,563-590`；NB `docs/specs/agent/run-guards.md:29-51`、`docs/specs/agent/sessions.md:71-75,99,115-119`；benchmark `run_eval.py:173-201,232-275`。

**现象**　两边同写 10/30 分钟，实际内部计时点不同。BU 的执行预算在预检和起浏览器之后进入模型循环，另有步数上限、交付专用轮、SDK 重发和流超时。NB 缺省允许 10 次模型重发，停一次运行靠会话 `abort`，放弃等待结果不会把运行停掉。中转 5xx 可能在内部重发后恢复，也可能由某侧独有的请求限制触发；如果遇到 5xx 就整题重开一遍，会把执行差异错归成基础设施故障。

**为什么是问题**　一侧获得额外尝试，另一侧保留原失败，配对分会有偏差。若只在最后写 `report.json`，进程中断后可能丢执行状态，续跑重复收费或遗失已有部分交付。有部分成果的超时、裁判出错与完全未执行需要不同结局。

**如何核实**　追踪上游的时限和取部分证据路径。benchmark 超时仍尝试留证，并分开已评分均值与完整均值。接入时用合成故障校验阶段与次数：任务中途达到时限、有部分文件；预检断开；模型间歇 5xx；浏览器进程被终止；裁判响应坏形状；收尾又超时。

**建议改法**　以调度器的单调墙钟定义相同的就绪点、硬截止与有限收尾，单列启动、执行、清理、裁判耗时，冻结并记录两侧内部限制。NB 按 `runId` 取消并等待终态，BU 留下部分结果和已产生证据。每个计划配对和每次物理尝试有独立 id，按阶段原子落盘。只有预定义且有独立证据的基础设施失败才允许按规则补同配对；执行超时、放弃或请求方式不兼容保留原结局。裁判失败仅对冻结证据重判，显式记账。续跑沿用完成项，所有原尝试和缺配对原因进入汇总。

### 9. 裁判返回数值时仍可能缺证，冻结模型名也不能证明判分等价

**严重程度**　重要
**类别**　正确性
**位置**　设计稿第 58、60–61、65–66 行；benchmark `evaluation.py:93-147,174-193,283-318`、`findings_judge.py:55-103,274-308`、`bcode_eval.py:73-85`。

**现象**　V2.1 的 `missing_evidence` 指采集方漏掉或截去了已有证据，`absent_scope` 指细则承认的范围或分支缺席。两者在原评分公式都不给该条权重。`judge_trace` 会另外输出 `evidence_missing_items`，仍能给数值；BrowserCode 适配器仅凭 `score is not None` 就标 `judged`。例如唯一缺失的是权重 20 的成功证据，数值上与该条真的做错相同。

**为什么是问题**　采集器差异可被误判成执行器得分差。合法的空范围、做错、证据缺失和裁判失败需要各自可追溯。指定 gpt-5.6-luna xhigh 仍未锁定中转实际部署、结构化输出、输出上限和判分波动。原适配器也按前缀过滤思考文字，两边若用不同标签，送判材料的形状会不一样。

**如何核实**　沿源码比较缺证分支、评分算式与 `judged` 的赋值。用合成细则做真完成、未执行、不可评估、证据被截、前后态冲突的标准轨迹，跑到两套证据组织和同一裁判输入；网关及裁判一致性未实测。

**建议改法**　冻结数据发行版与密文哈希、裁判代码和依赖、实收模型参数、证据适配版本。保留上游原分与逐条状态，另按采集完备性标明某项是否可纳入比较。统一剔除两侧思考字段、隐藏可去除的系统标签、核对引用的事实与证据，先以有人工真值的合成轨迹检查等价判分，再盲审少量样本和近阈值配对估计裁判误差。中文真站自制细则同样做判断校准，答对但无来源记录与诚实报阻断分别验收。

### 10. BU 的 56 题候选无法复算，偏向高分差的子集需要限定用途

**严重程度**　重要
**类别**　测试
**位置**　设计稿第 38–39、66、88 行；`ref/coding-agent-browser-tools.json:3-7,97-698`；benchmark `RUBRIC_REVISION.md:7-18`。

**现象**　四工具均分落在闭区间 [0.2, 0.8] 的是 81 题，去掉端点是 80 题。稿中的 56 题还用了「分差大」的条件，未给分差定义、阈值、同分顺序或可达性探测标准。公开成绩来自 Codex CLI 在 BU 云 Chrome 和美国代理下的单次运行。选分差大的任务会偏向那一组合下有极端观测值的题。再筛英国出口可达，只能覆盖被筛中的任务和站点。

**为什么是问题**　不同人可合理地选出不同 25 题，基线和后续版本也可能通过换题掩盖退步。一次执行的极端差值还混有模型、网站、采集和裁判波动，不能直接当作该题的稳定区分度。挑题诊断中，四工具均分由全 100 题的 59.44 分变为 81 个合格题的 54.62 分，再到按极差选 25 题的 58.24 分，组成改变已有可测影响。

**如何核实**　对公开 JSON 用四列等权平均计算边界内题数，再用每题最高分减最低分排序核对。只用公开分数，未解密或探测站点。

**建议改法**　两边正式执行之前冻结数据发行版、密文哈希、选题算法和最终题号清单。定义阈值、排序、同分处理、按站点或能力的配额、可达性窗口及排除理由。将面向问题定位的高分差题标为定向样本。若结论需要覆盖更广的能力，预留按能力与站点分层的题，以及不用于调提示词的留出题。里程碑只对固定清单作答，站点退役时开新版本并保留共同题桥接。

### 11. 假站规则尚不能区分页面操作、业务提交与安全事件

**严重程度**　重要
**类别**　正确性
**位置**　设计稿第 24–33、58–59 行。t01 `experiments/author-backend/index.html:107-131`、`server.py:19-21,36-54`。Work README 第 19 行要求动作经 CDP 发可信输入。

**现象**　原假后台的校验和确认位于页面端。服务端给发布请求编号、记正文并返回 200，连 JSON 解析失败也如此，未建可核对的业务状态。沿用这类日志做成功判据，直接请求站点接口和通过页面完成操作可得相同分。若只比规范化的回答，没读取来源的猜中也能得分。只改页面显示又可能在截图中看似已提交。

**为什么是问题**　得分可以绕过要覆盖的受控输入、拖放、二次确认与跨标签操作。安全项也需要独立定义。一次被拦的越界尝试与一次已生效的越权写入是不同事件。无收集请求也不能证明抗注入：页面可能没访问、注入载体没被呈现，或采集器漏记。重复提交可能属于业务错误，不能都归为遵从注入。

**如何核实**　对照现有服务端和页面的成功条件。用合成证据验收已提交、仅改显示、合法 API 交付、未经过要求的页面流程、错误条目、重复提交、越界被拒、越权已生效、注入未接触和观察缺失。验证答案规范化不会合并错误日期、单位、符号或顺序。

**建议改法**　每题预先注明测目标达成还是页面动作。对后者要求独立观测到有意义的输入及服务端提交，允许合法的页面 JS 读取，不按某个工具名卡解法。用独立裁判核对事务前后状态、记录 id、顺序和副作用，保留客户端请求、服务端接受与实际生效的区别。安全项单独记录暴露机会、尝试、拦截、效果和证据来源，预定哪些已证实事件触发全题清零，保留清零前分数。先用同套反例验收裁判，再增加题量。

### 12. 单一报表产物没有划清私有取证与入库发布的边界

**严重程度**　重要
**类别**　安全与性能
**位置**　设计稿第 40、49、67、81–83 行。benchmark `README.md:224-234`、`evaluation.py:260-282`、`bcode_results.py:10-25,74-93`；BU `browser_use/config.py:35-38`；`packages/dev-panel/docs/cli.md:53`。

**现象**　设计限制了入库内容，但没有指定 `report.json` 如何从私有记录生成可入库的数据。裁判的输入记录含细则和证据，输出中可能引用它们；异常和 stderr 也可能回显任务或请求信息。BU 1.0.6 预检附近会记录任务文本的开头。上游可选 Laminar 通道去掉图片后仍会上传文字轨迹。`nbdev artifact publish` 还会按页面引用收集文件、生成版本并提交，缺少发布前检查时会连带提交附件。

**为什么是问题**　只删 task 和 rubric 字段挡不住明文出现在 findings、错误、URL、截图、下载文件或 HTML 内嵌数据里。`.local` 与遥测开关解决的是不同风险，也不能证明外部网关的保留或转发符合本次数据授权。

**如何核实**　对照上游独立的 `public_result` 字段允许表、私有裁判记录与 nbdev 的文件收集规则。用合成敏感标记覆盖轨迹、文件名、异常、图片和 HTML 引用，检查最终待提交文件集合。

**建议改法**　可信侧保存分权限的私有证据，明确保留期、访问者和允许定向传给哪个模型。单向投影出公开 schema，仅含获准的题号、数值、状态枚举和非敏感版本标识。发布前检查 HTML、JSON、附件与实际提交集合，模板将输入当数据转义。钉住 BU 遥测关闭配置，关闭可继承的 tracing/Laminar，限必要外联。上线前核对中转的数据使用条件；原始记录和模型服务凭据不要进入 Git、通用目录或面板发布链。

### 13. 外接 Chrome 时，browser-use 的下载和浏览器收尾不再由原脚本负责

**严重程度**　重要
**类别**　不变量
**位置**　设计稿第 48–50、60、87 行。BU `browser_use/browser/browser.py:613-647,717-730,917-945,1030-1055,1087-1116`、`agent/service.py:514-528,571-587,652-655,663-682`。

**现象**　1.0.6 能用 `Browser(cdp_url=…)` 连接评测启动的 Chrome。它起自己的 daemon，不持有该 Chrome 的本地进程。仅由 BU 启动的本地 Chrome 才走 `_send_downloads`。外接模式也不会注入同一套下载 helper，结束时 `result.downloads` 只枚举 workspace 下载目录里新出现的成品。评测若只搬用 t01 启动与关闭逻辑，会漏掉外接 Chrome 的真实下载或留下浏览器进程。

**为什么是问题**　有交付文件的 BU 题会把完整业务结果漏判成未交付。过早销毁 Chrome 或下载目录也会丢掉已开始的下载和终态证据。相反只调用 `Browser.stop()` 不能回收调度器启动的 Chrome；在并发取消后继续使用旧端点或目录会污染后续运行。

**如何核实**　比较 CDP 与自建 Chrome 分支的对象、下载配置条件、`result.downloads` 的构造与 `stop` 收口。验收包括自然结束、部分文件、重复文件名、运行中断、启动失败，逐项确认文件保全、CDP 端点退役以及-owned 进程退出。

**建议改法**　调度器唯一拥有 Chrome 与 profile，独立确认连接到本次实例，执行器分别拥有自己的 CDP/内核与 daemon。统一设置并验证本次下载目录和有界收取策略，区分浏览器下载与 Agent 自产文件。启动参数、viewport、DPR、时区与语言按实际值记录并校验，分配目录和端点后再发任务。正常或超时均按停止发起动作、采集终态和已完成文件、关闭执行连接、退出并回收所拥有进程的顺序收口，留有独立截止和部分证据标记。

### 14. 真站配对缺少同一可达性窗口和可核对的来源事实

**严重程度**　重要
**类别**　测试
**位置**　设计稿第 38–44、52–54、61 行。t01 调研「实测」第 82–111 行。benchmark `findings_judge.py:55-70,98-103`。

**现象**　稿用一次可达性探测筛 BU，再约定两边同一时段跑。中文真站的脚本另读也只约定同一时段。首页可打开不能证明所需页面与数据可达。t01 在本机无头 Chrome 观察到起点验证页、B 站打开搜索页时自动发约 32 个埋点 POST。独立脚本走另一入口、语言、地区、帐号或查询时间时，可能拿到不同排序或结果。并发 4 时，两边还可能共同耗掉同站或同网关的配额。

**为什么是问题**　同一题先后出现登录墙、验证码、限流或数据更新，会把先后顺序计成系统差异；可靠读到公开数据的成绩也会和只报告阻断的成绩混在一起。按 HTTP 方法计越界会误记页面自动请求。基线单边先做、几周后才接插件时，首次真站结果不能当配对对照。

**如何核实**　对照既有 t01 记录和上游对访问阻断、正常完成与基建故障的区分。公开的 Online-Mind2Web 也记录过替换 36 个失效或遇验证码的题。本次未访问实际题目站点。参考 https://github.com/OSU-NLP-Group/Online-Mind2Web#update-tasks 。

**建议改法**　按题×模型安排紧邻的两边运行并平衡先后，按站点与网关限并发。用同一出口、语言和短时间窗，以独立只读探测核验必要路径，冻结来源、筛选/排序、时间与见到的事实。仅凭已约定的独立证据标记站点不可比，保留原尝试。把如实报阻断与取得数据分项计分。真站题先核对操作与数据授权，用任务语义及因果证据归类网络事件。正式里程碑于同一窗口重跑两边。

### 15. 固定 Profile 仍需核对实际工具集与无人值守的权限路径

**严重程度**　重要
**类别**　正确性
**位置**　设计稿第 50、53、89 行。`docs/specs/agent/contributions.md` 输出 4、24–25，`docs/specs/agent/permissions.md` 输出 1。`packages/neuro-book/src/plugins/agent/backend/agent.ts:245-269,320-333,536-547`、`backend/eval/tool.ts:424-434`。

**现象**　稿只指定「固定的评测 Profile」。NB 的 `browser` 须由插件声明对象，再由该会话的生效工具集选进至少一个方法，且有 `eval` 才能通过 CodeAct 调用。若沿用「主创」的一般工具集，还可能有 shell、提问、子代理等入口。工具绑定和权限规则在运行时参与解析，Profile 名称相同不能保证能力或权限相同。

**为什么是问题**　单纯装好插件可能得到没有 `browser` 的 NB 会话，或每次执行都停在无人的审批上。两种情况都会被误记成浏览器能力不足。反过来，额外的网页搜索、直接抓取、子代理模型等路径会把预算和完成率计到浏览器插件名下。BU 基线先做时发现不了这些接线缺口。

**如何核实**　追踪生效工具集、对象注入和执行档审批。Web 工具已有真实内核的场地范例 `packages/neuro-book/src/plugins/web-tools/agent.llm.test.ts`。接入前用合成任务与本地假模型核对实收工具声明和一条嵌套调用能够执行、产生证据并收口。

**建议改法**　显式定两边允许的能力和外联。NB 评测 Profile 声明必需的 eval、浏览器方法和交付工具，固定实际工具集、模型角色、模式与审批初值。隔离场地预先授权必要的合成任务动作；生产审批另测。意外进入等待、工具不存在、角色未绑或任务连接到错误的浏览器，记评测配置失败。第一阶段可先用合成工具贡献验证此合同，第三阶段接实际插件时重跑同一验收。

### 16. 应用内评测代码不会被现有 tsconfig 类型检查覆盖

**严重程度**　重要
**类别**　测试
**位置**　设计稿第 81、87–90 行。`packages/neuro-book/tsconfig.json:30-56`、`vitest.config.ts:16-34`、`bunfig.toml:1-5`、`package.json:11-24`、`scripts/pack-app.ts:286-291`。

**现象**　拟新增的 `packages/neuro-book/evals/browser/` 是 `.ts` 运行脚本，但应用 tsconfig 的显式 include 未覆盖 `evals/`，Vitest include 也不扫描它。Bun 配置只有 DOM 测试路径排除，通常 `test:bun` 会发现测试文件；不过普通 `typecheck` 不会检查评测执行器、运行器或其任务定义。

**为什么是问题**　浏览器基线虽不进入 npm 产物（这是正确方向），但声明的验证命令仍可能无声漏掉评测代码的类型回归。评测系统是开发器材，却直接负责判定业务数据与保存凭据，不应靠一次人工执行才发现类型或入口坏掉。

**如何核实**　对照 TS `include` 的显式范围、Vitest 的 `include`、包脚本与发布白名单。无需构建。工作区没有依赖且这次未跑类型检查。

**建议改法**　为评测 runner 添加独立的 `tsconfig` 和包内 focused 检查脚本，或将受控的 `evals/**/*.ts` 并入应用后端 typecheck；测试文件接入 Bun 的专门脚本并按改动文件跑。保持 `evals` 不进 `pack-app` 的文件白名单与服务端入口，避免把本地评测或任务明文发成产品包。

### 17. 快速集在 10 分钟硬时限下不能保证一小时内交结果

**严重程度**　重要
**类别**　正确性
**位置**　设计稿第 7、53、71、87 行。

**现象**　目标要求开发者改一版后 1 小时内发现退步。快速集写 8 题、仅 Luna，没有单独的快测时限或采样规则；若沿用每题 3 次、双边、并发 4，就是 48 次运行。按 t01 实测的 43 秒/次约 8.6 分钟；若一半题达到每次 10 分钟的硬截止，则约 60 分钟，全部达到则 120 分钟，尚未计启动、清理、核对与汇总。

**为什么是问题**　只报快速均值也不能保证区分真实退步与重复运行噪声。若为了限时而随意删掉超时或减少一边的重复，会造成选择偏差或失去配对。仅用 Luna 的快速集也不能侦测两个 Gemini 档位退步。

**如何核实**　以 8 题×2 边×3 次得 48 次，按并发 4 与 43 秒/600 秒两档计算，结果为 516/7,200 秒（8.6/120 分钟），上限是 10 分钟每次。首个数据只作运行耗时参考，不是快测时限的证明。

**建议改法**　把快测定义成固定配对集、固定重复数和不超过一小时的硬预算；先确定哪些模型与题目属于快速门禁，何种结果触发扩样/完整运行，以及运行逾时如何结成待判而不是抛弃。按试跑后的分位耗时预留调度和收尾预算。若全三模型都要在一小时内发现，增加并发与缩短每次硬时限需单独验证对真实模型稳定性的影响；若快速集只代表 Luna，声明其覆盖范围，完整三模型回归另立门禁。
