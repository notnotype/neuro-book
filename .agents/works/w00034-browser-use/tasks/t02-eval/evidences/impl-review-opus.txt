### 1. Chrome 崩溃永远归不到 harness-error：bwrap 把信号换成退出码 128+n，崩溃被算成执行者的 browser-lost 并计分
- **严重程度**：重要；**类别**：正确性
- **位置**：runner/chrome.ts:115（selfExit 交出 completion 的 exitCode 与 signal）；record/outcome.ts:47、52；record/outcome.test.ts:90
- **现象**：Chrome 在 bwrap 里跑，owned-process 的 completion 报的是 bwrap 这个直接子进程的终态。bwrap 自己总是正常退出，把子进程的信号换成 128+n。本机实测（bubblewrap 0.13.1，同样的 --unshare-pid --die-with-parent --new-session）：子进程被 SIGSEGV 结束时 bwrap 退出码 139，被 SIGKILL 结束时 137，signal 都是 null。所以 outcome.ts:47 的 `chromeExit.signal !== null` 在真实运行里不会成立；Chrome 崩溃或被 OOM killer 杀掉时，没交付的那回走到第 52 行记成 `executor-error / browser-lost`（计分，多半 0 分），交付了的照常 completed。outcome.test.ts:90 的用例直接喂 `{exitCode: null, signal: "SIGSEGV"}`，是真实运行里产生不了的输入，所以测试绿着。
- **为什么是问题**：结局表把“Chrome 被信号结束”定为不计分、重跑，是为了不把评测部件的故障记到执行者头上。本机 15 GB、并发 4 个 Chrome，加上机器上别的评测，OOM 杀进程并不罕见；这些回会作为 0 分进 browser-use 的基线，而且不重跑，直接拉低均分、放大方差（每题次数正是按这个方差算的）。
- **如何核实**：`bwrap --ro-bind / / --dev /dev --proc /proc --unshare-pid --die-with-parent --new-session -- /bin/sh -c 'kill -SEGV $$'; echo $?` 得 139。实机再补一条：起 Chrome 后在宿主上对沙箱里的 Chrome 主进程 `kill -SEGV`，看 selfExit() 交回的形状。
- **建议改法**：在 chrome.ts 里把 bwrap 的退出码还原：`exitCode > 128` 时交回 `signal = os.constants.signals` 里对应 n-128 的名字、exitCode 置 null（只有 Chrome 自己正常退出才是 0 到 127）；或者干脆把结局表的判据改成“退出码 0 归执行者，其它一律 harness-error”。测试改成在真 Chrome 上 kill 主进程得出的形状，而不是手写 signal。

### 2. 上游回 401、402、403、404、413 一律算执行者自己的失败：中转额度用完或单条消息超限时，后面的格全成计分的 0 分，止损线也不触发
- **严重程度**：重要；**类别**：正确性
- **位置**：record/outcome.ts:35-37（upstreamFailures 只认非数字与 >= 500）、51；runner/schedule.ts:268（计分即 settled，不重跑）；runner/schedule.ts:297（止损只看 token）
- **现象**：网关把上游的 4xx 原样记成数字状态码。outcome.ts 只把 5xx 与连接类失败算上游失败，所以 401（密钥失效）、402/403（`billing_error`、`insufficient_user_quota`）、404（中转下架了模型）、413（中转的单条消息上限）都会让 browser-use 以 `status: error` 结束（1.0.6 loop.py:1287 的 explain_error 专门处理 gateway 401/402/403/404），再被归成 `executor-error`、计分、settled、不重跑。这些回几乎不花 token，`--max-total-input-tokens` 的止损线永远不触发，批次会把剩下所有格都以 0 分跑完。
- **为什么是问题**：这些都是评测基础设施的故障，不是执行者的表现；照现在的归类它们会静默地进入 browser-use 的基线与每题方差。额度用完是这台机器上实际出现过的情况（omp 的提供方 403 `insufficient_user_quota`）；luna 中转的单条消息有约 70 到 80 KB 的上限（超了回 413），而 browser-use 每步都把截图以 base64 放进消息，一张 1280x900 的截图就可能逼近这个量级，见第 3 条要实机补的证据。
- **如何核实**：在 gateway.test.ts 的假上游上让它回 403 `{"error":{"type":"insufficient_user_quota"}}`，把网关记录与 `{executor: {status: "error"}}` 交给 classifyOutcome，得到 `executor-error`。实机：看试飞运行目录里 gateway[] 的 upstream 有没有 413。
- **建议改法**：把“上游拒收”单独成一类：upstream 为 401、402、403、404、413 时（不管执行者是否交付）记 `infra-error` 或新的 `upstream-rejected`，不计分；对 401、402、403 再加一条全批熔断：网关一旦记到就让 runPool 不再派新格（和止损共用 stoppedByBudget 那条路，改名为 stopped 并带原因）。400 仍归执行者（请求体是执行者造的），但要单列计数。

（第 2 条补记：主工作区 runs/pilot-1、smoke-1、probe-1 现有 10 回的 gateway[] 全是 200，没见到 413；413 是要试飞时留意的风险，不是已经发生的。第 2 条里“见第 3 条”作废。）

### 3. timeout 与 max_steps 的回答在运行记录里丢了：run.py 只取 final_result()，partial 与 success 没进 record.json，判分读不到
- **严重程度**：重要；**类别**：正确性 / 对照需求
- **位置**：arms/browser-use/run.py:110-112；runner/schedule.ts:240（result 只拷 finalAnswer、deliverables）；record/schema.ts:132-138（result 没有 partial 字段）；judge/rules.ts:79
- **现象**：browser-use 1.0.6 的 `final_result()` 在 status 不是 completed 时交回 None（views.py:130）；它在 timeout、max_steps 时把 partial 或最后一段模型文字放进 `result.text`（loop.py:1316-1318 的回退），run.py 没取 `text`。run.py 另把 `partial` 写进 executor.json，但调度器拼记录时没拷 `partial`，也没拷 `success`，schema 里也没有这两个字段。结果是：这两种结局下 `finalAnswer` 恒为 null，parseAnswer 交回 null，所有回答类条目（author-income 的 100 分、reader-* 的 100 分、forum-verify 的 80 分）一律不满足。
- **为什么是问题**：计划的结局表写的是“timeout、max_steps（什么都没交付，读 partial）| 照判分”，现在没有读；而且 partial 与 success 也是以后与 NeuroBook 一边配对时要对照的事实，记录里一旦没有就补不回来（executor.json 还在，但报表与判分只读 record.json）。`success: false` 的强制交付也分不出来，报表里没法区分“自认完成”与“到点硬交”。
- **如何核实**：读代码即可：`grep -n partial evals/browser/record/schema.ts evals/browser/runner/schedule.ts evals/browser/judge/rules.ts` 没有命中。实机：试飞里挑一回把 timeLimitSec 改成 20 秒，看 record.json 的 finalAnswer。
- **建议改法**：run.py 的 finalAnswer 改取 `result.text`（completed 时与 final_result() 相同，非 completed 时就是 browser-use 自己的回退），另把 `success` 与 `partial` 进 record.result；rules.ts 不用改。结局表里写明 timeout 的回答来自回退文字。

### 5. 改了判分或题以后，续跑与报表都不认 taskVersion：旧分照旧计、新旧版本混在同一个均分里
- **严重程度**：重要；**类别**：正确性 / 不变量
- **位置**：record/store.ts:72-86（attemptState 只看最后一回 score.json 的结局）；report/report.ts:111-125、131-135（countedRuns、taskScores 直接用 score.json 的分数，不按版本分组）、306-316（只把版本列出来）；tasks/types.ts:4、55-57
- **现象**：types.ts 的注释承诺“改了题就把 revision 加 1，taskVersion 跟着变，旧运行不再与新的放在一起算”，但全目录里读 taskVersion 的只有报表的“列出版本”一处：(a) 续跑时 attemptState 不比对版本，已 settled 的旧版格直接跳过，新版只补没跑的格；(b) 报表从 score.json 取分，不按当前代码重判，也不按 taskVersion 分开，同一题两个版本的分数进同一个 TaskScores；(c) taskVersion 的哈希只含条目的 id 与权重，不含 check 的逻辑、站点的种子数据生成与页面，所以只改判分逻辑（第 7 片“逐题人工核分，修判分”正是要做这件事）时版本号根本不变，旧的 score.json 照旧被读。

### 6. “有过一次上游失败且没交付就重跑”会挑着重跑失败的回，把均分往上推，而且偏差随一边的请求数变
- **严重程度**：重要；**类别**：正确性（统计口径）
- **位置**：record/outcome.ts:49-51；runner/schedule.ts:268-269
- **现象**：classifyOutcome 只要本回网关里出现过一次 5xx、超时或断开，且执行者最后没有 completed，就记 infra-error、不计分、重跑。它不看那次失败与结局有没有关系：第 3 步遇到一次 502、openai 客户端自己重试成功，后面第 40 步因为卡住到了 max_steps 或执行出错，这一回也被丢掉重跑；而同样碰到过 502 但最后交付了的回照常计分。
- **为什么是问题**：这是对失败回的有选择的重跑。设每回成功率 s、每回碰到至少一次上游失败的概率 f（相互独立），计分回里的成功率变成 s / (s + (1−s)(1−f))。s = 0.5、f = 0.2 时是 0.556，均分虚高约 5.6 分，正好是判据的容差 5 分；s = 0.3、f = 0.3 时 0.38，虚高 8 分。f 随每回的请求数增长，以后 NeuroBook 一边若请求数与 browser-use 不同，两边的偏差不同，配对差直接被这条规则带偏；全同分题与每题次数的估算也一起偏。现有 10 回实跑没见到上游失败，但两个 Gemini 经中转，计划自己也把 524 列为风险。
- **如何核实**：outcome.test.ts 加一条：gatewayCalls `[call(502), call(200), call(200)]`、executor `{status: "max_steps"}`，现在得 infra-error。统计偏差按上面的式子手算即可。
- **建议改法**：只在失败与结局有因果时才归 infra-error：本回的最后一次网关调用是上游失败（或最后一次成功调用之后再没有成功的调用），且执行者以 error 或 timeout 结束；之前被执行者自己重试掉的失败只计数、照常计分。max_steps 本来就是执行者自己的结局，不该进这一支（计划的结局表只写了“出错或超时”）。报表里另列“碰到过上游失败的计分回”的数量。

### 7. runTry（一回运行的起停、收尾与结局取证）没有任何测试；ready 之前的一段不在 try 里，抛错时 Chrome、假站与假密钥都不收

### 9. 试飞 24 回全是 100 分：这 8 题对 browser-use 顶格，按现在的公式，每题次数的建议与“接近”判据都会退化
- **严重程度**：重要；**类别**：正确性（统计口径，需开发者定）
- **位置**：主工作区 runs/pilot-1 的 24 个 score.json；report/stats.ts:124-128、158-173；report/stats.ts:80-122（百分位重抽样）
- **现象**：pilot-1 里 8 题 × 3 模型各 1 回，score 全部 100、rawScore 全部 100、没有清零、结局全是 completed（审查时读到的状态）。把同样的形状（8 题、每题 5 次全 100）交给 repeatAdvice（scratch/repeats.test.ts）：“方差记 0”给每题 1 次；推荐的“保守下界 + 功效法”给 T8 每题 96 次、T24 每题 32 次（σ̄² = 1224，即把每题当成 q = 1/7 的 0/100 分）。只要 8 题里有 1 题 5 次中错 1 次，保守功效法给 104 次，单边区间就成了 [92.5, 100]。
- **为什么是问题**：决定 5 要用第一阶段量出的波动定每题次数，但顶格的数据量不出波动：两种算法相差两个数量级，推荐的那个不可执行。判据这边，browser-use 全 100 的题在题内重抽样下宽度为 0，NeuroBook 一边在 40 回里只要错 1 回，配对差的下界就约 −7.5，判据不过；这是判据在天花板上的性质，不是两边水平的差别。第 8 片的 120 回正式运行若照计划跑，多半只得到更多的 100。
- **如何核实**：`jq .score runs/pilot-1/*/*/browser-use/a1/try-1/score.json`；`cd packages/neuro-book && bun test <scratch>/repeats.test.ts`。
- **建议改法**：这是要开发者拍板的口径问题，主会话带着数字去问：(a) 正式运行前先加难度（同一批 8 题收紧时限、加干扰、或先做第 2 阶段的几题有余量的），让 browser-use 的均分落在 30 到 80 之间；(b) 或者对全同分的题不用 q = 1/(n+2) 的保守方差，改用有波动的题的合并方差，并在报表里写明“顶格题不提供区分度”；(c) 判据改为只在 browser-use 未顶格的题上算配对差，顶格题单列“两边都满分的比例”。不改的话，至少在报表里给出“顶格题数”与两种次数算法的差距，别只给推荐值。

### 10. 网关的三处小漏：假密钥不绑模型；执行者断开后上游照跑最多 600 秒；收尾时在途的那次请求不进记录与止损

- **位置**：runner/gateway.ts:115-116（按请求体的 model 找路由）、129-136（上游 fetch 不带 request.signal）、125-127 与 221（record 推进 entry，calls() 取快照）；runner/schedule.ts:222-224

- **为什么是问题**：(a) 让“每回一个模型”的前提只靠执行者自觉，模型写的代码改了 model 也查不出来（报表不看 gateway[].model 是否与 identity.model 一致）；(b)(c) 每回多花一次请求的钱且不入账，兜底结束的回最明显。

### 12. 题内百分位重抽样在每题 5 次时把区间收窄约 11%，与按样本方差算的每题次数不是同一个口径
- **严重程度**：建议；**类别**：正确性（统计口径）
- **位置**：report/stats.ts:80-122（bootstrapMean、bootstrapPairedDiff）；report/stats.ts:71、135-137（样本方差除以 n−1）
- **现象**：对 n 次运行有放回重抽样，重抽均值的方差是 σ̂²(n−1)/n² ，即用的是除以 n 的方差；repeatsNeeded 按除以 n−1 的样本方差算“下界不低于 −5 所需的次数”。n = 5 时百分位区间的半宽比正态口径小 sqrt(4/5) ≈ 0.894，n = 3 时 0.816。
- **为什么是问题**：按公式定出的次数跑完，实际报出的区间比公式假设的窄 11%（5 次）到 18%（3 次），判据更容易判“达到”，方向对我们一边有利；第 9 条的天花板情形下更明显（全同分题的重抽宽度恒为 0）。
- **如何核实**：一题 5 次 [0, 100, 100, 100, 100]，重抽 10 万次的均值标准差约 35.8 而样本口径是 sqrt(2000/5) = 20 乘 sqrt(5/4)，可在 scratch 里用 bootstrapMean 与手算对一下。
- **建议改法**：二选一并写进 stats.ts 的注释：(a) 重抽样后对每题的偏差做 sqrt(n/(n−1)) 的放大（等价于对每题残差做 rescale 后再抽）；(b) 直接用正态口径算区间 `mean ± 1.96 × sqrt(Σ(s²_o/r_o + s²_b/r_b))/T`，与 repeatsNeeded 同一个式子，重抽样只作对照。

（第 12 条“如何核实”更正：那句数字写错了，作废。正确的是：[0, 100, 100, 100, 100] 的样本口径均值标准差 sqrt(2000/5) = 20，重抽样口径 sqrt(1600/5) ≈ 17.9，比值 0.894。单题的百分位区间受离散值影响（scratch/bootsd.test.ts 得 [40, 100]，正态口径 [40.8, 119.2]），要在 8 题都有波动的合成数据上比半宽才看得出系统性收窄；这一条的结论来自方差公式，没有做大样本实验，标为“从推导”。）

### 14. 同一个 --out 上没有互斥：两个 run 同时续跑会抢同一个 try-n 目录
- **严重程度**：建议；**类别**：不变量

- **建议改法**：二选一：在 Task 记录的实施偏离里写明“推理档写死 medium，probe 只核对不回退”，删掉计划里的 probe.json；或者照计划把 probe 的那几行写进 `<out>/probe.json`，run 起手时若同一 out 下有 probe.json 就核对 MODELS 的 reasoning 与之一致。

## 未发现问题的方面

- 密钥：主工作区 runs/ 下 pilot-1、smoke-1、probe-1 全部文件里没有 `sk-` 串，也没有 /home 路径；job.json 只有假密钥。env.ts 的报错只写键名与路径；网关转发失败只记分类，不带上游的错误文字或代理地址。
- 代理：评测进程里有代理变量就拒绝启动；luna 路由不带 proxy，Gemini 路由显式带；Chrome 有 --no-proxy-server，执行者与 Chrome 的环境都从空开始。
- 沙箱：同参数的 bwrap 里 .env、~/.omp、主工作区 .local、用户总线、docker.sock 都不可见；--dev 只给基本设备节点，所以 disk 组的身份碰不到块设备；X11 与 ICE 的抽象套接字连得上，但被认证挡住（xdpyinfo 报 Authorization required）。
- 网关：只绑 127.0.0.1，没登记的密钥回 401；回给执行者时去掉编码与长度头；gateway[] 的总输入与 browser-use 自报一致（试飞 25 回逐回相等）。
- 假站：各写接口对坏 JSON、数组、基本类型的请求体都回 4xx，没有能让执行者把一回变成 harness-error 的入口；状态不经 HTTP 暴露；试飞里流程题都是经页面拿的凭据。
- 统计：半宽法与功效法的公式、保守方差 100²·q(1−q) 与计划一致；重抽样的种子固定、各题等权。
- 运行快测：`bun test evals/browser` 100 过、11 跳过、0 失败（HEAD 8907cab89）。`bun run typecheck` 在负载约 7 时 900 秒内没跑完、被 timeout 截停，没有结论，留给主 Agent 跑。
- 实验都在 scratch/ 下（verify-edges、repeats、bootsd 三个 .test.ts），worktree 没有改动（git status 为空）。
