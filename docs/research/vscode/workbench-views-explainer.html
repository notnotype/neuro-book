VS Code 的 Workbench / View 模型

讲解「Part / View Container / View / Grid」这一套是怎么划分与渲染的，以及 NeuroBook 那张页面该怎么用它。 证据标注：文档已验证 出自仓库先行调查 docs/research/vscode/03-workbench-layout-views.md（固定 commit 核对）； 源码记忆 是我的补充，未在该文档核对；未验证 指调研明确列为未验证的部分。

1. 一句话模型

VS Code 的界面不是一棵「谁都能往里塞组件」的 DOM 树，而是四层各管一段的状态：

Part 管区域 → View Container 管一组视图 → View 管自己可见性与内容 → Editor Part 管编辑器的二维分屏。

四层的合法目标、持久化键和恢复边界都不同。所以你拖一个视图、移动整个面板、拆分编辑器，是三件事，走三条不同的路径。

2. grid 到底是不是树

是树，而且「grid」这个名字只表示「方向可以嵌套」。上一轮我说「二维网格、每个格子放一个 Part」是简化过头了，容易让人以为是平铺表。

GridRoot（分支：horizontal） ├── ActivityBar ← 叶子：一个 Part ├── Sidebar ← 叶子：一个 Part ├── Branch（vertical） ← 分支：再切一刀，方向不同 │ ├── EditorPart ← 叶子；它内部还有一棵自己的树 │ └── Panel ← 叶子 ├── AuxiliaryBar ← 叶子（右侧辅助栏） └── StatusBar ← 叶子 兄弟之间自动插入 Sash（可拖分隔条）；拖动改的是「分支节点的尺寸分配」，不是组件内部状态。

它装什么、不装什么

在 grid 里不在 grid 里
宿主能识别的节点：Part、Editor Group、占位（Placeholder） 文档已验证 任意 Vue/React 组件实例、视图内容、第三方 DOM 文档已验证：SerializableGrid 只保存宿主能识别的节点

两棵树 + 一个一维容器

  • 外部一棵树：Workbench 的 grid 装 8 个 Part 里的可见者。
  • 里面还有一棵树：EDITOR_PART 自己维护 SerializableGrid<IEditorGroupView> 装编辑器分组 文档已验证。
  • 容器内部不是 grid：侧栏/面板里多个视图是一维 split view 排列（同一容器只需要一个方向）。这也是为什么「同容器排序」和「跨容器移动」是两套状态。

3. 概念清单

概念是什么声明 / 运行时它拥有什么状态存哪
Contribution贡献声明（扩展 package.json 或内置注册）声明容器、视图、命令、菜单项的来源—
ViewContainerDescriptor一组视图的容器：id / title / icon / order / 默认位置声明容器的身份与默认归属—
ViewDescriptor单个视图的能力：id / name / icon / when / order / canMoveView / canToggleVisibility / factory声明身份、可见条件、可动性、工厂—
ViewsRegistry / ViewContainerRegistry登记上面两者的注册表声明层单例可枚举、可校验、可被追加—
PartWorkbench 的大区域，共 8 个枚举值（下方区域图）运行时区域几何、可见性、位置LayoutSettings / storage 文档已验证
ViewContainer（运行时）Part 里被打开的那一组视图（活动栏图标点开的那个）运行时容器级状态、标题与工具栏容器级状态
ViewContainerModel每个容器一个，管同容器内的事运行时视图的可见 / 顺序 / 折叠 / 尺寸容器 model 文档已验证
ViewDescriptorService跨容器位置的权威运行时用户挪过之后的实际位置（与默认位置分开）views.customizations 文档已验证
PaneView单个视图在一维 split view 里的可布局实现运行时自己的最小/最大尺寸、折叠、可见性容器 model
EditorPart + Editor Group/Grid编辑器的二维分屏运行时文件、分组、标签、脏状态editorpart.state 文档已验证
Command / MenuRegistry动作与其出现位置声明 + 运行时菜单、工具栏、上下文菜单项（配 when）—
ContextKeyService + when可见性/启用条件的求值器运行时上下文键 → 表达式结果—
最容易搞混的一条：View 不是 Part。View 是被容器装载的一项描述；Part 是区域，自己拥有几何。把 View 当成「一个可以随便塞的插槽」，后面所有设计都会歪。

4. 它们之间的关系

① 声明层（可枚举、可校验、可被追加）
Contribution→ViewContainerDescriptor→ViewDescriptor（when / factory / 可动性）
ViewContainerRegistryViewsRegistry
▼ 合并 + 用 when 求值（谁能出现、谁该隐藏）
② 运行时（宿主拥有，可恢复）
Layout→SerializableGrid { Part, EditorGroup, 占位 }
Part（SIDEBAR / PANEL / AUXILIARYBAR）→ViewContainer→ViewContainerModel→PaneView（每个可见视图一个）
跨容器位置 →ViewDescriptorService｜编辑器 →EditorPart → SerializableGrid<EditorGroup>
▼ 动作与显示
③ 状态（各存各的键）
Part 可见性/位置/尺寸 → LayoutSettings视图自定义位置 → views.customizations编辑器分组 → editorpart.state视图自身 UI → 每个视图的 memento领域数据 → 各自 authority

四条分界规则

  1. 三种拖动 = 三种意图 文档已验证：拖 View 回 View model；移动整个 Panel 回 Layout/Part；拆分编辑器回 EditorPart。
  2. 默认位置 ≠ 实际位置：descriptor/容器写的是默认，用户挪过之后实际位置由 ViewDescriptorService 记录，两者分开存、分开迁移。
  3. 可见性 ≠ 权限：when 只管显示，执行仍走命令与原 authority。
  4. grid 与注册表都只认宿主认识的节点/描述符：组件实例永远不进去——这就是「能声明 View，但不能改主布局」的实现方式。

6. 三种拖动 = 三种意图

你做的动作宿主收到的意图谁处理存到哪
把一个视图拖到另一个容器 / 另一侧viewId + 目标容器 + 目标位置ViewDescriptorService（跨容器）与容器 model（同容器顺序）views.customizations
把整个 Panel 移到右侧 / 隐藏侧栏Part 位置 / 可见性Layout / Part 服务LayoutSettings
把编辑器拆成两栏新建 Editor GroupEditorParteditorpart.state

所以「拖了一个面板，结果整个编辑器重排了」在正确分层下不会发生——三个动作碰的是三份互不相干的状态。

7. 生命周期

注册 descriptor→ when 求值→ 首次可见才实例化（懒）→ 隐藏不销毁（保活）→ 跨容器移动（descriptor 不变，只改归属）→ dispose（自身 UI 状态经 memento 留下）

源码记忆「首次可见才实例化、隐藏不销毁」这一条不在你们的调研文档里；还有一条相关机制：onView: 激活事件——某个视图第一次被打开可以触发扩展激活，扩展再把视图注册进来，所以注册允许迟到、允许异步，第一方与第三方走同一条路。

8. 声明长什么样

扩展侧：package.json 贡献

{
  "contributes": {
    "viewsContainers": {
      "activitybar": [{
        "id": "my-container",
        "title": "我的容器",
        "icon": "media/icon.svg"
      }]
    },
    "views": {
      "my-container": [{
        "id": "my-view",
        "name": "我的视图",
        "when": "workspaceHasPackageJSON"
      }]
    }
  }
}

注意：容器没有 when（不能按上下文整条隐藏），视图才有。
官方文档：contribution points、UX guidelines: views。

内部侧：描述符注册（等价字段）

viewsRegistry.registerViews([{
    id: "workbench.view.explorer",
    name: "资源管理器",
    containerTitle: "资源管理器",
    icon: Codicon.files,
    when: ContextKeyExpr.equals("workbenchState", "folder"),
    canToggleVisibility: true,   // 用户能否隐藏
    canMoveView: false,          // 能否拖到别的容器（默认关）
    order: 1,
    ctorDescriptor: new SyncDescriptor(FileExplorerView),
}], container)

第一方与第三方最终走同一张注册表——这正是 #192 想学的核心：宿主渲染的是数据，不是写死的槽位。

9. 映射到 NeuroBook

你那张页面上的东西在这套模型里现状
左侧图标栏（文件 / 角色 / 情节 / 世界 / 记录 / 历史 / Agent）ACTIVITYBAR_PART：图标 = 容器的入口写死的 capability 列表（app/utils/workbench-chrome.ts:12-26），不是注册表派生
文件树 / 大纲 / 世界书区SIDEBAR_PART → View Container → View（每张可折叠面板）固定槽位
中间 Markdown StudioEDITOR_PART（不是 View）固定槽位，单编辑器
右侧 Agent 面板 + 底部输入AUXILIARYBAR_PART：同一个 Part 类、不同位置独立实现——最值得改的一点
底部（目前没有）PANEL_PART无
顶部自绘 36px chromeTITLEBAR_PART（+ BANNER_PART 通知横幅）已有
设置窗口里的左栏 + 区段一个容器 + 手写 descriptor 列表最接近这套模型的现有实现：元数据驱动 + 受控插槽 + 宿主持有 I/O + fill/scroll 布局合同

从零渲染那张页面的七步

  1. 建静态骨架：一个树形布局，先放 6 个区域 + sash，尺寸写死；
  2. 建注册表：第一方 descriptor 表（id / title / icon / container / layout / when / order / canMoveView / canToggleVisibility / factoryKey）——这就是「从写死到数据驱动」的分界；
  3. 建 context 求值器：结构化谓词 + 依赖跟踪（可见性 ≠ 权限）；
  4. 造容器 UI：活动栏图标 + 容器内容区；
  5. 懒造视图：只为首次可见的 descriptor 造组件（现有 Vue 组件直接当内容，不用改）；
  6. 接命令/菜单：「打开视图」「隐藏视图」「移到辅助侧栏」都是命令，改的是位置服务的状态；
  7. 接状态与迁移：布局分用户级 / Project 级；视图自身 UI 按视图 id 存；领域数据仍走 Project 文件 / Session / Job 的现有 authority。
现状差距（决定工作量）：活动栏不是注册表派生的；侧栏/右栏/编辑器是固定槽位；布局状态三层混着（novel.ide.local 用户级、novel.ide.session 按 Project 分区、组件内 ref）；没有 when 求值器，也没有懒实例化 / 保活 / 失败隔离。

11. 一页速查

  • grid = 嵌套树，叶子是 Part / Editor Group / 占位；不装组件实例。
  • Part 管区域（几何、可见性、位置）；容器管一组视图；View 管自己；编辑器自己一套分屏。
  • 同容器顺序归容器 model；跨容器位置归位置服务；两者分开存。
  • 默认位置（声明）≠ 实际位置（用户移动的结果）。
  • 容器没有 when，视图才有；可见性不是权限。
  • 懒建 + 保活 + 失败隔离：注册允许迟到，一个视图坏了不拖垮工作台。
  • 状态三层：布局（Profile/Workspace）/ 视图自身 UI（per-view memento）/ 领域数据（原 authority）。
