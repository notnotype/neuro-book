一个 UI 不是一棵 DOM 树

它是**四层不同 owner 的对象**：区域（Part）、容器（View Container）、视图（View）、编辑器分屏（Editor Group/Grid）。 拖动 View、移动整个 Panel、拆分编辑器，是三种不同意图，回到三个不同的 owner。 这一页把 VS Code 的这套模型拆开画给你看——同时也说明我们自己的页面该怎么落进去。

① 屏幕上的每一块，先归到一个 Part

点任意区域：右边显示它是哪个 Part、是否直接装 View、状态存在哪。切换下面两个标签可对比「VS Code」与「NeuroBook 现在」。

点一个区域

左侧每个色块都是一个 Part（或 Part 里的一层）。Part 拥有**区域几何与可见性**，它本身不是 View。

八个 Part（VS Code 的固定词表）

Part人话直接装 View？典型模型
TITLEBAR_PART标题栏 / 命令中心否原生或自绘 chrome
BANNER_PART顶部通知横幅否Workbench Part
ACTIVITYBAR_PART左/右侧图标栏间接打开 Composite / Container
SIDEBAR_PART主侧栏是，承载 View ContainerPart + Pane 容器
PANEL_PART底部（可移动）面板是Part + Pane 容器
AUXILIARYBAR_PART次级侧栏 / 右侧辅助区是与 SIDEBAR 同型、不同位置
EDITOR_PART编辑器区域否，内部是 Editor GroupEditorPart + Grid
STATUSBAR_PART底部状态栏否左右两条 item 注册表
对 NeuroBook 的直接结论：右侧那个 Agent 面板属于 AUXILIARYBAR_PART—— 它不该是第二套实现；底部若要加终端/输出，是 PANEL_PART，与侧栏同型。

② grid 是树，不是表格

点节点看类型；按「换方向」看父子如何嵌套。叶子是宿主认识的节点，分支只有方向。拖动 sash 改的是**分支上的尺寸**，不是组件内部。

grid 里装什么

装
宿主能识别的节点：Part、Editor Group、占位（拖拽时的落点）
不装
任意组件实例。视图内容永远不在 grid 里——这是「插件能声明 View、但不能改主布局」的实现方式
两棵树
Workbench 外层一棵装 Part；EDITOR_PART 内部再一棵装 Editor Group，同一套抽象用在两层
容器内部
不是 grid：侧栏/面板里多个视图是一维 split view（同方向不需要树）
我上一版说错的地方：我曾说「二维网格、每格放一个 Part」——那是过度简化。 真实结构是嵌套的分割树：grid 这个名字指的是「方向可以嵌套」，不是一张二维数组。

③ 概念清单：谁声明、谁在运行时拥有

点卡片看它属于哪一层、拥有什么、状态落在哪。左边是声明层（可枚举、可校验、可被追加），右边是运行时（宿主拥有、可恢复）。

点一张卡片

声明层与运行时的分工是这套模型的地基：descriptor 描述能力，运行时对象持有状态。两者之间隔着注册表与 when 求值。

它们的关系

声明层（可枚举 / 可校验 / 可被追加）
  Contribution ──▶ ViewContainerDescriptor ──▶ ViewDescriptor(when / order / canMove / canToggle / factory)
                        │                              │
                 ViewContainerRegistry            ViewsRegistry
                        └────────────┬─────────────────┘
                                     ▼ 合并 + when 求值
运行时（宿主拥有，可恢复）
  Layout ──▶ SerializableGrid{ Part, EditorGroup, 占位 }        ← 只认宿主认识的节点
    Part(SIDEBAR | PANEL | AUXILIARYBAR)
        └──▶ ViewContainer ──▶ ViewContainerModel（同容器：可见 / 顺序 / 折叠 / 尺寸）
                                     └──▶ PaneView（每个可见视图一个；懒建、隐藏不销毁）
    跨容器位置 ──▶ ViewDescriptorService（用户移动的结果，与默认位置分开存）
    编辑器      ──▶ EditorPart ──▶ SerializableGrid<IEditorGroupView>（另一棵树）

状态层（各有各的键）
  Part 可见性/位置/尺寸 → LayoutSettings/storage ；视图自定义位置 → views.customizations ；
  Editor Group → editorpart.state ；视图自身 UI → 每个视图的 memento ；领域数据 → 各自 authority
两条最容易搞混的区分
  • descriptor（声明） vs PaneView（运行时）：描述符可以枚举、可以在没被打开时也存在；PaneView 只在第一次可见时创建。
  • 默认位置（写在 descriptor / 容器上）vs 实际位置（用户挪过之后记在 ViewDescriptorService 里）。两者分开存、分开迁移。

④ 一个视图的一生

按「下一步」走一遍：注册 → 求值 → 懒建 → 保活 → 移动 → 释放。打开「错误注入」看失败隔离。

① 注册

descriptor 进注册表。此刻没有任何组件被创建——包括那些最终会显示出来的。

⑤ 三种拖动 = 三种意图 = 三个 owner

点一个意图，看它改变谁的状态、又不碰谁。

混在一起的代价：把「拖 View」当「移动 Panel」处理，就会出现「拖个面板，整个编辑器跟着重排」。 Panel 的位置与对齐还有自己的两个词表：Position（left/right/bottom/top）与 PanelAlignment（left/center/right/justify）。

⑥ 状态存在五个不同的地方

点一条看它的作用域与恢复合同。

状态归谁落在哪恢复合同
Part 可见性 / 位置 / 尺寸Layout / Part servicestorage（profile / workspace 分层）+ LayoutSettings启动时先恢复外壳，再恢复内容
视图与容器的自定义位置ViewDescriptorServiceviews.customizations与默认位置分开；删除自定义即回落默认
编辑器分组与分屏EditorParteditorpart.state只恢复分组结构；文件内容走编辑器自己的 dirty/flush
单个视图自身 UI（展开项、筛选）该视图每个视图的 memento按视图 id + 作用域；视图被释放后仍在
领域数据（文件、会话、任务）原 authority各自真相源不进布局状态；视图只是投影

点一条状态

把布局状态和领域数据混在一起，就会出现「重开窗口后布局对了、数据串了」这类问题。

⑦ 映射到我们自己的页面

直观对照：现在哪些是「固定槽位」，套上模型后应该变成什么。

差距清单

  • 活动栏是**写死的 capability 列表**（app/utils/workbench-chrome.ts:12-26），不是注册表派生
  • 侧栏 / 右栏 / 编辑器是**固定槽位**；右栏 Agent 面板独立实现（应属 AUXILIARYBAR_PART）
  • 布局状态三层混着：novel.ide.local（用户级）、novel.ide.session（按 Project 分区）、组件内 ref（session）
  • 没有 when 求值器，也没有「懒实例化 + 保持存活 + 失败隔离」

已有的参照物

刚完成的设置外壳就是这套模型在**单容器、手写注册表**下的特例：元数据驱动 + 受控插槽 + 宿主持有 I/O + fill/scroll 布局合同 + 单一加载态。它缺的正是 location/container、factory 绑定与 descriptor 级错误——也就是「一个外壳」到「一个 View Registry」之间的距离。

探针该先证什么

不是「能不能拖动」，而是：注册表 + when 求值器 + 懒实例化能不能在不碰现有 authority 的前提下接上去。 上一版探针没做到这一点，所以它只是个手写的容器列表。
