# 作者视角的世界引擎内核（第一版）

本稿整理 w00039 t02 在 2026-10-31 到 11-02 的讨论。开发者的决定逐条列在 [Work README 的决定表](../../.agents/works/w00039-novel-writing-plugins/README.md#决定)，本稿的“决策记录”照抄；其余是主会话的方案，供审查与开发者确认。

第二版（2026-11-02）按第一轮深入设计审查修订，第三版、第四版（同日）分别按第二轮、第三轮修订；第四版由开发者接受，长期决定写在 [ADR 0037](../adr/0037-world-engine-story-change-log.md) 与 [ADR 0038](../adr/0038-world-engine-entry-text-is-whitelisted-mdx.md)。各轮的报告、归并与逐条处理都在 [t02](../../.agents/works/w00039-novel-writing-plugins/tasks/t02-story-model/README.md) 的证据里（第一轮 `design-review-consolidated.txt`、`design-review-round1-resolution.txt`，第二轮 `design-review-r2-resolution.txt`，第三轮 `design-review-r3-resolution.txt`）。

本稿只定**模型**：条目、剧情变更、状态、修订、Component、渲染，以及作者和 Agent 怎么用它。存储、界面布局、具体的 Component 字段不在这里定。名字没定（待定项 1），下文暂称“世界引擎”。

## 一、问题

**作者这边：**

1. 旧版的设定与人物只能靠文件管理，用户反馈太复杂。旧版有一个人物表单，字段写死在 745 行的组件里（`packages/neuro-book-legacy/app/components/novel-ide/workspace/WorkspaceCharacterDetailPanel.vue`）。
2. 设定会随剧情变：剧情推进、补充、补漏、改主意。旧 lorebook 被当成不变的设定集，写到后面就过时，作者要在一份份文件里手改，也分不清哪句话是“那时候”成立的。
3. 写完一章要“记账”：钱花了多少、谁加入了哪个组织、谁知道了什么。这是最累、最想交出去的一步，现在没有地方记。

**Agent 这边：**

1. 上下文有限，不能每次重读全书与全部设定，需要压缩过、能按章取的材料。
2. 状态要能核对。一章里的几笔账模型能算对（第一轮体验里，两个模型都算对了神典石 200 − 50 = 150），但几百章的累加、改了前面以后的重算，只能交给程序；靠模型重读文字得出的值，说不出来源。“谁知道什么”的混淆是 V9 评测的结论（[V9 小说记忆图](novel-memory-v9.md)，w00005 t34），属于第二版的知情。
3. 作者记不住全书，即使上下文无限，也需要整理好的视图（开发者 2026-11-01）。

**旧 WorldEngine 已经是事件溯源**，问题在别处（调研见 [仓库内的现状](../../.agents/works/w00039-novel-writing-plugins/research/2026-10-31-repo-survey.md) 的二、三、五节）：

- 只管世界状态；剧情在剧情工坊，是另一套数据，两边靠无外键的字符串 id 相连。
- 全库唯一的 bigint `instant` 加日历字符串，Agent 门槛高。
- 补写过去时，相对操作（`increment`、`append`）会断，报 `broken-relative`。
- 状态有两份真相源：人物文件说人物是无状态原型，人物模板却带 `state.md`。
- 没有分支，也没有回退。

**常见做法各缺一块**（备选方案的完整比较见第四部分第 11 节）：

| 做法 | 缺什么 |
|---|---|
| 一个文件夹，放设定和正文 | 只有原始材料，没有账；只有上下文无限才行 |
| 不可变的 lorebook（SillyTavern 式） | 世界一变就过时 |
| lorebook 加模板引擎 | 数从哪来、哪章改的说不清；只管得了数值 |
| lorebook 加按章追加的说明 | 只能补充，不能算数；某一章的样子要读的人自己把几段说明合起来 |

## 二、目标与非目标

**目标：**

1. 一个系统管设定、状态、剧情计划与情节：它们都是条目和剧情变更。
2. 作者只管说话、看和改。整理与记账由 Agent 做，默认生效，有问题才叫作者（开发者 2026-11-02）。
3. 任意一章开头或末尾时，每个条目是什么样，都能算出来；每一处变化都有描述和出处。
4. 每一次写入，不管是作者的还是 Agent 的，都在改动记录里留一条，可以逐条还原（开发者 2026-11-02）。
5. Agent 每一步要读的材料有上限，与书的长度无关。
6. 同一份数据，给作者看界面、给 Agent 读文字。作者能写视图，从而参与 Agent 的上下文。
7. 简单的条目零门槛：只有一段文字的条目也合法。

**验收时要量的：**

- 记账的漏记率与错记率：用样本书的前 5 章，对照人工答案（t26）；
- 作者每章要处理的待处理条数；
- 写手上下文的字数：第 5 章与第 100 章同一量级。

**第一版的非目标：**

- 关系、地图、知情与秘密三类 Component（开发者 2026-11-01：方向认可，第一版不做）。
- 世界线与回档，细到天和时段的故事时间（t04）。第一版的位置只精确到章，另加“前史”。
- 按某个角色的视角渲染（例如按他知道的合并马甲）。
- 第三方 Component 类型的文档与示例：第一版只发内置类型，但内置类型走的是第三方也能用的贡献点。
- 计算字段、历法、自由命名空间、状态快照缓存（第一轮审查 C：没有使用者，或没有证据说明需要）。
- 作者在界面里编辑主 MDX 的方式（开发者 2026-11-02：先不考虑前端渲染，以后另找办法）。
- 按任意历史版本重新渲染：第一版只承诺修订能还原（第四部分第 5 节）。
- CodeAct 式查询。
- 存储格式（t09）、改稿后的自动重新记账（t22）、模板新建与旧项目迁移（t12）。
- 与 nb-story 合并：先做作者这边，再看能不能统一。

## 三、当前行为与证据

- **新应用**：
  - 新建作品只建目录和 `.nbook/project.json`，没有设定与剧情模型（[`runtime/projects.md`](../specs/runtime/projects.md)）。
  - 三类文件夹已实现，活页夹 `*.binder/` 归剧情插件；章节编号是章的稳定身份，章序由活页夹的清单给出，两者不同（[`workspace/folder-kinds.md`](../specs/workspace/folder-kinds.md)）。
  - 编辑器区按文件认领文档（[`workbench/editor.md`](../specs/workbench/editor.md)）。不对应文件的只有页面标签 `editor.pages`（输出 33）：每个页面一个标签、不进会话记录、刷新不恢复、不能拆分、不带参数。编辑器控件能定位到末尾、大纲标题与行（源码编辑器），不能按一段原文定位。
  - nb-form 能按 JSON Schema 画表单，对应 Spec 还是 planned（[`ui/forms.md`](../specs/ui/forms.md)）。它是受控表单，每次提交一个新的整值；没有图片控件。
  - nb-markdown 是项目的 Markdown 方言（marked 加 TipTap），有批注 `<comment>`、文字颜色 `<span style>`、尖括号网址等写法（[`workspace/markdown-dialect.md`](../specs/workspace/markdown-dialect.md)）；语言目录约 5800 行，其中编解码约 1400 行。全仓没有 MDX 的解析与编辑。
  - harness 的提醒助手只在一轮开始时检查，`every` 按轮数算（`packages/nb-harness/src/kernel/helpers/reminder.ts`，[`harness/extensions.md`](../specs/harness/extensions.md)）。
- **MDX 实测**（MDX 3.1.1，2026-11-02，脚本与输出在 t02 证据 `mdx-probe-2026-11-02.txt`）：
  - 报错的写法：尖括号网址、HTML 注释、`<` 后面跟汉字或数字（`<叮！获得神典石×50>`、`魔力<50`）、正文里的 `{这里要不要加一句吐槽？}`。
  - 能编译但意思变了的：`好感度{+5}` 显示成“好感度5”。
  - 能编译的：批注 `<comment body="…">`、`<span style="color: …">`（后者 Vue 接受，React 不接受）。
  - 每个 `{}` 与每条 `import` 都拿得到语法树（取字段是 `MemberExpression`，条件是 `ConditionalExpression`，调用是 `CallExpression`），可以按白名单检查。
  - 第二轮审查补测（A2、B2）：`panel.任务[t3]` 里的 `t3` 是变量；`{panel.魔力 = 3}` 是赋值表达式；跨标题的块级标签整篇能编译，按标题切开后两块都报错；`**“走吧。”**然后` 不成粗体（CommonMark 的强调规则，第三方插件 remark-cjk-friendly 2.3.3 能补上）；表格、任务列表要 remark-gfm。
- **nb-story（读者视角）**：
  - 记录有对象、称呼、说法、秘密、知情、情节、状态变动、疑问；每条都有出处；模型只写章草稿，其余由程序生成。
  - 评测结论（w00005 t34）：100 章以内，读全文作答最准；把图当目录、挑章再读原文，能追上全读；用图作答的失分多是照搬了图里记错的内容；Agent 自己挑章时，出处章只挑中 69% 到 79%。
  - 能借鉴的概念：说法的事实、信念、说法三分（按渠道定）；“没有记录”不等于“不知道”；马甲单独建对象，再用“身份同一”相连；数值逐笔累加并与原文核对。前三项第一版用不上，留给关系与知情。
- **nb-memory**：
  - 有 episode、facts、主体注册表与状态（带失效区间）；双时间轴：`tick` 是叙事推进序，`instant` 是故事时间；按时刻查询、缺坐标时不可见（fail-closed）（`packages/nb-memory/README.md`）。
  - 写入不一定调模型：`addFact` 直接落库，状态写入不做消解；只有批量摄入时传入模型才做主体消解，而且“消解是增强不是闸门”。检索索引与查询过滤从公开入口导出。
  - 它的状态是“主题加一段文字，带有效区间”，不是带类型的字段补丁；没有计划，也没有作者的修订轴。复用边界见待定项 3。
- **nb-history**：工作区文件的 append-only 操作日志与快照，审阅收件箱按文件接受或整份还原，有 `acceptAtRevision`；单进程单写者（`packages/nb-history/README.md`）。新应用里还没有 history 插件与收件箱界面。它管得了正文和手记这类文件的历史，管不了“第 3 条记账单独驳回”这种记录级的操作。
- **ADR 0027**：内置插件与第三方插件用同一套清单、登记与贡献点，信任所有插件。

## 四、方案

### 1. 概念

| 概念 | 意思 |
|---|---|
| 条目 | 设定的单位：人物、组织、地点、物品、概念、剧情线……有稳定 id，在条目树里有一个位置 |
| 条目树 | 作者整理条目的目录。只用来组织和浏览，不表示地理上的包含、组织上的从属，也不表示身份同一 |
| 主 MDX | 每个条目都有的一段 MDX，既是作者写的文字，也是这个条目的主视图。按块存，块是闭合的语法单元 |
| 状态 | 条目上随剧情变化的数据：名字、别名、一句话描述，以及各 Component 的字段。概念上是一份 JSON，怎么存另定 |
| Component | 加在条目上的能力：可以带数据（一个命名空间加 schema）、界面、给 Agent 的文字视图、查询。分类型与实例 |
| 剧情变更 | 故事里发生的一件事：描述、生效位置、讲述、涉及的条目，以及对状态和主 MDX 的补丁 |
| 计划 | 还没写的剧情变更 |
| 创作修改 | 改的是设定本身（改正、改主意、调整排版），不是故事里发生了什么 |
| 修订 | 一次写入：一组操作，带谁写的、为什么、基于哪个版本，存改前与改后的值。改动记录里的一条 |
| 地址 | 补丁、核对点、字段引用、工具共用的写法：条目 id、命名空间、字段 id，列表元素按 id，对象按键 |
| 位置 | 故事里的一点：初值、前史、第 N 章开头或末尾 |
| 出处 | 变更的依据：正文（章加原句）、细纲、手记、作者消息、界面操作 |
| 记账 | 写完一章后，Agent 读这一章，写出本章的剧情变更，默认生效 |
| 待处理 | 交给作者拍板的事：记账里有问题的项、算不下去的变更、核对点不符、冲突、失联的出处…… |
| 建议 | 改设定以后给作者的正文修改建议，和待处理分开 |
| 未决问题 | 作者还没想好的事，例如“双王”指什么。Agent 不替作者补全 |
| 视图 | 给作者的界面（Vue）与给 Agent 的文字（MDX 渲染） |

两条轴：**位置**回答“故事讲到哪了”，**修订**回答“作者什么时候这样写的”。状态由两者一起决定，这是常见的双时间模型。

### 2. 条目

一个条目由三部分组成：

1. **身份**：稳定的 id，永不复用；条目树里的位置。
2. **主 MDX**：作者的文字与排版，可以引用本条目和别的条目的字段。按块存，每块有稳定 id（另存，不写进正文，改标题文字不影响）。块是闭合的 MDX 语法单元：块级标签不能跨块，引用定义只在本块内有效，跨块的写法在写入时拒收；标题只用来导航，不当解析的边界。块的边界在新建时切一次，之后稳定。
3. **状态**：名字、别名、一句话描述，加上每个带数据的 Component 的一块。

几条规则：

- **名字、别名、主 MDX、状态都能随剧情变**，靠打补丁。到第 10 章才得名“夜王”的角色，第 3 章的视图显示旧名。
- **存在区间**：条目可以有“出场”位置。作者手动建的默认从头就有；记账时建的，默认是第一次讲到它的那一章。早于出场的位置上，作者视图标“尚未出场”，Agent 的查询不返回它（按计划查、跨时期查除外）。删除留墓碑，引用它的地方显示“已删除的条目”。
- **主 MDX 不嵌入 Component 的视图。** 每个 Component 的界面在它自己的 Tab 里；主 MDX 只能用表达式引用字段，例如 `{panel.魔力}`（开发者 2026-11-01）。
- **经历不进主 MDX。** 经历就是涉及这个条目的剧情变更，靠检索查。
- **马甲**：每个马甲是单独的条目，和本体之间用显式的“身份同一”连接。条目树只管整理，把马甲挪到别的分组不会改变它是谁。共享的数（存款、魔力）放在本体上，只有一份；马甲只放自己的（名声、所属）。马甲页上，本体的共享字段只读显示，改它就是改本体；情节默认合并本体与马甲。
- **种类与个体**：“守护之星”这类道具种类是一个条目。某人手里那一枚要单独记经历时，另建条目并引用种类；不需要时，只在持有者面板的列表里记一项。

### 3. 剧情变更日志

全书一条日志，只有一种记录，就是剧情变更。

| 字段 | 意思 | 例子 |
|---|---|---|
| id | 稳定，不复用 | c09 |
| 描述 | 发生了什么，一句或一段自然语言 | 回房关掉滤镜，在阳台读《如何做个好哥哥》 |
| 种类 | 已写，或计划 | 已写 |
| 生效位置 | 前史（带先后），或某一章加章内的排序键；计划可以是“未排章” | 第 1 章 |
| 讲述 | 在哪些地方讲到，每处一条出处；同一件事可以讲好几次 | 正文第 1 章“她关掉了滤镜……” |
| 涉及 | 涉及的条目 | 星瑕 |
| 剧情线 | 属于哪些剧情线 | 做个好哥哥 |
| 连接 | 兑现（已写指向计划）、替代（新计划指向旧计划）、拆自（部分兑现时拆出的计划） | 兑现 c20 |
| 补丁 | 对状态与主 MDX 的修改，可以为空 | `星瑕.character.形态 = "原身"` |
| 核对点 | 正文写明的数，是独立的对象：地址、正文里的值、讲述、比较的位置；可以挂在一条变更的补丁之前或之后（见第 5 节） | 存款 41800，正文第 3 章“余额……” |
| 生效状态 | 生效、待定（作者处理前不生效）、已撤销（保留，不生效，带原因）。只由修订改变；这次重算套没套上是另一回事，见第 5 节 | 生效 |
| 来源 | 谁提出的（作者、哪个 Agent 会话）；把握：确定，或没把握（没把握的整条待定）。“估计”标在单个补丁上，见第 5 节 | Agent |

**计划怎么走：**

- 计划的进展：未兑现、已兑现、已取消、被替代。“已兑现”不单独存，由生效、而且这次重算套上了的兑现连接推出：兑现它的那条已写变更被撤销或没套上，计划就回到未兑现。
- 记账写出的已写变更用“兑现”连到计划。数以正文为准：计划写“花 100”，正文写“花 50”，就记 −50，差额写进回执，不算冲突。
- 正文写出发生了的部分才算兑现；没写的部分拆成一条新计划（连接“拆自”），带着没实现的补丁，默认排在下一章开头，回执里列出，可以改成未排章。细纲计划“花 300 买药 S、救下风信子”，正文只写了“花 50 买药 A”：原计划已兑现，“救下风信子”拆成新计划。判断不了（例如任务算不算完成）的，标“没把握”，整条待定，进待处理。
- 兑现、原计划被用掉的部分、拆出的计划记成一组：撤销那条兑现时，原计划回到未兑现，拆出的计划一起停用；拆出的计划已经有后续的（被改过、被兑现），按依赖列出（第 5 节“还原”）。
- 真实状态只用已写、生效、这次重算套上了的变更。“按计划”视图再加上生效、未兑现、排在第 N 章及以前的计划；已写章节上的未兑现计划不进那一章，只进之后的章；未排章的计划不进任何一章。已兑现、已取消、被替代的计划，它们的补丁不再进任何视图。
- 计划记着它来自细纲的哪一段。细纲改了，从它来的未兑现计划标“细纲已变”，由作者选择更新或保留。

其余几样都从这条日志得到：

- **经历**是变更的描述。
- **剧情表**是按章和剧情线排成的格子。
- **伏笔**是一条剧情线，剧情线条目自己有状态（计划中、进行中、已回收、放弃），不靠标签推断。

**剧情变更和创作修改要分开记：**

| | 剧情变更 | 创作修改 |
|---|---|---|
| 例子 | 第 3 章，星瑕花掉两千 | 作者把开局存款从四万改成五万；Agent 调整主 MDX 的排版 |
| 落在 | 生效位置上 | 给出这个值的那条记录（初值，或某条变更） |
| 改变的是 | 这个位置以后的状态 | 设定本身，所有位置都跟着变 |

两者都是修订，都在改动记录里。作者在界面上直接改，默认算创作修改，见第 8 节的“就地改”。Agent 写入时自己标明。

### 4. 位置与排序

- **章用稳定 id 引用**，章序由活页夹给出。调整章序也记成一次修订，按新的章序重算；删掉一章时，生效位置在它上面的变更进待处理，等作者重新安放。
- **章内的位置**：变更与核对点共用一种存下来的排序键，写入时按讲述原句在本章的先后算一次，之后只由修订改变，改稿不移动它。没有正文讲述的（界面上记的、来自细纲的），按写入的先后排在章首或章尾，排序键相同时按 id。给一条已有记录补上第一条正文讲述时（作者先“记一笔”、记账再补讲述），排序键改为这处讲述的位置，并写进回执。同一位置上赋值与加减的先后由排序键决定。
- **生效位置默认是第一次讲到它的那一章**，这是第一版的近似（开发者 2026-11-01）。正文明说发生在开篇之前的（“半年前，她遇到了白灵”），生效位置放前史，并给出它在前史里的先后。其余的也可以手动往前挪。
- **重讲不重记**：已经记过的事再讲一遍（回忆章、别人转述），只给原记录补一条讲述，不再打一次补丁，不会重复扣钱。
- **界面上记的剧情变化**：在“第 N 章开头”的视图上记的，落在第 N 章最前面；在“末尾”的视图上记的，落在第 N 章最后。
- **已知代价**：同一章里的补叙（先讲傍晚、再讲中午），第一版按排序键排，不按故事时间。细的故事时间在 t04。
- **位置是一个独立的类型**，只由一个模块比较与序列化。以后加故事时间和世界线时，换掉这个模块，调用方不改。

### 5. 状态怎么算

**修订：**

- 每一次写入都是一次修订：作者在界面上保存、Agent 的一次 `write`、一章的记账、直接改文件后被读进来的内容、调整章序、Component 的 schema 升级。
- 一次修订是一组操作，写明谁、为什么、基于哪个版本，并存下每个被改对象的改前与改后的值。状态值、补丁与改前改后的值都带所属 Component 的 schema 版本。整个世界模型有一个版本号，每次修订原子发布，版本加一。
- 第一版承诺两件事：当前版本的重算是确定的；每次修订都能还原（有依赖时连同依赖一起，见下文的“还原”）。不承诺按任意历史版本重新渲染：那要把章序、schema 与升级函数的版本也冻结进修订，需要时再加。

**某个位置上的条目 = 当前的初值 + 所有已写、生效、生效位置在此之前的变更，按位置和排序键依次打补丁。**

**地址**：补丁、核对点、MDX 里的字段引用、带值写法与工具用同一种地址。

- 写法：命名空间、字段 id，列表元素写 `[元素 id]`，对象的子字段写 `.键`，例如 `panel.任务[t3].奖励`、`character.立绘[原身].说明`。
- 根：`entry`（名字、别名、一句话描述）与本条目的命名空间；别的条目写 `ref("e12").panel.魔力`；内置函数的名字是保留名。
- 条目 id、元素 id、字段 id 都由程序生成成合法的标识符。字段 id 新建时由显示名生成，此后不变；改显示名不影响补丁与主 MDX 里的引用。
- `[]` 里只许常量，表示元素 id，不是变量；MDX 里写成 `["t3"]` 或 `[t3]` 都按 id 解释，动态下标与数字下标拒收。对象键与列表元素在 MDX 里都可以写方括号，按 schema 区分；存下来的地址一律写成 `.键` 与 `[id]`。
- “启用”是每个命名空间的保留字段，schema 里不许有同名字段。
- 显示名与 id 不同时，带值写法与 `lookup` 同时给出两者。工具参数里的条目与字段可以写名字或显示名，存下来的一律是 id。

**补丁的执行规则：**

| 补丁 | 用在 | 规则 |
|---|---|---|
| 赋值 | 任何字段、子字段、名字、一句话描述 | 直接取值 |
| 加减 | 数值字段 | 程序算，模型不心算 |
| 列表增删改 | 列表字段（道具、任务） | 元素有稳定 id，按 id 找，不按序号 |
| 整段替换 | 长文本字段、主 MDX 的一块 | 存全文，不存 diff。Agent 可以写成“把 A 换成 B”：A 要在当时的值里恰好出现一次，程序替换、算出全文，给作者预览后存下 |
| 别名增删 | 别名 | — |
| 增删块 | 主 MDX | — |

随剧情变化的文字不做三方合并（开发者 2026-11-02）。经常变的事实最好放进字段，文字只引用它：c30 只改 `character.发型`，以后改初值的发色，所有章都跟着变。人物 Component 给的是一段“外观”文字还是几个字段，在 t10 定，内核两种都支持。

**写入时校验**，不过就拒收，说明哪条、哪里不对：

- 条目存在，且在生效位置上已出场；剧情变更对某个 Component 的数据字段打补丁时，它在生效位置上已启用（“启用”字段本身不受这条限制，初值与创作修改也不受）；
- 字段在 schema 里，类型对得上；
- 约束（不能为负、上限）在一条变更的补丁全部套完之后检查，同一条里的先后不影响结果。每个数值约束声明溢出时拒绝还是截到上限，截掉的部分写进流水；
- 正文讲述的原句确实在那一章里；
- 每个数要有依据：讲述里的一段原文（程序验证原句存在，并用中文数字解析得出同一个数）、由核对点推出的差额（程序复算），或者在这个补丁上标“估计”。都没有就拒收；
- 预览与回执列出这次写入会让后面哪些变更套不上，这些问题记在这次写入名下，作者可以直接还原它。

**重算时算不下去**：改了前面以后，后面的补丁可能套不上。

- 每个补丁有三种结果：套上；不适用（命名空间被作者有意隐藏：Component 去掉了，或在这个位置没启用），只跳过这一个补丁，不算失败；套不上（元素没了、约束破了、类型不符）。
- 一条剧情变更里有补丁套不上，整条在这个位置不算数，转账不会只记一边。这是这次重算的诊断，不改记录的生效状态；前面修好了、重算套上了，诊断自动消失。`read`、`changes` 同时给出生效状态与这次套没套上。
- 受影响的地址从这里往后标“不完整”，粒度与地址一致，到列表元素与子键；跨字段约束失败时，标的是被约束的字段。不完整沿依赖往后传，遇到不依赖旧值的赋值或整段替换就截止，子键赋值只解除它覆盖的地址。作者视图和 Agent 的读取都看得到，不当作完整的状态交给写手。
- 进待处理的按根因合并：一次创作修改引起的一串套不上合成一项，列出受影响的记录数与范围。
- 重算只取存下来的值，不调用模型。

**核对点：**

- 记账时把正文写明的数记成核对点。只确认已有值的，不产生补丁：第 4 章“200 启动资金”已经是初值，不再记一笔。同一笔交易讲了两次，只记一笔，两处都是讲述。
- 核对点是独立的对象，有自己的比较位置，默认是讲到这个数的那一句在本章的位置（排序键与变更共用，见第 4 节）。挂在一条变更上时，写明比的是补丁之前还是之后（“花了 50，还剩 150”比的是之后）；挂靠的变更撤销或没套上时，核对点保留，按讲述的位置比较。回忆里的数（“出发时我有 100”）挂到它说的那个时候；定不了的，进待处理。
- 重算时比较，对不上就进待处理。待处理里列出嫌疑区间里的记录，估计的排在前面：同一地址上，从“上一个对得上的核对点”与“最后一次完整赋值”中较晚的一个起，到这里为止；都没有时从初值起，初值本身也列入；没套上的记录也列入。处理办法由作者选，不预选：
  - 改或撤前面的某条记录（记错了）；
  - 插一条校正变更（漏记了一笔）；
  - 改正文里的数，作为建议给作者（正文写错了）。
- 处理前，视图显示计算值，旁边标“正文写的是 Y”。

**改过去：**

- 改了初值、改了某条变更，或者插进一条，都是一次修订，发布后重算。
- 后面改过同一字段或同一块的变更，列给作者看，分两种：加减的会自动跟着变；赋值和整段替换的不会，要看一眼。
- 设定改了以后，正文里的旧写法怎么办，见第 8 节的“改设定以后”。

**还原：**

- 还原一次修订，是发布一次补偿修订，把那次修订改过的对象恢复成改前的值。单位是修订；整章撤销就是还原这一章的记账修订，作者在本章“记一笔”的不在内。
- 依赖：后面的修订改过同一个地址（状态到字段与列表元素，记录到字段）、引用了它新建的条目或列表元素、或者与它的记录同属一组兑现转换（第 3 节）。只往讲述、核对点、连接这类列表里加元素的修改，互不依赖；补偿只移除本次加的元素。依赖取传递闭包。
- 有依赖时，第一版不单独还原：列出依赖，作者可以选择连同它们一起还原（从后往前）。不会覆盖后面的修改。
- 恢复的旧值按它带的 schema 版本升级后再写。

**并发：**

- 读取带版本号。写入带上读取时的版本：它要改的对象在那之后被改过，就报冲突，返回这次修订涉及的全部对象，标出哪些被改过、当前值是什么，不静默覆盖。
- 就地改与带值回写，提交时还带上读到的值和它的来历；发布时重算这个位置的值，与读到的不同（期间别人在中间记了一笔）也报冲突。
- 跨条目的修改（转账：A 减 20、B 加 20）在一次修订里一起发布，不会只发一半。
- 所有写入在项目进程里排队发布，日志只有一个写者；渲染与查询读某一个固定的版本。
- 直接改文件：导出给 Agent 的文件旁边有一份旁车记录，记着导出时的版本与各对象的值摘要；导入时按对象判冲突（对象的当前值与导出时相同就接受），不比全局版本号。导入成功只更新旁车记录，不改 Agent 正在编辑的文件；导入被拒时，旁车标“有未导入的改动”，处理掉以后这份文件才再导入。导出的主 MDX 每块前有一行块标记 `{/* block:b7 */}`，导入按它对回块 id，块标记不完整的拒收。每次导入是一条修订，监视器合并掉的几次保存算一次。具体格式随 t09 定；全放数据库时没有这条路。

### 6. Component

**登记**：Component 类型经插件平台的贡献点登记，内置与第三方用同一套（ADR 0027）。第一版只发三个内置类型。属于哪个包、哪些在后端、哪些在浏览器，在 t14 定。

**类型提供，都是可选的：**

| 能力 | 用途 |
|---|---|
| 数据 | 一个命名空间加 schema：字段 id 稳定，schema 带版本。只有带数据的类型才占命名空间 |
| 作者界面 | Vue Tab |
| 给 Agent 的文字视图 | 可以用 MDX 写，随插件发布，和插件代码同样受信任 |
| 查询视图 | 带参数的查询，例如情节的分页与筛选 |
| 记账说明 | 写完一章后，记账要留意这个 Component 的哪些变化 |
| 用法说明 | 以提醒的方式给 Agent，见第 9 节 |

**实例**只提供这一个条目上的数据与配置，例如这个面板声明了哪些字段。字段声明可以从预设（金钱、体力、等级）或别的条目复制。

**生命周期：**

- 一个条目上同一类型只有一个实例；登记时拒绝重名的命名空间。
- 加一个 Component 是创作修改。每个实例有一个保留字段“启用”（地址 `<命名空间>.启用`），默认从头启用。它是内核随时可写的控制字段：同一条变更里先处理启用，再处理数据字段，整条一起校验。故事里第 3 章才得到面板的，加的时候选“从第 3 章起”：初值里不启用，再记一条第 3 章的剧情变更把它启用。
- 没启用的位置上，读取看不到这个命名空间；剧情变更对它的数据字段的补丁写入时拒收，已有的在重算时按“不适用”跳过。初值与创作修改不受启用限制：作者在启用前的位置上看到的是“第 3 章起生效的起始值”。再启用时恢复原来的值。
- 去掉时数据隐藏、保留，再加回来时恢复。
- schema 变了：补丁按字段 id 寻址，改显示名不影响历史；改类型、拆字段，要类型自带一个确定的升级函数，旧数据和旧补丁在读的时候升级，不改写历史。

**第一版内置三种，各验证一种用法：**

- **人物**（带数据，带表单和图片）：字段清单在 t10 定。立绘按形态各存一张，带说明；要图片控件。外观一类的文字改了，相关的立绘标“可能过期”。
- **面板**（要求精确的数值）：
  - 字段：数值（可带下限、上限，上限可以是另一个字段）、枚举、列表（道具、任务，元素有 id）；
  - Tab 显示当前值与流水。改数同样走第 8 节的就地改；“记一笔”是勾了“剧情变化”的快捷入口：输入增减和原因，生成一条加减补丁；
  - 数值约束声明溢出时拒绝还是截到上限（第 5 节）；
  - 正文写出的数当核对点；
  - 给 Agent 的视图带最近几笔流水。
- **情节**（只查询，不占命名空间）：
  - 是剧情变更日志里“涉及本条目”的那部分；
  - 作者界面：分页；按章、剧情线、已写或计划筛选；关键词与语义检索（没有嵌入服务时退回关键词）；
  - “问一句”：在筛出的结果上提问，回答每句标出处。它是一次性的 Agent 调用，用默认的模型角色，和 Agent 用同一套读取与检索，不另写一套问答；可以接着到 Agent 对话里问。

### 7. 渲染

**用 MDX**（开发者 2026-11-02，两次确认：表达力更强；条目里的 MDX 大多由插件作者和 AI 写。不复用项目的 Markdown 方言；作者在界面里怎么编辑，先不考虑，以后另找办法）。

- **输入**：条目、位置、实际或按计划、给谁看（作者或 Agent），读当前版本。结果只取决于输入。
- **一套解释器**，前后端共用：后端出给 Agent 的文字，前端出给作者的界面。
- **条目里的 MDX 是项目数据**，可能来自模板或别人分享的世界观，只放行白名单：
  - 表达式：取字段（地址见第 5 节；本条目的，或用 `ref("id")` 引用别的条目的）、字面量、比较、逻辑、条件、少数内置函数（例如数字格式化）；
  - 不许 `import`、`export`、定义函数、赋值、调用内置函数以外的函数；
  - 一个字段都不引用的表达式也拒收：`{+5}` 多半是正文里的花括号，提示转义；
  - 标签只有内置的几个：条目引用、图片；
  - 只含注释的表达式（`{/* … */}`）放行，用作块标记与注释；
  - 程序自己解释白名单里的语法树，不执行 JS，所以不需要另起隔离环境；
  - 写入时编译检查，不过就拒收，指出行和列。
- **按块解析**：块是闭合的语法单元（第 2 节），一块出错，只有这一块显示成纯文本加诊断，其余照常。
- **引用别的条目**：读同一版本、同一位置的原始状态。读不到（没出场、删了、没有这个字段、Component 没启用）时，显示一个带说明的占位，不是空白，也不让整篇失败。
- **作者看到的**：只显示值，悬停显示中文的字段名，不露路径。图片直接显示。
- **给 Agent 的渲染用带值写法：**

```text
姓名：{entry.name = "星瑕"}
立绘：{character.立绘[原身] = {"图片": "assets/星瑕/原身.png", "说明": "银白长发，校服"}}
魔力 {panel.魔力 = 3110}/{panel.魔力上限 = 12000}，{panel.魔力 >= 1000 ? "能变身" : "变不了身" -> "能变身"}
```

| 写法 | 意思 |
|---|---|
| `{地址 = 值}` | 单独一个字段。改这个值就是改这个字段 |
| `{表达式 -> 值}` | 算出来的或条件，只读；要改，改它依赖的字段 |

- **值统一写成 JSON**：文字带引号，数字不带，图片是带“图片”和“说明”的对象。
- **带值写法是一种独立的可读格式，不是 MDX**：`{地址 = 值}` 在 MDX 里是赋值，`->` 不是 MDX 的语法。源文里转义的 `\{` 在渲染结果里保持转义，代码里的花括号原样输出，都不当占位。它的文法：
  - 注记是 `{地址 = JSON}` 或 `{表达式原文 -> JSON}`。表达式原文按 JS 的词法（字符串、模板串）扫描到顶层的 `->`；`=` 左边只许地址，`=` 只有一个。
  - 内置标签原样输出；属性里的表达式也写成注记；条目引用写 id，附当时的名字（只读）。
  - 不完整的值带“不完整”标志与原因；`->` 的值依赖不完整的字段时一并标。具体写法在 Spec 定。
  - 显示名与字段 id 不同时，附上显示名。
- **回写**：读取结果带版本号和块 id。Agent 交回改过的一块，程序按这个顺序处理：
  1. 解析注记，JSON 值用 JSON 解析器读出边界，不按第一个 `}` 或 `->` 切；
  2. 按顺序和源文的表达式一一对应，核对地址与旧值；
  3. 拆成字段操作（`=` 后面的值变了）与文字操作（注记以外的字变了）；
  4. 还原源文，按白名单校验；
  5. 按就地改的规则（第 8 节）写回给出这个值的记录。请求里带两个参数：意图（改设定，或剧情变化）与来源不止一个时的处理（改基准、改某条记录并给 id、补一笔并给位置）。来源不止一个而没给处理方式的，拒收并返回来历，让 Agent 补上参数或转给作者。Agent 回写不弹确认条，改动记录与可以撤销的提示照常给作者。

  拒收的情况：`->` 的部分被改；占位被重排、复制或新增（新增引用请改源文）；同一字段出现两处，被改成两个不同的新值（只改了其中一处的，按改了的那处）；不完整的字段被改成别的（只接受不改或完整赋值）；读到的值与来历过期（与第 5 节同一口径，报冲突）。

### 8. 作者怎么用

**入口与用词：**

- 作者通过 NeuroBook 的界面，不直接编辑条目所在的文件夹；直接读写文件留给 Agent（开发者 2026-11-01）。
- 界面上不出现 Component、路径、记录 id：写“魔力 −90”，不写 `星瑕.panel.魔力 -= 90`；新建时选“人物”“带面板的人物”。

**条目页：**

- 是编辑器区里的一个标签页。要的是一种带参数的虚拟文档：每个条目一个地址，可以多开、拆分并排、刷新后恢复，有草稿与保存，条目删除后标签显示墓碑。现有的页面标签（`editor.pages`）是单例、不恢复、不能拆分，不够用，要扩展编辑器（见影响）。主 MDX 若在 t09 定为文件，现有的按文件认领能承接一部分。
- 一次保存是一次修订，可以同时改几个字段。保存时遇到冲突（Agent 刚改过同一处），给“用当前值”“保留我的修改”。
- 顶上选位置：当前、初值、第 N 章开头或末尾（可搜索的章列表）、按计划。所有 Tab 跟着同一个位置。
  - “当前”是最近获得焦点、有章序的章节标签所在的章；没有时是最新已写的一章。
  - 每个条目页的位置各自独立，可以锁定。开始编辑一个值时位置冻结，直到保存或放弃。
- 值旁边标出“和初值不同，最近一次在第 N 章改”。
- 作者在界面里怎么编辑主 MDX，先不定（开发者 2026-11-02）。已知要解决的：中文标点旁的粗体（`**“走吧。”**然后` 在 CommonMark 里不成粗体，有第三方插件 remark-cjk-friendly）、源码里的 `{` 与 `<`、没改的部分保持原样。

**就地改**（开发者 2026-11-02）：

- 作者在看到的样子上直接改，不用回到之前的章。
- 系统知道每个值、每一块文字是哪条记录给的，默认算改设定（“一直就是这样，之前写错了”），改动写回那条记录。来源只有一个的，直接改，保存后给一行可以撤销的提示：
  - 发色只有初值设过：改初值，所有章都变；
  - 发色是第 45 章“染成黑色”设的：改第 45 章那条，初值不动；
  - 一块文字来自第 52 章的整段替换：改第 52 章那条。初值和第 30 章的版本里也原样写着被改的那几个字时，问要不要一起改。
- 来源不止一个，或者改了会有下游后果（让别的核对点对不上、被后面的赋值盖掉）时，保存前弹确认条，写明会改哪条、有什么后果：
  - 数值是几笔累出来的（初值 200，第 2 章 +10，第 4 章 −50）：以最后一次完整赋值（或初值）为基准，其后的加减保持。列出这几笔（估计的标出来，最近对得上的核对点也标出来），作者选“改开局数”“改或撤某一笔”“补一笔漏记”，不预选。保存后核对结果等于作者填的值，不相等时整次拒收并说明原因（例如“你选的那一笔是 +10，差额是 −800”）。
- 确认条里可以勾“这是剧情里发生的变化”：在当前位置新记一条剧情变更；数值字段生成加减（差额），不是赋值。字段不完整时不生成差额，要求写成赋值，或者先处理根因。位置是初值、前史、按计划时，这个勾选置灰。

**开始一部作品**，三条路，什么都不必填：

1. **先发故事种子**：Agent 先问几个会挡住开局的问题，然后建条目、记前史与开局状态、起草剧情线。作者没定的建成未决问题，不替作者补全。建出来的已经生效；首次审阅是“看过”：未决问题在前，条目逐个看或改，前史排成一条时间线。
2. **已有成稿**：把章节放进活页夹，排队逐章记账，给一份总回执。字段的初值可以是“未知”：第一次在正文里出现的数当初值，标“估计”。
3. **先搭设定**：在界面里建条目、填表。

空状态给“先搭设定”的入口；配置了 Agent 时，再给“把故事种子交给 Agent”。

**日常循环：**

1. **细纲**挂在章上，是作者写的原文，不是剧情变更。讨论时，Agent 从细纲提出这一章的计划，作者可以直接增删改计划。
2. **写作指示**（“这次只让妹妹误会”）和未决问题挂在章或剧情线上，不进世界状态。
3. 写正文；途中可以在面板上“记一笔”。
4. 点“记账”（或“本章写完”）触发，不在每次保存时跑。记账会读到本章已经记过的（包括作者记的一笔），不重记。
5. 看回执：新建了几个条目、记了几条变更、兑现了哪些计划（计划与正文的差额）、哪些是 Agent 估的数、几处待处理。待处理的逐条处理，其余默认生效（开发者 2026-11-02）。整章可以一键撤销，只撤这次记账产生的。

**作者看到的几处：**

| 地方 | 放什么 | 跳到哪 |
|---|---|---|
| 回执 | 一次记账的结果，记账后弹出，之后在改动记录里能重开 | 变更详情、待处理 |
| 待处理 | 要作者拍板的：记账里核对点不符、与设定冲突、Agent 没把握的项（开发者 2026-11-02），算不下去的变更，出处失联，导入不了的文件 | 变更详情、正文原句、条目 |
| 建议 | 改设定以后给的正文修改建议，单独计数，不算进待处理 | 正文原句 |
| 改动记录 | 所有修订，按时间排，每条写谁、改了什么（改前改后）、为什么，可以还原（规则见第 5 节） | 变更详情、条目 |

**变更详情**是这些地方共同的跳转目标：一条剧情变更的描述、位置、讲述、涉及、补丁、核对点、连接，都能在这里改；挪生效位置、改补丁、补剧情线、取消或替代计划，也都在这里做。情节 Tab、面板流水里的每一行也打开它。

**改设定以后**（开发者 2026-11-02）：银白改成淡金色以后，正文里写过“银白”的地方，系统协助作者改，只给建议，不自动改正文。

1. **什么时候找**：只对会在正文里重述的文字字段（外观、性格这类）的改设定找；数值字段不找。
2. **找**：记账时留下的讲述（正文重述设定时会链到字段），加上在涉及这个条目的章节里按旧值与别名搜索；别的条目的主 MDX、未写章节的细纲、手记、变更描述也搜。换了说法的（“那抹银色”），只有记账时留了讲述才找得到，第一版不通读全章去找。
3. **判断**：只把候选段落交给 Agent。它要分清：写的是不是这个人；是不是她本来的样子（马甲、滤镜下的样子不改）；是不是故意写错的（记错、谣言）。每条带把握：确定，或请作者判断。
4. **作者过**：按上下文分组（“金色十字星”14 处一组），组内可以一起处理；“全部不改”会被记住，下次不再提。每条有原句、建议的改法和理由，“采用”“自己改”“不改”。
5. **采用**：章节已经打开的，改编辑器里的文档，不直接写盘；历史归文件层（nb-history）。采用时同步更新链到这句的讲述，不标“出处失联”，也不让这一章的账标“可能过期”。别的条目里的文字，采用时是一次修订。立绘标“可能过期”。

**出处**：正文出处存“章加原句”，不存段号。正文改了以后按原句重新定位，找不到就标“出处失联”。正文的修改碰到了讲述的原句，这一章的账才标“可能过期”，改别处的错别字不标。点出处跳到原句，需要编辑器能按一段原文定位（见影响）。改稿后的自动重新记账在 t22；第一版可以整章撤销后重记。

**找东西**：全书搜索（条目、变更、正文，命中直接显示出处）；条目列表按名字搜、按类型筛；“本章涉及的条目”由日志直接给出。

**剧情线**做成条目（待定项 4），有状态与意图文字；剧情表是章乘剧情线的格子。给旧变更补剧情线是创作修改。

界面的布局与字段清单放到 t10、t16。

### 9. Agent 怎么用

**三样基础**：条目树、剧情变更日志、正文（加细纲与手记）。

**工具：**

| 工具 | 做什么 |
|---|---|
| `lookup` | 按名字和别名查条目，用给定位置上有效的名字。返回 id、名字、描述、有哪些 Component，每个 Component 一行关键状态（“面板：神典石 200”）。没找到时分开说：没有这个条目；是某个字段的名字；在哪些条目的文字里出现 |
| `read` | 读一样东西在某个位置的样子：条目的主 MDX（带值写法）、某个 Component 的视图或查询、原始状态与来历（这个值由哪些变更依次算出）、一条变更的原记录与出处、某章正文的一段、待处理、改动记录 |
| `changes` | 按章、生效状态、计划进展、剧情线、涉及的条目列出变更；默认不列已撤销的 |
| `search` | 检索变更、条目文字、正文、手记，可以按章与涉及的条目过滤。空格分隔的几个词默认要全部命中，可以选“任一”；结果写明用的是哪种 |
| `tree` | 看条目树的一层 |
| `write` | 一次修订：建条目、加或去掉 Component、改初值或某条记录、就地改、交回改过的一块（带意图与多来源时的处理）、记剧情变更（带核对点、讲述、兑现）、取消或替代计划、报冲突（指到字段里的那段文字）、给正文提建议、记未决问题、还原一次修订。可以先预览（改后各条目在本章末尾的样子、冲突、会进待处理的项），再提交 |

- 每次返回都有条数和字数上限，写明共几条、是否截断，给续读的游标；结果都带位置与版本。
- **自动预查**：用户消息里出现的名字，按当前位置精确匹配，把结果当目录注入（和 `lookup` 的一行一样），有条数上限。别名可以标“不作为触发词”（“哥哥”“书”这类常见词）；两个条目有同一别名时都列出。没找到的词也列出来，按上面三种情况分开。
- **Component 用法以提醒的方式给**（开发者 2026-11-02）：
  - 首次出现和上下文压缩之后，由一个小扩展在工具结果写入之后、下一次请求之前补上；
  - “隔一段再提醒”按轮数，用现有的提醒助手；
  - 不放进系统提示词，也不随每次查询重复（开发者 2026-11-01）。
- **位置参数的默认值**：讨论或审查第 N 章的计划时，取“第 N 章开头”；记账时取“第 N 章末尾”。
- **审查细纲**：分三类检查，结论都指向具体的条目或变更：
  - 吃书：和已写的正文冲突；
  - 吃设定：和条目里的设定冲突；
  - 严谨：逻辑和动机说不通。

  审查时顺带列出“这一章会产生的变更”，就是第 N 章的计划。
- **记账：**
  - 输入：本章正文、涉及条目在本章开头的状态、本章的计划、本章已经记过的变更、各 Component 的记账说明。
  - 输出：一次修订（用 `write`，先预览再提交）。
  - 规则：
    - 设定与正文对不上（设定是金色眼眸，正文写了碧色），不自己挑一边，用“报冲突”交作者，指到那几个字。第一轮体验里，强模型把正文改成了设定的样子，方向错了。
    - 正文重述已有的事实，只给原记录补讲述；本章已经记过的，不重记。
    - 计划兑现按第 3 节的规则：数以正文为准，没写的部分拆出，判断不了的标“没把握”。
    - 正文明说发生在开篇之前的，放前史。
    - 角色说的、想的不算世界的变化。“说了这句话”这个行动可以记，话的内容不当事实；第二版记成知情。
    - 每个数给出依据（讲述里的原文，或由核对点推出的差额）；没有依据的，在补丁上标“估计”。
    - 有专名、会被再次指认、有自己的状态，三者有其一才建条目，出场是这一章；其余列在回执的“没建条目”里。
    - 剧情线默认继承兑现的计划；没有计划的，留空。
    - 核对点不符、补丁算不下去，会进待处理，不要替作者选处理办法。
  - 发布前程序校验（见第 5 节），不过的退回 Agent 重试一次，还不过的进待处理。
- **写手的上下文**：本章的计划与写作指示，涉及条目在本章开头的渲染，最近一两章的正文，再加按需检索。有字数上限，与书的长度无关。

### 11. 备选方案与取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| 与 nb-story 合成三个来源层（正文、设定、计划），再加对齐 | 否决（开发者 10-31） | 两种视角出发点不同，对齐太复杂；先做作者这边 |
| 只靠作者的手记与笔记，不要结构 | 否决（开发者 11-01） | 没有无限上下文；作者记不住全书，也需要视图 |
| 程序往作者的文件里写卡片 | 否决（开发者 11-01） | 改用 MDX 模板，渲染只在显示时做 |
| lorebook 加按章追加的说明（Novelcrafter 的 Codex 有类似做法，审查者凭记忆提供，未核实） | 不采用 | 只能补充，不能算数；某一章的样子要读的人自己合起来 |
| 七种账（立、事、变、知、计、疑、正） | 合成一种剧情变更 | 种类多了，记账员和作者都要先分类；一条记录加补丁就够 |
| 数据存在 Component 里（经典 ECS） | 不采用 | 补丁要有统一的地址；主 MDX 要跨命名空间引用；增删 Component 不必搬数据 |
| 条目的主文字用项目 Markdown 方言加一小块插值语法（第一轮 A、C，第二轮 B2 推荐） | 不采用，用 MDX（开发者 11-02，第二轮后再次确认） | MDX 表达力更强，插件作者和 AI 都会写。代价：与章节的写法不一致（中文标点旁的粗体、方言的标签）；作者的编辑器要另做，先不考虑；条目里的表达式要白名单 |
| 累加字段就地改时默认改初值、补差额 | 不采用（第二轮 A2、B2） | 会把记错的一笔藏起来（初值 200 被改成 190，估计的 +10 还在），让早先对上的核对点对不上；遇到中途的赋值还达不到作者要的值 |
| 每次修订冻结章序、schema 与升级函数，任意历史版本都能重新渲染 | 第一版不做 | 第一版只需要逐条还原；需要看历史版本时再加 |
| 随剧情变化的文字用文本 diff 加三方合并 | 改为整段替换（开发者 11-02） | 合并结果要存下来，作者改一次初值，后面每条改过这段的变更都要合一次；合得上也看不出意思是否过时。整段替换的重算是确定的，和字段走同一套“列出后面的变更”的流程 |
| 随剧情的文字只追加，不替换（审查 D） | 不采用 | 新旧文字并存，某一章的样子要读的人自己合 |
| 主 MDX 只有创作修改，随剧情变的都放字段（审查 C） | 不采用（开发者 11-01：主 MDX 也能随剧情改） | 整段替换已经够简单；推荐常变的事实放字段 |
| 记账先审后生效 | 改为默认生效，有问题的进待处理（开发者 11-02） | 作者不想每章逐条看；核对点、冲突检查、把握标记会把要看的挑出来 |
| Agent 不能改作者写的字，只能提建议（审查 D） | 不采用（开发者 11-02） | 保留“Agent 可以改”，靠同一条发布通道、改动记录与逐条还原兜底 |
| 用法提醒按 token 间隔 | 改为按轮数（开发者 11-02） | 现有提醒助手按轮触发；按 token 要另写扩展，没有证据说明轮数不够 |
| 马甲做成子条目 | 改为显式的“身份同一”连接 | 条目树只管整理；搬动条目不该改变身份 |
| 复用 nb-memory 的状态层 | 只复用检索（待定项 3） | 它的状态是带有效区间的文字，不是带类型的字段补丁；没有计划和修订轴 |
| Component 用法写进系统提示词，或者每次查询都附带 | 都不采用（开发者 11-01） | 前者占上下文、长对话里会忘；后者重复；改成提醒 |
| CodeAct 查询 | 第一版不做 | 先用视图加检索，评测显示不够再加 |
| 关系存在其中一边 | 改为：多值、各有状态的存成集中的边，单值的存成字段（第二版） | 关系是全书性的，放在某个人身上不妥（开发者 11-01） |

**没有放进表里、但要写明的三个取舍：**

- **日志归谁**：项目进程里只有一个写者，所有写入排成修订依次发布。不做多写者合并：同一本书同时写的只有作者和他开的几个 Agent 会话，排队足够。
- **渲染在哪**：一套解释器前后端共用。作者界面拿到状态后自己渲染，不必每次切位置都等后端；Agent 的渲染在后端。
- **失败怎么办**：写入时校验，不过就拒收；重算时套不上的整条变更不算数、进待处理（作者有意隐藏的命名空间只算不适用），涉及的地址标“不完整”，不中断，也不当作完整状态交给写手；渲染按块隔离。不管哪种失败，都不静默。

## 五、影响

- **数据**：新的项目数据有条目、状态、剧情变更、修订记录、未决问题、待处理，以及作为原文的作者手记与细纲。存储形态待定（t09）。
- **接口**：给 Agent 六个工具；Component 类型的贡献点；harness 的一个提醒扩展。
- **平台与共享包要先做的：**
  - 编辑器：带参数的虚拟文档（每个条目一个地址，可以多开、拆分、刷新后恢复，有草稿与保存，删除后显示墓碑），现有的页面标签不够用；和 t09 一起定，主 MDX 若定为文件，按文件认领能承接一部分；
  - 编辑器控件：按一段原文定位并选中，找不到时说明失联（富文本与源码各一份），点出处跳原句、改设定以后的“自己改”都要用；
  - nb-form：图片控件与资产上传；字段旁“随剧情改过”的标记；
  - nb-ui：分页、筛选条、时间线、差异对比；
  - 作者编辑主 MDX 的界面：先不考虑（开发者 2026-11-02），以后另找办法；
  - harness：首次出现与压缩后补提醒的小扩展，用现有扩展的“事件写入后反应、反应完成后才发下一次请求”即可（[`harness/extensions.md`](../specs/harness/extensions.md)）；
  - history 插件：正文与手记的文件级历史，复用 nb-history；新应用里还没有插件与界面。
- **安全**：
  - 条目的 MDX 是项目数据：按白名单解释，不执行 JS。插件随包带的 MDX 和插件代码同样受信任（ADR 0027）。
  - Agent 的写入走同一条发布通道，留改动记录，可以还原。直接改文件也作为一次修订读进来，按文件里的版本标记判冲突；校验不过、标记对不上的保留原样、进待处理，不成为真相。
- **迁移**：v2 还没有用户数据。旧项目的 lorebook、WorldEngine、剧情工坊怎么迁过来，在 t12 讨论。
- **成本**：每章记账一次模型调用，最多重试一次，量级参照 nb-story 的抽取；改设定后的正文协助只把候选段落交给模型，不通读全章；第一版检索用关键词，语义检索要算嵌入。
- **发布与回滚**：作为新插件发布，草案阶段不影响现有功能。

## 七、待定项

1. **名字。** 候选：法典、canon、WorldEngine。推荐中文叫“法典”、英文用 canon，避开和 OpenAI Codex 撞名的 codex。
2. **存储形态**（t09）。推荐先定模型、再定存储。候选有两种：文件加数据库索引；或者全部放进数据库。一起定的还有：条目树是不是 `lorebook.content/` 文件夹，修订记录放哪，Agent 是否经文件改主 MDX 与状态（若是，定旁车记录与块标记的格式，见第四部分第 5 节“并发”）。
3. **与 nb-memory 的复用边界。** 推荐第一版只复用它的检索索引，状态的折叠自己做：它的状态是“主题加文字，带有效区间”，不是带类型的字段补丁，也没有计划和修订轴。它的检索现在要求嵌入服务，没有只走关键词的入口；过滤只认 `tick`、`instant` 与标量元数据。复用要补关键词入口，并在截取结果之前按位置与版本过滤，在 t14 定包边界时一起定。
4. **剧情线做成条目，章不做。** 推荐：剧情线做成条目，Agent 查剧情和查设定用同一套 `lookup`、`read`，剧情线页可以放意图文字；章就是活页夹里的一项，细纲与写作指示挂在章上，不另建条目。
