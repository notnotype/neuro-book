# 作者视角的世界引擎内核（第一版）

本稿整理 w00039 t02 在 2026-10-31 到 11-01 的讨论。开发者的决定逐条列在 [Work README 的决定表](../../.agents/works/w00039-novel-writing-plugins/README.md#决定)，本稿的“决策记录”照抄；其余是主会话的方案，供审查与开发者确认。

本稿只定**模型**：条目、剧情变更、状态、Component、渲染，以及作者和 Agent 怎么用它。存储、界面细节、具体的 Component 字段不在这里定。名字没定（待定项 1），下文暂称“世界引擎”。

## 一、问题

**作者这边：**

1. 旧版的设定与人物只能靠文件管理，用户反馈太复杂。旧版有一个人物表单，字段写死在 745 行的组件里（`packages/neuro-book-legacy/app/components/novel-ide/workspace/WorkspaceCharacterDetailPanel.vue`）。
2. 设定会随剧情变：剧情推进、补充、补漏、改主意。旧 lorebook 被当成不变的设定集，写到后面就过时，作者要在一份份文件里手改，也分不清哪句话是“那时候”成立的。
3. 写完一章要“记账”：钱花了多少、谁加入了哪个组织、谁知道了什么。这是最累、最想交出去的一步，现在没有地方记。

**Agent 这边：**

1. 上下文有限，不能每次重读全书与全部设定，需要压缩过、能按章取的材料。
2. 模型算不准：数值累加、“谁知道什么”靠读文字容易错。V9 评测里最常见的错就是把读者知道的当成角色知道的，读全文作答也犯（[V9 小说记忆图](novel-memory-v9.md)的评测结论，w00005 t34）。
3. 作者记不住全书，即使上下文无限，也需要整理好的视图（开发者 2026-11-01）。

**旧 WorldEngine 已经是事件溯源**，问题在别处（调研见 [仓库内的现状](../../.agents/works/w00039-novel-writing-plugins/research/2026-10-31-repo-survey.md) 的二、三、五节）：

- 只管世界状态；剧情在剧情工坊，是另一套数据，两边靠无外键的字符串 id 相连。
- 全库唯一的 bigint `instant` 加日历字符串，Agent 门槛高。
- 补写过去时，相对操作（`increment`、`append`）会断，报 `broken-relative`。
- 状态有两份真相源：人物文件说人物是无状态原型，人物模板却带 `state.md`。
- 没有分支，也没有回退。

**三种朴素做法都不够：**

| 做法 | 缺什么 | 后果 |
|---|---|---|
| 一个文件夹，放设定和正文 | 只有原始材料，没有账 | 每次都要翻全部材料，只有上下文无限才行 |
| 不可变的 lorebook（SillyTavern 式） | 只有一张不会变的设定表 | 世界一变就过时 |
| lorebook 加模板引擎 | 在设定表上贴了几个会动的数 | 数从哪来、哪章改的说不清；只管得了数值 |

## 二、目标与非目标

**目标：**

1. 一个系统管设定、状态、剧情计划与情节：它们都是条目和剧情变更。
2. 作者只管说话、看和改；整理与记账由 Agent 做，作者审阅。
3. 任意一章开头或末尾时，每个条目是什么样，都能算出来；每一处变化都有描述和出处。
4. Agent 每一步要读的材料有上限，与书的长度无关。
5. 同一份数据，给作者看界面、给 Agent 读文字。作者能写视图，从而参与 Agent 的上下文。
6. 简单的条目零门槛：只有一段 Markdown 的条目也合法。

**第一版的非目标：**

- 关系、地图、知情与秘密三类 Component（开发者 2026-11-01：方向认可，第一版不做）。
- 世界线与回档，细到天和时段的故事时间（t04）。第一版按“讲于第几章”排序，加一个“前史”。
- 按某个角色的视角渲染（例如按他知道的合并马甲）。
- 第三方 Component 类型：第一版只有内置类型。
- CodeAct 式查询。
- 存储格式（t09）、改稿后的重新记账（t22）、模板新建与旧项目迁移（t12）。
- 与 nb-story 合并：先做作者这边，再看能不能统一。

## 三、当前行为与证据

- **新应用**：
  - 新建作品只建目录和 `.nbook/project.json`，没有设定与剧情模型（[`runtime/projects.md`](../specs/runtime/projects.md)）。
  - 三类文件夹已实现，活页夹 `*.binder/` 归剧情插件，章节编号就是章节的稳定身份（[`workspace/folder-kinds.md`](../specs/workspace/folder-kinds.md)）。
  - nb-form 能按 JSON Schema 画表单，对应 Spec 还是 planned（[`ui/forms.md`](../specs/ui/forms.md)）。
  - nb-profile 用 JSX 写提示词，Profile 文件由 Bun 直接 `import` 执行，没有隔离（`packages/nb-profile/src/loader.ts`）。
  - harness 能把内容作为提醒注入上下文（[`harness/profile.md`](../specs/harness/profile.md)）。
- **nb-story（读者视角）**：
  - 记录有对象、称呼、说法、秘密、知情、情节、状态变动、疑问；每条都有出处；模型只写章草稿，其余由程序生成。
  - 评测结论（w00005 t34）：100 章以内，读全文作答最准；把图当目录、挑章再读原文，能追上全读；用图作答的失分多是照搬了图里记错的内容；Agent 自己挑章时，出处章只挑中 69% 到 79%。
  - 能借鉴的概念：说法的事实、信念、说法三分（按渠道定）；“没有记录”不等于“不知道”；马甲单独建对象再按视角合并；情节之间的连接（在其后、接续、导致、动机、前提）；数值逐笔累加并与原文核对。前四项第一版用不上，留给关系与知情。
- **nb-memory**：
  - 有 episode、facts、主体注册表与状态（带失效区间）；双时间轴：`tick` 是叙事推进序，`instant` 是故事时间；边不是存储对象，涉及两个以上主体的事实就是边；按时刻查询、缺坐标时不可见（fail-closed）（`packages/nb-memory/README.md`）。
  - 与本稿的模型高度相关，取舍见待定项 3。
- **nb-history**：工作区文件的 append-only 操作日志与快照，带用户审查收件箱，可以接受或还原 AI 的修改（`packages/nb-history/README.md`）。可能承担“创作修改”的历史与审阅，见待定项 2。

## 四、方案

### 1. 概念

| 概念 | 意思 |
|---|---|
| 条目 | 设定的单位：人物、组织、地点、物品、概念、剧情线……有 id、名字、别名、一句话描述，在条目树里有一个位置 |
| 条目树 | 作者整理条目的目录。只用来组织和浏览，不表示地理上的包含或组织上的从属 |
| 主 MDX | 每个条目都有的一段 MDX，既是作者写的文字，也是这个条目的主视图 |
| 状态 | 条目上随剧情变化的数据，按命名空间分块。概念上是一份 JSON，怎么存另定 |
| Component | 加在条目上的能力：在状态里申请一个命名空间，并提供 schema、界面与文字视图。分类型与实例 |
| 剧情变更 | 故事里发生的一件事，带描述、讲于第几章、已写或计划、出处、涉及的条目，以及对状态和主 MDX 的补丁 |
| 创作修改 | 作者或 Agent 改的是设定本身（改正、改主意、调整排版），不是故事里发生了什么。只记什么时候、谁改的、为什么 |
| 凭证 | 变更和修改的依据：正文段落、作者手记（原话）、作者在界面上的操作 |
| 记账 | 写完一章后，Agent 读这一章，提出本章的剧情变更，作者审阅 |
| 视图 | 给作者的界面（Vue）与给 Agent 的文字（MDX 渲染） |

### 2. 条目

一个条目由三部分组成：

1. **身份**：id、名字、别名、一句话描述、在条目树里的位置。查询结果里的“名字与描述”取这里。
2. **主 MDX**：作者的文字与排版，可以引用本条目的状态和别的条目的数据。
3. **状态**：按命名空间分块，每个 Component 申请一块（例如 `character`、`panel`）；另有一块自由命名空间，作者随手加字段，不需要 schema（待定项 7）。

主 MDX 和状态都不是 Component，每个条目都有。没有任何 Component 的条目，例如“灵魂宝石”，就只有身份和主 MDX。

几条规则：

- **名字、别名、主 MDX、状态都能随剧情变。** 改名、赐名、外貌变化、数值变化都靠打补丁。
- **主 MDX 不嵌入 Component 的视图。** 每个 Component 的界面在它自己的 Tab 里；主 MDX 只能用表达式引用字段，例如 `{panel.魔力}`（开发者 2026-11-01）。
- **经历不进主 MDX。** 经历就是涉及这个条目的剧情变更，靠检索查。
- **马甲**：第一版不做视角渲染，但星瑕这类人物需要马甲各有自己的面板与所属。推荐做成子条目（待定项 5）。

### 3. 剧情变更日志

全书一条日志，只有一种记录，就是剧情变更。

| 字段 | 意思 | 例子 |
|---|---|---|
| 描述 | 发生了什么，一句或一段自然语言 | 被安上罪名软禁，靠彗做的魔偶逃脱；对外说隐退 |
| 讲于 | 在哪章讲出来；也可以是“前史” | 第 1 章 |
| 状态 | 已写，或计划 | 已写 |
| 出处 | 正文段落、手记段落，或者界面操作 | 正文 1.21–1.30 |
| 涉及 | 涉及的条目 | 星瑕、彗 |
| 剧情线 | 属于哪些剧情线（标签） | 做个好哥哥 |
| 连接 | 可选：在其后、接续、导致、动机、前提（沿用 nb-story 情节的连接） | 导致 c08 |
| 补丁 | 对状态与主 MDX 的修改，可以为空 | `星瑕.panel.魔力 -= 90` |
| 故事时间 | 先留空，t04 启用 | — |

其余几样都从这条日志得到：

- **计划**是状态为“计划”的变更，讲于可以是“未排章”。
- **经历**是变更的描述。
- **剧情线**是标签。
- **剧情表**是按“讲于”和“剧情线”排成的格子（章乘以剧情线）。
- **伏笔**是一条剧情线，最后一步“回收”还在计划状态。

**排序（第一版）：** 按讲于的章序排；同一章里按出处的段落顺序排；“前史”排在第 1 章之前，前史内部按作者给的先后排。已知的代价是：补叙章会被当成发生在讲到它的那一章（开发者 2026-11-01 接受，细的故事时间与世界线放到 t04）。

**剧情变更和创作修改要分开记：**

| | 剧情变更 | 创作修改 |
|---|---|---|
| 例子 | 第 3 章，星瑕花掉两千 | 作者把开局存款从四万改成五万；Agent 调整主 MDX 的排版 |
| 挂在 | 讲于第几章 | 只记什么时候、谁改的 |
| 改变的是 | 某一章以后的状态 | 设定本身，所有位置都跟着变 |

作者在界面上改一个值时，界面要问这是剧情里的变化还是改正；Agent 写入时自己标明。作者和 Agent 的修改都记录在案，并且带描述。Agent 可以直接写作者的文件，这一点不限制（开发者 2026-11-01）。

### 4. 状态怎么算

- **某个位置上的条目 = 初值 + 这个位置之前所有已写变更的补丁。** 初值由创作修改设定，排在前史之前。计划中的变更不算进真相；另有一个“按计划”视图，把计划也加上，用来看“照计划第 N 章会是什么样”。
- **补丁的种类：**
  - 字段：赋值；数值加减；列表增删。
  - 主 MDX 和长文本字段：文本 diff。
- **核对点**：正文里写明的数（例如面板上显示的余额）记成核对点，和累加的结果比，对不上就报。这是 nb-story 数值流水的做法，也替代了旧版 `broken-relative` 那种“断掉”的失败方式。
- **改过去**：改了初值、改了某条变更，或者在中间插进一条，后面的状态都要重算。
  - 文本 diff 用三方合并；合不上时由 Agent 提出合并后的写法，作者确认。
  - 改初值时，把后面改过同一字段的变更列给作者看。程序看不出语义上的过时：初值改成银发了，第 30 章那条“剪成黑色短发”还写着黑色。
- **缓存**：按章存一份状态快照，可以随时重建。

### 5. Component

**类型提供，实例只给数据和配置：**

| 类型提供 | 用途 |
|---|---|
| 命名空间与 schema | 状态里的一块，表单由 schema 画出来 |
| Vue Tab | 作者的界面：表单、图片、分页列表、搜索框之类 |
| 给 Agent 的文字视图 | `read` 这个 Component 时返回的文字 |
| 查询视图 | 带参数的查询，例如情节的分页与检索 |
| 计算字段 | 由别的字段算出来的值，只读 |
| 记账说明 | 写完一章后，记账员要留意这个 Component 的哪些变化 |
| 用法说明 | 以提醒的方式给 Agent，见第 7 节 |

实例只提供这一个条目上的数据与配置，例如这个面板声明了哪些字段。

**按数据放在哪，Component 分三类：**

| 类 | 数据在哪 | 例子 |
|---|---|---|
| 自有数据 | 这个条目的命名空间里 | 人物、面板 |
| 集中数据的视图 | 存在全书集中的地方，Component 只按“这个条目”筛选 | 情节；以后的关系、知情 |
| 自有数据加收集 | 每个条目各存一份，由一个视图统一收集 | 以后的地点加地图（地点存 `place.within`，地图收集所有地点） |

**第一版内置三种，各验证一种用法：**

- **人物**（自有数据，带表单和图片）：本名、性别、外貌、性格、说话方式、立绘等。立绘按形态各存一张，字段清单在 t10 定。
- **面板**（要求精确的数值）：
  - 作者声明字段：数值、上限、枚举、能不能为负；
  - 补丁做加减，正文里写出的数当核对点；
  - Tab 显示当前值和流水。
- **情节**（集中数据的视图）：
  - 不存数据，是剧情变更日志里“涉及本条目”那部分的查询视图。
  - 作者界面：分页；按章、剧情线、已写或计划筛选；关键词与语义检索；“问一句”，调用模型在筛出的结果上回答，每句标出处。
  - Agent 用 `read(条目, view: 情节, query, at, page)` 查。

**还没定的两件事**：去掉一个 Component 时它的数据怎么办，schema 变了以后已有的数据和补丁怎么办（待定项 6）。

### 6. 渲染

- **输入**：条目、位置（某章开头或末尾，或者按计划）、给谁看（作者或 Agent）。以后再加视角与世界线。
- **结果只取决于输入。** 渲染在沙箱里做：不能 `import` 任意模块，不能读写文件，不能联网；只能用表达式和少数内置标签（引用条目、图片）。条目的 MDX 是项目数据，可能来自模板或别人分享的世界观，不能像 Profile 那样直接执行。
- **作者文字里的 `{` 和 `<` 要转义。** 解析失败时显示源码和错误，不挡住作者。
- **给 Agent 的渲染用带值写法 `{路径 = 值}`：**

```text
姓名：{entry.name = 星瑕}
外貌：{character.appearance = "黑色长发，……"}
立绘：{character.portrait = 图片 assets/星瑕/原身.png}
魔力 {panel.魔力 = 3110}/12000 · 存款 {panel.存款 = 41800}
```

| 写法 | 意思 |
|---|---|
| `{路径 = 值}` | 可以直接按这个路径打补丁 |
| `{表达式 = 值}` | 算出来的，只读；要改，就改它依赖的字段 |

  这种写法要能**还原**：去掉 `= 值` 就是源文，所以 Agent 可以直接在渲染结果上改主 MDX，系统把改动对应回源文。能不能做好，在审查时专门查（开发者 2026-11-01）。
- **作者看到的**：主 MDX 渲染出的文字只显示值，鼠标悬停时显示路径；图片直接显示。Agent 拿到的是图片的路径和说明，需要时自己去读图。

### 7. 作者怎么用

- **入口**：通过 NeuroBook 的界面，不直接编辑条目所在的文件夹；直接读写文件留给 Agent（开发者 2026-11-01）。
- **开始一部作品**：
  1. 新建作品，选题材模板或空白。
  2. 把故事种子发给 Agent。Agent 先问几个会挡住开局的问题，然后建条目、记下前史与开局状态、起草剧情线。
  3. 作者审阅：建了哪些条目，记了哪些前史，还有哪些待确认。
- **日常循环**：
  1. 给一章写计划（细纲）；
  2. 和 Agent 讨论、审查；
  3. 写正文；
  4. 记账；
  5. 审阅本章的变更。
- **手动建一个人物（空白条目）**：
  1. 在条目树里新建，填名字和一句话描述；
  2. 加“人物”Component，填表单（填的都是初值，记为创作修改），上传立绘；
  3. 加“面板”Component，声明字段，填初值；
  4. 写主 MDX，或者先留空。
- **按章看**：条目页顶上可以选“第 N 章开头或末尾”，默认是写作进度。

### 8. Agent 怎么用

- **三样基础**：条目树、剧情变更日志、正文。剧情线和章要不要也做成条目，见待定项 4。
- **工具**（第一版，一个工具只做一件事）：
  - `lookup`：按名字和别名查条目，返回名字、位置、描述，以及有哪些 Component；
  - `read`：读一个条目的主 MDX，或者它某个 Component 的视图；参数有位置、查询词、页码；
  - `search`：检索剧情变更与条目文字，可以按章、按涉及的条目过滤，兜底 Component 视图漏掉的东西；
  - `tree`：看条目树；
  - 写入：记一条剧情变更，或者做一次创作修改，都带描述。
- **自动预查**：用户消息里出现已知的名字或别名时，系统先查一遍，把结果当目录注入：名字、位置、描述、有哪些 Component。没找到的词也列出来，它们可能是这一章新引入的设定，也可能是写错了名字。
- **Component 用法以提醒的方式给**：harness 记下当前上下文里已经有哪些 Component 的说明，只在三种时候注入一次：第一次出现时、离上次给出已经隔了一定 token 时、上下文压缩之后。不放进系统提示词，也不随每次查询重复（开发者 2026-11-01）。
- **位置参数的默认值**：讨论或审查第 N 章的计划时，取“第 N 章开头”；记账时取“第 N 章末尾”。
- **审查细纲**：分三类检查，结论都指向具体的条目或变更：
  - 吃书：和已写的正文冲突；
  - 吃设定：和条目里的设定冲突；
  - 严谨：逻辑和动机说不通。

  审查时顺带列出“这一章会产生的变更”，就是第 N 章的计划中变更。
- **记账**：
  - 读本章正文、涉及条目的状态，以及本章计划中的变更；
  - 提出本章的变更：兑现了哪些计划，哪些超出计划，核对点对不对；
  - 作者审阅。

  记账沿用 nb-story 的一条规则：角色说的、想的不算世界的变化，第二版记成知情。
- **写手的上下文**：第 N 章的计划，涉及条目在第 N 章开头的渲染，最近一两章的正文，再加按需检索。要读的量与书的长度无关。

### 10. 备选方案与取舍

| 方案 | 结论 | 理由 |
|---|---|---|
| 与 nb-story 合成三个来源层（正文、设定、计划），再加对齐 | 否决（开发者 10-31） | 两种视角出发点不同，对齐太复杂；先做作者这边 |
| 只靠作者的手记与笔记，不要结构 | 否决（开发者 11-01） | 没有无限上下文；作者记不住全书，也需要视图 |
| 程序往作者的文件里写卡片 | 否决（开发者 11-01） | 改用 MDX 模板，渲染只在显示时做 |
| 七种账（立、事、变、知、计、疑、正） | 合成一种剧情变更 | 种类多了，记账员和作者都要先分类；一条记录加补丁就够 |
| 数据存在 Component 里（经典 ECS） | 不采用 | 补丁要有统一的地址；主 MDX 要跨命名空间引用；增删 Component 不必搬数据 |
| 主 MDX 只有创作修改，不随剧情改 | 否决（开发者 11-01） | MDX 也能打补丁，文本 diff 用三方合并 |
| Component 往主 MDX 里嵌视图（卡片、`<Panel/>`） | 第一版不做（开发者 11-01） | 各自在 Tab 里，各司其职；有实际需求再加 |
| Component 用法写进系统提示词，或者每次查询都附带 | 都不采用（开发者 11-01） | 前者占上下文、长对话里会忘；后者重复；改成提醒 |
| CodeAct 查询 | 第一版不做 | 先用视图加检索，评测显示不够再加 |
| 关系存在其中一边 | 改为：多值、各有状态的存成集中的边，单值的存成字段（第二版） | 关系是全书性的，放在某个人身上不妥（开发者 11-01） |

## 五、影响

- **数据**：新的项目数据有条目、状态、剧情变更、创作修改和作者手记。存储形态待定（t09）。
- **接口**：给 Agent 五个工具；Component 类型的接口第一版只给内置类型用，以后开放给插件。
- **安全**：
  - 条目的 MDX 可能来自模板和别人分享的世界观，渲染必须在沙箱里做。
  - Agent 能直接写作者的文件，靠修改历史与作者审阅兜底。
- **迁移**：v2 还没有用户数据。旧项目的 lorebook、WorldEngine、剧情工坊怎么迁过来，在 t12 讨论。
- **成本**：每章记账一次模型调用，量级参照 nb-story 的抽取；检索要算嵌入。
- **发布与回滚**：作为新插件发布，草案阶段不影响现有功能。

## 七、待定项

1. **名字。** 候选：法典、canon、WorldEngine。推荐中文叫“法典”、英文用 canon，避开和 OpenAI Codex 撞名的 codex。
2. **存储形态**（t09）。推荐先定模型、再定存储。
   - 候选有两种：文件加数据库索引；或者全部放进数据库。
   - nb-history 能否承担创作修改的历史与作者审阅，审查时一并看。
3. **与 nb-memory 的关系。** 它已经有双时间轴、带失效区间的状态，以及缺坐标时不可见（fail-closed）。推荐借用它的这些做法，但不直接依赖它的存储与写入流程，原因是它每批写入都要把主体注册表全量放进上下文做消解，书长了会超。审查时专门对照。
4. **剧情线和章要不要也做成条目。** 推荐做成条目：Agent 查剧情和查设定用同一套 `lookup` 和 `read`；章就是活页夹里的那一项。
5. **马甲的做法。** 推荐做成子条目，父子关系就表示“身份同一”。另一种是 nb-story 的做法：同级的两个条目，再加一条“身份同一”的连接。
6. **去掉 Component、schema 变化。** 推荐：去掉 Component 时数据保留、隐藏起来，可以恢复；schema 带版本号，改字段名时生成一条创作修改，把旧数据迁过去。旧版 Zod schema 没有版本与迁移，是调研里记下的痛点之一。
7. **自由命名空间要不要。** 推荐要：作者想随手记一个字段时，不必先加 Component。
8. **记账结果怎么审阅。** 推荐整章一起接受，每条都可以单独驳回；有疑问的条目进待确认，沿用 nb-story 修订的待确认机制。
9. **自动预查怎么匹配。** 推荐第一版只按名字与别名精确匹配，语义检索交给 Agent 自己调 `search`。
10. **计算字段与历法。** 推荐第一版不做历法，年龄先当普通字段，由作者或记账员修改；历法在 t04。
11. **带值渲染能否做到可还原。** 审查时专门查（开发者 2026-11-01）。
