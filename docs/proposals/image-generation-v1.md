# 图像生成第一版：工作台、配方与标签库

给 NeuroBook 加文生图的第一版：作者在编辑区里的提示词工作台上搭提示词、抽卡、挑图，把好图收藏或收进书里。本稿把 [w00042](../../.agents/works/w00042-image-generation/README.md) 到 2026-11-10 为止开发者定下的决定连同取舍收到一处：
- 提示词工作台四轮静态稿的 22 条（[t07](../../.agents/works/w00042-image-generation/tasks/t07-prompt-workbench/README.md#已定)）；
- 提示词与配方的能力地图与假设；
- 产物管理、模型灵活度与图片存储三次讨论（[t03](../../.agents/works/w00042-image-generation/tasks/t03-core-contracts/README.md#产物管理与模型灵活度2026-11-10-开发者都按推荐)）。

插图方言与生图管线（t09、t10）、Agent 工具（t08）、角色视觉档案（t11）、局部重绘（t12）各自另写，本稿只给它们留接口。

## 问题

1. **生图在写作软件之外，产物会丢。** 作者现在在 NovelAI 网页版或法典图鉴这类站点上搭提示词，靠复制粘贴拼进输入框。NovelAI 网页版的历史只在页面会话里，刷新即清空；参数只写在下载的文件里。抽到的好图、它的提示词、它配的是哪一章，全靠作者手工对应。
2. **提示词有结构，输入框没有。** 一半的 V5 社区提示词用空行分节，有人写 `<style>` 标记；画风串整段复制到很多张图里；负面从几份流传的“标准负面”出发各自增删（[社区提示词的结构](../../.agents/works/w00042-image-generation/research/2026-11-10-community-prompt-structure.md)）。复用靠复制，改进一处要改很多处。
3. **标签难找、难懂、写法乱。** 标签是英文的 Danbooru 词，作者多半用中文想画面；权重写法从数括号变成写数值；社区提示词里重复的词、下划线写法、SD 写法、没闭合的权重都很常见。
4. **产物多到管不住。** 一下午几百张，几个月几 GB 到二十几 GB（纸面模拟的估计，没有实测，见[模拟](../../.agents/works/w00042-image-generation/research/2026-11-10-artifacts-and-model-stress-test.md)）。大部分是失败品，少数好图要留，进书的图要跟着书走；清理时不能把要用的图连带清掉。

## 目标与非目标

**目标（第一版）**

- **提示词工作台：** 编辑区里一个标签页编辑一份配方；提示词按节组织，预设是引用加差异，有片段与风格组合；结果与历史在右边。
- **标签系统：** 中文、英文、别名都能搜的打字联想；标签块（一词一块，下面一行中文，权重按数值）；体检；粘贴拆到各节；相近的词。
- **生成：** 首发后端（推荐 NovelAI，取决于 t02），全局排队，取消与失败，费用估算。
- **产物：** 书里的生成记录与缩略图；应用级的图片仓库与空间管理；收藏与收藏夹；书里的插图；图库页。
- **数据形状一次定对：** 以后加 LoRA、参考图、“几选一”、插图方言、别的后端时，不用迁移已有的配方、预设与记录。每种持久格式带版本号，规则见“影响”。

**非目标**

- 插图方言与生图管线（t09、t10）。本稿只定书里的图长什么样（`.image` 文件夹），正文怎么引用另写。
- Agent 工具（t08）。本稿只保证三件事：配方、预设、片段是 Agent 用文件工具读得懂的文件；检查结果是可序列化的数据；检索条件与图库共用一种结构。工具本身另写。
- 角色视觉档案（t11）；局部重绘、放大与它们的谱系（t12）。
- “只换画风”的对比抽卡：开发者 11-10 定第一版不做，要比画风时固定种子、换风格组合再生成。
- 自然语言类后端（gpt-image 等）；ComfyUI 与 SD 的 LoRA、区域提示词。
- 收藏跨机器同步、按画面内容找图、导出细则、按新设定自动重出。

## 方案

### 1. 插件、进程与数据放在哪

一个内置插件（暂名 `nbook.images`），依赖凭据插件 `nbook.credentials`（t04）。它就是 Work 决定里“按媒介各设一个门面”的图像那一个。

几块（提示词模型、配方、标签库、生成、图片库、工作台）共用同一套数据形状。现在拆成几个插件，只会多出插件之间的合同，而且还没有独立的第二个使用方；等 Agent 工具或别的后端插件要单独用某一块时再拆。本稿用到的都是平台公开的能力，第三方插件同样做得到（[ADR 0027](../adr/0027-builtin-and-third-party-plugins-are-equal.md)）。

| 运行位置 | 持有什么 |
|---|---|
| 服务端 | 后端调用（凭据只在服务端）、全局生成队列、图片仓库 `user://images/`（原图、缩略图、本机记录、内容快照、收藏）、收进书里的复制、标签库查询、空间管理 |
| 项目实例 | 书里的记录副本、快照与缩略图，对账，本书的 id 索引；配方、预设、片段是普通文件，经文件服务读写 |
| 浏览器 | 工作台编辑器、侧栏词库、图库页、设置里的“图片空间”、`.image` 文件夹在资源管理器里的显示 |

**谁是主人。**

| 数据 | 主人 | 放在哪 | 跟着书走 | 进 Git |
|---|---|---|---|---|
| 配方、本书的预设与片段、风格组合 | 书 | 作品目录里看得见的文件 | 是 | 是 |
| 书里的图 | 书 | 作品目录里的 `.image` 文件夹，缺省放 `插图/` | 是 | 是，建议用 LFS |
| 这台机器上生成的每一批，以及之后的标记（收藏、扔掉、看过、原图在不在） | 生成它的那台机器的仓库 | `user://images/` | 否 | 不在书里 |
| 上一行里属于这本书的全部记录行的副本 | 只是副本 | 记录 `.nbook/images/log/<安装 id>/`、内容快照 `.nbook/images/snapshots/`、缩略图 `.nbook/images/thumbs/` | 是 | 记录与快照建议提交，缩略图可选 |
| 我的预设库 | 用户 | `user://` | 否 | 不在书里 |
| 标签库 | 应用 | t05 定 | 否 | 不在书里 |
| 凭据 | 凭据插件 | `<状态根>/agent/credentials.db`（t04） | 否 | 不在书里 |

每台机器只写自己那份副本（按安装 id 分目录）。书拷到另一台机器上，别的机器的副本只读：能看缩略图、能恢复配方；原图不在本机，所以不能收藏、不能收进书里，角标写“不在本机”，和本机的“原图已清”分开。

**结果怎么进书：对账，不靠推送。** 原则同[多实例运行时拓扑](multi-instance-runtime-topology.md)“文生图”一例：不跨存储做事务，靠记录的状态与幂等处理，保证结果终将落进书里。做法比它更简单，不另设待交付记录：

1. 仓库里的记录是一行一件事，每行带安装 id 与一个按安装递增的序号。入队时记“排队”（带项目 id 与配方快照）；调后端之前记“已提交”；拿到结果，写原图与缩略图，再记“完成”；失败、取消、扔掉、撤销扔掉、原图已清、收进书里也各记一行。服务端重启时，还停在“排队”或“已提交”的批次记为“中断”，费用可能已经扣了，照样显示。
2. 项目入口对账：书里这台机器那份副本的最后一个序号就是游标，向服务端要“本书、序号大于游标”的行，按顺序先写缩略图与快照、再追加记录行。按“安装 id 加序号”去重，所以补几次都只进一次；同一本书的对账在项目入口里一次只跑一个。行多时分页取，每页不超过单条消息的上限（缩略图约 10 KB 一张，一页几十张）。复制到“扔掉的图原图已清”这一行时，项目入口顺手删掉书里它的缩略图。写到一半被强制结束留下的半行，照 canon 世界日志的做法处理（截掉、另存、写诊断）。
3. 什么时候对账：项目入口激活时；工作台或图库读历史时（先给出副本里已有的，补齐后再刷新，不等对账）；项目运行期间服务端推“有新记录”时。失败就等下一次。

所以关掉所有窗口、项目停了、宽限期里又回来、服务端重启，批次都会在下一次读历史时进书。仓库的记录本身就是“待交付”，不需要确认与退役；书移出书架也不留下没人收的记录。

**字节不走远程消息。** 原图不经远程服务传（单条消息上限 1 MiB）。缩略图很小（长边 256 像素的 WebP，约 10 KB），对账时随记录成批交给项目入口；仓库里的缩略图不清，书在对账之前原图就被清掉，也照样拿得到缩略图。“收进书里”由服务端做：项目实例的文件服务只管本书，读不到 `user://`，服务端两边都能写。服务端先临时钉住原图、核对哈希，再经文件服务的写入接口写进 `projects://` 下的这本书。缩略图由服务端生成，用哪个库在实施计划里选（候选是 sharp 与 WebAssembly 的 jsquash；`packages/neuro-book` 现在没有图片处理库）。

**机器的身份。** 副本按安装 id 分目录，两台机器经 Git 或同步盘共用一本书时不写同一个文件。安装 id 由插件第一次运行时生成，存成 `user://images/` 里的一个小文件；这个文件被删了，从仓库自己的记录行里找回，不另生成新 id。不放 Storage，因为共享的 Storage 记录以后要跨设备同步（[同步提案](storage-service-and-sync.md)），几台机器会拿到同一个 id。现有文档与代码里没有现成的机器身份。把整个状态根拷到另一台机器，会带着同一个 id；两台机器同一天都生成过时，同一个文件会有合并冲突，按行合并即可。

### 2. 提示词模型

- **一段提示词是一串项。** 项有三种：词、句子、片段引用。每项带自己的数值权重，可以为负，缺省是 1。第一版的项都是文字；数据上留出“不是文字的项”，以后放 LoRA、参考图。
- **不是括号树。** NovelAI 的花括号、方括号每层乘或除 1.05，可以不配对，可以跨半句话（[权重语法](../../.agents/works/w00042-image-generation/research/2026-11-06-tag-sources-and-novelai.md#权重语法)）。读入时按 NovelAI 的规则把每个词的实际权重算出来。
- **每一节自成一段。** 一节的文字不依赖别的节里开着的括号。
  - 写出时一律闭合，不写连写的数值权重（`1.6::甲, -1::乙` 这种），所以写出不依赖 t02 对连写语义的测试。
  - 一节的原文本身是闭合的、又没改过时，原样写回；否则按规范写法写出。
  - 原文里一个权重跨了几节（约 36% 的社区提示词如此），拆节时按每个词的实际权重切开，每节各自闭合。
- **两种读法。**
  - 粘贴的文字缺省按 NovelAI 读：圆括号是普通字符。Danbooru 本来就有很多带圆括号的标签名，例如 `saber (fate)`。
  - 识别到 SD 的 `(词:1.2)` 写法，或者作者选“这是 SD 写法”时，才按 SD 读：圆括号乘 1.1，方括号除以 1.1，`\(` 是字面的括号。
  - 预览里写明按哪种读的。
- **随机写法** `||a|b||`（NovelAI 的 Prompt Randomizer）是一种项，每个选项是一串项。
  - 抽签在本地按张做，生成记录按张记抽到的文字。
  - 选项是半个词或带着权重前缀、拆不成项时，这一节整段按原文保存、不拆，体检提示一句。
- **图中文字**（NovelAI 的 `Text:`）单独一项。
  - 内容里的空行是文字的一部分，粘贴拆节时 `Text:` 之后到末尾都归它，不按段落拆。
  - 展开时总放在主提示词最末。官方文档要求它在最末，否则后面的词可能被画成文字。
  - 角色框里也可以有自己的图中文字。
- **只靠语法能查出的毛病：** 权重没闭合、重复的词、下划线写法、SD 写法混进 NovelAI 文字、界面设置混进提示词。

### 3. 配方、节、预设、片段

| 概念 | 是什么 |
|---|---|
| 配方 | 一张图“要生成什么”，由四部分组成：有序的节、角色框、参数（含尺寸、张数、种子）、底图（预留：源图、遮罩、强度）。配方是作品里的一个文件，带 id，打开就是工作台标签页。配方不存历史 |
| 节 | 文字提示词按用途分的格子，生成时按顺序拼成主提示词或负面提示词。角色框与参数不是节 |
| 角色框 | 一个角色（或一个物体、一格分镜）自己的正面与负面提示词，对应 NovelAI 的角色提示词 |
| 预设 | 一种节或参数的一份有名字的内容，被引用后再记自己的改动 |
| 风格组合 | 一组预设，一次套上 |
| 片段 | 有名字的一小组词，哪一节都能嵌 |

**节。** 种类由系统定：主体、画风、质量、内容（原叫“场景与构图”）、自然语言、通用、负面。

- 同一种节可以有几个，可以起名，例如“服装”“光照”两个内容节；负面缺省分官方段、我的负面、要避开的画师三节。
- 新建的配方每种一节。多个同种节，只在作者自己加、或粘贴时为了保住词序才出现。
- 节和项都可以临时停用。
- “通用”节不参与“放错节”的检查。

**角色框。** 每个角色框有自己的正面与负面（NovelAI 叫角色的 Undesired Content），可以装文字、物体或一格分镜，标题可改。主体数量只按开头是 `girl`、`boy`、`other` 的角色框自动填。

**预设。** 画风、质量、负面三种节与参数能套。预设挂在具体的某一节上（按节的 id），一节最多一个。

- **项怎么认：** 一节里的项按规范化后的文字认（大小写、下划线与空格不计）。同一个词出现两次是体检要提示的毛病；万一出现，按出现的先后区分。改权重算“改值”，不算去了再加。
- **差异：** 配方记着引用了哪个预设、在上面改了哪几项。改动只有三种：加一项（记着加在哪一项后面，那一项没了就加到末尾）、去一项、改值。
- **更新预设只写预设文件，从不改配方文件。** 写回前列出受影响的配方：没改过那一项的跟着变，自己改过的保持自己的值，因为差异本来就存在各自的配方里。预设里已经没了的项，针对它的改动在配方打开或展开时算作作废，在那份配方的工作台里提示一次；不为此去写别的配方文件，也就不会和别的标签页撞磁盘冲突。
- **节上的三个动作：** 还原（去掉全部差异）、另存为新预设、更新预设（t07“已定”11）。
- **换预设：** 给一节换预设时，差异照“更新预设”的规则处理。
- **其它：**
  - 预设记着在哪个模型上调的，配方换了模型时对不上的节提示一句，不拦。
  - 参数预设不含尺寸、张数、种子。
  - 画风预设的样图从结果里挑一张，在预设里存一份缩小的副本。
  - “压制”是画风节里权重为负的项。词进哪一节看词的类别，不看权重的正负：`-1::hat::` 是去掉帽子，属于内容。

**风格组合。** 一组“节的种类与名字，对应一个预设”，外加一个参数预设。套组合时，每个预设挂到同种同名的节；没有同名的，挂到同种的第一节；没有同种的，新建一节。负面的三节可以各有一个预设，所以“要避开的画师”能随画风一起换。“本书默认”就是默认的那个组合，新配方从它开始。

数据支持把这几样绑在一起：画师相同的两条社区提示词，负面里的画师、压制词、质量词、采样参数有 61% 到 98% 也相同，随机两条只有 1% 到 34%。

**片段。**

- 核心词加陪衬词，陪衬词可以不带；用途是固定的一组，和文件夹分开。
- 一个片段可以分成几段：主提示词一段，加对应各角色框的几段。法典里三成的片段带角色框的内容。
- 片段是引用，只记关掉了哪几个陪衬词，不加差异层；要大改就拆开成普通词。

**书与预设库。**

- 预设、片段、风格组合跟着书走，配方只引用本书里的。
- 另有跨书的“我的预设库”（`user://`；原叫“我的书架”，和书架页重名所以改名）。拿进书里是复制一份，并记下来源。
- 官方预设每本书直接可用，只读。

**展开。** 点“生成”时：

1. 每一节如果引用了预设，先取预设的内容，按项套上配方自己的差异；
2. 片段展开成词，去掉关掉的陪衬词，去掉停用的项与节；
3. 按节的顺序排成主提示词与负面提示词的项序列，图中文字放最末；角色框各自展开正面与负面；
4. 交给后端适配器写成该后端的写法（第 5 节）；随机写法按张抽签；
5. 入队时记进仓库：这一批展开后的每一节；配方当时的样子（引用、差异、片段、随机写法的原文、停用的项）；所引用的预设与片段的内容。后两样以内容快照存，按哈希去重。再经对账进书（第 1 节、第 6 节）。

恢复与收藏都从快照取“当时的内容”，不依赖预设与片段现在还在不在。

**备选与取舍**

- **节的种类与个数。**
  - 每种只能一个：拆进各节再拼回，词序不变的社区提示词只有 5% 到 10%。
  - 种类由用户自定义：体检、粘贴拆分、联想、跨书复制、Agent 都要先知道“这一节是什么意思”，种类由用户造，这些都会失去依据。
  - 取“种类固定、同种可以多个”。数据从第一版起就是有序列表。
- **套预设是复制还是引用。** 复制以后改进画风要改每一份配方；取引用加差异。约九成的负面、八成的画风节离另一条不超过 5 项，差异读得懂。
- **一份预设跨几节，还是组合。** 一份预设跨几节，会让差异、更新确认、预设库复制都复杂很多；组合只是一组引用。
- **片段要不要差异层。** 被改着用的片段约一半，但片段只有十几个词，拆开成普通词比维护差异便宜。

### 4. 标签系统

- **标签库**（t05）：
  - Danbooru 的基础数据：类别、使用次数、别名，起步用 tagcomplete 的数据（MIT）。并入 NovelAI 官方的特殊标签、改名表、各模型自动追加的质量词与负面预设。
  - 中文名第一版必带：标签块下面那行中文和中文联想都靠它。
  - 相近的词（同组、常一起出现）第一版要；来源与授权见“待定项”。
  - 构建时拉取数据，运行时不依赖外部站点。NovelAI 的 `suggest-tags` 作在线增强，能不能用等 t02。
  - 使用次数是 Danbooru 的图片数，只作粗略参考；模型认不认识一个词，不能靠它判断。
  - 成人标签不隐藏；涉及未成年人性内容的标签在构建时去掉。排除规则（按 Danbooru 的标签组加一份维护在仓库里的词表）随构建脚本一起由 t05 维护，写进 `images/tags`。
- **打字联想：** 中文、英文、别名都能搜，片段在同一个列表里；选到属于别的节的词（例如画师），放进同种的节，当前节是同种或“通用”节时留在原处。
- **标签块：** 一词一块，下面一行中文，权重写成倍率；同一权重的几个词合成组框；每个提示词框可以切回原文。块上的操作：改权重（数值，可以为负）、压掉、相近的词、移到负面、收藏这个词、删除。
- **体检：** 第 2 节的语法毛病，加上要用词库才能查的：没收录、放错节、别名、改名表里的旧名。本地检查，不调模型；能自动改的一键整理。检查结果是可序列化的数据，界面画的就是这份数据，以后 Agent 工具拿到的也是它。
- **粘贴拆到各节：**
  - 一次收整套：主提示词、负面、角色框与角色负面（认 `|` 分角色的写法）、参数。
  - 默认按原文的段落分节、保住词序（实测中位拆成 3 到 4 节，约两成的词落进“通用”节）；勾“存成画风预设”时，才把画风词归拢成一节，并提示要挪动几个词。
  - 负面先和已有的预设比，差得少时提议“套用加改动”。
  - 把 NovelAI 生成的图拖进来，读图里的元数据，走同一张预览。

### 5. 生成

- **后端适配器**是展开与后端之间唯一的一层。它负责：
  - 声明能力：模型与档位、权重写法（花括号、数值、负数）、角色框与角色负面、图中文字、尺寸与张数的范围、提示词上限；
  - 把展开后的项序列写成本后端的写法；
  - 提交、取消、查进度；
  - 交回原图与元数据；
  - 估算费用。

  展开交给适配器的是与后端无关的“词加权重”，所以以后接 SD 或 ComfyUI 只是加一个适配器。后端不支持的写法（例如 V4 以前不认数值权重、不认负权重）在工作台上提示，并说明会怎么降级。
- **能力细到“模型加档位”：** 例如 V5 Full 的 Medium 档固定步数与采样器，不能自定义负面。配方换模型时，对不上的节提示一句，不拦。
- **NovelAI 自带的负面预设：** 负面的“官方段”就是要发出去的文字，请求里不再让 NovelAI 自己加负面预设，免得重复。质量词同理。
- **全局队列：** 点生成时拿当时的配方内容（含没保存的修改）入队，关掉标签页或窗口都不丢结果（第 1 节的对账）；状态栏显示进行中与排队的批次。
- **取消、失败、部分失败**都写进生成记录。
- **费用：** 生成前显示估算，记录里记实际花费。Opus 订阅免费的范围等 t02。
- **首发后端：** 推荐 NovelAI，等 t02 用真实令牌验证。

### 6. 产物：生成记录、图片仓库、收藏与书里的图

- **生成记录。** 主人是仓库里的本机记录，书里是副本（第 1 节）。每一批记：
  - 来源：项目 id、配方 id，以后加管线的请求与 Agent 会话；
  - 每一节展开后的内容，连同节的 id、种类与名字；
  - 配方当时样子的快照哈希；
  - 参数、模型、每张的种子、抽到的随机选项、图片哈希、状态（已提交、完成、失败、取消、中断）、费用。

  规则：
  - 只追加，按天分文件。
  - 内容快照（配方当时的样子、所引用预设与片段的内容）按哈希命名、去重，仓库与书里各存一份；同一份配方连抽几十批，快照只存一份。
  - 配方文件里不存历史。
- **图片仓库**（本机，`user://images/`）：
  - 这台机器上生成的全部原图，按 SHA-256 命名，按哈希前两位分子目录，同一张只存一份。原图保持后端交回的字节，不改；NovelAI 写在图里的元数据留作备份。
  - 每张原图有一张缩略图。
  - 本机记录、内容快照、收藏、安装 id。
  - 浏览器经 `user://` 现成的读字节路由取图，同源检查与上限照旧。书里 `.nbook/images/thumbs/` 的缩略图读字节路由读不到（控制目录一律 404），只在本机没有那张原图时用（例如换了机器），由项目入口经远程服务成批交给浏览器，每批不超过单条消息的上限。
  - 资源管理器的“用户资产”根（缺省折叠）下看得到 `images/`，Agent 也读得到。仓库只认“文件名等于内容哈希”的原图与缩略图：不见了的算“原图已清”；别人放进来的、改了名的、改了字节的不认，在“图片空间”里列为“不认识的文件”；收进书里前再核一次哈希。
  - 原图、缩略图、本机记录与快照量大或只追加，要排除在改动记账之外，否则每张图多存一份；收藏是每张一个小文件，照常记账，误删了能恢复。见“待定项”6。
- **收藏**是应用级的：
  - 收藏的图在仓库里钉住，出现在跨书的“我的收藏”里，书删了也还在。
  - 收藏时把它的完整来历写进收藏文件：那一批的展开内容与配方快照、所引用预设与片段的内容、来自哪本书哪份配方。
  - 第一版只存本机，另提供“导出收藏”：文件名可读，附来历说明。跨机器同步等平台的[同步提案](storage-service-and-sync.md)。
  - 备份 `<状态根>/user/` 就带上了收藏，而凭据库在 `<状态根>/agent/`，不会被一起带走。
- **书里的图。**
  - 一张图一个 `.image` 文件夹，里面是各个版本（`v1.png`、`v2.png`……）与 `image.json`（id、说明、当前版本、各版本的来历快照）。
  - 文件夹名在创建时定，之后不随说明改：插件界面里的“改名”只改 `image.json` 里的说明。在资源管理器里改名或移动，按 id 的引用不受影响；按路径的引用（第一版 canon 的定妆图）会断，和今天 canon 引用任何一张图片一样。
  - 资源管理器把它显示成一张图，靠的是[文件夹类型](../specs/workspace/folder-kinds.md)写明的“渲染贡献点”。这一点规范里有，实现里没搜到（`FolderKind` 是写死的三种），见“待定项”7；没有它时 `.image` 按普通文件夹显示，照样能用。
- **怎么收进书里。** 只经插件自己的动作：用作插图、设为定妆图、设为配方的源图或参考图、收进书里。服务端先把原图复制进 `.image` 文件夹，再写引用。别处（canon、正文）本来就只能引用作品目录里的文件，引用不到仓库里的图。收藏的图拿到别的书里用，也是复制进那本书。同一张图在仓库和书里各一份，是有意的。
- **引用一律按 id。**
  - 配方、预设、片段、风格组合、书里的图都带 id，只在本书里唯一；拷到别的书时 id 跟着走。
  - 项目入口在激活时扫描本书，之后跟着文件变化，维护一份“id 到路径”的索引，记着每个 id 上次在哪。
  - 资源管理器、文件管理器或 Git 复制出重复的 id 时：路径和索引对得上的是原件，另一份由插件换新 id。索引里没有记录时（第一次扫描、换了机器），先不动，等作者打开其中一份时问一句。
  - 两台机器各自给同一份副本换了不同的新 id，经 Git 合并会冲突，由作者选一个；这是已知的限制。
  - 插件自己的“复制配方”直接给新 id。具体规则在 `images/recipes` 与 `images/library`。
- **扔掉。** “删掉这张”只是在仓库里标成扔掉，并同步进书里的副本：历史里不再显示；清理时排最前，不受 7 天保护；原图要等下一次清理才真正删，在那之前可以撤销。所以扔掉不会马上腾出空间，手动清理里可以单选“清掉扔掉的”。扔掉的图原图被清时，书里它的缩略图也一并删掉。
- **历史与恢复。**
  - 结果区默认显示最近一批。
  - 历史缩略图带按天分段，带角标（收藏、在书里、花过点数、原图已清、不在本机），可以只看收藏的。
  - 点一批只看那批图；“恢复这批的配方”另有一个按钮，先显示和当前配方的差异；恢复是编辑器里可撤销的一次编辑。
  - 恢复时仍引用原来的预设，差异按快照里当时的内容重算；预设或片段已经没了，按快照恢复成普通词，并提示一句。
- **图库页。** 编辑区里的一个页面标签，一本书一个。全书的图按天分段排成网格，按配方（含已删除的）、日期、状态筛选。检索条件是一种可序列化的数据类型，以后 Agent 工具用同一种。

- **怎么组织与检索**（开发者 11-10 定）。
  - 仓库平铺、按内容哈希存，由程序管理，作者不在里面分目录。理由：抽出来的九成以上是失败品，没人整理；作者在里面挪文件，仓库就认不出图；一张图常常要属于几组，文件夹只能放一处。
  - 用进书里的图，在书的目录里管，层级随作者建，例如“插图/第一卷/”“角色/林夏/”；`.image` 文件夹挪到哪都不影响按 id 的引用。
  - 收藏的图用收藏夹分组，第一版就做：收藏夹有名字，一张图可以在几个收藏夹里，记在收藏文件里，不是磁盘上的文件夹；导出时按收藏夹生成真实的文件夹。按规则自动归类的智能收藏夹以后做。
  - 失败品不整理，用视图找：图库页的筛选与按提示词搜。
  - Agent 不读仓库目录，用 t08 的检索工具。条件与图库页同一套：书、配方、日期、状态、收藏夹、模型、提示词里的词。中文先经标签库换成标签再查，查不到的按原文匹配。返回的是记录（图的 id、来自哪本书哪份配方、按节的提示词、收藏夹），要看画面再按需取缩略图。检索用的索引由本机记录生成，可以删、可以重建，不是又一份真相。书里的图，Agent 用文件工具浏览书的目录即可，`image.json` 里有说明、版本与来历。

一张图生成以后的去向：

1. **生成：** 原图进仓库，仓库记一行；下一次对账时书里补上记录与缩略图。
2. **收藏：** 在仓库里钉住，进“我的收藏”。
3. **用作插图，或被插件的动作引用：** 服务端把它复制进书里的 `.image` 文件夹。
4. **什么都不做：** 算失败品，到空间上限时按顺序清掉。
5. **扔掉：** 下一次清理时删，之前可以撤销。

原图被清掉以后，书里的缩略图与记录还在：能看到抽过什么，能恢复配方，只是没有原图。

### 7. 空间管理

照 Telegram 的“存储用量”。设置里一个“图片空间”分区（page 分区，[设置窗口](../specs/settings/settings-window.md)）：

- **占用：** 分可清理的原图、收藏、缩略图三块，另列“不认识的文件”。书里的图属于书，不在这里显示，也不归这里清：要算它们得打开每一本书。
- **按书列出：** 按原图来自哪本书算，每本占多少、最早的图是哪天的，可以单清一本；已移出书架的书单列一组。一张原图只属于生成它的那本书。
- **只有一个开关：上限。** 缺省 40 GB，只管没收藏的原图；测试与实施可以经启动参数设到很小。收藏与书里的图不会被自动删，所以不放进会自动清的上限里，占用单独显示。
- **到上限自动清：**
  - 顺序：先清扔掉的（不受 7 天保护）；再按最久没看过的顺序，清没收藏、不在保护期的，清到上限的九成。
  - 受保护、不清：最近 7 天生成的、等审阅的候选（t10）。能清的都清完了还超上限，只提示。
  - 状态栏提示一次清了多少。
  - 也可以手动清：按书、按时间、只清扔掉的，先预览再确认。
- **看过：** 在工作台的结果区、灯箱或图库里显示过原图（缩略图不算）。浏览器报给服务端，同一张图一天最多记一次，攒一批再写。
- **并发：** 清理、收进书里、收藏都在服务端，同一把锁里做；收进书里复制期间临时钉住原图。正在看的旧图被清掉时，界面退回缩略图。
- **换盘：** 第一版要把图片挪到别的盘，就整个挪状态根（启动参数 `--state-root` 或环境变量 `NBOOK_STATE_ROOT`）。只把 `user://images/` 换成指向别处的链接不行：读字节路由会按“越出根”拒绝。单独给仓库选位置以后再做。

和 Telegram 的不同：Telegram 清掉的缓存能从云端重新下载，这里清掉的原图就没了；同一个种子能不能重新抽出同一张图，要等 t02 实测。所以有三样补偿：7 天的保护期；扔掉可以撤销；收藏键一按，好图就不会被清。主题素材的清理每次都先列名单、等用户确认；这里按开发者的要求到上限自动清，差别在于这里的量大、频繁，每次都确认作者会烦。

按模拟的用量估计，40 GB 在重度抽卡下约能存 5 个月，角色设计约 1 年，连载配图好几年。书里的缩略图在重度抽卡下三个月约 150 MB；扔掉的图的缩略图随原图清掉，留下的会少一些。

**留给 `images/library` 的机制。** 设计审查第 3 轮指出的这些，结构不变，在 Spec 里逐条定，每条后面是方向：

- **引用由谁写：** 服务端只负责把图复制进 `.image` 文件夹，交回它的 id 与路径；引用由发起方自己写。配方的源图与参考图，是工作台对打开着的文档做一次编辑，不撞磁盘冲突；定妆图经 canon 自己的接口写；正文的插图随 t09。复制成功、引用失败时留下的 `.image` 算“没用到的插图”，在图库里看得到。锁只管仓库里的钉住，不跨着另一个进程的提交。
- **仓库记录坏了：** 半行与坏行照 canon 世界日志的做法；写完原图、还没记“完成”就崩溃留下的原图，没有记录行，归进“不认识的文件”。
- **副本被人改了：** 副本由插件维护；在 Git 里删掉的行，下次对账会补回；改坏的行跳过并写诊断，不让整个目录只读。缩略图不进 Git 的话，别的机器上只有占位。
- **id 索引：** 上次所在的路径存在 `.nbook/images/` 里；`.image` 没有“打开”这一步，重复的 `.image` 在图库里提示；`image.json` 的几个写者（服务端、项目入口、浏览器）一律带期望写入，冲突就重读再写。
- **同一张图属于几批：** 同一个种子能重抽出同一张时，按哈希去重会让一个文件属于几批。只有它所属的每一批都允许清时才清；按书列出时，算在最早生成它的那本书上。
- **别的机器的批次：** 本机只能看，不能扔掉；要扔掉，得在生成它的那台机器上做。

**备选与取舍（第 6、7 节）**

| 备选 | 为什么不取 |
|---|---|
| 历史写进配方文件 | 作者没保存时写回批次就是磁盘冲突，编辑器只能“重新载入”或“覆盖”，总要丢一样；每批约 2.5 KB，常用的配方两三周就超过作品文件约 960 KiB 的正文上限；Git diff 被生成记录淹没 |
| 历史放在配方旁边的同名文件 | 在资源管理器里改名、移动配方时落下它 |
| 配方做成文件夹（配方加历史） | 编辑器要把文件夹当成一份文档打开，这是新能力；“配方是一个文件”也得改 |
| 原图放书里（`.nbook/cache/images/`） | 拷书能带走全部，但书几个月涨几 GB 到二十几 GB，Git 必须忽略，同步盘被撑爆；`.nbook/` 下的文件浏览器也读不到 |
| 仓库放插件私有目录 | 作者与 Agent 看不到、碰不着，但平台还没有插件私有目录（[`runtime/plugin-api`](../specs/runtime/plugin-api.md) 写“另定”），读图还要另开路由；`user://` 现成的读法、主题素材的先例都能直接用，代价是作者在资源管理器里看得到这个目录，并且要把它排除在记账之外 |
| 待交付记录加确认（拓扑提案“文生图”一例） | 要单独存待交付记录、处理确认与退役；宽限期里回来、项目还在启动时都没有触发交付的时机。改成拿仓库自己的记录对账，任何一次读历史都能补齐 |
| 好图搬进书的控制目录、随书走 | 书多约 0.7 GB（重度抽卡三个月），还要跨进程搬文件；改成应用级收藏加导出 |
| 书里的图平铺，另放一份总清单 | 别的工具看得见图，但在资源管理器里移动、改名以后，清单就对不上了 |
| 到上限只提醒、不自动清 | 一张都不会意外丢，但作者不理提醒的话，会一直涨到磁盘满；开发者要的是 Telegram 那样不用操心 |
| 再加按时间保留（Telegram 有） | 多一套状态，收益不大 |

### 8. 工作台界面

界面已在[评审板](../../.agents/works/w00042-image-generation/tasks/t07-prompt-workbench/artifacts/review/index.html)上定稿，要点：

- **布局：** 工作台是编辑区里的一个标签页，一个标签页一份配方。提示词在左、结果在右，各占一半；结果默认显示最近一批的大图，看大图进灯箱。
- **词库：** 在外壳的侧栏，和资源管理器换着用，分“本书”和“我的预设库”。预设页只做管理：改名、复制、放进预设库、删除、看用在哪。
- **收起：** 参数只露一行摘要，点开才展开；套了预设的节默认收起成一行，写着预设名和改了几处。
- **窄屏**（390 宽）：分段切换“提示词”与“结果”，生成后自动切到结果；词库是底部抽屉。
- **Agent** 不嵌进工作台，留在对话视图里经工具读写（t08）。
- **后端差异：** 静态稿按 NovelAI 的形态画；SD、ComfyUI 缺的部分在界面上标出。

## 影响

- **数据与格式：**
  - 新的持久化格式：配方、预设、片段、风格组合的文件；书里的生成记录与内容快照；`.image` 文件夹与 `image.json`；`user://images/` 里的本机记录与收藏。
  - 每种格式带版本号。读到比自己新的版本时只读不写，并提示升级；改写一个文件时，原样保留不认识的字段。文件的具体格式在各 Spec 里定。
  - 第一版就按“节是有序列表、权重在每一项上、项可以不是文字、展开结果与后端写法分开”的形状存。
- **宿主能力与接口：**
  - 要平台新增三样，都按 [ADR 0027](../adr/0027-builtin-and-third-party-plugins-are-equal.md) 做成任何插件都能用的能力，不给图像插件开特例（待定项 6）：
    1. 记账排除贡献点：插件声明自己的哪些目录不记账、也不发变更事件；
    2. 服务端代作者写入时带上发起者：现在服务端插件的写入一律记成 `system`；
    3. 仓库记录的写法：写入接口没有“追加”，要么加追加，要么按天分的小文件整份重写。
  - 其余都是平台已有的：仓库用 `user://` 与它现成的读字节路由；结果进书用远程服务、事件推送、项目入口的激活与服务端写 `projects://`（项目没在运行时，写入会把它打开）。
  - 两样要先补的：文件夹类型的渲染贡献点（规范有、实现没有，见“待定项”7）；缩略图的图片处理库（实施计划里选）。
  - 一样小的新东西：安装 id，存成 `user://images/` 里的一个文件。
  - 用到的已有贡献点：编辑器（工作台）、侧栏视图（词库）、设置的 page 分区、状态栏。
- **`.nbook/` 里的插件数据。** 生成记录、快照、缩略图由插件直接写在控制目录里，先例是 canon 的世界日志（[`canon/project`](../specs/canon/project.md)“不经文件服务”）。各插件各写一份目录与 Git 规则，迟早要有一条平台规则（例如一律放 `.nbook/<插件>/`，并给出一份 `.gitignore` 的写法）。本稿先按 `.nbook/images/` 做，平台规则交给文件底座的 Work。
- **安全：**
  - 凭据只在服务端，不进浏览器（t04 改模型服务的规则）。
  - 插件自己写进图片或导出文件的元数据，只写白名单字段，不写凭据与本机路径：ComfyUI 把整个工作流嵌进图，有人从公开图片里扫出了几百个有效的 API key。后端交回的原图字节不改。
  - 成人标签不隐藏；涉及未成年人性内容的标签在构建时去掉。
- **跨 Work：**
  - **canon**（w00039）：定妆图第一版存具体版本文件的路径，经插件设定妆图、换当前版本时问一句再写 canon；在资源管理器里改名、移动会断，和今天一样。以后再议让 `image` 字段存图片 id，由图像插件解析。
  - **文件访问与改动记账**（w00032 t13）：见“待定项”6。
  - **插图方言**（t09）：`<image-gen>` 加一个程序写的 id；`<image-generated id>` 解析到 `.image` 文件夹的当前版本。
  - **编辑器：** 接受候选要往打开着的文档里改一处，现在没有这个入口（随 t10）。
- **迁移：** 新功能，没有要迁移的数据。
- **体积：** 进书的图每三个月几百 MB，建议用 Git LFS；给作者一张“哪些进 Git”的表和建议的 `.gitignore`。
- **发布与回滚：** 内置插件，可以停用。停用后书里的配方是文本文件、插图是装着图片的文件夹，别的工具照样能打开；图片仓库留在 `user://images/`，重新启用后接着用。
- **接受时写的 ADR：**
  1. 提示词存成“每项带数值权重”，不是括号树；展开与后端写法分开。
  2. 预设是“引用加差异”，更新预设不改配方文件。
  3. 图片的存放：每台机器的仓库是它生成的批次的主人，书里存副本、快照、缩略图与插图；结果靠对账进书，不设待交付记录。
