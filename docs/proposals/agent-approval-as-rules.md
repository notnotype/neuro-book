# Agent 审批收成一套规则

来源：[w00043](../../.agents/works/w00043-neurobot/README.md) 2026-11-18，开发者看过现行审批的整理后说“这四关有点太复杂”，问“地址能不能写”能不能放进规则、模式闸门能不能用规则实现（“切换模式就是修改规则”），要一版新的方案。本文不能作为当前行为的依据。

## 一、问题

现在判断一次工具调用要不要问用户，要拼四样东西：地址能不能写、三层规则、讨论与计划模式的闸门、审批模式。“写这里没事”还有三份各管一段的名单：地址表里的“可写”、闸门的“草稿”、自动模式的“免问写”。后果：

- 同一次写 `session://a.md`：计划模式下不问，普通模式加“逐个确认”要问，自动模式下不问。
- 用户说不清“这次为什么问我”。权限规则页只列用户自己写的规则；模式与审批模式各自怎么判，页面上看不到。
- bot 要“写自己的记忆不问”，现有机制里没有地方放：草稿只有闸门看，免问写只有自动模式看，规则只能来自用户设置与作品。
- `nbook.agent` 里有一张只认五个方案的表，新登记的方案（例如 `bot://`）一律算不许写。

## 二、目标与非目标

目标：

- 审批只有一种东西：规则。讨论、计划模式是一组规则，审批模式（逐个确认、放行写入、自动、全部放行）也是一组规则；切换模式就是换掉那一组。
- “写这里没事”只有一份名单：自有目录。
- 用户能看到此刻生效的全部规则；每次询问都能说出来自哪一层、哪一条。
- 开发者已定的审批语义不变（第三节最后一条）。

非目标：

- 不做操作系统沙箱：规则仍然不是安全边界（[`agent/permissions.md`](../specs/agent/permissions.md) 的“不承诺”）。
- 不改已有规则的写法与匹配器；第三方仍不能新增匹配器。
- 不改审批向导、“本会话都批准”、“以后都允许”。
- bot 的会话怎样记下属于哪个 bot、怎样拿到 `bot://`，属于 bot 的提案；本稿只定“自有目录由宿主按会话给”。

## 三、当前行为与证据

- 判定顺序见 [`agent/permissions.md`](../specs/agent/permissions.md) 输出 1，实现是 nb-harness `kit/approval/judge.ts` 的 `decide`：规则拒绝、闸门拦写、规则放行、规则询问、闸门下只写草稿、读、审批模式。
- 地址能不能写有两份：
  - 文件服务按方案登记的授权规则执行，对界面、插件、Agent 所有调用方一样生效（[`workspace/resources.md`](../specs/workspace/resources.md) 的方案注册；NeuroBook 的方案在 `plugins/agent/backend/schemes.ts`）；
  - `nbook.agent` 另有一张只认五个方案的表（`backend/resources.ts` 的 `classify`），宿主写的目录（附件、全文、后台任务输出）在两处各列一份。
  - 审批钩子只用这张表里的“写入要询问”（`user://`）；“不许写”的在写入时由文件服务拒绝，根本不经审批。
- 这一层为什么存在，记录里没有写理由；从实现看，它保的是数据归属与完整：会话日志只有内核写，附件与全文只有宿主写，别的会话的 home 不归这个会话（推断）。
- 闸门只在讨论、计划模式下算（`permissions/index.ts` 的 `gated`）；草稿是布局的 `scratch`（`session://`、`tmp://`），自动模式的免问写是布局的 `localWrites`（作品加草稿）。
- 缺省审批模式是“逐个确认”（`ask`，内核的 `DEFAULT_CORE_SETTINGS`）。
- 开发者已定（[w00032 t06](../../.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md) 2026-11-06 与 [`agent/permissions.md`](../specs/agent/permissions.md) 输出 7）：
  - 规则从上到下，第一条命中（clash）；
  - 作品里的规则只收询问与拒绝；
  - 讨论、计划模式下，放行规则与全部放行都过不了闸门；
  - 全部放行下，询问规则也放行；
  - 写 `user://` 一律要问，放行规则、“本会话都批准”与放行写入都不免，全部放行下放行。

## 四、方案

### 1. 能不能写不是审批，留在文件服务

能不能写是数据归属，像操作系统的文件权限。Agent 写不了的地方，写入工具直接失败（`permission-denied`），和“文件不存在”同类：不弹审批，规则与审批模式都改不了。

不放进规则，因为两者管的是不同的事：

- 规则是用户的偏好，一条放行规则或全部放行就能改掉。能不能写保的是别人的数据：放进规则，全部放行就能让 Agent 改写会话日志、宿主写的附件。
- 它对所有调用方生效，不只 Agent：界面、别的插件写这些位置同样被拒。放进 Agent 的规则，界面与插件还得另写一份。

要改的是“两份变一份”：Agent 不再自己维护那张表。判断某个会话能不能写一个地址时，直接问拥有这个方案的插件登记的授权规则：以这个会话的身份试判一次，不真写。于是：

- 新方案按自己登记的规则可写：`bot://` 由 bot 插件声明“这个 bot 的会话能写”；
- 宿主写的目录只在方案登记里列一处；
- `user://` 的“写入要询问”是审批的事，挪进规则的固定层（下一小节）。

### 2. 审批：四层规则

规则的写法不变（`{tool, when?, action, reason?}`）。加两种匹配器：

| 匹配器 | 什么时候算命中 |
|---|---|
| `{type: "effect", is: "read" \| "write" \| "exec"}` | 工具这次调用的等级是它 |
| `{type: "writes", within: ("own" \| "project")[]}` | 这次调用有写路径，全部落在列出的区域里，命令都只读（就是现在闸门“只写草稿”的判断） |

**自有目录**（`own`）：会话自己的地方，由宿主按会话给：`session://`、`tmp://`；bot 的会话再加它自己的 `bot://`。它替换现在的 `scratch` 与 `localWrites` 两份名单。`profile://`（同一个 Profile 的会话与 bot 共用的笔记）不算。

四层，从上到下：

| 层 | 谁定 | 能写的动作 | 内容 |
|---|---|---|---|
| 模式层 | 当前 Agent 模式；普通模式下为空 | 拒绝、询问 | 讨论、计划：既不是读、又不是只写自有目录的调用，拒绝（设置 `modeWriteAction` 为 `ask` 时询问） |
| 固定层 | 应用内置，删不掉 | 询问 | 写 `user://` 要问 |
| 你的规则 | 用户层、作品层、会话层，同现在 | 同现在 | 你写的与“本会话都批准”记下的 |
| 缺省层 | 审批模式 | 放行、询问、交审批模型 | 见下表 |

缺省层就是审批模式，四组：

| 审批模式 | 规则 |
|---|---|
| 逐个确认（`ask`） | 读放行；只写自有目录放行；其余询问 |
| 放行写入（`allow-writes`） | 读放行；写放行；其余（执行命令）询问 |
| 自动（`auto`） | 读放行；写入工具只写自有目录与作品时放行（命令不算，同现在）；其余交审批模型 |
| 全部放行（`yolo`） | 全部放行 |

合并，取第一个成立的：

1. 任一层拒绝：拒绝。
2. 模式层询问：询问；全部放行也不放。
3. 固定层询问：询问；全部放行下放行。
4. 会话层放行（“本会话都批准”）：放行。
5. 你的规则询问：询问；全部放行下放行。
6. 你的规则放行：放行。
7. 缺省层的结论。

模式层与固定层只拦不放，所以放在最上面也不会盖掉你写的拒绝；“读放行”“只写自有目录放行”都在缺省层，排在你的规则之后。第 2、3、5 步里的“全部放行”照搬开发者已定的语义，第三节最后一条逐条成立。

几次调用在三种设置下的结论（“现在”一列只写与新方案不同的）：

| 调用 | 普通模式、逐个确认 | 计划模式、逐个确认 | 普通模式、全部放行 | 现在 |
|---|---|---|---|---|
| 读 `project://第一章.md` | 放行 | 放行 | 放行 | |
| 写 `session://plan.md` | 放行 | 放行 | 放行 | 普通模式、逐个确认下询问 |
| 写 `project://第一章.md` | 询问 | 拒绝 | 放行 | |
| `shell`：`git push` | 询问 | 拒绝 | 放行 | |
| 写 `user://settings.json` | 询问 | 拒绝 | 放行 | |

### 3. 模式就是一组规则加一段提示

Agent 模式由两样组成：一组模式层规则，一段提示（现在每轮开头的 `reminder`）。切换模式就是换掉这一组规则与提示。计划模式另有 `switch_mode` 与 `plan.md` 的流程，不变；模式扩展仍拥有模式（[`agent/modes.md`](../specs/agent/modes.md)）。以后加模式（例如“只许改设定、不许改正文”）只要写一组规则和一段提示，不改审批钩子。

### 4. 看得见

- 权限规则页按四层列出此刻生效的规则：模式层与缺省层只读，标明来自哪个模式；你的规则照现在可改。
- 审批向导写明这次询问来自哪一层、哪一条；日志里结论的来源（`by`）同样按层记。

### 5. 备选方案与取舍

- **只把 `bot://` 加进草稿**：普通模式加“逐个确认”下照样要问，三份名单还在。不选。
- **能不能写也并进规则**：全部放行或一条放行规则就能让 Agent 改写会话日志与宿主写的附件；界面与插件写这些位置的限制还得另写一份。不选。
- **模式和审批模式合成一个控件**：模式还管提示与计划流程，“要不要改东西”和“改的时候问不问”是两个各自有用的维度（[`agent/modes.md`](../specs/agent/modes.md) 的目标）。不选；两者都成了规则组，界面上并排显示。

## 五、影响

- **行为变化**只有一处：普通模式加“逐个确认”下，只写自有目录的调用不再问（`session://`、`tmp://`；命令只读、写重定向落在自有目录里的，例如 `echo x > tmp://a`，同样不问）。计划与讨论模式、放行写入、自动、全部放行下的结论都不变。
- **数据**：规则文件的格式只增两种匹配器，旧规则照旧有效；旧日志里结论来源的旧值（`mode:scratch` 等）照旧显示。
- **接口**：nb-harness 宿主套件的审批钩子，闸门的开关、文字与 `modeWriteAction` 换成“模式层规则”；宿主布局的 `scratch`、`localWrites` 合成 `own`（[`harness/host-kit.md`](../specs/harness/host-kit.md) 输出 10）。现在只有 NeuroBook 一个宿主，同一次改完。
- **安全**：今天会拒绝的调用都还拒绝；唯一放宽的是上面那处行为变化，范围是会话自己的目录。自动模式的审批模型照旧只看用户亲手打的字；定时注入进对话的话要标明来源、不算用户的授权，归 bot 的提案。
- **迁移与回滚**：没有数据迁移；回滚代码即可。
