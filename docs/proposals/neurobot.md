# NeuroBot（暂名）：常驻、有记忆的 AI 员工，第一版

需求原文、开发者已定的事与三份调研都在 [w00043](../../.agents/works/w00043-neurobot/README.md)。开发者 2026-11-09 看过第一稿的要点、同意了当时的待定项；第一轮设计审查后改成第二稿，第二稿的待定项开发者 2026-11-10 已定。第三稿按第二轮设计审查（[w00043 t01](../../.agents/works/w00043-neurobot/tasks/t01-direction/README.md) 的“设计审查第二轮的处理”）与开发者 2026-11-10 对其中四项的答复修订。本文不能作为当前行为的依据。

## 一、问题

现在和 Agent 打交道的单位是会话：用户自己开会话、切会话，会话之间不共享记忆，一段对话写长了要用户自己处理。开发者要的是另一种关系：

- 用户面对的是一个 bot，像面对一个真人员工。bot 有名字、有长期记忆，可以从多个渠道联系；会话由系统管，用户不感知。
- bot 能替用户办事：日程、周期任务（例如每周整理某个领域的简报）、主动提醒。
- 以后 bot 之间能协作、能被拉进群、能派子代理、能创建子 bot，组成一个小公司。

第一个用户是 NeuroBook 的看板娘，充当 NeuroBook 的 AI 运营官。

## 二、目标与非目标

第一版以搭起框架为准（开发者 2026-11-10）：拿不准、又不是框架必需的功能放进第四节第 11 小节的路线。第一版的目标：

- 看板娘一个 bot，在 web 上能像和真人一样长期聊下去：不开会话、不切会话，上下文由系统维持。
- 保留原始记录：之后换记忆系统、做记忆评测，都能从原始记录重放。
- 简单的长期记忆：bot 自己维护的 Markdown 记忆文件，加检索。
- 日程与周期任务：用户和 bot 一起维护；到点 bot 主动找用户，或自己去干活。
- 用户不在页面上时，bot 不会因为等审批而卡住。
- 应用与 NeuroBook 同在一个 monorepo，建在 nb-runtime 与 nb-harness 上。

非目标（第一版不做，见第四节第 11 小节的路线）：

- QQ 等外部渠道（定了用 LLOneBot，第二步做）、TUI、手机 app；
- 浏览器通知与页面完全关掉时的提醒触达（桌面通知、邮件）：第一版只有页面开着时的页面内提示，这是已知缺口；
- 多个 bot、bot 之间的对话与群、子 bot、组织架构、分身；
- 共享知识库、做梦整理、nb-memory；
- 搜索对话内容、让 bot 忘掉某段对话、重新开始对话、改写历史（编辑、重试、从此处分支）；
- 远端设备；社交媒体运营；
- 第三方插件的安装（只有内置插件）；远程访问与多用户。

## 三、当前行为与证据

- 能直接复用的包：nb-runtime（生命周期、服务、插件、远程服务；不经 NeuroBook 的 `plugin-platform` 也能装配内置插件，`createApplication` 直接收插件列表）、nb-harness（日志驱动的内核、压缩流程、审批钩子、扩展的 `opening`）、nb-agent-ui（对话视图，纯受控视图，不取数、不发请求）、nb-ui、nb-markdown。
- Agent 的压缩方法、审批判定、会话句柄表、通用工具现在在 NeuroBook 的 `nbook.agent` 插件里，由 [w00032 t32](../../.agents/works/w00032-agent-integration/tasks/t32-harness-backfill/README.md) 补回 nb-harness。
- 仍在 NeuroBook 应用里、t32 不搬的（行数是非测试代码）：服务端宿主 `src/server/` 3,952 行（监听回环、来源核对、状态根认领、RPC 端口、启动与停止），浏览器宿主 `src/web/` 约 1,990 行，模型服务 `nbook.models`（后端 `core.ts` 555 行，设置页约 3,100 行），设置、存储、HTTP 插件，Agent 的接线（t32 之后约 2,000 行），网页一侧的对话宿主 `nbook.agent/web/session-host.ts` 1,459 行（订阅、取历史、发指令、乐观消息、断线重连）。服务端宿主与对话宿主的行数是主 Agent 核实的；其余是审查者统计的，设置插件的 5,919 行含前端，只能当上限参考。
- NeuroBook 的压缩只在超过阈值、服务商报溢出、手动三种情况下触发（[`agent/compaction.md`](../specs/agent/compaction.md)）；宿主发起的只压缩运行固定按 `manual` 走缺省的方法顺序 `shake → inplace → summary`，指令里不能指定方法。
- NeuroBook 的会话由用户在界面上开，一个视图一个会话（w00032 t17）；审批与提问没有过期，运行停在“等用户”时会一直等。
- 会话日志是唯一的真相源，打开会话要从头归约，长会话靠预算守住（2 万条事件 1 秒内打开），超出时再加检查点快照（[ADR 0035](../adr/0035-harness-log-driven-kernel.md) 决策 1）。
- 第二轮设计审查核实的几条内核与宿主事实，第三稿的改动都以它们为前提：
  - 扩展在 `mount` 里写的外部事实，运行中排到下一个边界才写入；运行收口不写出它们，只压缩的运行也不经过边界。
  - 会话句柄表在会话空闲、没有引用 30 秒后关掉会话。
  - 内核的发出者只有用户与会话两种，审批只收用户的应答。
  - OMP 的缓存保留只收三档（不缓存、短、长），实际寿命由服务商、模型与凭据决定。
  - 服务端宿主对不带 `Origin` 的本机进程照常放行（[`runtime/server-host.md`](../specs/runtime/server-host.md) 的已知限制）。
  - 浏览器宿主连回不同的服务端进程时转入终态 `server-restarted`，不再重连。
  - 对话视图的适配器跳过扩展写的事件；分轮只认用户消息开头。
- 同类产品（[商业产品](../../.agents/works/w00043-neurobot/research/2026-11-09-commercial-bots.md)、[开源实现](../../.agents/works/w00043-neurobot/research/2026-11-09-open-source-architecture.md)）：
  - OpenClaw：会话键由“哪个 agent、在哪里聊”算出，私信默认汇入一个滚动的主会话，靠压缩维持；入站先把原始事件落盘再交给 agent；cron 每次运行一个新会话；写记忆的路径带来源，做梦时剔除不可信来源；缓存过期后只裁旧的工具结果。
  - nanobot：空闲 15 分钟自动压缩；压缩的摘要追加进历史文件，由离线整理处理，不在回复路径上多跑回合。
  - Grok Bot：例行任务由时间表或事件触发，后台工作引起的审批卡片 30 分钟过期，拒绝后不重试；Muse：记忆是用户能编辑、下载的几个 Markdown 文件。

## 四、方案

### 1. 概念

- **bot**：一个常驻的员工。有身份（名字、头像、人设）、用哪个 Profile、用哪个模型、自己的记忆、自己的对话。开发者的原话是“用户感知的是 bot（或者说 profile）”；讨论后同意分开（2026-11-09）：Profile 是岗位定义（工具、提示词），bot 是在岗的人，以后两个工程师 bot 可以共用一个 Profile；用户感知的仍然只有 bot。
- **对话场所**：bot 在哪里和谁聊。第一版只有一种：web 上用户与 bot 的私聊。以后加 QQ 私聊、QQ 群、bot 之间的私聊与群。
- **对话**：一个 bot 在一个对话场所里的全部往来，对用户是一条不断的消息流。
- **会话**：harness 的会话，是对话在模型那一侧的载体。主对话就是一个会话，一直写下去，靠压缩维持；用户看不到“会话”这个概念。
- **任务运行**：周期任务每到点一次，在一个新会话里跑，跑完就结束。
- **adhoc**：用一次就丢的子代理，没有长期记忆（w00032 t14 的子代理，第一版不用）。

### 2. 进程与拓扑

沿用 NeuroBook 的多实例拓扑（[ADR 0024](../adr/0024-multi-instance-runtime-topology.md)），角色对照：

| NeuroBot 的说法 | 对应 | 第一版 |
|---|---|---|
| gateway | 服务端实例：常驻进程，持有 bot、对话、会话、日程与调度 | 做，只监听本机 |
| web | 浏览器客户端实例，经内核远程服务连 gateway | 做 |
| tui、app | 其它客户端实例 | 不做 |
| QQ 等外部渠道 | gateway 里的渠道插件：把外部消息转成某个对话场所的入站消息，把回复发回来源渠道 | 不做，预留入站接口 |
| device | 远端主动连上 gateway、提供能力的实例（配对、按命令授权） | 不做 |

没有项目子进程：NeuroBot 不打开作品。一个数据目录同一时间只给一个 gateway 用，启动时认领，认领不到就退出。

### 3. 应用包与依赖

- 新应用包 `packages/neuro-bot`（暂名），技术栈同 NeuroBook（[ADR 0023](../adr/0023-v2-frontend-backend-stack.md)）：后端 Bun，前端 Vue 与 Vite，校验用 TypeBox。不依赖 `@notnotype/neuro-book`。
- 只用内置插件，不用 NeuroBook 的 `plugin-platform`。[ADR 0030](../adr/0030-plugin-platform-layering.md) 决策 2 的字面条件是“出现第二个使用插件模式的应用时，再把这个目录搬成包”；开发者 2026-11-10 同意另写 ADR 把条件改为“出现第二个需要第三方插件的应用”。
- 第三节列的“仍在 NeuroBook 应用里”的那些，按开发者 2026-11-10 的决定分两类：服务端与浏览器两端宿主中与应用无关的部分（监听、来源核对、数据目录认领、客户端连接的两端）、HTTP 的来源核对与诊断日志的输出抽进新包 `nb-host`，模型服务抽进新包 `nb-models`，加锁替换抽成一个与应用无关的小包，NeuroBook 与 NeuroBot 共用（开发者 2026-11-10 同意 t02 计划审查后的这三项）；设置、Agent 接线、网页对话宿主 NeuroBot 自己写。抽包是 [w00043 t02](../../.agents/works/w00043-neurobot/tasks/t02-host-base/README.md)，与 w00032 t32 一起排在 NeuroBot 第一版之前。
- 模型设置页（NeuroBook 的约 3,100 行）留在 NeuroBook，t02 不抽。NeuroBot 第一版只写最小的设置页（第 8 小节）。

### 4. 对话与上下文

**会话由对话决定。** 主对话一个会话，用户发消息就进它；用户没有“新建会话”的入口。不轮换会话：轮换要把会话私有的文件、设置、批准记忆带过去，还会在第二次轮换时丢掉第一段的摘要。会话长到打开变慢时（超出 ADR 0035 的预算），在 nb-harness 加检查点快照，NeuroBook 也受益；常驻的 bot 迟早会到这一步，第一版先记录打开耗时。

**主会话常驻。** 主对话的会话由 NeuroBot 的对话管理一直持有，gateway 运行期间不关。句柄表的空闲关闭只对任务会话生效。否则每次计时到点、每条提醒都要重开会话，从头归约整段日志。

**运行中的消息**：bot 正在回复时用户再发的消息走插话（steer），进当前这一轮。第一版不做空闲时的连发合并：每条消息一个指令，原始记录与乐观消息都是一对一（细节进 t06 的 Spec）。插话在聊天场景里怎么显示（现在的视图标成“补充说明”、轮末折叠），在 t03 的设计评审里定。

主对话停在等用户（审批或提问）时用户发来的消息，见第 7 小节“主对话里等用户”。

**压缩触发点**：沿用阈值、溢出、手动三种，再加两种，都是为了省钱（开发者 2026-11-09）：

- **缓存过期前压缩**：上一次对话请求之后，在服务商的提示词缓存过期之前一点，如果还没有新消息，就趁缓存还在用就地方法（`inplace`，用会话的模型，前缀与对话请求相同）压缩一次。读上下文按缓存价算；下一条消息从短的上下文开始。
- **空闲压缩**：缓存已经过期后，下一条消息本来要按全价重读整段上下文；空闲时先用“压缩”角色的模型（`summary` 方法）把上下文压短。

两种都只在划算时做，条件写成判断式，数值在 Spec 里定：

- 上下文超过一个下限；两次压缩之间至少隔一段时间。缓存寿命短的服务商（例如 Anthropic 的短档是 5 分钟）上，没有下限和间隔，用户每停顿几分钟就会压一次，细节越压越少。
- 设置里配的是缓存档位，不是时长：服务商只认几个档位，实际寿命由服务商、模型能力与凭据类型决定。寿命由 nb-models 查表得出，在设置页上显示。模型适配器把档位显式传给服务商，不让环境变量改掉它。
- 只对寿命确定的显式缓存做缓存过期前压缩；服务商自动做的隐式缓存没有确定的过期时刻，不做。
- 单价未知时不做；空闲压缩还要求压缩模型比会话模型便宜。订阅制凭据不做（审查者的推断：订阅按额度计，不按 token）。
- 指定的方法失败时不换别的方法：换了就不省钱，宁可不压缩。
- 每次触发记下花费与估算的节省，跑一段后按真实数据调数值。

截止时刻从最后一次对话请求的时刻起算，加上寿命；前缀相同的就地压缩请求也刷新缓存，同样算进去。运行中（含停在等用户）不计时。只压缩的运行结束时不重新排一次计时。截止时刻由会话日志算出，gateway 重启后照算，不靠内存里的计时器。

实现上的归属：

- nb-harness 内核的压缩指令要能带上原因与方法顺序（现在固定按 `manual`），归 t08。
- 两种新触发的判断条件与截止时刻的计算做成 nb-harness kit 里与应用无关的一块，NeuroBook 以后也能用（开发者 2026-11-09 定的“新的压缩触发点放进 nb-harness”）；到点发起压缩的计时由 NeuroBot 的对话管理持有，不放句柄表。归 t08。
- t02 给服务商配置预留的缓存字段，按档位对齐。
- 宿主发起的压缩进行中用户发来消息时：压缩请求已经发出的，让它做完再发这条消息，读上下文的钱已经花了，压完的短上下文正好给这条消息用；请求还没发出的才中止，中止时保留缓冲区。中止的压缩不改对话。

**压缩不多跑回合写记忆**：每次压缩成功后，把这一段新增的内容追加进 bot 记忆目录里按天的日记文件，以后由整理任务处理（nanobot 的做法）。压缩摘要是滚动的全量摘要，整段追加会让日记反复堆同样的内容；所以 NeuroBot 给压缩方法的摘要提示词多要一节“这一段新增的内容”（摘要的小节由应用决定，见 w00032 t32），日记只追加这一节。不跑额外的回合，不多花钱；bot 在对话中照常可以自己写记忆。

**重启**：gateway 重启后，主对话里有被中断的对话运行时，gateway 用内核已有的 `start` 指令（不带新输入的继续运行）让 bot 接着处理，不伪造用户输入。只对对话运行接续，被中断的只压缩运行交给计时重新判断；接续有次数上限，防止同一次运行反复让进程崩溃（细节进 t06 的 Spec）。页面上显示“已自动继续”，自动继续时输入框不再提示“回车继续”。还没受理的入站消息按原始记录补发（第 5 小节）。

### 5. 原始记录与记忆

**原始记录**：每个对话场所一份只追加的消息记录。与会话日志的分工按 ADR 0035 决策 1：

- 入站以原始记录为准：先写原始记录（带消息 id 与发给会话的指令 id，一条消息一个指令），再交给会话；重启时把会话还没受理的补发，指令 id 保证只生效一次。
- 出站与 bot 的行动以会话日志为准：运行结束后，把用户看得到的回复投影进原始记录，带“在哪个会话、第几条”指回日志。原始记录按会话日志的序号记一个“已投影到”的游标；重启时从游标之后补投影，投影按会话与序号幂等。
- 提醒到点时直接写进原始记录（第 6 小节），不等它进会话；任务结果同样记一条。都带来源。
- 每条带来源与信任级（主对话、日程、任务运行，以后的外部渠道）。外部内容第一版就会进来：周期任务会经抓取工具读网页（第 7 小节）。
- 附件存在对话一级，不放在会话的私有目录里。
- 以后群里没有 @ bot 的消息也记进原始记录；记忆评测与换记忆系统都从它重放。

界面的对话流来自主对话的会话日志。已知取舍：到多 bot 群聊时，一个场所里有几个 bot 各自的会话，流要改成按原始记录排序、按消息挂上各自的过程，那时重做流的来源。

**记忆**（第一版）：

- 每个 bot 一个记忆目录，放 Markdown 文件，bot 用读写工具维护。目录一把写锁，写暂存文件后改名；每次改动记一条（时刻、会话、工具调用、来源），写在磁盘上，页面上看改动记录放进路线。
- 一份核心记忆（关于用户、关于自己的要点）在会话创建时与每次压缩后取一次快照放进提示词（内核的 `opening`），不在每次请求重读：改了就让后面整段对话的缓存失效。对话中改了核心记忆，到下次压缩才进提示词。超过长度上限时磁盘上完整、放进提示词的截断，并在写入的工具结果里提示已超出。
- 其余按需用检索工具查，第一版用关键词检索。
- 任务运行不能写核心记忆，只能追加日记文件：任务读的外部内容可能带提示注入，不能让它变成长期生效的指令。这一条由 NeuroBot 的文件访问强制（第 7 小节），不只靠提示词。
- 用户在 web 上只读查看记忆文件；要改就在对话里让 bot 改。

记忆分层（私有、组织、共享知识库）、做梦整理、nb-memory 的取舍，等 bot 跑一段后用真实记录做评测再定（开发者 2026-11-09）。

### 6. 日程与周期任务

做成内置插件。

- 两种条目：一次性的（某时开会）与周期的（每天几点、每周几）。用户在 web 上改，bot 用工具改；一个工具只做一件事（w00032 t14 决定 6）。每条记谁建的、谁最后改的；bot 改了日程，在对话流里留一条说明。
- 第一版存在 NeuroBot 自己的数据里；接外部日历或 Todoist 以后做成同步插件。
- 到点的动作两种：提醒与任务。

**提醒**：一段固定格式的文字，不开运行、不多花钱。

- 到点先写进原始记录，页面开着时立刻提示（标题未读数与页面内的提示），不等主对话的运行结束。否则主对话停在等审批时，提醒最多晚 30 分钟。
- 提醒与任务结果都用“条目 id 加计划时刻”作幂等键，调度在记下“已发”之前崩溃也不会重复。
- 进会话由 NeuroBot 的扩展写一条自己的对话事件（第三人称的记录，例如“[日程提醒] …”），只在主对话空闲时写，正在运行时等运行结束。内核把它并进下一轮的附带内容：对模型它是下一条用户消息前的一段系统提示，不是 bot 说过的话；界面上它自成一轮（第 8 小节）。
- 判断空闲与写入之间有竞态，写入可能落进刚开始的运行或只压缩的运行。nb-harness 内核要在运行收口时（含只压缩的运行）写出扩展排着的外部事实，不让它滞留到用户下一次发消息。这条内核改动归 t10。
- 用户长时间不回时，这些附带内容会一直挂在轮外，压缩切不掉。累计长度设上限，超出时只留最近几条（数值进 t10 的 Spec）。

**任务**：

- 每次到点开一个新会话跑，会话 id 由“任务加计划时刻”定，重启后不会重复跑。
- 每个任务有允许的工具与命令清单，清单的强制见第 7 小节；任务会话装 kit 的花费守卫与循环守卫，每个任务有花费与轮数上限，超限按失败处理、进“待你处理”。
- 做完把结果写进主对话，写入时机与提醒相同。结果太长时只放摘要，全文存成工作目录里的文件，页面上能只读打开（第 8 小节）。
- 失败也发一条短消息，说明原因。gateway 中途退出、运行以中断收口的任务按失败处理（细节进 t10 的 Spec）。
- 错过的：周期任务错过几次合并成一次补跑；提醒过期太久就不发，只在对话里说明错过了。

### 7. 电脑、工具与审批

- bot 与电脑的对应可配置，缺省所有 bot 共享一台（开发者 2026-11-09）。第一版的电脑就是 gateway 所在的本机，工作目录缺省在 NeuroBot 数据目录下的 `workspace/`。
- 工具用 t32 补回 nb-harness 的通用工具；文件访问由 NeuroBot 实现，直接读写本机。
- 联网用 NeuroBot 自己的只读抓取工具（开发者 2026-11-10）：只取 http(s)，拒绝回环、链路本地与内网地址，结果标为外部内容。通用工具里没有联网工具，不加它的话任务只能放行 `curl` 一类命令，而命令能写任意文件、能连本机的 gateway。归 t10，周期任务第一次用到它。

审批沿用 harness 的审批判定，NeuroBot 的缺省规则：

- 记忆目录与工作目录内的读写放行；
- 读这两个目录之外的文件、执行命令、写目录之外的文件要批准。

**主对话里等用户**（开发者 2026-11-10）：

- 审批或提问挂着时输入框一直可用。用户发消息，就以拒绝结算挂着的事项，附上这句话（“没批准，用户说：……”），再把消息送进对话。这是用户本人的应答，以用户的名义结算是如实的。
- 30 分钟没人理时，由内核按“过期”结算，记为内核结算，不冒充用户；对话里留一条说明，bot 不会一直卡住。nb-harness 内核要支持审批与提问带期限，这条内核改动归 t06。
- 到期之后才到的点击，对话宿主提示已过期，不静默放弃。
- 拒绝或过期之后，同一调用在本次运行里不再申请，由 NeuroBot 包的审批钩子拦下。
- “记住”只保留一个，按 bot 存。

**任务运行不等审批**，清单外的直接拒绝。缺省规则会放行记忆目录与工作目录内的读写，规则判为放行的调用到不了转问那一步，所以清单要在三处强制：

- 任务会话的工具集按清单裁剪，不在清单的工具模型看不到；
- NeuroBot 在 harness 的审批判定外面按会话种类包一层审批钩子，任务会话先按清单判，清单外拒绝；
- NeuroBot 的文件访问拒绝任务会话写核心记忆，只许追加日记。

任务清单缺省不放行 `shell`（开发者 2026-11-10）：命令直接读写本机，不经 NeuroBot 的文件访问，上面的第三条管不到它。被拒绝的调用在任务结束时进“待你处理”，用户可以把它加进清单。

由另一个 bot 判定工具调用（开发者 2026-11-09）放到多 bot 那一步。

### 8. web 界面

第一版网页以搭起框架为准（开发者 2026-11-10）。

- 页面：bot（第一版只有一个，进来直接到它）、对话、日程、记忆、设置。路由带 bot，例如 `/bots/<bot>/chat`，以后多 bot 不改路由。
- 首次启动自动建缺省的看板娘，人设在一个可改的文件里；第一版没有编辑 bot 身份的界面。没有模型时引导去设置；没有消息时显示空状态。外观开工时按 design-review 出静态稿（t03）。
- 设置页只做最小版：服务商与密钥、绑定主模型与“压缩”两个角色、缓存档位（显示查表得出的寿命）。审批规则、任务清单等其余设置先改文件。
- “待你处理”的入口：等你批准的审批、任务运行被清单拒绝的调用、失败的任务、错过的提醒集中在一处，每条能跳回对话里的原处；被拒绝的调用可以直接加进那个任务的清单（开发者 2026-11-10 追认）。它是 gateway 持久保存的待处理项，带来源、状态与关联的消息，页面经远程合同取得与订阅。跳回原处要视图能滚到某条消息、能载入它附近的一段，归 t07。待处理项的状态与何时消解，细节进 t10 的 Spec。
- 只读查看文件：记忆页与任务的长结果，经 gateway 一个只读的文件入口，只许读记忆目录与工作目录。它是新的读文件面，走第 10 小节的来源核对与口令，进那里的验收。
- 对话视图复用 nb-agent-ui，按 NeuroBot 调整：
  - 关掉会话标题栏与“新会话”；关掉改历史的入口（编辑、重试、从此处分支）与分支树，消息上只留复制。重试两周前的一条会让主对话的叶子退回那里，之后的提醒、任务结果、压缩点都落到被放弃的旁支。
  - 隐藏输入框里的模型选择：模型按 bot 设置。
  - 等用户时输入框与审批、提问并存，不被审批向导替换；向导里的两个“记住”收成一个按 bot 的范围（第 7 小节）。
  - 加按天的分隔线。
  - 提醒、任务结果这类没有用户消息开头的内容，要能自成一轮，不并进上一轮。nb-agent-ui 现在按“用户消息开头”分轮，要加“由事件开启的轮次”（第六节）。
  - 长流按窗口取：网页只取主对话路径的尾部一段，往前翻时由 NeuroBot 的对话宿主实现 `loadPrevious` 再取，断线重连只补增量。nb-agent-ui 的适配器要支持只应用路径的后缀。归 t06、t07。压缩只缩短模型上下文，不删日志，不窗口化的话一个活跃的 bot 几周后每次打开、每次重连都要整条重取、重画。
- 页面开着时的提示：标签页标题带未读数；页面内有“你离开后”的未读分隔线。最后看到的位置存在 gateway、按 bot，多个标签页共用；什么算“看到”在 t06 的 Spec 里定。
- 断线与重启分开处理：同一个 gateway 进程内的断线由共用的浏览器宿主照旧重连；gateway 换了进程时浏览器宿主转入终态，由 NeuroBot 的 web 外壳自动重建页面，不要求用户刷新（t04）。重建时草稿在浏览器本地存储里保留，正在上传的附件丢失。被中断的运行在流里有说明。

### 10. 安全

gateway 只监听回环地址，没有登录。NeuroBot 不沿用 NeuroBook 的“本机进程可信”：bot 自己在同一台机器上跑命令，任务无人值守，还会读外部网页，被注入的一条命令就能写一个 WebSocket 客户端连上 gateway，以用户的身份批准审批、改任务清单。所以下面四条都要成立，第一版必须满足并有验收：

- 只许监听回环地址，别的地址启动失败；
- HTTP 的 `Host` 必须是回环名，否则 421（防 DNS 重绑定）；
- RPC 端口的 WebSocket 与带 `Origin` 的写请求只接受本进程页面的来源，否则 403。浏览器的跨源 WebSocket 不受 CORS 限制，少了这条，本机打开的任意网页都能连上 gateway、替用户批准审批；
- 本机口令（开发者 2026-11-10）：gateway 每次启动生成一个口令，只经页面的引导接口下发给页面；RPC 连接与写请求不带口令一律拒绝。不带 `Origin` 的本机进程因此连不上，第三条只挡浏览器，挡不住它们。

前三条是 NeuroBook 服务端宿主的现有规则（[`runtime/server-host.md`](../specs/runtime/server-host.md)），t02 抽进 nb-host。本机口令做成 nb-host 的可选项，NeuroBook 暂不开，归 t04。引导接口本身也要让本机进程拿不到口令，否则口令形同虚设；怎么做到在 t04 的 Spec 里定，可以参照 nb-story 的一次性登录链接加 HttpOnly 会话 Cookie（`packages/nb-story/src/server/auth.ts`）：链接只能用一次，之后只有带 Cookie 的页面拿得到口令。同一系统用户下的进程无法彻底隔离：能读到页面所持口令的进程照样能连，这是已知限制，口令挡的是“连上端口就能操作”。

其余的安全规则：

- 只读抓取工具拒绝回环、链路本地与内网地址，bot 也就不能经它连上 gateway。
- 只读的文件入口只许读记忆目录与工作目录，路径穿越与符号链接出界都拒绝，进第一版的验收。
- 外部内容不能改变权限：原始记录与记忆改动带来源和信任级；任务运行不能写核心记忆，由文件访问强制；任务清单缺省不放行 `shell`；读工作目录与记忆目录之外的文件要批准。

### 11. 第一版之后的路线

方向记录，不是承诺；每一步开工前另行讨论：

1. **QQ**：LLOneBot（OneBot v11）渠道插件；渠道到 bot 的路由规则；群里没有 @ bot 的消息作为背景记进原始记录，bot 可以选择插话；外部消息一律当作不可信内容。
2. **记忆**：用真实记录建评测（谁是谁、约过什么、会议几点、哪个梗用得对），比较 nb-memory 与其它方案；共享知识库（梗、平台风向、写作技巧，带来源与时效）；做梦整理，写入长期记忆前检查来源。
3. **多 bot**：bot 之间的私聊与群聊、防止 bot 之间无限对话的限流、子代理（w00032 t14）、创建子 bot（不审批）与同级 bot（用户审批）、bot 判定别的 bot 的工具调用、分身共享记忆。
4. **组织**：组织、岗位、工单、会议几样东西，组成小公司的结构。
5. **设备与渠道**：手机作为设备；TUI、app；bot 自己的邮箱；页面关掉时的提醒触达。
6. **社交媒体运营**：经浏览器插件（w00034）在 B 站、X 上看帖、回复；开工前先核对各平台对自动化账号的条款与风控。
7. **web 的补全**：浏览器通知（按提醒、任务、审批分类开关，免打扰时段，多标签页只由一个发）；按 bot、按天的用量与费用；记忆页的“让她改这一段”与改动记录；任务结果的“查看过程”（只读抽屉，运行中可跟随）；日程页列每个周期任务最近几次的运行；审批与提问的过期倒计时；编辑 bot 身份与人设的界面；完整的设置页（审批规则、任务清单、通知）。
8. **空闲时的连发合并**：短时间内连发的几条合成一条再发，要先定合并窗口与原始记录、乐观消息的对应关系。

### 12. 备选方案与取舍

开发者 2026-11-09 选了上面的方案（monorepo 里的新应用，nb-runtime 上自建，借 OpenClaw 的设计），没有说明不选其它方案的理由。下面是讨论时主 Agent 列出的各方案代价，不是开发者的理由，以后不要当作约束引用：

- **装 OpenClaw，NeuroBot 写成它的插件**：最快能用。代价：它跑在 Node 上、有自己的插件体系，nb-runtime 与 w00032 的成果用不上；仓库约 6.6 万个文件、更新很快；bot 不是会话、组织、子 bot、分身这类要改核心的东西，不一定能做成插件。fork 它的维护负担更大。
- **做成 NeuroBook 的一组插件**：服务端宿主、浏览器宿主、模型服务、设置、Agent 接线都现成（第三节列的那些）。代价：NeuroBook 是按作品打开的写作工作台，NeuroBot 是常驻的多渠道服务，产品与发布会绑在一起。第一稿只写了“不用抽包”，低估了它省下的量；开发者 2026-11-10 据此选了只把安全攸关、已调好的部分抽成包共用（第 3 小节）。
- **独立仓库**：代价是 nb-runtime、nb-harness、nb-ui 都要经 npm 版本跨仓库改，跨包改动不能一次提交。

## 五、数据、接口、安全、迁移、发布与回滚影响

- 数据：新的数据目录，与 NeuroBook 的数据互不读写。原始记录与会话日志只追加。
- 接口：新应用自己的远程合同。nb-harness 的内核、kit 与模型适配器，nb-models，nb-host，nb-agent-ui 都有改动（第六节）；新行为都是可选项或新字段，缺省时 NeuroBook 的行为不变。t32 本身保证 NeuroBook 行为不变。
- 安全：本机进程不再被信任，gateway 靠每次启动生成的口令挡住它们（第四节第 10 小节）。远程访问、外部渠道进来之后要重新评估（谁能给 bot 下指令、回复是不是外发通道）。
- 迁移：无。
- 发布：第一版只从仓库运行，不发 npm、不进 CI 的打包。
- 回滚：新包独立，删掉不影响 NeuroBook。共享包里的改动缺省关闭，回滚 NeuroBot 不必回滚它们。

- `schedule.md`：条目、谁建谁改、提醒（幂等键、写入时机、累计上限）与任务（清单的三处强制、花费与轮数上限、中断按失败）、错过的处理、时区；待处理项的数据、状态与消解。
- `gateway.md`：监听、三条来源核对与本机口令、数据目录认领、只读的文件入口、启动与停止。
- `web.md`：页面与路由、首次运行与空状态、最小设置页、“待你处理”、只读查看文件、未读数与未读分隔线、断线重连与换进程后的重建。
