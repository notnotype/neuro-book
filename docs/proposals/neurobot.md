# NeuroBook 的 bot：常驻、有记忆的 AI 员工，第一版

需求原文、开发者已定的事与调研都在 [w00043](../../.agents/works/w00043-neurobot/README.md)。前三稿写的是单独的应用 NeuroBot（第三稿 2026-11-10）。开发者 2026-11-18 改定：bot 先做成 NeuroBook 的内置插件，NeuroBot 应用暂停。本稿是第四稿，按这个决定改写，并吸收了同日的[耦合审查](../../.agents/works/w00043-neurobot/research/2026-11-18-coupling-audit.md)与已接受的提案 [Agent 审批：一份自有目录](agent-approval-simplification.md)。为独立应用抽出的三个包（nb-host、nb-models、nb-file-lock，[ADR 0045](../adr/0045-shared-host-packages-for-second-app.md)）已经合入，NeuroBook 继续用。本文不能作为当前行为的依据。

## 一、问题

现在用户和 NeuroBook 的 Agent 打交道，单位是会话：会话由用户自己开、自己切，会话之间不共享记忆，对话写长了也要用户自己处理。开发者要的是另一种关系（2026-11-09、2026-11-18）：

- 用户面对一个 bot，像面对一个真人员工。bot 有名字、人设和长期记忆，和用户一直在同一段对话里，会话由系统管。
- bot 能替用户办事：管日程、跑周期任务（例如每周整理某个领域的简报）、到点提醒。
- 会话仍可以用，只是不推荐。

第一个 bot 是 NeuroBook 的看板娘。[w00050](../../.agents/works/w00050-lyra-persona-and-prompts/README.md) 正在做的星璃（Lyra）现在是一个用户 Profile，记忆放在 `profile://memory/`，按本稿改成 bot 的预设（第四节第 3 小节）。

## 二、目标与非目标

第一版以搭起框架为准（开发者 2026-11-10）。目标：

- 一个 bot 常驻在 NeuroBook 里，用户能和它长期聊下去：不开会话、不切会话，上下文由系统维持。
- 简单的长期记忆：Markdown 记忆文件由 bot 自己维护，常驻的几份放进提示词，其余靠检索。
- 日程与周期任务：用户和 bot 一起维护；到点后系统往主对话注入一段提示词，bot 自己去办。
- 用户不在时，bot 不会因为等审批卡住。
- 两种省钱的压缩。

非目标（第一版之后的方向见第四节第 13 小节）：

- 多渠道、外部渠道入站与网关；单独的原始记录（开发者 2026-11-18：NeuroBook 没有多渠道入站）；
- 本机口令（开发者 2026-11-18：先不做），代价写在第四节第 12 小节；
- 多个 bot、bot 之间的对话与群、子 bot、组织架构、分身；
- 主对话绑定某一本书（开发者 2026-11-18 同意不绑）；
- 普通会话里的周期任务（待定项 3）；
- 页面关掉时的提醒触达（系统通知、邮件），标签页标题的未读数；
- 搜索对话内容、让 bot 忘掉某段对话、重新开始对话、改写历史（编辑、重试、从此处分支）；
- 共享知识库、做梦整理、nb-memory；
- 关掉内置插件（开发者 2026-11-18：内置插件不做成能关）。

## 三、当前行为与证据

下面是 NeuroBook 现有、本稿要依赖或要改的地方。没注明出处的，见耦合审查。

- **会话服务**：`nbook.agent` 的服务 `agentKey` 能建会话、发消息、插话、订阅、发起任务（[`agent/sessions.md`](../specs/agent/sessions.md)）。句柄表只在会话没有引用、没有运行、30 秒内没有调用时关闭会话，订阅在取消之前一直持有引用（同一 Spec 输出 6 与“时序与寿命”）。会话列表缺省不列后台会话，可以按项目、归档、后台筛选，不能按归属筛选。会话头没有归属字段（[`harness/session.md`](../specs/harness/session.md) 的“会话头”）。
- **插件能接入的点**：经贡献点交出扩展、工具与 Profile；插件不能在自己的激活过程中建会话或打开会话（[`agent/contributions.md`](../specs/agent/contributions.md) 输出 3）；扩展有 `opening` 助手，在会话创建时与每次压缩之后取一次内容放进稳定槽（[`harness/extensions.md`](../specs/harness/extensions.md) 输出 30）。
- **内核**（[`harness/runtime.md`](../specs/harness/runtime.md)）：
  - 空闲时 `send` 同时开始运行；运行中 `send` 进缓冲区，这一轮结束时取走、接着开下一轮（输出 2、7）。
  - 发出者只有用户与会话（输出 45、85），宿主送进来的话在日志里和用户亲手输入的分不出来，`auto` 审批模型会把它当成用户的授权。
  - 审批与提问没有期限，也没有“过期”这个结算值（输出 39、43）。
  - 宿主发起的压缩不能指定原因与方法。
  - 重启后，没收口的运行以 `interrupted` 收口；对没有正常结束的运行，`start` 能不带新输入接着跑（输出 4、34）。
- **地址与审批**：单数地址 `session://`、`profile://`、`tmp://` 由 `nbook.agent` 按会话改写（[`agent/resources.md`](../specs/agent/resources.md)）。审批提案已接受：只写自有目录的调用在任何模式下都不问，自有目录里有“bot 的 `bot://`”，具体怎样进入随本稿定。
- **子代理**：`agent_spawn` 用父会话 Profile 白名单里的 Profile 建子会话；子会话的审批一律交给用户（[`agent/subagents.md`](../specs/agent/subagents.md)）。
- **运行守卫**：费用上限按会话一生累计（[`agent/run-guards.md`](../specs/agent/run-guards.md)），对一直写下去的主对话不合适。
- **对话视图**：nb-agent-ui 的核心不带界面，但分轮只认用户消息开头；审批向导会替换输入框；整段历史一次取完；适配器跳过扩展写的事件；整个视图只有一个助手身份。网页一侧的对话宿主（`session-host.ts`，1,751 行）只在 `nbook.agent` 浏览器入口里建，没有对外的服务，别的插件只能抄一份。
- **封闭名单**：命令域词表 `COMMAND_DOMAINS`、设置类别、内置插件显示名表；`nbook.tasks` 已被后台任务占用。
- **本机进程可信**：RPC 端口与 HTTP 写请求对不带 `Origin` 的本机程序放行，经 RPC 进来的调用一律当成用户本人（[`runtime/server-host.md`](../specs/runtime/server-host.md) 的已知限制）。
- **长会话**：打开时从头归约，事件全部常驻内存；实测 98,667 条事件打开要 1,140 ms、堆增 105 MB（负载约 24 时）。
- 同类产品的做法见前三稿用的两份调研（[商业产品](../../.agents/works/w00043-neurobot/research/2026-11-09-commercial-bots.md)、[开源实现](../../.agents/works/w00043-neurobot/research/2026-11-09-open-source-architecture.md)）：OpenClaw 的私信汇入一个滚动的主会话、靠压缩维持；nanobot 空闲 15 分钟自动压缩，摘要追加进历史文件；Claude Code 的 cron 到点往当前会话注入提示词，忙时排队；Grok Bot 后台工作引起的审批卡片 30 分钟过期。

## 四、方案

### 1. 概念

- **bot**：常驻的员工。有身份（名字、头像）、人设、所用的 Profile、自己的记忆、一条主对话。
- **Profile**：岗位，定义工具与提示词。一个 Profile 可以给多个 bot 用（开发者 2026-11-18 同意）。
- **bot 预设**：插件交出的模板，内容有名字、头像、Profile、人设与记忆种子。用户的 bot 按预设建出来，建出来以后是用户数据。
- **主对话**：每个 bot 一个常驻会话，用户不开、不切，长了靠压缩维持。用户看到的是“和 bot 的对话”，看不到“会话”。
- **宿主发出的消息**：由系统而不是用户写进主对话的话，例如到点的周期任务。它会开启一轮，但不算用户的授权。
- **会话**：现有的 Agent 会话，照常能用。bot 派的子代理也是会话。

### 2. 两个内置插件

| 插件 | 管什么 | 依赖 |
|---|---|---|
| `nbook.bots` | bot 与预设、主对话、`bots://` 方案与记忆、bot 视图、省钱压缩的计时 | `nbook.agent`、`nbook.files`、设置与存储 |
| `nbook.schedule` | 日程条目、到点触发、注入、日程视图与工具 | `nbook.bots` |

- 两个插件都不能关（开发者 2026-11-18），和别的内置插件一样。
- 依赖只能单向：`nbook.schedule` 经 `nbook.bots` 的服务往某个 bot 的主对话注入，`nbook.bots` 不知道日程。
- 要改的封闭名单：命令域加 `bot`、`schedule`，内置插件显示名表加两项；设置类别不加，bot 的设置放进现有的 `ai`。

### 3. bot、Profile 与预设

- 预设经 `nbook.bots` 的贡献点交出：`{id, name, avatar, profile, persona, memorySeed?}`，其中 `persona` 与 `memorySeed` 是插件包里的文件与目录。`nbook.bots` 自带一个缺省预设。
- 首次启动时如果还没有 bot，按缺省预设建一个。第一版只有一个 bot，没有新建、删除 bot 的界面；数据形状按多个 bot 设计。
- 建 bot 的步骤：分配 id，写 bot 记录，把人设复制成 `bot://persona.md`，把记忆种子复制进 `bot://memory/`。只在建的时候复制，以后预设更新不覆盖 bot 自己演进出来的内容。
- bot 记录只存身份、预设与 Profile 的引用、主对话的会话 id。模型、推理档、审批模式与 Agent 模式就是主对话的会话设置，不在 bot 记录里另存一份，用户在 bot 视图的输入框上照常改。
- **星璃与 w00050**（开发者 2026-11-18：“profile://memory 有了 bot 后应该改成 bot://”）：
  - 星璃做成一个预设：Profile 里留岗位的部分，人设与关系的设定进 `persona`，`profile://memory/` 里的文件做成记忆种子。
  - [w00050 t04](../../.agents/works/w00050-lyra-persona-and-prompts/tasks/t04-profile-memory-init-and-permissions/README.md) 的三项改由本稿覆盖：记忆的初始化改成预设的记忆种子；写记忆不问改由 `bot://` 进自有目录，`profile://` 不加免问；frontmatter 标的常驻注入按 bot 做（第 8 小节）。
  - bot 做出来之前，w00050 照旧用 `profile://memory/` 做实验；已有的实验记忆到时候手工搬进 `bot://memory/`，或者直接做成种子。
- `profile://` 留给同一岗位的几个 bot 共用的笔记，规则不变。

### 4. 主对话

- **建与持有**：主对话在第一次用到时才建，例如打开 bot 视图或第一次注入；不在插件激活时建，因为插件不能在自己的激活里建会话。建好以后，`nbook.bots` 订阅它，在服务端运行期间一直持有，所以句柄表不会关掉它；省钱压缩的计时也挂在这个订阅上。
- **归属**：会话头加一个可选的 `owner: {plugin, id}`，由宿主解释，内核不管。主对话的 `owner` 是 `{plugin: "nbook.bots", id: <bot id>}`。
  - 会话列表缺省不列有归属的会话，也不列它们的后代，所以 bot 派的子代理不会散落在会话列表里。
  - 自有目录与 `bot://` 的改写都按 `owner` 算（第 9 小节）。
  - 这是一个通用字段，以后别的插件持有的会话也能用。
- **不绑作品**（开发者 2026-11-18 同意）：主对话和现在没有主项目的会话一样，`project://` 不可用，工作目录是 `session://`。要碰哪本书在对话里说，或者用 `@` 引用文件，写作品照审批模式处理。代价：bot 不知道窗口里正打开着哪本书。
- **不轮换会话**：轮换要把会话私有的文件、设置、批准记忆带过去，第二次轮换时还会丢掉第一段的摘要。会话长到打开变慢时，在 nb-harness 加检查点快照，NeuroBook 的普通会话也受益。第一版只记录打开耗时，到时候按实测决定。
- **运行中来的消息**：bot 正在回复时用户再发的消息走插话（steer），进当前这一轮。插话在聊天里怎么显示，由 t03 的设计评审定。
- **重启**：服务端重启后，主对话里有被中断的运行时，`nbook.bots` 用 `start` 让 bot 接着处理，不伪造用户输入；自动接续有次数上限，防止同一次运行反复让进程崩溃。页面上显示“已自动继续”。
- **费用上限**：主对话的运行守卫按本地日历日累计费用，不按会话一生累计，否则常驻的主对话迟早顶到上限。上限的数值放在 bot 的设置里。

### 5. 宿主发出的消息与日程

**内核加一种发出者 `host`**（开发者 2026-11-18：注入的话要标明来源、不算用户的授权）：

- 宿主经 `session.as({kind: "host", source})` 发消息，`source` 是 `{plugin, label, ref?}`，例如 `{plugin: "nbook.schedule", label: "每周简报", ref: <条目 id>}`。日志里的输入记 `by: {kind: "host", source}`。
- 空闲时它开一轮；运行中它进缓冲区，当前这一轮结束时接着开一轮。这两条都是现有的 `send` 语义（第三节），内核只多认一种发出者。所以“由事件开启一轮”不用新的指令。
- 给模型时，这条消息前面加一行固定格式的来源说明，例如“[系统 · 日程「每周简报」· 计划时刻 …]”，让模型知道不是用户说的。
- 不算用户的授权：`auto` 的审批模型拿到的对话材料里，宿主发出的消息单独标出来，提示词写明它不代表用户的意图；用户的审批应答只认用户本人。
- 等用户时，宿主发出的消息不会结算挂着的审批（只有用户发的消息才会，见第 6 小节）。

前三稿还要内核在运行收口时写出扩展排着的外部事实，那是给“提醒写成扩展事件、并进下一轮”那个做法用的。本稿的提醒和周期任务都走宿主发出的消息，经内核的输入缓冲区，用不到这条改动，所以去掉。

**日程**（`nbook.schedule`）：

- 条目分一次性的（某时开会）与周期的；周期用 cron 表达式写，每天几点、每周几都是它的特例。每条有名字、触发时间、时区、目标 bot 与一段提示词；记谁建的、谁最后改的。
- 用户在日程视图里改，bot 用工具改，一个工具只做一件事（w00032 t14 决定 6）。日程工具只在主对话里能用，从别的会话调用时失败，码 `no-bot`（待定项 3）。
- 到点时，按“条目 id 加计划时刻”生成幂等键，以它作 `commandId` 往目标 bot 的主对话发一条宿主消息，内核的 `commandId` 去重保证只生效一次。发出之前先记下“该发”，服务端在两步之间崩溃时，重启后照记录补发。
- 提醒与任务是同一种机制（待定项 1）：提醒就是一段让 bot 提醒用户的提示词，bot 回一句话。
- 错过的（服务端没在运行）：周期条目错过几次合成一次补发；一次性条目过期超过一个时限就不发，在对话里补一条说明。时限在 Spec 里定。
- **重活交给子代理**（开发者 2026-11-18）：主对话里的 bot 用 `agent_spawn` 派子代理去干，自己只收结果。`nbook.bots` 自带一个“资料员” Profile，只装只读的文件工具与抓取工具（第 9 小节），放进缺省预设所用 Profile 的子代理白名单。子代理的审批与主对话一样带期限（第 6 小节）。

### 6. 等用户

沿用开发者 2026-11-10 的决定：

- 主对话里有审批或提问挂着时，输入框一直可用。用户发消息，先以拒绝结算挂着的事项，附上这句话（“没批准，用户说：……”），再把消息送进对话。这是用户本人的应答，以用户的名义结算是如实的。
- **期限**：内核的审批与提问可以带期限。到期由内核按“过期”结算，结算者记为内核，不冒充用户；调用得 `denied`，码 `expired`，给模型的文字说明用户不在、不要再申请同一操作，改在回复里说明。期限是会话设置，主对话缺省 30 分钟；子会话继承父会话的设置，所以 bot 派的子代理也不会一直卡着。
- 到期之后才到的点击，对话宿主提示已过期，不静默放弃。
- 前三稿的“拒绝或过期之后，同一调用在本次运行里不再申请”要另包一层审批钩子；本稿改成只靠给模型的文字，模型不一定照做，算已知限制。
- 记住按钮按审批提案的规则显示。主对话只有一个会话，“本会话都批准”实际上就是对这个 bot 一直有效，不再另设“按 bot 记住”。

### 7. 省钱的压缩

沿用前三稿：在阈值、溢出、手动三种之外再加两种触发，都是为了省钱（开发者 2026-11-09）。

- **缓存过期前压缩**：上一次对话请求之后，到服务商的提示词缓存快过期的时候，如果还没有新消息，就趁缓存还在，用就地方法（`inplace`，用会话的模型，前缀与对话请求相同）压缩一次。读上下文按缓存价算，下一条消息从短的上下文开始。
- **空闲压缩**：缓存已经过期的话，下一条消息本来要按全价重读整段上下文；所以空闲时先用“压缩”角色的模型（`summary` 方法）把上下文压短。

两种都只在划算时做，条件写成判断式，数值在 Spec 里定：

- 上下文要超过一个下限，两次压缩之间至少隔一段时间；否则在缓存寿命短的服务商上（例如 Anthropic 的短档是 5 分钟），用户每停顿几分钟就压一次，细节越压越少。
- 设置里配的是缓存档位，不是时长。实际寿命由 nb-models 按服务商、模型能力与凭据类型查表得出，在设置页上显示。模型适配器把档位显式传给服务商，不让环境变量 `PI_CACHE_RETENTION` 改掉它。
- 缓存过期前压缩只对寿命确定的显式缓存做。单价未知时不做；空闲压缩还要求压缩模型比会话模型便宜；订阅制的凭据不做。
- 指定的方法失败时不换别的方法：换了就省不了钱，宁可不压缩。
- 每次触发记下花费与估算的节省，跑一段后按真实数据调数值。

截止时刻从最后一次对话请求算起，加上缓存寿命，由会话日志算出，重启后照样算。运行中（含等用户）不计时。宿主发起的压缩进行中来了消息时：压缩请求已经发出的，等它做完再发这条消息；还没发出的就中止，中止的压缩不改对话。

归属：内核的压缩指令要能带原因与方法顺序；两种新触发的判断条件与截止时刻的计算放进 nb-harness kit，与应用无关；到点发起压缩的计时由 `nbook.bots` 持有。普通会话以后要用时，接同一块 kit。

### 8. 记忆

- **位置**：每个 bot 一个 `bots://<bot id>/` 根，主对话里写成 `bot://`。
  - `bot://persona.md`：人设。
  - `bot://memory/`：记忆文件，bot 用读写工具维护。
  - `bot://diary/<日期>.md`：日记，每次压缩后追加。
  - 写入经文件服务，按文件加锁、原子替换（[`workspace/resources.md`](../specs/workspace/resources.md)）。
- **常驻注入**：人设，加上 `bot://memory/` 里 frontmatter 标了常驻的文件（例如 `load: always`），在主对话创建时与每次压缩之后取一次快照，经 `opening` 放进提示词，不在每次请求时重读，否则一改就让后面整段对话的缓存失效。对话中改了，到下次压缩才进提示词。总长超过上限时，磁盘上保持完整，放进提示词的部分截断，并在写入工具的结果里提示已经超出。
- **其余按需**：用现有的 `grep`、`glob` 在 `bot://` 里检索，第一版不加新的检索工具。
- **日记**：每次压缩成功后，把这一段新增的内容追加进当天的日记，留给以后的整理处理，不多跑回合、不多花钱。压缩摘要是滚动的全量摘要，整段追加会让日记反复堆同样的内容；所以 bot 的压缩方法给摘要提示词多要一节“这一段新增的内容”，日记只追加这一节（摘要的小节由应用决定，见 w00032 t32）。
- **用户怎么看、怎么改**：`bots://` 的文件在工作台里像别的文件一样能打开、能编辑；在资源管理器里从哪里进，由 t03 定。
- 记忆分层（私有、组织、共享知识库）、做梦整理、nb-memory 的取舍，等 bot 跑一段后用真实记录做评测再定（开发者 2026-11-09）。会话日志只追加，压缩也不删，评测从它重放。

### 9. 工具、审批与工作目录

- **自有目录**：审批提案定的自有目录，对有 `owner` 的会话再加上 owner 插件登记的根。主对话的自有目录因此是 `session://`（除去宿主写的子目录）、`tmp://` 与 `bot://`。实现上，`nbook.bots` 登记 `bots://` 方案时声明单数地址 `bot://` 和“归属会话的自有根”，`nbook.agent` 按会话的 `owner` 改写与判断，不写死 `nbook.bots`。
- **谁能写 `bots://<id>/`**：用户、`nbook.bots` 自己、这个 bot 的主对话。别的会话（含这个 bot 派的子代理）只能读。子代理读外部网页后被注入的指令，因此改不了 bot 的记忆与人设。
- **抓取工具**：`nbook.agent` 加一个只读的内置工具 `fetch`（开发者 2026-11-10 定的只读抓取）：只取 http(s)，拒绝回环、链路本地与内网地址，结果标为外部内容。等级算读，任何审批模式下都不问，所以无人值守的周期任务也能用。代价是模型可以把数据拼进网址带出去，用户可以按网址写询问或拒绝规则。普通会话同样能用。
- 前三稿的任务会话、任务的工具清单、按会话裁剪工具集、按会话种类包一层审批钩子都不做（开发者 2026-11-18）。
- 审批模式就是主对话的会话设置。用户选“每次询问”时，无人值守的周期任务碰到要问的调用，等 30 分钟后过期失败，这是预期行为；在 bot 视图里说明。

### 10. 界面

外观与交互由 t03 按 design-review 出静态稿定，这里只定要求：

- **bot 视图**：显示一个 bot 的主对话，打开作品时与在书架页上都能进入；同一个 bot 只有一个视图实例，再打开只是聚焦。放在工作台的哪里（固定视图、侧栏容器、书架页的入口）由 t03 定。
- **对话宿主做成服务**：`nbook.agent` 的浏览器入口对外提供对话宿主（按会话 id 打开、带一组选项），`nbook.bots` 用它装 bot 视图，不抄一份 `session-host.ts`。
- **对话视图（nb-agent-ui）不拆成几种外壳**。差别做成消息与待处理事项上的可选字段，字段缺省时现在的行为不变：
  - 一轮由什么开启，以及来源的标签：宿主发出的消息自成一轮，不并进上一轮；
  - 谁说的话：助手身份可以按消息给；
  - 待处理事项停在哪里：bot 视图里审批与提问不替换输入框，两者并存；
  - 适配器加“扩展事件到消息”的映射入口；
  - 按需往前取历史：宿主实现 `history.loadPrevious`，适配器支持只应用路径的后缀；断线重连只补增量。否则一个活跃的 bot 用上几周，每次打开、每次重连都要整条重取、重画。
- **用法档**：会话、bot、会话加 bot 三种用法写进 nb-agent-ui 的 Spec，每档配 Lab 场景与挂载测试。
- bot 视图关掉：会话标题栏与“新会话”、改写历史的入口（编辑、重试、从此处分支）与分支树。重试两周前的一条，会让主对话的叶子退回那里，之后的周期任务与压缩点都落到被放弃的旁支上。
- 按天的分隔线；页面内“你离开后”的未读分隔线。最后看到的位置由 `nbook.bots` 按 bot 存，几个窗口共用；什么算“看到”在 Spec 里定。有未读时 bot 视图的入口怎么提示，由 t03 定。
- **日程视图**：列出条目，能增删改，并显示下一次触发的时刻。
- 首次运行：没有模型时引导去模型设置；主对话没有消息时显示空状态。

### 11. 数据

- `nbook.bots` 的数据在应用级的状态根下，不按作品放：
  - bot 记录与预设引用；
  - `bots://<bot id>/` 的真实目录；
  - 最后看到的位置。
- 主对话是普通的 Agent 会话，存在 `nbook.agent` 的会话库里，靠会话头的 `owner` 认出来。附件按现有规则存在会话目录里。
- 日程条目、“该发”与“已发”的记录由 `nbook.schedule` 存。
- 具体的布局与格式版本在 Spec 里定。

### 12. 安全

- **本机进程照旧可信**（开发者 2026-11-18：本机口令先不做）。已知风险：bot 无人值守地跑命令，只要有一条被注入的命令连上本机的 RPC 端口，就能以用户的身份批准审批、把审批模式改成全部放行、改审批规则与模型凭据。`fetch` 拒绝回环地址，挡不住 `shell`。在“自动判断”下，这类命令要由审批模型拦；在“全部放行”下没有任何关卡。以后接外部渠道或远程访问时，必须先补本机口令。
- 宿主发出的消息不算用户的授权（第 5 小节）。
- 外部内容：`fetch` 的结果标为外部内容；子代理写不了 `bots://`。主对话本身照样能读网页、能写自己的记忆，被注入的内容可能经它变成长期记忆，第一版靠用户能随时打开记忆文件查看与修改。

### 13. 第一版之后的路线

方向记录，不是承诺；每一步开工前另行讨论：

1. **NeuroBot 独立应用**：等要外部渠道（QQ 用 LLOneBot，开发者 2026-11-09 定）、远端设备或不开界面的常驻服务时再议。到那时再加单独的原始记录与本机口令。
2. **记忆**：用真实记录建评测，比较 nb-memory 与其它方案；共享知识库；做梦整理，写入长期记忆前检查来源；从预设重置记忆。
3. **多 bot**：新建与删除 bot 的界面、bot 之间的私聊与群、子 bot 与同级 bot、bot 判定别的 bot 的工具调用（开发者 2026-11-09）、分身共享记忆、bot 与电脑的对应可配置（开发者 2026-11-09 定缺省所有 bot 共享一台）。
4. **触达**：系统通知、标签页标题的未读数、按 bot 与按天的用量与费用、审批的过期倒计时。
5. **会话的检查点快照**，长会话的打开耗时到了预算时做。
6. 普通会话里的周期任务（待定项 3）；空闲时的连发合并。

### 14. 备选方案与取舍

- **NeuroBot 独立应用**（前三稿）：开发者 2026-11-18 按主 Agent 的推荐改成内置插件，主 Agent 当时给的理由是：NeuroBook 不需要多渠道与网关；服务端宿主、浏览器宿主、模型服务、设置、Agent 接线、对话视图都已在 NeuroBook 里，独立应用要另写设置、Agent 接线和网页对话宿主。这是主 Agent 的理由，不是开发者的。
- **Profile 与 bot 一对一，记忆留在 `profile://`**：w00050 现在就是这样。和 2026-11-09“bot 与 Profile 分开”的决定冲突，开发者 2026-11-18 选了分开。
- **主对话跟着当前打开的书走**：切书时上下文与权限都要跟着换。开发者 2026-11-18 同意不绑。
- **周期任务在单独的任务会话里跑，按清单裁剪工具**（前三稿）：开发者 2026-11-18 改成往主对话注入、重活派子代理。
- **单独的原始记录**（前三稿）：它是给多渠道入站、群里没有 @ bot 的消息与换记忆系统时重放用的。NeuroBook 没有多渠道入站，会话日志只追加、压缩也不删，已经是完整记录。开发者 2026-11-18 定不做。
- **用 `background: true` 把主对话藏出会话列表**：不用新字段，但“后台”的意思是任务中心发起的会话，`running()` 也不列后台会话，混用会让在跑的工作、活动指示这些地方看不到主对话。所以另加 `owner`。

## 七、待定项

1. **提醒与任务用不用同一种机制。** 前三稿的提醒是一段固定格式的文字，不开运行、不花钱，到点立刻显示；理由是主对话停在等审批时，提醒最多会晚 30 分钟。本稿的提醒也是宿主发出的消息，由 bot 回一句话。
   - 推荐用同一种机制。晚到只发生在用户不在页面前、审批挂着的时候，而第一版没有页面以外的触达，那时候直接显示也没人看见；用户在页面前时，一发消息就结算了审批。代价是每条提醒多一次模型调用（短，按会话的模型）。
   - 另一种是提醒单独走一条“直接显示”的路，要多一种对话事件、视图里多一种条目，还要内核在运行收口时写出扩展排着的事件。
2. **第一版要不要“待你处理”入口。** 前三稿有这个入口（开发者 2026-11-10 追认），用来收拢等批准的审批、任务被清单拒绝的调用、失败的任务、错过的提醒，每条能跳回对话里的原处。本稿没有任务会话和清单，剩下的几样都在主对话的流里。
   - 推荐第一版不做，放进路线的“触达”。等用户时有未读分隔线和待处理事项，过期与错过的都在流里留一条说明。
   - 要做的话，还要视图能滚到某条消息、能载入它附近的一段。
3. **普通会话能不能排周期任务。** Claude Code 的 cron 是排在当前会话里的。
   - 推荐第一版只给 bot 的主对话：主对话一直开着，普通会话空闲 30 秒就关，到点要重新打开；会话被归档、删除后条目会悬空。日程工具在普通会话里失败，码 `no-bot`，提示让 bot 去排。
   - 另一种是条目可以指向任意会话，到点时打开它再注入，并定好会话归档、删除时条目怎么处理。
