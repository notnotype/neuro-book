## 问题

1. **多项目放不进一个服务端实例。** 新应用的服务端只有一个内核实例，所有窗口共用。插件的服务端入口要么只能服务一个项目，要么每个接口都显式携带项目身份、内部按项目分开管理、项目关闭时自行清理（现行 [`runtime/plugin-channel.md`](../specs/runtime/plugin-channel.md) 与 [`storage/persistence.md`](../specs/storage/persistence.md) 的写法）。每个插件各做一遍多路复用，容易串项目、漏清理。
2. **只有浏览器与服务端两种运行位置。** 开发者要求设计时同时考虑 TUI；以后可能还有别的客户端。
3. **通道只有一个方向。** 现行通道 Spec 只允许浏览器调用本插件的服务端，并明确“不提供服务端向浏览器发请求并等待回复”。Agent 要读取界面状态、执行界面命令（例如“把分屏改成三七开”），必须由服务端调用某个客户端。
4. **HTTP 与插件通信混在一起。** 插件通道建在 `nbook.http` 的端口上；`nbook.http` 是插件，它重启或热升级会中断所有插件通信。
5. **插件访问数据的方式不一致。** `runtime/plugin-api.md` 用内核注入的 `ctx.storage`、`ctx.config`、`ctx.secrets`，而 t49 已把命令从内核 `ctx` 移到内置插件的服务。

## 目标与非目标

**目标**

- 插件作者按“一个入口服务一个项目”写代码；多项目由内核与宿主处理。
- 内核只有一套代码，服务端、项目、浏览器、TUI 都是它的实例，差别只在宿主适配器与注入的能力。
- 插件之间只有两种通信：同一实例内的本地服务、跨实例的远程服务；跨实例由内核路由，任意实例之间（包括客户端之间）可达。
- 一套对称的 RPC 协议，传输可替换（WebSocket、进程间通信）。
- HTTP 只服务浏览器原生加载与外部调用方。

**非目标**

- 不实现 TUI 宿主（本稿只保证拓扑容得下它）、登录与鉴权、跨设备同步、第三方插件安装。
- 不定插件状态 store 与配置的细节（见配套稿）。
- 不改已 `accepted` 的平台设计与 v2 提案正文；本稿通过后按“对 Spec 与提案的预期改动”修订。

## 当前行为与证据

- **内核已接近通用。** 运行位置是封闭类型 `RuntimeLocation = "browser" | "server" | "desktop" | "worker"`（`packages/nb-runtime/src/lifecycle/contracts.ts`），用法只有“入口位置等于本实例位置才装配”（`plugins/registration.ts`、`application/bootstrap.ts`）。`createApplication(host, manifest)` 与运行位置无关；`InstanceTable` 已能在一个宿主里按实例 id 管多个实例；`ApplicationManifest.capabilities` 是“装配方提供的本地能力”，可用来注入父实例的服务代理。
- **端口归插件。** `nbook.http` 的后端入口拥有 Bun 监听、准入、静态资源与 `http.routes` 贡献点（`packages/neuro-book/src/plugins/http/server/plugin.ts`；[ADR 0023](../adr/0023-v2-frontend-backend-stack.md) 决策 3）。
- **通道 Spec 是单向、按插件的**：浏览器入口只经本插件的通道访问本插件服务端；跨插件要先到自己的服务端入口再调用对方（`runtime/plugin-channel.md`“目标与非目标”）。该 Spec 为 `planned`，未实现。
- **G2 实测**（[t27](../../.agents/works/w00017-application-runtime-architecture/tasks/t27-platform-risk-gates/README.md)）：Bun 的 `worker.terminate()` 打断不了 WebAssembly 与原生阻塞调用。
- **VS Code 的做法**（[调研 02](../research/vscode/02-hosts-web-remote-server.md)、[调研 07](../research/vscode/07-extension-system-deep-dive.md)）：
  - 远程服务端是共享进程，放文件、终端、搜索、扩展管理等平台服务；每个窗口连接建立一条扩展宿主连接，扩展后端代码只服务该窗口的工作区。“每个连接各起一个扩展宿主进程”出自对源码结构的理解，调研未单独记录，未实机验证。
  - 主线程与扩展宿主之间是对称 RPC（`RPCProtocol`）：双方把服务登记成整数编号的 actor，按 `$方法` 互相调用，请求 id、ACK、结果或错误、取消消息，3 秒无 ACK 标为无响应；不共享对象引用。
  - 同一宿主内扩展经 `activate()` 的返回值共享任意 JS 值；不同宿主之间只能经命令这类异步、可序列化的边界。
  - 在当前窗口打开另一个文件夹会重新加载工作台（常识，未在调研中核对）。

## 方案

### 1. 实例角色

内核只有一套代码。实例按角色分四类：

| 角色 | 运行位置 | 数量 | 在哪 | 绑定项目 | 例子 |
|---|---|---|---|---|---|
| 服务端（应用级） | `server` | 每个服务端进程一个 | 服务端进程 | 不绑定 | `nbook.http`、Storage 的 user 分区、配置、项目管理、模型 |
| 项目 | `project` | 0 到 N | 每个打开的项目一个**子进程** | 一个 | 文件服务、History、Storage 的 project 分区 |
| 浏览器客户端 | `browser` | 每个窗口一个 | 浏览器标签页 | 0 或 1 个，一生不变 | 工作台、编辑器、资源管理器视图 |
| TUI 客户端 | `tui` | 每个会话一个 | 终端进程，连到服务端进程 | 0 或 1 个，一生不变 | 终端界面 |

- **运行位置改为宿主声明的字符串**，内核不列举。清单里的入口声明 `location`，宿主只装配与自己相同的入口。
- **差别只在四处**：宿主适配器（谁拥有进程与信号、谁给停止截止）、注入的能力、按 `location` 选中的入口、父子关系。
- 一个插件按需声明多个入口，例如 Files 有 `project`、`browser`，可选 `server`。

### 2. 子实例与项目生命周期

**分层**（开发者 2026-10-07 确认）：

- **内核**提供通用的子实例机制：父实例创建、停止子实例；父先启动、后停止；子实例的使用者登记与释放（租约）；子实例的身份即代次，停止后不复用。内核不认识文件与目录。
- **服务端宿主**定义“项目”：目录校验、项目身份、防止两个服务端进程同时打开同一项目的锁、按项目启动子进程。

**子进程**（开发者 2026-10-07 确定，不用 worker）：一个打开的项目一个子进程，内部运行一个 `location: "project"` 的内核实例。

- 选子进程的理由：G2 实测 worker 无法打断原生阻塞调用；子进程可以单独结束，崩溃与内存泄漏都不波及服务端；关闭项目时操作系统整体回收内存。
- 代价：每个子进程的启动时间与常驻内存，在第一个实现切片实测并记入 Spec。

**打开**：使用者（客户端绑定、Agent 会话、后台任务）向项目管理申请某项目的租约；项目没在运行就启动子进程并创建项目实例，已在运行就复用。

**关闭**：最后一个租约释放后，经过宽限期（避免刷新页面就重启项目；时长待定）停止项目实例：内核按依赖逆序停止入口，然后子进程退出。服务端停止时，先停全部项目子进程（有截止，超时强制结束），再停服务端实例。

**崩溃**：项目子进程意外退出时，路由通知绑定它的客户端“项目已停止”；客户端显示提示与“重新打开”。重新打开得到新的项目实例（新代次）。是否自动重启待定。

**不能隐式打开**：Storage 读取、外部 HTTP 请求（例如 webhook）都不得为了一次请求启动项目子进程；需要时由插件把事项持久化，等项目打开后再处理（第 9 节文生图例子）。

### 3. 客户端绑定

**客户端实例一生只绑定一个项目，或不绑定；切换项目等于重启客户端实例**（开发者 2026-10-07 确认）。

- 浏览器：项目写在地址栏 `/?project=<项目 id>`，切换项目即导航到新地址、页面重新加载。客户端插件永远不处理“项目换了”，旧项目的迟到结果不可能进入新实例。
- 握手：客户端宿主连上内核 RPC 端口后发送实例 id、客户端种类、要绑定的项目、各插件版本、客户端身份（浏览器跨刷新稳定的标识，供 Storage 的 `local` 分区使用，不同于每次加载都换新的实例 id）。服务端路由为它申请项目租约，记录连接表、绑定表、租约表，回复已绑定的项目实例。打开失败时回复原因，浏览器显示失败页（重试、回到书架）。
- 两个窗口打开同一项目时共用同一个项目实例：领域数据一份，界面状态各一份。
- 不绑定项目的客户端（书架、欢迎页）只与应用级入口通信。

### 4. 插件之间的通信

| 层 | 方式 | 范围 | 传什么 |
|---|---|---|---|
| 内核原语 | ① 本地服务（`provide`/`require`） | 同一实例 | 任意 JS 值：函数、只读响应式变量、事件回调；类以“接口 + 工厂函数”导出 |
| | ② 远程服务（内核路由） | 任意实例之间，客户端之间也由内核经服务端转发 | 可序列化数据，按合同调用与订阅 |
| | ③ 贡献点 | 同一实例 | 声明，加上交给拥有者的实现 |
| | ④ 激活事件 | 同一实例 | 控制信号 |
| 内置插件提供 | ⑤ 命令（`nbook.commands`） | 跨实例，建在 ③ ② 上 | 有 id 的动作，给人与 Agent |
| | ⑥ 公开状态与插件状态 store | 同实例经 ①，跨实例经 ② | 只读状态（见配套稿） |
| | ⑦ 共享数据加变更通知 | 间接 | Storage、配置、项目文件 |
| 对外边缘 | ⑧ HTTP（`nbook.http`） | 外部调用方、浏览器原生加载 | HTTP 请求 |

真正的传输只有 ① ②。本地服务的约定：变量导出只读视图，修改走导出的函数；提供方停止前内核先停依赖它的入口，重新激活后要重新获取。

**远程服务**（开发者 2026-10-07 确认由内核路由、可直达任意服务）：

- **合同**：用 TypeBox 声明方法（输入、输出、读或写、业务失败码）与事件（订阅过滤参数、事件内容），以及允许哪些实例种类调用。合同放在插件的共享模块，三端共用。内核依赖 TypeBox，API 以子路径 `@notnotype/nb-runtime/remote` 导出（开发者确认内核可依赖 TypeBox）。
- **提供**：`ctx.remote.provide(合同, (caller) => 实现)` 登记一次。同一实例内的调用方直接调用同一实现、不序列化；跨实例的调用经路由，按合同校验输入与输出。开发模式下本地调用也按合同校验，防止依赖序列化后不存在的东西。只在本地提供、含不可序列化内容的接口另登记为普通本地服务。
- **按调用方生成实例**：路由在每次调用上标记调用方（实例、插件、入口），提供方按调用方取得实例。Storage 与配置据此隔离各插件的数据；以后登录时据此限制使用者。这是本地服务的同一机制（内核改动，开发者 2026-10-06 确认）。
- **目标**：`.at("project")`（本客户端绑定的项目）、`.at("server")`、`.at({project: id})`（只对已在运行的项目，且调用方需持有租约）、`.at({client: instanceId})`。`ctx.remote.instances()` 列出当前实例：种类、绑定的项目。
- **结果**：`{ok: true, value}` 或 `{ok: false, code, ...}`。路由层失败码对所有服务相同：`target-gone`、`unavailable`、`timeout`、`unknown-outcome`、`version-changed`、`invalid-input`、`denied`、`cancelled`、`provider-error`；业务失败码在合同中声明。
- **按需激活**：远程调用到达时目标入口未激活，按 `onRemote:<服务 id>` 激活（开发者 2026-10-07 确认）；该前缀由内核路由保留。
- **不进激活依赖图**：远程服务随时可能不可用，调用时失败即可，不阻塞入口激活。这与 VS Code 跨宿主依赖要求被依赖方放弃导出 API 一致（t27 依赖调研）。
- **订阅**：提供方的 `subscribe(过滤参数, sink, {signal})` 按订阅调用；过滤是领域逻辑，由提供方做，路由只送达。订阅同时挂在订阅方连接与提供方实例上，任一结束即取消。同一订阅内按序送达；断线期间不补发，重连后发 `resync`，订阅方重取基线；事件可带 `revision` 以发现遗漏。

原通道 Spec 的“插件通道”成为“调用本插件远程服务”的特例；原“跨插件须先回到自己服务端”的限制取消。

### 5. RPC 协议

所有跨实例的边用同一套对称协议，传输可替换：

| 边 | 传输 |
|---|---|
| 客户端 ↔ 服务端 | WebSocket（开发者 2026-10-07 确认），连内核 RPC 端口 |
| 服务端 ↔ 项目子进程 | 进程间通信（具体机制在实现切片定） |
| 客户端 ↔ 客户端、客户端 ↔ 项目 | 经服务端路由转发 |

协议要素：

- 请求 id、ACK（只表示收到，不表示成功）、结果或错误、取消消息；两个方向各自的请求 id 空间。
- 超时与无响应检测；目标实例重启后，发往旧实例的请求一律失败。
- **结果未知**：请求已送出而连接断开时返回 `unknown-outcome`，写操作不自动重试；只读操作可以重试。不重放未确认的请求（VS Code 会重放；我们选择更简单的明确失败）。
- **版本核对**：两个方向都核对插件版本。
- **重入**：处理器不得在持锁时等待对方回复。执行界面命令这类短请求允许双向；需要等用户回答的长交互仍持久化为待办事项，不挂在一次 RPC 上。
- **二进制**：不经 RPC，走 HTTP 资源地址（第 7 节做法 B）。

### 6. 端口

**内核拥有一个 RPC 专用端口；HTTP 端口仍归 `nbook.http`。业务端口与内核端口分离**（开发者 2026-10-07 确认）。

- 浏览器从 HTTP 端口加载页面，RPC 端口经引导接口告知。TUI 直接连 RPC 端口。
- 两个端口来源（origin）不同：RPC 端口必须校验 WebSocket 握手的 `Origin`，否则任何网页都能连本机端口。Cookie 不按端口隔离，登录上线时两个端口会收到同一会话 Cookie，安全设计要覆盖。
- 页面是 https 时 RPC 用 wss，RPC 端口也需证书；反向代理需转发两个端口或按路径分流。
- 开发模式由 Vite 代理把 WebSocket 转到 RPC 端口。
- 两个端口都遵守“鉴权未加载时只监听回环地址”（`packages/neuro-book/src/server/config.ts`）。
- `nbook.http` 重启或热升级不影响插件通信。

### 7. `nbook.http` 的定位

`nbook.http` 是**对外的 HTTP 边缘**：路由表（`http.routes`）、准入与鉴权、静态资源、外部路由。插件之间不经它通信。需要它的场景：浏览器原生加载（`<img>`、`<video>` 的 Range 请求、字体、下载、前端构建产物、插件静态文件）与外部调用方（webhook、OAuth 回调、脚本、API 文档）。

项目级服务需要 HTTP 时：

- **做法 A：应用级入口登记路由，再 RPC 到项目入口。** 适合 webhook、OAuth 这类本身不属于某个项目的请求。目标项目没在运行时，由插件选择拒绝或持久化为待交付，不隐式打开项目。
- **做法 B：短时有效的资源地址。** 适合图片、下载。项目入口校验资源后，请应用级入口签发令牌（绑定项目实例、相对路径、过期时间）；浏览器请求该地址时，应用级路由校验令牌，直接从磁盘读取并支持 Range。字节不经过 RPC 与项目子进程。
- 做法 C（项目入口直接登记路由、由 `nbook.http` 按路径中的项目 id 转发）只适合小的 JSON 请求，等有需要再加。

### 9. 两个走查

#### Files：打开项目到关闭项目

```text
1. 窗口 W 打开 /?project=P → 浏览器宿主创建客户端实例 W
2. W 连内核 RPC 端口握手（实例 id、browser、项目 P、插件版本、客户端身份）
   → 服务端路由为 W 申请 P 的租约：P 没在运行 → 启动子进程，创建项目实例 P#1
   → 记连接表（W 在线）、绑定表（W → P#1）、租约表（P#1 被 W 使用）→ 回复已绑定 P#1
3. W 激活浏览器入口；资源管理器视图第一次可见时加载组件、激活 files 的浏览器入口
4. files 浏览器入口：remote(filesService).at("project").list({uri: "project://"})
   → 客户端内核打包（请求 id、目标、服务、方法、参数、调用方、版本）经 WebSocket 发出
   → 路由校验连接、把“绑定的项目”解析为 P#1、核对合同允许浏览器调用与版本
   → 标记调用方，经进程间通信转给 P#1，开始计时
   → P#1：files 项目入口未激活则按 onRemote 激活；按调用方取得实例；
     只读这一层：名字、文件或文件夹、按后缀识别的文件夹类型；不读内容、不解析 frontmatter、不递归
   → 结果原路返回；途中 P#1 停止返回 target-gone，W 已断开则丢弃
5. 浏览器入口把结果放进按目录分开的查询缓存并显示；订阅 changes({uri: "project://"})
6. 展开目录按需 list；项目里新建文件时（见下）只刷新对应目录
7. 第二个窗口打开 P：复用 P#1，各自有自己的缓存
关闭：W 关闭或导航走，租约随连接释放 → 宽限期后停止 P#1：files 关闭监视器、丢缓存，子进程退出
```

**项目里新建了文件**：

```text
来源一：W1 调用 files.create({uri}) → P#1 写文件，来源 = 调用方 W1
        → 立即发出 {kind: "created", uri, source: 调用方}；监视器随后看到同一变化，按来源记录去重
来源二：Agent 或外部程序直接写磁盘 → 监视器发现 → {kind: "created", uri, source: "external"}

同一实例：History 在 P#1 里经本地服务订阅同一变更流，不走 RPC
```

## 待定项

1. **Agent 会话放哪**：项目实例（随项目关闭，天然隔离）还是服务端实例（跨项目，需显式持有项目租约）。
2. **项目关闭的宽限期**时长；**崩溃后是否自动重启**。
3. **服务端与项目子进程之间的进程间通信机制**：在 K3 实测后定。
4. **`.at({client})` 的权限**：任意实例都能调用任意客户端，还是按合同的 `callers` 加上“只能调用与自己绑定同一项目的客户端”。
5. **项目管理界面插件的名称与范围**。

## 数据、接口、安全、迁移、发布与回滚影响

- **数据**：项目分区与项目文件只由对应项目实例写；不迁移旧应用数据。
- **接口**：远程服务合同、实例寻址、失败码是对插件公开的长期合同，随 Spec 定稿。
- **安全**：RPC 端口校验 `Origin` 并只监听回环地址；登录上线前不得放开监听地址。外部请求不得隐式启动项目子进程。
- **资源**：每个打开的项目一个子进程，K3 实测并给出上限或提示。
- **回滚**：K1 的内核改动以子路径导出、单独提交；K2 起每片可单独回退，浏览器宿主可退回只用 HTTP 引导。
