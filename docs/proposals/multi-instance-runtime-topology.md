## 问题

1. **多项目放不进一个服务端实例。** 新应用的服务端只有一个内核实例，所有窗口共用。插件的服务端入口要么只能服务一个项目，要么每个接口都显式携带项目身份、内部按项目分开管理、项目关闭时自行清理（现行 [`runtime/plugin-channel.md`](../specs/runtime/plugin-channel.md) 与 [`storage/persistence.md`](../specs/storage/persistence.md) 的写法）。每个插件各做一遍多路复用，容易串项目、漏清理。
2. **只有浏览器与服务端两种运行位置。** 开发者要求设计时同时考虑 TUI；以后可能还有别的客户端。
3. **通道只有一个方向。** 现行通道 Spec 只允许浏览器调用本插件的服务端，并明确“不提供服务端向浏览器发请求并等待回复”。Agent 要读取界面状态、执行界面命令（例如“把分屏改成三七开”），必须由服务端调用某个客户端。
4. **HTTP 与插件通信混在一起。** 插件通道建在 `nbook.http` 的端口上；`nbook.http` 是插件，它重启或热升级会中断所有插件通信。
5. **插件访问数据的方式不一致。** `runtime/plugin-api.md` 用内核注入的 `ctx.storage`、`ctx.config`、`ctx.secrets`，而 t49 已把命令从内核 `ctx` 移到内置插件的服务。

## 目标与非目标

**目标**

- 插件作者按“一个入口服务一个项目”写代码；多项目由内核与宿主处理。
- 内核只有一套代码，服务端、项目、浏览器、TUI 都是它的实例，差别只在宿主适配器与注入的能力。
- 插件之间只有两种通信：同一实例内的本地服务、跨实例的远程服务；跨实例由内核路由，任意实例之间（包括客户端之间）可达。
- 一套对称的 RPC 协议，传输可替换（WebSocket、进程间通信）。
- HTTP 只服务浏览器原生加载与外部调用方。

**非目标**

- 不实现 TUI 宿主（本稿只保证拓扑容得下它）、登录与鉴权、跨设备同步、第三方插件安装。
- 不定插件状态 store 与配置的细节（见配套稿），不定 Agent harness 的内部设计。
- 不改已 `accepted` 的平台设计与 v2 提案正文；本稿通过后按“对 Spec 与提案的预期改动”修订。

## 当前行为与证据

- **内核已接近通用。** 运行位置是封闭类型 `RuntimeLocation = "browser" | "server" | "desktop" | "worker"`（`packages/nb-runtime/src/lifecycle/contracts.ts`），用法只有“入口位置等于本实例位置才装配”（`plugins/registration.ts`、`application/bootstrap.ts`）。`createApplication(host, manifest)` 与运行位置无关；`InstanceTable` 已能在一个宿主里按实例 id 管多个实例；`ApplicationManifest.capabilities` 是“装配方提供的本地能力”。每次入口激活有独立的作用域与代次（`plugins/host.ts`）；提供者服务按提供者作用域 single-flight（`services/composition.ts`）。
- **端口归插件。** `nbook.http` 的后端入口拥有 Bun 监听、准入、静态资源与 `http.routes` 贡献点（`packages/neuro-book/src/plugins/http/server/plugin.ts`；[ADR 0023](../adr/0023-v2-frontend-backend-stack.md) 决策 3）。服务端宿主在 `beforeStop` 完成后才触发内核停止（`packages/neuro-book/src/server/host.ts`）。
- **通道 Spec 是单向、按插件的**：浏览器入口只经本插件的通道访问本插件服务端；跨插件要先到自己的服务端入口再调用对方（`runtime/plugin-channel.md`“目标与非目标”）。订阅同时登记在连接作用域与插件入口作用域上。该 Spec 为 `planned`，未实现。
- **G2 实测**（[t27](../../.agents/works/w00017-application-runtime-architecture/tasks/t27-platform-risk-gates/README.md)）：Bun 的 `worker.terminate()` 打断不了 WebAssembly 与原生阻塞调用。
- **VS Code 的做法**（[调研 02](../research/vscode/02-hosts-web-remote-server.md)、[调研 07](../research/vscode/07-extension-system-deep-dive.md)、t27 [依赖调研](../../.agents/works/w00017-application-runtime-architecture/tasks/t27-platform-risk-gates/evidences/deps-vscode/REPORT.md)）：
  - 远程服务端是共享进程，放文件、终端、搜索、扩展管理等平台服务；服务端按连接为每个窗口 fork 一个扩展宿主进程（t27 依赖调研的源码级记录，未实机验证），扩展后端代码只服务该窗口的工作区。
  - 主线程与扩展宿主之间是对称 RPC（`RPCProtocol`）：双方把服务登记成整数编号的 actor，按 `$方法` 互相调用，请求 id、ACK、结果或错误、取消消息，3 秒无 ACK 标为无响应；不共享对象引用。
  - 同一宿主内扩展经 `activate()` 的返回值共享任意 JS 值；不同宿主之间只能经命令这类异步、可序列化的边界。跨宿主依赖（被依赖方声明 `api: none`）在激活时**仍会经 RPC 等待**对方宿主激活成功，只是拿不到对方的导出对象。
  - 在当前窗口打开另一个文件夹会重新加载工作台（常识，未在调研中核对）。
- **旧应用的 Agent 会话**存在应用级目录 `<根工作区>/.nbook/agent/sessions`，每个会话有一个可改绑的“当前项目”（`packages/neuro-book-legacy/server/agent/session/`，从代码推断）。

## 方案

### 1. 实例角色

内核只有一套代码。实例按角色分四类：

| 角色 | 运行位置 | 数量 | 在哪 | 绑定项目 | 例子 |
|---|---|---|---|---|---|
| 服务端（应用级） | `server` | 每个服务端进程一个 | 服务端进程 | 不绑定 | `nbook.http`、Storage 的 user 分区、配置、项目管理、Agent 会话 |
| 项目 | `project` | 0 到 N | 每个打开的项目一个**子进程** | 一个 | 文件服务、History、剧情数据、Storage 的 project 分区 |
| 浏览器客户端 | `browser` | 每个窗口一个 | 浏览器标签页 | 0 或 1 个项目代次，一生不变 | 工作台、编辑器、资源管理器视图 |
| TUI 客户端 | `tui` | 每个会话一个 | 终端进程，连到服务端进程 | 同上 | 终端界面 |

- **运行位置改为宿主声明的字符串**，内核不列举。清单里的入口声明 `location`，宿主只装配与自己相同的入口。
- **差别只在四处**：宿主适配器（谁拥有进程与信号、谁给停止截止）、注入的能力、按 `location` 选中的入口、父子关系。
- 一个插件按需声明多个入口，例如 Files 有 `project`、`browser`，可选 `server`。
- **代码写在它要用的数据所在的地方**：要用项目里的东西（项目文件、项目 SQLite、project 分区）就写在 `project` 入口；只用应用级资源或直接操作磁盘的写在 `server` 入口。`project` 入口的代码里**不出现项目参数**，“这次操作哪个项目”由调用方定位到具体项目实例：客户端靠绑定，Agent 靠 harness（第 9 节）。

### 2. 子实例与项目生命周期

**分层**（开发者 2026-10-07 确认）：

- **内核**提供通用的子实例机制：父实例创建、停止子实例；父先启动、后停止；子实例的使用者租约；子实例的身份即代次，停止后不复用。内核不认识文件与目录。
- **服务端宿主**定义“项目”：目录校验、项目身份（存在项目目录 `.nbook/` 里、不随路径变化的项目 id）、项目登记表（项目 id、短名、当前路径）、按项目启动子进程。原先列出的“防止两个服务端进程同时打开同一项目的锁”已去掉（2026-10-07，见决策记录）：它保护的是项目实例独占的项目级持久数据，K3 还没有这类数据；出现时（K4 或 History）再定，优先用数据本身的机制。

**子进程**（开发者 2026-10-07 确定，不用 worker）：一个打开的项目一个子进程，内部运行一个 `location: "project"` 的内核实例。选子进程的理由：G2 实测 worker 无法打断原生阻塞调用；子进程可以单独结束，崩溃与内存泄漏都不波及服务端；关闭项目时操作系统整体回收内存。代价：每个子进程的启动时间与常驻内存，在 K3 实测并记入 Spec。

**项目实例的状态与租约**：

| 状态 | 含义 | 新租约请求的结果 |
|---|---|---|
| `creating` | 子进程启动、实例激活中 | 排队，随创建结果一起返回成功或失败 |
| `available` | 可用 | 立即取得 |
| `idle-grace` | 最后一个租约已释放，宽限期计时中（缺省 5 分钟） | 取消关闭，回到 `available` 并取得 |
| `stopping` | 内核正在按依赖逆序停止 | 不复活该代次；等它真正退出、拥有权收口后，以新代次重新创建（或因服务端正在停止而拒绝） |
| `terminated` | 子进程已退出 | 同一项目再打开得到新代次 |

- **打开**：使用者（客户端绑定、Agent 会话、后台任务）向项目管理申请某项目的租约；项目没在运行就创建。
- **不能隐式打开**：Storage 读取、外部 HTTP 请求（例如 webhook）都不得为了一次请求启动项目子进程；需要时由插件把事项持久化，等项目打开后再处理（第 10 节文生图例子）。
- **崩溃**：项目子进程意外退出时，该代次直接进入 `terminated`，所有租约失效，路由通知绑定它的客户端与持有租约的会话。不自动重启（2026-10-07 确认）。

**服务端停止顺序**（先封闭接纳，再释放）：

1. 原子地封闭新的客户端握手、项目子实例创建与租约取得；保留在途请求收口所需的 RPC。
2. 排空：等在途请求结束或到截止。
3. 停止全部项目子实例并等子进程真正退出；超时则强制结束，强制结束按“外部观察到的终止”记录，不报成内核正常关闭。
4. 停止服务端实例，最后关闭内核 RPC 端口。

### 3. 客户端绑定

**客户端实例一生只绑定一个项目代次，或不绑定；切换项目等于重启客户端实例**（开发者 2026-10-07 确认）。

- 浏览器：项目写在地址栏 `/?project=<项目短名或 id>`，切换项目即导航到新地址、页面重新加载。客户端插件永远不处理“项目换了”，旧项目的迟到结果不可能进入新实例。
- **握手**：客户端宿主连上内核 RPC 端口后发送 wire 协议版本、实例 id、客户端种类、要绑定的项目、各插件版本、客户端身份（浏览器跨刷新稳定的标识，供 Storage 的 `local` 分区使用，不同于每次加载都换新的实例 id）。服务端路由为它申请项目租约，记录连接表、绑定表（客户端实例 → 项目实例代次）、租约表，回复已绑定的项目代次。打开失败时回复原因，浏览器显示失败页（重试、回到书架）。
- **连接代次与绑定代次分开**。每条连接建立时分配连接代次，连接表按它登记；连接断开即结算这条连接上的全部在途请求（按第 5 节的阶段规则）与订阅。断线后同一客户端实例重连，建立新的连接代次：
  - 原项目代次仍在（宽限期内，或项目从未进入停止）：恢复原绑定，重建仍有效的订阅并发 `resync`；
  - 原项目代次已结束（宽限期已过、崩溃、服务端重启）：拒绝恢复，客户端实例必须重启（浏览器重新加载页面），旧请求、订阅、句柄与查询缓存随旧实例一起作废；**绝不把旧绑定改投新代次**。
- 两个窗口打开同一项目时共用同一个项目实例：领域数据一份，界面状态各一份。
- 不绑定项目的客户端（书架、欢迎页）只与应用级入口通信。

### 4. 插件之间的通信

| 层 | 方式 | 范围 | 传什么 |
|---|---|---|---|
| 内核原语 | ① 本地服务（`provide`/`require`） | 同一实例 | 任意 JS 值：函数、只读响应式变量、事件回调；类以“接口 + 工厂函数”导出 |
| | ② 远程服务（内核路由） | 任意实例之间，客户端之间也由内核经服务端转发 | 可序列化数据，按合同调用与订阅 |
| | ③ 贡献点 | 同一实例 | 声明，加上交给拥有者的实现 |
| | ④ 激活事件 | 同一实例 | 控制信号 |
| 内置插件提供 | ⑤ 命令（`nbook.commands`） | 跨实例，建在 ③ ② 上 | 有 id 的动作，给人与 Agent |
| | ⑥ 公开状态与插件状态 store | 同实例经 ①，跨实例经 ② | 只读状态（见配套稿） |
| | ⑦ 共享数据加变更通知 | 间接 | Storage、配置、项目文件 |
| 对外边缘 | ⑧ HTTP（`nbook.http`） | 外部调用方、浏览器原生加载 | HTTP 请求 |

真正的传输只有 ① ②。本地服务的约定：变量导出只读视图，修改走导出的函数；提供方停止前内核先停依赖它的入口，重新激活后要重新获取。普通共享服务保持现有语义（提供者作用域内 single-flight、一次产出）。

**远程服务**（开发者 2026-10-07 确认由内核路由、可直达任意服务）：

- **合同**：用 TypeBox 声明合同 id 与版本、方法（输入、输出、读或写、业务失败码）、事件（订阅过滤参数、事件内容），以及允许哪些实例种类调用。合同放在插件的共享模块，三端共用。内核依赖 TypeBox，API 以子路径 `@notnotype/nb-runtime/remote` 导出。
- **提供**：`ctx.remote.provide(合同, (consumer) => 门面)` 登记一次，本地与远程共用这一个提供者登记与工厂。同一实例内的调用方同样按消费方取得门面、同样核对调用方身份与激活代次，差别只在参数与结果不序列化；跨实例的调用经路由，按合同校验输入与输出。开发模式下本地调用也按合同校验，防止依赖序列化后不存在的东西。只在本地提供、含不可序列化内容的接口另登记为普通本地服务。
- **调用方身份**：路由在每次调用上标记调用方实例 id、插件、入口与**入口激活代次**。同一入口停止再激活是不同的调用方。
- **按调用方生成门面**（内核改动，开发者 2026-10-06 确认）：门面按“消费方实例 + 插件 + 入口 + 激活代次”生成，同一键 single-flight。门面归消费方的激活作用域：消费方停止即释放，提供方停止即永久失效；重激活只能拿到新门面，旧门面不复活；释放失败可诊断。门面里的内存状态不跨激活代次保留。“按插件归属、跨代次保留”只指已有持久拥有者的数据（Storage 记录、配置），由这些拥有者按各自合同保存与收口，不是门面或提供者入口持有的运行资源。
- **受控代理的委托**：客户端的 `nbook.storage`、配置插件这类代理，要代表原消费插件访问分区拥有者。内核为声明了代理能力的内置插件签发**消费上下文**：原消费插件、入口激活代次、稳定客户端身份、精确项目代次（登录上线后加使用主体）。上下文由内核签发，放在路由帧里与业务参数分开传递；业务参数里出现同名字段一律拒绝（沿用 [`workspace/resources.md`](../specs/workspace/resources.md) 写入来源“由宿主依调用路径填写，调用方不能自称”的做法）。普通插件之间的业务调用仍按本跳身份标记。第一版只允许内置插件声明代理能力。
- **目标**：`.at("project")`（本客户端绑定的项目代次）、`.at("server")`、`.at({project: id})`（只对已在运行的项目；调用方持有该代次的租约，或是服务端插件且项目处于 `available`，2026-10-07 确认）、`.at({client: instanceId})`。合同声明提供方位置（`provider: server | project | client | any`），能由合同推出目标时 `.at()` 可以省略：`server` 的合同省略即 `server`，`project` 的合同省略即本客户端绑定的项目；目标与提供方位置不符时类型检查与运行时都拒绝（2026-10-07 确认）。`ctx.remote.instances()` 列出当前实例：种类、绑定的项目。
- **按需激活**：远程调用到达时目标入口未激活，按 `onRemote:<服务 id>` 激活（开发者 2026-10-07 确认）；该前缀由内核路由保留。
- **不进激活依赖图**：这是 NeuroBook 自己的弱依赖决定——远程服务随时可能不可用，调用时失败即可，不阻塞入口激活（VS Code 的跨宿主依赖仍会等待对方激活，不作为依据）。为防止激活期间主动远程调用形成等待环：内核给激活期间发起的远程调用强制加默认超时上限，作者只能设得更短；路由帧携带激活链标记（业务参数不可见），路由沿 `onRemote` 激活链检测等待环，发现环时以 `unavailable` 失败并记诊断。
- **订阅**：提供方的 `subscribe(过滤参数, sink, {signal})` 按订阅调用；过滤是领域逻辑，由提供方做，路由只送达。订阅绑定**两端精确的入口激活代次**，跨实例时另绑定所经的连接：任一入口开始停止、提供的服务撤回、实例失效或连接结束，都取消订阅并拦截迟到事件。同实例的订阅按同样的入口作用域规则。同一订阅内按序送达；断线期间不补发；同一项目代次内重连只重建仍有效的订阅并发 `resync`，订阅方重取基线；事件可带 `revision` 以发现遗漏。

原通道 Spec 的“插件通道”成为“调用本插件远程服务”的特例；原“跨插件须先回到自己服务端”的限制取消。

### 5. RPC 协议

所有跨实例的边用同一套对称协议，传输可替换：

| 边 | 传输 |
|---|---|
| 客户端 ↔ 服务端 | WebSocket（开发者 2026-10-07 确认），连内核 RPC 端口 |
| 服务端 ↔ 项目子进程 | 进程间通信（具体机制在 K3 定） |
| 客户端 ↔ 客户端、客户端 ↔ 项目 | 经服务端路由转发 |

**请求的阶段与结果**：

| 阶段 | 失败时的结果 |
|---|---|
| 未派发（路由校验不过、目标不存在或不可用、未持租约、版本不兼容） | 确定失败：`invalid-input`、`denied`、`target-gone`、`unavailable`、`version-changed` |
| 已派发到目标实例、尚未收到结果 | 读操作：按原因报告，可重试。写操作：一律 `unknown-outcome`，附 `cause`（`target-gone`、`timeout`、`cancelled`、`disconnected`），不自动重试 |
| 目标执行并回复 | 成功，或业务失败码（合同声明），或 `provider-error` |

- ACK 只表示目标收到，不能证明没有副作用。
- 不重放未确认的请求（VS Code 会重放；我们选择明确失败，由领域按自己的合同恢复）。
- 两个方向各自的请求 id 空间；超时与无响应检测；发往已结束实例代次的请求一律在未派发阶段失败。

**版本分两层**：

- **wire 协议版本**在握手时核对，不兼容就在解析任何业务帧、激活任何入口之前拒绝。
- **合同版本**：每个合同带 id 与版本；路由按目标实际提供该合同的插件版本与消费方编译时依赖的合同版本核对，沿用插件的版本与兼容范围，不另建按方法的版本体系。路由各跳只转发原始期望，重连后也不改用“当前版本”。

**重入**：处理器不得在持锁时等待对方回复。执行界面命令这类短请求允许双向；需要等用户回答的长交互仍持久化为待办事项，不挂在一次 RPC 上。

**二进制**不经 RPC，走 HTTP 资源地址（第 7 节做法 B）。

### 6. 端口

**内核拥有一个 RPC 专用端口；HTTP 端口仍归 `nbook.http`。业务端口与内核端口分离**（开发者 2026-10-07 确认）。

- 浏览器从 HTTP 端口加载页面，RPC 端口经引导接口告知。TUI 直接连 RPC 端口。
- 两个端口来源（origin）不同：RPC 端口必须校验 WebSocket 握手的 `Origin`，否则任何网页都能连本机端口。Cookie 不按端口隔离，登录上线时两个端口会收到同一会话 Cookie，安全设计要覆盖。
- 页面是 https 时 RPC 用 wss，RPC 端口也需证书；反向代理需转发两个端口或按路径分流。
- 开发模式由 Vite 代理把 WebSocket 转到 RPC 端口。
- 两个端口都遵守“鉴权未加载时只监听回环地址”（`packages/neuro-book/src/server/config.ts`）。
- `nbook.http` 重启或热升级不影响插件通信。

### 7. `nbook.http` 的定位

`nbook.http` 是**对外的 HTTP 边缘**：路由表（`http.routes`）、准入与鉴权、静态资源、外部路由。插件之间不经它通信。需要它的场景：浏览器原生加载（`<img>`、`<video>` 的 Range 请求、字体、下载、前端构建产物、插件静态文件）与外部调用方（webhook、OAuth 回调、脚本、API 文档）。API 文档只覆盖显式对外的 HTTP 贡献；内部远程合同由内核的合同目录发现，不生成 HTTP 端点。

项目级服务需要 HTTP 时：

- **做法 A：应用级入口登记路由，再 RPC 到项目入口。** 适合 webhook、OAuth 这类本身不属于某个项目的请求。目标项目没在运行时，由插件选择拒绝或持久化为待交付，不隐式打开项目。
- **做法 B：短时有效的资源地址。** 适合图片、下载。字节不经过 RPC 与项目子进程：
  - 宿主在项目打开时给服务端签发该项目代次的**只读根授予**；令牌只在这个授予内缩小范围（相对路径、过期时间）。
  - 每次 GET、HEAD、Range 读取都重新核验：授予仍有效、项目代次未结束、真实路径仍在项目根内（沿用 [`platform/files.md`](../specs/platform/files.md) 的包含校验与 `nbook.http` 静态服务的真实路径检查）。项目停止或删除即撤销授予，新读取失败，已接纳的流按拥有者收口。
  - 第一版令牌是持有即可用的能力（只监听回环、短时有效）；登录上线后绑定使用主体并随授权变化失效。
- 做法 C（项目入口直接登记路由、由 `nbook.http` 按路径中的项目 id 转发）只适合小的 JSON 请求，等有需要再加。

### 9. Agent 会话

**Agent 会话运行在服务端实例，一个会话可以同时操作多个项目**（开发者 2026-10-07 选定，方案 C）。

- **`projects://`**：应用级的资源方案，由宿主的项目登记表提供。`projects://` 列出所有已登记项目（短名、是否打开）；`projects://<短名>/…` 指向某项目里的路径。项目身份与路径分离，项目根目录移动后 URI 不变。
- **路径替换**：只在需要真实路径的地方替换，例如 shell 命令与输出；模型平时看到和使用的始终是 `projects://`。
- **工具的位置**按第 1 节的判据：
  - 不需要打开项目的工具写在应用级：shell（在会话工作目录 `local://` 运行）、列出项目、在项目之间移动文件；
  - 需要项目里的东西的工具写在项目级入口，例如剧情插件的 `list_plot()`（要用项目的 SQLite）、项目文件的读写。代码里没有项目参数。
- **项目参数由 harness 注入与绑定**：
  - 工具声明（例如 `agent.tools` 贡献）带 `scope: "project"`；声明是静态的，不打开项目就能列给模型。
  - harness 给模型看到的工具参数里加一个 `project`；模型调用时，harness 解析项目、为会话取得该项目的租约（项目没在运行就打开，会话是用户发起的）、经 `.at({project})` 调用，去掉 `project` 参数，结果附上项目身份。
  - 会话同时持有多个项目的租约；空闲超时、租约被收回（项目关闭、删除、崩溃）后返回 `target-gone`，交给模型的结果说明项目已关闭，会话暂停等用户。
- **写项目文件经项目实例**：写入工具经项目的文件服务完成（记写入来源、通知 History 与打开着的窗口），项目没在运行就按需打开。shell 是明确的绕过通道：项目打开时它的改动被监视器记为外部来源；项目未打开时没有监视器，History 记不到这段改动，下次打开时磁盘内容照常可见。
- 打开项目前是否需要用户确认、空闲超时时长、会话数据存放位置，留给 nb-harness 设计。

### 10. 两个走查

#### Files：打开项目到关闭项目

```text
1. 窗口 W 打开 /?project=P → 浏览器宿主创建客户端实例 W
2. W 连内核 RPC 端口握手（wire 协议版本、实例 id、browser、项目 P、插件版本、客户端身份）
   → 服务端路由为 W 申请 P 的租约：P 没在运行 → creating：启动子进程，创建项目实例 P#1 → available
   → 记连接表（W 在线）、绑定表（W → P#1）、租约表（P#1 被 W 使用）→ 回复已绑定 P#1
3. W 激活浏览器入口；资源管理器视图第一次可见时加载组件、激活 files 的浏览器入口
4. files 浏览器入口：remote(filesService).at("project").list({uri: "project://"})
   → 客户端内核打包（请求 id、目标、合同 id 与期望的合同版本、方法、参数、调用方与激活代次）经 WebSocket 发出
   → 路由校验连接、把“绑定的项目”解析为 P#1、核对合同允许浏览器调用与合同版本
   → 标记调用方，经进程间通信转给 P#1，开始计时
   → P#1：files 项目入口未激活则按 onRemote 激活；按调用方取得门面；
     只读这一层：名字、文件或文件夹、按后缀识别的文件夹类型；不读内容、不解析 frontmatter、不递归
   → 结果原路返回。list 是读操作：未派发前 P#1 已停止返回 target-gone；派发后中断按原因报告，可以重试
5. 浏览器入口把结果放进按目录分开的查询缓存并显示；订阅 changes({uri: "project://"})
6. 展开目录按需 list；项目里新建文件时（见下）只刷新对应目录
7. 第二个窗口打开 P：复用 P#1，各自有自己的缓存
关闭：W 关闭或导航走，租约随连接释放 → idle-grace → 宽限期满进入 stopping：files 关闭监视器、丢缓存，子进程退出 → terminated
```

**项目里新建了文件**：

```text
来源一：W1 调用 files.create({uri}) → P#1 写文件，来源 = 调用方 W1
        → 立即发出 {kind: "created", uri, source: 调用方}；监视器随后看到同一变化，按来源记录去重
来源二：Agent 的 shell 或外部程序直接写磁盘 → 监视器发现 → {kind: "created", uri, source: "external"}
投递：P#1 对每个订阅了该目录的 sink 调用 next → 路由送到 W1、W2 与 TUI 会话 → 各自缓存插入条目
同一实例：History 在 P#1 里经本地服务订阅同一变更流，不走 RPC
```

#### 文生图：用到 `nbook.http` 与 Storage

插件 `example.text-to-image`：`browser` 入口提供命令与进度；`project` 入口记录本项目的任务并把结果写进项目；`server` 入口持有密钥、调用外部服务、向 `nbook.http` 登记回调路由 `POST /api/plugins/example.text-to-image/raw/callback`（第三方路由前缀见通道 Spec）。

```text
发起：W 执行“生成插图”→ project 入口记任务 jobs[任务 id] = submitted（project 分区）
      → RPC 到本插件 server 入口 provider.submit → 调外部 API
      → 记 pending[外部任务 id] = {项目 id, 任务 id, 状态: waiting}（user 分区）
回调（经 nbook.http）：外部服务 POST 回调 → server 入口校验签名、下载图片到 tmp://
      → pending[外部任务 id].状态 = ready（附临时文件）
      → 项目在 available 状态：server 入口经路由向该项目推送一个“有可交付结果”事件（事件推送不需要租约，不改变项目状态）；
        项目没在运行或处于 idle-grace：只置 ready，不推送、不唤醒、不取消宽限期，等下次激活时查询
交付（项目入口激活时或收到通知时）：
      → project 入口向 server 入口查询本项目 ready 的 pending（只读，不删除）
      → 按任务 id 幂等处理：jobs 已是 done 就跳过；否则经 Files 写 project://assets/x.png，jobs 改为 done
      → 写入完成后调用 server 入口 ackPending(外部任务 id) → server 入口才退役该记录、清理临时文件
      → 任一步失败或 unknown-outcome：pending 仍是 ready，下次激活或重试时重新处理；重复处理由任务 id 与 jobs 状态识别
显示（又经 nbook.http）：编辑器要显示图片 → files.resourceUrl 取得短时有效地址 → <img src> → nbook.http 路由按做法 B 核验后读磁盘返回
```

不引入跨存储事务；交付由领域记录的状态与幂等处理保证“结果终将落入项目”。

Storage 记录（定义方式见配套稿）：

| 记录 | 分区 | 存在哪个实例 | 谁写 | 别处怎么读 |
|---|---|---|---|---|
| `jobs`（按任务 id） | project / shared | 项目实例 | project 入口 | 窗口经插件自己的 `jobs` 服务读并订阅，不直接读记录 |
| `pending-callbacks`（按外部任务 id） | user / shared | 服务端实例 | server 入口 | project 入口经本插件 server 入口的 `listReady`、`ackPending` 领取与确认；确认后才退役 |
| `ui`（上次选的画风） | user / local | 服务端实例 | browser 入口经客户端代理 | browser 入口 |

## 待定项

1. **项目关闭的宽限期时长、崩溃后是否自动重启**：已定，缺省 5 分钟、不自动重启（2026-10-07）。
2. **服务端与项目子进程之间的进程间通信机制**：已定，Bun IPC（2026-10-07，实测见 [t54 实施计划](../../.agents/works/w00017-application-runtime-architecture/tasks/t54-project-child-process/plan.md)）。
3. **`.at({client})` 的权限**：任意实例都能调用任意客户端，还是按合同的 `callers` 加上“只能调用与自己绑定同一项目的客户端”。
4. **项目管理界面插件的名称与范围**：已定，`nbook.projects`，只做界面与给客户端的远程入口（2026-10-07）。
5. **Agent 会话的数据存放**（应用级还是随项目）、打开项目前是否确认、空闲超时：留给 nb-harness 设计。

## 数据、接口、安全、迁移、发布与回滚影响

- **数据**：项目分区与项目文件只由对应项目实例写；不迁移旧应用数据。
- **接口**：远程服务合同、实例寻址、调用方身份、委托上下文、失败码是对插件公开的长期合同，随 Spec 定稿。
- **安全**：RPC 端口校验 `Origin` 并只监听回环地址；登录上线前不得放开监听地址。外部请求不得隐式启动项目子进程。资源令牌只缩小宿主签发的只读根授予，每次读取重新核验。委托上下文只能由内核签发。
- **资源**：每个打开的项目一个子进程，K3 实测并记入 Spec；暂不设上限与提示，记为已知限制。
- **回滚**：K1 的内核改动以子路径导出、单独提交；K2 起每片可单独回退，浏览器宿主可退回只用 HTTP 引导。
