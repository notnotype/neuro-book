# Agent 审批：一份自有目录、去掉 Agent 的地址表、询问写明来源

来源：[w00043](../../.agents/works/w00043-neurobot/README.md) 2026-11-18，开发者看过现行审批的整理后说“这四关有点太复杂”，问“地址能不能写”能不能放进规则、模式闸门能不能用规则实现（“切换模式就是修改规则”），要一版新的方案。第一稿把模式与审批模式都写成规则组；三位审查者（后端、界面、拉远看）核出它在现有规则引擎里会改掉至少五处结论、复杂度没有降，本稿据此改写，处理见 [t01 的审查处理](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/approval-proposal-review-r1-disposition.md)。本文不能作为当前行为的依据。

## 一、问题

- **同一次写，结论随设置乱变。** 写 `session://a.md`：计划模式下不问，普通模式加“逐个确认”要问，自动模式下不问。根因只有一处：“只写草稿就放行”只在讨论、计划模式下算（`permissions/index.ts` 的 `gated`），普通模式下不算；自动模式另有一份免问名单（布局的 `localWrites`）。
- **说不清“为什么问我”“为什么没问我”。** 审批向导只显示规则的 `reason`、闸门的原因或审批模型的理由，看不出是哪一种来源；放行的调用在界面上完全看不到来源（判定的 `by` 只进日志）。
- **bot 写自己的记忆没有地方放。** 要“写自己的记忆不问”，现有机制里草稿只有闸门看，免问写只有自动模式看。
- **免问名单把会话写不了的位置也算进去了。** 草稿是整个 `session://`，包括只有宿主能写的 `attachments/`、`artifacts/`、`jobs/`，所以计划与讨论模式下 `echo forged > session://attachments/b.txt` 被当作“只写草稿”直接放行，来源记为 `mode:scratch`（[复现脚本](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/approval-proposal-review-r1-shell-hostdir-repro.ts.txt)）；`write` 工具写同一位置则被拒。`cd` 之后的相对重定向也算错：没有主项目时工作目录是 `session://`，`cd /别处 && echo x > f` 被算成写 `session://f`，计划模式下不问就写到了会话目录之外（[第二轮审查的复现](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/approval-proposal-review-r2-repro.test.ts.txt)）。这不是要让 `shell` 拦得住：规则不是安全边界，模型总能换一种写法（`cp`、`python -c`），那些写法照常按审批模式处理。问题只在审批自己主动免问的名单不该包含会话本来就不能写的位置。
- **Agent 另有一张地址分类表，大半没人用。** `nbook.agent` 的 `classify`（`backend/resources.ts`）只认五个方案，宿主写的目录在它与方案登记（`backend/schemes.ts`）里各列一份；产品代码里只有审批钩子读它，而且只用“写入要询问”（`user://`）这一项（`kit/approval/hook.ts`），“可写、不许写、是不是作品内容”没有消费者，写入是否允许由文件服务按方案登记的授权决定。

## 二、目标与非目标

目标：

- “写这里没事”只剩一份名单：**自有目录**。只写自有目录的调用，在任何 Agent 模式、任何审批模式下都放行。
- 自有目录只含会话本来就能写的地方，不含宿主写的子目录。
- 去掉 Agent 的地址分类表；能不能写只由文件服务按方案登记判断。
- 每次询问写明来源，记住类按钮随来源显示；放行的来源在工具调用的详情里看得到。

非目标：

- 不把模式闸门与审批模式写成规则（第四节第 4 小节说明为什么）。
- 不改规则的写法、匹配器与三层合并；不做操作系统沙箱（规则仍然不是安全边界）。
- bot 的会话怎样记下属于哪个 bot、怎样拿到 `bot://`，属于 bot 的提案；本稿只定“自有目录由宿主按会话给”。

## 三、当前行为与证据

- 判定顺序（[`agent/permissions.md`](../specs/agent/permissions.md) 输出 1，nb-harness `kit/approval/judge.ts` 的 `decide`）：规则拒绝、闸门拦写、规则放行、规则询问、闸门下只写草稿、读、审批模式。
- 开发者已定（[w00032 t06](../../.agents/works/w00032-agent-integration/tasks/t06-approval/plan.md) 2026-11-06，[`agent/permissions.md`](../specs/agent/permissions.md) 输出 7）：规则从上到下第一条命中；作品里的规则只收询问与拒绝；讨论、计划下放行规则与全部放行都过不了模式闸门；全部放行下询问规则也放行；写 `user://` 一律要问，全部放行下放行。本稿都不改。
- 草稿豁免当初是为了让计划模式能写 `plan.md`（t06 计划“闸门怎样算写”）；“只在闸门下生效”“普通模式加逐个确认下写自己的会话目录也要问”没有写下来的理由（在 `docs/specs`、`docs/adr`、t06 计划里没搜到）。
- 同类产品（[w00032 的 Agent 模式调研](../../.agents/works/w00032-agent-integration/research/2026-11-06-agent-modes-survey.md)）：Claude Code 的权限模式（含计划模式）与 allow、ask、deny 规则是正交的两样；omp、Codex 的计划模式都是独立状态。没有一家把计划模式写成用户规则。

## 四、方案

### 1. 能不能写只在文件服务，删掉 Agent 的地址表

能不能写是数据归属，像操作系统的文件权限：会话日志只有内核写，附件、全文、后台任务输出只有宿主写，别的会话的 home 不归这个会话。它由文件服务按方案登记的授权规则判断，对界面、插件、Agent 所有调用方一样生效。Agent 的文件工具写不了的地方在执行时失败（`permission-denied`），和“文件不存在”同类。审批在执行之前判定，不知道写不写得了：逐个确认下照样先问，批准后得到同样的失败；不为此在审批里再判一次授权（第 5 小节）。

不放进规则，因为规则是用户的偏好，一条放行规则或全部放行就能改掉；能不能写保的是别人的数据，而且对界面与插件同样要成立。

要改的：

- 删掉 `nbook.agent` 的地址分类表与套件文件访问的 `classify`。新方案（例如 `bot://`）能不能写，只看它的插件登记的授权。
- `user://` 的“写入总要问”留在审批钩子里，判法与位置都不变，名单改由宿主布局给（`confirmWrites`，NeuroBook 是 `["user://"]`）。不写成路径规则：写路径算不出时，规则会按“命中”算，自动模式下 `echo x > "$F"` 一类的调用就会从交审批模型变成问用户。
- 文件服务的授权只管文件工具与别的调用方；`shell` 直接写磁盘，不经它（已知限制）。命令的写由审批处理，审批不承诺拦得住（规则不是安全边界）；只是下一小节的免问名单（自有目录）不能含会话本来就不能写的位置。

### 2. 自有目录

自有目录是会话自己的地方，由宿主按会话给：

- 会话的 `session://`，**不含**宿主写的 `attachments/`、`artifacts/`、`jobs/`；
- `tmp://`；
- bot 的会话再加它自己的 `bot://`（随 bot 的提案）。

宿主写的子目录，方案登记与自有目录共用一份名单和同一个判断，按名字比较不区分大小写（同作品控制目录 `.nbook` 的判法）。现在两处都区分大小写：大小写不敏感的卷（Windows、macOS 默认）上，`write session://Attachments/a.txt` 能写进宿主的附件目录（从代码推断，未在这两种系统上验证），这次一并改。

布局里的 `scratch` 与 `localWrites` 换成三项：

- `own`：自有目录，`{roots, except}`；`except` 是根下不算自有目录的子目录（NeuroBook 是 `session://` 下的三个宿主子目录），按名字比较不区分大小写。
- `autoWrites`：自有目录之外、自动模式下写入工具免问的根（NeuroBook 有主项目时是 `["project://"]`，没有时为空）。自动模式免问的写因此仍是“写入工具只写自有目录与作品”，同现在。
- `confirmWrites`：写入总要问的根（第 1 小节）。

判定顺序不变，只改第 5 步：

1. 规则拒绝：拒绝。
2. 讨论、计划模式下拦写（不是读、也不是只写自有目录）：拒绝，或按 `modeWriteAction` 询问；放行规则与全部放行都不能放过。
3. 规则放行：放行。
4. 规则询问：询问；全部放行下放行。写 `user://`（第 1 小节），以及作品的规则文件读不了时的写与执行，在这一步强制询问，同现在。
5. **只写自有目录：放行。**现在这一步只在讨论、计划模式下算，改成在任何模式下都算。
6. 读：放行。
7. 按审批模式：逐个确认询问；放行写入放行写、询问执行；自动下写入工具只写自有目录与 `autoWrites` 的放行，其余交审批模型；全部放行放行。

“只写自有目录”的判断同现在的闸门：有写路径，全部落在自有目录里，命令都只读；看整次调用，不按单条命令拆开算；没有交出写路径的写入或执行工具不算。另加一条：一次调用里有改工作目录的命令（`cd`、`pushd`、`popd`）时，相对路径的写重定向算不出。`shell` 每次调用都从工作目录起，不跨调用保留 `cd`，所以只看这一次调用就够。

对用户的说法因此是三样东西、两条固定：你的规则、Agent 模式（讨论、计划时拦写）、审批模式（没有别的结论时怎么办）；没有规则拦着时，会话自己的目录（含临时目录）写了不问，改用户设置总要问。

### 3. 询问写明来源，放行也看得到

- **来源要能送到界面。** 现在送不到：内核的询问只带 `reason` 与 `remember`，NeuroBook 用缺省的转问，钩子分出的来源在这里丢掉。界面靠 `reason` 里的固定串认出模式闸门与审批模型，用户规则的 `reason` 写成同样的串就能冒充；写用户设置、作品规则文件读不了、审批模式三种询问没有 `reason`，分不开。改法：钩子交给内核的询问与放行都加一个宿主定义的字段 `cause`，内核不解释，原样写进审批请求与 `toolStarted.approval`，同 `remember`；`by` 保留现在的取值，旧日志照旧读，没有 `cause` 的不显示来源。规则的命中结果带上是哪一层、哪一条。界面只看 `cause`，不再认 `reason` 里的固定串。字段不叫 `source`：待处理事项的 `source` 已经表示“来自后代会话”，带它的进停靠区。
- **来源有这些**：
  - 询问：你的规则（附 `reason`）、作品的规则、计划或讨论模式、写用户设置总要问、作品的规则文件读不了、审批模式（例如“逐个确认”）、审批模型转问（含审批模型这次没判成）。
  - 放行：你的规则、本会话批准过、自有目录、读、放行写入、全部放行（放过了一条询问规则时写明）、自动模式免问、审批模型批准、你批准的。
- **审批向导**第一行写这次为什么问。
- **记住类按钮按它起不起作用显示**：

  | 询问的来源 | 本会话都批准 | 以后都允许 |
  |---|---|---|
  | 你的规则、作品的规则 | 显示 | 不显示 |
  | 审批模式、审批模型转问 | 显示 | 显示 |
  | Agent 模式、写用户设置总要问、作品的规则文件读不了 | 不显示 | 不显示 |

  规则询问时，“以后都允许”记的放行加在我的规则末尾，层内先命中的仍是原来那条询问，作品层的询问也排在我的放行之前，以后照样问（[复现](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/approval-proposal-review-r2-repro.test.ts.txt)）；“本会话都批准”记在会话层，排在询问之前，起作用。最后一行的三种询问都盖过规则的结果，记下的放行规则不起作用；现在写 `user://` 时点“以后都允许”还会写进一条与本意不符的放行规则（没有可记的命令，按“整个工具”记，结果放行了所有路径的写）。
- **工具调用的详情**里加一行小字写放行来源（例如“放行：自有目录”“放行：本会话批准过 · `git diff *`”“放行：自动模式免问”“放行：审批模型”），由 `cause` 映射文案。
- **设置里的权限规则页**加一段固定说明：没有规则拦着时自有目录写了不问、写用户设置总要问、四档审批模式各做什么。不做“此刻生效的全部规则”整页视图：这一页不属于任何会话，而模式与审批模式是按会话存的。
- **文案**：“逐个确认”的说明改成“除读取、规则放行的、只写会话自己目录（含临时目录与命令的输出重定向）的调用外，每次都要批准”；非普通模式下审批模式控件变淡时的提示随之改。

### 4. 为什么不把模式闸门写成规则

可以写，但在现有规则引擎里会改掉已定的结论，要补齐就比现在更复杂。第一稿这样做过，审查核出：

- 规则按单条命令求值，“只写自有目录”是整次调用的性质：`cat a > tmp://x && ls` 里 `ls` 那一条会触发模式层拒绝，现在是放行。
- 规则引擎对放行规则有两条豁免（看不懂的命令、有写重定向时只认路径规则），写成缺省规则的“全部放行”“只写自有目录放行”会对 `eval touch a`、`echo x > tmp://a` 得不出结论。
- 计划模式加“放行写入”或“自动”下，命令只写草稿会从放行变成询问或交审批模型。
- “作品的规则文件坏了，写与执行都问”在规则层里没有位置：放进作品层，会被“本会话都批准”盖掉。
- 写 `user://` 写成路径规则后，写路径算不出的调用都会变成问用户。

要补齐，就得让内置的几组规则不走这些豁免、按整次调用求值，并在三处为全部放行特判，规则引擎因此多出一套只给内置规则用的语义。同类产品也是把模式放在规则之外（第三节）。所以 Agent 模式仍是“一段提示加拦不拦写”；以后加模式（例如“只许改设定、不许改正文”）时，再看拦写需要哪些可配置的条件。

### 5. 备选方案与取舍

- **第一稿：模式、审批模式、写用户设置都写成规则组**：见第 4 小节。不选。
- **只把 `bot://` 加进草稿**：普通模式加“逐个确认”下照样要问，自动模式的免问名单还是另一份。不选。
- **判断自有目录时对每个写路径再按方案授权试判一次**：授权函数是同步的，挂载点的目录要异步建好，`projects://`、`user://` 没有授权函数，只能试判按地址的那一次；不如宿主写的子目录共用一份名单与判断。不选。
- **来源继续放在 `reason` 的固定串里，不改内核**：用户规则的 `reason` 写成同样的串就能冒充，三种询问没有 `reason`，放行没有地方放。不选。
- **把审批钩子从 nb-harness 的宿主套件挪回 NeuroBook**（审查者指出放进套件的理由是第二个宿主 NeuroBot，而它已暂停）：挪回没有收益，NeuroBot 只是暂停。不选。

## 五、影响

- **行为变化**：
  1. 普通模式下，只写自有目录的调用在任何审批模式下都放行：逐个确认下用写入工具写 `session://`、`tmp://`，或命令只把输出重定向到那里（`cat a.md > tmp://x`），都不再问；放行写入下 `echo x > tmp://a` 不再问；自动模式下这类命令不再交审批模型。讨论、计划模式下的结论不变。
  2. 宿主写的子目录（`session://attachments/` 等，名字不分大小写）在任何模式下都不算自有目录：命令重定向写它们不再免问，按审批模式处理（计划与讨论模式下拦写）；自动模式下写入工具写它们从“免问、执行时失败”变成先交审批模型、批准后失败。
  3. 有 `cd`、`pushd`、`popd` 的命令里，相对路径的写重定向算不出：计划与讨论模式下 `cd sub && ls > out.txt` 从放行变成拦写；带路径条件的规则按“算不出”处理。
  4. 审批向导的记住按钮按第四节第 3 小节的表显示。
  5. 文件服务：`session://Attachments/a.txt` 这类大小写变体不再能写进宿主的子目录。
- **数据**：规则格式不变。会话日志的审批请求与 `toolStarted.approval` 多一个可选的 `cause`，旧日志没有它，照旧读、不显示来源。`by` 的取值不变（`mode:scratch` 仍表示只写自有目录），但普通模式下原来记为 `mode:allow-writes`、`mode:auto`、`mode:yolo` 的一部分放行会改记 `mode:scratch`，按 `by` 统计或断言的地方会看到分布变化。
- **接口**：
  - nb-harness 内核：`ApprovalVerdict` 的询问与放行加 `cause`，进审批请求与 `toolStarted.approval`（[`harness/runtime.md`](../specs/harness/runtime.md) 输出 17、39）。
  - nb-harness 套件：规则的命中结果带层与条；文件访问去掉 `classify`（本机参考实现 `kit/files/local.ts` 的写授权留作构造选项，去掉 `"ask"` 一值）；布局的 `scratch`、`localWrites` 换成 `own`、`autoWrites`、`confirmWrites`（[`harness/host-kit.md`](../specs/harness/host-kit.md) 输出 2、3、10）。
  - `nbook.agent`：共用合同里删掉 `ResourceClass`（内置插件里没有别的使用方）；宿主子目录的名单与判断只留一份。
  - nb-agent-ui：待审批数据与工具调用的数据各加 `cause`。
  - 现在只有 NeuroBook 一个宿主，同一次改完。
- **激活**：“只写自有目录”要看判定对象，只在它能改变结论时取：非读，并且审批模式不是全部放行，也不是放行写入下的写入工具。现在普通模式下只有规则需要时才取；改后逐个确认下每次非读调用、放行写入下每次执行调用都取。工具提供方还没激活时会在审批之前激活：插件代码先跑，再弹审批，用户拒绝了也已经激活，同现在的计划与自动模式（[`agent/permissions.md`](../specs/agent/permissions.md) 输出 9，[`agent/contributions.md`](../specs/agent/contributions.md) 输出 5）。没激活时按声明的等级判（作者常写成执行），非命令的执行工具不算自有目录；激活后实现按参数给出写，同样的参数第二次可能就不问。内置工具的提供方本来就在运行，影响的只是第三方工具。
- **安全**：放宽只在会话自己的目录；宿主写的子目录与 `cd` 之后的相对重定向收紧。自动模式的审批模型照旧只看用户亲手打的字；定时注入进对话的话要标明来源、不算用户的授权，归 bot 的提案。
- **测试**：`builtin-tools.test.ts` 的五个审批预览用例靠“逐个确认下写 `session://` 会停下等批准”，改成写作品（换成有主项目的世界）；nb-harness 里构造 `SessionFiles` 的测试（`hook`、`restore`、`kernel-resources`、`local` 与几个工具的测试）换布局形状；合同测试里断言 `classify` 的三个用例删掉或改断言授权。
- **迁移与回滚**：没有数据迁移；回滚代码即可，新日志里的 `cause` 旧代码不读。
