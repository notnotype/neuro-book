# 插件的数据与状态

## 状态

reviewing（2026-10-06 起草，2026-10-07 按开发者确认的总览改写，同日按 omp 审查修订，交开发者审批）。

本稿回答一个插件的全部数据各是什么、存在哪、谁写、谁能读，以及插件作者用什么入口声明它们。拓扑（实例角色、项目子进程、远程服务、端口）见配套的 [多实例运行时拓扑](multi-instance-runtime-topology.md) 与 [ADR 0024](../adr/0024-multi-instance-runtime-topology.md)；本稿的“实例”“远程服务”“按调用方生成实例”都按那里的定义。分类沿用 [`storage/boundaries.md`](../specs/storage/boundaries.md) 的四类（Config、Storage、内存、领域数据），在其上细分插件作者实际会遇到的情况。

## 问题

1. 讨论 Storage、配置与命令的 `when` 时，几类数据混在一起：组件开关、请求回来的数据、前端算出的临时数据、布局、设置、插件贡献的视图与菜单。
2. 旧应用的教训：
   - `packages/neuro-book-legacy/app/stores/novel-ide.ts` 一个 store 2309 行，文件、正文、会话、布局都在里面；持久化对整个 store 深度监听，3000 个文件时切换文件 0.9–1.6 s（[t42](../../.agents/works/w00017-application-runtime-architecture/tasks/t42-files-baseline-research/README.md)）。
   - 主题保存把整份 Global Config 快照写回，缺字段的 `costCurrency` 被服务端默认值重置（`app/composables/useThemeSettings.ts` 的注释）。
3. 插件作者需要一个统一的入口来声明自己的状态，而不是分别面对运行状态、Storage、配置与上下文键四套东西。

## 目标与非目标

**目标**

- 给出一组判据，任何一项插件数据都能据此归位。
- 给出插件作者的统一入口：插件状态 store。
- 定下 `when`、Storage、配置之间的关系。
- 定下 Storage 的命名空间、分区与实例归属，以及配置的读写规则。
- 用工作台举例走一遍。

**非目标**

- 不定 Storage 与配置的完整接口与失败语义（随各自的 Spec 与实现切片）。
- 不做跨设备同步。

## 方案

### 1. 一项数据要回答的问题

| 问题 | 可选值 |
|---|---|
| 是什么 | 配置（用户主动设定的偏好）、Storage（程序替用户记住的）、运行状态（只在内存）、派生（算出来的）、贡献声明（别的插件交来的）、文件或资产（大二进制）、地址栏、领域数据 |
| 作用域 | 应用级（跨项目）或项目级；再加 `local`（只给这个客户端）或 `shared`（所有客户端共用） |
| 存在哪个实例 | 服务端、项目子进程，或客户端（每个窗口一份） |
| 谁写、怎么写 | 设置界面或配置文件、插件的 action（多数登记成命令）、用户拖动、贡献方插件启用或停用 |
| 是否公开 | 私有；或公开只读，供 `when`、Agent、别的插件读 |
| 多窗口之间 | 即时同步、共用记录但不强行改对方的显示、各窗口独立 |

### 2. 十类数据

| # | 类别 | 例子 | 存在哪 | 活多久 | 谁能读写 |
|---|---|---|---|---|---|
| 1 | 组件内部状态 | 下拉框开合、未提交的输入 | 组件的 `ref` | 组件卸载即丢 | 组件自己 |
| 2 | 插件运行状态 | 面板最大化、紧凑呈现、焦点、命令面板最近使用 | 插件状态 store 的内存字段 | 入口停止即释放 | 插件内部；对外只经公开状态 |
| 3 | 服务端数据的前端副本 | 文件树某层的列表、最近项目列表 | 拥有者插件的客户端入口，按查询分开缓存 | 收到变更事件时重取；客户端实例结束即丢 | 拥有者插件；别的插件经它的服务读 |
| 4 | 派生数据 | 工作台呈现模型、命令筛选结果、`when` 结果 | `computed` 或纯函数 | 来源变化即重算，不存 | — |
| 5 | Storage | 布局、视图定制、展开的目录、最近项目 | `nbook.storage`；分区归对应实例（第 5 节） | 直到拥有者删除 | 拥有者插件 |
| 6 | 配置 | 主题、界面语言、字体、默认模型、用户自定义菜单与快捷键 | 配置插件：默认值、用户层文件、项目层文件 | 文件在即在 | 所有插件可读；声明者可写 |
| 7 | 密钥 | API Key | 配置插件的服务端，加密落盘 | 同上 | 只在服务端，不发往客户端 |
| 8 | 领域数据 | 正文、Agent 会话、History、项目文件 | 各领域；项目内的在项目实例 | 按领域合同 | 按领域合同 |
| 9 | 启动配置 | 端口、State Root、日志位置 | 宿主 | 改后须重启 | 宿主；插件只读结果 |
| 10 | 地址栏 | `/?project=…`、`/lab?component=…`、本标签页刷新后要保留的选择 | URL | 跟着标签页、刷新与链接走 | 拥有该页面的插件；读到的值逐项校验 |

另有两样不是“状态”但要归位：**贡献声明**（别的插件交来的视图、菜单、主题）由内核目录管，随贡献方启用而存在；**大文件**（图片等）放文件或资产服务，不进配置与 Storage 记录。

### 3. 插件状态 store：作者的统一入口

插件作者用一个 `defineStore` 声明本插件某块状态的全部来源（开发者 2026-10-07 确认）：

```ts
const workbench = defineStore("workbench", {
    // 读配置：自己声明的可读可写，别的插件声明的只读
    config: {theme: config("workbench.theme"), locale: config("application.locale")},
    // 持久化：映射到 Storage 记录；什么时候写由 action 决定
    persisted: {sizes: persist(sizesRecord), customizations: persist(customizationsRecord)},
    // 只在内存
    memory: {maximized: false, compact: false, focusedPart: "editor"},
    // 派生：不存
    derived: {presentation: (s) => buildPresentation(s.customizations, contributedViews, s.compact)},
    // 公开：只读投影，供 when、Agent、别的插件读
    public: {
        panelPosition: (s) => s.customizations.panel.position,
        compact: (s) => s.compact,
        layoutReady: (s) => s.sizes.ready && s.customizations.ready,
    },
    // 写入的唯一途径；需要给人与 Agent 用的登记成命令
    actions: {setPanelPosition(position) { /* 校验 → 改 customizations → 提交 Storage */ }},
});
```

与 Pinia 的区别，都针对旧应用的问题：

| Pinia 的默认做法 | 这里 | 理由 |
|---|---|---|
| 全局单例，谁都能读写 | 归插件所有，默认私有，只有 `public` 对外 | 内部字段不变成别人依赖的合同 |
| 任何地方都能直接改 | 只经 `actions` | 单一写入方 |
| 持久化插件深度监听整个 store | 每个字段声明落到哪条记录，写入时机由 action 决定（例如拖动结束才保存） | t42 的深度监听问题 |
| 什么都往里放 | 服务端数据的副本（第 3 类）不放进来，走查询缓存 | 同上 |

store 随插件入口激活创建、停止时释放；它在哪个实例里定义，就属于那个实例。

**持久化字段不是一份值。** `persist(record)` 绑定的字段至少持有（承接 [`storage/persistence.md`](../specs/storage/persistence.md) 的“布局投影与保存反馈”与状态转换）：

| 部分 | 含义 |
|---|---|
| 读取分类 | 缺失、正常、损坏、版本不支持、读取失败；损坏与版本不支持时不允许普通保存覆盖原件 |
| 已确认值与 revision | 最近一次读到或保存成功的值 |
| 当前显示 | 界面此刻用的值；拖动等手势只改它 |
| 未保存意图与保存状态 | action 提交的修改、正在保存、失败待重试 |

- 默认值只用于呈现，不自动保存。
- 订阅只更新已确认值，不改当前显示；什么时候把新确认值应用到显示，由拥有者在 action 或恢复时机里决定（另一窗口保存时不强行改本窗口布局）。
- 同一记录按提交顺序串行保存；冲突后由拥有者的窄 reducer 只重放本次主动修改的字段，再条件保存一次；失败保留意图与当前显示，提供重试与放弃。不做通用 JSON 合并。
- 公开状态投影当前显示，并公开“已就绪”“可保存”这类键。

**K5 与 K6 的分界**：`defineStore` 的 `config` 字段在 K5 固定声明形状；真实的配置来源与变更链在 K6 接入，K5 不交付桩实现。

### 4. 公开状态与 `when`

**`when` 只读本实例内存里的公开状态，不直接读 Storage 或配置**（开发者 2026-10-06 至 10-07 讨论确认）：

- Storage 与配置在别的实例，读取异步、可能失败；`when` 在列出命令、分发快捷键的那一刻求值，必须同步、不失败。
- 存储里的值不等于当前显示：窄窗口临时进入紧凑呈现时，存储里的面板位置没变，但面板命令此刻已不可用。

```text
Storage 记录 ──(打开时读取，之后订阅)──┐
配置有效值 ───(推到本实例，之后订阅)───┼──> store 的内存状态 ──(public 投影)──> 公开状态
运行状态 ─────────────────────────────┘                                        │
                                       ┌─────────────────┬─────────────────────┤
                                       ↓                 ↓                     ↓
                                   when 求值         Agent 读取          同实例的其它插件
```

- 公开状态是运行状态上一个有名字、只读、稳定的窗口。登记时交出读取函数，不复制数据。只公开标量给 `when`；复杂数据仍走插件的服务。
- 为什么不直接暴露整个运行状态：`when` 写在可序列化的声明里，只能按名字引用，需要一张键表；内部字段一旦被别人引用就成了合同；服务端的命令表拿不到客户端的响应式对象。
- **读取就绪之前**公开状态给出默认值，同时公开“已就绪”的键（例如 `layoutReady`），命令可据此判断此刻能否执行。
- **键名与类型静态声明，值在激活时绑定。** 命令的 `when` 在登记时校验（`workbench/commands.md`），这发生在不执行插件代码的描述层，懒激活插件的 store 此时还不存在。所以公开键的限定名、标量类型、未就绪时的取值与拥有者写在清单里，和命令一样是顶层声明；store 激活时只为本入口代次绑定读取函数，入口停止即撤回。合法但尚未绑定的键按“未就绪”求值；引用未声明的键、类型不符仍在登记时拒绝；插件被禁用时按既有声明撤回规则处理。
- **在本实例求值；镜像按客户端隔离。** 服务端命令若要按客户端状态判断，由客户端把那部分公开状态同步到服务端，`when` 不跨实例查询。服务端保存的镜像按**精确的客户端实例与入口代次**分开，一个窗口一份；执行或列出命令时，上下文显式选定目标客户端（Agent 默认是发起会话的窗口），没有进程级的“当前窗口”。镜像缺失、重连后等待基线、来源入口停止，都按“未就绪”处理。客户端命令到达目标客户端后，仍按该客户端的本地状态复查一次。
- 上下文键是公开状态里的标量子集，不再单独是一套机制。配置的有效值也以 `config.<键>` 形式进入公开状态。

### 5. Storage

- **按插件划分命名空间，不按入口。** 拥有者就是插件 id；同一插件的任何入口都能读写本插件的记录。内核按调用方生成 Storage 服务实例，每个插件只能访问自己的命名空间。
- **分区归实例**：

  | `nbook.storage` 的入口 | 在哪 | 管什么 |
  |---|---|---|
  | `server` | 服务端进程 | user 分区，`StateRoot` 下 |
  | `project` | 每个项目子进程 | 本项目的 project 分区，`ProjectRoot/.nbook/storage/` |
  | `browser`、`tui` | 客户端 | 不存数据；同样的接口，读写经远程服务转给分区的拥有者 |

  project 分区随项目关闭而关闭；一个项目同时只有一个项目实例，加上项目锁，project 分区只有一个写入方。

  客户端代理不能用自己的身份转发：那样服务端看到的调用方会变成 `nbook.storage`。代理经内核签发的**消费上下文**转发，上下文携带原消费插件、入口激活代次、稳定客户端身份与精确项目代次，不能由业务参数自报（拓扑稿第 4 节）。本地直用与经客户端代理访问的是同一个命名空间。
- **记录定义**写在插件的共享模块里，三端共用；第一次打开时登记，同名不同形状的定义被拒绝：

  ```ts
  export const sizesRecord = defineRecord({
      key: "layout-sizes", scope: "project", locality: "local", version: 1,
      schema: Type.Object({sidebar: Type.Number(), auxiliaryBar: Type.Number(), panel: Type.Number()}),
  });
  const sizes = storage.open(sizesRecord);
  const current = await sizes.read();            // status: missing | ok | corrupt | unsupported-version | error
  await sizes.save(next, {expect: current.revision});   // 条件保存：{ok, revision} 或 {ok: false, code}
  ```

  可按资源 id 寻址（`keyed: true`），例如按任务 id 一条记录。
- **别的插件或带业务逻辑的读取经插件自己的服务**，不直接共享记录。例如文生图的任务列表经插件的 `jobs` 服务读与订阅（拓扑稿第 9 节）。
- **不做 session/window 作用域**：本标签页刷新后要保留的状态放进 URL（第 10 类，开发者 2026-10-06 确认）。
- **大文件不进记录**：放文件或资产服务（开发者 2026-10-06 确认）。

### 6. 配置

- **层**：声明里的默认值 → 用户层 → 项目层，合成有效值。字段可声明“只允许用户层”。
- **声明**：配置项经贡献点声明：键、TypeBox schema、默认值、标题与说明（中英文本）、允许的层、改后是否需要重启、是否密钥。
- **读写**（开发者 2026-10-07 确认）：所有已声明的配置项都可只读访问，插件写入只限声明者。按键写入、按键通知，避免旧应用“整份快照写回”带来的连带修改。
- **用户编辑是另一条授权路径**：设置界面要能修改任何插件声明的配置项，但它不能靠“普通插件写别人的键”实现，也不能让任何入口声称“这是用户改的”。用户编辑由配置插件自己的设置界面经宿主签发的用户编辑能力完成，明确可写的层、按 schema 校验并记审计；普通插件拿不到这项能力。VS Code 也区分宿主的用户编辑流程与扩展经代理更新设置（[调研 05](../research/vscode/05-configuration-system.md)、[调研 07](../research/vscode/07-extension-system-deep-dive.md)）。具体形式在 K6 设计轮定。
- **界面语言**（开发者 2026-10-07 确认）：由配置插件声明为平台级设置，只允许用户层；客户端即时切换，不需要重启（`LocalizedText` 在渲染时取语言）。服务端与 TUI 同样读取它。
- **用户自定义菜单与快捷键**（开发者 2026-10-07 确认）：用户编辑的配置文件，类似 VS Code 的 `keybindings.json`。用户右键“隐藏”的菜单项属于 Storage。
- **密钥**：配置插件的服务端，加密落盘，任何接口都不发往客户端。
- **启动配置**：宿主在插件加载前读取，改后须重启，插件不能贡献。
- **从展示到保存**：

  ```text
  声明：插件贡献配置项
  读取：配置插件服务端读用户与项目两层文件，逐键校验，合成有效值；不合法的键丢弃并记诊断，原文件保留
  推送：有效值推到各实例并订阅变化
  展示：设置界面按声明选控件，显示有效值及其来源层
  保存：设置界面经用户编辑能力（插件自己写自己的键则经普通写入）update(键, 值, 目标层)
        → 按 schema 与允许的层校验 → 只改文件里这一个键 → 重新合成 → 通知所有实例
  外部改文件：文件监视 → 同一条通知
  失败：校验不过返回原因；写盘失败不报已保存
  ```

- 多窗口：配置变化即时同步到所有实例。

### 7. 配置与 Storage 怎么分

1. 用户会去设置界面改的是配置；程序看用户操作、替他记住的是 Storage。同一概念可两边都有：“侧栏默认在左”是配置，“用户把某视图拖到右栏”是 Storage 里的定制；读取时先看定制，没有再看配置的默认值。
2. 贡献声明不是 Storage：别的插件交来的视图、菜单、主题由内核目录管。用户对它们的调整按第 1 条归位；贡献方插件被禁用时按平台设计 P7 清理其布局项，用户手写的配置不删。
3. 大文件不进配置也不进 Storage：配置只记引用。

### 8. 工作台走查

| 数据 | 是什么 | 作用域 / 存放 | 所在实例 | 谁写 | 公开 | 多窗口 |

### 9. 组件怎样接触数据：能力标签

上面的分类回答“数据是什么”；组件规范的能力标签回答“一个组件经哪条通道碰到数据”。每个组件在同名 `.md` 里如实声明，Component Lab 按标签推导它能否单独挂载（`packages/neuro-book/src/plugins/lab/web/component-index-model.ts` 的 `deriveMountability`）。

| 标签 | 含义 | 碰到的数据类别 | Lab 怎么处理 | v2 里的去向 |
|---|---|---|---|---|
| 无标签 | 只靠 props 与 emits | 父组件传什么就是什么 | 可挂载 | 公共零件只允许这一种或 `state:local` |
| `state:local` | 自己持有临时状态 | 1 | 可挂载；fixture 可经数据 sink 上报只读快照 | 不变 |
| `state:shared-read` | 直接读 store | 旧应用的 Pinia store，相当于 2 或 3 | 可挂载，要预置快照 | 读插件状态 store 的公开字段或拥有者的缓存；要写理由 |
| `state:shared-write` | 直接写 store | 同上 | 不可挂载 | 只允许宿主组件，且只经 action |
| `state:inject` | 经 provide/inject 拿数据或能力 | 宿主给的上下文 | 到宿主场景里看 | 视图的 `ViewContext`、插件交给组件的服务句柄 |
| `persist:local`、`persist:session`、`persist:idb` | 直接访问浏览器存储 | 5 | 不可挂载 | 产品组件不再直接碰浏览器存储，由宿主经 store 的持久化字段读写；Lab 自己的偏好是开发工具的例外 |
| `io:read`、`io:mutate`、`io:stream` | 自己发请求、写请求、建订阅 | 3、8 | 不可挂载 | 只允许宿主组件；请求入口可替换 |
| `env:*` | 定时器、路由、全局监听、剪贴板、渲染到自身之外 | 10（`env:route`）等 | `env:portal` 同 `state:inject` | 不变 |

推荐配方把隐藏通道收在少数宿主组件里；组件用事件把可观察状态报给宿主，由宿主维护公开状态。

## 待定项

1. **store 放在哪、用什么响应式内核**：三端都用 `@vue/reactivity`（不依赖 DOM），浏览器组件直接消费；store 放内核子路径还是独立的运行时库。
2. **查询缓存工具库**（第 3 类）：按查询键缓存、合并相同请求、记录加载与错误、收到变更事件时过期重取。现成的有 TanStack Query、Pinia Colada；建议等第二个消费者出现再决定用现成库还是自写。
3. **只读检视**：开发模式下按插件列出 Storage 记录、配置有效值与来源层、公开状态的当前值，也可供 Agent 经命令读取。等 store、Storage、配置都有了再定。
4. **配置设计轮（K6）的问题**：用户编辑能力的来源与审计；是否需要内存层或策略层；设置界面放页面、视图还是编辑器区域；首版是否只给命令与 JSON 文件；第一个消费者（主题、界面语言）；启动配置与现有环境变量如何合并；背景图片等引用文件的配置项跨设备同步时，文件如何跟随。

## 数据、接口、安全、迁移、发布与回滚影响

- **数据**：Storage 与配置都写在 `StateRoot` 与 `ProjectRoot/.nbook/` 下；新应用未发布，不迁移旧数据。
- **接口**：`defineStore`、`defineRecord`、配置声明与公开状态都是对插件公开的长期合同，随 Spec 定稿。
- **安全**：密钥只在服务端；按调用方生成实例使插件只能访问自己的 Storage 命名空间（第一版完全信任，防误用不防恶意）。
- **回滚**：store 是对 Storage、配置与公开状态的封装，可单独回退为直接使用服务。
