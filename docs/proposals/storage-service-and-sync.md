# Storage 跨设备同步的后续设计

- 状态：draft
- 日期：2026-09-15
- 更新：2026-09-16；本地持久化已移入获批 Spec，本提案只保留跨独立 data 的在线同步未决项
- 已确定的架构边界：[storage.boundaries](../specs/storage/boundaries.md)
- 已确定的本地行为：[storage.persistence](../specs/storage/persistence.md)
- 取舍依据：[ADR 0021](../../packages/neuro-book/docs/adr/0021-local-storage-persistence.md)

## 问题

首期按本地 Spec 提供持久化、同后端多客户端隔离与备份恢复。
未来若要在独立运行的两套 data 间自动接续，需要处理身份对齐、冲突、删除与恢复；普通 KV 和完整备份不能自动提供这些保证。
本提案不启用同步，不重新决定已批准的本地服务与首批消费者归属。

## 目标与非目标

目标是决定独立 data 之间哪些状态可以复制以及如何收敛。
范围包括跨实例身份关联、复制确认、冲突、删除、离线恢复和同步版本兼容。
Config 的 Global/Project 及统一同步目标保持不变；本提案不重新设计 Config，不把正文、草稿、Session、Job 和历史转为普通 KV。
命令系统、协同编辑和第三方可执行插件隔离另有边界。

## 当前行为与证据（本地服务实施前）

- 主 Workbench 的左右尺寸来自 `novel.ide.local`，World Engine 的三个尺寸仍是 ref，未接通用 Storage。
- `novel.ide.session` 同时含项目编辑器、用户资产编辑器、当前项目和选择记忆，不能整桶迁 Project。
- 当前 Project 引用使用 Workspace Root 下的目录名；进程 key 和锁哈希依赖本机 Workspace 路径。
  Project manifest 尚未提供可直接作为跨设备身份的字段。
- 桌面存在连接远端服务的模式；服务端只有一份不分客户端的状态不能满足“设备本地”。
- `resolveViewStateLayer` 当前仅由聚焦测试调用。接线前必须补充有效上下文判断，不能单凭残留 `projectRoot` 选分区。

上述结论来自 [源码审查记录](../../.agents/works/w00003-neurobook-ui-foundation-migration/tasks/t21-storage-design-review/walkthroughs/001-storage-review.md)，
不表示新服务、身份映射或同步已经存在。

## 方案、备选方案和取舍

首期已经确定 scope=user/project、locality=local/shared 且默认 local，具体含义以持久化 Spec 为准。
后续复制只能在 owner 明确允许的状态中选择；不提供 Config 逐项同步选择功能。

备选方案：

- 全部同步：简单，但会把设备尺寸、本地路径和活动现场传播到不适用的设备；不推荐。
- 本地持久化加备份恢复：已选为首期；独立副本轮流使用，不自动合并分叉。
- 按状态定义决定：推荐。成本是每个 owner 要声明哪些状态可迁移、如何处理冲突和恢复。

### 已确定的本地消费者与后续候选

| 消费者状态 | 建议 scope | 建议属性与待决策项 |
|---|---|---|
| 主工作台左右栏、World Engine 尺寸 | project | local，已确定；World Engine 整页尚未迁移 |
| 无项目/用户资产工作面、普通 Dialog 尺寸 | user | local，显式记录，不作 Project 读取失败 fallback |
| 视图排序、明确隐藏偏好、布局结构 | user | 本地首期 local；与尺寸拆键，未来启用复制需另定兼容 |
| 项目置顶对象 | project | 共享候选；稳定对象身份和并发增删必须先闭合 |
| 当前 Tab、滚动位置、最近项目 | 按对象归属；最近项目为 user | 推荐设备本地；跨设备接续单独定义应用时机 |
| 拖拽、焦点、请求进度投影 | 内存 | 不持久化；不能把领域任务的权威进度只留内存 |

## 在线同步仍需闭合的行为决定

下表中的本地读写、快照订阅、revision、客户端隔离与故障分类已有 Spec；待定的是它们如何扩展到独立 data 的复制。

| 决定 | 需要明确的可观察结果 | 当前建议与限制 |
|---|---|---|
| 身份对齐 | 两套独立身份域、项目副本是否建立关联 | 必须显式配对；本地路径或同名账号不能证明身份相同 |
| 复制确认 | 本地持久化后何时可报告另一设备已收到 | 独立报告复制状态，不能改写本地保存结果 |
| 同键分叉 | 两边离线修改后合并或拒绝的结果 | 按 owner 的状态语义设计，不通用后写覆盖 |
| 重试 | 离线消息重投、结果不明时怎样避免重复应用 | 需要复制操作身份与保留窗口；本地 revision 不能代替复制日志 |
| 删除收敛 | 离线设备恢复后是否复活旧记录 | 需要删除确认和回收协议；本地阶段保留删除标记 |
| 版本与迁移 | 新旧同步协议、local/shared 或 scope 改变时如何处理旧记录 | 保留未知版本，迁移与回滚必须有独立兼容边界 |
| 远端应用时机 | B 正在拖拽/编辑时 A 的变更何时生效 | 保存值与当前显示分开，禁止抢占；何时采用远端值仍待各消费者确定 |
| 同步拓扑与离线 | 共用服务和各自 State Root 的同步保证是否相同 | 两种部署都存在需求；先定一个交付范围，不能宣称同一个 KV 调用自然覆盖两者 |
| 清理与容量 | 复制日志、离线设备与墓碑何时可以回收 | 不以设备暂时离线等同于删除；明确保留窗口与恢复行为 |

## 数据、接口、安全、迁移、发布与回滚影响

宿主负责身份、owner 隔离、持久化与事件边界，消费模块负责 schema、合法引用和恢复体验。
共享属性不授予跨用户或跨 owner 权限；进程内命名空间不提供第三方代码沙箱。
后端也可以消费 Storage；后端的“本地”必须明确指向哪个客户端或宿主，不能假装存在浏览器设备身份。

本地物理落点与首批旧桶迁移已有 Spec 和迁移合同；在线同步不得绕过已定义的访问、原件保留和单写者边界。
发布和回滚必须覆盖新旧 schema 共存及同步版本差，不能通过清空数据解决兼容问题。

## 对 Spec 的预期改动

架构与本地行为分别登记为 `storage.boundaries` 和 `storage.persistence`（planned）。后续候选能力：

- `storage.sync`：关联设备间复制、冲突、删除收敛与离线恢复；验收覆盖两设备同服务、各自服务、同时编辑和旧客户端。
- 各消费者的复制应用时机进入其自身 Spec，不根据已有 local/shared 字段宣称功能已经实现。

本地持久化已获批准；同步接口与协议未闭合前不登记 `storage.sync` 为获批或已实现，也不启动全量同步迁移。
