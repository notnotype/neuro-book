# nb-ui 表面盒子规范

- **状态**：draft
- **日期**：2026-09-02
- **范围**：`packages/nb-ui` 的表面（surface）角色、打包方式与主题合同

## 问题

在组件 Lab（`/lab`）把页面背景换成一张色彩复杂的照片之后，界面上大部分面板的文字**要盯着看才认得出**。这不是某一处写错了，是库里登记的表面角色本身就定得读不了。

三个具体症状：

1. **登记的 5 档表面里，4 档 chrome 全部读不了。** 工具栏 30%、侧栏 26%、浮层 14%、窄条 38%，实测下来都不合格。
2. **唯一读得清的配方根本没登记。** 它是 `FormSelect` 下拉菜单里的一行内联 style（65% 面板底），某个人当年调准了但没有把它变成规范，于是没有第二个组件受益。
3. **同一档面，不同地方长得不一样。** 库里只有「浮层」这一档被打包成了可直接使用的类，其余 4 档只给了一个颜色变量，消费方要自己拼面色、模糊、描边、抬起四样。拼漏一样不报错，只是看起来不对——Lab 页面上三处 chrome 各自走样就是这么来的。

## 目标与非目标

**目标**

- 表面角色按「**这块面上要读什么**」分档，不按「它是哪个部件」分。
- 每一档打包成一个可直接使用的类，消费方不再手工拼装。
- 可读性下限成为主题必须满足的合同，而不是靠人记住。

**非目标**

- 不统一各档的形状（圆角、投影）。形状归布局，同一档材料在不同位置可以有不同形状。
- 不限制主题的模糊配方。实测证明模糊强度不影响可读性，它属于主题的观感身份。
- 不改动控件（按钮、输入框）那一层的面。本提案只覆盖容器级表面。

## 当前行为与证据

### 库里现有的 5 档

登记在 `packages/nb-ui/src/theme/tokens.ts` 的 `nbThemeTokens` 里，是保留 token，主题只能赋值不能重新声明：

| 角色变量 | 用途 | nbook·昼 取值 |
|---|---|---|
| `--toolbar-surface` | 顶栏、应用条 | 侧栏色 30% |
| `--sidebar-surface` | 导航栏 | 侧栏色 26% |
| `--overlay-surface` | 下拉、菜单、对话框 | 侧栏色 14% |
| `--strip-surface` | 面板里的操作条、表头 | 次级底 38% |
| `--panel-surface` | 正文、数据面板 | 面板色 100%（实心） |

### 打包情况

只有浮层那一档被打包成类。`packages/nb-ui/src/styles.css` 的 `.nb-ui-popover-surface` 一次给全描边、圆角、面色、投影、磨砂五样，14 个组件在用（下拉、菜单、右键菜单、气泡、提示、日期选择、对话框等）。

其余 4 档没有对应的类，消费方各自手写。例如 Lab 顶栏要写两行（面色 + 模糊），而模糊那一行只能伸手去拿 nbook 主题的私有变量 `--glass-blur`——库里没有 chrome 层的模糊角色，只有浮层那一档 `--overlay-blur`。

### `FormSelect` 的内联覆盖

`packages/nb-ui/src/components/form/FormSelect.vue` 第 181–184 行用内联 style 覆盖了它自己那一档：

```
背景  面板色 65%（不是 --overlay-surface 的侧栏色 14%）
模糊  blur(8px) saturate(130%) brightness(1.0)（不是 sat 190% / bright 1.14）
```

也就是说 `--overlay-surface` 登记的 14% 在实际产品里**一处都没生效**，登记值是虚的。

### 实测：不透明度决定可读性，模糊配方不决定

2026-09-02 在 Lab 里用 `SurfaceTierDemo` 走查（`packages/neuro-book/app/component-lab/SurfaceTierDemo.vue`）。背景为一张色彩复杂的照片，底色统一固定为面板色，只变两个变量：

| | 强模糊 `sat(190%) bright(1.12)` | 弱模糊 `sat(130%) bright(1.0)` |
|---|---|---|
| **面 26%** | A 读不了 | B 读不了 |
| **面 65%** | C 读得清 | D 读得清 |

**结论**：分界线整齐落在不透明度上。两格 65% 的都能读，两格 26% 的都不能，与模糊配方无关。

两条推论：

1. 规范该定的是**不透明度下限**，不是模糊配方的规则。
2. 模糊配方可以完全留给主题。玻璃的观感不必为可读性让路——nbook 的 `saturate(190%)` 是它的身份，可以保留。

（走查证据：Lab 页面人工判读，无自动化断言。判据是「不盯着看能否认出字」。）

## 方案

### 三个盒子 + 一个「不给面」

按这块面上要读什么分档：

| 盒子 | 装什么 | 材料 | 形状 |
|---|---|---|---|
| **内容盒** | 正文、章节、要读的数据 | 实心暖底，不透光 | 面板圆角，轻抬起 |
| **器械盒** | 工具栏、侧栏、菜单、控件容器 | 玻璃，不透明度 ≥ 下限 | 面板圆角，轻抬起 |
| **浮层盒** | 下拉、对话框、气泡 | 同器械盒 | 菜单圆角，重投影 |

**「不给面」不是第四个盒子**，是「这块区域不该有容器」这个答案本身。展台、画布属于这一类：它们要能看穿到背后，给它上色就成了「面板里浮一块面板」。约束是不承载长文、不叠任何面色，浮在它上面的盒子自带面、边与抬起。

浮层盒与器械盒的**材料相同、形状不同**。单列一档是因为它压在别的面上而不是压在桌面上，将来若两者的材料需要分开，这里已经有位置。

### 交付形式：一个类拿走

复用库里已经验证过的机制——基座类 + 形状修饰类：

```
.nb-ui-paper-surface     内容盒
.nb-ui-chrome-surface    器械盒
.nb-ui-float-surface     浮层盒（= chrome 材料 + 菜单圆角 + 重投影）
```

每个类一次给全描边、圆角、面色、投影、磨砂。消费方写一个类，不再手工拼四样。现有的 `.nb-ui-popover-surface` 成为 `.nb-ui-float-surface` 的别名或直接改名，14 个消费方随之迁移。

### 主题合同

主题必须为器械盒提供一个不透明度不低于下限的面色。下限取 **65%**（实测通过的值），暗色下是否需要不同的数留待走查。

模糊配方、色相、饱和度、亮度全部由主题自由决定，库不约束。

不做玻璃的主题（aurora、editorial）把器械盒定成实心即可，天然满足下限。

## 备选方案与取舍

### 分档数（已决定：3 个盒子）

- **2 个盒子**：把浮层并进器械盒，形状差异用修饰类表达。更简，但失去了「浮层压在别的面上」这个将来可能需要的区分位置。
- **保持 5 档只补下限**：改动最小，但「按部件分」这个错误的轴保留下来，以后新增一种面还是得问「它算哪个部件」。

*2026-09-02 决定采用 3 个盒子。*

### 下限由谁把关（**未决**）

开发者已选择「加载器强制校验」，但现有机制做不到，需要先解决这一条。

**加载器看不见主题的 CSS。** `packages/nb-ui/src/theme/theme-loader.ts` 现有 9 条校验全部针对 manifest（宿主版本、变量声明、组件覆盖、配色、SVG 资源）。而 `--sidebar-surface` 这类角色是保留 token，主题在自己的 `vars.css` 里赋值，那是一个普通 CSS 文件，加载器从不解析。

三条路：

**甲、装载后实测。** 注入主题 CSS 之后，建一个屏幕外探针元素，读计算样式里的背景色，解析出透明度，低于下限就卸载并报错。

- 好处：量的是真实渲染结果，主题用什么写法都逃不掉。
- 代价：加载器从纯数据校验变成依赖 DOM。而且面色是配色的派生值，每套配色、明暗两态都要各探一次，组合数不小；藏在媒体查询里的取值探不到。

**乙、材料改成 manifest 数据，由库合成。** 主题不再在 CSS 里写器械盒的面色，改为在 manifest 里申报一个不透明度和一个基色，库负责合成出 `--chrome-surface`。

- 好处：下限**由构造保证**，不可能被绕过；申报值与实际值不可能不一致。
- 代价：改变了主题的写法，是本提案里最大的一处破坏性变更。主题作者失去用任意 CSS 表达面色的自由（例如渐变面色就写不了了）。

**丙、构建期检查。** 加一条检查脚本解析仓库内主题的 `vars.css`。

- 好处：改动最小，不碰运行期。
- 代价：只管得住仓库内的主题。市场装进来的第三方主题完全不受约束，而加载器那 9 条校验正是为市场场景写的。

**倾向乙**，因为它是唯一让下限真正成为合同的做法，而加载器「拒绝 + 明确报错，一条都不静默降级」的既有原则也指向这个方向。但它的代价最大，需要开发者拍板。

## 影响

**接口**：新增三个类，`--overlay-surface` 等 5 个角色变量的含义变化或废弃。属于 nb-ui 的公开表面，消费方（主应用、nb-workshop）需要同步。

**迁移**：
- nbook 主题的浮层 14%、侧栏 26%、工具栏 30%、窄条 38% 全部低于下限，必须调整。
- `FormSelect` 的内联覆盖删除，改用 `.nb-ui-float-surface`。
- 14 个消费 `.nb-ui-popover-surface` 的组件改名或走别名。
- 主应用里手工拼装表面的地方（例如 Lab 顶栏、侧栏）改用新类。

**安全**：无。

**发布与回滚**：主题合同变更影响已装主题的兼容性。若采用方案乙，旧写法的主题装不上，需要一次主题侧的版本升级。回滚方式是保留旧角色变量一个版本周期，新旧并行。

**风险**：65% 这个数只在 nbook·昼 + 一张照片背景下验证过。暗色、其他配色、其他背景类型都未走查，下限可能需要按明暗分别定。

## 对 Spec 的预期改动

- `packages/nb-ui/docs/ui-development-spec.md` 第 2 节第 1 条：材料判据从「装工具 vs 装长文」扩写为三个盒子加「不给面」，并写入不透明度下限。
- `packages/nb-ui/docs/design-language.md` 第一节：器械/稿面两栏表改为三盒子表，补充可读性下限的由来与实测证据。
- 主题合同文档：新增器械盒不透明度下限一条，以及它由什么机制保证。

验收：在 Lab 里把桌面换成复杂照片，三个盒子的正文均可不盯着读出；装载一个不满足下限的主题时按选定机制被拒绝或被纠正。
