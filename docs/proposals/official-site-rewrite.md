# 官方站重写：一个进程、两个模块、按能拆开的边界写

## 一、问题

现有官方站 `neuro-book-site`（`nbook.notnotype.com`，另一个仓库）是 Nuxt 全栈加 Prisma 与 SQLite 的单体，承载账号、设备码关联、对外 OAuth、云备份、工坊与管理后台。开发者决定重写它（2026-11-23、2026-11-24），理由是：

- 不再背旧版的历史包袱；以后要承载市场、小说发布、论坛，需要能把某一块单独拆出去、甚至换语言重写；
- 遥测（[本机统计、遥测与反馈](telemetry-stats-feedback.md)）需要一个服务端，开发者要它落在官方站里；
- 放进本仓库后，前端直接用仓库里的 nb-ui，不必像旧站那样固定在它某个旧的 Git 提交上。

旧站没有记录在案的具体缺陷（性能、安全、维护事故）；重写是偏好与为以后的扩展做准备。

## 二、目标与非目标

目标：

1. 第一版交付账号与管理：用户名或邮箱加密码登录、Google 与 GitHub 登录、凭注册码注册、对外提供 OAuth 服务、管理面板（用户、注册码与邀请码、OAuth 客户端、统计看板、审计）。
2. 第一版交付统计模块的服务端，协议见 [本机统计、遥测与反馈](telemetry-stats-feedback.md)。
3. 第一版是一个进程，但账号与统计按“以后能拆成两个服务”的边界写。
4. 后端的合同测试是黑盒的，换语言重写后原样可用。
5. 旧站的数据不丢：账号类数据导入新站，其余原样留存，重建对应功能时再导入。
6. 代码放在本仓库，技术栈与仓库一致（Bun、TypeScript、Hono、TypeBox、Vue 3、nb-ui）。

非目标：

- 第一版不做市场（工坊）、云备份、设备码关联、小说发布、论坛。“给用户看已登录的设备”随设备码流程一起做，不在第一版。
- 不保持旧应用与旧站之间的接口兼容；llmlint 已废弃，旧站 OAuth 服务没有要保留的客户端。
- 第一版不发邮件：没有邮箱验证与自助找回密码。
- 不做网站自身的访问量统计。诊断报告、用户反馈与调查问卷的收件不在第一版，第二阶段作为第三个模块加入。
- 不对机器规格与并发量设硬性验收口径（开发者 2026-11-24）。设计时按 2 核 2 GB 的机器估算，不写成验收条件。

第一版的范围有一处待开发者重新确认，见待定项 1。

## 三、当前行为与证据

- 旧站的模块与数据：账号（`username` 唯一且不可改、可空的密码哈希、角色、状态）、上游身份（GitHub，键是 GitHub 的数字 id）、注册码、邀请码、工坊条目与版本及互动、设备码关联与令牌、实例备份、OAuth 客户端与令牌；工坊压缩包与加密备份是数据卷里的文件。密码哈希是 `scrypt:<盐>:<十六进制>`。生产已开放凭注册码的密码注册。来源：旧站仓库的 `prisma/schema.prisma`、`server/utils/password.ts`、`PROJECT-STATUS.md`（2026-11-24 读取）。旧站现有多少账号、最近多少人登录过，本仓库里没有记录；旧站的用户名允许哪些字符、是否区分大小写也没有记录。
- 新应用 `packages/neuro-book` 里没有调用官方站的代码：搜 `nbook.notnotype.com` 只在旧应用与 llmlint 的部署配置里命中。第一版的账号功能因此没有来自应用的使用者。
- 身份库 Better Auth 1.7.27 的三轮探针（[w00037 t02](../../.agents/works/w00037-official-site/tasks/t02-selection/README.md) 的两轮在 PostgreSQL 上，[t03](../../.agents/works/w00037-official-site/tasks/t03-architecture/README.md) 的第三轮在 SQLite 上）。
  - 走通的：保留数字用户 id 并接着发号、用旧站的 scrypt 哈希登录、没带注册码的注册被拒、对外 OAuth 服务（授权码加 PKCE、`client_secret_basic`、`/userinfo`、授权码重放被拒）、封禁后会话失效、接仿真上游的社交登录、授权中途登录接自家登录路由。PostgreSQL 与 SQLite 上都能建表、保留 id、验旧哈希。
  - 库的默认行为与本稿要的不一致、必须另外处理的：
    - 任何登录用户都能调库的端点登记 OAuth 客户端（普通用户调用得到 201）。
    - 管理员改角色、重置密码之后，那个用户的旧会话仍然有效（只有封禁会清会话）。
    - 本地邮箱已验证时（经社交注册的账号都是），第二个上游用同一个已验证邮箱登录会被自动并入同一个账号；打开 `disableImplicitLinking` 后改为拒绝。
    - 社交注册带来的用户名与已有用户名只差大小写时，以库的内部错误收场，没有可读的错误码。
  - 没探的：注册码的消费（是否与建账号在同一个事务里、并发时会不会一码两用）、登录后把旧哈希换成新算法、取不到真实 IP 时库的限流行为。
- 探针量到的内存：进程初始化后空闲 85 MB，跑过 argon2 哈希后 155 到 165 MB。
- 设计审查（Opus、一位只看方向的 Sonnet，omp 在后台）的报告与逐条处理见 [w00037 t03](../../.agents/works/w00037-official-site/tasks/t03-architecture/README.md)。

## 四、方案

### 4.1 形态：边界照微服务，第一版一个进程

开发者先提出用微服务的思想搭，随后定第一版不拆进程、注意解耦、让以后想拆时不困难（2026-11-24）。本稿据此定四条规则：

1. **模块包的依赖有白名单。** 每个模块是一个工作区包，它的 `package.json` 只许依赖自己的合同包与通用包，不许依赖另一个模块的实现包；由一条测试读 `package.json` 守住。
2. **数据库分开。** 每个模块只经自己的连接写自己的库；跨模块的读写只经对方的 HTTP 接口。库用什么见待定项 2。
3. **合同是 HTTP。** 每个模块是一个挂在自己路径前缀下的 Hono 子应用，接口的 schema 在它的合同包里；进程入口只负责把模块装起来。拆分时加第二个入口文件。
4. **合同测试是黑盒。** 测试只经 HTTP 与被测进程说话；拆完后同一套测试跑通，就是拆对了的证据。

模块之间只有一个接口，“问身份”，它从第一版起就是账号模块的一个 HTTP 端点（给请求的 Cookie，返回用户 id 与角色，或未登录），有合同、有合同测试。第一版里统计模块在进程内调用同一个处理函数；拆分时由反向代理的转发鉴权指向这个端点，浏览器看到的合同不变。

第一版少掉的是进程级隔离：统计入口被刷会连带登录变慢，一处内存泄漏影响全部。靠反向代理对统计入口限流、限请求体大小来挡。出现下面任一情况再拆：统计写入拖慢了登录；某个模块要换语言；市场的扫描任务上线。为了让第一条看得出来，两个模块的请求耗时分开记进日志。

### 4.2 包

| 包 | 内容 |
|---|---|
| `nb-site-identity-contract` | 账号模块的接口 schema（含“问身份”）；只依赖 TypeBox |
| `nb-site-identity` | 账号模块的实现：Hono 子应用、迁移 |
| `nb-site-telemetry-contract` | 统计模块的接口 schema 与收集清单；只依赖 TypeBox。NeuroBook 里的遥测插件用它的收集清单 |
| `nb-site-telemetry` | 统计模块的实现 |
| `nb-site-server` | 进程入口：读配置、挂模块、健康检查、迁移命令、管理员初始化命令、旧站数据导入命令；镜像与部署脚本 |
| `nb-site-contract-tests` | 合同测试；只依赖两个合同包，并把 `nb-site-server` 当作“被测进程的启动命令”来依赖 |
| `nb-site-web` | 前端 |

合同单独成包：实现包换语言重写或删掉时，前端依赖的合同还在；NeuroBook 应用要用收集清单，但不该依赖一个带数据库驱动的服务端包。

合同测试单独成包：仓库的 `test:affected` 按包的依赖关系选测试，测试包依赖 `nb-site-server` 才会在实现改动时被选中；另有一条源码守卫禁止它 import 合同包之外的任何包，黑盒靠这条守卫保证。

### 4.3 进程与部署

- 一个 Bun 进程，Docker Compose；反向代理用生产主机上已有的 Nginx。
- 前端的构建产物打进同一个镜像，由这个进程发静态文件：接口与页面永远同一个版本。
- 镜像在 CI 里从本仓库构建；主机按固定摘要升级，升级前备份一次数据库，健康检查不过就换回上一个镜像。
- 迁移是每个模块自带的纯 SQL 文件，只往前；进程启动前由入口命令执行。**每个版本的迁移必须让上一个版本照常运行**，破坏性的改动拆到下一个版本；旧镜像遇到库里有它不认识的较新迁移时照常运行。回滚只换镜像、不恢复备份，备份只用于人工灾备。身份库升级带表结构变化时，重新导出表结构、与上一份比对、手写增量迁移。
- 配置只来自环境变量，启动时校验，缺密钥不启动。日志是 JSON，写标准输出，容器日志设轮转。
- 健康检查分两个：进程活着；数据库可达且迁移已全部执行。

### 4.4 地址布局

- 站点域名：`/` 前端；`/api/identity/v1/*` 账号模块自家接口；`/api/telemetry/v1/*` 统计模块给看板的查询接口；标准 OAuth 端点与发现文档；Google、GitHub 回调；`/health/*`。
- 统计的写入口单独一个域名，第一版指向同一台机器。发出去的客户端里地址改不了，单独的域名让写入口以后能独立搬走。
- OAuth 的签发者地址定为站点根地址、不带路径，发现文档的位置按 RFC 8414 与之对应；它在写 OAuth 的合同测试之前定死。

### 4.5 账号模块

- **库**：Better Auth。对外合同只有三类：自家路由、标准 OAuth 端点（授权、令牌、`/userinfo`、撤销、发现文档、公钥）、Google 与 GitHub 的回调。库的其余端点一律不可从外部到达：挂载处用“方法加路径”的精确白名单、默认拒绝，不按前缀放行。
- **库私有的东西不进合同**：授权确认页的提交、授权中途登录的续接、社交登录回调的错误，都由自家路由包一层。登录接口收一个不透明的“继续”令牌并原样交回；回调错误统一映射成自家的错误码再跳前端。合同测试只断言自家形状与标准 OAuth 端点。
- **登录方式**：用户名或邮箱加密码、Google、GitHub。Google、GitHub 用库的通用 OAuth 插件接入（上游地址可配）；GitHub 的邮箱与是否已验证要另取它的邮箱接口，仿真上游照真实的形状实现。
- **注册**：一律要注册码。沿用旧站的两种码：管理员发的注册码管准入，用户发的邀请码只记是谁邀请的。注册码的检查与消费、建账号在同一个事务里；合同测试覆盖“并发时一码不能两用”与“建账号失败后码仍可用”。
- **社交注册的顺序**：先在本站填注册码与用户名并校验，再跳到上游，回来时建账号；没有“回来再补填”的一步。Google、GitHub 首次登录不自动建账号。
- **用户名**：密码注册与社交注册共用同一套规则（转小写、允许的字符、长度、查重），冲突时给可读的错误码。
- **邮箱**：新注册必填、唯一，第一版不验证。不按邮箱自动合并账号（打开库的 `disableImplicitLinking`）：社交登录的邮箱撞上已有账号时拒绝，提示先登录再到账号设置里关联。邮箱不验证意味着有人可以先占用别人的邮箱；被占用的人由管理员处理。
- **同意条款**：注册时主动勾选同意服务条款与隐私政策，不预选；账号数据存放在境外要单独告知并单独勾选。账号上存同意记录（条款版本、境外存放的同意、时间）。导入的旧账号、以及条款版本变更后的账号，登录后先过一页同意。
- **找回密码**：第一版由管理员在面板里重置。
- **会话**：存数据库，不开库的会话缓存。封禁、改角色、改密码、管理员重置密码都由自家路由在同一个事务里改字段并删掉该用户的全部会话。
- **密码**：新密码用 argon2id；旧站的 scrypt 哈希照验，登录成功后换成 argon2id，写回时带上“原哈希没变”的条件，防止盖掉管理员刚重置的密码。哈希限并发，排队有上限与超时，满了直接回“稍后再试”。
- **对外 OAuth 服务**：客户端只能由管理员登记（库里也配上只许管理员的权限检查，作为白名单之外的第二道）；授权码加 PKCE、授权确认页。是否支持 `openid` 范围（那样要发 id_token、公开公钥并轮换密钥）在写 Spec 时定；第一版没有真实的外部客户端，做到合同测试用测试客户端走通标准流程为止。设备码流程等 NeuroBook 应用要接登录时再加。
- **管理接口**：用户列表与搜索、封禁、改角色、踢下线、重置密码；注册码与邀请码；OAuth 客户端；管理操作写进审计表。
- **限流**：三个键：IP、IP 加用户名、同一个用户名的失败总数（超了加等待时间，不锁死账号）。只信任来自反向代理的转发头，取不到真实 IP 时拒绝而不是全站共用一个桶。第一版记在进程内存里，拆进程或多副本时换成共享存储。

### 4.6 统计模块

收什么、怎么发、服务端怎么处理收到的东西，都在 [本机统计、遥测与反馈](telemetry-stats-feedback.md) 的“服务端”一节，本稿不重复。落在官方站上的只有三点：

- 三个写入口在单独的域名上，不带登录；看板的查询接口在站点域名的 `/api/telemetry/v1/*`，要管理员身份。
- 服务端收到即聚合，不存单份上报；“不留 IP”的那张清单里，反向代理与容器日志的几项由本站的部署配置负责。
- 看板第一版只做当前会看的几张图：活跃与新增、按周留存、在线、版本与平台分布、同意率、错误码。

### 4.7 前端

- 一个单页应用：登录、注册、账号设置（资料、邮箱、密码、已关联的 Google 与 GitHub、会话）、同意条款页、OAuth 授权确认页、管理（用户、注册码与邀请码、OAuth 客户端、统计看板、审计）。
- 三个公开页面：主页（含功能说明）、隐私政策、服务条款。Google 登录上线的前置条件是公开的主页、同域名的隐私政策，并在 Search Console 验证域名；“我们收集什么”的表由收集清单生成。
- Vue 3、Vite、vue-router、nb-ui、Tailwind 4；中英双语，沿用仓库的消息目录做法。
- 接口类型直接取合同包里的 schema，不做代码生成。
- 界面按仓库的设计评审流程：先出静态稿与评审板，开发者定了再实现。

### 4.8 合同与测试

- 合同测试起真实进程、真实数据库与仿真的 Google、GitHub，只用 HTTP；被测进程由 `nb-site-server` 的启动命令起，每个测试文件一个独立的库。
- 造状态只经公开接口、管理接口与管理员初始化命令，不直接改库。与时间有关的行为用环境变量把时限配短，测试等可观察的过期状态。
- 旧站五份集成测试里的场景（注册码并发双花、封禁、限流、OAuth 流程等）是验收场景的来源。
- 它是仓库里一类新的测试（要起进程，可能还要起数据库容器），在 [`docs/testing/README.md`](../testing/README.md) 里登记分类与 CI 的做法。
- 服务内部只留少量纯逻辑的单元测试。

### 4.9 旧站数据

- 一次性的导入命令：只读旧站的 SQLite 快照，写进新库。
- 导入：用户（id、角色、状态、时间不变）、密码哈希、GitHub 身份（键取旧站存的 GitHub 数字 id）、注册码与邀请码及其使用关系。
- 用户名导入为“小写的登录名加原样的显示名”。导入前先在快照上查出不合新规则的用户名（含大写、含不允许的字符、过短）与转小写后的重名，定处理规则（放宽规则以兼容，或由管理员逐个改名并通知）；演练把“每个导入的用户能用原用户名与原密码登录”列为核对项。
- 邮箱填 `.invalid` 结尾的占位值，账号上有一个“邮箱待补”的标记；登录后先过同意条款页，再提示补填邮箱。
- 不导入：会话（所有人重新登录）、设备码与令牌、旧 OAuth 客户端与令牌、工坊、备份。后几样连同文件卷原样留在快照里；用户的数字 id 不变，以后导入工坊与备份时靠它关联。
- 切到新站后，工坊页面、云备份、旧应用的设备码关联在重建之前不可用（开发者 2026-11-24 确认）。
- 先在副本上演练并核对条数；切换是停旧站、取快照、导入、起新站、改反向代理；退回是把反向代理指回旧站，退回会丢掉切换之后在新站产生的注册与修改。退回之后再切换一次时，丢弃新站的库、从旧站的新快照整库重导。

### 4.10 安全与运维

- Cookie 设 HttpOnly、Secure、SameSite=Lax；改状态的请求核对来源；请求体有上限。
- 遥测由 NeuroBook 的后端进程发出，不从浏览器发，写入口不开跨域。
- 第一个管理员由命令行创建，密码从标准输入读。
- 数据库每晚备份一份留在本机；备份与库在同一台主机上，主机丢失时一起丢。

### 4.11 备选与取舍

- **真正拆成两个服务**（主会话最初的提议）：有进程级隔离，但要多做令牌签发与验签、多进程的本地开发与部署，每个进程多占约 100 MB。开发者定第一版不拆，按 4.1 的规则留好拆分的路。
- **不分模块的单体**（[w00053 调研](../../.agents/works/w00053-telemetry-feedback-stats/research/2026-11-23-telemetry-feedback-and-stats.md)推荐过模块化单体）：本稿与它的差别是把模块边界落到包的依赖白名单、各自的库与合同测试上。
- **自己写账号核心、协议部分用小库**：OAuth 客户端库 arctic 已被作者弃用；可用的授权服务器库要么建在 Koa 上、没有 PostgreSQL 适配器，要么存储全要自己接。自写量最大。
- **单独部署现成的身份服务**：Logto、Keycloak、Zitadel、Authentik 与本站同机放不下或基本占满 2 GB；Casdoor、Ory 可能放得下，但界面与注册流程要按它们的模型来，用不上 nb-ui。
- **部署 Umami 看统计**：它的模型是网页访问与逐条事件、靠 IP 与浏览器标识的哈希认访客，与“每天一份汇总、不存 IP、入库即聚合”对不上。
- **聚合表接 Grafana 这类通用看板工具**：聚合表是普通的关系表，接上去就能出时间序列与分布图，不用自己写图表；代价是多一个常驻进程、要与自家的管理员登录对接、风格与语言跟站点不一致。没有实测过内存。开发者要的是管理面板里自带的看板（2026-11-24），本稿照做，第一版只做几张图。

选 Better Auth 的代价：每个账号必须有邮箱（开发者已定账号要邮箱，旧账号导入时填占位值）；库的若干默认行为要另外收紧（见第三节）；账号数据里自己拥有、换实现时要迁走的是用户 id、用户名、邮箱、密码哈希（两种前缀）、上游身份的关联、注册码与邀请码、同意记录，会话与库内部的表可以丢。

## 七、待定项

1. **第一版的范围与顺序。** 审查者指出：第一版里有使用者的只有遥测，账号这边的社交登录、对外 OAuth、邀请码、必填邮箱与旧站迁移在第一版都没有使用者，却带来遥测用不到的负担（境外存放的同意、Google 登录的上线条件、整条迁移链路）。两条路：
   - 照开发者 2026-11-24 定的范围做全（本稿正文按这条写）。
   - 旧站先不动，新站第一版只做统计模块加一个管理员登录，放在遥测的域名上；账号、OAuth 与迁移等第一个真正要用它的功能（应用内登录、市场、同步）出现时再做。好处是工坊与备份不用停、旧数据不用急着迁、出境同意晚点过；代价是两套系统并存一段时间。

   推荐先查旧站现有的账号数与最近登录数再定；查生产库需要开发者授权。
2. **数据库：PostgreSQL，还是每个模块一个 SQLite 文件。** 选 PostgreSQL 的理由（按模块分 schema 与角色、分区、多个写者）大多是为以后拆进程预付的，而最初选它是上一轮调研为了兼容 Cloudflare。每个模块一个 SQLite 文件：隔离更彻底（各开各的文件）、不占常驻内存、合同测试与 CI 不用起数据库容器、备份是复制文件；拆进程后每个服务仍只写自己的文件。它做不到的是同一份数据由多个进程或多个副本同时写。第三轮探针确认身份库在 SQLite 上能建表、保留数字 id、验旧哈希。推荐 SQLite，等某个模块真的需要多副本时再单独换。
3. **境外存放账号数据的出境条件。** 这决定“注册时收邮箱”的设计能不能成立，要在写账号模块之前找懂的人确认，不是上线前。导入旧账号的同意缺口（4.5 的同意条款页）不用等这个结论。
4. **异地备份**：推荐第一版只做本机每晚备份，开放大量注册前再定异地方案。
5. **图表库**：做看板时选，推荐先看体积小的。
