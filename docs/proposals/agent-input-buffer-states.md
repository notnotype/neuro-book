# Agent 内核的输入缓冲区：每条带状态，留着与放行由内核定

起因是 [NeuroBook 的 bot](neurobot.md) 的三轮设计审查：周期任务要往会话的输入缓冲区发消息，而“运行收口后缓冲区里的话归谁取”三轮都找出了新的漏洞（[w00043 t01 第三轮处理](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/bot-proposal-review-r3-disposition.md)）。开发者 2026-11-18 选了“直接改内核的缓冲区逻辑”。第一稿按收口方式逐行列表，审查又找出表外的路径；第二稿改成只在“会话回到空闲”一处定（[第一轮处理](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/buffer-proposal-review-r1-disposition.md)）。本稿是第三稿，按第二轮审查把合同写精确：状态改成显式的会话级事件，补上收口时的时间窗、放行的全部入口与失败码（[第二轮处理](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/buffer-proposal-review-r2-disposition.md)）。它改的是 nb-harness 内核，对所有会话生效，bot 提案引用它。本文不能作为当前行为的依据。

## 一、问题

输入缓冲区放着“提交了还没被取走”的话，每条是插话（`steer`）或排队（`followup`）。现在的规则（[`harness/runtime.md`](../specs/harness/runtime.md) 输出 2–4、7、28–30、34）：运行中每个边界取走全部插话；一轮正常结束时取最早一条排队，在同一次运行里接着开下一轮；一轮以出错或中止结束时不取排队的；中止缺省清空缓冲区、`keepQueue` 保留；重启后缓冲区留着、不自动发出。后几条来自开发者 2026-10-28 在 [w00032 t07](../../.agents/works/w00032-agent-integration/tasks/t07-run-control/README.md) 的决定 1、3。界面上的停止一律保留排队（开发者 2026-11-05，[`agent/conversation.md`](../specs/agent/conversation.md) 输出 6）。

毛病有三类，都已用真实内核复现（证据在 [t01 的证据目录](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/)，文件名以 `bot-proposal-review-r*` 与 `buffer-proposal-review-r*` 开头）：

1. **会话空闲了，缓冲区里却还有话、没人取**：只压缩的运行压完、以收尾工具交出结果、带结果要求的会话以文字收口、正常退出时进程内写下的中断、空闲时排进来的话、回复写下后运行还没收口的那一瞬间到达的话。普通会话里手动压缩时用户发的话，现在就会这样卡住。
2. **“不处理”不是一种状态**：出错、停止、重启之后留着的话，下一次不管谁开运行，都会被取走；停止进行中到达的话，指令已经交回成功，随后又被清空。只有用户会开运行时，这碰巧就是“等用户”；一旦系统也往缓冲区发消息，系统开的一次运行就会把用户留着的话一起带走。
3. **指令不看发出者**：`edit`、`remove`、`abort` 谁都能用；`inputEdited` 换了内容却保留原来的发出者；`start` 不记谁开的。NeuroBook 里插件经 `agentKey` 拿到的会话视图缺省就是用户的身份。

## 二、目标与非目标

目标：

- 缓冲区里每条话有明确的状态，写在日志里，取不取、什么时候放行都由内核一处决定，新的收口方式不会漏。
- 把 t07 决定 1、3、2026-11-05 的“停止时排队留着”与 2026-11-18 的“等恢复”写成同一种状态，重启后照样成立。
- 恢复时“留着的先跑”，恢复方式由用户选（开发者 2026-11-18）。
- 指令按发出者有权限，发出者在日志里不失真。

非目标：

- 周期任务本身、给模型的来源说明、算不算用户的授权：在 bot 提案。
- 缓冲区条目的过期：发出者要撤回过时的话，自己取消。
- 降级：旧内核读到新事件得 `log-corrupt`，同现有规则（[`harness/session.md`](../specs/harness/session.md) 的“边界与兼容”）。
- 对话视图的外观：由各自的设计评审定。
- 改插话与排队的基本含义、一条排队开一轮的规则（[Agent harness 的事件模型](agent-harness-event-model.md)待定项 15、16）。

## 三、当前行为与证据

- 一轮正常结束时取排队的、同一次运行接着跑：`kernel/run/loop.ts`；读缓冲区决定接着跑还是收口，与写 `runEnded` 不在同一个队列项里。只压缩的运行、交出结果、文字收口都直接写 `runEnded`，不看缓冲区。
- 恢复：打开会话时把没收口的运行以 `interrupted` 收口，缓冲区留着（输出 34）；正常退出时进程内已经写下 `runEnded{interrupted}`，重开时不再走恢复。回退到运行中途时运行暂停，之后的 `send`、`start` 让它接着跑，不写事件（输出 36）。
- 发出者只有用户与会话（`kernel/api/basics.ts`），用户发的不写 `by`（输出 85）；`edit`、`remove`、`abort`、`start` 不收发出者（`kernel/run/commands.ts`）；停止的受理记录写在 `runEnded` 之后的另一个写入批里。
- 会把话放进缓冲区的入口：`send`、`enqueue`、异步提问的回答（输出 42）、`rewind{resend}`（输出 36）。
- NeuroBook：`AgentService.session(id)` 不带发出者时是用户；`startTask` 以用户身份发；`jobs/steer.ts` 在内核外读快照的缓冲区，把“有插话”当成用户插话。界面：停止走 `abort{keepQueue: true}`；“上次运行已中断，按回车继续”走 `start`；错误气泡的“重试”与“编辑重发”也走 `start`；乐观消息按先后确认（`nb-agent-ui` 的 `kernel-transcript.ts`）。
- 子代理：父 Agent 用 `agent_send` 往子会话发话，空闲时开新一轮，在跑时缺省插话，不带话时走 `start`；父会话连带中止子会话时保留队列（[`agent/subagents.md`](../specs/agent/subagents.md) 输出 10、16）。

## 四、方案

### 1. 状态与一条规则

- 缓冲区里的每条话是**就绪**或**留着**。留着带原因 `cause`（这次运行的收口方式与码，或“空闲时排的”），由用户选“停止，排队的留着”留下的另带 `heldBy: "user"`：只有用户能放行。
- **会话回到空闲的那一刻**，缓冲区里还就绪的话全部转成留着，在收口的**同一个写入批**里写一条会话级事件 `inputHeld{ids, cause, heldBy?}`。不论这次运行怎样收口：正常结束、只压缩、交出结果、文字收口、出错、停止、进程内中断、打开会话时的恢复。
- **决定收口与写下收口在同一步**：运行循环判断“缓冲区里没有可取的了、收口”，与写 `runEnded`、`inputHeld` 在同一个写入批；在那之前受理的话由这次运行取走，在那之后受理的按空闲处理。回复写下后、运行收口前到达的话因此不会卡住。
- **暂停的运行按空闲算**：回退到运行中途而暂停的运行，接着跑时写一条 `runResumed{runId, by}`；暂停期间排进来的话同样算“空闲时排的”。
- **空闲时排进来的**：`inputQueued` 直接带 `state: "held"` 与原因“空闲时排的”。
- **原因记下就不改**：已经留着的话，之后再有运行收口时不改原因，也不改 `heldBy`。
- **运行只取就绪的**：内核读缓冲区的每一处都只看就绪的（边界取插话、一轮结束取排队、`start` 取第一条、“缓冲区还有插话就不结束这一轮”、预览的投影、快照的排队、空闲判断、恢复）。内核外读快照缓冲区的代码也按状态过滤，例如 NeuroBook 的 `jobs/steer.ts` 只认就绪的插话，放行出来的插话也算到达。
- 一轮正常结束时取排队、同一次运行接着跑，照旧：这时会话没有回到空闲。
- **旧日志**没有这些事件，条目都是就绪的，行为同现在，不另做补算。

### 2. 停止

- 内核 `abort` 的缺省不变（清空，t07 决定 1）。NeuroBook 界面照 2026-11-05 的决定传 `keepQueue: true`。
- 停止受理时把发出者与是否保留交给运行循环，收口的同一个写入批里写：保留时 `inputHeld{cause: 停止与谁停的, heldBy}`（用户停的带 `heldBy: "user"`）；清空时每条 `inputRemoved{by: 停的人, reason: "aborted"}`。清空只清停止受理那一刻在缓冲区里的；停止进行中才到的，按第 3 小节“运行不再取输入时”处理。
- 输入框的停止按钮在缓冲区里有用户自己的话时多给一个“停止并清空排队”（开发者 2026-11-18）；停止进行中这个选项不可用。审批向导里的“终止本轮”、子代理浮层里的停止走缺省。

### 3. 放行

**放行跟着新话走**：凡以某发出者的身份送进一条新输入（`send`、`enqueue`、异步提问的回答、`rewind{resend}`），都先放行这个发出者能放行的留着的话：

| 发出者 | 能放行的 |
|---|---|
| 用户 | 全部 |
| 会话、宿主 | 自己排的，且不带 `heldBy: "user"` |

- **留着的先跑**（开发者 2026-11-18）：放行出来的排在这次新话前面，怎么跑按第 4 小节的恢复方式；不带选项时等同“保留原插话与排队”。
- **只放行、不送新话**：`resume({mode?})` 放行同样的范围；会话里有中断或失败的那一轮时，先接着跑它，放行出来的随后。`release({inputIds})` 按条放行，权限同上表。
- **只接着跑、不放行**：`start` 照旧接着跑中断或失败的那一轮，错误气泡的“重试”用它，它不取留着的。宿主只能 `start` 自己开的那次运行，或会话头的 `owner` 是它自己的会话（开发者 2026-11-18）；用户自己开的普通会话被中断后，只有用户能点继续。
- **放行时会话空闲**就开运行，第一条开第一轮（经指令的常规检查：重新装配做完、能解析模型、不是只读；开不起来时失败，话仍留着）。**在跑**就把它们转成就绪，按取的规则在之后的边界或一轮结束时取。
- **运行不再取输入时**（只压缩的运行、正在中止、已决定收口）到达的新话与放行：新话照常排进缓冲区；回到空闲时，先把剩下的转成留着，再按这次的放行处理。停止进行中你打的那句话，因此在停止完成后按“你发了新消息”处理：留着的先跑，然后是这句。
- **子会话**：
  - 以收尾工具或文字交出结果后，排着的话留着，不接着跑，因为结果已经交给父 Agent（偏离 t07 决定 1 的“completed 后按序取”，开发者 2026-11-18 没有异议）。
  - 父 Agent 用 `agent_send` 送新话时放行它自己排的；不带话时改走 `resume`，以父会话的身份放行它自己的。
  - 用户停止子会话留下的（`heldBy: "user"`），父 Agent 的话也只有用户能放行；父 Agent 再发话时，工具结果写明“子会话里有 N 条你排的话被用户暂停，未发出”（开发者 2026-11-18）。
  - 父会话连带中止子会话、或父 Agent 停掉子代理时留下的，停的是父会话，没有 `heldBy: "user"`，父 Agent 能放行。
- **用户自己发起的压缩**：`compact({release: "arrived-during"})`。压完会话回到空闲，压缩期间进来、因这次收口留着的那几条，由内核按用户的放行处理（同 `resume` 的路径与检查）。压缩失败时它们仍留着，原因是失败的码。系统发起的压缩不带这个选项，压完留着（开发者 2026-11-18）。

失败的情形：

| 指令 | 情形 | 结果 |
|---|---|---|
| `resume` | 没有留着的、也没有可接着跑的 | `nothing-to-resume` |
| `resume`、`release` | 要放行的都带 `heldBy: "user"`，发出者不是用户 | `held-by-user` |
| `release` | 指定的条目不在缓冲区或不是留着的 | `nothing-to-release`，带不在的 id |
| `release` | 不是这个发出者能放行的 | `not-allowed` |
| `start` | 宿主接着跑别人开的运行、且会话不归它 | `not-allowed` |
| 开运行的各指令 | 开不起来（只读、没有模型等） | 照现有的码失败，话仍留着 |

### 4. 恢复方式

用户在设置里选（开发者 2026-11-18：“合并一起发（默认）、保留原 steer、followup 顺序”），宿主（NeuroBook）按它调用内核：

| 恢复方式 | 宿主怎么调 | 结果 |
|---|---|---|
| 合并一起发（缺省） | `send({input, replaces: [{id, edits}]})` | 宿主把留着的用户的话按原顺序与新话拼成一条；内核在同一个受理批里移除那几条（`inputRemoved{by, reason: "replaced", replacedBy}`）、放行其余能放行的、送进这条新输入 |
| 保留原插话与排队 | `send({input, release: "keep"})` | 放行出来的各保持原模式，排在新话前面 |
| 按排队顺序 | `send({input, release: "followups"})` | 放行出来的都转成排队，一条一轮，排在新话前面 |

- `replaces` 是条件写入：每项带它的 id 与改过几次（`edits`），任一项已不在缓冲区、改过、或不是这个发出者能移除的，整条以 `input-stale` 失败，什么都不写；宿主重新读快照再拼。结果未知时的重发用同一组参数。
- 只合并用户自己的话；宿主的消息不合并，按原顺序在合并的那一条前面放行。拼法（分隔、附件的先后）由宿主定，合并出的是一条普通的新输入，输入拦截照常经过它。快照与远程合同的条目带完整的输入（含附件），宿主拼得出来。
- 点继续、没有新话时：合并由宿主用 `send{replaces}` 做；另两种用 `resume({mode})`。

### 5. 发出者与权限

- **内核加一种发出者 `host`**：`{kind: "host", source: {plugin, label, ref?, at?}}`。日志里的输入记 `by: {kind: "host", source}`。判等按种类与身份：会话按会话 id，宿主按 `source.plugin`。给模型的来源说明、算不算用户的授权，在 bot 提案。
- **前提：发出者由宿主应用如实盖章**。NeuroBook 的 `agentKey` 按调用方门面提供（[`runtime/services.md`](../specs/runtime/services.md) 输出 12），插件拿到的会话视图缺省身份是带它插件名的宿主，只有远程合同（用户界面）上来的是用户；`startTask` 的发出者是调用方。这条写进 `agent/sessions.md`；权限表的安全性以它为前提。
- 权限表：

  | 指令 | 用户 | 会话、宿主 |
  |---|---|---|
  | `edit` | 只能改用户自己排的 | 只能改自己排的 |
  | `remove` | 任何一条 | 只能取消自己排的 |
  | `release`、`resume` | 全部 | 见第 3 小节的表 |
  | `abort` | 能 | 会话只能停自己派出的子会话（连带中止） |
  | `start` | 能 | 见第 3 小节 |

- 不允许时得 `not-allowed`。编辑只给原发出者，`by` 不变；`inputEdited` 记下编辑者。`runStarted` 记下开这次运行的发出者（`send`、`start`、`resume` 与放行都算）。
- 应答审批与提问的规则不变（输出 41）。

### 6. 日志、快照与远程合同

| 事件 | 作用域 | 新增或改动 |
|---|---|---|
| `inputHeld{ids, cause, heldBy?}` | 会话 | 新增：与收口同批 |
| `inputReleased{ids, by, mode}` | 会话 | 新增 |
| `runResumed{runId, by}` | 路径 | 新增：暂停的运行接着跑 |
| `inputQueued` | 会话 | 加 `commandId`；空闲时排的带 `state: "held"` 与原因 |
| `input`、`steer` | 路径 | 加 `commandId` |
| `inputRemoved` | 会话 | 加 `by`；原因 `cancelled`、`aborted`、`replaced`（旧日志的 `user` 读作 `cancelled`），`replaced` 带 `replacedBy` |
| `runStarted` | 路径 | 加 `by` |

- 缓冲区条目的状态只由这几种会话级事件决定（`inputQueued`、`inputHeld`、`inputReleased`、`inputRemoved`、取走它的 `inputConsumed`），会话级归约不读路径级事件。
- 快照与远程合同里，缓冲区的每条带 `by`、`state`、`cause`、`heldBy` 与完整的输入；转录直接读这些事件，不在客户端再推一遍。
- 乐观消息按受理它的 `commandId` 确认，不再按先后：留着的先跑时，先到的是旧话。

### 7. 对话视图

- **排队区**：每条带发出者；留着的显示“已暂停”与原因，文案按原因码取。“继续”放在排队区头上。不是用户排的只能取消、不能编辑；用户自己的“编辑”是取出到输入框，重发是新话。
- **输入框的入口**：有留着的话时是“继续”，上次中断时是“接着跑”，两者都有时“继续”先接着跑中断的那一轮，留着的随后；排队区头上的“继续”是同一个动作。
- **合并之后**：合并出的那一条作为乐观消息显示在末尾，前面还有宿主的话时标“前面还有 N 条”。
- **停止**：见第 2 小节。
- **“等你处理”**：状态栏的 Agent 活动条只把只有用户能放行的算进去（`heldBy: "user"` 的、用户自己的话留着）；其余在会话行上轻标“有暂停的话”。
- **设置**：恢复方式放在 Agent 对话的设置分区，用户层，取值“合并一起发”“保留原插话与排队”“按排队顺序”，缺省“合并一起发”；内核在不带模式时缺省“保留原插话与排队”。

### 8. 备选方案与取舍

- **不改内核，周期任务只在会话空闲、缓冲区为空时发**（bot 提案第三轮后主 Agent 的另一条路）：内核不动，代价是周期任务不能设成插话，排着的周期任务也不在排队区里显示。开发者 2026-11-18 问“直接改内核的缓冲区逻辑呢，架构上会不会更好？”，比较后选了本方案。
- **按收口方式逐行列表**（第一稿）：审查又找出表外的路径；改成“回到空闲”一处。
- **留着由日志推出**（第二稿）：会话级归约要读路径级事件，界面也得再推一遍，停止的原因与谁停的还落在别的写入批里；改成收口同批写显式事件，旧日志不补算。
- **合并做进内核**（第一稿）：合成的那一条要定内容、附件、原文、输入拦截，事件形状一发布就不能改；放到宿主拼，内核只做条件写入的“移除几条、送进一条”。
- **压完在同一次运行里接着开一轮**（第一稿）：已写下的压缩运行里出现对话轮，对话视图与运行结果的含义都要改；改成压完留着、用户自己点的压缩由内核按用户的放行处理。

## 五、数据、接口、安全、迁移、发布与回滚影响

- 数据：会话日志多三种事件、几种事件多几个字段；旧日志照读，旧条目都是就绪的。
- 接口：内核的 `resume`、`release`、`send` 与 `compact` 的选项、宿主发出者、指令按发出者校验与新的失败码；快照与远程合同的缓冲区条目；NeuroBook 的 `agentKey` 按调用方盖章、`jobs/steer.ts` 按状态过滤、对话视图的“继续”“已暂停”、停止的第二个选项、一项用户设置。
- 普通会话的行为变化：
  - 停止后留着的话：现在用户再发一条时新话先跑、留着的跟在后面；改成留着的先跑，缺省与新话合成一条，新话在最后。现行验收（`runtime.md` 验收 2：空闲时入队的排队排在下一句之后）随之改写。
  - 出错、重启之后排着的话：现在下一次运行会顺手带走；改成留着，用户发话或点继续时先跑。
  - 手动压缩时发的话：现在卡住；改成压完自动放行。
  - 回复写下后、运行收口前发的话：现在卡住；改成由这次运行取走或按空闲处理。
  - 子代理交出结果后、空闲时排进来的话：留着，等放行。
  - 错误气泡的“重试”不再顺带发出排着的话。
  - 插件经 `agentKey` 发的话不再算用户的。
- 安全：权限表以发出者如实盖章为前提；盖章之后，发出者不能再改写或取消别人的话，宿主的话不会被别的发出者顺手带走，用户停止留下的只有用户能放行。
- 迁移与回滚：无数据迁移；不支持降级，回滚要连同写过新事件的会话一起处理（同现有规则）。

## 六、对 Spec 的预期改动
