# Agent 内核的输入缓冲区：每条带状态，留着与放行由内核定

起因是 [NeuroBook 的 bot](neurobot.md) 的三轮设计审查：周期任务要往会话的输入缓冲区发消息，而“运行收口后缓冲区里的话归谁取”三轮都找出了新的漏洞（[w00043 t01 第三轮处理](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/bot-proposal-review-r3-disposition.md)）。开发者 2026-11-18 选了“直接改内核的缓冲区逻辑”，本提案就是这件事。它改的是 nb-harness 内核，对所有会话生效，bot 提案引用它。本文不能作为当前行为的依据。

## 一、问题

输入缓冲区放着“提交了还没被取走”的话，每条是插话（`steer`）或排队（`followup`）。现在的规则（[`harness/runtime.md`](../specs/harness/runtime.md) 输出 2、4、7、28–30、34）：

- 运行中每个边界取走全部插话；一轮正常结束（`completed`）时取最早的一条排队，在同一次运行里接着开下一轮。
- 一轮以出错或中止结束时不取排队的；中止缺省清空缓冲区，`keepQueue` 保留；重启后缓冲区留着、不自动发出。这几条来自开发者 2026-10-28 在 [w00032 t07](../../.agents/works/w00032-agent-integration/tasks/t07-run-control/README.md) 的决定 1、3（“出错或中止时不处理”“重启后队列还在但不自动发出，等用户确认”）。

三个毛病，都已用真实内核复现：

1. **两种收口不看缓冲区**：只压缩的运行压完就结束；以收尾工具交出结果的运行（`finished`）也直接结束。这时进来的话会一直留在缓冲区里，会话却已空闲，没人取（[复现一](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/bot-proposal-review-r1-stranded-buffer.test.ts.txt)、[复现二](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/bot-proposal-review-r2-stranded.test.ts.txt)）。普通会话里手动压缩时用户发的话，现在就会这样卡住。
2. **“不处理”不是一种状态**：出错、中止保留、重启之后留着的话，下一次不管谁开运行，都会在第一个边界或一轮结束时被取走（[复现三](../../.agents/works/w00043-neurobot/tasks/t01-direction/evidences/bot-proposal-review-r3-retained.test.ts.txt)）。只有用户会开运行时，这碰巧就是“等用户”；一旦系统也往缓冲区发消息，系统开的一次运行就会把用户留着的话一起带走。
3. **指令不看发出者**：`edit`、`remove` 谁都能对任何一条用；`inputEdited` 换了内容却保留原来的发出者；`start` 不记谁开的。

bot 提案在缓冲区外面补了三轮（只取指定那一条的 `start`、注入方盯着记录去取、自动接续前先查缓冲区），每轮都漏一条新路径。根因是“这条话现在能不能被取走”不在内核里。

## 二、目标与非目标

目标：

- 缓冲区里每条话有明确的状态，取不取、什么时候放行都由内核一处决定，对所有收口方式成立。
- 把 t07 决定 1、3 与开发者 2026-11-18 的“停止、排队的留着，等恢复”写成状态，重启后照样成立。
- 恢复时“留着的先跑”，恢复方式由用户选（开发者 2026-11-18）。
- 指令按发出者有权限，发出者在日志里不失真。

非目标：

- 周期任务本身、宿主消息的来源与授权：在 bot 提案。
- 对话视图的外观：由各自的设计评审定。
- 改插话与排队的基本含义、一条排队开一轮的规则（[Agent harness 的事件模型](agent-harness-event-model.md)待定项 15、16 已定）。

## 三、当前行为与证据

- 一轮正常结束时取排队的、同一次运行接着跑：`kernel/run/loop.ts` 第 381–383 行；只压缩的运行与 `finished` 收口不看缓冲区：同文件第 183–197、347–350 行。
- 中止缺省清空、`keepQueue` 保留、“轮以 `error` 或 `aborted` 结束时不取 `followup`”：输出 30。重启后“缓冲区里的输入留着，不自动发出”：输出 34。
- 输入记发出者：`send`、`enqueue` 经 `as(issuer)` 时写 `by`，用户发的不写（输出 85）；`edit`、`remove`、`start` 不收发出者（`kernel/run/commands.ts`）。
- 界面已有“上次运行已中断，按回车继续”：空着回车走 `start`，写了字走 `send`（[`agent/conversation.md`](../specs/agent/conversation.md) 输出 9）。
- 子代理：父 Agent 用 `agent_send` 往子会话发话，子会话空闲时开新一轮，在跑时缺省插话（[`agent/subagents.md`](../specs/agent/subagents.md) 输出 10）。

## 四、方案

### 1. 每条话的状态

缓冲区里的每条话是两种状态之一：

- **就绪**：可以被取走；
- **留着**：不会被任何运行取走，带原因（`error`、`stopped`、`interrupted`、`finished`、`cannot-continue`）与原因的详情（例如出错的码）。

运行只取就绪的：边界上取全部就绪的插话，一轮正常结束时取最早一条就绪的排队，其余规则不变。

### 2. 运行收口时

| 收口方式 | 缓冲区里就绪的话 |
|---|---|
| 一轮正常结束（`completed`） | 照旧：取最早一条排队，同一次运行接着开下一轮 |
| 只压缩的运行压完 | 有就绪的话时，先看聊天模型能不能解析、会话是不是只读；能用就在同一次运行里接着开一轮（与正常结束时一样，不另开运行）；不能用就全部转成留着（`cannot-continue`，带码） |
| 以收尾工具交出结果（`finished`） | 全部转成留着（`finished`）：结果已经交给父 Agent 或调用方，这次运行不再接着跑 |
| 出错（`error`） | 全部转成留着（`error`，带码） |
| 中止（`aborted`） | 缺省清空，同现在；`keepQueue: true` 时全部转成留着（`stopped`） |
| 重启中断（`interrupted`） | 打开会话恢复时全部转成留着（`interrupted`） |

“只压缩的运行接着开一轮”沿用正常结束时“同一次运行接着跑”的做法，所以不经过重新装配、不另记一次启动；开之前的检查与 `send` 开运行前的检查相同（输出 5）。

### 3. 放行

- **谁发新话，就放行自己留着的**：用户发新话放行全部留着的；会话或宿主以自己的身份发新话，只放行自己排的。例外：`stopped`（用户选了“停止、排队的留着”）只有用户能放行。
- **用户点继续**（`start`，或新增的 `resume`）：放行全部留着的。
- **按条放行**：`release({inputIds})`，用户能放行任何一条，原发出者能放行自己的（`stopped` 除外）。bot 提案里，日程插件在出错后用它放行自己的周期任务。
- **留着的先跑**（开发者 2026-11-18）：放行时，留着的话排在这次新话前面。怎么跑由放行的指令带一个模式，宿主（NeuroBook）按用户的设置传：
  - `merge`（缺省）：同一个发出者的、相邻的留着的话与这次的新话，合成一条输入，开一轮；不同发出者的不合并，宿主的消息单独成条。
  - `keep`：每条保持原来的模式，插话还是插话，排队的还是排队的。
  - `followups`：全部按排队处理，一条一轮，按先后跑。
- 合成的那一条在日志里记下由哪几条合成（`inputMerged{from, into}`），原来的几条以“已合并”离开缓冲区。
- 放行时会话空闲就开运行，第一条开第一轮；在跑就把它们转成就绪，按取的规则在之后的边界或一轮结束时取。

### 4. 指令按发出者的权限

| 指令 | 用户 | 原发出者（会话、宿主） | 别的发出者 |
|---|---|---|---|
| `edit` | 只能改自己发的 | 只能改自己发的 | 不能 |
| `remove` | 任何一条 | 自己发的 | 不能 |
| `release` | 任何一条 | 自己发的（`stopped` 除外） | 不能 |
| `start`、`resume` | 能 | 能，但只放行自己的 | 同左 |

- 不允许时得 `not-allowed`。`inputEdited` 记下编辑者；`start` 记下谁开的（写进 `runStarted`）。
- 应答审批、提问的规则不变（输出 41）。

### 5. 日志、快照与远程合同

- 新事件：`inputHeld{ids, reason, detail?}`、`inputReleased{ids, by, mode}`、`inputMerged{from, into}`。都是会话级事件，回退与 fork 不撤销，同现在的 `inputQueued`、`inputRemoved`。
- 快照与远程合同里，缓冲区的每条带 `state`（就绪或留着与原因）与 `by`。
- 旧日志没有这些事件：归约时按收口方式补出状态，规则同第 2 小节；补出来的只在内存里，不回写旧日志。

### 6. 子会话

- 子会话以收尾工具交出结果后，排着的话转成留着（`finished`）。派它的父 Agent 再用 `agent_send` 发话时，以会话的身份放行它自己排的；用户在子会话里发话或点继续，放行全部。
- 父会话连带中止子会话时用 `keepQueue: true`（[`agent/subagents.md`](../specs/agent/subagents.md)），子会话里排着的话转成留着（`stopped`），等用户。

### 7. 对话视图

- 排队区里留着的话显示“已暂停”与原因，旁边有“继续”；只有宿主排的、用户不能改写的那几条不显示“编辑”。
- 缓冲区不空时，停止按钮给两个选项：“停止并清空排队”，与“停止，排队的留着”（`keepQueue: true`）。
- 用户设置里选恢复方式：合并一起发（缺省）、保留原插话与排队、按排队顺序。

### 8. 备选方案与取舍

- **不改内核，周期任务只在会话空闲、缓冲区为空时发**（bot 提案第三轮后主 Agent 的另一条路）：内核不动，代价是周期任务不能设成插话，排着的周期任务也不在排队区里显示。开发者 2026-11-18 问“直接改内核的缓冲区逻辑呢，架构上会不会更好？”，比较后选了本方案。
- **在缓冲区外按发出者分别取**（bot 提案第五到第七稿）：三轮审查各漏一条路径，因为内核在边界上不分发出者地取整个缓冲区。
- **内核在 `finished`、只压缩之后另开一次运行**：要定它和重新装配的先后、这次运行的发起者与崩溃后的认法。只压缩的运行改成同一次运行接着跑，`finished` 改成留着，就都不需要了。

## 五、数据、接口、安全、迁移、发布与回滚影响

- 数据：会话日志多三种会话级事件；旧日志照读，状态按收口方式补出。
- 接口：内核的 `release`、`resume` 指令与放行模式，`edit`、`remove` 按发出者校验，`runStarted` 与 `inputEdited` 记发出者，快照与远程合同的缓冲区条目加 `state`、`by`；NeuroBook 加一项用户设置与对话视图的“继续”“已暂停”、停止的两个选项。
- 普通会话的行为变化：
  - 手动压缩时发的话，压完会接着跑；
  - 出错、“停止，排队的留着”、重启之后留着的话，要等用户发新话或点继续才跑，而且排在新话前面。现在是新话先跑、留着的跟在后面；
  - 子代理以收尾工具结束后，它缓冲区里的话等父 Agent 或用户放行，不会被下一次运行顺手带走。
- 安全：发出者不能再改写或取消别人的话，审批模型按发出者分的材料不会因编辑而失真。
- 迁移与回滚：无数据迁移；回滚时新事件会被旧内核当作未知的会话级事件，需要随内核一起回滚。

## 六、对 Spec 的预期改动

- `harness/session.md`：三种新事件、旧日志的补法。
- `agent/sessions.md`：远程合同的 `release`、`resume`，缓冲区条目的 `state`、`by`。
- `agent/conversation.md`：“继续”与已暂停的条目、停止的两个选项、恢复方式的用户设置（输出 9 一并改）。
- `agent/subagents.md`：`finished` 之后留着、`agent_send` 放行自己排的、连带中止时留着。
- `ui/agent-conversation-view.md`：排队区的状态与“继续”。
