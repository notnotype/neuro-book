# 桌面发行：Windows 安装包、便携包与打标签自动发布

本稿回应 [ADR 0033](../adr/0033-app-delivered-as-built-npm-package.md) 决定 6 留下的“发行按两个维度另写提案”。调研、实测与审查都在 [w00046 t01](../../.agents/works/w00046-desktop-release/tasks/t01-distribution-proposal/README.md)，下文只写结论，数字与过程见那里的证据。

## 一、问题

现在装 NeuroBook 只有一条路：先装 Bun，再在终端里 `bun add -g @notnotype/neuro-book`，再运行 `nbook`，页面开在浏览器里。对不用命令行的写作者，这三步每一步都会把人挡住；Windows 用户尤其如此，旧应用的 Windows 一键启动在 v2 里已经删掉（ADR 0033 决定 7）。

发布也是手工的：开发者在本机 `npm login` 后跑 `release:publish`，没有 GitHub Release，CI 不参与发布。

## 二、目标与非目标

目标：

- Windows 用户下载一个安装程序，装好后从开始菜单或桌面打开 NeuroBook，在应用自己的窗口里写作；不需要装 Bun，不需要碰命令行。
- 同时提供便携包：解压到一个可写的目录就能用，程序与 NeuroBook 的状态（作品登记、设置、插件）随这个目录走。
- 装好的桌面版能自动更新。
- 打产品版本的标签后，CI 验证、构建、冒烟并发布全部产物（npm 包、桌面包、GitHub Release），不需要人在本机操作。

非目标：

- macOS 与 Linux 的桌面包：方案按三平台设计，第一版只做 Windows。
- 代码签名（开发者 2026-11-13 定不买 Windows 签名证书）。
- 有界面的安装程序、自定义标题栏、桌面端专有设置（开机自启、系统托盘、通知）：已建为 w00046 的 t02 到 t04，另行设计。
- 服务器部署、后台常驻（`nbook service`）：ADR 0033 已把它们划给别的提案。

## 三、当前行为与证据

Windows 上的实测（开发机 pc-notype 与 GitHub 的 windows-2025 runner）结论：

- **新应用在 Windows 上能跑。** `smoke:server` 十个场景过九个，项目子进程、命名管道的实例认领、SQLite、标准输入停止都正常；没过的是 SIGTERM 停止，Windows 没有这个信号，标准输入是唯一的有序停止渠道。
- **Agent 的命令工具在 Windows 上能用。** 它跑在 pi-natives 内嵌的 bash 兼容 shell 里，自带常用命令，不需要 Git Bash；git、awk、python 走系统程序。
- **Electrobun 原型走通了单窗口的主路径。** 用随包的 Bun 拉起服务端、窗口加载回环页面、关窗经标准输入停止、卸载都正常；双击安装由开发者验证。安装包约 86 MB，装好后 275 MB（Bun 与 pi-natives 各占一百多 MB）；打开书房后整套工作集约 610 MB，其中 WebView2 约 430 MB。原型只覆盖空书架，没有覆盖编辑中的关闭、多窗口与更新。
- **CI 能无人值守地构建与冒烟。** runner 上能构建、静默安装、起应用到页面就绪、关窗停止、卸载；但安装程序在没有桌面的会话里装完不会自己打开应用，冒烟要直接起应用。
- **外壳崩溃。** 强行结束壳进程后服务端随之退出，不留孤儿，但没走有序停止。

## 四、方案

### 4.1 两种发行，同一份应用包

| 发行 | 给谁 | 运行时 | 界面 |
|---|---|---|---|
| npm 包 `@notnotype/neuro-book`（已有） | 会用命令行的人、Agent、作者 | 用户自己的 Bun | 浏览器 |
| 桌面包（新增） | 写作者 | 随包的 Bun | 应用窗口 |

桌面载荷由发布到 npm 的那个应用包 tarball 组装，不另外构建：

- 应用包补上服务端的托管入口 `server/main.js`（今天只在 `dist/server` 里，`pack-app.ts` 没打进包；`nbook.js` 不接受 `--stop-stdin`）。
- 组装时解开同一个 tarball，按它声明的四个外部依赖（`@oh-my-pi/pi-ai`、`pi-catalog`、`pi-natives`、`pi-utils`，ADR 0036 让它们留在 bundle 外）装出 Windows 的依赖闭包，版本与仓库根 `bun.lock` 一致；许可文件与产品文档随载荷保留。
- 载荷的文件清单与摘要记进发行清单，安装版与便携版都从这份载荷封装。

桌面包与 npm 应用包版本相同：桌面版只改壳也要发一个新的产品版本，代价是多发一次 npm 应用包，换来“一个版本号对应一份服务端”。

### 4.2 桌面壳用 Electrobun

开发者 2026-11-13 定直接用 Electrobun，候选 Electron，不再按 ADR 0033 决定 6 在三者之间逐一实测。看重的是：

- 包小：用系统的 WebView2，安装包约 86 MB；旧应用 2026-08 的同类实测里 Electron 便携包在 230 MB 以上。
- 自带安装程序、卸载程序、增量更新与 GitHub Actions 的构建示例。

代价与约束：

- 项目年轻（v2 刚发布）；系统 WebView2 的版本随用户机器变化，页面兼容性按 WebView2 测。
- 随包 Bun 的版本由 Electrobun 版本决定，不能单独指定（2.0.6 对应 Bun 1.4.4，正好是 pi-natives 要求的下限）。服务端或依赖要更新的 Bun 时，先升 Electrobun；升级顺序写进发布流程。
- 一次性选择：应用的 `identifier`、发布频道与更新源地址写进已装的应用，决定安装目录、WebView2 数据目录与更新来源，发出去以后改动要用户重装；第一版定下后写进 Spec。以后换壳（比如换成 Electron）时，服务端合同不变，但已装用户的安装与更新通道要迁移，这是换壳的真实代价。

候选 Electron 只在遇到 Electrobun 解决不了的阻断时启用。

### 4.3 桌面壳的寿命与窗口

壳只负责窗口与服务端的寿命，产品逻辑在服务端与页面。

**单实例。** 同一个状态根上只有一个桌面壳：壳启动时先取桌面自己的单实例锁（由状态根派生，做法同服务端的实例认领）；锁已被别的桌面壳持有时，把“开一个窗口”交给它，自己退出。所有桌面窗口都归这一个壳管。

**连接服务端。** 拿到锁之后问状态根上的服务端实例，判定与 `nbook start` 相同（[`runtime.cli`](../specs/runtime/cli.md) 的状态与转换）：

| 问到 | 桌面壳做什么 |
|---|---|
| 没有实例 | 用随包的 Bun 拉起 `server/main.js --stop-stdin`，成为它的拥有者 |
| 就绪的产品实例，版本相同（例如 `nbook` 起的） | 开窗口连它；不拥有它，关窗不停它 |
| 启动中或停止中，版本相同 | 启动页显示“正在启动”或“正在停止”，等它（有截止） |
| 版本不同、开发实例、没有应答 | 启动页说明运行中的是哪个版本、谁起的，提示先停掉它再打开；不碰那个实例 |

壳从实例认领的应答里读就绪状态与地址，不解析服务端标准输出的文字。服务端用缺省端口（4217 起，被占用时成对顺延）：页面的客户端身份、主题、语言存在按来源隔离的浏览器存储里，端口一变它们就不见了，所以不用随机端口。缺省端口被别的程序占着、发生顺延时，这些前端设置会回到默认，这是与 `nbook` 相同的已知限制。

**关闭窗口。** 用户关一个窗口时，壳先拦下原生关闭，问这个窗口里的页面能不能关：编辑器结算输入、按编辑器合同保存或询问用户；有 Agent 任务或工作流在跑、而这是最后一个窗口时，提示“关闭会中断正在进行的任务”，用户选取消或仍然关闭。页面同意后才真正关窗。原生关闭不会触发浏览器的 `beforeunload`，这个“关闭前询问”要页面与壳之间新加一个约定（见第六节）。

**停止服务端。** 最后一个窗口关闭、且服务端归这个壳拥有时，壳往服务端标准输入写 `stop`。壳的状态分运行中、停止中、已停止三态：没到已停止时，每一次退出请求（包括框架自己的末窗退出、更新退出）都同步否决。截止时间不短于服务端自己的停止预算（排空、项目子进程逐个停止）；超时才强制结束，并把这次记为“没有正常停止”，下次启动时提示。

**崩溃与异常结束。** 壳被强行结束、注销、关机时，服务端随之被结束，不保证有序停止。能保证的是服务端已经提交的数据（SQLite 与原子写入）；还在页面里、没交给服务端的输入可能丢失。Spec 分别写“正常停止”与“不保证清理”两类结果，验收在打开作品、正在写入时强行结束。

**导航与新窗口。** 窗口只允许导航到启动页与当前服务端的精确来源，其余一律拒绝；页面里打开本机作品的新窗口由壳开一个新的桌面窗口；外部的 `http`、`https` 链接交给系统浏览器；`file` 与其它协议拒绝。页面不需要壳的原生接口的部分启用 Electrobun 的沙箱，确需的接口（关闭前询问、更新提示）只给最小的方法。

**WebView2 缺失。** 第一版支持 Windows 10、11 的 x64（具体下限以 Electrobun 与 WebView2 的要求为准，实现时查清）。壳在创建网页视图之前检查 WebView2，没有时用系统对话框说明并给出官方安装地址，不显示空白窗口。

### 4.4 状态根与数据位置

| 内容 | 安装版 | 便携版 |
|---|---|---|
| NeuroBook 状态根（作品登记、设置、插件、日志） | ADR 0033 的缺省：`%LOCALAPPDATA%\NeuroBook`，与 `nbook` 共用 | 程序目录下的 `data\` |
| WebView2 的浏览器数据 | Electrobun 管的 `%LOCALAPPDATA%\<identifier>\stable` | 同左，留在本机 |
| 作品本身 | 用户选的文件夹，缺省 `文档\NeuroBook` | 同左 |

- 状态根不放进 Electrobun 管的目录：卸载时选“应用和数据”会删掉那个目录，作品登记与设置不应该跟着一个卸载选项消失；放在 ADR 0033 的位置，桌面版和 `nbook` 看到的是同一个书架。ADR 0033 定的“服务端进程要求显式状态根”不变：由壳算出状态根再交给服务端。
- 便携版的识别：程序根目录里的标记文件，只由 CI 打便携包时写入，安装包里没有；优先级是环境变量 `NBOOK_STATE_ROOT`、便携标记、缺省位置。
- 便携版要求程序目录可写；不可写（例如只读介质）时启动页显示实际路径，建议复制到可写位置，不悄悄改用安装版的状态根。
- 便携版只让程序与状态根随目录走：作品缺省仍建在本机文档目录；作品登记记的是绝对路径（[`runtime.projects`](../specs/runtime/projects.md)），把目录挪到别处或盘符变了以后，要重新打开作品；WebView2 的缓存留在本机（开发者 2026-11-13 接受）。这些写进便携包的说明。

### 4.5 安装包与便携包

- **安装包**：Hutch 产出的 `Setup.zip`，setup 没有界面，静默装到 `%LOCALAPPDATA%`（按用户安装，不要管理员权限），建开始菜单与桌面快捷方式，装完打开应用（开发者 2026-11-13 定第一版接受；有界面的安装程序是 t02）。
- **便携包**：CI 把组装好的应用加上便携标记打成 zip，作为独立资产单独冒烟（解压到别处启动），不是从安装版复制。便携版不做应用内更新，只提示有新版本并打开下载页。
- **未签名**：第一次运行 setup 会看到 SmartScreen 的“未知发布者”，下载页写明怎么点“仍要运行”。

### 4.6 自动更新

- 用 Electrobun 的 Updater，更新源是 GitHub Releases 最新 Release 的下载地址。应用启动后在后台检查；有新版本时提示用户，用户确认后下载，退出时换上，下次打开就是新版本。
- **只升不降**（开发者 2026-11-13 定）：Electrobun 的更新器只比较包的哈希、不比较版本，壳在下载前核对远端版本号，只接受更高的版本。
- **换上的时机**：更新下载好以后，壳在最后一个窗口关闭、自己拥有的服务端停完之后才调用更新器换文件；服务端不归自己（例如 `nbook` 起的）时不受影响，它用的是自己的文件。
- **目标移动**：检查到新版本 B 之后、下载之前又发了 C 时，按 B 校验会失败；壳在下载失败时重新检查、重新提示。跨版本（A 直接到 C）没有现成的增量补丁，下载完整包（约 86 MB）。
- **真实性**：不签名，只靠 HTTPS 与 GitHub 账号的安全（开发者 2026-11-13 接受）。谁能改 GitHub Release，谁就能给已装用户推更新；更新清单里的 SHA-256 只防传输损坏，不防冒充。

### 4.7 外部工具

开发者 2026-11-13 定第一版只检测、提示：Agent 用到找不到的 git 或 python 时，在对话里说明缺什么、去哪装（官方地址或 winget 命令）。随 NeuroBook 安装、装到系统两条安装路径，等有了实际需求再做。这部分与桌面壳没有技术依赖，npm 版同样适用，单独在 w00046 t05 做，配 Spec。

### 4.8 CI 与打标签自动发布

**标签与版本。** 只接受稳定版本号的标签 `v<产品版本>`，预发布标签第一版拒绝。产品版本只有一个来源，下列各处必须相同：应用包与 SDK 包的 `package.json`、`PRODUCT_VERSION`、Electrobun 的 `app.version`。九个源码包保留各自的版本，沿用现有规则：没发过的版本才发（ADR 0029）。

**新增 `release.yml`，由标签触发，按顺序：**

1. **门禁**：标签指向的提交在 `origin/master` 上；该提交的 CI 结论为成功（把 `ci.yml` 改成可复用的工作流，在标签提交上调用同一份，不另写一套）；版本一致性如上。任何一项不过就不往下走。
2. **构建与冒烟**：
   - ubuntu：`release:smoke` 打出 11 个包并跑现有闭环，tarball 与清单作为产物上传；
   - windows：下载上一步的应用包 tarball 组装桌面载荷（见 4.1），Hutch 构建，然后冒烟：静默安装、直接起应用到页面就绪、打开一部作品并执行一条内嵌 shell 命令、经关闭前询问关窗并有序停止、卸载；便携 zip 单独解压到别处再跑一遍；产出安装包、便携包、更新文件与摘要。
3. **发布 npm**：只发第 2 步验过的那批 tarball，核对清单的提交等于标签提交、每个 tarball 的摘要相同。CI 里用 npm CLI（11.5.1 以上）走 trusted publishing（GitHub OIDC），不存长期 token；`publish.ts` 增加 CI 入口：不跑 `npm whoami`、不要求当前分支叫 master（标签检出是分离的 HEAD），改核对标签提交，用 `npm publish <tarball>` 代替 `bun publish`（tarball 已由 `bun pm pack` 改写好依赖，ADR 0029 不用 npm 发布的理由在这里不适用）。本机的手工发布入口保留原有门禁。一次性准备：11 个包都要在 npm 上配置信任这个工作流。
4. **发布 GitHub Release**：先建草稿 Release，上传全部资产与 `SHA256SUMS`，核对后再公开并设为最新。

**失败与重跑。** 这四步不是跨 npm 与 GitHub 的事务，可能出现“npm 已发、Release 没建”。重跑时复用第 2 步保存的同一批产物，不重新构建；npm 上已有同版本而摘要不同时失败；Release 只补缺的资产，同名而摘要不同时失败。发布作业串行（同一时间只有一个），标签版本不高于当前最新 Release 时不设为最新，避免旧任务重跑把“最新”往回拨。

**其它。**

- Hutch 与 Electrobun 的版本都固定（现在是 0.29.0 与 2.0.6），升级单独提交。Hutch 0.29.0 在设了 `HTTPS_PROXY` 时下载必失败，只能直连；runner 上没有代理不受影响。
- 仓库的 GitHub Releases 里还有旧应用 0.10.x 的版本；v2 的桌面 Release 版本号更高，会成为“最新”。`repository-workflow.md` 里“GitHub Releases 只留旧应用历史版本”那句随本稿改写。

## 五、数据、接口、安全、迁移、发布与回滚影响

- 数据：桌面版与 `nbook` 共用状态根，格式不变；便携版的状态根在程序目录里。异常结束时只保证服务端已提交的数据（见 4.3）。
- 接口：应用包新增托管入口 `server/main.js`；`--stop-stdin` 与实例认领的应答从内部约定变成桌面壳依赖的合同；页面新增“关闭前询问”的约定。
- 安全：服务端仍只监听回环；窗口的导航与新窗口按 4.3 收紧。未签名的安装包与更新包的真实性只靠 HTTPS 与 GitHub（开发者已接受）。
- 发布：版本号收不回，所有验证与冒烟都在发布前跑完；部分成功的状态与重跑见 4.8。
- 回滚：不自动降级（开发者 2026-11-13 定）。出问题时发一个递增版本的修复版；npm 可以用 `npm dist-tag` 把 latest 指回旧版本，桌面版不把旧版本重新设为最新。用户确需旧版时手动重装；状态根与作品数据不会跟着回滚，旧版可能读不了新版写过的数据（例如 Storage 的分区版本），说明里写明先备份。

## 六、对 Spec 的预期改动

- 新建 `runtime/desktop-shell`：单实例与开窗转交、连接服务端的判定表、从认领应答取地址、关闭前询问与三态停止、截止与“没有正常停止”的记录、崩溃的两类结果、导航与新窗口、WebView2 检查、状态根与便携标记、更新的检查、只升不降、换上时机与目标移动。验收用 Windows runner 上的真实安装包：同版本复用、异版本拒绝、两个启动同时发生、任意顺序关窗、编辑中关窗（自动保存、未交出的输入、取消）、有任务在跑时关窗、写入中强行结束、便携包换目录、更新的升级与拒绝降级。
- 改 `runtime/server-host`：`--stop-stdin` 与认领应答作为托管宿主依赖的合同写明。
- 改 `runtime/browser-host` 与 `workbench/editor`：宿主发起的关闭前询问（结算输入、保存或询问、有任务时提示），原生窗口关闭不经 `beforeunload`。
