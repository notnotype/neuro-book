# 统一后台任务：一份清单汇总各插件的工作，会话收提示

第 3 稿（2026-11-19，接受）。本稿只写方向、开发者的决定与实现必须守住的规则；事件形状、取走的确切位置、预算的数值与各条时序由实现 Task 先用真实内核探针列全路径、再写进 Spec。两轮设计审查（[第一轮](../../.agents/works/w00032-agent-integration/tasks/t22-background-work/evidences/proposal-review-r1.txt) 28 条、[第二轮](../../.agents/works/w00032-agent-integration/tasks/t22-background-work/evidences/proposal-review-r2.txt) 30 条）没有质疑方向，问题都在实现层面，已按 Task 分好，作为各 Task 的输入。

## 一、问题

1. **后台工作分在几处，互相看不见**。插件的长任务在 `nbook.tasks` 的清单里；Agent 的后台命令与子代理运行只在对话的卡片上；Agent 的运行只在对话与会话列表里。以后还会有更新、带进度的计算、定时任务、HTTP 服务、端口转发。
2. **Agent 不知道后台任务结束了**：结果要它自己调 `wait` 才取得，这一轮结束了就没人提醒它。
3. **插件没法给会话递一句“你该知道的事”**：eval 的内核被回收或意外退出，模型要等下一次调 eval 才知道；后台任务结束、子代理有话问它，也是同一类需要。

## 二、目标与非目标

目标：

- 工作台有一份后台工作的清单，按归属（应用、项目、会话）、形态（一次性、服务、定时）与种类分组；清单只汇总与转发操作，状态留在拥有它的插件里。
- 内核的输入缓冲区多一种“提示”：下一次请求带上，可以要求唤起空闲的会话；唤起的门挂在会话上。
- Agent 取异步结果有两条路：自己 `wait`；或者结果作为提示送回会话。
- 给 t24（Workflow 与 Agent 的对接）与 w00043 t10（`nbook.schedule`）留好位置。

非目标：服务与定时的实现（随第一个用到的插件）；清单与任务表持久化；项目子进程里发起的工作进清单（第一批只收服务端的，`project` 只是归属标签）；Monitor、后台命令的 stdin、eval 单元自动转后台；周期任务本身与宿主消息的来源说明（[bot 提案](neurobot.md)）；输入的状态与放行（[缓冲区提案](agent-input-buffer-states.md)）。

## 三、当前行为与证据

- `nbook.tasks`（[`workbench/background-tasks.md`](../specs/workbench/background-tasks.md)）：服务端入口 `start()` 登记、内存清单、视图、状态栏、结束通知、“在跑的工作”；现在只有 Agent 装 Skill 依赖时用。
- Agent 的任务中心（[`agent/jobs.md`](../specs/agent/jobs.md)）：内存表，按启动它的会话记；`wait`、`kill`、`jobs`；结束时不通知、不唤起。后台命令是服务端进程的子进程，子代理在同一个进程的会话表里，eval 内核是单独的 Bun 子进程；插件的工具实现也由 Agent 在同一个进程里调。
- 内核的缓冲区（[`harness/runtime.md`](../specs/harness/runtime.md) 输出 3、28、103–110）：插话下一个边界取走、排队一轮结束时取走；就绪与留着；发出者有用户、会话、宿主。现在的边界先取插话、再压缩、再组请求。
- 参照：omp 18.14.1 把后台结果合成一条消息送回会话、空闲时开新的一轮、用户打断后不自动唤起；Claude Code 后台命令结束时唤起 Agent；VS Code 的 Task Provider、systemd 的 Unit 与 Job 都是“状态归各自的提供者，管理界面只汇总”。

## 四、方案

### 1. 缓冲区的提示（实现：t41）

缓冲区里每种话按自己的时机发出：提示下一次对话请求就带上、排在插话与新话前面；插话下一个边界；排队一轮结束时或下一次运行（开发者 2026-11-19）。

规则：

1. **取的位置同插话**：提示在取插话的同一处取走，同一次请求里排在插话与新话前面；压缩、回退、fork 对它与对插话一视同仁。为此可以改内核现有的边界顺序。只压缩的运行不取；预览按同样的规则只读显示，不取走。
2. **不是输入**：提示不进输入的就绪与留着、不用放行；回到空闲、停止、出错都不改变它，一直待发到下一次对话请求；它是会话级的，回退、换分支不影响待发的提示。
3. **送达的保证与插话相同**：取进某一次请求就算送达，之后随路径走。Profile 能合法地裁掉历史（`finalOnly`、不带历史的布局），这对提示与插话一样，由 Profile 自己注意；内核若能简单做到“取走后那次请求没发出去就放回缓冲区”，对提示与插话一起做，太复杂就接受这个限制（开发者 2026-11-19）。
4. **给模型的样子**：内核渲染成 `<system-reminder>` 加来源行（格式同 bot 提案的宿主消息），正文转义；提示不是用户的话，不算授权依据、不解除运行守卫的停止、不让 `wait` 或前台等待以“插话”提前返回。
5. **大小**：单条与每个会话待发的合计都有上限，并且与缓冲区里的输入共用快照的大小预算；超出时发提示失败、什么都不写，发出方自己留着内容。
6. **替换与撤回**：同一发出者带同一个 `key` 的新提示替换还没取走的那条；发出者能撤回自己的，用户能取消任何一条（开发者 2026-11-19）。
7. **唤起**：提示可以要求唤起。会话空闲、门开着时开一次运行；在提示受理时与每个收口的写入批里判。收口时一个会话只能开一次后继运行：推迟到收口的用户的话（或宿主的发话）优先开、记成它开的，待发提示随它的第一次请求带上；没有别的理由开运行时，才由提示开一次没有新话的运行。唤起的提示在第一次请求前都被撤回或取消时，不发空请求。
8. **门挂在会话上**（开发者 2026-11-19）：用户的停止被受理时、运行不是正常结束时（出错，含循环保护与费用上限；进程中断）关门，记在会话日志里；用户自己的发话、继续、放行真正被受理并开起运行时开门。回退、换分支、压缩都不开门；旧日志的初值在 Spec 里定。

和 bot 提案的关系：bot 提案的“宿主消息不另开一种输入类型”管的是要 Agent 去做事的消息，日程照旧发排队或插话；提示只告诉、不要求，所以有自己的取走规则。

### 2. 清单：自己的任务加提供方的行（实现：t42）

1. **状态各归其主**（开发者 2026-11-19）：`nbook.tasks` 只汇总显示、分组与转发操作。服务端插件把自己登记成提供方，交出“现在有哪些行”与变化，收到操作自己去做；简单的长任务照旧 `start()`，规则不变。服务与定时的定义由提供方存在自己的数据里，激活时重新交出行。
2. **行**：标题、进展、进度、状态、时刻、归属、种类（盖上提供方前缀）、形态、可做的操作、打开的去处；字段按编码后的大小有上限。
3. **指认要准**：操作带上提供方这次注册的代次，提供方停用又激活之后，旧窗口的点击落不到新一代的同名行上，得“目标已不在”。
4. **大小与分页**：整份清单不能因为某一家行多而超出远程合同的上限；按筛选分页，计数取汇总，不靠可见的那一页。
5. **隔离**：一家提供方出错或交出不合格的行，只影响它自己那几行；提供方撤回时先封住派发、退订，再丢旧回调。
6. **操作的结果**：停止分“已受理”“没受理”“结果未知”，未知的不自动重试；打开走拥有这个对象的插件的导航（会话走 Agent 按归属的导航，bot 的主对话走 bot 插件），打不开如实报失败。
7. **通知与看过**只对 `nbook.tasks` 自己的任务，照现在的规则；视图筛选只影响显示。
8. **视图**按归属分组：缺省看当前项目、应用与全部会话，能切到全部项目；状态栏只数在跑的一次性工作。远程合同升版本。

### 3. Agent：作提供方，结果送回会话（实现：t22，依赖 t41；交给清单的行依赖 t42）

1. **状态不搬**：后台命令、子代理运行、插件的工具登记的任务仍在 Agent 的任务中心；`jobId`、`wait`、`kill`、`jobs`、远程合同、上限照旧。Agent 仍自己向宿主报“在跑的工作”（含手动压缩），并修掉现在“同一个子代理执行报两次”的毛病。
2. **交给清单的行**：每件后台任务一行（子代理任务代表那次子会话的执行）；每个在跑或等你处理的根会话一行（开发者 2026-11-19：按会话一行），停止是以用户身份停它当前的运行、保留排队的话；没有任务覆盖、却在跑的子会话也要有行；结束了、没取过的任务行留到取过。
3. **结果只交一次**：一件任务的结果只有一个出口——`wait`、前台调用、或一条提示——在任务中心里同步领取。同一会话同时结束的几件合并成一条；每件有稳定的结果引用（输出文件、子会话日志），正文有上限；单件读失败不拖住别的。根会话的提示带唤起，子会话的不带。
4. **送达的结算**：受理即送达；确定没写进去就退回给 `wait`；写入结果未知时标“送达未确认”，下次打开会话时按提示的 id 查日志再定，绝不交两次（开发者 2026-11-19）。
5. **与 `wait` 一样的脱敏**：自动送达的正文要受 `wait` 的工具结果同样的发布约束，不能绕过扩展的脱敏。
6. **子代理有话问父 Agent**：同步提问也发一条带唤起的提示，写明子会话 id、提问 id、题干与回答的形状；在提示取走前被答了、停了或过期，就撤回。
7. **插件的工具登记任务**：每次真实的调用一份登记权，绑定这次调用与贡献工具的插件的这一代；撤回时封住这一代、退还没开始的名额、停掉在跑的；外部种类在 `jobs`、`wait` 与远程里都能辨认。
8. **子代理任务的停止与结果**绑定那一次执行：停止只停它，结果在收口时定下，`wait` 与提示用同一份。
9. **`shell` 自动转后台**：只对顶层的、不在子代理会话里的 `shell`；前台过门槛（缺省 60 秒，0 为关）转后台；时限照原来的（开发者 2026-11-19）；命令只起一次，从一开始就是一份连续的输出记录，交接时不同步拷贝大文件；转不成就留在前台照原合同跑完。nb-harness 套件只加可选的接口，`async` 不变。
10. **eval 的提示**：内核的持有者对每一代内核的退休只发一次提示（不唤起）；新内核已经能用之后不再排进去、已排的撤回；下一次 eval 结果第一行照旧写“内核已重置”（开发者 2026-11-19：说两遍）；执行中崩溃的那次结果已经说了，不另发。
11. **子代理卡片**：结果被送达后，卡片按子会话 id 与运行 id 读那次收口的有界结果；同一运行回退后接着跑时读到最近一次，算已知限制。

### 4. 备选方案与取舍

- **状态都搬进 `nbook.tasks`**（第 1 稿）：两套生命周期打架（50 件上限与“留到取过”、两种 id、校验卡住收口、一次执行登记两行），第一轮一半的问题在这里。
- **结果作为宿主的插话**（t22 计划第 1、2 稿）：模型看到的是用户角色的话，停过之后要定谁放行、回退后会不会被别的送达带走。
- **唤起看当前叶子**（第 1 稿）：停止之后回退一下就能唤起。
- **由扩展在请求时自己拼提醒**：每个发出方都得装在会话里、自己记说过没有；要随路径重新描述的事实以后仍可以用扩展。
- **提案里写定事件与时序**（第 2 稿）：两轮审查各近 30 条都在内核细节上；改成提案只定规则，细节由 Task 探针后写进 Spec。

## 五、数据、接口、安全、迁移、发布与回滚影响

- 日志：内核多几种会话级与路径事件（提示、门），旧内核读到拒读，不做降级。
- 接口：`nbook.tasks` 加提供方登记与新的远程合同版本；`nbook.agent` 的远程合同为取消提示与新种类改版本；nb-harness 套件的 `shell` 加可选参数。
- 安全：提示不算授权、不解除守卫；提供方与任务种类由服务盖章；工具登记的任务绑定真实调用；提示正文转义；自动送达受脱敏约束；派生的会话视图随插件停用作废。
- 迁移：没有持久数据要迁。回滚要连同日志格式。
