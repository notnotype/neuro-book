# 统一后台任务：一份清单汇总各插件的工作，会话收提示

第 2 稿（2026-11-19）。第 1 稿把 Agent 的任务状态搬进 `nbook.tasks`、提示的唤起按叶子判，第一轮审查（28 条，[证据](../../.agents/works/w00032-agent-integration/tasks/t22-background-work/evidences/proposal-review-r1.txt)）多半出在这两处；本稿改成清单只汇总、状态各归其主，唤起的门挂在会话上（决策记录 2026-11-19 第 5、6 行）。

## 一、问题

1. **后台工作分在几处，互相看不见**。插件的长任务（安装 Skill 的依赖）在 `nbook.tasks` 的清单里，工作台有视图、状态栏与通知；Agent 的后台命令与子代理运行在 `nbook.agent` 的任务中心里，只在对话的卡片上看得到；Agent 的运行只在对话与会话列表里看得到。用户切到别的对话，就不知道哪个会话还挂着一条命令。以后还会有更新、带进度的计算、定时任务、HTTP 服务、端口转发，按现在的做法每样都要再找个地方挂。
2. **Agent 不知道后台任务结束了**。转后台的命令、后台子代理结束后，结果等 Agent 自己调 `wait` 才取得；这一轮已经结束的话，没人提醒它。
3. **插件没法给会话递一句“你该知道的事”**。eval 的内核因空闲被回收或意外退出时，模型要等下一次调 eval 才在结果第一行看到“内核已重置”。后台任务结束、子代理有话问它，都是同一类需要：一条不是用户说的、下一次请求带给模型的提示。

## 二、目标与非目标

目标：

- 工作台有一份后台工作的清单，按归属（应用、项目、会话）与种类分组。清单只汇总与转发操作：每件工作的状态留在拥有它的插件里（Agent 的任务中心、以后的日程与服务插件），由它作为**提供方**交出行；没有自己状态表的简单长任务照旧直接登记进 `nbook.tasks`。
- 内核的输入缓冲区多一种“提示”：下一次对话请求带上、排在插话与新话前面，可以要求唤起空闲的会话；唤起的门挂在会话上。
- Agent 取异步结果有两条路：自己 `wait`；或者结果作为提示送回会话。
- 给 t24（Workflow 与 Agent 的对接）与 w00043 t10（`nbook.schedule`）留好位置：Agent 启动的 Workflow 登记进 Agent 的任务中心；日程作为提供方把条目交给清单。

非目标：

- 服务与定时的实现：本提案只定它们作为提供方的行有什么字段；实现随第一个用到的插件（日程是 w00043 t10）。
- 清单或任务表持久化；项目子进程里发起的工作进清单（第一批只收服务端的，`project` 只是归属的标签）。
- Monitor、后台命令的 stdin、eval 单元自动转后台。
- 周期任务本身、宿主消息的来源说明与授权（[bot 提案](neurobot.md)第四节第 6 小节）；缓冲区的状态与放行（[缓冲区提案](agent-input-buffer-states.md)）。

## 三、当前行为与证据

- `nbook.tasks`（[`workbench/background-tasks.md`](../specs/workbench/background-tasks.md)）：服务端入口调 `start` 登记，按登记它的插件入口记；清单只在内存，结束的至多留 50 件；视图、状态栏、结束通知；向宿主报“在跑的工作”。现在只有 `nbook.agent` 装 Skill 依赖时用它（可选依赖）。
- Agent 的任务中心（[`agent/jobs.md`](../specs/agent/jobs.md)）：`nbook.agent` 服务端入口里的内存表，按启动它的会话记；`wait`、`kill`、`jobs`；任务结束时不通知、不唤起。后台命令是服务端进程的子进程，子代理的子会话在同一个进程的会话表里，eval 的内核是单独的 Bun 子进程；别的插件的工具实现也由 Agent 在同一个进程里调。Agent 单独向宿主报“在跑的工作”（[`agent/sessions.md`](../specs/agent/sessions.md) 输出 20）。
- 内核的缓冲区（[`harness/runtime.md`](../specs/harness/runtime.md) 输出 3、28、103–110，w00043 t14 已实现）：插话下一个边界取走、排队一轮结束时取走；就绪与留着；发出者有用户、会话、宿主。内核自己的提醒（`notice{code: "tools-changed"}` 等）在请求之前写进日志，外部没有入口。
- 参照：omp 18.14.1 把后台任务的结果合成一条消息送回启动它的会话、空闲时开新的一轮、用户打断之后不自动唤起（`session/async-job-delivery.ts`、`session/agent-session.ts`、`session/yield-queue.ts`）；Claude Code 的后台命令结束时宿主唤起 Agent。

## 四、方案

### 1. 缓冲区的提示

缓冲区里每种话按自己的时机发出（开发者 2026-11-19）：

| 模式 | 什么时候取走 | 给模型的样子 |
|---|---|---|
| 提示 | 下一次对话的模型请求，排在插话与新话前面 | `<system-reminder>`，前面一行来源说明 |
| 插话 `steer` | 下一个边界 | 话本身，非用户的带来源行 |
| 排队 `followup` | 一轮结束时或下一次运行 | 同上，开一轮 |

**发与存**

- 只有会话与宿主能发提示。它不是一种输入：用新的会话级事件 `noticeQueued{id, by, key?, text, wake}`、`noticeRemoved{ids, by, reason}`、`noticeTaken{ids, runId}` 记，不进输入的状态机（就绪与留着、放行、恢复方式都不管它）。旧内核读到这些新事件拒读（同缓冲区提案的升级规则），不会把提示当成用户的话执行。
- 提示一直待发：回到空闲、停止、出错都不改变它。回退、换分支不影响它（会话级）。
- 单条正文至多 64 KiB；一个会话待发的提示合计至多 256 KiB（按编码后的大小，含来源）。超出时发提示失败、码 `notice-budget`，什么都不写；发出方自己留着结果（例如交给 `wait`）。长内容由发出方存成文件，提示里写地址。
- 同一个发出者带同一个 `key` 发的新提示替换还没取走的那条（`noticeRemoved{reason: "replaced"}`）；发出者能撤回自己还没取走的提示，用户能取消任何一条（开发者 2026-11-19）。

**取走**

- 对话运行组一次模型请求时，在压缩之后、组装请求之前，把全部待发的提示按发出的先后取走：同一个写入批里写 `noticeTaken` 与每条一个路径事件 `hostNotice{id, by, text}`，放在这一步的插话与新话前面。只压缩的运行与预览不取（预览按同样的规则只读投影）。
- `hostNotice` 由内核渲染成 `<system-reminder>` 加来源行（格式同 bot 提案的宿主消息，写死在 `runtime.md`），正文里的 `<system-reminder>` 标签转义；Profile 的 `render` 不能把它藏掉或改写。
- **“送达”就是写进了路径**：之后这条路径上的每次请求都带着它（直到被压缩进摘要）。这次请求没发出去（模型不可用、守卫拦下、出错）时它仍在路径上，重试或接着跑时照样带着。用户回退到它之前，它就不在上下文里了，不会再送一次（开发者 2026-11-19：接受，发出方在正文里写可查的地址）。
- 提示不是用户的话：不算授权依据，不解除运行守卫的停止，不让 `wait` 或前台等待以“插话”提前返回。

**唤起与“等你”的门**

- 发提示可以带 `wake: true`。会话空闲、门开着、还有带 `wake` 的待发提示时，开一次运行：没有新话，第一次请求取走待发的提示，`runStarted.by` 是最早那条带 `wake` 的发出者。判定在两处：发提示受理时（会话空闲）；以及每个正常收口的写入批里（还剩带 `wake` 的待发提示就接着开一次）——所以结果恰好在最后一条回复生成时到达，也不会漏掉唤起。一次只开一次运行。
- **门挂在会话上**（开发者 2026-11-19）：会话级事件 `wakeGate{open, cause}`。下列时刻在同一个写入批里关门：用户的停止被受理时（不看这次运行之后怎样收口，收尾工具在宽限期里交卷也一样）；运行因守卫停下（循环保护、费用上限）；进程中断收口。门关着时提示只等着，不唤起。用户自己发话、点继续（`send`、`resume`、`release`、`start` 的发出者是用户）时开门，同一批里待发的提示随那次运行的第一次请求取走。回退、换分支、压缩都不开门。
- 新会话的门是开的。宿主的 `send` 照旧按缓冲区提案开运行，不看这扇门；日程要不要也看它，由 w00043 t10 定。

和 bot 提案的关系：bot 提案定了“宿主消息不另开一种输入类型”，那是对“要求 Agent 去做事”的消息说的，日程照旧发排队或插话。提示只告诉、不要求，不开一轮、不用放行，所以用自己的事件与取走规则，不挤进输入的状态机。

### 2. 清单：自己的任务加提供方的行

`nbook.tasks` 的清单由两部分合成：

- **自己的任务**：照现在 `start()` 登记、由它存状态的（装 Skill 依赖这类），规则全不变：结束的至多 50 件、结束通知、看过、重试、移除、向宿主报“在跑的工作”。
- **提供方的行**：服务端插件经 `tasks.provide(provider)` 把自己登记成提供方（按调用方门面盖章，门面作废时它的行随之消失）。提供方给出“现在有哪些行”与变化通知，收到操作时自己去做；`nbook.tasks` 不存、不改、不移除这些行，不为它们弹通知、不记看过、不向宿主报“在跑的工作”（提供方自己报）。

一行（提供方的行与自己的任务共用显示字段）：

- `id`：提供方自己的 id（Agent 的任务仍是 `job-…`），清单里按“提供方加 id”区分。
- `title`、`message`、`progress`、`state`、`startedAt`、`endedAt`：同现在的任务，长度上限同现在（标题 200、进展 500 个 UTF-16 码元），超出的截掉，不拒收。
- `owner`：`{kind: "app"}`、`{kind: "project", project}` 或 `{kind: "session", session}`；会话的可以带根会话，用来分组。
- `kind` 与 `label`：种类由提供方给，`nbook.tasks` 盖上提供方的插件前缀。
- `form`：`once`（一次性）、`service`（服务：启动中、在跑、已停、出错；可带就绪与地址）、`schedule`（定时：生效、暂停、出错，带下一次触发与上一次结果）。第一批只有 `once`。
- `actions`：`stop`、`open`（以后 `restart`、`pause` 等由形态带来）。`open` 带一个去处 `{kind: "session", session}` 或别的种类，由浏览器端登记的导航处理（Agent 登记 `session` 这一种），导航交回真实结果：打不开时在窗口提示，不报成功。
- 每个提供方至多交 100 行，多出的合成一行“还有 N 件”；整份清单仍在远程合同的 512 KiB 以内。

远程合同 `nbook.tasks/tasks` 升到版本 2：每项加 `source`（`own` 或提供方）、`owner`、`kind`、`label`、`form`、`actions`、`open`；操作 `stop`、`open` 带上 `source` 转给提供方。

### 3. Agent：任务中心作提供方，结果送回会话

- **状态不搬**：后台命令、子代理运行、插件的工具登记的任务仍在 Agent 的任务中心；`wait`、`kill`、`jobs`、远程 `jobs`、`jobTail`、`killJob`、上限 `backgroundJobs`、取件与寿命规则都不变。Agent 仍自己向宿主报“在跑的工作”（含只压缩的运行）。
- **Agent 交给清单的行**：
  - 每件后台任务一行（一直被前台等着的不交；前台等待以超时、提问、插话返回后留下的才交），归属是启动它的会话。子代理任务就代表那次子会话的运行，不再给子会话另交一行。停止即 `kill`（以用户身份，同远程 `killJob`）；打开是子会话（子代理）或启动它的会话（命令）。
  - 每个在跑或在等你处理的根会话一行（开发者 2026-11-19：按会话一行，不是每次运行一行），状态“运行中”或“等你处理”（来自会话表的活动），子代理的任务分在它下面。停止是以用户身份停这个会话当前的运行，保留排队的话（`keepQueue`，同对话里的停止按钮）；打开是这个会话。
  - 结束了、还没取过的任务行一直留到取过；取过之后不再交。
- **结果送回会话**：任务结束时，Agent 在任务中心里同步领取它（`wait` 不再交回被领取的；前台续用一个被领取的任务时交回“结果已经送进对话”），短暂合并（同一会话在 1 秒内结束的合成一次，注入时钟）后发一条提示：
  - 每件一段，命令是 `wait` 交回的同一段，子代理是子代理工具交回的全文（带子会话 id、提问 id 与回答写法）；每段至多 12,000 字符，长的写全文地址；一条至多 8 段、48 KiB，多的留下一条。
  - 根会话带 `wake`；子会话不带（等父 Agent 下次发话时一起带上），不改“一个任务对应一次运行”。
  - 用稳定的 `commandId`。受理成功即取过；确定没写（会话打不开、`notice-budget`、`session-closed`）就退回领取、标“送达失败”，之后只留给 `wait`、不再自动送；结果未知时用同一个 `commandId` 重发一次，仍不确定就记诊断、按送达失败处理。
  - 正被前台调用或某次 `wait` 看着的不另送；每次 `wait` 各自登记看着哪些、返回时各自退回。
- **子代理有话问父 Agent**：后台子代理停在交给父 Agent 的同步提问上时，同样发一条提示（带 `wake`，`key` 是这个提问），写明子会话 id、提问 id、题干与回答的形状；提问在提示取走前被答了，就撤回这条提示。
- **别的插件的工具登记任务**：Agent 给工具的服务里有登记入口，会话与 `invocation` 取自这次调用、只在调用结算前能用；种类盖上贡献这个工具的插件；结束时插件交出给模型的文字（有上限），之后 Agent 不再找它要东西；这个插件的工具贡献被撤回时，它登记的在跑任务记为已中断、句柄封住。t24 的 Workflow 就这样登记，于是 `wait`、送达、清单的行都现成。
- **`shell` 自动转后台**：只对顶层的 `shell`（不在代码里调的、不在子代理会话里）；前台跑过门槛（缺省 60 秒，设置可调，0 为关）就转成后台任务，结果按上面送达；时限照原来的（缺省 300 秒，开发者 2026-11-19）。命令只起一次：门槛到了先异步准备好输出位置，再在一个同步步骤里核对命令还在跑、调用没被中止、名额还有，然后一起移交取消信号与整份输出记录（字节、行数、最后一行、截断、出错）；任一步不成就留在前台照原合同跑完。nb-harness 套件的 `shell` 多一个可选的自动转后台接口，原来的 `async` 接口不变。
- **eval 的提示**：内核因空闲被回收、意外退出时，当场给会话发一条提示（不唤起，`key` 带这个内核的代次）；这个会话的新内核在提示取走前已经起来，就撤回它。下一次 eval 结果的第一行照旧写“内核已重置（原因）”（开发者 2026-11-19：宁可说两遍，回退之后也不漏）。执行中崩溃的，那次 eval 的结果已经说了，不另发提示。
- **子代理卡片**：结果被送达后没有 `wait` 交回的终态，卡片按自己的 `runId` 读子会话的运行结果。同一个运行被回退后接着跑时读到的是最近一次收口，算已知限制。

### 4. 存盘与重启

- 清单与任务中心都只在内存：一次性的工作随进程结束，在跑的记为已中断，同现在。
- 服务与定时要跨重启的是**定义**，由提供方存在自己的数据里（[插件的数据与状态](plugin-data-model.md)），提供方激活时重新交出行；进程本身活不过应用重启。重启后服务怎样、错过的定时怎样补由提供方定（日程的规则在 bot 提案）。
- 会话里待发的提示与门的状态在会话日志里，重启后照旧。

### 5. 界面

- “后台任务”视图按归属分组：当前项目、应用、各会话（子代理归在根会话下）；按形态与种类筛选；组里先在跑的、再结束的。缺省看当前项目、应用与全部会话，能切到全部项目；会话组不按项目过滤（开发者 2026-11-19）。
- 状态栏条目只数在跑的一次性工作；服务与定时不算进“N 个任务”。
- 结束通知、看过与“失败没看过”的提醒只对 `nbook.tasks` 自己的任务，照现在的规则；视图的筛选只影响显示，标“看过”只标此刻显示出来的结束项。
- 对话里：排队区显示还没取走的提示（来源加一行摘要），用户能取消；取走之后是过程里的一行，点开看全文。自动转后台的命令画成后台命令卡片，注明“自动转到后台”。

### 6. 备选方案与取舍

- **状态都搬进 `nbook.tasks`**（第 1 稿）：同一件事两套生命周期——清单的 50 件上限与 Agent 的“留到取过”、`task-` 与 `job-` 两种 id、失败文字校验卡住收口、一次子代理运行登记两行、通知缺省开着——第一轮审查一半的问题在这里。改成提供方，像系统的任务管理器列出各程序的进程，状态归各自的程序。
- **结果作为宿主的插话送进会话**（t22 计划第 1、2 稿）：模型看到的是用户角色的话，停过之后要定谁放行、回退之后会不会被别的送达带走。提示不进输入的状态机，没有这些问题。
- **唤起看当前叶子上最后一次运行**（第 1 稿）：停止之后只要回退一下，下一条结果就能唤起，还会把停止后留下的一起带走；收尾工具在停止后的宽限期里交卷也分不出来。改成会话级的门。
- **由扩展在请求时自己拼提醒**（事件模型的 `reminder()`）：每个发出方都得是装在会话里的扩展，还要自己记“说过没有”。缓冲区的提示由内核保证取走一次，任何插件经会话视图都能发。要随路径重新描述的事实（例如文件被外部改了）以后仍可以用扩展。
- **`nbook.tasks` 自己存服务与定时**：它不知道怎样起服务、怎样算触发；归属拥有它的插件更清楚。

## 五、数据、接口、安全、迁移、发布与回滚影响
