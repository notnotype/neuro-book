# 本机统计、遥测与反馈：按“能不能认出人”分级

## 一、问题

NeuroBook 现在不知道有多少人在用、用的是哪个版本、哪些功能有人用、哪里最常出错；用户也看不到自己的字数、模型用量这些统计。开发者要两类互补的能力（2026-11-23）：给用户自己看的本机统计，与给产品改进用的匿名使用数据与反馈。

约束有三条：

- 用户是小说作者，正文、设定与对话内容不能离开本机。
- [`runtime/diagnostics`](../specs/runtime/diagnostics.md) 规定诊断不联网、不是遥测平台；遥测必须是独立的插件与通道。
- 收集要站得住规则：个人信息保护法对同意、告知与出境的要求，以及面向欧盟分发时的同意规则。调研见 [w00053 的三份报告](../../.agents/works/w00053-telemetry-feedback-stats/README.md)。

## 二、目标与非目标

目标：

1. 一个本机统计插件：记字数、模型用量、功能使用等，给用户看仪表盘（含日历热力图），不联网。
2. 一个遥测插件：默认发一份不带标识的匿名基础信息与在线心跳；用户同意后再发使用统计；每一档有独立开关，用户能看到将要发送的内容。
3. 反馈通道：诊断报告与用户写的反馈，后者每次确认才发；以后加调查问卷。
4. 两份文字：应用里的遥测说明，官方站的隐私政策与服务条款。
5. 服务端落在官方站的统计模块，见 [官方站重写](official-site-rewrite.md)。本稿定协议（收什么、怎么发、服务端怎么处理收到的东西），官方站的提案只写它落在哪。

非目标：

- 不带持久的安装标识，不做跨天跟踪同一个安装的分析。
- 不发逐条带时间的操作事件流。
- 不把匿名数据与账号关联。
- 第一版不把遥测开放给第三方插件（[w00053 t03](../../.agents/works/w00053-telemetry-feedback-stats/tasks/t03-telemetry-for-plugins/README.md)，搁置）。
- 给 OpenRouter 的应用归属请求头不属于遥测，由模型服务一侧做（[w00032 t45](../../.agents/works/w00032-agent-integration/tasks/t45-openrouter-app-attribution/README.md)）。
- “给用户看已登录的设备”要等应用能登录官方站（设备码流程），不在第一版；见官方站提案的非目标。

## 三、当前行为与证据

- 新应用没有任何对外上报。首次启动向导（`FirstRunWizard`）只在桌面壳的窗口里出现、每个状态根只出现一次，第 1 步可以点“跳过”或按 Esc；浏览器与命令行形态没有向导（[`runtime/desktop-shell`](../specs/runtime/desktop-shell.md)）。
- 现有的两个数据源都不能直接当账本用：`projects.stats` 的快照只有总字数与“今天”的基线，没有逐日历史（[`runtime/projects`](../specs/runtime/projects.md)）；模型请求记录可以被用户关掉、缺省只留 14 天，不经新内核会话的调用不记（[`agent/request-trace`](../specs/agent/request-trace.md)）。
- 诊断模块现在只有读有界内存记录的 `query()`，没有给本机其它插件的订阅接口（`packages/nb-runtime/src/diagnostics/`）。
- 桌面版的自动更新向 GitHub Releases 检查（[桌面发行](desktop-distribution.md)），不经过官方站。
- 官方站的生产主机在境外（开发者 2026-11-24）。
- 调研的要点（子代理查一手来源，主会话只核对了个人信息保护法的条文原文）：
  - 国内的认定方法把“以默认选择同意等非明示方式征求同意”列为未经同意收集；国家标准把主动勾选或点击作为明示同意的动作，并把匿名化写成“无法被识别或者关联”；个人信息保护法第十三条没有“正当利益”，第四条把匿名化处理后的信息排除在个人信息之外。
  - 欧盟：依赖同意时预先勾选无效；应用外发设备上的信息落入 ePrivacy 第 5(3) 条，不以是否个人信息为界。
  - Chrome 的更新协议用“距上次上报过了几天”算活跃数，日期以服务端给的为准，不需要稳定标识；Go 工具链的遥测与 Homebrew 都不带标识。
  - Mozilla 的 Glean 是每天一份汇总加单独的事件上报；Syncthing 在报告结构变动时提高版本号并重新询问；Firefox 在政策版本变化时是重新通知，不是重新取得同意。
- 设计审查（Opus、omp 与一位只看方向的 Sonnet，2026-11-24）指出匿名档在用户少时可以靠字段组合把同一个安装几天的上报对上；开发者定开发期原始上报留 7 天（见 4.1）。报告与处理见 [w00037 t03](../../.agents/works/w00037-official-site/tasks/t03-architecture/README.md)。

## 四、方案

### 4.1 分级：看能不能认出人

分界看三件事：能不能把两次上报认成同一个人、里面有没有用户写的内容、有没有绑到账号。

| 档 | 内容 | 怎么开 |
|---|---|---|
| 匿名档 | 每天一份基础信息；在线心跳 | 默认发；告知显示之前不发；设置里有开关 |
| 一级 使用统计 | 当天各项的计数与分档 | 默认关；用户主动打开（桌面版在向导里，其它形态在告知或设置里） |
| 二级 诊断报告 | 崩溃与错误的详情 | “以后自动发送”的开关，默认关；没开时每次崩溃后问一次。收件在第二阶段上线，之前应用里不出现这个开关与询问 |
| 三级 含内容的反馈 | 用户写的文字与他选择附上的内容 | 没有长期开关，每次提交都要看过并确认 |
| 账号档 | 登录官方站后的账号数据 | 注册时主动同意条款；见官方站的隐私政策 |

匿名档靠下面四条：

1. **不带任何持久标识。** 每份上报带一个只用于重发去重的随机编号，下一份换新的。
2. **原始上报只留 7 天。** 服务端保存单份上报，满 7 天按日删除，每晚的备份不含这张表；聚合结果长期保留。开发者 2026-11-24：还在开发、没有大规模上线，要哪些聚合还不清楚，先留 7 天。这 7 天里，同一个安装的几份上报可以靠字段组合互相对上（审查的阻断项），所以开发期的匿名档只能说“不带标识、短期保留”，不能说“无法关联”。大规模上线前改成入库即聚合（收到只给计数加一、不存单份），或者重新评估。
3. **服务端不留 IP。** 见 4.6 的清单。
4. **区分度高的字段收窄。** “安装所在周”只在安装后的 12 周内发，之后记为“12 周以上”。

一级放在要同意的一边，是因为它项目多，属于“软件使用记录”，一份就是一个安装当天的使用画像。

聚合表里取值很少见的格子（例如某个系统只有一个安装）会暴露“有这么一个安装”，不能定位到人；看板对小于 5 的格子显示“少于 5”。

### 4.2 收什么

**匿名档，每天最多一份**：应用版本、发行渠道、运行形态；操作系统及大版本、架构；界面语言；大区（客户端由本机时区换算成七八个取值之一，不发时区本身）；距上次上报过了几天（1 到 28 的精确值，更久记“28 天以上”，首次记“首次”）；安装所在周（12 周内）；“使用统计”的开关是否开着；告知是在哪里看到的（向导、工作台里的告知、设置页）。

**匿名档，在线心跳**：应用版本、运行形态。只在最近 15 分钟内有窗口连着并且有过用户操作时发；每个 15 分钟的时间段至多一次，在段内随机挑一个时刻发；服务端按收到的时间归段，只给那一段的计数加一。它数的是“有人在用的应用实例”，不是人数；应用重启或回应丢失时同一段可能多计一次，看板上叫“15 分钟内收到的心跳数”。

**一级**（每一项都要写出它回答的决策，写不出的不进清单；首批见 4.8 的分阶段）：

1. 功能使用：固定、公开的名单里每一项当天的使用次数分档，以及距上次使用过了几天。
2. 里程碑（这份安装至今是否做过）：建过项目、写满一千字、配过模型、发过第一次 Agent 请求、装过第三方插件。
3. Agent 用量分档：会话数、请求数、失败请求数、工具调用数、输入与输出与缓存 token；模型提供方类别；公开名单内的模型名，其余记“其他”。
4. 稳定性：按“拥有者加错误码”的次数、崩溃次数、升级结果。
5. 耗时分档：启动、打开项目、Agent 首次回应。
6. 规模分档：项目数、最大一部作品的字数、总字数、当天净增字数、累计活跃天数。
7. 第三方插件数量分档、界面主题（内置名单内的名字，其余记“自定义”）。

崩溃与升级失败另在下次启动时立即发一条（只有错误码），只用于发版后尽早看到异常；计数以每天那一份为准，看板不把两者相加。

**二级**：错误码、堆栈（函数名与行号）、去掉用户名的路径、出错前的操作类别序列（不含内容）、应用版本与环境。

**三级**：用户写的文字、类别、用户选择附上的日志片段与截图与对话片段、用户愿意留的联系方式、应用版本与环境。自动附带的内容在提交前可见、可逐项取消。Agent 代写的反馈先落在本机，写的时候不阻塞当前对话、不自动上传；待审阅的草稿有固定的入口可以随时回来审阅或丢弃，右下角的非阻塞通知只是指向它（通知在刷新后会消失）。用户确认的是他看到的那一份内容，确认之后内容不能再变；重复点击或回应丢失后重发不产生两份。

**永不自动收集**：正文、设定、提示词、对话内容、文件名、项目名、密钥、模型服务的地址、硬件指纹。唯一的例外是用户在三级里逐次挑选、逐项预览后附上的内容（例如一段对话或一张截图）；说明里要提醒截图与日志片段里可能带有这些信息。二级不走这个例外：路径只保留到已知的代码位置与类别，认不出的内容丢弃，脱敏失败就不发；它不附带诊断日志全文与模型请求记录。

回答不了的问题：按天的精确留存（只有按周）；操作的先后与漏斗（用里程碑近似）；同一个安装跨天的变化；国家一级的地域；超过 7 天的数据不能再换一种方式重算；一级的结论只代表打开了开关的人。看板上的数是安装数，不是人数：重装算新安装，一人多台各算一个。

### 4.3 上报形态与时间口径

每天一份计数汇总为主，少数事件立即发。不发逐条带时间的事件流：汇总没有时间点、整份可以给用户预览、每个安装每天一个请求、与本机统计直接共用计数；代价是次日才看到、看不到操作的先后、事后不能换一种方式分析。

- **日期以服务端为准。** 服务端在回应里给出它的日期，客户端存下“上次成功上报的服务端日期”，下一份的“距上次几天”由它算。本机时钟被改不影响口径。
- **每个服务端日至多一份。** 客户端在一天里随机挑一个时刻发；待发的那一份连同它的去重编号存在本机，失败按指数退避重试，重启后续用同一个编号；超过 48 小时还没发出去就丢弃。每次发送前按当时的开关与清单版本重新核对这一份，不符就丢弃。
- **不补发。** 几天没开应用，下次只发一份，中间的空缺由“距上次几天”表达；本机的统计不丢，只是不上报。
- **开发、测试与 CI 不发。** 只有正式发行的构建会发，另有一个环境变量可以整体关掉；由测试守住“非发行构建不出网”。
- **写入口无法验证来源。** 没有登录、没有标识，伪造的上报只能靠限流与请求体上限挡；看板的数字是趋势参考，不作精确口径。

### 4.4 三个插件与埋点怎么做

| 插件 | 职责 | 联网 |
|---|---|---|
| `nbook.stats` 本机统计 | 提供记数的服务与指标登记，存本机的按日计数，给用户看仪表盘 | 从不 |
| `nbook.telemetry` 遥测 | 发匿名档与一级；告知、开关、设置页、“查看将要发送的内容” | 是 |
| `nbook.feedback` 反馈 | 诊断报告、用户与 Agent 的反馈、以后的调查问卷 | 是，每次经用户确认或按二级的开关 |

埋点的接口由统计插件提供，不由遥测插件提供：

- **声明**：每个内置插件在自己的合同里声明它的指标：id（以插件 id 开头）、类型、名称与说明。类型有四种：计数、带标签的计数、耗时分布、里程碑。分档不写在这里。
- **记数**：拥有这个行为的插件在发生处调用统计服务记一次。token 与费用由 Agent 插件在每次请求结束处记，不从请求记录派生（请求记录可以关、会过期）。字数由项目插件在“今天”的基线切换时把前一天的净增与当时的总字数交给统计服务；项目没打开的日子没有数据，热力图上是空格。
- **错误码**：给诊断加一个只给本机的记录观察接口，统计插件在一处按“拥有者加错误码”计数，不在每个抛出失败的地方各记一次（那样覆盖不到内核与启动早期的失败）。崩溃与升级结果不靠它：项目进程异常退出由宿主记，升级成功与否由桌面壳在下次启动对账时记；被系统强行结束这类看不到的情况记为缺测。
- **多个实例**：统计服务在服务端实例里，项目子进程与窗口经内核的远程服务调用，攒一小批再发。调用结果不明时不重放，进程崩溃、断线时少计一小批可以接受；一次行为算在它发生的那一天，日期由记数的一方带上。
- **软依赖**：统计服务不可用或写入失败时，业务照常进行，只是缺这一段的数。
- **标签**：带标签的计数只能用声明里列出的取值；上报时不在收集清单里的取值归为“其他”。
- **存储**：按“日期、指标、标签”存每天的值，长期留在本机给用户看；遥测读的是上一个完整日的值，不需要清零。
- **遥测只读**：遥测插件经统计插件的只读接口取数，再按收集清单筛一遍、分档。分档只在收集清单里定义。一个指标要进上报，得同时满足“插件声明了它”与“收集清单里有它”；应用侧有一条测试核对清单里的每个指标都能在内置插件的声明里找到、类型一致。第三方插件可以往统计插件记数、给用户自己看，但进不了收集清单。
- **依赖方向**：内置插件依赖统计插件的合同；遥测与反馈依赖统计插件；没有插件依赖遥测。“统计插件不联网”的定义是：它的导入图里没有网络模块与 `fetch` 这类全局，经内核远程服务调用不算联网；由测试检查导入图，运行期不拦截，列为已知限制。

匿名档的字段来自运行时信息，不经统计插件。

### 4.5 告知、开关与清单版本

- **告知与向导分开。** 遥测插件自己有一条用户层记录“告知已显示（清单版本 N）”。桌面版在首次启动向导的一页里显示告知与“使用统计”的开关，点了“完成”才写设置；向导被跳过时，告知改在第一次打开工作台时以非模态的方式显示。浏览器形态、以及加入这一页之前就走过向导的老用户，同样在第一次打开工作台时显示。没有界面的命令行运行，在告知显示过之前不发。
- **开关的层次。** 匿名档是总开关：关掉后心跳与一级都不发，设置页把一级显示为不可用并说明原因。在线心跳在匿名档之下另有一个开关。一级开着时，它的内容与匿名档在同一份请求里发出。看板上的“同意率”只含开着匿名档的安装。
- **关闭后**不再发送，本机的统计照常记、照常给用户看。打开使用统计之前记下的计数不上报。
- **告知之后留一次机会。** 告知显示的那一次运行不发，从下一次启动起才发第一份，让用户来得及先关掉。
- **收集清单按档分版本**（匿名档一个、一级一个），每次变更标明种类：
  - 只加取值或改说明（例如功能名单加一项、错误码表加一码）：不停发，记进变更记录；
  - 同一档新增字段、或改分档边界：重新告知，告知显示之前只停那一档；分档表带版本，看板按版本分段显示；
  - 一级新增类别（4.2 一级的七类是封闭的列表）：重新取得同意。
- 暂停与否只看客户端自己的清单版本，与服务端的版本无关；服务端对不认识的字段丢弃并计数。指标的定义或分档变了算一个新的指标版本：服务端只聚合它登记过的版本，聚合表带版本；缺失、被拒与没同意的指标不当作 0。

### 4.6 服务端

- 写入口三个，都不带登录：每日上报、在线心跳、立即事件；它们不读取也不记录 Cookie 与登录凭据。诊断报告、反馈与问卷的收件在第二阶段。
- 原始上报按服务端日入库，靠去重编号拒掉重发；满 7 天按日删除，不进备份。聚合由定时任务从原始上报算出，7 天之内可以改聚合的办法重算，聚合结果长期保留。
- “不留 IP”是一张要逐项核对的清单：写入口所在的反向代理配置不记访问日志；限流拒绝、请求体超限这类错误日志不带客户端地址，或单独成文件并在几天内轮转；进程不把地址与转发头写进日志；容器日志设轮转；限流的内存表按时间窗淘汰。遥测说明里如实写“防滥用的日志会短期含 IP，保留若干天”，不写成绝对的“不存”。
- 收集清单是合同包里的 schema，每个字段带中英文说明与分档表；服务端校验、应用里的说明、官网的“我们收集什么”页面都由它生成。

### 4.7 条款

1. **应用里的遥测说明**：一句话说明目的与能关；分档表；“我们明确不收集”单独一节；每一档怎么关、关了有什么代价；服务端怎么处理（原始上报留 7 天、聚合长期保留）与防滥用日志；清单版本与变更怎么通知；发给第三方的信息（用户自己配置的模型服务会收到请求内容；OpenRouter 的应用归属请求头）；联系方式。
2. **官方站的隐私政策**：处理者与联系方式；账号数据逐项列出用途与保存期限；Google 与 GitHub 登录时取哪些数据；会话与 Cookie；怎样查看、更正、删除与注销；变更怎么通知；**数据存放在境外**一节。
3. **主动反馈与问卷一节**：不公开、只用于改进产品；附带了什么；保留多久。
4. **服务条款**：账号规则、禁止的行为、服务可用性与免责；不面向不满十四周岁的未成年人。

主机在境外的后果：账号档的邮箱等是个人信息，适用个人信息保护法第三十八、三十九条，注册时要单独告知并取得单独同意，另需满足出境条件；出境条件对小规模是否有豁免没有核实。匿名档与一级不带标识，本稿据此当作不属于个人信息出境，这只是主会话的理解；开发期原始上报留 7 天，这个理解更弱。二级与三级的收件同样在境外，第二阶段上线前另行判断。

条款由主会话起草中英两版，不是法律意见。有两处没有经懂的人确认：“匿名档算不算匿名化”这个默认发送的前提，与境外存放。开发者 2026-11-24 定先不确认，作为已知的未核实风险留着。

### 4.8 分阶段

第一阶段只做有人等着用的部分：

1. 匿名档的每日上报与在线心跳，告知与开关。它回答：有多少活跃安装、新增与按周留存、版本覆盖、该支持哪些系统与语言、同时有多少应用在用。
2. 本机统计的底层数据与给用户看的字数、模型用量、日历热力图。
3. 统计插件的记数服务与指标声明只做到这两项用得着的形态。

一级的指标在第一阶段只放“稳定性”一类（错误码计数、崩溃、升级结果，回答“这个版本能不能继续推”）。其余各类等有具体的决策要回答时逐类加入，每加一类按 4.5 重新取得同意。二级、三级与问卷在其后。

### 4.9 备选与取舍

- **带随机安装标识**（讨论稿第一版）：能做按安装的留存与跨天分析；国家标准的示例把唯一设备识别码与软件使用记录列为个人信息，默认发就站不住。放弃。
- **保存单份上报 90 天**（本稿第一稿）与**入库即聚合、完全不存**（审查后主会话的改法）：前者留得久，字段组合在用户少时等于一个跨天的标识；后者最稳，但要事先定好全部聚合。开发者取中间：开发期留 7 天，大规模上线前再定。
- **全部要用户选择加入**（Go 工具链的做法）与**完全不上报**（Obsidian 的做法，规模只看下载数）：对隐私最稳，代价是几乎拿不到数或完全没有。开发者定了“不敏感、不需要持续上报的可以默认收”（2026-11-24），本稿用不带标识加入库即聚合来支撑这个默认。
- **使用统计默认勾选**（开发者 2026-11-23 的决定）：参与率高；国内与欧盟的规则都不认预选的同意。开发者 2026-11-24 改为默认不勾选。
- **逐条事件流**：见 4.3。
- **由遥测插件提供埋点接口**：内置插件就会依赖联网的那个插件，关掉遥测也关掉了用户自己的统计，“不联网”的承诺也没处落。
- **部署 Umami 或接 Grafana 这类现成工具**：见官方站重写提案的备选。

## 五、数据、接口、安全、迁移、发布与回滚影响

- **数据**：本机新增按日计数的存储；服务端新增原始上报表（留 7 天）、聚合表与心跳的计数表。
- **接口**：新增统计插件的服务与指标声明、遥测的三个写入口。收集清单是公开合同，按档带版本。
- **安全与隐私**：见 4.1 的四条与 4.6 的清单。
- **发布**：遥测说明要先于第一次上报上线。
- **回滚**：客户端的开关关掉即停；服务端可以整表清空原始上报与聚合。

## 六、对 Spec 的预期改动

- 新增本机统计的 Spec：指标的声明与类型、记数与两个提供方的交数时机、存储、仪表盘与贡献点、“不联网”的定义与守卫。
- 新增遥测的 Spec：分级、每一档的字段与分档表、时间口径与重试、告知记录与各形态的告知时机、开关的层次与组合表、清单按档的版本与三种变更、“查看将要发送的内容”、非发行构建不发。
- 新增反馈的 Spec：诊断报告的内容与脱敏、反馈的审阅与确认、Agent 代写反馈不阻塞对话。
- [`runtime/diagnostics`](../specs/runtime/diagnostics.md)：加一个只给本机的记录观察接口，供统计插件按错误码计数；诊断自己仍不联网。
- 首次启动向导的组件文档加一页。

## 七、待定项

1. **大规模上线前原始上报怎么留**：推荐改成入库即聚合；届时要哪些聚合应已清楚。
2. **在线心跳要回答什么决策**：审查者指出它是匿名档里联网最频繁的一项，而“同时有多少应用在用”支持哪个决策没有记录。开发者 2026-11-24 明确要“同时在线人数”，本稿照做，心跳有独立开关。
3. **面向欧盟分发时匿名档是否默认关**：时区不等于法域；推荐到时按发行渠道或告知时让用户选所在地区来定。
4. **调查问卷的范围与时机**：推荐在统计与遥测做完后与主动反馈一起做（[w00053 t04](../../.agents/works/w00053-telemetry-feedback-stats/tasks/t04-surveys/README.md)）。
5. **法律审阅**：“匿名档算不算匿名化”与“数据存放在境外”两处，开发者 2026-11-24 定先不确认；面向公众大规模上线前再提。
