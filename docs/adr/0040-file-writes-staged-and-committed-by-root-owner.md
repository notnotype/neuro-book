# ADR 0040：文件服务不劫持读，写只有一个入口：写入方暂存、拥有根的进程在锁里提交并记账；外部改动由监视与对账发现，History 经文件服务定义的记账槽接入

- 决策者：开发者

## 背景

nbook.files 的读写接口照“浏览器经 RPC 编辑一个文档”设计：一次交整份文本、约 960 KiB 上限、不能读写字节。服务端的使用方（作品统计、Agent 的文件工具、以后的图生文与导入导出插件）都用不上，作品统计已经自己绕开。shell、外部编辑器、`git checkout` 直接写磁盘，“所有访问都经文件服务”本来就做不到；但审查收件箱、每轮改动文件、旧版本与恢复都要知道谁改了什么、改成什么。

两轮深入审查与三种写入方案的评估（t12 的 `evidences/`）比较过：写入方自己写盘后交账本（先记账或先改名各有一种），照 git 由监视发现、账本提交、写入方只认领，以及写入方暂存、拥有根的进程提交。前两种在中间夹着外部改动或崩溃时会记错改前内容或留下假版本；照 git 的一种在攒批窗口里会把两次写记成一次、把写到一半的文件记成版本。实测本机 RPC p99 约 2 ms，暂存加改名比就地写多约 1.5 ms。

## 决策

1. **读不经文件服务**：使用方按方案的读授权拿到本机路径或字节与基线，自己读；读不记账。
2. **写只有一个入口**：写入方把新内容写进文件服务交出的暂存文件，拥有根的进程在根的操作锁里核对期望、读出改前内容（中间有外部改动先补记外部）、原子替换、记账、以真实来源发出变更事件。一个根的全部写入共用一把锁。暂存与提交以同机共享文件系统为前提。
3. **文件监视只检测变化**，回声按 inode、修改时间与大小认；监视在项目实例里常驻，溢出、出错、启动与定时触发对账兜底。外部改动在文件安静后读一次、记为外部；Agent 的 `shell` 执行期间的改动归给该会话、标推断。
4. **History 是记账者，不是依赖**：nbook.files 定义记账槽，History 贡献记账者；槽空、撤回、超时或出错时写入照常，只写诊断。恢复与还原由 History 生成内容、经写入入口提交。
5. **账本在 nb-history 上继续做**，不复用 git：项目的账本 `.nbook/history.sqlite` 是作品数据、随书走、只支持单设备。

## 备选方案

- **给服务端补字节、流式、分页接口，维持读写都经文件服务**：劫持不了 shell 与外部工具，每类需求补一个接口。
- **写入方自己写盘，再交账本**：见背景。
- **照 git，监视发现、账本提交**：见背景。
- **History 作为服务被文件服务依赖**：两者互相依赖成环，History 的故障会拖垮文件写入。
- **隐藏 git 仓库、isomorphic-git、libgit2 绑定**：依赖系统 git 或成熟度没有一手证据，操作者、收件箱、会话游标仍要另建一套。

## 后果

- 记账只对守约的写入方成立，不是安全边界；往 `readPath` 交回的路径里直接写，只能记为外部。
- 项目子进程承担一本书的全部写入、监视与记账，常驻监视的开销要在大书上实测。
- 第 1 阶段交付写入接口后、接入 History 之前，改动不记账。
- nb-history 的 `revert`、`restore` 直接写盘的路径要去掉。
- 项目子进程移到别的机器时，暂存要换成分块上传。
