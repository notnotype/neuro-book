# ADR 0039：世界引擎的真相源是按大小分段的只追加修订日志，状态在内存里重放；条目不做成文件，第一版不开放经文件改设定

- 日期：2026-11-02
- 决策者：开发者
- 关联工作：[w00039 t09](../../.agents/works/w00039-novel-writing-plugins/tasks/t09-storage/README.md)
- 相关文档：[存储方案](../../.agents/works/w00039-novel-writing-plugins/tasks/t09-storage/storage-draft.md)（取舍、目录与测量的完整说明）；[作者视角的世界引擎内核（第一版）](../proposals/world-engine-kernel.md)；[ADR 0037](0037-world-engine-story-change-log.md)
- 部分取代：[ADR 0037](0037-world-engine-story-change-log.md) 决策 5 里的“包括直接改文件后被读进来的内容”（第一版没有这条写入路径）；0037 的其余决定不变

## 背景

ADR 0037 定了模型：世界里只存条目、剧情变更（含计划）、核对点、未决问题、正文建议、修订六种对象，每一次写入都是一次带版本、可还原的修订；存储留给 t09。t16 原型把修订定成“新建存整份、修改只存变了的字段、删除存整份旧值”，于是全部修订按顺序重放一遍就能得到其余五种对象的当前值，修订本身已经是一份完整的事件日志。

规模按每章 15 条情节估（比 t16 原型多一倍），在项目文件底座定的参考机器上实测（t09 证据 `log-scale.txt`、`engine-scale.txt`、`disk-growth.txt`）：

- 百万字的日志约 6.3 MB，三百万字约 19 MB；读入、解析、重放分别是 25 到 40 毫秒、65 到 120 毫秒。全部对象连同修订在内存里约 14 MB、42 MB。
- 原型每次从初值折叠整本书：百万字约 0.1 秒，三百万字约 0.3 秒；发布一次记账要折叠两次。
- 单个只追加的文件放进 Git、每记完一章提交一次：百万字 330 次后 `.git` 是 274 MB，三百万字 1000 次是 2.5 GB（手动 `git gc` 后 1.4 MB、5.8 MB，但默认要攒到约 6700 个零散对象才自动打包）。按 256 KiB 分段后是 13 MB、41 MB。

## 决策

1. **唯一真相源是一份只追加的修订日志**：`.nbook/world/log/` 下的 JSONL 文件，一行一次修订。当前一段超过 256 KiB 就开新的一段，文件名是这一段第一个版本号，旧段不再写。其余五种对象的当前值不另存。
2. **打开作品时在项目进程里重放**，折叠、查询、关键词检索都在内存里做，不用数据库。内存里按章留折叠的中间结果（每章只留这一章改到的条目），读一章、在最新一章发布都不从头折叠；这些是派生数据，不写到磁盘。语义档的归纳缓存与以后的嵌入放 `.nbook/cache/`，可以删除。
3. **写入**：项目子进程是唯一写者。一次修订写成一行并 fsync；追加时持跨进程锁并核对文件长度，防两个实例同开一部作品；版本号跨段连续。打开时最后一段末行写了一半，就另存、截掉、进诊断；中间的行坏了，只读打开到坏行之前。Git 合并两个分支出现重号时报错，第一版不支持分支合并。
4. **条目不做成文件**：条目树是条目上的字段，由世界引擎的设定树显示；`lorebook.content/` 不再是条目的家。给 Agent 读的只读文件视图（按某个位置渲染、派生、可删除）做不做，由 t09 的检索实验定。
5. **第一版不开放经文件改设定**：Agent 改设定只经 `write` 工具；正文、细纲、手记仍是文件，Agent 照样用文件工具读写。
6. **日志不进 nb-history**：`.nbook/` 是控制目录，日志由世界引擎直接写，与 `storage.sqlite` 同属不经文件服务的应用数据；日志本身就是改动记录。正文、细纲、手记的历史归 nb-history。章序的真相在活页夹，章序变了在日志里记一次“章序调整”修订。
7. **系列作品第一版不做**，一部作品一个项目。

## 备选方案

- **同样的日志放进 SQLite 的一张表**：事务自带，一样快；但二进制文件在 Git 里只能看到“变了”，每次提交同样存一份整库；SQLite 放在同步盘里有损坏的已知风险（官方文档 How To Corrupt An SQLite Database File）。
- **六种对象各存成文件，修订另存**：一次修订要同时改几个文件，得自己做预写日志；外部一改就绕过修订。
- **六种对象各一张表**（旧 WorldEngine 的做法）：表结构跟着模型改，模型还在变。
- **日志不分段**：Git 与不做块级增量的同步工具每次都要存或传整个文件，见背景里的数。
- **条目做成文件，Agent 经文件改、程序读回来**（提案第 5 节“并发”留的路）：要导出、旁车记录、块标记、监视、按对象判冲突，是同一份数据的第二条写入路径；条目的样子随位置变，一个文件只能放一个位置；项目文件底座也规定数据在库里的类型只经结构化工具写，“不接受改文本后解析回写”。`write` 的“把 A 换成 B”和改文件一样省 token。
- **把当前状态的快照存到磁盘**：打开时重放加一次整本折叠在三百万字约半秒，没有必要；慢在每次操作都从头折叠，内存里的中间结果就能解决。

## 后果

- 删掉的条目与变更仍留在日志里（还原要用）；要彻底清除（例如分享作品前去掉草稿设定），以后做一个重写日志的工具。
- 在作品目录里直接运行的外部 Agent 看不到设定，除非以后做文件视图或只读导出。
- 条目的标签页全部依赖编辑器的“带参数的虚拟文档”（提案“影响”已列为要先做）。
- 作者用 Git 管作品时，`world/` 要提交；`history.sqlite`、`storage.sqlite`、`cache/`、`locks/` 是本机的。不替作者写 `.gitignore`，写进用户文档。
- t27 的 Spec 写行格式、分段、写一半与坏行、锁与版本核对，以及“按章留中间结果”的性能要求（读任意一章的一个条目、在最新一章发布一次的耗时上限）。
