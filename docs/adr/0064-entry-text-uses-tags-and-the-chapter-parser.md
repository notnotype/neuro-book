# ADR 0064：条目的主文字改用标签写法，与章节共用 marked；给 Agent 的值只给看

- 日期：2026-11-26
- 决策者：开发者
- 部分取代：[ADR 0038](0038-world-engine-entry-text-is-whitelisted-mdx.md) 的决策 1（主文字用 MDX、不复用项目的 Markdown 方言）、决策 3（给 Agent 的可改注记 `{地址 = 值}` 与回写协议），以及决策 2 里的“标签只有内置的几个”（插件可以登记标签）；决策 2 的其余部分（只解释白名单、不执行代码、写入时检查）不变。决策 4（作者怎么编辑）不在本 ADR，由 w00055 的富文本编辑器另行决定
- 关联工作：[w00055](../../.agents/works/w00055-entry-rich-text/README.md)（决定表 2026-11-23 到 11-26，[t01 的评测与演示](../../.agents/works/w00055-entry-rich-text/tasks/t01-demos/README.md)，[t02 的实施计划](../../.agents/works/w00055-entry-rich-text/tasks/t02-kernel-tags/plan.md)）
- 相关文档：[`canon/rendering.md`](../specs/canon/rendering.md)、[11-24 的讨论](../../.agents/works/w00039-novel-writing-plugins/research/2026-11-24-entry-text-direction.md)

## 背景

ADR 0038 选了 MDX 的表达力，作者怎么编辑先不考虑。之后作者要一个完整的富文本编辑器来写条目，编辑器只能建在章节的解析器（nb-markdown，marked）上；内核却用 MDX 的解析器把关。两套解析器对同一段文字读法不同（`1<2`、`<br>`、正文里的花括号、行首缩进四格），w00039 t39 的设计审查估出要补的东西是原计划的两到三倍，那次退回了源文字编辑。MDX 的表达力来自执行 JSX，而条目的文字不执行（0038 决策 2），白名单里留下的只是取值、条件与两个标签，用标签同样写得出。

给 Agent 的可改注记 `{地址 = 值}` 让 Agent 能在文字里改值。t01 的评测（198 次，两种模型）里，三种做法的成功率分不出高低，跟写法有关的错误只出在“值写进标签、可以就地改”的那一组（漏掉一个式子、改坏格式），“带值、只给看”的一组没有。回写协议在产品里也没有调用方：Agent 改文字走的是写入工具的整块写与查找替换。

## 决策

1. **主文字是带标签的 Markdown，与章节共用 marked 与同一份 Markdown 配置**（开发者 2026-11-23、11-26）。取值、计算、条件写成标签：`<V of="…" />`、`<V expr="…" />`、`<If test="…">…<Else />…</If>`；条目引用与图片照旧是 `<Ref>`、`<Image>`；插件可以登记展示用的标签。不再有花括号表达式。式子（`expr`、`test`）仍只按白名单解释，加上四则运算与几个确定的函数（开发者 11-26 选的“计算值”一档）。
2. **内核与编辑器用同一份写法代码**：Markdown 的配置由 nb-markdown 出一个不带编辑器的纯入口，条目标签的读法放在 nb-canon 的纯子路径，后端与浏览器都引它。标签先在原文上认出、换成等长的占位再交给 marked，位置与落点由这一步给出，不从 marked 的词法单元回推。
3. **给 Agent 的渲染带值、只给看**（开发者 11-26，t01 第 2 轮）：值写在标签中间、用 JSON，Agent 在文字里改值不生效，交回时程序去掉值；改值用写入工具。0038 的可改注记与回写协议去掉。
4. **给作者的渲染是源文加值表**：前端用同一份写法读源文、按标签的顺序取值，不再由内核给语法树。

## 备选方案

- **保留 MDX、编辑器侧做双向对照**（t39 设计审查的路线）：要改已发布的 nb-markdown 的转义、给条目关掉缩进代码与 frontmatter、编辑器与内核的词法逐项对照，量大且两边会慢慢分叉。不采用。
- **marked 的配置在 nb-canon 里另留一份**：nb-markdown 已发布、不能依赖私有的 nb-canon，两份配置要手工同步。不采用。
- **把 marked 的配置拆成一个新发布的小包**：没有 Tiptap 的依赖闭包，但多一个要发布的包（nb-story 的发布清单跟着改）。nb-canon 要发布、或依赖闭包里的 Tiptap 成了问题时再换。
- **值不进原文、Agent 只经工具改值**（t01 评测的乙组）：成功率与“带值只给看”分不出高低，但 Agent 读文字时看不到值，要另调工具。开发者选了带值只给看。
- **按 marked 词法单元的 `raw` 回搜位置**：列表与引用去了前缀、表格按 `|` 切开标签时会定位错或静默丢内容（t02 独立设计的实验）。不采用。

## 后果

- 条目与章节的 Markdown 读法一致，富文本编辑器可以建在 nb-markdown 上；读法变化（`a < b` 成了文字、缩进四格成了代码块、单个 `~` 不再是删除线等）写进 Spec，样本与测试数据换写法。
- nb-canon 依赖 nb-markdown 的纯入口：依赖闭包带 Tiptap 与 vue，打包只进纯子路径，由边界测试守住。
- 浏览器能引条目的写法代码（marked、acorn 都是 ESM），nb-canon 不再只有 `./schema` 能进浏览器。
- 取值比花括号啰嗦；作者主要经富文本编辑器插入，Agent 照工具说明里的写法写。
- 已存的花括号写法在换写法以后是出错的块；开发者确认没有要迁移的真实作品（11-26），只改样本与测试。
