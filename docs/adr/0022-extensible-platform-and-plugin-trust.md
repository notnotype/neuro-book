# ADR 0022：可扩展应用平台与第一版插件信任模型

- 状态：Accepted
- 日期：2026-09-28
- 决策者：开发者（需求访谈逐条确认）
- 关联工作：[w00017 t26](../../.agents/works/w00017-application-runtime-architecture/tasks/t26-platform-architecture-redesign/README.md)
- 相关文档：[可扩展应用平台设计](../proposals/extensible-application-platform.md)（`accepted`，本 ADR 的机制展开）、[应用运行时总提案](../../packages/neuro-book-legacy/docs/proposals/application-runtime-and-plugins.md)（其“第三方代码加载”非目标由本 ADR 取代）
- 调研证据：[Cordis 插件框架调研](../research/cordis-plugin-kernel.md)、[运行时模块卸载能力](../research/runtime-module-unloading.md)（均为非规范资料，仅作证据来源）

## 背景

w00017 前两片已实现生命周期、服务装配、插件激活和运行实例四项内核合同，以及诊断、平台文件、SQLite 三个服务插件。但在产品里，内核仍寄居在 Nitro 中：运行实例由一个 Nitro 中间件模块在加载时经 `productRuntimeReady()` 建立并挂在全局对象上，启动失败靠抛出未捕获异常终止进程；进程信号与关闭顺序由旧的 `product-shutdown.ts` 手写清单决定。插件机制只服务内置功能，原提案把第三方代码加载列为非目标。

2026-09-28 开发者重新做了需求分析：NeuroBook 的形态接近 VS Code，目标是让社区开发者能写出同时扩展模型、Agent、编辑器、视图和 Project 数据的插件。旧的非目标和“内核寄居框架”的做法都不再符合这个目标。

## 决策

### 1. 开放第三方可执行插件

NeuroBook 以社区第三方插件为最终目标，公开 API、安装和隔离都按这个目标设计。最终验收样例是文生图插件：它从本地文件夹安装，不修改 NeuroBook 源码、不重新构建，安装后不需要重启就能在编辑器右键菜单、Agent 工具、侧边视图和 Project 资产写入四处生效。

插件的安装、启用、禁用、卸载与升级都即时生效（2026-09-29 开发者修订，原为重启生效）。用户可见的插件状态只有已启用、已禁用、未安装三种；启动必需的内置插件不能禁用。热插拔的承诺分三档（2026-09-30 开发者确认）：即时生效并撤回插件的全部可见效果与它交出的全部引用，是承诺；回收插件代码与内存，是尽力而为且在开发模式可验证；无论插件如何实现都恢复到启用前，不做，重启应用即完全干净。

第一版不做插件市场、在线分发、签名、权限沙箱、独立扩展宿主进程。

### 2. 内核拥有进程，领域能力都是内置插件

宿主适配器创建运行实例，内核只提供生命周期、服务、插件登记与激活等机制。HTTP 服务（Nitro）、workbench、编辑器、Agent、模型 Provider、Project 与 Files 都是内置插件，与第三方插件使用同一套登记、激活和贡献机制，区别只在信任级别和代码来源。

插件之间只通过三种方式协作：拥有者插件定义的贡献点、插件激活后导出的 API、按 id 调用的命令。插件不在运行时 import 其它插件的模块；类型经提供方的类型包在编译期共享。跨插件的引用只经内核建立并记账，这是运行期干净卸载的前提。

插件是安装、启用、禁用与升级的单位；插件内的入口是运行与依赖的单位，每个入口有自己的运行位置（服务端、浏览器，以后可加终端界面等），各自激活、各自受阻。依赖指向归某个插件所有的服务，而不是整个插件，只在同一运行位置内解析；跨位置只能依赖本插件的通道（2026-09-30 开发者确认）。依赖写进清单，使登记、禁用与升级之前就能判断影响。

### 3. 第一版完全信任，但 API 按远程调用设计

第一版插件与宿主运行在同一进程的同一线程（服务端）或同一页面（浏览器），不设权限沙箱。2026-09-30 评估过“每个第三方插件一个 worker 线程”：本机实测内存开销很小，但需要为全部 API 建跨线程代理层，工程量与收益不相称，不采用。安装时必须明确告知：安装插件等于授予它访问全部作品、服务器与本机资源的能力。

两条约束从第一版起生效：

- 公开 API 全部异步，参数与结果可序列化，插件只能经宿主注入的 API 对象访问宿主。以后把插件移入独立进程或 iframe 时只替换传输层，已发布插件不需要重写。
- API Key 等密钥由模型 Provider 插件保管。插件只拿到按能力调用模型的句柄，拿不到密钥本身。

### 4. 服务端部署按单一所有者处理

服务端（含容器）部署由部署者决定安装哪些插件，不支持多个用户各自安装插件。

### 5. 质量优先的推进顺序

先重排地基并建立必要的内置插件，再以主页面左侧文件资源管理器做第一个竖切验证，然后逐步补齐文生图所需的内置插件与扩展点，最后用文生图插件验收。演示时间不作为约束。

## 备选方案

- **竖切优先**：只为文生图在现有模块上开出扩展点，内核继续寄居 Nitro。演示最快，但新旧两套关闭机制会长期并存，内置功能也不走第三方同一套机制。开发者选择先重排地基。
- **第一版即引入隔离与权限**：扩展宿主进程、按声明授权文件和网络、第三方界面只允许 iframe。安全性更好，但第一版复杂度过高。改为完全信任加远程形态 API，给以后的隔离留出路径。
- **只做内置插件、不开放第三方**：不满足平台目标。

## 后果

- 迁移面大：旧关闭清单中的七项资源、浏览器端由主页面创建运行时的接线、以及随功能迁移的 Nitro 路由，都要逐步转为插件所有。
- 第一版用户装插件就授予了全部权限，需要安装提示和禁用第三方插件启动的安全模式作为兜底。
- 运行期禁用要求每个贡献点的拥有者都能在应用运行中撤回贡献，并妥善结束在途调用；插件绕过注入 API 自行创建的资源不受内核管理，禁用后可能残留到重启。
- 同线程运行时，插件在主线程上的同步 CPU 计算无法被打断，会使整个服务端失去响应。对策是 CPU 工作必须交给 SDK 的 worker 池；阶段 3 起由主线程卡死看门狗结束进程、重启后提示禁用或进入安全模式，违规插件仍能让服务端卡住到看门狗阈值（10 秒，须小于 Session Store 租约心跳间隔）。
- 远程形态约束让公开 API 比同进程直接调用多一层包装；内置插件之间的内部服务不受此约束。
- 以下情况出现时重新评估信任模型：需要安装不受信任的插件、服务端需要多用户各自装插件、或插件故障已实际拖垮宿主。届时先考虑共享插件宿主 worker，再考虑扩展宿主进程与权限模型，公开 API 的形态不变。
