# ADR 0025：服务键按服务 id 识别，插件之间可引用对方的合同模块

- 日期：2026-10-08
- 决策者：开发者
- 关联工作：[w00017](../../.agents/works/w00017-application-runtime-architecture/README.md)
- 相关文档：[`runtime.services`](../specs/runtime/services.md)、[`runtime.plugin-manifest`](../specs/runtime/plugin-manifest.md)、[ADR 0022](0022-extensible-platform-and-plugin-trust.md)

## 背景

内核第一片把服务键设计成凭据：`defineServiceKey(name)` 每次返回新对象，同名不等价，装配只认应用清单 `keys` 里登记过的键对象。它防的是插件凭猜名字解析到没交给它的服务。

为了配合这一点，插件之间只能 `import type`，依赖别的插件的服务时由宿主把键对象交给插件工厂。结果是工厂参数各不相同：有的收宿主配置，有的收别的插件的服务键，有的什么都不收；宿主要为每个插件逐个接线。开发者看示例插件时指出这一点（2026-10-08）。

这层保护现在已经没有作用：

- ADR 0022 定了第一版完全信任插件，命名空间防误用、不防恶意；
- 按插件隔离数据由按调用方门面与内核填写的调用方身份负责，与键是不是对象无关；
- 应用包的 `keys` 是从各插件自己的声明里收集出来的，没有挡住任何东西；
- 规划中的插件清单本来就以服务 id 字符串写依赖与提供项。

## 决策

1. 服务键按服务 id 识别：同一个 id 定义两次是同一个键。应用清单与服务装配不再有受信键清单，登记时也不再有“未登记的键”；依赖一个没有任何入口或宿主能力提供的 id，按 `missing-service` 受阻。
2. 服务 id 只在提供方插件的 `shared/contracts.ts` 定义一次。别的插件在运行时引用这个文件（服务键、远程合同、贡献点 id、schema），不引用对方的其它模块。
3. 插件入口的工厂只收宿主给的配置（运行位置、路径、开关、宿主拥有的对象）；对别的插件的依赖一律写在 `dependencies` 里。

## 后果

- 工厂签名统一，宿主装配只按清单取工厂、传配置；新插件不用改宿主接线。
- 同一 id 在两处定义成不同类型时，编译器查不出来。由第 2 条的约定与边界测试（跨插件的运行时导入只能指向对方的 `shared/contracts.ts`）约束。
- 以后接入第三方插件、各自打包时，同一 id 的键自然相等，不需要共享同一份键对象。
- 不改变的：唯一提供者、重复提供隔离、调用方身份与委托的签发记录（仍按身份对象登记，伪造的身份对象查不到）。
