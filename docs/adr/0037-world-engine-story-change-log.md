# ADR 0037：作者视角的世界引擎以剧情变更日志与修订为真相，条目由主 MDX 加按 Component 分块的状态组成

- 日期：2026-11-02
- 决策者：开发者
- 关联工作：[w00039 t02](../../.agents/works/w00039-novel-writing-plugins/tasks/t02-story-model/README.md)
- 相关文档：[作者视角的世界引擎内核（第一版）](../proposals/world-engine-kernel.md)（行为细节、例子与取舍都在提案里）

## 背景

旧应用的设定靠文件管理，旧 WorldEngine 只管世界状态，剧情在另一套数据里；补写过去时相对操作会断（`broken-relative`）。作者需要在任意一章看到每个设定当时的样子，每处变化都有出处；记账要交给 Agent，还要能核对、能撤销。2026-10-31 开发者决定先从作者视角重新设计，暂不与读者视角的 nb-story 合并。提案经三轮深入设计审查（共 13 路审查者，含作者与 Agent 的体验环节，第二轮的 Agent 体验在可执行夹具上做）后接受。

## 决策

1. **一条剧情变更日志统管设定、剧情与情节**（开发者 2026-11-01）。只有一种记录：故事里发生的一件事，带描述、生效位置、讲述（出处）、涉及的条目与补丁。计划是还没写的剧情变更；经历、剧情表、伏笔都从这条日志得到。
2. **条目由主 MDX 加随剧情变化的状态组成**（开发者 2026-11-01）。带数据的 Component 在状态里占一个命名空间，数据不存在 Component 里；Component 类型经插件平台的贡献点登记，内置与第三方同一套（ADR 0027）。
3. **某个位置上的条目 = 初值 + 生效位置在此之前的已写、生效的变更，按位置依次打补丁**。第一版的位置精确到章，另加前史（开发者 2026-11-01）；细的故事时间与世界线在 t04。
4. **随剧情变化的文字整段替换，不做文本 diff 与三方合并**（开发者 2026-11-02）。作者在看到的样子上就地改，默认算改设定，写回给出这个值的那条记录。
5. **每一次写入都是一次修订**（开发者 2026-11-02）：作者的保存、Agent 的写入（包括直接改文件后被读进来的内容）、一章的记账都走同一条发布通道，带读取时的版本，冲突时报冲突、不静默覆盖；修订存改前与改后的值，可以还原。Agent 可以改作者的东西（开发者 2026-11-01）。
6. **记账默认生效，整章可以撤销**；核对点不符、与设定冲突、Agent 没把握的进待处理，处理前不生效（开发者 2026-11-02）。

## 备选方案

- **与 nb-story 合成三个来源层（正文、设定、计划）再对齐**：两种视角的出发点不同，对齐太复杂。开发者 2026-10-31 否决，合并以后再看。
- **只靠作者的手记与笔记，不要结构**：没有无限上下文；作者记不住全书，也需要整理好的视图。开发者 2026-11-01 否决。
- **lorebook 加模板引擎，或 lorebook 加按章追加的说明**：数从哪来、哪章改的说不清，只能补充、不能算数。
- **随剧情变化的文字用文本 diff 加三方合并**：合并结果要存下来，作者改一次初值，后面每条改过这段的变更都要合一次；合得上也看不出意思是否过时。
- **记账先审后生效**：作者不想每章逐条看。
- **Agent 不能改作者写的字，只能提建议**（第一轮独立设计的方案）：开发者保留“Agent 可以改”，靠发布通道、改动记录与还原兜底。

## 后果

- 新写的是折叠规则、补丁与核对点、修订与还原、位置模型和记账的校验；行为合同在提案接受、存储（t09）定下之后写成 Spec。
- nb-history 只管正文与手记的文件级历史；记录级的审阅与还原由世界模型自己的修订负责。nb-memory 只考虑复用检索（提案待定项 3，t14 定）。
- 第一版只承诺当前版本的重算确定、修订能还原，不承诺按任意历史版本重新渲染。
- 以后加故事时间、世界线时，换掉位置模块，日志与补丁的形状不变；与 nb-story 合并时，共享出处与位置的写法。
