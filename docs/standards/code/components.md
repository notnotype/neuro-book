# 组件规范

适用：`app/**` 下的 Vue 单文件组件。页面、应用根组件和开发工具自身不受本规范约束。通用与语言规则由 [`README.md`](README.md) 路由；组件的 Vue 用法、CSS 与主题规则见 [`frontend.md`](frontend.md)。

本规范约束组件与外部世界的连接方式。核心判断：组件的真实依赖必须出现在它的调用签名里，否则调用方无法预见、测试无法隔离、状态无法追溯。

## 明面通道与隐藏通道

- **明面通道**只有三种：props、emits、slots。它们是合同，调用方一眼可见，不计入耦合。
- **隐藏通道**是绕过明面通道获取数据或产生影响的任何方式：读写 store、访问浏览器存储、发起请求、注册全局监听、渲染到组件树之外。
- **耦合度 = 隐藏通道数量**。`state:local` 不计入，它不伸出组件之外。
- 组件产生外部影响时发出事件，由父组件或宿主执行；需要外部能力时由父组件通过 props 传入可替换的入口。

## 组件文档

每个组件有一份同名 Markdown 文档与它并列，例如 `PlotTreeView.vue` 对应 `PlotTreeView.md`。文档先于实现写：设计组件时先想清它长什么样、怎么交互、吃什么数据、有哪些状态，再写实现。写多写少见下文的详略分档，但文档本身不可缺省。

文档描述的是当前应该成立的行为，实现与之不符即为缺陷。尚未实现的改进写在「已知偏差」一节明确隔开，不混入正文，避免留下无人知道是否生效的描述。正文里被偏差影响的那句话就地加一句回指，例如「当前实现见已知偏差」——否则照文档写验收用例的人会先失败一次，才找到那一节。订正之后连同回指一起删掉。

这份文档是组件的需求书，判据有两条，都要满足：读的人不看实现就知道这个组件是什么、能做什么、有什么别处没有的特点、用的时候要注意什么；照着它换一套写法能做出行为相同的组件。据此划线——props 的形状、事件携带的数据属于行为，要写；用了哪些库、内部如何推导出结果，换实现即不同，不写。

frontmatter 必须存在，承载能力标签供机器读取。标签为空时同样写出该文件：空标签表示已经确认这个组件没有隐藏通道，与「尚未有人处理」是两种不同状态，报告据此区分。机器扫不出隐藏通道不等于确实没有，藏在多层封装后的请求需要手写标签与实现交叉核对才能发现。

无论哪一档，开头都要有一段话说清这个组件是什么、解决什么问题、有什么别的组件没有的特点。Lab 摆得出组件有哪些状态，摆不出「为什么会有这个组件」，所以这段不能省。

这段之后写多少由 Lab 能否代为演示决定，不由编写者自评：

| 配方 | 开头一段之后的正文要求 |
|---|---|
| 纯零件、受控零件 | 可以不写。组件的状态与边界由 fixture 摆出来，看得见的不必再写一遍。 |
| 领域视图 | 只写演示不出来的部分：隐藏通道理由、不支持的事、数据的语义约束。 |
| 宿主、流式宿主 | 必须写全下列各节。它们不进 Lab，没有任何行为能被演示，文档是唯一说明书。 |
| 配方偏离 | 按「验证」一节推导的可验证程度取档：可完整验证或需预置状态快照的照领域视图一档，只能在真实界面验证的照宿主一档。无论哪一档，都要为使它偏离配方的那条隐藏通道写明理由——偏离本身即是需要交代的事。 |

对不写正文的组件，「先文档后实现」落在先想清楚它有哪些状态、该摆哪几个 fixture，设计动作不减少，只是载体从散文换成场景。

正文用自然语言描述，但 **props、emits、slots 直接写 TypeScript 类型声明**。类型是这三样最准确的写法，翻译成散文只会丢东西——漏掉一个事件，读的人无从发现。类型上用注释写含义、默认值和是否受控。除这些声明外不写实现代码。正文包含：

- **布局**：由哪几块组成及各自职责；哪块固定、哪块伸缩；内容变多时谁先让位；`390×844` 下结构如何变化。后三个问题答不上来说明设计尚未完成。
- **交互**：用户可执行的动作及其结果；键盘可做什么；组件出现和消失时焦点的去向。
- **数据**：props、emits、slots 的类型声明。每项注明含义、是否必填、默认值，以及哪些是受控值（父组件传入且组件自身不修改）；事件补写触发时机。同时声明组件的扩展面——**slots、expose、attrs 是否透传，三样都要写出来，没有就写没有**。「没写」和「没有」是两回事，读的人想加一个提示或拿一下内部状态时，得知道有没有口子可走。
- **状态**：默认、禁用、只读、加载中、出错、空数据各自的视觉与交互表现。
- **不支持**：明确不做的事。不适用的项写成不支持，不留空由使用者猜测。
- **上游边界**：组件封装了第三方库时，写明本组件承诺哪些行为，其余来自该库、不作承诺、升级可能变化。不把上游行为逐条抄进来——抄不全，也会随上游升级静默过期；但也不留给读者猜，读者至少要知道该去问谁。没有第三方依赖就不写这一节。
- **注意事项**：使用这个组件时容易踩的地方，例如与父组件布局的约束、外部依赖的前提、性能或时序上的陷阱。没有就不写这一节，不写「无」。
- **隐藏通道理由**：见下文「需要理由的声明」。

只有在用法反直觉时才给一段最小示例，例如事件命名使得常规的 `v-model` 写法会静默失效。本仓库用 Nuxt 自动注册，没有引入步骤，示例只承载「标签怎么写」这一件事；用法没有意外时不写，类型声明已经够推出来。

无障碍名称、角色与关联关系，以及最小最大尺寸、内容超出时滚动还是裁剪，写入对应的布局或交互一节。

frontmatter 的能力标签和「数据」一节的类型声明都可以与实现机械比对，工具尚未建立，当前靠评审核对。布局、交互与状态的自然语言描述无法自动校验，只能依靠「改行为时先改文档再改实现」这一顺序。缺少文档的组件在报告中列为待声明。

## 能力标签

写在组件文档的 frontmatter 中，取值为下列封闭清单。无隐藏通道的组件标签为空。出现清单未覆盖的通道时更新本规范新增标签，不用近似标签替代，不允许不声明。

| 标签 | 含义 | 计入耦合度 |
|---|---|---|
| `state:local` | 自己持有临时状态，组件销毁即丢失 | 否 |
| `state:shared-read` | 直接读取 store | 是 |
| `state:shared-write` | 直接写入 store | 是 |
| `state:inject` | 通过 provide/inject 获取数据或能力 | 是 |
| `persist:local` / `persist:session` / `persist:idb` | 直接访问对应浏览器存储 | 是 |
| `io:read` | 自己发起读请求 | 是 |
| `io:mutate` | 自己发起写请求，产生不可重放的副作用 | 是 |
| `io:stream` | 自己建立长连接或订阅推送 | 是 |
| `env:timer` | 使用定时器或轮询 | 是 |
| `env:route` | 自己读取路由参数或发起跳转 | 是 |
| `env:global` | 注册全局监听，例如窗口事件或全局快捷键 | 是 |
| `env:clipboard` | 直接读写系统剪贴板 | 是 |
| `env:portal` | 把内容渲染到自身组件树之外 | 是 |

`state:local` 不计入耦合但仍须声明，确定性验证需要知道初始状态。`state:inject` 单列，因为它比 store 更隐蔽：调用方从签名上看不出组件需要什么，只有运行时缺少提供方才暴露。

声明是对实现的如实描述，不是意图。实现用了某条通道而未声明，或声明了实现中不存在的标签，均以实现为准，整份声明不予采信。

## 需要理由的声明

以下情况仅有标签不足，必须在组件文档正文的对应一节同时写明理由。理由是可读文字，用于让后来者判断这条通道是否仍有必要；**理由不改变违规档位，不是豁免机制**。

- `state:shared-read`：读取哪个 store 的哪些字段，以及为什么这些值不能由父组件传入。
- 任何 `io:` 标签：为什么该请求不能由宿主发起并把结果传入。
- `env:portal`：渲染目标位置，以及该位置不存在时的表现。
- 使组件偏离推荐配方的那条隐藏通道：为什么这条通道属于该组件，而不是由父组件通过明面通道提供。

## 推荐配方

| 配方 | 标签 | 耦合度 | 确定性验证 |
|---|---|---|---|
| 纯零件 | 空 | 0 | 可以 |
| 受控零件 | `state:local` | 0 | 可以 |
| 领域视图 | `state:local` `state:shared-read` | 1 | 需预置状态快照 |
| 宿主 | `state:local` `state:shared-read` `state:shared-write` `io:read` `io:mutate` | 4 | 只能在真实界面验证 |
| 流式宿主 | 宿主标签加 `io:stream` `env:timer` | 6 | 只能在真实界面验证 |

- 公共零件目录下只允许纯零件与受控零件，耦合度恒为 0。
- 领域视图是妥协形态：允许使用，但每一处都要写理由，防止读取 store 悄悄扩散。
- 宿主与流式宿主是领域数据的进出口，每个领域只应有个位数个。
- 不属于以上五种、也未命中禁止规则的组合属于配方偏离，只提示不判错。同一种偏离反复出现说明应当新增配方，不是这些组件有问题。

## 禁止规则

**档位 A · 位置类**，与解耦方向直接冲突：

| 规则 | 理由 |
|---|---|
| 公共零件目录下耦合度大于 0 | 公共零件一旦绑定业务上下文就无法复用，公共与专属的边界随之消失。 |
| 非宿主组件声明 `state:shared-write` 或 `io:mutate` | 写操作散落后没有任何一处知道一次操作改了什么，取消、错误恢复与并发控制都无从建立。 |
| 同一领域出现多个宿主 | 两个数据进出口即两个真相源，状态迟早对不上且无法裁决。 |

**档位 C · 焊死类**，未放弃能力但放弃了可替换性：

| 规则 | 理由 |
|---|---|
| 声明 `io:` 但请求入口不可由外部替换 | 焊死后永远无法在确定性环境或测试中替换，等于主动放弃可验证性。 |
| 声明 `env:global` 但销毁时不解除监听 | 组件已消失而监听仍在响应，造成内存泄漏与无法解释的按键行为。 |
| 声明 `env:portal` 但不声明渲染目标 | 目标缺失或变化时浮层位置与主题继承都会出错且难以定位。 |

**档位 B · 组合类**，破坏数据一致性：

| 规则 | 理由 |
|---|---|
| 出现任何 `persist:` 标签 | 组件不直接访问浏览器存储，跨会话保留的值由 store 声明式持久化，组件通过明面通道读写。同一份数据只有一条持久化路径，才不会出现两处写入互相覆盖且顺序不确定。 |
| 同一份数据既由 props 传入又直接读 store | 两条来源并存时渲染结果取决于哪条后更新。这类问题极难定位，因为单看任一条路径都是正确的。 |

**档位 D · 配方偏离**，只提示。

档位顺序为 A、C、B、D。A 在最前因为它直接挡住解耦本身；C 次之因为它改动局部、代价最小，应优先处理；B 更靠后不是危害小，而是常常需要先决定数据该由谁持有。

命中禁止规则时把对应能力上移到宿主，或改为通过明面通道传入。确实无法上移时保留违规状态并写明理由，不引入豁免名单、不修改标签定义、不为单个组件放宽规则。

## 执行方式

只报告，不阻断构建、提交、合并或发布。报告按档位 A、C、B、D 排序，同档位内按耦合度从高到低，使耦合最深的组件排在最前；缺少文档或文档与实现不一致的组件按待声明单列。执行强度的变化需要更新本规范，不由检查工具自行决定。

## 边界

- 本规范只约束组件一侧。store 自身的规矩（哪些允许持久化、持久化哪些字段、谁有权写入）尚无规范，组件层收敛后需要单独补充，不在本规范内建立第二套状态管理约定。
- 组件索引、登记流程和任何一次重构的进度不属于本规范。
- 主题相关行为的变化更新主题规范本身，不在组件声明中建立第二处颜色或主题来源。

## 验证

组件能否在确定性环境下验证由标签推导：不含 `persist:`、`io:` 且不含 `state:shared-write` 的组件可完整验证；含 `state:shared-read` 的需要预置状态快照；含 `io:` 或 `state:shared-write` 的只能在真实产品界面验证。确定性验证环境见 [`ui/component-lab.md`](../../specs/ui/component-lab.md)。

耦合度与档位由检查报告给出，同一组件重复计算结果一致。界面改动另按 [`frontend.md`](frontend.md) 报告桌面与窄屏影响。

完成标准：每个受管组件都有同名组件文档，且文档的能力标签与实现一致；公共零件目录耦合度为 0；非宿主组件不含 `state:shared-write` 与 `io:mutate`；需要理由的声明都有理由；桌面（宽度不低于 1440px）与 `390×844` 下核心操作均可完成，无页面级横向滚动、无导致操作无法完成的遮挡、无未声明的布局位移。
