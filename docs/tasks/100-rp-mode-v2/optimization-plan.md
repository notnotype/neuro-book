# RP 模式运行逻辑优化计划

> 状态：设计确认，按依赖顺序实施。
> 本文整理 2026-07-27 至 2026-07-28 与用户逐项确认的 18 组产品议题，并作为 RP v2 后续重构的执行基准。

## 目标

本轮优化不以“补强提示词”为完成标准，而是把主持主动性、开团确认、事件生命周期、世界演化、角色认知、回滚分支和异常恢复落实为可持久化、可校验、可测试的系统能力。

最先解决的缺陷是：`rp.leader` 在引导尚未结束时擅自宣布开跑，并直接写入 `rp/manual/`、`rp/lorebook/`。修复必须同时具备持久状态、企划版本、用户确认操作和 Bootstrap 技术门禁。

## 一、18 组确认结论

### 1. 主持主动性与待选事件

- 左侧状态栏增加待选事件；默认提供平淡、刺激、危险、不寻常四张。
- 玩家可以选择、保留、放弃、换一批，或指定随机范围后由服务端抽取。
- 普通候选在离开地点后失效；玩家保留的候选继续保存，但触发前重新验证条件。
- 不按每 Tick 强制产出事件。进入新地点、新活动、已有计划到期、玩家主动请求，或连续完成 5 个平淡 Tick 后可以生成。
- 主持可以通过环境、偶遇、天气、机会和麻烦间接干预，但不能替玩家决定行动。
- 玩家自由行动时，主持应提供差异明显的四类发展方向。
- 推进速度与控制方式分开设置；控制支持完全自主、主持建议、大方向委托和随机惊喜。

### 2. 正式事件生命周期

事件状态采用：

```text
available -> saved/selected -> active -> suspended/terminal
```

- 终态包括 `resolved`、`failed`、`missed`、`continued_without_player`、`expired`、`cancelled`。
- 事件可跨多个 Tick，阶段包含入口、介入、发展、关键选择、结果和余波。
- 同时最多 3 个玩家 active 事件；硬性事件到期时可临时成为第四焦点。
- 硬性日程、异常天气、约定和已启动计划必然发生，但不强迫玩家参与。
- `continued_without_player` 不占 active 名额；suspended 事件中的 NPC 默认继续行动。
- 保留事件不设硬上限，但新增时校验合理性；冲突时说明原因并由玩家修改或放弃。
- 选择候选只确定入口，不预设结局。

### 3. 时间、Tick 与跳跃

- Tick 只记录 `startTime` 与 `endTime`；OOC 不推进世界时间。
- 玩家明确给出的时间跨度优先；screenwriter 判断合理耗时，leader 编排，world 记录结算。
- 长时间跳跃一次结算，不逐日生成 Tick；中途遇到不可跳过事件时暂停并询问玩家。
- 玩家离开途中事件后，screenwriter 根据客观时限判断 suspended、failed、missed 或 continued。
- 开始和结束时间进入正式记录，完整结算写入项目运行文件，不挤占对话上下文。

### 4. 惰性世界模拟

- 当前地点与当前事件精细运行；长期不接触的地点停止实时模拟。
- 再次进入时基于上次状态、经过时间和已启动计划进行低精度推演。
- 普通生活变化允许惰性生成；重大死亡、地点毁灭、重大背叛只能来自已启动事件或明确全局事件。
- 长跨度期间使用规则批量结算，再由 Agent 推演重点人物和计划，最后生成一次阶段摘要。

### 5. 层级地图与地点生长

- 地图层级为世界、地区、城镇、街区、建筑、重要子地点。
- 地点状态包含 `rumored`、`discovered`、`familiar`、`unavailable`、`destroyed`。
- rumored 只显示模糊节点与大致方向；秘密路线发现前完全隐藏。
- 玩家可以要求生成地点；与世界冲突时先说明，再由玩家决定是否调整设定。
- 首次抵达自动固化基础信息。只有能持续承载事件、NPC、资源或特殊连接的空间才建立节点。
- 封闭或毁坏地点保留原节点并标注状态。
- screenwriter 提出地点，world 校验、分配稳定 ID 并保存。

### 6. 小说地点导入

- Lorebook、Plot、World Engine 和正文中出现过的地点全部纳入候选。
- 完成盘点后统一让玩家确认删减。
- 信息不完整时支持玩家补充、主持提案、批量授权补全、保持模糊或排除。
- 后台可以导入完整 god-view 地点信息，玩家地图仍按化身认知逐步显示。
- 小说设定冲突标记为 `conflict`，不能由主持静默选择。

### 7. NPC 生命周期与主要角色

```text
临时群演 -> 具名 NPC -> 常驻 NPC -> 主要角色
```

- 群演说出姓名后自动建立最低具名记录，但不等于擢升。
- 具名升常驻、常驻升主要角色均需玩家确认；玩家也可主动登记或擢升。
- 敌人、宿敌和竞争者可以成为主要角色。
- 主要角色总数无硬上限，活跃主要角色软上限默认 8。
- 长期离场转为 `major_inactive`，档案不删除。
- 擢升时允许从历史 Tick、事件和互动摘要补建记忆。
- 擢升建议显示在角色侧栏，不阻塞当前叙事。
- 支持玩家主动提供人设创建角色；actor session 在实际出场时惰性创建。

### 8. 资源、金钱与周期模块

- 资源分为账本型、时间派生型和动态状态型。
- 后台保存精确数值，前台可以显示状态词。
- 金钱第一版采用单货币、单余额、交易流水和周期收入/支出。
- 仅常驻与主要角色维护精确货币；普通 NPC 按身份保存家境，升级时生成合理初始金额。
- 欲望使用 0-100，前台分为平静、微热、亢奋、难耐；整体欲望属于资源，针对某人的吸引属于关系。
- 欲望可以影响倾向，但不能单独替角色决定行为，也不能越过系统硬边界。
- 生理周期是角色可选模块，使用锚点与服务端波动。
- 生育概率由行为风险、周期和措施等计算，再由服务端随机。
- 支持玩家声明自定义资源、效果和增减逻辑；第一版采用声明式配置。

### 9. 关系模型

- 关系采用有方向的八维数据：熟悉、信任、情感、吸引、尊重、依赖、恐惧、敌意。
- 双方关系分别保存，不能镜像覆盖。
- 关系标签独立于数值，可多标签并存；标签必须来自设定或实际互动，不能由阈值自动生成。
- 重要变化记录原因与 Tick。
- 骰子只影响对方是否愿意交流、倾听或继续接触，不能直接建立关系或控制角色。
- 特殊关系允许跨越一般类别边界，但必须符合角色人设、经历与当前状态。

### 10. 认知与可见性

- 世界事实、角色认知、玩家 OOC 认知三层分离。
- 玩家可以查看所有角色的状态，但重要条目默认隐藏；可主动解除隐藏或重新隐藏。
- `user_revealed` 只代表玩家 OOC 知道，不自动成为 `avatar_known`。
- 传闻按相关性惰性传播。
- 系统默认不替玩家决定化身的情感、吸引和信任。
- 回滚后角色失去回滚点之后的记忆，玩家 OOC 认知继续保留。

### 11. 行动判定

- 使用 2d6：容易 5、普通 7、困难 9、极难 11。
- 低目标值 1-2 点为部分成功，低 3 点以上为失败。
- 有利/不利通常调整目标值不超过正负 2。
- 判定前公开目标值、主要风险、成功和部分成功范围，并允许玩家改变行动。
- 失败必须推动局面；条件不变时不能无限重试。
- 玩家行动公开掷骰；NPC 自主行动由 actor/screenwriter 判断，需要随机时由服务端后台执行。
- 对抗只让玩家掷一次，对手能力体现在目标值。
- 天然 12 增加合理优势，天然 2 增加合理复杂后果。
- 部分成功代价由 screenwriter 根据倾向与局面裁定，玩家不能自行挑选。

### 12. 开团引导状态机

开团入口支持引导开团、快速提案和改编现有设定。状态机为：

```text
empty -> source_selected -> premise_ready -> avatar_ready
-> play_style_ready -> systems_ready -> boundaries_ready
-> opening_ready -> reviewing -> confirmed -> bootstrapping -> active
```

- 草案保存在 Project Workspace `.nbook` 运行状态，不在确认前写入正式 `rp/` 内容。
- 每项状态为 `missing`、`provisional`、`confirmed`、`conflict` 或 `disabled`。
- 每轮只问 1-3 个相关问题；玩家一次回答多项时同时更新，允许跳序和返回修改。
- “你来定”只生成 provisional 提案，仍进入最终审阅。
- 草案版本化；确认后修改会使旧确认失效。
- RP 左侧“状态”页的“确认并开团”按钮是唯一确认入口；按钮绑定玩家当前看到的企划版本，leader 没有确认操作，也不能自行宣布确认。
- Bootstrap 校验已确认版本与当前版本一致，失败时拒绝初始化。
- 未完成草案可继续、查看或归档后重开。

### 13. 初始地图与开场事件

- 初始地图规模按实际项目决定；玩家可自行生成地点，也可授权主持生成。
- 开场事件必须在引导中设计，或由玩家明确要求生成。
- 开场生成支持玩家设计、主持候选、指定方向生成和随机惊喜。
- 确认的开场事件在 Bootstrap 后成为第一个 active 事件并占用名额。
- 开场局面稳定前默认不生成普通四卡候选，但玩家可主动要求。

### 14. 修订、回滚与世界切片树

- 区分纠错、设定修订、时间回滚和时间线分支。
- 修订前展示对事件、记忆、关系、资源、地点和后续 Tick 的影响范围。
- 确定性数据自动重算；剧情、人物决定和关系变化由 screenwriter 提出修复方案后确认。
- 被修订历史归档保存；直接状态修改记录为 `gm_override`。
- 完全重复行动沿用原骰；实质改变行动或条件时重新判定，可在开团设置中允许自由重掷。
- RP 界面增加树状世界切片管理器。每个节点最多 4 个直接子分支，后代数量不限。
- 点击旧切片先只读预览；恢复前询问建立安全切片。
- 第五条分支必须由玩家选择替换对象；锁定切片、根切片和 active 切片不能直接替换。
- 分支之间共享客观基础设定，但严格隔离分支后角色记忆。
- 使用阶段性完整切片与中间变化记录的混合存储。

### 15. RP 界面信息架构

- 左侧采用固定概览与“状态、事件、地图、角色”分页。
- 顶部固定显示时间、地点、Tick 状态、推进速度、控制模式和硬性提醒。
- 状态页展示化身资源、环境与持续效果；其他角色折叠显示。
- 事件页依次显示硬性日程、当前事件、待选事件、保留事件、暂停/离场事件。
- active 事件只显示玩家可理解的当前状况、时限和最近变化，不暴露幕后阶段。
- 地图默认层级树，复杂连接可切换关系图。
- 角色按当前场景、主要、常驻、具名、擢升建议和暂时离场分组。
- 普通变化使用角标和轻提示；必须处理的矛盾、跳跃阻断和分支替换才弹窗。
- 窄屏保留紧凑状态条。

### 16. Agent 回合管线与权限

```text
理解玩家行动 -> 读取当前世界切片 -> 条件检查
-> screenwriter 编排 -> actor/extras 反应 -> 必要判定
-> 生成叙事 -> world 原子结算 -> 更新界面
```

- OOC 查询、纠错和状态查看不进入世界推进。
- leader 组织回合并输出最终结果；screenwriter、actor 和 extras 只提交提案；world 是唯一客观状态提交者；服务端负责随机与事务。
- actor 人设与已建立状态优先于 screenwriter 的剧情计划。
- 玩家要求的方向若暂时不合理，leader 说明阻碍并提供逐步到达的建设性路径。
- 回合未提交时修改行动会取消旧回合；已提交后走纠错或回滚。
- 主要角色 actor 失败不能静默代演；普通群演可以由 extras 重建。
- screenwriter 或 world 失败时不提交半成品，并向玩家报告失败阶段、原因、提交状态和恢复选项。
- UI 只显示概括阶段，不展示内部思维或幕后剧情。

### 17. 关注度、运行强度与文件化记录

- 世界对象采用当前焦点、活跃后台、低频关注和休眠四级关注度。
- world 自动调整，玩家可以手动固定；主要角色至少保持低频关注。
- 时间、金钱、周期、硬性日程、候选失效和明确概率优先由确定性程序结算。
- 主要与重要常驻角色独立判断；普通具名 NPC 和群演由 extras 批量处理。
- 多 actor 基于同一回合开始状态并行提案，world 统一解决冲突。
- 运行强度分轻量、标准、深入。UI 直接修改持久变量，每轮读取，不因切换而单独调用 Agent。
- 档位只影响远端世界丰富程度，不能降低当前场景、直接互动角色、硬性事件与客观资源结算。
- 完整结算、运行记录、错误记录和长跳摘要写入项目专用文件；侧边栏按需分页读取，不注入聊天上下文。

### 18. 一致性、异常恢复与长期验收

- 回合状态为 `draft -> running -> awaiting_player -> committing -> committed`，失败和取消为旁支终态。
- 每回合使用唯一 ID；同 ID 重试必须幂等，不能重复扣款、推进时间或更新关系。
- 只有 committed 回合进入正式历史。
- 项目打开、切片切换、长跳、世界修订和提交前执行相应强度的一致性检查。
- 轻微索引/缓存问题可以自动修复；改变剧情、角色或资源的修复必须由玩家确认。
- 数据损坏时依次尝试完整切片、变化重放、上一个已验证切片和问题报告，不能静默编造。
- 叙事与 world 状态不一致时，展示前重新生成；提交后发现则让玩家选择以哪一侧为准或回滚。
- 失效候选、地点和角色标为不可用并显示玩家可知原因，不直接消失。
- 硬性完成标准：连续 100 Tick 无状态损坏、无重复结算、无跨分支记忆泄漏、无 leader 越权开团。
- 长期场景至少覆盖 20 个具名角色、30 个地图节点、10 个周期资源、3 条时间线、多次长跳和恢复。
- 测试随机支持固定种子；正常游玩使用服务端随机。

## 二、实施顺序

### P0：基线与契约整理

- 将本文作为当前产品合同，更新 Task 100 与稳定 reference 的交叉链接。
- 标记旧计划中“仅 Prompt 已完成但技术门禁缺失”的能力。
- 保持当前真实运行缺陷与测试证据可追溯。

### P1：开团状态、版本确认与 Bootstrap 门禁 ✅

- 在 Project Workspace `.nbook/rp/intake/` 建立版本化草案状态。
- 提供读取、字段更新、确认、开始 Bootstrap、失败回退和激活操作。
- 最终确认必须经过用户可见审批，Agent 不能自行伪造。
- 草案变更递增版本并使旧确认失效。
- Bootstrap 和正式 RP 写入只接受“当前版本已确认”的状态。
- 增加行为测试：缺字段、冲突、旧版本确认、Agent 自行开团、重复调用和失败恢复。

### P2：回合事务与文件化更新账本 ✅

- 建立唯一 turn ID、状态机、幂等提交和恢复扫描。
- 结算、运行记录、错误记录写入 Project Workspace `.nbook/rp/` 专用日志。
- 世界状态更新窗口按需读取，不把完整结算注入聊天上下文。

### P3：正式事件与主动主持 ✅

- 实现候选事件、服务端随机、保留/失效、active 上限、硬性事件和完整生命周期。
- 实现平淡 Tick 计数与事件触发器。
- 约束 screenwriter 提案、leader 展示、world 注册的权限边界。

### P4：时间、资源、关系与认知 ✅

- 实现时间跨度、长跳阻断、周期批量结算和自定义声明式资源。
- 实现八维有向关系、标签、原因账本与三层认知。
- 将生理周期、生育概率和其他随机结果迁移到服务端规则层。

### P5：地图与 NPC 生命周期 ✅

- 实现层级地图、地点状态、秘密路线、自动固化和小说地点候选导入。
- 实现群演到主要角色的升级链、确认门禁、擢升建议和 inactive 状态。

### P6：回合编排与关注度 ✅

- 把 P0-P6 旧 Prompt 流程升级为代码可见的运行阶段与统一事务。
- 实现 actor 同快照并行提案、world 冲突处理、失败报告和中断恢复。
- 实现四级关注度、三档运行强度和长跳惰性推演。

### P7：RP 侧边栏与世界更新窗口 ✅

- 重构状态、事件、地图、角色四分页。
- 增加运行进度、运行概况、待选事件操作和强度切换。
- 新增文件化更新记录的按需查看窗口。

### P8：世界切片树 ✅

- 建立树形切片索引、四分支限制、锁定、替换、安全切片和只读预览。
- 实现恢复、分支后认知隔离、随机记录处理和混合存储。

### P9：一致性与长期验收 ✅

- 建立 schema/引用/时间/资源/切片/认知一致性检查。
- 完成 100 Tick 数据面回归、固定随机种子和三档运行强度验证。

## 三、当前实施点

P1-P9 已完成代码实现。P9 新增 light/standard/deep 三档跨 store 审计，覆盖 schema、回合幂等、时间资源、地图 NPC、事件关注度、关系认知、pipeline/正文、World Engine SQLite 与切片材料；仅自动重建可由 parentId 唯一推导的切片 childrenIds。切片损坏按“目标材料 → 祖先验证 → 问题报告 → 玩家选择”处理，绝不静默编造或自动回退。测试固定随机通过 AsyncLocalStorage 隔离，仅在测试环境生效。100 Tick 规模场景已覆盖 20 个具名角色、30 个地图节点、10 个周期资源、三档强度、四次长跳和三条时间线，并以 deep healthy 收口。

2026-07-29 首次服务器实测发现九个 RP 多操作工具把根级 `Type.Union` 直接投影为 Provider function parameters，生成的 schema 只有 `anyOf`、没有 `type: "object"`，导致 `rp_intake` 在执行前收到 400。现已统一将 union 投影为模型可见 object 属性并集，原 union 转为执行期 `validationSchema`；工具注册表新增 object 根类型 fail-fast，内置工具契约测试遍历全部 schema。剩余为用户决定是否执行浏览器交互验收，不属于 P9 数据面实现阻塞项。

同日 RP 页面实测发现按 `v-if` 离开并重新进入后，`AgentChatSurface` 以 `active=true` 初始挂载，但原非 immediate active watcher不会恢复 session；新建操作因附带 refresh 才让旧列表重新出现。现已在通用对话面 `onMounted` 补齐初始 active 的幂等 `ensureSessionReady()`，保留 watcher 处理后续切换，并新增 RP 重挂载合同测试。session 数据与服务端筛选从未丢失。

后续开团实测确认 `rp.leader` 在 `review` 后漏调 `confirm`、直接尝试 `begin_bootstrap`，服务端虽正确拒绝，但前端没有任何确认入口；同时通用前端会丢弃 formSpec 的 `layout=dialog`，任务文档所述弹窗并未实现。当前确认权已从 Agent pending 流程迁到 RP 左侧状态页：`reviewing + version` 持久状态直接驱动按钮，玩家 API 按可见版本确认，主持回合结束自动刷新状态，确认后在主持空闲时自动发送可审计回执续跑。即使页面切换、服务器重启或主持漏调工具，按钮仍可从持久状态恢复。
