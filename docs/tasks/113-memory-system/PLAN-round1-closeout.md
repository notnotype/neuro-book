# PLAN：正式实现第一轮收口

**目标**：让 nb-memory 库本身达到可交付状态——能力补齐、有可信新基线、文档定稿。

**范围边界**：主仓集成**不在本轮**。它依赖用户对 subject 侧路线（换用 nb-memory vs 原地移植偷设计）的拍板，那个分叉在 Task 113 TODO 里挂了很久，属于另一个量级的工作。

**用户拍板**（2026-08-01）：
- describedAs 接入方式 = **`search()` 内兜底优先**（不是补规划器 + `--planner`）
- 收口边界 = **nb-memory 库收口**

## 背景：为什么是这两条

2026-08-01 回归评测（见 `nb-memory/docs/reports/2026-08-01-round1-regression.md`）定位到：

1. **瓶颈在召回不在时间语义**——DeepSeek 那轮 10 道错题里 8 道判词是「回答称无法确定」，as-of 泄漏率 0.0% 跨全部跑次稳定。
2. 其中 p018 / p021 / p037 三道是同一个病：**查询侧不含专名时主体锚定整条失效**。已用离线实验证明**主体解对则答案在 top-5**。
3. 缺口已实现（`179042c` `findSubjects.describedAs`），但**没接进评测路径**，效果未量化。

制定计划时的关键调研发现：**两个规划器（启发式 / LLM）都不产出 `describedAs`**，所以「把查询计划接进评测」这一步单独做完，新能力仍然不会被触发。而 `search()` 里主体锚定只有一个入口（`src/index.ts:365`），且 `queryVec` 在上一行（`:361`）已经算好——在那里兜底是**零额外网络调用**的。

## 批次 A：describedAs 接进 search()

### A1. 兜底解主体（`nb-memory/src/index.ts`，约 40 行）

在 `index.ts:365` 的 `mentionedIn` 之后加一条：字面路解不出任何主体时，用已算好的 `queryVec` 走描述索引。

三个设计点先定死：

- **触发条件保守**：只在 `mentioned` 为空时兜底，不做「总是解 + 合并」。后者会改变所有已有查询的锚点集合，把一次能力验证变成全面回归。
  **代价必须写进注释**：问题里只要提到任意一个主体名，兜底就不触发，哪怕真正问的是另一个没被点名的人。
- **必须传 `asOf`**：描述条目带 tick 与失效区间，传了坐标 `passesFilter` 才会挡住未来版本。**这是 as-of 红线上的一条新路径**。
- **上限对齐现有 `slice(0, 3)`**，不另立数字。

### A2. bench 开关（`nb-memory-bench`）

`NbMemoryEngine` 收 `resolveByDescription` 布尔，`run.ts` 加 `--describe on|off`（默认 off），并把它写进 `runDir` 名字——否则两组结果目录混在一起没法回溯。

### A3. 测试（`nb-memory/tests`）

- **红线**：兜底不产生 as-of 泄漏——描述在 t=50 才更新，`asOfTick=40` 的查询不能靠新描述解出主体。
- 字面路能解出主体时不触发兜底。

### A4. 验证跑（约 80 分钟）

跑一轮 `--describe on`。**主判据不是整体指标，是三道靶子题是否翻转**：

| 题 | 现状 | 期望 |
| --- | --- | --- |
| p018 匿名账号叫什么 | 答「无法确定」 | 解出苏天晴 → 别名在主体卡里 |
| p021 南嘉鱼是谁 | 答「无法确定」 | 描述解出主体 |
| p037 猫娘兽人与风信子什么关系 | 答「无法确定」 | 已离线证明主体解对则答案在 top-5 |

靶子翻转是二值观察，**单跑就能读**——这三道现在明确是「没召回」，翻转即直接证据。整体指标只作副判据，确认没有副作用（**泄漏率必须仍是 0**）。

## 批次 B：按 A4 结果分叉

- **靶子翻转** → 用 A4 的**实际相似度分布**定 `describedAs` 的下限（ADR 0005 未决 #5 残留项）。这个数字之前拒绝拍脑袋，现在有数据支撑。
- **靶子没翻** → 先离线复现（用已落盘的库，零成本），定位是解不出主体、还是解对了但第二跳没打中。**不加码猜测，先看数据**。

## 批次 C：新基线

- **C1**：DeepSeek 双跑取均值（`--describe on`），约 2.7 小时。加上 A4 的 on 跑与已有的 `2026-08-01T13-22` off 跑，形成 off 1 轮 / on 2 轮的对照。
  > 严格双跑 A/B 要 4 轮（5.3 小时）。**不做**：off 侧的能力边界已经摸清（8 道错题是「没召回」），再跑一轮 off 的信息量低于成本。
- **C2**：更新 `compare.md` 与回归报告，把 DeepSeek + describe on 定为新基线，写明口径与历史 mimo 跑次断裂。

## 批次 D：文档定稿

README 公开 API 合同、ADR 0005 未决项收口、回归报告补 A/B 结论。这是「库收口」的实际交付物。

## 明确不做（连同理由）

| 项 | 理由 |
| --- | --- |
| 补规划器产出 `describedAs` + 接 `--planner` | 用户已选兜底优先。两个变量同时变会让归因不清；等兜底净效果到手再单独排 |
| Calendar 抽独立包 | 本语料没有 `instant`，抽包对评测零影响。属能力扩展不属收口 |
| 检索命中率其余病灶（state topic 措辞不匹配、取代链 view 跑题） | 一个在检索侧一个在抽取侧，都是独立课题，塞进收口会让批次失控 |
| 评测工具断点续跑 | 换 DeepSeek 后重试从 130 次降到 1 次，紧迫性大幅下降 |
| 方案 A、A/B 计划质量离线对照 | 随查询计划那条线一起排 |

## 成本与风险

- **总评测时间约 4.2 小时**（A4 一轮 + C1 两轮），代码工作量小（约 60 行 + 测试）。
- **主要风险**：兜底解出错误主体，把第二跳锚偏，反而让原本能答对的题变差。保守触发条件把风险限制在「原本就没有锚点」的查询上——那些查询现在的表现是「答不知道」，很难更差。
- **次要风险**：DeepSeek 端点稳定性。今天一轮只重试 1 次，但样本只有一轮。

## 批次 A'：路线修正——改由规划器抽指代短语（2026-08-01）

**批次 A 的验证结论是负面的，且推翻了拍板前提。** 记录全过程，因为负面结论本身是产出。

### 发现 1：靶子清单本身是错的

A4 跑到第 4 批时停掉，核对真实注册表后发现：

- **p018 不是靶子**：问句里有「苏天晴」，且「魔法少女狐狐official」**已登记在别名里**（t≥160），主体卡会带上它。答不出另有原因。
- **p037 是靶子，但保守触发条件下不触发**：「风信子」是主体的**主名**，字面路解得出。

模拟 `mentionedIn` 对全部 10 道错题的解析：**只有 p021 一道「字面解出 0 个主体」**。「仅在空手时兜底」覆盖面几乎为零。

### 发现 2：改成「补齐锚点空位」仍然失败

补进来的是白貂精灵，不是南嘉鱼。对照实验定位根因：

| 输入 | 解出结果 |
| --- | --- |
| 整句「…猫娘兽人，与魔法少女风信子之间是什么关系？」 | ✗ 风信子 / 白貂精灵 / 花铃 |
| 「主角重生后在学校认识的猫娘兽人」 | ~ 第 2 |
| 「学校认识的猫娘兽人」 | ✓ **第 1** |
| 「深蓝色头发的猫女」 | ✓ **第 1** |
| 「会说话的黑色古书」 | ✓ **第 1** |

**描述索引本身工作良好，它要求输入是「指代短语」而非整个问句**——问句里另一个实体与疑问句式会把整句向量带偏。

**结论：「search() 内兜底」路线的前提不成立。** 它跳过规划器就只能灌整句，而整句是无效输入。抽指代短语这步绕不过去，而它正是规划器的职责。用户据此改选原选项 1（补规划器 + 接 `--planner`）。

代价：省下了 80 分钟的评测——离线实验约 10 分钟、零 chat 调用就得出了结论。

### 已落地

- `resolveByDescription`（补齐锚点空位版）+ 测试，**默认关闭**，保留为对照项；README 记下上面那张负面结论表
- LLM 规划器 prompt 加 `describedAs`，并把实测结论写进提示词（只写指代短语、不要整句、不要带上问句里点了名的另一个实体，附三个正反例）；规划准则去掉「有时间线索才用 findSubjects」这条（p037 这类关系题没有时间线索，旧准则下模型根本不会走这条）
- bench 接 `--planner llm`；计划里的 as-of 由 bench 强制覆盖而非交给模型填——探针的 `asOfTick` 是硬约束，让模型猜等于把泄漏风险交给提示词

### 离线预验（DeepSeek 作规划器，3 道靶子）

| 题 | 抽出的 describedAs | 解出主体 | 结果 |
| --- | --- | --- | --- |
| p037 | 「学校认识的猫娘兽人」 | 南嘉鱼 | **目标命中第 1–4 位** |
| p021 | 「君子有酒」（是署名不是描述） | 风信子（错） | 答案仍在第 2 / 5 位 |
| p018 | 未出 findSubjects（问句有专名，合理） | — | 未命中 |

### 顺带修掉一个我自己引入的缺陷

诊断 p018 时发现：先前那次「主体卡要服从 sources 过滤」的改动，会让规划器随手给个 `sources: ["state"]` 就把主体卡连带丢掉，**而答案常常正在卡里**（p018 的答案就是苏天晴的一个别名）。判据改对：主体卡是**上下文注入**而非被检索的层，只在「内部解主体」（`sources` 恰好只要 `subject`）时关闭。

### A4' 评测结果（`2026-08-02T00-16-47`，`--planner llm`）

对照同模型的 off 跑（`2026-08-01T13-22`）：

| 指标 | off | planner llm |
| --- | --- | --- |
| recall | 75.0% | **87.5%** |
| entity | 89.5% | 89.5% |
| asof | 62.5%（计 8） | 28.6%（计 7） |
| revision | 50.0%（计 12） | 36.4%（计 11） |
| as-of 泄漏率 | 0.0% | **0.0%** |
| revision 陈旧率 | 25.0% | 41.7% |
| 污染率 | 2.1% | 6.3% |
| **检索 p50** | 134ms | **8080ms** |

**主判据（靶子翻转）达成**：

| 题 | off | planner | 说明 |
| --- | --- | --- | --- |
| p037 | wrong | **correct** | 答「南嘉鱼是风信子（南小风）的姐姐」——与离线预验的机制一致 |
| p018 | wrong | **correct** | 翻转来自主体卡注入缺陷的修复（答案是苏天晴的一个别名） |
| p021 | wrong | wrong | 规划器把署名「君子有酒」当成描述，主体解错 |

**副判据（整体）不可裁决**：全题迁移 = 变好 5 / 变差 9 / 不变 34，净 −4。但：

- 变差的 9 道集中在 asof(3) 与 revision(4)——**正是 ADR 0003 记录的小样本高方差区**（计分题只有 7–11 道）。
- 其中 p014 / p028 已核实是**判卷翻转**：两轮答案内容几乎一样（都是「无法确定 + 只知道 X」），检索片段也高度相似，判卷模型给了不同结果。
- 按 ADR 0003 方法论，单跑不构成裁决。

**唯一确定的负面事实是成本**：检索 p50 从 134ms 涨到 8080ms（**60 倍**），来自每题一次规划调用。这个数字不受判卷噪声影响。

### 判读与决定

- `describedAs` 经规划器抽短语后**机制上确实生效**——p037 翻转 + 离线实验独立证实（解出南嘉鱼、目标命中前 4 位），这个结论不依赖判卷。
- 但整体收益在当前题量下测不出来，而代价（60 倍延迟）是确定的。**因此 planner 不作为默认路径**，保留为可选；**基线仍用 off 配置**。
- 记为下一轮候选：**混合策略**——先走 off，仅在字面路解不出主体（或问句检测到无专名指代）时才升级到规划器。这样把 60 倍代价限制在真正需要的查询上。
- 记为下一轮候选：规划器把「署名 / 代号」误当描述（p021）。prompt 里补反例即可，但改完需要重跑验证，本轮不做。

**遗漏**：本轮没有把生成的查询计划写进 `answers.jsonl`，导致事后无法直接核对每题的计划形状（只能重新调用规划器复现）。下次接入这类路径时应当一并落盘。

## 批次 C1 结果：新基线与真实分辨率（2026-08-02）

DeepSeek `off` 双跑（`08-01T13-22` + `08-02T01-31`）：

| 指标 | 跑1 | 跑2 | **均值** | 散布 |
| --- | --- | --- | --- | --- |
| recall | 75.0% | 62.5% | **68.8%** | 12.5pp |
| entity | 89.5% | 73.7% | **81.6%** | **15.8pp** |
| asof | 62.5% | 85.7% | **74.1%** | **23.2pp** |
| revision | 50.0% | 40.0% | **45.0%** | 10.0pp |
| as-of 泄漏率 | 0.0% | 0.0% | **0.0%** | 0.0 |
| 污染率 | 2.1% | 8.3% | 5.2% | 6.2pp |
| 检索 p50 | 134ms | 105ms | 120ms | 29ms |

**这是本轮方法论上最重要的一个数字：entity 双跑散布 15.8pp**，而 ADR 0003 记的 mimo 时代是 5.2pp。
散布来自**摄入 + 答题 + 判卷三重随机性叠加**，其中摄入最根本——两轮抽取出的 registry / state
内容不同，等于在两个不同的库上答题（摄入耗时 26 分钟 vs 37 分钟）。

**推论：10pp 以内的单跑差异一律没有裁决力。** 这条回头修正了本轮此前的若干读法，也修正了
「DeepSeek 污染率 2.1%」——应为**均值约 5%**（仍远低于 mimo 的 16.7%，方向不变幅度打折）。

**跨全部 5 跑唯一稳定的结论：as-of 时间泄漏率 0.0%**，在计分题数、答题模型、检索路径都变过的
情况下依然为零。

有了散布，§A4' 的 planner 判读也更准了：recall 高于 off 两跑任一（可能真好）、entity 与 revision
落在散布内（不可裁决）、**asof 28.6% 比 off 两跑最低值还低 33.9pp 且超出散布（唯一有退化嫌疑）**。
「planner 不作默认路径」的决定因此更有依据：确定的 60 倍成本 + asof 退化嫌疑 + 其余测不出差异。
